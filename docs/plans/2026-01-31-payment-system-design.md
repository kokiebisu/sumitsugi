# Payment System Design - 決定事項メモ

**作成日:** 2026-01-31
**タスク:** tsumugi-43p - Payment System Integration

## 決定事項サマリー

### 1. 支払いフロー: Option B (Combined Checkout)

**決定:** 引越し費用として一括で徴収（内訳は表示しない）

**内訳（ユーザーには非表示）:**
- 追加清掃費
- 前の住人への支払い
- プラットフォーム手数料

**理由:**
- ユーザーにとってシンプル（項目が多いと払いにくい）
- 一つの金額で完結する方がUX良い
- メルカリ的なシンプルさを重視

### 2. 清掃費モデル: Option A (管理会社が清掃)

**決定:** tsumugiが管理会社の清掃費を代理徴収

**フロー:**
```
次の住人 → tsumugi → 管理会社
         (引越し費用)  (追加清掃費を送金)
```

**理由:**
- 管理会社の協力を得やすい（既存業務の延長）
- tsumugiが清掃業者を手配する必要なし
- 物件ごとに管理会社が設定した金額を使える

### 3. 清掃費の二重構造（重要な気づき）

**通常の賃貸契約:**
- 前の住人の敷金から基本清掃費を差し引き（例: ¥20,000）
- これは変わらない（賃貸契約の一部）

**tsumugiが徴収する追加分:**
- **家具有りの追加清掃費**のみ
- 家具があることで増える作業分を次の住人が負担
- この追加費用を「引越し費用」に含める

**引越し費用の構成:**
```
引越し費用 = 追加清掃費 + 前の住人への支払い + プラットフォーム手数料
```

### 4. 追加清掃費の金額: シンプル定額制

**決定:** ¥5,000-8,000（一律・家具の数に関わらず）

**金額の根拠:**

**ユーザー視点:**
- 家具・引越し代の節約: ¥130,000-350,000
- 追加清掃費 ¥5,000-8,000 は節約額の5%以下
- → 「安い」と感じる心理価格

**実コスト:**
- 清掃業者の時給: ¥3,000-4,000
- 家具有りでの追加時間: 30-60分
- 実コスト: ¥1,500-4,000
- → ¥5,000-8,000 で十分なマージン確保

**シンプルさ重視:**
- 家具の数を数える必要なし
- ユーザーも管理会社もわかりやすい
- システムの複雑性を下げる

**段階制を避けた理由:**
- 家具が1個増えただけで料金変わるストレスを避ける
- 家具の定義が曖昧（何を1個と数える？）
- 計算ロジックの複雑化

### 5. 手数料モデル: Option C + 大家インセンティブ

**前の住人が引越し費用の総額を入力 → システムが分配**

**計算式:**
```typescript
// 前の住人が入力
const handoverFeeTotal = 150000 // ¥150,000

// システムが自動計算
const additionalCleaningFee = 8000 // 固定¥8,000
const landlordIncentive = Math.max(handoverFeeTotal * 0.01, 3000) // 1% + 最低¥3,000
const platformFee = handoverFeeTotal * 0.12 // 12%（仮）
const previousTenantReceives = handoverFeeTotal - additionalCleaningFee - landlordIncentive - platformFee

// 例: ¥150,000の場合
// - 追加清掃費: ¥8,000
// - 大家協力金: ¥3,000（1% = ¥1,500 < 最低保証¥3,000）
// - プラットフォーム手数料: ¥18,000（12%）
// - 前の住人受取: ¥121,000
```

### 6. 大家アカウント: 軽量アカウント → フルアカウント

**フェーズ1（初期）: 軽量アカウント**
- 物件登録時にメールアドレス + 銀行口座のみ
- tsumugiが自動振込（月次 or 取引ごと）
- ダッシュボード不要

**フェーズ2（成長後）: フルアカウント（オプション）**
- 大家用ダッシュボード
- 支払い履歴確認
- 物件管理機能

**理由:**
- 初期は導入ハードルを最小化
- 大家の協力を得やすくする
- プラットフォーム成長後に高機能を提案

### 7. 大家協力金: 1% + 最低保証¥3,000

**計算ロジック:**
```typescript
const landlordIncentive = Math.max(handoverFeeTotal * 0.01, 3000)
```

**金額例:**
- ¥80,000の場合  → ¥3,000（最低保証適用）
- ¥150,000の場合 → ¥3,000（1% = ¥1,500 < 最低保証）
- ¥400,000の場合 → ¥4,000（1% = ¥4,000 > 最低保証）

**根拠:**
- 大家の主なメリットは空室期間短縮（家賃6-10万円の差）
- 協力金は象徴的なインセンティブ（「協力してくれてありがとう」）
- 小額でも¥3,000あれば心理的に受け入れやすい
- tsumugiの競争力維持（手数料を抑える）

### 8. エスクローモデル（引き継ぎ完了後に支払い）

**決定:** メルカリ方式のエスクロー（一時預かり）を採用

**支払いフロー:**
```
次の住人が支払い
  ↓
tsumugiがエスクロー保管（Stripe Connect）
  ↓
引き継ぎ実施（鍵の受け渡し・家具確認）
  ↓
双方が「引き継ぎ完了」ボタンを押す
  ↓ 24-48時間後に自動リリース
前の住人・大家・管理会社に自動分配
```

**理由:**
- **トラブル防止:** 「家具が壊れていた」「約束と違う」リスクを軽減
- **次の住人の安心:** 先払いの不安を解消
- **業界標準:** メルカリ・Airbnbと同じ安心モデル
- **ビジネスメリット:**
  - 運転資金の確保（キャッシュフロー改善）
  - 銀行借入が不要（利息2-3%節約）
  - 銀行との交渉力向上

**注意点:**
- Stripe Connectを使用（tsumugiは直接資金を預からない）
- 資金決済法の規制を回避
- エスクロー期間は短く（24-48時間で自動リリース）

**Float（預かり金）の効果:**
```
想定: 月100件 × 平均¥150,000 × 3日間保管
= 常時約¥1,500,000の運転資金

スケール時: 月1,000件
= 常時約¥15,000,000の運転資金

※利息収入（年0.1%）は微々たるもの
※真のメリットは借入不要による利息節約（年2-3%）
```

### 9. デポジット（予約金）システム

**決定:** 30% + 上下限設定（¥30,000-50,000）

**計算ロジック:**
```typescript
const depositRate = 0.30 // 30%
const minDeposit = 30000  // 最低¥30,000
const maxDeposit = 50000  // 最高¥50,000

const depositAmount = Math.min(
  Math.max(handoverFee * depositRate, minDeposit),
  maxDeposit
)
```

**金額例:**
| 引越し費用 | 30%計算 | 実際のデポジット | 実質率 |
|-----------|---------|-----------------|--------|
| ¥80,000 | ¥24,000 | ¥30,000（最低保証） | 37.5% |
| ¥150,000 | ¥45,000 | ¥45,000 | 30% |
| ¥200,000 | ¥60,000 | ¥50,000（上限） | 25% |

**支払いタイミング:**
```
1. 内見実施
2. 双方が合意
3. デポジット支払い（30%、¥30k-50k）→ エスクロー保管
4. 前の住人は他の候補者を断る
5. 引き継ぎ2-3日前に残額支払い（70%）→ エスクロー保管
6. 引き継ぎ実施
7. 双方が「完了」押下
8. 24-48時間後に自動分配
```

**30%を選んだ根拠:**

**1. キャンセル抑止効果（最重要）**
- ¥45,000は心理的に大きい金額
- 「払った後にキャンセル」がかなり躊躇される
- 10-20%では抑止力が弱い

**2. 前の住人の保護**
- 次の住人がキャンセル時、デポジットが補償金になる
- ¥45,000 ≈ 1-1.5ヶ月分の探し直し時間の価値
- 他の候補者を断った機会損失をカバー

**3. 次の住人の負担感**
- ¥150,000一括より、¥45,000→¥105,000の方が心理的に楽
- 初期費用を分散できる
- 「まず¥45,000で予約」という段階的な意思決定

**4. 業界標準との整合性**
- 不動産の手付金: 5-10%（購入時）
- 賃貸の申込金: ¥10,000-30,000（固定額）
- tsumugiの30%: ちょうど中間で納得感あり

**上下限を設ける理由:**
- **下限¥30,000:** 低額物件でも十分な抑止力を確保
- **上限¥50,000:** 高額物件で次の住人を守る（初期負担を抑える）

**キャンセルポリシー:**
```
デポジット支払い後のキャンセル:
- 次の住人都合: デポジット没収（前の住人への補償）
- 前の住人都合: デポジット全額返金
- 双方合意: デポジット全額返金
```

### 10. 申込金モデル（前の住人ファースト戦略）

**決定:** 申込金¥20,000（非返金）+ デポジット30%（返金可能）

**支払いフロー:**
```
1. 内見 → 双方合意
   ↓
2. 申込金支払い: ¥20,000（固定額・非返金）
   ↓ 即座にStripe Transferで前の住人へ
   前の住人が¥20,000受け取る（確定）
   ↓ 安心して他の候補者を断れる
3. 賃貸審査申し込み
   ↓ 審査期間（1-2週間）
4a. 審査通過 ✅
   ↓
   デポジット支払い: ¥30,000-50,000（30%）
   ↓ エスクロー保管
   （以降、引き継ぎプロセス続行）

4b. 審査落ち ❌
   ↓
   申込金¥20,000は返金なし（前の住人が保持）
   次の住人は¥20,000の損失
   前の住人は¥20,000の補償を得て次の候補者探し
```

**申込金¥20,000の根拠:**

1. **前の住人の機会損失補償**
   - 他の候補者2-3人を断る
   - 審査待ち1-2週間の時間損失
   - 再募集の手間
   - 合計: ¥15,000-20,000相当

2. **次の住人のコミットメント**
   - 内見後なので本気度が高い
   - 引越し費用¥150,000に対して13%
   - 家具・引越し代節約¥100k-300kに対して微々たる額
   - churnは起こりにくい

3. **不動産業界の標準**
   - 賃貸の申込金相場: ¥10,000-20,000
   - tsumugiは上限の¥20,000で適正

**プラットフォームの基本スタンス:**

tsumugiは**前の住人ファースト**を採用（Airbnbのホスト重視戦略と同様）

**理由:**
- 供給側（前の住人）を守ることで供給が増える
- 物件数が増えれば需要（次の住人）は自然とついてくる
- 前の住人の方がリスクが高い（時間的プレッシャー、退去期限）

**具体的な施策:**
```typescript
// 1. 申込金は即座に前の住人へ
await stripe.transfers.create({
  amount: 20000,
  destination: previousTenantConnectAccountId,
  immediate: true
})

// 2. 引き継ぎ日調整は前の住人の都合優先

// 3. トラブル時は前の住人を信じる
//    （残置物同意書を証拠基準とする）

// 4. エスクロー解放は予定通り
//    （明確な詐欺でない限り）
```

**次の住人がchurnしない理由:**

内見後の心理状態:
- 時間・交通費を投資済み
- 感情的にコミット（「ここに住みたい」）
- 引越し費用¥150,000払う覚悟がある
- 家具・引越し代¥100k-300k節約できる

→ ¥20,000は誤差の範囲、問題にならない
