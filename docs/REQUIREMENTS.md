## 1. プロジェクト概要

### 1.1 プロジェクト名

**tsumugi（紡ぎ）**

### 1.2 コンセプト

暮らしを引き継ぐプラットフォーム

### 1.3 サービス概要

単なる物件のサブリースではなく、**家具・インテリア・ライフスタイルそのもの**を引き継ぐサービス。前の住人が築いた暮らしを次の住人へ繋ぐことで、空間の価値を最大化する。

---

## 2. 目的と背景

### 2.1 課題

- 引越し時の家具・インテリアの処分問題
- 理想的な空間探しの難しさ
- 短期〜中期の住まい探しの選択肢の少なさ

### 2.2 解決策

- 家具・インテリア付きの物件をそのまま引き継げる仕組み
- 前の住人のライフスタイルを可視化し、マッチングを促進
- 1〜6ヶ月の短期〜中期契約に対応

### 2.3 目標

- 暮らしを引き継ぐ人同士のコミュニティ形成
- 持続可能な暮らしの提案
- 空間の価値の最大化

## 3. スコープ

### 3.1 MVP（最小リリーススコープ）

> プロダクトミーティング（2026-02-06）にて全ペルソナ合意。
> 選定基準：「初めて使う人が信頼できる最小限」
>
> **信頼の連鎖（ペルソナ合意の核心）：**
> 承認バッジの機能を作っても、承認を取るための資料がなければバッジは永遠に「未承認」。
> 次の住人は不安になり問い合わせしない。前の住人にも問い合わせが来ない。誰も使わない。
> → B2B信頼インフラ（PDF自動生成・使い方ガイド）はMVP必須。

**コア機能：**

- 物件情報の表示（一覧・詳細・画像ギャラリー・テイスト検索・暮らしストーリー）
- 物件登録・管理機能（新規登録・編集・ステータス管理）
- 問い合わせフォーム + 問い合わせ一覧（シンプルなリスト表示）
- 基本的な認証機能（サインアップ・ログイン・ログアウト・セラー化）
- アカウント機能（プロフィール表示・編集）
- 大家承認ステータス表示（バッジ・バナー）
- 退去日フィールド + 最低猶予期間チェック（F-501, F-502）

**信頼・安心感インフラ（2026-02-06 追加）：**

- 使い方ガイドページ（F-701）— 問い合わせ〜入居の8ステップを図解
- PDF自動生成（F-611, F-612, F-616）— リスティングデータから2段階で自動生成
  - 出品時：オーナー説明資料（F-611）、仲介向け物件シート（F-616）— 暫定家具リスト
  - 内見後・家具リスト確定時：残置物同意書（F-612）— 確定家具リスト＋署名欄
- 管理会社向けFAQ（F-615）— 静的ページ
- 問い合わせ受付自動通知メール（F-204）— 問い合わせ送信時の確認メール

### 3.2 Phase 1 Post-MVP（MVP後に段階的追加）

MVPリリース後、利用実績に応じて段階的に追加する機能群。最初の数件は手動対応で代替可能と全ペルソナが合意。

- 決済システム（Stripe Connect, エスクロー, 多者間分配）→ 最初は手動決済で対応

- 引き継ぎフロー可視化の残り（ステップインジケーター F-711〜F-712, 支払いタイムライン F-713, 費用の仕組み説明 F-702, 所要期間の目安表示 F-703）→ 手動案内で代替

- マッチング促進（即入居ラベル, 入居可能日フィルター F-507〜F-508）→ 物件数が増えてから
- 最終手段（緊急引き取り案内, 処分業者リスト F-509〜F-511）→ 手動対応で代替
- 内見負担軽減（FAQ機能, 内見承認制 F-801〜F-804）→ 問い合わせフォームで代替

## 4. ユーザー種別

### 4.1 ユーザーモデル（Airbnb風）

全ユーザーは入居希望者として登録し、暮らしを譲る側の登録で`isSeller=true`に切り替わる統一モデル。

**User（基本属性）**:

- id: UUID形式
- email: メールアドレス
- name: 氏名
- phone: 電話番号
- avatarUrl: プロフィール画像URL（任意）
- createdAt: 作成日時
- authProvider: 認証プロバイダー（email/google/facebook/apple）
- emailVerified: メール確認済みフラグ
- isSeller: セラーフラグ
- sellerProfile: セラープロフィール（isSeller=trueの場合のみ）

### 4.2 前の住人（Seller）

セラー登録済みのユーザー（`isSeller=true`）。自分の物件をリスティングできる。

**重要:** セラー登録済みのユーザーも、他の物件では次の住人として暮らしを引き継ぐことができる。「前の住人」「次の住人」はロールであり、ユーザーの固定的な分類ではない。

**SellerProfile（前の住人プロフィール）**:

- occupation: 職業
- bio: 自己紹介
- socialLinks: SNSリンク（Instagram, Twitter, YouTube, TikTok, Website）
- yearsSelling: 活動歴（年数）
- sellerSince: セラー登録日

**Phase 2以降で実装予定:**

- rating: 評価（1-5）
- reviewCount: レビュー数

### 4.3 次の住人

暮らしを引き継ぐ側のユーザー。**すべてのユーザー**（`isSeller`の値に関わらず）が次の住人として物件に問い合わせできる。セラー登録済みのユーザーも、自身が登録した物件以外では次の住人として活動できる。

#### 5.8.1 管理会社連携（Phase A: 資料・テンプレート提供）

Phase 1で管理会社を味方につけるための資料群。PDF自動生成により管理会社の作業負担をほぼゼロに。

> **2段階PDF自動生成（2026-02-06 プロダクトミーティング決定）：**
>
> 管理会社・オーナーの意思決定は2段階で進む。PDFもそれに合わせて自動生成する。
>
> **Stage 1: 出品時（暫定版）**
>
> - オーナー説明資料（F-611）：リスティングデータ（物件概要・暫定家具リスト・退去日）を自動流し込み
> - 仲介向け物件シート（F-616）：同上
> - → 管理会社がオーナーの事前了承を取るために使用
> - → 承認ステータス: `pending` → `conditional`
>
> **Stage 2: 内見後・家具リスト確定時（確定版）**
>
> - 残置物同意書（F-612）：次の住人と合意済みの確定家具リスト＋条件＋署名欄を自動生成
> - → オーナーが印刷・手書きサインして正式承認
> - → 承認ステータス: `conditional` → `approved`

#### 5.8.4 B2B戦略ロードマップ

**Phase A（立ち上げ期: 物件0-20件）**

- 管理会社: フィー¥3,000/成約で引き込む
- 仲介会社: 物件リスト手動共有
- 管理会社の作業負担: 約30分/件（資料・テンプレート提供で削減）
- tsumugiが提供: オーナー説明PDF、同意書テンプレート、残置物チェックリスト、日程調整案

**Phase B（成長期: 物件20-50件）**

- 管理会社: フィー¥1,500/成約に縮小
- 仲介会社: API連携検討
- 管理会社の作業負担: 約15分/件（一部テック自動化）

**Phase C（成熟期: 物件50件以上）**

- 管理会社: フィー廃止 → データ提供モデル（空室短縮データ等）
- 仲介会社: ダッシュボード提供
- 管理会社の作業負担: 約10分/件（ほぼ自動化）

## 11. 引き継ぎフロー

物件の引き継ぎは以下の8ステップで行われる:

1. **物件登録・公開** - 前の住人が物件情報を登録し公開。オーナー説明資料PDF（F-611）が自動生成される
2. **大家事前了承**（推奨）- 管理会社がPDFをオーナーに転送し事前了承を取得（承認ステータス: `conditional`）
3. **問い合わせ** - 次の住人からの問い合わせ受付（自動通知メール F-204）
4. **内見調整** - 内見日程の調整
5. **内見実施** - 実際の物件見学。前の住人と次の住人で引き継ぐ家具を確定
6. **家具リスト確定・大家正式承認** - 残置物同意書PDF（F-612）が自動生成。オーナーが署名して正式承認（承認ステータス: `approved`）
7. **契約** - 賃貸契約の締結（管理会社/仲介会社が主導）、引越し費用の支払い（tsumugi経由）
8. **引き継ぎ** - 物件・ライフスタイルの引き継ぎ完了

### 所要期間の目安

| 区間               | 目安         |
| ------------------ | ------------ |
| 問い合わせ〜内見   | 3〜7日       |
| 内見〜契約申し込み | 1〜7日       |
| 契約〜引き継ぎ     | 1〜2週間     |
| **全体**           | **2〜4週間** |

※ 上記はあくまで目安。大家承認の取得状況や賃貸審査の進捗により変動する。

### 契約フローの役割分担

tsumugiは「暮らしの発見・マッチング・家具引き継ぎ」を担い、賃貸契約は従来通り管理会社/仲介会社が主導する。

| フェーズ             | 主体                 | tsumugiの関与          |
| -------------------- | -------------------- | ---------------------- |
| 物件発見・問い合わせ | tsumugi              | マッチング・内見調整   |
| 賃貸契約             | 管理会社 or 仲介会社 | 契約先の案内・誘導のみ |
| 家具引き継ぎ決済     | tsumugi              | 決済処理・エスクロー   |

### 大家承認について

大家承認は2段階で進む（プロダクトミーティング 2026-02-06 合意）：

**Stage 1: 事前了承（出品時）**

- 物件登録時に大家承認は必須ではない（`pending`でも公開可能）
- 出品時にオーナー説明資料（F-611）が自動生成される
- 前の住人 or 管理会社がPDFをオーナーに転送し、事前了承を取得
- 了承後、承認ステータスを `conditional` に更新 → 「条件付き承認」バッジ表示

**Stage 2: 正式承認（内見後・家具リスト確定時）**

- 次の住人と合意した家具リストが確定した段階で、残置物同意書（F-612）が自動生成される
- オーナーが印刷・署名して正式承認
- 承認ステータスを `approved` に更新 → 「✓ 大家承認済み」バッジ表示

**ステータスとバッジの対応：**

| ConsentStatus | バッジ表示                   | 意味                                   |
| ------------- | ---------------------------- | -------------------------------------- |
| `pending`     | 表示なし or グレー「要確認」 | 未確認（デフォルト）                   |
| `conditional` | 黄色「条件付き承認」         | オーナー事前了承済み、家具リスト未確定 |
| `approved`    | 緑「✓ 大家承認済み」         | オーナー正式署名済み                   |
| `rejected`    | 赤「承認不可」               | オーナーが拒否                         |

- 物件詳細ページでは、承認ステータスに応じてバナーを表示し、次の住人に期待値を伝える

## 12. 決済システム

### 12.1 概要

tsumugiの決済システムは、次の住人から前の住人・大家・管理会社への複数者間の資金分配を安全かつ自動的に処理します。

### 12.2 決済プロバイダー

- **Stripe Connect**: エスクロー機能を活用した多者間決済を実現

### 12.3 引越し費用の構成

次の住人が支払う「引越し費用」の内訳（ユーザーには一括表示）:

```
引越し費用 = 追加清掃費 + 前の住人への支払い + 大家協力金 + プラットフォーム手数料
```

**金額例（引越し費用 ¥150,000 の場合）:**

- 追加清掃費: ¥8,000（固定額）
- 大家協力金: ¥3,000（引越し費用の1%、最低保証¥3,000）
- プラットフォーム手数料: ¥22,500（15%）
- 前の住人受取: ¥116,500

**管理会社フィーについて:**

管理会社紹介フィー（F-601: ¥3,000/成約）は上記の引越し費用分配とは**別枠**。プラットフォーム手数料からtsumugiが負担し、エスクロー解放時にStripe Transferで管理会社へ送金する。次の住人・前の住人の受取額には影響しない。

### 12.4 支払いフロー

#### 1. 申込金（¥20,000）

内見後、賃貸審査申し込み時に支払い:

- **金額**: ¥20,000（固定額）
- **性質**: 非返金
- **分配**: 即座にStripe Transferで前の住人へ
- **目的**: 前の住人の機会損失補償、次の住人のコミットメント確保

#### 2. デポジット（30%）

賃貸審査通過・契約締結後に支払い:

- **金額**: 引越し費用の30%（最低¥30,000、最高¥50,000）
- **性質**: 返金可能（キャンセルポリシーに基づく）
- **保管**: Stripe Connect でエスクロー保管

#### 3. 残額（70%）

引き継ぎ日確定時に支払い:

- **金額**: 引越し費用の70%
- **性質**: 返金可能（キャンセルポリシーに基づく）
- **保管**: Stripe Connect でエスクロー保管

#### 4. エスクロー解放

引き継ぎ完了後、双方が「完了」確認:

- **待機期間**: 24-48時間（異議申し立て期間）
- **自動分配**: 前の住人・大家・管理会社へ自動送金

### 12.5 キャンセルポリシー

**申込金支払い後のキャンセル:**

- 次の住人都合: 申込金¥20,000は返金なし（前の住人が保持）
- 前の住人都合: 申込金¥20,000は全額返金
- 審査落ち: 申込金¥20,000は全額返金（審査結果は次の住人の責によらないため）

**デポジット/残額支払い後のキャンセル:**

- 次の住人都合: デポジット没収（前の住人への補償）
- 前の住人都合: デポジット・残額 全額返金
- 双方合意: デポジット・残額 全額返金

### 12.6 データモデル拡張

決済システム実装のため、以下のテーブルが必要:

**Payment（支払い）:**

- `id`: 支払いID
- `propertyId`: 物件ID
- `userId`: 支払者ID（次の住人）
- `type`: 支払い種別（`application_fee` | `deposit` | `remaining`）
- `amount`: 支払い総額
- `stripePaymentIntentId`: Stripe PaymentIntent ID
- `status`: ステータス（`pending` | `succeeded` | `failed` | `refunded`）
- `createdAt`: 作成日時

**Transaction（分配ログ）:**

- `id`: 取引ID
- `paymentId`: 支払いID
- `recipientType`: 受取人種別（`previous_tenant` | `landlord` | `property_management` | `platform`）
- `recipientId`: 受取人ID
- `amount`: 分配金額
- `stripeTransferId`: Stripe Transfer ID
- `status`: ステータス（`pending` | `succeeded` | `failed`）
- `createdAt`: 作成日時

**StripeAccount（Stripe Connect アカウント）:**

- `id`: アカウントID
- `userId`: ユーザーID
- `stripeAccountId`: Stripe Connect Account ID
- `accountType`: アカウント種別（`previous_tenant` | `landlord` | `property_management`）
- `onboardingCompleted`: オンボーディング完了フラグ
- `createdAt`: 作成日時
