## 1. 新規技術決定

### T-9: 画像アップロード遅延化 + R2削除機能

**背景:** 大株主からの指摘。現状の出品フォームでは画像選択時に即座にR2アップロードされるが、(1) ダイアログキャンセル時に孤児ファイルが発生する、(2) 画像変更・削除時にR2から削除されない。

**決定内容:**

1. **遅延アップロード:** ファイル選択時はローカルプレビュー（`URL.createObjectURL`）のみ。ダイアログの「アップロード」確認ボタン押下時にR2へアップロード
2. **R2削除機能:** `storage.ts`に`deleteImage`/`deleteImages`関数を追加。画像変更・削除時にR2バケットからも削除
3. **削除APIエンドポイント:** DELETE `/api/upload`を新設（認証必須）

**影響範囲:**

| ファイル                       | 変更内容                                                                                                                                       |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/lib/storage.ts`           | `deleteImage`, `deleteImages`関数追加                                                                                                          |
| `src/app/api/upload/route.ts`  | DELETEハンドラ追加                                                                                                                             |
| `src/app/listing/new/page.tsx` | `pendingPhotos: string[]` → `pendingFiles: File[]`に変更、`handleFilesSelect`からR2アップロード除去、`handleUploadConfirm`でR2アップロード実行 |
| 物件編集API（将来）            | 保存時に旧画像 vs 新画像を比較し、除外された画像を削除                                                                                         |

**工数:** 1日（遅延アップロード0.5日 + 削除機能0.5日）

## 技術的インサイト

- 画像のライフサイクル管理（アップロード・削除）は早期に正しく設計すべき。孤児ファイルの蓄積はコストだけでなく、将来のAIパイプライン（画像分析等）に不要な処理を発生させるリスク
- 遅延アップロードパターンは「ユーザーが確定するまでサーバーリソースを消費しない」という原則に沿う
- `DeleteObjectCommand`の実装は`PutObjectCommand`と対称的で、既存のS3クライアント設定をそのまま使える
