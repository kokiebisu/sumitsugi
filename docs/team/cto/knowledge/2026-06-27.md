# CTO Knowledge - 2026-06-27

## Daily Update (2026-06-27)

### 1. Next.js performance optimization 2026

- **ポイント1:** Next.js 16ではTurbopackが正式デフォルトとなり、開発時のHMRだけでなく本番ビルドも大幅に高速化されている。`next build --turbopack`への移行を検証し、CIのビルド時間短縮を測定すべき。

- **ポイント2:** Partial Prerendering（PPR）が安定版に近づき、静的シェルと動的コンテンツを1リクエストで組み合わせられるようになった。物件一覧ページのように「ヘッダーは静的・在庫情報は動的」という構成に向いており、TTFBの改善が期待できる。

- **ポイント3:** React Server Componentsを前提としたデータフェッチの「N+1リクエスト問題」が依然多くのプロジェクトで発生している。`use cache`ディレクティブやfetchのリクエストメモ化を活用し、サーバー側での重複フェッチを削減することが2026年のベストプラクティス。

- **ポイント4:** 画像・フォント最適化はもはや当たり前で、次の焦点はJSバンドルの「ルート単位」の軽量化に移っている。`next/dynamic`によるコード分割に加え、Server Actionsを使うことでクライアントに送るJSそのものを減らす設計が重要。

- **ポイント5:** Core Web VitalsはINP（Interaction to Next Paint）がLCPと並ぶ主要指標として定着した。フォームや一覧フィルタなどユーザー操作が多いUIでは、useTransitionやServer Actionsの楽観的更新を使い、操作直後のレスポンス遅延を抑える設計を優先すべき。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の安定化:** Next.js 16ではPPRが標準的な選択肢となり、静的シェルを即時配信しつつ動的部分（例: ユーザー固有の物件一覧や予約状況）をストリーミングで後追い描画できる。sumitsugiの`src/app/properties/`のような一覧ページでLCPを大幅改善できるため、優先的に導入検討すべき。

- **`loading.tsx` / Suspense境界の細粒度化:** ページ単位ではなくコンポーネント単位（例: 物件カード、レビューセクション）でSuspense境界を切ることで、遅いデータ取得（DB/外部API）がページ全体をブロックしなくなる。引越し費用計算など重い処理を持つコンポーネントは個別にストリーミングすべき。

- **Server Actionsとストリーミングの統合:** フォーム送信後のレスポンスをストリーミングで返し、楽観的UI更新と組み合わせるパターンが主流化。前の住人/次の住人間のやり取り機能のような多段フォームでUX改善が期待できる。

- **キャッシュ戦略の明示化（`use cache`ディレクティブ）:** Next.js 16では`use cache`によるキャッシュ境界の明示が推奨され、暗黙的なフルルートキャッシュへの依存を減らす方向。物件データのような頻繁に更新される情報と静的なUI部分を分離管理しやすくなる。

- **RSCペイロードサイズの監視が必須に:** ストリーミングでもシリアライズされるRSCペイロード自体は肥大化しがちで、特にネストの深いコンポーネントツリーではTTFBより転送量がボトルネックになるケースが増えている。`bun run build`時のバンドル分析に加え、RSCペイロードサイズも定期的に計測する運用が望ましい。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの実用性:** sumitsugiのようなNext.js + TypeScriptモノレポでは、tRPCがREST/GraphQLより開発速度に優れる。フロントエンド・バックエンド間でスキーマ定義を共有でき、Zodバリデーションと組み合わせれば型安全性とランタイム検証を同時に確保できる（標準化された`.claude/rules/standards.md`のZod方針とも合致）。

- **GraphQLは過剰投資になりやすい:** 物件検索やリスティングのようにクエリパターンが比較的固定的なプロダクトでは、GraphQLのスキーマ管理・N+1問題対策・キャッシュ戦略のコストがメリットを上回ることが多い。複数クライアント（モバイルアプリ等）が並走する段階になるまでは導入を見送るのが妥当。

- **RESTは依然エコシステムの中心:** 外部連携（決済・電子契約・地図API等）とのインテグレーションでは、RESTが事実上の標準であり続けている。社内APIはtRPC、外部公開APIはREST（OpenAPI仕様書付き）という二層構成が2026年のベストプラクティス。

- **Server Actions/RPCへの収束:** Next.js 16のServer Actionsの普及により、tRPC的なRPCパターンとフレームワーク標準機能の境界が曖昧化している。シンプルなCRUDはServer Actionsで済ませ、複雑な型共有が必要な箇所だけtRPCを使う、という選択的併用が増えている。

- **エッジ・ストリーミング対応:** API設計において、レスポンスのストリーミング（特にAI機能を含む場合）とエッジランタイム対応が標準要件になりつつある。今後のメッセージング機能や引越しサポートAI等を実装する際は、ストリーミング前提の設計を最初から組み込むべき。

### 4. serverless edge computing 2026

- **コールドスタートの実質ゼロ化:** V8 isolate（Cloudflare Workers）やWasmベースの軽量サンドボックスが標準化し、起動レイテンシがミリ秒未満まで縮小。sumitsugiのようなNext.js物件検索でも、エッジでのSSRが選択肢に入る。

- **データ層のエッジ移行:** D1/Turso/PlanetScaleなど「エッジ近接DB」が普及し、読み取りレイテンシをユーザー地域に依存させない構成が主流化。物件一覧や検索APIをエッジレプリカで配信すれば、地方ユーザーの体感速度が改善する。

- **AIエージェント推論のエッジ実行:** 軽量LLM推論（Llama/Gemma系の量子化モデル）をエッジで動かす動きが加速。チャット型の物件マッチングや前の住人とのやり取り支援を低遅延で提供できる可能性がある。

- **フレームワークのエッジネイティブ化:** Next.js 16のApp RouterはVercel Edge RuntimeやCloudflareとの統合が深化し、Middleware/Route Handlerをエッジ標準で書ける設計が前提になってきている。新規実装時はNode.js依存APIを避け、エッジ互換を最初から意識すべき。

- **コスト構造の逆転:** 従量課金エッジ実行はトラフィックの少ないMVP〜ベータ期に圧倒的に安価。ローンチ前の現フェーズ（ベータローンチ準備中）なら、常時起動サーバーよりエッジ関数での初期運用がコスト最適。

### 5. authentication security best practices 2026

- **パスキー（WebAuthn/FIDO2）のデフォルト化:** 2026年現在、主要ブラウザ・OSが標準対応済みのため、パスワード+SMS-OTPからパスキーを第一の認証手段に切り替える設計がベストプラクティス。フィッシング耐性が高く、ユーザー体験も向上する。
- **トークンのライフサイクル管理を厳格化:** JWT等のアクセストークンは短寿命（5〜15分）＋リフレッシュトークンのローテーション・再利用検知をセットで実装し、漏洩時の被害範囲を最小化する。`sumitsugi`のようなNext.jsアプリではSecure/HttpOnly/SameSite=Strict Cookieでの保管が必須。
- **多層防御としてのデバイス・行動シグナルの活用:** 単純なMFAだけでなく、デバイスフィンガープリントやログイン時刻・地理的位置などの行動シグナルをリスクベース認証に組み込み、異常検知時のみ追加認証を要求する手法が主流化している。
- **認可（Authorization）ロジックの認証からの分離と最小権限化:** 認証成功後の権限チェックをミドルウェアやRLS（Row Level Security）で一元管理し、エンドポイントごとの実装漏れを防ぐ。`'draft'|'public'`のようなステータス制御を持つ物件データでは、APIレイヤーとDBレイヤーの両方でアクセス制御を検証する二重防御が推奨される。
- **シークレット管理とゼロトラスト前提の設計:** APIキー・OAuthトークンをコードにハードコードせず環境変数/シークレットマネージャーで管理し、内部サービス間通信でも「信頼しない」前提でmTLSや短命トークンを使う構成が標準になりつつある。

### 6. database architecture Prisma Supabase 2026

- **PrismaのRust-free移行:** Prisma 6以降、クエリエンジンをRustバイナリからTypeScript/WASMベースに置き換える動きが進んでおり、Bunのようなネイティブランタイムとの相性・コールドスタートが改善されている。Supabase上のEdge FunctionsでもバイナリDL不要になるメリットが大きい。

- **Supabaseのブランチング機能活用:** Supabase Branching（PR連動のDBプレビュー環境）を使うと、Prisma Migrateとの組み合わせでスキーマ変更をPRごとに安全に検証できる。sumitsugiのような小規模MVPでもCIにDBマイグレーションの自動検証を組み込むべきタイミング。

- **RLS（Row Level Security）とPrismaの併用:** SupabaseのRLSはPrismaのクエリ層をバイパスしないため、`seller`/`buyer`のようなロール別アクセス制御は「PrismaでのバリデーションだけでなくDB層のRLSも必須」という二重防御が2026年のベストプラクティス。物件データの`draft`/`public`ステータス制御にも直結する。

- **Connection Pooling（PgBouncer/Supavisor）の必須化:** Next.js App RouterのServerless関数からPrisma経由でSupabaseに接続する場合、Supavisor（Supabase独自のpooler）経由のtransaction modeが標準化されており、直接接続だとコネクション枯渇が起きやすい。`DATABASE_URL`と`DIRECT_URL`を分けて設定するのが定石。

- **Prisma Accelerate / Edge対応:** グローバル分散のエッジキャッシュレイヤーとしてPrisma Accelerateが成熟し、Supabaseのreadレプリカと組み合わせることで、物件検索のような読み取り中心のページを大幅高速化できる。ただしコスト増になるため、betaローンチ初期はシンプルな構成を優先すべき。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデルの標準化:** WASM Component Model がブラウザ・サーバー双方で安定し、Rustの`wit-bindgen`を使えば言語境界を越えた型安全な相互運用が容易になった。マイクロサービスやプラグインアーキテクチャの実装コストが大幅に下がっている。
- **メモリ管理の改善:** WasmGC連携やlinear memoryの最適化により、Rustの所有権モデルがWASM上でもオーバーヘッドなく機能するケースが増え、ガベージコレクション言語との混在環境でも高いパフォーマンスを維持できる。
- **SIMD/マルチスレッド対応の成熟:** WASM SIMDとshared memory + Web Workersの組み合わせが安定し、Rustで書いた画像処理・暗号化・物理演算などCPU負荷の高い処理をネイティブに近い速度でブラウザ実行できる。
- **エッジコンピューティングでの採用拡大:** Cloudflare Workers、Fastly Compute@Edge等でRust+WASMが標準的な選択肢となり、コールドスタートの速さとサンドボックス安全性が評価され、自社のサーバーレス機能実装でも検討価値がある。
- **ビルドツールチェーンの簡素化:** `cargo component`や改良された`wasm-pack`によりビルド・デプロイのフリクションが減少しており、開発初期段階での導入障壁が下がっている一方、デバッグツールの成熟度はまだネイティブ開発に追いついていない点は留意が必要。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分のみSuspenseでストリーミングする構成が標準パターンに。ダッシュボードや一覧ページでTTFBを大幅改善できる。

- **Server Actionsとデータ変更の一元化:** フォーム送信やミューテーションをAPI Routeではなくサーバーアクションに集約し、`revalidatePath`/`revalidateTag`でキャッシュ無効化まで一気通貫で行う設計が定着。クライアント側のfetchロジックを大幅に削減できる。

- **キャッシュ戦略の明示化:** `fetch`のデフォルトキャッシュ挙動がNext.js 15以降で「明示的opt-in」に変わったため、`cache: 'force-cache'`を意図的に指定する運用が必須。暗黙キャッシュに依存したコードは挙動が変わるので移行時は要注意。

- **Server/Client Componentsの境界設計:** 「Client Componentをツリーの葉に押し込める」原則が定石化し、状態を持つUIだけを切り出してServer Componentでデータ取得・レンダリングを行う分離が、バンドルサイズとパフォーマンスの両面で効果を発揮。

- **`use cache`ディレクティブによる関数レベルキャッシュ:** ルートやfetch単位でなく任意の関数・コンポーネント出力をキャッシュできる`use cache`が実用フェーズに入り、計算コストの高いサーバーロジックを細かい粒度でキャッシュ制御できるようになった。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Vercel Edge FunctionsはNode.js Runtimeではなく軽量なV8ベースのEdge Runtimeで動作するため、コールドスタートが大幅に短縮される。sumitsugiのような物件検索・認証系APIはレイテンシがUX直結なので、地理的に分散したユーザーへの応答速度向上に有効。

- **ポイント2:** 2026年時点ではEdge Middlewareとの組み合わせでA/Bテストやジオロケーション別の表示分岐（例: 地域別の「引越し費用」表示）を、オリジンサーバーを経由せずエッジ層で完結できる設計が主流になっている。

- **ポイント3:** Edge Functionsは実行時間・メモリ制約があるため、画像処理やPDF生成など重い処理はServerless Functions（Node.js Runtime）側に残し、認証チェックやリダイレクト判定など軽量なロジックのみをEdgeに配置する「ハイブリッド配置」が定石。

- **ポイント4:** Next.js 16のApp RouterではRoute Segment Configで`runtime: 'edge'`を個別指定できるため、全体をEdge化するのではなく、トラフィックの多いページ（物件一覧・検索）だけを段階的に移行しコスト・パフォーマンスを検証するアプローチが推奨される。

- **ポイント5:** Edge環境ではNode.js特有のAPI（`fs`やネイティブDBドライバなど）が使えないため、Supabase/Postgresなどのデータアクセス層をEdge対応のHTTPベースクライアントに統一しておく必要があり、移行前にデータ層の互換性確認が必須。

### 10. TypeScript type safety patterns 2026

- **Branded Types / Nominal Typing:** `string`や`number`に意味的な型タグ(`type UserId = string & { __brand: 'UserId' }`)を付与し、IDの取り違えなどをコンパイル時に検出する。Zodの`.brand()`と組み合わせることでランタイム検証と型安全性を同時に担保できる。

- **Zodなどによる「型はスキーマから生成」アプローチ:** 手書きの`interface`定義からZodスキーマを書き、`z.infer<>`で型を導出する流れが標準化。APIの境界（リクエスト/レスポンス、env変数、フォーム入力）では必ずスキーマ検証を通すことで、TypeScriptの「コンパイル時だけ安全」という限界を補完できる。

- **`satisfies`演算子の定着:** 型を強制的に上書き(widen)せず、リテラル型を保持したまま制約チェックだけ行う`satisfies`が、設定オブジェクトやルーティング定義などで標準パターンに。型推論を犠牲にせず安全性を得られる点が実用上大きい。

- **Discriminated UnionとExhaustiveness Check:** ステータス管理(`'draft' | 'public'`のような本プロジェクトのパターン含む)でユニオン型+`switch`+`never`を使った網羅性チェックが定石化。新しい状態を追加した際にコンパイルエラーで漏れを検知できるため、本リポジトリのような状態遷移の多いドメインでは特に有効。

- **`unknown`優先・`any`禁止の徹底とLinter強制:** 外部入力や`JSON.parse`の戻り値は`any`ではなく`unknown`で受け、型ガードを通すまで使用不可にするルールがチーム標準に。ESLintの`no-explicit-any`を必須化し、型安全性をレビュー任せにせず自動化する流れが加速している。
