# CTO Knowledge - 2026-04-09

## Daily Update (2026-04-09)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを劇的に削減できる RSC を基本戦略に据え、`"use client"` は本当に必要な葉コンポーネントにのみ限定する。

- **PPR（Partial Prerendering）の本格採用:** Next.js 15以降で安定化した PPR により、静的シェルを即時配信しつつ動的コンテンツをストリーミングで注入できる。ISR/SSR の二択から解放される重要な転換点。

- **`<Image>` / `<Font>` の最適化は「やって当然」:** next/image の priority 制御と sizes 属性の正確な設定、next/font によるゼロ CLS フォント読み込みは、Core Web Vitals 対応の最低ライン。見落としが多い。

- **Turbopack の実用段階到達:** 2026 時点で Turbopack は本番ビルドでも実用域に達しており、大規模プロジェクトでのビルド時間を Webpack 比で数倍改善できる。CI/CD パイプラインのボトルネック解消に直結。

- **サーバーアクション + 楽観的 UI で UX と DX を同時向上:** `useOptimistic` と Server Actions の組み合わせにより、API ルートを介さない型安全なデータ変更が実現し、体感レスポンス速度と開発速度が両立できる。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化:** 2026年時点でRSCストリーミングの主流課題は「どこにSuspenseを置くか」の設計判断。コンポーネント単位で細かく分割しすぎるとウォーターフォールが増え、粗すぎるとTTFBが悪化する。データ依存グラフを可視化するツール（Next.js DevTools等）での分析が実務上必須になりつつある。

- **PPR（Partial Prerendering）との統合:** Next.js 15以降でPPRが安定化し、静的シェルを即座に返しつつ動的コンポーネントをストリーミングするハイブリッドアーキテクチャが標準パターンに。`<Suspense>`の配置がデプロイ戦略（Edge/Node）に直接影響するため、インフラと密結合した設計判断が求められる。

- **サーバーアクションとの組み合わせによる状態管理の再考:** RSC＋Server Actionsにより、従来のRedux/Zustandが不要なユースケースが拡大。ただしOptimistic UIの実装が複雑になるケースがあり、`useOptimistic`フックの適切な使い方を理解していないと競合状態を生む。

- **ストリーミング対応CDNキャッシュ戦略:** CloudflareやVercelのEdgeでRSCペイロードをセグメント単位でキャッシュする設計が普及中。`cache()`関数やリクエストスコープのメモ化を正しく使わないと、CDNキャッシュが意図せずバイパスされパフォーマンスを損なう。

- **バンドルサイズとClient Boundary管理:** `"use client"`の境界設計ミスによりサーバー側モジュールがクライアントバンドルに混入する問題が依然多発。`@next/bundle-analyzer`と`react-scan`等のツールでClient Componentツリーを定期監査することが、大規模プロジェクトでの技術負債防止に直結する。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの実用的優位性:** フルスタックTypeScriptプロジェクトでは、tRPCがスキーマ定義不要でエンドツーエンドの型安全を実現し、GraphQLのボイラープレートコストなしに同等の開発体験を提供するため採用が急増している。

- **GraphQLの選択基準の明確化:** 複数クライアント（Web/Mobile/サードパーティ）が異なるデータ形状を要求するケースに限定してGraphQLを選ぶべきで、単一フロントエンドのBFFパターンにはオーバーエンジニアリングになりがち。

- **REST + OpenAPIの再評価:** AIコード生成ツールとの親和性が高く、OpenAPI仕様からクライアントSDKを自動生成するワークフロー（`openapi-ts`等）が成熟したことで、RESTが「レガシー」ではなく合理的選択として見直されている。

- **HTTP/3とStreaming APIの台頭:** Server-Sent Events（SSE）やWebSocketを活用したStreaming API設計が、AIアシスタント系機能の普及により標準的になり、REST/GraphQL問わずストリーミング対応が設計時の必須考慮事項になった。

- **APIゲートウェイ層の重要性:** どのプロトコルを選ぶかより、認証・レート制限・オブザーバビリティをAPIゲートウェイ（Cloudflare Workers、AWS API Gateway）で統一管理する設計パターンの方が長期的な保守コストに大きく影響する。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジの標準ランタイムへ:** Cloudflare Workers・Fastly Compute@Edgeを中心に、コンテナより軽量なWasmがエッジ実行の主流となり、コールドスタートがほぼゼロになった。言語選択の自由度も大幅に拡大。

- **エッジDBとデータ局所化の加速:** Cloudflare D1・Turso（libSQL）・Neon Serverlessのエッジレプリカにより、データをユーザー近傍に配置するパターンが一般化。グローバルレイテンシの壁が実用的に突破されつつある。

- **AI推論のエッジオフロード:** LLMの軽量モデル（≤7B）をエッジで直接推論するニーズが急増。Cloudflare AI・Vercel AI SDKのエッジ対応により、中央集権的なAPIコールなしで低レイテンシ推論が実現できる設計が現実的になった。

- **オブザーバビリティの課題が顕在化:** エッジ環境は従来のAPMツールが届かず、分散トレーシング（OpenTelemetry）のエッジ対応が急務。ログの集約コストと遅延のトレードオフ設計が設計上の重要判断になっている。

- **エッジとオリジンの責務分離が設計原則に:** 認証・A/Bテスト・レート制限はエッジ、トランザクション処理はオリジンという責務分離が定石化。ただしエッジのステートレス制約を無視した設計は運用時に崩壊するため、アーキテクチャレビューで必ず確認すべき点。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の標準化:** パスワードレス認証がデファクトスタンダードとなりつつあり、フィッシング耐性のあるパスキーへの移行が急務。主要プラットフォームのサポートが揃った今、新規実装ではパスキーファーストで設計すべき。

- **トークンバインディングとDevice Bound Session Credentials（DBSC）:** セッショントークンをデバイスに紐付けることでクッキー窃取攻撃を無効化する手法が普及中。特にChromeのDBSCサポートにより、実装コスト低減が見込める。

- **継続的認証（Continuous Authentication）:** ログイン時の一点認証から、行動バイオメトリクスや異常検知による継続的なリスク評価へシフト。高権限操作の直前に再認証を挟む「ステップアップ認証」との組み合わせが効果的。

- **AIを活用した不正アクセス検知の高度化:** クレデンシャルスタッフィング攻撃がAIで高度化しており、防御側もML-basedの異常検知（IPレピュテーション、ベロシティチェック、デバイスフィンガープリント）の多層防御が必須。

- **OAuth 2.1 / DPoP（Demonstrating Proof-of-Possession）の採用:** アクセストークンの窃取対策として、リクエストにクライアントの鍵ペアを紐付けるDPoPが標準化。既存のJWTベース実装からの移行ロードマップを今から策定しておくべき。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応成熟:** Prisma 6でEdge Runtime（Cloudflare Workers / Vercel Edge）での動作が安定し、Supabase + Prisma Accelerateによるコネクションプーリングがサーバーレスアーキテクチャの標準パターンになりつつある。

- **Supabase RLSとPrismaの統合が課題:** Row Level SecurityはSupabaseの強みだが、PrismaはRLSを直接サポートしないため、`SET LOCAL role`やサービスロール切り替えの実装が必要で、マルチテナント設計時にアーキテクチャ上の工夫が求められる。

- **Supabase Branching × PR-per-branchが主流化:** 2025年後半からSupabase Branchingが本番利用可能になり、PRごとにDBスキーマをプレビュー環境に自動デプロイするワークフローがCI/CDのベストプラクティスとして定着し始めている。

- **型安全の恩恵がフルスタックに拡張:** Supabaseの`supabase gen types`とPrismaのzod-prisma-typesを組み合わせることで、DB→API→UIまで型が貫通するアーキテクチャが実現でき、ランタイムエラーを大幅に削減できる。

- **PgVectorとAI統合がゲームチェンジャー:** SupabaseのpgVector + Prismaによるベクター検索の組み合わせが急速に普及しており、RAG（Retrieval-Augmented Generation）を既存のPostgresインフラに統合するアーキテクチャが2026年の標準的な選択肢になっている。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASIp2（WASI Preview 2）の安定化により、Rustで書いたWasmコンポーネントがサーバーレス・エッジ環境（Cloudflare Workers、Fastly Compute）でネイティブに近いコールドスタートを実現し、Node.jsより10〜50倍高速な起動が報告されている。

- **ポイント2:** Rustの`wasm-bindgen` + `wasm-pack`エコシステムが成熟し、GCの存在しないRust×Wasmの組み合わせはメモリ使用量の予測可能性が高く、レイテンシのP99外れ値問題を抱えるGoやJVMベースのワークロードの置き換えとして注目されている。

- **ポイント3:** Chrome・Firefox両エンジンでWasm GC・Tail Callsが本番有効化され、Rust以外の言語（Kotlin、Swift）もWasmターゲットを強化しているが、システム寄りの処理ではRustが依然としてパフォーマンスリファレンスとなっている。

- **ポイント4:** `cargo component`（WebAssembly Component Model）の採用が拡大し、Rustで書いたビジネスロジックをWasmコンポーネントとしてパッケージ化・バージョン管理する運用が実用段階に入った。マイクロサービスのコンテナ代替として検討価値がある。

- **ポイント5:** SIMD命令・スレッド（SharedArrayBuffer）のWasm対応が安定化し、画像処理・機械学習推論・暗号演算などCPU集約タスクでRust×WasmがJavaScriptより2〜8倍のスループットを示すベンチマークが増えており、フロントエンドへの処理移譲戦略が現実的な選択肢になっている。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの設計:** 2026年はServer Componentsをデフォルトとし、インタラクティビティが必要な部分のみ`'use client'`を付与するパターンが定着。クライアントバンドルサイズを劇的に削減できる。

- **Partial Prerendering (PPR) の本格採用:** 静的シェルと動的ストリーミングを同一ルートで混在させるPPRが安定版に。`<Suspense>`境界の設計がアーキテクチャの中心的関心事になっている。

- **Server Actions によるAPI層の簡略化:** フォーム送信・データ変更処理をServer Actionsに集約し、APIルートを削減するパターンが主流。ただしZodによる入力バリデーションとCSRF対策は必須。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** `fetch`のキャッシュオプションより柔軟な`use cache`（関数・コンポーネント単位）が標準化。`cacheTag`/`cacheLife`で無効化戦略を明示的に設計する。

- **Parallel Routes + Intercepting Routes の実用化:** モーダルやドロワーをURLに紐づけつつ、直リンクでもフルページとして機能させるパターンが複雑なUXの定番解となっている。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの適材適所:** Edge Functionsはコールドスタートがほぼゼロで地理的分散に強いが、Node.js APIの制約（fs、一部のnpmパッケージ不可）があるため、軽量な認証・A/Bテスト・リクエスト変換に限定し、重い処理はServerless Functionsに委ねる設計が現実的。

- **Fluid computeへの移行:** Vercel 2025以降は「Fluid compute」モデルにより、EdgeとServerlessの境界が曖昧になりつつある。リクエスト間でのインスタンス再利用が可能になり、コスト効率と応答速度が向上——従来の「Edge一択」思考は見直しが必要。

- **KV・データストアとの組み合わせ最適化:** Vercel KV（Upstash Redis）やNeon PostgreSQLのEdgeネイティブ接続を活用することで、DBラウンドトリップをEdge側で吸収できる。ただしコネクションプールの設定ミスが隠れたレイテンシ要因になるため、`maxIdleConnections`の調整が重要。

- **Bundle sizeの1MB制限への対応:** Edge Runtimeの1MBバンドル上限は依然として厳しい制約。`import`のtree-shakingが効かないライブラリ（momentjs等）は動的importまたはNode runtime fallbackへの切り出しが必須。`@vercel/edge-config`のような軽量SDKを優先選択する習慣をチームに根付かせること。

- **Middleware乱用のアンチパターン:** `middleware.ts`でのロジック肥大化はNext.jsのすべてのリクエストに影響し、デバッグ困難なパフォーマンス劣化を招く。Middlewareは最小限（認証チェック・リダイレクト・ヘッダー付与）に留め、ビジネスロジックはRoute HandlersかServer Actionsに移すことを徹底すべき。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** プリミティブ型に意味的な区別を付ける Branded Types（`type UserId = string & { readonly _brand: 'UserId' }`）が標準パターンとして定着し、ID混同バグを型レベルで防止できる。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` を使い、型推論を維持しながら型チェックを強制する手法が主流に。`as` キャストより安全で、オブジェクトリテラルの過剰プロパティ検出に特に有効。

- **Zod + `z.infer<>` によるランタイム/静的型の統合:** APIバウンダリでZodスキーマを唯一の真実源とし、`z.infer<typeof schema>` で静的型を導出するパターンが定番化。型とバリデーションの乖離が根絶できる。

- **Template Literal Types によるAPI型安全性:** `${HttpMethod} ${ApiPath}` 形式のテンプレートリテラル型でルート定義を型化し、存在しないエンドポイント呼び出しをコンパイル時に検出するアーキテクチャが実用段階に。

- **`NoInfer<T>` ユーティリティの戦略的使用:** TypeScript 5.4で導入された `NoInfer<T>` を使い、ジェネリック関数のデフォルト値推論を制御することで、意図しない型の広がり（widening）を防ぎAPIの誤用を型レベルで阻止できる。
