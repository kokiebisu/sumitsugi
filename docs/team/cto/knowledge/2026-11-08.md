# CTO Knowledge - 2026-11-08

## Daily Update (2026-11-08)

### 1. Next.js performance optimization 2026

- **React Server Components とストリーミングの深化:** Next.js 16ではRSCとPartial Prerenderingがさらに成熟し、ページ単位ではなくコンポーネント単位で静的/動的を混在させることで、TTFBとLCPを同時に改善できる。

- **Turbopackのビルド高速化:** Turbopackが本格的に安定版となり、開発時のHMRだけでなく本番ビルドでも大幅な高速化が得られるため、CI時間短縮とデプロイサイクルの短縮に直結する。

- **キャッシュ戦略の明示化:** `fetch`のキャッシュ指定やRoute Segment Configがより細かく制御可能になり、「何がキャッシュされているか分からない」問題を減らすために、データ取得箇所ごとにrevalidate戦略を明示的にコード化することが重要になっている。

- **Edge/Node実行環境の使い分け:** 軽量なミドルウェアやパーソナライゼーションはEdge Runtime、重い処理はNode Runtimeという役割分担が定着しつつあり、物件検索のようなレイテンシ重視の画面ではEdgeを活用する判断が有効。

- **Core Web Vitals計測の自動化:** Lighthouse CIやVercel Speed Insightsをデプロイパイプラインに組み込み、回帰を自動検知する体制が標準になってきているため、sumitsugiでも`bun run build`後のパフォーマンス計測をCIに統合する余地がある。

### 2. React Server Components streaming 2026

- **ポイント1:** React Server ComponentsのストリーミングはNext.js 16でさらに洗練され、Partial Prerendering（PPR）と組み合わせることで、静的シェルを即時表示しつつ動的データ部分だけを後からストリーミングできるようになっている。sumitsugiの物件一覧ページのような「骨格は即表示、価格や空室状況は非同期取得」という構成に適している。
- **ポイント2:** `loading.tsx`とSuspenseバウンダリの粒度設計がパフォーマンスの要。バウンダリを細かく切り過ぎるとウォーターフォールが発生し逆にTTFBが悪化するため、データ取得の依存関係を意識した単位で分割する必要がある。
- **ポイント3:** Server Actionsとストリーミングの組み合わせにより、フォーム送信後のUI更新を再フェッチなしで部分的に反映できる。引越し費用の見積りフォームなど多段階フローで有効だが、キャッシュ無効化（revalidatePath/revalidateTag）の設計を誤るとstaleなUIが残るリスクがある。
- **ポイント4:** 2026年時点でEdge Runtimeとの組み合わせがデファクト化しており、ストリーミングレスポンスをCDNエッジで開始できるため、地理的に離れたユーザーへのTTFB改善が顕著。ただしNode.js限定のライブラリ（一部のDB driverなど）はEdgeで動かないため、依存ライブラリの互換性確認が必須。
- **ポイント5:** 開発ベストプラクティスとしては、ストリーミングHTMLのチャンク順序がSEOクローラーの解釈に影響するケースがあるため、物件詳細ページのようなSEO重要ページでは主要コンテンツ（タイトル・価格・画像）を最初のチャンクに含める設計が推奨される。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCのようなend-to-end型安全アプローチがTypeScriptモノレポ構成で主流化しており、スキーマ定義とクライアント生成の手間を省きつつランタイムエラーを大幅に削減できる。ただし社外向け公開APIにはOpenAPI/RESTの方が相互運用性で優位。
- **ポイント2:** GraphQLは複数データソースの集約やモバイルクライアントの帯域最適化に強いが、N+1問題やキャッシュ戦略の複雑さから運用コストが高く、小規模チームでは過剰設計になりやすい。
- **ポイント3:** 住人情報・物件データ・決済など異なるドメインを扱う場合、単一方式に固執せず「内部管理画面はtRPC、外部パートナー向けはREST」のようにユースケース別に併用するハイブリッド構成が2026年のベストプラクティス。
- **ポイント4:** APIスキーマをSSOT（Single Source of Truth）としてZodやPrisma由来の型から自動生成する流れが加速しており、フロントエンド・バックエンド間の型不整合によるバグを未然に防げる。
- **ポイント5:** 認証・決済など機密性の高いエンドポイントはプロトコルに関わらずレート制限・入力検証・CSRF対策を標準装備すべきで、APIゲートウェイ層での一元管理が運用負荷を下げる。

### 4. serverless edge computing 2026

- **エッジでのAI推論標準化:** 2026年はCloudflare Workers AI、Vercel Edge Functions、Deno Deployなどでエッジ上での軽量LLM推論が標準機能化し、レイテンシが数msの地域最適化が一般的になっている。sumitsugiのような物件検索・レコメンド機能はエッジ推論で初期表示速度を大幅改善できる。

- **コールドスタート問題の実質解消:** V8 isolateベースのランタイム（Workers、Fastly Compute）がコンテナ型サーバーレス（Lambda）を置き換えつつあり、起動時間が1ms未満に。認証チェックや物件ステータス判定などの軽量APIロジックはエッジファーストで実装すべき時代。

- **エッジデータベースとの統合が鍵:** Turso、Cloudflare D1、PlanetScaleなどのエッジレプリケーション型DBが普及し、読み取り負荷の高いAPI（物件一覧・検索）はオリジンDBを経由せずエッジで直接応答可能。Next.js 16のPPR（Partial Prerendering）と組み合わせると静的部分はCDN配信、動的部分のみエッジ関数で処理できる。

- **コスト構造の変化に注意:** エッジ実行は従量課金だが、CPU時間ベースの課金モデルが細分化され、重い処理（画像変換、PDF生成など）をエッジに持ち込むと従来のサーバーレスより高コストになるケースも増えている。引越し費用計算やPDF出力のような重処理はオリジン/バッチ処理に残す判断が必要。

- **Vendor lock-inの再燃:** エッジランタイム固有API（KV、Durable Objects等）への依存が深まり、移行コストが上昇傾向。MVPフェーズのsumitsugiは標準Web APIに近い抽象化を保ち、特定ベンダーへの過度な依存は避けるのが無難。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）がデフォルト化:** FIDO2/WebAuthnベースのパスキーが主流になり、パスワードレス認証をデフォルトの選択肢として実装すべき時期に入っている。フォールバックとしてのパスワード認証も残しつつ、新規登録フローではパスキーを第一候補として提示するのが望ましい。

- **セッション管理の継続的検証:** ログイン時の一度だけの認証ではなく、デバイスフィンガープリントやリスクベース認証（異常なIP・デバイス変更の検知）でセッション全体を継続的に評価する設計が標準になっている。特に民泊・物件引き継ぎのような高価値トランザクションを含むsumitsugiでは、決済や契約操作時に再認証（step-up authentication）を挟む設計が有効。

- **トークンのスコープ最小化と短命化:** JWTなどのアクセストークンは有効期限を短くし（15分程度）、リフレッシュトークンのローテーションとサーバーサイドでの即時失効（revocation）をセットで実装する。長命トークンの漏洩は被害範囲が大きく、特にサーバーレス/エッジ環境では失効の仕組みが後回しにされがちなので要注意。

- **CSRF/XSS対策の多層化:** Next.js App RouterではServer Actionsのオリジン検証、HttpOnly+SameSite=Strict/Laxクッキー、CSPヘッダーの組み合わせが基本線。認証関連のクッキーは`Secure`属性必須で、ローカル開発でもHTTPS相当の環境でテストすることを推奨。

- **監査ログとレート制限の標準装備:** ログイン試行・パスワードリセット・アカウント復旧の各エンドポイントにレート制限（IP単位＋アカウント単位）を設け、認証イベントを改ざん不可能な形で監査ログに記録する。法務確認待ちの現フェーズでも、プライバシーポリシー公開前にログ保持方針を固めておくと手戻りが少ない。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** PrismaのRust製クエリエンジン廃止とTypeScript-native化（Prisma ORM 6以降）により、Supabaseのようなサーバーレス/エッジ環境でのコールドスタートが大幅に改善され、Edge Functions上でのDB接続が実用的になっています。
- **ポイント2:** SupabaseはPgBouncer依存から独自のコネクションプーリング（Supavisor）へ移行しており、Prismaを使う際は`pgbouncer=true`と`connection_limit`の設定をSupavisorの仕様に合わせて見直す必要があります。
- **ポイント3:** Row Level Security（RLS）とPrismaのスキーマ定義を併用するハイブリッド構成が主流化しており、認証ロジックをアプリ層だけでなくDB層でも強制することで多層防御を実現できます。
- **ポイント4:** Prisma Accelerate等のマネージドコネクションプーリング+キャッシュ層を使うことで、SupabaseのようなマネージドPostgres上でもNext.js 16のServer Componentsからの大量同時接続を安全に処理できるようになっています。
- **ポイント5:** マイグレーション管理において、Prisma Migrateの宣言的ワークフローとSupabase CLIのマイグレーション機能が競合しやすいため、どちらか一方を正とする運用ルールを早期に決めることが技術的負債を防ぐ鍵です。

### 7. WebAssembly Rust performance 2026

- **Component Model / WASI Preview 2の本格普及:** 2026年にはComponent Modelが主要ランタイム（Wasmtime、wasmer）で標準対応となり、Rustの`wasm32-wasip2`ターゲットが安定版に。モジュール間のインターフェースがWITで型安全に定義できるため、FFI境界のオーバーヘッドとバグが大幅に減少している。

- **SIMDとTail Callの標準化による演算性能向上:** 128-bit SIMD提案とTail Call最適化がブラウザ・ランタイム両方で広くサポートされ、Rustコンパイラが自動的にSIMD命令を生成できるケースが増加。画像処理や暗号計算など計算集約型ワークロードでネイティブの80-90%の性能に近づいている。

- **バイナリサイズ最適化がデプロイのボトルネックに:** `wasm-opt`や`wit-bindgen`の進化でグルーコードは減ったが、依存クレートの肥大化は依然課題。CI/CDパイプラインに`twiggy`等のサイズ解析を組み込み、リリース前にバイナリサイズをゲートすることが実用的なベストプラクティスになっている。

- **マルチスレッド対応の実用化:** Shared Memory + Web Workerベースのスレッディングが安定し、Rustの`rayon`をWASM上でそのまま使えるケースが増えた。ただしスレッド生成コストが高いため、ワーカープールの事前起動パターンが推奨される。

- **AOTコンパイルによるコールドスタート短縮:** Wasmtimeの`compile-async`やCranelift AOTキャッシュの活用で、サーバーレス環境（エッジコンピューティング）でのコールドスタートがミリ秒台まで短縮。sumitsugiのような物件検索の重い計算処理をエッジで動かす選択肢として現実的になってきている。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** 静的シェルを即座に返しつつ動的部分をストリーミングする設計がNext.js 16で標準化され、`loading.tsx`やSuspense境界の設計がパフォーマンスに直結するようになった。本プロジェクトでも物件一覧ページなど「静的な骨組み+動的な価格/在庫情報」構成に積極活用すべき。

- **`use cache`ディレクティブによるキャッシュの明示化:** 従来の暗黙的なfetchキャッシュから、関数単位で`use cache`を明示する方式に移行しつつあり、キャッシュ戦略がコードレベルで追跡可能になった。`src/lib/data.ts`のデータ取得関数はこの明示的キャッシュ指定に揃えることで、挙動の予測可能性とデバッグ性が向上する。

- **Server Actionsの型安全なバリデーション統合:** Server ActionsとZodスキーマを組み合わせたパターンが定着し、フォーム送信(お問い合わせ・内見予約など)で「境界でのバリデーション」が自然に実現できる。クライアント側の重複バリデーションコードを削減できる点が開発速度に効く。

- **Turbopackのデフォルト化によるビルド高速化:** Next.js 16でTurbopackが本番ビルドでも既定となり、`bun run build`の実行時間が大幅短縮される。CIのビルド待ち時間が開発サイクルのボトルネックだった場合、ここで改善余地がある。

- **Route GroupsとParallel Routesによるレイアウト分離の洗練:** `(group)`構文と`@slot`による並行ルーティングが、ダッシュボード系UI(前の住人向け管理画面など)の複雑なレイアウト分割に適している。物件管理とアカウント設定を同一レイアウト内で独立更新させたいケースに有効。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge FunctionsのCPU時間課金モデルを意識した実装が重要で、重い処理（画像変換・暗号化処理など）はNode.js Runtimeやバックグラウンドジョブに退避させ、Edgeには認証チェックやリダイレクト、A/Bテスト振り分けなど軽量なロジックのみを残すのが基本戦略です。

- **ポイント2:** `waitUntil()`を使った非同期処理のオフロードが一般化しており、レスポンスを即座に返しつつログ記録や分析イベント送信をバックグラウンドで実行することで、ユーザー体感速度（TTFB）を大きく改善できます。

- **ポイント3:** Edge MiddlewareとEdge Functionsの責務分離がパフォーマンス最適化の鍵で、Middlewareはルーティング判断に限定し、データフェッチや認可ロジックは個別のEdge Functionに委譲することでコールドスタート影響を最小化できます。

- **ポイント4:** Vercelの地理分散実行（Regional Edge Deployment）を活用し、データベースやAPIの物理的な近さを考慮したリージョン選択（`regions`設定）を行うことで、レイテンシをミリ秒単位で削減できる点が見落とされがちです。

- **ポイント5:** キャッシュ戦略としてISR/`stale-while-revalidate`とEdge Cacheを組み合わせることで、動的コンテンツでもCDNエッジからの応答が可能になり、引っ越し費用計算や物件検索のような頻繁にアクセスされるが更新頻度が低いデータに特に有効です。

### 10. TypeScript type safety patterns 2026

- **`satisfies`演算子とconst型パラメータの定着:** TS 5.x系で標準化された`satisfies`は、型推論を保ったまま型チェックを行えるため、設定オブジェクトやZodスキーマ定義で型安全性と可読性を両立させる主流パターンになっている。

- **境界でのランタイム検証（Zod/Valibot）とスキーマ駆動開発:** コンパイル時の型だけでは外部入力（API・フォーム）を守れないため、Standard Schema仕様に対応したZod/Valibotでランタイム検証と型推論を一体化する設計が業界標準化している。本プロジェクトのStandards（Zod境界検証）とも合致する方向性。

- **Branded Types（名前的型付け）によるプリミティブの誤用防止:** `UserId`と`string`を型レベルで区別するブランド型パターンが、IDの取り違えなどの実行時バグを防ぐ実用手法として広く採用されている。

- **エンドツーエンド型安全性（tRPC型ルーター、型安全ORM）:** フロントエンド〜バックエンド〜DBまで型を伝播させる構成（tRPC、Drizzle等）により、API変更時の破壊的変更をコンパイル時に検出できる開発体験が標準化しつつある。

- **`noUncheckedIndexedAccess`や厳格フラグの既定化:** 配列・オブジェクトアクセス時の`undefined`混入を型で強制するコンパイラオプションが、新規プロジェクトの初期設定として定着し、null安全性のバグを事前に排除する流れが加速している。
