# CTO Knowledge - 2026-03-21

## Daily Update (2026-03-21)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、デフォルトをServer Componentsとし、インタラクティブな部分のみ`'use client'`に限定する。2026年時点でRSCはNext.jsの基本設計となっており、採用しないことがパフォーマンス負債になる。

- **Partial Prerendering (PPR) による静的・動的の最適統合:** Next.js 15以降で安定化したPPRを活用し、ページのシェルを静的配信しつつ、動的部分はStreaming SSRで後続取得する。CDNキャッシュ効率とTTFBの両立が可能。

- **`next/image` と `next/font` によるCore Web Vitals対策:** LCP改善にはAVIF/WebP自動変換と`priority`属性の適切な設定が必須。フォントはビルド時インライン化でCLS（累積レイアウトシフト）をゼロに抑える。

- **Server Actions のバンドル分離意識:** Server Actionsは便利だが、`'use server'`の乱用によりサーバーサイドコードが意図せずクライアントバンドルに混入するリスクがある。`next build --analyze`で定期的にバンドル構成を可視化し、モジュール境界を明示的に管理する。

- **Edge Runtimeへの選択的移行:** ミドルウェアやA/Bテスト処理はEdge Runtimeで低レイテンシ化できるが、Node.js固有APIは使用不可。ユーザー認証チェックやリダイレクトなど軽量処理から段階移行し、Cold Startの最小化と実行コスト削減を両立する。

### 2. React Server Components streaming 2026

- **Suspense境界の戦略的配置が鍵:** RSCストリーミングでは、Suspenseバウンダリをコンポーネントツリーの適切な粒度に配置することで、TTFBを維持しながらインタラクティブ部分を優先レンダリングできる。粗すぎると恩恵が薄く、細かすぎるとウォーターフォールが発生する。

- **PPR（Partial Pre-Rendering）が本番レディに:** Next.js 15以降でPPRが安定化し、静的シェルを即座に返しつつ動的コンテンツをストリームするハイブリッドモデルが実用段階に入った。CDNキャッシュと動的データの両立が現実的になった。

- **データフェッチのコロケーションによる開発効率向上:** サーバーコンポーネントで直接DBアクセスやAPIコールを行い、クライアントへのpropsドリルを排除できる。ただし、N+1問題がサーバー側に移動するため、DataLoaderパターンやReact cache()の活用が必須。

- **ストリーミング対応のエラーハンドリング設計が必要:** ストリーム開始後のエラーはHTTPステータスコードで表現できないため、error.tsxとSuspenseの組み合わせによるUI層でのエラー境界設計が重要。グレースフルデグラデーションを意識したコンポーネント分割が求められる。

- **バンドルサイズの非対称化でCore Web Vitals改善:** RSCはサーバー側でレンダリングされJSバンドルに含まれないため、重いライブラリ（日付処理・マークダウンパーサー等）をサーバー側に移動するだけでLCPとTTIが劇的に改善する実績が蓄積されている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの成熟とフルスタック型安全性の標準化:** 2026年現在、Next.js + tRPCの組み合わせが中小規模プロジェクトのデファクトに近づきつつあり、スキーマ定義なしでフロントエンド・バックエンド間の型共有が当たり前になっている。

- **GraphQLはBFF層に特化:** クライアント直接呼び出しよりも、マイクロサービスを束ねるBFF（Backend for Frontend）レイヤーとしての用途が主流化。Relay/Apollo Clientの複雑さを避け、GraphQL Meshやステッチングで既存REST APIを束ねるパターンが増加。

- **RESTはリソース型APIとして依然強固:** 外部公開API・サードパーティ連携ではOpenAPI 3.1 + Zodスキーマ自動生成（orval, Hey APIなど）による型安全RESTが実用的選択肢として再評価されている。

- **Server-Sent Events / WebSocketの軽量代替としてHTTP Streaming普及:** LLM統合の急増により、RESTのストリーミングレスポンス（`text/event-stream`）がリアルタイム系ユースケースに採用される場面が増え、WebSocketの複雑さなしに双方向に近い体験を実現。

- **エッジ環境対応がAPI設計の制約に:** Cloudflare Workers / Vercel Edge Runtimeでは長時間接続・大容量ペイロードに制限があるため、APIの粒度・ペイロードサイズ設計がインフラ選定と密結合になっている。このプロジェクト（Next.js on Vercel想定）ではtRPC + Server Actionsのハイブリッド構成が現実的な最適解。

### 4. serverless edge computing 2026

- **ポイント1: エッジでのAI推論の標準化:** WebAssembly（WASM）とONNX Runtimeの成熟により、LLMの軽量モデルをCDNエッジノードで直接実行するケースが急増。レイテンシを50ms以下に抑えつつAI機能を提供できる。

- **ポイント2: Durable Objects / Stateful Edgeの普及:** Cloudflare Durable ObjectsやVercel KV等、エッジでの状態管理が実用レベルに到達。「エッジ＝ステートレス」の前提が崩れ、セッション管理やリアルタイム同期をエッジで完結させるアーキテクチャが増加。

- **ポイント3: コールドスタート問題の実質的解消:** V8 IsolateベースのランタイムとSnapshottingの改善により、コールドスタートが0ms〜数ms台に。Node.jsコンテナ型のサーバーレスより1〜2桁速く、ユーザー体験への影響がほぼゼロになった。

- **ポイント4: エッジでのデータローカリゼーション対応:** GDPR・個人情報保護法への対応として、データをユーザーの地理的リージョンから出さずに処理するエッジアーキテクチャが規制対応の標準手法に。特に医療・金融領域で必須要件化。

- **ポイント5: エッジ・オリジン間のコスト最適化が設計の核心に:** エッジ実行は安価だがオリジンDBへのフォールバックが多いと逆効果。キャッシュ戦略・データレプリケーション設計の精度がTCOを左右するため、「何をエッジに置き、何をオリジンに残すか」のアーキテクチャ判断力が開発チームの重要スキルになっている。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準化:** FIDO2/WebAuthnベースのパスキーが2026年の認証標準となり、フィッシング耐性とUX向上を両立。パスワードレス移行はもはやオプションではなく必須要件。

- **トークンバインディングとDPoP:** OAuth 2.0でのDPoP（Demonstrating Proof of Possession）採用が加速し、アクセストークンの盗用・リプレイ攻撃を防止。JWTのみの実装は脆弱とみなされる。

- **ゼロトラスト継続認証:** 初回ログイン時だけでなく、セッション中も行動バイオメトリクスやリスクスコアリングで継続的に認証。長期セッショントークンの廃止が推奨される。

- **AIを活用した異常検知:** LLMベースのユーザー行動分析でアカウント乗っ取りをリアルタイム検出。従来のルールベースのレート制限では高度なCredential Stuffing攻撃に対応不能。

- **サプライチェーン認証リスク:** 認証ライブラリ（Auth.js、NextAuth等）のSBOM管理と依存関係の定期監査が必須。2025年に発生した複数のOAuth ライブラリへの攻撃事例から、Lock File Pinningとプロビナンス検証の徹底が求められる。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x + Supabase の統合成熟:** Prisma 6はEdge Runtimeサポートが強化され、Supabase Edge FunctionsとのDirect Connection（pgbouncer不要ケース）が増加。コネクションプーリング戦略の選択（Transaction vs Session mode）がパフォーマンスのキーになっている。

- **Row Level Security (RLS) の設計が最重要課題:** Supabaseはデフォルトでクライアント直接アクセスを想定するため、RLSポリシーの設計ミスがデータ漏洩に直結する。Prisma経由（サービスロールキー使用）の場合はRLSをバイパスするため、アクセス層の責務分離を明確にする必要がある。

- **Supabase Realtime + Postgres Logical Replication の活用拡大:** 2026年時点でRealtimeのBroadcast/Presenceが安定し、チャット・通知・コラボ機能をWebSocketで実装するパターンが定着。ただしRLSとRealtimeの組み合わせはフィルタリング設計に注意が必要。

- **Prisma Accelerate によるグローバルキャッシュ層:** Prisma AccelerateはCDNエッジでのクエリキャッシュを提供し、読み取り多用アプリ（例: 物件一覧）のレイテンシを大幅削減できる。ただしキャッシュ無効化戦略（TTL設計）を怠るとデータ鮮度問題が発生する。

- **型安全なDB操作とマイグレーション管理の標準化:** Prisma SchemaはSupabaseのマイグレーション（`supabase db push` vs `prisma migrate deploy`）と競合しやすい。2026年のベストプラクティスはPrismaをスキーマ・型生成の主権とし、Supabase CLIはシードデータ・RLSポリシー管理に限定する役割分担が主流となっている。

### 7. WebAssembly Rust performance 2026

- **Component Model の成熟:** WebAssembly Component Model (WASM CM) が2026年に実用段階へ移行し、RustコンポーネントをJS/Python等と型安全に合成できるようになった。`wasm-tools` と `wit-bindgen` のエコシステムが安定し、マイクロサービス境界をWASMで定義するパターンが増加中。

- **WASI Preview 2 による非同期IO:** WASI Preview 2のAsync対応により、RustのTokioランタイムをWASM上で動かすユースケースが現実的になった。エッジコンピューティング（Cloudflare Workers、Fastly Compute）でのRust WASMが本番ワークロードで採用される事例が急増している。

- **コンパイルサイズと起動時間の改善:** `wasm-opt` (Binaryen) と Rustの `panic = "abort"` + LTO の組み合わせにより、バイナリサイズを従来比30-50%削減できる。Wasmtime/WASMer のAOTコンパイルにより、コールドスタートがJVMと同等以下に収束してきた。

- **SIMD・スレッド対応の標準化:** WebAssembly SIMD (Fixed-width 128bit) が全主要ブラウザで安定し、RustのSIMDクレート（`packed_simd`, `std::simd`）との統合が成熟。画像処理・機械学習推論をブラウザ上でネイティブ近傍の速度で実行する実用例が増えている。

- **Rustを選ぶべき判断基準:** ガベージコレクタなし・予測可能なメモリ使用量・ゼロコストの外部関数インターフェースという特性から、レイテンシ要件が厳しいWASMモジュール（暗号処理、コーデック、パーサー）はRust一択になりつつある。GCプロポーザル経由のKotlin/SwiftはバイナリサイズとGC停止の点でまだRustに追いついていない。

### 8. Next.js App Router patterns 2026

- **Server Components優先設計:** クライアントバンドルサイズ削減のため、デフォルトをServer Componentsとし、インタラクティビティが必要な箇所のみ`'use client'`を付与する境界設計が標準化。データフェッチはコンポーネント内で直接行うことでpropsバケツリレーを排除できる。

- **Partial Prerendering (PPR) の実用化:** 静的シェルと動的ストリームを1リクエストで混在させるPPRがStable化し、`<Suspense>`境界を戦略的に配置することでTTFBとCLS両方を改善できる設計が主流に。

- **Server Actions によるミューテーション統一:** API Routeを経由せずServer Actionsでフォーム送信・DB更新を行うパターンが定着。楽観的UIは`useOptimistic`と組み合わせることでネットワーク待ちなしのUXを実現できる。

- **キャッシュ戦略の明示化:** Next.js 15以降、fetchのキャッシュはオプトインに変更。`revalidateTag`/`revalidatePath`によるオンデマンド再検証と`unstable_cache`によるDB結果キャッシュを組み合わせ、キャッシュ層を意図的に設計することが必須。

- **Parallel Routes + Intercepting Routes による複雑なUI:** モーダル・スライドオーバー・並列ダッシュボードを`@slot`と`(.)route`で実装するパターンが成熟。URLを保持したまま複数ビューを管理でき、シェアリンクやブラウザバックが自然に動作する。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge Runtimeの選択的活用:** 全APIルートをEdgeに移行するのではなく、レイテンシ感度の高いルート（認証チェック、A/Bテスト、地理的リダイレクト）に絞って適用することがベストプラクティス。Node.js APIに依存する処理はServerlessのままにする。

- **ポイント2: Cold Start撲滅のためのStreaming活用:** `Response.body` のReadableStreamとEdge Streamingを組み合わせることで、TTFB（Time to First Byte）を大幅に削減できる。特にAI応答系のUIでは必須の最適化になっている。

- **ポイント3: KV・キャッシュ戦略の重要性:** Vercel KV（Redis）やEdge Cacheヘッダー（`stale-while-revalidate`）を組み合わせ、Edge Function自体の実行を最小化する設計が2026年の主流。関数を「実行するもの」ではなく「キャッシュのオーケストレーター」として設計する。

- **ポイント4: バンドルサイズ制限への対応:** Edge RuntimeはNode.jsランタイムより制約が厳しく（1MB上限）、`zod`や`date-fns`などの重いライブラリがそのまま使えないケースがある。`bundlewatch`やVercelの`@vercel/edge`軽量ユーティリティへの移行が推奨される。

- **ポイント5: Middleware vs Edge Route の使い分け:** `middleware.ts`（全リクエストに対するグローバル処理）とEdge API Routes（特定エンドポイント）を混同しない設計が重要。Middlewareに重い処理を入れるとサイト全体のパフォーマンスに影響するため、本プロジェクトのようなNext.js App RouterではMiddlewareは認証確認のみに留めるべき。

### 10. TypeScript type safety patterns 2026

- **Template Literal Types の高度活用:** 文字列リテラル型を組み合わせたルーティングやAPIエンドポイントの型定義が主流化し、実行時エラーをコンパイル時に検出できる範囲が大幅に拡大している。

- **`satisfies` 演算子の定着:** `as const` に代わり `satisfies` を使った型推論の維持が標準パターンとなり、型の安全性を損なわずに補完が効く実装スタイルが浸透している。

- **Branded Types による値の区別:** `UserId` と `PropertyId` のような同じプリミティブ型の値を型レベルで区別するBranded（Opaque）Typesが、大規模コードベースでのバグ防止手法として採用増加中。

- **Effect-ts / neverthrow による型安全なエラーハンドリング:** `try/catch` に依存せず `Result<T, E>` 型でエラーを明示的に扱うパターンが普及し、エラーの取りこぼしをコンパイル時に検出できるアーキテクチャが増えている。

- **Zod + tRPC によるスキーマ駆動開発:** APIの入出力をZodスキーマで一元定義し、フロント・バック双方の型を自動導出する構成が事実上の標準となり、手書きの型定義との乖離リスクを排除している。
