# CTO Knowledge - 2026-05-22

## Daily Update (2026-05-22)

### 1. Next.js performance optimization 2026

- **React Server Components の徹底活用:** クライアントバンドルサイズを劇的に削減できるため、デフォルトをServer Componentsにして `'use client'` を必要最小限に絞ることが2026年のベストプラクティス。

- **Partial Prerendering (PPR) の本格採用:** 静的シェルと動的コンテンツを同一ページで共存させるPPRがstableになり、TTFBと動的コンテンツの両立が現実的に。`experimental.ppr` から正式APIへの移行を進めるべき。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15以降の `use cache` + `cacheTag` / `cacheLife` APIで、ページ単位ではなく関数・コンポーネント単位のキャッシュ制御が可能になり、不要な再レンダリングを大幅に削減できる。

- **Turbopack のデフォルト化に伴うビルド最適化:** `next dev --turbopack` がデフォルトになり、大規模プロジェクトではHMR速度が数倍改善。ただしカスタムwebpack設定との互換性確認が移行時の実務的ボトルネック。

- **Image / Font の自動最適化の恩恵を確実に受ける:** `next/image` のサイズ自動選択と `next/font` のゼロレイアウトシフトは設定不足で無効化されがち。`sizes` prop の適切な指定と `display: swap` 回避がCore Web Vitals直結の改善点。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の本格普及:** Next.js 15以降でPPRが安定化し、静的シェルを即座に配信しつつ動的コンテンツをストリームする手法が標準パターンに。ウォーターフォール問題を根本から解消できる。

- **`use()` フックによる宣言的なデータフェッチ:** React 19で正式化された`use(Promise)`パターンにより、サーバー側でSuspense境界を活用した細粒度のストリーミングが書きやすくなった。`async/await`と組み合わせた設計が主流。

- **Turbopackの実用化でビルド遅延が解消:** RSCのストリーミングはビルド複雑性を増すが、TurbopackのRSC対応成熟によりHMRのコストが大幅削減。開発体験のボトルネックが取り除かれた。

- **`dynamicIO`フラグと推奨キャッシュ戦略の変化:** Next.js 16系では`fetch`のデフォルトキャッシュ挙動が変更され、明示的な`cache`指定が必須に。ストリーミングと組み合わせると意図しないキャッシュバスティングが起きやすいため、設計時の意識が重要。

- **Server Actions との統合でRPCレイヤーが不要に:** フォームやミューテーションをServer Actionsで処理し、RSCストリーミングで結果を再描画する一気通貫フローが確立。REST/GraphQL APIレイヤーをBFFとして別途立てるコストを削減できる。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** TypeScriptプロジェクトではtRPCがデファクトに近づきつつあり、スキーマ定義不要でクライアント・サーバー間のE2E型安全を実現できるため、Next.js + Prismaスタックとの親和性が特に高い。

- **RESTは「基盤」として健在:** 外部公開APIや異言語間連携ではRESTの普及率は依然として圧倒的であり、OpenAPI 3.1 + Zodによるスキーマ駆動開発が標準化しつつある。

- **GraphQLはユースケースが絞られてきた:** BFF（Backend for Frontend）パターンや複雑なデータグラフを持つプロダクトには有効だが、単純なCRUDには過剰であるという認識が広まり、Relay/Apollo離れも一部で進んでいる。

- **エッジ・ストリーミングへの対応が差別化ポイント:** 2026年時点でVercel/Cloudflare Workers環境でのストリーミングレスポンス（Server-Sent Events、HTTP/2 streaming）対応がAPI設計の新たな要件となっており、tRPCもサブスクリプション対応が強化されている。

- **AIエージェント連携を見据えたAPI設計:** MCPやOpenAPI仕様ベースのツール定義が普及し、「人間が叩くAPI」に加えて「AIエージェントが自律的に利用するAPI」の設計思想（冪等性・自己記述性・エラー明確化）が重要性を増している。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジの標準ランタイムへ:** Cloudflare Workers・Fastly Compute@Edgeを中心にWasmが主流化し、言語非依存でコールドスタートほぼゼロの実行環境が整った。Next.jsのEdge Runtimeも実質Wasm前提の設計へ移行しつつある。

- **エッジDBとの統合が加速:** PlanetScale/Turso（libSQL）・Cloudflare D1・Neon ServerlessがHTTPベースのエッジ対応APIを提供し、「エッジでSQLが引ける」が当たり前になった。レイテンシ削減の恩恵を最大化するにはリージョン戦略の設計が重要。

- **AI推論のエッジオフロード:** 小型LLM（Phi-3 mini・Gemma 2B級）をエッジで直接実行するケースが増加。Cloudflare AI・AWS Inferentiaエッジノードにより、PII等の機密データをクラウド送信せず推論できる点がコンプライアンス面で評価されている。

- **オブザーバビリティの課題が顕在化:** エッジ関数は数百ノードに分散するため、従来のAPMツールでは追跡が困難。OpenTelemetryのエッジ対応とBaggageによるトレース伝播が実装必須となっており、設計初期からの組み込みを推奨。

- **コスト構造の再評価:** リクエスト単価は低いが、グローバル分散キャッシュとの組み合わせで「オリジンへのリクエストをほぼゼロ」にできるアーキテクチャが費用対効果最大。一方でステートフルな処理（WebSocket・長時間実行）はDurable Objects等の専用プリミティブを使わないとコストが跳ね上がる点に注意。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** FIDO2/WebAuthnベースのパスキーが主流となり、フィッシング耐性のある認証が標準になりつつある。パスワードレス移行を先延ばしにするほど技術的負債が積み上がる。

- **セッション管理の厳格化:** JWTの有効期限を短く（15分以下）設定し、リフレッシュトークンのローテーションと即時無効化機能を必須とする。「永続ログイン」の利便性とセキュリティのトレードオフを正しく設計すること。

- **デバイス信頼スコアリングの統合:** IPアドレスや時刻だけでなく、デバイスフィンガープリントや行動パターンを組み合わせたリスクベース認証が普及。異常検知時にのみMFAを要求するアダプティブ認証でUXを損なわずにセキュリティを強化できる。

- **サプライチェーン攻撃への対策:** 認証ライブラリや外部IdP（Auth0、Cognito等）の依存関係を定期的に監査し、SBOM（ソフトウェア部品表）管理を導入する。外部サービスの侵害が自プロダクト全体のアカウント乗っ取りに直結するリスクを忘れてはならない。

- **AI駆動のクレデンシャルスタッフィング対策:** ボット攻撃が高度化しており、従来のreCAPTCHAだけでは不十分。行動バイオメトリクスと機械学習ベースの異常検知を認証フローに組み込み、リアルタイムで不正ログイン試行を遮断する体制が求められる。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のエッジ対応成熟:** Prisma Client のエッジランタイム（Cloudflare Workers, Vercel Edge）対応が安定し、Supabase の Connection Pooler（PgBouncer → Supavisor）との組み合わせでサーバーレス環境でのコネクション枯渇問題がほぼ解消された。

- **Supabase の Row Level Security (RLS) が設計の中心へ:** RLSをアプリ層ではなくDB層で実装することで、Next.js の Server Actions や API Routes を通じたデータアクセスでも一貫したアクセス制御が担保できる。Prisma 経由でもサービスロールとアノニマスロールを使い分ける設計が主流になっている。

- **Prisma Accelerate によるグローバルキャッシュ戦略:** Prisma Accelerate（旧 Data Proxy）のクエリキャッシュ機能を活用し、Supabase の読み取りレプリカと組み合わせることで、グローバルユーザー向けのレイテンシを大幅に削減できる構成が現実的な選択肢になっている。

- **型安全なリアルタイム統合の課題:** Supabase Realtime はネイティブでは Prisma の型システムと統合されないため、`zod` によるランタイムバリデーションをリアルタイムペイロードに挟む設計パターンが事実上の標準になっている。

- **マイグレーション戦略の二重管理問題:** `prisma migrate` と Supabase の組み込みマイグレーション管理が競合しやすく、チームでは `prisma migrate diff` でSQL生成 → Supabase ダッシュボードまたは `supabase db push` で適用という一方向フローに統一することで摩擦を避けるのがベストプラクティス。

### 7. WebAssembly Rust performance 2026

- **Component Model の成熟:** WebAssembly Component Model（WASI 0.2）が2025年に安定版となり、RustコンポーネントをNext.jsなどのJSエコシステムとシームレスに統合できるようになった。wasm-bindgenへの依存が減り、インターフェース定義がより型安全になっている。

- **SIMD・スレッド対応の実用化:** WASMのSIMDとshared memoryスレッドが主要ブラウザで広くサポートされ、Rustの`rayon`相当の並列処理がブラウザ内でも動作可能に。画像処理・ML推論など計算集約型タスクでネイティブ比95%の性能を達成するケースが増えている。

- **ファイルサイズ問題の大幅改善:** `wasm-opt`（Binaryen）＋Rustの`size`プロファイル最適化により、バンドルサイズが従来比30〜50%削減。`wasm-pack`との組み合わせでtree-shakingも効くため、Rustを部分的に導入するコストが下がった。

- **エッジランタイムでの採用加速:** Cloudflare Workers・Vercel Edge RuntimeがWASMをファーストクラスサポートし、RustロジックをNode.js依存なしにデプロイできる。コールドスタートがほぼゼロのためサーバーレス環境との相性が特に良い。

- **デバッグ・プロファイリング環境の整備:** DWARF情報を使ったソースマップ対応がChrome DevToolsで安定し、RustコードをWASMレベルでブレークポイントデバッグできる。本番採用の最大障壁だったデバッグ困難問題が実用レベルで解消された。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** デフォルトでServer Componentsを使い、インタラクティブ性が必要な箇所だけ`'use client'`を付与する。クライアントバンドルを最小化し、初期表示パフォーマンスが大幅に向上する。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的コンテンツを同一ページ内で共存させるPPRが安定化し、ストリーミングとキャッシュ戦略の設計が重要になった。`<Suspense>`境界の配置がパフォーマンスの鍵を握る。

- **Server Actions によるAPI層の簡略化:** フォーム送信やデータ変更を`'use server'`関数で直接処理し、別途APIルートを作るコストを削減。ただしバリデーション（Zod）とCSRF対策は必須。

- **`use cache` ディレクティブによる細粒度キャッシュ:** `fetch`キャッシュから`use cache`+`cacheTag`/`revalidateTag`への移行が進み、コンポーネント・関数レベルで宣言的にキャッシュ戦略を制御できる。

- **Route Handlers の役割縮小:** App Router成熟により、Route Handlersは外部Webhookやファイルダウンロードなど真に必要な箇所に限定される。内部データフェッチはServer Componentsから直接DB/サービスを呼ぶパターンが主流。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge Runtimeでの計算コスト最小化:** Edge Functionsは起動レイテンシが極めて低い反面、Node.js APIの一部が使えないため、`crypto`や`fetch`などWeb標準APIに限定したロジック設計が必須。重い処理はバックグラウンドでサーバー関数に委譲するパターンが定着してきた。

- **ポイント2: Partial Prerendering（PPR）との統合が主流に:** Next.js 15以降でPPRが安定化し、静的シェル＋動的ストリームの組み合わせがEdgeで高速に動作するアーキテクチャが標準化。Edge Functionsを「認証・パーソナライズのゲートウェイ」として位置づけ、ページ本体はCDNキャッシュから配信する分離設計が効果的。

- **ポイント3: Middleware中のデータベース直接アクセスは禁止パターン:** Upstash RedisやEdge-compatibleなKVストアを挟むことで、Middlewareのコールドスタートを100ms以下に抑える。PrismaやDrizzleのEdgeアダプターも成熟したが、接続プール管理に依然注意が必要。

- **ポイント4: `waitUntil()` を使った非同期バックグラウンド処理:** レスポンス返却後に分析ログ送信やキャッシュウォームアップを行う`ctx.waitUntil()`パターンが最適化の鍵。ユーザー体感レイテンシを犠牲にせず副作用処理を完了できる。

- **ポイント5: リージョン戦略の見直し（Japan東京リージョン優先）:** Vercelのリージョン指定（`export const preferredRegion = 'hnd1'`）を明示することで、日本ユーザーへのTTFBを劇的改善できる。グローバル展開より**ターゲット市場に近いエッジへの集中配置**の方がsumitsugiのような国内向けサービスでは有効。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { _brand: 'UserId' }` のような Branded Types が標準パターンとなり、プリミティブ型の誤用（例: userId に email を渡す）をコンパイル時に防止できる。

- **`satisfies` 演算子の活用:** TypeScript 4.9+ の `satisfies` が広く使われ、型推論を失わずに型チェックを行えるため、設定オブジェクトやルックアップテーブルで特に有効。

- **Template Literal Types によるAPI型安全性:** `type Route = '/users' | '/posts/${string}'` のようなパターンで、ルーティングや i18n キーの型をコンパイル時に検証し、実行時エラーを大幅削減できる。

- **`const` 型パラメータ（TypeScript 5.0+）:** `function fn<const T>(arg: T)` により、配列・オブジェクトリテラルを自動的に `readonly` かつ最狭型で推論でき、as const の記述を不要にする。

- **Zod + `z.infer<>` によるスキーマ駆動型定義:** ランタイムバリデーションスキーマから TypeScript 型を自動生成するパターンが定着し、外部 API レスポンスやユーザー入力の型が「宣言と検証の単一ソース」として管理される。
