# CTO Knowledge - 2026-02-28

## Daily Update (2026-02-28)

### 1. Next.js performance optimization 2026

- **Partial Pre-rendering (PPR) の活用:** Next.js 15で安定化したPPRにより、静的シェルと動的コンテンツを同一ルートで共存できる。TTFBを維持しながらパーソナライズコンテンツを配信できるため、従来の「静的か動的か」の二択が不要になった。

- **Turbopackへの移行:** `next dev --turbo`が本番対応となり、大規模コードベースでHMRが最大10倍高速化。`bun run dev`との組み合わせでローカル開発体験が大幅に向上する。

- **React Server Components (RSC) のデータフェッチ最適化:** クライアントバンドルを削減するため、データ取得ロジックをRSCに集約し`use cache`ディレクティブで細粒度キャッシュを制御する。`fetch`の`cache`オプションよりも明示的で予測可能。

- **Bundle分析の継続的実施:** `@next/bundle-analyzer`をCI/CDに組み込み、`next build`後のバンドルサイズを自動チェック。特にApp RouterでのClient Componentの肥大化（`"use client"`の誤用）が主要なパフォーマンスリグレッション要因になりやすい。

- **Streaming + Suspenseによる知覚速度の改善:** ページ全体のブロッキングを避け、重いコンポーネント（ダッシュボード、リスト）をSuspense境界で分割してストリーミング配信する。FCP（First Contentful Paint）の改善がCore Web Vitalsスコアに直結する。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の普及:** Next.js 15以降でPPRが安定化し、静的シェルをCDNキャッシュしつつ動的コンテンツをストリーミングするハイブリッド戦略が標準パターンになりつつある。TTFBとCWVの両立が現実的になった。

- **Suspense境界設計の重要性増大:** ストリーミングの恩恵を最大化するには`<Suspense>`の粒度設計がボトルネックになる。データフェッチ単位ではなくUX単位で境界を引くことが求められ、設計スキルの差が顕著に出る。

- **Server Actions + ストリーミングの統合:** フォーム送信・楽観的UI更新とストリーミングレスポンスの組み合わせが成熟し、ページ遷移なしのサーバーサイド処理が自然に書けるようになった。ただしキャッシュ無効化戦略の複雑さは依然課題。

- **エッジランタイムとの相性問題:** CloudflareやVercel Edgeでのストリーミングは制約（実行時間、メモリ）があり、全コンポーネントをエッジで動かす設計は現実的でないケースが多い。Node.jsランタイムとの使い分け判断が重要。

- **モニタリングの難しさ:** ストリーミングレスポンスは従来のAPMツールでは計測が困難。チャンク単位のTTFB・FCP可視化にはOpenTelemetry + カスタムスパンの実装が必要で、可観測性コストが上がる点を考慮する必要がある。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** tRPCはNext.js/TypeScriptスタックでのデファクトになりつつあり、クライアント・サーバー間のスキーマ共有によりAPI契約違反をビルド時に検出できる。ただしBFFパターン専用であり、外部公開APIには不向き。

- **REST vs GraphQLの決着:** 2026時点でGraphQLは「オーバーエンジニアリング」の文脈で再評価され、複雑なデータグラフ（SNS・ECなど）以外ではREST+OpenAPI 3.1が実用的な選択肢として回帰している。N+1問題やキャッシュ複雑性がGraphQL採用コストを押し上げている。

- **OpenAPI 3.1 + コード生成の成熟:** `zod-openapi`や`hono`等でスキーマファーストなREST設計が効率化され、型安全なクライアントSDKの自動生成が標準化。tRPCに匹敵するDXをRESTで実現できる。

- **HTTP/3とエッジAPIの影響:** CloudflareやVercelのエッジランタイムの普及により、レイテンシ敏感なAPIはエッジ配置が前提に。GraphQLのような重い処理はエッジと相性が悪く、REST/tRPCが有利。

- **AIエージェント向けAPI設計:** MCPやOpenAPI互換の「ツール定義」として設計されたAPIがエージェント統合で優位に。2026ではAIが消費しやすいAPI設計（明確な操作単位・べき等性・詳細なエラーレスポンス）が競争優位になりつつある。

### 4. serverless edge computing 2026

- **ポイント1: WebAssembly (Wasm) がエッジの標準実行環境に:** Cloudflare Workers・Fastly Compute@Edgeを中心に、Wasmがコンテナに代わるエッジ実行環境として普及。コールドスタートがほぼゼロになり、Node.js依存から脱却できる。

- **ポイント2: AIインファレンスのエッジシフト:** LLMの量子化技術の進歩により、GPT-4クラスのモデルをエッジで動かすコストが現実的になった。レイテンシ削減とデータプライバシー確保が同時に達成できる。

- **ポイント3: SQLite-on-Edgeの台頭:** Cloudflare D1・Turso (libSQL) により、エッジから直接DBアクセスが可能に。分散レプリケーションが自動化され、グローバルなread latencyが劇的に改善される。

- **ポイント4: エッジ/オリジン間のアーキテクチャ複雑性が課題:** キャッシュ戦略・認証状態の同期・デバッグのしにくさが依然としてボトルネック。Next.jsのような フレームワークが `runtime: 'edge'` を段階的に吸収しているが、本番運用での落とし穴は多い。

- **ポイント5: コスト計算モデルの再評価が必要:** リクエスト課金から CPU時間課金へのシフトが進み、計算集約型の処理をエッジに移すと予想外にコスト増になるケースがある。ワークロード特性に応じたオリジン/エッジの使い分けが設計の肝になる。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）への移行加速:** FIDO2/WebAuthn標準のパスキーがパスワード代替として主流化。フィッシング耐性が高く、ユーザー体験も向上するため、新規サービスでは初期設計からパスキーを第一認証手段として組み込むべき。

- **トークン有効期限の短縮とリフレッシュ戦略の厳格化:** アクセストークンは5〜15分以内に設定し、リフレッシュトークンのローテーション（Refresh Token Rotation）を必須化。トークン漏洩時の被害範囲を最小化するゼロトラスト設計が標準。

- **デバイスフィンガープリントとリスクベース認証の組み合わせ:** 静的なMFAだけでなく、ログイン時のデバイス・場所・行動パターンを継続的に評価するアダプティブ認証を導入。異常検知時のみ追加認証を要求することでUXと安全性を両立。

- **サプライチェーン攻撃への対策（IdP依存リスク）:** Auth0・Cognitoなどサードパーティ認証基盤への依存度を評価し、IdPが侵害された際のフォールバック戦略を事前設計。依存ライブラリのSBOM管理とSHA固定も必須。

- **セッション管理のサーバーサイド強化:** JWTのステートレス設計に頼りすぎず、重要操作（決済・設定変更等）はサーバーサイドセッション検証を併用。ログアウト時の即時無効化と「すべてのデバイスからログアウト」機能を必ず実装。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORM の Edge Runtime 対応成熟:** Prisma 6.x では `@prisma/adapter-pg` を使ったドライバーアダプターが安定し、Next.js Edge Functions・Cloudflare Workers での動作が実用レベルに達した。`DATABASE_URL` の接続プール設定（Supavisor経由）が必須となる。

- **Supabase Branching によるDB開発フロー変革:** Supabase の Database Branching が GA化し、PRごとに独立したDBブランチを持てるようになった。これにより「マイグレーション先行・レビュー後マージ」のワークフローが標準化され、本番DBへの直接マイグレーションリスクが大幅低減。

- **pgvector × Supabase の AI統合が主流化:** `pgvector` 拡張を活用したベクトル検索が、別途Pinecone等を使わずSupabase単体で完結できるようになった。RAGアーキテクチャにおいてRDBとベクトルDBの二重管理コストを削減できる。

- **接続プール管理は Supavisor 一択へ:** PgBouncerから Supavisor（Supabase公式のElixir製プーラー）への移行が推奨され、サーバーレス環境での大量短命コネクション問題への対応が改善。Prisma側では `?pgbouncer=true` に加え `connection_limit=1` の設定が重要。

- **Row Level Security (RLS) と Prisma の共存戦略:** Supabase の RLS を活かしつつ Prisma を使う場合、`SET LOCAL role = 'authenticated'` をトランザクション内で実行するミドルウェアパターンが定着。アプリ層とDB層の二重セキュリティで堅牢な設計が実現できる。

### 7. WebAssembly Rust performance 2026

- **ポイント1: WASIp2（Component Model）の実用化加速:** 2026年はWASI Preview 2が主流となり、RustコンパニオントゥWasmのエコシステムが成熟。`wasm-bindgen`や`wit-bindgen`によるホスト連携が安定し、プロダクション採用のハードルが大幅低下。

- **ポイント2: SIMD・スレッド並列化の標準化完了:** WebAssembly SIMDとThreads提案が主要ブラウザで完全サポート済み。RustのSIMDライブラリ（`packed_simd`, `wide`）経由でネイティブに近い演算性能が実現でき、画像処理・ML推論への実戦投入が現実的。

- **ポイント3: JIT最適化の成熟によるネイティブ比95%超の性能:** V8・SpiderMonkeyのWasm JITが洗練され、計算集約型タスクではRust+WasmはC++ネイティブ比90〜97%の性能を達成。ただしメモリアクセスパターンの最適化（線形メモリ設計）が依然クリティカル。

- **ポイント4: エッジ実行環境（Cloudflare Workers / Fastly）での本番稼働増加:** サーバーレスエッジでRust+WasmはNode.js比で3〜10倍の低レイテンシを実現。コールドスタートがほぼゼロのため、低遅延APIやリアルタイム変換処理の採用事例が急増。

- **ポイント5: `cargo component`ツールチェーンによる開発体験の標準化:** Bytecode Allianceの`cargo component`が安定リリースされ、Rustプロジェクトから直接Wasmコンポーネントをビルド・テストできる開発フローが確立。CI/CDパイプラインへの組み込みが容易になり、チーム開発の実用性が大幅向上。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの設計:** `'use client'` はコンポーネントツリーの末端（インタラクティブな葉ノード）にのみ配置し、バンドルサイズを最小化する「クライアント境界の押し下げ」パターンが標準化。データフェッチはサーバーコンポーネントで直接行うことでウォーターフォールを排除。

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降でPPRが安定し、静的シェル＋動的ストリーミングのハイブリッドレンダリングがデファクト。`<Suspense>` 境界の設計がアーキテクチャの核心になっており、ページの初期表示速度と動的コンテンツを両立。

- **Server Actions でAPIルートを置き換え:** フォーム処理・データミューテーションにServer Actionsを使うことでREST APIのボイラープレートが消滅。Progressive Enhancement対応でJSオフ環境でも動作し、型安全性もエンドツーエンドで担保される。

- **キャッシュ戦略の明示化が必須:** Next.js 15でデフォルトキャッシュが `no-store` に変更され、開発者が `revalidatePath` / `revalidateTag` / `unstable_cache` を意図的に設計する必要がある。「キャッシュは暗黙」から「キャッシュは宣言」へのパラダイムシフト。

- **並列ルート＆インターセプトルートによるUX向上:** `@slot` と `(.)route` を組み合わせたモーダルルーティングが普及し、ページ遷移なしでURLを変えるGitHub風UIが実装しやすくなった。ダッシュボード系アプリのUI設計に特に有効。

### 9. Vercel Edge Functions optimization 2026

- **Edge RuntimeとNode.js Runtimeの使い分け:** Edge FunctionsはV8 Isolateベースで起動レイテンシがほぼゼロだが、Node.js APIが制限されるため、認証ミドルウェアやA/Bテストなど軽量ロジックに限定し、DB接続やファイルI/OはNode.js Runtimeに委ねるのが最適解。

- **Fluid Computeによるコールドスタート問題の実質的解消:** Vercelが導入したFluid Computeにより、従来のサーバーレス関数でもEdge並みの起動速度を実現可能になり、「Edge一択」ではなく用途に応じたランタイム選択の重要性が増している。

- **バンドルサイズの厳格管理が必須:** Edge Functionsは圧縮後4MBの上限があるため、依存ライブラリの選定とtree-shakingが不可欠。特にORM（Prisma等）の使用は避け、軽量クライアント（`@vercel/postgres`等）を採用すること。

- **Streaming Responseによるパフォーマンス体感向上:** `ReadableStream`を使ったレスポンスのストリーミングはTime-to-First-Byteを劇的に改善し、LLMや重い処理の結果表示に特に有効。Next.js App RouterとEdgeの組み合わせで標準的なパターンになっている。

- **データローカリティとGDPR対応:** Edge Functionsはグローバル分散実行が強みだが、個人データを扱う処理はリージョン制限（`export const runtime = 'edge'; export const preferredRegion = ['nrt1']`）で日本リージョンに固定し、規制対応とレイテンシを両立する設計が重要。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の`satisfies`が2026年においてさらに普及し、型推論を維持しつつ型チェックを強制できるため、`as`キャストを排除した安全なコードパターンが標準化されている。

- **Template Literal Types + Branded Types の組み合わせ:** `type UserId = string & { readonly __brand: 'UserId' }`のようなBranded Typesと、テンプレートリテラル型を組み合わせることで、ID混在バグやSQLインジェクション系ミスをコンパイル時に防ぐアプローチが主流になっている。

- **`const` type parameters（TypeScript 5.x）の定着:** `function f<const T>(x: T)`により配列・オブジェクトリテラルを自動的にreadonly narrowingできるようになり、`as const`の手動付与が不要なケースが増え、コードの可読性が向上している。

- **Zod v4 + `z.infer`による型とバリデーションの一元管理:** スキーマ定義から型を自動導出するパターンが完全に定着し、APIレスポンス・フォームデータ・環境変数すべてのシステム境界でZod/Valibot系ライブラリを使うことが実質的なベストプラクティスとなっている。

- **`NoInfer<T>`ユーティリティ型による型推論制御:** TypeScript 5.4で追加された`NoInfer<T>`を使い、ジェネリック関数の型推論サイトを明示的に制御することで、意図しない型の拡大推論（widening）を防ぎライブラリ品質が向上している。
