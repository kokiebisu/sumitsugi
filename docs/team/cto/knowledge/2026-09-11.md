# CTO Knowledge - 2026-09-11

## Daily Update (2026-09-11)

### 1. Next.js performance optimization 2026

- **ポイント1: Partial Prerendering (PPR) の本格運用** Next.js 15以降で導入されたPPRがNext.js 16で安定版となり、静的シェルと動的コンテンツを同一ページ内で組み合わせられる。初期表示速度を保ちながらパーソナライズされたコンテンツを配信できるため、物件一覧ページなど「基本情報は静的・空室状況は動的」という構成に最適。

- **ポイント2: React Server Components前提のデータ取得最適化** クライアントへのJS転送量を最小化するため、データフェッチをできる限りサーバー側に寄せ、`use client`境界を末端コンポーネントに限定する設計が主流。物件詳細ページの画像ギャラリーやフォーム部分のみクライアント化し、それ以外はRSCで完結させるのが定石。

- **ポイント3: Turbopackによるビルド・開発体験の高速化** Turbopackがデフォルトビルドツールとして定着し、大規模コードベースでもHMRとプロダクションビルドが大幅に高速化。CI上の`bun run build`時間短縮に直結するため、PRサイクルのスループット向上に寄与する。

- **ポイント4: 画像・フォント最適化のエッジ処理** `next/image`のエッジ最適化とAVIF優先配信が標準化し、Core Web Vitals（特にLCP）改善に効果的。前の住人の物件写真のような画像点数が多いページでは、優先度制御（`priority`属性の適切な使用）が引き続き重要。

- **ポイント5: キャッシュ戦略の明示的制御** `fetch`のデフォルトキャッシュ挙動が変更されたことで、`revalidate`や`cache: 'no-store'`を意図的に指定する設計が必須に。ステータスが`draft`/`public`で切り替わる物件情報のような可変データは、キャッシュミスによる古い情報表示を防ぐため明示的な再検証戦略が必要。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** Next.js 16ではRSCのストリーミングとSuspenseの組み合わせがデフォルト挙動として定着し、`loading.tsx`やネストされた`<Suspense>`境界を細かく分割することでTTFB（Time to First Byte）を維持したままファーストビューを段階的に表示できる。物件一覧ページなど重いデータ取得を伴う画面ではこの粒度設計がLCP改善に直結する。

- **Partial Prerendering (PPR) の実用化:** 静的シェル（ヘッダー・レイアウト）を事前レンダリングし、動的部分（在庫状況・価格など）だけをストリーミングで後追い表示するPPRがNext.jsで安定運用フェーズに入っており、CDNエッジでの配信と組み合わせることでコストとパフォーマンスの両立がしやすくなっている。

- **Server Actions とキャッシュ戦略の成熟:** `use cache`ディレクティブやタグベースの再検証（`revalidateTag`）がRSCと組み合わさり、物件データの更新（ステータス変更など）を伴う書き込み系操作でもキャッシュの一貫性を保ちやすくなった。ミューテーション後の楽観的UI更新パターンが標準化されつつある。

- **クライアントバンドル削減の実効性:** RSCによりインタラクティブ性が不要なコンポーネント（物件詳細の説明文、静的な引継ぎ情報表示など）を明示的に`"use client"`から切り離すことで、初期JSペイロードを大幅に削減できる。うちのようなAirbnb風UIでは画像ギャラリーやフォームなど「本当にクライアントが必要な部分」を意識的に絞り込む設計が効いてくる。

- **エラーバウンダリとストリーミングの相性:** ストリーミング中に発生したサーバーエラーを`error.tsx`で適切にキャッチしつつ、既にフラッシュ済みのチャンクを壊さない設計が重要になっており、決済・認証フローなど途中失敗が許されない多段階フローでは、ストリーミング境界とエラー境界を意図的に一致させる設計判断が求められる。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCやOpenAPI+Zodによる「スキーマファースト」開発が主流化し、フロントとバックエンドで型を共有することでAPI変更時の実行時エラーを大幅に削減できる。sumitsugiのようなNext.js＋TypeScript構成では、tRPCまたはZodスキーマ駆動のRoute Handlersが開発速度と型安全性の両立に有利。

- **ポイント2:** GraphQLは複雑な集約クエリ（物件検索の複合フィルタ等）に強い一方、キャッシュ制御やCDN活用の難しさがネックであり続けている。単純なCRUD中心のMVPフェーズでは、GraphQLの学習・運用コストに見合わないケースが多く、REST/tRPCで十分。

- **ポイント3:** BFF（Backend for Frontend）パターンとtRPCの組み合わせが、モノレポ構成のNext.jsアプリで定番化しつつある。API層を薄く保ちServer Actions/Route Handlersに寄せることで、マイクロサービス化を急がず単一デプロイでもスケールしやすい。

- **ポイント4:** REST APIの契約テスト（Contract Testing）とOpenAPI自動生成ドキュメントが、外部連携（決済・本人確認等）を持つプロダクトでの必須要件になっている。法務確認やベータローンチ前の外部パートナー連携を控える現フェーズでは、契約の明文化がリスク低減に直結する。

- **ポイント5:** エッジランタイム（Vercel Edge Functions等）向けにAPI設計を最適化する動きが加速しており、レイテンシ要件がシビアな検索・地図機能ではストリーミングレスポンス（Server-Sent Events/Suspense）を前提としたAPI設計が推奨される。

### 4. serverless edge computing 2026

- **エッジでのLLM推論の一般化:** WebAssembly (WASM) とWASI-NNの成熟により、Cloudflare WorkersやDeno Deployなどのエッジランタイムで軽量モデルの推論が実用段階に入り、ユーザーに最も近いPoPでレイテンシを1桁ミリ秒台に抑えられるようになっている。

- **コールドスタート問題の実質的解消:** V8 isolateベースのランタイムとプリウォーミング技術の進化により、従来のFaaSで課題だったコールドスタートが数msレベルまで縮小し、常時起動サーバーとの性能差がほぼなくなってきている。

- **エッジDBとグローバル整合性の両立:** Turso（libSQL）やCloudflare D1のようなSQLiteベースの分散DBが、リージョン間レプリケーションと強整合性のトレードオフを開発者が細かく選択できる形で提供し始めており、住所・在庫情報など地理分散が重要なsumitsugiのようなプラットフォームに向く。

- **請求モデルのCPU時間課金への移行:** リクエスト数ではなくCPU使用時間ベースの課金（Cloudflare Workers Paidプラン等）が主流化し、I/O待ちの多い物件検索APIのようなワークロードはコスト効率が大幅に改善する一方、計算集約的な処理は慎重な設計が必要。

- **Next.jsとのネイティブ統合の深化:** Next.js 16のPartial PrerenderingとApp RouterがVercel Edge FunctionsやCloudflare Workersとの統合を前提に最適化されており、sumitsugiの物件一覧・詳細ページのような読み取り主体のルートをエッジでレンダリングしつつ、認証必須ページのみオリジンにフォールバックする設計がしやすくなっている。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証（WebAuthn/Passkeys）が標準になりつつあり、フィッシング耐性とUX向上を同時に実現できるため、sumitsugiのような個人情報を扱うサービスでは優先的に導入すべき。
- **多要素認証の適応型強化:** リスクベース認証（デバイス指紋・行動パターン・地理的位置を組み合わせたリスクスコアリング）により、不審なログイン試行時のみ追加認証を要求し、通常時のUXを損なわない設計が主流。
- **トークン管理の厳格化:** JWTやセッショントークンは短命化（15分以内）＋リフレッシュトークンのローテーション必須。localStorageでの保存はXSS耐性が低いため、httpOnly Cookie + SameSite属性での管理を徹底する。
- **ゼロトラスト前提の認可設計:** 認証後も全APIリクエストで権限を再検証し、「前の住人」「次の住人」間のデータアクセス境界（物件情報・個人情報の分離）をサーバー側で厳密に制御する必要がある。
- **監査ログと異常検知の自動化:** 認証失敗・パスワードリセット・権限変更などのイベントを構造化ログで記録し、異常なログインパターンを自動検知する仕組みを早期に組み込むことで、法務確認フェーズでのセキュリティ説明責任にも対応しやすくなる。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はRust製クエリエンジンを段階的に廃止し、TypeScript純正のクエリコンパイラへ移行が進んでいます。バイナリ依存が減ることでVercel/Edge環境やDockerイメージサイズが軽量化され、コールドスタートが改善します。

- **ポイント2:** SupabaseのRLS（Row Level Security）とPrismaを併用する場合、Prisma自体はRLSを認識しないため、`auth.uid()`ベースのポリシーをSQLマイグレーションで直接管理し、Prisma Migrateとの二重管理を避ける設計が定着しつつあります。

- **ポイント3:** Supabaseの接続プーリング（PgBouncer/Supavisor）とPrismaのコネクション管理は相性問題が出やすく、サーバーレス関数からは`pgbouncer=true`＋`connection_limit=1`を明示し、マイグレーション実行時のみ直接接続を使う運用が推奨パターンです。

- **ポイント4:** Prisma AccelerateやSupabaseのEdge Functionsを組み合わせたキャッシュ層により、物件検索のような読み取り主体のクエリはDB直叩きより大幅にレイテンシ改善が可能です。sumitsugiのようなpublic物件一覧は良い適用対象になります。

- **ポイント5:** スキーマの`status: 'draft' | 'public'`のようなUnion型はPrisma側でも`enum`定義し、DBレベルのCHECK制約とTypeScript型を一致させることで、アプリ層とDB層の状態不整合を防げます（マイグレーション時は必ず全usageをgrepしてから変更）。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASM GC (Garbage Collection) 提案が主要ブラウザで安定し、RustのようなGCなし言語は依然として最小バイナリサイズと予測可能なレイテンシで優位性を保っている。画像処理や暗号化などCPU集約的な処理をフロントエンドにオフロードする際、Rust+WASMの組み合わせは純粋なJS実装比で3〜10倍の性能差が出るケースが多い。

- **ポイント2:** Component Model / WASI Preview 2の成熟により、Wasmtimeなどのランタイムでネイティブに近い起動速度（ミリ秒未満のコールドスタート）が実現しつつあり、サーバーレス関数やエッジコンピューティング用途でRust製WASMモジュールを採用する動きが加速している。物件検索や価格計算のようなロジックをエッジで実行すればAPIレイテンシを大幅に削減できる可能性がある。

- **ポイント3:** SIMD命令のWASM対応が標準化されたことで、画像最適化（物件写真のリサイズ・圧縮）やPDF生成のようなバッチ処理をブラウザ内で完結させられるようになり、サーバー負荷とインフラコストを削減できる。

- **ポイント4:** wasm-bindgen / wasm-packのツールチェーンは成熟しているが、依然としてバンドルサイズとJS↔WASM間のシリアライズオーバーヘッドが実運用上のボトルネック。頻繁に小さいデータをやり取りする用途（フォーム検証など）にはWASM導入の費用対効果が薄く、計算量の多い処理（画像・PDF・暗号）に限定して採用するのが現実的な判断基準になる。

- **ポイント5:** Next.js 16のようなRSC中心アーキテクチャでは、WASMモジュールをサーバーコンポーネント側（Node/Bun runtime）で実行するパターンが増えており、クライアント配信不要でRustの性能をそのまま享受できる。sumitsugiのようなプロジェクトでは、PDF生成や物件データのバッチ変換処理をBunのWASM対応で高速化する余地がある。

### 8. Next.js App Router patterns 2026

- **Server Components優先の設計:** 2026年時点でもデフォルトはServer Componentsとし、`'use client'`は本当にインタラクティブな末端コンポーネントにのみ限定するのがベストプラクティス。データフェッチをコンポーネント内で直接行うことで、クライアントバンドルサイズを最小化できる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的コンテンツを1つのルートで組み合わせられるPPRが安定版に移行し、`loading.tsx`のSuspense境界設計が事実上必須のパフォーマンス最適化パターンになっている。物件一覧のような「静的レイアウト＋動的な空室情報」構成に特に有効。

- **Server Actionsによるフォーム処理の標準化:** API Routeを介さず`'use server'`関数を直接呼び出すパターンが定着し、Zodバリデーションと組み合わせることで型安全なフォーム処理が実現できる。内見予約や問い合わせフォームなどの実装がシンプルになる一方、CSRF対策は引き続き明示的に意識する必要がある。

- **Route Handlers + Middlewareの責務分離:** 認証チェックはMiddlewareで軽量に行い、実際のデータアクセス制御はServer Component/Route Handler側で行う二層防御パターンが推奨される。特にセラー（前の住人）向け管理画面のような権限分岐が多い箇所で有効。

- **キャッシュ戦略の明示化:** `fetch`のデフォルトキャッシュ挙動への暗黙依存を避け、`revalidateTag`/`revalidatePath`によるオンデマンド再検証を明示的に設計するのがチーム開発での事故防止に直結する。物件ステータス（`draft`/`public`）切り替え時のキャッシュ無効化は特に要注意ポイント。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Vercel Edge FunctionsはV8 isolateベースで動作するため、コールドスタートがほぼゼロに近く、認証チェックやリダイレクトなどの軽量処理はEdge、DB接続を伴う重い処理はNode.js Runtimeに振り分ける「ハイブリッド配置」が2026年のベストプラクティスになっている。
- **ポイント2:** Edge Config（KVストア）とEdge Middlewareを組み合わせることで、フィーチャーフラグやA/Bテストの判定をオリジンサーバーに触れずミリ秒単位で完結でき、`sumitsugi`のようなdraft/public出し分けロジックもMiddleware側に寄せることでレイテンシを削減できる。
- **ポイント3:** ISR（Incremental Static Regeneration）とEdge Cacheの併用が主流になり、物件一覧のような更新頻度が中程度のページは`revalidate`タグベースの部分再検証で、フルリビルドなしに鮮度を保てる。
- **ポイント4:** Edge RuntimeはNode.js APIの一部（fs, 一部のnet系）が使えない制約が依然残るため、Prisma等の重いORMをEdge Functionsに持ち込むとビルドエラーになりやすく、DBアクセスは引き続きServer Actions／Node Runtimeに分離するのが安全。
- **ポイント5:** Observability面ではVercelのEdge Function実行ログがOpenTelemetry対応を強化しており、地理的に分散したユーザーのレイテンシ計測がしやすくなったため、パフォーマンスSLAを地域別に設定する運用が現実的になってきている。

### 10. TypeScript type safety patterns 2026

- **ポイント1（Branded Types / Nominal Typing）:** IDや金額など構造的に同じ`string`/`number`型でも意味が異なる値は`type UserId = string & { readonly __brand: 'UserId' }`のようなブランド型で区別し、コンパイル時に取り違えバグを防ぐパターンが定着してきている。

- **ポイント2（`satisfies`演算子の活用）:** 型注釈で推論を狭めずに、オブジェクトリテラルが特定の型を満たすことだけを検証できる`satisfies`が標準的になり、設定オブジェクトやルーティング定義などで「型安全性」と「リテラル型の恩恵」を両立できる。

- **ポイント3（Zodなどによるランタイム検証とスキーマ駆動開発）:** APIレスポンスやフォーム入力など外部境界ではZodスキーマから型を`z.infer`で導出する「スキーマファースト」が主流になり、コンパイル時の型とランタイムの実際のデータ形状のズレを防いでいる。当プロジェクトでも標準ルールとして採用済み。

- **ポイント4（Template Literal Typesによる文字列の型安全化）:** ルートパスやCSSクラス名、i18nキーなど文字列ベースの値をテンプレートリテラル型で厳密に型付けし、タイポや不正なパスをコンパイル時に検出する使い方が広がっている。

- **ポイント5（`unknown`優先とtype guardの徹底）:** `any`の使用を実質禁止し、外部データは`unknown`で受けてからtype predicate（`is`関数）やZodで絞り込む設計がベストプラクティスとして定着し、TypeScript 5.x系のcontrol flow analysis改善もこれを後押ししている。
