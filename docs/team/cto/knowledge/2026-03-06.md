# CTO Knowledge - 2026-03-06

## Daily Update (2026-03-06)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** 2026年時点でRSCはNext.jsのデフォルト設計思想となり、クライアントバンドルサイズを劇的に削減できる。`'use client'`は最小限に留め、データフェッチはサーバー側で完結させるのが基本。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降で安定化したPPRにより、静的シェルと動的ストリーミングを1リクエストで配信可能。ISRとSSRの使い分け議論が不要になり、ページ単位でなくコンポーネント単位でレンダリング戦略を選択できる。

- **`next/cache` APIによる細粒度キャッシュ制御:** `unstable_cache`や`revalidateTag`を活用したタグベースのオンデマンド再検証が主流。CDNとサーバーキャッシュを統合的に管理し、不必要な再レンダリングを排除することがパフォーマンスの核心。

- **Turbopack移行によるビルド高速化:** 2026年ではTurbopackが実質デフォルトとなり、大規模プロジェクトでのHMRが10倍以上高速化。`next.config.ts`のTypeScript対応も含め、開発体験自体をパフォーマンス指標として計測することが重要。

- **Core Web Vitals重視のImage/Font最適化継続:** `next/image`のAVIF対応とフォントサブセット自動生成は成熟しているが、LCPターゲット要素への`priority`付与漏れと、レイアウトシフト(CLS)を引き起こすサーバー/クライアント不一致が依然として頻出する実装ミス。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化:** 2026年時点では、RSCストリーミングはSuspense境界の配置が性能の鍵となっており、コンポーネントツリーの上位ではなく、データ依存の最小単位に境界を設置することでTTFB（初期バイト到達時間）を大幅に改善できる。

- **PPR（Partial Prerendering）の本格普及:** Next.js 15以降で安定化したPPRにより、静的シェルを即座にストリーミングしつつ動的コンポーネントをサスペンドする戦略が標準化されつつあり、Edge Runtimeとの組み合わせで世界規模の低レイテンシ配信が現実的になった。

- **ストリーミングとSEOの共存問題の解決:** クローラーのRSCストリーミング対応が進み、`<Suspense>`でラップされたコンテンツもインデックスされるようになったが、クリティカルコンテンツはfallback外に置く設計原則は依然として重要。

- **Server ActionsとStreaming UIの統合:** フォーム送信・ミューテーション後に`useOptimistic`とServer Actionsを組み合わせることで、楽観的UIとストリーミングレスポンスが統合され、従来のSPA的なUXをサーバー主導で実現できるようになった。

- **バンドルサイズへの影響を過信しない:** RSCはクライアントJSを削減するが、ストリーミング用のフライトプロトコル（RSCペイロード）がネットワークを圧迫するケースがあり、`React.cache()`によるサーバー側重複排除と組み合わせた設計が必要。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの主流化:** 2026年時点でTypeScriptフルスタック環境ではtRPCが事実上の標準に近づいており、型安全性をエンドツーエンドで保証しながらスキーマ定義の二重管理を排除できる点が決定的な優位性となっている。

- **GraphQLの適用範囲の明確化:** GraphQLは「複数クライアントが異なるデータ形状を必要とする場合」に限定されつつあり、内部API・BFF層ではオーバーエンジニアリングとみなされるケースが増加。Relay/Client Presetsによるフラグメントコロケーションが必須プラクティスに。

- **RESTの再評価とOpenAPI 3.1:** RESTは「シンプルなCRUD」と「外部公開API」で依然として最適解。OpenAPI 3.1 + `zod-to-openapi` 等のコードファースト生成ツールにより、型定義からドキュメント・クライアントSDKを自動生成するパターンが定着している。

- **エッジランタイム対応の重要性:** Cloudflare Workers / Vercel Edge Functionsの普及により、APIレイヤーはNode.js依存のランタイムを避けるアーキテクチャが求められる。tRPCとHonoの組み合わせがエッジ対応の現実解として台頭。

- **Contract-First vs Code-First の収束:** スキーマ駆動（Contract-First）とコード駆動（Code-First）の議論は終息し、「型システムをSingle Source of Truthとするコードファースト + 自動スキーマ出力」がチーム生産性・CI整合性の両面で優勢となっている。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジの標準実行環境へ:** 2026年時点でCloudflare Workers・Fastly Compute@Edgeが本番WasmサポートをGAとし、言語非依存のエッジロジックが現実的な選択肢となっている。コールドスタートがほぼゼロになり、Node.js依存からの脱却が加速。

- **エッジDBの成熟とデータローカリティ戦略の必須化:** Cloudflare D1・Turso（libSQL）・Neon（geo-distributed Postgres）がエッジ近傍でのSQLを実現し、「コンピュートはエッジ、データはオリジン」という構造的課題が解消されつつある。ただしレプリケーション遅延の設計考慮は依然必要。

- **エッジ推論（Edge Inference）の台頭:** 軽量LLM（Phi-3 mini・Gemma 2B相当）をエッジノードで実行するユースケースが増加し、レイテンシとプライバシー要件を同時に満たす構成が評価されている。GPUレスでのonnxruntimeベース推論が実用域に入った。

- **オブザーバビリティの欠如が依然ボトルネック:** エッジ環境はログ・トレースの収集インフラが分散しており、OpenTelemetryのエッジ対応（Tail Sampling等）がまだ発展途上。本番導入時はベンダーロックインとトレードオフで可観測性設計を先に決めることが重要。

- **コスト構造の再評価が必要:** リクエスト課金モデルはトラフィックスパイクに強い一方、常時接続・長時間処理にはオリジンサーバーの方が安価なケースが多い。エッジ適用はCDNキャッシュ不可の動的処理かつレイテンシ要件が厳しいユースケースに絞るのがROI最大化のポイント。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準採用:** FIDO2/WebAuthnベースのパスキーがパスワード認証を実質的に置き換えつつあり、フィッシング耐性とUX向上を両立できる。Google・Apple・Microsoftのエコシステムが成熟し、実装コストも大幅に低下している。

- **ゼロトラスト＋継続的認証:** 「一度認証すれば信頼」ではなく、セッション中もリスクスコアを継続評価し、異常行動を検知したら再認証を要求するアーキテクチャが必須。デバイス状態・位置情報・行動パターンを組み合わせた多層評価が主流。

- **トークン管理の厳格化（JWT/セッション）:** JWTの有効期限を短く保ち（15分以下）、リフレッシュトークンをHTTP-Only Cookieで管理するパターンが定着。トークンローテーションとリボケーションリストの実装が2026年のスタンダード。

- **AIを活用した不正アクセス検知:** 機械学習による異常ログイン検出（新デバイス・深夜アクセス・地理的矛盾など）がSaaS認証基盤に組み込まれ、ルールベース防御を超えた適応型防御が現実的コストで実現可能。

- **サプライチェーンリスクとしての認証ライブラリ管理:** `passport.js`や`next-auth`等の依存ライブラリへの攻撃が増加。定期的な`bun audit`実施、Dependabot/Renovateによる自動更新、そしてSBOM（ソフトウェア部品表）の管理が義務的対策となっている。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6のEdge Runtime対応が加速:** 2026年時点でPrisma Accelerateを使ったエッジ環境での接続プーリングが標準化され、Next.js App RouterのServer Actionsとの相性が大幅に改善。Cold startによるレイテンシ問題がほぼ解消された。

- **Supabase Branching が開発フローを変革:** データベースのブランチ戦略がgitブランチと連動できるようになり、PR単位でスキーマ変更を安全にプレビューできる。Prisma Migrateとの組み合わせで、ステージング環境管理のコストが大幅削減。

- **RLSとPrismaの統合が成熟:** Row Level SecurityをPrismaのミドルウェア層で扱うパターンが確立。Supabaseのauth.uid()とPrismaのクライアント拡張を組み合わせることで、型安全なマルチテナント設計が実現できる。

- **pgvector + Supabase Vector が実用段階に:** 2026年のRAGアーキテクチャではSupabaseをベクトルDBとして使うケースが増加。Prismaの生SQLエスケープ(`$queryRaw`)経由でpgvectorを扱う実装パターンが標準化されつつある。

- **接続プーリングの選択肢整理が重要:** PgBouncerベースのSupabase組み込みプーラー vs Prisma Accelerate vs direct connectionの使い分けが設計上の鍵。サーバーレス環境では必ずプーラーを挟む、長寿命サーバーではdirect接続を検討するのが現在のベストプラクティス。

### 7. WebAssembly Rust performance 2026

- **WASM GC・コンポーネントモデルの成熟:** WebAssembly Component Modelが2026年に実用段階へ移行し、Rustで書いたモジュールを言語横断で型安全に合成できるようになった。バックエンド・フロントエンド間のコード共有コストが大幅に低下。

- **SIMD・スレッド並列化の本格活用:** WASMのFixed-width SIMDとShared Memoryが主要ブラウザで安定し、Rustの`rayon`相当の並列処理がWebでも現実的に。画像処理・音声・ML推論でネイティブの70〜90%性能が出るケースが増加。

- **Wasmtime/WASIpの進化でサーバーサイド実用化:** WASI Preview 2（WASIp2）により、RustのWASMバイナリがCloudflare Workers・Fastly Compute等のエッジ環境でコールドスタート<1msを実現。コンテナに代わるサーバーレス実行単位として注目。

- **ビルドサイズ最適化の標準化:** `wasm-opt`・`wasm-bindgen`のツールチェーンが成熟し、Rustバイナリのデフォルトサイズが従来比30〜50%削減。`cargo-component`によるコンポーネント単位のビルドが主流になりつつある。

- **採用判断の実務指針:** CPUバウンドな処理（パーサー・暗号・エンコード）は積極的にRust+WASMへ移行する価値あり。一方、DOM操作が多いUIロジックはJS/TSのままが依然合理的。境界をAPIレベルで明確に切ることが設計の鍵。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの設計原則:** データフェッチはServer Componentsで完結させ、クライアントへのJS転送を最小化する。`'use client'`境界は葉コンポーネントに限定し、バンドルサイズを抑制することがパフォーマンスの基本戦略。

- **Partial Prerendering (PPR) の実用化:** 静的シェルと動的コンテンツを同一ルートで共存させるPPRが安定版に到達。`<Suspense>`境界の設計がUXとTTFBの両立に直結するため、ルート設計の初期段階から考慮が必須。

- **Server Actions によるフォーム・ミューテーション:** API Routeを経由しない直接的なサーバー関数呼び出しが主流に。`useActionState` + `useOptimistic`の組み合わせで、楽観的UIと型安全なフォーム処理が宣言的に実現できる。

- **Parallel Routes / Intercepting Routes の活用:** モーダルやサイドパネルをURLに紐付けるパターンが成熟。ディープリンク可能なUIを実現しつつ、ブラウザバック時の挙動も自然に制御できる。

- **`next/cache` の細粒度キャッシュ制御:** `revalidateTag` / `revalidatePath`によるオンデマンド再検証が標準パターンに定着。`fetch`ごとのキャッシュタグ設計がインフラコストとデータ鮮度のトレードオフを決定するため、データ層設計と同時に検討すべき。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択的活用:** 全APIルートをEdgeに移行するのは逆効果。認証チェック・A/Bテスト・地理的ルーティングなど低レイテンシが本質的な処理に絞り、DBアクセスを伴うロジックはNode.js Runtimeに留める。

- **Cold Start最小化のためのバンドルサイズ管理:** Edge Functionsは1MB制限（圧縮後）があるため、`next/server`の軽量インポートを徹底し、重いSDKは動的インポートまたはサーバーサイドに逃がす。

- **KV・Blob・Postgres接続の最適化:** Vercel KV（Upstash Redis）やNeon PostgresのHTTP接続はEdgeと相性が良いが、コネクションプーリング設定ミスによるレイテンシ増大に注意。`waitUntil()`でレスポンス後の非同期処理を活用する。

- **Middleware乱用のアンチパターン回避:** `middleware.ts`はすべてのリクエストを通過するため、重い処理を入れると全体のTTFBに影響する。`matcher`で対象パスを明示的に絞り込むことが必須。

- **Fluid ComputeによるEdge/Serverlessの境界消滅:** 2025年後半にVercelが導入したFluid Computeにより、従来のEdge vs Serverlessの二択が緩和。ストリーミングレスポンスとリージョン配置を組み合わせた設計が2026年の主流になりつつある。

### 10. TypeScript type safety patterns 2026

- **Branded Types の実用化:** `type UserId = string & { readonly _brand: 'UserId' }` のようなブランド型が本番コードでも定着し、プリミティブ型の誤用をコンパイル時に防止するパターンが標準化されている。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` が広く普及し、型の絞り込みを保ちつつ型チェックを行える。`const config = { ... } satisfies Config` で推論精度を維持しながら安全性を確保できる。

- **Template Literal Types による API 契約の強化:** `type Route = `/api/${string}`` のような型でルート・イベント名・CSSクラスをコンパイル時に検証し、文字列の型安全性を大幅に向上させている。

- **`infer` + Conditional Types による深い型推論:** 複雑なユーティリティ型（`ReturnType`の応用など）を活用してライブラリの型定義を自前で拡張するパターンが普及。外部型定義が不完全な場合の実用的な対策となっている。

- **Zod/Valibot によるランタイム検証との統合:** 型定義とバリデーションロジックを一元化し、`z.infer<typeof Schema>` で型を自動生成するアプローチが事実上の標準。システム境界（API・フォーム入力）での型安全性を実行時まで保証できる点が特に重要。
