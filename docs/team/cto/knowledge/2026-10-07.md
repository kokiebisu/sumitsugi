# CTO Knowledge - 2026-10-07

## Daily Update (2026-10-07)

### 1. Next.js performance optimization 2026

- **ポイント1: React Server Components とストリーミングSSRの徹底活用:** Next.js 16ではPPR（Partial Prerendering）が安定版となり、静的シェルを即時配信しつつ動的部分のみストリーミングすることでTTFBとLCPを大幅改善できる。sumitsugiの物件一覧・詳細ページのような「静的に近いが一部動的」なUIに特に有効。

- **ポイント2: キャッシュ戦略の明示化（`use cache` / Cache Components）:** データ取得層でキャッシュ境界を明示的に宣言するAPIが主流化し、暗黙的なフルルートキャッシュへの依存を減らせる。物件検索・フィルタリング機能で再検証タイミングを細かく制御すれば、鮮度とパフォーマンスのトレードオフを最適化できる。

- **ポイント3: 画像・フォント最適化の自動化が前提に:** `next/image`のAVIF優先配信やフォントのセルフホスティングはデフォルト挙動化が進み、手動チューニングの比重が下がっている。物件写真が多いsumitsugiでは、CDN経由の画像最適化設定がCore Web Vitals（特にLCP）に直結する。

- **ポイント4: Turbopackによるビルド・開発体験の高速化:** Turbopackがビルドの既定エンジンとなり、大規模コードベースでのビルド時間が大幅短縮される。CI上の`bun run build`実行時間短縮にも直結し、PRごとのフィードバックループが速くなる。

- **ポイント5: Edge/Node実行環境の使い分けが性能最適化の鍵:** 認証チェックやリダイレクトなど軽量処理はEdge Runtimeに、DBアクセスを伴う重い処理はNode Runtimeに配置する設計が定石化している。auth-context周辺のミドルウェア処理をEdgeに寄せることで、全ページのレイテンシを下げられる余地がある。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** React Server ComponentsのストリーミングがNext.js 16で完全に標準パターンとなり、`loading.tsx`やSuspense境界を使った段階的レンダリングがデフォルトの開発フローに組み込まれている。初期表示速度（TTFB/LCP）を犠牲にせず複雑なデータ取得を扱える。

- **Partial Prerendering (PPR) の成熟:** 静的シェルを即時配信しつつ動的部分だけストリーミングで後から流し込むPPRが安定版機能として広く使われ始めており、物件一覧ページのような「静的レイアウト＋動的データ」構成に最適。sumitsugiの`properties/`ページで検討する価値あり。

- **Server Actions × streamingの組み合わせ:** フォーム送信後の楽観的UI更新とストリーミングレスポンスを組み合わせたパターンが一般化し、`useActionState`と`useOptimistic`を併用することでローディング状態の自前管理が大幅に減らせる。

- **エッジランタイムでのストリーミング制約:** Vercel Edge等でのストリーミングは依然メモリ・実行時間制限があり、大きなコンポーネントツリーを多数のSuspense境界に分割しすぎるとウォーターフォール（直列リクエスト）を招くため、データ取得の並列化（`Promise.all`やpreload pattern）が重要な設計判断点になる。

- **キャッシュ戦略との相互作用:** RSCストリーミングと`unstable_cache`/Next.jsのキャッシュディレクティブの相互作用が複雑化しており、どの境界で何をキャッシュするかを明示的に設計しないと、意図しない再レンダリングやキャッシュミスが発生しやすい。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの採用拡大）:** TypeScriptモノレポ構成のプロジェクトでは、型安全性とスキーマ定義の二重管理を避けられるtRPCの採用が増えている。Next.js App RouterとServer Actionsの組み合わせにより、内部API層そのものをtRPCで代替する選択肢も現実的になっている。

- **ポイント2（GraphQLは複雑なクライアント要件に限定）:** GraphQLは依然としてモバイル/Web間でデータ取得パターンが大きく異なる場合に強みがあるが、スキーマ管理・N+1問題対策のコストが高く、シンプルなCRUD中心のプロダクトでは過剰投資になりやすい。本プロジェクトのような単一Webアプリ中心の構成ではtRPC/RESTで十分なケースが多い。

- **ポイント3（RESTは外部公開APIの標準として継続）:** 外部パートナーや将来のモバイルアプリ、サードパーティ連携を想定する場合、ドキュメント化・キャッシュ戦略・HTTPセマンティクスが成熟しているRESTが依然有利。内部通信はtRPC、外部公開APIはREST（OpenAPI）という「二層構成」が2026年のデファクトになっている。

- **ポイント4（Zodによるランタイム検証の一体化）:** tRPCでもRESTでも、Zodスキーマを型定義・ランタイム検証・OpenAPI生成の単一ソースとして使う構成が標準化している。既にCLAUDE.mdで「Input validation: Zodスキーマ」が明記されている通り、この方針を物件データ等の境界（前の住人⇄次の住人間のデータ引き継ぎ）にも一貫適用すべき。

- **ポイント5（エッジ・サーバーレス前提の設計）:** Next.js 16のサーバーアクションやエッジランタイムを前提にすると、API設計はレイテンシよりも「コールドスタートの回避」と「キャッシュ境界の明示」が重要になる。物件検索・画面公開ステータス（draft/public）のような読み取り頻度の高いエンドポイントは、tRPCのクエリキャッシュやISRと組み合わせて設計するのが実用的。

### 4. serverless edge computing 2026

- **エッジでのAI推論統合:** 2026年にはCloudflare Workers AI、Vercel Edge Functions、Deno Deployなどが小型LLM・埏め込み推論をエッジランタイムに標準搭載し、ユーザーに最も近いPoPでレイテンシ数十ms単位の推論が可能になっている。sumitsugiのような検索・レコメンド機能はエッジでの軽量推論オフロードを検討する価値がある。

- **WASMベースの軽量ランタイムが主流化:** V8 isolatesやWasmtimeベースのコールドスタート最適化が進み、起動時間がミリ秒単位になったことで、従来Node.js前提だった処理（画像変換、認証チェックなど）をエッジ層に移しやすくなっている。Next.js 16のMiddleware/Edge Runtimeとの親和性が高く、物件検索のジオロケーション処理などに応用できる。

- **データレイヤーのエッジ分散（Edge-native DB）:** Turso、Cloudflare D1、PlanetScale等のエッジレプリケーション型DBが実用段階に入り、読み取りをリージョン分散しつつ書き込みは中央集権的に保つパターンが定石化している。物件データの読み取りが多いsumitsugiの構成では、読み取り系APIのエッジキャッシュ戦略がパフォーマンス改善の鍵になる。

- **可観測性とコスト管理の重要性増大:** エッジ実行は分散するほどデバッグ・トレーシングが難しくなり、OpenTelemetryのエッジ対応やper-request課金の最適化が開発ベストプラクティスとして定着してきている。本番導入前に計測基盤（ログ・トレース）を整備しないと、コストとパフォーマンスのブラックボックス化を招くリスクがある。

- **セキュリティ境界の見直し:** エッジでの処理増加に伴い、従来のオリジンサーバー中心のCSRF/CSP設計をエッジ層にも拡張する必要があり、WAFルールやレート制限をエッジ側で一次防御として実装するのが2026年のデフォルトパターンになっている。認証・決済など機密性の高い処理は依然オリジン集中が無難。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証がデフォルトになりつつあり、フィッシング耐性のあるパスキーをソーシャルログインと並ぶ第一選択として実装すべき。既存のパスワード+SMS OTPはSIMスワップ攻撃に脆弱なため段階的に廃止すべき。

- **セッション管理とトークンの短寿命化:** JWTのexpiry短縮＋リフレッシュトークンのローテーション（使用後即失効）が標準に。長寿命トークンの漏洩リスクを抑えるため、sumitsugiのようなB2Cプラットフォームでも導入コストは低く効果が高い。

- **デバイスバインディングとコンテキスト認証:** IPアドレスやデバイスフィンガープリントを用いたリスクベース認証（異常なログインのみ追加検証を要求）が主流になり、UXを損なわずセキュリティを強化できる。

- **ゼロトラストとBFF（Backend for Frontend）パターン:** トークンをフロントエンドに直接露出させず、サーバーサイドでセッションを管理するBFFアーキテクチャがXSS/トークン漏洩対策として推奨される。Next.jsのApp Routerはサーバーコンポーネント中心なのでこのパターンと親和性が高い。

- **監査ログと異常検知の自動化:** 認証イベント（ログイン失敗、権限昇格など）の構造化ログを蓄積し、異常検知を自動化する動きが加速。法務確認中の現フェーズでも、将来のコンプライアンス要件（個人情報保護法対応）に備えて早期に設計しておくべき。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6.x以降、Supabase向けにPgBouncer経由の接続プーリング設定が標準化され、ServerlessやEdge関数からの接続数爆発問題が実用レベルで解消されつつある。`DIRECT_URL`と`DATABASE_URL`を分離する構成がベストプラクティスとして定着している。

- **ポイント2:** SupabaseのRow Level Security（RLS）とPrisma ORMの併用には注意が必要で、Prismaはservice_roleキーでRLSをバイパスするため、認可ロジックをアプリケーション層（ミドルウェアやZodバリデーション）で明示的に再実装する必要がある。

- **ポイント3:** Prisma Migrateの宣言的スキーマ管理とSupabaseのマイグレーション機能が競合しやすく、どちらか一方をSingle Source of Truthとして運用を統一しないと、本番環境でスキーマドリフトが発生するリスクが高い。

- **ポイント4:** Supabaseのリアルタイム機能（Postgres Changes）を使う場合、Prisma経由の書き込みでもWAL（Write-Ahead Log）ベースのイベントは正しく発火するため、ORM選定がリアルタイム機能の制約にはならない点は見落としがちな利点。

- **ポイント5:** sumitsugiのようなMVPフェーズでは、Prisma + Supabaseの組み合わせはマイグレーション速度と型安全性のバランスが良く、今後の物件ステータス（`draft`/`public`）のような列挙型変更時もPrismaのスキーマファイルを単一の変更点として扱えるのが運用上のメリットになる。

### 7. WebAssembly Rust performance 2026

- **ポイント1（WASM GC本格普及）:** WasmGCがブラウザ・ランタイム双方で標準対応し、RustでもGCベース言語との相互運用がしやすくなった一方、Rustは元々Linear Memoryモデルなので恩恵は限定的。むしろ`wasm-bindgen`やComponent Modelとの統合改善がRust開発者には実利が大きい。

- **ポイント2（Component Model / WASIp3の成熟）:** WASI Preview 3とWasmのComponent Modelが安定し、Rustクレートを言語非依存の再利用可能コンポーネントとして配布できるようになった。マイクロサービス的にWasmモジュールを組み合わせる設計がサーバーサイドでも実用段階に入っている。

- **ポイント3（SIMD・マルチスレッドの標準化）:** Wasm SIMDとthreads/atomicsがほぼ全主要ランタイムで利用可能になり、`std::simd`やrayon的な並列処理をRust→Wasmでネイティブ並列処理にさらに近いレベルで動かせる。画像処理・ML推論系のワークロードでネイティブの70〜90%程度の性能が狙いやすい。

- **ポイント4（コンパイル時間とバイナリサイズの最適化）:** `wasm-opt`やLTO、`codegen-units=1`などの最適化に加え、Cranelift系バックエンド（wasmtimeのCraneliftなど）のJIT最適化が進み、コールドスタート性能が大幅改善。エッジ/サーバーレス用途（Fastly Compute、Cloudflare Workersなど）でのRust+Wasm採用がさらに現実的になっている。

- **ポイント5（実務的な洞察）:** 自社プラットフォームへの適用を考えるなら、まずは画像処理や料金計算など計算集約的な一部ロジックをRust+Wasmに切り出し、Next.js側からWASIなしのブラウザWasmモジュールとして呼ぶのが低リスクな導入パス。フルスタックでWasmに全面移行する必要はない。

### 8. Next.js App Router patterns 2026

- **サーバーコンポーネント優先:** App RouterではServer Componentsがデフォルトとなり、クライアントバンドルサイズを削減できる。本プロジェクトでも`'use client'`は認証状態やインタラクションが必要な箇所のみに限定し、データフェッチはサーバー側で完結させるのが基本方針。
- **Partial Prerendering (PPR)の実用化:** 静的シェルを即時配信しつつ動的部分をストリーミングする手法が2026年には標準的な選択肢になっている。物件一覧ページのような「静的なレイアウト＋動的な検索結果」構成に相性が良い。
- **並列データフェッチとSuspense境界の細分化:** `loading.tsx`やネストしたSuspenseで待機範囲を最小化し、一部データの遅延がページ全体をブロックしないよう設計するのが定石。物件詳細＋レビュー＋空き状況のような複数データソースのページで効果が大きい。
- **Server Actionsの責務分離:** フォーム送信や更新処理をServer Actionsに寄せる一方、Zodによる入力検証をサーバー側境界で必須化する流れが定着。認証・決済系のミューテーションでは特に重要。
- **キャッシュ戦略の明示化:** `fetch`のデフォルトキャッシュ挙動が変化してきているため、`revalidate`やタグベースの再検証(`revalidateTag`)を明示的に指定する実装が増えている。公開/非公開ステータスが変わる物件データでは、キャッシュ無効化のタイミング設計が特に重要になる。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化とIsolate再利用:** V8 isolateベースの実行モデルが成熟し、関数の初期化コストがほぼゼロに近づいている。頻繁にアクセスされないAPIルートでもレイテンシ劣化を避けられるため、ユーザー向け動的コンテンツは積極的にEdge Runtimeへ移行すべき。

- **Streaming SSRとの統合:** Edge Functionsを使ったレスポンスのストリーミングが標準化され、TTFB（Time to First Byte）が大幅に改善している。特に検索・レコメンド機能など、部分的な結果を先行表示するUXに向いている。

- **リージョン分散とデータ近接性:** Edge Config / KVストアとの組み合わせで、ユーザーに最も近いリージョンでパーソナライズ処理を完結できるようになった。物件検索のような地理的に偏在するトラフィックを扱う`sumitsugi`では、地域別キャッシュ戦略の見直しに価値がある。

- **Node.js APIの互換性拡大:** 従来Edge Runtimeで使えなかったNode.js固有API（crypto、streamsなど）の対応範囲が広がり、Middleware層でのバリデーションやセッション処理をEdgeに寄せやすくなっている。認証系の処理をEdgeで前段処理することでオリジンの負荷を減らせる。

- **コスト最適化とObservability:** 実行時間課金モデルの透明性が向上し、関数単位でのコスト・レイテンシのトレースがダッシュボードから直接見られるようになった。本番投入前にEdge/Node runtimeのコスト比較を数値で判断できるため、ローンチ準備中の今、課金体系を踏まえたランタイム選定を早めに検証する価値がある。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x以降の`satisfies`演算子とconst type parametersの組み合わせが定着し、型推論を保ちながら厳密なリテラル型チェックが可能になった。2026年は特にAPIレスポンスやconfig定義でこのパターンが標準化されている。
- **ポイント2:** Zodなど実行時スキーマからの型導出（`z.infer`）が「型とランタイム検証の二重管理」を解消する主流パターンとなり、システム境界（API入力、環境変数）での型安全性がビルド時だけでなく実行時にも保証されるようになった。sumitsugiでも標準化済みのアプローチ。
- **ポイント3:** Discriminated Union（タグ付きユニオン型）による状態管理が、`'draft' | 'public'`のようなステータス管理のデファクトスタンダードとして広く使われており、exhaustiveness checking（`never`型を使った網羅性チェック）でswitch文の漏れをコンパイル時に検出できる。
- **ポイント4:** テンプレートリテラル型とBranded Types（nominal typing）を使い、`UserId`と`ProductId`のようなプリミティブ型の意味的な混同をコンパイル時に防ぐパターンが、大規模コードベースでのバグ防止策として普及している。
- **ポイント5:** AIコーディングアシスタント（Claude Code等）との協働が前提になったことで、型定義自体が「エージェントへの実行可能な仕様書」として機能するようになり、曖昧な`any`や緩い型は人間だけでなくAIの誤実装リスクも高めるという認識が強まっている。
