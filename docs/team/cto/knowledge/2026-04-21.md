# CTO Knowledge - 2026-04-21

## Daily Update (2026-04-21)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降でPPRが安定化し、静的シェルと動的コンテンツを同一ルートで混在できるようになった。`<Suspense>`境界を戦略的に配置することで、TTFB短縮とパーソナライズを両立できる。

- **React Server Components キャッシュ戦略の精緻化:** `fetch()`の`cache`・`revalidate`オプションに加え、`unstable_cache`による関数レベルのキャッシュが実用段階に。データフェッチをサーバー側に集約しつつ、適切なキャッシュ粒度を設計することがパフォーマンスの鍵。

- **Turbopack移行によるビルド高速化:** Turbopackが本番ビルドでも安定動作するようになり、大規模プロジェクトでのビルド時間を最大80%短縮できるケースが報告されている。`next.config.ts`で`bundler: 'turbopack'`を設定するだけで移行可能。

- **`<Image>`と`<Font>`の最適化強化:** `next/image`のリモートパターンマッチングとAVIF優先配信が改善され、LCP指標に直結する画像配信の最適化が容易になった。`next/font`によるフォントのゼロCLS実現は引き続き必須対応。

- **Edge RuntimeとStreaming UIの使い分け:** 認証チェックやA/Bテストはエッジで処理してレイテンシを削減しつつ、重いデータ処理はNode.js Runtimeに留める分離設計が重要。Streamingと組み合わせることでFCP・INPの両指標を同時に改善できる。

### 2. React Server Components streaming 2026

- **Suspense境界の細粒度化が標準に:** 2026年時点では、ページ単位ではなくコンポーネント単位でSuspenseを配置し、TTFBを最小化しつつ段階的にUIをストリームするパターンが実践的ベストプラクティスとして定着している。

- **Server Actionsとの統合でウォーターフォールが消滅:** RSCストリーミングとServer Actionsを組み合わせることで、従来のfetch→render→hydrationの連鎖待ちが解消され、インタラクティブ要素を後からhydrateしながら静的コンテンツを即座に表示できる。

- **PPR（Partial Prerendering）の本格運用:** Next.js 15+でstableになったPPRにより、静的シェルを即時配信しつつ動的部分のみストリームする構成が可能になり、CDNキャッシュとSSRの利点を同時に享受できる。

- **エッジランタイムでのストリーミング制約に注意:** Cloudflare WorkersやVercel Edgeでは長時間のストリーム接続にタイムアウト制限があるため、重いデータフェッチはNode.jsランタイム側に置くか、ストリームチャンクを細かく区切る設計が必要。

- **DevToolsでのデバッグ体験が向上:** React DevTools 6.x系でストリーミングの各チャンク到達タイミングとSuspenseフォールバックの切り替えを可視化できるようになり、パフォーマンスボトルネックの特定が大幅に容易になっている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** tRPCはNext.js/TypeScript環境でのAPI設計標準として定着しており、クライアント・サーバー間の型共有により実行時エラーを大幅に削減できる。特にモノレポ構成では生産性の向上が顕著。

- **REST vs GraphQLの使い分けの成熟:** 2026年時点でGraphQLは「全てに使う」から「複雑なデータ依存関係がある場面に絞る」方向にシフト。シンプルなCRUDはRESTまたはtRPC、複雑なクエリ要件にはGraphQLという実用的な棲み分けが定着している。

- **OpenAPI 3.1 + コード生成の復権:** REST APIでもopenapi-generatorやorbなどのツールによる型安全なクライアント自動生成が普及し、tRPCに近い開発体験が得られるようになった。マイクロサービス間通信やサードパーティ公開APIではOpenAPIが依然として主流。

- **Server-Sent Events / HTTP Streaming の再評価:** WebSocketの複雑さを避けつつリアルタイム性を確保するSSEとHTTP Streamingが、AI系機能（LLMレスポンスストリーミング等）の普及で急速に需要拡大。Next.js App RouterのRoute HandlersもStreaming対応を強化。

- **Contract-First設計の重要性:** フロントエンド・バックエンド並行開発の普及により、APIスキーマを先に定義してモックサーバーを立てるContract-Firstアプローチが標準化。tRPCのルーター定義やGraphQLのスキーマファーストがこのプラクティスを自然に促進する。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジの標準ランタイムへ:** Cloudflare Workers・Fastly Compute@Edgeを中心に、Wasmがコンテナに代わるポータブルなエッジ実行環境として定着。コールドスタートがほぼゼロになり、Node.js依存から脱却できる。

- **エッジDBの成熟によりステートフルアーキテクチャが現実的に:** Cloudflare D1・Turso・PlanetScale Metalなどの分散SQLが各リージョンで低レイテンシ読み取りを実現。「エッジはステートレスのみ」という制約が崩れ始めている。

- **AI推論のエッジオフロードが加速:** 小型LLM（3B〜7Bパラメータ）をエッジノードで実行するパターンが普及。中央クラウドへのラウンドトリップなしにパーソナライズ処理が完結し、レイテンシとプライバシーを同時に改善できる。

- **オブザーバビリティのギャップが最大の運用課題:** エッジ関数は数百リージョンに分散するため、分散トレーシングとログ集約のコストが急増。OTel対応のエッジネイティブなモニタリング基盤への投資が必須になっている。

- **コスト最適化のためのインテリジェントルーティング:** すべてのリクエストをエッジで処理するのではなく、キャッシュヒット率・計算コスト・レイテンシ要件に基づいてエッジ／リージョン／オリジンを動的に選択するハイブリッドアーキテクチャが主流になりつつある。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準採用:** FIDOアライアンスのパスキーが業界標準となり、パスワード認証からの完全移行が加速している。生体認証ベースのため、フィッシングやクレデンシャルスタッフィング攻撃を根本から排除できる。

- **ゼロトラスト + 継続的認証:** ログイン時の一度きりの認証から、セッション中もリスクスコアを継続評価するアーキテクチャが主流になっている。異常な操作パターンを検知した場合に再認証を要求する仕組みが不可欠。

- **MFAの必須化とSMS廃止:** SMS OTPはSIMスワップ攻撃に脆弱なため、TOTP（Time-based OTP）またはハードウェアキー（YubiKey等）への移行が求められている。特に管理者アカウントへのSMSベースMFAは2026年時点でセキュリティ上のリスクとみなされる。

- **セッション管理の厳格化:** JWTの有効期限を短く（15分以下）設定し、Refresh Tokenローテーションと組み合わせることがベストプラクティス。トークンの保存場所はlocalStorageではなくhttpOnly Cookieを使用してXSSリスクを軽減する。

- **サプライチェーン認証の強化:** OAuth/OIDCプロバイダーやサードパーティ認証ライブラリへの依存がサプライチェーン攻撃の経路になりうる。使用するパッケージのSBOM管理と定期的な脆弱性スキャンを開発パイプラインに組み込むことが必須。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応:** Prisma 6ではEdge-compatibleドライバーが安定し、Vercel Edge FunctionsやCloudflare Workersから直接DBアクセスが可能になった。Next.js App Routerのサーバーコンポーネントとの相性が大幅に改善されている。

- **Supabase pgvector + AI統合の本格化:** `pgvector`拡張によるベクトル検索がSupabaseのコアサービスに統合され、RAGアーキテクチャをPostgreSQL一本で実現できる。外部ベクターDBを別途持つ設計は過剰になりつつある。

- **Row Level Security (RLS) の設計が競争優位になる:** SupabaseのRLSをPrismaと組み合わせる場合、`SET LOCAL role`でPostgresロールを切り替えるパターンが定石に。セキュリティポリシーをDB層で担保することでアプリ側のバグリスクを大幅に削減できる。

- **Prisma Accelerateによるコネクションプーリング:** サーバーレス環境でのDB接続枯渇問題に対し、Prisma Accelerateがグローバルキャッシュ付きコネクションプールを提供。SupabaseのPgBouncerと使い分けの判断が重要になっている（Accelerateはエッジキャッシュ優位、PgBouncerはレイテンシ優位）。

- **マイグレーション戦略の成熟:** `prisma migrate`とSupabaseの`supabase db push`の混在は運用事故の温床。2026年現在のベストプラクティスはPrismaをスキーマの唯一のソースオブトゥルースとし、Supabase CLIはローカル開発環境の起動にのみ使用する方針が定着しつつある。

### 7. WebAssembly Rust performance 2026

- **Component Model の成熟:** WASIp2（WASI Preview 2）とComponent Modelが2025年末に安定化し、RustのWasmコンポーネントがホスト環境に依存せず再利用可能になった。マイクロサービスの代替として「Wasmコンポーネント」単位でのデプロイが現実的な選択肢になっている。

- **Wasmtime / WasmEdge の本番採用加速:** Craneliftバックエンドの最適化により、Wasmtimeでのコールドスタートは数ミリ秒以下に到達。Rustで書いたコンポーネントはネイティブ比95%超のスループットを出せるケースが増え、エッジ・サーバーレス環境での採用障壁が実質的に消えた。

- **SIMD・スレッド対応の実用化:** Fixed-width SIMDとWasm Threadsが主要ランタイムで安定稼働。画像処理・ML推論などの計算集約型ワークロードでRust+Wasmがネイティブに近いパフォーマンスを発揮できるようになり、クロスプラットフォーム展開のコスト優位が明確になった。

- **GCプロポーザルによる相互運用性向上:** Wasm GC提案の普及で、JS/Python側オブジェクトとRustコンポーネント間のゼロコピー連携が容易になった。ただしRustネイティブの所有権モデルとのインピーダンスミスマッチは依然設計上の注意点。

- **ツールチェーン成熟（cargo-component / wit-bindgen）:** `cargo-component`が標準ワークフローに統合され、WITインターフェース定義からバインディング自動生成が安定化。ビルドパイプラインへの組み込みコストが大幅に下がり、既存RustクレートをWasm化するROIが向上している。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** デフォルトでServer Componentsを採用し、インタラクションが必要な箇所のみ`'use client'`を付与することで、クライアントバンドルを最小化しTTFBを大幅に改善できる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的ストリーミングを同一ルートで共存させるPPRが安定化し、`<Suspense>`境界を戦略的に配置することでFCPとINPの両立が現実的になった。

- **Server Actions によるAPI Route の置き換え:** フォーム送信やデータ変換処理をServer Actionsに移行することで、API Routeの管理コストを削減しつつ型安全なend-to-endを実現できる。ただし長時間処理は依然としてRoute Handlersが適切。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15以降の`use cache`により、関数・コンポーネント単位でキャッシュ戦略を宣言できる。`revalidateTag`との組み合わせでISRより柔軟なキャッシュ無効化が可能。

- **Parallel Routes + Intercepting Routes のモーダルパターン:** `@modal`スロットとインターセプトルーティングを組み合わせると、URLを保持したままモーダル表示が実現でき、シェア・リロード時も正しいページが表示される。本プロジェクトの物件詳細モーダルに適用価値が高い。

### 9. Vercel Edge Functions optimization 2026

- **エッジでのキャッシュ戦略の高度化:** Vercel Edge Functionsでは `waitUntil()` を活用したバックグラウンド再検証（SWR パターン）が主流となり、コールドスタートのコストを最小化しつつ、動的コンテンツのキャッシュヒット率を大幅に改善できる。

- **Fluid Computeによるリソース効率化:** 2025年後半に一般化した Fluid Compute モデルにより、関数の実行が同一インスタンス内で多重化され、従来のサーバーレスと比較してCPU使用率・コスト共に最大60%削減できるケースがある。

- **Edge Middlewareでの認証・パーソナライゼーション集約:** 認証チェックやA/Bテスト分岐をEdge Middlewareに集約することで、オリジンへのリクエスト数を削減できる。ただしJWT検証はCPU負荷が高いため、軽量な`jose`ライブラリの選択が重要。

- **地理的レイテンシの可視化と最適化:** Vercel Speed Insightsと組み合わせてリージョン別のP95レイテンシを計測し、ボトルネックになっているエッジロケーションを特定してデータソース（KV・D1等）の配置を調整するアプローチが実践的。

- **Node.js APIからEdge Runtimeへの段階的移行:** `runtime: 'edge'` への切り替えは `crypto`・`fs` 等のNode.js組み込みAPIが使えなくなるため、依存ライブラリの互換性確認（特に認証・DB系）を先に実施し、影響範囲の小さいルートから段階的に移行するのがリスク最小の戦略。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `type UserId = string & { readonly __brand: 'UserId' }` パターンが普及し、プリミティブ型の混同バグをコンパイル時に防ぐアプローチが実プロダクトで主流になっている。

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の `satisfies` が定着し、型推論を維持しながら型チェックを行えるため、`as` キャストによる型安全性の破壊を避けられる設計が推奨されている。

- **Zod + tRPC による境界の型安全:** APIの入出力をZodスキーマで定義しtRPCで接続するパターンが事実上の標準となり、フロント・バック間の型ズレをゼロにするアーキテクチャが当たり前になっている。

- **`noUncheckedIndexedAccess` の必須化:** `tsconfig.json` のこのオプションを有効化することで配列・オブジェクトアクセスの `undefined` 見落としを排除できるが、既存コードベースへの導入コストが課題であり、段階的移行戦略が重要になっている。

- **Template Literal Types による状態機械の表現:** `type Route = '/users' | '/users/${string}/profile'` のようにURLや状態遷移をリテラル型で表現し、不正な文字列を型レベルで弾く設計が複雑なドメインロジックで有効活用されている。
