# CTO Knowledge - 2026-04-07

## Daily Update (2026-04-07)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチとレンダリングをサーバー側に集約する。`'use client'` は本当に必要な葉コンポーネントのみに限定するのが鉄則。

- **Partial Prerendering (PPR) の本番投入:** 静的シェルを即座に配信しつつ、動的部分をストリーミングで埋める PPR が Next.js 15以降で安定化。Vercel以外のセルフホスト環境でも活用できる構成を設計すべき。

- **`next/image` と `next/font` による Core Web Vitals 改善:** LCP・CLS の改善は SEO 直結。フォントはサブセット化＋`display: swap`、画像は `sizes` 属性を正確に指定してレスポンシブ最適化を怠らない。

- **Server Actions のバンドル影響に注意:** Server Actions は便利だが、誤った使い方でクライアントへの参照が増えバンドルが膨らむ。`'use server'` ファイルの分離と、不要な再レンダリングを引き起こす `revalidatePath` の乱用を避ける。

- **Edge Runtime とキャッシュ戦略の再設計:** `fetch` キャッシュの挙動が Next.js 15 で変更（デフォルト no-cache）。`unstable_cache` や `revalidateTag` を使った細粒度キャッシュ設計が必須で、Edge での TTFBを最小化するアーキテクチャを意識する。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度が鍵:** RSCストリーミングはSuspense境界単位でHTMLをチャンク送信するため、境界設計が粗いとTTFBは改善されてもLCP改善効果が薄れる。コンポーネントツリーを意図的に分割し、データ依存の深いコンポーネントだけを境界内に閉じ込めること。

- **PPR（Partial Prerendering）が実用段階に:** Next.js 15以降でPPRが安定化し、静的シェルを即座に返しつつ動的部分をストリームする設計が本番運用可能になった。CDNキャッシュとストリーミングを両立できる点でアーキテクチャ上のゲームチェンジャー。

- **Reactの`use()`APIがデータフェッチのプリミティブに:** `use(promise)`でSuspense連携が宣言的に書けるようになり、RSC内でのウォーターフォールをクライアント側でも回避しやすくなった。サーバー側でPromiseを作成してクライアントに渡すパターンが推奨される。

- **ストリーミングとエラーハンドリングの複雑性:** ストリームが途中で失敗した場合、HTTPステータスは200を返した後にエラーが発生するためモニタリングが難しい。`errorBoundary`とサーバーサイドのログ基盤（OpenTelemetryなど）を組み合わせた可観測性設計が必須。

- **バンドルサイズよりRSCペイロードサイズに注目:** RSCはJSバンドルを削減する一方、サーバーからクライアントへのRSCペイロード（JSONシリアライズされたツリー）が肥大化するリスクがある。不必要なデータをクライアントコンポーネントに流さない設計と、ペイロードサイズのCI監視が2026年のベストプラクティス。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年時点でtRPCはNext.js/TypeScriptスタックにおけるデファクトに近づいており、スキーマ定義なしにクライアント・サーバー間の型共有が可能なため、小〜中規模プロダクトではREST/GraphQLより開発速度が大幅に向上する。

- **GraphQLの棲み分け明確化:** GraphQLはBFFパターンや複数クライアント（Web/Mobile/サードパーティ）が存在する大規模APIに有効だが、単一フロントエンドの場合はオーバーエンジニアリングになりやすく、tRPCかREST+OpenAPIが現実的な選択肢となっている。

- **REST+OpenAPI 4.0の再評価:** OpenAPI 4.0（Moonwalk）仕様の成熟により、コード生成ツール（orval, heyapi）の精度が向上し、型安全なRESTクライアントをほぼ自動生成できる環境が整った。既存REST資産の多い組織では移行コストなしに型安全性を確保できる。

- **Server-Sent Events / HTTP Streamingの普及:** AIレスポンスのストリーミング需要増により、WebSocketではなくSSEやHTTP Streamingを選ぶケースが急増。tRPCもサブスクリプションでSSEをサポートしており、インフラ複雑性を下げつつリアルタイム通信を実現できる。

- **エッジ・サーバーレス環境での制約:** Cloudflare WorkersやVercel Edge RuntimeではWebSocketや長時間接続に制限があるため、APIデザイン選定はデプロイ環境との整合性を先に確認することが2026年の必須プラクティスとなっている。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジのデファクトランタイムに:** Cloudflare Workers・Fastly Compute@Edgeを中心にWasmが標準化し、言語非依存でコールドスタートほぼゼロの実行環境が普及。Rustや Go製のコンポーネントをそのままエッジにデプロイするワークフローが定着している。

- **エッジDBとデータロカリティの融合:** Cloudflare D1・Turso（libSQL）などのエッジネイティブSQLiteが本番レベルに成熟し、「コンピュートはエッジ、データはリージョン中央」というレイテンシ問題が実用的に解消されつつある。

- **AI推論のエッジオフロード加速:** LLMの量子化モデル（Llama系・Phi系）をエッジで動かすユースケースが急増。Cloudflare AI Gatewayなどのプロキシ層がキャッシュ・レート制限・ルーティングを統合し、インフラコストとレイテンシを同時に削減する設計が現実解になった。

- **オブザーバビリティの課題がボトルネック:** エッジ関数は分散ノード数が桁違いに多く、従来のAPMツールでは追跡が困難。OpenTelemetryのエッジ対応（Baggageプロパゲーション・サンプリング戦略）の設計を最初から組み込まないと、障害調査コストが跳ね上がる。

- **ベンダーロックインリスクの再評価:** WinterCG（Web-interoperable Runtimes Community Group）準拠のAPIが広がり、Deno Deploy・Vercel Edge・Netlify Edgeをほぼ同一コードで動かせるようになった。アーキテクチャ選定時はWinterCG準拠度を移植性の指標として使うべき。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準採用:** FIDO2/WebAuthn ベースのパスキーがパスワードレス認証の主流となり、フィッシング耐性と UX 向上を両立できる。Next.js プロジェクトでは `@simplewebauthn/server` で比較的容易に実装可能。

- **セッション管理の短命化と再検証:** アクセストークンの有効期限を 15 分以下に設定し、リフレッシュトークンのローテーションを必須化する。JWTのペイロードに機密情報を含めず、サーバーサイドのセッションストア（Redis 等）との組み合わせが推奨される。

- **デバイスフィンガープリントによる継続的認証:** ログイン時の一度限りの確認ではなく、デバイス特性・IPレンジ・行動パターンを継続監視する「Continuous Authentication」が普及。異常検知時に Step-up 認証を要求するフローが実用的。

- **サプライチェーン攻撃対策としての依存関係監査:** 認証ライブラリへの悪意あるコード混入（例: 2025年の複数npm package事件）が増加。`bun audit` の CI 必須化と、`package.json` の依存ロックによるハッシュ検証が最低限の対策。

- **OAuth 2.1 + DPoP によるトークン binding:** Bearer トークンの盗難リスクを軽減するため、DPoP（Demonstrating Proof of Possession）でトークンをクライアントの鍵ペアに紐付ける OAuth 2.1 の採用が拡大。特にモバイル・SPA からの API 呼び出しに有効。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6 + Supabase の相性が向上:** Prisma 6でのEdge Runtime対応とコネクションプーリング改善により、Supabase PgBouncerとの組み合わせがサーバーレス環境でも安定稼働。`DATABASE_URL`にpooling URLを使い、マイグレーションは`DIRECT_URL`で分離する設定が標準パターンに。

- **Row Level Security (RLS) をORMレイヤーで扱う複雑性:** SupabaseのRLSはPostgresネイティブだが、Prismaはbypassして接続するためセキュリティ境界が曖昧になりやすい。サービスロールキーの使用範囲を最小化し、RLSはDBレイヤー、アプリ認可はミドルウェアと責務を明確に分離すべき。

- **Supabase Realtime + Postgres Changes の実用化:** 2026時点でRealtime v2が安定し、テーブル変更をWebSocket経由でサブスクライブできる。PrismaのCRUD操作後にリアルタイムUIを更新する用途では、Realtimeチャネルとの二重管理を避けるアーキテクチャ設計が重要。

- **マイグレーション戦略の分岐:** `prisma migrate`はスキーマファースト、Supabase CLIは`supabase db diff`でDBファースト。両者を混在させるとコンフリクトが発生しやすいため、チームで**どちらをSingle Source of Truth**にするか早期に決定することが必須。

- **ベクトル検索との統合 (pgvector):** Supabase + pgvectorによるセマンティック検索が実用段階に。Prismaはpgvectorのネイティブサポートが限定的なため、RAW SQLや`$queryRaw`を併用するか、Drizzle ORMへの移行も選択肢として評価すべきタイミング。

### 7. WebAssembly Rust performance 2026

- **Component Model の成熟:** WASI Preview 2 / Component Model が2025年に安定化し、RustのWasmコンポーネントをホスト言語に依存せず構成・再利用できるようになった。マイクロサービス的なWasmコンポジションが実用フェーズへ。

- **コンパイルサイズの大幅改善:** `wasm-opt` + `wee_alloc` 代替の `talc` アロケータ活用により、バイナリサイズが従来比30-50%削減可能。初回ロードのボトルネックが解消され、エッジデプロイの現実解になりつつある。

- **SIMD & スレッド並列の普及:** WebAssembly SIMDとShared Memory Threads が主要ブラウザで安定稼働。Rustの `rayon` ライクな並列処理をWasm上で動かす事例が増え、画像処理・暗号・ML推論での採用が加速。

- **Wasmtime / WasmEdge のサーバーサイド高速化:** JITコンパイル最適化により、ネイティブ比95%超のスループットを達成するケースが報告されている。Cloudflare Workers・Fastly Compute でのRust Wasmは、Coldstart < 1ms が現実的な数値に。

- **デバッグ・プロファイリング環境の整備:** DWARF対応の強化により、Chrome DevToolsとRustのソースマップが正確に紐づくようになった。`cargo-component` + `wit-bindgen` によるツールチェーンも統合が進み、開発体験のギャップがほぼ解消。

### 8. Next.js App Router patterns 2026

- **Server Componentsをデフォルトに:** 2026年時点でApp Routerの主流はRSC（React Server Components）ファーストの設計。データフェッチはサーバー側で完結させ、`'use client'`は状態・イベントハンドラが必要な最小限のリーフコンポーネントに限定することでバンドルサイズを大幅削減できる。

- **Partial Prerendering（PPR）の本格活用:** Next.js 15以降で安定化したPPRにより、静的シェル＋動的ストリーミングを1ルートで混在させるパターンが標準化。`<Suspense>`境界の設計がアーキテクチャの核心になっている。

- **Server Actionsによるフォーム処理の一本化:** API Routeを介さずServer Actionsで直接ミューテーションを処理するパターンが定着。`useActionState`との組み合わせでオプティミスティックUIも簡潔に実装でき、バックエンドとのAPI定義の二重管理が不要になる。

- **`cache()`と`unstable_cache`の使い分け:** リクエスト内重複排除には`cache()`、クロスリクエストのキャッシュには`unstable_cache`（またはNext.js 15の`use cache`ディレクティブ）と役割が明確化。キャッシュ戦略の設計ミスがパフォーマンスの最大の落とし穴になっている。

- **Parallel Routes＋Intercepting Routesによるモーダル設計:** モーダル・スライドオーバーをURLと紐づけたまま実装できるこのパターンが成熟。シェアラブルURL・ブラウザバック対応・SEO維持を同時に達成でき、従来の`useState`ベースのモーダル管理を置き換えつつある。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの活用範囲拡大:** 2026年時点ではVercel Edge FunctionsはNode.js互換性が大幅に向上し、従来はServerless Functionsが必要だった処理もEdgeで実行可能になった。コールドスタートがほぼゼロのため、レイテンシ重視のAPIエンドポイントはEdgeに移行するのが定石。

- **Fluid Compute導入によるスケーリング効率化:** Vercelが導入したFluid Computeモデルにより、リクエスト間でのCPUリソース再利用が可能になり、従来のサーバーレスモデルと比べてコスト効率が向上。バースト処理が多いワークロードで特に効果的。

- **データベース接続の最適化:** EdgeからのDB接続はコネクションプーリング対応のPrisma Accelerate、Neon Serverless Driver、Upstash Redisを組み合わせるのが2026年のベストプラクティス。従来型のTCP接続は不可のため、HTTP/WebSocket対応のドライバー選定が設計上の重要ポイント。

- **Partial Prerendering（PPR）との組み合わせ:** Next.js 15以降でPPRが安定化し、静的シェルをCDNから配信しつつ動的部分のみEdge Functionでストリーミングするパターンが主流に。TTFBとINPの両方を改善できるため、パフォーマンス最適化の優先度高い。

- **地理的ルーティングとA/Bテストのネイティブ化:** Edge Middlewareを使ったgeolocationベースのルーティングやフィーチャーフラグ評価をアプリケーション層で実装するケースが増加。ただしMiddlewareのバンドルサイズ上限（1MB）を超えないよう、依存ライブラリの精査が必須。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `type UserId = string & { _brand: 'UserId' }` パターンが広く採用され、プリミティブ型の混同バグをコンパイル時に検出できるようになった。zodの `.brand()` との組み合わせでバリデーション層との統合も容易。

- **satisfies 演算子の活用:** TypeScript 4.9以降の `satisfies` が2026年では当たり前の書き方に。型推論を保ちながら型チェックを行えるため、`as const` との組み合わせでオブジェクトリテラルの型安全性が大幅向上。

- **Template Literal Types による API 型定義:** `type Route = '/users' | '/users/${string}'` のようなパターンでREST APIのパスを型レベルで表現し、誤ったエンドポイント呼び出しをコンパイル時に防ぐ設計が普及。

- **Discriminated Union の徹底と exhaustive check:** `never` 型を使った網羅性チェックが標準実装パターンに。switch文の `default` で `assertNever(x)` を呼ぶことで、Union型に新ケースが追加された際のコンパイルエラーを保証できる。

- **Zod + tRPC による型の単一ソース化:** フロントエンド・バックエンド間でスキーマを共有し、実行時バリデーションと静的型を同時に確保するアーキテクチャが定着。手書きの型定義とバリデーションの二重管理が撲滅されつつある。
