# CTO Knowledge - 2026-06-26

## Daily Update (2026-06-26)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格採用:** Next.js 15以降で安定した PPR により、静的シェルを即時配信しつつ動的部分を Suspense でストリーミングできる。本プロジェクトの `properties/` 一覧ページなど、ヘッダーやレイアウトは静的化し、物件データのみ動的取得する構成にすれば初期表示速度（TTFB/LCP）を大幅改善できる。

- **React Server Components のデータフェッチ最適化:** クライアントバンドルを減らすため、可能な限り Server Component でデータ取得を行い、`use client` の境界を最小限に絞る。`src/lib/data.ts` のようなデータ層を Server Component から直接呼び出し、不要な API Route 経由のフェッチを排除するのが2026年のベストプラクティス。

- **`next/image` と AVIF/レスポンシブ配信の徹底:** 物件写真のような画像中心の体験では、AVIF優先・`sizes` 属性の適切な指定・CDNキャッシュ戦略がCore Web Vitals（特にLCP）に直結する。Airbnb風UIの画像ギャラリーは特に影響が大きい領域。

- **Turbopack ビルドの本番運用とキャッシュ戦略:** Turbopack が安定し、ビルド時間とHMRが大幅短縮される一方、`fetch` キャッシュやルートセグメントキャッシュの挙動が変わりやすいため、`revalidate` 戦略を明示的に設計しないと意図しないキャッシュヒット/ミスが発生しやすい。

- **Edge Runtime の選択的活用:** 認証チェックやリダイレクトなど軽量なミドルウェア処理はEdge Runtimeに寄せ、DBアクセスを伴う重い処理はNode.jsランタイムに残すハイブリッド構成が、レイテンシとコストのバランスにおいて2026年の定番パターンになっている。

### 2. React Server Components streaming 2026

- **Suspenseバウンダリの粒度設計:** RSCストリーミングの効果はSuspense境界の置き方で決まるため、ページ全体を1つの境界で囲うのではなく、データ取得が遅いコンポーネント単位で細かく分割し、TTFBとLCPを両立させるのが定石です。

- **selective hydrationとPartial Prerendering(PPR)の併用:** Next.js 15以降で安定したPPRにより、静的シェルを即時返しつつ動的部分だけをストリームで後送りできるため、Edgeでの初期表示速度がさらに改善されています。本プロジェクトもNext.js 16なので、物件詳細ページの静的部分（レイアウト・固定情報）と動的部分（在庫状況・前の住人レビュー）を分けてPPR適用を検討する価値があります。

- **Server Actionsとストリーミングの統合:** フォーム送信後の楽観的UI更新がuseActionState/useOptimisticと組み合わさり、ストリーミングレスポンス中でも段階的にUIを更新できるパターンが2025-2026年で標準化されつつあります。

- **キャッシュ戦略の複雑化への対応:** RSCのストリーミングが進むほど`fetch`のキャッシュタグ管理（revalidateTag）やper-segment cachingの設計ミスがパフォーマンス劣化やデータ不整合の原因になりやすく、本番投入前にキャッシュ境界を明示的に文書化すべきです。

- **観測性（Observability）の重要性:** ストリーミング中の各チャンク到達時間を計測しないとボトルネックが見えないため、Server Timing APIやVercel Analyticsなどでセグメント単位のレイテンシを可視化する運用が、ローンチ後の改善サイクルで必須になっています。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭継続:** Next.js App Router + TypeScriptの組み合わせでは、tRPCがREST/GraphQLより開発速度に優れる。型がエンドツーエンドで自動推論されるため、API契約の手動同期(OpenAPI生成やGraphQLスキーマ管理)が不要になり、当プロジェクトのようなモノレポ構成では特に有利。

- **GraphQLは複雑なクライアント要件がある場合のみ:** 複数クライアント(モバイル/Web/サードパーティ)が異なるデータ形状を要求する場合はGraphQLが依然強い。sumitsugiのような単一Next.jsアプリ+内部APIのみの構成では、GraphQLのオーバーヘッド(リゾルバ層、N+1対策)は過剰投資になりがち。

- **RESTはパブリックAPI・外部連携の標準:** 将来的に外部の不動産連携(物件情報API連携など)を想定するなら、外部向けはREST(OpenAPI仕様)、内部の前の住人/次の住人間のやり取りはtRPCというハイブリッド構成が2026年のベストプラクティス。

- **Server ActionsとtRPCの境界が曖昧化:** Next.js 16のServer Actionsが進化し、単純なCRUD(物件のdraft/public切り替えなど)はServer Actionsで十分なケースが増えている。tRPCは複雑なクエリ・キャッシュ戦略が必要な箇所(検索・フィルタリング)に限定する判断が重要。

- **Zodによる入力検証がAPI設計の共通言語に:** REST/GraphQL/tRPCいずれを選んでも、Zodスキーマでの境界検証が標準化されつつある。当プロジェクトの`.claude/rules/standards.md`にもある「システム境界でのZod検証」方針は、どのAPI方式を選んでも一貫して適用すべき原則。

### 4. serverless edge computing 2026

- **エッジでのコールドスタート解消:** V8 isolateベースのランタイム(Cloudflare Workers、Vercel Edge等)がデフォルト化し、コンテナ起動を待たないミリ秒単位の応答が標準になりつつある。sumitsugiのようなNext.js App Routerプロジェクトでは、物件検索や画像配信のAPI routeをEdge Runtimeに切り出すことでTTFBを大幅短縮できる。

- **ステートフルエッジ(Durable Objects/KVの進化):** エッジでも一貫性のあるデータ操作が可能になり、SQLite互換のエッジDB(Cloudflare D1, Turso等)が実用段階に入った。リアルタイム性が求められる物件ステータス更新や通知機能をリージョン跨ぎで低遅延に扱える設計が選択肢として広がっている。

- **AI推論のエッジ移行:** 軽量LLM・embeddingモデルをエッジで直接実行する事例が増え、レコメンドや検索のレイテンシをオリジン往復なしで改善できる。前の住人と次の住人のマッチング推薦のような機能は、将来的にエッジ推論で個人情報をリージョン外に出さずに処理する設計が現実的になる。

- **ビルド/デプロイの単純化とベンダーロックインのトレードオフ:** Next.jsのEdge最適化が各プラットフォーム(Vercel/Cloudflare/Deno Deploy)で進む一方、Node.js APIの一部非対応など制約も残る。本番投入前にはミドルウェアやAPI routeの互換性検証が必須で、build integrityルール(`bun run build`)で型・実行環境の差異を早期に検出する体制が重要。

- **コスト構造の変化(従量課金の精緻化):** リクエスト単位・CPU時間単位の課金がさらに細分化され、低トラフィック期のコストはほぼゼロに近づく一方、スパイク時のコスト予測が難しくなる傾向。ベータローンチ前のsumitsugiのような段階では、エッジ移行はコスト最適化よりもまず体感速度改善の効果を測定してから判断するのが実用的。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への全面移行:** パスワードレス認証(WebAuthn)がデフォルト選択肢となり、フィッシング耐性のある認証情報を端末のSecure Enclaveで管理することが標準化している。sumitsugiでも前の住人/次の住人の本人確認フローにパスキーを組み込むことで、SMS OTPより低コストかつ高セキュリティを実現できる。

- **トークンの短命化とリフレッシュトークンローテーション:** JWTのアクセストークンは15分以内の短寿命にし、リフレッシュトークンはワンタイム使用+ローテーションで盗用検知（reuse detection）を行うのがベストプラクティス。Next.js App RouterではServer Actions経由でhttpOnly Cookieにのみトークンを保持し、クライアントJSに触れさせない設計が重要。

- **CSRF対策のSameSite Cookie依存からの脱却:** SameSite=Strict/Laxだけに頼らず、Origin/Refererヘッダー検証とCSRFトークンの併用が2026年の標準。物件公開状態(`draft`/`public`)の切り替えなど破壊的操作には必ず二重防御を入れるべき。

- **認可ロジックのZero Trust化:** 認証(誰か)と認可(何ができるか)を分離し、RBACからABAC/ReBAC（属性・関係ベース）へ移行する流れが加速。引越し費用決済や個人情報を含む引き継ぎフローでは、リクエスト単位でのきめ細かい権限チェックがコンプライアンス上必須になる。

- **シークレット管理のSecretless化:** 環境変数への直接ハードコードを避け、Vault/KMSによる動的シークレット発行とOIDC連携（GitHub Actions ↔ Cloudプロバイダー）で長期APIキーを撲滅する流れ。CLAUDE_CODE_OAUTH_TOKENのような長期トークンも定期ローテーションと最小権限スコープの徹底が必要。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6系のRust-free移行:** Prisma ORMのクエリエンジンがRustバイナリ依存から脱却しTypeScript/WASMベースへ移行が進み、Vercel/Edge環境でのコールドスタートとバンドルサイズが大幅改善される。sumitsugiのNext.js 16 App Router構成では特にEdge Functions利用時のレイテンシ低減効果が大きい。

- **Supabase Branching + Prisma Migrate併用:** Supabaseのデータベースブランチ機能とPrisma Migrateを組み合わせることで、PR単位で本番同等のスキーマ環境を自動生成し、マイグレーションの破壊的変更をCIで事前検知できる。物件ステータス（`draft`/`public`）のようなUnion型変更時のリグレッション防止に有効。

- **Row Level Security (RLS) とPrisma Client併用の標準化:** SupabaseのRLSをDB層の最終防御線とし、Prismaのアプリ層バリデーション（Zod）と二重化する構成が2026年のベストプラクティスとして定着。前の住人/次の住人間の物件データアクセス制御で認可ロジックの単一障害点を回避できる。

- **PgBouncer/Supavisorによる接続プーリング最適化:** ServerlessなNext.js環境ではPrisma ClientのコネクションプールがDB接続を枯渇させやすく、SupabaseのSupavisor（トランザクションモード）併用が必須になっている。`DATABASE_URL`と`DIRECT_URL`の分離設定が事実上の標準パターン。

- **Prisma Accelerate/キャッシュ層の普及:** 読み取り頻度の高い物件一覧・検索クエリにPrisma Accelerateのグローバルキャッシュやエッジキャッシュを導入し、Supabase本体への負荷を削減する構成が増えている。引っ越し費用計算など計算コストの高いクエリのレスポンス改善に直結する。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデルの定着:** WASM Component ModelとWASIp2/p3の標準化が進み、Rustでも`cargo component`を使ったポリグロット連携が実用段階に入っている。これにより異なる言語で書かれたWASMモジュール同士をネイティブ並みの速度で呼び出せる。

- **メモリ管理の効率化:** Rustの所有権モデルはGC不要なWASMバイナリを生成できるため、JS/TypeScriptやGo由来のWASMよりも起動時間とメモリフットプリントが小さく、エッジ・サーバーレス環境（Cloudflare Workers, Fastly Compute）での採用が増えている。

- **SIMDとマルチスレッドの実用化:** `wasm32-unknown-unknown`でのSIMD128サポートとシェアードメモリ/Web Workersを使った並列処理が安定し、画像処理・暗号化・数値計算系のワークロードでネイティブの70-90%程度の性能まで近づいている。

- **ツールチェーンの成熟:** `wasm-bindgen`/`wasm-pack`に加えて、`wit-bindgen`によるインターフェース定義が標準化されつつあり、バイナリサイズ削減（`wasm-opt`, `twiggy`）とデバッグ体験（DWARF対応）が改善され、本番投入の障壁が下がっている。

- **サーバーサイドWASMの台頭:** Wasmtime/WasmEdgeなどのランタイムがコンテナの軽量な代替として注目され、Rust製のWASMモジュールをサンドボックス化したプラグインシステム（例: マルチテナントSaaSでのカスタムロジック実行）に使うパターンが増えている。sumitsugiのような物件管理プラットフォームでも、将来的に前の住人ごとのカスタムルール処理を安全に分離実行する用途で検討の余地がある。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格採用:** 静的シェルと動的コンテンツを1つのルートで共存させ、TTFBを最小化しつつパーソナライズされたUIを提供できる。sumitsugiの`properties/`一覧ページのような「静的な検索UI＋動的な物件データ」構成に特に有効。

- **Server Actionsのキャッシュ戦略統一:** `revalidatePath`/`revalidateTag`の使い分けが2026年では標準化され、ミューテーション後の再検証ロジックをuseOptimisticと組み合わせて即時反映するパターンが主流に。物件ステータス変更（`draft`↔`public`）のようなトグル操作で有効。

- **`use cache`ディレクティブの定着:** Next.js 15以降で導入されたコンポーネント/関数レベルのキャッシュ制御が成熟し、`fetch`オプションよりも明示的で予測可能になった。`src/lib/data.ts`のデータ取得層に適用すればビルド時間とランタイムコストを両方削減できる。

- **Layout/Templateの責務分離が厳格化:** ネストしたレイアウトでのデータ重複フェッチを避けるため、Request Memoizationを前提にした設計が必須になりつつある。認証コンテキスト（`auth-context.tsx`）をServer Componentベースに移行する際の落とし穴になりやすい。

- **App Router専用の型安全ルーティング:** `next typegen`によるルート・検索パラメータの型生成が一般化し、`listing/[id]`のような動的ルートでの型ミスマッチをビルド時に検出可能になった。当プロジェクトのBuild Integrity方針（CLAUDE.md）と相性が良く、導入価値が高い。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1（Edge Runtimeの制約理解):** Vercel Edge FunctionsはNode.js APIの一部（fs, 一部のcryptoなど）が使えないV8 isolateベースの実行環境のため、依存ライブラリ選定時にEdge互換性を事前検証することがデプロイ失敗を防ぐ鍵になる。

- **ポイント2（コールドスタート最小化）:** Edge FunctionsはServerless Functionsよりコールドスタートが大幅に短いが、バンドルサイズ（特にimportするライブラリ）が大きいとTTFBが悪化するため、不要な依存を削ぎ落とし軽量化することがレイテンシ最適化に直結する。

- **ポイント3（地理的ルーティングの活用）:** リクエストの発生地点に最も近いEdge Locationで実行されるため、ユーザー位置情報に基づくパーソナライズ（言語切替、地域別価格表示など）をEdgeで処理し、オリジンサーバーへの往復を減らすことでレスポンス速度を改善できる。

- **ポイント4（キャッシュ戦略との併用）:** Edge Functionsだけに頼らず、ISR（Incremental Static Regeneration）やstale-while-revalidateと組み合わせることで、動的処理が必要な部分のみEdgeで実行し、それ以外は静的配信に任せるハイブリッド構成がコストとパフォーマンスの両立に有効。

- **ポイント5（オブザーバビリティの確保）:** Edge環境はデバッグが難しいため、構造化ログとトレーシング（OpenTelemetry等）を早期から組み込み、本番でのレイテンシ・エラー要因を可視化しておくことが、sumitsugiのようなユーザー向け機能（物件検索・認証フローなど）の安定運用に重要。

### 10. TypeScript type safety patterns 2026

- **Branded Types / Nominal Typing:** `type UserId = string & { readonly __brand: 'UserId' }` のようなブランド型で、プリミティブ型の取り違えバグ（例: `propertyId`と`userId`の混同）をコンパイル時に防止。sumitsugiのような複数IDが飛び交うドメインでは特に有効。

- **Zodによるランタイム検証とスキーマ駆動の型推論:** `z.infer<typeof schema>`で型定義とランタイム検証を一元化し、APIレスポンスやフォーム入力など「境界」での型安全性を保証。本プロジェクトの標準（システム境界でのZod利用）とも合致するパターン。

- **Discriminated Union による状態管理:** `'draft' | 'public'`のようなステータス型は、単純なリテラルユニオンではなく判別可能なオブジェクト（`{ status: 'draft', ... } | { status: 'public', publishedAt: Date }`）に拡張することで、状態ごとに必須プロパティを型レベルで強制できる。

- **`satisfies` 演算子の定着:** TypeScript 4.9以降、設定オブジェクトや定数定義で型推論を保ったまま型チェックする`satisfies`が標準パターンとして広く普及し、`as const`との併用でリテラル型推論と型安全性を両立。

- **TypeScript 6.x のGo移植コンパイラ（tsgo）によるビルド高速化:** 2025年末〜2026年にかけて進む型チェッカーのネイティブ移植により、大規模モノレポでの型チェック時間が大幅短縮。CIのビルド検証ステップ（`bun run build`必須化）のコストを下げる方向に寄与する見込み。
