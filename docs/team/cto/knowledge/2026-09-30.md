# CTO Knowledge - 2026-09-30

## Daily Update (2026-09-30)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格採用:** Next.js 15以降で安定版となったPPRにより、静的シェルを即座に配信しつつ動的部分のみをストリーミングできる。初期表示速度（TTFB/LCP）が大幅に改善するため、`properties`一覧ページのような「静的な枠+動的な物件データ」構成に適用すると効果が大きい。

- **React Compiler導入によるメモ化の自動化:** `useMemo`/`useCallback`を手動で書かなくても、ビルド時に最適な再レンダリング制御が自動生成される。既存コンポーネントの手動最適化コードを削減しつつ、レンダリングパフォーマンスを底上げできる段階に来ている。

- **`next/image`とストリーミングメタデータの最適化:** 物件写真のような画像中心のUIでは、`sizes`属性の適切な設定とCDN経由の自動フォーマット変換（AVIF/WebP）がCore Web Vitalsに直結する。加えてメタデータのストリーミング対応により、OGP生成がブロッキングにならなくなった。

- **Server Actions のキャッシュ戦略見直し:** `unstable_cache`や`revalidateTag`を使った粒度の細かいキャッシュ無効化が主流になり、問い合わせフォームや引越し費用計算など動的処理でも過剰な再検証を避けられる。物件ステータス（draft/public）の切り替え時にタグベースの再検証を組み込むと、キャッシュ整合性と速度を両立しやすい。

- **Edge Runtimeの使いどころの明確化:** 全てをEdgeに寄せるのではなく、認証チェックや軽量なリダイレクトのみEdge Middlewareで処理し、DB接続を伴う処理はNode runtimeに残す「ハイブリッド配置」がベストプラクティスとして定着してきている。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではRSCのストリーミングとPartial Prerendering(PPR)が標準的な組み合わせとなり、静的シェルを即座に返しつつ動的部分をSuspense境界ごとに段階的にストリーミングすることで、TTFBとLCPを大幅に改善できる。物件一覧・詳細ページのような「静的な骨組み＋動的な価格/在庫情報」の構成に特に有効。
- **ポイント2:** `use cache`ディレクティブとCache Componentsの実用化が進み、RSCペイロードのキャッシュ粒度をコンポーネント単位で制御できるようになった。頻繁に更新されない物件情報と、リアルタイム性が必要な空室状況を分離してキャッシュ戦略を組むべき。
- **ポイント3:** ストリーミングSSR環境でのエラーバウンダリ設計が重要度を増している。Suspense境界内で発生した例外が部分的なストリームに漏れないよう、`error.tsx`とSuspenseの組み合わせを各セクション（物件画像、レビュー、地図など）ごとに細かく設計する必要がある。
- **ポイント4:** RSCとClient Componentsの境界を意識したバンドルサイズ最適化が引き続き重要。フォームや認証まわりのインタラクティブ要素（`src/components/auth/`等）を最小限のClient Componentに閉じ込め、それ以外はServer Componentとしてストリーミングすることで初期JS転送量を削減できる。
- **ポイント5:** Edge Runtimeでのストリーミング配信とCDN側のストリーミングキャッシュ（stale-while-revalidate的な挙動）の組み合わせが一般化しており、グローバル配信時のレイテンシ改善に寄与する。当社の引越し費用計算やマッチング機能のような動的要素も、Edgeでのストリーミングにより体感速度を落とさず提供可能。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** 2026年はtRPCがフルスタックTypeScriptプロジェクトの標準的選択肢として定着しており、Next.js 16のApp Routerとの親和性が高く、型安全性をエンドツーエンドで担保できる点が最大の利点。sumitsugiのような単一リポジトリ構成では、REST+OpenAPIよりもスキーマ同期のオーバーヘッドが少ない。

- **ポイント2:** GraphQLは大規模で複数クライアント（Web/モバイル/サードパーティ）が同一バックエンドを叩く場合に依然強いが、単一のNext.jsフロントエンドのみを持つプロダクトでは過剰設計になりやすく、N+1問題やキャッシュ戦略の複雑さがコストに見合わないケースが多い。

- **ポイント3:** RESTは依然としてWebhookや外部連携（決済代行・不動産データ連携API等）の事実上の標準であり、tRPCを内部API、RESTを外部公開APIとして使い分けるハイブリッド構成が2026年のベストプラクティスになりつつある。

- **ポイント4:** OpenAPI仕様からのコード生成（Zodスキーマ + 型定義の自動生成）がtRPC/REST双方で一般化し、標準に定めているZodバリデーションをAPI境界と型定義の両方で再利用することで、二重メンテナンスを避けられる。

- **ポイント5:** サーバーコンポーネント（RSC）の普及により、フロントエンド-バックエンド間の「API」自体を薄くする設計（Server Actions中心）が増えており、tRPCすら不要になるユースケースも出てきているため、新機能ではまずServer Actionsで十分か検討し、外部連携やクライアント側の複雑な状態管理が必要な箇所にのみtRPC/RESTを充てるのが効率的。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG仕様（Web標準API準拠）が浸透し、Cloudflare Workers・Vercel Edge・Deno Deployなど各社ランタイムの互換性が向上。ベンダーロックインを避けつつ、Next.jsのMiddlewareやRoute Handlersを複数プラットフォームで再利用しやすくなっている。

- **エッジDBとレイテンシ解消:** Cloudflare D1、Turso、PlanetScaleなどのエッジネイティブDBが成熟し、「エッジで動くがDBだけ中央集権」というボトルネックが緩和。sumitsugiのような物件検索・リアルタイム性が求められる機能では、リージョン分散読み取りレプリカの活用で体感速度を大きく改善できる。

- **コールドスタート問題の実質解消:** V8 isolateベースの実行モデルにより、エッジ関数のコールドスタートはミリ秒未満が一般化。認証チェックや物件ステータス判定など軽量ロジックをMiddlewareでエッジに逃がすコストが実質ゼロになり、オリジンサーバーの負荷分散に直結する。

- **AI推論のエッジ配置:** 軽量LLM推論（埋め込み生成、レコメンド、要約）をエッジで実行するパターンが一般化。物件マッチングや「引越し費用」見積もりのような軽量AI処理をエッジに置くことで、往復レイテンシを削減しつつAPI費用も抑えられる。

- **コスト構造の逆転リスク:** リクエスト数課金のエッジ関数は、トラフィックが伸びると従来のサーバーレス（Lambda等）より高コストになるケースが増加。MVPローンチ初期はエッジ活用で高速なUXを実現しつつ、スケール時のコスト試算（リクエスト単価×想定PV）を早めにシミュレーションしておくべき。

### 5. authentication security best practices 2026

- **ポイント1（パスキー標準化）:** パスワードレス認証（FIDO2/WebAuthn準拠のパスキー）が2026年時点でデファクトスタンダードとなり、フィッシング耐性のある認証がユーザー体験を損なわずに実現可能。sumitsugiのような個人情報を扱うプラットフォームでは、次の住人・前の住人双方の本人確認にパスキーを優先導入すべき。

- **ポイント2（多層防御とセッション管理）:** MFAだけでなく、デバイスフィンガープリンティングと異常ログイン検知（IPリスクスコアリング）を組み合わせたアダプティブ認証が主流に。長期セッショントークンはリフレッシュトークンローテーション＋短命アクセストークンで運用し、盗難時の被害範囲を最小化する。

- **ポイント3（サプライチェーンとOAuth設定の堅牢化）:** サードパーティ認証連携（Google/Apple等のソーシャルログイン）を使う場合、redirect_uri検証とstate/PKCEパラメータの厳格な検証が必須。認証ライブラリの依存関係は定期的な脆弱性スキャンを自動化し、CIに組み込む。

- **ポイント4（ゼロトラストとRBAC）:** 認証（誰か）と認可（何ができるか）を明確に分離し、物件ステータス（draft/public）や取引フローに応じた最小権限のRBACを徹底。管理者権限を持つアカウントには追加のステップアップ認証を要求する。

- **ポイント5（監査ログと法規制対応）:** 認証イベント（ログイン・パスワードリセット・権限変更）は改ざん防止の監査ログとして保存し、個人情報保護法対応の観点からログ自体にも保持期間とアクセス制御を設定。ローンチ前の法務確認フェーズでは、この監査ログ設計をプライバシーポリシーの記述と整合させることが重要。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma ORMはRust製クエリエンジンからWasm/TypeScript純正エンジンへの移行を進めており、Supabaseのようなエッジ・サーバーレス環境（Vercel Edge Functions、Cloudflare Workers）でのコールドスタート短縮とバンドルサイズ削減が実現しつつある。sumitsugiのようなNext.js App Router構成では、Route Handler単位でのDB接続オーバーヘッド削減に直結する。
- **ポイント2:** SupabaseはPostgreSQLのRLS（Row Level Security）をPrisma経由でも活用しやすくなっており、認証コンテキスト（`auth.uid()`）をアプリ層とDB層の両方で二重に検証する設計が主流化している。物件データの`draft`/`public`ステータス制御のような可視性ロジックは、アプリ側のフィルタだけでなくRLSポリシーでも強制すべき。
- **ポイント3:** コネクションプーリング問題（サーバーレス関数ごとに新規接続が乱立する問題）への対応として、Supabase純正のPgBouncer（Supavisor）とPrisma Accelerateの併用がデファクト化している。トラフィック増加時のDB接続枯渇を防ぐため、本番運用前にプーリング設定の検証が必須。
- **ポイント4:** Prisma 6系以降はマルチスキーマ・マルチファイルスキーマ定義（`prisma/schema/*.prisma`）が安定化し、物件・ユーザー・取引など複数ドメインを持つプロジェクトでスキーマファイルを分割しやすくなった。200-400行/ファイルというコーディング規約とも相性が良い。
- **ポイント5:** SupabaseのリアルタイムサブスクリプションとPrismaのイベントフックを組み合わせ、「次の住人」への引き継ぎステータス変更を即座にUIへ反映するパターンが一般化している。ただし過度なリアルタイム購読はコネクション数を圧迫するため、必要な画面（取引進行中のみ等）に限定する設計が推奨される。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** wasm-bindgenやwasm-packのツールチェーンが成熟し、RustコンパイラのLLVM最適化とWASMのSIMD128命令セットが標準サポートされたことで、ネイティブコードの80〜90%程度の実行速度が現実的になっている。画像処理や暗号化処理など計算集約的な処理をブラウザ側に移す判断がしやすくなった。
- **ポイント2:** WASI Preview 2やComponent Modelの普及により、サーバーサイドでもWasmランタイム（Wasmtime, Wasmer）上でRustバイナリを動かすユースケースが増えている。コンテナより起動が速く分離性も高いため、エッジコンピューティングやマルチテナントSaaSのサンドボックス実行に向いている。
- **ポイント3:** メモリ管理はまだ課題で、Wasmの線形メモリモデル上でのGC連携（GC提案）が進行中だが、Rustのような所有権モデル言語は追加のGC不要で有利。JS/TS側との頻繁なデータ受け渡しがある場合はシリアライズコストがボトルネックになりやすく、境界を越える呼び出し回数を減らす設計が重要。
- **ポイント4:** バンドルサイズ最適化（wasm-opt, `wee_alloc`廃止後の軽量アロケータ選定）が引き続き重要な実務ポイントで、初期ロード時間を抑えるためコード分割・遅延ロードとの組み合わせが標準パターンになっている。
- **ポイント5:** マルチスレッド対応（Wasm Threads + SharedArrayBuffer）がブラウザで広くサポートされ、Rustの`rayon`をWasm向けに使う事例が増加。CPU負荷の高い処理を並列化できるため、フロントエンドでの重い前処理をサーバーにオフロードせず完結させる選択肢が増えた。

### 8. Next.js App Router patterns 2026

- **ポイント1: Server Components前提の設計がデフォルト化:** Next.js 16ではApp RouterのServer Componentsが標準となり、クライアントバンドルサイズを最小化するために「Client Componentは末端の葉ノードにのみ配置する」設計が定石化しています。sumitsugiでも`src/app/`配下のページは可能な限りServer Componentのまま保ち、インタラクティブなUIパーツ（フォーム、モーダル等）のみ`'use client'`を付与する構成が推奨されます。

- **ポイント2: Partial Prerendering (PPR) の実用化:** 静的シェルを即座に返しつつ動的部分をストリーミングするPPRが安定版として広く採用され、物件一覧ページのような「静的なレイアウト+動的な検索結果」の組み合わせに最適です。`loading.tsx`とSuspense境界を細かく設計することで、体感速度とSEOを両立できます。

- **ポイント3: Server ActionsによるフォームロジックのAPI Route脱却:** 問い合わせフォームや引き継ぎ申請フローなど、これまでAPI Routeで実装していたミューテーションをServer Actionsに統合する流れが定着しています。Zodバリデーションと組み合わせることで、境界での入力検証（standards.mdの方針）とサーバーロジックを1ファイルに閉じ込められ、型安全性も向上します。

- **ポイント4: キャッシュ戦略の明示化（`use cache`ディレクティブ）:** Next.js 16で導入された`use cache`によりコンポーネント/関数単位でキャッシュ粒度を明示的に制御できるようになり、暗黙的なfetchキャッシュへの依存から脱却するトレンドがあります。物件データのようにドラフト/公開ステータスが頻繁に変わるデータでは、キャッシュタグによる再検証（`revalidateTag`）を明示的に設計することが重要です。

- **ポイント5: Turbopackがビルドの標準に:** Bunとの組み合わせでもTurbopackが本番ビルドの既定エンジンとなり、`bun run build`の高速化が期待できる一方、Webpack専用プラグインへの依存がある場合は移行時に注意が必要です。CIでのビルド検証（standards.mdの必須項目）を継続することが、この移行期において特に重要になります。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの軽量化:** Node.js APIへの依存を最小限に抑え、Web標準API（fetch, streams）ベースで実装することで、コールドスタートを数十ms単位に短縮できる。特にミドルウェア層はバンドルサイズを1MB以下に保つのが実用的な目安。

- **リージョナルEdge Config活用:** グローバルに分散したKVストア（Edge Config）を使い、フィーチャーフラグやA/Bテスト設定をエッジ内で完結させることで、オリジンへの往復を排除しレイテンシを大幅削減できる。

- **Streaming SSRとの組み合わせ:** Edge FunctionsとReact Server Componentsのストリーミングを組み合わせることで、TTFB（Time to First Byte）を改善しつつ、動的パーソナライゼーション（前の住人情報など）を低遅延で配信可能。

- **キャッシュ戦略の細分化:** `stale-while-revalidate`とEdge Cacheのタグベース無効化を併用し、物件ステータス（draft/public）変更時のみ該当キャッシュをピンポイントで破棄する設計が、スケール時のコスト効率とデータ鮮度の両立に有効。

- **観測性とコスト管理:** Edge実行はリクエスト単位課金のため、不要な関数呼び出し（画像最適化やリダイレクトロジック）をCDN層やMiddlewareのmatcher設定で事前に絞り込み、実行回数自体を削減するのが2026年時点のベストプラクティス。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x以降の`satisfies`演算子が定着し、型推論を保ちながら型チェックできるため、`as`によるキャストを排除するパターンが標準になっている。
- **ポイント2:** Zodなどのスキーマバリデーションライブラリから型を自動生成する手法（`z.infer`）が主流化し、実行時検証と静的型を二重管理せず単一ソースで担保するアプローチが広がっている。
- **ポイント3:** テンプレートリテラル型やconditional typesを活用した「不正な状態を表現できない型設計」（Illegal States Unrepresentable）が、フォームやAPIレスポンスの型設計で重視されている。
- **ポイント4:** `unknown`を境界値のデフォルトとし、`any`を実質禁止するESLint設定（`no-explicit-any`厳格化）が新規プロジェクトの標準になりつつある。
- **ポイント5:** tRPCやHono RPCのようなEnd-to-Endの型共有フレームワークにより、フロントエンドとバックエンド間の型ズレをコンパイル時に検出する構成が普及している。
