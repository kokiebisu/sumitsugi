# CTO Knowledge - 2026-05-20

## Daily Update (2026-05-20)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを劇的に削減できるRSCを基本設計とし、`'use client'`は本当にインタラクティブな部分のみに限定する。境界設計を誤るとウォーターフォールが発生するため、データフェッチはサーバー側に集約する。

- **Partial Prerendering (PPR) による静的・動的コンテンツの混在:** Next.js 15以降で安定化したPPRを活用し、ページの静的シェルをエッジからCDN配信しつつ、動的部分をStreaming SSRで後から注入する。TTFBとLCPの両方を改善できる。

- **`next/image` と `next/font` による Core Web Vitals 最適化:** 画像は`sizes`属性を正確に指定してレスポンシブ最適化し、フォントはビルド時にサブセット化してCLS（累積レイアウトシフト）をゼロにする。これだけでLighthouseスコアが10-20pt改善するケースが多い。

- **Route Segment Config によるキャッシュ戦略の精緻化:** `revalidate`・`dynamic`・`fetchCache`をルートセグメントごとに細かく制御し、過剰な`no-store`設定を排除する。デフォルトキャッシュ挙動がNext.js 15で変わったため、既存プロジェクトは意図しないキャッシュ外れに注意。

- **Turbopack の本番採用とバンドル分析:** 2026年時点でTurbopackがstable化しており、大規模プロジェクトでのHMR速度が大幅に向上。`@next/bundle-analyzer`で定期的にクライアントチャンクを可視化し、意図しない依存の混入を早期検出することが開発速度とランタイム性能の両立に不可欠。

### 2. React Server Components streaming 2026

- **Suspense境界の細粒度設計が鍵:** 2026年時点でRSCストリーミングの実運用では、Suspenseの粒度が体感速度を左右する。ページ全体より、コンポーネント単位のfallbackを設計し、重いデータフェッチだけをサスペンドさせるパターンが定着している。

- **`use(promise)` APIによるストリーミング統一:** React 19の`use()`フックにより、Client ComponentでもServer Componentと同様にPromiseをサスペンドできる。これによりストリーミングの制御ロジックがサーバー・クライアント間で一貫して書けるようになった。

- **PPR（Partial Prerendering）との組み合わせが主流:** Next.js 15+のPPRにより、静的シェルを即座に配信しつつ動的部分だけをストリームする構成が実用化。CDNキャッシュの効果を保ちながらパーソナライズドコンテンツを遅延配信できる。

- **ストリーミングとキャッシュの衝突に注意:** `fetch()`のキャッシュ設定（`no-store` vs `force-cache`）がストリーミングのタイミングと干渉するバグが頻出。RSCでデータフェッチする際はキャッシュ戦略を明示的に宣言し、暗黙の挙動に依存しないこと。

- **エラー境界のネストがUX品質を決める:** ストリーミング中にデータ取得が失敗した場合、`error.tsx`の配置が粗いと画面全体がエラー表示になる。クリティカルパスとオプショナルコンテンツを`ErrorBoundary`で分離し、部分的な失敗をグレースフルに扱う設計が必須。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの主流化:** 2026年現在、Next.js + TypeScriptスタックではtRPCがデファクトに近い存在となり、型安全なエンドツーエンド開発がボイラープレートなしで実現できるため、スタートアップでの採用率が急増している。

- **GraphQLの役割の再定義:** GraphQLはBFF（Backend for Frontend）や複雑なデータグラフを持つ大規模サービスに特化し、単純なCRUDには過剰という認識が定着。Federationによるマイクロサービス統合での優位性は依然として高い。

- **REST + OpenAPI の堅牢な地位:** 外部公開APIや他社連携では依然としてRESTが標準。OpenAPI 3.1 + Zodによる型生成（`zod-to-openapi`等）でスキーマファーストな開発が容易になり、RESTの生産性が向上している。

- **RPC over HTTPの台頭:** Connect-RPC（gRPCのHTTP/1.1互換実装）がブラウザ対応を実現し、内部マイクロサービス間通信でgRPCの実用的な代替として注目されている。

- **API設計の判断軸:** 「誰が呼ぶか」で選択する時代。内部フルスタック→tRPC、内部サービス間→Connect-RPC/gRPC、外部公開→REST+OpenAPI、複雑なグラフ→GraphQL、という分担が2026年の実践的なベストプラクティスとなっている。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジのデファクト標準に:** Cloudflare Workers・Fastly Compute@Edgeを中心に、WasmによるポータブルなエッジランタイムがNode.js系を置き換えつつある。コールドスタートがマイクロ秒レベルになり、レイテンシSLAが従来比10倍厳しくなっている。

- **AI推論のエッジオフロードが本格化:** LLMの軽量化（Llama系の量子化モデル等）とNPU搭載エッジノードの普及により、プライバシー要件の高い推論処理をエッジで完結させるアーキテクチャが現実的な選択肢になった。

- **Durable ObjectsとSQLite-at-Edgeによるステートフル化:** 従来「エッジはステートレス」が前提だったが、Cloudflare Durable Objects・Turso（libSQL）等によりエッジでの永続化が可能に。設計上の複雑性は増すため、どこまでエッジに持つかの判断が重要。

- **エッジのオブザーバビリティが最大の運用課題:** 数百リージョンに分散するトレース・ログの集約はコスト・遅延ともに難しく、OpenTelemetryのエッジ対応とサンプリング戦略の設計が運用品質を左右する。

- **ベンダーロックインへの逆張りとしてWinterCG準拠が重視:** Cloudflare・Deno・Vercel等がWinterCG（Web互換ランタイム仕様）に準拠し始め、ポータビリティを担保した設計が評価されている。特定プロバイダー依存のAPIは技術的負債になるリスクを認識した上で採用判断すること。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の標準化:** 2026年現在、パスワードレス認証はもはやオプションではなく標準。主要プラットフォームのパスキー対応が揃い、フィッシング耐性のある認証をUXコストなしに実装できる。

- **セッション管理のゼロトラスト化:** JWTの長期トークン依存から脱却し、短命トークン（15分）＋リフレッシュトークンローテーションが必須。リフレッシュトークンの再利用検知（Refresh Token Rotation + Reuse Detection）を組み合わせることでトークン漏洩時の被害を最小化できる。

- **デバイスバインディングの普及:** セッションをデバイス固有の暗号鍵に紐づけることでセッションハイジャックを防止。ブラウザのPrivate State Token APIやデバイス証明書の活用が現実的な選択肢になっている。

- **継続的認証（Continuous Authentication）:** ログイン時点の認証だけでなく、行動バイオメトリクスや異常検知をセッション中に継続適用するアプローチが金融・エンタープライズ領域で主流化。高リスク操作には再認証を挿入するStep-up Authも標準パターン。

- **OAuth/OIDCのセキュリティ強化（PKCE必須・DPoP導入）:** Authorization Code FlowへのPKCE適用はすでに必須。さらにDPoP（Demonstrating Proof of Possession）によりアクセストークンをクライアントの秘密鍵に束縛し、トークン盗難後の悪用を防ぐ実装が推奨される。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のEdge Runtime対応成熟:** Prisma Client がVercel Edge・Cloudflare Workers上でネイティブ動作し、Supabase の接続プーリング（PgBouncer / Supavisor）と組み合わせることでサーバーレス環境でのコネクション枯渇問題がほぼ解消された。

- **Supabase Realtime + RLSの主流化:** Row Level Security をデータ層の認可境界として扱い、アプリ側で認可ロジックを重複実装しないパターンが定着。Prisma の `$executeRaw` でRLSポリシーをテストするCI構成が推奨される。

- **Prisma Migrate vs. Supabase Migrations の競合リスク:** 両ツールが同一スキーマを管理しようとすると競合が起きる。2026年のベストプラクティスは「Prisma をスキーマの唯一の真実源とし、Supabase CLI の migration は読み取り専用で生成のみ」に統一すること。

- **Vector / pgvector との統合:** Supabase がpgvectorをファーストクラスサポートしたことで、RAGパイプラインのベクトルストアをPostgresに集約できる。Prisma の `Unsupported` 型経由でvectorカラムを扱う回避策は依然必要だが、型安全ラッパーライブラリが普及している。

- **接続アーキテクチャの選択基準:** 長命プロセス（Next.js App Router サーバーコンポーネント等）は Prisma 直接接続、短命プロセス（Edge Functions）は Supabase JS Client 経由が原則。混在するとコネクションプール設定のチューニングが複雑になるため、アーキテクチャ初期に境界を明確化すべき。

### 7. WebAssembly Rust performance 2026

- **Component Modelの成熟:** WASIp2とWasm Component Modelが2026年に実用段階に達し、RustコンポーネントをJS/Pythonランタイムとゼロコピーで相互運用できるようになった。マイクロサービス間のバインディング自動生成が実運用で使えるレベルになっている。

- **SIMD・スレッド最適化の普及:** Wasm SIMDとShared Memoryが主要ブラウザ・ランタイムで安定し、Rustの`rayon`相当の並列処理がWasm上でも機能する。画像処理・ML推論の計算集約タスクでネイティブ比90%以上の性能が出るケースが増えた。

- **バイナリサイズの劇的な改善:** `wasm-opt`とRustコンパイラのWasm向け最適化が進み、`panic`ランタイムを切ればシンプルなクレートは50KB以下が現実的。`no_std`＋`wee_alloc`廃止→`talc`等の軽量アロケータ採用が新定番になっている。

- **Wasmtime/WasmEdgeのサーバーサイド採用加速:** エッジランタイム（Cloudflare Workers、Fastly Compute）でRust+Wasmのコールドスタートが1ms以下に到達し、Dockerコンテナの代替として本番投入する企業が増加。起動速度と隔離性の両立がユースケースを広げている。

- **デバッグ・プロファイリング環境の整備:** DWARF対応の改善によりChrome DevTools・wasm-pack経由でRustのスタックトレースが実用的に読めるようになった。`cargo-component`がビルドパイプラインを統一しており、onboardingコストが大幅に下がっている。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点でApp Routerの主流はRSC（React Server Components）をデフォルトとし、`'use client'`を境界として最小化する設計。クライアントバンドルサイズの削減が直接パフォーマンスに直結する。

- **Partial Prerendering（PPR）の実用化:** Next.js 15以降でPPRが安定し、静的シェル＋動的ストリーミングの組み合わせが標準パターンに。`<Suspense>`境界の設計がアーキテクチャの核心になった。

- **Server Actions でAPI Routeを置き換える:** フォーム送信・ミューテーション処理はServer Actionsが主流となり、`/api`エンドポイントは外部公開APIのみに限定するのがベストプラクティス。型安全性とコロケーションが向上する。

- **キャッシュ戦略の明示化:** `fetch`の`cache`オプションや`revalidate`タグを意識的に設計しないとパフォーマンスが不安定になる。Next.js 15以降はデフォルトがno-cacheに変わったため、既存コードの移行時に注意が必要。

- **Turbopackへの移行完了:** 2026年時点でTurbopackがデフォルトビルダーとして安定。`next dev --turbo`から単純に`next dev`へ移行済みのプロジェクトが多く、ローカル開発のHMR速度が大幅に改善されている。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択最適化:** 2026年現在、VercelはNode.js RuntimeとEdge Runtimeの選択をより明示的に設計することが重要。Edge Runtimeはコールドスタートが数ms単位だが、Node.js APIの制限があるため、認証・リダイレクト・A/Bテスト用途に限定するのがベストプラクティス。

- **Fluid Compute活用によるコスト削減:** Vercelの「Fluid Compute」モデル（サーバーレス＋長寿命インスタンスのハイブリッド）を活用し、リクエスト間でメモリをシェアすることでDBコネクションの再利用が可能になり、コネクションプール管理コストが大幅削減できる。

- **Regional Edge Cachingの戦略的設計:** `Cache-Control`ヘッダーと`stale-while-revalidate`を組み合わせ、Edge側でのキャッシュヒット率を最大化する。特にNext.js App RouterのISRとEdge Middlewareを組み合わせたパターンが2026年の主流アーキテクチャ。

- **Middleware実行コストの最小化:** Edge Middlewareは全リクエストで実行されるため、重い処理（DB参照・外部API呼び出し）を入れると遅延が蓄積する。`matcher`設定で対象パスを限定し、KV（Vercel KV）を活用してセッション検証を軽量化することが必須。

- **Web Vitalsへの直接影響把握:** Edge Functionsの最適化はTTFB（Time to First Byte）に直結し、Core Web VitalsのLCP改善に寄与する。Vercel Analyticsで地域別のEdgeレイテンシを継続的にモニタリングし、ボトルネックを特定するループを開発プロセスに組み込むべき。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなブランド型がドメイン境界での型安全性を強化しており、プリミティブ型の誤用をコンパイル時に防ぐパターンが標準化されつつある。

- **Template Literal Types の実践活用:** APIルートやイベント名をテンプレートリテラル型で表現することで、文字列ベースのインターフェースにも型推論が効き、typoによるバグをゼロにできる。

- **satisfies 演算子の定着:** TypeScript 4.9以降の `satisfies` が型チェックと型推論の両立を実現し、`as const` との組み合わせで設定オブジェクトの型安全性が格段に向上している。

- **Zod + tRPC によるランタイム境界の型統一:** スキーマ定義から型を導出するパターン（`z.infer<typeof schema>`）がフロントエンド・バックエンド間の型共有の事実上の標準となり、型の重複定義が排除できる。

- **Exact Types / NoUncheckedIndexedAccess の有効化:** `noUncheckedIndexedAccess` を `tsconfig.json` で有効にすることで配列・オブジェクトアクセスの undefined 安全性が保証され、ランタイムエラーの主要原因を静的に排除できる。
