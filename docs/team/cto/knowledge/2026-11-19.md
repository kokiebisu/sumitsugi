# CTO Knowledge - 2026-11-19

## Daily Update (2026-11-19)

### 1. Next.js performance optimization 2026

- **部分プリレンダリング（PPR）の標準化:** Next.js 16ではPartial Prerenderingが安定版となり、静的シェルと動的コンテンツを1つのルートで組み合わせられるため、初期表示速度（TTFB/LCP）を落とさずに動的機能を追加できる。

- **Turbopackのデフォルト化とビルド高速化:** `bun run build`時のコンパイル速度が大幅に向上し、開発時のHMRもほぼ即時反映になるため、CI時間短縮と開発者体験の両方に直結する。

- **React Server Components前提のデータフェッチ戦略:** クライアントバンドルサイズを削減するため、`src/lib/data.ts`のようなデータ取得ロジックは可能な限りServer Component側に留め、`'use client'`境界を最小化することが引き続き重要。

- **キャッシュ戦略の明示化（`use cache`ディレクティブ）:** Next.js 16で導入された`use cache`により、物件一覧や検索結果などの再利用可能なデータを関数単位で明示的にキャッシュでき、無駄な再計算やDBアクセスを削減できる。

- **画像・フォント最適化の継続的徹底:** `next/image`と`next/font`の活用はAirbnb風UIでの物件写真表示において依然必須で、特にモバイルでのCLS（レイアウトシフト）対策がLCP改善に直結する。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 15〜16でPPRが安定版に移行し、静的シェルを即時配信しつつ動的部分だけストリーミングする構成がデフォルト化。初期表示速度（TTFB/LCP）とパーソナライゼーションを両立できる。

- **Suspense境界の粒度設計がパフォーマンスの肝:** `loading.tsx`やネストした`<Suspense>`の分割単位を細かくしすぎるとウォーターフォールが発生し、粗すぎると体感速度が落ちる。データ取得の依存関係をツリー構造で可視化してから境界を決めるのが実用的。

- **React Compilerとの併用でメモ化コストが低減:** React CompilerがクライアントComponentの再レンダリングを自動最適化するため、RSCでサーバー処理を減らしつつクライアント側の`useMemo`/`useCallback`の手動チューニングが不要になり、開発速度が上がる。

- **キャッシュ戦略（`use cache`ディレクティブ）との統合が必須:** ストリーミングで動的データを配信する場合でも、`use cache`で再利用可能な部分を明示しないとサーバー負荷が増大する。本番運用ではCDNエッジキャッシュとRSCペイロードキャッシュの境界設計が重要。

- **エラーバウンダリとストリーミングの相性に注意:** ストリーム中に例外が発生すると、すでに送信済みのHTMLチャンクとの整合性が崩れやすい。`error.tsx`をSuspense境界と1対1で設計し、部分的失敗がUX全体を壊さないようにするのが本番運用上のベストプラクティス。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはTypeScriptフルスタック構成（Next.js + 単一リポジトリ）で型安全性とコード生成コストゼロを両立でき、sumitsugiのような小規模チームには開発速度の面で非常に有利。ただしクライアントが別言語・別リポジトリになる将来の拡張（モバイルアプリ、外部パートナー連携）には不向き。

- **ポイント2:** GraphQLは「前の住人の物件情報」「次の住人の引越し費用見積もり」など関連エンティティを一括取得する複雑なクエリに強いが、スキーマ運用・N+1問題対策・キャッシュ戦略の学習コストが高く、MVPフェーズのチーム規模では過剰投資になりやすい。

- **ポイント3:** REST + OpenAPI(Zodから自動生成)は外部連携（決済・本人確認・行政API等）との相性が最も良く、法務確認後のベータローンチでパートナー企業とAPI連携する場合は標準化されたRESTが交渉・ドキュメント化コストを下げる。

- **ポイント4:** 2026年のトレンドとして「BFF(Backend for Frontend)パターン + 内部tRPC/外部REST」のハイブリッド構成が主流化しており、Next.jsのApp Router内部はtRPCまたはServer Actionsで型安全に、外部公開APIはREST/OpenAPIで分離する設計が実務的な落とし所。

- **ポイント5:** 現フェーズ(MVP完了・ローンチ準備)では新規API基盤への投資より、既存のdraft/public等のステータス管理やデータ検証(Zod境界チェック)の堅牢化を優先すべきで、API方式の大規模変更はベータローンチ後の負荷状況を見てから判断するのが妥当。

### 4. serverless edge computing 2026

- **ポイント1（エッジ推論の標準化）:** 2026年はLLM推論がCDNエッジ（Cloudflare Workers AI、Vercel Edge Functions等）に標準搭載され、Next.js 16のEdge Runtimeと組み合わせることでTTFBを大幅短縮できる。sumitsugiのような物件検索・AI要約機能では、ユーザー地理に近いエッジでの軽量推論が効果的。

- **ポイント2（コールドスタート問題の実質解消）:** V8 isolateベースの実行環境が主流化し、コールドスタートはミリ秒単位まで縮小。従来Lambdaで課題だった認証・DB接続のレイテンシ問題が緩和され、Server Actionsを多用する現在のアーキテクチャをエッジ移行しやすくなっている。

- **ポイント3（DBとエッジの統合）:** Turso/PlanetScale等のエッジ対応DBが普及し、Postgres互換のレプリカをリージョンごとに自動配置する構成が一般化。現状のデータ層をエッジ前提で設計すれば、将来的なグローバル展開（多言語対応含む）に備えやすい。

- **ポイント4（コスト構造の変化）:** 従量課金がさらに細分化され、リクエスト単位でなく実行時間×メモリのミリ秒課金が主流に。MVPフェーズのsumitsugiにとっては、トラフィックが小さい間は固定サーバーより圧倒的に低コストで運用できる。

- **ポイント5（運用の落とし穴）:** エッジ環境はNode.js API非互換が多く、認証ライブラリや画像処理系で動かないケースが依然発生する。本格移行前に`auth-context.tsx`やAPI Routesの依存ライブラリがEdge Runtime対応かを事前検証すべき。

### 5. authentication security best practices 2026

- **パスキー/FIDO2が標準に:** パスワードレス認証(WebAuthn/Passkeys)が主要ブラウザ・デバイスで標準化され、フィッシング耐性の高い認証手段として2026年時点では新規実装のデフォルトになっている。sumitsugiのようなtoCサービスでも、SMS OTPより先にパスキー導入を優先すべき。

- **セッション管理とトークンの短命化:** JWTやセッショントークンは有効期限を短く設定し、リフレッシュトークンのローテーション・無効化リストを必須にするのがベストプラクティス。盗難トークンの再利用を防ぐため、デバイスフィンガープリントと組み合わせた異常検知も推奨される。

- **ゼロトラスト前提のバックエンド検証:** フロントエンドでの権限チェックだけでなく、APIレベル・DBクエリレベルでの認可（RLS/行レベルセキュリティ）を徹底し、クライアントを信用しない設計が標準。物件の`draft`/`public`ステータスのような機微情報は、サーバー側で必ず再検証する。

- **多要素認証の文脈適応(Adaptive MFA):** 全ログインで一律MFAを要求するのではなく、リスクスコア（新デバイス・新IP・不審な挙動）に応じて追加認証を動的に要求する方式が主流化。ユーザー体験とセキュリティのバランスを取れる。

- **サプライチェーン/依存ライブラリの認証周りの脆弱性管理:** 認証ライブラリ（NextAuth/Auth.jsなど）のCVE監視と迅速なアップデートが重要視されており、`bun audit`やDependabotのようなツールでの継続的スキャンが2026年のベストプラクティスとして定着している。

### 6. database architecture Prisma Supabase 2026

- **型安全性とスキーマ駆動開発:** Prismaは2026年時点でもTypeScript向けORMの定番で、スキーマファイルから型を自動生成するためフロントエンド〜APIまでエンドツーエンドの型安全性を確保できる。sumitsugiのような小規模チームではランタイムエラーを減らし開発速度を保つ上で有効。

- **SupabaseのPostgreSQL基盤 + RLS:** Supabaseは単なるBaaSではなく「マネージドPostgreSQL」として捉えるべきで、Row Level Security (RLS) をDBレイヤーで直接適用することでアプリケーション側の認可ロジックを薄くできる。物件データ（`draft`/`public`）のようなステータス制御はRLSポリシーで表現すると漏洩リスクが下がる。

- **PrismaとSupabaseの接続方式（Pooling）に注意:** Supabaseはサーバーレス環境を想定したPgBouncer経由のコネクションプーリングを提供しており、Prismaから接続する際は`DATABASE_URL`とは別に`DIRECT_URL`（マイグレーション用）を分けて設定するのが2025年以降のベストプラクティス。Next.js 16のサーバーアクション/Edge Runtimeを使う場合、プール枯渇に注意が必要。

- **マイグレーション運用:** `prisma migrate deploy`をCI/CDパイプラインに組み込み、本番適用前にステージング環境で検証する運用が標準化している。union型（例: `status: 'draft' | 'public'`）を変更する際はPrismaスキーマとDB制約（CHECK制約やenum）を両方更新し、コードベース全体をgrepして整合性を確認すべき。

- **Realtime/Edge Functionsの活用余地:** Supabase RealtimeやEdge Functionsを使えば、物件公開時の通知やインテリア利用料（引越し費用）計算などのビジネスロジックをDB層に近づけて実行できるが、sumitsugiの現フェーズ（ローンチ準備）では過剰な複雑化を避け、まずはPrisma + 標準APIルートでMVPを安定させる方が優先度は高い。

### 7. WebAssembly Rust performance 2026

- **コンパイル時最適化の進化:** Rustの`wasm-opt`やLLVMバックエンドの改善により、2026年ではWasmバイナリサイズがさらに縮小し、コールドスタート時間がネイティブJSに近づいている。組み込みでSSR/エッジ環境に展開する際はバンドルサイズのKPIを明確に設定すべき。

- **WASI 0.3とコンポーネントモデルの普及:** WASI Preview 2/コンポーネントモデルが実用段階に入り、Rust製Wasmモジュールの言語間相互運用（Component Model経由）が現実的になった。マイクロサービス的にWasmモジュールを組み合わせる設計がアーキテクチャ選択肢として検討可能。

- **SIMDとマルチスレッド対応の標準化:** Wasm SIMD・スレッド（SharedArrayBuffer経由）がブラウザ全体で安定サポートされ、画像処理・物理演算などCPU負荷の高い処理をRust+Wasmに委譲する価値が上がっている。パフォーマンスクリティカルな機能（例: 物件写真の画像処理）で検討候補になる。

- **ネイティブとの性能差は縮小も、FFIオーバーヘッドが残課題:** 計算自体はネイティブの85-95%程度まで近づいたが、JS↔Wasm間のデータ受け渡し（文字列・オブジェクト）コストは依然ボトルネック。頻繁に小さなデータをやり取りする設計は避け、バッチ処理的なAPI設計が推奨される。

- **Next.js/Edge Runtimeとの統合が本格化:** Cloudflare WorkersやVercel Edge RuntimeでのWasm実行が成熟し、RustロジックをEdge Functionとして配置するパターンが増加。本プロジェクト（Next.js 16）では、PDF生成や画像変換など重い処理をRust+Wasmのエッジ関数に切り出す選択肢が現実的になってきている。

### 8. Next.js App Router patterns 2026

- **Server Components first:** デフォルトでServer Componentsを使い、`'use client'`は本当にインタラクティブな部分のみに限定する。バンドルサイズとTTIが改善し、データフェッチもサーバー側に閉じ込められるため、APIレイヤーの設計がシンプルになる。

- **Partial Prerendering (PPR) の実用化:** 静的シェルを即時配信しつつ動的部分だけSuspenseでストリーミングする構成が標準化してきている。物件一覧のような「ほぼ静的だが一部動的」なページ（在庫状況など）に特に有効。

- **キャッシュ戦略の明示化:** `fetch`のデフォルトキャッシュ挙動が変わり続けているため、`cache: 'force-cache'`や`revalidate`を意図的に指定する運用が必須。暗黙のキャッシュに依存すると本番で挙動が変わるリスクが高い。

- **Route Handlersとserver actionsの責務分離:** フォーム送信・ミューテーションはServer Actionsに寄せ、外部連携や複雑なAPIロジックはRoute Handlersに分離する設計が定着。認証・決済など副作用の大きい処理は型安全なServer Actions + Zodバリデーションの組み合わせが事実上の標準。

- **並列データフェッチとウォーターフォール対策:** `Promise.all`やPPRのSuspense境界を使い、ネストしたレイアウト間でのフェッチのウォーターフォールを避ける設計が重要視されている。レイアウト単位でのデータ依存を可視化し、早期にクリティカルパスを洗い出すレビューが有効。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約を前提にした設計:** Vercel Edge FunctionsはNode.js APIではなくWeb標準API（Fetch, Streams等)上で動くため、重い依存ライブラリやNode専用モジュール（fs, crypto一部等）を使うコードはEdgeでは動作しない。本プロジェクトでNext.js 16のApp Routerを使う場合、認証ミドルウェアなど軽量処理のみをEdgeに置き、DB接続やファイルI/Oを伴う処理はNode.js runtimeに残す判断が重要。

- **Cold Start最小化とリージョン配置:** 2026年のトレンドとして、Edge Functionsはリクエスト発生地点に最も近いリージョンで実行されるため、コールドスタートがほぼゼロに近い。ただし日本（東京）ユーザーが多いsumitsugiのようなサービスでは、`regions`設定や`geo`情報を使った明示的なルーティング最適化が引き続き有効。

- **Streaming SSRとの組み合わせ:** Next.js 16のPartial Prerendering (PPR) とEdge Functionsを組み合わせることで、物件一覧ページなど静的部分を即時配信しつつ、動的な価格・在庫情報だけをEdgeでストリーミング挿入できる。これにより初期表示速度（LCP）を大きく改善できる。

- **キャッシュ戦略の高度化:** Vercel Data CacheとEdge Config（KVストア）を使い、物件ステータス（`draft`/`public`）のような頻繁に読むが更新頻度の低いデータをEdge上でキャッシュすることで、DBラウンドトリップを削減できる。ただしキャッシュ無効化のタイミング設計を誤ると公開/非公開の切り替えが反映されない事故に繋がるため、revalidateのロジックは厳密にテストすべき。

- **コスト管理の可視化:** Edge Functionsは実行時間課金ではなく呼び出し回数・CPU時間ベースの課金モデルが主流になってきており、トラフィックが伸びた際の予期せぬコスト増を防ぐため、モニタリング（Vercel Analytics等）を早期から組み込み、しきい値アラートを設定しておくことを推奨する。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x系で`satisfies`演算子と const type parameters(`const T`)が定着し、型推論の精度を保ちながら過剰な型注釈を減らすパターンが主流になっている。
- **ポイント2:** Zodなどのスキーマライブラリによる「スキーマファースト」設計が標準化し、APIバウンダリでランタイム検証とコンパイル時型を単一ソースから生成する手法が広がっている（本プロジェクトのZod活用方針と合致）。
- **ポイント3:** Branded types / nominal typingパターンでID文字列やステータス値の取り違えを型レベルで防ぐ手法が、union型を多用する業務ロジック（例: `'draft' | 'public'`）で特に有効。
- **ポイント4:** `tsc --noEmit`に加えてarktype/typiaなど高速な型検証ツールをCIに組み込み、ビルド時間を抑えつつ型安全性を担保する構成が増えている。
- **ポイント5:** AIコード生成が普及する中で、型定義を「仕様書」として扱い、生成コードの正しさをコンパイラに検証させる"型による自動レビュー"がベストプラクティスとして重視されている。
