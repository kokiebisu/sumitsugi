# CTO Knowledge - 2026-03-08

## Daily Update (2026-03-08)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するためにRSCをデフォルトとし、インタラクティビティが必要な部分のみ`'use client'`を適用する設計が2026年の標準となっている。

- **Partial Prerendering (PPR) の本番導入:** Next.js 15以降で安定化したPPRにより、静的シェルを即時配信しながら動的コンテンツをストリーミングする手法が主流に。TTFBとCLSの両立が実現できる。

- **`use cache` APIによる細粒度キャッシュ制御:** 従来の`fetch`オプションベースのキャッシュから、関数・コンポーネント単位で`use cache`ディレクティブを付与する方式に移行。キャッシュ境界が明示的になり、意図しないキャッシュバグが減少する。

- **Turbopackの完全移行:** `next dev --turbopack`がデフォルト化し、大規模コードベースでのHMRが従来比5〜10倍高速化。CI/CDのビルド時間削減にも寄与しており、esbuild/webpackからの脱却が加速している。

- **Edge Runtimeとサーバーレスの使い分け戦略:** グローバルレイテンシが重要なAPIはEdge Runtime、複雑なビジネスロジックはNode.js Runtimeと使い分けることでコストとパフォーマンスを最適化。特にDBコネクション管理の観点でのRuntime選択がクリティカルになっている。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化が鍵:** 2026年時点では、RSCストリーミングの実運用でSuspense境界を細かく設定しすぎるとウォーターフォールが逆に増加するケースが報告されており、コンポーネント粒度の設計がTTFBとLCPに直結する。

- **PPR（Partial Pre-Rendering）との組み合わせが主流:** Next.js 15+でのPPRとRSCストリーミングの併用により、静的シェルを即時配信しつつ動的データを段階的にストリームするパターンが本番採用の標準になりつつある。

- **サーバーコンポーネントのデータフェッチ並列化:** `Promise.all`でのデータ並列取得とSuspense境界の組み合わせが推奨パターン。シリアルフェッチを放置するとストリーミングの恩恵がほぼ消えるため、コードレビューで必ずチェックすべき。

- **クライアントバンドルサイズへの間接効果:** RSCによりサードパーティライブラリをサーバー側に閉じ込めることでJS転送量を削減できるが、`"use client"`の境界設計ミスで巨大なライブラリがクライアントに漏れるアンチパターンが依然多い。バンドルアナライザーによる定期監視が必須。

- **エラーハンドリングの複雑性増加:** ストリーミング中のエラーは従来のSSRと挙動が異なり、部分的なUIがクライアントに届いた後に失敗するケースがある。`error.tsx`とSuspenseの組み合わせによる境界設計を事前に標準化しておかないと、本番障害時のデバッグコストが高くなる。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの実用的優位性:** 2026年現在、TypeScriptフルスタック環境ではtRPCが事実上の標準に近づいており、型安全性をエンドツーエンドで担保しながらボイラープレートを大幅削減できる。Next.js + tRPC + Prismaのスタックは特にスタートアップで支配的。

- **GraphQLの適用範囲の明確化:** GraphQLは「複雑なクエリが必要なパブリックAPI」や「複数クライアント対応」に特化するケースが増え、内部APIへの乱用は減少傾向。Relay/Apolloのオーバーヘッドを嫌い、シンプルなユースケースではRESTまたはtRPCへの回帰が見られる。

- **REST + OpenAPI 3.1の再評価:** AI・LLMツールチェーンとの相性からOpenAPIスキーマ駆動開発が再注目。`zod-openapi`や`hono`など型安全なREST実装ライブラリが成熟し、外部公開APIではRESTが依然として最適解。

- **エッジランタイム対応が設計制約に:** Cloudflare Workers・Vercel Edge等の普及により、APIアーキテクチャ選定時にコールドスタートレイテンシとバンドルサイズが重要な制約となった。tRPCとHonoはエッジ対応が良好で、GraphQLの重厚な実装は不利。

- **Server Actionsによる境界の溶解:** Next.js App RouterのServer Actionsが普及し、「APIエンドポイントを設計する」という概念自体が内部ユースケースでは希薄化。ただしAPIをサードパーティ公開する場合は依然としてREST/tRPCの明示設計が必要で、用途による使い分けリテラシーが求められる。

### 4. serverless edge computing 2026

- **ポイント1:** WebAssembly（Wasm）がエッジランタイムの標準に：Cloudflare Workers・Fastly Compute@Edgeが本格的にWasmを採用し、言語非依存でコールドスタートほぼゼロを実現。Next.js/Remixのエッジミドルウェアも恩恵を受けている。

- **ポイント2:** AI推論のエッジオフロードが加速：LLMの小型化（SLM）により、画像認識・パーソナライゼーション・コンテンツモデレーションをエッジで完結。レイテンシとプライバシー要件を同時に満たせる。

- **ポイント3:** エッジ×データベースの成熟：Turso（libSQL）・Neon・D1がエッジリードレプリカを提供し、「エッジでDBに触れない」問題が解消。ただしWrite一貫性のトレードオフ設計は依然として重要。

- **ポイント4:** オブザーバビリティの課題が顕在化：分散エッジ環境でのトレーシングはOpenTelemetryベースのツールが整備途上。Baselime（Cloudflare買収）など専用ソリューションを選定しないと本番デバッグが困難。

- **ポイント5:** コスト管理の再評価：リクエスト課金モデルはトラフィックスパイクに強い一方、常時接続・WebSocket系ユースケースはDurable Objects等の新プリミティブを使わないとコストが跳ね上がる。アーキテクチャ選定時にトラフィックパターンの分析が必須。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）への移行加速:** 2026年現在、主要プラットフォームのパスキー対応が成熟し、SMS OTPやTOTPより強固なフィッシング耐性を持つパスキーをデフォルト認証手段として採用すべき段階に入った。

- **ゼロトラスト + 継続的認証の標準化:** 「一度ログインすれば安全」の時代は終わり、セッション中もリスクスコアを継続評価（デバイス状態・位置情報・行動パターン）し、異常検知時に再認証を要求するアーキテクチャが必須となっている。

- **AIを活用したクレデンシャルスタッフィング対策:** 漏洩パスワードリストを使った自動攻撃がより高度化しており、Have I Been Pwned連携に加え、ボット行動パターンをMLで検出するWAFレイヤーの導入が実質的な標準になっている。

- **トークン設計の見直し（短命JWTとリフレッシュローテーション）:** アクセストークンのTTLを5〜15分に短縮し、リフレッシュトークンのローテーション（使用済みトークンの即時無効化）を徹底することで、トークン漏洩時の被害半径を最小化する。

- **サプライチェーンリスクとしての認証ライブラリ管理:** 認証・認可ライブラリへのサプライチェーン攻撃が増加しており、依存パッケージの固定（lockfile厳守）・SBOM生成・Renovatebotによる自動セキュリティアップデートをCI/CDに組み込むことが重要。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x の Edge Runtime 対応:** Prisma は 2025〜2026 年にかけて Cloudflare Workers / Vercel Edge での動作が安定し、`@prisma/adapter-pg` を介した接続プーリング（PgBouncer/Supabase Pooler）との組み合わせが実質的な標準パターンになっている。コネクション枯渇問題はほぼ解決済みだが、`pgBouncer=true` の URL パラメータ設定は依然として必須。

- **Supabase の Row Level Security (RLS) と Prisma の共存戦略:** RLS をデータ層のセキュリティ境界として活用し、Prisma はデータアクセス抽象化に徹する設計が主流。`set_config('app.user_id', ...)` を Prisma の `$executeRaw` で設定するパターンが定着しており、アプリ層での権限チェック重複を排除できる。

- **Supabase Realtime × Prisma の役割分担:** リアルタイム更新は Supabase の Realtime チャネルに委ね、書き込み・複雑なクエリは Prisma ORM に任せるアーキテクチャが効率的。Prisma で書いたデータが Supabase Realtime でブロードキャストされる組み合わせは、Next.js App Router の Server Actions との相性も良い。

- **Prisma Accelerate によるグローバルキャッシュ層:** Prisma Accelerate（旧 Data Proxy）のエッジキャッシュ機能により、Supabase の地理的に単一なデータベースへのレイテンシを補完できる。TTL ベースのクエリキャッシュを `cacheStrategy` で設定するだけで実装でき、Read-heavy なシナリオでは劇的なパフォーマンス改善が見込める。

- **型安全マイグレーションの運用成熟:** `prisma migrate diff` と CI/CD の組み合わせによるスキーマドリフト検出が標準化。Supabase の `supabase db push` との使い分け（開発時は Prisma migrate、Supabase Dashboard 変更の取り込みは `prisma db pull`）を明確にしないと、本番スキーマの不整合リスクが高まる点に注意が必要。

### 7. WebAssembly Rust performance 2026

- **WASM GC（ガベージコレクション）の成熟:** Chrome・Firefox・SafariでWasm GCが標準サポートされ、RustのARC不要な軽量メモリ管理が可能になり、バイナリサイズが最大40%削減できるケースも出てきた。

- **WASI Preview 2（Component Model）の普及:** Rustで書いたWasmコンポーネントがサーバー・エッジ・ブラウザ間でポータブルに動作し、Cloudflare Workers・Fastly Compute等のエッジランタイムでのRust採用が加速している。

- **SIMD & スレッド並列化の実用化:** WebAssembly SIMDとShared Memoryが主要ブラウザで安定稼働し、Rustのrayon等を使った並列処理がブラウザ内でも動作し、画像処理・暗号化などのCPU集約タスクでネイティブ比90%超の性能を達成できる。

- **`wasm-bindgen` / `wasm-pack` エコシステムの成熟:** Rust↔JS間のバインディング自動生成が洗練され、TypeScript型定義も自動出力されるため、フロントエンドチームとの統合コストが大幅に低下している。

- **バイナリサイズ最適化の標準化:** `wasm-opt`（Binaryen）+ LTO + `panic=abort` の組み合わせが定番となり、50〜100KB以下の本番用Wasmモジュールが現実的になった。特にNext.js等のバンドラとの統合プラグインが充実してきた。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点でApp Routerの主流パターンは「サーバーコンポーネントファースト」。`'use client'`は状態・イベントハンドラが必要な末端コンポーネントのみに限定し、バンドルサイズを最小化する。

- **Partial Prerendering（PPR）の本番活用:** Next.js 15以降でStableになったPPRにより、静的シェルと動的ストリーミングを同一ルートで共存できる。`Suspense`境界の設計がパフォーマンスの鍵。

- **`use cache` / `cacheLife` APIへの移行:** `fetch`キャッシュオプションに依存する旧パターンから、`use cache`ディレクティブと`cacheLife`/`cacheTag`による明示的なキャッシュ制御へ。細粒度の無効化が容易になった。

- **Server Actions によるデータ変更の統一:** API Routeを経由せず、Server Actionsで直接DBを操作するパターンが定着。`useActionState`・`useOptimistic`との組み合わせでクライアント状態管理が大幅に簡素化される。

- **Turbopackがデフォルトビルダーに:** `next dev --turbopack`がデフォルト化し、開発サーバーの起動・HMRが従来比で大幅高速化。大規模プロジェクトでは特に差が顕著なため、早期移行を推奨する。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの成熟:** 2026年時点でVercel Edge Functionsは`Node.js`互換APIが大幅に拡充され、従来の制約（fs, net等の非対応）が解消されつつある。移行コストが下がりエッジ採用が加速している。

- **Fluid Computeとの統合:** VercelのFluid Compute（サーバーレスとエッジの中間モデル）により、コールドスタートを最小化しつつグローバル分散を実現。`export const runtime = 'edge'`だけで恩恵を得られるが、DB接続はPrisma Accelerateなどエッジ対応レイヤーが必須。

- **Streaming ResponseとAI統合:** `ReadableStream` / Vercel AI SDKのストリーミングがエッジで安定動作するようになり、LLMレスポンスのTTFBを劇的に改善できる。Next.jsの`app/`ルートとの組み合わせが最もパフォーマンスを発揮する。

- **地域ピニングとデータ主権:** GDPRやデータローカライゼーション要件に対応するため、`export const preferredRegion = ['hnd1', 'sin1']`で実行リージョンを明示制御するパターンが標準化。日本向けサービスでは`hnd1`（東京）固定が実質必須。

- **コスト最適化の落とし穴:** エッジ関数はリクエスト単価が安い一方、キャッシュ戦略（`Cache-Control` + `stale-while-revalidate`）を怠ると呼び出し回数が膨れ上がる。ISRとエッジの境界設計をアーキテクチャ初期に決めることが重要。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の`satisfies`演算子が2026年の標準パターンとして定着。型推論を維持しつつ型チェックを強制できるため、`as`キャストによる型安全性の損失を回避できる。

- **Template Literal Typesによる文字列型安全:** APIルートやイベント名などを`type Route = \`/api/${string}\``のようにテンプレートリテラル型で表現することで、実行時エラーをコンパイル時に検出。特にNext.js App Routerとの組み合わせで威力を発揮する。

- **Branded Types（Nominal Typing）の普及:** `type UserId = string & { readonly _brand: 'UserId' }`パターンが広く採用され、同じプリミティブ型でも意味的に異なる値の混在バグを防止。決済・認証系コードで特に重要。

- **`const` type parametersとInferred tuple types:** TypeScript 5.xで導入された`<const T>`によって、配列リテラルや設定オブジェクトの型推論が大幅に精密化。ランタイムオーバーヘッドゼロで型安全なビルダーパターンが実装可能になった。

- **Zod + `z.infer<>`によるスキーマ駆動型定義:** APIバウンダリでZodスキーマを「真実の源」とし、`type T = z.infer<typeof schema>`でTypeScript型を自動導出するパターンが事実上の標準に。型定義と検証ロジックの二重管理を排除し、当プロジェクトでも既に採用している。
