# CTO Knowledge - 2026-11-26

## Daily Update (2026-11-26)

### 1. Next.js performance optimization 2026

**ポイント1: Partial Prerendering (PPR) の本格運用:** Next.js 15以降で導入されたPPRが2026年には主流パターンとなり、静的シェルを即時配信しつつ動的部分だけをストリーミングすることで、TTFBとLCPを大幅に改善できる。sumitsugiの物件一覧・詳細ページのような「静的な骨組み＋動的な在庫/価格情報」の構成に特に相性が良い。

**ポイント2: React Server Components とデータフェッチの最適化:** クライアントバンドルを減らすためRSCでのデータ取得を徹底し、`fetch`のキャッシュ戦略（`revalidate`/`tags`）を物件データの更新頻度に合わせて明示的に設計することが重要。曖昧なキャッシュ設定はビルド後の不整合バグの温床になりやすい。

**ポイント3: 画像・フォント最適化の自動化:** `next/image`のAVIF優先配信と`next/font`のセルフホスティングは必須化しつつあり、特に物件写真が多いUIではLCP改善に直結する。CDN側のキャッシュヘッダー設定も合わせて見直すべき。

**ポイント4: Turbopackビルドの標準化:** Next.js 16でTurbopackがデフォルトとなり、開発体験（HMR速度）だけでなく本番ビルド時間も短縮されるため、CI/CDパイプラインの実行時間短縮に直結する。ただし一部のwebpackプラグイン依存機能は移行検証が必要。

**ポイント5: Bundle分析とCore Web Vitalsの継続監視:** `next build`時の自動バンドル分析とLighthouse CIをPRごとに回し、回帰を早期検知する体制が2026年のベストプラクティス。認証やフォームなどユーザー操作が多いページほどINP（Interaction to Next Paint）の劣化に注意が必要。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Prerendering (PPR) の標準化** 静的シェルを即時返しつつ動的部分だけをストリーミングする構成がNext.jsの主流パターンとして定着しており、TTFBとLCPを両立させやすい。既存の`loading.tsx`やSuspense境界の粒度設計次第で効果が大きく変わるため、ページ単位より「データ依存の重いコンポーネント単位」で境界を切るのが実用的。

- **ポイント2: Server Actionsとストリーミングの組み合わせによるUX最適化** フォーム送信後の楽観的UI更新とRSCストリーミングを組み合わせ、`useOptimistic`やトランジション中の部分再レンダリングでネイティブアプリ的な応答性を実現するのが2026年のベストプラクティス。本プロジェクトの物件登録・問い合わせフォームのような多段階フローは特に恩恵が大きい。

- **ポイント3: エッジランタイムでのストリーミング配信コスト最適化** Vercel Edge FunctionsやCloudflare Workersでのストリーミングは、サーバーの滞留時間を短縮できるぶんコスト効率が良いが、Node.js専用ライブラリ（画像処理・PDF生成など）との互換性に注意が必要。引越し費用計算や契約書PDF生成のような重い処理はNode runtimeに残し、表示系のみエッジに寄せる構成が現実的。

- **ポイント4: キャッシュ戦略の複雑化とデバッグコスト** `use cache`ディレクティブやRouter Cacheの世代交代で挙動が変わりやすく、本番で「古いデータが表示される」系の不具合が増える傾向にある。ステータス（`draft`/`public`）の切り替えのような即時反映が必要な箇所は、キャッシュ無効化のタグ付け（`revalidateTag`）を明示的に設計すべき。

- **ポイント5: ストリーミング中のエラーハンドリングとSEOへの影響** ストリーミング中に発生したエラーがクライアント側の`error.tsx`に委譲される挙動は、クローラーが不完全なHTMLを取得するリスクを伴う。公開物件ページのような検索流入が重要な画面では、ストリーミング境界の外側で主要コンテンツ（価格・住所等）を確定させ、SEOクリティカルな情報を遅延させない設計が重要。

### 3. API design REST GraphQL tRPC 2026

- **スキーマファースト設計の標準化:** tRPCのエンドツーエンド型安全性がTypeScriptモノレポのデフォルトになりつつあり、OpenAPI/GraphQLスキーマからのコード生成も含めて「手書きの型定義」は技術的負債とみなされる流れが強まっている。

- **GraphQLの使い分けが明確化:** 複雑なクライアント主導のデータ取得（モバイルアプリ、複数データソース統合）ではGraphQLが有効だが、社内BFFやシンプルなCRUDにはtRPC/RESTの方がオーバーヘッドが少なく、「全部GraphQLで統一」という流行は収束してきている。

- **RESTはAI/LLMエージェント連携との相性で再評価:** OpenAPI仕様がLLMツールコール（Function Calling, MCP）の記述フォーマットとして再利用されており、人間向けAPIとAIエージェント向けAPIを同じスキーマで両立させる設計が重視されている。

- **sumitsugiへの実用的示唆:** 現状のNext.js App Router + Server Actions構成はtRPC的な型安全性を内部通信（フロント⇔BFF）で得られているため、新たに別のAPI層を追加するより、外部連携（決済・不動産データ連携など）が必要になった時点でRESTまたはOpenAPI準拠のエンドポイントを個別追加するのが現実的。

- **パフォーマンス面での注意点:** GraphQLのN+1問題やオーバーフェッチ対策（DataLoader等）は運用コストが高く、MVPフェーズのsumitsugiのようなプロダクトでは、必要になるまで導入を見送り、REST/Server Actionsでシンプルさを優先する判断が合理的。

### 4. serverless edge computing 2026

- **ポイント1: エッジでのLLM推論が本格化** WebAssembly（WASI-NN）とGPU対応エッジノードの普及により、Cloudflare Workers AIやVercel Edge Functionsで軽量LLM推論が実用レベルに。Sumitsugiのようなマッチングロジックもエッジでのリアルタイム推薦に応用可能。

- **ポイント2: コールドスタート問題がほぼ解消** V8 isolateベースの実行環境とプリウォーミング技術の進化で、コールドスタートが1桁ミリ秒まで短縮。Next.js 16のEdge RuntimeもこれによりSSRのレイテンシが大幅改善され、物件検索ページのTTFBに直結。

- **ポイント3: データのローカリティとコンプライアンスが設計の中心に** 個人情報保護法・GDPR対応で「データ処理地域の固定」要件が増加。賃貸契約や本人確認情報を扱うsumitsugiでは、エッジでの処理と中央DBの分離を意識したアーキテクチャが今後必須になる。

- **ポイント4: Edge-first + ISRのハイブリッド戦略が標準化** 静的生成（SSG）をエッジでキャッシュし、動的パーソナライズ部分のみオリジンサーバーやエッジ関数で処理する構成が主流。物件一覧は静的配信、ユーザー固有の「引越し費用」計算のみ動的に行うことでコストとパフォーマンスを両立できる。

- **ポイント5: ベンダーロックイン回避のためOpenNext/標準化レイヤーが台頭** Next.jsをCloudflare/Deno/Fastly等複数エッジプラットフォームで動かす抽象化レイヤー（OpenNext等）が成熟し、特定ベンダー依存を避けた移行性の高い構成が取れるようになった。MVP後のスケール判断を遅らせられるのが利点。

### 5. authentication security best practices 2026

- **パスキー/FIDO2が標準に:** 2026年ではパスワードレス認証（パスキー）がデフォルトの選択肢となり、フィッシング耐性のある公開鍵暗号方式により認証情報の漏洩リスクを根本的に排除できる。実装時はWebAuthnのフォールバックとデバイス紛失時のリカバリーフローを必ず設計する必要がある。

- **多層防御としてのリスクベース認証:** 単純なMFAだけでなく、デバイスフィンガープリント・IPレピュテーション・行動分析を組み合わせたアダプティブ認証が主流になっている。本サービスのような不動産プラットフォームでは、物件情報や個人情報へのアクセス時に段階的な認証強度の調整を検討すべき。

- **トークン管理のゼロトラスト化:** JWTやセッショントークンは短寿命化（アクセストークン15分以下）し、リフレッシュトークンローテーションを必須とする流れが加速している。`src/contexts/auth-context.tsx` のようなクライアント側のトークン保持はhttpOnly Cookie + Secure + SameSite=Strictの徹底が基本線。

- **サプライチェーン経由の認証情報漏洩対策:** npm/依存パッケージ経由の資格情報窃取が増加しており、認証関連コードのサードパーティ依存は最小限にし、CIでのSBOM生成と依存パッケージの署名検証が重要になっている。

- **監査ログとセッション可視化:** 不正アクセス検知のため、ログイン試行・デバイス変更・異常なセッションパターンを本人がダッシュボードで確認できるUI（セキュリティログイン履歴）の提供が、金融・不動産系サービスでは事実上の必須機能になりつつある。

### 6. database architecture Prisma Supabase 2026

- **Prisma脱Rustエンジン化:** Prisma ORMはRustバイナリ依存から段階的に移行し、TypeScript/WASMベースのクエリエンジンへ移行が進んでいる。これによりコールドスタートが改善され、Vercel等のサーバーレス環境でのデプロイサイズ・起動速度が向上するため、本プロジェクトのようなNext.js App Router構成では特に恩恵が大きい。

- **コネクションプーリングが必須設計要素に:** Supabase標準のSupavisor（pgBouncer後継）やPrisma Accelerateを使わないと、サーバーレス関数のスケール時にPostgres接続数が枯渇する。本番運用前に`DATABASE_URL`をプール経由（6543番ポート等）に切り替える設計を今のうちに決めておくべき。

- **RLS（Row Level Security）中心のアクセス制御:** SupabaseはPrismaのORMレベルの権限管理よりもPostgres側のRLSを信頼境界の基本に据える方向が定着している。`seller`/`buyer`等のロール分離がある本プロダクトでは、アプリ層のバリデーションに加えてDB側RLSポリシーを併用する二重防御が推奨される。

- **ブランチ型DB運用の普及:** Supabaseの「Database Branching」機能（PR単位で本番スキーマのクローンを作成）がCI/CDと統合され、マイグレーションの安全性検証がPRレベルで自動化されるのが2026年のデファクト。Beads/Linearタスクのスキーマ変更PRにもこのフローを組み込むと、`bun run build`以外のDBレイヤーの検証が強化できる。

- **Prisma Postgres（マネージドDB）との統合選択肢:** PrismaがSupabaseと競合する自社マネージドPostgres（Prisma Postgres）を提供開始しており、エッジでのレイテンシ最適化が強み。現状Supabaseを選定済みなら移行コストは低いが、将来的なマルチリージョン展開時の比較検討ポイントとして留意しておくとよい。

### 7. WebAssembly Rust performance 2026

- **コンパイル最適化の進化:** Rust 1.80以降のwasm-opt統合とLLVMバックエンド改善により、WASMバイナリサイズとランタイム速度の両方が向上。Component Model標準化でネイティブに近いFFIオーバーヘッド削減が実現。
- **WASI Preview 2の普及:** 非同期I/Oとcomponent-based設計が標準化され、サーバーサイドWASM（Wasmtime, Spin等）でのRust採用が加速。マイクロサービスのコールドスタートがコンテナより1桁速いケースも増加。
- **SIMD/マルチスレッド対応の成熟:** wasm-bindgenとwasm-pack経由でSIMD128とシェアードメモリの実用化が進み、画像処理・暗号化などCPU負荷の高い処理をブラウザ内で高速実行可能に。
- **ツールチェーンの簡素化:** cargo-componentやtrunkの改善でビルド〜デプロイの開発体験がネイティブ開発に近づき、学習コストが大幅に低下。
- **実用上の注意点:** WASM導入はバンドルサイズとJS↔WASM間のシリアライズコストのトレードオフが依然課題。本当にCPU負荷が高い処理（画像/動画処理、暗号化、物理演算など）に限定して適用するのが2026年時点でも最も実用的な戦略。

### 8. Next.js App Router patterns 2026

- **Server Components優先の設計:** App Routerではデフォルトでサーバーコンポーネントを使い、`'use client'`は本当に必要な部分（インタラクティブなUI・hooks利用箇所）のみに限定することで、バンドルサイズとTTFBを最適化できる。

- **Partial Prerendering (PPR) の実用化:** 静的なシェルを即時配信しつつ動的な部分だけをストリーミングするPPRが安定し、ECや物件一覧ページのようにSEOと動的性（在庫・価格変動）を両立する用途で有効になっている。

- **`fetch`キャッシュとRevalidationの明示化:** Next.js 15以降で`fetch`のデフォルトキャッシュ挙動が変わったため、`cache: 'force-cache'`や`revalidate`オプションを明示的に指定する設計が必須になり、意図しないキャッシュ漏れ・過剰取得のバグを防げる。

- **Server Actionsによるフォーム処理の簡素化:** API Routeを介さずServer Actionsで直接ミューテーションを行う構成が主流化し、物件登録・申込フォームのようなフローでクライアント側のコード量とAPIレイヤーの保守コストを削減できる。

- **並列ルート・インターセプトルートの活用:** `@modal`のような並列ルートとインターセプトルートを使い、物件詳細をモーダル表示しつつURLも独立させるパターンが、一覧→詳細のUXで標準的になっている。

### 9. Vercel Edge Functions optimization 2026

## Vercel Edge Functions 最適化 — 2026年の動向

- **ポイント1（ランタイム統合の進化）:** Edge RuntimeとNode.jsランタイムの機能差がほぼ解消され、ミドルウェアだけでなくAPI Routes全体をEdgeで動かす選択がデフォルト寄りになっている。移行判断の基準は「レイテンシ要件」より「依存ライブラリのEdge対応状況」に移っている。

- **ポイント2（Streaming + Partial Prerenderingの組み合わせ）:** Next.js 16のPartial Prerendering（PPR）とEdge Functionsを組み合わせることで、静的シェルを即時配信しつつ動的部分だけEdgeでストリーミングする構成が主流化。sumitsugiの物件一覧・検索結果ページのようなSSR比率が高い画面でTTFB改善の効果が大きい。

- **ポイント3（コールドスタート対策としてのリージョン最適化）:** Edge Functionsはグローバル分散だが、DB接続（Supabase/Postgres等）がリージョン固定の場合はEdge→Originのレイテンシが逆に増えるケースがある。DB接続プーリング（PgBouncer等）をEdge近接リージョンに置くか、読み取り専用クエリのみEdgeに寄せる判断が重要。

- **ポイント4（コスト観点）:** Edge Functions課金はリクエスト数＋実行時間ベースで、重い処理（画像変換・PDF生成など）をEdgeに置くと従来のServerless Functionsより高コストになりやすい。sumitsugiの物件PDF出力機能はNode.jsランタイムに残す判断が妥当。

- **ポイント5（観測性・デバッグ）:** Edge環境はログ・スタックトレースの取得がServerlessより制限されやすいため、`console.log`禁止ルール（本プロジェクトのコーディング規約）と合わせて、構造化ロギング＋Vercelのランタイムログドレインを前提にした設計が必須。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** `satisfies`演算子と const type parameters（TS 5.x以降）の組み合わせが標準化し、型推論を保ったままリテラル型の厳密性を維持できるようになった。Zodスキーマから`z.infer`で型を導出するパターンと組み合わせることで、バリデーションと型定義の二重管理を排除できる。

- **ポイント2:** Branded types（nominal typing）がID誤代入バグ防止の定番パターンとして定着。例えば`type UserId = string & { __brand: 'UserId' }`のようにして、`UserId`と`PropertyId`のような同じ`string`型同士の混同をコンパイル時に検出できる。

- **ポイント3:** Discriminated unionによる状態表現が、本プロジェクトの`'draft' | 'public'`のようなステータス管理で重要性を増している。`switch`文での網羅性チェック（`never`型での exhaustiveness check）を徹底すると、新しいステータス追加時に未対応箇所をビルドエラーで検出できる。

- **ポイント4:** `unknown`型とtype guardの組み合わせがAPI境界（外部データ取得時）のデフォルトになりつつあり、`any`の使用はlintルールで禁止するチームが増えている。これはSystem境界でのZod検証と相性が良く、型安全性とランタイム安全性を同時に担保できる。

- **ポイント5:** モノレポ環境でのProject References活用により、型チェックの差分ビルドが高速化。大規模化するコードベースでは`tsc --build`のインクリメンタルモードが開発体験を大きく左右するため、CI構築時の優先事項になっている。
