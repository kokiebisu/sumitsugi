# CTO Knowledge - 2026-11-10

## Daily Update (2026-11-10)

### 1. Next.js performance optimization 2026

- **ポイント1: Partial Prerendering (PPR) の本格運用** App Routerの静的シェルと動的コンテンツを1つのレスポンスで配信するPPRが安定版に近づき、初回表示速度とSEOを維持したまま個人化コンテンツを扱えるようになっている。物件詳細ページのように静的な建物情報と動的な空室状況が混在するケースに有効。

- **ポイント2: キャッシュ戦略の明示化（`use cache` ディレクティブ）** これまで暗黙的だったfetchキャッシュが廃止され、`use cache`で明示的にキャッシュ境界を宣言する方式に移行。キャッシュミスによる予期しないDBヒットを防ぎやすくなるが、既存コードの移行コストを見積もる必要がある。

- **ポイント3: Turbopackのビルド最適化が標準化** 開発時だけでなく本番ビルドでもTurbopackがデフォルト化しつつあり、ビルド時間が大幅短縮。CI/CDのビルド待ち時間短縮に直結するため、`bun run build`のCI実行コストにも影響する。

- **ポイント4: Server ActionsのN+1問題への対応強化** Server Actions経由のデータ変更が増える中、React CompilerとSuspenseの組み合わせで不要な再フェッチを抑制する最適化が進展。フォームや多段階フローでのパフォーマンス劣化を未然に防げる。

- **ポイント5: 画像・フォントの自動最適化がCore Web Vitalsに直結** `next/image`と`next/font`の最適化精度が上がり、LCP/CLSの改善がデフォルトで得られるようになった。物件写真が多い当プラットフォームでは特に恩恵が大きく、追加実装なしでスコア改善が見込める。

### 2. React Server Components streaming 2026

- **ストリーミングSSRのデフォルト化:** Next.js 16ではPPR（Partial Prerendering）が安定化し、静的シェルを即座に返しつつ動的部分を`Suspense`境界でストリーミングするのが標準パターンになっている。初回表示（TTFB/LCP）の改善に直結するため、`properties/`一覧や`listing/`詳細ページのような「静的な骨組み＋非同期データ」構成に向いている。

- **`use cache`ディレクティブとの併用:** React 19.2以降のキャッシュAPIとRSCストリーミングを組み合わせ、物件データのような頻繁に変わらないフェッチ結果をキャッシュしつつ、ユーザー個別の情報（認証状態など）だけをストリーミングで後追い送信する設計が主流になりつつある。

- **クライアントバンドル削減よりも「体感速度」重視:** RSCの価値はバンドルサイズ削減だけでなく、サーバー側でレンダリングを進めながら段階的にUIを届けられる点にシフトしている。`src/contexts/auth-context.tsx`のようなクライアント状態が必要な部分だけを`'use client'`境界に切り出し、それ以外はサーバーでストリーミングするのが実用的な分離ライン。

- **エラーバウンダリとストリーミングの組み合わせに注意:** ストリーミング中に発生したエラーは、シェル送信後だとステータスコードを変更できない制約がある。決済や認証フローなど重要な処理は、ストリーミングに乗せる前にサーバー側で検証を完了させ、エラー時は非ストリーミングのフォールバック（通常のレスポンス）にするのが安全。

- **テスト・計測の難化:** ストリーミングはE2E（Playwright）での待機条件が複雑になりがち（`waitForSelector`だけでは不十分、ストリーミング完了を示すマーカーが必要）。パフォーマンス計測も「TTFB」だけでなく「各Suspenseチャンクの到着タイミング」を見る必要があり、Lighthouseの単純なスコアだけでは実態を捉えにくい。

### 3. API design REST GraphQL tRPC 2026

- **スキーマファーストの収束:** tRPCやGraphQL CodegenによるEnd-to-Endの型安全性がデファクト化し、OpenAPI/Zodスキーマから型・クライアント・バリデーションを自動生成するフローが主流になっている。手動でAPIドキュメントとコードの整合性を取る作業はほぼ廃れた。

- **BFF層でのtRPC採用加速:** モノレポ（Next.js + TypeScript）構成ではtRPCがREST/GraphQLのオーバーヘッドを排除し、フロント・バック間の型推論がリアルタイムに効くため、sumitsugiのような単一チーム・単一リポ構成に特に適している。ただし外部パートナー向け公開APIにはREST/OpenAPIが依然必須。

- **GraphQLはマルチクライアント・複雑グラフ構造向けに残存:** 複数のモバイル/Web/外部統合が絡む大規模プラットフォームではGraphQLのフィールド選択・N+1対策（DataLoader）が優位だが、学習コストとキャッシュ戦略の複雑さから中小規模プロダクトでは採用が減少傾向。

- **RSC/Server Actionsとの境界の曖昧化:** Next.js App RouterのServer Actionsが「APIレイヤー」の一部を代替し、単純なCRUDはtRPC/RESTを介さずServer Actions直結で実装するケースが増加。外部公開や複雑なバリデーションが必要な箇所のみ明示的なAPI層を設ける設計判断が求められる。

- **API境界でのZod/Valibotバリデーション必須化:** 2026年現在、入力検証はランタイムスキーマ（Zod等）をAPI境界に必ず配置するのが標準プラクティスで、型だけに依存した「コンパイル時は安全だがランタイムは無防備」な実装はセキュリティレビューで即座に指摘される運用が一般化している。

### 4. serverless edge computing 2026

- **WASMランタイムの主流化:** WebAssemblyベースのエッジランタイム（Cloudflare Workers、Fastly Compute等）がコールドスタートをミリ秒未満に抑え、Node.js互換レイヤーも成熟してきたため、重いSSRロジックもエッジに安全に移せるようになった。Next.jsのEdge Runtimeを使う場合は対応APIの制約（fsやnative moduleの非対応）を事前に確認すべき。

- **データレイヤーのエッジ分散:** Turso、PlanetScale、Cloudflare D1など「エッジ対応DB」がリードレプリカをPoP単位で自動配置し、読み取りレイテンシを数十msまで短縮している。書き込みは依然中央集権的なため、強整合性が必要な予約・決済処理は従来通りオリジンDBに残す設計判断が重要。

- **コスト構造の変化:** サーバーレスはリクエスト課金からCPU時間課金への移行が進み、アイドルコストはゼロでも「計算量が多い処理」は従来のVMより割高になるケースが増えている。画像処理やPDF生成のような重い処理は、エッジではなくバッチ/キュー処理に切り出すコスト最適化が有効。

- **観測性（Observability）の難しさ:** 分散PoPで実行されるため従来のAPMツールでは追跡しづらく、OpenTelemetryのエッジ対応トレーシングが2026年の実質的な標準になりつつある。デバッグ困難を避けるため、エッジ関数は薄く・ステートレスに保ち、複雑なビジネスロジックは中央サーバーに残すのが実用的。

- **フレームワーク統合の進化:** Next.js 16のようなフレームワークがPartial Prerenderingとエッジミドルウェアを組み合わせ、「静的配信はエッジ、動的パーソナライズのみサーバーレス関数」というハイブリッド構成がデフォルト化している。sumitsugiのような物件検索UIでは、検索結果の個人化だけをエッジ関数に切り出し、物件データ自体はCDNキャッシュに任せる構成が相性が良い。

### 5. authentication security best practices 2026

- **ポイント1:** パスキー（FIDO2/WebAuthn）がデフォルトの認証手段として定着し、パスワードは「フォールバック」の位置付けに後退している。実装コストが下がったため、新規サービスはパスワードレスを前提に設計すべき。
- **ポイント2:** フィッシング耐性のあるMFA（ハードウェアキー・デバイスバインド型パスキー）への移行が加速し、SMS/OTPベースのMFAは中間者攻撃に弱いとして非推奨化が進んでいる。
- **ポイント3:** セッショントークンの盗難（トークン窃取によるMFAバイパス）が主要な攻撃経路となり、短命トークン＋デバイスフィンガープリンティング＋継続的リスク評価（Continuous Authentication）が標準プラクティスになっている。
- **ポイント4:** AIエージェント自体が認証主体となるケース（エージェント間API呼び出し）が増え、人間向けのOAuthフローとは別に、スコープを限定した短命クレデンシャル（Workload Identity）の設計が重要になっている。
- **ポイント5:** ゼロトラスト原則のもと、認証後も「信頼済み」として扱わず、リクエストごとに権限とコンテキストを再評価する設計（継続的認可）が求められている。

### 6. database architecture Prisma Supabase 2026

- **スキーマ駆動の安全性:** Prisma 6+はTypeScript型推論がさらに強化され、Supabase側のRow Level Security (RLS)ポリシーもスキーマファイルで宣言的に管理できるようになっており、マイグレーション時の型とDB制約のズレを早期に検出できる。

- **Edge対応コネクション管理:** Supabaseのconnection pooler (PgBouncer/Supavisor) とPrismaのEdge-compatibleクライアントの組み合わせが標準化し、Next.js 16のServer ComponentsやEdge Runtimeからの同時接続数問題を気にせずスケールできる。

- **リアルタイム機能の活用:** SupabaseのRealtime機能とPrismaのクエリ層を併用するハイブリッド構成が普及しており、本サービスのような「物件公開ステータス変更の即時反映」のようなUXに向いている。

- **マイグレーション運用の自動化:** `prisma migrate` とSupabaseのブランチング機能（開発用DBブランチ）を組み合わせることで、本番前のステージング検証フローが標準化され、`'draft'|'public'`のようなステータス変更を含むスキーマ変更も安全にロールアウトできる。

- **コスト最適化:** Supabaseの新しい使用量ベース課金とPrisma Accelerate（キャッシュ+コネクションプーリング）を組み合わせることで、MVPローンチ初期の低トラフィック期はコストを抑えつつ、将来のスケールにもシームレスに対応できる構成が主流になっている。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASM GC (Garbage Collection) proposalの実用化が進み、Rust以外の言語（Kotlin、Dart等）とのWasmモジュール間連携が容易になったが、Rustは依然ゼロコスト抽象化とリニアメモリ直接制御の強みでパフォーマンスクリティカルな処理（画像処理、暗号化、物理演算）のデファクトスタンダードであり続けている。

- **ポイント2:** Component Model（WASI Preview 2）の標準化により、異言語間でのWasmコンポーネント合成がブラウザ外（サーバーサイド、エッジ）で実用段階に入り、RustはWITバインディング生成のサポートが最も成熟しているため、マイクロサービスのサンドボックス実行基盤としての採用が増えている。

- **ポイント3:** `wasm32-wasip2`ターゲットの安定化とツールチェーン改善（`cargo component`等）により、ビルド設定の複雑さが大幅に下がり、小規模チームでもWasmモジュールのプロダクション投入コストが現実的になった。

- **ポイント4:** SIMDとマルチスレッド（Shared Memory + Web Workers）のサポートがブラウザ全体で安定し、Rust製Wasmでネイティブ比80-95%程度の性能が達成可能になったが、JS↔Wasm間のFFI境界越え（特に文字列・構造体のシリアライズ）は依然ボトルネックであり、`wasm-bindgen`の呼び出し頻度を減らす設計が重要。

- **ポイント5:** sumitsugiのような物件情報・画像処理を含むWebアプリでは、画像圧縮・PDF生成・類似度計算などCPU負荷の高い処理をRust/Wasmにオフロードすることで、Next.jsのサーバーレス実行時間制限（コールドスタート含む）を回避しつつクライアント/エッジ双方で再利用可能なロジックを維持できる、という設計パターンが2026年の主流になっている。

### 8. Next.js App Router patterns 2026

- **ポイント1:** Server Components をデフォルトとし、Client Components は`'use client'`境界を最小限に留める設計が定着。インタラクティブなUI部分だけを切り出すことで、バンドルサイズと初期表示速度が大幅に改善する。

- **ポイント2:** Partial Prerendering (PPR) の実運用が進み、静的なシェルを即時配信しつつ動的な部分だけをストリーミングする構成が標準パターンになっている。ダッシュボードや一覧ページのような「一部だけ動的」なUIに特に有効。

- **ポイント3:** `fetch`のキャッシュ戦略（`force-cache` / `no-store` / `revalidate`）をルートごとに明示的に設計することが重要で、曖昧なキャッシュ設定がバグの温床になりやすい。データ更新頻度に応じてタグベースの再検証（`revalidateTag`）を使う設計が推奨される。

- **ポイント4:** Server Actionsがフォーム処理の主流になり、APIルートを別途実装せずに`"use server"`関数で完結させるパターンが増えている。ただしミューテーション後のキャッシュ無効化（`revalidatePath`等）を忘れるとUIが古いままになる点に注意。

- **ポイント5:** Route Groups とParallel Routes / Interceptorsを組み合わせたモーダル・多段ナビゲーションパターンが洗練され、物件詳細や予約フローのようなステップ型UXをURL駆動で実装しやすくなっている。本プロジェクトの`listing/`配下のフローにも応用余地がある。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1（コールドスタート最小化）:** Edge Runtimeは軽量なV8 isolateベースのため従来のコールドスタート問題は大幅に改善されているが、依存パッケージを極力減らし、Node.js APIに依存しないコードを書くことで起動時間をさらに短縮できる。バンドルサイズ監視を継続的に行うことが重要。
- **ポイント2（データ取得の地理的最適化）:** Edge Functionsはユーザーに最も近いリージョンで実行されるため、DB/APIへのレイテンシが逆にボトルネックになりやすい。Vercel Edge ConfigやRegional/Read Replicaの活用、またEdge Middlewareでのキャッシュ戦略（`stale-while-revalidate`）を組み合わせることでTTFBを最小化すべき。
- **ポイント3（ISR/PPRとの併用）:** Next.js 16のPartial Prerendering（PPR）とEdge Functionsを組み合わせることで、静的シェルを即時配信しつつ動的部分のみEdgeでレンダリングできる。物件一覧ページのような一覧+動的フィルタUIに特に有効。
- **ポイント4（監視とコスト管理）:** Edge Functionsは実行時間課金のため、無限ループやリトライ処理の監視が必須。Vercelの`Observability`機能でレイテンシ分布とエラー率を常時確認し、異常時はアラート設定することを推奨。
- **ポイント5（認証・セッション処理の配置判断）:** 認証チェックなど軽量なロジックはEdge Middlewareに置き、重い処理（DB書き込みやPDF生成など）はNode.js Runtimeに残すという役割分担が2026年のベストプラクティス。全てをEdgeに寄せるとAPI互換性の問題（一部npmパッケージ非対応）に当たりやすい。

### 10. TypeScript type safety patterns 2026

- **スキーマ駆動の型安全性:** ZodやValibotで実行時検証と型定義を一元化し、`z.infer<>`でコンパイル時の型を自動生成する手法が主流になっている。本プロジェクトのように`'draft' | 'public'`のような状態をZodの`z.enum`で定義すればAPI境界と内部ロジックの型ズレを防げる。

- **`satisfies`演算子の定着:** オブジェクトリテラルの型を明示しつつ推論結果（リテラル型）を保持できるため、設定オブジェクトや定数マップで型の広がり（widening）を防ぎながら安全性を確保する書き方が標準化している。

- **Branded Types（nominal typing）:** `UserId`や`PropertyId`のようなstring/number型を区別するためにブランド型を使うパターンが広がり、IDの取り違えによるバグをコンパイル時に検出できるようになっている。

- **厳格なコンパイラオプションの常態化:** `noUncheckedIndexedAccess`や`exactOptionalPropertyTypes`をデフォルト有効にするプロジェクトが増え、配列アクセスやoptionalプロパティの曖昧さによる実行時エラーを型レベルで排除する流れが加速している。

- **判別可能なUnion型による網羅性チェック:** `switch`文で`never`型チェックを組み合わせ、新しいstatus値やバリアントを追加した際にコンパイルエラーで漏れを検出する「exhaustiveness checking」が、状態遷移の多いUIロジック（物件ステータス管理など）で実用パターンとして定着している。
