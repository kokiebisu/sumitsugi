# CTO Knowledge - 2026-06-15

## Daily Update (2026-06-15)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の活用:** Next.js 15以降で安定したPPRにより、静的シェルを即座に配信しつつ動的コンテンツをストリーミングできる。TTFBを犠牲にせずにパーソナライズを実現する設計が標準になりつつある。

- **React Server Components による JS バンドル削減:** RSCをデフォルトとする設計に移行することで、クライアント送信JSを大幅削減できる。`"use client"` の境界を意識的に管理し、必要最小限のインタラクティブ領域のみをクライアントに委ねる設計が重要。

- **Turbopack の本番投入:** Turbopackが安定版となり、Webpackと比較してコールドスタートで最大10倍の高速化が実現可能。大規模プロジェクトでは開発体験のボトルネックが解消され、CI/CDのビルド時間にも直結する。

- **Edge Runtime の戦略的配置:** ミドルウェアやAPIルートをEdge Runtimeで動かすことで、グローバルユーザーへのレイテンシを削減。ただしNode.js APIとの互換性制約があるため、全面採用ではなく認証・リダイレクト等の軽量処理に限定するのが現実的。

- **`next/image` + `next/font` の徹底活用:** LCP（Largest Contentful Paint）改善に最も即効性がある施策。フォントのCLS（レイアウトシフト）ゼロ化と画像の自動WebP変換・サイズ最適化を見落としているプロジェクトはまだ多く、計測ベースで優先対応する価値が高い。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の実用化:** Next.js 15以降でPPRが安定化し、静的シェルを即座に配信しつつ動的コンテンツをストリームするハイブリッドモデルが標準パターンになった。TTFBを犠牲にせずCLS（レイアウトシフト）も最小化できる。

- **Suspenseの粒度設計がパフォーマンスの鍵:** 単一の大きなSuspense境界より、コンポーネント単位の細粒度配置が推奨される。ウォーターフォールを避けるには `Promise.all` でデータフェッチを並列化しつつ各境界を独立ストリームにするのが定石。

- **React 19の `use()` フックによるデータフェッチの簡素化:** `use(promise)` でServer Component内の非同期データ取得とストリーミングが統合され、`async/await` パターンがクライアント側でも使えるようになった。コード量が大幅に削減される。

- **Server Actionsとオプティミスティック更新の成熟:** `useActionState` / `useOptimistic` とストリーミングの組み合わせで、ミューテーション後のUI更新がより宣言的に記述可能。フォームのプログレッシブエンハンスメントも実用的に。

- **エッジランタイムでのストリーミング最適化:** Cloudflare WorkersやVercel Edgeでの RSC ストリーミングが安定し、グローバルTTFBが大幅改善。ただしNode.js APIへの依存がある場合はエッジ非対応になるため、依存関係の設計段階での意識が必要。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの成熟とフルスタック型安全性の普及:** tRPC v11がNext.js App RouterやReact Server Componentsとシームレスに統合され、型安全なAPI通信がBoilerplate不要で実現できるようになった。特にモノレポ構成のプロジェクトでは、GraphQLに代わる第一選択肢になりつつある。

- **GraphQLの役割の再定義:** 複数クライアント（Web/Mobile/サードパーティ）に対応する公開APIでは依然としてGraphQLが強力だが、内部APIにGraphQLを使うコストが見直され始めた。Federation v2（Apolloなど）によるマイクロサービス統合は有効だが、運用コストを過小評価しないことが重要。

- **RESTの復権と「REST + OpenAPI」の堅牢化:** Hono・Elysia（Bun対応）などの軽量フレームワークとOpenAPI 3.1の組み合わせで、型生成・バリデーション・ドキュメントを自動化できる体制が整った。シンプルなCRUD APIでは依然としてRESTが最もコスト効率が高い。

- **HTTP/3とストリーミングAPIの台頭:** AI機能の組み込みによりSSE（Server-Sent Events）やWebSocketsの需要が急増。Next.js / Vercel AIのストリーミングレスポンスパターンが事実上の標準になりつつあり、API設計段階でストリーミング対応を考慮することが不可欠になった。

- **契約駆動開発（Contract-First）の実践:** API設計をコードより先に定義し（OpenAPIスキーマ・Protobufなど）、フロント・バックエンドが並行開発できる体制が大規模チームでは標準化しつつある。型の自動生成（`openapi-typescript`等）と組み合わせることで、実装のドリフトを防止できる。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジのデファクトランタイムに:** V8 IsolatesからWasmへの移行が加速し、Cloudflare Workers・Fastly Compute等で任意言語のコンパイルが現実的になった。コールドスタートがほぼゼロになりGoやRustのエッジ展開が増加。

- **エッジDB・ステートフル処理の台頭:** Cloudflare D1・Turso等の分散SQLiteやDurable Objectsにより「エッジはステートレス」の前提が崩れた。レイテンシ敏感なread-heavyワークロードはオリジンへのラウンドトリップなしに処理可能。

- **AI推論のエッジオフロード:** LLMの軽量モデル（1〜7B）をエッジで推論するユースケースが急増。Cloudflare AI・Fastly AI Acceleratorなどにより、プライバシー要件の高いデータをオリジンに送らずローカル処理できるアーキテクチャが現実解になった。

- **オブザーバビリティの複雑化が課題:** 数百のPoP（Point of Presence）に分散した実行環境でのトレーシング・ログ集約はまだ成熟途上。OpenTelemetryのエッジ対応が進んでいるが、従来のAPMツールとのギャップを埋めるための追加投資が必要。

- **ベンダーロックインのリスク管理:** Workers/Lambda@Edge/Vercel Edge Runtimeはいずれも独自APIを持ち、WinterCG（Web-interoperable Runtimes Community Group）による標準化が進むも完全互換はまだ先。コアロジックをWeb標準APIに限定し、プラットフォーム依存をアダプター層に閉じ込める設計が重要。

### 5. authentication security best practices 2026

- **パスキー（Passkey）の標準採用:** FIDOアライアンスのパスキーがパスワード認証を実質的に置き換えつつあり、2026年時点では主要プラットフォームすべてで対応済み。新規サービスはパスワードレスをデフォルトに設計すべき。

- **デバイスバウンド認証の重要性:** フィッシング耐性を持つデバイス紐付け認証（WebAuthn/CTAP2）が必須化。セッショントークンを盗んでもデバイスがなければ不正アクセス不可という設計が基本となった。

- **継続的認証（Continuous Authentication）:** ログイン時点の確認だけでなく、行動バイオメトリクスやリスクスコアによるセッション中の継続的な正当性検証が高セキュリティサービスでは標準化。

- **AIを活用した異常検知の統合:** 機械学習ベースの不正ログイン検知が低コストで利用可能になり、IPレピュテーション・デバイスフィンガープリント・行動分析を組み合わせたリスクベース認証をスモールスタートでも導入できる。

- **サプライチェーン攻撃対策としてのOAuthトークン管理:** OIDCプロバイダーやサードパーティ認証ライブラリ経由の攻撃が増加。依存ライブラリの定期的な監査と、トークンの短命化（アクセストークン5〜15分）が防御の要。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6 + Supabase の統合成熟:** Prisma v6でのクエリエンジン刷新（Rust製ドライバ採用）により、Supabase PostgreSQLとの接続パフォーマンスが大幅向上。コネクションプーリング（Supavisor）との組み合わせでサーバーレス環境でのN+1問題やコネクション枯渇が現実的に解決可能になった。

- **Edge Runtimeへの対応が分岐点:** Prisma AccelerateやSupabase Edge Functionsを使ったグローバルキャッシュ＋エッジ実行が実用化。ただしPrismaのフルクライアントはEdge非対応のため、`@prisma/client/edge`や`drizzle-orm`への移行を検討すべき場面も増えている。

- **型安全クエリの競争が激化（Drizzle台頭）:** 2025-2026にかけてDrizzle ORMがPrismaの有力代替として急成長。スキーマをコードファーストで定義しマイグレーション管理も軽量なため、Supabaseとの組み合わせで採用増加中。Prismaは依然エコシステム最大手だが選定理由の再評価が必要。

- **Row Level Security (RLS) とORMの共存が課題:** SupabaseのRLSはPostgreSQL側で堅牢なマルチテナント制御を実現するが、PrismaはRLSポリシーを直接認識しない。`SET LOCAL role`や`set_config`を使ったセッション変数の受け渡しパターンの標準化が2026年のベストプラクティスとして定着しつつある。

- **Supabase Branching × CI/CDでのスキーマ管理:** Supabase Branchingが安定化し、PRごとにDBブランチを自動生成するワークフローが現実的に。Prismaマイグレーションとの組み合わせで「インフラもPRレビュー対象」という開発文化に移行するチームが増えており、本番スキーマの事故リスクを大幅に低減できる。

### 7. WebAssembly Rust performance 2026

- **Component Modelの実用化:** WebAssembly Component Model (wasm-pkg等) が2026年に本格普及し、Rustで書いたWASMモジュールを言語をまたいで型安全に合成できるようになった。マイクロサービス的なWASMコンポジションが現実的な選択肢に。

- **WASI 0.2安定化でサーバーサイドが加速:** WASI Preview 2の安定化により、Rust+WASMがエッジ環境（Cloudflare Workers、Fastly Compute）でネイティブに近いI/Oパフォーマンスを発揮。コールドスタート1ms以下が標準になりつつある。

- **SIMD・スレッドサポートの広がり:** `wasm-simd128`とWebAssembly Threadsが主要ブラウザ・ランタイムで安定化。Rustの`rayon`ベースの並列計算をWASMに移植しやすくなり、画像処理・ML推論で3〜5倍の速度向上事例が増加。

- **バイナリサイズの劇的改善:** `wasm-opt`＋`cargo-component`＋Rustの新しいリンカ（`mold`+LTO）の組み合わせで、本番WASMバイナリが100KB以下に収まるケースが増えた。初回ロード時間がボトルネックになりにくくなっている。

- **`unsafe`なしでネイティブ同等性能:** Rustの所有権モデルとゼロコスト抽象化により、GCなし・メモリ安全でC/C++比95%以上の性能を達成。特に暗号処理・コーデック・パーサー領域でRust+WASMがデファクトスタンダード化している。

### 8. Next.js App Router patterns 2026

- **React Server Components (RSC) の全面採用:** データフェッチをサーバー側に寄せることで、クライアントバンドルを大幅削減できる。`'use client'`は本当に必要な場所（インタラクティブUI）にだけ付けるのが鉄則。

- **Partial Prerendering (PPR) による静的・動的の融合:** ページの静的シェルを事前ビルドしつつ、動的部分だけをストリーミングで差し込む。Edge + PPPの組み合わせでTTFBを劇的に改善できる。

- **Server Actions によるAPI Route削減:** フォーム送信・ミューテーション処理をServer Actionsに集約し、冗長なAPI Routeを排除。`revalidatePath` / `revalidateTag`との連携でキャッシュ制御も一体化できる。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15+で安定化した`use cache`で、関数・コンポーネント単位のキャッシュが可能に。`fetch`のオプション頼みから脱却し、より直感的なキャッシュ設計ができる。

- **並列ルート＋インターセプトルートによるモーダルUX:** `@modal`スロットとインターセプトルートを組み合わせると、URLを持つモーダル（シェアリンク対応）を素直に実装できる。SPAライクなUXとSSR互換性を両立できる点が強み。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge Runtimeでのコールドスタート排除が主流に** — 2026年時点でVercelはEdge FunctionsのV8アイソレートを常時ウォーム状態に維持する最適化を強化しており、従来のServerless Functionsと比較してp99レイテンシが10倍以上改善されている。

- **ポイント2: Node.js互換APIの拡充によりEdge移行コストが激減** — Edge RuntimeでのNode.js組み込みモジュール対応が大幅に拡張され、`crypto`・`stream`・`buffer`等が使用可能になったため、既存コードのEdge移植障壁がほぼ解消された。

- **ポイント3: Fluid ComputeモデルによるEdge/Serverlessの境界消滅** — VercelのFluid Computeは同一関数をEdgeとServerlessの両環境で動的にルーティングし、地理的近接性とコールドスタートコストをランタイムに最適判断するため、手動チューニングが不要になっている。

- **ポイント4: ISRとEdge Middlewareの組み合わせがキャッシュ戦略の最適解** — Incremental Static RegenerationをEdge Middlewareでのパーソナライゼーションと組み合わせることで、静的パフォーマンスと動的コンテンツを両立でき、sumitsugiのような物件一覧ページに直接適用可能。

- **ポイント5: バンドルサイズ制限（4MB）とWasm活用が差別化ポイント** — Edge FunctionsはバンドルサイズがNode.jsより厳しいため、重いライブラリをWasmに置き換えるパターンが台頭しており、画像処理・PDF生成・暗号化処理でパフォーマンスと制約の両立が実現している。

### 10. TypeScript type safety patterns 2026

- **Branded Types の実用化:** `type UserId = string & { readonly _brand: 'UserId' }` のようなブランド型が標準パターンとして定着し、プリミティブ型の混用バグをコンパイル時に防ぐ手法が広く採用されている。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` を使い、型推論を損なわずに型チェックを行うパターンが普及。`const config = { ... } satisfies Config` により、リテラル型を保持しつつ型安全性を確保できる。

- **Template Literal Types による API 型生成:** `type Route = '/users' | '/posts'` のようなテンプレートリテラル型を使い、エンドポイント・イベント名・CSS クラス名などをコード生成なしに型安全にする手法が成熟している。

- **`NoInfer<T>` ユーティリティの活用:** TypeScript 5.4 で追加された `NoInfer` により、ジェネリック関数の型推論を意図的に制御できるようになり、APIデザインの精度が向上した。

- **Zod + `z.infer<>` による Schema-First 設計:** バリデーションスキーマを Single Source of Truth とし、そこから TypeScript 型を派生させる設計が定番化。ランタイムとコンパイル時の型が乖離するリスクを根本から排除できる。
