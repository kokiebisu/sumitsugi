# CTO Knowledge - 2026-06-12

## Daily Update (2026-06-12)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルを最小化するためにデータフェッチロジックをServer Componentsに集約し、`'use client'`境界を葉コンポーネントに限定することでTTI（Time to Interactive）を大幅に削減できる。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降で安定化したPPRにより、静的シェルを即座に配信しながら動的コンテンツをStreamingで注入できる——従来のSSR vs SSGのトレードオフが実質的に消滅した。

- **`@next/bundle-analyzer` + Tree Shakingの定期監査:** サードパーティライブラリの肥大化は依然として最大のパフォーマンスボトルネック。`dynamic()`による遅延ロードとbarrel exportの排除を組み合わせることでバンドルサイズを30-50%削減できるケースが多い。

- **Turbopack移行によるDX改善:** 開発時のHMRがWebpackの10倍以上高速化される。本番ビルドも2026年時点でほぼ安定しており、大規模プロジェクトでのCI時間短縮効果が顕著。

- **`unstable_cache` / `use cache` APIによるきめ細かいキャッシュ制御:** ページ単位のキャッシュから関数単位のキャッシュへ移行し、`revalidateTag()`と組み合わせることでオーバーフェッチを防ぎつつ鮮度を保証できる。

### 2. React Server Components streaming 2026

- **ポイント1:** RSC + Streaming の成熟：Next.js App Router の`Suspense`境界を活用したPPR（Partial Prerendering）が本格普及し、静的シェルを即時配信しながら動的コンテンツを非同期ストリームで差し込むアーキテクチャが標準パターンになった。

- **ポイント2:** Server Actions との統合強化：フォーム送信やミューテーションをサーバー側で完結させつつ、結果を楽観的UIで即座に反映する`useOptimistic`との組み合わせが定着し、クライアント状態管理の必要箇所が大幅に縮小した。

- **ポイント3:** キャッシュ戦略の複雑化への対処：`fetch`キャッシュ・Router Cache・Full Route Cacheの3層構造が整理され、`use cache`ディレクティブ（React 19以降）で宣言的にキャッシュ粒度を制御できるようになり、過去の`revalidatePath`乱用問題が解消されつつある。

- **ポイント4:** バンドルサイズへの直接的効果：重いライブラリ（日付処理・Markdownパーサー等）をServer Componentに移行するだけでクライアントJSが劇的に削減できる点が再評価され、既存コードベースの「Server化リファクタ」がパフォーマンス改善の最優先施策となっている。

- **ポイント5:** エッジランタイムとの相性：Cloudflare Workers / Vercel Edge RuntimeでのRSCストリーミングが安定し、TTFBを100ms以下に抑えるグローバル配信が現実的なコストで実現可能になった。ただしNode.js専用APIへの依存が残るコードは引き続きブロッカーとなる点に注意。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年においてtRPCはNext.js/TypeScriptスタックでのデファクト選択肢となりつつあり、スキーマ定義不要でクライアント・サーバー間のend-to-end型安全性を実現できるため、小〜中規模チームの開発速度を大幅に向上させる。

- **GraphQLの適用範囲の明確化:** GraphQLは「複数クライアントが異なるデータ形状を必要とする」BFF（Backend for Frontend）やパブリックAPIに有効だが、オーバーエンジニアリングになりやすく、単一クライアントの社内APIにはtRPCやREST+OpenAPIの方が費用対効果が高い。

- **REST + OpenAPI 3.1の再評価:** AIコード生成ツールやSDK自動生成との相性が良く、OpenAPI 3.1仕様をソース・オブ・トゥルースとする設計（コードファースト or スキーマファースト）が2026年の標準プラクティスとして復権している。

- **HTTP/3とストリーミングAPIの普及:** Server-Sent Events（SSE）やWebSocketに加え、AI機能の普及でストリーミングレスポンスが必須要件となり、tRPC subscriptionsやGraphQL Subscriptionsの実運用評価が高まっている。

- **APIゲートウェイとエッジでの認証集約:** 認証・レート制限・キャッシュをエッジ（Cloudflare Workers等）に集約し、各APIルートには純粋なビジネスロジックのみを置く分離パターンが、セキュリティと保守性の観点でベストプラクティスとして定着している。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジの標準ランタイムに:** Cloudflare Workers・Fastly Compute@Edgeを筆頭に、WasmがJavaScriptに代わるポータブルなエッジ実行環境として定着しつつある。言語の選択肢が広がり、RustやGoで書いたロジックをコールドスタートなしで動かせる。

- **エッジDBの成熟とデータローカリティの重要性:** Cloudflare D1・Turso（libSQL）・Neon のブランチング機能など、エッジに近いSQLiteベースのDBが実用段階に入った。レイテンシ改善だけでなく、GDPR等のデータ主権要件への対応手段としても注目される。

- **AI推論のエッジシフト:** 軽量LLM（Llama 3系の量子化モデル等）をエッジで動かすユースケースが急増。中央APIへのラウンドトリップを削減し、プライバシー保護と低レイテンシを両立する設計が現実的な選択肢になってきた。

- **オブザーバビリティのギャップが最大の課題:** エッジ環境は実行ノードが数百〜数千に分散するため、従来のAPMツールでは追跡が困難。OpenTelemetryのエッジ対応と分散トレーシングの整備が、本番運用の可否を左右する。

- **マルチエッジ戦略とベンダーロックインリスク:** Cloudflare・Vercel・AWS Lambda@Edgeの間で実行モデルやAPIに差異が残る。WinterCG（Web-interoperable Runtimes Community Group）による標準化が進んでいるが、重要なサービスでは抽象レイヤーを挟む設計判断が必要。

### 5. authentication security best practices 2026

- **パスキー（Passkey）へのシフト加速:** FIDO2/WebAuthn標準のパスキーがパスワード認証を実質的に置き換えつつある。2026年時点でiOS/Android/主要ブラウザ全対応が完了し、新規サービスではパスワードレス設計がデフォルトになっている。

- **MFAの"疲労攻撃"対策が必須:** プッシュ通知MFAへのスパム攻撃（MFA Fatigue）が多発しているため、数値マッチング確認やフィッシング耐性のあるFIDO2キーを採用すべき。SMS/メールOTPは脆弱と見なされ始めている。

- **セッション管理のゼロトラスト化:** 一度認証したセッションを長期間信頼する設計は時代遅れ。デバイス状態・位置情報・行動パターンを継続評価するContinuous Authentication（継続的認証）がエンタープライズ標準になっている。

- **トークン設計の見直し（短命JWTとRefreshトークンローテーション）:** JWTのアクセストークンは15分以内、Refreshトークンは使い捨てローテーション（Refresh Token Rotation）を徹底する。漏洩時の被害半径を最小化するための基本設計として定着した。

- **OAuth 2.1 + DPoP の採用:** Bearer tokenによるトークン窃取リスクに対し、DPoP（Demonstrating Proof of Possession）でトークンをクライアント証明書に紐づける手法が標準化。特にモバイル・SPA環境では必須の対策となっている。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x の Edge Runtime 対応成熟:** Prisma の Accelerate（コネクションプール + グローバルキャッシュ）が Vercel Edge・Cloudflare Workers で本番利用可能になり、Supabase との組み合わせでサーバーレス環境のコールドスタート問題がほぼ解消された。

- **Supabase の RLS × Prisma 統合の課題:** Row Level Security は Supabase のセキュリティ基盤だが、Prisma はデフォルトでサービスロール接続するため RLS をバイパスする。`SET LOCAL role = anon` を Prisma の `$executeRaw` や middleware で明示的に設定するパターンが2026年時点のベストプラクティス。

- **Drizzle ORM の台頭と Prisma の差別化:** 型安全なSQLを書ける Drizzle が軽量・高速で人気上昇中だが、Prisma は schema-first のマイグレーション管理と `prisma studio` の開発体験で優位性を維持。新規プロジェクトではチームのSQL習熟度で選択する。

- **Supabase Realtime + pgvector の活用:** `pgvector` 拡張が Supabase で標準利用可能になり、ベクトル検索と通常のリレーショナルクエリを同一DBで実装できる。RAG パイプラインにおけるマルチDBアーキテクチャの複雑性を排除できる重要なトレンド。

- **マルチテナント設計のスキーマ戦略:** Supabase でのマルチテナントは「RLS によるシングルスキーマ」か「テナント別スキーマ」かの選択が重要で、規模が小さい段階は RLS が運用コスト低だが、テナント数増加時のパフォーマンス劣化に備えたスキーマ分離戦略を初期設計に含めておくべき。

### 7. WebAssembly Rust performance 2026

- **WASI 0.2 / Component Model の成熟:** 2026年時点でWASI Preview 2とComponent Modelが実用段階に入り、RustコンポーネントをJavaScript/Pythonランタイムとコンポーネント単位で合成できるようになった。マイクロサービス境界でのポリグロット統合が現実的な選択肢になっている。

- **WasmGC との差別化:** GC言語（Kotlin/Dart）がWasmGCで参入する中、Rustの強みは「GCなしの予測可能なレイテンシ」。リアルタイム処理・ゲームエンジン・音声DSPなど、p99レイテンシが重要な領域ではRust+Wasmは依然として最有力。

- **SIMD・スレッドの実用化:** WebAssembly SIMDとShared Memoryが主要ブラウザ・Wasmtimeで安定化し、Rustの`packed_simd`/`rayon`ベースのコードがほぼそのままWasmで動くようになった。CPUバウンドな画像処理・ML推論で2-4倍の実測改善が報告されている。

- **Wasmtime/WasmEdge のサーバーサイド最適化:** エッジランタイム（Fastly Compute、Cloudflare Workers）でのコールドスタートが1ms以下に到達。RustのWasmバイナリは起動コストがほぼゼロに近く、Lambdaコンテナより明確に有利なユースケースが確立されつつある。

- **ツールチェーンの成熟とバイナリサイズ問題の解消:** `wasm-opt`（Binaryen）＋`wasm-pack 2.x`の組み合わせで、Rustの標準的なWebビルドは50-150KB程度に収束。以前の「バイナリが大きすぎる」という懸念は実用上ほぼ解決済みで、導入障壁が大幅に低下している。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点では「必要な箇所だけ `'use client'`」が鉄則。データフェッチはServer Componentで完結させ、クライアントバンドルを最小化することでCore Web Vitalsが大幅改善する。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的ストリーミングを同一ルートで混在できるPPRが安定版に。`<Suspense>` 境界の設計がアーキテクチャの核心になり、「全部SSR or 全部SSG」という二択思考は時代遅れ。

- **Server Actions でAPI RouteをReplaceする流れ:** フォーム送信・ミューテーション処理をServer Actionsに集約することで、APIルートのボイラープレートが激減。ただし入力バリデーション（Zod）とCSRF対策は必須で、セキュリティ設計を省略しないこと。

- **`use cache` ディレクティブによる細粒度キャッシュ:** `fetch` レベルではなく関数・コンポーネント単位でキャッシュ戦略を指定できる `use cache` が主流に。`revalidateTag` との組み合わせで、CDNとサーバーキャッシュを統一的に管理できる。

- **Turbopack が本番デフォルトに:** ビルド時間が大幅短縮され、大規模リポジトリでの開発体験が向上。webpack プラグインへの依存がある場合は移行コストを事前に見積もり、CI/CDパイプラインのビルド時間ベンチマークを定期計測する習慣を持つこと。

### 9. Vercel Edge Functions optimization 2026

- **エッジでのキャッシュ戦略の高度化:** `Cache-Control` ヘッダーと `stale-while-revalidate` を組み合わせ、Edge Functionsの実行回数を最小化することが最重要。不必要な動的処理をキャッシュ層に押し込むだけでコスト・レイテンシを大幅削減できる。

- **Cold Start撲滅のためのStreaming活用:** Edge RuntimeはNode.jsランタイムより起動が速いが、`Response.body` のストリーミングを活用することで体感TTFBをさらに改善できる。特にAI応答やSSRページでは必須テクニックになっている。

- **Middleware vs Edge Route Handlerの使い分け徹底:** 認証・リダイレクト・A/Bテストは`middleware.ts`で処理し、データフェッチを伴うロジックはEdge Route Handlerに分離する。Middlewareにビジネスロジックを詰め込むとデバッグ地獄になる。

- **バンドルサイズの1MB制限への対応:** Edge Functionsは依存関係のサイズ制限が厳しく、`date-fns`より`Temporal API`、`lodash`より組み込みメソッドを使うなどランタイム最適化が差別化ポイントになっている。`@vercel/edge` のtree-shakingも必ず確認。

- **Fluid Compute移行でコールドスタートコストを逆転させる:** 2025年後半から一般化したFluid Computeモデルでは、リクエスト間でインスタンスを再利用できるため、従来のEdge Functionsのステートレス制約が緩和。頻繁に呼ばれるエンドポイントはむしろFluidの方が安くなるケースが増えており、ワークロード特性に応じた選択が重要。

### 10. TypeScript type safety patterns 2026

- **Satisfies演算子の標準化:** `satisfies`演算子が広く普及し、型推論を維持しながら型検証を行うパターンが定着。`as`キャストを排除してランタイムエラーを大幅に削減できる。

- **Template Literal Typesによる文字列DSL:** APIルートやイベント名をテンプレートリテラル型で厳密に定義するパターンが成熟。`\`/api/${ResourceName}/${Action}\``のような型定義でtypoをコンパイル時に検出できる。

- **Branded Types（名義型）の実用化:** `type UserId = string & { readonly _brand: 'UserId' }`パターンで構造的型付けの限界を補完。IDの取り違えなどドメインレベルのバグをゼロコストで防止できる。

- **const型パラメータとinferの組み合わせ:** `const`型パラメータ（TypeScript 5.0+）とconditional typesを組み合わせたライブラリ設計が標準化。Zodなどのバリデーションライブラリとの統合でランタイム型とコンパイル時型の乖離が解消される。

- **Exactオプショナル型（`--exactOptionalPropertyTypes`）:** 厳格モードの一環として`undefined`と「プロパティ未存在」を明確に区別する設定が本番採用増加。既存コードベースへの段階的導入が推奨されており、nullabilityバグの根本解決につながる。
