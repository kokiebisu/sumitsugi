# CTO Knowledge - 2026-07-13

## Daily Update (2026-07-13)

### 1. Next.js performance optimization 2026

- **React Compiler の標準採用:** React 19対応のCompilerがNext.js 16で安定版となり、`useMemo`/`useCallback`の手動最適化がほぼ不要に。ビルド時の自動メモ化で再レンダリングコストを大幅削減できるため、既存コンポーネントのメモ化コードは順次撤去すべき。

- **Partial Prerendering (PPR) のデフォルト化:** 静的シェルを即座に配信しつつ動的部分だけSuspenseでストリーミングする方式が標準構成に。物件一覧ページのような「基本レイアウトは静的、価格・空室状況は動的」なページ構成に特に有効。

- **Turbopackへの完全移行:** `next dev`だけでなく`next build`もTurbopackがデフォルトとなり、ビルド時間が大幅短縮。CI上の`bun run build`実行時間短縮に直結し、PRごとのフィードバックループが速くなる。

- **Server Actionsのキャッシュ制御強化:** `use cache`ディレクティブがStable化し、DB問い合わせを含むServer Componentの粒度別キャッシュが容易に。物件詳細ページなど読み取り頻度の高いデータ取得で活用余地が大きい。

- **画像・フォントの自動最適化の進化:** `next/image`がAVIF優先配信とLCP計測ベースの優先度自動判定に対応。物件写真中心のUIではLCP改善に直結するため、既存の`priority`指定を見直す価値がある。

### 2. React Server Components streaming 2026

**ポイント1:** Next.js 16では`loading.tsx`とSuspenseバウンダリの粒度設計がパフォーマンスの鍵になっており、ページ単位ではなくコンポーネント単位でストリーミング境界を切ることで、TTFB（Time to First Byte）を維持しつつ重いデータフェッチ部分だけを遅延表示できる。

**ポイント2:** Partial Prerendering（PPR）が実質標準化し、静的シェルを即座に返しつつ動的部分だけをストリーミングする構成が一般化している。sumitsugiのような物件一覧・詳細ページでは、静的なレイアウト＋動的な在庫状況/価格をPPRで分離することでLCPを大幅改善できる。

**ポイント3:** RSCペイロードのシリアライズコストがボトルネックになりやすく、`use cache`ディレクティブとの併用でサーバー側キャッシュ層を明示的に制御する設計が重要。特に「前の住人」情報のような更新頻度の低いデータはキャッシュ、価格や空室状況のような動的データのみストリーミング対象にする使い分けが推奨される。

**ポイント4:** クライアントバンドルサイズの削減効果が定着し、'use client'境界を最小化する設計レビューがコードレビューの標準項目になっている。フォームや認証まわり（引越し費用の決済フローなど）は依然クライアントコンポーネントが必要だが、表示のみのUIはServer Componentのままに保つべき。

**ポイント5:** エラーバウンダリとストリーミングの組み合わせで、部分的な失敗（例：外部API連携の物件情報取得エラー）がページ全体をブロックしないUXが実装しやすくなっており、`error.tsx`をSuspenseの粒度に合わせて配置する設計パターンが浸透している。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはNext.jsのようなTypeScriptフルスタック構成で採用が拡大しており、スキーマ定義とクライアント生成の手間を省ける。sumitsugiのようなBun/Next.js 16構成では、社内API（前の住人↔次の住人のマッチング処理など）にtRPCを採用すると型安全性を維持しつつ開発速度を上げられる。

- **ポイント2:** GraphQLは複雑な関係性データ（物件・ユーザー・引き継ぎ履歴など）を持つプロダクトで依然強いが、N+1問題やキャッシュ戦略の複雑さがコストになる。MVPフェーズでは無理にGraphQLを導入せず、RESTかtRPCでシンプルに保つ方が保守性が高い。

- **ポイント3:** RESTは外部連携（決済、外部弁護士向け書類生成システムなど）や公開APIでは依然デファクトスタンダード。sumitsugiのように今後外部パートナー（不動産会社等）との連携APIを想定する場合、内部はtRPC、外部公開はRESTという使い分けが現実的。

- **ポイント4:** 2026年のトレンドとして、OpenAPI仕様からのコード生成やZodスキーマ駆動のAPI設計（Zod→OpenAPI→クライアント自動生成）が主流化しており、標準化されているZodバリデーション（`standards.md`のInput validation要件）をAPI境界の型定義にも一貫して使うことで、フロントエンド・バックエンド間の型ズレを防げる。

- **ポイント5:** エッジランタイム（Vercel Edge, Cloudflare Workers）でのAPI実行が一般化しており、レイテンシ重視の物件検索・フィルタリングAPIはエッジ配置を検討する価値がある。ただし認証・決済など機密性の高い処理は引き続きNode.jsランタイムに残すべき。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG仕様準拠のエッジランタイム（Cloudflare Workers, Vercel Edge, Deno Deploy）が実質的なデファクトスタンダードとなり、Node.js固有APIへの依存を避けることでベンダーロックインを回避しやすくなっている。sumitsugiのようなNext.js 16構成では、ミドルウェアやAPI Routeの一部をエッジ互換に保つ設計判断が移植性を高める。

- **コールドスタート問題のほぼ解消:** V8 isolateベースの実行モデルとプリウォーミングにより、エッジ関数のコールドスタートはミリ秒単位まで縮小し、SSRやAPI Routeをエッジで動かす選択肢が現実的になった。物件検索や認証チェックなど低レイテンシが求められる処理はエッジ配置の優先候補になる。

- **データレイヤーのエッジ対応が鍵:** エッジ実行の恩恵はDB接続がボトルネックにならない場合に限られるため、エッジ対応DB（PlanetScale, Turso, Neon等）やキャッシュ層（KV, Durable Objects）との組み合わせが前提になりつつある。従来型のコネクションプール型DBをエッジから直接叩く構成は避けるべき。

- **観測性とデバッグの複雑化:** 分散したエッジロケーションでの実行はログ・トレーシングの集約が難しく、OpenTelemetry対応やエッジ専用APMツールの導入が2026年のベストプラクティスとして定着している。障害発生時の切り分けコストを考慮し、導入は段階的に（まずキャッシュ・静的配信から）進めるのが現実的。

- **コスト構造の変化:** リクエスト数課金からCPU時間課金への移行が進み、重い計算処理をエッジに置くとコストが跳ね上がるケースがある。認証・リダイレクト・A/Bテストなど軽量処理はエッジ、レポート生成やPDF出力（sumitsugiの引き継ぎ資料生成など）のような重い処理はオリジンサーバーに残す使い分けが実用的。

### 5. authentication security best practices 2026

- **ポイント1:** パスキー（FIDO2/WebAuthn）がパスワードレス認証の主流になりつつあり、フィッシング耐性とUX向上を両立できる。sumitsugiのようなtoC向けサービスでは、初期実装コストよりも離脱率低下のメリットが大きい。

- **ポイント2:** JWTの検証漏れ（署名アルゴリズムのnone攻撃、有効期限未検証）が依然として頻出する脆弱性であり、リフレッシュトークンはHttpOnly+Secure Cookieで管理し、アクセストークンの短寿命化（15分程度）とローテーションを徹底すべき。

- **ポイント3:** Zero Trust的な発想で、認証後も継続的にセッションの正当性を検証する（デバイスフィンガープリンティング、異常ログイン検知）実装が標準になってきている。物件情報や個人情報を扱うsumitsugiでは特に重要。

- **ポイント4:** レート制限とアカウントロックアウトだけでなく、CAPTCHA疲れを避けるためbot検知（行動分析ベース）とMFA（TOTP/SMS依存を減らしプッシュ通知型に）の組み合わせが推奨される。

- **ポイント5:** Supabase AuthやNextAuth.js（Auth.js）などのマネージドソリューションを使う場合も、RLS（Row Level Security）ポリシーの設定漏れが実質的な認可バグの温床になるため、認証と認可を分けてレビューする必要がある。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORM の型安全性と Edge 対応:** Prisma 6系はNext.js 16のEdge Runtimeとの親和性が向上しており、Server Actions内でのDB操作もエンドツーエンドで型安全に書ける。ただしEdgeではPrisma Accelerate等のコネクションプーリング層が実質必須になる点に注意。

- **Supabase のコネクションプーリング戦略:** サーバーレス環境（Vercel等）からの直接接続はコネクション枯渇を招きやすいため、Supavisor（Supabaseのプーラー）をtransactionモードで使い、マイグレーション実行時のみdirect connectionに切り替える設計が定石になっている。

- **RLS (Row Level Security) とPrismaの併用:** SupabaseのRLSはDB層でのアクセス制御に強いが、Prisma Client経由のクエリはデフォルトでservice roleを使うことが多くRLSをバイパスしがちなので、認証済みユーザーコンテキストを`auth.uid()`に渡す設計（PrismaのRLS拡張やSupabase JS Client併用）を最初から組み込む必要がある。

- **マイグレーション運用の一本化:** Prisma MigrateとSupabase CLIのマイグレーションを両方使うと状態がズレるトラブルが多発するため、どちらか一方（推奨はPrisma Migrateに統一しSupabaseはDB/Auth/Storageインフラとしてのみ利用）に決めてCI上で一貫させるべき。

- **物件データのようなJSONBカラム活用:** sumitsugiの物件情報（間取り・設備リスト等）は将来的にスキーマが増減しやすいため、コアなフィールドはリレーショナルに正規化しつつ、可変性の高い属性はSupabaseのJSONBカラム＋Prismaの`Json`型で持つハイブリッド設計がスケーラビリティと開発速度のバランスが良い。

### 7. WebAssembly Rust performance 2026

## CTO視点: WebAssembly × Rust パフォーマンス 2026

- **Component Model標準化の実用化:** WASI Preview 2とComponent Modelが本番運用レベルに達し、Rustで書いたWASMモジュールを言語非依存で組み合わせられるようになった。マイクロサービス的な粒度でWASMコンポーネントを再利用する設計が現実的な選択肢になっている。

- **SIMD・マルチスレッドの一般化:** `wasm32-unknown-unknown`ターゲットでのSIMD128とスレッド(shared memory)がbrowser/edge runtimeで広くサポートされ、Rustの`std::simd`やrayon的な並列処理をWASM上でもネイティブに近い速度で実行できる。画像処理や暗号化処理などCPUバウンドな処理をクライアント側にオフロードする判断がしやすくなった。

- **バイナリサイズ最適化がボトルネックに:** 実行速度自体はネイティブの80-95%程度まで近づいたが、実務上のボトルネックは初回ロード時間とバイナリサイズ。`wasm-opt`、`wee_alloc`代替の`talc`、LTO+`opt-level="z"`の組み合わせが標準的なチューニングセットになっている。

- **エッジコンピューティングでのRust+WASM採用拡大:** Cloudflare Workers、Fastly Compute、Vercel Edge FunctionsなどでRust+WASMがコールドスタート性能の優位性からデファクトになりつつある。sumitsugiのような物件検索・フィルタリングのような計算負荷の高いエッジ処理があれば検討価値あり。

- **wasmtime/wasmerのAOTコンパイル進化:** サーバーサイドではJITではなくAOT(事前コンパイル)キャッシュが主流になり、起動レイテンシがミリ秒未満まで縮小。CIパイプラインでのプリコンパイル運用がベストプラクティス化している。

### 8. Next.js App Router patterns 2026

- **Server Components + Actionsの標準化:** Server ActionsがCRUD処理の主流パターンとして定着し、APIルートを介さないデータ変更が一般化。フォーム送信・楽観的更新も`useActionState`と組み合わせるのが定番になっている。

- **Partial Prerendering (PPR) の本格採用:** 静的シェルを即座に返しつつ動的部分を`Suspense`でストリーミングする構成が主流化し、TTFBとインタラクティブ性を両立できる。sumitsugiのような物件一覧・詳細ページでは、静的なレイアウトと動的な在庫状況を分離する設計が有効。

- **キャッシュ戦略の明示化:** `fetch`のデフォルトキャッシュ挙動が変化してきたことで、`cacheLife`/`cacheTag`など明示的なキャッシュ制御APIを使い、意図しない古いデータ表示を防ぐ設計が必須になっている。

- **クライアント境界の最小化:** `'use client'`境界をできるだけ末端コンポーネントに絞り、フォームやモーダルなど本当にインタラクティブな部分だけをクライアント化するのがベストプラクティスとして浸透。バンドルサイズ削減に直結する。

- **型安全なルーティング:** App Routerのファイルベースルーティングに対し、`next typegen`的な型付きリンク・パラメータ検証がエコシステムで普及し、`/properties/[id]`のような動的ルートでの実行時エラーを型チェック段階で検出できるようになってきている。

### 9. Vercel Edge Functions optimization 2026

**ポイント1:** Edge RuntimeでのNode.js API互換性が大幅に拡大し、`fs`や一部のネイティブモジュール以外はほぼフル機能で動作するようになったため、Edge/Serverlessの使い分けを「互換性」ではなく「レイテンシ要件」だけで判断できるようになっている。

**ポイント2:** ISR（Incremental Static Regeneration）とEdge Functionsの組み合わせによるstale-while-revalidateパターンが標準化され、物件詳細ページのような高頻度アクセス・低頻度更新コンテンツはEdge Cache + On-demand Revalidationで実質ゼロレイテンシに近づけられる。

**ポイント3:** Edge Middlewareの実行コスト（CPU時間課金）がより厳格化される傾向にあるため、認証チェックのようなmiddlewareロジックは「早期リターンの徹底」と「不要なfetch呼び出しの排除」が引き続き重要——弊社の`auth-context`周りのミドルウェアも定期的にプロファイリングすべき。

**ポイント4:** Edge Config（KVベースの低レイテンシ設定ストア）を使ったフィーチャーフラグ・A/Bテストの配信が一般化しており、`site-config.ts`のような静的設定の一部を動的化したい場合、ビルド再デプロイ不要で切り替えられる利点が大きい。

**ポイント5:** リージョン選択の自動最適化（Smart Placement）が進化し、Edge FunctionとDB/APIの物理的距離を考慮した自動配置が可能になったため、日本国内ユーザー中心のsumitsugiのようなサービスでは`fra1`/`hnd1`等の明示的リージョン指定より自動配置に任せる方がパフォーマンスが安定するケースが増えている。

### 10. TypeScript type safety patterns 2026

- **ポイント1（`satisfies` 演算子の定着）:** 型注釈で変数の型を狭めてしまう問題を避けつつリテラル型推論を保持できる `satisfies` が標準的な書き方として定着し、`site-config.ts` のような設定オブジェクトの型安全性を型注釈より正確に担保できます。

- **ポイント2（Zodなどによるランタイム検証とスキーマ駆動の型生成）:** `z.infer` でスキーマから型を生成する手法が主流化し、コンパイル時の型とランタイムのバリデーションが二重管理にならずに一致します。本プロジェクトでも入力境界（フォーム、API）で標準化する価値があります。

- **ポイント3（Discriminated Unionによる状態の網羅性チェック）:** `'draft' | 'public'` のようなステータス型は、switch文で `never` 型チェックを使うことでケース漏れをコンパイル時に検出でき、新しいステータス追加時の実装漏れ（`.claude/rules/standards.md` が指摘するunion型の全箇所grep問題）を型システム側で機械的に防げます。

- **ポイント4（テンプレートリテラル型・ブランド型の実用化）:** IDやパス文字列など「意味的に異なるstring」をブランド型（`type UserId = string & { __brand: 'UserId' }`）で区別する手法がライブラリ非依存で書けるようになり、取り違えバグを型レベルで防止します。

- **ポイント5（`tsc --noEmit` のCI必須化とビルド駆動の型安全性）:** ESLintやユニットテストだけでは型エラーを検出しきれないため、CIパイプラインに `bun run build` を必ず含めることが2026年のベストプラクティスとして広く合意されています。本プロジェクトの `workflow.md` でも既に同様の方針（ビルド検証必須）を採用しており、業界標準と一致しています。
