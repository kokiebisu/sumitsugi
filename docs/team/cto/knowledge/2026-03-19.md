# CTO Knowledge - 2026-03-19

## Daily Update (2026-03-19)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを劇的に削減できるRSCをデフォルト戦略とし、`"use client"`は状態・インタラクション必須のコンポーネントのみに限定する。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15+で安定化したPPRにより、静的シェルを即時配信しつつ動的コンテンツをストリーミングする「ハイブリッド戦略」が標準化——ISR vs SSRの二択思考は時代遅れ。

- **`use cache` APIによるきめ細かいキャッシュ制御:** App Routerの新しい`use cache`ディレクティブで、ルートレベルではなく関数・コンポーネント単位でキャッシュ戦略を定義できる。TTLと依存関係を明示的に管理することでCache Poisoningリスクも低減。

- **Turbopackへの移行とビルド時間の最適化:** Turbopackが本番ビルドでも実用段階に入り、大規模プロジェクトでwebpack比3〜5倍の高速化が見込める。`next.config`で`bundler: 'turbopack'`に切り替えるだけだが、カスタムwebpackプラグインとの互換性を事前検証すること。

- **Core Web Vitals（INP）への対応:** 2024年にCLS・LCPに加えてINP（Interaction to Next Paint）が正式指標化され、重いイベントハンドラの`startTransition`化・`useOptimistic`によるUI即時更新が必須テクニックに。Lighthouseだけでなくフィールドデータ（CrUX）でのモニタリングを組み込む。

### 2. React Server Components streaming 2026

- **Suspense境界の細粒度化が主流に:** 2026年時点では、ページ単位ではなくコンポーネント単位でSuspense境界を設計するのがベストプラクティスとなり、TTFBを維持しつつCLSを最小化できる。

- **PPR（Partial Pre-Rendering）との統合:** Next.js 15+のPPRにより、静的シェルを即時配信しつつ動的ストリームを注入するハイブリッド戦略が実用段階に達し、Vercel以外のエッジ環境でも安定稼働している。

- **サーバーアクションとストリーミングの融合:** `use server`＋`useOptimistic`の組み合わせで、楽観的UIとサーバー側の整合性を保ちながらプログレッシブなデータ更新が可能になり、従来のSWR/React Queryの役割が縮小傾向にある。

- **バンドルサイズへの影響が顕在化:** RSCにより クライアントJSを大幅削減できる一方、Client Component境界を誤ると逆にハイドレーションコストが増大するため、`"use client"`の配置戦略がチーム内での重要なアーキテクチャ判断になっている。

- **可観測性の整備が急務:** ストリーミング環境ではウォーターフォール型のトレーシングが機能しないため、OpenTelemetryのストリーミング対応トレースや、サーバー/クライアント境界をまたぐRUM計測の導入がプロダクション運用の前提条件となっている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年現在、Next.js等のフルスタック環境ではtRPCが主流化しつつあり、クライアント・サーバー間でTypeScript型を共有することでランタイムエラーを大幅削減できる。スキーマ定義なしで型安全なAPIが実現できるため、小〜中規模チームの開発速度が向上している。

- **GraphQLの適用領域の明確化:** GraphQLは「何でも解決策」から「複雑なデータグラフが必要な場面（BFF、マルチクライアント）」に特化する傾向が強まっている。過剰なオーバーヘッドを避けるため、単純なCRUD APIにGraphQLを採用するのはアンチパターンとして認識されるようになった。

- **REST + OpenAPIの再評価:** AIコード生成ツールとの親和性が高く、OpenAPI仕様からクライアントSDKを自動生成するワークフロー（orval、hey-api等）が普及。REST自体は枯れた技術だが、ツールチェーンの成熟により「シンプルで十分」という判断が増えている。

- **エッジ・ストリーミング対応の必要性:** Vercel Edge / Cloudflare Workersの普及により、APIデザインにストリーミングレスポンス（SSE、ReadableStream）を考慮することが必須になってきた。tRPCとGraphQL（Yoga等）はエッジ対応を強化しており、RESTでも`Transfer-Encoding: chunked`の活用が増加。

- **選定基準の実用指針:** 2026年の判断軸は「チームのTypeScript習熟度 × クライアント種別 × チーム規模」。フルスタックTS + 単一クライアント → tRPC、複数クライアント + 複雑なデータ → GraphQL、外部公開API + 言語非依存 → REST+OpenAPIが現実的な選択肢。

### 4. serverless edge computing 2026

- **エッジでの本格的なAI推論:** WebAssembly + ONNX Runtime のエッジ実行が成熟し、LLMの小型モデル（1-3B params）をCDNノードで動かすアーキテクチャが実用段階に入った。レイテンシ重視のユースケースではオリジンへのラウンドトリップが不要になる。

- **Durable Objects / Actor モデルの普及:** Cloudflare Durable ObjectsやAWS Lambda@Edgeのステートフル拡張により、「エッジでも状態を持てる」設計が定着。リアルタイムコラボレーションやセッション管理をエッジで完結させる構成が増加している。

- **コールドスタートの事実上の解消:** V8 Isolateベースのランタイム（Cloudflare Workers, Vercel Edge Runtime）が主流化し、従来のコンテナ型Lambdaのコールドスタート問題が設計上の考慮事項から外れつつある。ただしNode.js互換レイヤーのオーバーヘッドには注意が必要。

- **エッジでのデータ整合性の課題が顕在化:** エッジKV（eventually consistent）とリージョナルDBの使い分けが設計の核心に。書き込み重視の操作をエッジに寄せすぎると整合性バグが発生しやすく、read-heavy なキャッシュ層としての活用に留めるのが現実的なベストプラクティス。

- **コスト構造の再設計が必要:** リクエスト数ベースの課金からCPU時間・メモリ使用量ベースへの移行が進み、バースト時のコスト予測が難しくなっている。エッジ関数の実行時間をp99で監視し、上限を設けるガードレール設計が運用上不可欠。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の標準採用:** パスワードレス認証がデファクトスタンダードとなり、フィッシング耐性のあるパスキーをプライマリ認証手段として設計することが必須。レガシーパスワードフォールバックは段階的に廃止する。

- **セッション管理のゼロトラスト化:** 長寿命トークン（30日リフレッシュなど）は廃止傾向。短命アクセストークン（15分）＋デバイスバインドセッションの組み合わせで、トークン漏洩時の被害を最小化する。

- **MFAはTOTPではなくハードウェアキー or パスキーへ移行:** SMS/TOTPはSIMスワップやリアルタイムフィッシングに脆弱。2026年時点でSMS-OTPをMFAとして使い続けることはリスクとみなされる。

- **OAuth 2.1 + DPoP（Demonstrating Proof of Possession）の採用:** Bearer tokenの盗用対策としてDPoPが実用段階に入った。トークンを発行先デバイスに暗号的にバインドすることで、中間者攻撃を防止する。

- **認証イベントの継続的リスク評価（CAEP/SSF）:** ログイン時点だけでなく、セッション中のリスクシグナル（位置変化・デバイス異常）を継続評価し、動的に再認証を要求するアダプティブ認証が標準的になっている。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6 + Supabase の統合成熟:** Prisma v6ではEdge Runtime対応が強化され、Supabaseの`pgbouncer`接続プーリングとの組み合わせでサーバーレス環境でのコールドスタート問題が大幅に改善。`DATABASE_URL`と`DIRECT_URL`の使い分けがベストプラクティスとして定着している。

- **Row Level Security (RLS) とアプリ層の責務分離:** SupabaseのRLSをデータ層のセキュリティ境界として活用し、PrismaはORMとして型安全なクエリに専念する設計が主流。RLSをPrismaのミドルウェアで迂回しないよう`service_role`キーの管理が重要。

- **Supabase Realtime + 楽観的UI:** RealtimeチャンネルとPostgresのWALを活用したリアルタイム同期が本番レベルで安定。PrismaのミューテーションとSupabaseのRealtimeを組み合わせる場合、二重更新を避けるためクライアント側の状態管理設計が鍵。

- **pgvector によるAIネイティブアーキテクチャ:** Supabaseがpgvector拡張を標準サポートし、ベクター検索をPostgres内で完結させるパターンが2026年の主流。Prismaからの`$queryRaw`でベクター演算を呼び出す設計が現実的だが、専用ORM対応は未成熟なため注意。

- **マイグレーション戦略の厳格化:** `prisma migrate deploy`（CI用）と`supabase db push`の混在は競合リスクが高く、どちらか一方をソースオブトゥルースにする方針を組織として統一することが2026年時点での重要な意思決定事項。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の本格普及:** 2026年はWASI Preview 2が主流となり、RustのWASM出力がよりポータブルかつ相互運用可能になった。`cargo component`ツールチェーンで型安全なインターフェース定義が実現し、マイクロサービス間のABI問題が大幅に軽減されている。

- **SIMD・スレッド命令の安定化によるネイティブ近接パフォーマンス:** WebAssembly SIMDとShared Memoryスレッドが全主要ブラウザ・ランタイムで安定稼働し、数値計算・画像処理ワークロードでRust/WASMのスループットがネイティブの85〜95%に到達するケースが報告されている。

- **Edge Runtime（Cloudflare Workers / Fastly Compute）でのRust WASMが事実上の標準:** Cold startがマイクロ秒オーダーで、Node.jsベースのEdge Functionと比べてレイテンシが1桁改善されるケースが増加。サーバーレス関数の選定基準として「Rust+WASM対応か否か」が重要指標になっている。

- **`wasm-opt`と`twiggy`によるバイナリサイズ最適化が必須工程に:** Rustのデフォルトリリースビルドでも数百KB〜数MBになりがちだが、`wasm-opt -O3`とLTO＋`panic=abort`の組み合わせで50〜70%削減が現実的。初回ロード体験に直結するため、CI/CDパイプラインへの組み込みが標準化されている。

- **GCプロポーザル（WasmGC）でRust以外との住み分けが明確化:** GCを持つ言語（Kotlin/Dart）はWasmGCへ移行し、RustはGC不要の低レイヤー・パフォーマンスクリティカルな処理に特化するアーキテクチャ分離が進んでいる。Rustを選ぶ判断基準は「予測可能なレイテンシとゼロコスト抽象化が必要か」に絞られてきた。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** 2026年のベストプラクティスは「クライアント境界を最小化する」こと。`'use client'`はインタラクション必須のリーフコンポーネントのみに限定し、データフェッチ・ロジックはServer Componentsに集約することでバンドルサイズを大幅削減できる。

- **Partial Prerendering（PPR）の本格活用:** Static ShellとDynamic Holesを組み合わせたPPRが安定版となり、ISRの代替として普及。ページ全体をSSR/SSGで二択する時代は終わり、コンポーネント単位でレンダリング戦略を選択できる。

- **`use cache` APIによるきめ細かいキャッシュ制御:** Next.js 15+で導入された`use cache`ディレクティブとタグベース無効化（`revalidateTag`）の組み合わせが主流。`fetch`のキャッシュオプションよりも明示的でコンポーネント単位の制御が可能になった。

- **Server Actions の設計原則:** フォーム送信・ミューテーション処理はServer Actionsに集約し、APIルートを廃止するプロジェクトが増加。ただしZodバリデーションとエラーハンドリングをActions内で必ず実装しないとセキュリティホールになるため、入力検証は必須。

- **Turbopackへの移行完了:** 2026年時点でTurbopackがデフォルトバンドラーとして安定化し、開発サーバー起動とHMRが劇的に高速化。大規模プロジェクトでは`next.config`のwebpack拡張をTurbopack対応に移行する作業コストを見積もる必要がある。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの制約を理解した設計:** Node.js APIの一部（`fs`、`net`等）はEdge Runtimeで使用不可。`next.config.js`で`runtime: 'edge'`を明示し、依存ライブラリのEdge互換性を事前にチェックすることが必須。

- **Cold Start最小化のためのバンドルサイズ管理:** Edge Functionsは1MB制限があり、バンドルが大きいほどCold Startが遅延する。`@vercel/nft`でTree Shakingを徹底し、重いライブラリ（例：`zod`の代わりに`valibot`）への置き換えを検討する。

- **Streaming ResponseとSuspense境界の活用:** `ReadableStream`を使ったストリーミングレスポンスにより、TTFB（Time to First Byte）を大幅に改善できる。Next.js App RouterのSuspense境界と組み合わせると、体感レスポンス速度が向上する。

- **キャッシュ戦略の階層化:** `Cache-Control`ヘッダーとVercelのEdge Cacheを組み合わせ、Stale-While-Revalidateパターンを採用する。動的コンテンツでもエッジでの部分キャッシュ（ISR）により、オリジンへのリクエストを70〜90%削減可能。

- **Geo・A/BロジックはMiddlewareで一元管理:** ユーザーの地域判定やA/Bテストのルーティングは`middleware.ts`のEdge層で処理し、アプリケーション層に漏らさない。`request.geo`と`EdgeConfig`（低レイテンシなKVストア）を組み合わせると、設定変更をデプロイなしで反映できる。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded Typesが実運用で定着し、プリミティブ型の誤用をコンパイル時に防ぐパターンが標準化されている。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` が広く使われ、型推論を維持しながら型チェックを行う場面で `as` キャストを置き換えつつある。型安全性とDXの両立が実現できる。

- **Zod + tRPC による境界防衛:** APIの入出力をZodスキーマで定義し、tRPCでクライアント/サーバー間の型を自動共有するパターンが事実上の標準に。ランタイム検証と静的型が一致することで、バグの温床だった境界の問題が解消される。

- **`noUncheckedIndexedAccess` の有効化:** `tsconfig.json` でこのオプションを有効にすることで、配列・オブジェクトのインデックスアクセス時に `undefined` が型に含まれるようになり、実行時エラーをコンパイル時に検出できる。2026年時点では新規プロジェクトでのデフォルト化が推奨されている。

- **Template Literal Types の実用化:** `type EventName = \`on${Capitalize<string>}\`` のようなTemplate Literal Typesが、イベントシステムやAPIルート定義で本格採用され、文字列パターンの型安全性が大幅に向上している。
