# CTO Knowledge - 2026-09-07

## Daily Update (2026-09-07)

### 1. Next.js performance optimization 2026

- **Turbopackの標準化とビルド高速化:** Next.js 16ではTurbopackがデフォルトバンドラーとなり、開発サーバー起動やHMRが大幅に高速化されている。当社のような中規模コードベースでもビルド時間短縮の恩恵を受けやすく、CI時間の削減にも直結する。

- **Partial Prerendering (PPR) による静的×動的の両立:** 静的シェルを即座に配信しつつ、動的部分のみストリーミングでレンダリングする手法が主流になりつつある。物件一覧のような「共通レイアウトは静的、価格や空室状況は動的」というページ構成に相性が良い。

- **React Compilerによる自動最適化:** `useMemo`/`useCallback`の手動チューニングが不要になりつつあり、コードのシンプルさとパフォーマンスを両立できる。既存コンポーネントの最適化コストを下げられるため、開発速度への影響が小さい。

- **`use cache`ディレクティブによる粒度の細かいキャッシュ制御:** ページ単位ではなく関数・コンポーネント単位でキャッシュ戦略を指定できるようになり、物件詳細ページなど更新頻度が異なるデータが混在する画面でのキャッシュ設計がしやすくなっている。

- **Server Componentsによるクライアントバンドル削減:** ロジックをサーバー側に寄せることでクライアントに送るJSを最小化し、特にモバイル回線でのTTI(Time to Interactive)改善に寄与する。認証まわりなどインタラクティブ性が必要な部分だけをClient Componentに限定する設計指針が引き続き有効。

### 2. React Server Components streaming 2026

- **ポイント1（Partial Prerendering との統合）:** Next.js 16ではPPR（Partial Prerendering）がRSCストリーミングとより深く統合され、静的シェルを即時返却しつつ動的部分を`Suspense`境界でストリームする構成が標準化。TTFBとインタラクティブ性の両立が図りやすくなっている。
- **ポイント2（キャッシュ戦略の複雑化）:** `use cache`ディレクティブやセグメント単位のキャッシュ制御が浸透し、ストリーミングとキャッシュの組み合わせ設計が重要な論点に。物件詳細ページのような一覧+詳細構成では、キャッシュ粒度の見誤りが古いデータ表示や過剰な再計算を招くリスクがある。
- **ポイント3（エラーバウンダリの粒度設計）:** ストリーミング中の部分的失敗（一部コンポーネントのfetchエラー）をどう扱うかが実務上の課題。`error.tsx`やネストした`Suspense`+`ErrorBoundary`の粒度を機能単位で細かく分けることで、1箇所の失敗が全体をブロックしない設計が重要。
- **ポイント4（クライアントバンドルの継続的縮小）:** RSCによりクライアントJSの送信量を最小化する流れが加速し、フォームや認証系のような`'use client'`境界を必要最小限に絞る設計判断がパフォーマンスに直結する。うちのプロダクトでは`listing/`配下のインタラクティブ要素の境界見直しが効果的。
- **ポイント5（Observability/計測の標準化）:** ストリーミングのTTFB/TTIをサーバー側で計測するツールチェーン（Next.js内蔵の`instrumentation.ts`やOpenTelemetry連携）が整い始めており、本番投入前にストリーミング境界ごとのレイテンシ計測を組み込むのがベストプラクティスになりつつある。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1: tRPCの採用拡大とスキーマ駆動開発の一体化** — フルスタックTypeScriptプロジェクトでは、REST/GraphQLのスキーマ定義とクライアント型生成の二重管理を避けるため、tRPCによるエンドツーエンドの型安全性が標準になりつつある。sumitsugiのようなNext.js App Routerベースの構成では、Server Actionsとの併用でtRPCの必要性自体が薄れるケースもあるため、チームの規模とAPI公開範囲（外部公開かモノレポ内限定か）で選定すべき。

- **ポイント2: GraphQLはBFF/集約レイヤーに限定活用** — 汎用APIとしてのGraphQL全面採用は複雑性（N+1問題、キャッシュ設計、認可の細粒度化）に見合わないことが多く、2026年は「複数クライアント・複数バックエンドを束ねる集約層」としての限定利用がベストプラクティス。sumitsugiのようにNext.js単体で完結する構成では優先度は低い。

- **ポイント3: RESTはOpenAPI + 型生成で"退化"ではなく成熟** — OpenAPI仕様からのTypeScript型自動生成（orval, openapi-typescript等）が定着し、RESTでも実質的な型安全性をtRPCに近づけられるようになった。外部連携（決済代行、外部システムとの引き継ぎ連携など）が視野にあるsumitsugiでは、外部公開のしやすさ・ドキュメント標準化の観点でRESTが有利。

- **ポイント4: エッジ/サーバーレス実行環境への最適化が設計の前提に** — Vercel Edge FunctionsやCloudflare Workers上でのAPI実行が前提になり、コールドスタート・バンドルサイズを意識したAPI設計（tRPCの軽量ルーター、REST側はエッジ対応ランタイム限定のライブラリ選定）が重要な評価軸になっている。

- **ポイント5: 認可・監査ログをAPI層に組み込む設計が必須化** — 個人情報や住宅引き継ぎのような機微データを扱うドメインでは、API設計時点でリクエスト単位の認可チェックと監査ログ出力を仕組み化することが求められており、これはREST/GraphQL/tRPCいずれを選んでも共通の設計原則として先に固めるべき（`.claude/rules/standards.md`のセキュリティ要件とも整合）。

### 4. serverless edge computing 2026

- **ポイント1（WASMベースの実行環境の主流化）:** Cloudflare Workers、Fastly Compute、Deno DeployなどWebAssemblyベースのエッジランタイムが、コールドスタートをミリ秒未満に抑えつつNode.js並みの互換性を実現しつつある。sumitsugiのようなNext.js SSRアプリでは、認証チェックや物件検索のリライト処理をエッジ関数に寄せることでTTFBを大幅に短縮できる。

- **ポイント2（エッジでのデータレイヤー統合）:** Cloudflare D1/Durable Objects、Vercel Edge Config、Turso（libSQL）のようにデータベース自体がエッジにレプリケートされる流れが加速しており、読み取りが多い物件一覧・検索機能はリージョンをまたいだレイテンシをほぼゼロにできる。ただし書き込み整合性（前の住人・次の住人間のマッチング状態更新など）はまだリージョン集約が必要な場合が多く、設計時の見極めが重要。

- **ポイント3（Next.js 16とエッジランタイムの親和性向上）:** App RouterのPartial Prerendering（PPR）とエッジランタイムの組み合わせで、静的な物件詳細ページの殻を即座に配信しつつ、価格や空室状況などの動的部分だけをエッジでストリーミングする設計が2026年の標準パターンになりつつある。

- **ポイント4（コスト構造の変化）:** 実行時間課金からリクエスト数＋CPU時間の細粒度課金への移行が進み、常時起動のサーバーレスコンテナ（Fly.io Machines、AWS Lambda SnapStartなど）とエッジ関数を用途別に使い分けるハイブリッド構成がコスト最適化の鍵になっている。ベータローンチ前のsumitsugiにとっては、トラフィックが読めない初期段階でこそエッジ+従量課金のメリットが大きい。

- **ポイント5（可観測性とセキュリティの課題）:** エッジは分散実行ゆえにログ集約・トレーシングが難しく、OpenTelemetry対応のエッジネイティブAPM（Baselime、Axiomなど）の採用が2026年のベストプラクティスになっている。またエッジでの認証情報の扱い（JWT検証など）はKVストアの整合性遅延を考慮した設計が必須で、CLAUDE.mdのセキュリティ基準（シークレットのハードコード禁止・入力検証）はエッジ関数にも同様に適用すべき。

### 5. authentication security best practices 2026

- **パスキー標準化:** FIDO2/WebAuthnベースのパスキーがデフォルト認証手段になりつつあり、パスワード+SMS OTPは非推奨。フィッシング耐性が高く、当プラットフォームでも次の住人向けログインはパスキー優先で設計すべき。
- **フィッシング耐性MFA必須化:** SMSやTOTPよりハードウェアキー・パスキーによるフィッシング耐性MFAが業界標準に。決済や本人確認を伴う引き継ぎフローでは特に必須。
- **セッションハイジャック対策:** トークン窃取を防ぐDPoP（Demonstrating Proof of Possession）やセッションバインディングの実装が重要。JWTを単純にlocalStorageへ保存する実装は避け、HttpOnly Cookie＋短命トークンの組み合わせを徹底。
- **継続的・リスクベース認証:** ログイン時点だけでなく、デバイス指紋やアクセスパターンを見て継続的にリスク評価するZero Trust型認証が主流化。物件掲載・決済など高リスク操作時にステップアップ認証を挟む設計が有効。
- **認証情報管理の自動化:** シークレットローテーションやKMS連携が標準要件に。`.env`への直書きは厳禁とし、Supabase/Vercelのシークレット管理機能を活用する運用を継続すべき。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMのRust脱却が完了:** Prisma 6以降、クエリエンジンがRustバイナリからTypeScript/WASM実装に移行し、コールドスタートが大幅短縮。Vercel等のエッジ・サーバーレス環境（Next.jsのApp Router）との相性が向上し、デプロイサイズも軽量化された。

- **SupabaseのDBブランチ機能がCI/CDの標準に:** PRごとに本番スキーマの独立コピー（ブランチ）を自動生成でき、マイグレーションやRLSポリシーの変更をステージングで検証してからマージする運用が主流化。sumitsugiのようなdraft/public状態管理を持つプロダクトでは、スキーマ変更の回帰テストに有効。

- **RLS（Row Level Security）とPrisma接続の整合性に注意:** PrismaはデフォルトでDB接続にサービスロールを使うため、SupabaseのRLSを素通りしやすい。前の住人/次の住人のようなロール別アクセス制御をDB層で担保したい場合、Supavisor経由でユーザーコンテキストを渡すか、アプリ層でのZodバリデーション＋RLS二重防御が必要。

- **Prisma Accelerateによるコネクションプーリングの外部化:** サーバーレス関数の同時実行数増加に伴うDB接続枯渇問題に対し、PrismaAccelerateやSupabaseのSupavisorをエッジ層でのプーリングに使うパターンが定着。物件検索のような読み取り負荷の高いAPIでレイテンシ改善が見込める。

- **型安全性とマイグレーション運用の分業:** Prisma SchemaをSSOT（Single Source of Truth）とし、Supabase CLIでマイグレーションを管理する二重管理より、`prisma migrate`一本化＋Supabase Studioは閲覧専用にする運用が、型不整合（例: `'draft' | 'public'`のようなUnion型）の事故防止に有効。

### 7. WebAssembly Rust performance 2026

- **ポイント1（Component ModelとWASI Preview 2の定着）:** WASI Preview 2とComponent Modelがツールチェーン標準になり、RustクレートをWasmコンポーネントとして相互運用できるようになったことで、マイクロサービスの一部をWasmサンドボックスに置き換える設計がコスト効率よく実現できる。
- **ポイント2（JITに迫るAOTコンパイル最適化）:** WasmtimeやWasmerのCranelift/LLVMバックエンド改善により、Rust製WasmモジュールのAOTコンパイル後の実行速度がネイティブの85〜95%程度まで近づいており、CPUバウンドな処理をエッジで実行する判断がしやすくなっている。
- **ポイント3（メモリ管理とマルチスレッドの成熟）:** `wasm64`とshared memory + threads提案の主要ランタイム対応が進み、Rustの`rayon`ベースの並列処理をWasm側でもほぼそのまま活用できるようになったため、画像処理やPDF生成のような重い処理をブラウザ/エッジ双方で共通コード化しやすい。
- **ポイント4（バンドルサイズと起動時間のトレードオフ管理）:** `wasm-opt`や`twiggy`などの解析ツールがCIパイプラインに組み込まれるのが一般的になり、Rust側のfeature flag設計と組み合わせて不要なpanicメッセージやモノモーフ化コードを削減する運用が定石化している。sumitsugiのような物件情報配信でPDF生成や画像最適化をエッジで行う際、初回ロード時間への影響を継続的に計測する価値がある。
- **ポイント5（デバッグ・可観測性の改善）:** ソースマップ相当のDWARF対応やWasm向けprofilerの充実により、本番環境でのパフォーマンスボトルネック特定がしやすくなっており、「Wasmはブラックボックス」という導入障壁が下がっている。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 15以降で導入されたPPRが2026年には主流パターンとして定着し、静的シェルを即座に返しつつ動的部分をストリーミングすることで、SSGのパフォーマンスとSSRの鮮度を両立できる。物件一覧ページのような「ヘッダーは静的・在庫情報は動的」という構成に特に有効。

- **Server Actions中心の設計:** APIルートを介さずServer Actionsで直接フォーム送信・データ変更を行う設計が定番化し、`use server`ディレクティブとZodバリデーションを組み合わせた型安全なミューテーションパイプラインが標準パターンになっている。予約フローや問い合わせフォームの実装コストを大幅に削減できる。

- **`use cache`ディレクティブによる明示的キャッシュ制御:** これまで暗黙的だったfetchキャッシュ戦略が、関数・コンポーネント単位で`use cache`を明示するモデルに移行し、キャッシュの意図が読みやすくコントロールしやすくなった。物件詳細データなど更新頻度の異なるデータを細かく制御する際に有用。

- **Server Componentsファーストのコンポーネント設計:** 「Client Componentは末端の葉ノードのみ」という原則がより徹底され、インタラクティブなUI（フィルタ、モーダル等）だけを`'use client'`境界で切り出す設計がベストプラクティスとして確立。バンドルサイズ削減とTTIの改善に直結する。

- **型安全なルーティングとレイアウト分離:** App Routerの`typedRoutes`が安定機能となり、動的セグメント（`[id]`等）の型チェックがビルド時に効くようになった。並行して、Route Groupsを使った認証済み/未認証エリアのレイアウト分離が定石化し、`(auth)`や`(public)`のようなグルーピングでミドルウェアロジックをシンプルに保てる。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約理解:** Vercel Edge FunctionsはNode.js APIの一部が使えないV8アイソレートベースのため、重い依存関係を持つライブラリは避け、Web標準API（fetch, crypto.subtle等）ベースの軽量実装に寄せることでコールドスタートをほぼゼロに近づけられる。

- **Streaming + Partial Prerendering(PPR)の活用:** Next.js 16のPPRとEdge Functionsを組み合わせることで、静的シェルを即座に返しつつ動的部分をストリーミングでき、体感TTFBを大幅に改善できる。sumitsugiの物件検索・一覧ページのような動的+静的混在コンテンツに特に有効。

- **リージョン最適化とデータ近接性:** Edge Functionsはグローバル分散されるが、DB（Supabase/Postgres等）へのレイテンシがボトルネックになりやすいため、`regions`設定でDBに近いリージョンに固定するか、Edge対応のデータレイヤー（Vercel KV, Neon Edge Driver等）への移行を検討すべき。

- **ミドルウェアの肥大化に注意:** 認証チェックや前の住人/次の住人の権限判定ロジックをmiddleware.tsに詰め込みすぎると全リクエストで実行コストがかかるため、必要最小限のロジックのみに絞り、重い処理はページ側のServer Componentsに委譲する設計が2026年のベストプラクティス。

- **コスト管理:** Edge Functionsは実行時間課金モデルのため、無限ループやポーリング的な処理は避け、Vercel Analyticsで実行時間分布を監視しつつ、必要ならNode.jsランタイムとのハイブリッド運用（重い処理はServerless/Node、軽量なリダイレクト・A/Bテスト判定はEdge）を選択するとコスト効率が良い。

### 10. TypeScript type safety patterns 2026

- **ポイント1（Branded Types / Nominal Typing）:** IDやメールアドレスなど構造的に同じstring型を混同しないよう、`type UserId = string & { readonly __brand: 'UserId' }`のようなブランド型が標準的なパターンとして定着。sumitsugiでも`propertyId`と`userId`の取り違えバグをコンパイル時に防げる。

- **ポイント2（Zodによるランタイム/コンパイル時の型統合）:** `z.infer<typeof schema>`でZodスキーマから型を自動導出し、システム境界（APIレスポンス、フォーム入力）での実行時検証と静的型を一致させる手法が主流。CLAUDE.mdの「Input validation: Zodスキーマ」方針とも合致しており、`draft`/`public`のようなUnion型もZodの`z.enum`で二重管理を回避できる。

- **ポイント3（Discriminated Unionsによる状態管理）:** 物件ステータスのような`'draft' | 'public'`型に加え、各状態が持つべきプロパティが異なる場合は`{ status: 'draft', ... } | { status: 'public', publishedAt: Date, ... }`という判別可能なUnionにすることで、switch文の網羅性チェック（`never`型での exhaustiveness check）がコンパイル時に効き、Union型に値を追加した際の考慮漏れを防げる。

- **ポイント4（`satisfies`演算子の活用）:** TypeScript 4.9以降定着した`satisfies`により、型推論を保ったまま制約チェックが可能。設定オブジェクト（`site-config.ts`など）で型の広がりを防ぎつつリテラル型推論を維持できるため、`as const`との使い分けが2026年時点でのベストプラクティスとして定着。

- **ポイント5（型安全なルーティング）:** Next.js App Routerの型付きルート機能（typedRoutes）やtRPC的なend-to-end型推論パターンが普及し、`src/app/`配下のページ間リンクやAPIクライアントで文字列パスのタイプミスをコンパイル時に検出できるようになっている。
