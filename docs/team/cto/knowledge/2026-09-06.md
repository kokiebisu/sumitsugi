# CTO Knowledge - 2026-09-06

## Daily Update (2026-09-06)

### 1. Next.js performance optimization 2026

- **ポイント1: Partial Prerendering (PPR) の本格運用** — Next.js 15以降で導入されたPPRがNext.js 16で安定版となり、静的シェルと動的コンテンツを1つのレスポンスで配信できるため、TTFBを大幅に短縮しつつパーソナライズも両立できる。sumitsugiの物件詳細ページのような「静的な物件情報＋動的な空き状況」構成に特に有効。

- **ポイント2: React Server Components + Cache Componentsの活用** — `use cache`ディレクティブによる関数・コンポーネント単位の明示的キャッシュ制御が主流化し、`revalidateTag`と組み合わせることで物件一覧・検索結果のような更新頻度が異なるデータを細かく制御できる。過剰なre-fetchを防ぎつつデータ鮮度も担保できる。

- **ポイント3: Turbopackのビルド・開発体験のデフォルト化** — Turbopackが本番ビルドでも安定運用フェーズに入り、ビルド時間短縮（大規模プロジェクトで数倍高速）が期待できる。`bun run build`のCI実行時間短縮に直結するため、PRごとのフィードバックループが速くなる。

- **ポイント4: 画像・フォントの自動最適化とEdge Runtimeの使い分け** — `next/image`のAVIF優先配信やCore Web Vitals（特にLCP・INP）への直接的な影響が評価軸として重視され続けている。認証不要な公開ページ（物件一覧など）はEdge Runtimeで配信しTTFBを削減、認証必須ページはNode.js Runtimeに留めるハイブリッド構成が定石化している。

- **ポイント5: Client Componentの「境界」設計がパフォーマンスの鍵** — バンドルサイズ削減の観点から、`'use client'`境界を末端コンポーネントまで押し下げる設計が重視されており、Interactive要素（お気に入りボタン、フィルターUIなど）のみをクライアント化しJSペイロードを最小化するパターンが標準的なベストプラクティスとして定着している。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPartial Prerendering (PPR) が安定版となり、静的シェルを即座に返しつつ動的部分だけをストリーミングする構成が標準化。初期表示速度とSEOを両立させたい`src/app/properties/`のような一覧ページに特に有効。
- **ポイント2:** `loading.tsx`と`<Suspense>`境界の粒度設計が重要な設計判断に。過度に細かく分割するとウォーターフォールが発生し逆に体感速度が悪化するため、データ取得の依存関係を見てバウンダリを配置する必要がある。
- **ポイント3:** Server ActionsとRSCストリーミングの組み合わせで、フォーム送信後の楽観的UI更新がより自然に。物件掲載や予約フローなど`multi-step flows`でuseOptimisticと組み合わせるパターンが定番化しつつある。
- **ポイント4:** キャッシュ戦略（`fetch`のrevalidateタグ、`unstable_cache`）とストリーミングの相互作用に注意が必要——キャッシュミス時にストリーミングが長引くケースがあるため、頻繁に変わるデータ（空室状況など）は明示的にタグ管理する設計が推奨される。
- **ポイント5:** RSCペイロードのサイズ増加によるハイドレーションコスト増が課題として顕在化しており、クライアントコンポーネントの境界を最小化する「サーバーファースト」設計が引き続きベストプラクティス。`src/components/ui/`のような共通UIは可能な限りサーバーコンポーネントのまま保つ方針が有効。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCの採用が拡大中で、TypeScriptモノレポ構成のプロジェクトではスキーマ定義とAPI型を自動同期でき、フロント/バック間の型不整合バグを大幅に削減できる。sumitsugiのようなNext.js App Router構成なら、Server Actionsとの使い分けを明確にすることが重要。

- **ポイント2:** GraphQLは依然として複雑なデータ取得（ネストしたリレーション、モバイル向け帯域最適化）に強いが、2026年は「GraphQL疲れ」も進み、単純なCRUD中心のプロダクトではオーバーエンジニアリングと判断されるケースが増えている。物件・ユーザー・予約程度のドメインならRESTかtRPCで十分。

- **ポイント3:** RESTはOpenAPI 3.1 + コード生成（openapi-typescript等）でtRPCに近い型安全性を後付けできるようになり、「外部公開APIはREST/OpenAPI、内部BFFはtRPC」というハイブリッド構成がデファクトになりつつある。

- **ポイント4:** どの方式でもZodなどによる境界でのランタイムバリデーションは必須（standards.mdの方針とも一致）。型はコンパイル時の保証に過ぎず、外部入力の実行時検証を省略するとセキュリティリスクになる。

- **ポイント5:** Edge/Serverless環境（Vercel等）へのデプロイが前提の場合、tRPCやRESTはコールドスタートやペイロードサイズの観点で有利。GraphQLサーバーはリゾルバのN+1問題対策（DataLoader等）が追加の運用コストになる点に注意。

### 4. serverless edge computing 2026

- **エッジでのAI推論標準化:** 2026年はCloudflare Workers AIやVercel Edge FunctionsでLLM推論がエッジネイティブになり、レイテンシ重視のUXでは中央集権的なAPI呼び出しより高速化が進む。sumitsugiのような物件検索・レコメンド機能はエッジ推論でTTFBを大幅短縮できる可能性がある。

- **コールドスタート問題の実質解消:** V8 isolateベースのランタイム改善とプリウォーミング技術により、エッジ関数のコールドスタートは数ミリ秒まで縮小。ただしNext.js 16のApp RouterでSSRを多用する場合、エッジ/Node.jsランタイムの使い分け設計が引き続き重要。

- **データレイヤーのエッジ化:** D1やTurso等のエッジネイティブDBが普及し、リージョン跨ぎのレイテンシがボトルネックになりにくくなった。ただしsumitsugiのような日本国内ユーザー中心のサービスでは、単一リージョン最適化の方がコスト対効果が高いケースが多く、過剰なグローバル分散は避けるべき。

- **ベンダーロックインとコストの再評価:** エッジ実行はリクエスト課金モデルが主流で、トラフィックパターン次第では従来サーバーレスより割高になる場合がある。ローンチ前の今は、実測トラフィックが読めない段階でのエッジ全面移行はリスクが高く、必要な箇所（静的コンテンツ配信・認証チェックなど）に限定した部分採用が現実的。

- **Observabilityの分散化課題:** エッジ環境は分散トレーシングの複雑性が増すため、OpenTelemetry対応が進んだとはいえ、デバッグ体験は依然中央集権型より劣る。ベータローンチ後の初期段階では、シンプルなNode.jsランタイム＋集約ログの構成を維持し、スケール課題が実際に顕在化してからエッジ移行を検討するのが妥当。

### 5. authentication security best practices 2026

- **パスキー移行の本格化:** パスワードレス認証（WebAuthn/FIDO2）がデファクトスタンダードとなり、SMS/メールOTPはフィッシング耐性の低さから補助手段に格下げされている。sumitsugiのようなtoC向けサービスでは、初回登録時にパスキー選択肢を前面に出すことでアカウント乗っ取りリスクを大幅に低減できる。

- **セッション管理とトークンの短命化:** 長期有効なJWTやセッションCookieの窃取被害が増えており、リフレッシュトークンのローテーション・デバイスフィンガープリンティング・異常ログイン検知（IPやUAの急変）を組み合わせた多層防御が標準化している。

- **AI悪用への対策:** 生成AIによるフィッシングメールやディープフェイク音声を使ったソーシャルエンジニアリングが高度化しており、単純なCAPTCHAでは不十分。行動ベースのボット検知（reCAPTCHA Enterprise相当）やレート制限、異常検知をAPI層に組み込む必要がある。

- **最小権限とゼロトラスト設計:** 「前の住人」「次の住人」など役割ごとにアクセス範囲を厳密に分離し、内部APIでもリクエストごとに認可チェックを行う設計が重要。特に個人情報（住所・連絡先）を扱う引き継ぎフローでは、RBACに加えて属性ベースアクセス制御（ABAC）の検討価値がある。

- **監査ログと侵害後対応の自動化:** 認証イベント（ログイン失敗、パスワードリセット、デバイス追加）の構造化ログを保持し、異常検知時に自動でセッション無効化・通知を行う仕組みが2026年のベストプラクティスとして定着している。法務確認中の現フェーズでも、プライバシーポリシー策定と合わせて監査ログ保持ポリシーを明文化しておくべき。

### 6. database architecture Prisma Supabase 2026

- **ポイント1（Prisma ORMの進化）:** Prisma 6以降はRustベースのクエリエンジンから移行し、TypeScript純正のクエリコンパイラ（Prisma ORM without Rust engine）を採用したことでコールドスタートが大幅に改善され、Vercelなどのサーバーレス環境でのレイテンシ問題が解消されつつある。sumitsugiのようにNext.js App Routerでサーバーレス関数を多用する構成では、この恩恵を受けやすい。

- **ポイント2（Supabase + Row Level Security）:** SupabaseはPostgreSQLのRLS（Row Level Security）をアプリ層の認可ロジックと併用するのが2026年のベストプラクティスになっており、`auth-context.tsx`のようなクライアント側の認証状態だけに依存せず、DB側でも「前の住人」「次の住人」のデータアクセス境界を強制する多層防御が推奨されている。

- **ポイント3（Prisma × Supabase接続戦略）:** Supabaseのconnection pooler（PgBouncer/Supavisor）とPrismaのPrisma Accelerateを組み合わせることで、サーバーレス関数のコネクション枯渇問題を回避するのが定石化しており、本番導入前に`DATABASE_URL`（pooler経由）と`DIRECT_URL`（マイグレーション用）を分離設定することが必須。

- **ポイント4（型安全なスキーマ駆動開発）:** Prisma SchemaからZodスキーマを自動生成するツール（zod-prisma-typesなど）が標準化しつつあり、`.claude/rules/standards.md`が求める「システム境界でのZod検証」をDBスキーマと二重管理せず一元化できる点は、物件ステータス（`'draft' | 'public'`）のようなUnion型の整合性維持にも直結する。

- **ポイント5（Supabase Branching/プレビュー環境）:** Supabaseのデータベースブランチング機能がGA化し、PRごとに本番同等のPostgreSQLプレビュー環境を自動生成できるようになったため、E2Eテスト（Playwright）でのデータ依存テストの信頼性が向上し、`bun run test:e2e`のflaky率低減に寄与する事例が増えている。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデルの本格普及:** WebAssembly Component Model（WASI Preview 2）が主要ランタイム（Wasmtime, wasmer）で安定し、Rustの`cargo component`を使ったモジュール間の型安全な連携がプロダクションレベルで使えるようになっている。前の住人データを扱う際の物件検索エンジンなどを言語非依存で疎結合に構成できる。

- **SIMD/マルチスレッドの標準化完了:** WASM SIMDとthreads提案がブラウザ間で完全にベースライン対応となり、Rustの`wasm-bindgen`経由で画像処理（物件写真の圧縮・リサイズ）がネイティブに近い速度で動く。フロントエンドでの重い処理をサーバーに逃さず完結できる選択肢が増えた。

- **バイナリサイズとコールドスタートの改善:** `wasm-opt`とRustのLTO/`opt-level="z"`最適化が組み合わさり、Cloudflare WorkersやFastly Compute@Edge上でのコールドスタートがミリ秒単位に短縮。エッジでの物件検索API（地域フィルタリングなど）をエッジ実行に寄せることでレイテンシを削減できる。

- **Rust以外との相互運用コストの低下:** wasm-bindgenとJS間のシリアライズオーバーヘッドが「メモリ共有ビュー」方式でほぼゼロコピーに近づき、Next.jsのRSC/クライアント境界をまたぐ重い計算（例: 物件価格シミュレーション）でWASMモジュールを呼び出すハードルが下がった。

- **開発体験の成熟:** `trunk`や`leptos`など全体的なRust WASMツールチェーンのホットリロード・デバッグ体験がJS並みに改善し、小規模チームでも段階的にWASM導入を試しやすくなっている。ただしMVP段階のsumitsugiでは、導入コストに見合うボトルネックがまだ顕在化していないため、優先度は低いと判断。

### 8. Next.js App Router patterns 2026

- **ポイント1:** Partial Prerendering（PPR）が2026年時点で安定版の主流パターンとなり、静的シェルを即座に返しつつ動的部分をSuspense境界でストリーミングする構成が標準化。TTFBとインタラクティブ性を両立できるため、`loading.tsx`や`<Suspense>`の粒度設計がパフォーマンス設計の中心課題になっている。

- **ポイント2:** Server Actionsが単なるフォーム処理を超え、キャッシュ無効化（`revalidateTag`/`revalidatePath`）と組み合わせた楽観的UI更新の標準パターンとして定着。ミューテーション後の一貫性担保のため、タグベースのキャッシュ戦略を最初から設計に組み込む必要がある。

- **ポイント3:** `use cache`ディレクティブ（Cache Components）がRSCのキャッシュ制御を宣言的に扱う主流手法になり、`fetch`単位の暗黙キャッシュより明示的で予測可能な挙動が求められるように。既存コードのキャッシュ挙動を棚卸しし、意図しない再検証・過剰キャッシュを防ぐレビューが重要。

- **ポイント4:** Route HandlersとServer Componentsの責務分離がより明確化し、外部API連携やWebhook受信はRoute Handlers、データ取得・表示はServer Componentsという住み分けが定石に。認証チェックはMiddlewareではなくデータアクセス層（DAL）で行う「データレイヤーでの認可」パターンが推奨されつつある。

- **ポイント5:** ビルド時間とエッジ/Node.jsランタイムの使い分けが最適化の焦点に。Turbopackのビルド安定化により大規模モノレポでもビルド時間が実用的な範囲に収まる一方、ランタイム選択（Edge vs Node.js）をルートごとに最適化する設計判断がパフォーマンスとコストに直結する。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Vercel Edge Functionsは実行時間・メモリ制限が緩和され、Fluid Computeモデルとの統合が進んだことで、コールドスタートを抑えつつミドルウェアだけでなくAPIルート全体をエッジに寄せる設計が現実的になっている。Next.js 16のPartial Prerenderingと組み合わせることで、静的シェルを即座に返しつつ動的部分だけEdgeでストリーミングする構成がデファクトになりつつある。

- **ポイント2:** リージョン選択の重要性が増しており、特にDB接続を伴う処理はEdge実行環境とデータベースのリージョンを揃えないとレイテンシがかえって悪化するケースが多い。sumitsugiのようにSupabase/Postgresを使う構成では、Edge Functionをどこで実行するかよりも「データに近い場所で実行する」設計判断の方が効いてくる。

- **ポイント3:** Edge Runtimeでの`fetch`キャッシュとISR/On-Demand Revalidationの組み合わせが洗練され、物件一覧のような読み取り頻度の高いページはEdge Cache + タグベースの再検証で、書き込み時（内見予約・ステータス変更など）だけピンポイントに無効化する設計がベストプラクティス化している。

- **ポイント4:** 全部をEdgeに寄せるアンチパターンへの反省も進んでおり、Node.js特有のライブラリ（重い画像処理、PDF生成など）はEdge非対応のためNode Runtimeとの使い分けが明確になった。前の住人向けの引き継ぎ資料PDF生成のような処理は、依然としてサーバーレスNode Functions側に残すのが妥当。

- **ポイント5:** Observability面では、Edge Functionsの分散トレーシングがVercelの標準機能として強化され、認証やレート制限のようなミドルウェア処理をEdgeで行う際のデバッグ容易性が向上した。認証周りをEdgeで扱う場合はこのトレーシングを前提に設計するとインシデント対応が早くなる。

### 10. TypeScript type safety patterns 2026

- **ポイント1（`satisfies`演算子の定着）:** TypeScript 4.9以降定番となった`satisfies`を型推論とリテラル型の両立に活用するパターンが2026年時点で標準化。設定オブジェクトやZodスキーマ定義で型注釈を明示せず安全性を確保できる。

- **ポイント2（Zodによる境界検証とスキーマ駆動型生成）:** APIレスポンスやフォーム入力などシステム境界では`z.infer`で型を自動導出し、ランタイム検証と静的型を単一ソースで管理する手法が主流化。手動で型定義とバリデーションを二重管理するミスを防げる。

- **ポイント3（Branded Types / Nominal Typingの活用）:** `UserId`と`ProductId`のような構造的に同じstring型を誤って混同するバグを防ぐため、ブランド型パターン（`type UserId = string & { __brand: 'UserId' }`）の採用が増加。ID系のバグはテストで検出しづらいため型レベルで防ぐ価値が高い。

- **ポイント4（TypeScript 6.x + Go移植コンパイラによる高速化）:** TypeScriptコンパイラのネイティブ移植（tsgo）により大規模モノレポでの型チェック速度が大幅改善、CIの型チェックがボトルネックになりにくくなった。厳格な型設定（`strict: true`）を維持したままスケールしやすくなっている。

- **ポイント5（Union型の網羅性チェックを徹底）:** `'draft' | 'public'`のようなstatus型を扱う際、switch文で`never`型を使った網羅性チェック（exhaustiveness check）を必ず入れる運用が定着。新しいステータス追加時にコンパイルエラーで検知でき、本プロジェクトでも標準化ルールとして守るべき箇所。
