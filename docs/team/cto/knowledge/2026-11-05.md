# CTO Knowledge - 2026-11-05

## Daily Update (2026-11-05)

### 1. Next.js performance optimization 2026

- **ポイント1:** Next.js 16ではTurbopackがデフォルトビルドツールとして完全に安定し、開発時のHMRだけでなく本番ビルドでもWebpack比で大幅な高速化が得られる。大規模な`src/app`配下のコードベースでもビルド時間を気にせず機能追加できる。
- **ポイント2:** Partial Prerendering (PPR) が実用フェーズに入り、静的シェルと動的コンテンツ（例: 物件一覧の価格・空室状況）を1ページ内で混在させられるため、SEOに強い静的配信とパーソナライズの両立がしやすい。
- **ポイント3:** `use cache`ディレクティブとCache Componentsにより、データフェッチ単位での明示的キャッシュ制御が主流になりつつある。`fetch`任せの暗黒キャッシュから脱却し、物件データやユーザー情報ごとに意図を明示できる。
- **ポイント4:** React Server Components前提のアーキテクチャが定着し、クライアントJSバンドルを最小化する設計（インタラクティブ部分だけ`'use client'`に限定）がパフォーマンス指標（LCP/INP）改善の基本戦略として重視されている。
- **ポイント5:** Core Web Vitalsの評価軸がINP中心になったことで、`useOptimistic`やServer Actionsを使った楽観的UI更新が、フォームや検索フィルターなどのインタラクション応答性を高める実装パターンとして推奨される。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPPR（Partial Prerendering）とストリーミングが標準パターンとして定着し、静的シェルを即時返しつつ動的部分をSuspense境界でストリーム配信する構成が主流になっている。レイテンシ改善とSEOの両立がしやすい。
- **ポイント2:** RSCペイロードのキャッシュ戦略（`use cache`ディレクティブやCache Componentsなど）が成熟し、サーバー側の再計算コストを抑えつつストリーミングの初期表示速度をさらに高速化できるようになっている。
- **ポイント3:** Server ActionsとRSCストリーミングの組み合わせで、フォーム送信後の差分更新がよりきめ細かくなり、クライアントJSバンドルを増やさずにインタラクティブ性を確保できる。sumitsugiの物件一覧・詳細ページのような読み取り中心のUIには特に有効。
- **ポイント4:** エラーバウンダリとストリーミングの相性が改善され、一部のコンポーネントがタイムアウト・失敗しても他の部分の表示をブロックしない設計が標準化している。本番の安定性向上に直結する。
- **ポイント5:** Bunやエッジランタイムとの統合が進み、RSCストリーミングのTTFB（Time to First Byte）がさらに短縮される傾向にある。現状のBun 1.x構成でも恩恵を受けやすく、将来的なエッジデプロイ移行の選択肢が広がる。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはTypeScriptモノレポ（フロントエンド/バックエンド共有）で型安全性を保ちつつスキーマ定義不要という利点があり、sumitsugiのようなNext.js App Router構成では今後の内部API統合に適している。REST/GraphQLのような別レイヤーのドキュメント管理が不要になる。

- **ポイント2:** GraphQLはN+1問題やオーバーフェッチ対策が年々洗練（Relay, persisted queries, federation）されているが、小〜中規模チームでは運用コストが依然高く、現状のsumitsugiのようなCRUD中心の物件管理プラットフォームにはRESTで十分というケースが多い。

- **ポイント3:** 2026年の潮流はOpenAPI 3.1 + Zodスキーマ駆動のREST API（型定義とバリデーションを一箇所で管理）で、本プロジェクトの「Zodスキーマをシステム境界で使用」という既存方針とも合致する。

- **ポイント4:** AIエージェント（LLM）がAPIを直接呼び出す機会が増え、Tool-use/MCP形式でのAPI設計（明確な説明文・冪等性・エラーメッセージの構造化）が新たな非機能要件として重要度を増している。

- **ポイント5:** エッジランタイム（Next.js 16のEdge/Node runtime選択）とAPI設計は密結合になりつつあり、レイテンシ要件に応じてtRPC/REST routeをEdgeに配置するかNodeに留めるかの判断が、今後のアーキテクチャ決定の鍵になる。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** Cloudflare Workers AIやVercel Edge Functionsなど、エッジ環境でのLLM推論・ベクトル検索が実用段階に入り、レイテンシ要件の厳しいユーザー向け機能（検索補完、レコメンド）はエッジ配置が既定路線になりつつある。

- **コールドスタート問題の実質解消:** V8 isolateベースの実行環境が成熟し、起動時間がミリ秒単位まで短縮されたことで、低頻度アクセスのAPIでもエッジ関数を躊躇なく採用できるようになった。

- **データレイヤーのエッジ化:** Cloudflare D1、Turso、PlanetScaleなどエッジ対応DBが普及し、「コンピュートはエッジ、データは中央」という分離構成から、両方をエッジに持つ構成への移行が進んでいる。sumitsugiのようなNext.jsアプリでは、物件検索のようなread-heavyな処理をエッジDBに載せる選択肢が現実的になってきた。

- **Next.js 16とのネイティブ統合:** App Routerのランタイム指定（`edge` / `nodejs`）がルートセグメント単位で柔軟になり、ページ単位で最適な実行環境を選べるようになった。全ページをエッジに寄せる必要はなく、認証や決済など状態を伴う処理はnodejsランタイムに残すハイブリッド構成が定着している。

- **コスト構造の変化に注意:** エッジ実行は従量課金の粒度が細かく、トラフィックが伸びると従来のサーバーレスより割高になるケースがある。MVPフェーズのsumitsugiでは全面エッジ化を急がず、負荷が高くレイテンシに敏感な一部機能（検索・画像配信）から段階的に検証するのが妥当。

### 5. authentication security best practices 2026

**CTO視点:** 認証セキュリティのベストプラクティス（2026年）

- **ポイント1（パスキー/FIDO2が標準化）:** フィッシング耐性のあるパスキー認証がSMS/メールOTPを置き換える主流になっており、パスワード+パスキーのハイブリッド移行が現実的な導入パス。実装時はWebAuthnのフォールバック設計（デバイス紛失時の再登録フロー）を最初から組み込む必要がある。
- **ポイント2（セッション管理の継続的検証）:** 一度ログインしたら信頼する「静的セッション」から、デバイスフィンガープリントやIPレンジ変化を監視する「継続的リスク評価」への移行が進んでいる。JWTの有効期限を短く設定し、リフレッシュトークンのローテーション＋再利用検知を必須にすべき。
- **ポイント3（最小権限・RLSの徹底）:** DB層でのRow Level Security（Supabase/Postgres等）をアプリ層の認可チェックと二重化することで、APIルートの実装ミスが即データ漏洩に直結しない構造にする。sumitsugiのような物件情報プラットフォームでは、`draft`ステータス物件へのアクセス制御がRLSレベルで保証されているか特に重要。
- **ポイント4（シークレット管理の自動ローテーション）:** 環境変数への長期シークレット埋め込みを避け、Vault/KMS等で短命トークンを発行する運用が標準化。GitHub Actionsのワークフローでは`CLAUDE_CODE_OAUTH_TOKEN`のような長期トークンもスコープ最小化と定期ローテーションの対象にすべき。
- **ポイント5（レート制限とボット対策の多層化）:** ログイン試行だけでなく、パスワードリセットやOTP検証エンドポイントにも段階的バックオフとCAPTCHA代替（Cloudflare Turnstile等）を適用し、クレデンシャルスタッフィング攻撃への耐性を上げる。

### 6. database architecture Prisma Supabase 2026

- **Prisma Postgres & Accelerate の普及:** Prisma公式のマネージドPostgres（グローバルエッジキャッシュ付き）が本格的に普及し、Supabase単体構成よりも「Prisma Postgres + Supabase Auth/Storage」のハイブリッド構成を選ぶチームが増えている。コネクションプーリング問題（サーバーレス環境でのPgBouncer管理）が大幅に軽減される点が実務上の決め手。

- **RLS（Row Level Security）とORMの統合強化:** SupabaseのRLSポリシーとPrismaのクエリ層を組み合わせる際、従来はRLSをバイパスするservice_role鍵を使いがちだったが、2026年はPrisma Client Extensionsでユーザーコンテキストを注入し、RLSを活かしたままアプリ層の型安全性を保つパターンが標準化。sumitsugiのような物件情報プラットフォームでは、`seller`/`buyer`の権限分離にRLSを使うなら、Prismaスキーマ側でもポリシー前提のクエリ設計をドキュメント化すべき。

- **Edge Runtime対応のドライバアダプタ:** Prisma Driver Adapters（`@prisma/adapter-pg`等）によりVercel EdgeやCloudflare Workersからも直接Postgresに接続できるようになり、Next.js 16のApp Router + Server Actionsでのレイテンシが改善。本プロジェクトのApp Router構成なら、Edge対応を見据えてアダプタ導入を検討する価値がある。

- **マイグレーション運用の分離:** Supabase CLIのマイグレーション機能とPrisma Migrateを併用すると競合しやすいため、2026年のベストプラクティスは「スキーマ変更はPrisma Migrateに一本化し、Supabaseダッシュボードでの直接編集を禁止する」運用ルールの徹底。チームで複数人がdraft/publicステータスのようなenum変更を行う場合、特にこのルール整備が重要。

- **型生成とZodバリデーションの連携:** Prisma SchemaからZodスキーマを自動生成するジェネレータ（`zod-prisma-types`系）が成熟し、システム境界でのバリデーション（本プロジェクトの標準要件）とDBスキーマの二重管理を回避できる。入力検証とDB型の単一ソース化により、`'draft' | 'public'`のようなunion型変更時の手戻りを防げる。

### 7. WebAssembly Rust performance 2026

- **Component Model の実用化:** WASI Preview 2とComponent Modelが2026年に主流ツールチェインへ統合され、Rustで書いたWasmモジュール間の型安全な連携（インターフェース定義によるゼロコスト抽象化）が標準化。マイクロサービス的にWasmコンポーネントを組み合わせる設計が現実的になった。

- **SIMDとMemory64の安定化:** Wasm SIMD提案が全主要ランタイムで安定版となり、Rustの`std::simd`やexplicit intrinsicsを使った画像処理・数値計算が実質ネイティブ並みの速度に近づいている。Memory64により4GB超のメモリ空間も扱えるようになり、大規模データ処理のWasm移行障壁が下がった。

- **エッジでの低レイテンシ実行:** Cloudflare Workers・Fastly Compute等でRust+Wasmのコールドスタートがミリ秒未満まで最適化され、エッジでの認証・画像変換ロジックをRustで書くパターンが定着。バイナリサイズ削減には`wasm-opt -Oz`とstrip、`wee_alloc`代替としてデフォルトアロケータ最適化の併用が実用的なベストプラクティス。

- **AOTコンパイルの進化:** WasmtimeのCraneliftバックエンド改善やWasmerのネイティブAOT化により、起動時JITコンパイルコストがほぼゼロに近づき、サーバーレス用途でのRust/Wasm採用が加速している。

- **ネイティブ相互運用の簡素化:** `wasm-bindgen`と`wit-bindgen`のメンテナンスが進み、JS↔Wasm間のデータコピーを減らすゼロコピー戦略（共有メモリ・直接ポインタ渡し）がデフォルトパターン化。フロントエンドで重い計算をRust/Wasmにオフロードする際のオーバーヘッドが大幅に減っている。

### 8. Next.js App Router patterns 2026

- **ポイント1:** Partial PrerenderingやCache Componentsの実用化が進み、静的シェルを即時表示しつつ動的部分をストリーミングする設計がデフォルト化している。ページ単位でなくコンポーネント単位でキャッシュ戦略を指定できるため、物件一覧ページのような「一部は静的・一部は動的」な構成に向いている。

- **ポイント2:** Server Actionsがフォーム処理・ミューテーションの標準パターンとして定着し、API Routesを独立して書くケースが減っている。引越し費用計算や物件ステータス更新のような単純なミューテーションはServer Actionで直接実装し、複雑な外部連携のみRoute Handlerに残す切り分けが効率的。

- **ポイント3:** `use cache`ディレクティブとRequest Memoizationの組み合わせで、DBアクセスの重複排除が自動化されつつある。データ層（`src/lib/data.ts`）での明示的なキャッシュ管理コードを削減でき、実装がシンプルになる。

- **ポイント4:** Server Componentsがデフォルトという前提が強まり、Client Componentの境界を「本当にインタラクションが必要な最小単位」まで絞る設計レビューが重要になっている。認証状態や物件データのpropsドリリングを避けるため、Context（`auth-context.tsx`）はClient Component境界内でのみ使う原則が明確化された。

- **ポイント5:** ビルド時の型エラー検出とルーティングの静的解析が強化され、動的ルート（`[id]`など）の型安全性がフレームワークレベルで保証されやすくなっている。これにより`bun run build`でのTypeScriptチェックがより信頼できるゲートになる。

### 9. Vercel Edge Functions optimization 2026

- **Fluid Computeの本格活用:** Vercelの Fluid Compute モデルが成熟し、同一インスタンス内で複数リクエストを並列処理できるようになったため、従来のEdge Functionsより低コストでコールドスタートを抑えつつ、重い処理も実行可能になっている。sumitsugiのようなAPI Routesを多用する構成では、移行による実行コスト削減効果を検証する価値がある。

- **Edge RuntimeのNode.js API対応拡大:** 2026年時点でEdge Runtimeが対応するNode.js APIが増え、以前はNode.js Runtime必須だった処理（一部の暗号化処理やファイル操作系ライブラリ）もEdgeで動かせるケースが増えている。ただし依存ライブラリの互換性は都度確認が必要。

- **Edge Configによる低レイテンシ設定配信:** フィーチャーフラグやA/Bテスト設定など頻繁に読むが低頻度で更新するデータはEdge Configに置くことで、グローバルに1桁ms台で読み出せる。物件ステータス（draft/public）の表示切替のような軽量な判定ロジックに応用できる。

- **ISR + Edge Middlewareの組み合わせ最適化:** Incremental Static RegenerationとEdge Middlewareを組み合わせ、キャッシュヒット時はEdgeで即時応答、ミス時のみOriginにフォールバックする構成がベストプラクティスとして定着。物件一覧ページなど更新頻度が低いページで有効。

- **Observability標準化:** OpenTelemetry対応がVercel標準に統合され、Edge Functionsの実行トレースをDatadog/Grafana等に直接送れるようになった。本番投入前にレイテンシのボトルネックをEdge/Origin境界で切り分けられる体制を整えておくべき。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x系の`satisfies`演算子とconst型パラメータが定着し、型推論を保ったまま厳密な制約チェックができるようになった。sumitsugiのような`'draft' | 'public'`のユニオン型管理では、`satisfies`で網羅性チェックを強制し、新しいステータス追加時の漏れを防げる。

- **ポイント2:** Zodなど実行時スキーマからの型導出（schema-first）が標準パターンとして広がり、型定義とランタイム検証の二重管理を解消できる。システム境界（API入力、フォーム送信）でZodスキーマを単一ソースとし、`z.infer`で型を導出すれば標準規約にも合致する。

- **ポイント3:** テンプレートリテラル型とBranded Types（nominal typing）が、ID混在バグの防止に実用レベルで使われ始めている。例えば`PropertyId`と`UserId`を構造的に区別できないstring型のまま扱うと、関数呼び出し時の取り違えがコンパイラで検出できない。

- **ポイント4:** `tsgo`（TypeScriptネイティブコンパイラ、Go実装）が2026年にプレビューから実用段階に入り、大規模コードベースの型チェック速度が大幅改善されている。CIのビルド時間短縮に直結するため、ビルド整合性ルール（`bun run build`必須化）の運用コストを下げる選択肢になる。

- **ポイント5:** AIコード生成が増える中、型安全性は「生成コードの自動検証レイヤー」としての役割が強まっている。Claude Codeなどが生成したコードでも、厳密な型とZod境界検証があれば、人間レビュー前に多くの誤りを機械的に弾ける。
