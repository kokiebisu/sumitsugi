# CTO Knowledge - 2026-02-23

## Daily Update (2026-02-23)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルを最小化するため、データフェッチ・重いロジックはサーバーコンポーネントに移行する。`"use client"` の使用を末端のインタラクティブ部分のみに限定することがベストプラクティス。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降で安定化したPPRにより、静的シェルと動的コンテンツをストリーミングで組み合わせ可能。TTFBを犠牲にせずパーソナライズされたページを配信できる。

- **`<Image>` と `next/font` による Core Web Vitals 最適化:** LCP改善のため `priority` prop と `sizes` 属性を正確に設定し、`next/font` によるCLS（レイアウトシフト）ゼロを確実に実現する。

- **Route Segment Config と `staleTimes` によるキャッシュ戦略の精緻化:** Next.js 15でデフォルトキャッシュ挙動が変更されたため、`revalidate` / `dynamic` / `staleTimes` を明示的に設定し、予期しない古いデータや過剰なリクエストを防ぐ。

- **Turbopack の採用とバンドル分析の習慣化:** 開発環境ではTurbopackがデフォルト化し高速HMRを実現。本番では `@next/bundle-analyzer` で定期的にバンドルサイズを可視化し、肥大化したクライアントチャンクを早期に発見・対処する。

### 2. React Server Components streaming 2026

- **ポイント1: Suspense境界による細粒度ストリーミング:** React 19以降、`<Suspense>`を入れ子にすることでコンポーネント単位の段階的ストリーミングが実用レベルに達し、TTFBを維持しつつFCPを大幅改善できる。

- **ポイント2: Server Actions × Optimistic UIの統合:** Server Actionsとストリーミングの組み合わせにより、フォーム送信等の非同期操作でサーバーの処理完了を待たずに楽観的更新を即反映するパターンが標準化されつつある。

- **ポイント3: PPR（Partial Prerendering）の本格採用:** Next.js App RouterのPPRが安定化し、静的シェルを即座に配信しつつ動的コンテンツをストリームで流す「静的＋動的のハイブリッド」が最もパフォーマンス効率の高いアーキテクチャとして台頭している。

- **ポイント4: キャッシュ戦略の複雑化への対応:** RSCストリーミング環境ではルートレベル・コンポーネントレベル・リクエストレベルの複数キャッシュ層が交差するため、`cache()`・`revalidateTag()`・`unstable_cache`の使い分けを明示的に設計しないとキャッシュ汚染が起きやすい。

- **ポイント5: エッジランタイムとの相性:** CloudflareやVercel Edgeでのストリーミングレスポンスが成熟し、地理的に分散したRSCストリーミングが現実的になった一方、Node.js専用APIへの依存がエッジ移行のボトルネックになるため、依存ライブラリのランタイム互換性チェックが設計初期から必須。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全APIの標準化:** TypeScript採用プロジェクトでtRPCが急速に普及し、クライアント・サーバー間のエンドツーエンド型安全性がベストプラクティスとして定着。スキーマ定義の重複を排除できるため、Next.js / Remix等のフルスタックフレームワークとの相性が特に良い。

- **GraphQLの選択基準の明確化:** 「とりあえずGraphQL」から「複数クライアント・複雑なデータグラフが必要な場合に限る」へと評価が成熟。BFFパターンやfederated graphでマイクロサービスを束ねるユースケースでは依然として強力だが、小規模プロダクトではオーバーエンジニアリングになりやすい。

- **REST + OpenAPIの復権:** Hono・Elysia等の軽量フレームワークがOpenAPIスキーマ自動生成とバリデーションを統合し、型安全なRESTが再評価されている。特にサードパーティ公開APIやモバイルアプリ向けでは、GraphQLよりキャッシュ・CDN最適化が容易なRESTが選ばれるケースが増加。

- **エッジランタイム対応がAPI設計の制約に:** Cloudflare Workers・Vercel Edge等のエッジ実行環境ではNode.js固有APIが使えないため、ランタイム非依存の設計（Web標準APIのみ使用）が必須。tRPCやHonoはこれを意識した設計になっており、エッジ対応が選定基準の一つになっている。

- **AIエージェント統合を前提としたAPI設計:** MCPやOpenAPIベースのツール公開が普及し、「人間だけでなくAIエージェントが呼び出すAPI」を意識した設計が重要に。明確なセマンティクス・冪等性・適切なエラーレスポンスの重要性が再認識されており、自己記述的なスキーマ（OpenAPI/GraphQL introspection）の価値が高まっている。

### 4. serverless edge computing 2026

- **エッジでのAI推論の主流化:** WebAssembly（WASM）とONNX Runtimeの成熟により、軽量LLMやエンベディングモデルをエッジで直接実行するケースが急増。Cloudflare Workers AI・Vercel Edge Functionsがそのインフラを担う。

- **コールドスタート問題の実質的解消:** V8 Isolatesベースのランタイムが普及し、コンテナ型より100倍以上高速な初期化を実現。ただし、Node.js互換性の制限（`fs`/`net`モジュール等）が依然としてアーキテクチャ上の制約になる。

- **エッジDB・ストレージの台頭:** Cloudflare D1、Turso、Neon（サーバーレスPostgres）などがエッジに近いリージョンでSQLを提供。レイテンシを最小化しつつデータ整合性を保つ「データロカリティ」設計が必須スキルになりつつある。

- **オブザーバビリティの難度上昇:** 分散エッジ環境では従来のAPMが機能しにくく、OpenTelemetryのエッジ対応とサンプリング戦略の設計が重要。ログ集約コストがバカにならないため、構造化ログ＋テールサンプリングが現実解。

- **ベンダーロックインリスクの再評価:** WinterCGによるランタイム標準化が進むが、各プラットフォーム固有のバインディング（KV・R2等）への依存はポータビリティを下げる。抽象レイヤーを薄く設計し、ビジネスロジックをプラットフォーム非依存に保つことが長期的な技術負債回避の鍵。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** FIDO2/WebAuthnベースのパスキーがパスワード認証を急速に置き換えており、フィッシング耐性とUX向上を両立できる。2026年時点でGoogle・Apple・Microsoftが揃って標準サポートしており、新規実装ではパスキーをデフォルトにすべき。

- **継続的認証（Continuous Authentication）の台頭:** ログイン時点だけでなく、セッション中の行動パターン（操作リズム・位置情報・デバイス状態）をリアルタイム評価するゼロトラストモデルが主流化。特権操作前の再認証と組み合わせることでセッションハイジャックリスクを大幅に低減できる。

- **AIを使った認証攻撃への対策強化:** ディープフェイク音声・顔認証バイパス・LLMを使ったソーシャルエンジニアリングが高度化しており、生体認証単体への過信は危険。ライブネス検知（Liveness Detection）と多要素の組み合わせが必須。

- **トークン管理の厳格化（短命トークン＋DPoP）:** JWTの有効期限を極力短くし（15分以下）、Demonstrating Proof-of-Possession（DPoP）でトークン窃取攻撃を無効化するパターンが標準化。リフレッシュトークンはローテーション必須、かつデバイス紐づけを推奨。

- **サプライチェーン経由の認証ライブラリ汚染リスク:** npmやPyPI経由の認証関連パッケージへのマルウェア混入事例が増加。依存ライブラリのSBOM管理、署名検証（Sigstore）、定期的な脆弱性スキャンをCI/CDに組み込むことがアーキテクチャレベルの必須要件になっている。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x + Supabase の統合深化:** Prisma 6では`prisma generate --sql`による型安全なRaw SQLが強化され、SupabaseのRLSポリシーとの共存がより実用的になった。ORM層とDB層の責務分離が明確になりつつある。

- **Edge Runtime対応の本格化:** Prisma AccelerateとSupabase Edge Functionsの組み合わせで、Cloudflare WorkersやVercel Edgeでのゼロコールドスタートが実現可能に。コネクションプーリングをクライアントサイドで意識しなくて済む設計が標準化している。

- **Row Level Security (RLS) の設計パターン成熟:** Supabase RPCとRLSを活用した「DBレベルでの認可」が普及し、アプリ層での権限チェックの二重実装を避けるアーキテクチャが推奨されるようになった。Prismaのミドルウェアと組み合わせたオーディットログも実装しやすい。

- **リアルタイム + ベクター検索の融合:** Supabase Realtimeとpgvector拡張を組み合わせたRAGパイプラインが実用段階に入り、Prismaのスキーマでベクター型を管理するパターンが確立されつつある。AIチャット系機能の基盤として採用事例が急増。

- **マルチテナント設計の標準化:** Row-levelテナント分離（RLS活用）とSchema-levelテナント分離（Prismaの`datasource`動的切り替え）の使い分けが明確化。小〜中規模はRLS、コンプライアンス要件の強い大規模はスキーマ分離という指針が業界標準になりつつある。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の実用化:** WebAssembly System Interface v2のComponent Modelが2025年末に安定化し、RustからWasmへのコンパイル時のABI境界問題が大幅に解消。サービス間のポータブルなバイナリ配布が現実的になった。

- **SIMD・マルチスレッド拡張の普及:** WebAssembly SIMDとShared Memoryスレッドがすべての主要ブラウザ・ランタイムで安定稼働し、RustのSIMD intrinsicsを活用した画像処理・ML推論ワークロードでネイティブ比85-95%の性能を達成するケースが増加。

- **Wasmtime・WasmEdgeの起動時間改善:** AOT（Ahead-of-Time）コンパイルとプロファイルガイド最適化（PGO）により、コールドスタートが1ms以下に。サーバーレス・エッジコンピューティングでのRust/Wasm採用のブロッカーがほぼ解消された。

- **メモリ管理の進化（GCプロポーザル）:** WasmのGC proposalが主流ランタイムに実装され、Rustは引き続きゼロコスト抽象化で線形メモリを直接操作できる優位性を維持。他言語と混在するポリグロット環境でもRustコンポーネントが性能のボトルネックになりにくい。

- **ツールチェーンの成熟（`wasm-bindgen` / `cargo-component`）:** `cargo-component`がCargo公式ワークフローに統合されつつあり、Rust→Wasmのビルドパイプラインが大幅に簡素化。プロダクション採用のコストが下がり、Next.jsのEdge RuntimeへのRustロジック埋め込みが標準的なパターンとなりつつある。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** クライアントバンドルを最小化するため、デフォルトでServer Componentsを採用し、インタラクティブな部分のみ`'use client'`境界を設ける。2026年はこの分離がパフォーマンスの決定的な差を生む。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的コンテンツを同一ルートで混在させるPPRが安定化し、TTFBとFCPを両立できる。`experimental.ppr`から正式APIへの移行タイミングを見極めることが重要。

- **`use cache` ディレクティブによるきめ細かいキャッシュ制御:** Next.js 15以降、関数・コンポーネント単位でキャッシュ戦略を宣言できる。`revalidate`や`tags`との組み合わせでISRより柔軟なデータ鮮度管理が可能になる。

- **Server Actions の設計原則:** フォーム送信・ミューテーション処理をServer Actionsに集約することで、APIルート数を削減できるが、入力バリデーション（Zod）とエラーハンドリングを必ずサーバー側で実装すること。クライアントへのエラー情報漏洩に注意。

- **Streaming と Suspense の階層設計:** `loading.tsx`と`<Suspense>`を意図的に配置し、ウォーターフォールを避けた並列データフェッチを実現する。`Promise.all`を使った並列fetch + 個別Suspense境界がUX最適化の定石パターン。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge Runtimeの選択的活用:** 全APIをEdgeに移行するのではなく、認証チェック・A/Bテスト・地理的ルーティングなど低レイテンシが必要な処理に絞って使うのが2026年のベストプラクティス。Node.js Runtimeとの使い分けがパフォーマンス最適化の鍵。

- **ポイント2: Cold Start問題の継続的改善:** Vercelは2025-2026年にかけてEdge Functionsのコールドスタートをほぼゼロに近づけているが、バンドルサイズ管理（1MB以下推奨）は依然重要。`next/dynamic`と`import()`による遅延インポートでバンドルを削減すること。

- **ポイント3: Streaming ResponseとPartial Prerendering (PPR)の組み合わせ:** Next.js 15以降でPPRとEdge Functionsを組み合わせることで、静的シェルを即座に配信しつつ動的部分をEdgeでストリーミング。TTFB（Time to First Byte）が劇的に改善される。

- **ポイント4: KV・R2等のEdgeネイティブストレージ活用:** Vercel KV（Redis互換）やCloudflare R2との組み合わせで、Edgeからデータベースへのラウンドトリップを回避。セッション管理・レートリミット・キャッシュ層をEdgeで完結させる設計が主流に。

- **ポイント5: Observabilityの強化:** Edge Functionsは従来のAPMツールとの統合が難しかったが、Vercel Analytics・OpenTelemetry対応が進化。分散トレーシングでEdge→Origin間のボトルネックを特定し、継続的な最適化サイクルを回すことが競争優位につながる。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `type UserId = string & { readonly __brand: 'UserId' }` のようなBranded Types（Nominal Typing）が実務での採用が広まり、プリミティブ型の混同バグを型レベルで防ぐパターンが定着しつつある。

- **`satisfies` 演算子の積極活用:** TypeScript 4.9で導入された `satisfies` が2026年時点では標準的な型安全パターンとして普及し、型推論を保ちながら型チェックを強制できるため、`as` キャストの代替として推奨される。

- **Zod + tRPC による境界型安全の徹底:** API境界・フォーム・外部データにはZodスキーマから型を生成し、ランタイム検証と静的型を一元管理する手法がフルスタック開発の事実上の標準になっている。

- **Template Literal Types の実用化:** `type EventName = `on${Capitalize<string>}`` のようなTemplate Literal Typesが文字列操作の型安全に広く活用され、特にイベント名・ルートパス・CSS変数の型定義で効果を発揮する。

- **Exact Types / `NoInfer` ユーティリティの活用:** TypeScript 5.4で導入された `NoInfer<T>` を使い、型引数の意図しない推論を防ぐことで、ジェネリック関数のAPIをより明示的・安全に設計できるようになっている。
