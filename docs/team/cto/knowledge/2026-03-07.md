# CTO Knowledge - 2026-03-07

## Daily Update (2026-03-07)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを劇的に削減できる。`'use client'`は本当に必要な葉コンポーネントのみに限定し、データフェッチはサーバー側で完結させる設計が2026年の基本。

- **Partial Prerendering (PPR) の本番投入:** 静的シェルと動的コンテンツを1リクエストで配信するPPRがStable化。`next.config`で`ppr: true`を有効化するだけで、TTFBを維持しつつ動的データを扱える。

- **`unstable_cache` / `use cache` によるきめ細かいキャッシュ制御:** `fetch`単位のキャッシュから関数・コンポーネント単位へ移行。`revalidateTag`で外科的なキャッシュ無効化を行い、過剰な再レンダリングを防ぐ。

- **Turbopack の実用化:** Next.js 15+でTurbopackがデフォルト化。大規模コードベースでのHMRが数十倍高速になり、開発体験とCI速度の両方が改善される。

- **Core Web Vitals への継続投資（特にINP）:** Interaction to Next Paint (INP) がLCP・CLSと並ぶ重要指標に。`useTransition`・`startTransition`でUIブロッキングを回避し、重い処理はServer Actionsに移譲することが実質必須。

### 2. React Server Components streaming 2026

- **Suspense境界とStreaming SSRの成熟:** 2026年時点でNext.js App RouterのRSC streamingは実運用レベルに達しており、`<Suspense>`境界を細粒度で配置することでFCP（First Contentful Paint）とTTFB（Time to First Byte）を大幅に改善できる。重いデータフェッチコンポーネントを境界で分割し、シェルを先行配信する設計が標準化されている。

- **Server Actionsとの統合による往復削減:** Server ActionsがRSC streamingと組み合わさることで、フォーム送信後の再レンダリングもストリーミングで返せるようになり、クライアントのJS量を抑えながらインタラクティビティを実現できる。APIルートを介さない直接的なサーバー関数呼び出しがアーキテクチャを単純化する。

- **PPR（Partial Prerendering）の実用化:** Vercelが推進するPPRにより、静的シェルをエッジでキャッシュしつつ動的部分だけをストリーミングする構成が可能になった。CDNヒット率とリアルタイム性を両立できるため、コンテンツ重視のアプリに特に有効。

- **キャッシュ戦略の再設計が必須:** `fetch`のキャッシュオプション（`force-cache` / `no-store` / `revalidate`）とストリーミングの組み合わせは複雑なバグを生みやすい。コンポーネント単位でキャッシュ境界を明示し、`unstable_cache`や`React.cache`でメモ化を制御する設計レビューを必ずチームで実施すること。

- **DevToolsとObservabilityの整備が課題:** Streamingにより従来のウォーターフォール型プロファイリングが通用しなくなるため、OpenTelemetryベースのサーバーサイドトレーシングとVercel Speed Insights / Datadog APMの導入が実運用上の前提条件になりつつある。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの主流化:** 2026年現在、TypeScriptフルスタック環境ではtRPCがデファクトスタンダードになりつつある。スキーマ定義不要で型安全なend-to-endが実現でき、Next.js App RouterとのServer Actions統合も進んでいる。

- **GraphQLの用途特化:** GraphQLはBFF（Backend for Frontend）パターンやマルチクライアント対応が必要な場面に絞られ、小中規模プロジェクトでのオーバーエンジニアリングという批判が定着した。Relay/Apollo Clientの学習コストに見合うユースケースを慎重に判断すること。

- **REST + OpenAPI の再評価:** AIコード生成ツールとの相性が良いことから、OpenAPI 3.1ベースのREST APIが見直されている。`zod-to-openapi`や`ts-rest`などで型安全性を保ちながらREST互換を維持するアプローチが実用的。

- **Server Actions vs API Routes:** Next.js App RouterのServer Actionsが成熟し、フォーム・ミューテーション系処理ではAPI Routes不要のパターンが普及。ただし外部クライアント連携が必要な場合はAPIエンドポイントを別途設計する二層構造が推奨される。

- **エッジランタイム対応:** Cloudflare Workers / Vercel Edgeへのデプロイを前提とするなら、WebSocket依存のGraphQL Subscriptionより、Server-Sent Events（SSE）またはポーリングベース設計の方が運用コストが低い。プロトコル選定にランタイム制約を必ず含めること。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジの標準ランタイムに:** V8アイソレーションに代わりWasmベースのサンドボックスが主流となり、コールドスタートがほぼゼロになった。Next.jsのEdge Runtimeも`runtime: 'edge'`でWasm対応が進んでいる。

- **AIインファレンスのエッジ分散が加速:** LLMの小型化（1B〜7Bパラメータ）により、Cloudflare WorkersやVercel Edge FunctionsでのオンデバイスRAGが現実的になり、レイテンシとプライバシーを両立できる。

- **ステートフルエッジの台頭:** 従来のステートレス前提が崩れ、Cloudflare Durable ObjectsやVercel KVのようなエッジ近接ストレージが成熟。セッション管理や分散ロックをエッジで完結できる。

- **エッジ・コア間のデータ整合性が新たな複雑性:** グローバル分散による結果整合性（Eventual Consistency）の扱いが設計上のボトルネックに。CRDTベースのデータ構造採用やリージョン固定戦略の選択が重要な設計判断になっている。

- **オブザーバビリティがエッジのアキレス腱:** 分散トレーシングがエッジ→オリジン間で断絶しやすく、OTel（OpenTelemetry）の対応が不完全なプロバイダーも残る。本番投入前にトレーシング戦略を確立しないと障害調査が困難になる。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準化:** FIDO2/WebAuthn ベースのパスキーが2026年の認証標準となりつつあり、フィッシング耐性が高くパスワードレス体験を実現できる。Next.js環境では `@simplewebauthn` ライブラリが実装の起点として有力。

- **セッション管理の短命化とローテーション:** JWTの有効期限は15分以内に抑え、リフレッシュトークンのローテーション（Refresh Token Rotation）を必須とする。トークン漏洩時の被害範囲を最小化するゼロトラスト設計が前提。

- **デバイスフィンガープリントと異常検知の組み合わせ:** 正規ユーザーでも不審なデバイス・地域からのアクセスをリスクスコアリングで評価し、追加認証をトリガーする適応型認証（Adaptive MFA）が主流になっている。

- **サプライチェーンリスクとしての認証ライブラリ管理:** 2025年以降、OSSの認証ライブラリへの攻撃が増加。`bun audit` による定期監査と、依存ライブラリのピン留め（exact versioning）を CI パイプラインに組み込むことが必須。

- **ログとオブザーバビリティの分離:** 認証イベント（ログイン成功/失敗/MFAチャレンジ）は通常ログから分離し、専用のセキュリティログとして SIEM に転送する。エラーレスポンスに内部情報を含めない設計は引き続き基本原則。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x の Edge Runtime 対応成熟:** Prisma が Cloudflare Workers / Vercel Edge Functions に完全対応し、サーバーレス環境でのコネクションプーリング問題が `@prisma/adapter-pg` + PgBouncer で解消。Supabase の Supavisor と組み合わせることで接続数の爆発的増加を抑制できる。

- **Supabase の Row Level Security (RLS) が設計の中核に:** 2026 年時点では RLS をアプリ層ではなく DB 層で担保するアーキテクチャが主流。Prisma からアクセスする際も `SET LOCAL role` でユーザーコンテキストを渡すパターンが定着しており、サービス層のバグによるデータ漏洩リスクを根本から削減できる。

- **Supabase Realtime + Prisma の二重管理問題:** リアルタイム機能は Supabase の Postgres Changes を直接使い、CRUD は Prisma 経由という分離アーキテクチャが実用的。スキーマ定義は `prisma.schema` を Single Source of Truth にし、Supabase マイグレーションと同期するパイプラインを CI に組み込むことが重要。

- **型安全なクエリビルダーとしての Prisma の地位確立:** Drizzle ORM との競合が続くが、Prisma は `$extends` によるクライアント拡張と TypeScript 型推論の完成度で優位。パフォーマンスクリティカルな箇所のみ `$queryRaw` で生 SQL を使うハイブリッド戦略が現実解。

- **Supabase Vector (pgvector) と AI 統合:** pgvector 拡張が Supabase に標準搭載され、RAG（Retrieval-Augmented Generation）パイプラインを既存の Postgres インフラ内で完結できる。Prisma 側は `Unsupported("vector")` 型でマッピングし、ベクトル検索クエリのみ raw SQL で記述するパターンが 2026 年の標準アプローチ。

### 7. WebAssembly Rust performance 2026

- **Component Model の成熟:** WebAssembly Component Model (WASM CM) が2026年に本格普及し、RustコンポーネントをJS/Python/他言語と型安全にインターオペレートできるようになった。`cargo component` ワークフローが標準化され、ビルドパイプラインへの統合が大幅に簡略化。

- **WASI Preview 2 による本番利用の拡大:** WASI Preview 2（ソケット・ファイルシステム・HTTP）の安定化により、RustのWASMをサーバーサイドで実用的に使えるシーンが増加。Cloudflare Workers・Fastly Compute・WasmEdge などのエッジランタイムでの採用が加速。

- **パフォーマンスギャップの縮小:** SIMD命令サポートの強化とJITコンパイラの改善（特にWasmtime v30+）により、ネイティブRustとの性能差が多くのユースケースで5〜15%以内に。暗号処理・画像処理・パーサー系では実質同等の性能が出せるケースも。

- **Rustツールチェーンの開発体験向上:** `wasm-bindgen` と `wasm-pack` の後継として `wit-bindgen` が主流化し、型定義から自動生成されるバインディングで開発効率が向上。`trunk` によるホットリロード開発も安定し、フロントエンドRust（Leptos/Dioxus）の実用性が増した。

- **メモリモデルの制約が依然ボトルネック:** 線形メモリモデルとGCインターフェースの限界により、大量のJSオブジェクトとやり取りするユースケースでは依然としてオーバーヘッドが発生。**設計原則として「WASMとJSの境界を最小化し、バッチ処理を優先する」アーキテクチャが不可欠。**

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点では、データフェッチはServer Componentsで完結させ、`'use client'`はインタラクティブな最小単位にのみ付与するのがベストプラクティス。クライアントバンドルを最小化することでCore Web Vitalsが劇的に改善する。

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降でStableになったPPRにより、同一ページ内で静的シェルと動的コンテンツを混在させることが可能。`<Suspense>`境界を戦略的に配置することがアーキテクチャ設計の核心になった。

- **Server Actions でAPI Routes を置き換える:** フォーム送信・ミューテーション処理はServer Actionsに集約し、`/api/`ルートを極力減らす方向が主流。型安全性が保たれ、ボイラープレートも削減できる。

- **`use cache` ディレクティブによる細粒度キャッシュ:** `fetch`キャッシュではなく、関数・コンポーネント単位で`use cache`を宣言するモデルに移行。`cacheTag`・`cacheLife`でキャッシュの無効化戦略を明示的にコントロールできる。

- **並列ルート・インターセプトルートでモーダルUXを設計:** `@modal`スロットとインターセプトルート`(..)`の組み合わせにより、URL駆動のモーダル（シェアラブル・ブラウザバック対応）が標準パターンに。Airbnb風UIを構築するsumitsugiには特に有効なアプローチ。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの成熟と標準化:** Web標準API（Fetch, Streams, WebCrypto）への完全準拠が進み、Node.js依存コードをEdgeに移植する際の互換性問題が大幅に減少。ただし依存ライブラリのEdge対応確認は依然として必須。

- **Cold Startの事実上の解消:** 2025〜2026年にかけてVercelはEdge Functionsのインスタンス管理を改善し、p99レイテンシが安定。従来のサーバーレスより有利だが、大きなbundleサイズ（>1MB）は依然としてリスク — `import`の絞り込みとtree-shakingが最重要最適化施策。

- **Partial Prerendering（PPR）との組み合わせが主戦場:** Next.js 15以降でPPRが安定し、静的シェル＋動的EdgeストリーミングのハイブリッドがISRに代わるデフォルト設計になりつつある。キャッシュ戦略をEdge層で明示的にコントロールする設計が求められる。

- **地理的ルーティングとデータローカリゼーション:** GDPR・個人情報保護法対応でデータ処理地域の制御が強く求められており、Edge Configと組み合わせたリージョン別ロジック分岐が実用的な解。DBへのラウンドトリップを避けるためEdge Configを「軽量KVキャッシュ」として活用するパターンが定番化。

- **可観測性の整備が前提条件:** Edgeはサーバーログが取りにくいため、OpenTelemetry対応の分散トレーシング（Axiom, Baselime等）をデプロイ前に必ず組み込む。エラーの無音死を防ぐことが運用品質の分水嶺になっている。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded Typesが標準的になり、プリミティブ型の混同バグをコンパイル時に防ぐ手法が主流に。

- **`satisfies` 演算子の活用拡大:** TypeScript 4.9で導入された `satisfies` が2026年には設計パターンとして定着し、型推論を保ちながら型チェックを強制できるため、`as` キャストの排除に有効。

- **Zod + tRPC によるEnd-to-End型安全:** APIスキーマをZodで定義しtRPCで共有することで、フロントエンド〜バックエンド間の型ズレをランタイム前に検出する設計が事実上の標準に。

- **Template Literal Types の高度活用:** `type Route = '/users' | '/users/${string}'` のようなテンプレートリテラル型がルーティングやイベント名の型付けに使われ、文字列ベースAPIの安全性が大幅向上。

- **`noUncheckedIndexedAccess` の強制:** `tsconfig` で `noUncheckedIndexedAccess: true` を有効化し、配列・オブジェクトアクセス時の `undefined` を型レベルで強制ハンドリングするプロジェクトが増加——これが未設定のコードベースは技術的負債と見なされる傾向。
