# CTO Knowledge - 2026-10-24

## Daily Update (2026-10-24)

### 1. Next.js performance optimization 2026

- **Partial Prerenderingの本格採用:** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分のみストリーミングすることで、TTFBとLCPを大幅に改善できる。既存の`getStaticProps`的な全体ISRから、ページ単位で静的/動的を混在させる設計への移行が鍵。

- **React Server Componentsの境界最適化:** `"use client"`境界を不必要に広げるとJSバンドルが肥大化するため、インタラクティブな葉コンポーネントのみをクライアント化し、データ取得はServer Componentsに留める設計が重要。sumitsugiでも`listing/`配下のカードやフィルタUIで境界の見直しが効果的。

- **`next/image`とフォント最適化の自動化:** AVIF優先配信・`next/font`による自動セルフホスティングでCLS/LCPが改善するが、物件写真のような可変枚数ギャラリーでは`priority`指定とサイズヒントの精度が実効性を左右する。

- **Turbopackによるビルド・開発体験の高速化:** Next.js 16でTurbopackがデフォルト化され、開発時のHMRとプロダクションビルド時間が短縮。CIの`bun run build`時間短縮にも直結するため、ローンチ前のパイプライン最適化と相性が良い。

- **キャッシュ戦略の明示化（`use cache`/Cache Components）:** 暗黙的なデータキャッシュから明示的な`use cache`ディレクティブへの移行により、どのデータがどの粒度でキャッシュされるかをコードレベルで制御可能になり、物件検索のような動的データと静的コンテンツが混在するページでの予期しないキャッシュ事故を防ぎやすくなる。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPartial Prerendering (PPR)とRSC streamingの統合が進み、静的シェルを即時配信しつつ動的部分のみSuspense境界でストリーミングする構成が標準化している。初期表示速度(TTFB/LCP)を落とさずに動的データを扱えるのが実用上の強み。

- **ポイント2:** `loading.tsx`やネストしたSuspense境界の粒度設計がパフォーマンスの肝になっており、1つの大きなSuspense境界に全データ取得をまとめると「ウォーターフォール待ち」が発生しやすい。物件一覧→詳細→レビューのような段階的な情報粒度に合わせて境界を細かく分割すべき。

- **ポイント3:** Server Actionsとストリーミングの組み合わせで、フォーム送信後のUI更新をクライアントJSなしで段階的に反映できるようになり、認証やお問い合わせフォームなどのJSバンドルサイズ削減に直結する。

- **ポイント4:** ストリーミングSSRはキャッシュ戦略（CDNエッジでの部分キャッシュ）との相性がまだ発展途上で、個人情報を含む動的部分を誤ってエッジキャッシュしないよう`cache: 'no-store'`やセグメント単位のrevalidate設定を明示する必要がある。物件データのような公開情報と、ユーザー固有データを扱う部分でキャッシュポリシーを分離する設計が重要。

- **ポイント5:** エラーバウンダリ(`error.tsx`)とストリーミングの組み合わせでは、ストリーム中に発生した例外が後続チャンクの表示をブロックしないよう、コンポーネント単位でtry/catchとフォールバックUIを用意するのがベストプラクティスとして定着してきている。

### 3. API design REST GraphQL tRPC 2026

- **RESTは依然主流、だが"契約"重視に進化:** OpenAPI 3.1+JSON Schemaでの型定義が標準化し、スキーマファーストでクライアント生成（openapi-typescript等）が当たり前になっている。手書きのAPI仕様書は技術的負債とみなされる傾向。

- **tRPCはフルスタックTypeScriptの第一選択肢:** フロントエンドとバックエンドを同一モノレポ・同一言語で書く場合、tRPCはスキーマ不要で型安全性が最強。Next.jsのApp Router + Server Actionsとの組み合わせで、社内向け・単一クライアントのAPIにはtRPCかServer Actions直接呼び出しが主流になりつつある。

- **GraphQLは「複数クライアント・複雑なデータグラフ」に限定利用:** モバイル・Web・サードパーティ向けに同じデータを異なる形で提供する必要がある場合のみGraphQLの過剰フェッチ防止が活きる。単純なCRUDアプリにGraphQLを導入するのはオーバーエンジニアリングという認識が業界で定着した。

- **sumitsugiへの実用的な示唆:** 現状のNext.js App Router構成なら、物件検索・引っ越し手続きなどの内部APIはServer Actions/tRPCで型安全に、将来パートナー企業向けに外部公開APIを出すならRESTこそが互換性・ドキュメント性で有利。GraphQLを今から導入する必要性は低い。

- **AI/LLMエージェント対応がAPI設計の新基準:** 2026年はAIエージェントがAPIを直接呼ぶケースが増え、エンドポイントの意味が自己記述的（記述的なエラーメッセージ、冗長だが明確なフィールド名）であることが人間向けAPI設計以上に重視されている。将来AIエージェント経由の物件検索連携を想定するなら、意味の明確なREST設計を今のうちに意識すべき。

### 4. serverless edge computing 2026

**セラレスエッジコンピューティング 2026 — CTO視点**

- **ポイント1:** エッジでの推論実行が標準化しつつあり、軽量LLM（量子化・蒸留モデル）をCloudflare WorkersやVercel Edge Functionsで直接実行できるようになったため、レイテンシ要件の厳しいUX（検索補完・リアルタイム翻訳）をオリジンサーバー往復なしで実現できる。sumitsugiのような物件検索UXでも、検索フィルタや地図描画の初期応答をエッジ側で捌く余地がある。

- **ポイント2:** コールドスタート問題がV8 isolateベースのランタイム（Workers、Deno Deploy）でほぼ解消され、Node.js互換APIのサポートも進んだことで、Next.jsのMiddlewareやRoute Handlersをエッジにデプロイしやすくなった。ただしDB接続はエッジ非対応のドライバが多いため、PrismaなどはHTTPベースの接続プーラー（Neon, PlanetScaleなど）経由が前提になる点に注意が必要。

- **ポイント3:** エッジKV/エッジSQLite（Cloudflare D1, Turso）が本番運用レベルに成熟し、グローバル分散読み取りが低コストになった一方、書き込みの強一貫性はまだトレードオフが残る。物件情報のような「読み取り多・書き込み少」なデータはエッジキャッシュ戦略（stale-while-revalidate）との相性が良い。

- **ポイント4:** エッジでの課金モデルがリクエスト数＋CPU時間ベースに収斂し、トラフィックが急増するローンチ直後のコスト予測がしやすくなった。ベータローンチ時のバーストトラフィックに対し、オリジンサーバーより障害耐性とコスト効率の両方で有利。

- **ポイント5:** セキュリティ面ではエッジでのWAF/Bot管理が標準装備化し、OWASP Top 10対策（CSRF, XSS防御）をCDN層で前段処理できるため、アプリケーション層の実装負荷が軽減される。ただし機密情報（APIキー等）をエッジ変数に置く際は、環境ごとのスコープ管理を誤らないよう運用ルールの整備が必須。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への移行加速:** パスワードレス認証（WebAuthn/パスキー）が主流になり、フィッシング耐性のある認証がデフォルト選択肢に。実装コストは下がったが、デバイス間同期やリカバリーフローの設計が新たな課題。

- **AI駆動の不正検知と適応型認証:** 行動バイオメトリクスやリスクベース認証（ログイン時のデバイス・位置・行動パターン分析）により、リスクが高い場合のみ追加認証を要求する仕組みが標準化。ユーザー体験と安全性のバランスが取りやすくなった。

- **トークンのライフサイクル管理の厳格化:** 短命アクセストークン＋リフレッシュトークンローテーション、そしてトークンバインディング（デバイス固有化）により、トークン漏洩時の被害範囲を最小化する設計が必須に。

- **サプライチェーン・MCP/AIエージェント認証の新リスク:** AIエージェントやMCPサーバーが人間の代わりに認証情報を扱うケースが増え、エージェント専用のスコープ制限された認可（OAuth 2.1 + 細粒度スコープ）が重要なセキュリティ境界になっている。

- **ゼロトラスト原則の実装徹底:** セッション確立後も継続的に検証する「常時再認証」モデルが普及し、長期セッションを信頼し続けるリスクを減らすため、重要操作（決済・個人情報変更）では再認証を都度要求する設計が推奨される。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMの型安全性とSupabaseのマネージドPostgres:** Prisma SchemaからTypeScript型を自動生成することでランタイムエラーを大幅に減らせる一方、Supabaseはレプリケーション・バックアップ・RLS（行レベルセキュリティ）を標準提供するため、スキーマ変更時はPrisma Migrateの差分適用前に必ずステージング環境で検証する運用が必須です。

- **Row Level Security (RLS) とORMの責務分離:** PrismaはRLSを直接扱わないため、Supabase側でRLSポリシーを設計し、アプリ層の認可ロジックと二重管理にならないよう「DBはデータ整合性、アプリは業務ロジック」の境界を明確にすることが2026年のベストプラクティスです。

- **Connection Poolingの最適化:** サーバーレス環境（Vercel等）からPrisma経由でSupabaseに接続する場合、PgBouncer（Supabaseの`pooler`エンドポイント）の利用が必須で、直接接続するとコネクション枯渇による本番障害リスクが高まります。

- **Edge Functions + Prisma Accelerateのキャッシュ戦略:** 読み取り頻度の高いクエリ（物件一覧など）はPrisma Accelerateのグローバルキャッシュを活用することで、Supabaseへの負荷を下げつつレイテンシを改善できますが、キャッシュ無効化のタイミング設計を誤るとステータス変更（draft→public）の反映遅延につながるため注意が必要です。

- **マイグレーションの可逆性:** `src/lib/data.ts`のような`status: 'draft' | 'public'`といったUnion型をスキーマ変更する際は、Prisma Migrateの破壊的変更（カラム削除・型変更）を避け、追加→移行→削除の3段階デプロイで本番データ損失を防ぐ体制が重要です。

### 7. WebAssembly Rust performance 2026

- **ポイント1（Component Model の普及）:** WASI Preview 2とComponent Modelの標準化が進み、RustクレートをWasmコンポーネントとして配布・合成できるようになった。結果、Wasmモジュール単位での依存管理やバージョニングが実用レベルに達し、マイクロフロントエンド的な構成がバックエンドでも採用しやすくなっている。
- **ポイント2（SIMD・スレッドの本番活用）:** `wasm32-wasip1-threads`やSIMD128が主要ブラウザ・ランタイム（Wasmtime, Wasmer）で安定サポートされ、画像処理・暗号化・ML推論など計算負荷の高い処理をRust+Wasmでネイティブ比80-90%台の性能で実行できるケースが増えた。本プロジェクトでPDF生成や物件画像処理を高速化する余地がある。
- **ポイント3（サーバーサイドWasmの台頭）:** Fastly Compute、Cloudflare Workers、Fermyonなどのedge runtimeがRust+Wasmを第一級citizenとして扱い、コールドスタートがミリ秒未満になったことでサーバーレス関数の選択肢としてNode.jsを置き換える事例が増加。レイテンシが重要なAPI（検索・価格計算）で検討余地あり。
- **ポイント4（バイナリサイズとツールチェインの成熟）:** `wasm-opt`やLTO、`wee_alloc`後継の軽量アロケータの改善で、典型的なRust+WasmバンドルがNext.jsのクライアントバンドルに統合しやすいサイズ（数十KB〜）まで最適化可能になった。フロントの重い計算（画像トリミング、PDFプレビュー）をクライアント側Wasmにオフロードする選択肢が現実的。
- **ポイント5（デバッグ・可観測性の改善）:** DWARFベースのソースマップとブラウザDevTools連携が改善し、本番Wasmのスタックトレースとプロファイリングが容易になった。導入時の最大の懸念だった「デバッグしづらさ」が大きく解消されており、採用ハードルが下がっている。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** 静的シェルと動的コンテンツを同一ページ内で組み合わせられるため、SEOに強い物件一覧ページの骨格は静的生成しつつ、価格や在庫状況などリアルタイム性が必要な部分だけストリーミングする設計が標準化してきている。初期表示速度とデータの鮮度を両立できる点が大きい。

- **Server Actions のミューテーション一元化:** フォーム送信や物件ステータス変更（draft→public）などの更新処理をAPI Routeではなく`"use server"`アクションに集約する流れが定着し、クライアント/サーバー間の型安全性がエンドツーエンドで保てる。社内の`src/lib/data.ts`周りの更新ロジックも、API層を経由せずServer Actionsへ移行する余地がある。

- **キャッシュ戦略の明示化（`revalidateTag`/`revalidatePath`中心）:** デフォルトキャッシュの挙動がバージョンごとに変わってきた経緯から、2026年のベストプラクティスはキャッシュ期待値を暗黙に頼らず、タグベースの明示的invalidationで制御すること。物件データのような頻繁に更新されるコンテンツほどこの設計が重要。

- **Route Groups + Parallel Routes によるレイアウト分離:** `(auth)`や`(dashboard)`のようなルートグループと、モーダル・サイドパネルを並行ルートで実装するパターンが、`properties/`や`account/`のような複数ロールが絡む画面で複雑なlayout.tsxの肥大化を防ぐ手段として広く採用されている。

- **型安全なデータフェッチとRSCの境界設計:** Client Component境界を必要最小限に絞り、Zodスキーマでサーバー境界の入出力を検証するパターンが定石化。バンドルサイズ削減とランタイムの型安全性を同時に担保できるため、新規機能実装時の既定アーキテクチャとして推奨される。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの再設計:** Vercel Edge Functionsは2026年にV8 isolateベースから更に軽量なWasmランタイムへの移行が進み、コールドスタートが実質ゼロに近づいている。既存のNode.js依存コードはEdge Runtime互換性チェックを早めに行うべき。

- **リージョン自動選択とデータ局所性:** Edge Middlewareが地理的レイテンシだけでなくデータベースのリージョンまで考慮した自動ルーティングを行うようになり、Next.js 16のPPR（Partial Prerendering）と組み合わせることで、動的部分のレンダリングもエッジ側で完結できる。sumitsugiの物件検索のような地理依存クエリは恩恵が大きい。

- **ストリーミングSSRとの統合コスト:** Edge Functionsの実行時間課金がストリーミング対応で変わりつつあり、長時間接続（SSE/WebSocket風ストリーミング）のコスト管理が重要になる。認証チェックなど軽量処理はEdgeに残し、重い処理はNode runtimeに委譲する境界設計が引き続き有効。

- **キャッシュ戦略の高度化:** `next/cache`のタグベース無効化とEdge Config（KVストア）の統合が進み、物件ステータス（draft/public）のような頻繁に変わらないがリアルタイム性も求められるデータに対して、エッジでの差分キャッシュ無効化が実用的な選択肢になっている。

- **可観測性の標準化:** Edge Functions用のOpenTelemetry対応が成熟し、リージョンごとのレイテンシ・エラー率をダッシュボードで追えるようになった。本番ローンチ前にこの計測基盤を組み込んでおくと、ベータ後のパフォーマンス問題の切り分けが早くなる。

### 10. TypeScript type safety patterns 2026

- **型レベルプログラミングの実用化:** TypeScript 5.x系でconst型パラメータやTemplate Literal Typesが成熟し、ZodやValibotとの組み合わせでランタイム検証とコンパイル時型を単一ソースから生成するパターンが標準化している。
- **スキーマファースト設計:** Zodスキーマから型を推論する`z.infer`パターンが、APIバウンダリ（本プロジェクトでも`src/lib`のユーティリティやフォーム入力）での型安全性のデフォルトになっている。重複定義を避け、スキーマを唯一の真実源にできる。
- **Branded Types / Nominal Typing:** `'draft' | 'public'`のようなUnion型だけでなく、IDやステータスにBranded Typesを使い、構造的に同じ文字列・数値型でも意味的な混同をコンパイル時に防ぐ手法が広まっている。
- **strictモード+`noUncheckedIndexedAccess`の常用化:** 配列・オブジェクトアクセス時の暗黙的`undefined`を型レベルで強制するオプションが、2026年ではほぼ必須の設定になりつつある。
- **AIコード生成との相性:** LLMが生成するコードは型エラーを見逃しやすいため、CIでの`bun run build`必須化（本プロジェクトの方針と同様）や、型を厳格にすることでAIエージェントの自己検証能力を高める運用が広がっている。
