# CTO Knowledge - 2026-07-02

## Daily Update (2026-07-02)

### 1. Next.js performance optimization 2026

- **App Router のPartial Prerendering (PPR) 標準化:** Next.js 15以降で導入されたPPRが2026年には安定版の主要機能となり、静的シェルと動的コンテンツを1つのルートで組み合わせて初回表示速度とパーソナライズ性を両立できる。物件一覧のような「共通レイアウトは静的、価格・空室状況は動的」なページ構成に直接効いてくる。

- **React Compiler によるメモ化自動化:** `useMemo`/`useCallback`の手動最適化が不要になり、ビルド時に自動でメモ化される。物件検索フィルターや一覧の再レンダリングコストを開発者が意識せず削減できるため、コードのシンプルさとパフォーマンスを同時に確保できる。

- **Turbopack のフルスタック採用:** dev/buildともにTurbopackがデフォルト化しつつあり、大規模コードベースでのHMR速度とビルド時間が大幅短縮される。今後リスティング機能が増えてsrc/配下が肥大化しても、開発体験の劣化を防げる。

- **Server Actions + キャッシュ戦略の精緻化:** `use cache`ディレクティブとfetchキャッシュの粒度制御が進化し、問い合わせフォームや前の住人とのマッチング処理などのミューテーションを伴う機能でも、キャッシュ無効化を明示的かつ局所的に制御できるようになっている。

- **Core Web Vitals の実測ベース最適化(INP重視):** LCP/CLSに加えINP(Interaction to Next Paint)がSEO・UX評価の中心になっており、物件詳細ページの画像ギャラリーやお問い合わせボタンなどインタラクション要素の応答性を`next/image`最適化やコード分割と合わせて計測・改善するワークフローが必須になっている。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 15〜16でPPRが安定版となり、静的シェルを即座に返しつつ動的部分だけをストリーミングする構成が主流に。`sumitsugi`の物件一覧・詳細ページのような「一覧は静的、価格や空室状況は動的」なUIと相性が良く、初期表示速度(TTFB/LCP)を大きく改善できる。

- **`use cache` ディレクティブによるキャッシュ制御の明示化:** キャッシュ境界をコンポーネント単位で宣言的に書けるようになり、従来の`revalidate`頼みの曖昧なキャッシュ戦略から脱却しつつある。物件データのようにDBアクセスを伴うServer Componentでは、キャッシュ粒度を明示することでストリーミングとの相性・パフォーマンスが安定する。

- **Suspense境界の設計がUXの肝に:** ストリーミングの恩恵はSuspense境界の粒度設計次第で大きく変わる。ページ全体を1つの境界にすると結局「全部揃うまで待つ」形になりがちなので、`src/app/properties/`配下では「物件カードは即表示、レビュー・空室カレンダーは遅延」のように機能単位で細かく分割するのがベストプラクティス。

- **エラーバウンダリとストリーミングの組み合わせ:** ストリーミング中に一部のServer Componentが失敗しても、他の部分は表示され続けるようにerror.tsxをコンポーネント単位で配置する設計が定着してきた。認証チェックや外部API呼び出しを含む部分（決済・引越し費用計算など）は特に個別のエラーバウンダリで囲むことで、障害時にもページ全体を巻き込まない。

- **Server Actions + ストリーミングフォームの成熟:** フォーム送信後の楽観的UI更新とストリーミング応答の組み合わせが定番パターン化。物件掲載フォームや問い合わせフォームのような多段階フローでは、`useOptimistic`とServer Actionsを組み合わせることで体感速度を落とさずにサーバー側バリデーションを実行できる。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCやGraphQLのようなスキーマファースト・型安全なAPI層が主流化し、フロントエンド/バックエンド間でTypeScriptの型を共有することで、実行時エラーではなくビルド時にAPI不整合を検出できるようになっている。sumitsugiのような小〜中規模チームには、コード生成不要で型推論が効くtRPCが特にDXの面で有利。

- **ポイント2:** REST vs GraphQLの二択論争は終わりつつあり、「公開APIや外部連携はREST（またはOpenAPI準拠）、社内・BFF層はtRPCやGraphQL」という使い分けが一般的になっている。sumitsugiも将来的に外部パートナー（不動産会社等）連携を見据えるなら、内部はtRPC・外部向けはREST+OpenAPIの二層構成が現実的。

- **ポイント3:** GraphQLのN+1問題やオーバーフェッチ対策として、DataLoaderパターンやPersisted Queriesがデファクト標準になりつつあるが、実装コストが高いため、中小規模サービスでは「必要な画面ごとに最適化されたREST/tRPCエンドポイント」の方がシンプルで保守しやすいケースが多い。

- **ポイント4:** API境界でのZodスキーマバリデーションが標準化しており、tRPCはこれをそのまま入力検証に使えるため、standards.mdにある「Zodスキーマによる境界検証」の方針とも自然に合致する。REST APIを追加する場合も同様にZodでリクエスト/レスポンスを検証すべき。

- **ポイント5:** 2026年時点でEdge Runtime（Vercel Edge, Cloudflare Workers）とAPIレイヤーの統合が進み、レイテンシ重視の物件検索・地図表示APIなどはEdge関数化する動きが増えている。sumitsugiの物件一覧・検索APIは今後トラフィック増加時にEdge化候補として検討価値あり。

### 4. serverless edge computing 2026

- **エッジでのSSR/ISRが標準化:** Next.js 16のようなフレームワークはCloudflare Workers / Vercel Edge RuntimeでのSSRが前提になりつつあり、物件一覧ページのようなSEO重視コンテンツはCDNエッジでレンダリングしてTTFBを50ms以下に抑えるのが実用ライン。

- **Edge DBとRegional Read Replica:** D1やTurso、PlanetScaleのようなSQLiteベースのエッジDBが普及し、ユーザーに地理的に近いノードでクエリを返す構成が一般化。sumitsugiのような日本国内向けサービスでも、東京リージョン集中より複数エッジPoP配信の方がモバイル回線でのレイテンシ改善効果が大きい。

- **コールドスタート問題はほぼ解消:** V8 isolateベースのランタイム（Workers, Deno Deploy）はコールドスタートが1桁ms台になり、認証や決済のような同期処理をエッジ関数に置いても許容できるレイテンシに。ただしNode.js APIフル互換ではないため、依存ライブラリの互換性確認は必須。

- **コスト構造がリクエスト課金からCPU時間課金へシフト:** 2026年時点で主要プロバイダはCPU実行時間ベースの課金が主流になり、画像処理やPDF生成（引越し費用明細など）のような重い処理はエッジで実行するとコストが跳ねやすい。軽量処理はエッジ、重い処理はリージョナルなサーバーレス（Lambda等）に振り分けるハイブリッド設計が推奨される。

- **観測性（Observability）がボトルネック化:** エッジ環境は分散度が高く、従来のAPMツールでは追跡しづらいため、OpenTelemetryのエッジ対応SDKやトレースコンテキストのプロパゲーションが必須要件になっている。認証フローなど複数エッジロケーションをまたぐ処理は、導入初期からトレーシングを組み込まないとデバッグコストが急増する。

### 5. authentication security best practices 2026

- **パスキー移行の本格化:** FIDO2/WebAuthnベースのパスキーがパスワードの主要な代替として標準化され、フィッシング耐性のある認証がデフォルトになりつつある。sumitsugiでも将来的にメール+パスワードからパスキー併用への移行を検討すべき。
- **セッション管理とトークンローテーション:** 長寿命のJWTやリフレッシュトークンの単純運用はセッションハイジャックのリスクが高く、短命アクセストークン＋ローテーション＋デバイスバインディングの組み合わせが2026年のベストプラクティス。
- **多要素認証の「フィッシング耐性」重視:** SMS OTPは依然弱点とされ、TOTPやプッシュ通知型MFAより、WebAuthn/ハードウェアキーによる中間者攻撃耐性が重視される流れ。
- **ゼロトラスト前提のAPI認可:** 認証（誰か）と認可（何ができるか）を分離し、リクエスト単位で権限検証するアーキテクチャが標準化。物件データや個人情報を扱う本サービスでは特にAPIレベルでのアクセス制御の粒度が重要。
- **AI駆動の不正検知:** ログイン試行パターンやデバイスフィンガープリントを用いた異常検知が普及し、ブルートフォースやアカウントテイクオーバーの早期検出に活用されている。

不動産・個人情報を扱うsumitsugiでは、特にパスキー対応と短命トークン運用が優先度高いと考えます。

### 6. database architecture Prisma Supabase 2026

- **ポイント1（Prisma Postgres / Accelerate）:** Prisma 6以降は自社マネージドの「Prisma Postgres」とグローバルキャッシュ層「Accelerate」への統合が進み、Supabaseと組み合わせる場合もコネクションプーリング（PgBouncer/Supavisor）越しのレイテンシ対策としてAccelerateを併用する構成が増えている。サーバーレス環境（Vercel Edge等）でのコールドスタート時のコネクション枯渇を防ぐ設計が必須。

- **ポイント2（RLSとORMの責務分離）:** SupabaseのRow Level Security（RLS）はDB層でのアクセス制御を担うが、PrismaはRLSを認識しないため、Prisma経由のクエリでもRLSが有効になるよう`service_role`キーの扱いとRLSポリシーの両方をテスト対象に含める必要がある。マルチテナントの物件データ（前の住人/次の住人の個人情報）を扱う本プロジェクトでは特に、DB層とORM層の二重の権限管理を明示的に設計すべき。

- **ポイント3（マイグレーション運用）:** Prisma MigrateとSupabase CLIのマイグレーション機構が競合しやすいため、2026年時点のベストプラクティスは「Supabase CLIをスキーマのソース・オブ・トゥルースとし、Prisma側は`db pull`でスキーマを同期する」片方向運用が主流になっている。双方向の手動マイグレーションはスキーマドリフトの原因になるため避けるべき。

- **ポイント4（Edge Functions + Prisma Data Proxy）:** SupabaseのEdge Functions（Deno環境）とPrismaを併用する場合、Prismaの通常クライアントはNode.js依存が強くDenoでは動作しないため、Prisma AccelerateのようなHTTPベースのデータプロキシ経由でのアクセスが必須になる。物件検索など高頻度読み取りAPIをEdge化する際はこの制約を事前に確認すべき。

- **ポイント5（型安全性とリアルタイム機能の両立）:** Supabaseのリアルタイム購読（Realtime）はPrismaのスキーマ変更検知と独立しているため、`status: 'draft' | 'public'`のようなUnion型変更時は、Prismaスキーマ・Zodバリデーション・Supabase Realtimeのチャネル定義の3箇所を同期更新するチェックリスト運用が事故防止に有効。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** RustのWasm向けツールチェイン（wasm-bindgen, wasm-pack）とComponent Model対応が2026年には安定期に入り、JSグルーコードのオーバーヘッドが大幅に削減されている。SIMD命令とWASI Preview 2の普及で、画像処理やPDF生成などCPU負荷の高い処理をブラウザ/サーバー両方で高速化できる。
- **ポイント2:** WasmGCとの統合により、Rustの所有権モデルを活かしたゼロコピーなメモリ共有がJS/TypeScript側と直接可能になり、従来のシリアライズコストが解消されつつある。sumitsugiのようなドキュメント（重要事項説明書等のPDF）生成処理に応用できる可能性がある。
- **ポイント3:** サーバーサイドではWasmランタイム（Wasmtime, Spin）がコールドスタート数ミリ秒を実現し、Node.js/Bunのサーバーレス関数の代替として採用が進んでいる。引っ越しマッチングのような可変負荷なバッチ処理に向く。
- **ポイント4:** Next.js/Vercelエコシステムでも、画像最適化やエッジミドルウェアの一部にRust製Wasmモジュールが組み込まれるケースが増え、ビルド時の型安全性とランタイム性能を両立しやすくなっている。
- **ポイント5:** 開発体験面では、RustのマクロエラーメッセージやWasmデバッグツール（`console_error_panic_hook`、DevToolsのソースマップ対応）が改善され、TypeScriptチームでもRust導入の学習コストが下がっている。ただし小規模チームでは言語スタック追加の運用コストとのトレードオフを慎重に見極めるべき。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** 静的シェルと動的コンテンツを同一ルートで組み合わせるPPRが安定版として定着し、`loading.tsx`とStreamingを併用することでTTFBを維持しつつパーソナライズされたUIを配信できる。

- **Server ActionsのセキュリティとRSC境界の明確化:** `'use server'`関数への直接バインドが増える一方、認可チェック漏れがOWASP的リスクになりやすいため、Server Action内で必ずセッション検証を行い、`use client`境界を最小限に絞る設計が推奨される。

- **キャッシュ制御の明示化（`use cache`ディレクティブ）:** デフォルトキャッシュ挙動への依存から脱却し、`fetch`のオプションや`use cache`で意図を明示するパターンが主流になり、物件一覧やステータス更新のような可変データでの事故を防ぎやすくなる。

- **App Router + Server Componentsでのデータフェッチ集約:** ページ/レイアウト単位でのウォーターフォール防止のため、`Promise.all`や並列データフェッチパターンをRSCレベルで徹底し、クライアントバンドルサイズを削減する設計が定番化している。

- **Middlewareの責務縮小とEdge Runtime依存の見直し:** 認証・リダイレクトなど軽量処理のみをMiddlewareに残し、重い処理はServer Components/Actionsに移す構成が、Vercel以外のホスティング選択肢の広がりとともに主流になりつつある。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの最適化:** Vercel Edge FunctionsはV8 isolateベースで起動が高速なため、認証チェックやリダイレクト、A/Bテストの振り分けなど軽量なミドルウェア処理に限定して使い、DB接続やファイルI/Oが必要な重い処理はNode.jsランタイム（Serverless Functions）に任せる住み分けが重要。

- **リージョン配置とレイテンシ削減:** ユーザーに地理的に近いエッジで実行できる特性を活かし、`sumitsugi`のような不動産マッチングでは物件検索の初期フィルタリングやキャッシュ済みデータの返却をエッジ側に寄せることで、TTFBを大幅に短縮できる。

- **コールドスタート対策とバンドルサイズ管理:** Edge Functionsは軽量とはいえ依存関係が肥大化すると初期化コストが増えるため、Zodスキーマ検証など必要最小限のロジックのみをエッジ層に配置し、不要なライブラリのimportを避けることがパフォーマンス維持の鍵。

- **キャッシュ戦略との組み合わせ:** Next.js 16のApp RouterにおけるISR/On-demand Revalidationと組み合わせ、`'draft'`/`'public'`ステータスの切り替えに応じたキャッシュ無効化をエッジ側で制御することで、公開物件一覧のような頻繁にアクセスされるページの応答速度を最適化できる。

- **可観測性の確保:** Edge Functionsはconsole.logが使えない制約下でも、Vercelの組み込みObservability機能やOpenTelemetry連携でリクエストトレースを取得し、本番環境でのボトルネック特定を継続的に行う体制が必要。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.9以降の`const type parameters`とテンプレートリテラル型の組み合わせが標準化し、APIレスポンスの型を実行時バリデーションなしでも高精度に絞り込めるようになった。ただしZodやValibotとの併用は依然必須で、コンパイル時の型と実行時の型を分離しない設計は事故の元になる。

- **ポイント2:** `satisfies`演算子の活用がベストプラクティスとして定着し、`as const`と組み合わせて設定オブジェクトやルーティング定義の型推論を保ちながら過剰な型注釈を排除する書き方が主流になっている。sumitsugiの`site-config.ts`のような設定ファイルでも積極採用すべきパターン。

- **ポイント3:** Branded Types（公称型）によるID誤代入防止が2026年時点で一般化し、`PropertyId`や`UserId`のようなプリミティブ型のなりすまし防止が中規模以上のプロジェクトで標準装備になりつつある。sumitsugiのような`draft`/`public`のUnion型を扱うコードベースでは、ステータス文字列の取り違えバグをコンパイル時に検出できる利点が大きい。

- **ポイント4:** モノレポ・大規模プロジェクトでは`tsgo`（TypeScriptのGo移植によるネイティブコンパイラ）の実運用採用が進み、型チェックのCI時間が数分から数十秒に短縮される事例が増えている。ビルド健全性を重視するCLAUDE.mdの方針（`bun run build`必須）とも相性が良く、CI高速化の投資対効果が高い。

- **ポイント5:** Zodなど実行時スキーマライブラリから型を逆生成する「Schema-first」設計が、フォームやAPI境界（システム境界での入力検証）のデファクトになった。型定義を手書きせずスキーマから`z.infer`で導出することで、標準ルール（Zodスキーマによる入力検証）と型安全性を二重管理せずに一致させられる。
