# CTO Knowledge - 2026-06-08

## Daily Update (2026-06-08)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを劇的に削減できるRSCは2026年時点でのデファクトスタンダード。`"use client"` の使用を最小限に抑え、データフェッチをサーバー側に集約することでTTFBとLCPを大幅改善できる。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降で安定化したPPRにより、静的シェルを即座に配信しつつ動的コンテンツをストリーミングするハイブリッドモデルが実用段階に。SSG・SSR・ISRの三択という旧来の設計判断が不要になりつつある。

- **Turbopack によるビルド高速化:** Webpackから完全移行したTurbopackはコールドスタートとHMRを大幅に短縮。大規模プロジェクトでは開発体験（DX）の向上だけでなく、CI/CDのビルド時間削減によるコスト削減効果も無視できない。

- **`<Image>` / フォント最適化の確実な適用:** `next/image` の `sizes` prop の適切な設定と、`next/font` によるCLS排除は基本だが、現場では未対応のプロジェクトが多い。Core Web Vitalsのスコアに直結するため、Lighthouseを定期CI組み込みにして継続的に計測することが重要。

- **App Router でのキャッシュ戦略の再設計:** Next.js 15でデフォルトがno-cacheに変更されたことで、意図しないキャッシュヒットの問題は減ったが、逆にパフォーマンスを引き出すには `revalidate` や `unstable_cache` を意識的に設計する必要がある。キャッシュ設計をルーティング設計と同時に行う習慣が不可欠。

### 2. React Server Components streaming 2026

- **PPR（Partial Pre-Rendering）の普及:** 静的シェルを即時配信しつつ、動的部分をSuspenseでストリーミングする手法が標準化。TBT（Total Blocking Time）を大幅削減できる。

- **Server Actionsとストリーミングの統合:** フォーム送信後の楽観的UI更新とサーバー側処理を同一コンポーネントで完結できるようになり、クライアント/サーバー間のwaterfallが構造的に解消された。

- **Suspense境界の細粒度設計がボトルネック:** コンポーネントツリー全体ではなく、データ依存のある最小単位にSuspenseを配置することが重要。粗い境界設計はストリーミングの恩恵を殺す。

- **Edge Runtimeでの制約に注意:** Node.js APIに依存するライブラリはEdgeで動作しないため、DBアクセス層（Prisma等）をRSCで直接使う場合はデプロイ環境を事前に確認する必要がある。

- **キャッシュ戦略の複雑化:** `fetch`のキャッシュ、`unstable_cache`、ルートセグメントの`revalidate`が混在し、ストリーミングと組み合わせると予期しない古いデータが配信されるリスクがある。明示的なキャッシュ境界の設計が不可欠。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭:** TypeScriptフルスタック環境ではtRPCが事実上の標準に近づいており、型安全なend-to-end開発体験がDX向上と実行時エラー削減を両立させている。Next.js + tRPCの組み合わせは特に社内ツールやスタートアップで支持が高い。

- **GraphQLの選択基準の明確化:** 「とりあえずGraphQL」という時代は終わり、複数クライアント（モバイル・Web）が異なるデータ要件を持つ場合や、BFF（Backend for Frontend）パターンが必要な場合に限定して採用するのがベストプラクティス。Relay/Apollo Clientの複雑さに対するROIを慎重に評価すべき。

- **RESTの復権とOpenAPI 3.1:** シンプルなCRUD APIやサードパーティ公開APIではRESTが依然として最適解。OpenAPI 3.1 + zod-to-openapi等のコードファーストなスキーマ生成により、型安全性とドキュメント自動化が両立できるようになった。

- **HTTPプロトコル層の進化:** HTTP/3（QUIC）の普及により、gRPC-webやServer-Sent Eventsのパフォーマンスが実用レベルに達した。リアルタイム要件のあるAPIではWebSocket一択でなく、SSEやgRPCを選択肢として真剣に評価する価値がある。

- **APIゲートウェイとSchema Registry:** マイクロサービス環境ではAPI設計よりも「スキーマの単一ソース管理」が重要課題になっており、Buf Schema RegistryやHive等のツールを使ったスキーマファーストな開発フローが組織横断の一貫性を担保する鍵となっている。

### 4. serverless edge computing 2026

- **ポイント1: WebAssembly (Wasm) がエッジのデファクトランタイムに:** V8 isolateに代わりWasmがエッジ実行の標準になりつつあり、言語非依存・コールドスタートほぼゼロ・セキュアなサンドボックスを同時に実現している。Cloudflare Workers・Fastly Compute等が本番対応済み。

- **ポイント2: AI推論のエッジオフロードが加速:** LLMの量子化モデル（1〜7B規模）をエッジで実行するパターンが普及し、レイテンシ削減とプライバシー保護を両立。ただしモデル更新のデプロイ戦略が新たな運用課題になっている。

- **ポイント3: エッジDBとの統合が成熟:** Cloudflare D1・Turso（libSQL）・Neon（Postgres serverless）などエッジ近傍に置けるSQLが整備され、「エッジでDBアクセスできない問題」がほぼ解消。グローバルレプリケーションの整合性モデル選択が設計の肝になる。

- **ポイント4: オブザーバビリティのギャップが顕在化:** 数百POPに分散したエッジ関数のトレーシング・ログ集約は依然として課題。OpenTelemetry対応が進んでいるが、コスト増との兼ね合いでサンプリング戦略の設計が重要。

- **ポイント5: ベンダーロックイン回避としてのWinterTC/WinterCG標準:** ブラウザ外のJS実行環境（Workers・Deno Deploy・Bun等）の相互互換API標準化が進み、ポータビリティが向上。Next.js等のフレームワークもエッジランタイムを抽象化しているため、インフラ差し替えコストが下がっている。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の標準化:** パスワードレス認証がデファクトスタンダードになりつつある。主要プラットフォーム（Apple/Google/Microsoft）の同期パスキー対応で、UXを損なわず強固なフィッシング耐性を実現できる。

- **トークンバインディングとDPoP:** OAuth 2.0のBearer Tokenは盗難・リプレイ攻撃に脆弱なため、DPoP（Demonstrating Proof of Possession）で送信者制約付きトークンを採用するのが2026年のベストプラクティス。特にBFF（Backend for Frontend）パターンと組み合わせると効果的。

- **継続的認証（Continuous Authentication）:** ログイン時の一回限りの認証から、セッション中のリスクスコアリング（行動パターン・デバイス信頼性・地理情報）による動的再認証へ移行が進む。異常検知時のみ追加認証を求めるアダプティブMFAが主流。

- **サプライチェーン攻撃への対策としての依存関係監査:** 認証ライブラリ（passport.js、jose等）への悪意ある改ざんが増加。Dependency Pinning・SLSA Level 3以上の準拠・Software Bill of Materials（SBOM）の生成を認証基盤では必須とすべき。

- **機密情報の分離とゼロトラスト設計:** JWTペイロードに個人情報を含めない（参照型トークン＋サーバーサイドストア）、Refresh TokenのRotation＋Family Detection実装、さらにmTLS（相互TLS）をサービス間通信に採用することで、内部脅威にも対応できるアーキテクチャを構築する。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6のEdge対応成熟:** Prisma Accelerateによりエッジランタイム（Cloudflare Workers等）からのDB接続が実用レベルに達した。コネクションプーリングをマネージドで提供するため、サーバーレス構成でのN+1問題とコールドスタートが大幅に改善。

- **SupabaseのpgVector活用がRAGの標準に:** Supabase上のpgvector拡張がAIアプリのベクトルストアとして主流となり、別途Pinecone等を立てずにPostgreSQL一本で済む構成が増加。RLSと組み合わせることでマルチテナントRAGも安全に実装可能。

- **Database Branchingがワークフローを変える:** Supabase BranchingとPrisma Migrateの組み合わせにより、PRごとに独立したDBプレビュー環境が自動生成できるようになった。マイグレーションの安全性検証がCIに組み込まれ、本番事故が激減。

- **Row Level Security (RLS) をアプリ層でなくDB層に集約:** Supabase+Prismaの構成でRLSをDB側に寄せるパターンが定着。アプリコードのセキュリティ漏れリスクを根本から排除できるが、Prismaの型推論とRLSポリシーの乖離をテストで担保する運用が必要。

- **Realtime + Postgres Changes の活用拡大:** SupabaseのRealtime機能がLogical Replicationベースで安定化し、WebSocket経由でのDB変更通知が低コストで実装可能に。ポーリング型アーキテクチャからイベント駆動への移行が加速している。

### 7. WebAssembly Rust performance 2026

- **WASM Component Model の成熟:** 2026年はWASM Component Modelが実用段階に達し、RustコンポーネントをJS/Python/Goと型安全に組み合わせるインターオペラビリティが標準化。既存のWebアプリにRustの高速処理を段階的に組み込む設計が容易になった。

- **WASI Preview 2 によるサーバーサイド活用の拡大:** WASI Preview 2の安定化でRust製WASMがエッジ/サーバーサイドのFaaSで本格採用。Cloudflare Workers・Fastly Compute等でコールドスタートを抑えつつネイティブに近いスループットを実現できる。

- **SIMD・マルチスレッド対応の実用化:** WASMのSIMDとShared Memory/Atomicsが主要ブラウザで安定稼働し、Rust側のSIMD intrinsicsとrayon的な並列処理をWASMへコンパイルする事例が急増。画像処理・音声処理・ML推論で特に効果が大きい。

- **バイナリサイズとコンパイル時間の改善:** `wasm-opt`・`twiggy`・LTOの組み合わせ最適化が成熟し、リリースビルドのバイナリサイズが2年前比で30〜50%削減可能に。開発体験面でもincrementalビルドの改善でイテレーション速度が向上している。

- **Rust+WASM vs ネイティブのギャップ縮小:** メモリモデルの制約（GC不在・線形メモリ）によるオーバーヘッドが最適化ツールチェーンの進化で縮小し、計算集約型タスクではネイティブ比95%以上のパフォーマンスが現実的。ただしDOM操作を多用するUI層ではJS-WASM境界コストが依然ボトルネックになるため、処理をWASM側に集約するアーキテクチャ設計が重要。

### 8. Next.js App Router patterns 2026

- **Server Components First原則:** 2026年のApp Routerでは「デフォルトServer Components、必要時のみClient Components」が定着。データフェッチはServer側で完結させ、バンドルサイズを最小化するのが標準パターン。

- **Partial Prerendering (PPR)の本格活用:** 静的シェル＋動的ストリーミングを同一ルートで混在できるPPRが安定版に。`<Suspense>`境界の設計がアーキテクチャの核心になっており、ページ単位ではなくコンポーネント単位でのキャッシュ戦略が求められる。

- **Server Actions中心のデータ変更:** `use server`によるServer Actionsがform・mutation処理の主流に。APIルートを挟まずDBに直接アクセスできるため、型安全性とDXが向上するが、認可チェックをAction内に必ず実装する規律が重要。

- **`use cache`ディレクティブによる細粒度キャッシュ:** `unstable_cache`の後継として`use cache`が関数・コンポーネントレベルのキャッシュ制御を提供。`cacheTag`/`cacheLife`でタグベース無効化が可能になり、CDNキャッシュとの統合戦略が設計上の重要論点になっている。

- **Turbopackの本番利用:** Next.js 15+でTurbopackがデフォルトdevサーバーに。ビルドパイプラインのwebpack依存カスタマイズ（babel plugins等）をTurbopack互換に移行できているかが、チームのアップグレード可否を左右する実務上のボトルネック。

### 9. Vercel Edge Functions optimization 2026

- **バンドルサイズの最小化が最優先:** Edge Runtimeは1MB制限があるため、`import`の選択的利用とtree-shakingが必須。Node.js専用APIへの依存をEdge互換ライブラリ（例: `jose`で`jsonwebtoken`を代替）に置き換えることが、パフォーマンス改善の最初の一手。

- **Streaming + Partial Prerendering (PPR) の組み合わせ:** 2025-2026年のVercelの主力機能であるPPRをEdge Functionsと組み合わせることで、静的シェルを即座に配信しつつ動的部分をEdgeでストリーミングする構成が実用段階に入った。TTFBを大幅削減できる。

- **Middleware の適切なスコーピング:** `matcher`設定で処理対象パスを厳密に絞ることが重要。全パスに当たるMiddlewareは全リクエストにレイテンシを追加する。認証・リダイレクト・A/Bテスト以外の処理はMiddlewareに置かない原則を徹底する。

- **KV / Edge Configによるコールドスタート回避:** 設定値やフィーチャーフラグをEdge Configで管理することで、DBラウンドトリップなしにEdge層で判断できる。Vercel KVはEdge Functionsと同一リージョンに配置することでレイテンシをほぼゼロにできる。

- **Node.js RuntimeとEdge Runtimeの使い分け戦略:** 重い処理（PDF生成・複雑なDB操作）はNode.js Runtime、認証・パーソナライゼーション・地域ルーティングはEdge Runtimeと明確に役割分担する。2026年時点では両Runtimeの機能差が縮まりつつあるが、制約を把握した上での選択が依然重要。

### 10. TypeScript type safety patterns 2026

- **Branded Types の本格普及:** `type UserId = string & { readonly _brand: 'UserId' }` のような Branded Types が実務で標準化。プリミティブ型の混在バグをコンパイル時に完全排除できる。

- **`satisfies` 演算子の活用:** 型推論を保ちながら型制約を検証できる `satisfies` が2026年現在の定番パターン。`as` キャストの代替として、型安全性を犠牲にせずに記述できる。

- **Template Literal Types による API 型安全化:** `type Route = '/users/${string}'` のような Template Literal Types でルートやイベント名を型レベルで縛る実装が増加。ランタイムエラーの多くをビルド時に検出可能。

- **`noUncheckedIndexedAccess` の必須化:** `tsconfig.json` の `noUncheckedIndexedAccess: true` が厳格プロジェクトの標準設定に。配列アクセス時の `undefined` を型レベルで強制的に意識させ、実際の境界外アクセスバグを激減させる。

- **Zod + tRPC パターンのフルスタック型共有:** API の入出力スキーマを Zod で定義し、クライアント〜サーバー間でスキーマを単一ソースとして共有するパターンが成熟。バリデーションと型定義の重複を排除しつつ、エンドツーエンドの型安全性を実現できる。
