# CTO Knowledge - 2026-02-24

## Daily Update (2026-02-24)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的コンテンツを単一リクエストで配信するPPRがNext.js 15以降で安定化。`<Suspense>`境界を適切に設計することで、TTFBを維持しつつ動的データを後続ストリーミングできる。

- **React Server Components (RSC) によるバンドルサイズ削減:** クライアント送信JSを最小化するため、`'use client'`ディレクティブを葉コンポーネントに限定する設計が標準化。データフェッチロジックをServerコンポーネントに集約することでウォーターフォールも排除できる。

- **Turbopackへの完全移行:** webpack比最大10倍高速なTurbopackが本番ビルドでも安定化し、大規模プロジェクトでのHMR・ビルド時間を大幅短縮。`next.config.js`の`turbo`オプション設定が重要。

- **`<Image>`と`next/font`によるCore Web Vitals最適化:** LCP改善のため`priority`プロパティとサイズ明示が必須。`next/font`でのフォントサブセット化によりCLS・FID両方を同時に改善できる。

- **Edge RuntimeとISRの組み合わせ戦略:** グローバルユーザー向けには`runtime: 'edge'`でレイテンシを削減し、データ変更が頻繁なページはISRの`revalidate`間隔をビジネス要件に合わせて最適化。キャッシュ戦略の設計がパフォーマンスの鍵となる。

### 2. React Server Components streaming 2026

- **ポイント1:** RSC + Suspense Streamingの成熟: Next.js 15以降でPPR（Partial Prerendering）が安定化し、静的シェルを即座に配信しつつ動的コンポーネントをストリームする設計が標準パターンになった。TTFBとLCPの両立が現実的になっている。

- **ポイント2:** Server Actionsとの統合深化: フォーム送信・ミューテーションにおいてServer Actionsが主流となり、クライアントサイドのAPI呼び出しコードが大幅に削減。ただしリプレイアタック対策やCSRF考慮が依然として必要。

- **ポイント3:** エッジ実行環境でのストリーミング制約: Cloudflare Workers・Vercel Edge等でのRSCストリーミングはNode.jsランタイム依存の一部APIが使えず、`runtime: 'edge'`指定時のポリフィル管理が実務上のボトルネックになっている。

- **ポイント4:** キャッシュ戦略の再整理: Next.js 15でfetch cacheのデフォルトが`no-store`に変更され、明示的なキャッシュ設計が必須に。`unstable_cache`やRequest Memoizationを組み合わせたレイヤー構造の理解がパフォーマンス設計の要。

- **ポイント5:** バンドルサイズへの影響: RSCにより大型ライブラリをサーバー側に閉じ込めることで、クライアントJSバンドルの30〜50%削減事例が報告されている。ただしコンポーネント境界（`'use client'`）の設計ミスで効果が相殺されるため、アーキテクチャレビューが不可欠。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全API:** tRPCはNext.js/TypeScriptスタックでの採用が急増しており、コードジェネレーション不要でエンドツーエンドの型安全を実現できるため、フルスタックTypeScriptプロジェクトではREST/GraphQLより開発速度が大幅に向上する。

- **REST vs GraphQLの棲み分けの明確化:** 2026年時点でGraphQLは「BFFパターン」での活用が主流となり、公開APIはRESTのシンプルさを維持しつつ、フロントエンド向けの集約レイヤーにのみGraphQLを採用するハイブリッド設計が増えている。

- **OpenAPI 3.1とコード生成の成熟:** `openapi-typescript`や`orval`などのツールが成熟し、OpenAPIスキーマからTypeScriptクライアントを自動生成するワークフローが定番化。REST APIでも型安全の恩恵を享受できるようになった。

- **Server-Sent Events / HTTP Streampingの復権:** LLM統合の普及に伴いリアルタイムデータストリーミングの需要が高まり、WebSocketより実装が簡単なSSE/HTTP StreamingがAPIデザインの重要な選択肢となっている。

- **エッジ対応APIアーキテクチャ:** Cloudflare WorkersやVercel Edge Functionsの普及により、APIの設計段階からエッジ実行を考慮する必要が生まれ、ステートレス設計・Cold Start最小化・地理的分散への対応がベストプラクティスとなっている。

### 4. serverless edge computing 2026

- **WebAssembly のエッジ標準化:** WasmがCloudflare Workers・Fastly Compute等で主流となり、言語非依存のエッジ関数デプロイが現実的に。コールドスタートがほぼゼロになり、Node.js依存から脱却できる。

- **ステートフルエッジの台頭:** Cloudflare Durable Objects・Vercel KV等により、エッジでの状態管理が可能に。従来「エッジは無状態」という制約が崩れ、セッション・リアルタイム同期をエッジで完結できる。

- **エッジAI推論の実用化:** 軽量LLM（Phi-3 Mini等）やembeddingモデルをエッジで実行するパターンが普及。オリジンへのラウンドトリップなしにパーソナライズ・モデレーションが実現し、レイテンシが劇的に改善。

- **エッジネイティブDB の成熟:** Cloudflare D1・Turso（libSQL）等の分散SQLiteが本番利用に耐えうる水準へ。「エッジ関数＋エッジDB」の完結構成で、オリジンサーバーレスなアーキテクチャが設計できる。

- **マルチエッジオーケストレーション:** 単一プロバイダー依存を避け、OpenTelemetry＋IaC（Pulumi/Terraform）で複数エッジ環境を統一管理するパターンが標準化。ベンダーロックインリスクの低減が設計上の必須要件になっている。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準採用:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の主流となり、フィッシング耐性と利便性を両立できる。既存のパスワード認証からの移行計画を今から策定すべき。

- **トークン有効期限の短縮とリフレッシュ戦略の見直し:** JWTのアクセストークンは15分以下、リフレッシュトークンにはローテーション＋Refresh Token Family検出を実装し、トークン盗難時の被害を最小化する。

- **デバイスフィンガープリンティングと行動ベース異常検知:** ログイン時のデバイス情報・IPジオロケーション・操作パターンをリアルタイム分析し、不審なセッションを自動ブロックするリスクベース認証が標準化されている。

- **OAuth 2.1 + DPoP（Demonstrating Proof of Possession）の採用:** ベアラートークンの横流し攻撃を防ぐため、DPoPによりトークンを特定クライアントに紐付ける実装が推奨される。Next.jsではAuth.js v5がこれをサポート。

- **サプライチェーンリスクとしての認証ライブラリ管理:** 認証関連パッケージの依存関係は最小化し、`bun audit`による定期的な脆弱性スキャンとLockfileの厳格管理を徹底する。特に間接依存での脆弱性混入が増加傾向にある。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6のパフォーマンス最適化:** Prisma 6.xではクエリエンジンがRustベースの新アーキテクチャに移行し、コールドスタートが大幅改善。Next.js App RouterのServer Componentsとの統合がより最適化され、接続プーリング（`@prisma/client` + `pgBouncer`）の設定が簡素化された。

- **Supabase Edge Functionsとの統合深化:** Supabase Postgres + Prisma ORM の組み合わせが2026年の標準パターンとして定着しつつある。ただし、Supabase独自のRow Level Security（RLS）とPrismaのミドルウェアを併用する際は、セキュリティレイヤーの二重管理に注意が必要。

- **Prisma Accelerateによるグローバルキャッシュ:** Prisma Accelerateがエッジキャッシュ＋コネクションプーリングをワンストップ提供。SupabaseのDirect Connection上でPrisma Accelerateを使うことで、サーバーレス環境での接続枯渇問題をほぼ解消できる。

- **型安全なリアルタイム:** Supabaseのリアルタイム機能（Realtime）はPrismaスキーマと直接連携しないため、型の一貫性維持にZodによるランタイム検証を挟むパターンが推奨される。`supabase-js` v3のジェネリクス強化により、フロントエンドの型補完が改善。

- **マイグレーション戦略の分岐:** Prisma MigrateとSupabase Migrationsは共存が可能だが、2026時点でのベストプラクティスは「Prismaでスキーマ定義・マイグレーション生成 → Supabase CLI経由で適用」の一方向フローに統一すること。双方向の操作は競合リスクが高い。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の本格普及:** 2026年現在、WASI Preview 2とComponent Modelが安定化し、RustでコンパイルしたWasmモジュールをホスト環境非依存で合成・再利用できる設計が現実的な選択肢となった。マイクロサービスのサイドカーをWasmで置き換えるユースケースが増加中。

- **wasmtime / Craneliftの最適化成熟:** Bytecode AllianceのCraneliftコンパイラが成熟し、JITコンパイル速度と生成コードの品質が向上。コールドスタート問題が大幅に改善され、エッジコンピューティング（Cloudflare Workers、Fastly Compute）でのRust+Wasmのレイテンシが実用レベルに達している。

- **SIMD・スレッド対応の実用化:** WebAssembly SIMDとShared Memoryスレッドのブラウザサポートが安定し、Rustの`std::arch`を使ったSIMD最適化やRayonベースの並列処理がWasm環境でも有効に機能するようになった。画像処理・ML推論での採用が拡大。

- **バイナリサイズの最適化ツール成熟:** `wasm-opt`（Binaryen）、`wasm-pack`、`cargo-component`のエコシステムが成熟。`wee_alloc`の後継として`talc`や`dlmalloc`が採用され、標準ライブラリなしでも50KB以下の実用的なバイナリ生成が容易になった。

- **Rust→Wasm移行コストの現実:** Rustの`no_std`環境やFFI境界でのメモリコピーオーバーヘッドは依然として設計上の課題。JS↔Wasm間のデータ転送が頻繁なユースケースでは、`wasm-bindgen`の境界設計を慎重に行わないとネイティブ比でのパフォーマンス優位性が失われる点に注意が必要。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** React Server Components が完全に主流化し、クライアントバンドルサイズを大幅削減。`'use client'` は本当に必要な葉コンポーネントにのみ付与し、データフェッチはサーバー側で完結させるのが標準パターン。

- **Partial Prerendering (PPR) の実用化:** 静的シェルと動的ストリーミングを同一ルートで混在させる PPR が安定版に。`<Suspense>` 境界で囲むだけで静的部分は CDN キャッシュ・動的部分はサーバーレンダリングと自動分離される。

- **Server Actions によるフォーム・ミューテーションの一元化:** API Route を経由せず `action={serverAction}` で直接サーバー関数を呼び出すパターンが定着。楽観的 UI は `useOptimistic` で実装し、クライアント状態との整合性を保つ。

- **`use cache` ディレクティブによるキャッシュ粒度の細粒化:** Next.js 15/16 で導入された `use cache` がコンポーネント・関数レベルのキャッシュを宣言的に制御可能にした。`revalidateTag` との組み合わせでオンデマンド再検証を精密に設計できる。

- **Turbopack + React Compiler でDX向上:** Turbopack がデフォルトビルダーとして安定し、HMR が大幅高速化。React Compiler（自動メモ化）との組み合わせにより、`useMemo` / `useCallback` の手動最適化が不要になりつつある。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge Runtimeの選択的活用:** Edge Functionsは低レイテンシが強みだが、Node.js APIへのアクセスが制限される。認証・リダイレクト・パーソナライゼーションなどステートレスな処理に絞り、DB接続が必要な処理はServerless Functionsに委譲するハイブリッド設計が最適。

- **ポイント2: Fluid ComputeによるCold Start排除:** 2025年後半から展開されたFluid Computeモデルにより、従来のEdge FunctionsのCold Start問題が大幅に改善。インスタンスの再利用率が向上し、特にトラフィックスパイク時のパフォーマンス安定性が高まった。

- **ポイント3: KV・キャッシュ戦略の精緻化:** Vercel KVやEdge Configとの組み合わせでデータアクセスをEdgeに寄せるパターンが成熟。`cache()`関数とReact Server Componentsのキャッシュ境界を意識した設計で、オリジンへのリクエストを最小化することが重要。

- **ポイント4: バンドルサイズ管理の徹底:** Edge Functionsは1MBのコードサイズ上限があるため、依存ライブラリの精査が必須。`@vercel/og`やlightweight crypto libraryなどEdge対応ライブラリへの移行、およびtree-shakingの効果確認がパフォーマンスに直結する。

- **ポイント5: オブザーバビリティの強化:** Edge層はデバッグが難しいため、OpenTelemetryベースのトレーシングをMiddlewareから関数まで通貫させることが重要。Vercel Analytics + 外部APM（Datadog等）との統合で、リージョン別レイテンシの異常を早期検知する体制を整備すべき。

### 10. TypeScript type safety patterns 2026

- **Template Literal Types の高度活用:** 文字列ベースのAPIルートや状態機械を型レベルで完全に表現できるようになり、ランタイムエラーを大幅に削減。特にREST APIクライアントの自動型付けで実用価値が高い。

- **`satisfies` 演算子の定着:** 型推論を維持しながら型チェックを行える `satisfies` が標準パターンとして普及。`as const` との組み合わせで設定オブジェクトの型安全性が飛躍的に向上した。

- **Branded Types（名前付き型）の普及:** `UserId`, `Email` などプリミティブをラップした型が実務で当たり前に。Zodとの組み合わせでバリデーションと型が一体化し、境界値の混入バグがゼロになる。

- **`using` キーワードによるリソース管理:** ES2024の Explicit Resource Management がTypeScriptに統合され、DB接続・ファイルハンドルのリークを型システムで防止。`Symbol.dispose` パターンが非同期処理の定石に。

- **型レベルテスト（`tsd` / `expect-type`）の必須化:** 型定義そのものをユニットテストする文化が成熟。CIに型テストを組み込まないライブラリはメンテナンス不良とみなされるようになっている。
