# CTO Knowledge - 2026-09-08

## Daily Update (2026-09-08)

### 1. Next.js performance optimization 2026

- **ポイント1（Turbopackの本番ビルド標準化）:** Next.js 15以降でTurbopackが本番ビルドでも安定運用され、Webpackと比較してビルド時間が大幅短縮。大規模ページ数を持つ本サイトのような不動産系プラットフォームではCI/CDのフィードバックループが速くなり、開発体験とデプロイ頻度の両方に効く。

- **ポイント2（Partial Prerendering / PPR の実用化）:** 静的シェルを即座に配信しつつ動的部分だけをストリーミングする手法が主流化。物件一覧のような「共通レイアウトは静的、価格や空き状況は動的」なページ構成に相性が良く、TTFBとLCPを同時に改善できる。

- **ポイント3（React Server Components前提のデータフェッチ設計）:** クライアントバンドルを増やさずにDBアクセスを行えるRSCパターンが定着し、`use client`境界を最小限に絞る設計が重要視されている。認証状態やユーザー固有データはできるだけサーバー側で解決し、クライアントJSを削減するのがベストプラクティス。

- **ポイント4（画像・フォント最適化の自動化強化）:** `next/image`と`next/font`がCore Web Vitals対策の中心であり続けており、AVIF優先配信やフォントのセルフホスティング自動化が標準化。物件写真を多用するUIではLCP改善に直結するため優先度が高い。

- **ポイント5（Edge/Node runtimeの使い分けとキャッシュ戦略）:** `fetch`キャッシュやRoute Handlersのrevalidate戦略が精緻化され、地理的に分散したユーザー向けにEdge Runtimeを使うか、DBアクセスの多い処理はNode Runtimeに留めるかの判断が性能とコストの両面で重要になっている。

### 2. React Server Components streaming 2026

**ポイント1:** Next.js 16のPartial Prerendering(PPR)が安定版となり、静的シェルを即座に配信しつつ動的部分をストリーミングで補完する構成が標準化。TTFBの改善とSEOの両立が容易になった。

**ポイント2:** Suspense境界の粒度設計がパフォーマンスチューニングの中心的な論点に。粒度を細かくしすぎるとウォーターフォールが発生するため、データ取得の依存関係に沿った境界設計が重要。

**ポイント3:** RSCペイロードのキャッシュ戦略（`use cache`ディレクティブなど）が実用段階に入り、サーバー負荷とレイテンシを大幅に削減できるようになった。データフェッチ層でのキャッシュキー設計が開発者の腕の見せ所。

**ポイント4:** クライアントバンドルサイズの削減効果が定量的に評価されやすくなり、RSC化によるJS転送量削減が計測・可視化しやすいツールチェーン（バンドルアナライザ等）が整備された。

**ポイント5:** エラーバウンダリとストリーミングの組み合わせで、部分的な失敗時でも他コンポーネントの表示を継続できる耐障害性の高いUXパターンが一般化している。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1: tRPCの採用拡大** フルスタックTypeScriptプロジェクト（Next.js含む）ではtRPCがエンドツーエンドの型安全性を提供し、スキーマ定義とクライアント生成の手間を省けるため、社内API・BFF層での採用が増えている。ただし外部公開APIには不向きで、モバイルや他言語クライアントとの連携にはRESTかGraphQLが依然必要。

- **ポイント2: GraphQLはBFF・複雑なデータ取得に集約** 単純なCRUDではオーバーヘッドが大きいため、GraphQLは「複数ソースを1リクエストに集約する」ユースケース（ダッシュボード、モバイルアプリの初期ロード等）に限定して使われる傾向が強まっている。汎用API化するより、特定画面向けBFFとして設計するのが2026年のベストプラクティス。

- **ポイント3: RESTはOpenAPI+型生成で延命** REST自体は依然主流だが、OpenAPIスキーマからTypeScriptの型を自動生成するツールチェーン（openapi-typescript等）によりtRPC並みの型安全性を後付けできるようになり、「型安全性のためだけにtRPCへ移行する」動機が薄れつつある。

- **ポイント4: sumitsugiの現状に対する示唆** 現在Next.js App Router単体構成のため、外部連携（不動産ポータル連携API等）が発生するまではtRPC導入は過剰。まずはSever ActionsとRoute Handlersで十分であり、外部APIが必要になった時点でREST+OpenAPI型生成を検討するのが妥当。

- **ポイント5: 認証・入力検証はプロトコルに依存せず必須** REST/GraphQL/tRPCいずれを選んでも、Zodによる境界でのバリデーション（`.claude/rules/standards.md`のルール通り）とレート制限・CSRF対策は共通して必要であり、プロトコル選定より先に固めるべき基盤。

### 4. serverless edge computing 2026

- **エッジでのAI推論の主流化:** Cloudflare WorkersやVercel Edge FunctionsでLLM推論を直接実行できるようになり、レイテンシをミリ秒単位に削減できる一方、モデルサイズとコールドスタートのトレードオフを慎重に見極める必要がある。
- **WASMランタイムの成熟:** WebAssemblyベースのエッジランタイムがNode.js互換性を高め、既存コードの移植コストが大幅に下がった。sumitsugiのような画像処理・PDF生成を含む機能は、エッジ実行の候補として検討価値がある。
- **エッジDBとの統合強化:** Cloudflare D1やTurso等、エッジ近接のSQLiteベースDBが実用段階に入り、読み取り中心のワークロード（物件検索・一覧表示）ではオリジンDBへの往復を回避できる。
- **コスト構造の変化:** リクエスト課金からCPU時間課金への移行が進み、重い処理（PDF生成・画像最適化）はエッジではなくサーバーレス関数側に残す判断がコスト最適化の鍵になる。
- **観測性のギャップ:** 分散実行環境ゆえにトレーシング・ログ収集が複雑化しており、OpenTelemetry対応が事実上の標準になりつつある。導入初期から計装しておかないと障害時の切り分けが困難になる。

### 5. authentication security best practices 2026

- **パスキー/WebAuthn標準化:** パスワード+SMS OTPはSIMスワップ・フィッシングに脆弱なため、FIDO2/WebAuthnベースのパスキーをデフォルト認証手段に据え、パスワードは救済手段（アカウント復旧のみ）に格下げするのが2026年の主流。

- **フィッシング耐性MFAの必須化:** TOTPアプリすらリアルタイムフィッシング（AiTM攻撃）で突破される事例が増えているため、デバイス証明書やハードウェアキー（YubiKeyなど）を用いたフィッシング耐性の高い要素を最低1つ組み込むべき。

- **セッション管理とトークン寿命の短縮:** ログイン成功後の「セッション乗っ取り」が主要な侵害経路になっているため、アクセストークンは短命化（15分程度）+リフレッシュトークンのローテーション、デバイスフィンガープリントとの紐付けを徹底する。

- **段階的リスクベース認証:** 全ユーザーに一律で強い認証を課すとUX劣化と離脱につながるため、IPレピュテーション・デバイス履歴・行動パターンをスコアリングし、リスクが高い操作（決済・個人情報変更）にのみステップアップ認証を要求する設計が効果的。

- **シークレット管理の自動化:** APIキーやDBクレデンシャルのハードコードは依然として最大の侵害原因の一つであるため、Vault/KMS等でのシークレット一元管理と自動ローテーション、CI/CDでのシークレットスキャン（gitleaks等）をパイプラインに必須化すべき。

### 6. database architecture Prisma Supabase 2026

- **エッジ最適化とPrisma Accelerate:** Prisma 6以降はエッジランタイム（Vercel Edge, Cloudflare Workers）向けのコネクションプーリングとキャッシュ層が標準化されており、Supabase接続時もPgBouncer経由の直接接続ではなくAccelerate/Data Proxyを挟むことでコールドスタート時のレイテンシを大幅に削減できる。

- **RLS（Row Level Security）とORMの二重防御:** SupabaseのRLSポリシーはDB層での最終防衛線として維持しつつ、Prismaスキーマ側でも型安全なアクセス制御を重ねる「Defense in Depth」構成が主流になっている。前の住人・次の住人間の個人情報分離が必要な本サービスでは、RLS単体に頼らずアプリ層バリデーション（Zod）とセットで設計すべき。

- **マイグレーション管理の一本化:** Prisma MigrateとSupabase CLIのマイグレーションを二重管理すると本番でスキーマドリフトが起きやすいため、2026年時点のベストプラクティスはPrisma Migrateを正とし、Supabase固有機能（RLS、Realtime、Storage）はSQLマイグレーションとして`prisma/migrations`配下に統合管理する方式。

- **リアルタイム機能とコネクション枯渇対策:** 物件のステータス変更（draft/public）をリアルタイム反映する場合、Supabase Realtimeはpostgres_changesではなくBroadcast/Presenceベースの新APIを使う方がDBコネクション消費を抑えられ、Prisma経由の通常クエリと競合しにくい。

- **サーバーレス環境でのコネクション管理:** Next.js 16のServer Actions/RSCから直接Prisma Clientを呼ぶ構成では、関数ごとのコールドスタートでコネクション数が急増しやすいため、SupabaseのTransaction Pooler（port 6543）を必ず使用し、Prisma Client自体はグローバルシングルトン化してホットリロード時の多重生成を防ぐことが必須。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC（Garbage Collection提案）の主要ブラウザ対応が進み、Rustのようなライトウェイト言語だけでなく、GC言語のWasmコンパイルも現実的になってきている。ただしRustはlinear memoryモデルとの相性が良く、依然としてWasm生成言語の第一選択。

- **ポイント2:** `wasm-bindgen`や`wasm-pack`のビルドパイプラインが成熟し、Rust→Wasmのバンドルサイズ最適化（`wee_alloc`代替、`wasm-opt`との統合）が容易になった。SumitsugiのようなSSR中心Next.jsアプリでは、画像処理や物件検索の高速化ロジックをWasmモジュール化する余地がある。

- **ポイント3:** Component Model（WIT/WASI Preview 2）の標準化が進み、Wasmモジュール間の型安全な相互運用が可能になってきている。将来的にマイクロサービス的な機能分割（例: PDF生成、住所ジオコーディング）をWasmコンポーネント単位で切り出せる。

- **ポイント4:** ブラウザ内SIMD命令のサポートが安定し、Rust製Wasmでの画像・動画処理（物件写真の圧縮・EXIF処理など）がネイティブJSより数倍高速に実行できるケースが増えている。

- **ポイント5:** エッジランタイム（Cloudflare Workers, Vercel Edge Functions等）でのWasm実行がデフォルト化しつつあり、Rust製Wasmを使うことでコールドスタート時間をJS実装より大幅に短縮できる — サーバーレス構成のSumitsugiバックエンドにも応用余地あり。

### 8. Next.js App Router patterns 2026

- **ポイント1: Server Actionsのデフォルト化とバリデーション境界:** 2026年時点ではServer Actionsがフォーム処理の主流となり、Zodなどによる入力検証をAction内部で必ず行う設計が定着している。クライアント側の検証は補助的に留め、`"use server"`境界を明確なAPI境界として扱うのがベストプラクティス。

- **ポイント2: Partial Prerendering (PPR) の実用段階への移行:** 静的シェルを即座に返しつつ動的部分をストリーミングするPPRが安定版として広く採用され、物件一覧のような「静的な骨格＋動的な価格/在庫」構成のページでLCPを大幅改善できる。ルートごとに`experimental_ppr`のオン/オフを細かく制御する設計が一般化している。

- **ポイント3: キャッシュ戦略の明示化 (`use cache` ディレクティブ):** Next.js 15以降で導入された`use cache`ディレクティブがApp Routerの標準的なキャッシュ制御手段となり、`fetch`のオプションに依存しない関数レベル・コンポーネントレベルのキャッシュ宣言が推奨される。タグベースの再検証(`revalidateTag`)と組み合わせることで、物件情報更新時の即時反映が実現しやすい。

- **ポイント4: Server Componentsを軸にしたバンドルサイズ最適化:** クライアントコンポーネントの境界を末端の対話的UI（フォーム、モーダル等）に限定し、データ取得・レンダリングロジックはServer Componentsに寄せる設計が定着。これによりJSバンドルサイズを削減し、モバイル回線でのパフォーマンスに直結する。

- **ポイント5: Route Handlersとミドルウェアでの認証・認可の一元化:** 認証チェックをミドルウェアやRoute Handlers層に集約し、各ページ・APIで個別に実装しない構成がセキュリティ上のベストプラクティスとして浸透。多層防御の観点から、Server Actions内でもセッション検証を重複して行う設計が推奨される。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約を前提にした設計:** Vercel Edge FunctionsはNode.js APIの一部が使えないV8アイソレート上で動くため、依存ライブラリを事前に軽量化・Web標準API（fetch, crypto.subtle等）ベースで書くことがコールドスタート短縮とデプロイサイズ削減の鍵になる。

- **Streaming SSRとの組み合わせ:** Next.js 16のPartial Prerenderingと組み合わせ、パーソナライズ部分だけEdgeで動的生成し、静的部分はCDNキャッシュから即返す構成にすることで、TTFBを保ちながら動的な体験（ログイン状態表示など）を提供できる。

- **リージョン選択とデータ近接性:** ミドルウェアや認証チェックなど軽量処理はEdgeに置きつつ、DB接続が必要な処理はEdgeから直接叩かず、リージョン固定のServerless Function/Fluid Computeに委譲する「適材適所」の使い分けが2026年のベストプラクティス。

- **Fluid Computeへの移行:** VercelはFluid Compute（従来のEdge/Serverlessの垣根を減らす実行モデル）を推進しており、同時実行の効率化とコスト最適化（アイドル時間の課金削減）が図れるため、新規プロジェクトではデフォルト採用を検討すべき。

- **可観測性とコスト管理:** Edge Functionsは実行時間・呼び出し回数ベースの課金体系のため、Vercel Observability Plusやログドレインを使って高頻度実行箇所（middlewareの誤用など）を早期に特定し、無駄なEdge実行を削減することが運用コストに直結する。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.xの`satisfies`演算子と`const`型パラメータの組み合わせが定着し、型推論を保ちながら値の妥当性チェックができるパターンが標準化されている。設定オブジェクトやAPIレスポンスの型安全性を保証しつつ、余計な型注釈を減らせるのが実用上のメリット。

- **ポイント2:** Zodなどのランタイムバリデーションライブラリと型定義を一体化する「schema-first」開発が主流になり、`z.infer`で型を自動生成することでスキーマと型の二重管理を排除できる。sumitsugiでも入力検証にZodを使っており、システム境界での型安全性を担保する標準パターンとして機能している。

- **ポイント3:** Branded Types（`type UserId = string & { __brand: 'UserId' }`）によるnominal typingがID系のバグ防止に広く使われ始めており、`propertyId`と`userId`のような同じ`string`型でも意味的に区別してコンパイル時に混同を防げる。

- **ポイント4:** TypeScript 5.5以降のnarrowing改善（`isMobile`のようなユーザー定義型ガードの推論強化）により、Union型のstatusフィールド（例: `'draft' | 'public'`）を扱うコンポーネントでの型ガードコードが簡潔になり、実行時エラーの削減につながっている。

- **ポイント5:** tRPCやHono RPCのようなend-to-end型安全フレームワークが2026年も拡大しており、フロントエンドとバックエンド間でAPI型を自動同期することで、契約のズレによるバグを設計段階で排除するアプローチが標準になりつつある。
