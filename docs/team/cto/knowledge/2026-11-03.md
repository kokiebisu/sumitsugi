# CTO Knowledge - 2026-11-03

## Daily Update (2026-11-03)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Prerenderingの本格活用）:** Next.js 16ではPPR（Partial Prerendering）が安定版となり、静的シェルを即時配信しつつ動的部分のみストリーミングすることでTTFBを大幅短縮できる。物件一覧ページのような「検索条件は動的・レイアウトは静的」な構成に特に有効。
- **ポイント2（React Compilerによる自動メモ化）:** React CompilerがNext.js 16で標準統合され、`useMemo`/`useCallback`の手動最適化が不要になりつつある。既存コンポーネントの手動メモ化コードを棚卸しし、冗長な最適化ロジックを削減できる好機。
- **ポイント3（Turbopackビルドの恩恵）:** Turbopackが本番ビルドでも既定化され、ビルド時間とHMRが大幅改善。`bun run build`のCI実行時間短縮に直結するため、ビルド検証の高速化としてメリットを享受できる。
- **ポイント4（画像・フォント最適化の自動化深化）:** `next/image`のAVIF既定化やフォントのセルフホスティング最適化が進み、LCP改善の多くが設定不要で得られるようになった。物件写真が多い本サービスではCore Web Vitals改善に直結しやすい。
- **ポイント5（Server Actionsのキャッシュ戦略）:** `use cache`ディレクティブによる細粒度キャッシュ制御が実用段階に入り、問い合わせフォームや内見予約などのServer Actionsでも適切なrevalidation設計が重要になる。キャッシュ漏れ・過剰キャッシュの両方に注意が必要。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の標準化:** Next.js ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分だけをストリーミングする構成がデフォルト化。初期表示速度(TTFB/LCP)とパーソナライズの両立が、追加実装なしで実現できる点が実務上の大きな利点。

- **Suspense境界の粒度設計がパフォーマンスの鍵:** コンポーネント単位で`Suspense`を細かく切ることで、重いデータ取得（検索・レコメンド等）が他のUIをブロックしなくなる。弊社サービスでも物件一覧ページの「似た物件」セクションなどは個別にストリーミングさせるべき領域。

- **Server Actions + RSCの合流でAPI層が薄くなる:** フォーム送信やミューテーションをServer Actions経由で直接RSCに繋げる設計が主流化し、従来のREST/API Routeの中間層を減らせる。ただしキャッシュ無効化（`revalidatePath`/`revalidateTag`）の設計ミスが本番バグの温床になりやすく、レビュー時の重点チェック項目。

- **キャッシュ戦略の複雑化とオブザーバビリティの重要性:** RSCのデータキャッシュ・フルルートキャッシュ・クライアントルーターキャッシュが多層化し、「なぜ古いデータが表示されるか」の調査コストが上がっている。ストリーミング導入時はトレーシング（例: Vercel Observability相当）をセットで入れないと障害対応が困難になる。

- **エッジランタイムとの相性:** RSCストリーミングはEdge Runtimeとの組み合わせで地理的レイテンシを大きく削減できるが、Node.js専用ライブラリ（一部のPDF生成・画像処理等）が使えない制約がある。引越し費用の見積りPDF生成など重い処理はNode runtimeに残し、閲覧系ページのみEdge化するハイブリッド構成が現実的。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはTypeScriptモノレポ（フロント・バック同一言語）での採用が定番化しており、型を手書きせずE2Eで安全に共有できる点が、スキーマ定義やコード生成の手間を省ける利点として評価されている。Next.js App Router構成のsumitsugiのような構成では、Server Actions/RSCとtRPCの境界設計が今後の検討ポイントになる。
- **ポイント2:** GraphQLは「複数クライアントが異なる粒度でデータを取得する」ケース（モバイル/Web/パートナーAPIなど）で依然優位だが、単一フロントエンドのみを想定するプロダクトではオーバーエンジニアリングになりやすく、2026年はtRPC/REST+OpenAPIへの揺り戻しが目立つ。
- **ポイント3:** RESTはOpenAPI 3.1 + コード生成（openapi-typescript等）との組み合わせで型安全性のギャップをかなり埋められるようになり、「外部公開API・サードパーティ連携が前提」の場合は依然第一選択。将来的に外部パートナー（不動産業者等）との連携を見据えるならRESTのほうが長期的な互換性管理がしやすい。
- **ポイント4:** 2026年のトレンドとして、BFF（Backend For Frontend）層を薄く持ち、内部通信はtRPCやgRPC、外部公開部分だけRESTで公開するハイブリッド構成が主流になっている。一枚岩のAPI方式を選ぶより、用途別に使い分ける設計判断がベストプラクティス化している。
- **ポイント5:** API設計よりも「型の一貫性とバリデーション（Zodなど）をAPI境界に必ず挟む」運用面が重要度を増しており、sumitsugiのCLAUDE.md規約にもあるようにZodスキーマでの入力検証を徹底することが、プロトコル選定以上に品質・セキュリティに直結する。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** 2026年はLLM推論自体をCDNエッジ（Cloudflare Workers AI、Vercel Edge Functions等）で実行するのが一般的になり、レイテンシを数十ms台に抑えつつサーバーコストを削減できる。弊社のような小規模チームでも、中央集権的なGPUクラスタを持たずに「準リアルタイムAI機能」を提供可能になっている。

- **コールドスタート問題の実質的解消:** V8 isolateベースのランタイム（Workers、Deno Deploy）がコンテナ型サーバーレスを置き換えつつあり、起動遅延がほぼゼロに近づいている。sumitsugiのような物件検索・マッチング機能では、ユーザー体験に直結するため採用を検討する価値が高い。

- **データレイヤーのエッジ分散:** エッジKV（Cloudflare D1/KV, Turso等）によりデータベースクエリ自体をユーザーの地理的近接ノードで処理できるようになり、グローバル展開前提のアーキテクチャが前提化している。現状はNext.js 16 + 単一リージョンDBだが、将来的な多拠点展開時にはこの分散データ戦略の検証が必要。

- **コスト構造の逆転リスク:** 従量課金モデルのエッジ実行は低トラフィック時は圧倒的に安いが、トラフィックが伸びると従来のサーバーより高コストになるケースが増えている。MVPローンチ直後の低トラフィック期はエッジ採用の恩恵が大きいが、スケール時のコストシミュレーションを事前に行うべき。

- **ベンダーロックインの再燃:** 各クラウドのエッジランタイムAPI（Workers API、Edge Runtime API等）の差異が大きく、移行コストが無視できないレベルになっている。現在のVercel依存度が高い構成のまま進めるか、ポータビリティを意識した抽象化レイヤーを入れるかは、ベータローンチ後のスケール戦略と合わせて早期に意思決定すべき論点。

### 5. authentication security best practices 2026

- **パスキー/FIDO2がデフォルト化:** パスワードレス認証（WebAuthn/パスキー）がiOS・Android・主要ブラウザで標準装備となり、フィッシング耐性のある認証がコストなしで実装可能。sumitsugiのような個人情報を扱うサービスでは、パスワード単独の運用はもはやセキュリティ負債になる。

- **トークンのローテーションと短命化:** アクセストークンの寿命を短く（5-15分）保ち、リフレッシュトークンはローテーション必須＋再利用検知（reuse detection）を組み込むのが標準。Next.js App Router構成ではサーバーコンポーネント側でhttpOnly cookieを使い、クライアントにトークンを露出させない設計が重要。

- **認可とRLSの分離設計:** 認証（誰か）と認可（何ができるか）を明確に分離し、物件データのような所有権ベースのリソースはAPI層だけでなくDB層（Row Level Security相当）でも二重に防御する。`'draft'/'public'`のようなステータス制御は特にUIだけでなくAPI/DB両方でチェックが必須。

- **セッション管理の可観測性:** 異常ログイン検知（新デバイス・新地域）やセッション一覧・強制ログアウト機能をユーザーに提供するのが2026年の最低ラインになっている。前の住人/次の住人間で物件情報を引き継ぐsumitsugiの文脈では、引き継ぎタイミングでの権限委譲・セッション無効化のフローを明示的に設計すべき。

- **シークレット管理の自動化:** APIキーやOAuthトークンのハードコードを防ぐだけでなく、短期的に失効するマネージドID（OIDC federation、GitHub ActionsのOIDC連携など）への移行が進んでいる。CI/CDで`CLAUDE_CODE_OAUTH_TOKEN`のような長期シークレットを使う場合も、スコープ最小化と定期ローテーションの運用ルールを明文化しておくべき。

### 6. database architecture Prisma Supabase 2026

- **エッジ対応の重要性:** Supabaseはグローバルエッジでのレイテンシ改善（Edge Functions、リードレプリカの地理分散）を強化しており、日本国内ユーザー向けサービスでもリージョン選択とコネクションプーリング（PgBouncer/Supavisor）の設計が性能に直結する。

- **Prisma × Postgres接続管理:** サーバーレス環境（Vercel等）でのコネクション枯渇対策として、Prisma Accelerate（グローバルキャッシュ＋コネクションプーリング）とSupabaseのPooler設定を併用するのが2026年時点の標準パターンになっている。

- **型安全性とRLSの両立:** PrismaのスキーマからTypeScript型を自動生成しつつ、SupabaseのRow Level Security（RLS）をDB層で強制するハイブリッド構成が増えており、アプリ層とDB層で二重に検証ロジックを持たせず、RLSをセキュリティの最終防衛線として位置づける設計が推奨されている。

- **マイグレーション運用:** Prisma Migrateの宣言的マイグレーションとSupabaseのブランチング機能（開発用DBブランチ）を組み合わせることで、本番前のスキーマ変更をプレビュー環境で検証するCI/CDフローが一般化している。

- **リアルタイム機能の活用判断:** Supabase Realtime（Postgres Changes）はチャットや通知など低頻度更新には適するが、高頻度書き込みを伴う機能ではコスト・スケーラビリティの観点から別途WebSocket基盤やポーリングとの比較検討が必要——sumitsugiの物件ステータス更新や引っ越し費用計算のような単発更新系には標準的なREST/RPCで十分なケースが多い。

### 7. WebAssembly Rust performance 2026

- **ポイント1: wasm-bindgenとwasm-packの最適化進展** Rust→WASMのビルドチェーンはLTOとサイズ最適化（`opt-level = "z"`, `wasm-opt`）が標準化され、バンドルサイズを数百KB単位で削減できるようになっている。フロントエンド配信コストを抑えるなら、ビルド設定の見直しだけで数十%の改善余地がある。

- **ポイント2: WASM GC / Component Modelの実用化** WasmGCとComponent Modelが主要ランタイム（wasmtime, V8）で安定運用レベルに達し、Rust以外言語とのモジュール間連携やホスト関数呼び出しのオーバーヘッドが大幅に減少した。マルチ言語マイクロフロントエンド構成を検討する際の選択肢が広がっている。

- **ポイント3: SIMD・スレッド対応で計算集約処理が実用域に** `wasm32-simd128`とWeb Workers経由のマルチスレッド実行が安定し、画像処理・暗号化・物件データの座標計算など計算負荷の高い処理をクライアント側にオフロードできる。サーバーコストを抑えつつUXを向上させる手段として有効。

- **ポイント4: Node.js/Bun上でのネイティブ代替としての採用拡大** BunやDenoがWASMモジュールを一次サポートし、Rust製の画像リサイズ・PDF生成ロジックをサーバーサイドでネイティブバイナリ同等の速度で実行できる。本プロダクトのPDF生成（引き継ぎ資料等）処理をRust+WASM化すれば、Node bindingより配布・デプロイが簡素化される。

- **ポイント5: デバッグ・プロファイリング環境の成熟** ソースマップ対応やDWARFベースのデバッグツールがブラウザDevToolsに統合され、WASM特有の「ブラックボックス化」問題が解消されつつある。本番導入時の障害対応コストが以前より下がっている点は採用判断の後押しになる。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16ではPPRが安定版として扱われ、静的シェルと動的コンテンツを1つのルートで組み合わせられる。物件一覧ページのようにヘッダー/レイアウトは静的配信しつつ、在庫状況や価格だけをストリーミングで最新化する構成が標準になってきている。

- **Server Actionsのセキュリティ強化:** フォーム送信やミューテーションをServer Actionsに寄せる流れが定着したが、2026年はCSRF対策・認可チェックをアクション内で明示的に行う設計が重視されている。`src/app`配下でServer Actionを使う場合、入力値はZodで必ず検証し、セッション確認を関数冒頭で行うパターンを徹底すべき。

- **キャッシュ戦略の明示化（`use cache` ディレクティブ):** 旧来の暗黙的fetchキャッシュから、`use cache`やキャッシュタグによる明示的な制御へ移行が進んでいる。引越し費用計算や前の住人の活動歴など更新頻度が異なるデータは、タグベースの再検証（`revalidateTag`）で粒度を分けるのが現在のベストプラクティス。

- **Server/Client境界の最小化:** Client Componentの「境界を小さく、葉に近い場所に置く」設計が成熟し、Context APIの濫用を避けてServer Componentでデータを取得しClientにはインタラクション部分のみ渡す構成が主流。`auth-context.tsx`のような認証状態も、可能な範囲でServer Componentでの事前解決＋最小限のClient hydrationに置き換える動きがある。

- **Route Handlersの位置づけの変化:** 外部webhookや決済連携など「本当に外部I/Oが必要な場合」のみRoute Handlersを使い、内部データ取得はServer Actions/Server Componentsに統一する設計が推奨されるようになった。これによりAPI層の二重管理（Route HandlerとServer Action両方でロジックを書く）を防げる。

### 9. Vercel Edge Functions optimization 2026

- **Fluid Compute採用の加速:** Vercelの新しい実行モデルでは、同一インスタンス内で複数リクエストを並行処理できるため、Edge Functionsのコールドスタート削減とコンピュート費用の大幅圧縮が進んでいる。sumitsugiのような物件検索API等、スパイクが読みにくいトラフィックには特に有効。

- **Edge ConfigとKVの使い分けが鍵:** 低レイテンシが必要な設定値・フラグはEdge Config（グローバルレプリケーション、読み取り特化）に、動的かつ更新頻度の高いデータはKVに分離する設計が定着しつつあり、ミドルウェアでの認可チェックなどに効果的。

- **Node.js Runtime互換性の拡大でEdge/Serverlessの境界が曖昈化:** 2026年はEdge RuntimeでサポートされるNode.js APIが増え、以前はServerless Functionでしか動かなかった処理（一部の暗号処理・ファイルI/O）もEdgeに移行可能になってきている。移行判断は「本当にグローバル分散が必要か」で見極めるべき。

- **Streaming + Partial Prerenderingとの組み合わせ最適化:** Next.js 16のPPRとEdge Functionsを組み合わせることで、静的シェルを即時配信しつつ動的部分（認証状態、パーソナライズ）だけをEdgeでストリーミングする構成が標準化しつつある。認証コンテキスト（`auth-context.tsx`）配下のユーザー個別表示に適用余地がある。

- **リージョン選定とデータ局所性のコスト影響:** Edge Functionsはデフォルトで実行リージョンが動的決定されるが、DB（Supabase等）との往復レイテンシがボトルネックになりやすいため、`regions`設定で実行先をDBリージョンに固定する最適化が2026年のベストプラクティスとして広まっている。

### 10. TypeScript type safety patterns 2026

- **型推論の強化によるZod/Valibot連携:** 2026年はスキーマ定義から型を自動導出する`z.infer`的パターンがさらに普及し、APIバウンダリでの型安全とランタイム検証を1つの定義で済ませる開発が標準化しています。sumitsugiでも`src/lib`のZodスキーマをAPI入力検証と型定義の単一ソースとして活用すべきです。

- **Template Literal Typesによるルーティング・URL安全化:** Next.js App Routerの`src/app/properties/[id]`のような動的ルートに対し、Template Literal Typesでパスを型レベルで検証するパターンが定着し、存在しないルートへのリンクをビルド時に検出できます。

- **`satisfies`演算子の定着:** 型を狭めすぎずに追加の型チェックを行う`satisfies`が、`site-config.ts`のような設定オブジェクトの型安全性向上に広く使われるようになっています。型推論を保ちながら誤字や欠落プロパティをコンパイル時に検出できる点が実用的です。

- **Branded Types/Nominal Typingの普及:** `'draft' | 'public'`のようなUnion型だけでなく、IDやステータス値をBranded Typesでラップし、構造的に同一だが意味が異なる値（例: `PropertyId`と`UserId`）の取り違えをコンパイル時に防ぐパターンが、特にEC/不動産系ドメインで増えています。

- **AIコード生成とTypeScriptの型チェックの組み合わせ:** Claude Codeのような自動実装ワークフローが増える中、「ビルドが通ること」だけでなく型の網羅性（exhaustive check、`never`型でのswitch文完全性チェック）を自動検証するCIゲートが、AI生成コードの品質保証として重要性を増しています。これはまさにsumitsugiの`autonomous-developer.yml`のような自動化パイプラインに直結する観点です。
