# CTO Knowledge - 2026-06-22

## Daily Update (2026-06-22)

### 1. Next.js performance optimization 2026

- **Turbopackの本格採用:** Next.js 16ではTurbopackが本番ビルドでも標準化され、Webpack比で大幅なビルド時間短縮が見込めます。大規模化する前にCIのビルド時間をベースライン計測しておくと、将来の劣化を早期検知できます。

- **Partial Prerendering (PPR) の活用:** 静的シェルを即時配信しつつ動的部分のみストリーミングする設計により、TTFBとLCPを同時に改善できます。物件一覧ページのような「静的レイアウト＋動的データ」構成に特に効果的です。

- **Server ComponentsでのデータフェッチパターンWaterfall回避:** ネストしたコンポーネントで逐次fetchするとレンダリングが直列化しボトルネックになるため、`Promise.all`での並列フェッチやキャッシュタグ設計（`fetch`のrevalidateTag）を徹底すべきです。

- **画像・フォント最適化の自動化への依存リスク:** `next/image`や`next/font`の自動最適化は強力ですが、CDN・キャッシュヘッダー設定をデフォルトのままにすると本番環境で期待した効果が出ないケースがあるため、Vercel以外のホスティングを使う場合は配信経路を個別検証する必要があります。

- **Bundle分析の定例化:** App RouterではRoute Segmentごとにバンドルが分割されるため、`@next/bundle-analyzer`を定期実行し、shadcn/uiコンポーネントの過剰インポートやクライアントコンポーネント境界の肥大化を継続的に監視する運用が重要です。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** Next.js 16ではSuspenseとServer Componentsの組み合わせによる段階的ストリーミングがデフォルト化し、初期表示（TTFB）を保ったまま遅いデータ取得を後追いで流し込めるようになっています。ローディングUIを各コンポーネント単位で設計することがUX改善の鍵です。

- **Partial Prerendering(PPR)の実用化:** 静的シェルを即時返しつつ動的部分のみストリーミングするPPRが主流になり、ECサイトや物件一覧のような「ヘッダーは静的・在庫情報は動的」なページに特に有効です。sumitsugiの物件一覧ページにも適用余地があります。

- **キャッシュ戦略の複雑化:** RSCのストリーミングが進むほど、どのコンポーネントをキャッシュ可能にするか（`use cache`ディレクティブ等）の設計判断がパフォーマンスを左右し、キャッシュキーの設計ミスがバグの温床になりやすい点に注意が必要です。

- **エラーバウンダリの粒度設計:** ストリーミング中に一部コンポーネントが失敗した場合の挙動（部分的なエラー表示か全体ロールバックか）を明確に設計しないと、ユーザーに不完全な画面を見せてしまうリスクがあります。

- **計測ツールの追従:** ストリーミングはWaterfallではなくパラレル/段階的なリクエストパターンになるため、従来のLighthouse的な単一ロード計測ではなく、Server Timing APIやReal User Monitoring(RUM)でストリームごとのチャンク到達時間を可視化する必要があります。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはNext.js + TypeScriptモノレポ構成と相性が良く、フロントエンド-バックエンド間で型を共有できるため、スキーマ定義やコード生成の手間を省きつつ開発速度を上げられる。当社のような単一リポジトリ構成のMVPフェーズでは特に有効。
- **ポイント2:** GraphQLは複雑なリレーション（物件・前の住人・次の住人など多対多データ）を持つプロダクトでオーバーフェッチ/アンダーフェッチを防げる一方、N+1問題やキャッシュ戦略の設計コストが高く、チーム規模が小さいうちは投資対効果が薄い。
- **ポイント3:** REST APIは依然としてサードパーティ連携（決済、外部弁護士向けシステム連携、将来的なパートナーAPI公開）において業界標準であり、OpenAPI/Zodスキーマで型安全性を担保しつつ外部公開インターフェースとして維持するのが現実的。
- **ポイント4:** 2026年のトレンドとして、Server ActionsやRSC（React Server Components）がAPI層の一部を代替し始めており、Next.js 16採用済みの当社では、内部CRUD操作をtRPC/Server Actionsに寄せ、外部公開APIのみRESTで切り出す「ハイブリッド構成」が現実的な落とし所。
- **ポイント5:** どの方式を選ぶにせよ、Zodによる境界での入力検証とエラーハンドリングは標準化（`.claude/rules/standards.md`にも明記）すべきで、API層の設計よりも「型安全性とバリデーションの一貫性」の方が長期的な保守コストを左右する。

### 4. serverless edge computing 2026

- **エッジでのLLM推論最適化:** 2026年はCloudflare Workers AIやVercel Edge Functionsで軽量モデル（量子化・蒸留版）をエッジ実行する事例が一般化し、レスポンス遅延を50ms以下に抑える設計が標準になりつつあります。

- **コールドスタート問題の実質的解消:** V8 isolatesベースのランタイム（Deno Deploy、Cloudflare Workers）の進化により、コールドスタートが1ms未満まで短縮され、低トラフィックなSaaS機能でも常時稼働サーバーが不要になっています。

- **データレイヤーのエッジ移行:** Turso、PlanetScale、Cloudflare D1などのエッジネイティブDBが普及し、読み取りレイテンシをユーザーの地理的位置に応じて最小化する「データもエッジに置く」設計が主流化しています。

- **コスト構造の変化に注意:** 従量課金モデルは低〜中トラフィックでは大幅に安くなりますが、高トラフィック・長時間実行ワークロードでは従来のコンテナ/VM運用より割高になるケースがあるため、見積もり時にトラフィックパターンの精査が必須です。

- **Next.js 16との相性:** App RouterのEdge Runtimeサポートが成熟し、本プロジェクトのスタック（Next.js 16）でも特定ページ（物件検索・地図表示など地理依存の機能）をエッジ関数化することで、グローバル展開時のレイテンシ改善が見込めます。

### 5. authentication security best practices 2026

- **パッキーレス認証の主流化:** FIDO2/WebAuthnベースのパスキーがフィッシング耐性の高い標準になっており、SMS OTPやパスワードのみの認証は段階的に廃止すべきフェーズに入っている。実装コストも各ブラウザ・OSのネイティブサポートで大幅に下がっている。

- **継続的リスクベース認証:** ログイン時の一回認証だけでなく、デバイスフィンガープリント・行動パターン・IPレピュテーションを組み合わせたセッション中のリスク再評価が標準化しつつあり、異常検知時に再認証を要求するアダプティブMFAが必須になっている。

- **トークン管理の厳格化:** JWTやセッショントークンの有効期限を短く保ち、リフレッシュトークンのローテーション・バインディング（デバイス/IPと紐付け）を行うことで、トークン漏洩時の被害範囲を最小化するパターンが重要。`httpOnly`/`Secure`/`SameSite=Strict`クッキーの徹底も基本だが軽視されがち。

- **サプライチェーン経由の認証リスク:** OAuth/OIDCのサードパーティ連携（ソーシャルログイン等）における同意フィッシングやリダイレクトURI検証不備が攻撃ベクトルとして増加しており、redirect_uriの厳密な許可リスト管理とstate/PKCEパラメータの必須化が重要。

- **ゼロトラスト前提の権限設計:** 認証（誰か）と認可（何ができるか）を分離し、最小権限原則のもとリソース単位でのアクセス制御（RBAC/ABAC）を行うことで、認証突破後の被害拡大を防ぐ設計が前提になっている。sumitsugiのような物件情報・個人情報を扱うプラットフォームでは特に、`seller`/`buyer`ロール間のデータアクセス境界をAPI層で厳密に検証する必要がある。

### 6. database architecture Prisma Supabase 2026

- **ポイント1（Prisma Accelerateとエッジ最適化）:** Prismaはエッジランタイム（Vercel Edge, Cloudflare Workers等）対応が進み、Prisma Accelerateによるコネクションプーリング＋クエリキャッシュが標準的な選択肢になっている。サーバーレス環境でのDB接続枯渇問題を避けるため、本番では素のPrismaクライアントよりAccelerateやPgBouncer経由の接続を必須にすべき。

- **ポイント2（SupabaseのRow Level SecurityとPrismaの併用）:** Supabaseの強みであるRLS（行レベルセキュリティ）はPrisma Migrate管理下のスキーマでは適用漏れが起きやすく、マイグレーションファイルにRLSポリシーをSQLで明示的に含める運用が重要。Prisma側のスキーマ変更とSupabase Studioでの直接変更が競合しないよう、スキーマ変更経路を一本化するルールが必要。

- **ポイント3（型安全性とリアルタイム機能の両立）:** PrismaのTypeScript型生成とSupabaseのRealtime（Postgres Changes）を組み合わせる際、Prismaのモデル定義とRealtimeのpublication設定がズレやすいため、型定義とDB側publicationを同期するスクリプトをCIに組み込むのが2026年のベストプラクティス。

- **ポイント4（マイグレーション戦略の一本化）:** SupabaseのCLIマイグレーションとPrisma Migrateを両方使うと履行順序が壊れるリスクが高いため、どちらか一方（多くのチームはPrisma Migrate）に統一し、Supabase固有機能（Auth, Storage, RLS）はSQLマイグレーションファイル内で管理するのが安全。

- **ポイント5（コスト最適化とプーリング設計）:** Supabaseのプーラー（Supavisor）とPrismaの接続モードを正しく設定しないと、特にサーバーレスデプロイで接続数超過やレイテンシ悪化が起きるため、トランザクションモード/セッションモードの使い分けをアーキテクチャ設計の初期段階で決めておくべき。

### 7. WebAssembly Rust performance 2026

- **WASI Preview 2とComponent Model:** WASI 0.2系の安定化に伴い、Rustでコンパイルしたコンポーネント間の言語非依存なインターフェース連携が容易になり、マイクロサービス的にWasmモジュールを組み合わせる設計が実用段階に入っている。

- **SIMD・スレッド対応の成熟:** `wasm32-unknown-unknown`でのSIMD128命令とWasm Threads(共有メモリ+Atomics)のサポートが主要ブラウザ・ランタイムで揃い、画像処理や数値計算系ワークロードでネイティブに近い性能が出しやすくなっている。

- **AOTコンパイル・ランタイムの多様化:** Wasmtime/Wasmer/WasmEdgeなどがAOTキャッシュやコンポーネントプリロードを強化し、コールドスタートのレイテンシが大幅に改善。サーバーレスやエッジ実行でRust+Wasmの採用ハードルが下がっている。

- **バイナリサイズ最適化の重要性:** `wasm-opt`、`twiggy`、`wee_alloc`代替の軽量アロケータなどのツールチェーンが洗練され、依存クレートの見直しと組み合わせることでバンドルサイズを数十〜数百KB単位で削減できる事例が増えている。

- **デバッグ・プロファイリング体験の向上:** DWARF対応のソースマップやブラウザDevToolsのWasm統合が進み、Rustのスタックトレースやステップ実行がネイティブ開発に近い感覚で行えるようになった点が、本番導入の心理的障壁を下げている。

### 8. Next.js App Router patterns 2026

- **Server Components優先設計:** App RouterではデフォルトでServer Componentsを使い、Client Componentsは`'use client'`境界を末端のインタラクティブ要素に限定するのが定石。バンドルサイズとTTFBの両方を改善でき、特にPartial Prerendering（PPR）と組み合わせると静的シェル＋動的ストリーミングのハイブリッドが実現しやすい。

- **`use cache`ディレクティブとキャッシュ戦略の明示化:** Next.js 15以降で導入された`use cache`により、データ取得・計算結果のキャッシュ範囲をコンポーネント/関数単位で明示できるようになった。暗黙的なfetchキャッシュに依存せず、`revalidate`やタグベース無効化（`revalidateTag`）を組み合わせた設計が推奨される。

- **Server Actionsはミューテーション専用、読み取りはRSCで:** Server Actionsをデータ取得に流用するアンチパターンが減り、「書き込みはServer Action、読み取りはRSC＋fetch」という分離が定着。バリデーションはZodで境界（Server Action入口）に集約し、型安全性をクライアント〜サーバーで一貫させる。

- **Streaming + Suspenseによる段階的UI:** `loading.tsx`やネストした`<Suspense>`境界を細かく設計し、重いデータ取得を持つセクションだけを遅延ストリーミングすることでLCPを改善。Airbnb的なリスト/詳細ページ（sumitsugiの物件一覧・詳細など）では、上部の重要情報を先に出し、レビューや関連物件など下位コンポーネントを後から流すパターンが効果的。

- **Edge/Node runtimeの使い分けとObservability:** 認証・DBアクセスが必要なルートはNode runtime、軽量な変換・リダイレクトはEdge runtimeに振り分けるのが2026年のベストプラクティス。`instrumentation.ts`によるOpenTelemetry連携で、Server Components/Actionsのレイテンシを可視化し、本番のボトルネックを特定しやすくする。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化:** Edge Functionsはランタイムが軽量なV8 isolateベースのため、Node.js Functionsと比較してコールドスタートが大幅に短縮される。ただし依存パッケージのバンドルサイズが増えるとisolate初期化が遅延するため、不要なライブラリのimportを徹底的に削ぎ落とす必要がある。

- **リージョン配置とデータ局所性:** `sumitsugi`のような物件検索・問い合わせフローはレイテンシ影響が大きいため、Edge Middlewareでの地理的ルーティングとデータベース（Supabase等）のリージョンを揃えることが重要。Edgeで処理を分散しても、DBアクセスが遠隔だとボトルネックが移動するだけになる。

- **Streaming SSRとの組み合わせ:** Next.js 16のPartial Prerendering（PPR）とEdge RuntimeのStreaming Responseを組み合わせることで、静的な骨格を即時配信しつつ動的部分（在庫状況・価格等）を後続でストリーミングできる。これにより認知的なTTFBが改善し、物件一覧ページのような動的コンテンツが多いページでもLCPを抑えられる。

- **Edge Configとフィーチャーフラグの活用:** Vercel Edge Configを使えば、デプロイなしでA/Bテストや機能フラグの切り替えがEdgeレベルで低レイテンシに行える。ベータローンチ前の段階的機能公開（例：特定エリアのみ先行公開）に向いている。

- **コスト管理の落とし穴:** Edge Functionsは実行時間課金ではなく呼び出し回数・帯域でコストが積み上がる構造のため、画像最適化やリダイレクトロジックを安易にEdgeに置くと想定外のコスト増になりやすい。重い処理はNode.js Functions側に残し、Edgeはルーティング・認証チェックなど軽量な前処理に限定するのが2026年のベストプラクティス。

### 10. TypeScript type safety patterns 2026

- **ポイント1: 型レベルプログラミングの実用化:** TypeScript 5.x系で`satisfies`演算子やconst type parametersが定着し、Zodなどのスキーマライブラリと組み合わせた「実行時検証と型定義の一体化」が標準パターンになっている。APIレスポンスやフォーム入力の境界で型安全性を保証しつつ、型定義の二重管理を排除できる点が開発効率に直結する。

- **ポイント2: ブランド型・Opaque型による意味的型安全性:** `UserId`と`OrderId`のような構造的には同じstring型でも、ブランド型（branded types）を使って意図的に区別することでID取り違えバグをコンパイル時に検出できる。sumitsugiのような不動産プラットフォームでは`PropertyId`や`SellerId`の混在を防ぐために特に有効。

- **ポイント3: テンプレートリテラル型による文字列の型安全化:** ルーティングパスやCSSクラス名、i18nキーなどをテンプレートリテラル型で制約することで、ハードコードされた文字列のtypoをビルド時に検知できる。Next.js App Routerのパス定義やTailwindのユーティリティクラス管理との相性が良い。

- **ポイント4: `unknown`優先とtype guardの徹底:** `any`の使用を完全に排除し、外部入力は`unknown`で受けてZodなどでパースする「parse, don't validate」が事実上の標準になっている。これによりランタイムエラーの大半をビジネスロジック層に到達する前に潰せる。

- **ポイント5: 型チェックのCI必須化とパフォーマンス最適化:** `tsc --noEmit`をCIのビルドステップに必ず含めることに加え、大規模化したプロジェクトではproject references（`tsconfig.json`の分割）やincremental buildを使い、型チェック時間を線形に増やさない工夫が重要になっている。本プロジェクトの「Build Integrity」ルール（`bun run build`必須）はこの観点で既に正しい方向性。
