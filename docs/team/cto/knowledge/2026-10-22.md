# CTO Knowledge - 2026-10-22

## Daily Update (2026-10-22)

### 1. Next.js performance optimization 2026

- **ポイント1（React Server Components とキャッシュ戦略の成熟）:** Next.js 15/16でのPartial PrerenderingとCache Componentsの実用化が進み、静的部分を即時配信しつつ動的部分のみストリーミングする構成が標準化している。`use cache`ディレクティブによる明示的キャッシュ境界の指定が、暗黙的なfetchキャッシュよりも予測可能で推奨される。

- **ポイント2（Turbopackのビルド高速化）:** Turbopackが本番ビルドでも安定版となり、大規模アプリでのビルド時間が大幅に短縮。開発体験だけでなくCI/CDパイプラインの所要時間削減に直結するため、本プロジェクトのような小〜中規模リポジトリでも`next build --turbo`の採用を検討する価値がある。

- **ポイント3（画像・フォント最適化の自動化深化）:** `next/image`のAVIF優先配信とレイアウトシフト抑制、`next/font`のセルフホスティング自動化により、Core Web Vitals（特にLCP・CLS）対策がほぼデフォルトで担保される。物件写真を多用するsumitsugiのようなサービスでは、画像最適化設定の見直しがUX改善に直結する。

- **ポイント4（Server ActionsとMutationのエッジ実行）:** Server Actionsがエッジランタイムでも安定動作するようになり、フォーム送信や引越し費用計算などの処理をユーザーに地理的に近い場所で実行できる。レイテンシ削減だけでなく、クライアント側JSバンドルの軽量化にも寄与する。

- **ポイント5（計測駆動の最適化）:** Vercel AnalyticsやWeb Vitals APIとの統合が強化され、実ユーザー環境（RUM）でのパフォーマンス劣化を本番デプロイ前に検知するワークフローが一般化している。物件一覧や詳細ページなどトラフィックの多いページから優先的にモニタリングを導入すべき。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16ではPPRが安定版となり、静的シェルを即座に返しつつ動的部分（物件の空き状況や価格など）だけをストリーミングで後から流し込めます。`properties/`一覧ページのように「骨格は固定・データは可変」なページでTTFBを大幅短縮できるため、優先的に導入する価値があります。

- **Suspense境界の粒度設計がパフォーマンスを左右:** 2026年のベストプラクティスは「ページ単位」ではなく「カード単位・セクション単位」でSuspenseを切ることです。例えば物件カードごとに境界を設けると、1件の画像取得が遅れても他のカードの表示をブロックしません。粒度が粗いとウォーターフォールが発生し、せっかくのストリーミングの恩恵が消えるので注意が必要です。

- **`use cache` ディレクティブとストリーミングの併用:** Next.js 16の`use cache`は、ストリーミングされるRSCペイロードにもキャッシュレイヤーを挟めるようになりました。前の住人のプロフィールなど更新頻度が低いデータはキャッシュ＋ストリーミングを組み合わせ、引越し費用の計算のような動的データのみをSuspenseで遅延させる、という使い分けが効果的です。

- **Server Actions のストリーミングフィードバック:** フォーム送信（内見予約など）でServer Actionsの結果をストリーミングで段階的に返すパターンが普及しています。`useActionState`と組み合わせ、処理中→途中結果→完了のUIを段階的に更新することで、多段階フローのUXが向上します。認証や決済が絡む箇所はSecurity Reviewと合わせて導入する必要があります。

- **エッジでのストリーミングはコスト対効果を見極める:** グローバル配信が前提でない限定ユーザー向けサービス（国内の住み替えマッチングなど）では、エッジランタイムでのストリーミングはレイテンシ改善より運用複雑化のコストが先に出るケースが多く、Node.jsランタイム＋リージョン最適化で十分な場合が多いです。

### 3. API design REST GraphQL tRPC 2026

- **APIファーストのハイブリッド戦略:** 2026年はREST/GraphQL/tRPCの「どれか一つ」ではなく、外部公開API（パートナー/サードパーティ向け）はRESTまたはGraphQL、内部のTypeScriptフルスタック間通信はtRPCという使い分けが主流。sumitsugiのようにNext.js App Router + TypeScriptで一枚岩的に書けるなら、社内API層はtRPCでエンドツーエンドの型安全性を取り、外部連携が必要になった時点でREST層を追加するのが現実的。

- **tRPCはモノレポ・単一言語チームで最大効果:** フロントとバックエンドが同じTypeScriptコードベース（sumitsugiのApp Router構成）にある場合、tRPCはスキーマ重複やコード生成ステップを排除し、Zodバリデーションとも直結できる。`.claude/rules/standards.md`の「Zodスキーマで境界検証」という方針とも自然に噛み合う。

- **GraphQLは「クライアントの多様性」が出た時に初めて検討:** モバイルアプリ・外部パートナー・複数フロントエンドが増えてoverfetching/underfetchingが問題化した段階で導入を検討すべきで、MVPフェーズのsumitsugiには時期尚早。早期導入はリゾルバのN+1問題やキャッシュ戦略の複雑さというコストに対してリターンが小さい。

- **型安全性とランタイム検証の両立が標準に:** 2026年のベストプラクティスはOpenAPI/GraphQLスキーマからの型生成ではなく、Zod（またはts-rest/Valibot）でスキーマを単一定義し、型とランタイム検証を同時に導出する手法が定着。これにより「ビルドは通るがランタイムで型不一致」という事故を防げる。

- **エッジ・サーバーレス環境でのAPI設計:** Next.jsのApp RouterでRoute HandlersをEdge Runtimeに配置する場合、tRPCのバッチング/ストリーミング機能とVercel等のエッジ関数のコールドスタート特性を考慮した設計が必要。引越し費用計算など同期的で軽量な処理はエッジに向くが、将来的に決済やPDF生成などの重い処理を追加する際はNode.js Runtimeへのルーティング分離を検討すべき。

### 4. serverless edge computing 2026

- **コールドスタートの実質ゼロ化:** V8 isolateベースのランタイム（Cloudflare Workers, Deno Deploy等）が進化し、2026年にはエッジでのコールドスタートが1ms未満まで短縮。SSRやAPI Routesをエッジに配置する判断がデフォルト化している。

- **エッジでのステートフル処理:** Durable Objects / Workers KV / D1のような分散ステート管理がエッジ単体で完結可能になり、従来は中央サーバー必須だったセッション管理や認証もエッジで処理できる。sumitsugiのようなSSRアプリでも、物件検索の地理的局所性を活かしたエッジキャッシュ戦略が有効。

- **AI推論のエッジシフト:** 軽量LLM推論（ルーティング・分類・レコメンド）をエッジで実行するパターンが普及し、レイテンシ要件の厳しいUX（検索サジェスト等）に適用されつつある。本格的な生成AIはまだ中央集権的なAPIに依存するケースが多く、用途の切り分けが重要。

- **Next.js 16とエッジランタイムの互換性拡大:** App Routerのedge runtimeサポートが成熟し、Node.js APIへの依存を減らせば大半のページ・APIをエッジで動かせるようになった。ただしファイルシステムアクセスや一部npmパッケージは依然Node.jsランタイムが必要で、全面移行には注意が必要。

- **コスト構造の変化:** 従量課金のエッジ実行モデルにより、低トラフィック期のインフラコストが大幅に下がる一方、ピーク時のコスト予測が難しくなる。MVPローンチ初期のsumitsugiのようなプロダクトには適しているが、スケール後のコスト監視体制が別途必要。

### 5. authentication security best practices 2026

- **パスキー/FIDO2が標準化:** パスワードレス認証（WebAuthn/Passkeys）がフィッシング耐性のあるデフォルト手段として普及し、SMS OTPは中間者攻撃に弱いため補助手段に格下げすべきです。

- **トークンのライフサイクル管理:** JWTを使う場合は短命アクセストークン＋リフレッシュトークンのローテーション＋サーバー側での即時失効（blocklist/DB検証）を組み合わせ、ステートレスの利便性と即時無効化のトレードオフを管理する必要があります。

- **セッション・デバイスバインディング:** 認証後のセッションをIP/デバイスフィンガープリントと緩やかに紐付け、異常な変化（地理的ジャンプ、新デバイス）を検知してre-authを要求するリスクベース認証が標準的になっています。

- **Zero Trust的な認可の分離:** 認証（誰か）と認可（何ができるか）を明確に分離し、RBAC/ABACをAPI境界（例: Next.jsのMiddleware/Route Handler）で一貫して検証、クライアント側のロールチェックのみに依存しないことが重要です。

- **シークレット管理の自動化:** APIキーやセッション署名鍵はコードに埋め込まず環境変数＋シークレットマネージャーで管理し、定期ローテーションと漏洩検知（GitHub Secret Scanningなど）をCIパイプラインに組み込むことが前提になっています。

### 6. database architecture Prisma Supabase 2026

- **スキーマ駆動開発の深化:** Prisma 6系はSupabaseのRow Level Security (RLS)との統合が進み、Prisma Schema内で直接RLSポリシーを定義・管理できるようになりつつある。マイグレーションとセキュリティポリシーを同一ワークフローで扱えるため、`sumitsugi`のような物件データ・個人情報を扱うサービスでは監査性が向上する。

- **Edge Runtime対応とコネクションプーリング:** Next.js 16のServer Components/Edge Functionsから直接Supabaseに接続する構成が増え、Prisma Accelerate等のコネクションプーラーが必須化している。サーバーレス環境でのコネクション枯渇を避けるため、`src/lib/data.ts`層でのプーリング設定を早期に検証すべき。

- **Realtime機能とのハイブリッド運用:** SupabaseのRealtime（Postgres Changes）とPrismaのORM層を併用するケースが一般化し、「書き込みはPrisma、購読はSupabase Client」という責務分離パターンが定着している。前の住人⇄次の住人間のメッセージ機能などリアルタイム性が必要な領域ではこの併用を検討する価値がある。

- **型安全なマイグレーション運用:** `prisma migrate diff`とSupabase CLIのマイグレーション管理を組み合わせ、本番適用前にスキーマドリフトを検出するCIパイプラインが標準になってきている。`'draft' | 'public'`のようなUnion型のステータス変更時は、この仕組みで本番DBとの不整合を事前に検知できる。

- **コスト最適化としてのRLS活用:** Supabaseの無料〜Proプラン移行期にあるスタートアップでは、アプリケーション層の認可ロジックをRLSに移管してAPI呼び出し数とサーバー負荷を削減する動きが加速している。法務確認中の個人情報保護要件とも相性が良く、ローンチ前のセキュリティレビューで検討する余地がある。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデルの成熟:** WASM Component Modelが標準化され、言語間（Rust/Go/JS）でのゼロコストな相互運用が実用レベルに到達。Rustはwit-bindgenの改善により、複数言語混在のマイクロサービス的アーキテクチャをブラウザ外でも構築しやすくなっている。

- **SIMDとマルチスレッドの定着:** WASM SIMD128とシェアードメモリ+Web Workersの組み合わせが主要ブラウザで安定運用可能になり、Rustの`wasm-bindgen`/`rayon`経由で画像処理・物理演算系のワークロードがネイティブの70-90%程度の性能に達するケースが増加。

- **バイナリサイズ最適化の自動化:** `wasm-opt`やLTO、`opt-level = "z"`設定がビルドパイプラインにデフォルト統合され、Rustの型安全性を保ったまま数十KB台のWASMバイナリを量産できるようになった。初回ロード時間がUXの差別化要因として重視される中、小規模なインタラクティブ機能（例：物件の間取りビューア等）に向いている。

- **サーバーサイドWASM(WASI Preview 2)の台頭:** WasmtimeやSpinなどのランタイムがWASI Preview 2に対応し、Rust製WASMモジュールをエッジ/サーバーレス環境でコンテナより高速に起動（ミリ秒単位）できる。レイテンシに敏感なAPI処理の一部をWASMへ切り出す選択肢が現実的になってきている。

- **デバッグ・プロファイリング環境の改善:** DWARF対応のソースマップやブラウザDevTools統合が進み、RustのWASMビルドでも実コードベースでのステップデバッグが可能に。これまで「本番は速いが開発体験が悪い」という課題が緩和され、採用のハードルが下がっている。

### 8. Next.js App Router patterns 2026

- **ポイント1（Partial Prerenderingの本格採用）:** 静的シェルと動的コンテンツを1つのルートで共存させるPPRが安定化し、初期表示速度を保ちながら個人化された部分（例: ユーザーごとの物件レコメンド）をストリーミングできるようになっています。`sumitsugi`の`properties/`一覧でも、静的な物件カード部分と動的な「引越し費用」計算部分を分離する設計が有効です。

- **ポイント2（`use cache`ディレクティブによる明示的キャッシュ制御）:** Next.js 16では関数・コンポーネント単位で`use cache`を付けてキャッシュ対象を明示するパターンが主流になり、`fetch`のオプション地獄から脱却しつつあります。データ取得ロジック（`src/lib/data.ts`）側でキャッシュ境界を明示することで、ドラフト物件と公開物件の表示切り替えのようなステータス依存データでも安全に高速化できます。

- **ポイント3（Server Actionsのスキーマ検証との統合強化）:** Server Actionsがフォーム処理の標準になりつつあり、Zodとの組み合わせでクライアント・サーバー両方の検証ロジックを一枚化するパターンが定着しています。本プロジェクトの標準（Zodによる境界検証）とも直接合致するため、物件登録・問い合わせフォームは素直にServer Actions化できます。

- **ポイント4（Route GroupsとParallel Routesによるレイアウト分割の成熟）:** `(group)`や`@slot`を使ったレイアウト分割が、モーダル内フォームやダッシュボード型UIの標準実装パターンとして定着しました。アカウントページや物件詳細のモーダル表示など、戻る操作で状態が崩れやすいUIの実装コストを下げられます。

- **ポイント5（Turbopackのビルド高速化が開発体験の前提に）:** Turbopackが本番ビルドでもデフォルト候補になり、CI上の`bun run build`実行時間が短縮される一方、一部のWebpack依存プラグインとの互換性に注意が必要です。CIのビルドステップ必須化（本リポジトリの標準）と相性が良く、ビルド検証のフィードバックループが速くなります。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化:** Edge Functionsは依然V8 isolateベースで軌道に乗っており、2026年時点ではバンドルサイズを1MB以下に抑えることでコールドスタートを1桁msに維持できる。依存関係を動的importで分割し、不要なNode.js互換ポリフィルを削除するのが実用的な第一歩。

- **Streaming + Partial Prerendering(PPR)の併用:** Next.js 16のPPRとEdge Functionsを組み合わせることで、静的シェルを即時配信しつつ動的部分だけをEdgeでストリーミングできる。物件検索や空室カレンダーのような「大部分静的・一部動的」なページに最適。

- **リージョン固定よりフォールバック戦略:** グローバル分散よりも、主要ユーザー層(日本国内)に近いリージョンを明示指定し、`regions`設定でコスト・レイテンシのトレードオフを管理する方が、完全グローバル配信より運用コストが読みやすい。

- **Edge Middlewareの責務を薄く保つ:** 認証チェックやA/Bテスト振り分けなど軽量処理に限定し、DB直接アクセスやPDF生成のような重い処理はNode.js runtimeのServer Actionsに委譲する。Edge実行時間の課金単価が高いため、誤って重い処理を置くとコストが跳ねる。

- **Observability統合が必須化:** 2026年はVercelのOpenTelemetry統合が標準化され、Edge Function単位でのレイテンシ・エラー率トレースが容易になった。本番投入前にトレースダッシュボードでp95レイテンシを確認する運用を標準フローに組み込むべき。

### 10. TypeScript type safety patterns 2026

- **型推論ファースト設計:** `satisfies`演算子やconst型パラメータを活用し、明示的な型注釈を減らしつつ型の厳密性を保つパターンが主流に。推論に型を語らせることでリファクタリング耐性が上がり、型定義の二重管理を防げる。

- **スキーマ駆動のランタイム検証:** Zodなど（本プロジェクトでも境界入力に採用済み）でスキーマを単一の真実源とし、型はスキーマから`z.infer`で導出する流れが標準化。コンパイル時の型安全とランタイム検証のズレが構造的に起きなくなる。

- **Branded/Nominal型によるプリミティブ混同防止:** `UserId`と`PropertyId`のような文字列IDを構造的型付けのままでは区別できないため、brandedタイプで意味的な型安全性を担保する手法が定着。IDの取り違えバグをコンパイル時に検出できる。

- **Exhaustiveness checkingの徹底:** Union型（本プロジェクトの`'draft' | 'public'`のようなステータス型）に対し、`switch`文で`never`型を使った網羅性チェックを必須化する流れ。新しいステータスを追加した際にコンパイルエラーで漏れを検知でき、CLAUDE.mdの「型一貫性」ルールとも整合する。

- **型レベルテストの一般化:** `tsd`やVitestの型テスト機能で「型が正しく推論されるか」自体をテスト対象にする文化が拡大。複雑なユーティリティ型やジェネリクスの回帰を防ぎ、TDDサイクルに型安全性の検証を組み込める。
