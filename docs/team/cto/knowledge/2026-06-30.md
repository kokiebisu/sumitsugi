# CTO Knowledge - 2026-06-30

## Daily Update (2026-06-30)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを削減するため、データフェッチをサーバー側に集約する。`"use client"`ディレクティブは本当に必要なインタラクティブ部分のみに絞り込む。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降で安定化したPPRにより、静的シェルを即座に配信しつつ動的コンテンツをストリーミングできる。一つのルートでSSGとSSRの両方の利点を得られる。

- **`<Image>`と`next/font`による Core Web Vitals 最適化:** LCPスコア改善のため`priority`フロップと適切な`sizes`指定が必須。フォントのCLSゼロ化は`next/font`一択で、Google Fontsも含めてセルフホストに切り替える。

- **Route Segment Configとキャッシュ戦略の見直し:** Next.js 15でデフォルトキャッシュ挙動が変わり、`fetch`はデフォルトでキャッシュされなくなった。`revalidate`と`dynamic`設定を各ルートセグメントで明示的に管理することが重要。

- **Bundle Analyzerとトレースによる継続的計測:** `@next/bundle-analyzer`とVercel Speed Insightsを組み合わせ、ビルドごとにバンドルサイズとCWVを計測する。「最適化した気分」ではなく数値で判断するCI文化を定着させることが本質。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化が鍵:** 2026年時点では、RSCのストリーミングはSuspense境界をコンポーネント単位で細かく設定することで、TTFB（初回バイト到達時間）を最小化しつつ段階的なレンダリングを実現するのがベストプラクティスになっている。

- **PPR（Partial Prerendering）との統合が標準化:** Next.js 15以降でStableになったPPRにより、静的シェルを即座に配信しつつ動的コンテンツをストリームする構成が主流。静的部分のキャッシュヒット率とダイナミック部分のレイテンシを分離して最適化できる。

- **`use cache` ディレクティブによるサーバーサイドキャッシュ制御:** Next.jsの`use cache`（旧`unstable_cache`の後継）がRSCのデータフェッチ層に統合され、コンポーネント・関数単位でキャッシュ戦略を宣言的に定義できる。ストリーミングと組み合わせることでウォーターフォールを回避しつつキャッシュ効率を最大化。

- **Server Actions + optimistic updateのUXパターンが成熟:** RSCとServer Actionsの組み合わせで、フォーム送信やデータ変更時に`useOptimistic`でUIを即時更新しつつサーバーで確定する設計が確立。クライアントバンドルを増やさずにインタラクティブなUXを実現できる。

- **エッジランタイムでのストリーミング制約に注意:** Cloudflare WorkersやVercel EdgeランタイムではNode.jsランタイムと異なりストリームのバッファリング挙動に差異がある。データベース接続（PrismaのEdge版、Drizzle等）との組み合わせでコールドスタートとコネクションプールの設計が重要になっている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年現在、Next.jsなどのフルスタックフレームワークとの親和性からtRPCが急速に普及しており、クライアント・サーバー間でTypeScriptの型を共有することでランタイムエラーを大幅に削減できる。

- **RESTは死んでいないが「デフォルト」ではなくなった:** 外部公開APIや多言語クライアントが存在する場合はREST（OpenAPI 3.1）が依然として最有力だが、内部API・モノレポ環境ではtRPCやgRPCへの移行が加速している。

- **GraphQLは「選択的採用」フェーズへ:** 複雑なデータグラフを持つ大規模サービス（BFF層など）では有効だが、オーバーエンジニアリングになりがちなため、小〜中規模プロジェクトへの採用は慎重に判断すべき。

- **Server-Sent Events / HTTP Streaming がリアルタイムAPIの新標準:** WebSocketの複雑さを避けつつ、AI生成コンテンツのストリーミングやライブ更新に対応するため、Fetch APIベースのストリーミングが主流になりつつある。

- **スキーマファーストの設計が不可欠:** REST/GraphQL/tRPC問わず、Zod・Valibot等によるスキーマ定義を起点とし、バリデーション・型生成・ドキュメントを自動化するアプローチが2026年のベストプラクティスとして定着している。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジの標準ランタイムへ:** CloudflareやFastlyがWasmファーストのエッジ実行環境を本格展開し、コールドスタートがほぼゼロに。コンテナレスで安全なサンドボックスが実現し、Node.js依存から脱却する動きが加速している。

- **AI推論のエッジオフロードが主流化:** LLMの小型化（SLM）とエッジGPUの普及により、ユーザーに最近いノードで推論を実行するアーキテクチャが現実的に。レイテンシ削減だけでなく、データをオリジンに送らないことでプライバシー規制（GDPR・改正個人情報保護法）への対応も同時に達成できる。

- **エッジDBとの統合が設計の前提に:** Cloudflare D1・Turso・Neon（エッジレプリカ）など、エッジ近傍で読み書きできるSQLiteベースのDBが成熟。「ステートレス前提」から「ステートフルエッジ」へパラダイムシフトが起きており、設計時にデータ配置戦略を明示的に選ぶ必要がある。

- **オブザーバビリティの複雑性が課題:** リージョンが数百に分散するためトレースの集約コストが高騰。OpenTelemetryのエッジ対応と、サンプリング戦略の最適化が実運用の鍵になっており、ベンダーロックインを避けるなら標準プロトコル採用が必須。

- **コスト構造の再評価が必要:** リクエスト単価は安くても、エッジキャッシュのバイパス率やオリジンへのフォールバック頻度によって従来サーバーレスより高くなるケースがある。CDNヒット率・KVストア読み取り数・Wasm実行時間を組み合わせたコストモデルを事前に試算することが重要。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の標準採用:** パスワードレス認証がついに主流となり、フィッシング耐性のあるパスキーをデフォルトにすることで、クレデンシャルスタッフィング攻撃のリスクをほぼゼロにできる。

- **継続的認証（Continuous Authentication）の実装:** ログイン時点の一度きりの認証から、セッション中も行動パターン・デバイス状態を監視するリスクベース認証へシフトし、セッションハイジャックを早期検知する。

- **トークン寿命の最小化とDPoP（Demonstrating Proof of Possession）:** JWTのアクセストークンは15分以内に短縮し、DPoPバインディングでトークン流出時の横取り攻撃（replay attack）を無効化するのがベストプラクティスとなっている。

- **サプライチェーン攻撃への対策（依存ライブラリの監査）:** 認証ライブラリへの悪意あるコード混入リスクが高まっており、`bun audit` / Dependabotによる自動監視と、SBOMの生成・管理が必須の運用標準となっている。

- **AIを活用した異常ログイン検知:** 通常の行動基準線（ベースライン）をMLで学習し、地理的異常・時間帯外アクセス・デバイス指紋の不一致をリアルタイムで検出してステップアップ認証をトリガーする仕組みが、中規模SaaSでも現実的なコストで導入可能になっている。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のEdge対応成熟:** Prisma ClientがEdge RuntimeおよびServerless環境で安定稼働するようになり、Next.js App RouterのServer Componentsとの相性が大幅に改善。コネクションプーリングは`@prisma/adapter-pg`経由でPgBouncerを使うパターンが定番化。

- **Supabase Branching による開発フロー変革:** SupabaseのDatabase Branchingが本番利用可能になり、PRごとに独立したDBブランチを持てる。マイグレーションのCI/CDテストが現実的になり、本番スキーマ破壊リスクが激減。

- **Row Level Security (RLS) とPrismaの統合課題:** SupabaseのRLSをPrismaと組み合わせる場合、`SET LOCAL role`でセッションごとのロール切り替えが必要で、ミドルウェア層の設計が重要。`prisma.$executeRaw`でセッション変数を設定するラッパーパターンが実用的。

- **Vector/pgvector の標準化:** Supabase上のpgvectorが成熟し、RAG構成のセマンティック検索をアプリDBと同一インスタンスで完結できる。Prismaは`Unsupported`型でvectorカラムを扱う回避策が主流だが、2026年内にネイティブ対応予定。

- **コスト最適化としてのConnection Pooling必須化:** Vercel/Cloudflareなどサーバーレス環境ではDBコネクション枯渇が現実的な問題。Supabase Transaction Pooler（port 6543）を環境変数で分けて使い、長期セッション用Direct接続とServerless用Pooler接続を明示的に使い分けるアーキテクチャが必須。

### 7. WebAssembly Rust performance 2026

- **WASI Preview 2の実用化:** 2026年時点でWASI Preview 2（Component Model）が主要ランタイムに広く普及し、Rustで書いたWasmコンポーネントがホスト環境に依存せず安全にI/Oを扱えるようになった。サーバーレス・エッジ環境でのRust/Wasmの採用が急加速している。

- **SIMD・スレッド命令の安定化:** Wasm SIMDとShared Memory/Atomicsが全主要ブラウザ・ランタイムで安定稼働し、Rustの`std::simd`と組み合わせることで画像処理・ML推論のネイティブ比90%以上の性能を達成できるケースが増えた。

- **コンパイルサイズの劇的改善:** `wasm-opt`（Binaryen）＋`cargo`の`strip`オプション＋LTOの組み合わせで、Rustバイナリのサイズが以前比30〜50%削減可能になり、初回ロード遅延がエッジキャッシュと合わせて実用域に入った。

- **Wasmtime/WasmEdgeの組み込み採用拡大:** サーバーサイドでWasmtimeをプラグインランタイムとして組み込む設計パターンが定着し、Rustで書いたビジネスロジックをサンドボックス実行することでセキュリティ分離とホットリロードを両立できる。

- **ガベージコレクションWasm GC提案との差別化:** WasmGCの普及でGo/Kotlinなどがブラウザ上で動くようになったが、Rustはゼロコスト抽象＋線形メモリの強みを生かし、レイテンシ敏感なユースケース（音声・ゲーム・暗号）では依然として最速の選択肢であり続けている。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** 2026年はSC（Server Components）をデフォルトとし、インタラクティビティが必要な箇所だけ `'use client'` を付与するパターンが定着。クライアントバンドルサイズを大幅に削減できる。

- **Partial Prerendering（PPR）の本格活用:** 静的シェルと動的ストリームを同一ルートで混在させるPPRが安定版へ。`<Suspense>` 境界を戦略的に配置することで、TTFBと動的コンテンツのバランスを両立できる。

- **`use cache` ディレクティブによる細粒度キャッシュ:** `fetch` レベルのキャッシュに代わり、関数・コンポーネント単位で `use cache` を宣言するパターンが主流に。キャッシュライフタイムを `cacheLife` / `cacheTag` で明示的に管理することが推奨される。

- **Server Actions の型安全強化:** `next-safe-action` 等を活用し、ZodスキーマでServer Actionsの入出力を型付けするパターンが標準化。フォームバリデーションとサーバー処理を一本化できる。

- **並列・インターセプトルートの設計規律:** `@slot` / `(.)` パターンの乱用によるルーティング複雑化が問題視され、モーダル・ドロワー用途に限定し、それ以外はシンプルなネストルートを維持する設計指針が浸透している。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeのコールドスタート最小化:** 2026年時点でVercel Edge FunctionsはV8 Isolateベースのため起動は数ミリ秒以内だが、`export const runtime = 'edge'` を適切なルートにのみ適用し、不要なモジュールバンドルを避けることでさらなる削減が可能。

- **Fluid Computeとの使い分け:** VercelはFluid Compute（サーバーレス＋エッジのハイブリッド）を推進しており、CPU集約タスクはFluid、レイテンシ優先のA/BテストやJWT検証はEdgeと明確に役割分離するのがベストプラクティス。

- **KV・キャッシュ戦略の重要性:** Edge FunctionsはステートレスなためVercel KVやEdge Cacheの活用が必須。`Cache-Control: stale-while-revalidate` とISRの組み合わせで、動的コンテンツのEdge配信コストを大幅削減できる。

- **バンドルサイズの厳守:** Edge RuntimeはNode.js APIの一部が使用不可で、バンドル上限（2MB）がある。`next bundle-analyzer` で依存関係を可視化し、重いライブラリを軽量代替（例: `jose` → Web Crypto API直接利用）に置き換えることが現実的な最適化手段。

- **Observabilityの整備:** Edge環境ではログがVolatileなため、Vercel Log Drains + 外部APM（Datadog / Axiom）への転送設定が必須。2026年はEdge専用のトレーシングSDKが成熟しており、スパン単位でのボトルネック特定が容易になっている。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の `satisfies` により、型推論を保持しながら型チェックを行えるため、`as` キャストによる型安全性の損失を避けられる。特にコンフィグオブジェクトや定数定義での利用が2026年のスタンダードになっている。

- **Template Literal Types によるAPI契約の厳格化:** エンドポイント文字列やイベント名を `\`/api/${string}\`` のような型で表現することで、実行前に誤ったパスを検出できる。バックエンドとフロントエンドの型共有（tRPC等）と組み合わせると効果が最大化される。

- **`const` 型アサーションとブランド型の組み合わせ:** `UserId extends string & { readonly _brand: 'UserId' }` のようなBranded Typesで、同一プリミティブ型のIDを混同するバグをコンパイル時に排除できる。本プロジェクトのような物件IDとユーザーIDが混在するドメインで特に有効。

- **`noUncheckedIndexedAccess` の標準化:** `tsconfig.json` でこのオプションを有効にすることで、配列・オブジェクトのインデックスアクセスが自動的に `T | undefined` になり、実行時のundefinedエラーを型レベルで防止できる。2026年では新規プロジェクトでのデフォルト設定が推奨されている。

- **Zod + `z.infer<>` による単一真実源の確立:** バリデーションスキーマから型を派生させることで、「型とバリデーションロジックが乖離する」問題を根絶できる。本プロジェクトのAPIバウンダリ（`src/lib/`）でZodスキーマを型の起点にすると、型の二重管理が不要になる。
