## Daily Update (2026-08-04)

### 1. Next.js performance optimization 2026

## CTO視点: Next.js Performance Optimization 2026

- **ポイント1（Partial Prerendering の本格運用）:** Next.js 15以降で導入されたPPRが2026年には安定版の主要機能となり、静的シェルを即座に配信しつつ動的部分をストリーミングすることで、TTFBとLCPを大幅に改善できる。sumitsugiの物件一覧・詳細ページのような「一部は静的（物件基本情報）、一部は動的（空室状況・価格）」な構成に特に有効。

- **ポイント2（React Compiler によるメモ化の自動化）:** React Compilerが安定化し、`useMemo`/`useCallback`の手動最適化が不要になりつつある。手動メモ化のバグ（依存配列漏れ）による再レンダリング問題を根本的に減らせるため、リスト表示が多い物件検索UIでの導入価値が高い。

- **ポイント3（Turbopack本番ビルドの標準化）:** Turbopackが本番ビルドでもデフォルト化され、Webpack比でビルド時間が大幅短縮。CI/CDパイプライン（`bun run build`）の実行時間短縮に直結し、autonomous-developer.ymlのような自動化ワークフローの回転率向上にも寄与する。

- **ポイント4（画像・フォント最適化のCDNエッジ処理）:** `next/image`の最適化処理がエッジランタイムでより高速化され、Cache-Controlヘッダーの自動チューニングが進化。物件写真が多いsumitsugiのようなプラットフォームではLCP改善に直結する重要ポイント。

- **ポイント5（Server Actionsのキャッシュ戦略成熟）:** Server Actions呼び出し後の再検証（revalidation）がより細粒度になり、`revalidateTag`ベースの選択的キャッシュ無効化が主流に。物件ステータス変更（draft/public）のような部分更新で、ページ全体の再生成を避けられる。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPartial Prerendering（PPR）が安定版となり、静的シェルを即座に返しつつ動的部分をストリーミングで補完する構成が標準化してきている。初期表示速度とパーソナライズの両立が可能になり、`suspense`境界の設計がパフォーマンス最適化の中心的な作業になる。

- **ポイント2:** `loading.tsx`や`<Suspense>`によるストリーミングSSRは、データ取得が遅いコンポーネント（レビュー数、在庫状況など）を後回しにしてTTFBを改善する。本サービスの物件詳細ページのような「即座に見せたい基本情報」と「多少遅れてもいい付帯情報」を分離する設計が引き続き有効。

- **ポイント3:** Server ActionsとRSCの組み合わせでAPI Routeを介さないデータ更新が一般化し、フォーム送信・楽観的更新のボイラープレートが減少している。ただしキャッシュ無効化（`revalidatePath`/`revalidateTag`）の設計ミスがバグの温床になりやすく、レビュー時は要注意ポイント。

- **ポイント4:** クライアントバンドルサイズ削減の観点で「デフォルトはServer Component、対話が必要な葉ノードだけClient Component」という原則が定着し、`'use client'`境界を意図的に浅く保つ設計がベストプラクティスとして広まっている。

- **ポイント5:** ストリーミングはSEOやCore Web Vitals（特にLCP/INP）と密接に絡むため、計測（Vercel Analytics等）を伴わない体感ベースの最適化は避け、実測データに基づいてSuspense境界の粒度を調整するアプローチが推奨される。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはフルスタックTypeScriptモノレポ（Next.js等）でのRPC通信において、スキーマ定義とAPI呼び出しを型レベルで完全同期できる点が評価され、社内API・小〜中規模チームでの採用が拡大している。ただし言語横断のクライアント（モバイルアプリ等）が絡む場合はスキーマ共有の壁があり適用範囲は限定的。

- **ポイント2:** GraphQLはBFF（Backend for Frontend）層やモバイル/Web複数クライアントが異なるデータ形状を必要とするケースで依然強く、N+1問題対策としてDataLoaderやPersisted Queriesの標準化が進んでいる。一方でスキーマ設計・キャッシュ戦略のコストは高く、シンプルなCRUDにはオーバースペックになりがち。

- **ポイント3:** RESTはOpenAPI 3.1 + JSON Schemaによるコード生成（型定義・クライアントSDK自動生成）がエコシステム成熟により実質的にtRPC的な型安全性に近づいており、外部公開API・パートナー連携APIではRESTが依然デファクトスタンダード。

- **ポイント4:** 弊社（sumitsugi）のようなNext.js App Router構成では、内部API（前の住人/次の住人のマッチングロジック等）はtRPCまたはServer Actions＋Zodバリデーションで型安全性を優先し、将来的な外部連携（不動産会社API連携など）を見据える箇所のみREST/OpenAPIで切り出す、というハイブリッド戦略が現実的。

- **ポイント5:** 2026年のトレンドとして、AIエージェント（LLM）がAPIを直接呼び出すユースケースの増加により、人間可読なOpenAPIスキーマ＋明確なエラーメッセージ設計（`.claude/rules/standards.md`にもある「セキュアなエラーメッセージ」原則と整合）がAPI設計の新たな評価軸になっている。

### 4. serverless edge computing 2026

CTOとして、edge computingの技術トレンドを日本語で回答します。

- **ポイント1（コールドスタート撲滅）:** V8 isolatesベースのランタイム(Cloudflare Workers, Deno Deploy等)がコンテナ型サーバーレスに代わり主流化し、コールドスタートが1桁ミリ秒未満に短縮。低レイテンシが要求される認証・検索APIから優先的に移行する価値がある。

- **ポイント2（データレイヤーのエッジ化）:** D1/Turso等のedge-native DBやKVストアがグローバルレプリケーション標準機能となり、「エッジで計算、中央でDB」から「エッジで計算・データ共存」へシフト。読み取り中心のワークロードほど恩恵が大きい。

- **ポイント3（フレームワーク統合の深化）:** Next.js等のフレームワークがedge runtimeをファーストクラスでサポートし、Route単位でedge/node実行環境を選択可能に。ISR/SSRのハイブリッド運用が一般化し、開発体験とパフォーマンスの両立がしやすくなっている。

- **ポイント4（コスト構造の変化）:** リクエスト課金＋実行時間課金モデルによりトラフィックの少ないサービスの運用コストが大幅低下。一方で高頻度・長時間実行ワークロードでは従来型サーバーの方が安くなるケースもあり、ワークロード特性に応じた使い分けが重要。

- **ポイント5（可観測性の課題）:** 分散実行環境ゆえにログ・トレースの集約が難しく、OpenTelemetryのedge対応が急速に進展中。導入時はモニタリング基盤の整備を後回しにせず、初期段階から組み込む設計が推奨される。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証がデファクトスタンダードとなり、フィッシング耐性のあるパスキーをプライマリな認証手段として実装すべき。従来のパスワード+SMS認証は2026年時点で非推奨とされるケースが増えている。

- **継続的リスクベース認証:** ログイン時の一点評価ではなく、デバイスフィンガープリント・行動パターン・地理的位置をセッション中も継続的に評価するアダプティブ認証が主流化。異常検知時に段階的にMFAを要求する設計が有効。

- **トークンのショートリブド化とローテーション:** JWTやセッショントークンの有効期限を短く保ち、リフレッシュトークンのローテーション・失効管理を徹底することで、トークン漏洩時の被害範囲を最小化する。

- **BFF（Backend for Frontend）パターンでのトークン隠蔽:** SPAやモバイルアプリからアクセストークンを直接扱わず、HTTPOnly Cookieを介したBFF層で認証情報を管理することで、XSSによるトークン窃取リスクを構造的に排除する。

- **サプライチェーン・依存関係の認証監査:** 認証ライブラリ（NextAuth/Auth.js等）自体の脆弱性が攻撃対象になるケースが増加しており、依存パッケージの定期的なセキュリティ監査とSBOM管理を認証基盤の一部として組み込む必要がある。

### 6. database architecture Prisma Supabase 2026

**CTO視点：データベースアーキテクチャ（Prisma / Supabase）2026年の要点**

- **ポイント1（Prisma ORM の進化）:** Prisma 6以降はRust非依存の新エンジン（TypeScript製クエリコンパイラ）に移行し、コールドスタートが大幅短縮された。Vercel等のサーバーレス環境でのAPI Route実行時のレイテンシ改善に直結するため、sumitsugiのようなNext.js App Router構成では積極的に追従すべき。
- **ポイント2（Supabase + RLS標準化）:** Row Level Security（RLS）をアプリケーション層の権限チェックの代替ではなく必須の防御線として設計するのが2026年の主流。`seller`/`buyer`のようなロール分岐が多いsumitsugiのデータ構造では、Prisma経由の書き込みでもSupabase側RLSポリシーを二重に効かせる設計が安全。
- **ポイント3（Connection Pooling）:** サーバーレス関数からのDB接続はSupabase側のPgBouncer（Supavisor）経由のプーリング接続必須。Prismaの`directUrl`と`url`を使い分け、マイグレーションは直接接続・実行時はプーリング接続という構成が事実上の標準。
- **ポイント4（型安全なリアルタイム機能）:** Supabase Realtimeのpostgres_changesとPrisma生成型を組み合わせ、物件ステータス（`draft`/`public`）のような列挙値変更を型安全にリッスンする実装パターンが普及。ステータス変更の即時UI反映が必要な機能（内見予約状況など）に有効。
- **ポイント5（マイグレーション運用）:** Prisma Migrateのみに頼らず、Supabase CLIのマイグレーション管理と併用してスキーマドリフトを防ぐハイブリッド運用が推奨される。本番環境への直接DDL変更を避け、CI上でmigration diffを必ずレビューするフローが必須。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデルの成熟:** WASI Preview 2とComponent Modelが実用段階に入り、Rustの`wit-bindgen`で言語間インターフェースを型安全に定義できるようになった。マイクロサービス的にWasmモジュールを組み合わせる設計が現実的な選択肢になっている。

- **SIMD・スレッドの標準化進展:** Wasm SIMDとシェアードメモリ+スレッドがブラウザ・サーバーランタイム双方で広くサポートされ、Rust側も`std::simd`や`wasm-bindgen`経由での最適化がしやすくなった。画像処理や暗号演算など計算集約タスクをネイティブに近い速度でブラウザ実行できる。

- **ビルドサイズとコールドスタート最適化:** `wasm-opt`やLTO、`panic = "abort"`設定に加え、Rustのコード生成側でも不要なpanicメッセージ削減など、エッジ関数（Cloudflare Workers等）でのコールドスタート短縮が重視されている。サーバーレス用途ではミリ秒単位の起動速度がボトルネックになりやすい。

- **ネイティブとの性能差縮小:** Wasmtimeなどのランタイムがtiered compilation（Cranelift）を採用し、JITウォームアップ後はネイティブの80〜95%程度の性能を達成するケースが増えている。ただしGC言語との連携やメモリコピーのオーバーヘッドは依然ボトルネックになりやすく、Rustでゼロコピーな設計（`&[u8]`ベースのFFI）を意識すべき。

- **ツールチェーンの実用性向上:** `cargo component`や`cargo-wasi`のエコシステムが整い、CI/CDへの組み込みが容易になった。sumitsugiのような物件データ処理・PDF生成などCPU負荷の高い処理をエッジ側Wasmにオフロードする選択肢も検討価値がある。

### 8. Next.js App Router patterns 2026

- **ポイント1（Partial Prerendering の標準化）:** PPR（Partial Prerendering）がstableとなり、静的シェルと動的コンテンツを1つのルートで組み合わせるパターンが主流に。物件一覧ページのような「ヘッダーは静的・在庫データは動的」という構成に最適で、TTFBを大きく改善できる。

- **ポイント2（Server Actions の型安全な運用）:** `use server`ディレクティブとZodバリデーションを組み合わせたServer Actionsが、フォーム処理・問い合わせ送信のデファクトパターンに定着。API Routeを別途書かずに済み、`src/lib`側のスキーマ定義を共有できるためコード量が削減できる。

- **ポイント3（`use cache`ディレクティブによる粒度制御）:** Next.js 15以降で導入された`use cache`が2026年時点で主要パターンとして定着し、`fetch`単位ではなく関数・コンポーネント単位でキャッシュ戦略を制御可能。物件検索結果など更新頻度が異なるデータごとに`cacheLife`/`cacheTag`を分けて再検証コストを最適化できる。

- **ポイント4（Server/Client境界の意識的設計）:** "Client Componentを葉に押し出す"設計が定石として確立。認証状態や前の住人プロフィールのようなインタラクティブ部分だけをClient Componentに切り出し、それ以外はServer Componentに留めることでバンドルサイズとハイドレーションコストを最小化する。

- **ポイント5（Route Handlers + Middleware の軽量化）:** Edge Runtimeの制約を踏まえ、認証チェックなど軽量な処理のみMiddlewareに残し、重い処理はServer Component/Server Actionに寄せる分離が推奨される。sumitsugiのようなauth-context連携型アプリでは、Middlewareでのセッション検証を最小限に保つことでレイテンシを抑えられる。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化:** Vercel Edge FunctionsはV8 isolateベースで起動しているため、Node.js Functionsと比較してコールドスタートが数ms〜数十msと大幅に短い。認証チェックやリダイレクトなど超軽量な処理はEdgeに寄せ、DB接続を伴う重い処理はNode.js Runtimeに残す使い分けが2026年時点でのベストプラクティス。

- **Fluid Compute対応:** Vercelの新しい実行モデル（Fluid Compute）により、Edge/Serverless間の境界が曖昧になりつつあり、同一関数内で複数リクエストを束ねて実行コストを削減できる。sumitsugiのような物件検索APIでは、リクエストの束ね効果が高いエンドポイント（一覧取得系）から優先的に移行検討すべき。

- **キャッシュ戦略の一体化:** `next: { revalidate }` とEdge Cache（stale-while-revalidate）を組み合わせることで、物件一覧や引越し費用シミュレーションなど頻繁に読まれるが更新頻度の低いデータをEdgeでキャッシュし、オリジンへのアクセスを削減できる。ISRとEdge Middlewareのキャッシュヘッダー設計を揃えることが重要。

- **地域分散とレイテンシ:** ユーザー分布（現状は日本国内想定）に対してEdge Networkのリージョン最適化は効果が限定的なため、過剰投資は避け、まずは国内ユーザーへの応答速度がボトルネックになっていないかを計測（Vercel Analytics / Web Vitals）してから投資判断すべき。

- **実行環境の制約に注意:** Edge Runtimeは一部のNode.js API（`fs`, 一部の暗号ライブラリ等）が使えないため、認証まわり（NextAuth等）やPDF生成処理をEdgeに移す場合は依存ライブラリの互換性を事前検証する必要がある。特商法表記やプライバシーポリシー関連のサーバー処理はNode.js Runtime維持が無難。

### 10. TypeScript type safety patterns 2026

- **型推論の強化(TypeScript 5.x以降):** `satisfies`演算子やconst型パラメータの活用により、型注釈を最小限にしつつ厳密な型安全性を維持できるようになり、shadcn/uiのようなコンポーネントライブラリとの相性も良い。

- **Zodによる実行時検証と型定義の統合:** APIレスポンスやフォーム入力など、システム境界での`z.infer`を用いたスキーマ駆動開発が主流化しており、コンパイル時の型とランタイムのバリデーションを二重管理せずに一致させられる。

- **判別可能なユニオン型(Discriminated Union)の徹底:** `status: 'draft' | 'public'`のような状態管理では、単純なstring unionよりオブジェクト全体を判別可能にすることで、網羅性チェック(`never`による exhaustiveness check)がコンパイル時に効くようになる。

- **`strict`+`noUncheckedIndexedAccess`の標準化:** 配列・オブジェクトアクセス時のundefined漏れを防ぐ設定がデフォルト推奨になりつつあり、本番環境でのランタイムエラーを未然に防ぐコストパフォーマンスの高い施策。

- **Template Literal Typesによるドメイン特化の型安全性:** ルーティングパスやi18nキーなど、文字列ベースのAPIに対してリテラル型で制約をかけることで、リファクタリング時の破壊的変更をコンパイラが検出できるようになっている。
