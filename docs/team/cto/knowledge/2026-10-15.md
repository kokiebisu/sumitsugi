# CTO Knowledge - 2026-10-15

## Daily Update (2026-10-15)

### 1. Next.js performance optimization 2026

## CTO視点: Next.js Performance Optimization 2026

- **ポイント1（Turbopackの標準化）:** Next.js 16ではTurbopackが開発・本番ビルドの両方でデフォルトとなり、大規模プロジェクトでもビルド時間が大幅短縮。CI/CDのフィードバックループが速くなるため、`bun run build`の検証コストが下がる。
- **ポイント2（明示的キャッシュ戦略）:** `"use cache"`ディレクティブによる明示的キャッシュ制御が主流化し、暗黒箱だった自動キャッシュに依存せず、データフェッチごとにキャッシュ境界を宣言的に管理できる。本プロジェクトのproperty一覧など頻繁に更新されないデータ取得に適用すべき。
- **ポイント3（Partial Prerendering本格運用）:** 静的シェルと動的コンテンツを1ページ内で混在させるPPRが安定版として実用レベルに到達。物件詳細ページのように「基本情報は静的・在庫状況は動的」という構成に理想的で、TTFBを改善できる。
- **ポイント4（React Compilerによる自動最適化）:** React Compilerがメモ化を自動化し、`useMemo`/`useCallback`の手動チューニングが不要に。コンポーネント数が増えるほどレンダリングコストの管理が楽になり、開発速度と実行時パフォーマンスを両立できる。
- **ポイント5（クライアントJS最小化）:** Server Componentsとストリーミングالسト活用でクライアントへ送るJSバンドルを最小化するのが依然最大のインパクト。インタラクティブ性が必須な箇所（フォーム、認証周り）だけをClient Componentに限定する設計原則を徹底すべき。

### 2. React Server Components streaming 2026

- **Partial Prerendering(PPR)の本格普及:** Next.js 16ではStatic ShellとDynamic Holesを組み合わせたPPRが標準化され、静的部分を即時配信しつつ動的部分をSuspense境界でストリーミングする構成がデフォルトパターンになっている。初期表示速度(TTFB/LCP)とパーソナライゼーションを両立できるため、物件一覧ページのような「静的なレイアウト＋動的な検索結果」に相性が良い。

- **`use cache`ディレクティブとキャッシュ粒度の制御:** コンポーネント/関数単位で明示的にキャッシュ戦略を指定できるようになり、従来の`fetch`キャッシュ依存から脱却しつつある。物件詳細のような読み取り頻度の高いデータはコンポーネント単位でキャッシュし、在庫状況など変化の速いデータはストリーミングで最新化する、という粒度設計が重要になる。

- **ストリーミングSSRとエラーバウンダリの組み合わせが必須パターン化:** `loading.tsx`/`error.tsx`に加え、ネストしたSuspense境界ごとに失敗を局所化する設計が定着し、一部のデータ取得失敗がページ全体をブロックしない構成が標準的なベストプラクティスになっている。決済や引き継ぎフローなど複数ステップのUIでは、各ステップを独立したSuspense境界にすることでUX劣化を防げる。

- **Server Actionsのストリーミングレスポンス対応:** フォーム送信後の処理結果を段階的に返せるようになり、長時間処理（例: 契約書生成、PDF出力）でも「処理中→部分結果→完了」のUIをクライアント側の複雑な状態管理なしで実現できる。前の住人の引き継ぎフローのような多段階処理に適用余地がある。

- **バンドルサイズよりも「サーバー往復回数」がパフォーマンスの主戦場に:** RSCが定着した結果、クライアントJSの削減効果は一巡し、現在はネットワークウォーターフォール（ネストしたデータ取得による直列化）の削減が最大の最適化ポイントになっている。`Promise.all`的な並列データ取得とストリーミング境界の設計を意識しないと、RSC導入自体がパフォーマンス改善にならないケースが増えている。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（GraphQL疲れとtRPCの台頭）:** GraphQLはスキーマ管理やN+1問題のオーバーヘッドが指摘され、TypeScriptモノレポではエンドツーエンドの型安全性を軽量に実現できるtRPCへの移行が進んでいる。Next.js App Router構成のsumitsugiのような小〜中規模チームには、tRPC（またはServer Actions）が開発速度の面で有利。
- **ポイント2（RESTの根強さとOpenAPI自動生成）:** 外部公開APIやサードパーティ連携が必要な領域では、依然としてREST + OpenAPIが標準。Zodスキーマからの型・OpenAPI自動生成（zod-to-openapi等）により「Single Source of Truth」を保ちつつドキュメント保守コストを下げるパターンが定着してきている。
- **ポイント3（Server Actions / RPCへの収斂）:** Next.js 16世代ではクライアント-サーバー間通信がServer Actionsに寄り、従来のREST/GraphQL APIレイヤーを薄くする設計が増えている。内部UIロジックはServer Actions、外部/決済連携など境界部分のみ明示的なAPI層に分離するハイブリッド構成が実用的。
- **ポイント4（契約駆動とスキーマバリデーションの必須化）:** API設計のトレンドとして、Zod/Valibot等によるランタイムバリデーションをAPI境界に必ず挟む「契約駆動開発」が標準化。本プロジェクトの標準にもあるZod境界バリデーションの徹底は、この潮流と合致しており追加対応は不要。
- **ポイント5（エッジ・ストリーミング対応の重視）:** 2026年はLLM機能統合やリアルタイムUXの要求から、ストリーミングレスポンス（SSE/Server Actionsのストリーミング）やエッジランタイム対応がAPI設計の評価軸になっている。将来的にAI接客機能等を追加する場合は、この観点を設計初期から考慮すべき。

### 4. serverless edge computing 2026

- **ポイント1（コールドスタート問題の実質的解消）:** V8 Isolateベースのランタイム（Cloudflare Workers、Deno Deploy等）が主流化し、起動時間がミリ秒単位に短縮。これにより従来のコンテナベースサーバーレスで課題だったレイテンシ問題が解消され、リアルタイム性が求められるAPIでもエッジ実行が実用的な選択肢になっている。

- **ポイント2（エッジでのデータレイヤー統合）:** Edge-native DB（Cloudflare D1、Turso、PlanetScale等）がエッジロケーションに分散レプリカを配置し、「計算だけエッジ、DBは中央」という従来の非対称性が解消されつつある。読み取りの大半をユーザー近傍で処理できるため、グローバル展開するB2Cサービスではレイテンシとコストの両面で優位。

- **ポイント3（AI推論のエッジシフト）:** 小型・量子化モデル（SLM）の精度向上により、簡易な推論（レコメンド、入力検証、パーソナライゼーション）をエッジ上で完結させる動きが加速。中央集権的なLLM API呼び出しを削減することで、コストとレイテンシを同時に改善できる。

- **ポイント4（ベンダーロックインとポータビリティのトレードオフ）:** 各クラウドが独自のエッジランタイムAPIを展開する一方、WinterCG標準化の動きでWeb標準API（Fetch, Request/Response等）への収斂が進行中。移行容易性を重視するなら、プロバイダ固有APIへの依存を最小化する設計判断が今後より重要になる。

- **ポイント5（運用コストモデルの変化）:** リクエスト課金からCPU時間課金への移行で、I/Oバウンドな処理（他API呼び出し待ち等）のコストが実質ゼロに近づき、従来のコンテナ常駐型より大幅に安くなるケースが増加。sumitsugiのような物件検索・マッチングAPIなら、画像変換やジオロケーション処理をエッジ関数に切り出すことでコスト削減余地がある。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の標準化:** 2026年現在、主要ブラウザ・OSでパスキーがデフォルトの認証手段として普及し、パスワード+SMS OTPよりフィッシング耐性が高く、UXも向上する。新規実装では最初からパスキー対応を前提にアーキテクチャを設計すべき。

- **多層防御としてのリスクベース認証:** IPレピュテーション・デバイスフィンガープリント・行動分析を組み合わせたアダプティブMFAが標準化しており、固定ルールのMFAより誤検知が少なく、UXとセキュリティのバランスが取れる。

- **トークン管理の厳格化:** JWTのexp/refresh token rotationを徹底し、httpOnly + Secure + SameSite=Strict Cookieでの保管が必須。localStorageへのトークン保存はXSS耐性がないため避けるべき。

- **ゼロトラスト前提の認可設計:** 認証後も毎リクエストで権限チェックを行い、セッション固定・権限昇格攻撃を防ぐ。マイクロサービス間はmTLSやサービスメッシュでの相互認証を組み合わせる。

- **サプライチェーン経由の認証リスク:** OAuthアプリの過剰スコープ付与やサードパーティSDKの認証情報漏洩が2025-2026で増加傾向。外部連携は最小権限スコープ＋定期的なトークンローテーションの監査が必要。

### 6. database architecture Prisma Supabase 2026

- **Postgres接続管理の進化:** SupabaseはPgBouncer依存から移行し、Supavisor等のクラウドネイティブなコネクションプーリングが標準化。Prisma側もEdge環境向けに`driverAdapters`でネイティブドライバ接続が安定し、サーバーレス関数でのコールドスタート時の接続枯渇問題が大幅に改善している。

- **Prisma ORMのRust脱却(Node.js化)完了:** Prismaクエリエンジンが段階的にRustバイナリからTypeScript/WASM実装へ移行し、Vercel Edge FunctionsやCloudflare Workersでのバンドルサイズ・コールドスタートが改善。sumitsugiのようなNext.js App Router構成では、Edge Runtimeでのデータ取得がより軽量になる。

- **Row Level Security (RLS) とORMの統合設計:** SupabaseのRLSとPrismaのアプリケーション層権限制御を併用する「二層防御」が標準パターン化。前の住人/次の住人間の物件データアクセス制御など、マルチテナント的な権限要件がある`sumitsugi`では、PrismaだけでなくDB側RLSも設計時に組み込むべき。

- **リアルタイム機能とORMの分離:** Supabase RealtimeのサブスクリプションはPrisma経由ではなくSupabase Client直接利用が推奨される設計が定着。物件ステータス変更(`draft`→`public`)のリアルタイム反映など、WebSocket系の機能はPrismaとSupabase Clientを併用するハイブリッド構成が実用的。

- **マイグレーション運用の厳格化:** Prisma Migrateのスキーマドリフト検知とSupabaseのブランチング機能（開発用DBブランチ）を組み合わせたプレビュー環境でのマイグレーション検証が主流に。本番法務リリース前の`sumitsugi`にとって、スキーマ変更の安全なロールバック手順を整備しておく価値が高い。

### 7. WebAssembly Rust performance 2026

- **コンパイル時間とツールチェーンの成熟:** `wasm-pack` / `cargo component` のビルド速度が大幅に改善され、CI/CDでのWasmバイナリ生成が実用的な速度になった。小規模プロジェクトなら数秒でビルド可能なため、開発イテレーションのボトルネックではなくなっている。

- **WASI Preview 2とコンポーネントモデルの定着:** RustのWasm出力がWASI Preview 2に対応し、ホスト関数呼び出しのオーバーヘッドが大幅に減少。ネイティブコードとの性能差が特定ワークロードで5%未満まで縮小しており、サーバーサイド処理の一部をWasmに移す選択肢が現実的になった。

- **SIMDとマルチスレッドの標準化:** Wasm SIMDとthreads proposalがブラウザ・ランタイム両方で広くサポートされ、画像処理や数値計算系の処理でネイティブ比80-90%の性能が得られるケースが増えている。画像変換・PDF生成など重い処理をクライアント側にオフロードするアーキテクチャが選択肢になる。

- **バイナリサイズ最適化の自動化:** `wasm-opt`やLTO設定がデフォルトで洗練され、`wee_alloc`に代わる軽量アロケータの選択肢も増加。ただし依然としてバンドルサイズはJSライブラリより大きくなりがちなため、初回ロード体験が重要なUIにはまだ不向き。

- **実用面での注意点:** sumitsugiのようなNext.js主体のプロジェクトでは、画像処理（物件写真のリサイズ・EXIF除去など）や暗号化処理など、計算集約的かつセキュリティ上クライアント実行が望ましい箇所に限定して導入するのが現実的。全面的なWasm化は過剰設計になりやすい。

### 8. Next.js App Router patterns 2026

- **ポイント1:** Partial Prerendering(PPR)が安定版となり、静的シェルを即時配信しつつ動的部分をストリーミングする設計がデフォルトパターンに。初期表示速度とSEOを両立しつつ、個人化コンテンツも扱いやすくなった。

- **ポイント2:** Server ActionsがCRUDの標準手段として定着し、APIルートを書かずにフォーム送信・ミューテーションを直接Server Componentから呼び出す構成が主流。ただし認可チェックをAction内部に必ず入れる必要があり、クライアントからの直接呼び出しを前提に設計すべき。

- **ポイント3:** `use cache`ディレクティブによるきめ細かいキャッシュ制御が普及し、`fetch`キャッシュに依存しないデータ取得層（ORM経由など）でも明示的キャッシュ戦略が組みやすくなった。再検証タイミングの設計ミスがパフォーマンス事故の主要因になるため、キャッシュ境界を明文化すべき。

- **ポイント4:** レイアウト単位でのStreaming SSR + Suspense境界の細分化が定着し、1ページ内の「遅いデータ」と「速いデータ」を分離するのが標準プラクティス。ローディングUIの設計コストが上がる分、体感速度は大きく向上する。

- **ポイント5:** Route Handlersはエッジランタイムとの組み合わせが前提になりつつあり、Node.js専用APIへの依存を減らす設計（Web標準API優先）がデプロイ先の柔軟性を高める鍵になっている。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Middlewareの実行時間制限（CPU時間ベース課金）を意識し、認証チェックやA/Bテストの振り分けなど軽量なロジックのみをEdgeに置き、重い処理はServerless/Node runtimeに委譲する設計が主流になっている。
- **ポイント2:** `fluid compute`モデルの普及により、Edge/Serverless間でインスタンスを再利用しコールドスタートを削減できるため、DBコネクションプーリングやキャッシュのウォームアップ戦略を見直す価値がある。
- **ポイント3:** ISR/PPR（Partial Prerendering）とEdge Functionsを組み合わせることで、静的シェルを即時配信しつつ動的部分のみEdgeでストリーミングする構成が、物件検索やユーザー固有コンテンツの表示速度改善に効果的。
- **ポイント4:** Edge Runtimeは一部のNode.js API（fs、一部のcrypto）が使えないため、依存ライブラリの互換性を事前に`next build`やCI上で検証する仕組みを入れておくとデプロイ後の不具合を防げる。
- **ポイント5:** リクエストごとの課金・レイテンシ計測がリージョン単位で可視化できるようになったため、ユーザーの地理分布（国内向けサービスなら東京リージョン優先）に応じてEdge関数のリージョンピニングを行うとコストとレイテンシの両方を最適化できる。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x系では`satisfies`演算子が定着し、型推論を保ちながら値が特定の型に適合することを検証できるため、オブジェクトリテラルや設定値の型安全性が大きく向上した。特にUIの文言定義やステータス定数（`'draft' | 'public'`など）で、widening問題を避けつつ型チェックできる点が実用的。

- **ポイント2:** Zodなど実行時スキーマ検証ライブラリと型推論の統合（`z.infer`）が標準パターンとして定着し、「型は静的解析のみ」から「スキーマが単一の真実の源（Single Source of Truth）」という考え方に移行している。APIレスポンスやフォーム入力など外部境界でのバリデーションにそのまま型を流用できるのが利点。

- **ポイント3:** Template Literal TypesとBranded Types（nominal typingのエミュレーション）が、IDや単位付き数値などの取り違えを防ぐパターンとして広く使われ始めている。例えば`UserId`と`PropertyId`を単純な`string`のまま使うと事故が起きやすいが、brandingで型レベルで区別できる。

- **ポイント4:** `tsc`単体のビルドパフォーマンス限界から、Rust実装の高速型チェッカー（oxc系など）やIncremental/Project References活用が注目されており、大規模モノレポでのCI時間短縮に直結する。型安全性の「正しさ」だけでなく「チェックの速さ」もアーキテクチャ上の論点になってきている。

- **ポイント5:** Union型の網羅性チェック（exhaustiveness check、`never`を使ったswitch文の網羅性保証）が、ステータス遷移や状態機械の実装で事実上の必須パターンになっている。新しい値を追加した際にコンパイルエラーで検知できるため、型の変更漏れを防ぐ仕組みとして引き続き重要。
