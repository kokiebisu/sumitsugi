# CTO Knowledge - 2026-05-18

## Daily Update (2026-05-18)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の最大活用:** サーバーサイドでデータフェッチとレンダリングを完結させることでクライアントJSバンドルを大幅削減できる。`use client`ディレクティブは本当に必要なインタラクション部分のみに絞ることが鉄則。

- **Partial Prerendering (PPR) の本番投入:** 静的シェルと動的ストリーミングを組み合わせるPPRがNext.js 15+で安定化し、TTFBを犠牲にせず動的コンテンツを提供できる。`experimental.ppr: true`から始めて計測しながら適用範囲を拡大する戦略が現実的。

- **`next/image` + CDNキャッシュ戦略の最適化:** `sizes`属性と`priority`フラグの適切な設定でLCP改善が即効性高い。Vercel以外のホスティングでは`loader`カスタムとCloudflare Images等の組み合わせでコスト効率も両立できる。

- **Server Actions のN+1問題に注意:** フォーム送信やミューテーションをServer Actionsで実装する際、ループ内でのDB呼び出しが生じやすい。DataLoader パターンやRDBのバッチクエリを意識的に適用しないとサーバー負荷が顕在化する。

- **Bundle Analyzer + Turbopack の活用:** `ANALYZE=true bun run build`でバンドルの肥大化を定期的に可視化し、動的インポート（`next/dynamic`）で初期ロードを分割する習慣が重要。Turbopackへの移行でローカルビルドが大幅高速化し、開発速度そのものが上がる。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度設計が鍵:** RSCストリーミングでは、Suspense境界をコンポーネントツリーのどこに置くかがTTFB/LCPに直結する。粒度が荒すぎるとウォーターフォールが残り、細かすぎるとHTTPフレームオーバーヘッドが増大する。

- **PPR（Partial Prerendering）の本格普及:** Next.js 15以降でPPRがstableになり、静的シェルを即時配信しつつ動的部分のみストリームする設計が標準的なパターンになった。静的/動的の境界をコンポーネント単位で制御できる点がApp Routerの最大の強み。

- **サーバーコンポーネントのデータフェッチ並列化:** `Promise.all`でのデータ並列取得と、個々のSuspenseラッパーによる独立ストリームの組み合わせが実装パターンとして定着。シリアルなawaitチェーンは2026年時点でアンチパターンとみなされる。

- **キャッシュ戦略の複雑化への対応:** React 19の`use cache`ディレクティブにより、コンポーネント・関数・ルートレベルで細粒度のキャッシュ制御が可能になった。ただしキャッシュ無効化ロジックの設計ミスがバグの温床になるため、invalidation戦略をアーキテクチャ初期に明確化することが重要。

- **Edge Runtimeとの相性改善:** Cloudflare Workers / Vercel EdgeでのRSCストリーミングが安定し、地理的に近いエッジからのFCPを稼ぐ戦略が現実的になった。ただしNode.js専用モジュール依存のライブラリとの互換性チェックは依然として必要。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性の標準化:** 2026年現在、Next.js等のフルスタックフレームワークではtRPCがデファクトに近づきつつあり、クライアント・サーバー間でTypeScriptの型を共有することでランタイムエラーを根絶できる。

- **GraphQLの「適材適所」への収束:** Federationによるマイクロサービス統合やBFF（Backend for Frontend）パターンでは依然GraphQLが強いが、単純なCRUDにはオーバーエンジニアリングとなる場合が多く、採用判断はユースケースで明確に分かれてきた。

- **REST+OpenAPIの復権:** TypeSpec（Microsoft）やZod→OpenAPI生成ツールの成熟により、RESTでもコードファースト型スキーマ駆動開発が容易になり、シンプルさと型安全性を両立できるようになった。

- **エッジ・ストリーミング対応が設計の必須条件に:** Vercel Edge / Cloudflare Workersの普及で、APIはロングポーリング・SSE・WebSocketではなくHTTP Streaming（Server-Sent Events）ファーストで設計する潮流が加速している。

- **AIエージェント向けAPI設計の新要件:** MCPやOpenAI Function Callingの普及により、「人間が読むUI向けAPI」に加えて「LLMエージェントが消費しやすいスキーマ設計」（明確なツール記述・べき等性・エラー構造の標準化）が新たな設計基準となりつつある。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がEdgeのデファクトランタイムに:** V8 Isolateに代わりWasmが主流となり、コールドスタートがほぼゼロ（<1ms）になった。Cloudflare Workers・Fastly Compute@Edgeともにデフォルトランタイムとして採用済み。

- **AIインファレンスのEdge実行が現実的に:** 量子化モデル（INT4/INT8）とWasm SIMDの組み合わせにより、小〜中規模LLMをエッジで低レイテンシ実行できる。ユーザーデータをオリジンに送らず推論できるため、プライバシー規制対応の設計パターンとして注目。

- **エッジDBの成熟（Distributed SQLの普及）:** TursoやNeon、Cloudflare D1がグローバルレプリケーションを標準提供し、「エッジはステートレスのみ」という制約が実質的に解消。ただしWrite一貫性のトレードオフ設計は依然として必須。

- **Cold Start問題の構造的解決:** SnapshottingとMemory-mapped I/OによりNode.js系ランタイムでもコールドスタートを10ms以下に抑える手法が普及。従来「Lambdaは遅い」とされていたユースケースを置き換えつつある。

- **Observabilityの課題が顕在化:** 数百POPにまたがる分散トレーシングは依然難しく、OpenTelemetryのEdge対応（バッファリング・サンプリング）が標準化の途上。エッジ採用時はトレーシング基盤の設計コストを見積もりに含めるべき。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）への移行加速:** 2026年時点でパスワードレス認証はデファクトスタンダードになりつつあり、パスキーはフィッシング耐性が高くUXも優れるため、新規システムではパスワード認証を採用しない設計が推奨される。

- **ゼロトラスト前提のセッション管理:** 長期トークン（長いJWT有効期限）は廃止し、短命アクセストークン（15分）＋ローテーションするリフレッシュトークンの組み合わせが必須。デバイス信頼性・位置情報・行動パターンを組み合わせたリスクベース認証も標準的になっている。

- **サプライチェーン攻撃対策としての依存関係監査:** 認証ライブラリ（Passport.js、NextAuth等）の脆弱性は攻撃の主要経路であり、`bun audit`やDependabotによる自動監視＋SBOMの管理が実装の一部として必要。

- **AIを悪用したクレデンシャルスタッフィング対策:** LLMを活用したボットによる認証突破が巧妙化しており、レート制限だけでは不十分。行動バイオメトリクスや適応型CAPTCHA（Cloudflare Turnstile等）の組み合わせが現実的な防御策。

- **シークレット管理の厳格化:** 環境変数への直書きではなく、AWS Secrets ManagerやVaultによる動的シークレット発行が推奨。Next.jsプロジェクトでは`.env.local`のコミット防止とCI/CDでのシークレットスキャン（Gitleaks等）を必ず導入すること。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のEdge Runtime対応成熟:** Prisma Accelerateがエッジ環境でのコネクションプーリングを標準化し、Supabase + Vercel Edge Functionsの組み合わせでコールドスタート問題がほぼ解消された。サーバーレス環境での本番運用が現実的な選択肢になっている。

- **Supabase RLSとPrismaの二重防衛:** Row Level SecurityをSupabase側で定義しつつ、Prismaのミドルウェアで型安全なアクセス制御を重ねるパターンが定着。どちらか一方に依存せず両方を活用することでセキュリティと開発体験を両立できる。

- **pgvectorによるベクトル検索のファーストクラス化:** Supabaseがpgvectorをネイティブサポートし、PrismaのunsafeRaw経由で統合するパターンから、専用の型拡張へ移行が進んでいる。RAGや意味検索をRDBと同一インフラで完結させるアーキテクチャが増加中。

- **Prisma Migrationsの本番適用リスク管理:** `prisma migrate deploy` をCI/CDに組み込む際、Supabaseのブランチ機能（Preview Branches）と組み合わせてPR単位でスキーマ変更を検証するワークフローがベストプラクティスになっている。本番の無停止マイグレーションには `expand-contract` パターンが依然として有効。

- **リアルタイム機能のアーキテクチャ選択:** SupabaseのRealtime（PostgreSQL論理レプリケーション）はシンプルなユースケースに最適だが、高頻度更新ではコネクション数とレイテンシに注意が必要。Prismaのサブスクリプション機能と競合しないよう、責務を明確に分離して設計することが重要。

### 7. WebAssembly Rust performance 2026

- **WasmGC とコンポーネントモデルの成熟:** 2026年時点でWasm Component Model（WASI Preview 2）が広く採用され、RustのWASM出力が複数言語間でのインターオペラビリティを持ち、マイクロサービス境界での利用が現実的になっている。

- **SIMD・スレッド対応によるネイティブ並行パフォーマンス:** Wasm SIMDとshared memoryが主要ブラウザ/ランタイムで安定稼働し、Rustの`rayon`相当の並列処理をWasm上で実現できるユースケースが増加している。

- **エッジ・サーバーサイドでのRust+Wasmが主流に:** Cloudflare Workers / Fastly Compute / wasmtime ベースのサーバーレス環境でRustコンパイルWasmが低コールドスタートと高スループットを両立し、Go/Node代替として評価が定着した。

- **バイナリサイズとビルド最適化の課題は継続中:** `wasm-opt`（Binaryen）やLTO・`panic=abort`設定でバイナリを削減できるが、複雑なcrateでは依然200KB超になりやすく、初期ロードのUX改善にストリーミングコンパイルの活用が必須。

- **AI推論ワークロードへの適用が加速:** ONNXRuntime Wasm・WebLLM経由でRustベースの前処理パイプラインとWasm推論を組み合わせるアーキテクチャが台頭しており、ブラウザ内でのプライバシー保護AIの実装パターンとして注目されている。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** クライアントコンポーネントは状態・インタラクションが必要な最小単位に限定し、デフォルトはServer Componentsで実装する。バンドルサイズ削減とTTFBの改善が顕著で、`"use client"`の乱用は技術的負債になる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的コンテンツを同一ルートで共存させるPPRが安定版に。`<Suspense>`境界を意識した設計が前提となり、ページ単位の静的/動的の二択から解放される。

- **`use cache` APIによるキャッシュ戦略の明示化:** `fetch`のキャッシュオプションに依存する旧来の暗黙的キャッシュから、`use cache`ディレクティブによる明示的なキャッシュ制御へ移行。データ取得関数単位でTTLと再検証ロジックを定義できる。

- **Server Actions の型安全強化:** `next-safe-action`等のラッパーでZodバリデーションとエラーハンドリングを統一するパターンが定着。フォームの`action`属性とのシームレスな統合で、APIルートを介さないミューテーションが標準化されつつある。

- **`nuqs`による URL State 管理:** `useSearchParams`の煩雑さを解消する`nuqs`ライブラリがデファクトスタンダード化。型安全なクエリパラメータ管理でServer ComponentsとClient Componentsをまたぐ状態共有がシンプルになる。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Fluid Compute による Cold Start の実質的排除:** Vercel の Fluid Compute アーキテクチャにより、Edge Functions のコールドスタート問題がほぼ解消。リクエスト間でのインスタンス再利用が可能になり、レイテンシが予測可能になった。

- **ポイント2: Partial Prerendering (PPR) との組み合わせが最強パターン:** 静的シェルをCDNキャッシュしつつ動的部分のみEdgeでストリーミング配信するPPRが主流化。Next.js App RouterのSuspense境界と組み合わせることでTTFBを劇的に削減できる。

- **ポイント3: Edge KV / Edge Config の活用でDB往復を削減:** Vercel Edge Config や KV Store をEdge Functionsと同一リージョンに配置することで、フィーチャーフラグや設定値の取得にゼロレイテンシを実現。ABテストやロールアウト制御に特に有効。

- **ポイント4: V8 Isolate の制約を意識したコード設計が必須:** Edge RuntimeはNode.js API（fs, net等）非対応のため、依存ライブラリのEdge互換性確認が重要。`next/server` のMiddlewareで `runtime: 'edge'` を明示し、バンドルサイズを4MB以下に抑える設計が求められる。

- **ポイント5: 地理的ルーティングと言語処理のEdgeへの移行:** ユーザーのgeolocationベースのリダイレクト・i18nルーティングをEdge Middlewareで処理することで、オリジンサーバー負荷を大幅削減。sumitsugiのような国内特化サービスでも、将来の多拠点展開を見越したEdgeファーストのルーティング設計を今から組み込むべき。

### 10. TypeScript type safety patterns 2026

- **Template Literal Types の高度活用:** 文字列ベースのAPIやルーティング定義でTemplate Literal Typesを使うことで、URLパスやイベント名のタイプミスをコンパイル時に検出できる。`/api/${string}`形式の型定義が実務標準になりつつある。

- **`satisfies` 演算子の定着:** `as const`の代替として`satisfies`が主流化し、型推論を保ちながら型制約を検証できる。過度な型アサション（`as`キャスト）を排除し、型安全性を損なわないコードが書きやすくなった。

- **Branded Types によるドメイン安全性:** `UserId`と`ProductId`が同じ`string`型でも混在しないよう、Branded/Nominal Typesパターンが普及。特に金融・医療系ドメインでの誤用防止に効果的。

- **`noUncheckedIndexedAccess` の標準化:** `tsconfig.json`でこのオプションを有効化することで、配列・オブジェクトアクセスの`undefined`漏れを防止。2026年時点では新規プロジェクトのデファクト設定になっている。

- **型レベルテスト（`tsd` / `expect-type`）の普及:** ランタイムテストだけでなく、型定義自体をテストする文化が浸透。ライブラリ公開時だけでなくアプリ内の複雑な型ユーティリティにも適用され、型リグレッションを早期検出できる。
