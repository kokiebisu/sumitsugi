# CTO Knowledge - 2026-11-23

## Daily Update (2026-11-23)

### 1. Next.js performance optimization 2026

- **React Server Components とストリーミングの深化:** Next.js 16ではPPR(Partial Prerendering)がより安定し、静的シェルを即時配信しつつ動的部分を段階的にストリーミングすることで、TTFBとLCPを大幅に改善できる。物件一覧ページのような動的コンテンツが多い画面ほど効果が大きい。

- **Turbopackのビルド/devパフォーマンス:** Turbopackが本番ビルドでも安定版となり、Webpack比で大幅な高速化が見込める。CI時間短縮に直結するため、自律開発ワークフロー（4時間ごとのタスク実装）のサイクルタイム短縮にも効く。

- **画像・アセット最適化の自動化:** `next/image`とCDN連携（AVIF/WebP自動変換、適応的サイズ配信）が標準化し、物件写真が多いUIでは手動チューニングなしでCore Web Vitalsを維持しやすい。設定ミスでの最適化スキップに注意。

- **Server Actionsの濫用によるウォーターフォール回避:** フォーム送信やインタラクションでServer Actionsを多用すると、クライアント側で逐次実行のウォーターフォールが発生しやすい。データ取得はRSCで並行実行し、Server Actionsは書き込み系操作に限定するのが2026年のベストプラクティス。

- **Edge RuntimeとISRの使い分け:** 引っ越し費用計算など動的性が高いロジックはEdge Runtimeで低レイテンシ化し、物件詳細ページのような更新頻度が低いコンテンツはISR＋オンデマンドRevalidationで静的配信コストを抑える、という明確な分離が主流になっている。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Prerendering（PPR）の本格普及** 静的シェルを即時配信しつつ、動的部分だけをストリーミングで後から流し込む構成がNext.js App Routerの標準パターンになっている。物件一覧ページなどSEOと動的データ（空室状況・価格）を両立させたい箇所に有効。
- **ポイント2: Suspense境界の粒度設計がパフォーマンスの肝** 境界を細かく切りすぎるとウォーターフォールでTTFBが悪化し、粗すぎると初期表示が遅れるため、データ取得の依存関係に合わせた境界設計が重要。物件詳細ページなら「基本情報→画像→前の住人プロフィール」の順で段階的に開示する設計が有効。
- **ポイント3: Server Actionsとストリーミングの組み合わせでフォームUXが向上** 送信後の楽観的UI更新とストリーミングレスポンスを組み合わせることで、問い合わせフォームや申込フローの体感速度が改善する。
- **ポイント4: キャッシュ戦略の複雑化への対応** `use cache`ディレクティブやタグベース無効化が成熟し、物件データのような更新頻度が異なるコンテンツを細かく制御できるようになったが、キャッシュキー設計のミスがステータス不整合（draft/public漏れ表示など）を招くリスクがあるため注意が必要。
- **ポイント5: エッジランタイムとの統合深化** ストリーミングSSRをエッジで実行するケースが増え、ユーザーに地理的に近い場所から部分的レンダリングを配信できるようになったが、Node.js専用ライブラリとの互換性チェックが依然必要。

### 3. API design REST GraphQL tRPC 2026

- **tRPCのエッジ/フルスタックTS統合が標準化:** Next.js 16のApp Router + Server Actionsとの組み合わせで、tRPCの型安全なエンドツーエンド通信がREST/GraphQLのスキーマ管理コストを置き換える流れが加速している。sumitsugiのようなTypeScript一枚岩構成では、API層とクライアント層の型共有によりZodバリデーションとの二重管理を回避できる。

- **GraphQLはBFF（Backend for Frontend）用途に収束:** 汎用APIとしてのGraphQL採用は減り、複数クライアント（モバイル/Web/パートナー連携）を抱える企業がデータ集約層として限定的に使うパターンが主流に。単一フロントエンド構成のプロジェクトでは、GraphQLの運用コスト（N+1対策、スキーマガバナンス）に対してtRPC/RESTの方がROIが高いことが多い。

- **RESTはOpenAPI+型生成で「退屈だが安定」な選択肢として残存:** 外部公開API・サードパーティ連携・長期互換性が必要な領域では、依然RESTが優位。社内フルスタックはtRPC、外部公開APIはREST(OpenAPI)というハイブリッド構成が2026年のデファクトになっている。

- **Server Actions/RSCがAPI境界を曖昧化:** Next.js 16のReact Server ComponentsとServer Actionsにより、「APIを明示的に定義せずデータ取得する」設計が増加。ただし再利用性・テスト容易性の観点から、入力検証（Zod）とエラーハンドリングを持つ薄いサービス層を挟む設計は依然推奨される。

- **実装への示唆:** sumitsugiの規模（Next.js 16 / Bun / 単一TSコードベース）では、外部公開APIが不要な現段階ではtRPC導入よりもServer Actions + Zod境界検証のシンプルな構成を維持し、パートナー連携や外部公開APIが必要になった時点でREST(OpenAPI)層を追加する段階的アプローチが合理的。

### 4. serverless edge computing 2026

- **ポイント1:** 2026年はEdge Functionsの実行時間制限が大幅に緩和され（Vercel/Cloudflare WorkersともCPU時間課金モデルへ移行）、重い処理もエッジで完結できるようになった。sumitsugiのような画像・PDF生成処理（内見資料、引き継ぎ書類）をエッジ側にオフロードしてレイテンシを削減できる余地がある。
- **ポイント2:** WASM（WebAssembly）ベースのエッジランタイムが主流化し、Node.js互換層なしでTypeScript/Rustコードがそのままエッジで動く。Next.js 16のEdge Runtimeとの統合が進んでおり、物件検索APIなど読み取り中心のエンドポイントをエッジ化しやすい。
- **ポイント3:** エッジでのSQLite互換DB（Cloudflare D1, Turso等）が実用段階に入り、地理的に分散したレプリカで低レイテンシ読み取りが可能になった。ただしsumitsugiは強い一貫性が必要な取引データ（契約・決済）を持つため、読み取り専用キャッシュ用途に限定すべき。
- **ポイント4:** エッジでのAI推論（軽量LLM推論、画像解析）がコスト面で現実的になり、物件情報の自動タグ付けやスパム検知をエッジで即時実行できる。ただしモデルサイズとコールドスタートのトレードオフは依然存在する。
- **ポイント5:** マルチクラウドのエッジベンダーロックイン回避が課題として浮上し、WinterCG標準（Web標準API準拠）に沿った実装がベストプラクティスに。現状のNext.js構成なら将来の移行コストを抑えられるため、特定ベンダー固有APIへの依存は避けるべき。

### 5. authentication security best practices 2026

- **パスキー（WebAuthn/FIDO2）への完全移行:** パスワードを前提としたUIを廃止し、パスキーをデフォルトの認証手段とすることでフィッシング耐性を確保する。SMS/メールOTPは中間者攻撃に弱いため、バックアップ手段としてのみ残すのが実用的。

- **トークンのスコープ最小化と短命化:** アクセストークンの有効期限を短く（15分程度）し、リフレッシュトークンはローテーション必須＋再利用検知を実装する。長期間有効なトークンの漏洩は被害範囲が指数的に拡大するため、セッション管理の設計段階で強制的に短命化すべき。

- **デバイス・コンテキストバインディング:** 認証後も「誰がログインしたか」だけでなく「どの端末・ネットワークから継続的にアクセスしているか」を検証するContinuous Authenticationが標準化してきている。特に決済や個人情報編集など高リスク操作には再認証（step-up auth）を必須にする。

- **AI生成攻撃への対策:** ディープフェイク音声/動画を使ったソーシャルエンジニアリングや、LLMを使った高速クレデンシャルスタッフィングが増加しているため、レート制限だけでなく行動ベースの異常検知（ログインパターン・入力速度等）を認証フローに組み込む必要がある。

- **サーバーサイドのシークレット管理の徹底:** 本サービスの標準でも `process.env` 経由のAPIキー管理を徹底しているが、2026年のベストプラクティスではシークレットの定期ローテーション＋アクセスログの監査可能性（who accessed what, when）までセットで求められる。sumitsugiのように個人情報（引継ぎ物件・契約情報）を扱うサービスでは、認可レイヤーでの最小権限原則（RBAC/ABAC）も合わせて徹底すべき。

### 6. database architecture Prisma Supabase 2026

- **スキーマ変更の自動化:** Prisma MigrateとSupabaseのマイグレーション機能を組み合わせることで、スキーマ変更をコードレビュー対象のdiffとして扱える。手動でのSQL実行を避け、CI上でマイグレーションを検証するフローが2026年の標準になっている。

- **Row Level Security (RLS) とORMの分離:** SupabaseのRLSはDB層でアクセス制御を保証するが、PrismaクライアントはRLSをバイパスしやすい（service roleキー利用時）。アプリ層の認可ロジックとRLSを二重に設計し、どちらか一方に依存しない構成が推奨される。

- **コネクションプーリングの考慮:** Supabase（PgBouncer経由）とPrismaの組み合わせでは、Prisma Client側のコネクション数設定（`connection_limit`）をサーバーレス環境（Vercel等）に合わせて調整しないと、同時接続数超過でエラーが頻発する。

- **型安全性とリアルタイム機能の両立:** Prismaの型生成はクエリ層で強力だが、Supabaseのリアルタイムサブスクリプション（Realtime）はPrisma経由では扱えないため、リアルタイムが必要な箇所のみSupabase JS Clientを直接使うハイブリッド構成が一般的。

- **Edge環境での実行制約:** Prismaの標準エンジン（Rustバイナリ）はEdge Runtime非対応のため、Edge FunctionsでDBアクセスする場合はPrisma Accelerate等のHTTPベースドライバーかSupabaseのREST/PostgREST APIを使う必要がある点に注意。

### 7. WebAssembly Rust performance 2026

- **ポイント1: コンポーネントモデルの成熟:** WASM Component Model（WIT/WASI 0.2系）が安定し、Rustのcargo-componentツールチェーンで言語間の相互運用が実用レベルに。マイクロサービス的にWASMモジュールを疎結合で組み合わせる設計がパフォーマンス劣化なく可能になってきている。

- **ポイント2: SIMD・スレッド対応の普及:** WASM SIMDとマルチスレッド（shared memory + atomics）がブラウザ・ランタイム両方でデフォルト有効化され、Rustの`std::simd`やrayonを使った並列処理がネイティブに近い性能を出せるようになった。画像処理や数値計算系の処理をRust/WASMに移す判断がしやすくなっている。

- **ポイント3: 起動時間とバイナリサイズの最適化:** `wasm-opt`やRustの`opt-level="z"`/LTO設定、`wee_alloc`の後継（talc等の軽量アロケータ）により、コールドスタートがサーバーレス環境でも数ms単位まで短縮。エッジコンピューティング（Cloudflare Workers、Fastly Compute等）でRust/WASMがデフォルト選択肢になりつつある。

- **ポイント4: サーバーサイドWASM（WASI Preview 2）の本格採用:** コンテナの代替としてWASMランタイム（Wasmtime、Spin）上でRustバックエンドを動かす事例が増加。コールドスタートの速さとサンドボックス隔離性から、マルチテナントSaaSのisolation戦略として有望——sumitsugiのような物件データ処理基盤でも将来的な検討候補になり得る。

- **ポイント5: デバッグ・プロファイリング体験の向上:** DWARF対応のソースマップやブラウザDevToolsのWASM統合が進み、Rust側のパニック情報がブラウザコンソールに正しくマッピングされるようになった。従来の「WASMはデバッグしづらい」という導入障壁が下がっている。

### 8. Next.js App Router patterns 2026

**CTO視点:**

- **ポイント1（Partial Prerenderingの本格採用）:** 静的シェルを即時配信しつつ動的部分をストリーミングする PPR がデフォルト運用レベルに成熟し、TTFBとパーソナライズ性を両立できる。sumitsugiの物件一覧ページのようにSEO重視かつ個別化要素（お気に入り状態等）を含むページに向いている。
- **ポイント2（Server Actionsのキャッシュ戦略の重要性）:** `revalidatePath`/`revalidateTag`の粒度設計がパフォーマンスとデータ整合性を左右し、物件ステータス(`draft`/`public`)切り替えのような更新系操作ではタグベースの無効化を徹底しないと古いキャッシュを配信し続けるリスクがある。
- **ポイント3（"use cache" ディレクティブによる明示的キャッシュ制御）:** コンポーネント/関数単位でキャッシュ対象を明示する流れが定着し、暗黙的なfetchキャッシュへの依存より意図が明確で事故が減る。
- **ポイント4（Server Componentsファーストだがクライアント境界の最小化が鍵）:** `'use client'`境界を機能単位ではなくインタラクション単位（ボタンやフォームの末端）まで絞る設計がベストプラクティスとして定着し、バンドルサイズと水和コストを抑えられる。
- **ポイント5（Edge/Node runtimeの使い分けの精緻化）:** 認証チェックや軽量API Routeはedge、DB接続や重い処理はNode runtimeという分離が標準化し、認証コンテキスト(`auth-context.tsx`)を使う箇所ではruntime境界を意識した設計が求められる。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Middlewareの実行は依然としてV8 isolateベースで、Node.js APIが使えない制約があるため、`fetch`ベースの軽量ロジック（認証チェック、A/Bテスト振り分け、リダイレクト）に限定し、重い処理はEdge FunctionsではなくNode.js Functionsやバックグラウンドジョブに逃がす設計が定石。
- **ポイント2:** Vercel Fluid Compute（従来のEdge/Serverlessの垣根を薄くした実行モデル）により、同一インスタンス内で複数リクエストを並行処理できるようになったため、コールドスタート削減とコスト最適化の観点でDBコネクションプーリングや再利用可能なクライアントインスタンスの設計が重要になっている。
- **ポイント3:** ISR（Incremental Static Regeneration）とEdge Cacheの併用で、動的パーソナライズが必要な物件詳細ページでも`stale-while-revalidate`戦略を使い、エッジでのレンダリングコストを抑えつつ鮮度を保つパターンが実用的。
- **ポイント4:** リージョン選択（`regions`設定）はDBのレイテンシが支配的なアプリでは必須のチューニングポイントで、Edge Function実行リージョンをDB（例: Supabase/Neonのリージョン）に近づけることで、グローバル分散の恩恵よりもレイテンシ削減効果の方が大きいケースが多い。
- **ポイント5:** Observability（OpenTelemetryトレーシングのEdge Runtime対応）が強化され、Edge FunctionsでもNode.js Functions同様の分散トレーシングが可能になったため、本番導入前にレイテンシのボトルネック（特にコールドスタート vs. 実行時間）を計測してから最適化判断をすべき。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** `satisfies`演算子とconst型パラメータ（`const T`）の組み合わせが標準化し、型推論を保ったまま構造的な制約チェックが可能になっている。
- **ポイント2:** Zodなどのスキーマライブラリから型を導出する「スキーマファースト」パターンが定着し、ランタイム検証と静的型を単一の真実の源から生成できる。
- **ポイント3:** テンプレートリテラル型とブランド型（branded types）を使った「不正な値を表現不可能にする」設計が、IDやステータスの誤用をコンパイル時に防ぐ標準手法になっている。
- **ポイント4:** TypeScript 5.x系のnarrowing改善により、discriminated unionでのexhaustiveness checkがより軽量に書けるようになり、`'draft' | 'public'`のような状態管理の型安全性が強化しやすい。
- **ポイント5:** tRPCやHonoのようなエンドツーエンド型推論フレームワークの普及で、API境界でも手動の型定義を書かずにクライアント・サーバー間の型安全性を維持できる。
