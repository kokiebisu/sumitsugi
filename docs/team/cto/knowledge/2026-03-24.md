# CTO Knowledge - 2026-03-24

## Daily Update (2026-03-24)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチはサーバー側で完結させ、インタラクティブな部分のみ `'use client'` に限定する設計が2026年のベストプラクティス。

- **Partial Prerendering (PPR) の本番投入:** 静的シェルと動的ストリーミングを同一ルートで共存させるPPRがNext.js 15+で安定化し、TTFBを維持しながらパーソナライズコンテンツを配信できるアーキテクチャが現実的な選択肢になっている。

- **Turbopack への完全移行:** Next.js 15でTurbopackがデフォルト化し、大規模プロジェクトでの`bun dev`起動が従来比5〜10倍高速化。CIのキャッシュ戦略もTurbopackのモジュールグラフ単位キャッシュに最適化する必要がある。

- **`next/image` + `sizes` 属性の精緻化:** Core Web VitalsのLCPスコアに直結するため、レスポンシブ画像の`sizes`属性を実際のレイアウトに合わせて正確に指定し、不要な大サイズ画像のダウンロードを防ぐことが引き続き重要。

- **Server Actions のバンドル最適化:** Server Actionsの多用によりクライアント→サーバーのウォーターフォールが発生しやすいため、複数アクションをまとめる設計と`useOptimistic`による楽観的UI更新を組み合わせ、体感速度を向上させる。

### 2. React Server Components streaming 2026

- **ポイント1:** RSC + Suspense の成熟化により、コンポーネント単位の段階的ストリーミングが実用フェーズに入った。`loading.tsx` と `<Suspense>` の組み合わせで、TTFBを維持しつつLCPを改善できる。

- **ポイント2:** Server Actions との統合が深まり、フォーム送信・データ変更をサーバー側で完結させるパターンが定着。クライアントバンドルサイズの削減（-30〜50%）が実測値として報告されている。

- **ポイント3:** PPR（Partial Prerendering）が安定化し、静的シェル＋動的ストリームのハイブリッドが標準戦略になりつつある。CDNキャッシュとリアルタイムデータの両立が実現可能になった。

- **ポイント4:** キャッシュ戦略の再設計が必要。`fetch` の `cache` / `revalidate` オプションに加え、`unstable_cache` や `use cache` ディレクティブ（Next.js 15+）の使い分けがアーキテクチャの鍵になっている。

- **ポイント5:** エラーバウンダリとストリーミングの相性問題が実務上の課題。`error.tsx` はストリーミング後のエラーをキャッチできないケースがあるため、Server Componentレベルでの防御的なエラーハンドリング設計が必須。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの実用的優位性:** フルスタックTypeScriptプロジェクトではtRPCが標準化しつつあり、スキーマ定義なしでエンドツーエンドの型安全性を実現できる。Next.js App Routerとの親和性も高く、Server Actionsとの使い分けが設計の鍵になる。

- **GraphQLの適用範囲の明確化:** GraphQLは複数クライアント（Web/Mobile/サードパーティ）が異なるデータ形状を要求するケースに限定するのがベストプラクティス。単一クライアントのBFFレイヤーではオーバーエンジニアリングになりやすく、tRPCやREST+OpenAPIで十分なことが多い。

- **REST+OpenAPIの再評価:** OpenAPI 3.1 + `openapi-typescript` によるコード生成が成熟し、型安全なREST APIクライアントが自動生成できる。外部公開APIや既存インフラとの統合ではRESTが依然として最も互換性が高い選択肢。

- **Server Actionsによるレイヤーの溶解:** Next.js 15以降、単純なフォーム処理やデータ変更はServer Actionsで直接処理できるため、「APIが不要なAPI」が増えている。これによりAPIは外部連携・マイクロサービス間通信に特化する傾向が強まっている。

- **パフォーマンス観点での選択基準:** レイテンシが重要なエッジ環境ではHTTP/2対応のRESTが有利。GraphQLはN+1問題をDataLoaderで解決する必要があり、tRPCはバンドルサイズと初期化コストを考慮してサーバーコロケーション前提で使うのが現実的。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジのデファクトランタイムに:** V8 isolatesに代わりWasmがエッジ関数の主流となり、言語非依存・コールドスタートほぼゼロ・サンドボックス安全性を同時に実現している。Next.jsのEdge Runtimeも完全Wasm対応が進んでいる。

- **エッジでのAI推論が実用フェーズへ:** 量子化モデル（INT4/INT8）とWebGPU APIの組み合わせにより、分類・埋め込み生成・小規模LLM推論がCDNノードで完結するようになった。レイテンシ削減と個人データのリージョン外流出防止を同時に達成できる。

- **Durable Objects / SQLite-at-edgeによるステートフル化:** Cloudflare Durable ObjectsやFastly Compute上のSQLiteにより、「エッジはステートレス」という制約が崩れた。セッション管理やリアルタイムコラボ機能をオリジンなしで実装できる設計が現実的になった。

- **エッジミドルウェアのオブザーバビリティが課題:** 数百ノードに分散した関数のトレーシング・ログ集約はいまだ成熟途上。OpenTelemetry Collector on-edgeとサンプリング戦略の設計が、本番運用の可否を左右する重要な差別化ポイントになっている。

- **コスト構造の再評価が必須:** 従来の「オリジンサーバー削減コスト＞エッジ実行コスト」という前提が崩れるユースケースが増加。リクエスト数・実行時間・データ転送量の三次元でコスト試算し、一部処理をオリジンに戻す「ハイブリッド配置」が設計の定石になりつつある。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** FIDO2/WebAuthn標準に基づくパスキーが主流となり、パスワードレス認証が実用段階に入っている。Apple・Google・Microsoftのエコシステム全体でのサポートが整い、導入コストが大幅に低下した。

- **トークン設計の見直し（Short-lived + Rotation）:** JWTの有効期限を15分以内に抑え、リフレッシュトークンのローテーションを必須とするアーキテクチャが標準化されている。長命なトークンはセッション固定攻撃のリスクが高く、採用すべきでない。

- **デバイスバインドセッション:** セッショントークンをデバイスフィンガープリント（User-Agent・IPレンジ・TLSクライアント証明書）に紐付け、トークン窃取時の横展開を抑制する手法が普及している。

- **AIを活用した異常検知:** ログイン行動（タイピングリズム・アクセス時刻・地理情報）をリアルタイムに機械学習モデルで評価し、不審なセッションを即時フラグする仕組みがミドルウェアレベルで組み込まれつつある。

- **サプライチェーンリスクとしてのOAuth依存:** サードパーティIdP（Google・GitHub等）への依存はSSOダウン時の完全ロックアウトリスクを持つ。フォールバック認証経路の設計と、OAuthスコープの最小権限原則（least-privilege）の徹底が不可欠。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x + Supabase の統合成熟:** Prisma 6系ではEdge Runtime対応が強化され、Supabase Edge FunctionsとのシームレスなDB接続が実現。`@prisma/adapter-neon`や`prisma-supabase`アダプターにより、コネクションプーリング（PgBouncer/Supavisor）を意識した設計が標準化された。

- **Supabase Supavisor の普及:** 旧来のPgBouncerに代わりSupavisorがデフォルトのプーリング層となり、サーバーレス環境での接続枯渇問題が大幅に緩和。Prismaの`connect_timeout`・`pool_timeout`チューニングとセットで設定すること。

- **Row Level Security (RLS) × Prismaの責務分離:** SupabaseのRLSをDB層で有効化しつつ、Prismaは`service_role`キーでバイパスするパターンが主流。アプリ層とDB層のセキュリティ境界を明確に設計しないと二重管理の温床になる。

- **型安全なリアルタイム購読:** Supabase Realtime + Prismaの組み合わせでは、PrismaのZodスキーマ生成（`prisma-zod-generator`等）でリアルタイムペイロードの型保証を担保するパターンが浸透。REST/Realtimeの型不整合バグを防ぐ。

- **マイグレーション戦略の二分化:** `prisma migrate`（開発環境）と`supabase db push`（本番）を混在させると競合リスクが高い。2026時点では **Prismaをスキーマ管理のSSoT**とし、`prisma migrate deploy`でCI/CDから本番適用する一元管理が推奨アーキテクチャ。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の本格普及:** 2026年はWASI Preview 2が主流となり、RustのWASM出力がブラウザ外（サーバー・エッジ・組み込み）で実用レベルに達した。`wasm-bindgen`や`wit-bindgen`によるインターフェース定義が標準化され、相互運用性が大幅に向上している。

- **SIMD・マルチスレッドの安定化:** WebAssembly SIMDとShared Memoryが主要ランタイム（V8/SpiderMonkey/Wasmtime）で安定稼働し、Rustの`rayon`相当の並列処理がWASM上でも現実的になった。画像処理・暗号・ML推論の分野で特にネイティブ比90%以上の性能が報告されている。

- **Wasmtime/WasmEdgeのAOTコンパイル最適化:** サーバーサイドではJITより事前コンパイル（AOT）が主流となり、コールドスタートが数十μs台に短縮。Rustで書いたWASMモジュールをCloudflare Workers・Fastly Compute等にデプロイする際のレイテンシが問題になりにくくなった。

- **メモリ管理のオーバーヘッド削減:** Rustの`wee_alloc`に代わり`talc`や`dlmalloc`のチューニング済みフォークが普及し、WASMバイナリサイズと割り当てコストが改善。GCなしで小さいバイナリ（〜100KB未満）を維持しつつ複雑なロジックを扱えるようになっている。

- **ツールチェーンの成熟（`cargo-component`が主役）:** `cargo-component`がWASMビルドの事実上の標準となり、`wasm-pack`の役割を置き換えつつある。TypeScriptとRust WASMの型安全な連携が宣言的に記述でき、フロントエンドチームとの統合コストが大きく下がった。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** 2026年のベストプラクティスは「クライアントコンポーネントを末端に押し込む」アーキテクチャ。データフェッチはServer Componentで完結させ、`'use client'`境界を最小化することでバンドルサイズを劇的に削減できる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的コンテンツを同一ルートで混在させるPPRが安定版に。`<Suspense>`境界をアーキテクチャ設計の中心に置き、TTFBとDynamic Contentのバランスを最適化する時代になった。

- **Server Actions によるAPI層の簡略化:** フォーム処理・データ変更をServer Actionsに集約することで、従来のAPI Routes (`/api/*`) が不要になるケースが増加。ただしZodバリデーションとCSRF対策は引き続き必須。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** `fetch`キャッシュから関数・コンポーネント単位のキャッシュへ移行。`revalidateTag`との組み合わせでオンデマンド再検証を精密にコントロールし、不要なキャッシュ無効化を防ぐ。

- **Turbopack 完全移行:** 2026年時点でTurbopackがデフォルトバンドラーとして実用レベルに到達。大規模プロジェクトでのHMR速度が従来比10倍以上になるケースもあり、webpack依存のカスタム設定を持つプロジェクトは移行コストを早めに見積もるべき。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge Runtimeでの計算コスト最小化:** Edge Functionsはコールドスタートがほぼゼロだが、バンドルサイズ（1MB制限）を厳守することが重要。`export const runtime = 'edge'` を使う際は、Node.js専用モジュールの混入を避けるため依存関係を精査する。

- **ポイント2: Streaming ResponseによるTTFB改善:** `ReadableStream` や Next.js の `StreamingTextResponse` を活用し、LLMや重い処理のレスポンスをチャンク配信することで体感パフォーマンスが大幅向上。2026年時点でStreaming対応はもはや「オプション」ではなく標準実装。

- **ポイント3: Edge ConfigとKVの戦略的活用:** フィーチャーフラグや設定値は `@vercel/edge-config`（超低レイテンシ読み取り）に集約し、セッションデータは `@vercel/kv` へ。DBへの直接接続はEdgeでは避け、Data FetchはAPI Routeに委譲するアーキテクチャが安定する。

- **ポイント4: Middleware最適化でルーティングコストを削減:** `middleware.ts` のマッチャー設定（`matcher`）を絞り込み、静的アセット（`/_next/static`）やAPIルートへの不要なミドルウェア実行を排除。全リクエストにミドルウェアを当てるとEdgeの恩恵が相殺される。

- **ポイント5: 地理情報・A/Bテストのエッジ処理:** `request.geo` でユーザーの国・地域を取得し、コンテンツのパーソナライズやリダイレクトをEdgeで完結させる。オリジンサーバーへのラウンドトリップを省くことで、グローバルユーザーへのレイテンシを数十〜数百ms削減できる。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の本格活用:** TypeScript 4.9以降の`satisfies`が2026年において標準パターンとして定着し、型推論の精度を保ちながら型チェックを強制できるため、`as`キャストによる型安全性の穴を排除できる。

- **Template Literal Types × branded types の組み合わせ:** `type UserId = string & { __brand: 'UserId' }` のようなBranded Typesに加え、Template Literal Typesで文字列フォーマットをコンパイル時に検証するパターンが普及し、ランタイムエラーをゼロコストで防げる。

- **`noUncheckedIndexedAccess` の必須化:** tsconfig の`noUncheckedIndexedAccess`を有効にすることで、配列・オブジェクトのインデックスアクセス時に`T | undefined`が強制され、未定義アクセスによるバグをビルド時に捕捉できる。本プロジェクトでも即時導入を推奨。

- **Zod + `z.infer<>` によるスキーマ駆動型定義:** APIレスポンスやフォーム入力の型をZodスキーマから自動導出することで、型定義とバリデーションロジックの乖離を構造的に排除し、境界値の型安全性を一元管理できる。

- **`using` キーワード（Explicit Resource Management）の活用:** TypeScript 5.2以降の`using`構文でリソースの自動解放が型安全に行え、DBコネクションやファイルハンドルの解放漏れをコンパイラが検知できるようになった。
