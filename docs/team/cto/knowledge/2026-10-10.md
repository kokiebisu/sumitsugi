# CTO Knowledge - 2026-10-10

## Daily Update (2026-10-10)

### 1. Next.js performance optimization 2026

- **ポイント1:** Next.js 16ではReact Server Components前提のPartial Prerendering（PPR）が安定版となり、静的シェルを即時配信しつつ動的部分だけストリーミングする構成が標準に。初期表示（TTFB/LCP）の改善効果が大きく、物件一覧ページなど静的要素が多い画面で優先的に導入すべき。

- **ポイント2:** Turbopackがビルド・開発サーバーのデフォルトになり、大規模コードベースでのHMR・ビルド時間が大幅短縮。CIのビルド時間短縮にも直結するため、`bun run build`のボトルネック解消にそのまま効いてくる。

- **ポイント3:** 画像最適化は`next/image`のAVIF優先・CDNエッジでの自動フォーマット選択が主流に。物件写真を多用するsumitsugiのようなサービスでは、LCP改善の最も費用対効果が高い施策の一つ。

- **ポイント4:** React Compilerの本格普及により、`useMemo`/`useCallback`の手動最適化が不要になるケースが増加。コードレビューで過剰なメモ化を指摘する基準を見直す必要がある。

- **ポイント5:** Edge Runtimeでの認証・パーソナライズ処理（ミドルウェア）がコールドスタートほぼゼロで動くようになり、ログイン状態分岐やA/Bテストをエッジで完結させる設計が一般化。サーバー往復を減らし、認証チェックのレイテンシを削減できる。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPartial Prerendering（PPR）が安定版となり、静的シェルを即時配信しながら動的部分だけをストリーミングする構成が標準化している。初期表示（TTFB/LCP）を犠牲にせず、物件検索結果のような動的データを扱える。
- **ポイント2:** `loading.tsx`とSuspenseバウンダリの粒度設計がパフォーマンスの肝になっており、1ページに大きなSuspenseを1つ置くのではなく、物件カードや価格情報など単位で細かく分割するパターンが定着してきている。
- **ポイント3:** Server ActionsとRSCストリーミングの組み合わせで、フォーム送信後のUI更新をクライアントJSなしで実現するケースが増え、バンドルサイズ削減に直結している（本サービスの内覧申込・問い合わせフォームにも適用余地あり）。
- **ポイント4:** キャッシュ戦略（`fetch`のrevalidate/tags）とストリーミングの相性が課題として残っており、動的データを含むRSCでは過剰なキャッシュミスによるサーバー負荷増に注意が必要。計測なしでの導入は避けるべき。
- **ポイント5:** エッジランタイム（Vercel Edge/Cloudflare Workers）でのRSCストリーミング対応が進み、地理的に分散したユーザーへの初期応答速度が改善しているが、Node.js専用ライブラリとの互換性制約は依然ボトルネック。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCの採用がTypeScriptフルスタック構成（Next.js App Router + Bun）で急速に拡大しており、REST/GraphQLのスキーマ同期コストを排除してクライアント・サーバー間の型安全性を直接保証できる点が最大の利点。sumitsugiのようなNext.js 16 + TypeScript構成では、物件データ（`'draft' | 'public'`等のUnion型）の変更を型エラーとして即座に検知できる。
- **ポイント2:** GraphQLは複数クライアント（Web/モバイル/パートナーAPI）が同一データソースから異なる形状のデータを取得するケースで依然強みを持つが、N+1問題対策（DataLoader等）とキャッシュ戦略の複雑さから、単一Next.jsアプリのみの場合は過剰設計になりやすい。
- **ポイント3:** RESTは外部公開API・サードパーティ連携・長期的な後方互換性が必要な領域（決済、外部弁護士向け契約データ連携など）で標準。OpenAPI 3.1 + コード生成が成熟し、2026年はAI エージェントがAPI仕様を直接読み取って呼び出す「エージェント消費前提」の設計が重要トレンドに。
- **ポイント4:** 内部admin/管理画面やダッシュボードはtRPC、外部公開・サードパーティ連携はREST、という「ハイブリッド構成」が2026年のデファクト。1つのプロトコルに統一するより、境界ごとに適切なプロトコルを選ぶ判断力が重要。
- **ポイント5:** ZodスキーマをtRPC/REST両方のバリデーション層で共有する設計が定着しつつあり、`.claude/rules/standards.md`が求める「システム境界でのZod検証」を実装レベルで満たしやすくなっている。API層とバリデーション層を分離せず一体化することで、型安全性とセキュリティ要件を同時に満たせる。

### 4. serverless edge computing 2026

- **ポイント1:** コールドスタート問題は2026年にはほぼ解消され、WebAssembly（WASM）ベースのランタイム（Fermyon Spin、Cloudflare Workers等）がコンテナより軽量かつ高速な起動を実現している。マイクロサービスの粒度をさらに細かくしても遅延が増えにくくなった。

- **ポイント2:** エッジでのステートフル処理（Durable Objects、エッジKV/SQLite）が成熟し、グローバル分散DBとの同期コストが下がったため、低レイテンシが求められる予約・チャット機能はエッジ上で直接状態管理するのが実用的になっている。

- **ポイント3:** AI推論のエッジ配置（小型モデルのオンデバイス/エッジ実行）が標準化し、画像最適化やレコメンドのような軽量なAI処理をオリジンサーバーを経由せずエッジで完結させるアーキテクチャが増えている。

- **ポイント4:** Next.jsのApp RouterはVercel Edge RuntimeやCloudflareとの統合が進み、ミドルウェアでの認証・地域別コンテンツ出し分けがエッジネイティブで書けるようになった。弊社のような不動産情報サービスでは、地域ごとの物件検索結果キャッシュをエッジで行うことでTTFBを大幅短縮できる。

- **ポイント5:** ベンダーロックイン回避のため、WinterCG標準（Web標準API準拠のサーバーレスランタイム）への準拠が選定基準として重視され始めている。将来的な移行コストを抑える観点から、特定ベンダー専用APIへの依存を最小化する設計が推奨される。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** 2026年現在、主要ブラウザ・OSでパスキーがデフォルト推奨となり、パスワードレス認証への移行が本格化。フィッシング耐性が高く、認証フローの実装では`WebAuthn` APIを優先検討すべき。
- **トークンの短命化とローテーション:** アクセストークンの有効期限を短く設定し、リフレッシュトークンのローテーション（refresh token rotation）を必須化する実装が標準化。長命トークンの漏洩リスクを最小化できる。
- **ゼロトラスト前提のセッション管理:** IPアドレスやデバイスフィンガープリントだけに頼らず、デバイスバインディング（DPoPなど）でトークンの不正利用を検知する仕組みが重要。sumitsugiのような個人情報を扱うプラットフォームでは特に有効。
- **サプライチェーン経由の認証リスク:** npm/Bunパッケージ経由の資格情報漏洩事例が増加しており、認証関連の依存パッケージはSBOM管理と定期的な脆弱性スキャンを行うべき。
- **多要素認証の体験最適化:** MFAの強制だけでなく、リスクベース認証（ログイン元・挙動異常を見て段階的にMFAを要求）でUXとセキュリティのバランスを取るアプローチが主流になっている。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はSupabaseのPgBouncer経由接続とRLS（Row Level Security）の相性問題が改善され、`directUrl`と`pooled connection`を分離する構成がデファクト標準になっている。マイグレーション時は必ず`directUrl`を使い、ランタイムはpooled接続を使う設計が推奨される。
- **ポイント2:** SupabaseのEdge Functions + Prisma Accelerate（またはPrisma Postgres）の組み合わせで、サーバーレス環境でのコネクションプール枯渇問題が実質的に解消され、Next.js 16のServer Actionsからの直接DB操作がより安全に行えるようになった。
- **ポイント3:** RLSをDB層のセキュリティ境界として使う場合、Prismaのクエリはservice_roleキーでRLSをバイパスしがちなため、「前の住人」「次の住人」のようなマルチテナント的なデータアクセス制御は、アプリ層（auth-context.tsx等）とRLSポリシーの二重チェックで設計するのがベストプラクティス。
- **ポイント4:** スキーマ変更の際はPrisma Migrateの`shadow database`機能がSupabase上で正しく動くよう別DBインスタンスを用意する必要があり、CI上でこれを省略するとステージング環境でのみ失敗する不整合が起きやすい。
- **ポイント5:** 2026年時点でSupabaseのベクトル検索（pgvector）とPrisma ORMの型安全性を両立させる需要が増えており、物件検索のレコメンド機能などを将来実装する場合は早めにスキーマ設計へ組み込んでおくとマイグレーションコストを抑えられる。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WebAssemblyのComponent Model標準化が進み、Rustの`wit-bindgen`を使った言語間連携がシンプルになった。マイクロサービスをWasmモジュール単位で疎結合に構成できるようになり、サーバーレス基盤（Fermyon Spin、Fastly Compute等）での採用が加速している。

- **ポイント2:** Wasmtimeのネイティブ比パフォーマンスが大幅改善し、JITウォームアップのオーバーヘッドがAOTコンパイル（`wasmtime compile`）で実質ゼロに近づいている。CPU集約的な処理（画像変換、PDF生成）をエッジで実行する用途に向いている。

- **ポイント3:** WasmGC提案が主要ランタイムで実用段階に入り、RustのようなGCなし言語でもホスト言語とのメモリ共有が効率化された。これにより従来必要だった手動シリアライズ/コピーのオーバーヘッドを削減できる。

- **ポイント4:** `wasm32-wasip2`ターゲットの安定化でファイルI/Oやネットワークアクセスを含むアプリケーションもWasm化しやすくなり、サンドボックス化されたプラグインシステム（ユーザー生成コードの安全実行）としての採用例が増えている。

- **ポイント5:** SIMD命令のサポートが成熟し、数値計算・画像処理系のRustクレートでネイティブの80〜90%程度の速度を達成できるケースが増えた。ブラウザ内の重い処理（画像編集、動画エンコード）をクライアントサイドにオフロードする判断材料になる。

### 8. Next.js App Router patterns 2026

- **ポイント1（キャッシュ戦略の明確化）:** Next.js 16では`use cache`ディレクティブとPartial Prerendering（PPR）が安定化し、ページ単位ではなくコンポーネント単位で静的/動的を混在させるのが標準パターンになっている。実装時は「このコンポーネントは本当に動的データが必要か」を常に問い、不要な`dynamic`強制を避けることでビルド時間とTTFBを大幅に削減できる。

- **ポイント2（Server Actionsの責務分離）:** フォーム送信や更新処理はServer Actionsに集約する流れが定着したが、ビジネスロジックをActionに直接書くとテストしづらくなるため、`src/lib`の純粋関数に切り出してActionは薄い呼び出し層にするのがベストプラクティス。本プロジェクトの`src/lib/data.ts`的な構成と相性が良い。

- **ポイント3（Turbopackがデフォルト化）:** Next.js 16以降、開発・本番ビルド双方でTurbopackがデフォルトになり、Webpack設定への依存度は下がっている。カスタムwebpack.config.jsに依存したプラグインがある場合は早期に移行検証をしておくべき。

- **ポイント4（Server/Client境界の最小化）:** "use client"境界を極力リーフコンポーネントに限定し、インタラクティブなUI（フォーム、モーダル等）だけをクライアント化するパターンが2026年のベストプラクティスとして広く浸透。ページ全体を"use client"化すると、RSCの恩恵（バンドルサイズ削減・初期表示高速化）を失う。

- **ポイント5（型安全なルーティング）:** `typedRoutes`やApp Router用の型生成ツールが成熟し、`Link href`やServer Actionのパラメータに対する型チェックが開発時エラー検出の主流になっている。TypeScript中心の本スタックでは早期導入の価値が高い。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの統合深化:** Vercel Edge FunctionsとNode.js Runtimeの機能差が縮小し、Web Streams APIやWASMモジュールをエッジ上でネイティブに扱えるようになったため、レンダリング処理をオリジンに戻さず完結できるケースが増えている。

- **コールドスタート最小化とISRの併用:** エッジ側の初期化コストがほぼゼロに近づいた一方、データ取得レイヤーをInfinite/Stale-While-Revalidate戦略と組み合わせることで、物件検索のような動的フィルタリングUIでもTTFBを安定させやすい。

- **リージョン指定の粒度向上:** `regions`設定がより細かく制御可能になり、ユーザーの地理的分布に応じて処理リージョンを動的に選べるため、国内向けサービスでも東京リージョン固定ではなくレイテンシベースの自動最適化を検討する価値がある。

- **コスト最適化としての関数分割:** 重い処理（画像変換、PDF生成など）をEdgeから通常のServerless/Node Functionsに切り出し、軽量な認証・リダイレクト・A/Bテスト判定のみをEdgeに残す「役割分担」が2026年のベストプラクティスとして定着している。

- **可観測性の標準化:** Vercelのネイティブオブザーバビリティ機能がエッジ関数の実行トレースをOpenTelemetry形式で出力できるようになり、本プロジェクトのような小規模チームでも追加のAPM導入なしにレイテンシ原因を特定しやすくなっている。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x系の`satisfies`演算子とconst型パラメータ（`const T`）の組み合わせが定着し、リテラル型を保持したまま型チェックできるパターンが標準化されている。本プロジェクトでも`site-config.ts`のような設定オブジェクトに適用すると、型推論を保ちつつ構造の妥当性を検証できる。

- **ポイント2:** Zodなど実行時スキーマから型を導出する「Schema-first」アプローチが主流になり、`z.infer<typeof schema>`で型とランタイム検証を単一ソースに統一する流れが加速している。本プロジェクトのStandardsにもある「システム境界でZodを使う」方針はこの潮流と合致しており、`'draft' | 'public'`のようなUnion型もZod enumで一元管理すると型とバリデーションのズレを防げる。

- **ポイント3:** Branded Types（nominal typing）がID混在バグ防止のベストプラクティスとして広く採用されており、例えば`PropertyId`と`UserId`を単純な`string`ではなく区別可能な型にすることで、誤った値の代入をコンパイル時に検出できる。

- **ポイント4:** `tsc --strict`に加え、`noUncheckedIndexedAccess`や`exactOptionalPropertyTypes`といった追加の厳格フラグを有効化するチームが増えており、配列アクセスやオプショナルプロパティの不整合をより早期に検出できる。

- **ポイント5:** AIコード生成が増える中で、型定義そのものが「仕様書」として機能する重要性が増しており、型の自動生成（OpenAPI/GraphQLスキーマからの型生成）とCI上での型チェック必須化（本プロジェクトのBuild Integrityルールと同様）が、生成コードの正しさを保証する主な防衛線になっている。
