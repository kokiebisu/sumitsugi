# CTO Knowledge - 2026-05-14

## Daily Update (2026-05-14)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチロジックはすべてRSCに移行する。`"use client"`ディレクティブは本当に必要な末端コンポーネントのみに限定する。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降で安定化したPPRにより、静的シェルと動的コンテンツを同一ルートで混在させられる。`fallback: <Skeleton/>`パターンでTTFBを維持しつつ動的データを遅延配信する。

- **`next/image` + `sizes`属性の最適化:** レスポンシブ画像の`sizes`属性を正確に指定しないと不要な大画像をダウンロードし続ける。Core Web Vitals（LCP）の改善に直結するため、各ビューポートごとの実際の表示幅を計測して設定する。

- **Server Actions のN+1問題に注意:** Server Actionsは便利だが、ループ内での連続呼び出しがパフォーマンスボトルネックになりやすい。DataLoader パターンやバッチ処理を導入し、DBクエリを集約する。

- **Edge Runtime vs Node.js Runtimeの使い分け:** 認証チェックやA/Bテスト等の軽量ミドルウェアはEdge Runtimeで高速化できるが、重いORM（Prismaなど）はNode.js Runtimeでしか動作しない。ルートごとに`export const runtime = 'edge'`を意識的に選択する。

### 2. React Server Components streaming 2026

- **ポイント1:** React Server Components（RSC）とSuspenseを組み合わせたStreaming SSRは2026年の標準アーキテクチャとなり、TTFBを大幅に削減しつつ、ページ全体のブロッキングなしに段階的なレンダリングが実現できる。

- **ポイント2:** Next.js App Routerの`loading.tsx`とSuspense境界の設計が品質の分岐点となっており、粒度の粗いSuspense配置はStreaming効果を相殺するため、コンポーネントツリーの「データ取得ウォーターフォール」を事前に可視化した設計が必須。

- **ポイント3:** PPR（Partial Prerendering）の本格普及により、静的シェルを即時配信しつつ動的部分のみをStreamingで差し込む手法が主流になりつつあり、CDNキャッシュとStreamingの二項対立が解消されてきた。

- **ポイント4:** Server Actionsとの組み合わせで、フォーム送信後のUI更新もクライアントJSなしに実現できるケースが増えており、JavaScriptバンドルサイズの削減と表示速度の両立がより容易になっている。

- **ポイント5:** ただしStreaming環境ではエラーバウンダリの設計が複雑化するため、`error.tsx`の粒度とロギング戦略（特にStream途中のエラーハンドリング）を開発初期から設計に組み込むことが運用安定性のカギ。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの実用的優位性:** 2026年においてフルスタックTypeScriptプロジェクトではtRPCが事実上の標準になりつつあり、スキーマ定義不要でエンドツーエンドの型安全を実現できるため、小〜中規模チームの開発速度が大幅に向上している。

- **GraphQLの棲み分け明確化:** GraphQLは複数クライアント（Web/Mobile/サードパーティ）が異なるデータ形状を必要とする大規模サービスに特化し、単一フロントエンドのプロジェクトではオーバーエンジニアリングとみなされるケースが増えている。

- **REST + OpenAPIの再評価:** AIツール（GitHub Copilot、Cursor等）がOpenAPIスキーマから自動でクライアントコードを生成できるようになったため、REST+OpenAPIの組み合わせが「シンプルで相互運用性が高い」として再注目されている。

- **Server-Sent Events / HTTPストリーミングの台頭:** WebSocketの複雑さを避けつつリアルタイム性を実現するSSEが、AI系レスポンスストリーミングの普及により標準的なパターンとして定着し、APIデザインの選択肢として無視できない存在になっている。

- **APIゲートウェイとエッジキャッシュの統合:** Cloudflare WorkersやVercel Edge Functionsの成熟により、APIレイヤーをエッジに分散させるアーキテクチャが現実的な選択肢となり、レイテンシ削減とコスト最適化を同時に達成できる設計が求められている。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジのデファクトランタイムへ:** V8 Isolateに加えWasmがエッジ実行の標準となり、言語非依存でコールドスタートほぼゼロを実現。Cloudflare Workers・Fastly Computeともにファーストクラスサポートを提供している。

- **エッジでのAI推論が実用フェーズに:** 量子化モデル（INT4/INT8）のエッジ直接実行が普及し、LLMのストリーミングレスポンスをCDNエッジで完結させるアーキテクチャが増加。レイテンシとコストの両面でオリジンサーバー依存を削減できる。

- **エッジデータベースの成熟（D1・Turso・Neon）:** SQLiteベースの分散エッジDBが実用レベルに達し、読み取り重視のワークロードでは「エッジだけで完結」するフルスタック構成が現実的になった。書き込み整合性の設計は依然として重要な検討事項。

- **オブザーバビリティの課題が顕在化:** エッジノードが数百〜数千に分散するため、従来の集中型モニタリングが機能しない。OpenTelemetry対応のエッジネイティブなトレーシング（Honeycomb、Axiom等）が必須となっている。

- **コールドスタート問題は「解決済み」だが、ウォームアップ戦略は依然重要:** Isolateモデルにより数ミリ秒以下のスタートが標準化されたが、外部依存（DB接続・KVキャッシュウォームアップ）による実効レイテンシのチューニングは設計段階で織り込む必要がある。

### 5. authentication security best practices 2026

- **パスキー（Passkey）の標準化加速:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の主流となり、フィッシング耐性が根本的に向上している。主要ブラウザ・OSの対応が揃った今、新規サービスではパスキーをデフォルト認証として設計すべき。

- **セッション管理の短命化とリフレッシュ戦略:** アクセストークンの有効期限を15分以下に設定し、リフレッシュトークンのローテーションを必須化。セッション固定攻撃やトークン漏洩のリスクを最小化できる。

- **デバイスバインディングによるゼロトラスト強化:** 認証時にデバイス証明書やTPMチップを活用し、「正規デバイスからの正規ユーザー」を検証するアーキテクチャが普及。クレデンシャルスタッフィング攻撃への有効な防御層になる。

- **AIを活用した異常検知の組み込み:** ログイン時の行動分析（タイムゾーン・デバイス・操作パターン）をリアルタイムでスコアリングし、リスクベース認証を実装する。SIEMとの統合より、認証レイヤー自体に組み込む設計が効率的。

- **サプライチェーンリスクとしての認証ライブラリ管理:** OAuthライブラリやJWT実装の脆弱性がサプライチェーン攻撃の標的になるケースが増加。依存ライブラリのSBOM管理と、認証フロー単体のペネトレーションテスト自動化が必須の運用となっている。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x の Edge Runtime 対応成熟:** Prisma が Edge Runtime（Cloudflare Workers, Vercel Edge）で安定稼働できるようになり、Supabase の接続プーリング（PgBouncer / Supabase Pooler）と組み合わせることでサーバーレス環境のコールドスタート問題が大幅に緩和された。

- **Supabase の RLS (Row Level Security) をORMと共存させる設計:** Prisma はRLSを透過的に扱えないため、マルチテナント設計では「Prismaをサーバー側の信頼済みクライアントとして使い、RLSはSupabase Client直接呼び出しに任せる」という役割分担が定着しつつある。

- **リアルタイム機能は Supabase Realtime に委譲:** Prisma のサブスクリプション機能は限定的なため、リアルタイム更新（チャット・通知・在庫変動等）はSupabase RealtimeのPostgresチェンジイベントを直接使い、Prismaは読み書きのCRUD層に専念させるアーキテクチャが合理的。

- **型安全な移行管理の二重管理問題:** Prisma Migrateと Supabase の Dashboard マイグレーションが競合するリスクがある。2026年時点のベストプラクティスは「Prisma Migrateを唯一の真実（source of truth）とし、Supabase Dashboard でのスキーマ直接変更を禁止するチームルール」を設けること。

- **接続数枯渇対策としての Supabase Pooler (Supavisor):** Serverless 環境で Prisma を使うと接続数が爆発するリスクがある。Supabase の Supavisor（pgbouncer 代替）をトランザクションモードで挟むことで、数千の同時リクエストを数十の実DB接続に収束させるのが現在の標準構成。

### 7. WebAssembly Rust performance 2026

- **Component Modelの成熟:** WebAssembly Component Model（WASI 0.2+）が2026年に広く採用され、RustコンポーネントをJavaScript/Python製システムと型安全にインターオペレーブルに組み合わせられるようになった。マイクロサービス境界でのRustの採用障壁が大幅に低下している。

- **GCなし言語の優位性継続:** RustのゼロコストアブストラクションはWasmのリニアメモリモデルと相性が良く、JVMやGo製Wasmと比較して初期化レイテンシが低く、メモリフットプリントが小さい。エッジ・サーバーレス環境での冷起動問題を実質的に解消できる。

- **SIMD・スレッド拡張の実用化:** Wasm SIMDとshared memoryスレッドのブラウザ・ランタイム対応が揃い、Rustで書いたAI推論・画像処理・暗号処理をネイティブに近い速度でブラウザ内実行できる。`wasm-pack` + `rayon`の組み合わせで並列処理も現実的になった。

- **Wasmtime/WASMERの最適化成熟:** Craneliftバックエンドの最適化とAOTコンパイルにより、Wasmtimeでの実行速度がネイティブの85〜95%に到達するケースが増えている。Cloudflare Workers・Fastly Computeといったエッジ基盤でのRust Wasmの本番採用が急増している。

- **ツールチェーンの整備:** `cargo-component`・`wit-bindgen`の安定化により、RustのWasmビルドがCIに組み込みやすくなった。ただしデバッグシンボル・DWARF対応はまだ発展途上で、本番トラブルシュートにはまだ工夫が必要な点に注意。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの徹底:** 2026年時点ではデフォルトでServer Componentsを使い、クライアント境界を最小化するパターンが定着。`'use client'`は状態・イベント・ブラウザAPIが必要な葉コンポーネントのみに限定するのがベストプラクティス。

- **Partial Prerendering（PPR）の実用化:** 静的シェルと動的ストリーミングを同一ページで共存させるPPRが安定版に。`<Suspense>`境界の設計がパフォーマンスの核心となり、LCPの大幅改善が可能。

- **Server Actions によるAPI Routes の置き換え:** フォーム送信・データ変更は`use server`のServer Actionsで完結させ、不要なREST APIエンドポイントを排除する流れが加速。バンドルサイズ削減とセキュリティ（CSRF自動対応）の両立が魅力。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** Next.js 15以降で導入された`use cache`が主流化。関数・コンポーネント単位でキャッシュ戦略を宣言でき、従来の`fetch`オプションより直感的なキャッシュ設計が可能。

- **並列ルート・インターセプトルートの活用:** モーダルやスライドオーバーなどのUIパターンを`@slot`と`(.)route`で実装し、URLを保持したままシームレスなナビゲーションを実現。SPAライクな体験をSSRと両立できる点が評価されている。
