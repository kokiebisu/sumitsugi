# CTO Knowledge - 2026-10-13

## Daily Update (2026-10-13)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分をストリーミングすることで、TTFBを大幅に改善できる。既存ページを段階的に移行し、計測しながら適用範囲を広げるのが実用的。

- **Turbopackへの完全移行:** `next dev`・`next build`両方でTurbopackがデフォルト化され、Webpack比でビルド時間が大幅短縮される。CI時間とローカル開発体験の両方に効くため、移行コストより投資回収が早い。

- **React Server Components前提のデータフェッチ設計:** クライアントバンドルを減らすため、データ取得をできるだけServer Componentsに寄せ、`use client`境界を最小化する。境界が多いほどハイドレーションコストが増えるので、境界設計自体がパフォーマンス設計になる。

- **キャッシュ戦略の明示化（`cacheLife`/`cacheTag`):** App Routerのキャッシュ挙動がより明示的なAPIで制御可能になっており、暗黙キャッシュに依存せず意図的にTTLやタグを設定することで、再検証漏れによる古いデータ表示やキャッシュ崩壊を防げる。

- **画像・フォント最適化の継続的な計測:** `next/image`や`next/font`は依然有効だが、Core Web Vitals（特にLCP/INP）を本番トラフィックで継続計測し、物件写真のような画像中心コンテンツではCDN側の変換・配信設定も含めて最適化する必要がある。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではRSCのストリーミングがデフォルト最適化され、`loading.tsx`やSuspense境界を細かく分割することで、TTFB（Time To First Byte）を犠牲にせずにインタラクティブ部分だけを先行表示できるようになった。弊社のproperties/listing一覧ページでも、画像やレビューなど重いデータ取得部分をSuspenseで分離すべき。

- **ポイント2:** Partial Prerendering（PPR）がRSCストリーミングと統合され、静的シェル（ヘッダー・ナビ）を即時配信しつつ動的部分（在庫状況・価格）だけをストリームする構成が主流化。物件詳細ページのような「静的な外枠＋動的な空室情報」構成に特に有効。

- **ポイント3:** Server Actionsとストリーミングの組み合わせで、フォーム送信後のUI更新をページ全体の再読み込みなしに段階的に反映できる。問い合わせフォームや引越し費用の見積り計算など、多段階フローのUXをシンプルに実装できる。

- **ポイント4:** ストリーミング中のエラーバウンダリ設計が重要論点に。一部のチャンクが失敗しても他のチャンクは正常表示を継続する「部分的失敗許容」設計が推奨されており、サードパーティAPI（決済・地図等）依存部分は必ず独立したSuspense/ErrorBoundaryで囲むべき。

- **ポイント5:** RSCストリーミングはCDN/エッジキャッシュとの相性がまだ発展途上で、Vercel以外のホスティングではキャッシュ戦略の自前実装が必要になるケースがある。自社インフラ選定時はこの制約を踏まえてホスティング先を検討する必要がある。

### 3. API design REST GraphQL tRPC 2026

## CTO視点: API設計トレンド 2026

- **ポイント1（tRPCの定着）:** TypeScriptモノレポにおいてtRPCがコード生成不要のEnd-to-End型安全性を提供する標準的選択肢として定着。Next.jsのServer Actionsと機能が重なる部分もあるため、「クライアント/サーバーが完全に分離されているか」で両者を使い分ける判断が重要。

- **ポイント2（GraphQLは適材適所に収束）:** GraphQLは複数クライアント（Web/モバイル/パートナー）が異なるデータ要件を持つ大規模組織では依然有効だが、単一フロントエンドのプロダクトでは過剰な複雑さ（N+1問題、キャッシュ戦略、リゾルバ管理）がコストに見合わないケースが増加。sumitsugiのような単一Webアプリ中心のプロダクトではREST/tRPCの方が運用コストが低い。

- **ポイント3（Zodによるスキーマファースト設計）:** Zodスキーマを単一のソースとしてバリデーション・型・OpenAPI仕様を自動生成する「スキーマファースト」が主流化。本プロジェクトでも境界（API Route）でのZod活用を徹底することで、ランタイムバリデーションと型安全性を同時に確保できる。

- **ポイント4（AIエージェント対応API）:** LLMエージェントがAPIを直接呼び出す機会が増え、MCP（Model Context Protocol）のような「AIが読める」API記述形式が新たな設計要件に。将来的に外部連携（決済代行・不動産DB連携等）を増やす際は、人間向けREST設計だけでなくエージェント向けツール定義も意識すると拡張性が高い。

- **ポイント5（BFFパターンの再評価）:** フロントエンド専用のBFF（Backend for Frontend）層を薄く設け、外部API/DBの複雑さを隠蔽する設計が再注目されている。Next.jsのRoute Handlers自体がBFFとして機能するため、追加のAPIゲートウェイ層を持たずシンプルな構成を維持できる点は本プロジェクトの規模にも合致する。

### 4. serverless edge computing 2026

- **ポイント1:** エッジでのAI推論が主流化し、V8 Isolateやwasmベースのランタイム（Cloudflare Workers AI、Vercel Edge Functionsなど）でLLM推論の一部をエッジに配置するパターンが増加。レイテンシ要件の厳しいUX（検索候補、レコメンド）に効果的。

- **ポイント2:** コールドスタート問題は事実上解消され、エッジランタイムはCDN同等の起動速度を実現。これにより「エッジ=静的配信専用」という前提が崩れ、認証・A/Bテスト・パーソナライズ処理をエッジ層に移すアーキテクチャが標準化しつつある。

- **ポイント3:** エッジとオリジン間のデータ整合性がボトルネックに。分散KVストア（Cloudflare KV、Durable Objects等）やエッジネイティブDB（Turso、PlanetScale）の採用で、グローバル分散時の読み取り一貫性と書き込みレイテンシのトレードオフ管理が重要な設計判断になっている。

- **ポイント4:** Next.js 16のようなフレームワークはApp RouterでNode.js/Edgeランタイムの選択がルート単位で可能なため、本プロジェクトでも認証チェックや軽量API（物件検索フィルタなど）はEdge Runtimeに寄せ、DB書き込みを伴う処理はNode.jsランタイムに残す、というハイブリッド戦略が実用的。

- **ポイント5:** エッジ実行はベンダーロックインのリスクが高まる領域でもあり、WinterCG標準（Web標準API準拠）に沿った実装を優先することで、将来的なマルチプロバイダ移行コストを下げられる。

### 5. authentication security best practices 2026

- **パスワードレス認証の標準化:** FIDO2/WebAuthnによるパスキー認証が主流になり、フィッシング耐性のある公開鍵暗号方式が実質的なデフォルトに。パスワード単体での認証はセキュリティリスクとして扱うべき段階に来ている。

- **多層防御としてのリスクベース認証:** IPアドレス・デバイスフィンガープリント・行動パターンを組み合わせたアダプティブ認証により、固定的な2FAより高い精度で異常ログインを検知できる。全ユーザーに同じ強度の認証を強制するのではなく、リスクスコアに応じて動的に要求レベルを変える設計が効率的。

- **セッション管理とトークンの短命化:** JWTなどのアクセストークンは短寿命化し、リフレッシュトークンのローテーション・無効化リストと組み合わせる運用が必須。トークン漏洩時の被害範囲を最小化する設計を初期段階から組み込むべき。

- **認証ロジックは信頼境界で一元化:** クライアント側での認可判断は信頼せず、サーバー側（APIレイヤー）で必ず再検証する。sumitsugiのような物件情報プラットフォームでは、`seller`/`buyer`権限の境界をミドルウェアで一元管理し、個々のルートに分散させない設計が保守性とセキュリティの両面で有利。

- **シークレット管理の自動化:** APIキーやOAuthトークンのハードコード防止だけでなく、定期的なローテーションとシークレットスキャン（CI組み込み）が2026年のベストプラクティス。GitHub Actions等のCI/CDパイプラインで使うシークレットも最小権限の原則で発行・失効管理する。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はSupabaseのPgBouncer（トランザクションプール）と相性が改善され、`directUrl`でマイグレーション用の直接接続、`url`でプール接続を分ける構成が標準化してきている。sumitsugiで導入する場合もサーバーレス環境（Vercel等）でのコネクション枯渇を防ぐためこの二重接続設定は必須。

- **ポイント2:** SupabaseのRow Level Security（RLS）とPrismaの型安全なクエリは責務が異なるため併用が推奨される——PrismaはアプリケーションロジックのORM、RLSはDB層での「前の住人」「次の住人」間のデータ漏洩防止の最終防衛線として機能する。

- **ポイント3:** 2026年の潮流としてPrisma ORMの軽量化（Rustエンジン撤廃、WASM/TypeScriptベースのクエリコンパイラへの移行）が進み、Edge Runtime（Vercel Edge Functions等）からの直接DBアクセスが現実的になってきている。物件検索のような読み取り中心のAPIはEdgeで捌く設計がパフォーマンス上有利。

- **ポイント4:** SupabaseのRealtime機能（Postgres Changes）は「引越し費用」決済状況や内見予約のライブ更新に使えるが、PrismaのスキーマとSupabase Realtimeのpublication設定は別管理になるため、スキーマ変更時に両方の同期を忘れないドキュメント化が必要。

- **ポイント5:** 現状sumitsugiのコードベースにはPrisma/Supabaseの導入実績がない（`src/lib/data.ts`で管理している模様）。本格導入する場合はまず`.claude/rules/standards.md`のZodバリデーション方針との整合——PrismaのスキーマとZodスキーマの二重管理コストを避けるため、`zod-prisma-types`等での自動生成を検討すべき。

### 7. WebAssembly Rust performance 2026

- **コンパイル最適化の成熟:** Rust の `wasm-bindgen` / `wasm-pack` ツールチェーンが安定し、`wasm32-wasip2` ターゲットでのネイティブ比パフォーマンスギャップが縮小。特にSIMD命令（`std::simd`）の活用で数値計算系ワークロードはネイティブの80-90%程度まで到達している。

- **コンポーネントモデルとWASI Preview 2:** WebAssembly Component Model の普及により、Rustで書いた小さな関数単位をブラウザ・サーバー・エッジで共通モジュールとして再利用できるようになり、フロントエンド/バックエンド間のロジック重複を減らせる。

- **バンドルサイズ vs 起動速度のトレードオフ:** `wasm-opt` やコードサイズ最適化（`opt-level = "z"`）を使っても、JSバンドルより初期ロードは重くなりがち。ユーザー向けの重い処理（画像編集、PDF生成、暗号処理など）に限定して導入するのが実用的な判断基準。

- **エッジランタイムでの採用拡大:** Cloudflare Workers や Fastly Compute などのエッジ環境でRust+WasmがJSよりコールドスタートが速く、CPU集約的な処理（画像変換、決済バリデーション等）をエッジで実行するアーキテクチャが2026年に一般化しつつある。sumitsugiのような物件画像処理・PDF生成機能があれば候補になりうる。

- **デバッグ体験の改善:** ソースマップとDWARF対応が進み、ブラウザDevToolsでRustのスタックトレースを直接追えるようになったため、「Wasmは本番で何かあった時に追えない」という従来の懸念が薄れてきている。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR)の本格普及:** 静的シェルと動的コンテンツを1レスポンス内で組み合わせられるようになり、`loading.tsx`やSuspense境界の設計がパフォーマンス最適化の中心的な技術選定ポイントになっています。

- **Server Actionsのセキュリティ境界強化:** `use server`関数が暗黙的に公開APIになる点が課題視され続けており、認可チェックとZodによる入力検証をServer Action内部で必ず行う設計が標準プラクティスとして定着しています。

- **キャッシュ戦略の明示化:** `fetch`のデフォルトキャッシュ挙動が廃止されオプトイン方式になったことで、`cache: 'force-cache'`や`revalidate`タグを意識的に指定する必要があり、データ取得層での命名規則・タグ管理の設計負荷が増しています。

- **Server/Client Componentsの境界設計:** "island化"を意識し、Client Componentを末端の小さな単位に留めることでバンドルサイズとハイドレーションコストを抑える設計が、レビュー観点として重視されています。

- **Route Handlers vs Server Actionsの使い分け:** 外部連携・Webhook・GET的な読み取りはRoute Handlers、UIからのミューテーションはServer Actionsという分離が実用的なパターンとして広がり、責務が混在した実装はレビューで指摘されやすくなっています。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** 2026年のEdge Functionsはコールドスタートがほぼゼロに近づいており、V8 isolateベースの実行環境がさらに最適化されているため、レスポンスタイムが重要なSSR処理（物件検索・絞り込みなど）はEdgeに寄せる判断がしやすくなっている。

- **ポイント2:** Edge Middlewareでの認証チェック（JWT検証など）は依然軽量ロジックに限定すべきで、DBアクセスを伴う認可判定はNode.js runtimeにフォールバックする設計が推奨される。sumitsugiの`auth-context.tsx`連携部分は、Edgeでの検証とNode側でのセッション確定を分離する構成が安全。

- **ポイント3:** Vercelの料金モデルがEdge実行時間とリクエスト数ベースで細分化されており、画像処理や重いレンダリングをEdgeで行うとコストが跳ねやすい。物件詳細ページの画像最適化は`next/image`経由でCDNキャッシュに任せ、Edge Functionの処理は最小限（リダイレクト、A/Bテスト、地域判定）に留めるのがコスト最適。

- **ポイント4:** Partial Prerendering（PPR）とEdge Functionsの組み合わせが2026年の主流パターンになっており、静的な物件一覧シェルを即時配信しつつ、動的な空室状況や価格だけをEdgeでストリーミング差し込む構成が、Core Web Vitals改善とサーバー負荷軽減を両立できる。

- **ポイント5:** リージョン指定（`regions`設定）を日本リージョン優先に固定し、グローバル分散よりレイテンシ予測可能性を優先する設計が、国内ユーザー中心のプロダクトには適している。マルチリージョンの恩恵よりデバッグ・監視の単純さを優先すべきフェーズ。

### 10. TypeScript type safety patterns 2026

- **構造的型チェックの強化:** TypeScript 5.x系では`satisfies`演算子が定着し、型推論を保ったまま構造的な整合性チェックが可能になった。型アノテーションで情報を失わずにリテラル型を保持できるため、設定オブジェクトやルーティング定義で特に有効。

- **Branded Types（名目的型付け）の普及:** `UserId`や`Email`のようなプリミティブの混同を防ぐため、`type UserId = string & { __brand: 'UserId' }`パターンが標準化しつつある。Zodなど実行時検証ライブラリとの組み合わせで「型レベルの安全性」と「ランタイムの安全性」を一致させる設計が主流。

- **Zodを中心としたSchema-first開発:** 型定義とランタイム検証を単一のスキーマから生成する手法（`z.infer<typeof schema>`）が、APIバウンダリやフォーム入力の標準パターンとして確立。このプロジェクトのように「Input validationにZodを使う」という方針は、型安全性とセキュリティを両立させる現在のベストプラクティスと一致している。

- **厳格なユニオン型とTemplate Literal Typesの活用:** `'draft' | 'public'`のようなステータス型を拡張する際、全使用箇所をgrepで洗い出すプラクティスは重要だが、さらに進んでTemplate Literal Typesや`as const`で定義した配列から型を導出することで、値の追加漏れをコンパイル時に検出できる設計が増えている。

- **tscの型チェックとビルドパイプラインの分離の限界:** ESLintやテストだけでは型エラーを捕捉できないケースが多く、CIに`tsc --noEmit`相当のビルドステップを必須化する動きが強まっている。型安全性は「書く時」だけでなく「CIで強制する」ことで初めて組織的に機能する。
