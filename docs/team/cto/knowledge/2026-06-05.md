# CTO Knowledge - 2026-06-05

## Daily Update (2026-06-05)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 15で安定化したPPRにより、静的シェルを即座に配信しつつ動的コンテンツをストリーミングする設計が標準化。`<Suspense>`境界の設計がパフォーマンスの核心になっている。

- **Turbopackへの完全移行:** Webpackベースのビルドは実質レガシー化。Turbopackによりコールドスタート数十秒→数秒、HMRも大幅高速化されており、開発体験とCI時間の両方に直結する。

- **React Server Componentsのデータフェッチ最適化:** クライアントへのJS転送量を削減するためにRSCを最大活用し、`fetch`のキャッシュ戦略（`force-cache`/`no-store`/`revalidate`）を意図的に設計することがTTFBとLCP改善の鍵。

- **Server Actions + 楽観的UIパターン:** フォーム処理をServer Actionsに寄せ、`useOptimistic`で即時フィードバックを提供する設計が主流。APIルートを減らしつつUXを向上できる。

- **Core Web Vitals計測の自動化:** `@vercel/speed-insights`やLighthouse CIをCD/CDパイプラインに組み込み、INP（Interaction to Next Paint）をLCPと同等に監視する体制が2026年の標準。リグレッション検知なしのデプロイは危険。

### 2. React Server Components streaming 2026

- **Suspense境界の細粒度化が鍵:** 2026年時点ではSuspenseをコンポーネント単位で細かく配置し、重いデータフェッチ部分だけをストリーミングで遅延させることがベストプラクティス。ページ全体をブロックしない設計が標準化されている。

- **`use()`フックによる非同期処理の統一:** React 19で安定化した`use(Promise)`パターンにより、Server/Client Components間でのデータ受け渡しがシンプルになり、ウォーターフォール問題を回避しやすくなった。

- **PPR（Partial Prerendering）との組み合わせが主流:** Next.js 15以降でPPRが安定し、静的シェルを即座に返しつつ動的部分をストリーミングする手法が本番環境での標準パターンになっている。TTFBとTTIを同時に最適化できる。

- **キャッシュ戦略の再設計が必要:** `fetch()`のデフォルトキャッシュ挙動がNext.js 15で変更されたため、`unstable_cache`や`cacheTag`/`revalidateTag`を明示的に使い、ストリーミングと組み合わせたきめ細かいキャッシュ制御が求められる。

- **エラー境界の配置がUXに直結:** ストリーミング環境ではエラーが部分的に発生するため、`error.tsx`をSuspense境界と対応させて配置しないと、エラー時にページ全体が壊れるリスクがある。境界設計はアーキテクチャレビューの必須項目。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの成熟とフルスタック型安全の標準化:** 2026年時点でtRPCはNext.js/Remix環境での事実上の標準となり、スキーマ定義なしにフロントエンド↔バックエンド間の型共有が完結するため、小〜中規模チームのDXを劇的に改善している。

- **GraphQLはBFF層に集約:** マイクロサービス間の通信にGraphQLを使うユースケースは減少し、複数バックエンドをクライアント向けに集約するBFF（Backend for Frontend）レイヤーとしての用途に特化してきた。Federation（Apollo/Hive）の採用が大規模組織で加速。

- **RESTはパブリックAPIの不動の王者:** サードパーティ向け公開APIでは引き続きRESTが主流。OpenAPI 3.1 + Zodによるスキーマファースト設計と自動型生成（`@hey-api/openapi-ts`等）を組み合わせることで、tRPC並みの型安全を実現するアプローチが普及。

- **HTTPストリーミングとServer-Sent Eventsの台頭:** AI/LLM統合の普及でストリーミングレスポンスの需要が急増し、WebSocketより軽量なSSEがリアルタイム通信の選択肢として再評価されている。tRPCもサブスクリプション対応を強化。

- **コントラクトファーストとAPI Governance:** チーム規模が拡大するにつれ、Spectral/Bump.shによるAPIリントと変更検知をCIに組み込み、破壊的変更を自動検出するガバナンス体制が不可欠になっている。設計→実装ではなく、コントラクト（スキーマ）が唯一の真実となる。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** 2026年時点でWebAssembly（Wasm）ランタイムが成熟し、LLMの量子化モデルをエッジノードで直接実行するパターンが普及。レイテンシ削減と個人情報のローカル処理を両立できる。

- **SQLite-at-the-Edgeの台頭:** Cloudflare D1やTurso（libSQL）に代表される分散SQLiteが実用段階に入り、エッジでの読み書きが可能に。従来「エッジはステートレス」という制約が崩れ、アーキテクチャ設計の前提を見直す必要がある。

- **コールドスタート問題の実質的解消:** V8 Isolateベースの実行環境が主流となり、Node.jsコンテナと比較してコールドスタートがサブミリ秒レベルに。ただしNode.js互換性の制限（一部NPMパッケージ非対応）は依然として設計上の制約となる。

- **エッジ/オリジン間のデータ整合性管理が主戦場:** 分散キャッシュやエッジKVの普及により、キャッシュ無効化戦略とデータ一貫性保証が複雑化。eventual consistencyを前提とした設計スキルが開発チームに求められる。

- **マルチクラウド・エッジの標準化圧力:** Cloudflare Workers・Vercel Edge・AWS Lambda@Edgeの差異をWASI（WebAssembly System Interface）で吸収しようとする動きが加速。ベンダーロックインを避けたい場合はWasm移植性を設計段階から考慮すべき。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の本格採用:** 2026年はパスワードレス認証が主流となり、フィッシング耐性のあるパスキーをデフォルトにすることが業界標準になった。Next.jsでは`@simplewebauthn`ライブラリが実績ある選択肢。

- **セッション管理の厳格化:** JWTの有効期限を短く（15分）設定し、リフレッシュトークンはHTTP-only Cookieに限定する。`localStorage`へのトークン保存はXSS脆弱性の温床として完全に非推奨化。

- **デバイスバインディングとコンテキスト認証:** IPアドレス・デバイスフィンガープリント・行動パターンを組み合わせたリスクベース認証が標準化。異常検知時に追加認証を要求するアダプティブMFAが重要。

- **OAuth 2.1 / DPoP（Demonstrating Proof of Possession）:** トークン盗難対策としてDPoPが普及し、アクセストークンを特定のクライアントキーに紐付ける。BFFパターン（Backend for Frontend）と組み合わせることでSPA環境のセキュリティを大幅強化できる。

- **サプライチェーン攻撃への対策:** 認証ライブラリ自体の依存関係汚染リスクが増大しており、`bun audit`による定期スキャンとSBOM（ソフトウェア部品表）の管理が不可欠。Auth.jsやSupabase Authなど実績あるライブラリに集約することが推奨。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x の Edge Runtime 完全対応:** Prisma ORM が Cloudflare Workers・Vercel Edge Functions などのエッジ環境でネイティブ動作するようになり、Supabase の Connection Pooler（PgBouncer / Supavisor）と組み合わせることでコールドスタートの課題がほぼ解消された。

- **Supabase Realtime + RLS の本番運用成熟:** Row Level Security を Prisma スキーマと併用する際、マイグレーション管理が複雑になりがちだが、`prisma migrate` 後に RLS ポリシーを別ファイルで管理するパターン（`supabase/migrations/`）が業界標準として定着しつつある。

- **Connection Pooling は Supavisor 一択へ:** Supabase が PgBouncer から Supavisor（Elixir ベース）に移行完了し、サーバーレス環境での多数コネクション問題が大幅改善。Prisma の `directUrl` + `DATABASE_URL`（pooled）の二重設定が必須パターン。

- **型安全な DB アクセスの標準化:** Prisma Client の生成型と Supabase の `supabase-js` 型生成（`supabase gen types typescript`）を共存させるよりも、**Prisma 単一に統一**するプロジェクトが増加。Auth のみ Supabase、データアクセスは Prisma という責務分離が現実的な選択。

- **ベクター検索の組み込み:** Supabase が `pgvector` を標準提供し、Prisma の `Unsupported` 型経由でのベクター列操作が一般化。RAG 構成で Supabase をベクター DB 兼 RDBMS として使う設計が 2026 年の主流トレンドになっている。

### 7. WebAssembly Rust performance 2026

- **Component Model の成熟:** WASIp2（WASI Preview 2）とComponent Modelが2025年に安定化し、RustのWebAssemblyコンポーネントが言語間で型安全に相互運用できるようになった。プラグインアーキテクチャやマイクロサービス間通信への採用が加速している。

- **SIMD・スレッド対応の普及:** WebAssembly SIMDとShared Memoryスレッドが主要ブラウザ・ランタイムで広く利用可能となり、Rustの`std::simd`や`rayon`を活用した並列処理が実用レベルに達した。画像処理・音声解析などCPU集約タスクでネイティブに迫るスループットが出る。

- **Wasmtime / WasmEdgeのサーバーサイド採用:** エッジコンピューティング（Cloudflare Workers、Fastly Compute）でRust+WasmがNode.jsより低レイテンシ・低メモリで稼働する事例が増加。コールドスタートが1ms以下というベンチマークも出ており、FaaSの代替として現実的な選択肢になっている。

- **バイナリサイズの最適化成熟:** `wasm-opt`（Binaryen）＋`wasm-pack`＋Rustの`panic = "abort"` / `opt-level = "z"` 組み合わせで、フロントエンド向けWasmバイナリが50〜100KB台に収まるケースが標準化。初期ロードのUXペナルティがほぼ解消されつつある。

- **Rust専用ツールチェーンの整備:** `cargo-component`が実用段階に入り、従来の`wasm-bindgen`ワークフローより型生成・バインディングが大幅に簡略化された。開発体験がWebpackエコシステムと遜色ないレベルまで改善されており、採用コストが下がっている。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの設計:** 2026年のベストプラクティスは「デフォルトServer Components、必要な箇所だけClient Components」。`'use client'`境界を末端コンポーネントに押し下げることでバンドルサイズを最小化できる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的ストリームを同一ルートで混在させるPPRが安定版となり、Suspense境界の設計がアーキテクチャの核になった。`<Suspense fallback>`の粒度がUXとTTFBを直接左右する。

- **Server Actions によるAPI Routes の置き換え:** フォーム送信・ミューテーション処理はServer Actionsに集約し、従来の`/api/*`ルートを削減する流れが加速。ただしCSRF対策はフレームワーク任せにせず、`zod`バリデーションとオリジン検証を必ず実装する。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15+で導入された`use cache`で、関数・コンポーネント単位のキャッシュ制御が可能に。`revalidateTag`と組み合わせてデータ依存のオンデマンド再検証を設計するのが現在のベストプラクティス。

- **Turbopack の本番採用:** Turbopackがデフォルトビルダーとして安定化し、大規模プロジェクトでのコールドスタートが従来比50-70%改善。ただし一部のwebpackプラグイン互換性は依然確認が必要で、移行前に`next build --turbo`でCIを通すことを推奨。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Runtimeでは`Node.js`互換APIが拡充されており、`crypto`・`Buffer`等の標準モジュールが利用可能になったが、バンドルサイズは依然1MB未満に抑えることがコールドスタート最小化の鉄則。

- **ポイント2:** `waitUntil()`を活用した非同期バックグラウンド処理（ログ送信・キャッシュ更新）により、レスポンスタイムを応答完了後の処理と分離できる——これを使わずにawaitするのはEdgeの利点を捨てることに等しい。

- **ポイント3:** KV・Blob・Postgresなどのストレージは「リージョン固定」か「グローバルレプリカ」かで遅延特性が大きく異なる。Edge Functionのデプロイリージョンとデータストアのリージョンを揃えないと、Edgeにした意味がなくなる。

- **ポイント4:** `middleware.ts`の肥大化は全リクエストへのレイテンシ汚染につながるため、認証チェック・A/Bフラグ・リダイレクトのみに絞り込み、ビジネスロジックはRoute Handlersに委譲するのがアーキテクチャ上の正解。

- **ポイント5:** ISR（Incremental Static Regeneration）と`stale-while-revalidate`ヘッダーの組み合わせにより、Edge Functionの実行回数自体を削減するキャッシュ戦略が2026年時点での最重要最適化——コードを速くするより「呼ばれない」設計が先。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の`satisfies`は型チェックを維持しながら推論を最大化でき、`as`キャストの危険な使用を大幅に削減できる。2026年現在、コードベース全体への適用が標準実践となりつつある。

- **Template Literal Types + Branded Types の組み合わせ:** `type UserId = string & { readonly _brand: 'UserId' }`のようなBranded Typesで実行時コストゼロのドメイン安全性を実現し、プリミティブ型の混同バグを根絶できる。

- **`noUncheckedIndexedAccess` の必須化:** tsconfig で`noUncheckedIndexedAccess: true`を有効にすることで配列・オブジェクトアクセスが`T | undefined`となり、ランタイムエラーの主要原因を型レベルで封じ込められる。

- **Discriminated Union の徹底と`never`チェック:** `exhaustive check`パターン（`default: const _: never = val`）をswitch文に組み込むことで、将来のunion型拡張時にコンパイルエラーとして検出でき、サイレントなロジック欠落を防げる。

- **Zod + 型推論の一元管理:** `z.infer<typeof schema>`でバリデーションスキーマから型を導出し、型定義とバリデーションロジックの乖離を構造的に排除する。APIバウンダリやフォームの入力点に集中配置するのが2026年のベストプラクティス。
