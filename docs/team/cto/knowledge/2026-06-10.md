# CTO Knowledge - 2026-06-10

## Daily Update (2026-06-10)

### 1. Next.js performance optimization 2026

- **React Server Components の徹底活用:** RSCをデフォルトとし、クライアントコンポーネントは状態・インタラクションが必要な最小単位に限定することで、クライアント側のJSバンドルを大幅削減できる。

- **Partial Prerendering (PPR) の採用:** 静的シェルをCDNから即座に配信しつつ、動的コンテンツをストリーミングする手法が2026年時点で本番利用可能となり、TTFBとLCPを同時改善できる。

- **Turbopack による開発・ビルド高速化:** Webpackからの移行が完了したプロジェクトでは、ローカル開発のHMRが劇的に高速化し、大規模チームの生産性向上に直結する。

- **Server Actions とキャッシュ戦略の精緻化:** `'use cache'`ディレクティブ（Next.js 15+）と`revalidateTag`による細粒度のキャッシュ制御で、不要なリクエストを削減しつつ鮮度を保つ設計が標準化されている。

- **Core Web Vitals ファースト設計:** LCP・INP・CLSをCI/CDパイプラインに組み込み（Lighthouse CI等）、デプロイ前にパフォーマンス劣化を検知する体制を構築することが、ローンチ後の品質維持に不可欠。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Prerendering (PPR) の本番普及:** Next.js 15以降でPPRが安定化し、静的シェルを即座に配信しつつ動的コンテンツをストリーミングする「ハイブリッドレンダリング」がデフォルト戦略になりつつある。TTFBとLCPの両立が現実的になった。

- **ポイント2: Suspense境界の設計が勝負どころ:** RSCストリーミングの恩恵を最大化するには、Suspenseの粒度設計が重要。粗すぎるとウォーターフォールが残り、細かすぎるとLayout Shiftが増える。コンポーネントツリーのデータ依存関係を明示的に整理する設計プラクティスが求められる。

- **ポイント3: Server Actionsとの統合でクライアントJS削減が加速:** `useOptimistic` + Server Actionsの組み合わせにより、多くのフォーム・CRUD操作でReact Queryやreduxが不要になる。バンドルサイズ削減と開発シンプル化を同時に達成できる。

- **ポイント4: Edgeランタイムでのストリーミング制約に注意:** Cloudflare WorkersやVercel Edgeでは一部Node.js APIが使えず、DBクライアントやファイル操作でフォールバックが必要なケースがある。RSCをEdgeデプロイする際はランタイム互換性の事前検証が不可欠。

- **ポイント5: DevToolsとObservabilityの整備が急務:** ストリーミング環境ではサーバー/クライアント境界をまたぐトレースが複雑になる。OpenTelemetry + Vercel SpeedInsights等でServer Componentの実行時間を可視化し、ストリーミング遅延のボトルネックを特定する体制を整えることが本番運用の前提条件になっている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの成熟と採用拡大:** Next.js/フルスタックTS環境でtRPCが事実上の標準になりつつある。型安全性をAPIバウンダリ越しに担保できるため、スキーマ定義の二重管理が不要になった。

- **REST vs GraphQL の収束:** GraphQLはBFF（Backend for Frontend）パターンに特化し、内部マイクロサービス間はREST or gRPCという棲み分けが定着。「全部GraphQL」のアンチパターンから脱却したチームが増えている。

- **OpenAPI 3.1 + コード生成の標準化:** REST採用時はOpenAPI仕様からクライアント/サーバーコードを自動生成（`openapi-ts`等）するパターンが主流。型安全性でtRPCに近い体験を実現できる。

- **エッジ・ストリーミング対応:** Vercel AI SDK等の影響でSSE/WebSocketによるストリーミングAPIが必須要件化。tRPCもサブスクリプション対応が強化され、リアルタイム機能の実装コストが大幅に低下。

- **契約駆動開発（Contract-First）の復権:** APIを先にスキーマ定義し、フロント/バックが並行開発するワークフローが再評価されている。特にチーム分割後の開発速度向上に直結する。

### 4. serverless edge computing 2026

- **ポイント1: エッジファーストアーキテクチャの主流化** — Cloudflare Workers・Vercel Edge Functions・Deno Deployが成熟し、レイテンシ感度の高い処理（認証、A/Bテスト、パーソナライゼーション）をエッジで実行するのが標準になりつつある。

- **ポイント2: WebAssembly（WASM）がエッジランタイムの共通言語に** — V8 IsolateだけでなくWASMベースのランタイムが普及し、Go・Rust・Pythonで書いたコードをコールドスタートなしにエッジへデプロイできるようになった。ポータビリティとパフォーマンスを両立できる点が大きい。

- **ポイント3: エッジDBとの統合が実用フェーズへ** — Cloudflare D1・Turso（libSQL）・PlanetScale Metalなど、エッジ近傍でクエリが完結するDB群が登場し、「エッジはステートレス」という制約が崩れてきた。ただしグローバル整合性のトレードオフは依然として設計上の難所。

- **ポイント4: AI推論のエッジ実行が現実的に** — Cloudflare Workers AI・Vercel AI SDKのEdge Runtimeサポートにより、軽量LLM（1〜3Bパラメータ）の推論をエッジで完結させるユースケースが増加。レイテンシとコストでオリジンへの往復を避けられる。

- **ポイント5: オブザーバビリティがエッジ展開のボトルネック** — 分散実行環境ゆえにトレーシング・ログ集約が複雑化しており、OpenTelemetryのエッジ対応とサンプリング戦略の設計が2026年の実務的課題。エッジ導入前にオブザーバビリティ基盤を整えることが失敗を防ぐ鍵。

### 5. authentication security best practices 2026

**Authentication Security Best Practices 2026**

- **パスキー（Passkeys）の本格採用:** FIDO2/WebAuthnベースのパスキーが業界標準となり、フィッシング耐性の高いパスワードレス認証が実用段階に到達。新規プロダクトはパスワード認証をレガシーとして扱い始めている。

- **フィッシング耐性MFAへの移行:** SMS OTPはSIMスワップ攻撃の脆弱性から非推奨化が進み、FIDO2ハードウェアキーやデバイスバウンドパスキーへの移行が加速。TOTPも中間者攻撃に弱いため、ハイセキュリティ領域では廃止対象。

- **ゼロトラスト認証の実装:** "一度認証したら信頼"から"継続的検証"へ。デバイス健全性・地理情報・行動パターンをリアルタイム評価するコンテキストアウェア認証が標準になりつつある。

- **トークンライフタイムの最小化:** アクセストークンは15分以下、リフレッシュトークンは使い捨てローテーション（RTR）が必須。JWTの長命トークンはセッションハイジャックリスクが高く、短命＋失効リストの組み合わせが主流。

- **AI駆動の異常検知との統合:** ログイン行動のベースラインをMLで学習し、異常なアクセスパターン（時間帯、場所、デバイス変化）をリアルタイム検出してステップアップ認証をトリガーする仕組みが普及。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORM の成熟とPrisma Postgres:** 2026年時点でPrisma v6+が主流となり、Prisma独自のPrisma Postgresサービス（エッジ対応コネクションプーリング内蔵）がSupabaseと直接競合する形に。ORM層とDB層の垂直統合が加速している。

- **Supabase の Row Level Security (RLS) ファースト設計:** SupabaseのRLSをPrismaと併用する場合、Prisma経由ではRLSがバイパスされるリスクがある。サービスロールキーの使いどころを明確に分離し、エッジ関数側でユーザーコンテキストを正しく伝播させる設計が必須。

- **エッジ/サーバーレス環境でのコネクション管理:** Vercel Edge / Cloudflare Workersとの組み合わせでは、Prisma Accelerateや`@supabase/supabase-js`のHTTPモードなどコネクションプーリング非依存の接続戦略が標準化。Cold start問題が事実上解消されつつある。

- **型安全なクエリとZodの統合:** PrismaのスキーマからZodバリデーターを自動生成する`zod-prisma-types`や`prisma-zod-generator`が実用段階に入り、APIバウンダリの型整合性をビルド時に担保するパターンが定着。このプロジェクトでも導入検討の価値あり。

- **マイグレーション戦略の二分化:** Prisma Migrateによる「開発者主導スキーマ管理」vs Supabase Migrations（SQL直書き）の選択は、チーム規模とDBA有無で決まる。フルスタック少人数チームならPrisma一本化、Supabaseのダッシュボード機能（Auth/Storage/Realtime）を多用するならSupabase Migrations優先が実用的。

### 7. WebAssembly Rust performance 2026

- **Component Model の本格普及:** WebAssembly Component Model（WASI 0.2）が2025年に安定化し、Rustで書いたWasmコンポーネントを言語間で安全に合成できるようになった。マイクロサービスの代替としてエッジ・サーバーサイドでの採用が急増している。

- **SIMD・スレッド対応の成熟:** Wasm SIMD命令とShared Memoryが全主要ブラウザ・ランタイムで安定しており、RustのSIMDライブラリ（`std::simd`）経由で画像処理・ML推論をネイティブに近い速度で実現できる。ゲームエンジンや音声処理での実績が蓄積されている。

- **コールドスタートの課題は残存:** Wasmのインスタンス化コスト（特にコンパイル）はCDNエッジ環境でまだボトルネックになり得る。Wasmtime の AOT コンパイル（`.cwasm`）や Wasmer の Singlepass backend で軽減できるが、設計段階での考慮が必要。

- **`wasm-bindgen` から `wit-bindgen` へ移行が加速:** ブラウザ向けの `wasm-bindgen` に加え、サーバーサイド・クロスプラットフォーム向けには `wit-bindgen`（WITインターフェース定義）が標準になりつつある。新規プロジェクトはComponent Model前提で設計すべき。

- **メモリ管理の最適化が差別化ポイント:** RustのゼロコストアブストラクションはWasm環境でも有効だが、GCなし言語ゆえのメモリレイアウト設計（アロケータ選択：`wee_alloc` vs `dlmalloc`、アリーナアロケータの活用）がパフォーマンスの鍵。バイナリサイズと速度のトレードオフを計測ベースで判断することを推奨する。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** クライアントコンポーネントは「インタラクティブな葉ノード」に限定し、データフェッチ・ロジックはすべてServer Componentsに集約する。バンドルサイズの劇的な削減とTTFBの改善が得られる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェル＋動的スロットの組み合わせにより、従来の SSG/SSR の二択を超えた最適化が可能になった。`experimental_ppr` から安定版への移行タイミングを見極めることが2026年の重要課題。

- **Server Actions による API Routes の置き換え:** フォーム送信・ミューテーション処理をServer Actionsに移行することで、`/api` ルートの乱立を防ぎ、型安全性とコロケーションを両立できる。ただし長時間処理や外部Webhookは引き続きRoute Handlersが適切。

- **Streaming と Suspense の粒度設計:** `loading.tsx` による粗粒度のフォールバックではなく、コンポーネント単位の `<Suspense>` で段階的ストリーミングを設計する。ユーザー知覚速度の改善に直結するが、ウォーターフォールを生まない並列フェッチパターン（`Promise.all`）との組み合わせが必須。

- **キャッシュ戦略の明示化:** Next.js 15以降はデフォルトキャッシュが変更され、`fetch` のキャッシュ挙動が opt-in になった。`revalidate` / `no-store` を各データフェッチで明示的に宣言し、「暗黙のキャッシュ」による本番バグを防ぐことが開発規律として定着してきている。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタートの実質ゼロ化:** V8 Isolateベースの実行モデルにより、コンテナ型と比べてコールドスタートは数ms以下に抑えられる。ただしIsolate間でメモリを共有できないため、キャッシュ戦略はリクエスト単位で設計する必要がある。

- **バンドルサイズ制約への対処:** Edge Functionsは圧縮後4MB以下のバンドルサイズ制限があり、重量級ライブラリ（prisma、zod等）の直接インポートは避け、軽量代替か動的インポートで回避するのがベストプラクティス。

- **Middlewareのマッチャー最適化:** `matcher`設定で対象パスを絞り込まないと全リクエストにEdge処理が走りコスト増大につながる。静的アセットや`_next/`パスは明示的に除外するのが必須。

- **ストリーミングレスポンスとRSCの親和性:** React Server ComponentsとEdge Runtimeを組み合わせたStreaming SSRは、TTFBを大幅に短縮できる。2026時点ではSuspense境界の粒度設計がパフォーマンスの鍵で、過細粒度はオーバーヘッドになる。

- **エッジでのDBアクセスパターン:** Neon・PlanetScale等のHTTPベースDB、またはCloudflare D1相当のエッジネイティブDBの採用が進む。従来のTCP接続型DBはEdgeから直接叩けないため、接続プーリング層（Prisma Accelerate等）を挟むアーキテクチャが標準化しつつある。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `type UserId = string & { readonly _brand: 'UserId' }` のようなブランド型がライブラリ依存なしに普及し、ドメイン境界での誤った型混入をコンパイル時に防ぐ設計が当たり前になっている。

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の `satisfies` が型推論を維持しながら型チェックを強制できるため、`as const` との組み合わせで設定オブジェクトや定数マップの安全性が大幅に向上している。

- **Template Literal Types によるAPIルート型付け:** `type Route = '/users/${string}' | '/posts/${number}'` のようにエンドポイントパターンを型レベルで表現し、タイプセーフなルーティングとフェッチラッパーを構築するパターンが主流になっている。

- **`using` / Explicit Resource Management の普及:** TypeScript 5.2のリソース管理構文（`using`）によりDB接続・ファイルハンドル・ロックのスコープ管理が型安全になり、リソースリークのクラス全体をコンパイル時に検出できる。

- **型レベルテストの義務化:** `tsd` や `expect-type` を使った「型の振る舞いのテスト」をCIに組み込み、リファクタリング時の型退行を検出する運用が成熟したチームでは標準になっている。
