# CTO Knowledge - 2026-11-13

## Daily Update (2026-11-13)

### 1. Next.js performance optimization 2026

- **ポイント1:** Next.js 16ではTurbopackがビルド・devサーバーの標準となり、Webpack比で大幅な高速化を実現している。大規模な`src/`配下のコンポーネント数が増えても、HMRやコールドスタートの遅延を抑えられる。
- **ポイント2:** Partial Prerendering (PPR)が本格普及期に入り、静的部分と動的部分を1ページ内で混在させてTTFBを最適化できる。物件一覧ページのように「静的なレイアウト＋動的な価格・在庫情報」という構成に特に有効。
- **ポイント3:** React Server Components中心の設計が定着し、クライアントバンドルサイズを最小化する「use client境界を最後まで押し込む」設計が重要になっている。認証状態やフォームなど本当にインタラクティブな部分だけをクライアント化すべき。
- **ポイント4:** 画像・フォント最適化は`next/image`と`next/font`のデフォルト設定だけでは不十分になりつつあり、物件写真のような大量画像を扱うUIではCDN側のレスポンシブ配信・AVIF優先設定を明示的にチューニングする必要がある。
- **ポイント5:** CachingはNext.js 15以降で「デフォルトはキャッシュしない」方向に転換されたため、`fetch`のキャッシュ戦略（`revalidate`, `cache: 'force-cache'`等）を明示的に設計しないとパフォーマンスが退化する。物件データのようにSSGとISRを使い分ける設計判断が今まで以上に重要。

### 2. React Server Components streaming 2026

**CTO視点: React Server Components Streaming 2026のトレンド**

- **ポイント1（Partial Prerenderingの標準化）:** Next.js 16ではPPR（Partial Prerendering）がデフォルトの最適化パスとして定着し、静的シェルを即時配信しつつ動的部分だけをストリーミングする構成が標準化。弊社のようなlisting/propertiesページでは、物件カード一覧の静的部分と在庫状況・価格などの動的部分を分離することでTTFBとLCPを同時に改善できる。

- **ポイント2（Suspense境界の粒度設計がパフォーマンスの肝）:** Suspense boundaryを細かく切りすぎるとウォーターフォールが増え、粗すぎるとストリーミングの恩恵が薄れる。データ依存の深さに応じて境界を設計する「段階的開示」パターンが重要で、`loading.tsx`と組み合わせたネストしたSuspenseの設計レビューをコードレビューの標準項目に入れるべき。

- **ポイント3（RSC Payloadのキャッシュ戦略）:** `use cache`ディレクティブとCache Componentsの組み合わせで、RSCペイロード単位のキャッシュ制御が実用段階に入っている。`draft`/`public`ステータスを持つ物件データのようにミューテーション頻度が異なるデータは、キャッシュタグを分けて部分的に再検証する設計が推奨される。

- **ポイント4（Server Actionsとストリーミングの統合）:** フォーム送信後にServer Actionの結果をストリーミングで返しつつUIを即時更新する「Optimistic + Streaming」パターンが一般化。問い合わせフォームや内見予約フローなど多段階フローのUXに直結するため、E2Eテストでストリーミング中の中間状態も検証対象に含める必要がある。

- **ポイント5（エッジランタイムとの親和性）:** RSCストリーミングはエッジでの部分実行（Edge Runtime + Node Runtimeのハイブリッド）と組み合わさることで、地理的に分散したユーザーへの初期応答を高速化できる。ベータローンチ後のスケール局面で検討すべき最適化領域として優先度を上げておきたい。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCの型安全性メリットはBFF層に限定的に有効で、モバイルクライアントや外部パートナー向けAPIにはOpenAPIスキーマを持つRESTまたはGraphQLが依然優位。sumitsugiのような単一Next.jsアプリ構成ではtRPC導入コストは低いが、将来モバイルアプリや外部連携を想定するなら早期のスキーマ駆動設計（Zod→OpenAPI自動生成）を優先すべき。

- **ポイント2:** GraphQLは「過剰適合」のリスクが指摘され続けている——N+1問題やキャッシュ戦略の複雑さに対するリソースが、物件検索・フィルタリングのような単純なCRUD中心アプリには見合わないケースが多い。sumitsugiの物件一覧・検索機能はRESTのページネーション＋クエリパラメータで十分であり、GraphQL導入は過剰設計になりやすい。

- **ポイント3:** 2026年はAPI設計における「エージェント消費」が新たな制約条件として定着しつつある——LLMエージェントがAPIを直接呼ぶケースを想定し、冗長だが明示的なレスポンス構造（型安全なエラーコード、自己記述的フィールド名）が人間向けAPI以上に重要になっている。今後sumitsugiで外部AI連携（物件マッチング等）を検討するなら、この観点を設計初期から組み込むべき。

- **ポイント4:** Zodを境界検証に使う現在の方針（`.claude/rules/standards.md`記載）は、tRPC・REST問わずAPI実装の型安全性の土台として引き続き最適解。tRPCに移行してもZodスキーマはそのまま再利用できるため、将来の技術選定の自由度を損なわない。

- **ポイント5:** 小規模チーム・単一リポジトリ構成（Next.js App Router）では、Route Handlers + Zod検証による薄いREST層が運用コスト最小で、Beads/Linear連携スクリプトのような内部ツール統合にも扱いやすい。外部公開APIが必要になった時点でtRPC/GraphQLを検討する「後回し判断」が合理的。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** V8 isolateベースのWinterCG準拠ランタイム（Cloudflare Workers、Deno Deploy、Vercel Edge）がデファクトスタンダード化し、コールドスタートがほぼゼロに近づいたことで、エッジでのSSRやAPI処理がデフォルト選択になっている。

- **エッジでのステート管理の成熟:** Durable Objects・Cloudflare D1・Turso（libSQL）など、エッジ分散に対応したデータレイヤーが実用段階に入り、「エッジはステートレスのみ」という制約が崩れつつある。sumitsugiのような物件検索・予約フローでも低レイテンシなリード処理をエッジに寄せる余地がある。

- **コスト構造の変化:** リクエスト課金からCPU時間課金への移行が進み、I/O待ち（DB呼び出し等）のコストが実質ゼロになるモデルが増加。Next.jsのサーバーコンポーネントと組み合わせることで、従来のサーバーレス（Lambda等）よりコスト効率が上がるケースが多い。

- **観測性・デバッグの弱点は依然残る:** 分散実行環境ゆえにローカル再現が難しく、ログ・トレーシング（OpenTelemetry対応）の整備が遅れているベンダーも多い。MVP段階では本格導入より、まずVercelの標準エッジ機能を使い、観測性ツールが整ってから段階的に移行するのが現実的。

- **ロックインリスクの顕在化:** 各ベンダー独自APIへの依存が強く、移行コストが高い。sumitsugiはNext.js on Vercelという比較的ポータブルな構成を維持しており、法務確認中の現フェーズでは無理にマルチクラウド化を急ぐ必要はない。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証（WebAuthn/パスキー）がデフォルトとなり、フィッシング耐性のある認証がユーザー体験と安全性を両立させる主流になっています。sumitsugiでも次の住人・前の住人双方のログインにパスキー対応を検討する価値があります。

- **トークンのライフサイクル管理の厳格化:** 短命アクセストークン＋リフレッシュトークンローテーション、デバイスバインディング（DPoP等）が標準化し、トークン漏洩時の被害範囲を最小化する設計が重視されています。

- **継続的リスク評価（Continuous Authentication）:** 一度のログインで終わらず、デバイス・位置情報・行動パターンを基にセッション中も継続的にリスクを評価し、異常時に再認証を要求する仕組みが主流化しています。

- **サプライチェーン経由の認証情報漏洩対策:** npm/依存パッケージ経由の資格情報窃取が増加しており、Secretのスキャン・ローテーション自動化と、認証ロジックへのサードパーティ依存を最小限に抑える設計が重要です。

- **プライバシー・コンプライアンスとの統合:** 法務確認待ちの現フェーズを踏まえると、認証設計自体が個人情報保護法・特商法対応の一部となるため、最小権限のセッション管理とログの取り扱い（個人情報を含めない）を初期設計に組み込むべきです。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Supabaseの接続プーリング（Supavisor/PgBouncer）とPrisma Accelerateの組み合わせがサーバーレス環境での必須構成になっており、PrismaClientのコールドスタート時のコネクション枯渇問題を解決する標準パターンとして定着している。

- **ポイント2:** PrismaのTypedSQL機能が成熟し、複雑なクエリをORM経由ではなく型安全な生SQLで書けるようになったことで、Supabase側のRLS（Row Level Security）ポリシーと組み合わせたパフォーマンスチューニングがしやすくなっている。

- **ポイント3:** SupabaseのRealtime機能とPrisma Schemaを直接統合する動きが進み、物件ステータス（`draft`/`public`）のような状態変化をフロントエンドにリアルタイム反映させる実装コストが大幅に下がっている。

- **ポイント4:** マイグレーション管理において、Prisma MigrateとSupabase CLIのマイグレーション機構が競合しやすいため、どちらか一方（通常はPrisma Migrate）に一本化し、Supabase Studio側での直接スキーマ変更を禁止する運用ルールが推奨される。

- **ポイント5:** エッジ関数（Supabase Edge Functions）からPrisma経由でDBアクセスする際はPrisma AccelerateまたはData Proxyが前提となるため、コスト計算に従量課金分を事前に織り込んだ設計判断が必要。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Rust製WasmモジュールはComponent Model（WASI Preview 2）の普及により、言語間連携のオーバーヘッドがほぼゼロになりつつあり、Next.jsのエッジランタイムでも画像処理やPDF生成などCPU集約処理をWasm化する事例が増えている。
- **ポイント2:** `wasm-bindgen`と`wee_alloc`の組み合わせから、よりコンパクトなアロケータ（`wee_alloc`後継やdlmalloc最適化版）への移行が進み、バンドルサイズが数十KB単位で削減できるようになっている。
- **ポイント3:** SIMD128命令セットのブラウザ対応がほぼ完了したことで、Rust側で`std::simd`やportable-simdクレートを使った画像・動画処理が実用速度に達し、JS実装比で3〜5倍の高速化が報告されている。
- **ポイント4:** Wasmのコールドスタート時間がJITウォームアップ不要な特性から、Vercel EdgeやCloudflare WorkersでのSSR時のレイテンシ改善に有効— sumitsugiのようなSSR中心のNext.jsアプリでは、重い画像変換（住居写真の最適化など）をRust/Wasmに切り出す価値がある。
- **ポイント5:** `cargo-component`や`wasmtime`のツールチェーン成熟により、ローカル開発時のビルド時間が短縮され、TDDサイクル（RED→GREEN→IMPROVE）にWasmモジュールのテストを組み込むコストが下がっている。

### 8. Next.js App Router patterns 2026

- **ポイント1（Server Actions中心の設計）:** フォーム処理やデータ更新はAPI Routesではなく`Server Actions`に統一する流れが定着しつつある。`revalidatePath`/`revalidateTag`との組み合わせでキャッシュ無効化のロジックがシンプルになり、クライアント側のfetchコードを大幅に削減できる。

- **ポイント2（Partial Prerendering (PPR)の実用化）:** 静的シェルを即時返しつつ動的部分をストリーミングするPPRが安定し、物件一覧のような「静的な骨格＋動的な価格/在庫情報」構成のページでTTFBを大幅改善できる。sumitsugiの`properties/`ページのような検索結果表示に特に有効。

- **ポイント3（`use cache`ディレクティブによる明示的キャッシュ制御）:** fetchベースの暗黙キャッシュから、関数単位で`use cache`を宣言する明示的モデルへ移行が進んでいる。どのデータがいつ再計算されるかがコード上で追いやすくなり、キャッシュ関連の不具合（古いステータス表示など）を防ぎやすい。

- **ポイント4（Route Handlersの薄型化とRSC優先）:** クライアント状態管理が必要なUI以外は極力Server Componentsで完結させ、Route Handlersは外部webhook連携やOAuthコールバックなど本当に必要な箇所のみに限定するのがベストプラクティスとして定着。バンドルサイズと水和(hydration)コストの削減に直結する。

- **ポイント5（Turbopackのビルド高速化が標準化）:** Next.js 16ではTurbopackが本番ビルドでも既定となり、大規模コードベースでのビルド時間が大幅短縮。`bun run build`のCI実行時間短縮にも寄与するため、CIコスト削減の観点からも採用メリットが大きい。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge RuntimeとNode.js Runtimeの使い分け最適化:** 2026年現在、Vercel Edge FunctionsはV8 isolateベースで起動が数ms単位と高速だが、全てのAPIルートをEdgeに寄せるのではなく、重い処理（画像変換、DB接続プールなど）はNode.js Runtimeに残し、認証チェックやリダイレクト等の軽量ロジックのみEdgeに置く「ハイブリッド配置」が定着している。本サービスでも`src/app/api/`配下のmiddlewareレベルの処理（認証ガード等）はEdge化を検討する価値がある。

- **ポイント2: Streaming SSRとの組み合わせでTTFBを短縮:** Next.js 16のPartial Prerendering (PPR)とEdge Functionsを組み合わせることで、静的シェルを即時配信しつつ動的部分（物件詳細の在庫状況など）をストリーミングで後追い配信できる。物件一覧ページのような動的要素が多いページでTTFB改善に直結する。

- **ポイント3: リージョン配置とデータ局所性の設計:** Edge Functionsはグローバル分散実行されるが、バックエンドDB（Supabase/Postgres等）が単一リージョンの場合、Edgeからのレイテンシがむしろ増える「コールドパス問題」が起きうる。DBリージョンとEdge実行リージョンを揃える、またはRead Replicaをエッジ側に近づける設計が重要。

- **ポイント4: コスト最適化のための実行時間計測:** Vercelの課金はGB-Hours/実行時間ベースのため、Edge Function内でのawait待ち（外部API呼び出し等）が長いと逆にコスト増になるケースがある。2026年のベストプラクティスは、外部呼び出しをEdge内で直列化せず、Vercel KV/Cacheやバックグラウンドジョブ（Vercel Queue等）に委譲して実行時間を短く保つこと。

- **ポイント5: Middlewareの肥大化防止:** `middleware.ts`は全リクエストを通過するため、認証ロジックやA/Bテスト分岐が増えるとEdge側の実行コストと複雑性が線形に増加する。本プロジェクトでも認証周り（`auth-context.tsx`連携）を今後Edgeに持ち込む場合は、matcherで対象パスを絞り込み、必要最小限のロジックのみを実行する設計を徹底すべき。

### 10. TypeScript type safety patterns 2026

**TypeScript Type Safety Patterns 2026**

- **ポイント1（型推論の活用強化）:** `satisfies`演算子やconst型パラメータの利用が一般化し、明示的な型アノテーションを減らしつつ型安全性を保つパターンが定着している。Zodなどのスキーマライブラリから型を自動導出する手法（schema-first）が標準的なアプローチになっている。
- **ポイント2（ランタイム検証との統合）:** コンパイル時の型チェックだけでは不十分な境界（API入出力、環境変数）でZod/Valibotによるランタイム検証を組み合わせるのが必須パターン化。sumitsugiでも`src/lib/`のデータ層で境界検証を徹底すべき。
- **ポイント3（Discriminated Unionの活用）:** `'draft' | 'public'`のようなstatus型は、単純なUnion型よりタグ付きUnion（Discriminated Union）で分岐させることで、網羅性チェック（exhaustiveness check）がコンパイラに効くようになり、新しいステータス追加時の漏れを防げる。
- **ポイント4（テンプレートリテラル型の実用化）:** ルーティングパスやCSSクラス名（Tailwind）など文字列ベースのAPIに対し、テンプレートリテラル型で型安全な文字列結合を行うパターンが浸透。App Routerのパス定義などに応用価値が高い。
- **ポイント5（strictビルド設定のCI必須化）:** `noUncheckedIndexedAccess`や`exactOptionalPropertyTypes`などの厳格フラグをCIのビルドステップで強制する流れが強まっている。型の緩みがプロダクションバグに直結するため、`bun run build`をCIに必ず含める運用（本プロジェクトの既存ルール通り）が業界標準になってきている。
