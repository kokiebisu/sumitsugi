# CTO Knowledge - 2026-07-23

## Daily Update (2026-07-23)

### 1. Next.js performance optimization 2026

- **ポイント1: Partial Prerendering (PPR) の本格運用** Next.js 16でPPRが安定版となり、静的シェルと動的コンテンツを1つのルートで組み合わせられるようになった。初期表示は静的配信で高速化しつつ、パーソナライズ部分だけSuspenseでストリーミングする設計が標準パターンになりつつある。

- **ポイント2: React Compilerによる自動メモ化** `useMemo`/`useCallback`を手動で書かなくてもビルド時に最適化されるため、コンポーネント設計がシンプルになる一方、依存配列のバグが減り再レンダリングコストが下がる。ただしコンパイラの挙動を理解せず既存コードに闇雲に適用すると意図しない最適化漏れが起きるので、段階導入が安全。

- **ポイント3: Server ActionsとRSCペイロード最適化** データフェッチをサーバー側に寄せることでクライアントバンドルサイズを削減できるが、RSCペイロード自体が肥大化しやすいので、`cache()`やタグベースの再検証（`revalidateTag`）を使ってペイロード再生成を最小限に抑える設計が重要。

- **ポイント4: Turbopack本番ビルドの採用拡大** ビルド時間短縮により開発イテレーションだけでなくCI/CDのデプロイ速度も改善する。ただしカスタムWebpack設定に依存しているプラグイン（画像最適化・SVGローダーなど）は移行時に個別検証が必要。

- **ポイント5: Core Web Vitals計測のリアルユーザー監視強化** ラボ環境（Lighthouse）だけでなく、Vercel AnalyticsやRUM（Real User Monitoring）でINP（Interaction to Next Paint）を継続監視する体制が2026年のベストプラクティス。うちのプロダクトでも物件一覧・検索フィルタのようなインタラクション過多なUIはINP悪化しやすいため、優先的に計測対象にすべき。

### 2. React Server Components streaming 2026

- **ポイント1:** Partial PrerenderingとRSC streamingの組み合わせが標準化され、静的シェルを即座に返しつつ動的部分をストリームで後追い配信するパターンがNext.js 16でデフォルトの構成になっている。SumitsugiのようなDBクエリを伴う物件一覧ページでは、TTFBを大幅に短縮できる。

- **ポイント2:** `use cache`ディレクティブとRSCのキャッシュセマンティクスが安定し、Server Component単位で細かくキャッシュ境界を制御できるようになった。物件詳細ページなど更新頻度の低いコンポーネントと、在庫状況など頻繁に変わるコンポーネントを分離してキャッシュ戦略を最適化すべき。

- **ポイント3:** Suspenseバウンダリの粒度設計がパフォーマンスの鍵になっており、粒度が粗すぎるとウォーターフォールが発生し、細かすぎるとレイアウトシフトやネットワークオーバーヘッドが増える。物件検索・フィルタリングUIでは「重要な情報（価格・写真）を先に、レビューや関連物件を後で」というストリーミング優先順位の設計が重要。

- **ポイント4:** Client Componentとの境界(`'use client'`)を最小化し、フォームやインタラクティブ要素だけをクライアントバンドルに含める設計がベストプラクティスとして定着している。認証や決済フローなど`src/components/auth`配下のコンポーネントは特に、サーバー/クライアント境界の見直しでバンドルサイズ削減の余地がある。

- **ポイント5:** RSC streamingとエラーバウンダリの組み合わせで、一部のデータ取得が失敗してもページ全体をブロックしない「部分的な劣化」が実装しやすくなった。外部弁護士確認待ちのような段階的ローンチでも、機能ごとに独立したストリーミング境界を持たせることで、一部機能の障害が他機能に波及しないアーキテクチャを組める。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはNext.jsやフルスタックTypeScriptプロジェクトで「フロントとバックの型を分離しない」開発体験を提供し、sumitsugiのようなApp Router構成では内部API（管理画面・引き継ぎフロー等）に特に相性が良い一方、外部パートナー連携やモバイルアプリ対応にはREST/GraphQLの方が適している。

- **ポイント2:** GraphQLは複雑な関係性データ（物件・前の住人・次の住人・引越し費用見積もりなど）を1リクエストで柔軟に取得したい画面に強いが、キャッシュ戦略やN+1問題への対応コストが高く、シンプルなCRUDが中心の現フェーズでは過剰投資になりやすい。

- **ポイント3:** 2026年のトレンドとして「API境界にZodスキーマを置き、それをOpenAPI/GraphQL SDLに変換する」スキーマファースト設計が主流化しており、standards.mdの「Input validation: Zod at system boundaries」の方針とも合致するため、まずはZod+REST（or tRPC）で型安全性を担保するのが現実的。

- **ポイント4:** ベータローンチ直前のフェーズでは、API設計の複雑化よりも「型の一貫性」と「ビルド健全性」が優先事項（standards.mdのBuild Integrity方針と一致）であり、tRPCの型推論はCIでの型崩れ検出コストを下げる実利がある。

- **ポイント5:** 将来的に外部（不動産事業者・自治体等)とのB2B連携APIが必要になった場合は、内部用tRPC/GraphQLとは別に、安定したバージョニング可能なREST公開APIを分離して設計するのが2026年の一般的なベストプラクティス。

### 4. serverless edge computing 2026

**ポイント1:** WebAssembly (Wasm) ベースのエッジランタイムがコールドスタート問題をほぼ解決し、Cloudflare WorkersやDeno Deployで数ミリ秒起動が標準に。sumitsugiのような物件検索・画像処理を伴うページでは、SSRの一部をエッジに移すことでTTFBを大幅短縮できる可能性がある。

**ポイント2:** エッジでのステートフル処理（Durable Objects、Cloudflare D1、PartyKit等）が実用段階に入り、これまでオリジンサーバーに集中していたセッション管理やリアルタイム機能（チャット・通知）をエッジ側に分散できるようになった。前の住人↔次の住人間のマッチング通知のようなリアルタイム要素と相性が良い。

**ポイント3:** AI推論のエッジ実行（軽量LLM・埋め込みモデルのオンデバイス/オンエッジ実行）が普及し、検索のセマンティックマッチングや画像タグ付けをリージョン単位で低遅延に処理できるようになりつつある。ただしNext.js 16のApp Router構成では、Edge RuntimeとNode.js Runtimeの機能差（特にファイルI/OやCookie周り）に注意が必要。

**ポイント4:** マルチリージョンデプロイのコスト最適化が進み、「デフォルトでエッジ」から「必要な部分だけエッジ」への揺り戻しも見られる。全ページをエッジ化するのではなく、認証・物件検索APIなど遅延に敏感な箇所を選定して段階導入するのが2026年時点の現実的なベストプラクティス。

**ポイント5:** ベンダーロックインへの警戒感からOpenTelemetry互換の分散トレーシングやWinterCG（Web-interoperable Runtimes）準拠のランタイムが重視されており、将来的なプロバイダ変更コストを抑える設計判断が求められる。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証がデフォルトになりつつあり、フィッシング耐性のあるパスキーを主要フローに組み込むことで、認証情報漏洩リスクを構造的に排除できる。
- **ゼロトラスト前提のセッション管理:** IPアドレスやデバイスに依存しない継続的なリスク評価（Continuous Authentication）が主流化しており、トークンの有効期限を短くし、異常検知時に即座に再認証を要求する設計が求められる。
- **AIエージェント/APIアクセスの認可分離:** 人間のログインとは別に、AIエージェントや外部連携が使うトークンにはスコープを最小化したOAuth 2.1 + PKCEを徹底し、権限昇格の攻撃面を減らす必要がある。
- **多要素認証の疲労攻撃対策:** MFAプッシュ通知の「疲労攻撃」が増えているため、番号マッチングやコンテキスト表示（場所・デバイス情報）を必須化し、単純承認型のプッシュ通知は廃止すべき。
- **サプライチェーン経由の認証情報漏洩対策:** npm/依存パッケージ経由でのトークン窃取事例が増加しており、シークレットのローテーション自動化とサーバーサイドでのシークレット管理（環境変数＋Vault等）を徹底することが引き続き重要。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はSupabaseのPgBouncer（Transaction Pooling）との互換性が大幅に改善され、Edge Functions・Serverless環境でのコネクションプール枯渇問題が実質解消されている。sumitsugiのようなVercelデプロイ構成では、`DATABASE_URL`をpooling用、`DIRECT_URL`をマイグレーション用に分離する構成が事実上の標準になっている。

- **ポイント2:** SupabaseのRow Level Security(RLS)とPrismaのアプリケーション層バリデーションを二重に効かせる「Defense in Depth」設計がベストプラクティス化しており、`seller`/`buyer`のようなロール別アクセス制御は、Prismaのミドルウェアだけに頼らずDB側のRLSポリシーでも担保すべき。

- **ポイント3:** Prisma ORMのクエリ最適化機能（`prisma.$queryRaw`との併用、Preview機能の`relationJoins`）により、N+1問題を避けつつSupabaseのPostgres拡張機能（pg_trgm、PostGIS等）を直接活用できるようになった。物件検索・位置情報検索の高速化に有効。

- **ポイント4:** SupabaseのRealtime機能とPrismaのスキーマ管理を組み合わせる際は、Prismaのマイグレーション（`prisma migrate`）とSupabaseのRealtime publication設定が同期しないケースがあるため、CI/CDパイプラインにスキーマ差分チェックを組み込む必要がある。

- **ポイント5:** 2026年時点でPrisma Accelerate（マネージドコネクションプーリング＋グローバルキャッシュ）を採用するプロジェクトが増えており、ベータローンチ前のスケール準備として、物件一覧・検索系のread-heavyクエリにキャッシュ層を導入する価値が高い。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Component Model の実用化が進み、Rustで書いたWasmモジュールを言語非依存のインターフェースで組み合わせられるようになった。マイクロサービス的な粒度でWasmコンポーネントを配布・差し替えできるため、フロントエンドの重い処理（画像加工、PDF生成、暗号化）を段階的に移植しやすい。

- **ポイント2:** wasm-bindgen / wasm-pack のツールチェーンが成熟し、ビルド時間とバンドルサイズの最適化（`wasm-opt -Oz`、`wee_alloc`代替のアロケータ選定）が定石化している。Next.js 16のRSC/エッジランタイムと組み合わせる際は、サーバー側での事前実行 vs クライアント側実行の使い分けが性能のカギになる。

- **ポイント3:** WASI Preview 2 対応により、サーバーサイド（Node/Bun/Deno/エッジワーカー）でのWasm実行が標準化され、Bunのネイティブ実行速度に近いパフォーマンスが出せるケースが増えている。sumitsugiのようなBun前提のスタックでは、重い検証ロジック（画像EXIF処理、PDF生成）をRust+Wasmに切り出す選択肢が現実的になった。

- **ポイント4:** SIMD命令とマルチスレッド（`SharedArrayBuffer`前提）のサポートがブラウザ側で安定し、画像処理・検索インデックス構築などCPUバウンドな処理でネイティブの70-90%程度の性能が出るようになった。ただしCOOP/COEPヘッダー設定が必須で、既存のNext.js設定への影響を事前に検証する必要がある。

- **ポイント5:** 依然としてWasm↔JS間のマーシャリングコストがボトルネックになりやすく、小さな関数呼び出しを頻繁に行うより、まとまった処理単位（バッチ処理）でWasm側に渡す設計が推奨される。導入判断は「本当にJSのボトルネックか」をプロファイリングしてから、が鉄則。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 16では静的シェルと動的コンテンツを1つのルートで組み合わせるPPRが安定版となり、初期表示速度を犠牲にせずパーソナライズされたコンテンツを配信できる。sumitsugiの物件一覧ページでも、静的な検索UIと動的な在庫データを分離することでLCP改善が見込める。

- **Server Actions のセキュリティ強化パターン:** フォーム送信や引越し費用計算などのミューテーションをServer Actionsに寄せる流れが定着しつつあるが、認証チェックとZodバリデーションを各Actionの先頭で必須化する運用が業界標準になっている。CSRF対策も含め、`src/app`配下のActionには境界検証を徹底すべき。

- **`use cache` ディレクティブによる粒度別キャッシュ:** ルート単位ではなく関数・コンポーネント単位でキャッシュ戦略を指定できるようになり、物件データのようにセラー（前の住人）ごとに更新頻度が異なるデータに対して、フェッチ層でのキャッシュ制御が容易になった。

- **Server Componentsファーストのデータフェッチ:** クライアント側の`useEffect`によるフェッチはアンチパターンとして扱われ、認証状態を含むデータはServer Componentsから直接取得するのが2026年時点のベストプラクティス。`auth-context.tsx`のようなクライアントコンテキストは表示状態管理に限定し、データ取得責務を持たせない設計が推奨される。

- **エッジランタイムの選択的採用:** 全ルートをEdgeで動かすのではなく、レイテンシが重要な検索・地図表示機能のみをEdge Runtimeに限定する「ハイブリッド配置」が主流に。Node.js Runtimeとの使い分けを明示的にルートごとに設定するプロジェクトが増えている。

### 9. Vercel Edge Functions optimization 2026

- **エッジでのレイテンシ最適化:** Vercel Edge Functionsはユーザーに最も近いPOPで実行されるため、DBアクセスを伴う処理はEdge-compatibleなデータベース（Neon、PlanetScale、Turso等）と組み合わせ、リージョン間往復を最小化するのが2026年の定石です。

- **コールドスタート対策:** V8 isolateベースの軽量ランタイムによりコールドスタートはほぼ解消されつつあるが、依存関係バンドルサイズが1MBを超えると起動遅延が顕著になるため、`edge`ランタイム利用時は不要なライブラリのtree-shakingを徹底すべきです。

- **Streaming SSRとの相性:** Next.js 16のPartial Prerenderingと組み合わせることで、静的シェルを即座に返しつつ動的部分をEdgeでストリーミングでき、TTFBを大幅短縮できます。sumitsugiの物件詳細ページのような「静的情報＋動的な空き状況」構成に特に有効です。

- **Observabilityの強化:** Edge環境はNode.js APIが制限されるため、従来のAPMツールが使えないケースが多く、Vercelネイティブの`@vercel/otel`やWeb標準の`fetch`計装を使った分散トレーシング導入が必須になっています。

- **コスト構造の変化:** 2026年はEdge Function課金がリクエスト数＋実行時間のハイブリッド型に移行しており、重い処理をEdgeに置くとコスト増につながるため、認証チェックやリダイレクトなど軽量なロジックに限定し、重い処理はServerless/Node runtimeに残す使い分けが重要です。

### 10. TypeScript type safety patterns 2026

- **ポイント1（`satisfies`演算子の定着）:** TypeScript 4.9で導入された`satisfies`が2026年には標準的な書き方として定着し、型推論を保持しつつ型チェックも行えるため、`as const`との併用でconfig定義やAPI応答の型安全性を大幅に向上させています。

- **ポイント2（テンプレートリテラル型の実務活用）:** ルーティングパスやAPIエンドポイント、CSSクラス名などをテンプレートリテラル型で厳密に表現するパターンが普及し、文字列の「意味」をコンパイル時に検証できるようになっています。sumitsugiでも`src/app/`のルート定義に応用すれば、タイプミスによるルーティングバグを防げます。

- **ポイント3（Zodなどスキーマファーストのランタイム検証）:** 型安全性は静的解析だけでは不十分という認識が広がり、Zod/Valibotのようなライブラリでスキーマを定義し、そこから型を推論する「スキーマファースト」パターンが主流化しています。プロジェクトの標準規約にある「システム境界でのZodバリデーション」はこの潮流に沿っており、フォーム入力やAPI境界での安全性強化に直結します。

- **ポイント4（Branded Types / Nominal Typingの普及）:** `UserId`と`PropertyId`のような構造的に同じstring型でも、ブランド型（nominal typing）で区別する手法が広まり、IDの取り違えバグをコンパイル時に検出できます。物件ID・セラーID・ユーザーIDが混在するsumitsugiのようなドメインでは特に有効です。

- **ポイント5（strictモード＋noUncheckedIndexedAccessの標準化）:** `strict: true`はもはや前提で、2026年は`noUncheckedIndexedAccess`や`exactOptionalPropertyTypes`など、より厳格なコンパイラオプションを有効化するチームが増えています。配列・オブジェクトアクセス時の暗黙的な`undefined`を型システムで強制的に扱わせることで、本番環境でのランタイムエラーを未然に防げます。
