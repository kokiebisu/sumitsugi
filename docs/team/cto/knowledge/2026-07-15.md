# CTO Knowledge - 2026-07-15

## Daily Update (2026-07-15)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格採用:** Next.js 15以降で安定した PPR により、静的シェルを即座に返しつつ動的部分のみをストリーミングできるため、TTFBを維持したままパーソナライズされたコンテンツを配信できる。App Routerの`loading.tsx`と組み合わせることでLCP改善が実測しやすい。

- **React Compiler + Server Componentsの相乗効果:** React Compilerによる自動メモ化でクライアント側の再レンダリングコストが減り、Server Componentsとの組み合わせでバンドルサイズとハイドレーションコストの両方を削減できる。手動`useMemo`/`useCallback`のメンテナンスコストが不要になる点も開発速度に効く。

- **`next/image`とCache Components API:** 画像最適化に加え、`use cache`ディレクティブによる関数単位のキャッシュ制御が主流化。DB問い合わせやAPI呼び出しをコンポーネント粒度でキャッシュし、再検証タイミングを明示的に制御することでCore Web Vitalsのばらつきを抑えられる。

- **Edge RuntimeとISRのハイブリッド戦略:** 物件詳細ページのような読み取り頻度の高いページはEdge + ISRで配信し、書き込み系（お問い合わせフォームなど）はNode.js runtimeに残す使い分けが定石になっている。全ページをEdge化するとDB接続やライブラリ互換性で詰まるケースが多い。

- **Bunとの組み合わせによるビルド高速化:** `bun run build`のインストール・型チェック速度がボトルネック解消に直結しており、本プロジェクトのようにBunをランタイムに使う場合、Turbopackとの併用でローカル開発時のHMR速度がwebpack比で大幅に改善される。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPPR（Partial Prerendering）が安定版になり、静的シェルを即座に返しつつ動的部分だけをストリーミングできるため、TTFBとLCPを両立させやすくなっている。
- **ポイント2:** `use cache` ディレクティブとCache Componentsの組み合わせで、RSCペイロードのキャッシュ粒度をコンポーネント単位で制御できるようになり、過剰な再フェッチを防げる。
- **ポイント3:** Suspenseバウンダリの粒度設計がパフォーマンスの鍵になっており、粒度が粗いと滝状のウォーターフォールが起きるため、データ取得境界とUI境界を一致させる設計が重要。
- **ポイント4:** エッジランタイムでのRSCストリーミングが一般化し、Cloudflare WorkersやVercel Edgeでの部分ハイドレーションによりモバイル回線でも体感速度が向上している。
- **ポイント5:** サーバーアクションのストリーミングレスポンス（楽観的UI更新とのペアリング）が標準パターン化し、フォーム送信や引越し費用計算などの多段階フローでUXの継ぎ目が減っている。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** 2026年時点ではtRPCがTypeScriptフルスタック構成（Next.js等）における社内API/BFF層のデファクトになりつつあり、型安全性とコード生成レスの開発体験がREST/GraphQLに対する明確な優位点。ただし外部公開APIやクロス言語連携には不向きなため、内部限定で採用すべき。
- **ポイント2:** GraphQLは大規模・複数クライアント（Web/モバイル/パートナー）を持つプロダクトで依然強いが、N+1問題やキャッシュ設計の複雑さから中小規模チームでは運用コストが見合わないケースが増えている。sumitsugiのような単一Webアプリ中心の構成ではオーバーエンジニアリングになりやすい。
- **ポイント3:** RESTはシンプルさとキャッシュ戦略（CDN/HTTPキャッシュ）の扱いやすさで、決済や外部連携（弁護士確認後の外部システム連携等）が絡む境界領域では依然最有力。設計原則は「内部はtRPC、外部公開・Webhook・決済連携はREST」という使い分けが2026年のベストプラクティス。
- **ポイント4:** OpenAPI/JSON Schemaの自動生成とAIエージェントによるAPI利用（Claude Code等のツール呼び出し）が普及し、APIドキュメントの機械可読性が採用判断の新基準になっている。今後の外部パートナー連携を見据えるなら、tRPC採用部分もOpenAPI変換レイヤー（trpc-openapi等）を併設しておくと将来の柔軟性が高い。
- **ポイント5:** sumitsugiの現フェーズ（ローンチ準備・法務確認待ち）ではAPI層の大規模刷新は優先度低。今tRPCへの部分移行を検討するなら、決済・法務連携が絡まない内部管理機能（ダッシュボード等）から段階導入するのがリスクが低い。

### 4. serverless edge computing 2026

- **エッジランタイムの統一標準化:** WinterCG（WinterTC）準拠のランタイムAPIがCloudflare Workers・Vercel Edge・Deno Deployで収束し、2026年はコードの可搬性が飛躍的に向上している。移植を前提にNode.js固有APIへの依存を避けるべき。

- **推論ワークロードのエッジ移行:** 軽量LLM推論（量子化モデル、蒸留モデル）がエッジGPU/NPU上で実行可能になり、レイテンシ要件が厳しい機能（リアルタイム検索・パーソナライズ）はオリジンサーバーからエッジへ移す価値が出てきた。

- **エッジ・ネイティブなデータ層の成熟:** Cloudflare D1、Turso（libSQL）、PlanetScale Edgeなどの分散SQLiteベースDBが本番運用に耐える段階に達し、read-heavyなワークロードはリージョン跨ぎのレプリケーションでp99レイテンシを大幅短縮できる。

- **コールドスタート問題の実質解消:** V8 isolateベースの起動時間はミリ秒未満が標準となり、旧来の「サーバーレスは遅延に弱い」という懸念はエッジ環境では過去のものになりつつある。ただしVPC接続や大型依存パッケージを持つ関数は依然コールドスタートの影響を受けるため注意。

- **コスト構造の変化と過剰請求リスク:** リクエスト課金＋CPU時間課金のモデルが主流になり、非効率なポーリングやリトライロジックが直接コストに跳ね返るため、エッジ関数のプロファイリングとタイムアウト設計をリリース前に必須チェック項目に加えるべき。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証（Passkeys）が主要ブラウザ・OSで標準サポートされ、フィッシング耐性のある認証がデフォルト選択肢になっている。実装コストが下がったため、新規プロジェクトはパスワード認証を第一候補にすべきではない。

- **継続的リスクベース認証:** ログイン時点の一度きりの検証から、デバイス・位置情報・行動パターンをセッション中も継続監視するリスクベース認証へシフトしている。高リスク操作（決済・個人情報変更）でのみ追加認証を要求するステップアップ方式がUXとセキュリティを両立させる。

- **トークン管理の厳格化:** JWTの長期有効化が攻撃対象を広げるため、短命アクセストークン＋リフレッシュトークンローテーション＋失効リストの組み合わせが必須になっている。特にリフレッシュトークンの再利用検知（token reuse detection）は侵害の早期発見に直結する。

- **サプライチェーン経由の認証情報漏洩対策:** OAuth連携やサードパーティSDK経由でのトークン漏洩事例が増加しており、スコープの最小化とトークンのオーディエンス（aud）検証が重要性を増している。外部連携を追加する際は必ずスコープを絞り込む設計にすべき。

- **AIエージェント・Bot向け認証の新設計:** LLMエージェントやMCP経由の自動化アクセスが増え、人間向けセッション認証とは別に、短命かつ監査可能なマシン間認証（mTLS + 短命トークン）の設計が求められている。既存の認証基盤にエージェント用の分離レーンを持たせることが今後の設計課題になる。

### 6. database architecture Prisma Supabase 2026

- **エッジ対応とPrisma Accelerate:** Prisma 6以降はエッジランタイム（Vercel Edge, Cloudflare Workers）でのコネクションプーリングが標準化され、Supabase側のPgBouncer設定と併用することでコールドスタート時のDB接続エラーを大幅に削減できる。sumitsugiのようなNext.js 16 App Router構成では、Server Actions多用時のコネクション枯渇対策として必須になりつつある。

- **Row Level Security (RLS) とORMの二層防御:** SupabaseのRLSポリシーをDBレベルの最終防御ラインとし、Prisma Client側でもZodバリデーションと権限チェックを行う二層構造が2026年のベストプラクティス。前の住人/次の住人のような多対多の権限モデル（物件所有者・購入希望者・管理者）を持つプロダクトでは、RLSだけに頼るとクエリ最適化が難しくなるため、アプリ層での明示的な権限フィルタも併用すべき。

- **Prisma Postgres / Supabaseブランチングによる開発体験向上:** Supabaseのdatabase branching機能（PR単位でのDBスキーマ分岐）とPrismaのマイグレーションを組み合わせることで、`draft`/`public`のようなステータス変更を伴うスキーマ変更をPRごとに安全に検証できる。Git worktreeを使う開発フロー（本プロジェクトの`worktree:create`運用）と相性が良い。

- **型安全なリアルタイム機能:** SupabaseのRealtime機能をPrisma型定義と統合するパターン（`prisma-supabase-realtime`的なコード生成）が2026年に成熟し、物件のステータス変更（draft→public）や引越し費用の交渉状況をクライアントにリアルタイム反映する際、型の二重管理を避けられる。

- **パフォーマンス最適化のためのRead Replica活用:** Supabaseのread replica機能とPrismaの`readReplicas`拡張を組み合わせ、物件一覧・検索系の読み取り負荷を書き込みDBから分離するアーキテクチャが主流化。ローンチ後のトラフィック増加を見据え、早期にread/write分離を設計に組み込んでおくとスケール時の移行コストを抑えられる。

### 7. WebAssembly Rust performance 2026

- **ポイント1（Component Model普及）:** WASM Component Model と WASI Preview 2 が本格的に安定運用フェーズに入り、Rustクレートを言語非依存のコンポーネントとして配布・合成できるようになった結果、フロントエンドの重い処理（画像処理、PDF生成、暗号化など）をWASMモジュール単位で差し替え可能にする設計が主流になっている。

- **ポイント2（SIMD・マルチスレッドの標準化完了）:** WASM SIMDとスレッド（SharedArrayBuffer + Atomics）がブラウザ全体でデフォルト有効になり、Rust側は`std::simd`や`rayon`ベースの並列コードをほぼそのままWASMにコンパイルできる。数値計算・画像処理系は依然ネイティブの70〜90%程度の性能まで到達しており、うちのような不動産プラットフォームでも間取り図画像の解析処理などをクライアントサイドWASMにオフロードする選択肢が現実的になっている。

- **ポイント3（バイナリサイズとコールドスタート最適化）:** `wasm-opt`、Component Modelのモジュール分割、`wee_alloc`後継のアロケータ改善により、Rust製WASMのコールドスタートが大幅に短縮された。Cloudflare Workers等のエッジ環境でRust+WASMを使う際、初回リクエストのレイテンシがミリ秒単位に収まるケースが増え、SSR補助処理やミドルウェアをRustで書く選択が現実的な選択肢になっている。

- **ポイント4（Rustツールチェーンの成熟）:** `wasm-bindgen`と`wasm-pack`のエコシステムが安定し、TypeScript型定義の自動生成精度が向上したことで、Next.js/TypeScriptプロジェクトへの統合コストが下がった。ただしビルドパイプラインが複雑化するため、導入は「本当に計算コストが高い処理」（画像圧縮、契約書PDF生成、大量データのバリデーションなど）に限定するのが費用対効果として妥当。

- **ポイント5（デバッグ・可観測性の課題は依然残る）:** ソースマップ対応やDevTools統合は改善したものの、本番環境でのWASMエラーのスタックトレース追跡はJSに比べてまだ手間がかかる。導入する場合はSentry等でWASM専用のエラーバウンダリとログ計装を最初から設計に組み込む必要がある。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** 静的シェルと動的コンテンツを1つのレスポンスに統合するPPRが安定版となり、初期表示速度とパーソナライゼーションを両立できるようになった。sumitsugiの物件一覧ページのように「静的なレイアウト＋動的な在庫データ」という構成に特に有効。

- **Server Actions のセキュリティ強化パターンの定着:** `"use server"` 関数への直接アクセスを防ぐため、認証チェックとZodによる入力検証をServer Actionsの冒頭で必須化するパターンが業界標準になりつつある。前の住人・次の住人間の個人情報を扱う本サービスでは特に徹底すべき領域。

- **キャッシュ戦略の明示化（`use cache` ディレクティブ）:** App Routerのキャッシュ挙動が暗黙的で分かりにくかった反省から、関数・コンポーネント単位で明示的にキャッシュ範囲を指定する`use cache`が主流化。物件データの鮮度（`draft`/`public`ステータス切り替え）とキャッシュ無効化の整合性を取りやすくなる。

- **Server ComponentsとClient Componentsの境界最適化:** 「できるだけServer Componentsに寄せる」から一歩進み、インタラクティブなUIの塊（フォーム、モーダル）を意図的に小さなClient Component islandsとして切り出す設計が定石化。バンドルサイズ削減とTTIの改善に直結する。

- **Turbopackのビルド標準化とCI高速化:** Next.js 16でTurbopackが本番ビルドのデフォルトとなり、`bun run build`のCI実行時間が大幅短縮。ただし一部のwebpack依存プラグイン（画像最適化系など）で互換性の落とし穴があるため、導入前にビルド成果物の差分検証が必要。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge FunctionsのコールドスタートはV8 isolateベースの分離実行により数ミリ秒まで短縮されており、認証チェックやリダイレクトなどのミドルウェア処理をEdgeに寄せることでTTFBを大幅に削減できる。

- **ポイント2:** Edge RuntimeはNode.js APIの一部（fs、net等）が非対応のため、依存ライブラリ選定時にEdge互換性を事前検証する必要があり、重い処理はNode.js Functionsに分離するハイブリッド構成が実用的。

- **ポイント3:** リージョン近接実行（Region-aware routing）とISR/PPR（Partial Prerendering）を組み合わせることで、動的パーソナライズ部分だけをEdgeでレンダリングしつつ静的部分をCDNキャッシュで配信し、コストとレイテンシを両立できる。

- **ポイント4:** Edge Config / KVストアを使った低レイテンシなフィーチャーフラグ・A/Bテスト配信が一般化しており、ユーザー体験の出し分け（例: 物件検索のパーソナライズ）をオリジンサーバーへの往復なしに実現可能。

- **ポイント5:** 実行時間・メモリ課金モデルのためEdge Function内でのループ処理や大量データ変換はコスト増につながりやすく、重い集計処理はバックグラウンドジョブやISRの再検証タイミングに逃がす設計が推奨される。

### 10. TypeScript type safety patterns 2026

- **型推論とconst型パラメータ:** TypeScript 5.x以降の`const`型パラメータやsatisfies演算子により、明示的な型注釈を減らしつつ厳密な型推論を維持できる。設定オブジェクトやリテラル型を扱う際に特に有効。

- **Zodなどスキーマファーストのバリデーション:** ランタイム検証と型定義を一元化するパターンが主流に。APIレスポンスやフォーム入力など外部境界では、型だけでなくZodスキーマから型を`z.infer`で導出することで実行時と静的解析の乖離を防げる。

- **Branded Types / Nominal Typingの普及:** `UserId`と`PostId`のような構造的に同じstring型を誤って混用するミスを防ぐため、ブランド型パターンの採用が増えている。型エイリアスの誤用によるバグをコンパイル時に検出できる。

- **Discriminated Unionによる状態管理の厳密化:** `status: 'draft' | 'public'`のような状態を持つ型は、switch文でexhaustiveness checking（`never`型での網羅性チェック）を組み合わせることで、新しい状態追加時の考慮漏れをビルド時に検知できる。sumitsugiの物件ステータス管理にも直結する実用パターン。

- **strictな型設定の標準化:** `strict: true`に加え`noUncheckedIndexedAccess`や`exactOptionalPropertyTypes`など追加の厳格フラグを有効化するプロジェクトが増加。配列アクセスやオプショナルプロパティ由来のnullチェック漏れバグを未然に防げる。
