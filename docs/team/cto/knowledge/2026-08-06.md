# CTO Knowledge - 2026-08-06

## Daily Update (2026-08-06)

### 1. Next.js performance optimization 2026

- **ポイント1: Partial Prerendering (PPR) の本格運用** Next.js 16ではPPRが安定版となり、静的シェルと動的コンテンツを1つのルート内で共存させられる。ダッシュボードや一覧ページで「即表示される骨格＋非同期で埋まるデータ」を実現でき、TTFBとLCPを同時に改善できる。

- **ポイント2: React Server Components前提のデータフェッチ設計** クライアントへのJS転送量を減らすため、可能な限りServer Componentsでデータ取得し、インタラクティブ部分だけをClient Componentに切り出す設計が標準化しつつある。`use client`境界を最小化することが、そのままバンドルサイズ削減に直結する。

- **ポイント3: `next/image`と`next/font`の最適化を前提にしたビルド計画** 画像・フォントの遅延読み込みとセルフホスティングはCore Web Vitals（特にCLS・LCP）に大きく効くため、物件写真が多いsumitsugiのようなサービスでは必須。物件一覧・詳細ページでのレイアウトシフト対策として優先度を上げるべき。

- **ポイント4: Turbopackによるビルド・開発体験の高速化** Next.js 16でTurbopackがデフォルト化され、開発時のHMRと本番ビルド時間が大幅短縮。CI/CDのビルド時間短縮にも直結するため、`bun run build`のパフォーマンス測定を定期的に行う価値がある。

- **ポイント5: キャッシュ戦略の明示化（`use cache`ディレクティブ）** データキャッシュの挙動が暗黙的だった従来と異なり、`use cache`で明示的に制御する設計に移行が進んでいる。物件データのような更新頻度が異なるコンテンツ（公開ステータス変更は即時反映、活動歴などは緩やかにキャッシュ）に対して、粒度の細かいキャッシュ設計が可能になる。

### 2. React Server Components streaming 2026

- **ポイント1（Selective/Partial Prerendering の定着）:** Next.js 16ではPPR（Partial Prerendering）が実質標準化され、静的シェルを即座に返しつつ動的部分だけをストリーミングする設計が主流に。初期表示速度とパーソナライズ性を両立できるため、`properties/`一覧ページなど検索結果を含む画面ではSuspense境界の粒度設計が体感速度を大きく左右する。

- **ポイント2（use cache ディレクティブの普及）:** `"use cache"` によるキャッシュ制御がexperimentalから実用段階に入り、fetchベースの手動キャッシュ管理より宣言的にRSCのキャッシュ境界を切れるようになった。データ取得層（`src/lib/data.ts`）の関数単位でキャッシュ戦略を明示できるため、物件情報のような更新頻度が低いデータで採用価値が高い。

- **ポイント3（ストリーミングとエラーバウンダリの一体設計）:** Suspenseでのストリーミングが前提になったことで、`error.tsx`/`loading.tsx`の設計がUXの主戦場になっている。特に認証や決済のような多段階フローでは、部分的にストリーミングされた状態でエラーが起きた際のフォールバックUIを個別に設計しないと、ユーザーが「壊れた画面」を見るリスクがある。

- **ポイント4（Server ActionsとRSCストリーミングの相性向上）:** フォーム送信後の再検証（revalidate）がストリーミングと統合され、楽観的更新（`useOptimistic`）と組み合わせることでクライアント側の状態管理コードを大幅に削減できる。問い合わせフォームや内見予約のような多段階フォームで、クライアントJSを増やさずにリッチな体験を実装できる。

- **ポイント5（可観測性の課題）:** ストリーミングSSRはサーバー側のレイテンシがネットワークウォーターフォールとして可視化されにくく、従来のAPMツールでは各Suspense境界のTTFB/TTIを個別に追跡しにくい。本番投入前にストリーミング特有のトレーシング（例: `generateStaticParams`込みのビルド時間、境界ごとのサーバーレンダリング時間）を計測する仕組みを用意しておくべき。

### 3. API design REST GraphQL tRPC 2026

**CTO視点: API設計トレンド (REST/GraphQL/tRPC) 2026**

- **ポイント1（tRPCの台頭）:** TypeScriptフルスタック構成（Next.js等）ではtRPCがスキーマ定義・コード生成なしに型安全なAPIを実現でき、フロントとバックエンドが同一リポジトリの場合は開発速度が大幅に向上する。ただし外部公開APIやポリグロット環境では不向き。

- **ポイント2（GraphQLはBFF/集約層で継続利用）:** 複数マイクロサービスやモバイル/Web双方への最適化が必要な場合、GraphQLはoverfetch/underfetch問題を解決する強みが健在。ただしN+1問題やキャッシュ戦略の複雑さは運用コストとして残る。

- **ポイント3（RESTは依然デファクト標準）:** 外部連携・パブリックAPI・シンプルなCRUDにおいてはRESTが最もシンプルで学習コストが低く、OpenAPI仕様との親和性も高いため、住人向け外部連携（決済・弁護士確認フロー等）にはRESTが適切。

- **ポイント4（sumitsugiへの実用的示唆）:** 現状Next.js App Router + TypeScriptの構成であれば、内部の`src/app`⇔`src/lib`間のデータ取得にtRPC導入を検討する価値はあるが、MVPローンチ直前の今フェーズでは新規アーキテクチャ変更よりも既存REST/Server Actions構成の安定性を優先すべき。

- **ポイント5（型安全性の一貫性が最重要）:** どの方式を選んでも、Zodスキーマによる境界バリデーション（`.claude/rules/standards.md`の方針と一致）とエンドツーエンドの型共有が2026年のベストプラクティスの核であり、API設計方式そのものより型安全性の徹底の方が投資対効果が高い。

### 4. serverless edge computing 2026

- **エッジコンピューティングの標準化とWASM統合:** WasmEdge/WASIによりランタイムが軽量化・標準化され、CloudflareやFastlyのエッジプラットフォームでコールドスタートがミリ秒未満に短縮。sumitsugiのような予約・決済フローには、地理的に近いエッジで認証・レート制限を処理し、DBアクセスのみオリジンに逃がす構成が有効。
- **エッジDBとリードレプリカの分散:** Cloudflare D1/Durable Objects、Turso、PlanetScaleのエッジレプリカが実用段階に入り、読み取り中心の物件検索・一覧表示をユーザー近傍で処理できる。書き込み（予約確定・決済）は依然中央集権が安全で、read/writeの分離設計が重要。
- **エッジAI推論の一般化:** 画像最適化・レコメンド・不正検知などの軽量モデルをエッジで直接推論する構成が主流化。物件写真のリサイズ・NSFW判定・検索ランキングをCDN層で完結させ、オリジンサーバーの負荷とレイテンシを削減できる。
- **コスト構造の変化と従量課金の細分化:** リクエスト数・CPU時間・メモリの秒単位課金が一般化し、トラフィックが不規則なスタートアップに有利。ただしエッジ関数の乱立はオブザーバビリティを分断するため、分散トレーシング（OpenTelemetry）の導入を早期に組み込む必要がある。
- **ベンダーロックインとポータビリティのリスク:** WinterCG標準（Fetch API、Web Streams等）への準拠が進み、Vercel/Cloudflare/Deno間の移植性が向上しつつあるが、KVストアやDurable Objectsなど独自機能への依存はロックインを生む。MVP段階では標準APIに寄せた実装を優先すべき。

### 5. authentication security best practices 2026

- **ポイント1（パスキー標準化）:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の主流となっており、フィッシング耐性とUX向上を両立できるため、新規実装では最初からパスキーをプライマリな認証手段として設計すべき。
- **ポイント2（多層防御とゼロトラスト）:** 単一要素のMFAだけでなくデバイス証明・行動分析・リスクベース認証を組み合わせたアダプティブ認証が標準になっており、住人向けプラットフォームのような個人情報を扱うサービスでは、ログイン時のリスクスコアリング導入が推奨される。
- **ポイント3（トークン管理の厳格化）:** JWTなどのステートレストークンは有効期限を短く（アクセストークン15分程度）し、リフレッシュトークンのローテーション＋再利用検知（Refresh Token Rotation）を必須にする実装が業界標準になっている。
- **ポイント4（サプライチェーン・依存関係リスク）:** 認証ライブラリ（NextAuth/Auth.jsなど）自体の脆弱性やnpm依存関係経由の攻撃が増えており、定期的な依存監査（`bun audit`相当）とSBOM管理をCI/CDに組み込む必要がある。
- **ポイント5（セッション管理とログアウト設計）:** マルチデバイス利用が前提の今、「全デバイスからログアウト」機能とサーバー側でのセッション無効化（トークンブラックリスト or セッションストア方式）を最初から設計に含めることが、アカウント乗っ取り時の被害最小化に直結する。

### 6. database architecture Prisma Supabase 2026

- **エッジ最適化とコネクションプーリング:** Supabaseの`Supavisor`やPrismaの`Accelerate`によるコネクションプーリングが標準化し、Next.js 16のサーバーコンポーネント/Server Actionsからの大量の同時接続でもDB接続枯渇を防げるようになった。サーバーレス環境では必須の構成。

- **Prisma ORMのRust脱却とパフォーマンス向上:** Prisma 6以降はクエリエンジンがTypeScript/WASMベースに移行し、コールドスタートが大幅改善。Vercel等のエッジ関数でのレイテンシが課題だったが、実用レベルに達している。

- **Row Level Security (RLS) をアプリ層と併用:** SupabaseのRLSポリシーをDB側の最終防衛線として維持しつつ、Prisma側でも型安全なアクセス制御ロジックを重ねる「二重ガード」構成が主流になりつつある。個人情報（`seller`データ等）を扱う本サービスでは特に重要。

- **スキーマ変更のゼロダウンタイム運用:** Prisma Migrateの`expand-contract`パターン（旧カラム維持→新カラム追加→段階的移行→旧カラム削除）が、ステータス値のような列挙型変更（例: `'draft' | 'public'`）を伴うマイグレーションの標準手法として定着している。

- **リアルタイム機能とベクター検索の統合:** SupabaseのRealtime SubscriptionsとpgvectorによるAI検索・レコメンド機能の統合が容易になり、物件マッチングのような類似性検索ユースケースをPrisma経由でも扱いやすくなっている。

### 7. WebAssembly Rust performance 2026

## CTO視点: WebAssembly × Rust パフォーマンス 2026

- **ポイント1（Component Model成熟）:** WASM Component Modelの標準化が進み、Rustの`wit-bindgen`を使った言語横断の相互運用が実用レベルに到達。マイクロサービス的なプラグインアーキテクチャをブラウザ・サーバー双方で同一バイナリで扱えるようになり、開発効率が向上している。

- **ポイント2（SIMD・スレッド対応の一般化）:** WASM SIMDとマルチスレッド（`wasm-bindgen-rayon`等）がほぼ全モダンブラウザで安定サポートされ、画像処理・暗号化・物理演算などCPU集約的処理をネイティブの70-90%程度の速度で実行可能に。フロントエンドの重い計算処理をRust+WASMにオフロードする選択肢が現実的になった。

- **ポイント3（起動時間とバンドルサイズの最適化）:** `wasm-opt`やRustの`opt-level = "z"`設定、`wee_alloc`に代わる軽量アロケータの普及により、初回ロード時間とバイナリサイズの課題が大きく改善。特にコールドスタートが重要なエッジ環境（Cloudflare Workers等）でのWASM採用が加速している。

- **ポイント4（サーバーサイドWASI採用拡大）:** WASI Preview 2への移行が進み、RustコンパイルのWASMモジュールをサーバーレス/エッジ環境でサンドボックス実行するケースが増加。コンテナより起動が速く、セキュリティ境界も明確なため、軽量マイクロサービスの代替として検討価値がある。

- **ポイント5（開発体験の課題は依然残る）:** デバッグツールチェーン（ソースマップ、プロファイリング）はネイティブRust開発に比べまだ発展途上。導入する際はパフォーマンス要件が明確な箇所（画像処理、PDF生成、暗号化処理等）に限定し、全面採用は避けるのが現実的な判断。

### 8. Next.js App Router patterns 2026

- **ポイント1:** Partial Prerendering (PPR) が標準化され、静的シェルを即座に返しつつ動的部分をストリーミングする設計が主流に。物件一覧のような「基本レイアウトは静的・価格や空室状況は動的」なページでTTFBを大幅改善できる。
- **ポイント2:** Server ActionsとuseActionState/useOptimisticの組み合わせがフォーム処理の標準パターンとして定着。問い合わせフォームや内見予約など、API Route不要でサーバー完結の処理を書けるため、コード量とレイテンシの両方を削減できる。
- **ポイント3:** `cache: 'force-cache'`頼みの暗黙キャッシュから、`use cache`ディレクティブによる明示的キャッシュ制御への移行が進んでいる。物件データのようにDBアクセス頻度が高い箇所で、キャッシュ境界を関数単位で明示できるのは事故防止に効く。
- **ポイント4:** Route Handlers + Server Componentsの責務分離が明確化し、「データ取得はServer Component、外部Webhookや認証コールバックのみRoute Handler」という原則が広がっている。認証まわりのバグを減らす意味でも踏襲価値が高い。
- **ポイント5:** ビルド時間肥大化への対策として、Turbopackのproduction build対応が本格化し、大規模App Routerプロジェクトでのビルド高速化が実用レベルに。CIのビルド時間短縮に直結するため、`bun run build`のCI導入と合わせて検討する価値がある。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1（Edge RuntimeとNode.js Runtimeの統合が進行）:** Vercelは2025年後半からEdge RuntimeとNode.js Runtimeの機能差を縮小しており、Fluid Computeの適用範囲拡大でコールドスタートを抑えつつNode.js APIの多くがEdgeでも動くようになっている。移行時は依存ライブラリ（特にDB接続系）のEdge対応状況を先に確認すべき。

- **ポイント2（Fluid Computeによるインスタンス再利用でコスト最適化）:** 同一リージョン内でインスタンスを使い回すFluid Computeにより、リクエストごとの起動オーバーヘッドと課金が削減される。当社のような小〜中規模トラフィックのサービスでは、常時稼働のサーバーレス関数より実行時間ベースの課金が有利になるケースが多い。

- **ポイント3（Edge Configとの組み合わせで動的パーソナライゼーションを高速化）:** 物件検索や地域別表示のようなリクエスト単位の条件分岐は、Edge Config（低レイテンシKVストア）と組み合わせることでDBアクセスなしにエッジで完結できる。前の住人検索のフィルタリングロジックなど、頻繁に読むが更新頻度の低いデータに向いている。

- **ポイント4（Streaming SSR + Partial Prerenderingの相性）:** Next.js 16のPartial Prerendering（PPR）はEdge Functionsとの親和性が高く、静的シェルを即座に返しつつ動的部分（ログイン状態や物件のリアルタイム在庫）だけをストリーミングできる。物件詳細ページのようなSEO重視かつパーソナライズが必要なページに適用余地がある。

- **ポイント5（可観測性とデバッグの制約に注意）:** Edge環境は依然としてNode.js Runtimeに比べてプロファイリング・ログ収集ツールの選択肢が限定的で、Vercel純正のOTel統合はあるものの自前APM連携は工数がかかる。決済や認証など障害時の原因究明が重要な機能は、当面Node.js Runtimeに残す判断が妥当。

### 10. TypeScript type safety patterns 2026

**ポイント1:** TypeScript 5.x系で強化された`satisfies`演算子とconst型パラメータの活用が一般化し、型推論を保ちながら値の形状を検証するパターンが定着している。実際、APIレスポンスの型と実データの整合性チェックに`satisfies`を使うことで、過剰な型アサーションを排除できる。

**ポイント2:** Zodなどのスキーマバリデーションライブラリと型定義の統合（`z.infer`）が標準的なプラクティスとなり、実行時検証と静的型付けの二重管理コストを削減している。本プロジェクトでもシステム境界（フォーム入力・API境界）でのZod活用を徹底すべき。

**ポイント3:** `unknown`型を起点としたブランド型（Branded Types）やNominal Typingパターンが、IDの取り違えなど構造的類似性による誤用を防ぐ手段として浸透している。物件IDとユーザーIDのような同一プリミティブ型の混同防止に有効。

**ポイント4:** テンプレートリテラル型とMapped Typesを組み合わせたAPI型自動生成（tRPCやHono RPCなど）が、フロントエンド・バックエンド間の型共有を実現し、手動での型同期を不要にしつつある。

**ポイント5:** `strictNullChecks`や`noUncheckedIndexedAccess`など厳格なコンパイラオプションの標準化が進み、配列アクセスやオプショナルチェーンの安全性がコンパイル時に保証されるようになった。既存コードベースでも段階的に有効化を検討する価値がある。
