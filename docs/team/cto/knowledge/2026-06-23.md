# CTO Knowledge - 2026-06-23

## Daily Update (2026-06-23)

### 1. Next.js performance optimization 2026

- **App Router + Partial Prerendering (PPR):** Next.js 15/16で安定版となったPPRを使えば、静的シェルを即時配信しつつ動的部分のみストリーミングできるため、TTFBとLCPを大幅に改善できます。ダッシュボードや物件詳細ページなど、一部だけ動的なページに特に効果的です。

- **React Server Components の活用徹底:** クライアントバンドルサイズを減らすため、`use client`境界を最小限に絞り、データフェッチはサーバー側で完結させるのが基本。特に物件一覧・検索などデータ量が多いページではRSCでのフェッチがJSバンドル削減に直結します。

- **`next/image` と `next/font` の最適化設定:** AVIF/WebP自動変換、`priority`属性によるLCP画像の優先読み込み、`fetchPriority`の活用など、画像最適化は依然としてコアウェブバイタル改善の最も投資対効果が高い施策です。

- **キャッシュ戦略の明示化（`unstable_cache`/`revalidate`タグ）:** Next.js 16ではキャッシュの挙動がより明示的になったため、物件データのようにDBアクセスが絡む箇所はタグベースの再検証戦略を設計段階で決めておくと、不要な再フェッチやキャッシュミスを防げます。

- **Edge Runtimeの選択的採用:** 全てをEdgeに乗せるのではなく、認証チェックやリダイレクトなどレイテンシ感度の高い処理だけEdge Middlewareに限定し、重いDB処理はNode runtimeに残すハイブリッド構成が2026年のベストプラクティスです。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** Next.js 16ではPPR（Partial Prerendering）がデフォルト挙動に近づき、静的シェルを即時返却しつつ動的部分を`Suspense`境界でストリーミングする構成が定石化している。TTFBとLCPの両立がほぼ自動で得られる。
- **キャッシュ戦略の明示化:** `use cache`ディレクティブやセグメント単位のrevalidate設定が普及し、RSCのレンダリング結果をCDNエッジでキャッシュする構成が一般的になった。データ取得層とキャッシュ境界を意識した設計が必須スキルになっている。
- **クライアント境界の最小化:** `"use client"`を末端コンポーネントまで押し込み、フォームやインタラクションのみをクライアントに残す設計が定着。バンドルサイズ削減とハイドレーションコスト低減の効果が大きい。
- **エラーバウンダリとローディングUXの分離設計:** `error.tsx`/`loading.tsx`をルートセグメントごとに細かく配置し、ストリーミング中の部分的失敗をユーザーに見せない設計パターンが標準化している。
- **Server Actionsとの統合深化:** フォーム送信やミューテーションをServer Actions経由でストリーミングレスポンスに直結させ、楽観的UI（`useOptimistic`）と組み合わせる実装がプロダクション標準になりつつある。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** GraphQLは「型安全性とクライアント主導のデータ取得」という強みを保ちつつ、N+1問題やキャッシュ設計の複雑さがネックとなり、フロントエンドとバックエンドを同一言語（TypeScript）で書く構成ではtRPCへの移行が進んでいる。スキーマ定義とランタイム検証を一元化できる点が採用理由になりやすい。

- **ポイント2:** tRPCはモノレポ・フルスタックTypeScript構成（Next.js App Router含む）との親和性が高く、型推論だけでAPI契約を共有できるため開発速度が速い。一方、外部パートナーへのAPI公開やモバイルクライアント・他言語クライアントとの連携には弱く、社内向けAPIとパートナー向けAPIで使い分ける「ハイブリッド構成」が2026年のデファクトになっている。

- **ポイント3:** REST APIは依然として「外部公開API・Webhook・サードパーティ連携」の標準であり、OpenAPI（Swagger）からのコード生成・ドキュメント自動生成のエコシステムが成熟している。社内はtRPC、対外はREST（OpenAPI）という二層構成が現実的な選択肢。

- **ポイント4:** Server Actions（Next.js）やRSC（React Server Components）の普及により、「APIレイヤーを介さずサーバー関数を直接呼ぶ」設計が増加。tRPCやGraphQLの一部の役割をフレームワーク標準機能が代替し始めている点は要注視。

- **ポイント5:** AIエージェント・LLM連携の増加により、API設計に「構造化出力（JSON Schema）」と「ツール呼び出し可能なエンドポイント設計」が求められるようになっている。MCP（Model Context Protocol）のような標準化レイヤーがAPI設計の新しい考慮事項として浮上している。

### 4. serverless edge computing 2026

**Serverless Edge Computing 2026 — CTO視点**

- **WASMランタイムの主流化:** Cloudflare WorkersやFastly Compute@EdgeなどでWasmベースの実行環境が標準となり、コールドスタートがミリ秒未満まで短縮。Node.js互換層の成熟でNext.jsのEdge Runtimeへの移行コストも下がっている。
- **エッジでのステートフル処理:** Durable Objects（Cloudflare）やDeno KVのようなエッジネイティブなストレージプリミティブにより、従来は中央集権的DBが必要だったセッション管理やリアルタイム機能をエッジ単体で実装可能に。
- **AI推論のエッジシフト:** 軽量LLM・埋め込みモデルのエッジ実行が普及し、レコメンドや検索の前処理をユーザーに最も近いロケーションで完結させ、レイテンシとサーバーコストを同時に削減する設計が増加。
- **観測性の課題が顕在化:** エッジ分散により従来のAPM（中央集約型ログ・トレース）が機能しづらく、OpenTelemetryのエッジ対応や分散トレーシングの再設計が2026年の重要investment領域。
- **コスト構造の逆転リスク:** リクエスト課金モデルのエッジは低トラフィック時は安いが、高トラフィックではVM常駐型より高コストになるケースが報告されており、トラフィックパターンに応じたハイブリッド構成（エッジ+リージョナル）の判断が重要。

### 5. authentication security best practices 2026

- **パスキー/WebAuthnのデフォルト化:** 2026年はパスワードレス認証が標準となり、FIDO2準拠のパスキーをプライマリ認証手段とし、パスワードは復旧用フォールバックに留めるべき。これにより資格情報のフィッシング耐性が大幅に向上する。

- **トークンのライフサイクル管理:** アクセストークンは短命（5-15分）に保ち、リフレッシュトークンはローテーション+再利用検出（reuse detection）を実装する。漏洩時の被害範囲を最小化できる。

- **セッション管理のサーバーサイド検証強化:** JWTだけに依存せず、サーバー側でセッション無効化リスト（denylist）やデバイスフィンガープリンティングを併用し、即時のセッション失効を可能にする設計が重要。

- **段階的MFA（Adaptive/Risk-based Auth）:** ログイン場所・デバイス・行動パターンの異常検知に基づき、リスクが高い操作（決済・個人情報変更等）にのみ追加認証を要求することで、UXとセキュリティのバランスを取る。

- **シークレット管理の自動化:** APIキーやOAuthクライアントシークレットは環境変数管理だけでなく、Vault等のシークレットマネージャーでの自動ローテーションを前提とし、ハードコードや長期固定シークレットを排除する運用が必須。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMの型安全性とSupabaseのマネージドPostgresの組み合わせ:** Prisma SchemaでDB定義を一元管理しつつ、SupabaseのRow Level Security(RLS)をPrisma経由で扱う際はミドルウェアやRPC関数を併用するパターンが定着しており、型安全性とDB側セキュリティを両立できる。

- **Prisma Accelerate / Pgbouncerによるコネクションプーリング最適化:** サーバーレス環境（Vercel等）では同時接続数の急増がボトルネックになりやすく、Prisma AccelerateやSupabase標準のPgbouncer(Transaction mode)を組み合わせたプーリング戦略が必須になっている。

- **マイグレーション運用の二重管理問題:** Prisma MigrateとSupabase CLIのマイグレーションを併用すると履行履歴が分岐しやすいため、どちらか一方（多くの場合Prisma Migrate）を単一ソースとして運用し、Supabase側の機能（Auth/Storage/Realtime）はSQLマイグレーションとして別管理する設計が推奨される。

- **Realtime機能とORMの非対称性:** SupabaseのRealtimeサブスクリプションはPrismaのクエリ層を経由しないため、リアルタイム更新が必要な機能ではSupabase Clientを直接使う設計とPrismaを使う設計を機能単位で分離する判断が重要。

- **エッジランタイム対応の進化:** Prisma 6以降のEdge対応とSupabaseのData APIを組み合わせることで、Cloudflare Workers等のエッジ環境からも低レイテンシでDBアクセスが可能になり、Next.js App Routerのエッジレンダリングとの親和性が高まっている。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 16ではPPRが安定版となり、静的シェルと動的コンテンツを1つのルートで組み合わせられる。ダッシュボードや一覧ページで初期表示を高速化しつつ、パーソナライズ部分のみStreamingで遅延読み込みする構成が標準パターンになっている。

- **Server Actionsのキャッシュ戦略成熟:** `use cache`ディレクティブとタグベースの再検証（`revalidateTag`）が組み合わさり、Server Actions経由のミューテーション後にきめ細かいキャッシュ無効化が可能になった。物件詳細やステータス変更（draft/public切り替え）のような部分更新に有効。

- **レイアウト境界でのエラーバウンダリ設計:** `error.tsx`/`global-error.tsx`をルートグループ単位で配置し、認証エリアと公開エリアで異なるフォールバックUIを持たせる構成が定着。エラー時のUX分離がベストプラクティスとして広まっている。

- **Route Handlersの薄型化とビジネスロジック分離:** App RouterのRoute Handlers（`app/api/**/route.ts`）は薄いI/O層に留め、ロジックは`src/lib`側のサービス関数に切り出す構成が主流。テスタビリティとVitestでの単体テストカバレッジ確保がしやすくなる。

- **`searchParams`/`params`の非同期化への完全対応:** Next.js 15以降で`searchParams`と`params`がPromiseになった変更が定着し、Server Componentsでの`await`必須パターンが当たり前になった。型レベルでの一貫性チェック（Zodスキーマでのバリデーション含む）を境界に置くことで、移行時の型崩れを防ぐ運用が推奨される。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化:** Edge RuntimeはNode.js APIではなくWeb標準APIに限定することで起動を高速化しているため、`fetch`/`Request`/`Response`ベースの実装に統一し、重い依存ライブラリ（Node専用SDKなど）の混入を避けることが性能維持の鍵になる。

- **リージョン配置とデータ局所性:** Vercel Edge Functionsは実行リージョンを指定できるが、DB（Supabase等）やセッションストアと地理的に離れているとレイテンシが相殺されるため、バックエンドのリージョンに合わせた`regions`設定や、Edge Configを使ったグローバルなキー値キャッシュの活用が重要。

- **Edge ConfigとISRの併用:** 高頻度読み取り・低頻度更新のデータ（フラグ、設定値、軽量なリスティング情報）はEdge Configに置き、ページ単位の重いコンテンツはISR/Next.jsの`revalidate`で再生成する分離設計が、Edgeの実行時間制限（CPU時間ベース課金）とコストの両面で有利。

- **ストリーミングSSRとの組み合わせ:** Next.js App RouterのストリーミングRSCをEdge Functionsで動かすと、TTFBを大幅短縮できる一方、Edge Runtime非対応のNode APIを使うコンポーネントが混在するとビルド時にエラーになるため、`runtime: 'edge'`指定箇所のNode依存を事前に切り出す設計が必須。

- **可観測性の確保:** Edge環境では従来のAPMエージェントが使えないケースが多く、Vercelの`waitUntil()`やOpenTelemetry対応のログ転送を使って非同期にメトリクス・エラーを送出する構成にしないと、本番障害時の原因特定が困難になる。

### 10. TypeScript type safety patterns 2026

- **型推論ファーストの設計:** 明示的なアノテーションを最小限にし、TypeScriptの推論エンジンに型を導出させることで、変更時の型定義の不整合を防ぐ。zodやvalibotなどのスキーマライブラリで「ランタイム検証→型推論」を一体化する手法が標準化している。

- **Branded Types / Nominal Typing:** `type UserId = string & { __brand: 'UserId' }` のようなブランド型でプリミティブの誤用（例: `sellerId`と`listingId`の取り違え）をコンパイル時に検出する。本プロジェクトのような`seller`/`listing`/`property`が絡む型では特に有効。

- **`satisfies`演算子の活用:** `as const satisfies Record<Status, Config>`のように、リテラル型の保持と型チェックを同時に行うことで、`'draft' | 'public'`のようなUnion型に新しい値を追加した際の網羅漏れを早期検出できる。

- **Discriminated Unionによる状態モデリング:** if-elseのネストを避け、`{ status: 'draft' } | { status: 'public', publishedAt: Date }`のような判別可能なUnion型で「このステータスの時だけ存在するフィールド」を型レベルで保証する。

- **Type-level Testing (tsd / expect-type):** 型定義自体をテスト対象とし、関数の戻り値型やジェネリクスの推論結果が意図通りかをCI上で検証する手法が、80%カバレッジ要件のあるプロジェクトでも単体テストと並んで採用され始めている。
