# CTO Knowledge - 2026-10-08

## Daily Update (2026-10-08)

### 1. Next.js performance optimization 2026

- **ポイント1:** Next.js 16ではPartial Prerendering (PPR)が安定版となり、静的シェルを即時配信しながら動的部分だけをストリーミングできるため、ECサイトや物件一覧ページのようにパーソナライズ要素と静的コンテンツが混在するUIでTTFBを大幅に改善できる。

- **ポイント2:** Turbopackがビルド・開発両方のデフォルトバンドラーとなり、webpackと比較して大規模モノレポでのコールドビルドが数倍高速化するため、sumitsugiのようにコンポーネント数が増えてきたプロジェクトではビルド時間とCI実行コストの削減に直結する。

- **ポイント3:** `next/image`と`next/font`に加えてReact Server Components前提のデータフェッチパターン（`fetch`のリクエストメモ化とタグベースの`revalidateTag`）を徹底することで、クライアントバンドルサイズを削減しつつキャッシュ無効化を細粒度で制御でき、物件詳細ページのような頻繁に更新されるコンテンツでも不要な再レンダリングを防げる。

- **ポイント4:** Core Web Vitalsの評価指標がINP（Interaction to Next Paint）中心になったため、useEffect内の重い処理やハイドレーション時のJS実行をServer ActionsやuseTransitionでオフロードする設計が重要で、フォーム入力や検索フィルタのようなインタラクション主体のUIで特に効果が出る。

- **ポイント5:** Edge RuntimeとNode.js Runtimeの使い分けが明確化され、認証チェックやリダイレクトのような軽量ミドルウェアはEdgeに置き、DB接続やPDF生成のような重い処理はNode Runtimeに残すハイブリッド構成がベストプラクティスとなっており、レイテンシとコストのバランスを取りやすい。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPartial Pre-Rendering (PPR) が安定版となり、静的シェルを即時配信しつつ動的部分だけをストリーミングで補完する構成が標準化。初期表示（TTFB/LCP）の高速化と動的データの鮮度を両立できる。
- **ポイント2:** Server Actions + Suspense boundaryの粒度設計が重要性を増しており、1ページに大量のSuspense境界を細かく切りすぎるとウォーターフォール（直列リクエスト）が発生しやすい。データ取得の並列化（`Promise.all`やpreload pattern）を意識した設計が必須。
- **ポイント3:** RSC Payloadのキャッシュ戦略（`use cache`ディレクティブ）が実用段階に入り、物件一覧・詳細ページのような読み取り頻度の高いページでサーバー側キャッシュとストリーミングを組み合わせることで、DBアクセスを減らしつつ動的パーソナライズ（ログイン状態等）を維持できる。
- **ポイント4:** エラーバウンダリとストリーミングの組み合わせで、一部コンポーネントの失敗がページ全体をブロックしない設計が重要。sumitsugiのような物件詳細ページでは、画像・レビュー・引越し費用計算など独立したセクションごとにSuspense+Error Boundaryを分離し、部分的な障害耐性を持たせるべき。
- **ポイント5:** クライアントバンドルサイズ削減の観点で「Server Componentsをデフォルト、Client Componentsは対話が必要な葉ノードのみ」という原則が2026年も変わらず有効。認証状態やフォームなどのインタラクティブ部分を小さく切り出すことで、ストリーミングのペイロードも軽量化できる。

### 3. API design REST GraphQL tRPC 2026

- **スキーマファーストの収束:** tRPCのEnd-to-End型安全性がREST/GraphQLの「型定義とランタイムのズレ」問題を解消し、BFF層でのtRPC採用が増加。ただし外部公開APIではOpenAPI/GraphQL SDLの標準性が依然必須。
- **GraphQLの用途特化:** 汎用APIゲートウェイとしてよりも、複数クライアント（Web/Mobile/Partner）が異なるデータ粒度を要求する集約レイヤーとして使われる傾向が強まっている。N+1問題対策としてDataLoaderパターンは依然必須。
- **RESTの衰退ではなく定着:** シンプルなCRUD・Webhook・サードパーティ連携ではRESTが最適解として残り続け、「REST vs GraphQL」の対立構造は実務上ほぼ解消され、用途別併用が一般化。
- **tRPC + Next.js App Routerの親和性:** 同一TypeScriptモノレポ内（弊社のようなNext.js構成）ではtRPC + Server Actionsの組み合わせがAPI層自体を省略できるケースもあり、開発速度とバンドルサイズの両面で有利。
- **AIエージェント向けAPI設計:** LLMエージェントがAPIを直接呼び出すケースが増え、Zodスキーマ（弊社も採用済み）をそのままツール定義やMCPサーバーの入出力契約に転用する設計が2026年のベストプラクティスとして定着しつつある。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** V8 isolatesベースのランタイム(Cloudflare Workers, Vercel Edge)が主流となり、コールドスタートが1ms未満まで短縮。Next.js 16のEdge Runtimeとの統合でSSRのレイテンシを大幅削減できる。
- **データレイヤーのエッジ分散:** D1やTurso等のSQLiteベースエッジDBが普及し、読み取りをユーザー近接リージョンで処理可能に。sumitsugiのような物件検索は地理的に分散したユーザーが多いため、読み取り負荷の高い検索APIから段階的に移行する価値がある。
- **AI推論のエッジ化:** 軽量モデル(埋め込み生成、画像最適化)をエッジで実行するパターンが定着。物件写真の自動タグ付けや検索のベクトル検索をエッジで動かせば、現在のサーバーサイド処理より応答速度を改善できる可能性がある。
- **コスト構造の変化:** リクエスト課金からCPU時間課金への移行が進み、I/O待ちの多いAPIほど割安になる。認証・物件データ取得など外部I/O中心の処理はエッジ化のコストメリットが大きい。
- **Observabilityの複雑化:** エッジ分散によりトレーシングが難しくなるため、OpenTelemetry対応が前提条件になりつつある。導入する場合は分散トレーシングの仕組みを最初から組み込む必要がある。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証（WebAuthn/Passkeys）が主流になり、フィッシング耐性の高い認証がデフォルトになっている。sumitsugiのような個人情報（物件・引き継ぎ情報）を扱うサービスでは、パスキー対応で離脱率とセキュリティインシデントを同時に減らせる。

- **多層防御としてのリスクベース認証:** 固定MFAではなく、デバイス・位置情報・行動パターンを組み合わせたアダプティブ認証が標準。ログイン頻度の低い「前の住人」アカウントなど、休眠アカウントの不正利用対策として特に有効。

- **トークン管理の厳格化:** JWTやセッショントークンの短命化・ローテーション・サーバーサイド無効化リストの運用が必須。長期間有効なトークンの放置は、物件データや個人情報の漏洩リスクを直接高める。

- **サプライチェーン/依存関係の認証周り脆弱性監視:** OAuthライブラリや認証SDKのCVE監視を自動化し、Dependabot等でのパッチ適用を迅速化。認証基盤は自社実装よりマネージドIdP（Auth0, Clerk等）活用がコスト・セキュリティ両面で優位になりつつある。

- **ゼロトラスト前提のAPI保護:** 認証後も全APIリクエストで認可チェックを行う設計（BOLA対策）が重要。物件ステータス（draft/public）やユーザー権限の境界チェックを、フロントエンドだけでなくAPI層で必ず検証する必要がある。

### 6. database architecture Prisma Supabase 2026

- **接続プーリングの重要性:** Prisma + Supabaseの組み合わせではサーバーレス/Edge環境での同時接続数超過が頻発するため、SupavisorまたはPrisma Accelerateによるコネクションプーリングが2026年時点で事実上の標準構成となっている。直接接続文字列ではなくプール済みURLを使うことで本番障害を回避できる。

- **RLS（Row Level Security）との責務分離:** PrismaはSupabaseのRLSポリシーを直接解釈できないため、認可ロジックをDB側（RLS）とアプリ側（Prismaクエリ）のどちらに置くか明確に切り分ける必要がある。実用的には「公開読み取りはRLSで保護、書き込みはPrisma+サーバー側検証」というハイブリッド構成が多い。

- **スキーマ管理の一元化:** Prisma MigrateとSupabase CLIのマイグレーションを混在させるとスキーマのズレが発生しやすい。どちらか一方を「真実の源」として固定し、もう一方はそれに追従する運用ルールをCLAUDE.mdレベルで明文化すべき。

- **pgvector/AI機能への対応:** Supabaseのネイティブpgvectorサポートが成熟し、レコメンドや検索（例: 物件マッチング）にベクトル検索を組み込む事例が増加。PrismaはpgvectorカラムをUnsupported型として扱うため、該当クエリは`$queryRaw`での記述が必要になる点は事前に認識しておくべき制約。

- **ブランチング開発フローの定着:** Supabaseのデータベースブランチ機能とPrisma Migrateを組み合わせ、PRごとに独立したDB環境でマイグレーションを検証するCI/CDパターンが一般化している。sumitsugiのような小〜中規模チームでも、本番スキーマ破壊のリスクを下げる低コストな導入として有効。

### 7. WebAssembly Rust performance 2026

- **ポイント1: コンポーネントモデルの成熟** WASI Preview 2とComponent Modelの標準化が進み、Rust製WASMモジュール間の相互運用性が大幅に向上。マイクロサービス的な粒度でWASMコンポーネントを組み合わせる設計がプロダクションで実用的になっている。

- **ポイント2: SIMD・マルチスレッドの本格活用** `wasm32-wasip2`ターゲットとSIMD128命令セットの対応により、画像処理や暗号計算などCPU負荷の高い処理でネイティブの70-90%程度の性能に到達。Rustの`std::simd`やthreadsプロポーザルとの組み合わせで、フロントエンドでの重い計算をサーバーにオフロードせず完結できる。

- **ポイント3: コールドスタート最適化がエッジ実行の鍵** WasmtimeやWasmerのAOTコンパイル・component precompilationにより起動時間がミリ秒単位に短縮。サーバーレス/エッジ関数でRust+WASMを使う場合、初回リクエストのレイテンシが実用上の判断基準になる。

- **ポイント4: バイナリサイズとツリーシェイキング** `wasm-opt`やRustの`panic = "abort"`設定、`wee_alloc`代替としての軽量アロケータ採用で、配布バイナリを数十KB〜数百KBに抑制可能。引き継ぎプラットフォームのような一般ユーザー向けWebアプリでは、初回ロード体感速度に直結するため優先度が高い。

- **ポイント5: ツールチェーンの安定化によるリスク低減** `cargo component`やtrunk、wasm-bindgenのエコシステムが2026年時点で十分枯れており、新規導入時の「実験的技術」リスクは大きく下がった。ただし現行のsumitsugiはNext.js/TypeScriptスタックなので、WASM導入は「将来、地図描画や画像処理など特定ボトルネックが発生した際のオプション」として位置づけるのが妥当。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR)の標準化:** Next.js 16ではPPRが安定版として扱われ、静的シェルと動的コンテンツを同一ルートで組み合わせられる。ダッシュボードや物件詳細ページのように「ヘッダーは静的・在庫情報は動的」という構成に最適で、初期表示速度(TTFB)を大きく改善できる。

- **`use cache` ディレクティブによる明示的キャッシュ制御:** これまで曖昧だったApp RouterのキャッシュモデルがNext.js 15以降`use cache`で明示化され、Server Component/関数単位で「何をキャッシュするか」をコードで宣言できる。`fetch`の暗黙キャッシュに依存する実装は徐々に非推奨方向なので、`src/lib/data.ts`のようなデータ取得層は早めに移行を検討すべき。

- **Server Actionsのセキュリティ強化が必須:** Server Actionsは2026年時点でCSRF対策・認可チェックが組み込みでは不十分なケースが多く、`"use server"`関数内で必ずセッション検証を行う必要がある。物件公開/非公開(`draft`/`public`)切り替えのような権限付き操作は、Server Action内で前の住人本人かどうかのチェックを徹底すること。

- **`<Activity>` / 部分ハイドレーションによるクライアントJS削減:** React 19.2以降の`<Activity>`やSuspense境界の細分化により、インタラクティブ領域を最小限に絞れる。物件一覧のような大半が静的なページでは、フィルターUIなど本当に必要な部分だけをClient Componentにする設計がバンドルサイズ削減に直結する。

- **Turbopackがビルドのデフォルト化:** Next.js 16でTurbopackが本番ビルドでも既定となり、Webpack比で大幅な高速化が見込める一方、一部のカスタムWebpack設定やloaderは移行が必要。`bun run build`のCI実行時間短縮にも効くため、移行コストと得られる速度向上を早期に検証する価値がある。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの制約と進化:** Node.js APIの一部がEdge Runtimeでも利用可能になりつつあるが、依然としてWeb標準API中心のため、重い処理はNode.js Functionsに委譲し、Edgeは認証チェックやリダイレクト、A/Bテストなど軽量なリクエスト処理に限定するのが2026年のベストプラクティス。
- **Cold Start最小化とISR連携:** Edge Functionsは起動が速いが、グローバル分散配置を活かすにはISR（Incremental Static Regeneration）やData Cache戦略と組み合わせ、動的パーソナライゼーションを静的レンダリングの上に薄いレイヤーとして載せる設計が主流。
- **Streaming SSRとの統合:** React ServerコンポーネントのストリーミングとEdge Functionsを組み合わせることで、TTFB（Time to First Byte）を大幅短縮できる。sumitsugiのような物件一覧・検索ページでは、検索フィルタ処理をEdgeで行い結果をストリーミング返却する構成が有効。
- **コスト最適化:** Edge Functionsは実行時間課金が細かいため、不要なミドルウェア多重適用（middleware.tsでの重複処理）を避け、matcherで対象パスを絞ることがコスト・パフォーマンス両面で重要。
- **Observability強化:** 2026年はVercelのEdge Observability（リクエストトレーシング・リージョン別レイテンシ可視化）が標準装備されつつあり、本番導入前にリージョン別パフォーマンスを検証する運用が推奨される。

### 10. TypeScript type safety patterns 2026

**CTO視点: TypeScript Type Safety Patterns 2026**

- **ポイント1（型述語とブランド型の標準化）:** `type UserId = string & { readonly __brand: 'UserId' }` のようなブランド型が、IDや金額などのプリミティブ混同バグを防ぐ標準パターンとして定着。Zodの`.brand()`との組み合わせで実装コストが大幅に下がった。
- **ポイント2（Zodなどのスキーマ駆動型推論）:** `z.infer<typeof schema>` でランタイム検証と型定義を一元化するパターンが主流に。本プロジェクトのようにAPI境界でのバリデーションが必須な場合、スキーマを単一のソースオブトゥルースにすることで型とバリデーションのズレを根本的に排除できる。
- **ポイント3（Discriminated UnionによるStateの排他的表現）:** `status: 'draft' | 'public'` のようなUnion型は、switch文の`satisfies`チェックやexhaustiveness checkingと組み合わせることで、新しいステータス追加時の漏れをコンパイル時に検出できる。CLAUDE.mdにもある「型変更時は全使用箇所をgrep」の運用を補完する仕組みとして有効。
- **ポイント4（`satisfies`演算子の普及）:** TS 4.9以降の`satisfies`を使い、型推論を狭めずに型チェックだけ行うパターンが、設定オブジェクトやconstマップの定義で一般化。`as const satisfies Config`のような組み合わせがベストプラクティス化している。
- **ポイント5（strictな型境界とtRPC/OpenAPI連携）:** フロントエンド・バックエンド間の型共有を、手書きの型定義ではなくtRPCやOpenAPIコード生成で自動化する流れが加速。Next.js App Router構成では、Server Actions自体が型安全な境界として機能するため、追加のAPI層を薄く保つ設計が重視されている。
