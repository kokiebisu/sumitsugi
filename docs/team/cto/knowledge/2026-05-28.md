# CTO Knowledge - 2026-05-28

## Daily Update (2026-05-28)

### 1. Next.js performance optimization 2026

- **App Router + React Server Components の徹底活用:** RSCによりクライアントバンドルサイズを大幅削減できる。データフェッチをサーバー側に集約し、`"use client"`は本当に必要な箇所のみに限定する。

- **Partial Prerendering (PPR) の本番投入:** 静的シェルと動的コンテンツを単一リクエストで配信するPPRが安定化。`next.config`で`ppr: true`を有効にするだけで、ISRとSSRのいいとこ取りが可能になる。

- **Turbopack の採用加速:** Next.js 15以降、Turbopackがデフォルトのdev bundlerに。ビルド時間が従来比最大70%短縮され、大規模コードベースでの開発体験が劇的に改善される。

- **`<Image>`と`next/font`による Core Web Vitals 最適化:** LCPとCLSはランキング要因として依然重要。`sizes`プロップの適切な設定と、フォントのsubset指定によるFONT LOADINGの排除を徹底する。

- **Server Actions + キャッシュ戦略の精緻化:** `use cache`ディレクティブ（Next.js 15+）によりコンポーネント・関数レベルのキャッシュが宣言的に書ける。`revalidateTag`と組み合わせることで、過剰なfull-route revalidationを避けたきめ細かいキャッシュ無効化が実現できる。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度設計が鍵:** RSCストリーミングは`<Suspense>`境界の配置次第でTTFBとLCPが大きく変わる。データフェッチの依存関係を分析し、独立したウォーターフォールを並列化するよう境界を細かく設計するのがベストプラクティス。

- **PPR（Partial Pre-Rendering）の本格普及:** Next.js 15以降でPPRが安定化し、静的シェル+動的ストリームのハイブリッドモデルが主流になりつつある。CDNキャッシュとストリーミングを両立できるため、パフォーマンスとパーソナライゼーションのトレードオフが解消された。

- **`use cache`ディレクティブによる細粒度キャッシュ:** 2025〜2026年にかけてNext.jsが導入した`use cache`により、コンポーネント単位・関数単位でキャッシュ戦略を宣言できる。従来のISRより柔軟で、ストリーミングと組み合わせることでサーバー負荷を大幅に削減できる。

- **Server Actionsとの統合によるUX向上:** フォーム送信後の楽観的更新（`useOptimistic`）とServer Actionsを組み合わせることで、ネットワーク遅延を感じさせないインタラクションが実現できる。RSCのストリーミング再レンダリングと連携させると、部分的なUI更新がシームレスになる。

- **エラー境界とローディング状態の設計標準化:** `error.tsx`と`loading.tsx`の階層設計がチーム内で標準化されていないと、ストリーミング時のUXが不安定になる。ルートセグメントごとにエラー・ローディング境界を明示的に定義し、ユーザーに常に意味のあるフィードバックを返す設計を徹底すべき。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタックType Safety:** 2026年時点でtRPCはNext.js/Remixエコシステムで標準的な選択肢となり、クライアント・サーバー間のスキーマ共有によりAPIコントラクトの不整合が根絶された。特にモノレポ構成では型安全なRPCが開発速度を大幅に向上させる。

- **GraphQLの選択的採用:** GraphQLはBFF（Backend for Frontend）パターンや複雑なデータグラフを持つサービス（ECサイト、SNS）では依然有力だが、単純なCRUDにはオーバーエンジニアリングとみなされるようになった。Relay/Apollo Clientの成熟でキャッシュ戦略が洗練されている。

- **REST + OpenAPI 3.1の再評価:** Zodベースのスキーマ生成（`zod-openapi`、`@hono/zod-openapi`）により、RESTでもtRPC同等の型安全性が実現可能になった。外部向けパブリックAPIでは依然RESTが標準であり、SDK自動生成との相性も良い。

- **Honoの躍進とEdge-first設計:** HonoはCloudflare Workers/Vercel Edgeで動作する軽量フレームワークとして急速に普及し、型安全なルーティングとOpenAPI統合を両立。レイテンシ要件が厳しいAPIのEdgeデプロイが現実的な選択肢になった。

- **プロトコル選択の実用的指針:** 内部マイクロサービス間→tRPC or gRPC、フロントエンド専用BFF→tRPC or GraphQL、外部公開API→REST+OpenAPI、リアルタイム要件→WebSocket over tRPC subscriptions、というように用途別の使い分けが2026年のベストプラクティスとして定着している。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジの標準ランタイムへ:** Cloudflare Workers・Fastly Compute@Edgeなどが本格的にWasmを採用し、言語非依存でコールドスタートほぼゼロのエッジ実行環境が当たり前になった。Node.js互換レイヤーも整備され移行コストが激減。

- **AI推論のエッジオフロード加速:** LLMの軽量蒸留モデル（1B〜7Bクラス）がエッジで動作可能になり、レイテンシ削減とデータ主権確保を両立できる構成が現実的な選択肢となった。RAGのベクトル検索もエッジDBと組み合わせて分散化が進んでいる。

- **SQLite-on-Edge の台頭:** Cloudflare D1・Turso（libSQL）などが普及し、エッジでもリレーショナルDBを持てるようになった。グローバルレプリケーションと結果整合性のトレードオフを意識した設計が必須。

- **エッジ〜オリジン間のオーケストレーション複雑化:** ビジネスロジックの分散配置が進んだ結果、エッジ関数・オリジンAPI・CDNキャッシュ間のデバッグ・トレーシングが困難になっている。OpenTelemetryの分散トレースをエッジまで通すことがもはや必須の運用基盤。

- **コスト最適化の再評価:** リクエスト数課金モデルでトラフィックが多いサービスはオリジン集約の方が安価なケースも出てきた。エッジへの盲目的なオフロードではなく、レイテンシ要件・データ局所性・コストの三角形で判断する設計思想が成熟しつつある。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** FIDO2/WebAuthnベースのパスキーがパスワード認証を実質的に置き換えつつあり、フィッシング耐性と利便性を両立できるため、新規サービスはパスワードレス設計を標準とすべき。

- **トークンバインディングとDPoP の標準化:** OAuth 2.0のDPoP（Demonstrating Proof of Possession）が広く採用され、Bearer トークンの窃取リスクを大幅に低減。API認証設計では DPoP を必須と見なすべき時代に入った。

- **継続的認証（Continuous Authentication）の台頭:** ログイン時の一度きりの認証から、セッション中の行動パターン・デバイス状態を継続監視するゼロトラスト型認証へシフト。異常検知と組み合わせることで内部不正リスクも軽減できる。

- **AIを活用したクレデンシャルスタッフィング対策:** 漏洩パスワードリストを用いた自動攻撃が高度化しており、従来のレートリミットだけでは不十分。行動バイオメトリクスやデバイスフィンガープリントとAI異常検知の組み合わせが実用段階に入っている。

- **サプライチェーン経由の認証ライブラリ汚染リスク:** npm/PyPI等の依存パッケージへの悪意ある改ざんによる認証バイパスが増加。`package-lock.json`のインテグリティ検証とSBOM（ソフトウェア部品表）管理を CI/CD に組み込むことが実質的な必須要件になっている。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のEdge Runtime対応成熟:** Prisma AccelerateによるConnection Poolingがエッジ環境で安定稼働し、Supabase + Vercel Edge Functionsの組み合わせでコールドスタートを最小化できる。Next.js App RouterのServer Actionsとの親和性が高く、型安全なDB操作がフルスタックで実現できる。

- **Supabase の Row Level Security (RLS) 設計がボトルネックに:** RLSポリシーが複雑化するとクエリプランが劣化するため、`auth.uid()`を使ったポリシーはインデックスと組み合わせて設計することが必須。PrismaからRLSを活用する場合は`SET LOCAL role`でサービスロールと匿名ロールを適切に切り替える必要がある。

- **Supabase Realtime v2 + Prisma の組み合わせ戦略:** RealtimeのBroadcast/Presenceチャンネルはビジネスロジック外で扱い、PrismaはCQRSパターンのWrite側に専念させる構成が2026年のベストプラクティス。Read側はSupabaseクライアントのリアルタイムサブスクリプションで補完する。

- **pgvectorによるAI統合がデフォルト化:** Supabaseはpgvectorをネイティブサポートしており、RAG（Retrieval-Augmented Generation）アーキテクチャをPrismaスキーマに`Unsupported("vector")`型として組み込むパターンが普及。専用ベクターDBを別途持たずにPostgres一本化する設計が主流になりつつある。

- **マイグレーション戦略の二重管理リスク:** Prisma MigrationsとSupabase Migrationsが競合するケースが増えており、`supabase db push`とPrismaの`migrate deploy`を混用するとdrift（スキーマ乖離）が生じる。CI/CDでは`prisma migrate diff`を使ったdrift検出ステップを必ずパイプラインに組み込むべき。

### 7. WebAssembly Rust performance 2026

- **Component Modelの成熟:** WASI 0.2/Component Modelが本番利用に耐えられるレベルに達し、RustのWASMコンポーネントをブラウザ・サーバー・エッジで再利用可能なバイナリとして配布できるようになった。

- **SIMD・マルチスレッドの実用化:** WebAssembly SIMDとShared Memoryが主要ブラウザで安定化し、Rustの`rayon`相当の並列処理をWASM上で実現できるユースケース（画像処理・音声・ML推論）が増加している。

- **バイナリサイズ問題の改善:** `wasm-opt`（Binaryen）や`twiggy`によるサイズ分析、`wee_alloc`代替の新アロケータにより、Rustの典型的なWASMバイナリが300-500KB台に収まるケースが増え、初回ロードのボトルネックが緩和された。

- **Wasmtime/WASMEdgeの高速化:** サーバーサイドランタイムのJITコンパイル最適化が進み、ネイティブ比90%以上の実行速度が実測できるワークロードが増加。Cloudflare WorkersやFastly Compute@Edgeでの採用が加速している。

- **RustツールチェーンのWASM対応強化:** `cargo-component`が公式ツールに近い位置づけとなり、`wasm-bindgen`の型生成精度も向上。RustをWASM開発の第一言語として選択するチームが増えており、C++比でデバッグコストが大幅に下がっている。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの設計:** 2026年時点でApp Routerの成熟により、デフォルトでServer Componentsを使い、`'use client'`は状態・インタラクションが必要な最小単位にのみ付与するパターンが定着。バンドルサイズとTTIの大幅削減に直結する。

- **Partial Prerendering（PPR）の本格活用:** 静的シェルと動的ストリームを同一ルートで共存させるPPRが安定版となり、Suspense境界の設計がアーキテクチャの中核。`fallback`UIの粒度がUXに直接影響するため、ローディング設計を先に決める。

- **Server Actions によるAPI層の簡略化:** フォーム・mutation処理をServer Actionsに集約することで、従来の`/api/*`ルートハンドラが不要になるケースが増加。ただしZodによる入力バリデーションとCSRF対策は必須（Server Actionsはデフォルトで保護されるが過信は禁物）。

- **`cache()`と`unstable_cache`の使い分け:** リクエスト内メモ化には`cache()`、クロスリクエストのKVキャッシュには`unstable_cache`（`revalidateTag`付き）を使う二層構造が標準パターン。キャッシュ設計のミスがスケール時の致命的ボトルネックになる。

- **Turbopackによるビルド高速化の恩恵:** Next.js 16でTurbopackがデフォルトになりHMRが大幅高速化。ただしカスタムwebpack設定との互換性に注意が必要で、移行前に`bun run build`での動作確認を徹底すること（本プロジェクトも同様）。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの制約を理解した設計:** Edge FunctionsはNode.js APIの完全サポートがなく（`fs`、`net`等不可）、Cold Startを最小化するためバンドルサイズを50KB以下に抑えることが2026年でも基本原則。`next/server`の`NextRequest`/`NextResponse`を活用し、不要な依存を排除する。

- **Fluid Compute移行による実行モデルの変化:** VercelはEdge FunctionsとServerless Functionsの境界を「Fluid Compute」で再定義しており、リージョン選択とconcurrency設定の最適化が従来より重要。単純なJWT検証・A/Bテスト・地理ルーティングはEdge、DB接続が必要な処理はFluid Serverlessへ明確に分離する。

- **Middleware最適化でのマッチャー活用:** `middleware.ts`の`matcher`設定を精緻化し、静的アセット（`_next/static`、`favicon.ico`等）をスキップすることで不要なEdge実行を削減。全リクエストにMiddlewareを適用するアンチパターンはP99レイテンシに直結する。

- **Edge KV・Cache APIとの組み合わせ:** Vercel KV（Upstash Redis）やEdge Config（読み取り専用低レイテンシストア）を活用し、Edge Functions内でのDB直接クエリを回避するアーキテクチャが主流。特にフィーチャーフラグやルーティングルールはEdge Configが最適解。

- **監視とコスト管理:** Edge Function Invocations単価はServerlessより低いが、グローバルレプリケーションによる実行回数増加でコストが跳ね上がるケースがある。Vercel Analyticsの`Edge Function Duration`メトリクスを常時監視し、異常なロングテールを早期検出する体制が必須。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の`satisfies`は型推論を保ちながら型チェックを強制できるため、オブジェクトリテラルの過剰な型アサーション（`as`）を排除し、ランタイムエラーを大幅に削減できる。

- **`branded types`によるプリミティブの安全化:** `type UserId = string & { _brand: 'UserId' }`パターンで意味的に異なるstring/numberを型レベルで区別し、関数引数の取り違えをコンパイル時に検出する運用が標準化しつつある。

- **`const type parameters`（TypeScript 5.0+）の定着:** `function fn<const T>(arg: T)`によりリテラル型推論が自動化され、`as const`の明示的な指定なしにタプルや文字列リテラルの型精度が向上する。

- **Zodによるランタイム境界の型統合:** API境界・環境変数・フォーム入力は`z.infer<typeof schema>`でZodスキーマから型を導出し、ランタイム検証と静的型を単一ソースで管理するのが2026年のデファクト。

- **`noUncheckedIndexedAccess`の必須化:** `tsconfig.json`でこのフラグを有効にすることで配列・オブジェクトのインデックスアクセスが`T | undefined`になり、未チェックアクセスによるクラッシュをコンパイル時に強制排除できる。新規プロジェクトでは有効化を前提とすべき。
