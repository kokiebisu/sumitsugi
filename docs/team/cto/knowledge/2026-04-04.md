# CTO Knowledge - 2026-04-04

## Daily Update (2026-04-04)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを劇的に削減できる。`'use client'`境界を最小化し、データフェッチはサーバー側で完結させることが2026年の標準プラクティス。

- **Partial Prerendering (PPR) の本番導入:** 静的シェルと動的コンテンツを同一ルートで混在させる PPR が安定版へ。`next.config` で `ppr: true` を有効化するだけで TTFB と LCP を同時改善できる。

- **`@next/bundle-analyzer` + Tree Shaking の継続監視:** `shadcn/ui` や大型ライブラリのバレルエクスポートが依然としてバンドル肥大の主因。CI パイプラインにバンドルサイズチェックを組み込み、リグレッションを自動検知する。

- **Image / Font 最適化の自動化:** `next/image` の `sizes` 属性と `next/font` のサブセット指定を徹底するだけで CLS スコアが大幅改善。特にモバイル向け `srcset` 生成は App Router と組み合わせると設定ゼロで機能する。

- **Edge Runtime とキャッシュ戦略の再設計:** `fetch` の `revalidate` / `tags` ベースのオンデマンドキャッシュ無効化を活用し、CDN エッジでのキャッシュヒット率を最大化する。データの鮮度要件ごとにキャッシュ境界を明示設計することが運用安定性のカギ。

### 2. React Server Components streaming 2026

- **Suspense境界の戦略的配置が鍵:** RSCのストリーミングでは、Suspense境界をコンポーネントツリーのどこに置くかがTTFB（最初のバイト到達時間）とTTI（操作可能時間）に直結する。データフェッチが遅いコンポーネントは積極的にSuspenseで囲い、クリティカルパスをブロックしない設計が必須。

- **PPR（Partial Prerendering）との組み合わせが主流化:** Next.js 15以降、静的シェルを即時配信しつつ動的部分をストリームする PPR が実用段階に入った。「全ページ静的か動的か」の二択から脱却し、コンポーネント単位での最適化が可能になっている。

- **サーバーアクションとのデータ整合性に注意:** ストリーミング中にServer Actionが実行されると、部分的にレンダリング済みのUIとサーバー状態がずれるケースがある。`revalidatePath` / `revalidateTag` の粒度設計と、楽観的UI更新のロールバック戦略を事前に決めておくべき。

- **エッジランタイムでのNode.js APIの制約:** Cloudflare WorkersやVercel Edgeでストリーミングを活かすには、`fs`・`crypto`など一部のNode.js APIが使えない点を意識する必要がある。重いロジックはオリジンサーバーに残し、エッジはキャッシュ層として割り切る設計が現実的。

- **DevToolsとObservabilityがまだ未成熟:** ストリーミングレスポンスのどのチャンクがボトルネックかを可視化するツールが2026年時点でも発展途上。OpenTelemetryのServer Componentsトレーシング対応を自前で整備するか、Vercel Analyticsなどプラットフォーム依存の計測に頼る判断が必要。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** Next.js/Remixとの親和性から、tRPCがスタートアップや小〜中規模チームで急速に採用が進んでいる。TypeScriptのend-to-end型安全性により、スキーマ定義の二重管理が不要になり開発速度が大幅に向上する。

- **GraphQLの選択基準の明確化:** 複数クライアント（Web/Mobile/サードパーティ）が異なるデータ要件を持つ場合のみGraphQLが真価を発揮する。単一フロントエンドのプロジェクトにGraphQLを採用するのはオーバーエンジニアリングであり、REST+tRPCで十分なケースが多い。

- **REST APIは死んでいない、むしろ進化:** OpenAPI 3.1とZodの組み合わせにより、RESTでも型安全なスキーマファーストな開発が実現できる。外部公開APIや他社との連携では、依然としてRESTが最も相互運用性が高い。

- **Server Actions / RSCによるAPI層の再考:** Next.js 15以降、React Server ComponentsとServer Actionsの普及により「APIエンドポイントを作らない」設計パターンが現実的になった。内部通信においてHTTPオーバーヘッドを排除できるため、パフォーマンスとDXの両面で有利。

- **APIゲートウェイとBFF（Backend for Frontend）の標準化:** マイクロサービス環境では、クライアント別にBFFを置いてGraphQL集約 or tRPC経由で統一するパターンが定着しつつある。認証・レート制限・キャッシュをゲートウェイに集約することでサービス間の責務分離が明確になる。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジのデファクトランタイムに:** V8/Node.jsベースのコールドスタート問題をWasmが根本解決し、Cloudflare Workers・Fastly Compute等でサブミリ秒起動が標準化。コンテナ移行コストなしに任意言語をエッジで実行可能になった。

- **エッジDBとデータローカリティの成熟:** Cloudflare D1・Turso・Neon Branchingなどがエッジ近傍にSQLiteレプリカを分散配置し、「エッジで書けるがデータが遠い」問題を解消。アーキテクチャ設計の重心がCDN層からデータ層に移った。

- **AI推論のエッジオフロード加速:** LLMの軽量モデル（1B〜7Bクラス）をエッジで動かすユースケースが急増。レイテンシ・プライバシー・コストのトリレンマをエッジ推論が部分的に解決し始めている。

- **オブザーバビリティの空白が最大のボトルネック:** 分散エッジ環境ではトレースが断片化し、従来のAPMツールが機能しない。OpenTelemetryのエッジ対応とTail Samplingの設計が2026年の実運用上の最重要課題。

- **ベンダーロックインリスクの再評価:** WinterCGによるWASI/Service Worker APIの標準化が進むも、各プラットフォームの独自拡張（Bindings等）への依存が深まる矛盾が続く。抽象レイヤー（Hono、Nitro等）の採用でポータビリティを確保する設計判断が重要。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）への移行加速:** パスワードレス認証が業界標準となりつつあり、フィッシング耐性とUX向上を両立できる。既存システムでも段階的移行が現実的になっている。

- **セッション管理の短命化:** アクセストークンの有効期限を15分以内に絞り、リフレッシュトークンをローテーションする設計が主流。トークン漏洩時の被害範囲を最小化できる。

- **デバイスフィンガープリントと行動分析の組み合わせ:** IPアドレスだけでなく、デバイス特性・操作パターンを継続的に検証するリスクベース認証が普及。正規ユーザーへの摩擦を減らしながら異常検知精度を高められる。

- **OAuth 2.0 / OIDCの実装ミスへの警戒:** `state`パラメータ未検証やオープンリダイレクト脆弱性など古典的な実装バグが依然として多発。サードパーティライブラリに依存するだけでなく、実装レビューを必須化すべき。

- **AIを悪用した認証突破への対策:** LLMを使ったリアルタイム音声クローンやディープフェイクによるKYC迂回が現実の脅威となっている。生体認証単独への過信を避け、複数要素の組み合わせと人間によるレビューフローを維持することが重要。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応が実用段階に:** Prisma 6ではEdge-compatible driverが安定し、Vercel Edge FunctionsやCloudflare WorkersからSupabaseへ直接接続できるようになった。Cold startの影響を最小化しつつ、グローバル分散アーキテクチャが現実的な選択肢となっている。

- **Supabase pgvectorとRAGアーキテクチャの統合:** pgvector拡張の成熟により、Supabaseをベクターストアとして活用するRAGパイプラインが増加。PostgreSQLのACIDトランザクションとベクター検索を同一DBで扱える点がRedis+外部VectorDBより運用コストを下げる。

- **Row Level Security（RLS）をORMレイヤーで扱う複雑性:** PrismaはRLSをネイティブサポートしていないため、Supabaseのマルチテナント設計ではDrizzle ORMへの移行や、Prisma + `set_config`による`auth.uid()`伝達の実装が必要になるケースが増えている。スタック選定時に要注意。

- **Supabase Branching + CI/CDがDX変革:** 2025年GAとなったSupabase Branchingにより、PRごとに独立したDBインスタンスを自動生成できる。マイグレーションのテストが本番同等環境で行えるため、スキーマ変更のリスクが大幅に低減。

- **接続プーリング戦略の見直し:** Supabase標準のPgBouncerに加え、Prisma Accelerateのキャッシュレイヤーを組み合わせることで、サーバーレス環境での接続数爆発問題が解消しつつある。ただしレイテンシ要件によってはPgBouncer直接接続の方が有利な場合も残る。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の本格普及:** 2026年時点でWASI Preview 2が安定化し、RustからWasmコンポーネントをビルドする際のインターフェース定義（WIT）が標準化。異なるランタイム間での相互運用性が大幅に向上した。

- **SIMD・スレッド対応の成熟:** Wasm SIMDとshared memoryスレッドがすべての主要ブラウザ・ランタイムで安定サポートされ、Rustの`rayon`や`packed_simd`を使った並列処理がネイティブに近いスループットを実現できる。

- **GC提案による言語境界のオーバーヘッド削減:** Wasm GC proposalの普及により、JS↔Wasm間のデータ受け渡しコストが低減。Rustで書いた高頻度呼び出しの計算カーネルをバインディングコスト無しに統合しやすくなった。

- **エッジ・サーバーサイドでのRust+Wasmが主流化:** Cloudflare Workers / Fastly Compute@Edge等でRust製Wasmが本番ワークロードの主力となり、コールドスタート1ms以下・メモリ分離の両立がプロダクション実績で証明されている。

- **`wasm-opt`＋LTOのビルドパイプライン最適化が必須:** `cargo`の`opt-level='z'`＋`lto=true`＋Binaryen `wasm-opt -O3`の組み合わせで、バイナリサイズを30〜50%削減しつつ実行速度を維持するのがベストプラクティスとして定着。CI/CDに組み込むことが前提。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** App Router では全コンポーネントがサーバーコンポーネントとして動作するため、`'use client'` は最小限の境界（インタラクティブUIのみ）に留め、データフェッチと重いロジックはサーバー側で処理する設計が定着している。

- **Partial Prerendering (PPR) の活用:** 静的シェルと動的ストリームを同一ルートで共存させるPPRが安定化し、LCPを犠牲にせず動的コンテンツを提供できる。`<Suspense>` の粒度設計がアーキテクチャの鍵。

- **Server Actions でAPIルートを削減:** フォームや変更処理に `use server` 関数を直接使うことで、不要なAPI Routeを排除しつつ型安全なend-to-endのデータフローを実現。ただしCSRF・認可チェックはAction内で必須。

- **`use cache` ディレクティブによる宣言的キャッシュ:** Next.js 15以降で`fetch`キャッシュがデフォルト無効化された代わりに、`use cache` / `cacheTag` / `revalidateTag`による明示的キャッシュ制御が主流。コンポーネント単位でのきめ細かいキャッシュ戦略が求められる。

- **パラレルルート＋インターセプトルートでモーダルUXを実現:** `@slot` と `(.)intercept` を組み合わせたモーダルパターンが成熟し、画像ギャラリーや詳細パネルなどをURLを保ちつつ実装できる。本プロジェクトの物件詳細モーダルにも適用価値がある。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択的活用:** 全APIルートをEdgeに移行するのは逆効果。認証チェック・A/Bテスト・地域リダイレクトなど低レイテンシが本質的に重要な処理のみEdgeに限定し、DBアクセスを伴うロジックはNode.jsランタイムに留める。

- **Cold Start問題の実質的解消:** 2025年後半のVercelアップデートでV8 Isolateの再利用率が大幅改善。ただしbundleサイズが1MB超になるとまだペナルティがあるため、edge向けコードは依存関係を極力排除した軽量実装が必須。

- **Middleware設計の見直し:** `middleware.ts`のmatcherを厳密に設定しないと全リクエストに実行コストが発生する。2026年時点では`/((?!_next|favicon).*)` パターンより明示的なパスマッチが推奨され、不要なEdge実行を削減できる。

- **キャッシュ戦略との組み合わせ:** Edge FunctionsとNext.js 15の`unstable_cache` / ISRを組み合わせることで、動的パーソナライゼーションと高速配信を両立できる。「Edgeで分岐判定 → キャッシュ済みレスポンスを返す」パターンが最もコスト効率が高い。

- **可観測性の整備:** Edge環境はNode.jsと異なりログが揮発しやすい。OpenTelemetry + Vercel Log Drains（または Axiom/Datadog連携）を早期に組み込み、レイテンシ異常をリージョン別に追跡できる体制を構築することが本番運用の前提となる。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の`satisfies`は型推論を維持しつつ型チェックを行うため、`as`キャストを排除してランタイムエラーを防ぐ最もクリーンなパターンとして定着している。

- **Branded Types によるドメイン安全性:** `type UserId = string & { readonly __brand: 'UserId' }` のようなBranded/Nominal Typesで、構造的型付けの落とし穴（誤ったIDの混在等）をコンパイル時に検出できる。特にDDD設計との相性が良い。

- **`noUncheckedIndexedAccess` の標準化:** `tsconfig`でこのフラグを有効にすることで配列・オブジェクトアクセスが`T | undefined`になり、ランタイムのundefinedエラーを根絶できる。2026年時点では厳格プロジェクトのデフォルト設定になりつつある。

- **Zod + `z.infer<>` によるSchema-First型定義:** ランタイムバリデーションとTypeScript型を単一ソースから生成するZodパターンが完全に主流化。APIバウンダリでの型安全性はこれで担保し、`interface`手書きを避けるのがベストプラクティス。

- **Template Literal Types の実用化加速:** `type Route = \`/api/${string}\`` のようなTemplate Literal Typesがルーティング・i18nキー・イベント名等の文字列ドメインに広く使われており、ドキュメントなしでも誤入力をコンパイル時に防げる実装が増えている。
