# CTO Knowledge - 2026-06-13

## Daily Update (2026-06-13)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降でPPRが安定化し、静的シェルと動的コンテンツを同一ルートで共存できる。ページ全体をSSRに落とさず、キャッシュヒット率を最大化しながらパーソナライズが実現できる。

- **Turbopackへの完全移行:** `next dev --turbopack` がデフォルト化され、大規模プロジェクトでもHMRが数十ms台で完了する。webpack依存のカスタム設定が残っている場合は早期に移行コストを払うべき。

- **React Server Components (RSC) によるバンドルサイズ削減:** データフェッチロジックをサーバーに留め、クライアントJSを最小化するのが今や標準戦略。`"use client"` の境界を慎重に引かないとRSCの恩恵が消える。

- **`after()` API でレスポンス後処理を分離:** Next.js 15.1で安定した `after()` を使い、ロギング・分析・メール送信などをレスポンス返却後に非同期実行。ユーザー体験に直接影響する処理のみをクリティカルパスに残せる。

- **`<Form>` コンポーネントとServer Actionsの最適化:** フォーム送信をServer Actionsで処理する際、`useOptimistic` と組み合わせることでUIのレイテンシを知覚ゼロに近づけられる。ただしアクションの冪等性と楽観的更新のロールバック設計が不可欠。

### 2. React Server Components streaming 2026

- **Partial Pre-rendering (PPR) の本格普及:** Next.js 15以降でPPRが安定化し、静的シェルを即座に返しながらDynamic部分をストリーミングするハイブリッドモデルが標準アーキテクチャになりつつある。ビルド時に静的境界を自動検出するため、手動の`Suspense`境界設計の負担が大幅に減少。

- **サーバーアクション + Optimistic UIの成熟:** Server ActionsとReactの`useOptimistic`を組み合わせたパターンが定着し、クライアント状態管理ライブラリへの依存を減らせる設計が現実的になった。ただしトランザクション的な複数アクションの一貫性保証は依然として設計上の注意点。

- **Streaming SSRのキャッシュ戦略が複雑化:** `fetch`レベルのData Cacheと`unstable_cache`、Route Cache、Full Route Cacheが混在し、ストリーミング中のキャッシュ無効化タイミングのバグが本番事故の主因になっている。チームとして**キャッシュ層ごとのライフサイクル図**を整備することを強く推奨。

- **React 19 Compiler（旧React Forget）との統合:** コンパイラが自動でメモ化を最適化するため、RSCとClient Componentsの境界設計に集中できるようになった。ただし`use client`境界を越えるpropsのシリアライズコストは依然ボトルネックになり得るため、境界設計のレビューは継続必須。

- **Edge RuntimeとNode.js Runtimeの使い分け:** ストリーミングレスポンスはEdge Runtimeが低レイテンシで有利だが、DBコネクションや大規模計算はNode.js Runtimeが安定。**ルートごとにruntimeを明示的に宣言**する規約をプロジェクト初期に決めないと、後からの変更コストが高い。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全性の最重要化:** 2026年においてtRPCはNext.js/フルスタックTypeScriptプロジェクトのデファクトになりつつあり、クライアント・サーバー間で型を共有することによるランタイムエラーの排除が最大の価値。

- **GraphQLの棲み分け明確化:** BFF（Backend for Frontend）パターンやマイクロサービス集約レイヤーでGraphQLは依然強力だが、シンプルなCRUD APIにGraphQLを採用するコストが見直され、「適材適所」の判断が成熟してきた。

- **REST + OpenAPI 3.1の再評価:** Zodやts-rest等のライブラリがRESTにも型安全性をもたらし、OpenAPIスキーマから自動生成されるクライアントSDKの品質が向上。GraphQLほどの学習コストなしに型安全APIが実現できる。

- **ストリーミング対応の必須化:** LLM統合の普及でSSE（Server-Sent Events）とHTTP Streamingへの対応がAPI設計の前提になり、tRPCのsubscriptionsやGraphQL subscriptionsの実装パターンが重要度を増している。

- **エッジランタイムとの親和性:** Cloudflare Workers/Vercel Edge等のエッジ環境でAPIを動かす場合、Node.js依存のライブラリが使えない制約があり、tRPC + Honoの組み合わせや軽量RESTが選ばれるケースが増加している。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** WebAssembly + WASI Preview 2の成熟により、LLMの量子化モデル（1-7B）をエッジノードで低レイテンシ実行するパターンが主流になりつつある。Cloudflare Workers AIやVercel AI SDKがその代表例。

- **Durable Objects / Stateful Edgeの台頭:** 従来「ステートレス」が前提だったエッジが、分散KVとアクターモデルを組み合わせたステートフル実行に対応。リアルタイムコラボ・ゲームロジックもエッジで完結できるようになった。

- **Cold Startの事実上の解消:** V8 Isolateベースのランタイム（Cloudflare Workers、Deno Deploy）では0ms cold startが当たり前になり、Node.js互換レイヤーの改善でレガシーコードの移行障壁も大幅に低下している。

- **エッジDBとのセット採用が加速:** Turso（libSQL）・Neon（PgEdge）・Upstash Redisなど、エッジリージョンに自動レプリケートするDBが整備され、「計算もデータもユーザーの近く」というアーキテクチャが現実的なコストで実現可能に。

- **オブザーバビリティの課題が顕在化:** エッジ分散環境では従来のAPMツールが機能しにくく、OpenTelemetry + ClickHouseベースの軽量トレーシング基盤を自前で構築するチームが増加。エッジ対応のo11yスタック選定が2026年のCTO最重要課題の一つ。

### 5. authentication security best practices 2026

- **パスキー（Passkey）ファーストへの移行:** FIDO2/WebAuthnベースのパスキーが2026年のデファクトスタンダードとなり、パスワードレス認証を全ユーザーにデフォルト提供しないサービスは競争力を失いつつある。

- **トークンバインディングとDPoP（Demonstrating Proof of Possession）の標準化:** OAuthアクセストークンの盗難・リプレイ攻撃対策として、DPoPによりトークンをクライアント鍵ペアに紐づける実装がエンタープライズ要件化されている。

- **継続的認証（Continuous Authentication）の台頭:** ログイン時の一回限りの認証から、行動バイオメトリクスやリスクスコアリングによるセッション中の継続的な正当性検証へシフトし、セッションハイジャックリスクを大幅に低減できる。

- **サプライチェーン攻撃対策としての依存ライブラリの厳格管理:** `passport.js`や`next-auth`などの認証ライブラリへの悪意ある更新を通じた侵害が増加しており、lockfileの固定・SBOMの管理・Dependabotのセキュリティアラート自動対応が必須となった。

- **Entra ID / Okta等のIDP統合とゼロトラスト前提のセッション設計:** 自前のセッション管理を廃し、IdPのトークンライフサイクルに全面委譲することで、侵害時の影響範囲をトークン有効期限（短命トークン15分以下）に限定する設計が主流になっている。

### 6. database architecture Prisma Supabase 2026

- **Prisma Accelerate の常時採用:** エッジ環境でのコールドスタート問題はPrisma Accelerateのコネクションプーリング＋グローバルキャッシュで解消されており、サーバーレス構成でも安定したレイテンシを維持できる。

- **Supabase = PostgreSQL フルスタック:** Row Level Security（RLS）とリアルタイムサブスクリプションを活用することで、バックエンドAPIレイヤーを大幅に削減できる——ただしRLSポリシーの複雑化はデバッグコストになるため設計段階から慎重に。

- **pgvector による AI統合が標準化:** Supabaseの`pgvector`拡張でベクター検索をPostgreSQL内に集約できるため、外部ベクターDBを別途持つコスト・複雑性を排除できる。RAG構成の第一選択肢になりつつある。

- **Prisma + Supabase の組み合わせ上の注意点:** PrismaはSupabaseのRLSを「バイパス」するservice_roleキーで動作するため、サーバーサイドのビジネスロジックと、クライアント直接アクセスのセキュリティ境界を明確に設計する必要がある。

- **マイグレーション管理の統一が課題:** Prisma Migrateを使うとSupabaseのマイグレーション管理（`supabase db push`）と競合しやすい——どちらか一方をソース・オブ・トゥルースに決め、CIパイプラインで整合性を担保することがベストプラクティス。

### 7. WebAssembly Rust performance 2026

- **WASM Component Modelの成熟:** 2026年時点でWASI 0.2が安定化し、RustのWASMコンポーネント間でインターフェース型を安全に共有できるようになった。これにより、マイクロサービス的な分離とネイティブに近い性能を両立できる。

- **SIMD・スレッド並列化の実用化:** WebAssembly SIMDとShared Memoryがメジャーブラウザ・Wasmtime双方で安定対応済み。Rustの`rayon`や`packed_simd`を使った並列処理がブラウザ内でも有効になり、画像処理・ML推論で特に効果大。

- **ネイティブとのパフォーマンスギャップ縮小:** Cranelift/Wasmtimeのコンパイラ最適化が進み、計算集約型タスクではネイティブ実行の85〜95%程度の性能に到達。ただしメモリアクセスパターンによってはまだ差が出るため、`wasm-pack`のプロファイリングが重要。

- **RustのWASMツールチェーン成熟度:** `wasm-bindgen`・`wasm-pack`が安定し、`cargo component`でComponent Modelへの移行も容易に。ビルドサイズは`wasm-opt`（Binaryen）で30〜50%削減可能で、本番導入のハードルが大幅に下がった。

- **エッジ・サーバーサイドWASMの台頭:** CloudflareWorkers・Fastly Compute等でRust WASMがファーストクラス対応。コールドスタートがコンテナ比で100倍以上高速なため、アーキテクチャ選択肢として積極的に検討すべきフェーズに入っている。

### 8. Next.js App Router patterns 2026

- **React Server Components (RSC) の全面採用:** 2026年はRSCが「オプション」から「デフォルト設計」へ移行。データフェッチはサーバー側で完結させ、クライアントバンドルを最小化するパターンが標準化された。

- **`use cache` APIによる宣言的キャッシュ:** Next.js 15以降の`use cache`ディレクティブにより、関数・コンポーネント単位でキャッシュ戦略を宣言できる。`revalidate`と`tags`ベースの無効化で、`fetch`に依存しない柔軟なキャッシュ設計が可能になった。

- **Partial Pre-rendering (PPR) の実用化:** 静的シェルと動的ストリーミングを同一ルートで共存させるPPRが安定版に。`<Suspense>`境界を設計の起点とすることで、TTFBとFCPを両立できる。

- **Server Actions の非同期UXパターン:** フォーム送信にとどまらず、楽観的更新（`useOptimistic`）とServer Actionsを組み合わせたミューテーション設計が主流。APIルートを廃止しServer Actionsに一本化するアーキテクチャが増えている。

- **`unstable_after` による非同期サイドエフェクト分離:** レスポンス送信後に解析・ログ送信などを実行する`after()`APIにより、メインのレスポンスパスを汚染せずに副作用を処理できる。パフォーマンス計測やAuditログに有効。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge RuntimeからNode.js Runtimeへの選択的移行:** Edge Functionsは低レイテンシーに優れるが、2026年時点ではNode.js互換APIの制限が依然として存在する。CPUバウンドな処理や重いライブラリが必要な場合はFluid compute（サーバーレスの新モデル）を優先し、Edge Functionsは認証・A/Bテスト・地理的ルーティングなど軽量なミドルウェアに絞るのがベストプラクティス。

- **ポイント2: Cold Start最小化のためのバンドルサイズ管理:** Edge Functionsは1MB（圧縮後）の制限があり、バンドルが大きいほどコールドスタートが増加する。`@vercel/og`や`next/font`など最適化済みライブラリを活用し、`import`の動的分割でバンドルを最小化することがパフォーマンスの鍵。

- **ポイント3: Streaming Responseの積極活用:** 2026年ではAI機能の統合が標準化しており、LLMストリーミングレスポンスをEdgeから直接返すパターンが主流。`ReadableStream` + `TransformStream`を使ったパイプラインで、Time to First Byte（TTFB）を劇的に改善できる。

- **ポイント4: ISR（Incremental Static Regeneration）とEdgeキャッシュの組み合わせ:** Edge FunctionsでのCache-Control設定を正確に制御し、`stale-while-revalidate`パターンを活用することで、動的コンテンツでも静的サイト並みのパフォーマンスを実現。`revalidatePath` / `revalidateTag`によるオンデマンド再検証との組み合わせが効果的。

- **ポイント5: 可観測性（Observability）の強化:** Edge環境は分散実行のためデバッグが困難。Vercel Analytics + Speed InsightsをEdge専用メトリクスと組み合わせ、リージョン別のp99レイテンシーを監視する。`waitUntil()`を使った非同期ロギング（ Datadog/Axiom連携）でパフォーマンス劣化の早期検知体制を整えることが重要。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のような Branded Types が標準パターンとして定着し、プリミティブ型の誤用（UserIdとProductIdの混同など）をコンパイル時に検出できるようになった。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` が2026年では必須スキルとなり、型推論を保ちながら型制約を検証できるため、`as` キャストによる型安全性の破壊を大幅に減らせる。

- **Template Literal Types によるAPI型生成:** REST エンドポイント名やイベント名を `type Route = \`/api/${string}\`` のようにテンプレートリテラル型で表現し、ランタイムエラーをコンパイル時に排除するパターンが浸透している。

- **`noUncheckedIndexedAccess` の標準化:** `tsconfig.json` のこのオプションが多くのチームで必須設定となり、配列・オブジェクトへのインデックスアクセスで自動的に `T | undefined` となることで、nullアクセスのバグが激減した。

- **Zod + `z.infer` による型の単一ソース:** スキーマ定義から型を導出する `type User = z.infer<typeof UserSchema>` パターンが定着し、バリデーションと型定義の二重管理を廃止してランタイムとコンパイル時の型整合性を保証している。
