# CTO Knowledge - 2026-07-22

## Daily Update (2026-07-22)

### 1. Next.js performance optimization 2026

- **React Server Components とストリーミングの標準化:** Next.js 16ではRSCペイロードの部分的キャッシュとPartial Prerendering (PPR)が安定版となり、静的部分を即時配信しつつ動的部分だけをストリーミングすることで、初回表示速度(TTFB/LCP)を大幅に改善できる。物件一覧ページのように「上部は静的、価格や空き状況は動的」な構成に特に有効。

- **Turbopackへの完全移行:** ビルド・devサーバー共にTurbopackがデフォルト化し、Webpack比で大幅な高速化が実現している。大規模化しつつあるsumitsugiのコードベースでも、ローカル開発のHMR速度とCI上のビルド時間短縮に直結するため早期移行のメリットが大きい。

- **画像・フォント最適化のエッジ処理:** `next/image`とフォント最適化がCDNエッジでのAVIF/WebP自動変換・レスポンシブ配信に対応し、物件写真が多いプラットフォームではCore Web Vitals（特にLCP）改善に直結する。

- **キャッシュ戦略の明示化（`use cache`ディレクティブ）:** 従来の暗黙的なfetchキャッシュから、関数・コンポーネント単位で`use cache`を明示する方式に移行し、キャッシュの意図が読みやすくバグりにくくなった。物件データや前の住人プロフィールなど更新頻度が異なるデータの粒度別キャッシュ設計がしやすい。

- **Bunとの統合最適化:** Next.js 16はBunランタイムでのSSR実行パスが公式サポートされ、Node.js比でコールドスタート・レスポンス速度が改善している。当プロジェクトはBun 1.xを既に採用しているため、この恩恵をそのまま享受できる立場にある。

### 2. React Server Components streaming 2026

- **ストリーミングSSRのデフォルト化:** Next.js 16ではRSCのストリーミングレンダリングが標準構成となり、`loading.tsx`とSuspenseバウンダリを組み合わせることで、ページ全体の初回表示を待たずに段階的にコンテンツを配信できる。物件一覧ページのように画像・レビュー・空室状況など取得速度の異なるデータが混在する画面で、TTFBを大幅に短縮できる。

- **Partial Prerendering (PPR) の本格運用:** 静的シェル（ヘッダー、レイアウト）を事前生成しつつ、動的部分（ログイン状態、パーソナライズ情報）のみをストリーミングする手法が主流化している。sumitsugiの物件詳細ページでも、静的な物件情報とユーザー固有の「引越し費用」計算を分離することで、CDNキャッシュ効率とパーソナライズ性を両立できる。

- **Server Actionsとの統合強化:** フォーム送信（内見予約、問い合わせ）がServer Actionsで完結し、クライアントJSバンドルを最小化しつつストリーミングレスポンスで即座にUIフィードバックを返せるようになった。認証系フローでのuseOptimisticとの組み合わせが定石化している。

- **ウォーターフォール回避のためのデータフェッチ設計が必須:** RSCでは`fetch`のリクエストメモ化があっても、コンポーネントツリーが深いとデータ取得が直列化しやすい。`Promise.all`や並列Suspenseバウンダリの分割設計をレビュー観点に加えないと、ストリーミングの恩恵が実質半減する点に注意が必要。

- **キャッシュ戦略の複雑化とデバッグコスト:** `use cache`ディレクティブやRouter Cache、Full Route Cacheが層をなし、ステータス変更（`draft`→`public`）の反映タイミングがズレるリスクが増している。物件ステータス更新のようなミューテーション後は、明示的な`revalidatePath`/`revalidateTag`の設計をコードレビューで必ず確認すべき。

### 3. API design REST GraphQL tRPC 2026

- **設計哲学の使い分け:** REST/GraphQL/tRPCの二者択一ではなく、外部公開APIはREST（キャッシュ・エコシステム重視）、社内BFFやモノレポ内通信はtRPC（型安全・開発速度重視）、複雑なデータ集約が必要なフロントエンドにはGraphQLと、用途別に併用するのが2026年の主流です。

- **エンドツーエンド型安全の標準化:** tRPC・Hono RPC・OpenAPI(TypeScript)ジェネレータの成熟により、バックエンドの型変更がフロントエンドのビルドエラーとして即座に検知される構成が一般化。sumitsugiのようなNext.js App Router構成では、Server ActionsとtRPC/Honoを組み合わせて手書きAPIクライアントを排除する設計が有効です。

- **GraphQLはBFF・集約レイヤーに収束:** 汎用APIとしてのGraphQL採用は減少し、複数マイクロサービスやサードパーティAPIを1画面向けに集約する「BFF専用レイヤー」としての採用にフォーカスが移っています。小規模チームでは運用コスト（N+1対策、スキーマ管理）が見合わないケースが多い点に注意が必要です。

- **AIエージェント消費を前提としたAPI設計:** LLMエージェントやMCP（Model Context Protocol）経由でAPIが呼ばれる前提が増え、明確なエラーメッセージ・冪等性・自己記述的なスキーマ（JSON Schema/Zod）を持つAPI設計が「人間向けドキュメント」より重要度を増しています。Zodバリデーションを既に採用しているsumitsugiは、この点で有利な立ち位置にあります。

- **エッジ・サーバーレス環境への最適化:** Next.js 16のServer ActionsやEdge Runtimeを前提に、コールドスタート・バンドルサイズを意識した軽量ランタイム（Hono等）がREST/RPC層で選好される傾向が続いています。tRPCもEdge対応が標準化され、Vercel等のエッジ配信との親和性が向上しています。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** Cloudflare Workers、Deno Deploy、Vercel Edge FunctionsがWebAssembly System Interface (WASI) 準拠に収束しつつあり、ベンダーロックインを避けたマルチプラットフォーム展開が現実的になっている。

- **コールドスタート問題の実質解消:** V8 isolateベースの起動が1桁ミリ秒台まで高速化し、2026年時点ではエッジでのステートフルな処理（軽量DB接続・セッション管理）も遅延を気にせず組み込めるレベルに達している。

- **エッジ×DBの融合:** Turso、PlanetScale、Cloudflare D1などエッジロケーションにレプリカを持つDBが一般化し、ユーザーに地理的に近いノードで読み書きが完結する設計が主流になりつつある。sumitsugiのような不動産系プラットフォームでは、物件検索の低レイテンシ化に直結する。

- **AIワークロードのエッジ配置:** 小型LLM（quantized/distilled model）をエッジで推論させ、認証・レコメンド・軽量な自然言語処理をオリジンサーバーを介さず完結させる構成が増加。個人情報を含むリクエストをオリジンに送らずに済む分、プライバシー面のメリットも大きい。

- **観測性とデバッグの課題:** 分散されたエッジ実行環境ではトレーシング・ログ集約が依然として難しく、OpenTelemetry対応のエッジ向けAPMツールへの投資が2026年の重要な技術的意思決定ポイントになっている。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証がデファクトスタンダード化しており、フィッシング耐性のあるパスキーをプライマリ認証手段とし、パスワードは廃止ロードマップに乗せるべき。sumitsugiのようなCtoC取引プラットフォームでは特にアカウント乗っ取り対策として優先度が高い。

- **セッション管理とトークンローテーション:** JWTの長期有効化を避け、短命アクセストークン＋リフレッシュトークンローテーション（Refresh Token Rotation）を実装し、漏洩時の被害範囲を最小化する。Supabase Auth等のBaaSを使う場合もセッション無効化APIを明示的に呼び出せる設計にしておく。

- **デバイスバインディングと異常検知:** ログイン時のデバイスフィンガープリンティングと地理的異常検知（Impossible Travel検知）を組み合わせ、不審なログインをリアルタイムでブロック・再認証要求する仕組みが2026年の標準になりつつある。

- **最小権限のRLS（Row Level Security）徹底:** DB層でのアクセス制御をアプリケーションロジックに依存せず、Supabase/PostgreSQLのRLSポリシーで物件データ・個人情報を保護することが監査観点でも必須。前の住人・次の住人間の個人情報露出リスクを構造的に防ぐ。

- **CSRF/XSS対策のフレームワーク標準化:** Next.js 16のServer Actions利用時はCSRFトークンの自動検証とSameSite Cookie設定を組み合わせ、フォーム送信（引越し費用決済含む）を保護する。決済関連フローは特に入力サニタイズとCSP（Content Security Policy）を厳格化する必要がある。

### 6. database architecture Prisma Supabase 2026

- **ポイント1（Prisma ORMの型安全性とEdge対応）:** Prisma ClientはEdge Runtime対応が進み、Next.js 16のServer Componentsと組み合わせることで、DBアクセス層の型安全性を保ったままレイテンシを抑えられる。ただしコネクションプーリングの設計（Prisma Accelerate等）を誤ると同時接続数の上限に早期に達するため、サーバーレス環境ではプーリング戦略の検証が必須。

- **ポイント2（Supabaseのマネージドインフラとしての強み）:** SupabaseはPostgreSQL本体に対する薄いレイヤーとしてRLS（Row Level Security）・Auth・Realtimeを統合提供しており、住人情報や物件データのようにユーザー単位のアクセス制御が重要なドメインでは、アプリケーション層でのアクセス制御ロジックを減らせる利点が大きい。

- **ポイント3（RLSとPrismaの併用パターン）:** Prisma経由でSupabaseにアクセスする場合、Prisma自体はRLSを意識しないため、サービスロールキーでバイパスしないよう注意し、ユーザーコンテキストに応じたRLSポリシーをPostgres側に必ず定義する設計が2026年時点でのベストプラクティスとして定着している。

- **ポイント4（マイグレーション運用の一元化）:** Prisma MigrateとSupabase CLIのマイグレーション機構が競合しやすいため、どちらか一方（推奨はPrisma Migrateに統一）をSSOTとして運用し、CI上でマイグレーション差分チェックを必須化することでスキーマドリフトを防止できる。

- **ポイント5（コスト最適化の観点）:** 物件データのような読み取り比率が高いワークロードでは、Supabaseのリードレプリカ機能とPrismaのクエリキャッシュ（Prisma Accelerate）を組み合わせることで、ベータローンチ後のスケール時にDBコストを抑制しつつレスポンス速度を維持できる。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデルの成熟:** WASI Preview 2とComponent Modelが実用段階に入り、Rustの`wasm32-wasip2`ターゲットが安定化。異なる言語間でのWasmモジュール連携が現実的になり、プラグインアーキテクチャの設計がシンプルになる。

- **SIMD・マルチスレッド対応の一般化:** WebAssembly SIMDとスレッド（共有メモリ+アトミック）がブラウザ・ランタイム双方で標準サポートされ、Rustの`std::simd`やrayonとの組み合わせで、画像処理・暗号処理などCPU集約的な処理でネイティブに近い性能を出せる。

- **起動時間の最適化（Wizer / AOTプリイニシャライズ）:** コールドスタートが課題だったサーバーレス・エッジ用途で、Wizerのようなプリイニシャライズツールやランタイム側のAOTコンパイル（Wasmtime, wasmer）が普及し、ミリ秒未満の起動が実用範囲に。sumitsugiのようなNext.jsアプリでは直接使う場面は少ないが、将来的にエッジミドルウェアの重い処理をWasmに切り出す選択肢として意識すべき。

- **バイナリサイズとツリーシェイキング改善:** `wasm-opt`やRustのLTO設定、`wee_alloc`に代わる軽量アロケータの選択肢が広がり、フロントエンドに配布するWasmモジュールのサイズが継続的に縮小。画像処理や暗号化などクライアント側で重い計算をさせたい場合、数十KB〜数百KB規模で導入しやすくなっている。

- **Rust以外の言語のGC Wasm対応拡大の裏で、Rustの優位性が明確化:** GC ProposalによりKotlin/Java/DartなどのWasm対応が進む一方、Rustは所有権モデルによりGC不要かつ決定的なメモリ管理を維持できるため、パフォーマンスクリティカルな部分（決済処理、画像圧縮、PDF生成など）ではRust+Wasmが引き続き第一選択肢であり続ける。

### 8. Next.js App Router patterns 2026

- **Server Actions の標準化とキャッシュ戦略:** Next.js 16では`use cache`ディレクティブによる部分的な静的キャッシュ制御が主流となり、Server ActionsとPPR（Partial Prerendering）を組み合わせて動的部分と静的部分を明確に分離するパターンが定着している。sumitsugiのような物件一覧・詳細ページでは、静的な物件情報と動的な問い合わせ状況を分けてキャッシュすることでLCPを大幅に改善できる。

- **Parallel Routes / Intercepting Routes によるモーダルUX:** 物件詳細のモーダル表示や画像ギャラリーなど、URLを保持しつつオーバーレイUIを実現するパターンがApp Routerの標準的な設計手法として広く採用されている。`@modal`スロットと`(.)`インターセプトの組み合わせは、前の住人プロフィールや引越し費用の内訳表示などに応用しやすい。

- **Server Components ファーストのデータフェッチ:** クライアントでのuseEffectベースのfetchは基本的に排除し、Server Componentsでのデータ取得＋Suspense境界によるストリーミングが標準パターンになっている。認証状態や物件ステータス(`draft`/`public`)のようなアクセス制御ロジックはServer Component層で完結させることでセキュリティリスクを減らせる。

- **型安全なルーティングとZodによる境界検証:** TypeScriptのルート型生成（typed routes）とZodスキーマによる入力検証を組み合わせ、Server Actions/Route Handlersの境界で型とランタイム検証を二重に担保する設計が2026年のベストプラクティスとして定着。本プロジェクトの「Input validation: Zodスキーマ必須」方針とも整合する。

- **Bundle最適化とEdge Runtimeの使い分け:** 全ページをEdgeで動かすのではなく、認証や決済など重い処理はNode.js Runtime、静的コンテンツ配信はEdge Runtimeという使い分けが一般化。`next/dynamic`とReact Server Componentsの境界を意識したコード分割で、初期バンドルサイズを抑えるパターンが引き続き重要。

### 9. Vercel Edge Functions optimization 2026

- **エッジでのバンドルサイズ最適化:** Vercel Edge FunctionsはV8 isolateベースで起動するため、依存関係を最小限に抑えTree Shakingを徹底することがコールドスタート短縮に直結する。特にNext.js 16のReact Server Componentsと組み合わせる際は、クライアント専用ライブラリをEdge Runtimeにバンドルしないよう`runtime`指定を明示すべき。

- **Streaming SSRとの相性:** Edge Functionsは地理的に分散配置されるため、ユーザーに近いノードからストリーミングレスポンスを返すことでTTFB（Time to First Byte）を大幅短縮できる。物件一覧や検索結果ページのような読み込み量が多いUIでは、Suspenseと組み合わせたストリーミングSSRの導入価値が高い。

- **KVストレージとの統合設計:** Edge Functionsはステートレスが前提のため、セッション情報や物件ステータスのキャッシュにはVercel KV（Redis互換）やEdge Configを併用するのが定石。DBへの直接アクセスは避け、頻繁に読むが更新頻度の低いデータ（`draft`/`public`ステータスなど）をEdge Configに逃がすとレイテンシが改善する。

- **Node.js APIの利用制限に注意:** Edge RuntimeはWeb標準APIのみをサポートし、`fs`や一部のcrypto APIが使えない。認証まわり（JWT検証等）を実装する際はEdge互換ライブラリ（`jose`など）を選定しないとビルド時にエラーになるため、事前の依存ライブラリ監査が必須。

- **コスト最適化の観点:** Edge Functionsは実行時間課金モデルのため、重い処理（画像処理・PDF生成など）はEdge Functionsではなく通常のServerless Functionsに切り出す設計が2026年時点でもベストプラクティス。役割分担を誤ると想定外のコスト増につながる。

### 10. TypeScript type safety patterns 2026

- **ポイント1（TypeScript 5.5+の型述語推論）:** `filter`などの配列メソッドで型ガード関数を書かなくても、TypeScriptがコントロールフローから自動的に型述語を推論するようになり、ボイラープレートが大幅に減少している。実務では`.filter(Boolean)`的なコードの型安全性が自然に担保される。

- **ポイント2（Zodなどのスキーマ駆動型定義）:** 型定義とランタイムバリデーションを二重管理せず、Zodスキーマから`z.infer`で型を導出する手法が標準化しつつある。本プロジェクトでも「Zodスキーマを境界で使う」というルールがあるが、スキーマを型のSingle Source of Truthとして扱うことで、フォームや外部APIレスポンスの型ズレを防げる。

- **ポイント3（`satisfies`演算子の定着）:** 型を強制的に狭めず、リテラル型推論を保ちながら型チェックする`satisfies`が、設定オブジェクトや`as const`との組み合わせでデファクトスタンダードになっている。`site-config.ts`のような設定ファイルの型安全性向上に有効。

- **ポイント4（Branded Types / Nominal Typingの普及）:** `PropertyId`と`UserId`のような構造的に同じstring型を区別するBranded Typesパターンが、IDの取り違えバグを防ぐために広く採用されるようになった。物件ステータス（`'draft' | 'public'`）のようなUnion Typeと組み合わせることで、状態遷移のミスをコンパイル時に検出できる。

- **ポイント5（AI生成コードに対する型の防波堤としての役割強化）:** LLMによるコード生成が一般化する中、strictな型定義とZodバリデーションが「AIが書いた誤ったコード」を早期に検出する防波堤として重要性を増している。自律開発ワークフロー（autonomous-developer.yml）を運用する本プロジェクトでは特に、型安全性がAI生成コードの品質担保の要となる。
