# CTO Knowledge - 2026-06-24

## Daily Update (2026-06-24)

### 1. Next.js performance optimization 2026

- **React Server Components の活用拡大:** Next.js 16ではRSCのキャッシュ戦略が成熟し、クライアントへのJS転送量を削減できる。データ取得はサーバー側に閉じ込め、`use client`境界を最小限にすることでバンドルサイズを抑えるのが鍵。

- **Partial Prerendering (PPR) の本格採用:** 静的部分と動的部分を1ページ内で混在させ、TTFBを改善しつつ個人化コンテンツも提供できる。ダッシュボードや物件詳細ページのような「一部だけ動的」なUIに特に有効。

- **画像・フォント最適化の自動化:** `next/image`と`next/font`の自動最適化に加え、AVIF/WebPの優先配信とサブセット化フォントの活用でLCPを大幅改善できる。物件写真が多いsumitsugiのようなサービスでは特に効果が大きい。

- **Edge Runtimeとキャッシュ階層の見直し:** Vercel以外のホスティングでもEdge Middlewareの活用が一般化し、認証チェックやリダイレクトをオリジンサーバーに到達する前に処理できる。`fetch`のキャッシュタグ（`revalidateTag`）を使った粒度の細かい再検証が標準パターンになっている。

- **Turbopackによるビルド・開発体験の高速化:** Next.js 16でTurbopackがビルドでも安定版となり、開発時のHMRだけでなく本番ビルド時間も短縮。大規模コードベースでのCI時間削減に直結する。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPPR（Partial Prerendering）とRSC streamingが標準化され、staticシェルを即時返しつつ動的部分をSuspense境界でストリーミングする構成が一般的に。本プロジェクトのproperties/listing系ページでもLCP改善に直結する。
- **ポイント2:** Server ActionsとRSCの組み合わせでクライアントJSバンドルを最小化する流れが加速しており、フォームや認証フローはuse client境界を絞ることでバンドルサイズと初期表示速度を両立できる。
- **ポイント3:** キャッシュ戦略（fetch cache, unstable_cache, Route Segment Config）の設計ミスがstreaming導入時の落とし穴になりやすく、引越し費用や物件ステータスのような頻繁に変わるデータは明示的なrevalidate設定が必須。
- **ポイント4:** エラーバウンダリとSuspense fallbackのUX設計がRSC streaming時代の新しい責務になっており、ネットワークが遅い環境でも「前の住人」情報などのコンテンツが段階的に表示される体験を意識すべき。
- **ポイント5:** Vercel以外のセルフホスト環境でのstreaming対応（Node runtime vs Edge runtime）に差が出やすく、デプロイ先のランタイム制約を早期に検証することがアーキテクチャ決定の鍵になる。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはフルスタックTypeScript構成（Next.js + Bun環境）において、スキーマ定義とランタイム検証を一体化でき、フロントエンド/バックエンド間の型安全性をend-to-endで保証できる点で2026年も採用が拡大している。本プロジェクトのようなNext.js 16 + TypeScript構成では、REST/GraphQLのようなスキーマ同期コストを排除できるメリットが大きい。

- **ポイント2:** GraphQLはマイクロサービス統合やモバイル/Web間でのデータ取得最適化（over-fetching/under-fetching回避）が必要な大規模システムで依然強いが、単一フロントエンド・単一バックエンドのモノリス構成では運用コスト（リゾルバ設計、N+1問題対策）が過剰投資になりやすい。

- **ポイント3:** RESTはシンプルさとキャッシュ戦略（CDN/HTTPキャッシュ）の成熟度から、公開APIや外部連携（決済、外部サービス連携）の標準として2026年も第一選択。Zodなどのスキーマバリデーションと組み合わせることで、型安全性の弱さを補える。

- **ポイント4:** API設計はもはや「どのプロトコルか」より「型安全性をどこで保証するか」が論点になっている。tRPC + Zodのようにコンパイル時とランタイムの両方で検証する構成が、本プロジェクトの「Input validation: Zodスキーマ使用」という標準とも整合する。

- **ポイント5:** 今後のスケール（前の住人/次の住人の引き継ぎマーケットプレイス）を考えると、内部API（自社フロントエンド向け）はtRPCで型安全性を最大化し、将来的な外部パートナー連携やパブリックAPI公開が必要になった時点でRESTまたはGraphQLゲートウェイを追加するハイブリッド構成が現実的。

### 4. serverless edge computing 2026

- **WASMファーストのエッジランタイム:** Cloudflare Workers / Vercel Edge / Deno Deployなどがコールドスタート数msを実現し、V8 isolateベースの分離が主流に。重い依存を持つNode.js APIを避け、Web標準API（fetch, Streams）に寄せた実装が前提になる。

- **エッジでのステート管理:** Durable Objects、Cloudflare D1/KV、PlanetScale的なグローバルレプリケーションDBが普及し、「エッジ=ステートレス」という制約が崩れつつある。地理的に分散したユーザーに低レイテンシでデータ整合性を提供する設計が現実的な選択肢になっている。

- **エッジでのAI推論:** 軽量LLM（量子化モデル）やルーティング層（プロンプトの一次処理・キャッシュ判定）をエッジで実行し、本体の重い推論は中央サーバーに委ねるハイブリッド構成が増加。レイテンシ削減とコスト最適化を両立させる設計パターンとして定着しつつある。

- **Next.jsとの統合深化:** App RouterのMiddleware/Edge Runtimeがデフォルトの実行環境として扱われる流れが続き、Node.js専用APIを使うコードはビルド時に明確にエラーになる。sumitsugiのようなNext.js 16構成では、認証チェックやリダイレクト処理をエッジでどこまで処理できるかが今後の最適化余地になる。

- **観測性とデバッグの課題:** 分散実行環境での分散トレーシング（OpenTelemetry対応）が標準要件になり、エッジ関数のログ集約・デバッグツールチェーンの成熟が2026年の重要テーマ。ローカル開発環境とエッジ実行環境の差異（特にタイムゾーン、ファイルシステムアクセス不可）に起因するバグの早期検出が課題として残る。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証(WebAuthn)が主流となり、フィッシング耐性のある認証がデフォルトに。本サービスでもメール認証に加えてパスキー対応を検討する価値がある。
- **ゼロトラスト前提のセッション管理:** ログイン成功後も継続的にリスク評価を行うcontinuous authenticationが標準化。IPアドレス変化やデバイス指紋の異常検知をセッション維持の条件に組み込む流れが強い。
- **トークン漏洩対策の強化:** JWTなどのアクセストークンは短命化＋リフレッシュトークンのローテーション必須が常識に。XSS経由でのトークン窃取を防ぐため、httpOnly Cookie + SameSite=Strictの組み合わせが推奨される。
- **AIを利用した不正検知:** ログイン試行のパターン分析にML/AIを使い、クレデンシャルスタッフィングやブルートフォースをリアルタイムで遮断する仕組みが普及。Rate limitingだけでは不十分という認識が広がっている。
- **サプライチェーン上の認証リスク:** OAuth連携先(Google/Apple等)のスコープ管理や、依存ライブラリの認証関連パッケージの脆弱性監査が重要性を増している。SBOM(Software Bill of Materials)による依存関係の可視化が求められる。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** PrismaのSupabase向けDirect Connection機能が成熟し、Prisma Accelerate不要でPgBouncer経由のコネクションプーリングが安定運用可能になった。サーバーレス環境（Vercel/Edge）でのコールドスタート時の接続枯渇問題が大幅に改善されている。

- **ポイント2:** Row Level Security (RLS) とPrisma Clientの統合パターンが標準化され、`auth.uid()`をベースにしたポリシー設計とPrismaのミドルウェアを組み合わせることで、アプリ層とDB層の二重防御が実現しやすくなった。物件データや個人情報を扱う本サービスでは特に重要。

- **ポイント3:** Prisma ORMのTypeScript型生成とSupabaseのリアルタイムサブスクリプション（Realtime）を併用する際は、スキーマのドリフトに注意が必要。`prisma db pull`での定期的なスキーマ同期をCIに組み込むのが2026年のベストプラクティス。

- **ポイント4:** マイグレーション管理はPrisma MigrateとSupabase CLIの役割分担を明確化する流れが定着——スキーマ変更はPrisma Migrateで一元管理し、Supabase固有機能（RLS、Storage、Edge Functions連携）は別途SQLマイグレーションで管理する2トラック運用が推奨される。

- **ポイント5:** Supabaseのブランチング機能（Preview Branches）とPrismaのシードスクリプトを組み合わせることで、PR単位での独立したDB環境テストが容易になり、E2Eテストの信頼性向上とCI実行時間短縮の両立が可能になっている。

### 8. Next.js App Router patterns 2026

- **Server Components優先設計:** App RouterではデフォルトでServer Componentsを使い、クライアントへのJSバンドルを最小化するのが基本戦略。`'use client'`境界は本当に必要なインタラクティブ部分（フォーム、状態管理）だけに絞ることで、初期表示速度とCore Web Vitalsを大幅に改善できる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルを即座に返しつつ動的部分をストリーミングするPPRが2026年には実用フェーズに入り、ECサイトや物件一覧ページのような「一部は常に同じ、一部はユーザー依存」な画面で特に効果を発揮する。sumitsugiの物件詳細ページなどに適用余地がある。

- **Server Actions + キャッシュ戦略の成熟:** `revalidatePath`/`revalidateTag`によるきめ細かいキャッシュ無効化がベストプラクティスとして定着し、フォーム送信からデータ更新までAPIルートを書かずに完結できるパターンが標準化している。物件のdraft/public切り替えのような状態更新に向いている。

- **Parallel Routes & Intercepting Routesの実務適用:** モーダル表示（物件詳細をオーバーレイで開く等）や、ダッシュボード系のレイアウトでタブごとに独立してローディング状態を持たせる設計に、Parallel Routesが定番パターンとして使われるようになってきている。

- **型安全なルーティングとミドルウェアの軽量化:** Next.js 16系では型付きルートパラメータの活用が進み、middlewareの実行コストを抑えるためにEdge Runtimeでの処理を最小限に絞り、認証チェックなど本当に必要な処理だけをmiddlewareに残す設計が推奨されている。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化:** V8 Isolateベースの実行環境がさらに最適化され、初回起動レイテンシが数十ms単位まで縮小。重い依存関係をEdge Function本体から分離し、軽量なルーティング層のみをEdgeに置く設計が定石になっている。

- **リージョン選択の自動化:** Vercelのスマートルーティングがユーザー位置とデータソース（DB/KVストア）の地理的距離を考慮し、最適なEdgeリージョンを自動選択。手動でのリージョン固定よりも、データレイヤーをEdge近接型（Turso, PlanetScale Edge等）に揃える方が効果的。

- **Streaming + Partial Prerendering(PPR)との組み合わせ:** Next.js 16のPPRとEdge Functionsを組み合わせることで、静的シェルを即時配信しつつ動的部分のみEdgeで計算・ストリーミングする構成が標準化。TTFBの大幅短縮が見込める。

- **コスト最適化の重要性:** 実行時間とメモリ使用量に応じた課金モデルが続いているため、不要なミドルウェア処理（認証チェックの重複等）をEdgeから排除し、Node.js Functionsとの責務分離を明確にすることがコスト管理の鍵。

- **観測性（Observability）の強化:** Edge Functions専用のトレーシング・ログ集約ツールが充実し、分散実行環境でのデバッグが容易に。本番導入前にOpenTelemetry連携でレイテンシのボトルネックを可視化する運用が推奨される。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x以降、`satisfies`演算子と`const`型パラメータの組み合わせが定着し、型推論の精度を保ちながら過剰な型アノテーションを排除するパターンが主流になっている。

- **ポイント2:** Zod・Valibotなどのスキーマライブラリによる「実行時検証＋型推論の自動生成」が標準化し、システム境界（API入力・フォーム）での型安全性をランタイムでも保証する設計が必須要件になっている。

- **ポイント3:** Branded Types（タグ付き型）を用いて`UserId`と`string`のような構造的に同一だが意味的に異なる値を区別する手法が、大規模コードベースでのバグ防止策として広く採用されている。

- **ポイント4:** テンプレートリテラル型とMapped Typesを活用したルーティング・i18nキーの型安全な自動補完（例: Next.js App Routerのパス型生成）が、フレームワーク統合の標準パターンとして普及している。

- **ポイント5:** `strict`モード＋`noUncheckedIndexedAccess`の有効化がデフォルト推奨となり、配列・オブジェクトアクセス時のundefined混入をコンパイル時に検出する厳格な設定がチーム標準になっている。
