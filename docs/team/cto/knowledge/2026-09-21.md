# CTO Knowledge - 2026-09-21

## Daily Update (2026-09-21)

### 1. Next.js performance optimization 2026

CTOとしての回答なので、コードを書くタスクではなく、トピックについての洞察を日本語で共有します。

- **ポイント1（PPR × Cache Componentsの本格活用）:** Next.js 15で導入された`use cache`ディレクティブとPartial Prerenderingが2026年には主流の最適化手法として定着しつつあり、ページ単位ではなくコンポーネント単位で静的/動的を細かく制御できることで、TTFBを維持しながら個人化されたコンテンツを配信できる。物件詳細ページのような「基本情報は静的・在庫状況は動的」という構成に特に有効。
- **ポイント2（RSCペイロードの最適化がボトルネックの中心に）:** App Routerの普及に伴い、Server Componentsのシリアライズサイズがパフォーマンスのボトルネックになりやすく、`select`的なデータ取得で不要なフィールドをServer→Clientの境界に流さない設計が重要になっている。一覧ページのようなデータ量が多い画面では特に効いてくる。
- **ポイント3（画像・フォント最適化の自動化が標準化）:** `next/image`のAVIF自動配信と`next/font`のセルフホスティングがデフォルト挙動として洗練され、Core Web Vitals（特にLCP）への影響が手動チューニングなしで大幅に改善されるようになった。物件写真中心のUIではLCP改善効果が大きい。
- **ポイント4（Turbopackのビルド速度がCI/CD戦略に影響）:** Turbopackが本番ビルドでも安定運用フェーズに入り、ビルド時間短縮によりCI上での`bun run build`実行やPRごとのプレビューデプロイのコストが下がっている。頻繁なPRサイクルを回す開発フローとの相性が良い。
- **ポイント5（Edge RuntimeとPPRの組み合わせでグローバル配信最適化）:** Edge Runtimeの成熟により、認証チェックなど軽量なミドルウェア処理をエッジで完結させつつ、重い処理はNode.js Runtimeに委譲するハイブリッド構成が実用的になった。ユーザーの地理的分散が進めば体感速度の差として顕在化する。

### 2. React Server Components streaming 2026

- **Partial Prerendering(PPR)の主流化:** Next.js 15/16で安定版となったPPRにより、静的シェルを即座に返しつつ動的部分だけをストリーミングする設計が標準に。初回表示（TTFB/LCP）の体感速度が大幅改善し、当プロジェクトのproperties一覧やlisting詳細ページのような「静的な骨格＋動的な在庫データ」構成と相性が良い。

- **Suspense境界の粒度設計が設計スキルとして重要に:** どこにSuspense境界を置くかでストリーミングのUXが決まるため、「ページ単位」ではなく「コンポーネント単位」での境界設計がベストプラクティスとして定着。物件カード単位・レビュー単位など小粒度でストリーミングすることでウォーターフォールを回避できる。

- **Server ActionsとStreamingの統合が進化:** フォーム送信後の再検証（revalidatePath/revalidateTag）とストリーミングUIの組み合わせがより洗練され、楽観的更新（useOptimistic）と組み合わせた「即時反映＋バックグラウンド確定」パターンが一般化。物件公開/下書き切り替えのような操作に応用できる。

- **エッジランタイムでのRSCストリーミング最適化:** Vercel Edge FunctionsやCloudflare Workers上でのRSCストリーミングが成熟し、地理的に分散したユーザーへの初回応答速度がさらに改善。日本国内向けサービスでも東京リージョン以外からのアクセスがあれば効果が出やすい。

- **キャッシュ戦略の複雑化とデバッグの難しさが課題:** ストリーミング＋部分キャッシュ（`use cache`ディレクティブの一般化）により表現力は上がったが、キャッシュの無効化タイミングを誤ると「古いデータが一瞬見える」バグが増加。本番導入時はE2Eテストでキャッシュ境界のシナリオを明示的にカバーすべき。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCは同一TypeScriptモノレポ（Next.js App Router + サーバーレス関数）内でのスキーマ共有・型安全性の恩恵が大きく、sumitsugiのようなフルスタックTS構成では内部API/BFF層に適しているが、外部公開APIや将来的な多言語クライアント対応を見据えるとREST/OpenAPIの方が長期的な互換性維持コストが低い。

- **ポイント2:** GraphQLは物件検索・フィルタリングのような「クライアント側で必要なフィールドが可変」なユースケース（物件一覧の絞り込み、前の住人プロフィール表示の出し分けなど）で過剰フェッチを防げるが、N+1問題対策（DataLoaderパターン）とキャッシュ戦略の実装コストが増えるため、MVP段階では過剰投資になりやすい。

- **ポイント3:** 2026年のトレンドとして、RESTベースでもZodスキーマからOpenAPI仕様を自動生成し、フロントエンドの型を同期させる「契約駆動開発」が主流化しており、tRPCの型安全性のメリットをRESTのシンプルさと両立できる — sumitsugiは既にZodをバウンダリ検証に使っているため、この移行コストは低い。

- **ポイント4:** 認証・決済（引越し費用の支払いフロー）を含むAPIは、キャッシュ制御・冪等性キー・Webhook設計などRESTの成熟したエコシステム（HTTPステータスコード、標準ミドルウェア）に乗った方が事故率が低く、法務・セキュリティレビューの観点でも監査しやすい。

- **ポイント5:** ローンチ準備フェーズ（法務確認待ち）の今は新規API方式の大規模移行より、既存App Router API Routes + Zod境界検証を維持しつつ、将来の外部連携（不動産ポータル連携等）を見据えてOpenAPI仕様書だけ整備しておくのが費用対効果が高い判断。

### 4. serverless edge computing 2026

- **エッジでのコールドスタート解消:** V8 Isolateベースの実行環境（Cloudflare Workers、Vercel Edge Functions等）が主流化し、コールドスタートが1桁ミリ秒台まで短縮。グローバル分散が前提のsumitsugiのような不動産プラットフォームでも、物件検索APIのレイテンシ改善に直結する。

- **エッジDBとの統合:** D1、Turso、PlanetScaleなど「エッジネイティブ」なデータベースが実用段階に入り、読み取りレプリカをユーザー近傍に配置できるように。前の住人・次の住人のマッチングのような地理的に分散したユースケースで、DB往復のレイテンシを大幅削減できる可能性がある。

- **AI推論のエッジシフト:** 軽量LLM推論（分類・要約・embedding生成）をエッジ実行する動きが加速。物件マッチングのスコアリングやレコメンドの一部をエッジ側に寄せることで、サーバーレス関数の実行コストとレイテンシを同時に下げられる。

- **Next.js 16とエッジランタイムの親和性向上:** App RouterのStreamingやPPR（Partial Prerendering）とエッジランタイムの組み合わせが成熟し、TTFB最適化が容易に。ただしNode.js APIの制約（一部ライブラリ非対応）は引き続き設計上の制約として残るため、依存パッケージの選定時に注意が必要。

- **運用コストの予測可能性向上:** 2026年時点でエッジ課金モデルがリクエスト数ベースから実行時間+メモリのハイブリッド課金に統一されつつあり、MVPローンチ後のスケール時コスト試算がしやすくなっている点は、ローンチ準備中の現フェーズで特に参考になる。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証がデファクトスタンダードとなり、フィッシング耐性のあるパスキーを第一の認証手段として実装すべき。パスワード認証は補助的なフォールバックに留めるのが望ましい。

- **段階的リスクベース認証:** ログイン時のデバイス指紋・行動パターン・地理的位置を組み合わせたリスクスコアリングにより、通常アクセスは摩擦なく、異常検知時のみ追加認証(MFA)を要求する設計が主流化している。

- **セッション管理とトークンのライフサイクル管理:** JWTなどのアクセストークンは短命化し、リフレッシュトークンのローテーション・失効管理を徹底することが必須。長期間有効なトークンの放置は最大の攻撃面になる。

- **サプライチェーン・依存パッケージの認証周りの監査:** 認証ライブラリ(NextAuth/Auth.jsなど)は頻繁に脆弱性が報告されるため、依存バージョンの定期監査とCVE追跡をCIパイプラインに組み込むべき。

- **ゼロトラスト前提のAPI保護:** クライアント側の検証だけに頼らず、全てのAPIエンドポイントでサーバー側の認可チェック(RBAC/ABAC)を必須とし、レート制限・CSRF対策をデフォルトで有効化する設計が求められる。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMのRust依存脱却:** Prisma 6以降でクエリエンジンがRustバイナリからTypeScript製に段階的移行しており、コールドスタート短縮とエッジランタイム（Vercel Edge, Cloudflare Workers）対応が進んでいる。sumitsugiのようなNext.js App Router構成では、この変更でVercel上のデプロイサイズとレイテンシが改善する可能性が高い。

- **Supabaseのブランチング機能:** SupabaseのDatabase Branchingが本番運用レベルで安定してきており、PRごとに独立したPostgresインスタンス＋シードデータを自動生成できる。ワークツリーベースの並行開発フローと相性が良く、`feat/*`ブランチごとにマイグレーション検証を隔離できる。

- **RLS（Row Level Security）中心の設計への回帰:** アプリケーション層での権限チェックに加え、SupabaseのRLSポリシーをPrisma Client Extensionsと組み合わせて二重に強制する構成がベストプラクティス化している。認証・決済まわりを持つプラットフォームでは、DB層での防御を怠らないことが重要。

- **Prisma Accelerate / PgBouncer必須化:** サーバーレス関数の同時実行数増加に伴い、SupabaseのPooler（Transaction mode）かPrisma Accelerateのコネクションプーリングが事実上必須になっている。素のPrisma Clientを直接サーバーレス関数から叩く構成は本番でコネクション枯渇を起こしやすい。

- **型安全なマイグレーション運用:** `prisma migrate diff`とSupabase CLIの`db diff`を併用し、スキーマドリフトをCIで検知する運用が主流化。`status: 'draft' | 'public'`のようなUnion型を持つプロジェクトでは、マイグレーション前にZodスキーマとPrismaスキーマの整合性をCIでチェックする仕組みが有効。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデルの成熟:** WASM Component Model と WASI 0.2/0.3系の安定化により、RustコンパイルのWasmモジュールを言語非依存で相互運用できるようになり、フロントエンドとエッジ双方で共通ロジックを再利用しやすくなっています。パフォーマンス面ではインターフェース境界のシリアライズコストが下がり、JS⇔Wasm間のFFIオーバーヘッドが実用上無視できる水準に近づいています。

- **SIMD・スレッド対応の一般化:** `wasm32-unknown-unknown` での SIMD128 とスレッド（共有メモリ+Atomics）がブラウザ標準搭載になり、画像処理や暗号計算などCPUバウンドな処理をRust側で並列化してネイティブの70〜90%程度の速度が現実的になっています。ただしスレッドを使う場合はCOOP/COEPヘッダー設定が必須で、デプロイ時に見落としやすい落とし穴です。

- **バイナリサイズ最適化がUX直結:** `wasm-opt`、`twiggy`によるサイズ分析、`wee_alloc`に代わる軽量アロケータ選定など、初回ロード時間を左右するバイナリサイズ削減の重要性が増しています。sumitsugiのような不動産系プラットフォームでは、モバイル回線での初期表示速度に直結するため、Wasmを使う機能は遅延ロード＋コード分割を前提に設計すべきです。

- **サーバーサイドWasm（Wasmtime/Wasmer）の実用化:** エッジコンピューティング（Cloudflare Workers、Fastly Compute）でRust製Wasmランタイムがコールドスタート数ミリ秒を実現しており、Next.jsのAPI Routeやミドルウェアの一部処理をWasmに切り出す選択肢が現実的になっています。ただしNode.js/Bunランタイムとの統合はまだエコシステムが発展途上で、本番導入前にBun側のWasmサポート範囲を検証する必要があります。

- **開発体験（DX）の改善:** `wasm-bindgen`と`wasm-pack`のツールチェーンが安定し、TypeScript型定義の自動生成精度が向上したことで、Rust↔TypeScript間の型安全な連携がしやすくなっています。ただし依然としてデバッグ（ソースマップ経由のスタックトレース）は発展途上のため、複雑なロジックをWasm化する際はユニットテストをRust側で厚めに書くのが安全です。

### 8. Next.js App Router patterns 2026

- **サーバーコンポーネント優先設計:** Server Componentsをデフォルトとし、Client Componentsは対話性が必要な葉ノードのみに限定する構成が定着。データフェッチをサーバー側に寄せることでバンドルサイズとウォーターフォールを大幅削減できる。

- **Partial Prerendering (PPR) の実用化:** 静的シェルを即座に返しつつ動的部分を`Suspense`でストリーミングする手法が標準化し、TTFBとインタラクティブ性を両立させやすくなった。キャッシュ戦略と組み合わせる設計判断が重要になる。

- **`use cache` ディレクティブによる明示的キャッシュ制御:** これまでの暗黙的キャッシュから、関数・コンポーネント単位で明示的に指定する方式へ移行。意図しないキャッシュヒット/ミスによるバグが減り、パフォーマンスチューニングが予測可能になる。

- **Server Actions のセキュリティ境界の重要性:** フォーム送信やミューテーションをServer Actionsに集約する設計が広がる一方、認可チェックを各Action内で必ず行う規律が必須。エンドポイントの暗黙的な公開範囲を意識しないとCSRF/認可漏れのリスクがある。

- **ルートグループ+並行ルート(Parallel Routes)によるレイアウト分割:** ダッシュボードやモーダルを伴う複雑なUIで、`@slot`規約を使った並行ルートとIntercepting Routesの組み合わせが実務パターンとして成熟し、状態管理をURLに委譲しやすくなった。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge FunctionsはV8 isolateベースで起動するため、Node.js APIに依存しないコードに絞ることでコールドスタートをほぼゼロに近づけられる。特に認証チェックやリダイレクトなど軽量なミドルウェア処理に向いている。

- **ポイント2:** 2026年はEdge Runtimeでのストリーミングレスポンス最適化が進み、`ReadableStream`を使った部分的なHTMLストリーミング（React Server Componentsとの組み合わせ）でTTFBを大幅に短縮できる。sumitsugiの物件一覧ページのような一覧+詳細パターンに適用余地がある。

- **ポイント3:** Edge ConfigやKV系ストレージ（低レイテンシKVストア）をEdge Functions内で直接参照する構成が主流になり、DBラウンドトリップを避けて頻繁に読むが更新頻度の低いデータ（物件ステータスのフラグ管理など）をエッジに寄せられる。

- **ポイント4:** リージョン指定（Edge Middlewareの`regions`設定）を活用し、ユーザーの地理的分布に応じて実行リージョンを絞ることで、無駄なマルチリージョン実行コストを削減できる — 日本国内向けサービスなら`hnd1`固定が有効。

- **ポイント5:** Edge FunctionsはNode.js互換API（fs、一部のcryptoなど）が使えないため、認証ロジックやPDF生成のような重い処理はServerless Functions（Node runtime）に残し、「軽量・低レイテンシ処理はEdge、重い処理はNode」という役割分担を明確にするのがベストプラクティスとして定着している。

### 10. TypeScript type safety patterns 2026

**ポイント1:** Zodなどのスキーマライブラリでランタイム検証と型推論を統合するパターンが主流化し、`z.infer<typeof schema>` でAPI境界の型と検証ロジックを一本化する手法が定着している。

**ポイント2:** `satisfies` 演算子の活用が広がり、型の widening を防ぎつつリテラル型推論を保持できるため、設定オブジェクトや定数マップの型安全性が向上している。

**ポイント3:** テンプレートリテラル型とconditional typesを組み合わせたブランド型（Branded Types）で、`UserId` と `string` のような意味的に異なる値をコンパイル時に区別する実装が増えている。

**ポイント4:** `unknown` を許容境界のデフォルト型として扱い、`any` を実質禁止するESLintルール（`no-explicit-any`厳格化）が標準化し、外部入力は必ず型ガード関数を通す設計が浸透している。

**ポイント5:** モノレポでのプロジェクト参照（`tsconfig` の `references`）とインクリメンタルビルドの組み合わせで、大規模コードベースでも型チェックの高速化と型安全性の両立が実用段階に入っている。
