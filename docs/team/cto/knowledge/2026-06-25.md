# CTO Knowledge - 2026-06-25

## Daily Update (2026-06-25)

### 1. Next.js performance optimization 2026

- **App Router + Partial Prerendering (PPR) の本格運用:** 静的シェルと動的部分を1つのレスポンスで配信できるPPRが安定版に近づき、TTFBを大幅短縮できる。動的データ取得部分のみSuspenseで切り出す設計が標準になってきている。

- **React Server Components のバンドル最適化:** クライアントJSを最小化する設計（`use client`境界を末端コンポーネントに限定）が定石化し、Lighthouse上のTBT/INP改善に直結する。サードパーティライブラリのRSC対応状況を事前確認することが重要。

- **Turbopackのビルド/devサーバー高速化:** Next.js 16でTurbopackが本番ビルドでも実用レベルになり、大規模リポジトリでのビルド時間がWebpack比で大幅短縮。CI時間短縮にも直結するため、`bun run build`のパフォーマンス計測を定期的に行う価値がある。

- **画像・フォントの自動最適化の進化:** `next/image`のAVIF優先配信やレスポンシブ`sizes`自動推論、`next/font`のセルフホスティングによるCLS抑制が標準化。物件写真が多い当サービスのようなプロダクトではLCP改善に直結する。

- **Edge Runtimeとキャッシュ戦略の精緻化:** `fetch`キャッシュタグやオンデマンドRevalidationを活用し、物件一覧のような頻更新データでもCDNエッジでの配信を維持する設計（stale-while-revalidate的運用）がベストプラクティスとして定着している。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではRSCのストリーミングがデフォルト挙動として最適化され、`loading.tsx`やSuspense境界を細かく分割するほどTTFBとLCPが改善する。当プロジェクトでも`properties/`一覧ページなど検索結果系コンポーネントをSuspense境界で分割し、ファーストビューの初期データのみを優先ストリーミングする設計が有効。

- **ポイント2:** Server Actionsとストリーミングの組み合わせで、フォーム送信後の楽観的UI更新がより自然になってきている。`listing/`の物件登録フローのような多段階フォームでは、各ステップの検証結果を逐次ストリームすることでユーザー体感の遅延を減らせる。

- **ポイント3:** RSCペイロードのキャッシュ戦略（`use cache`ディレクティブ等）が安定し、データフェッチ層とUIストリーミングの責務分離がしやすくなった。`src/lib/data.ts`のようなデータ取得ロジックをサーバー専用に閉じ込め、クライアントバンドルサイズを最小化する設計を継続すべき。

- **ポイント4:** ストリーミング中のエラーバウンダリ設計が重要度を増している——途中で失敗したチャンクが画面の一部だけを破壊しないよう、`error.tsx`をルートだけでなくコンポーネント単位で配置する粒度が推奨されるようになってきた。

- **ポイント5:** パフォーマンス計測の観点では、Server Componentsのストリーミングは可観測性（どのチャンクがいつ届いたか）の計測が難しく、Web VitalsだけでなくTTFB分解やChunk-level timingを取得するカスタム計測が必要になる場面が増えている。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCの採用が拡大しており、TypeScriptフルスタック構成（Next.js + tRPC）ではエンドツーエンドの型安全性とコード生成不要の開発体験が決定的な優位性になっている。sumitsugiのようなNext.js App Router構成では、内部API（BFF層）にtRPCを採用することでフロントエンド/バックエンド間の型ズレを防げる。

- **ポイント2:** GraphQLは複雑なリレーション（物件×前の住人×インテリア×レビューなど）を持つドメインで効果を発揮するが、N+1問題やキャッシュ戦略の複雑さがコストになる。中〜小規模チームでは運用負荷が回収できないケースが多く、REST/tRPCで十分な場面が増えている。

- **ポイント3:** RESTは依然として外部公開API（パートナー連携、決済、行政API連携など）の標準であり、OpenAPI/Zodスキーマからの型自動生成が2026年の主流パターン。社内向けはtRPC、対外公開はREST+OpenAPIという二層構成が現実的な選択肢。

- **ポイント4:** Server Actions（Next.js）の普及により「API層を書かずにミューテーションを書く」設計が増えているが、再利用性・テスト容易性・レート制限の観点ではAPI Routes/tRPC procedureとして明示的に切り出す方が長期的に保守しやすい。

- **ポイント5:** どの方式でもZodによる境界での入力検証は必須（standards.mdの方針と一致）。tRPC/Server ActionsはZodと統合しやすく、型安全性とランタイム検証を一致させやすいのが2026年のベストプラクティス。

### 4. serverless edge computing 2026

- **ポイント1:** WebAssembly (WASM) ベースのエッジランタイムが主流化し、Cloudflare Workers や Fastly Compute@Edge のようなコールドスタートがほぼゼロのVM隔離技術が、Node.js依存の従来サーバーレスを置き換えつつある。Next.js 16のApp Routerをエッジ最適化する際は、依存ライブラリのWASM互換性を事前に確認すべき。

- **ポイント2:** エッジでのステート管理が成熟し、Durable Objects / SQLite-at-the-edge（例: Cloudflare D1, Turso）により、グローバル分散でも強整合性のあるデータアクセスが可能になっている。住人の引き継ぎ情報のような低レイテンシ・地域分散が必要なデータは、エッジDBへの移行候補として検討余地がある。

- **ポイント3:** エッジでのAI推論（小型LLM・埋め込みモデルの推論)がコスト効率化しており、レコメンドや検索の前処理をエッジ側で実行するパターンが増えている。物件マッチングのような軽量推論はオリジンサーバーへの往復を減らせる可能性がある。

- **ポイント4:** マルチクラウド・マルチエッジベンダーロックイン回避のため、OpenTelemetry + WinterCG (Web-interoperable runtimes) 標準への準拠が事実上のベストプラクティスになっている。将来のベンダー切り替えコストを下げるため、エッジ関連コードは標準APIに依存する設計が望ましい。

- **ポイント5:** セキュリティ面では、エッジでのゼロトラスト認証（mTLS + JWT検証をエッジ層で完結）が標準化し、オリジンサーバーへの不要なリクエストを削減しつつ攻撃面を縮小できる。認証・前処理フローのエッジシフトは、今後の負荷増大に備えたアーキテクチャ判断として優先度が高い。

### 5. authentication security best practices 2026

- **ポイント1（パスキー標準化の本格化）:** FIDO2/WebAuthnベースのパスキーがパスワードを代替する主流認証手段となり、Next.jsアプリでも`@simplewebauthn`等のライブラリでネイティブ実装が容易になっている。フィッシング耐性が高く、UXも向上するため新規認証実装はパスワード優先からパスキー優先へ転換すべき。

- **ポイント2（セッション管理のゼロトラスト化）:** JWTの長期有効化は漏洩時の被害が大きいため、短命アクセストークン＋リフレッシュトークンのローテーション、デバイスフィンガープリンティングによる異常検知を組み合わせる構成が標準化している。`auth-context.tsx`のようなクライアント側コンテキストでもトークン失効を即時反映する設計が必須。

- **ポイント3（IDプロバイダー責務の分離）:** 自前で認証ロジックを書くリスクが再認識され、Supabase Auth・Clerk・Auth0等のマネージドIDPに認証フローを委譲し、アプリ側はRBAC/権限制御に専念する分業が進んでいる。物件の`'draft'`/`'public'`のようなリソース権限制御はミドルウェアやRLSで一元管理するのが安全。

- **ポイント4（CSRF/XSS対策の自動化）:** Next.js 16のServer Actionsでは暗号署名付きアクション参照によりCSRFリスクが軽減されるが、Cookieの`SameSite=Strict`/`HttpOnly`設定とCSPヘッダーの併用が依然必須。手動実装ではなくフレームワーク標準機能を最大活用する方針が推奨される。

- **ポイント5（多層防御としてのレート制限・監査ログ）:** 不正ログイン試行に対するIPベース＋アカウントベースの二重レート制限と、認証イベントの構造化ログ（成功/失敗/異常デバイス）が法務・セキュリティ両面で重要性を増している。引っ越しプラットフォームのような個人情報を扱うサービスでは、特商法・プライバシーポリシー対応とあわせて監査証跡の保持期間も明文化すべき。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Supabaseが2026年にかけてPostgres本体へのPrisma統合を深化させ、Prisma Postgres（旧Prisma Accelerate基盤）とSupabaseのリアルタイム/Auth機能を組み合わせたハイブリッド構成が標準化しつつあり、エッジ環境でのコネクションプーリング問題が大幅に解消されている。

- **ポイント2:** Prisma ORMのRust製クエリエンジンからTypeScript native実装への移行（Prisma 6以降）により、サーバーレス環境（Vercel/Cloudflare Workers）でのコールドスタートが改善され、sumitsugiのようなNext.js App Router構成では特にAPI Route/Server Actionsのレイテンシ削減効果が大きい。

- **ポイント3:** Row Level Security（RLS）をPrismaスキーマレベルで宣言的に管理するパターンが普及し、`seller`/`buyer`のような内部データモデルでも、UI表示用語（前の住人/次の住人）とは独立してDB層のアクセス制御を一元化できるようになっている。

- **ポイント4:** Supabase Branchingを使ったプレビュー環境ごとのDBスキーマ分離が一般化し、PRごとに独立したDBインスタンスでマイグレーションを検証できるため、`'draft'|'public'`のようなステータス変更時の型整合性チェックがCI上で安全に行える。

- **ポイント5:** Prisma + Supabaseのフルマネージド構成でも、物件データのような地理空間検索（PostGIS）や全文検索（pg_trgm）はORM抽象化を超えてRaw SQL/`$queryRaw`を使う実装が依然必要で、不動産プラットフォームでは検索体験の差別化要因として重要。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデルの実用化:** WebAssembly Component Model (WIT/wasm-tools) が安定し、RustクレートをWASMコンポーネントとして言語非依存に合成できるようになった。マイクロサービス的な「WASMプラグイン」アーキテクチャが本番投入しやすくなっている。

- **SIMD・スレッド・例外処理の標準化進展:** WASM SIMD128とシェアードメモリ＋アトミクスがブラウザ・ランタイム双方で安定サポートされ、Rustの`std::simd`やrayon系並列処理をWASM上でもネイティブに近い速度で動かせる。画像処理や数値計算ワークロードの移植コストが下がった。

- **Wasmtime/Wasmer等サーバーサイドランタイムの高速化:** Cranelift/Winchベースのコンパイラ最適化により、コールドスタート時間がミリ秒単位まで短縮。Cloudflare WorkersやFastly Compute@EdgeのようなエッジコンピューティングでRust+WASMが事実上の標準スタックになっている。

- **バイナリサイズとツリーシェイキングの改善:** `wasm-opt`やRustの`wasm-bindgen`周辺ツールチェーンの進化で、不要コードの除去精度が向上し、フロントエンド配信時のWASMバンドルサイズが大幅に削減できる。初回ロード体感速度がネイティブJSに近づいている。

- **GC統合（WasmGC）とのハイブリッド運用:** WasmGCの普及によりKotlin/DartなどGC言語との相互運用が進む一方、Rustは依然「GCなし・低レイテンシ」用途（ゲームエンジン、暗号処理、リアルタイム推論）で優位性を保ち、用途に応じた言語選択の指針がより明確になっている。

### 8. Next.js App Router patterns 2026

- **ポイント1:** Partial Prerendering（PPR）が安定版に近づき、静的シェルと動的コンテンツを1ページ内で混在させられるため、ダッシュボードやEC商品ページのようなハイブリッドUIでTTFBを大幅に改善できる。

- **ポイント2:** Server Actionsの型安全性とエラーハンドリングのベストプラクティスが定着し、`use cache`ディレクティブと組み合わせたデータフェッチ戦略が標準化されている。フォーム処理や予約フローではバリデーションをZodでServer Action境界に集約するのが定石。

- **ポイント3:** Route Groupsとparallel routes（`@slot`）を使ったレイアウト分割が、モーダルや多段ナビゲーション（物件詳細→内見予約のようなフロー）でクライアント側の状態管理を減らす設計として広く採用されている。

- **ポイント4:** キャッシュ戦略の複雑さ（`fetch`キャッシュ、Router Cache、Full Route Cache）が依然最大の落とし穴で、`revalidateTag`/`revalidatePath`の使い分けを誤るとstaleデータ表示やビルド時間肥大のリスクがある。チーム内でキャッシュポリシーをドキュメント化しておくことが重要。

- **ポイント5:** Turbopackがビルド・dev両方でデフォルト化され、大規模モノレポでもHMRとプロダクションビルド時間が短縮された一方、一部のWebpack専用プラグインに依存する構成は移行時に注意が必要。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge MiddlewareとEdge Functionsの境界が曖昧になり、Vercelは「Fluid Compute」モデルでコールドスタートを抑えつつ、リクエストごとの課金を実行時間ベースに最適化する方向に進んでいる。同時実行リクエストをインスタンス間で束ねることでコンピュートコストを大幅に削減できる点が実用上のメリット。

- **ポイント2:** Edge Runtime（V8 isolateベース）はNode.js APIの対応範囲が年々広がっているが、依然としてファイルシステムアクセスや一部のネイティブモジュールに制約がある。重い処理（画像変換、PDF生成など）はEdgeではなくServerless/Node Functionsに分離し、Edgeは認証チェックやリダイレクト、A/Bテストなど軽量なロジックに限定するのが鉄則。

- **ポイント3:** リージョン選択戦略が重要で、データベースとの往復が多い処理をEdgeに置くとレイテンシがむしろ悪化するケースがある。DBがリージョン固定（例: us-east-1）なら、Edge Functionの`regions`設定をDB近接リージョンに固定するか、Read Replica/Cache（Vercel KVやUpstash Redis）をEdgeから直接読む構成にすべき。

- **ポイント4:** ISR/On-Demand RevalidationとEdge Cachingの組み合わせが2026年も主流で、`stale-while-revalidate`を活用したEdge Configによる動的フラグ配信（フィーチャーフラグ、メンテナンスモード切替）がミリ秒単位で反映できる点が強み。sumitsugiのような物件公開/非公開ステータス切り替えにも応用可能。

- **ポイント5:** 観測性（Observability）の強化が進み、Vercelのネイティブログ・トレーシングだけでなく、OpenTelemetry統合でEdge Function内のスパンを外部APM（Datadog, Sentry等）に送れるようになった。本番でのレイテンシ劣化やタイムアウトの原因特定にはこの統合が必須。

### 10. TypeScript type safety patterns 2026

- **型推論とブランド型の活用:** Template Literal Types や Branded Types（`type UserId = string & { __brand: 'UserId' }`）を使い、プリミティブ型の取り違えをコンパイル時に検出するパターンが標準化してきている。

- **Zodなどによるランタイム検証との統合:** `z.infer<typeof schema>` でスキーマから型を自動生成し、コンパイル時の型とランタイムの検証ロジックを単一ソースで管理する手法が、APIバウンダリやフォーム入力で定着している。

- **`satisfies` 演算子の普及:** TypeScript 4.9以降の `satisfies` を使うことで、型の widening を防ぎつつ型推論の精度を保てるため、設定オブジェクトや定数定義での採用が増えている。

- **Exhaustiveness Checkingの徹底:** Union型やStatus型（例: `'draft' | 'public'`）に対して `never` 型を使った網羅性チェックを行い、新しいケース追加時のコンパイルエラーで漏れを防ぐパターンが、状態管理の必須プラクティスになっている。

- **型のみのimport分離:** `import type` を明示的に使い分けることで、バンドルサイズの最適化とランタイム依存の混入防止を両立させる運用が、ESLintルール（`consistent-type-imports`）と組み合わせて広がっている。
