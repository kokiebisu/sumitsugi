# CTO Knowledge - 2026-06-11

## Daily Update (2026-06-11)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチはサーバーコンポーネントに集約し、インタラクティブな部分のみ `"use client"` を使う設計が2026年のベストプラクティスとなっている。

- **Partial Prerendering (PPR) の本番適用:** Next.js 15+で安定化したPPRにより、静的シェルを即座に配信しつつ動的コンテンツをストリーミングする「ハイブリッドレンダリング」が標準戦略となり、TTFBとLCPの両方を改善できる。

- **`after()` APIによる非クリティカル処理の分離:** レスポンス返却後にログ記録・分析送信・キャッシュウォームアップを実行する `after()` が実用段階に入り、リクエストのクリティカルパスを細くすることでP99レイテンシが大幅改善する。

- **Turbopackの本番使用:** Next.js 15.3でTurbopackがビルドにも対応し、大規模プロジェクトでのビルド時間が従来比30-50%短縮。CI/CDパイプラインのコスト削減にも直結する。

- **`<Image>`と`<Script>`の自動最適化を信頼する:** LCPに直結する画像は `priority` フラグと `sizes` を正確に設定し、サードパーティスクリプトは `@next/third-parties` 経由で読み込むことで、手動最適化より確実にCore Web Vitalsを改善できる。

### 2. React Server Components streaming 2026

- **Suspense境界とStreamingの成熟:** RSCとSuspenseを組み合わせたProgressive Streamingが本番環境で標準化し、TTFBを維持しながらFCPを大幅に改善できるアーキテクチャパターンが確立された。

- **PPR（Partial Prerendering）の実用化:** Next.js 15+でPPRが安定し、静的シェルを即座に配信しつつ動的コンテンツをストリーミングする手法が主流となり、CDNキャッシュとダイナミクスの両立が現実的になった。

- **Server Actionsとの統合深化:** Server Actionsがフォーム送信だけでなく、楽観的UI更新とストリーミングレスポンスを組み合わせた非同期UXパターンの中核に位置づけられ、クライアントJSバンドルの削減に直結している。

- **キャッシュ戦略の複雑化:** `fetch`キャッシュ・Router Cache・Full Route Cacheの三層構造を正しく理解しないと予期せぬstaleデータが発生するため、`revalidatePath`/`revalidateTag`の粒度設計がアーキテクチャ上の重要な意思決定になっている。

- **エッジランタイムとの相性問題:** Streaming RSCはNode.jsランタイムでは安定しているが、Edge Runtimeでは長時間ストリームのタイムアウト制限があり、ユースケースに応じたランタイム選択（`runtime: 'nodejs'` vs `'edge'`）が設計初期に必要。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの実用的優位性:** フルスタックTypeScriptプロジェクトではtRPCがデファクト化しつつあり、スキーマ定義不要でエンドツーエンドの型安全性を実現できるため、Next.js App Routerとの相性が特に良い。

- **GraphQLの適用領域の絞り込み:** GraphQLは複数クライアント（モバイル・Web・サードパーティ）が異なるデータ要件を持つ場合に依然有効だが、単一クライアント構成では過剰設計になりやすく、導入コストに見合わないケースが増えている。

- **REST + OpenAPI の堅牢な生存:** パブリックAPI・外部連携ではRESTとOpenAPI 3.1が標準であり続ける。Zod→OpenAPIの自動生成ツール（`zod-openapi`等）により型安全性を確保しつつ仕様書も自動化できる点で実用性が再評価されている。

- **Server Actions / RPC-over-HTTP の台頭:** Next.js Server ActionsやHono RPCのように、明示的なAPIレイヤーを設けずサーバー関数を直接呼び出すパターンが普及し、小〜中規模アプリではAPIエンドポイント設計そのものが不要になるケースが増えている。

- **プロトコル選定の実用基準:** 2026時点の判断軸は「誰がAPIを消費するか」に尽きる——内部フルスタックならtRPC、複数異種クライアントならGraphQL、外部公開・他社連携ならREST+OpenAPI、という棲み分けを明確にするだけでアーキテクチャの複雑性を大幅に削減できる。

### 4. serverless edge computing 2026

- **エッジWASM実行の本格普及:** WebAssemblyがエッジランタイムの標準となり、Cloudflare Workers・Fastly Compute等でコールドスタートがほぼゼロに。言語非依存の実行環境が開発者体験を大幅に向上させている。

- **AI推論のエッジオフロード:** LLMの軽量モデル（1B〜7Bパラメータ）がエッジノードで動作可能になり、レイテンシとプライバシーの両立が実現。クラウド送信コストの削減とリアルタイム応答が同時に得られる。

- **分散データ整合性の課題が顕在化:** エッジでの状態管理（CRDTs、eventual consistency）が設計の主戦場に。Durable ObjectsやPartyKitのようなステートフルエッジプリミティブが普及し始めているが、トランザクション設計の複雑さは依然高い。

- **観測可能性（Observability）のギャップ:** 数百〜数千のエッジロケーションにわたる分散トレーシングが困難で、デバッグコストが増大。OpenTelemetryのエッジ対応が進んでいるが、従来のAPMツールとの統合はまだ発展途上。

- **コスト構造の再評価が必要:** リクエスト単価は安価だが、エッジ特有の課金モデル（CPU時間・データ転送・ロケーション数）によりスパイクトラフィック時の請求が予測困難。アーキテクチャ設計段階からコストシミュレーションを組み込む運用が必須。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準採用:** FIDO2/WebAuthn ベースのパスキーがパスワードレス認証の主流となり、フィッシング耐性と UX の両立が実現している。新規プロダクトではパスワード認証をレガシー扱いとし、パスキーをデフォルトにすべき。

- **トークンライフタイムの短縮化:** アクセストークンの有効期限を15分以下に設定し、リフレッシュトークンのローテーションを必須とする設計が標準化されている。漏洩時の爆発半径を最小化するためのゼロトラスト原則の実践。

- **デバイスバインディングと継続的検証:** セッション開始時だけでなく、操作中も端末フィンガープリントや行動シグナル（タイピングパターン等）で継続的にリスクを評価する CAEP（Continuous Access Evaluation Protocol）の採用が広がっている。

- **MFAのフィッシング耐性要件:** SMS/TOTP ベースの MFA はリアルタイムフィッシングに脆弱であり、ハードウェアキーまたはパスキーのみを「強 MFA」として扱う規制・標準が増加。特に金融・医療領域では必須要件になりつつある。

- **サプライチェーン認証リスクへの対応:** OAuth クライアントの定期的な棚卸し、スコープの最小権限原則の徹底、サードパーティ SDK の依存関係監査が不可欠。`npm audit` や Dependabot だけでなく、ランタイム時のトークン権限検証も組み込むべき。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x の Edge Runtime 対応成熟:** Prisma は Cloudflare Workers・Vercel Edge Functions での動作が安定し、Supabase の `connection_limit` 問題も Prisma Accelerate（接続プーリング）で解消できるようになった。エッジ環境でのフルスタック構成が現実的な選択肢になっている。

- **Supabase の Row Level Security (RLS) を Prisma と組み合わせる設計パターン:** RLS はデータベース層でのマルチテナント分離に強力だが、Prisma は RLS を透過的に扱えないため、`SET LOCAL role` や `set_config` を使ったセッション変数の受け渡しをミドルウェア層で明示的に実装する必要がある。

- **Supabase Realtime + Prisma の使い分け:** リアルタイム更新は Prisma ではなく Supabase の Realtime（PostgreSQL の logical replication ベース）を直接使う設計が主流。Prisma は書き込み・複雑なクエリ担当、Realtime はサブスクリプション担当という役割分担が明確になってきた。

- **型安全な DB スキーマ管理の一元化:** `prisma/schema.prisma` を single source of truth にして、Supabase の型生成（`supabase gen types`）との二重管理を避けるアーキテクチャが推奨される。2026年現在、Prisma の `prisma db pull` + CI での自動型生成が最もメンテナンスコストが低い。

- **接続プーリングは必須インフラ:** Supabase の PostgreSQL はデフォルト接続数に上限があり、Next.js のサーバーレス環境では接続枯渇が起きやすい。Supabase 内蔵の PgBouncer (Supavisor) か Prisma Accelerate を必ず挟む構成がプロダクション要件になっている。

### 7. WebAssembly Rust performance 2026

- **WASI 0.2 / Component Modelの本格普及:** 2026年時点でWASI Preview 2とComponent Modelが安定化し、RustのWasmコンポーネントがNode.js・Deno・Cloudflare Workersをまたいでポータブルに動作するようになった。マイクロサービス間の言語非依存な型安全インターフェースとして実用レベルに達している。

- **WasmGCとRustの相互運用:** WasmGC命令セットの普及により、RustのWasmバイナリがGC付き言語ランタイム（Swift・Kotlin）と効率的にデータ共有できるようになった。Rustの`wasm-bindgen`エコシステムもこの変化に追従し、FFIオーバーヘッドが大幅に削減されている。

- **SIMD/マルチスレッドWasmの実用化:** Relaxed SIMDとShared Memory（Atomics）の対応ブラウザが揃い、RustのSIMD intrinsicsがWasm上でほぼネイティブ同等のスループットを発揮できる。画像処理・暗号・LLM推論の軽量ワーカーとしての採用が加速している。

- **ビルドサイズの課題と`wasm-opt`の進化:** Rustのバイナリサイズ問題は`wasm-opt`（Binaryen）の最適化レベル向上と`cargo-component`の改善で緩和されつつあるが、依然としてGoやSwiftと比べて大きい。プロダクション採用では`no_std` + `alloc`クレートの組み合わせで100KB以下に抑えるアーキテクチャ設計が重要。

- **Edge RuntimeにおけるRust Wasmの定番化:** Fastly Compute・Cloudflare Workers・Vercel Edge FunctionsでRust製Wasmが第一級サポートとなり、コールドスタート0ms・メモリ分離の両立が評価されている。新規Edgeサービスの選定ではRust+Wasmがデファクトの選択肢になりつつある。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** デフォルトでServer Componentsを使用し、インタラクティブな部分のみ`'use client'`に分離することで、バンドルサイズを最小化しつつTTFBを最適化する。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的コンテンツを同一ルートで共存させるPPRが安定化し、`<Suspense>`境界の設計がパフォーマンスの核心になっている。

- **Server Actions によるAPI Routes の置き換え:** フォーム送信やデータ変更にServer Actionsを使うことで、別途APIエンドポイントを設けず型安全なサーバー実行が実現できる。ただしCSRF対策とrate limitingは依然として必要。

- **キャッシュ戦略の明示化:** Next.js 15以降、`fetch`のデフォルトキャッシュが`no-store`に変わったため、`revalidate`や`cache`オプションを意図的に指定する設計が必須となった。

- **Turbopackの本番利用:** Turbopackが安定化し、大規模プロジェクトでのHMR速度が劇的に改善。ただし一部のwebpack固有プラグインとの互換性は要検証。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge RuntimeからNode.js Runtimeへの選択的移行:** Edge Functionsは低レイテンシに優れるが、Node.js APIの制約が多い。2026年時点では「全部Edge」より、認証・地理判定はEdge、重い処理はNode.js Runtimeと使い分けるハイブリッド戦略が主流。

- **ポイント2: Fluid Computeによるコールドスタート問題の実質的解消:** VercelのFluid Computeアーキテクチャにより、従来のサーバーレス課題だったコールドスタートが大幅に緩和。Edge Functionsとの組み合わせで、グローバル分散と温かいインスタンス維持を両立できる。

- **ポイント3: ISR（Incremental Static Regeneration）とEdgeキャッシュの連携最適化:** `stale-while-revalidate`パターンをEdgeレイヤーで適切に設定することで、動的コンテンツでも静的サイト並みのTTFBを実現。`Cache-Control`ヘッダーとVercelのEdgeキャッシュ設定の理解が必須。

- **ポイント4: Middleware最適化——matcher設定の精度が性能を左右する:** `middleware.ts`のmatcher設定が粗いと全リクエストにオーバーヘッドが発生。静的アセット（`/_next/static`等）を確実に除外し、必要なパスのみに絞ることで、実測で20-40%のレイテンシ改善ケースも報告されている。

- **ポイント5: Edge ConfigとKV Storageによるリモート設定の低レイテンシ化:** Feature flagsや設定値の取得にEdge Configを活用することで、外部APIコールをゼロに抑えつつグローバルに一貫した設定配信が可能。DBへのラウンドトリップを排除できるのがアーキテクチャ上の大きな利点。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded Typesが広く採用され、プリミティブ型の混在バグを根本から防ぐパターンが定着しつつある。

- **satisfies 演算子の活用:** TypeScript 4.9以降の `satisfies` が「型チェックしつつ推論も保持する」用途で不可欠になり、`as` キャストの乱用を排除するコードベースが増加している。

- **Template Literal Types による API 契約:** エンドポイントパスやイベント名を `type Route = '/users' | '/users/${string}/profile'` のように型で表現し、実行前に不正なパス文字列を検出できるようになった。

- **Zod + tRPC による型の一気通貫:** バックエンドのスキーマ定義からフロントエンドの型まで自動伝播させる設計が主流化し、「型とバリデーションの二重管理」というアンチパターンが撲滅されつつある。

- **Exactness（余剰プロパティ）の厳格化:** `NoExtraProperties<T>` ユーティリティや `declare function fn<T extends Exact<Schema, T>>` パターンで、余剰フィールドの混入を型レベルで封じるアプローチが本番採用され始めている。
