# CTO Knowledge - 2026-06-07

## Daily Update (2026-06-07)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチロジックをサーバーコンポーネントに移行する。`"use client"` の境界を慎重に設計し、インタラクティブ部分だけをクライアントに残すことが2026年のベースライン。

- **Partial Prerendering (PPR) の本番投入:** 静的シェルを即座に配信しつつ動的コンテンツをストリーミングするPPRが安定化。`experimental.ppr` を有効にするだけでTTFBとLCPの両立が実現できる。

- **`<Image>` / `<Font>` の自動最適化を超えた細粒度制御:** `sizes` プロパティと `priority` フラグの適切な設定、さらに `fetchPriority="high"` の明示的指定でLCPヒーロー画像のスコアを大幅改善できる。

- **Server Actions によるウォーターフォール排除:** `fetch` のキャッシュ戦略（`revalidate` / `tags`）と組み合わせたServer Actionsで、クライアント→API往復を削減。`cache()` 関数によるリクエスト重複排除も標準パターンになっている。

- **Edge Runtime vs Node.js Runtime の使い分け:** ミドルウェア・A/Bテスト・認証ゲートはEdgeで処理してコールドスタートを抑え、重い計算やDB接続はNode.js Runtimeに委ねる二層設計が推奨アーキテクチャ。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の本格採用:** Next.js 15以降でPPRが安定化し、静的シェルを即座に配信しつつ動的コンテンツをストリーミングする設計が標準的なパターンになっている。TTFBとLCPの両立が現実的になった。

- **Suspense境界の設計が競合優位に直結:** `<Suspense>`の粒度をコンポーネント単位で適切に設計することで、ユーザーが「待たされている感覚」を大幅に削減できる。粗すぎると旧来のSSRと変わらず、細かすぎるとハイドレーションコストが増大する。

- **Server Actions + Optimistic UIの組み合わせが主流化:** `useOptimistic`とServer Actionsを組み合わせることで、サーバーラウンドトリップを隠蔽しながらリアルタイム感のあるUIを実現できる。クライアント状態管理ライブラリへの依存が減少傾向。

- **Edge Runtimeでのストリーミング制約に注意:** Vercel EdgeやCloudflare Workersでのストリーミングは、Node.js Runtimeと異なり一部APIが使えない。`runtime = 'edge'`に移行する際は実行環境の互換性マトリクスを事前に確認することが必須。

- **キャッシュ戦略の再設計が必要:** Next.js 15でデフォルトキャッシュ動作が変更され、`fetch()`がデフォルトでキャッシュされなくなった。ストリーミングと`unstable_cache`/`revalidateTag`を組み合わせた細粒度キャッシュ設計を明示的に行わないと、パフォーマンスが劣化するリスクがある。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全フルスタック:** 2026年時点でtRPCはNext.js/TypeScriptスタックにおける事実上の標準に近づいており、クライアント・サーバー間の型共有によってランタイムエラーを大幅に削減できる。スキーマ定義の二重管理が不要なため、小〜中規模チームの開発速度が顕著に向上する。

- **GraphQLの役割の絞り込み:** GraphQLは「複数クライアント（モバイル・Web・パートナーAPI）が異なるデータ形状を要求する」ユースケースに特化しつつあり、単一フロントエンドへの採用はオーバーエンジニアリングとみなされる傾向が強まっている。Federation v2によるマイクロサービス統合には依然として強みがある。

- **RESTは死なず、OpenAPI 3.1で再強化:** REST + OpenAPI 3.1の組み合わせはエンタープライズ・外部公開APIで引き続き主流であり、`zod-to-openapi`等のツールでtRPCライクな型安全性をRESTでも実現できる。AIエージェントがOpenAPIスキーマを直接消費するユースケースが増え、REST仕様の価値が再評価されている。

- **Protocol Buffersとバイナリプロトコルの復権:** gRPCおよびConnect（gRPC互換のHTTP/1対応プロトコル）がマイクロサービス間通信で採用増加。JSONより数倍高速なシリアライゼーションとスキーマ強制が、レイテンシ敏感なサービスで評価されている。

- **サマリ — プロジェクト規模で使い分け:** 社内フルスタック→tRPC、外部公開API→REST+OpenAPI、複数クライアント統合→GraphQL Federation、高スループット内部通信→gRPC/Connect。2026年は「一択」ではなく「文脈依存の選択」が成熟した判断とされている。

### 4. serverless edge computing 2026

- **エッジでのAI推論が主流化:** 2026年時点でWebAssembly（Wasm）ランタイムの成熟により、LLMの軽量モデル（<1B params）をエッジノードで直接実行するパターンが定着。レイテンシを50ms以下に抑えながらAI機能を提供できる。

- **V8 IsolatesからWasmへの移行加速:** CloudflareやFastlyがWasmファーストのエッジ実行環境に移行し、言語の選択肢がJavaScript/TypeScript以外（Rust、Go）にも広がった。コールドスタート問題がほぼ解消されている。

- **エッジDBの実用化:** Cloudflare D1、Turso（libSQL）などのエッジネイティブなSQLiteベースのDBが本番環境で使われ始め、「エッジで状態を持てない」という制約が緩和。ただしグローバル整合性の設計は依然として重要。

- **オブザーバビリティがボトルネック:** 数百のエッジロケーションにまたがる分散トレーシングはまだ成熟途上。OpenTelemetryのエッジ対応が進んでいるが、デバッグコストが高く、本番投入前に可観測性戦略を設計に組み込むことが必須。

- **コスト構造の再評価が必要:** リクエスト数課金モデルはトラフィックが予測困難なアプリで想定外のコスト増を招く。2026年現在、エッジ＋オリジンのハイブリッドアーキテクチャ（重い処理はオリジンに逃がす）が現実解として定着している。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準採用:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の主流となり、フィッシング耐性が根本的に向上。新規サービスではパスワード認証を廃止し、パスキーをデフォルトにすべき段階に入っている。

- **トークンの短命化とDPoP（Proof of Possession）:** JWTの有効期限を5〜15分に短縮し、DPoPでトークンをクライアントの鍵ペアに束縛することでトークン窃取攻撃を無力化。リフレッシュトークンのローテーションも必須。

- **継続的認証（Continuous Authentication）:** ログイン時の一点突破ではなく、行動バイオメトリクスやリスクスコアリングでセッション全体を監視。異常検出時に段階的な再認証を要求するアーキテクチャが標準化されつつある。

- **サプライチェーン攻撃対策としてのOIDCフェデレーション:** OAuth/OIDCプロバイダー自体が攻撃対象となるリスクが顕在化。複数のIdPを束ねるフェデレーション層を設け、単一プロバイダー依存を排除することが大規模サービスの必須要件になっている。

- **秘密情報のゼロ知識管理:** シークレット（APIキー・証明書）をコードやenvファイルから完全排除し、HashiCorp VaultやAWS Secrets Managerの動的シークレット発行を徹底。ローテーションの自動化なしに「管理している」とは言えない時代。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6のEdge Runtime対応:** PrismaはEdge環境（Cloudflare Workers、Vercel Edge Functions）での動作が安定し、Supabaseの接続プーリング（Supavisor）と組み合わせることでサーバーレス構成でのコネクション枯渇問題がほぼ解消された。

- **Supabase Branchingによるスキーマ管理の変革:** Preview環境ごとにDBブランチを作成できるため、PRベースの開発フローとスキーマ変更が完全に統合可能。Prisma Migrationsとの組み合わせで「コードとスキーマを同一PRで管理」が現実的になった。

- **Row Level Security（RLS）との設計摩擦:** PrismaはRLSを直接サポートしないため、Supabaseのセキュリティモデルとの整合性確保が設計課題になる。`set_config('request.jwt.claims', ...)`をミドルウェアで注入するパターンが主流だが、ORMレイヤーとのギャップを常に意識した設計が必要。

- **Prisma Accelerateによるグローバルキャッシュ:** Prisma Accelerateのエッジキャッシュ機能により、Supabaseの地理的制約（単一リージョン）を補完できる。読み取り負荷の高いクエリをAccelerate経由でキャッシュし、Supabaseへの直接アクセスを削減するアーキテクチャが有効。

- **型安全性とZodの統合強化:** Prisma Zodジェネレーター（`zod-prisma-types`）を使ってスキーマからバリデーション型を自動生成するパターンが定着。DBスキーマ変更が即座にAPI境界のバリデーションに反映される「Single Source of Truth」構成が2026年のベストプラクティス。

### 7. WebAssembly Rust performance 2026

- **コンパイル最適化の成熟:** RustのWASM向けコンパイルチェーン（`wasm-opt`、`wasm-pack` 3.x）が2026年に大幅に成熟し、バイナリサイズが従来比30-40%削減可能になった。ランタイムオーバーヘッドもネイティブコードの5%以内に収まるケースが増加している。

- **SIMD・スレッドサポートの普及:** WebAssembly SIMD命令とShared Memory/Atomicsがメジャーブラウザで安定稼働し、画像処理・機械学習推論でRust+WASMがJSの3-8倍のスループットを達成できるユースケースが実用段階に。

- **Component Model（WASI 0.3）によるインターオペラビリティ:** WASIのComponent ModelとWIT（WebAssembly Interface Types）により、Rustで書いたWASMモジュールをNext.jsのEdge RuntimeやCloudflare Workersに組み込む際のFFIオーバーヘッドが実質ゼロに近づいた。

- **Streaming Compilationとキャッシュ戦略:** V8/SpiderMonkeyのStreaming Compilationにより、初回ロード時間のボトルネックが解消されつつある。ただし大規模WASMバイナリ（5MB超）ではCode Splitting戦略が依然として必要で、`wasm-bindgen`の`split-chunks`オプション活用が実践的アプローチ。

- **サーバーサイド（WASI）での採用加速:** Next.jsのEdge RuntimeやVercel/Cloudflareがwasm実行を正式サポートしたことで、Rustで書いた計算集約型ロジック（バリデーション・変換処理）をEdgeに配置するパターンが標準化。レイテンシ敏感な処理はWASMモジュール化を検討する価値あり。

### 8. Next.js App Router patterns 2026

- **Partial Pre-rendering (PPR) の本格活用:** Next.js 15以降でPPRが安定版となり、静的シェルと動的コンテンツを同一ルートで混在させるパターンが主流に。`<Suspense>`境界の設計がパフォーマンスの鍵となる。

- **Server Components ファースト設計:** デフォルトをServer Componentsとし、インタラクションが必要な最小単位にのみ`'use client'`を付与する「Islands Architecture」的アプローチが定着。クライアントバンドルサイズの削減に直結する。

- **Server Actions によるAPI層の簡素化:** `'use server'`関数でフォーム処理・データ変更を直接実装するパターンが広まり、REST APIエンドポイントを別途作らないケースが増加。ただしバリデーション（Zod等）は必須。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** Next.js 15で導入された`use cache`により、関数・コンポーネント単位でのキャッシュ戦略が明示的に記述可能に。`revalidateTag`との組み合わせでISR的な更新制御が容易になった。

- **Turbopack の本番利用:** Next.js 15.1以降でTurbopackがデフォルトビルドツールとなり、大規模プロジェクトでのビルド時間が50-80%短縮。webpack設定の移行コストを早めに評価しておくことを推奨。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタートの実質ゼロ化:** V8 Isolatesベースの実行モデルにより、従来のLambda比で起動レイテンシが大幅削減。2026年時点では地域ルーティングの精度も向上し、ユーザーに最近傍のエッジノードを自動選択できる。

- **ストリーミングレスポンスとAI統合:** Edge FunctionsでのStreaming APIサポートが安定化し、LLMレスポンスのTTFBを最小化するパターンが標準化。`ReadableStream`を使ったプログレッシブUIが本番グレードで運用可能。

- **バンドルサイズ制限への対策が必須:** Edge Runtimeは~4MBのサイズ制限があり、`node_modules`の軽量化（barrel imports排除、tree-shaking確認）が重要。`@next/bundle-analyzer`でEdge向けバンドルを定期計測すること。

- **Edge ConfigとKV StorageでState管理:** `@vercel/edge-config`や`@vercel/kv`をエッジで直接参照することで、DBラウンドトリップなしにA/Bフラグやセッション情報を取得可能。レイテンシを数十msオーダーで削減できる。

- **MiddlewareはRoute Handlersの前段として設計:** Next.js App RouterではMiddleware（Edge）→Route Handler（Node.js or Edge）の責務分離が鍵。認証チェック・リダイレクト・ロケール判定はMiddlewareに集約し、Route Handlerを薄く保つことでコールドスタートリスクを分散させる。

### 10. TypeScript type safety patterns 2026

- **Branded Types の主流化:** `type UserId = string & { readonly __brand: 'UserId' }` パターンが標準化し、プリミティブ型の取り違えによるバグをコンパイル時に完全排除できるようになった。

- **`satisfies` 演算子の活用拡大:** 型推論を保ちながら型チェックを行える `satisfies` が、設定オブジェクトやルーティング定義で広く使われ、`as const` との組み合わせで型安全性が大幅に向上した。

- **Template Literal Types による API 契約:** `type Route = \`/api/${string}\`` のようなパターンで URL・イベント名・CSS クラス名をすべて型で縛り、ランタイムエラーをゼロに近づける設計が定着しつつある。

- **Variance Annotations（`in`/`out`）の明示:** TypeScript 5.x 以降の `in`/`out` 修飾子を使い、共変・反変を明示することでジェネリクスの型安全性を強化し、大規模なモノレポでのコンパイルパフォーマンスも改善された。

- **`using` キーワードと Explicit Resource Management:** TC39 の Resource Management 仕様が TypeScript に取り込まれ、DB 接続・ファイルハンドルなどのリソース解放を型システムで保証できる構造が実用段階に入った。
