# CTO Knowledge - 2026-10-30

## Daily Update (2026-10-30)

### 1. Next.js performance optimization 2026

**ポイント1: Partial Prerendering (PPR) の本格運用:** Next.js 15以降で導入されたPPRがNext.js 16で安定版となり、静的シェルと動的コンテンツを1つのページ内で組み合わせて、TTFBを大幅に短縮しつつパーソナライズ要素も即時配信できる。sumitsugiの物件一覧ページのような「静的なレイアウト＋動的な空室状況」構成に適している。

**ポイント2: React Server Components のキャッシュ戦略最適化:** `use cache` ディレクティブとファイングレインなキャッシュタグ管理により、DBクエリ結果を関数単位でキャッシュし、再検証（revalidate）を細かく制御できるようになった。物件データのような更新頻度が低い情報と、空室状況のような頻繁に変わる情報を分離してキャッシュ設計することが重要。

**ポイント3: Turbopackのビルド・devサーバー高速化:** Turbopackが本番ビルドでも安定し、Webpackと比較してビルド時間が大幅短縮。大規模なコードベース（sumitsugiのようにpropertiesやlistingなど多数のルートを持つ構成）ほど恩恵が大きく、`bun run build`の時間短縮に直結する。

**ポイント4: 画像・フォント最適化のAVIF/WebP自動化とエッジ配信:** `next/image`のAVIF対応強化とCDNエッジでのオンデマンド変換により、物件写真が多いUIでのLCP（Largest Contentful Paint）改善に効果的。モバイル中心のAirbnb風UIでは特に重要な指標。

**ポイント5: Streaming SSR + Suspense境界の粒度設計:** ページ全体ではなくコンポーネント単位でSuspense境界を細かく設計し、ユーザー体験上重要な部分（例: 物件の基本情報）を先に表示し、レビューや関連物件などは後から段階的にストリーミングする設計が定番化している。

### 2. React Server Components streaming 2026

- **部分的ハイドレーションとSelective Streaming:** RSCのストリーミングは単なる「遅いコンポーネントを後で送る」から、クライアント側で優先度の高いインタラクティブ要素だけを先にハイドレーションする方向に進化している。初期表示速度と操作可能になるまでの時間（TTI）を分離して最適化できる点が実務上大きい。

- **Suspense境界の粒度設計がパフォーマンスの肝:** 境界を細かく切りすぎるとウォーターフォールが増え、粗すぎると全体がブロックされるため、データ取得の依存関係に合わせた境界設計がボトルネック対策の中心的な作業になっている。

- **Server ActionsとStreamingの統合が標準化:** フォーム送信後の楽観的UI更新とストリーミングされた再検証（revalidate）が組み合わさり、ページ遷移なしでサーバー状態を反映するパターンが定着してきた。sumitsugiの物件一覧・詳細ページのような動的データ表示に適用しやすい。

- **エッジランタイムとの相性:** RSCストリーミングはエッジでの部分レンダリングと組み合わせることでTTFBを大幅に短縮できるが、Node専用APIへの依存があると実行できないため、データ取得層の互換性チェックが必要になる。

- **キャッシュ戦略の複雑化:** ストリーミングHTMLとRSCペイロードのキャッシュ層が分離し、`'use cache'`ディレクティブや再検証タグの設計を誤るとドラフト物件が公開済みキャッシュに混入するような事故につながるため、`status: 'draft' | 'public'`のような状態分岐がある箇所は特に注意が必要。

### 3. API design REST GraphQL tRPC 2026

- **統合プロトコルの時代:** 2026年はREST/GraphQL/tRPC「どれか一つ」ではなく、内部BFF層はtRPC（型安全・ゼロコード生成）、外部パートナー向けはREST/OpenAPI、複雑なクライアント要件にはGraphQLと用途別に併用する構成が主流化。sumitsugiのような小規模チームでは、まずtRPCで型安全な内部API層を固め、将来的な外部公開時にREST/GraphQLゲートウェイを追加する段階的アプローチが効率的。

- **tRPCの型安全性がフロント/バックエンド分離を高速化:** Next.js App Router + TypeScriptの構成ではtRPCがコード生成不要で型が自動伝播するため、スキーマ変更時のバグをコンパイル時に検知できる。前の住人/次の住人間のマッチングロジックなど頻繁に変更が入る機能では、tRPCの恩恵が特に大きい。

- **GraphQLは「読み取りが複雑」な場面に限定採用:** 物件一覧・フィルタリング・検索のような多条件クエリではGraphQLのN+1問題対策（DataLoaderパターン）とコストが依然ネック。sumitsugiの物件検索機能のような単純なフィルタ主体のUXならREST+クエリパラメータで十分、過剰設計を避けるべき。

- **エッジでのAPI実行とストリーミングレスポンスが標準化:** Next.js 16のServer ActionsやEdge Runtimeとの統合で、API Routes自体を書かずにServer Componentsから直接データ取得する設計が増加。tRPCもReact Server Components対応が進み、クライアント/サーバー境界のAPI層が薄くなる傾向。

- **認証・レート制限はAPI層に関わらずZodでの入力検証が必須:** プロトコルを問わず、システム境界（API Routes、Server Actions）でのZodスキーマ検証とレスポンスでの機密情報漏洩防止が2026年のセキュリティ基準として定着。CLAUDE.mdの「Input validation: Zodスキーマ使用」方針と完全に整合する。

### 4. serverless edge computing 2026

- **ポイント1: WASMランタイムの主流化** Cloudflare WorkersやDenoなどのエッジプラットフォームがWasmベースの実行環境を標準化し、コールドスタートがミリ秒未満まで短縮されている。V8 isolateに比べて言語非依存性が高く、Rust/Goで書いた処理をエッジに直接デプロイできる点が開発効率を大きく向上させる。

- **ポイント2: エッジでのステートフル処理の実用化** Durable Objects（Cloudflare）やエッジKVストア、SQLiteベースの分散DB（Turso, D1）の成熟により、従来は中央サーバー必須だったセッション管理や在庫カウントもエッジで完結できるようになった。sumitsugiのような物件検索・予約フローでは、ユーザーに最も近いリージョンで整合性のある状態管理ができることがレイテンシ改善の鍵になる。

- **ポイント3: AI推論のエッジシフト** 小型LLM（量子化モデル）やEmbedding生成をエッジ側で実行する構成が増え、中央のAPIコールを待たずに検索・レコメンド処理の一部をユーザー近傍で完結できるようになってきた。全処理をエッジに寄せる必要はないが、低レイテンシが要求される部分（画像最適化、入力検証、A/Bルーティング判定など）から段階的に移行するのが現実的。

- **ポイント4: Next.jsのエッジランタイム統合の深化** Next.js 16のMiddlewareやServer Actionsがエッジランタイムとの統合をさらに強化しており、Vercel/Cloudflare両方でのデプロイが前提になりつつある。ただしNode.js APIに依存するライブラリ（一部の画像処理やPDF生成）はエッジ非対応のままなので、機能ごとにランタイムを選別する設計判断が必要。

- **ポイント5: コスト構造の変化によるアーキテクチャ見直し** エッジのリクエスト課金モデルは「常時起動サーバー」よりも低トラフィック期のコストを抑えられる一方、高頻度アクセスのバッチ処理では従来型サーバーレス（Lambda等）より割高になるケースも出てきている。sumitsugiの規模感では、物件検索などバースト性のあるエンドポイントをエッジに、バッチ集計処理は従来型に残すハイブリッド構成が合理的。

### 5. authentication security best practices 2026

- **パスキー/WebAuthnへの全面移行:** パスワード+SMS OTPはフィッシング耐性が低く、2026年の実質的な業界標準はFIDO2準拠のパスキー。実装コストは初期のみで、サポート負荷とクレデンシャルスタッフィング被害を長期的に大幅削減できる。

- **セッション・トークン管理の厳格化:** JWTを長寿命で発行せず、短命アクセストークン＋リフレッシュトークンのローテーション、デバイスバインディング（DPoPやmTLS）を組み合わせる。盗難トークンの再利用窓を狭めることが侵害被害の最小化に直結する。

- **AI時代のフィッシング・ディープフェイク対策:** 生成AIによる精巧なフィッシングやソーシャルエンジニアリング（音声/動画含む）が増加しているため、知識ベース認証（秘密の質問など）は廃止し、デバイス証明や行動分析によるリスクベース認証を組み込むべき。

- **ゼロトラスト＋継続的検証:** ログイン時点の一発認証ではなく、IPレピュテーション・デバイス姿勢・異常操作検知を踏まえた継続的なセッション評価（Continuous Authentication）が前提になっている。特にsumitsugiのような個人情報（住所・内見情報）を扱うプラットフォームでは、取引完了までの間に再認証をトリガーする設計が有効。

- **サプライチェーン/サードパーティ認証の監査:** OAuthアプリやAPI連携のスコープを最小権限に絞り、定期的にアクセストークンの発行元・権限を棚卸しする。侵害の多くは直接の認証基盤ではなく連携先の過剰権限から発生している点に注意。

### 6. database architecture Prisma Supabase 2026

- **Edge-nativeなコネクション管理:** PrismaのEdge対応ドライバー（Prisma Accelerate等）とSupabaseのPgBouncer内蔵プーリングを組み合わせることで、Vercel Edge Functions上でもコールドスタート時のDB接続枯渇を防げる。Next.js 16のPPR/Edge Runtimeを使う場合、通常のPrisma Clientではなく接続プーリング対応版を必ず使うべき。

- **Row Level Security (RLS) をアプリ層バリデーションの代替にしない:** SupabaseのRLSはDB層の最終防衛線として有効だが、Prisma経由でアクセスする場合は`service_role`キーでRLSをバイパスしがちなので、Zodによる入力検証と組み合わせた二重防御が2026年のベストプラクティス。本プロジェクトの`'draft'|'public'`ステータス制御にも同様の考え方を適用すべき。

- **Prisma SchemaとSupabase Migrationの一本化:** `prisma migrate`とSupabase CLIのマイグレーションを並走させると差分ズレが起きやすいため、Prismaを単一のソースオブトゥルースにし、Supabase側はRLSポリシーとRealtime設定のみを管理する分離が定着しつつある。

- **pgvectorによるRAG/検索機能の統合:** 物件検索や「前の住人の暮らし」のレコメンドにベクトル検索を使う場合、SupabaseのpgvectorをPrisma経由で扱うにはネイティブ拡張のサポートが限定的なため、生SQL（`$queryRaw`）併用が現実的な選択。

- **コスト最適化:** SupabaseのBranching機能（開発用DBブランチ）とPrismaのマイグレーション履歴を連携させることで、PRごとに独立したDB環境を低コストで用意できる。CI/CDでのE2Eテスト環境分離に有効。

### 7. WebAssembly Rust performance 2026

- **WASM GCとコンポーネントモデルの成熟:** WASI 0.3とComponent Modelの実用化が進み、Rustで書いたWASMモジュールを言語を問わず組み合わせられるようになってきた。ブラウザ外（サーバーレス、エッジ）での採用判断材料として注視する価値がある。
- **SIMD128とマルチスレッド対応の標準化:** wasm-bindgen/wasm-pack経由でSIMDとWeb Workers連携が安定し、画像処理や物理演算などCPU負荷の高い処理をネイティブの70-90%程度の速度でブラウザ実行できるようになった。
- **バイナリサイズ最適化がボトルネック化:** `wasm-opt`やLTO、`opt-level = "z"`設定での縮小は限界があり、Rust std依存を減らす`no_std`運用やtree-shakingツールチェーンの選定が初期ロード速度に直結する。
- **コールドスタート改善でエッジ採用が加速:** Wasmtimeやwasmerのプリコンパイル（AOT）によりコールドスタートがミリ秒単位まで短縮され、Cloudflare WorkersやFastly Compute@Edge的な用途でRust+WASMがNode.jsベースの代替より優位に立つケースが増えている。
- **デバッグ・プロファイリング環境の追随不足:** パフォーマンス自体は向上している一方、ソースマップやDevTools上でのRustコードのデバッグ体験は依然ネイティブ開発に劣るため、採用前にチームの開発体験コストを見積もる必要がある。

### 8. Next.js App Router patterns 2026

- **ポイント1:** Partial Prerendering (PPR) が安定版となり、静的シェルと動的コンテンツを1ページ内で混在させるのが標準パターンに。ローディングUIを待たずに初期表示を高速化できるため、`loading.tsx`中心の設計から移行する価値が高い。
- **ポイント2:** Server Actionsの型安全性がZodバリデーションとの組み合わせでベストプラクティス化しており、フォーム送信時のクライアント/サーバー間の型不整合を防げる。`src/app`配下の新規フォームは全てServer Actions + Zod境界検証で統一すべき。
- **ポイント3:** `use cache`ディレクティブ（Next.js 15以降で導入、2026年時点で主流）によりキャッシュ戦略がコンポーネント単位で宣言的に記述可能になり、`fetch`オプションのキャッシュ指定より保守性が高い。データ取得層（`src/lib/data.ts`）のリファクタ候補。
- **ポイント4:** Route Groups + Parallel Routesを使った「レイアウト分割」が一般化し、物件詳細ページのようなタブ/モーダル併存UIをURL同期しながら実装できる。`properties/`配下の複雑なUIで検討の余地がある。
- **ポイント5:** RSC（React Server Components）境界でのバンドルサイズ監視が重要度を増しており、`"use client"`境界を最小化しないと2026年のベンチマーク基準（Core Web Vitals強化）で不利になる。認証系コンポーネント（`auth-context.tsx`周辺)は特に境界設計を見直す価値がある。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化:** Vercel EdgeランタイムはV8 isolateベースで起動が数ms単位のため、DBクライアント初期化をグローバルスコープでキャッシュし、リクエストごとの再接続コストを避けるのが前提になっている。

- **Streaming + Partial Prerendering(PPR)の組み合わせ:** Next.js 16ではPPRが安定し、Edge Functionsで静的シェルを即時返しつつ動的部分をストリーミングする構成がデフォルト戦略になっている。sumitsugiの物件詳細ページのようなSEO重視+動的価格表示には特に有効。

- **リージョン選択とデータ局所性:** Edge Functionsは地理的に分散実行されるため、Supabase/DB接続先リージョンとの往復レイテンシがボトルネックになりやすい。`regions`設定をDBリージョンに固定するか、Edge Config/KVでリード用データをエッジにレプリケートする判断が重要。

- **Node.js APIの一部解禁:** 2026年にかけてVercel EdgeランタイムはNode.js互換APIを拡充しており、以前はMiddlewareに書けなかった処理（一部のcrypto, Buffer操作など）がEdge側に書けるようになった。Middlewareでの認証チェックをEdgeに寄せられる範囲が広がっている。

- **コスト最適化:** Edge Functionsは実行時間課金だが、不要なミドルウェア全ルート適用（`matcher`未指定）はコストとレイテンシを両方悪化させる。`middleware.ts`の`matcher`を認証必須パス（`/account`, `/listing/new`等）に絞るのがsumitsugiのような小〜中規模トラフィックには実用的。

### 10. TypeScript type safety patterns 2026

- **構造的型チェックの強化:** TypeScript 5.x系で導入された`satisfies`演算子とconst型パラメータの活用が標準化し、型推論を保ちながら型安全性を保証するパターンが定着している。sumitsugiのような`'draft' | 'public'`といったUnion型の状態管理では、`satisfies`を使うことで余分な型アサーションなしに網羅性チェックが可能。

- **Zodなどのランタイム検証とのシナジー:** 静的型だけでは外部入力（API/フォーム）の安全性を保証できないため、Zodスキーマから型を推論する`z.infer<>`パターンが実質的な標準になっている。本プロジェクトのCLAUDE.mdでも「システム境界でのZod利用」を規定している通り、型定義とランタイム検証を単一ソースから生成することで二重管理を防げる。

- **Discriminated Unionによる状態管理の徹底:** `status: 'draft' | 'public'`のような単純なUnionから、関連フィールドを含むDiscriminated Unionに発展させることで、「存在しないはずの状態」をコンパイル時に排除するパターンが広がっている。型の変更時は全使用箇所をgrepする運用（本プロジェクトのルール通り）と組み合わせることで、リファクタリング時の取り残しを防止できる。

- **`noUncheckedIndexedAccess`と厳格な設定の標準化:** 配列・オブジェクトアクセスで`undefined`を型レベルで強制するコンパイラオプションの採用が広がり、null安全性のバグを事前に検出する文化が定着してきている。新規プロジェクトでは`strict: true`に加えてこのオプションを初期設定に含めるのが実用的。

- **型とテストの責務分離:** 型は「ありえない状態を排除する」ことに専念し、ビジネスロジックの正しさはテスト（TDD）で保証するという分業が明確化している。型安全性だけに依存せず、本プロジェクトのようにTDDサイクル（RED→GREEN→IMPROVE）と80%カバレッジを併用することで、型エラーでは捕まえられない振る舞いのバグを防げる。
