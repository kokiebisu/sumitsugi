# CTO Knowledge - 2026-04-02

## Daily Update (2026-04-02)

### 1. Next.js performance optimization 2026

- **React Server Components の徹底活用:** RSCをデフォルトとし、クライアントコンポーネントを本当にインタラクティブな部分に限定することで、バンドルサイズを劇的に削減できる。`'use client'` の境界を慎重に設計することが2026年の必須スキル。

- **Partial Prerendering (PPR) の本番導入:** Next.js 15以降で安定化したPPRにより、静的シェルを即座に返しつつ動的コンテンツをストリーミングできる。静的/動的の二択ではなく「両方同時」がデフォルト戦略になった。

- **`<Image>` と `next/font` の最適化継続:** LCP改善の最短経路は依然としてこの2つ。特に `sizes` prop の精緻な指定と `priority` の適切な設定は、Core Web Vitals スコアへの即効性が高い。

- **サーバーアクションのバンドル影響に注意:** Server Actions は便利だが、大量定義するとクライアントに不要な参照が漏れるリスクがある。`'use server'` ファイルを機能単位で分割し、ツリーシェイキングが効く構成を保つこと。

- **Edge Runtime vs Node.js Runtime の使い分け:** ミドルウェア・軽量APIはEdgeで低レイテンシを確保し、DB接続・重い処理はNode.jsランタイムに明示的に振り分ける。`export const runtime = 'nodejs'` の明示指定が予期せぬEdge実行を防ぐ。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化が鍵:** 2026年時点でRSCストリーミングの実運用知見が蓄積され、Suspense境界を細かく分割しすぎると「ウォーターフォール」を逆に誘発するケースが明らかに。コンポーネント単位ではなく「ユーザー体感の意味単位」で境界を設計することがベストプラクティス化している。

- **PPR（Partial Prerendering）との組み合わせが主流:** Next.js 15以降でPPRが安定化し、静的シェルを即座に返しつつ動的部分をストリームする構成が標準パターンに。TTFBとLCPの両立が現実的になった。

- **Server Actionsとの統合でフォーム処理のUXが向上:** ストリーミングレスポンス中にServer Actionsを挟むことで、送信→楽観的更新→確定の一連フローをネットワークラウンドトリップ最小で実現できる。

- **Edge Runtimeでのストリーミング制約に注意:** CloudflareやVercel EdgeはNode.js Runtimeと異なりWeb Streams APIベースのため、一部のNode依存ライブラリがストリーミングと非互換。アーキテクチャ選定時にRuntime制約を事前に確認することが必須。

- **React 19の`use()`フックによるクライアント側キャッシュ統合:** `use(promise)`がSuspenseと連携することで、サーバーからストリームされたデータをクライアントキャッシュに統合する層が薄くなり、ReactQuery等の従来ライブラリの役割が部分的に代替されつつある。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** tRPCはNext.js/Remixエコシステムで急速に普及し、型定義を共有することでクライアント・サーバー間の型安全性をゼロコストで実現できる。スタートアップやモノレポ構成では最も生産性の高い選択肢になりつつある。

- **GraphQLの用途特化:** GraphQLは「全API」への適用から「BFF（Backend for Frontend）や複雑なデータグラフ」への特化へシフト。オーバーヘッドを許容できないマイクロサービス間通信にはREST/gRPCが依然優位。

- **REST+OpenAPIの再評価:** OpenAPI 3.1 + TypeScript自動生成（`openapi-typescript`等）の組み合わせにより、REST APIでもtRPC並みの型安全性が実現可能になった。既存REST資産を持つ企業ではこの路線が現実的。

- **AIエージェント対応がAPI設計の新要件に:** LLMエージェントがAPIを自律的に呼び出すユースケースが増加し、構造化レスポンス・明示的なエラー型・OpenAPI仕様の整備が「エージェント互換性」として重視される。

- **エッジ・ストリーミング対応:** Vercel Edge / Cloudflare Workersでの実行を前提に、REST/tRPC問わず**ストリーミングレスポンス（SSE/ReadableStream）**への対応が標準的な設計要件になってきている。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジの標準ランタイムに:** CloudflareWorkers・Fastly Compute@Edgeを中心にWasmが事実上の標準となり、言語非依存でコールドスタートほぼゼロを実現。Rustや Go製マイクロサービスをそのままエッジにデプロイするパターンが主流化している。

- **エッジDBとの統合が加速:** PlanetScale・Turso・Cloudflare D1など「エッジネイティブDB」が成熟し、「エッジで読み書きまで完結」するアーキテクチャが現実的になった。レイテンシ感度の高い機能（認証・パーソナライゼーション）はオリジンに戻さず完結させるのが設計原則になりつつある。

- **AI推論のエッジオフロード:** LLMの軽量モデル（Phi-3 mini等）や量子化モデルをエッジノードで実行するユースケースが増加。中央クラウドへのラウンドトリップを排除し、プライバシー規制（GDPR等）対応とレイテンシ改善を同時に達成できる。

- **オブザーバビリティの課題が顕在化:** エッジ実行は分散度が極めて高く、従来のAPMツールでは追跡困難。OpenTelemetry準拠のエッジ向けトレーシング（Baselime等）が必須インフラになっており、導入コストを設計段階から見込むべき。

- **コスト最適化の落とし穴:** リクエスト単価は安価でも、エッジKVストアのread/write・帯域・ログ転送量が予想外に膨らむケースが頻発。「エッジ＝安い」の前提は危険で、キャッシュ戦略とコスト上限アラートをセットで設計することが実務上不可欠。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準採用:** FIDO2/WebAuthn ベースのパスキーがパスワード認証を事実上置き換えつつあり、フィッシング耐性と UX 向上を同時に実現できる。主要プラットフォームのサポートが成熟した今、新規実装ではパスキーをファーストクラス認証として設計すべき。

- **ゼロトラスト前提のセッション管理:** 「一度認証したら信頼し続ける」モデルは廃止。継続的リスク評価（デバイス状態・位置情報・行動パターン）に基づく動的な再認証要求が標準になり、短命トークン＋リフレッシュローテーションは必須。

- **AI 駆動の異常検知との統合:** クレデンシャルスタッフィングやアカウント乗っ取りをリアルタイムで検出するML パイプラインを認証フローに組み込む動きが加速。ルールベースの WAF だけでは不十分で、ベースライン行動モデルとの組み合わせが差別化になる。

- **サプライチェーンリスクとしての認証ライブラリ管理:** Auth0・Cognito などの外部 IdP や OSS 認証ライブラリへの依存は攻撃面を広げる。依存バージョンの固定・SBOM 管理・定期的な脆弱性スキャンを CI パイプラインに組み込むことが不可欠。

- **プライバシーバイデザインと最小権限トークン:** GDPR/個人情報保護法の厳格化により、JWT に含めるクレームの最小化とトークンスコープの細粒度制御が求められる。アクセストークンにユーザー属性を詰め込む設計は、漏洩時の影響範囲を不必要に拡大させるアンチパターン。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応:** Prisma 6ではEdge互換ドライバーが安定化し、Next.js App RouterのServer ComponentsやEdge Functionsから直接DB接続が可能になった。Supabase Connection Pooler（PgBouncer/Supavisor）との組み合わせでコールドスタートのコネクション枯渇問題が大幅に改善されている。

- **Supabase Branchingによる開発フロー変革:** Supabase Branchingが正式GAとなり、GitブランチごとにDBスキーマをプレビュー環境として分離できる。PRベースのスキーマレビューが実現し、Prisma Migrateとの連携でマイグレーションの安全性が格段に上がった。

- **RLSとPrismaの統合パターン成熟:** Row Level Security（RLS）をPrisma経由で扱うベストプラクティスが確立され、`SET LOCAL app.user_id`によるセッション変数パターンが標準化。アプリ層でのフィルタリングに頼らない多層防御アーキテクチャが組みやすくなっている。

- **pgvectorによるAI統合の実用化:** SupabaseのpgvectorサポートとPrismaのunsupported型回避策が整備され、ベクトル検索をRDBトランザクションと同一スキーマで管理できる。RAGパイプラインのインフラをSupabase単体で完結させるアーキテクチャが2026年のデファクトになりつつある。

- **サーバーレス時代のコネクション管理:** Supabase Supavisor（Elixirベースのコネクションプーラー）が成熟し、PgBouncerよりもPrepared Statement互換性が高い。Prismaの`pgbouncer=true`フラグを外せるケースが増え、クエリ最適化の制約が減った。

### 7. WebAssembly Rust performance 2026

- **WASM GC の本格普及:** 2024年にChrome/Firefox/SafariがWasm GC仕様を標準サポートし、2026年時点ではRustのwasm-bindgenやwit-bindgenを使ったコンポーネントモデル（WASI 0.2）が実用段階に入っている。メモリ管理のオーバーヘッドが減り、Rustバイナリサイズも大幅に削減可能。

- **SIMD・スレッドによるネイティブ並走:** WebAssembly SIMDとShared Memoryが安定化し、Rustの`rayon`クレートをWasmターゲットで活用した並列処理が現実的に。画像処理・音声解析・ML推論でNativeに近いスループットを達成しているケースが増加。

- **コールドスタートの改善:** WasmtimeやV8のAOTコンパイル（Cranelift最適化）により、Rustコンパイル済みWasmのコールドスタートが大幅短縮。エッジランタイム（Cloudflare Workers、Fastly Compute）でのRust+Wasm採用が加速している。

- **Component Modelによる多言語相互運用:** WASIp2のコンポーネントモデルで、RustモジュールをJS/Python/Goから型安全に呼び出せる構造が整備された。マイクロサービスの計算ロジックをRust Wasmに切り出すアーキテクチャが現実的な選択肢になっている。

- **ツールチェーンの成熟:** `cargo-component`、`wasm-opt`（Binaryen）、`wasmtime`のRust埋め込みAPIが安定し、CI/CDでのWasmビルド・テスト・デプロイが標準化。開発者体験はネイティブビルドに近い水準まで向上している。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** クライアントコンポーネントは最末端の「葉」に限定し、データフェッチとロジックはサーバー側に集約する設計が定着。バンドルサイズ削減と初期表示速度に直結する。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的ストリーミング部分を同一ルートで混在させる PPR が安定版に移行。`<Suspense>` 境界の設計がアーキテクチャの核になりつつある。

- **`use cache` / `use server` ディレクティブによる明示的なキャッシュ制御:** `fetch` の暗黙キャッシュが廃止され、`use cache` による明示的なキャッシュ戦略が必須に。キャッシュ粒度（ルート・コンポーネント・データ単位）を意識した設計が求められる。

- **Server Actions の型安全強化:** `zod` + Server Actions の組み合わせによるフォームバリデーションが標準パターン化。`useActionState` フックとの連携でプログレッシブエンハンスメントも担保できる。

- **`after()` API によるレスポンス後処理:** レスポンス送信後に非同期処理（ログ送信・分析イベント等）を実行できる `after()` が安定化。バックグラウンド処理をエッジで完結させる設計が可能になった。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択的活用:** 全APIルートをEdgeに移行するのは逆効果。認証チェック・geo-routing・A/Bテストなど低レイテンシが本質的に必要な処理のみEdgeに分離し、DB直接アクセスが必要なロジックはNode.js Runtimeに残す。

- **Cold Start撲滅のためのコードサイズ管理:** Edge Functionsは1MB制限（圧縮後）があり、バンドルが肥大化するとCold Startが顕在化する。`@vercel/og`や重いライブラリは動的インポートを避け、軽量な代替（`jose`→JWT検証など）を選定する。

- **ISR + Edge Middlewareの組み合わせ戦略:** Static Generation済みのページにEdge Middlewareでパーソナライゼーション（cookie判定によるリダイレクト・ヘッダー付与）を重ねることで、フルSSRなしにユーザー別コンテンツを実現しキャッシュヒット率を維持できる。

- **KV/キャッシュストアとの連携が前提:** Vercel KV（Upstash Redis）やEdge Configをセット活用することで、Edge側でのDB問い合わせを排除。レート制限・フィーチャーフラグ・セッション検証はすべてKVで完結させる設計が2026年のデファクト。

- **Fluid Compute移行の検討:** Vercelが推進する"Fluid Compute"モデルではEdge/Serverlessの境界が曖昧になりつつある。長時間処理はStreaming Responseで段階的にフラッシュし、タイムアウト上限（Edge: 30s）を意識したストリーミングファーストの実装に移行することが今後の主流。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の `satisfies` は型推論を保ちつつ型チェックを行えるため、`as` キャストを排除しより安全なコードベースを実現できる。

- **Template Literal Types によるAPIコントラクト強化:** エンドポイントパス・イベント名・CSSプロパティをTemplate Literal Typesで表現することで、ランタイムエラーをコンパイル時に検出できる。

- **`noUncheckedIndexedAccess` の標準化:** 配列・オブジェクトのインデックスアクセスを `T | undefined` として扱うこの設定が2026年現在の厳格なプロジェクトでは必須となっており、nullish coalescing との組み合わせが定石。

- **Branded Types でドメイン境界を保護:** `UserId` と `ProductId` を単なる `string` として扱わずBranded Typesで区別することで、関数の引数取り違えなどのロジックバグをゼロコストで防止できる。

- **`const` type parameters（TS 5.x）で推論精度を向上:** ジェネリック関数に `<const T>` を使うことで、呼び出し側がリテラル型として推論されるため、設定オブジェクトやルーティング定義の型安全性が大幅に上がる。
