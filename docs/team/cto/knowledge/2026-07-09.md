# CTO Knowledge - 2026-07-09

## Daily Update (2026-07-09)

### 1. Next.js performance optimization 2026

**CTO視点: Next.js performance optimization 2026**

- **ポイント1（Partial Prerendering の本格運用）:** Next.js 16ではPPRが安定版となり、静的シェルを即座に配信しつつ動的部分をストリーミングできる。sumitsugiの物件一覧・詳細ページのように「基本情報は静的、在庫状況は動的」なページ構成に特に有効で、TTFBを大幅短縮できる。
- **ポイント2（React Compiler によるメモ化の自動化）:** React CompilerがデフォルトでuseMemo/useCallbackの手動最適化を代替するため、コンポーネントの再レンダリングコストを気にせず書ける。ただしeslint-plugin-react-compilerで最適化不能パターン（副作用のある条件分岐など）を検知する運用が必須。
- **ポイント3（Turbopackビルドの標準化）:** Turbopackがビルド・devサーバーの既定エンジンとなり、大規模化していくsrc/components配下のビルド時間を数倍短縮できる。CIのbuild時間短縮にも直結するため、build:CI導入時に恩恵が大きい。
- **ポイント4（画像・フォントの自動最適化強化）:** next/imageのAVIF優先配信とレイアウトシフト対策が進化しており、物件写真中心のUIでは特にLCP改善効果が大きい。引き継ぎ物件の写真枚数が多いページではpriority属性の適切な設定がスコアを左右する。
- **ポイント5（Server Actionsのキャッシュ戦略見直し）:** `use cache`ディレクティブとキャッシュタグの粒度制御が洗練され、物件ステータス（draft/public）更新時の再検証を細かく制御可能に。過剰な再検証によるサーバー負荷を防ぎつつ、鮮度を担保できる。

### 2. React Server Components streaming 2026

- **段階的ハイドレーションの標準化:** Next.js 16ではSuspense境界ごとのストリーミングがデフォルト最適化され、`loading.tsx`と組み合わせることでTTFBとLCPを大きく改善できる。うちの`properties/`一覧ページのような重いデータ取得箇所は、境界を細かく切るほど体感速度が上がる。

- **Server ActionsとRSCの責務分離が明確化:** ミューテーション処理はServer Actionsに寄せ、RSCは純粋な読み取り・描画に専念させる設計が定着してきた。`src/lib/data.ts`のデータ取得層をこの前提で整理しておくと、将来のキャッシュ戦略変更に強くなる。

- **部分プリレンダリング(PPR)との組み合わせが本命:** 静的な骨格を即座に返しつつ動的部分だけストリーミングする構成が、ECサイト・物件検索系UIとの相性が良い。`listing/`のような検索結果ページで導入余地が大きい。

- **クライアントバンドル削減の指標が可視化コスト重視に:** Server Componentsをデフォルトにし、`'use client'`境界を意図的に絞ることがパフォーマンスKPIとして重視されるようになった。shadcn/uiコンポーネントも必要な部分だけクライアント化する運用を継続すべき。

- **エラーバウンダリとストリーミングの相性に注意:** ストリーミング中に発生したサーバーエラーはハイドレーション後にクライアント側で再スローされるケースがあり、`error.tsx`の設計とログ計装（Sentry等）を合わせて見直す価値がある。認証・決済フローなど重要導線では特に検証が必要。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはフルスタックTypeScriptモノレポ（フロントエンド・バックエンド同一言語）での型安全性において圧倒的に有利で、Next.js App Routerとの親和性も高い。ただしクライアントとサーバーが疎結合な外部API公開には向かず、社内マイクロサービス間通信やモバイルアプリ向け公開APIには不向き。

- **ポイント2:** GraphQLは複数クライアント（Web/モバイル/パートナー連携）が異なるデータ形状を要求する場面で依然強いが、N+1問題対策（DataLoader等）とキャッシュ戦略の実装コストが高く、シンプルなCRUD中心のプロダクトにはオーバーエンジニアリングになりがち。

- **ポイント3:** 2026年時点ではREST（特にOpenAPI + Zodスキーマ駆動）が「境界を跨ぐ公開API」のデファクトであり続けている。理由はツールチェーンの成熟度（Stripe/GitHub等の実績）とキャッシュ・CDN親和性の高さ。

- **ポイント4:** sumitsugiのような単一Next.jsモノレポ・Bunスタックでは、内部API（前の住人/次の住人間のやり取り、物件データ取得）はtRPCで型安全に、決済や外部連携（弁護士確認後の特商法対応システム等）が発生する箇所はREST/OpenAPIで切り出すハイブリッド構成が現実的。

- **ポイント5:** Zodスキーマを「システム境界での入力検証」に使う既存方針（`.claude/rules/standards.md`）は、tRPCのinput validationともREST + OpenAPIの型生成とも自然に統合できるため、API層の技術選定が変わってもこの部分の投資は無駄にならない。

### 4. serverless edge computing 2026

- **エッジランタイムの統一標準化:** WinterCG（WinterTG）準拠のランタイムがCloudflare Workers・Vercel Edge・Deno Deployで事実上のデファクトスタンダードとなり、Node.js固有APIへの依存を減らすことがマルチプラットフォーム移植性の鍵になっている。

- **コールドスタート問題の実質解消:** V8 isolateベースの分離モデルとプリウォーミング技術の成熟により、ミリ秒単位の起動遅延が実用上無視できるレベルになった。sumitsugiのような認証周りのAPI Routeも、レイテンシを気にせずエッジ実行を選択肢にできる。

- **エッジでのステートフル処理（Durable Objects/KV）の一般化:** 従来「エッジ=ステートレス」が前提だったが、Cloudflare Durable ObjectsやVercel KVのようなエッジネイティブなデータレイヤーが普及し、セッション管理や在庫ロックなど軽量な状態管理もエッジで完結できるようになった。物件公開ステータスのキャッシュ制御などに応用余地あり。

- **AI推論のエッジ配置とコスト最適化:** 軽量LLM推論（埋め込み生成やモデレーション判定）をエッジで実行し、中央サーバーへの往復を減らす構成が2026年のベストプラクティスになりつつある。ただしフルスケールのLLM呼び出しは依然リージョナルAPIが主流で、エッジは前処理・後処理に限定するのが現実的。

- **観測性(Observability)がボトルネックに:** 分散したエッジ実行環境ではトレーシング・ログ集約が複雑化しており、OpenTelemetry対応がエッジプラットフォーム選定の実質的な必須条件になっている。Next.js 16構成での移行を検討する際はこの点の対応状況を要確認。

### 5. authentication security best practices 2026

- **パスキー標準化の加速:** WebAuthn/FIDO2ベースのパスキーが主要IdPで既定選択肢となり、パスワード+SMS OTPは非推奨に移行中。実装時はプラットフォーム認証器とローミング認証器（セキュリティキー）の両対応、フォールバック手段の慎重な設計が必須。

- **フィッシング耐性MFAの必須化:** SMS/TOTPは中間者攻撃・SIMスワップに脆弱なため、OAuth 2.1準拠のフローとFIDO2ベースの認証器を組み合わせるのが業界標準に。特に決済・個人情報を扱うsumitsugiの物件取引フローでは優先度高。

- **セッション管理とトークンの寿命短縮:** リフレッシュトークンのローテーション必須化とDPoP（Demonstrating Proof of Possession）によるトークンバインディングで、トークン窃取時の被害範囲を限定するのが2026年のベストプラクティス。

- **AI駆動の異常検知によるクレデンシャルスタッフィング対策:** ボットによる大量ログイン試行がAI高度化で巧妙化しており、レート制限だけでなくデバイスフィンガープリンティングと行動分析を組み合わせた多層防御が必要。

- **シークレットレス認証への移行:** サーバー間通信では長期APIキーではなくOIDC/Workload Identity Federationによる短命トークン発行が標準化。当プロジェクトでも`.env`に長期シークレットを置く現行方式は将来的に見直しの余地あり。

### 6. database architecture Prisma Supabase 2026

- **エッジ最適化とコネクションプーリング:** Supabase の PgBouncer + Prisma Accelerate 等の組み合わせにより、Next.js のサーバーレス/エッジ関数からのDB接続枯渇問題が解消されつつある。サーバーレス環境ではコネクションプーリングを必ず経由する構成を前提に設計すべき。

- **Prisma のスキーマ駆動開発とRLSの二重管理:** Prisma でスキーマ定義しつつ Supabase の Row Level Security (RLS) をSQLマイグレーションで管理する運用が主流化しており、型安全性とDB側のアクセス制御を分離して二重に守る設計が推奨される。特に「前の住人」「次の住人」のようなロール別データアクセスにはRLSが有効。

- **リアルタイム機能とPrismaの共存:** Supabase Realtime（Postgres の論理レプリケーション）を使う場合、Prisma経由の書き込みとRealtimeサブスクリプションの整合性を意識する必要がある。物件ステータス（`draft`/`public`）変更の即時反映など、UX上重要な箇所から段階的に導入するのが実用的。

- **マイグレーション運用の一本化:** Prisma Migrate と Supabase CLI のマイグレーションを併用すると差分がずれるトラブルが多いため、どちらか一方（多くの場合Prisma Migrate）を正とし、CI上で `prisma migrate deploy` を強制する運用が2026年時点のベストプラクティス。

- **型生成とビルド健全性:** `status: 'draft' | 'public'` のようなUnion型はPrismaのenum定義と同期させ、スキーマ変更時に生成された型がビルドを通るかを必ずCIで検証する。型のズレは実行時エラーよりもビルド時に検出する方がコストが低い。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC（GC提案）の主要ブラウザ実装が安定し、Rustでも`wasm-bindgen`を介さない軽量な相互運用パターンが増えている。ただしRust自体はGCを使わないため恩恵は限定的で、JS/Kotlin等の言語ほど恩恵を受けない点に注意が必要。

- **ポイント2:** WASI Preview 2（Component Model）の普及により、Rustのwasm32-wasip2ターゲットでのサーバーサイド・エッジ実行が実用段階に入っている。SumitsugiのようなNext.js中心の構成では、重い画像処理やPDF生成処理（物件資料生成など）をWasmコンポーネント化してエッジで実行する選択肢が現実的になりつつある。

- **ポイント3:** SIMD128とマルチスレッド（`wasm-bindgen-rayon`）の組み合わせで、ブラウザ内での画像最適化・検索インデックス構築などCPU負荷の高い処理がネイティブの60-80%程度の性能まで到達している。ただしバンドルサイズとコールドスタートのトレードオフは依然として残るため、全処理をWasm化するのではなく計算集約的な部分のみに限定するのが実用的。

- **ポイント4:** `wasm-pack`/`wasm-bindgen`のツールチェーンは成熟しているが、ビルド時間とバンドルサイズの管理コストがまだ高い。小規模チームが少人数で運用するsumitsugiのようなプロジェクトでは、導入前に「本当にJS/TSの最適化では足りないのか」を検証すべきで、現状のプロダクトフェーズ（MVP完了・ローンチ準備中）では優先度は低いと判断する。

- **ポイント5:** Cloudflare WorkersやVercel Edge FunctionsでのWasmサポートが進み、Rust製の検証ロジック（例:住所正規化・重複物件検出などのアルゴリズム）をエッジで高速実行する事例が増加。将来的なスケール時の検討候補にはなるが、現時点でのアーキテクチャ変更は不要という結論。

### 8. Next.js App Router patterns 2026

- **ポイント1（Partial Prerendering の本格運用）:** Next.js 15〜16で安定したPPR（Partial Prerendering）により、静的シェルと動的コンテンツを1ページ内で組み合わせるのが標準パターンに。`<Suspense>`境界の設計が実質的なパフォーマンス設計そのものになっている。
- **ポイント2（Server Actions中心のデータ変更）:** フォーム送信やミューテーションはAPI Routesを介さずServer Actionsで完結させる設計が主流化。`useActionState`と組み合わせたプログレッシブエンハンスメントが標準的なフォーム実装パターン。
- **ポイント3（`use cache` ディレクティブによる明示的キャッシュ制御）:** キャッシュ挙動の暗黙性が批判されてきた反省から、関数・コンポーネント単位で`use cache`を明示する方式が浸透。うちのプロジェクトでも`src/lib/data.ts`のようなデータ層で採用すればキャッシュの意図が読みやすくなる。
- **ポイント4（Route Handlers vs Server Components の使い分け）:** 外部Webhookや非HTML応答が必要な場合のみRoute Handlersを使い、それ以外はServer Componentsで完結させる方針が定着。境界を混同すると認証・エラーハンドリングが二重管理になりがちなので注意。
- **ポイント5（型安全なルーティングとMiddlewareの軽量化）:** `typedRoutes`によるリンクの型チェックが実用段階に入り、Middlewareは認証チェックなど最小限に留めて重い処理はServer Components側に寄せるのがベストプラクティスとして定着している。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約を前提とした設計:** Node.js APIの一部（fsやネイティブモジュール）が使えないため、依存ライブラリ選定時点でEdge対応を確認する必要がある。重い処理はNode.js Functionsに切り出し、Edgeはレイテンシ最優先の軽量処理（認証チェック、リダイレクト、A/Bテスト振り分け）に限定するのが実用的。

- **コールドスタート削減とISR/キャッシュ戦略の組み合わせ:** Edge FunctionsはNode.js Functionsよりコールドスタートが短いが、それでもキャッシュヒット率を最大化する設計（`stale-while-revalidate`、Vercel Data Cache、`fetch`のcache設定）が体感速度を左右する。DBアクセスを伴うEdge Functionは接続プーリング（Neon/PlanetScaleのHTTPドライバ等）が必須。

- **リージョン配置の最適化:** デフォルトの自動リージョン選択に任せず、データソース（DB、外部API）に地理的に近いリージョンを明示指定することでレイテンシを大幅に削減できる。日本向けサービスなら`hnd1`固定 or DBとの近接性を優先すべき。

- **Streaming + Partial Prerendering (PPR) の活用:** Next.js 16ではPPRが安定版に近づいており、静的シェルを即座に返しつつ動的部分をEdgeでストリーミングする構成がTTFB改善の鍵。物件詳細ページのような「静的な骨格＋動的な空室状況」に向いている。

- **可観測性とコスト管理:** Edge Functionsは実行時間ベース課金のため、無限ループやリトライ処理のバグがコストに直結しやすい。Vercel Observability（OpenTelemetry統合）でP99レイテンシとエラー率を監視し、しきい値超過をCIでブロックする仕組みを検討すべき。

### 10. TypeScript type safety patterns 2026

- **型推論の強化パターン:** `satisfies`演算子とconst型パラメータ(`const T`)の組み合わせが標準化し、明示的な型注釈を減らしつつ型安全性を維持する書き方が主流になっている。

- **スキーマファースト開発:** Zodなどのバリデーションライブラリで型を「実行時スキーマから逆算」する手法が定着し、システム境界（API入出力・フォーム）での型と実行時検証の乖離を防ぐ。sumitsugiでも`.claude/rules/standards.md`の方針通り、境界でのZodバリデーションが型安全性の要になっている。

- **Branded Types / Nominal Typing:** `type UserId = string & { __brand: 'UserId' }`のようなブランド型で、構造的型付けの弱点（異なる意味のstring同士が混在するバグ）を防ぐパターンが普及している。物件ステータスのようなUnion型（`'draft' | 'public'`）でも、値の取り違えを防ぐのに有効。

- **Exhaustiveness Checking:** Union型を扱う際に`never`型を使った網羅性チェック（switch文のdefaultで`const _exhaustive: never = value`）が標準的なレビュー観点になり、型の追加・変更時の考慮漏れをコンパイル時に検出できる。

- **型テストの自動化:** `tsd`や`expect-type`を使い、型定義自体をユニットテストとして検証する動きが広がっており、公開APIの型シグネチャの意図しない破壊的変更をCIで検知できるようになっている。
