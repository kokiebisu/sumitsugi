# CTO Knowledge - 2026-05-27

## Daily Update (2026-05-27)

### 1. Next.js performance optimization 2026

- **React Server Components の徹底活用:** RSC によるサーバーサイドレンダリングをデフォルトとし、クライアントコンポーネントを最小限に絞ることで、JavaScript バンドルサイズを大幅削減できる。`'use client'` の追加は必要最小限に留めること。

- **PPR（Partial Prerendering）の本番投入:** Next.js 15+ で安定化した PPR により、静的シェルと動的コンテンツを同一ルートで混在させられる。CDN キャッシュのヒット率を維持しながら動的データを提供できる最重要最適化手法。

- **`next/image` と `next/font` の厳守:** 画像は WebP/AVIF 自動変換＋遅延読み込み、フォントはビルド時インライン化で CLS（レイアウトシフト）をゼロに近づける。Core Web Vitals の LCP/CLS 改善に直結する。

- **Route Segment Config によるキャッシュ戦略の精緻化:** `revalidate`、`dynamic`、`fetchCache` を各ルートセグメントで細かく制御し、全体を Static にも Dynamic にも倒さない中間設計が 2026 年のベストプラクティス。特に ISR と on-demand revalidation の組み合わせが有効。

- **Bundle Analyzer + Turbopack の常時監視:** `@next/bundle-analyzer` でサードパーティ依存の肥大化を定期チェック。Turbopack（Next.js 15 でデフォルト化）により開発ビルドが高速化され、CI での型チェックとビルド検証のサイクルを短縮できる。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の本格化:** Next.js 15以降でPPRが安定版になり、静的シェルを即座に配信しつつ動的コンテンツをStreamingで後続配信するパターンが標準になった。TTFBとLCPを同時に改善できる。

- **Suspense境界の粒度設計がパフォーマンスの鍵:** Server ComponentsのStreaming効果はSuspense境界をどこに置くかで決まる。データ取得の遅い部分だけを遅延させ、骨格UIを先に見せる設計が必須になっている。

- **`use` hookによる非同期処理の統一:** React 19で安定した`use(promise)`により、Client ComponentsでもServer Componentのデータ受け取りが宣言的に書けるようになり、Streaming境界のコードが大幅にシンプル化された。

- **Edge RuntimeでのStreaming制約に注意:** Vercel Edge / Cloudflare WorkersでのRSCはNode.js Runtimeより制約が多く、特定のNode APIが使えない。パフォーマンス優先でEdgeに寄せる場合、依存ライブラリのEdge互換性確認が先決。

- **Server Actionsとの組み合わせがフォーム・ミューテーションの新標準:** StreamingはデータFetchだけでなくServer Actionsのレスポンス返却にも適用され、楽観的UIアップデートと組み合わせることでSPAに近いUXをサーバー中心アーキテクチャで実現できる。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの成熟と普及:** Next.js + TypeScriptスタックでの型安全なend-to-end開発においてtRPCが事実上の標準となり、スキーマ定義なしでクライアント・サーバー間の型共有が実現。中小規模のSaaSでは「REST vs GraphQL」の議論自体が不要になっている。

- **GraphQLの適用範囲の明確化:** BFF（Backend for Frontend）パターンや複雑なデータグラフが必要なプロダクト（ECマルチプラットフォーム等）ではGraphQLが依然強力だが、単純なCRUDにGraphQLを採用するコストへの反省が広まり、ユースケース適合性の見極めが重視されている。

- **REST + OpenAPI 3.1の再評価:** LLM/AIエージェントとのAPI連携においてOpenAPIスキーマが機械可読性で優位に立ち、「RESTは古い」という認識が逆転。型生成ツール（Zod、Orval等）の整備により型安全性のギャップも縮小している。

- **エッジ・ストリーミングへの対応:** Vercel Edge RuntimeやCloudflare Workersの普及で、従来のRESTリクエスト・レスポンスモデルに加えRSC（React Server Components）とServer-Sent Eventsを組み合わせたストリーミングAPIパターンが標準化されつつある。

- **APIゲートウェイとの統合戦略:** 認証・レート制限・観測性をアプリケーション層ではなくインフラ層（Kong、AWS API Gateway、Cloudflare等）に委譲するアーキテクチャが主流となり、APIデザインをビジネスロジックに集中させる分離が進んでいる。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) のファーストクラス化:** Cloudflare Workers・Fastly Compute@Edgeを中心に、Wasmがエッジランタイムの標準となり、Rust/Go/Pythonを低レイテンシで直接デプロイできる環境が成熟。言語の選択肢が大幅に広がった。

- **エッジ×AI推論の融合加速:** 小型LLM（1B〜7Bパラメータ）をエッジノードで実行するパターンが普及し、ユーザーデータをクラウドに送らずにパーソナライズ処理できるアーキテクチャが現実的な選択肢になっている。

- **Cold Start問題の実質的解消:** V8 Isolateモデルの最適化とプリウォーム戦略の進化により、大半のエッジプラットフォームでコールドスタートが1ms以下に。サーバーレスの最大の弱点がほぼ無効化された。

- **エッジDBの台頭（Distributed SQLite/Turso等）:** エッジ関数と同居するローカルDB（Turso、Cloudflare D1）が実用段階に入り、「エッジでの書き込み→非同期レプリケーション」パターンで一貫性とレイテンシのトレードオフを制御できるようになった。

- **可観測性の標準化（OpenTelemetry at Edge）:** 分散エッジ環境でのトレーシングがOpenTelemetryに収束し、従来ブラックボックスだったエッジ実行の分散トレースが可能に。デバッグコストが劇的に下がっている。

### 5. authentication security best practices 2026

- **パスキー（Passkey）の標準採用:** FIDO2/WebAuthn ベースのパスキーがパスワードレス認証の主流となっており、フィッシング耐性と利便性を両立できるため、新規サービスでは最優先で導入を検討すべき。

- **MFAの必須化とリスクベース認証の組み合わせ:** 全ユーザーへのMFA強制は基本となり、さらにログイン文脈（地理・デバイス・行動パターン）に基づく動的なステップアップ認証で、摩擦とセキュリティのバランスを最適化する。

- **トークンの短命化とRotationの徹底:** JWTのアクセストークン有効期限は15分以内、リフレッシュトークンのRotation（使い捨て）を必須とし、セッションハイジャック被害の最小化を図る。

- **サプライチェーン攻撃への対策（OAuth/OIDCライブラリの監視）:** 認証ライブラリへの悪意ある依存注入が増加しており、`npm audit` / Dependabot の自動更新と、SBOMによる依存関係の可視化が不可欠。

- **AIを活用した異常ログイン検知:** 機械学習による行動バイオメトリクス（タイピングリズム・マウス動作）や、クレデンシャルスタッフィング攻撃のリアルタイム検知が実用段階に入っており、WAFと組み合わせた多層防御が2026年標準となっている。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応:** Prisma 6はEdge RuntimeとPrisma Accelerateによりサーバーレス・エッジ環境での接続プーリングが標準化され、Cold Start問題が大幅に改善された。Next.js App RouterのServer Actionsとの相性も向上。

- **Supabase pgvector + RAGアーキテクチャの主流化:** `pgvector`拡張によるベクトル検索がSupabaseのコアに統合され、AIアプリ開発でPostgresを単一DBとしてリレーショナル＋ベクトル検索を両立するパターンが標準的になった。

- **Row Level Security (RLS) ファーストの設計:** SupabaseではRLSをORM層ではなくDB層で強制する設計が主流。Prismaと組み合わせる際はサービスロール/匿名ロールを使い分けるマルチクライアント構成がベストプラクティス。

- **Prisma + Supabase の型安全なリアルタイム:** Supabase RealtimeとPrismaのスキーマを同期させる`supabase gen types`により、DB変更のリアルタイム購読まで型安全に実装できる体制が整い、フロントエンドとのデータ契約が強化された。

- **マルチテナントとスキーマ分離:** 2026時点ではテナント分離にPostgresのスキーマ単位分割（`schema per tenant`）を使うパターンが再評価されており、PrismaのマルチスキーマプレビューとSupabaseのプロジェクト分離コストのトレードオフを慎重に設計する必要がある。

### 7. WebAssembly Rust performance 2026

- **WASI 0.2 + Component Modelの成熟:** 2026年時点でWASI Preview 2が広く採用され、RustのWASMコンポーネントが言語間で型安全に合成可能になった。マイクロサービス間の軽量RPC代替として実用段階に入っている。

- **WASMGCとRustの共存:** GC提案の安定化により、GCランタイム不要なRustはWASM環境でのメモリ効率の優位性をさらに発揮。特にエッジ・サーバーレス環境（Cloudflare Workers、Fastly）でのコールドスタート時間が1ms以下を達成。

- **SIMD・マルチスレッド対応の標準化:** WASMのRelaxed SIMDとThreads proposalが主要ブラウザで安定化し、Rustの`rayon` + `wasm-bindgen`スタックで画像処理・暗号処理が従来JS比3〜5倍のスループットを実現できる。

- **Wasmtime/WasmEdgeのAOTコンパイル:** サーバーサイドRuntimeでのAhead-of-Time最適化が進み、NativeバイナリとのパフォーマンスギャップはI/Oバウンド処理で実質ゼロに近づいた。RustのWASMターゲットをコンテナ代替として採用するプロジェクトが増加中。

- **ツールチェーンの成熟（`cargo-component`）:** `cargo-component`によるComponent Model対応が安定し、WASMモジュールのビルド・テスト・配布がネイティブRustと同等のDXで実現。導入コストが大幅に低下したため、既存RustクレートのWASM移植が加速している。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** クライアントコンポーネントは「必要な場所だけ」に限定し、ツリーの末端に押し込む設計が定着。データフェッチはすべてサーバーサイドで完結させることでバンドルサイズと初期ロードを最小化する。

- **Partial Prerendering (PPR) の実用化:** 静的シェルと動的ストリーミング部分を同一ページで共存させる PPR が安定版となり、ISR の代替として採用が進む。`<Suspense>` 境界の設計がパフォーマンスの鍵になる。

- **Server Actions によるミューテーション一元化:** API Route の代わりに Server Actions でフォーム送信・データ更新を処理するパターンが主流化。`useActionState` + `useFormStatus` による楽観的 UI 更新が標準的なUXパターンとなっている。

- **Parallel Routes / Intercepting Routes の活用:** モーダルやスライドオーバーを URL に紐づける Intercepting Routes が普及し、シェア可能な URL を持つ複雑な UI を Next.js ネイティブで実装できるようになった。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** `unstable_cache` から `use cache` への移行が進み、関数・コンポーネント単位でキャッシュのライフタイムとスコープを宣言的に制御できる。`cacheTag` / `cacheLife` との組み合わせで ISR より柔軟なキャッシュ戦略が実現する。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge Runtimeでの計算コスト削減:** Vercel Edge FunctionsはV8 Isolateベースのため、Node.js Runtimeより起動レイテンシが大幅に低い（コールドスタートほぼゼロ）。`export const runtime = 'edge'` を適切なルートに設定し、重い処理はNode.js側に残す分離設計が2026年の定石。

- **ポイント2: Streaming ResponseとSuspenseの活用:** `ReadableStream` + React Suspenseの組み合わせでTTFBを最小化。特にAI系APIレスポンス（Anthropic/OpenAI）のストリーミングはEdgeで処理することでユーザー体感速度が顕著に改善される。

- **ポイント3: Edge ConfigとKVによるデータアクセス最適化:** データベースへの直接接続はEdgeでは使えないため、Vercel Edge Config（超低レイテンシの設定読み取り）とVercel KV（Redis互換）の組み合わせでホットデータをキャッシュする設計が必須。

- **ポイント4: バンドルサイズ制限への対応:** Edge Functionsのバンドル上限（1MB圧縮後）に注意。`import`するライブラリのEdge互換性を事前確認し、`next/server`の`NextRequest`/`NextResponse`を活用してpolyfillの肥大化を防ぐ。

- **ポイント5: リージョン選択とデータロカリティ:** デフォルトのグローバル展開はDB接続元とレイテンシ差が生じるため、`export const preferredRegion = 'hnd1'`（東京）で固定し、データベース（Supabase/PlanetScale）のリージョンと合わせることがNext.js App Routerでのパフォーマンス確保の鍵。

### 10. TypeScript type safety patterns 2026

- **ポイント1: `satisfies` 演算子の本格活用:** TypeScript 4.9以降で導入された `satisfies` が2026年のコードベースでは標準化。型の推論精度を保ちながら制約チェックができ、`as const` との組み合わせでリテラル型の精度を最大化できる。

- **ポイント2: `using` キーワードによるリソース管理型安全性:** Explicit Resource Management（TC39 Stage 4）のサポートが安定し、DB接続・ファイルハンドルのリークをコンパイル時に検出可能に。`Symbol.dispose` を活用したクリーンアップパターンが普及している。

- **ポイント3: Template Literal Typesによる文字列型の厳格化:** APIルートやイベント名を `type Route = \`/api/${string}\`` のように型付けし、実行時エラーをコンパイル時に潰すパターンが成熟。特にNext.js App Routerのルートパラメータ型定義で効果大。

- **ポイント4: Branded Types（Nominal Typing）の実用化:** `type UserId = string & { readonly _brand: 'UserId' }` パターンで、構造的型付けの落とし穴（IDの取り違えなど）をゼロコストで防止。Zodの `.brand()` APIと組み合わせると境界バリデーションも一体化できる。

- **ポイント5: `noUncheckedIndexedAccess` の標準採用:** `tsconfig.json` の厳格オプションとして普及が加速。配列・オブジェクトのインデックスアクセスに自動で `T | undefined` が付与され、実行時の `undefined` 参照エラーを型レベルで撲滅できる。
