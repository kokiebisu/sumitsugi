# CTO Knowledge - 2026-09-22

## Daily Update (2026-09-22)

### 1. Next.js performance optimization 2026

- **ポイント1:** Next.js 16ではTurbopackがデフォルトビルドツールとなり、開発時のHMRだけでなく本番ビルドも大幅高速化されている。sumitsugiのようなプロパティ一覧・詳細ページが多い構成では、ビルド時間短縮がCI/CDのフィードバックループ改善に直結する。

- **ポイント2:** Partial Prerendering（PPR）とReact Server Componentsの組み合わせが主流化しており、静的な物件情報（画像・基本情報）と動的な部分（在庫状況・価格変動）を1ページ内で分離してストリーミング配信できる。物件詳細ページのTTFB改善に有効。

- **ポイント3:** React Compilerの安定版採用により、`useMemo`/`useCallback`の手動最適化が不要になりつつある。前の住人・次の住人のマッチングロジックのような複雑な状態管理コンポーネントでも、再レンダリング最適化を書かずに済むケースが増える。

- **ポイント4:** 画像最適化はAVIF/WebPの自動変換に加え、`next/image`のpriority属性とLCP計測の連携が強化されている。物件写真が多いUIでは、ファーストビューの画像のみpriority指定し、それ以外は遅延読み込みを徹底することがCore Web Vitals改善の鍵。

- **ポイント5:** キャッシュ戦略として`use cache`ディレクティブ（Cache Components）が本格運用フェーズに入り、データフェッチ単位での粒度の細かいキャッシュ制御が可能になった。ドラフト/公開ステータスが切り替わる物件データでは、キャッシュ無効化のタイミング設計を誤ると古いデータが表示されるリスクがあるため、タグベースの再検証（`revalidateTag`）を徹底すべき。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではRSCのストリーミングSSRがデフォルト最適化され、`loading.tsx`と`Suspense`境界の粒度設計がTTFB短縮の鍵になっている。sumitsugiの`properties/`一覧や`listing/`詳細ページのような画像・地図データが重いページでは、コンポーネント単位でSuspense境界を細かく切ることでLCPを大幅改善できる。

- **ポイント2:** Partial Prerendering（PPR）が安定版に近づき、静的シェル＋動的ストリーミングのハイブリッドが標準パターンに。物件検索結果のような「静的な枠＋動的な検索結果」構成に向いており、キャッシュ戦略とStale-While-Revalidateの併用でインフラコストも下げられる。

- **ポイント3:** Server ActionsのストリーミングレスポンスがuseActionState/useOptimisticと組み合わさり、フォーム送信（問い合わせ・引き継ぎ申込フロー）でクライアントJSを増やさずに楽観的UI更新が可能に。認証系フォームでの活用時は必ずZodバリデーションとCSRF対策をサーバー側で担保する必要がある。

- **ポイント4:** RSCペイロードのキャッシュ透過性が向上し、`fetch`のタグベース無効化（`revalidateTag`）がストリーミングと自然に組み合わさるように。物件ステータス（draft/public）変更時に該当タグだけを無効化する設計にすれば、全体再ビルドなしで即時反映できる。

- **ポイント5:** ストリーミング中のエラーバウンダリ設計が重要課題として浮上しており、部分的なストリーム失敗時のフォールバックUIがUXの分かれ目に。決済や引っ越し費用計算など重要フローでは、ストリーミング区間を最小限にして同期的なエラーハンドリングを優先すべき。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの実質的デファクト化）:** TypeScriptフルスタック構成（Next.js等）では、スキーマ定義と型生成を別途行うGraphQLより、tRPCがエンドツーエンドの型安全性をゼロコード生成で実現できる点で採用が増加。sumitsugiのようなNext.js単一リポジトリ構成では、API層とクライアントの型を自動同期できるtRPCが開発速度の面で有利。

- **ポイント2（GraphQLは大規模・複数クライアント向けに収束）:** GraphQLは複数フロントエンド（Web/モバイル/パートナー向けAPI）やBFF層が必要な場合に依然強みがあるが、単一チーム・単一フロントエンドのMVPフェーズでは過剰投資になりやすい。sumitsugiは現状Web単体なのでGraphQL導入の必要性は低い。

- **ポイント3（RESTは外部公開APIの標準であり続ける）:** サードパーティ連携（決済、外部弁護士確認フローの電子契約API等）やWebhookは依然RESTが業界標準。内部通信はtRPC、外部公開・パートナー連携はREST、というハイブリッド構成が2026年の主流パターン。

- **ポイント4（エッジランタイムとの親和性）:** Next.js 16のApp Router + Edge Runtimeでは、tRPCのプロシージャ単位での軽量な実行がコールドスタート面で有利。物件検索や引越し費用計算のような低レイテンシが求められるAPIはEdge化を検討する価値あり。

- **ポイント5（OpenAPI自動生成による相互運用性の確保）:** tRPCを採用してもOpenAPI仕様を自動生成するアダプタ（trpc-openapi等）を併用すれば、将来の外部パートナー向けAPI公開や他言語クライアント対応の道を残せる。ローンチ後の拡張性を考慮し、型安全性と相互運用性を両立する設計が推奨される。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG/WinterTC準拠のランタイム（Cloudflare Workers、Deno Deploy、Vercel Edge）が事実上の標準となり、V8 IsolatesベースでコールドスタートがミリSEC単位に短縮。Node.js固有APIへの依存を減らせば、複数プロバイダー間の移植性が高まる。

- **エッジでのステートフル処理:** Durable Objects（Cloudflare）やActor モデルの普及により、従来はサーバーレスの弱点だった「状態管理」がエッジ上で可能に。sumitsugiのようなリアルタイム物件検索・チャット機能をエッジ最寄りで処理すれば、日本国内ユーザーへのレイテンシを大幅改善できる。

- **エッジDB/ストレージの成熟:** Turso（libSQL）、Cloudflare D1、PlanetScaleなどエッジレプリケーション対応DBが実用段階に入り、読み取りをエッジで完結できるように。物件一覧など読み取り比率の高いページはエッジキャッシュ＋エッジDBの組み合わせでTTFBを劇的に改善可能。

- **AI推論とエッジの融合:** 軽量LLM（量子化モデル）やベクトル検索をエッジで実行する動きが加速しており、レコメンドや検索の一次処理をエッジで済ませ、重い生成処理のみ中央APIに委譲する「ハイブリッド推論」が2026年のベストプラクティスになりつつある。

- **コスト・運用面の注意点:** エッジ関数は実行時間・メモリ制約が厳しく、Next.js 16のApp Router使用時はどのルートをEdge Runtime化するか慎重な見極めが必要（DBコネクションプーリングや重いnpmパッケージ依存はNode Runtimeに残すべき）。全面移行より「レイテンシが効くページだけ」段階的にエッジ化するのが現実的。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証（WebAuthn/Passkeys）が業界標準となり、フィッシング耐性の高さから2026年は主要OSブラウザで標準サポートが完備。sumitsugiのようなtoC向けプラットフォームでは、離脱率低減とセキュリティ強化を両立できるため優先度が高い。

- **多層防御としてのリスクベース認証:** IPレピュテーション・デバイスフィンガープリント・行動分析を組み合わせたアダプティブ認証が主流化し、異常なログイン試行のみに追加検証（MFA）を要求する設計がUXとセキュリティのバランスを取る鍵となる。

- **トークン管理の厳格化:** JWTの有効期限を短く保ち（アクセストークン15分程度）、リフレッシュトークンはHTTPOnly+Secure+SameSite=Strict Cookieで管理するのがベストプラクティス。localStorage保存はXSS経由の窃取リスクがあるため避けるべき。

- **セッション固定・CSRF対策の再点検:** Next.js App Router移行時はServer Actions経由の認証フローでCSRFトークン検証が抜け落ちやすいため、フレームワーク標準のCSRF保護機構を必ず有効化し、認証状態変更を伴うエンドポイントは全てPOST+トークン検証必須とする。

- **監査ログとゼロトラストの実装:** 「前の住人」「次の住人」間で個人情報を扱う本サービスの特性上、認証イベント（ログイン・パスワード変更・引き継ぎ承認）は改ざん不可能な監査ログとして記録し、最小権限原則に基づくロールベースアクセス制御（RBAC）を徹底することがコンプライアンス上も必須。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMのマイグレーション体験向上:** Prisma 6以降はエッジランタイム対応が強化され、Prisma Accelerate/Data Proxyを使うことでNext.js 16のEdge FunctionsやServer Actionsからも低レイテンシでDB接続できるようになった。コネクションプーリングの管理が不要になる点が特に有効。

- **Supabaseのブランチング機能でプレビュー環境が容易に:** SupabaseのDatabase Branching（PRごとに独立したPostgres環境を自動生成）を使うと、Vercelプレビューデプロイと連携してPRごとに本番相当のDBでE2Eテストが可能。sumitsugiのようにdraft/publicステータス管理を持つプロジェクトでは、スキーマ変更を安全に検証できる。

- **Row Level Security (RLS) をアプリ層バリデーションの補完に:** Zodによる入力検証（境界層）に加え、SupabaseのRLSをDB層の最終防御ラインとして併用するのが2026年のベストプラクティス。特に「前の住人」「次の住人」間のデータアクセス制御など、ユーザー種別ごとの閲覧権限が絡むsumitsugiの物件データには有効。

- **Prisma + Supabase Realtimeの組み合わせでリアルタイム機能を低コスト実装:** 物件の公開ステータス変更や引き継ぎ進捗の通知など、WebSocketサーバーを自前構築せずにSupabase Realtimeで実現できる。Prisma SchemaとRealtimeのチャンネル設計を一致させることで型安全性を保てる。

- **型安全なDBスキーマ変更フローの重要性:** `'draft' | 'public'`のようなUnion型のステータス管理は、Prismaのenum定義とTypeScript側の型を単一ソース化（`prisma generate`の出力を直接importする）することで、standards.mdにある「Union型変更時は全箇所grep」のリスクを構造的に低減できる。

### 7. WebAssembly Rust performance 2026

## CTO視点: WebAssembly Rust performance 2026

- **ポイント1（Component Model標準化）:** WASI Preview 3とComponent Modelの標準化が進み、Rustで書いたWASMモジュールを言語非依存で組み合わせられるようになった。マイクロサービス的な機能分割をエッジ環境でも安全に実現できる点が実用上大きい。

- **ポイント2（SIMD・スレッド対応の成熟）:** WASM SIMDとスレッド（SharedArrayBuffer経由）が主要ブラウザ・ランタイムで安定運用され、Rust側もこれらを素直に叩けるようになった。画像処理や地図描画など計算負荷の高い機能をクライアント側に持ってきてもネイティブに近い速度が出る。

- **ポイント3（バイナリサイズとコールドスタート最適化）:** `wasm-opt`やRustのLTO/`opt-level=z`設定の組み合わせで、エッジ関数（Cloudflare Workers等）でのコールドスタートが数ミリ秒台まで縮小。物件検索APIのような低レイテンシが求められる箇所をエッジWASM化する選択肢が現実的になっている。

- **ポイント4（ツールチェーンの安定化）:** `wasm-bindgen`/`wasm-pack`のTypeScript型生成が実用レベルに達し、既存のNext.js/TypeScriptスタックへの統合コストが下がった。パフォーマンスクリティカルな一部処理（画像最適化・PDF生成など）だけRustに切り出す、という部分導入がしやすくなっている。

- **ポイント5（採用判断の実用ライン）:** 現状のsumitsugiの規模ではJS/TSで十分な箇所がほとんどで、WASM導入はPDF生成や大量データの集計処理など「明確にCPUバウンドなボトルネックが特定できた箇所」に限定するのが費用対効果として妥当。

### 8. Next.js App Router patterns 2026

**ポイント1:** Server ComponentsとPartial Prerendering（PPR）の組み合わせが標準化し、静的な骨格を即座に配信しつつ動的部分（例：物件詳細ページの空室状況や価格）だけをストリーミングする構成が主流になっている。sumitsugiでは`src/app/properties/`のようなSEO重視ページで特に有効。

**ポイント2:** `use cache`ディレクティブ（Next.js Cache Components）によるキャッシュ制御が明示的・宣言的になり、従来の`revalidate`や`fetch`オプションへの暗黙依存から脱却しつつある。データ取得ロジック（`src/lib/data.ts`）のキャッシュ戦略を見直す好機になる。

**ポイント3:** Server Actionsがフォーム処理の第一選択肢として定着し、クライアント側のAPI呼び出し用ボイラープレートを削減できる。物件掲載フォームや問い合わせフォームなど、認証・バリデーションが絡む多段フローで特に恩恵が大きい。

**ポイント4:** Route Groupsと Parallel Routes/Intercepting Routesを使ったモーダル型UIパターン（例：物件一覧から詳細をモーダルで開きつつURLも変わる）がAirbnb系UXの実装で定番化している。デザイン原則の「Airbnb風クリーンUI」との親和性が高い。

**ポイント5:** エッジランタイムとNode.jsランタイムの使い分けがより細かく制御可能になり、認証チェックのようなレイテンシ重視の処理はedge、DB操作を伴う重い処理はNode.jsに分離するハイブリッド構成が推奨されつつある。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの計算コスト最適化:** 2026年のVercel Edge Functionsは従量課金がより細粒度化しており、CPU時間だけでなくメモリ使用量も課金対象に含まれるため、不要な依存関係（特に大きなSDKやポリフィル）を削減し、bundle sizeを小さく保つことがコスト削減に直結する。

- **Streaming SSRとの統合強化:** Next.js 16のPartial Prerendering (PPR) とEdge Functionsの組み合わせにより、静的シェルを即座に返しつつ動的部分をストリーミングできるため、`src/app/properties/`のような一覧ページでTTFBを大幅に改善できる余地がある。

- **リージョン選択とデータ局所性:** 引越し費用計算や物件検索のようなDB問い合わせを伴う処理は、Edge FunctionsをDB（Supabase/Neon等）のリージョンに近い場所へ明示的にピン留めしないと、逆にレイテンシが悪化するケースがある。マルチリージョン展開時は要検証。

- **Node.js互換性の拡大:** Edge RuntimeでのNode.js API互換性が2026年時点でかなり向上しており、以前はServerless Functions必須だった処理（一部の`crypto`や`fs`依存ライブラリ）もEdgeで動くようになった。移行前にランタイム制約の再チェックが有効。

- **観測性（Observability）の標準装備:** Vercel標準のEdge Functionsログ・トレーシングが charAt改善され、OpenTelemetry連携が容易になったため、認証フローや決済関連のエッジ処理では構造化ログを組み込んでおくと障害調査が格段に楽になる。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** `strict`モードに加えて`noUncheckedIndexedAccess`や`exactOptionalPropertyTypes`を有効化する構成が標準化しつつあり、配列アクセスやoptionalプロパティ由来のランタイムエラーをコンパイル時に検出できる。当プロジェクトでも`tsconfig.json`に未設定なら早期に導入すべき。

- **ポイント2:** Zodなど実行時バリデーションライブラリと型推論(`z.infer`)を組み合わせ、APIレスポンスやフォーム入力など「境界」でのみ検証する設計が定着している。`.claude/rules/standards.md`が定めるZod必須方針とも一致しており、境界外での過剰な型ガードは避けるべき。

- **ポイント3:** `satisfies`演算子の活用が広がり、型を明示的にアサーションせずにオブジェクトリテラルの型安全性と型推論の両立ができるようになった。設定オブジェクトや定数マップ定義で`as const satisfies`パターンが有用。

- **ポイント4:** Template Literal TypesとBranded Types（nominal typing）を使い、`listingId: string`のような単純な文字列型を`ListingId`のような区別可能な型に置き換える設計が増えている。物件ステータスなどUnion型の誤用防止に有効で、`standards.md`にあるUnion型変更時のgrep徹底ルールとも相性が良い。

- **ポイント5:** モノレポ・大規模コードベースでは`tsc --build`によるプロジェクト参照分割とインクリメンタルビルドが必須化しており、ビルド速度と型チェックの独立性を両立させている。ファイル数が増えた場合の将来的な検討事項として意識しておきたい。
