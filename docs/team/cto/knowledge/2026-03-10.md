# CTO Knowledge - 2026-03-10

## Daily Update (2026-03-10)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本番活用:** Next.js 15以降でPPRが安定化し、静的シェルと動的コンテンツを同一ルートで混在させることで、TTFBを大幅に削減できる。キャッシュ戦略の設計をページ単位ではなくコンポーネント単位で考える時代になった。

- **React Server Components のバンドルサイズ影響:** RSCにより重いライブラリ（date-fns、lodash等）をサーバー側に閉じ込め、クライアントバンドルを劇的に削減できる。`"use client"` の境界設計がパフォーマンスの要となる。

- **`next/image` と Core Web Vitals:** LCPスコアへの直接影響が大きく、`priority` prop・`sizes` 属性の適切な設定と、AVIFフォーマットの積極採用が必須。画像最適化の手抜きは検索順位に直結する。

- **Edge Runtime vs Node.js Runtime の使い分け:** ミドルウェアや認証チェックはEdge Runtimeで実行することでコールドスタートを回避できるが、Node.js専用モジュールへの依存には注意が必要。Vercel以外のエッジ環境（Cloudflare Workers等）との互換性も設計時に考慮する。

- **`unstable_cache` と細粒度キャッシュ制御:** `fetch` キャッシュに加え、`unstable_cache` でDB queryや外部APIの結果をキャッシュし、`revalidateTag` でピンポイント無効化する設計が主流になっている。適切なキャッシュ粒度の設計が、サーバーコスト削減と鮮度のトレードオフを決める。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Pre-renderingの本格普及** Next.js 15以降でPPR（Partial Pre-rendering）が安定化し、静的シェルと動的ストリーミングコンポーネントを同一ルートで共存させるパターンが標準化。TTFBとTTIの両立が現実的になった。

- **ポイント2: Suspense境界設計がアーキテクチャの核心に** ストリーミングの恩恵を最大化するには、Suspenseの粒度設計が重要。粗すぎると滝型ウォーターフォール、細かすぎるとレイアウトシフト—コンポーネント境界の設計がパフォーマンスに直結する。

- **ポイント3: Server Actionsとの統合でフォーム体験が刷新** RSC + Server Actionsの組み合わせにより、楽観的UI更新とサーバーサイド処理が密結合。クライアントバンドルを削減しながら、SPA相当のインタラクション体験を実現できる。

- **ポイント4: キャッシュ戦略の複雑化** `fetch`キャッシュ、Router Cache、Full Route Cacheの3層構造を理解せずにストリーミングを使うと、古いデータの混在や意図しない再レンダリングが発生。`revalidate`戦略の明示化が必須。

- **ポイント5: エッジランタイムとの相性問題** CloudflareやVercel EdgeでRSCストリーミングを動かす際、Node.js専用APIへの依存やコールドスタートがボトルネックになるケースが継続中。2026時点でもNode.jsランタイムとEdgeの使い分けは慎重に判断すること。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** tRPCはNext.js・Remixとの相性から採用が加速し、エンドツーエンドの型安全を実現。スキーマ定義不要でバックエンド変更が即座にフロントエンドの型エラーとして検出できるため、小〜中規模チームの開発速度が大幅に向上している。

- **GraphQLの「適切な規模」問題:** FacebookやShopify規模では依然強力だが、2026時点では「オーバーエンジニアリング」として見直す動きが顕著。N+1問題・認可ロジックの複雑化・DataLoaderの学習コストを考慮すると、BFF（Backend for Frontend）パターンとREST/tRPCの組み合わせが現実解になるケースが多い。

- **REST + OpenAPI 3.1の再評価:** Zodベースのスキーマ生成（`zod-openapi`等）によりOpenAPI仕様の自動生成が容易になり、型安全なREST APIクライアントの自動生成が成熟。サードパーティ連携やパブリックAPIではREST+OpenAPIが依然ベストプラクティス。

- **Server ActionsとAPIレイヤーの融合:** Next.js 15以降のServer Actionsが普及し、内部APIコールを省略できるケースが増加。ただしキャッシュ戦略・楽観的更新の実装複雑性から、外部公開や複雑なデータフローにはtRPCやRESTを併用するハイブリッド設計が主流。

- **エッジコンピューティングとAPIプロトコル選択:** Cloudflare Workers・Vercel Edgeでの制約（Node.js APIの非対応等）により、軽量なHTTP APIが再評価。gRPCはエッジ非対応が多く、REST/tRPCが2026のエッジファースト設計では実質的な標準となっている。

### 4. serverless edge computing 2026

- **エッジでのAI推論が主流化:** 2026年時点では、LLMの量子化・蒸留技術の成熟により、Cloudflare Workers AIやVercel Edge Functionsでの軽量モデル推論がコスト効率の観点から標準的な選択肢となっている。

- **WebAssembly（WASM）がエッジのユニバーサルランタイムに:** WASMのコンパイルターゲットとしての普及により、Go・Rust・Pythonで書かれたコードがコールドスタートほぼゼロでエッジ実行可能になり、Node.js依存から脱却が加速。

- **データの局所化規制（GDPR・各国データ主権法）への対応手段として確立:** エッジコンピューティングが単なるパフォーマンス最適化ではなく、コンプライアンスアーキテクチャの必須コンポーネントとして設計段階から組み込まれるようになった。

- **エッジ・オリジン間のステート管理が課題から解決フェーズへ:** Durable ObjectsやR2 + KVの組み合わせにより、エッジでの分散ステート管理パターンが成熟。ただしトランザクション整合性はまだ設計上の注意が必要。

- **コスト最適化の複雑化:** リクエスト単価は低いが、エッジロケーション数×実行時間の組み合わせでコストが予測困難になるケースが増加。可観測性（OpenTelemetry対応）とコスト上限設定を設計初期から組み込むことが必須。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）への移行加速:** パスワードレス認証がデファクトスタンダードになりつつあり、フィッシング耐性のあるパスキーへの移行はもはや「推奨」ではなく「必須」。Next.jsプロジェクトでは`@simplewebauthn`の導入を検討すべき。

- **セッション管理の見直し（短命トークン＋ローテーション）:** JWTの有効期限を15分以内に短縮し、リフレッシュトークンのローテーションを実装することで、トークン漏洩時の被害を最小化。`httpOnly` + `Secure` + `SameSite=Strict`クッキーは絶対条件。

- **デバイスフィンガープリンティングによる異常検知:** IPアドレスだけでなく、デバイス情報・行動パターンを組み合わせたリスクベース認証が主流に。新デバイスからのログイン時には追加確認を挟む設計が標準化されている。

- **サプライチェーン攻撃対策としての依存関係監査:** 認証ライブラリへの悪意あるコード混入（npm package hijacking）が増加。`bun audit`の定期実行とSBOM（ソフトウェア部品表）の管理をCI/CDに組み込むことが2026年のベストプラクティス。

- **OAuth 2.1 + DPoP（Demonstration of Proof-of-Possession）の採用:** Bearer tokenの盗用リスクを排除するDPoPがOAuth 2.1で標準化。外部IDプロバイダー連携時はDPoP対応のクライアント実装を選定すること。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6のEdge Runtime対応:** Prisma 6.xからEdge Functionsでのネイティブ実行が安定化し、Supabase Edge FunctionsとのフルスタックTypeScript統合がよりシームレスになった。Cold start問題はPrisma Accelerateのコネクションプーリングで実質的に解消。

- **Supabase pgvectorとAIの統合:** pgvector拡張が成熟し、RAGアーキテクチャをPostgreSQL単体で完結させるパターンが主流に。外部ベクターDBを別途立てるより、Supabaseの既存RLSポリシーをそのまま活用できる点がセキュリティ上有利。

- **Row Level Security（RLS）ファーストの設計:** Supabaseでは認証・認可をアプリ層ではなくDB層（RLS）に集約するアーキテクチャが2026年のベストプラクティス。PrismaからのアクセスもService Role Keyではなくユーザーコンテキストを引き継ぐ設計が推奨される。

- **Prisma Pulse（リアルタイムCDC）の活用:** Prisma PulseがSupabaseのPostgres WALと統合され、イベントドリブンアーキテクチャをORMレベルで構築可能に。WebSocketやPollingを自前実装する必要がなくなりつつある。

- **マイグレーション戦略の二重管理問題:** PrismaマイグレーションとSupabaseマイグレーション（`supabase db push`）の競合が依然として運用上の課題。本番ではSupabase CLIをソースオブトゥルースとし、Prismaは`introspect`モードで同期させるパターンが安全。

### 7. WebAssembly Rust performance 2026

- **Component Model の普及加速:** WASI 0.2 と Component Model が2026年に本格普及し、Rust製WasmコンポーネントがJS/Python等と型安全な形で相互運用可能になった。マイクロサービス的なWasm合成アーキテクチャが現実的な選択肢となっている。

- **SIMD・マルチスレッド最適化の成熟:** WebAssembly SIMD とShared Memory/Atomicsが主要ブラウザで安定稼働し、Rustの`rayon`等を活用した並列処理で、ネイティブ比80-95%のスループットが計測されるケースが増えている。

- **起動レイテンシの改善:** Wasm Binary Compressionとストリーミングコンパイル（`instantiateStreaming`）の最適化により、大規模Rustバイナリでも初期化オーバーヘッドが大幅に削減。サーバーサイド（Cloudflare Workers / Fastly Compute）ではコールドスタートが1ms以下の事例も。

- **メモリ管理の精度向上:** Rust の所有権モデルがGCレスなWasm実行と相性良く、`wasm-bindgen` + `js-sys` の改善でJS↔Wasmのメモリコピーコストが削減。特に画像処理・音声解析・暗号処理領域でReact/JSより10〜50倍高速な実装が実用段階に入っている。

- **Wasmtime / WASMer のサーバー採用:** エッジ・サーバー環境でのWasmランタイム採用が拡大し、DockerコンテナよりもWasmの方が起動速度・セキュリティ分離で優れるユースケースが明確化。Rustでコンパイルした単一バイナリをポータブルに展開するパターンがCI/CDの標準戦略になりつつある。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点では「必要な場所だけ `'use client'`」が鉄則。データフェッチはServer Componentで完結させ、クライアントバンドルを最小化することがパフォーマンスの基本戦略。

- **Partial Prerendering (PPR) の実用化:** 静的シェル＋動的ストリーミングを1ルートで混在できるPPRが安定化。`<Suspense>` 境界設計がアーキテクチャの核心となり、TTFB改善に直結する。

- **Server Actions でAPI Routeを減らす:** フォーム送信・ミューテーションはServer Actionsに集約し、`/api` エンドポイントを外部連携・Webhook専用に絞る設計が主流。ボイラープレートが大幅削減される。

- **`use cache` ディレクティブによるきめ細かいキャッシュ制御:** `fetch` キャッシュオプションから `use cache` + `cacheTag`/`cacheLife` APIへ移行が進む。コンポーネント・関数単位でキャッシュ戦略を宣言できるため、動的コンテンツの鮮度管理が精密化。

- **Turborepo + Turbopack によるモノレポ統合が加速:** Next.js公式のTurbopackが本番利用可能になり、大規模モノレポでのビルド時間が従来比3〜5倍高速化。CI/CDのボトルネックがDB・外部APIに移行している。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge RuntimeからV8 Isolateへの移行加速** — 2026年時点でVercelはV8 Isolateベースのランタイムを標準化しており、コールドスタートが<1msに抑えられる。Node.js互換レイヤーの成熟により、従来のEdge制約（`fs`不可など）が大幅に緩和された。

- **ポイント2: Fluid Computeによるスケーリング最適化** — Vercelが導入したFluid Computeモデルでは、Edge FunctionとServerless Functionの境界が曖昧化し、レイテンシとコスト効率を動的に最適化できる。リージョン選択の手動チューニングが不要になりつつある。

- **ポイント3: キャッシュ戦略の精緻化が最重要** — `stale-while-revalidate`パターンとEdge Cacheの組み合わせが依然として最大のパフォーマンス向上要因。`Cache-Control`ヘッダーの細かい制御（`s-maxage`と`revalidate`の使い分け）がDBヒット削減の鍵。

- **ポイント4: Middleware最適化でバンドルサイズを最小化** — MiddlewareはEdge Runtimeで動作するため、Node.js専用パッケージの混入がビルドエラーの主因。依存関係を厳格に管理し、Middlewareのバンドルサイズを50KB以下に保つことが推奨される。

- **ポイント5: Edge KVとの組み合わせでステートフル処理を実現** — Vercel KV（Redis互換）やDurable Objectsとの統合により、純粋なステートレス制約が実質的に解消。レート制限・A/Bテスト・セッション管理をEdgeで完結できるアーキテクチャが主流になっている。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `string` や `number` をそのまま使わず、`type UserId = string & { readonly brand: 'UserId' }` のような Branded Types がドメイン境界での型安全性確保のデファクトパターンになっている。誤った値の受け渡しをコンパイル時に防げる。

- **`satisfies` 演算子の積極活用:** TypeScript 4.9 以降の `satisfies` が2026年時点で広く普及し、型推論を保持しつつ型チェックを行うパターンが定着。`as` キャストの乱用を排除できる。

- **Template Literal Types による API 型定義:** HTTPメソッドやルートパスを `type Route = \`GET /users/${string}\`` のように型で表現し、実装とスキーマのズレをゼロにする手法が実用段階に達している。

- **`NoInfer<T>` ユーティリティの活用:** TypeScript 5.4 で追加された `NoInfer<T>` により、ジェネリクス関数での意図しない型推論の広がりを制御しやすくなり、ライブラリ設計の品質が向上している。

- **Zod + `z.infer<>` による Runtime/Compile 二重保証:** スキーマ定義から型を自動導出するパターンが標準化され、APIバリデーションと型定義の二重管理が解消。`tRPC` や `Hono` のような型安全フレームワークとの組み合わせが特に効果的。
