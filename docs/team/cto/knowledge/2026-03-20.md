# CTO Knowledge - 2026-03-20

## Daily Update (2026-03-20)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチはサーバーコンポーネントに集約し、インタラクティブな部分のみ `'use client'` に分離する設計が標準となっている。

- **Partial Prerendering (PPR) の本番適用:** Next.js 15以降でStableになったPPRにより、静的シェルと動的コンテンツをルート単位ではなくコンポーネント単位で混在させられる。`<Suspense>` 境界の設計がパフォーマンスの鍵。

- **Turbopack への移行完了:** `next dev --turbo` はほぼ全プロジェクトで安定稼働しており、webpack比でコールドスタートが最大50%高速化。本番ビルドへのTurbopack対応も2026年中に進む見込み。

- **`<Image>` と `next/font` の最適化深化:** AVIFデフォルト化・`sizes` 属性の自動推論により、LCPスコアの改善が容易になっている。フォントはサブセット化と `display: swap` がゼロコンフィグで適用される。

- **Edge Runtime とキャッシュ戦略の再設計:** `fetch` キャッシュのデフォルト動作がNext.js 15で変更（no-store デフォルト）されたため、`revalidate` や `cache` オプションを明示的に指定する設計が必須。CDNエッジでのキャッシュヒット率向上がTTFBに直結する。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化:** 2026年時点では、RSCのストリーミングはSuspense境界を細かく設計することが主流となり、TTFBを最小化しつつLCPを段階的に改善するアーキテクチャパターンが定着している。

- **PPR（Partial Prerendering）の本格採用:** Next.js 15+でStableになったPPRにより、静的シェルを即座に配信しながら動的コンテンツをストリーミングする手法が標準化され、従来のSSR/SSGの二項対立が解消されつつある。

- **Server Actionsとの組み合わせによる楽観的UI:** Server Actionsをストリーミングと組み合わせ、`useOptimistic`で即座にUIを更新しながらサーバー処理を非同期に完了させるパターンが、フォームやミューテーション処理の標準手法となった。

- **キャッシュ戦略の複雑化と`use cache`ディレクティブ:** コンポーネント・関数単位でキャッシュ制御できる`use cache`が登場し、ストリーミング中のデータフェッチをきめ細かく制御できるが、キャッシュ無効化戦略の設計ミスがパフォーマンス劣化の新たな原因となっている。

- **Edge Runtimeでのストリーミング制約への対応:** Vercel Edge・Cloudflare Workersなどのエッジ環境ではNode.js APIが使えないため、RSCのストリーミングをエッジで動かす際はランタイム互換性の確認が依然として重要な実装上の注意点である。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年時点でtRPCはNext.js/TypeScriptスタックにおけるデファクトに近づいており、スキーマ定義なしにクライアント・サーバー間で型を共有できる開発体験が小〜中規模チームに特に支持されている。

- **GraphQLの適用範囲の明確化:** GraphQLは「何でも使える万能解」から「複数クライアント（モバイル/Web）が異なる形状のデータを要求する場合」の専用ツールへと位置づけが収束。BFFパターンと組み合わせたHasura/Stellate等のキャッシュ層が成熟した。

- **REST + OpenAPIの再評価:** Hono・Elysia等の軽量フレームワークがZodベースのスキーマからOpenAPIを自動生成するアプローチを普及させ、「型安全なREST」が現実的な選択肢に。tRPCが使えない外部公開APIや多言語クライアント向けにはRESTが依然として合理的。

- **ストリーミング・リアルタイムAPIの標準化:** Server-Sent Events（SSE）とHTTP/2ストリームがAI系レスポンスのデファクトとなり、WebSocketは双方向通信が必須な場合のみ採用という棲み分けが明確になった。

- **契約駆動開発（Contract-First）の復権:** APIゲートウェイ・マイクロサービス間ではOpenAPI/AsyncAPIを「契約」として先に定義しCIで破壊的変更を検出する運用が標準化。ツール（Speakeasy、Stainless）によりSDK自動生成も実用レベルに達している。

### 4. serverless edge computing 2026

- **ポイント1: エッジでのAI推論が主流化:** 2026年はLLMの軽量化（量子化・蒸留）が進み、Cloudflare Workers AIやVercel Edge Functionsでモデル推論がエッジ実行可能に。レイテンシ50ms以下の実現が現実的になり、バックエンドへのラウンドトリップが不要になる。

- **ポイント2: WASMがランタイムの標準に:** WebAssemblyがV8 Isolatesに代わるエッジランタイムとして台頭。言語非依存で実行可能なため、RustやGoで書いたロジックをそのままエッジにデプロイでき、コールドスタート問題をほぼ解消。

- **ポイント3: ステートフルエッジの実現（Durable Objects / KV進化）:** 従来「エッジはステートレス」が前提だったが、Cloudflare Durable ObjectsやFastly KVの進化により、エッジでセッション管理・リアルタイム協調が可能に。Next.jsのようなフルスタックフレームワークとの統合が加速。

- **ポイント4: コスト構造の変革:** リクエスト課金からCPU時間課金へのシフトが定着。エッジ実行はオリジンサーバー負荷を60〜80%削減できるケースもあり、インフラコスト最適化の主戦場になっている。

- **ポイント5: セキュリティ境界の再設計が必須:** エッジでビジネスロジックが動くことで、WAF・レート制限・認証処理もエッジに移行。ただし分散実行によるシークレット管理（環境変数の安全な配布）と監査ログ収集が新たな課題として浮上しており、ゼロトラスト設計の徹底が求められる。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の本格普及:** 2026年はパスワードレス認証が業界標準となり、フィッシング耐性のあるパスキーへの移行が加速。新規プロダクトでは最初からパスワード認証を採用しないアーキテクチャ設計が推奨される。

- **セッション管理のゼロトラスト化:** 「一度認証すれば信頼する」モデルは廃止され、コンテキスト（デバイス・IP・行動パターン）を継続評価するContinuous Authentication（継続的認証）が主流。短命トークン（15分以内）＋サイレントリフレッシュの組み合わせが標準実装。

- **AIを活用した異常検知の組み込み:** ログイン試行パターンの機械学習分析により、クレデンシャルスタッフィング攻撃をリアルタイム検出。レート制限だけでは不十分で、行動バイオメトリクスとの組み合わせが有効。

- **サプライチェーンリスクとしての認証ライブラリ管理:** OAuth/OIDCライブラリへの依存が増える中、依存ライブラリの定期監査（`npm audit` / Dependabot）と固定バージョン管理が必須。Auth0・Cognitoなどのマネージドサービス利用でも、設定ミス（過剰なスコープ・コールバックURL未制限）が主要攻撃ベクターとなっている。

- **MFAの「疲労攻撃」対策:** プッシュ通知型MFAへのMFA Fatigue攻撃が増加。番号マッチング（Number Matching）や追加コンテキスト表示の義務化が進んでおり、TOTPかパスキーへの切り替えが安全策として推奨される。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6 + Supabase の統合成熟:** Prisma v6ではEdge Runtime対応が強化され、Supabase Edge Functionsとの組み合わせでサーバーレス環境でのORM利用が実用レベルに達した。`@prisma/adapter-neon` や `prisma-supabase` アダプター経由のコネクションプーリングが標準構成になりつつある。

- **Row Level Security (RLS) とORMの責務分離:** SupabaseのRLSをDB層のセキュリティ境界として活用し、Prismaはアプリ層のクエリビルダーに徹する設計が推奨される。RLSをバイパスする `service_role` キーの扱いに注意が必要。

- **Prisma Accelerate によるグローバルキャッシュ:** Prisma Accelerateの接続プールとエッジキャッシュを活用することで、Supabaseへの直接接続数の枯渇問題（デフォルト上限の低さ）を回避できる。特にサーバーレス環境では必須の検討事項。

- **型安全なリアルタイム設計の課題:** SupabaseのRealtime（Broadcast/Presence）はPrismaのスキーマと独立しているため、型の整合性を保つには `zod` スキーマの二重管理が発生しやすい。2026年時点でもこの乖離は未解決であり、カスタム型ガードでのラッピングが現実的な対応策。

- **マイグレーション戦略の統一:** `prisma migrate` と Supabase CLIのマイグレーション（`supabase db push`）が競合しやすい。CI/CDでは `prisma migrate deploy` を正とし、Supabase Dashboardからの直接スキーマ変更を禁止するガバナンスルールが重要。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** **WASIp2（Component Model）が本番実用段階に到達** — 2026年時点でWASI Preview 2が安定し、RustのWASMコンポーネントをホスト言語非依存でCompose可能に。マイクロサービス境界でのRust WASMモジュール再利用が現実的な選択肢になった。

- **ポイント2:** **SIMD・スレッド対応の成熟でネイティブに肉薄するパフォーマンス** — WebAssembly SIMD（Fixed-width SIMD）が全主要ブラウザで安定稼働し、Rustの`packed_simd`等を活用した画像・音声処理はネイティブ比90%以上のスループットを達成するケースが増加。

- **ポイント3:** **`wasm-bindgen` + `wasm-pack`の成熟でJS/TSとの統合コストが激減** — TypeScript型定義の自動生成精度が向上し、RustロジックをNPMパッケージとして配布するパターンが標準化。バンドルサイズも`wasm-opt`の自動適用で50-70%削減が当たり前に。

- **ポイント4:** **エッジランタイム（Cloudflare Workers, Fastly Compute）でのRust WASMが主戦場** — V8 IsolateよりもWASMの起動レイテンシが低く、Cold start問題の解決策としてRust+WASMがエッジ処理の事実上の標準に近づいている。

- **ポイント5:** **GCプロポーザル不要のRustが参照型言語より有利な局面が明確化** — GC搭載言語（Go, Kotlin/Wasm）は初期化コストとメモリオーバーヘッドが残るのに対し、Rustは予測可能なメモリ使用量でリアルタイム処理・ゲームロジック・暗号処理に適している。

**実務への示唆:** sumitsugiのような検索・マッチングロジックの重い計算部分（類似度スコアリング等）をRust+WASMに切り出すことで、エッジキャッシュと組み合わせたレイテンシ削減が狙えます。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** 2026年現在、Server Componentsをデフォルトとし、インタラクティビティが必要な箇所のみ `"use client"` を付与するパターンが定着。クライアントバンドルを最小化しCore Web Vitalsを大幅に改善できる。

- **PPR（Partial Prerendering）の本格活用:** 静的シェルと動的コンテンツを同一ページで混在させるPPRが安定版となり、`<Suspense>` 境界を戦略的に配置することでTTFBとインタラクティビティを両立するアーキテクチャが標準化されつつある。

- **Server Actions によるAPI Routes の代替:** フォームや突然変異処理にServer Actionsを使うことでAPI Routes の冗長なボイラープレートを排除できる。ただし複雑なバリデーションはZodとの組み合わせ必須、過信するとセキュリティホールになりやすい点に注意。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** `next/cache` のタグベース無効化に加え、関数レベルで `use cache` を宣言できるようになり、データフェッチ層のキャッシュ戦略がより宣言的に記述可能。`revalidateTag` との組み合わせでCMS連携が格段にシンプルになる。

- **Turbopack の本番利用解禁:** Turbopackが`next build`でも利用可能となり、大規模プロジェクトでのビルド時間が従来比50〜80%削減。ただし一部プラグインとの互換性確認は依然必要なため、段階的移行（まずdev環境から）を推奨。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** **Edge Runtimeのコールドスタート排除が最優先** — 2026年時点でVercel Edge Functionsは従来のServerless Functionsと比べコールドスタートがほぼゼロだが、バンドルサイズを1MB以下に抑えることがレイテンシ維持の鍵。`export const runtime = 'edge'` 指定時は不要なNode.js APIへの依存を排除すること。

- **ポイント2:** **Streaming ResponseとSuspenseの組み合わせが標準パターンに** — `ReadableStream` + React Server ComponentsのSuspenseによる段階的レンダリングが主流。LCP改善に直結するため、重いデータフェッチを持つルートは積極的にストリーミング化すべき。

- **ポイント3:** **キャッシュ戦略の再設計が必須** — Edge Functionsは地理分散されるため、`Cache-Control` + `stale-while-revalidate` の設計が複雑になる。Vercel Data CacheやKV（Upstash等）をEdge近傍に配置し、DB直撃を避けるアーキテクチャが推奨。

- **ポイント4:** **Middleware最適化でルーティングコストを削減** — `middleware.ts` での認証・リダイレクト処理はすべてのリクエストに適用されるため、`matcher` で対象パスを厳密に絞ること。不要なmiddleware実行がp95レイテンシに影響する。

- **ポイント5:** **WebAssembly(WASM)活用で処理能力の拡張** — Edge RuntimeはNode.js非対応APIがある一方、WASMは実行可能。画像処理・暗号化・バリデーション等の重い処理をWASMにオフロードすることでCPU制限を回避できる。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded/Nominal Typingが標準的な防御パターンとなり、ドメイン間での誤った値渡しをコンパイル時に防止できる。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` が2026年では必須知識となり、型推論を維持しながら型チェックを強制できるため、`as const` との組み合わせで設定オブジェクトの型安全性が大幅に向上する。

- **Template Literal Types によるAPI契約:** `type Route = `/api/${string}`  ` のようなテンプレートリテラル型がURLルーティングやイベント名のタイプセーフな表現に多用され、ランタイムエラーをゼロに近づけられる。

- **`noUncheckedIndexedAccess` の標準化:** `tsconfig.json` でこのオプションを有効化することで配列・オブジェクトアクセス時に `T | undefined` が返るようになり、nullableな値の見落としを構造的に排除できる—2026年では厳格モードの一部として扱われる傾向にある。

- **Zod + infer によるSchema-First型定義:** バックエンド・フロントエンド間の型共有には `z.infer<typeof schema>` でランタイムバリデーションと静的型を一元管理するパターンが定着しており、`tRPC` 等と組み合わせることでAPI境界での型安全性が完全に確保できる。
