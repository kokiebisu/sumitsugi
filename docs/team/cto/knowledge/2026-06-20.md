# CTO Knowledge - 2026-06-20

## Daily Update (2026-06-20)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Prerendering の本格採用）:** Next.js 14で実験的導入されたPPRが14/15系で安定し、静的シェルと動的コンテンツを1ページ内で混在させられるため、TTFBを保ったままパーソナライズされたUIを配信できる。`loading.tsx`やSuspenseの境界設計が性能チューニングの主戦場になる。

- **ポイント2（Turbopackのビルド/devサーバー標準化）:** Webpackからの移行が進み、devサーバー起動とHMRが大幅高速化。大規模モノレポではビルド時間がCIコストに直結するため、Turbopack移行はインフラコスト削減としても効果が大きい。

- **ポイント3（Server Componentsでのデータフェッチ最適化）:** `fetch`のリクエストメモ化・`cache`/`unstable_cache`の活用で、同一レンダリング内の重複リクエストを排除しつつ、必要な箇所だけ`revalidateTag`で再生成する戦略が定着。N+1的なサーバーフェッチを防ぐレビュー観点が重要になる。

- **ポイント4（画像・フォントの自動最適化の深化）:** `next/image`のAVIF優先配信や`next/font`のセルフホスティングが標準となり、Core Web Vitals（特にLCP・CLS）改善がほぼ設定不要で得られる。逆に外部CDN画像やWeb Fontを混在させると最適化の恩恵が消えるため、構成の一貫性が鍵。

- **ポイント5（Edge RuntimeとISRの併用設計）:** Edge Middlewareでの認証・リダイレクト処理とISR/On-Demand Revalidationを組み合わせ、グローバルなレイテンシ低減とコンテンツ鮮度を両立する設計が主流に。リアルタイム性が低いページ（物件一覧など）はISR、認証分岐のような軽量処理はEdgeに寄せる判断基準が重要。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分のみをストリーミングする手法が主流に。sumitsugiの物件詳細ページのような「ほぼ静的だが一部動的（在庫状況等）」な構成に有効。

- **Server Actions + Streaming のエラーバウンダリ設計:** ストリーミング中の例外処理が複雑化しており、`Suspense`境界ごとに`error.tsx`を細かく配置する設計が定石化。1つのSuspenseの失敗が全体のストリームをブロックしないよう、コンポーネント単位の粒度設計が重要。

- **Cache Components / `use cache` ディレクティブの普及:** React 19系で導入されたキャッシュ境界をRSCストリーミングと組み合わせ、DB問い合わせ（前の住人情報、引越し費用計算など）を再フェッチせず再利用するパターンが一般化。

- **クライアントバンドル削減への寄与:** RSCストリーミングにより「最初に見えるべき情報」（物件一覧の上部カード等）を優先送信し、LCP改善とJS転送量削減を同時に達成できる。Airbnb風UIのようなカード一覧UIでは特に効果が大きい。

- **計測の難しさが残る:** ストリーミング順序がネットワーク状況に依存するため、従来のLighthouse単発計測では実体感とズレが出やすく、フィールドデータ（CrUX/Web Vitals実測）ベースの監視が必須という認識が定着してきている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCのTypeScript統一プロジェクトでの優位性:** sumitsugiのようなNext.js App Router + TypeScriptの単一リポジトリ構成では、tRPCがスキーマ定義とクライアント型を自動同期できるため、Zodバリデーションと組み合わせれば型安全なAPI層を最小コストで構築できる。GraphQLのような別レイヤーのスキーマ管理コストが不要な点が2026年も支持される理由。

- **GraphQLは「複数クライアント・複雑なデータ取得」がある場合のみ採用:** モバイルアプリや外部パートナー向けAPIなど、クライアントごとに必要なフィールドが大きく異なるケースでなければ、GraphQLのオーバーフェッチ対策コスト（リゾルバ設計、N+1対策、キャッシュ戦略）はROIが低い。社内向け単一フロントエンドが中心ならtRPC/RESTで十分。

- **RESTは外部公開APIや長期互換性が必要な場合の第一選択:** 物件情報や引き継ぎフローを将来的にパートナー企業や外部システムに公開する可能性があるなら、OpenAPI仕様で明示的にバージョニングできるRESTの方が長期的な互換性管理がしやすい。tRPCは型共有が前提のためTypeScript外のクライアントには不向き。

- **エッジ・Server Actions統合がAPI設計の境界を変えている:** Next.js 16のServer ActionsやRSCの普及により、「API」を明示的にエンドポイント化せずサーバー関数を直接呼ぶパターンが増加。社内向けの簡易な処理（フォーム送信など）はServer Actionsに任せ、外部公開や複雑なビジネスロジックのみtRPC/REST化する設計分離が2026年のベストプラクティス。

- **AIエージェント連携を見据えたAPI設計:** LLMエージェントがAPIを直接呼ぶケースが増えており、関数呼び出し用のJSON Schemaを自然に生成できる構造（Zod→OpenAPI/JSON Schema変換）を持つAPI設計が将来的な拡張性を高める。tRPCルーターからのスキーマ抽出はこの点でも相性が良い。

### 4. serverless edge computing 2026

- **エッジでのフルスタック実行:** Cloudflare WorkersやVercel Edge FunctionsがNode.js互換性を強化し、DBアクセス（D1, Turso, PlanetScale）までエッジで完結可能に。sumitsugiのような物件検索・絵フィルタリングは、リージョン跨ぎのレイテンシ削減効果が大きい。

- **コールドスタートの実質ゼロ化:** V8 isolateベースの実行モデルが主流化し、従来のコンテナ型サーバーレスより起動が1桁早い。Next.js 16のEdge Runtimeはこの恩恵を直接受けられるため、bun devでのローカル検証と本番挙動の差異に注意が必要。

- **WASMによる言語非依存化:** Rust/Goで書いた重い処理（画像リサイズ、PDF生成）をWASMコンパイルしてエッジで実行するパターンが定着。物件写真の最適化や引越し費用計算のような重い処理を、ユーザー近接ノードで処理できる。

- **エッジ環境特有の制約:** ファイルシステムアクセス不可、実行時間制限、Node API互換性の差異により、本番で動いていたコードがエッジで動かないケースが頻発。CI/CDにエッジ環境専用のスモークテストを組み込むことが必須になっている。

- **観測性（Observability）の追いつき:** 分散実行モデルゆえにトレーシング・ログ集約が難しく、OpenTelemetry対応のエッジネイティブAPM（Sentry, Axiom等）導入が2026年のデファクトに。本番障害時の原因特定速度に直結するため、早期導入を推奨。

### 5. authentication security best practices 2026

- **パスキー/WebAuthnの標準化:** パスワードレス認証（FIDO2/WebAuthn）が主流となり、フィッシング耐性のある認証がデフォルトに。実装コストも下がり、Supabase AuthやAuth0等の主要プロバイダが標準サポートしている。

- **多層防御としてのデバイスバインディング:** トークン窃取（XSS、セッションハイジャック）対策として、リフレッシュトークンをデバイスフィンガープリントやDPoP（Demonstrating Proof-of-Possession）で紐付ける手法が標準化しつつある。

- **短命アクセストークン + 厳格なリフレッシュローテーション:** アクセストークンのTTLを15分以内に短縮し、リフレッシュトークン再利用検知（reuse detection）で漏洩時の被害範囲を最小化するのが現在のベストプラクティス。

- **認可ロジックのDB層集約（RLS）:** SupabaseのRow Level Securityのように、認可をアプリケーションコードからDB層に移すことで「うっかり認可漏れ」のクラスを構造的に排除できる。sumitsugiのような不動産プラットフォームでは物件オーナー/閲覧者の権限分離に有効。

- **シークレット管理の自動ローテーション:** 環境変数への直接ハードコードを排除するだけでなく、APIキー・DBクレデンシャルの自動ローテーション（短期間で失効）をCI/CDに組み込み、漏洩時の露出期間を最小化する流れが加速している。

### 6. database architecture Prisma Supabase 2026

- **Prisma + Supabase接続プーリング:** Supabase上でPrismaを使う際はPgBouncer経由のTransaction modeが必須。Prisma Migrateはこのプール越しだとDDL実行に失敗するため、マイグレーション用に直接接続URL（ポート5432）とアプリ用のプール接続URL（ポート6543）を分け、`DATABASE_URL`/`DIRECT_URL`の二系統で管理するのがデファクトになっている。

- **RLS（Row Level Security）とPrismaの併用:** SupabaseのRLSはPostgresレベルのセキュリティだが、PrismaクライアントはService Roleキーで接続するためRLSをバイパスしがち。認証ユーザー単位のアクセス制御が必要な箇所はRLSに頼らず、アプリ層（API Route/Server Action）でのテナント分離チェックを必須化すべき。

- **Prisma Accelerate / Edge対応:** Next.js 16のEdge RuntimeやVercel Edge Functionsから直接PostgresにTCP接続できないため、Prisma AccelerateやSupabaseのData APIを介したHTTPベースのアクセスが主流になっている。sumitsugiのようにApp Router中心の構成では、どのRoute Handlerをedge/nodeランタイムにするかで接続方式が変わる点に注意。

- **マイグレーション運用の二重管理リスク:** SupabaseのダッシュボードでスキーマをGUI変更すると、Prismaの`schema.prisma`とDB実態がドリフトする。`prisma db pull`での同期か、Supabase側のスキーマ変更を禁止してPrisma Migrateを単一の真実源とする運用ルールの徹底が重要。

- **型安全性とパフォーマンスのトレードオフ:** Prismaの自動生成クライアントはDX（開発体験）に優れるが、N+1クエリを生みやすい（`include`の多用）。物件一覧のような高頻度アクセスのエンドポイントは、Prismaの`select`を絞るか、複雑な集計はSupabaseのRPC（Postgres関数）に落として実行計画を最適化する判断が必要。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデルの安定化:** WASI Preview 2/Component Modelが本格普及し、Rust製WasmコンポーネントをJS/Python/Goなど他言語から透過的に呼び出せるようになった。マイクロサービス境界をWasmサンドボックスで切る設計が選択肢として現実的に。

- **メモリ管理の高速化:** `wasm-gc`の主要ランタイム対応進展により、RustのGCなし設計の優位性がより活きる形になり、特にCPU負荷の高い画像処理・パーサー系処理でJS実装比2〜5倍の速度差が出るケースが増えている。

- **ビルドサイズとコールドスタート最適化:** `wasm-opt`/LTOチューニングとtree-shaking精度向上で、バイナリサイズを数百KB台まで縮小可能になり、エッジ（Cloudflare Workers等）でのコールドスタートが数msレベルに短縮されている。

- **デバッグ・プロファイリング体験の向上:** DWARF対応とブラウザDevToolsのソースマップ統合が進み、Wasmの「デバッグしにくい」という従来の弱点が大きく改善された。本番導入の心理的障壁が下がっている。

- **実用判断の指針:** 全部をWasm化するのではなく、計算負荷の高いホットパス（画像/動画処理、暗号化、パーシング）だけをRust+Wasmに切り出し、UIロジックはJSに残すハイブリッド構成が最もROIが高い。

### 8. Next.js App Router patterns 2026

- **ポイント1: Partial Prerendering (PPR) の標準化** — Next.js 16ではPPRが安定版となり、静的シェルと動的コンテンツを1つのルートで共存させられる。物件一覧ページのように「ヘッダーは静的・在庫データは動的」という構成に最適で、TTFBを大きく改善できる。

- **ポイント2: Server Actions中心のデータ変更フロー** — フォーム送信やミューテーションをAPI Routeではなく`"use server"`関数に寄せる設計が定着し、`src/app/properties/`のような物件登録・更新フローではクライアントJSバンドルを削減しつつ型安全性を維持できる。

- **ポイント3: キャッシュ戦略の明示化（`cacheLife`/`cacheTag`）** — 暗黙的なフルルートキャッシュから、`use cache`ディレクティブ＋明示的なタグ・有効期限指定への移行が進んでいる。物件ステータス（`draft`/`public`）の切り替えなど即時反映が必要な箇所は`revalidateTag`で個別制御すべき。

- **ポイント4: Server Componentsでのcomposition優先設計** — Client Componentの「島」を最小化し、`auth-context.tsx`のようなContextは本当に必要な境界だけに絞る運用がベストプラクティス化。バンドルサイズとHydration負荷の両方を抑えられる。

- **ポイント5: Streaming + Suspenseによる段階的UX** — 引っ越し費用見積もりや前の住人情報取得など、レイテンシの異なるデータ取得を`loading.tsx`/`<Suspense>`で分離し、Airbnb風UIで重視される「即時表示→徐々に詳細」という体験を技術的に実現しやすくなっている。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Fluid Compute によるコールドスタート解消** Vercelの Fluid Compute モデルがデフォルト化し、Edge FunctionsとServerless Functionsの境界が薄れつつある。リクエスト間でインスタンスを再利用する仕組みにより、コールドスタートのレイテンシをほぼゼロに抑えられるため、引越し費用計算や物件検索APIなど頻繁に呼ばれるエンドポイントで特に効果が大きい。

- **ポイント2: リージョン選択よりも「データ近接性」が重要** Edge Functionsは実行リージョンを自動最適化するが、DB（例: Supabase/Postgres）のリージョンとの距離がボトルネックになりやすい。物件データのようにリードが多いワークロードはRead Replicaやエッジキャッシュ（ISR/Data Cache）と組み合わせて、DBラウンドトリップを減らす設計が2026年のベストプラクティス。

- **ポイント3: Streaming SSRとPartial Prerenderingの併用** Next.js 16のPPR（Partial Prerendering）とEdge Runtimeを組み合わせることで、静的な物件一覧シェルを即時表示しつつ、価格や空き状況などの動的部分だけをストリーミングできる。UI応答性が大きく改善し、特にモバイル回線での初期表示速度に効く。

- **ポイント4: ミドルウェアの肥大化に注意** Edge Middlewareは認証チェックやリダイレクトに便利だが、コード量とNode.js非対応API（一部のcrypto/fsなど）の制約により、ロジックが複雑化すると実行時間制限（CPU時間）に引っかかりやすい。認証は`auth-context`側で軽量化し、重い処理はServer Actionsに移すべき。

- **ポイント5: コスト最適化はインボケーション課金ではなく実行時間課金で考える** 2026年のVercel価格モデルではEdge FunctionsはCPU時間ベース課金が主流になっており、無駄なJSON parse/外部fetchの直列化を避け、`Promise.all`での並列化やレスポンスキャッシュ（`Cache-Control`+ISR）を徹底することが、トラフィック増加時のコスト管理に直結する。

### 10. TypeScript type safety patterns 2026

- **型述語よりも `satisfies` 活用:** `as const satisfies` パターンでリテラル型を保持しつつ型チェックを行う書き方が定着し、過剰な型アサーションを減らせる。sumitsugiの`site-config.ts`のような設定オブジェクトに有効。

- **Branded Types でのドメイン境界保護:** `PropertyId`や`UserId`のような名目的型をbranded typeで実装し、`string`の取り違えをコンパイル時に検出する手法が、Zodバリデーションと組み合わせて標準化しつつある。

- **テンプレートリテラル型によるAPI契約の静的検証:** ルーティングパスやAPIエンドポイントをテンプレートリテラル型で表現し、`src/app/`のApp Router構造とパス文字列の整合性をビルド時に保証する事例が増加。

- **Zodスキーマからの型推論の一方向化:** `z.infer<typeof schema>`を唯一の型ソースとし、TypeScript型を別途手書きしない「スキーマファースト」が標準パターン化。境界（フォーム入力・API応答）でのバリデーションと型定義の重複を排除できる。

- **`unknown`優先とtype narrowingの厳格化:** `any`を排除し`unknown`+カスタムtype guardを使う設計が、ESLintルール（`no-explicit-any`）とセットで強制されるケースが増え、ランタイムエラーの早期検出につながる。
