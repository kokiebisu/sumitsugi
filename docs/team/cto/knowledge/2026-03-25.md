# CTO Knowledge - 2026-03-25

## Daily Update (2026-03-25)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチやロジックは可能な限りServer Componentsに寄せる。`"use client"`ディレクティブは本当に必要な末端コンポーネントのみに絞ること。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降でstableになったPPRにより、静的シェルと動的コンテンツを同一ルートで共存させられる。`<Suspense>`境界の設計がパフォーマンスの鍵になる。

- **Turbopackへの移行完了:** 2026時点でTurbopackはproductionビルドも対応済み。開発サーバーの起動・HMR速度が大幅改善されるため、未移行プロジェクトは積極的に切り替えるべきタイミング。

- **`next/image` と `next/font` の最適化強化:** AVIFフォーマット対応とサブセット化フォントのゼロレイアウトシフトが成熟。Core Web Vitals（LCP/CLS）改善の即効策として優先度が高い。

- **Edge Runtimeの選択的利用:** ミドルウェアや軽量APIはEdgeで処理し、Node.jsランタイムはDB接続が必要な重い処理に限定する。Cold startとランタイム制約のトレードオフを設計段階で意識することが重要。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Prerendering (PPR) の本格普及:** Next.js 15以降でPPRが安定化し、静的シェルと動的ストリーミングコンテンツを同一ページ内で効率的に組み合わせられるようになった。TTFBとLCPの両立が現実的な選択肢になっている。

- **ポイント2: Suspense境界の設計がアーキテクチャの要になる:** ストリーミングの粒度はSuspense境界の配置で決まるため、コンポーネント設計段階でデータ依存関係を明示的にモデリングする必要がある。「データが揃ってからレンダリング」思考から「いつ何をストリームするか」思考への転換が求められる。

- **ポイント3: Server Actions との統合でクライアントJSをさらに削減:** Server ActionsがRSCと組み合わさることで、フォームやミューテーション処理のクライアントバンドルへの依存がほぼゼロに近づいている。モバイルファーストなプロダクトでは体感速度に直結する。

- **ポイント4: エラーハンドリングとローディングUIの標準化が課題:** `error.tsx` / `loading.tsx` のルートレベル管理と、細粒度Suspenseの組み合わせでUXが大きく変わる。ストリーミング中のエラー回復戦略をチームで統一しないと、ユーザー体験がバラつく。

- **ポイント5: エッジランタイムとの相性がさらに向上:** Cloudflare WorkersやVercel Edge Runtimeでのストリーミング対応が成熟し、グローバルユーザーへの初期レスポンスを低レイテンシで届けるアーキテクチャが実用段階に入っている。インフラ選定時にNode.jsランタイムとエッジランタイムのトレードオフを意識することが重要。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全API:** 2026年時点でtRPCはフルスタックTypeScriptプロジェクトのデファクトに近い存在となっており、スキーマ定義不要でエンドツーエンドの型安全性を実現できる点が特に小〜中規模チームに支持されている。

- **GraphQLの選択基準の明確化:** GraphQLは「複数クライアント（Web/Mobile/外部）が異なるデータシェイプを要求する」ケースに絞られつつあり、内部API用途ではオーバーヘッドが大きいとして敬遠されるトレンドが加速している。

- **REST + OpenAPIの再評価:** OpenAPI 3.1 + コード生成（`openapi-ts`等）の成熟により、REST APIでも型安全なクライアント生成が容易になり、「tRPCほど密結合でなくて良い」公開APIや外部連携ではRESTが依然として合理的選択となっている。

- **エッジ・ストリーミング対応の必要性:** Vercel AI SDKやCloudflare Workersの普及により、APIはServer-Sent Events / ReadableStreamベースのストリーミングレスポンスを標準サポートすることが求められるようになっており、設計段階からストリーミング経路を考慮する必要がある。

- **プロトコル選択よりコントラクトファーストの思想が重要:** REST/GraphQL/tRPCのどれを選ぶかより、スキーマやZodバリデーションを「Single Source of Truth」として設計し、クライアント・サーバー間のコントラクトを自動生成・検証するアーキテクチャが2026年の主流パターンになっている。

### 4. serverless edge computing 2026

- **ポイント1: WebAssembly（Wasm）がエッジの標準ランタイムに:** V8 IsolatesからWasmへの移行が加速し、言語非依存でコールドスタートほぼゼロを実現。Cloudflare Workers・Fastly Computeが主導するこのシフトは、Rustや Go製マイクロサービスのエッジ直接デプロイを現実のものにしている。

- **ポイント2: エッジDBとエッジKVの統合が本格化:** Cloudflare D1・Turso・Neon Serverlessなどエッジ近傍のSQLiteクローンが実用域に達し、「エッジで読み書き完結」アーキテクチャが設計の選択肢に。レイテンシP99を劇的に削減できるが、整合性モデルの理解が必須。

- **ポイント3: AI推論のエッジオフロードが競争優位に:** LLM量子化（GGUF/Q4等）の進化でエッジノードでの小規模推論が可能になり、プライバシー要件の高いユースケースでクラウドへのデータ送信を回避できる。Sumitsugiのような個人情報を扱うプラットフォームには特に注目すべきトレンド。

- **ポイント4: オブザーバビリティの分散課題が顕在化:** エッジ拠点が200+になると従来の集中型ログ・トレーシングが機能不全に。OTel（OpenTelemetry）のエッジ対応と、Grafana Alloy等のエッジ側コレクターの組み合わせが実務的解答になりつつある。

- **ポイント5: コスト最適化の主戦場がCPU時間→リクエスト課金へ:** 従来のサーバーレスはGB-秒課金だったが、エッジは実行時間が極短のためリクエスト数・データ転送量が支配的コスト因子に。アーキテクチャ設計段階でリクエスト集約（batching）とキャッシュ戦略を組み込まないと、スケール時に予算超過しやすい。

### 5. authentication security best practices 2026

**authentication security best practices 2026** — CTO視点からの主要ポイント:

- **パスキー（FIDO2）への移行加速:** パスワードレス認証がデファクトスタンダードになりつつあり、WebAuthn/パスキーの採用はフィッシング耐性を根本的に解決する。新規サービスはパスワード認証をレガシー扱いにして設計すべき。

- **セッション管理の厳格化:** JWTの有効期限を短く（15分）設定し、リフレッシュトークンのローテーションを必須化。トークン漏洩時の爆発半径を最小化することが2026年の標準的な設計。

- **デバイスバインド認証の台頭:** 認証情報をデバイスのTPM/Secure Enclaveにバインドすることで、トークン窃取攻撃に対する耐性を強化。モバイルアプリでは特に重要。

- **継続的認証（Continuous Authentication）:** ログイン時点だけでなく、行動パターン・位置情報・デバイス指紋を用いてセッション中もリスクスコアを継続評価。異常検知時に再認証を要求するゼロトラスト設計が主流化。

- **OAuthフローのセキュリティ強化:** PKCE必須化はすでに標準だが、さらに `DPoP`（Demonstrating Proof of Possession）によるトークンバインディングが普及。アクセストークンを盗んでも別環境では使えない仕組みへ。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6 + Supabase の組み合わせが標準化:** Prisma ORM v6（2025年リリース）ではEdge Runtime対応とコネクションプーリングが大幅改善され、Supabase の Pgbouncer / Supavisor との相性が向上。サーバーレス環境でのコールドスタート問題がほぼ解消された。

- **Row Level Security (RLS) をアーキテクチャの中心に置く設計が主流に:** Supabase のRLSをORMレイヤーではなくDB側で担保する設計が普及し、Prisma は `SET LOCAL role` でユーザーコンテキストを渡すパターンが定石化。アプリ層でのアクセス制御よりもセキュアで漏れが少ない。

- **Postgres の拡張機能（pgvector / pg_cron）活用が必須知識に:** AI機能組み込みにpgvectorが不可欠となり、Supabase上でベクトル検索とリレーショナルデータを同一DBで管理するアーキテクチャが標準。Prisma の `$queryRaw` でネイティブ関数を呼び出す実装パターンを習得しておくべき。

- **スキーマ管理は Prisma Migrate ではなく supabase CLI migrate に移行するチームが増加:** Supabase のマイグレーション管理（`supabase db push` / `supabase migration`）とPrismaのスキーマ定義を分離し、Prismaはクエリビルダーとして使い、DDLはSupabase CLIで管理するアーキテクチャが本番環境での安定性が高い。

- **リアルタイム機能はRLSと連動したRealtime Channelsへ:** Supabase Realtime v2 ではRLSポリシーがWebSocketの購読権限にも適用されるようになり、クライアントからの直接DB購読が安全に実現可能。Prismaとの組み合わせでは、書き込みはPrisma経由・リアルタイム受信はSupabase Clientという役割分担が最適解。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の本格普及:** WASI Preview 2がスタンダードになり、RustからWasmコンポーネントをビルドする際のインターフェース型安全性と相互運用性が大幅向上。`cargo component`ツールチェーンが実用レベルに達した。

- **SIMD・スレッド対応の成熟:** WebAssembly SIMDとShared Memoryスレッドが主要ブラウザ・ランタイムで安定し、RustのSIMD intrinsicsがそのままWasm向けにコンパイル可能に。CPU集約型処理（画像/音声/ML推論）でネイティブに近いスループットを達成できる。

- **Wasmtime/WasmEdgeのサーバーサイド採用加速:** エッジコンピューティング（Fastly、Cloudflare Workers等）でRust+Wasmのコールドスタートがコンテナ比100倍高速な事例が増加。サーバーレス関数の実行基盤として実績が積み上がっている。

- **バイナリサイズ最適化の進化:** `wasm-opt`（Binaryen）とRustコンパイラのLTO・`panic=abort`組み合わせで、本番バイナリを50-200KB台に抑えられるケースが標準化。`twiggy`等のサイズプロファイラが開発フローに組み込まれてきた。

- **GC提案とRust ABI境界の整理:** WebAssembly GC proposalの普及でJS↔Wasm間のデータ受け渡しオーバーヘッドが減少傾向。ただしRustは`no_gc`モデルのまま強みを発揮するため、「Rustはパフォーマンスクリティカルなモジュール、GC言語はオーケストレーション層」という役割分担が設計定石になりつつある。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** クライアントバンドルを最小化するため、デフォルトをServer Componentsとし、インタラクティブな部分のみ`'use client'`を付与する境界設計が定着。コンポーネントツリーの末端にクライアント境界を押し込む「leaf node pattern」が標準化されている。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的ストリーミングを同一ルートで混在させるPPRが安定版となり、`<Suspense>`境界による段階的ハイドレーションが高トラフィックサービスでの選択肢になっている。

- **Server Actions によるAPI層の簡略化:** フォーム送信・ミューテーション処理をServer Actionsで完結させることで、従来の`/api`ルートが不要になるケースが増加。ただし複雑なバリデーション（Zod）や認証チェックを必ずServer Action内に実装しないとセキュリティホールになる点に注意。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** `revalidatePath`/`revalidateTag`に加え、関数レベルで`use cache`を宣言する新APIにより、データフェッチとキャッシュ戦略をコードと同じ場所で管理できるようになり、キャッシュの見通しが大幅に改善。

- **型安全なルーティング:** `next/navigation`の型推論強化と`typedRoutes`設定が普及し、`router.push('/typo')`のような実行時エラーをビルド時に検出できる体制が整いつつある。本プロジェクトでも`tsconfig`に`typedRoutes: true`の追加を推奨。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge RuntimeでのStreaming Response活用:** 2026年現在、Edge FunctionsはStreaming SSEやReadableStreamを活用したリアルタイムレスポンスが主流になっており、初回バイト時間（TTFB）を大幅に削減できる。特にAI系APIとの組み合わせで効果が顕著。

- **ポイント2: Cold Start撲滅のためのWarm-up戦略:** Edge Runtimeは従来のNode.jsより起動が速いが、依存モジュールの重さがボトルネックになる。`import`の遅延読み込みとバンドルサイズの最小化（目安: 1MB以下）が依然として最重要チューニング項目。

- **ポイント3: KV・Durable Objectsとのデータ局所性の最適化:** Vercel KVやCloudflare Workers KVをEdgeと同一リージョンに配置する「データ局所性」設計が2026年のベストプラクティス。リクエストとデータが地理的に離れていると、Edgeの低レイテンシ効果が完全に失われる。

- **ポイント4: ミドルウェアの責務分離:** `middleware.ts`に認証・A/Bテスト・地域振り分けを集約しすぎると処理時間が増大する。各ミドルウェアの実行時間を計測し、50ms超の処理は原則としてEdge Functionではなくサーバーサイドへ移譲する設計が推奨される。

- **ポイント5: Observabilityの強化:** Edge環境での`console.log`はコスト増につながるため、OpenTelemetry準拠のトレーシング（Vercel Observability連携）を使い、サンプリングレートを調整しながら本番モニタリングを行うことが不可欠。ログではなくスパンで状態を追う発想への転換が求められる。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded Typesが標準化し、プリミティブ型の誤用をコンパイル時に防ぐパターンが広く採用されている。

- **satisfies 演算子の活用:** TypeScript 4.9以降の `satisfies` が定着し、型推論を維持しながら型チェックを行えるため、`as` キャストによる型安全性の損失を避けるベストプラクティスとなっている。

- **Template Literal Types によるAPI型定義:** REST APIのパスやイベント名をTemplate Literal Typesで表現することで、ランタイムエラーをゼロにする設計が主流。特にルート定義の補完と型チェックが強力。

- **Zod + tRPC によるスキーマ駆動開発:** バリデーションスキーマから型を自動生成するパターンが定着し、フロントエンド・バックエンド間でランタイム検証と静的型を一元管理することがデファクトスタンダードに。

- **Exact Types / NoUncheckedIndexedAccess の徹底:** `noUncheckedIndexedAccess` を `tsconfig.json` で有効化し、配列・オブジェクトアクセス時の暗黙的な `undefined` を型システムで強制的に扱うことで、実行時クラッシュを大幅削減できる。
