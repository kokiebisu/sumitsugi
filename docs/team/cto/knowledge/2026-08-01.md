# CTO Knowledge - 2026-08-01

## Daily Update (2026-08-01)

### 1. Next.js performance optimization 2026

- **ポイント1（Turbopackの本番運用):** Next.js 16ではTurbopackがビルドの既定エンジンとなり、大規模ページでもコールドビルドが数倍高速化される。当プロジェクトのようにpropertiesやlistingページ数が増えるフェーズでは、ローカル開発体験とCIのビルド時間短縮に直結する。

- **ポイント2（Partial Prerendering / PPRの活用):** 静的シェル+動的ホールという構成により、物件一覧のような「一部は静的（写真・基本情報）、一部は動的（在庫状況・価格）」ページで、TTFBを保ちながらパーソナライズを両立できる。draft/publicのステータス切り替えがあるページ設計と相性が良い。

- **ポイント3（Server ComponentsでのDBアクセス最適化):** RSC内でのN+1クエリが依然として見落とされがちな性能劣化要因。`src/lib/data.ts`のようなデータ層でリクエストごとのキャッシュ（`cache()`関数）とバッチングを徹底することが、物件詳細ページのレイテンシに大きく効く。

- **ポイント4（画像最適化とCore Web Vitals):** 物件写真中心のUIでは`next/image`のresponsive srcsetとpriority指定の適切な使い分けがLCPを左右する。2026年時点ではAVIF配信とCDNエッジでの動的リサイズが標準化しており、引越し費用比較のようなビジュアル重視ページで特に重要。

- **ポイント5（Bunとの統合によるCI高速化):** Bun 1.xランタイムとNext.jsの組み合わせで、`bun run build`のインストール〜ビルドまでの総時間が短縮される。ベータローンチ前の頻繁なPRサイクルにおいて、CIの待ち時間削減がそのまま開発速度に跳ね返る。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** RSCのstreaming responseは `Suspense` 境界と組み合わせることでTTFBを大幅短縮でき、2026年時点ではNext.js App Routerのデフォルトパターンとして定着している。sumitsugiでも物件一覧・詳細ページのようなデータ取得が重い画面で優先的に適用すべき。

- **Server Actionsとの統合深化:** フォーム送信やミューティエーション処理をServer Actionsに寄せることで、クライアントバンドルサイズを削減しつつストリーミングUIとシームレスに連携できる。引越し費用計算や物件登録フローなど多段階フォームで有効。

- **部分的プリレンダリング（PPR）の実用化:** 静的シェルを即座に返しつつ動的部分だけストリーミングする手法が本番運用レベルに成熟してきており、CDNキャッシュとの相性が良い。物件検索ページのような「共通UI＋動的検索結果」構成に適用可能。

- **エラーバウンダリとストリーミングの共存設計:** ストリーミング中に発生したサーバーエラーをどう`error.tsx`にフォールバックさせるかが実装上の落とし穴になりやすく、特に決済や認証を含む画面ではテスト（E2E含む）でストリーミング失敗時の挙動を必ず検証すべき。

- **キャッシュ戦略との組み合わせ:** RSCのストリーミングはNext.jsのData Cache/Router Cacheと密結合しており、キャッシュ無効化のタイミング設計を誤るとユーザーごとの表示崩れ（前の住人情報の取り違え等）につながるため、多住人プラットフォームでは特に慎重な設計が必要。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1: tRPCの採用拡大とエンドツーエンド型安全性** モノレポ構成でNext.js + tRPCの組み合わせが定着し、フロントエンドとバックエンド間でスキーマ定義なしに型が伝播する開発体験が標準になりつつある。sumitsugiのようなTypeScriptモノレポでは、REST/OpenAPIのスキーマ同期コストを削減できる有力な選択肢。

- **ポイント2: GraphQLは「集約層」としての役割に収束** 単一サービスのAPIとしてよりも、複数マイクロサービス・外部APIを束ねるBFF（Backend for Frontend）層としての採用が主流化。sumitsugi規模のMVPでは過剰設計になりやすく、当面はtRPC/RESTで十分。

- **ポイント3: RESTはpublic API・サードパーティ連携で依然として第一選択** 内部API（管理画面、フロント⇔BFF）はtRPC、外部公開API（決済連携、パートナー向けAPI）はREST+OpenAPIという使い分けが2026年のベストプラクティスとして定着。将来的に外部業者連携（不動産会社API等）を見据えるなら、RESTの設計指針を早めに固めておくべき。

- **ポイント4: Zodスキーマの一元管理がAPI設計の中心に** tRPCでもREST（OpenAPI生成）でも、Zodスキーマを唯一の真実源（Single Source of Truth）として入力検証・型生成・ドキュメント生成を統合する構成が主流。既存の「Zodで境界検証」方針と自然に整合するため、追加投資なしで恩恵を受けられる。

- **ポイント5: エッジランタイム対応とレイテンシ最適化が差別化要因に** Next.js 16のエッジランタイムやストリーミングSSRとAPI層の統合により、地方の不動産検索・物件一覧のようなレイテンシ敏感な機能でのパフォーマンス最適化が競争力になる。API設計時点でエッジ実行を意識した軽量なハンドラ設計が推奨される。

### 4. serverless edge computing 2026

**CTO視点:serverless edge computing 2026**

- **ポイント1（V8 Isolatesの主流化）:** Cloudflare Workers・Deno Deploy等のV8 Isolate方式がコンテナベースFaaSを置き換えつつあり、コールドスタートが1桁ミリ秒台まで短縮。sumitsugiのようなSSR中心のNext.js構成でも、地理的に近いエッジでのレンダリングによりTTFB改善が見込める。

- **ポイント2（データレイヤーのエッジ化）:** Turso・PlanetScale・Cloudflare D1など「エッジレプリカ付きDB」が普及し、従来はエッジ化のボトルネックだったDBアクセスのレイテンシ問題が緩和されつつある。物件検索・一覧表示など読み取り中心の機能から段階的に移行するのが現実的。

- **ポイント3（Next.js 16とEdge Runtimeの相性）:** App RouterのPartial Prerenderingが安定し、静的部分をCDNエッジでキャッシュしつつ動的部分（認証状態・お気に入り等）のみランタイムでフェッチする構成が標準化。全ページをEdge Runtime化するより、この使い分けの方がコストと複雑性のバランスが良い。

- **ポイント4（ベンダーロックインのリスク）:** 各社エッジランタイムはNode.js APIの一部非対応（fsアクセス制限等）があり、移行時に想定外の書き換えが発生しがち。ローンチ準備フェーズの現状では、法務対応が優先事項のため、エッジ移行は「今すぐ着手」ではなく技術的負債として認識した上で先送りが妥当。

- **ポイント5（コスト面の実利）:** リクエスト課金モデルのエッジ関数は、現状のトラフィック規模（MVP〜ベータローンチ初期）では常時稼働サーバーより明確にコスト優位。ユーザー数が増えるベータ後の段階で本格導入を検討する判断軸で良い。

### 5. authentication security best practices 2026

**ポイント1:** パスキー（FIDO2/WebAuthn）が2026年時点で標準的な第一選択肢になっており、パスワードレス認証への移行はフィッシング耐性の観点でもUXの観点でも優位。sumitsugiのような個人情報を扱うプラットフォームでは、パスワード＋SMS OTPより優先的に導入価値が高い。

- **ポイント2:** セッション管理はJWTの検証ロジックに脆弱性が集中しやすいため、有効期限の短縮とリフレッシュトークンのローテーション（再利用検知付き）を必須にすべき。特にNext.js App RouterでのServer Actions経由の認証チェックは、ミドルウェアだけに依存せず各エンドポイントで再検証するのが安全。

- **ポイント3:** 「前の住人」「次の住人」間で個人情報や物件情報をやり取りするsumitsugiの性質上、認可（authorization）の粒度がセキュリティの要。認証（誰か）だけでなく、リソースレベルでの所有権チェック（この物件・この引き継ぎ情報にアクセスできるか）をAPI境界で徹底する必要がある。

- **ポイント4:** レート制限とアカウント列挙対策（ログイン失敗時に「メールアドレスが存在しない」と「パスワードが違う」を区別しない等）は、ベータローンチ前の最低ラインとして必須。法務確認と並行して技術的な基礎防御は先に固めておくべき。

- **ポイント5:** シークレット管理は環境変数＋Vercel/GitHub Actions Secretsに一元化し、`CLAUDE_CODE_OAUTH_TOKEN`のようなCI用トークンも含めてローテーション計画を持つこと。自律開発ワークフローが動いている環境では、CIのシークレット漏洩が本番認証基盤への攻撃経路になりうる点を軽視すべきではない。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降のTyped SQL機能により、複雑なクエリでもORM経由の型安全性を維持しつつ生SQLの性能を引き出せるようになった。Supabase側のRLS（Row Level Security）と組み合わせる際は、Prisma Client経由の接続がRLSポリシーを正しく尊重するようサービスロールキーとanonキーの使い分けを徹底すべき。

- **ポイント2:** Supabaseのconnection pooling（PgBouncer/Supavisor）とPrismaのコネクション管理は相性問題が起きやすく、サーバーレス環境（Vercel等）ではPrisma Accelerateやトランザクションモード指定（`pgbouncer=true`）が実質必須になっている。この設定漏れは本番でのコネクション枯渇の主要因。

- **ポイント3:** Prisma Migrateのマイグレーション履歴とSupabase Studioでの手動スキーマ変更が競合しやすいため、スキーマ変更は必ずPrisma Migrate経由に一本化し、Supabase Studioでの直接編集を禁止するチーム運用ルールが重要。

- **ポイント4:** 2026年時点でPrismaのedge runtime対応（Driver Adapters）が成熟し、Cloudflare WorkersやVercel Edge FunctionsからSupabase Postgresへ直接低レイテンシ接続できるようになった。グローバル展開を見据えるなら早期に移行検討する価値がある。

- **ポイント5:** Supabaseのリアルタイム機能（Realtime/Broadcast）とPrismaのデータ層は別レイヤーとして扱う必要があり、書き込みはPrisma経由・購読はSupabase Client経由という二重構成が一般的なベストプラクティスとして定着している。

### 7. WebAssembly Rust performance 2026

- **ポイント1: Component Model の実用化** — WASI Preview 2ベースのComponent Modelが安定期に入り、Rustコンポーネント同士を言語非依存で組み合わせられるようになった。マイクロサービス的な設計をWASMバイナリ単位で実現でき、モジュール分割による保守性向上が期待できる。

- **ポイント2: SIMD・マルチスレッド対応の成熟** — WASM SIMDとThreads提案（SharedArrayBuffer経由）が主要ブラウザ・ランタイムで実用レベルに達し、Rustの並列処理コードがネイティブに近い性能でWASM上でも動く。画像処理や暗号計算など計算集約タスクをフロントエンドにオフロードする選択肢が現実的になっている。

- **ポイント3: エッジコンピューティングでの起動時間短縮** — wasmtime・wasmerのAOTコンパイル最適化（Cranelift）により、コールドスタートがミリ秒単位まで短縮。Cloudflare WorkersやFastly Compute@Edgeのようなエッジ環境でRust+WASMを使うと、Node.jsベースの実装より低レイテンシを狙いやすい。

- **ポイント4: バイナリサイズとツールチェーンの改善** — `wasm-bindgen`/`wasm-pack`のtree-shaking精度向上と`wee_alloc`に代わる軽量アロケータの採用で、出力バイナリが小型化。物件写真の画像最適化処理など、クライアントサイドの重い処理をWASM化してもページロードへの影響を抑えやすくなった。

- **ポイント5: 過度な最適化への注意** — 性能面のメリットは大きいが、WASM境界を跨ぐデータのシリアライズコストは無視できない。sumitsugiのようなSaaSでは、まずJS/TSで実装しボトルネックが明確な処理（画像処理・PDF生成など）だけをRust+WASMに切り出す方が、開発速度とのバランスが取れる。

### 8. Next.js App Router patterns 2026

- **ポイント1（Partial Prerendering成熟）:** PPR（Partial Prerendering）がNext.js 15〜16で安定版となり、静的シェルと動的コンテンツを1つのルートで組み合わせられるように。物件一覧ページのように「検索フォームは静的、結果は動的」という構成に最適で、sumitsugiのproperties一覧でTTFB短縮に直結する。

- **ポイント2（Server Actions＋Zodバリデーション）:** Server Actionsがフォーム処理の標準パターンとして定着し、`use server`関数の入口でZodスキーマ検証を行うのがベストプラクティスに。物件登録・引き継ぎ申請フォームなど、standards.mdの「システム境界でZod」方針と直接整合する。

- **ポイント3（Cache Componentsとexplicit caching）:** Next.js 16で導入されたCache Components（`"use cache"`ディレクティブ）により、キャッシュ挙動が暗黙的から明示的に変更。data.tsのような共有データ取得ロジックは、キャッシュ境界を意図的に指定しないと過剰再検証やstale dataのリスクがある点に注意が必要。

- **ポイント4（Route Handlersの軽量化）:** App RouterではRoute Handlers（`app/api/*/route.ts`）よりもServer Actions＋Server Componentsで完結させる設計が主流に。外部Webhook（決済・認証コールバック等）以外はRoute Handlerを増やさない方が、認証コンテキストの二重管理を避けられる。

- **ポイント5（Turbopack本番ビルド標準化）:** Turbopackが`next build`のデフォルトとなりビルド時間が大幅短縮。CIのbuild検証ステップ（standards.mdのBuild Integrity方針）が高速化される一方、一部のwebpack依存プラグインとの互換性は個別確認が必要。

### 9. Vercel Edge Functions optimization 2026

## CTO視点: Vercel Edge Functions optimization 2026

- **Fluid Computeへの移行:** Vercelの新しい実行モデルでは、Edge FunctionsとServerless Functionsの垣根が薄れ、リクエストの同時実行（in-function concurrency）でコールドスタートとコストを大幅削減できる。sumitsugiのような物件検索APIでは、同時アクセスが多い検索エンドポイントに適用すると費用対効果が高い。

- **バンドルサイズの徹底管理:** Edge Runtimeはコールドスタート性能がバンドルサイズに直結するため、依存関係を最小化し重いライブラリ（画像処理・PDF生成等）はNode.jsランタイムに分離するのがベストプラクティス。物件PDF資料生成のような処理をEdgeに載せると逆に遅くなるので注意。

- **Partial Prerendering (PPR) との組み合わせ:** 静的シェルを即座に返しつつ動的部分（在庫状況・価格）だけEdgeでストリーミングする構成が主流化。物件一覧ページのように「静的な骨格＋動的な最新情報」という構造に相性が良く、TTFB改善に直結する。

- **Edge ConfigとMiddlewareの軽量化:** A/Bテストやフィーチャーフラグ判定をMiddlewareで行う際、Edge Config（低レイテンシKVストア）を使うことでDBラウンドトリップを排除できる。ただしMiddlewareはリクエスト全体を通るため、ロジック肥大化がサイト全体のレイテンシに波及するリスクがあり、責務を最小限に保つ規律が必要。

- **リージョン最適化とデータ局所性:** Edge Functionsが呼び出すDB/APIのリージョンとの距離がボトルネックになりやすいため、`region`設定をデータソースに近づけるか、読み取りレプリカ・キャッシュ層を併用して「Edgeで実行しても結局DBが遠い」状態を避けることが重要。

### 10. TypeScript type safety patterns 2026

- **ポイント1（型推論の限界とas constの活用）:** TypeScript 5.x以降、`satisfies`演算子と`as const`の組み合わせがデフォルトパターンとして定着し、型の広がりを抑えつつ推論の恩恵を維持できるようになっています。本プロジェクトでも`site-config.ts`のような設定オブジェクトに積極採用すべきです。

- **ポイント2（Zodによるランタイム検証との統合）:** 静的型はコンパイル時のみの保証にすぎないため、外部入力（フォーム、API応答）は必ずZodスキーマで検証し、`z.infer`で型を導出する運用がベストプラクティスとして定着しています。standards.mdの「システム境界でZodを使う」方針と一致しており、引き続き徹底すべきです。

- **ポイント3（Discriminated Unionによる状態管理）:** `status: 'draft' | 'public'`のようなUnion型は、判別可能なプロパティを持たせて網羅性チェック（`never`型でのexhaustive check）と組み合わせることで、新しいステータス追加時のバグを型検査の段階で検出できます。

- **ポイント4（テンプレートリテラル型とブランド型）:** ID・URLパスなどの文字列に対してテンプレートリテラル型やブランド型（nominal typing）を使い、単なる`string`同士の取り違えをコンパイル時に防ぐパターンが2026年時点でも継続的に有効です。

- **ポイント5（型のみのimportとビルド高速化）:** `import type`の徹底とTypeScriptの`isolatedModules`設定により、Bunのようなトランスパイラベースのビルドでも型情報が安全に除去され、ビルド速度と型安全性を両立できます。CIのビルド健全性維持（standards.mdの必須項目）にも直結します。
