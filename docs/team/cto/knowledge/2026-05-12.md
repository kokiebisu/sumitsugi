# CTO Knowledge - 2026-05-12

## Daily Update (2026-05-12)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 15でStableになったPPRにより、静的シェルを即座に配信しつつ動的コンテンツをストリーミングする設計が標準化。`<Suspense>`の粒度設計がTTFBとLCPに直結する。

- **Turbopackへの完全移行:** Next.js 15でTurbopackがデフォルト化し、ローカルdevサーバーが最大76%高速化。ただし一部カスタムwebpackプラグインとの互換性確認が移行の要注意点。

- **キャッシュ戦略の再設計:** Next.js 15でfetchのデフォルトキャッシュが`no-store`に変更。従来のキャッシュ前提のアーキテクチャは明示的な`cache: 'force-cache'`や`unstable_cache`への書き直しが必要。

- **React Server Componentsのデータフェッチ集約:** クライアントへのJSバンドルを削減するため、データ取得ロジックをRSCに集約し、Client Componentsはインタラクション専用に絞る設計がパフォーマンスの鍵。`use server` / `use client`の境界設計が開発品質を左右する。

- **Core Web Vitalsの継続的モニタリング:** `@vercel/speed-insights`やOpenTelemetryとの統合が普及し、INP（Interaction to Next Paint）がSEOランキング要因として定着。Server Actionsの応答速度がINPに影響するため、DB クエリの最適化がフロントエンド指標に直結する。

### 2. React Server Components streaming 2026

- **Suspense境界の戦略的配置が性能の鍵:** RSCとStreamingの組み合わせでは、`<Suspense>`境界をデータフェッチの粒度に合わせて細かく配置することで、TTFBを最小化しつつ段階的なUI描画が実現できる。

- **PPR（Partial Prerendering）が本番レディに:** Next.js 15以降でPPRが安定し、静的シェルを即時配信しながら動的部分をストリームする設計が標準パターンになりつつある。キャッシュ戦略との組み合わせが設計の核心。

- **Server Actions + Optimistic UIで往復コストを削減:** フォームやミューテーションをServer Actionsで処理しつつ、`useOptimistic`でクライアント側の即時反映を担保するパターンが成熟し、RTTによるUX劣化をほぼ排除できる。

- **バンドルサイズの非対称性を活かす設計が必須:** RSCはサーバー側でのみ実行されるためクライアントバンドルに含まれない。重いライブラリ（日付処理、Markdownパーサー等）をServer Component側に閉じ込める意識的な分割が、Core Web Vitalsへ直結する。

- **エッジランタイムとの相性に注意:** Cloudflare WorkersやVercel Edgeでの実行はNode.js APIの制約があり、DB接続やファイルシステムアクセスを含むRSCはリージョナルサーバーに留める判断が現実的。ストリーミングのレイテンシ利得とエッジの地理的利点のトレードオフを設計初期に明確化すべき。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** tRPCはNext.js/TypeScriptプロジェクトで事実上の標準となりつつあり、クライアント・サーバー間の型共有によりランタイムエラーを大幅に削減できる。スキーマ定義が不要で開発速度が向上する点が特に小〜中規模チームに支持されている。

- **GraphQLの選択的採用:** GraphQLは複雑なデータグラフを持つ大規模プロダクト（BFF層、マイクロサービス統合）には依然有効だが、オーバーエンジニアリングになるケースも多く「本当に必要か？」の問いが重要。Relay/Apollo Clientのバンドルサイズと学習コストを考慮すると、tRPCやREST+OpenAPIで十分なケースが多い。

- **REST+OpenAPI/Zodの再評価:** OpenAPI 3.1とZodを組み合わせた型生成（`zod-openapi`, `orval`等）により、RESTでもエンドツーエンドの型安全性が実現可能になった。既存チームのスキルセットを活かしつつ、型安全の恩恵を得られる現実的な選択肢として再注目されている。

- **エッジ・サーバーレス環境への最適化:** Cloudflare Workers/Vercel Edge等での実行を前提としたAPIでは、コールドスタートとバンドルサイズが制約となる。tRPCやHono等の軽量フレームワークがこの要件にマッチしており、Expressベースの重厚な構成は避けるべき。

- **AIエージェント統合を前提としたAPI設計:** 2026年時点では、APIがLLMエージェントから呼ばれることを想定した設計が必須。MCP（Model Context Protocol）準拠やOpenAPI仕様の充実が「機械可読性」の観点で重要になっており、ドキュメント品質がそのままエージェント統合品質に直結する。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジのデファクトランタイムへ:** Cloudflare Workers・Fastly Compute@Edgeを中心に、Wasmがコンテナに代わるエッジ実行環境として定着。言語非依存かつコールドスタートがほぼゼロで、Node.js依存から脱却できる。

- **エッジDBの成熟でステートフルアーキテクチャが現実的に:** Cloudflare D1・Turso・PlanetScale Metalなどの分散SQLiteがエッジに浸透し、「エッジはステートレスのみ」という制約が崩れてきた。レイテンシ重視のユーザーデータ処理をエッジで完結できる。

- **AI推論のエッジオフロードが加速:** LLMの軽量モデル（Llama 3 8B級）がエッジで動作可能になり、Cloudflare Workers AI・Vercel AI SDKがエッジ推論をファーストクラスサポート。プライバシー要件の高いデータをオリジンに送らずに処理できる点が評価されている。

- **オブザーバビリティのギャップが依然課題:** エッジ環境はログ・トレースのコレクションが分散しており、OpenTelemetry対応が各プラットフォームで道半ば。本番運用では従来のAPMと異なるモニタリング戦略が必要で、ここへの投資を怠ると障害対応が困難になる。

- **コスト構造の再評価が必要:** リクエスト単価は安価でも、エッジDBのリードレプリカ料金やAI推論コストが積み上がるケースが増加。「エッジ＝安い」という前提を捨て、オリジンとエッジのコスト分岐点を設計段階でモデル化することが不可欠。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準化:** FIDO2/WebAuthnベースのパスキーが2026年の認証標準となり、フィッシング耐性があるためパスワードレス移行は必須の優先事項。

- **ゼロトラスト・セッション管理:** JWTの長期トークンに依存せず、短命アクセストークン（5〜15分）＋ローテーション付きリフレッシュトークンの組み合わせが基本構成。トークン失効機能も必須。

- **MFAのフィッシング耐性評価:** SMSやTOTPはSIMスワップ・リアルタイムフィッシングに脆弱。ハードウェアキー（YubiKey等）またはパスキーによるMFAへの移行が推奨水準。

- **AI駆動の異常検知:** ログインパターン・デバイスフィンガープリント・行動バイオメトリクスをリアルタイム分析し、不正アクセスを認証フロー内で検出する仕組みが競争優位に。

- **OAuth 2.1 / DPoP の採用:** Bearer tokenの盗用リスクに対応するため、DPoP（Demonstrating Proof-of-Possession）によるトークンバインディングが標準化。既存OAuth 2.0実装の見直しが必要。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のEdge Runtime対応成熟:** Prisma AccelerateとEdge Runtimeの組み合わせが本番運用レベルに達し、Vercel/Cloudflare Workers上でのコネクションプーリングが不要になりつつある。Next.js App RouterとのServer Actions統合がシームレスになった。

- **Supabase Realtime v3のスケーラビリティ改善:** Broadcast/PresenceチャンネルがPostgresのロジカルレプリケーションから独立し、大規模同時接続時のDB負荷が大幅に低減。リアルタイム機能をPostgresから切り離した設計判断が有効。

- **Row Level Security (RLS) とPrismaの相性問題:** SupabaseのRLSポリシーはPrismaのORM層を素通りするため、アプリ側バリデーションとDBポリシーの二重管理が必要。`prisma.$executeRaw`でのセッション変数設定パターンが定着しつつある。

- **Supabase Branching（Database Branches）の普及:** 開発環境ごとにDBブランチを切る運用が標準化され、PRレビュー時にマイグレーションを本番に影響なく検証できる。Prismaのマイグレーション管理との組み合わせが特に有効。

- **pgvector + Supabase によるRAG統合:** ベクトル検索をアプリDBと同一インスタンスで扱えるため、外部ベクトルDBを排除した軽量RAGアーキテクチャが現実解になっている。Prismaの型安全性をベクトル操作に適用するための`$queryRaw`ラッパーパターンが広まっている。

### 7. WebAssembly Rust performance 2026

- **WASI Preview 2 の本格普及:** Component Model仕様が安定し、Rustで書いたWasmモジュールをサーバー・ブラウザ・エッジ環境で再コンパイルなしに共有できる時代になった。依存関係の境界を明確にしつつバイナリサイズを削減できる。

- **GC提案によるメモリ管理の改善:** WasmGC（Garbage Collection拡張）の主要ブラウザ対応が進み、Rustのownership modelと組み合わせることで、ヒープ割り当てコストを最小化しながら安全なメモリ管理が実現できる。

- **SIMD・スレッド並列化の成熟:** Fixed-width SIMDとThreads拡張が安定し、画像処理・機械学習推論・暗号処理でネイティブに近いスループットを達成。`wasm-pack` + `rayon`の組み合わせでブラウザ内マルチスレッド処理が実用レベルに。

- **起動レイテンシの課題は継続中:** AOTコンパイル（Cranelift等）の改善で実行速度は向上したが、モジュールの初期化時間はJSより依然重い。エッジ関数やサーバーレス環境では、スナップショット技術（`wizer`等）での事前初期化が実用解。

- **Rustツールチェーンの成熟度が競争優位に:** `wasm-bindgen`・`wit-bindgen`・`cargo-component`の整備により、他言語と比べてRustのWasmエコシステムが最も本番適用しやすい状態。特にパフォーマンスクリティカルなコアロジックをRust/Wasmに切り出す「ハイブリッドアーキテクチャ」が主流になりつつある。

### 8. Next.js App Router patterns 2026

- **Server Componentsをデフォルトに:** App RouterではすべてのコンポーネントがデフォルトでServer Componentになるため、`'use client'`は最小限のインタラクティブな境界にのみ使用し、不要なクライアントバンドルを避けることが最重要パターンとなっている。

- **Partial Prerendering（PPR）の本格活用:** Next.js 15〜16ではPPRが安定化し、静的シェルと動的ストリーミング部分を1リクエストで配信できるため、従来のSSR/SSGの二択から解放され、初期表示速度とリアルタイム性を両立できる。

- **Server Actionsによるフォーム設計の刷新:** APIルートを介さずServer Actionsで直接サーバー処理を行うパターンが主流化。`useActionState`と組み合わせることでPending状態・バリデーションエラーをシンプルに扱え、クライアントコードの大幅削減につながる。

- **キャッシュ戦略の明示的制御:** `fetch`のキャッシュオプション（`force-cache` / `no-store`）やRoute Segment Configの`revalidate`を意図的に設計することが必須。デフォルトキャッシュ挙動がNext.js 15以降で変更されたため、暗黙の前提に依存すると予期しない動作を引き起こす。

- **コロケーション原則によるディレクトリ設計:** ページ・コンポーネント・テスト・型定義を機能単位でまとめる「Feature Colocation」が普及。`src/app/`配下に関連ファイルをまとめることで、大規模チームでの見通しと保守性が向上する。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択的適用:** 全APIルートをEdgeに移行するのは逆効果。Cold startが不要でレイテンシ感度が高いルート（認証チェック、A/Bテスト、地域リダイレクト）に絞ることで、Node.js Runtimeとのハイブリッド構成が最適解となっている。

- **Fluid Computeによる課金モデルの変化:** 2025年後半からVercelが導入したFluid Computeにより、リクエスト待機中のCPUアイドル時間は課金対象外になった。これによりEdge vs Serverlessのコスト比較軸が変わり、単純なリクエスト数ではなく実CPU使用時間で最適化を考える必要がある。

- **ISRとEdgeキャッシュの組み合わせ:** `stale-while-revalidate`パターンをEdge Configと組み合わせることで、動的コンテンツをほぼ静的なレイテンシで配信できる。キャッシュキーの設計（地域・ユーザーセグメント・フィーチャーフラグ）が性能の鍵になる。

- **サードパーティSDKの互換性チェックが必須:** Edge RuntimeはWeb標準APIのみサポートするため、Node.js固有モジュール（`fs`, `crypto`, `buffer`等）に依存するSDKは動作しない。依存ライブラリの`edge-light`エクスポートの有無を事前確認し、非対応ならMiddlewareではなくServerless Functionに配置する。

- **Observabilityの整備:** Edge FunctionsはVercel以外のAPMツールとの統合が限定的なため、`waitUntil()`を使った非同期ログ送信（Axiom, Betterstack等）をパターン化しておくことが運用上不可欠。レイテンシの99パーセンタイルをリージョン別に計測することで、特定POPでの劣化を早期検知できる。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の標準化:** TypeScript 4.9で導入された`satisfies`が2026年には実践的なベストプラクティスとして定着し、型推論を保ちながら型チェックを行う用途でキャストより優先される。

- **Template Literal Types の高度活用:** APIルートやイベント名の型安全化に`${Method}${Endpoint}`パターンが普及し、ランタイムエラーをコンパイル時に検出できる設計が主流になっている。

- **`using` 宣言によるリソース管理:** ECMAScript Explicit Resource Management（Stage 4）に対応したTypeScriptで`using`キーワードが普及し、DB接続やファイルハンドルのリーク防止が型システムと統合された。

- **Branded Types によるドメイン安全性:** `UserId`と`ProductId`を同じ`string`として混同するバグを防ぐBranded/Nominal Typingが、大規模プロジェクトの標準パターンとして採用が拡大している。

- **`noUncheckedIndexedAccess` の必須化:** `tsconfig`の`noUncheckedIndexedAccess`フラグが厳格設定のデフォルトとして業界標準化しつつあり、配列・オブジェクトアクセス時の`undefined`を型レベルで強制処理することでランタイムクラッシュを削減できる。
