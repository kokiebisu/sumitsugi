# CTO Knowledge - 2026-09-29

## Daily Update (2026-09-29)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Prerendering / PPR の本格運用）:** Next.js 16ではPPRが安定版となり、静的シェルを即座に返しつつ動的部分をストリーミングする構成が標準化。初期表示速度（TTFB/LCP）を大幅改善できるため、物件一覧ページなど「静的な枠+動的な検索結果」の構造に最適。

- **ポイント2（React Compiler によるメモ化自動化）:** React Compilerがデフォルト有効になり、`useMemo`/`useCallback`の手動最適化がほぼ不要に。開発者はビジネスロジックに集中でき、レンダリング最適化のバグ（依存配列漏れ等）を構造的に排除できる。

- **ポイント3（Turbopackのビルド高速化）:** Turbopackが本番ビルドでも既定になり、大規模コードベースでのビルド時間が数分→数十秒に短縮。CI/CDのフィードバックループが速くなり、autonomous-developerのような自動化ワークフローの回転率にも直結する。

- **ポイント4（画像・フォントの自動最適化強化）:** `next/image`のAVIF自動配信とレイアウトシフト対策がさらに厳格化。物件写真中心のUIでは、LCP改善とCore Web Vitalsスコア向上に直接効く投資対効果の高い施策。

- **ポイント5（Edge Runtimeとキャッシュ戦略の再設計）:** `use cache`ディレクティブによる明示的キャッシュ制御が主流化し、Edge/Node Runtimeの使い分けがより細粒度に。認証周り（auth-context）はNode Runtime、公開物件ページはEdgeでキャッシュする、といった住み分け設計がパフォーマンスとコストの両面で重要になる。

### 2. React Server Components streaming 2026

- **ポイント1:** React 19以降、Server ComponentsのストリーミングはSuspense境界の粒度設計が肝になっており、単一の大きなSuspenseで囲むのではなく、ページ内のセクション単位で分割することでTTFB（Time to First Byte）とLCPを大幅に改善できる。

- **ポイント2:** Next.js 16のPartial Prerendering（PPR）が安定化し、静的シェルを即座に返しつつ動的部分だけをストリーミングで差し替える構成が標準化しつつある。物件一覧ページのような「静的なレイアウト＋動的な検索結果」構成に特に有効。

- **ポイント3:** Server Actionsとストリーミングの組み合わせで、フォーム送信後の楽観的UI更新がよりシンプルに書けるようになっており、`useOptimistic`との併用がベストプラクティスとして定着している（引越し費用の見積もりフォームなどに応用可能）。

- **ポイント4:** ストリーミングSSRはエッジランタイム（Vercel Edge, Cloudflare Workers）との親和性が高く、地理的に分散したユーザーへのレイテンシ削減効果が大きい一方、DBアクセスを伴うServer Componentsをエッジで実行する場合はコネクションプーリング（例: Prisma Accelerate、Neon Serverless）の設計が必須になる。

- **ポイント5:** ストリーミング中のエラーハンドリングが複雑化しやすいため、`error.tsx`とSuspense境界を組み合わせた「部分的失敗の許容」設計（一部セクションが失敗しても他は表示継続）が2026年のベストプラクティスとして推奨されている。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** 2026年時点では「REST vs GraphQL」の二択論争は下火になり、内部BFF（Backend for Frontend）層にtRPCやGraphQLを使い、外部公開APIはRESTまたはOpenAPI準拠で提供するハイブリッド構成が主流になっている。sumitsugiのようにNext.js App Router単体で完結するプロダクトでは、tRPCによる型安全なエンドツーエンド通信（フロント⇔サーバー間で型を共有）が開発速度とバグ削減の両面で有利。

- **ポイント2:** tRPCはNext.js + TypeScriptモノレポとの親和性が高く、スキーマ定義とAPIクライアントの二重管理が不要になるため、物件情報や引越し費用計算のような複雑なデータ構造を扱う際の型不整合バグを大幅に減らせる。ただし公開APIやモバイルアプリ・外部パートナー連携が視野に入るフェーズではREST/OpenAPIへの移行コストを見込んでおく必要がある。

- **ポイント3:** GraphQLは複数クライアント（Web/モバイル/外部パートナー）が異なるデータ粒度を要求するケースで依然強みを持つが、N+1問題やキャッシュ設計の複雑さから、単一フロントエンド構成のMVPフェーズでは過剰投資になりやすい。sumitsugiの現フェーズ（ベータローンチ準備）ではtRPC継続が妥当。

- **ポイント4:** 2026年のトレンドとして、Zodなどのランタイムスキーマ検証ライブラリをAPI境界のバリデーションと型定義の両方に使う「Schema-first」アプローチが定着しており、tRPC+Zodの組み合わせは本プロジェクトの`.claude/rules/standards.md`が求める「システム境界でのZod検証」方針とも合致する。

- **ポイント5:** 将来的に外部連携（決済、不動産ポータル連携、行政システム連携など）が必要になった場合は、内部tRPC APIとは別にREST/OpenAPI準拠の公開APIレイヤーを追加する「API Gateway分離」パターンが2026年のベストプラクティスとして定着しつつある。今から意識しておくとスケール時の再設計コストを抑えられる。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG/WinterTCが推進するWeb標準API準拠のランタイム（Cloudflare Workers、Deno Deploy等）が主流化し、ベンダーロックインを避けたポータブルなコードが書けるようになっている。移行コストを見積もる際はこの標準準拠度を基準にすべき。

- **コールドスタートの実質ゼロ化:** V8 isolateベースの起動が数msまで短縮され、従来のコンテナ型サーバーレス（Lambda等）とのレイテンシ差が拡大している。ユーザー体験を左右するリアルタイム性の高い機能（在庫確認、価格計算等）はエッジファーストで設計すべきタイミング。

- **エッジDBとの一貫性トレードオフ:** D1、Turso、PlanetScale等のエッジレプリケーション型DBが実用段階に入ったが、強一貫性が必要な決済・予約系ロジックは依然オリジン集約が安全。読み取り主体のページ（物件検索・一覧）はエッジキャッシュ、書き込み系（予約確定）は中央集約という使い分けが定石。

- **AI推論のエッジシフト:** 軽量LLM推論（分類・要約・embedding生成）をエッジで実行するパターンが増え、レイテンシとコストの両面で中央集約型API呼び出しより有利なケースが出てきている。ただし複雑な生成タスクは引き続き中央のLLM APIに委譲するハイブリッド構成が現実的。

- **観測性の分散課題:** エッジで処理が分散するほど従来のAPMツールでは追跡が困難になり、OpenTelemetryのエッジ対応が急速に進んでいる。本番導入前にトレーシング基盤を先に整備しないと、障害時の原因特定が困難になるリスクが高い。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証がデファクトスタンダード化しており、フィッシング耐性のあるパスキーをプライマリな認証手段とし、パスワードは廃止対象とすべき。実装コストは`next-auth`や`Clerk`等のSDKでほぼ吸収できるため、新規機能は最初からパスキー前提で設計する。

- **セッション管理とトークンのゼロトラスト化:** 長期JWTのlocalStorage保存は避け、httpOnly + SameSite=StrictなCookieでの短命アクセストークン＋リフレッシュトークンローテーションを徹底する。特にsumitsugiのような個人情報（前の住人・次の住人の連絡先等）を扱うプラットフォームでは、セッションハイジャック対策が信頼性に直結する。

- **段階的リスクベース認証（Adaptive MFA):** 全ユーザーに一律MFAを強制するのではなく、デバイスフィンガープリント・IPレンジ・行動パターンからリスクスコアを算出し、高リスク操作（決済・個人情報変更）時のみ追加認証を要求する設計がUXとセキュリティの両立に有効。

- **認可ロジックの一元化とテスト:** 認証（誰か）と認可（何ができるか）を混同せず、`draft`/`public`のような物件ステータスやロール（seller/buyer）に基づくアクセス制御はミドルウェア層で一元管理し、Zodスキーマ＋ユニットテストで境界条件を必ず検証する。

- **サプライチェーン・依存関係の継続監査:** 認証関連ライブラリ（NextAuth、bcrypt等）はCVE情報を`bun audit`等で定期チェックし、OAuthプロバイダの設定ミス（redirect_uri検証漏れ等）がないかCI段階で自動検査する体制を構築する。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma ORMはRust製クエリエンジンから完全TypeScript実装へ移行が進み（Prisma 6以降）、エッジランタイム（Vercel Edge, Cloudflare Workers）でのコールドスタートが大幅に改善。sumitsugiのようなVercelデプロイ前提のNext.jsアプリでは、この移行によりレイテンシ削減が期待できる。

- **ポイント2:** SupabaseはPostgreSQLのRow Level Security（RLS）をPrisma経由でも直接活用する構成が主流化しており、アプリ層とDB層で二重に権限チェックを書く必要が減る。物件の`draft`/`public`ステータス制御のような可視性ロジックをRLSポリシーに寄せることで、バグの温床になりがちな条件分岐を減らせる。

- **ポイント3:** Supabase BranchingとPrisma Migrateを組み合わせたプレビュー環境ごとのDBブランチ運用が定着し、PRごとに独立したDBスキーマでE2Eテストを実行できる。現状のworktreeベースのPR運用と相性が良く、CI上でのテストデータ汚染リスクを下げられる。

- **ポイント4:** pgvectorのSupabase標準サポート強化により、Prisma経由でのベクトル検索実装がしやすくなった。将来的に「前の住人」の物件説明文やインテリア情報の類似検索・レコメンド機能を追加する際、外部ベクトルDBを別途導入せずSupabase内で完結できる。

- **ポイント5:** コネクションプーリング（Supabase Supavisor）とPrisma Accelerateの併用がサーバーレス環境でのデファクトになりつつあり、Next.jsのServer Actionsから多発するDB接続のスパイクに対する耐性が上がっている。ベータローンチ後のトラフィック増加時にDB接続枯渇で落ちるリスクを事前に潰せる。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGCとcomponent modelの標準化が進み、Rustのwasm-bindgen依存を減らしつつ言語間相互運用性が向上。2026年時点でwasmtimeやwasmerのAOTコンパイル最適化により、コールドスタート速度がネイティブに近づいている。

- **ポイント2:** `wasm32-wasip2`ターゲットの安定化でPOSIX風I/Oが可能になり、サーバーサイドでのRust+Wasmマイクロサービスがコンテナ代替として実用段階に入った。起動時間がコンテナの1/10以下という報告もあり、エッジ配信基盤に向く。

- **ポイント3:** SIMD128とmulti-value returnのブラウザ実装が成熟し、画像処理・物理演算など計算集約タスクでJS実装比3〜5倍高速化が一般的に。sumitsugiのような物件検索・フィルタリングUIでも、大量データのクライアントサイド処理に応用余地あり。

- **ポイント4:** バンドルサイズ最適化ツール（`wasm-opt`, `twiggy`）の進化で、Rust製Wasmモジュールが数百KB台まで削減可能に。Next.js App RouterのStreaming SSRと組み合わせれば、初期表示速度を犠牲にせず重い処理をオフロードできる。

- **ポイント5:** ただし開発体験面では、デバッグツールチェーン（ソースマップ、プロファイラ）がJS/TSエコシステムに比べまだ未成熟。導入は「検索・レコメンドエンジンの計算コア」など局所的な最適化用途に限定し、UI全体をWasm化するのは時期尚早という判断が妥当。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 15後半〜16でPPRが安定版となり、静的シェルと動的コンテンツを1つのルートで混在させるのが一般的なパターンに。物件一覧ページのように「枠は静的、価格や空室状況だけ動的」という構成にすることで、TTFBを大幅に改善できる。

- **`use cache` ディレクティブによる明示的キャッシュ制御:** fetchのキャッシュ挙動が暗黙的だった旧来の方式から、関数単位で`use cache`を明示する方式へ移行が進んでいる。sumitsugiのような物件データ表示では、キャッシュ境界を明示することで「前の住人」プロフィールなど更新頻度の低いデータと、公開ステータスのような即時性が求められるデータを分離しやすくなる。

- **Turbopackがビルド・開発両方でデフォルト化:** Webpackからの移行がほぼ完了し、`bun run build`のようなビルドコマンドの高速化が顕著。CI時間の短縮に直結するため、ビルド検証を頻繁に行う運用（PRごとにローカルビルド必須というsumitsugiの方針）と相性が良い。

- **Server Actionsのセキュリティパターンが定着:** 認証チェックやZodバリデーションをServer Actionの先頭で必ず行う「ガード節パターン」がベストプラクティスとして確立。物件公開・非公開の切り替えや引越し費用の計算など、状態変更を伴う操作はServer Actions+Zodで境界検証するのが2026年の標準的な設計。

- **React Compilerとの統合によるメモ化の自動化:** useMemo/useCallbackの手動最適化が不要になりつつあり、App Router配下のクライアントコンポーネントでもパフォーマンスチューニングの工数が削減される。一覧・検索系のような再レンダリングが多いUIで特に恩恵が大きい。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最適化:** V8 isolateベースの実行モデルにより、ミリ秒単位の起動が標準化しつつあるが、依存関係のバンドルサイズが引き続き最大のボトルネック。動的importの遅延ロードとtree-shakingの徹底で、Edge Function自体のペイロードを小さく保つことが重要。

- **Streaming SSRとの統合:** Edge FunctionsとReact Server Componentsのストリーミングレンダリングを組み合わせることで、TTFB（Time To First Byte）を大幅短縮できる。物件一覧や検索結果ページのような動的コンテンツは、この構成でLCP改善効果が大きい。

- **リージョナル実行の使い分け:** 全リクエストをEdgeで処理するのではなく、DB書き込みを伴う処理（予約確定・決済）はNode.js runtimeへ、読み取り中心の処理（物件検索・画像最適化）はEdgeへ、という使い分けが2026年のベストプラクティスとして定着。ミドルウェアでのルーティング判断がパフォーマンスとコストの両立に直結する。

- **キャッシュ戦略の高度化:** Incremental Static Regeneration (ISR) とEdge Cache のTTL/タグベース無効化を組み合わせ、物件情報更新時のみピンポイントで再検証する設計が主流に。sumitsugiのような物件データベースでは、ステータス変更（draft→public）をトリガーにしたオンデマンドrevalidationが有効。

- **観測性（Observability)の重視:** Edge環境はデバッグが難しいため、OpenTelemetry対応のトレーシングをEdge Functionsに組み込み、レイテンシの内訳（DNS/TLS/実行時間）を可視化する運用が必須になっている。本番障害の切り分けコストを抑える投資として優先度が高い。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** プリミティブ型を`type UserId = string & { readonly brand: unique symbol }`のようにブランド化し、意味の異なる文字列・数値の混在を型レベルで防ぐパターンが定着。IDや金額など取り違えバグが多発する箇所で特に効果的。

- **`satisfies`演算子の定着:** 型の広がりを保ちつつ制約チェックを行える`satisfies`が、設定オブジェクトやZodスキーマの定義で標準的な書き方になった。`as const satisfies Config`のように併用し、型推論の精度とリテラル型の保持を両立できる。

- **スキーマファーストな型定義:** Zod/Valibotなどでランタイム検証スキーマを先に書き、`z.infer<typeof schema>`で型を導出する流れが主流化。境界（API境界・フォーム入力）でのバリデーションと型定義を一箇所に集約でき、本プロジェクトの「Input validation: Zodスキーマ使用」方針とも合致する。

- **Exhaustiveness Checking の徹底:** Union型（例: `status: 'draft' | 'public'`）に対する`switch`文で`default`に`never`型アサーションを置き、新しいステータス追加時のコンパイルエラーを保証する手法が標準プラクティス化。CLAUDE.mdにある「union型変更時は全使用箇所をgrep」というルールを型システム側で自動チェックできる。

- **TypeScript Native (Go実装コンパイラ) の普及:** 2025年後半以降、tsc互換の高速コンパイラ（tsgo系）への移行が進み、大規模モノレポでの型チェック時間が大幅短縮。CIのビルド検証ステップ（`bun run build`必須ルール）の実行コスト削減に直結するため、導入検討の価値がある。
