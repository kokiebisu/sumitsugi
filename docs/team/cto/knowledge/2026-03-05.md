# CTO Knowledge - 2026-03-05

## Daily Update (2026-03-05)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** 2026年時点でRSCはデファクトスタンダードとなり、クライアントバンドルサイズを大幅削減できる。`'use client'`の使用を最小限に抑え、データフェッチをサーバー側に集約することが基本戦略。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降で安定化したPPRにより、静的シェルと動的コンテンツを同一ページで混在させられる。TFBTを維持しつつ動的データを提供できるため、Suspense境界の設計が重要な設計判断になる。

- **Turbopack への完全移行:** Dev環境でのTurbopack採用は高速化が顕著（HMRが数十ms単位）。本番ビルドもTurbopackが安定化しており、大規模プロジェクトではビルド時間の50-70%削減が報告されている。

- **`next/image` と `next/font` の最適化徹底:** LCP改善の最短経路。`sizes`属性の正確な指定とフォントの`display: swap`設定は今も見落とされがち。Core Web Vitalsへの直接的な影響が最も大きい箇所。

- **Edge Runtimeの選択的利用:** ミドルウェアや地理情報依存のロジックをEdgeに移すとレイテンシが劇的に改善するが、Node.js API非対応の制約がある。Runtime選択はAPIルート設計時に明示的に議論すべきアーキテクチャ決定事項。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Prerendering (PPR) の本格普及:** Next.js 15/16でPPRが安定化し、静的シェル+動的ストリーミングのハイブリッドがデフォルト戦略となった。TTFBを維持しながらパーソナライズコンテンツを遅延配信できる点が最大の価値。

- **ポイント2: Suspense境界の設計がアーキテクチャの核心に:** データフェッチの粒度とSuspense境界の配置がUXとBundle Sizeの両方に直結する。粗すぎると滝型レンダリングに逆戻り、細かすぎるとレイアウトシフトが増加するため、コンポーネント設計段階からの意識が必須。

- **ポイント3: Server Actions + optimistic UI の統合パターンが成熟:** `useOptimistic` + Server Actionsの組み合わせが標準的なミューテーションパターンとして確立。クライアントStateを最小化しつつ体感速度を高められる。

- **ポイント4: Edge Runtime でのストリーミング制約に注意:** Vercel EdgeやCloudflare WorkersでRSCストリーミングを使う場合、Node.js API非対応・メモリ制限・実行時間制限が依然ボトルネック。Durable Objects等との組み合わせが現実解。

- **ポイント5: キャッシュ戦略の複雑化がチームの技術負債に:** `fetch` キャッシュ・Route Cache・Full Route Cache・Client Router Cacheの4層が絡み合い、デバッグコストが高い。`"use cache"` ディレクティブ（Next.js 16実験的機能）による明示的キャッシュ制御への移行を早めに検討すべき。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの実用的普及:** Next.js + TypeScript スタックでは tRPC がデファクトに近づいており、型安全なend-to-end APIをスキーマ定義なしで実現できる点が開発速度を大幅に向上させている。

- **GraphQLの用途特化:** 汎用APIには過剰なため、複雑なデータグラフ（BFF・マイクロサービス集約）に絞って採用するパターンが定着。Apollo Federationより軽量な Hive / Mesh が選ばれる傾向。

- **REST + OpenAPI の再評価:** AI ツール（Copilot・Claude）がOpenAPIスキーマからコードを生成できるため、RESTの「退屈さ」が逆に資産になっている。Zod → OpenAPIの自動生成チェーンが実用的。

- **HTTP/3 と Server-Sent Events の台頭:** WebSocketの複雑さを避けてSSE（一方向ストリーム）が再注目。特にAI応答ストリーミングのユースケースで、REST+SSEの組み合わせが最もシンプルな解となっている。

- **Contract-first vs Code-first の収束:** tRPC・Zod・Effect-TS など型システムを中心に据えたCode-firstアプローチが、従来のContract-first（OpenAPI先行）の利点を吸収しつつあり、2026年はその境界がさらに曖昧になっている。

### 4. serverless edge computing 2026

- **ポイント1: WebAssembly（Wasm）がエッジのデファクトランタイムに:** V8 IsolateベースのCloudflare WorkersやDeno Deployに加え、WasmベースのランタイムがNode.js非依存でコールドスタートをほぼゼロに抑える主流手段となった。Next.js Edge RuntimeもWasm互換が前提になりつつある。

- **ポイント2: AI推論のエッジ移動が加速:** LLMの量子化モデル（<4B params）をエッジで直接推論するユースケースが急増。Cloudflare AI・Vercel AI SDKのEdge対応により、レイテンシ敏感なAI機能はオリジンへのラウンドトリップなしで完結できる。

- **ポイント3: エッジDBとデータの局所性が課題から強みへ:** Cloudflare D1・Turso（libSQL）・Neon（Postgres serverless）がエッジリージョンへのレプリカ配布をサポートし、「エッジで書き込みができない」問題が解消されつつある。スタック選定時にDBのエッジ対応可否が必須チェック項目。

- **ポイント4: 可観測性ギャップへの対応が急務:** エッジ関数はサーバーレスよりさらに分散しており、分散トレーシング（OpenTelemetry）の導入がデバッグの前提条件。Baselime買収後のCloudflare ObservabilityやVercel Analyticsがエッジ特化の可観測性を整備中。

- **ポイント5: コスト構造の再評価:** リクエスト単価は安いが、グローバルレプリケーションやKV書き込みコストが積み上がりやすい。CDNキャッシュ戦略（`stale-while-revalidate`、ISR）との組み合わせ設計でオリジンリクエストを最小化することがコスト最適化の핵심。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** FIDO2/WebAuthn標準のパスキーがパスワード認証を置き換えるデファクトスタンダードになりつつあり、主要ブラウザ・OSでの対応も成熟した今、新規プロジェクトでは最初からパスキー対応を設計に組み込むべき。

- **セッション管理の短命化とリフレッシュ戦略:** JWTのアクセストークンは5〜15分の短い有効期限を設定し、リフレッシュトークンはRotating Refresh Token方式で都度無効化する設計が標準的。トークンの長期有効化はリスクが高く、いまや設計ミスと見なされる。

- **デバイス信頼スコアリングの導入:** IPアドレス・デバイスフィンガープリント・行動パターンを組み合わせたリスクベース認証（Adaptive MFA）が普及しており、異常検知時のみ追加認証を求めるUX設計が競争優位になる。

- **サプライチェーン攻撃対策としての依存ライブラリ審査:** 認証ライブラリ（NextAuth等）の脆弱性は影響範囲が広大なため、`npm audit` や Dependabotのアラートを自動CIに組み込み、認証関連パッケージの更新を最優先で適用するプロセスが必須。

- **ゼロトラスト原則の徹底:** 「内部ネットワークは安全」という前提を捨て、全APIリクエストでトークン検証・最小権限チェックを実施する設計を採用する。特にマイクロサービス・Edge Functionsが増えた現在、サービス間通信にもmTLSまたは署名付きトークンを使うべき。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のエッジ対応強化:** Prisma Accelerate によりエッジランタイム（Cloudflare Workers等）でのコネクションプーリングが実用レベルに達し、Supabase との組み合わせでサーバーレス環境でのコールドスタート問題が大幅に緩和された。

- **Supabase の RLS (Row Level Security) とアプリ層の責務分離:** 2026年時点では RLS をデータアクセス制御の主軸に置き、Prisma はクエリビルダーとして活用する二層防衛アーキテクチャが定着しつつある。ただし RLS の複雑化がパフォーマンスボトルネックになるケースに注意が必要。

- **Prisma Postgres（旧 Prisma Data Platform）の台頭:** Prisma が独自マネージド Postgres を提供し始め、Supabase と直接競合する領域が生まれた。プロジェクト規模・チーム体制に応じた選定基準の見直しが求められる。

- **型安全クエリの限界とパフォーマンスチューニング:** Prisma の ORM 抽象化は開発速度を上げる一方、複雑な集計・全文検索では生 SQL（Supabase の `rpc` 関数）へのエスケープが依然必要。`EXPLAIN ANALYZE` を CI に組み込む運用が現場のベストプラクティスとして広まっている。

- **リアルタイム機能は Supabase Realtime に一任:** Prisma はリアルタイム変更監視を持たないため、チャット・通知・共同編集等のユースケースでは Supabase の Realtime チャンネル（PostgreSQL の論理レプリケーションベース）を直接利用し、Prisma と役割を明確に分担するアーキテクチャが推奨される。

### 7. WebAssembly Rust performance 2026

- **WASI 0.2 / Component Modelの成熟:** 2025年末にWASI 0.2が安定版となり、Rustの`cargo component`ツールチェーンでWasmコンポーネントをライブラリ単位で構成・再利用できるようになった。マイクロサービス的なモジュール分割がWasm上で現実的に。

- **SIMD・スレッド対応の普及:** WebAssembly SIMDとShared Memoryがブラウザ・サーバー双方で標準化され、Rustの`rayon`並列処理がWasm環境でも動作するケースが増加。画像処理・ML推論のクライアントサイド実行が実用域に。

- **Wasmtime / WasmEdgeのサーバーサイド高速化:** JIT最適化の改善により、ネイティブコード比で95%前後の実行速度を達成するケースが報告されている。エッジランタイム（Fastly Compute、Cloudflare Workers）でのRust+Wasmは今や本番採用の第一選択肢。

- **バイナリサイズ問題の緩和:** `wasm-opt`（Binaryen）とRustの`panic = "abort"` + LTOの組み合わせで、従来比30-40%のサイズ削減が容易になった。ただし初期ロード最適化にはStreaming Instantiationの実装が依然として重要。

- **GCプロポーザルとRustの関係:** WasmGCの標準化によりGC言語（Kotlin、Dart）のWasm参入が加速しているが、Rustはゼロコストなメモリ管理でその恩恵を受けない代わりに**予測可能なレイテンシ**という差別化優位性が明確化。リアルタイム処理領域ではRustが引き続き最有力。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** クライアントコンポーネントは「葉ノード」に限定し、データフェッチ・レイアウト・ビジネスロジックはすべてServer Componentsで処理する。バンドルサイズとTTFBが劇的に改善される。

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降でPPRが安定化し、静的シェル＋動的ストリーミングのハイブリッドが標準パターンに。`Suspense`境界の設計がパフォーマンスの鍵となる。

- **Server Actions によるフォーム処理の統一:** API Routeを経由せず、Server Actionsで直接ミューテーションを処理するパターンが定着。`useActionState`との組み合わせで楽観的UI更新も簡潔に実装できる。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** `fetch`のキャッシュオプションに加え、`use cache`で関数・コンポーネント単位のキャッシュが可能に。`revalidateTag`との組み合わせでISRより柔軟なキャッシュ戦略を実現。

- **Parallel Routes + Intercepting Routes でモーダル設計を簡素化:** URLを保持しつつモーダルやサイドパネルを実装するパターンが成熟。ブックマーク・シェア可能なUIを追加実装コストなしで実現できる。

### 9. Vercel Edge Functions optimization 2026

- **Cold Start排除の優先度:** Edge FunctionsはV8 Isolateベースでコールドスタートが~0msだが、2026年時点でもバンドルサイズ管理が重要。`next/dynamic`による遅延ロードとtree-shakingを徹底し、1MB制限を意識した設計が必要。

- **Fluid Compute活用:** VercelのFluid Computeモデルにより、Edge/Serverlessの境界が曖昧化。CPUバウンドな処理はServerless（Node.js runtime）、レイテンシ敏感なルーティング・A/B・認証はEdgeと使い分けることでコスト最適化できる。

- **Middleware最適化:** `matcher`設定で処理対象パスを絞り込み、不要なリクエストへのMiddleware実行を排除。`request.geo`や`request.ip`を活用した地域別コンテンツ配信をEdgeで完結させる。

- **KV/R2との組み合わせ:** Vercel KV（Redis）やCloudflare R2との連携でEdge上でのステートフルな処理が実用域に。データベース接続よりレイテンシを大幅削減でき、セッション管理・レートリミットの実装に有効。

- **Observability強化:** 2026年時点でEdge FunctionsのOpenTelemetry対応が進化。`@vercel/otel`を導入してスパントレースを取得し、どのEdgeリージョンでボトルネックが発生しているか可視化することがパフォーマンスチューニングの前提になっている。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded/Nominal Typesが標準化し、プリミティブ型の誤用（UserIdとOrderIdの混在など）をコンパイル時に防ぐパターンが定着しつつある。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` が2026年では必須スキルとなり、型推論を維持しながら型チェックを行うことで、`as` キャストの危険な使用を大幅に削減できる。

- **Template Literal Typesによる文字列の型安全性:** APIルートやイベント名など文字列定数を `type Route = \`/api/${string}\`` のように型付けすることで、実行時エラーをコンパイル時に捕捉するパターンが成熟してきた。

- **`NoInfer<T>` ユーティリティの活用:** TypeScript 5.4で導入された `NoInfer<T>` により、ジェネリック関数の型推論をより精密に制御でき、意図しない型の広がり（widening）を防ぎやすくなった。

- **Zodとの統合によるランタイム型安全性の確立:** `z.infer<typeof schema>` でZodスキーマから型を導出するパターンが事実上の標準となり、APIバウンダリでの型安全性がコンパイル時・実行時の両方で保証されるアーキテクチャが主流になっている。
