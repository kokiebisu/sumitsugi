# CTO Knowledge - 2026-04-08

## Daily Update (2026-04-08)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルを最小化するため、データフェッチとロジックをサーバーコンポーネントに集約する。`"use client"` ディレクティブは本当に必要な箇所（インタラクション・状態管理）のみに限定することがパフォーマンスの起点となる。

- **Partial Prerendering (PPR) の本番投入:** 静的シェルを即座に配信しつつ、動的コンテンツをStreaming SSRで差し込むPPRがNext.js 15以降で安定化。TTFB削減とパーソナライズの両立が実現できる。

- **`<Image>` / フォント最適化の再確認:** `next/image` のサイズ指定漏れやCLS（Cumulative Layout Shift）は依然としてCore Web Vitalsのボトルネック。`next/font` によるフォントのセルフホスティングでネットワークウォーターフォールを排除できる。

- **Route Segment Cache の適切な設計:** App Routerの `revalidate` / `dynamic` 設定を誤るとキャッシュが効かず、無駄なサーバー負荷が発生する。データの鮮度要件に応じてセグメント単位でキャッシュ戦略を明示的に設計すること。

- **Bundle Analyzer + Server-only の継続的運用:** `@next/bundle-analyzer` で肥大化を定期検出し、クライアントに流出すべきでないコード（DB接続・APIキー）は `server-only` パッケージで保護する。CI上でバンドルサイズの差分を可視化する習慣が長期的な品質維持に直結する。

### 2. React Server Components streaming 2026

- **Suspense境界による段階的ストリーミングの成熟:** 2026年時点でRSCのストリーミングはNext.js App Routerで本番標準となり、`<Suspense>`境界を細粒度に配置することでTTFB最小化とUX向上が両立できる設計パターンが確立されている。

- **PPR（Partial Pre-Rendering）の実用化:** Next.js 15以降でPPRが安定化し、静的シェルを即時配信しつつ動的部分をストリームするハイブリッドアーキテクチャが主流になりつつある。CDNキャッシュとダイナミックデータを同一ページで共存させられる点が最大の実務メリット。

- **Server Actionsとの統合でRound-tripを削減:** RSCとServer Actionsの組み合わせにより、フォーム送信後の再レンダリングもストリームで返せるようになり、従来のAPI Route + クライアントfetchパターンより大幅にネットワーク往復を減らせる。

- **キャッシュ戦略の複雑化が課題:** `fetch`キャッシュ、Route Segment Cache、Full Route Cacheなど複数レイヤーが存在し、ストリーミングと組み合わせると意図しないキャッシュヒットが発生しやすい。`revalidateTag`と`unstable_cache`を適切に設計しないと本番で予期しない古いデータ表示が起きる。

- **エラーハンドリングの境界設計が重要:** ストリーミング中のエラーは`error.tsx`境界で捕捉されるが、すでに送信済みのHTMLヘッダーは変更できないため、ユーザー体験を守るには粒度の細かいエラー境界と`loading.tsx`の組み合わせ設計が不可欠。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年時点でtRPCはNext.js/Remixとの統合が成熟し、フロントエンド・バックエンド間の型共有が標準的なアプローチになりつつある。スキーマ定義の重複排除により開発速度が大幅に向上している。

- **GraphQLの選択的採用:** 複数クライアント（Web/Mobile/サードパーティ）が異なるデータ形状を必要とするケースでは依然としてGraphQLが最適だが、内部APIや単一クライアント構成ではオーバーエンジニアリングになりやすく、tRPCやREST+OpenAPIへの回帰が見られる。

- **REST+OpenAPIの再評価:** OpenAPI 3.1とコード生成ツール（Orval, Hey API）の成熟により、型安全なRESTクライアントが自動生成可能になった。外部公開APIやチーム間契約にはREST+OpenAPIが依然として業界標準。

- **Server Actionsとの競合:** Next.js 15以降のServer ActionsがtRPCの一部ユースケースを代替しており、APIレイヤーを省略したサーバー直接呼び出しパターンが普及。ただし複雑な認証・バリデーションロジックはtRPCミドルウェアの方が整理しやすい。

- **選定指針:** 公開API→REST+OpenAPI、内部フルスタック（TypeScript統一）→tRPC、多様なクライアント/複雑なデータグラフ→GraphQL。2026年の現場では「用途別使い分け」が最適解であり、単一技術への統一にこだわらないことが重要。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** WebAssembly（Wasm）ランタイムの成熟により、軽量LLMモデルをCDNエッジノードで直接実行するパターンが定着。レイテンシを劇的に削減しつつ、中央サーバーへの依存を排除できる。

- **Durable Objectsによるステートフルエッジの台頭:** Cloudflare Durable ObjectsやWorkers KVの進化により、「エッジはステートレス」という制約が崩れ、分散セッション管理やリアルタイム協調機能をエッジで実装できるようになった。

- **コールドスタート問題の実質的解消:** V8 Isolateベースの実行環境が主流となり、従来のコンテナベースに比べてコールドスタートが<1msに。ただしNode.js互換レイヤー依存のコードは依然としてペナルティがあり、エッジネイティブな設計が求められる。

- **マルチクラウドエッジの複雑性:** Cloudflare Workers・Vercel Edge Functions・AWS Lambda@Edgeの間でAPIと制約が異なり、ベンダーロックインが深刻化。抽象レイヤー（Hono等）の採用で移植性を確保する設計判断が重要になっている。

- **オブザーバビリティの遅れがボトルネック:** エッジ実行環境は分散ログ・トレーシングの標準化が遅れており、障害調査コストが高い。OpenTelemetryのエッジ対応が進んでいるが、本番運用前にモニタリング戦略を先に設計することを強く推奨する。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の標準化:** パスワードレス認証がデファクトスタンダードになりつつあり、フィッシング耐性のあるパスキーをメインの認証手段として採用することが必須レベルになっている。

- **MFAの強制とフォールバック廃止:** SMS/メールOTPはSIMスワップ攻撃に脆弱なため、TOTPまたはハードウェアキーのみを許可し、弱いフォールバック手段を残さない設計が求められる。

- **セッション管理のゼロトラスト化:** 長期セッショントークンは廃止傾向にあり、短命なアクセストークン（15分以下）＋ローテーションするリフレッシュトークンの組み合わせに加え、デバイス・IP・行動ベースの継続的リスク評価が主流になっている。

- **サプライチェーン攻撃対策としての依存関係の最小化:** 認証ライブラリへの依存はOIDC/OAuth2の実績あるSDKに絞り、npm/PyPIのマルウェア混入リスクを軽減するためSBOMの生成と定期監査が必須。

- **AIによる異常ログイン検知の組み込み:** 2026年時点では機械学習ベースの行動分析をIDaaS層（Auth0, Clerk等）が標準提供しており、カスタム実装よりもこれを活用してアカウント乗っ取りを事前検知するアプローチが費用対効果で優れている。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x の Edge Runtime 対応成熟:** Prisma の Accelerate（グローバルコネクションプール）と組み合わせることで、Next.js Edge Functions や Cloudflare Workers からも安全にDB接続できるようになり、サーバーレスでのコールドスタート問題が実用レベルで解消されている。

- **Supabase の pgvector 活用が主流化:** `pgvector` 拡張による埋め込みベクトル検索が Supabase に標準統合され、外部ベクトルDBを別途立てずに RAG アーキテクチャを単一 Postgres インスタンスで完結させる構成が増加している。

- **Row Level Security（RLS）とアプリ層の責務分離:** Supabase の RLS ポリシーをデータ層のアクセス制御として活用し、アプリ側の認可ロジックを薄くする設計が定着。ただし Prisma 経由では RLS がバイパスされるリスクがあるため、`set_config('app.user_id', ...)` によるセッション変数注入パターンが必須の実装知識となっている。

- **Prisma Migrate vs Supabase Migrations の二重管理問題:** Supabase CLI の `supabase/migrations/` と Prisma の `prisma/migrations/` が競合しやすく、2026年現在は **Prisma をスキーマ定義のみに使い、マイグレーション実行は Supabase CLI に統一**するパターンが推奨される運用として固まってきた。

- **リアルタイム機能の設計境界:** Supabase Realtime（Postgres の Logical Replication ベース）は読み取り系のリアルタイム同期に強力だが、Prisma の ORM 層とは独立して動作するため、**書き込みは Prisma・購読は Supabase Client** と明確に責務を分けることが保守性の高いアーキテクチャの鍵。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の本格普及:** 2026年時点でWASI Preview 2が安定化し、RustのWASM出力がホスト環境非依存のポータブルコンポーネントとして配布可能になった。wasmtime・spinなどランタイムの互換性も向上し、エッジ・サーバーレス双方での採用が加速している。

- **Rustコンパイル最適化の成熟:** `wasm-opt`（Binaryen）との統合やLTO（Link-Time Optimization）がCargoで標準化され、バイナリサイズと実行速度の両立が容易になった。`wasm32-unknown-unknown`と`wasm32-wasip2`のターゲット選択が用途に応じて明確化されている。

- **SIMD・スレッド対応の実用化:** WebAssembly SIMDとShared Memory（Threads提案）がChrome/Firefox/Safariで揃って安定サポートされ、Rustの`std::arch`経由でSIMD命令を直接活用できる。音声処理・画像処理・ML推論での実測スループットがネイティブの80〜95%に到達するケースも出ている。

- **Wasmtime/WasmEdgeのサーバーサイド採用:** CloudflareワーカーやAWS Lambdaの一部でRust+WASMコンテナがOCIコンテナの代替として使われ始め、コールドスタートが数ミリ秒単位に短縮された。Kubernetes上でwasmunoを用いたWasm Podも実運用例が増えている。

- **ツールチェーン成熟による開発体験向上:** `cargo-component`と`wit-bindgen`によるインターフェース定義が標準化し、Rustの型安全性をWASMコンポーネント境界まで保ったままABI設計できるようになった。フロントエンド（`wasm-bindgen`/`leptos`）とバックエンドWASMで同一Rustコードを共有するモノレポ構成が現実的な選択肢となっている。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** クライアントコンポーネントは状態・イベントハンドラが必要な最小単位に限定し、データフェッチはすべてServer Componentsで行う。バンドルサイズとTime to Interactiveが劇的に改善される。

- **Parallel Routes と Intercepting Routes の活用:** モーダル・スライドオーバー・タブUIを `/(@modal)/` パターンで実装することで、URLを維持しつつ柔軟なUI遷移が可能になる。複雑なUX要件をルーティング層で解決できる。

- **`use cache` / `unstable_cache` による細粒度キャッシュ:** ページ単位ではなく関数・クエリ単位でキャッシュを制御する設計が主流に。`revalidateTag` との組み合わせで、サーバープッシュなしに即時無効化が実現できる。

- **Server Actions を状態管理の代替として使用:** フォーム送信・楽観的更新に `useActionState` + Server Actions を採用することで、REST APIエンドポイントを別途定義するコストを削減。ただし複雑な非同期フローはAPIルートに残す判断が重要。

- **Turbopack 本番対応への移行:** 2026時点でTurbopackが安定化し、大規模プロジェクトでのコールドスタート・HMRが従来比5〜10倍高速化。`next dev --turbo` から `next build --turbo` への段階移行を計画すべき時期。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択最適化:** Node.js RuntimeとEdge Runtimeの使い分けが重要で、Edge Functionsは低レイテンシが必要なルーティング・認証ミドルウェアに限定し、重いDBアクセスは通常のServerless Functionsに委ねるのが2026年のベストプラクティス。

- **Fluid Computeとのハイブリッド活用:** VercelのFluid Compute（サーバーレスとエッジの中間）が成熟し、リージョン間でのリクエスト集約とコールドスタート削減を両立できるため、Pure Edgeに固執せずワークロードに応じた使い分けが求められる。

- **KVストアとの連携パターン:** Vercel KV（Redis互換）やEdge Configを活用した設定値・セッション管理が定番化しており、エッジでの外部DB直接呼び出しは避け、低レイテンシストアをキャッシュ層として挟む設計が必須。

- **バンドルサイズの厳格管理:** Edge FunctionsのサイズはNode.js Runtimeより大幅に制限されるため（~4MB）、`next/server`のtree-shakingやdynamic importの活用、重量級ライブラリ（Prisma等）のEdge排除がパフォーマンスを左右する。

- **オブザーバビリティの強化:** Edge層は従来のAPMが効きにくく、Vercel Analytics + OTELカスタムスパンを組み合わせたトレーシングを早期に導入することで、レイテンシのボトルネック特定とコスト最適化の両方に効果がある。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `type UserId = string & { readonly _brand: 'UserId' }` パターンがチーム標準として定着し、プリミティブ型の意味的誤用（UserIdにOrderIdを渡すなど）をコンパイル時に防ぐ。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` により、型推論を保ちつつ型チェックを強制できる。`as` キャストの乱用を廃止しコードの安全性が向上した。

- **Template Literal Types によるAPIルート型安全:** `type ApiRoute = `/api/${string}`` のようなパターンでURLやイベント名を型レベルで制約し、実行時エラーをゼロに近づける設計が主流。

- **`NoInfer<T>` ユーティリティの実用化:** TypeScript 5.4で導入された `NoInfer<T>` により、ジェネリック関数の型推論をコントロールしやすくなり、意図しない型ワイドニングを防ぐコードが書きやすくなった。

- **Zod + `z.infer<>` のバウンダリ戦略:** 外部API・フォーム・環境変数などシステム境界では必ずZodでバリデーションし、内部は `z.infer<>` から型を派生させる。型定義の重複を排除しながら実行時安全性を担保する設計が2026年のデファクト。
