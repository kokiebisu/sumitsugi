# CTO Knowledge - 2026-09-16

## Daily Update (2026-09-16)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Prerendering / PPRの標準化）:** Next.js 16ではPPRが安定版に近づき、静的シェルを即座に返しつつ動的部分をストリーミングできる。ダッシュボードや物件詳細ページなど、静的部分（レイアウト）と動的部分（在庫状況）が混在する画面ほど恩恵が大きい。

- **ポイント2（React Compilerの導入）:** 手動`useMemo`/`useCallback`への依存を減らし、ビルド時に自動メモ化される。App Router全体で有効化することで、リストや検索結果コンポーネントの再レンダリングコストを大幅に削減できる。

- **ポイント3（Turbopackのフルサポート）:** ビルド・開発サーバー両方でTurbopackがデフォルト化しつつあり、`bun run build`の時間短縮に直結する。CIのビルド時間がボトルネックになっている場合、移行の投資対効果が高い。

- **ポイント4（画像・フォントの自動最適化とCDNキャッシュ戦略）:** `next/image`のAVIF優先配信と、Vercel以外のホスティングでもISR/On-Demand Revalidationを組み合わせることで、物件写真中心のUIでもLCPを抑えられる。キャッシュヘッダー設計がSEOとCore Web Vitals双方に効く。

- **ポイント5（Server Actionsのセキュリティとパフォーマンスの両立）:** フォーム送信（引越し費用計算・問い合わせ等）をServer Actionsに寄せる際、Zodバリデーションと組み合わせてクライアントJSバンドルを削減できる一方、乱用するとウォーターフォールが発生するため、並列fetchやキャッシュタグ（`revalidateTag`）の設計が重要になる。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 16ではPPRが安定版となり、静的シェルを即座に返しつつ動的部分のみをストリーミングする構成が標準になっている。sumitsugiでは物件一覧の静的レイアウトを即表示し、価格や空き状況などの動的データだけを`Suspense`境界でストリーミングすることで、体感速度を大きく改善できる。

- **`use cache`ディレクティブとの組み合わせ:** RSCのキャッシュ制御がディレクティブベースで明示的になり、コンポーネント単位でキャッシュ戦略を宣言できるようになった。前の住人の活動歴データのように更新頻度が低いデータは積極的にキャッシュし、ストリーミングと併用することでサーバー負荷とTTFBを同時に最適化できる。

- **Server Actionsのストリーミングレスポンス対応:** フォーム送信後のUI更新をストリーミングで段階的に返せるようになり、引越し費用計算のような多段階処理（バリデーション→計算→結果表示）を1つのリクエストで逐次表示できる。ユーザーに待機中の空白画面を見せずに済むため、成約フローの離脱率改善に直結する。

- **エラーバウンダリとストリーミングの粒度設計が重要:** ストリーミング単位を細かくしすぎるとウォーターフォールでかえって遅くなるケースがあるため、`Suspense`の粒度は「意味のあるUI単位」（例: 物件カード1枚ではなく一覧セクション全体）で設計すべきというのが最近のベストプラクティス。過度な分割はネットワークラウンドトリップ数を増やすだけなので注意。

- **Bunランタイムとのストリーミング互換性向上:** Bun 1.xのHTTPサーバー実装がNode.jsのReadableStream APIとの互換性を高めており、RSCのストリーミングレスポンスをBun環境でも安定して扱えるようになった。sumitsugiのBunベース構成でも追加の互換レイヤーなしにストリーミングの恩恵を受けられる。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** 2026年時点では「REST vs GraphQL vs tRPC」の二者択一ではなく、社内向けフルスタックTypeScript環境ではtRPCで型安全性とDXを最大化し、外部公開APIやサードパーティ連携にはRESTを維持するハイブリッド構成が主流になっている。sumitsugiのようにNext.js App Router単一リポジトリで完結するなら、Server ActionsとtRPCの組み合わせでAPI層自体を薄くし、型定義をクライアント・サーバー間で共有するのがコスト対効果が高い。

- **ポイント2:** GraphQLは大規模チームでのフィールド粒度の柔軟性という利点より、N+1問題やキャッシュ戦略の複雑さ、追加インフラ（Apollo Server等）の運用負荷がMVP段階では割に合わないケースが多く、物件検索のようなクエリパターンが比較的固定的なドメインではRESTやtRPCの方がシンプルで保守しやすい。

- **ポイント3:** OpenAPI 3.1 + Zodスキーマから型とドキュメントを自動生成する構成（zod-to-openapi等）が定着し、Zodをバリデーション層として既に採用している場合はAPIスキーマとランタイム検証を一元管理できるため、二重管理によるドリフトを防げる。

- **ポイント4:** エッジランタイム（Vercel Edge Functions, Cloudflare Workers）でのAPI実行が一般化し、レイテンシーが重要な物件検索・お気に入り機能などの読み取り系エンドポイントはエッジ配置、決済や引越し費用計算のような書き込み系はNode.jsランタイムに残すという使い分けが、パフォーマンスとNext.js 16の互換性の両立に有効。

- **ポイント5:** 認証・レート制限・入力検証をAPI Route/Server Action単位で個別実装するのではなく、middlewareレイヤーで横断的に共通化する設計が標準化しつつあり、`.claude/rules/standards.md`が求めるZodによる境界検証とセキュリティ要件（XSS/CSRF対策）を満たすうえでも、認証系のtRPCミドルウェアやNext.jsのmiddleware.tsに検証ロジックを集約する方が保守コストを抑えられる。

### 4. serverless edge computing 2026

- **エッジでのAI推論:** Cloudflare Workers AIやVercel Edge Functionsで軽量LLM推論をエッジ実行できるようになり、レイテンシをms単位に削減しつつコストも抑えられる。ただしモデルサイズ制約があるため、重い処理は依然中央集権的なAPIとのハイブリッド構成が現実的。

- **WASMベースのランタイム統一:** WebAssemblyがエッジ・サーバー・ブラウザ間で共通実行環境として定着し、Node.js互換レイヤー(WinterCG準拠)により同一コードをVercel/Cloudflare/Denoで動かせるようになった。ベンダーロックイン回避の観点からも採用価値が高い。

- **コールドスタート問題の実質解消:** V8 Isolateベースのアーキテクチャ(Cloudflare Workers等)によりコールドスタートが1ms未満まで縮小し、従来のコンテナ型サーバーレス(Lambda等)との差が開いている。ユーザー体験を重視するなら分散配信が必要なコンポーネントから優先的にエッジ移行を検討すべき。

- **エッジDBの成熟:** Turso/D1/PlanetScaleなど分散SQLiteベースのエッジDBが実用段階に入り、リージョンレプリケーションで読み取りレイテンシを大幅短縮できる。ただし書き込み一貫性のトレードオフがあるため、住人情報のようなトランザクション整合性が重要なデータは引き続き中央DB設計を維持すべき。

- **観測性・デバッグの複雑化:** 分散実行によりトレーシング(OpenTelemetry)とログ集約の重要性が増しており、エッジ導入前にモニタリング基盤を整備しないと障害時の原因特定コストが跳ね上がる。sumitsugiのような小規模チームでは、エッジ移行は「効果が高い箇所」に限定し、全面移行は避けるのが賢明。

### 5. authentication security best practices 2026

**ポイント1:** パスキー（FIDO2/WebAuthn）への完全移行が主流化しており、パスワードレス認証をデフォルトにすることでフィッシング耐性を大幅に高められます。SMS OTPは依然としてSIMスワップ攻撃に脆弱なため、TOTPやパスキーへの段階的移行を推奨します。

**ポイント2:** セッション管理では、トークンのローテーション（refresh token rotation）とデバイスフィンガープリンティングを組み合わせ、盗まれたセッショントークンの再利用を検知する仕組みが標準になりつつあります。

**ポイント3:** ゼロトラスト原則に基づき、ログイン時だけでなくセッション中も継続的にリスクスコアを評価する「継続的認証（Continuous Authentication）」が重要視されています。

**ポイント4:** 認可（Authorization）側では、RBACからABAC/ReBAC（属性・関係ベース）への移行が進み、特に多社間・多役割が絡むマーケットプレイス型サービスではきめ細かいアクセス制御が必須になっています。

**ポイント5:** レート制限やアカウントロックアウトだけでなく、Web Application Firewall（WAF）とビヘイビア分析を組み合わせたクレデンシャルスタッフィング対策が、ログインエンドポイントの標準防御として求められています。

### 6. database architecture Prisma Supabase 2026

- **エッジ最適化とコネクション管理:** Prisma AccelerateやSupabaseのPgBouncer統合により、サーバーレス環境でのコネクションプール枯渇問題が実用レベルで解決されつつある。当社のようなNext.jsサーバーレス構成では、Prisma Client単体でなくAccelerate経由の接続を標準化することでコールドスタート時のDB接続エラーを大幅に削減できる。

- **Row Level Security (RLS) をアプリ層の代わりに使う設計:** SupabaseのRLSポリシーをPrismaのスキーマ管理と併用し、認可ロジックをDB側に寄せる設計が主流になりつつある。前の住人・次の住人間の物件データアクセス制御など、マルチテナント的な権限分離が必要な箇所ではRLSを優先すべき。

- **Prisma Postgres / Supabase Branching によるプレビュー環境DB:** PRごとに独立したDBブランチを自動生成する機能（Supabase Branching、Neonライクなブランチ戦略）が2026年時点で成熟し、E2Eテストやステージング検証のためのデータ分離コストが激減している。CI/CDにこれを組み込めば、`bun run test:e2e` の信頼性が上がる。

- **型安全とスキーマドリフト対策:** Prismaのスキーマを唯一の真実源（Single Source of Truth）とし、SupabaseのマイグレーションをPrisma Migrate経由で一元管理することで、`status: 'draft' | 'public'` のようなUnion型とDBのenum/check制約の乖離を防げる。手動でSupabase側のスキーマを変更するとドリフトが発生しやすいため要注意。

- **パフォーマンス面ではPgBouncerのトランザクションモードとPrismaの相性に注意:** Prisma 6系以降は`pgbouncer=true`パラメータの扱いが改善されているが、Supabaseのプーラーモード（Transaction vs Session）によってPrepared Statementの挙動が変わるため、本番導入前に負荷テストで確認するのが必須。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Wasm GCとcomponent modelの標準化が進み、Rustのwasm-bindgen/wasm-packを介さずとも軽量なバイナリ生成が可能になってきている。当プロジェクトのフロントで重い処理（PDF生成やインテリアシミュレーション等）を持つ場合、ネイティブJSより2〜5倍高速化できるケースがあるため、将来的な検討候補になる。

- **ポイント2:** WASI Preview 2の普及によりサーバーサイドでのWasm実行（Wasmtime, Fastly Compute等）が現実的な選択肢になっており、コールドスタートがコンテナより大幅に速い。ただし現状のNext.js/Bunスタックとの統合コストが高いため、今すぐ移行する優先度は低い。

- **ポイント3:** RustのSIMD対応とマルチスレッド（Wasm Threads）がブラウザで広くサポートされ始め、画像処理・座標計算など重い演算をクライアント側にオフロードしやすくなった。物件検索の地図描画や画像最適化機能を強化する際に有効な選択肢。

- **ポイント4:** バイナリサイズ最適化（`wasm-opt`, `twiggy`によるプロファイリング）がツールチェーンとして成熟し、ページロード時間への影響を抑えやすくなっている。ただし依然としてTypeScript実装より開発・デバッグコストが高いため、パフォーマンスがボトルネックになる箇所に限定して導入すべき。

- **ポイント5:** 現状のMVPフェーズでは通常のTS/Next.js実装で十分にパフォーマンス要件を満たせるため、Wasm導入はROIが低い。ローンチ後にスケールし、明確なCPUバウンドのボトルネック（大量データの地図クラスタリング等）が顕在化した際に再評価するのが妥当。

### 8. Next.js App Router patterns 2026

- **ポイント1（Server ActionsとPPR標準化）:** Partial Prerendering（PPR）がstableとなり、静的シェルを即座に返しつつ動的部分をストリーミングする構成が標準パターン化。Server Actionsと組み合わせることで、フォーム送信やミューテーションをAPI Routeなしで完結でき、`src/app/`配下のコード量を大幅に削減できる。

- **ポイント2（`use cache`ディレクティブによる細粒度キャッシュ）:** Next.js 15以降で導入された`use cache`ディレクティブが2026年時点で主流化し、関数・コンポーネント単位でキャッシュ境界を明示的に制御可能に。`revalidateTag`との併用で、物件情報（`data.ts`）のような頻繁に更新されるデータでも過剰な再検証を避けつつ鮮度を保てる。

- **ポイント3（Server Component中心のデータフェッチ）:** クライアントサイドの`useEffect`によるfetchは非推奨傾向が強まり、Server Componentでのデータ取得＋Suspenseによるストリーミングが基本パターンに。sumitsugiのような物件一覧・詳細ページでは、初期表示速度（LCP）改善に直結する。

- **ポイント4（型安全なルーティングとMiddleware軽量化）:** TypeScript統合が進み、`typedRoutes`によるリンク先の型チェックが実用レベルに。Middlewareは認証チェックなど最小限の処理に留め、重い処理はServer ComponentやRoute Handlerに委譲する設計が推奨される（Edge Runtimeの実行時間制約回避のため）。

- **ポイント5（Composable Architectureとテスト容易性）:** App Routerの`layout.tsx`/`template.tsx`によるネスト構造を活かし、認証コンテキスト（`auth-context.tsx`）のようなクロスカッティングな関心事をレイアウト層に集約する設計が定着。これによりPlaywrightでのE2Eテストがページ単位ではなくレイアウト単位で書きやすくなり、TDDサイクルとの親和性が高い。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約を前提にした設計:** Vercel Edge FunctionsはNode.js APIの一部が使えないV8アイソレート環境のため、重い依存関係（Prisma本体など）を避け、`@vercel/postgres`やEdge対応ORMを選定することでコールドスタートをほぼゼロに抑えられる。

- **ミドルウェアの実行コストに注意:** 全リクエストを通るMiddlewareにロジックを詰め込みすぎるとTTFBが悪化するため、認証チェックやリダイレクトなど軽量な処理に限定し、重い処理はサーバーレス関数やRSCに分離するのがベストプラクティス。

- **リージョン指定によるレイテンシ最適化:** データベース（例: Supabase/Neon）のリージョンとEdge Functionの実行リージョンを揃える（`export const preferredRegion`）ことで、DB往復のレイテンシを大幅に削減できる。日本向けサービスなら`hnd1`指定が有効。

- **Streaming SSR + Partial Prerenderingとの組み合わせ:** Next.js 16のPPR（Partial Prerendering）とEdge Functionsを組み合わせることで、静的シェルを即座に返しつつ動的部分（例: 物件の空き状況）だけをEdgeでストリーミング配信し、体感速度を改善できる。

- **可観測性の確保:** Edge環境はログ収集が制限されがちなので、Vercelの`waitUntil()`を使った非同期ログ送信や、OpenTelemetry対応のトレーシングを組み込み、本番障害時に原因追跡できる体制を早めに作っておくべき。

### 10. TypeScript type safety patterns 2026

**ポイント1:** ブランド型（Branded Types）による名目的型付けが標準化し、`UserId`と`ProductId`のような構造的に同一だが意味の異なるstring型を静的にコンパイル時に区別できるようになっている。

**ポイント2:** `satisfies`演算子の活用が定着し、オブジェクトリテラルの型推論を狭めたまま（widen させずに）、事前定義された型との適合性チェックを両立できるようになった。

**ポイント3:** Zodなどのスキーマライブラリと`z.infer`によるスキーマファースト開発が主流となり、実行時バリデーションと静的型を単一の定義から生成することで、境界（API入力・フォーム）での型安全性の二重管理を排除している（本プロジェクトのZod活用方針とも合致）。

**ポイント4:** テンプレートリテラル型と`const`型パラメータの組み合わせで、ルーティングパスやCSSクラス名のような文字列パターンをコンパイル時に検証するライブラリ（tRPCの後継的パターン）が普及し、フロントエンド・バックエンド間の型共有がさらに強化されている。

**ポイント5:** TypeScript 6系のGo移植版コンパイラ（tsgo）により大規模モノレポでの型チェック速度が10倍規模で向上し、strictモード全開でも開発体験を損なわないビルド構成が現実的な選択肢になっている。
