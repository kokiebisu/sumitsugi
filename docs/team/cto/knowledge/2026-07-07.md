# CTO Knowledge - 2026-07-07

## Daily Update (2026-07-07)

### 1. Next.js performance optimization 2026

- **ポイント1: Partial Prerendering (PPR) の標準化** Next.js 16ではPPRがデフォルト挙動に近づき、静的シェルを即座に返しつつ動的部分をストリーミングすることで、TTFBとLCPを大幅に改善できる。物件一覧ページのような「共通レイアウトは静的・物件データは動的」な構成に特に有効。

- **ポイント2: React Compiler によるメモ化の自動化** `useMemo`/`useCallback`を手動で書く必要が減り、再レンダリングコストが自動最適化される。ダッシュボードや検索フィルタなど、状態変化が多いUIでのCPU負荷削減に直結する。

- **ポイント3: `after()` とサーバーアクションの分離** レスポンス返却後に走らせたい処理（ログ記録、通知送信など）を`after()`で分離することで、ユーザー体感速度を落とさずにバックグラウンド処理を実行できる。問い合わせフォームや契約手続きの通知処理に応用可能。

- **ポイント4: 画像・フォントの最適化強化** `next/image`のAVIF優先配信とフォントのセルフホスティング自動化により、CLS(Cumulative Layout Shift)対策が簡素化。物件写真を多用するUIではCore Web Vitalsスコアに直接効いてくる。

- **ポイント5: Turbopackのビルド高速化が本番運用にも波及** 開発時だけでなく本番ビルドでも恩恵が出始めており、CI/CDのビルド時間短縮によってデプロイ頻度を上げやすくなる。頻繁な機能リリースを目指す現フェーズと相性が良い。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPartial Prerendering（PPR）が安定版となり、静的シェルを即座に返しつつ動的部分だけをストリーミングする構成が標準化された。初期表示速度とパーソナライゼーションを両立できるため、当プロジェクトのproperties一覧ページのような「静的な検索UI＋動的な物件データ」構成に適用しやすい。

- **ポイント2:** `use cache` ディレクティブとCache Componentsの組み合わせにより、Server Component単位での細粒度キャッシュ制御がAPI Routeを介さず可能になっている。listing詳細ページなど読み取り頻度が高く更新頻度が低いデータ（物件情報）はこの仕組みでDB負荷を大きく下げられる。

- **ポイント3:** Suspense境界の設計がパフォーマンスのボトルネックになりやすく、「1コンポーネント1 Suspense」ではなくウォーターフォールを避けるための境界の粒度設計（並列fetch + 単一境界）がベストプラクティスとして定着した。前の住人/次の住人のマッチング情報など複数データソースをまとめて取得するページで特に効く。

- **ポイント4:** Server Actionsのストリーミングレスポンス対応が進み、フォーム送信後の進捗UI（例: 引越し費用計算の多段処理）をクライアント側の複雑な状態管理なしで実装できるようになった。auth-contextのような既存Context実装との併用時は、RSCとクライアントStateの境界を明確にする設計判断が引き続き必要。

- **ポイント5:** ストリーミングSSRとエッジランタイムの組み合わせがデフォルト構成になりつつあり、TTFB最適化の観点からVercel以外のホスティングでもエッジ対応が前提になってきている。ローンチ判断時にはホスティング選定とストリーミング機能の互換性を事前検証すべき。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCの採用がフルスタックTypeScriptプロジェクトで加速している。型安全性がスキーマ定義なしで自動的に得られるため、Next.js 16のようなモノレポ構成では開発速度が大幅に向上する一方、マイクロサービス間連携やモバイルクライアントには不向き。

- **ポイント2:** GraphQLはBFF(Backend for Frontend)層での採用が定着し、複数クライアント(Web/モバイル)が異なるデータ形状を要求するケースで威力を発揮するが、キャッシュ戦略やN+1問題の運用コストは依然として高い。

- **ポイント3:** RESTは依然として外部公開APIやサードパーティ連携のデファクトスタンダード。OpenAPI 3.1 + JSON Schemaによる自動生成ツールチェーン(zod-to-openapi等)が成熟し、Zodバリデーションと型定義を一本化できるようになった。

- **ポイント4:** 2026年の実務トレンドは「内部通信はtRPC、外部公開はREST、複雑な集約クエリのみGraphQL」というハイブリッド構成。単一プロトコルで全てを賄うより、用途ごとに使い分ける設計判断がベストプラクティスとして定着している。

- **ポイント5:** エッジランタイム(Vercel Edge, Cloudflare Workers)との親和性がAPI設計の新たな評価軸に。tRPCやRESTの軽量ハンドラーはコールドスタートに強く、sumitsugiのようなNext.js App Routerベースの構成ではRoute Handlers + tRPCの組み合わせがレイテンシ面で有利。

### 4. serverless edge computing 2026

**エッジコンピューティング／サーバーレス 2026年トレンド**

- **エッジでのLLM推論分散:** V8 Isolateベースのランタイム(Cloudflare Workers AI等)で軽量モデルをエッジ実行するのが標準化しつつある。前の住人の物件データ検索や画像解析など、レイテンシが体感に直結する機能は中央API呼び出しからエッジ推論へ移行する価値がある。

- **コールドスタート問題の実質的解消:** V8 IsolateやWasmベースのランタイムはミリ秒単位の起動が可能になり、Lambda系の秒単位コールドスタートより低レイテンシを実現。予約物件検索やチャット機能など、レスポンス速度がUX直結の機能から段階的に移行するのが実用的。

- **Edge-Native Database(Read Replica分散):** Turso/D1/PlanetScaleのようなSQLiteベースのグローバル分散DBが普及し、読み取りをリクエスト元に最も近いリージョンから返せる。物件検索は読み取り比率が高いため、書き込みは中央、読み取りはエッジという構成がコスト・速度両面で有利。

- **Next.js 16のPartial Prerendering + Edge Runtime連携:** 静的部分をCDNエッジでキャッシュしつつ動的部分のみサーバー実行するハイブリッド構成が主流化。物件一覧の静的部分と在庫状況・価格の動的部分を分離すれば、Vercel等でのビルド・配信コストを抑えつつ体感速度を改善できる。

- **運用面の注意点:** エッジ環境はNode.js APIの一部(fsやネイティブモジュール)が使えないため、既存のNext.jsコードをEdge Runtimeに移行する際は依存関係の棚卸しが必須。全面移行より、レイテンシが効くページ単位で段階的に適用するのが現実的なアプローチ。

### 5. authentication security best practices 2026

- **パスキー標準化の加速:** FIDO2/WebAuthnベースのパスキーがパスワードの主要な代替として定着しつつあり、フィッシング耐性のある認証をデフォルトにすることでクレデンシャルスタッフィング攻撃のリスクを大幅に低減できる。

- **多要素認証の「フィッシング耐性」重視:** SMS OTPやTOTPだけでなく、デバイス証明・ハードウェアキー（YubiKeyなど）を組み合わせたフィッシング耐性MFAへの移行が求められており、認証まわりの実装では単純なOTP実装に留まらない設計が必要。

- **セッション管理とトークンの短命化:** 長期有効なセッショントークンよりも、短命アクセストークン＋リフレッシュトークンのローテーション、デバイスバインディングを組み合わせる設計がベストプラクティスになっており、漏洩時の被害範囲を最小化できる。

- **ゼロトラスト前提の継続的認証:** ログイン時点の一発認証ではなく、行動パターンやデバイス指紋を用いたリスクベース認証・継続的検証（Continuous Authentication）を組み込むことで、セッションハイジャックへの耐性を高められる。

- **AIを悪用した攻撃への対策:** ディープフェイク音声・映像を用いたソーシャルエンジニアリングやAI生成フィッシングが増加しており、本人確認プロセスに生体認証＋ライブネス検出を組み合わせるなど、AI悪用を前提としたセキュリティ設計が重要になっている。

### 6. database architecture Prisma Supabase 2026

- **エッジ最適化とコネクションプーリング:** Supabaseの`pgbouncer`統合やPrismaの`Accelerate`を使うことで、サーバーレス環境（Vercel等）でのDB接続枯渇問題を回避できる。特にNext.js 16のServer Actionsを多用する構成では必須級の対策。

- **Row Level Security (RLS) とPrisma併用の落とし穴:** SupabaseのRLSはPostgres標準機能だが、Prismaクライアント経由のアクセスは通常`service_role`キーでRLSをバイパスするため、アプリ層での権限チェックを別途実装する必要がある。認証・所有権チェックをミドルウェアやスキーマバリデーション（Zod）で二重化するのが安全。

- **スキーマ駆動 + 型安全性の一貫性:** Prisma Schemaを単一の真実源とし、`prisma generate`で型を自動生成する運用がTypeScriptプロジェクトの標準になっている。物件の`status: 'draft' | 'public'`のようなUnion型はPrisma Enumと同期させ、マイグレーション時の型不整合を防ぐべき。

- **マイグレーション運用の分離:** 開発環境は`prisma migrate dev`、本番は`prisma migrate deploy`をCI/CDパイプラインに組み込み、Supabaseのブランチ機能（Preview環境ごとのDBブランチ）と組み合わせることで、PRごとに安全にスキーマ変更を検証できる。

- **リアルタイム機能とのハイブリッド構成:** Prismaは通常のCRUDに強いが、リアルタイム通知（チャット・物件更新通知など）はSupabaseのRealtime機能（Postgres Changes）を直接使う方が効率的。ORMとネイティブ機能を用途で使い分けるハイブリッド構成が2026年のベストプラクティス。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Component Model（WASI Preview 2）の安定化により、Rustで書いたWasmモジュール間の言語非依存な連携が容易になり、フロントエンドの重い処理（画像処理・PDF生成・暗号化など）をブラウザ側にオフロードしやすくなっている。
- **ポイント2:** `wasm-bindgen`や`wasm-pack`のビルドパイプラインが成熟し、SIMD/マルチスレッド（`wasm-bindgen-rayon`）対応が標準化してきたことで、Rust製Wasmのネイティブ比パフォーマンスがさらに向上している。
- **ポイント3:** Wasmバイナリサイズの最適化（`wasm-opt`, `twiggy`によるプロファイリング）がビルドCIに組み込まれるのが一般的になり、初回ロード時間（TTI）への影響を継続的に監視できる体制が重要視されている。
- **ポイント4:** サーバーサイドでもWasmランタイム（Wasmtime, WasmEdge）がエッジコンピューティングやプラグインサンドボックス用途で採用が進んでおり、Next.jsのEdge RuntimeでRust製Wasmモジュールを使うことでコールドスタートを抑えつつ計算集約的処理を高速化できる。
- **ポイント5:** sumitsugiのような画像・PDF処理を伴う機能（物件写真の圧縮、引き継ぎ書類PDF生成）では、将来的にRust+Wasmへの切り出しがサーバー負荷軽減とレイテンシ改善の有力な選択肢になり得る。

### 8. Next.js App Router patterns 2026

- **サーバーコンポーネント優先設計:** App RouterではデフォルトでServer Componentsを使い、`'use client'`は本当にインタラクティブ性が必要な葉ノードのみに限定するのが2026年の定石。データフェッチをサーバー側に寄せることでバンドルサイズとウォーターフォールを削減できる。

- **Partial Prerendering (PPR) の実運用化:** 静的シェルを即座に返しつつ動的部分を`Suspense`でストリーミングする構成が安定してきており、`sumitsugi`の物件一覧・詳細ページのようにSEOと動的性（在庫・価格）を両立させたいユースケースに適している。

- **`use cache` ディレクティブによるキャッシュ制御の明示化:** キャッシュ戦略がファイル/関数単位で宣言的に書けるようになり、以前の`fetch`オプションや`revalidate`頼みの暗黙的挙動より予測可能になった。物件データのような更新頻度が異なるリソースを細かく制御しやすい。

- **Server Actionsの型安全な境界設計:** フォーム送信や引越し費用計算のような処理をServer Actionsに寄せつつ、Zodによる入力検証をアクション内部で必須化する運用が定着。クライアント-サーバー間の型不整合バグを防ぐため、DTO層を明示的に分離するプロジェクトが増えている。

- **ルートグループとParallel/Intercepting Routesの活用拡大:** モーダルでの物件プレビューや認証フローなど、URLを保ちつつUXを分岐させるパターン（`(..)listing/[id]`など）が一般化し、`src/app/properties/`のような一覧×詳細×モーダルの構成に適用しやすくなっている。

### 9. Vercel Edge Functions optimization 2026

- **リージョン最適化とデータ局所性:** Edge Functionsは実行リージョンをリクエスト発信地に自動マッチさせるため、DBやKVストアも同一リージョンに配置しないとレイテンシ削減効果が相殺される。Vercel KV/Postgresのリージョン設定を意識したアーキテクチャ設計が必須。

- **コールドスタート最小化のための軽量化:** Edge RuntimeはNode.js APIの一部しか使えないため、依存パッケージを絞り込みバンドルサイズを小さく保つことが実行速度に直結する。重いライブラリ（画像処理・PDF生成等）はServerless Functionsに逃がす判断が重要。

- **ストリーミングレスポンスの活用:** AI機能（チャット、レコメンド等）を実装する際はEdge FunctionsでのストリーミングSSE/ReadableStreamがTTFB改善に効く。うちのサービスでも問い合わせ対応や物件検索の逐次表示に応用余地がある。

- **キャッシュ戦略との統合:** `next: { revalidate }` やISRとEdge Middlewareを組み合わせたstale-while-revalidateパターンが標準化しつつあり、物件一覧のような更新頻度が低いページはEdgeでキャッシュしつつ、認証が絡む個人化部分だけ動的処理する分離設計が効率的。

- **観測性（Observability）の強化:** Edge実行環境はNode.jsのプロファイリングツールが使えないため、Vercelの組み込みAnalytics/Logsやトレーシング連携（OpenTelemetry対応拡大）で計測する運用が前提になってきている。ローンチ後の監視設計に組み込むべき。

### 10. TypeScript type safety patterns 2026

- **ポイント1（`satisfies` 演算子の定着）:** 型注釈で情報が失われる問題を回避しつつリテラル型を保持できるため、設定オブジェクトやルーティング定義など「形は決まっているが値は絞り込みたい」ケースで標準的な書き方になっている。

- **ポイント2（スキーマ駆動の型生成）:** Zod / Valibot などのランタイムバリデータから型を推論する「schema-first」アプローチが主流化し、APIレスポンスやフォーム入力など境界値でのランタイム検証と静的型を二重管理せずに一本化できる。

- **ポイント3（テンプレートリテラル型 + 型レベルパーサ）:** ルートパスやCSSクラス名などの文字列を型レベルで構造化・検証するパターンが増え、`src/app/` のようなファイルベースルーティングとの相性が良く、タイポによるランタイムエラーをコンパイル時に検出できる。

- **ポイント4（`unknown` ファーストの外部境界設計）:** 外部API・ユーザー入力は `any` ではなく `unknown` で受け、Zodスキーマでナローイングしてから内部型に変換する二段構えが定着し、`.claude/rules/standards.md` の「システム境界でZod検証」という方針とも合致する。

- **ポイント5（Discriminated Union によるステータス管理）:** `'draft' | 'public'` のようなユニオン型に判別プロパティを持たせ、`switch` の網羅性チェック（`never` 型での exhaustiveness check）をCIに組み込むことで、状態追加時の考慮漏れをビルド時に検出するパターンが標準になっている。
