# CTO Knowledge - 2026-07-29

## Daily Update (2026-07-29)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16ではPPRが安定版となり、静的シェルを即座に返しつつ動的部分のみStreamingで補完できる。ダッシュボードやユーザー個別化領域が多いsumitsugiの物件詳細ページでもTTFBを大幅短縮できる。

- **React Compilerによる自動メモ化:** `useMemo`/`useCallback`を手動で書かずにビルド時最適化が効くため、リスト表示（物件一覧・検索結果）のレンダリングコストを削減しつつコードの可読性も維持できる。

- **Turbopackのビルド高速化:** 開発時・本番ビルド双方でWebpack比数倍の速度改善が進んでおり、CI/CDのビルド時間短縮に直結する。`bun run build`のCI組み込みを徹底している当プロジェクトとも相性が良い。

- **キャッシュ戦略の明示化（`use cache`ディレクティブ）:** データフェッチ単位でキャッシュ境界を明示できるようになり、暗黙的なフルルートキャッシュに依存しない設計が可能。物件データのようにdraft/public状態で鮮度要件が異なるデータには特に有効。

- **画像・フォントの自動最適化強化:** `next/image`のAVIF優先配信とフォントのself-hosting自動化により、Core Web Vitals（特にLCP）改善がほぼ設定不要で得られる。Airbnb風の画像重視UIを持つsumitsugiでは効果が大きい。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** React 19以降、`loading.tsx`とSuspenseによる段階的レンダリングがApp Routerのデフォルトパターンとして定着し、TTFBとLCPの両立が容易になっている。

- **Server ActionsとRSCの統合深化:** フォーム送信やミューテーションをRSC境界内で完結させる設計が主流になり、クライアントJSバンドルの削減とAPI Routes依存の低下が進んでいる。

- **キャッシュ戦略の複雑化への対応:** `use cache`ディレクティブなどNext.js 16系の新キャッシュAPIにより、部分的な再検証（Partial Prerendering）が実運用レベルで扱いやすくなった一方、キャッシュ無効化のデバッグコストは依然として高い。

- **Edge Runtimeとの親和性:** RSCストリーミングはEdgeでの部分レンダリングと相性が良く、地理的に分散したユーザーへのTTFB改善に直結するため、sumitsugiのような物件一覧・検索系ページでは優先的に検討価値がある。

- **型安全性とのトレードオフ:** Server/Clientコンポーネント境界を跨ぐpropsのシリアライズ制約により、TypeScriptの型チェックだけでは検出できない実行時エラーが発生しやすく、境界設計にはZodなどのランタイム検証を併用すべき。

### 3. API design REST GraphQL tRPC 2026

- **統合の加速:** 2026年現在、単一プロトコルを選ぶ時代は終わり、外部公開APIはREST（安定性・キャッシュ性・ツール互換性）、内部BFFやモノレポ内通信はtRPC（型安全・ビルド時検証）、複数クライアントが異なるデータ形状を要求する場面ではGraphQLと、用途ごとに使い分けるハイブリッド構成が主流になっています。

- **tRPCの採用拡大:** Next.js 16 + TypeScriptのようなフルスタックTS環境では、スキーマ定義とコード生成を省略できるtRPCが開発速度で優位。sumitsugiのようなApp Router構成なら、Server Actions/tRPCの組み合わせでクライアント-サーバー間の型ズレをコンパイル時に検出でき、Zodバリデーションとも自然に統合できます。

- **GraphQLは「集約層」に特化:** GraphQLは全APIの代替ではなく、複数マイクロサービス・複数データソースを1クエリに集約するBFF層としての採用が定着。オーバーフェッチ削減よりも「フロントエンドが必要な形にサーバー側で整形する」用途で価値を発揮します。

- **契約駆動開発（Contract-First）の重要性:** OpenAPI/JSON SchemaやZodスキーマをSource of Truthとし、フロント・バック双方でスキーマから型・バリデーション・ドキュメントを自動生成する流れが標準化。これにより`.claude/rules/standards.md`にある「Zodスキーマによる境界検証」の方針とも整合し、API変更時の破壊的変更を早期検知できます。

- **エッジ・ストリーミング対応の必須化:** Next.jsのApp RouterやServer Componentsとの親和性から、REST/tRPCともにストリーミングレスポンス（Suspense対応）やエッジランタイムでの実行が標準要件に。物件検索や画像アップロードなど大量データを扱うsumitsugiの機能では、この点をAPI設計初期から考慮すべきです。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG(WinterTC)準拠のランタイム(Cloudflare Workers, Vercel Edge, Deno Deploy)がAPI互換性を高め、ベンダーロックインが緩和されつつある。実装時はNode.js固有APIへの依存を避け、Web標準API(fetch, Streams等)ベースで書くと移植性が上がる。

- **エッジでのステートフル処理:** Durable Objects、Cloudflare D1、PartyKitのようなエッジネイティブなデータレイヤーが成熟し、単純なキャッシュ用途を超えてセッション管理やリアルタイム同期をエッジで完結できるようになった。sumitsugiのような予約・チャット機能を持つプロダクトでは、レイテンシ削減とDB負荷分散の両面で検討価値がある。

- **AI推論のエッジシフト:** 小型LLM/量子化モデルをエッジで動かす動き(Cloudflare Workers AI等)が進み、単純な分類・要約・埋め込み生成はオリジンサーバーを介さずエッジで完結できるケースが増えている。全処理をエッジに寄せる必要はなく、レイテンシ要求とモデルサイズのトレードオフで使い分けるのが実用的。

- **コールドスタート問題の実質解消:** V8 isolateベースの起動が数ms単位まで高速化し、Lambda等の伝統的サーバーレスとの差が明確に。ただしCPU時間課金やメモリ制限は依然厳しく、重い画像処理やPDF生成(sumitsugiの契約書生成など)は従来型サーバーレス or 専用インスタンスとの併用が現実的。

- **Next.js × エッジの相性:** Next.js 16のApp RouterはEdge Runtimeとの統合が進んでいるが、Node.js API依存のライブラリ(一部の認証・PDF系ライブラリ)は非対応な場合がある点に注意。ミドルウェアはエッジ、重い処理はNode.jsランタイムという使い分けが現実的な落とし所。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への全面移行:** パスワードレス認証がデファクトスタンダードとなり、SMS/メールOTPはフィッシング耐性の低さから非推奨化が進んでいる。実装コストを考慮し、既存の前の住人/次の住人アカウントにはパスキー移行を段階的に案内する設計が現実的。

- **セッション管理とトークンローテーション:** 短命アクセストークン＋リフレッシュトークンローテーションが標準化し、盗難トークンの再利用検知（Refresh Token Reuse Detection）が必須要件になりつつある。Next.jsのミドルウェアレイヤーでセッション検証を一元化し、Cookie属性（`HttpOnly`, `Secure`, `SameSite=Strict`）を徹底する必要がある。

- **デバイスバインディングとリスクベース認証:** IPアドレスやデバイスフィンガープリントの変化を検知して追加認証を要求する適応型MFAが主流化。物件取引という金銭が絡むフローでは、決済・重要操作前のステップアップ認証を組み込むべき。

- **ゼロトラスト前提のAPI境界防御:** 認証済みでも各リクエストでの認可（RBAC/ABAC）チェックを徹底し、内部API呼び出しでも「信頼しない」設計が標準に。Zodによる入力検証と組み合わせ、認可漏れによるIDOR（Insecure Direct Object Reference）を防ぐレビュー観点が重要。

- **サプライチェーン・依存関係の認証情報保護:** npm/Bunパッケージ経由の認証情報窃取が増加傾向にあり、`bun.lock`の整合性検証とCI環境でのシークレットスコープ最小化（GitHub Actions OIDC活用）が推奨される。ハードコードされたAPIキーの排除は引き続き最優先事項。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prismaは2026年時点でRust製クエリエンジンからTypeScript/WASMベースへの移行を完了し、Supabaseのようなサーバーレス・エッジ環境でのコールドスタート時間が大幅に改善されている。sumitsugiのようなVercelデプロイ構成では、この変更によりAPI Route初回応答が体感できるレベルで速くなる。

- **ポイント2:** SupabaseのRow Level Security(RLS)とPrisma Client拡張機能(Client Extensions)を組み合わせたマルチテナント設計がデファクトスタンダード化しており、`seller`/`buyer`といった役割ごとのデータアクセス制御をDB層で強制できる。物件の`draft`/`public`ステータス制御など、UIロジックだけに頼らずDB側でも二重に守るのが2026年のベストプラクティス。

- **ポイント3:** SupabaseのPostgres上でpgvectorが標準機能として成熟し、物件検索やレコメンド（前の住人の暮らし方に近い物件提案など）にAI埋め込み検索を追加する際、別のベクターDBを導入せずPrisma経由で完結できるようになった。

- **ポイント4:** Prisma MigrateとSupabase Branching（プレビュー環境ごとのDBブランチ）の統合が進み、PRごとに独立したDBスキーマでE2Eテストを回せる体制が一般化している。現状のCI構成にこれを組み込めば、`bun run test:e2e`のデータ依存による不安定さを減らせる可能性がある。

- **ポイント5:** Supabase Realtimeを使った楽観的UI更新（例: 内見予約の空き状況をリアルタイム反映）と、Prismaのトランザクション整合性を両立させる設計パターンが定着してきた。今後、引越し費用の決済フローや予約管理を強化する際に参考になる。

### 7. WebAssembly Rust performance 2026

- **ポイント1（WASI 0.3とコンポーネントモデルの成熟）:** WASI Preview 2/コンポーネントモデルが実用段階に入り、Rustの`wit-bindgen`でWasmコンポーネント間の型安全な連携がしやすくなった。非同期I/O対応も進み、サーバーサイドWasmでの採用障壁が下がっている。
- **ポイント2（ネイティブとの性能差縮小）:** Rustコンパイラの最適化とWasm GC/SIMD拡張の普及により、計算集約ワークロード（画像処理、暗号演算等）でネイティブの80-95%程度の性能が現実的になった。フロントエンドの重い処理（PDF生成、画像編集）をWasmオフロードする選択肢が広がっている。
- **ポイント3（起動速度とコールドスタート最適化）:** WasmはコンテナやNode.jsに比べ起動が1桁速く、Wasmtime/Wasmerのcomponent instantiation最適化でエッジ関数（Cloudflare Workers等）のコールドスタートがさらに短縮。サーバーレスAPIの低レイテンシ要件に適する。
- **ポイント4（バイナリサイズとツリーシェイキング）:** `wasm-opt`やRustの`wee_alloc`代替（デフォルトアロケータの改善）により、不要なコード削減がしやすくなり、ブラウザ配信時の初回ロード負荷が軽減されている。sumitsugiのような画像・PDF処理を伴うUIでは体感速度に直結する。
- **ポイント5（開発体験とデバッグツールの充実）:** ソースマップ対応やDWARF情報を使ったブラウザDevToolsでのRustコードデバッグが実用レベルに達し、「動くが遅い」から「プロファイルして最適化する」ワークフローが組みやすくなった。

**sumitsugiへの示唆:** 現状はNext.js中心のためWasm導入の緊急性は低いが、将来的に契約書PDF生成や画像圧縮など重い処理をクライアントサイドで高速化したい場面が出れば、Rust+Wasmは検討候補になる。

### 8. Next.js App Router patterns 2026

- **App Router + Server Components標準化:** 2026年時点でNext.js App RouterはPages Routerを完全に置き換え、React Server Componentsがデフォルトの設計単位に。クライアントバンドルサイズを抑えるため「Server Componentsを基本、'use client'は末端の対話部分のみ」という境界設計が定石化している。

- **Partial Prerendering (PPR) の実用化:** 静的シェルを即座に返しつつ動的部分を`<Suspense>`でストリーミングする手法が安定版として普及し、TTFBとインタラクティブ性を両立。sumitsugiのような物件一覧・詳細ページでは、静的な物件情報とリアルタイムな空室状況を分離して配信するのに向いている。

- **Server Actionsによるフォーム/ミューテーション統一:** API Routeを個別に書かずServer Actionsで完結させる設計が主流化。ただしZodによる入力検証とCSRF対策（Next.js標準のOrigin検証に加えrevalidate戦略の明示）は引き続き必須で、標準化ドキュメント通りの境界バリデーションが重要。

- **キャッシュ戦略の明示化:** Next.js 15以降で`fetch`のデフォルトキャッシュ挙動が変わり、「明示的にキャッシュを指定する」方針が定着。`revalidateTag`/`revalidatePath`を使った細粒度の再検証が、引越し費用や物件ステータス変更のようなデータ更新頻度が高い箇所で重要になる。

- **Turbopackの本番ビルド定着:** Turbopackが`next build`のデフォルトとなり、ビルド時間が大幅短縮。CI上の`bun run build`検証コストが下がる一方、一部エッジケースのWebpack依存プラグインとの互換性は個別確認が必要。

### 9. Vercel Edge Functions optimization 2026

**Vercel Edge Functions optimization 2026**

- **ポイント1（コールドスタート最適化）:** V8 isolateベースの実行環境がさらに進化し、コールドスタートが1ms未満まで短縮されつつある。頻繁に呼ばれないAPIルートでもレイテンシ懸念が実質解消され、SSRのミドルウェア処理をEdgeに寄せる判断がしやすくなっている。

- **ポイント2（データアクセスのローカリティ）:** Edge Config・Vercel KVなどのグローバル分散ストアと組み合わせることで、DB往復を避けたリードヘビーな処理（フィーチャーフラグ、A/Bテスト判定、認証トークン検証）をEdge側で完結できる。sumitsugiのような物件検索・ステータス判定処理は、DBクエリを伴わない軽量判定であればEdge化の候補になる。

- **ポイント3（Node.js API互換性の拡大）:** Edge RuntimeでサポートされるNode.js APIが増え、以前はNode Runtime必須だったライブラリ（一部のcrypto処理やstream処理）もEdgeで動くケースが増加。ただしPrismaなど一部ORMは依然非対応が多く、DBアクセス層は引き続きNode Runtime（Serverless Functions）に残す設計が現実的。

- **ポイント4（コスト最適化）:** Edge Functionsの実行時間課金モデルが精緻化され、短時間・高頻度の処理（リダイレクト、ヘッダー付与、A/Bテスト振り分け）はEdgeに寄せることで従来のServerless Functionsよりコスト効率が上がるケースが増えている。認証チェックのミドルウェア化が典型例。

- **ポイント5（Observability統合）:** Vercel純正のEdge Observability（トレーシング・ログ）がGA相当に成熟し、分散実行環境でのデバッグ難易度が下がった。Edge移行の障壁だった「本番での可視性不足」が緩和されたため、段階的にEdge化を進めやすい状況になっている。

### 10. TypeScript type safety patterns 2026

- **型推論の強化とconst型パラメータ:** TypeScript 5.x以降の`const`型パラメータやsatisfies演算子の活用が定着し、明示的な型注釈を減らしつつ厳密な型推論を実現するパターンが主流になっている。sumitsugiのようなZodバリデーション中心の設計では、スキーマから型を推論する`z.infer`パターンとの相性が良い。

- **Branded Types(公称型)による意味的安全性:** `string`や`number`のプリミティブ型に意味を持たせるBranded Typesが、IDの取り違えなどのバグ防止策として定着しつつある。例えば`PropertyId`と`UserId`を別型にすることで、実行時コストゼロでコンパイル時に混同を防げる。

- **Discriminated Unionの徹底活用:** `status: 'draft' | 'public'`のようなUnion型を判別可能な形で設計し、`switch`文の網羅性チェック(`never`型での担保)と組み合わせることで、状態追加時の実装漏れをビルド時に検出できる。sumitsugiの物件ステータス管理にも直結する実用パターン。

- **エンドツーエンドの型安全性(tRPC的アプローチ):** APIレイヤーからフロントエンドまで型を共有し、手動同期を排除する潮流が加速している。Next.js App RouterのServer Actionsと組み合わせることで、REST APIの型ズレを構造的に防げる。

- **Zodなどのランタイムバリデーションとの統合:** 「境界での検証」の原則が浸透し、コンパイル時の型だけでなくランタイムでも型を保証する二重の安全網が標準化しつつある。外部入力(フォーム、API応答)は必ずZodでパースしてから型付きデータとして扱う設計が推奨される。
