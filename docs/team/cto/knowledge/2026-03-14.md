# CTO Knowledge - 2026-03-14

## Daily Update (2026-03-14)

### 1. Next.js performance optimization 2026

- **React Server Components の徹底活用:** RSCをデフォルトとし、クライアントコンポーネントは状態・インタラクション必須箇所のみに限定する。バンドルサイズを大幅削減でき、TTFBが顕著に改善する。

- **PPR（Partial Prerendering）の本番導入:** Next.js 15以降で安定化したPPRにより、静的シェルを即時配信しつつ動的部分をストリーミングする。Suspense境界の設計がパフォーマンスを左右する。

- **`use cache` ディレクティブによる細粒度キャッシュ:** 関数・コンポーネント単位でキャッシュポリシーを宣言できる新APIにより、過剰な再検証を排除。`revalidate`戦略よりも意図が明確になる。

- **画像・フォントの最適化は next/image・next/font に全委譲:** 独自実装を避け、フレームワーク組み込みの最適化（AVIF自動変換、CLS防止、フォントサブセット化）を最大限に活用する。

- **Bundle Analyzer + Turbopack でのビルド高速化:** `@next/bundle-analyzer` で肥大化したクライアントバンドルを定期的に計測し、`next.config` の `experimental.turbo` で開発ビルドを高速化する。本番はまだwebpackが安定。

### 2. React Server Components streaming 2026

- **ポイント1: Suspense境界との統合成熟** React 19以降、Server ComponentsとSuspenseの組み合わせによるストリーミングが実用段階に達し、`loading.tsx`だけでなく細粒度のSuspense境界設計が本番品質のUXを左右する。

- **ポイント2: PPR（Partial Prerendering）の普及** Next.js 15+でPPRが安定版に移行し、静的シェルを即座に返しつつ動的部分をストリームする手法が標準パターンになりつつある。キャッシュ戦略の設計がパフォーマンスのボトルネックに直結する。

- **ポイント3: `use()` フックによるデータフェッチの変化** `use(Promise)`パターンにより、クライアントコンポーネントでもサーバーからのPromiseをSuspenseと組み合わせて扱えるようになり、Client/Server境界をまたぐデータフローの設計が簡潔化されている。

- **ポイント4: Edge Runtimeとの相性問題** ストリーミングはNode.jsランタイムで最も安定しており、EdgeではReadableStream対応の制限が依然存在する。インフラ選定時にVercel/CloudflareのEdge制約を事前に確認すること。

- **ポイント5: バンドルサイズへの影響の再評価** Server Componentsによりクライアントバンドルの削減効果が定量的に計測できるようになったが、Server→Client境界に`'use client'`を安易に追加するとその恩恵を損なう。コンポーネントツリーの境界設計レビューを開発プロセスに組み込むべき。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年時点でtRPCはNext.js/Remixエコシステムで事実上の標準に近づいており、TypeScriptのend-to-end型推論によりスキーマ定義なしにクライアント・サーバー間の契約を保証できる。

- **GraphQLの「適材適所」への回帰:** マイクロサービス間のBFF（Backend for Frontend）やモバイルクライアントでは依然強力だが、小〜中規模のアプリでオーバーヘッドが問題視され、「GraphQL疲れ」からRESTやtRPCへ回帰するプロジェクトが増加している。

- **REST + OpenAPI 3.1の堅牢化:** 外部公開APIではRESTが引き続き主流で、OpenAPI 3.1 + Zodスキーマによるコード生成（`zod-openapi`、`@anatine/zod-openapi`）が開発体験を大幅に改善し、型安全なRESTクライアントを自動生成できる。

- **Server ActionsとRPCパターンの融合:** Next.js 15以降のServer ActionsはtRPCに近いRPCセマンティクスをフレームワーク層で提供しており、小規模プロジェクトでは独立したAPIレイヤーを省略するアーキテクチャが現実的な選択肢になっている。

- **選定基準の明確化:** 2026年の実践的な判断軸は「外部公開ならREST+OpenAPI、内部フルスタックならtRPC、複雑なデータグラフや複数クライアントならGraphQL」。技術の優劣より**チームの習熟度とユースケースのフィット**が最重要。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジの標準ランタイムに:** 2026年時点でCloudflare Workers・Fastly Compute@Edgeを中心にWasmが主流化。コンテナ起動の寒冷起動問題を解消し、多言語対応とセキュリティサンドボックスを両立している。

- **エッジDBとの統合が加速:** PlanetScale、Turso（libSQL）、Cloudflare D1など、エッジに近いSQLiteベースのDBが普及。「エッジで読み書き完結」するアーキテクチャが現実的な選択肢になった。

- **AIインファレンスのエッジ移行:** 小型LLM（<7B）のエッジ実行が実用レベルに到達。Cloudflare AI、Vercel AI SDKのEdge Runtimeがストリーミング推論をサポートし、レイテンシとコスト削減を実現。

- **観測可能性（Observability）がボトルネック:** 分散エッジ環境でのトレーシング・ログ収集は依然として課題。OpenTelemetryのエッジ対応が進むが、コールドスタート時のサンプリング損失など運用上の落とし穴に注意が必要。

- **地政学的分散とデータ主権への対応:** GDPR・各国データローカライゼーション規制により、「どのリージョンで処理するか」をコードレベルで制御する設計が必須。エッジは地理的コントロールの手段として戦略的価値が高まっている。

### 5. authentication security best practices 2026

- **パスキー（Passkey）の標準化:** FIDO2/WebAuthn ベースのパスキーが2026年のデファクトスタンダードに。パスワードレス認証はフィッシング耐性が高く、Next.jsでは`@simplewebauthn`等のライブラリで実装可能。

- **トークン設計の見直し（短命アクセストークン + ローテーティングリフレッシュトークン）:** アクセストークンは15分以内、リフレッシュトークンは使用のたびに再発行するローテーション方式が必須。JWTの`exp`と`jti`クレームを組み合わせたリプレイ攻撃対策が標準化。

- **デバイスバインディング認証:** セッションをデバイスフィンガープリントやIPに紐付け、異常検知（Impossible Travel等）を組み込むゼロトラストアプローチが普及。Next.js Middlewareで実装しやすい。

- **MFAの強制とOTPの段階的廃止:** SMS-OTPはSIMスワップ攻撃のリスクから非推奨化が加速。TOTP（Google Authenticator）かハードウェアキー（YubiKey）への移行を促すUXが求められる。

- **サプライチェーン攻撃対策（認証ライブラリの監査）:** `next-auth`等の依存ライブラリのSBOM（Software Bill of Materials）管理と`bun audit`の定期実行が必須。認証フローに関わるパッケージは特にバージョンピン留めを徹底。

### 6. database architecture Prisma Supabase 2026

- **PrismaとSupabaseの統合成熟:** Prisma 6.x系でSupabaseのConnection Pooling（PgBouncer/Supabase Pooler）との組み合わせが標準化され、サーバーレス環境でのコネクション枯渇問題がほぼ解消された。`DATABASE_URL`にPooler URL、`DIRECT_URL`に直接接続を使い分けるパターンが定着。

- **Row Level Security（RLS）との責務分離:** SupabaseのRLSをデータ層のセキュリティとして活用し、Prismaをアプリ層のORM（型安全なクエリ）として分離する設計が主流。ただしPrismaはRLSを透過しないため、管理系処理はService Role Keyを使うトレードオフを意識する必要がある。

- **Prisma Pulse / Accelerateの台頭:** PrismaのAccelerate（グローバルキャッシュ＋接続プール）とPulse（リアルタイムDB変更検知）がSupabase Realtimeと競合・補完関係に。Supabase内完結ならRealtime、マルチクラウド・エッジ展開ならAccelerateが選択肢。

- **型安全なマイグレーション管理:** `prisma migrate dev`によるスキーマ駆動開発が、Supabaseの手動SQL管理より型安全性で優位。一方、Supabase Storageや認証テーブルはPrismaスキーマ外で管理されるため、`prisma db pull`で定期的に同期確認するワークフローが重要。

- **Serverless/Edgeでの接続戦略:** Next.js App Router＋Edge RuntimeではPrismaフルランタイムが動作しないため、`@prisma/adapter-neon`や`drizzle-orm`への移行も選択肢に。2026年現在、Next.js＋Supabase構成では「Node.js Runtimeで統一してPrisma使用」か「Edge対応のDrizzle移行」かを明確にアーキテクチャ決定することが重要。

### 7. WebAssembly Rust performance 2026

- **Component Model の成熟:** WASIp2（WASI Preview 2）とComponent Modelが2025年末に安定化し、RustからWasmコンポーネントを型安全にコンポーズできるエコシステムが実用段階に入った。`cargo component`ツールチェーンが標準化されつつある。

- **SIMD・スレッド対応の本格化:** Wasm SIMD128とShared Memoryが主要ブラウザ・ランタイムで安定し、Rustの`std::simd`やRayonとの組み合わせで、ネイティブの70〜90%のスループットを達成するケースが増えている。

- **Wasmtime／WasmEdge のサーバーサイド高速化:** AOTコンパイルとPGO（Profile-Guided Optimization）の組み合わせにより、Rustで書いたWasmのコールドスタートが1ms以下に到達。エッジ・FaaS環境でのRust+Wasmが現実的な選択肢になった。

- **メモリ管理のトレードオフ認識:** RustのゼロコストアブストラクションはWasm線形メモリ上でも有効だが、JSホストとのデータ受け渡し（`wasm-bindgen`経由のシリアライズ）がボトルネックになりやすい。`SharedArrayBuffer`や`externref`活用で往復コストを削減する設計が重要。

- **ツールチェーンの統合成熟:** `wasm-pack`から`cargo component` + `wit-bindgen`への移行が加速。Rustのビルドパイプラインにwasm-optの最適化を組み込むことで、バイナリサイズを30〜50%削減しつつ実行速度を維持できる。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの設計:** 2026年時点でApp Routerの主流はServer Componentsをデフォルトとし、`'use client'`は最小限の葉コンポーネントにのみ適用するパターンが定着。データフェッチはサーバー側で完結させ、クライアントバンドルを極限まで削減する。

- **Partial Prerendering (PPR) の実用化:** Next.js 15以降でPPRが安定し、静的シェルと動的ストリーミングを同一ルートで混在させるハイブリッド戦略が標準化。`<Suspense>`境界の設計がパフォーマンスチューニングの核心になっている。

- **Server Actions によるミューテーション統一:** フォーム送信・データ変更をServer Actionsに集約し、APIルートを廃止するプロジェクトが増加。`revalidatePath`/`revalidateTag`との組み合わせでキャッシュ制御も宣言的に記述できる。

- **parallel routes / intercepting routes の本格活用:** モーダルやサイドパネルをURLに紐づける`@slot`パターンが普及。共有レイアウトを壊さずにUI状態をディープリンク可能にする設計が複雑なSPAの代替として評価されている。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15で導入された`use cache`により、関数・コンポーネント単位でキャッシュ戦略を宣言的に指定可能に。従来の`fetch`オプションよりも柔軟で、DBクエリ結果のキャッシュも統一的に扱える。

### 9. Vercel Edge Functions optimization 2026

- **Edge RuntimeでのCold Start排除:** 2026年時点でVercel Edge Functionsは従来のServerless FunctionsよりもCold Startが実質ゼロに近く、V8 Isolateベースの実行モデルにより初回レスポンスも安定して低レイテンシを実現している。

- **Fluid Computeによる動的スケーリング:** Vercelが導入したFluid Computeモデルにより、リクエスト単位での課金とCPUの効率的な共有が可能になり、バースト的なトラフィックでもコールドスタートなしに対応できるようになった。

- **Edge ConfigとKV Storageの組み合わせ活用:** Feature flagや設定値をEdge Configで超低レイテンシ読み取りし、動的データはVercel KV（Redis）で扱うパターンが定番化しており、データベースへのラウンドトリップを最小化できる。

- **Runtime制約の理解が依然重要:** Edge RuntimeはNode.js APIの一部（`fs`、`child_process`等）が使えないため、Next.js App RouterでEdge対応コンポーネントを設計する際は依存ライブラリのEdge互換性を事前に`bun run build`で検証することが必須。

- **地理的分散とISR/PPRの連携:** Partial Pre-rendering（PPR）とEdge Functionsを組み合わせることで、静的シェルをCDNエッジから配信しつつ動的部分のみEdgeで補完するハイブリッドアーキテクチャが成熟しており、TTFB（Time To First Byte）の大幅な改善が期待できる。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly __brand: 'UserId' }` のようなブランド型が標準的になり、プリミティブ型の混同バグをコンパイル時に防ぐ手法が広まっている。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` が主流化し、型推論を保持しつつ型チェックを行えるため、`as` によるキャストを避けた安全なコードが書けるようになっている。

- **Zod + tRPC による Runtime/Compile-time の統合:** スキーマ定義を単一ソースとしてZodで管理し、tRPCやValibot経由でフロントエンド・バックエンド双方の型を自動導出するパターンが定着している。

- **`noUncheckedIndexedAccess` の標準化:** 配列・オブジェクトアクセス時に `T | undefined` を返す厳格フラグが多くのプロジェクトで有効化され、実行時エラーの主要原因であるインデックスアクセスの安全性が向上している。

- **Template Literal Types による DSL 型付け:** URLパターン、イベント名、CSSクラスなどを `type Route = \`/users/\${string}\`` で型付けする手法が成熟し、文字列ベースAPIの安全性が大幅に改善されている。
