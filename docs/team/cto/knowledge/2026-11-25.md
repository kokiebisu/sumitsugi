# CTO Knowledge - 2026-11-25

## Daily Update (2026-11-25)

### 1. Next.js performance optimization 2026

- **Turbopackのデフォルト化と高速ビルド:** Next.js 16ではTurbopackが本番ビルドでも標準採用され、大規模プロジェクトでのビルド時間が大幅短縮。CIパイプラインの待ち時間削減に直結するため、moduleやchunk分割の設定を見直す価値がある。

- **Partial Prerendering (PPR) の本格運用:** 静的シェルと動的コンテンツを1ページ内で共存させることで、TTFBを維持しつつ個人化コンテンツを配信可能。物件詳細ページのように「静的な物件情報＋動的な在庫状況」が混在する構成に特に有効。

- **React Server Components前提のデータフェッチ最適化:** クライアントへのJS転送量を減らすため、`use cache`ディレクティブやセグメント単位のキャッシュ戦略が重要に。不要な`'use client'`境界を減らし、Server Component側でデータ整形を完結させることでハイドレーションコストを削減できる。

- **画像・フォントの自動最適化の深化:** `next/image`のAVIF優先配信やレイアウトシフト防止策が強化されており、物件写真中心のサービスではLCP改善に直結。フォントのサブセット化・self-hostingもデフォルト挙動に近づいている。

- **Edge/Node runtimeの選択的使い分け:** 認証やDB直結の処理はNode runtime、軽量な表示ロジックはEdge runtimeに振り分けることで、レイテンシとコールドスタートのバランスを最適化する設計が一般化してきている。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPartial Prerendering（PPR）が安定版となり、静的シェルを即時配信しつつ動的部分のみをストリーミングするパターンが標準化。sumitsugiの物件詳細ページのような「静的な外枠+動的な空室状況」構成に適用すると、TTFBを大幅短縮できる。
- **ポイント2:** Server ComponentsとSuspenseの組み合わせによる段階的ストリーミングが、一覧ページのスケルトンUI実装をシンプル化している。`loading.tsx`やネストした`<Suspense>`境界を物件カードごとに切ることで、1件の画像読み込み遅延が全体をブロックしない設計が標準パターンになっている。
- **ポイント3:** Server Actionsのストリーミングレスポンス対応が進み、フォーム送信後の即時フィードバック（楽観的UI更新）がRSCの標準機能内で実現可能に。問い合わせフォームや申込フローのUX改善に直結する。
- **ポイント4:** キャッシュ戦略の複雑さがRSCストリーミング運用の最大のボトルネック。`unstable_cache`やタグベース再検証の設計ミスがビルド後の意図しない再検証・過剰リクエストを招くため、`'draft'|'public'`のようなステータス切り替えを含むページでは再検証タグの命名規則を事前に固めておくべき。
- **ポイント5:** Edge Runtimeとの組み合わせでストリーミングのレイテンシ改善が進むが、BunランタイムでのNext.js 16 RSCストリーミングは互換性検証がまだ発展途上。本番投入前に`bun run build`後の実機ストリーミング挙動を必ず確認する運用にすべき。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1: tRPCとBFFパターンの定着** フルスタックTypeScriptプロジェクト（sumitsugiのようなNext.js App Router構成）では、tRPCがフロントエンド/バックエンド間の型安全性を保証する選択肢として定着しており、スキーマ重複やAPIドキュメント同期の手間を削減できる。

- **ポイント2: GraphQLはBFF/集約層に特化** GraphQLは複数データソースの集約やモバイル向け柔軟なクエリが必要な場面に限定利用される傾向が強まり、シンプルなCRUD中心のプロダクトではオーバーエンジニアリングになりやすい。

- **ポイント3: RESTはシンプルさと公開APIで優位** 外部公開APIや決済・物件情報連携など第三者統合が前提のエンドポイントでは、学習コストが低くキャッシュ戦略が成熟しているRESTが依然として安全な選択。

- **ポイント4: Zodスキーマの一元化が鍵** tRPC/REST問わず、Zodで入出力スキーマを定義し、クライアント型・バリデーション・OpenAPI生成を一元化する構成が標準化しつつあり、本プロジェクトの「システム境界でZod使用」という方針とも合致する。

- **ポイント5: エッジ・サーバーレス前提の設計** Next.js 16のApp Router + Server Actionsの普及で、従来のAPI層を薄くし、サーバーアクション経由でDBアクセスする設計が増えている。ただし認証・CSRF対策を各アクションで個別に担保する必要があり、セキュリティレビューの対象が分散する点に注意が必要。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** Cloudflare Workers、Deno Deploy、Vercel Edge FunctionsがWinterCG仕様（Web標準API）に収束し、ベンダーロックインが減少。コールドスタートもV8 isolateベースでミリ秒単位まで短縮されている。

- **エッジでのステートフル処理:** Durable Objects、Cloudflare D1、PartyKitのようなプリミティブにより、従来RDBMSが必要だったセッション管理やリアルタイム協調処理もエッジで完結できるようになった。レイテンシクリティカルな機能はエッジに移す判断基準になる。

- **AI推論のエッジシフト:** 軽量LLM（量子化モデル、SLM）がエッジで推論可能になり、ユーザーに近い場所でパーソナライズやモデレーションを実行するパターンが増加。重い生成タスクは中央集権的なGPUクラスタに残す「ハイブリッド推論」が実用的な設計。

- **コスト構造の変化:** リクエスト課金からCPU時間課金への移行が進み、I/O待ちの多いワークロード（APIプロキシ、BFF）はエッジで極めて低コストに運用可能。ただし計算集約的な処理をエッジに持ち込むとコストが跳ねるため、ワークロード分類が重要。

- **Next.jsとの統合強化:** Next.js 16のPartial Prerenderingやedge runtimeサポートにより、静的配信とエッジでの動的処理を同一ルート内で混在させやすくなった。sumitsugiのようなNext.jsアプリでも、物件検索や認証チェックなど低レイテンシ処理をedge middlewareに切り出す余地がある。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証（WebAuthn/Passkeys）が業界標準となり、フィッシング耐性のある認証がデフォルトに。従来のパスワード+SMS OTPは脆弱性が指摘され続けており、新規実装では最初からパスキーを第一選択とすべき。

- **セッション管理とトークンの短命化:** JWTやセッショントークンは有効期限を短く設定し、リフレッシュトークンのローテーション（refresh token rotation）を必須化。トークン漏洩時の被害範囲を最小化する設計が重視されている。

- **デバイスバインディングとリスクベース認証:** IPアドレス・デバイスフィンガープリント・行動パターンを組み合わせたリスクベース認証（adaptive authentication）が標準化し、異常なログイン試行を自動検知してMFAを追加要求する仕組みが重要。

- **Zero Trust前提のAPI設計:** 認証後も「信頼しない」前提で、各APIリクエストごとに認可チェック（RBAC/ABAC）を行う設計が必須。sumitsugiのような個人情報（物件・引き継ぎ情報）を扱うプラットフォームでは特に重要。

- **Supabase Auth等のBaaS活用とセキュリティ監査の自動化:** 自前実装よりマネージドの認証基盤（Supabase Auth, Auth0等）を使い、CI/CDパイプラインにセキュリティスキャン（依存関係の脆弱性チェック、OWASP準拠チェック）を組み込むことで、ヒューマンエラーによる認証バグを減らす。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はSupabaseのPgBouncer経由のコネクションプーリングと相性が改善され、Edge環境（Vercel Edge Functions等）でもPrisma Accelerateを使わずにDirect Connection + pgbouncer=trueで安定運用できるようになった。
- **ポイント2:** SupabaseのRow Level Security（RLS）とPrismaのスキーマ管理を併用する場合、マイグレーションはPrisma Migrateで一元管理しつつ、RLSポリシーはSQLファイルで別管理するハイブリッド構成が2026年のベストプラクティスとして定着している。
- **ポイント3:** Prisma AccelerateによるグローバルキャッシュとSupabaseのリードレプリカを組み合わせることで、物件検索のようなread-heavyなクエリのレイテンシを大幅削減できるが、キャッシュ無効化のタイミング設計（公開/非公開ステータス変更時など）が重要になる。
- **ポイント4:** SupabaseのRealtime機能とPrismaの型安全なクエリを組み合わせる際、Prismaはあくまる書き込み・バッチ処理に使い、リアルタイム通知（内見予約の即時反映等）はSupabase Clientを直接使う「用途分離」パターンが推奨されている。
- **ポイント5:** 本サービスのようなdraft/publicステータスを持つスキーマでは、Prismaのenum変更時に型不整合が起きやすいため、CLAUDE.mdにもある通り変更前に全usageをgrepする運用がSupabase側のRLSポリシー更新にも波及することに注意が必要。

### 7. WebAssembly Rust performance 2026

- **ネイティブ比90%超の実行効率:** 2026年にはWasm GC提案とcomponent modelが主要ランタイム（Wasmtime, V8）で安定化し、RustコンパイルのWasmバイナリがネイティブコードの90%以上の性能を達成するケースが増えている。Next.jsのSSR内で重い画像処理やPDF生成（本プロジェクトの契約書生成機能）をWasm化することで、Node.js単体より数倍高速化できる余地がある。
- **バイナリサイズ最適化がデフォルト化:** `wasm-opt`やLTO、`wee_alloc`代替の軽量アロケータが標準ツールチェインに統合され、数十KB〜数百KB級のバイナリが一般的になった。モバイル回線でのローンチを控える本プロジェクトでは、フロントエンド配信コストを抑える上で有効。
- **Edge Runtime対応の成熟:** Vercel EdgeやCloudflare WorkersがWasmモジュールのコールドスタートを1ms未満に短縮しており、Next.js 16のEdge Middlewareと組み合わせることで、物件検索のフィルタリングロジックなど計算負荷の高い処理をエッジで実行できる。
- **TypeScriptとの型安全な連携強化:** `wasm-bindgen`と`tsify`の組み合わせでRust側の型定義がTypeScriptに自動生成されるようになり、Zodスキーマとの境界検証も容易になった。システム境界でのバリデーションを重視する本プロジェクトの方針（standards.md）と相性が良い。
- **並行処理の実用化:** WasmのSIMDとthreads提案がブラウザ全体で安定サポートされ、画像圧縮や住宅データの大量CSVインポートなど、バッチ処理をブラウザ上でマルチスレッド実行できるようになった点が開発生産性に直結する。

### 8. Next.js App Router patterns 2026

**Next.js App Router patterns 2026 — CTO視点**

- **ポイント1（Partial Prerendering の本格採用）:** PPRが安定版となり、静的シェル＋動的コンテンツのストリーミングが標準パターンに。物件一覧ページのように「レイアウトは静的、価格や空き状況はリアルタイム」という構成に最適で、sumitsugiのproperties/一覧でもTTFB改善に直結する。
- **ポイント2（Server Actions + "use cache" の併用）:** データ取得とミューテーションを`use cache`ディレクティブで明示的にキャッシュ制御する設計が定着。引越し費用の見積もりや物件ステータス更新など、再検証タイミングが重要な処理では`revalidateTag`との組み合わせが必須。
- **ポイント3（Turbopackのデフォルト化）:** Turbopackが`next build`のデフォルトになり、ビルド時間が大幅短縮。CIのビルド検証（`bun run build`）のフィードバックループが速くなる分、型エラーの早期検出にも依存しやすくなる — CLAUDE.mdのBuild Integrity原則がより活きる。
- **ポイント4（Parallel/Intercepting Routesでのモーダルパターン成熟）:** 物件詳細のモーダル表示や認証フロー（ログイン/サインアップ）をURL駆動で実装する設計が標準化。ブラウザ履歴・ディープリンク対応が自然に得られるため、account/配下のUXに適用余地が大きい。
- **ポイント5（Server Component境界でのエラーハンドリング強化）:** `error.tsx`/`not-found.tsx`の粒度をルートセグメント単位で細かく設計する運用が定着。決済や引き継ぎフローなど多段階プロセスでは、セグメントごとの障害分離がユーザー体験と運用保守性の両方に効く。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Runtimeのコールドスタート最適化が進み、V8 isolateの起動時間がミリ秒単位まで短縮されているため、レイテンシクリティカルなAPI（認証・物件検索など）はEdge Functionsへの移行を優先すべき。
- **ポイント2:** Vercel Fluid Computeの普及により、Edge/ServerlessでのI/Oバウンド処理（DB問い合わせ、画像変換）がインスタンス間で効率的に多重化されるため、同時実行数あたりのコストを大幅に下げられる。
- **ポイント3:** Edge Config / Edge Middlewareを使ったA/Bテストやフィーチャーフラグの配信がグローバルCDNレベルで完結するようになり、オリジンへのラウンドトリップなしでUI分岐（例: 公開/非公開物件の表示切替）を高速に行える。
- **ポイント4:** Next.js 16のPartial Prerenderingとの組み合わせで、静的シェルをEdgeでキャッシュしつつ動的部分のみストリーミングする構成が標準化され、物件一覧ページなどのTTFBを大きく改善できる。
- **ポイント5:** Edge環境でのNode.js API互換性が拡大している一方、依然としてファイルシステムや一部のネイティブモジュールは非対応のため、Edge/Node runtimeの使い分けをルート単位で明示的に設計する必要がある。

### 10. TypeScript type safety patterns 2026

- **ポイント1（型のみインポートとisolatedModules強制）:** TS 5.x以降`verbatimModuleSyntax`が標準化し、`import type`の明示が必須に近づいている。ビルド高速化とツリーシェイキングの両立のため、2026年のプロジェクトはこれをlintルールで強制するのが定石。
- **ポイント2（Zodなどランタイムスキーマとの型統合）:** コンパイル時の型だけでは外部入力（API/フォーム）を保証できないため、Zod/Valibotでスキーマを定義し`z.infer`で型を生成する「スキーマ・ファースト」設計が主流。本プロジェクトでも境界検証にZodを使う方針は時流に合っている。
- **ポイント3（Discriminated UnionとExhaustiveness Check）:** `'draft' | 'public'`のようなステータス管理は、switch文で`never`型を使った網羅性チェックを徹底することで、新しい値追加時の漏れをコンパイルエラーで検出できる。型を増やす際は全使用箇所をgrepするルールと組み合わせると安全性が倍増する。
- **ポイント4（TypeScript Native実行基盤の普及）:** Go移植によるコンパイラ高速化（tsc→native）が2026年にかけて実運用段階に入り、大規模モノレポでの型チェック時間が大幅短縮。CI時間短縮の観点でビルド検証ステップに組み込む価値が高い。
- **ポイント5（テンプレートリテラル型とBranded Typeの実務活用）:** IDやステータス文字列を単純な`string`で扱わず、Branded Type（`type UserId = string & { __brand: 'UserId' }`）で区別することで、不正な値の混入をコンパイル時に防ぐパターンが浸透。認証・決済など機密性の高いドメインでの採用が増えている。
