# CTO Knowledge - 2026-07-17

## Daily Update (2026-07-17)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 15以降で導入されたPPRが2026年にはデファクトスタンダードとなり、静的シェルと動的コンテンツを1つのレスポンスでストリーミングできるため、ダッシュボードやEC商品ページのようなハイブリッドUIでもTTFBを大幅に短縮できる。sumitsugiの物件詳細ページ（静的な物件情報＋動的な空室状況）にも適用余地がある。

- **React Compiler + Server Actionsの組み合わせ:** React CompilerがuseMemo/useCallbackの手動最適化を不要にし、Server Actionsと組み合わせることでクライアントバンドルサイズが削減される。フォーム送信（問い合わせ・申込フロー）はServer Actions化することでJS転送量を抑え、Core Web Vitals（特にINP）が改善する。

- **Cache Componentsによる粒度制御:** `use cache`ディレクティブとCache Componentsにより、ページ単位ではなくコンポーネント単位でキャッシュ戦略を指定できるようになった。物件一覧のような頻繁に更新されるデータと、会社概要のような静的データを同一ページ内で異なるキャッシュポリシーで扱えるため、不要な再検証コストを削減できる。

- **画像・フォント最適化のエッジシフト:** `next/image`のエッジ最適化とVariable Fontsの活用が標準化し、LCP改善の主要因になっている。物件写真が多いsumitsugiのようなプロダクトでは、AVIF/WebP自動変換とpriorityヒントの適切な設定がLCPスコアに直結する。

- **Turbopackの安定版移行によるビルド高速化:** 2026年時点でTurbopackがdev/build両方でデフォルト化され、大規模モノレポでもHMRとプロダクションビルドが数倍高速化。開発サイクルの短縮はリリース頻度に直結するため、CI時間の短縮にも寄与する。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** Next.js 16ではRSCペイロードのストリーミングとPartial Prerenderingが統合され、静的シェルを即座に返しつつ動的部分を`Suspense`境界ごとに逐次ストリームできる。初期表示速度（TTFB/LCP）を犠牲にせず動的データを扱えるため、物件一覧のような検索結果ページで特に有効。

- **Server ActionsとRSCの境界設計:** ミューテーション処理をServer Actionsに寄せ、Client Componentは「操作トリガー」に徹する設計が主流化。sumitsugiの物件公開・お気に入り登録などの操作はServer Actionsで実装し、クライアントバンドルを最小化すべき。

- **選択的ハイドレーション（Selective Hydration）:** ページ全体を一括ハイドレートせず、ユーザー操作に応じて必要なコンポーネントから優先的にハイドレートする仕組みが成熟。認証状態を扱う`auth-context.tsx`のようなClient Componentは、ページ下部でも操作されるまでハイドレーション遅延が可能。

- **キャッシュ戦略の複雑化への対応:** `fetch`のデフォルトキャッシュ挙動が変更され続けており、`revalidateTag`/`revalidatePath`を明示的に使うベストプラクティスが定着。物件ステータス（`draft`/`public`）の切り替えなど即時反映が必要な箇所では、キャッシュ無効化を必ず明示的に書くべき。

- **Streaming中のエラーバウンダリ設計:** `Suspense`と`error.tsx`の組み合わせで、部分的なストリーミング失敗が全体のページ崩壊に繋がらない設計が必須になっている。外部API（決済・法務関連の外部サービス連携時など）呼び出しを含むコンポーネントは個別の境界で隔離することが推奨される。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPC vs REST/GraphQL）:** Next.js + TypeScriptモノレポ構成のsumitsugiのようなプロジェクトでは、tRPCはスキーマ定義とコード生成が不要でエンドツーエンドの型安全性を得られるため、社内API・BFF層に最適。ただし外部公開APIや多言語クライアントが必要な場合はOpenAPI(REST)の方が相互運用性で有利。
- **ポイント2（GraphQLの用途縮小と特化）:** GraphQLは「何でも屋」から「複雑な集約クエリが必要な特定ドメイン」向けに用途が絞られてきている。物件検索・フィルタリングのような多条件クエリがある場合は検討価値があるが、シンプルなCRUD中心の現状規模ではオーバーエンジニアリングになりやすい。
- **ポイント3（AIエージェント消費を前提にしたAPI設計）:** 2026年はLLMエージェント（Claude等）がAPIを直接呼び出すケースが急増しており、関数呼び出し用のスキーマ（JSON Schema/Zod）を明確に定義しておくことがAPI設計の新たな要件になっている。Zodスキーマをそのまま型検証とツール定義の両方に流用できる設計が効率的。
- **ポイント4（Server Actions とAPI層の境界）:** Next.js App RouterのServer Actionsが単純なミューテーションを吸収しつつあり、「本当にAPIエンドポイントが必要か」を都度問い直す価値がある。sumitsugiでも物件登録・引き継ぎフローなど内部完結する操作はServer Actions、外部連携（決済・地図API等）が絡む部分のみ明示的なAPI層、と使い分けるのが妥当。
- **ポイント5（エッジ・レイテンシ最適化）:** APIをVercel Edge/Cloudflare Workersなどエッジ環境で動かす流れが定着しつつあり、DB接続をエッジ対応ドライバー（例: Prisma Accelerate, PlanetScale等）に揃えることが2026年のパフォーマンス設計の前提になっている。

### 4. serverless edge computing 2026

- **エッジでのAI推論標準化:** 2026年時点でCloudflare WorkersやVercel EdgeでのLLM推論・軽量モデル実行が一般化し、レイテンシ要件の厳しいUX（住所検索・チャット応答など）はエッジ層で完結させるのが定石になっている。

- **コールドスタート問題の実質解消:** V8 IsolateベースのランタイムとWASMの成熟により、コールドスタートは数msオーダーに短縮され、サーバーレスを避ける理由だった「初回応答遅延」がほぼ解消された。

- **エッジとDBの距離問題:** 計算はエッジに寄っても、Postgresなど中央集権DBとの往復遅延がボトルネックとして残るため、Read Replicaのエッジ配置やSQLiteベースの分散DB（Turso等）を併用する設計が重要になる。

- **コスト構造の変化:** リクエスト課金モデルにより低トラフィック期のインフラコストがほぼゼロになる一方、スパイク時の予測不能な課金が課題となり、レート制限やコストアラートの実装が必須要件化している。

- **可観測性の複雑化:** 分散したエッジロケーション間でのトレーシング・デバッグが難しく、OpenTelemetry等の分散トレーシング基盤への早期投資が、サーバーレス移行の隠れた前提条件になっている。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証(WebAuthn)がデファクトスタンダードとなり、フィッシング耐性のある認証方式として実装コストも大幅に低下している。既存パスワード認証との併用期間を設けつつ、段階的に移行するロードマップが必要。

- **トークン管理のゼロトラスト化:** 短命JWT(5-15分)+リフレッシュトークンローテーション+デバイスバインディングの組み合わせが標準になり、トークン漏洩時の被害範囲を最小化する設計が必須。localStorage保存は避け、httpOnly Cookie + SameSite=Strictを徹底すべき。

- **AIエージェント/Bot向け認証の分離:** 自律エージェントによるAPIアクセスが急増しており、人間ユーザーとは別のスコープ制限付き認証基盤(OAuth 2.1 + PKCE、細粒度スコープ)を用意しないと、過剰権限のエージェントが攻撃対象領域を広げるリスクがある。

- **継続的リスクベース認証:** ログイン時の一発認証から、セッション中の行動パターン・デバイスフィンガープリント・位置情報を継続的に評価するリスクベース認証へのシフトが進んでいる。異常検知時のみ追加認証(step-up MFA)を要求することでUXとセキュリティを両立できる。

- **サプライチェーン経由の認証情報漏洩対策:** npm/依存パッケージ経由でのトークン窃取事例が増加しており、CI/CDのシークレットは短命化(OIDC federated credentials)し、長期APIキーの利用を廃止する方向が推奨される。sumitsugiのようなNext.js構成では、`.env.local`の管理徹底とVercel/GitHub Actions間のOIDC連携を検討する価値がある。

### 6. database architecture Prisma Supabase 2026

- **エッジ対応の重要性:** Supabaseのグローバルエッジロケーション対応とPrisma Accelerateのコネクションプーリングを組み合わせることで、サーバーレス環境でのDBコネクション枯渇問題を回避しつつ低レイテンシを実現できる。

- **型安全性とRLSの両立:** Prismaのスキーマ駆動開発とSupabaseのRow Level Security（RLS）を併用する場合、Prisma経由のアクセスはservice_roleで認可を迂回しがちなので、アプリ層でのポリシー検証をテストに組み込む必要がある。

- **マイグレーション運用の一本化:** Prisma MigrateとSupabase CLIのマイグレーションを二重管理すると乖離が起きやすいため、どちらか一方（推奨はPrisma Migrate）を正とし、CI上で自動検証する運用が定着しつつある。

- **リアルタイム機能の使い分け:** Supabase Realtimeは物件ステータス変更などのライブ更新に有効だが、複雑な集計クエリはPrisma経由のRESTやRPCに任せる住み分けが、パフォーマンスとコードの見通しの両面で有利。

- **PostgreSQL拡張機能の活用:** pgvector（類似物件レコメンド）やpg_cronなどSupabaseのPostgreSQL拡張は、Prismaのスキーマでは直接表現しづらいため、生SQLマイグレーションと組み合わせるハイブリッド運用が2026年のベストプラクティスとして定着している。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Wasm GC提案の主要ランタイム実装が進み、Rustのメモリ管理オーバーヘッドが減少。将来的にはJS連携部分でのシリアライズコストを削減できる可能性がある。
- **ポイント2:** `wasm-bindgen`と`wasm-pack`のツールチェーンが成熟し、ビルドサイズ最適化（`wasm-opt`との連携）が標準化されつつある。バンドルサイズを気にするフロントエンドでは採用障壁が下がっている。
- **ポイント3:** WASI Preview 2によりコンポーネントモデルが実用段階に入り、サーバーサイドでのサンドボックス実行（プラグインシステムなど）にRust+Wasmを使うケースが増加。
- **ポイント4:** SIMD命令サポートが主要ブラウザで安定し、画像処理・暗号処理などCPU負荷の高い処理をWasmにオフロードするパターンが実用的になっている。
- **ポイント5:** ネイティブに対して依然1.5〜3倍程度のオーバーヘッドが残るケースもあり、全面移行より「ホットパスのみWasm化」というハイブリッド戦略が現実的な選択肢。

### 8. Next.js App Router patterns 2026

**Next.js App Router patterns 2026**

- **ポイント1:** Partial Prerendering (PPR) が安定版として広く採用され、静的シェルと動的コンテンツを1つのルートで組み合わせられるようになった。物件一覧ページのように「静的な枠組み＋動的な空室状況」を持つ画面では、TTFBを大幅に改善できる。
- **ポイント2:** `use cache` ディレクティブによる細粒度キャッシュ制御がデファクトスタンダード化し、`revalidateTag`と組み合わせたオンデマンド再検証が主流に。物件ステータス（draft/public）切り替え時のキャッシュ無効化を明示的に設計する必要がある。
- **ポイント3:** Server Actionsのセキュリティベストプラクティスが成熟し、`"use server"`関数への認可チェック必須化・CSRF対策の標準パターンが確立。フォーム送信や引越し費用計算などのミューテーションは、クライアント側検証に加えServer Actions内での再検証が必須という認識が定着。
- **ポイント4:** ルートグループ＋Parallel Routes＋Interceptors の組み合わせでモーダル型UIの実装が定番化。物件詳細のクイックビューや前の住人プロフィールのプレビューなど、URLを保ちながらモーダル表示する体験がSEOとUXの両立を実現。
- **ポイント5:** RSC（React Server Components）のペイロードサイズ最適化とストリーミングSSRのcomposable patternsが普及し、`loading.tsx`だけでなくコンポーネント単位のSuspense境界を細かく設計する「granular streaming」が推奨される。一覧画面のような大量データ表示で体感速度改善に直結する。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約とNode.js APIの互換性拡大:** Vercel Edge FunctionsはV8 isolateベースで軽量・低レイテンシですが、Node.js特有のAPI（fsなど）は依然使えないため、住所検索や画像処理などの重い処理はServerless Functions（Node runtime）に振り分ける設計判断が重要です。

- **Streaming SSRとの組み合わせでTTFB短縮:** Next.js 16のPPR（Partial Prerendering）とEdge Functionsを組み合わせることで、物件一覧ページなど動的コンテンツのTTFBを大幅に改善できます。静的シェルを即座に返しつつ、パーソナライズ部分のみエッジでストリーミングする構成が2026年のベストプラクティスです。

- **リージョン最適化とデータ局所性:** エッジ関数はユーザーに最も近いリージョンで実行されますが、DBが単一リージョンにある場合はレイテンシの恩恵が薄れます。sumitsugiのようにDBアクセスを伴う認証・物件データ取得処理は、エッジでのキャッシュ層（KVやISR）を挟むことでコールドパスを減らすべきです。

- **コスト構造の変化に注意:** Edge Functionsは実行時間課金からリクエスト数・CPU時間ベースの課金へ移行が進んでおり、高トラフィックページでは想定外のコスト増につながる場合があります。ミドルウェアでの過度なロジック実行（認証チェック以外の重い処理）は避け、必要最小限に留めるべきです。

- **観測性ツールの成熟:** Vercel OTelサポートやEdge Config連携により、エッジ関数のトレーシング・A/Bテスト設定がより容易になっています。ベータローンチ前に、認証まわりのエッジミドルウェアでのエラー監視を組み込んでおくと、本番障害の早期検知に役立ちます。

### 10. TypeScript type safety patterns 2026

- **ポイント1（型推論の高度化）:** TypeScript 5.x以降、`satisfies`演算子やconst型パラメータの活用が定着し、型注釈を減らしながら厳密な型安全性を保つパターンが主流になっている。sumitsugiのようなZodスキーマ駆動の設計では、`z.infer`と`satisfies`を組み合わせて型の二重管理を避けるのが有効。

- **ポイント2（スキーマファースト開発）:** Zodなどのランタイムバリデーションライブラリから型を導出する「Schema as Single Source of Truth」パターンが、API境界・フォーム・DBモデルの型不整合を防ぐ標準手法として確立している。本プロジェクトの「Input validation: Use Zod schemas at system boundaries」方針と合致しており、今後はServer Actionsの入出力にも一貫適用すべき。

- **ポイント3（Discriminated Unionの徹底活用）:** `status: 'draft' | 'public'`のようなUnion型は、switch文の網羅性チェック（`never`型による exhaustiveness check）と組み合わせることで、新しいステータス追加時のコンパイル時検出漏れを防げる。型の使用箇所を追加する際は必ずgrepで全参照を確認する運用ルールを、コンパイラの網羅性チェックで機械的に担保できる。

- **ポイント4（型とテストの境界の再定義）:** 2026年のトレンドとして、型システムでは表現しきれない不変条件（ビジネスルール）をブランド型（Branded Types）やopaque型で表現し、単なるprimitive型の誤用（例: 物件IDと会員IDの取り違え）をコンパイル時に防ぐパターンが普及している。TDD運用と組み合わせることで、型テストとユニットテストの責務分担が明確になる。

- **ポイント5（AI生成コードの型安全性ガードレール）:** Autonomous developerのような自動化ワークフローでコード生成を行う体制では、`bun run build`を必須ゲートとする現行ルールに加え、strict modeとno-explicit-anyのESLint強制を組み合わせることで、AIが生成した型の緩い実装を早期に弾く仕組みが2026年のベストプラクティスとして重要性を増している。
