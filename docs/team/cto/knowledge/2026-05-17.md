# CTO Knowledge - 2026-05-17

## Daily Update (2026-05-17)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを削減する最も効果的な手法として定着。`"use client"` を境界として明確に分離し、データフェッチはサーバー側で完結させることでウォーターフォールを排除できる。

- **Partial Prerendering (PPR) の本格導入:** 静的シェルを即座に配信しつつ動的コンテンツをストリーミングする PPP が Next.js 15以降で安定化。従来の SSR/SSG の二択を超えた、ハイブリッドアーキテクチャが標準となりつつある。

- **Turbopack によるビルド高速化:** webpack から Turbopack への移行が実用段階に達し、大規模プロジェクトでコールドスタートが最大 10x 高速化。CI/CD パイプラインのボトルネック解消に直結する。

- **`<Image>` / `<Script>` の最適化設定の見直し:** `priority` 属性の過剰付与と未設定の両方が LCP に影響。Core Web Vitals を継続的に計測し、`next/font` の `display: swap` 設定とあわせて CLS・LCP を定期チューニングする運用が重要。

- **Edge Runtime とキャッシュ戦略の再設計:** `fetch` の `revalidate` 設定や `unstable_cache` を活用したきめ細かいキャッシュ制御が主流。過剰なキャッシュ無効化がパフォーマンス劣化を招くため、データの鮮度要件に応じた戦略設計が不可欠。

### 2. React Server Components streaming 2026

- **Suspense境界の戦略的配置が鍵:** RSCストリーミングでは、Suspense境界をコンポーネントツリーのどこに置くかがTTFB・LCP直結の設計判断になる。データフェッチの依存関係を分析し、並列ストリームを最大化する設計が必須。

- **PPR（Partial Prerendering）との統合が主流化:** Next.js 15以降でPPRが安定化し、静的シェルを即時配信しつつ動的部分をストリームで差し込むパターンが標準アーキテクチャになりつつある。これにより「静的か動的か」の二択から解放される。

- **Server Actions + Optimistic UIの組み合わせが実装パターンを変える:** RSCとServer Actionsを組み合わせることで、従来のREST API層を省略したフルスタックコンポーネントが実現可能。`useOptimistic`との併用でUXを損なわずにラウンドトリップを削減できる。

- **Cacheの粒度制御が複雑性の核心:** `fetch`のキャッシュ、`unstable_cache`、`revalidatePath`/`revalidateTag`の使い分けを誤るとキャッシュ汚染が発生する。チーム全体でキャッシュ戦略をドキュメント化・標準化しないとデバッグコストが跳ね上がる。

- **Reactコア側のストリーミングAPIが成熟:** `use(Promise)`によるクライアント側の非同期解決が可能になり、Server/Client境界をまたぐデータフローの設計自由度が増した。ただしウォーターフォールを避けるため、Promiseをpropsとして早期に生成・受け渡しするパターンを徹底すること。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年現在、Next.js + tRPCの組み合わせが中小規模プロダクトのデファクトになりつつある。スキーマ定義なしでクライアント・サーバー間の型を共有できるため、開発速度と型安全性を両立できる。

- **GraphQLの役割の再定義:** GraphQLはBFF（Backend for Frontend）層やマイクロサービス集約のためのフェデレーション用途に絞られてきており、単一サービスでの採用は過剰設計になるケースが増えた。Relay/Apollo Federationの成熟でエンタープライズ向けは依然有力。

- **REST + OpenAPI 3.1の復権:** Zod + `zod-openapi` や `hono` などのスキーマファースト設計ツールにより、RESTでも型安全なコード生成が容易になった。シンプルなCRUD APIでは依然RESTが最もコストパフォーマンスが高い。

- **エッジランタイム対応がAPI選定の制約に:** Cloudflare Workers / Vercel Edge Runtimeの普及により、重厚なGraphQLランタイムよりも軽量なREST/tRPCが有利な場面が増えた。API設計はランタイム制約とセットで検討する必要がある。

- **AI統合のためのMCP（Model Context Protocol）:** LLMとAPIを繋ぐ標準として2025年以降MCPが急速に普及。新規API設計時はMCPサーバーとしての公開も視野に入れ、ツール呼び出し可能な構造化スキーマ設計が重要になっている。

### 4. serverless edge computing 2026

- **エッジでのAI推論が主流化:** WebAssembly（Wasm）とONNXランタイムの成熟により、LLMの軽量モデル（1-7Bパラメータ）をエッジノードで直接実行するパターンが普及し、レイテンシとプライバシーの両立が現実的になった。

- **V8 IsolatesからWasmへの移行加速:** CloudflareやFastlyがWasmファーストのランタイムを標準化しつつあり、Node.js互換レイヤーへの依存を脱してよりセキュアで予測可能なコールドスタート（< 1ms）を実現している。

- **エッジDBとの統合が成熟:** Cloudflare D1、Turso（libSQL）、Neon（PostgreSQL）のエッジレプリカにより、「エッジで読む・オリジンで書く」パターンが定着し、グローバル分散アプリの構築難易度が大幅に低下した。

- **オブザーバビリティの課題が顕在化:** 数百ノードに分散したエッジ関数のトレーシングはOpenTelemetryだけでは不十分で、エッジ特有のサンプリング戦略とコスト管理が実務上のボトルネックになっている。

- **コスト構造の見直しが必要:** リクエスト単価は安価だが、エッジキャッシュのバイパス率が高いと予想外のオリジンコストが発生する。CDNとエッジ関数の責務分離を設計段階で明確にしないと、マイクロサービス化のコスト爆発と同じ轍を踏む。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準化:** FIDO2/WebAuthn ベースのパスキーが主流となり、パスワードレス認証が実用段階へ。フィッシング耐性が本質的に高く、生体認証と組み合わせることでUXとセキュリティを両立できる。

- **ゼロトラスト認証モデルの徹底:** 「一度認証したら信頼する」モデルは廃止し、リクエストごとにコンテキスト（デバイス健全性・場所・行動パターン）を評価する継続的認証が必須。特にAPIゲートウェイ層でのmTLS実装が重要。

- **AIを活用した異常検知の組み込み:** ログイン試行パターンの機械学習分析により、クレデンシャルスタッフィング攻撃をリアルタイムで検出。従来のレートリミットだけでは不十分で、行動バイオメトリクスとの組み合わせが効果的。

- **OAuthトークン管理の厳格化:** アクセストークンの有効期限を15分以下に短縮し、リフレッシュトークンのローテーション（RTR）を必須化。トークン漏洩時の被害を最小化するため、スコープの最小権限原則を徹底する。

- **サプライチェーン攻撃対策としての依存関係監視:** 認証ライブラリ（NextAuth・Passportなど）の脆弱性は即座に攻撃対象になるため、Dependabotや`bun audit`の自動化とSBOM（ソフトウェア部品表）の管理が不可欠。

### 6. database architecture Prisma Supabase 2026

- **PrismaとSupabaseの統合成熟:** Prisma v6以降、Supabaseとのネイティブ統合が安定し、`prisma generate --accelerate`によるコネクションプーリングがエッジ環境でも実用レベルに達した。Prisma Accelerateを使うことでサーバーレス・エッジ関数での接続枯渇問題が大幅に軽減される。

- **Row Level Security (RLS) との責務分離:** SupabaseのRLSはDBレベルのアクセス制御として強力だが、PrismaはRLSを直接認識しないため、アプリ層とDB層で二重管理になるリスクがある。2026年時点では、Prismaクライアントにユーザーコンテキストを渡すミドルウェアパターン（`prisma.$use`）でRLSと協調させるアーキテクチャが主流。

- **Supabase Branchingによる開発フロー変革:** Supabase BranchingがGA化したことで、PRごとにDBプレビュー環境を自動作成できる。Prismaマイグレーションをブランチと連動させることで、本番データを汚さずスキーマ変更の検証が可能になり、CI/CDの品質が劇的に向上する。

- **pgvectorとAIワークロードの台頭:** SupabaseのpgvectorサポートとPrismaの`Unsupported`型活用により、ベクトル検索をRDBと同一DB内で運用するパターンが急増。専用ベクトルDBを別途立てるより運用コストが低く、トランザクション整合性も保てる。

- **型安全なクエリの限界とraw SQLの併用:** 複雑な集計・再帰CTEはPrismaのクエリAPIでは表現しにくく、`prisma.$queryRaw`とZodによる結果バリデーションを組み合わせるパターンが定着。型安全性を保ちつつSQLの表現力を活かす「ハイブリッドORM」アプローチが2026年のベストプラクティス。

### 7. WebAssembly Rust performance 2026

- **Component Model の成熟:** WebAssembly Component Model (WIT/WASI 0.2) が2026年に実用段階に達し、RustコンポーネントをJS/Python等と型安全に合成できるようになった。マイクロサービスのWasm化が現実的な選択肢になっている。

- **SIMD・スレッド対応の普及:** wasm-simd128とShared Memory/Atomicsのブラウザサポートが安定し、RustのSIMDクレート（`std::simd`）をそのままWasmターゲットでフル活用できる。画像処理・ML推論で2〜4倍の性能向上が報告されている。

- **バイナリサイズの改善:** `wasm-opt`（Binaryen）+ Rustの`opt-level = 'z'`の組み合わせに加え、component-modelのfine-grained linkingにより、実用的なCRUDアプリで100KB以下のバイナリが達成可能になった。

- **Wasmtime/WASIedgeのサーバーサイド採用:** エッジランタイムでのコールドスタートがV8 Isolateより高速な場合があり、RustターゲットのWasmをCloudflare Workers・Fastly Compute等に直接デプロイするパターンが主流になりつつある。

- **デバッグ・プロファイリングの整備:** DWARF over Wasmのサポートが成熟し、Chrome DevTools・wasmdbgでRustのソースレベルデバッグが実用的になった。`cargo-flamegraph`のWasm対応も進み、ボトルネック特定のコストが大幅に下がっている。

### 8. Next.js App Router patterns 2026

- **Server Componentsをデフォルトに:** 2026年現在、App RouterではServer Componentsが標準で、クライアントコンポーネントは`'use client'`が必要な境界でのみ使用する設計が定着。データフェッチはサーバー側で完結させ、バンドルサイズを最小化するのがベストプラクティス。

- **Partial Prerendering (PPR) の本格活用:** Next.js 15+でStableになったPPRにより、同一ページ内の静的シェルと動的コンテンツを混在させられる。`<Suspense>`境界で動的部分を囲むだけでエッジキャッシュと動的レンダリングを両立できる。

- **Server Actionsによるフォーム処理の簡素化:** API Routeを介さずにフォームからサーバー側のミューテーションを直接呼び出せるServer Actionsが主流化。`useFormState`/`useActionState`との組み合わせでProgressiveEnhancementも自然に実現できる。

- **`use cache`ディレクティブによる細粒度キャッシュ制御:** Next.js 16世代では`fetch`のキャッシュオプションに加え、`use cache`ディレクティブで関数・コンポーネント単位のキャッシュ戦略を宣言的に定義可能。`cacheTag`/`cacheLife`APIで動的invalidationも容易になった。

- **Parallel Routes + Intercepting Routesによるモーダルパターンの標準化:** `@slot`によるParallel Routesと`(.)`記法のIntercepting Routesを組み合わせることで、URLを維持しながらモーダル表示するパターン（例：写真詳細モーダル）がフレームワークレベルでサポートされ、シェアリンクやブラウザバックの挙動も正しく動作する。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択的活用:** 全APIルートをEdgeに移行するのではなく、地理的レイテンシが重要なルート（認証チェック、A/Bテスト、リダイレクト処理）に絞ることがコスト最適化の鍵。Node.js Runtimeとの使い分けが2026年の基本戦略。

- **Cold Start撲滅のためのStreaming対応:** Edge FunctionsでのStreaming Response（`ReadableStream`）活用により、初期バイト到達時間（TTFB）を大幅短縮できる。特にAI系レスポンスのストリーミングとの相性が抜群。

- **KV・データストアの配置設計:** Vercel KVやUpstash Redisのリージョン設定をEdge Functionのデプロイリージョンと合わせないと、往復レイテンシが逆に増大するアンチパターンに注意。データの近傍配置が大前提。

- **Bundle Sizeの厳格管理:** Edge Runtimeは最大4MBのコード制限があり、重いnpmパッケージ（例: `date-fns`全体import）が即座に問題になる。`import { format } from 'date-fns'`のようなtree-shaking前提の書き方と、`@edge-runtime/jest-environment`での事前検証が必須。

- **Middleware乱用の回避:** Next.js Middlewareは全リクエストに対して実行されるため、複雑なロジックを入れるとスループットのボトルネックになる。マッチャー（`matcher`設定）で対象パスを明示的に絞り込み、処理は100ms以内に収めるのが実運用上の鉄則。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded Typesが実運用で定着し、プリミティブ型の意図しない混在によるバグを型レベルで防ぐパターンが標準化されつつある。

- **`satisfies` 演算子の活用:** TypeScript 4.9で導入された `satisfies` が2026年時点で広く浸透し、型推論を維持しながら型チェックを行えるため、`as const` との組み合わせで設定オブジェクトや定数定義の安全性が大幅に向上した。

- **Template Literal Types による API 型生成:** `type Route = `/api/${string}`; のようなTemplate Literal Typesを活用して、エンドポイント名やイベント名を静的に型付けする手法が拡大し、ランタイムエラーをコンパイル時に検出できるようになっている。

- **Zod + tRPC による End-to-End 型安全:** フロントエンドからバックエンドまで型を一貫させるtRPCパターンが成熟し、Zodスキーマを単一の真実の源（Single Source of Truth）としてバリデーションと型推論を同時に担わせる設計が主流になっている。

- **`NoInfer` ユーティリティ型の実用化:** TypeScript 5.4で追加された `NoInfer<T>` により、ジェネリック関数での意図しない型推論の広がりを抑制できるようになり、ライブラリ設計における型安全性の粒度が向上した。
