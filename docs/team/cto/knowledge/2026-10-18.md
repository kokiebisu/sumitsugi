# CTO Knowledge - 2026-10-18

## Daily Update (2026-10-18)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 15以降で導入されたPPRがNext.js 16でも中核機能として定着し、静的シェルを即時配信しつつ動的部分をストリーミングすることで、SSRのレイテンシ問題とSSGの柔軟性不足を同時に解決できる。ダッシュボードや一覧ページなど「一部だけ動的」なUIで特に効果が大きい。

- **Turbopackのデフォルト化によるビルド高速化:** Next.js 16でTurbopackが本格的にデフォルトビルドツールとなり、開発時のHMRだけでなくプロダクションビルドも大幅に高速化されている。大規模コードベースでのCI時間短縮に直結するため、`bun run build`のCI実行時間が気になるなら設定を確認する価値がある。

- **React Server Components (RSC) のバンドルサイズ最適化:** クライアントコンポーネントの境界を最小限に絞り、データ取得をServer Componentに寄せることで、クライアントJSバンドルを削減するパターンが2026年のベストプラクティスとして確立している。特に物件一覧・詳細ページのような閲覧中心のUIはServer Componentに全面移行する余地が大きい。

- **キャッシュ戦略の明示化（`use cache` ディレクティブ）:** Next.js 15/16系で導入された`use cache`指令により、関数単位・コンポーネント単位でキャッシュ境界を明示的に制御できるようになった。暗黒魔術的だった自動キャッシュ挙動への依存を減らし、デバッグ可能性とパフォーマンスの両立がしやすくなっている。

- **画像・フォント最適化のエッジ処理シフト:** `next/image`の最適化処理やWebフォントのサブセット化がエッジランタイム側にオフロードされる傾向が強まり、特にモバイル回線でのLCP改善に効いている。物件写真を多用するUIでは、CDN側の画像変換設定の見直しが投資対効果の高い改善点になりやすい。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではRSCのストリーミングがデフォルト最適化され、`loading.tsx`やSuspenseバウンダリの粒度設計がLCP改善の主戦場になっている。重要なUIを先出しし、レビューやランキングなど重くないデータを後続ストリームに回す設計が効果的。

- **ポイント2:** Partial Prerendering（PPR）が実質標準化し、静的シェルを即時配信しつつ動的部分だけストリーミングする構成が主流に。sumitsugiの物件詳細ページのような「ほぼ静的＋一部動的（空室状況・価格）」な画面に特に向いている。

- **ポイント3:** `use cache`ディレクティブとストリーミングの組み合わせで、キャッシュヒット時は即時レスポンス、ミス時のみストリーミングにフォールバックする制御がしやすくなった。物件一覧のようなアクセス頻度の高いページでTTFBを安定させられる。

- **ポイント4:** Server Actionsのストリーミングレスポンス対応により、フォーム送信後の多段階フィードバック（検証中→保存中→完了）をRSC側だけで表現可能になり、クライアントの状態管理コードを減らせる。問い合わせフォームや引越し費用計算などのマルチステップUIに適用価値が高い。

- **ポイント5:** エラーバウンダリとストリーミングの相性が改善され、一部のRSCチャンクが失敗しても他のチャンクの配信を止めない設計が容易に。外部API（地図・決済等）依存の箇所をSuspense境界で分離し、障害時のページ全体ブロックを防ぐパターンが推奨される。

### 3. API design REST GraphQL tRPC 2026

- **スキーマファースト+型安全性の統合:** tRPCの採用が拡大し、TypeScriptモノレポではエンドツーエンドの型推論により手書きのAPIクライアントコードが不要になっている。弊社のようなNext.js構成では、GraphQLのような別言語スキーマ定義を持たずに済むtRPCが開発速度の観点で有利。

- **GraphQLは複雑な関係性データに限定使用:** 物件検索のような多面的フィルタリングやネスト関係（物件→前の住人→インテリア）がある場合はGraphQLのクエリ柔軟性が効くが、単純なCRUDにはオーバーエンジニアリング。RESTとの併用（BFFパターン）が2026年の主流。

- **RESTはシンプルさとキャッシュ戦略で依然強い:** CDN/HTTPキャッシュを活用した公開物件一覧ページなどの読み取り中心エンドポイントはREST+適切なCache-Controlヘッダーが最もコスト効率が良い。認証必須の内部APIはtRPCに寄せる住み分けが効果的。

- **AIエージェント/LLM統合を見据えたAPI設計が必須トレンド:** MCP（Model Context Protocol）のようにAIエージェントが直接呼び出せるAPI設計が注目されており、将来的に「前の住人」とのマッチングや引越しフローをAIエージェント経由で操作できるAPI公開を検討する価値がある。

- **Zodによるランタイム検証の一元化:** tRPC・REST問わずZodスキーマを型定義とバリデーションの単一ソースとする設計が標準化しており、弊社の`standards.md`にある「Zodスキーマによる入力検証」方針とも合致する。境界層でのスキーマ再利用がバグ削減に直結する。

### 4. serverless edge computing 2026

- **ポイント1:** Cloudflare WorkersやVercel Edge Functionsなど、V8 Isolateベースのエッジランタイムが成熟し、コールドスタートがほぼゼロになったことで、Next.js 16のApp Routerでも地理的に近いエッジでSSRを完結できるようになっています。sumitsugiのような物件検索は地域性が強いため、閲覧者に近いリージョンでレンダリングすることでTTFBを大幅短縮できます。

- **ポイント2:** エッジでのデータベースアクセスは依然ボトルネックで、2026年はDurable Objects・Turso・PlanetScaleのようなエッジレプリカ型DBとエッジKV（例: Cloudflare KV, Vercel Edge Config）を組み合わせる「読み取りはエッジ、書き込みはオリジン」構成が標準化しています。物件一覧や検索結果のような読み取り中心のページはエッジキャッシュ+ISRで高速化し、問い合わせ・契約系の書き込みはオリジンAPIに委譲する設計が有効です。

- **ポイント3:** Edge MiddlewareでのA/Bテストや認証チェックがコスト・レイテンシの両面で主流になっており、auth-context.tsxのようなクライアント側認証ロジックの一部をエッジミドルウェアに移すことで、未認証ユーザーへの不要なページ配信を防げます。ただしNode.js API非対応の制約があるため、依存ライブラリの互換性確認が必須です。

- **ポイント4:** 2026年はエッジとサーバーレスの境界がさらに曖昧になり、「どこで実行されるか」をコードから抽象化するフレームワーク（Next.jsのruntime設定など）が普及しています。実装時は`export const runtime = 'edge'`指定を機能ごとに明示し、ビルド時にエッジ非互換なNode API依存を検出する仕組み（lint/CIチェック）を組み込むべきです。

- **ポイント5:** 観測性（オブザーバビリティ）が課題として残っており、分散したエッジ実行環境でのトレーシング・ログ集約が重要になっています。将来的にアクセス解析や引越し費用計算のようなビジネスロジックをエッジに置く場合は、OpenTelemetry対応のエッジ計装を早期に導入し、障害時の原因特定を可能にしておく必要があります。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証(WebAuthn)がデファクトスタンダード化しており、フィッシング耐性のある認証をデフォルトで提供し、SMS/メールOTPよりも優先実装すべき。弊社でも新規サインアップフローではパスキーをプライマリ選択肢として提示する設計が望ましい。

- **トークンのライフサイクル管理の厳格化:** JWTなどのアクセストークンは短寿命化(5-15分)し、リフレッシュトークンのローテーション＋再利用検知(reuse detection)を必須化。漏洩時の被害範囲を最小化するアーキテクチャが標準になっている。

- **セッション管理とデバイスバインディング:** トークンを特定デバイス/ブラウザフィンガープリントに紐付け、異常なIPやデバイスからのセッション利用を即座に無効化する仕組みが重要。特に引越し費用決済など金銭が絡む操作では再認証(step-up auth)を強制すべき。

- **認可ロジックの分離とゼロトラスト原則:** 認証(誰か)と認可(何ができるか)を明確に分離し、物件ステータス(`draft`/`public`)やユーザーロール(前の住人/次の住人)ごとのアクセス制御をAPI境界で一元管理する。クライアント側のみの検証は信頼しない。

- **シークレット管理の自動化:** APIキーやOAuthトークンのハードコード禁止はもちろん、短期的なシークレットローテーションとシークレットスキャン(CI組み込み)が2026年のベースライン。sumitsugiのGitHub Actions(`CLAUDE_CODE_OAUTH_TOKEN`等)も定期ローテーション対象として運用ルール化することを推奨。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Supabaseは2025年以降Prisma Accelerateとの統合を強化し、Edge Functionsからのコネクションプーリング問題（PgBouncer経由のprepared statement制約）が大幅に改善されており、サーバーレス環境でのDB接続安定性が向上している。
- **ポイント2:** Prisma 6系ではRust製クエリエンジンから移行したTypeScript版エンジンが主流になり、コールドスタートが短縮されたため、Vercel/Next.jsのようなサーバーレスデプロイとの親和性が高まっている。
- **ポイント3:** Row Level Security (RLS) をPrismaのスキーマレベルで扱う際は、Supabase側のポリシーとアプリ側のビジネスロジックが二重管理になりがちなので、`seller`/`listing`等の重要テーブルでは認可ロジックをRLSに一本化する方が運用コストが下がる。
- **ポイント4:** マイグレーション管理は`prisma migrate`とSupabaseのマイグレーションCLIが競合しやすいため、どちらか一方（通常はPrisma側）に統一し、CI上で`prisma migrate diff`による差分検証を必須化するのがベストプラクティスになっている。
- **ポイント5:** リアルタイム機能（Supabase Realtime）を使う場合、Prismaのコネクションとは別経路になるためスキーマ変更時の整合性チェックが漏れやすく、物件ステータス（`draft`/`public`）のような状態遷移はDB側トリガーではなくアプリ層で一元管理する方が事故が少ない。

### 7. WebAssembly Rust performance 2026

**CTO視点: WebAssembly Rust performance 2026**

- **ポイント1: Component ModelとWASI Previewの本格普及** — WASI 0.2/Component Modelの標準化が進み、Rustで書いたWasmモジュールを言語非依存の再利用可能なコンポーネントとして配布できるようになった。マイクロサービス的な粒度でWasmモジュールを合成する設計が実用レベルに達している。
- **ポイント2: ネイティブ比80-95%の実行性能を実現** — LLVMのWasm向け最適化とSIMD128の普及により、画像処理・暗号化・パーサーなどCPUバウンドな処理ではネイティブコードとの差が1桁%まで縮小。ブラウザ内での重い前処理をサーバーに逃がさずクライアントで完結できる場面が増えている。
- **ポイント3: 起動時間とコールドスタートの圧倒的優位性** — Wasmランタイム（Wasmtime, Wasmer）はマイクロ秒〜数ミリ秒でインスタンス化できるため、エッジコンピューティングやサーバーレス関数でコンテナより高速に起動できる。弊社のようなアクセス頻度が不均一なプロダクトではコスト・レイテンシ両面で有利。
- **ポイント4: メモリ安全性とサンドボックス実行が標準要件になった** — RustのメモリセーフティとWasmのサンドボックス特性の組み合わせが、ユーザー生成コンテンツやプラグイン実行機構におけるセキュリティ要件として事実上の標準になりつつある。サードパーティ拡張機能を安全に実行する基盤として検討価値が高い。
- **ポイント5: ツールチェーンの成熟でビルド運用コストが低下** — `wasm-bindgen`、`wasm-pack`、`cargo-component`などのエコシステムが安定し、CI/CDへの統合コストが大幅に下がった。Bunベースの我々の開発フローとも相性が良く、将来的にパフォーマンスクリティカルな機能（画像処理・PDF生成など）をRust/Wasm化する選択肢として現実的になっている。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 15以降で実験的だったPPRが2026年には標準パターン化し、静的シェルを即時配信しつつ動的部分をStreamingで差し込む構成がデフォルト選択肢になっている。初期表示速度(TTFB)を犠牲にせずパーソナライズ可能になるため、物件一覧ページのような「検索条件は動的・レイアウトは静的」な構造に相性が良い。

- **Server Actions のセキュリティ境界強化:** Server Actionsがデータ変更の主流になった一方、意図しない公開APIエンドポイント化を防ぐための入力検証（Zod）とCSRF対策が標準プラクティス化している。本プロジェクトの`.claude/rules/standards.md`が求める「システム境界でのZod検証」はまさにこの文脈で重要。

- **Caching戦略の明示化（`use cache`ディレクティブ）:** 従来の暗黙的fetchキャッシュから、`'use cache'`や`revalidate`タグを明示的に指定するモデルへ移行が進んでいる。公開/非公開物件（`'draft' | 'public'`）のようなステータス切り替えを伴うデータは、キャッシュタグ無効化の設計を最初から組み込む必要がある。

- **ルートグループ＋Parallel Routesでの関心分離:** `(group)`ルートグループとParallel Routes/Intercepting Routesを組み合わせ、モーダルや多段フローを1ページ内で宣言的に扱うパターンが定着。引越しフロー等の多段フォームUIに適用すると、ブラウザ履歴・ディープリンクを保ったまま実装できる。

- **Server ComponentsファーストでのTypeScript型安全性:** クライアント境界(`'use client'`)を最小化し、Server Component間でのprops受け渡しを型で保証する設計が主流。小さいファイル・小さい関数という本プロジェクトの方針とも合致し、ビルド時の型チェックで早期にバグを検出できる。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge FunctionsのCold Start削減が2026年の主要トレンド。V8 isolateベースの実行環境がさらに最適化され、初回リクエストのレイテンシがほぼゼロに近づいているため、認証チェックやA/Bテストのロジックをミドルウェア層に移すことで、オリジンサーバーへの不要なラウンドトリップを削減できる。

- **ポイント2:** Edge Config（KVストア）とEdge Functionsの統合が深化しており、フラグ管理や多言語ルーティングなどの低頻度更新データをグローバルに1桁ミリ秒で読み取れる。sumitsugiのようなプロパティ検索機能では、地域別の表示設定をEdge Configに置くことでDB往復を避けられる。

- **ポイント3:** Streaming SSR + Edge RenderingがNext.js 16のApp Routerで標準化され、`loading.tsx`やSuspenseバウンダリと組み合わせることで、物件一覧ページのような重いデータ取得を含むページでもTTFBを大幅に短縮できる。ただしEdge RuntimeはNode.js APIの一部（`fs`、一部の暗号モジュール）が使えないため、認証ロジックなどを移行する際は事前に互換性を確認する必要がある。

- **ポイント4:** 課金モデルがCPU時間ベースに移行しており、無駄なポーリングやリトライロジックが直接コストに反映されるようになった。前の住人検索APIのような高頻度アクセスのエンドポイントは、Edge Functions内でのキャッシュヘッダー（`stale-while-revalidate`）設計を見直すだけで大幅なコスト削減が見込める。

- **ポイント5:** Observability統合が強化され、Vercel標準のトレーシングでEdge Function単位のレイテンシ・エラー率が可視化しやすくなった。本番ローンチ前のブロッカー（法務確認待ち）の間に、決済・認証周りのEdge Middlewareのパフォーマンス計測を仕込んでおくと、ベータローンチ直後のボトルネック特定が早くなる。

### 10. TypeScript type safety patterns 2026

- **ポイント1（型推論の強化とconst type parameters）:** TypeScript 5.x系の`const`型パラメータやより賢いnarrowingにより、明示的なジェネリクス指定を減らしつつ型安全性を保てるようになっている。sumitsugiのような`'draft' | 'public'`といったUnion型を多用する設計では、推論精度の向上がボイラープレート削減に直結する。

- **ポイント2（Zodなどのスキーマ駆動型安全性）:** 「型を書いてから実装」ではなく「スキーマを書いて型を生成」するZod/Valibotのようなランタイム検証ライブラリが標準化しつつあり、システム境界（API入出力・フォーム）での型安全性とランタイム安全性を一つの定義で両立できる。CLAUDE.mdのルールにもあるZod必須化はこの流れに合致している。

- **ポイント3（Branded Typesによる意味的区別）:** `string`や`number`のプリミティブ型を素通りさせず、`type UserId = string & { __brand: 'UserId' }`のようなBranded Typesで意味の異なる値を型レベルで区別するパターンが定着してきた。`seller`/`buyer`のID混在などのバグをコンパイル時に防げる。

- **ポイント4（Exhaustiveness Checkingの徹底）:** Union型が増えるほど`switch`文での`never`型を使った網羅性チェックが重要になる。`status: 'draft' | 'public'`に新しい値を追加した際、コンパイルエラーで全使用箇所の漏れを検知できる設計が2026年のベストプラクティスとして定着している（CLAUDE.mdの「Union型変更時は全箇所grep」ルールと整合）。

- **ポイント5（型とテストの責務分離）:** 型チェックは「あり得ない状態」を排除し、テストは「ロジックの正しさ」を保証するという分業がより明確になってきている。型安全性だけでは機能の正しさは保証されないため、ビルド成功とE2Eテストの両方を完了条件とする運用（当プロジェクトの`bun run build`必須化）が妥当なプラクティスとして広く支持されている。
