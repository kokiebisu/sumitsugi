# CTO Knowledge - 2026-10-27

## Daily Update (2026-10-27)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Prerendering / PPR の本格普及）:** Next.js 15〜16で安定化したPPRにより、静的シェルを即時返しつつ動的部分のみStreamingで後から埋める構成が標準化。LCPとTTFBを両立できるため、物件一覧ページのようなハイブリッドコンテンツに最適。
- **ポイント2（React Server Components前提のデータフェッチ最適化）:** クライアントへのJS転送量を減らすため、データ取得をRSCに寄せ、`use client`境界を最小限に絞る設計が定着。弊社の`properties/`や`listing/`ページでも、インタラクティブ要素（画像ギャラリー・お気に入りボタン等）だけをClient Componentに切り出すべき。
- **ポイント3（Turbopackビルドの標準化）:** Next.js 16でTurbopackが本番ビルドでもデフォルト化され、Webpack比でビルド時間が大幅短縮。CI実行時間の短縮に直結するため、`bun run build`のCI実行コストを下げられる余地がある。
- **ポイント4（画像・フォント最適化の自動化）:** `next/image`のAVIF対応強化やフォントのセルフホスティング自動化により、Core Web Vitals（特にCLS）改善が運用負荷なしで進む。物件写真が多いUIほど効果が大きい。
- **ポイント5（キャッシュ戦略の明示化）:** Next.js 15以降でfetchキャッシュがデフォルトOFFになったため、`cache: 'force-cache'`やルート単位の`revalidate`設定を意図的に書く必要がある。暗黙キャッシュに依存した実装は見直しが必要。

### 2. React Server Components streaming 2026

- **ポイント1:** Partial Prerendering（PPR）が標準化されつつあり、静的シェルを即時配信しつつ動的部分だけをストリーミングする設計がNext.js 16でも中心的パターンになっている。初期表示速度（TTFB/LCP）とパーソナライズの両立がしやすくなった。
- **ポイント2:** Suspenseバウンダリの粒度設計が重要になっており、1ページに大きなSuspenseを1つ置くのではなく、コンポーネント単位で細かく分割してストリーミング順序を制御するのがベストプラクティスとして定着してきている。
- **ポイント3:** `use cache` ディレクティブやキャッシュコンポーネント（Cache Components）がRSCストリーミングと組み合わさり、サーバー側のデータ取得コストとストリーミングのレイテンシをさらに下げられるようになっている。
- **ポイント4:** エッジランタイム（Edge Runtime）でのRSCストリーミングが現実的な選択肢になり、地理的に分散したユーザーに対するTTFB改善が進んでいるが、Node.js APIの制約には依然注意が必要。
- **ポイント5:** クライアント側のハイドレーション待ちを減らすため、Server ActionsとRSCストリーミングを組み合わせた「楽観的UI更新」パターンが一般化し、フォーム送信や多段フローでのUX改善に直結している。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはTypeScriptモノレポ（Next.js App Router + Bunのような構成）において、スキーマ共有とエンドツーエンドの型安全性をREST/GraphQLより低コストで実現できるため、小〜中規模チームのプロダクト初期フェーズで採用が加速している。社内BFF層限定の採用が現実的。

- **ポイント2:** GraphQLは依然としてマルチクライアント（Web/モバイル/パートナーAPI）向けの集約レイヤーとして強いが、N+1問題やキャッシュ制御の複雑さから、単一フロントエンド中心のプロダクトでは過剰設計になりやすい。sumitsugiのようにNext.js単体でフロント・バックを閉じている場合はtRPC/RESTで十分。

- **ポイント3:** RESTは依然として外部公開API・サードパーティ連携・将来のパートナー向けAPI公開を見据えた場合の「最大公約数」であり、OpenAPI + Zodでスキーマ検証とドキュメント生成を同時に行う構成が2026年のデファクト。

- **ポイント4:** 2026年のトレンドとして、tRPCとREST/OpenAPIを併用する「内部はtRPC、外部公開層は自動生成OpenAPI」というハイブリッド構成が増えている。tRPC→OpenAPI変換ツール（trpc-openapi系）が成熟してきたため、将来の外部API公開を見据えても初期実装コストを抑えられる。

- **ポイント5:** sumitsugiの現状（物件情報の取得・契約フロー中心、外部パートナー公開APIは未計画）を踏まえると、今は内部tRPC中心で型安全性とスピードを優先し、将来パートナー向けAPIが必要になった時点でOpenAPI層を追加する段階的アプローチが最もリスクが低い。

### 4. serverless edge computing 2026

- **ポイント1:** エッジでのAI推論とサーバーレスの融合が進み、Cloudflare WorkersやVercel Edge FunctionsでLLM推論を直接実行できるようになっている。レイテンシ要件の厳しい検索・レコメンド機能はエッジ上での軽量推論に移行する価値が高い。
- **ポイント2:** コールドスタート問題がV8 isolateベースの実行環境（Workers/Deno Deploy）でほぼ解消され、従来のコンテナ型サーバーレス（Lambda等）との差が明確化している。本サービスのような不動産検索・物件表示APIはエッジ実行への移行でTTFBを大幅改善できる可能性がある。
- **ポイント3:** エッジでのステートフルな処理（Durable Objects、Cloudflare D1など）が実用段階に入り、「エッジ=読み取り専用キャッシュ」という制約が緩和されている。物件のお気に入り・内見予約のような書き込み処理もリージョン分散のまま扱える設計が選択肢になってきた。
- **ポイント4:** 開発体験面では、Next.js 16のEdge RuntimeとNode.js Runtimeの切り替えがルート単位で柔軟になり、「全部エッジ」ではなく機能ごとの最適配置がベストプラクティスとして定着している。認証や決済など一貫性が重要な処理はNode Runtime、物件一覧表示などはEdge Runtimeという使い分けが現実的。
- **ポイント5:** コスト面では従量課金の粒度がさらに細分化され（CPU時間課金が主流化）、トラフィックの少ないMVPフェーズでは固定費ゼロに近い運用が可能。ベータローンチ前の本サービスにとっては、初期コストを抑えつつスケール時の移行コストも低いアーキテクチャとして相性が良い。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証（WebAuthn/Passkeys）がフィッシング耐性の高い標準として定着しつつあり、新規実装ではパスワード+SMS-OTPよりパスキーを第一選択とすべき。

- **トークンのライフサイクル管理:** JWTなどのアクセストークンは短命化（5-15分）し、リフレッシュトークンのローテーション＋再利用検知（refresh token rotation with reuse detection）を組み合わせることで、漏洩時の被害範囲を最小化する。

- **セッション固定・CSRF対策の継続的検証:** 認証後のセッションIDを必ず再発行し、SameSite=Strict/Lax Cookie＋CSRFトークンの二重防御を継続する。特にApp Router移行時はServer Actionsのオリジン検証漏れが起きやすいので要注意。

- **最小権限のRBAC/ABACと監査ログ:** 「前の住人」「次の住人」など役割が切り替わるsumitsugi特有のフローでは、ロール遷移のたびに権限を再評価し、認可失敗・権限昇格の試行を全て監査ログに残す設計が必須。

- **シークレット管理とゼロトラスト前提:** APIキー・DB認証情報はVaultや環境変数経由で管理し、内部ネットワークも信頼しない前提（ゼロトラスト）でサービス間通信にもmTLS/短命トークンを使う方向が2026年の主流。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORM v6以降の進化:** Rust非依存の新クエリエンジン（TypeScript製）への移行が進み、コールドスタートが大幅短縮。サーバーレス環境（Vercel Edge等）でのレイテンシ問題が実質解消された。
- **Supabase Branching:** 本番DBのスキーマ変更前にブランチ環境で検証できる機能が標準化され、マイグレーション起因の障害リスクが低減。Prisma Migrateとの組み合わせでCI/CDに組み込みやすい。
- **Row Level Security (RLS) とORMの併用:** SupabaseのRLSをPrisma経由で使う場合、Prisma Client自体はRLSを意識しないため、サービスロールキー経由のアクセス制御を別層で設計する必要がある点が依然注意点。
- **Connection Pooling:** サーバーレス関数からの接続数爆発を防ぐため、SupabaseのSupavisor（PgBouncer後継）とPrismaの`pgbouncer=true`設定の組み合わせが実質必須になっている。
- **Realtime + Prisma の併存:** Supabase Realtimeで直接購読する部分とPrismaで書き込む部分が分離しがちなため、型安全性を保つにはPrismaの生成型をRealtimeペイロードにも共有する設計が推奨される。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデル成熟:** WASM Component Model (WASI Preview 2) が主要ランタイム(wasmtime, wasmer)で安定運用レベルに達し、Rustクレートを言語非依存の再利用可能コンポーネントとして配布できるようになった。マイクロフロントエンドやプラグインアーキテクチャでの採用を検討する価値がある。

- **SIMD/マルチスレッド標準化の恩恵:** WASM SIMDとthreads(共有メモリ)proposalがブラウザ・サーバー双方で広くサポートされ、Rustの`std::simd`やrayonとの組み合わせで画像処理・暗号化・ML推論系の処理がネイティブの70-90%程度の速度に近づいている。

- **バイナリサイズ最適化がボトルネック化:** 機能が増えるほどwasmバイナリが肥大化しやすく、`wasm-opt`、`cargo-contract`的なtree-shaking、`no_std`構成の活用が実運用上のパフォーマンス差を左右する。弊社の初期ローディング速度を重視するなら最初から最小構成を意識すべき。

- **サーバーサイドWASM(Wasm on Edge)の普及:** Cloudflare Workers/Fastly Compute等のエッジランタイムでRust+WASMがコールドスタート数msレベルを実現し、サーバーレスでのレイテンシ面でJS/V8ベースより優位になりつつある。引越し費用計算のような軽量API処理をエッジで動かす選択肢として有望。

- **デバッグ・プロファイリング環境の改善:** DWARF対応のソースマップやwasm向けプロファイラ(`twiggy`, Chrome DevToolsのwasm統合)が進化し、以前ネックだった「ブラウザ上でのRustコードデバッグ」の難易度が大幅に下がった。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分をストリーミングする構成がデフォルトパターンに。`loading.tsx`と`Suspense`境界の設計精度がLCP改善の鍵になる。

- **Server Actions のセキュリティ強化:** `"use server"`関数が実質的に公開APIエンドポイントになるため、Zodによる入力検証とレート制限を各Actionに必須化する運用が標準化してきている。特に認証・決済系Actionでは認可チェックを関数先頭で明示する実装が推奨される。

- **キャッシュ戦略の明示化:** `fetch`のデフォルトキャッシュ挙動が変わったことで、`cacheLife`/`cacheTag`を使った明示的なキャッシュ制御（`use cache`ディレクティブ）が主流に。意図しないキャッシュ漏れ・陳腐化を防ぐため、データ更新パスごとに再検証戦略を文書化する必要がある。

- **Route Groups + Parallel Routes によるレイアウト分離:** `(group)`構文と`@slot`を組み合わせ、ダッシュボード系UIでモーダル・サイドパネルをURL状態として管理するパターンが定着。本プロジェクトの`properties/`や`account/`配下でも、詳細モーダルをインターセプトルート化すると戻るボタン対応が自然になる。

- **Client Component境界の最小化:** `"use client"`境界を葉(leaf)コンポーネントまで押し込み、フォームや認証コンテキストなどの状態を持つ部分だけをクライアント化する設計が改めて重視されている。バンドルサイズとTTIの両方に直結するため、`src/components/`配下のコンポーネント分割時にサーバー/クライアント境界を都度見直す価値がある。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化:** V8 isolateベースのEdge Functionsは2026年時点でコールドスタートが1ms未満まで最適化され、Node.js Runtimeとの差がほぼ解消。ただし依存バンドルサイズが大きいと依然影響するため、tree-shakingと動的importの徹底が重要。
- **Streaming SSRとの統合強化:** Partial Prerendering (PPR) が標準化され、Edge上で静的シェルを即時配信しつつ動的部分をストリーミングする構成がデフォルトパターンに。TTFBを犠牲にせずパーソナライズを実現できる。
- **リージョン選択の自動最適化:** `Vercel Edge Config` と地理的ルーティングが連携し、ユーザー近接リージョンへの自動フェイルオーバーが強化。グローバル展開時の手動リージョン指定が不要になるケースが増えている。
- **Edge Middlewareのコスト最適化:** 実行時間課金モデルの見直しにより、Middlewareでの重い処理（画像変換・認証検証等）を避け、必要最小限のルーティング判断に絞る設計が推奨される。
- **オブザーバビリティの標準装備:** OpenTelemetry連携がEdge Runtimeに標準統合され、分散トレーシングがコード変更なしで有効化可能に。パフォーマンス劣化の早期検知がしやすくなった。

### 10. TypeScript type safety patterns 2026

- **型レベルプログラミングの実用化:** TypeScript 5.x系で導入された`const`型パラメータやテンプレートリテラル型の進化により、ランタイムバリデーションなしでAPIレスポンスの形状を静的に保証できる範囲が広がっている。sumitsugiでは`'draft' | 'public'`のようなUnion型の網羅性チェック（`satisfies`演算子併用）が特に有効。

- **`satisfies`演算子によるZodスキーマとの統合:** Zodで定義したスキーマから`z.infer`で型を導出し、さらに`satisfies`で意図した構造と一致させることで、システム境界（APIリクエスト/レスポンス）での型安全性とランタイム検証を一元化できる。標準化ルールにある「Zodスキーマ必須」との相性が良い。

- **Branded Types（名前付き型）でID混同を防止:** `PropertyId`と`UserId`のような一見同じ`string`型でもBrand型で区別することで、コンパイル時にID取り違えバグを検出できる。物件管理のようにエンティティIDが多いドメインでは投資対効果が高い。

- **Discriminated Unionの徹底とexhaustiveness check:** `status: 'draft' | 'public'`のような状態分岐では、`switch`文の`default`に`never`型チェックを置くことで、将来ステータスが追加された際にコンパイルエラーで検知できる。標準化ルールの「Union型変更時は全箇所grep」を型システム側からも補強する。

- **型安全なルーティング/フォーム:** Next.js App Router + `next-safe-navigation`的なパターンや`react-hook-form`+Zodの組み合わせにより、ページ遷移パラメータやフォーム入力の型不整合を実行前に検出するのが2026年のデファクト。認証・決済など機微な入力を扱う本プロジェクトのフォームには優先適用すべき。
