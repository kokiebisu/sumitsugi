# CTO Knowledge - 2026-04-24

## Daily Update (2026-04-24)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを劇的に削減できるRSCをデフォルト選択とし、`'use client'`は本当に必要な箇所のみに限定する設計原則が2026年の標準となっている。

- **Partial Prerendering (PPR) の本番投入:** 静的シェルと動的コンテンツを同一ルートで混在させるPPRが安定版に達し、TFBTとLCPの両立が実現可能になった。`experimental.ppr`を有効化してストリーミングSuspenseと組み合わせるのが定石。

- **`next/image` + `next/font` の最適化を省略しない:** LCPの最大要因である画像とフォントのCLS/LCPへの影響は依然大きく、`priority`属性とサイズ指定の適切な設定を自動チェックするCIルールを入れることを推奨する。

- **Server Actions のバンドル汚染に注意:** Server Actionsが増えるとクライアントへの型情報漏洩やバンドル肥大化が起きやすい。`'use server'`ファイルは専用ディレクトリに集約し、`import` の方向を一方向に保つアーキテクチャが重要。

- **Turbopack をデフォルトに移行:** Next.js 15以降でTurbopackがstableとなり、大規模プロジェクトでのHMR速度が従来比5〜10倍改善される。`next dev --turbo`から`next dev`（デフォルト）への移行を完了させ、webpack独自プラグインへの依存を棚卸しするタイミング。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Prerendering（PPR）の本格普及:** Next.js 15以降でPPRが安定化し、静的シェルと動的ストリーミング部分を1リクエストで配信するパターンが標準化。TTFB最小化と動的コンテンツの両立が実現しやすくなった。

- **ポイント2: Suspense境界設計がアーキテクチャの核心に:** RSCストリーミングの効果はSuspense境界の粒度で決まる。粗すぎると遅延が集約され、細かすぎるとウォーターフォールが発生するため、データ依存グラフに基づいた境界設計レビューが必須となっている。

- **ポイント3: Server Actions + optimistic UIの組み合わせが主流に:** `useOptimistic`とServer Actionsの連携により、追加のAPIエンドポイントなしでフォームや状態変更のUXが向上。クライアント/サーバー境界を意識した設計コストが低減した。

- **ポイント4: キャッシュ戦略の複雑化に注意:** `fetch`キャッシュ・`unstable_cache`・Route Segment Configが混在し、意図せずキャッシュされる/されないバグが増加傾向。キャッシュの明示的なタグ管理（`revalidateTag`）とモニタリングが運用上の重要課題になっている。

- **ポイント5: Edgeランタイムとの相性が改善:** CloudflareやVercel EdgeでのRSCストリーミングサポートが成熟し、グローバル低レイテンシ配信が現実的な選択肢に。ただしNode.js専用APIへの依存がEdge移行のボトルネックになるため、依存関係の精査が先決。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全性の標準化:** 2026年においてtRPCはフルスタックTypeScriptプロジェクトでのデファクトになりつつあり、コード生成不要で型安全なAPIを実現できる点が、REST/GraphQLの複雑さに疲れた開発チームに刺さっている。

- **GraphQLは大規模・マルチクライアント向けに特化:** BFF（Backend for Frontend）パターンの普及により、GraphQLは「全部入り」から「複数クライアント（Web/Mobile/Partner API）が異なるデータ形状を必要とする場合」に特化するポジションに落ち着きつつある。

- **RESTはシンプルさと相互運用性で依然として主役:** 外部公開APIやマイクロサービス間通信では、OpenAPI 3.1 + TypeScriptコード生成（`orval`, `openapi-typescript`）の組み合わせが成熟し、型安全性の面でtRPCに近い開発体験を実現できる。

- **Server Actions（Next.js）がtRPCの領域を浸食:** App RouterのServer Actionsが安定化したことで、Next.jsプロジェクトではtRPCすら不要になるケースが増えており、APIレイヤーの「消去」という方向性が現実的になっている。

- **プロトコル選定の判断軸は「チーム境界」:** 同一チームがフロント/バック両方を触るならtRPC or Server Actions、チームが分かれる・外部公開するならREST、複数クライアントが複雑なデータ要求を持つならGraphQL、という使い分けが2026年の実用的な指針。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジの標準ランタイムに:** V8アイソレートに加えWasmが主流となり、言語非依存でコールドスタートほぼゼロのエッジ関数が実現。RustやGoで書いたロジックをそのままCDNエッジで動かすユースケースが急増している。

- **エッジでのAI推論が本番水準へ:** 量子化LLMや小型モデル（1〜7B）のエッジ実行が実用化され、レイテンシ敏感なユースケース（リアルタイム翻訳・パーソナライズ）でクラウドラウンドトリップを排除できるようになった。

- **ステートフルエッジの台頭:** Cloudflare Durable ObjectsやFastly Compute@Edgeのキー・バリューストアが成熟し、「エッジはステートレス」という前提が崩れつつある。セッション管理やカート処理をエッジで完結させるアーキテクチャが現実的になった。

- **オブザーバビリティの整備が急務:** エッジノードが数百拠点に分散する分、分散トレーシング（OpenTelemetry）の導入なしに障害の根本原因特定が困難になる。エッジ固有のコールドスタート頻度やリージョン別エラー率の可視化を設計段階から組み込むべき。

- **ベンダーロックインリスクの再評価:** Vercel/Cloudflare/Fastlyの独自APIへの依存が深まっており、WinterTC（旧WinterCG）標準への準拠度を選定基準に加えることで移行コストを抑制できる。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準採用:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の主流となり、フィッシング耐性と利便性を両立。主要プラットフォームのサポートが成熟した今、新規システムではパスワードを廃止する設計が推奨される。

- **MFAの必須化とリスクベース認証の組み合わせ:** 静的なMFAだけでなく、ログイン文脈（デバイス・地域・行動パターン）を評価するアダプティブ認証が標準になりつつある。高リスク操作のみ追加認証を要求することでUXとセキュリティを両立できる。

- **セッション管理の短命化とトークンローテーション:** アクセストークンの有効期限を15分以内に抑え、リフレッシュトークンの自動ローテーションを徹底することでトークン漏洩時の被害を最小化。特にJWTをステートレスに使う場合は失効メカニズムの設計が必須。

- **サプライチェーン攻撃への対策（依存ライブラリの監視）:** 認証ライブラリへの悪意ある改ざんが増加しており、`npm audit` / `bun audit` の自動実行と SBOMの管理がCI/CDに不可欠。特に認証フロー周辺のサードパーティコードは定期的なピンニングとハッシュ検証が推奨される。

- **ゼロトラスト前提のセッション継続検証:** 「一度認証したら信頼する」モデルを廃止し、各リクエストでデバイス整合性・ネットワーク文脈を継続評価するアーキテクチャが主流に。特にバックエンドAPIはJWT検証だけでなく、異常検知と組み合わせた多層防御を設計段階から組み込むべき。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のEdge Runtime対応:** Prisma AccelerateによるEdgeデプロイが本格化し、Next.js App RouterのServer Actionsと組み合わせたコネクションプーリングが標準パターンになっている。Cold startの問題をAccelerate側で吸収できるため、Vercel/Cloudflare Workers構成での採用障壁が大幅に下がった。

- **Supabase の Row Level Security (RLS) 設計が勝負どころ:** Supabaseの認証とRLSを適切に設計すれば、バックエンドAPIレイヤーを薄くできるが、複雑なポリシーはクエリパフォーマンスに直撃する。`EXPLAIN ANALYZE`でRLSポリシーのコストを定期計測し、インデックス設計とセットで管理することが必須。

- **Supabase Realtime + Prismaの併用パターン:** Prismaでの書き込みとSupabase Realtimeのサブスクリプション購読を組み合わせる構成が増えているが、`postgres_changes`チャンネルはテーブル単位のため、複雑なJOINが必要なリアルタイムビューはDB ViewとRLSで解決するのが現実解。

- **型安全性の一気通貫:** Supabaseの`supabase gen types typescript`とPrismaのtype generationを二重管理するコストは高い。2026年時点ではPrismaをORM層に統一し、Supabase SDKはAuth・Storage・Realtimeのみに絞る分業パターンがメンテナビリティの面で優勢。

- **マイグレーション戦略の統一:** `prisma migrate`とSupabase Migrations（`supabase/migrations/`）は競合しやすい。本番環境では`prisma migrate deploy`をCI/CDに組み込み、Supabase Dashboardからの直接DDL変更を禁止するガバナンスルールを設けることで、スキーマのドリフトを防ぐ。

### 7. WebAssembly Rust performance 2026

- **WASM GC と線形メモリの共存:** 2025〜2026年にかけてWASM GC提案が主要ブラウザで安定化し、RustのGCレスモデルと組み合わせることで、メモリ効率と予測可能なレイテンシを両立するアーキテクチャが実用段階に入った。

- **SIMD・スレッド拡張の本格活用:** WASM SIMDとshared memoryが全主要ランタイムで標準化され、RustのSIMDクレート（`std::simd`）経由で画像処理・ML推論をネイティブ比95%以上のスループットで実現するプロダクション事例が増加している。

- **Component Modelによるインターオペラビリティ:** WASI Component Model（`wasm-bindgen`後継の`wit-bindgen`）が成熟し、RustコンポーネントをJS/Python/Goから型安全に呼び出せる。マイクロサービスのホットパスをRust WASMに置き換える構成がエッジ環境で主流化しつつある。

- **コールド起動の実質解消:** WASMネイティブコンパイル（Wasmtime・V8の最適化）により、Rustで書かれたWASMモジュールの起動時間がサブミリ秒台に到達。FaaSのコールド起動問題がアーキテクチャ上の制約でなくなりつつある。

- **デバッグ・プロファイリングツールの成熟:** DWARF over WASMとChrome DevToolsの連携が改善され、RustソースレベルのWASMデバッグが実用的に。`cargo-component`と組み合わせることで、開発者体験のギャップが大幅に縮小している。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点では、データフェッチはServer Componentsで完結させ、`'use client'`は本当にインタラクティブな境界にのみ付与するのが標準。クライアントバンドルサイズを劇的に削減できる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的ストリームを同一ルートで混在させるPPRが安定版に。`<Suspense>`境界の設計がパフォーマンスチューニングの核心になっている。

- **Server Actions によるAPI層の簡略化:** フォーム送信・データ変更は`use server`のServer Actionsで直接処理し、専用APIルートを書かないパターンが主流。ただしZodによる入力バリデーションは必須。

- **`cache()` / `unstable_cache` の使い分け:** リクエスト内メモ化には`React.cache()`、クロスリクエストのキャッシュには`unstable_cache`（またはその後継）を使い分けることで、データフェッチの重複排除とパフォーマンスを両立する。

- **Parallel Routes + Intercepting Routes でモーダルUX:** URLを維持しながらモーダルを表示する`@`スロット＋`(.)route`パターンが、SPAライクなUXをサーバー主体で実現する定番手法になっている。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Functionsは`Edge Runtime`上で動作するため、Node.js互換性の制約（`fs`モジュール非対応など）を事前に把握し、`@vercel/edge`の最新APIを活用することでコールドスタートを最小化できる。

- **ポイント2:** Fluid computeの導入により、Edge FunctionsとServerless Functionsの境界が曖昧になりつつある—リクエストパターンに応じて`export const runtime = 'edge'`と`nodejs`を使い分ける戦略的判断が重要。

- **ポイント3:** KVストア（Vercel KV）やEdge Configとの組み合わせで、フィーチャーフラグやA/Bテストをゼロレイテンシで配信可能—データベースラウンドトリップを排除した低レイテンシアーキテクチャが競争優位になる。

- **ポイント4:** Middleware（`middleware.ts`）はすべてのリクエストに適用されるため、重い処理をMiddlewareに置くとサイト全体のパフォーマンスに影響する—`matcher`設定で適用パスを厳密に絞り込むことがコスト最適化の鍵。

- **ポイント5:** WebAssembly（WASM）のEdge Functions上でのサポートが成熟しており、画像処理・暗号化・パーサー処理などCPU集約タスクをエッジで実行可能—Next.jsとの統合では`next.config.js`の`experimental.serverComponentsExternalPackages`設定に注意が必要。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の標準活用:** TypeScript 4.9以降の `satisfies` が2026年では必須パターンとなり、型推論を維持しつつ型チェックを強制できるため、`as` キャストの使用を大幅に削減できる。

- **Branded Types によるドメイン安全性:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded Typesが普及し、プリミティブ型の混同（ユーザーIDと注文IDを誤って渡すなど）をコンパイル時に防止する実装が主流になっている。

- **Template Literal Types の実用化:** APIルートや i18nキーなどを `type Route = `/api/${string}`" のように型定義することで、文字列操作の型安全性が飛躍的に向上し、ランタイムエラーをビルド時に検出できる。

- **`noUncheckedIndexedAccess` の有効化が必須:** `tsconfig.json` でこのフラグを有効にすることで配列・オブジェクトへのインデックスアクセスが `T | undefined` を返すようになり、実運用で最も多い `Cannot read property of undefined` 系バグを根絶できる。

- **Zod + `z.infer<>` によるスキーマ駆動開発:** バリデーションスキーマから型を自動導出するパターンが事実上の標準となり、型定義とバリデーションロジックの二重管理を排除しつつ、システム境界での安全性を保証している。
