## Daily Update (2026-09-19)

### 1. Next.js performance optimization 2026

## Next.js Performance Optimization 2026

- **ポイント1（Partial Prerendering の本格運用）:** Next.js 16ではPPRが安定版となり、静的シェルと動的コンテンツを1つのルートで共存させられる。物件一覧のような「検索フォームは静的・結果は動的」といった構成に適しており、初期表示速度とパーソナライズを両立できる。
- **ポイント2（React Compilerによる自動メモ化）:** React Compilerがデフォルト有効化される流れが進み、`useMemo`/`useCallback`の手動最適化が不要になりつつある。物件詳細ページの複雑なフィルタリングUIなど、再レンダリングコストが高いコンポーネントで特に効果が大きい。
- **ポイント3（Turbopackビルドの高速化）:** Turbopackが本番ビルドでも既定になり、開発体験だけでなくCI上のビルド時間短縮にも寄与する。うちのMVPローンチ前フェーズでは、頻繁なPRサイクルのCI待ち時間削減に直結する。
- **ポイント4（画像・アセットの適応的最適化）:** `next/image`の自動フォーマット選択（AVIF優先）とCDNエッジでのオンデマンド変換が主流化。物件写真が多いプラットフォームでは、LCP改善とデータ転送量削減の両面で費用対効果が高い。
- **ポイント5（Server Actionsのキャッシュ戦略成熟）:** Server Actions周りの再検証（`revalidateTag`など)がより細粒度化し、問い合わせフォームや内覧予約などの更新系処理でも部分的キャッシュ活用がしやすくなっている。過剰な全体再検証を避け、必要な箇所だけ更新するのが2026年のベストプラクティス。

### 2. React Server Components streaming 2026

- **Selective Hydration の高度化:** Next.js 16ではSuspense境界ごとのストリーミングが洗練され、優先度の高いUIコンポーネント（例：物件詳細の価格・CTA）を先にハイドレートし、コメント欄など優先度の低い部分を遅延させることで、体感速度（TTI）を大幅に改善できます。

- **サーバー/クライアント境界の設計が肝:** RSCでは「どこでdata fetchingするか」の設計ミスがバンドルサイズ肥大化を招くため、`'use client'`境界を極力末端コンポーネントに寄せ、Server Actionsでのフォーム処理（引越し費用計算など）をクライアントJSに含めない設計が重要です。

- **Partial Prerendering (PPR) との組み合わせ:** 静的シェル（物件一覧のレイアウト）を即座に配信しつつ、動的部分（在庫状況・価格変動）だけをストリーミングするPPRパターンが標準化しつつあり、CDNキャッシュ効率とパーソナライズの両立が可能になっています。

- **Waterfall防止のためのpreload戦略:** RSCストリーミングでもデータ取得の直列化（waterfall）は依然リスクで、`Promise.all`での並列fetchやReactの`cache()`関数を使ったリクエスト重複排除を徹底しないと、期待したパフォーマンス改善が得られません。

- **エラーバウンダリとストリーミングの相性:** ストリーミング中に発生したサーバーエラーが後から届くUXになるため、`error.tsx`とSuspense fallbackの設計を細かく分離し、ユーザーに「読み込み中」と「エラー」を正しく区別させるUI設計が必須です。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの台頭）:** TypeScriptフルスタック構成（Next.js等）ではtRPCがREST/GraphQLに代わる選択肢として定着し、スキーマ定義とクライアント型が自動同期されるため、API層のボイラープレートとドキュメント同期コストを大幅に削減できる。sumitsugiのようなNext.js App Router構成では、Server ActionsとtRPCの併用が型安全性とDXの両立に有効。

- **ポイント2（GraphQLは特定用途に収束）:** GraphQLは複数クライアント（Web/モバイル/パートナーAPI）が異なるデータ形状を要求する大規模プラットフォームで依然強いが、単一Webフロントエンド中心の中小規模プロダクトでは過剰投資になりやすく、2026年はREST/tRPCへの「揺り戻し」傾向が明確。

- **ポイント3（RESTはOpenAPI+コード生成で延命）:** RESTはOpenAPI 3.1とコード生成ツール（openapi-typescript等）の成熟により、外部公開APIや他言語クライアントとの連携が必要な場面（決済代行、外部連携）では依然デファクト標準。社内向けとパートナー向けでプロトコルを使い分けるハイブリッド構成が主流化。

- **ポイント4（BFF層の重要性）:** マイクロサービス化が進むほどBackend For Frontend層の必要性が増しており、モバイルアプリ対応や引越し費用計算など複数ドメインを横断する処理は、BFFで集約してからクライアントにtRPC/RESTで返す設計が保守性を高める。

- **ポイント5（型安全性とランタイム検証の両立）:** ZodなどのスキーマファーストなバリデーションをtRPC/REST双方の境界に統一適用することが標準化しつつあり、コンパイル時の型安全性だけでなく実行時の入力検証（特に決済・個人情報を扱うsumitsugiのようなサービス）まで一貫させる設計が求められている。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** Cloudflare WorkersやVercel Edge FunctionsでのLLM軽量推論（量子化モデル、Wasmベースの推論エンジン）が2026年には一般化しており、ユーザーに最も近いロケーションでパーソナライズ処理が可能になっている。物件検索のレコメンドなど低レイテンシが必要な機能に応用できる。

- **コールドスタート問題のほぼ解消:** V8 isolateベースのランタイムとプリウォーミング技術の進化で、エッジ関数のコールドスタートは数ミリ秒レベルまで短縮された。Next.js 16のEdge Runtimeを使えば、リストページのSSRをオリジンサーバーレスより高速に配信できる。

- **エッジデータベース／KVの成熟:** Cloudflare D1、Turso、PlanetScale等の分散SQLiteレイヤーがリージョン跨ぎのレプリケーションを自動化し、読み取りをエッジ側で完結できるように。物件情報のような「読み取り多・更新少」なデータには特に相性が良く、DBレイテンシがボトルネックになりにくい。

- **費用対効果とロックインのトレードオフ:** 従量課金モデルは低トラフィック期には有利だが、スケール時にはコンテナベースの専用インスタンスより割高になるケースが増えている。ベンダー固有APIへの依存も強まっているため、ベータローンチ段階のsumitsugiではまず標準Fetch APIベースの実装に留め、将来の移行コストを抑えるのが得策。

- **オブザーバビリティの分散化への対応:** エッジで処理が分散するほどトレーシングが難しくなるため、OpenTelemetryのエッジ対応エクスポーターが2026年の必須ツールに。本番導入前に分散トレーシング基盤を整えておかないと、障害時の原因特定が著しく困難になる。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** 2026年時点でパスワードレス認証（Passkey）が主流化しており、フィッシング耐性のある公開鍵暗号方式を採用することで、資格情報の漏洩リスクを根本的に排除できる。

- **多層防御としてのリスクベース認証:** IPレピュテーション・デバイスフィンガープリント・行動パターンを組み合わせたアダプティブ認証を導入し、ログイン時の摩擦を最小化しつつ異常なアクセスのみ追加検証を要求する設計が推奨される。

- **セッション管理の厳格化:** JWTなどのトークンは短命化し、リフレッシュトークンのローテーション・失効リスト管理を徹底することで、トークン窃取時の被害範囲を限定する。

- **APIレベルでのレート制限とゼロトラスト:** 認証エンドポイントへの総当たり攻撃対策として、IPベースだけでなくアカウントベースのレート制限を実装し、内部サービス間通信も含めて「信頼しない・常に検証する」ゼロトラスト原則を徹底する。

- **監査ログとインシデント対応の自動化:** 認証失敗・異常ログインパターンをリアルタイムで検知し、Slack等への自動アラートとアカウントロックを組み合わせることで、侵害の早期発見と被害最小化を実現する。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMの進化:** Prisma 6以降はRust非依存のクエリエンジン（TypeScript製）へ移行が進み、コールドスタートが大幅に高速化。Edge Runtime（Vercel Edge、Cloudflare Workers）との親和性が高まり、Next.js 16のApp Routerと組み合わせたサーバーコンポーネントでの直接クエリ実行がより現実的な選択肢になっている。

- **SupabaseのPostgres拡張活用:** pgvector（埋め込み検索）、pg_cron（定期ジョブ）、Realtime（WebSocket購読）などのネイティブ拡張が成熟し、追加インフラなしで「物件検索のセマンティック検索」や「メッセージのリアルタイム通知」を実装できる。sumitsugiのような住み継ぎマッチングでは、物件×ユーザーの類似度検索にpgvectorを使う設計が有力。

- **RLS（Row Level Security）とPrismaの併用パターン:** SupabaseのRLSとPrismaのマイグレーション管理を両立させる場合、Prisma側はスキーマ定義とマイグレーションに専念し、認可ロジックはRLSポリシーに寄せるのがベストプラクティス。アプリ層の権限チェックとDB層のRLSを二重に持つと保守コストが上がるため、`draft`/`public`のようなステータス制御はRLSポリシーで一元化すべき。

- **コネクションプーリングの重要性:** Next.jsのサーバーレス/エッジ環境ではDB接続数が急増しやすいため、SupabaseのPgBouncer（Transaction mode）とPrismaの`directUrl`/`url`の使い分けが必須。マイグレーション時は直接接続、ランタイムはプーリング接続、という設定ミスがローンチ後の障害要因になりやすい。

- **型安全なE2E開発フロー:** PrismaのスキーマからTypeScript型を自動生成し、SupabaseのGenerated Types（`supabase gen types typescript`）と組み合わせることで、DB→API→フロントまでの型の一貫性を保てる。物件ステータスのようなunion型変更時は、この型生成を再実行しないと`standards.md`が指摘する「union型変更時の全箇所grep漏れ」が発生しやすい。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデルの成熟:** WASM Component ModelとWASIプレビュー2の普及により、Rust製WASMモジュール間の連携がFFIオーバーヘッドなしで可能になり、マイクロサービス的な構成でも実用的な性能が出せるようになっています。
- **SIMDとマルチスレッドの標準化:** WASM SIMD命令とスレッド（SharedArrayBuffer経由）がブラウザ・ランタイム双方で標準サポートされ、Rustの`std::simd`やrayonクレートと組み合わせることで画像処理・暗号化などCPUバウンド処理がネイティブに近い速度で動作します。
- **バイナリサイズ最適化の重要性:** `wasm-opt`や`wee_alloc`に加え、Rust 1.7x系のコード生成改善により、リリースビルドのサイズ削減と起動時間短縮がパフォーマンスKPIとして重視されるようになっています（初回ロード体験に直結）。
- **サーバーサイドWASM（Wasmtime/Wasmer）の台頭:** RustバックエンドでWASMをプラグインサンドボックスとして使うパターンが一般化し、コールドスタートがコンテナより大幅に速く、マルチテナントSaaSのアイソレーション用途で採用が進んでいます。
- **JIT/AOTハイブリッドの進化:** Cranelift等のコード生成基盤の改善で、WASMのインタプリタ実行とネイティブ実行のギャップが縮小しており、Rust→WASMのユースケースが「軽量化のための妥協」から「本番採用に足る選択肢」へシフトしています。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 15〜16でPPRが安定版となり、静的シェルを即座に返しつつ動的部分をストリーミングで後追い表示するパターンが主流に。ダッシュボードや物件詳細ページのように「一覧は静的・在庫状況は動的」といった混在UIで特に効果を発揮する。

- **Server Actionsによるフォーム処理の一本化:** API Routeを経由せずServer Actionsで直接ミューテーションを行う設計が定着し、`useActionState`とZodバリデーションを組み合わせた型安全なフォーム実装が標準パターンに。問い合わせ・申込フォームなどのボイラープレートが大幅に削減できる。

- **`use cache`ディレクティブによるキャッシュ制御の明示化:** これまで暗黙的だったfetchキャッシュ挙動が、関数単位で`use cache`を明示する形に移行。キャッシュタグ（`cacheTag`/`cacheLife`）と組み合わせることで、物件データ更新時の再検証タイミングを細かく制御できる。

- **Server/Client Componentsの境界設計がパフォーマンスの鍵:** "Client Componentは葉（leaf）に留める"という原則が定石化。インタラクティブなUIパーツ（フィルタ、モーダル等）だけをクライアント化し、データ取得ロジックはServer Componentに寄せることでJSバンドルサイズを最小化する。

- **Route Handlersよりも直接DBアクセス+Server Componentsが優勢:** 内部向けデータ取得ではAPI層を挟まず、Server Component内で直接ORM/DBクエリを実行するパターンが増加。外部公開APIが不要なプロジェクト（社内ツールやMVP）では開発速度とレイテンシの両面で有利。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約を前提にした設計:** Node.js APIが使えないEdge Runtime特有の制約（一部npmパッケージ非対応、ファイルシステムアクセス不可）を早期に把握し、認証・リダイレクト・A/Bテストなど軽量なロジックのみをEdgeに配置するのが定石。重い処理はNode.js Functionsに残す判断が重要。

- **コールドスタート最小化とバンドルサイズ削減:** Edge Functionsはリージョン分散・低レイテンシが売りだが、依存関係が肥大化するとバンドルサイズ上限（1-4MB程度）に抵触しやすい。tree-shakingを意識した最小限のimportと、不要なpolyfillの除去でコールドスタートを抑える。

- **ミドルウェアの実行コストに注意:** `middleware.ts`は全リクエストで実行されるため、matcherで対象パスを絞り込まないとコスト・レイテンシが無駄に増える。静的アセットや不要なパスを`config.matcher`で除外するのが基本のベストプラクティス。

- **キャッシュ戦略との併用:** Edge Functionsだけで高速化を狙うより、Vercelの`ISR`やData Cache、`fetch`のキャッシュタグと組み合わせることでオリジンへのアクセス自体を減らす方が費用対効果が高い。特に住人の物件検索・一覧表示のような読み取り中心の画面はISR併用が有効。

- **観測性（Observability）の確保:** Edge環境はデバッグがしづらいため、Vercelの`waitUntil`を使った非同期ロギングや、OpenTelemetry対応のトレーシングを組み込んでおくと本番障害時の切り分けが早くなる。sumitsugiのような認証・決済導線ではこの観測性投資が特に重要。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x以降の`satisfies`演算子とconst型パラメータの組み合わせが標準化し、型推論を保ちながら過剰なアサーションを排除するパターンが定着している。sumitsugiでも`data.ts`のようなマスタデータ定義に活用すると型の取りこぼしを防げる。
- **ポイント2:** ZodなどのスキーマファーストバリデーションからTypeScriptの型を自動生成する「Schema-to-Type」パターンがデファクトになり、システム境界（API入力・フォーム）での二重定義を防止できる。standards.mdの「Zodスキーマ必須」方針と直接合致する。
- **ポイント3:** ブランド型（Branded Types）による`PropertyId`と`UserId`のような同一プリミティブ型の誤用防止が、大規模TypeScriptプロジェクトの標準プラクティスになりつつある。`'draft' | 'public'`のようなUnion型のtypoバグも同様のパターンで防げる。
- **ポイント4:** `exactOptionalPropertyTypes`や`noUncheckedIndexedAccess`など厳格なtsconfigフラグの採用が2026年のベストプラクティスとして広がっており、`undefined`の握りつぶしによる実行時エラーを型検査段階で検出できる。
- **ポイント5:** テンプレートリテラル型とDiscriminated Unionを組み合わせたルーティング・状態管理（例: 物件ステータスの`draft`→`public`遷移）が、状態機械を型レベルで表現する主流パターンとして普及している。
