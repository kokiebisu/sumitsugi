# CTO Knowledge - 2026-10-03

## Daily Update (2026-10-03)

### 1. Next.js performance optimization 2026

- **Turbopackのデフォルト化とビルド高速化:** Next.js 16ではTurbopackが本番ビルドでも安定版となり、Webpack比で大幅なビルド時間短縮が実現。大規模な`src/app`配下でも差分ビルドが効くため、CI上の`bun run build`時間の監視指標にもなる。

- **Partial Prerendering (PPR) の本格運用:** 静的シェルを即時配信しつつ動的部分のみストリーミングする手法が標準化しつつあり、物件一覧(`properties/`)のような「静的な骨組み＋動的な在庫データ」構成のページでTTFBを大きく改善できる。

- **React Server Components前提のデータフェッチ最適化:** クライアントバンドルを減らすため、`src/lib/data.ts`のようなデータ取得ロジックはServer Component内に閉じ込め、`use client`境界を最小限にすることがパフォーマンスのベストプラクティスとして定着。

- **キャッシュ戦略の明示化（`cacheLife`/`cacheTag`):** Next.js 16で導入された明示的キャッシュAPIにより、「いつ再検証すべきか」をコードで宣言できるようになった。物件ステータス変更（`draft`→`public`）のような更新頻度の低いデータと、在庫のようなリアルタイム性が必要なデータを分けてキャッシュ設計することが重要。

- **画像・フォント最適化とCore Web Vitals計測の継続的モニタリング:** `next/image`の自動フォーマット変換とLCP計測をCIパイプラインに組み込み、リリースごとに回帰がないか確認する運用が2026年のベストプラクティス。ベータローンチ前の今こそ計測基盤を整えるべきタイミング。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化が進展:** React Server Componentsの`<Suspense>`境界を活用したストリーミングが、Next.js 16で安定稼働するプリミティブとなり、初期表示（TTFB）を犠牲にせず段階的にUIを届けられるようになった。sumitsugiの物件一覧・詳細ページのような非同期データ依存の強いUIで優先的に採用すべき。

- **Partial Prerendering(PPR)との組み合わせが主流に:** 静的シェルを即座に返しつつ、動的部分だけをストリーミングで後から埋める設計がデフォルト化。物件検索結果や予約状況など「ほぼ静的だが一部だけ動的」なページで、ビルド時レンダリング＋ストリーミングのハイブリッドが最も費用対効果が高い。

- **クライアントバンドルの肥大化抑制が引き続き最重要課題:** RSCはサーバー側で完結するコンポーネントを増やせる反面、`'use client'`境界の設計を誤るとかえってバンドルが肥大化する。インタラクティブなフォーム（お問い合わせ・予約）だけをクライアント化し、表示系は極力サーバーコンポーネントに留めるのが鉄則。

- **キャッシュ戦略の複雑化とデバッグ困難性:** ストリーミング+RSCキャッシュ（Data Cache / Router Cache）が絡み合い、本番環境特有のキャッシュ不整合バグが増えている。CIにキャッシュ無効化パターンのE2Eテストを組み込み、ステージングで本番相当のキャッシュ設定を再現することが必須。

- **エラーバウンダリとストリーミングの両立:** ストリーミング中に発生したサーバーエラーのハンドリングがUXを左右する重要ポイントになっており、`error.tsx`とSuspense境界を細かく分割し、一部コンポーネントの失敗が画面全体をブロックしない設計が2026年のベストプラクティスとして定着している。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはフルスタックTypeScriptモノレポ（Next.js App Router前提）において事実上の標準になりつつあり、スキーマ定義とランタイム検証を一体化できるためZodとの組み合わせでクライアント・サーバー間の型安全性を無コストで担保できる。sumitsugiのようにフロント・バックが同一リポジトリの場合、GraphQLのリゾルバ層を持たずに済み開発速度が上がる。
- **ポイント2:** GraphQLは複数クライアント（モバイル・Web・外部パートナー）が異なる粒度でデータを取得する必要がある場合に依然強いが、単一フロントエンドのみのプロダクトではオーバーエンジニアリングになりやすく、2026年はBFF（Backend for Frontend）層としての限定利用が主流。
- **ポイント3:** RESTは依然として外部公開API・Webhook・サードパーティ連携（決済、本人確認サービスなど）のデファクトであり、OpenAPI 3.1 + JSON Schemaで契約駆動開発（Contract-First）をするパターンが定着している。内部通信はtRPC、外部公開APIはRESTという使い分けが2026年のベストプラクティス。
- **ポイント4:** Server Actions（Next.js）の普及により「API層自体を薄くする」設計が増えており、CRUD中心の操作はtRPC/Server Actionsに寄せ、重い非同期処理や外部連携のみを明示的なAPIエンドポイントに切り出す設計が、保守コストとパフォーマンスの両面で有利。
- **ポイント5:** 認証・入力検証はAPI方式に関わらずZodスキーマをAPI境界に集約するのが鉄則で、tRPCのinput schema・REST のミドルウェアバリデーション・GraphQLのリゾルバ引数検証のいずれでも同じZodスキーマを再利用することで、物件ステータス（`draft`/`public`）のようなUnion型の整合性をコードベース全体で保証できる。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** Cloudflare Workers、Deno Deploy、Vercel Edge Functionsが共通のWeb標準API（Fetch, Streams）に収束し、ベンダーロックインが大幅に軽減されている。マルチプラットフォーム対応のコードを書きやすくなった。

- **コールドスタートの実質ゼロ化:** V8 isolateベースの実行環境が主流となり、コンテナ型サーバーレスと比べて起動遅延がミリ秒単位まで縮小。レイテンシが重要なAPI（認証・リダイレクト処理など）をエッジに移す設計が標準的になってきている。

- **エッジでのデータレイヤー進化:** Cloudflare D1、Turso、PlanetScaleなどエッジネイティブなSQLiteベースDBが成熟し、読み取りレプリカをユーザー近接ノードに配置するパターンが一般化。グローバル分散でもレイテンシを抑えた一貫性のあるデータアクセスが実用段階に入った。

- **AI推論のエッジシフト:** 小型LLM・量子化モデルをエッジで直接実行する動きが加速し、プロンプト前処理やルーティング判断をエッジ側で行うことでオリジンへのリクエスト数とコストを削減するアーキテクチャが増えている。

- **コスト・運用面の落とし穴:** リクエスト課金モデルは安価に見えるが、エッジ特有の制約（実行時間上限、メモリ制限、ベンダー固有API）によりテスト・デバッグの難易度が上がる点は要注意。本番導入前にローカルエミュレーション環境での十分な検証が必須。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証がついに主流化し、フィッシング耐性のあるパスキーがログインのデフォルトになりつつある。sumitsugiのような個人情報を扱うプラットフォームでは、早期導入がセキュリティとUX両面で競争優位になる。

- **多層防御としてのセッション管理:** 認証後のセッショントークンの取り扱い（httpOnly Cookie、短命トークン＋リフレッシュローテーション）が、ログイン方式自体と同じくらい重要視されている。トークン漏洩によるセッションハイジャックが依然として主要な攻撃経路。

- **AIを使った異常検知:** ログイン試行パターンや不正アクセスをリアルタイムで検知するML駆動の不正検知が標準装備になりつつあり、特に物件取引のような高額トランザクションを扱うサービスでは必須要件になりつつある。

- **ゼロトラスト前提のAPI設計:** 「ログイン済み＝信頼できる」ではなく、リクエストごとに権限を再検証する設計が主流。特にdraft/public状態の物件データなど、ロールベースのアクセス制御（RBAC）をAPI境界で厳格に実施する必要がある。

- **サプライチェーン経由の認証リスク:** OAuth連携先やSDKの脆弱性を突いた間接的な認証バイパスが増加傾向。外部依存（決済・本人確認サービス等）を統合する際は、依存先自体のセキュリティ姿勢の継続的な監査が不可欠。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMのRustフリー化が本格普及:** Prisma 6以降の新クエリエンジン（TypeScript/WASMベース）により、Vercel EdgeやCloudflare Workersなどのエッジランタイムでも軽量に動作するようになった。本プロジェクトのNext.js 16 App RouterでEdge Functionsを使う場合、ドライバアダプタ（`@prisma/adapter-pg`等）の導入検討が有効。

- **Supabase + Prisma併用時のコネクションプーリングが鍵:** サーバーレス環境ではPostgresの直接接続数制限にすぐ当たるため、SupabaseのSupavisor（内蔵プーラー）経由でのTransaction mode接続、またはPrisma Accelerateのキャッシュ付きプーリングを使うのが2026年のデフォルト構成になっている。

- **Row Level Security (RLS) を正とする認可モデル:** アプリ層（Prisma）だけでなくDB層（Supabase RLS）で二重に権限制御するハイブリッド構成が標準化。`seller`/`buyer`のようなロール分岐が多い本プロダクトでは、RLSポリシーをマイグレーションとして明示管理するとセキュリティレビューが通りやすい。

- **pgvectorによるAI機能の内製化:** Supabaseのpgvector拡張で物件検索の類似度マッチングやレコメンドをDB内で完結させる事例が増加。外部ベクトルDBを増やさずにPostgresだけでRAG/検索を実装できるため、運用コストと構成の複雑さを抑えられる。

- **スキーマ変更のブランチ運用:** Supabaseのデータベースブランチ機能とPrisma Migrateを組み合わせ、PRごとに本番同等のDBスナップショットでマイグレーションを検証するワークフローが一般化。`.worktrees`での並行開発が多いこのリポジトリとも相性が良い。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASI 0.3の普及により、コンポーネントモデルを使った言語間連携が標準化され、RustコンパイルのWASMモジュール間でゼロコピーなデータ共有が可能になってきている。パフォーマンス面では境界越えのオーバーヘッドが大幅に削減される。
- **ポイント2:** `wasm-bindgen`や`wasm-pack`のツールチェーンが成熟し、バンドルサイズ最適化（`wee_alloc`代替やLTO設定）がデフォルトで効くようになったため、クライアントサイドでの初回ロード時間がネイティブJS実装に近づいている。
- **ポイント3:** Wasmtime/WasmerなどのランタイムがJITからAOTコンパイルへの移行を進め、コールドスタート性能がサーバーレス環境（Cloudflare Workers, Fastly Compute）で改善され、Rust+WASMがエッジでの重い計算処理（画像変換、PDF生成など）に実用的になった。
- **ポイント4:** SIMD128とマルチスレッド（`wasm-bindgen-rayon`経由）のサポートがブラウザ・サーバー両方で安定し、RustのWASMモジュールで並列数値計算（画像処理、暗号処理）がネイティブの70-80%程度の速度を達成できるケースが増えている。
- **ポイント5:** sumitsugiのような物件情報サイトでは、PDF生成や画像最適化処理をRust+WASMに切り出すことで、Node.jsのシングルスレッド制約を回避しつつ、Vercel/Edge環境でのレイテンシを抑える選択肢として検討価値がある（ただしビルドパイプラインの複雑化とのトレードオフに注意）。

### 8. Next.js App Router patterns 2026

**ポイント1:** Partial Prerenderingが安定版となり、静的シェルと動的コンテンツを1つのルートで組み合わせられるようになった。初期表示速度とパーソナライズの両立が容易になり、ECやダッシュボード系ページで特に有効。

**ポイント2:** Server Actionsの採用が標準化し、APIルートを明示的に書かずにフォーム送信・ミューテーションを実装するパターンが主流に。ただし入力バリデーション（Zod等）とCSRF対策を怠るとセキュリティホールになりやすいため、境界での検証は引き続き必須。

**ポイント3:** `use cache`ディレクティブとCache Componentsにより、キャッシュ戦略がコンポーネント単位で宣言的に制御可能に。従来の`revalidate`設定だけに頼る実装から移行し、再検証タイミングを機能ごとに最適化するのがベストプラクティス。

**ポイント4:** React Server Components前提の設計が定着し、「何をクライアントに送るか」を意識したコンポーネント分割がパフォーマンスの肝に。`'use client'`境界を末端に押し出すほどバンドルサイズと初期表示が改善する。

**ポイント5:** ミドルウェアとルートハンドラーのエッジ実行が一般化し、認証・リダイレクト処理を地理的に近いエッジで完結させる構成が増加。ただしNode.js APIに依存するロジックはエッジランタイムで動かないため、実行環境の制約を早期に設計へ織り込む必要がある。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Vercel Edge FunctionsはV8 isolateベースでコールドスタートが数ms単位まで短縮されており、Node.js Runtimeではなく明示的にEdge Runtimeを指定することでTTFBを大幅に改善できる。ただしファイルシステムアクセスや一部npmパッケージの非対応には引き続き注意が必要。

- **ポイント2:** `next.config`でのPartial Prerendering (PPR)とEdge Middlewareの組み合わせが主流になりつつあり、認証チェックやA/Bテストのロジックをミドルウェア層でEdge実行することで、オリジンへのリクエスト数自体を削減できる。

- **ポイント3:** Edge上でのDBアクセスはコネクションプール枯渇が課題になりやすいため、Neon・PlanetScale・Upstash Redisなど「HTTPベース/サーバーレス対応」のデータ層を選定するのがベストプラクティス。本プロジェクトでもSupabase接続はEdge経由ではなくServer Actions/Node Runtime側に寄せる判断が無難。

- **ポイント4:** リージョン選択（特に`fra1`/`hnd1`など）をEdge Config経由で動的に制御し、ユーザーの地理的位置に応じてレイテンシを最適化する手法が一般化している。日本向けプロダクトであるsumitsugiでは東京リージョン(`hnd1`)固定よりも、画像・静的アセットはCDNキャッシュに任せ、Edge Functions自体は認証・リダイレクトなど軽量処理に限定するのが費用対効果が高い。

- **ポイント5:** Vercelの課金モデルがEdge Function実行時間とCPU時間ベースに変わってきているため、重い処理（PDF生成、画像変換など）をEdge上で行うとコスト増になりやすい。本番運用前にはルートごとにEdge/Node Runtimeの使い分けを明確化し、計測（Vercel Analytics）を前提にした設計判断が重要。

### 10. TypeScript type safety patterns 2026

- **型レベルプログラミングの実用化:** TypeScript 5.x以降のテンプレートリテラル型やconditional typesがランタイム検証（Zod等）と統合され、スキーマ定義から型を自動推論する`z.infer<typeof schema>`パターンが標準化。システム境界でのバリデーションと型安全性を1つの定義で両立できる。

- **`unknown`優先とtype narrowingの徹底:** `any`の使用を事実上禁止し、`unknown`+ユーザー定義type guard（`is`述語）でnarrowingする設計が主流。外部API/フォーム入力など信頼できない入力は必ずこの経路を通すことで、実行時エラーをコンパイル時に検出できる。

- **Discriminated Unionによる状態管理の厳格化:** `'draft' | 'public'`のようなstatusフィールドは単純なstring unionではなく、各状態に紐づくプロパティを含むdiscriminated unionとして設計し、`switch`の`exhaustiveness check`（`never`型での網羅性チェック）を組み合わせることで、新しい状態追加時の漏れをコンパイルエラーで検知できる。

- **Branded/Nominal Typesでのプリミティブ誤用防止:** `UserId`と`PropertyId`のような同じ`string`型でも意味が異なるIDは、branded typeで区別することで、関数呼び出し時の引数取り違えをコンパイル時に防止する実践が広がっている。

- **型とテストの責任分離の明確化:** 型チェック（`tsc --noEmit`）はビルドパイプラインに必須化され、ESLintやユニットテストでは検出できない型不整合（union型の値漏れなど）を型チェック単体で保証する運用が定着——「ビルドが通ること」自体をCIの必須ゲートとする考え方（本リポジトリの`Build Integrity`方針とも一致）。
