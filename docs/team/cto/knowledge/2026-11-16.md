# CTO Knowledge - 2026-11-16

## Daily Update (2026-11-16)

### 1. Next.js performance optimization 2026

- **ポイント1:** Partial Prerendering (PPR) が安定版となり、静的シェルと動的コンテンツを1つのルートで混在させられるため、TTFBを維持しつつパーソナライズ領域だけストリーミングできる。
- **ポイント2:** Turbopackがビルド・devの両方でデフォルト化され、大規模リポジトリでのHMR速度とプロダクションビルド時間が大幅短縮されるため、CI時間短縮にも直結する。
- **ポイント3:** `use cache`ディレクティブ（Cache Components）によりコンポーネント単位でのキャッシュ制御が明示的になり、意図しないフルページ再検証を避けやすくなった。
- **ポイント4:** React Server Components前提の設計が進み、クライアントバンドルサイズをComponent単位で可視化する`next build --analyze`系ツールの活用が重要になっている。
- **ポイント5:** 画像・フォント最適化はほぼ自動化済みのため、今のパフォーマンス差は「どこでサーバー/クライアント境界を切るか」というアーキテクチャ判断で決まる。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPPR(Partial Prerendering)がデフォルト挙動に近づき、静的シェルを即時配信しつつ動的部分をStreaming SSRで後追いさせる構成が標準パターンになっている。`loading.tsx`と`Suspense`境界の粒度設計がTTFBとLCPを大きく左右するため、物件詳細ページのような「基本情報は即表示、レビューや空き状況は後から流す」設計が有効。

- **ポイント2:** RSCペイロードのシリアライズコストがスケールのボトルネックになりやすく、サーバーコンポーネントからクライアントコンポーネントに渡すpropsを最小限に絞る（巨大な配列やオブジェクトをそのまま渡さない）設計が重要。本プロジェクトの`src/lib/data.ts`のような一覧データをRSCで直接フェッチする際は、必要なフィールドだけをシェイプしてから渡すべき。

- **ポイント3:** `use cache`ディレクティブ（Next.js Cache Components）が安定し、RSCレベルでの部分キャッシュとストリーミングを組み合わせることで、物件検索のようなフィルタ処理込みページでも初回表示を高速化できる。キャッシュキーの粒度設計（ユーザー依存データを含めない）を誤るとクロスユーザーでデータ漏洩するリスクがあるため要注意。

- **ポイント4:** エラーバウンダリとストリーミングの組み合わせでは、個々のSuspense境界ごとに`error.tsx`相当のフォールバックを用意しないと、1つのコンポーネントの失敗がページ全体のストリームを巻き込んで落とすケースがある。決済や認証など失敗が致命的な箇所は独立したエラーバウンダリで隔離すべき。

- **ポイント5:** Streaming SSRはSEO観点で検索エンジンのクロール挙動（JSが実行されない場合に非同期部分が見えない）に注意が必要で、重要なメタ情報（物件タイトル・価格など）は必ず初期シェル側でサーバーレンダリングし切ることを徹底すべき。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCのエンドツーエンド型安全性は、TypeScriptモノレポ（Next.js App Router + Bun構成のような本プロジェクト含む）では開発速度を大きく上げるが、クライアント/サーバーが別言語・別チームになる場合はスキーマ共有ができず恩恵が消えるため、採用は「同一言語スタックが続く前提」に強く依存する。

- **ポイント2:** GraphQLは依然モバイル/複数クライアント向けの柔軟なクエリに強いが、N+1問題やキャッシュ戦略の複雑さ、スキーマガバナンスの運用コストが高く、2026年の潮流としては「内部向けはtRPC、外部公開APIはREST or GraphQL Federation」のように用途で分ける混成アーキテクチャが主流になっている。

- **ポイント3:** RESTはOpenAPI 3.1 + JSON Schemaの成熟により、コード生成（型・クライアントSDK）の自動化が進み、「シンプルさ」と「型安全性」のギャップがtRPC登場前より縮まっている。外部パートナー連携や将来的な決済・外部弁護士対応が必要なsumitsugiのようなプロダクトでは、標準化され監査しやすいRESTが法務・セキュリティレビューの観点で有利。

- **ポイント4:** 2026年はAPI境界でのZodなどランタイムスキーマ検証と型生成の統合が当たり前になり、「型があるから安全」という思い込みが減った。入力検証はAPI設計方式（REST/GraphQL/tRPC）に関わらず必須という認識が標準化（本プロジェクトのstandards.mdの方針と合致）。

- **ポイント5:** sumitsugiのような小〜中規模チームでは、tRPC中心のAPI設計が最も生産的（型安全・ボイラープレート最小・Next.js App Routerとの統合が自然）。ただし将来的に外部パートナーAPIや公開APIが必要になった場合は、tRPCルーターの一部をRESTライクなpublic facadeでラップする二層構成を早めに検討すべき。

### 4. serverless edge computing 2026

- **ポイント1:** Cloudflare Workers・Vercel Edge・Deno Deployなどのエッジランタイムは2026年時点でV8 isolateベースの起動時間が1ms未満まで最適化され、コールドスタート問題が実質解消。レイテンシ要件の厳しいSSRやAPI Gatewayの前段処理に標準採用が進んでいる。

- **ポイント2:** エッジでの軽量LLM推論（量子化モデル・小型モデル）が普及し、パーソナライゼーションや簡易な意図分類をエッジ側で完結できるようになった。中央サーバーへのラウンドトリップを減らし、UXとコスト両面で優位。

- **ポイント3:** エッジとオリジンDB間の整合性管理（read-your-writes保証、キャッシュ無効化）が依然最大の技術的難所。本番導入時はエッジKV/Durable Objectsのようなステートフルプリミティブの設計を早期に固めるべき。

- **ポイント4:** マルチクラウド・マルチCDNのベンダーロックイン回避が重要トレンド化し、WinterCG準拠（Web標準API）のコードを書くことで実行環境を問わず移植可能にする設計が主流になりつつある。

- **ポイント5:** エッジでの可観測性（分散トレーシング、ログ集約）がボトルネック。sumitsugiのような小規模チームが採用する場合、運用負荷と学習コストを考慮し、まずは静的コンテンツ配信やA/Bテスト分岐など低リスク領域から段階的に導入するのが実用的。

### 5. authentication security best practices 2026

- **パスキー/FIDO2標準化:** パスワードレス認証（WebAuthn/Passkeys）が主流化し、フィッシング耐性のある認証がデフォルトになっている。実装時はプラットフォーム（iCloud Keychain、Google Password Manager）間の同期互換性を早期に検証すべき。

- **トークンの短命化とリフレッシュ戦略:** JWTなどのアクセストークンは5〜15分程度の短寿命化が標準となり、リフレッシュトークンローテーション＋検知（再利用検知でセッション無効化）が必須要件に。長寿命トークンの放置は漏洩時の被害範囲を大きく広げる。

- **多要素認証のリスクベース適用:** 全ユーザー一律のMFAではなく、デバイスフィンガープリンティングや行動分析によるリスクベース認証（Adaptive MFA）が実用段階。ログイン時の摩擦を減らしつつ異常アクセスのみ追加認証を要求する設計がUXとセキュリティを両立する。

- **ゼロトラスト前提のセッション管理:** 認証後も「信頼しない」設計が前提になり、セッションごとのデバイス証明・継続的な認可チェック（Continuous Authorization）が重要視されている。本番環境では認証成功後の権限昇格やセッション固定攻撃への対策が抜けやすいポイント。

- **シークレット管理の自動ローテーション:** APIキーやOAuthクライアントシークレットの静的管理はリスクとみなされ、Vault/KMS等による自動ローテーション＋アクセスログの監査が標準化。本プロジェクトでも`process.env`依存の設計から、将来的にシークレットマネージャー連携への移行を見据えておくと良い。

### 6. database architecture Prisma Supabase 2026

- **Prisma Postgres とエッジ最適化:** Prisma は自社マネージドの「Prisma Postgres」とAccelerate（コネクションプーリング＋グローバルキャッシュ）を強化しており、Supabaseと組み合わせる場合もサーバーレス関数からのコールドスタート・コネクション枯渇対策としてPgBouncer/Accelerateの併用が実質標準になっている。

- **RLS (Row Level Security) とORMの責務分離:** SupabaseのRLSはDB層でのアクセス制御を担い、Prismaはスキーマ管理とクエリ層に専念する構成が定着。認可ロジックをアプリケーション層とDB層で二重に持たず、RLSポリシーをSQLマイグレーションとして管理し、Prisma側はservice_roleでRLSをバイパスする設計が増えている。

- **マイグレーション運用の一本化:** SupabaseのネイティブマイグレーションとPrisma Migrateを併用すると競合しやすいため、どちらかに一本化する（多くのケースでPrisma Migrateに統一し、Supabase CLIはローカル開発のみに使用）流れが明確になってきている。

- **型安全性とリアルタイム機能の併存:** Prismaの型生成の恩恵を受けつつ、Supabaseのリアルタイム（Realtime/Broadcast）やStorageなど独自APIを使う部分はSupabase SDKを直接叩くハイブリッド構成が一般的——全てをPrisma経由にする必要はない。

- **エッジランタイム対応:** Next.js 16のEdge RuntimeやServer Actionsでは、PrismaのDriver Adapters（`@prisma/adapter-pg`等）を使ってSupabaseのPostgresに直接接続する構成が推奨されており、従来のPrisma Client（Node.js専用バイナリ）からの移行が進んでいる。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASM GCとコンポーネントモデルの標準化が進み、Rustのツールチェイン（`wasm-bindgen`/`wit-bindgen`）がWASI Preview 2に対応したことで、ホスト言語間のゼロコピーなデータ受け渡しが可能になり、JS↔WASM間のシリアライズオーバーヘッドが大幅に削減されている。

- **ポイント2:** `wasm32-wasip2`ターゲットとマルチスレッド（スレッドproposalの安定化）により、重いレンダリングや画像処理（物件写真の最適化など）をブラウザ側WASMにオフロードしてもメインスレッドをブロックしない構成が実用段階に入っている。

- **ポイント3:** Rust + WASMのバイナリサイズは`wasm-opt`やLTO設定の成熟で以前より小さくなったが、Next.jsのようなSSR/RSC環境との統合はまだエッジケースが多く、クライアント専用コンポーネントに限定するのが無難。

- **ポイント4:** SIMD128が主要ブラウザで安定サポートされ、地図描画や座標計算（物件検索のジオフィルタリング等）をRust/WASMに移すと、純JS実装比で2〜5倍の高速化が報告されているが、導入コストに対して現状のスケール（MVP規模）では投資対効果が低い可能性がある。

- **ポイント5:** 当面sumitsugiの規模ではNext.js標準のパフォーマンス最適化（画像最適化・RSC・キャッシュ戦略）で十分であり、WASM導入は「大量データの地図計算」や「クライアント側PDF生成の高速化」など具体的ボトルネックが実測された時点で検討すべき。

### 8. Next.js App Router patterns 2026

## Next.js App Router パターン 2026 — CTO視点

- **ポイント1（`use cache` ディレクティブの本格運用）:** Next.js 16では`use cache`によるファイル/関数単位の明示的キャッシュ制御が主流になり、従来の暗黙的フェッチキャッシュより予測可能性が上がった。sumitsugiの物件一覧・検索結果のような頻繁更新データには、タグベース再検証（`cacheTag`/`revalidateTag`）と組み合わせるのが実用的。

- **ポイント2（Partial Prerenderingの実運用化）:** 静的シェル＋動的holeのPPRが安定版として扱われ、LCPを静的部分で確保しつつパーソナライズ領域だけSuspenseでストリーミングする設計が標準パターン化している。物件詳細ページで「価格・写真は静的、ログインユーザー向けお気に入りボタンは動的」のような分離に向いている。

- **ポイント3（Turbopackデフォルト化によるビルド高速化）:** Next.js 16でTurbopackが本番ビルドのデフォルトとなり、`bun run build`の実行時間がwebpack比で大幅短縮される一方、一部のwebpack専用プラグイン依存コードは移行時に要注意。CI時間短縮の恩恵が大きいので、現状のbuild検証フローへの影響を確認する価値がある。

- **ポイント4（Server Actionsのセキュリティ境界明確化）:** Server Actionsが実質的な公開APIエンドポイントである前提が強調され、認可チェック・Zodによる入力検証を各Action内で必須とする運用がベストプラクティス化している。前の住人/次の住人間のデータ引き継ぎのような機微な操作ではここが特に重要。

- **ポイント5（Route Handlersとの責務分離）:** 外部Webhook・サードパーティ連携はRoute Handlers、UIからの状態変更はServer Actionsという役割分担が定着し、"何でもAPI Route"から脱却する設計が推奨されている。決済や外部弁護士連携などの外部システム接続が増えるフェーズでは、この分離がコードの見通しを良くする。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Vercel Edge FunctionsはV8 isolateベースで、Node.js runtimeと比べてコールドスタートが大幅に短い。認証チェックやリダイレクトなどレイテンシが重要な処理はEdge Middlewareに移すことで、物件検索ページなどのTTFBを改善できる。

- **ポイント2:** 2026年はEdge Config（低レイテンシKVストア）とEdge Functionsの組み合わせがより洗練され、フィーチャーフラグやA/Bテストの判定をリクエスト処理の最前段で完結できるようになっている。sumitsugiの物件ステータス（draft/public）の出し分けなど軽量な判定ロジックに向いている。

- **ポイント3:** Edge RuntimeはNode.js APIの完全サポートではないため、Prisma等のDB接続やfsアクセスを含む処理はEdgeに乗せられない。認証・リダイレクト・ヘッダー書き換えなど「軽量・ステートレス」な処理に限定するのがベストプラクティス。

- **ポイント4:** ISR（Incremental Static Regeneration）とEdge Functionsを組み合わせたハイブリッド配信が主流になり、公開済み物件ページは静的生成＋Edgeでの個人化（例：前の住人の活動歴バッジ表示）という構成がパフォーマンスとSEOの両立に有効。

- **ポイント5:** Observability面ではVercelのOpenTelemetry統合が進み、Edge Function単位でのトレーシングが容易になった。レイテンシ劣化の原因箇所（DNS/TLS/関数実行/DB）を切り分けやすくなっており、ローンチ後の本番監視体制構築に活用できる。

### 10. TypeScript type safety patterns 2026

- **型レベルプログラミングの実用化:** TypeScript 5.x以降のconst type parameters、satisfiesオペレータ、Template Literal Typesが成熟し、Zodなどのスキーマ定義から型を自動導出する「スキーマファースト」設計が主流に。sumitsugiでも`z.infer`で境界検証と型を一本化し、二重管理を避けられる。
- **Branded Types/Nominal Typingの普及:** `PropertyId`と`UserId`のような構造的に同じstring型を混同しないよう、ブランド型でコンパイル時に区別する手法が標準化。物件IDとセラーIDの取り違えなど、実行時まで気づかないバグをコンパイル時に防げる。
- **Exhaustiveness Checkingの徹底:** Union型（例: `status: 'draft' | 'public'`）に対し`never`型を使った網羅性チェックを全switch文で強制するのがベストプラクティス化。新しいステータスを追加した際、対応漏れの分岐をビルド時に検出できる。
- **tRPC/Server Actions経由のEnd-to-End型安全性:** Next.js App RouterのServer Actionsとクライアント間で型を共有し、API層での型の不整合をなくす流れが加速。フロント・バックエンドで型定義を一元化すれば、UI用語変換（セラー→前の住人など）のマッピング漏れも型チェックで検出可能。
- **AIコード生成時代の型安全性の価値向上:** LLMが生成するコードが増える中、厳格な型システムが「生成コードの自動レビュアー」として機能する重要性が増している。型エラーをCI必須ゲートにすることが、自動化開発フローでの品質保証の最後の防衛線になる。
