# CTO Knowledge - 2026-06-09

## Daily Update (2026-06-09)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) 最大活用:** RSCをデフォルト戦略として採用し、クライアントバンドルサイズを大幅削減。`'use client'`は状態・イベントハンドラが必要な最小コンポーネントにのみ付与する。

- **Partial Prerendering (PPR) の本格導入:** Next.js 15で安定化したPPRにより、同一ページでStatic ShellとDynamic Streamingを共存させ、FCP（First Contentful Paint）とTTFB両方を改善できる。

- **Turbopack によるビルド高速化:** Next.js 15以降デフォルトのTurbopackはWebpackと比較してHMRが最大10倍高速。CI/CDパイプラインのビルド時間短縮にも直結する。

- **Server Actions + キャッシュ戦略の精緻化:** `unstable_cache`や`revalidateTag`を活用した細粒度キャッシュ制御が重要。データフェッチのウォーターフォールを避けるため、`Promise.all`と並列フェッチを徹底する。

- **Bundle Analyzerと`@next/bundle-analyzer`による継続的計測:** パフォーマンス最適化は計測なしには語れない。Core Web Vitals（特にLCP・INP）をCI段階でモニタリングし、リグレッションを自動検知する仕組みを組み込むことが2026年標準のプラクティス。

### 2. React Server Components streaming 2026

- **ポイント1:** RSC + Suspense によるストリーミングが成熟し、`use()` フックと組み合わせることでウォーターフォールなしに非同期データを宣言的に扱えるようになった。TTFBとLCPの両方を改善できる実践的な選択肢として定着。

- **ポイント2:** PPR（Partial Prerendering）がNext.js 15で安定化し、静的シェルを即座に配信しつつ動的部分をストリームインする手法が標準化。CDNキャッシュと動的コンテンツを両立できる。

- **ポイント3:** Server Actionsとストリーミングの統合が深化し、フォーム送信後のUIアップデートをクライアントJSなしに実現できるパターンが普及。バンドルサイズ削減とUX向上を同時に達成可能。

- **ポイント4:** `<Suspense>` の粒度設計が重要な設計判断になっており、粒度が荒すぎるとCLS、細かすぎるとリクエスト爆発という両側のトレードオフに注意が必要。

- **ポイント5:** React 19の`use(promise)`によりRSCからクライアントコンポーネントへのデータ受け渡しがシンプルになり、Context + Server境界の設計がより直感的になった。既存のApp Routerアプリの段階的移行コストが低下。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全性の標準化:** TypeScript fullstackプロジェクトではtRPCがデファクトになりつつあり、ランタイムエラーを排除した end-to-end型安全性がDX向上の決め手になっている。特にNext.js + Prismaスタックとの親和性が高い。

- **GraphQLは「複雑なデータグラフ」特化に収束:** マイクロサービス間のデータ集約やBFF（Backend for Frontend）パターンには依然有効だが、シンプルなCRUDにはオーバーエンジニアリングという認識が定着。Federation v2による分散スキーマ管理が本番運用の鍵。

- **REST + OpenAPI 3.1はパブリックAPIの事実上の標準:** 外部パートナーや3rd party連携には型生成（openapi-ts等）と組み合わせたRESTが最もエコシステムが成熟しており、SDKの自動生成も含めて運用コストが最低。

- **Server Actionsの影響でAPIレイヤーが薄くなる傾向:** Next.js 15以降のServer Actionsにより、内部用途では従来のREST/GraphQLエンドポイントを省略するアーキテクチャが増加。ただしキャッシュ戦略とリクエスト管理に注意が必要。

- **選択基準の実用ルール（2026年版）:** 内部フルスタックTS → tRPC、複数クライアント/BFF → GraphQL、外部公開API → REST+OpenAPI、プロトタイピング → Server Actionsが現時点での最適解。技術選定より「チームが運用できるか」が最重要判断軸。

### 4. serverless edge computing 2026

- **エッジファーストアーキテクチャの主流化:** Cloudflare Workers・Vercel Edge Functions・AWS Lambda@Edgeが成熟し、レイテンシ要件の厳しいAPIはエッジデプロイがデフォルト選択肢になっている。RTTを50ms以下に抑えられるユースケース（認証、A/Bテスト、パーソナライゼーション）では特に効果的。

- **V8 Isolateモデルの限界と次世代ランタイム:** WASMベースのエッジランタイム（WinterCG準拠）が普及し、Node.js互換性の制約を超えた多言語デプロイが可能になった。RustやGo製のエッジ関数がコールドスタートゼロを実現しつつある。

- **エッジDBとの統合が鍵:** Turso（libSQL）・Cloudflare D1・PlanetScale Metalなど、エッジ対応分散DBが整備され「エッジで書き込みができない」問題が解消されつつある。ただしグローバル整合性トレードオフの設計判断は依然重要。

- **コスト構造の再評価:** リクエスト数課金からCPU時間課金への移行が進み、重い処理をエッジに置くと逆にコスト増になるケースが増加。薄いルーティング・認証・キャッシュ制御のみエッジに置き、ビジネスロジックはリージョナルに残す「ハイブリッドエッジ」設計が現実解。

- **オブザーバビリティの課題が未解決:** 分散エッジ環境でのトレーシング・ログ集約はまだ成熟途上。OpenTelemetryのエッジ対応が進んでいるが、デバッグコストを過小評価するとオペレーション負債になるため、採用前にツールチェーンの確認が必須。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）への移行加速:** FIDO2/WebAuthnベースのパスキーが2026年の標準となりつつあり、パスワードレス認証はフィッシング耐性が高くUXも優れるため、新規サービスでは最初からパスキー対応を設計に組み込むべきです。

- **セッション管理の短命化とRotating Refresh Token:** アクセストークンの有効期限を15分以下に設定し、リフレッシュトークンをシングルユース（使用ごとに再発行）にすることで、トークン漏洩時の被害範囲を最小化できます。

- **デバイスバインドセッション（Device-Bound Sessions）の採用:** ブラウザのDevice Bound Session Credentials（DBSC）を活用し、セッションクッキーを端末のTPMチップに紐付けることで、クッキー窃取攻撃（AiTM phishing）に対する実質的な防御が可能になります。

- **AI駆動の不正検知との統合:** ログイン試行のタイミング・地理情報・行動パターンをリアルタイム分析するリスクベース認証が主流化しており、パスワード正否だけでなくコンテキスト全体でアクセスを判断する設計が求められます。

- **サプライチェーンリスクとしての認証ライブラリ管理:** Auth0・NextAuth等の外部認証ライブラリへの依存は攻撃面を広げるため、`bun audit`や依存関係のピン留め（exact versioning）、Sigstoreによるサプライチェーン検証を CI/CD に組み込むことが重要です。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x + Supabase の統合成熟:** Prisma 6でEdge RuntimeサポートとPrisma Postgresが正式リリースされ、Supabase との接続プーリング（pgbouncer）なしの直接接続が安定。コネクション管理の複雑さが大幅に軽減された。

- **RLS（Row Level Security）ファースト設計:** Supabaseでは認証・認可をアプリ層ではなくDB層（PostgreSQL RLS）で実装するパターンが主流。Prismaと併用する場合は`SET LOCAL role`でセッションコンテキストを切り替える設計が推奨されている。

- **リアルタイム機能の住み分け:** Supabase Realtimeは読み取り系のリアルタイム更新に最適、書き込み系はPrismaを通じてトランザクション保証を維持するハイブリッド構成が現実的なベストプラクティス。

- **pgvector によるベクトル検索の内製化:** Supabase（PostgreSQL + pgvector）でベクトルDBを別途持たずEmbedding検索を実装するコストが激減。LLMアプリの検索基盤をRDBと統合できるため、マルチDBの運用複雑度を下げられる。

- **スキーマ管理の一元化:** `prisma migrate`をSingle Source of Truthとして使いつつ、Supabase Dashboardは閲覧専用とする運用が安全。スキーマドリフト（Dashboard直接編集）はCI/CDでの`prisma migrate diff`検知で防ぐ構成が定番になっている。

### 7. WebAssembly Rust performance 2026

- **WASM Component Modelの実用化:** 2026年時点でWASI 0.2が安定稼働し、RustのコンポーネントモデルサポートによりWASMモジュールの相互運用性が実現。マイクロサービス間でのWASMバイナリ共有がエッジ環境で実践的な選択肢になっている。

- **Wasmtime/WasmEdgeのAOTコンパイル成熟:** クランタイムのAOT（事前コンパイル）最適化により、ネイティブRustコードとの性能差が5-15%以内に収束。コールドスタート問題がほぼ解消され、サーバーレス環境での採用が加速している。

- **SIMD・スレッドサポートの標準化:** Fixed-Width SIMDとスレッド提案が主要ランタイムで安定実装済み。RustのRAYONと組み合わせることで、画像処理・暗号演算などのCPUバウンド処理においてネイティブ同等の並列性能が出せる。

- **Rustのゼロコストアブストラクションとの相性:** RustはGCを持たないため、WASMのGCプロポーザルに依存せずリニアメモリを直接制御できる。JavaScriptやPythonとの比較でメモリ使用量が2-5倍効率的で、リソース制約のあるエッジノードに最適。

- **デバッグ・プロファイリングエコシステムの整備:** DWARF情報付きWASMのソースマップが充実し、`wasm-pack`+`cargo-component`のツールチェーンが安定。開発体験のボトルネックだったビルド時間も増分コンパイル改善で40%短縮されており、採用障壁が大幅に低下した。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** デフォルトでServer Componentsを使い、インタラクティビティが必要な箇所のみ`'use client'`を付与する。バンドルサイズとTTIが大幅に改善され、2026年時点でこのパターンが業界標準として定着している。

- **Partial Prerendering (PPR) の本格採用:** 静的シェルと動的コンテンツを同一ルートで混在させるPPRが安定版となり、`Suspense`境界設計が重要なアーキテクチャ判断になった。適切な境界設計でCore Web Vitalsを最大化できる。

- **Server Actions によるAPI簡略化:** フォーム送信やミューテーションにServer Actionsを使うことで、APIルートを書かずに型安全なサーバー処理が実現できる。ただし冪等性とエラーハンドリングの設計が甘くなりがちな点に注意。

- **`use cache` APIとキャッシュ戦略の明示化:** `fetch`の暗黙キャッシュが廃止され、`use cache`ディレクティブで明示的にキャッシュを宣言するスタイルへ移行。予測可能なキャッシュ挙動により本番障害が減少している。

- **parallel/intercepted routesによるモーダルUX:** モーダルやスライドオーバーをURLに紐づけて実装するパターンが成熟し、共有可能なURLと深いリンク性を保ちながらSPA的UXを実現できる。複雑さとのトレードオフは依然あるため、ユースケースを絞って採用することを推奨。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタートの実質ゼロ化:** Edge FunctionsはV8 Isolatesベースのため従来のServerless比で起動時間が~100ms→<5msに短縮。2026年時点では**バンドルサイズ管理（4MB上限）**が唯一の主要ボトルネックとなっており、tree-shakingとdynamic importの徹底が必須。

- **Fluid Computeによるリージョン選択の自動最適化:** Vercelの2025年末導入のFluid Computeにより、Edge/Serverlessの境界が曖昧になりつつある。Node.js互換API使用時は自動でServerlessにフォールバックするため、**無理にEdge制約に合わせた実装を避け**、Middlewareはルーティング・認証のみに絞るのが現実解。

- **データローカリティが律速要因:** Edge Functionのレイテンシ優位性はDB往復で相殺される。PlanetScale/Neon/Tursoなど**エッジ対応分散DBとのセット採用**、またはKV（Vercel KV / Upstash Redis）でホットデータをキャッシュする設計が2026年のデファクト。

- **Streaming Responseによる体感速度の改善:** `ReadableStream`とSuspenseを組み合わせたStreaming SSRがEdge Functionsで安定稼働。Time to First Byteを下げつつ重い処理を後続チャンクに分散させることで、**LCP指標を犠牲にせず複雑なページを配信可能**。

- **可観測性の整備が急務:** Edge実行環境はログが揮発しやすくデバッグが困難。OpenTelemetry + Vercel Observability（旧Speed Insights統合版）を**初期から組み込む**ことで、本番でのレイテンシ分解とエラートレースが可能になる。後付けは工数が跳ね上がる。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の本格活用:** TypeScript 4.9以降の`satisfies`が2026年では標準的なパターンとなり、型推論を保持しながら型安全性を検証できるため、`as`キャストによる型情報の喪失を防ぐ場面で必須になっている。

- **Template Literal Typesによる文字列DSL:** APIルートやイベント名などの文字列をリテラル型で表現し、実行時エラーをコンパイル時に検出するパターンが定着。特にRPC系ライブラリ（tRPC, Hono）との組み合わせでEnd-to-End型安全性が実現されている。

- **Branded Types（Nominal Typing）の普及:** `UserId`と`ProductId`が両方`string`であっても混在を型レベルで防ぐBranded Types（`type UserId = string & { _brand: 'UserId' }`）が、DDD実践プロジェクトでのデファクトパターンになっている。

- **`infer`と再帰的型によるSchema-First開発:** ZodやArkTypeなどのランタイムバリデーションから型を自動導出（`z.infer<typeof schema>`）するアプローチが主流となり、型定義とバリデーションの二重管理が解消されている。

- **`const` type parametersとVariance Annotations:** TypeScript 5.x系で導入された`const`型パラメータとVariance(`in`/`out`修飾子)により、ジェネリック関数の型推論精度が向上し、過度な型アサーションなしにリテラル型を維持できるようになっている。
