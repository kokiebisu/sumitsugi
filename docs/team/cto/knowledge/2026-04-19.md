# CTO Knowledge - 2026-04-19

## Daily Update (2026-04-19)

### 1. Next.js performance optimization 2026

- **React Server Components の徹底活用:** RSCでクライアントバンドルを最小化し、データフェッチをサーバー側に集約することで、TTFBとLCPが劇的に改善される。`"use client"`は本当に必要な箇所のみに限定すること。

- **Partial Prerendering (PPR) の本番投入:** 静的シェルと動的コンテンツを同一ルートで混在させるPPRがNext.js 15以降で安定化。CDNキャッシュ効率とパーソナライズを両立できる。

- **`<Image>`と`next/font`の最適化徹底:** LCPの主因は未最適化画像とフォントのCLS。`priority`属性・`sizes`指定・サブセット化を組み合わせるとCore Web Vitalsスコアが大幅改善。

- **Server Actionsのバンドルサイズへの影響を監視:** Server Actionsは便利だが、過多になるとクライアントマニフェストが肥大化する。`@next/bundle-analyzer`で定期的に計測し、不要なインポートを整理。

- **Edge Runtimeの選択的適用:** ミドルウェアや認証チェックはEdgeに移行してレイテンシを削減できるが、Node.js専用APIは使えない。`runtime = 'edge'`の適用範囲をAPIルートごとに慎重に判断すること。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化:** 2026年時点でRSCストリーミングの実践知が蓄積され、Suspense境界を細かく設定しすぎるとウォーターフォールが発生する問題が明確化。コンポーネントツリー設計段階での境界計画が必須になっている。

- **PPR（Partial Prerendering）の本格普及:** Next.js 15以降でPPRが安定化し、静的シェル+動的ストリームのハイブリッドが標準パターンに。TTFBを犠牲にせずインタラクティブ性を確保できる。

- **Server Actionsとストリーミングの統合:** フォーム送信後のUI更新をストリーミングで返す手法が定着。`useActionState`と`Suspense`の組み合わせで楽観的UIとサーバー状態を一貫管理できる。

- **エッジランタイムとの相性問題:** CloudflareWorkers等のエッジ環境ではNode.js固有APIが使えずRSCのストリーミングに制約が残る。ランタイム選定はデプロイ先ファーストで判断すべき。

- **バンドルサイズへの誤解:** RSC自体はクライアントJSを削減するが、`"use client"`の境界管理を怠ると逆効果。定期的な`@next/bundle-analyzer`でクライアント流出を検知する運用が重要。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年においてtRPCはNext.js/TypeScriptスタックでデファクトに近い存在となり、スキーマ定義なしでクライアント・サーバー間の型共有が実現できるため、小〜中規模チームの開発速度が劇的に向上している。

- **GraphQLの適用範囲の明確化:** GraphQLは複数クライアント（Web/Mobile/外部API）が異なるデータ形状を必要とするケースに特化しつつあり、内部APIにGraphQLを使うオーバーエンジニアリングは淘汰される傾向にある。

- **REST + OpenAPIの復権:** AIコード生成ツールとの相性の良さから、OpenAPI仕様ベースのREST APIが見直されている。`openapi-typescript`等でtRPC同様の型安全性を確保しつつ、外部公開APIの標準として使い勝手が上がっている。

- **エッジ・ストリーミング対応がAPI設計の必須要件に:** Vercel/Cloudflare WorkersなどのエッジランタイムとServer-Sent Events/WebStreamの普及により、ロングポーリング型APIは設計段階から避けるべき選択肢となった。

- **プロトコル選択の判断軸:** 「外部公開→REST+OpenAPI」「社内フルスタック→tRPC」「マルチクライアント複雑クエリ→GraphQL」という棲み分けが2026年の実務的なコンセンサスになりつつある。

### 4. serverless edge computing 2026

- **WebAssembly（WASM）がエッジのデファクトに:** Cloudflare Workers・Fastly Compute@Edgeでの WASM採用が標準化し、言語非依存でコールドスタートほぼゼロの実行環境が実現。V8 Isolate一択だった時代が終わりつつある。

- **エッジDBの成熟:** Cloudflare D1・Turso（libSQL）・Neon Serverlessのエッジレプリカにより、"DB接続のためだけにオリジンへ往復"問題が解消。レイテンシ重視のAPIはエッジ完結が現実的になった。

- **AI推論のエッジシフト:** Workers AI・Vercel AI SDKのEdge Runtimeサポートにより、軽量LLM（~7B量子化モデル）をエッジで推論可能に。プライバシー規制対応とレイテンシ削減を同時に達成できる。

- **コールドスタート問題の再燃:** Isolateベースは速いがWASMコンテナやより重いランタイムは依然コールドスタートが問題。Provisioned Concurrency相当の機能がエッジでも必要になってきている。

- **可観測性のギャップが課題:** エッジ分散実行はトレーシング・ログ集約が困難で、OpenTelemetry対応も途上。本番投入前にエッジ専用のo11yパイプライン設計を必須とすべき。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** FIDO2/WebAuthnベースのパスキーがパスワード認証を事実上置き換えつつあり、フィッシング耐性とUX向上を両立できる。Apple/Google/Microsoftのエコシステム対応が成熟した今、新規実装ではパスワードレスをデフォルトにすべき。

- **セッション管理のゼロトラスト化:** 「一度ログインしたら信頼」モデルは終焉し、継続的なリスク評価（デバイス・IP・行動パターン）に基づく動的セッション失効が標準となっている。短命トークン（15分）＋サイレントリフレッシュの組み合わせが推奨。

- **OAuthトークンの最小権限徹底:** アクセストークンのスコープを機能単位で細分化し、不要な権限を排除することが重要。特にサードパーティ連携では、トークン漏洩時の爆発半径を最小化するDPOP（Demonstration of Proof-of-Possession）の採用が進んでいる。

- **AIを悪用したクレデンシャルスタッフィング対策:** 大規模言語モデルを使ったCAPTCHAバイパスが一般化し、従来のボット対策が陳腐化。行動バイオメトリクス（タイピングリズム・マウス軌跡）との組み合わせが新たな防御層として有効。

- **サプライチェーン認証リスクの管理:** OAuth/OIDC実装ライブラリへの依存は脆弱性の温床になりやすく、定期的なSBOM（ソフトウェア部品表）監査と依存関係の固定（lock file）が必須。特にOAuthフローを実装するOSSへのバージョン固定は怠らないこと。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のパフォーマンス最適化:** Prisma ORM はコネクションプーリング（Prisma Accelerate）が実用段階に達し、サーバーレス環境でのコールドスタート問題が大幅に軽減された。Edge Runtimeでの直接利用も安定している。

- **Supabase の GA 成熟度:** 2026年時点でSupabaseはエンタープライズ採用が加速しており、Row Level Security（RLS）とリアルタイムサブスクリプションの組み合わせが、マルチテナントSaaSの標準構成になりつつある。

- **Prisma + Supabase の統合パターン:** Prismaをスキーマ管理・マイグレーション専用に使い、クエリは`@supabase/supabase-js`で直接RLSを活用する「ハイブリッド構成」が実用的。型安全性とセキュリティの両立に有効。

- **pgvector による AI 統合:** SupabaseのpgvectorサポートでベクトルDB別途不要のケースが増加。RAGパイプラインをPostgreSQL単体で完結させるアーキテクチャが小〜中規模プロダクトの定番になっている。

- **マイグレーション戦略の重要性:** `prisma migrate deploy` を CI/CD に組み込み、Supabaseのブランチ機能（Preview Branches）と連携させることで、本番DBへの破壊的変更リスクを大幅に低減できる。

### 7. WebAssembly Rust performance 2026

- **Component Model の本格普及:** WebAssembly Component Model（WASI 0.2）が2025年末に安定化し、Rustで書いたWasmモジュールをホスト言語に依存せず再利用できる基盤が整った。マイクロサービスの代替として注目度が高まっている。

- **SIMD・スレッド対応の成熟:** Wasm SIMD命令とShared Memoryが主要ブラウザ・ランタイムで安定稼働し、Rust+Wasmによる画像処理・ML推論のネイティブ比90%以上のスループットが実用域に入った。

- **Wasmtime / WasmEdgeの高速化:** AOTコンパイルとキャッシュ機構の改善により、コールドスタートがサーバーレス用途でも許容範囲（<1ms）になった。Rustで書いたロジックをエッジランタイムにデプロイするパターンが増加中。

- **GCプロポーザルとメモリ管理の変化:** Wasm GC提案の普及でRustのゼロコストメモリ管理の優位性が相対化されつつあるが、リアルタイム・低レイテンシ用途ではRustのGCレスモデルが依然として最強。

- **ツールチェーン成熟（wasm-bindgen / wit-bindgen）:** `wit-bindgen`による型安全なインターフェース生成が実用的になり、RustとJavaScript/Python間のFFIコストが大幅に削減された。新規プロジェクトでは`wasm-pack`より`cargo component`への移行を推奨。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年では「必要な場合のみ `'use client'`」が鉄則。データフェッチはServer Componentsで完結させ、クライアントバンドルサイズを最小化する。

- **Partial Prerendering (PPR) の本格採用:** 静的シェルと動的ストリーミングを同一ルートで共存させるPPRが安定版となり、TTFBとLCPを両立できる唯一の現実解になった。

- **Server Actions でAPIルートを削減:** フォームやミューテーションはServer Actionsに集約し、`/api/*` エンドポイントを乱立させない。型安全性とRPCライクな開発体験が得られる。

- **`use cache` ディレクティブによる細粒度キャッシュ:** `fetch` キャッシュではなく `use cache` で関数・コンポーネント単位のキャッシュ制御が可能になり、`revalidateTag` との組み合わせで柔軟な無効化戦略が実現できる。

- **Parallel/Intercepting Routesの慎重な利用:** モーダルやサイドバーUIに有効だが、複雑になりすぎると保守コストが跳ね上がる。本プロジェクト規模では「使えるから使う」ではなく、UX上の明確な必要性がある場合に限定すべき。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択基準:** Node.js Runtimeより起動時間が~100ms短いEdge Runtimeは、認証ミドルウェアやA/Bテストなどレイテンシ重視のユースケースに最適だが、Node.js APIの制限があるため用途を明確に分けることが重要。

- **Fluid Compute活用:** 2025年末に導入されたFluid Computeモデルにより、リクエスト待機中のCPUアイドル時間が課金対象外となった。I/O待ちの多いEdge Functionsではコスト削減と処理効率が大幅に向上する。

- **Key-Value ストアの近接配置:** Vercel KVやUpstash Redisをエッジに近いリージョンに配置し、`waitUntil()`でレスポンス後のキャッシュ書き込みを非同期化することで、P99レイテンシを劇的に改善できる。

- **Middleware Chainingの最適化:** 複数のMiddlewareロジックを単一ファイルに集約し、早期リターンパターンを徹底することで、冷起動コストの重複を避け、全体的なウォームアップ時間を削減できる。

- **ISRとEdgeの組み合わせ戦略:** 静的生成（ISR）をベースラインとしつつ、パーソナライゼーションのみEdge Functionで差分適用する「Partial Prerendering（PPR）」パターンが2026年の標準アーキテクチャになりつつある。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded Typesが標準化し、プリミティブ型の誤用をコンパイル時に防ぐパターンが定着している。

- **satisfies 演算子の活用:** TypeScript 4.9以降の `satisfies` が広く採用され、型推論を保ちながら型チェックを行える表現が増え、`as` キャストの乱用が減少傾向にある。

- **Zod + tRPC によるランタイム型安全性:** スキーマ定義をAPIの境界に置き、フロントエンド〜バックエンド間の型を自動同期する構成がデファクトに近づいており、手動の型定義二重管理が不要になっている。

- **Template Literal Types の実用化:** ルートパスやイベント名などの文字列を型レベルで制約する用途が成熟し、ライブラリの型定義品質を大きく向上させている。

- **Exact Types への期待と代替策:** `exactOptionalPropertyTypes` コンパイラオプションが本番採用され、`undefined` と「プロパティ未定義」の区別が厳密化。既存コードの移行コストに注意が必要。
