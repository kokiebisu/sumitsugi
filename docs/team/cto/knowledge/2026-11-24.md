# CTO Knowledge - 2026-11-24

## Daily Update (2026-11-24)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Prerendering / PPR の本格活用):** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分のみストリーミングする構成が標準に。LCPとTTFBを両立できるため、ダッシュボードや一覧ページで優先的に導入すべき。

- **ポイント2（React Server Components + キャッシュ戦略の精緻化):** `use cache` ディレクティブやセグメント単位のキャッシュ制御が実用レベルに達し、過剰なクライアントフェッチを削減できる。物件一覧・詳細ページのようなSSRページはキャッシュキー設計を見直す価値が大きい。

- **ポイント3（Turbopackのビルド/devパフォーマンス):** Turbopackがデフォルト化しwebpack比で大幅なビルド高速化が得られるため、CI時間短縮に直結する。本プロジェクトの `bun run build` 実行時間もTurbopack前提で再計測すべき。

- **ポイント4（画像・フォント最適化の自動化強化):** `next/image` のAVIF/レスポンシブ最適化とフォントのセルフホスティングがより自動化され、Core Web Vitals（特にCLS/LCP）改善の手間が減少。物件写真が多いUIほど効果が大きい。

- **ポイント5（Edge Runtime適用範囲の拡大):** 認証チェックや軽量API（物件ステータス切替など）をEdge Runtimeに寄せることでレイテンシを削減できるが、Node.js専用ライブラリ依存がある箇所は要検証。段階的な移行が無難。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** React 19以降、`<Suspense>`境界ごとのストリーミングがNext.js App Routerの既定動作となり、TTFBとLCPを分離して最適化できる。重いデータ取得をページ単位ではなくコンポーネント単位でストリームすることで、体感速度が大きく改善する。

- **Partial Prerendering (PPR) の実用化:** 静的シェルを即時配信しつつ動的部分だけをストリーミングで後追いする手法が、Next.js 15〜16で安定版に近づいている。ISRと組み合わせることで、ECサイトのような「ヘッダーは静的・在庫情報は動的」な構成にコスト効率よく対応できる。

- **サーバー/クライアント境界の設計が肝:** RSCはデフォルトでサーバー実行されるため、`'use client'`の境界をどこに置くかがバンドルサイズとインタラクティブ性のトレードオフを決める。フォームや状態を持つUIのみをクライアント化し、データ表示は極力サーバー側に留める設計が2026年のベストプラクティス。

- **キャッシュ戦略の複雑化への対応:** `fetch`のデフォルトキャッシュ挙動がバージョンごとに変化しており、`revalidate`や`cache: 'no-store'`の明示指定が必須になっている。暗黙のキャッシュに依存すると本番で古いデータを表示するバグに繋がるため、データ取得層でキャッシュポリシーを明文化すべき。

- **エラーバウンダリとストリーミングの組み合わせ:** ストリーミング中に発生したサーバーエラーは、個別の`error.tsx`やSuspense境界内で捕捉しないとページ全体が崩れるリスクがある。本プロジェクトのような物件一覧・詳細ページでは、画像や外部APIに依存する箇所を細かくSuspense分割し、障害の影響範囲を局所化することが重要。

### 3. API design REST GraphQL tRPC 2026

- **API進化の方向性:** RESTは依然としてパブリックAPIの標準だが、社内・BFF層ではtRPCの採用が増加。型安全性を自動で保証でき、OpenAPI/Swaggerのスキーマ同期の手間を省ける点が評価されている。

- **GraphQLの使い所の明確化:** モバイルや複数クライアントでデータ要件が異なる場合はGraphQLが有効だが、N+1問題やキャッシュ戦略の複雑さから、シンプルなCRUD中心のsumitsugiのようなプロダクトでは過剰設計になりやすい。

- **tRPC + Next.js App Routerの親和性:** TypeScriptモノレポ構成（フロント・バックエンドが同一リポジトリ）ではtRPCが最も実装コストが低く、Server Actionsとの組み合わせでクライアント・サーバー間の型共有がシームレスになる。

- **エッジ・ストリーミング対応:** 2026年のトレンドとして、API設計自体がストリーミングレスポンス（SSE/WebSocket併用）やエッジランタイムでの実行を前提に設計されるケースが増加。レイテンシ重視の物件検索・チャット機能などで有利。

- **スキーマファーストとZodの統合:** 入力検証（Zod）をAPI契約の単一ソースとして扱い、型定義・バリデーション・ドキュメントを一元化する設計が主流化。sumitsugiの現行スタンダード（Zodでの境界検証）はこの流れに合致しており、追加のGraphQL層導入よりも既存tRPC/REST構成の型安全性強化に投資する方が合理的。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** V8 isolates(Cloudflare Workers, Deno Deploy)やWASMベースの軽量ランタイムが主流となり、コールドスタートがミリ秒単位まで短縮。Node.js互換APIの充実で、既存コードの移行コストも大幅に低下している。

- **AI推論のエッジシフト:** 軽量LLM(量子化モデル・SLM)をエッジで直接推論させる構成が増加。レイテンシ要求の厳しいチャット/レコメンド機能は、中央サーバーを経由せずエッジで完結させる設計が実用段階に入った。

- **データレイヤーのエッジ対応:** Cloudflare D1/Durable Objects、Turso、PlanetScaleなど、エッジ近接型のデータベースが成熟し、読み取りだけでなく書き込みもリージョン分散できるようになった。グローバル展開時のDB選定基準が変わっている。

- **観測性・デバッグの課題:** エッジ実行環境は分散度が高く、従来のAPMツールでは追跡しづらい。OpenTelemetryのエッジ対応やログ集約の設計を初期段階から組み込む必要がある。

- **コスト構造の変化:** リクエスト単位課金が中心で、小規模トラフィックでは大幅なコスト削減になるが、高頻度処理ではサーバーレス特有の課金予測の難しさが残る。sumitsugiのような物件検索・一覧表示系のような読み取り中心ワークロードは、エッジキャッシュ+エッジDBの組み合わせで特に恩恵を受けやすい。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証(WebAuthn/Passkeys)がメインストリームとなり、フィッシング耐性のある認証がデフォルトに。パスワードは第二要素またはフォールバックとしてのみ残す設計が主流。
- **リスクベース適応型認証:** デバイス指紋・行動パターン・位置情報を組み合わせたリスクスコアリングで、怪しいログインのみMFAを要求する方式が標準化。ユーザー体験とセキュリティのトレードオフを動的に最適化できる。
- **トークンのスコープ最小化と短寿命化:** JWTやセッショントークンは有効期限を短く設定し、リフレッシュトークンローテーション(re-use detection付き)を必須に。長寿命トークンの漏洩リスクを根本から減らす。
- **サーバーサイドのセッション管理の徹底:** クライアント側に機密情報を持たせず、httpOnly/secure/SameSite=strictなCookieでセッションIDのみ管理。XSS経由のトークン窃取を防ぐ基本だが見落としがちな対策。
- **ゼロトラスト前提のAPI認証:** マイクロサービス間もmTLSやサービスメッシュでの相互認証を行い、「内部ネットワークだから安全」という前提を排除。侵入後の水平移動を防ぐ設計が重要。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMの進化（Rust-freeエンジン）:** Prisma 6以降はクエリエンジンがTypeScript/WASMベースに移行し、コールドスタートが大幅に改善。Vercelなどのサーバーレス環境でのレイテンシ問題が実用レベルで解消されつつある。

- **Supabaseのブランチング機能活用:** Supabaseのデータベースブランチ機能とPrisma Migrateを組み合わせることで、PRごとに独立したDB環境を作れる。sumitsugiのようなfeature-branch中心の開発フローには特に相性が良く、CI上でのマイグレーション検証に活用できる。

- **Row Level Security (RLS) とPrismaの併用パターン:** SupabaseのRLSはPrisma Client経由のアクセスでは直接効かないため、「サービスロールキー＋アプリ層での権限チェック」か「Prismaは管理系操作のみ、ユーザー向けクエリはSupabase Clientで」という使い分けが2026年のベストプラクティスとして定着。認証・決済など機密性の高い機能ではRLSを過信せずアプリ層の検証を必須にすべき。

- **PgBouncer/Supavisor経由のコネクションプーリング:** サーバーレス関数ごとに新規DB接続が発生する問題は、Supavisor（トランザクションモード）とPrismaの`connection_limit`設定の組み合わせで解決するのが標準。本番環境では直接接続ではなくプーラー経由のURLを必ず使うことをルール化すべき。

- **型安全なマイグレーションとZodの統合:** Prisma Schemaから生成した型とZodスキーマを一致させ、DB層・APIバウンダリの両方で検証する「スキーマ駆動開発」が主流に。sumitsugiの`.claude/rules/standards.md`にあるZod必須ルールとも自然に整合する。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASI Preview 2とComponent Modelの普及により、Rust製WASMモジュールの相互運用性が向上し、異なる言語間でのコンポーネント共有が実用レベルに達している。マイクロサービス的な粒度でWASMモジュールを組み合わせる設計がパフォーマンスとデプロイ容易性の両立に有効。
- **ポイント2:** `wasm-opt`やLLVMバックエンドの改善により、Rust→WASMのバイナリサイズとランタイム速度がネイティブに近づいており、エッジ環境（Cloudflare Workers等）での採用が加速している。初期ロード時間がクリティカルな用途ではバイナリサイズ最適化を優先すべき。
- **ポイント3:** SIMD128命令の安定サポートとマルチスレッド（共有メモリ+Atomics）が主要ランタイムで標準化され、画像処理や数値計算系ワークロードでネイティブの70-90%程度の性能が出せるようになった。計算集約的な処理をフロントエンドに持ち込む選択肢として現実的。
- **ポイント4:** Garbage Collection提案（WasmGC）の進展によりRust以外の言語のWASM対応も進むが、Rustは所有権モデルのおかげでGCオーバーヘッドなしで動作する優位性を維持しており、パフォーマンスクリティカルな部分はRustに任せる設計が定石化している。
- **ポイント5:** ブラウザ外（サーバーサイド、CLI、プラグインサンドボックス）でのWASMランタイム（Wasmtime、Wasmer）活用が増え、Rustの「一度コンパイルしてどこでも安全に実行」という特性がプラグインアーキテクチャの標準解になりつつある。本プロダクトでも拡張機能基盤を検討する際の有力候補になる。

### 8. Next.js App Router patterns 2026

- **ポイント1（Server Components優先設計）:** デフォルトでServer Componentsを使い、Client Componentsは`'use client'`境界を最小限に留めることで、バンドルサイズとハイドレーションコストを削減できる。データ取得をコンポーネント内で直接行う設計により、Props Drilling問題も自然に解消される。

- **ポイント2（Partial Prerendering / PPR）:** 静的シェルを即座に返しつつ、動的部分だけを`Suspense`でストリーミングするPPRが主流化しており、SEOとTTFBを両立できる。LCP改善が必要なページ（物件詳細ページなど）に特に有効。

- **ポイント3（キャッシュ戦略の明示化）:** Next.js 16以降は`fetch`の暗黙キャッシュよりも`cacheLife`/`cacheTag`等の明示的キャッシュ制御APIが推奨され、再検証タイミングをコード上で意図的に管理する必要がある。物件情報のようにステータス変更（draft/public）が即時反映されるべきデータは、タグベースの再検証（`revalidateTag`）で整合性を保つべき。

- **ポイント4（Server Actionsのセキュリティ境界）:** フォーム送信・認証系はServer Actionsに集約されつつあるが、Server Actionは実質パブリックAPIエンドポイントになるため、Zodによる入力検証とレート制限が必須。弊社のセラー向け物件登録フォームなど、認可チェックをAction内で必ず再実施する設計が標準。

- **ポイント5（Route Groups + Parallel Routesでの関心分離）:** `(group)`や`@slot`を使ったRoute Groups/Parallel Routesにより、認証済み/未認証レイアウトやモーダル（物件詳細のインターセプトルートなど）を宣言的に分離できる。小さなファイル構成（本リポジトリの200〜400行方針）とも相性が良く、ページ単位の責務が明確になる。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの選択的活用:** Node.js Runtimeとの機能差が縮小したため、全APIルートをEdgeに統一するのではなく、低レイテンシが必須な認証チェックやリダイレクト処理のみをEdge Functionsに残し、DB接続が必要な処理はFluid Computeへ移すのが2026年のベストプラクティスです。
- **Fluid Computeとのハイブリッド構成:** Vercel Fluid Compute（サーバーレスとEdgeの中間層）が成熟し、コールドスタート対策としてEdge Functionsと組み合わせることでレスポンスタイムとコストの両立が可能になっています。
- **Streaming SSRとの統合:** Next.js 16のPartial Prerendering（PPR）とEdge Functionsを組み合わせることで、静的シェルを即時配信しつつ動的部分のみEdgeでストリーミングする設計がパフォーマンス面で主流になっています。
- **リージョン指定とデータレイテンシの最適化:** 住人向けの位置情報・物件検索機能では、`export const preferredRegion` を活用し、ユーザーに最も近いリージョンでEdge実行することでAPI応答速度を改善できます。
- **バンドルサイズ制限への対応:** Edge Functionsは依然としてバンドルサイズ・実行時間に制約があるため、重い処理（画像処理、PDF生成など）はEdgeから分離し、Node.js RuntimeまたはBackground Functionsに委譲する設計が引越し費用計算などの重い処理を含むsumitsugiのようなプロダクトでは重要です。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x系の`satisfies`演算子と厳格な`noUncheckedIndexedAccess`設定が標準化しつつあり、型推論を保ったまま意図しない型拡大を防ぐパターンが浸透している。実務では配列・オブジェクトアクセス時の暗黙的`undefined`漏れを防ぐため、`tsconfig.json`で早期から有効化するのが定石。

- **ポイント2:** ZodやValibotなどのスキーマライブラリで「ランタイム検証」と「型定義」を単一ソースから生成するパターンが主流化し、APIバウンダリでの型安全性がコンパイル時だけでなく実行時にも保証されるようになっている。本プロジェクトでも`.claude/rules/standards.md`が指示する「Zodスキーマによる境界検証」はこの流れに合致している。

- **ポイント3:** テンプレートリテラル型とConditional Typesを組み合わせた「Branded Types（ブランド型)」が、IDやステータス文字列の誤用防止に広く使われ始めている。例えば本プロジェクトの`'draft' | 'public'`のようなUnion型ステータスも、将来的にブランド型やdiscriminated unionでより厳密に扱う余地がある。

- **ポイント4:** `tRPC`や`ts-rest`のようなEnd-to-Endで型を共有するアプローチが、フロントエンド/バックエンド間の型ズレを防ぐデファクトパターンとして定着し、手動のAPI型定義の二重管理を排除している。

- **ポイント5:** AIコード生成が普及した2026年現在、型エラーを「人間が解釈する」より「LLMが自動修正する」ワークフロー（本リポジトリの`build-fix`スキルや`build-error-resolver`エージェントのような仕組み）が重要になり、型安全性は「書く時」より「CIで検知・自動修復する時」の価値が高まっている。
