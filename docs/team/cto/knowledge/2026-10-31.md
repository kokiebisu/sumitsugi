# CTO Knowledge - 2026-10-31

## Daily Update (2026-10-31)

### 1. Next.js performance optimization 2026

- **React Compiler のデフォルト化:** Next.js 16ではReact CompilerがGAとなり、`useMemo`/`useCallback`の手動最適化が大幅に不要になる。既存コンポーネントの再レンダリング起因のパフォーマンス問題は、まずコンパイラ有効化で解決できるか確認すべき。

- **Partial Prerendering (PPR) の本格運用:** 静的シェルを即時配信しつつ動的部分をストリーミングする手法が安定版に入り、物件一覧ページのようにSEO要件（静的）とパーソナライズ（動的）が混在するページで特に効果が大きい。

- **Turbopack ビルドの標準化:** `bun run build`のビルド時間がTurbopackベースで大幅短縮されており、CI時間短縮にも直結する。Webpack依存のカスタムloaderが残っていないか棚卸しが必要。

- **Server Actions のキャッシュ戦略:** `use cache`ディレクティブの活用により、DB呼び出しを伴うServer Actionsの再検証コストを細粒度で制御できる。本物件のステータス更新（`draft`/`public`切替）など書き込み系アクションのレイテンシ改善に直結する。

- **画像・フォント最適化の自動化:** `next/image`のAVIF優先配信とフォントのセルフホスティングが標準になり、Core Web Vitals（特にLCP）改善がほぼ設定不要で得られる。物件写真が多いUIでは優先度の高い施策。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPartial Prerendering (PPR) が標準化され、静的シェルを即時配信しつつ動的部分だけをストリーミングする構成が主流になっています。初期表示（LCP）を大幅に改善できるため、物件一覧ページのような「ヘッダーは静的・物件データは動的」という構造に特に有効です。
- **ポイント2:** `loading.tsx` と `Suspense` 境界の粒度設計が重要な論点になっており、境界を細かく切りすぎるとウォーターフォールが発生し逆にTTIが悪化するケースが報告されています。データ取得をコロケーションしつつ、意味のある単位（例：物件詳細カード単位）でSuspenseを区切るのがベストプラクティスです。
- **ポイント3:** RSCペイロードのキャッシュ戦略として `use cache` ディレクティブ（Next.js Cache Components）が実用段階に入り、DBクエリ結果をコンポーネント単位でキャッシュできるようになっています。SSR時のDB負荷を抑えつつストリーミングの恩恵を両立できる点が評価されています。
- **ポイント4:** Server Actionsとストリーミングの組み合わせで「楽観的UI更新＋バックグラウンドでのサーバー再検証」パターンが定着しており、`useOptimistic` と組み合わせることでフォーム送信時の体感速度が向上します。
- **ポイント5:** エッジランタイム（Vercel Edge, Cloudflare Workers）でのRSCストリーミング対応が進み、地理的に分散したユーザーへのTTFB改善が可能になっています。ただしNode.js依存のライブラリ（一部のPDF生成やDB driverなど）はエッジ非対応なことが多く、ランタイム選択時の制約として注意が必要です。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1: tRPCの採用拡大とEnd-to-Endの型安全性** フロントエンドとバックエンドを同一TypeScriptモノレポで管理するプロジェクトでは、tRPCがREST/GraphQLに代わる選択肢として定着しつつあります。コード生成なしでクライアント・サーバー間の型が自動的に同期されるため、スキーマのドリフトによる本番バグを大幅に削減できます。

- **ポイント2: GraphQLはBFF/集約レイヤーとして役割を限定** 複数のマイクロサービスやサードパーティAPIを束ねる「集約層」としてのGraphQL需要は根強いものの、単一チーム・単一リポジトリのプロダクトではオーバーヘッド（リゾルバ設計、N+1対策、キャッシュ複雑性）が問題視され、シンプルな内部APIにはtRPCやRESTが選ばれる傾向です。

- **ポイント3: RESTは依然として外部公開APIのデファクト標準** パートナー連携や公開APIでは、言語非依存性・キャッシュ容易性・OpenAPI/Swaggerによるドキュメント自動生成の成熟度から、RESTが引き続き優位です。sumitsugiのような社外連携（決済、本人確認、不動産データ連携など）を想定するなら、外部向けはREST+OpenAPI、内部の管理画面やモバイルBFFはtRPCという併用が現実的です。

- **ポイント4: Zodを軸にしたスキーマ駆動開発の一体化** Zodスキーマをバリデーション・型推論・OpenAPI生成・tRPCの入出力定義すべてに共用する設計が主流になっています。本プロジェクトの標準（Zodによる入力検証）とも相性が良く、スキーマ変更時の手戻りを最小化できます。

- **ポイント5: エッジ/サーバーレス前提のAPI設計が前提化** Next.js App Router + Vercel/Cloudflare Workers環境では、レイテンシ最小化のためAPIレイヤーをエッジで実行することが標準になりつつあり、DB接続はコネクションプーラー（PlanetScale, Neon等)やHTTP経由のドライバを使う設計が必須になっています。

### 4. serverless edge computing 2026

- **エッジでのAI推論標準化:** 2026年はLLM推論自体がCDNエッジノードで実行可能になり、Cloudflare WorkersAIやVercel Edge Functionsのようなプラットフォームで軽量モデルをユーザーの近くで動かすのが一般的になった。sumitsugiのような物件検索体験では、画像の自動タグ付けやレコメンドをエッジ側で処理することでレイテンシを大幅に削減できる。

- **コールドスタート問題の実質的解消:** V8 isolateベースのランタイム（Cloudflare Workers, Deno Deploy）が成熟し、起動時間がミリ秒単位に収まるようになったため、Next.jsのSSRをエッジで動かす際のパフォーマンス懸念がほぼなくなった。Next.js 16のエッジランタイム対応を活かし、物件詳細ページなどアクセス頻度の高いルートをエッジにオフロードする価値が高い。

- **データのローカリティとコンプライアンスの両立:** 住宅・不動産データは個人情報を含むため、エッジでのデータレプリケーションとリージョンごとのデータ主権要件（国内法務対応）を両立させる設計が重要なトレンド。D1/Turso的な分散SQLiteやエッジKVストアを使い分け、法務確認待ちの現フェーズでもアーキテクチャを先取りしておく価値がある。

- **Bunとエッジランタイムの相性向上:** Bunのネイティブパフォーマンスとエッジ実行環境（WinterCG標準準拠のWeb APIベース）の組み合わせが2026年に実用段階に入り、ビルド時間とランタイム性能の両方で恩恵を受けやすくなった。現状のBun 1.x構成からエッジ対応へ移行する際の互換性コストが下がっている。

- **観測性・デバッグの難易度が依然ネック:** 分散実行による分散トレーシングの複雑さは解決しきっていない課題で、OpenTelemetry対応が進んだとはいえ、エッジ特有の「どのPoPで何が起きたか」の可視化はまだ発展途上。本番導入時はモニタリング投資を軽視しないことが実用上の重要ポイント。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** 2026年時点でパスワードレス認証が標準化し、WebAuthn/パスキーをプライマリな認証手段として実装すべき。フィッシング耐性があり、パスワード漏洩のリスクを根本的に排除できる。

- **セッション管理とトークンのローテーション:** JWTなどのアクセストークンは短寿命（5-15分）にし、リフレッシュトークンはローテーション方式で漏洩時の被害範囲を最小化する。httpOnly + Secure + SameSite=Strict属性でXSS/CSRF対策を徹底する。

- **多層防御としてのレート制限とデバイスフィンガープリンティング:** ログイン試行・パスワードリセットAPIにはIPベースだけでなくアカウントベースのレート制限を併用し、異常なデバイス/地理情報からのアクセスには追加認証（MFA）を要求する。

- **最小権限の原則とRLS（Row Level Security）:** 本プロジェクトのようなマルチユーザーのマーケットプレイス型プロダクトでは、DB層でのRow Level Securityを認証ロジックの最終防衛線として設置し、アプリケーション層のバグがデータ漏洩に直結しない構造にする。

- **シークレット管理の自動化:** APIキー・DB認証情報はすべて環境変数経由で管理し、定期的なローテーションとシークレットスキャン（CI内でのgit-secretsやgitleaks）を組み込み、ハードコードされた認証情報のコミットを構造的に防止する。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prismaのクエリエンジンが完全にRust依存から脱却し、WASM/TypeScriptネイティブ化が進んだことで、Supabaseのエッジ関数（Deno/Edge Runtime）からのコールドスタートが大幅に短縮され、サーバーレス環境でのDB接続オーバーヘッドが実用レベルまで下がっている。

- **ポイント2:** SupabaseのPgBouncer標準統合とPrismaの`directUrl`/`relationMode`設定により、コネクションプーリング問題（Lambda/Vercel Functionsでの同時接続過多）が設定レベルで解消しやすくなっており、本番運用での「too many connections」エラーのリスクが下がっている。

- **ポイント3:** Row Level Security（RLS）をPrisma側のミドルウェアやPolicy定義と組み合わせる運用が一般化し、アプリケーション層とDB層で二重に権限チェックを書く必要が減っている — 住宅情報のような個人情報を扱う`sumitsugi`のようなプロダクトでは、`seller`/`listing`テーブルへのRLS適用がセキュリティレビューの標準項目になりつつある。

- **ポイント4:** SupabaseのPostgreSQL拡張（pgvector、pg_cronなど）とPrisma Schemaの共存が改善され、「物件のおすすめ検索」のようなベクトル検索機能をORMスキーマ管理のまま追加できるようになってきている。

- **ポイント5:** マイグレーション管理において、PrismaのMigrate機能とSupabaseのブランチ機能（開発用DBブランチ）を組み合わせたプレビュー環境でのスキーマ検証が標準ワークフロー化しており、`draft`/`public`のようなステータス変更を含むスキーマ変更も本番反映前にプレビューDBで安全に検証できる。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGCとコンポーネントモデルの成熟により、Rust製WasmモジュールがJSグルーコードなしで直接ホスト環境と連携できるようになり、バンドルサイズと起動レイテンシが大幅に削減されています。CPU負荷の高い処理（画像処理、PDF生成等）をフロントエンドにオフロードする選択肢として実用段階に入りました。

- **ポイント2:** `wasm32-wasip2`とWASIプレビュー2の普及で、サーバーサイドでもRust/Wasmをサンドボックス化されたプラグイン実行環境として使う事例が増加。マルチテナントSaaSでユーザー定義ロジックを安全に実行する用途（例: 料金計算ルールのカスタマイズ）に向いています。

- **ポイント3:** SIMD対応とタイアードコンパイル（Baseline→Optimizing）の改善により、純粋なネイティブ実行比で80-90%程度の性能に到達するケースも増えており、「遅いから避ける」という判断は見直す価値があります。ただしDOM操作を伴う処理はJS境界超えのオーバーヘッドが依然大きく、適用箇所の見極めが重要です。

- **ポイント4:** `wasm-bindgen`や`wasm-pack`のビルドパイプラインがCI/CDに組み込みやすくなり、Next.jsのようなフレームワークとの統合コストが下がっています。ただしチームにRust経験者が少ない場合、デバッグ・保守コストが性能メリットを上回ることがあるため、導入は限定的なホットパスに絞るのが現実的です。

- **ポイント5:** エッジランタイム（Cloudflare Workers等）でのWasm実行がデフォルト選択肢になりつつあり、コールドスタートの速さとセキュリティ分離の両立という観点で、Node.js/V8ベースより優位になるケースが増えています。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 15以降で安定化したPPRにより、静的シェルと動的コンテンツを同一ルートで組み合わせられるため、`loading.tsx`に依存せず初期表示速度（TTFB）を大幅改善できる。sumitsugiの物件詳細ページのような「静的な基本情報＋動的な空室状況」構成に適している。

- **Server Actions の型安全な活用拡大:** `use server`ディレクティブとZodバリデーションを組み合わせたパターンが定番化し、APIルートを介さずフォーム送信・データ更新を実装するケースが増えている。`listing/`配下のフォーム処理ではServer Actions+Zodで境界検証を徹底すべき。

- **キャッシュ戦略の明示化（`revalidate`/`cache: 'no-store'`の使い分け）:** Next.js 15以降でfetchのデフォルトキャッシュ挙動が変わり、暗黙のキャッシュに依存するコードはバグの温床になる。物件ステータス（`draft`/`public`）のような可変データは明示的な再検証戦略が必須。

- **Parallel Routes / Intercepting Routes によるモーダル体験:** 物件一覧→詳細モーダルのようなAirbnb的UXは、`@modal`スロット+Intercepting Routesで実装するのが2026年時点のベストプラクティス。ブラウザバックやディープリンクも自然に機能する。

- **React Server Components とクライアント境界の最小化:** `'use client'`境界を機能単位で小さく切り出し、認証状態（`auth-context.tsx`）のようなインタラクティブ部分だけをクライアントコンポーネント化する設計が、バンドルサイズとパフォーマンスの両面で推奨されている。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Vercel Edge FunctionsはV8 isolateベースのため、Node.js Runtimeに比べてコールドスタートが数十ms単位で短縮される。認証チェックやリダイレクト、A/Bテストの振り分けなど軽量処理をEdgeに寄せることで、Next.js 16のミドルウェア層全体のレイテンシを削減できる。

- **ポイント2:** Edge Runtimeはfsやネイティブモジュールなど一部のNode.js APIを利用できない制約があるため、DBアクセスはHTTP経由のドライバ（Postgres over Fetch、PlanetScaleなど）を使う必要がある。本プロジェクトでSupabase/Prisma等を使う場合、Edge対応ドライバへの切り替えコストを事前に見積もるべき。

- **ポイント3:** Vercelのリージョン最適化（`regions`設定）により、Edge FunctionをユーザーのPOP（Point of Presence）に近い場所で実行できるため、日本国内ユーザー中心のsumitsugiでは`hnd1`（東京）リージョン指定でレイテンシを最小化できる。

- **ポイント4:** ISR（Incremental Static Regeneration）とEdge Functionsを組み合わせたハイブリッド戦略が2026年のベストプラクティス。物件一覧ページのような高頻度アクセスだが更新頻度は低いページはEdge上でキャッシュしつつ、`stale-while-revalidate`で裏側更新することでTTFBを大幅改善できる。

- **ポイント5:** Edge Functionsの実行時間・メモリ制限（デフォルト25秒/128MB程度）に注意し、PDF生成や画像処理など重い処理はNode.js RuntimeまたはVercel Blob+バックグラウンドジョブに分離する設計が推奨される。契約書PDF生成など本サービスの引越しフローはEdgeではなくServerless/Node Runtimeに留めるべき。

### 10. TypeScript type safety patterns 2026

- **スキーマファースト設計の定着:** Zodなどのランタイムスキーマから型を自動導出する`z.infer`パターンが標準化し、API境界・フォーム・DBクエリで「型定義」と「実行時検証」の二重管理が不要になった。本プロジェクトでもZodスキーマを型定義のSingle Source of Truthとして扱うことで、バリデーション漏れによる実行時エラーを設計段階で排除できる。

- **`satisfies`演算子とconst assertionの活用拡大:** オブジェクトリテラルの型を狭めすぎず、かつ構造的な整合性を保証する`satisfies`が設定オブジェクトや列挙的な定数（`site-config.ts`のような構成ファイル）で定番化。型推論の恩恵を失わずに型安全性チェックを入れられるのが実用上の利点。

- **判別可能なUnion型による網羅性チェック:** `'draft' | 'public'`のようなステータス型をswitch文で分岐する際、`default`に`never`型のアサーションを入れる網羅性チェック（exhaustiveness check）が標準プラクティス化。新しいステータス値を追加した際にコンパイルエラーで検知漏れを防げるため、本プロジェクトのような状態遷移が多いドメインでは必須パターン。

- **エラーハンドリングのResult型シフト:** 例外ベースの`try/catch`から`Result<T, E>`型（neverthrow等）やTS 5.x系の型推論改善を活かした明示的エラー型へのシフトが進行中。「失敗しうる処理」が型シグネチャに現れることで、呼び出し側のハンドリング漏れをコンパイル時に検出できる。

- **AIコード生成との相性を意識した型設計:** LLMが生成するコードの型チェック精度を上げるため、関数シグネチャやZodスキーマに意図（単位・制約・ブランド型）を明示する傾向が強まっている。例えば`type ListingId = string & { __brand: 'ListingId' }`のようなブランド型でID誤用をコンパイル時に防ぐパターンが、AI協働開発が主流の現場で再評価されている。
