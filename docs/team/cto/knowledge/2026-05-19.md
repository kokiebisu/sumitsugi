# CTO Knowledge - 2026-05-19

## Daily Update (2026-05-19)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを削減するため、データフェッチはサーバー側で完結させ、`"use client"` は本当にインタラクティブな部分だけに限定する。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降で安定化したPPRにより、静的シェルを即座に返しつつ動的コンテンツをストリーミングする設計が標準化されている。静的・動的の二択思考から脱却すべき。

- **`use cache` ディレクティブによるきめ細かいキャッシュ制御:** ページ単位ではなく関数・コンポーネント単位でキャッシュ戦略を定義できる新APIが主流に。`unstable_cache` からの移行を進め、TTLとタグベース無効化を組み合わせる。

- **Bundle Analyzerとサーバーコストの両軸監視:** `@next/bundle-analyzer` で定期的にクライアントバンドルを計測しつつ、Vercel/CloudflareのEdge関数コールド起動時間もSLO対象に含める運用が必須。

- **画像・フォントの自動最適化を「デフォルトON」前提に設計:** `next/image` のサイズ最適化と `next/font` によるフォントインライン化は今や当たり前。むしろカスタムローダーや外部CDNとの干渉を避ける設計判断の方が重要になっている。

### 2. React Server Components streaming 2026

- **Suspense境界の細粒度化が主流に:** 2026年のRSCでは、コンポーネント単位でのストリーミング制御が成熟し、ページ全体ではなく意味のある単位（ウィジェット・セクション）でSuspense境界を設計するのがベストプラクティスとなっている。

- **PPR（Partial Prerendering）との組み合わせが実用段階へ:** Next.js 15+でPPRが安定し、静的シェルを即座に配信しつつ動的コンテンツをストリームで差し込むハイブリッドアーキテクチャが、パフォーマンス最適化の標準パターンになっている。

- **Server ActionsとStreamingの統合によるUX向上:** フォーム送信後のUIフィードバックをストリーミングで段階的に返すパターンが普及し、楽観的更新（optimistic UI）とサーバー側バリデーションの組み合わせがボイラープレートなしで実装できる。

- **キャッシュ戦略の再設計が必須:** RSCのストリーミングはキャッシュの粒度に直結するため、`fetch`レベル・ルートレベル・コンポーネントレベルの3階層でキャッシュ戦略を設計しないと、CDNヒット率の低下やウォーターフォールが発生しやすい。

- **エッジランタイムでのストリーミング対応が前提化:** Vercel/Cloudflare Workers等のエッジ環境でRSCストリーミングが安定動作するようになり、グローバルなTTFB最適化のためにエッジでのレンダリングを前提にアーキテクチャを組む時代になっている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年時点でtRPCはNext.js/TypeScriptスタックにおけるデファクトに近づいており、クライアント・サーバー間でZodスキーマを共有することでランタイムエラーをゼロに近づける設計が主流になっている。

- **GraphQLの適所が明確化:** GraphQLはBFF（Backend for Frontend）や複数クライアントが異なるデータ形状を必要とするケースに絞られ、単一フロントエンドのプロジェクトではオーバーエンジニアリングとみなされるようになった。

- **REST + OpenAPI 3.1の再評価:** Zodベースの`@hono/zod-openapi`や`ts-rest`により、RESTでもtRPC同等の型安全性が実現可能になり「RESTかtRPCか」の二択ではなく用途別の使い分けが進んでいる。

- **エッジ・ストリーミングへの対応が設計制約に:** Cloudflare WorkersやVercel Edgeでのデプロイが標準化し、長時間コネクションを前提とするGraphQL Subscriptionより、Server-Sent Events（SSE）やHTTP Streamingとの相性が設計選定の重要軸になっている。

- **AIエージェント連携を見据えたAPI設計:** MCPプロトコルの普及により、APIをエージェントが呼び出すことを前提とした「ツール互換設計」（明確なスキーマ・エラーメッセージ・冪等性）が求められ、RESTとtRPCどちらでも機械可読な仕様の整備が必須になっている。

### 4. serverless edge computing 2026

- **エッジでのAI推論が主流化:** 2026年はLLMの量子化・蒸留技術の成熟により、WebAssembly経由でエッジノード上での小型モデル推論が現実的になった。レイテンシ敏感なユースケース（リアルタイム翻訳、不正検知）ではクラウド往復を排除できる。

- **Durable Objects / Actor モデルの台頭:** Cloudflare Durable ObjectsやFastly Compute@Edgeが示すように、エッジ上でステートフルなActorを動かすパターンが定着。従来「エッジ＝ステートレス」という前提が崩れ、分散セッション管理やリアルタイムコラボレーションをエッジで完結できる。

- **コールドスタート問題の実質的解消:** V8 Isolateベースのランタイムが標準となり、Node.js/コンテナ系と異なりサブミリ秒起動が当たり前に。ただしNode.js互換APIの網羅性にまだギャップがあり、依存ライブラリの互換性検証が依然コストになる。

- **エッジ×可観測性のギャップ:** 分散エッジノード（200+PoP）でのトレーシング・ログ集約はまだ成熟途上。OpenTelemetryのエッジ対応は進んでいるが、デバッグ体験はセントラルクラウドに比べ劣る。本番投入前に可観測性戦略を設計しないと運用地獄になる。

- **コスト構造の再評価が必要:** リクエスト数課金モデルはトラフィックスパイクに強い反面、常時接続・ロングポーリング系ワークロードでは割高になる。Next.jsのEdge Runtimeを全面採用する前に、ワークロードプロファイル別のコスト試算が必須。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準採用:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の主流となり、フィッシング耐性と利便性を両立できる。主要プラットフォームのサポートが成熟した今、新規サービスではパスキーをデフォルト認証として設計すべき。

- **ゼロトラスト・継続認証:** ログイン時の一度の認証ではなく、セッション中の行動パターン・デバイス状態・位置情報を継続的に評価するリスクベース認証が不可欠。異常検知時に再認証を要求するアダプティブMFAと組み合わせることで多層防御を実現。

- **AIを活用した認証情報詐取への対策:** LLMを悪用したリアルタイムフィッシングやDeepfake音声による認証バイパス攻撃が増加。セッショントークンの短命化（15分以下）とDevice Binding（デバイス証明書紐付け）が有効な対抗策となる。

- **OAuth/OIDCの実装セキュリティ強化:** PKCE必須化・DPoP（Demonstrating Proof of Possession）によるトークン盗用対策・Refresh Token Rotation の徹底が2026年標準。特にBFFパターン（Backend for Frontend）でトークンをサーバーサイドに閉じ込める設計が推奨される。

- **サプライチェーン経由の認証ライブラリ汚染対策:** npm/PyPIパッケージへの悪意ある改ざんによる認証情報窃取が増加傾向。依存ライブラリのSBOM管理・Sigstoreによる署名検証・Lock fileの厳格な運用が最低限の防衛ラインとなる。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のエッジランタイム対応成熟:** Prisma Driver Adapters が安定化し、Cloudflare Workers / Vercel Edge Functions から直接 Supabase Postgres に接続できるようになった。コネクションプーリングの複雑さが大幅に軽減されている。

- **Supabase の pgvector 活用が主流に:** RAG（検索拡張生成）アーキテクチャにおいて、pgvector 拡張による埋め込みベクトル検索が標準的な選択肢となった。別途ベクターDBを立てるコストなしに Postgres 一本で完結できる点が評価されている。

- **Row Level Security (RLS) の設計が品質の分水嶺:** Supabase では RLS ポリシーの設計ミスがパフォーマンスボトルネックになるケースが増加。`auth.uid()` を使ったポリシーはインデックスと組み合わせて設計しないと大規模テーブルでフルスキャンが発生する。

- **Prisma + Supabase の型安全性:** `prisma generate` で生成した型を Supabase の `Database` 型と統合する層が増えてきたが、2つの型システムが並走する管理コストに注意。どちらかに統一する判断（例：Drizzle ORM への移行）も現実的な選択肢として検討すべき。

- **Branching 機能による開発フローの変革:** Supabase の Database Branching（Preview Branches）が GA 化し、PR ごとに独立した DB 環境を持てるようになった。CI/CD パイプラインのマイグレーションテストが格段に安全になるため、積極的に採用を推奨する。

### 7. WebAssembly Rust performance 2026

- **Component Model の本格普及:** WebAssembly Component Model（WASI 0.2）が2025年末に安定化し、Rustで書いたWasmコンポーネントが言語間で型安全に連携できるようになった。`cargo component`ツールチェーンが成熟し、フロントエンド・バックエンド・エッジ関数の境界を越えた再利用が実用レベルに達している。

- **SIMD・スレッド対応の拡充:** Wasm SIMD（Fixed-width SIMD）が全主要ブラウザ・ランタイムで安定稼働し、Rustの`std::arch`経由のSIMD最適化がそのままWasmにコンパイルできる。画像処理・機械学習推論などのCPU集約処理でネイティブ比80〜95%のスループットが報告されている。

- **WASIp2 + Wasmtime によるサーバーサイド高速化:** Fastly・Cloudflare・Fermyon等のエッジプラットフォームがWASIp2ベースのRust Wasmを採用し、コールドスタートが1ms未満。Dockerコンテナに比べ起動コストとメモリフットプリントが大幅に削減できる。

- **`wasm-opt` + `twiggy` によるバイナリサイズ管理:** Rustのゼロコスト抽象化はWasmバイナリサイズに影響するため、`wasm-opt -Oz`とLTO・`panic=abort`設定の組み合わせが標準プラクティスになっている。`twiggy`でシンボルサイズを分析し、不要な依存を削るワークフローがCI必須になりつつある。

- **Rust ↔ JS バインディングの自動化成熟:** `wasm-bindgen`と`tsify`の組み合わせにより、RustのstrutがTypeScriptの型定義に自動変換されるようになった。Next.js（App Router）との統合も`next-wasm`プラグインで簡略化されており、Rustロジックをフロントエンドに組み込む際のグルーコスト（ボイラープレート）が大幅に減少している。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** 2026年時点でのベストプラクティスは「デフォルトServer Components、必要な箇所だけClient Components」。`'use client'`境界を最小化することで、バンドルサイズとTTIを大幅に削減できる。

- **Partial Prerendering (PPR) の本格活用:** Next.js 15+で安定化したPPRにより、静的シェルと動的コンテンツを同一ルートに共存させることが可能に。`<Suspense>`境界がそのままPPRの分割単位となるため、設計時からSuspense配置を意識することが重要。

- **Server Actions によるミューテーション統一:** API Routeを新規作成せず、Server ActionsでCRUD操作を完結させるパターンが主流。フォームの`action`属性に直接バインドでき、楽観的UI更新（`useOptimistic`）との組み合わせでUXも損なわない。

- **`use cache` ディレクティブによる細粒度キャッシュ:** `fetch`キャッシュからコンポーネント・関数レベルの`use cache`へ移行が進む。キャッシュタグ（`cacheTag()`）とオンデマンド再検証（`revalidateTag()`）を組み合わせることで、CDNレベルのパフォーマンスをアプリ層で制御可能。

- **`after()` APIによる非同期副作用の分離:** レスポンス送信後に実行される`after()`を使い、ログ・アナリティクス送信・通知などの副作用をリクエストパスから切り離せる。ユーザーへのレスポンス速度を犠牲にせずに後処理を実装できる。

### 9. Vercel Edge Functions optimization 2026

- **Edge RuntimeでのStreaming最優先:** 2026年はEdge FunctionsでのStreaming Response（`ReadableStream`）が標準実装となり、TTFB削減に直結する。Next.js App RouterのServer Componentsとの組み合わせでレイテンシを50ms以下に抑えられるケースが増えている。

- **Cold Start撲滅のためのMiddleware設計:** Edge Middlewareはグローバル配置によりCold Startがほぼゼロだが、処理ロジックを肥大化させるとCPU時間制限（通常50ms）に引っかかる。認証・リダイレクト・A/Bテストのみに絞り、ビジネスロジックはEdgeに持ち込まない設計が鉄則。

- **KVストア（Vercel KV / Upstash Redis）との連携で状態管理を最適化:** ステートレスなEdge FunctionsにセッションやFeature Flagsを持たせるには、Edge-compatible KVストアが必須。レイテンシは1-5ms程度で、DBへのフォールバックを避けるキャッシュ層として機能する。

- **ISR + Edge Cacheの二段構え:** Incremental Static Regeneration（ISR）でコンテンツをEdge Cacheに乗せ、動的部分だけEdge Functionsで差し込むハイブリッド戦略が2026年のコスト効率・パフォーマンスのベストプラクティス。`stale-while-revalidate`の積極的活用がポイント。

- **Observabilityの強化が急務:** Edge環境はログ収集が従来のサーバーより難しく、Vercel LogDrains + OpenTelemetryによる分散トレーシングの整備が遅れがちな組織が多い。Edge Functionのエラー率・P95レイテンシを可視化しないまま本番運用するのは技術的負債になる。

### 10. TypeScript type safety patterns 2026

- **Branded Types の主流化:** `type UserId = string & { _brand: 'UserId' }` のようなブランド型が標準パターンとなり、プリミティブ型の誤用をコンパイル時に検出できるようになった。特にドメイン境界での型安全性が大幅に向上している。

- **satisfies 演算子の積極活用:** TypeScript 4.9以降の `satisfies` 演算子が2026年では必須知識となり、型推論を保持しつつ型チェックを行うことで `as` キャストの排除が進んでいる。

- **Zod + tRPC による End-to-End 型安全:** フロントエンドからバックエンドまで単一のスキーマ定義で型を伝搬させるアーキテクチャが定着し、実行時バリデーションとコンパイル時型チェックを同時に担保するのが標準構成になった。

- **Template Literal Types による API 契約:** `type Route = \`/api/${string}\`` のようなパターンで、URLルーティングやイベント名などの文字列を型レベルで制約する手法が広く普及し、typoによるバグが激減している。

- **noUncheckedIndexedAccess の有効化が常識に:** `tsconfig.json` で `noUncheckedIndexedAccess: true` を有効化し、配列・オブジェクトアクセス時に必ず `undefined` チェックを強制するのがチームの標準設定となり、実行時エラーの大幅削減につながっている。
