# CTO Knowledge - 2026-07-04

## Daily Update (2026-07-04)

### 1. Next.js performance optimization 2026

- **ポイント1:** Next.js 16ではTurbopackがビルド・開発サーバーのデフォルトになり、ローカル開発のHMRと本番ビルド時間が大幅に短縮された。大規模なsrc/appディレクトリ構成でも型チェックとの並列実行でCI時間を圧縮できる。
- **ポイント2:** `use cache`ディレクティブとPartial Prerendering（PPR）の組み合わせが主流になり、静的な物件一覧と動的な予約状況を1ページ内で分離してキャッシュできる。物件詳細ページのようなSEO重視ページで特に効果が大きい。
- **ポイント3:** React Compilerの安定化により、`useMemo`/`useCallback`の手動最適化が不要になりつつある。ただしフォームや認証コンテキストなど副作用の多いコンポーネントは引き続き明示的な最適化とプロファイリングが推奨される。
- **ポイント4:** Server ComponentsとClient Componentsの境界設計がパフォーマンスの決め手になっており、認証状態（auth-context.tsx）のような重いコンテキストをクライアント境界の末端に押し込むことでハイドレーションコストを削減できる。
- **ポイント5:** 画像・フォント最適化はNext/Imageの自動AVIF配信とセルフホストフォントが標準化し、Core Web Vitals（特にLCP）改善の主要因になっている。物件写真中心のUIでは特に優先度が高い。

### 2. React Server Components streaming 2026

- **ポイント1:** RSCのストリーミングは`loading.tsx`やSuspenseバウンダリの粒度設計が肝で、ウォーターフォールを避けるにはデータ取得を並列化し、クリティカルパス外のコンポーネントを積極的に別バウンダリに切り出すのがベストプラクティスとして定着してきている。
- **ポイント2:** Partial Prerendering (PPR) がNext.jsで安定版に近づき、静的シェルを即座に返しつつ動的部分だけをストリームする構成が標準化しつつあるため、CDNキャッシュとパーソナライズを両立させたい引越し費用計算や物件検索UIに向く。
- **ポイント3:** Server Actionsとの組み合わせでフォーム送信後の再検証（revalidate）がストリーミングレンダリングと絡むと、キャッシュ無効化のタイミングがずれてUIがちらつくケースがあるため、`revalidateTag`の粒度を細かく設計する必要がある。
- **ポイント4:** クライアントバンドルサイズ削減効果は依然大きいが、RSCペイロード自体（シリアライズされたツリー）がリスト表示系ページで肥大化しやすく、`use cache`ディレクティブや選択的ハイドレーションでTTFB/TTIのバランスを取る運用ノウハウが重要になっている。
- **ポイント5:** エラーバウンダリとストリーミングの組み合わせでは、一部コンポーネントのサーバーエラーが全体のストリームを壊さないよう、`error.tsx`をSuspense単位で細かく配置する設計が事実上のデファクトになってきた。

### 3. API design REST GraphQL tRPC 2026

## API設計トレンド（REST / GraphQL / tRPC）2026年視点

- **ポイント1: tRPCがNext.js + TypeScriptスタックの第一選択肢に定着** — フルスタックTypeScriptプロジェクトでは、スキーマ定義とクライアント型を自動同期できるtRPCが、REST+OpenAPI生成やGraphQLコードジェネレーションより開発速度で優位。sumitsugiのようなNext.js App Router構成では、社内向けAPI（管理画面、内部ダッシュボード）にtRPCを採用すると型安全性とDX（開発体験）が大きく向上する。

- **ポイント2: 公開APIやモバイル/サードパーティ連携にはRESTが依然として現実解** — tRPCは同一TypeScriptモノレポ内でこそ真価を発揮するが、外部パートナー連携やモバイルアプリ、Webhookなど言語非依存の境界にはREST（+ Zodによるスキーマバリデーション）が安定選択。物件情報の外部API公開（不動産ポータル連携など）を見据えるなら、内部tRPC・外部RESTのハイブリッド構成が現実的。

- **ポイント3: GraphQLは複雑な関係性クエリを持つドメインに限定採用** — フロントエンドが多様なデータ取得パターンを必要とする場合（物件検索の複雑なフィルタ・関連データの一括取得など）はGraphQLが有効だが、単一チーム・単一フロントエンドの現状ではオーバーエンジニアリングになりやすい。導入は「複数クライアント×複雑なクエリ要件」が揃ってから検討すべき。

- **ポイント4: Server ActionsとtRPCの役割分担が明確化** — Next.js 16のServer Actionsはフォーム送信など単純なミューテーションに適し、tRPCは型安全なクエリ・複雑な状態管理・キャッシュ連携（React Query統合）が必要な箇所に使い分けるのが2026年のベストプラクティス。両方を無秩序に混在させるとデータフェッチ層が分裂するため、境界を明文化すべき。

- **ポイント5: エッジランタイム対応とストリーミングがAPI設計の必須要件に** — Vercel Edge FunctionsやNext.jsのストリーミングSSRが標準化する中、APIレイヤーもレイテンシ最適化（エッジ実行可能なtRPCプロシージャ、部分レスポンスのストリーミング）を前提に設計する必要がある。特にモバイル回線での物件一覧表示など、初期表示速度が体験を左右する箇所は優先的にストリーミング対応を検討すべき。

### 4. serverless edge computing 2026

- **エッジ推論の標準化:** Cloudflare Workers AIやVercel Edge Functionsなど、エッジ上でのLLM推論・軽量モデル実行が2026年には標準的な選択肢となり、レイテンシに敏感なUX(物件検索のオートコンプリート等)をリージョン中心からエッジ中心に移行できる。

- **コールドスタート問題の実質解消:** V8 isolateベースのランタイム(Cloudflare Workers, Deno Deploy)がコールドスタートを1桁ミリ秒台に抑え、サーバーレスでも常時稼働サーバーに近いレスポンス性能を確保できるようになった。Next.js 16のEdge Runtimeとの親和性が高い。

- **データレイヤーのエッジ化:** Turso/Cloudflare D1のようなSQLiteベースの分散DBが普及し、読み取り中心のワークロード(物件一覧・検索)をユーザーに地理的に近いレプリカから配信できる。書き込み一貫性とのトレードオフ設計が引き続き重要。

- **コスト構造の変化:** 実行時間課金からリクエスト数+CPU時間の細粒度課金にシフトしており、トラフィックが不安定な立ち上げ期のsumitsugiのようなプロダクトには固定サーバーより有利。ただしバーストトラフィック時の予測不能な費用増には注意が必要。

- **観測性・デバッグの複雑化:** エッジ分散実行はトレーシング(OpenTelemetry)なしではデバッグが困難になるため、早期からの分散トレーシング導入が開発ベロシティを左右する。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の主流化:** パスワードレス認証がデフォルト選択肢となり、フィッシング耐性のある認証情報がアカウント乗っ取りの根本的な対策として普及している。実装コストも下がっているため、新規サービスは最初からパスキー対応を前提に設計すべき。

- **継続的リスクベース認証:** ログイン時の一回限りの認証から、デバイス・位置情報・行動パターンを常時評価する適応型認証へのシフトが進んでいる。高リスク操作（決済・住所変更等）にはステップアップ認証を組み込むのが標準的なアプローチになっている。

- **トークンの適切な保存とローテーション:** JWTやセッショントークンをlocalStorageに保存する実装は依然として狙われやすく、httpOnly + Secure + SameSite Cookieやショートリブドアクセストークン＋リフレッシュトークンローテーションが必須要件になっている。

- **SaaS/API連携のスコープ最小化:** OAuthやAPIキー連携が増える中、過剰な権限スコープの付与が侵害時の被害範囲を広げる主因となっており、最小権限原則とトークンの定期失効・監査ログが重要視されている。

- **サプライチェーン経由の認証情報侵害への警戒:** 依存パッケージや外部連携先経由でのシークレット漏洩事例が増加しており、シークレットのハードコード禁止（既存ルール通り）に加え、CI/CDでのシークレットスキャンと環境変数管理の徹底が求められている。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMの型安全性とエッジ対応:** Prisma 6以降はEdge Runtime対応が進み、Vercel EdgeやCloudflare Workersでの直接DB接続が現実的に。ただしコネクションプーリング（PgBouncer/Prisma Accelerate）は依然必須で、サーバーレス環境でのコネクション枯渇対策を初期設計に組み込むべき。

- **SupabaseのRLS（Row Level Security）中心設計:** アプリ層だけでなくDB層でも認可を強制するRLSがデファクト化しつつある。sumitsugiのようなマルチロール（前の住人/次の住人）プラットフォームでは、Prismaのアプリ層バリデーションとSupabase RLSの二重防御が漏洩防止の実用解。

- **Prisma × Supabase の使い分け:** マイグレーションとスキーマ管理はPrisma Migrateで一元化しつつ、リアルタイム機能（物件ステータス変更通知など）はSupabase Realtimeを併用する構成が主流。両者のスキーマ定義がズレないよう、CI上でスキーマdiffチェックを自動化するのが実用的。

- **ブランチDB（Preview環境）の一般化:** SupabaseのDatabase Branching機能でPR毎に独立したDBブランチを立てる運用が定着。draft/public物件ステータスのような状態遷移テストを本番データに触れず安全に検証できるため、E2Eテストの信頼性向上に直結する。

- **pgvector活用によるレコメンド機能:** 物件検索・マッチング（IC相談マッチング等）でSupabaseのpgvector拡張を使った埋め込み検索が普及。追加のベクトルDBを持たずPostgres単体で完結できるため、運用コストと構成複雑度を抑えられる点がMVP段階のプロダクトに適している。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC（Garbage Collection提案）とcomponent modelの標準化が進み、RustからWasmへのコンパイル時にGCランタイムを介さず直接メモリ管理できる利点がより明確になり、C++/Goに対する性能優位性が拡大している。
- **ポイント2:** wasmtimeやwasmerのAOTコンパイル（Cranelift/LLVM backend）が成熟し、cold startのオーバーヘッドが大幅に削減されたため、エッジ関数やサーバーレス用途でのRust+Wasm採用が実用レベルに到達している。
- **ポイント3:** SIMD命令セット（wasm-simd128）とmulti-threading（wasm-threads提案）が主要ブラウザ・ランタイムで安定サポートされ、画像処理や物件マップのレンダリングなどCPU負荷の高いクライアント処理をRust製Wasmモジュールにオフロードする選択肢が現実的になっている。
- **ポイント4:** バンドルサイズ最適化ツール（wasm-opt, twiggy）とtree-shaking連携が進化し、Next.js 16のRSC環境下でもWasmモジュールの遅延ロードが容易になったため、初期表示速度を犠牲にせず重い計算処理を導入できる。
- **ポイント5:** sumitsugiのような物件検索・比較UIでは、フィルタリングやスコアリングロジックをRust+Wasmに移行することでJS実装比2〜5倍の処理速度向上が報告されており、将来的な物件検索の高度化（複雑な条件マッチング）を見据えた技術投資として検討価値がある。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 15以降で導入されたPPRが16系で安定版となり、静的シェルと動的コンテンツを1つのルートで組み合わせられるように。物件一覧ページなど「共通レイアウトは静的・在庫状況は動的」という構成に最適で、TTFBを大幅短縮できる。

- **Server ActionsとuseActionState/useOptimisticの定着:** フォーム送信（お問い合わせ・予約申込など）をAPI Routeなしで完結させるパターンが主流化。楽観的UI更新とバリデーションエラー表示が標準フックで簡潔に書けるようになり、`src/app`配下のフォーム実装コード量を削減できる。

- **キャッシュ制御の明示化（`use cache`ディレクティブ）:** 暗黙的キャッシュから明示的キャッシュ（`use cache` + `cacheTag`/`cacheLife`）への移行が進み、物件データのようにセラー更新頻度がまちまちなコンテンツで「いつ再検証すべきか」をコード上で宣言できる。キャッシュ起因のバグ（古い物件ステータス表示など）を防ぎやすい。

- **Route Groups + Parallel Routesによるダッシュボード分割:** `@modal`や`@sidebar`のようなパラレルルートを使い、物件詳細ページのモーダル（内見予約フォーム等）を独立したエラーバウンダリ・ローディング状態で管理する構成が一般化。ページ遷移を伴わないUXと、コンポーネント責務の分離を両立できる。

- **Turbopackのビルド標準化とEdge/Node runtimeの使い分け最適化:** Turbopackが本番ビルドのデフォルトとなり大規模モノレポでもビルド時間が安定。認証チェックなど軽量処理はEdge runtime、Prisma等DBアクセスを伴う処理はNode runtimeと明示的に使い分ける設計が定石化しており、`src/lib/data.ts`のようなデータ層の実行環境をルートごとに最適化する余地が広がっている。

### 9. Vercel Edge Functions optimization 2026

- **リージョン最適化とデータ局所性:** Edge Functionsは実行リージョンをリクエスト発生地に自動選択するが、DBやKVストアが単一リージョンにある場合はレイテンシが逆に悪化するため、Vercel KV/Postgresのリードレプリカ配置とEdge Config活用でデータ層もエッジに近づけることが重要。

- **バンドルサイズとコールドスタート:** Edge RuntimeはNode.js APIの一部（fs, net等）が使えない制約があるため、依存関係を最小限に保ちTree-shakingを徹底することで、実行時間制限（CPU時間ベース課金）内での安定動作とコスト削減を両立できる。

- **Streaming SSRとの統合:** Next.js 16のPartial Prerendering (PPR) とEdge Functionsを組み合わせることで、静的シェルを即座に配信しつつ動的部分のみをエッジでストリーミング生成でき、TTFBを大幅短縮できる。sumitsugiの物件検索・地図表示のような動的コンテンツに有効。

- **Middleware統合による認証最適化:** 認証チェック（`auth-context.tsx`連携）をEdge Middlewareに寄せることで、オリジンサーバーへのラウンドトリップ前にリダイレクト/拒否を完結させ、不要なオリジン負荷とレイテンシを削減できる。

- **Observability強化:** 2026年時点でVercelはEdge Function向けのOpenTelemetry統合を強化しており、`console.log`禁止ルールのある本プロジェクトでは、構造化ログ＋分散トレーシングを本番監視の標準にすべき（本番デバッグ時の可視性確保）。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.xの`satisfies`演算子が定着し、型推論を保ちながら型チェックする書き方が標準化。設定オブジェクトやルーティング定義など「形は保証しつつ推論も欲しい」箇所で必須パターンになっている。
- **ポイント2:** Zodなどのスキーマライブラリでランタイム検証と型定義を一元化する「Schema-first」開発が主流に。APIレスポンスやフォーム入力など外部境界での型安全性はコンパイル時だけでは不十分という認識が広がっている（本プロジェクトのZod活用方針とも合致）。
- **ポイント3:** テンプレートリテラル型やconst型パラメータを使い、文字列ベースのルートパスやi18nキーをコンパイル時に検証する「型レベルプログラミング」の実用化が進む。存在しないURLやキーを打鍵ミスで参照するバグをビルド段階で防げる。
- **ポイント4:** `unknown`優先・`any`根絶の徹底が定番化し、ESLintの`no-explicit-any`をCIで強制するチームが増加。型安全性の"抜け道"を塞ぐことがコードレビューの標準チェック項目になっている。
- **ポイント5:** tRPCやHono RPCのようなエンドツーエンド型推論フレームワークにより、フロントエンド⇔バックエンド間で型定義を共有し、APIスキーマのドリフトをビルド時に検出する構成が拡大。Next.js App Router構成でもServer Actionsの型共有として応用が進んでいる。
