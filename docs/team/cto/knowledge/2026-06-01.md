# CTO Knowledge - 2026-06-01

## Daily Update (2026-06-01)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するためにRSCをデフォルトとし、`'use client'`はインタラクティブな葉コンポーネントのみに限定する。Next.js 15以降のPPR（Partial Prerendering）と組み合わせることで、静的・動的コンテンツを同一ルートで最適に配信できる。

- **Turbopack の本番採用:** Next.js 16でTurbopackが安定化し、Webpackと比較してコールドビルドが最大10倍高速化。CI/CDパイプラインの実行時間短縮に直結するため、`next.config.js`で`turbo: true`への移行を優先する。

- **`<Image>`と`<Font>`の最適化深化:** `priority`属性とサイズヒントの精緻な設定でLCPを改善。Google Fonts等の外部フォントをNext.js Font Moduleでホスト自己管理し、ネットワークラウンドトリップを排除する。

- **Server Actions のキャッシュ戦略:** `unstable_cache`と`revalidateTag`を組み合わせた細粒度キャッシュ制御が主流に。データフェッチをコンポーネント層に分散させつつ、タグベースの無効化でStale問題を防ぐ設計が実践的。

- **Bundle Analyzer + `use server`境界の監視:** `@next/bundle-analyzer`をCI必須ツールとして組み込み、クライアントバンドルへの意図しない依存混入を早期検出する。特に大規模ライブラリ（date-fns、lodash等）のサーバー側封じ込めが重要。

### 2. React Server Components streaming 2026

- **ポイント1:** RSC + Suspenseによる段階的ストリーミングが標準化し、`loading.tsx`とSuspense境界の組み合わせでTTFBを最小化しつつ、重要コンテンツを先行表示するパターンが定着している。

- **ポイント2:** `use cache`ディレクティブ（Next.js 15+）でコンポーネント・関数・ルートレベルのキャッシュを宣言的に制御できるようになり、従来の`fetch()`オプションによるキャッシュ設定より粒度が細かく管理しやすい。

- **ポイント3:** PPR（Partial Prerendering）が本番投入フェーズに入り、静的シェルを即座に配信しつつ動的部分のみをストリームする手法により、静的サイトのパフォーマンスと動的コンテンツの両立が実用レベルに達している。

- **ポイント4:** Server Actionsとストリーミングの組み合わせによるOptimistic UIパターンが普及し、`useOptimistic`+`startTransition`でサーバー応答待ちのUX劣化をほぼ排除できる設計が一般化している。

- **ポイント5:** Turbopackがデフォルトビルダーとして安定化し、大規模RSCプロジェクトでのコールドスタートが従来Webpackと比較して3〜5倍高速化されており、開発体験（DX）の向上が実測できる段階になっている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの成熟と普及:** Next.js/TypeScriptスタック全体での採用が加速し、フルスタック型安全性がデフォルト選択になりつつある。特にモノレポ構成では、API定義の重複排除とリアルタイム型チェックが開発速度を大幅に向上させる。

- **GraphQLの選択的採用:** 複数クライアント（Web/Mobile/サードパーティ）が同一データを異なる形状で消費するケースに限定されるようになった。オーバーエンジニアリングリスクを認識し「本当に必要か」を問う文化が定着している。

- **REST + OpenAPI 3.1の再評価:** Hono・Fastify等の高速フレームワークとZodによるスキーマ自動生成により、RESTでも型安全なSDK生成が実現。シンプルさとインターオペラビリティが求められるパブリックAPIでは依然最強の選択。

- **エッジコンピューティングへの対応:** Cloudflare Workers・Vercel Edge等での動作を前提としたAPI設計が重要に。コールドスタートレスのtRPCやLightweight RESTが優位で、重量級GraphQLサーバーはエッジ非対応になりがち。

- **AI統合とMCPプロトコルの台頭:** LLMエージェントがAPIを直接呼び出すユースケースが増加し、OpenAPI仕様の機械可読性・MCP（Model Context Protocol）対応が新たな設計基準になりつつある。2026年以降はAIエージェント向けAPIファーストデザインが競合優位に直結する。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジの標準ランタイムへ:** Cloudflare Workers・Fastly Compute@Edgeを中心に、WasmがJavaScript以外の言語（Rust・Go）をエッジで動かす主流手段となった。コールドスタートがほぼゼロになり、レイテンシの予測可能性が大幅に向上している。

- **エッジDBとデータの局所化:** Cloudflare D1・Turso（libSQL）などのエッジ対応SQLiteが普及し、「コンピュートだけでなくデータもエッジへ」というパターンが現実的になった。グローバルレプリケーション戦略の設計が新たな必須スキルになっている。

- **AI推論のエッジオフロード:** 小型LLM（Llama 3.x系、phi-3系）のエッジ実行が実用域に入り、プライバシー要件の高いユースケース（医療・金融）での採用が加速。ただしモデルサイズとエッジリソース制約のトレードオフ設計が依然課題。

- **オブザーバビリティの分散化問題:** エッジノードが数百拠点に分散するため、従来の集中型ログ・トレーシングが機能しにくい。OpenTelemetryのエッジ対応とサンプリング戦略の見直しが運用上のボトルネックになっている。

- **ベンダーロックインリスクの再評価:** Vercel Edge Functions・Cloudflare Workers間の移植性は依然低く、WinterCG（Web-interoperable Runtimes Community Group）標準への準拠度がアーキテクチャ選定の重要指標になった。マルチエッジ戦略を取る場合は抽象化レイヤーのコストを事前に見積もること。

### 5. authentication security best practices 2026

- **パスキー（Passkey）の本格採用:** FIDO2/WebAuthn標準に基づくパスキーがパスワードの実質的な後継として主流化。フィッシング耐性があり、生体認証と組み合わせることでUXとセキュリティを両立できる。

- **ゼロトラスト認証の徹底:** 「ネットワーク内部だから安全」という前提を廃止し、すべてのリクエストを継続的に検証するアーキテクチャが必須。セッション中も定期的な再認証とリスクベースの適応認証を組み合わせる。

- **短命トークン＋トークンローテーション:** JWTのアクセストークンは15分以下に設定し、リフレッシュトークンは使用ごとにローテーション。トークン漏洩時の被害を最小化するため、リフレッシュトークンの再利用検出（Refresh Token Rotation）を必ず実装する。

- **AIを活用した異常検知:** ログインパターン・デバイスフィンガープリント・行動バイオメトリクスをリアルタイム分析し、不正アクセスを早期検出。ルールベースのブロックではなくリスクスコアに基づく段階的な認証強化が標準的なアプローチになっている。

- **サプライチェーン攻撃への対策:** 認証ライブラリ（NextAuth.js、Auth.jsなど）の依存パッケージを定期監査し、SBOMを管理する。外部IdP（Google、GitHub等）との連携においてもOIDCスコープを最小権限に絞り、トークンのオーディエンス検証を厳格に行う。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x + Supabase の統合成熟:** Prisma ORM と Supabase の組み合わせが事実上のスタンダードになりつつあり、`prisma generate --sql` によるマイグレーション管理とSupabaseのRow Level Security(RLS)を組み合わせることで、型安全かつセキュアなデータ層が構築しやすくなっている。

- **Supabase Realtime + Edge Functions の台頭:** 2026年時点でSupabase RealtimeはPostgresのWALを直接購読できるため、WebSocketポーリング不要のリアルタイム同期が低コストで実現可能。Edge Functionsとの組み合わせでサーバーレスアーキテクチャがより実用的になった。

- **Prisma Accelerate によるコネクションプーリング問題の解消:** サーバーレス/エッジ環境でのDB接続枯渇問題はPrisma Accelerateのグローバルコネクションプールで緩和される。Supabase側のpgbouncerと二重にプーリングするとオーバーヘッドになるため、どちらか一方に統一する設計判断が重要。

- **RLS とアプリケーション層の責務分離:** SupabaseのRLSをセキュリティの主要ゲートとして活用し、Prismaをデータアクセス層に限定する設計が堅牢。ただしPrismaはRLSを自動適用しないため、`SET LOCAL role`でPostgresロールを切り替えるミドルウェアの実装が必須。

- **pgvector + Supabase による RAG アーキテクチャ:** Supabaseがpgvectorを標準サポートしており、ベクトル検索とリレーショナルデータを同一DBで扱えるようになった。外部ベクトルDBを別途立てるより運用コストが低く、2026年のAI統合アーキテクチャではまず検討すべき選択肢。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の本格普及:** 2026年にWASI Preview 2が安定化し、RustのWASMコンポーネントが言語をまたいで型安全に合成可能となった。マイクロサービスのポータビリティが飛躍的に向上している。

- **Wasmtime/WASMEdgeのAOTコンパイル最適化:** JITではなくAhead-of-Timeコンパイルの精度が大幅に改善され、ネイティブ実行の85〜95%の速度を達成するケースが増加。サーバーサイドWASMがコンテナの代替として現実的な選択肢になっている。

- **SIMD・スレッド拡張の標準化完了:** WASM SIMDとShared Memoryが全主要ランタイムで安定サポートされ、Rustの`std::arch`と連携した画像処理・ML推論ワークロードで顕著な性能向上（2〜4倍）が得られる。

- **バイナリサイズの課題が緩和:** `wasm-opt`（Binaryen）とRustの`min-size-rel`プロファイルの組み合わせにより、エッジ配信に必要な小バイナリを実現しやすくなった。ただしstd全体を含む場合は依然として500KB+になりやすい点に注意。

- **Rustが事実上のWASMファーストクラス言語に:** ツールチェーン（`cargo-component`、`wasm-bindgen`の後継）の成熟により、WebとサーバーサイドWASMを同一コードベースで扱えるようになり、チームの学習コストが大幅に低下している。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** App Router では Server Components をデフォルトとし、`'use client'` の境界を最小化する。クライアントバンドルを削減し、初期ページロードを大幅に改善できる。

- **Partial Prerendering (PPR) の本格採用:** 静的シェルと動的ストリーミングを同一ルートで共存させる PPR が安定版となり、ISR の後継として使われるケースが増加。`<Suspense>` 境界の設計がパフォーマンスに直結する。

- **Server Actions によるデータ変更の一元化:** フォーム送信・データ更新を Server Actions に集約し、API Route を経由しないパターンが主流に。楽観的 UI 更新（`useOptimistic`）との組み合わせで UX を担保する。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** 関数・コンポーネント単位で `use cache` を宣言し、`cacheTag` / `cacheLife` で無効化戦略を明示するパターンが浸透。暗黙的なキャッシュ挙動への依存を排除できる。

- **Parallel Routes と Intercepting Routes の活用:** モーダル・スライドオーバー・タブ UI を URL 対応で実装する際に必須。直接 URL アクセスとナビゲーション経由で異なる表示を提供でき、SEO と UX を両立させる。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge Middlewareによるレイテンシ削減の標準化:** 2026年現在、認証・A/Bテスト・パーソナライゼーションをEdge Middlewareに移動させるパターンが定着。コールドスタートが実質ゼロになったことで、従来Lambdaで処理していたロジックの積極的なEdge移行が推奨される。

- **ポイント2: Fluid ComputeモデルによるCPU課金の最適化:** VercelのFluid Computeにより、リクエスト処理中のCPU待機時間（外部API呼び出し等）が課金対象外に。`fetch()`を多用するEdge Functionはコスト削減効果が大きく、適切な`waitUntil()`活用でバックグラウンド処理も効率化できる。

- **ポイント3: KV・Redis連携パターンの成熟:** `@vercel/kv`とEdge Runtimeの組み合わせによるキャッシュ戦略が成熟。`stale-while-revalidate`パターンをEdge側で実装することで、オリジンサーバーへのリクエスト数を大幅削減できる。

- **ポイント4: Edge-first Streaming（Suspense境界の活用）:** Next.js App RouterのServer ComponentsとEdge Streamingを組み合わせることで、TTFB（Time to First Byte）を従来比60〜70%削減する事例が増加。Suspense境界の粒度設計がパフォーマンスの鍵。

- **ポイント5: リージョン戦略の見直し（データ主権との両立）:** GDPRや国内法規制対応でEdge Functionのリージョンを明示的に制御する必要性が増加。`export const config = { regions: ['hnd1'] }`による日本リージョン固定と、グローバルCDNキャッシュを組み合わせるハイブリッド設計がベストプラクティス。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなブランド型が標準化しつつあり、プリミティブ型の意味的な混同によるバグを型レベルで防止できる。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` が定着し、型推論を保持しながら型チェックを行えるため、`as` キャストによる型安全性の破壊を避けられる。

- **Template Literal Types によるAPI型生成:** `${HTTPMethod} /${string}` のようなパターンでルート型を自動生成し、ランタイムエラーをコンパイル時に検出する手法が実用段階に達している。

- **`using` キーワード（Explicit Resource Management）:** TypeScript 5.2で導入された `using` によりリソース解放を型安全に強制でき、メモリリークや接続の閉じ忘れをコンパイラが保証する。

- **Zod + tRPC によるEnd-to-End型安全:** APIの入出力をZodスキーマで定義しtRPCで共有することで、フロントエンド〜バックエンド間の型ドリフトをゼロにするアーキテクチャがデファクトに近い状態になっている。
