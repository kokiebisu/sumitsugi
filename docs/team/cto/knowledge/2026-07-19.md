## Daily Update (2026-07-19)

### 1. Next.js performance optimization 2026

## Next.js Performance Optimization 2026 — CTOの視点

- **ポイント1（Partial Prerendering の本格運用）:** 静的シェルを即座に配信しつつ動的部分だけストリーミングするPPRが標準化しつつあり、TTFBとLCPを大幅に改善できます。sumitsugiの物件一覧・詳細ページのような「静的な骨格＋動的な在庫データ」の構成に特に有効です。

- **ポイント2（Turbopackによるビルド高速化）:** Next.js 16でTurbopackがデフォルトのビルド・開発ツールとなり、大規模コードベースでもHMRとプロダクションビルドが数倍高速化されています。CI時間の短縮に直結するため、`bun run build` のCIコストが今後さらに下がる見込みです。

- **ポイント3（`use cache` ディレクティブによる明示的キャッシュ制御）:** データ取得単位・コンポーネント単位でキャッシュ挙動を明示的に宣言できるようになり、これまでの暗黙的な自動キャッシュより予測可能でデバッグしやすくなっています。物件データのようにstaleさが許容できる情報とリアルタイム性が必要な予約状況を分離して設計すべきです。

- **ポイント4（React Server Componentsでのバンドルサイズ削減）:** クライアントJSを最小限に抑える設計が引き続き重要で、フォームや認証まわり以外はできる限りServer Componentsに寄せることで、モバイル回線でのFirst Load JSを削減できます。

- **ポイント5（画像・フォント最適化のCDN連携強化）:** `next/image` とEdge/CDN連携が進化し、地域最適化配信がより簡単になっています。物件写真が多いsumitsugiのようなプロダクトでは、CLS対策とLCP改善の効果が大きく、優先的に投資すべき領域です。

### 2. React Server Components streaming 2026

- **Partial Prerendering の標準化:** Next.js 16では静的シェルを即座に返しつつ、動的部分だけをストリーミングで後追い配信するPPRパターンが一般化し、TTFBとインタラクティブ性を両立できる。

- **Suspense境界の粒度設計が重要に:** ページ全体を1つのSuspenseで囲むのではなく、データ取得単位ごとに細かく境界を分けることで、遅いAPIが速いコンポーネントの表示をブロックしなくなる。うちのproperties一覧やlisting詳細ページでも、物件カードごとに境界を切ると体感速度が改善する。

- **Server Actionsとの組み合わせでネットワーク往復が削減:** フォーム送信やミューテーションをRSC内で完結させることで、クライアント側のfetch/API層が不要になり、コード量と攻撃面（XSS/CSRF対策箇所）が減る。認証・お問い合わせフォームなど`.claude/rules/standards.md`のセキュリティ要件とも相性が良い。

- **キャッシュ戦略の複雑化に注意:** RSCのストリーミングは強力だが、`revalidatePath`/`revalidateTag`の設計を誤るとdraft/public状態の物件が古いキャッシュのまま表示されるリスクがある。ステータス変更系のミューテーションでは明示的なキャッシュ無効化を徹底すべき。

- **エッジランタイムとの組み合わせでグローバルレイテンシ改善:** ストリーミングSSRをエッジ実行環境に載せることで、地理的に離れたユーザーへの初期表示速度が向上する。ベータローンチ後にユーザー分布が広がった際のスケーラビリティ対策として検討価値あり。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCの採用がフルスタックTypeScriptチームで加速しており、型生成不要でエンドツーエンドの型安全性を実現できる点がsumitsugiのようなNext.js App Router構成と特に相性が良い。REST/OpenAPIのようなスキーマ管理コストを削減できるため、小規模チームでの開発速度向上に直結する。

- **ポイント2:** GraphQLは大規模・複数クライアント（Web/モバイル/パートナーAPI）を持つ組織での採用が依然として優勢だが、単一フロントエンドのプロダクトではオーバーエンジニアリングになりがちで、N+1問題やキャッシュ戦略の複雑さが運用コストを押し上げる。sumitsugiのような単一Webアプリ中心の構成ではtRPCまたはREST+Zodの方が適合度が高い。

- **ポイント3:** RESTは外部公開API・パートナー連携・将来的なモバイルアプリ対応を見据える場合に依然として標準であり、OpenAPI仕様書による自動ドキュメント生成やサードパーティ連携のしやすさが強み。「引越し費用」決済連携など外部サービスとの接点が増えるフェーズではREST境界を明示的に設けておくべき。

- **ポイント4:** 2026年時点のトレンドとして、単一プロトコルへの統一ではなく「内部通信はtRPC、外部公開APIはREST」というハイブリッド構成が主流化しており、Zodスキーマを共有基盤として両者の型定義を一元化するパターンが増えている。既存の`.claude/rules/standards.md`にあるZod境界検証の方針とも整合する。

- **ポイント5:** Server Actions（Next.js 16）の普及により、単純なフォーム送信やCRUDについてはAPIレイヤー自体を省略する動きも強まっているが、認証・決済・外部連携など監査性が求められる処理は引き続き明示的なAPI層（tRPC/REST）を通すべきで、セキュリティレビューの観点からもこの分離を維持することが重要。

### 4. serverless edge computing 2026

- **エッジでのAI推論標準化:** 2026年時点でCloudflare Workers AI、Vercel Edge Functions、Fastly Compute@Edgeなどが軽量LLM推論をエッジで直接実行できるようになり、レイテンシがユーザー体感に直結するsumitsugiのような物件検索・チャット機能では、東京リージョンに縛られずグローバルエッジでレスポンスを返す設計が競争力の差別化要因になる。

- **コールドスタート問題の実質的解消:** V8 isolateベースのランタイム（Cloudflare Workers、Deno Deploy）はミリ秒単位の起動時間を実現しており、Next.js 16のApp RouterとPPR（Partial Prerendering）を組み合わせることで、静的シェルを即座に返しつつ動的部分（在庫状況、価格）だけエッジでストリーミングする構成が主流化している。

- **データレイヤーのエッジ移行:** D1、Turso、PlanetScaleなどエッジ対応DBが実用段階に入り、読み取り頻度の高い物件一覧・検索系はリードレプリカをエッジに配置しつつ、書き込み（契約・決済関連）は引き続き中央集権的なDBに委ねる「Hybrid Data Placement」が定石になっている。ただしsumitsugiの規模ではまだROIが薄く、時期尚早な可能性がある。

- **ベンダーロックインとコスト管理の再考:** エッジランタイムはNode.js APIの一部が未対応（fs、一部のcryptoなど）で、移行コストと引き換えのメリットを慎重に見極める必要がある。特にMVPローンチ直後のsumitsugiでは、まずVercelの標準エッジ機能で十分であり、フルマイグレーションは尚早——法務確認・プライバシーポリシー整備が優先事項である現フェーズでは、インフラの大規模刷新よりローンチ完了を優先すべき。

- **Observabilityの複雑化への備え:** エッジで処理が分散するとトレーシングが難しくなるため、OpenTelemetry対応のエッジランタイムを選定時の必須要件にしておくと、将来的なスケール時のデバッグコストを大幅に削減できる。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証がデフォルトとなり、パスキーによるフィッシング耐性のある認証がエンタープライズ・コンシューマー双方で標準実装に。フォールバックとしてのSMS OTPは非推奨とし、WebAuthn実装を優先すべき。

- **継続的リスクベース認証:** ログイン時点の一回限りの検証から、セッション中の行動・デバイス・位置情報を継続監視するリスクベース認証へ移行。異常検知時に段階的にMFAを再要求する仕組みが業界標準になりつつある。

- **トークン窃取対策の強化:** DPoP（Demonstrating Proof of Possession）やトークンバインディングにより、盗まれたセッショントークン単体では悪用できない設計が重要視されている。従来のBearerトークンのみの実装はリスクが高い。

- **AIエージェント認証の新課題:** LLMエージェントやMCP経由の自動化ツールが増える中、人間とエージェントを区別する認証・認可モデル（スコープ限定トークン、監査ログの粒度向上）の整備が急務。sumitsugiのような自動化ワークフローを持つプロジェクトでは特に重要。

- **ゼロトラスト最小権限の徹底:** 「前の住人」「次の住人」双方のPIIを扱う本サービスでは、ロールベースアクセス制御（RBAC）を最小権限原則で設計し、認証成功後も操作単位での認可チェックをサーバーサイドで必須化すべき。

### 6. database architecture Prisma Supabase 2026

- **Prismaのマルチファイルスキーマ標準化:** Prisma 6以降、schema.prismaをドメイン単位で分割管理できるようになり、Supabaseのマイグレーションと組み合わせた際のコンフリクトが大幅に減少している。物件・ユーザー・取引ドメインごとにスキーマファイルを分けることで、`draft`/`public`のようなステータス管理の変更影響範囲を局所化できる。

- **Supabase RLSとPrismaの共存パターン確立:** PrismaのORM層だけに認可ロジックを寄せず、Supabase側のRow Level Securityを「最後の砦」として併用する二層防御が2026年のデファクトになっている。前の住人/次の住人間のデータ分離のような機微な権限制御は、アプリ層のバグに関わらずDB層で担保すべき。

- **Prisma Accelerate/pgbouncerによるコネクション管理:** サーバーレス関数からのコネクション枯渇問題に対し、Prisma AccelerateまたはSupabaseのSupavisor（pgbouncer後継）経由の接続プーリングがVercel/Next.js構成では必須化している。GitHub Actionsの自律開発ワークフローが並行DBアクセスを行う場合、この設定漏れがボトルネックになりやすい。

- **型安全なマイグレーションCI連携:** `prisma migrate diff`をCIに組み込み、Supabase本番環境への適用前にスキーマドリフトを検知する運用が一般化。ビルド整合性を重視する当プロジェクトの方針（`bun run build`必須ルール）と同様、マイグレーションも「CIで検証済みでない変更はマージしない」原則を適用すべき。

- **pgvector統合による検索機能拡張:** Supabaseのpgvector拡張とPrismaの`Unsupported`型を組み合わせ、物件検索やマッチング（ICコンサルテーション等）にベクトル類似検索を組み込む事例が増加。将来的な「引越し費用」見積もりのレコメンド機能などに応用余地がある。

### 7. WebAssembly Rust performance 2026

## CTO視点: WebAssembly × Rust パフォーマンス動向 2026

- **ポイント1: Component Model の実用化とツールチェーン成熟:** WASM Component Modelが主要ランタイム（wasmtime, wasmer）で安定運用フェーズに入り、Rustの`wit-bindgen`と組み合わせることで言語間インターフェースの型安全な合成が容易になった。マイクロサービスをWASMコンポーネント単位で分割するアーキテクチャが、コールドスタートの速さとメモリ分離のメリットから採用が進んでいる。

- **ポイント2: SIMD128とスレッド機能の標準化による数値計算高速化:** WASM SIMDとShared Memory + Threadsがブラウザ・サーバー双方で広くサポートされ、Rustの`std::simd`やrayonと組み合わせた並列処理がネイティブに近い性能を出せるようになった。画像処理・暗号処理・データ変換などCPUバウンドな処理をフロントで完結させるケースが増えている。

- **ポイント3: WASI Preview 2 移行によるサーバーサイド活用の拡大:** WASI 0.2ベースのランタイムがKubernetes系プラットフォーム（SpinKube等）で本番採用され、Rust製WASMバイナリをコンテナより軽量なサンドボックスとしてデプロイする事例が増加。起動時間がミリ秒単位で、Function-as-a-Serviceの新たな選択肢になっている。

- **ポイント4: バンドルサイズ最適化の実務的知見が蓄積:** `wasm-opt`、`twiggy`によるサイズ解析、`wee_alloc`に代わる新世代アロケータの採用など、Rust→WASMのビルドパイプラインでの最適化ノウハウが定着。不要なパニックハンドラやフォーマット処理を削ることで数百KB単位の削減が定石化している。

- **ポイント5（sumitsugiへの示唆）: 現状は導入優先度低:** 当プロジェクトはNext.js/TypeScriptベースのCRUD中心アプリで、CPUバウンドな重い計算処理（画像加工・PDF生成等）が将来的にボトルネックになった場合の選択肢として留めておくのが妥当。MVPローンチ前の今は投資対象ではない。

### 8. Next.js App Router patterns 2026

- **ポイント1（Server Components前提の設計）:** App RouterではServer Componentsがデフォルトとなり、データフェッチをコンポーネント内で直接行う設計が主流に。クライアントバンドルを最小化するため、`'use client'`境界を末端の対話的UI（ボタン、フォーム）だけに絞る規律が重要。

- **ポイント2（Partial Prerendering / PPR の実用化）:** 静的シェルを即座に返しつつ動的部分をストリーミングする手法が安定運用フェーズに入り、一覧ページや物件詳細ページのようにSEOと即応性を両立させたいページで採用が進んでいる。sumitsugiのようなpublic/draft混在の物件一覧では、静的な骨格＋動的な在庫データという分離が体感速度に直結する。

- **ポイント3（並列データ取得とWaterfall回避）:** `Promise.all`やServer Actions内での並列fetch、あるいはSuspenseによる境界分割で、シーケンシャルなデータ待ちを避けるパターンが定石化。物件詳細×前の住人プロフィール×レビューのような複数データソースを持つページほど効果が大きい。

- **ポイント4（Server Actionsのバリデーション徹底）:** フォーム送信をServer Actionsで完結させる設計が増えているが、クライアント側検証を信用せずZodなどでサーバー側にも必ずバリデーションを置くパターンが標準化。引越し費用の決済フローなど金銭が絡む処理では特に重要。

- **ポイント5（キャッシュ戦略の明示化）:** Next.js側のデフォルトキャッシュ挙動が変遷してきた反省から、`fetch`のキャッシュオプションや`revalidate`を暗黙のデフォルトに頼らず明示的に指定する運用が定着。物件ステータス（draft/public）のような即時性が求められるデータは特に、意図しないキャッシュヒットを避ける設計が必須。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約とWasm活用:** Vercel Edge FunctionsはV8 isolateベースで軽量・高速起動が強みだが、Node.js API非対応の制約があるため、重い処理はWasmモジュール化して実行時間を短縮するパターンが2026年の主流になっている。

- **Streaming SSRとの組み合わせ:** Next.js 16のPartial PrerenderingとEdge Functionsを組み合わせ、静的シェルを即座に返しつつ動的部分をストリーミングすることで、TTFBを大幅に改善できる — sumitsugiの物件一覧・詳細ページのような動的コンテンツに有効。

- **リージョン最適化とコールドスタート対策:** リクエスト発生元に最も近いエッジで実行される特性を活かし、`export const preferredRegion`で日本ユーザー向けにhnd1(東京)を明示指定することでレイテンシを削減できる。

- **キャッシュ戦略の細分化:** `stale-while-revalidate`とEdge Config/KVを組み合わせ、頻繁に読むが更新頻度の低いデータ（物件ステータスやサイト設定など）をエッジ側でキャッシュし、DBラウンドトリップを削減するのがベストプラクティスとして定着。

- **可観測性の重要性:** Edge Functionsはデバッグがサーバーレスより難しいため、構造化ログとOpenTelemetry連携によるトレーシングを最初から組み込む設計が推奨される — 本番障害の切り分けコストを大きく下げる。

### 10. TypeScript type safety patterns 2026

## TypeScript Type Safety Patterns 2026

- **ポイント1: `satisfies`演算子によるスキーマ検証の定着** — 型推論を保ったまま制約チェックできる`satisfies`が、設定オブジェクトやルーティング定義などで標準パターン化。`as const`との組み合わせでリテラル型を維持しつつ型安全性を担保できる。

- **ポイント2: Zodを起点にした「スキーマファースト」開発** — `z.infer<>`でランタイム検証とコンパイル時型を単一のスキーマから生成するアプローチが主流に。当プロジェクトでもZodをシステム境界（フォーム入力・API）で使う方針は、この流れに合致している。

- **ポイント3: Branded Types（公称型）による意味的な区別** — `UserId`と`ListingId`のようにどちらも`string`だが混同してはいけない値を、intersection typeでタグ付けして区別する手法が普及。DBのID型混在バグを防ぐのに有効で、`src/lib/data.ts`のような型定義層への導入価値が高い。

- **ポイント4: 網羅性チェック（Exhaustiveness Checking）の徹底** — union型のswitch文で`never`型を使ったdefaultケースの検証が、CIのlintルールとしてもテンプレ化。`'draft' | 'public'`のようなステータス型を扱う際、新しい値を追加した時の漏れを型レベルで検知できる。

- **ポイント5: TypeScript 6系のパフォーマンス最適化とGo移植版の普及** — 大規模モノレポでの型チェック速度がボトルネックになりやすく、incrementalビルドやproject referencesの活用が事実上必須に。ビルド時間はCI待ち時間に直結するため、`bun run build`の高速化にも波及する論点。
