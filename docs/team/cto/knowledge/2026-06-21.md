# CTO Knowledge - 2026-06-21

## Daily Update (2026-06-21)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Pre-Rendering の本格活用）:** Next.js 15以降で導入されたPPRが2026年には標準パターン化し、静的シェルと動的コンテンツを1ページ内で混在させることでTTFBとインタラクティブ性を両立できる。sumitsugiの物件一覧・詳細ページのようにSEO重視の静的部分とユーザー固有の動的部分（お気に入り状態等）が混在するUIには特に有効。

- **ポイント2（Server Componentsでのデータフェッチ最適化）:** `fetch`のリクエストメモ化とキャッシュ戦略（`cache: 'force-cache'` / `revalidate`）を明示的に設計することが必須になっており、N+1的なフェッチをServer Components内で並列化（`Promise.all`）するパターンが定石化している。

- **ポイント3（バンドルサイズより実行時パフォーマンス計測）:** Lighthouseスコアだけでなく、実ユーザー環境のINP（Interaction to Next Paint）がCore Web Vitalsの主要指標として重視され、クライアントコンポーネントの境界を最小化する設計判断が重要になっている。

- **ポイント4（Turbopackのプロダクションビルド成熟）:** 開発時だけでなく本番ビルドでもTurbopackが安定運用フェーズに入り、大規模リポジトリでのビルド時間短縮がCI/CDパイプラインの高速化に直結する。sumitsugiのような頻繁なPRサイクルを持つプロジェクトではCI時間短縮の恩恵が大きい。

- **ポイント5（画像・フォント最適化の自動化深化）:** `next/image`のAVIF優先配信やレイアウトシフト防止がデフォルト挙動として強化され、物件写真のような画像中心UIではLCP改善に直接寄与する。手動チューニングより設定の見直し（`sizes`属性やpriority指定の精査）が投資対効果が高い。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16のPPR(Partial Prerendering)が安定版となり、静的シェルを即時返しつつ動的部分のみSuspense境界でストリーミングする構成が標準化した。初期表示(TTFB)とインタラクティブ性を両立できるため、物件一覧ページのような「即時表示+動的フィルタ」構成に最適。

- **ポイント2:** Server Componentsでのデータフェッチが`use cache`ディレクティブと組み合わさり、キャッシュ粒度をコンポーネント単位で制御できるようになった。物件詳細ページの「前の住人」情報など更新頻度の低いデータはキャッシュ、空室状況など頻繁に変わるデータはストリーミングで分離する設計が効果的。

- **ポイント3:** エラーバウンダリとSuspenseの組み合わせによるストリーミングエラーハンドリングが洗練され、一部のチャンクが失敗しても他のチャンクは表示継続できる。決済フローや問い合わせフォームなど、外部APIに依存する部分を独立したストリーミング単位に切り出すことでUX劣化を局所化できる。

- **ポイント4:** RSCペイロードのシリアライズコストがハイドレーション全体のボトルネックになりやすく、Client Componentsへ渡すpropsを最小限に絞る設計レビューが重要。`src/components`配下で「Server→Client境界」を意識したコンポーネント分割を継続的にチェックすべき。

- **ポイント5:** ストリーミングSSRとEdge Runtimeの組み合わせで、ユーザーの地理的位置に近いエッジでレンダリング開始できるようになり、TTFBがさらに短縮されている。ベータローンチ後のスケール局面で、Vercel Edge/CDN戦略の見直しが投資対効果の高い改善ポイントになる。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCのようなEnd-to-End型安全なRPC方式が、Next.js + TypeScriptモノレポ構成（本プロジェクトのスタックに近い）で主流化しており、フロントエンド/バックエンド間のスキーマ手動同期コストを削減できる。新規の内部APIではtRPC、外部公開APIではREST/OpenAPIを併用する「ハイブリッド戦略」が2026年のデファクトになっている。

- **ポイント2:** GraphQLは大規模・多クライアント（モバイル/Web/パートナー連携）でのデータ取得最適化に強みを持つが、N+1問題やキャッシュ複雑性のコストが高く、中小規模プロダクトではオーバーエンジニアリングになりやすい。sumitsugiのような単一Webアプリ中心のMVPでは、現状のREST/Server Actions構成を維持し、外部API連携が増えた段階でGraphQL Gatewayを検討するのが妥当。

- **ポイント3:** Next.js App RouterのServer Actionsが「RPC的な薄いAPI層」として定着しつつあり、tRPCを導入せずともServer Actions + Zodバリデーションだけで型安全なAPI境界を構築できるケースが増えている。既存の`src/lib`構成を踏まえると、まずServer Actions化を優先し、tRPC導入は外部クライアント（モバイルアプリ等）が必要になったタイミングで判断するのが現実的。

- **ポイント4:** 2026年はAPIの「LLMエージェント消費」を前提とした設計（MCPサーバー化、構造化レスポンス、冪等性保証）が新たな要件として浮上しており、将来的に物件データや引き継ぎフローをAIエージェント経由で操作させる場合、REST/tRPCどちらでも「決定的でリトライ安全」なエンドポイント設計が重要になる。

- **ポイント5:** スキーマファースト開発（Zod/OpenAPI生成）によるドキュメント自動生成とテスト連携が標準化しており、本プロジェクトの「Zodスキーマによる入力検証」方針はAPI設計のベストプラクティスと既に整合している。今後はこのZodスキーマをOpenAPI/tRPCルーター定義の単一ソースとして再利用する設計にすると保守コストを下げられる。

### 4. serverless edge computing 2026

- **WASMエッジランタイムの主流化:** Cloudflare WorkersやFastly Compute@EdgeでWasmベースの実行環境が標準となり、コールドスタートがミリ秒未満まで短縮された。当社のSSRやAPI Routesを段階的にエッジ実行へ移行することで、TTFBを大幅に改善できる可能性がある。

- **エッジでのデータレイヤー進化:** Cloudflare D1やTurso、PlanetScaleなどエッジネイティブなSQLiteベースDBが実用段階に入り、グローバル分散の読み取り遅延が解消されつつある。物件検索のような読み取り中心の機能はエッジDBレプリカへの移行候補になる。

- **AI推論のエッジシフト:** 軽量LLM・量子化モデルがエッジ上で直接推論可能になり、レコメンドや検索のパーソナライズをリージョン跨ぎのレイテンシなしで実現できる。前の住人マッチング機能の高速化に応用余地あり。

- **Next.js × エッジランタイムの成熟:** Next.js 16のEdge Runtimeサポートが安定し、Middleware・一部Server Componentsをエッジで実行するパターンが実運用レベルに達した。ただしNode.js API依存の処理は引き続きNode runtimeが必要なため、機能ごとの棚分けが重要。

- **コスト構造の変化:** エッジ実行は従量課金が細粒度化し、低トラフィック期のコストは大幅に下がる一方、ピーク時のコスト予測がしづらくなる傾向がある。ベータローンチ後のトラフィック特性を見極めてからエッジ移行の優先度を判断すべき。

### 5. authentication security best practices 2026

- **パスキー/WebAuthnへの完全移行:** パスワードベース認証はフィッシング耐性が低く、2026年時点ではFIDO2/WebAuthnによるパスキーがデフォルトの認証手段となっている。実装コストよりもセキュリティインシデント対応コストの方が高いため、新規プロダクトはパスワードレスを前提に設計すべき。

- **フィッシング耐性のあるMFAの必須化:** SMS OTPやTOTPはセッションハイジャックやリアルタイムフィッシング攻撃に弱く、デバイスバインド型の認証（パスキー、ハードウェアキー）への移行が業界標準になっている。特に決済や個人情報を扱うsumitsugiのようなサービスでは、SMS-OTPのみに依存しない設計が重要。

- **継続的・コンテキストベースの認証（Continuous Auth）:** ログイン時の一度きりの認証ではなく、デバイスフィンガープリント・行動パターン・IPレピュテーションなどを組み合わせたリスクベース認証が普及。異常なアクセスパターンを検知してセッションを動的に再認証させる仕組みが求められる。

- **トークン管理のベストプラクティス:** JWTやセッショントークンをlocalStorageに保存する実装は依然としてXSSリスクが高く、httpOnly + Secure + SameSite=Strict cookieでの管理が推奨される。リフレッシュトークンのローテーションと短命アクセストークンの組み合わせが標準パターン。

- **サードパーティ認証プロバイダのサプライチェーンリスク:** Auth0やSupabase Authなどの外部認証基盤を使う場合でも、設定ミス（リダイレクトURI検証不備、CORS設定の甘さ）が依然として主要な侵害原因。導入時はベンダー任せにせず、自社でセキュリティレビューを行う体制が必要。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma ORM のRust非依存化（v6以降）でコールドスタートが大幅短縮され、Supabaseのサーバーレス/Edge Functions環境との相性が向上。Vercel等のサーバーレス環境でのレイテンシ問題が実用上ほぼ解消された。
- **ポイント2:** Supabaseの接続プーリング（PgBouncer/Supavisor）とPrismaを併用する際は、`directUrl`と`pooledUrl`を分離設定するのが必須パターンとして定着。マイグレーションは直接接続、実行時クエリはプール経由が標準。
- **ポイント3:** Row Level Security（RLS）をPrisma側のスキーマ定義だけでは表現できないため、SupabaseのRLSポリシーはSQLマイグレーションで別管理し、Prismaの型生成とRLSの権限ロジックを二重管理する運用が必要。Zodバリデーションと組み合わせて多層防御を構成するのが推奨構成。
- **ポイント4:** pgvector拡張を使ったベクトル検索（AI機能・レコメンド）の需要が増加しており、Prismaのスキーマでベクトル型を扱う際はrawクエリ（`$queryRaw`）併用が現状のベストプラクティス。
- **ポイント5:** Supabaseのデータベースブランチング機能とCI連携することで、PRごとに本番相当のスキーマでE2Eテストを実行できる。sumitsugiのようなPRベース開発フローでは、マイグレーションの破壊的変更を早期検知する仕組みとして有効。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGCとcomponent modelの普及により、RustからWasmへのコンパイル時にGCを介さない線形メモリモデルの優位性がより明確になり、Wasm/Rustの組み合わせは依然レイテンシ重視のエッジ処理に最適。

- **ポイント2:** wasm-optやwit-bindgenの成熟でバインディング生成コストが下がり、ホスト言語（JS/Node/Python）からのFFI呼び出しオーバーヘッドが2023年比で大幅に削減、サーバーレス関数のコールドスタートにも有利。

- **ポイント3:** SIMD128とthreads proposalがブラウザ・ランタイム双方で標準サポートされ、Rust側で`std::simd`や`wasm_simd128`を使った並列処理がプロダクションレベルで使えるようになり、画像処理・暗号化などCPU重い処理をクライアントサイドにオフロード可能。

- **ポイント4:** WASIプレビュー2の安定化でWasmtime/Wasmer上でのファイルI/Oやネットワークアクセスが実用段階に入り、Next.js Edge Runtimeのようなサンドボックス実行環境でRust製モジュールを安全に動かす選択肢が増加。

- **ポイント5:** バイナリサイズ最適化（`wasm-opt -Oz`、LTO、panic=abort）の自動化ツールチェーンが整い、初期ロード時間を犠牲にしないWasmモジュール配信がCDN経由で容易になったため、フロントエンドの重い計算処理を段階的にWasm化する移行コストが下がっている。

### 8. Next.js App Router patterns 2026

- **ポイント1:** Partial Prerendering（PPR）の本格運用が進み、静的シェルを即時表示しつつ動的部分をストリーミングする構成が標準化。LCPとTTFBの両立がしやすくなり、物件一覧ページのような「一覧は静的・在庫情報は動的」な構成に最適。

- **ポイント2:** Server Actionsがフォーム処理の主流となり、APIルートを介さないデータ更新が一般化。内見予約や引き継ぎ申請フォームなど多段階フローでも、`useActionState`と組み合わせた楽観的UI更新がベストプラクティスとして定着。

- **ポイント3:** `cacheLife`/`cacheTag`によるきめ細かいキャッシュ制御がデフォルト化し、Next.js 15以降で導入された明示的キャッシュモデルが定石に。物件ステータス（draft/public）の切り替えなど、再検証タイミングをタグ単位で制御できることが運用上重要。

- **ポイント4:** Route Handlers + Edge Runtimeの組み合わせで、認証チェックや軽量なAPI処理をリージョン近接配信するパターンが普及。ただしNode.js依存のライブラリ（PDF生成等）はNode Runtime維持が必要で、混在管理がアーキテクチャ上の課題。

- **ポイント5:** Server Components内でのデータフェッチが「Composable Fetching」パターンへ収斂し、`Suspense`境界の粒度設計がパフォーマンスチューニングの主戦場に。過剰なネストはウォーターフォール問題を招くため、並列フェッチ（`Promise.all`）とコンポーネント分割の設計判断が引き続き重要。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Vercelは2026年にかけてEdge Runtimeのコールドスタートをさらに圧縮し、V8 isolateの再利用とリージョン間のルーティング最適化により、グローバルでのレイテンシが大幅に低下している。地理的に近いユーザーへの配信が前提のSaaSでは、Edge FunctionsとNode.js Functionsの使い分け基準を明確化すべき。

- **ポイント2:** `Vercel Functions`の統合（Edge/Serverlessの境界が薄くなる方向）が進み、`runtime: 'edge'`指定の意味合いが変わってきているため、移行時はランタイム制約（Node API非対応など）を都度確認する必要がある。

- **ポイント3:** ISR/PPR（Partial Prerendering）とEdge Middlewareの組み合わせが標準パターン化し、認証チェックやA/Bテストなどの軽量処理をEdgeで行い、重い処理はNode.jsランタイムに委譲する責務分離が定石になっている。

- **ポイント4:** Edge Functionsはステートレス・低レイテンシ向けに最適化されているため、DBアクセスが必要な処理はKV/Edge Config等の分散ストアと組み合わせるか、Node.jsランタイムにフォールバックする判断基準をプロジェクト内で明文化しておくべき。

- **ポイント5:** コスト面では実行時間課金モデルの最適化が進んでおり、不要なEdge Middleware実行（全パスマッチなど）を`matcher`設定で絞り込むことが、レイテンシとコストの両方に直結する重要な実装ポイントになっている。

### 10. TypeScript type safety patterns 2026

- **型レベルバリデーションのZod-first化:** Zodなどのスキーマライブラリで実行時検証とコンパイル時型を一元化し、`z.infer`で型を導出することで境界(API入出力、env)の型安全性とバリデーションの重複実装を排除する。

- **Branded Types / Nominal Typingの普及:** `type UserId = string & { __brand: 'UserId' }`のようなブランド型でプリミティブの誤用(例: `userId`と`listingId`の取り違え)をコンパイル時に検出するパターンが標準化してきている。

- **`satisfies`演算子の定着:** 型推論を保持したまま型適合チェックを行う`satisfies`が、設定オブジェクトや定数マップの定義で`as const`と組み合わせて使われ、過剰な型注釈による推論の劣化を防ぐ。

- **Exhaustiveness Checkingの徹底:** Union型(例: `'draft' | 'public'`)に対する`switch`文で`never`型を使った網羅性チェックを必須化し、新しいステータス追加時のハンドリング漏れをビルド時に検出する運用が広がっている。

- **strictモード+`noUncheckedIndexedAccess`の標準採用:** 配列・オブジェクトアクセス時の`undefined`混入をコンパイル時に強制することで、ランタイムエラーを未然に防ぐ設定が新規プロジェクトのデフォルトになりつつある。
