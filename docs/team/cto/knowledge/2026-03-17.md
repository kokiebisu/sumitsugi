# CTO Knowledge - 2026-03-17

## Daily Update (2026-03-17)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを劇的に削減できるため、デフォルトでServer Componentsを選択し、インタラクティブな部分にのみ `'use client'` を付与する設計原則が定着している。

- **Partial Prerendering (PPR) の本格採用:** 静的シェルと動的コンテンツを同一ページで混在させるPPRが安定版になり、ISR/SSR/SSGの使い分けを意識する必要が減少。`<Suspense>` の適切な配置がパフォーマンスの鍵となる。

- **`next/font` + `next/image` の最適化徹底:** フォントのCLS（Cumulative Layout Shift）ゼロ化と画像の自動WebP/AVIF変換は今や必須。`priority` 属性の付与漏れがLCPスコアの主因になりやすい。

- **Turbopack（標準ビルダー）への移行完了:** 2026年時点でTurbopackがデフォルトになり、開発サーバーの起動・HMRが大幅高速化。`next.config` のカスタムwebpack設定との互換性確認が移行時の主な作業。

- **Edge Runtimeの選択的活用:** ミドルウェアやA/Bテストロジックはエッジで処理しレイテンシを最小化。ただし Node.js API非対応の制約があるため、`runtime: 'edge'` の適用範囲を慎重に設計することが依然として重要。

### 2. React Server Components streaming 2026

- **Suspense境界の戦略的配置が鍵:** RSCとStreamingの組み合わせで、TTFBを維持しながら動的コンテンツを段階的に送信できるようになった。Suspense境界をデータフェッチの粒度に合わせて細かく設計することで、ユーザー体感速度が大幅に改善される。

- **PPR（Partial Prerendering）が本格普及:** Next.js 15+でstableになったPPRにより、静的シェルを即時配信しつつ動的部分をストリームする設計が標準化。CDNキャッシュとStreamingの両立が現実的な選択肢になった。

- **Server Actions × Optimistic UIの成熟:** Server Actionsがストリーミングレスポンスに対応し、楽観的更新とサーバー状態の同期が宣言的に書けるようになった。`useOptimistic`との組み合わせでクライアント状態管理の複雑さが減少傾向にある。

- **エラー境界とローディング状態の設計負債に注意:** Streaming導入時にエラー境界（`error.tsx`）とローディング境界（`loading.tsx`）の粒度設計を後回しにするチームが多い。ここを曖昧にすると、部分的な失敗時にUXが壊れるため、アーキテクチャ初期に明示的に設計すべき。

- **React 19のuse()フックでデータフェッチパターンが変化:** `use(promise)`によりクライアントコンポーネントからもPromiseを直接消費できるようになり、Client/Server境界をまたぐデータフローの実装選択肢が増えた。ただし乱用するとウォーターフォールが復活するリスクがあるため、コードレビューでの意識的な管理が必要。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全性の標準化:** 2026年現在、フルスタックTypeScriptプロジェクトではtRPCが事実上の標準となりつつあり、スキーマ定義なしにエンドツーエンドの型安全性を実現できるため、開発速度と品質が大幅に向上している。

- **GraphQLの選択基準の明確化:** GraphQLは複数クライアント（モバイル・Web）が異なるデータ形状を必要とするケースや、BFF（Backend for Frontend）パターンに特化した選択肢となり、単一クライアントの内部APIにはオーバースペックという認識が定着した。

- **REST + OpenAPI 3.1の堅牢性再評価:** 外部公開APIやサードパーティ連携ではRESTとOpenAPI 3.1の組み合わせが依然として最強であり、自動コード生成（oapi-codegen、orval）による型安全クライアント生成が普及している。

- **Server Actions / RPC-over-HTTPの収束:** Next.js Server ActionsやHono RPCなど、HTTPを意識させないRPCスタイルが増加しており、フロントエンドとバックエンドの境界が曖昧になる「コロケーション設計」が主流になりつつある。

- **プロトコル選定の実用基準:** 「外部公開 → REST+OpenAPI」「モノレポ内フルスタック → tRPC」「複雑なデータグラフ・複数クライアント → GraphQL」という選定基準が業界で共有されており、技術選定の迷いが減少している。

### 4. serverless edge computing 2026

- **エッジAI推論の標準化:** WebAssembly（WASM）とONNXランタイムの成熟により、MLモデルをエッジノードで実行するコストが大幅低下。Cloudflare Workers AIやVercel AI SDKが主要インフラとして定着しつつある。

- **Cold Start問題の実質的解消:** V8 Isolateベースのランタイム（Deno Deploy、Cloudflare Workers）が従来Lambdaの10〜100ms問題を1ms未満に圧縮。ただしNode.js互換性の制約は依然存在するため、ライブラリ選定が重要。

- **エッジDBとデータローカリティ:** Turso（libSQL）やCloudflare D1のレプリカ戦略により、エッジでの読み取りレイテンシが劇的改善。書き込み整合性のトレードオフ設計がアーキテクチャの核心課題になっている。

- **観測可能性（Observability）のギャップ:** 分散エッジ環境でのトレーシングはまだ成熟途上。OpenTelemetryのエッジ対応が進んでいるが、従来のAPMツールとの統合に運用コストがかかる点は要注意。

- **コスト最適化の再評価:** リクエスト数課金モデルはトラフィックスパイクに強い一方、常時接続型ユースケース（WebSocket、Server-Sent Events）ではコストが予測困難。Next.jsのようなフルスタックフレームワークはエッジ/サーバー/静的の混在デプロイで最適化の余地が大きい。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の本格採用:** パスワードレス認証がデファクトスタンダードになりつつあり、フィッシング耐性のあるパスキーへの移行が急務。Next.jsアプリでも`@simplewebauthn`などのライブラリで比較的容易に実装可能。

- **セッション管理の強化:** JWTの有効期限を短く（15分以下）設定し、リフレッシュトークンのローテーションを必須化。セッション固定攻撃を防ぐため、認証成功時には必ずセッションIDを再生成する。

- **デバイスバインディングとリスクベース認証:** ログインコンテキスト（IP、デバイス指紋、行動パターン）を分析し、異常検知時のみ追加認証を要求するアダプティブMFAが主流に。ユーザー体験を損なわずにセキュリティを強化できる。

- **OAuth/OIDCのセキュリティ強化:** PKCEの強制適用とDPoP（Demonstrating Proof of Possession）の導入でトークン盗用リスクを低減。`state`パラメータのCSRF対策も依然として見落とされがちな必須項目。

- **依存関係の継続的監査:** 認証ライブラリのサプライチェーン攻撃が増加しており、`bun audit`や GitHub Dependabotによる自動脆弱性スキャンをCI/CDパイプラインに組み込むことが不可欠。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のパフォーマンス改善:** Prisma ORM はクエリエンジンをRustからTypeScriptネイティブに移行しつつあり、コールドスタートが大幅に短縮されEdge Runtimeでの利用が現実的になった。Next.js App RouterのServer Componentsとの相性が向上している。

- **Supabase の Realtime + RLS の成熟:** Row Level Security（RLS）とRealtimeを組み合わせたマルチテナント設計が標準パターンとして確立され、`auth.uid()`をポリシーに組み込むことでアプリ層での権限制御を最小化できる。

- **Prisma + Supabase の接続プール問題への対処:** サーバーレス環境ではPrisma Accelerate（旧Data Proxy）またはSupabaseのPgBouncer（ポート6543）を必ず経由する設計が必須。直接接続（ポート5432）はコネクション枯渇を招く。

- **スキーマ管理の二重管理リスク:** PrismaマイグレーションとSupabaseのダッシュボード直接変更が競合しやすい。2026年時点では `prisma migrate deploy` を唯一の真実の源とし、Supabaseコンソールでの手動DDLを禁止するCIルール設定が推奨される。

- **Vector / pgvector との統合:** Supabase が pgvector を標準サポートし、Prisma側も `Unsupported("vector")` 型での対応が進んでいる。RAG構成でのセマンティック検索をPostgreSQL単体で完結できるため、外部ベクトルDBのコスト・複雑性を削減できる。

### 7. WebAssembly Rust performance 2026

- **WASM Component Model の本格普及:** 2025年末にWASI 0.2が安定版となり、2026年はRustで書かれたWasmコンポーネントの相互運用性が飛躍的に向上。言語をまたいだコンポーネント合成が実用レベルに達し、マイクロサービスの代替としての採用が増加している。

- **WASMThreads + SIMD による演算性能の向上:** Rust+WasmのSIMD命令（`wasm-simd128`）とAtomicsサポートが主要ブラウザ・Wasmランタイム全体で安定し、ネイティブ比80-95%の演算性能が現実的に。画像処理・ML推論・音声処理など計算集約タスクで採用が加速。

- **Wasmtime / WasmEdge のサーバーサイド成熟度:** エッジランタイムとしてWasmtime（Bytecode Alliance）がコンテナ起動時間比で10-100x高速なコールドスタートを実現。RustでWasmを書きCloudflare Workers / Fastly Computeにデプロイするパターンが標準的なエッジ戦略になりつつある。

- **`wasm-bindgen` から `wit-bindgen` へのシフト:** Rustエコシステムでは`wasm-bindgen`（ブラウザ向け）に加え、`wit-bindgen`（WIT仕様準拠）の利用が急増。型安全なインターフェース定義によりホスト↔ゲスト間のABI管理が大幅に簡素化され、ランタイム非依存な設計が可能に。

- **メモリ管理の最適化とGC提案:** WebAssembly GC提案（Phase 4）の普及により、RustのGCなし設計とのハイブリッド運用が現実的に。Rustは引き続きゼロコストWasmバイナリで優位だが、`wasm-opt`（Binaryen）との組み合わせでバイナリサイズをさらに20-30%削減できるケースが増えている。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** デフォルトでServer Componentsを使い、インタラクティビティが必要な箇所のみ`'use client'`を付与する。クライアントバンドルサイズが劇的に削減され、Core Web Vitalsが改善する。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルを先に配信しつつ動的コンテンツをSuspenseでストリームする。`experimental.ppr`が安定化に向かっており、SSG/SSRのトレードオフを解消する切り札となる。

- **Server Actions によるフォーム処理の簡素化:** APIルートを介さず直接サーバー関数を呼び出すパターンが定着。`useActionState`と組み合わせたオプティミスティックUIが標準イディオムになっている。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15以降で`unstable_cache`を置き換える`use cache`が導入。関数・コンポーネント単位でキャッシュ戦略を宣言でき、`cacheTag`/`cacheLife`でタグベース無効化が可能。

- **Turbopack 移行と開発速度:** Turbopackがデフォルト化に近づいており、大規模コードベースでのHMRが10倍以上高速化。ただし一部webpackプラグインとの互換性に注意が必要で、移行前に`bun run build`で動作確認を怠らないこと。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge RuntimeからNode.js Runtimeへの選択的移行:** 2026年時点でEdge FunctionsはCold Start最小化に有効だが、Node.js互換APIの制限が依然あるため、DBアクセスやファイル処理を含むルートはNode.js Runtimeを選択し、純粋なリクエスト変換・認証チェックのみEdgeに留める設計が最適。

- **ポイント2: Fluid Computeの活用でコスト削減:** VercelのFluid Compute（2025年GA）により、同一インスタンスの並行リクエスト処理が可能になり、従来のEdge/Serverless比較でコスト最大70%削減のケースも。sumitsugiのようなトラフィック予測困難なサービスでは積極採用を検討すべき。

- **ポイント3: ISRとEdge Middlewareの組み合わせ最適化:** Edge Middlewareで認証・A/Bテスト・リダイレクトを処理し、バックエンドへのリクエストをISRキャッシュで吸収するパターンが定石。`x-matched-path`ヘッダーを活用したキャッシュバイパス制御が重要。

- **ポイント4: Streaming ResponseとSuspenseの統合:** Next.js App RouterのSuspense境界とEdge Streamingを組み合わせることで、TTFBを維持しつつLCPを改善できる。ただしEdgeでのStreaming中断時のエラーハンドリングが脆弱なため、`AbortController`によるタイムアウト制御を必ず実装。

- **ポイント5: Regional Edgeの戦略的配置:** `export const preferredRegion = ['nrt1']`（東京）を明示指定することでレイテンシを最小化。グローバル展開前はDBリージョンと同一のEdgeリージョンに固定し、データ境界を越えるラウンドトリップを排除することがパフォーマンスのボトルネック解消に直結する。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のような Branded Types が標準パターンとして定着し、プリミティブ型の誤用をコンパイル時に防止する。

- **`satisfies` 演算子の積極活用:** TypeScript 4.9+ の `satisfies` が2026年には必須テクニックとなり、型推論を保ちつつ型チェックを行うことで、`as` キャストの乱用を排除できる。

- **Template Literal Types による API 設計:** `type Route = `/api/${string}`̀` のような Template Literal Types でルートや文字列パターンを型安全に表現し、実行時エラーをゼロに近づける設計が主流になった。

- **`noUncheckedIndexedAccess` の必須化:** `tsconfig.json` の厳格オプションとして `noUncheckedIndexedAccess: true` が事実上の標準となり、配列・オブジェクトアクセス時の暗黙的 `undefined` を強制的に処理させる。

- **Zod + `infer` による Schema-First 設計:** バリデーションスキーマから型を自動導出する `z.infer<typeof schema>` パターンが、システム境界（API・フォーム・DB）での型定義の二重管理を完全に排除する。
