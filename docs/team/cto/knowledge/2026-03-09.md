# CTO Knowledge - 2026-03-09

## Daily Update (2026-03-09)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データ取得ロジックはすべてServer Componentsに移動し、`'use client'`ディレクティブは本当にインタラクティブな末端コンポーネントのみに限定する。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降でPPRが安定化し、静的シェルと動的ストリーミングを同一ルートで共存させることで、TTFBと体感速度を両立できる。`experimental.ppr`から`ppr: true`への移行タイミングを計画すべき。

- **`next/image` + `sizes` 属性の最適化:** 2026年時点ではAVIF対応ブラウザが主流となり、`formats: ['image/avif', 'image/webp']`の明示設定と適切な`sizes`属性によりLCP改善の費用対効果が高い。

- **Server Actions のバンドル分離意識:** Server Actionsはクライアントから直接呼び出せる利便性の一方、誤用するとウォーターフォールが発生する。データ更新は`revalidatePath`/`revalidateTag`と組み合わせ、Optimistic UIパターンで体感レスポンスを補う。

- **Edge Runtime vs Node.js Runtime の使い分け戦略:** ミドルウェアと認証チェックはEdge Runtimeで低レイテンシを確保しつつ、DBアクセスを伴うRoute HandlersはNode.js Runtimeに留める。Vercel以外のセルフホスト環境では`output: 'standalone'`とコンテナキャッシュ戦略が鍵になる。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化:** 2026年時点でRSCストリーミングはSuspense境界の設計が鍵で、コンポーネント単位でデータフェッチを分離することでTTFB（最初のバイトまでの時間）を大幅に削減できる。

- **PPR（Partial Prerendering）の本格活用:** Next.js 15以降でPPRが安定し、静的シェルを即時配信しつつ動的部分をストリーミングするハイブリッド戦略が標準パターンになっている。

- **React 19のuse()フックとの統合:** `use(Promise)`によりクライアントコンポーネントでもストリーミングデータを自然に扱えるようになり、RSC/RCCの境界設計がよりシンプルになった。

- **Waterfall問題への対策:** `Promise.all`でデータフェッチを並列化し、複数のSuspense境界を適切に配置することで逐次ウォーターフォールを回避するのがベストプラクティス。

- **キャッシュ戦略の複雑化:** `fetch`キャッシュ・`unstable_cache`・Route Segment Configが絡み合うため、ストリーミングと組み合わせる際はキャッシュのスコープと無効化タイミングを明示的に設計する必要がある。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性の標準化:** Next.js + tRPCの組み合わせが中小規模プロダクトのデファクトになりつつあり、クライアント・サーバー間でZodスキーマを共有することでランタイムエラーを大幅に削減できる。

- **GraphQLはBFF層での活用に収束:** フロントエンド直接接続よりも、マイクロサービスの集約レイヤー（BFF）として使うユースケースが主流。Apollo FederationやGraphQL Meshによるスキーマ統合が実用段階に入った。

- **RESTは死なず、OpenAPI 3.1が再評価:** Zodベースの自動スキーマ生成（`zod-openapi`、`hono`など）により、型安全なREST APIをコードファーストで構築できるようになり、外部公開APIではREST+OpenAPIの組み合わせが依然として最有力。

- **エッジ対応がAPI設計の制約条件に:** Cloudflare Workers / Vercel Edgeの普及により、Cold startレイテンシを避けるため軽量ランタイムで動くAPIが求められる。tRPCやHonoはエッジ対応が優れており、重厚なORMやNode専用ライブラリは選定段階で除外されるケースが増えている。

- **AIエージェント向けAPI設計が新しい関心領域:** MCPプロトコルやOpenAPI仕様をLLMに読み込ませてツール呼び出しさせるユースケースが急増。APIの「機械可読性」（明確なスキーマ・エラー構造・冪等性）が設計品質の評価軸として加わっている。

### 4. serverless edge computing 2026

- **AIワークロードのエッジシフト加速:** LLM推論の軽量化（量子化・蒸留）により、クラウド往復なしでエッジノードでリアルタイムAI処理が可能になりつつある。レイテンシ削減とプライバシー保護を同時に実現できる点が注目されている。

- **WebAssembly（Wasm）がランタイムの標準に:** V8/Node.jsに代わりWasmがエッジサーバーレスの主要ランタイムとして定着しつつあり、コールドスタートが数ms以下に。Cloudflare Workers・Fastly Compute等がWasm-firstアーキテクチャを推進している。

- **分散SQLとエッジDBの成熟:** PlanetScale、Turso（libSQL）、Cloudflare D1などがエッジリージョンへのデータレプリケーションを自動化し、「エッジで読み書きできるDB」が現実的な選択肢になった。グローバル整合性とレイテンシのトレードオフ設計が新たな設計スキルとして必要。

- **エッジでのオブザーバビリティ課題:** 分散実行環境での分散トレーシング・ログ集約がまだ未成熟で、OpenTelemetry対応が各プロバイダー間で不均一。エッジ導入時はモニタリング戦略を事前に設計しないとデバッグコストが跳ね上がる。

- **マルチ・クラウドエッジの標準化圧力:** WinterCG（Web-interoperable Runtimes Community Group）主導でエッジランタイムAPI仕様の標準化が進み、ベンダーロックイン回避が現実的になってきた。ただしCI/CDパイプラインのエッジ対応テストは依然として各社独自実装のため、抽象レイヤー導入を推奨。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の標準化:** パスワードレス認証がデファクトスタンダードとなり、フィッシング耐性のあるパスキーをデフォルト認証手段として採用することが必須。iOS/Android/主要ブラウザの対応が揃い、UXの障壁もほぼ解消された。

- **トークンの短命化とリフレッシュ戦略の厳格化:** JWTのアクセストークンは15分以下、リフレッシュトークンはローテーション必須（Refresh Token Rotation）。トークン漏洩時の被害半径を最小化するため、`jti`クレームによる無効化リストの管理も標準的な実装に。

- **デバイスバインディングとコンテキスト認証:** 認証成功後もデバイスフィンガープリント・IPジオロケーション・行動パターンを継続評価するContinuous Authentication（継続的認証）が重要。異常検知時に再認証を要求するアダプティブ認証の導入が攻撃耐性を大幅に向上させる。

- **サプライチェーンリスクとしての認証ライブラリ管理:** `next-auth`等の依存ライブラリの脆弱性は攻撃の主要経路。`bun audit`の定期実行、Dependabotによる自動更新、ライブラリのピン留めを組み合わせてSBOM（ソフトウェア部品表）を管理することが不可欠。

- **セッション管理のゼロトラスト化:** 「一度認証したら信頼する」モデルを廃止し、リソースアクセスごとに権限を再評価。特権操作（決済・個人情報変更等）には必ずステップアップ認証を挟む設計にすることで、セッションハイジャック被害を局所化できる。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のパフォーマンス革新:** Prisma ORM 6系ではクエリエンジンのRust実装が成熟し、N+1問題の自動検出と`relationLoadStrategy: "join"`によるクエリ最適化が実用レベルに達した。Supabase との組み合わせではコネクションプーリング（PgBouncer）との相性を考慮した設定が必須。

- **Supabase の Edge Functions + pgvector によるAI統合:** 2026年時点でSupabaseはpgvector拡張を標準サポートし、ベクトル検索をPostgreSQL内で完結できる。外部ベクトルDBを別途立てるコストを避け、既存RLSポリシーをそのまま適用できる点がアーキテクチャ上の強み。

- **Row Level Security (RLS) の設計が生産性のボトルネック:** Supabaseでは全テーブルにRLSを有効化するのがベストプラクティスだが、Prismaからは直接RLSをバイパスするservice roleと、ユーザー権限のanon/authenticated roleを使い分けるアーキテクチャ設計が重要。サーバーサイド（Next.js Server Actions）ではservice roleを使い、クライアントサイドアクセスは最小化する。

- **Prisma Migrate vs Supabase Migrations の棲み分け:** Prismaのマイグレーション管理とSupabaseのダッシュボード操作は競合しやすい。本番環境では`prisma migrate deploy`をCIパイプラインに組み込み、Supabaseダッシュボードからの手動変更を禁止するガバナンスが不可欠。

- **Connection Pooling の設定ミスが最大の落とし穴:** Supabase + Prismaでは`DATABASE_URL`にTransaction modeのPgBouncerポート（6543）、`DIRECT_URL`にDirect接続（5432）を分離して設定する。マイグレーション実行はDirect接続必須であり、この設定漏れが本番障害の頻出パターン。

### 7. WebAssembly Rust performance 2026

- **ポイント1: WASIp2による本格的なシステム統合** WASIp2（WebAssembly System Interface Preview 2）が2025年に安定化し、Rustから直接ファイルシステム・ネットワーク・非同期I/Oをポータブルに扱えるようになった。エッジ・サーバーレス環境でのRust+WASM採用が急加速している。

- **ポイント2: コンポーネントモデルによる相互運用性の向上** WASMコンポーネントモデルの普及により、Rustで書いたモジュールをJS/Python/Goと型安全に組み合わせられる。`wasm-tools`や`wit-bindgen`のエコシステムが成熟し、マイクロサービス的なWASMコンポジションが実用段階に入った。

- **ポイント3: SIMD・スレッド並列化の実用化** WASMのFixed-width SIMDとWASM Threadsが主要ランタイム（Wasmtime、V8）で安定サポートされ、Rustの`std::simd`や`rayon`相当の並列処理がブラウザ・サーバー両方で動作する。画像処理・ML推論タスクでネイティブの80〜95%程度の性能が出るケースも増えている。

- **ポイント4: Rustのコンパイルサイズ最適化が進化** `wasm-opt`（Binaryen）との統合強化と`cargo-component`の普及で、バイナリサイズの問題が大幅に緩和。`min-sized-rust`のプラクティスを適用すると50〜100KB台のモジュールが当たり前になりつつある。

- **ポイント5: エッジ実行環境でRust+WASMがデファクトに** Cloudflare Workers・Fastly Compute・Fermyon SpinなどのエッジプラットフォームがWASMファーストに移行し、コールドスタートがNode.jsの1/10以下（< 1ms）のRustベースのFunctionが本番採用されている。Next.jsのEdge Runtimeでも内部的にWASMモジュールを活用するパターンが定着してきた。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** App Routerではデフォルトでサーバーコンポーネントを使い、クライアントコンポーネントは`'use client'`で明示的に分離する。不要なJSバンドルを削減し、初期ロードパフォーマンスを大幅に改善できる。

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降でStableになったPPRにより、静的シェルと動的コンテンツを同一ルートで共存させられる。`<Suspense>`境界を適切に設計することで、TTFBとインタラクティビティを両立できる。

- **Server Actions によるデータ変更の統一:** フォーム送信やミューテーション処理をServer Actionsに集約することで、API Routeの乱立を防ぎ、型安全性とセキュリティを確保する。`revalidatePath`/`revalidateTag`との組み合わせでキャッシュ無効化も明示的に管理できる。

- **Parallel Routes & Intercepting Routes の活用:** モーダルやスライドオーバーUIをURLと連動させる場合、`@slot`パターンで実装することでブラウザ履歴との整合性を保ちつつ、SEOにも対応した設計が可能になる。

- **`use cache` ディレクティブへの移行:** Next.js 15の`unstable_cache`から`use cache`への移行が進行中。コンポーネント・関数レベルでキャッシュを宣言できるため、`fetch`に依存しないサーバーサイドロジックでも細粒度のキャッシュ制御が実現できる。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの制約を理解した設計:** Edge FunctionsはNode.js APIの一部（fs, net等）が使用不可のため、依存ライブラリのEdge互換性を事前にチェックし、必要に応じてNode.js Runtimeと使い分けるアーキテクチャが必須。

- **Cold Startの最小化:** バンドルサイズを50KB以下に抑えることがEdge Functionsのレイテンシ最適化の鍵。tree-shakingの徹底と、重いライブラリのダイナミックインポート回避が実効的な手法。

- **KV・Cache APIの積極活用:** Vercel KVやEdge Config、`waitUntil()`を使ったバックグラウンドキャッシュ更新により、DBアクセスをEdgeで行わずにStale-While-Revalidateパターンを実装することでスループットを大幅に向上できる。

- **地理的ルーティングの精緻化:** `request.geo`による地域別コンテンツ配信やA/Bテストをミドルウェアレベルで実装することで、オリジンへのリクエストを削減しつつパーソナライズを実現できる。

- **Observabilityの強化:** Edge環境ではログ取得が限られるため、OpenTelemetryベースのトレーシング（Vercel SpeedInsightsやDatadog Edge統合）を早期に導入し、p99レイテンシの異常を本番前に検出できる体制を整えることが重要。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の普及:** TypeScript 4.9で導入された`satisfies`が2026年には標準パターンとして定着。型推論を維持しながら型チェックを行えるため、`as`キャストによる型安全性の損失を回避できる。

- **Branded Types（名前付き型）の実用化:** `type UserId = string & { readonly _brand: 'UserId' }` パターンが広まり、プリミティブ型の混同バグをコンパイル時に防止。ZodやvaliботとのRefinement統合で実装コストも低下した。

- **`const` type parametersによる型推論の強化:** TypeScript 5.xの`const`型パラメータにより、リテラル型推論が自動化。`as const`アサーションを手書きする必要が減り、設定オブジェクトやルーティング定義の型安全性が向上。

- **Template Literal Types + Mapped Typesの組み合わせ:** APIエンドポイントやイベント名を型レベルで表現するパターンが成熟。`'GET /users/:id'`のような文字列からパラメータ型を自動抽出するユーティリティ型が実プロジェクトで活用されている。

- **`using`宣言（Explicit Resource Management）との統合:** TC39 Stage 4の`using`構文がTypeScriptで安定化し、DB接続・ファイルハンドル等のリソース管理をより型安全に実装可能。`Symbol.dispose`を持つ型の設計が新たなベストプラクティスになりつつある。
