# CTO Knowledge - 2026-08-05

## Daily Update (2026-08-05)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Prerendering の標準化）:** Next.js 15以降で導入されたPPR（Partial Prerendering）が2026年には主流パターンとして定着し、静的シェルを即座に配信しつつ動的部分をストリーミングすることで、Core Web VitalsのTTFB/LCPを大幅改善できる。物件一覧・詳細ページのような「共通枠は静的・在庫情報は動的」な構成に特に有効。

- **ポイント2（React Compilerによる自動最適化）:** React Compilerが安定版として普及し、`useMemo`/`useCallback`の手動チューニングが不要になりつつある。ただし既存コードのリファクタリング時は依存配列の副作用が消えるわけではないため、レンダリング最適化はコンパイラ任せにせず計測ベースで検証すべき。

- **ポイント3（Turbopackのビルド高速化）:** Turbopackが本番ビルドでも標準採用され、大規模コードベースでのビルド時間が数分から数十秒に短縮される事例が増えている。CI/CDのフィードバックループ短縮に直結するため、`bun run build`の実行時間自体もパフォーマンス指標として監視する価値がある。

- **ポイント4（画像・フォントの自動最適化とエッジ配信）:** `next/image`と`next/font`の最適化がエッジランタイムと統合され、CDNキャッシュヒット率を意識した設計が重要になっている。物件写真が多いsumitsugiのようなサービスでは、画像最適化の設定ミスがLCP悪化の最大要因になりやすいので優先的にレビューすべき。

- **ポイント5（Server Actionsのキャッシュ戦略）:** Server Actionsとキャッシュタグ（`revalidateTag`）を組み合わせた細粒度の再検証が一般化し、「物件ステータス変更時のみ該当ページを再生成」といった無駄のない更新が可能になっている。過度な`revalidatePath`の乱用はサーバー負荷増につながるため、更新粒度の設計レビューが必要。

### 2. React Server Components streaming 2026

- **ポイント1:** Partial Prerendering（PPR）が主流化し、静的シェルを即時配信しつつ動的部分だけをストリーミングする構成が標準パターンになっている。物件一覧ページのような「静的なレイアウト＋動的な検索結果」構成に特に有効。
- **ポイント2:** `loading.tsx`とSuspenseの粒度設計が重要度を増しており、コンポーネント単位で細かくストリーミング境界を切ることでTTFB（Time to First Byte）とLCPを分離改善できる。物件詳細ページで画像/レビュー/空室状況を個別にストリームすると体感速度が向上する。
- **ポイント3:** Server ActionsとRSCストリーミングの組み合わせで、フォーム送信後の楽観的UI更新がクライアントJS最小限で実現可能になった。引っ越し費用の見積りフォームなど多段階フローに向いている。
- **ポイント4:** キャッシュ戦略（`use cache`ディレクティブ、Next.js 16のCache Componentsなど）がRSCストリーミングと統合され、再検証タイミングをコンポーネント単位で制御できるようになった。ビルド時の静的判定とランタイムの動的判定の境界を明示的に書けるのが利点。
- **ポイント5:** ストリーミングSSRのモニタリング（TTFB、chunk配信タイミング、hydrationエラー）がObservability標準になりつつあり、Vercelなどのプラットフォームメトリクスと連携した監視体制の構築がベータローンチ前のパフォーマンス確認事項として重要。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの台頭）:** TypeScriptフルスタック構成（Next.js等）ではtRPCがGraphQLの代替として定着しつつあり、スキーマ定義なしで型安全なAPIを実現できる点が開発速度を大きく向上させる。sumitsugiのようなNext.js App Router構成なら、内部API（BFF層）にtRPCを採用することでフロント・バックエンド間の型不整合バグを減らせる。

- **ポイント2（RESTは外部公開APIの標準であり続ける）:** 外部パートナーや第三者連携（決済、不動産ポータル連携など）はRESTまたはOpenAPI仕様が依然として業界標準で、GraphQL/tRPCは主に内部・自社フロントエンド向けに使い分けるハイブリッド構成が主流化している。

- **ポイント3（GraphQLは複雑な集約クエリに限定活用）:** GraphQLの学習コストとキャッシュ戦略の複雑さから、単純なCRUD中心のプロダクトでは採用が減少傾向。物件検索・フィルタリングのような多次元クエリが必要な機能に限定して部分導入するのが現実的。

- **ポイント4（BFFパターンとエッジ実行の融合）:** 2026年はAPI層をVercel EdgeやCloudflare Workers上で実行し、レイテンシを地理的に最小化する構成が一般化。Next.js 16のRoute Handlersをエッジランタイムで動かし、認証・データ整形をBFF層に集約する設計が推奨される。

- **ポイント5（AIエージェント向けAPI設計）:** LLMエージェントやMCP経由でのAPI利用を前提とした「エージェントフレンドリーなAPI」設計（明確なエラーメッセージ、冪等性、構造化レスポンス）が新たな設計基準として重要視されている。将来的な自動化（自律開発ワークフロー等）を見据え、sumitsugiの内部APIも同様の原則を意識すべき。

### 4. serverless edge computing 2026

- **エッジでの推論処理:** 2026年はLLM推論の一部をエッジで実行する構成が普及し、Cloudflare Workers AIやFastlyのCompute@Edgeでの軽量モデル実行がレイテンシ改善の主戦場になっている。ただし大規模モデルは依然中央集権的なGPUクラスタが必須で、エッジは前処理・ルーティング・キャッシュ層に留めるのが現実的な設計。

- **コールドスタート問題の実質解消:** V8 isolateベースの実行環境（Workers、Deno Deploy等）はミリ秒単位の起動を実現しており、従来のコンテナ型サーバーレス（Lambda等）と比べて体感差が大きい。新規APIエンドポイントの設計時はこの起動特性の違いを踏まえてプラットフォームを選ぶべき。

- **データローカリティ制約:** エッジ実行はステートレスが前提だが、実際のアプリはDBアクセスが伴うため、D1やTurso等のエッジ対応DBとの組み合わせが鍵になる。sumitsugiのような物件データ中心のプラットフォームでは、読み取りが多い一覧ページはエッジキャッシュ、書き込みを伴う予約・決済処理は中央サーバーに残す、というハイブリッド設計が現実解。

- **観測性の複雑化:** エッジは分散実行されるため、従来のAPMツールでは追跡が難しく、OpenTelemetryベースの分散トレーシングが事実上の標準になりつつある。導入コストを考えると、全機能を一気にエッジ化するのではなく、まずは静的コンテンツ配信とA/Bテスト振り分けなど副作用の少ない箇所から段階的に移行するのが安全。

- **コスト構造の逆転リスク:** リクエスト数課金のエッジ実行は低トラフィック時は安いが、高トラフィックのSaaSでは従来のサーバーより高くつくケースが増えている。MVP段階の今は静的資産配信（Next.jsのISR/静的ページ）にエッジCDNを使う程度に留め、本格的なエッジコンピューティング投資はローンチ後のトラフィック実績を見てから判断するのが妥当。

### 5. authentication security best practices 2026

- **パスキー/WebAuthnのデフォルト化:** パスワードレス認証（FIDO2/WebAuthn）が主流となり、フィッシング耐性のある認証をUXを損なわずに実装できる。パスワードは補助手段に格下げし、初期実装コストより長期的な漏洩リスク低減を優先すべき。

- **セッション管理とトークンの短命化:** JWTなどのアクセストークンは短命化し、リフレッシュトークンのローテーション＋失効検知（reuse detection）を組み合わせることで、トークン漏洩時の被害範囲を最小化できる。

- **多要素認証の段階的強制:** 全ユーザー一律ではなく、リスクベース認証（IPレート異常・デバイス変更・高額取引等）でMFAを動的に要求する設計が、セキュリティとコンバージョン率のバランスとして2026年の標準的アプローチ。

- **認証基盤の外部化・標準化:** 自前実装よりOAuth2.1/OIDC準拠のマネージドID基盤（Auth0, Clerk等）を採用し、脆弱性修正やコンプライアンス対応をベンダー側に委ねることで開発リソースをコア機能に集中できる。

- **監査ログとゼロトラスト前提の設計:** 認証成功後も「信頼しない」前提でAPIレベルの認可チェックを都度行い、全認証イベントを不変ログとして保持することで、インシデント発生時の追跡と法的対応（個人情報保護法対応含む）を担保する。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** PrismaはORM層とマイグレーション管理を担い、Supabaseはその下のPostgreSQL基盤・認証・Row Level Security（RLS）・リアルタイム機能を提供する構成が主流化しており、両者を組み合わせることで型安全性とマネージドインフラの両立が可能になっている。

- **ポイント2:** SupabaseのRLSポリシーとPrismaのスキーマ管理を併用する場合、Prisma Migrateで生成したDDLにRLSポリシーが含まれないため、`supabase/migrations`とPrismaのマイグレーションを二重管理せず、Prisma側を単一の真実源（source of truth）にしてRLSはSQLマイグレーションファイルで別管理するのが実務上の落とし穴回避策になる。

- **ポイント3:** Prisma AccelerateやSupabaseのConnection Pooler（PgBouncer）を使ったコネクションプーリングは、Next.jsのサーバーレス関数・エッジ環境で必須級の対策であり、これを怠るとDB接続数枯渇によるプロダクション障害に直結する。

- **ポイント4:** 物件データのようなステータス遷移（`draft` | `public`）を持つスキーマでは、PrismaのenumやZodスキーマとDB制約（CHECK constraint）を二重に定義し、アプリ層とDB層の両方で不整合を防ぐ設計が2026年時点のベストプラクティスとして定着している。

- **ポイント5:** SupabaseのVector拡張（pgvector）とPrismaを組み合わせたAI検索機能（物件のセマンティック検索など）の実装事例が増えており、将来的な「次の住人」マッチング機能の拡張余地としても技術選定上の強みになる。

### 7. WebAssembly Rust performance 2026

- **ポイント1（コンパイル最適化とバイナリサイズ）:** Rust 1.8x系のwasm32-wasip2ターゲットとComponent Modelの安定化により、wasm-optやwit-bindgenのツールチェーンが成熟し、バイナリサイズを保ちながらネイティブの80-95%程度の実行速度を安定して出せるようになっています。

- **ポイント2（SIMDとマルチスレッド標準化）:** WASM SIMDとshared memory + Web Workersを組み合わせた並列処理がブラウザ全般で安定サポートされ、画像処理・PDF生成・地図描画のような重い処理をメインスレッドから切り離せるため、sumitsugiの物件写真最適化や間取り図生成に応用できそうです。

- **ポイント3（Component Model / WASI Preview 2）:** WASIの標準化が進み、Rust製ロジックをNode.js/Bunだけでなくブラウザ・エッジ（Cloudflare Workers等）で同一バイナリとして再利用できるようになったため、料金計算や引っ越し費用シミュレーションのコアロジックをRust+WASMで一元化する選択肢が現実的になっています。

- **ポイント4（Bunとの相性）:** Bunのネイティブwasm実行がV8/JSCより高速なケースが増えており、Next.js 16のServer Componentsからwasmモジュールを直接importして重い計算（検索スコアリング、画像フィンガープリンティング等）をサーバー側で完結させるパターンが実用段階に入っています。

- **ポイント5（開発体験の落とし穴）:** 依然としてJS⇔WASM間のメモリコピーがボトルネックになりやすく、小さな関数呼び出しを頻繁に行う設計だとオーバーヘッドで逆に遅くなるため、「重い計算をまとめて渡す」バッチ設計を徹底することが2026年時点でも成功の鍵です。

### 8. Next.js App Router patterns 2026

- **ポイント1: Server Actionsのデフォルト化とProgressive Enhancement:** フォーム送信やミューテーションはServer Actionsが標準パターンとなり、`useActionState`と組み合わせてJS無効環境でも動作するProgressive Enhancementが実装しやすくなっている。sumitsugiの物件登録・お問い合わせフォームでもクライアント側バリデーションとServer Actionsを併用する構成が主流になりつつある。

- **ポイント2: Partial Prerendering (PPR) の本格採用:** 静的シェルを即座に返しつつ動的部分をストリーミングするPPRが安定版として広まり、物件一覧ページのように「検索フィルタは動的、レイアウトは静的」という構成でTTFBを大幅に改善できる。Next.js 16ではキャッシュ戦略（`use cache`ディレクティブ）との組み合わせがベストプラクティスとして定着している。

- **ポイント3: `use cache`ディレクティブによる明示的キャッシュ制御:** `unstable_cache`から進化した`use cache`が本命APIとなり、関数・コンポーネント単位で「何を・どれだけキャッシュするか」を明示的に宣言する設計が推奨される。物件データのような更新頻度が中程度のデータでは、タグベースの再検証（`revalidateTag`）と組み合わせて鮮度とパフォーマンスを両立させやすい。

- **ポイント4: Server ComponentsとClient Componentsの境界設計:** 「Client Componentsは葉（leaf）に寄せる」という原則がより厳格に運用されるようになり、認証状態や物件データの取得はServer Componentsに集約、インタラクティブなUI（フィルタ、モーダル等）のみをClient Componentsに分離する構成がパフォーマンスとメンテナンス性の両面で標準化している。

- **ポイント5: Route Handlersの型安全化とMiddlewareの軽量化:** Zodスキーマと連携した型安全なRoute Handlersパターンが普及し、Middlewareは認証チェックなど最小限の処理に留め重い処理はServer Componentsやgeneral-purposeのAPI層に移す設計が推奨される。これはstandards.mdの「Zodスキーマによる境界バリデーション」方針とも合致する。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約設計:** Vercel Edge FunctionsはV8アイソレートベースでNode.js APIの一部が使えないため、`fs`や重いライブラリに依存するコードは事前にNode.js Runtime向けと分離し、認証チェックやリダイレクトなど軽量処理に限定して使うのが2026年時点でも鉄則です。

- **コールドスタート削減とバンドルサイズ:** Edge Functionsの起動遅延はバンドルサイズに比例するため、依存パッケージを最小限にし（Zodなど軽量ライブラリの選定）、Tree-shakingを意識したimportを徹底することでレスポンスタイムを数十ms単位で改善できます。

- **ISR/Edge Cachingとの組み合わせ:** Next.js 16のPartial Prerendering（PPR）とEdge Functionsを組み合わせることで、静的部分をCDNキャッシュしつつ動的部分のみEdgeで処理する構成が主流になっており、物件一覧ページのような読み込み頻度が高いページで有効です。

- **リージョン最適化とデータレイテンシ:** Edge Functionsはグローバル分散実行が強みですが、DB（例: Supabase/Postgres）のリージョンとEdge実行リージョンが離れているとかえってレイテンシが悪化するため、`export const runtime = 'edge'`を指定する箇所はデータアクセスパターンを精査してから採用すべきです。

- **可観測性とデバッグの難しさ:** Edge環境はNode.jsデバッガやローカルログが使いにくいため、Vercelの`waitUntil`やOpenTelemetry連携によるトレーシングを早期に導入し、本番障害時の切り分けコストを下げる投資が重要です。

### 10. TypeScript type safety patterns 2026

- **型推論の高度化:** TypeScript 5.x系でconst型パラメータやsatisfies演算子が定着し、型注釈を減らしつつ厳密な型安全性を保てるようになっています。sumitsugiのようなNext.js App Routerプロジェクトでは、APIレスポンスの型を`satisfies`で検証しつつ推論結果を保持するパターンが有効です。

- **Zodによるランタイム検証との統合:** 静的型だけでは外部入力（フォーム、API、DB）の安全性は担保できないため、Zodスキーマから型を生成する`z.infer<>`パターンが標準化しています。当プロジェクトのstandards.mdにもある「システム境界でのZod検証」は2026年のベストプラクティスと一致しており、継続すべき方針です。

- **ブランデッド型（Branded Types）の普及:** `type SellerId = string & { __brand: 'SellerId' }`のようなブランデッド型で、`sellerId`と`propertyId`のような同じ`string`型同士の取り違えをコンパイル時に防ぐパターンが浸透しつつあります。物件・ユーザーIDが多いsumitsugiのデータ構造では導入価値が高いです。

- **Discriminated Unionによる状態管理:** `'draft' | 'public'`のようなステータス列挙は、単純なUnion型よりも判別可能なオブジェクト型（`{status: 'draft', ...}`）に発展させることで、各状態で必要なプロパティの有無をコンパイル時に強制できます。物件ステータスの拡張時（例: 公開予約中など）を見据えると有用です。

- **Template Literal Typesによる文字列検証:** ルーティングパスやi18nキーなど、`` `properties/${string}` ``のようなテンプレートリテラル型で文字列パターンを型レベルで検証する手法が、App Routerプロジェクトで広く使われ始めています。ハードコードされたパス文字列のタイプミスを防げます。
