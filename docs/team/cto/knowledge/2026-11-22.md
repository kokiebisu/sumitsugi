# CTO Knowledge - 2026-11-22

## Daily Update (2026-11-22)

### 1. Next.js performance optimization 2026

- **Turbopackのデフォルト化とビルド高速化:** Next.js 16ではTurbopackが本番ビルドでも安定版となり、大規模コードベースでもdev起動・HMR・buildの待ち時間が大幅短縮される。sumitsugiのようにpropertiesやlisting配下でコンポーネントが増えていくプロジェクトでは、ビルド時間の劇増を防ぐ効果が大きい。

- **Partial Prerendering (PPR) の活用:** 静的なレイアウト部分（ヘッダーや物件一覧の骨格）を事前レンダリングしつつ、動的な部分（認証状態・リアルタイム在庫など）だけをストリーミングすることで、TTFBとLCPを両立できる。`'draft'/'public'`ステータスで表示が切り替わる物件ページのようなケースに適している。

- **Server ComponentsでのN+1フェッチ抑制:** React 19/Next.js 16のキャッシュ機構（`use cache`ディレクティブ）を活用し、`src/lib/data.ts`経由のデータ取得を明示的にメモ化・タグ付けすることで、再検証コストを抑えつつ鮮度を保てる。無計画な`fetch`多用はサーバーレスポンスを悪化させやすい。

- **画像・フォント最適化の継続的徹底:** `next/image`のAVIF/WebP自動変換とレスポンシブ配信、`next/font`によるレイアウトシフト防止は依然重要。物件写真を多用するUIではCLS・LCPに直結するため、優先度高で見るべき指標。

- **Bunとの組み合わせでのエッジ最適化:** Bunランタイムの高速な依存解決とNext.jsのEdge Runtime対応を組み合わせることで、認証チェックやリダイレクトなどの軽量ミドルウェア処理を低レイテンシ化できる。CIでのビルド時間短縮にも寄与するため、`bun run build`の実行時間を定期的に計測し退行を早期検知する運用が有効。

### 2. React Server Components streaming 2026

- **ポイント1:** RSCのストリーミングはNext.js 16でさらに細粒度化され、`loading.tsx`やSuspense境界単位ではなくコンポーネント単位でのPartial Prerendering（PPR）が標準化されつつある。静的シェルを即時配信し、動的部分だけを後続ストリームで差し込む構成にすることで、TTFBとLCPを両立できる。

- **ポイント2:** サーバー側のデータフェッチとストリーミングの組み合わせが前提になり、`Promise`をそのままJSXに渡して`<Suspense>`で待つパターンが主流化。sumitsugiの物件詳細ページのような「基本情報は即表示、価格計算や空室状況は遅延表示」という使い分けに向いている。

- **ポイント3:** ストリーミングSSRはウォーターフォール（直列await）を避けないと効果が薄れる。`Promise.all`で並列フェッチしてから各コンポーネントに個別のPromiseを渡す設計にしないと、Suspense境界があってもTTFBが改善しない点は要注意。

- **ポイント4:** キャッシュ戦略（`revalidate`やタグベースの再検証）とストリーミングの相性が重要になっている。`'draft'`/`'public'`のようなステータス切り替えがあるページでは、キャッシュの無効化タイミングを誤ると古い状態がストリーム配信されるリスクがあるため、ステータス変更時のタグ再検証を徹底する必要がある。

- **ポイント5:** エッジランタイムでのストリーミングが一般化し、グローバル配信時のレイテンシ改善が顕著。ただしNode.js専用APIに依存するライブラリ（PDF生成など）はエッジ非対応のため、ランタイムの混在構成（Edge/Node）を意識したアーキテクチャ設計が必要。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** 2026年現在、新規プロジェクトでは型安全性を最優先する傾向が強まり、tRPCがTypeScriptフルスタック構成（Next.js + tRPC）でのデフォルト選択肢になっている。REST/GraphQLのようなスキーマ定義・コード生成の手間なく、フロントエンドとバックエンドで型を共有できる点が開発速度に直結する。

- **ポイント2:** GraphQLは依然として「複数クライアント（Web/モバイル/パートナーAPI）が異なるデータ形状を必要とする」ケースで優位性を保つが、N+1問題やキャッシュ設計の複雑さから、社内向けAPIでは採用が減りつつある。外部公開APIや多様なコンシューマが想定される場合のみ検討する価値がある。

- **ポイント3:** RESTは「公開API」「サードパーティ連携」「長期的な後方互換性が必須な契約」において依然最有力。HTTPキャッシュ・CDN・標準ツールチェーンとの相性が良く、sumitsugiのような外部連携（決済・不動産データ連携等）が今後必要になる場面ではRESTが安全な選択。

- **ポイント4:** アーキテクチャ選定は「誰がクライアントか」で決めるべき — 自社フロントエンドのみならtRPC、外部パートナー/サードパーティ統合が絡むならREST、多様なクライアント形状が必要ならGraphQL。sumitsugiは現状Next.jsモノレポ構成のため、tRPCまたはNext.js Server Actions + Zodバリデーションの組み合わせが最も運用コストが低い。

- **ポイント5:** いずれの方式でも、Zodなどによる境界バリデーションとエラーハンドリングの一貫性が設計品質を左右する。API形式そのものより「型安全性・入力検証・契約のテスト可能性」を重視する流れが2026年の主流になっている。

### 4. serverless edge computing 2026

- **ポイント1:** エッジでのAI推論（Edge Inference）が標準化し、Cloudflare Workers AIやVercel Edge Functionsで軽量LLM推論をオリジン無しで実行できるようになった。レイテンシ要件の厳しい機能（検索補完・パーソナライズ）はエッジ実行を検討する価値がある。

- **ポイント2:** コールドスタート問題がV8 isolateベースの実行環境（Workers/Deno Deploy）でほぼ解消され、ミリ秒単位の起動が一般化。Next.jsのMiddlewareやRoute Handlersをedge runtimeに切り替える際のNode.js API制約（fs非対応など）は依然注意が必要。

- **ポイント3:** エッジでのデータ整合性を担保する分散SQLite（Cloudflare D1、Turso）が成熟し、グローバル分散でも強整合性読み取りが可能になった。弊社のようなマーケットプレイス型サービスでは、在庫・公開状態（`draft`/`public`）の整合性確保にこの種のレプリケーション戦略が有効。

- **ポイント4:** サーバーレスのベンダーロックイン対策として、WinterCG標準（Web標準API準拠のランタイム）への準拠が進み、Workers/Deno/Node.jsエッジランタイム間の移植性が向上。新規実装では`fetch`ベースのWeb標準APIに寄せることで将来の移行コストを下げられる。

- **ポイント5:** エッジでのコスト最適化は「実行時間課金」から「リクエスト数+CPU時間」の細粒度課金へ移行し、静的生成（SSG）とエッジSSRのハイブリッド戦略がコスト効率の鍵。トラフィックの少ないMVPフェーズでは、全ページをedgeで動かすより、静的化できるページを見極めるROI分析が重要。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワード+SMS OTPはフィッシング耐性が低く、2026年はパスキー（WebAuthn）をデフォルト認証手段とし、パスワードは復旧用の第二手段に格下げするのが標準。

- **セッション・トークンの短命化とバインディング:** 長寿命JWTの単独利用は漏洩時のリスクが大きいため、短命アクセストークン＋リフレッシュトークンローテーション、かつデバイス/IPフィンガープリントとのバインディング（token binding/DPoP）で盗難トークンの再利用を防ぐ。

- **認可ロジックのアプリ層への分離:** 認証(Who)と認可(What)を混在させず、属性ベース（ABAC）やポリシーエンジン（OPA等）で権限判定を一元化し、エンドポイントごとにアドホックなif文でチェックするのを避ける。

- **ゼロトラスト前提の多層防御:** ログイン成功後も「信頼しない」設計（継続的リスク評価、異常検知、ステップアップ認証）を組み込み、単発のログイン認証だけでセッション全体を保証しない。

- **シークレット管理の自動ローテーション:** APIキー・DB認証情報をコードやenvファイルに静的に置かず、Vault等のシークレットマネージャーで動的発行・自動失効する仕組みを前提にする（sumitsugiのようにenv varsを使う場合も、長期固定キーは定期ローテーション対象にする）。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はPostgreSQLの行レベルセキュリティ（RLS）をスキーマレベルでサポートし、SupabaseのRLSポリシーとORM定義を併用する際の型安全性が大幅に向上した。マルチテナントSaaSではDB側のRLSとアプリ側の認可ロジックを二重に書かず、Prismaのポリシー定義から型を生成する運用が主流になっている。

- **ポイント2:** SupabaseのEdge Functions + Prisma Accelerateを組み合わせたコネクションプーリングが標準パターンとして定着し、サーバーレス環境でのDB接続数枯渇問題が実質的に解消された。本プロジェクトのようなNext.js App Router + Bun構成では、Vercel/Edgeランタイムからの直接接続ではなくPrisma Accelerate経由を推奨。

- **ポイント3:** スキーマ駆動開発（Prisma Schema → Zodスキーマ自動生成）が標準標準化し、`zod-prisma-types`系ツールでDBスキーマとAPI境界のバリデーションを単一ソースから生成できる。本プロジェクトの「Input validation: Use Zod schemas at system boundaries」方針と直結し、`status: 'draft' | 'public'`のようなUnion型もスキーマ変更時に自動で整合性チェックできる。

- **ポイント4:** SupabaseのPostgres 17対応により、JSON型カラムのインデックス性能が改善し、物件データのような半構造化データ（アメニティ・画像メタデータ等）をJSONBで持ちつつPrisma経由で型安全にクエリできるようになった。正規化とJSONBのハイブリッド設計がパフォーマンスとスキーマ柔軟性のバランスとして評価されている。

- **ポイント5:** Supabase RealtimeとPrismaのトランザクション境界を明確に分離する設計が推奨されるようになった。前の住人↔次の住人間のメッセージングのようなリアルタイム機能はSupabase Realtimeで、トランザクショナルな整合性が必要な予約・決済処理はPrisma + Postgresのトランザクションで担当する、という責務分離が業界標準パターン化している。

### 7. WebAssembly Rust performance 2026

- **コンパイル最適化の進化:** Rust 1.80+とwasm-bindgenの最新版では、LLVMベースの最適化パイプラインが強化され、WASMバイナリサイズが従来比20-30%削減可能に。`wasm-opt`との組み合わせでさらにペイロードを圧縮し、初回ロード時間を短縮できる。

- **Component Model標準化の進展:** WASI Preview 2とComponent Modelの実装が各ランタイム（Wasmtime, Wasmer）で成熟し、言語間の相互運用性が実用レベルに。Rustで書いたコンポーネントを他言語のホストから直接呼び出せるため、マイクロサービス的なモジュール分割がブラウザ外でも現実的な選択肢になっている。

- **メモリ管理のボトルネック解消:** 従来WASMの弱点だったGCとの統合がWasm GC proposalの実装進展で改善され、Rustのゼロコスト抽象化とWASMの線形メモリモデルの組み合わせが、JS/TS実装比で2-5倍のスループット向上を示すベンチマークが増加。CPU負荷の高い画像処理・PDF生成などのフロントエンド処理に適している。

- **ビルドチェインの実務的な摩擦:** `wasm-pack`やTrunkのエコシステムは安定してきたが、Next.js 16のApp RouterでのSSR環境とWASMモジュールの統合（特にNode.js runtimeとEdge runtimeでの挙動差異）は依然として検証コストが高い。導入前にEdge環境でのWASM実行可否を必ず確認すべき。

- **実用化の判断基準:** 一般的なCRUD処理やDOM操作ではWASM導入のオーバーヘッド（JS↔WASM間のシリアライズコスト）が利益を上回るケースが多い。sumitsugiのような物件情報プラットフォームでは、画像処理・PDF生成・大量データのクライアント側フィルタリングなど計算集約的な処理に限定して適用するのが現実的。

### 8. Next.js App Router patterns 2026

Next.js App Router patterns 2026について、CTOの視点から要点をまとめます。

- **ポイント1（Server Components優先 + Partial Prerendering標準化):** 静的部分をビルド時に生成しつつ動的部分をストリーミングするPPRが安定版として本格採用され、ページ単位ではなくコンポーネント単位でキャッシュ戦略を設計するのが標準になっている。sumitsugiのように`properties/`配下に動的な物件データと静的なレイアウトが混在するページでは、適用効果が大きい。

- **ポイント2（`use cache`ディレクティブによる明示的キャッシュ制御):** fetchベースの暗黙キャッシュから、関数・コンポーネント単位で`'use cache'`を明示する方式に移行が進んでいる。データ鮮度の制御が予測しやすくなり、`draft`/`public`のようなステータス変更が即時反映されるべき箇所とキャッシュ可能な箇所を明確に分離できる。

- **ポイント3（Server Actionsのセキュリティ境界強化):** Server Actionsが本番運用で一般化した一方、CSRFや認可漏れのインシデント事例が増え、Zodによる入力検証とオリジン検証をミドルウェアで強制するパターンがベストプラクティスとして定着した。弊社の「入力検証はZodスキーマで」という方針と直接一致する。

- **ポイント4（Route Handlersとの責務分離):** Server Actionsは「ミューテーション」、Route Handlers（`route.ts`）は「外部API・webhook・ファイルダウンロード」という役割分担が明確化され、混在させるアンチパターンが減少した。

- **ポイント5（ビルド時間最適化のための粒度設計):** App Router採用プロジェクトの規模拡大に伴い、Turbopack本採用後もモノレポ化・ディレクトリ分割によるインクリメンタルビルドの重要性が増している。「小さいファイル」方針（200-400行目安）は、この観点でもビルド速度とキャッシュ命中率に有利に働く。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge FunctionsのランタイムはV8 isolateベースで実行されるため、Node.js API全体ではなくWeb標準API（fetch, Request/Response等）に依存した実装にすることで、コールドスタートを最小限に抑えられる。重い依存関係（ORM、暗号ライブラリ等）はNode.js Runtime側に残し、Edgeは認証チェックやリダイレクト、A/Bテストの軽量処理に限定するのが鉄則。

- **ポイント2:** Streaming SSR・Partial Prerendering（PPR）との組み合わせが主流になっており、Edge側で静的シェルを即時返しつつ、動的部分をストリーミングで後追いする構成がTTFBを大きく改善する。sumitsugiのような物件詳細ページ（画像多め・動的データ混在）では特に効果が大きい。

- **ポイント3:** Edge Middlewareの濫用がパフォーマンス劣化の典型的な原因になっている。全リクエストに対して認証・ロケール判定・Bot検知などを一つのmiddlewareに積み過ぎると、matcherを絞らない限り静的アセットまで処理が走ってしまうため、`config.matcher`でパスを厳密に絞り込むことが重要。

- **ポイント4:** リージョン選択はEdge Functionsが実行されるPOP（Point of Presence）と、呼び出し先のデータベース/APIのリージョンを揃えることが性能の鍵。Edge-to-Origin間のレイテンシがボトルネックになりやすいため、Edge Config（KVストア）やVercel内製キャッシュを使ってDBラウンドトリップ自体を減らす設計が推奨される。

- **ポイント5:** 観測性（Observability）の強化が2026年のトレンドで、Edge Runtime向けのOpenTelemetry対応が成熟してきている。Edge特有の「関数ごとの実行時間制限」「メモリ制限」を監視しないと、本番でサイレントにタイムアウトするケースがあるため、Vercelの組み込みObservabilityまたは外部APM連携を早期に導入すべき。

### 10. TypeScript type safety patterns 2026

- **ポイント1: 構造的型チェックの強化（`satisfies`演算子の定着）** `satisfies`を使うことで、型推論を保ったまま型の整合性を検証できるため、`as`によるキャスト濫用を防ぎつつ開発者体験を損なわない実装が主流になっています。

- **ポイント2: ブランド型（Branded Types）による値の誤用防止** `type UserId = string & { __brand: 'UserId' }`のようなパターンで、`listingId`と`userId`のような同じ基底型だが意味の異なる値の取り違えをコンパイル時に検出するケースが増えています。弊社の`src/lib/data.ts`のようなドメインモデルが多い構造では特に有効です。

- **ポイント3: Zodなどのスキーマライブラリとの型推論統合** `z.infer<typeof schema>`でランタイム検証と静的型を単一のソースから生成するパターンが標準化し、「検証コードと型定義の二重管理」という典型的な技術的負債を排除できます。弊社の標準でも入力境界でのZod利用を規定しており、今後はAPI境界・フォーム・DBクエリ全てで一貫したスキーマ駆動開発を徹底すべきです。

- **ポイント4: Discriminated Unionによる状態管理の網羅性チェック** `'draft' | 'public'`のようなUnion型に対し、`switch`文で`never`型を使った網羅性チェック（exhaustiveness check）を組み合わせることで、新しいステータス追加時の見落としをコンパイル時に検出できます。物件ステータスのような重要なドメイン状態には必須のパターンです。

- **ポイント5: TypeScript 6系のネイティブGo実装移行による高速化がもたらす開発体験向上** 型チェック速度が大幅に向上することで、より厳格な型設定（`strict`, `noUncheckedIndexedAccess`等）をCIで常時実行するコストが下がり、「速度のために型安全性を妥協する」というトレードオフが過去のものになりつつあります。
