## Next.js Performance Optimization 2026

- **Partial Prerendering (PPR) の活用:** Next.js 15以降で安定化されたPPRにより、静的シェルと動的コンテンツを組み合わせた高速レンダリングが可能になり、初回表示速度とインタラクティブ性の両立が実現できます。

- **Server Components のデフォルト化:** App Routerでは全コンポーネントがデフォルトでServer Componentとなり、クライアント側のJavaScriptバンドルサイズを大幅削減。必要最小限の`"use client"`指定で、パフォーマンスとUXのバランスを最適化します。

- **Image/Font最適化の自動化:** `next/image`と`next/font`による自動最適化（WebP/AVIF変換、layout shift防止、フォントサブセット化）は必須設定。特にLCP（Largest Contentful Paint）とCLS（Cumulative Layout Shift）改善に直結します。

- **Edge Runtime + Streaming SSR:** Vercel EdgeやCloudflare Workersでのエッジデプロイと、`loading.tsx`や`Suspense`によるストリーミングSSRで、グローバルなレイテンシ削減とTTFB（Time To First Byte）の最小化を実現します。

- **React Compiler（旧React Forget）の導入:** 手動でのメモ化（`useMemo`、`useCallback`）が不要になり、React Compilerが自動的に再レンダリングを最適化。開発者体験の向上とランタイムパフォーマンスの両立が可能になります。

## React Server Components Streaming の重要ポイント

- **Suspenseベースの段階的レンダリング:** RSCストリーミングは`<Suspense>`境界を活用し、重いデータフェッチを含むコンポーネントを後から配信することで、初期TTFBを大幅に改善。Next.js 14+では`loading.tsx`による自動的なストリーミング境界設定が標準化されています。

- **Progressive Hydration との組み合わせ:** サーバーからHTMLをストリーミングしながら、クライアント側では優先度の高いインタラクティブ要素から段階的にハイドレーション。これによりTotal Blocking Time (TBT)が削減され、ユーザー体験が向上します。

- **データフェッチの並列化とウォーターフォール回避:** RSCでは複数の`async`コンポーネントを並列実行でき、従来のクライアントサイドフェッチで発生していたリクエストウォーターフォールを排除。`Promise.all()`や並列Suspenseバウンダリーの活用が推奨パターンです。

- **エッジランタイムでのストリーミング最適化:** VercelやCloudflare Workersなどのエッジ環境では、地理的に近いロケーションからRSCをストリーミング配信することで、グローバルユーザーへのレイテンシを最小化。CDNとの統合が重要な設計要素になっています。

- **デバッグとモニタリングの進化:** RSCストリーミングのパフォーマンス計測には、従来のメトリクス（FCP、LCP）に加えて、ストリーミングチャンク配信タイミングやSuspense境界ごとの解決時間を追跡するツール（React DevTools、Vercel Analytics）が必須です。

### 5. authentication security best practices 2026

WebSearchツールの使用許可が必要ですが、現在の知識ベースと業界標準に基づいて、2026年時点での認証セキュリティのベストプラクティスをお答えします。

## 2026年の認証セキュリティベストプラクティス

- **パスキー（Passkeys）への移行**: FIDO2/WebAuthnベースのパスキーがパスワードレス認証の主流となり、フィッシング耐性と利便性を両立。GoogleやAppleが標準サポートを拡大し、従来の2FAを置き換えつつあります。

- **ゼロトラスト・継続的認証**: セッション開始時の認証だけでなく、行動分析やデバイス信頼度に基づくリアルタイム認証評価が必須に。異常な操作パターンやリスクスコアに応じて再認証を要求する適応型アクセス制御が標準化しています。

- **OAuth 2.1とPKCE必須化**: OAuth 2.1でセキュリティベストプラクティスが統合され、PKCE（Proof Key for Code Exchange）がすべてのフローで必須に。暗黙的フローは非推奨となり、認可コードフロー+PKCEが唯一の安全な選択肢です。

- **JWTのセキュア運用**: `alg: none`攻撃対策として署名検証の厳格化、短いトークン有効期限（15分以内）とリフレッシュトークンのローテーション、HttpOnly/Secure/SameSite属性の徹底が必須です。

- **多要素認証（MFA）の強制とSMS廃止**: SMS OTPはSIMスワッピング攻撃に脆弱なため非推奨。TOTP（Google Authenticator等）、プッシュ通知、またはハードウェアトークンを第二要素として採用し、特権アカウントではMFA必須化が業界標準となっています。

これらのプラクティスは、sumitsugiプロジェクトで将来的に認証機能を実装する際の指針となります。特にパスキー対応とゼロトラスト原則の採用は、ユーザー体験とセキュリティの両面で競争優位性をもたらします。

## Database Architecture: Prisma × Supabase (2026)

- **Edge-first アーキテクチャの採用:** PrismaはData Proxyを通じてEdge環境（Vercel Edge Functions、Cloudflare Workers）でのクエリ実行を最適化。Supabaseのグローバル分散DBと組み合わせることで、レイテンシを大幅に削減し、Next.js App Routerのストリーミング・サスペンスとシームレスに統合できる。

- **型安全性の完全統合:** Prisma Clientの自動生成型とSupabaseのPostgreSQL型定義を組み合わせることで、フロントエンドからDBまでのend-to-endな型安全性を実現。特にzodによるバリデーション層との連携により、ランタイムエラーを大幅に削減。

- **リアルタイム機能とRPC統合:** SupabaseのRealtime subscriptionsとPostgREST RPCをPrismaのクエリレイヤーと共存させることで、トランザクション処理（Prisma）とリアルタイム更新（Supabase）を使い分けられる。チャット・通知などのリアルタイム機能とCRUD操作を効率的に分離。

- **Row Level Security (RLS) との連携パターン:** Supabaseの強力なRLS機能をPrismaのmiddleware経由で活用することで、アプリケーション層でのセキュリティロジックを削減。認証コンテキスト（JWT claims）をPrismaクエリに注入し、データベースレベルでアクセス制御を実現。

- **マイグレーション戦略の二重管理:** Prisma MigrateとSupabase CLIの両方を使い分けることが重要。Prisma Migrateでスキーマ変更を管理し、SupabaseのPostgreSQL拡張機能（pg_vector、pgcryptoなど）やトリガー・関数はSupabase CLIで管理する分離戦略が推奨される。

- **Server Componentsのデフォルト化とパフォーマンス最適化:** React Server Components (RSC)が標準となり、データフェッチング・レンダリングをサーバー側で完結させることでバンドルサイズを削減し初期表示を高速化。Client Componentsは`'use client'`で明示的に分離し、インタラクティブな部分のみに限定することでハイドレーションコストを最小化する。

- **Streaming SSRとSuspenseによる段階的レンダリング:** `loading.tsx`やSuspenseバウンダリーを活用したStreaming SSRで、重い処理を待たずに段階的にUIを表示。TTFBとFCPを改善し、ユーザー体験を向上させながら、SEOにも有利な構造を維持できる。

- **Route Handlers (API Routes)の型安全性とコロケーション:** `app/api/`配下のRoute Handlersで、Next.js特有のRequest/Response型を活用し、Zodなどでバリデーションを統合。ビジネスロジックはサーバーコンポーネント内で直接実行できるため、不要なAPI呼び出しを削減できる。

- **Parallel RoutesとIntercepting Routesによる高度なルーティング:** 同一画面内で複数のルートを並列表示（例: ダッシュボード+サイドバー）したり、モーダル表示のためにルートをインターセプトする設計が可能。これによりSPA的な体験を保ちながらURLベースのナビゲーションを実現できる。

- **Metadata APIとOG Image Generationの活用:** `generateMetadata()`とdynamic OG image生成(`@vercel/og`)を組み合わせ、各ページのSEO・SNSシェア最適化を自動化。静的・動的両対応でパフォーマンスを損なわずにメタデータ管理を一元化できる。

### 9. Vercel Edge Functions optimization 2026

Web検索の権限が必要です。現在の知識ベース（2025年1月まで）に基づいて、Vercel Edge Functionsの最適化に関する重要なポイントをお伝えします。

## Vercel Edge Functions最適化の重要ポイント（2026年）

- **コールドスタート時間の最小化:** Edge Functionsは軽量な依存関係と最小限のバンドルサイズを維持することが重要。不要なライブラリのインポートを避け、dynamic importで必要なコードのみをロードすることで、初回実行時のレイテンシを大幅に削減できます。

- **Edge Runtimeの制約を理解する:** Node.js APIの一部は使用不可（fs、child_processなど）。`@vercel/og`のような専用ライブラリを活用し、WebCrypto APIやFetch APIなどのWeb標準を優先することで、互換性とパフォーマンスを両立します。

- **適切なキャッシング戦略:** `Cache-Control`ヘッダーとVercelのEdge Cacheを組み合わせることで、レスポンス時間を劇的に改善。動的コンテンツでも`stale-while-revalidate`パターンを活用し、ユーザー体験とサーバー負荷のバランスを最適化できます。

- **地理的分散の活用:** Edge Functionsはグローバルに分散されているため、リージョン固有のロジックや地理情報に基づいたパーソナライゼーションを実装することで、ユーザーに最も近いエッジでコンテンツを生成し、レイテンシを最小化します。

- **モニタリングとデバッグ:** Vercel Analyticsと統合されたEdge Function metricsを活用し、実行時間、メモリ使用量、エラー率をリアルタイムで監視。本番環境での問題を早期に検出し、継続的な最適化サイクルを回すことが重要です。

### 10. TypeScript type safety patterns 2026

**CTO視点: TypeScript type safety patterns 2026**

- **Branded Typesによる実行時バリデーション統合:** Zodなどのスキーマバリデーションライブラリと組み合わせたBranded Types（`type UserId = string & { __brand: 'UserId' }`）が主流に。コンパイル時の型安全性と実行時のバリデーションを両立し、不正な値の混入を防ぐパターンが確立されています。

- **Template Literal Typesの実用化:** 文字列リテラル型をテンプレートで組み合わせる機能が成熟し、ルーティングパス（`/users/${UserId}`）やCSS変数名の型安全性を静的に保証。API設計やデザインシステムでの採用が加速しています。

- **const type parametersによる推論の最適化:** TypeScript 5.0以降の`const`型パラメータ（`<T extends string>(x: T)`）が広く採用され、過度な型の拡大を防止。ユーティリティ関数やビルダーパターンでの型推論が大幅に改善されました。

- **Satisfies operatorによる型アサーションの改善:** `as`による強制キャストを避け、`satisfies`演算子で型適合性を検証しながらリテラル型を保持。リファクタリング時の安全性とIDEの補完精度が向上し、チーム開発での型エラー検出が早期化しています。

- **Effect-TSなど型駆動エラーハンドリングの台頭:** 例外ではなく型システムでエラーを表現するEffect-TSやNeverThrowが普及。`Result<T, E>`型による明示的なエラーハンドリングで、実行時エラーの予測可能性とテスタビリティが大幅に向上しています。
