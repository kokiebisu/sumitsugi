# CTO Knowledge - 2026-06-19

## Daily Update (2026-06-19)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降で安定したPPRにより、静的シェルを即時表示しつつ動的部分のみストリーミングできるため、LCP/TTFBを大幅改善できる。`sumitsugi`の物件一覧・詳細ページのような「ヘッダーは静的・在庫情報は動的」という構成に特に有効。

- **Turbopack本番ビルドの標準化:** Next.js 16でTurbopackがビルドでも既定化され、Webpack比でビルド時間が大幅短縮。CI実行時間の短縮に直結するため、`bun run build`を含むCIパイプラインの待ち時間削減が見込める。

- **React Server Components + キャッシュ戦略の精緻化:** `use cache`ディレクティブやセグメント単位のキャッシュ制御が普及し、データフェッチ層（`src/lib/data.ts`相当）でのキャッシュ境界設計が性能の鍵になる。draft/public状態を持つ物件データのような「一部だけ動的」なデータには細粒度キャッシュが有効。

- **画像・フォント最適化のエッジ化:** `next/image`の自動フォーマット変換とCDNエッジでのオンデマンド最適化が一般化し、Airbnb風のリッチな物件写真UIでもCore Web Vitalsへの影響を抑えられる。

- **Bunランタイムとの組み合わせ最適化:** Bunのインストール・実行速度を活かしたNext.jsのdevサーバー起動・HMR高速化が進み、開発体験（DX）の改善が生産性に直結する領域として注目されている。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 16では静的シェルを即時返却しつつ動的部分のみストリーミングする手法が安定版となり、TTFBを大幅短縮しつつパーソナライズされたコンテンツも扱えるようになっています。sumitsugiの物件一覧・詳細ページでも、固定レイアウト部分を静的化しデータ取得部分のみSuspenseでストリーミングする構成が有効です。

- **Server Actionsとストリーミングの統合深化:** フォーム送信後のレスポンスをストリーミングしつつ楽観的UIを更新するパターンが一般化し、`useActionState`と組み合わせることで物件登録・引き継ぎ申請フローのようなマルチステップフォームのUXが改善できます。

- **キャッシュ戦略の細分化（`use cache`ディレクティブ）:** コンポーネント単位・関数単位でキャッシュ境界を明示的に制御できるようになり、価格や在庫など更新頻度が異なるデータを同一ページ内で適切な粒度でストリーミングできます。物件ステータス（draft/public）の切り替えに対するキャッシュ無効化設計が重要になります。

- **エッジランタイムでのRSCストリーミング普及:** Vercel EdgeやCloudflare Workers上でRSCペイロードをエッジから直接ストリーミングする構成が主流化し、地理的レイテンシ削減に寄与。ただしNode.js依存のライブラリ（PDF生成など）はエッジ非対応のため、ランタイム分離設計が必須です。

- **Suspenseバウンダリの粒度設計がパフォーマンスKPIに直結:** 過度に細かい境界はウォーターフォールを生み、粗すぎる境界はストリーミングの利点を失わせるため、Core Web Vitals（特にINP）を見ながら境界設計をプロファイリングする運用が定着しています。

### 3. API design REST GraphQL tRPC 2026

- **tRPCのエッジ統合が標準化:** Next.js 16のApp Router環境ではtRPC + React Server Componentsの組み合わせがデファクトとなり、型安全性をクライアント・サーバー間でビルド時に保証できるため、sumitsugiのような中規模Next.jsプロジェクトでは新規API追加時にtRPCを優先検討すべき。

- **GraphQLは「集約レイヤー」用途に縮小:** フロントエンド直結ではなく、複数マイクロサービスやサードパーティAPI（決済・本人確認など）を束ねるBFF層としての採用が主流になり、単一Next.jsモノリスである現状ではGraphQL導入の優先度は低い。

- **RESTはWebhook・公開APIの定番のまま:** 外部パートナー（不動産ポータル連携、決済プロバイダ）向けの公開APIはOpenAPI仕様付きRESTが依然標準で、tRPCのような型共有が効かない外部接続にはRESTを使い分けるハイブリッド戦略が現実的。

- **Zodスキーマの再利用がAPI設計の中心に:** 入力検証（Zod）をtRPCプロシージャ・REST両方で共有することで、`.claude/rules/standards.md`にもある「Zodスキーマでの境界検証」がAPI層全体の一貫性を担保する鍵になっている。

- **ストリーミングレスポンス（Server Actions/RSC）の普及:** 物件一覧や検索結果のような大量データ表示では、tRPCのsubscriptionやNext.jsのストリーミングSSRを使った段階的レンダリングがUX指標（LCP/TTFB）改善の主要トレンド。

### 4. serverless edge computing 2026

- **WASMランタイムの主流化:** V8 isolatesに加え、WasmエッジでのCold start短縮（数ms単位）が標準化されつつあり、Next.jsのEdge RuntimeでもWASI互換APIの採用が進む見込み。本プロジェクトのSSR/APIルートでも軽量関数のエッジ移行を検討する価値がある。

- **エッジでのステート管理:** Durable Objects/KVライクな分散ストレージがエッジ標準機能化し、リージョン跨ぎの強整合性をアプリ側で意識せず扱えるようになってきている。認証コンテキストや物件ステータスのキャッシュ層に応用余地あり。

- **コールドスタート対策の進化:** スナップショット起動（V8 snapshot, pre-warming pools）により99パーセンタイルのレイテンシが大幅改善、SLA保証付きのエッジ実行が一般的になっている。

- **エッジ×AI推論の融合:** 小型LLM/埋め込みモデルのエッジ推論が普及し、レコメンドや検索のレイテンシをデータセンター往復なしで実現できるようになっている。マッチング機能（IC consultation matching）の高速化に転用可能。

- **可観測性とコスト管理の課題:** 分散実行ゆえにトレーシング・ログ集約が複雑化し、エッジ特化のObservabilityツール（OpenTelemetry edge exporter等）への投資が必須になっている — コスト最適化とセットで運用チームの新たな課題。

### 5. authentication security best practices 2026

- **パスキー/WebAuthnのデフォルト化:** 2026年時点でパスワードレス認証(FIDO2/WebAuthn)が業界標準になりつつあり、フィッシング耐性のある公開鍵暗号方式により、パスワード+SMS OTPより圧倒的に高いセキュリティを実現できる。sumitsugiでも次の住人/前の住人の本人確認フローにパスキー対応を検討すべき。

- **多層防御としてのリスクベース認証:** デバイスフィンガープリント・IPレピュテーション・行動分析を組み合わせたアダプティブMFAが主流になり、ログイン時のコンテキスト(新規デバイス・地理的異常等)に応じて追加認証を動的に要求する設計が求められる。

- **セッショントークンのライフサイクル管理:** 短命なアクセストークン+リフレッシュトークンローテーション、httpOnly/secure/SameSite=Strict Cookieの徹底、サーバーサイドでの即時失効(ログアウト・パスワード変更時)が必須。`src/contexts/auth-context.tsx`周辺の実装で確認しておきたい。

- **認可とアクセス制御の分離(Zero Trust):** 認証(誰か)と認可(何ができるか)を明確に分離し、物件ステータス(`draft`/`public`)やオーナー権限のチェックをクライアント側だけでなくAPI/サーバー側で必ず再検証する設計が2026年のベストプラクティス。

- **サプライチェーン・依存パッケージの監査:** npm/Bunパッケージ経由の認証ライブラリ(NextAuth等)の脆弱性が増加傾向にあり、`bun audit`相当の定期スキャンとSBOM管理を開発フローに組み込むことが推奨される。

### 6. database architecture Prisma Supabase 2026

- **Prisma + Supabase Pooler構成:** Supabaseのpgbouncer経由接続では`directUrl`と`url`を分離し、マイグレーションはdirect connection、ランタイムはpooled connectionを使うのが必須パターン。これを怠るとサーバーレス環境で接続枯渇エラーが頻発する。

- **Row Level Security (RLS) とPrismaの責務分離:** SupabaseのRLSはDB層でアクセス制御を強制できるが、Prisma Clientは通常service_role経由で接続するためRLSをバイパスしがち。認可ロジックをアプリ層だけに依存せず、RLSポリシーを併用する二重防御が安全。

- **Prisma Accelerate / Edge対応:** Next.js 16のEdge RuntimeやServer Actionsから直接PostgreSQLに繋ぐのは相性が悪く、Prisma AccelerateやSupabaseのData APIを介したキャッシュ・コネクション管理が実質標準になっている。

- **マイグレーション運用:** `prisma migrate dev`をSupabase上で直接実行すると本番スキーマとのドリフトが起きやすいため、ステージング環境でのマイグレーション検証とshadow databaseの活用をCIに組み込むべき。

- **型安全性とスキーマ駆動開発:** Prismaのスキーマファイルを単一の真実源とし、Supabase側のRLSポリシーやトリガーもバージョン管理下のSQLマイグレーションとして同期させることで、住人データ（前の住人・次の住人の情報）のような機密性の高いデータ構造の整合性を保ちやすい。

### 7. WebAssembly Rust performance 2026

- **Component Model標準化の本格普及:** WASI Preview 2 / Component Modelが各ランタイム（wasmtime, wasmer）で安定し、Rust↔JS↔他言語間のインターフェース定義が型安全かつゼロコストで行えるようになっている。マイクロサービス的にWasmモジュールを組み合わせる設計が現実的な選択肢になっている。

- **エッジ・サーバーレスでの採用拡大:** Cloudflare Workers, Fastly Compute, Fermyon Spinなど、コールドスタートがミリ秒単位で済むRust+Wasmの実行環境が増え、Node.js/Next.jsのAPI Routesから計算集約的な処理（画像処理、PDF生成、価格計算ロジックなど）をWasmにオフロードするパターンが一般化している。

- **バイナリサイズとロード時間の最適化:** `wasm-opt`、`twiggy`、Rustの`wee_alloc`に代わる`talc`等のアロケータ選択により、ブラウザ実行時のWasmバイナリを数十KB単位まで削減できる。ただしツールチェインの設定次第で差が大きく、ベンチマークなしの導入は逆効果になりやすい。

- **SIMD・スレッド対応の安定化によるネイティブ級性能:** Wasm SIMD128とshared memory + Web Workersの組み合わせがV8/SpiderMonkeyで安定し、画像変換や検索インデックス構築といった計算負荷の高い処理でネイティブの80〜95%程度の性能が得られるケースが増えている。住宅物件の画像処理や検索機能で検討価値あり。

- **デバッグ・プロファイリング体験の向上:** DWARF対応のソースマップやChrome DevToolsのWasm統合が進み、以前は「ブラックボックス」だったRust→Wasmのデバッグが本番相当の体験に近づいている。導入コストの大きな障壁だった部分が下がっている点は意思決定材料になる。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** 静的シェルと動的コンテンツを1つのルートで共有できるPPRが安定版となり、初回表示速度を保ちながら個人化されたUIを配信しやすくなった。`loading.tsx`境界の設計次第でTTFBが大きく変わるため、Suspense境界の粒度設計が重要な技術判断になる。

- **Server Actions のキャッシュ戦略成熟:** `revalidateTag`/`revalidatePath`の使い分けに加え、Server Actions自体の冪等性・楽観的更新パターンが定着し、フォーム送信や予約フローでのレースコンディション対策がベストプラクティス化している。

- **キャッシュ層の明示化（`use cache`ディレクティブ):** Next.jsのデフォルトキャッシュ挙動が度々変更された反省から、`use cache`で明示的にキャッシュ境界を宣言する方向に進んでおり、不可視のキャッシュバグを防ぐために積極採用すべき。

- **RSCペイロード最適化とバンドル分離:** Client Componentの境界を最小化し、`'use client'`の伝播範囲を意識した設計（leaf componentに限定）が、初期JS転送量とハイドレーションコストを左右する主要なパフォーマンス指標になっている。

- **Edge/Node runtimeの使い分けの再定義:** 認証・決済など機密処理はNode runtime、軽量な読み取り系APIはEdge runtimeという分離が一般化し、ミドルウェアの肥大化を避けるためルートグループ単位でruntimeを明示指定する設計が推奨されている。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化:** Edge RuntimeはNode.js Runtimeに比べて起動が高速だが、依存パッケージのバンドルサイズが大きいと初回応答が遅れるため、`unstable_allowDynamic`や軽量ライブラリへの置き換えでバンドルを1MB以下に抑えるのが実用的な目安。

- **データフェッチの地理的局所性:** Edge Functionsの真価はユーザーに近いリージョンで実行できることだが、バックエンドDBやAPIが単一リージョンにある場合はレイテンシが逆に悪化するため、Vercel Postgres/PlanetScaleなどのエッジ対応データストアやRegional Edge Cachingと組み合わせる設計が必須。

- **Streaming SSRとの併用:** Next.js 16のPartial PrerenderingとEdge Functionsを組み合わせることで、静的シェルを即時返却しつつ動的部分をストリーミングできるため、TTFBを大幅に改善できる。sumitsugiの物件詳細ページのような動的データを含むページに有効。

- **実行時間とコストの監視:** Edge Functionsは実行時間課金のため、ループ処理や外部API待機が長いコードを置くとコストが跳ねやすく、重い処理はBackground FunctionsやQueueに分離してEdgeは認証チェック・リダイレクト・A/Bテスト判定など軽量ロジックに限定するのがベストプラクティス。

- **Observabilityの強化:** 2026年時点でVercelのEdge Observabilityはトレース粒度が向上しており、`waitUntil()`を使った非同期ログ送出とOpenTelemetry連携で、エッジ特有のリトライ・タイムアウト挙動を可視化できるようになっている点が運用上の大きな改善点。

### 10. TypeScript type safety patterns 2026

- **型レベルプログラミングの実用化:** TypeScript 5.x系のconst type parametersやtemplate literal typesを活用し、API契約やルーティング定義をコンパイル時に検証する設計が標準化してきている。Zodなどのスキーマライブラリと組み合わせ、ランタイム検証と型推論を一体化させる「Parse, don't validate」パターンが定着している。

- **`any`排除よりも`unknown`起点の設計:** strictモード前提で外部入力は必ず`unknown`として受け取り、Zod/Valibotでパースしてから型を確定させるフローが主流。`as`によるキャストを極力減らし、型ガード関数で安全に絞り込む実装が品質指標として重視されている。

- **Branded Types / Nominal Typingの普及:** `UserId`と`ProductId`のような構造的に同一だが意味の異なるstring型を、ブランド付き型で区別し、誤代入をコンパイル時に防ぐパターンがドメインモデルの定番になっている。本プロジェクトでも`listingId`や`sellerId`のような識別子に適用余地がある。

- **末尾のexhaustiveness check:** union型（例: 物件ステータスの`'draft' | 'public'`）を扱うswitch文の末尾に`never`型を使った網羅性チェックを必須化し、新しいステータス追加時にコンパイルエラーで漏れを検知する運用がベストプラクティスとして広がっている。standards.mdにある「union型変更時は全箇所grep」をさらに型システムで強制できる。

- **型とテストの境界線の再定義:** 型安全性が高度化したことで「型で保証できることは単体テストで重複検証しない」という分業が進み、TDDのテストは挙動・副作用の検証に集中し、型はビルド時の静的検証に専念させる切り分けが2026年のチーム標準になっている。
