# CTO Knowledge - 2026-10-09

## Daily Update (2026-10-09)

### 1. Next.js performance optimization 2026

- **ポイント1:** Partial Prerendering（PPR）が安定版となり、静的シェルと動的コンテンツを1つのルートで混在させられるため、TTFBを維持しつつパーソナライズされたコンテンツを配信できる。
- **ポイント2:** Turbopackがビルド・開発両方のデフォルトバンドラーとして定着し、大規模モノレポでもHMRとプロダクションビルドが大幅に高速化されている。
- **ポイント3:** React Server Components中心の設計が進み、クライアントバンドルを最小化するために「use client」境界を末端コンポーネントに限定する設計パターンが定石化している。
- **ポイント4:** `next/image`や`next/font`に加え、Cache Components（`use cache`ディレクティブ）によるきめ細かいキャッシュ制御が普及し、データ取得レイヤーでの過剰な再フェッチを防げる。
- **ポイント5:** Core Web Vitals計測がINP中心に移行したため、サーバーアクションの多用やハイドレーション戦略（selective hydration）を見直し、インタラクション遅延を減らす実装が重要になっている。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** Next.js 16ではSuspense境界ごとのストリーミングがデフォルト挙動となり、初回ペイロードを最小化しつつTTFBを改善できる。ページ全体を待たずに骨格→データの順でレンダリングする設計が基本パターンになっている。

- **Partial Prerendering (PPR) の実用化:** 静的シェルを事前生成し、動的部分だけをストリーミングで差し込むアプローチが安定運用レベルに達し、CDNキャッシュとパーソナライズを両立できる。物件一覧ページのような「共通UI+個別データ」構成に相性が良い。

- **RSCペイロードのネットワークコスト管理:** サーバーコンポーネントのツリーをクライアントに送る際のシリアライズサイズが肥大化しやすく、`use client`境界の切り方次第でストリーミングの恩恵が相殺される。コンポーネント粒度の設計レビューが性能チューニングの主戦場になっている。

- **エラーバウンダリとストリーミングの組み合わせ:** ストリーミング中に発生した例外をSuspenseの外側にリークさせないよう、境界ごとに`error.tsx`を配置する設計が重要。一部だけ失敗しても他のセクションは表示を継続できるグレースフルデグラデーションが求められる。

- **キャッシュ戦略との統合:** `fetch`のリクエストメモ化とストリーミングを組み合わせることで、同一リクエスト内の重複フェッチを避けつつ段階的にUIを出せるようになったが、キャッシュの再検証タイミングを誤るとストリーミングの体感速度向上が台無しになる点は要注意。

### 3. API design REST GraphQL tRPC 2026

- **統一レイヤーとしてのtRPC定着:** フルスタックTypeScript環境ではtRPCがスキーマ共有とエンドツーエンド型安全性を提供し、REST/GraphQLの境界レイヤーを代替する選択肢として採用が進んでいる。

- **GraphQLはBFF/集約用途に限定:** 複数クライアントや複雑な関連データ取得が必要な場合に限りGraphQLを採用し、シンプルなCRUD主体のサービスはRESTまたはtRPCで十分という「用途別選定」が主流になっている。

- **Zodスキーマ駆動によるランタイム検証の標準化:** API境界でのバリデーションはZodなどのスキーマライブラリで型定義と検証ロジックを一元化し、OpenAPI/GraphQLスキーマも自動生成する流れが加速している（本プロジェクトでも標準に準拠）。

- **エッジ/サーバーレス環境でのレイテンシ最適化:** Next.js App RouterのServer ActionsやRoute Handlersが軽量なAPI代替として普及し、従来のREST APIレイヤーを薄くする、もしくは完全に省略する設計が増えている。

- **AIエージェント連携を見据えたAPI設計:** LLMエージェントやMCPツール呼び出しを前提に、人間向けAPIとAIエージェント向けAPI（構造化出力・ツール定義）を分離して設計する必要性が高まっている。

### 4. serverless edge computing 2026

**サーバーレス/エッジコンピューティング 2026年のトレンド**

- **ポイント1: V8 Isolateベースの実行環境の標準化:** Cloudflare WorkersやDeno Deployに代表されるV8 Isolate方式が、コールドスタート数msという特性からコンテナベースのサーバーレスを置き換えつつある。sumitsugiのような地域密着型サービスでも、物件検索APIのレイテンシ改善にエッジでのレスポンスキャッシュ戦略が効果的。

- **ポイント2: エッジでのAI推論（Edge Inference）の普及:** 軽量LLM・embeddingモデルをエッジ側で実行し、ユーザーの近くで推論を完結させる構成が増えている。検索レコメンドやチャット応答のような低レイテンシ要求機能は、中央API呼び出しよりエッジ推論の方がUX面で優位。

- **ポイント3: Next.js 16とエッジランタイムの統合深化:** App RouterのEdge RuntimeがNode.js APIとの互換性を広げ、認証チェックやミドルウェアロジックをエッジで実行しやすくなった。ただしDB接続（Prisma等）はエッジ非対応のものが多く、データアクセス層の設計次第でエッジ化できる範囲が制限される点は要注意。

- **ポイント4: コールドスタート問題の実質的解消とコスト構造の変化:** 2026年時点でエッジ実行環境のコールドスタートはほぼ無視できるレベルになり、常時起動サーバーより従量課金のエッジ関数がコスト効率で優位になるケースが増加。トラフィックが不均一なMVPフェーズのプロダクトには特に適している。

- **ポイント5: マルチリージョンデータ整合性の複雑化:** エッジでの書き込み処理が増えるほど、グローバルなデータ一貫性（強一致vs結果整合性）の設計判断が重要になる。日本国内向けサービスであれば単一リージョン+エッジキャッシュの構成で十分なケースが多く、過剰なグローバル分散は避けるべき。

### 5. authentication security best practices 2026

- **パスキー/WebAuthnへの全面移行:** パスワードレス認証（FIDO2/WebAuthn）がデフォルトとなり、フィッシング耐性のある生体認証・デバイス認証がSMS OTPやメール認証を置き換えつつある。実装コストも下がっており、新規プロダクトは最初からパスキー対応で設計すべき。

- **トークンの短命化とバインディング:** アクセストークンの有効期限を短くし、デバイス/セッションにバインドする（DPoPやmTLS等）ことで、トークン漏洩時の被害を最小化する流れが主流。長期JWTをlocalStorageに保存する実装は2026年基準では脆弱と見なされる。

- **リスクベース・継続的認証:** ログイン時の一度きりの認証から、行動パターン・デバイス情報・IPなどを継続的に評価してリアルタイムでリスクスコアリングする方式へ移行している。異常検知時に再認証を要求するアダプティブMFAが標準装備になりつつある。

- **サプライチェーン・サードパーティ認証の監査強化:** OAuthアプリの過剰権限スコープやSSOプロバイダの設定ミスが侵害の主要経路となっており、認可フローのPKCE必須化やスコープの最小化、定期的な連携アプリの棚卸しが重要視されている。

- **セッションハイジャック対策の高度化:** Cookie窃取やセッション再利用を防ぐため、デバイスフィンガープリンティングとセッション固定化対策（IPやUser-Agent変化時の再認証）を組み合わせる実装が増えており、特にヘルプデスク等のソーシャルエンジニアリング経由の侵害対策として注目されている。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** PrismaはSupabaseの接続プーリング（PgBouncer/Supavisor）との相性問題が長年の課題だったが、2025年以降のPrisma Accelerate統合でサーバーレス環境でのコネクション管理が大幅に改善されており、Edge Functionsとの組み合わせでも安定運用できる。
- **ポイント2:** Supabaseのポイントインタイムリカバリとブランチング機能（開発用DBの一時分岐）はステージング環境の構築コストを下げるが、Prismaのマイグレーション履歴とSupabase CLIのマイグレーションを二重管理しないよう、どちらか一方に統一する運用ルールが必須。
- **ポイント3:** Row Level Security（RLS）はSupabaseの強みだが、PrismaはORMレイヤーでRLSを認識しないため、物件ステータス（`draft`/`public`）のような権限制御はRLSポリシー側で必ず二重化し、アプリ層の条件分岐だけに依存しない設計が安全。
- **ポイント4:** Prismaのクエリ最適化（`select`での必要カラム限定、N+1回避のための`include`設計）は、本サービスの物件一覧・検索のようなリスト表示画面でのレスポンス速度に直結するため、β版ローンチ前にスロークエリのプロファイリングを一度実施すべき。
- **ポイント5:** スキーマ変更時はPrisma側のユニオン型（`seller`等の内部用語フィールド）とSupabase側のDB制約（CHECK制約やenum型）を同期させる必要があり、型の不整合がビルドを通過してしまうケースがあるため、マイグレーションPRには必ずDB制約側の変更も含めるレビュー基準を設けるとよい。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Component Model（WASI Preview 2）の標準化が進み、Rustの`cargo component`ツールチェーンで言語間インターフェースの記述が簡素化され、マイクロサービス的なWasmモジュール連携が実用レベルに達している。
- **ポイント2:** `wasm-opt`やLLVMのSIMD128最適化が成熟し、Rust→Wasmのホットパス処理ではネイティブコードの80〜90%程度の実行速度に近づいており、画像処理・暗号化などCPU負荷の高い処理のブラウザ/エッジ実行に向く。
- **ポイント3:** WasmGC提案の実装が進展し、RustのようなlinearメモリAOT言語でもGC連携オーバーヘッドが減少、JS/TSとのインターオペが以前より軽量になっている（ただしRust自体はGC不要なため恩恵は主に相互運用側）。
- **ポイント4:** CloudflareやFastlyなどエッジランタイムでのWasmコールドスタートが1ms未満まで短縮され、Rust製WasmはサーバーレスAPIの低レイテンシ処理に適した選択肢として定着してきている。
- **ポイント5:** `wasm-pack`やViteのWasmプラグインとの統合が安定し、フロントエンドビルドパイプラインへのRust/Wasm組み込みコストが下がったため、画像処理や検証ロジックの一部をクライアント側Wasmにオフロードする設計判断がしやすくなっている。

### 8. Next.js App Router patterns 2026

- **ポイント1（Server Actions中心の設計）:** フォーム送信やミューテーションは`"use server"`のServer Actionsを第一選択とし、APIルートは外部連携や細かい制御が必要な場合に限定する流れが定着している。sumitsugiでも物件登録・引越しフローなど多ステップの入力はServer Actions+Zodのバリデーションで実装するのが安全かつ高速。

- **ポイント2（Partial Prerendering / キャッシュ戦略の明確化）:** 静的部分とパーソナライズ部分を同一ページ内で分離してストリーミングするPartial Prerenderingが実用段階に入り、`fetch`のキャッシュオプション（`force-cache`/`no-store`/`revalidate`）を明示的に書く規約が重要になっている。物件一覧ページなど「全体は静的、価格・空室状況だけ動的」という構成に向いている。

- **ポイント3（Server Components優先、Client Componentsは境界を薄く）:** `"use client"`境界を末端のインタラクティブ部分（フォーム入力、モーダル操作など）に限定し、データ取得・レイアウトはServer Componentsに留める設計がベストプラクティスとして固まっている。バンドルサイズとTTIの観点で、認証コンテキストなど重いロジックをクライアント側に広げすぎない注意が必要。

- **ポイント4（並行データ取得とSuspenseの組み合わせ）:** ネストしたレイアウト/ページで`Promise.all`やSuspenseバウンダリを使った並行フェッチが標準化し、ウォーターフォール問題を避ける設計がレビュー観点として定番化している。物件詳細ページ（物件情報・前の住人情報・引越し費用計算を並行取得）のような画面で特に効果が大きい。

- **ポイント5（型安全なルーティングとミドルウェアの軽量化）:** App Routerの型付きルート（typed routes）がデフォルト推奨になりつつあり、`middleware.ts`は認証チェックなど最小限の処理に留めて、重い処理はエッジではなくServer Components/Actions側に移す設計が推奨されている。Next.js 16ではミドルウェアの実行コストがそのままレイテンシに直結するため、特に注意が必要。

### 9. Vercel Edge Functions optimization 2026

## CTO視点: Vercel Edge Functions optimization 2026

- **ポイント1（Fluid Computeの活用）:** 2024年末に導入されたFluid Computeモデルが本格的に主流化し、同一インスタンス内で複数リクエストを並行処理できるようになった。コールドスタート頻度と実行コストを大幅に削減できるため、APIルートやミドルウェアの課金最適化には必須の設定。

- **ポイント2（Partial Prerendering + Edgeの組み合わせ）:** Next.js 16のPPR（Partial Prerendering）とEdge Functionsを組み合わせることで、静的シェルを即時配信しつつ動的部分だけEdgeでストリーミングできる。物件一覧ページのような「一部は静的、一部はユーザー依存」な画面で特に効果が高い。

- **ポイント3（バンドルサイズとランタイム選定の見直し）:** Edge Runtime実行環境でNode.js APIの互換性がかなり進んだため、「Edgeで動かせるか」より「本当にEdgeで動かすべきか」の判断が重要になった。認証チェックやリダイレクトなど軽量処理はEdge、重い処理やDB接続が多い処理はNode.jsランタイムに残す切り分けが基本方針。

- **ポイント4（リージョン配置とデータ局所性）:** Edge Functionsのリージョン自動選択に加えて、DB（例: Supabase/Postgres）との物理的距離がレイテンシを支配するケースが増えている。Edgeで処理を速くしても、DBが遠いリージョンだと効果が相殺されるため、データ層のリージョン戦略とセットで最適化する必要がある。

- **ポイント5（Observabilityコスト管理）:** OpenTelemetry連携によるEdge関数のトレーシングが標準化されつつあるが、トレース量自体が課金対象になりやすい。本番環境ではサンプリングレートを明示的に制御し、必要なパス（決済・認証系）だけ100%トレースする設定が実用的。

### 10. TypeScript type safety patterns 2026

## TypeScript Type Safety Patterns 2026

- **ポイント1: 型推論ファーストの設計** TypeScript 5.x系の`satisfies`演算子やconst型パラメータが定着し、明示的な型アノテーションより推論に委ねる設計が主流に。これにより型定義の重複が減り、リファクタリング時の型不整合を早期検出できる。

- **ポイント2: スキーマ駆動のランタイム検証** Zodのようなライブラリで「型定義とランタイム検証の一元化」が標準パターンとなり、APIレスポンスやフォーム入力など境界部分での`z.infer`による型生成が必須プラクティスに。CLAUDE.mdの標準でも「システム境界でZodスキーマを使う」と明記されている通り、コンパイル時の型安全とランタイムの実データ不一致を防ぐ唯一の方法。

- **ポイント3: Discriminated UnionとExhaustiveness Check** `'draft' | 'public'`のようなUnion型に対し、switch文で`never`型を使った網羅性チェックを徹底することで、新しいステータス追加時にコンパイルエラーで漏れを検知できる。sumitsugiの物件ステータス管理のような小さなUnion型でも、将来の値追加を見据えて早期にこのパターンを導入する価値がある。

- **ポイント4: テンプレートリテラル型によるID/パスの型安全化** ルーティングパスやCSS変数名など文字列ベースの値にテンプレートリテラル型を適用し、タイポによるバグをコンパイル時に排除する動きが加速。Next.js App Routerのような規約ベースのルーティングとの組み合わせで特に効果が高い。

- **ポイント5: 型レベルテストの一般化** `expectTypeOf`（Vitest統合）などを使い、ユニットテストと同じワークフローで型そのものをテストする手法が普及。複雑なジェネリクスやユーティリティ型を持つプロジェクトでは、ロジックのテストだけでなく型定義自体の回帰テストが品質保証の一部になっている。
