# CTO Knowledge - 2026-11-12

## Daily Update (2026-11-12)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16ではPPRが安定版となり、静的シェルと動的コンテンツを1ページ内で混在させつつ初期表示を高速化できる。物件一覧ページのような「検索条件は動的・レイアウトは静的」な構成に特に有効。

- **React Server Components の活用深化:** データ取得をサーバー側に寄せることでクライアントバンドルサイズを削減でき、物件詳細ページの画像ギャラリーなどインタラクティブ要素のみをClient Componentに限定する設計が標準化してきている。

- **Turbopack本番ビルドの定着:** `bun run build`の高速化に直結し、CI/CDのフィードバックループを短縮できる。大規模な画像アセット（物件写真）を扱うプロジェクトではビルド時間の差が顕著に出やすい。

- **next/image とCDNキャッシュ戦略の最適化:** 物件写真のような画像中心のUXでは、`sizes`属性の適切な指定とISR(Incremental Static Regeneration)の組み合わせがLCP改善の鍵。Airbnb風UIのカード一覧ではlazy loadingの優先度制御（`priority`props）も重要。

- **Edge Runtimeの選択的採用:** 認証チェックなど軽量なミドルウェア処理はEdge Runtimeに寄せ、重いDB処理はNode.js Runtimeに残すハイブリッド構成が、TTFB改善とレイテンシ削減の実用的なバランス点として定着している。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPartial Prerendering（PPR）とRSC streamingが標準的な組み合わせとなり、静的シェルを即座に返しつつ動的部分（物件の空室状況や価格など）だけをSuspense境界でストリーミングすることで、TTFBとLCPを両立できる。sumitsugiの`properties/`一覧ページのような動的データを含むページで特に効果が大きい。
- **ポイント2:** `use cache`ディレクティブとRSCストリーミングの併用がベストプラクティス化しており、物件データのような頻繁には変わらないがリアルタイム性も欲しいデータに対して、キャッシュ粒度を細かく制御しながらストリーミングできる。データ層（`src/lib/data.ts`）のキャッシュ戦略を見直す価値がある。
- **ポイント3:** Server Actionsとストリーミングの組み合わせで、フォーム送信後のUI更新（例: 内見予約フォーム）をクライアントJSなしで段階的に反映できるようになり、バンドルサイズ削減とインタラクション速度向上を同時に実現できる。
- **ポイント4:** ストリーミングSSR環境でのエラーバウンダリ設計が重要度を増している — Suspense境界内で例外が起きた際に全体がブロックされないよう、コンポーネント単位で`error.tsx`相当の粒度のフォールバックを用意する必要がある。
- **ポイント5:** E2Eテスト（Playwright）側でストリーミングのタイミング依存のテストが不安定化しやすいため、`waitForLoadState('networkidle')`に頼らず、Suspenseのフォールバック要素が消えることを明示的に待つテスト設計への移行が2026年のトレンド。

### 3. API design REST GraphQL tRPC 2026

- **tRPCのエッジ化が進展:** Next.js 16のApp Router + Server Actionsとの統合が成熟し、型安全なエンドツーエンド通信がtRPCなしでも実現しやすくなった。sumitsugiのようなNext.js単一リポ構成では、tRPCよりもServer Actions + Zodの組み合わせがオーバーヘッド少なく実用的。

- **GraphQLは"内部BFF"用途に収束:** 複数クライアント（Web/モバイル/パートナーAPI）を持つ組織ではGraphQLが残るが、単一フロントエンドのプロダクトではオーバーエンジニアリングになりがち。現状の物件情報・引き継ぎフローのような単純なCRUD中心のドメインではRESTまたはServer Actionsで十分。

- **OpenAPI生成の自動化が標準化:** Zodスキーマからの型・ドキュメント自動生成（zod-to-openapi等）が定着し、入力検証とAPI仕様書の同期コストが大幅に下がった。既存の「Zodで境界検証」というプロジェクト方針とも相性が良く、外部連携（決済・弁護士確認フロー等）が必要になった際に導入価値が高い。

- **Streaming/Suspenseファーストの設計:** React Server ComponentsとStreaming SSRの普及で、APIレイヤーも「一括レスポンス」から「段階的ストリーミング」への設計シフトが起きている。物件一覧や検索結果のような体感速度が重要な画面では、API設計時点でストリーミング対応を意識すべき。

- **認証・レート制限はAPI Gateway層に委譲する潮流:** 個別エンドポイントでの認可ロジック実装よりも、Edge Middleware/Gatewayでの集中管理が主流になりつつある。ベータローンチ前の今、認証・CSRF対策をミドルウェア層に集約しておくと将来のスケール（決済連携等）に備えやすい。

### 4. serverless edge computing 2026

- **コールドスタート問題の実質的解消:** V8 isolateベースのランタイム（Cloudflare Workers、Deno Deploy等）が標準化し、起動遅延がミリ秒単位まで縮小。従来はLambdaのコールドスタートを恐れて避けていたレイテンシクリティカルな処理も、エッジ関数に移行しやすくなった。

- **ステートフルエッジの普及:** Durable Objects / Workers KVのようなエッジネイティブなストレージが成熟し、グローバル分散のまま強整合性のある状態管理が可能に。物件検索や引越しスケジュールのような地理分散ユーザー向け機能で、DBラウンドトリップを減らせるのが実用的なメリット。

- **AI推論のエッジシフト:** 小型LLM・量子化モデルのエッジ実行が現実的になり、画像認識やレコメンドのような軽量AI処理をオリジンサーバーやAPI呼び出しなしで完結できるケースが増えた。レイテンシとコストの両方を削減できるが、モデルサイズとエッジのリソース制約のトレードオフは依然残る。

- **Next.js 16とエッジランタイムの統合深化:** App RouterのエッジミドルウェアやPartial Prerenderingがエッジ実行を前提に設計されており、サーバーレス/エッジのハイブリッド構成がデフォルト選択になりつつある。弊社のようなVercel/Next.jsスタックでは、追加のインフラ投資なしにグローバル配信の恩恵を受けやすい。

- **運用コストの逆転現象に注意:** エッジは「常時起動なし＝安い」という前提が崩れつつあり、呼び出し頻度が高いワークロードではエッジの従量課金が従来型サーバーより高くつくケースが報告されている。採用前にトラフィックパターンに応じたコスト比較が必須。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** 2026年現在、パスワードレス認証(WebAuthn/パスキー)がデフォルト選択肢になっており、フィッシング耐性とUX向上を両立できるため、新規実装では最初からパスキーを第一選択肢にすべきです。

- **多層防御としてのリスクベース認証:** デバイスフィンガープリント・行動分析・地理情報を組み合わせたアダプティブ認証で、固定MFAより高い検知精度とユーザー体験の両立が可能になっています。

- **トークン管理の厳格化:** 短命アクセストークン＋リフレッシュトークンローテーション、JWTのaudience/issuer検証の徹底が必須で、トークン漏洩時の被害範囲を最小化します。

- **認証基盤のサプライチェーンリスク管理:** Auth0やClerkなどのIDaaSを利用する場合でも、依存ライブラリの脆弱性監視とSBOM管理を行い、認証周りのサードパーティリスクを定常的に評価する体制が求められます。

- **ゼロトラスト的セッション管理:** セッション固定攻撃対策として、権限変更時(パスワード変更・MFA設定変更等)に既存セッションを即時無効化する仕組みを組み込むことが、2026年のベストプラクティスとして定着しています。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はSupabaseのPgBouncer（トランザクションプーリング）との相性が改善され、`directUrl`と`url`を分離する接続設定がデフォルト推奨になっている。サーバーレス環境（Vercel Edge等）でのコネクション枯渇を防ぐため、本プロジェクトでもPrisma AccelerateかSupabaseのPooler経由接続を必須にすべき。

- **ポイント2:** SupabaseのRow Level Security（RLS）とPrismaのアプリケーション層権限制御は責務が重複しやすく、「前の住人／次の住人」間の物件データアクセス制御のような機微な認可ロジックはRLSに一本化し、Prisma側はビジネスロジックのみに専念させる設計が2026年のベストプラクティス。

- **ポイント3:** PrismaのTypedSQLやSupabaseのRealtime機能を併用する場合、スキーマのソースオブトゥルースをPrisma Migrateに統一し、Supabase管理画面から直接スキーマを変更しない運用ルールが重要（ドリフト防止）。

- **ポイント4:** `draft`/`public`のようなステータス列を持つテーブルでは、Supabaseのパーティショニングやインデックス戦略よりも、まずPrismaスキーマ上のenum/union型とRLSポリシーの整合性をCIで検証する仕組み（型チェック＋ポリシーテスト）を優先すべき。少数物件規模のMVPでは過度な最適化は不要。

- **ポイント5:** PrismaのJSONフィールド型とSupabaseのpgvector拡張を組み合わせることで、将来的な物件レコメンド（類似物件検索）機能を低コストで追加できる余地があるが、現フェーズ（ベータローンチ準備）では法務確認が優先であり、着手は次フェーズ以降が妥当。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASI 0.3の普及により、Component Modelベースの言語間連携が実用段階に入り、RustのWASMバイナリを他言語（Go, JS, Python）から呼び出すオーバーヘッドが大幅に削減されている。sumitsugiのような画像処理やPDF生成の重い処理をRust+WASMに切り出す選択肢が現実的になってきている。

- **ポイント2:** `wasm-opt`や`twiggy`によるバイナリサイズ最適化が成熟し、Rust製WASMモジュールが数十KB〜数百KB規模まで小型化できるようになった。Next.jsのエッジランタイム（Vercel Edge/Cloudflare Workers）でコールドスタートを気にせず使えるレベルに達している。

- **ポイント3:** SIMD対応とマルチスレッド（SharedArrayBuffer経由）がブラウザ全般で標準化され、画像のリサイズ・透かし処理・PDFレンダリングなど計算集約的なクライアントサイド処理でネイティブの70-90%程度の速度が出せるようになった。物件写真の一括加工機能を検討する際の技術的選択肢として有力。

- **ポイント4:** `wasm-bindgen`と`wasm-pack`のツールチェーンが安定し、TypeScript型定義の自動生成品質が向上したため、Rust側のロジック変更がフロントエンドの型安全性を破壊するリスクが下がっている。TDD必須のsumitsugiの開発フローとも相性が良い。

- **ポイント5:** サーバーサイドではWasmtimeやwasmCloudを使ったRustマイクロサービスのサンドボックス実行が、Node.jsプロセスより起動が速く隔離性も高いため、信頼できない処理（ユーザーアップロードファイルの変換等）をセキュアに実行する用途で採用が増えている。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 16ではPPRがデフォルト挙動に近づき、静的シェルを即時返しつつ動的部分をストリーミングできる。弊サービスの物件一覧・詳細ページのようにSEOと動的データ（在庫状況等）が混在するページで、TTFBを大きく改善できる。

- **`use cache` ディレクティブによる明示的キャッシュ制御:** fetchの暗黙キャッシュから、関数・コンポーネント単位で`use cache`を明示する方式に移行している。キャッシュの意図がコードに残るため、`src/lib/data.ts`のようなデータ取得層でのキャッシュバグ（古い物件情報の表示等）を防ぎやすい。

- **Server Actions のセキュリティ強化が必須:** Server Actionsは事実上の公開APIエンドポイントなので、認証チェック・Zodによる入力検証・CSRF対策を各actionに必ず実装する必要がある。`auth-context.tsx`と連携したミドルウェアでの認可チェックを徹底すべき。

- **`after()` APIによるレスポンス後処理:** レスポンス返却後にログ記録や通知送信などの副作用を実行できる`after()`が定着してきており、ユーザー体感速度を落とさずに分析イベント送信や引越しフローの通知処理を行える。

- **Turbopackのビルド標準化:** Turbopackが本番ビルドでも安定し、デフォルト化が進んでいる。ビルド時間短縮によりCIでの`bun run build`検証サイクルが速くなり、型エラー検出のフィードバックループが短縮される。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約最適化:** Vercel Edge FunctionsはV8 isolateベースで実行されるため、Node.js APIに依存しないコードを書くことがパフォーマンスの鍵。bundle sizeを1MB以下に抑えることで、コールドスタートをほぼゼロに近づけられる。

- **ストリーミングレスポンスの活用:** 2026年時点では、Edge FunctionsでのストリーミングSSR（React Server Components含む）がデフォルトパターン化しており、TTFB（Time To First Byte）を大幅短縮できる。sumitsugiのような物件一覧ページでは、画像メタデータ取得前にレイアウトを先行送出する設計が有効。

- **リージョン配置の戦略的選定:** Edge Functionsは全世界のPoPで実行されるが、データベース（例: Postgres）が特定リージョンに固定されている場合、`regions`設定を明示的にDB近傍に絞ることでレイテンシが大幅改善する。グローバル配信とDB近接性のトレードオフを都度評価すべき。

- **キャッシュ戦略とISRの併用:** Edge Middlewareでの認証・リダイレクト処理と、ISR（Incremental Static Regeneration）によるページキャッシュを組み合わせることで、動的要件（ログイン状態など）と静的配信の高速性を両立できる。`src/app`のpropertiesページのような一覧系は好適候補。

- **Observabilityコストの見落とし注意:** Edge Functionsは実行時間課金・リクエスト課金モデルのため、ログ出力やモニタリング呼び出しが増えるほどコストに直結する。`console.log`禁止ルール（本プロジェクトのコーディング規約）はコスト面でも合理的で、構造化ログは必要最小限のサンプリングで運用すべき。

### 10. TypeScript type safety patterns 2026

- **型推論優先の設計:** TypeScript 5.x以降では`satisfies`演算子とconst型パラメータ（`const T`）を活用し、明示的な型注釈を減らしつつ型の厳密性を保つパターンが主流。過度な型注釈は保守コストを上げるため、推論に任せられる箇所は積極的に任せるべき。

- **スキーマ駆動のランタイム検証:** Zodなど（当プロジェクトでも採用）でスキーマを単一の真実源とし、`z.infer`で型を自動生成することで「型は合っているが実データは違う」というギャップを防ぐ。システム境界（API、フォーム入力）では静的型だけでは不十分。

- **Branded Types / Nominal Typingの普及:** `UserId`と`PropertyId`のような構造的に同じstring型を誤って混用するバグを防ぐため、brandingパターン（`type UserId = string & { __brand: 'UserId' }`）が実務で定着してきている。IDが多いドメインモデルほど効果が大きい。

- **Discriminated Unionによる状態管理の徹底:** 本プロジェクトの`'draft' | 'public'`のようなステータス管理は、オプショナルプロパティの組み合わせではなく判別可能なUnion型で表現し、網羅性チェック（`never`を使ったexhaustiveness check）をコンパイル時に強制するのが2026年のベストプラクティス。

- **型とテストの役割分担の明確化:** 型システムは「あり得ない状態を表現不可能にする」ことに専念し、ビジネスロジックの正しさはテスト（TDD）で保証するという分業が成熟してきた。型だけで全てを守ろうとすると過剰に複雑な型定義（型レベルプログラミング）に陥りやすく、可読性を損なう。
