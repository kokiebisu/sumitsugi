# CTO Knowledge - 2026-10-19

## Daily Update (2026-10-19)

### 1. Next.js performance optimization 2026

- **部分プリレンダリング (PPR) の本格運用:** Next.js 16ではPartial Prerenderingが安定版となり、静的シェルを即時配信しつつ動的部分だけをストリーミングできるため、TTFBとLCPを同時に改善できます。sumitsugiの物件一覧ページのような「静的な外枠＋動的な検索結果」構成に特に有効です。

- **React Server Components前提のデータフェッチ最適化:** サーバー側でのデータ取得をコンポーネント単位に分散させ、`use cache` ディレクティブやタグベースのキャッシュ無効化を組み合わせることで、クライアントへのJS転送量を最小化しつつ常に最新データを保てます。

- **Turbopackによるビルド・HMR高速化:** Turbopackがデフォルトビルドツールとして定着し、大規模コードベースでもコールドスタート・差分ビルドが数秒単位で完了するため、CI時間の短縮と開発体験の向上が同時に得られます。

- **画像・フォントの自動最適化とCore Web Vitals計測の標準化:** `next/image`のAVIF優先配信や、Vercel Speed Insights等との統合によるフィールドデータ計測が標準化され、INP（Interaction to Next Paint）の継続監視がSEO・CVR両面で必須になっています。

- **Edge RuntimeとISRのハイブリッド配置戦略:** 認証判定や地域別表示などの軽量ロジックをEdgeで実行し、重いレンダリングはISRでオリジン側に委ねることで、グローバルなレイテンシとサーバーコストのバランスを最適化する設計が主流になっています。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPPR（Partial Prerendering）がデフォルト前提の設計になり、静的シェルを即時配信しつつ動的部分だけをストリーミングで差し込む構成が標準化されています。sumitsugiの`properties/`一覧ページのような「骨格は静的・物件データは動的」なページ構成に特に適しています。

- **ポイント2:** `loading.tsx`とSuspenseバウンダリの粒度設計が性能のボトルネックになりやすく、1ページに大きなSuspenseを1つ置くより、カード単位・セクション単位で細かく分割した方がTTFBとLCPの両方が改善します。物件詳細ページの画像ギャラリーと賃料情報を別バウンダリに分けるなどの工夫が有効です。

- **ポイント3:** Server Actionsのストリーミングレスポンス（`useActionState`との組み合わせ）が成熟し、フォーム送信中の中間状態をプログレッシブに返せるようになっています。問い合わせフォームや引越し費用の見積りフローのような多段階フォームでUX向上に直結します。

- **ポイント4:** RSCペイロックのキャッシュ戦略（`revalidateTag`/`revalidatePath`とストリーミングの併用）がより重要になり、物件ステータス（`draft`/`public`）の切り替えのようなミューテーション後にどの粒度でキャッシュを無効化するかが設計上の鍵になります。

- **ポイント5:** エッジランタイムでのストリーミングSSRが一般化し、地理的に分散したユーザーへのTTFB改善が見込めますが、Node.js専用ライブラリ（画像処理・PDF生成など）との互換性に注意が必要です。見積書PDF生成機能がある場合は、その部分だけNode runtimeに固定する設計が必要になります。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCの採用がTypeScriptフルスタック構成（Next.js+Bun等）で加速しており、スキーマ定義とクライアント型を自動同期できるため、API層の型安全性とDX（開発者体験）が大幅に向上する。小〜中規模チームでは「型が仕様書」になり、OpenAPI生成の手間自体が不要になるケースが増えている。

- **ポイント2:** GraphQLは大規模・複数クライアント（Web/モバイル/パートナーAPI）を持つ組織での採用が中心となり、単一フロントエンド+単一バックエンド構成ではオーバーヘッドが過剰と判断されることが多い。sumitsugiのような単一Next.jsアプリではtRPCやServer Actionsで十分というのが実務上の結論になりやすい。

- **ポイント3:** RESTは外部公開APIやサードパーティ連携（決済、地図、認証プロバイダ等）の標準として依然強く、内部APIはtRPC/GraphQL、外部APIはRESTという「ハイブリッド戦略」が2026年のデファクトになっている。

- **ポイント4:** Next.js 16のServer Actions / Server Componentsの成熟により、「APIレイヤーそのものを薄くする」設計が主流化。クライアント-サーバー間のネットワーク境界をAPIスキーマではなくRSC境界で管理するパターンが増え、tRPCと組み合わせることでAPI層のボイラープレートをさらに削減できる。

- **ポイント5:** どの方式でも、Zodなどによる実行時スキーマ検証とAPI契約の一元管理が必須になっている。型だけでは不十分（ビルド時のみ保証）なため、境界（フォーム入力、外部webhook等）でのランタイム検証は標準化が進んでいる。sumitsugiの既存方針（Zod境界検証）とも合致する。

### 4. serverless edge computing 2026

- **ポイント1:** Cloudflare WorkersやVercel Edge Functionsなどのエッジランタイムは2026年にはV8 isolateベースのコールドスタート実質ゼロが標準化し、Node.js API互換性も大幅に向上している。sumitsugiのようなNext.js App Routerプロジェクトでは、物件検索や位置情報系APIをエッジに配置することでレイテンシを大幅短縮できる。

- **ポイント2:** エッジでのデータベースアクセスはDrizzle+Turso/NeonのようなエッジネイティブDBドライバが主流になり、従来のコネクションプール問題が解消されつつある。ただし本プロジェクトのMVPフェーズでは、全機能をエッジ化するより「読み取り頻度の高いページ（物件一覧・公開ページ）」を優先的にエッジ化するのが投資対効果が高い。

- **ポイント3:** Next.js 16のPartial Prerendering（PPR）がエッジ環境と組み合わさることで、静的シェルを即時配信しつつ動的部分（ログイン状態・在庫状況）だけをストリーミングする構成が一般化している。物件詳細ページのような「静的コンテンツ+動的な引越し費用計算」に適している。

- **ポイント4:** エッジでの認証・セッション管理はJWT検証をエッジミドルウェアで行い、重い処理はオリジンに委譲する分離パターンが定着。sumitsugiのauth-context.tsxと組み合わせる際は、middleware.tsでの認可チェックをエッジに置き、個人情報を含むDB処理はオリジン（Node runtime）に残す設計が安全かつ高速。

- **ポイント5:** コスト面では、エッジ実行はリクエスト課金モデルが多く、トラフィックが少ないベータローンチ初期（現フェーズ）では非常に低コストだが、スケール後は従量課金が急増するケースがあるため、ローンチ後のトラフィック予測に基づいた早期のコストモニタリング設計が重要。

### 5. authentication security best practices 2026

- **パスキー/WebAuthnの標準化:** パスワードレス認証が主流化し、FIDO2/WebAuthnベースのパスキーがフィッシング耐性のある認証手段として実装コストも下がってきている。実装時はフォールバック手段（SMS等）を安全に設計することが重要。

- **セッション管理とトークンの短命化:** JWTなどのアクセストークンは短寿命化し、リフレッシュトークンのローテーション＋バインディング（デバイスフィンガープリントやDPoP）で盗難リスクを低減する設計が標準になっている。

- **ゼロトラスト前提の多層防御:** 認証成功後も継続的にリスクスコアリング（IP変化、異常操作パターン）を行い、必要に応じて再認証を要求する「継続的認証」がベストプラクティス化している。

- **シークレット管理の自動化:** 環境変数へのハードコードを避け、Vault/Secrets Manager等での自動ローテーションが前提。侵害時の被害範囲を最小化する設計（最小権限・短命クレデンシャル）が重要。

- **CSRF/XSS対策の標準装備:** SameSite=Strict/Laxクッキー、Content-Security-Policy、HttpOnlyフラグの併用が基本セットとなり、フレームワーク側でデフォルト有効化されるケースが増えている（Next.jsのApp Router構成でも同様の設計を徹底すべき）。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma ORMはPostgreSQL向けに大幅なクエリエンジン最適化を進めており、Rustバイナリ依存を減らしTypeScript純正実装への移行が進んでいる。これによりコールドスタートが改善し、Vercelなどのサーバーレス環境との相性が向上している。
- **ポイント2:** SupabaseはRow Level Security (RLS) とRealtime機能を軸に、認証・DB・ストレージを一体化したBaaSとして定着しており、MVPフェーズのsumitsugiのような小規模チームには運用コストを抑えつつ本番品質のセキュリティを実現できる利点がある。
- **ポイント3:** PrismaとSupabaseを併用する場合、RLSポリシーとPrisma側のアクセス制御が二重管理になりやすいため、`'draft'|'public'`のような物件ステータス制御はDB層（RLS）で一元化し、アプリ層はそれに追従する設計が推奨される。
- **ポイント4:** Supabaseの接続プーリング（PgBouncer経由）とPrismaのコネクション管理の相性問題が頻発するため、サーバーレス環境ではPrisma Accelerateやトランザクションモード指定が事実上の必須パターンになっている。
- **ポイント5:** 2026年時点でPrisma CLIの`migrate`ワークフローとSupabaseのマイグレーション管理がコンフリクトしやすい点は既知の課題で、どちらか一方をスキーマのソース・オブ・トゥルースに統一する運用ルールを早期に決めておくことが、ローンチ後の技術的負債を防ぐ。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGCとコンポーネントモデルの標準化が進み、RustのWasmビルドがJS/DOM連携なしで直接他言語モジュールと相互運用できるようになってきている。sumitsugiのような画像処理・PDF生成を伴う機能では、サーバーレス環境でのコールドスタート短縮に活用できる。
- **ポイント2:** `wasm-bindgen`や`wasm-pack`のツールチェインが成熟し、バンドルサイズの最適化（`wee_alloc`代替やLTO設定）がデフォルトのベストプラクティスとして定着している。重い計算処理（画像リサイズ、座標変換など）をフロントに持ち込む際はこれらの最適化を前提に設計すべき。
- **ポイント3:** ブラウザのSIMD対応とマルチスレッド（`SharedArrayBuffer`経由）がほぼ全モダンブラウザで安定し、Rust+Wasmのネイティブ比パフォーマンスギャップが大幅に縮小している。画像のサムネイル生成や住所検索のクライアントサイド高速化に実用段階で導入可能。
- **ポイント4:** Next.js 16のEdge Runtime/Middlewareと組み合わせた「WasmをEdgeで動かす」パターンが普及し、物件検索のフィルタリングロジックなどをEdge側で高速処理するケースが増えている。インフラコストを抑えつつレイテンシ改善を狙えるため、スケール時の検討候補になる。
- **ポイント5:** ただし導入コストとデバッグの複雑さは依然高く、MVPフェーズでは過剰投資のリスクがある。現在の「ローンチ準備フェーズ」では優先度は低く、ベータ後にパフォーマンス課題が具体化した段階で検討するのが合理的。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16時点でPPRが安定し、静的シェルを即時配信しつつ動的部分だけ`<Suspense>`でストリーミングする構成が標準化。LCP改善とパーソナライズの両立が可能になり、ECや物件検索のようなページで特に効果が大きい。

- **Server Actions中心のデータ更新:** フォーム送信やミューテーションはAPI Routeではなく`"use server"`のServer Actionsに統一する流れが定着。クライアント側のfetch/状態管理コードが減り、楽観的更新（`useOptimistic`）と組み合わせることでUXも向上する。

- **キャッシュ戦略の明示化:** `fetch`のデフォルトキャッシュ挙動が過去に混乱を招いたため、`cacheLife`/`cacheTag`など明示的なキャッシュAPIを使う設計が推奨される。`revalidateTag`によるオンデマンド再検証を意識的に設計しないと、本番で古いデータが表示されるリスクがある。

- **Route Groups + Parallel Routesでのレイアウト分離:** `(group)`や`@slot`を使った並行ルーティングで、モーダルやダッシュボードの複数ペインをURL駆動で管理するパターンが一般化。戻る/進むボタンの挙動が自然になり、E2Eテストも書きやすくなる。

- **Server ComponentsとClient Componentsの境界設計:** 「葉（leaf）のみをClientにする」原則が浸透し、バンドルサイズ削減とハイドレーション時間短縮を狙う。本プロジェクトでも`src/components/`配下で`'use client'`境界を最小化できているか、定期的にレビューする価値がある。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Vercel Edge FunctionsはV8 isolateベースで実行されるため、Node.js APIに依存するコードは動かず、`fetch`やWeb標準APIのみ使える制約を踏まえた設計が前提になる。認証チェックやリダイレクトなどの軽量ロジックに限定するのがベストプラクティス。
- **ポイント2:** コールドスタートがほぼゼロに近いのがEdgeの強みだが、DBクエリなど重い処理を乗せるとレイテンシメリットが相殺される。sumitsugiでは物件検索APIはEdgeに置かず、認証ミドルウェアやジオロケーション判定など「判断系」の軽量処理に絞るべき。
- **ポイント3:** 2026年時点でVercelはEdge Middleware経由のA/Bテスト・パーソナライゼーションを推進しており、前の住人/次の住人のマッチング表示などリクエスト単位の出し分けはEdgeで処理すると中央サーバーの負荷を下げられる。
- **ポイント4:** Edge Functionsの実行リージョンはユーザーに最も近い場所で自動選択されるため、グローバル展開よりも日本国内向けサービスであるsumitsugiでは効果が限定的。コスト対効果を見極め、全面移行ではなく認証・リダイレクトなど効果の出る箇所にスコープを絞るのが現実的。
- **ポイント5:** Next.js 16のPPR（Partial Prerendering）とEdge Runtimeの組み合わせが2026年の主流パターンになっており、静的な物件一覧ページの骨格をプリレンダーしつつ、動的な「引越し費用」計算部分だけEdgeでストリーミングする構成がパフォーマンスとSEOを両立させる。

### 10. TypeScript type safety patterns 2026

- **ポイント1（Branded Types / Nominal Typing）:** `type UserId = string & { __brand: 'UserId' }` のようなBranded Typesで構造的型付けの弱点を補い、`listingId`と`userId`のような同じ`string`型同士の取り違えをコンパイル時に防ぐパターンが定着しています。Zodの`.brand()`と組み合わせることで、バリデーション済みの値だけが型レベルでも保証されます。

- **ポイント2（Zodスキーマからの型推論を正とする）:** `z.infer<typeof schema>`で型を導出し、手書きの`interface`と重複させないアプローチが標準化しています。`src/lib/`の境界（API・フォーム入力）で一度スキーマを定義すれば、ランタイム検証と静的型が常に同期し、union型（例: `'draft' | 'public'`）の値追加漏れもスキーマ側の変更漏れとして検知しやすくなります。

- **ポイント3（Discriminated Unionによる状態モデリング）:** `status: 'draft' | 'public'`のような単純なフラグよりも、物件の状態ごとに異なるフィールドを持つ場合は`{ status: 'draft'; publishedAt?: never } | { status: 'public'; publishedAt: Date }`のようなDiscriminated Unionで表現し、`switch`文の`exhaustive check`（`never`型でのassertion）を使って分岐漏れをビルド時に検出するのが実用的です。

- **ポイント4（`satisfies`演算子の活用）:** `as const satisfies Config`のように、型の広がりを保ちつつ型チェックだけ行う`satisfies`が定着し、`site-config.ts`のような設定オブジェクトで「型安全だが推論結果は具体的な値のまま」という理想的な状態を実現できます。

- **ポイント5（strictな設定とCI連携）:** `strict: true`に加え`noUncheckedIndexedAccess`や`exactOptionalPropertyTypes`を有効化する流れが2026年も続いており、これらは配列アクセスやoptionalプロパティの思わぬ`undefined`をコンパイル時に検出します。重要なのは「ESLint/テストだけでは検知できない型エラーがある」ため、CIに`bun run build`（tscの型チェック相当）を必ず含めることです。
