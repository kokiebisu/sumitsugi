# CTO Knowledge - 2026-03-12

## Daily Update (2026-03-12)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを劇的に削減できるため、`"use client"` は最小限に留め、データフェッチはサーバーコンポーネントで完結させる設計を標準化すべき。

- **Partial Prerendering (PPR) の本番採用:** Next.js 15以降で安定化したPPRにより、静的シェルと動的コンテンツを同一ルートで共存できる。`export const experimental_ppr = true` で段階的に移行し、TTFBを最小化する。

- **`use cache` APIによるきめ細かいキャッシュ制御:** 関数・コンポーネント単位でキャッシュタグを付与できるため、ページ全体の再検証ではなく必要な粒度でのオンデマンド再検証が可能になった。

- **Turbopackの本番ビルド対応:** Next.js 15.3以降でTurbopackが`next build`に対応し、大規模プロジェクトでのビルド時間が従来比40-60%削減される報告が増加。早期移行でCI/CDの高速化を狙う価値あり。

- **Image/Font最適化のゼロコンフィグ徹底:** `next/image`のサイズ自動最適化と`next/font`によるCLS排除は今や必須。さらに`priority`属性をLCP対象画像に付与する習慣をコードレビューチェックリストに組み込むべき。

### 2. React Server Components streaming 2026

- **Suspense境界の細粒度化が標準に:** 2026年時点では、RSCとSuspenseを組み合わせたストリーミングが「デフォルト設計」となり、ページ単位ではなくコンポーネント単位でのプログレッシブレンダリングが当たり前になっている。

- **PPR（Partial Prerendering）の本格普及:** Next.js 15〜16でStableになったPPRにより、静的シェルを即座に配信しつつ動的コンテンツをストリームする「ハイブリッドアーキテクチャ」が実用的になり、TTFB改善と動的性の両立が容易になった。

- **データフェッチの並列化戦略が鍵:** `Promise.all`でデータを並列フェッチしSuspenseでwaterfallを排除するパターンが必須知識に。`use()`フックの活用によりクライアント側でもサーバーからのPromiseを扱えるようになり、設計の柔軟性が増した。

- **キャッシュ戦略の複雑さが増大:** `fetch`のキャッシュ、`unstable_cache`、Route Segment Configなど複数レイヤーのキャッシュが絡み合い、ストリーミングとキャッシュの整合性確保が設計上の主要課題となっている。`stale-while-revalidate`をサーバー側で意識した実装が重要。

- **エラーバウンダリとローディングUIの設計が品質を左右:** ストリーミング環境では`error.tsx`と`loading.tsx`の配置がUXに直結する。特にネスト構造でのフォールバックUI設計を怠ると、部分的なエラーがページ全体のクラッシュに見えるなど、デグレードが起きやすい点に注意が必要。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年時点でtRPCはNext.js/Remix等のフルスタックプロジェクトにおいてデファクトに近づいており、TypeScriptの型をサーバー・クライアント間で共有できるため、スキーマ定義の重複やランタイムエラーを大幅に削減できる。

- **GraphQLの用途特化:** GraphQLは「すべてのAPIに使う」から「複雑なデータグラフ・BFF（Backend for Frontend）パターン」への用途特化が進み、Federation v2によるマイクロサービス統合が主戦場になっている。

- **RESTは死なず、HTTP/3とOpenAPI 3.1で進化:** RESTはシンプルさとエコシステムの広さから依然主流だが、OpenAPI 3.1 + Zod/TypeBoxによる自動型生成と、HTTP/3（QUIC）による低レイテンシ化で実用性が向上している。

- **エッジコンピューティングとAPI設計の再考:** Cloudflare Workers・Vercel Edge等のエッジランタイム普及により、従来のRESTエンドポイントをエッジに近づけるアーキテクチャが増加。コールドスタートを排除できるtRPC/Honoの組み合わせが注目されている。

- **AIエージェント向けAPIとMCPの登場:** LLMエージェントがAPIを直接呼び出すユースケースが急増しており、Anthropicが提唱するMCP（Model Context Protocol）のような標準化が進む中、REST/GraphQL/tRPCの各設計にも「機械可読性」と「ツール定義の明示化」が求められ始めている。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジの標準ランタイムへ:** Cloudflare Workers・Fastly Compute@Edgeを中心に、WasmがJavaScript以外の言語（Rust、Go、Python）をエッジで動かす主流手段となり、コールドスタートをほぼゼロに抑えられる。

- **エッジDBの成熟:** Cloudflare D1・Turso・Neon（HTTP経由）の普及により、エッジ関数からSQLiteクローンやPostgres互換DBへ低レイテンシアクセスが現実的になり、「エッジ = ステートレス」の制約が崩れつつある。

- **AIインファレンスのエッジシフト:** 小型LLM（Llama 3.2 1B/3B相当）をエッジノードで動かすユースケースが急増。Cloudflare AI・Vercel AI Gatewayがその基盤となり、レイテンシ削減とデータ主権の両立が可能になる。

- **オブザーバビリティの課題が顕在化:** 数百のエッジロケーションに分散したトレース・ログを集約するコストと複雑さが増大。OpenTelemetry対応のエッジネイティブAPM（Baselime買収後のCloudflare等）の整備が急務。

- **エッジ・オリジン間の「ハイブリッド実行」がデフォルトへ:** 全てをエッジに寄せるのではなく、認証・キャッシュ判定はエッジ、ビジネスロジック・DB書き込みはオリジンという役割分担を明示的に設計するアーキテクチャが標準パターンとして定着しつつある。

### 5. authentication security best practices 2026

- **パスキー（Passkey）の標準化:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の主流となり、フィッシング耐性が高く、デバイス間同期も容易になった。2026年時点でGoogle・Apple・Microsoftのエコシステムが成熟し、実装コストが大幅に低下している。

- **MFAの必須化とTOTP廃止の流れ:** SMSベースのOTPは中継攻撃（SIM Swapping）により非推奨化が進み、TOTP/FIDO2ベースのMFAが最低要件に。セッション継続中も定期的な再認証（Step-up Authentication）を組み合わせることが推奨される。

- **ゼロトラスト・コンテキスト認証:** IPアドレス・デバイスフィンガープリント・行動バイオメトリクスを組み合わせた継続的なリスク評価が主流。「一度認証したら信頼する」モデルから、リクエストごとにコンテキストを評価するモデルへの移行が加速している。

- **JWTの短命化とトークンローテーション:** アクセストークンの有効期限を15分以下に短縮し、リフレッシュトークンのローテーション（使用ごとに再発行）を徹底することでトークン漏洩時の被害を最小化。トークンの失効管理にはRedisベースのブロックリストが標準的。

- **サプライチェーン攻撃対策としての依存関係監査:** 認証ライブラリ（`next-auth`等）のアップデートを自動化し、`npm audit`・Dependabotを必須CIステップとして組み込む。特にOAuthライブラリのオープンリダイレクト脆弱性は2025-2026年に多発しており、バージョン固定より定期更新の方がリスクが低い。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のエッジ対応強化:** Prisma Accelerate（グローバルコネクションプール）とEdge Runtime対応が成熟し、Next.js App RouterのServer ComponentsからD1/Supabaseへの直接クエリが現実的な選択肢になった。コールドスタート問題がほぼ解消されている。

- **Supabase の Row Level Security (RLS) とPrismaの統合:** RLSポリシーをDBレイヤーで定義しつつ、Prismaで型安全なクエリを書くパターンが定着。`auth.uid()`をPrismaミドルウェアで自動注入するアプローチが実用的で、アプリ層での認可ロジックを大幅削減できる。

- **Prisma Schema → Supabase Migrations の管理戦略:** `prisma migrate` と Supabase CLI の `supabase db push` の二重管理が依然として摩擦源。2026年現在、Prismaをスキーマの「Single Source of Truth」とし、生成したSQLをSupabaseに適用するワークフローがベストプラクティスとして確立しつつある。

- **リアルタイム + Prisma の棲み分け:** SupabaseのRealtime（Postgres CDC）はリアルタイム購読に使い、Prismaはミューテーション・複雑なクエリに専念させる責務分離が重要。両方をまとめようとするとN+1問題やコネクション枯渇を招く。

- **型安全性のフルスタック担保:** Prisma Clientの型 → tRPC or Server Actions → クライアントまで型を通す設計が2026年のスタンダード。Supabase TypeScript SDK（`supabase-js v3`）の型生成と競合しないよう、DBアクセス層をPrismaに統一することでメンテコストを抑えられる。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の本格普及:** 2026年はWASI Preview 2が主流となり、Rustで書いたWasmコンポーネントがホスト環境に依存せずポータブルに動作する。wit-bindgenによる型安全なインターフェース生成がエコシステムを大きく加速している。

- **Wasmtime・WASMERのAOTコンパイル最適化:** JITからAOT（事前コンパイル）への移行が進み、コールドスタートが数ミリ秒以下に。RustのゼロコストアブストラクションがWasm上でもほぼそのまま活きるため、ネイティブ比90〜95%のパフォーマンスが現実的になった。

- **SIMD・スレッド対応の安定化:** WebAssembly SIMDとShared Memoryが主要ブラウザ・ランタイムで安定稼働。Rustの`packed_simd`や`std::simd`を使った音声・画像処理でネイティブ超えのケースも報告されている。

- **エッジ実行基盤としてのRust+Wasm:** Cloudflare Workers・Fastly Compute・Fermyon Spinがデファクトスタックとして定着。Rustのメモリ安全性とWasmのサンドボックスが組み合わさり、マルチテナント環境での分離コストがほぼゼロになっている。

- **ガベージコレクション不要の優位性が再評価:** GC付き言語（Go・Kotlin）のWasm出力がGCプロポーザルで動くようになったことで逆説的に、RustのGCなし・予測可能なレイテンシという特性が低レイテンシ要件（リアルタイム処理・ゲーム）で差別化ポイントとして明確化された。

### 8. Next.js App Router patterns 2026

- **Server Componentsをデフォルトに:** 2026年時点でApp Routerの成熟度が上がり、データフェッチはServer Components内で直接行うのが標準。`fetch`のキャッシュ制御（`cache: 'force-cache'` vs `no-store`）をページ単位で使い分けることでパフォーマンスが大幅に改善される。

- **Partial Prerendering (PPR) の実用化:** Next.js 15+でPPRがstableになり、静的シェルと動的コンテンツを同一ルートで混在できる。`<Suspense>`境界を意識的に設計することで、TTFBを維持しつつ動的データを後続ストリームで流す構成が主流になっている。

- **Server Actions でAPI Route不要化:** フォーム送信・mutation処理はServer Actionsに集約し、`/api/*`ルートを減らす方向が定着。ただしバリデーション（Zod）とエラーハンドリングをAction内で厳密に行わないとセキュリティリスクになる点に注意。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15の`use cache`で関数レベル・コンポーネントレベルのキャッシュ制御が可能に。従来の`revalidate`よりも宣言的で、コロケーションしやすいため、データ依存関係の管理が明確になる。

- **Turborepack + `next/font` + Server Component最適化でCore Web Vitals改善:** ビルドツールがTurbopackに移行しHMRが高速化。バンドルサイズの観点では、Client Componentへの`'use client'`境界を末端コンポーネントに限定し、ツリーの大部分をServer Componentに保つ設計が引き続きLCPとTBT改善の鍵。

### 9. Vercel Edge Functions optimization 2026

- **Edge RuntimeでのCold Start削減:** 2026年時点でVercel Edge FunctionsはV8 Isolateベースのため従来のNode.jsランタイムより起動が高速だが、バンドルサイズを50KB以下に抑えることがレイテンシ最適化の要。依存ライブラリはEdge互換かを`@vercel/edge`で事前検証する。

- **Fluid Compute（動的スケーリング）の活用:** Vercelが2024-2025に導入したFluid Computeにより、リクエスト間でCPUリソースを共有・継続利用できるようになった。バースト処理やストリーミングレスポンスと組み合わせるとコスト効率が大幅改善する。

- **地理的ルーティングとキャッシュ戦略の精緻化:** `Cache-Control`ヘッダーと`stale-while-revalidate`を組み合わせたEdgeキャッシュの階層設計が重要。ISR（Incremental Static Regeneration）をEdge層で制御することで、動的コンテンツでも99パーセンタイルレイテンシを50ms以下に抑えられる。

- **Middleware vs Edge Route Functionsの使い分け:** 認証・リダイレクト・A/BテストにはMiddleware（全リクエストに適用）、APIロジックにはEdge Route Functionsを使い分けることがベストプラクティス。Middlewareの肥大化はグローバルレイテンシ劣化の主因。

- **可観測性の強化:** 2025年以降、Vercel ObservabilityとOTelの統合が進み、Edge Function単位のトレーシングが可能になった。P95/P99レイテンシをリージョン別に監視し、ホットスポットを特定するワークフローを開発プロセスに組み込むことが推奨される。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の積極活用:** TypeScript 4.9で導入された`satisfies`は型推論を保ちつつ型チェックを強制できるため、`as`キャストの代替として2026年現在のベストプラクティスとなっている。

- **Template Literal Typesによる文字列の厳格化:** APIエンドポイントやイベント名を`` `/api/${string}` ``のような型で表現することで、文字列リテラルに型安全性をもたらし、ランタイムエラーをコンパイル時に検出できる。

- **Branded Types（不透明型）でドメイン境界を強化:** `type UserId = string & { readonly _brand: 'UserId' }` パターンにより、IDの混在バグを型レベルで防ぐ手法が実務での採用が進んでいる。

- **`noUncheckedIndexedAccess` の標準有効化:** `tsconfig.json`でこのオプションを有効にすることで配列・オブジェクトアクセスが`T | undefined`として扱われ、インデックスアクセス起因のランタイムエラーを大幅に削減できる。

- **型レベルバリデーションとZodの融合:** `z.infer<typeof schema>`でバリデーションスキーマから型を自動導出するパターンが定着し、フロントエンド・バックエンド間の型共有コストを排除しながら実行時安全性も確保できる。
