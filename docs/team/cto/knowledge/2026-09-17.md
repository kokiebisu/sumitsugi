# CTO Knowledge - 2026-09-17

## Daily Update (2026-09-17)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Prerendering の本格運用）:** 静的部分と動的部分を1ページ内で共存させるPPRが安定版となり、ダッシュボードのような「一部だけ動的」なページでもTTFBを大幅短縮できる。うちのproperties一覧ページのような検索フィルタ付き画面に適用余地がある。

- **ポイント2（React Compilerによる自動メモ化）:** `useMemo`/`useCallback`の手動最適化が不要になりつつあり、ビルド時に自動でメモ化される。コードレビューの負担が減る一方、依存する古いメモ化パターンは書き換えが必要になる。

- **ポイント3（Turbopackのプロダクションビルド標準化）:** devだけでなく本番ビルドでもTurbopackが既定になり、ビルド時間が大幅短縮。CI時間の圧縮に直結するため、`bun run build`のCIコストが下がる見込み。

- **ポイント4（キャッシュ制御の明示化）:** `fetch`のデフォルトキャッシュ挙動が変わり、`use cache`ディレクティブなど明示的なキャッシュ指定が主流に。曖昧なキャッシュ挙動によるバグ（古いセラー情報の表示など）を防ぐため、境界を明確にする設計が重要。

- **ポイント5（画像・フォント最適化の自動化強化）:** `next/image`のCDN連携やAVIF優先度がさらに強化され、物件写真中心のUIでLCP改善効果が大きい。引越し費用の説明ページなど画像多用箇所から優先適用すべき。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPPR（Partial Prerendering）が安定版となり、静的シェルを即座に配信しつつ動的部分のみストリーミングする構成が標準化。TTFBを維持したままパーソナライズされたコンテンツを配信できる。
- **ポイント2:** `use cache`ディレクティブとCache Componentsの組み合わせで、コンポーネント単位のキャッシュ粒度がRSCストリーミングと統合され、再検証境界を細かく制御できるようになった。
- **ポイント3:** Suspenseバウンダリの粒度設計が引き続き重要な設計判断で、粒度が粗すぎるとウォーターフォールが発生し、細かすぎるとハイドレーション負荷とレイアウトシフトが増える。物件詳細ページのような画像+レビュー+料金計算が混在するUIでは、初期表示に必須なブロックとそうでないブロックを明確に分離すべき。
- **ポイント4:** RSCペイロードのシリアライズコストがストリーミングのボトルネックになりやすく、サーバーコンポーネントからクライアントコンポーネントに渡すpropsのサイズ削減（特に大きな配列・画像メタデータ）がパフォーマンスチューニングの焦点になっている。
- **ポイント5:** エッジランタイム上でのRSCストリーミング（Vercel Edge / Cloudflare Workers）が実用段階に入り、地理的に分散したユーザーへのTTFB改善が可能に。ただしNode.js専用ライブラリ（一部のPDF生成・画像処理系）との互換性確認が必要。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはNext.js×TypeScriptのようなフルスタックTS環境で「型安全性とスキーマレス開発速度」の面で最有力な選択肢になっている。当プロジェクトのようなモノレポ的なApp Router構成では、REST用のOpenAPI型生成より、tRPCのエンドツーエンド型推論の方が開発コストが低い。

- **ポイント2:** GraphQLは複数クライアント（Web/モバイル/パートナーAPI）が同一データソースを異なる粒度で取得する場合に強みを維持しているが、単一フロントエンド（自社Webのみ）のプロダクトでは過剰投資になりがちで、当プロダクトの規模では時期尚早。

- **ポイント3:** RESTは外部連携（決済、行政API、他社SaaS連携）やWebhookが絡む場面で依然デファクト標準。2026年時点でも「社内はtRPC、外部境界はREST/OpenAPI」というハイブリッド構成が主流トレンド。

- **ポイント4:** API設計よりも「型のドリフト検知」が重要度を増している。union型（`'draft' | 'public'`のような物件ステータス）を跨ぐ変更でクライアント/サーバーの型不整合が起きやすく、tRPC採用時もzodスキーマでランタイム検証を併用するのがベストプラクティス。

- **ポイント5:** 2026年はAIエージェントがAPIを直接呼ぶケース（MCP経由など）が増え、人間向けAPI設計とエージェント向けAPI設計（曖昧さの少ない入出力、構造化エラー）を分けて考える必要が出てきている。将来的にAIオンボーディング機能を拡張するなら、この観点を早めに設計に組み込む価値がある。

### 4. serverless edge computing 2026

- **エッジでのAI推論標準化:** 2026年はLLMの軽量化(量子化・蒸留)が進み、CDNエッジノード上でのAI推論(パーソナライゼーション、レコメンド)がレイテンシとコストの両面で現実的な選択肢になっている。sumitsugiでは物件検索のリランキングやチャット応答の一次処理をエッジで行うことでTTFBを大幅短縮できる可能性がある。

- **コールドスタート問題の実質的解消:** Cloudflare Workers・Vercel Edge Functions等がV8 isolateベースの実行環境を成熟させ、ミリ秒未満のコールドスタートが標準化。Next.js 16のApp RouterはEdge Runtimeとの統合が深まっており、`src/app`配下の一部ルート(認証チェックや簡易API)をEdgeに移行する価値が高まっている。

- **データ整合性とエッジの分散トレードオフ:** エッジでの処理は高速だが、グローバルに分散したデータストア(D1、Turso等)との整合性管理が複雑化する。物件ステータス(`draft`/`public`)のような強整合性が必要なデータは中央集権的なDB(現状のアーキテクチャ)に留め、静的コンテンツや検索インデックスのみエッジ最適化する、というハイブリッド戦略が実用的。

- **観測性ツールの追従不足:** エッジ環境は分散実行のためトレーシング・ロギングの複雑性が増し、従来のAPMツールの対応が遅れがち。移行を検討する場合、まず限定的なエンドポイント(例:画像最適化API)から段階導入し、可観測性を確保できるかを検証すべき。

- **コスト構造の逆転リスク:** リクエスト数課金のエッジ実行は低トラフィック時は安価だが、高トラフィックの画像処理やSSRでは従来のサーバーレス(Lambda等)より割高になるケースが2026年も引き続き報告されている。sumitsugiの規模(MVP直後)ではまだ移行の投資対効果が低く、ローンチ後のトラフィック実測データを踏まえて判断すべき段階。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への全面移行:** パスワードレス認証（WebAuthn/パスキー）が業界標準となり、フィッシング耐性の高い認証をデフォルトにすることでアカウント乗っ取りリスクを大幅に削減できる。実装コストも下がっているため、新規プロジェクトでは最初からパスキーファーストで設計すべき。

- **セッション管理とトークンのローテーション:** JWTを使う場合は短命アクセストークン＋リフレッシュトークンローテーションを徹底し、漏洩時の被害範囲を最小化する。加えてデバイスフィンガープリンティングと組み合わせた異常検知で、盗まれたトークンの再利用を検出する。

- **ゼロトラスト前提のAPI設計:** 認証と認可を分離し、全リクエストで最小権限の原則（RBAC/ABAC）を検証する。マイクロサービス間通信でもmTLSやサービスメッシュレベルの認証を導入し、内部ネットワークを信頼しない設計にする。

- **レート制限とボット対策の標準装備:** ログイン・パスワードリセットなどの認証エンドポイントには必ずレート制限とCAPTCHA/behavioral analysisを組み込み、クレデンシャルスタッフィング攻撃を前提とした防御を行う。監視ログにも認証イベントを必ず含める。

- **サードパーティ依存の最小化とサプライチェーン監査:** 認証ライブラリ（NextAuth/Auth.jsなど）は定期的な脆弱性スキャンとバージョン追従を行い、OAuthプロバイダー連携時のスコープは必要最小限に絞る。自前実装より監査済みライブラリの活用を優先し、車輪の再発明によるバグ混入を避ける。

### 6. database architecture Prisma Supabase 2026

- **接続プーリング必須:** Supabaseはpgbouncer/Supavisor経由の接続が基本のため、Next.jsのサーバーレス関数からPrismaを使う場合は`DATABASE_URL`（プール用）と`DIRECT_URL`（マイグレーション用）を分離設定しないと、コネクション枯渇やタイムアウトが頻発する。

- **RLSとPrismaの相性に注意:** PrismaはデフォルトでSupabaseのRow Level Securityを尊重しない単一ロール接続になりがちなので、`前の住人`/`次の住人`間のデータ分離を本気で担保するならRLSポリシー＋Supabase Authのjwtクレームをアプリ層のバリデーションと二重化するのが安全。

- **Prisma 6以降の軽量エンジン:** Rustバイナリ非依存のクエリコンパイラがデフォルト化し、コールドスタートが大幅短縮。VercelのEdge/Serverless両方でのデプロイサイズ・起動速度が改善するため、物件検索APIのレイテンシ改善に直結する。

- **pgvectorでのマッチング活用:** SupabaseのpgvectorとPrismaを組み合わせ、IC相談マッチング（先日の会議方向性）や物件レコメンドにベクトル検索を組み込む事例が増えている。Prismaの`$queryRaw`でベクトル演算を扱う形が現状の定石。

- **DBブランチングでPRごとにプレビューDB:** Supabaseのブランチ機能を使うとPRごとに独立したPostgresインスタンスを自動作成でき、マイグレーションの検証をCI上で本番相当環境に近い形で行える。現状のPRフロー（`bun run build`必須・E2E必須）に組み込むと回帰検知が強化される。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC(Garbage Collection提案)の主要ブラウザ実装が成熟し、RustでもGCを前提としたホスト連携が簡素化されている。従来のリニアメモリ+手動メモリ管理の複雑さが減り、JS/TS側とのオブジェクト共有コストが下がっている。

- **ポイント2:** `wasm32-wasip2`とComponent Model(WIT)の採用が進み、Rustクレートを言語非依存の再利用可能コンポーネントとして配布できるようになった。マイクロサービス的に機能を切り出し、サーバーサイドでもWasmランタイム(wasmtime等)で高速コールドスタートを実現しやすい。

- **ポイント3:** SIMD(固定幅128bit)とマルチスレッド(Web Workers連携)がRust側で標準的に使えるようになり、画像処理やPDF生成のようなCPU負荷の高い処理をクライアントに オフロードする選択肢が現実的になっている。弊社の「引越し費用」計算や物件データのクライアント側前処理に応用余地がある。

- **ポイント4:** バイナリサイズ最適化(`wasm-opt`, `twiggy`, LTO+`opt-level="z"`)のツールチェーンが安定し、Next.js的なコード分割と組み合わせることで初回ロードのオーバーヘッドを抑えられる。ただしビルド時間とのトレードオフがあるため、CI時間への影響は要検証。

- **ポイント5:** Rust製Wasmモジュールのデバッグ体験(DWARF対応・ソースマップ)が改善され、本番障害時のスタックトレース追跡が現実的になってきた。ただし現状のNext.jsスタックにWasmを導入するホットパスがまだ無いため、優先度は低く「将来の重い計算処理が出た時の選択肢」として留めておくのが妥当。

### 8. Next.js App Router patterns 2026

- **ポイント1（PPR本格採用）:** Partial Prerendering が2026年時点で安定版の主力機能となり、静的シェルと動的コンテンツを1ページ内で共存させることで、TTFBを維持しつつパーソナライズやログイン状態表示が可能に。sumitsugiの物件一覧ページのように「静的な物件情報＋動的な空き状況・お気に入り状態」を組み合わせる箇所で有効。

- **ポイント2（Server Actionsのキャッシュ戦略成熟）:** `revalidateTag`/`updateTag` ベースの細粒度キャッシュ無効化が標準パターン化し、Server Actionsをmutation専用に使い、キャッシュタグ設計をデータモデル（物件ID単位など）に合わせて最初から設計することがベストプラクティスに。

- **ポイント3（"use cache" ディレクティブの定着）:** Next.js 16で導入された`"use cache"`によりコンポーネント/関数単位のキャッシュ制御が明示的になり、`fetch`のオプション地獄から解放。データ取得ロジック（`src/lib/data.ts`）をキャッシュ境界として再設計する余地がある。

- **ポイント4（Server Componentsファーストのフォーム設計）:** クライアントJSを最小化するため、フォームバリデーションをZodスキーマ＋Server Actionsで完結させ、クライアント側は`useActionState`のみに絞る構成が主流。認証・引越し費用の入力フォームなどセキュリティが絡む箇所ほどこの恩恵が大きい。

- **ポイント5（ルートグループ＋Parallel/Interceptingルートの実務活用）:** モーダル型UI（物件詳細のクイックビューなど）にIntercepting Routesを使い、直リンク時はフルページ、クリック遷移時はモーダル表示という「1実装で2体験」パターンがEC/不動産系アプリで定番化。ディレクトリ構成の複雑化とのトレードオフを見極める必要あり。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Runtimeでのコールドスタート短縮が進み、V8 isolateの起動を数ms単位に抑えられるようになったため、SSRのTTFBを重視するページはNode.js RuntimeからEdge Runtimeへの移行を再検討する価値がある。ただしNode.js APIの一部制約は依然残るため、依存ライブラリの互換性確認が前提になる。

- **ポイント2:** Vercelの`waitUntil`とEdge Middlewareを組み合わせたバックグラウンド処理（ログ送信・キャッシュ再検証など）がベストプラクティスとして定着しており、レスポンスをブロックせずに副作用処理を実行できる設計が推奨される。

- **ポイント3:** Edge ConfigやKVとの統合による「リクエスト時のDBアクセスを避ける」パターンが重要で、フィーチャーフラグやリダイレクトルールなど頻繁に読むが更新頻度が低いデータはEdge Configに寄せることでレイテンシを大幅に削減できる。

- **ポイント4:** リージョン指定（`regions`設定）を活用し、ユーザーの地理分布とデータベース/APIのリージョンを一致させることでレイテンシを最小化する「co-location」戦略が2026年時点でのデファクトになっており、単一リージョンのDB前提の設計はEdge化のボトルネックになりやすい。

- **ポイント5:** Streaming SSR（React Server ComponentsのPPR: Partial Prerendering）とEdge Functionsの組み合わせにより、静的部分を即座に配信しつつ動的部分のみをEdgeで解決する構成が主流化しており、sumitsugiのような物件検索・一覧ページでは体感速度向上に直結する施策として優先度が高い。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** `satisfies`演算子とテンプレートリテラル型の組み合わせが標準化し、リテラル型を保持したままオブジェクトの構造検証が可能になっている。型推論を犠牲にせず「意図した形」を静的に保証できるため、設定オブジェクトやAPIレスポンスの定義で広く採用が進んでいる。

- **ポイント2:** Zodなどのスキーマバリデーションライブラリと型定義を一体化する「Schema-first」開発が主流化し、`z.infer`でランタイム検証と静的型を単一ソースから生成するパターンが定着している。本プロジェクトでも境界値検証にZodを使う方針と合致しており、二重管理によるドリフトを防げる。

- **ポイント3:** `unknown`を起点にした型ガードとDiscriminated Union（タグ付きユニオン）の徹底により、`any`の使用を実質ゼロにする「strict boundary」パターンが浸透している。特に外部APIやユーザー入力の境界で`unknown → 型ガード → 具体型`の変換を義務付けることでランタイムエラーを大幅に削減できる。

- **ポイント4:** TypeScript 5.x系の`const`型パラメータや`NoInfer`ユーティリティ型が普及し、ジェネリック関数での意図しない型推論の広がり（widening）を防ぐ設計が一般化している。ライブラリ関数のAPI設計で型安全性と使いやすさを両立させやすくなった。

- **ポイント5:** モノレポ構成でのプロジェクト参照（Project References）とインクリメンタルビルドが標準運用となり、型チェックの高速化と同時に「変更が波及する範囲」を型レベルで可視化できるようになっている。大規模化するコードベースでのビルド時間管理に直結する重要な観点。
