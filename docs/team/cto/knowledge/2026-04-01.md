# CTO Knowledge - 2026-04-01

## Daily Update (2026-04-01)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降で安定化したPPRにより、静的シェルと動的コンテンツを同一ルートで混在させることが可能になった。`<Suspense>`境界を適切に設計することで、TTFBを維持しながらパーソナライズされたコンテンツを提供できる。

- **React Server Components (RSC) によるバンドルサイズ削減:** サーバー側でのみ実行されるコンポーネントはクライアントバンドルに含まれないため、重いライブラリ（日付処理・MDXパーサー等）はRSCに移行するだけで劇的なJS削減効果がある。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** Next.js 15で導入された`use cache`により、ページ・コンポーネント・関数単位でのキャッシュ戦略が宣言的に記述可能になった。`cacheTag`と`revalidateTag`を組み合わせてオンデマンド再検証を設計することが2026年のベストプラクティス。

- **Turbopack のプロダクション対応化:** Turbopackがbuildにも対応し始め、大規模コードベースでのビルド時間が従来比最大60%短縮。CI/CDパイプラインのボトルネック解消に直結するため、早期移行の評価を推奨する。

- **Image/Font最適化の徹底:** `next/image`のsizes属性とRemote Patternsの適切な設定、`next/font`によるCLS排除は依然として効果が高い。特にCore Web Vitals（INP対応）が2026年のSEOランキングに強く影響するため、Lighthouseスコアの継続モニタリングが必須。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度が競争優位に:** 2026年時点では、Suspense境界をコンポーネント単位で細かく設計することがTTFB最適化の核心。粗すぎる境界はストリーミングの恩恵を殺し、細かすぎるとウォーターフォールを引き起こす。

- **PPR（Partial Prerendering）の本格普及:** Next.js 15以降でstableになったPPRにより、静的シェルを即座に配信しつつ動的部分のみストリームする設計が標準化。`<Suspense>`の配置戦略がアーキテクチャ設計の第一級市民になった。

- **サーバー/クライアント境界の誤設計がパフォーマンス負債の主因:** `"use client"`の安易な多用でRSCのメリットが消える。バンドルサイズへの影響をCI段階で計測する仕組み（`@next/bundle-analyzer`等）を必須化すべき。

- **データフェッチはコンポーネント内で完結させる:** RSC時代はReact Queryのようなクライアントキャッシュ層に依存せず、サーバーコンポーネントが直接DBやAPIを叩く設計が主流。`fetch`のキャッシュ・再検証戦略（`revalidate`タグ）の設計が実質的なデータアーキテクチャになる。

- **エラー境界とストリーミングの組み合わせに要注意:** ストリーミング中のエラーは`error.tsx`で捕捉されるが、すでに送信済みのHTMLはロールバックできない。クリティカルなデータは早期にフェッチしてストリーム開始前にバリデーションを完了する設計が安全。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年時点でNext.js等のフルスタック構成ではtRPCが主流に近づいており、クライアント・サーバー間でZodスキーマを共有することでランタイムエラーをビルド時に検出できる。

- **GraphQLの用途特化:** GraphQLはBFF（Backend for Frontend）や複雑なデータグラフを持つ大規模サービス向けに絞られ、小〜中規模プロジェクトではオーバーエンジニアリングとみなされる傾向が強まっている。

- **REST + OpenAPI 3.1の再評価:** Zodベースのスキーマから自動生成されるOpenAPI仕様と型安全クライアント（`openapi-fetch`等）の組み合わせにより、RESTの可読性・相互運用性を保ちながらtRPC並みの型安全性を実現できる。

- **エッジ・ストリーミングへの対応:** Server-Sent Events（SSE）やHTTP Streamingを活用したAIレスポンスのストリーミングが普及し、API設計段階からストリーム対応を考慮することが標準となっている。

- **契約駆動開発（Contract-First）の復権:** AI生成コードの増加により、スキーマ/型定義を先に確定させてからクライアント・サーバーを並行実装するアプローチが開発速度と品質の両立に有効で、チームが大きくなるほど効果が顕著。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジの標準ランタイムへ:** Cloudflare Workers・Fastly Compute@Edgeを中心にWasmが主流となり、言語非依存でコールドスタートほぼゼロを実現。Rustや Go製マイクロサービスをエッジに直接デプロイするパターンが定着しつつある。

- **AI推論のエッジシフトが加速:** LLMの軽量モデル（Llama系、Phi系）がエッジで動作可能になり、レイテンシ削減とデータプライバシー確保を同時に実現。ユーザーデータをオリジンに送らずにパーソナライズ処理するアーキテクチャが競争優位になる。

- **エッジDBとの統合が成熟:** Cloudflare D1、Turso（libSQL）、Neon Serverlessなど、エッジから直接クエリできる分散SQLが実用段階に。「エッジで全処理完結」するスタックが現実的な選択肢となり、オリジンへのラウンドトリップが不要になる。

- **コールドスタート問題の実質的な解消:** V8 Isolateモデルの成熟とWasmの普及により、従来のLambda型コールドスタート（数百ms）が5ms以下に。これによりエッジに移せないユースケースが激減し、BFF（Backend for Frontend）層のエッジ移行が現実的になった。

- **オブザーバビリティの遅れがボトルネック:** エッジ実行環境は分散度が高くトレーシングが困難で、OpenTelemetryのエッジ対応がまだ途上。本番運用では分散トレースの設計を事前に織り込まないと、障害時の原因特定に著しく時間がかかるリスクがある。

### 5. authentication security best practices 2026

- **パスキー（Passkey）ファーストへの移行:** FIDO2/WebAuthn標準に基づくパスキーがパスワードレス認証の主流となり、フィッシング耐性と利便性を両立。新規サービスではパスワード認証をレガシーとして位置づけるべき。

- **デバイスバインド型セッション管理:** セッショントークンをデバイスフィンガープリントやTPMチップと紐づけ、トークン窃取によるセッションハイジャックを無効化。Cookieの`SameSite=Strict`＋短命JWTの組み合わせが標準的構成。

- **継続的認証（Continuous Authentication）:** ログイン時の一点認証から、行動バイオメトリクスやリスクスコアリングによるセッション中の継続的検証へ。異常な操作パターンを検知した時点で再認証を要求する設計が求められる。

- **サプライチェーンリスクとしてのOAuthプロバイダー管理:** サードパーティIdP（Google/GitHub等）への依存はSSOジャッキングリスクを内包。`state`パラメータ検証・PKCEの必須化に加え、プロバイダー側インシデント時のフォールバック認証経路を設計段階で確保すること。

- **秘密情報のゼロ知識化:** シークレットをコードやDBに保存せず、HashiCorp Vault/AWS Secrets Managerによる動的シークレット発行が標準化。本プロジェクト（Next.js）では`process.env`経由での取得とビルド時リークチェックをCI必須ステップとして組み込むべき。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応:** Prisma 6がVercel Edge・Cloudflare Workersに完全対応し、Supabase Connection Pooler（PgBouncer）と組み合わせることで、サーバーレス環境でのコールドスタートと接続数の問題が大幅に解消された。

- **Supabase Branching × PR-driven DB migration:** Supabase BranchingとGitHub PRを連動させることで、DB migration をコードレビューフローに統合できる。本番DBを汚さずにスキーマ変更を検証できる開発体験が2026年の標準になりつつある。

- **RLSファーストアーキテクチャへの移行:** Row Level Security（RLS）を後付けではなく設計初期から組み込む「RLSファースト」が主流化。Prismaの`$extends`でRLSコンテキスト（`auth.uid()`）を自動注入するパターンが定番になっている。

- **Prisma Pulse によるリアルタイム変更検知:** Prisma PulseがSupabase Realtimeの代替・補完として機能し、DB変更をTypeScript型安全なストリームで受け取れる。WebSocket管理をアプリ層から切り離せる点がアーキテクチャ上のメリット。

- **pgvectorとAIワークロードの統合:** SupabaseのpgvectorサポートとPrismaのraw query組み合わせによるベクトル検索が実用段階に入り、外部ベクトルDBを持たずにPostgres単一DBでRAGパイプラインを完結させる設計が現実的な選択肢になっている。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の本格普及:** 2026年はWASI Preview 2が主流となり、RustのWASM出力がホスト間でよりポータブルに。`cargo component`ツールチェーンで型安全なインターフェース定義が標準化され、マイクロサービス間の相互運用性が大幅に向上した。

- **Wasmtime/WASMEdgeのAOTコンパイル最適化:** JITからAOTへのシフトが進み、コールドスタートがネイティブコードの1.1〜1.3倍程度まで接近。Rustの`wasm-opt`パスと組み合わせることでバイナリサイズも平均30%削減できる。

- **SIMD・スレッド拡張の安定化:** WebAssembly SIMDとShared Memoryが全主要ランタイムで安定版に。RustのSIMD intrinsicsがwasm32ターゲットで透過的に機能し、数値計算・画像処理ワークロードでの採用が加速している。

- **Rustのコンパイル時間問題への対策成熟:** `wasm-bindgen`や`trunk`のインクリメンタルビルド改善により、大規模フロントエンドでの開発体験がReact/Viteに近づいた。ただしCI環境ではキャッシュ戦略（`sccache` + Dockerレイヤー）が依然必須。

- **エッジ実行（Cloudflare Workers / Fastly）でのRust WASM採用増加:** 起動時間とメモリ効率の優位性からエッジランタイムでの採用が拡大。ただしWASM線形メモリの上限（現状4GB）と非同期I/Oの制約は設計時に考慮が必要。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点でApp Routerの主流はServer Components優先設計。データフェッチはコンポーネント内で直接行い、クライアントバンドルを最小化することがパフォーマンスの基本戦略。

- **Partial Prerendering (PPR) の本格活用:** Next.js 15+でstableになったPPRにより、同一ページ内でstatic shellと動的コンテンツを混在させるハイブリッド戦略が標準化。`<Suspense>`境界の設計がアーキテクチャの要点になっている。

- **`use cache` / `use server` ディレクティブによる細粒度キャッシュ:** `fetch`レベルのキャッシュ制御から、関数・コンポーネント単位の`use cache`アノテーションへ移行。`revalidateTag`と組み合わせたオンデマンド再検証が複雑なデータ依存の標準解。

- **Server Actions の成熟と型安全:** フォーム送信・ミューテーションはServer Actionsに集約され、`next-safe-action`等のラッパーでZodバリデーション＋型推論を統合するパターンが定着。APIルートへの依存が大幅に減少。

- **`<Link prefetch>` とRoute Groups によるコード分割戦略:** `(group)`構文でレイアウトを共有せずにルートをグループ化し、`prefetch="viewport"`で遷移体験を最適化。モノリシックなレイアウトツリーを避ける設計がスケーラブルなApp Router運用の鍵。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択基準明確化:** 2026年時点では、Edge FunctionsはCold Startゼロの低レイテンシが強みだが、Node.js APIの制約（fs, crypto等）があるため、地理的分散が必要なルーティング・認証ミドルウェアに限定して採用するのが最適。

- **Fluid Computeによるコスト効率:** VercelのFluid Computeモデルにより、アイドル時間の課金が削減され、Edge/Serverlessの使い分けよりも「リクエスト特性に合わせた選択」が重要になった。高頻度・軽量処理はEdge、重い計算はServerlessという分離が基本戦略。

- **ISR + Edge Cacheの組み合わせ最適化:** `stale-while-revalidate`パターンをEdgeキャッシュと組み合わせることで、動的コンテンツでも静的に近いパフォーマンスを実現できる。Cache-Control設計が2026年のフロントエンドパフォーマンスチューニングの核心。

- **AI推論のEdge展開:** 軽量LLM（小型モデル・埋め込み生成）をEdgeで実行するユースケースが増加。ただしWasm制約とメモリ上限（128MB）を考慮し、重い推論はAI Gatewayを介してバックエンドに委譲するアーキテクチャが現実的。

- **可観測性の整備が必須:** Edge環境はデバッグが難しく、`@vercel/otel`によるOpenTelemetryトレーシングの導入が2026年のベストプラクティス。分散トレースなしでのEdge最適化は「計測なき最適化」になるリスクが高い。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded Typesが標準的なプラクティスとなり、プリミティブ型の混同によるバグをコンパイル時に防止できる。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` が2026年には広く定着し、型推論を維持しながら型チェックを行えるため、`as` キャストへの依存を大幅に削減できる。

- **Zod + tRPC によるEnd-to-Endな型安全性:** スキーマ定義からAPIレスポンス・フォームバリデーションまで単一のZodスキーマで管理するパターンが主流となり、フロント・バック間の型ズレが構造的に排除される。

- **Template Literal Types の実用化:** ルーティングや翻訳キーに `type Route = '/users' | '/users/${string}'` のような型を使うことで、文字列ベースのAPIでも補完と型チェックが効く。

- **`noUncheckedIndexedAccess` の標準化:** `tsconfig.json` でこのオプションをオンにするプロジェクトが増え、配列・オブジェクトのインデックスアクセスが常に `T | undefined` として扱われ、実行時エラーの温床を設計段階で潰せる。
