# CTO Knowledge - 2026-10-02

## Daily Update (2026-10-02)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 15以降で導入されたPPRがNext.js 16で安定版となり、静的シェルと動的コンテンツを同一ルートで組み合わせられるため、TTFBを維持しつつパーソナライズされたUIを配信できる。物件詳細ページのような「基本情報は静的、空室状況は動的」という構成に特に有効。

- **Turbopackのビルド/devサーバー標準化:** Turbopackがデフォルトビルドツールとして定着し、webpack比で大幅な高速化（devサーバー起動・HMR）が得られる。CIのビルド時間短縮にも直結するため、`bun run build`のパイプライン全体のレイテンシ削減が見込める。

- **React Server Components + Server Actionsの境界最適化:** クライアントバンドルサイズを削るには「本当にインタラクティブなコンポーネントだけ`'use client'`にする」という原則が引き続き重要。引越し費用計算や問い合わせフォームなど、フォーム系はServer Actionsに寄せることでJS転送量を削減できる。

- **`next/image`とキャッシュ戦略の見直し:** 物件写真のような画像中心のUIでは、`next/image`のAVIF/WebP自動変換に加え、Cache Componentsによる`fetch`レベルの粒度の細かいキャッシュ制御（revalidateタグ）が、物件一覧の鮮度とパフォーマンスの両立に効く。

- **Edge RuntimeとStreaming SSRの使い分け:** 全ページをEdgeに寄せるのではなく、認証チェックなど低レイテンシが必要な部分のみEdge Middlewareで処理し、重い処理はNode runtime + Streamingで段階的にレンダリングする設計が、コストとパフォーマンスのバランスとして主流になっている。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16のPartial Prerendering (PPR) が安定版となり、静的シェルを即座に返しつつ動的部分だけをストリーミングする構成が標準化している。TTFBを犠牲にせずパーソナライズされたコンテンツを出せるため、物件一覧ページのような「静的なレイアウト＋動的な検索結果」に最適。

- **ポイント2:** Suspenseバウンダリの粒度設計がパフォーマンスの肝になっている。粒度が粗いとウォーターフォールが発生し、細かすぎるとレイアウトシフトが増えるため、物件詳細ページでは「価格・基本情報」「前の住人の活動歴」「写真ギャラリー」を独立したバウンダリに分けるのが実用的。

- **ポイント3:** Server Actionsのストリーミングレスポンス対応が進み、フォーム送信後の結果を段階的に返せるようになった。問い合わせフォームや内見予約フローで「送信中→検証中→確定」のような段階的UIが実装しやすくなっている。

- **ポイント4:** キャッシュ戦略（`use cache`ディレクティブ）とストリーミングの組み合わせが重要になっており、物件データのような更新頻度が低いコンテンツはキャッシュ、空室状況など頻繁に変わるデータだけをストリーミングで最新化する使い分けが、インフラコストとUXの両立に直結する。

- **ポイント5:** エッジランタイムでのRSCストリーミングが実用段階に入り、地理的に分散したユーザーへのTTFB改善が見込める。ただしBunとの互換性やエッジ特有の制約（DBコネクション等）を検証してから導入判断すべき。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCのようなend-to-end型安全アプローチが、TypeScriptモノレポ内のBFF/内部APIでGraphQLを置き換えつつある。クライアント・サーバー間でスキーマ生成なしに型が共有できるため、開発速度が上がる一方、外部公開APIには向かない。
- **ポイント2:** GraphQLは「複数クライアント・複雑なデータグラフ」を持つtoC向け大規模サービスで依然強いが、N+1問題やキャッシュ設計の複雑さから、中小規模プロダクトでは採用コストが見合わないケースが増えている。
- **ポイント3:** RESTはOpenAPI/JSON Schemaとの組み合わせでcodegenが成熟し、「シンプルで枯れた技術」として外部公開API・パートナー連携のデフォルトであり続けている。
- **ポイント4:** 2026年の実務トレンドは「単一技術で統一」ではなくハイブリッド構成 — 内部通信はtRPC、外部公開はREST(OpenAPI)、複雑な集約が必要な画面のみGraphQLという使い分けが主流になっている。
- **ポイント5:** sumitsugiのようなNext.js App Router + Bunスタックでは、tRPCを採用するとServer ComponentsやServer Actionsとの責務分担が曖昧になりやすいため、まずはServer Actions + Zodバリデーションで内部APIを簡潔に保ち、外部連携が必要になった時点でREST/OpenAPIを追加する段階的アプローチが現実的。

### 4. serverless edge computing 2026

- **ポイント1:** 2026年はCloudflare Workers・Vercel Edge Functions・Deno DeployがV8 isolateベースでコールドスタートをほぼゼロ化しており、SSRやAPIルートをエッジ実行することでTTFBを大幅短縮できる。sumitsugiのような物件検索・一覧ページはエッジキャッシュ+ISRの組み合わせでグローバルな応答速度改善が見込める。

- **ポイント2:** エッジでのDB直接アクセスが現実的になり、Cloudflare D1やTurso（libSQL）、Neonのエッジ対応ドライバーが普及。読み取り中心の物件検索APIはリージョン分散レプリカ+エッジ実行で、DBレイテンシ自体をユーザー近傍に持ち込める。

- **ポイント3:** Next.js 16のPartial Prerendering（PPR）とエッジランタイムの組み合わせが標準化しつつあり、静的シェル+動的パーツのストリーミングでSEOとパーソナライズを両立できる。前の住人の情報やレビューなど動的要素を含むページでも初期表示を高速に保てる。

- **ポイント4:** エッジ実行はNode.js API非互換（fsアクセス不可、一部npmパッケージ非対応）という制約が依然残るため、認証・決済など複雑なロジックは引き続きサーバーレス（Node runtime）かコンテナに置き、エッジは「軽量・高頻度・地理分散が効く」処理（リダイレクト、A/Bテスト、画像最適化、簡易API）に限定する設計判断が重要。

- **ポイント5:** コスト面ではエッジ実行は従量課金でリクエスト数に強く比例するため、トラフィックが伸びた際の予算予測が難しい。MVPローンチ前のこの段階では、まず静的ページ+CDNキャッシュで様子を見て、実測トラフィックを見てからエッジ移行箇所を選別するのが安全。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への本格移行:** パスワードレス認証（WebAuthn/Passkeys）がブラウザ・OS標準でサポートされ、フィッシング耐性の高い認証手段として主流化。sumitsugiのような個人間取引プラットフォームでは、アカウント乗っ取りリスク低減のため早期導入が有効。

- **継続的リスクベース認証:** ログイン時の一発認証ではなく、デバイス・位置情報・行動パターンを基にしたリスクスコアリングで、怪しいセッションのみ追加認証（MFA）を要求する方式が標準化。UXを損なわずセキュリティを強化できる。

- **トークン窃取対策の強化（DPoP/Token Binding）:** JWTやセッショントークンが漏洩してもリプレイ攻撃を防ぐため、トークンを特定のクライアント/デバイスに紐付けるDPoP（Demonstrating Proof-of-Possession）の採用が広がっている。決済・個人情報を扱うsumitsugiでは優先度高。

- **認可ロジックの最小権限・ゼロトラスト化:** 「前の住人」「次の住人」間のデータアクセスなど、ロール別の認可境界をAPIレイヤーで厳格に検証し、IDOR（Insecure Direct Object Reference）を防ぐことが重要。Supabase RLS等のDBレベル制御との二重防御が推奨される。

- **セッション管理のサーバーサイド強制失効:** パスワード変更・不審なアクティビティ検知時に全デバイスのセッションを即座に無効化できる仕組み（リフレッシュトークンのrevocationリスト等）が必須要件として定着しつつある。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORM の進化（Rust脱却とパフォーマンス改善）:** Prisma 6以降でクエリエンジンがTypeScript/WASMベースに移行し、コールドスタートの高速化とバンドルサイズ削減が進んでいる。Supabaseのようなサーバーレス環境と組み合わせる際、Edge FunctionsでのPrisma利用が現実的になった点は、ローンチ後のAPI応答速度に直結する。

- **Supabase Row Level Security (RLS) とPrismaの併用設計:** PrismaはRLSを直接扱えないため、認証済みユーザーのDBアクセスをどう守るか（Supabase AuthのJWTをPostgresセッションに渡す、もしくはPrismaはサービスロール専用にしてRLSはSupabase Client経由のみで使う）という設計判断が必須。弊社の「前の住人」「次の住人」間のデータ分離（他ユーザーの物件情報・個人情報保護）を考えると、RLSを信頼境界として明示的に設計すべき。

- **コネクションプーリング（PgBouncer/Supavisor）の必須化:** Supabaseはサーバーレス関数からの大量同時接続を前提にSupavisor（旧PgBouncer）をデフォルト提供しており、Prismaの`DATABASE_URL`をpooler経由、マイグレーション用に直接接続用の`DIRECT_URL`を分ける構成が標準パターンになっている。Vercel等にデプロイする際、これを誤ると本番で接続枯渇エラーが頻発するため、MVPローンチ前に必ず確認すべき項目。

- **スキーマ駆動開発とマイグレーション運用の分離:** `prisma migrate dev`（開発）と`prisma migrate deploy`（CI/CD）を明確に分け、Supabase側のダッシュボードから直接スキーマ変更をしないルールを徹底するチームが増えている。物件ステータス（`draft`/`public`）のようなenum変更時に、Prismaスキーマを唯一の真実源（Single Source of Truth）とすることで、ユニオン型の整合性管理がしやすくなる。

- **pgvector + Prismaによる検索/レコメンド機能への布石:** SupabaseはpgvectorをネイティブサポートしておりPrismaからも`Unsupported("vector")`型経由で扱える。将来的に「前の住人の暮らし」と「次の住人の希望」のマッチング精度を上げる機能（IC consultation matching、物件類似検索）を見据えるなら、今のうちにベクトル検索を見据えたテーブル設計をしておく価値がある。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC（WebAssembly Garbage Collection）がブラウザ主要エンジンで安定版となり、RustでもGC連携を意識したコンパイル戦略が重要になっている。ただしRust自体はGC不要な言語設計のため、既存のlinear memoryモデルの方が依然パフォーマンス優位。
- **ポイント2:** `wasm32-wasip2`やComponent Modelの普及により、Rust製WasmモジュールをWASI経由で複数言語・複数ランタイム間で安全に合成できるようになり、サーバーサイド（Cloudflare Workers、Fastly等）での採用が加速している。
- **ポイント3:** SIMD128とマルチスレッド（`wasm-bindgen` + Web Workers / shared memory）の組み合わせが実用段階に入り、画像処理・ML推論など計算負荷の高いワークロードでネイティブの70-90%程度の性能に近づいている。
- **ポイント4:** バイナリサイズ最適化（`wasm-opt`、`twiggy`での分析、`#![no_std]`構成）が引き続き重要な差別化要因で、コールドスタート速度が求められるエッジ/サーバーレス環境ではRustの型安全性とゼロコスト抽象化が選定理由になりやすい。
- **ポイント5:** sumitsugiのようなNext.js主体のプロダクトでは、重い計算（画像変換・PDF生成・地理データ処理等）を部分的にRust/Wasmへオフロードする設計が、Node.js側のCPUバウンド処理のボトルネック回避策として現実的な選択肢になり得る。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** 静的シェルと動的コンテンツを1つのルートで共存させ、初回表示を高速化しつつパーソナライズ領域だけSuspenseでストリーミングする設計が標準化。sumitsugiの物件一覧ページのような「静的なレイアウト＋動的な空室状況」構成に適用すると初期表示速度を大きく改善できる。

- **"use cache" ディレクティブによる明示的キャッシュ制御:** fetchベースの暗黙キャッシュから、関数・コンポーネント単位で`cacheLife`/`cacheTag`を指定する明示的モデルへ移行。データ更新頻度に応じてキャッシュ戦略を細かく制御できるため、物件データのような更新頻度が異なるリソースの再検証ロジックが書きやすくなる。

- **Server Actions のセキュリティ強化パターン定着:** Server Actionを「公開APIエンドポイント」として扱い、Zodによる入力検証・認可チェック・レート制限をアクション内に必ず組み込むパターンが業界標準に。認証・決済系のフォームではこの徹底が特に重要で、standards.mdのZod必須ルールとも合致する。

- **Turbopackのビルド安定化による開発体験向上:** devだけでなく`next build`でもTurbopackが既定になり、大規模コードベースでもビルド時間が大幅短縮。ただし一部のWebpackプラグイン依存ライブラリは移行が必要なため、依存関係の棚卸しを早めに行う価値がある。

- **Parallel Routes / Intercepting Routesによるモーダル型UXの一般化:** 物件詳細のモーダル表示や予約フローのステップ遷移をURL駆動で実装するパターンが定着し、ブラウザの戻る/進むやディープリンクとの整合性を保ちながらリッチなUXを実現できる。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化:** Edge Runtimeは V8 isolateベースのため起動が数ms単位だが、2026年時点では依存バンドルの肥大化（特に外部SDKや重いpolyfill）がボトルネック化しやすい。`edge-light`条件分岐でNode専用コードを除外し、バンドルサイズを継続的に計測することが重要。

- **Fluid Compute / 自動スケーリングとの併用:** VercelのFluid Computeモデルにより、Edge FunctionsとServerless Functionsの使い分けがより柔軟になっている。レイテンシ重視の軽量処理（認証チェック、リダイレクト、A/Bテスト振り分け）はEdgeに、DB接続やSDK依存の重い処理はFluid/Node runtimeに寄せる設計が定石。

- **リージョン近接配信とDBレイテンシの罠:** Edge Functionsはグローバル分散で実行されるが、バックエンドDB（Postgres等）が単一リージョンの場合、Edge→DB間の往復レイテンシがかえって悪化するケースがある。Neon/PlanetScaleのようなエッジ対応DBやコネクションプーラー（PgBouncer, Prisma Accelerate）の併用が必須。

- **キャッシュ戦略の一体化:** `next: { revalidate }` やVercel Data Cache、ISRとEdge Middlewareを組み合わせたスタイル推奨チャェーンが主流に。Edge Functionでの個人化処理と、静的配信のキャッシュヒット率を両立させる設計（キャッシュキーの分離）が性能差を生む。

- **可観測性の強化:** Edge環境ではNode標準のプロファイラが使えないため、OpenTelemetry対応のVercel Observabilityやログドレインを初期段階から組み込み、isolateごとの実行時間・メモリ超過をモニタリングする体制が2026年のベストプラクティスとして定着している。

### 10. TypeScript type safety patterns 2026

- **ポイント1: `satisfies`演算子とconst型パラメータの定着:** TypeScript 5.x系で導入された`satisfies`は型推論を保ったまま型チェックができるため、Zodスキーマやconfig定義で型の広がりを防ぐ標準パターンとして定着。`const`型パラメータ（`<const T>`）と組み合わせることで、リテラル型の自動保持がボイラープレートなしで実現できる。

- **ポイント2: Zodなど「スキーマファースト」なランタイム検証の標準化:** 型は コンパイル時にしか効かないため、API境界（フォーム入力・外部API応答）では`z.infer<typeof schema>`でスキーマから型を導出する設計が主流に。`standards.md`にある「入力検証はZodスキーマで」という方針通り、型安全性とランタイム安全性を一体化できる。

- **ポイント3: Discriminated UnionによるStateの排他的表現:** `status: 'draft' | 'public'`のようなUnion型を使う場合、各状態に応じたプロパティ違いがあるなら単純なUnionでなくdiscriminated union（`{status: 'draft'} | {status: 'public', publishedAt: Date}`）にすることで、`switch`文でのexhaustiveness check（`never`型を使った網羅性チェック）がコンパイル時に効き、新しいstatus追加時の漏れをビルドエラーで検出できる。

- **ポイント4: テンプレートリテラル型とBranded Typeによるドメイン制約:** IDや単位付き数値（例: `UserId`, `ListingId`）を単純な`string`/`number`ではなくBranded Type（`type UserId = string & { __brand: 'UserId' }`）で区別することで、取り違えバグをコンパイル時に防止。テンプレートリテラル型はルーティングパスやイベント名のパターン制約に活用が進んでいる。

- **ポイント5: 型レベルテストの一部導入（コストと効果のバランス重視）:** `tsd`やVitestの`expectTypeOf`で型定義自体をテストする動きが増えているが、過剰適用は保守コストが高いため、公開APIの型シグネチャや複雑なユーティリティ型など「壊れたら影響が大きい箇所」に限定して導入するのが2026年の実務的なベストプラクティス。
