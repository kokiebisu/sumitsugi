# CTO Knowledge - 2026-04-26

## Daily Update (2026-04-26)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本番活用:** Next.js 15以降でPPRが安定化し、静的シェルと動的コンテンツを単一リクエストで配信できるようになった。Suspense境界の設計が収益に直結するため、初期設計での粒度選択が最重要。

- **React Server Components + Server Actions のフル活用:** クライアントバンドルサイズを劇的に削減できるが、`"use client"`の乱用がボトルネックになりやすい。コンポーネントツリーのどこでデータ取得するかを設計段階で決める習慣が必要。

- **`next/cache` とオンデマンド再検証の精緻化:** `revalidateTag` / `revalidatePath` によるきめ細かいキャッシュ無効化が標準パターンに。CDNキャッシュとの二重管理を避けるため、キャッシュ戦略をインフラ込みで一元設計すること。

- **Turbopack の実用段階移行:** 2026時点でTurbopackがデフォルトビルダーとして成熟しつつあり、大規模モノレポでのビルド時間が従来比60〜80%削減される事例が増加。ただし一部プラグイン非互換が残るため、移行前の互換性監査は必須。

- **Core Web Vitals の INP 対応:** LCP・CLSに続きINP（Interaction to Next Paint）が評価軸として定着。`useTransition` / `useDeferredValue` による優先度付きレンダリングと、Server Actionsの楽観的UI更新パターンの組み合わせが実践的な対策となっている。

### 2. React Server Components streaming 2026

- **Suspense境界の細粒度設計が鍵:** 2026年時点では、RSCストリーミングの効果を最大化するためにSuspense境界を粗くではなく細かく設計することが定着しており、TTFBを維持しながらLCPを大幅に改善できる。

- **PPR（Partial Prerendering）の本格普及:** Next.js 15以降でPPRが安定化し、静的シェルを即時配信しつつ動的なRSCチャンクをストリームするハイブリッドモデルが実用的な選択肢になっている。

- **キャッシュ戦略の複雑化に注意:** `fetch`のキャッシュ、Route Cache、Full Route Cacheの3層が絡み合うため、ストリーミング環境でのキャッシュ無効化設計を最初から考慮しないと、スタールなデータが配信されるリスクがある。

- **エラーバウンダリとストリーミングの連携:** ストリーミング中にサーバーエラーが発生した場合の`error.tsx`のスコープ設計が重要で、境界が広すぎると部分的な失敗がページ全体のフォールバックを引き起こす。

- **Bundle分析とServer/Client境界の継続的監視:** `"use client"`ディレクティブの配置ミスでクライアントバンドルが肥大化するケースが増えており、CI上での`@next/bundle-analyzer`や`next build`の出力監視を自動化することがベストプラクティスとして定着している。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年時点でtRPCはNext.js/TypeScriptスタックで事実上の標準に近づきつつあり、スキーマ定義不要でクライアント・サーバー間の型共有が実現できるため、小〜中規模チームの開発速度を大幅に向上させる。

- **GraphQLの使いどころが明確化:** GraphQLは複雑なデータグラフ（複数サービスの集約、モバイル向け柔軟クエリ）に有効だが、オーバーエンジニアリングになりやすいため、単純なCRUDにはRESTかtRPCが依然として適切という棲み分けが定着している。

- **REST+OpenAPIの堅牢性は健在:** 公開APIや外部パートナー連携ではOpenAPI 3.1仕様に基づくRESTが引き続き主流であり、`zod-openapi`などのツールでTypeScript型とスキーマを単一ソースから生成するパターンが普及している。

- **エッジ・ストリーミング対応が設計の必須要件に:** Vercel/Cloudflare Workers上でのエッジデプロイが一般化し、APIレスポンスのストリーミング（`ReadableStream`/Server-Sent Events）やPartial Prerendering対応を設計段階から考慮しないと後からの改修コストが高くなる。

- **Contract-First開発とAI生成コードの品質管理:** AIコード生成ツールの普及により、APIスキーマを先に定義する「Contract-First」アプローチが重要性を増している——スキーマなしにAI生成コードを統合すると型の不整合が蓄積しやすく、`Zod`や`TypeSpec`でスキーマを中心に据えることが品質担保の鍵となる。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジのデファクトランタイムに:** V8アイソレートに加えWasmが主流となり、Cloudflare Workers・Fastly Compute等でポータブルなマルチ言語実行が可能になった。コールドスタートはほぼゼロに近づき、ネイティブに近いパフォーマンスを実現している。

- **エッジでのAI推論が実用フェーズへ:** 量子化された小型LLM（1B〜7Bパラメータ）をエッジノードで直接実行するユースケースが急増。レイテンシ削減とデータ主権の両立が主な採用動機となっている。

- **データの重力問題がボトルネックに:** 計算はエッジに移っても、データストアは中央集権のままでRTTが発生するケースが多い。Cloudflare D1・Turso等の分散SQLや、エッジネイティブなKVストアとの組み合わせ設計が必須になっている。

- **オブザーバビリティの難易度が急上昇:** リクエストが数百のエッジPOPに分散するため、従来の集中型APMでは追跡が困難。OpenTelemetryのエッジ対応と、分散トレーシングを前提としたアーキテクチャ設計が開発ベストプラクティスとして定着しつつある。

- **コスト構造の再設計が必要:** エッジはリクエスト単価が低い一方、エグレス費用とストレージ同期コストが予想外に膨らむ事例が増加。「何をエッジで、何をリージョンで」というレイヤー分離の判断基準を明示的にアーキテクチャドキュメントに落とし込むことが重要。

### 5. authentication security best practices 2026

- **パスキー（Passkey）の本格採用:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の標準となり、フィッシング耐性とUX向上を両立できる。主要ブラウザ・OSがサポート済みのため、新規実装ではパスワードより優先すべき。

- **セッション管理の短命化とリフレッシュ戦略:** アクセストークンの有効期限を15分以内に抑え、リフレッシュトークンのローテーション（RTR）を徹底することでトークン漏洩時の被害を最小化する。

- **デバイスバインディングの強化:** 認証トークンをデバイス固有の鍵（TPM/Secure Enclave）に紐付け、トークン窃取によるセッションハイジャック（Pass-the-Token攻撃）を防ぐ手法が主流になりつつある。

- **継続的認証（Continuous Authentication）:** ログイン時のみ認証するのではなく、行動分析・リスクスコアリングを用いてセッション中も継続的にユーザーを検証し、異常検出時に再認証を要求するゼロトラスト設計が求められる。

- **OAuth 2.1 / DPoP の標準化:** OAuth 2.0の脆弱なフロー（Implicit、ROPC等）が廃止され、DPoP（Demonstrating Proof of Possession）によるトークンとクライアントの紐付けが推奨標準となっている。既存の認証基盤はOAuth 2.1準拠への移行を計画すべき。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x の Edge Runtime 対応成熟:** Prisma Client が Cloudflare Workers・Vercel Edge Functions に完全対応し、接続プーリング（Prisma Accelerate）と組み合わせることでサーバーレス環境でのコールドスタート問題がほぼ解消された。

- **Supabase の pgvector 活用が主流に:** AI 機能統合において Supabase + pgvector の組み合わせが標準パターンとなり、外部ベクトルDBを別途用意するコストを削減しながら RLS（Row Level Security）でデータアクセス制御を一元管理できる。

- **Prisma + Supabase の接続管理はコネクションプーラー必須:** Supabase は PostgreSQL の直接接続数に制限があるため、Supabase の組み込み PgBouncer または Prisma Accelerate を必ず挟む構成が推奨されており、これを省略するとスケール時に接続枯渇が起きる。

- **型安全なマイグレーション戦略の二分化:** `prisma migrate` による宣言的マイグレーションと、Supabase CLI の `supabase db diff` を併用するプロジェクトが増えているが、両者を混在させると driftが生じるため、どちらを「Source of Truth」にするかをチームで明確に決定する必要がある。

- **RLS と Prisma の統合に注意:** Supabase の RLS ポリシーは Prisma 経由のクエリにも適用されるが、サービスロール（`service_role`）キーを使うと RLS をバイパスするため、バックエンド API での権限分離設計を慎重に行わないとセキュリティホールになる。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の実用化:** 2026年現在、WASI Preview 2が広く採用され、RustからWasmコンポーネントを生成する`cargo component`ツールチェーンが安定。モジュール間の型安全なインターフェースが実現し、マイクロサービス的なWasm分割アーキテクチャが現実的になった。

- **GCとメモリ管理の改善:** WasmGC proposalの普及により、Rustのゼロコスト抽象化と組み合わせることでJSランタイム比で3〜10倍のスループットが計測されるケースが増加。特にCPU負荷の高い演算処理（画像・音声・暗号）での採用が加速している。

- **SIMD・スレッド対応の成熟:** Wasm SIMD命令とShared Memoryスレッドが主要ブラウザで安定稼働。Rustの`rayon`や`std::simd`とほぼそのまま組み合わせられ、ネイティブ比80〜90%のパフォーマンスが実戦投入レベルに達した。

- **エッジ実行環境の主流化:** Cloudflare Workers・Fastly Compute・WasmEdgeなどがRust+Wasmをファーストクラスサポート。コールドスタートがコンテナ比100倍以上高速なため、レイテンシクリティカルなAPIをRustで書いてWasmデプロイする構成がスタンダードになりつつある。

- **ツールチェーン成熟によるDX向上:** `wasm-bindgen`・`wasm-pack`の次世代として`wit-bindgen`が台頭し、ホスト言語（JS/Python/Go）との型バインディング生成が自動化。ボイラープレートが激減し、Rustに不慣れなチームでもWasm統合のコストが大幅に下がっている。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** クライアントコンポーネントは状態・インタラクションが必要な最小単位に限定し、`'use client'` 境界を葉ノードに押し込むことでバンドルサイズを大幅に削減できる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的ストリームを同一ルートで共存させる PPR が安定化し、従来の SSG/SSR の二択から解放される設計が主流になりつつある。

- **`use cache` / `use server` ディレクティブによる細粒度キャッシュ:** Next.js 15 以降の `cacheTag` / `revalidateTag` を組み合わせることで、ページ単位ではなく関数単位でキャッシュ戦略を制御でき、過剰な再検証を避けられる。

- **Server Actions を TRPC 代替として使う動き:** `'use server'` 関数を型安全な RPC として活用するパターンが普及し、API Routes レイヤーを省いたフルスタック設計が現実的な選択肢になっている。

- **Parallel Routes + Intercepting Routes によるモーダル UX:** URL を維持しながら重ねて描画する intercept パターンが複雑化しがちなため、`@slot` 設計は早期にルート構造図に落として管理しないと技術的負債になりやすい。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択戦略:** Node.js RuntimeとEdge Runtimeの使い分けが重要で、コールドスタートを最小化するためにはEdge Runtimeを優先しつつ、Node.js APIが必要な処理はServer Functionsに分離するパターンが主流になっている。

- **Fluid computeの活用:** Vercelが2025年に導入したFluid computeモデルにより、リクエスト間でのサーバーリソース共有が可能になり、従来の「1リクエスト=1インスタンス」から脱却してコスト効率と応答性が大幅に向上している。

- **ISR + Edge Cachingの組み合わせ:** Incremental Static RegenerationとEdge Cacheを組み合わせることで、動的コンテンツでもTTFBを50ms以下に抑えられる設計が現実的になっており、`revalidate`の粒度をルート単位で細かく制御することが鍵となる。

- **バンドルサイズの厳格管理:** Edge Functionsには1MBのサイズ制限があり、`import`するライブラリのTree-shakingを徹底し、重量級の依存（例: `moment.js`や大型ORM）をEdge層から排除してServer層に移す設計が不可欠。

- **Observabilityの強化:** Edge層はデバッグが難しいため、Vercel LogsとOpenTelemetryを組み合わせたトレーシングを初期から組み込み、`waitUntil()`を使った非同期ログ送信でレイテンシに影響を与えない計装を行うことがベストプラクティスとなっている。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の主流化:** TypeScript 4.9以降の`satisfies`が2026年では標準的なパターンとなり、型推論を維持しつつ型チェックを強制できるため、`as`キャストの乱用を大幅に削減できる。

- **Template Literal Types によるAPIの型安全性:** REST APIのエンドポイントやイベント名をTemplate Literal Typesで表現するパターンが普及し、ランタイムエラーをコンパイル時に検出できる設計が主流になっている。

- **`noUncheckedIndexedAccess`の有効化が実質必須:** 配列・オブジェクトのインデックスアクセス時に`undefined`を含む型を返すこのオプションが、堅牢なコードベースでは標準設定となり、境界外アクセスによるバグを根絶する。

- **Branded Types によるドメインモデルの厳密化:** `type UserId = string & { readonly _brand: 'UserId' }` パターンでプリミティブ型を区別し、IDの取り違えなどのロジックバグをコンパイル時に防ぐDDD的アプローチが広がっている。

- **`zod` + `infer` による単一ソース原則:** バリデーションスキーマからTypeScript型を`z.infer`で自動導出し、スキーマと型定義の二重管理を排除するパターンが、特にAPIバウンダリで事実上の標準となっている。
