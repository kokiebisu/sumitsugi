# CTO Knowledge - 2026-04-22

## Daily Update (2026-04-22)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチ・重いロジックはサーバーコンポーネントに集約する。2026年時点でRSCは安定成熟しており、`"use client"`の乱用はパフォーマンス負債になる。

- **Partial Prerendering (PPR) の本番導入:** Next.js 15以降で安定化したPPRにより、静的シェルを即時配信しつつ動的コンテンツをストリーミングする設計が標準化。ISRとSSRのトレードオフを解消する重要なパターン。

- **Turbopack の活用でビルド高速化:** Webpackからの移行が完了しつつあり、大規模プロジェクトでのHMRが数倍高速化。開発体験の向上だけでなく、CI/CDパイプラインのビルド時間短縮にも直結する。

- **Image / Font 最適化の継続強化:** `next/image`のCumulative Layout Shift (CLS) ゼロ運用と`next/font`によるフォント自己ホスティングは今や必須。Core Web Vitalsへの影響が大きく、SEOと実体験両面で優先度が高い。

- **Edge Runtime とキャッシュ戦略の設計:** `fetch`のキャッシュ粒度制御（`revalidate`、`cache: 'no-store'`）と、Edge Middlewareによる認証・リダイレクト処理の分離が、APIレイテンシとTTFBを決定づける。キャッシュ設計はアーキテクチャ初期に確定すべき。

### 2. React Server Components streaming 2026

- **Streaming SSRの成熟:** React 19 + Next.js 15以降、`Suspense`境界を活用したストリーミングSSRが実運用レベルに達し、TTFBを維持しながらFCPを大幅に改善できる設計パターンが確立されつつある。

- **Server Componentsとクライアントの境界管理:** `"use client"`ディレクティブの粒度設計がパフォーマンスの鍵であり、インタラクティブな部分のみをクライアントコンポーネント化することでJSバンドルサイズを40〜60%削減できるケースが報告されている。

- **Partial Prerendering（PPR）の台頭:** Next.js 15でStableになったPPRは、静的シェルを即座に配信しつつ動的コンテンツをストリームする手法で、CDNキャッシュとストリーミングの両立という従来のトレードオフを解消する。

- **データフェッチの並列化設計が必須:** `Promise.all`や`React.use()`を活用したウォーターフォール排除が、Server Components環境でのレイテンシ改善の最重要施策であり、シリアルフェッチは即座にボトルネックになる。

- **エラー境界とローディング状態のUX設計:** `error.tsx`と`loading.tsx`のネスト設計が複雑化しており、Streaming環境では部分的な失敗をどの粒度でハンドリングするかを事前にアーキテクチャレベルで定義しておかないと、本番障害時のユーザー体験が崩壊するリスクがある。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの成熟とフルスタック型安全性の標準化:** 2026年時点でtRPCはNext.js/Remixエコシステムで事実上の選択肢となり、フロントエンド・バックエンド間の型共有が「あって当然」の水準になった。新規プロジェクトでREST+手書きOpenAPIを選ぶコストが相対的に上がっている。

- **GraphQLの適用領域の再定義:** GraphQLは「何でもGraphQL」から「複数データソースの統合レイヤー（Federation）」に用途が絞られつつある。単一チームの内部APIにGraphQLを採用するケースは減少し、マイクロサービス間の公開APIやBFF層での採用が主流。

- **REST+OpenAPI 4.0の復権:** OpenAPI 4.0（Arazzo）の仕様策定が進み、コード生成ツール（Orval、Hey APIなど）の品質向上でREST APIの開発体験が大幅に改善。外部公開APIやサードパーティ連携ではRESTがまだ圧倒的に有利。

- **エッジ・ストリーミングAPIの台頭:** Vercel AI SDKやCloudflare Workersの普及により、Server-Sent Events / ReadableStreamを使ったストリーミングAPIが設計の必須考慮事項に。REST/tRPC問わず「ストリーム対応できるか」がAPI設計の新たな評価軸になっている。

- **契約駆動開発（Contract-First）の再評価:** AIによるコード生成が増えた結果、スキーマ・型定義を先に書いてからコードを生成する契約駆動アプローチの価値が再認識されている。tRPCのZodスキーマ、GraphQLのSDL、OpenAPIのYAMLいずれもAIとの相性が良い。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジの標準ランタイムに:** CloudflareWorkers・Fastly Compute@Edgeを中心にWasmが本格普及し、コールドスタートほぼゼロ・言語非依存のエッジ実行が現実的な選択肢になった。Rustや Go製のビジネスロジックをそのままエッジにデプロイするパターンが増加している。

- **エッジDBの成熟でステートフルな処理がエッジに移行:** Cloudflare D1・Turso（libSQL）・Neon Branchingなど分散SQLが安定稼働し、「エッジはステートレス」という前提が崩れた。レイテンシ重視のリード処理をエッジに寄せ、書き込みはリージョナルに集約するアーキテクチャが主流になりつつある。

- **AI推論のエッジオフロードが加速:** 軽量LLM（Gemma・Phi系）をエッジノードで実行しバックエンドへのラウンドトリップを削減する構成が現実的になった。プライバシー規制の厳しいEU/日本市場ではデータをオリジンから出さないエッジ推論が競争優位になる。

- **エッジ-クラウド間のオーケストレーション複雑性が課題:** 実行環境が「エッジPOP・リージョナルクラウド・オンプレ」に分散するにつれ、デプロイパイプラインやオブザーバビリティ（分散トレーシング）のコストが増大している。OpenTelemetryのエッジ対応と、Terraform/Pulumi での統合IaCが必須投資になっている。

- **コスト構造の再評価が必要:** エッジは安価に見えるが、リクエスト数課金＋データ転送費でトラフィック急増時に想定外のコストスパイクが起きるケースが増えた。キャッシュ戦略とエッジ実行範囲の設計段階での精緻化（何をエッジに置き何をオリジンに残すか）がアーキテクチャ上の最重要判断になっている。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** FIDO2/WebAuthn標準に基づくパスキーが主要ブラウザ・OSで広くサポートされ、パスワードレス認証が現実的な選択肢になった。フィッシング耐性が高く、UXも向上するため、新規サービスではデフォルト採用を検討すべき。

- **セッション管理の厳格化:** JWTの有効期限を短く（15分以下）設定し、リフレッシュトークンのローテーションを必須化する。トークン窃取対策として、Sender-Constrained Token（DPoP）の採用が2026年のベストプラクティスとなっている。

- **MFAの義務化とフィッシング耐性:** SMS/TOTPベースのMFAはSIMスワップ攻撃に脆弱なため、ハードウェアキーまたはパスキーへの移行を推進。特に管理者アカウントはフィッシング耐性MFAを必須とするポリシーが標準化されつつある。

- **継続的認証（Continuous Authentication）:** ログイン時の一点認証ではなく、行動バイオメトリクスやリスクスコアリングを用いてセッション中も継続的にユーザーを検証するゼロトラストアーキテクチャが実用段階に入った。

- **サプライチェーン攻撃への対策:** OAuthフロー経由のサードパーティ認証ライブラリが攻撃ベクターになるケースが増加。依存パッケージの定期監査とSBOM（ソフトウェア部品表）管理を認証基盤にも適用することが求められる。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のエッジランタイム対応強化:** Prisma Accelerate により、Next.js Edge Runtime / Cloudflare Workers での接続プーリングが本番利用レベルに達した。Supabase との組み合わせでグローバル低レイテンシを実現できる構成が現実的になっている。

- **Supabase の RLS (Row Level Security) をORM層と分離して考える:** Prisma はRLSを自動管理しないため、マルチテナント設計では `SET LOCAL role` による Supabase の RLS ポリシーと Prisma のクエリ層を明確に責務分離する必要がある。混在させるとセキュリティホールになる。

- **型安全なリアルタイム機能の統合:** Supabase Realtime + Prisma の組み合わせはまだ公式統合がなく、リアルタイム更新は Supabase クライアントSDK側で受け取り、スキーマ型は Prisma 側で管理するというハイブリッドパターンが主流。型の一元管理に工夫が必要。

- **マイグレーション管理の二重化問題:** Supabase には独自の `supabase db push` があり、Prisma Migrate と競合しやすい。2026年時点では **Prisma をスキーマのソースオブトゥルース** として `prisma migrate deploy` に統一し、Supabase CLI はローカル開発環境のみに限定するパターンが安全。

- **Branching (Supabase) × Preview Deploy の組み合わせ:** Supabase の Database Branching 機能とVercel Preview Deploymentを連携させることで、PRごとに独立したDBスナップショット環境を自動構築できる。CI/CDのE2Eテスト信頼性が大幅に向上するため、チーム規模が拡大する前に設計に組み込むべき。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の本格普及:** 2026年はWASI Preview 2が主流となり、RustからWasmコンポーネントを生成する`cargo component`ツールチェーンが安定。インターフェース定義（WIT）による型安全なABI自動生成で、ホスト間の移植性が大幅向上した。

- **Wasmtime／WasmEdgeのAOTコンパイル最適化:** JITに加えAOT（事前コンパイル）が実用段階に達し、コールドスタートがネイティブ比5〜10%以内に収束。サーバーレス・エッジ環境でのRust+Wasmスタックが、Node.jsを性能面で上回るケースが増えている。

- **SIMDおよびThreads拡張の標準化完了:** Wasm SIMD128とShared Memoryが全主要ランタイムで確実に動作し、Rustの`std::simd`やRayonベースの並列処理がWasm上でも効果を発揮。画像処理・ML推論ワークロードでネイティブ比80〜90%のスループットが達成可能。

- **メモリモデルの改善（GC提案・線形メモリ上限緩和）:** Wasm GC Proposalの普及でRustのスマートポインタ戦略との使い分けが明確化。線形メモリの64bit化（Memory64）も段階的に対応が進み、大規模データ処理時のアドレス空間制約が解消されつつある。

- **Rustツールチェーン統合の成熟:** `wasm-bindgen` / `wasm-pack`に加え、`wit-bindgen`が標準的な選択肢となり、フロントエンド（ブラウザ）・バックエンド（サーバーレス）双方で同一Rustコードベースを共有するモノレポ構成が現実的な設計パターンとして定着している。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点でのベストプラクティスは「クライアントコンポーネントは最小限に」。データフェッチ・認証チェックはすべてServer Component側で完結させ、`'use client'`はインタラクション境界のみに留める。

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降でStableになったPPRにより、静的シェルと動的コンテンツを同一ルートで混在可能。`<Suspense>`境界を意識的に設計することでTTFBとCLSを両立できる。

- **Server Actions でAPI Route削減:** フォーム送信・ミューテーション処理はServer Actionsに集約し、`/api/`エンドポイントを不必要に増やさない。ただしバリデーション（Zod）は必ずAction内で実施—クライアント側だけでは不十分。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15の`use cache`はページ単位ではなく関数・コンポーネント単位でキャッシュ戦略を定義できる。`cacheLife`・`cacheTag`と組み合わせてオンデマンド再検証を設計することが重要。

- **型安全なルーティング:** `next/navigation`の`useRouter`と組み合わせて型付きルートパラメータを管理する。`nuqs`などのライブラリでURLステートをサーバー側と同期させることで、検索・フィルタUIのSSR対応が格段に楽になる。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Cold Start の最小化:** Edge Functionsはランタイムにいくつかの制約があるため、依存関係を軽量に保つことが重要。2026年時点では `npm` パッケージの代わりに Web標準API（`fetch`, `crypto`, `Cache`）を優先し、バンドルサイズを50KB以下に抑えることがベストプラクティスとなっている。

- **ポイント2: Edge Config との組み合わせによる動的制御:** Feature flagsやA/Bテストのロジックをデータベースアクセスなしにエッジで実行するため、Vercel Edge Configを活用するパターンが主流。レイテンシが1ms未満で設定値を読み取れるため、リクエストごとの条件分岐コストがほぼゼロになる。

- **ポイント3: Middleware の責務分離:** Vercel Middlewareは認証チェック・ジオルーティング・リライトに特化させ、ビジネスロジックは含めない設計が推奨される。Middlewareが肥大化するとすべてのルートに影響するため、`matcher` で対象パスを明示的に絞ることがパフォーマンス上の必須事項。

- **ポイント4: Streaming レスポンスの活用:** `ReadableStream` と `TransformStream` を使ったストリーミングレスポンスにより、LLM出力やSSEをエッジで直接中継できる。2026年ではAI関連APIのプロキシをEdgeに置くアーキテクチャが一般的になり、オリジンサーバーへの負荷を大幅に削減できる。

- **ポイント5: 地理的ルーティングと ISR の組み合わせ:** `request.geo` を使った国別コンテンツ出し分けと、Incremental Static Regenerationを組み合わせることで、キャッシュヒット率を最大化しながら地域最適化を実現。エッジキャッシュの `Cache-Control: s-maxage` を適切に設定することが、グローバルレイテンシ削減の鍵となる。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の標準化:** TypeScript 4.9以降、`satisfies` が型推論を保持しながら型チェックを行う標準パターンとして定着。`as const` との組み合わせでリテラル型の精度が大幅に向上した。

- **Template Literal Types の実用化:** APIルートやイベント名などの文字列パターンを型レベルで表現できるようになり、ランタイムエラーをコンパイル時に検出するケースが増加。`${Method}/${Endpoint}` 形式でRESTパスを型安全に扱う手法が普及している。

- **`noUncheckedIndexedAccess` の採用加速:** 配列・オブジェクトのインデックスアクセスを `T | undefined` として扱うこのコンパイラオプションが、厳格なコードベースのデファクト設定に。`tsconfig` の `strict` に含まれていないため意識的に有効化が必要。

- **Branded Types によるドメイン安全性:** `UserId` と `ProductId` が共に `string` でも混在しないよう、Branded/Opaque型パターンが実務標準化。Zodの `.brand()` との統合でバリデーションと型安全性を一元管理できる。

- **型レベル状態機械:** `never` を使った網羅性チェック（exhaustive check）と discriminated union の組み合わせで、状態遷移のバグをビルド時に検出する設計が増加。特にフォームや非同期フローの複雑な状態管理で効果を発揮している。
