# CTO Knowledge - 2026-09-03

## Daily Update (2026-09-03)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16でPPRが安定版となり、静的シェルと動的コンテンツを1レスポンスで配信できるため、TTFBを維持しつつパーソナライズ表示が可能になった。物件一覧の静的部分と在庫状況のような動的部分を分離するのに有効。

- **React Compilerによる自動メモ化:** `useMemo`/`useCallback`を手動で書かなくても再レンダリングが最適化されるため、リスト表示（物件カードなど）のパフォーマンスチューニング工数が大幅に削減できる。

- **Turbopackのビルド標準化:** 開発時・本番ビルド共にTurbopackがデフォルト化し、Webpack比で大規模プロジェクトのビルド時間が大幅短縮。CI時間の削減にも直結する。

- **キャッシュ戦略の明示化（`use cache`ディレクティブ）:** ファイル/関数単位でキャッシュ挙動を明示的に制御できるようになり、暗黙的なキャッシュバグ（古いデータ表示など）を防ぎやすくなった。物件データのようにdraft/publicが混在するケースでは特に重要。

- **画像・フォントの自動最適化の高度化:** `next/image`のAVIF優先配信とCLS対策が強化され、Core Web Vitals（特にLCP）改善がほぼ設定不要で得られる。Airbnb風の画像重視UIとの相性が良い。

### 2. React Server Components streaming 2026

- **段階的ハイドレーション最適化:** Next.js 16ではPartial Prerendering（PPR）が標準化され、静的シェルを即座に返しつつ動的部分のみをストリーミングすることで、TTFBとLCPを大幅に改善できる。sumitsugiの`properties/`一覧ページのような静的部分（レイアウト・ヘッダー）と動的部分（在庫・価格）が混在する画面に特に有効。

- **Suspense境界の粒度設計:** RSCストリーミングの効果はSuspense境界の切り方に依存するため、物件詳細ページなどでは「前の住人」情報・写真ギャラリー・引越し費用計算のように独立したデータフェッチ単位ごとに境界を分割し、遅いAPIが全体をブロックしないようにする設計が重要。

- **Server Actionsとの統合による往復削減:** フォーム送信（問い合わせ・申込）でServer Actionsを使うことで、クライアントJSバンドルを増やさずにストリーミングレスポンス内で楽観的UI更新が可能になり、認証周りのバリデーションもサーバー側に閉じ込められセキュリティ面でも有利。

- **キャッシュ戦略の複雑化への対応:** `use cache`ディレクティブとRouter Cacheの相互作用が複雑になっており、`draft`/`public`ステータスの物件データのようにミューテーション頻度が異なるデータは、キャッシュタグを明示的に分離しないと古いデータが配信されるリスクがある。ビルド前にキャッシュ無効化パスをテストで担保すべき。

- **エッジランタイムとの親和性:** RSCストリーミングはVercel Edge/Cloudflare Workers等のエッジ実行環境と組み合わせることでレイテンシがさらに改善するが、Bun runtimeとの互換性はまだ発展途上のため、本番デプロイ先のランタイム制約を早めに検証しておく必要がある。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの本格採用拡大）:** TypeScriptモノレポ構成のプロジェクトではtRPCが定番化しつつあり、フロント/バック間の型安全性を担保できるためスキーマ定義とドキュメント作成の工数を削減できる。sumitsugiのようなNext.js App Router構成では、Server Actionsと組み合わせることでtRPCすら不要になるケースも増えており、まず「本当に別レイヤーのAPI層が必要か」を見極めるのが重要。

- **ポイント2（GraphQLは特定ユースケースに収束）:** GraphQLは複雑なデータ取得要件（モバイルアプリの複数エンティティ結合、パートナー向け公開API）に強みを持つ一方、社内向けの単純なCRUDにはオーバーヘッドが大きいという認識が定着。2026年時点では「デフォルトで採用」ではなく「必要な箇所にだけ導入」する選択的採用が主流。

- **ポイント3（RESTの延命とOpenAPI自動生成）:** RESTは依然として外部連携・サードパーティ統合のデファクトスタンダードであり、ZodスキーマからOpenAPI仕様を自動生成するツールチェーン（zod-to-openapi等）が普及し、Zodバリデーション（本プロジェクトの標準）とAPI仕様書を単一ソースで管理できるようになった。

- **ポイント4（型安全性がAPI設計の中心指標に）:** REST/GraphQL/tRPCいずれを選んでもエンドツーエンドの型安全性（DBスキーマ→APIレスポンス→UIコンポーネント）が評価軸の中心となっており、型不整合によるランタイムエラーを設計段階で潰すアーキテクチャが標準化。CLAUDE.mdのUnion型チェック方針（例: `'draft' | 'public'`）とも合致する方向性。

- **ポイント5（BFF/エッジ関数によるAPI層の薄型化）:** Next.jsのServer Components/Server ActionsやEdge Functionsの成熟により、独立したAPIサーバーを持たず「BFF層をアプリ内に内包」する構成が増加。sumitsugiの規模（MVP〜ローンチ準備フェーズ）では、独立APIサーバーを新設するより既存のNext.js構成内で完結させる方が保守コストとレイテンシの両面で有利。

### 4. serverless edge computing 2026

- **エッジでのAI推論が標準化:** Cloudflare Workers AIやVercel Edge Functionsがモデル推論をエッジに配置する構成が一般化し、Next.js 16のミドルウェア層でもレイテンシ数十ms単位の応答が現実的になっている。sumitsugiのような物件検索・マッチング機能では、ユーザーの地理的位置に応じた検索結果の事前計算・キャッシュにエッジ関数を使うことでTTFBを大幅短縮できる。

- **Cold Start問題の実質的解消:** V8 Isolatesベースのランタイム（Cloudflare Workers、Deno Deploy）がコンテナ型サーバーレス（AWS Lambda等）を置き換えつつあり、コールドスタートがミリ秒未満に近づいている。認証チェックや画像最適化など、レイテンシに敏感な処理を今後Edge Runtimeへ移行する価値がある。

- **データレイヤーのエッジ分散:** Turso（libSQL）やCloudflare D1のようなSQLiteベースの分散DBが、リージョン単位でのレプリケーションを容易にしている。前の住人・次の住人間のリアルタイムメッセージング機能を将来的に強化する際は、こうしたエッジDBを検討する余地がある。

- **フロントとバックの境界が曖昧化:** Next.js 16のPartial Prerenderingとエッジミドルウェアの組み合わせで、静的配信とパーソナライズを同一リクエスト内で両立できるようになった。物件一覧ページのようなSEO重視かつユーザー依存のコンテンツで有効。

- **コスト構造の変化に注意:** エッジ実行は従量課金だがリクエスト単価はリージョンや帯域幅で変動が大きく、ベータローンチ後のトラフィック増加時にコスト予測を誤りやすい。本格導入前に想定トラフィックでの試算とベンダーロックインのリスク評価を行うべき。

### 5. authentication security best practices 2026

- **パスキー移行の加速:** パスワードレス認証（FIDO2/WebAuthn）が2026年の標準になりつつあり、フィッシング耐性とUX向上の両立が可能。sumitsugiでも認証周りの再設計時にパスキー対応を優先すべき。

- **AIを悪用したフィッシング・ソーシャルエンジニアリング対策:** 生成AIによる高精度な詐欺メール・なりすましが増加しており、MFA必須化に加え、デバイスフィンガープリンティングや行動分析ベースの異常検知を組み合わせる多層防御が重要。

- **トークン管理の厳格化:** JWTなどのアクセストークンは短寿命化＋リフレッシュトークンローテーションが必須要件になっている。長寿命トークンの保存・漏洩リスクは監査で真っ先に指摘される。

- **ゼロトラスト前提のセッション管理:** 「一度ログインしたら信頼する」モデルから脱却し、セッションごとにデバイス・IP・行動パターンを継続的に検証する設計が求められる。特に決済や個人情報を扱う「引越し費用」関連フローでは重要。

- **サードパーティ認証ライブラリの依存管理:** OAuth/OIDCライブラリの脆弱性は継続的に発見されるため、依存関係の自動スキャン（Dependabot等）とSLA付きパッチ適用フローをCI/CDに組み込むことが2026年のベストプラクティス。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はRust非依存のクエリエンジン（TypeScript版）への移行が進み、Edge Runtime（Vercel Edge, Cloudflare Workers）でのコールドスタートが大幅改善。Supabase連携時はEdge Functions側でもPrisma Clientが軽量に使えるようになっている。

- **ポイント2:** Supabaseの`pgbouncer`によるコネクションプーリングとPrismaの相性問題（prepared statement競合）は`?pgbouncer=true`+`directUrl`設定で解消済みだが、サーバーレス環境ではPrisma Accelerateのようなマネージドプーリング層を併用するのが実質標準になっている。

- **ポイント3:** Row Level Security（RLS）をSupabase側で強制しつつPrismaでスキーマ管理する構成が主流化。マイグレーションはPrisma Migrateで行い、RLSポリシーはSQLマイグレーションとして別管理することで、型安全性とDB層セキュリティを両立できる。

- **ポイント4:** sumitsugiのようなマーケットプレイス型サービスでは、物件・ユーザー・取引データの整合性が重要なため、Prismaのトランザクション（`$transaction`）とSupabase Realtimeを組み合わせ、在庫状態（`draft`/`public`）の同時更新を楽観的ロックで防ぐパターンが有効。

- **ポイント5:** 2026年時点ではPrisma ORMからの移行選択肢としてDrizzle ORMも成熟しており、Supabaseとの型生成連携がより軽量。ただし既存のPrisma資産が大きい場合は移行コストが見合わないため、当面はPrisma継続が現実的な判断。

### 7. WebAssembly Rust performance 2026

- **ポイント1（Component Model / WASI Preview 2の実用化）:** WASIプレビュー2とコンポーネントモデルが主要ランタイム（wasmtime, wasmer）で安定運用フェーズに入り、Rustの`wasm32-wasip2`ターゲットで言語間相互運用が容易になった。マイクロサービス的に小さなWasmコンポーネントを組み合わせる設計が現実的な選択肢になっている。

- **ポイント2（コールドスタートの優位性が縮小しつつも依然強い）:** Cloudflare WorkersやFastly Compute等のエッジ環境ではRust製Wasmのコールドスタートがミリ秒未満と圧倒的で、宿泊物件検索のような低レイテンシAPIには向くが、V8のスナップショット高速化などJS側も追いついてきているため「Wasm一択」ではなく用途を絞った採用が現実的。

- **ポイント3（SIMD・スレッド標準化でネイティブ比の性能差が縮小）:** Wasm SIMDとShared Memory/Threadsがブラウザ・ランタイム双方で標準サポートされ、画像処理（物件写真の圧縮・サムネイル生成）のようなCPUバウンド処理をクライアント/エッジ双方でネイティブの70-90%程度の性能で実行できるようになった。

- **ポイント4（バイナリサイズとビルド時間がボトルネックとして残る）:** `wasm-opt`や`twiggy`によるサイズ最適化は成熟したが、Rustの依存クレートが増えるとビルド時間とWasmバイナリサイズが肥大化しやすく、フロントエンドで使う場合はコード分割・遅延ロード設計が必須。

- **ポイント5（当社への適用余地は限定的だが将来オプション）:** sumitsugiは現状Next.js/TypeScriptスタックのため即座の導入価値は低いが、将来的にPDF生成や物件データの重い変換処理（画像解析、間取り図パース等）をエッジで高速化したい場合、Rust+Wasmの部分導入は検討価値がある。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 15以降で導入されたPPRがApp Routerの主要パターンとして定着し、静的シェルと動的コンテンツ（Suspense境界内）を1つのレスポンスで配信できるため、TTFBを維持しつつパーソナライズされたUIを実現できる。sumitsugiのような物件一覧+ユーザー固有情報（お気に入り等）が混在する画面で有効。

- **Server Actions の設計成熟:** フォーム送信やミューテーションをAPI Routeではなく`'use server'`関数に集約するのが標準になり、Zodバリデーションと組み合わせて型安全なフォーム処理を書くパターンが確立。物件登録・お問い合わせフォームなどで冗長なAPIエンドポイントを削減できる。

- **キャッシュの明示的制御（`use cache`/`cacheLife`）:** 暗黙的なフルルートキャッシュから、`use cache`ディレクティブによる関数・コンポーネント単位の明示的キャッシュ制御へ移行が進んでいる。物件データのようにDB更新頻度が異なるデータに対して、キャッシュ戦略を細かく調整できる。

- **Server/Client境界の最小化:** 「Client Componentは葉（leaf）に留める」パターンがベストプラクティスとして定着し、インタラクティブな部分（フィルタ、モーダル等）だけを`'use client'`に切り出し、レイアウトやデータ取得はServer Componentに残す設計が推奨されている。バンドルサイズ削減とパフォーマンス向上に直結。

- **並列ルート・インターセプトルートの実用化:** モーダルUI（物件詳細のクイックビューなど）を`@modal`スロットとインターセプトルート（`(.)`）で実装するパターンが、URLの一貫性とブラウザバック対応を両立する手法として広く採用されている。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: ランタイム統合とコールドスタート削減** Edge FunctionsのV8アイソレートがさらに最適化され、コールドスタートがミリ秒単位まで短縮。Node.js APIとの互換性も拡大し、Edge/Serverlessの使い分けを意識しなくてもよいケースが増えている。

- **ポイント2: ストリーミングSSRとの親和性** Next.js 16のPartial Prerenderingと組み合わせることで、静的シェルを即座に返しつつ動的部分をEdgeでストリーミングする構成が主流に。TTFBを大幅に改善できるため、物件一覧・検索ページのような動的コンテンツに有効。

- **ポイント3: リージョン最適化とデータ近接配置** Edge ConfigやKV系ストレージをEdge Functionsと同一リージョンに配置し、DB往復を減らす設計が定着。認証チェックやフィーチャーフラグ判定など軽量ロジックをEdgeに寄せ、重い処理はNode runtimeに残す「ハイブリッド配置」が推奨パターン。

- **ポイント4: 観測性とコスト管理の強化** Edge Function単位でのレイテンシ・コスト可視化ツールが充実し、関数の粒度を細かくしすぎるとコールド起動回数増でコスト増になる点への注意が広まっている。バンドルサイズ制限（1MB前後）を意識した依存関係の最小化も引き続き重要。

- **ポイント5: セキュリティ境界としての活用** Bot対策・レート制限・地域制限などをEdgeでリクエスト到達前に処理するパターンが標準化。sumitsugiのような認証必須ページでは、Edge Middlewareでの軽量セッション検証→Node runtimeでの本処理、という二段構成がパフォーマンスとセキュリティ両立に有効。

### 10. TypeScript type safety patterns 2026

- **`satisfies`演算子の定着:** 型推論を保ちながら型チェックも行える`satisfies`が標準パターン化し、`as const satisfies T`の組み合わせで設定オブジェクトやAPIレスポンスの型安全性を損なわずに具体的なリテラル型を維持できます。

- **スキーマ駆動の型生成:** Zodなどのスキーマライブラリで実行時バリデーションと型定義を一元化する流れが主流になり、`z.infer<typeof schema>`でシステム境界（フォーム入力・API境界）の型と実装がズレるリスクを構造的に排除します。本プロジェクトでもZodはバリデーション標準として採用済みです。

- **Branded Types / Nominal Typingの普及:** `UserId`と`ProductId`のような構造的に同じ`string`型を誤って混同するバグを防ぐため、ブランド型パターン（`type UserId = string & { __brand: 'UserId' }`）が特にID周りの型安全性強化で広く使われるようになっています。

- **テンプレートリテラル型 + 型レベルルーティング:** Next.js App Routerのようなファイルベースルーティングと組み合わせて、テンプレートリテラル型でパス文字列やクエリパラメータの型安全性を担保するパターンが拡大し、存在しないルートへのリンクをコンパイル時に検出できます。

- **`unknown`優先とtype guardの徹底:** `any`の使用をlintルールで実質禁止し、外部データは必ず`unknown`で受けてZodやtype predicate（`is`）で絞り込むフローが標準化。エラーメッセージへの機密情報混入防止（`.claude/rules/standards.md`のセキュリティ方針）とも相性が良く、型安全性とランタイム安全性を同時に担保できます。
