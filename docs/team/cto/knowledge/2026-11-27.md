# CTO Knowledge - 2026-11-27

## Daily Update (2026-11-27)

### 1. Next.js performance optimization 2026

- **ポイント1:** Turbopackが本番ビルドでも標準化され、Webpack比で大幅なビルド時間短縮が実現。大規模ページ数のプロジェクトではCI/CDのビルド時間がボトルネックになりやすいため、早期移行が有利。
- **ポイント2:** Partial Prerendering（PPR）が安定版となり、静的シェルと動的コンテンツを1ページ内で混在させられるため、TTFBを静的配信レベルに保ちつつパーソナライズ要素を維持できる。物件一覧ページのような「静的な骨格＋動的な在庫情報」構成に適している。
- **ポイント3:** React Server Components中心の設計により、クライアントバンドルサイズを最小化できるが、`'use client'`境界の設計を誤るとハイドレーションコストが逆に増える。コンポーネント境界の見直しを定期的に行う運用が重要。
- **ポイント4:** `next/image`と`next/font`の自動最適化に加え、Cache Componentsによる関数レベルの再検証制御が普及。画像が多い不動産サイトではLCP改善に直結するため優先度高。
- **ポイント5:** Edge RuntimeとNode.js Runtimeの使い分けがより明確化され、認証・DB接続が必要なルートはNode Runtime、軽量な地理分散処理はEdgeという設計指針が定着。無計画なEdge全面採用はコールドスタートやDB接続制限で逆効果になりやすい。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の実用化:** 静的シェルを即時配信しつつ動的部分だけストリーミングする構成がNext.js 16で標準的になり、TTFBとインタラクティブ性の両立が設計レベルで可能になった。sumitsugiの物件一覧・詳細ページのような「共通UIは静的、価格や空き状況は動的」なページ構成に特に有効。

- **Suspense境界の粒度設計がパフォーマンスを左右:** コンポーネント単位で`Suspense`を細かく切るほどストリーミング効果は上がるが、ウォーターフォール（直列fetch）を誘発しやすいので、並列データ取得とのバランス設計がアーキテクチャ上の重要課題になっている。

- **`use cache`ディレクティブによるキャッシュ制御の明示化:** データ取得のキャッシュ戦略をコード上で宣言的に表現できるようになり、RSCのストリーミングと組み合わせることで「初回は静的キャッシュから即返却、裏側で再検証」というパターンが実装しやすくなった。

- **Server Actionsとストリーミングレスポンスの統合:** フォーム送信後の結果を段階的にストリーミングで返せるようになり、引越し費用の見積りや申込フォームなど多段階フローのUXが、クライアントサイドの状態管理なしで改善できる。

- **エッジランタイムでのストリーミングコストの低下:** CDNエッジでのRSCストリーミング対応が進み、地理的に分散したユーザーへのTTFB改善がサーバーレス関数の冷起動問題を気にせず実現できるようになってきている。ベータローンチ時のインフラ選定で検討余地あり。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCの採用はTypeScriptモノレポ構成のチームで加速しており、スキーマ定義とクライアント型を自動同期できるため、フロントエンド/バックエンド間のAPI契約ズレによるバグをビルド時に検出できる。Next.js App RouterとServer Actionsの普及で、むしろ「API層そのものを薄くする」選択（RPCレスでServer Actions直結）も増えている。

- **ポイント2:** GraphQLは依然として複雑な集約クエリや複数クライアント（モバイル/Web）でのオーバーフェッチ回避に強いが、N+1問題やキャッシュ戦略の運用コストが高く、中小規模チームではtRPC/RESTの方が開発速度で優位になりやすい。導入判断は「クライアントの多様性」と「チーム規模」で決めるべき。

- **ポイント3:** REST APIはOpenAPI 3.1 + Zodスキーマ連携での型安全性確保がデファクト化し、`zod-to-openapi`のようなツールでスキーマとドキュメントの単一ソース化が進んでいる。公開APIや外部パートナー連携が必要な場合は、言語非依存性の観点からRESTが依然第一選択。

- **ポイント4:** sumitsugiのような単一Next.jsアプリ内製チームの場合、外部公開APIが不要ならtRPC（またはServer Actions）でエンドツーエンドの型安全性を最優先し、将来的に外部連携（不動産仲介システム連携など）が必要になった時点でRESTレイヤーを薄く追加する段階的アプローチが合理的。

- **ポイント5:** 2026年のトレンドとして、AIエージェント（MCP経由のツール呼び出し）がAPIクライアントになるケースが増え、エンドポイント設計時に「人間向けREST」だけでなく「エージェント向けの構造化された入出力スキーマ」を意識する必要性が高まっている。tRPC/Zodスキーマはこの点でもMCPツール定義への変換がしやすく相性が良い。

### 4. serverless edge computing 2026

**CTOの視点:serverless edge computing 2026のトレンド**

- **ポイント1（WASMランタイムの主流化）:** Cloudflare Workers、Deno Deploy、FastlyなどがWasmベースの実行環境を標準化し、コールドスタートがミリ秒未満まで短縮。言語非依存でRust/Go/TypeScriptを同一エッジ上で動かせるため、我々のような小規模チームでもマルチリージョン配信を低コストで実現できる。

- **ポイント2（エッジでのAI推論統合）:** 軽量LLM推論やベクトル検索をエッジノードで直接実行するパターンが普及し、ユーザーの地理的位置に近い場所でレコメンド・検索処理が可能になった。物件検索や「引越し費用」見積もりのようなレイテンシ敏感な機能に応用できる余地がある。

- **ポイント3（エッジデータベースの成熟）:** Turso、Cloudflare D1、PlanetScaleなどのエッジ対応SQLiteベースDBが本番運用レベルに達し、グローバルな読み取りレプリケーションがデフォルト化。read-heavyな物件一覧ページのパフォーマンス改善に直結する選択肢になりつつある。

- **ポイント4（コスト構造の変化）:** 従量課金モデルがCPU時間課金からリクエスト課金・GB-秒課金へ移行し、予測可能なコスト管理が容易に。ただしベンダーロックインのリスクは依然高く、移行コストを見込んだアーキテクチャ選定が必要。

- **ポイント5（観測性・デバッグの進化）:** OpenTelemetryのエッジネイティブ対応が進み、分散トレーシングがサーバーレス環境でも実用レベルに。本番環境での障害調査がこれまでより格段にやりやすくなっている一方、導入には追加の計装コストがかかる点は留意すべき。

**実務的な所感:** 現時点のsumitsugiのスケール（MVPローンチ前）では、エッジ移行の投資対効果はまだ限定的。Next.js on Vercelの現構成で十分だが、物件検索のグローバル展開やAI機能拡張のタイミングで再検討する価値がある。

### 5. authentication security best practices 2026

- **パスワードレス認証の標準化:** パスキー（WebAuthn/FIDO2）が主流になり、パスワード依存を減らすことでフィッシングやクレデンシャルスタッフィングのリスクを大幅に低減できる。sumitsugiのような個人情報・決済情報を扱うプラットフォームでは、Supabase AuthやAuth0のパスキー対応を早期に導入する価値が高い。

- **多層防御としてのリスクベース認証:** IP・デバイス・行動パターンから異常を検知し、必要な場合のみMFAを要求するアダプティブ認証が、UXを損なわずセキュリティを高める実用的アプローチ。前の住人↔次の住人間の高額取引（引越し費用決済）など、リスクが高い操作に絞って追加認証を発火させる設計が効果的。

- **トークン管理のゼロトラスト化:** JWTの有効期限を短くし、リフレッシュトークンのローテーション＋デバイスバインディングを行うことで、トークン漏洩時の被害範囲を限定する。Next.js 16のServer Actions/Middlewareでトークン検証を一貫して行い、クライアント側に長寿命トークンを保持しない設計が必須。

- **セッション管理とデバイス可視化:** ユーザーが自分のログイン中デバイス一覧を確認・個別ログアウトできるUIを提供することが、2026年のベストプラクティスとして標準化されている。不正アクセス発覚時の被害抑制だけでなく、ユーザーの信頼構築にも直結する。

- **サプライチェーン・依存パッケージの認証リスク監査:** 認証フローに関わるライブラリ（NextAuth、Supabase SDKなど）の脆弱性を定期的にスキャンし、CVE対応を自動化するパイプライン（Dependabot/Snyk連携）を組み込むことで、認証基盤自体の脆弱性を未然に防ぐ。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** PrismaのRust製クエリエンジンから純TypeScript実装への移行（Prisma ORM v6以降）が進み、エッジランタイム（Vercel Edge, Cloudflare Workers）でのコールドスタートが大幅に改善されている。sumitsugiのSSR/APIルートでレイテンシ改善を検討する価値がある。

- **ポイント2:** SupabaseのRLS（Row Level Security）とPrisma Clientを併用する場合、Prismaは通常DB接続で直接クエリを投げるためRLSをバイパスしがちな問題が知られており、認証済みユーザーのコンテキストを`SET LOCAL`で明示的に渡す設計が必須。「前の住人」「次の住人」間の物件データアクセス制御では特に注意が必要。

- **ポイント3:** Supabaseの接続プーリング（PgBouncer/Supavisor）とPrismaのPrepared Statementsの相性問題が解消され、Transaction ModeでのServerless対応が安定化。Next.jsのServer ActionsやRoute Handlersからの同時接続数が増えるフェーズ（ベータローンチ後）で効果が出る。

- **ポイント4:** Prisma Postgres（マネージド版）とSupabaseの機能競合が進み、リアルタイム機能（Realtime subscriptions）はSupabase優位、スキーマ管理・型安全性はPrisma優位という分業が定着。物件ステータス（`draft`/`public`）のリアルタイム反映にはSupabase Realtimeの活用余地がある。

- **ポイント5:** マイグレーション管理において`prisma migrate`とSupabase CLIの二重管理を避け、Prisma側に一本化する運用がベストプラクティス化している。法務確認フェーズ中の今、スキーマ変更履行が最小化されるこの時期にマイグレーション運用ルールを整備しておくと、ベータローンチ後の変更コストを抑えられる。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC（WebAssembly Garbage Collection）の普及により、RustだけでなくKotlinやJava由来のコードも軽量にWasm化できるようになり、Rust製コンポーネントとの相互運用がより現実的になってきている。ただしRustの強みは依然GC不要な決定論的メモリ管理にあり、低レイテンシが求められるSSRやエッジ処理ではRust+Wasmが優位。

- **ポイント2:** Component Model（WASI 0.3系）の安定化で、Rustで書いたWasmモジュールを言語・ランタイム非依存の「部品」として配布・合成できるようになり、マイクロフロントエンドやサーバーレス処理の再利用性が向上している。社内で共通ロジック（料金計算、PDF生成など）をWasmコンポーネント化すれば、Node/Deno/Bunどのランタイムでも同じバイナリを使い回せる。

- **ポイント3:** SIMD128とマルチスレッド（共有メモリ＋Web Workers連携）がブラウザ主要エンジンで標準的に使えるようになり、画像処理や検索インデックス構築のようなCPUバウンド処理をRust+Wasmでクライアント側にオフロードする設計が増えている。サーバー負荷を下げつつUXを損なわない選択肢として検討価値がある。

- **ポイント4:** `wasm-bindgen`/`wasm-pack`のビルドチェーンが成熟し、バンドルサイズ最適化（`wasm-opt`, tree-shaking）がデフォルト化したことで、以前課題だった「初回ロードの重さ」が大幅に改善している。ただし依然バンドルサイズとコンパイル時間はJS/TSより重く、小規模な単発処理には過剰投資になりやすい点は注意。

- **ポイント5:** サーバーサイドではWasmtime/Wasmerを使ったサンドボックス実行（プラグインシステム、マルチテナントのユーザー定義ロジック実行）がRustエコシステムで定番化しており、セキュリティ分離とパフォーマンスを両立する手段として、プラグイン型機能拡張を検討する際の第一候補になっている。

### 8. Next.js App Router patterns 2026

- **ポイント1:** Partial Prerendering（PPR）が安定版として本格運用フェーズに入り、静的シェルを即時配信しつつ動的部分のみストリーミングする構成が標準化。ランディングページや物件一覧ページで初期表示速度（LCP）を大幅改善できる。
- **ポイント2:** Server ActionsとuseActionState/useOptimisticの組み合わせが、フォーム処理のデファクトパターンとして定着。問い合わせフォームや物件登録フローでAPI Route不要になり、コード量とクライアントJSバンドルを削減できる。
- **ポイント3:** `cacheLife`/`cacheTag`によるきめ細かいキャッシュ制御（Cache Components）が普及し、「ページ単位」ではなく「データ単位」で再検証戦略を設計するのが主流に。物件ステータス（draft/public）更新時のタグベース再検証がベストプラクティス。
- **ポイント4:** Server Componentsからのデータフェッチを`React.cache`とcomposable fetchパターンでレイヤー化し、N+1フェッチ問題をビルド時/リクエスト時に可視化するツール（例: Next.js DevTools Overlay）の活用が進んでいる。
- **ポイント5:** Route GroupsとParallel Routes/Interceptorsを使ったモーダル実装（物件詳細のライトボックス等）が成熟し、SEOを損なわずにリッチなUXを実現する設計パターンとして定着。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約を前提にした設計:** Node.js APIが使えないV8 isolateベースのため、重い処理はBackground Functions等に逃がし、Edge側は認証・リダイレクト・パーソナライゼーションなど軽量なロジックに限定するのが2026年の定石です。
- **Streaming + Partial Prerendering(PPR)の活用:** 静的シェルを即時配信しつつ動的部分だけEdgeでストリーミングすることで、TTFBを数十ms単位に抑えられます。弊社のようなLP・物件一覧ページ(`src/app/properties/`)では特に効果が出やすいです。
- **リージョン指定とデータ局所性:** Edge Functionはグローバル分散がウリですが、DB/KVが単一リージョンにある場合はラウンドトリップがボトルネックになります。`regions`オプションで実行リージョンをデータ側に寄せる、またはKV/Edge Configで読み取りをエッジに持たせる設計が重要です。
- **コールドスタート最小化のためのバンドルサイズ管理:** 依存関係を絞り込み(Edge対応ライブラリのみ使用)、1〜4MBのバンドル上限を意識することで、初回応答の遅延を防げます。tree-shaking前提でimportを書くのが必須です。
- **Observability統合の標準化:** 2026年はVercelのEdge Middleware/Functionsのトレーシングが OpenTelemetry と統合されつつあり、エッジ特有のレイテンシ・エラーをダッシュボードで可視化できるようになっています。本番投入前にこの計測基盤を組み込んでおくべきです。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x系の`satisfies`演算子とconst型パラメータが定着し、型推論を保ちながら厳密な制約チェックができるようになった。sumitsugiの`'draft' | 'public'`のようなUnion型管理では、`satisfies`を使うことで値の網羅性チェックが型安全に行える。

- **ポイント2:** Zodなど実行時スキーマから型を生成する「Schema-first」設計が標準化し、`z.infer<typeof schema>`でAPI境界の型とランタイム検証を一元管理する流れが強まっている。これは`.claude/rules/standards.md`のZod境界検証ルールとも整合する。

- **ポイント3:** Branded Types（例: `type UserId = string & { __brand: 'UserId' }`）による名目的型付けが、IDの取り違えバグ防止策として一般化してきている。物件IDやユーザーIDを文字列で扱う本プロジェクトでも、型レベルでの混同防止に有効。

- **ポイント4:** `tsc`のビルド速度改善（増分コンパイル、`isolatedDeclarations`）が進み、大規模コードベースでも型チェックをCIのブロッキングゲートとして運用しやすくなった。`bun run build`を必須化している現行方針とも方向性が一致。

- **ポイント5:** AIコード生成が普及する中、型定義そのものを「仕様書」として扱う傾向が強まり、exhaustive switch + `never`チェックによる網羅性保証が、AIが生成したコードの退行防止に重要なセーフティネットとして再評価されている。
