# CTO Knowledge - 2026-06-28

## Daily Update (2026-06-28)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分のみストリーミングする構成が標準化。物件一覧ページのような「ヘッダーは固定・在庫情報は動的」な構造に最適。
- **React Server ComponentsでのN+1抑制:** RSCのデータフェッチが分散しがちな問題に対し、`cache()` APIとリクエストレベルのメモ化を徹底することがパフォーマンス上の最重要ポイント。
- **Turbopackビルドの標準化:** 開発・本番ビルド双方でTurbopackがデフォルト化され、Webpack比でビルド時間が大幅短縮。bunとの組み合わせでCI時間もさらに圧縮可能。
- **画像・フォント最適化の自動化深化:** `next/image`のAVIF優先配信とフォントのセルフホスティングが自動化され、物件写真中心のUIではLCP改善に直結。
- **Edge RuntimeとISRの粒度制御:** `revalidate`タグベースの再生成がより細粒度になり、引っ越し費用や物件ステータス変更時のキャッシュ無効化を最小範囲に限定できる。

### 2. React Server Components streaming 2026

- **PPR (Partial Prerendering) の標準化:** Next.js 15/16で安定したPPRが主流になり、静的シェルを即時配信しつつ動的部分をStreamingで遅延配信する構成が標準パターン化している。Suspense境界の設計がパフォーマンスチューニングの中心になる。

- **`use cache` ディレクティブの普及:** Next.jsのキャッシュコンポーネント機能（`use cache`）がRSCのデータフェッチ層に組み込まれ、サーバー側でのメモ化粒度がコンポーネント単位で制御できるようになった。これによりDBクエリの重複実行を抑えつつストリーミングの即応性を両立できる。

- **Server Actionsとフォーム送信のストリーミング融合:** mutation後のレスポンスもストリーミングで段階的に返せるようになり、フォーム送信→楽観的UI→サーバー確定という流れがSuspense/`useOptimistic`で滑らかに繋がるようになった。本サービスの内見予約フォームや問い合わせフローに適用余地がある。

- **エッジランタイムでのRSCストリーミング:** Vercel Edge / Cloudflare Workers等でのRSC実行が成熟し、TTFB短縮のためにエッジでストリーミング開始→オリジンでデータ取得という分離構成が一般化している。物件一覧のような地理的に分散したアクセスに有効。

- **可観測性とストリーミングのデバッグ性向上:** React DevTools/Next.jsのトレーシングがSuspense境界ごとのストリーミングタイミングを可視化できるようになり、「どのチャンクがボトルネックか」を本番でも特定しやすくなった。パフォーマンス劣化の早期検知に活用すべき。

### 3. API design REST GraphQL tRPC 2026

- **tRPCのデフォルト化:** Next.js + TypeScriptのフルスタック構成（まさにsumitsugiの構成）では、REST/GraphQLのスキーマ定義・コード生成を省略できるtRPCがデフォルト選択になりつつある。型がサーバーからクライアントまでEnd-to-Endで保証されるため、開発速度と型安全性のトレードオフが事実上なくなった。

- **GraphQLは「集約レイヤー」に縮小:** GraphQLは単一サービスのAPIとしてではなく、複数のマイクロサービス/サードパーティAPIを束ねるBFF（Backend For Frontend）的な集約レイヤーとして使われる場面が増えている。社内向け単一サービスなら素直にtRPCかRESTで十分というのが2026年の主流的判断。

- **RESTはAI/外部公開APIで依然強い:** LLMエージェントやサードパーティ連携が前提のAPIは、OpenAPI仕様との相性・キャッシュ制御・幅広いツール対応の観点から依然RESTが安全な選択。sumitsugiが将来外部パートナー向けAPIを公開する場合はRESTを検討すべき。

- **エッジ・ストリーミング対応が必須要件化:** Next.js 16のApp RouterではServer Actions/Streaming SSRとの統合が重視され、APIレイヤーもエッジランタイムでの低レイテンシ応答とストリーミングレスポンス（特にAI機能向け）への対応が標準要件になっている。

- **スキーマファースト + Zodバリデーションの一体化:** tRPC/RESTいずれを選んでもZodなどのスキーマバリデーションを型定義の単一ソースとして使う設計が定着し、`.claude/rules/standards.md`にある「Zodで境界検証」という方針はこの潮流と一致している。

### 4. serverless edge computing 2026

- **エッジでのAI推論統合:** Cloudflare Workers AIやVercel Edge Functionsのようにエッジランタイムへ軽量LLM推論を組み込む動きが加速しており、レイテンシが要件となるレコメンドやチャット機能はオリジンサーバーを経由せずエッジで完結させられる。

- **コールドスタート問題の事実上の解消:** V8 isolateベースの実行モデル（Cloudflare Workers, Deno Deploy等）が主流化し、従来のFaaSで課題だったコールドスタートは数msレベルまで縮小、レスポンス要件が厳しいフロントエンド向けAPIをエッジに移行しやすくなった。

- **エッジとデータベースの距離問題:** コンピュートはエッジに分散できても整合性のあるデータストアは依然リージョナルに偏っており、Turso/PlanetScaleのようなエッジレプリケーション対応DBやD1のようなSQLiteベースのエッジネイティブDBの選定が設計の分岐点になる。本プロジェクトのような物件情報・ステータス管理（`draft`/`public`）を伴うアプリでは、強整合性が必要な書き込みパスとエッジで完結できる読み取りパスを明確に分離する設計が実用的。

- **Next.js App Routerとエッジランタイムの相性:** Next.js 16のApp RouterはMiddlewareやRoute Handlersをエッジランタイムで実行できるため、認証チェックや地域別コンテンツ振り分けなど軽量なロジックをオリジンへ到達する前に処理し、TTFBを削減できる。ただしNode.js APIに依存する処理（一部のライブラリ）はエッジ非対応のため、ランタイム選定時の制約確認が必須。

- **コスト構造の変化と運用への影響:** 従量課金（リクエスト数・CPU時間ベース）が主流のため、トラフィックパターンが急変するサービスではコスト予測がしづらく、モニタリング・アラート設計（リクエスト数急増時のサーキットブレーカー等）が運用上重要になる。

### 5. authentication security best practices 2026

- **パスワードレス認証の標準化:** WebAuthn/FIDO2によるパスキーがデフォルトとなり、フィッシング耐性のある認証がコンプライアンス要件として求められるようになっている。実装時はフォールバック手段（マジックリンク等）も用意し、未対応デバイスでも離脱させない設計が重要。

- **トークン管理の厳格化:** アクセストークンの短寿命化（5-15分）とリフレッシュトークンのローテーション・盗用検知（reuse detection）が標準的なベストプラクティスになっている。sumitsugiのような物件情報を扱うプラットフォームでは、セッション固定化攻撃やトークン漏洩時の影響範囲を最小化する設計が必須。

- **デバイス・コンテキストベースのリスク評価:** IPアドレス・デバイスフィンガープリント・行動パターンを組み合わせたリスクベース認証（ステップアップMFA）が主流になり、固定的な「常にMFA要求」から「リスクに応じた動的要求」へ移行している。

- **認証基盤の責務分離:** 自前実装よりAuth0/Clerk/Supabase Authなど専門プロバイダーへの委譲が加速しており、セキュリティパッチ・脆弱性対応の負荷を軽減できる。`src/contexts/auth-context.tsx`のような既存実装がある場合、外部プロバイダー移行時はセッション管理ロジックの置き換え範囲を事前に明確化すべき。

- **監査ログとゼロトラスト原則:** 認証イベント（ログイン・パスワード変更・権限昇格）の不可変ログ記録と、「前の住人」「次の住人」間の権限境界を明示的に検証するゼロトラスト設計が、不動産プラットフォームのような個人情報を扱うサービスでは法務・コンプライアンス観点からも重要性が増している。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6+とPostgreSQL拡張機能の統合強化:** Prisma ORMはネイティブな`pgvector`サポートやRow Level Security(RLS)との連携が進化し、Supabase上でのAI機能（embedding検索）やマルチテナント設計が型安全に実装しやすくなっている。sumitsugiの物件検索・レコメンド機能を強化する際の選択肢として有効。

- **Supabase Branching + Prisma Migrateの組み合わせ:** Supabaseのデータベースブランチ機能とPrisma Migrateを併用することで、PR単位で独立したDB環境を持てるようになり、`status: 'draft' | 'public'`のようなスキーマ変更も本番に影響を与えずにテストできる。

- **Edge Functions + Prisma Accelerateでのコネクション管理:** サーバーレス/Edge環境でのコネクションプール枯渇問題に対し、Prisma Accelerateやpgbouncer統合が標準化されつつある。Next.js 16のApp RouterでServer Actionsを多用する構成では、コネクション管理戦略を早期に固めるべき。

- **型安全なRLSポリシーのコード化:** SupabaseのRLSポリシーをSQLで直接管理するのではなく、Prisma schemaやTypeScriptコードからポリシーを生成・検証するツールチェーンが普及しつつある。`seller`/`buyer`のような内部データモデルに対する権限制御をコードレビュー可能な形で管理できる。

- **リアルタイム機能とORMの分離設計:** Supabase Realtimeを使う場合、Prismaでの書き込みパスとRealtimeのサブスクリプションパスを明確に分離し、楽観的UI更新とサーバー確定状態の整合性を保つパターンが定着してきている。物件のステータス変更通知などUX向上に直結する。

### 7. WebAssembly Rust performance 2026

- **WasmGCとコンポーネントモデルの成熟:** 2026年現在、WASI Preview 2とComponent Modelが本格普及し、Rustのwasm-toolsチェーンでモジュール間の型安全な連携が標準化されつつある。これにより、フロントエンドの重い処理（画像処理・暗号化等）をRust/Wasmに切り出す設計判断がよりやりやすくなっている。

- **SIMDとマルチスレッド対応の実用化:** wasm-bindgen + wasm-pack経由でWasm SIMD128とSharedArrayBuffer活用のマルチスレッドが主要ブラウザで安定動作するため、画像/動画処理や物理演算など計算負荷の高い機能をネイティブの70-90%程度の速度でブラウザ実行できる。

- **バイナリサイズ最適化が依然ボトルネック:** `wasm-opt`や`twiggy`での解析、`wee_alloc`からの移行（現在は`dlmalloc`やデフォルトアロケータ推奨）など、配信パフォーマンス（初回ロード）を意識した最適化が必要で、不要なpanicハンドラ削除や`opt-level = "z"`設定が定石になっている。

- **サーバーサイドWasm（Wasmtime/Wasmer）でのエッジ実行拡大:** Cloudflare Workers、Fastly Compute等でRust/Wasmランタイムがコールドスタート数msという特性を活かし、エッジでのレイテンシ重視API処理に使われるケースが増えている。sumitsugiのような自社サービスでも、将来的に重い計算処理（PDF生成や画像変換）をエッジWasm化する余地がある。

- **デバッグ・プロファイリングの改善:** ソースマップ対応とDWARF統合が進み、ブラウザDevToolsでRustのまま（コンパイル後のWasmではなく）ステップデバッグできる環境が整ってきたため、導入コストが以前より下がっている。

### 8. Next.js App Router patterns 2026

- **PPR (Partial Prerendering) の本格普及:** Next.js 16では静的シェルと動的コンテンツを同一ページ内で組み合わせるPPRが標準的なパターンとなり、初回表示の速度とSEOを両立しつつパーソナライズされたコンテンツも提供できる。sumitsugiの物件一覧ページのような「静的なレイアウト＋動的な空室状況」構成に適している。

- **Server Actionsによるmutation処理の標準化:** API Routesを使わずServer Actions単体でフォーム送信・データ更新を完結させる設計が主流になり、型安全性とコード量の削減に寄与する。引越し費用の見積りフォームなどで`use server`関数を直接呼び出す構成がシンプルになる。

- **`use cache`ディレクティブによる粒度の細かいキャッシュ制御:** ページ単位ではなく関数・コンポーネント単位でキャッシュ戦略を指定できるようになり、`revalidateTag`との組み合わせで物件データ更新時の即時反映と高速表示を両立しやすい。

- **Parallel RoutesとIntercepting Routesの定着:** モーダルやタブ切替を伴うUI（物件詳細のモーダル表示など）で、URLを保ちつつ独立したローディング/エラー境界を持たせる設計が一般化している。`@slot`構成によりコンポーネント分割がより自然になる。

- **Server Componentsファーストのデータフェッチ:** クライアント側の`useEffect`によるfetchを避け、Server Componentsでのデータ取得とstreaming（`loading.tsx`/`Suspense`）を組み合わせる設計がベストプラクティスとして固まりつつあり、ウォーターフォール問題の回避とバンドルサイズ削減に直結する。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタートとランタイム選定:** Edge Functions は V8 isolate ベースで起動が高速なため、レイテンシが重要なAPI（認証チェックや簡易リダイレクト）はEdgeに、重い処理やNode.js依存ライブラリはNode.jsランタイムのServerless Functionsに振り分けるハイブリッド構成が定石。

- **データ取得の地理的局所性:** Edge Functionsの利点を最大化するには、DBやKVストアもエッジロケーション近傍（Vercel KV/Upstash Redis等）に置く必要がある。リージョン固定のDBに毎回往復するとEdgeの低レイテンシメリットが相殺される。

- **バンドルサイズの最小化:** Edge Runtimeはサイズ制限が厳しく、依存パッケージが肥大化するとデプロイエラーやコールドスタート増加につながる。Tree-shaking前提のライブラリ選定と、不要なpolyfill排除を継続的にlintレベルでチェックすべき。

- **キャッシュ戦略との併用:** Edge Functionsそのものの最適化だけでなく、`stale-while-revalidate`やISR（Incremental Static Regeneration）と組み合わせ、可能な限り「実行しない」選択を取ることが最大のパフォーマンス改善になるケースが多い。

- **可観測性の確保:** Edge環境はNode.jsの一部APIが使えないため、従来のAPMツールが機能しないことがある。Vercelの組み込みObservabilityやOpenTelemetry対応の計測を早期に導入し、実行時間・コールドスタート率を継続的に監視する体制が必須。

### 10. TypeScript type safety patterns 2026

- **Branded Types / Nominal Typing:** `type UserId = string & { __brand: 'UserId' }` のようなブランド型でstring/numberのプリミティブ型を意味的に区別し、IDの取り違えなどをコンパイル時に検出する手法が標準化しつつある。

- **Zodなどによるスキーマファースト設計:** 型定義をZodスキーマから`z.infer`で生成し、ランタイム検証とコンパイル時型を単一のソースから保証するアプローチが、システム境界（API、フォーム入力）での標準パターンになっている。

- **Discriminated UnionsとExhaustiveness Checking:** `status: 'draft' | 'public'`のような状態を判別可能なUnion型で表現し、`switch`文で`never`型を使った網羅性チェックを行うことで、新しいstatus追加時の漏れをコンパイルエラーで検出できる。

- **`satisfies`演算子の定着:** TypeScript 4.9以降の`satisfies`を使い、型推論を保ちながら型適合性を検証するパターンが浸透し、`as const`との組み合わせでより安全なオブジェクトリテラル定義が可能になっている。

- **strictモード＋`noUncheckedIndexedAccess`の標準化:** 配列・オブジェクトアクセス時の`undefined`混入をコンパイル時に強制検出する設定がデフォルト推奨となり、null安全性のギャップを減らす流れが強まっている。
