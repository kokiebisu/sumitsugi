# CTO Knowledge - 2026-09-15

## Daily Update (2026-09-15)

### 1. Next.js performance optimization 2026

- **ポイント1: Partial Prerendering (PPR) の本格運用** — Next.js 15以降で導入されたPPRがstableとなり、静的シェルと動的コンテンツを1つのルートで共存させられる。ページ全体をSSR/SSGで切るのではなく、コンポーネント単位でストリーミング境界を設計する設計思想への転換が進んでいる。

- **ポイント2: React Compilerとの統合による自動メモ化** — `useMemo`/`useCallback`の手動最適化が不要になりつつあり、ビルド時に自動でメモ化コードが生成される。開発速度とランタイム性能の両立が可能になったが、既存コードのマイグレーション時は依存配列の暗黙的な前提を洗い出す必要がある。

- **ポイント3: Turbopackのビルド/devサーバーがデフォルト化** — 大規模モノレポでのHMR速度とプロダクションビルド時間が大幅短縮。ただしカスタムWebpack設定に依存しているプラグイン（画像最適化系など）は移行時に互換性確認が必須。

- **ポイント4: Server Actionsのキャッシュ戦略が成熟** — `use cache`ディレクティブによる細粒度キャッシュ制御が主流になり、revalidateタグの設計がパフォーマンスとデータ鮮度のトレードオフを決める重要な設計判断になっている。sumitsugiの物件ステータス（draft/public）切り替えのような即時反映が必要な箇所ではタグ設計を誤るとキャッシュ汚染のリスクがある。

- **ポイント5: Core Web Vitalsの評価軸がINPからさらに拡張** — 画像・フォント最適化だけでなく、JSバンドルの「配信タイミング」設計（`next/dynamic`のselective hydration、Islands的な部分ハイドレーション）が評価に直結。UI用語変換（前の住人/次の住人など）のような表示ロジックはクライアント側で軽量に保ち、初期表示に不要なJSは遅延ロードすべき。

### 2. React Server Components streaming 2026

- **ポイント1:** 2026年時点でRSCのストリーミングはPartial Prerendering（PPR）とデフォルトで統合され、静的シェルを即座に返しつつ動的部分だけをSuspense境界でストリーミングするパターンがNext.js 16の標準構成になっている。TTFBとLCPの両立が容易になり、`loading.tsx`の粒度設計がパフォーマンスチューニングの主戦場になっている。

- **ポイント2:** サーバー/クライアント境界の「どこで切るか」が設計の中心課題として定着し、データ取得ロジックはRSC側に寄せ、インタラクティブなUIのみ`'use client'`に閉じ込める方針が明確なベストプラクティスになった。sumitsugiの`src/app/properties/`のような一覧+詳細画面では、フィルタUIだけをクライアントコンポーネント化し、物件データ取得はサーバー側でストリーミングする構成が効果的。

- **ポイント3:** Server Actionsとストリーミングの組み合わせで、フォーム送信後の楽観的UI更新（`useOptimistic`）とストリーミングレスポンスを併用するパターンが普及し、多段階フロー（物件登録・引き継ぎ申込など）でのUX改善に直結している。

- **ポイント4:** キャッシュ戦略（`revalidateTag`/`revalidatePath`とストリーミングの併用）が複雑化し、誤ったキャッシュ設定によるstaleデータ表示が本番障害の主要因になりやすい。ダッシュボードや在庫ステータス（`draft`/`public`）のようにリアルタイム性が求められる画面では、キャッシュ無効化ロジックのテストがCIに必須という認識が広がっている。

- **ポイント5:** ストリーミングSSR環境でのエラーバウンダリ設計が重要視されており、Suspense境界ごとに`error.tsx`を細かく配置し、一部のストリームが失敗しても他のUIブロックが表示され続ける「グレースフルデグラデーション」が求められる。特に決済や本人確認など外部API依存の強い機能では必須パターンとなっている。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCの採用が本格化 — Next.js 16のようなフルスタックTypeScript環境では、フロントエンドとバックエンドで型を共有できるtRPCがREST/GraphQLより開発速度と型安全性の面で優位に立っており、sumitsugiのような単一リポジトリ構成には特に相性が良い。

- **ポイント2:** GraphQLは「複雑なデータ取得が必要な画面」に限定利用が主流 — 物件検索や複数エンティティを跨ぐダッシュボードなど over-fetching/under-fetching が問題になる箇所にのみ導入し、単純なCRUDにはtRPCやREST+Zodを使う「ハイブリッド戦略」が2026年のベストプラクティス。

- **ポイント3:** Zodスキーマがコントラクトのハブになっている — API境界でのバリデーション（本プロジェクトの標準にも合致）をZodで定義し、それをtRPCのinput/outputスキーマ、OpenAPI生成、フロントのフォームバリデーションにまで再利用する「スキーマファースト」設計が定着している。

- **ポイント4:** RESTは依然として外部連携・パートナーAPIの標準 — 弁護士確認や特商法対応が絡む決済・契約まわりなど、将来的に外部システム（決済代行、電子契約サービス等）と連携する部分は、ドキュメント性とキャッシュ制御に優れるRESTを維持すべき。

- **ポイント5:** エッジランタイム（Edge Functions）との組み合わせが標準化 — Next.js 16のApp Router上でtRPCやREST APIをエッジで実行し、物件検索などレイテンシに敏感なエンドポイントをCDN近くで処理する構成が2026年時点でのパフォーマンス最適化の定石になっている。

### 4. serverless edge computing 2026

- **エッジでのAI推論が標準化:** Cloudflare Workers AI や Vercel Edge Functions 上でLLM推論を直接実行するパターンが一般化し、レイテンシをユーザーに近い場所で数十ms単位に削減できるようになった。sumitsugiのような物件検索・レコメンド機能では、エッジ側での軽量推論導入によりTTFBを大幅短縮できる可能性がある。

- **コールドスタート問題の実質解消:** V8 isolateベースのランタイム（Workers, Deno Deploy等）が主流化し、コールドスタートがミリ秒未満まで縮小。Next.js 16のApp RouterでもEdge Runtimeとの統合が進み、Server Componentsをエッジで動かす選択肢が実用的になっている。

- **ステートフルエッジ（Durable Objects/KV系）の普及:** これまで「エッジ=ステートレス」が前提だったが、Durable Objects的なプリミティブがデファクト化し、セッション管理や在庫ロックのような強整合性が必要な処理もエッジ側で完結できるようになった。物件の「仮押さえ」機能など競合制御が必要な箇所での活用余地がある。

- **マルチリージョンDBのエッジ統合が進化:** Turso/PlanetScale/Neonなどのエッジレプリケーション対応DBが成熟し、読み取りをエッジ、書き込みをリージョンプライマリに自動ルーティングする構成が容易になった。地方物件情報を扱うsumitsugiにとって、地方ユーザー向けの読み取りレイテンシ改善に直結する。

- **コスト構造の変化に注意:** エッジ実行はリクエスト単価が安い一方、長時間実行や大きなペイロード処理では従来型サーバーより割高になるケースが顕在化してきた。PDF生成や画像処理など重い処理はエッジではなくバックエンドに残す「ハイブリッド配置」の判断が重要になる。

### 5. authentication security best practices 2026

CTOとしての回答です。

- **パスキー/FIDO2への全面移行:** パスワードレス認証がデファクトスタンダード化し、フィッシング耐性のあるWebAuthn/パスキーを優先実装すべき。sumitsugiのようなB2C不動産プラットフォームでは、離脱率の高いSMS OTPより、パスキー+フォールバックのハイブリッド構成が実用的。
- **セッション管理の厳格化:** JWTのステートレス性に頼りすぎず、短命アクセストークン＋サーバー側失効可能なリフレッシュトークンの組み合わせが標準。特に「前の住人」の物件所有権移転など重要操作前には再認証(step-up auth)を要求すべき。
- **ゼロトラスト前提の認可設計:** 認証（誰か）と認可（何ができるか）を分離し、RLS（Row Level Security）やミドルウェアでリクエスト毎に検証。Next.js App Routerではサーバーコンポーネント/Server Actionsごとに認可チェックを徹底する必要がある。
- **AIエージェント対策の強化:** 2026年はボットやAIエージェントによる自動アカウント作成・クレデンシャルスタッフィングが急増しており、レート制限だけでなくデバイスフィンガープリンティングやProof-of-Humanity的な仕組みの検討が必要。
- **秘密情報管理の徹底:** APIキー・シークレットのハードコード禁止は当プロジェクトの標準ルール通りだが、加えてシークレットローテーションの自動化とCI/CDでのシークレットスキャン（gitleaks等）をパイプラインに組み込むことを推奨する。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORM の型安全性と移行の容易さ:** Prisma Client の自動生成型により、スキーマ変更が即座にTypeScriptの型エラーとして検出できるため、`'draft' | 'public'` のようなunion型の一貫性チェックが強力になる。Prisma Migrate でスキーマ変更を宣言的に管理し、レビュー可能なマイグレーション履歴を残せる点も本番運用で重要。

- **Supabase のRow Level Security (RLS) 活用:** 認証済みユーザーのみが自分の物件データやプロフィールにアクセスできるようRLSポリシーをDB層で強制することで、アプリケーション層のバグに依存しないセキュリティ境界を作れる。前の住人・次の住人間の個人情報保護が要件となるsumitsugiのようなサービスでは特に有効。

- **Prisma + Supabase のコネクションプーリング設計:** サーバーレス環境（Vercel等）ではDB接続数が問題になりやすいため、Supabase の PgBouncer（Transaction mode）経由の接続とPrismaの`directUrl`（マイグレーション用）を使い分ける構成が定番化している。

- **リアルタイム機能とPrismaの併用:** Supabase Realtime を使ってメッセージング機能やステータス変更通知を実装しつつ、書き込み・複雑なクエリはPrismaで型安全に行うハイブリッド構成が増えている。両者が同じPostgreSQLを見ているため整合性の設計に注意が必要。

- **Edge Functions とデータベースの地理的分散:** Supabase Edge Functions とリードレプリカを組み合わせ、ユーザーに近いリージョンからの読み取りでレイテンシを削減する構成が、グローバル展開を見据えたプロダクトで採用され始めている。MVPフェーズのsumitsugiでは優先度は低いが、スケール時の検討事項として留めておきたい。

### 7. WebAssembly Rust performance 2026

- **コンパイル最適化の進化:** Rustの`wasm-bindgen`やCargoのwasm向けプロファイルが成熟し、LTOやコードサイズ最適化(`opt-level = "z"`)を組み合わせることで、バイナリサイズを保ちつつネイティブに近い実行速度を達成できるようになっている。

- **WASI Preview 2とComponent Model:** WASI 0.2ベースのComponent Modelが実用段階に入り、Rust製Wasmモジュール同士やホスト言語との連携がゼロコピーに近い形で可能になり、サーバーサイドでのマイクロサービス的な利用が加速している。

- **SIMD・スレッド対応の標準化:** Wasm SIMDとWasm Threads（Shared Memory + Atomics）がブラウザ・ランタイム双方で標準サポートされ、Rustの`std::simd`やRayonクラスの並列処理をWasm上でも活用できるユースケースが増えている。

- **エッジランタイムでの採用拡大:** Cloudflare Workers、Fastly Compute、Fermyonなどのエッジプラットフォームが軒並みRust+Wasmを一級サポートし、コールドスタートの速さとサンドボックス分離を活かしたAPIゲートウェイ/画像処理の実装先として選ばれるケースが増えている。

- **開発体験の改善:** `wasm-pack`や`trunk`に加え、Rust製フレームワーク（Leptos, Dioxus等）のHMR・デバッグ体験が向上し、フロントエンドの一部を段階的にWasmへ移行する「部分的Wasm化」がしやすくなっている。

### 8. Next.js App Router patterns 2026

- **Server Components優先の設計:** データ取得は極力Server Componentsで完結させ、Client Componentsは`'use client'`境界を末端の小さいUIパーツに限定することで、バンドルサイズとハイドレーションコストを最小化できる。

- **Partial Prerendering (PPR) の実用化:** 静的シェルを即座に返しつつ動的部分を`<Suspense>`でストリーミングする構成が主流になり、TTFBとインタラクティブ性を両立できるため、ダッシュボードや一覧ページで積極採用する価値がある。

- **`use cache` ディレクティブによる粒度の細かいキャッシュ制御:** ルート単位ではなく関数・コンポーネント単位でキャッシュ戦略を指定できるようになり、`revalidateTag`と組み合わせた選択的再検証がパフォーマンスチューニングの主戦場になっている。

- **Server Actionsのセキュリティ境界の明確化:** フォーム送信や更新処理をServer Actionsに寄せる一方、認可チェックとZodバリデーションを各Actionの入口で必須化する設計が定着し、APIルートとの使い分け基準（公開APIかUI専用か）を明文化しておくことが重要。

- **Route Groupsとparallel/intercepting routesの実践的活用:** モーダルや多段レイアウトを`(group)`や`@slot`、`(.)`インターセプトで表現するパターンが安定し、`src/app/properties/`のような一覧＋詳細モーダル構成に適用しやすい。

### 9. Vercel Edge Functions optimization 2026

**ポイント1:** Vercel Edge FunctionsはV8アイソレート上で動作しコールドスタートがほぼゼロなため、我々の物件検索・地図表示APIなど低レイテンシが求められる箇所に適用することで、地方在住ユーザーのUX（引越し先探し体験）を改善できる。

**ポイント2:** Edge Middlewareでの認証チェックやA/Bテスト分岐は、Node.js APIに依存すると動かないため、`auth-context.tsx`まわりのセッション検証ロジックをEdge対応にする際はWeb標準API（`fetch`, `crypto.subtle`等）のみで書く必要がある。

**ポイント3:** Edge FunctionsはリージョンごとのDB接続プーリングに制約があるため、物件データのようなリレーショナルクエリはEdgeで直接実行せず、Vercel経由のData Cache（`fetch`のrevalidateタグ）やRead Replica経由での読み取りに寄せるのが2026年時点の定石。

**ポイント4:** Next.js 16のPartial Prerenderingとの組み合わせで、静的な物件一覧の骨組みをプリレンダーしつつ「空室状況」などの動的部分だけをEdgeでストリーミングする構成が主流になっており、ローンチ前のパフォーマンス最適化として効果が高い。

**ポイント5:** Edge実行環境はモニタリング面でNode.js Functionsと計装方法が異なるため、導入する場合はVercel純正のObservability（OpenTelemetry対応）を前提に設計し、独自ログ基盤への移行コストを事前に見積もっておくべき。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x系の`satisfies`演算子とconst type parametersの組み合わせが定着し、型推論を保ったままリテラル型の厳密性を維持するパターンが標準化されています。設定オブジェクトやAPIレスポンスの型付けで、型注釈を書かずに型安全性を担保できます。

- **ポイント2:** Zodなどのスキーマバリデーションライブラリから型を`z.infer`で導出する「Schema-first」開発が主流化し、APIバウンダリでの実行時検証と静的型を単一のソースで二重管理せずに済むようになっています。sumitsugiでもBoundaryでのZod活用方針と整合的です。

- **ポイント3:** テンプレートリテラル型と型レベル関数の実用範囲が広がり、ルーティングパス（Next.js App Routerの`href`型）やi18nキーの型安全性をコンパイル時に検証する事例が増えています。UI用語の日本語⇄内部データ構造（seller→前の住人など）のようなマッピング層でも応用余地があります。

- **ポイント4:** 厳格な`noUncheckedIndexedAccess`や`exactOptionalPropertyTypes`をデフォルト有効にするチームが増加し、「型は通るが実行時にundefinedで落ちる」クラスのバグを型検査段階で潰す動きが加速しています。物件ステータスのような union type（`'draft' | 'public'`）を扱う際、網羅性チェック（exhaustiveness check）と組み合わせることで、値追加時の考慮漏れをビルドで検知できます。

- **ポイント5:** モノレポ・大規模コードベースでは型チェックの実行速度がボトルネックになり、`tsgo`（TypeScriptのGoネイティブ実装）やincremental/projectReferencesの活用でCIの型検査時間を大幅短縮する事例が増えています。ビルド整合性を重視する開発フローでは、型エラーを早期・高速に検出できる基盤investmentがROIの高い改善です。
