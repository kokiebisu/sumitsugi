# CTO Knowledge - 2026-09-01

## Daily Update (2026-09-01)

### 1. Next.js performance optimization 2026

**Next.js Performance Optimization 2026 — CTO視点**

- **ポイント1（Turbopackの本番標準化）:** Next.js 16でTurbopackがビルド・開発の既定エンジンとなり、Webpack比で大幅な高速化が実現。ローンチ前の`bun run build`時間短縮に直結するため、CI時間削減の観点でも継続的に恩恵を受けられる。
- **ポイント2（Partial Prerendering / PPRの実運用化）:** 静的シェルを即座に配信しつつ動的部分をストリーミングする手法が安定期に入り、物件一覧のような「一部は静的・一部は動的（在庫状況等）」なページで初期表示速度とSEOを両立しやすくなっている。
- **ポイント3（React Compilerによる自動メモ化）:** `useMemo`/`useCallback`の手動最適化が不要になりつつあり、リスト表示や検索フィルタなど再レンダリングが頻発するUIでの実装コストと不具合リスクを削減できる。
- **ポイント4（キャッシュ戦略の明示化）:** `use cache`ディレクティブ導入により、データ取得のキャッシュ境界をコードレベルで明示できるようになった。物件データや在庫のような更新頻度が異なる情報を混在させる際のキャッシュ無効化バグを防ぎやすい。
- **ポイント5（画像・フォント最適化の継続進化）:** `next/image`のAVIF既定化やフォントのセルフホスティング自動化が進み、物件写真中心のUIでLCP（Largest Contentful Paint）改善に直接効く。ベータローンチ前のCore Web Vitals対策として優先度が高い。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPartial Prerendering（PPR）が安定版となり、静的シェルを即座に返しつつ動的部分のみストリーミングする構成が標準化。本プロジェクトの`src/app/properties/`のような一覧ページでも、静的なレイアウト部分と物件データ取得部分を分離することでTTFBを大幅に改善できる。

- **ポイント2:** `loading.tsx`とSuspenseバウンダリの粒度設計がパフォーマンスの鍵になっており、粗すぎると恩恵が薄く、細かすぎるとウォーターフォールが増える。物件詳細ページなら「価格・基本情報」「引越し費用の内訳」「前の住人インタビュー」のようにコンテンツの重要度順にバウンダリを分けるのが実践的。

- **ポイント3:** RSCとServer Actionsの組み合わせでクライアントバンドルサイズを最小化する流れが加速しており、`src/contexts/auth-context.tsx`のようなクライアントコンテキストは本当にインタラクティブな部分だけに限定し、それ以外はサーバーコンポーネントに寄せる設計判断がコスト・パフォーマンス両面で重要。

- **ポイント4:** キャッシュ戦略（`use cache`ディレクティブやタグベースの再検証）がストリーミングと組み合わさることで、物件ステータス(`draft`/`public`)の切り替えなど動的更新が必要な箇所でも、静的配信の高速性を維持しつつ最新データを保証できるようになってきている。

- **ポイント5:** エラーバウンダリとストリーミングの相性問題（ストリーム開始後のエラーでステータスコードを変更できない制約）に対する運用ノウハウが蓄積されており、決済や本人確認など失敗が許されないフローは事前にサーバーサイドでバリデーションを完了させてからストリーミングを開始する設計が推奨される。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCの採用はTypeScriptフルスタック構成（Next.js等）で拡大しており、スキーマ定義とクライアント型を自動同期できるため、社内API・BFF層では開発速度と型安全性の両立に有利。ただし外部公開APIには不向きで、パートナー連携が必要な機能では引き続きRESTかGraphQLを選ぶべき。

- **ポイント2:** GraphQLは複雑なデータ取得パターン（物件検索・フィルタリング・関連データの一括取得）で威力を発揮するが、N+1問題やキャッシュ戦略の設計コストが高く、チーム規模が小さいうちは過剰投資になりやすい。sumitsugiのような単一プロダクトでは導入優先度は低い。

- **ポイント3:** RESTは依然としてシンプルさ・キャッシュ容易性・デバッグのしやすさで強く、CDNキャッシュやHTTPセマンティクスをそのまま活用できる公開API（物件一覧・検索）には最適。2026年時点でも「迷ったらREST」が実用的な指針。

- **ポイント4:** OpenAPI/Zodスキーマからの型生成・ドキュメント自動生成が標準化しつつあり、tRPCを使わない場合でもZodスキーマを起点にAPI契約とバリデーションを一元管理する設計（既にsumitsugiのstandards.mdで定義済み）は、REST/GraphQLどちらでも型安全性のギャップを埋める現実的な選択肢。

- **ポイント5:** 認証・決済など機微データを扱うエンドポイントは、GraphQLの単一エンドポイント構成よりもREST的にリソース境界を明確に分離した設計の方が、権限制御とレート制限の実装・監査がしやすく、セキュリティレビューの観点からも推奨。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG準拠のWeb標準API（Fetch, Streams等）がCloudflare Workers・Vercel Edge・Deno Deployで共通化され、ベンダーロックインを避けたコードの可搬性が現実的になっています。sumitsugiのような物件検索・画像最適化処理は、この標準に沿って書けば将来のインフラ移行コストを抑えられます。

- **エッジDBとの統合が本命化:** Cloudflare D1/Durable Objects、Turso（libSQL）、PlanetScaleなどエッジ近接のデータレイヤーが成熟し、read-heavyな物件一覧・検索APIをオリジンDBに触れずにエッジで完結できるようになっています。sumitsugiの`properties`検索のようなread多めのエンドポイントはエッジキャッシュ+エッジDBの対象として優先度が高いです。

- **コールドスタート問題はほぼ解消:** V8 isolateベースのエッジランタイムはコールドスタートが1桁ms台まで縮み、Lambdaのようなコンテナ起動オーバーヘッドが実質不要になっています。ただしNode.js API依存（fs, 一部npmパッケージ）が使えない制約は残るため、依存ライブラリの互換性確認は必須です。

- **AI推論のエッジ配置がトレンド化:** 軽量LLM推論（要約・レコメンド）をエッジで実行するパターンが増えており、ユーザーの地理的近さ由来のレイテンシ削減効果が明確になっています。sumitsugiで将来的に「前の住人」プロフィール要約やマッチング推薦をAI化する場合、エッジ推論は検討価値があります。

- **コスト構造の変化に注意:** リクエスト課金からCPU時間課金への移行が進み、重い処理（画像変換等）をエッジに置くとコストが跳ねるケースが増えています。Next.js 16のApp Routerでは「軽い動的処理はEdge Runtime、重い処理はNode Runtime」という使い分け設計が引き続き重要です。

### 5. authentication security best practices 2026

- **パスキー(WebAuthn)の標準化:** パスワードレス認証がデファクトスタンダードとなり、フィッシング耐性のある公開鍵暗号方式への移行が加速している。sumitsugiのような個人情報を扱うプラットフォームでは、パスワード+SMS認証よりパスキーを優先実装すべき。

- **フィッシング耐性MFAの必須化:** SMS/TOTPベースのMFAはSIMスワップやリアルタイムフィッシング攻撃に弱く、FIDO2/WebAuthnベースの認証器への切り替えが業界標準になりつつある。特に決済・引越し費用のやり取りが発生する本サービスでは優先度が高い。

- **セッション管理とトークンの短命化:** 長寿命JWTのリスクが再認識され、短命アクセストークン＋リフレッシュトークンローテーション、デバイスバインディングが主流に。トークン漏洩時の被害範囲を最小化する設計が求められる。

- **ゼロトラスト型の認可設計:** 認証後も継続的にリスクスコアを評価し、異常な操作（例: 異なる地域からの物件情報編集）には再認証を要求する適応的認証(Adaptive Authentication)が普及。

- **AIを悪用した攻撃への対策:** ディープフェイク音声・生成AIによるなりすまし申請が増加しており、本人確認(KYC)フローにはライブネス検出付きの生体認証や複数要素の突合が必要になっている。前の住人・次の住人間の本人確認プロセスにも影響する論点。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMのマルチドライバ対応が標準化:** Prisma 6以降、Supabase（PostgreSQL）向けにPgBouncer経由のコネクションプーリングとPrisma Accelerateのエッジキャッシュ層が統合され、サーバーレス環境でのコールドスタート問題とコネクション枯渇が大幅に緩和されている。実装時は`DATABASE_URL`と`DIRECT_URL`を分離し、マイグレーションは直接接続、ランタイムクエリはプーラー経由にする構成が必須。

- **Row Level Security（RLS）とORMの併用が実質デファクト:** SupabaseのRLSポリシーとPrismaのスキーマ管理を組み合わせることで、アプリ層のバリデーションとDB層の権限制御を二重に担保できる。sumitsugiのような住宅情報プラットフォームでは、`property.status`（draft/public）や前の住人の個人情報アクセス制御をRLSで強制し、アプリバグによる情報漏洩リスクを最小化すべき。

- **Prisma Migrateのスキーマドリフト検知が本番運用の必須プラクティスに:** Supabase側で手動DDL変更（ダッシュボードからのカラム追加など）が発生するとPrismaのマイグレーション履歴と乖離するため、CI上で`prisma migrate diff`を毎回実行しドリフトを検知するフローが2026年時点のベストプラクティスとして定着している。

- **pgvector + Prismaによる検索機能の一次DB内蔵化:** 物件検索やマッチング機能（IC consultation matching等）において、専用ベクトルDBを別立てせずSupabaseのpgvector拡張をPrisma経由で扱う構成がコスト・運用面で優位。Prismaのraw query（`$queryRaw`）でベクトル演算を行い、通常のリレーショナルクエリと同一トランザクション内で完結できる。

- **Edge Functions + Prisma Client Rust実行環境の相性改善:** Supabase Edge Functions（Deno）とPrisma Client間の非互換が長らく課題だったが、Prisma 6の軽量Wasmエンジンにより解消されつつある。ただしsumitsugiの現行スタック（Next.js App Router）では、DBアクセスをServer Components/Route Handlersに集約し、Edge Functionsは通知等の副次処理に限定する設計が引き続き堅実。

### 7. WebAssembly Rust performance 2026

- **ポイント1（Component Model成熟）:** WASM Component ModelとWASIプレビュー2が2025-2026年で実用段階に入り、Rustのcargo-componentツールチェーンが安定化。異なる言語で書かれたWASMモジュール間の連携がゼロコストに近づき、マイクロサービスをWASMコンポーネントとして構成する設計が現実的になっている。

- **ポイント2（SIMD・スレッドの標準化）:** WASM SIMD128とスレッド（共有メモリ+Atomics）がブラウザ・サーバーランタイム双方でデフォルト有効化され、Rust側は`std::simd`やwasm-bindgenの対応が進んだ。画像処理・数値計算系のワークロードでネイティブ比80-90%の性能が出るケースが増えている。

- **ポイント3（起動時間とコールドスタート）:** WasmtimeやWasmerのAOTコンパイル・プリコンパイルキャッシュ機能により、RustコンパイルWASMのコールドスタートがミリ秒単位に短縮。サーバーレス/エッジ環境（Fastly Compute、Cloudflare Workers等）でNode.js比で優位性が明確になっている。

- **ポイント4（メモリ安全性とサンドボックス）:** RustのメモリセーフティとWASMのサンドボックス実行が組み合わさり、プラグインシステムやマルチテナントの信頼できない実行環境として採用が拡大。sumitsugiのような不動産プラットフォームでも、ユーザー入力を扱う変換処理（画像リサイズ等）を隔離実行する用途で検討価値がある。

- **ポイント5（バンドルサイズ最適化の限界打破）:** `wasm-opt`とRustの`panic=abort`+`opt-level=z`の組み合わせに加え、2026年はLLVMのWASM向けコード生成改善で、従来より20-30%小さいバイナリが得られるようになった。フロントエンドでの部分的なWASM活用（重い計算処理のみオフロード）がより現実的な選択肢になっている。

### 8. Next.js App Router patterns 2026

- **ポイント1（Server Components前提の設計）:** App RouterではServer Componentsがデフォルトとなり、データフェッチをコンポーネント内で直接行う設計が主流に。クライアントバンドルを最小化するため、`'use client'`境界は末端のインタラクティブ要素のみに限定するのがベストプラクティス。

- **ポイント2（Partial Prerendering / PPRの本格運用）:** 静的シェルを即座に配信しつつ動的部分をストリーミングするPPRが2026年には安定運用フェーズに入り、ECサイトや物件検索など「一部だけ動的」なページのTTFB改善に有効。sumitsugiの物件一覧・詳細ページのような静的+動的混在UIと相性が良い。

- **ポイント3（キャッシュ戦略の明示化）:** `fetch`のデフォルトキャッシュ挙動が変化し続けているため、`cacheLife`/`cacheTag`など明示的なキャッシュAPIを使い、意図しないstaleデータや過剰な再検証を防ぐ設計が必須。特に物件ステータス（draft/public）のような頻繁に変わるデータは`revalidateTag`での明示的無効化が安全。

- **ポイント4（Server Actionsのセキュリティ境界）:** Server Actionsは便利だが実質的に公開APIエンドポイントになるため、認証・入力検証（Zod等）をアクション内部で必ず行う必要がある。フォーム送信や引越し費用計算など機密性の高い処理では、クライアント側のUI制御に頼らずサーバー側で権限チェックを徹底すべき。

- **ポイント5（ルーティング構造とパフォーマンス計測の一体化）:** Parallel RoutesやIntercepting Routesを使ったモーダル型UI（物件詳細のクイックビューなど）が定着しつつある一方、`next/dynamic`や`loading.tsx`の粒度設計がCore Web Vitalsに直結するため、機能追加時は必ずルートセグメント単位でのバンドルサイズ計測を組み込むべき。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの標準化:** Vercel Edge FunctionsはV8 isolateベースでの起動が数十ミリ秒以下まで最適化が進み、Node.js Runtimeとの機能差が縮小しているため、レイテンシ重視のAPIは積極的にEdgeへ寄せるべきです。
- **Streaming SSRとの組み合わせ:** React Server Componentsのストリーミングレンダリングをエッジで実行することで、TTFB（Time to First Byte）を大幅に短縮できるため、一覧ページや検索結果など初期表示速度が重要な画面から優先的に移行すると効果が高いです。
- **リージョン最適化とデータ近接性:** Edge Config・KVストアをユーザーに地理的に近いリージョンに配置し、DBアクセスを伴う処理はEdgeからNode Runtimeへフォールバックする「ハイブリッド構成」が2026年のベストプラクティスとして定着しています。
- **コールドスタート対策としてのミドルウェア分離:** 認証チェックやリダイレクトなどの軽量ロジックのみをmiddleware.tsに残し、重い処理を通常のRoute Handlerに分離することで、Edge実行時間の課金対象を最小化しコストを抑えられます。
- **可観測性の強化:** Vercelのランタイムログとトレーシングがエッジ関数にも対応してきており、本番導入前にステージング環境でレイテンシ分布とエラー率を計測してから段階的にロールアウトする運用が推奨されます。

### 10. TypeScript type safety patterns 2026

**TypeScript type safety patterns 2026**

- **ポイント1（Zod/Valibotによる境界検証の標準化）:** API入力・フォームデータなど外部境界では、型定義だけでなくランタイムスキーマ（Zod等）で検証するパターンが主流化。`z.infer`で型とバリデーションを一元管理し、二重定義を防ぐのが定石になっています。
- **ポイント2（`satisfies`演算子の定着）:** TS 4.9で導入された`satisfies`が、設定オブジェクトや定数マップの型安全性を保ちつつリテラル型推論を維持する手法として普及。`as const`との組み合わせでUI用語マッピング（例: `seller`→表示用日本語）のような固定辞書に有効です。
- **ポイント3（Discriminated Unionによる状態管理の徹底）:** `'draft' | 'public'`のようなステータス型は単純なUnionだけでなく、関連フィールドを含むDiscriminated Unionに拡張し、`switch`文の網羅性チェック（`never`型での分岐漏れ検出）と組み合わせるパターンが定着しています。
- **ポイント4（型のみインポートの明示化）:** `import type`の徹底利用がビルド高速化とTree-shakingの観点で標準化。Next.js 16のようなApp Router環境では、Server/Client Component境界で型と実装の分離がバンドルサイズに直結するため重要性が増しています。
- **ポイント5（Branded Typesによるプリミティブの誤用防止）:** `UserId`と`PropertyId`のような同じ`string`型でも意味の異なるIDをBranded Type（`type UserId = string & { __brand: 'UserId' }`）で区別し、コンパイル時に取り違えを防ぐパターンが、DB/APIレイヤーの多いプロジェクトで実用的な効果を上げています。
