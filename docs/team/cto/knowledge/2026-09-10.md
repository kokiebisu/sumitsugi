## Daily Update (2026-09-10)

### 1. Next.js performance optimization 2026

## Next.js Performance Optimization 2026 — CTO視点

- **ポイント1（Partial Prerendering の本格活用）:** Next.js 16ではPPRが安定化し、静的シェルを即座に返しつつ動的部分のみストリーミングできる。物件一覧ページなど「ヘッダーは静的、価格・空室状況は動的」という構成に最適で、TTFBを大幅に短縮できる。

- **ポイント2（'use cache' ディレクティブによる明示的キャッシュ制御）:** データフェッチ単位で `'use cache'` を付与し、キャッシュのライフタイムやタグを明示的に管理する運用が主流化。`src/lib/data.ts` のような共通データ層に導入すれば、再検証コストを抑えつつ最新データを保証できる。

- **ポイント3（Turbopackのビルド/devデフォルト化）:** Turbopackが本番ビルドでも安定運用フェーズに入り、CIのビルド時間短縮に直結する。`bun run build` の時間が長くなってきたらTurbopack移行を検討すべきタイミング。

- **ポイント4（RSCペイロード最小化とクライアントJS削減）:** shadcn/uiのようなコンポーネントは基本サーバーコンポーネントのまま保ち、`'use client'` 境界を末端の小さなインタラクティブ部分（フォーム、モーダル等）に限定することで、バンドルサイズと水和コストを抑える。

- **ポイント5（Edge/CDN配置とObservability）:** 認証やDB問い合わせを伴わないページはEdge Runtimeで配信し、OpenTelemetry連携で「どのServer Actionが遅いか」を可視化する体制を今のうちに整えておくと、ローンチ後のスケール対応がスムーズ。

### 2. React Server Components streaming 2026

- **段階的ハイドレーションの標準化:** RSCとSuspenseによるストリーミングSSRが定着し、`loading.tsx`やネストされた`<Suspense>`境界を細かく設計することで、重いデータ取得を待たずに画面の主要部分から順次表示できる。これによりTTFBとLCPを分離して最適化できる点が実用上の肝。

- **Server Actionsとの統合が進みフォーム処理が簡素化:** クライアント側のfetch呼び出しやAPI Routeの記述量が減り、`use server`関数を直接コンポーネントから呼べるため、うちのプロパティ登録・問い合わせフォームのようなCRUD処理はコード量・バグ面積ともに削減できる。

- **キャッシュ戦略の複雑化に注意:** `fetch`のデフォルトキャッシュ挙動やRouter Cacheの仕様がバージョンごとに変わりやすく、公開/下書きステータス（`draft`/`public`）のような状態を扱う画面では、意図しない古いデータ表示（stale content）のリスクがあるため、`revalidateTag`や`revalidatePath`を明示的に設計する必要がある。

- **Client Componentsとの境界設計がパフォーマンスを左右する:** "use client"の乱用でバンドルサイズが肥大化するケースが多く、インタラクティブな部分（お気に入りボタン、フィルターUI等）だけを切り出し、それ以外はServer Componentのまま保つ設計判断が、実際のCore Web Vitalsに直結する。

- **エッジランタイムとの相性:** ストリーミングレンダリングはVercelなど各ホスティングのエッジ実行環境と組み合わせることで地理的レイテンシを削減できるが、Node.js APIに依存するライブラリ（画像処理・PDF生成など）はEdge Runtime非対応な場合があり、事前の依存関係確認が必須。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCとGraphQLの用途分離が明確化）:** 2026年はtRPC/gRPCが「フルスタックTypeScript内部通信」、GraphQLが「複数クライアント・複雑な集約クエリ」、RESTが「公開API・シンプルなCRUD」という役割分担が定着しつつあります。sumitsugiはNext.js App Router単体構成なので、内部API層はtRPCまたはServer Actionsで型安全性を優先するのが合理的です。

- **ポイント2（Server Actionsによる境界の再設計）:** Next.js 16世代ではServer Actionsが従来のREST/tRPC的な役割を一部代替し、フロント〜バックエンドの型共有コストがさらに下がっています。物件登録・引越し費用計算など多段フォームのミューテーションはServer Actionsに寄せることで、Zodバリデーションと型推論をエンドツーエンドで一本化できます。

- **ポイント3（BFF/エッジ集約パターンの普及）:** 外部連携（決済、地図API等）が増えるフェーズでは、クライアントに複数APIを直接叩かせず、Edge Runtime上のBFF層で集約・キャッシュするパターンが主流化しています。ローンチ後に外部サービス連携が増える想定なら、早期にBFF層を`src/app/api/`配下に薄く用意しておくと後の拡張が楽になります。

- **ポイント4（スキーマファースト＋契約テストの標準化）:** OpenAPI/GraphQL SDLだけでなく、Zodスキーマから型・ドキュメント・バリデーションを自動生成する「コードファースト・スキーマ駆動」が2026年の主流です。すでにZodをバウンダリで使う方針があるので、ここからOpenAPI生成やクライアントSDK自動生成まで拡張するのは低コストで高ROI。

- **ポイント5（パフォーマンス指標としてのレイテンシ予算管理）:** API設計はエンドポイント単位でなく「ユーザー操作単位のレイテンシ予算」で評価する流れが強まっています。物件検索・引越しフロー等のユーザー体験クリティカルな操作は、N+1やover-fetchingを避けるためGraphQL的な必要フィールド選択かtRPCのバッチ機能を検討する価値があります。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG/WinterTCによるWeb標準API（Fetch, Streams）への収斂が進み、Cloudflare Workers・Vercel Edge・Deno Deployなど各ベンダー間でのコード可搬性が2026年時点でほぼ実用レベルに達している。移行ロックインを恐れず採用しやすい。

- **エッジでのステートフル処理:** Durable Objects（Cloudflare）やCloudflare D1/Turso（SQLite系）の成熟により、従来はオリジンでしか扱えなかったセッション状態やトランザクションがエッジ側で完結できるようになり、レイテンシとオリジン負荷の両方を削減できる。

- **AI推論のエッジシフト:** 小型LLM（3B〜8B級）の量子化技術向上により、簡易な分類・要約・パーソナライゼーションをエッジ上で完結させる構成が現実的になった。中央のClaude API呼び出しと使い分けることでコストとレイテンシを最適化できる。

- **コールドスタート問題の実質解消:** V8 Isolateベースのランタイムが主流化し、コンテナ型FaaS比でコールドスタートが1桁ms台に短縮された。sumitsugiのような日本国内向けサービスでも、東京リージョン以外のエッジPoPから配信してもUXへの影響が無視できるレベルになっている。

- **実務上の注意点:** Next.js 16のEdge RuntimeはNode.js API互換性が限定的なため、Prisma等の一部ライブラリはNode.jsランタイムへのフォールバックが必要。ページ単位で`runtime: 'edge' | 'nodejs'`を明示的に使い分ける設計判断が引き続き重要。

### 5. authentication security best practices 2026

**CTO視点:CTOとして技術的な観点から回答します。**

- **ポイント1(パスキー/FIDO2への移行):** パスワードレス認証(WebAuthn/パスキー)が2026年のデファクトスタンダードになりつつあり、フィッシング耐性が高くユーザー体験も向上する。当プラットフォームでもメール/パスワード認証に加えて段階的にパスキー対応を検討すべき。
- **ポイント2(トークン管理の厳格化):** JWTのショートリブド化+リフレッシュトークンのローテーション(reuse detection付き)が標準になっており、`httpOnly`/`Secure`/`SameSite=Strict`クッキーでの管理が必須。ローカルストレージへのトークン保存はXSSリスクのため避けるべき。
- **ポイント3(多層防御とレート制限):** ログイン試行・パスワードリセットへのレート制限、IPベースの異常検知、CAPTCHA/デバイスフィンガープリンティングの組み合わせがブルートフォース・クレデンシャルスタッフィング対策の基本セットになっている。
- **ポイント4(ゼロトラスト×セッション管理):** セッション固定攻撃対策として認証成功時のセッションID再生成、デバイス/場所変更時の再認証要求(ステップアップ認証)が重要。特に「前の住人」から「次の住人」への引き継ぎフローでは、本人確認の強度を機微情報(鍵の受け渡し等)に応じて動的に変える設計が有効。
- **ポイント5(サプライチェーン/依存関係の監査):** 認証ライブラリ(NextAuth/Auth.js等)のCVE監視を自動化し、Zodによる入力検証を認証境界(ログイン・サインアップAPI)で徹底することが、OWASP Top 10対策の基本線として引き続き重要。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prismaはv6以降でPostgreSQL向けのネイティブなRow Level Security(RLS)連携が強化されており、SupabaseのRLSポリシーとPrismaスキーマを併用する際は、Prisma Client経由のクエリがRLSをバイパスしないよう、サービスロールキーとanonキーの使い分けを明確に設計する必要がある。

- **ポイント2:** SupabaseのConnection Pooler（PgBouncer/Supavisor）とPrismaのコネクション管理は相性問題が出やすく、サーバーレス環境（Vercel等）ではPrisma Accelerateやpgbouncer=trueオプションを設定しないとコネクション枯渇が発生しやすい。本プロジェクトのようなNext.js App Router構成では特に注意が必要。

- **ポイント3:** Prisma SchemaとSupabase Migrationsの二重管理は事故の元になるため、どちらか一方をSingle Source of Truthとして採用し、`prisma db pull`または`supabase db diff`で一方向に同期するフローを確立するのがベストプラクティス。

- **ポイント4:** 2026年時点ではPrismaのRust製クエリエンジンからTypeScriptネイティブエンジン（Prisma ORM v6+のPrisma Client Rustless）への移行が進んでおり、Edge Runtime（Vercel Edge Functions等）との互換性が向上している。エッジデプロイを検討するなら移行の恩恵が大きい。

- **ポイント5:** `seller`/`public`/`draft`のようなステータス管理は、SupabaseのPostgres Enum型をPrisma側でミラーリングする形が型安全性とDB制約の二重保証になるため推奨。union type変更時は本プロジェクトのルール通り、コード内のgrepに加えてDBマイグレーションも同時に確認する運用が必須。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデルの本格普及:** WebAssembly Component Model (WASI Preview 2)が主要ランタイム（wasmtime, wasmer）で安定し、Rustの`wit-bindgen`を使った言語間相互運用が実用レベルに到達。マイクロサービス的にWasmモジュールを組み合わせる設計がしやすくなっている。

- **SIMD・スレッド対応の成熟:** `wasm32-wasip1-threads`やSIMD拡張がRustのstableツールチェーンで扱いやすくなり、画像処理・暗号化・ML推論などCPU集約タスクでネイティブに近い性能が出せるように。ブラウザ側とサーバーサイド（wasmCloud, Spinなど）両方でスレッド並列が現実的な選択肢になっている。

- **バイナリサイズとコールドスタートの最適化:** `wasm-opt`, `twiggy`によるサイズ最適化、`wee_alloc`後継のアロケータ戦略が洗練され、エッジ環境（Cloudflare Workers, Fastly Compute）でのコールドスタートがミリ秒単位まで縮小。サーバーレス用途でRust+Wasmが第一候補になりつつある。

- **デバッグ・プロファイリング環境の改善:** DWARF対応が進みブラウザDevToolsやVSCodeでのソースマップ付きデバッグが実用化。パフォーマンスボトルネックの特定が「Wasmだから見えない」から「ネイティブと同等に可視化できる」状態に近づいている。

- **JS-Wasm境界コストの低減:** `wasm-bindgen`の呼び出しオーバーヘッド削減や、Interface Typesによる文字列・複合型の直接受け渡しが進み、頻繁なJS↔Wasm往復を伴うUIロジックでもパフォーマンス劣化が目立ちにくくなっている。sumitsugiのようなNext.jsアプリで画像処理や検索ロジックの一部をWasm化する際の障壁が下がっている。

### 8. Next.js App Router patterns 2026

- **React Server Components のデフォルト化:** App Routerでは全コンポーネントがデフォルトでサーバーコンポーネントとなり、クライアントバンドルサイズを大幅に削減できる。`'use client'`は本当にインタラクティブな部分にのみ絞り込むのがベストプラクティス。

- **Partial Prerendering (PPR) の本格運用:** 静的シェルを即座に返しつつ動的部分を`Suspense`でストリーミングする手法が主流化し、TTFBとインタラクティブ性を両立できる。物件一覧ページのような一部動的・一部静的なUIに特に有効。

- **Server Actions によるフォーム処理の簡素化:** APIルートを経由せず`'use server'`関数を直接呼び出すパターンが定着し、引越し費用の見積もりフォームなど多段階フローの実装コストを削減できる。ただし入力検証（Zod）とCSRF対策は引き続き明示的に実装する必要がある。

- **キャッシュ戦略の明示化:** Next.js 15以降でfetchのデフォルトキャッシュ挙動が変更されたため、`revalidate`や`cache: 'no-store'`を意図的に指定する設計が必須になった。物件ステータス（draft/public）のような頻繁に変わるデータは特に注意。

- **Route Handlers とミドルウェアの軽量化:** エッジランタイムでの実行制約を意識し、認証チェックなど重い処理はミドルウェアから機能単位のガードへ移す設計が推奨されている。認証まわりの変更は必ずセキュリティレビューを経ること。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約を前提にした設計:** Node.js APIが使えないEdge Runtimeでは、依存パッケージの選定段階でWeb標準API（fetch, Streams）ベースのライブラリに寄せることで、コールドスタートを数十ms単位で削減できる。

- **Streaming SSRとの組み合わせ:** Vercel Edge FunctionsとReact Server Componentsのストリーミングを組み合わせることで、TTFB（Time to First Byte）を大幅短縮できるが、キャッシュ戦略（`fetch`のrevalidate設定）を誤るとエッジ側で過剰な再計算が発生するため、Cache-Controlヘッダーの明示的な設計が必須。

- **Regional Edge実行の使い分け:** 全リージョンでの実行がデフォルトで最適とは限らず、DBやAPIの物理的な近接性を考慮して`regions`オプションで実行リージョンを絞ることで、レイテンシとコストの両方を改善できるケースが多い（特にsumitsugiのような単一リージョン主体のユーザー基盤では有効）。

- **Middlewareの肥大化に注意:** 認証チェックやリダイレクトロジックをEdge Middlewareに詰め込みすぎると、全リクエストで実行されるため、軽量な条件分岐のみに留め、重い処理はページ側のServer Componentに委譲する設計が2026年のベストプラクティスとして定着している。

- **Observability統合:** Vercelの`waitUntil`とOpenTelemetryの統合が進み、Edge Function内での非同期ロギング・メトリクス送信がレスポンスをブロックせずに行えるようになったため、本番運用時のデバッグ性が大きく向上している。

### 10. TypeScript type safety patterns 2026

- **型推論の限界を明示する `satisfies` 演算子の定着:** TypeScript 5系で導入された `satisfies` が2026年には標準的な設計パターンとして定着し、型の広がりを保ちつつ厳密なチェックを両立できる。本プロジェクトでも `site-config.ts` のような設定オブジェクトに適用すると、型安全性を落とさずに具体的なリテラル型推論を維持できる。

- **Zodなどスキーマファーストのランタイム検証との統合:** コンパイル時の型と実行時の検証を二重管理せず、Zodスキーマから型を`z.infer`で導出する手法が主流化している。`.claude/rules/standards.md`で定めている「システム境界でのZodバリデーション」方針と直結しており、フォーム入力やAPI境界での型ズレを防げる。

- **Branded Types / Nominal Typingによる意味的区別の強化:** `sellerId`と`buyerId`のように構造が同じでも意味が異なるstring型を、branded typesで区別する手法が実用パターンとして広がっている。物件ステータスの`'draft' | 'public'`のようなUnion型でも、値の混同を防ぐ設計に応用可能。

- **strictな型チェックのCI必須化がデファクト化:** `tsc --noEmit`をCIのビルドステップに含めることが業界標準になりつつあり、本プロジェクトの「Build Integrity」ルール（`bun run build`必須）は先取りした実践と言える。型のUnion値を変更する際に全使用箇所をgrepする運用も、これに沿ったベストプラクティス。

- **AIコード生成時代の型定義の重要性向上:** LLMによるコード生成が一般化する中、型定義自体が「仕様書」として機能し、AIが生成するコードの正しさを型チェックで担保する運用が普及している。型の緩さがAI生成コードのバグを見逃す原因になりやすいため、strictモードの徹底がより重要になっている。
