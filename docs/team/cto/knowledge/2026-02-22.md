# CTO Knowledge - 2026-02-22

## Daily Update (2026-02-22)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降でPPRが安定化し、静的シェルと動的コンテンツを同一ページで混在させることで、TTFBを維持しながらパーソナライズが可能になった。`experimental.ppr` から正式APIへの移行を優先すべき。

- **React Server Components (RSC) によるバンドルサイズ削減:** サーバー専用ロジックをRSCに移すことでクライアントJSを大幅削減できる。`"use client"` の境界を最小化し、重いライブラリ（chart.js等）はサーバー側に閉じ込めるのが定石。

- **`next/image` + `next/font` の徹底活用:** CLS（累積レイアウトシフト）対策として画像の`sizes`属性とフォントの`display: swap`は必須。2026年時点でこれを省略するプロジェクトはCore Web Vitalsで確実に減点される。

- **Turbopack の本番利用開始:** Next.js 15.xでTurbopackが安定し、大規模プロジェクトでのビルド時間が従来比最大70%短縮。`next dev --turbopack` から `next build` への対応も進んでおり、段階的移行を検討すべきタイミング。

- **Edge Runtime の選択的適用:** ミドルウェアや認証チェックはEdge Runtimeで低レイテンシを確保しつつ、DB接続が必要なAPIはNode.js Runtimeを維持するハイブリッド戦略が最適。全てをEdgeに寄せるとコールドスタートや制約で逆効果になるケースがある。

### 2. React Server Components streaming 2026

- **ポイント1:** RSC + Suspense によるプログレッシブ配信が標準化  
  React 19 以降、`<Suspense>` バウンダリを活用したストリーミング HTML 配信が Next.js App Router の主流パターンとなり、TTFB を大幅に短縮できる。重いデータ取得コンポーネントを境界で囲むだけで UX が向上する。

- **ポイント2:** `use()` フックによるデータフェッチの簡素化  
  React 19 の `use(promise)` により、サーバーコンポーネント内での非同期処理がより宣言的になり、Suspense との組み合わせでウォーターフォール問題を回避しやすくなっている。

- **ポイント3:** エッジランタイムとのシナジーが鍵  
  Vercel Edge / Cloudflare Workers など Edge 環境でのストリーミングが本格化しており、地理的に近いサーバーから部分的な HTML を即座に返すことで、グローバルユーザーの体感速度が劇的に改善される。

- **ポイント4:** PPR（Partial Prerendering）との組み合わせで静的・動的の境界が消える  
  Next.js の PPR により、ページの静的部分を CDN キャッシュしつつ動的部分をストリーム配信する設計が可能になり、「静的か動的か」という二択から解放される。

- **ポイント5:** クライアントコンポーネントの責務を最小化する設計が重要  
  RSC ストリーミングの恩恵を最大化するには、`'use client'` の範囲を末端のインタラクティブ要素に限定するアーキテクチャ設計が不可欠。バンドルサイズ削減とストリーミング効率は表裏一体。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全API:** tRPCはNext.js/TypeScriptスタックでの採用が急増し、2026年時点ではフルスタックTS環境の事実上の標準に近づいている。スキーマ定義不要でエンドツーエンドの型安全性が得られる点が開発速度を大幅に向上させる。

- **REST vs GraphQLの収束:** 新規プロジェクトでの"純粋REST"は減少傾向にあり、GraphQLも複雑性コストが再評価されている。代わりに、REST + OpenAPIスキーマ自動生成（Hono、ElysiaJS等）でGraphQL並みの型安全性を低コストで実現するアプローチが現実解として浮上している。

- **エッジ・サーバーレス向けAPI設計の最適化:** Cloudflare Workers / Vercel Edge Runtimeの普及により、コールドスタートを意識した軽量APIフレームワーク（Hono等）が主流になりつつある。従来のExpressベース設計は見直しが必要。

- **API契約駆動開発（Contract-First）の復権:** OpenAPI 3.1やProtobuf等のスキーマを先に定義し、クライアント・サーバー双方のコードを自動生成するワークフローが普及。`orval`や`buf`等のツールチェーンが成熟し、手書きAPIクライアントは技術的負債とみなされる傾向。

- **AIエージェント対応API設計の重要性:** LLMエージェントがAPIを呼び出すユースケースの増加に伴い、OpenAPI仕様の記述品質（`description`フィールド等）がそのままエージェントの精度に直結する。2026年以降、APIは人間だけでなくAIエージェントのファーストクラス消費者として設計する必要がある。

### 4. serverless edge computing 2026

- **ポイント1: エッジでのAI推論の標準化** WebAssembly（WASM）とWASIの成熟により、軽量LLMをエッジノードで実行するパターンが普及。レイテンシを大幅削減しつつ、プライバシー要件（GDPR等）にも対応できる。

- **ポイント2: ステートフルエッジの台頭** Cloudflare Durable Objects・Fastly Compute@Edgeなどがエッジでの永続状態管理を実現し、「エッジ＝ステートレス」の前提が崩壊。セッション管理やリアルタイム同期をエッジで完結できる設計が現実的になった。

- **ポイント3: Cold Startの事実上の解消** V8 Isolatesや事前ウォームアップ戦略の進化で、エッジのCold Startは数ms以下に。従来のサーバーレス（Lambda等）との差別化ポイントとして、レイテンシSLAの厳格な要件に対応可能になった。

- **ポイント4: エッジネイティブなオブザーバビリティ** 分散エッジ環境でのトレーシング・ログ集約が課題だったが、OpenTelemetry + エッジ対応のコレクターにより、分散トレースの統合が実用段階に。デバッグコストが大幅に改善されている。

- **ポイント5: マルチクラウドエッジのベンダーロック警戒** AWS Lambda@Edge・Cloudflare Workers・Vercel Edge Functionsの仕様差異が依然として大きく、抽象化レイヤー（Hono.js等）の採用が重要。今後のポータビリティを確保するためWASMベースのランタイム標準化動向を注視すべき。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の本格普及:** FIDO2/WebAuthn準拠のパスキーがパスワードレス認証の標準となり、フィッシング耐性と利便性を両立。主要プラットフォーム（Apple/Google/Microsoft）が対応済みのため、新規実装はパスキーファーストで設計すべき。

- **AIを活用した異常検知:** 機械学習による行動ベースの認証（デバイス特性、タイピングパターン、地理的移動）が不正アクセス検知の精度を大幅向上。静的なルールベースのみのリスク評価は時代遅れ。

- **MFAの「疲弊攻撃」対策:** MFAプッシュ通知の連打でユーザーを騙す「MFA Fatigue Attack」が増加。Number matchingや位置情報の確認を組み合わせたコンテキスト認証が必須対策。

- **トークンライフタイムの最小化とRTR（Refresh Token Rotation）:** アクセストークンは15分以内、リフレッシュトークンはローテーション＋ワンタイム使用を徹底。Token Theftシナリオへの耐性が大幅向上する。

- **サプライチェーン認証リスクの管理:** OAuth/OIDCライブラリへの依存は依然高リスク。定期的なdependency auditと、認証フロー自体の侵入テスト（特にOAuth Misconfiguration）を開発サイクルに組み込むことが重要。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のパフォーマンス改善:** Prisma 6でクエリエンジンがRustからTypeScriptネイティブへ移行し、コールドスタートが大幅に短縮。Next.js App RouterやEdge Runtimeとの相性が向上し、サーバーレス環境での実用性が増した。

- **Supabase Branching の普及:** データベースのブランチ機能が安定化し、PRごとにステージング環境を自動生成するワークフローが標準化。本番DBへのマイグレーションリスクを大幅に低減できる。

- **PrismaとSupabaseの直接統合:** `prisma generate --accelerate` によるSupabase + Prisma Accelerateの組み合わせが主流化。接続プーリングをPrismaレイヤーで管理することでSupabaseの同時接続制限問題を回避できる。

- **Row Level Security (RLS) との設計整合性:** SupabaseのRLSポリシーとPrismaのデータアクセス層を適切に分離することが重要。PrismaはサーバーサイドのService Role経由で使用し、クライアント向けはSupabase JSクライアント + RLSで制御する二層設計がベストプラクティス。

- **pgvector × AI統合の標準化:** Supabaseの`pgvector`拡張とPrismaの`Unsupported("vector")`型を組み合わせたベクトル検索が実用段階に。RAGアーキテクチャをPrismaスキーマに統合する際は、生SQLのフォールバックを前提とした設計が現実的。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデルの成熟:** WebAssembly Component Model（WASI 0.2以降）が2025年に安定化し、RustでビルドしたWasmモジュール間の型安全な相互運用が実用レベルに達した。`cargo component`ツールチェーンにより、マイクロサービス的なWasmコンポーネント設計が現実的な選択肢になっている。

- **SIMD・スレッドの標準化完了:** Wasm SIMD128とShared Memoryが主要ランタイム（Wasmtime、V8、WasmEdge）で完全対応済み。RustのSIMDイントリンシクスがそのままWasmにコンパイルされ、数値計算・画像処理で**ネイティブの70-90%**のパフォーマンスが出るケースが増えている。

- **WASIp2によるサーバーサイド活用の拡大:** Fastly・CloudflareのエッジランタイムがWASI Preview 2を採用し、RustのWasmバイナリをコールドスタートほぼゼロでデプロイ可能に。Next.jsのEdge Runtimeとの統合も進み、重い処理をWasmにオフロードするパターンが増えている。

- **Wasmtime JITの最適化深化:** Craneliftバックエンドの改善により、長時間稼働ワークロードでのJITウォームアップコストが大幅削減。Rustで書いたAI推論・パーサー・暗号処理を、**セキュアなサンドボックス内でネイティブに近い速度**で実行できる実績が蓄積されている。

- **ツールチェーンの整備（`wasm-bindgen` → `wit-bindgen`移行）:** `wasm-bindgen`中心のエコシステムから、WIT（WebAssembly Interface Types）ベースの`wit-bindgen`へのシフトが進行中。既存のRust Wasmプロジェクトを中長期でComponent Model対応に移行する計画を今から立てておくことが、技術的負債回避の観点で重要。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点でApp RouterのServer Componentsが成熟し、クライアントバンドルを最小化する設計が標準化。`'use client'`は本当にインタラクティブな境界にのみ使用し、データフェッチはサーバー側に集約するのがベストプラクティス。

- **Partial Prerendering (PPR) の本格採用:** Next.js 15以降でPPRが安定化し、静的シェルと動的ストリーミングを同一ルートで混在させるパターンが普及。`<Suspense>`境界の設計がパフォーマンスの要になっている。

- **Server Actions によるAPI層の簡略化:** フォーム送信やミューテーションをServer Actionsで処理することで、APIルートを別途作成する必要が減少。ただし認証・バリデーション（Zod）を必ずサーバー側で行うセキュリティ設計が必須。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15の`use cache`によりコンポーネント・関数レベルでのキャッシュ制御が可能になり、`revalidatePath`/`revalidateTag`と組み合わせたon-demand再生成が主流のキャッシュ戦略に。

- **Turbopack の実用化とビルド高速化:** Turbopackがデフォルトのdev bundlerとして安定化し、大規模プロジェクトでのHMRが劇的に高速化。CI/CDでのビルド時間短縮にも寄与しており、`bun run build`との組み合わせで開発体験が大幅向上。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタートの最小化:** Edge Functionsは従来のServerless Functionsと異なりV8 Isolateベースで動作するため、コールドスタートがほぼゼロ。ただしバンドルサイズ上限（1MB）を超えると初期化コストが跳ね上がるため、依存関係の厳選とtree-shakingが最重要施策となる。

- **Streaming Responseの積極活用:** Edge RuntimeはWeb Streams APIをネイティブサポートしており、LLM応答やSSR結果をストリーミング配信することでTTFB（初回バイト到達時間）を大幅改善できる。Next.js App RouterのSuspense境界との組み合わせが2025-2026年の主流パターン。

- **Node.js互換性レイヤーの拡張対応:** Vercelは段階的にEdge RuntimeへのNode.js API追加を進めており、以前は使えなかった`crypto`や`buffer`が利用可能になった。ただし`fs`等は依然未対応のため、既存コードの移植時はランタイム互換性チェックを自動化することを推奨。

- **Middlewareのコスト管理:** 全リクエストを通過するMiddlewareに重い処理を入れると、レイテンシではなくコスト面でボトルネックになる。matcher設定で対象パスを絞り込み、認証トークン検証程度の軽量処理に留めるのがベストプラクティス。

- **KV・Durable Objectsとの連携設計:** Edge FunctionsからVercel KVやCloudflare Durable Objectsへのアクセスは同一リージョン内では低レイテンシだが、リージョン間呼び出しは逆効果になる。データの局所性を考慮したアーキテクチャ設計が2026年時点での差別化要素になっている。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly __brand: 'UserId' }` のようなブランド型が標準化され、プリミティブ型の意味的な区別を強制することで、ID の取り違えなどのバグを型レベルで防止している。

- **`satisfies` 演算子の活用:** TypeScript 4.9+ の `satisfies` が2026年では必須パターンに。型推論を保ちながら型チェックを行えるため、`as const` との組み合わせで設定オブジェクトの型安全性が大幅に向上した。

- **Template Literal Types による API 設計:** `type Route = \`/api/${string}\`` のような型でルートや文字列パターンを静的に検証し、ランタイムエラーをコンパイル時に捕捉する設計が広まっている。

- **Zod + 型推論の完全統合:** `z.infer<typeof schema>` でランタイムバリデーションと型定義を一元管理するパターンが定着。API境界・フォーム・環境変数すべてにZodスキーマを置くことで、型とバリデーションの二重管理を排除できる。

- **`NoInfer<T>` ユーティリティの活用:** TypeScript 5.4で追加された `NoInfer<T>` により、ジェネリック関数での意図しない型推論を防止できる。デフォルト値を持つジェネリックAPIの設計精度が向上した。
