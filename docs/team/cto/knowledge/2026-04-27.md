# CTO Knowledge - 2026-04-27

## Daily Update (2026-04-27)

### 1. Next.js performance optimization 2026

- **PPR（Partial Prerendering）の本格活用:** Next.js 15以降で安定化したPPRにより、静的シェルと動的コンテンツを単一リクエストで配信可能になった。`experimental_ppr`フラグを外し、キャッシュ境界設計をアーキテクチャの中心に据えることが2026年のベストプラクティス。

- **React Server Componentsのバンドルサイズ削減効果を最大化:** RSCにより重いUIライブラリをサーバー側に閉じ込めることで、クライアントJSを大幅削減できる。`"use client"`ディレクティブを末端コンポーネントに限定し、ツリーの上位に置かない設計が重要。

- **`next/image`と`next/font`の徹底活用:** CLS（Cumulative Layout Shift）とLCPはCore Web Vitalsの主要指標であり、画像の`sizes`属性とfont subsettingの適切な設定がLighthouseスコアに直結する。特にモバイルファーストの物件画像配信では見落としがち。

- **Turbopackの本番採用:** Next.js 15.xでTurbopackがstable化し、大規模コードベースでのHMRが5〜10倍高速化した。`next dev --turbopack`から`next build`（Turbopack対応）への移行を段階的に進め、ビルド時間ボトルネックを解消する。

- **Server Actionsのキャッシュ戦略とrevalidation設計:** `revalidatePath` / `revalidateTag`の粒度設計が不適切だと、データ更新のたびに全キャッシュが無効化されパフォーマンスが劣化する。タグベースのキャッシュ無効化を採用し、影響範囲を最小化するアーキテクチャが必須。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度設計が鍵:** RSCストリーミングでは、Suspense境界をコンポーネントツリーのどこに置くかがTTFB/LCP直結の設計判断になる。細かすぎると管理コストが増し、粗すぎるとストリーミングの恩恵が薄れる。

- **PPR（Partial Prerendering）との統合が主流化:** Next.js 15以降でPPRが安定し、静的シェルを即座に配信しながら動的部分をストリームするパターンが標準になりつつある。新規プロジェクトではISR/SSRの二択ではなくPPRを第一候補として検討すべき。

- **サーバーアクションとの組み合わせでウォーターフォールを排除:** クライアント→APIルート→DBという往復をサーバーアクション＋RSCで1ホップに圧縮できる。特にフォーム送信後の再レンダリングはRound Trip Timeを大幅削減できる。

- **キャッシュ戦略の複雑性が増大:** `fetch`のキャッシュタグ、`revalidatePath`、`revalidateTag`の組み合わせが増え、キャッシュの不整合バグが増加傾向にある。チームとしてキャッシュ境界を明示的にドキュメント化するルールを設けることを推奨。

- **Edge Runtimeとの相性に注意:** Node.js依存ライブラリ（Prisma等）をRSC内で使う場合、Edge Runtimeでは動作しないケースがある。アーキテクチャ初期にランタイム制約をADRに残しておくと後の手戻りを防げる。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全APIの標準化:** tRPCはNext.js/TypeScriptスタックでのデファクトになりつつあり、スキーマ定義なしでフロント・バック間の型を共有できるため、開発速度と安全性が大幅に向上する。

- **GraphQLの適用範囲の絞り込み:** GraphQLは複数クライアント（Web/モバイル/サードパーティ）が同一データを異なる形で取得する場面に限定されつつあり、内部API・BFF層ではオーバーエンジニアリングとして避けられるケースが増えている。

- **RESTはOpenAPI 3.1 + Zodで再評価:** シンプルなCRUDやパブリックAPIではRESTが依然として主流で、OpenAPI 3.1とZodによる自動型生成（`zod-openapi`等）により、tRPCに近い型安全性をREST上で実現できる。

- **Server Actionsによるエンドポイントレス設計:** Next.js 15以降のServer Actionsが成熟し、社内ツールや小規模プロダクトではAPIエンドポイント自体を定義しない設計が現実解となっている。ただしキャッシュ・再利用性の面でトレードオフがある。

- **エッジ・分散環境への対応がAPI設計の新制約:** CloudflareやVercel Edgeでの実行を前提とすると、コネクション維持が難しいため、RPCよりもステートレスなHTTP+キャッシュ戦略の設計が再重要視されている。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジのデファクト実行環境に:** V8アイソレートに加えWasmが主流となり、言語非依存でコールドスタートをほぼゼロに抑えつつ、セキュリティサンドボックスも強化されている。

- **エッジDBとデータローカリティの融合:** Cloudflare D1・Turso・Neon Branchingなどエッジ対応SQLが成熟し、「コンピュートをデータの近くで動かす」だけでなく「データ自体をエッジに持つ」設計が現実的な選択肢になった。

- **AI推論のエッジオフロード加速:** LLMの量子化モデル（3B〜7Bクラス）がエッジノードで動作可能になり、レイテンシ削減とデータプライバシー確保を両立するオンデバイス×エッジのハイブリッド推論アーキテクチャが普及している。

- **オブザーバビリティの空白が最大の運用課題:** 分散エッジ環境では従来のAPMが機能せず、OpenTelemetry over HTTPのエッジネイティブ実装と、テール・サンプリングの工夫が必須になっている。

- **マルチベンダー標準化の遅れがロックインリスク:** WinterCGによるWASI/Service Worker APIの標準化が進むも、Cloudflare Workers・Vercel Edge・Fastly Computeの挙動差は依然大きく、抽象レイヤー（HonoやNitroなど）を挟んでポータビリティを確保する設計判断が重要。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の本格移行:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の標準となり、フィッシング耐性と利便性を両立。2026年時点でApple/Google/Microsoftのエコシステム全体で安定稼働しており、新規サービスはパスワード認証を廃止する方向が主流。

- **セッション管理の短命化とトークンローテーション:** アクセストークンの有効期限を15分以内に短縮し、Refresh Tokenのローテーション（使い捨て）を徹底することでトークン盗取の被害範囲を最小化。Next.jsアプリでは`next-auth` v5のServer Actionsとの統合が実用的。

- **ゼロトラスト原則の認証レイヤー適用:** ネットワーク内部でも常に認証・認可を検証する設計が必須。デバイス状態・位置情報・行動パターンをリスクスコアに組み込む継続的認証（Continuous Authentication）が普及。

- **サプライチェーン攻撃対策としての依存関係監査:** `next-auth`や`jose`等の認証ライブラリの脆弱性がサプライチェーン攻撃の標的になるケースが増加。`bun audit`による定期スキャンとDependabotによる自動更新PRの運用が最低ライン。

- **AIによる異常検知との連携:** ログイン試行パターンをリアルタイム分析するAIベースの不正検知（Credential Stuffing対策等）が実用レベルに到達。自前実装よりもCloudflare TurnstileやAuth0のAttack Protectionといったマネージドサービスへの委譲が費用対効果で優位。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge対応成熟:** Prisma 6系ではEdge RuntimeおよびServerless環境での接続プーリング（Prisma Accelerate）が本番レベルに達し、Supabase + Vercel/Cloudflare Workersのスタックでコネクション枯渇問題が実用的に解消されつつある。

- **Supabase pgvectorとAIワークロードの統合:** Supabase上のpgvector拡張が安定し、RAGパイプラインやセマンティック検索をPostgreSQL単体で完結させるアーキテクチャが主流化。外部ベクトルDBへの依存を減らすことでインフラ複雑度を抑制できる。

- **Row Level Security (RLS) の設計負債リスク:** SupabaseのRLSはセキュリティ層として強力だが、複雑なポリシーがクエリプランナーを阻害しN+1問題を引き起こすケースが増加。PrismaのORMレイヤーと組み合わせる際はRLSポリシーの粒度設計を初期から慎重に行う必要がある。

- **Supabase Branchingによる開発フロー変革:** 2025年末にGAとなったDatabase Branchingにより、PRごとに独立したDBスナップショット環境を持つCIフローが現実的に。ステージング環境の管理コストが大幅に削減される。

- **Prisma Schema v2（Multi-file）での大規模スキーマ管理:** Prisma 5.15以降で安定したMulti-file schema機能により、モノレポや大規模サービスでのスキーマ分割が可能に。ドメインごとにスキーマファイルを分割し、マイグレーション管理の見通しを改善できる。

### 7. WebAssembly Rust performance 2026

- **WASM GC と Component Model の成熟:** 2026年時点でWASM Component Modelが安定し、RustコンポーネントをJS/Python等と型安全に合成できるようになった。ランタイム間の相互運用コストが大幅に削減されている。

- **SIMD・スレッド拡張によるCPUバウンド処理の高速化:** WASM SIMDとShared Memoryが主要ブラウザ・エッジランタイムで標準サポート済み。Rustの`std::simd`との組み合わせでネイティブに近いベクトル演算が実現できる。

- **Wasmtime / WASMERのAOTコンパイル最適化:** サーバーサイドランタイムのAOT（事前コンパイル）が成熟し、コールドスタートがミリ秒以下に。エッジ関数・サーバーレス文脈でのRust+WASMの採用コストが実質ゼロに近づいた。

- **メモリ管理のオーバーヘッド削減:** Linear Memory64の普及により4GBの壁が解消され、大規模データ処理ユースケースでのRust WASMが現実的になった。`wasm-bindgen`のゼロコピー最適化も進み、JS⇔WASM間のデータ転送コストが従来比で大幅改善。

- **開発体験の実用化:** `cargo component`ツールチェーンとWASI 0.3の組み合わせで、ファイルI/O・ネットワーク・非同期処理がネイティブRust感覚で書けるようになった。プロダクション導入の判断基準がパフォーマンスより開発・運用コストにシフトしている。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの設計:** データフェッチはServer Componentsに集約し、インタラクティブな部分のみ `'use client'` を付与する「islands architecture」的アプローチが定着。バンドルサイズ削減とTTFBの改善に直結する。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的コンテンツを同一ページで共存させるPPRが安定化し、`<Suspense>` 境界の設計がアーキテクチャの核心に。ページ単位ではなくコンポーネント単位でのキャッシュ戦略が必要になる。

- **Server Actions によるミューテーション統一:** API Routeを経由せずServer Actionsでフォーム処理・DB更新を行うパターンが主流化。`useActionState` との組み合わせでoptimistic UIも実装しやすくなり、クライアント↔サーバー間のボイラープレートが大幅削減。

- **`use cache` ディレクティブによる細粒度キャッシュ:** `revalidatePath` / `revalidateTag` に加え、関数レベルで `use cache` を宣言できるAPIが普及。データソース単位でのキャッシュ無効化が容易になり、`unstable_cache` からの移行が推奨される。

- **型安全なルーティング:** `next/navigation` の型推論強化と `nuqs` 等のライブラリを組み合わせたURLステート管理がベストプラクティスに。`searchParams` の型付けを怠るとServer/Client間で型の乖離が生じるため、Zodによるバリデーションを境界に必ず挟む。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge Runtimeの制約を逆手に取る設計:** Edge Functionsは128MB以下のメモリ・Node.js APIの一部制限があるため、重い処理はバックグラウンドジョブやServerless Functionsに分離し、EdgeはJWT検証・A/Bフラグ判定・geo-routingなど軽量ロジックに特化させるのが鉄則。

- **ポイント2: Fluid Compute（Streaming + ISR）との組み合わせ:** 2025年後半に安定したVercelのFluid Computeモデルでは、Edge Middlewareでリクエストを早期フィルタリングしつつ、重いデータフェッチはStreaming RSCにオフロードすることでTTFBを最小化できる。

- **ポイント3: Cold Start排除のためのWarm-up戦略:** Edge FunctionsはV8 Isolateベースでコールドスタートはほぼゼロだが、外部APIコールの初回DNS解決がボトルネックになりやすい。`waitUntil()`でバックグラウンドキャッシュウォームアップを行い、次リクエストの応答を高速化する。

- **ポイント4: KV / Edge Config の適切な使い分け:** 頻繁に読むが滅多に書かないフラグ（機能フラグ・レートリミット閾値）はEdge Configに、ユーザーセッションやカウンターはVercel KVに置く。Edge Config読み取りはレイテンシ1ms未満で、Middlewareとの相性が最も良い。

- **ポイント5: オブザーバビリティの確立が最優先:** Edge層のデバッグはローカル再現が難しいため、OpenTelemetry + Vercel Log Drains（Datadog/Axiom連携）を早期に整備する。`X-Vercel-Edge-Region`ヘッダーをログに含めることで、特定リージョンの性能劣化を即座に特定できる。

### 10. TypeScript type safety patterns 2026

- **Template Literal Types の高度活用:** 文字列リテラル型を組み合わせたAPIルートやイベント名の型安全な定義が標準化され、ランタイムエラーをコンパイル時に検出できる設計が主流になっている。

- **`satisfies` 演算子の普及:** `as const` の代替として `satisfies` を使うことで、型推論の恩恵を保ちながら型制約を強制できる。特にコンフィグオブジェクトや定数マップの定義で威力を発揮する。

- **Branded Types によるドメイン安全性:** `UserId`・`OrderId` などプリミティブをブランド化し、誤った値の混入をコンパイル時にブロックするパターンが、DDD志向のコードベースで定着してきた。

- **`noUncheckedIndexedAccess` の実用化:** TypeScript 4.1以降のこのコンパイラオプションが2026年には「デファクトオン」になりつつあり、配列・オブジェクトアクセス時の `undefined` 見落としを構造的に排除できる。

- **型レベルテスト（`tsd` / `expect-type`）の導入:** 型定義そのものをテストする文化が広まり、ライブラリのAPIサーフェスや複雑なジェネリクスの回帰を防ぐCI組み込みが増えている。
