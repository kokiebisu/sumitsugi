# CTO Knowledge - 2026-06-14

## Daily Update (2026-06-14)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、デフォルトでサーバーコンポーネントを使い、`'use client'`は状態・インタラクションが必須な末端コンポーネントにのみ付与する設計が標準になっている。

- **Partial Prerendering (PPR) の本格採用:** 静的シェルを即時配信しつつ、動的部分をSuspenseでストリーミングするPPRが安定化し、SSGとSSRの二択から解放される。`experimental.ppr`を有効化してページ単位で段階移行できる。

- **`next/image` + `next/font` による Core Web Vitals 自動最適化:** LCP改善のため`priority`属性と`sizes`の適切な設定が依然重要。フォントはデプロイ時にself-hostedされCLSがゼロになるため、Google Fonts直接参照は廃止すべき。

- **Server Actions のバンドル分離:** フォーム送信・ミューテーション処理をServer Actionsに移行することで、APIルートのオーバーヘッドとクライアントフェッチコードを削減できる。ただし、過度な細分化は逆にウォーターフォールを生む点に注意。

- **Turbopack の本番利用:** Next.js 15以降でTurbopackが安定し、大規模プロジェクトでのビルド・HMT速度が大幅改善。`next dev --turbopack`から始め、CIも`next build`（Turbopack対応版）に切り替えることで開発速度が体感できる。

### 2. React Server Components streaming 2026

- **Partial Pre-rendering (PPR) の本格普及:** Next.js 15以降でPPRが安定し、静的シェルを即座に返しつつ動的部分をストリーミングする設計が標準パターンに。TTFBとLCPの両立が実現しやすくなった。

- **React 19 の Suspense + use() API の成熟:** `use(promise)` によるコンポーネント内での非同期データ取得が実用レベルに達し、ウォーターフォールを避けた並列ストリーミング設計が容易になった。

- **エッジランタイムとの相性が鍵:** Cloudflare Workers / Vercel EdgeでRSCストリーミングを動かす際、Node.js専用APIへの依存が障壁になる。ランタイム非依存なデータ取得層の設計が重要。

- **Server Actions との組み合わせで楽観的UI:** フォーム送信・ミューテーションをServer Actionsで処理しつつ、`useOptimistic`でクライアント側即時反映。ストリーミングとの組み合わせでSPAに近いUXをサーバー中心で実現できる。

- **バンドルサイズ削減の恩恵が計測可能に:** RSCにより重いライブラリ（日付・Markdownパーサー等）をサーバー側に閉じ込めることでJS転送量が30〜50%減のケースも。Core Web Vitalsへの直接的な貢献として優先度高い。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年時点でtRPCはNext.js/TypeScriptスタックにおけるデファクトスタンダードに近づいており、スキーマ定義なしにエンドツーエンドの型安全を実現できるため、小〜中規模チームでは REST/GraphQL より開発速度が大幅に向上する。

- **GraphQLの役割の再定義:** GraphQLは「汎用API」ではなく「複雑なデータフェッチが必要なBFF（Backend for Frontend）層」に特化しつつあり、Relay/Apollo Client のオーバーヘッドを嫌うチームは Server Components + tRPC に移行している。

- **RESTは死なず、OpenAPI 3.1が進化の鍵:** REST + OpenAPI 3.1は外部公開APIやマイクロサービス間通信のスタンダードであり続け、Zod→OpenAPIの自動生成ツール（`zod-to-openapi`等）でスキーマファーストな開発が効率化している。

- **HTTP/3とEdge Computingによるプロトコル選択の変化:** Cloudflare Workers / Vercel Edge などのエッジ環境ではコールドスタートとレイテンシが最優先課題となり、gRPC-Web より軽量なREST/tRPCが選ばれる傾向が強まっている。

- **API設計の判断基準（2026年版）:** 外部サード向け→REST+OpenAPI、社内フルスタックTypeScript→tRPC、モバイル複数クライアント+複雑なリレーション→GraphQL、が現実的な選択指針であり、「何でもGraphQL」はアンチパターンとして認識されてきている。

### 4. serverless edge computing 2026

- **エッジ・ファーストアーキテクチャの標準化:** Cloudflare Workers・Vercel Edge Functions・Deno Deployが成熟し、「エッジで動かすことが前提」の設計パターンが普及。コールドスタート問題がほぼ解消され、レイテンシ < 5ms が現実的に。

- **WebAssembly (Wasm) がエッジのデファクトランタイムに:** ブラウザ外での Wasm 活用が加速し、言語非依存でエッジ関数を記述可能に。RustやGoで書いたコードを安全にサンドボックス実行できるため、セキュリティと性能を両立。

- **エッジでのAI推論の台頭:** 軽量LLM（1B〜7Bパラメータ）がエッジノードで動作し始め、ユーザーデータをクラウドに送らずにリアルタイム推論が可能に。プライバシー規制（GDPR等）への対応コストが下がる。

- **データ主権とコンプライアンスの解決手段として定着:** データが物理的にリージョン外に出ないことを保証できるため、金融・医療分野でのエッジ採用が急増。「Compliance by Architecture」の考え方が主流に。

- **オブザーバビリティの課題が最大のボトルネック:** 分散したエッジノードでのトレーシング・ログ集約が依然困難で、OpenTelemetryのエッジ対応強化が2026年の開発チームの最重要投資領域になっている。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の本格採用:** FIDO2/WebAuthn標準に基づくパスキーがパスワードの実質的な代替となった。フィッシング耐性が高く、生体認証との組み合わせでUXも向上するため、新規サービスではパスワード認証を廃止する方向が主流。

- **ゼロトラスト + 継続的認証:** 「一度ログインすれば信頼」の時代は終わり、セッション中も行動パターン・デバイス状態・ネットワークを継続的に評価するリスクベース認証が標準化。異常検知時に再認証を要求する設計が必須。

- **OAuthトークンのセキュリティ強化:** アクセストークンの短命化（有効期限15分以下）＋リフレッシュトークンローテーションが基本。DPoP（Demonstration of Proof-of-Possession）によるトークンバインディングで盗難トークンの悪用を防ぐ。

- **AIを使った認証攻撃への対抗:** ディープフェイクを使ったKYCバイパスや、LLMを活用したソーシャルエンジニアリングが急増。ライブネス検出の強化と、SMS/音声OTPを廃止してTOTPまたはハードウェアキーへの移行が急務。

- **サプライチェーン経由の認証ライブラリ汚染:** 認証SDKへの悪意ある依存関係注入が増加。`package-lock.json` のハッシュ検証・SBOMの管理・定期的な依存関係監査（`bun audit`相当）をCI/CDに組み込むことが不可欠。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6のEdge対応成熟:** Prisma AccelerateがEdge Runtime（Cloudflare Workers、Vercel Edge）で安定動作するようになり、コネクションプーリングをプラットフォーム側に委譲できるため、サーバーレス環境でのN+1問題やコネクション枯渇が大幅に解消された。

- **Supabase pgvectorの実用化:** pgvectorがSupabaseでプロダクション利用に耐えるスケールに達し、RAG（検索拡張生成）やセマンティック検索をPostgresの既存スキーマに統合できる——別途ベクトルDBを立てるコストとレイテンシを避けられる点が2026年の重要な選択肢。

- **Row Level Security（RLS）設計の重要性:** SupabaseでRLSを後付けするとパフォーマンス劣化とロジック複雑化が深刻になる。設計初期からRLSポリシーをデータモデルと一緒に定義し、Prismaのクライアント拡張でRLSコンテキスト（`auth.uid()`）を注入するパターンが標準化されつつある。

- **PrismaとDrizzle ORMの選択基準:** 型安全性と開発体験ならPrisma、パフォーマンスとバンドルサイズ最小化ならDrizzleという棲み分けが明確になった。Supabaseとの組み合わせではDrizzleのほうがEdge環境での起動が軽量なため、APIルートが多いプロジェクトでは再評価の余地がある。

- **Supabase Branchingによる開発フロー改善:** `git branch`に連動したDBブランチング機能が実用段階に入り、PRごとにマイグレーションを独立して検証できるようになった。CIでのマイグレーション破壊検知が自動化でき、本番スキーマへの影響リスクを大幅に低減できる。

### 7. WebAssembly Rust performance 2026

- **ポイント1: Component Modelの成熟がゲームチェンジャー:** WASI 0.2とComponent Modelが安定化し、RustでビルドしたWasmモジュールをホスト言語に依存せず再利用できるようになった。マイクロサービスのポータビリティが大幅に向上している。

- **ポイント2: SIMD/スレッド対応で数値計算性能がネイティブ並みに:** WasmのFixed-width SIMDとShared Memory Threads（Atomics）がブラウザ・サーバー双方で広くサポートされ、RustのSIMDクレート（`std::simd`）との組み合わせでCPUバウンドな処理がネイティブの80〜95%の性能を達成できるケースが増えた。

- **ポイント3: GCプロポーザル採用でメモリ管理の境界が緩和:** Wasm GC提案の普及により、Rustコンポーネントが他のGC言語ランタイムと相互運用しやすくなった。ただしRust自体はゼロコストで動作するため、性能クリティカルな処理はRust側に寄せる設計が引き続き有効。

- **ポイント4: エッジ環境でのコールドスタートが課題から強みへ:** Cloudflare Workers/Fastly ComputeなどのエッジランタイムでRust Wasmのコールドスタートが1ms以下になってきており、Node.jsベースのサービスとの性能差が逆転するケースが実運用で報告されている。

- **ポイント5: `wasm-bindgen`から`wit-bindgen`へのシフト:** ブラウザ特化だった`wasm-bindgen`に加え、WIT（Wasm Interface Types）を使う`wit-bindgen`が標準になりつつある。新規プロジェクトはWIT-firstで設計することで、クライアント・サーバー・エッジの三環境への展開コストを削減できる。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** クライアントコンポーネントは状態・インタラクションが必要な末端ノードに限定し、データフェッチは全てServer Componentsで行う設計が定着。バンドルサイズが大幅に削減される。

- **Partial Prerendering (PPR) の本格活用:** 静的シェル + 動的ストリーミングを同一ルートで混在させるPPRが安定版に。`<Suspense>` 境界の設計がパフォーマンスのキーになる。

- **Server Actions によるAPI Route廃止トレンド:** フォーム送信やミューテーションはServer Actionsに集約し、`/api` ルートは外部連携のみに限定するパターンが主流。型安全性が向上し、エンドポイント管理が不要になる。

- **`use cache` ディレクティブによるきめ細かいキャッシュ制御:** `fetch` のキャッシュ設定から、コンポーネント・関数単位での `use cache` アノテーションへの移行。`cacheTag`/`cacheLife` で無効化戦略を宣言的に記述できる。

- **Turbopack 本番対応とビルド高速化:** Next.js 16系でTurbopackがデフォルト化し、大規模プロジェクトでもHMRが数百ms以内に収まる。`next.config.ts`（TypeScript設定ファイル）が標準化され、型補完が効くようになった。

### 9. Vercel Edge Functions optimization 2026

- **パフォーマンス:** Edge Functionsはユーザーに地理的に近いノードで実行されるため、コールドスタートを最小化するにはランタイムを`edge`に固定し、Node.js APIへの依存を排除することが最重要。

- **ストリーミングレスポンス:** `ReadableStream`とReact Server ComponentsのストリーミングをEdgeで組み合わせることで、TTFB（初期バイト到達時間）を大幅に削減できる—特に動的コンテンツの多いページで効果的。

- **キャッシュ戦略:** `stale-while-revalidate`パターンをEdge Cacheと組み合わせ、動的処理をキャッシュヒット時にスキップする設計が2026年のベストプラクティス—`Cache-Control`ヘッダーの精緻な設計が鍵。

- **バンドルサイズ制限:** Edge Functionsは1MB以下のバンドルサイズ制約があるため、重い依存ライブラリ（例: `date-fns`全体）をtree-shakingして軽量代替(`Temporal` API等)に置き換えることが必須。

- **Middleware最適化:** Next.jsのMiddlewareはEdgeで全リクエストに適用されるため、条件分岐を早期returnで最小化し、認証チェックのみに絞ることで不要なレイテンシを防ぐ。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の`satisfies`は型推論を保ちながら型チェックを強制できるため、`as`キャストによる型安全性の損失を避けられる。2026年現在、これを使わないコードはレガシーと見なされつつある。

- **Branded Types による境界防衛:** `type UserId = string & { readonly _brand: 'UserId' }` パターンが実装レベルで標準化。IDの取り違えやAPIの誤用をコンパイル時に検出でき、Zodの`.brand()`と組み合わせると入力境界での型安全性が完結する。

- **Template Literal Types の実用化:** APIルートやイベント名など文字列パターンの型定義に`\`/api/${string}\``が使われるようになり、ランタイムエラーをコンパイル時に潰せる。特にtRPCやHonoとの組み合わせで効果が顕著。

- **`const` 型パラメータと`NoInfer`の活用:** TypeScript 5.xで追加された`const T`と`NoInfer<T>`により、ジェネリック関数での不必要な型の拡大（widening）を防止できる。ライブラリ設計での誤用を防ぐ上で必須の知識になっている。

- **型レベルテストの義務化:** `tsd`や`expect-type`を使った「型が意図通りに推論されるか」のテストがCI必須項目になりつつある。実装テストだけでは検出できない型回帰（type regression）を防ぐための実践として定着してきた。
