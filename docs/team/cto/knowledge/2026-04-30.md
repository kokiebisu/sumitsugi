# CTO Knowledge - 2026-04-30

## Daily Update (2026-04-30)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを劇的に削減できるRSCを基本設計として採用し、`'use client'`はインタラクティブな末端コンポーネントのみに限定することがベストプラクティスとして確立された。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降でstableになったPPRにより、静的シェルと動的コンテンツを同一ルートで組み合わせ可能になり、TTFBとLCPを両立できる。`experimental.ppr`から`ppr: true`への移行タイミングを見極めるべき。

- **`use cache` APIによるきめ細かいキャッシュ制御:** 従来の`fetch`オプションに加え、`use cache`ディレクティブとタグベースのrevalidationを組み合わせることで、コンポーネント・関数単位でのキャッシュ戦略が実装可能になった。

- **Turbopack本番採用とビルド時間の短縮:** Turbopackが`next build`でもstable化され、大規模プロジェクトでのビルド時間が最大60%短縮。CI/CDパイプラインのコスト削減に直結するため、即時移行を推奨。

- **`@next/bundle-analyzer`とServer Action最適化:** Server Actionsの乱用はクライアント・サーバー間のウォーターフォールを生む。定期的なバンドル分析と、重い処理をRSCに戻すリファクタリングサイクルを開発フローに組み込むことが重要。

### 2. React Server Components streaming 2026

- **Suspense境界の細粒度化が主流に:** 2026年時点では、ページ単位ではなくコンポーネント単位でSuspenseを配置し、クリティカルパスのデータだけを優先ストリーミングするアーキテクチャが標準となっている。TTFBを最小化しつつ、LCPも改善できる。

- **PPR（Partial Pre-Rendering）の実用化:** Next.js 15以降でPPRが安定化し、静的シェルを即座に配信しつつ動的部分だけをストリーミングするハイブリッド戦略が現実的な選択肢になった。エッジキャッシュとStreaming SSRを組み合わせることでCDN効率も最大化できる。

- **Server Actionsとのシームレスな統合:** RSCとServer Actionsの組み合わせにより、フォーム送信後の再レンダリングもストリーミングで処理可能になり、クライアントバンドルを増やさずにインタラクティブ性を実現できる。

- **データフェッチのウォーターフォール排除が必須:** `Promise.all`や`React.use()`を活用した並列フェッチ設計が不可欠。Sequential fetchingはストリーミングの恩恵を相殺するため、依存関係グラフを明示的に設計する必要がある。

- **Edge RuntimeとNode.js Runtimeの使い分け:** ストリーミングレスポンスはEdge Runtimeで低レイテンシを実現できるが、Node.js固有のAPIや重い処理はNode.js Runtimeに留める。2026年ではこの判断基準がチームの設計スキルとして問われている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの実用的優位性:** フルスタックTypeScriptプロジェクトではtRPCが事実上のデファクトになりつつある。スキーマ定義なしにエンドツーエンドの型安全性を実現でき、Next.js + Prismaスタックとの親和性が特に高い。

- **GraphQLの適用領域の明確化:** GraphQLは「データグラフが複雑で複数クライアントが異なるフィールドを要求する」ケースに限定されつつある。単純なCRUDやB2Bサービス間通信にGraphQLを選ぶのはオーバーエンジニアリングと判断される傾向が強まった。

- **REST + OpenAPIの再評価:** AIコード生成ツールとの相性からOpenAPI仕様書ベースのREST APIが見直されている。`openapi-typescript`等でクライアント型を自動生成すれば、tRPC並みの型安全性を既存インフラで実現できる。

- **Protocol Buffersの浮上:** gRPC / ConnectRPCがマイクロサービス間通信で採用増加。バイナリ効率とスキーマファーストの契約駆動開発が評価され、特にレイテンシ敏感なサービスメッシュ構成で選ばれている。

- **sumitsugiへの示唆:** 現在のNext.js + TypeScript構成ではtRPCかOpenAPI+型生成が最もコスト対効果が高い。GraphQLへの移行は現フェーズでは不要で、APIが外部公開・複数クライアント対応になる段階で再検討するのが適切。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** 2026年時点でVercel、Cloudflare Workers AI、Fastly Compute等がエッジでのLLM推論をネイティブサポート。レイテンシ敏感なAI機能（リアルタイム翻訳・パーソナライゼーション）はエッジ実行が事実上の標準となっている。

- **WebAssembly（Wasm）がランタイムの主流に:** Node.js互換レイヤーの限界を超え、WasmコンパイルターゲットとしてRust/Goによるエッジ関数が増加。コールドスタート問題がほぼ解消され、サブミリ秒起動が実現している。

- **エッジDB・KVストアの成熟:** Cloudflare D1、Turso（libSQL）、Neon Serverlessなどエッジ近傍のSQLiteクローンが本番実績を積み、「エッジでDBまで完結」するアーキテクチャが現実的な選択肢になった。

- **コスト管理の複雑化がボトルネック:** リクエスト数課金からCPUサイクル・メモリ時間課金へ移行が進み、従来のバックエンド感覚での見積もりが通用しない。オブザーバビリティツール（OpenTelemetry対応）のエッジ統合が必須投資になっている。

- **マルチランタイム戦略のリスク:** Vercel Edge Runtime、Cloudflare Workers、Deno Deployの仕様差異が依然として存在し、ベンダーロックインが技術的負債になりやすい。WinterCG標準への準拠度を選定基準に入れることが重要。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）への移行加速:** パスワードレス認証がデファクトスタンダードになりつつあり、フィッシング耐性のあるパスキーをプライマリ認証手段として採用することが2026年のベストプラクティス。

- **セッション管理の強化:** 短命トークン（アクセストークン15分・リフレッシュトークンローテーション）＋デバイスフィンガープリントの組み合わせで、トークン盗用リスクを大幅に低減できる。

- **継続的認証（Continuous Authentication）の台頭:** ログイン時点だけでなく、行動パターン・リスクスコアをセッション中も評価するゼロトラストモデルが金融・医療系では標準化しつつある。

- **サプライチェーンリスクとしてのOAuth/OIDCプロバイダー依存:** 外部IdPへの過度な依存はリスクで、プロバイダー障害・規約変更への備えとして自前のフォールバック認証経路を持つ設計が重要。

- **AIを活用した異常検知:** 従来のルールベースより、機械学習によるログイン異常検知（時間帯・ロケーション・デバイス変化）がコスト効率よく実装できるようになっており、クラウドネイティブなサービス（AWS Cognito Advanced Security等）で容易に導入可能。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x の Edge Runtime 対応成熟:** Prisma の Accelerate（接続プール + グローバルキャッシュ）が Vercel/Cloudflare Edge で安定稼働できるようになり、Supabase との組み合わせでコールドスタート問題がほぼ解消された。

- **Supabase の RLS（Row Level Security）を ORM レイヤーで活用:** Prisma から Supabase に接続する際、`SET LOCAL role = 'authenticated'` をトランザクション内で発行することで RLS を活かしつつ型安全なクエリが書ける設計が標準化しつつある。

- **Postgres の pgvector + Supabase Vector Store:** RAG 構成において Supabase の pgvector 拡張が実用レベルに達し、外部ベクター DB（Pinecone 等）を持たずに Prisma スキーマ内で埋め込みベクターを管理できるアーキテクチャが普及している。

- **Prisma Migrate vs Supabase Migrations の二重管理リスク:** Supabase CLI の `supabase db push` と Prisma Migrate を混在させると migration 履歴が乖離するため、どちらか一方（通常は Prisma）をソースオブトゥルースとし、Supabase CLI はローカル環境起動のみに限定するのがベストプラクティス。

- **接続プール戦略の見直し（PgBouncer → Supabase Pooler）:** Supabase の Transaction mode Pooler（Supavisor）が PgBouncer の後継として安定化し、サーバーレス環境での `max_connections` 枯渇問題に対して Prisma の `directUrl` / `url` 分離設定で対処するパターンが定番になっている。

### 7. WebAssembly Rust performance 2026

- **Component Model の本格普及:** WASI 0.2とComponent Modelが2025年に安定化し、2026年はRust製WasmコンポーネントをNext.jsやEdge Runtimeに組み込むパターンが実用段階に入った。インターフェース定義（WIT）によりホスト言語との型安全な連携が大幅に簡易化されている。

- **SIMD・スレッド対応による計算性能の向上:** WebAssembly SIMDとShared Memoryが主要ブラウザで安定稼働し、RustのSIMD intrinsicsをそのままWasmにコンパイルできるケースが増えた。画像処理・暗号・MLインファレンスでネイティブの70〜90%水準のスループットが報告されている。

- **バイナリサイズと起動レイテンシの改善:** `wasm-opt`（Binaryen）＋Rustの`opt-level="z"`設定の組み合わせで、プロダクションバイナリを100〜200KB台に抑えやすくなった。ただしEdge環境でのコールドスタートはJSと比較して依然コストになるため、AOTコンパイル（Wasmtime/WazerGo）との使い分けが重要。

- **GCプロポーザルとメモリ管理の変化:** WasmGCが主要ランタイムに実装され、RustのWasm向けアロケータ戦略（`wee_alloc`廃止→`talc`や標準アロケータ）の再評価が必要。所有権モデルとGCの境界設計を誤るとヒープ断片化が起きやすい。

- **ToolchainとDX成熟:** `cargo-component`が`wasm-pack`を置き換えつつあり、CI/CDでのWasmビルドが標準化された。`wasmtime`のEmbedding APIやCloudflare Workers + Rustのデプロイフローが整備され、「Rustで書いてWasmで配布」がスタートアップでも現実的な選択肢になっている。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの設計:** 2026年現在、App RouterではRSC（React Server Components）をデフォルトとし、クライアント境界を最小化する設計が定着。`'use client'`はインタラクティブな末端コンポーネントのみに限定し、不要なバンドルサイズ増加を防ぐ。

- **Partial Prerendering（PPR）の本番投入:** Next.js 15以降でPPRが安定化し、静的シェルと動的ストリーミングを1ルートで共存させるパターンが主流に。`<Suspense>`境界の設計がアーキテクチャの核心になっている。

- **Server Actions によるAPI層の簡素化:** `use server`アクションがフォーム送信・ミューテーション処理の標準となり、個別のAPIルートを書く必要が減少。ただし入力バリデーション（Zod）とCSRF対策は必須——省略するとセキュリティホールになる。

- **`use cache` / `cacheTag` によるきめ細かいキャッシュ制御:** `fetch`レベルのキャッシュから関数・コンポーネントレベルへ移行。タグベースの無効化（`revalidateTag`）で、ページ全体を再生成せず必要なデータだけを更新できる粒度が実現。

- **Turbopack の本番利用と開発体験の変化:** Turbopack が dev/build 両モードで安定稼働し、大規模プロジェクトでもHMRが高速化。`next.config.ts`（TypeScript設定）への移行も進んでおり、型安全な設定管理が標準化しつつある。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの適切な使い分け:** Edge FunctionsはCold Start削減（~0ms）に優れるが、Node.js APIの制限（fs, native modules不可）があるため、重い処理はServerless Functionsに残し、認証・リダイレクト・A/Bテストなど軽量ロジックのみをEdgeに移行するのが現実的。

- **Fluid Compute（2025年〜）の活用:** VercelのFluid Computeにより、リクエスト間でのCPUリソース共有が可能になり、従来のServerless比でコストと応答速度の両方が改善された。EdgeとServerlessの境界がより流動的になっている。

- **Middleware最適化の重要性:** `middleware.ts`はすべてのリクエストに適用されるため、`matcher`設定で対象パスを絞り込むことが必須。不要なMiddleware実行はp99レイテンシーに直撃する。

- **KV・キャッシュ戦略との組み合わせ:** Vercel KV（Redis）やEdge Configとの組み合わせで、フィーチャーフラグや設定値の読み取りをEdgeで完結させられる。DBへのround-tripを排除し、グローバルに低レイテンシーを実現できる。

- **オブザーバビリティの整備:** Edge環境はログが取りにくいため、OpenTelemetry + Vercel Log Drainsを早期に設定しておくこと。本番でのデバッグコストが大幅に変わる。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `type UserId = string & { readonly __brand: 'UserId' }` のようなブランド型が実務で定着し、プリミティブ型の誤用（userIdにorderId代入など）をコンパイル時に防ぐパターンが普及している。

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の `satisfies` が2026年時点で成熟し、型推論を保ちながら型チェックを行えるため、`as const` との組み合わせで設定オブジェクトの型安全性が大幅に向上している。

- **Zod + tRPC による境界型の自動伝播:** APIスキーマをZodで定義し、フロントエンド・バックエンド間で型を自動共有するパターンが標準化。ランタイム検証と静的型が一致し、型の乖離によるバグがほぼゼロになる。

- **Template Literal Types による文字列安全性:** ルートパス・イベント名・CSSクラス名などの文字列をリテラル型で厳密に制約するパターンが実用化され、タイポによるバグをビルド時に検出できるようになっている。

- **`noUncheckedIndexedAccess` の必須化:** `tsconfig.json` でこのフラグを有効化することで配列・オブジェクトアクセスが `T | undefined` になり、未チェックアクセスによるランタイムエラーをコンパイル時に強制検出できる。2026年時点でのチーム標準設定として推奨。
