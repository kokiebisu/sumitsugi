# CTO Knowledge - 2026-09-12

## Daily Update (2026-09-12)

### 1. Next.js performance optimization 2026

- **React Compiler の標準採用:** Next.js 16ではReact Compilerが安定版として統合され、`useMemo`/`useCallback`の手動最適化が不要になりつつある。手動メモ化のコードを削除してビルドサイズと保守コストを下げる方向にシフトすべき。

- **Partial Prerendering (PPR) の本格運用:** 静的シェルを即座に返しつつ動的部分をストリーミングする方式が主流化しており、当プロジェクトでも物件一覧ページなど「静的な骨格＋動的な在庫情報」の構成に適用すればTTFBを大幅に改善できる。

- **Turbopackのビルド高速化:** `bun run build`のデフォルトバンドラーとしてTurbopackが成熟し、大規模プロジェクトでもWebpack比で数倍のビルド速度が出る。CIのビルド時間短縮に直結するため、まだ有効化していなければ優先度高く検討したい。

- **Server Actionsのキャッシュ戦略見直し:** `use cache`ディレクティブとキャッシュタグの粒度制御が洗練され、物件データのようにセラー側の更新頻度が低いデータはより積極的にキャッシュしつつ、公開ステータス切り替え時だけタグ無効化する設計が推奨される。

- **画像・フォントの自動最適化拡張:** `next/image`のレスポンシブ最適化に加え、Core Web Vitals（特にINP）計測がビルドパイプラインに組み込まれる流れがあり、リリース前チェックにINP閾値を追加することでUX劣化を早期検知できる。

### 2. React Server Components streaming 2026

- **段階的ハイドレーションとSuspense境界の粒度設計:** 2026年現在、単一ページ内で複数のSuspense境界を細かく分割し、重要なコンテンツ（LCP要素）を優先ストリーミングする設計が標準化。境界を粗くしすぎると滝落ち（waterfall）が発生するため、データ取得の依存関係ごとに境界を分けるのが定石。

- **Server ActionsとRSCストリーミングの統合による体感速度向上:** フォーム送信後の再検証（revalidate）をストリーミングレスポンスに乗せることで、フルページリロードなしに部分的なUI更新が可能。sumitsugiの物件一覧・詳細ページのような一覧→詳細遷移で特に効果が大きい。

- **キャッシュ戦略の複雑化とデバッグコスト:** Next.js 16ではRequest MemoizationとData Cacheの挙動がより明示的になったが、`'use cache'`ディレクティブの適用範囲を誤ると古いデータが表示されるバグを生みやすい。物件ステータス（`draft`/`public`）のような可変性の高いデータは特に慎重なキャッシュタグ設計が必要。

- **エラーバウンダリとストリーミングの共存:** ストリーミング中に発生したサーバーエラーがクライアントに部分的に流れ込むケースがあるため、`error.tsx`の粒度をSuspense境界と揃えることが重要。特に決済や認証フローではエラー処理の抜け漏れが致命的になりやすい。

- **パフォーマンス計測の再定義:** TTFBだけでなくTTI（Time to Interactive）やストリーミングチャンクごとのレイテンシを計測する必要があり、Core Web Vitalsの評価基準もRSC前提のアプリでは再解釈が必要。前の住人・次の住人の物件詳細ページのような画像多めのページでは特に注視すべき指標。

### 3. API design REST GraphQL tRPC 2026

- **APIパラダイムの使い分けが定着:** 2026年はREST/GraphQL/tRPCの「三択どれか一つ」ではなく、公開API・パートナー連携はREST（またはOpenAPI+REST）、内部BFFやフロント-バックエンド間はtRPC、複雑な集約クエリが必要な画面はGraphQLという使い分けが主流化。sumitsugiのようなNext.js App Router構成では、フロント/バック同一リポジトリならtRPCが型安全性とDX面で最有力。

- **tRPC + Next.js App Routerの相性:** tRPCはmonorepo・TypeScriptフルスタック構成で真価を発揮し、フロントとバックの型を自動同期できるためZodバリデーションとの組み合わせでスキーマ検証も一元化できる。sumitsugiの`src/lib`のZod活用方針とも親和性が高く、外部公開が不要な内部APIはtRPC移行の検討余地あり。

- **GraphQLは「集約・パーソナライズ」領域で存続:** 汎用APIよりも、複数リソースを1リクエストで取得したい物件検索・レコメンド画面など、オーバーフェッチ削減が効くユースケースに限定活用される傾向。全面採用ではなく特定エンドポイントへの部分導入が2026年のベストプラクティス。

- **RESTはOpenAPI+型生成で生き残る:** 外部パートナーや将来のモバイルアプリ対応を見据えると、REST+OpenAPI Specから型を自動生成する運用（`openapi-typescript`等）が引き続き主流。外部公開APIを将来設けるなら、この構成がtRPCより相互運用性で優位。

- **エッジ/ストリーミング対応が選定基準に:** Next.js 16のServer ActionsやストリーミングSSRとの統合しやすさが2026年のAPI設計選定で重視されており、tRPCのSubscription機能やGraphQLのSSE/WebSocket対応より、Server Actions単体で完結する設計がシンプルさの観点で見直されつつある。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG準拠のランタイム（Cloudflare Workers, Vercel Edge, Deno Deploy）がAPI互換性を高めており、ベンダーロックインを避けつつマルチクラウドでのエッジデプロイが現実的になっている。

- **コールドスタート問題の実質解消:** V8 isolateベースの軽量分離とWASMプリコンパイルにより起動レイテンシが1桁ミリ秒台まで下がり、レイテンシに敏感なSSR/APIルートをエッジへ移行する障壁が下がった。

- **エッジでのステート管理が成熟:** Durable Objects・Turso（libSQL）・PlanetScaleのエッジレプリカなど、エッジ上で強整合性のあるステートを扱う選択肢が増え、「エッジ=静的配信のみ」という制約が薄れつつある。

- **コスト構造の見直しが必要:** リクエスト課金モデルはトラフィックが読みにくいMVP段階ではコスト予測が難しく、住人一致のようなロングテールアクセスパターンのプロダクトでは従量課金の実測データを早めに取ってから本番採用を判断すべき。

- **観測性のギャップに注意:** 分散エッジ環境ではトレーシング（OpenTelemetry対応）が中央集権型サーバーより複雑化するため、導入前にログ集約・エラートラッキングの体制を先に整えることが実運用での失敗を防ぐ鍵になる。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証（Passkeys）がデファクトスタンダード化しており、フィッシング耐性のある公開鍵暗号方式を採用することで、認証情報漏洩リスクを構造的に排除できる。sumitsugiのような個人情報を扱うプラットフォームでは、パスワード認証は補助手段に格下げすべき。

- **セッション管理とトークンのローテーション:** JWTを使う場合はshort-lived access token + refresh tokenローテーションを徹底し、リフレッシュトークンの再利用検知（reuse detection）で盗難を即座に検知する仕組みを組み込む。長寿命トークンの放置は最も見落とされがちな脆弱性。

- **ゼロトラスト前提のセッション検証:** IPアドレスやデバイスフィンガープリントだけでなく、リクエストごとのコンテキスト（デバイス変更・異常な地理的移動）をリスクスコアリングし、疑わしい場合は段階的にMFAを再要求するアダプティブ認証が2026年の標準。

- **CSRF/XSS対策の多層防御:** SameSite=Strict Cookie + CSPヘッダー + 入力サニタイズを組み合わせ、単一の対策に依存しない。特にNext.js App Routerではサーバーアクションの認証チェックをミドルウェアだけに任せず、各アクション内でも再検証する（defense in depth）。

- **監査ログと異常検知の自動化:** 認証イベント（ログイン失敗・パスワードリセット・権限変更）を構造化ログとして残し、閾値ベースのアラートだけでなく異常検知（急激なログイン失敗増加など）を自動化することで、インシデント対応の初動を早める。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** PrismaのRust製クエリエンジンからWASM/TypeScript製エンジンへの移行が進み、Supabase等のエッジ環境（Cloudflare Workers、Vercel Edge Functions）でのコールドスタートが大幅に改善されている。エッジデプロイを検討するなら最新のPrismaクライアント設定を確認すべき。

- **ポイント2:** SupabaseのConnection Pooler（PgBouncer/Supavisor）とPrismaの相性問題は依然として注意点で、サーバーレス環境ではPrismaのDataProxy的な仕組みかSupavisorのTransaction Modeを併用しないとコネクション枯渇が起きやすい。

- **ポイント3:** Row Level Security（RLS）をアプリ層のZodバリデーションと併用する「二重防御」がSupabase運用のベストプラクティスとして定着しており、Prisma経由の書き込みでもRLSポリシーを必ず有効化すべき（サービスロールキーの誤用によるRLSバイパスは重大インシデントの温床）。

- **ポイント4:** Prisma SchemaからSupabaseのマイグレーション（`supabase migration`）へのワークフロー統合が改善され、`prisma migrate diff`でSQL生成→Supabase CLIで適用、というハイブリッド運用が主流になりつつある。単一ツールに依存しないことで、Supabaseの拡張機能（pgvector、Realtime等）をPrismaのスキーマ管理外で安全に扱える。

- **ポイント5:** pgvectorを使ったベクター検索・AI機能の需要増加により、SupabaseのPostgres拡張機能とPrismaのカスタム型サポートの組み合わせが重要になっている。sumitsugiのような不動産マッチング機能（IC相談マッチング等）を今後強化するなら、pgvectorでの類似物件検索は有力な選択肢。

### 7. WebAssembly Rust performance 2026

- **Component Model成熟によるオーバーヘッド削減:** WASI Preview 2とComponent Modelの普及で、Rust製WASMモジュール間のFFI呼び出しコストが大幅に下がり、マイクロサービス的な分割でもネイティブに近い速度を維持できるようになった。フロントエンド側の重い画像処理やPDF生成をWASM化する際の設計指針として活用できる。

- **SIMD標準化で計算集約タスクが実用域に:** WASM SIMD（`std::arch::wasm32`）がブラウザ横断で安定サポートされ、画像リサイズや暗号化処理などをJSより数倍速く実行可能。物件写真の自動リサイズ・透かし処理などをクライアントサイドに移す選択肢が現実的になっている。

- **バイナリサイズ最適化ツールチェーンの整備:** `wasm-opt`・`twiggy`・LTO+`opt-level="z"`の組み合わせで、Rust製WASMの初期ロードサイズを大幅圧縮できる。モバイル回線でのTTIを重視するsumitsugiのようなBtoCサービスでは、初回訪問時の体感速度に直結するポイント。

- **wasm-bindgen-rayonによるマルチスレッド化:** Web Workers + SharedArrayBufferを使ったデータ並列処理がRustのrayonクレートとほぼそのまま統合できるようになり、CPUバウンドな処理（検索インデックス構築、CSVエクスポート集計など）をUIスレッドから切り離しやすい。ただしCOOP/COEPヘッダー設定が前提条件になる点は注意。

- **Next.js App Routerとの統合パターンが定着:** WASMモジュールをEdge RuntimeやServer Componentsから直接呼び出すパターンが確立し、SSR時点で重い計算（画像メタデータ解析など）をNode.jsネイティブモジュールなしで完結できるケースが増えた。ビルドパイプラインの複雑化とのトレードオフは要検討。

### 8. Next.js App Router patterns 2026

- **ポイント1（Server Components前提の設計）:** App RouterではServer Componentsがデフォルトとなり、クライアントバンドルを最小化する設計が主流。データ取得はコンポーネント内で直接行い、`use client`は本当にインタラクティブなUIにのみ限定するのがベストプラクティス。

- **ポイント2（Partial Prerendering / PPR）:** 静的シェルを即座に返しつつ動的部分をストリーミングするPPRが安定運用フェーズに入り、ECサイトや物件検索のような「一部だけ動的」なページで体感速度が大幅に向上する。sumitsugiの物件一覧ページのような、静的なレイアウト＋動的な検索結果という構成に特に相性が良い。

- **ポイント3（キャッシュ戦略の明示化）:** Next.js 15以降でGETのデフォルトキャッシュ挙動が変わり、`fetch`のキャッシュはオプトインが基本に。`revalidateTag`/`revalidatePath`によるオンデマンド再検証を明示的に設計しないと、意図せず古いデータが表示されるリスクがある。

- **ポイント4（Server Actions の型安全な活用）:** フォーム送信・ミューテーションはServer Actionsに寄せる流れが定着し、Zodバリデーションと組み合わせることでAPI Routeを介さずに型安全なend-to-endフローが組める。物件登録・引き継ぎ申請フォームのような多段階フローに適している。

- **ポイント5（エラーバウンダリとローディングUXの粒度）:** `error.tsx`/`loading.tsx`をルートセグメントごとに細かく配置し、部分的な失敗が全体をブロックしないようにする設計が定石化。物件詳細ページで画像取得だけ失敗してもレビューや基本情報は表示され続けるような、耐障害性の高いUXが求められる。

### 9. Vercel Edge Functions optimization 2026

**CTOの視点:Vercel Edge Functions最適化 2026**

- **ポイント1:コールドスタート最適化:** V8 isolateベースの実行環境の進化により、ミリ秒単位のコールドスタートがさらに短縮されており、認証チェックやリダイレクトなどの軽量ロジックはEdge Middlewareに寄せることでTTFBを改善できる。
- **ポイント2:リージョン選択の戦略化:** データベース（特にPlanetScale/Neon等のエッジ対応DB）との地理的距離がレイテンシに直結するため、Edge Functionの実行リージョンをDB配置に合わせて固定する設計が重要になっている。
- **ポイント3:Node.js API互換性の拡大:** Edge RuntimeでサポートされるNode.js API（crypto, streams等）が拡大しており、従来Serverless Functionでしか動かせなかった処理を段階的にEdgeへ移行できる余地が広がっている。
- **ポイント4:キャッシュ戦略との統合:** `stale-while-revalidate`やISRとEdge Functionsを組み合わせることで、動的パーソナライゼーションを保ちながらCDNキャッシュのメリットを享受できるため、sumitsugiのような物件検索・一覧ページでは有効な手段になり得る。
- **ポイント5:コスト・実行時間のトレードオフ管理:** Edge Functionは実行時間・メモリ制限が厳しいため、重い処理（画像処理、PDF生成等）は引き続きServerless/Node runtimeに残し、軽量・低レイテンシ処理のみをEdgeに配置する判断基準を明確にすることが必要。

### 10. TypeScript type safety patterns 2026

- **型安全な状態管理:** `satisfies`演算子とDiscriminated Unionsを組み合わせることで、Redux/Zustandのstate型が実行時の値と完全一致し、`as`キャストなしでコンパイル時に不正な状態遷移を検出できる。

- **スキーマ駆動の境界検証:** Zodなどのスキーマライブラリで型を「定義」ではなく「導出」（`z.infer`）することで、APIレスポンスやフォーム入力などシステム境界での型と実行時バリデーションが乖離しなくなる。本プロジェクトでも`.claude/rules/standards.md`の方針通りZodを境界に徹底すべき。

- **Branded Typesによるプリミティブ誤用防止:** `UserId`や`PropertyId`のようにstringを直接使わずbranded typeで区別すると、`sellerId`と`buyerId`の取り違えのようなバグをコンパイル時に検出できる。sumitsugiのような複数エンティティ（前の住人/次の住人）を扱うドメインで特に有効。

- **テンプレートリテラル型とルーティングの整合:** Next.js App RouterのパスをTemplate Literal Typesで表現し、`src/app/properties/[id]`のようなdynamic routeのパラメータ型を`params`と自動同期させることで、リンク生成時のtypoをビルド時に検出できる。

- **`unknown`優先とnarrowingの徹底:** `any`を実質禁止し外部データは常に`unknown`で受けてtype guard/Zodでnarrowingする運用が2026年の標準になりつつあり、ESLintの`no-explicit-any`ルールと組み合わせて型の穴を塞ぐのが実用的。
