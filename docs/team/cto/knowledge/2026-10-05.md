# CTO Knowledge - 2026-10-05

## Daily Update (2026-10-05)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分のみSuspense境界でストリーミングすることで、TTFBとLCPを大幅に改善できる。既存の`getServerSideProps`依存ページから段階的に移行する価値が高い。

- **React Server Components前提のバンドル最適化:** クライアントバンドルサイズはRSC境界の設計で決まるため、`"use client"`境界を末端コンポーネントまで絞り込み、状態を持たない表示部分はサーバーコンポーネントに留めることがCore Web Vitals改善の近道。

- **キャッシュ戦略の明示化（`use cache` / Cache Components）:** Next.js 16で導入された明示的キャッシュディレクティブを使うことで、暗黙的なISR挙動によるキャッシュ崩壊を防ぎ、物件一覧・検索結果など更新頻度が異なるデータごとに粒度の細かいキャッシュ制御が可能。

- **画像・フォント最適化のCDNオフロード:** `next/image`と`next/font`は既に標準装備だが、2026年のベストプラクティスはVercel/CloudflareなどエッジCDNでのAVIF/WebP自動変換＋優先度ヒント（`fetchPriority`）併用で、物件写真が多いsumitsugiのようなリスティング中心サイトではLCP改善効果が特に大きい。

- **Turbopack本番ビルドの採用検討:** Turbopackが本番ビルドでも安定し始めており、ビルド時間短縮はCI全体のフィードバックループ短縮に直結する。ただし既存Webpack依存プラグインとの互換性は要検証。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** React 19/Next.js 16ではSuspenseバウンダリ単位でのストリーミングがデフォルト挙動となり、初期表示（TTFB）を遅延させずに重いデータ取得コンポーネントを後追いで送信できる。sumitsugiの物件一覧・詳細ページのような非同期データ取得が多い画面で特に効果が大きい。

- **Partial Prerendering (PPR) の実用化:** 静的シェル（ヘッダー、検索UI）を即時配信し、動的部分（在庫状況、価格）だけをストリームする手法が本番採用レベルに成熟。`src/app/properties/` のような一覧ページで、静的レイアウトを即描画しつつ物件データを非同期で流し込む設計が可能。

- **Server Actionsとの統合強化:** フォーム送信やミューテーション後の再検証（revalidation）がストリーミングと組み合わさり、楽観的UI更新がよりシンプルに書けるようになった。引越し費用の見積もりフォームなど多段階フローで有効。

- **キャッシュ戦略の複雑化に注意:** ストリーミング導入でコンポーネント単位のキャッシュ境界が増え、`fetch` のrevalidate設定ミスによる古いデータ表示リスクが上がる。物件ステータス（draft/public）のような状態変化が多いデータは、キャッシュタグを明示的に設計する必要がある。

- **計測指標の見直し:** TTFBだけでなくTTVC（Time to Visually Complete）やストリーミングチャンクごとのレイテンシ計測が重要になってきている。パフォーマンス改善の優先順位付けには、従来のLighthouse単体評価だけでなく分割済みチャンクの到達時間も見るべき。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはTypeScriptモノレポ構成（フロントエンド/バックエンド同一言語）において型安全性とDX面で優位性が明確になり、2026年時点では社内API・BFF層での採用がデフォルト化している。sumitsugiのようなNext.js App Router + TypeScript構成では、REST/GraphQLのスキーマ同期コストを避けられる点が特に有効。
- **ポイント2:** GraphQLは依然としてマルチクライアント（Web/iOS/Android/サードパーティ）が絡む複雑なデータグラフに強いが、N+1問題やキャッシュ制御の複雑さから「必要な場所にだけ使う」局所的採用が主流になっている。全面移行ではなくBFF境界での部分採用が実用的。
- **ポイント3:** RESTは外部公開APIやWebhook、サードパーティ連携の標準として依然最有力。OpenAPI 3.1 + JSON Schemaによる自動型生成・自動テスト生成が成熟し、「枯れた技術」としての安定運用コストの低さが評価されている。
- **ポイント4:** 2026年のトレンドとして、tRPCやGraphQLのレスポンスをそのままStreaming/Suspense（React Server Components）に流し込むパターンが普及。Next.js App Routerとの統合では、tRPCのsubscriptionやGraphQLのdeferred queryよりも、Server Actions + Server Componentsで直接データ取得する「API層を薄くする」設計が増えている。
- **ポイント5:** 内部API（住人間メッセージング、物件検索など）はtRPCで型安全に、外部連携（決済、本人確認API等のサードパーティ連携）はREST/OpenAPIで疎結合に、という「用途別ハイブリッド構成」が2026年のベストプラクティスとして定着している。

### 4. serverless edge computing 2026

- **ポイント1:** エッジでのLLM推論が本格化し、CDNエッジ上で軽量モデルのレイテンシが数十ms台まで短縮される一方、重い処理は依然中央のGPUクラスタに委ねるハイブリッド構成が主流になっています。
- **ポイント2:** WebAssembly（Wasm）ベースのランタイム（Fastly Compute、Cloudflare Workers等）がコールドスタートをほぼゼロに近づけ、Node.js互換レイヤーの成熟によりサーバーレスとエッジの境界がさらに薄くなっています。
- **ポイント3:** エッジでのステート管理（Durable Objects、エッジKV、分散SQLite系）が実用レベルに達し、グローバル分散でも強整合性に近い体験を低コストで実現できるようになっています。
- **ポイント4:** データレジデンシー・プライバシー規制対応のため「どこで処理するか」をルーティングレベルで制御するニーズが増え、エッジがコンプライアンス要件を満たす手段としても注目されています。
- **ポイント5:** 観測性・デバッグ環境の改善が進んだものの、分散トレーシングのコストはまだ高く、小規模チームではエッジ採用前にモニタリング基盤への投資判断が必要です。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証(WebAuthn/Passkeys)が主流となり、フィッシング耐性のある認証がユーザー体験を損なわずに実現可能。本サービスのログイン・本人確認フローでも優先的に採用すべき。

- **ゼロトラスト前提のセッション管理:** 「ログイン=信頼」ではなく、デバイス・位置情報・行動パターンを継続的に検証するリスクベース認証が標準化。短命トークン＋リフレッシュトークンのローテーションを徹底する。

- **OAuth/OIDC実装の脆弱性対策:** redirect_uri検証不備やPKCE未実装によるトークン漏洩が依然多発。サードパーティログイン(Google等)連携時はPKCE必須化とstateパラメータ検証を徹底する。

- **多要素認証のSIMスワップ耐性:** SMS-OTPはSIMスワップ攻撃に脆弱なため、認証アプリ(TOTP)やパスキーへの移行が推奨される。不動産取引は金銭が絡むため、本人確認フローでのSMS依存は見直すべき。

- **監査ログとセッション無効化の即時性:** 不正アクセス検知時に全セッションを即時失効できる仕組み(JWTのブラックリスト or 短命トークン設計)が必須。前の住人↔次の住人間の個人情報受け渡しがあるため、不正ログイン時の被害範囲を最小化する設計が重要。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はRustフリーのTypeScript版クエリエンジンへ移行しており、コールドスタートが大幅に短縮されたため、Supabase EdgeやVercel Edge Functionsとの組み合わせでもレイテンシ問題が解消されつつある。

- **ポイント2:** SupabaseのRLS（Row Level Security）とPrismaのスキーマ管理を併用する際は、Prisma Migrateで生成したDDLにRLSポリシーが引き継がれない点に注意し、`supabase/migrations`とPrismaのマイグレーションを分離・連携させる運用が定着してきている。

- **ポイント3:** Supabase PostgresのPooler（PgBouncer/Supavisor）とPrismaのコネクションプール設定の相性問題が頻発するため、サーバーレス環境では`DATABASE_URL`にトランザクションモード、直接接続用に別の`DIRECT_URL`を指定する二系統構成がベストプラクティス化している。

- **ポイント4:** pgvector + Supabase + Prismaでのベクトル検索対応が進み、Prisma側は`Unsupported("vector")`型での素のSQL併用が必要だが、埋め込み検索を伴うAI機能実装でのデータ基盤として選ばれるケースが増えている。

- **ポイント5:** マイグレーション起因の本番障害を防ぐため、CI上で`prisma migrate diff`による差分チェックとSupabaseのブランチング機能（開発用DBブランチ）を組み合わせ、本番適用前に自動検証するワークフローが標準になりつつある。

### 7. WebAssembly Rust performance 2026

- **WASI 0.2 / Component Modelの本格普及:** Preview2ベースのComponent Modelが2026年には主要ランタイム（Wasmtime, wasmCloud等）で標準化され、Rustの`cargo component`ツールチェーンで言語非依存なコンポーネント合成が実用レベルに。マイクロサービスをWasmコンポーネントとして分割し、起動コストをミリ秒未満に抑えられるのが強み。

- **エッジコンピューティングでの採用加速:** Cloudflare Workers、Fastly Compute、Vercel EdgeなどでRust+Wasmがネイティブに近い実行速度とコールドスタート数msを両立しており、Node.js/V8ベースより低レイテンシが求められるAPI層（認証、画像変換、A/Bルーティング）での採用が増加傾向。

- **SIMD128とマルチスレッド（Wasm Threads）の安定化:** `wasm32-wasip1-threads`や`std::simd`経由でRustのSIMD最適化がブラウザ/サーバー双方のWasmランタイムでフル活用可能になり、画像処理・暗号計算・ML推論前処理などCPUバウンドな処理でネイティブ比80-90%の性能が現実的に。

- **バイナリサイズ最適化とビルド時間のトレードオフ:** `wasm-opt`やLTO、`panic=abort`設定は定番化した一方、Cranelift backendの採用でデバッグビルドの高速化が進み、開発イテレーション速度とプロダクション最適化のバランスを取る設定分離がベストプラクティスとして定着。

- **WasmGC提案とRustの立ち位置:** GC言語（Kotlin, Java, Go）向けのWasmGCが標準化されつつある中、Rustは引き続きGCなし・linear memoryモデルの恩恵（予測可能なレイテンシ、小さいランタイムフットプリント）で差別化されており、リアルタイム処理が要求される用途ではRust+Wasmの優位性が維持される見込み。

### 8. Next.js App Router patterns 2026

## CTO視点: Next.js App Router patterns 2026

- **ポイント1（Server Components優先 + 最小限のクライアント化）:** デフォルトはServer Componentsで、`'use client'`は本当にインタラクティブな末端コンポーネントだけに絞るのが2026年の定石。バンドルサイズとTTIが直接改善するため、本プロジェクトでも`src/components/listing/`配下のインタラクション部分だけをクライアント境界にするレビューを継続すべき。

- **ポイント2（Cache Components / `use cache`ディレクティブ）:** Next.js 15以降で導入された明示的キャッシュモデル（fetchのデフォルト非キャッシュ化 + `use cache`での明示的指定）が16でも主流。暗黙的キャッシュに依存するコードは意図しない再検証漏れ・古いデータ表示の温床になるため、`src/lib/data.ts`のデータ取得関数は意図を明示したキャッシュ戦略にすべき。

- **ポイント3（Partial Prerendering + Suspense境界設計）:** PPRが安定化し、静的シェル＋動的穴（Suspense）の組み合わせが標準パターン。物件一覧ページのような「ヘッダーは静的・在庫データは動的」なページで、Suspense境界の粒度設計がCore Web Vitalsに直結する。

- **ポイント4（Server Actionsでのミューテーション一本化）:** フォーム送信・物件ステータス変更（`draft`/`public`切替など）はAPI Routeを増やさずServer Actionsに寄せるのが2026年のベストプラクティス。Zodによる入力検証をAction内で行うことで、API境界の重複実装を避けられる（`.claude/rules/standards.md`のZod方針とも整合）。

- **ポイント5（Turbopackのビルド/dev標準化）:** Turbopackがdevだけでなくビルドでもデフォルトになり、`bun run build`の実行時間が大幅短縮。CI上のビルド検証（CLAUDE.mdのBuild Integrity方針）がより高速にフィードバックを返せるようになっている点は、ワークフロー全体のイテレーション速度向上に効く。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge RuntimeはV8 isolateベースで実行されるため、Node.js APIに依存する重いライブラリ（`fs`、`crypto`のフルセットなど）を避け、Web標準API（`fetch`、`crypto.subtle`等）に統一することでコールドスタートを最小化できる。

- **ポイント2:** Edge Config / Vercel KVなどのエッジ最適化ストアを使い、DBへの往復をEdge Function内で行わない設計にすることで、グローバル配信時のレイテンシを大幅に削減できる（本プロジェクトの物件一覧・検索のような読み取り頻度の高いデータに有効）。

- **ポイント3:** ISR（Incremental Static Regeneration）とEdge Middlewareを組み合わせ、認証チェックやA/Bテストの判定はMiddlewareで軽量に行い、重い処理はServer Actions/Route Handlersに委譲する分離が2026年のベストプラクティスとして定着している。

- **ポイント4:** Streaming SSR（React Server Componentsのstreaming）をEdge Functionsと併用することで、初期バイトまでの時間（TTFB）を改善できるが、物件詳細ページのような画像を含むコンテンツはCDNキャッシュ戦略（`stale-while-revalidate`）との併用が必須。

- **ポイント5:** リクエスト課金モデルの変化（実行時間ベース→リクエスト数ベースの混合）が進んでおり、Edge Function内でのループ処理や外部API呼び出しの待機時間を減らす実装が、パフォーマンスだけでなくコスト最適化の観点でも重要になっている。

### 10. TypeScript type safety patterns 2026

**ポイント1:** Zodなどのランタイムスキーマバリデーションとの連携が標準化し、型定義とバリデーションロジックを単一ソースから自動生成するパターンが主流化。外部API入力やフォームデータの境界で型安全性を保証できる。

**ポイント2:** `satisfies`演算子の活用が定着し、型推論を狭めずに型チェックのみ行う設計が一般化。オブジェクトリテラルの意図しない型拡大を防ぎつつ、推論結果はそのまま活用できる。

**ポイント3:** Template Literal TypesとBranded Typesを組み合わせたドメイン固有の型（例: `UserId`と`PropertyId`の混同防止)が、大規模コードベースでの実行時エラー予防に効果的。sumitsugiのような`seller`/`property`等の内部用語を扱うデータ構造でも有用。

**ポイント4:** `tsc`の型チェック速度のボトルネックを解消するため、型チェックとトランスパイルを分離し、エディタ上の型チェックはLSPに委任、CI上はビルド時の型エラー検出を必須化する構成が定着。これはこのプロジェクトの「Build Integrity」方針（`bun run build`必須）とも合致する。

**ポイント5:** Discriminated Unionと網羅性チェック（`never`型を使ったexhaustiveness check）が、ステータス管理（例: `'draft' | 'public'`のような状態)の拡張時に新しい値の見落としをコンパイル時に検出する標準パターンとして広く採用されている。
