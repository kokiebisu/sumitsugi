# CTO Knowledge - 2026-07-24

## Daily Update (2026-07-24)

### 1. Next.js performance optimization 2026

- **ポイント1（Turbopackのデフォルト化）:** Next.js 16ではTurbopackが本番ビルドでも標準になりつつあり、Webpack比で大幅なビルド時間短縮が見込めます。sumitsugiのようなApp Routerベースの構成では、`next build --turbopack`への移行でCI時間の短縮効果が特に大きいです。

- **ポイント2（Partial Prerendering + キャッシュ制御の成熟）:** PPRと`use cache`ディレクティブの組み合わせが実用段階に入り、静的部分と動的部分（例: 物件一覧の枠は静的、価格や空室状況は動的）を1ページ内で細かく分離できます。物件詳細ページのようにSEOと個別性が両立するページで効果が高いです。

- **ポイント3（React Compilerによる自動最適化）:** React Compilerが安定版として広く使われ始め、`useMemo`/`useCallback`の手動最適化が不要になりつつあります。既存コンポーネントのメモ化コードを段階的に削除できる余地があり、コードの見通しも良くなります。

- **ポイント4（画像・フォントの自動最適化の強化）:** `next/image`のAVIF優先配信やフォントのサブセット最適化がデフォルトで賢くなっており、Airbnb風のビジュアル重視UIを持つsumitsugiではLCP改善に直結します。特に物件写真が多いページでの効果が大きいです。

- **ポイント5（計測基盤としてのCore Web Vitals統合）:** Vercel Analytics等とNext.jsの統合が進み、実ユーザー計測（RUM）ベースでのボトルネック特定が容易になっています。ローンチ前の今のタイミングで計測を仕込んでおくと、ベータ後のパフォーマンス改善サイクルが回しやすくなります。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** React Server Componentsのストリーミングは、Suspenseバウンダリ単位での段階的レンダリングがApp Router全般でデフォルト挙動として定着し、Time to First Byteとインタラクティブ化までの体感速度が大幅に改善されています。

- **Partial Prerendering (PPR) の実用化:** 静的シェルを即座に配信しつつ動的部分のみをストリーミングで後追いする手法が主流になり、CDNキャッシュと動的パーソナライズを両立できるようになっています。物件一覧のような静的+動的混在ページに有効です。

- **サーバー/クライアント境界の最適化がボトルネック管理の鍵:** `use client`境界をどこに引くかがバンドルサイズとストリーミング効率を左右するため、コンポーネント設計時に「どこまでサーバーで完結させるか」を意識した粒度設計が重要になっています。

- **エラーバウンダリとストリーミングの組み合わせ:** 個別Suspenseチャンクの失敗が全体のレンダリングをブロックしないよう、細粒度のerror.tsxとフォールバックUIの設計が2026年のベストプラクティスとして重視されています。

- **キャッシュ戦略との統合:** `revalidateTag`/`revalidatePath`とストリーミングを組み合わせ、ドラフト物件公開時などのミューテーション直後に該当セクションのみを再ストリーミングする部分的無効化パターンが普及しています。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはフルスタックTypeScript構成（Next.js + tRPC）において型安全性とDX面で優位性を維持しており、当プロジェクトのような単一リポジトリ構成では、REST/GraphQLよりスキーマ定義とクライアント生成の手間が少なく開発速度が上がる。
- **ポイント2:** GraphQLは複数クライアント（モバイル/Web/パートナーAPI）が同一バックエンドを利用する場合に有効だが、単一Next.jsアプリではオーバースペックになりがちで、キャッシュ戦略やN+1問題対策の運用コストが増える。
- **ポイント3:** RESTは依然として外部公開API・サードパーティ連携（決済、地図、外部弁護士向け書類生成など）のデファクトスタンダードであり、OpenAPI + Zodスキーマ検証の組み合わせが型安全性とドキュメント自動生成を両立させる主流パターン。
- **ポイント4:** 2026年時点ではAPI設計の潮流が「エージェント/LLM経由の呼び出し」を前提にした設計（構造化出力・関数呼び出し互換のスキーマ設計）にシフトしており、Zodスキーマをそのままツール定義に転用できる設計が実務上の資産になる。
- **ポイント5:** 当プロジェクトの規模（MVPローンチ準備フェーズ）では、tRPC中心+一部RESTエンドポイント（Webhook、外部連携）のハイブリッド構成が最も合理的で、GraphQL導入はマルチクライアント化が具体化してから検討すべき。

### 4. serverless edge computing 2026

- **ポイント1（WASMランタイムの主流化）:** Cloudflare Workers・Fastly Compute・Deno DeployなどのWASMベースのエッジランタイムがコールドスタートをほぼゼロに近づけており、2026年には重い処理を除く大半のAPIロジックをエッジファーストで書くのがデフォルト選択になりつつある。うちのAPI Routeも段階的にエッジ実行可能な部分（認証チェック、リダイレクト、軽量なデータ整形）から移行を検討する価値がある。

- **ポイント2（エッジDBとの整合性）:** Turso（libSQL）、Cloudflare D1、PlanetScaleのマルチリージョンレプリケーションが成熟し、エッジからの低レイテンシ読み取りが実用段階に入った。ただし書き込み整合性（read-your-writes）の設計判断がボトルネックになりやすく、物件公開・予約確定のようなクリティカルな書き込みは依然オリジンDB（Postgres等）に寄せる方が安全。

- **ポイント3（Next.js × Edge Runtimeの制約）:** Next.js 16のEdge Runtimeは依然Node.js APIの一部（fs、一部のcrypto、ネイティブモジュール）が使えないため、認証まわりのミドルウェアや軽量なリダイレクト処理には向くが、PDF生成やメール送信のような重い処理は引き続きNode.js Runtime（サーバーレス関数）に残す判断が現実的。

- **ポイント4（コスト最適化の観点）:** エッジ実行はリクエスト単位課金が細かく、トラフィックが薄いMVPフェーズでは「常時起動サーバーより明確に安い」が、スケール後は帯域・実行時間の従量課金が読みにくくなるため、ローンチ初期はエッジ活用でコストを抑えつつ、成長後の料金シミュレーションを早めに用意しておくべき。

- **ポイント5（可観測性のギャップ）:** エッジ環境は分散実行のためトレーシング・ログ集約が難しく、2026年時点でもOpenTelemetryのエッジ対応は発展途上。本番導入前に、Sentry/Datadog等のエッジ対応状況を検証し、最低限のエラートラッキングを先に固めておくことを推奨する。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証がデフォルトになりつつあり、フィッシング耐性のあるパスキーをNext.js/Auth.js等の標準フローに組み込むことが2026年のベストプラクティス。実装時はフォールバック手段（メール/SMS OTP）も併設し、デバイス紛失時の復旧導線を用意する。

- **セッション管理の厳格化:** JWTのみに頼らずリフレッシュトークンローテーションとサーバーサイドセッション無効化を組み合わせ、侵害時に即座に全セッションを失効できる設計が必須。httpOnly/secure/SameSite=strictなCookie設定とCSRFトークンの併用が前提。

- **ゼロトラスト×多層防御:** ログイン成功後もデバイスフィンガープリンティングや異常検知（IPの急変、非定型時間帯アクセス）で継続的にリスクスコアリングし、疑わしい操作にはステップアップ認証（MFA再要求）を挟む。

- **認可ロジックの分離とレート制限:** 認証（誰か）と認可（何ができるか）を明確に分離し、RBAC/ABACをミドルウェア層で一元管理。ブルートフォース対策として指数バックオフ付きレート制限をAPIエンドポイントごとに実装する。

- **秘密情報管理の自動化:** APIキーやシークレットのハードコード撲滅に加え、短命トークン（TTL短縮）と自動ローテーションを組み合わせ、漏洩時の被害範囲を最小化する運用が2026年の標準になりつつある。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のRust非依存化:** Prisma 6以降はQuery EngineがRustバイナリからTypeScript実装に移行し、Edge Runtime（Vercel Edge, Cloudflare Workers）でのコールドスタートが大幅短縮された。Supabase運用でもEdge Functions経由のDB接続がしやすくなっている。

- **Supabase Branching + Prisma Migrateの併用:** Supabaseのdatabase branching機能とPrisma Migrateを組み合わせることで、PR単位で本番同等スキーマのプレビュー環境を作れる。sumitsugiのような`draft`/`public`ステータス変更を伴うスキーマ変更は、本番反映前にbranch環境で検証すべき。

- **RLS（Row Level Security）とORMの責務分離:** SupabaseのRLSポリシーをアプリ層のZodバリデーションと二重で持つ設計がベストプラクティス化しつつある。前の住人/次の住人間の物件データアクセス制御は、アプリ層だけでなくDB層（RLS）でも強制すべき — 特にAuthコンテキスト経由の権限漏れ対策として。

- **Connection Poolingの重要性:** Prisma + Supabase構成ではPgBouncer（Supavisor）経由のプーリング設定が必須。サーバーレス関数（Vercel Functions）からの直接接続はコネクション枯渇を招くため、`DATABASE_URL`は必ずプーラー経由、マイグレーション時のみ直接接続用の別URLを使う構成が標準。

- **型安全性とスキーマドリフト検知:** Prisma Client生成型とSupabase CLIの`supabase gen types`を両方使うプロジェクトでは、片方だけ更新してドリフトが起きるリスクがある。CIに`prisma migrate diff`によるスキーマ整合性チェックを組み込むのが2026年のベストプラクティス。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Rustコンパイラの`wasm32-wasip2`ターゲット成熟により、WASIプレビュー2ベースのコンポーネントモデルが標準化され、ネイティブに近い起動速度とサンドボックス隔離を両立できるようになった。
- **ポイント2:** `wasm-opt`やLTO・`codegen-units=1`などのビルド最適化に加え、SIMD128命令の安定サポートが進み、画像処理・暗号化などCPU負荷の高い処理でネイティブ比80-90%の性能が現実的になっている。
- **ポイント3:** メモリモデルがlinear memoryからwasm-gc/コンポーネントモデルへ移行しつつあり、Rust側では`wit-bindgen`を使ったゼロコピーに近いインターフェース設計がパフォーマンスとバンドルサイズの両立に効いてくる。
- **ポイント4:** Cloudflare WorkersやFastly Compute@EdgeなどエッジランタイムでのRust/Wasm採用が進み、コールドスタート数ミリ秒という特性がサーバーレスAPIのレイテンシ改善に直結している。
- **ポイント5:** バンドルサイズ削減には`wee_alloc`より軽量な`talc`等の代替アロケータや`#![no_std]`構成が実用段階に入っており、フロントエンドへのWasm組み込み時の初期ロードコストを大きく下げられる。

### 8. Next.js App Router patterns 2026

- **App Router + Server Componentsのデフォルト化:** Client Componentは「必要な葉ノード」にのみ限定し、データ取得はServer Componentで完結させる設計が定着。バンドルサイズ削減とTTFB改善に直結するため、`use client`境界の見直しは継続的なパフォーマンス改善タスクになる。

- **Partial Prerendering (PPR) の実用フェーズ入り:** 静的シェルを即座に返しつつ、動的部分だけSuspenseでストリーミングする手法が本番運用レベルで安定。sumitsugiのような物件一覧・詳細ページでは、SEOに効く静的部分とログイン状態依存の動的部分を分離できるため、体感速度とCore Web Vitals両方に効く。

- **Server Actions中心のフォーム/Mutation設計:** APIルートを介さず`'use server'`関数を直接呼ぶパターンが標準化し、フォーム送信・楽観的UI更新のコードが大幅に簡素化。ただしCSRF・入力検証(Zod)は境界がぼやけやすいので、Server Action自体をシステム境界として明示的にバリデーションする規律が必須。

- **キャッシュ戦略の明示化(`cache: 'force-cache'` / `revalidate` / `unstable_cache`):** App Routerの暗黙キャッシュが混乱を招いた反省から、2026年時点ではキャッシュ意図をコード上で明示するのがベストプラクティス。物件情報のような「準リアルタイム性が求められるが更新頻度は低い」データには、tag-basedリバリデーション(`revalidateTag`)が特に有効。

- **Route Handlerの薄型化とドメインロジックの分離:** `src/app/api/`配下は認証・レート制限などの薄いレイヤーに留め、ビジネスロジックは`src/lib/`側に切り出す構成が主流。テスト容易性(unit/integration分離)とApp Router特有の型不整合リスクの低減に寄与する。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** 2026年のVercel Edge Runtimeは V8 isolateベースのコールドスタートがほぼゼロ（数ms単位）まで最適化されており、Node.js Runtimeとの機能差も縮小したため、認証チェックやリダイレクトのようなリクエスト単位の軽量処理はデフォルトでEdgeに寄せるのが定石になっている。

- **ポイント2:** Fluid Compute（Vercelの新しい実行モデル）により、Edge/Serverless関数間でインスタンスを再利用しつつ同時実行数をスケールできるようになったため、DBコネクションプーリングやAPI呼び出しの多いエンドポイントでもコスト効率が大幅に改善している。

- **ポイント3:** Next.js 16のPartial Prerendering（PPR）とEdge Functionsの組み合わせが本命の構成になりつつあり、静的シェルを即座に返しつつ動的部分だけEdgeでストリーミングすることで、TTFBを犠牲にせずパーソナライズを実現できる。

- **ポイント4:** リージョン選択の自動最適化（`vercel.json`のregionsではなく実際のトラフィック分布に基づく動的ルーティング）が進化し、日本国内ユーザー中心のsumitsugiのようなサービスでは`hnd1`固定より自動配置の方がレイテンシで有利になるケースが増えている。

- **ポイント5:** Edge Middleware内でのDBアクセス（Postgres over HTTPやKV系）が一般化し、認証・レート制限・A/Bテストの判定をミドルウェア層に寄せることで、実際のページ/APIルート側のロジックをシンプルに保てる設計が主流になっている。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x以降で強化された`satisfies`演算子とconst型パラメータの組み合わせが標準化し、型推論の精度を保ちながら過剰なアサーションを排除できるようになった。特にAPIレスポンスやconfigオブジェクトの型安全な定義に有効。
- **ポイント2:** Zodなどのスキーマバリデーションライブラリと型定義を一元化する「Schema-first」アプローチが定着し、実行時検証と静的型チェックの二重管理を防ぐパターンが主流になっている。本プロジェクトでも`Input validation: Use Zod schemas at system boundaries`として既に採用済み。
- **ポイント3:** Branded Types（Nominal Typing）を使った`UserId`や`ListingId`のようなID型の区別が、大規模コードベースでのバグ防止策として一般化。単なる`string`同士の誤代入をコンパイル時に検知できる。
- **ポイント4:** `unknown`をデフォルトとし`any`を原則禁止するESLintルール（`no-explicit-any`）の厳格運用が業界標準になりつつあり、型の穴を早期に塞ぐ文化が根付いている。
- **ポイント5:** テンプレートリテラル型とDiscriminated Unionを組み合わせたステートマシン的な型設計（例: `status: 'draft' | 'public'`の網羅性チェック）が、`switch`文の`exhaustiveness check`と併用されることでランタイムエラーを大幅削減している。
