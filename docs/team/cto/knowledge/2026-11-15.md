# CTO Knowledge - 2026-11-15

## Daily Update (2026-11-15)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分のみストリーミングする構成が標準に。物件一覧ページなど「ヘッダーは静的・在庫データは動的」という構成に特に有効で、TTFBを大幅短縮できる。

- **React Server Components前提のデータフェッチ最適化:** `fetch`のリクエストメモ化とキャッシュタグ（`revalidateTag`）を使い、物件詳細・前の住人プロフィールなど更新頻度が異なるデータを粒度別にキャッシュ制御するのが鍵。クライアントへのJS転送量を減らすため、インタラクティブ要素のみをClient Componentに切り出す設計が重要。

- **Turbopackのビルド/dev速度向上の活用:** Next.js 16でTurbopackが本番ビルドでも既定化され、`bun run build`の時間が短縮。CI上のビルド検証（CLAUDE.mdで必須化しているステップ）が高速化し、PRフィードバックループが短くなる。

- **画像・フォント最適化の継続的な見直し:** `next/image`のAVIF優先配信とレスポンシブ`sizes`指定、`next/font`のサブセット化を物件写真ギャラリーに適用し、LCPを改善。写真枚数が多い物件詳細ページほど効果が大きい。

- **Edge Runtime + Server Actionsの選択的採用:** 認証チェックや簡易なミューテーション（お気に入り登録など）はEdge Runtime上のServer Actionsに寄せ、レイテンシの地理的ばらつきを減らす。一方、重い処理（PDF生成など）はNode.js Runtimeに残すハイブリッド構成が2026年のベストプラクティス。

- **ポイント2:** `loading.tsx` と `Suspense` 境界の粒度設計がUXを左右する——粒度を細かくしすぎるとウォーターフォールでTTFBが悪化するため、データ取得の依存関係をコンポーネント境界に揃える設計が重要。
- **ポイント3:** Server Actionsのストリーミングレスポンス対応が進み、フォーム送信後の楽観的UI更新とサーバー側処理の進捗表示を組み合わせやすくなった。引越し費用決済フローなど多段階フォームでの活用価値が高い。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** 2026年現在、tRPCはTypeScriptフルスタック構成（Next.js + Bunなど）において「型安全性のオーバーヘッドゼロ」という強みから社内向けAPIやBFF層での採用が加速している一方、外部公開APIやモバイルクライアント向けには依然GraphQL/RESTが優位——クライアントの多様性に応じてプロトコルを使い分けるハイブリッド構成が主流になっている。
- **ポイント2:** GraphQLはフェデレーション（Apollo Federation / schema stitching）によるマイクロサービス統合で成熟期に入ったが、N+1問題やキャッシュ戦略の複雑さから「本当にクライアント側で柔軟なクエリが必要か」を見極めることが重要——sumitsugiのような単一フロントエンド+単一バックエンド構成ではtRPCまたはREST+Zodの方がシンプルで保守コストが低い。
- **ポイント3:** RESTは依然as the lingua francaとして健在——OpenAPI 3.1 + Zodスキーマからの型生成（zod-to-openapi等）により「スキーマファースト」の開発体験がtRPC並みに近づいており、外部連携や将来のパートナーAPI公開を見据えるなら拡張性の高いRESTを選ぶ価値がある。
- **ポイント4:** 2026年のトレンドとして、エッジランタイム（Vercel Edge / Cloudflare Workers）でのAPI実行が標準化し、プロトコル選定よりも「コールドスタート・レイテンシ・リージョン分散」を軸にAPI設計を評価する傾向が強まっている——sumitsugiのような日本国内向けサービスではエッジ配置によるレイテンシ改善がUX上の優先事項になり得る。
- **ポイント5:** AIエージェント統合（MCP: Model Context Protocolなど）が新たなAPI設計の軸として浮上しており、ツール呼び出し用のスキーマ定義（Zod/JSON Schema）がREST/GraphQL/tRPCいずれの選択とも独立した「第三の設計レイヤー」として求められ始めている——将来的にAIエージェント（内覧案内・問い合わせ対応など）を組み込む場合、API層をMCP互換のツール定義と分離して設計しておくと拡張が容易。

### 4. serverless edge computing 2026

## サーバーレスエッジコンピューティング 2026 — CTO視点

- **ポイント1（コールドスタートの実質ゼロ化）:** V8 isolates系ランタイム（Cloudflare Workers、Deno Deploy等）がスナップショット起動を標準化し、起動遅延がミリ秒未満に。重い初期化を要するNext.jsのようなフレームワークでもエッジSSRが本番運用に耐えるレベルになった。
- **ポイント2（データ層のエッジ移行）:** D1/Turso/PlanetScaleなど分散SQLiteベースのエッジDBが普及し、「コンピュートだけエッジ、DBは中央」という従来の非対称構成が崩れつつある。レイテンシ要件の強いプロダクトでは、DB選定をエッジ対応前提で再検討する価値がある。
- **ポイント3（WASM主導のポータビリティ）:** WASIの成熟により言語を問わずエッジ実行可能になり、ベンダーロックインのリスクが下がった。特定プラットフォーム専用APIへの依存を最小化する設計が長期的な柔軟性を生む。
- **ポイント4（エッジ推論の実用化）:** 軽量LLM/embeddingモデルのエッジ推論対応が進み、レコメンドや検索の一部をユーザー近傍で処理可能に。全てをエッジに寄せるのではなく、レイテンシが体験に直結する箇所だけ選択的に移行するのが現実的。
- **ポイント5（運用複雑性のトレードオフ）:** マルチリージョン・エッジ分散は可観測性とデバッグの難易度を上げる。小規模チームでは「どこまでエッジ化するか」を機能単位で見極め、過剰最適化を避ける判断が重要。

### 5. authentication security best practices 2026

- **パスキー/FIDO2が標準化:** 2026年現在、パスワードレス認証(WebAuthn/パスキー)が主流となり、フィッシング耐性のある認証がデフォルト要件になっています。sumitsugiでも新規登録フローにパスキー対応を優先すべきです。

- **多要素認証の強制とリスクベース認証:** 単純なMFAだけでなく、デバイスフィンガープリントやログイン挙動を分析してリスクが高い場合のみ追加認証を求める適応型認証が標準になっています。

- **トークン管理の厳格化:** JWTのような自己完結型トークンより、短命アクセストークン＋リフレッシュトークンのローテーション、サーバーサイドでの即時失効（revocation）機構が重視されています。セッション固定攻撃対策としてログイン毎にセッションIDを再生成することも必須です。

- **ゼロトラスト原則の浸透:** 「前の住人」「次の住人」間でのやり取りが発生するsumitsugiのような引継ぎプラットフォームでは、認証後も各APIリクエストで権限（物件所有者か、取引当事者か）を再検証するきめ細かい認可チェックが重要です。

- **サプライチェーン・依存ライブラリの監視:** 認証周りのライブラリ（NextAuth等）は攻撃対象になりやすく、定期的な依存関係スキャンとCVE監視が必須です。シークレットは必ず環境変数で管理し、エラーメッセージに認証情報の詳細を含めないことも基本原則として徹底します。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はRust不要の純TypeScriptエンジン（Prisma ORM Next-gen/QueryCompiler）に移行し、Supabaseのエッジ環境（Deno/Cloudflare Workers）でもコールドスタートなく動作するようになったため、サーバーレス構成でのレイテンシ問題が大幅に解消されている。
- **ポイント2:** SupabaseのRLS（Row Level Security）とPrismaのスキーマ管理を併用する際は、Prisma Migrateが生成するDDLにRLSポリシーが含まれないため、`supabase/migrations`とPrismaのマイグレーションを分離し、CIでRLS適用漏れを検知する仕組みが必須になっている。
- **ポイント3:** Supabaseの新しい Branching機能（PRごとにDBブランチを自動生成）とPrisma Migrate をCIに組み込むことで、PRレビュー時に実データ構造の差分確認ができ、本番マイグレーション事故を防げる。sumitsugiのような小規模チームでも導入コストが低い。
- **ポイント4:** コネクションプール問題（Supabase PgBouncer transaction modeとPrismaのprepared statement）は2026年時点でも注意点であり、`pgbouncer=true`設定とPrisma Accelerate等の併用、またはSupabaseのSession modeポートへの切り替えが実質的な回避策として定着している。
- **ポイント5:** Prismaの型安全性とSupabaseのリアルタイム機能（Postgres Changes）を組み合わせる場合、型生成はPrisma側、リアルタイム購読はSupabase SDK側と責務を分離するのがベストプラクティスで、物件ステータス（`draft`/`public`）のような状態遷移をリアルタイム反映する機能に有効。

### 7. WebAssembly Rust performance 2026

- **コンパイル最適化の進化:** Rust 2024 editionとwasm-bindgenの改善により、WASMバイナリサイズがさらに削減され、`wasm-opt`との統合がデフォルトのビルドパイプラインに組み込まれるケースが増えている。実装時はCI上で必ずサイズ計測を行い、リグレッションを早期検知すべき。

- **Component Model / WASIの成熟:** WASI Preview 2とComponent Modelの実運用が進み、Rustで書いたWASMモジュールをブラウザ外（エッジ、サーバーレス）でも共通インターフェースとして再利用しやすくなっている。将来的に画像処理や物件データのバリデーションロジックをWASMモジュール化して複数ランタイムで共有する選択肢が現実的になってきた。

- **SIMD/マルチスレッドの標準化:** WASM SIMDとスレッド（SharedArrayBuffer経由）がブラウザ主要エンジンで広くサポートされ、Rust側も`std::simd`やrayonのWASM対応が進展。画像のサムネイル生成やPDF生成などCPU負荷の高い処理をクライアント側にオフロードする余地が広がっている。

- **ツールチェーンの統合コスト低下:** `cargo component`やTrunkなどのツールが安定し、Next.js/Bunのビルドパイプラインへの統合が以前より容易になった。ただし導入時はビルド時間とデバッグ体験（sourcemap対応）のトレードオフを事前に検証すべき。

- **実務適用の勘所:** sumitsugiのようなプロダクトでは、全面的なWASM化よりも「重い計算のみ部分的にRust/WASMへ切り出す」ハイブリッド戦略が費用対効果が高い。現状はNext.js/TypeScriptの開発速度を優先し、PDF生成や画像処理などの特定ボトルネックが明確になった時点で導入を検討するのが妥当。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** 静的シェルと動的コンテンツを1つのレスポンスでストリーミング配信できるため、初期表示速度（TTFB/LCP）を落とさずに動的なパーソナライズ要素を組み込める。`sumitsugi`の物件一覧ページのように「静的なレイアウト＋動的な空室状況」といった構成に特に有効。

- **`"use cache"` ディレクティブによるキャッシュ制御の明示化:** fetchベースの暗黙的キャッシュから、関数/コンポーネント単位で`cacheLife`・`cacheTag`を明示する方式に移行。物件データのような更新頻度が異なる情報を細かく制御でき、再検証漏れによる古いデータ表示のリスクを減らせる。

- **Server Actions のセキュリティパターン成熟:** 入力のZod検証、認可チェック、CSRF対策をActions内で一貫して行うパターンがベストプラクティスとして定着。特にフォーム（物件登録・引越し費用算出など）ではActions内での検証を怠ると直接APIエンドポイント化されたリスクがあるため、`standards.md`にある「システム境界でのZod検証」をServer Actionsにも適用すべき。

- **Server/Client Component境界の最小化設計:** "use client"境界を葉（leaf）ノードまで押し下げ、インタラクティブな部分のみをクライアントコンポーネント化する設計が定石化。バンドルサイズ削減とRSCのストリーミング効果を最大化できる。

- **Turbopackのデフォルト化によるビルド時間短縮:** 開発時・本番ビルド双方で高速化が進み、`bun run build`のCI実行時間短縮に直結。大規模化した際のCI待ち時間がボトルネックになりにくい。

### 9. Vercel Edge Functions optimization 2026

- **Fluid Computeへの統合が進む:** Vercelは2025年にEdge FunctionsとServerless Functionsを統合した「Fluid Compute」モデルを本格展開しており、コールドスタート削減とインスタンス再利用による課金最適化が進んでいる。sumitsugiのようなSSR中心のNext.jsアプリでは、APIルートの実行時間課金を抑える設計（同時リクエストのバッチ処理）が重要になる。

- **Node.js runtimeとの差が縮小:** Edge Runtime（V8 isolates）は従来Node.js APIの制約が大きかったが、Web標準API互換が進み、認証ミドルウェアや軽量なリダイレクト処理であればEdgeで十分動くケースが増えている。重い処理（DB接続、PDF生成など）はNode runtimeに留め、`middleware.ts`のようなレイテンシ重視の処理のみEdge化するのが現実的な切り分け。

- **リージョン指定とデータ局所性:** Edge Functionsはグローバル分散がメリットだが、DB（Supabase/Postgresなど）が特定リージョンにある場合、Edgeからの往復レイテンシがむしろ悪化するケースがある。`vercel.json`の`regions`設定をDBに近いリージョンに固定し、「Edgeならどこでも速い」という誤解を避けるべき。

- **キャッシュ戦略の高度化:** Vercel Data Cache / ISRとEdge Middlewareを組み合わせた「stale-while-revalidate at the edge」が標準化しつつある。物件一覧・検索ページなど読み取り頻度が高いページは、Edgeでのキャッシュキー設計（ユーザー認証状態で分岐させない）がパフォーマンスとコストの両方に直結する。

- **可観測性コストに注意:** Edge Functionsの実行数・帯域課金はダッシュボードで見えにくく、ログ量も増えやすい。本番導入前に`bun run build`後のバンドルサイズとVercel Analyticsでの実行回数モニタリングを仕組み化しておかないと、スケール時に想定外のコスト増につながる。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** ブランド型（Branded Types）とテンプレートリテラル型の組み合わせで、ID文字列やUnit付き数値の誤用をコンパイル時に防ぐパターンが標準化しつつある。`type UserId = string & { __brand: 'UserId' }` のような手法が、Zodのようなスキーマライブラリと統合され、実行時検証と型の両方を1箇所で担保できるようになっている。

- **ポイント2:** `satisfies` 演算子の活用が定着し、型の広がり（widening）を防ぎながら推論を最大限活かす書き方が一般化している。設定オブジェクトや定数マップの定義で `as const satisfies Config` のようなパターンを使うことで、型安全性と自動補完を両立できる。

- **ポイント3:** Zod・Valibotなどのスキーマファーストライブラリが型定義の「単一の真実の源」となり、APIレスポンスやフォーム入力など境界（boundary）での実行時検証と静的型を自動同期させる設計が主流になっている。sumitsugiのコーディング規約でも「境界でのZod検証」を必須としている点と合致する。

- **ポイント4:** `exactOptionalPropertyTypes` や `noUncheckedIndexedAccess` など厳格なtsconfigフラグをデフォルトで有効化するプロジェクトが増え、`undefined`の暗黙的な混入によるランタイムエラーを型レベルで排除する動きが加速している。

- **ポイント5:** Discriminated Union（タグ付き合併型）を状態管理やAPIレスポンスの表現に使い、`switch`の網羅性チェック（`never`型での exhaustiveness check）と組み合わせることで、新しい状態追加時の実装漏れをビルド時に検出するパターンが引き続き重視されている。物件ステータス（`'draft' | 'public'`）のような union 型拡張時の全使用箇所grep確認は、このパターンの実践そのもの。
