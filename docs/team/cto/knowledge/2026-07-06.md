# CTO Knowledge - 2026-07-06

## Daily Update (2026-07-06)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16では静的シェルと動的コンテンツを1つのレスポンスでストリーミングできるPPRが安定版となり、TTFBを維持しつつパーソナライズされたUIを配信可能。sumitsugiの物件一覧ページなど「静的な骨格＋動的な空室状況」構成に特に有効。

- **Turbopackへの完全移行:** ビルド・devサーバーの標準バンドラーがTurbopackに統一され、Webpack比で大規模プロジェクトのビルド時間が大幅short化。`bun run build`のCI実行時間短縮にも直結するため、移行済みかの確認価値が高い。

- **React Server Components + Server Actionsのキャッシュ戦略見直し:** `use cache`ディレクティブとgranularなキャッシュタグ管理が主流化し、データ取得層でのover-fetch/under-cache問題を解消しやすくなった。物件詳細ページのようなSSRコンテンツで特に効果大。

- **画像・フォント最適化のエッジ処理シフト:** `next/image`の最適化処理がエッジランタイムでより高速化され、CDN層でのAVIF/WebP変換とpriority hintsの自動化が進んでいる。引越し費用シミュレーターのような画像多用ページのLCP改善に直結。

- **Core Web Vitals計測のRUM統合が標準化:** Vercel Analytics等がINP（Interaction to Next Paint）を軸にした計測をデフォルト提供し、フォーム多数のリスティング作成フローなどインタラクション重視の画面でのボトルネック特定が容易に。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPartial Prerendering（PPR）が安定版となり、静的シェルを即座に返しつつ動的部分だけをストリーミングする構成が標準化されている。物件一覧ページのような「上部は静的、下部は動的」な画面ではTTFBが大幅に改善される。
- **ポイント2:** `loading.tsx`とSuspense境界の粒度設計がパフォーマンスの分かれ目になる。境界を細かく切りすぎるとウォーターフォールが発生するため、データ取得の依存関係に沿って境界を設計する必要がある（例: 物件詳細ページの本体情報と前の住人プロフィールで境界を分ける）。
- **ポイント3:** Server Actionsのストリーミング対応が進み、フォーム送信中の楽観的UI更新（`useOptimistic`）と組み合わせることで、引越し費用の見積もりフォームのような多段階フローの体感速度を改善できる。
- **ポイント4:** RSCペイロードのキャッシュ戦略として`use cache`ディレクティブ（Next.js 16でGA）が重要になっている。物件データのような更新頻度が低いコンテンツはこれで明示的にキャッシュし、リクエストごとの再フェッチを避けるべき。
- **ポイント5:** ストリーミングSSRとエッジランタイムの組み合わせで、グローバルなレイテンシ改善が可能だが、Node.js専用ライブラリ（一部の認証・DB接続まわり）との互換性に注意が必要。移行前に依存ライブラリのエッジ対応状況を確認すべき。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの台頭）:** TypeScriptフルスタック構成（Next.js等）ではtRPCがスキーマ定義・型生成のオーバーヘッドなしにエンドツーエンドの型安全性を実現し、社内API/BFF層でREST/GraphQLに代わる選択肢として定着しつつある。ただし外部公開APIやマルチ言語クライアントには不向き。

- **ポイント2（GraphQLは複雑なクエリ要件に限定活用）:** GraphQLは依然としてクライアント側で柔軟なデータ取得が必要な複雑UI（ダッシュボード等）で強みを持つが、N+1問題やキャッシュ設計の複雑さから、シンプルなCRUD中心のプロダクトではオーバーエンジニアリングになりやすい。

- **ポイント3（RESTは外部公開APIのデファクト）:** サードパーティ連携や決済・不動産情報連携などの外部公開APIでは、依然としてRESTfulなJSON APIが標準。OpenAPI仕様からの型・SDK自動生成ツールチェーンが成熟しており、tRPCの型安全性の恩恵を境界を越えて得られる。

- **ポイント4（境界による使い分けが主流）:** 2026年時点のベストプラクティスは「内部通信はtRPC、外部公開APIはREST+OpenAPI、複雑な集約クエリが必要な箇所のみGraphQL」というハイブリッド構成。1つのプロトコルで全てを統一しようとする設計は避ける傾向が強まっている。

- **ポイント5（sumitsugiへの示唆）:** 現状のNext.js App Router構成では、Server Actions/Route Handlers + tRPCによる内部API型安全性の確保がまず優先度が高く、外部（決済代行・電子契約サービス等）との連携が増えるフェーズでOpenAPIベースのREST層を追加する段階的アプローチが妥当。

### 4. serverless edge computing 2026

- **ポイント1:** V8 Isolateベースのエッジランタイム（Cloudflare Workers、Vercel Edge Functions等）がコールドスタートをほぼゼロに近づけており、Next.jsのSSRをエッジで実行することでTTFBを大幅短縮できる。sumitsugiのような物件検索・一覧表示のようなレイテンシ敏感なページから段階的に移行するのが費用対効果が高い。

- **ポイント2:** エッジでのデータベースアクセスがボトルネックになりやすいため、エッジ対応DB（Turso/libSQL、PlanetScale、Neon等のリードレプリカをエッジ近接配置）やKVストア（Cloudflare KV, Vercel Edge Config）とのペアリングが2026年の標準構成になっている。物件データのような読み取り頻度が高いデータはエッジキャッシュ戦略の恩恵が大きい。

- **ポイント3:** WebAssembly (WASM) のエッジ実行が成熟し、画像処理・PDF生成（引越し費用の見積書生成など）といった重い処理もエッジで完結できるようになってきた。ただし全ての処理をエッジに寄せると可観測性（ログ・トレーシング）が分散して複雑化するため、Sentry等の分散トレーシング導入が前提条件になる。

- **ポイント4:** コスト面では「実行時間課金」から「リクエスト数課金」への移行が進み、トラフィックが不安定なMVPフェーズのプロダクトには従来のサーバーレス（Lambda等）よりエッジの方がコスト予測しやすい。ただしベンダーロックインリスクがあるため、Next.jsのミドルウェア層を薄く保ち、特定プラットフォーム依存のAPIを直接コンポーネントに埋め込まない設計が重要。

- **ポイント5:** セキュリティ観点では、エッジでの認証・認可判定（JWT検証など）を行うことでオリジンサーバーへの不正リクエストを事前に遮断できるが、エッジ関数内でのシークレット管理（環境変数の露出範囲）に注意が必要。認証まわりを扱う場合は特に、エッジとオリジンの責務分担を明確にドキュメント化すべき。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証がデファクトスタンダード化しており、フィッシング耐性のあるWebAuthn/パスキーをファーストクラスの認証手段として実装することが必須。SMS OTPやメール認証はフォールバックに留めるべき。

- **ゼロトラスト前提のセッション管理:** IPやデバイス単位での継続的なリスク評価（Adaptive Authentication）を組み込み、ログイン時だけでなくセッション中も異常検知を行う設計が主流になっている。JWTの有効期限を短くし、リフレッシュトークンのローテーション・失効管理を徹底する。

- **認可ロジックの分離とZodによる境界検証:** 認証（誰か）と認可（何ができるか）を明確に分離し、APIやServer Actionsの入力はすべてZodスキーマで検証する。ロールベースだけでなく属性ベース（ABAC）や関係ベース（ReBAC）の認可モデルも検討する価値がある。

- **秘密情報のシークレット管理徹底:** APIキーやセッションシークレットのハードコード禁止を徹底し、環境変数・シークレットマネージャー経由での管理を強制する。特にNext.jsのServer/Client境界を跨ぐ情報漏洩（クライアントバンドルへのシークレット混入）に注意が必要。

- **CSRF/XSS対策の多層防御:** Same-Site Cookie、CSPヘッダー、CSRFトークンを組み合わせた多層防御が基本。sumitsugiのような個人情報（前の住人・次の住人の連絡先等）を扱うプラットフォームでは、認証エラーメッセージに機密情報を含めない設計も重要。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma ORMはPostgreSQL向けにネイティブなRow Level Security連携やエッジランタイム対応を強化しており、SupabaseのAuth/RLSと組み合わせることでアプリケーション層とDB層の権限制御を二重に持たず、スキーマ定義だけでアクセス制御を完結できるようになっている。

- **ポイント2:** SupabaseはPostgres拡張（pgvector, pg_cron等）を標準搭載しており、ベクトル検索やバッチ処理を別サービスに切り出さずDB内で完結できる点が、マイクロサービス乱立を避けたい小規模チームにとって開発速度と保守性の両面で有利。

- **ポイント3:** Prisma Accelerate/Pulseのようなコネクションプーリング＋キャッシュ層がサーバーレス環境（Vercel等）でのコールドスタート時のDB接続枯渇問題を解消しており、Next.js App RouterのServer Components/Server Actionsから直接Prismaを呼ぶ構成でもスケーラビリティを確保しやすくなった。

- **ポイント4:** マイグレーション管理はPrisma Migrateのdeclarative schema diffが主流化しつつあり、SupabaseのCLIベースmigrationと役割分担（アプリ側スキーマはPrisma、DB側のRLS/トリガーはSupabase migration）を明確にすることでコンフリクトを防げる。

- **ポイント5:** sumitsugiのような`draft`/`public`のようなステータス遷移を持つドメインでは、PrismaのスキーマレベルでZodバリデーションと型を同期させる`zod-prisma-types`的なアプローチが、標準化ルールにある「union型変更時は全箇所grep」の手間を減らす実用的な選択肢になる。

### 7. WebAssembly Rust performance 2026

- **ゼロコストFFIの普及:** `wasm-bindgen`と`wit-bindgen`（Component Model準拠）が成熟し、JS⇄Rust間のデータコピーが大幅削減。文字列・配列操作を伴うAPIでも実測5-10倍の高速化が見込める。

- **SIMD標準化とマルチスレッド:** WASM SIMDが主要ブラウザで安定サポートされ、Rustの`std::simd`経由で画像処理・暗号化・数値計算が大きく高速化。Web Workers + SharedArrayBufferによる並列処理も現実的な選択肢に。

- **バイナリサイズ最適化の重要性継続:** `wasm-opt`、`twiggy`によるサイズ分析、`no_std`構成、LTO(`lto = true`)とcodegen-units=1の組み合わせが依然必須。初回ロード時間がUX直結のため、機能追加時は必ずバンドルサイズを計測すべき。

- **Component Model移行の実務化:** WASI Preview 2とComponent Modelが実運用フェーズに入り、言語間で再利用可能なWASMモジュール設計が可能に。当社が将来的にRust製の重い計算処理（PDF生成・画像最適化）をWASM化する際の設計指針として有効。

- **ネイティブ比80-95%の性能到達:** Rust→WASMのオーバーヘッドは特定ワークロード（数値計算・パーサー）でネイティブの90%超まで縮小。ただしDOM操作を伴う処理はJS境界越えコストが支配的なため、計算集約部分のみWASM化する設計判断が引き続き重要。

### 8. Next.js App Router patterns 2026

- **ポイント1（Server Components前提の設計）:** 2026年時点ではPartial Prerendering (PPR)が安定版となり、静的シェルと動的コンテンツを1リクエスト内で組み合わせるのがデフォルトパターン。物件一覧ページなどは静的部分（レイアウト・ヘッダー）と動的部分（在庫・価格）を分離することでTTFBを大幅短縮できる。

- **ポイント2（`use cache`ディレクティブの普及）:** Next.js 15以降で導入された`use cache`が2026年には主流のキャッシュ戦略になっており、`cacheTag`/`cacheLife`によるきめ細かい再検証が可能。sumitsugiの物件データ（`draft`/`public`ステータス変更）のような頻繁に変わるデータでも、タグベースの選択的invalidationで無駄な再ビルドを避けられる。

- **ポイント3（Server Actionsのセキュリティ強化）:** Server Actionsが本番運用のデファクトになった一方、CSRF対策・認可チェックの実装ミスが依然として最多の脆弱性源。認証まわり（`auth-context.tsx`）を触る際は、Server Action内で必ずセッション検証を行い、クライアントから渡されたIDだけで信頼しない設計が必須。

- **ポイント4（Route Groupsとparallel routesの実務活用）:** ダッシュボード的なUI（前の住人/次の住人双方向のビュー切り替えなど）では、parallel routes + intercepting routesを使ったモーダル/スライドオーバー実装が定番化。ページ遷移なしで詳細表示ができ、UXとSEOを両立できる。

- **ポイント5（ビルド時間とEdge Runtimeのトレードオフ）:** App Routerのバンドル最適化が進んだ一方、Edge Runtime対応のためにNode.js専用ライブラリ（一部の決済SDKなど）が使えないケースが依然残る。引越し費用の決済処理などNode依存が濃い部分はNode.js Runtimeに固定し、混在構成で運用するのが現実的。

### 9. Vercel Edge Functions optimization 2026

**CTO視点：Vercel Edge Functions optimization 2026**

- **ポイント1（コールドスタート最適化）:** V8 isolateベースの実行環境が成熟し、コールドスタートが1ms未満まで短縮されている。sumitsugiのようなSSRを多用するアプリでは、認証チェックや物件検索APIをEdge Functionsに移行することでTTFBを大幅改善できる。

- **ポイント2（Streaming SSRとの組み合わせ）:** Next.js 16のPartial Prerenderingと組み合わせることで、静的部分（物件一覧の骨組み）を即座に返しつつ、動的部分（在庫状況・価格）のみEdgeでストリーミング配信できる。ユーザー体験の初期表示速度が体感で大きく向上する。

- **ポイント3（リージョン配置の重要性）:** データベース（Supabase等）のリージョンとEdge Functionの実行リージョンが離れているとレイテンシが逆に悪化するケースがある。DBに近いリージョンへのアフィニティ設定、もしくはEdge対応のリードレプリカ活用が必須。

- **ポイント4（コスト管理）:** Edge Functionsは実行時間課金がNode.js Functionsと異なるモデルのため、重い処理（PDF生成、画像変換など）を誤ってEdgeに置くとコスト増につながる。軽量・低レイテンシ要求の処理（認証、リダイレクト、A/Bテスト振り分け）に限定するのが実用的。

- **ポイント5（Observability）:** Edge環境はNode.js APIの制約があるため、既存のロギング/監視ツールがそのまま動かないことがある。OpenTelemetry対応のEdge向け計装を早期に導入し、本番移行前にトレース欠落がないか検証すべき。

### 10. TypeScript type safety patterns 2026

## CTO所感：TypeScript type safety patterns 2026

- **ポイント1（`satisfies`演算子の定着）:** 型推論を保ちながら型チェックできる`satisfies`が標準的な書き方として浸透し、`as`によるアサーションで型安全性を損なうコードが減少。設定オブジェクトやconstマップの定義で特に有効。
- **ポイント2（Branded Types / Nominal Typing）:** `UserId`と`ProductId`のような構造的に同じstring型を区別するBranded Typesパターンが、IDの取り違えバグ防止のためAPI境界やDBクエリ周りで標準化しつつある。
- **ポイント3（Zodなどによるランタイム検証とコンパイル時型の統合）:** `z.infer`で型定義とバリデーションスキーマを一元化し、フォーム入力やAPIレスポンスなど「境界」での実行時型崩壊を防ぐパターンが強化。本プロジェクトのZod活用方針とも一致。
- **ポイント4（Exhaustiveness Checkingの徹底）:** Union型（例: `'draft' | 'public'`）を扱う`switch`文で`never`型を使った網羅性チェックを必須化する動きが強まり、新しいステータス追加時のハンドリング漏れをコンパイル時に検出。
- **ポイント5（型レベルテストの一般化）:** `tsd`や`expect-type`を使い、型定義自体をユニットテストのように検証する「型テスト」がCIパイプラインに組み込まれるケースが増加、複雑なジェネリクスやユーティリティ型の回帰を防止。
