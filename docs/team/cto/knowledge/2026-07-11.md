# CTO Knowledge - 2026-07-11

## Daily Update (2026-07-11)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Prerendering / PPR の本格運用）:** Next.js 15以降で導入されたPPRがNext.js 16では安定版として広く使われており、静的シェルを即座に配信しつつ動的部分をストリーミングすることで、TTFBとLCPを大幅に改善できる。うちのプロパティ一覧・詳細ページのような「共通レイアウトは静的、価格や空き状況は動的」という構成に特に相性が良い。

- **ポイント2（React Compiler前提の設計）:** React Compilerがデフォルト有効化されつつあり、`useMemo`/`useCallback`の手動最適化が不要になってきている。ただし過度な再レンダリングを誘発するpropsのバケツリレー設計は依然として問題なので、コンポーネント境界の切り方自体を見直す価値がある。

- **ポイント3（Server Components + データフェッチの並列化）:** ウォーターフォール状のfetchをやめ、`Promise.all`やparallel data fetchingパターンをServer Componentsで徹底することが、依然として最大の効きどころ。特に前の住人プロフィールと物件情報を同時取得するようなページで顕著に効果が出る。

- **ポイント4（画像・フォントの自動最適化の限界を理解する）:** `next/image`のAVIF/WebP自動変換やフォントのself-hostingは前提になっているが、Airbnb風のギャラリー表示のような大量画像UIでは、CDNレベルでのresponsive image配信（Cloudflare Images等）と組み合わせないとCore Web Vitalsが頭打ちになる。

- **ポイント5（Edge Runtimeの適用範囲を見極める）:** Edge Runtimeは低レイテンシだが、Node.js APIの制約が多く、認証まわり（auth-context.tsxが依存するライブラリ）で互換性問題が出やすい。全ページEdge化を狙うより、地理的レイテンシがクリティカルな箇所（物件検索API等）に限定適用するのが2026年時点の現実的な落とし所。

### 2. React Server Components streaming 2026

## CTO視点: React Server Components Streaming 2026

- **ポイント1（Partial Prerendering (PPR) の本格普及）:** Next.js 16ではPPRが安定版となり、静的シェルを即座に配信しつつ動的部分だけをストリーミングするパターンが標準化。物件一覧ページなどでTTFBを大幅短縮できる一方、キャッシュ境界の設計ミスが起きやすいので、`loading.tsx`と`Suspense`の粒度設計を最初に固めるべき。

- **ポイント2（Server ActionsとStreamingの統合が深化）:** フォーム送信後の楽観的UI更新とRSCストリーミングが組み合わさり、`useOptimistic` + Server Actionsでページ遷移なしの即時フィードバックが実装しやすくなった。物件掲載フォームや問い合わせフローで体感速度を上げられるが、エラー時のロールバック処理を丁寧に書かないとUXが崩れる。

- **ポイント3（Selective Hydrationのコスト最適化）:** クライアントバンドルサイズを抑えるため、インタラクティブ部分（画像ギャラリー、フィルターUI）だけをClient Componentに限定し、それ以外は全てServer Componentに寄せる設計が主流に。`"use client"`境界を安易に上位コンポーネントに置くと恩恵が消えるため、境界は末端に置くルールをチームで徹底する必要がある。

- **ポイント4（エッジランタイムとの親和性向上）:** Streaming SSRがVercel Edge / Cloudflare Workers等でネイティブサポートされ、地理的に分散したユーザーへの初期表示が高速化。ただしEdge Runtimeは一部Node.js APIが使えないため、`src/lib/data.ts`のようなデータ層をEdge互換に保つ検討が必要（DB接続方式に制約が出る可能性）。

- **ポイント5（デバッグ・可観測性ツールの成熟）:** React DevToolsやNext.js自体がストリーミングタイムライン可視化に対応し始め、どのチャンクがボトルネックかを特定しやすくなった。パフォーマンス問題の切り分けが「勘」から「計測」ベースに移行できるため、本番導入前に計測基盤を整えておく価値が高い。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの再興）:** フロントエンド/バックエンドを単一TypeScriptモノレポで管理するチームでは、tRPCがスキーマ生成不要でエンドツーエンドの型安全性を実現し、GraphQLの学習コストを避けたい小〜中規模チームで採用が加速している。

- **ポイント2（GraphQLはBFF層に集約）:** マイクロサービスが増える大規模組織では、GraphQLを「集約レイヤー」として使い、内部通信はgRPCやREST、外部公開のみGraphQLというハイブリッド構成が主流になっている。

- **ポイント3（OpenAPI×AI連携の重要性増）:** LLMエージェントやMCPサーバーがAPIを直接呼び出す機会が増え、厳密なOpenAPIスキーマ（型・エラー形式・説明文）が「人間向けドキュメント」から「AIエージェントが正しく叩くための契約」へと役割が変化している。

- **ポイント4（RESTのシンプルさが再評価）:** キャッシュ戦略やCDN活用が重要なpublic APIでは、HTTPセマンティクスをそのまま使えるRESTの運用しやすさが見直され、「デフォルトはREST、複雑なクエリが必要な箇所だけGraphQL」という使い分けが定着しつつある。

- **ポイント5（sumitsugiへの実用的示唆）:** 現状のNext.js App Router構成ではServer ActionsやRoute Handlersで十分なため、無理にGraphQLやtRPCを導入するより、型安全性はZodスキーマ＋TypeScript推論で担保し、将来的に外部パートナー連携（不動産会社API等）が必要になった段階でRESTのpublic APIを追加する方が、MVP後の開発速度とのバランスが取れる。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** 2026年にはLLM推論そのものをCDNエッジで実行するランタイム（Cloudflare Workers AI、Vercel Edge Functions等）が実用段階に入り、レイテンシ要件の厳しい機能（検索補完・レコメンド）はオリジンサーバーを介さず数十msで応答できるようになった。当プロジェクトのような住宅マッチング検索でも、エッジ側での軽量フィルタリングを検討する価値がある。

- **コールドスタート問題の実質的解消:** V8 isolateベースの実行環境が主流化し、コンテナ型サーバーレスに付きまとっていたコールドスタート（数百ms〜秒単位の遅延）がほぼゼロに近づいた。Next.js 16のEdge Runtimeもこの恩恵を受けており、認証チェックやミドルウェア処理をエッジに寄せる設計判断がしやすくなっている。

- **データレイヤーのエッジ分散が鍵:** 計算はエッジ化が進んだ一方、状態を持つデータベースアクセスがボトルネックになりやすい。エッジ対応のリードレプリカ（Turso/libSQL、PlanetScale等）やRegional Persistenceパターンの採用が2026年のベストプラクティスとして定着しており、本プロジェクトの物件データ読み取りパスにも応用余地がある。

- **コスト構造の逆転リスク:** リクエスト数に応じた従量課金は低トラフィック期には有利だが、スケールするとVM/コンテナ型より割高になるケースが増えている。ベータローンチ段階では最適だが、成長フェーズでの再アーキテクチャ（ハイブリッド構成への移行）を見据えたコスト試算を早めに行うべき。

- **可観測性とベンダーロックインのトレードオフ:** エッジランタイムはVercel/Cloudflare等プラットフォーム固有のAPIに依存しがちで、標準的なNode.js APIが使えない制約が開発速度に影響する。WinterCG仕様（Web標準API互換）への準拠が進んでいるベンダーを選ぶことで、将来の移行コストを抑えられる。

### 5. authentication security best practices 2026

- **パスキー標準化:** FIDO2/WebAuthnベースのパスキーが2026年時点でデファクトスタンダードとなり、パスワード+SMS認証は非推奨。実装コストが下がったため、新規プロジェクトはパスワードレスをデフォルト設計にすべき。

- **セッション管理の厳格化:** JWTの長期有効化は攻撃面を広げるため、短命アクセストークン＋リフレッシュトークンローテーション＋デバイスフィンガープリンティングの組み合わせが標準に。トークン漏洩時の被害範囲を最小化できる。

- **ゼロトラスト前提の認可設計:** 認証（誰か）と認可（何ができるか）を分離し、リクエスト単位でコンテキスト（IP・デバイス・行動パターン）を再評価する仕組みが求められる。RBACだけでなくABAC/リスクベース認証の併用が実用段階に入っている。

- **AIエージェント・ボット対策としての行動的シグナル活用:** LLMベースの自動化攻撃が増加し、CAPTCHAだけでは不十分。デバイス証明・行動生体認証・レート制限を多層化する設計が重要。

- **サプライチェーン経由の認証情報漏洩対策:** npm/依存パッケージ経由のトークン窃取事例が増加しており、シークレットは環境変数管理に加え、短命化・スコープ最小化・監査ログの自動アラートを組み合わせるべき（本プロジェクトの`API_KEY`環境変数運用方針とも整合）。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMの進化と型安全性の強化:** Prisma 6以降はRust非依存のTypeScriptネイティブクエリエンジンへ移行が進み、コールドスタート時間が大幅に短縮された。Edge環境（Vercel Edge Functions等）でのサーバーレスDB接続との親和性が高まっており、sumitsugiのようなNext.js App Routerベースの構成では特にメリットが大きい。

- **Supabaseのコネクションプーリング最適化:** PgBouncer統合とSupavisorの成熟により、サーバーレス関数からの大量同時接続問題が実質的に解消された。物件検索や引き継ぎフローのような読み取り負荷の高いエンドポイントでは、トランザクションモードのプーリングを明示的に設定することが引き続き重要。

- **Row Level Security (RLS) とアプリケーション層認可の二重防御:** SupabaseのRLSポリシーをDB側の最終防衛線として維持しつつ、Prismaのミドルウェア層でも認可チェックを行う「多層防御」パターンが2026年のベストプラクティスとして定着。特にセラー（前の住人）情報や個人情報を扱うテーブルでは必須。

- **Prisma AccelerateによるDXとキャッシュ層:** グローバルなクエリキャッシュとコネクションプーリングをマネージドで提供するAccelerateの採用が進み、物件一覧のような読み取り頻度が高いデータに対してレイテンシとDBコストを同時に削減できる。ただし料金体系はクエリ数課金のため、トラフィック予測に応じたキャッシュTTL設計が必要。

- **マイグレーション運用の自動化:** Prisma MigrateとSupabaseのブランチング機能（開発用DBブランチ）を組み合わせ、PRごとに独立したDB環境でスキーマ変更を検証するワークフローが標準化。sumitsugiの`draft`/`public`ステータスのようなunion型変更時は、このブランチング環境での事前検証がビルド崩壊の防止に直結する。

### 7. WebAssembly Rust performance 2026

- **ポイント1（WASM GCとRustの相性）:** WasmGC(Garbage Collection提案)の標準化が進み、Rustのようなランタイム不要言語はネイティブにコンパクトなwasmバイナリを生成できる優位性がさらに際立っている。JVM系言語がGC連携で苦労する中、Rustは引き続き最速クラスのWASM実行速度を維持している。

- **ポイント2（コンポーネントモデルの実用化）:** WASI Preview 2 / Component Modelが2026年時点で主要ランタイム（wasmtime, jco等）に定着し、Rustクレートをwasmコンポーネントとして再利用しやすくなった。マイクロサービス的に機能をwasmモジュール単位で分離・デプロイする設計が現実的な選択肢になっている。

- **ポイント3（SIMDとマルチスレッドの成熟）:** wasm SIMD128とスレッド（SharedArrayBuffer + Web Workers）がブラウザ全体で安定サポートされ、Rust+wasm-bindgenで画像処理・動画コーデック・暗号処理などCPU集約タスクをネイティブの70〜90%程度の性能で実行できるケースが増えている。

- **ポイント4（ビルドサイズと起動速度の最適化）:** `wasm-opt`、Rustのビルドプロファイル調整（`opt-level = "z"`, LTO, panic=abort）に加え、cargo-componentツールチェーンの改善でコールドスタート時間が大幅短縮。エッジ関数（Cloudflare Workers, Fastly Compute等）でRust+wasmを使う際のレイテンシメリットが引き続き大きい。

- **ポイント5（sumitsugiへの実用的示唆）:** 現状のNext.js/TypeScriptスタックには直接関係しないが、将来PDFレンダリングや画像処理・住宅診断ロジックなど計算負荷の高い機能を追加する場合、Rust+WASMをクライアントサイドまたはエッジで実行する選択肢は検討価値がある。ただし現フェーズ（ベータローンチ準備中）では優先度は低い。

### 8. Next.js App Router patterns 2026

- **ポイント1（Partial Prerendering の本格運用）:** Next.js 15以降で導入されたPPRが2026年には標準的な選択肢となり、静的シェルと動的コンテンツを1つのルートで共存させることで、TTFBを犠牲にせずパーソナライズ表示が可能になっている。sumitsugiの物件一覧ページのように「静的な検索UI＋動的な在庫データ」という構成に特に相性が良い。

- **ポイント2（`use cache` ディレクティブによるキャッシュ制御の明示化）:** fetchベースの暗黙キャッシュから、関数・コンポーネント単位で`use cache`を明示する方式への移行が進み、キャッシュの意図がコードから読み取れるようになった。物件詳細ページなど更新頻度が異なるデータ（価格 vs 物件基本情報）を分離してキャッシュ戦略を立てやすい。

- **ポイント3（Server Actionsの認可・バリデーション設計が定石化）:** Server Actionsは便利だが「実質的に公開APIエンドポイント」であるため、Zodによる入力検証とセッション検証をアクション冒頭で必ず行うパターンが業界標準になっている。認証まわり（前の住人/次の住人のロール分岐）を扱う本プロジェクトでは特に重要。

- **ポイント4（Turbopackがデフォルトビルドツールとして安定）:** 開発体験・本番ビルド速度の両方でwebpackから完全移行が進み、大規模モノレポでもビルド時間の短縮が実測されている。ただし一部のwebpack専用プラグインは移行対応が必要になるため、依存ライブラリの互換性は事前確認が必須。

- **ポイント5（Parallel Routes / Interceptingを使ったモーダル型UXの普及）:** 物件詳細のモーダル表示や画像ギャラリーなど、URLを保持したままオーバーレイUIを実現するパターンが定着し、SEOとUXを両立させやすくなった。Airbnb風のリスティング体験を目指す本プロジェクトのデザイン原則と親和性が高い。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約を前提にした設計:** Vercel Edge FunctionsはNode.js APIの一部が使えないため、依存ライブラリを事前に精査し、軽量な代替（`fetch`ベースのSDKなど）を選定することでコールドスタートを最小化できる。

- **リージョン最適化とデータ近接性:** 2026年時点ではEdge Config・Edge Middlewareと組み合わせ、DB読み取りをユーザーに最も近いリージョンにルーティングする構成が主流になっており、レイテンシをミリ秒単位で削減できる。

- **ストリーミングレスポンスの活用:** LLM連携やSSRの部分ハイドレーションにおいて、Edge Functionsからのストリーミングレスポンス（`ReadableStream`）を使うことでTTFB（Time To First Byte）を大幅に改善できる。

- **ISR/On-Demand Revalidationとの併用:** 静的コンテンツはEdge Cacheに任せ、動的処理のみEdge Functionsに委譲する棲み分けにより、コンピュートコストと応答速度のバランスを最適化できる。

- **可観測性の強化:** Edge環境特有のデバッグ困難さに対応するため、OpenTelemetry対応のトレーシングを導入し、リクエスト単位でのレイテンシ内訳を可視化する運用が2026年のベストプラクティスとして定着しつつある。

### 10. TypeScript type safety patterns 2026

- **ポイント1（型優先の関数設計）:** `satisfies`演算子とconst型パラメータの活用が定着し、型推論を保ったまま値のリテラル性を維持する設計が主流になっている。Zodなど実行時バリデーションからの型導出（`z.infer`）と組み合わせ、システム境界での型安全性を二重に担保するパターンが標準化。

- **ポイント2（Branded Types / Nominal Typing）:** `UserId`と`PropertyId`のような構造的には同じstring型を区別するBranded Typesが、DB IDやステータス値の取り違えバグを防ぐパターンとして一般化。sumitsugiの`'draft' | 'public'`のようなunion型ステータスも、Branded化やexhaustiveness checkと組み合わせることで安全性が上がる。

- **ポイント3（Exhaustiveness Checkingの徹底）:** switch文の`default`ケースで`never`型アサーションを使い、union型に新しい値が追加された際にコンパイルエラーで検知する手法が必須パターン化。CLAUDE.mdにある「union型変更時は全usageをgrep」というルールを、型システム側でも機械的に担保できる。

- **ポイント4（型テスト = TDDの一部）:** `tsd`や`expect-type`を使った型レベルのユニットテストが、関数シグネチャや複雑なジェネリクスの回帰防止策として普及。実装コードだけでなく型定義そのものをTDDサイクルに組み込む動きが加速している。

- **ポイント5（AIエージェント時代のビルド健全性）:** 自律開発エージェント（Claude Codeなど）が並列でコード生成する運用が増える中、`tsc --noEmit`の高速化（Isolated Declarations、プロジェクト参照分割）が重要度を増している。ビルドを唯一の信頼できる正解源とし、「ビルドが通らなければタスク未完了」という運用ルールが型安全性のガードレールとして機能する。
