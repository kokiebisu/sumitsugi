# CTO Knowledge - 2026-11-09

## Daily Update (2026-11-09)

### 1. Next.js performance optimization 2026

- **React Server Components とPartial Prerendering の本格活用:** Next.js 16ではPPRが安定版となり、静的シェルを即座に返しつつ動的部分だけストリーミングすることで、TTFBとLCPを大幅に改善できる。ページ単位ではなくコンポーネント単位でキャッシュ戦略を設計することが重要になる。

- **Turbopack によるビルド・開発体験の最適化:** Turbopackがデフォルトビルドツールとして定着し、大規模コードベースでもHMRとプロダクションビルドが高速化。CIのビルド時間短縮にも直結するため、`bun run build` の実行時間を定期的に監視する価値がある。

- **`use cache` ディレクティブによる明示的キャッシュ制御:** fetchベースの暗黙キャッシュから、関数・コンポーネント単位で `use cache` を明示する方式へ移行が進んでいる。データ取得ロジック（`src/lib/data.ts`など）のキャッシュ境界を明確化し、過剰な再フェッチを防げる。

- **画像・フォント最適化とCore Web Vitals (INP重視):** LCP/CLSに加えINP（Interaction to Next Paint）がより重視される流れで、`next/image`のpriority指定やフォントのセルフホスティングに加え、クライアントコンポーネントの肥大化を避け、インタラクション処理を軽量化することが評価に直結する。

- **Edge/Node ランタイムの使い分けとコールドスタート対策:** 認証やpropertiesページなど地理的レイテンシに敏感な箇所はEdge Runtimeを選び、DB接続が必要な処理はNode Runtimeに留めるなど、ルート単位でランタイムを最適配置する判断が重要になっている。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPPR（Partial Prerendering）が安定版となり、静的シェルを即時配信しつつ動的部分だけをストリーミングする構成が標準化。本プロジェクトの`properties/`一覧ページのような「検索結果+パーソナライズ要素」混在UIで初期表示速度を大きく改善できる。

- **ポイント2:** `loading.tsx`とSuspenseバウンダリの粒度設計がパフォーマンスの鍵になっており、1ページに対して粗すぎる境界だと「遅いAPI1本がページ全体をブロックする」問題が起きやすい。物件詳細ページなど複数データソース（物件情報・前の住人のレビュー・引越し費用見積もり）を持つ画面では、データソース単位でSuspenseを分割すべき。

- **ポイント3:** RSCのストリーミングはCDN/Edgeランタイムとの相性がさらに重要になっており、Vercel以外のホスティングでもHTTPチャンク転送をサポートするインフラ選定が前提になる。自前インフラやリバースプロキシを挟む場合、バッファリング設定でストリーミングが無効化される事故が2026年も頻発している。

- **ポイント4:** Server ActionsとRSCストリーミングの組み合わせで、フォーム送信後の楽観的UI更新パターンが成熟してきた。認証や決済など`useFormStatus`/`useActionState`を使った段階的フィードバックは、本プロジェクトの登録・問い合わせフォームのUX改善に直接応用できる。

- **ポイント5:** ストリーミングSSR環境でのテスト戦略（Playwrightでのネットワークスロットリング下の表示順序検証）が重要な技術的負債ポイントになりやすく、E2Eテストに「ストリーミング順序が崩れていないか」の検証を明示的に加えるチームが増えている。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1: tRPCの採用拡大とスキーマ駆動開発の統合** TypeScriptモノレポ構成のプロジェクトでは、tRPCがREST/GraphQLに代わる選択肢として定着しつつあり、フロントエンド・バックエンド間の型安全性をコード生成なしで実現できる点が評価されている。sumitsugiのようなNext.js App Router構成では、tRPCかServer Actions直呼びのどちらかに統一することで、API層の二重メンテナンスを避けられる。

- **ポイント2: GraphQLはBFF（Backend for Frontend）用途に特化** 汎用APIとしてのGraphQL採用は減少傾向にあり、複数クライアント（Web/モバイル/パートナー連携）が同一データソースに異なる形で依存する場合のアグリゲーション層としての利用に収束している。単一のWebアプリのみが現状のスコープであれば、GraphQL導入のROIは低い。

- **ポイント3: RESTは外部連携・サードパーティAPIの標準として残存** 内部通信はtRPCやRPC的な型安全通信に移行しても、決済代行（Stripe等）や外部連携（物件情報API等）とのインターフェースはREST/Webhookが依然主流。外部境界ではOpenAPI仕様書とZodスキーマの同期を自動化しておくと、仕様ドリフトを防げる。

- **ポイント4: エッジランタイム対応とレイテンシ最適化が設計の前提に** Next.js 16世代ではVercel EdgeやCloudflare Workers上でのAPI実行が標準的な選択肢になっており、API設計時点でNode.js専用ライブラリ依存（特定のORMやネイティブモジュール）を避けることが、将来のエッジ移行コストを下げる。

- **ポイント5: AIエージェント経由アクセスを想定したAPI設計** LLMエージェントがAPIを直接呼び出すケース（MCP経由含む）が増え、エンドポイント設計時に「人間向けUI用」と「エージェント向け構造化アクセス用」を分離するか、十分な自己記述性（スキーマ・エラーメッセージの明確さ）を持たせる必要性が高まっている。sumitsugiの引き継ぎフローのような複雑な業務ロジックは、将来的にエージェント操作を想定した設計を検討する価値がある。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** 2026年はCloudflare Workers AI、Vercel Edge Functions、Deno DeployなどでLLM推論を直接エッジ実行する構成が一般化し、レイテンシ要件の厳しい機能（検索、レコメンド）はオリジンサーバーを経由せずエッジで完結させるのが実用的な選択肢になっている。

- **コールドスタート問題の実質解消:** V8 isolateベースのランタイム（Cloudflare Workers等）やWasmの採用により起動時間がミリ秒単位に収まり、トラフィックが不規則なB2Cサービス（sumitsugiのような物件検索・マッチング系UI）でもサーバーレスエッジを常用インフラとして採用しやすくなった。

- **エッジDBとの統合がボトルネック解消の鍵:** Turso、PlanetScale、Cloudflare D1などエッジ対応のレプリケーションDBが成熟し、読み取り主体のページ（物件一覧・検索）をエッジでSSRしつつ書き込みは中央DBに委譲する「読み書き分離」構成がデフォルトパターンになっている。Next.js 16のPPR（Partial Prerendering）と組み合わせると特に効果的。

- **コスト構造の変化に注意:** エッジ実行は従量課金でリクエスト単価は下がる一方、長時間実行・大きなペイロード処理には不向きなため、PDF生成や画像処理などの重い処理は依然Node.jsランタイム（Vercel Functions等）に残すハイブリッド構成が2026年のベストプラクティス。全部エッジ化しようとするとコストと複雑性が逆に増える。

- **Observabilityの難易度上昇:** 分散実行されるため従来のAPMツールでは追跡しづらく、OpenTelemetryのエッジ対応やトレースIDの伝播設計を初期段階から組み込む必要がある。後回しにすると本番障害時の原因特定が著しく困難になる。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** 2026年現在、パスワードレス認証（パスキー）が主流となり、フィッシング耐性のあるWebAuthn/FIDO2ベースの認証がSaaSの標準実装になっている。sumitsugiのような個人情報（物件・引越し情報）を扱うプラットフォームでは、パスキー対応により不正ログインリスクを大幅に低減できる。

- **セッション管理とトークンの短命化:** JWTやセッショントークンの有効期限を短くし、リフレッシュトークンのローテーション＋デバイスフィンガープリンティングを組み合わせる手法が標準化している。長期セッションを許すUXと安全性のバランスは、物件情報へのアクセス権限の重みに応じて段階的に設計すべき。

- **ゼロトラスト前提のAPI境界検証:** フロントエンドの認証状態だけに依存せず、全APIエンドポイントでサーバーサイドの権限チェック（RBAC/属性ベース）を徹底する考え方が必須化している。`src/app/api`配下の各ルートで、`seller`/`buyer`といったロールごとのアクセス制御を漏れなく検証する必要がある。

- **多要素認証（MFA）の段階的強制:** 全ユーザーに一律MFAを強制するのではなく、リスクベース（決済・物件公開操作など高リスク操作時のみ）でMFAを要求する適応型認証（Adaptive MFA）が実用的なベストプラクティスとして定着している。

- **シークレット管理とローテーションの自動化:** 2026年のベストプラクティスでは、APIキーやOAuthトークンを環境変数に留めるだけでなく、Vault/KMS等による自動ローテーションと漏洩検知（GitHub Secret Scanning等）をCI/CDに組み込むことが前提となっている。本プロジェクトのCLAUDE_CODE_OAUTH_TOKENのようなシークレットも定期ローテーション運用を検討すべき。

### 6. database architecture Prisma Supabase 2026

- **マネージドPostgresへの統合加速:** SupabaseはPrismaとの相性を前提に、Row Level Security（RLS）とPrisma ORMを併用する構成が2026年の標準パターンになっている。Prisma側でRLSバイパス用の`DIRECT_URL`接続とプール接続（PgBouncer経由）を分離する設計が重要。
- **Prisma Accelerateによるエッジ最適化:** サーバーレス環境（Vercel Edge Functions等）でのコールドスタート問題に対し、Prisma Accelerateのコネクションプーリング＋キャッシュ層を使うことでレイテンシを大幅改善できる。Next.js 16のPartial Prerenderingと組み合わせる際は特に有効。
- **スキーマ駆動開発とマイグレーション安全性:** Prisma Migrateのshadow database機能とSupabaseのブランチング（Preview環境ごとのDB分岐）を併用すると、本番マイグレーション前の検証フローを自動化できる。CI上で`prisma migrate diff`を必須チェックにするのが実用的。
- **型安全性とZodの連携:** Prismaが生成する型とZodスキーマを`zod-prisma-types`等で同期させることで、本プロジェクトの「システム境界でのZod検証」方針とDB層の型を一貫させられる。物件ステータス（`'draft' | 'public'`）のようなUnion型はDB enumとTS型を必ず一致させる。
- **リアルタイム機能の使い分け:** Supabase Realtimeは「前の住人」「次の住人」間のチャット等のライブ更新に有効だが、Prismaの書き込みと競合しないよう、Realtimeはあくまる読み取り通知用に限定し、書き込みはPrisma経由に統一するのが2026年のベストプラクティス。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC（ガベージコレクション提案）とcomponent modelの標準化が進み、RustからWasmへのコンパイルでメモリ管理のオーバーヘッドが減少。ネイティブに近い実行速度を保ちつつ、JS/他言語との相互運用がより軽量になっている。
- **ポイント2:** SIMD128やmulti-value returnsがブラウザ・ランタイム（wasmtime, wasmer）で標準サポートされ、画像処理・暗号化・数値計算系のRustワークロードでネイティブの80-95%の性能に到達するケースが増えている。
- **ポイント3:** `wasm-bindgen`やトレイトベースのFFIレイヤーが成熟し、Rust側のゼロコスト抽象化がWasmバイナリサイズ・起動時間に直結する課題として注目されている。`wasm-opt`とLTO設定を組み合わせたビルドパイプラインの最適化が実務的な差別化要因。
- **ポイント4:** サーバーサイドではWASI Preview 2によりファイルI/O・ネットワークアクセスが標準化され、RustのWasmバイナリをエッジ（Cloudflare Workers、Fastly Compute）でコールドスタート1ms以下で動かす事例が一般化しつつある。
- **ポイント5:** 弊社のようなNext.js/TypeScript中心のスタックでは、画像変換やPDF生成など計算負荷の高い処理を部分的にRust+Wasmへオフロードすることで、サーバーコスト削減とレスポンス速度向上を同時に狙える余地がある（ただしビルド複雑性とデバッグ難易度のトレードオフは要検討）。

### 8. Next.js App Router patterns 2026

**CTO視点:Next.js App Router patterns 2026**

- **ポイント1(Partial Prerendering標準化):** PPRが安定版となり静的シェル+動的ホールの組み合わせが標準パターンに。本プロジェクトでも物件一覧ページなど「静的な骨組み+動的な価格/在庫情報」構成に適用し、TTFBを大幅改善できる。
- **ポイント2(Server Actionsのバリデーション一体化):** Zodスキーマをサーバーアクション内で直接実行し、クライアント側の型安全性とサーバー側検証を一本化する流れが定着。`standards.md`の「入力検証はZod必須」方針とも合致し、フォーム処理のボイラープレートを削減できる。
- **ポイント3(キャッシュ戦略の明示化):** `fetch`のデフォルトキャッシュ挙動が廃止方向にあり、`cacheLife`/`cacheTag`による明示的な再検証指定が主流に。問い合わせフォームや予約状況など鮮度が重要なデータで、意図しないキャッシュ事故を防げる。
- **ポイント4(Server Componentsの境界設計):** 'use client'境界を機能単位ではなくインタラクション単位で最小化する設計が定石化。バンドルサイズ削減に直結し、物件詳細ページの画像ギャラリーなど一部のみクライアント化する判断がより重要になる。
- **ポイント5(ミドルウェアの軽量化トレンド):** Edge Middlewareは認可チェックなど最小限に留め、重い処理はServer Componentsへ移す流れが加速。認証コンテキスト(`auth-context.tsx`)周りのレイテンシ最適化に活用できる。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge FunctionsのCPU時間課金が洗練され、2026年はコールドスタート最適化よりも「実行時間あたりのコスト」を意識した設計が主流になっている。重い処理はEdgeからNode.js Functions（Fluid compute）に切り出す判断が重要。
- **ポイント2:** Fluid Compute（インスタンスの同時リクエスト処理）がデフォルト化し、Edge/Serverlessの境界が薄くなっているため、物件検索APIのような読み取り中心の処理はEdgeに残し、DB書き込みを含む処理はNode runtimeに寄せる構成が実用的。
- **ポイント3:** ISR/PPR（Partial Prerendering）とEdge Middlewareの組み合わせが成熟し、物件一覧ページのような「一部動的・一部静的」なUIをEdgeでストリーミング配信できるようになっている。Next.js 16のキャッシュコンポーネント活用が鍵。
- **ポイント4:** Edge Config / KVのリージョンレプリケーションが進化し、認証状態や物件ステータス(`draft`/`public`)の判定など低レイテンシ参照はEdge Configに寄せることで、オリジンへのラウンドトリップを削減できる。
- **ポイント5:** Observability面でVercelのOpenTelemetry統合が強化され、Edge Function単位でのレイテンシ・コスト可視化が容易になったため、パフォーマンス劣化の早期検知と課金最適化を同時に進めやすくなっている。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x系の`satisfies`演算子が標準化し、型推論を保ちながら型チェックを強制するパターンが定着。Zodなど実行時バリデーションとの組み合わせで「型は静的、値は動的」の境界を明確にする設計が主流に。
- **ポイント2:** Branded Types（nominal typing）がID誤代入防止の定番パターンとして普及。`type UserId = string & { readonly __brand: 'UserId' }`のような手法で、構造的に同じ型同士の混在バグをコンパイル時に検出。
- **ポイント3:** テンプレートリテラル型とConditional Typesを使った「スキーマからAPI型を自動生成」する手法が成熟し、tRPCやOpenAPI生成ツールとの統合でフロント・バック間の型安全性がエンドツーエンドで保証されるようになった。
- **ポイント4:** `exactOptionalPropertyTypes`や`noUncheckedIndexedAccess`など厳格化フラグをデフォルトで有効にするのがベストプラクティス化。本プロジェクトのような`'draft' | 'public'`のUnion型も、この設定下では網羅性チェック（exhaustiveness check）が漏れを即座に検出する。
- **ポイント5:** Zodなどのスキーマライブラリで型定義とバリデーションを一元化する「Schema-first」開発が標準化。`standards.md`にある「Zodスキーマで境界検証」の方針は、型安全性と実行時安全性を同時に満たす2026年のベストプラクティスと一致している。
