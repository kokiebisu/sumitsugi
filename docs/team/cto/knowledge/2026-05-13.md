# CTO Knowledge - 2026-05-13

## Daily Update (2026-05-13)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを大幅削減できるRSCを default にし、`'use client'` はインタラクティブな末端コンポーネントのみに限定する。2026年時点では多くのプロジェクトがまだ誤った粒度で配置しており、バンドル肥大化の主因になっている。

- **Partial Prerendering (PPR) による静的/動的の最適な組み合わせ:** Next.js 15以降で安定したPPRを活用し、ページの静的シェルを即時配信しつつ動的コンテンツをSuspenseでストリーミングする。SSR・SSGの二択思考から脱却することで、TTFB と LCP の両方を改善できる。

- **`next/image` と `next/font` の設定見直し:** `sizes` prop の最適化とAVIF優先フォーマット指定、Googleフォントのセルフホスティングによるサードパーティリクエスト削減が、Core Web Vitals（特にCLS・LCP）に直結する低コスト改善策。

- **Server Actions のN+1問題対策:** Server Actionsの普及でDB直接呼び出しが増えたが、DataLoader相当のバッチング（Prismaであれば `findMany` + Map変換）やReact `cache()` によるリクエストスコープキャッシュの導入が不可欠。

- **Edge Runtimeの選択的適用:** ミドルウェアや認証チェックはEdge Runtimeで低レイテンシを実現できるが、Node.js API依存の処理と混在するとデプロイ複雑性が上がる。Vercel以外の環境ではEdge互換性の検証コストも考慮した上で採用範囲を判断する。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度がパフォーマンスの鍵:** 2026年時点では、RSCのstreaming効果を最大化するためにSuspense境界を適切に細分化することが標準的なベストプラクティスとなっており、ウォーターフォールを避けつつTTFBを最小化できる。

- **PPR（Partial Prerendering）との統合が主流に:** Next.js 15以降でPPRが安定化し、静的シェルを即座に配信しつつ動的コンテンツをstreamingで差し込むハイブリッド戦略が、RSC設計の基本パターンになっている。

- **Server ActionsとStreamingの組み合わせでUIの応答性が向上:** フォーム送信・ミューテーション後のUI更新をStreamingで段階的に反映できるようになり、楽観的UI更新との使い分けが設計上の重要な判断点となっている。

- **エラー境界とloading.tsxの設計が運用品質を左右する:** Streaming環境ではエラーが部分的に発生するため、`error.tsx`と`loading.tsx`の粒度設計が不十分だとUXが著しく劣化する。階層ごとのフォールバック設計をアーキテクチャレビューの必須項目とすべき。

- **キャッシュ戦略の複雑性増大に注意:** `fetch`のキャッシュ、`unstable_cache`、Route Cache等が混在するため、Streaming有効時のキャッシュ挙動を誤解すると古いデータが配信され続けるリスクがある。データフェッチ層のキャッシュ設計をチームで明文化することを推奨。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの成熟とフルスタック型安全性の標準化:** 2026年時点でtRPCはNext.js/Remixエコシステムで事実上の標準となりつつあり、TypeScriptプロジェクトではAPIスキーマ定義の重複を排除できるため、小〜中規模チームの生産性が劇的に向上している。

- **GraphQLの棲み分け明確化:** GraphQLは「複数クライアント・複数チームが同一データソースを消費するケース」に特化し、単一フロントエンド + 単一バックエンド構成では過剰設計になることが業界的に認識されてきた。

- **RESTはOpenAPI 3.1 + Zodで再評価:** スキーマファーストなREST（`zod-to-openapi`等）が型安全性とドキュメント自動生成を両立させており、外部API公開やサードパーティ連携が必要なプロダクトでは依然としてRESTが最適解。

- **エッジ・ストリーミング対応がAPI設計の新要件:** Vercel/Cloudflare Workersの普及により、APIはエッジでの実行とStreaming Response（Server-Sent Events / ReadableStream）を前提に設計する必要があり、従来のRESTの同期モデルでは対応しきれないケースが増加。

- **BFF（Backend for Frontend）パターンの復権:** マイクロサービス構成でGraphQLやgRPCを内部通信に使いつつ、クライアント向けにはtRPCまたはRESTのBFFを薄く挟む階層設計が、型安全性・パフォーマンス・チーム境界の観点から最も現実解として支持されている。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** 2026年はWebAssembly（Wasm）ベースのランタイムが成熟し、LLMの量子化モデルをエッジノードで直接実行するパターンが普及している。Cloudflare Workers AI・Fastly Compute@Edgeが主戦場。

- **コールドスタート問題の実質的解消:** V8 Isolateの進化とスナップショット技術により、コールドスタートは1ms以下が当たり前になった。従来のLambda型サーバーレスとの差別化ポイントが明確になっている。

- **エッジでのデータ永続化の台頭:** KV / SQLite at edge（Cloudflare D1、Turso embedded replicas）により「エッジは読み取り専用」という制約が崩れた。書き込み一貫性とレイテンシのトレードオフ設計が今の核心課題。

- **Durable Objects / Actor モデルの普及:** ステートフルなリアルタイム処理（WebSocket、ゲーム、共同編集）をエッジで実現するActorパターンが実用段階に入り、従来のWebSocketサーバー運用が不要になりつつある。

- **可観測性とデバッグの成熟:** 分散エッジ環境のトレーシング（OpenTelemetry対応）が整備され、「エッジはデバッグが難しい」という懸念が薄れてきた。ただしベンダーロックインリスクは依然高く、抽象化レイヤー（Hono、workers-sdk）の採用が実務上の必須判断になっている。

### 5. authentication security best practices 2026

- **パスキー（Passkey）の標準化加速:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の主流となり、フィッシング耐性と利便性を両立。Apple/Google/Microsoftのエコシステム統合により、実装コストが大幅に低下している。

- **セッション管理の短命化とローテーション:** アクセストークンの有効期限を15分以内に短縮し、リフレッシュトークンの自動ローテーションを必須とする設計が標準。トークン盗難時の被害範囲を最小化できる。

- **コンテキストアウェア認証（リスクベース認証）:** デバイスフィンガープリント・IPレピュテーション・行動パターンをリアルタイム分析し、リスクスコアに応じて追加認証をトリガーする。静的なMFAより適応的な防御が効果的。

- **サプライチェーンリスクとしての認証ライブラリ管理:** OAuth/OIDCライブラリへの依存は定期的なSBOM監査と自動脆弱性スキャン（Dependabot等）が必須。2025年に複数の認証ライブラリでサプライチェーン攻撃が確認されており、`lockfile`の完全性検証も重要。

- **AI駆動のクレデンシャルスタッフィング対策:** 従来のレートリミットでは突破されるケースが増加。機械学習ベースの異常ログイン検知とDevice Trustの組み合わせが、ボット攻撃への実効的な対策となっている。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge対応成熟:** Prisma ClientがEdge Runtimeで安定稼働し、Next.js App RouterのServer ComponentsやVercel Functionsと組み合わせた際のコールドスタート問題が大幅に改善。Connection Pooling（Prisma Accelerate）は本番必須の構成になりつつある。

- **Supabase pgvectorによるRAG統合の標準化:** ベクター検索とリレーショナルデータを同一DBで扱うパターンが定着し、AI機能追加のコストが激減。既存スキーマにembeddingカラムを追加するだけでセマンティック検索が実現できる。

- **Row Level Security（RLS）の設計負債リスク:** SupabaseのRLSは強力だが、ポリシーが複雑化するとクエリプランが劣化しやすい。早期から`EXPLAIN ANALYZE`でRLSポリシーのコストを計測し、インデックス戦略と合わせて設計することが重要。

- **Prisma MigrationsとSupabase Migrationsの二重管理問題:** `prisma migrate`と`supabase db push`を混在させると履歴が乖離する。どちらかをSingle Source of Truthに統一し、CIで`supabase db diff`による差分検出を自動化するのがベストプラクティス。

- **Multi-tenancy戦略の再評価:** Row-levelテナント分離（shared schema）からSchema-per-tenantへの移行コストが問題になるケースが増加。初期設計時にテナント規模・セキュリティ要件を見極め、Supabaseの`search_path`切り替えパターンかPrisma Middlewareでの動的スキーマルーティングを検討すべき。

### 7. WebAssembly Rust performance 2026

- **Component Model の本格普及:** WASI 0.2 と WebAssembly Component Model が2025年に安定化し、2026年はRustで書いたコンポーネントを言語をまたいで安全に合成できる実用フェーズに突入。Wasm同士の呼び出しオーバーヘッドが大幅に削減された。

- **Wasmtime・WASMEdgeの高速化:** JITとAOTコンパイルの改善により、Rust製Wasmのコールドスタートが数ミリ秒以下に。サーバーレス・エッジ環境でのRust+WasmがNode.jsを性能面で明確に上回るケースが増えている。

- **SIMD・スレッド対応の成熟:** WasmのSIMD命令セットとShared Memoryスレッドが主要ランタイム全体で安定稼働。RustのSIMD intrinsicsがそのままWasmに落ちるため、画像処理・ML推論の用途で特に恩恵が大きい。

- **Rust→Wasm ツールチェーンの開発体験向上:** `wasm-pack` + `cargo-component` の組み合わせで、ビルド〜バンドル〜デプロイまでのDXが大幅改善。型安全なバインディング自動生成により、JSとのFFIコストを意識する場面が減った。

- **メモリ管理の注意点は依然残る:** Rustの所有権モデルはWasm上でも安全だが、線形メモリの断片化とGCランタイムとの境界でのコピーコストは引き続き要計測。`wasm-opt` による最適化パスをCIに組み込むことが本番運用の前提になりつつある。

### 8. Next.js App Router patterns 2026

- **Server Componentsをデフォルトに:** App RouterではRSC（React Server Components）をデフォルトとし、`'use client'`は状態・イベントハンドラが必要な末端コンポーネントのみに限定することで、バンドルサイズを劇的に削減できる。

- **Partial Prerendering（PPR）の本番活用:** Next.js 15以降で安定化したPPRにより、静的シェルを即座に配信しつつ動的コンテンツをストリーミングする設計が標準パターンになりつつあり、`<Suspense>`境界の設計が性能の鍵を握る。

- **Server Actionsによるデータ変更の一元化:** フォーム送信やデータ更新を`action={serverAction}`で処理することでAPI routeを削減でき、型安全なend-to-endの変更フローが実現できる。ただしCSRF対策はNext.js組み込みの仕組みを信頼してよい。

- **`use cache` / キャッシュ戦略の明示化:** Next.js 15で導入された`use cache`ディレクティブにより、関数・コンポーネント単位でキャッシュ粒度を制御できる。`unstable_cache`からの移行とキャッシュ無効化戦略を早期に設計することが重要。

- **Parallel Routes / Intercepting Routesで複雑なUXを実現:** モーダル・ドロワー・タブUIをURLと同期させながら実装できるこのパターンは、本プロジェクトの物件詳細モーダルなどにも応用可能で、ディープリンク対応のUXを低コストで構築できる。

### 9. Vercel Edge Functions optimization 2026

- **Cold Start の実質ゼロ化:** Edge FunctionsはV8 Isolatesベースのため従来のLambdaと異なりコールドスタートがほぼ発生しない。2026年現在、Vercelはグローバル100+リージョン展開でP99レイテンシを一桁ms台に抑えており、APIルートをEdgeに移行するだけで体感速度が大きく改善される。

- **Streaming Responseの積極活用:** `ReadableStream` + `TransformStream` を使ったストリーミングレスポンスが標準的になり、LLM応答や大容量JSONの逐次配信が容易になった。Next.js App RouterのServer Componentsと組み合わせることで、TTFB（最初のバイト到達時間）を最小化できる。

- **Edge ConfigとKVによるステートレス設計の徹底:** Feature flags・A/Bテスト設定はEdge Configで、セッションや一時データはVercel KV（Redis互換）でEdge上に持つことで、オリジンサーバーへの往復を排除できる。リクエストごとのデータベースラウンドトリップが不要になるパターンが増えている。

- **Middleware最適化でRoute-level制御:** `middleware.ts`で認証・リダイレクト・ジオロケーション分岐をEdgeで完結させることが主流。ただしMiddlewareのバンドルサイズ上限（1MB）を超えるとデプロイ失敗になるため、外部ライブラリへの依存を最小化し`edge-light`対応モジュールのみ使用する設計が重要。

- **Web標準APIへの統一が加速:** Node.js固有API（`fs`、`net`等）はEdge Runtimeで使用不可。2026年では`fetch`・`Request`・`Response`・`crypto`（Web Crypto API）などのWeb標準に準拠したコードを書くことが、Vercel・Cloudflare Workers間の可搬性確保とパフォーマンス最大化の両面で業界標準となっている。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** プリミティブ型に意味的な区別を持たせる Branded Types（`type UserId = string & { readonly _brand: 'UserId' }`）が標準パターンとして定着し、実行時エラーをコンパイル時に検出できる設計が主流になっている。

- **`satisfies` 演算子の活用:** TypeScript 4.9 以降の `satisfies` が 2026 年には広く使われており、型推論を保ちながら型チェックを行えるため、`as` キャストによる型安全性の損失を回避できる。

- **Zod + tRPC による境界型保証:** APIの入出力にZodスキーマを定義し、tRPCでエンドツーエンドの型安全性を確保するパターンが事実上の標準となり、ランタイムとコンパイル時の型を一元管理できる。

- **Template Literal Types による文字列制約:** `type EventName = \`on${Capitalize<string>}\`` のような Template Literal Types が設定キーやイベント名の誤り検出に活用され、マジックストリングを型レベルで排除できる。

- **`noUncheckedIndexedAccess` の有効化:** `tsconfig.json` の厳格オプションとして本オプションを ON にすることで、配列・オブジェクトへのインデックスアクセス時に `undefined` の考慮が必須となり、実行時クラッシュを大幅に削減できる。
