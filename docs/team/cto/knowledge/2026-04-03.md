# CTO Knowledge - 2026-04-03

## Daily Update (2026-04-03)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチとロジックをサーバーコンポーネントに集約する。`'use client'` は本当にインタラクティビティが必要な末端コンポーネントのみに限定するのが鉄則。

- **Partial Prerendering (PPR) による静的・動的の最適融合:** Next.js 15以降で安定したPPRを活用し、ページのシェルを静的に配信しつつ動的コンテンツをストリーミングする。TTFBを損なわずにパーソナライズが実現できる。

- **`next/image` と `next/font` の適切な設定:** LCPの最大要因は未最適化の画像とフォント。`priority` 属性の付与、`sizes` の正確な指定、セルフホスティングフォントによるCLS排除が依然として高コスパな改善策。

- **キャッシュ戦略の明示的な設計:** Next.js 15でデフォルトキャッシュが変更されたため、`fetch` の `cache` / `revalidate` オプションを明示的に設定しないと意図しない挙動が生じる。キャッシュの境界をアーキテクチャ設計時に明文化しておくことが重要。

- **バンドル分析とTree Shakingの定期監査:** `@next/bundle-analyzer` を CI に組み込み、依存関係の肥大化を早期検知する。特にサードパーティSDKは名前付きインポートを徹底し、barrel exportsによる意図しない大量インポートを防ぐ。

### 2. React Server Components streaming 2026

- **Suspense境界の戦略的配置が鍵:** RSCストリーミングはSuspenseの粒度設計で体感速度が大きく変わる。クリティカルパス外のコンポーネント（レコメンド、コメント等）を個別にSuspenseで囲むことでTTFBを最小化できる。

- **PPR（Partial Prerendering）との組み合わせが主流に:** Next.js 15以降でPPRが安定化し、静的シェルを即座に返しつつ動的部分をストリームする設計パターンが標準化。ビルド時に静的/動的境界を意識した設計が必須になっている。

- **Server Actionsとの連携でウォーターフォール排除:** データフェッチをServer Component側に集約し、クライアントへのラウンドトリップを削減する設計が成熟。`use cache`ディレクティブと組み合わせることでキャッシュ戦略も同一ファイルに記述できる。

- **エラーバウンダリの粒度管理が品質の分岐点:** ストリーミング中にエラーが発生した場合、`error.tsx`の配置が粗いとページ全体がクラッシュする。機能単位でエラーバウンダリを分離し、部分的な失敗をグレースフルに処理する設計が求められる。

- **Core Web Vitals視点ではLCPとINPのトレードオフに注意:** ストリーミングはFCPを改善する一方、LCP対象要素が遅延ストリームに含まれると逆効果になるケースがある。LCPヒーロー要素は優先ストリームか静的シェルに含める設計レビューを徹底すること。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの実用的優位性:** TypeScript フルスタック環境では tRPC が事実上の標準になりつつあり、スキーマ定義なしでクライアント・サーバー間の型安全を実現できるため、Next.js + Bun 構成との相性が抜群。

- **GraphQL は「必要な複雑さ」にだけ使う:** データグラフが複雑なマルチチーム環境やモバイル最適化が必要な場面では依然強力だが、小〜中規模では over-engineering になりやすい。Federation v2 の成熟でマイクロサービス間の統合には有効。

- **REST は死んでいない、むしろ洗練された:** OpenAPI 3.1 + Zod による自動型生成、HTTP/3 対応、Problem Details (RFC 9457) によるエラー標準化など、REST のエコシステムが成熟し「シンプルで正しい REST」の価値が再評価されている。

- **エッジ対応が設計制約になった:** Cloudflare Workers / Vercel Edge Runtime での動作を前提とすると、重いランタイム依存（Apollo Server 等）が選択肢から外れる。tRPC や軽量 REST が有利で、コールドスタートと Cold DB connection の問題がアーキテクチャ決定に直結。

- **AI エージェント統合を見据えた API 設計:** MCP（Model Context Protocol）や tool-calling との統合を考えると、セマンティックな操作名・冪等性・structured output の返却が重要になる。REST の動詞設計や tRPC のプロシージャ命名がエージェントの「理解しやすさ」に影響する。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** 2026年時点でVercel、Cloudflare Workers AI、Fastly Compute等がエッジでのLLM推論を本番対応レベルで提供。レイテンシ sensitive なアプリではサーバーレスエッジがAI処理の第一選択肢になりつつある。

- **WebAssembly（WASM）がランタイムの主流に:** Node.jsサンドボックスから脱却し、WASMベースのランタイム（Cloudflare Workers、Fastly）が隔離性・起動速度の両立を実現。ポータビリティも高く、マルチクラウドエッジ戦略に適している。

- **エッジDBの成熟:** Cloudflare D1、Turso（libSQL）、PlanetScale等のエッジ対応データベースが普及し、「エッジでread-heavy処理＋グローバルレプリケーション」のパターンが現実的な選択肢になった。ただしwrite整合性の設計は依然要注意。

- **Cold Startはほぼ解決済み、次の課題はオブザーバビリティ:** V8 Isolateベースの実行環境でコールドスタートは数ms以下に。一方、分散エッジ環境での分散トレーシングやログ集約が運用上のボトルネックになっており、OpenTelemetryのエッジ対応が急務。

- **コスト構造の再評価が必要:** リクエスト単価は安いが、エッジ拠点数×実行回数でコストが想定外にスケールするケースあり。特にグローバルトラフィックが多いサービスでは、どの処理をエッジに置くかの設計判断がTCOに直結する。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）への移行加速:** パスワードレス認証がデファクトスタンダードになりつつあり、フィッシング耐性の高いパスキーを優先採用することで、クレデンシャルスタッフィング攻撃のリスクをほぼゼロにできる。

- **トークンバインディングとDPoP（Demonstrating Proof of Possession）の実装:** Bearer tokenの盗用リスクに対し、DPoPを用いてアクセストークンをクライアントの秘密鍵に紐付けることで、トークン窃取後の不正利用を防ぐ。

- **継続的認証（Continuous Authentication）の採用:** セッション確立時の一度きりの認証から、行動分析・デバイスフィンガープリント・リスクスコアリングによるリアルタイム監視へ移行し、セッションハイジャックを早期検知する。

- **サプライチェーン攻撃対策としての依存ライブラリ監査:** 認証ライブラリ（OAuth/OIDCクライアント、JWTライブラリ等）はSBOMで管理し、CVE自動検知とピン留めバージョン管理を組み合わせて脆弱なバージョンの混入を防ぐ。

- **AIを悪用したソーシャルエンジニアリングへの対策強化:** ディープフェイク音声・映像を使ったSIM swap詐欺やMFAバイパス攻撃が増加しており、アウトオブバンドの物理キーや管理者向け特権アクセスにはハードウェアセキュリティキー（YubiKey等）を必須化する。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応成熟:** Prisma 6ではEdge RuntimeとPrisma Accelerate（コネクションプーリング）の統合が安定し、Supabase + Next.js App RouterのServer Componentsとの組み合わせでサーバーレス環境でのコールドスタート問題が実用レベルで解消された。

- **Supabase Realtime + Row Level Security (RLS)の設計が核心:** 2026時点でRLSをORMレイヤーではなくDB側で強制する設計パターンが主流となり、Prismaのクエリをservice_roleではなくanon/authenticated roleで実行するアーキテクチャがセキュリティベストプラクティスとして定着している。

- **PgVector + Supabaseによるベクトル検索の内製化:** 外部ベクトルDB（Pinecone等）を使わずSupabase内のpgvectorで類似検索を完結させるアーキテクチャが普及し、Prismaの`$queryRaw`でベクトル演算を扱うパターンがRAGシステム構築の標準になりつつある。

- **Supabase Branchingによる開発フロー革新:** DB schemaのブランチ機能が実用化され、PRごとにDB環境を分離できるようになった結果、Prisma MigrationsとSupabase Branchingの組み合わせがCI/CDパイプラインの標準構成として確立されている。

- **型安全性の完全保証:** Prisma Clientの型生成とSupabaseの`supabase gen types typescript`を組み合わせることで、DB〜APIレイヤー間の型安全性をゼロコストで担保できるが、2つの型定義が乖離するリスクがあるため、どちらか一方に統一するか自動同期のCI stepを設けることが重要。

### 7. WebAssembly Rust performance 2026

- **Component Model の成熟:** WebAssembly Component Model (WASM 2.0) が2026年に広く採用され、RustコンポーネントをJavaScript/Pythonと型安全に連携できる。ホスト間の相互運用性が大幅に向上し、マイクロサービス的なWASM活用が現実的になった。

- **SIMD・スレッド対応の普及:** `wasm-simd128` と SharedArrayBuffer ベースのスレッドがほぼ全ブラウザ・Wasmtimeで安定化。Rustの `rayon` や `std::simd` をターゲット向けに活かせるようになり、数値計算・画像処理で3〜10倍の性能向上が得られるケースも。

- **WASIp2（Preview 2）による本格的サーバーサイド利用:** WASIp2のSocket/HTTP対応により、RustのWASMバイナリをエッジランタイム（Fastly、Cloudflare Workers）で直接実行可能。コールドスタートがネイティブに近く、Node.js比で起動時間を大幅削減できる。

- **ビルドサイズとLTO最適化:** `wasm-opt` + LTO + `panic=abort` の組み合わせが標準レシピとして定着。`cargo-component` ツールチェーンがこれを自動化しており、10MB超のバイナリを1MB台に抑えることが実運用レベルで達成されている。

- **デバッグ・プロファイリングの改善:** DWARF over WASMのサポートが充実し、Chrome DevToolsやWasmtime CLIでRustのソースレベルデバッグが可能に。本番障害のトレースが現実的になり、「WASMはデバッグしにくい」という従来の懸念が解消されつつある。

### 8. Next.js App Router patterns 2026

- **Server Componentsをデフォルトに:** 2026年時点でApp Routerの成熟により、データフェッチはServer Components内で直接行うのが標準パターン。`use client`は状態・イベント処理が必要な末端コンポーネントのみに限定し、バンドルサイズを最小化する。

- **Partial Prerendering (PPR) の実用化:** 静的シェルと動的コンテンツを同一ページで混在させるPPRが安定版に到達。`<Suspense>`境界の設計がパフォーマンス戦略の中心となり、TTFB改善と動的性を両立できる。

- **Server Actions によるAPI層の簡素化:** フォーム処理・ミューテーションをServer Actionsに集約することでREST APIエンドポイントの実装が不要なケースが増加。ただし複雑な認可ロジックはミドルウェアまたは専用サービス層に分離すること。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15以降で安定した`use cache`により、関数・コンポーネント単位でのキャッシュ戦略が可能に。`revalidateTag`との組み合わせでISRより柔軟なキャッシュ無効化が実現できる。

- **Parallel Routes + Intercepting Routes の活用:** モーダル・スライドオーバーなどのUIパターンをURL駆動で実装できるため、シェアリング・ブックマーク対応が容易。複雑なレイアウト構成では`@slot`の乱用に注意し、ファイル構造を早期に設計すること。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択的活用:** Edge Functionsはコールドスタートがほぼゼロだが、Node.js APIの制約が大きい。2026年時点では「全部Edge化」より、認証・地理的ルーティング・A/Bテストに絞った選択的配置がベストプラクティスとなっている。

- **Fluid computeによるハイブリッド実行:** VercelのFluid compute（2025年GA）により、Edge↔Serverlessの境界が曖昧になった。リクエストパターンに応じて動的にリソースを割り当てるため、従来のEdge/Serverless二択から解放され、コスト効率が大幅に改善。

- **KVストアとの組み合わせが前提:** Edge FunctionsはステートレスなためVercel KV（Redis）やD1との併用が実質必須。レイテンシを活かすには、データストアもエッジリージョンに近接配置し、グローバルレプリケーション戦略を設計段階から考慮する必要がある。

- **バンドルサイズの厳格管理:** Edge RuntimeはWasm制約（1MB上限）が依然として厳しい。`next/server`のミドルウェアに重いライブラリを混入させないよう、`bundleAnalyzer`と`@next/bundle-analyzer`による定期的なサイズ監査をCIに組み込むべき。

- **Observabilityの整備が急務:** Edgeの分散実行はデバッグが難しく、2026年現在もログの欠落・トレース断絶が現場課題として残る。Vercel Log Drains＋OpenTelemetryの組み合わせで、エッジ実行のトレースをDatadogやGrafanaに集約する構成が主流になりつつある。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の積極活用:** 型推論を保持しつつ型チェックを行える `satisfies` は、オブジェクトリテラルの過剰な型アノテーションを排除し、コードの簡潔性と安全性を両立させる標準パターンになっている。

- **Template Literal Types によるAPI契約の静的保証:** エンドポイントパス・イベント名・CSSクラス名などを `\`/api/${string}\`` 形式で型付けすることで、ランタイムエラーをコンパイル時に検出できる。特にRPCレイヤーやイベントバスの型安全化に効果的。

- **Branded Types でドメイン境界を強化:** `UserId` と `PropertyId` を同じ `string` として扱う誤りをコンパイル時に防ぐ。`type UserId = string & { readonly _brand: 'UserId' }` パターンがZodのパースポイントと組み合わせて主流になっている。

- **`const` type parameters（TypeScript 5.x）で推論精度を向上:** ジェネリック関数に `const T` を付与することで、引数をリテラル型として推論させ、`as const` の記述を省略できる。ビルダーパターンやクエリビルダーの型精度が大幅に向上する。

- **Zod + tRPC によるスキーマファーストの型共有:** バックエンドのZodスキーマをフロントエンドと共有し、`infer` で型を導出するアーキテクチャが定着。「型は一箇所で定義し、残りは推論させる」がチーム開発の原則になっている。
