# CTO Knowledge - 2026-03-23

## Daily Update (2026-03-23)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチロジックはサーバーコンポーネントに集約し、`"use client"` 境界を末端の葉コンポーネントまで押し下げることが基本戦略。

- **Partial Prerendering (PPR) の本番投入:** 静的シェルを即時配信しつつ動的コンテンツをストリーミングするPPRが安定化。`experimental.ppr` を有効化することでTTFBとLCPを同時改善できる。

- **`next/image` と `next/font` の最適化徹底:** `sizes` 属性の適切な設定とAVIF優先配信、フォントの `display: swap` + サブセット化は手間が少ない割にCWV（Core Web Vitals）スコアへの効果が大きい。

- **Turbopackへの移行完了:** Next.js 15以降でTurbopackがデフォルト化。開発ビルドの高速化だけでなく、本番バンドルのツリーシェイキング精度向上によりランタイムパフォーマンスにも寄与。

- **キャッシュ戦略の再設計:** Next.js 15でデフォルトキャッシュ動作が変更（`fetch` がキャッシュしない方向へ）。`revalidate` / `unstable_cache` / `use cache` ディレクティブを意図的に設計し、過剰フェッチと陳腐化データの両方を防ぐアーキテクチャが必須。

### 2. React Server Components streaming 2026

- **Suspense境界の戦略的配置が鍵:** RSCのストリーミングはSuspenseで細粒度に制御できるが、境界が多すぎると逆にウォーターフォールを生む。クリティカルパス上のコンポーネントを優先的にストリームし、非クリティカルなものは遅延させる設計が重要。

- **PPR（Partial Prerendering）との統合が主流化:** Next.js 15以降、PPRによりスタティックシェルを即座に返しつつ動的部分をストリームする戦略が現実的になった。2026年時点でPPRはstableとなり、ISRの後継として標準パターンになりつつある。

- **Server ActionsとStreamingの組み合わせでUXが向上:** フォーム送信後のレスポンスをストリーミングで段階的に返す設計が増加。`useActionState`と`Suspense`の組み合わせで、ローディング状態管理のボイラープレートが大幅に削減できる。

- **Edgeランタイムの制約を意識した設計が必須:** CloudflareやVercel Edgeでのストリーミングは強力だが、実行時間制限やNode.js APIの非互換が依然として課題。`runtime: 'edge'`採用時は依存ライブラリのEdge対応を事前に確認する運用フローを組み込むべき。

- **バンドルサイズとTime-to-First-Byteのトレードオフ管理:** RSCはクライアントJSを削減できるが、サーバー側のコールドスタートが遅いとTTFBが悪化する。2026年ではReact Compiler（旧React Forget）の本格普及により、クライアントコンポーネントの最適化コストが下がり、Server/Clientの境界判断がより柔軟になっている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全API:** TypeScriptフルスタック環境ではtRPCが主流化しつつあり、スキーマ定義不要でエンドツーエンドの型安全性を実現。Next.js + tRPCの組み合わせはBFFパターンの事実上の標準になりつつある。

- **GraphQLの選択基準の明確化:** GraphQLは「複数クライアント向けの柔軟なデータフェッチ」が必要な場面に限定される傾向。内部API・単一クライアント構成ではオーバーエンジニアリングになりがちで、tRPCやREST+OpenAPIへの回帰が見られる。

- **REST + OpenAPI 3.1の再評価:** Scalar・Hono・Zod OpenAPIなどのツールチェーンの充実により、RESTでも型安全なコード生成が実用的に。シンプルさと相互運用性の観点から公開APIはREST一択の流れが続く。

- **Server-Sent Events / WebSocketのAPI設計統合:** リアルタイム要件の増加に伴い、REST/tRPCとSSE・WebSocketを組み合わせたハイブリッド設計が標準化。Next.js App RouterのServer Actionsもこの流れを加速している。

- **エッジ対応とレイテンシ最適化:** Cloudflare Workers・Vercel Edgeでの動作を前提としたAPI設計が必須に。Cold startを避けるためRPCスタイルの軽量エンドポイント設計が重視され、tRPCやHonoがエッジ環境での採用を伸ばしている。

### 4. serverless edge computing 2026

- **エッジでのAI推論が標準化:** Cloudflare Workers AI、Vercel Edge Functions等でLLM推論がエッジ実行可能になり、レイテンシ50ms以下のAIレスポンスが現実的に。モデルの量子化・蒸留技術の成熟がこれを後押ししている。

- **WebAssembly（WASM）がランタイムの主流に:** Node.js依存からWASMベースのポータブルランタイムへの移行が加速。言語非依存でコールドスタートがほぼゼロになり、Go/Rust製エッジ関数の採用が増加している。

- **エッジDBとの統合が成熟:** Cloudflare D1、Turso等のエッジネイティブDBが本番利用に耐える水準に達し、「エッジで完結するフルスタック」が現実的な選択肢になった。ただしグローバル一貫性のトレードオフは依然として設計上の課題。

- **コスト最適化の再評価が必要:** 低トラフィック時は従来のサーバーレスより安価だが、高頻度・長時間処理ではエッジの課金モデルが割高になるケースも。ワークロード特性に応じた使い分けの判断基準を持つことが重要。

- **オブザーバビリティがボトルネック:** エッジ分散環境でのトレーシング・ログ集約はまだ発展途上。OpenTelemetryのエッジ対応が進んでいるが、分散トレースの完全なサポートには引き続き注意が必要。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準採用:** FIDO2/WebAuthn ベースのパスキーがパスワードレス認証の主流となり、フィッシング耐性とUX両立の観点から2026年は実装必須レベルに到達している。

- **セッション管理の短命化とローテーション:** JWTの有効期限を15分以内に抑え、Refresh Tokenを`httpOnly` Cookieで管理するパターンが定着。トークン盗難時の被害範囲を最小化する設計が前提となった。

- **デバイスフィンガープリントと行動バイオメトリクスの併用:** 静的なMFAだけでなく、ログイン後の行動パターン異常検知（typing rhythm、マウス動作）を組み合わせたリスクベース認証が実用フェーズに入っている。

- **OAuth 2.1 + DPoP の採用推進:** Bearer TokenからDPoP（Demonstrating Proof-of-Possession）への移行により、トークン傍受・リプレイ攻撃のリスクが大幅低減。新規実装ではOAuth 2.1を基準とする。

- **サプライチェーン攻撃対策としての依存ライブラリ監査:** 認証ライブラリ（NextAuth.js、Lucia等）への悪意ある依存注入事例が増加しており、`bun audit`やSBOM管理をCI必須ステップとして組み込むことがベストプラクティスになっている。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6 + Supabase の統合成熟:** Prisma v6でEdge Runtime対応が強化され、Supabase Edge FunctionsとPrisma Accelerateの組み合わせがグローバル分散アーキテクチャの標準パターンになりつつある。コネクションプーリングをPrisma Accelerate側に委譲することでサーバーレス環境でのコールドスタート問題が大幅に改善された。

- **Row Level Security (RLS) との責務分離が重要:** SupabaseのRLSポリシーとPrismaのクエリ層を混在させると認証バイパスリスクが生じる。アプリ層（Prisma）でビジネスロジック、DB層（RLS）でデータアクセス制御と明確に分離し、両方を二重防衛として設計するのがベストプラクティス。

- **Supabase Realtime + ダイレクトクエリの使い分け:** リアルタイム機能（チャット・通知）はSupabase Realtimeチャンネルを活用し、複雑なビジネスクエリはPrismaで処理する二層構造が効率的。全てをPrisma経由にするとWebSocket連携でオーバーヘッドが増える。

- **pgvectorによるベクトル検索の内製化:** 2026年時点で、外部ベクトルDBを別途持つより `pgvector` をSupabase上で運用する方がコスト・運用負荷ともに優位。Prismaからは生SQL（`$queryRaw`）でベクトル検索を呼び出す実装パターンが定着している。

- **マイグレーション管理の複雑性に注意:** Supabaseの組み込みマイグレーション（`supabase db push`）とPrisma Migrateが競合しやすい。本番環境では「Prismaをスキーマの唯一の真実」として扱い、Supabase CLIはローカル開発・シード専用に限定する運用が安全。

### 7. WebAssembly Rust performance 2026

- **ポイント1: WASM GC とメモリ管理の成熟:** 2026年時点でWASM GCプロポーザルが主要ブラウザに安定実装済みとなり、Rustの所有権モデルとの統合でGCオーバーヘッドなしに高性能なメモリ管理が実現できるようになった。

- **ポイント2: SIMD・スレッド対応の実用化:** WASM SIMDとShared Memoryが全主要ランタイムで標準サポートされ、Rustの`rayon`や`packed_simd`との組み合わせでネイティブに近いマルチコア並列処理が可能になっている。

- **ポイント3: コンポーネントモデルによる相互運用性の向上:** WASM Component Modelの普及により、Rustで書いたWASMモジュールをJS/Python/GoなどのホストからIDL（WIT）経由で型安全に呼び出せるようになり、マイクロサービス的なWASMアーキテクチャが現実的な選択肢になった。

- **ポイント4: エッジ・サーバーサイドでの主戦場化:** Cloudflare Workers・Fastly Compute・WASMtimeベースの実行環境が成熟し、Rustで書いたコードをエッジで低レイテンシ実行するパターンがプロダクション標準になりつつある。コールドスタートはNode.jsの1/10以下。

- **ポイント5: バイナリサイズとビルド時間がボトルネック:** パフォーマンスは優秀だが、依存クレートが増えるとWASMバイナリが数MB超になりやすい。`wasm-opt`（Binaryen）・`wasm-pack`のLTO設定・`cargo-component`の活用が実務上の必須知識となっている。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点でApp Routerの設計原則は「Clientは最小限」。データフェッチ・ビジネスロジックはServer Componentに集約し、インタラクションが必要な箇所のみ`'use client'`を宣言することでバンドルサイズを大幅削減できる。

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降で安定化したPPRにより、静的シェル＋動的ストリーミングを1ページ内で混在させることが可能。`<Suspense>`境界の設計がアーキテクチャの核心になっている。

- **Server Actions によるAPI層の簡略化:** フォーム送信・ミューテーション処理をServer Actionsに集約することで、従来の`/api`ルート乱立を防げる。ただしバリデーション（Zod）とエラーハンドリングをAction内で徹底することが前提。

- **`use cache` ディレクティブによるきめ細かいキャッシュ制御:** Next.js 15で導入された`use cache`により、関数・コンポーネント単位でキャッシュのライフタイムを宣言的に制御できる。`revalidate`の設計をページ単位から関数単位に落とし込むことがパフォーマンスチューニングの鍵。

- **Parallel Routes / Intercepting Routes の設計複雑性に注意:** モーダルやダッシュボードレイアウトに強力だが、`@slot`構造の深いネストはデバッグが難しくなる。チームで共通のルーティング規約を文書化しておかないと、後から読めないコードになりやすい。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択戦略:** 2026年時点でVercel Edge Functionsは`nodejs`ランタイムとの使い分けが重要で、レイテンシ重視のルーティング・認証・A/Bテストにはエッジを、DBアクセスやヘビーな処理はNode.jsランタイムに留めるのがベストプラクティス。

- **Regional Edge Cachingの活用:** `cache: 'force-cache'`とISR（Incremental Static Regeneration）をエッジと組み合わせることでキャッシュヒット率を最大化し、オリジンへのフォールバックを最小限に抑えられる。特に`stale-while-revalidate`パターンが効果的。

- **Cold Startの実質ゼロ化:** Edge FunctionsはV8 Isolateベースのため従来のLambdaと異なりコールドスタートがほぼ存在しない。ただしバンドルサイズが1MBを超えると初期化コストが増すため、`import`の最小化とtree-shakingが依然として重要。

- **Middleware最適化:** Next.js App RouterのMiddlewareはすべてエッジで実行されるため、ここに重いロジックを置くとグローバル全リクエストに影響する。認証チェックはJWT検証のみに絞り、DBクエリは絶対に含めないこと。

- **観測性の強化:** Vercel 2026のダッシュボードではEdge Function単位のp99レイテンシ・エラーレート・リージョン分布が確認可能。`waitUntil()`を使った非同期ログ送信（Datadog/Axiom連携）でレスポンスを遅延させずに計測するパターンが標準化されてきている。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の`satisfies`は、型推論の精度を保ちながら型チェックを強制できる。`as`キャストの代替として、ランタイム安全性を損なわずに型安全を実現する場面で標準化が進んでいる。

- **Template Literal Types + infer の組み合わせ:** APIエンドポイントのパスパラメータ抽出やイベント名マッピングなど、文字列ベースのドメインモデリングに活用される。`ParseRouteParams<'/users/:id/posts/:postId'>`のような型レベルパーサーがライブラリ不要で書ける。

- **Branded Types（名義的型付け）の普及:** `type UserId = string & { readonly __brand: 'UserId' }`パターンで、同じプリミティブ型の混同バグを型レベルで防ぐ。特に決済・認証系のIDハンドリングでのアダプトが増加している。

- **`noUncheckedIndexedAccess` + Strict Mode フル活用:** 配列・オブジェクトインデックスアクセスを`T | undefined`として扱う`noUncheckedIndexedAccess`フラグが、バグの多い実装パターンを抑制。2026年時点では新規プロジェクトの標準設定として定着しつつある。

- **型レベルテスト（`tsd`, `expect-type`）の CI 組み込み:** 実装コードのテストに加え、型定義自体が壊れていないか検証する型テストをCIパイプラインに含めることが増えている。ライブラリ開発だけでなく、社内共有型定義の品質保証にも有効。
