# CTO Knowledge - 2026-11-18

## Daily Update (2026-11-18)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 16ではPPRが安定版として扱われ、静的シェルを即時配信しつつ動的部分だけをストリーミングできるため、`loading.tsx`やSuspense境界の設計次第でTTFBとLCPを大きく改善できる。本プロジェクトの`properties/`や`listing/`ページでも、物件一覧の骨組みは静的化し、価格や在庫などの動的データのみストリーミングする構成が有効。

- **Turbopackのビルド・devサーバー最適化:** Turbopackが本番ビルドでも既定化されつつあり、`bun run build`の時間短縮とHMRの高速化が期待できる。大規模な`src/components/`配下でのビルド時間がCIのボトルネックになっている場合、Turbopack移行の効果測定を優先すべき。

- **Server ActionsとCache Componentsの粒度設計:** `use cache`ディレクティブによる関数レベルのキャッシュ制御が主流になり、データ取得（`src/lib/data.ts`相当）をコンポーネント単位で細かくキャッシュ/再検証できる。過剰なrevalidateや`no-store`の濫用がパフォーマンス劣化の典型パターンなので、実際のデータ更新頻度に合わせた`revalidateTag`戦略が重要。

- **画像・フォント最適化の自動化強化:** `next/image`のAVIF優先配信やレスポンシブ画像の自動生成がさらに高度化しており、物件写真が多い本サービスのようなサイトではLCPスコアへの影響が大きい。CDN側のエッジキャッシュと組み合わせることで、画像起因のパフォーマンス問題はほぼ自動で解消できる段階に来ている。

- **Reactコンパイラとバンドル最適化:** React Compilerの統合により不要な再レンダリングが自動排除され、手動の`memo`/`useMemo`チューニングの必要性が減っている。ただし既存コードに手動最適化が残っている場合は競合・冗長化するため、移行時は段階的に手動メモ化を削除して計測し直すのが安全。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16ではPPRが標準的な選択肢となり、静的シェルを即時配信しつつ動的部分だけをStreamingで後から流し込めるため、TTFBとLCPを同時に改善できる。弊社の`src/app/properties/`のような一覧ページは、検索フィルタ部分だけをSuspense境界で分離し、残りを静的にキャッシュする構成が効果的。

- **`use cache` ディレクティブとキャッシュコンポーネント化:** React/Next.jsのキャッシュAPIが成熟し、コンポーネント単位で明示的にキャッシュ境界を宣言できるようになった。物件詳細ページのような読み取り頻度が高いデータは、関数レベルでキャッシュを宣言するだけでCDNエッジキャッシュと連携しやすくなる。

- **Server Actionsとストリーミングの統合:** フォーム送信（引越し費用の見積もりなど）でServer ActionsをRSCストリーミングと組み合わせることで、クライアントJSを増やさずに楽観的UI更新ができる。`useOptimistic`との組み合わせが実質的な標準パターンになっている。

- **Suspense境界の粒度設計がパフォーマンスの肝:** 境界を粗く取ると「全部待たされる」、細かく取りすぎるとウォーターフォールでリクエスト数が爆発する。物件一覧→詳細のようなネストしたデータ取得では、親でまとめてfetchして子に渡す「fetch once, pass down」パターンが推奨される。

- **React Compilerによる自動メモ化がRSC境界設計を軽くする:** クライアントコンポーネント側で手動`memo`/`useMemo`が不要になりつつあるため、RSC/クライアント境界の切り方を「パフォーマンス都合」より「データ依存関係」で決めやすくなっている。本プロジェクトのようにインタラクティブなフィルタUIが多い場合、境界設計のシンプル化に直結する。

### 3. API design REST GraphQL tRPC 2026

- **GraphQLの再評価と使い分け:** 2026年はtRPCの台頭でGraphQLの採用は減速傾向。社内向けフルスタックTypeScriptならtRPCの型安全性が圧倒的に有利だが、モバイル・サードパーティ公開APIではGraphQLのスキーマファーストな柔軟性が依然優位。

- **tRPCはモノレポ・フルスタックTSに最適:** sumitsugiのようなNext.js App Router構成では、tRPC（またはServer Actions直呼び）によりAPI層とフロント型をシングルソース化でき、OpenAPI/GraphQLスキーマ生成の往復コストを削減できる。

- **RESTは依然「境界」としての標準:** 外部連携・Webhook・サードパーティ統合ではREST+OpenAPIが鉄板。内部はtRPC、外部公開APIはREST(+Zodバリデーション)とハイブリッド構成にするのが2026年の実用解。

- **Server ActionsがAPI層そのものを吸収:** Next.js 16世代ではServer Actionsが単純なCRUDのtRPC/REST呼び出しを代替し始めており、「APIレイヤーを書かない」選択肢が増加。ただし複雑なクライアント状態管理・キャッシュ無効化が必要な場合はtRPC+TanStack Queryが依然有利。

- **型安全性とランタイム検証の両立が必須:** TypeScriptの型だけでは外部入力を守れないため、Zodなどによる境界検証（`.claude/rules/standards.md`のInput validation方針と同様）はAPI設計方式を問わず必須。tRPC/Server ActionsでもZodスキーマを共有し、型定義とランタイム検証を一元化するのが現在のベストプラクティス。

### 4. serverless edge computing 2026

- **エッジでのAI推論標準化:** 2026年はLLM推論自体をCDNエッジ（Cloudflare Workers AI、Vercel Edge Functions等）で実行するのが一般化し、ユーザー近接性によるレイテンシ削減とコールドスタート問題の解消が両立できるようになっている。sumitsugiのような日本向けサービスでも、画像最適化や物件検索のパーソナライズ処理をエッジ側に寄せることでTTFBを大幅改善できる。

- **WASM主導のランタイム統合:** V8 isolateベースのエッジランタイムに加え、WebAssembly（特にWASI Preview 2）がNode.js非互換の重い処理（画像変換、PDF生成）をエッジで動かす主流手段になっており、コールドスタートがミリ秒単位に収まる。

- **データレイヤーのエッジ移行:** D1/Turso/PlanetScale等のSQLiteベース分散DBがエッジと同一リージョンで読み書きできるようになり、「エッジ実行だがDBだけ中央集権」というレイテンシボトルネックが解消されつつある。物件データのような読み取り多めのワークロードには特に相性が良い。

- **Next.js 16とエッジランタイムの境界明確化:** App RouterのPPR（Partial Prerendering）とエッジランタイムの組み合わせが成熟し、静的シェルをエッジで即時配信しつつ動的部分（在庫状況・価格）だけNode.jsランタイムにフォールバックする設計が定石化している。全部をエッジに寄せようとするとDB接続やNode API依存で逆に複雑化するため、適材適所の判断が重要。

- **コスト構造の変化によるベンダーロックイン警戒:** リクエスト課金からCPU時間課金への移行（Cloudflare/Deno Deploy系）が進み、計算量の多い処理（PDF生成、画像処理等）をエッジに置くと従来より高コストになるケースが出てきている。移行前にワークロードのプロファイリングと複数ベンダーでのコスト比較が必須。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証（WebAuthn/Passkeys）が標準となり、フィッシング耐性のある生体認証・デバイス認証をデフォルトにすることで、資格情報盗用リスクを根本的に排除できます。sumitsugiでも次フェーズのログイン改善ではパスキー対応を優先候補にすべきです。

- **ゼロトラスト前提のセッション管理:** 「ログイン＝信頼」ではなく、デバイス・IP・行動パターンを継続的に検証するリスクベース認証が主流に。JWT/セッショントークンは短命化し、リフレッシュトークンのローテーション＋バインディング（デバイス紐付け）が必須になっています。

- **多要素認証（MFA）の強制とSMS依存の脱却:** SMS OTPはSIMスワップ攻撃に弱いため、TOTPアプリやプッシュ通知ベースのMFAへの移行が推奨されます。本物件のような実住所・決済情報を扱うプラットフォームでは、特に「前の住人」↔「次の住人」間の引き継ぎ承認フローにMFAを組み込むべきです。

- **BFF（Backend for Frontend）パターンでのトークン保護:** アクセストークンをブラウザのJSに露出させず、サーバーサイドでトークン管理するBFFアーキテクチャがXSS対策のベストプラクティスとして定着しています。Next.js App RouterのServer Actions/Route Handlersと組み合わせることでsumitsugiにも適用しやすい構成です。

- **認証基盤のサプライチェーン監査:** Auth0やSupabase AuthなどのSaaS認証プロバイダを使う場合も、自社でZodによる入力検証・CSRF対策・レート制限を重ねる「多層防御」が必須という点は変わっていません。`src/contexts/auth-context.tsx`のような認証コンテキストは、外部ライブラリ更新時に定期的なセキュリティレビュー対象にすべきです。

### 6. database architecture Prisma Supabase 2026

- **Edge-nativeなコネクション管理:** Supabaseの PgBouncer 統合と Prisma の Accelerate/Data Proxy を組み合わせることで、サーバーレス環境でのコネクションプール枯渇問題を回避できる。Vercel等のEdge Functionsからの接続はプール必須。

- **RLS(Row Level Security)とORMの共存:** SupabaseのRLSはDB層で認可を担保する強力な仕組みだが、Prismaはデフォルトでservice_role経由でRLSをバイパスしがちなため、アプリ層の認可ロジックとRLSポリシーの二重管理・整合性チェックが必須になる。

- **スキーマドリフト対策:** Prisma Migrateのマイグレーション履歴とSupabase上の手動変更（ダッシュボード経由のDDL）が食い違う事故が多発しており、`prisma migrate diff`での定期検証とダッシュボード操作の禁止ルール化が実用的な防御策。

- **型安全性のフロントエンドへの伝播:** Prismaが生成する型をSupabaseの生成型（`supabase gen types`）と統合し、DBスキーマ→API→UIまでの型の一貫性を保つパイプラインが2026年のベストプラクティスとして定着しつつある（本プロジェクトの`'draft' | 'public'`のようなunion型変更時は特に重要）。

- **読み書き分離とキャッシュ戦略:** SupabaseのRead Replica機能とPrisma Accelerateのキャッシュレイヤーを組み合わせることで、物件一覧のような読み取り負荷の高いクエリをオフロードしつつ、書き込み系（予約・決済）は一貫性優先でプライマリに直接向ける設計が有効。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Rustの`wasm-bindgen`/`wasm-pack`ツールチェーンが成熟し、JS/TS側との型安全な連携がしやすくなった結果、画像処理や暗号化などCPU負荷の高い処理をWasmモジュールに切り出す実装パターンが標準化してきている。

- **ポイント2:** WASI 0.2（Component Model）の普及で、ブラウザ外（サーバーサイド・エッジ）でもRust製Wasmモジュールをポータブルに実行できるようになり、Cloudflare WorkersやFastlyなどのエッジランタイムでの採用が進んでいる。

- **ポイント3:** SIMD命令（Fixed-width SIMD）の主要ブラウザ対応が一般化し、Rust+Wasmで数値計算・画像処理系の処理速度がネイティブに近づいたため、「重い処理だけWasm化」ではなく主要ロジック全体をRustで書く選択肢が増えている。

- **ポイント4:** バンドルサイズとコールドスタート時間がWasm導入時の主なボトルネックであり続けており、`wasm-opt`によるサイズ最適化と、必要最小限のAPIサーフェスだけをバインディングする設計が実運用上重要。

- **ポイント5:** Next.js(App Router)のようなSSR環境ではWasmモジュールの初期化タイミング（サーバー/クライアントの分岐）に注意が必要で、本プロジェクトのようなWeb UIにWasmを導入する場合は、まず計測してボトルネックが本当にJS側にあるかを確認してから採用判断すべき。

### 8. Next.js App Router patterns 2026

- **Server Actions の本格採用:** フォーム送信やミューテーションをAPI Routeではなく`'use server'`のServer Actionsで実装するのが標準化し、クライアント側のfetchコードが大幅に削減できる。sumitsugiの物件登録・問い合わせフォームも移行候補。

- **Partial Prerendering (PPR):** 静的部分と動的部分を同一ページ内で混在させ、初回表示を高速化しつつパーソナライズされた内容も配信できる。物件一覧ページのような「静的なレイアウト＋動的な空室状況」構成に有効。

- **キャッシュ戦略の明示化:** `fetch`のデフォルトキャッシュ挙動が変更され、`cacheLife`/`cacheTag`で明示的にキャッシュ期間・無効化ルールを指定する設計が主流に。曖昧なキャッシュによる古いデータ表示バグを防げる。

- **Server Componentsのデータフェッチ集約:** コンポーネント内で直接DBアクセス・非同期処理を行い、クライアントへのJS転送量を削減。`src/lib/data.ts`のようなデータ層をServer Component専用に整理すると保守性が上がる。

- **Route Groups + Parallel Routesでのレイアウト分離:** `(auth)`や`(dashboard)`のようなグループ化と、モーダル・サイドパネルを`@slot`で並行レンダリングする構成が、`account/`配下の複雑なUIで効果的。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Functionsの実行ランタイムがWeb標準API（Fetch, Streams, WebCrypto）に収束しており、Node.js互換レイヤーへの依存を減らすことでコールドスタートがほぼゼロに近づいている。処理の軽量化のため、重い依存ライブラリをEdge側に持ち込まない設計が鍵。

- **ポイント2:** Incremental Static Regeneration (ISR) とEdge Middlewareの組み合わせで、パーソナライゼーション処理をオリジンサーバーに戻さずEdgeで完結させるパターンが主流になっている。例えば認証チェックやA/Bテストの振り分けをMiddlewareで行い、キャッシュヒット率を落とさずに動的な体験を実現できる。

- **ポイント3:** Vercel Functionsの「Fluid Compute」モデル（Edge/Serverlessの垂直統合）により、同一インスタンス内で複数リクエストを並行処理できるようになり、コスト効率と低レイテンシを両立。常時起動のDBコネクションプーリングなど、従来Edge環境では難しかった処理も扱いやすくなっている。

- **ポイント4:** リージョン選択の自動化（Smart Placement）がデフォルト化し、DBやAPIの地理的近接性に基づいて実行リージョンを動的に決定するため、手動でのリージョン指定ミスによるレイテンシ問題が減少している。

- **ポイント5:** Observability（OpenTelemetry統合）がEdge Functionsにも標準搭載され、分散トレーシングでボトルネックの特定が容易になった。本サービスのような不動産プラットフォームでは、物件検索API等のレイテンシをEdgeレベルで計測・最適化する運用が現実的になっている。

### 10. TypeScript type safety patterns 2026

- **Const Type Parameters & テンプレートリテラル型の活用拡大:** TypeScript 5.x系で導入された`const`型パラメータやテンプレート文字列リテラル型を使い、API応答やルーティングパスなどを文字列レベルで厳密に型付けするパターンが2026年も定着。`as const`を多用せず、関数シグネチャ側で推論精度を上げる設計が主流になっています。

- **Zodなどのスキーマ駆動による「実行時型」と「静的型」の統合:** 当プロジェクトでも採用している通り、Zodスキーマから型を`z.infer`で導出し、システム境界（API入出力・フォーム）でパース＝検証することで、静的型チェックだけでは防げないランタイムの型崩れを防ぐアプローチが事実上の標準になっています。

- **Branded Types / Opaque Typesによるプリミティブの誤用防止:** `UserId`と`PropertyId`のように同じ`string`型でも意味の異なるIDを混同しないよう、ブランド型でコンパイル時に区別するパターンが、特にドメインモデルが複雑なアプリ（当サービスの物件・ユーザー・契約関連）で有効です。

- **Discriminated Unionによる状態の網羅性チェック:** `'draft' | 'public'`のようなステータス管理では、switch文の`default`で`never`型を使った網羅性チェック（exhaustiveness check）を徹底することで、新しいステータス追加時にコンパイルエラーで検知できる設計が重要度を増しています。CLAUDE.mdにも明記されている「union型変更時は全使用箇所をgrep」というルールは、この網羅性チェックと組み合わせることでより安全になります。

- **`satisfies`演算子によるオブジェクトリテラルの型安全な検証:** 型を明示的にアサーションせずに、推論された型を保ったままオブジェクトの構造を検証できる`satisfies`が、設定オブジェクトや`site-config.ts`のような定数定義で広く使われるようになっています。
