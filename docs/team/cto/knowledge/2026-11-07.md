# CTO Knowledge - 2026-11-07

## Daily Update (2026-11-07)

### 1. Next.js performance optimization 2026

- **サーバーコンポーネント優先:** Next.js 16ではRSC（React Server Components）をデフォルトにし、クライアントJSを最大70%削減可能。streaming + Suspenseで遅いデータが速いデータの表示をブロックしない構成にすべき。

- **Turbopackの本番採用:** Turbopackが16系で安定版・デフォルトバンドラーになり、`turbopackFileSystemCacheForDev`を有効にすると本番ビルドが2〜5倍、Fast Refreshが最大10倍高速化。ローンチ前のビルド時間短縮に直結する。

- **バンドルサイズの予算管理:** ルートごとのFirst Load JSを100KB（圧縮後）未満に抑える目標を設定し、重いクライアント専用ウィジェット（チャート、エディタ等）は`next/dynamic`で遅延読み込みする。sumitsugiの物件詳細ページなど画像・UIが重いページで特に効果が出やすい。

- **画像・フォント最適化:** `next/image`でAVIF形式＋LCP画像への`priority`/`sizes`指定を徹底（AVIFはWebPより30〜50%軽量）。フォントは`next/font`でセルフホストし、レンダーブロッキングを排除。物件写真が多いUIなので優先度高め。

- **計測ベースの継続改善:** 推測ではなくWeb Vitals計測とバンドル監査をCIに組み込み、パフォーマンス予算を自動チェックしてリグレッションを防ぐ。ベータローンチ前に導入しておくと運用後の劣化を早期検知できる。

### 2. React Server Components streaming 2026

- **ポイント1（Partial Prerendering成熟）:** Next.js 16世代ではPPR（Partial Prerendering）がデフォルト前提になり、静的シェルを即時配信しつつ動的部分だけストリーミングする構成が標準化。本プロジェクトのproperties一覧やlisting詳細ページでも、価格・在庫などの動的要素のみSuspense境界で遅延させれば初期表示が速くなる。

- **ポイント2（Server/Clientの境界設計）:** "use client"境界を過剰に広げるとストリーミングの恩恵が消えるため、インタラクティブなUIパーツ（フォーム・認証状態表示など）だけをクライアントコンポーネント化し、データ取得ロジックはサーバー側に残す設計が重要。auth-context.tsx配下のクライアント依存範囲は定期的に見直す価値がある。

- **ポイント3（キャッシュ戦略とストリーミングの両立）:** Next.js 16のキャッシュAPI刷新（`use cache`ディレクティブ系）により、ストリーミング単位でのキャッシュ制御が可能になった。物件データのような更新頻度が低いデータはキャッシュしつつ、空室状況など頻度が高いデータだけをストリーミングで最新化する分離が実用的。

- **ポイント4（エラーバウンダリとUX）:** ストリーミング導入時はSuspenseのfallback UIとerror.tsxの設計が体験を左右する。「前の住人」情報などユーザーが待てる要素にはスケルトンUIを、致命的な部分には即時エラー表示を割り当てる使い分けが2026年のベストプラクティス。

- **ポイント5（計測の重要性）:** TTFB改善だけでなくTBT・INPもストリーミング導入後に悪化するケースがあるため、本番相当環境でのCore Web Vitals計測を欠かさないこと。ビルド検証（`bun run build`）だけでは体感速度の劣化は検出できない点に注意。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはTypeScriptモノレポ内で型安全性を保てる反面、クライアント・サーバーが同一言語スタックに縛られるため、sumitsugiのようなNext.js単一スタック構成では相性が良いが、将来モバイルアプリや外部パートナー連携を想定するならREST/GraphQLとの併用設計を早めに検討すべき。

- **ポイント2:** GraphQLは「前の住人」「次の住人」のようなネストした関係データ（物件・ユーザー・引越し費用情報など）を1リクエストで取得できる強みがあるが、2026年現在はNext.js App RouterのServer Componentsがデータ取得の大半を担うため、GraphQLを導入するコストに対して実利が薄くなりやすい。

- **ポイント3:** RESTは依然としてWebhook連携や決済・外部サービス（弁護士確認フロー後に予定される決済連携など）とのインテグレーションでデファクトスタンダードであり、内部APIはtRPC、外部公開APIはREST、という「ハイブリッド構成」が2026年のベストプラクティスとして定着している。

- **ポイント4:** スキーマ駆動開発（Zodをソース・オブ・トゥルースとし、tRPCの型推論とOpenAPI定義を同時生成するツール群）が主流化しており、本プロジェクトのZod活用方針（標準規約に明記）とも整合するため、API層でもZodスキーマを中心に据えるのが効率的。

- **ポイント5:** ベータローンチ直前の今のフェーズでは、新APIパラダイムへの移行よりも既存tRPC構成の型整合性・エラーハンドリングの堅牢性（ビルド時の型チェック徹底）を優先すべきで、API設計の大規模変更は法務確認完了後の次フェーズに回すのが妥当。

### 4. serverless edge computing 2026

- **ポイント1:** 2026年はエッジでのLLM推論（軽量モデル・量子化モデル）が本格化し、Cloudflare WorkersやVercel Edge Functionsでリアルタイムパーソナライゼーションが低コストで実現可能に。sumitsugiの物件検索レコメンドなどもコールドスタート無しでエッジ実行できる段階に来ている。

- **ポイント2:** エッジKVストア（Cloudflare D1/Durable Objects、Vercel Edge Config）の成熟により、グローバル分散でも強整合性のあるセッション管理が可能。認証トークン検証やレート制限をオリジンサーバーに戻さずエッジで完結できる。

- **ポイント3:** Next.js 16のPartial Prerenderingとエッジランタイムの統合が進み、静的シェル＋動的パーソナライズ部分のストリーミングがデフォルトパターン化。物件一覧ページのような「骨格は静的・在庫情報は動的」な構成に適合しやすい。

- **ポイント4:** コスト面では従量課金エッジ関数が中小規模トラフィックにおいてサーバーレス（Lambda等）より割安になるケースが増加。ただしCPU時間制限（多くが10-50ms級）があるため、画像処理や重いPDF生成（契約書類生成など）はオリジンに残す設計判断が必要。

- **ポイント5:** エッジでのオブザーバビリティ（分散トレーシング）が課題として残る。マルチリージョン展開時はOpenTelemetry対応のエッジランタイムを選定しないと障害調査が困難になるため、ベータローンチ時点でのログ集約方針を早めに固めるべき。

### 5. authentication security best practices 2026

- **パスキー/WebAuthnのデフォルト化:** 2026年現在、パスワードレス認証（FIDO2/WebAuthn）が標準となり、パスキーをプライマリ認証手段として実装すべき。フィッシング耐性があり、ユーザー体験も向上するため、本サービスの前の住人・次の住人双方のログインフローに優先導入する価値がある。

- **多層防御としてのデバイスバインディング:** セッショントークンをデバイスフィンガープリントやhardware-backed keyに紐付けることで、トークン漏洩時の横展開リスクを下げる。特にPC/モバイル間で引越し手続きのような高価値操作を行うフローでは重要。

- **ゼロトラスト前提のセッション管理:** 短命アクセストークン＋リフレッシュトークンのローテーション、異常ログイン検知（IP/地理/デバイス変化）をセットで実装するのが2026年のベストプラクティス。認証を「一度通れば信頼し続ける」モデルから「継続的検証」モデルへ移行する。

- **Supabase Auth等のBaaS利用時もRLSを前提にした最小権限設計:** 認証だけでなく認可（authorization）をDB層（Row Level Security）でも二重に担保し、アプリ層のバグがデータ漏洩に直結しない構成にする。物件データや個人情報を扱う本サービスでは特に重要。

- **シークレット管理の自動ローテーション:** JWT署名鍵やAPIキーは静的な環境変数運用から、定期ローテーション＋Secret Managerでの管理に移行するのが2026年の標準。ハードコード禁止はCLAUDE.mdの既存ルールと一致しており、継続して徹底すべき。

### 6. database architecture Prisma Supabase 2026

- **ポイント1: Prisma ORMのRust脱却とパフォーマンス向上** 最新のPrisma(v6以降)はQuery EngineをTypeScript/WASMベースに移行し、Rustバイナリ依存を排除。コールドスタートが改善され、Vercelなどのサーバーレス環境でのデプロイサイズと起動速度が大幅に向上している。

- **ポイント2: Supabaseの接続プーリング(PgBouncer/Supavisor)との組み合わせが必須** サーバーレス関数からPrismaで直接Postgresに接続すると接続数が枯竭しやすいため、SupabaseのTransaction Pooler(ポート6543)を経由し、`?pgbouncer=true`オプションや`directUrl`でマイグレーション用の直接接続を分離する構成が標準化している。

- **ポイント3: Row Level Security (RLS)とPrismaの併用パターン** SupabaseのRLSはPrisma Clientのクエリをバイパスしがちなので、アプリ層の認可をPrismaミドルウェア/拡張(Client Extensions)で行うか、RLS用の`auth.uid()`をセッション変数として渡す設計が重要。sumitsugiのような「前の住人/次の住人」間の権限分離が絡む物件データでは特に、RLSとアプリ層認可の二重防御を検討すべき。

- **ポイント4: Edge FunctionsとPrisma Accelerateの活用** Supabase Edge Functions(Deno)環境ではPrismaの素のTCP接続が使えないため、Prisma Accelerate経由のHTTP接続プールが実質的な標準解になっている。レイテンシが重要な物件検索・一覧表示系のクエリはAccelerateのキャッシュ機能(TTLベース)で読み取り負荷を大幅に削減できる。

- **ポイント5: マイグレーション管理はSupabase CLIとPrisma Migrateの一本化** 2026年現在、両者を並行運用すると差分検出でコンフリクトが起きやすいため、`prisma migrate`をマイグレーションの単一ソースとし、Supabase CLIはローカル開発環境の起動・Studio確認用途に限定する運用がベストプラクティスとして定着している。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Wasm GC(Garbage Collection)提案の実装が進み、Rustに限らずマネージド言語もWasmで効率的に動く土台が整ってきた。ただしRustはGC不要な所有権モデルのため、依然としてWasmバイナリサイズ・起動速度で優位性を保っている。
- **ポイント2:** Component Model(WASI Preview 2)の安定化により、Rust製Wasmモジュール同士をFFIオーバーヘッドなしで合成できるようになり、マイクロサービス的な「Wasmコンポーネント」設計がサーバーサイドでも実用段階に入っている。
- **ポイント3:** SIMD128やマルチスレッド(共有メモリ+Atomics)のブラウザ対応が一般化し、Rust+Wasmで画像処理・動画エンコード・物理演算などCPU負荷の高い処理をクライアント側にオフロードする事例が増加している。
- **ポイント4:** `wasm-bindgen`/`wasm-pack`のビルドチェーンが成熟し、Rustの`wee_alloc`代替としてデフォルトアロケータの最適化が進んだことで、同等JSロジックと比べて実行速度2〜5倍、バイナリサイズも大幅削減できるケースが標準化している。
- **ポイント5:** サーバーレスエッジ環境(Cloudflare Workers、Fastly Compute等)でRust+Wasmがコールドスタート数ミリ秒を実現し、Node.js/Pythonランタイムに対するレイテンシ優位性がエッジコンピューティング採用の決め手になりつつある。当社のプラットフォームでも画像変換・PDF生成などの重処理をエッジWasm化することでサーバーコスト削減とレスポンス向上を同時に狙える。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 16ではPPRが安定版となり、静的シェルと動的コンテンツを1つのレスポンスで配信できるため、ダッシュボードや一覧ページで初期表示速度とパーソナライゼーションを両立しやすくなっている。

- **Server Actions中心のデータ更新:** APIルートを別途作らずServer Actionsでミューテーションを完結させる設計が主流になり、`src/app`配下にAPI層が増えすぎる問題を避けられる。本プロジェクトでも物件ステータス更新などはServer Actions + Zodバリデーションの組み合わせが実用的。

- **キャッシュ戦略の明示化:** `fetch`のデフォルトキャッシュ挙動が変わった影響で、`cacheLife`/`cacheTag`を使った明示的なキャッシュ制御が必須になっており、曖昧な暗黙キャッシュに依存したコードはビルド時に挙動が変わるリスクがある。

- **React Server Components前提のコンポーネント分割:** "use client"境界を最小化し、認証状態やフォームなど本当にクライアント側が必要な部分だけを切り出す設計が定着。`auth-context.tsx`のようなコンテキストは境界直下に配置し、上位ツリーをServer Componentのまま保つのがパフォーマンス上有利。

- **型安全なルーティング:** Next.js 16のTyped Routesがデフォルト有効になり、`properties/`や`listing/`配下の動的ルートでパラメータの型ミスマッチをビルド時に検出できる。`'draft' | 'public'`のようなユニオン型とあわせて使うことで、ステータス不整合によるランタイムエラーを削減できる。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約最適化:** Vercel Edge FunctionsはNode.js APIの一部しか使えないため、`fetch`ベースの軽量処理に限定し、重い処理はServerless Functionsに委譲する設計が定着しつつある。

- **コールドスタート短縮とIsolate再利用:** V8 Isolatesベースの実行モデルにより起動が数ms〜数十msに抑えられており、頻繁に呼ばれるミドルウェア（認証チェック、A/Bテスト振り分け、リダイレクト）はEdgeに置くのがベストプラクティス。

- **Edge Configとの組み合わせ:** フラグ判定やリダイレクトルールなど低頻度更新・高頻度読み取りのデータは、Edge Function内でデータベースを叩かずEdge Configから読むことでレイテンシを数msレベルに削減できる。

- **リージョン選択の明示化:** デフォルトの自動リージョン選択よりも、ユーザー分布やデータベースのリージョンに合わせて`regions`設定を明示する方が、DB往復が絡む処理ではレイテンシが安定しやすい。

- **ストリーミングSSR/RSCとの相性:** Next.js 16のPartial PrerenderingやRSCストリーミングと組み合わせることで、Edge上でTTFBを最小化しつつ、重いデータ取得はSuspense境界でオリジンに任せる構成が主流になっている。

### 10. TypeScript type safety patterns 2026

- **厳格な型推論とconst型パラメータ:** TypeScript 5.x系で`const`型パラメータやconditional typesの推論が強化され、APIレスポンスやフォームスキーマの型をランタイム検証（Zod等）と自動同期させるパターンが標準化している。手動での型定義とスキーマ定義の二重管理を避け、`z.infer<typeof schema>`で単一ソース化することが実務的な鉄則。

- **Branded Types / Nominal Typingの普及:** `UserId`と`PropertyId`のように構造的に同じ`string`でも意味が異なる値を区別するBranded Typesが、大規模コードベースでのバグ防止策として定着。sumitsugiのような物件ID・ユーザーID混在リスクのあるドメインでは特に有効。

- **Exhaustiveness Checkingの徹底:** Union型（`'draft' | 'public'`のようなステータス型）に対して`switch`文の`default`ケースで`never`型チェックを強制するパターンが、型安全性担保の基本作法として広く浸透。新しいステータス値追加時のコンパイルエラーで漏れを即検知できる。

- **サーバー/クライアント境界の型安全性:** Next.jsのServer Actions・RSC環境では、サーバー専用の型とクライアントに漏れる型を明確に分離する設計（`'use server'`境界でのシリアライズ可能型のみ許可）が重要トレンドとなっており、型の「越境」をビルド時に検出する仕組みが求められている。

- **型レベルテストの一般化:** `vitest`の`expectTypeOf`や`tsd`を使い、型定義自体をユニットテストとして検証する手法が、特に公開APIやユーティリティ関数のリグレッション防止策として採用が進んでいる。
