# CTO Knowledge - 2026-09-20

## Daily Update (2026-09-20)

### 1. Next.js performance optimization 2026

- **Turbopackのフル安定化:** Next.js 16でTurbopackがビルド・開発両方のデフォルトになり、webpack比で大幅な高速化が実現。特に大規模モノレポでのHMR速度とプロダクションビルド時間が課題だった場合、移行の恩恵が大きい。

- **Partial Prerendering (PPR) の本格運用:** 静的シェルを即座に返しつつ動的部分をストリーミングする手法が主流化。物件一覧や詳細ページのように「大部分は静的だが一部パーソナライズが必要」なページ構成に相性が良く、TTFBとLCPの両立が可能。

- **React Server Componentsでのデータフェッチ最適化:** `fetch`のリクエストメモ化とキャッシュタグ（`revalidateTag`）を組み合わせ、物件データ更新時に必要な箇所だけを再検証する設計が定石に。過剰なクライアントフェッチを避けることでネットワークウォーターフォールを削減できる。

- **画像・フォント最適化の自動化強化:** `next/image`のAVIF優先配信とレイアウトシフト対策、`next/font`によるセルフホスティングが標準化。物件写真を多用するUIではCLS（Cumulative Layout Shift）改善への影響が特に大きい。

- **Bundle分析とEdge Runtimeの使い分け:** `@next/bundle-analyzer`での定期監査に加え、認証など軽量ロジックはEdge Runtime、DB操作を伴う重い処理はNode Runtimeに配置する住み分けが、コールドスタート短縮とレイテンシ改善の両立に有効。

### 2. React Server Components streaming 2026

## CTO視点: React Server Components Streaming 2026

- **ポイント1（Partial Prerenderingの標準化）:** Next.js 16ではPPR（Partial Prerendering）がstableとなり、静的シェルを即座に配信しつつ動的部分をストリーミングする構成が標準パターンに。当プロジェクトの物件一覧ページのような「静的レイアウト+動的データ」構成に特に有効で、TTFBを大幅短縮できる。

- **ポイント2（Suspense境界の粒度設計が重要に）:** ストリーミングの効果はSuspense境界の切り方次第。粒度が粗いと一部の遅いデータ取得（例: 前の住人の活動歴API）が全体をブロックしてしまうため、コンポーネント単位で意図的にfallback UIを設計する必要がある。

- **ポイント3（RSC Payloadのキャッシュ戦略）:** React 19.2以降でRSC専用のキャッシュタグ機構が整備され、`revalidateTag`によるきめ細かい再検証が可能に。物件のdraft/public切り替えのような更新頻度の異なるデータを扱う本プラットフォームでは、キャッシュ粒度の見直しでビルド時間とサーバー負荷を削減できる余地がある。

- **ポイント4（Server Actionsとの統合が成熟）:** フォーム送信（問い合わせ・引き継ぎ申込など）でServer Actions + `useActionState`の組み合わせがストリーミングUIと自然に統合され、楽観的更新の実装コストが下がっている。認証周りのバリデーションはZodスキーマをServer Action境界にそのまま適用できる点も実装効率が良い。

- **ポイント5（エッジランタイムとの相性）:** ストリーミングSSRはエッジ環境（Vercel Edge等）との親和性が高く、ユーザーの地理的分散が大きいtoC不動産系サービスではレイテンシ改善効果が顕著。ただしNode.js専用ライブラリ依存があると制約になるため、依存関係の棚卸しが前提条件。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはNext.js 16のようなフルスタックTypeScriptプロジェクトで採用が加速しており、スキーマ定義とAPI型の二重管理が不要になる分、フロントとバックを同一リポジトリで開発するsumitsugiのような構成には特に相性が良い。
- **ポイント2:** GraphQLは複雑なクエリ集約や複数クライアント（Web/モバイル）向けの柔軟なデータ取得が必要な場面で依然強いが、キャッシュ制御やN+1問題対策のコストが高く、単一Webアプリ中心のプロダクトではオーバーエンジニアリングになりやすい。
- **ポイント3:** RESTは依然としてWebhookや外部連携（決済・地図API等）のデファクトスタンダードであり、内部通信はtRPC、外部公開APIはREST（OpenAPI併記）という「使い分け」が2026年の主流パターンになっている。
- **ポイント4:** エッジランタイム（Vercel Edge, Cloudflare Workers）でのAPI実行が一般化し、tRPCやRESTハンドラをエッジ互換に保つこと（Node固有APIへの依存を避ける）がパフォーマンス最適化の鍵になっている。
- **ポイント5:** AIエージェント（MCP経由）からの直接API呼び出しが増えており、Zodスキーマによる入力検証をAPI境界に持つ設計（standards.mdの方針と一致）が、そのままツール定義の自動生成にも転用できる点が実用上のメリットになっている。

### 4. serverless edge computing 2026

**CTO視点：Serverless Edge Computing 2026のトレンド**

- **ポイント1（V8アイソレートの標準化）:** Cloudflare Workers・Vercel Edge Functions・Deno Deployなど、コールドスタートをほぼゼロにするV8アイソレート方式が主流化しており、従来のコンテナベースFaaSより初回応答速度で優位に立っている。sumitsugiのような一覧表示・検索系ページは特に恩恵が大きく、TTFB改善の投資対効果が高い。

- **ポイント2（エッジでのデータレイヤー統合）:** D1（SQLite）、Turso、PlanetScale等の「エッジネイティブDB」が実用段階に入り、DBクエリ自体をユーザーに近いリージョンで実行できるようになった。物件検索のような読み取り中心の機能はエッジDBへの移行でレイテンシを大幅短縮できるが、書き込み整合性（在庫・予約状態など）は依然リージョン集約が必要な点に注意が必要。

- **ポイント3（Next.js App RouterとEdge Runtimeの相性）:** Next.js 16のPartial PrerenderingとEdge Runtimeの組み合わせで、静的シェル＋動的パーソナライズをエッジで完結させる設計が一般化。認証状態や「前の住人」情報のようなユーザー依存コンテンツをエッジでストリーミング注入することで、SEOを保ちつつパーソナライズ体験を高速化できる。

- **ポイント4（コスト構造の逆転リスク）:** エッジ実行は従量課金モデルが多く、トラフィックが伸びるほど中央集権的サーバーレス（Lambda等）より割高になるケースが増えている。ローンチ初期はエッジのレイテンシ優位を活かしつつ、スケール後はハイブリッド構成（重い処理は専用リージョン、軽量UIロジックのみエッジ）への移行判断を早めに設計しておくべき。

- **ポイント5（可観測性の分断問題）:** エッジ実行はリージョン分散のためログ・トレースが断片化しやすく、障害調査が難しくなる傾向がある。Sentry/Datadog等のエッジ対応オブザーバビリティを早期に組み込まないと、法務確認後のベータローンチ以降に本番障害の原因特定が遅れるリスクがある。

### 5. authentication security best practices 2026

- **パスキー標準化の完了:** 2026年時点でFIDO2/WebAuthnベースのパスキーがパスワードレス認証のデファクトスタンダードとなっており、フィッシング耐性の観点から新規実装では最初からパスキーを第一候補とし、パスワードは復旧手段程度に格下げすべきです。

- **トークンのハンドリング:** アクセストークンは短命(5-15分)にし、リフレッシュトークンはHTTPOnly+Secure+SameSite=StrictなCookieに格納してlocalStorage保存を避けることで、XSS経由のトークン窃取リスクを大幅に下げられます。

- **多層防御としてのリスクベース認証:** IPレピュテーション・デバイスフィンガープリント・行動パターンを組み合わせたアダプティブMFAが主流になっており、常時MFAを強制するより不審なログインのみ追加認証を要求する方がUX/セキュリティのバランスが良いです。

- **セッション管理の厳格化:** 前の住人・次の住人間で個人情報や決済情報を扱う本サービスの特性上、重要操作(引越し費用の支払い、物件公開設定変更など)の前には再認証(step-up authentication)を必須にし、セッション固定化攻撃・CSRF対策をセットで実施すべきです。

- **監査ログとゼロトラスト:** 認証イベント(ログイン失敗、パスワードリセット、MFA変更)を改ざん不可能な形で記録し、内部APIも含めてリクエストごとに認可を検証するゼロトラスト前提の設計にすることで、法務確認中の現フェーズでも第三者監査に耐えられる体制を先んじて整えられます。

### 6. database architecture Prisma Supabase 2026

- **エッジ最適化とコネクションプーリング:** Supabaseの2026年時点のPgBouncer/Supavisor統合が進み、Prisma AccelerateやData Proxyと組み合わせることでサーバーレス環境（Vercel Edge等）でのコールドスタート時のDB接続枯渇問題が実質解消されつつある。当プロジェクトのようなNext.js App Router構成では、API RouteごとにPrisma Clientを再生成せずシングルトン化し、Supabaseのプーラー経由で接続することが必須のベストプラクティス。

- **Prisma ORMのTypedSQLとRLSの共存:** Prismaが型安全な生SQL（TypedSQL）をサポートしたことで、Supabaseの強みであるRow Level Security（RLS）をPrisma経由で書きつつ型を失わない設計が可能になった。物件データのようにpublic/draftステータスでアクセス制御が必要な場合、RLSポリシーをDB側の防衛線とし、アプリ側の認可ロジックと二重化するのが2026年の標準パターン。

- **リアルタイム機能とPrisma Pulseの選択:** Supabase RealtimeとPrisma Pulseは競合する選択肢だが、既にSupabaseをAuth/Storageで使っている場合はRealtimeに寄せる方が運用コストが低い。物件のステータス変更通知や引越し費用の交渉チャットのような機能を今後追加するなら、新規サービス導入より既存Supabase Realtimeの活用を優先すべき。

- **マイグレーション運用の一本化:** Prisma MigrateとSupabase CLIのマイグレーションを併用すると差分がズレる事故が多発するため、2026年のベストプラクティスはPrisma Migrateを単一の真実源とし、Supabase側はスキーマ変更を検知するだけの構成にすること。CI上で`prisma migrate diff`を使ったドリフト検知をビルドゲートに含めるべき。

- **ベータローンチ前の法務要件との接続:** プライバシーポリシー対応で個人情報（住所・連絡先）のカラムレベル暗号化が必要になる可能性が高く、SupabaseのVault機能とPrismaのミドルウェアを組み合わせた暗号化/復号層を今のうちに設計しておくと、法務確認後の実装遅延を防げる。

### 7. WebAssembly Rust performance 2026

- **ポイント1（WASI Preview 2とコンポーネントモデルの定着）:** WASI 0.2以降のコンポーネントモデルが実用段階に入り、Rustの`cargo component`ツールチェーンで言語間相互運用がゼロコストに近い形で実現できるようになった。マイクロサービスをWasmコンポーネントとして分割することで、デプロイの粒度とコールドスタート性能が大幅に改善している。

- **ポイント2（AOTコンパイルとWasmtime/Wasmerの実行時最適化）:** WasmtimeのCraneliftバックエンドがAOTキャッシュとPGO（Profile-Guided Optimization）に対応し、Rust製Wasmバイナリのネイティブ比性能ギャップが多くのワークロードで1.1〜1.3倍程度まで縮小している。サーバーサイドWasmを検討する際はJITではなくAOT配布を前提に設計すべき。

- **ポイント3（SIMD・スレッド・共有メモリの標準化）:** Wasm SIMD128とシェアードメモリ+アトミクスがブラウザ・サーバー双方で安定運用可能になり、Rustの`std::simd`やRayon的並列処理をWasm上でも活用できる。画像処理や暗号処理など計算負荷の高い前の住人向け機能（物件写真の自動補正など）をクライアントサイドWasmにオフロードする選択肢が現実的になった。

- **ポイント4（バイナリサイズとツリーシェイキング）:** `wasm-opt`とRustの`build-std`最適化、および`no_std`対応クレートの充実により、機能単位のWasmモジュールを数十KB台に抑えられるケースが増えている。sumitsugiのようなNext.js中心のプロダクトでは、重い一括処理（PDF生成、契約書チェックなど）だけを部分的にWasm化する漸進的採用が費用対効果が高い。

- **ポイント5（エッジランタイムとの統合）:** Cloudflare Workers・Fastly Compute・Vercel EdgeなどがWasmランタイムをネイティブに統合し、Rust+Wasmでエッジ実行するレイテンシメリットが明確化した。前の住人と次の住人のマッチングロジックのような軽量・高頻度な処理をエッジでRust/Wasm実装すると、サーバー往復を減らしつつ型安全性も担保できる。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 16では静的シェルと動的コンテンツを1つのルートで組み合わせるPPRが安定版となり、`loading.tsx`のSuspense境界を活用することでTTFBを大幅に改善できる。sumitsugiの物件一覧ページのように「検索フィルタは動的・カード枠は静的」という構成に特に有効。

- **Server Actions の型安全な検証パターン:** `'use server'`関数の入力をZodスキーマでバリデーションし、`useActionState`（旧`useFormState`）と組み合わせるのが2026年の定石。フォーム送信・エラー表示・楽観的UIを一貫したパターンで実装でき、`standards.md`が求める「システム境界でのZod検証」とも整合する。

- **Cache Components / `use cache` ディレクティブ:** ファイル・関数単位でキャッシュ戦略を明示的に指定する`use cache`がデフォルト推奨になりつつあり、暗黙的なフルルートキャッシュへの依存から脱却できる。データ取得層（`src/lib/data.ts`）に導入すると、再検証タイミングの制御が細かくできる。

- **Route Groups + Parallel Routes によるダッシュボード構成:** `@modal`や`@sidebar`のようなParallel Routesは、物件詳細ページでモーダル表示（画像ギャラリー等）とURL状態を両立させるのに実用的。ブラウザバックで自然にモーダルが閉じる挙動も無料で得られる。

- **Server-only境界の徹底 (`server-only`パッケージ):** クライアントバンドルへの機密データ混入を防ぐため、DB接続やAPIキーを扱うモジュールに`import 'server-only'`を明示するパターンが定着。認証・決済まわりのコードでは特に重要で、`security.md`の「秘密情報のハードコード禁止」原則とも直結する。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約設計:** Vercel Edge FunctionsはNode.js APIの多くが使えないV8 isolateベースのため、`fetch`ベースのAPIやWeb標準APIを前提に設計し、重い処理はNode.js Functionsに分離するのが2026年時点でも基本方針です。

- **Coldスタート回避とストリーミング活用:** Edge Functionsは起動が数msと高速なため、レスポンスの初速が重要なSSRやAPIプロキシに向いており、`ReadableStream`によるストリーミングレスポンスを組み合わせることでTTFBを大幅短縮できます。

- **リージョン配置の最適化:** データベースやバックエンドAPIの物理リージョンに近いEdge Configを選択しないと、かえってレイテンシが悪化するケースがあるため、`export const preferredRegion`を用いてDB近接リージョンに固定するのがベストプラクティスです。

- **キャッシュ戦略との併用:** Edge Middlewareでの認証・A/Bテスト振り分けとISR/Data Cacheを組み合わせることで、動的処理とキャッシュ効率を両立させる構成が主流になっており、Next.js 16のPartial Prerenderingとの相性が特に良いです。

- **コスト・実行時間制限の管理:** Edge Functionsは実行時間やメモリに制約があるため、長時間処理やファイルシステムアクセスが必要な処理は誤って配置しないよう、モニタリング（Vercel Observability）で関数ごとの実行特性を可視化しておくことが重要です。

### 10. TypeScript type safety patterns 2026

- **ポイント1: Branded Types / Nominal Typingの標準化** — 構造的型システムの弱点を補うため、IDやドメイン値（`UserId`, `PropertyId`など）にbranded typeを使う手法が定着。単純な`string`混同バグ（例: セラーIDと物件IDの取り違え）をコンパイル時に検出できる。

- **ポイント2: `satisfies`演算子とconst型パラメータの活用** — TS 4.9以降の`satisfies`で「型を広げずに検証する」パターンが浸透し、TS 5.x系の`const`型パラメータと組み合わせることで、設定オブジェクトやZodスキーマの型推論精度が向上。sumitsugiの`site-config.ts`のような設定ファイルでも、型安全性を保ちながら値の自動補完が効く。

- **ポイント3: Zodなどのスキーマバリデーションと型のSingle Source of Truth化** — `z.infer<>`でランタイムバリデーションと静的型を同一スキーマから生成する手法が主流化。境界（API入出力・フォーム）でのバリデーションが型定義と乖離しなくなり、`status: 'draft' | 'public'`のようなUnion型変更時の一貫性チェックも自動化しやすい。

- **ポイント4: Discriminated Union + 網羅性チェック（exhaustiveness check）の徹底** — `never`型を使ったswitch文の網羅性チェックがベストプラクティスとして標準化。新しいステータスや状態を追加した際、対応漏れをビルドエラーとして検出でき、「Union型変更時は全使用箇所をgrep」という運用ルールを型レベルで補強できる。

- **ポイント5: 型のみのimport分離とビルド高速化** — `import type`の強制（ESLintルール`consistent-type-imports`）とisolatedModules対応が、BunやTurbopackのような高速ビルドツールとの組み合わせで重要視されている。型情報とランタイムコードを明確に分離することで、Next.js 16のビルド時間短縮とツリーシェイキング精度向上に直結する。
