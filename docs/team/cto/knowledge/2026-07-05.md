# CTO Knowledge - 2026-07-05

## Daily Update (2026-07-05)

### 1. Next.js performance optimization 2026

- **ポイント1（Turbopackの本番ビルド標準化）:** Next.js 16ではTurbopackが本番ビルドでも安定版となり、大規模プロジェクトでもwebpack比で数倍のビルド高速化が期待できるため、CIのビルド時間短縮に直結する。移行時はカスタムwebpack設定の互換性を事前に洗い出す必要がある。

- **ポイント2（Partial Prerendering / PPRの本格活用）:** 静的シェルと動的コンテンツを1リクエスト内で組み合わせるPPRが安定化し、ECサイトや物件一覧ページのようにSEOが必要な部分は静的、価格や在庫などは動的にストリーミングする設計が主流になっている。`suspense`境界の粒度設計がパフォーマンスとキャッシュヒット率を左右する。

- **ポイント3（Cache Componentsとキャッシュの明示化）:** `use cache`ディレクティブによりキャッシュ境界をコンポーネント単位で明示的に指定する方式が定着し、暗黙のキャッシュ挙動によるバグ（stale data表示など）を防げる。物件詳細ページなど更新頻度が異なるデータを扱う場合、この粒度制御が重要になる。

- **ポイント4（React Compilerによる自動メモ化）:** React Compilerが安定運用フェーズに入り、`useMemo`/`useCallback`の手動最適化が不要になるケースが増えている。既存コードのメモ化コードを段階的に削除しつつ、Compilerが生成する最適化を信頼する方向にシフトすべき。

- **ポイント5（Core Web Vitals計測とINP最適化の継続重視）:** LCP/CLSに加えてINP（Interaction to Next Paint）が引き続き重視されており、フォームや検索フィルタなどインタラクション過多なUIではServer Actionsの多用よりもクライアント側の軽量な状態更新を組み合わせるハイブリッド設計が推奨される傾向にある。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** Next.js 16ではPartial Prerenderingとの統合が進み、静的シェルを即座に返しつつ動的部分だけをストリーミングするパターンがデフォルト構成になりつつある。物件詳細ページのような「基本情報は即表示、レビューや空き状況は遅延ロード」という構成に適している。

- **Suspense境界の粒度設計が重要課題に:** 境界を細かく切りすぎるとウォーターフォールが発生し、粗すぎるとTTFBのメリットが失われるため、コンポーネント単位ではなく「ユーザーが最初に見る情報」単位で境界を設計するのがベストプラクティスとして定着してきている。

- **RSC PayloadのキャッシュとCDN連携:** Vercelや類似プラットフォームでRSCペイロード自体をエッジでキャッシュする仕組みが成熟し、`use cache`ディレクティブと組み合わせることで、物件一覧のような読み取り中心ページのTTFBを大幅に短縮できる。

- **クライアントバンドル削減効果の再評価:** Server Componentsによるバンドルサイズ削減効果はデータ取得コンポーネントに集中しており、認証状態やフォーム操作を含む`account/`配下のようなインタラクティブ画面ではClient Componentsとの境界設計（"use client"の配置場所）が引き続きパフォーマンスを左右する。

- **エラーバウンダリとストリーミングの相互作用:** ストリーミング中に発生したエラーのハンドリングが複雑化しやすく、`error.tsx`とSuspenseのネスト構造を事前に設計しないと、部分的に壊れたUIがユーザーに見えるリスクがあるため、本番導入前にE2Eでの検証が不可欠。

### 3. API design REST GraphQL tRPC 2026

- **APIファーストからスキーマファーストへ:** GraphQLやtRPCのようにスキーマ/型定義を起点に開発する流れが定着し、フロントエンドとバックエンドの型不整合によるバグを大幅に削減できる。sumitsugiのようなNext.js App Router構成ではtRPCを使うとend-to-endの型安全性を維持しつつAPI層のボイラープレートを減らせる。

- **BFF（Backend for Frontend）パターンの普及:** 単一の汎用APIではなく、フロントエンドごとに最適化されたAPI層を用意する設計が主流になりつつあり、Next.jsのRoute HandlersをBFF的に使うことでモバイル/Web双方の要求に個別最適化しやすくなる。

- **RESTの継続的な優位性(公開API/外部連携):** 内部通信ではtRPC/GraphQLが伸びる一方、決済や外部パートナー連携など第三者向けの公開APIは依然としてREST + OpenAPIが標準であり、ドキュメント生成・監査のしやすさが評価されている。

- **エッジランタイムとAPIレイテンシ最適化:** Vercel EdgeやCloudflare Workersなど、API処理をエッジで実行する構成が一般化し、物件検索や引越し費用計算のような読み取り中心の処理はエッジキャッシュ+ISRで大幅に高速化できる。

- **AIエージェント向けAPI設計(MCP対応):** LLMエージェントが直接APIを呼び出すケースが増え、Model Context Protocol(MCP)のようにエージェントが安全にツールを発見・実行できるインターフェース設計が新たな標準として重要性を増している。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** Cloudflare Workers AIやVercel Edge Functionsなど、エッジランタイム上で軽量LLM推論を直接実行する構成が2026年には一般化しており、レイテンシ要件が厳しいUI（チャット応答、検索候補生成など）はオリジンサーバーを経由せずエッジで完結させるのが実用的な選択肢になっている。

- **コールドスタートのほぼ解消:** V8 isolateベースのランタイム（Cloudflare Workers, Deno Deploy等）が主流化し、コールドスタートは数ミリ秒単位まで縮小。Next.jsのようなフレームワークもエッジランタイム前提の設計が増えており、sumitsugiのような物件検索・一覧表示系のページはエッジでのSSR/ISRを積極採用する価値がある。

- **エッジ×データベースのレイテンシ問題が構造的課題として残存:** コンピュートはエッジに分散できても、正整合性が必要なデータ（予約・決済トランザクション等）は依然としてリージョナルDBへの往復が発生する。エッジでキャッシュ・読み取り専用処理を行い、書き込みは集中管理するハイブリッド構成が現実解。

- **WASMベースのポータブルランタイムが差別化要因に:** WASI準拠のWebAssemblyモジュールとして関数をデプロイし、Cloudflare/Fastly/AWS Lambda@Edge間でベンダーロックインを避ける動きが加速。将来的なコスト最適化・マルチクラウド戦略の選択肢を残す意味で、新規エッジ機能はWASM互換を意識した設計が望ましい。

- **コスト構造の変化とFinOps連携:** リクエスト課金からCPU時間課金へのシフトが進み、エッジ関数の実行時間・メモリ効率が直接コストに直結するようになった。監視・アラートの仕組み（実行時間の異常検知）をCI/CDに組み込む運用が、スケール時のコスト暴走を防ぐ標準プラクティスになりつつある。

### 5. authentication security best practices 2026

- **パスキー標準化の加速:** FIDO2/WebAuthn ベースのパスキーが2026年にはパスワードのデフォルト代替として主流化しており、フィッシング耐性のある認証をユーザー体験を損なわずに実装できる。sumitsugiでも新規ユーザー登録・ログインフローにパスキー対応を優先検討すべき。

- **AI駆動の異常検知:** ログイン試行パターンや端末フィンガープリントをAIでリアルタイム分析し、クレデンシャルスタッフィングやボット攻撃を検知する仕組みが標準になりつつある。物件情報・個人情報を扱うプラットフォームとして、不正ログイン検知は法務確認前でも先行実装の価値が高い。

- **トークンのショートリブド化:** JWTなどのアクセストークンは有効期限を短く（15分程度）し、リフレッシュトークンのローテーション＋失効管理を組み合わせる設計がベストプラクティス化している。`src/contexts/auth-context.tsx` の認証フローを見直す際はこの点を優先的にチェックしたい。

- **ゼロトラスト前提のセッション管理:** IPアドレスやデバイス変更を検知した際に再認証を要求する「継続的認証」が標準化。前の住人・次の住人間で機密性の高い引き継ぎ情報をやり取りするsumitsugiの特性上、セッションハイジャック対策は優先度が高い。

- **サプライチェーン経由の認証情報漏洩対策:** npm/Bunパッケージ経由の依存関係汚染によるトークン窃取が2025〜2026年に増加傾向。`bun.lock`の定期監査とAPIキーの環境変数管理徹底（`.env.local`運用ルール）を継続すべき。

### 6. database architecture Prisma Supabase 2026

- **ポイント1（Prisma ORMのRust脱却とパフォーマンス改善）:** Prisma 6以降はクエリエンジンのTypeScript/WASM化が進み、Rustバイナリ依存が減ったことでコールドスタートが大幅短縮された。サーバーレス関数（Vercel Edge等）でのレイテンシ改善に直結するため、sumitsugiのようなNext.js App Router構成では特にメリットが大きい。

- **ポイント2（Supabaseのブランチング機能とプレビュー環境）:** Supabase Branching（DBのGitライクなブランチ運用）がGA後さらに安定し、PRごとに独立したPostgresインスタンス＋RLSポリシーをプレビューできるようになった。物件データのステータス変更（`draft`/`public`）のようなスキーマ変更を伴う機能でも、本番を汚さずに検証できる。

- **ポイント3（RLS + Prisma併用のベストプラクティス定着）:** PrismaはRow Level Securityを直接扱えないため、Supabase側でRLSを必須にしつつPrismaは`service_role`経由でアクセスし、アプリ層で認可を再検証する二重防御パターンが2026年時点の定番になっている。認証・決済系のセキュリティレビューで必ずチェックすべき点。

- **ポイント4（Prisma Postgres/Accelerateとエッジキャッシュ）:** Prisma Accelerateによるコネクションプーリングとグローバルキャッシュが標準化し、Supabase Pooler（PgBouncer）との二重プーリング構成が一般化。設定を誤ると接続枯渇やキャッシュ不整合を起こしやすいため、導入時はどちらか一方に統一するか役割分担を明確にすべき。

- **ポイント5（型安全なマイグレーション自動化）:** Prisma MigrateとSupabase CLIのマイグレーションを二重管理せず、Prisma側を単一の真実源（source of truth）にしてCIで`prisma migrate diff`を自動チェックする運用が主流化。`status: 'draft' | 'public'`のようなunion型変更時の全参照箇所チェック（standards.md記載のルール）とも相性が良く、型とスキーマのドリフトを防げる。

### 7. WebAssembly Rust performance 2026

**CTO視点: WebAssembly Rust performance 2026**

- **ポイント1（コンポーネントモデルの成熟）:** WASM Component Model仕様が安定期に入り、Rustクレートを言語非依存の再利用可能コンポーネントとして配布できるようになった。マイクロサービス的な設計をエッジ環境でも低オーバーヘッドで実現できる。
- **ポイント2（起動速度とコールドスタート）:** wasmtimeやWasmerのAOTコンパイル最適化により、コールドスタートがミリ秒未満に短縮され、サーバーレス/エッジ関数用途でRust+WASMがNode.js系ランタイムより有利になるケースが増えている。
- **ポイント3（SIMD・マルチスレッド対応の実用化）:** WASM SIMDとthreads提案がブラウザ・サーバー双方で広くサポートされ、画像処理や数値計算などCPU負荷の高い処理をブラウザ内でネイティブに近い速度で実行できるようになった。
- **ポイント4（バイナリサイズ最適化ツールの進化）:** `wasm-opt`やRustの`wasm-bindgen`ツールチェーンが継続的に改善され、ツリーシェイキングとデッドコード除去が高精度化。フロントエンド配信のペイロード削減に直結し、初期ロードのパフォーマンス指標を大きく改善できる。
- **ポイント5（実運用での採用判断基準）:** 本プロジェクトのような不動産マッチングプラットフォームでは、画像処理（物件写真の圧縮・変換）やPDF生成などCPU集約的な処理をクライアントサイドWASMにオフロードすることで、サーバーコストと待ち時間を同時に削減できる可能性がある — ただしNext.js 16との統合コストとチーム習熟度を踏まえ、まずは限定的なユースケースでのPoCを推奨。

### 8. Next.js App Router patterns 2026

- **ポイント1（Server ActionsとRSCの標準化）:** Next.js 16では Server Actions がデータ変更の第一級パターンとして定着し、APIルートを介さずフォーム送信やミューテーションを直接サーバー関数に委譲する設計が主流に。sumitsugiのような予約・引き継ぎフローでも、クライアント側の状態管理を減らしつつ型安全性を保てる利点が大きい。

- **ポイント2（Partial Prerendering の実用化）:** 静的シェルと動的コンテンツを1ページ内で共存させるPPRが安定版になり、物件一覧のようなSEO重視ページで「静的部分は即表示、価格や空室状況だけ動的フェッチ」という構成がデフォルト戦略になりつつある。

- **ポイント3（Cache Componentsとキャッシュ制御の明示化）:** `use cache` ディレクティブによりキャッシュ境界をコンポーネント単位で明示できるようになり、暗黙的なfetchキャッシュの挙動に悩まされるケースが減少。物件データのようにdraft/publicでキャッシュ要件が異なるデータには特に有効。

- **ポイント4（Route Handlersの薄型化）:** ビジネスロジックをServer Actions/RSCに寄せ、Route Handlersは外部Webhook受信やストリーミングなど本当に必要な場合のみに使う設計が推奨される傾向。認証・決済まわりの薄いAPI層設計と相性が良い。

- **ポイント5（型安全なミドルウェアとエッジ最適化）:** Middlewareでのセッション検証がより軽量化され、Edge Runtimeでの認証チェックとNode Runtimeでのビジネスロジックを明確に分離する構成が一般化。前の住人/次の住人といったロール別アクセス制御を持つsumitsugiでは、この分離がパフォーマンスとセキュリティ両面で有効。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1（コールドスタート最適化）:** Edge RuntimeはV8 isolateベースのため、Node.js Functionsと比べてコールドスタートが大幅に短い。ただしバンドルサイズ（1MB前後の制限）を意識し、不要な依存関係を減らすことがレイテンシ改善の鍵になる。

- **ポイント2（ミドルウェアの配置戦略）:** 認証チェックやA/Bテストの振り分けなど軽量な処理はMiddlewareでEdgeに寄せ、DB接続やSSRの重い処理はNode.js Functions（またはFluid Compute）に残すという役割分担が定石になっている。すべてをEdgeに寄せるとかえって複雑性が増す。

- **ポイント3（データアクセスのEdge対応）:** 通常のRDBMSはEdgeからの直接接続に向かないため、Vercel Postgres / Neon / PlanetScaleのようなHTTPベース・エッジ対応DBドライバー、またはKV/Edge Configをキャッシュ層として使う設計が前提になる。sumitsugiのような物件データ表示では、頻繁に変わらない一覧データをEdge Configやキャッシュに載せると効果的。

- **ポイント4（Fluid Computeとの使い分け）:** VercelのFluid Compute（Node.js関数の同時実行最適化）が登場したことで、「とりあえずEdgeに乗せる」から「ワークロード特性で使い分ける」への移行が進んでいる。ストリーミングSSRやリアルタイム性が必要な箇所のみEdgeを選定するのが2026年時点のベストプラクティス。

- **ポイント5（可観測性とコスト管理）:** Edge Functionsは実行時間課金の粒度が細かいため、Vercel Observability（OpenTelemetry連携）でレイテンシとコストを継続的に可視化し、リージョン偏重（アクセス元と実行リージョンのミスマッチ）を早期発見する運用が定着しつつある。

### 10. TypeScript type safety patterns 2026

- **型推論優先の設計:** `satisfies` 演算子やユーティリティ型を活用し、明示的なアノテーションを減らしつつ型安全性を保つパターンが主流化。過剰な型注釈は保守コストを増やすだけなので、推論に任せられる箇所は任せる方針が定着している。

- **スキーマ駆動のランタイム検証:** Zodなど（本プロジェクトでも標準化済み）でスキーマを1箇所に定義し、型とバリデーションを同時に導出する手法が標準に。API境界・フォーム入力での「型はあるがランタイムでは検証されない」という穴を塞げる。

- **Discriminated Unionによる状態管理:** `status: 'draft' | 'public'` のようなUnion型に対して、網羅性チェック（`never`型を使ったexhaustiveness check）をコンパイル時に強制するパターンが浸透。新しいステータス追加時の考慮漏れをビルド時に検出できる。

- **型とテストの二重防御:** 型安全性はロジックの正しさを保証しないため、型チェックとユニット/E2Eテストを組み合わせる「型はコンパイル時の契約、テストは実行時の振る舞い」という役割分担が明確化されつつある。

- **strictモードの段階的強化:** `strict: true` に加え `noUncheckedIndexedAccess` や `exactOptionalPropertyTypes` など、より厳格なコンパイラオプションを有効化するプロジェクトが増加。既存コードベースへの段階導入（ファイル単位のオプトイン）がベストプラクティスとして定着。
