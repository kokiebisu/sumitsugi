# CTO Knowledge - 2026-04-29

## Daily Update (2026-04-29)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチはサーバーコンポーネントに集約し、`'use client'`はインタラクティブなリーフコンポーネントのみに限定する。

- **Partial Prerendering (PPR) の本番適用:** Next.js 15以降で安定化したPPRにより、静的シェルを即時配信しつつ動的コンテンツをストリーミングする設計が標準となり、TTFBとLCPを同時に改善できる。

- **`use cache` APIによる細粒度キャッシュ制御:** 従来の`fetch`レベルキャッシュから、関数・コンポーネント単位でキャッシュ戦略を宣言的に指定できるようになり、過剰な再検証を防ぎつつ鮮度を保つ設計が可能になった。

- **Turbopack移行によるビルド高速化:** Next.js 15でTurbopackがデフォルトに近づき、大規模プロジェクトでのHMRが最大10倍高速化。ローカル開発体験の改善が生産性に直結する。

- **Image/Font最適化の自動化とCore Web Vitals:** `next/image`のサイズ自動最適化と`next/font`のフォントサブセット化は2026年でも必須。CLSゼロを担保するためレイアウトシフト原因を`@next/bundle-analyzer`で定期的に計測する習慣が重要。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度が競争優位に:** 2026年時点では、Suspense境界の設計がUXの決め手となっており、コンポーネント単位でのストリーミング制御により、TTFBを維持しつつLCPを大幅に改善できる。

- **PPR（Partial Prerendering）の本番採用が加速:** Next.js 15以降でstableになったPPRにより、静的シェルを即時配信しつつ動的部分をストリームする構成が標準化され、CDNキャッシュとSSRの両立が現実的になった。

- **Server Actionsとのストリーミング統合:** `useActionState` + Suspenseの組み合わせにより、フォーム送信後の結果もストリーミングで返せるようになり、ローディング状態の管理コードが大幅に削減されている。

- **エラー境界とストリーミングの共存が設計必須事項に:** ストリーミング中にサーバーエラーが発生した場合のフォールバック戦略（`error.tsx`の配置単位）を事前設計しないと、部分的に壊れたUIがそのまま表示されるリスクがある。

- **React 19のtransition APIとの連携でウォーターフォールを撲滅:** `use(promise)` + `startTransition`により、クライアント側でのデータフェッチウォーターフォールをRSCレイヤーに移譲できるため、バンドルサイズとネットワークラウンドトリップの両方を削減できる。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** tRPCはNext.js/Remixとの相性が良く、スキーマ定義なしにTypeScriptの型をフロントエンド・バックエンド間で共有できるため、小〜中規模チームでの採用が急増している。2026年時点でT3スタック（Next.js + tRPC + Prisma）はスタートアップのデファクトになりつつある。

- **GraphQLの適用範囲の明確化:** GraphQLは複数データソースの集約（BFF層）やモバイルアプリの柔軟なクエリに依然有効だが、「すべてにGraphQL」の反省からシンプルなCRUDにはREST/tRPCを選ぶ実用主義が広まっている。Federation v2（Apollo）によるマイクロサービス統合は大規模組織で標準化が進んでいる。

- **RESTはOpenAPI 3.1 + コード生成で復権:** OpenAPI仕様からTypeScriptクライアントを自動生成する（Orval, heyAPIなど）アプローチにより、RESTでも型安全性を担保できるようになり「tRPCが不要」な場面が増えた。外部公開APIはRESTが引き続き標準。

- **HTTPプロトコル層の進化:** HTTP/3（QUIC）の普及とともに、ストリーミングレスポンス（Server-Sent Events / ReadableStream）がREST・GraphQL両方で実用段階に入り、AIチャットのようなリアルタイム応答のユースケースをREST単独でカバーできるようになっている。

- **Contract-First設計の重要性:** チームが増えるほどAPI契約（スキーマ）を先に定義してからコードを書くContract-First開発が生産性を大きく左右する。tRPCはコードがスキーマを兼ねるため小チーム向き、一方GraphQL SchemaやOpenAPIは大チーム・複数チーム間の境界定義として機能する。

### 4. serverless edge computing 2026

- **エッジでのAI推論が主流化:** 2026年時点でVercel、Cloudflare Workers AI、Fastly Compute@Edgeがエッジ上でのLLM軽量推論（Whisper、LLaMAの量子化モデル等）をサポート。レイテンシ削減とデータローカリゼーション要件への対応が同時に達成できる。

- **WebAssembly（WASM）がエッジのデファクトランタイムに:** V8アイソレートに加え、WASMがポータブル・高速・安全なエッジ実行環境として定着。Rustや Go製バイナリをコンパイルしてデプロイする構成がエンタープライズで増加している。

- **エッジDBとの統合が成熟期へ:** Cloudflare D1、Turso（libSQL）、PlanetScale Boost等のエッジ対応データベースが普及し、「エッジで完結するフルスタック」が現実的に。ただしグローバル整合性のトレードオフ設計は依然として難所。

- **コールドスタート問題は事実上解消、課題はオブザーバビリティに移行:** ランタイムの改善でコールドスタートはほぼ無視できるレベルに。代わりに分散トレーシング（OpenTelemetry）やエッジ固有のデバッグ環境整備が開発生産性のボトルネックになっている。

- **コスト構造の再評価が必要:** リクエスト数課金から CPU時間・メモリ課金へのモデル変化が進み、従来のサーバーレスコスト試算が通用しないケースが増加。特にAI推論をエッジで回す場合はプロファイリングとキャッシュ戦略が費用対効果を左右する。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準採用:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の実質的な標準となり、フィッシング耐性とUX向上を同時に実現する。主要プラットフォーム対応が完成した今、新規プロダクトではパスワード認証を設計から除外すべきフェーズに入った。

- **セッション管理の短命化とリフレッシュトークンローテーション:** アクセストークンの有効期限を15分以内に抑え、リフレッシュトークンの使用ごとに再発行する「ローテーション戦略」が必須。トークン漏洩時の被害半径を最小化する設計が求められる。

- **デバイスバインディングと継続的認証:** 「ログイン時だけ認証」から「セッション中の継続的リスク評価」へシフト。デバイスフィンガープリントや行動分析を組み合わせ、異常検知時に再認証を要求するアダプティブ認証が標準化しつつある。

- **サプライチェーンリスクとしての認証ライブラリ管理:** next-authやPassportなどの認証ライブラリへの依存はサプライチェーン攻撃の主要な攻撃面。依存バージョンの固定（lockfileコミット）とSBOM（ソフトウェア部品表）の整備が監査対応上も不可欠になっている。

- **ゼロトラスト前提のAPIアクセス制御:** JWTのスコープ検証を各エンドポイントで実施し、「内部だから信頼」という前提を排除する。特にマイクロサービス間通信でもmTLSまたは短命サービストークンによる相互認証が求められる。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdgeランタイム対応:** Prisma 6ではEdge-compatibleドライバー（`@prisma/adapter-neon`, `@prisma/adapter-d1`など）が安定し、Vercel Edge FunctionsやCloudflare Workersでも直接DBアクセスが可能になった。コールドスタートを最小化するアーキテクチャ設計が現実解となっている。

- **Supabaseのローカルファースト開発:** `supabase db push` / `supabase db diff`によるマイグレーション管理が成熟し、ブランチごとにDBプレビュー環境を自動生成するワークフローがCIに統合しやすくなった。Prismaと組み合わせる場合はマイグレーション管理をどちらが担うか明確に決めることが重要。

- **Row Level Security（RLS）の設計を先行させる:** Supabase利用時はRLSポリシーを後付けすると大規模リファクタが発生する。スキーマ設計段階でマルチテナントの境界（`auth.uid()`ベースの分離）を定義し、Prismaのクエリはサービスロールキーでバイパスするか、ユーザースコープのクライアントで実行するかを明示的に決める。

- **PgBouncer / Supabase Transaction Poolerの必須化:** Next.jsのサーバーコンポーネント・API Routesでは短命なDB接続が大量発生するため、Supabaseの`[YOUR_PROJECT].pooler.supabase.com:6543`（Transaction mode）をPrismaの接続URLに使うことがプロダクション要件になっている。`?pgbouncer=true&connection_limit=1`の設定を忘れると接続枯渇が起きる。

- **Prisma Accelerateによるグローバルキャッシュ層:** Prisma Accelerateを挟むことでエッジロケーションにクエリ結果をキャッシュでき、読み取り多めのワークロード（物件一覧など）のレイテンシを劇的に削減できる。SupabaseのRealtimeと役割分担し、リアルタイム更新はRealtime・静的読み取りはAccelerateと棲み分けるのが2026年の標準パターン。

### 7. WebAssembly Rust performance 2026

- **Component Model の本格普及:** WebAssembly Component Model（wasm32-wasip2）が2025年末に安定化し、RustコンポーネントをJS/Python/Goと型安全にバインドできるようになった。モノリス分割の新選択肢として実用フェーズに入っている。

- **SIMD・スレッド対応の成熟:** Wasm SIMD命令とShared Memory Threadsが主要ブラウザで安定稼働し、Rustの`rayon`相当の並列処理が実現可能に。画像処理・暗号化・ML推論でネイティブの80〜95%の性能が出るケースも増えている。

- **WASIp2によるサーバーサイド活用拡大:** Cloudflare Workers・Fastly Computeに加え、WasmtimeベースのサーバーレスがAWS/GCPでも選択肢に。Rustで書いたWasmバイナリが数ミリ秒コールドスタートで動くため、エッジコンピューティングの実装言語としてGoと並ぶ位置づけになっている。

- **メモリ管理の課題は依然存在:** Rustの所有権モデルはWasmバイナリサイズ削減に有利だが、JS↔Wasm間のメモリコピーがボトルネックになりやすい。`wasm-bindgen`の最適化と`SharedArrayBuffer`活用の設計判断が性能の分かれ目。

- **ツールチェーンの成熟度:** `cargo-component`・`wasm-pack` v2・`Wasmtime`のAOTコンパイルが揃い、CI/CDへの組み込みが現実的になった。ただしデバッグ体験（DWARF over Wasm）はまだネイティブに比べて一歩劣るため、開発効率とのトレードオフを考慮すること。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年現在、App RouterのServer Componentsはクライアントバンドルサイズを大幅に削減する標準パターンとなっており、`'use client'`は状態・イベント処理が必要な葉コンポーネントのみに限定するのがベストプラクティス。

- **Partial Prerendering（PPR）の本番採用:** PPRが安定版となり、静的シェルと動的ストリーミングを同一ルートで共存させる設計が主流化。`<Suspense>`境界の設計がパフォーマンスの鍵となる。

- **Server Actions によるAPI Routes 削減:** フォームやミューテーションはServer Actionsで直接処理し、不要なAPI Routeを排除するパターンが定着。ただし、Zodによる入力バリデーションをAction内で必ず実施すること。

- **`use cache` ディレクティブの活用:** Next.js 15以降で導入された`use cache`により、関数・コンポーネント単位での細粒度キャッシュ制御が可能になり、`revalidateTag`と組み合わせたオンデマンド再検証が推奨パターン。

- **Parallel Routes & Intercepting Routes の設計:** モーダルやスライドオーバーのUI実装にIntercepting Routesを活用することで、URLの整合性を保ちつつSPA的なUXを実現できる。乱用すると`@slot`の複雑性が増すため、設計段階でのルート構造レビューが重要。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択戦略:** Node.js RuntimeとEdge Runtimeを用途別に使い分けることが重要——データベース接続や重い処理はNode.js、レイテンシ最優先のルーティング・認証・A/BテストはEdgeに割り当てることでコールドスタートを最小化できる。

- **Fluid Compute活用:** Vercelの「Fluid Compute」モデルにより、同一インスタンス上でのリクエスト並列処理が可能になり、アイドル時間のCPUコストが削減される——長時間処理よりも短時間・高並列なワークロードに合わせてFunction設計を最適化すべき。

- **キャッシュ戦略の精緻化:** `stale-while-revalidate`とEdge Cacheを組み合わせたISR（Incremental Static Regeneration）により、動的コンテンツでも実質的な静的配信に近いパフォーマンスを実現できる——`cache-control`ヘッダーの設計がスループット最大化の鍵。

- **バンドルサイズの厳格管理:** Edge Functionsには1MB（圧縮後）の制限があるため、`import`の tree-shaking 徹底と重いライブラリ（`moment.js`等）の排除が必須——`@vercel/next` のビルド解析で定期的にサイズ監視を組み込む。

- **Observabilityの内製化:** Vercel Analytics＋OpenTelemetryによるトレース連携で、Edge Function単位のP99レイテンシを可視化する——地域別コールドスタート頻度を計測し、トラフィックパターンに応じたウォームアップ戦略（Cron Jobによる定期ping等）を検討する価値がある。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `type UserId = string & { readonly _brand: 'UserId' }` パターンが広く普及し、プリミティブ型の混在バグを型レベルで防ぐ手法がチームの標準ガイドラインに組み込まれている。

- **satisfies 演算子の積極活用:** TypeScript 4.9以降の `satisfies` が2026年には定番となり、型推論を保ちながら型チェックを行うことで、`as` キャストの乱用を排除する設計が主流になっている。

- **Template Literal Types による API 契約:** REST エンドポイントやイベント名を `type Route = \`/api/${string}\`` で表現し、文字列ベースの API 契約を型安全に定義するパターンが定着している。

- **Zod + tRPC による実行時型保証の統合:** スキーマ定義を single source of truth とし、バリデーション・型推論・ドキュメント生成を一元化するアプローチが、境界値（API境界・DB境界）での型安全性の標準となっている。

- **`noUncheckedIndexedAccess` の全面有効化:** tsconfig の厳格オプションとして定着し、配列・オブジェクトアクセスで `T | undefined` を強制することで、実行時の `undefined` 参照エラーをコンパイル時に撲滅するプロジェクトが増加している。
