# CTO Knowledge - 2026-10-06

## Daily Update (2026-10-06)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 16ではPPRが安定化し、静的シェルを即時配信しつつ動的部分のみストリーミングできる。`properties/`一覧ページのような一覧+詳細構成では、静的な骨組みと動的な価格・空室情報を分離することでTTFBを大幅短縮できる。

- **`use cache` ディレクティブによる明示的キャッシュ制御:** これまでの暗黙的キャッシュから明示的な`use cache`指定に移行しており、`src/lib/data.ts`のデータ取得関数に粒度細かくキャッシュを付与することで、過剰な再検証や意図しないキャッシュミスを防げる。

- **Turbopackのビルド/devサーバー標準化:** Turbopackが本番ビルドでも安定版となり、`bun run build`の速度が大幅改善。CI時間短縮に直結するため、ビルド検証を必須とする現行フロー（CLAUDE.md記載のBuild Verification）のコストを下げられる。

- **React Compilerによる自動メモ化:** 手動の`useMemo`/`useCallback`チューニングが不要になりつつあり、物件一覧のフィルタリングUIなど再レンダリングが多いコンポーネントで恩恵が大きい。導入時はLintルールとの整合性確認が必要。

- **画像最適化とCore Web Vitals対応:** `next/image`のAVIF優先配信とレスポンシブ`sizes`指定の最適化が重要度を増しており、物件写真が多いUI（Airbnb風クリーンUI）ではLCP改善に直結する。モバイル回線での引越し費用・物件詳細ページの体感速度に特に効果が大きい。

### 2. React Server Components streaming 2026

- **Partial Prerendering(PPR)の本格普及:** Next.js 16ではPPRが標準パターン化し、静的シェルを即時配信しつつ動的部分だけをストリーミングで後追い表示する構成が主流に。初期表示速度(TTFB)とSEOを両立できるため、商品一覧ページなど「前の住人」情報を含む動的コンテンツがあるページで特に効果的。
- **`use()` フックとSuspense境界の粒度最適化:** Server Component内でのデータフェッチが`use()`に統一され、Suspense境界を細かく切ることでウォーターフォールを避ける設計が定着。物件詳細ページなら画像・価格・レビューを個別のSuspense境界にすることで、遅いAPIが他の表示をブロックしなくなる。
- **Server Actionsのストリーミングレスポンス対応:** フォーム送信後の結果をストリームで返しUIを段階的に更新するパターンが増加。問い合わせフォームや申込フローのような多段階フローでローディング体感を大幅改善できる。
- **Cache Components (`'use cache'`) との組み合わせ:** RSCストリーミングとキャッシュディレクティブを組み合わせ、再検証タイミングを細かく制御するのが2026年のベストプラクティス。頻繁に変わらないマスターデータ(物件の基本情報)はキャッシュしつつ、空室状況など鮮度が重要な部分だけ再フェッチする構成が効率的。
- **エッジランタイムでのストリーミング配信:** Vercel Edge/Cloudflare Workers等でRSCストリームをオリジンに近い場所から配信し、グローバルでのTTFBを縮小する動きが加速。多言語・多地域展開を見据えるなら早期に検証すべき領域。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの採用拡大:** TypeScriptフルスタック構成（Next.js×tRPC）では型安全性のオーバーヘッドが小さく、スキーマ定義とコードが一致するため、sumitsugiのようなモノレポ構成では今後APIレイヤーの有力な選択肢になる。GraphQLのような別言語でのスキーマ管理が不要な点が開発速度に直結する。

- **GraphQLはBFF層での使い分けが定着:** 複数クライアント（Web/モバイル）向けに柔軟なクエリが必要な場合はGraphQLが有利だが、単一フロントエンド中心のプロダクトでは過剰設計になりやすい。sumitsugiは現状Webのみなので、無理にGraphQLを導入する必要性は低い。

- **RESTはシンプルさと公開APIで依然強い:** 外部連携（決済、物件情報提供、将来的なサードパーティ連携）を見据えると、RESTのキャッシュ戦略やHTTPセマンティクスの分かりやすさは依然有効。内部通信はtRPC、外部公開APIはRESTという併用パターンが2026年のベストプラクティス。

- **Zodスキーマの一元化がトレンドの中心:** tRPC/REST問わず、Zodで入力検証とTypeScript型を同時に定義し、フロント・バックエンドで共有する設計が標準化しつつある。これはCLAUDE.mdの「Zodスキーマ at system boundaries」方針とも一致しており、既存スタックを変える必要はない。

- **Server Actions/RSCとAPI層の境界が曖昧化:** Next.js 16のServer Actionsが増えるほど、「APIを明示的に公開するか、内部関数として隠すか」の設計判断が重要になる。物件公開/下書き切り替えのような内部操作はServer Actionsで十分で、API Routeを増やす必要はない。

### 4. serverless edge computing 2026

- **ポイント1:** 2026年にはCloudflare Workers、Vercel Edge Functions、Deno DeployなどのV8 Isolate方式がコールドスタートをほぼゼロに近づけ、従来のコンテナ型サーバーレス（Lambda等）との性能差がさらに拡大している。レイテンシが重要なSSRやAPIルートはエッジ実行をデフォルト選択肢として検討すべき。

- **ポイント2:** エッジでのステート管理（Durable Objects、Cloudflare D1/KV、Vercel KV等）が成熟し、「エッジは読み取り専用」という制約が崩れつつある。sumitsugiのような物件検索・お気に入り機能はエッジKVでグローバル低遅延化できる可能性がある。

- **ポイント3:** AI推論のエッジ分散（小型モデルのオンデバイス/エッジ実行）がトレンド化しており、画像解析や簡易レコメンドをリージョン単位で処理するアーキテクチャが増えている。ただし本プロジェクトの規模ではまずNext.js on Vercelの標準エッジ機能で十分、オーバーエンジニアリングは避けるべき。

- **ポイント4:** マルチリージョンでのデータ一貫性（特にユーザー認証・決済系）はまだエッジの弱点。認証やDB書き込みは依然オリジン（単一リージョン）に寄せ、読み取り系・静的コンテンツのみエッジ化するハイブリッド構成が2026年の実践的ベストプラクティス。

- **ポイント5:** エッジランタイムはNode.js APIの一部が使えない（fsアクセス制限など）ため、ライブラリ選定時に「Edge Runtime対応」を事前確認する必要がある。本プロジェクトで将来エッジ化を検討する場合、依存パッケージの互換性チェックを早期に行うべき。

### 5. authentication security best practices 2026

- **パスワードレス認証の主流化:** FIDO2/WebAuthnによるパスキー認証がデフォルト選択肢となり、フィッシング耐性のある認証をユーザー体験を損なわずに実現できる。sumitsugiのようなtoCサービスでも、SMS OTPより実装コストを抑えつつセキュリティを高められる。

- **トークン管理の厳格化:** JWTのexpiry短縮とリフレッシュトークンのローテーション（rotation on use）が標準実装になっており、トークン漏洩時の被害範囲を最小化できる。Supabase/NextAuth系のライブラリでも標準サポートされているため、自前実装は避けるべき。

- **セッション固定攻撃・CSRF対策の継続的重要性:** OAuthやマジックリンク認証を使う場合でも、state/nonceパラメータの検証とSameSite Cookie設定は依然必須。新しい認証方式を導入しても基本的なOWASP対策を省略しない姿勢が重要。

- **段階的リスクベース認証（Adaptive MFA）:** ログイン元のデバイス・IP・行動パターンに応じてMFA要求を動的に変える手法が普及。不動産プラットフォームでは「前の住人」「次の住人」間の金銭的やり取りが絡むため、高リスク操作（決済・契約確定）時のみ追加認証を課す設計が有効。

- **サプライチェーン経由の認証情報漏洩対策:** 依存パッケージの改ざん（npm/bunパッケージ汚染）経由でのトークン窃取が増加傾向にあり、`bun.lock`の整合性チェックとSecret Scanning（GitHub Actions組み込み）を定常運用に入れることが必須になっている。

### 6. database architecture Prisma Supabase 2026

- **Prisma + Supabase の責務分離が定番化:** PrismaをORM/マイグレーション管理に、SupabaseのRLS（Row Level Security）を認可レイヤーに使う構成が主流になりつつある。アプリ層とDB層で認可ロジックが二重管理にならないよう、RLSポリシーを「正」としてPrisma側は型安全なクエリ記述に専念させるのが運用上シンプル。

- **Prisma Accelerate / Connection Poolingの重要性が増している:** Supabase(PostgreSQL)はサーバーレス環境からの直接接続数に弱いため、Prisma AccelerateやSupabaseのPgBouncer（Transaction/Session mode）を併用したコネクションプーリングが必須になっている。特にVercel等のサーバーレスデプロイでは、これを怠るとDB接続枯渇が本番障害の典型パターンになる。

- **スキーマドリフト対策としてPrisma Migrateの採用が加速:** Supabase StudioでUIから直接スキーマ変更すると、Prismaのスキーマ定義と実DBがズレる「スキーマドリフト」が起きやすい。`prisma db pull`での定期的な同期、またはマイグレーションは必ずPrisma経由で一元管理するルールを徹底するプロジェクトが増えている。

- **Supabase RealtimeとPrismaの組み合わせはまだ発展途上:** リアルタイム購読機能はSupabase Client（RealtimeチャンネルAPI）側で直接扱い、Prismaは書き込み・集計系のクエリに限定する「ハイブリッド構成」が現実的。Prisma単体でリアルタイム機能を代替しようとすると複雑化しやすい。

- **型安全性とマイグレーションの自動検証をCIに組み込む流れ:** `prisma validate` + `prisma migrate diff` をCIパイプラインに組み込み、本番適用前にスキーマ変更の影響範囲を可視化する運用が2026年時点でベストプラクティス化している。sumitsugiのような`status: 'draft' | 'public'`のようなUnion型を持つスキーマでは、この検証が型不整合の早期発見に直結する。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC（Wasm Garbage Collection）とcomponent model標準化が進み、RustはWasmターゲットのデフォルト言語という地位をさらに固めています。`wasm-bindgen`抜きでも軽量なFFIが可能になりつつあり、ビルド設定の複雑さが下がっています。

- **ポイント2:** `wasm32-wasip2`（WASI Preview 2）の普及により、ブラウザ外（サーバーレス・エッジ）でのRust Wasm実行が実用段階に入っています。弊社のような不動産プラットフォームでも、画像処理や料金計算ロジックをエッジで高速実行する選択肢が増えています。

- **ポイント3:** SIMD（`wasm32-simd128`）とマルチスレッド（`wasm-bindgen-rayon`）がブラウザ側で安定サポートされ、Wasmのネイティブ比パフォーマンスギャップが縮小（多くのベンチマークで80-95%程度）。クライアント側の重い計算処理（画像リサイズ、PDF生成等）をWasm化する価値が高まっています。

- **ポイント4:** バイナリサイズ最適化（`wasm-opt`, `twiggy`, LTO設定）がツールチェーンに統合され、ビルドパイプラインへの組み込みコストが下がっています。初回ロード時間がUXに直結するため、本プロジェクトのようなLCP重視のWebアプリでは導入判断の基準になります。

- **ポイント5:** 現状の実用ハードル：デバッグ体験（source map対応の不完全さ）とnpm/Bunエコシステムとのビルド統合の煩雑さが残存。導入する場合は「本当にネイティブJSでは不十分な処理か」を見極めるのが先決で、小規模チームでは保守コストが性能メリットを上回るケースが多い点に注意が必要です。

### 8. Next.js App Router patterns 2026

- **Server Actions のデファクト化:** フォームやMutation処理はAPI Routeを書かずServer Actionsに統一するのが主流になり、クライアント側のfetchロジックが大幅に減る。ただし楽観的UI更新（`useOptimistic`）とエラーハンドリングの設計を最初から組み込まないと、UXが壊れやすい。

- **Partial Prerendering (PPR) の本格運用:** 静的シェルを即時表示しつつ動的部分だけSuspenseでストリーミングする構成が標準化し、LCP改善とパーソナライズの両立が可能になった。導入時はキャッシュ境界（`loading.tsx`粒度）の設計が肝になる。

- **`cache()` / `unstable_cache` によるデータ取得の最適化:** Request Memoizationを前提に、同一リクエスト内の重複fetchをコンポーネント跨ぎで自動排除する設計が定着。DB直叩きのServer Componentが増え、BFF層を薄くできる反面、キャッシュ無効化（revalidateTag）の運用ルールを早期に決めておく必要がある。

- **Server/Client境界の明示的設計:** "use client" の濫用でバンドルが肥大化する失敗が多発したため、Composition Pattern（ClientコンポーネントにServerコンポーネントをchildrenで渡す）を前提とした設計レビューが必須化している。

- **Edge Runtimeの選択的採用:** 全ルートをEdgeにするのではなく、認証チェックやリダイレクトなどレイテンシが効く箇所だけEdge Middlewareに限定し、重い処理はNode Runtimeに残すハイブリッド構成が現実的なベストプラクティスとして定着している。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Vercel Edge FunctionsはV8 isolateベースで実行されるため、Node.js APIに依存しないコードを書くことがコールドスタート短縮の鍵。`fetch`や`Web Crypto API`などWeb標準APIへの移行で、Edge Runtime対応ライブラリを選定することがパフォーマンス最適化の基本となる。

- **ポイント2:** Next.js 16のPartial Prerendering (PPR)とEdge Functionsを組み合わせることで、静的シェルを即時配信しつつ動的部分のみEdgeでストリーミングできる。sumitsugiの物件一覧ページのような「公開物件」表示に適用すれば、TTFBを大幅に改善できる可能性がある。

- **ポイント3:** Edge Middlewareの実行回数課金モデルを考慮し、認証チェックなど全リクエストに適用するロジックは最小限に絞るべき。`matcher`設定で対象パスを絞り込み、不要なEdge実行コストを削減するのが実用的なコスト最適化策。

- **ポイント4:** Edge Functionsはリージョン分散実行されるため、DB接続はPrismaのEdge対応ドライバ（例: Neon/PlanetScaleのHTTPベース接続）やKVストア（Vercel KV, Upstash Redis）を使うことが前提となる。従来のTCPベースDB接続はEdge環境では使えない点に注意。

- **ポイント5:** 2026年時点でVercelはEdge FunctionsのオブザーバビリティをOpenTelemetry統合で強化しており、分散トレーシングが容易になった。本番導入前にレイテンシ計測を行い、Edge化すべきルートとServerless/Node.jsに残すルートを明確に切り分ける判断が重要。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** `satisfies`演算子とconst型パラメータの組み合わせが定着し、型推論を保ったままリテラル型の厳密性を保証するパターンが標準化している。Zodなど実行時検証ライブラリとの連携でAPI境界の型安全性がさらに強化されている。
- **ポイント2:** Template Literal Typesを活用したブランド型（Branded Types）が、IDやステータス文字列など「構造的には同じだが意味的に異なる」値の混在バグを防ぐ定番パターンとして普及している。本プロジェクトの`'draft' | 'public'`のようなUnion型管理にも応用価値が高い。
- **ポイント3:** TypeScript 5.x系でのコンパイラ最適化（インクリメンタルビルド・プロジェクト参照）が大規模モノレポでのビルド時間短縮に直結し、CIでの型チェックコストが運用上の重要な指標になっている。
- **ポイント4:** 型レベルでのユニットテスト（`expectTypeOf`やvitestの型テスト機能）がTDDサイクルに組み込まれ、ランタイムテストだけでは検出できない型の後退（regression）を早期に検知する運用が広がっている。
- **ポイント5:** AIコード生成が増える中、ユニオン型の網羅性チェック（exhaustiveness checking / `never`パターン）が「生成されたコードの型安全性を人間がレビューしなくても保証する」ガードレールとして重要性を増している。
