# CTO Knowledge - 2026-10-16

## Daily Update (2026-10-16)

### 1. Next.js performance optimization 2026

**CTO視点:** Next.jsパフォーマンス最適化の最新トレンドをまとめます。

- **ポイント1（Partial Prerendering / PPR）:** 静的シェルを即時配信しつつ動的部分をストリーミングする手法が標準化し、TTFBとLCPを大幅改善できる。sumitsugiの物件一覧・詳細ページのような静的+動的混在コンテンツに特に有効。
- **ポイント2（React Server Componentsの徹底活用）:** クライアントバンドルサイズを削減するため、`'use client'`境界を最小限に絞り込むことが重要。フォームやインタラクティブUI（物件検索フィルタ等）のみをクライアント化し、残りはサーバーコンポーネントに留める。
- **ポイント3（キャッシュ戦略の明示化）:** Next.js 16ではキャッシュ挙動がより明示的なAPI（`fetch`オプションや`revalidate`設定）で制御可能になり、暗黙的キャッシュによる事故を防げる。物件データのような更新頻度が異なるデータソースごとに適切なrevalidate値を設定すべき。
- **ポイント4（画像・フォント最適化の継続重要性）:** `next/image`のAVIF/WebP自動変換とレスポンシブサイズ指定、`next/font`によるフォントの自己ホスティングは依然LCP改善の基本。物件写真が多いUIでは画像最適化のROIが特に高い。
- **ポイント5（Edge/Node runtimeの使い分け）:** 認証チェックなど軽量処理はEdge Runtimeで低レイテンシ化し、DB接続を要する処理はNode Runtimeに残す、という使い分けがパフォーマンスとコストのバランスとして定着している。

### 2. React Server Components streaming 2026

- **ポイント1:** React 19/Next.js 16ではRSCのストリーミングがデフォルト挙動として定着し、`loading.tsx`やSuspenseバウンダリの粒度設計がLCP改善の主要レバーになっている。ページ単位ではなくコンポーネント単位でストリーミング境界を切ることで、初期表示を大幅に高速化できる。

- **ポイント2:** Server Actionsとストリーミングの組み合わせで「楽観的UI更新→サーバー確定」のパターンが標準化しつつあり、フォーム送信や一覧更新のUXが従来のクライアントフェッチより滑らかになる。物件検索・内見予約フローなど非同期性の高いUIに有効。

- **ポイント3:** キャッシュ戦略（`use cache`ディレクティブ、Partial Prerendering）とストリーミングの併用が鍵。静的部分を即時配信しつつ動的部分（在庫状況、価格変動）だけをストリームする設計で、CDNコストとTTFBを同時に改善できる。

- **ポイント4:** エッジランタイムでのRSCストリーミング対応が広がり、Vercel/Cloudflare等でグローバルなTTFB短縮が可能に。ただしNode.js専用ライブラリ（画像処理、PDF生成など）との互換性制約には注意が必要で、本プロジェクトのような業務ロジックが重い構成では混在運用の検討が要る。

- **ポイント5:** ストリーミングSSRはエラーハンドリングが複雑化する（部分的に描画済みのツリーに対するエラーバウンダリ設計）。本番導入時はPlaywright E2Eで「ストリーミング中断・リトライ」シナリオを明示的にテストすることが品質担保の実用的なポイント。

### 3. API design REST GraphQL tRPC 2026

- **スキーマファーストの統一:** tRPCがフルスタックTypeScriptプロジェクトで主流になり、GraphQLの型安全性のメリットをコード生成なしで実現。社内APIはtRPC、外部公開APIはRESTが2026年の標準的な分離パターン。
- **GraphQLの使い所が明確化:** モバイル/複数クライアントで帯優先度が異なるケースやBFF層での採用に収束し、単純なCRUD APIでのGraphQL採用は減少傾向。オーバーフェッチ問題がない単一クライアントならtRPC/RESTで十分。
- **OpenAPI 3.1 + AIエージェント対応:** LLMエージェントがAPIを自律的に呼び出す時代に入り、OpenAPIスキーマの質がエージェントの精度を直接左右する。関数呼び出し用のメタデータ（description充実、enum明示）への投資価値が上がっている。
- **Edge/サーバーレスでのレイテンシ最適化:** tRPCのバッチング＋Next.js Server Actionsの組み合わせで、クライアント-サーバー間のラウンドトリップを削減する設計が定番化。sumitsugiのようなNext.js App Routerプロジェクトでは、Server Actionsとtypedな内部APIの併用が実装コストを下げる。
- **バージョニングより後方互換性重視:** `/v1/`のようなURLバージョニングより、フィールド追加のみ・削除は非推奨期間を設けるスキーマエボリューション戦略が主流。破壊的変更が必要な場合のみ新エンドポイントを切る方針が運用コストを下げる。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** CloudflareのWorkers AIやVercel Edge Functionsなど、エッジランタイム上でLLM推論を直接実行する構成が2026年には一般化しており、ユーザーに近い場所でレイテンシを数十ms単位で削減できる。sumitsugiのようなB2C向けマッチング機能（物件検索・レコメンド）に組み込む際はコールドスタート対策とモデルサイズの制約を見極める必要がある。

- **コールドスタート問題の実質的解消:** V8 isolateベースのランタイム（Workers、Deno Deploy等）がコンテナ型サーバーレスを置き換えつつあり、ミリ秒未満の起動時間が標準になっている。Next.js 16のPartial Prerenderingと組み合わせると、動的な物件ページでもほぼ静的配信並みのTTFBが狙える。

- **データレイヤーのエッジ分散:** D1/Turso/PlanetScaleなどのエッジレプリケーション対応DBが普及し、read-heavyなワークロード（物件検索・絞り込み）をリージョン分散できるが、write-heavyな部分（予約・決済）は依然中央集権的な一貫性保証が必要で、ハイブリッド構成の設計判断が重要になる。

- **コスト構造の変化:** 従量課金のエッジ実行はトラフィックの急増に強いが、実行時間ベースの課金モデルのため、重い処理（画像生成・PDF生成など）をエッジに安易に載せるとコストが跳ねやすい。sumitsugiの引越しレポートPDF生成のような処理は、エッジではなくバックグラウンドジョブ/キュー型のアーキテクチャに残す判断が妥当。

- **ベンダーロックインへの警戒:** 2026年現在もエッジランタイムAPI（KV、Durable Objects、Queues等）はプラットフォーム間で非互換なため、移行コストを下げるには抽象化層（例: unstorage、itty-router等）を薄く挟む設計が実用的なリスク低減策になる。

### 5. authentication security best practices 2026

- **パスキー/FIDO2がデフォルト化:** パスワードレス認証（WebAuthn/パスキー）が業界標準になりつつあり、フィッシング耐性とUX向上を両立できる。本サービスでも「前の住人」「次の住人」間の本人確認フローに段階的導入を検討すべき。
- **デバイスバインド型セッション管理:** トークン窃取（session hijacking）対策として、JWTだけでなくデバイスフィンガープリントやDPoP（Demonstrating Proof of Possession）でセッションをデバイスに紐付ける手法が主流化している。
- **AIを使ったクレデンシャルスタッフィング対策:** 生成AIによるパスワードリスト攻撃・なりすましが高度化しており、レート制限だけでなく行動ベースの異常検知（ログイン時刻・場所・デバイスパターン）が必須になってきている。
- **ゼロトラスト前提のトークン短命化:** アクセストークンの有効期限を短くし、リフレッシュトークンのローテーション＋再利用検知（refresh token rotation with reuse detection）を組み合わせることで、漏洩時の被害範囲を最小化する設計が標準になっている。
- **サプライチェーン経由の認証リスク:** OAuthサードパーティ連携や外部SDKを通じた認証情報漏洩が増加しており、依存パッケージの認証関連コードは定期的なセキュリティレビュー（`/security-review`）の対象にすべき。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMの進化:** Prisma 6以降でRust非依存のクエリエンジン（TypeScript/WASMベース）への移行が進み、コールドスタートの高速化とサーバーレス環境（Vercel Edge等）との親和性が向上しています。Supabaseとの組み合わせでは、Prisma Accelerate等のコネクションプーリングを併用するのが実用上のベストプラクティスです。

- **Supabaseのサーバーレス最適化:** Supabaseの標準PostgreSQL接続はサーバーレス関数のコネクション数上限に弱いため、PgBouncer経由のTransaction Pooler利用が必須。Prismaの`directUrl`と`url`を分けてマイグレーション用と実行時用のコネクションを使い分ける設計が定石になっています。

- **Row Level Security (RLS) とORMの境界:** SupabaseのRLSはDB層でのセキュリティ強制に強力ですが、PrismaはRLSを認識しないため、認可ロジックをPrisma側にも二重実装するか、RLSに一本化するかの設計判断が重要です。sumitsugiのように`draft`/`public`のようなステータス制御がある場合、RLSポリシーとアプリ層のバリデーションを一致させる必要があります。

- **マイグレーション運用:** Prisma Migrateのマイグレーション履歴とSupabase CLIのマイグレーション管理が競合しやすく、どちらか一方（通常はPrisma Migrate）に一本化し、Supabase側のスキーマ変更はCLI経由でPrisma管理下に取り込む運用が推奨されます。

- **型安全性とZodとの連携:** Prisma生成型をベースにZodスキーマを自動生成する構成（`zod-prisma-types`等）により、DBスキーマ・API境界・フロントエンドの型を一貫させる流れが主流化しており、本プロジェクトの「システム境界でZod検証」という方針とも整合します。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WebAssemblyのコンポーネントモデル（Component Model）が2025-2026年で実用段階に入り、Rustのwasm-bindgen/wit-bindgenを使ったモジュール間連携が標準化されつつある。複数言語で書かれたWasmモジュールを型安全に組み合わせられるため、マイクロサービス的な分割がブラウザ外（サーバーレス、エッジ）でも現実的になっている。

- **ポイント2:** WasmGC（Garbage Collection提案）がブラウザ実装で成熟し、RustのようなGC不要言語は依然軽量ランタイムで優位を保つ。弊社のような不動産プラットフォームでは、画像処理や検索インデックスのようなCPU負荷の高い処理をRust+Wasmでクライアント側にオフロードし、サーバーコストを削減する選択肢が増えている。

- **ポイント3:** WASIのPreview2/P3移行により、ファイルI/Oやネットワークアクセスを含むサーバーサイドWasm（Fermyon Spin, Wasmtime）の実用性が向上。Next.jsのEdge RuntimeやCloudflare Workersとの統合も進み、SSR処理の一部をWasmに切り出すパフォーマンス改善の余地がある。

- **ポイント4:** SIMD命令とマルチスレッド（Wasm Threads）のサポートがブラウザ全体で安定し、Rustの`std::simd`やrayon相当のライブラリと組み合わせることで、画像圧縮・PDF生成（引越し費用計算書など）のクライアント処理を大幅高速化できる。現状のNext.js構成では未活用だが、重い計算処理があれば検討価値あり。

- **ポイント5:** バイナリサイズ最適化（wasm-opt, twiggy）とツリーシェイキングの精度向上で、Rust製Wasmモジュールの初期ロードコストが大幅低減。モバイル中心のUXを重視する前提なら、重い機能だけを遅延ロードするWasm分割戦略が初期表示速度とのトレードオフを解消する鍵になる。

### 8. Next.js App Router patterns 2026

- **ポイント1: Partial Prerendering (PPR) の標準化** — 静的シェルと動的コンテンツを1ページ内で併存させるPPRがApp Routerの主流パターンとなり、`loading.tsx`やSuspense境界の設計がパフォーマンス戦略の中心になっている。

- **ポイント2: Server Actions のセキュリティ境界強化** — Server Actionsが本番運用のデフォルトになる一方、認可チェック漏れがAPI相当の脆弱性になりやすく、各Actionで明示的な権限検証を行う規約が必須になっている。

- **ポイント3: キャッシュ戦略の明示化** — `fetch`の暗黙キャッシュから`cacheLife`/`cacheTag`等の明示的なキャッシュAPIへ移行する流れが強まり、再検証ロジックをコードで宣言する設計が推奨されている。

- **ポイント4: Route Handlersとミドルウェアの責務分離** — 認証・リダイレクトなど横断的関心事はEdge Middlewareに、ビジネスロジックはRoute Handlers/Server Componentsに分離するパターンが定着し、レイヤー混在によるデバッグコストを削減している。

- **ポイント5: 型安全なデータフェッチの徹底** — Server ComponentsでのデータフェッチにZodスキーマを組み合わせ、DBから画面表示まで型が切れない設計が標準化し、実行時エラーの早期検出につながっている。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1（コールドスタート最小化）:** Edge Runtime上のV8 Isolateは元来軽量だが、2026年はバンドルサイズの削減（Tree-shakingとDynamic Import Boundaryの明確化）がコールドスタート短縮の主戦場になっている。依存関係をNode Runtimeからの移植時に肥大化させないよう、Edge専用の軽量ライブラリ選定が重要。

- **ポイント2（Streaming + Partial Prerendering）:** Next.js 16のPPR（Partial Prerendering）とEdge Functionsを組み合わせることで、静的シェルを即時配信しつつ動的部分だけEdgeでストリーミングする構成が標準化しつつある。物件一覧ページのような「静的な骨組み＋動的な空室状況」構成に適用すれば初期表示速度（LCP）を大きく改善できる。

- **ポイント3（リージョン最適化とデータ局所性）:** Edge Functionsの実行リージョンをデータベース（PlanetScale/Neon等）のリージョンに揃える「Region Affinity」設計が重要性を増している。DBとEdgeのリージョンが不一致だとレイテンシのメリットが相殺されるため、sumitsugiのようなDB依存度が高いAPIルートはEdge化の前にデータ局所性を検証すべき。

- **ポイント4（料金・実行時間制限の見直し）:** Vercelの2026年プランでEdge Functionsの実行時間・メモリ制限が緩和傾向にあるが、依然としてCPU集約的な処理（PDF生成、画像処理など）はNode.js Runtime（Serverless Functions）に残すのが定石。「引越し費用」計算や契約書PDF生成など重い処理はEdge化対象から除外し、軽量なAPI（認証チェック、リダイレクト、A/Bテスト振り分け）に絞るべき。

- **ポイント5（Observability強化）:** Edge Middlewareの可視性向上のため、Vercel標準のOTel統合やWaitUntil APIを使った非同期ロギングが2026年の実用パターンとして定着。Edge特有のデバッグしにくさを補うため、本番導入前にリクエストトレーシングの仕込みをセットで行うことを推奨する。

### 10. TypeScript type safety patterns 2026

- **厳格な型チェックの標準化:** `strict: true`に加え`noUncheckedIndexedAccess`や`exactOptionalPropertyTypes`をデフォルト有効にするプロジェクトが増え、配列アクセスやオプショナルプロパティ由来のランタイムエラーを型レベルで事前に検出できるようになっている。
- **スキーマファーストな境界検証:** Zodなどのスキーマライブラリで「ランタイム検証＋型推論」を一体化し、API入出力やフォームなど外部境界で`z.infer`から型を生成するパターンが標準化し、手書き型とランタイム検証のズレを防いでいる。
- **テンプレートリテラル型とブランド型の活用:** URLパスやID文字列など「構造を持つstring」をテンプレートリテラル型で表現し、さらにブランド型（nominal typing）でプリミティブ型の取り違えを防ぐ設計が一般化している。
- **型推論を重視したユーティリティ関数設計:** `satisfies`演算子や条件型を活用し、明示的な型注釈を減らしつつ推論の正確性を保つコードベースが増え、過剰な型アノテーションによる保守コストを下げている。
- **Result型によるエラーハンドリングの型安全化:** `throw`に依存せず、成功/失敗を表すUnion型（Result/Either型）を関数の戻り値として明示し、呼び出し側に例外処理漏れを型チェックで強制するパターンが浸透している。
