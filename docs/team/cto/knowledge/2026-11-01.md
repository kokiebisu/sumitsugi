# CTO Knowledge - 2026-11-01

## Daily Update (2026-11-01)

### 1. Next.js performance optimization 2026

- **Turbopackのフル採用:** Next.js 16ではTurbopackが安定版としてデフォルトのビルド・開発サーバーとなり、Webpack比で大幅な高速化を実現。移行時は`next.config`のカスタムWebpack設定の互換性を事前に確認する必要がある。

- **Partial Prerendering (PPR) の本格運用:** 静的シェルを即時配信しつつ動的部分をストリーミングする手法が標準化しつつある。物件一覧ページのように「検索結果は動的だが枠組みは静的」なUIに特に有効で、TTFBを大幅に改善できる。

- **React Server Componentsでのデータフェッチ最適化:** クライアントへのJS転送量を減らすため、Server Componentsでのデータ取得とクライアントComponentsの境界設計が重要。`use cache`ディレクティブによる関数レベルキャッシングで、DBアクセスの重複を削減できる。

- **画像・フォント最適化の自動化強化:** `next/image`のAVIF/WebP自動変換と、`next/font`によるレイアウトシフト防止が標準化。物件写真が多いUIでは、Core Web Vitals（特にLCP）への影響が大きいため優先的に適用すべき。

- **計測駆動の最適化:** Vercel Speed InsightsやLighthouse CIをデプロイパイプラインに組み込み、バンドルサイズとCore Web Vitalsのリグレッションを自動検知する体制が2026年のベストプラクティス。感覚ではなく実測値で判断する文化が重要。

### 2. React Server Components streaming 2026

- **ポイント1:** Partial Prerendering（PPR）が本格的に実用フェーズに入り、静的シェルを即時配信しつつ動的部分だけをストリーミングする構成が標準化してきている。sumitsugiのproperties一覧やlisting詳細ページでも、価格・在庫などの動的データのみをSuspense境界で遅延させれば初期表示（LCP）を大幅改善できる。

- **ポイント2:** Server Actionsとストリーミングの組み合わせでウォーターフォール問題が解消されつつあり、フォーム送信後の楽観的UI更新とストリーミングレスポンスを併用するパターンが主流化している。引越し費用の見積もりフォームなど多段階フローに適用すれば、UX劣化なく体感速度を上げられる。

- **ポイント3:** キャッシュ戦略の複雑化が最大の運用課題になっている。`use cache`ディレクティブやタグベース再検証が普及し、RSCのキャッシュ境界設計を誤るとステールデータ表示のバグが起きやすい。物件ステータス（draft/public）の切り替えなど即時反映が必要な箇所は、キャッシュ無効化の設計を最初から明示すべき。

- **ポイント4:** エッジランタイムでのストリーミングSSRがコスト最適化の鍵になっており、Vercel Edge FunctionsやCloudflare Workers上でRSCペイロードを分割配信する構成がデフォルト選択肢に。ただしNode.js専用ライブラリへの依存があると移行コストが高いため、新規実装では早期にランタイム制約を確認すべき。

- **ポイント5:** ストリーミング中のエラーハンドリングが成熟し、`error.tsx`とSuspense boundaryの組み合わせでpartial failureを個別のUIセグメントに隔離できるようになった。決済や引き継ぎフローのような多段階処理では、一部コンポーネントの失敗が全体をブロックしないよう境界設計を細かく分けることが重要。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCの採用がTypeScriptフルスタック構成（Next.js App Router + Bun）で加速している。型安全性をスキーマ定義なしで確保できるため、本プロジェクトのような小〜中規模チームでは開発速度の面でRESTやGraphQLより優位。

- **ポイント2:** GraphQLは依然としてマルチクライアント（Web/モバイル/パートナーAPI）が絡む場合に強いが、N+1問題やキャッシュ戦略の複雑さから、社内向けAPIには過剰設計になりやすい。sumitsugiのような単一Webアプリ中心の構成では導入コストに見合わないケースが多い。

- **ポイント3:** RESTは依然として外部公開API（決済連携、不動産データ連携など将来の弁護士・特商法対応後の外部連携）の標準。OpenAPI/Zodスキーマとの統合でcontract-first開発がしやすく、サードパーティ連携が増えるフェーズでは最有力。

- **ポイント4:** 2026年のトレンドとして「BFF（Backend for Frontend）パターン + tRPC」の組み合わせが定着しつつある。Next.jsのServer Actions/Route Handlersと組み合わせることで、クライアント・サーバー間の型共有をRPC層で完結させ、API境界そのものを薄くする設計が主流になっている。

- **ポイント5:** どの方式を選ぶにせよ、Zodによる入力検証とエラーハンドリングの一貫性が重要（本プロジェクトのスタンダードにも合致）。API設計の議論よりも「境界でのバリデーション」と「型の一貫性」をどう保つかの方が、実務上のインパクトが大きい。

### 4. serverless edge computing 2026

**serverless edge computing 2026 — CTO視点**

- **ポイント1（コールドスタート実質ゼロ化）:** V8 isolateやWasmベースのランタイムが成熟し、コールドスタートが数ミリ秒〜ゼロに近づいている。レイテンシに敏感な物件検索・地図表示などのUXに直接効いてくるため、今後のAPI設計ではエッジファーストを前提にできる。

- **ポイント2（エッジでのステートフル処理）:** Durable Objects / KVやエッジネイティブDB（例: SQLite on edge）の普及で、従来は中央集権サーバーに閉じていたセッション管理や在庫ロックのようなステートフル処理もエッジで完結できるようになった。地理的に分散したユーザー（内見予約の同時アクセスなど）に強い。

- **ポイント3（AI推論のエッジ分散）:** 軽量LLM/埋め込みモデルのエッジ推論が一般化し、検索補完やレコメンドをユーザーに最も近いノードで処理できる。中央API呼び出しのコストとレイテンシを削減しつつ、物件マッチングのようなリアルタイム性が求められる機能に向いている。

- **ポイント4（Observabilityの分散化が課題）:** エッジ実行は分散トレーシングが難しく、従来のAPMツールでは可視性が落ちる。OpenTelemetry対応のエッジネイティブ計測を早期に組み込まないと、障害時の原因特定に時間がかかるリスクがある。

- **ポイント5（ベンダーロックインとコスト設計）:** Cloudflare Workers / Vercel Edge / Deno Deployなど主要プラットフォームでAPIの差異が大きく、移行コストが高い。Next.js 16のようなフレームワーク抽象化を活用しつつ、段階的にエッジへ移行する戦略（まずは静的コンテンツ・認証ミドルウェアから）が現実的。

### 5. authentication security best practices 2026

- **パスキー/FIDO2が主流化:** パスワード+SMS認証からWebAuthn/パスキーへの移行が2026年には標準となり、フィッシング耐性のある認証がユーザー向けサービスのデフォルト選択肢になっている。実装時はフォールバック手段（マジックリンク等）も用意し、デバイス未対応ユーザーを切り捨てない設計が重要。

- **トークン管理の厳格化:** JWTやセッショントークンの短命化・ローテーション、リフレッシュトークンのDB側での無効化対応（revocation list）が必須になっている。特に物件情報や個人情報を扱うsumitsugiのような住宅系プラットフォームでは、トークン漏洩時の被害範囲を最小化する設計（短いTTL + 再認証要求）が重要。

- **認可ロジックのサーバーサイド一元化:** クライアント側での権限チェックに依存せず、全APIエンドポイントでサーバーサイドの認可を徹底する「ゼロトラスト」的な実装が標準。`'draft'`/`'public'`のような物件ステータス制御は、UIの表示制御だけでなくAPI層でも必ず検証する必要がある。

- **レート制限とクレデンシャルスタッフィング対策:** ログイン試行への適応的レート制限、既知の漏洩パスワードチェック（HaveIBeenPwned API連携等）が2026年のベストプラクティス。ログイン・会員登録フォームには最低限このレベルの防御が期待される。

- **監査ログとセッション可視化:** ユーザー自身が自分のアクティブセッション・ログイン履歴を確認し、異常なセッションを強制終了できるUIが求められるようになっている。引越し費用決済など金銭が絡むフローでは、この透明性がユーザー信頼の獲得に直結する。

### 6. database architecture Prisma Supabase 2026

- **Prismaのクエリエンジン刷新:** Prisma 6以降、RustバイナリからTypeScript/WASMベースのクエリエンジンへ移行が進み、コールドスタートが大幅に改善。Vercel等のサーバーレス環境でのデプロイサイズ・起動速度の問題が実用上解消されつつある。

- **接続プーリングが依然最大の落とし穴:** SupabaseのPostgresは直接接続数に上限があるため、Prisma + サーバーレスの組み合わせでは必ずSupabaseのTransaction Pooler（PgBouncer経由、ポート6543）かPrisma Accelerateを使うべき。開発環境のDirect URLを本番にそのまま使うと即座にコネクション枯渇を起こす。

- **RLS（Row Level Security）とPrismaの相性:** SupabaseのセキュリティモデルはRLSが前提だが、PrismaはDB層のポリシーを認識しないため、アプリ層の権限チェックとRLSの二重管理になりがち。弁護士確認中の個人情報（前の住人の情報等）を扱う本プロジェクトでは、RLSをサーバーレスAPI経由のみで有効化し、Prismaのserviceロール接続は管理用APIに限定する設計が安全。

- **スキーマ変更はSupabase branching + Prisma Migrateの二層管理:** Supabaseのプレビューブランチ機能とPrisma Migrateのマイグレーション履歴を併用すると、どちらが正とするか曖恗になりやすい。`prisma/migrations`をSSOTとし、Supabase branchingはプレビュー環境の使い捨てDBとしてのみ使う運用がシンプル。

- **型安全性のエンドツーエンド化:** Prisma Client生成型をZodスキーマ（`zod-prisma-types`等）に連携させ、フォーム入力からDBまでの型を一本化するパターンが2026年の定石になっている。本プロジェクトの`src/lib/data.ts`周辺でも、物件ステータス(`'draft' | 'public'`)のようなUnion型をPrismaのenumとZodで二重定義せず単一ソース化すると保守性が上がる。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGCとComponent Modelの標準化が進み、Rust→Wasmのバンドルサイズと起動時間が大幅に改善。`wasm-bindgen`なしでも言語間連携がしやすくなり、マイクロフロントエンドやプラグインアーキテクチャに実用的な選択肢になっている。
- **ポイント2:** SIMD128とマルチスレッド（Wasm Threads + SharedArrayBuffer）がブラウザ主要エンジンで安定サポートされ、画像処理・動画エンコード・物理演算などCPU負荷の高い処理をネイティブの70-90%の速度でブラウザ実行できる。
- **ポイント3:** サーバーサイドでもWasmtime/Wasmerを使ったサンドボックス実行が普及し、Rust製Wasmモジュールはコンテナより軽量な分離実行環境として、エッジコンピューティング（Cloudflare Workers等）での採用が加速している。
- **ポイント4:** `cargo build --target wasm32-wasip2`によるWASI Preview2対応が安定し、ファイルI/Oやネットワークアクセスを含むアプリケーションもポータブルにWasm化できるようになった。
- **ポイント5:** Rustのコンパイル時最適化（LTO、`wasm-opt`との統合）が成熟し、開発者がパフォーマンスチューニングに費やす時間が削減。sumitsugiのような物件検索・フィルタリングのような計算負荷のあるクライアントサイド処理に、将来的な最適化余地として検討価値がある。

### 8. Next.js App Router patterns 2026

**Next.js App Router Patterns 2026 — CTO視点**

- **ポイント1: Partial Prerendering (PPR) の本格運用:** 静的シェルと動的コンテンツを1ページ内で混在させるPPRがstable化し、ダッシュボードや商品一覧ページで「ヘッダーは静的・データ部分はストリーミング」という構成が標準パターンになっている。弊社の`properties/`一覧でも導入すればTTFBを大幅改善できる。
- **ポイント2: Server Actionsのセキュリティ境界明確化:** Server Actionsは便利だが「隠れたAPIエンドポイント」として扱われがちで、認可チェック漏れが頻発する脆弱性パターンとして指摘されている。`auth-context.tsx`から取得するセッション検証を各Server Action内で必須化するルール化が推奨される。
- **ポイント3: `use cache` ディレクティブによる明示的キャッシュ制御:** Next.js 15以降で導入された`use cache`が2026年には主流となり、暗黙的なフルルートキャッシュへの依存から、関数単位での明示的キャッシュ指定へシフトしている。`data.ts`のデータ取得層に適用すると、キャッシュの意図が追いやすくなる。
- **ポイント4: Server/Client Componentsの境界設計がパフォーマンスの肝:** "use client"の濫用によるバンドル肥大化が依然多くのプロジェクトの課題で、Client Componentはインタラクティブな葉(leaf)ノードに限定し、できるだけツリーの上流はServer Componentに留める設計原則が再評価されている。
- **ポイント5: Edge Runtimeの適用範囲の見極め:** Edge Runtimeは低レイテンシだがNode.js APIの制約が多く、認証・決済など複雑なロジックを持つ処理はNode.js Runtimeに留め、静的コンテンツ配信や軽量なリダイレクト処理のみEdgeに寄せるハイブリッド戦略が実務的なベストプラクティスとして定着している。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Functionsの実行時間制限緩和とストリーミングSSR最適化が進み、Time to First Byteを数十ms単位で削減できるようになった。重い処理はEdge Middlewareで早期リダイレクト・パーソナライゼーションに限定し、本体処理は分離するのが鉄則。

- **ポイント2:** Edge RuntimeとNode.js Runtimeの機能差が縮小し、一部のDB接続やcryptoライブラリもEdgeで動くようになったが、コールドスタート・バンドルサイズ制約は依然あるため、依存パッケージの軽量化（tree-shaking可能なライブラリ選定）が優先度高。

- **ポイント3:** Vercel Data CacheとISRの組み合わせでEdgeキャッシュヒット率を最大化し、オリジンへのリクエストを削減するのが2026年のベストプラクティス。sumitsugiのような物件一覧系ページはstale-while-revalidate戦略で「公開」ステータス変更時のみ再検証をトリガーする設計が有効。

- **ポイント4:** リージョン選択（Edge Network Regions設定）を東京優先にピン留めすることで、日本国内ユーザー向けレイテンシを安定化できる。グローバル分散よりレイテンシ予測性を取るべきフェーズ（ベータローンチ前）には明示的リージョン固定が推奨。

- **ポイント5:** 観測性ツール（Vercel Observability Plus）がEdge Functions単位でのコールドスタート・エラー率を可視化できるようになり、本番投入前のE2Eテストに加えてEdge関数単位のモニタリング設定をCI/CDに組み込むことが実質標準になっている。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** テンプレートリテラル型とConst Type Parametersの活用が標準化し、API routeのパスパラメータやクエリ文字列を文字列操作レベルで型安全に検証できるようになった。実務では`Record`の雑な利用を減らし、コンパイル時にルーティングミスを検出できる。
- **ポイント2:** Zodなど実行時スキーマからの型推論（`z.infer`）が「型は手動定義、検証は別」という二重管理を解消する主流パターンとして定着し、システム境界（API入出力、環境変数）での型と実行時検証の不一致バグを構造的に防げる。
- **ポイント3:** `satisfies`演算子の普及により、型の広がりを抑えつつ元のリテラル型情報を保持できるようになり、`status: 'draft' | 'public'`のようなUnion型をオブジェクトリテラルで使う際の意図しない型拡大を防止できる。
- **ポイント4:** TypeScriptのビルド速度改善（増分コンパイル・プロジェクト参照の最適化）が進み、モノレポや大規模コードベースでも型チェックをCIのボトルネックにせず、`bun run build`レベルの型検証をPRごとに現実的に回せるようになった。
- **ポイント5:** Branded Types（nominal typing）がID系の値（`UserId`、`PropertyId`など）の取り違えを防ぐパターンとして一般化し、構造的部分型のTypeScriptでも意味的に異なる文字列/数値を型レベルで区別できるようになった。
