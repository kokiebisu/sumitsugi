# CTO Knowledge - 2026-07-16

## Daily Update (2026-07-16)

### 1. Next.js performance optimization 2026

- **Turbopackの本格採用:** Next.js 16でTurbopackがビルド・開発サーバーのデフォルトになり、Webpack比で大幅なビルド高速化が実現。大規模プロジェクトでのCI時間短縮に直結するため、まだ移行していなければ優先度高。
- **Partial Prerendering (PPR) の安定化:** 静的シェルと動的コンテンツを1つのルートで組み合わせられるようになり、TTFBを維持しつつパーソナライズされたUIを提供可能。物件一覧ページのような「静的な枠+動的な検索結果」構成に相性が良い。
- **React Compilerによる自動メモ化:** `useMemo`/`useCallback`の手動最適化が不要になりつつあり、再レンダリングコストが自動的に削減される。コードレビュー観点でも過剰な最適化コードを書かない方針に転換すべき。
- **Server Componentsのキャッシュ戦略の明確化:** `use cache`ディレクティブやキャッシュタグによる細粒度の再検証が主流化し、データフェッチのウォーターフォール問題が緩和。listing/propertiesページのデータ取得見直しの余地あり。
- **画像・フォント最適化の自動化強化:** `next/image`のAVIF優先配信やフォントのセルフホスティングがデフォルト挙動として強化され、Core Web Vitals（特にLCP）改善の追加設定が最小限で済むようになっている。

### 2. React Server Components streaming 2026

- **ポイント1:** RSCのストリーミングは`loading.tsx`やSuspenseによる段階的レンダリングが標準化し、TTFBを保ったままデータ取得の遅いコンポーネントだけを後追いでハイドレートできる。物件詳細ページのような重いデータ（口コミ・周辺情報など）を後回しにして初期表示を高速化する設計が定石になっている。

- **ポイント2:** Server ActionsとRSCストリーミングの組み合わせで、フォーム送信後の再検証（`revalidatePath`/`revalidateTag`）がより細粒度になり、内見予約フローのような多段階フォームでもページ全体を再取得せずに部分更新できる。

- **ポイント3:** キャッシュ戦略（`use cache`ディレクティブ系）の成熟により、静的に近い一覧ページ（物件検索結果など）とパーソナライズが必要な部分（お気に入り状態、ログイン情報）を同一ツリー内で分離しつつストリーミングできるようになってきた。パフォーマンスとパーソナライズの両立がしやすい。

- **ポイント4:** エラーバウンダリとストリーミングの相性が改善し、一部コンポーネントの取得失敗が全体のレンダリングをブロックしない設計が容易になった。外部API（地図・決済連携など）への依存箇所を局所化しておくと障害時の影響範囲を最小化できる。

- **ポイント5:** ストリーミングSSRはWaterfall（直列的なデータ取得の連鎖）を誘発しやすいため、依存関係のないデータ取得は並列化し、依存があるものだけ意図的にネストするという設計判断が重要。特に物件一覧＋フィルタのような複合UIでは並列取得を意識しないとかえって体感速度が悪化するケースがある。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCのような型安全なRPCアプローチが、TypeScriptモノレポ構成のプロダクトで急速に採用が進んでいる。フロントエンドとバックエンドで型を共有できるため、スキーマ定義とコード生成のオーバーヘッドを削減でき、開発速度が重視される初期フェーズのプロダクトに適している。

- **ポイント2:** GraphQLは依然として複雑なデータ取得要件（ネストしたリレーション、モバイル/Web間での取得粒度の違い）がある場合に強みを持つが、N+1問題やキャッシュ設計の複雑さから、小〜中規模チームでは運用コストが見合わないケースが増えている。

- **ポイント3:** RESTは依然として外部公開APIやサードパーティ連携のデファクトスタンダードであり、OpenAPI仕様書の自動生成・検証（Zodスキーマからの型生成など）と組み合わせることで、型安全性の弱点を補完できる。

- **ポイント4:** 2026年現在、単一のAPIパラダイムに固執するより、内部通信（社内フロントエンド⇔BFF）はtRPC、外部公開APIはREST+OpenAPIというハイブリッド構成が一般的になっており、境界を明確に設計することが重要。

- **ポイント5:** Server ActionsやRSC（React Server Components）の普及により、Next.jsのようなフルスタックフレームワークでは「クライアント⇔サーバーAPI」自体を意識しない設計も増えており、APIレイヤーの必要性そのものを見直す動きがある。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG/WinterTC準拠のランタイム（Cloudflare Workers, Vercel Edge, Deno Deploy）が2026年には事実上の標準APIセットに収束し、Web標準API（fetch, Request/Response）ベースで書けばベンダーロックインが大幅に減少しています。移行コストを見積もる際はこの点を前提にできます。

- **Cold Startのほぼ解消:** V8 IsolatesベースのエッジランタイムはコールドスタートがミリSEC単位まで低下し、SSRやAPI Routeをエッジで動かすハードルが実質なくなりました。Next.js 16のApp RouterでもEdge Runtimeを選択肢として本番投入しやすくなっています。

- **エッジDBの実用化:** D1, Turso, PlanetScale等の分散SQLiteレプリケーションがエッジ近接での読み取りレイテンシを劇的に改善し、「エッジは静的コンテンツのみ」という制約が崩れつつあります。物件検索・一覧表示のような読み取り中心のページはエッジDB化の検討価値があります。

- **コスト構造の逆転リスク:** リクエスト数課金モデルのため、トラフィックパターン次第では従来のサーバーレス（Lambda等）よりコストが跳ね上がるケースがあり、導入前にトラフィック予測とコストシミュレーションが必須です。

- **観測性の追いつき遅れ:** 分散エッジ環境ではトレーシング・ログ集約が依然として弱く、OpenTelemetry対応が進んでいるものの、本番導入時は可観測性ツールの検証を先に行うべきです。

### 5. authentication security best practices 2026

- **ポイント1（パスキー標準化）:** パスワードレス認証（FIDO2/WebAuthn）がデフォルトの選択肢になり、SMS OTPは中間者攻撃・SIMスワップに脆弱なためフォールバック専用に格下げすべき。実装コストは初期は高いが、フィッシング耐性とサポートコスト削減で長期的にペイする。

- **ポイント2（トークンのライフサイクル管理）:** JWTを使う場合はアクセストークンを短命化（15分以内）し、リフレッシュトークンはローテーション＋再利用検知（reuse detection）を必須にする。長寿命トークンの漏洩は「前の住人」の個人情報流出に直結するため、本サービスのような機微データを扱うプラットフォームでは特に重要。

- **ポイント3（多層防御としてのRBAC/RLS）:** アプリ層の認可チェックだけでなく、DB層（Row Level Security）でも同じルールを二重に強制する。バグや実装漏れによる水平権限昇格（他ユーザーの物件情報閲覧など）を防ぐ最後の砦になる。

- **ポイント4（監査ログとセッション管理の可視化）:** ログイン試行・セッション作成/失効をユーザー本人が確認できるUI（「ログイン履歴」画面）を提供し、異常検知時は自動でセッション無効化する。個人情報を含む物件データを扱う以上、法務確認後のプライバシーポリシーとも整合させる必要がある。

- **ポイント5（Zodによる境界検証との連携）:** 認証まわりのAPIエンドポイントは特に、Zodスキーマでの入力検証とレート制限（ブルートフォース対策）をセットで実装する。既存の`.claude/rules/standards.md`の「入力検証はZodで」という方針を認証層にも一貫して適用する。

### 6. database architecture Prisma Supabase 2026

- **RLSとPrisma併用の定石化:** Supabaseの Row Level Security とPrismaのクエリ層を組み合わせる際は、Prisma Client自体がRLSコンテキストを認識しないため、`auth.uid()`をセッション変数として明示的に渡すミドルウェア層が2026年時点でも必須のベストプラクティスです。

- **コネクションプーリングの重要性:** サーバーレス環境（Vercel等）からSupabaseへ接続する場合、PrismaのDirect ConnectionではなくPgBouncer経由のTransaction Pooler（ポート6543）を使い、`pgbouncer=true`をDATABASE_URLに付与しないと接続枯渇が起きやすい点は依然として要注意です。

- **Prisma Migrateとダッシュボード変更の競合:** SupabaseダッシュボードでスキーマをGUI編集するとPrisma Migrateの履歴と乖離しやすいため、`prisma db pull`で定期的にスキーマドリフトを検知し、マイグレーションはPrisma側に一本化する運用ルールを徹底すべきです。

- **Edge Functions + Prisma Accelerateの組み合わせ:** SupabaseのEdge Functions（Deno）からはPrisma標準のNode.jsドライバが動かないため、Prisma AccelerateまたはPrisma経由のHTTPベースクエリを使う構成が2026年の主流パターンになっています。

- **型安全性とRLSポリシーの二重管理コスト:** PrismaスキーマとSupabaseのRLSポリシーは別々に定義・管理されるため、`sumitsugi`のようにdraft/publicステータスでアクセス制御が絡む場合は、両者の整合性をCIで検証する仕組み（例: ポリシーのSQLをテストで実行）を入れておくと事故を防げます。

### 7. WebAssembly Rust performance 2026

- **WASI Preview 2とComponent Model成熟:** WASIプレビュー2の普及により、異なる言語で書かれたWasmコンポーネント間の相互運用が実用段階に入り、Rust製の高性能コンポーネントを他言語アプリに組み込みやすくなった。sumitsugiのような画像処理・PDF生成の重い処理をWasmモジュール化する際の設計選択肢が広がっている。

- **SIMD128とマルチスレッド対応の標準化:** WebAssembly SIMDとシェアードメモリ+Atomicsがブラウザ全体でベースライン対応になり、Rustコンパイラ側の最適化も進んで、画像リサイズやPDFレンダリングなどCPU負荷の高い処理をネイティブに近い速度でクライアントサイド実行できる。

- **バイナリサイズ削減が依然として最大の課題:** `wasm-opt`や`twiggy`によるサイズ解析、`wee_alloc`に代わる軽量アロケータの採用など、Rust特有のランタイムオーバーヘッド削減が2026年も継続的な最適化テーマ。初回ロード体験を左右するため、物件写真アップロード機能など高頻度で使う機能ほど投資対効果が高い。

- **サーバーサイドWasm(Wasmtime/Wasmer)によるサンドボックス実行の実用化:** Next.jsのAPI Routeやedge関数からRust製Wasmモジュールを安全に呼び出すパターンが一般化し、ユーザー入力を扱う変換処理（画像変換、契約書テンプレート生成等）をプロセス分離しつつ低レイテンシで実行できるようになった。セキュリティとパフォーマンスの両立という観点で導入価値がある。

- **ツールチェーンの簡素化:** `wasm-bindgen`のビルド時間短縮とcargo-generateテンプレートの充実により、Rust→Wasmの導入コストが下がった一方、TypeScript側の型安全な連携（`.d.ts`自動生成）が標準化されつつある。既存のTypeScript中心のスタックに部分的にRust/Wasmを組み込む際の統合コストが小さくなっている。

### 8. Next.js App Router patterns 2026

- **ポイント1（Server Components前提の設計）:** データ取得はデフォルトでServer Componentsに寄せ、`use client`境界を末端の小さなインタラクティブ部品に限定することで、バンドルサイズとハイドレーションコストを最小化するのが2026年時点の主流パターン。UIの状態管理が必要な箇所だけをクライアント化する「Client Islands」的な粒度設計が重要。

- **ポイント2（Partial Prerendering / PPRの実用化）:** 静的シェルを即座に返しつつ動的部分をストリーミングするPPRが安定運用フェーズに入り、`loading.tsx`とSuspense境界の設計次第でLCP・TTFBが大きく変わる。sumitsugiの物件一覧・詳細ページのような「静的な骨格＋動的な在庫情報」構成に適用余地が大きい。

- **ポイント3（Server Actionsのセキュリティ境界）:** フォーム送信・決済連携をServer Actionsに寄せる設計が一般化した一方、`'use server'`関数は事実上の公開APIエンドポイントであるためZodによる入力検証と認可チェックを関数内で必ず行う必要がある。標準規約（standards.md）のZod境界検証方針とも一致する。

- **ポイント4（キャッシュ戦略の明示化）:** Next.js 15以降でGET Route Handlers・`fetch`のデフォルトキャッシュ挙動が変わったため、`revalidate`・`cache: 'no-store'`・`unstable_cache`を明示的に指定しないと意図しないstaleデータが露出するリスクがある。物件のdraft/public切り替えのようなステータス変化を扱う箇所は特に注意。

- **ポイント5（型安全なルーティング）:** App Routerの`typedRoutes`とZod/TypeScript連携によるルート・パラメータの型安全性がデファクト化しており、`src/app/properties/[id]`のような動的セグメントでのランタイムエラーをビルド時に検出できる。ビルド健全性（build integrity）を重視する現行の開発規約とも相性が良い。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1（Fluid Compute考慮の設計）:** Vercelは2025年にFluid ComputeをEdge/Serverless双方の既定実行モデルに統合しており、同一インスタンス内で複数リクエストを処理しコールドスタートとコンピュートコストを削減できる。sumitsugiのようなSSR中心のNext.js 16アプリでは、DBコネクションの使い回しやin-memoryキャッシュの設計を「1リクエスト=1インスタンス」前提から見直す必要がある。

- **ポイント2（Edge Middlewareの責務を最小化）:** Edge RuntimeはV8 isolateベースで軽量だがNode.js APIの制約が大きいため、認証チェックやリダイレクトなど軽量処理に限定し、DB書き込みや重い処理はRegional/Node.jsランタイムに委譲するのがベストプラクティス。物件検索やお問い合わせフォームのバリデーションはEdgeに置かず、middleware.tsは認証ガード（auth-context.tsx連携）に専念させるべき。

- **ポイント3（Partial Prerendering + Edgeキャッシュの組み合わせ）:** Next.js 16のPPR（Partial Prerendering）とVercelのEdge Cache/ISRを組み合わせることで、物件一覧の静的シェルを即座に配信しつつ、価格や空室状況など動的部分のみEdgeでストリーミングできる。property listing系ページ（`src/app/properties/`）に適用すればTTFBを大幅短縮できる。

- **ポイント4（リージョン選択とデータローカリティ）:** Edge Functionsは全世界のPoPで実行されるが、DB（Supabase/Postgres想定）が単一リージョンにある場合はEdge実行がかえってレイテンシを悪化させることがある。国内向けサービスであるsumitsugiでは`fra1`/`hnd1`等のリージョン固定や、DB近接のRegional Functionsを優先し、Edgeは真にグローバル・低レイテンシが必要な処理（IPベースの表示切替等）に限定すべき。

- **ポイント5（可観測性とコスト管理）:** VercelのEdge Functionsは実行時間・帯域で課金されるため、2026年時点ではOpenTelemetry統合によるEdge実行のトレーシングが標準化されつつある。本番ローンチ前に`Vercel Observability`でEdge関数のレイテンシ分布とエラー率を計測し、法務確認完了後のベータローンチ時点でコスト予測を立てておくことを推奨する。

### 10. TypeScript type safety patterns 2026

- **ポイント1（`satisfies`とテンプレートリテラル型の徹底活用）:** `as const satisfies` パターンで型推論を保ったままリテラル型を固定する書き方が主流化しており、`seller`/`draft`/`public`のようなUnion型の値を扱う際に型の取りこぼしをコンパイル時に検出できます。

- **ポイント2（Zodスキーマからの型導出を単一情報源にする）:** バリデーションスキーマ（Zod）から`z.infer`で型を導出し、フォームや境界のバリデーションと型定義を二重管理しない構成が2026年時点でのベストプラクティスです。物件ステータスのようなUnion型を変更する際も、スキーマ側の修正だけで型・バリデーション両方に反映されます。

- **ポイント3（Discriminated Unionによる状態管理の厳密化）:** `status: 'draft' | 'public'`のような単純なUnionよりも、関連フィールドをまとめたDiscriminated Union（例: `{status: 'draft', publishedAt: null} | {status: 'public', publishedAt: Date}`）にすることで、「公開済みなのに公開日がない」といった不整合状態を型レベルで排除できます。

- **ポイント4（`noUncheckedIndexedAccess`と厳格な`tsconfig`設定）:** 配列・オブジェクトアクセス時の`undefined`混入をコンパイラに強制検出させる設定が標準化しつつあり、実行時エラー（特にAPIレスポンスや検索結果配列の扱い）を未然に防げます。

- **ポイント5（型エラーはCIのビルドステップで必ず検出する運用）:** ESLint・単体テストだけでは型不整合を見逃すケースがあるため、`bun run build`をCIパイプラインに必ず組み込み、Union型の変更時は全使用箇所をgrepで洗い出す運用ルールが事故防止に直結します。
