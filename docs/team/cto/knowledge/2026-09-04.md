# CTO Knowledge - 2026-09-04

## Daily Update (2026-09-04)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Prerendering の本格運用）:** Next.js 16ではPPRが安定版となり、静的シェルを即座に返しつつ動的部分をストリーミングできる。物件一覧ページのような「検索フィルタは動的、レイアウトは静的」という構成に最適で、TTFBを大幅に短縮できる。

- **ポイント2（React Compilerによる自動メモ化）:** React Compilerがデフォルト有効になり、`useMemo`/`useCallback`の手動最適化が不要に近づく。ただし依存配列の暗黙的な誤りを検知しづらくなるため、ESLintの`react-compiler`プラグインを併用し、リストレンダリング（物件カード等）で意図せぬ再レンダリングが混入していないか定期チェックが必要。

- **ポイント3（画像・アセット最適化のCDN境界での実施）:** `next/image`のオンデマンド最適化はVercel外だとコスト・レイテンシが読みにくいため、物件写真のような大量画像はビルド時プリ最適化+CDNキャッシュの組み合わせが2026年のベストプラクティス。AVIF優先、レスポンシブ`sizes`属性の徹底も引き続き重要。

- **ポイント4（Server Actionsのキャッシュ戦略の複雑化）:** `revalidateTag`/`revalidatePath`の粒度設計を誤ると、内見予約や物件ステータス更新（draft⇔public）のような書き込み系操作でキャッシュ不整合が起きやすい。タグベースの細粒度invalidationを設計段階で明示し、E2Eテストでキャッシュ更新の反映を検証すべき。

- **ポイント5（バンドルサイズより「初回インタラクション遅延」を計測対象に）:** Core Web Vitalsの重心がINP（Interaction to Next Paint）に完全移行しており、単純なバンドルサイズ削減よりも「クリック後の応答性」を計測・最適化する方が効果が大きい。認証・お気に入り登録など頻繁なユーザー操作のあるコンポーネントから優先的にプロファイリングするのが費用対効果が高い。

### 2. React Server Components streaming 2026

- **ポイント1（Partial Prerendering成熟化）:** Next.js 16ではPPR（Partial Prerendering）が安定版となり、静的シェルを即座に返しつつ動的部分だけをストリーミングする構成が標準パターンに。当社の物件詳細ページ（`src/app/properties/`）でも、静的な基本情報とサーバー側の在庫確認・価格計算を分離してTTFBを改善できる余地がある。

- **ポイント2（Suspenseバウンダリの粒度設計）:** ストリーミングの効果はSuspenseの分割単位に直結するため、「ページ単位」ではなく「コンポーネント単位」（例: 物件一覧のカードごと、レビューセクションごと）で境界を切るのがベストプラクティス。粒度が粗いと最も遅いデータ取得がページ全体をブロックしてしまう。

- **ポイント3（キャッシュとの併用が鍵）:** RSCストリーミング単体では初回表示は速くならないため、`unstable_cache`やfetchのrevalidate設定と組み合わせて「静的に近いデータは事前計算、動的データのみストリーミング」という役割分担が重要。前の住人の活動歴データなど更新頻度が低い情報はキャッシュ寄りにすべき。

- **ポイント4（サードパーティライブラリのRSC対応状況に注意）:** shadcn/uiやLucide Reactなど当社が採用しているライブラリは概ねRSC対応が進んでいるが、`'use client'`境界の配置を誤るとストリーミングのメリットが打ち消される。境界を末端（インタラクティブな最小単位）に寄せる設計を継続すべき。

- **ポイント5（計測を伴わない最適化は避ける）:** ストリーミング導入自体が目的化しやすいが、TTFB/LCP/INPの実測（Vercel AnalyticsやLighthouse CI）なしに境界を増やすと複雑性だけが増す。本番導入前にE2Eテストとパフォーマンス計測をセットで行うべき。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1: tRPCの採用拡大とEnd-to-End型安全性** モノレポ構成のNext.jsプロジェクトでは、tRPCによりフロントエンド〜バックエンド間の型を自動同期でき、スキーマ定義とコード生成の二重管理が不要になる。sumitsugiのようにNext.js App Router + TypeScriptで完結する構成では、REST+OpenAPIより開発速度が上がるため新規APIはtRPC優先を検討する価値がある。

- **ポイント2: GraphQLは複雑なデータ取得パターンに限定採用** GraphQLは物件検索のような多対多・フィルタ条件が複雑な画面で威力を発揮する一方、N+1問題やキャッシュ戦略の複雑さがオーバーヘッドになるため、単純なCRUDにはREST/tRPCを使う「適材適所」の設計が2026年のベストプラクティスとして定着している。

- **ポイント3: RESTは外部連携・Webhook用途で依然主流** 決済代行や外部システム（弁護士確認フロー、特商法関連の外部サービス等）との連携にはRESTが標準であり続けるため、内部通信はtRPC、外部公開APIはREST（OpenAPI仕様書付き）という併用構成が実務的。

- **ポイント4: エッジランタイムとの親和性がAPI選定の新基準** Next.js 16のエッジ関数・Server Actionsを使う場合、tRPCやServer Actions自体が軽量なAPI層として機能し、従来のREST APIルートを省略できるケースが増えている。物件一覧・詳細ページなどSSR中心の画面ではServer Actions優先で実装コストを削減できる。

- **ポイント5: スキーマファースト設計とZodの統合が必須化** tRPC・REST問わず、Zodスキーマを型定義とバリデーションの単一ソースとして扱う設計が標準になりつつある。sumitsugiのCLAUDE.md規約にもある「Zodスキーマによる境界検証」は、API設計全体の一貫性を保つ基盤として今後も維持すべき方針。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG（Web-interoperable Runtimes）準拠のエッジランタイムがCloudflare Workers・Vercel Edge・Deno Deployで共通化が進み、ベンダーロックインを避けたコード移植が現実的になっている。Next.js 16のEdge Runtimeもこの流れに沿っており、採用判断がしやすい。

- **コールドスタート問題の実質解消:** V8 isolateベースの起動時間はミリ秒単位まで短縮され、認証チェックやパーソナライゼーションなどレイテンシ敏感な処理をエッジ側に寄せる設計が主流になりつつある。sumitsugiの物件検索・地図表示のような低遅延が価値になる機能は、エッジ移行のROIが高い。

- **DBのエッジレプリケーション:** TursoやNeonのようなSQLiteベース/Postgresのエッジレプリカが実用段階に入り、読み取り中心のワークロード（物件一覧・検索）をユーザーに地理的に近いノードから返せるようになった。書き込みは依然中央集権的なため、読み書き分離の設計判断が必要。

- **コスト構造の変化:** リクエスト課金からCPU時間課金への移行が進み、静的コンテンツ配信や軽量API呼び出しではコスト削減効果が大きい一方、画像処理やPDF生成のような重い処理はエッジに向かないため、ワークロードごとの適材適所判断がより重要になっている。

- **観測性ツールの追随:** OpenTelemetryのエッジ対応が進んだが、分散トレーシングの複雑さは依然課題。移行前に、エラー監視・ログ収集基盤がエッジ環境で同等の可視性を確保できるか検証すべき。

### 5. authentication security best practices 2026

- **パスキー移行の本格化:** パスワードレス認証（WebAuthn/FIDO2）が業界標準になりつつあり、フィッシング耐性のあるパスキーへの移行が急務。sumitsugiでも次の住人・前の住人の本人確認フローに段階的導入を検討すべき。

- **AIを悪用したフィッシング・なりすまし対策:** 生成AIによる高精度な偽サイト・偽メールが増加しており、単純なパスワード認証やSMS OTPだけでは不十分。デバイスバインディングやリスクベース認証（異常ログイン検知）の組み込みが重要。

- **セッション管理とトークンの短命化:** JWT等のアクセストークンは有効期限を短く設定し、リフレッシュトークンのローテーション・失効管理を徹底する。長期セッションの放置は乗っ取りリスクを高める。

- **最小権限とゼロトラスト設計:** 前の住人・次の住人・管理者など役割ごとにアクセス範囲を厳密に分離し、認証後も操作ごとに権限チェックを行う。物件データや個人情報へのアクセスは特に重要。

- **Rate Limiting・ブルートフォース対策:** ログイン試行回数制限、CAPTCHA、IPベースの異常検知を実装し、認証エンドポイントへの攻撃を早期に遮断する。Zodによる入力検証と合わせてAPI境界での防御を強化すべき。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のType-safe Migrations強化:** Prisma 6系ではスキーマ変更の破壊的影響を事前検知する機能が強化されており、`prisma migrate diff`をCIに組み込むことで本番デプロイ前にダウンタイムリスクを可視化できる。

- **Supabase Row Level Security (RLS) とPrismaの併用:** SupabaseのRLSポリシーはPrisma Client経由のクエリにも適用されるため、アプリ層のバリデーションだけに頼らずDB層でのアクセス制御を必須にすべき。前の住人/次の住人のようなロールベースデータアクセスには特に有効。

- **Connection Poolingの必須化:** Next.js 16のServer Actions/RSCはリクエストごとに新規DB接続を張りやすく、SupabaseのSupavisor（またはPgBouncer）経由でのプーリングなしではコネクション枯渇が起きやすい。`DATABASE_URL`はプーリング用、`DIRECT_URL`はマイグレーション用に分離するのが定石。

- **Edge Runtime対応のドライバ選定:** Vercel EdgeやCloudflare Workers上で動かす場合、従来のPrisma ClientはNode.js依存が強いため、Prisma Accelerateまたはドライバアダプタ（`@prisma/adapter-pg`等）経由でSupabaseに接続する構成が主流になりつつある。

- **物件ステータス管理へのRealtime活用:** SupabaseのRealtime機能とPrismaのスキーマ定義を組み合わせることで、`'draft'`/`'public'`のステータス変更を即座にUIへ反映できる。ポーリング不要になりサーバー負荷とレイテンシの両方を削減できる。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Rustコンパイラのwasm向け最適化が進み、`wasm-opt`との連携やLTO/コード分割の精度が上がったことで、バンドルサイズと起動時間が大きく改善している。実装面では初期ロードが要件になる機能でwasmを検討する価値が増している。
- **ポイント2:** Component Model / WASI Previewの標準化が進み、言語間相互運用やホスト機能アクセスがより安定してきた。ただしまだエコシステムの成熟度にばらつきがあるため、採用前にツールチェーンの安定性を必ず検証すべき。
- **ポイント3:** SIMD・スレッド（shared memory + Web Workers）のブラウザサポートが広がり、画像処理や暗号化など計算集約的な処理でネイティブに近い性能が出せるようになった。パフォーマンスクリティカルな処理を切り出す際の有力な選択肢。
- **ポイント4:** JS↔wasmの境界を跨ぐデータコピー（特に文字列・複雑なオブジクト）が依然ボトルネックになりやすい。設計時はメモリレイアウトを揃え、境界越えの回数自体を減らす方針が重要。
- **ポイント5:** ビルド・デバッグのDXが向上（ソースマップ、プロファイラ連携）してきたとはいえ、通常のTS/JSデバッグに比べるとまだ手間がかかる。小さく閉じたモジュール単位で導入し、段階的に拡大するのが現実的なアプローチ。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 15〜16でPPRが安定版となり、静的シェルを即座に返しつつ動的部分をストリーミングする構成が主流に。初期表示速度とパーソナライズを両立できるため、物件一覧ページのような「静的な骨組み＋動的な価格・在庫情報」に最適。

- **Server Actions とキャッシュ戦略の成熟:** `use cache` ディレクティブやきめ細かい再検証（tag-based revalidation）が実用段階に入り、フォーム送信からDB更新までを一貫してサーバー側で完結できる。前の住人情報の更新など、クライアントJSを増やさずに実装可能。

- **App Router のバンドルサイズ最適化:** React Compilerの統合が進み、手動の`useMemo`/`useCallback`が不要になりつつある。ただしサードパーティライブラリの`"use client"`境界設計が依然としてパフォーマンスのボトルネックになりやすく、コンポーネント分割の設計判断がより重要に。

- **Middlewareの責務縮小:** Edge Middlewareでの重い処理（認証チェック等）はレイテンシコストが顕在化しやすいため、2026年時点ではRoute Handlers + Server Componentsでの認可チェックに寄せる設計が推奨される流れ。認証コンテキスト（`auth-context.tsx`）のようなクライアント側状態管理との責務分離を明確にすべき。

- **Turbopackの本番採用拡大:** `bun run build`のビルド時間短縮に直結するため、CI高速化の観点でも導入価値が高い。ただし一部のWebpack依存プラグインは互換性検証が必要。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約とWasm活用:** Vercel Edge FunctionsはV8 isolateベースで軽量・高速起動が強みだが、Node.js API非対応の制約が根強く残る。計算集約処理はWebAssemblyにコンパイルしてエッジで実行するパターンが2026年も定番化しており、画像処理や暗号化処理などで採用が進んでいる。

- **Streaming SSRとPartial Prerenderingの組み合わせ:** Next.js 16のPPR（Partial Prerendering）とEdge Functionsを組み合わせることで、静的シェルを即座に配信しつつ動的部分のみをストリーミングする構成が主流化。TTFBを大幅に短縮できるため、初期表示速度がKPIとなるプロダクトでは必須の最適化手法。

- **リージョン近接実行によるコールドスタート最小化:** `waitUntil`や地理的ルーティング設定を活用し、ユーザーに最も近いエッジロケーションでリクエストを処理する構成が標準化。DBアクセスを伴う場合はエッジ最寄りのレプリカ（Neon、PlanetScale、Turso等）と組み合わせないと、かえってレイテンシが悪化する点に注意が必要。

- **コスト最適化のためのミドルウェア設計:** Edge Middlewareの実行回数課金モデルを踏まえ、認証チェックやリダイレクトなど本当にエッジで必要な処理のみに限定し、重い処理はServer ActionsやRoute Handlersに逃がす設計判断がベストプラクティスとして定着。全リクエストにミドルウェアを挟む設計は避けるべき。

- **可観測性とデバッグの改善:** Edge FunctionsはNode.jsランタイムに比べデバッグが難しい問題が長らく課題だったが、Vercel OTel統合やWeb標準の`console`/`fetch`ベースのトレーシングが充実し、分散トレースをエッジ〜オリジン間で追跡しやすくなった。本番導入前にステージング環境でのトレース検証を組み込むことが推奨される。

### 10. TypeScript type safety patterns 2026

- **型レベルプログラミングの実用化:** TypeScript 5.x以降のconst type parametersやtemplate literal typesが安定し、Zodなどのスキーマライブラリと組み合わせてランタイム検証と型推論を一元化するパターンが標準化。境界（API入出力、フォーム）でのZod schema→型推論という流れが本プロジェクトの標準スタイルとも合致する。

- **`unknown`優先とtype narrowingの徹底:** `any`の排除が単なるリンタールールではなく、discriminated unionとexhaustiveness check（`never`型を使った網羅性チェック）を組み合わせることで、コンパイル時にケース漏れを検知するパターンが主流化している。

- **Branded types / nominal typingの普及:** `UserId`と`ListingId`のような構造的に同じstring型を混同しないよう、branded typesで意味的な区別をつける手法が広く採用されている。物件ID・ユーザーID・予約IDなど識別子が多いドメインでは特に有効。

- **Result型によるエラーハンドリングの型安全化:** try/catchに頼らず、`Result<T, E>`パターンで成功・失敗を型として表現し、呼び出し側に処理を強制する設計が浸透。境界（決済処理や外部API連携）でのエラー握りつぶしを構造的に防げる。

- **AIコード生成時代の型の重要性増大:** LLMが生成するコードの正しさをレビューする際、厳格な型定義（strict mode必須、`noUncheckedIndexedAccess`等）がAIの誤りを機械的に検出する「セーフティネット」として再評価されており、型定義そのものをAIへの仕様書として扱う開発フローが増えている。
