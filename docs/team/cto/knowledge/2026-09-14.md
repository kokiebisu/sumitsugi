# CTO Knowledge - 2026-09-14

## Daily Update (2026-09-14)

### 1. Next.js performance optimization 2026

- **Turbopackのフル安定化:** Next.js 16でTurbopackがビルド・開発両方のデフォルトになり、大規模プロジェクトでのコールドスタートとHMR速度が大幅に改善。sumitsugiのようなbun運用でも`bun run build`の時間短縮に直結するため、CIキャッシュ戦略の見直しも検討価値あり。

- **Partial Prerendering (PPR) の本格運用:** 静的シェルを即座に配信しつつ動的部分（物件検索結果や在庫状況など）だけをストリーミングする手法が主流化。物件一覧ページのような「一部は静的・一部はリアルタイム」なUIとの相性が良く、TTFB改善に効果的。

- **`"use cache"` ディレクティブによる明示的キャッシュ制御:** Route/Data Cacheの挙動が暗黙的だった問題が解消され、キャッシュ境界をコード上で明示できるように。物件データ更新の反映タイミング（下書き→公開の切り替えなど）を厳密に制御したい場面で有用。

- **React Compilerとの統合:** `useMemo`/`useCallback`の手動最適化が不要になりつつあり、コンポーネント側のパフォーマンスチューニングコストが低下。ただし移行時は既存の最適化コードとの重複・競合がないかビルド後の挙動確認が必須。

- **`next/after` によるレスポンス後処理:** レスポンス返却後にログ記録や通知送信などの副作用処理を実行できる仕組みが定着。問い合わせ通知やアクセスログなど、ユーザー体験（応答速度）を犠牲にせず裏側の処理を非同期化できる。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** RSCのSuspenseベースのストリーミングは、CDNエッジでの部分ハイドレーションと組み合わせることで、TTFB(Time to First Byte)を保ちながら初期表示速度を大幅改善できる。sumitsugiでも物件詳細ページのような重いデータ取得を伴う画面で、`loading.tsx`とSuspense境界を細かく設計することでLCP改善が見込める。

- **Server Actionsとの統合最適化:** フォーム送信やインタラクション後の再検証（revalidatePath/revalidateTag）がRSCストリーミングと組み合わさり、クライアントJSを増やさずにインタラクティブなUXを実現できる。前の住人と次の住人間のメッセージングやステータス変更フローなど、フォーム中心の機能でこのパターンを積極活用すべき。

- **Partial Prerendering (PPR) の実用化:** 静的シェルを即座に返しつつ動的部分だけをストリーミングするPPRがNext.js 16でより安定してきており、物件一覧ページのように「静的なレイアウト＋動的な検索結果」という構成に適している。導入コストと効果のバランスを見極めた上で段階的採用が現実的。

- **キャッシュ戦略の複雑化への注意:** RSCストリーミングはキャッシュ層（fetchキャッシュ、Router Cache、CDN）が増える分、デバッグが難しくなるトレードオフがある。物件ステータス(`draft`/`public`)の即時反映が必要な箇所では、キャッシュの取り違えによる情報漏洩リスクを避けるため、明示的な`no-store`やタグベースの再検証を徹底すべき。

- **エラーバウンダリとストリーミングUXの両立:** ストリーミング中に発生したエラーは`error.tsx`で個別のSuspense境界ごとに捕捉できるため、一部のコンポーネント（例: 周辺施設情報の外部API取得）が失敗してもページ全体をブロックしない設計が可能。障害耐性の高いUXとして今後のリファクタリングで検討したい。

### 3. API design REST GraphQL tRPC 2026

- **GraphQLの選択的採用が定着:** フロントエンド要件が複雑なプロダクト（複数クライアント、柔軟なデータ取得）ではGraphQLが依然有効だが、単純なCRUD中心のサービスではオーバーエンジニアリングになりがちで、tRPCやREST+OpenAPIへの回帰が2026年も続いている。

- **tRPCはフルスタックTypeScriptモノレポの定番に:** sumitsugiのようなNext.js App Router構成では、クライアント/サーバー間の型共有によりAPIスキーマの二重管理が不要になり、開発速度とバグ削減の両面でROIが高い。ただしモバイルや外部連携が絡む場合はREST/OpenAPIとの併用設計が必要。

- **AI駆動のAPI設計・ドキュメント自動生成:** Zodスキーマからのドキュメント自動生成、LLMによるエンドポイント設計レビューが一般化し、「スキーマファースト」が「AIアシスト・スキーマファースト」に進化している。当プロジェクトでも入力バリデーションにZodを使っているため、この流れとの親和性が高い。

- **エッジ・BFF層でのAPI集約が加速:** Next.jsのServer ActionsやRoute Handlersをエッジで動かし、外部サービス（決済、法務確認系API等）を薄いBFFで束ねる構成が主流化。レイテンシ削減とセキュリティ境界の明確化（秘密情報をクライアントに露出しない）が主な動機。

- **REST APIの「退場」ではなく「棲み分け」:** 公開APIやサードパーティ連携（今後の決済・本人確認連携を見据えると重要）は依然RESTが業界標準であり、内部通信はtRPC/GraphQL、外部公開はRESTという使い分けが2026年のベストプラクティスとして定着している。

### 4. serverless edge computing 2026

- **ポイント1:** エッジ実行環境の標準化が進み、Cloudflare Workers・Deno Deploy・Vercel Edge FunctionsがWinterCG準拠のWeb標準APIに収斂したことで、ベンダーロックインが大幅に低減した。移行コストを気にせずマルチクラウド戦略を取れる段階に来ている。

- **ポイント2:** エッジでのステートフル処理（Durable Objects、Edge KV、分散SQLite系のD1/Turso）が実用段階に入り、単純なキャッシュ用途を超えてセッション管理や簡易トランザクションもエッジで完結できるようになった。中間層のAPIサーバーを削減できるケースが増えている。

- **ポイント3:** 軽量LLM推論のエッジ配置（量子化モデル＋WASMランタイム）が現実的になり、パーソナライズやレコメンドの一次判定をエッジで行いレイテンシを数十ms単位で削減する事例が増加。sumitsugiのような不動産マッチングでも「前の住人」検索の初期フィルタリングをエッジで実行する余地がある。

- **ポイント4:** コールドスタート問題はV8 isolateベースの実行モデルでほぼ解消されたが、代わりに「エッジでのオブザーバビリティ」が新たな課題に。分散トレーシング（OpenTelemetry）のエッジネイティブ対応が2026年の重要な選定基準になっている。

- **ポイント5:** コスト構造がリクエスト課金から「実行時間×メモリ」の細粒度課金へ移行しつつあり、トラフィックが不安定な初期フェーズのプロダクト（ベータローンチ前のsumitsugiのような）には従来型サーバーレスより有利になるケースが多い。ローンチ後の負荷予測が立つまではNext.js 16のエッジランタイム活用を検討する価値がある。

### 5. authentication security best practices 2026

## 認証セキュリティのベストプラクティス 2026（CTO視点）

- **パスキー（Passkeys）のデフォルト化:** FIDO2/WebAuthnベースのパスキーがパスワード+SMS OTPを置き換える主流になっている。SIMスワップ詐欺に弱いSMS認証は段階的に廃止し、生体認証+デバイス鍵によるフィッシング耐性のあるログインをsumitsugiのような個人情報（物件・引継ぎ契約）を扱うプラットフォームでは優先すべき。

- **リスクベース／継続的認証:** ログイン時の一発認証ではなく、デバイスフィンガープリント・IP・行動パターンをもとにリアルタイムでリスクスコアを算出し、異常時のみ追加認証（ステップアップ認証）を要求する方式が標準化。過剰なMFA摩擦を避けつつセキュリティを維持できる。

- **トークンのDPoP/Sender-Constrained化:** Bearerトークンの単純な盗用リスクに対し、DPoP（Demonstrating Proof of Possession）やmTLSでトークンを送信元に紐付ける実装が広がっている。認証ロジック実装時はセッショントークンが漏洩しても再利用不可能な設計を意識する。

- **ゼロトラスト前提のセッション管理:** 認証後も「信頼し続けない」設計が基本。短命アクセストークン+リフレッシュトークンローテーション、デバイスごとのセッション可視化・強制失効機能をユーザー（前の住人／次の住人）双方のアカウント管理画面に持たせるべき。

- **サプライチェーン・依存ライブラリの認証コンポーネント監査:** OAuth/OIDCライブラリやSDKの脆弱性が2025-2026にかけて認証バイパスの主要因になっている。`bun run build`前のセキュリティレビューで認証関連パッケージのCVEを定期チェックし、Supabase Authなど外部プロバイダのアップデートに追従する体制が必須。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** SupabaseはRLS（Row Level Security）を前提にPrisma Client拡張やPrisma Postgres連携が強化されており、Prismaのマイグレーション管理とSupabaseのAuth/Storageを組み合わせる構成が2026年のデファクトになりつつある。物件データのような個人情報を含むテーブルでは、Prisma側でスキーマ管理しつつRLSポリシーはSQLマイグレーションで別管理するのが実用的。

- **ポイント2:** Prisma Accelerate等のコネクションプーリング／エッジキャッシュ層がSupabaseのPgBouncerと競合しやすく、サーバーレス関数（Vercel/Next.js API Route）からのDB接続数枯渇が本番障害の主因になりやすい。sumitsugiのような一覧・検索ページはRead ReplicaかAccelerateキャッシュを積極活用し、書き込み系（問い合わせ・契約）と分離すべき。

- **ポイント3:** Prisma 6系以降はTypedSQLやリレーションのJOIN最適化が進み、`draft`/`public`のようなステータス列を含むクエリではPrismaの型安全なフィルタとSupabaseのインデックス設計を両輪で見る必要がある。ステータス値を追加・変更する際は、DB制約（CHECK制約）とTypeScript側のUnion型を両方更新する運用ルールが事故防止に効く。

- **ポイント4:** SupabaseのRealtime機能とPrismaのORMレイヤーは直接統合されないため、「前の住人↔次の住人」間のチャット等リアルタイム要件がある機能ではSupabase Clientを部分的に併用するハイブリッド構成が一般化している。データの正はPrisma経由で書き込み、購読だけSupabase Realtimeを使う責務分離が事故を防ぐ。

- **ポイント5:** マイグレーションのCI組み込み（`prisma migrate deploy`をビルドパイプラインに組み込む）が標準化しており、Supabase側のブランチ機能（開発用DBブランチ）と組み合わせてPRごとに独立したDB環境でE2Eテストを回す構成が増えている。ローンチ前の今のフェーズでは、本番相当のステージングDBをSupabaseブランチで用意し、法務確認と並行して負荷テストを済ませておくと手戻りが少ない。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Wasm Component Model と WASI 0.2/Preview 2 の標準化が進み、Rustのwasm32-wasip2ターゲットが安定化。異なる言語で書かれたWasmモジュール同士を型安全に連携できるようになり、モジュール単位でのマイクロサービス的な構成がエッジ環境で現実的になっている。

- **ポイント2:** wasm-bindgen/wasm-packのビルドサイズ最適化（wasm-opt、`opt-level = "z"`、LTO有効化）に加え、Rustコンパイラ側のWasm向けコード生成が改善され、JSグルーコードなしでネイティブに近いDOM操作が可能に。前の住人の物件情報を扱う重い画像処理や検索インデックス処理をクライアントサイドWasmにオフロードすれば、サーバー負荷を減らしつつUXを保てる。

- **ポイント3:** SIMD128とマルチスレッド（`wasm-threads` + SharedArrayBuffer）がブラウザ主要3系統で安定サポートされ、Rust製Wasmでの並列処理性能がネイティブの70-90%程度まで到達。ただしNext.jsのSSR環境ではWorker連携の実装コストがあるため、まずは非同期の重い計算（画像リサイズ、PDF生成など）から段階導入するのが現実的。

- **ポイント4:** WasmGCの実装が進み、GC言語（Kotlin/Dart等）だけでなくRustのRc/Arc多用コードでもメモリ管理のオーバーヘッドが減少傾向。ただし現状のRustエコシステムでは線形メモリモデルの方が枯れており実績十分なため、当面はwasm32-unknown-unknownを本命とし、WasmGCは様子見でよい。

- **ポイント5:** Cloudflare WorkersやFastly Compute@EdgeなどのWasmベースエッジランタイムがコールドスタート数ミリ秒を実現しており、Rust+Wasmはエッジでの認証チェックやレート制限といった軽量処理に適している。sumitsugiのような不動産プラットフォームでは、物件検索のジオフィルタリングなど地理的に分散した軽量ロジックをエッジWasmに載せる余地がある。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** App Routerではデフォルトで全コンポーネントがServer Componentsとして扱われ、クライアントバンドルサイズを大幅に削減できる。`'use client'`境界を末端の葉コンポーネントに限定することで、初期表示速度とSEOを両立させるのが2026年の定石。

- **Partial Prerendering (PPR) の本格運用:** 静的シェルを即座に配信しつつ、動的部分をストリーミングで後から埋める手法が安定版として広く採用されている。物件一覧ページのように「静的な枠組み＋動的な検索結果」という構成に相性が良く、体感速度を大きく改善できる。

- **Server Actionsによるフォーム処理の標準化:** APIルートを介さずServer Actionsで直接データ更新できるため、問い合わせフォームや引き継ぎ申請フローなどのミューテーションをシンプルに実装可能。ただしCSRF対策とZodによる入力検証は引き続き必須。

- **キャッシュ戦略の明示化（`use cache`ディレクティブ）:** Next.js 16では`use cache`によりキャッシュ境界を関数単位で明示的に制御できるようになり、暗黙的キャッシュに起因するバグが減少。物件データのような更新頻度が異なるデータソースを扱う本プロダクトでは、キャッシュ粒度の設計が今後の重要な技術的意思決定になる。

- **Route GroupsとParallel Routesによるレイアウト分離:** `(properties)`や`(listing)`のようなルートグループで認証要否やレイアウトを分離しつつ、ダッシュボード系ページではParallel Routesでモーダルやサイドパネルを実装するパターンが定着。ページ数が増えても保守性を保ちやすい。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約設計:** Node.js API非互換な軽量ランタイムのため、依存ライブラリ選定時点でEdge対応を確認し、重い処理はServerless/Node runtimeに逃がす設計判断が重要。
- **Cold Start最小化:** Edge Functionsはコード量とバンドルサイズがレイテンシに直結するため、動的importの削減・不要なpolyfill除去でCold Startを数ms単位まで詰める余地がある。
- **リージョン配置とデータ局所性:** ユーザーに最も近いエッジで実行されるが、DB/APIが単一リージョンだと結局そこへの往復遅延がボトルネックになるため、EdgeとDBのリージョン戦略を合わせて設計すべき。
- **キャッシュ戦略の高度化:** `stale-while-revalidate`やISR的な部分再検証をEdge Middlewareと組み合わせることで、動的パーソナライズとキャッシュヒット率を両立できる。
- **可観測性コストの見落とし注意:** Edge実行はログ・トレースの集約が分散しやすく、監視コストが増加しがちなので、導入前にオブザーバビリティ基盤（OpenTelemetry対応等）を前提に組み込む必要がある。

### 10. TypeScript type safety patterns 2026

TypeScript type safety patterns 2026について、CTO視点で回答します。

- **ポイント1（型レベル検証の標準化）:** Zodなどのスキーマライブラリで実行時バリデーションとコンパイル時の型を単一のソースから生成する手法が定着し、APIリクエスト/レスポンスやフォーム入力など境界層での型不整合バグを大幅に削減している。`.claude/rules/standards.md`にもある通り、システム境界でのZodバリデーションは既にsumitsugiでも標準採用済み。

- **ポイント2（テンプレートリテラル型とブランド型の活用）:** ルーティングパスやIDなど「文字列だが意味的に区別すべき値」をテンプレートリテラル型・ブランド型（nominal typing）で表現し、`seller`と`buyer`のIDを取り違えるような論理バグをコンパイル時に検出する流れが強まっている。物件ステータス（`'draft' | 'public'`）のようなUnion型も同様に、文字列の取り違えを型で防げる。

- **ポイント3（strictな型チェックのCI必須化）:** `noUncheckedIndexedAccess`や`exactOptionalPropertyTypes`など、より厳格なtsconfigフラグをデフォルト有効にする組織が増え、配列アクセスやoptionalプロパティ周りの実行時エラーを未然に防ぐ。sumitsugiでも「Union型を変更する際は全使用箇所をgrep」というルールがあるが、これらのフラグを有効化すればコンパイラが自動検出してくれるため、ビルド健全性（Build Integrity）の観点で導入価値が高い。

- **ポイント4（型推論とAIコード生成の相性）:** LLMによるコード生成が主流になる中、型が厳密であるほどAIが生成したコードの誤りをコンパイル時に検出できるため、「型安全性への投資」が「AI活用の生産性」に直結するという認識が広がっている。sumitsugiのようにAIエージェント（autonomous-developer等）がコードを書く体制では特に重要。

- **ポイント5（型とテストの役割分担の明確化）:** 型システムでは表現しきれない「ビジネスロジックの正しさ」はユニット/E2Eテストに任せ、型は「形状の正しさ」に集中させる分業が明確になってきている。sumitsugiのTDD必須方針（カバレッジ80%以上）とも整合的で、型安全性はバグ予防の第一層、テストは第二層という位置づけが実務的。
