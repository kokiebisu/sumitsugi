# CTO Knowledge - 2026-07-10

## Daily Update (2026-07-10)

### 1. Next.js performance optimization 2026

- **ポイント1（Turbopackのデフォルト化）:** Next.js 16でTurbopackが本番ビルドの標準バンドラーとなり、webpack比で大幅なビルド時間短縮が可能。移行時はカスタムwebpack設定やloaderの互換性を事前に確認すべき。

- **ポイント2（明示的キャッシュ戦略への移行）:** `use cache`ディレクティブとキャッシュプロファイル（`cacheLife`/`cacheTag`）による明示的なキャッシュ制御が主流になり、暗黙的な自動キャッシュに依存する設計は避けるべき。物件検索・一覧ページなど頻繁に更新されるデータには適切なタグ付けが必須。

- **ポイント3（Partial Prerendering + Streaming）:** 静的シェルと動的コンテンツを組み合わせるPPRが実運用フェーズに入り、初期表示速度（LCP）とパーソナライズの両立が可能に。物件詳細ページのように「静的な物件情報＋動的な在庫状況」の構成に相性が良い。

- **ポイント4（React Compilerによる自動最適化）:** React Compilerが安定版となり、`useMemo`/`useCallback`の手動最適化が不要なケースが増加。ただし既存コードのメモ化ロジックとの相互作用は要検証で、段階的導入を推奨。

- **ポイント5（Server Componentsを前提としたバンドルサイズ管理）:** クライアントコンポーネントの境界を最小化し、認証コンテキストや状態管理ライブラリのクライアントバンドルへの影響を定期的に計測（`next build`のバンドル分析）することが、モバイル回線でのパフォーマンス維持に直結する。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** React 19以降、`use()`とSuspenseによるストリーミングがApp Routerの既定挙動として定着し、TTFBを保ったままLCPを大幅改善できる。sumitsugiでも物件一覧の画像・詳細データを段階的に流し込む設計が有効。

- **Partial Prerendering (PPR) の実用化:** Next.js 16でPPRが安定版となり、静的シェル（ヘッダー・レイアウト）を即座に返しつつ動的部分（在庫状況・価格）だけをストリーミングするハイブリッド構成が主流に。物件詳細ページのような「静的な骨組み+動的データ」の構成と相性が良い。

- **RSC Payloadのキャッシュ戦略が焦点に:** `'use cache'`ディレクティブとタグベース再検証(`revalidateTag`)の組み合わせで、DBクエリを跨いだ細粒度キャッシュが可能になった。物件データ更新時の即時反映と高速表示のバランス設計が重要な検討ポイント。

- **エラーバウンダリとストリーミングの相互作用:** ストリーミング中に発生したサーバーエラーのハンドリングが複雑化するため、`error.tsx`の粒度をコンポーネント単位で細かく設計する必要がある。フォームや決済フローなど失敗が許されない箇所は、あえてストリーミングを避け同期的にレンダリングする判断も有効。

- **Server Actionsとの統合深化:** ストリーミングレスポンス中でもServer Actionsの楽観的UI更新(`useOptimistic`)が安定動作するようになり、内見予約や引越し費用計算のような多段階フォームでの体感速度向上に直結する。

### 3. API design REST GraphQL tRPC 2026

- **スキーマファースト×型安全性の融合:** tRPCのエンドツーエンド型推論とGraphQLのスキーマ駆動開発が収束し、Next.js App Router環境ではServer Actions + tRPCの組み合わせでクライアント/サーバー間の型安全性を最小コストで確保するのが主流になっている。

- **BFF層でのGraphQL限定利用:** フルGraphQL APIより、モバイル/複数フロントエンド向けのBFF（Backend for Frontend）層としてGraphQLを局所的に採用し、内部サービス間はRESTやtRPCで完結させるハイブリッド構成がスケール時のコスト対効果で優位。

- **RESTのシンプルさが小〜中規模で再評価:** OpenAPI 3.1 + Zodスキーマ生成の自動化が進み、tRPCのような型共有の恩恵をRESTでも得られるようになったため、単一フロントエンド（sumitsugiのような自社Next.jsのみの構成）ではtRPCまたは薄いREST + Zod検証が最もメンテコストが低い。

- **エッジランタイムとの相性がAPI選定を左右:** Vercel Edge/Cloudflare Workers等でのコールドスタート最適化のため、GraphQLの重いリゾルバより軽量なtRPC/RESTルートハンドラの方がレイテンシ面で有利という実測データが増えている。

- **AI Agent連携を見据えたAPI設計:** LLMエージェントやMCPからの呼び出しを想定する場合、GraphQLの柔軟なクエリよりも、明確な入出力スキーマを持つtRPC/REST + JSON Schemaの方がツール定義（function calling）との親和性が高く、2026年はこの観点からの設計判断が増えている。

### 4. serverless edge computing 2026

- **エッジでのAI推論統合:** Cloudflare Workers AIやVercel Edge Functionsなど、エッジランタイムに軽量LLM推論（数億パラメータ級のモデル）を直接デプロイする構成が主流化。sumitsugiのようなマッチング機能でも、レイテンシが重要なリコメンド処理をエッジ側に寄せることでオリジンサーバーの負荷とレスポンス時間を同時に削減できる。

- **コールドスタート問題の実質的解消:** V8 isolateベースのランタイム（Workers, Deno Deploy）が成熟し、コールドスタートが1桁ミリ秒台まで短縮。Next.js 16のEdge Runtimeを積極活用することで、認証チェックやリダイレクトなどミドルウェア相当の処理をエッジで完結させ、TTFBを大幅改善できる。

- **データレイヤーのエッジ追従:** Turso/D1のようなSQLiteベースの分散DBやエッジKVストアが普及し、「コンピュートはエッジ、データは中央」という従来の制約が崩れつつある。ただし強整合性が必要な決済・契約データ（引越し費用の決済等）は依然としてリージョナルDBに残すべきで、全面移行ではなくハイブリッド設計が現実解。

- **ベンダーロックインへの警戒:** WinterCG（Web-interoperable Runtimes Community Group）標準に準拠したコードを書くことで、Cloudflare/Vercel/Deno間の移植性を確保する動きが加速。契約書PDF生成など重い処理は引き続きNode.jsランタイムに残し、エッジは「薄いI/O処理」に限定する設計判断がベストプラクティスとして定着している。

- **コスト構造の見直し:** リクエスト課金モデルの複雑化により、常時稼働の低トラフィックMVPではエッジの実行コストが従来型サーバーレスより割高になるケースも報告されている。sumitsugiのβローンチ規模ではコスト試算を先に行い、全機能をエッジ化するのではなく効果の高い箇所（認証・リダイレクト・静的パーソナライズ）から段階的に移行するのが妥当。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）中心への移行:** パスワード+SMS認証は2026年時点でフィッシング耐性が低いとみなされており、WebAuthn/FIDO2ベースのパスキーをプライマリ認証手段にするのが業界標準になっています。sumitsugiのようなtoC不動産プラットフォームでは、離脱率の高いパスワードリセットフローを削減できる副次効果もあります。

- **セッション管理の厳格化:** JWTを使う場合はshort-lived access token + rotating refresh tokenの組み合わせが必須で、refresh tokenの再利用検知（token reuse detection）を実装しないとセッションハイジャックのリスクが残ります。Next.js App Routerではミドルウェアレベルでのセッション検証とhttpOnly Cookie管理が基本線です。

- **BFF（Backend for Frontend）パターンでのトークン隔離:** アクセストークンをブラウザに直接渡さず、サーバーサイド（Route Handlers/Server Actions）でトークンを保持しCookieセッションだけをクライアントに渡す設計が、XSS耐性の面で推奨されています。特に決済情報や個人情報を扱う「引越し費用」フローでは重要です。

- **レート制限とボット対策の多層化:** ログイン試行だけでなく、パスワードリセット・お問い合わせフォーム・物件登録APIなど全エンドポイントにレート制限をかける必要があります。IPベースだけでなくデバイスフィンガープリンティングやCAPTCHA代替（Cloudflare Turnstile等）の併用がクレデンシャルスタッフィング対策の主流です。

- **最小権限とRBAC/ABACの明確化:** 「前の住人」「次の住人」といったロールが増えるほど権限境界の複雑性が上がるため、認可ロジックをAPI層で一元化し、UIの表示制御だけに頼らないことが重要です。サーバーサイドでの認可チェック漏れがOWASP Top 10で継続的に上位に入っています。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6系ではPostgreSQL向けのネイティブなRow Level Security(RLS)サポートが強化されており、SupabaseのRLSポリシーとPrisma Clientを併用する際はコネクションプーラー（PgBouncer/Supavisor）経由でも`auth.uid()`が正しく伝播するよう、接続方式（transaction mode vs session mode）を明示的に選定する必要がある。

- **ポイント2:** サーバーレス環境（Vercel等）からのDB接続はコネクション枯渇が最大の障害要因になりやすく、SupabaseのSupavisor（transaction pooling）をPrismaの`directUrl`/`url`使い分けと組み合わせ、マイグレーション時のみdirect connectionを使う構成がデファクトになっている。

- **ポイント3:** Prisma AccelerateやSupabaseのEdge Functionsとの組み合わせで、読み取りクエリのキャッシュ層をDB手前に置くことでレイテンシを大幅短縮できるが、住人データのようにリアルタイム性が求められる箇所（物件ステータス変更など）はキャッシュ無効化ロジックを別途設計する必要がある。

- **ポイント4:** スキーマ変更の運用面では、Prisma Migrateの`shadow database`をSupabaseのブランチ機能（Database Branching）と統合することで、PRごとに隔離された検証環境を自動生成でき、`draft`/`public`のようなステータス遷移を伴うマイグレーションの安全性が高まる。

- **ポイント5:** 2026年時点ではPrismaのORM層とSupabaseのPostgREST/Realtimeを併用するハイブリッド構成が主流となっており、型安全性が必要な業務ロジックはPrisma経由、リアルタイム通知（内見予約通知等）はSupabase Realtimeを使う役割分担が推奨される。

### 7. WebAssembly Rust performance 2026

- **ポイント1（コンポーネント化とWASI Preview 2）:** WASI 0.2以降のcomponent modelが実用段階に入り、Rustの`wit-bindgen`でWasmモジュールを言語非依存の再利用可能コンポーネントとして配布できるようになった。マイクロサービスをWasmコンポーネントに置き換えることで、コールドスタートをコンテナの1/10以下に短縮できるケースが増えている。

- **ポイント2（SIMDとネイティブ比の性能ギャップ縮小）:** Wasm SIMDとmulti-value returnがブラウザ・サーバー両方で標準化され、Rust製の画像処理・暗号演算ワークロードでネイティブ比80〜90%の性能を安定して出せるようになった。ただし境界を跨ぐメモリコピー（JS⇔Wasm）が依然ボトルネックなので、ホットパスは`wasm-bindgen`の`&[u8]`共有バッファ設計を徹底すべき。

- **ポイント3（サーバーサイドWasmランタイムの台頭）:** Wasmtime/WasmEdgeがエッジコンピューティング用途で急速に採用が進み、Rust製Wasmバイナリを使ったマルチテナントSaaSのサンドボックス分離が実用的な選択肢になっている。当社のような不動産プラットフォームでも、テナント固有のカスタムロジック（料金計算・審査ルール）を安全に実行する用途で検討価値がある。

- **ポイント4（ツールチェーンの成熟）:** `cargo component`とTrunk/Leptosなどのフレームワークが安定し、Rust→Wasmのビルド・デプロイパイプラインが大幅に簡素化された。ただしバイナリサイズ最適化（`wasm-opt`、LTO、`opt-level = "z"`）は依然として手動チューニングが必要で、CI段階でサイズ回帰を検知する仕組みを入れておくと良い。

- **ポイント5（GC統合とハイブリッド言語連携）:** WasmGC提案が主要ブラウザで実装され始め、Rust以外の言語（Kotlin、Dart等）ともWasmランタイム上で相互運用しやすくなった。今後フロントエンドのパフォーマンスクリティカルな処理（PDF生成、画像最適化など）をRust/Wasmに切り出す判断がしやすくなる。

### 8. Next.js App Router patterns 2026

- **ポイント1（Partial Prerendering / PPR の標準化）:** 静的シェルを即座に返しつつ動的部分を非同期でストリーミングするPPRが本格運用フェーズに入り、初期表示速度とパーソナライズを両立できるようになった。sumitsugiのような物件一覧+個別ステータス表示が混在するUIでは、静的な物件カードと動的な「公開/非公開」状態を分離するのに有効。

- **ポイント2（Server Actions のバリデーション統合）:** Server ActionsとZodスキーマを組み合わせたフォーム処理が定番化し、`useActionState`でクライアント側のエラー表示とサーバー側バリデーションを1つのコードパスに統合できる。認証・引越し費用計算など多段階フォームで冗長なAPI Route実装を削減できる。

- **ポイント3（Route Groups + Parallel Routes の使い分け成熟）:** `(group)`によるレイアウト分離と`@slot`による並行ルートの使い分けが定着し、モーダル・ダッシュボード系UI（例: 物件詳細をモーダルで開きつつURLも変わる）を素のNext.js機能だけで実装するパターンが主流に。

- **ポイント4（キャッシュ戦略の明示化）:** `fetch`のデフォルトキャッシュ挙動が縮小し、`revalidate`やタグベース再検証（`revalidateTag`）を明示的に指定する運用が標準になった。物件ステータス変更（draft→public）のような即時反映が必要な処理では、キャッシュ設計を意識しないと古いデータが表示されるリスクが増えている。

- **ポイント5（Edge/Node ランタイムの使い分け最適化）:** 認証チェックやリダイレクトなど軽量処理はEdge Runtime、DB接続やファイル生成（PDF等）はNode Runtimeという使い分けが明確化し、ミドルウェアのレイテンシ削減とバックエンド処理の安定性を両立させるベストプラクティスが確立された。

### 9. Vercel Edge Functions optimization 2026

## Vercel Edge Functions最適化 2026

- **ポイント1: Fluid Compute によるコールドスタート削減** Vercelの Fluid Compute モデルがEdge/Serverless間の垣根を減らし、リクエスト間でインスタンスを再利用することでコールドスタートとコストを大幅に削減している。長時間実行の要件がなければ、まずFluid Computeの設定を見直すのが最も費用対効果が高い。

- **ポイント2: Edge Middlewareの責務を最小限に絞る** 認証チェックやリダイレクトなどミリ秒単位で完結する処理のみをEdge Middlewareに残し、重い処理（DB書き込み、外部API呼び出し）はNode.jsランタイムに逃がすのがベストプラクティス。Edgeランタイムの実行時間制限とAPI互換性の制約を意識する必要がある。

- **ポイント3: ISR/PPR (Partial Prerendering) との組み合わせ** Next.js 16のPartial Prerenderingを活用し、静的シェルをCDNから即座に返しつつ動的部分だけEdgeでストリーミングする構成がTTFB最適化の主流になっている。物件一覧ページのような一部動的コンテンツを含むページに有効。

- **ポイント4: リージョン選定とデータ局所性** EdgeとDB（例: Supabase, Neon）のリージョンが離れているとレイテンシが逆に悪化するケースがある。Edge Functionsのリージョン設定をDBに近づけるか、Read Replica/エッジキャッシュ（Vercel KV等）を併用するのが定石。

- **ポイント5: 観測性とコスト監視の自動化** Edge Functionsは従量課金かつ挙動が見えにくいため、Vercel Observability Plusやログドレインでリクエスト数・実行時間を継続監視し、異常なトラフィックパターンを早期検知する体制が重要視されている。

### 10. TypeScript type safety patterns 2026

- **ポイント1（`satisfies`演算子の定着）:** 型推論を保ちつつ制約チェックもできる`satisfies`が標準的な書き方として定着し、`as const`との組み合わせで設定オブジェクトやルーティング定義の型安全性が大きく向上した。widening問題を回避しながら具体的なリテラル型を保持できる点が実用上のメリット。
- **ポイント2（テンプレートリテラル型の実用化）:** ルートパスやAPIエンドポイント、CSS変数名などの文字列パターンをテンプレートリテラル型で表現し、コンパイル時に不正な文字列を検出する手法が本番コードで一般化。本プロジェクトでも`src/app/`配下のルート定義に応用余地がある。
- **ポイント3（Zodスキーマからの型導出が標準に）:** `z.infer<typeof schema>`でスキーマから型を導出し、実行時バリデーションと静的型を単一の情報源から生成するパターンが主流化。本プロジェクトの「Zodスキーマを境界で使う」方針とも合致し、型とバリデーションの二重管理を防げる。
- **ポイント4（`unknown`優先とtype narrowingの徹底）:** `any`を避け`unknown`から型ガード関数でnarrowingする書き方がlintルールで強制されるケースが増加。エラーハンドリングやAPI応答の型安全性を高める上で、catch節の`unknown`化がデフォルトになりつつある。
- **ポイント5（型レベルテストの導入）:** `tsd`や`expect-type`のような型レベルテストをユニットテストに組み込み、リファクタリング時の型破壊的変更を検知する手法が広がっている。ユニオン型（例: `'draft' | 'public'`）を扱う本プロジェクトのような場面で、型の網羅性チェックに有効。
