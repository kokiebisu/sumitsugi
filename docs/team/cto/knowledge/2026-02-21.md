# CTO Knowledge - 2026-02-21

## Daily Update (2026-02-21)

### 1. Next.js performance optimization 2026

- **React Server Components の本格活用:** RSCが成熟し、クライアントサイドJSバンドルを大幅削減できる段階に。コンポーネント設計の起点を「どこで実行するか」から考えるアーキテクチャシフトが必須。

- **Partial Prerendering (PPR) の活用:** Next.js 15以降でstableとなったPPRにより、静的シェル+動的ストリーミングの組み合わせが現実的な選択肢に。ページ単位のSSR vs SSG二択から脱却できる。

- **Turbopack への移行:** webpackの後継としてTurbopackが実用段階に達し、ローカルビルド・HMR速度が劇的改善。大規模プロジェクトほど恩恵が大きく、移行コストに見合う価値がある。

- **キャッシュ戦略の再設計:** Next.js 15でのキャッシュデフォルト変更（fetch自動キャッシュ廃止等）を踏まえ、明示的な`cache()`・`revalidate`設計が求められる。暗黙の挙動への依存は技術的負債になる。

- **Edge Runtimeの使い所の明確化:** ミドルウェアやA/Bテスト等の軽量処理にはEdgeが有効だが、Node.js API非対応の制約も多い。過度なEdge活用より「適材適所」の判断がパフォーマンスとDXのバランスを保つ鍵。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Prerendering (PPR) の本格普及:** Next.js 15以降でPPRが安定化し、静的シェルを即時配信しつつ動的コンテンツをSuspense境界でストリーミングする手法が標準パターンになっている。TTFBを維持しながらLCPを大幅改善できる。

- **ポイント2: Suspense境界の設計がアーキテクチャの核心:** RSCストリーミングの恩恵を最大化するには、Suspense境界をどこに置くかが設計上の最重要判断になる。細かすぎると並列フェッチの利点が消え、粗すぎるとウォーターフォールが残る。

- **ポイント3: Server Actionsとの統合でミューテーションも最適化:** フォーム送信後のUI更新をServer Actionsとストリーミングで処理することで、クライアントJS量を削減しつつリアルタイム応答感を実現できる。`useActionState`フックが鍵。

- **ポイント4: React 19のuse() APIでデータフェッチが宣言的に:** `use(promise)`でサーバーからのPromiseを直接コンポーネントで消費できるようになり、ローディング状態の管理コードが激減。ただし適切なエラーバウンダリとセットで使わないと本番障害につながる。

- **ポイント5: Edgeランタイムとの組み合わせが実用段階に:** CloudflareやVercel EdgeでRSCストリーミングを動かす事例が増加。コールドスタート問題は解消されつつあるが、Node.js専用ライブラリの制約は依然として移行コストになるため技術選定時に要注意。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの成熟とエンタープライズ採用:** tRPCはNext.js / Honoエコシステムでのデファクト化が進み、型安全なAPI契約をゼロスキーマで実現できるため、TypeScriptファーストチームでのREST/GraphQL置き換えが加速している。

- **RESTの復権とOpenAPI 3.1:** AI/LLMエージェントがAPIを直接消費するユースケースが増加し、機械可読なOpenAPI仕様の整備が急務に。Scalar・Stainlessなどのコードジェネレーターで「仕様→SDK」の自動化が標準ワークフローになりつつある。

- **GraphQLはデータグラフ特化へ収束:** Federation（Apollo/Hive）によるマイクロサービス統合と、Relay仕様に基づくページネーション標準化が進み、汎用APIではなく「複雑なリレーションを持つドメイン」専用という位置づけが明確化している。

- **HTTP Streamingとサーバー送信イベント(SSE)の台頭:** LLMレスポンスや長時間処理のストリーミングニーズにより、WebSocketより軽量なSSE / Fetch Streamingが主流に。tRPCもサブスクリプション対応でSSEをサポート済み。

- **エッジランタイム対応がAPI設計の制約に:** Cloudflare Workers / Vercel Edge等の普及で、Node.js固有のAPIや長期接続を前提とした設計が問題化。`Hono`など軽量フレームワークへの移行や、ステートレス設計の徹底がアーキテクチャ要件として浮上している。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）の主流化:** Wasm Runtimeがエッジ環境の標準実行環境として定着し、Cloudflare Workers・Fastly Compute@Edgeが言語非依存の高速コールドスタートを実現。Rustや Go製マイクロサービスのエッジ移行が加速している。

- **エッジDB・分散ストレージの成熟:** Cloudflare D1・Turso・PlanetScale Edge等、エッジに近い低レイテンシDBが実用段階に。グローバルユーザー向けアプリで「データをユーザーに近づける」設計が必須の選択肢になった。

- **AI推論のエッジシフト:** LLMの量子化・蒸留技術の進化により、小型モデル（1〜7B）がエッジで動作可能に。プライバシー保護と低レイテンシを両立したオンデバイス/エッジ推論がアーキテクチャの差別化要素になっている。

- **Durable Objects・Actor Modelの普及:** ステートフルなエッジ計算がCloudflare Durable Objectsやその後継仕様で標準化。WebSocket管理・リアルタイムコラボレーション機能をエッジのみで完結させるパターンが増加。

- **コールドスタート問題の実質的解決:** V8 Isolateベースのアーキテクチャとsnapshotting技術により、Node.jsランタイム比で100倍以上高速な起動を達成。「サーバーレス＝コールドスタートが遅い」という常識が崩れ、ミッションクリティカルな用途への採用障壁が低下している。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** FIDO2/WebAuthn標準に基づくパスキーが主流となり、パスワードレス認証が実用段階に入った。Apple・Google・Microsoftの全プラットフォーム対応により、新規サービスはパスキーをデフォルトにすべき局面。

- **AIによるリスクベース認証の高度化:** ユーザーの行動パターン・デバイス・位置情報をリアルタイム解析し、リスクスコアに応じてMFAを動的に要求する仕組みが標準化。静的なMFA設定より体験とセキュリティの両立が可能。

- **セッション管理の再設計:** JWTの長寿命トークンは廃止傾向。短命トークン（15分）＋ローテーションリフレッシュトークン、かつデバイスバインディング（DPoP）の組み合わせが推奨パターンに。

- **サプライチェーン攻撃対策としての依存性監査:** OAuth/OIDCライブラリ経由の侵害が増加。`npm audit`・Dependabot自動PRだけでなく、SBOMの生成とライセンス・脆弱性の定期棚卸しをCI/CDに組み込むことが必須。

- **ゼロトラスト前提のAPIアクセス制御:** 「ネットワーク内部は安全」という前提を完全廃棄し、すべてのAPIリクエストにトークン検証＋最小権限スコープを強制。内部サービス間通信もmTLS or サービスメッシュで暗号化・認証することがベストプラクティス。

### 6. database architecture Prisma Supabase 2026

- **Prisma + Supabase の統合成熟:** Prisma 6.x では Supabase の接続プール（PgBouncer / Supavisor）との相性が改善され、`DATABASE_URL` に `?pgbouncer=true` を付与するだけで安定した本番運用が可能になった。ただし `$transaction()` 使用時は接続モードに注意が必要。

- **Edge Runtime 対応が実用段階に:** Prisma Accelerate（グローバルキャッシュ + 接続プール）と Supabase Edge Functions を組み合わせることで、Cloudflare Workers や Vercel Edge でも ORM を介した DB アクセスが現実的になった。コールドスタートのレイテンシ問題はほぼ解消されている。

- **Supabase Realtime の採用拡大:** Postgres の CDC（Change Data Capture）をベースにした Realtime チャンネルが安定し、WebSocket による行レベルのリアルタイム同期が本番ユースケースで増加。Prisma との併用では、書き込みは Prisma・購読は Supabase クライアントと役割分担するパターンが定番化している。

- **Row Level Security (RLS) と Prisma の設計分離:** Supabase の RLS ポリシーをデータ層のセキュリティ基盤とし、Prisma はアプリ層の型安全なクエリビルダーとして位置づける二層防御アーキテクチャが推奨される。`service_role` キーの使用を最小限に抑えることが重要。

- **Supabase Branching による開発フロー変革:** 2025〜2026 年にかけて GA となった DB ブランチ機能により、Git ブランチ単位でマイグレーションをプレビュー環境に自動適用できる。Prisma Migrate との組み合わせで、CI/CD パイプライン上での schema drift 検出が標準的になっている。

### 7. WebAssembly Rust performance 2026

- **ポイント1: WASIp2によるコンポーネントモデルの実用化:** WASI Preview 2が標準化され、RustのWasmコンポーネントがホスト環境に依存せずポータブルに動作するようになった。ランタイム間の相互運用性が飛躍的に向上し、エッジ・サーバーレス環境での採用が加速している。

- **ポイント2: GCなしゼロコストが競争優位に:** Rustの所有権モデルにより、WasmでもGCポーズなしで動作するため、レイテンシが重要なリアルタイム処理（ゲーム・金融取引）においてGo/Kotlinベースより一貫して優位。特に尾部レイテンシ（p99）の安定性が評価されている。

- **ポイント3: SIMD・スレッド拡張の本格活用:** WebAssembly SIMDとShared Memoryが主要ランタイムで安定化し、Rustクレートが画像処理・ML推論でネイティブ近似のスループットを実現。`wasm-bindgen`と`rayon`の組み合わせで並列処理も現実的になった。

- **ポイント4: Wasmtime/WasmEdgeの最適化コンパイラ成熟:** ランタイム側のAOTコンパイル（Cranelift/LLVM backend）が進化し、コールドスタート問題がほぼ解消。RustのWasmバイナリはサーバーサイドで実質ネイティブバイナリと同等のパフォーマンスに達しつつある。

- **ポイント5: バイナリサイズと初期化コストがボトルネックに残る:** `wasm-opt`や`twiggy`でのサイズ最適化は必須。`std`を避け`no_std`＋`wee_alloc`等を使うか、`panic=abort`設定でバイナリを100KB台に抑えることが本番運用のベストプラクティスとして定着している。

### 8. Next.js App Router patterns 2026

- **Server Componentsのデフォルト化:** App RouterではRSC（React Server Components）がデフォルトになり、クライアントバンドルサイズを大幅削減できる。`'use client'`は本当に必要な境界にのみ付与し、無闇に広げないことが重要。

- **Partial Prerendering（PPR）の実用化:** 静的シェルと動的コンテンツを同一ページで混在させるPPRが安定化し、TTFBを落とさずにパーソナライズを実現できる。`<Suspense>`境界の設計がアーキテクチャの核心になった。

- **Server Actionsによるミューテーション:** フォーム送信やデータ更新をAPI Route不要で実装できるServer Actionsが主流に。ただしCSRF対策はNext.js側でビルトインされているが、認証チェックはAction内で必ず実施すること。

- **`use cache`ディレクティブによる細粒度キャッシュ制御:** Next.js 15以降で導入された`use cache`により、関数・コンポーネント単位でキャッシュ戦略を明示的に定義できる。`revalidateTag`との組み合わせでオンデマンド無効化が容易になった。

- **Middleware + Edge Runtimeの役割明確化:** 認証チェック・リダイレクト・A/BテストはゼロコールドスタートのMiddlewareに集約し、重い処理はNode.js Runtimeのまま維持するというレイヤー分離がベストプラクティスとして定着。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの活用範囲拡大:** Vercel Edge FunctionsはV8 isolateベースで起動レイテンシが~0ms（Cold Start不要）。2026年現在、Middleware・API Routes・Server ActionsすべてにEdge Runtimeを適用できるため、グローバルユーザー向けの認証・リダイレクト処理はEdgeへ移行が標準化されている。

- **Fluid Computeによるコスト最適化:** 2025年後半に導入されたFluid Computeにより、同一リクエスト内でEdgeとServerlessを動的に切り替え可能になった。CPU集約処理はServerless、レイテンシ敏感処理はEdgeと使い分けることで、コストとパフォーマンスを両立できる。

- **Edge ConfigとKVの組み合わせ:** フィーチャーフラグ・A/Bテスト・パーソナライゼーションはEdge Config（超低レイテンシ読み取り）とVercel KV（永続化）を組み合わせるパターンが定番。データベース呼び出しをEdgeで減らすことがP95レイテンシ改善の鍵。

- **Streaming ResponseとSuspenseの最適化:** Edge FunctionsでのStreaming（`ReadableStream`）とReact Suspenseの組み合わせにより、TTFB（Time to First Byte）を削減しつつ段階的UIレンダリングが実現。特に検索・フィード系ページで体感速度の大幅改善が報告されている。

- **バンドルサイズの制約管理:** Edge Runtimeは最大4MBのバンドル制限があり、重量級ライブラリ（`@prisma/client`等）は使用不可。`prisma/accelerate`やHTTP APIラッパーへの置き換え、または`dynamic import`でServerless側に逃がすアーキテクチャ判断が重要。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly __brand: 'UserId' }` のようなBranded/Nominal Typingが標準化し、プリミティブ型の誤用（IDの混在等）をコンパイル時に防ぐパターンが定着してきた。

- **satisfies 演算子の積極活用:** TypeScript 4.9+の `satisfies` が2026年時点で広く採用され、型推論を保持しながら型チェックを行う用途（定数オブジェクトの型安全な定義）での利用が増加している。

- **Template Literal Types による厳密なAPI契約:** `type Endpoint = \`/api/${string}\`` のようなTemplate Literal Typesでルートや文字列フォーマットを型レベルで制約し、実行時エラーをゼロに近づける設計が注目されている。

- **Zod + tRPC による型の単一ソース化:** スキーマ定義（Zod）からフロント・バック双方の型を自動導出するアーキテクチャが主流となり、型の重複定義や不整合を根本から排除できる。

- **型レベルテスト（`expect-type`）の導入:** ユニットテストと並行して型定義の正しさを `expectTypeOf().toEqualTypeOf<T>()` で検証するパターンが定着し、型のリグレッションをCIで検知できる体制が整いつつある。
