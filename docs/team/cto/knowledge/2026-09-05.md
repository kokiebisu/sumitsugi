# CTO Knowledge - 2026-09-05

## Daily Update (2026-09-05)

### 1. Next.js performance optimization 2026

- **ポイント1（React Compiler / Turbopack本番採用）:** Next.js 16ではTurbopackが本番ビルドでも安定運用可能になり、React Compilerとの組み合わせで手動memoization（useMemo/useCallback）への依存を減らせる。ビルド時間・HMR速度の両方が改善するため、大規模コードベースほど恩恵が大きい。
- **ポイント2（Partial Prerendering / PPRの本格活用）:** 静的シェルを即座に返しつつ動的部分をストリーミングするPPRが実用段階に入り、`loading.tsx`やSuspense境界の設計次第でTTFBとインタラクティブ性を両立できる。物件一覧のような「静的な骨格＋動的な検索結果」構成のページに特に有効。
- **ポイント3（キャッシュ戦略の明示化）:** `use cache`ディレクティブやcacheLifeでキャッシュの粒度をコンポーネント単位で制御できるようになり、暗黙的なフルルートキャッシュに頼らない設計が推奨される。データ更新頻度の異なる箇所（物件情報 vs ユーザー認証状態）を分離してキャッシュ設計する必要がある。
- **ポイント4（Server ComponentsでのバンドルサイズDiet）:** クライアントバンドルに漏れ出す依存関係をlint/analyzeで継続的に監視し、"use client"境界を末端コンポーネントまで絞り込むことが引き続き最重要。特に認証まわり（auth-context）やshadcn/uiコンポーネントの持ち込み方でバンドルサイズが大きく変動する。
- **ポイント5（画像・フォント最適化の自動化）:** `next/image`のAVIF/WebP自動変換とプレースホルダー戦略、`next/font`によるフォントのセルフホスティングは引き続き基本だが、2026年時点ではCore Web Vitals（特にINP）改善のためインタラクション部分のコード分割・遅延読み込みとの併用が重要度を増している。

### 2. React Server Components streaming 2026

- **ポイント1:** RSCのストリーミングは`loading.tsx`とSuspense境界の粒度設計が成熟し、単一ページ内で複数の独立したデータフェッチを並列ストリームできるようになった。設計時は「どこで待たせるか」をコンポーネント単位で明示的に決めることがUX最適化の鍵。

- **ポイント2:** Partial Prerendering（PPR）が安定運用フェーズに入り、静的シェルを即座に返しつつ動的部分だけをストリーミングする構成が標準パターンに。CDNキャッシュと組み合わせることでTTFBを大幅短縮できるが、キャッシュ無効化戦略の設計コストは依然高い。

- **ポイント3:** サーバー・クライアント境界の可視化ツール（バンドルアナライザ、RSCペイロード検査）が実用レベルに達し、"use client"の過剰付与によるハイドレーションコスト膨張を早期検知できるようになった。定期的な境界監査をCIに組み込む価値が高い。

- **ポイント4:** ストリーミングSSR中のエラーバウンダリ設計が重要度を増しており、部分的なストリーム失敗時に他のSuspense境界へ影響を波及させない「隔離されたエラーハンドリング」が実装のベストプラクティスとして定着。

- **ポイント5:** エッジランタイムでのRSCストリーミング対応が進み、地理的に分散したユーザーへの初期表示速度改善が可能に。ただしDBアクセスを伴うコンポーネントはリージョン制約があるため、データ取得層とレンダリング層の配置設計を分離して考える必要がある。

### 3. API design REST GraphQL tRPC 2026

- **GraphQL/tRPCの使い分けが明確化:** 社内向けフルスタックTS環境ではtRPCの型安全性が圧倒的に効率的だが、外部パートナーAPI（不動産情報連携など）は依然REST/OpenAPIが標準。sumitsugiのような単一Next.jsモノレポ構成ならtRPC一択で、スキーマ変換コストを削減できる。

- **BFF層でのGraphQL Federationは過剰投資になりがち:** マイクロサービス化していない現段階（MVPフェーズ）でGraphQL Federationを導入するのは複雑性に見合わない。物件データ・ユーザーデータが単一DBなら、REST+tRPCのシンプル構成で十分。

- **AIエージェント連携を見据えたAPI設計:** 2026年はLLMエージェントが直接APIを叩くケースが増加。OpenAPI/JSON Schemaでの厳密な入出力定義がMCPツール化の前提になるため、将来的にAIエージェント経由での物件検索・引き継ぎ手続き自動化を見据えるなら、tRPCルーターにZodスキーマを付与しておくとMCP変換が容易。

- **Edge Runtime対応がAPI設計の分岐点に:** Next.js 16のEdge Functionsでレイテンシ最適化する場合、tRPCのNode.js依存部分（一部ミドルウェア）が制約になることがある。物件検索のような高頻度アクセスAPIはEdge対応を前提にシンプルなREST/Route Handlersで実装する方が安全。

- **契約テスト（Contract Testing）の重要性が増大:** 前の住人↔次の住人のマッチングのような複数ステークホルダーが絡むAPIは、Zodスキーマをテストコードと共有し、E2E前に契約違反を検知する仕組みが必須。standards.mdの「Zodスキーマによる境界検証」方針と直接整合する。

### 4. serverless edge computing 2026

- **ポイント1（WASM主導のエッジランタイム）:** Cloudflare Workers・Fastly Compute・Vercel Edge FunctionsなどWASMベースのランタイムが主流化し、コールドスタートがミリ秒未満まで縮小。sumitsugiのような画像多用・SEO重視の物件検索UIでは、地理的に近いエッジでのSSR/ISRがCore Web Vitals改善に直結する。

- **ポイント2（データレイヤーのエッジ分散）:** D1/Turso/PlanetScaleなどエッジレプリケーション対応DBが実用段階に入り、リージョン間レイテンシがボトルネックになりにくくなった。ただし強整合性が必要な予約・決済処理は依然オリジンDBに寄せる設計判断が必要（読み取りはエッジ、書き込みは中央、が2026年のデファクト）。

- **ポイント3（Next.js × エッジのデフォルト化）:** Next.js 16ではミドルウェア・一部Server Componentsのエッジ実行がデフォルト選択肢になりつつあり、Vercel以外（Cloudflare、Deno Deploy）へのマルチプラットフォーム対応も進展。ベンダーロックイン回避の観点で、標準Web API（Fetch/Request/Response）準拠のコードを書くことが移植性の鍵。

- **ポイント4（コスト構造の変化）:** 従量課金＋常時起動不要のモデルにより、低トラフィック期のインフラコストが大幅減。ただしAI推論（画像認識・レコメンド）をエッジに載せる場合はGPU非対応エッジが多く、推論だけは中央/専用APIに残すハイブリッド構成が現実的。

- **ポイント5（オブザーバビリティの複雑化）:** 分散実行環境が増えるほどトレーシング・ログ集約が難化。OpenTelemetry対応が事実上の標準になり、エッジ導入前にトレースID伝搬とエラー監視基盤を先に整備しないと障害切り分けコストが跳ね上がる。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** 2026年時点でパスキーはパスワードに代わる主流認証手段となっており、Appleやgoogleに限らずBtoB SaaSでも実装が標準化。フィッシング耐性が高く、SMS認証より安全なため新規実装では優先的に採用すべき。

- **ゼロトラスト前提のセッション管理:** IPやデバイスだけでなく、行動パターン（操作速度、アクセス頻度）まで含めたリスクベース認証が一般化。sumitsugiのような個人間取引プラットフォームでは、なりすまし詐欺対策として「前の住人」「次の住人」間のやり取り時に追加認証を挟む設計が有効。

- **トークン管理の厳格化:** JWTの長期利用が攻撃対象になりやすいため、短命アクセストークン＋リフレッシュトークンのローテーション、かつリフレッシュトークンの再利用検知（token replay detection）が必須要件に。`src/contexts/auth-context.tsx` 実装時はこの前提で設計する必要がある。

- **多要素認証の摩擦最小化:** 一律MFA強制ではなく、取引額や個人情報アクセスなど「リスクの高い操作」にのみステップアップ認証を要求する設計がUX/セキュリティ両立の鍵。物件情報の`draft`→`public`切り替えや決済関連操作は要ステップアップ対象の候補。

- **サプライチェーン・依存パッケージ監査:** 認証ライブラリ自体の脆弱性（npm/bunパッケージの改ざん）が2025-2026年に増加傾向。認証まわりの依存関係は`bun run build`前のCI段階でSBOM/脆弱性スキャンを組み込むことが望ましい。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMのRust脱却とパフォーマンス向上:** Prisma 6以降はQuery EngineをTypeScript/WASMベースに刷新し、Rustバイナリ依存を解消。エッジランタイム（Vercel Edge, Cloudflare Workers）でのコールドスタートが大幅改善され、Next.js 16のEdge Middlewareとの相性が良くなった。

- **SupabaseのPrisma公式サポート強化:** SupabaseがPrisma Accelerate/Pulseとの統合を公式ドキュメント化し、Connection Pooling（PgBouncer）周りの設定ミスによる`too many connections`エラーが起きにくくなった。sumitsugiのようなサーバーレス構成では`DIRECT_URL`と`DATABASE_URL`の使い分けを徹底すべき。

- **RLS（Row Level Security）とORMの二重防御:** SupabaseのRLSポリシーとアプリケーション層のZodバリデーションを併用する構成が標準化。前の住人/次の住人のようなロールベースアクセス制御は、RLSで「最終防衛線」を敷きつつPrisma側で型安全なクエリを書くのがベストプラクティス。

- **リアルタイム機能とPrismaの組み合わせ:** Supabase Realtimeのpostgres_changesをPrismaのスキーマ変更と同期させる際、マイグレーション時にレプリケーションスロットが壊れるケースが報告されており、`prisma migrate deploy`前にRealtimeのpublication設定を確認するフローが推奨されている。

- **ブランチング環境の活用:** Supabaseのデータベースブランチング機能とPrisma Migrateを組み合わせ、PRごとに独立したDB環境を自動生成するCI/CDパターンが2026年時点で一般化。E2Eテスト（Playwright）の並列実行時のデータ競合を防げるため、sumitsugiのCI強化にも応用余地あり。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC（Garbage Collection提案)の標準化が進み、Rustでも`wasm32-unknown-unknown`に加えてGC連携型のホスト言語との相互運用が容易になりつつある。ただしRust自体はGC不要なため、恩恵は主にJS/他言語とのインターオペ性能改善に出る。
- **ポイント2:** Component Model + WASIプレビュー2の普及により、Rustコンポーネントをブラウザ外（サーバーサイド・エッジ）でネイティブに近い起動速度で実行できるようになり、コールドスタートがコンテナ比で大幅短縮できる。
- **ポイント3:** `wasm-opt`やLTO、`codegen-units=1`の最適化に加え、SIMD128命令の主要ブラウザ全対応が完了し、画像処理・暗号演算などの数値計算はネイティブの80-90%程度の性能に到達している。
- **ポイント4:** Rustのバイナリサイズ最適化（`opt-level="z"`、`wasm-snip`、tree-shaking強化）がツールチェイン標準に組み込まれ、初回ロード時間を意識した設計がしやすくなった。
- **ポイント5:** マルチスレッド対応（`SharedArrayBuffer` + Web Workers連携）がRustの`wasm-bindgen-rayon`等で実用段階に入り、CPUバウンドな前処理（画像・PDF生成等）をUIブロックなしで並列実行できる。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR):** 静的シェルをビルド時に生成し、動的部分（例：物件の空き状況・引越し費用の見積り）だけをストリーミングで後から埋める構成が標準化。物件詳細ページのようなSEO重視×パーソナライズ混在のUIと相性が良く、TTFBを大幅改善できる。

- **Server Actionsによるミューテーション集約:** フォーム送信や状態変更をAPI Routeではなく`'use server'`関数に寄せる設計が主流。物件登録・引き継ぎ申請フォームなどのバックエンドロジックをコンポーネントに隣接させられ、型安全性と保守性が向上する一方、キャッシュ再検証（`revalidatePath`/`revalidateTag`）の設計を誤るとstaleデータのバグを生みやすいので注意が必要。

- **`use cache`ディレクティブによる粒度制御:** ページ単位ではなく関数・コンポーネント単位でキャッシュ戦略を宣言できるようになり、fetchのオプション指定より意図が明確になる。前の住人の活動歴データなど更新頻度の低い情報と、リアルタイム性が必要な空室状況を同一ページ内で使い分けやすい。

- **React Compilerによるメモ化の自動化:** `useMemo`/`useCallback`の手動最適化が不要になりつつあり、コードレビューの観点も「メモ漏れ」から「不要な再レンダリングの構造的原因」にシフトしている。ただし導入時は既存の手動メモ化コードとの相性を必ず検証すべき。

- **Turbopackの本番ビルド標準化:** ローカル開発だけでなく`bun run build`のプロダクションビルドでもTurbopackが既定になり、大規模モノレポでのビルド時間短縮が顕著。CIのビルドステップが軽くなる分、型チェックやE2Eなど他の検証工程に時間を回せるようになっている。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約とV8アイソレート最適化:** Node.js APIが使えない制約は変わらないが、コールドスタートは数ミリ秒まで縮小しており、認証チェックやリダイレクト、A/Bテストの判定など「軽量・低レイテンシが必須」な処理をEdge Functionsに寄せ、DB接続や重い処理はServerless/Node runtimeに残す使い分けが定石化している。

- **Streaming SSRとの組み合わせ:** Edge Functionsでのレスポンスストリーミングを使い、ヘッダーやシェル部分を即座に返しつつコンテンツ本体を段階的に配信することでTTFBを改善できる。うちのプロパティ詳細ページのような画像多めのSSRページで有効。

- **リージョン近接ルーティングとキャッシュ戦略:** `runtime: 'edge'`指定時のリージョン自動選択に加え、Vercel側のData Cache/ISRとの併用でDB往復を減らすパターンが主流。物件検索のような読み取り頻度の高いAPIはEdge + キャッシュタグ無効化戦略との相性が良い。

- **観測性とコスト管理の強化:** Edge FunctionsのCPU時間・実行回数ベースの課金が明確化され、Vercel標準のObservability（OpenTelemetry連携）でルートごとの実行時間を可視化しやすくなった。本番投入前に重い処理が紛れ込んでいないか計測してから展開すべき。

- **middleware.tsの責務を絞る設計:** すべてのリクエストを通るmiddlewareに認証・国際化・Bot判定などを詰め込みすぎるとエッジ全体のレイテンシが底上げされるため、必要最小限の判定のみに絞り、重い処理はAPI Route側に分離する設計が推奨されている。

### 10. TypeScript type safety patterns 2026

- **ポイント1（型レベルバリデーションの標準化）:** Zod/Valibotのようなスキーマライブラリで型定義とランタイム検証を一体化する手法が定着し、`z.infer`で型を自動導出することで「境界での検証漏れ」によるバグを構造的に防げる。当プロジェクトでもAPI境界・フォーム入力にはZodスキーマを必須としている方針は、この流れに沿っている。

- **ポイント2（`satisfies`演算子の定着）:** TypeScript 4.9で導入された`satisfies`が2026年には標準的な書き方として定着し、リテラル型の推論を保持しつつ型チェックできるため、`as const`と組み合わせた設定オブジェクトやステータスのUnion型（例: `'draft' | 'public'`）の安全な定義に有効。

- **ポイント3（Discriminated Unionによる状態管理の徹底）:** 「あり得ない状態を型で表現不可能にする」設計（例: `{status: 'loading'} | {status: 'success', data: T} | {status: 'error', error: E}`）が主流になり、nullチェックの散在やoptionalプロパティの誤用によるランタイムエラーを減らせる。

- **ポイント4（型の一貫性チェックの自動化）:** Union型やstatusフィールドを変更する際、ripgrep/ts-pruneによる全使用箇所の洗い出しをCIに組み込む動きが強まっている。当プロジェクトの「Union型変更前に全使用箇所をgrep」というルールもこの実務知に合致しており、型の破壊的変更を早期検知できる。

- **ポイント5（AIコード生成との相性）:** 型が厳格であるほどAIエージェント（Claude Codeなど）が生成するコードの正しさをコンパイラが即座にフィードバックできるため、「型安全性への投資」がAI駆動開発の生産性に直結するという認識がCTOレベルで広がっている。
