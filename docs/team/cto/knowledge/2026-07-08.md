# CTO Knowledge - 2026-07-08

## Daily Update (2026-07-08)

### 1. Next.js performance optimization 2026

- **React Server Components とストリーミングの深化:** RSCによりクライアントJSバンドルを大幅削減しつつ、`loading.tsx`とSuspenseによる部分的ストリーミングでTTFBとLCPを両立できる。データフェッチをコンポーネント単位に分散させることで、ウォーターフォールを回避しやすくなる。

- **Partial Prerendering (PPR) の本格運用:** 静的シェルを即座に返しつつ動的部分のみをストリーミングするPPRが安定期に入り、ECサイトや不動産物件ページのような「一部は静的・一部は個人化」なページに最適。sumitsugiの物件詳細ページでも、価格や在庫状況など動的要素だけをストリーミングし、写真ギャラリーやレイアウトは静的化する構成が有効。

- **`next/image`とAVIF/レスポンシブ最適化:** 画像重量がLCPのボトルネックになりやすいため、AVIF形式とサイズ別`srcset`の自動生成を徹底し、CDNエッジでのキャッシュ戦略と組み合わせることが重要。物件写真のような画像点数が多いUIでは特に効果が大きい。

- **キャッシュ戦略の明示化（`use cache`ディレクティブ）:** Next.js 15以降で導入された`use cache`により、データ・コンポーネント単位でキャッシュ境界を明示的に制御できるようになった。暗黙的なフルルートキャッシュに依存せず、更新頻度の異なるデータ（物件情報 vs ユーザーセッション）を分離してキャッシュ設計することがパフォーマンスと鮮度のバランスの鍵。

- **Bunランタイムとビルド時間の最適化:** Bunを採用している構成では、`bun run build`のコールドスタート・型チェック時間がCI全体のボトルネックになりやすいため、Turbopackのインクリメンタルビルドと組み合わせてCI時間を継続的に計測・改善することが、開発速度とデプロイ頻度の両方に直結する。

### 2. React Server Components streaming 2026

- **Partial Prerendering との統合:** Next.js 16ではPPR(Partial Prerendering)がRSCストリーミングと組み合わさり、静的シェルを即座に返しつつ動的部分だけSuspense境界でストリーミングする構成が主流化。初期表示速度(TTFB)とSEOを両立できる。
- **selective hydration の粒度向上:** `<Suspense>`単位でのハイドレーション優先度制御がより細かくなり、ユーザー操作(クリック等)があったコンポーネントを優先的にハイドレートする挙動がデフォルト化。体感パフォーマンスが向上する一方、実装時はSuspense境界の設計ミスが即座に表示崩れに繋がるため注意。
- **キャッシュ戦略の複雑化:** RSCのstreaming responseとNext.jsのData Cache/Router Cacheの相互作用が複雑になり、`fetch`のrevalidate設定やタグベース無効化(`revalidateTag`)を誤ると古いストリームが配信されるリスクがある。本プロジェクトの`draft`/`public`ステータス切り替えのような状態依存UIでは特に検証が必要。
- **エラーバウンダリとストリーミングの相性:** ストリーミング中に発生したサーバーエラーがクライアントに正しく伝播せず「無限ローディング」化するケースが依然課題。`error.tsx`とSuspense境界の設計を組み合わせたフォールバック戦略が実質必須になっている。
- **バンドルサイズより「配信タイミング」が指標に:** RSCの普及でクライアントJSバンドルサイズの重要性は相対的に下がり、代わりに「いつ・どの順でストリームが届くか」がパフォーマンス設計の中心指標になっている。Lighthouseだけでなく実ユーザーのストリーミング順序を可視化する計測が推奨される。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの実用的優位性）:** 社内向けAPIやフルスタックTypeScriptモノレポでは、tRPCがスキーマ定義とクライアント型を自動同期できるため、GraphQLのようなスキーマ管理コストなしにE2E型安全性を実現でき、sumitsugiのようなNext.js App Router構成との親和性が高い。

- **ポイント2（GraphQLは外部公開・複雑なクエリ要件がある場合に限定採用）:** 前の住人・次の住人・物件情報など関連データが複雑に絡む画面でオーバーフェッチ/アンダーフェッチを避けたい場合はGraphQLが有効だが、単一チーム・単一クライアント（Web中心）構成では運用コストに見合わないケースが多く、2026年時点では「本当に必要か」を精査してから導入すべきという流れが強い。

- **ポイント3（RESTは依然としてデファクト、特に外部連携・決済系）:** 引越し費用の決済連携や外部サービス（弁護士確認フロー、外部API）とのインテグレーションでは、シンプルさとキャッシュ制御のしやすさからRESTが第一選択であり続けている。

- **ポイント4（BFF/Server ActionsによるAPI層の簡素化トレンド）:** Next.js App RouterのServer Actionsやedge functionsの普及により、「API設計」そのものを最小化し、フロントとバックの境界を薄くする方向性が主流化している。sumitsugiのようなMVPフェーズのプロダクトでは、tRPCまたはServer Actionsのみで完結させ、将来的な外部パートナー連携が具体化した時点でREST/GraphQL層を追加する段階的アプローチが最も開発速度とメンテナンス性のバランスが良い。

- **ポイント5（認証・入力検証の一元化が設計上の最重要ポイント）:** どのAPIスタイルを選ぶにせよ、Zodなどによる境界でのスキーマ検証とtRPC/REST共通のミドルウェアでの認可チェックを一元化することが、セキュリティ標準（本プロジェクトの`.claude/rules/standards.md`に準拠）を満たす上で技術選定より優先度が高い。

### 4. serverless edge computing 2026

- **ポイント1（V8 Isolates主流化）:** Cloudflare Workers / Deno Deploy型の軽量V8 Isolateランタイムがデファクトになりつつあり、コールドスタートがミリ秒未満まで縮小。sumitsugiのNext.js App Routerも、Vercel Edge Runtimeへの部分移行で認証チェックや物件ステータス判定（draft/public）のような軽量処理を高速化できる余地がある。

- **ポイント2（エッジDBとの結合）:** Cloudflare D1、Turso（libSQL）、PlanetScaleのようなエッジレプリケーション対応DBが普及し、読み取りをユーザー近傍で完結できるように。物件検索・一覧表示のような読み取り比率の高いページはエッジキャッシュ+エッジDB化でTTFBを大幅短縮できる。

- **ポイント3（ステートフルエッジ = Durable Objects/Actor Model）:** Cloudflare Durable ObjectsやFly.ioのようなアクターモデル型サービスにより、エッジ上でもセッション状態や在庫ロックのような一貫性が必要な処理が扱えるようになった。予約・引き渡しフローの排他制御に応用できる可能性。

- **ポイント4（Server ActionsとEdgeの相性問題）:** Next.jsのServer Actionsは重い依存（Prisma等のNode専用ライブラリ）とEdge Runtimeの相性が依然課題。フル移行より「認証・リダイレクトなど軽量なMiddleware/Edge Functionのみエッジ化し、DB書き込みはNode Runtimeに残す」ハイブリッド構成が2026年の現実解。

- **ポイント5（コスト構造の変化）:** エッジ実行は従量課金がリクエスト数ベースになりがちで、トラフィックが少ない現フェーズ（ベータローンチ前）では過剰投資になりやすい。MVPの現状規模では、まずMiddlewareレベルの部分的エッジ化に留め、本格移行はトラフィック増加後の判断が妥当。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）標準化の加速:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の主流になりつつあり、フィッシング耐性とUX向上を両立できる。sumitsugiのような個人間取引プラットフォームでは、なりすまし対策として早期導入が有効。

- **多層防御としてのリスクベース認証（Adaptive MFA）:** IPレピュテーション・デバイスフィンガープリント・行動分析を組み合わせ、ログイン試行ごとにリスクスコアを算出し動的にMFA要求を変える方式が標準化。物件情報や個人情報を扱う本サービスでは、不審なアクセスパターン検知が実装コストに対して効果が高い。

- **トークン管理の厳格化（短命アクセストークン + リフレッシュトークンローテーション）:** JWTなどのアクセストークンは有効期限を短く保ち、リフレッシュトークンは使用のたびに再発行・旧トークン失効させる「ローテーション方式」が事実上の必須要件になっている。トークン漏洩時の被害範囲を最小化できる。

- **サプライチェーン・依存パッケージ経由の認証迂回対策:** npm/Bunエコシステムの依存脆弱性を突いた認証バイパスが増加傾向にあるため、`bun audit`相当の定期スキャンと、認証ミドルウェアの外部パッケージ依存を最小限に抑える設計が重要。

- **セッション固定化・CSRF対策の基本徹底:** 新しいトレンドに目を奪われがちだが、Cookieの`SameSite=Strict`/`HttpOnly`/`Secure`属性、CSRFトークン、ログイン後のセッションID再生成といった基本対策の徹底が依然として最も費用対効果の高い防御策である。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORM の進化:** Prisma 6以降で導入されたRust非依存のTypeScriptネイティブクエリエンジン（Query Compiler）が安定し、コールドスタートが大幅短縮。Supabaseのようなサーバーレス/エッジ環境との相性が向上し、Vercel Edge Functionsからの直接接続がしやすくなっている。

- **Supabase の主要機能拡張:** Row Level Security (RLS) とPrisma Client を組み合わせたマルチテナント設計が定番化。認証(Supabase Auth)・ストレージ・リアルタイム購読を単一プラットフォームで扱えるため、sumitsugiのような「前の住人→次の住人」の引き継ぎフローに必要なユーザー間データ共有・権限分離を実装しやすい。

- **コネクションプーリング戦略:** Supabase の PgBouncer（Transaction mode）とPrismaの相性問題は解消傾向にあるが、依然としてサーバーレス関数からの接続数管理は要注意。`directUrl` と `pooledUrl` を使い分け、マイグレーション時のみ直接接続する設計がベストプラクティス。

- **型安全性とスキーマ駆動開発:** Prisma Schema を単一の真実源とし、Zodバリデーション（本プロジェクトの標準）とTypeScript型を自動生成する構成が主流。物件ステータス（`draft`/`public`）のようなユニオン型は、Prismaのenum定義と`.claude/rules/standards.md`のガイドライン通りコードベース全体でgrep確認しながら変更するのが安全。

- **AIエージェント連携の増加:** SupabaseのVector拡張（pgvector）を使ったRAG基盤や、Claude Code等のAIエージェントがPrisma Migrateを自動実行するCI/CDパイプラインが2026年時点で一般化。ただし自動マイグレーションは本番DBへの破壊的変更リスクがあるため、承認フロー（PRレビュー必須）を組み込むことが重要。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC（Garbage Collection提案）の主要ブラウザ対応が進み、Rustの`wasm-bindgen`を介さずにより軽量なバイナリ生成が可能になりつつあるが、Rust自体はGCなし言語のため恩恵は主にKotlin/Java系言語向けで、Rustは引き続きサイズ最適化（`wasm-opt`、`opt-level = "z"`）が有効。

- **ポイント2:** Component Model / WASI Preview 2の安定化により、Rustで書いたWasmモジュール間の型安全な連携やホスト関数呼び出しが標準化されつつあり、サーバーサイド（Cloudflare Workers、Fastly Compute等）でのマイクロサービス的な利用が現実的になっている。

- **ポイント3:** SIMD128やスレッド（`wasm32-wasip1-threads`）のサポートが安定し、画像処理・動画エンコード・数値計算など重い処理をブラウザ内でネイティブに近い速度で実行できるようになったため、フロントエンドの重い処理をRust+Wasmへオフロードする選択肢が現実的なパフォーマンス改善策になる。

- **ポイント4:** ビルドツールチェーン（`wasm-pack`、`trunk`、`cargo-component`）の成熟でRust→Wasmの開発体験が向上した一方、依然としてバンドルサイズとJS↔Wasm境界でのシリアライゼーションコストがボトルネックになりやすく、頻繁に呼ばれる小さな関数はJS側に残し、計算量の多い処理だけをWasmに委譲する設計が推奨される。

- **ポイント5:** エッジコンピューティング領域（Cloudflare Workers、Fermyon Spin等）でRust+Wasmがコールドスタート時間の短さとセキュアなサンドボックス実行を武器に採用が拡大しており、リクエストごとの起動が多いアーキテクチャではNode.jsコンテナよりコスト効率で優位に立つケースが増えている。

### 8. Next.js App Router patterns 2026

- **React Server Components前提の設計:** App Routerではデフォルトでサーバーコンポーネントとなるため、`'use client'`境界を最小限に留め、データフェッチはできるだけサーバー側で完結させる設計が定着してきています。クライアントバンドルサイズの削減とTTFB改善に直結します。

- **Partial Prerendering (PPR) の実用化:** 静的シェルと動的コンテンツを1つのルートで組み合わせられるPPRが安定版となり、SEOが重要なページ（物件一覧など）で静的部分を即座に表示しつつ、パーソナライズ部分をストリーミングする構成が主流になりつつあります。

- **Server Actionsによるフォーム処理の簡素化:** APIルートを介さずServer Actionsで直接ミューテーションを行うパターンが標準化し、`useActionState`と組み合わせた楽観的UI更新がフォーム実装のデフォルトパターンになっています。物件登録・問い合わせフォームなどで採用価値が高いです。

- **キャッシュ戦略の明示化:** Next.js 15以降でGETルートやクライアントルーターキャッシュがデフォルトで「キャッシュしない」方向に変わったため、`revalidate`やキャッシュタグを明示的に指定する設計判断がチーム全体で必要になっています。曖昧なキャッシュ挙動によるバグを防ぐには、キャッシュポリシーをコードレビューの必須観点に加えるのが有効です。

- **並行ルート・インターセプトルートの実用パターン定着:** モーダル表示（物件詳細のクイックビューなど）で`@modal`スロットとインターセプトルートを組み合わせる実装が一般化し、URLを保ったままモーダルUXを実現する手法がベストプラクティスとして確立しています。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge RuntimeとNode.jsランタイムの使い分けが重要。純粋なリクエスト処理・リダイレクト・A/Bテストなどの軽量処理はEdge Functionsに寄せ、DBコネクションプーリングや重いnpmパッケージ依存の処理はNode.js Functionsに残すことで、コールドスタートとレイテンシを最小化できる。

- **ポイント2:** Fluid Compute（Vercelの新しい実行モデル）の活用により、同一インスタンス内で複数リクエストを並行処理できるため、I/Oバウンドな処理（外部API呼び出しなど）のコスト効率が大幅に改善している。Next.js 16のApp Routerとの相性も良く、積極採用を検討すべき。

- **ポイント3:** Edge Middlewareの実行時間・バンドルサイズ制限（1MB前後）を意識した設計が必須。認証チェックなど本当に全リクエストに必要なロジックのみをMiddlewareに置き、それ以外はRoute Handler側に移すことでレイテンシとバンドルサイズを抑えられる。

- **ポイント4:** リージョン指定（`export const preferredRegion`）を活用し、DBやSupabaseなど主要データソースに地理的に近いリージョンでEdge Functionsを実行することで、体感速度が大きく変わる。sumitsugiのようにユーザーが日本国内中心なら`hnd1`固定が有効。

- **ポイント5:** Streaming SSR + Edge Functionsの組み合わせで、物件一覧ページなどのTTFB（Time To First Byte）を短縮できる。ただし全ての処理をEdgeに寄せるとPrisma等のNode専用ライブラリが動かないため、データ取得層は明確に分離しておく設計が長期的な保守性を左右する。

### 10. TypeScript type safety patterns 2026

- **ポイント1（`satisfies`とconst型パラメータの定着）:** TypeScript 5.x系で導入された`satisfies`演算子と`const`型パラメータが標準的な書き方として定着し、型推論を保ちながら過剰な型注釈を排除するパターンが主流になっている。sumitsugiの`site-config.ts`のような設定オブジェクトでも、型の広がりを防ぎつつ推論を活かせる。

- **ポイント2（Zodなどスキーマ駆動の型生成）:** `.claude/rules/standards.md`にもある通り境界でのZodバリデーションが標準化され、`z.infer<typeof Schema>`でランタイム検証と静的型を単一ソースから生成するパターンが一般化。フォームや物件データ（`draft`/`public`ステータスなど）のユニオン型はスキーマ側で一元管理すべき。

- **ポイント3（Branded Types/Nominal Typingの普及）:** `id: string`のような構造的型の取り違えバグ（例: sellerIdとlistingIdの混同）を防ぐため、branded typeでの型安全なID管理がフロントエンド/バックエンド間で一般的になっている。

- **ポイント4（テンプレートリテラル型によるルーティング安全性）:** Next.js App Routerのようなファイルベースルーティングにおいて、テンプレートリテラル型でパス文字列を検証し、`href`のタイポをコンパイル時に検出するパターンが普及。動的ルート（`properties/[id]`等）の型安全なリンク生成に有効。

- **ポイント5（AIエージェント生成コードの型ガードとしての活用）:** 自律開発ワークフロー（`autonomous-developer.yml`）のようにAIがコードを生成する体制では、strictモード＋noUncheckedIndexedAccessを必須にし、型システム自体をAI生成コードの品質ゲートとして機能させる運用が広がっている。
