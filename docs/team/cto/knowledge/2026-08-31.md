# CTO Knowledge - 2026-08-31

## Daily Update (2026-08-31)

### 1. Next.js performance optimization 2026

**ポイント1:** Partial Prerendering(PPP)の安定版採用が進み、静的シェルを即座に返しつつ動的部分をストリーミングすることで、TTFBとLCPを大幅に改善できる。物件一覧ページのような公開ページで特に効果的。

**ポイント2:** React Server Components(RSC)によるサーバー側データフェッチの活用で、クライアントバンドルサイズを削減しウォーターフォールを解消。物件詳細ページのようなデータ量が多いページで顕著な効果がある。

**ポイント3:** `next/image`の自動最適化とAVIF/WebP対応に加え、Turbopackのビルド高速化により開発体験とプロダクションビルド時間の両方が改善されている。画像中心のプラットフォーム(物件写真)には必須の最適化。

**ポイント4:** キャッシュ戦略の明示化(`cache: 'force-cache'`や`revalidate`の細かい制御)が重要になり、ステータス(draft/public)が変わる物件データではISRの再検証タイミング設計がパフォーマンスとデータ鮮度のトレードオフを左右する。

**ポイント5:** Core Web Vitalsの新指標(INP)への対応が引き続き重要で、認証フローやフォーム操作(引き継ぎ申請など)のインタラクション応答性を計測・改善することがコンバージョン率に直結する。

### 2. React Server Components streaming 2026

- **ポイント1（Partial Prerendering の主流化）:** Next.js 16ではPPR（Partial Prerendering）が安定版となり、静的シェルを即座に返しつつ動的部分だけをストリーミングする設計が標準化。うちのproperties一覧ページのような「検索フィルタは動的・カード枠は静的」という構成に特に効く。

- **ポイント2（Suspense境界の粒度設計が本質的な最適化ポイント）:** RSCストリーミングの体感速度は、`loading.tsx`やSuspense境界をどこに置くかでほぼ決まる。物件詳細ページなら「基本情報→即表示」「引越し費用の見積もり→非同期ロード」のように、UIの優先度に沿って境界を切るのが重要。

- **ポイント3（Server Actionsとの組み合わせでネットワークウォーターフォールを削減）:** クライアント側でのfetch連鎖をServer Componentsのデータ取得に寄せることで、ブラウザ⇄サーバーのラウンドトリップを削減できる。認証コンテキスト（`auth-context.tsx`）を経由する処理は特に恩恵が大きい。

- **ポイント4（キャッシュ戦略の複雑化に注意）:** ストリーミング導入によりRequest Memoization / Data Cache / Full Route Cacheの3層が絡み合い、「前の住人」データ更新後に古いキャッシュが表示されるバグが起きやすい。`revalidateTag`の設計をデータモデル変更時に必ず見直す必要がある。

- **ポイント5（E2Eテストのタイミング依存に注意）:** ストリーミングUIはPlaywrightで「要素が最終的に表示される」ことを待つ必要があり、従来の即時アサーションが不安定化しやすい。`waitFor`ベースのテスト設計を標準にすべき。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCの採用は「TypeScriptフルスタック」構成のチームで急速に定着しており、フロントエンドとバックエンドで型を共有できるためスキーマ定義や型生成の二重管理が不要になる。Next.js App Router + Server ActionsとtRPCの役割分担が2026年の主流論点で、社内向け・単一フロントエンドのAPIならtRPC、複数クライアント（モバイル/外部連携）が絡むならREST/GraphQLという使い分けが実用的。
- **ポイント2:** GraphQLは大規模・複数クライアントを持つプロダクトでの採用が根強い一方、N+1問題やキャッシュ戦略の複雑さから中小規模チームでは敬遠される傾向が続いている。sumitsugiのような単一Webアプリ中心のMVPでは、GraphQLのオーバーヘッドは現時点では過剰投資になりやすい。
- **ポイント3:** RESTは依然として「デファクトスタンダード」であり、OpenAPI（Swagger）ベースのスキーマファースト開発とAIコード生成（Claude Codeなど）の相性が良く、型安全なクライアントSDKを自動生成するワークフローが2026年のベストプラクティスとして定着している。
- **ポイント4:** Zodなどのスキーマバリデーションライブラリを軸に「1つのスキーマ定義から型・バリデーション・APIドキュメントを生成する」アプローチ（tRPC + Zod、Hono + Zod OpenAPIなど）が主流化しており、境界（システム境界）での入力検証を徹底する現行のコーディング規約とも整合性が高い。
- **ポイント5:** エッジランタイム（Vercel Edge, Cloudflare Workers）向けAPI設計では、GraphQLの重いランタイムよりtRPCやシンプルなREST+Zodの組み合わせがレイテンシ面で有利とされ、Next.js 16のようなエッジファーストなフレームワークとの親和性を考えると、sumitsugiの現行構成（Next.js + Bun）にはtRPCまたは型安全RESTが妥当な選択肢と言える。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化が加速:** V8 IsolatesベースのCloudflare Workers、Deno Deploy、Vercel Edge Functionsなどが収束し、WinterCG(Web-interoperable Runtimes)準拠のAPIが事実上の標準になりつつある。ベンダーロックインを避けるため、Fetch API/Web Standardsに準拠したコードを書くことが移植性の観点で重要。

- **コールドスタート問題の実質的解消:** V8 Isolate方式やWasmベースのランタイムにより起動時間が1桁ms台まで短縮され、レイテンシSLAが厳しい認証・決済フローでもエッジ実行が実用的になっている。sumitsugiの物件検索や決済処理のようなレイテンシ敏感な処理はエッジ移行の候補になり得る。

- **エッジDBとの統合が鍵:** Turso(libSQL)、Cloudflare D1、PlanetScaleなど「エッジに近いレプリカを持つDB」が普及し、エッジ関数単体では解決できなかったデータレイヤーのレイテンシ問題に対処できるようになった。Next.js 16のようなフレームワークではこれらとの統合パターンが整備されつつある。

- **コスト構造の変化に注意:** リクエスト課金モデルはトラフィックが読みにくいMVP初期には有利だが、スケール後は従来のコンテナ/サーバー型より割高になるケースがあるため、ローンチ後のトラフィック予測をもとに再評価すべき。

- **観測可能性(Observability)がまだ発展途上:** 分散トレーシングやログ集約がエッジ環境では中央集権的なサーバーより複雑になりがちで、OpenTelemetry対応が進んでいるものの、本番導入前にエラートラッキング・アラート体制を明確にしておく必要がある。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証（Passkeys）がiOS/Android/主要ブラウザで標準搭載され、フィッシング耐性のある認証がデフォルトになりつつある。sumitsugiでも次のPhaseでパスキー対応を検討し、パスワードリセット関連のサポートコストを削減できる。

- **多層防御としてのリスクベース認証:** 単純な2FAから、デバイスフィンガープリント・行動パターン・IPレピュテーションを組み合わせたアダプティブ認証へ移行が進んでいる。不動産取引のような高額決済が絡むプラットフォームでは、異常ログイン時のみ追加認証を要求する設計がUXとセキュリティの両立に有効。

- **トークン管理の厳格化:** JWTの長期保存や`localStorage`格納が引き続き主要な脆弱性要因。短命アクセストークン＋HttpOnly Secure Cookieでのリフレッシュトークン管理、および定期的なローテーションが必須要件として定着している。

- **セッション/認可の分離とゼロトラスト化:** 認証（誰か）と認可（何ができるか）を明確に分離し、APIレベルでの最小権限原則（RBAC/ABAC）を徹底する流れが強まっている。前の住人・次の住人間のデータアクセス境界（物件情報・個人情報の閲覧権限）を厳密に設計する必要がある。

- **サプライチェーン・依存関係の認証リスク:** OAuth/SSO連携先（Google, LINE等）のライブラリ脆弱性やトークン漏洩が2025-2026年で増加傾向。認証まわりの依存パッケージは`bun audit`等での定期スキャンとバージョン固定が推奨される。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORM v6以降のマルチファイルスキーマ:** Prismaはスキーマをドメイン単位で複数ファイルに分割管理できるようになり、モノリシックな`schema.prisma`を避けて`src/lib/db/schema/`配下に機能別分割することで、大規模化するデータモデルの見通しが良くなる。sumitsugiのような物件・契約・引き継ぎドメインが増える構成では早めに採用する価値がある。

- **Supabase Row Level Security (RLS) とPrisma併用の境界設計:** SupabaseのRLSポリシーとPrismaのアプリケーション層バリデーションを二重防御にするのが2026年の定石で、特に`draft`/`public`ステータスや前の住人・次の住人の個人情報アクセス制御はDB側RLSを一次防衛線、Prisma+Zodをアプリ層の二次防衛線にすべき。

- **Prisma Accelerate / Supabase Poolerによるコネクションプーリング:** サーバーレス（Vercel/Next.js App Router）環境ではDB接続数の枯渇が典型的な障害点になるため、Prisma AccelerateかSupabaseのTransaction Pooler(pgbouncer)を必ず経由させる構成が標準化している。ローンチ前に負荷テストでこの設定を検証しておくべき。

- **Supabase pgvector + Prismaでのマッチング機能:** IC（相続人）consultation matchingのような「条件マッチング」機能は、pgvectorで埋め込み検索を行いPrismaでリレーショナルデータと結合するハイブリッド構成が2026年のベストプラクティスになりつつある。プロダクト会議で出ていたマッチング方向性の技術的裏付けに使える。

- **マイグレーション運用の自動化:** Prisma Migrateのシャドウデータベースとブランチ環境（Supabase Branching）を組み合わせ、PRごとに独立したDBブランチでマイグレーションを検証してからmainにマージするCI構成が広がっている。build検証必須のこのプロジェクトのCI強化にも直結する。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Rustのwasm32-wasip2ターゲットとComponent Modelの安定化により、WASI 0.2ベースのモジュール間連携が実用段階に入り、マイクロサービス的な粒度でWasmコンポーネントを組み合わせる設計がしやすくなっている。

- **ポイント2:** wasm-bindgenやwit-bindgenのツールチェーンが成熟し、SIMD128やスレッド(shared memory + Web Workers)対応が標準的になったことで、画像処理・PDF生成などCPU負荷の高い処理をブラウザ/Edgeで実行してもネイティブの70〜90%程度の性能が出せるケースが増えている。

- **ポイント3:** CloudflareやFastly、Vercel Edge FunctionsなどのエッジランタイムがWasmを第一級市民として扱うようになり、Rust製のWasmバイナリをコールドスタート数ミリ秒で起動できる点は、Node.jsベースのSSRよりレイテンシ面で優位。当プラットフォームでもPDF生成やコスト計算ロジックのエッジ実行を検討する価値がある。

- **ポイント4:** バイナリサイズ最適化(`wasm-opt`, `opt-level = "z"`, LTO)のベストプラクティスが確立し、数百KB〜1MB台のバンドルが一般的になったことで、フロントエンドにWasmを組み込む際の初回ロードコストの懸念が実務上は解消されつつある。

- **ポイント5:** ただしデバッグ体験とスタックトレース可読性はまだJS/TSに劣り、既存のNext.js/TypeScriptスタックへの導入は「性能が本質的にボトルネックになる処理」に限定するのが現実的—全面移行ではなく部分的な最適化ツールとして採用するのが2026年時点の主流アプローチ。

### 8. Next.js App Router patterns 2026

- **ポイント1（Partial Prerendering の標準化）:** Next.js 16では`use cache`ディレクティブとPPRが安定版となり、静的シェルを即座に返しつつ動的部分をストリーミングする設計がデフォルトパターンに。物件一覧のような「基本情報は即表示、価格や在庫は非同期更新」というUXに最適。

- **ポイント2（Server ActionsとフォームのFirst-classサポート）:** `<form action={serverAction}>`パターンが定着し、APIルートを介さずミューテーションを完結できる。認可チェックやZodバリデーションをServer Action内に集約することで、`src/app/`配下のコードが薄くなり、セキュリティ境界も明確になる。

- **ポイント3（Turbopackのビルド時デフォルト化）:** 開発・本番ビルド双方でTurbopackが標準になり、ビルド時間が大幅短縮。CIでの`bun run build`の待ち時間が減ることで、PRごとのフィードバックループが速くなる。

- **ポイント4（Cache Componentsによる粒度制御）:** ページ単位ではなくコンポーネント単位でキャッシュ戦略を指定できるため、「物件詳細は長めにキャッシュ、レビュー数はリアルタイム」のような混在パターンを1ファイル内で表現しやすくなった。過剰なrevalidateタグ管理から解放される。

- **ポイント5（Server ComponentsとClient Componentsの境界最適化）:** "use client"境界を末端に寄せる設計がベストプラクティスとして定着し、JSバンドルサイズの継続的な削減が可能に。認証コンテキストなどグローバル状態を持つ部分だけをクライアント化し、それ以外はServer Componentsに留める構成が推奨される。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Functionsの実行時間制限とコールドスタートは大幅に改善されており、V8 isolateベースの起動をさらに軽量化する動きが進んでいる。物件検索や引き継ぎフローのAPIをEdgeに寄せる際は、依存パッケージを最小限にしてバンドルサイズを抑えることがレイテンシ改善の鍵になる。

- **ポイント2:** Next.js 16のPartial Prerendering (PPR) とEdge Functionsの組み合わせが標準化されつつあり、静的シェルを即時配信しつつ動的部分（在庫状況・価格など）だけをEdgeでストリーミングする設計が主流。sumitsugiの物件詳細ページのような「ほぼ静的だが一部動的」なUIに特に相性が良い。

- **ポイント3:** Edge Runtimeでは依然としてNode.js APIの一部（fs, 一部のcrypto等）が使えないため、認証まわり（auth-context.tsx関連）やDB接続を伴う処理はNode.js Runtimeに残し、地理的分散が効くリクエスト（リダイレクト、A/Bテスト、簡易バリデーション）だけをEdgeに配置する「ハイブリッド配置」が2026年のベストプラクティス。

- **ポイント4:** Vercelの課金モデルはEdge Function実行時間・リクエスト数ベースが精緻化されており、不要なミドルウェア（全ルートに適用されるauth middlewareなど）を絞り込まないとコストが跳ねやすい。matcherを最小限にスコープすることが直接コスト削減につながる。

- **ポイント5:** Observability面ではVercelのEdge Function向けトレーシング（OpenTelemetry統合）が強化されており、本番ローンチ前に主要APIルートへの計測導入をしておくと、ベータローンチ後のパフォーマンス問題の切り分けが格段に速くなる。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** ID や金額など意味的に異なるプリミティブ値を`type UserId = string & { __brand: 'UserId' }`のようなブランド型で区別し、コンパイル時に取り違えを防ぐパターンが2026年もデファクト化している。sumitsugiでも`listingId`と`sellerId`のような同型string混同バグをこの手法で未然に防げる。

- **`satisfies`演算子によるリテラル型保持:** `as const satisfies Config`のように書くことで、型チェックを通しつつ推論結果を狭いリテラル型のまま維持できる。`'draft' | 'public'`のようなステータス定義や`site-config.ts`のような設定オブジェクトで、意図しない型拡張を防ぎつつ安全性を担保できる。

- **Zodからの型導出を一次情報源にする:** `z.infer<typeof schema>`でランタイムバリデーションとコンパイル時の型を単一の定義から生成するのが主流になり、フォームや外部APIレスポンスなど境界部分で「型は合っているがランタイムでは失敗する」ズレを防げる。標準化規約にある「Zodスキーマで境界検証」と自然に統合できる。

- **Discriminated Union + 網羅性チェックの徹底:** `switch`文の`default`で`const _exhaustive: never = value`を書くパターンにより、新しいstatus値やUIバリアントを追加した際にコンパイルエラーで検知漏れを防ぐ。物件ステータスのような union type を拡張する際、CLAUDE.mdにある「grepで全usageを確認」を型システム側でも強制できる。

- **TypeScript Native Preview (Go移植版) によるビルド高速化:** 2026年時点でtsc互換の高速コンパイラが実用段階に入り、大規模リポジトリでの型チェック時間が大幅短縮されている。CI上の`bun run build`のボトルネック解消策として今後検討価値がある。
