# CTO Knowledge - 2026-04-17

## Daily Update (2026-04-17)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチはRSCで完結させ、`"use client"`は真にインタラクティブな部分のみに限定する。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降でPPRが安定化し、静的シェルと動的コンテンツを同一ルートで共存できる。ストリーミングと組み合わせることでTTFBを大幅に削減できる。

- **`<Image>`と`next/font`によるCore Web Vitals最適化:** LCP改善には`priority`属性と`sizes`の正確な指定が必須。フォントはCLSゼロ達成のため`next/font`以外を使わない方針を徹底する。

- **Route Segment ConfigとキャッシュのExplicit管理:** `fetch`のデフォルトキャッシュ挙動がNext.js 15で変更されたため、`revalidate`や`cache: 'no-store'`を明示的に指定し、意図しないキャッシュによるデータ陳腐化を防ぐ。

- **Turbopackへの移行とバンドル分析:** 開発環境はTurbopackがデフォルト化し、HMR速度が劇的に向上。本番は`@next/bundle-analyzer`で定期的に肥大化モジュールを検出し、dynamic importで分割する習慣をCIに組み込む。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の本格採用:** Next.js 15以降でPPRが安定版となり、静的シェルを即座に配信しつつ動的コンテンツをストリームする手法が標準パターンになった。初期表示速度とSEOを同時に最適化できる。

- **Suspense境界の設計がアーキテクチャの要:** データフェッチの粒度ごとにSuspenseをネストすることで、ウォーターフォールを避けながら段階的UIを実現できる。境界設計のミスがパフォーマンスボトルネックの主因になるため、コンポーネント分割の判断基準として明示的に持つべき。

- **Server Actions + optimistic UIの組み合わせが主流:** `useOptimistic`とServer Actionsを組み合わせることで、従来のREST/クライアント状態管理なしにリアルタイム感のあるUXが構築可能。Reduxやswr/tanstack-queryの役割が限定的になりつつある。

- **Edge Runtimeとの相性改善:** Cloudflare Workers・Vercel Edge等でのRSCストリーミングが実用レベルに達し、グローバルレイテンシを大幅削減できる。ただしNode.js専用APIへの依存がEdge移行の主な障壁として残る。

- **Cacheレイヤーの明示的制御が必須:** `fetch`の`cache`/`revalidate`オプションやunstable_cacheの適切な設定なしに、意図しないキャッシュヒット・ミスがストリーミングの恩恵を消す。キャッシュ戦略はコンポーネント設計と同レベルの設計判断として扱うべき。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの成熟とフルスタック型安全性の標準化:** tRPC v11がNext.js App Routerとの統合を深め、TypeScriptプロジェクトではスキーマ定義なしにクライアント・サーバー間の型共有が当たり前になりつつある。

- **GraphQLの選択的採用:** 複雑なデータグラフを持つ大規模サービスでは依然有効だが、オーバーエンジニアリングのリスクから中小規模では敬遠される傾向が続く。HotChocolate/StrawberryなどサーバーサイドのDX向上が差別化要因。

- **REST + OpenAPI 3.1の堅牢化:** AIコードジェネレーター（GitHub Copilot等）との相性が良く、OpenAPIスキーマからの自動型生成・クライアント生成が成熟。特にチーム間APIコントラクトとして再評価されている。

- **エッジ・ストリーミング対応のAPI設計:** Vercel/Cloudflare Workersの普及でレイテンシ最適化が必須に。Server-Sent Events（SSE）やHTTP Streamingを活用したリアルタイムAPIが、WebSocketより軽量な選択肢として台頭。

- **AIエージェント向けAPI（MCP/Tool calling対応）の急浮上:** LLMエージェントがAPIを直接呼び出すユースケースが増加し、ツール定義の明確なREST+OpenAPIが再び注目。tRPCもMCPアダプターが登場し始めており、エージェント統合が設計上の新要件になっている。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジのデファクト実行環境に:** Cloudflare Workers・Fastly Compute@Edgeを中心に、Wasmがコンテナの代替として定着。コールドスタートがほぼゼロになり、多言語対応も実現している。

- **エッジDBの成熟:** Cloudflare D1・Turso（libSQL）などのエッジ分散SQLが実用レベルに達し、「エッジでReadだけ」という制約が崩れ始めた。レイテンシとデータ整合性のトレードオフ設計が腕の見せどころ。

- **AI推論のエッジシフト:** 小型LLM（Llama 3.2など）のエッジ実行が現実的になり、プライバシー要件の厳しい用途でクラウド送信なしの推論が選択肢に。ただしモデルサイズとコールドスタートの管理が課題。

- **観測可能性の遅れが最大のリスク:** エッジノードの分散性により、従来のAPMツールが機能しないケースが多い。OpenTelemetryのエッジ対応が進んでいるが、デバッグ体制を先に設計しないとインシデント対応が困難になる。

- **ベンダーロックインの現実:** Next.js + Vercel、Remix + Cloudflareなど、フレームワークとエッジ基盤の結合が深化。WinterCG標準への準拠度を選定基準に入れ、移行コストを事前に見積もるべき。

### 5. authentication security best practices 2026

- **パスキー（Passkey）の標準化:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の主流となり、フィッシング耐性が大幅に向上。主要プラットフォーム（iOS/Android/Windows）の対応が成熟し、UXコストなしで導入可能になった。

- **トークンバインディングの厳格化:** JWTの有効期限を15分以下に短縮し、リフレッシュトークンのローテーションを必須化。盗まれたトークンの悪用ウィンドウを最小化することがZero Trustアーキテクチャの基本となっている。

- **デバイスフィンガープリントとリスクベース認証:** ログイン時にデバイス・IP・行動パターンを総合評価し、リスクが高い場合のみMFAを要求する適応型認証が標準化。ユーザー摩擦を最小化しつつセキュリティを担保できる。

- **セッション管理のサーバーサイド制御強化:** クライアントサイドのJWTのみに依存せず、サーバー側でセッションの失効管理（Redis等）を持つハイブリッド方式が推奨。強制ログアウト・デバイス管理機能が必須要件になりつつある。

- **OAuth 2.1 / DPoP（Demonstrating Proof of Possession）の採用:** アクセストークンをHTTPリクエストに暗号的に紐付けるDPoPにより、トークン傍受攻撃を無効化。サードパーティ連携を持つサービスでは早期採用が競争優位につながる。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のEdge Runtime対応成熟:** Prisma Client がVercel Edge・Cloudflare Workers上で安定動作するようになり、Supabase Poolerと組み合わせたサーバーレスアーキテクチャが本番運用レベルに達している。

- **Supabase Auth + RLS の設計が鍵:** Row Level Security をDBレイヤーで完結させることでAPIロジックを薄く保てるが、Prismaからは`SET LOCAL role`経由でのRLS適用が必要なため、ミドルウェア設計に注意が要る。

- **PgVector によるAI統合がデフォルト化:** Supabase の`pgvector`拡張がRAGパターンの標準インフラとなり、Prismaの`unsupported()`型でベクター列を扱うワークアラウンドから、より洗練されたORM対応へ移行中。

- **接続プール管理はSupabase Pooler（PgBouncer）に委ねる:** Next.js App RouterのServer ComponentsはリクエストごとにDB接続を生成するため、`connection_limit=1`でPrismaを設定しPoolerに集約するパターンが必須。

- **マイグレーション戦略の分離:** `prisma migrate`はスキーマ管理に使いつつ、Supabase CLIで環境間のマイグレーション履歴を管理する「二重管理」を避けるため、Prismaを正とした単一パイプラインに統一することが2026年のベストプラクティス。

### 7. WebAssembly Rust performance 2026

- **Component Model の本格普及:** WebAssembly Component Model (WASM 2.0) が標準化され、Rust製コンポーネントを言語間で再利用可能に。`cargo component` ツールチェーンが成熟し、マイクロサービス的なWASM構成が現実的になった。

- **WASI 0.3 + async/await ネイティブ対応:** WASIプレビュー3でasync I/Oが正式サポートされ、Rustの `async/await` がWASM上でそのまま動作。従来のポーリング方式に比べスループットが大幅改善。

- **Wasmtime / WasmEdge のAOTコンパイル最適化:** ランタイム側のAhead-of-Time最適化が進み、RustコンパイルのWASMバイナリがネイティブの85〜95%の性能に到達。コールドスタート問題がほぼ解消された。

- **SIMD・スレッド拡張の実用化:** Fixed-width SIMDとWASMスレッド（SharedArrayBuffer経由）が主要ブラウザ/ランタイムで安定化。Rustの `packed_simd` / `rayon` を活用した並列処理が本番投入可能な段階に。

- **バイナリサイズとビルド時間のトレードオフ管理:** `wasm-opt` + LTO + `panic=abort` の組み合わせが定石化。ただし大規模プロジェクトではインクリメンタルビルドの遅さが依然ボトルネックで、`cargo-component` のキャッシュ戦略が重要。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** クライアントバンドルサイズを最小化するため、`'use client'` は状態・イベントハンドラが必要な末端コンポーネントのみに限定する。データフェッチは Server Component で完結させるのが基本。

- **Parallel Routes + Intercepting Routes の活用:** モーダルやスライドオーバーをURLに紐づけることで、直リンク・ブラウザバックが自然に動作する。`@modal` スロットパターンは複雑なUXを宣言的に表現できる。

- **Server Actions でAPIルートを削減:** フォーム送信や mutation は `action=` + Server Action で完結し、`/api/` エンドポイントの乱立を防ぐ。`revalidatePath` / `revalidateTag` でキャッシュ制御も一元化できる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的コンテンツを同一ページに混在させ、TTFBを犠牲にせずパーソナライズを実現。`<Suspense>` 境界の設計がパフォーマンスの鍵になる。

- **`unstable_cache` + `use cache` ディレクティブ:** Next.js 15以降、関数レベルのキャッシュ制御が宣言的になった。`'use cache'` を付けるだけでサーバー側キャッシュが有効になり、`cacheLife` / `cacheTag` で細粒度の無効化が可能。

### 9. Vercel Edge Functions optimization 2026

- **Edge RuntimeとNode.js Runtimeの使い分け:** 2026年時点でEdge Functionsは低レイテンシが必要なルーティング・A/Bテスト・認証ミドルウェアに最適だが、Node.js固有のモジュール（Prisma等）はNode Runtimeを使う設計が現実的。

- **Fluid Computeの活用:** VercelのFluid Computeモデルにより、Cold StartがEdge/Serverless問わず大幅に短縮。関数の分割粒度より「リージョン選択」と「キャッシュ戦略」がパフォーマンスの主要ボトルネックになっている。

- **ISR + Edge Cacheの組み合わせが主流:** `stale-while-revalidate`パターンをEdgeキャッシュと組み合わせることで、動的コンテンツもCDN配信レベルのTTFBを実現。`revalidatePath`/`revalidateTag`の設計がアーキテクチャの核心。

- **Middleware最適化の重要性:** Next.js Middlewareは全リクエストを経由するため、不要なEdge Function実行がコスト増に直結。`matcher`設定の精度と処理の軽量化（DB呼び出し禁止、JWT検証のみ等）が必須。

- **Edge KV・Durable Objectsとの連携:** Cloudflare Workers KVやVercel KVをEdge Functionsのセッションストアに使うパターンが定着。ステートレス設計を維持しつつ、低レイテンシな状態参照を実現する標準アーキテクチャになっている。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の活用:** `as` キャストより安全な型検証が可能で、型推論を保ちながら制約を強制できる。2025年以降、コードベースでの `as` 使用を `satisfies` に置き換えるリファクタリングがベストプラクティスとして定着した。

- **Branded Types によるドメイン安全性:** `UserId` と `PostId` を同じ `string` として混在させないため、Branded/Nominal Types パターンが普及。実行時コストゼロでビジネスロジックの誤用をコンパイル時に防げる。

- **`noUncheckedIndexedAccess` の標準化:** tsconfig でこのフラグを有効化することで配列・オブジェクトアクセスに自動的に `undefined` が付与され、実行時の予期せぬクラッシュを大幅に削減できる。

- **Zod + `infer` による Schema-First 開発:** API境界でZodスキーマを定義し `z.infer<typeof schema>` で型を導出するパターンが主流。型とバリデーションの二重管理が不要になり、型安全性と実行時安全性が一致する。

- **Template Literal Types による厳密なAPI設計:** `'GET' | 'POST'` のような単純なユニオンではなく、`\`/api/${string}\`` 形式でルートパターンを型として表現し、型レベルでAPIの誤用を防ぐ設計が増加している。
