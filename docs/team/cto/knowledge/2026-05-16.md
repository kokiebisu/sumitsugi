# CTO Knowledge - 2026-05-16

## Daily Update (2026-05-16)

### 1. Next.js performance optimization 2026

- **PPR（Partial Prerendering）の本格活用:** Next.js 15以降で安定化したPPRにより、静的シェルと動的コンテンツを同一ルートで共存できる。Suspense境界を戦略的に配置することで、TTFB改善とパーソナライズを両立できる。

- **React Server Componentsのバンドルサイズ削減:** RSCにより重いライブラリ（date-fns、markdown parsers等）をサーバー側に閉じ込め、クライアントバンドルを劇的に削減できる。Client Componentへの境界設計が2026年のフロントエンド設計の核心スキル。

- **`use cache` APIによる細粒度キャッシュ制御:** Next.js 15で導入された`use cache`ディレクティブで、関数・コンポーネント単位のキャッシュが可能になった。`cacheTag`と`revalidateTag`を組み合わせてオンデマンド無効化を実装するのが現代のベストプラクティス。

- **Turbopackの実用段階移行:** Turbopackがdev環境でほぼ安定し、大規模プロジェクトでのHMR速度が従来比10倍以上。本プロジェクト（sumitsugi）もTurbopack前提の依存関係整理を検討すべきタイミング。

- **画像・フォント最適化の自動化徹底:** `next/image`のAVIF対応とViewport-aware lazy loadingが成熟。`next/font`によるCLS（Cumulative Layout Shift）ゼロ化は今や必須で、手動フォント読み込みは技術的負債とみなされる。

### 2. React Server Components streaming 2026

- **Suspense境界の細粒度化が標準に:** 2026年時点では、ページ全体ではなくコンポーネント単位でSuspense境界を設計するのがベストプラクティスとして定着し、TTFBを維持しながらFCPを最適化できる。

- **PPR（Partial Pre-Rendering）との組み合わせが主流:** Next.js 15+のPPRにより、静的シェルを即時配信しながらRSCストリームで動的コンテンツを注入するハイブリッドアーキテクチャが実用段階に入り、CDNキャッシュと動的レンダリングの両立が実現。

- **Waterfallの排除が設計の最優先課題:** `Promise.all`による並列データフェッチと、Suspense境界の適切な配置を組み合わせないと、RSCのストリーミングメリットが相殺される — コンポーネント設計段階でデータ依存グラフを明示的に管理することが必須。

- **クライアントバンドルサイズの継続的削減:** RSCにより対話不要なコンポーネントをサーバー側に移行できるが、`"use client"`の乱用で効果がゼロになる — コンポーネントツリーの末端のみをクライアント化する「葉ノード原則」の遵守が重要。

- **エラーハンドリングとローディング状態の設計コスト増:** ストリーミングではエラーが部分的に発生するため、`error.tsx`と`loading.tsx`をルートセグメントごとに設計する必要があり、UXの一貫性を保つための設計コストが増加している点に注意。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全APIの標準化:** 2026年時点でtRPCはフルスタックTypeScriptプロジェクトのデファクトに近づいており、スキーマ定義不要でエンドツーエンドの型安全性を実現できるため、Next.js/Bunスタックとの相性が特に高い。

- **GraphQLの選択基準の明確化:** GraphQLは「複数クライアント（Web/モバイル/サードパーティ）が異なるデータ形状を要求する」ケースに限定すべきで、単一フロントエンドのプロジェクトにGraphQLを導入するのはオーバーエンジニアリングという認識が業界で定着しつつある。

- **REST + OpenAPI 3.1の再評価:** Zodベースのバリデーションライブラリ（`zod-openapi`等）でスキーマからOpenAPI仕様を自動生成するパターンが普及し、RESTの「型なし問題」が解消されてきている。外部API公開が必要な場合はRESTが依然として最適解。

- **Server Actions / RPC-firstへの移行:** Next.js App RouterのServer Actionsが成熟し、「APIエンドポイントを別途設計しない」アーキテクチャが現実的な選択肢になった。内部通信のAPI設計コストを大幅に削減できる。

- **パフォーマンス観点：レイヤー削減が最優先:** どの方式でも、N+1問題対策（DataLoader/バッチング）とエッジキャッシュ戦略が2026年の差別化ポイント。tRPCでもGraphQLでも「ネットワークラウンドトリップ数」を設計初期から意識することがCTOとして最重要チェック項目。

### 4. serverless edge computing 2026

- **WebAssembly（WASM）がエッジの標準ランタイムに:** V8アイソレート一辺倒から脱却し、WASMベースのエッジランタイム（Fastly Compute、Cloudflare Workers + WASM）が本格普及。言語非依存でコールドスタートほぼゼロを実現している。

- **エッジでのAI推論が実用フェーズへ:** 量子化モデル（INT4/INT8）とWebGPU対応によりLLM推論がエッジノードで動作可能になり、レイテンシ敏感なパーソナライゼーションやモデレーション処理をオリジンへ送らずに完結できる。

- **分散SQLとエッジDBの成熟:** Turso（libSQL）、Cloudflare D1、Neon Branching などエッジ対応DBが読み取り性能を大幅改善。ただし書き込み整合性のトレードオフは依然設計上の最重要課題。

- **オブザーバビリティのギャップが顕在化:** 数百PoP（ポイント・オブ・プレゼンス）に分散した実行環境では従来のAPMが機能不全。OpenTelemetryのエッジ対応とサンプリング戦略の見直しが急務になっている。

- **コスト構造の再評価:** リクエスト単価は安価でも、エッジ↔オリジン間のデータ転送費とキャッシュ無効化コストが予想外に膨らむケースが増加。アーキテクチャ設計段階でのコストモデリングが不可欠。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の主流となり、フィッシング耐性と利便性を両立。2026年現在、主要ブラウザ・OSの対応が成熟し、新規サービスはパスキーをデフォルトにすべき段階に入っている。

- **MFAの「疲労攻撃」対策が必須:** プッシュ通知型MFAへの連打攻撃（MFA Fatigue）が頻発しており、番号マッチング（Number Matching）やコンテキストベース承認を組み合わせた実装が標準要件になっている。

- **JWTのアルゴリズム固定とローテーション戦略:** `alg: none`脆弱性やRS256/HS256混在による検証バイパスは依然として発生する。署名アルゴリズムをサーバーサイドで強制固定し、短命トークン（15分）＋リフレッシュトークンローテーションを組み合わせることが必須。

- **デバイスフィンガープリントと継続的認証:** ログイン時点だけでなく、セッション中の行動・デバイス変化を継続的に評価するリスクベース認証（Continuous Authentication）が普及。異常検知時のステップアップ認証をミドルウェア層で実装することで、UXを損なわずにセキュリティを強化できる。

- **シークレット管理のゼロトラスト化:** 環境変数への平文シークレット保存は非推奨となり、Vault・AWS Secrets Manager等の動的シークレット発行（短命・ローテーション自動化）が実装標準。CI/CDパイプラインへのシークレット注入もOIDC連携による一時トークン方式に移行が進んでいる。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のパフォーマンス最適化:** Prisma ORM はコネクションプーリング（Prisma Accelerate）とクエリエンジンの改善により、Supabase との組み合わせでサーバーレス環境でのコールドスタートが大幅に削減された。Edge Functions との親和性が高まっている。

- **Supabase の RLS（Row Level Security）との統合:** Supabase の RLS ポリシーと Prisma を組み合わせる場合、Prisma は RLS をバイパスするサービスロールを使うことが多く、セキュリティ境界の設計が重要。アプリ層での認可ロジックと DB 層の RLS を適切に分担する設計が 2026 年のベストプラクティス。

- **Supabase Realtime + Prisma の棲み分け:** リアルタイム機能（チャット・通知等）は Supabase Realtime を直接使用し、CRUD 操作は Prisma 経由とするハイブリッド構成が主流。型安全性を保ちながら Supabase の機能を最大活用できる。

- **マイグレーション管理の複雑性:** `prisma migrate` と Supabase の `supabase db push` が競合しやすい。2026 年現在、Prisma をスキーマの Source of Truth として扱い、Supabase CLI は RLS ポリシーや関数管理に限定するパターンが安定している。

- **Edge ランタイム対応:** Next.js の Edge Runtime では Prisma Client の一部機能が非対応のため、Supabase の `@supabase/supabase-js` クライアントを Edge で使い、Node.js ランタイムでは Prisma を使う層分けが実用的な回避策となっている。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）が本番利用フェーズへ:** 2026年時点でWASIp2とComponent Modelが安定化し、RustコンパイルWasmモジュールをブラウザ・サーバー・エッジで再利用できるポータブルバイナリとして配布するユースケースが急増している。

- **Wasm GCとの境界コストが実用レベルに低下:** wasmtime・V8のWasm GC実装成熟により、RustとJS間のデータ受け渡しオーバーヘッドが旧来の「コピー必須」モデルから線形メモリ共有モデルへ移行し、FFI境界のボトルネックが大幅に緩和された。

- **SIMD・マルチスレッドWasmが標準化完了:** WebAssembly SIMDとshared memoryスレッドが全主要ブラウザで標準サポートされ、RustのSIMDイントリンシック（`std::arch`）がWasmターゲットでもネイティブに近いスループットを発揮できる。

- **`wasm-opt`＋PGO（Profile-Guided Optimization）の組み合わせが必須最適化:** `cargo`→`wasm-pack`パイプラインに`wasm-opt -O3`とRust PGOを組み合わせることで、バイナリサイズ20〜40%削減・実行速度10〜25%向上が現場で報告されており、CI組み込みが標準的プラクティスになっている。

- **エッジランタイム（Cloudflare Workers/Fastly）でのRust Wasmが主流化:** cold startがゼロに近いWasmランタイム上でRustを動かすアーキテクチャが、Node.jsベースのエッジ関数を性能面で圧倒しており、レイテンシクリティカルなAPIロジックをRust Wasmに移植するROIが明確に出ている。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** データフェッチはServer Componentsに集約し、クライアント境界を最小化することで、バンドルサイズを大幅削減できる。`"use client"`は状態・インタラクションが必要な末端コンポーネントにのみ付与する原則が定着。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的コンテンツを同一ルートで混在させるPPRが安定版となり、TBTを下げながらパーソナライズも実現できる。`<Suspense>`境界の設計がアーキテクチャ上の核心になる。

- **Server Actions によるフォーム・ミューテーション統合:** APIルートを介さずServer Actionsで直接DBアクセスするパターンが主流化。楽観的更新（`useOptimistic`）と組み合わせることでREST/GraphQLレイヤーを省略できるケースが増加。

- **キャッシュ戦略の明示化:** Next.js 15以降、`fetch`のデフォルトキャッシュが`no-store`に変更され、キャッシュは意図的にオプトインする設計へ。`revalidateTag`/`revalidatePath`による細粒度キャッシュ無効化の設計が必須スキルに。

- **Parallel Routes / Intercepting Routes の活用:** モーダルやスライドオーバーをURLに紐づけて実装するインターセプトルートパターンが成熟。共有状態管理の複雑性を下げつつ、ディープリンク可能なUIが構築しやすくなっている。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択戦略:** Node.js Runtimeとの使い分けが重要で、Edge Functionsは起動レイテンシが1ms以下だが、利用可能なNode.js APIに制限があるため、認証ミドルウェアや地理的ルーティングに絞って採用するのが最も効果的。

- **Fluid Computeによるコールドスタート排除:** 2025年後半から本格化したFluid Computeモデルにより、リージョン間でのコンテナ再利用が可能となり、従来のEdge Functionsの弱点だったステートレス制約を補完しつつ低レイテンシを維持できる。

- **ISR + Edge Cachingの組み合わせ:** `stale-while-revalidate`パターンをEdgeレイヤーで実装し、動的コンテンツのキャッシュヒット率を高めることで、オリジンへのリクエストを劇的に削減できる。

- **バンドルサイズの厳格な管理:** Edge Functionsは1MBのサイズ制限があるため、`next/server`の`NextResponse`のみをインポートするなど、tree-shakingを意識した依存関係の選定がパフォーマンスに直結する。

- **Observabilityの強化:** Vercel Speed InsightsとOTel（OpenTelemetry）を組み合わせることで、Edge関数ごとのP99レイテンシとキャッシュヒット率を可視化し、ボトルネックを定量的に特定できる体制が2026年のベストプラクティス。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の本格活用:** `satisfies` を使うことで型推論の恩恵を保ちつつ型チェックを強制できる。`as const` との組み合わせでリテラル型の精度が大幅に向上する。

- **Template Literal Types によるAPIルート型付け:** `${Method}:${Path}` 形式でHTTPエンドポイントを型として表現し、ルートミスマッチをコンパイル時に検出するパターンが定着しつつある。

- **`NoInfer<T>` ユーティリティの普及:** TypeScript 5.4で導入された `NoInfer<T>` により、ジェネリック関数での意図しない型推論の拡散を防げる。特にデフォルト引数を持つ汎用関数で有効。

- **Branded Types によるドメイン駆動型安全:** `type UserId = string & { readonly _brand: 'UserId' }` パターンでプリミティブ型の混在バグをゼロコストで防ぐ。Zodのバリデーションと組み合わせてシステム境界での変換を明示化するのが現代的なプラクティス。

- **型レベルテストの標準化:** `expectTypeOf`（vitest）や `tsd` を使い、型定義そのものをテストする文化が広まっている。型の変更が意図せずAPIサーフェスを壊すリグレッションを防ぐ上で不可欠になりつつある。
