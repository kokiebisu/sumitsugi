# CTO Knowledge - 2026-04-23

## Daily Update (2026-04-23)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを削減する最も効果的な手法として、データフェッチはサーバー側に集約し、`"use client"` は真にインタラクティブなコンポーネントのみに限定する。

- **Partial Prerendering (PPR) の本格採用:** 静的シェルと動的コンテンツを同一ルートで共存させるPPRがNext.js 15以降で安定化。TTFBを大幅に改善しながら、動的データも扱える設計が主流になりつつある。

- **`next/image` と `next/font` の最適化徹底:** LCPスコアに直結するため、`priority` 属性の適切な設定と、フォントのsubset指定・preloadを組み合わせることでCore Web Vitalsを効率的に改善できる。

- **Server Actions によるAPI層の削減:** 従来の `/api/*` ルートを経由せずにServer Actionsで直接ミューテーションを処理することで、ネットワークラウンドトリップを削減し、コードの複雑性も低下する。

- **Bundle Analyzer + Turbopack の組み合わせによる継続的監視:** `@next/bundle-analyzer` で肥大化したクライアントチャンクを定期的に可視化しつつ、Turbopack（dev環境）の高速HMRで開発体験も維持するのが2026年のデファクト構成。

### 2. React Server Components streaming 2026

- **Suspense境界の細粒度化が標準に:** RSCのストリーミングでは、Suspense境界を画面の各セクション単位で設定し、FID/LCPを最小化するアーキテクチャが主流。ウォーターフォール回避のため、データフェッチはサーバーコンポーネント内で並列化が必須。

- **Partial Prerendering（PPR）の本格活用:** Next.js 15以降でPPRが安定化し、静的シェルを即時配信しつつ動的部分をストリーミングするパターンが普及。CDNキャッシュとストリーミングの両立が実現。

- **Server Actions + optimistic UI の組み合わせ:** フォーム送信やミューテーションにServer Actionsを使い、`useOptimistic`でクライアント状態を即時更新するパターンが定番化。RTT削減とUX向上を同時達成できる。

- **エッジランタイムとの相性が課題:** ストリーミングはNode.jsランタイムでは安定しているが、Cloudflare Workers等のエッジ環境ではWeb Streams APIの挙動差異に注意。デプロイ先ランタイムに合わせた検証が不可欠。

- **バンドルサイズとクライアント境界の管理:** `"use client"`の乱用でサーバーコンポーネントの恩恵が失われるケースが増加。コンポーネントツリーのどこでクライアント境界を引くかを設計段階で決める「境界設計」がアーキテクチャレビューの重要項目になっている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの実用的優位性:** フルスタックTypeScriptプロジェクトではtRPCが主流になりつつあり、スキーマ定義不要でエンドツーエンドの型安全性を実現できるため、Next.js + Prismaスタックとの相性が特に優れている。

- **GraphQLの棲み分け明確化:** マイクロサービス間や複数クライアント（Web/Mobile/外部API）を持つ大規模システムでは引き続きGraphQLが有効だが、単一チームの内部APIにGraphQLを採用するのはオーバーエンジニアリングになるケースが増えている。

- **REST + OpenAPI の堅牢性:** 外部公開APIや他社連携では、OpenAPI 3.1 + Zodによるスキーマファーストな設計が依然として最も実用的な選択肢であり、`zod-openapi` や `@hono/zod-openapi` で型安全とドキュメント自動生成を両立できる。

- **サーバーコンポーネント時代のAPI設計見直し:** Next.js App RouterのServer Componentsでは「APIを経由せずDBを直接読む」パターンが標準化し、クライアント向けAPIエンドポイントの総量が減少している。APIはミューテーション・外部連携・リアルタイム用途に絞り込む設計が現実的。

- **エッジ・ストリーミング対応:** Vercel/Cloudflare WorkersなどのエッジランタイムではHTTP Streaming（`ReadableStream`）とServer-Sent Eventsの活用が増えており、AIレスポンスのストリーミングAPIはもはや標準機能として設計に含める必要がある。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジの標準ランタイムへ:** CloudflareやFastlyがWasmファーストのアーキテクチャを採用し、コールドスタートがほぼゼロになった。言語非依存で動くため、Rustで書いたビジネスロジックをそのままエッジにデプロイできる。

- **AIインファレンスのエッジシフトが加速:** LLMの量子化（INT4/INT8）技術の成熟により、GPT-4クラスのモデルをエッジノードで実行するコストが2024年比で1/5以下に。レイテンシ削減とデータ主権の両立が現実的になった。

- **エッジDBとグローバル整合性の両立:** TursoやNeon（Serverless Postgres）のエッジレプリカが成熟し、「読み取りはエッジ、書き込みはリージョン」パターンが定番化。ただしコンフリクト解決ロジックは依然として設計上の難所。

- **オブザーバビリティの複雑化が最大の運用課題:** リクエストが数百のエッジPoPに分散するため、従来のAPMツールでは追跡が困難。OpenTelemetryのエッジ対応とサンプリング戦略の設計が実装品質を左右する。

- **コールドスタート問題の「再燃」:** Wasmで改善された一方、AI推論ワークロードではモデルロードが新たなボトルネックに。プリウォーミング戦略とモデルの分割ロードがアーキテクチャ設計の必須検討事項。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** FIDO2/WebAuthn標準のパスキーがパスワード認証を実質的に置き換えつつあり、フィッシング耐性と利便性を両立できるため、新規サービスではパスキーをデフォルト認証として設計すべき。

- **ゼロトラスト・継続的認証:** 「一度ログインしたら信頼する」モデルは廃止され、セッション中も行動パターン・デバイス状態・位置情報を継続評価してリスクスコアを動的に算出するアプローチが標準化されている。

- **MFAの必須化とSIM swap対策:** SMSベースのOTPはSIMスワップ攻撃に脆弱なため、TOTPアプリ（TOTP/HOTP）またはハードウェアキー（YubiKey等）への移行を推進し、SMS MFAは廃止フローを今から設計しておくべき。

- **シークレット管理の自動化:** 静的APIキーや長期トークンは最小化し、短命トークン（有効期限15分以内）＋ローテーション自動化（AWS Secrets Manager / HashiCorp Vault）を組み合わせることで、漏洩時の被害半径を大幅に縮小できる。

- **OAuth 2.0 / OIDCの実装精度:** 特にPKCE必須化・state/nonce検証・トークンバインディングの実装漏れが依然として多く、ライブラリ任せにせず定期的に認証フロー全体をセキュリティ監査することが重要。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6のEdge Runtime対応が成熟:** Prisma Accelerateを活用することでNext.js App RouterのEdge FunctionsからもDBアクセスが可能になり、コールドスタートの問題を最小化しながら接続プーリングを外部委譲できる。

- **Supabase pgvectorがプロダクション標準に:** ベクトル検索とリレーショナルデータを同一DBで管理するアーキテクチャが主流化し、AIフィーチャー追加時に別途ベクトルDBを立てるコストが不要になっている。

- **RLS（Row Level Security）をORMレイヤーで扱う課題:** PrismaはSupabaseのRLSポリシーを直接認識しないため、`supabase-js`（サービスロール）とPrisma（マイグレーション・型生成）を役割分担で使い分ける二層構成が現実解として定着している。

- **スキーマドリフト防止にPrisma Migrateが有効:** Supabaseダッシュボードから直接スキーマ変更すると`prisma migrate`との乖離が発生しやすいため、全DDL変更をPrismaのマイグレーションファイルで一元管理するルールをチームで徹底することが重要。

- **Supabase Branchingで開発環境の分離が容易に:** PRごとに独立したDBブランチを自動生成する機能が安定化し、E2Eテストや機能開発時のデータ汚染リスクを排除しながらCI/CDパイプラインとの統合がシンプルになっている。

### 7. WebAssembly Rust performance 2026

- **Component Model の実用化加速:** WASI 0.2とComponent Modelが2025年に安定版となり、2026年はRust製WasmコンポーネントをNext.jsやNode.jsに組み込む事例が急増。型安全なインターフェース定義（WIT）により、Rustライブラリを各言語から呼び出すコストが大幅に低下した。

- **Wasmtime / WASMer のJITパフォーマンス成熟:** サーバーサイドランタイムでのコールドスタートが1ms以下に達し、Rustで書かれたエッジ関数がネイティブに迫る速度で動作。特にCloudflare Workers・Fastlyでは、Rust+Wasmの組み合わせがデファクトになりつつある。

- **SIMD・スレッドサポートの広域展開:** Wasm SIMDとShared Memoryが主要ブラウザで完全サポートされ、画像処理・機械学習推論などの演算集約タスクでJavaScript比5〜10倍の速度を実現。Rustの`rayon`クレートに相当する並列処理をWasm上でも活用できるようになった。

- **Rustコンパイル最適化ツールチェーンの整備:** `wasm-opt`（Binaryen）とRustの`lto + opt-level=z`設定の組み合わせでバイナリサイズが従来比30〜50%削減可能。`wasm-pack` v0.14系でビルドパイプラインとの統合が簡素化され、CI/CDへの組み込みコストが激減した。

- **GC提案によるメモリ管理の選択肢拡大:** Wasm GC提案が安定化したことでRustの所有権モデルとの使い分けが明確化。パフォーマンスクリティカルな処理はRustの線形メモリで、UIロジック等は軽量言語（Kotlin/Dartなど）でWasm化し、同一Wasmモジュール内で協調動作させるアーキテクチャが現実的な選択肢になった。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年現在、App RouterではServer Componentsが基本単位であり、`"use client"`は本当に必要な箇所（インタラクション・ブラウザAPI）のみに限定することでバンドルサイズを大幅削減できる。

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降でstableになったPPRにより、静的シェルと動的コンテンツを同一ルートで共存させられ、TTFBとパーソナライズを両立できる。

- **Server Actions によるAPI層の簡素化:** フォーム送信・データ変更をServer Actionsで処理することで、`/api`ルートを減らし、型安全なend-to-endフローを少ないボイラープレートで実現できる。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15で導入された`use cache`により、コンポーネント・関数レベルでキャッシュ戦略を制御でき、`revalidate`タグと組み合わせてオンデマンド無効化が可能になった。

- **Streaming + Suspense の設計パターン成熟:** `loading.tsx`とSuspense境界の組み合わせが標準化し、ウォーターフォールを避けるためのデータフェッチをコンポーネントツリーの末端に押し下げる設計が2026年のベストプラクティスとなっている。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択的活用:** Vercel Edge Functionsは低レイテンシが強みだが、Node.js APIの制限（`fs`、一部npm packages不可）があるため、認証・A/Bテスト・リダイレクト処理など軽量ロジックに限定し、重い処理はサーバーレス関数に分離するのが2026年時点のベストプラクティス。

- **Fluid Computeによるコールドスタート削減:** VercelのFluid Compute（2025年GA）により、Edge/Serverless双方でインスタンス再利用が可能になり、従来のコールドスタート問題が大幅に緩和された。`maxDuration`と`memory`の適切な設定でコスト最適化も両立できる。

- **Middleware最適化とマッチャー設定:** `middleware.ts`の`matcher`設定を厳密に絞り込まないと全リクエストでEdge実行が走りパフォーマンス劣化を招く。静的アセット（`/_next/static/`等）を明示的に除外することが必須。

- **KV・R2との組み合わせによるステート管理:** Edge Functionsはステートレスなため、Vercel KV（Upstash Redis）やR2（Cloudflare互換）との組み合わせでセッション・レート制限・キャッシュを実装するパターンが定着。レイテンシを最小化するにはリージョンをユーザー分布に合わせて設定する。

- **観測性の強化:** Edge環境では従来の`console.log`ベースのデバッグが困難なため、Vercel Log Drains + OpenTelemetry連携による分散トレーシングの導入が2026年では事実上の標準。`@vercel/otel`パッケージで簡易統合が可能。

### 10. TypeScript type safety patterns 2026

- **Branded Types の本格採用:** `type UserId = string & { readonly _brand: 'UserId' }` のような Branded Types が、IDや金額など意味論的に異なる値の混在バグを防ぐ標準パターンとして定着。ランタイムコストゼロで型安全性を強化できる。

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の `satisfies` が推論を維持しつつ型チェックを行える点で普及が加速。`as` キャストによる型アサーションを排除し、意図しない型の拡張を防ぐ。

- **Template Literal Types による文字列の厳密化:** `type EventName = \`on${Capitalize<string>}\`` のようなパターンが API キー・イベント名・ルートパスの検証に活用され、マジックストリングのバグをコンパイル時に検出できる。

- **`const` 型パラメータと `infer` の組み合わせ:** TypeScript 5.x の `const` type parameter (`<const T>`) により、リテラル型の推論精度が向上。設定オブジェクトや配列のタプル推論が自動化され、型定義の冗長性が大幅に削減される。

- **Zod + tRPC パターンの標準化:** スキーマファーストの型生成（Zod → TypeScript 型）が API 境界での実行時検証と静的型安全性を同時に担保する事実上の標準に。`z.infer<typeof schema>` で型の二重定義を排除するアプローチが中規模以上のプロジェクトで必須となっている。
