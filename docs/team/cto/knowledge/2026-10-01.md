# CTO Knowledge - 2026-10-01

## Daily Update (2026-10-01)

### 1. Next.js performance optimization 2026

- **ポイント1:** Partial Prerendering（PPR）やApp Routerのキャッシュ戦略の洗練が進み、静的部分と動的部分を1ページ内で共存させることでTTFBを大幅短縮できるようになっている。sumitsugiでは`properties/`一覧ページで有効活用できる。
- **ポイント2:** React Server Components（RSC）を前提に、クライアントバンドルを最小化する設計が標準化しつつある。`'use client'`境界を末端コンポーネントに絞ることで、物件詳細ページなど画像・インタラクション多めの画面でもJS転送量を抑えられる。
- **ポイント3:** 画像最適化（`next/image`のAVIF/WebP自動変換、CDN連携）とフォント最適化（`next/font`によるセルフホスティング）が引き続き重要で、物件写真が多いsumitsugiのようなプラットフォームではLCP改善に直結する。
- **ポイント4:** Turbopackの本番ビルド安定化によりビルド時間短縮が見込め、Bunとの組み合わせでCI全体のフィードバックループがさらに速くなる可能性がある。
- **ポイント5:** Edge RuntimeとISR（Incremental Static Regeneration）の併用で、地域ごとのレイテンシを抑えつつ物件情報の鮮度も保てる — ベータローンチ後のスケール時に検討価値あり。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** Next.js 16ではReact Server Componentsのストリーミングが`loading.tsx`やSuspenseバウンダリと組み合わさり、ページ全体の初期表示（TTFB）を待たずに段階的にUIを配信できる。sumitsugiの`properties/`一覧など重いデータ取得があるページで優先的に適用すべき。

- **Partial Prerendering (PPR) の実用化:** 静的な骨組みを即時配信し、動的部分（在庫状況・価格など）だけをストリーミングで後追い表示するパターンが2026年には実運用レベルで安定。物件詳細ページのような「静的レイアウト＋動的データ」構成に適している。

- **キャッシュ戦略とRSCペイロードサイズ:** Server Componentsが増えるほどRSCペイロード自体の転送量が課題になる。`use cache`ディレクティブと組み合わせたセグメント単位のキャッシュ設計が、ビルド時間とランタイムパフォーマンスの両立に必須。

- **エラーバウンダリとストリーミングの相性:** ストリーミング中に発生したサーバーエラーは個別のSuspenseチャンクごとに`error.tsx`で捕捉する設計が求められる。認証やフォームなどユーザー操作が絡む箇所では、ストリーミング途中の失敗がUXを損なわないようフォールバックUIの設計が重要。

- **開発者体験（DX）とデバッグの複雑化:** サーバー/クライアント境界が曖昧になりがちで、`'use client'`境界の誤配置によるバンドルサイズ肥大やハイドレーションエラーが増える傾向。ビルド検証（`bun run build`）を徹底し、境界設計をコードレビューの必須チェック項目に組み込むべき。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCのようなend-to-end型安全なRPCアプローチが、TypeScriptモノレポ構成のチームで主流になりつつある。sumitsugiのようなNext.js App Router構成では、GraphQLのスキーマ管理コストを払わずに型安全性を得られる点が魅力。

- **ポイント2:** GraphQLは依然としてマルチクライアント（Web/モバイル/パートナーAPI）でのデータ取得最適化に強いが、N+1問題やキャッシュ戦略の複雑さから、単一フロントエンドのプロダクトでは過剰設計になりがち。公開APIを外部提供する計画がなければ優先度は低い。

- **ポイント3:** RESTは依然としてWebhookや外部連携（決済、物件情報連携など）のデファクトスタンダード。シンプルさとキャッシュ容易性（CDN/HTTPキャッシュ）が必要な公開エンドポイントにはRESTが最適。

- **ポイント4:** Server Actions（Next.js）とtRPCの境界が曖昧になってきており、2026年のトレンドとしては「APIレイヤーを薄くし、型をスキーマではなくコードから生成する」方向が強まっている。前の住人/次の住人のマッチングロジックのような内部処理は、Server Actionsで十分なケースが多い。

- **ポイント5:** 認証・決済など外部連携が増えるフェーズでは、内部用tRPC + 外部公開用REST（OpenAPI仕様書付き）のハイブリッド構成が現実解。法務確認後のベータローンチに向けて、外部パートナー（不動産会社等）向けAPIを想定するならOpenAPI生成を早めに検討すべき。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterTC(旧WinterCG)によるWeb標準API準拠が進み、Cloudflare Workers・Vercel Edge・Deno Deployなど主要プラットフォーム間でのコード可搬性が大幅に向上した。ベンダーロックインを避けるため、Node.js固有APIではなくWeb標準API（fetch, Request/Response）に依存した実装を徹底すべき。

- **コールドスタート問題の実質解消:** V8 isolateベースの実行環境とWASMの組み合わせにより起動時間が1桁ミリ秒まで短縮され、リアルタイム性が求められるSSR・パーソナライゼーション処理もエッジで実行可能になった。sumitsugiのような物件検索・位置情報系の軽量API処理はエッジ移行を検討する価値がある。

- **エッジでのAI推論（Edge Inference)の普及:** 小型LLM・embeddingモデルのエッジ実行が実用段階に入り、レイテンシ要件の厳しいレコメンド・検索補完をCDNエッジで処理するパターンが増加。中央集権的なAPI呼び出しのコスト・レイテンシ削減に直結する。

- **エッジデータベース/ステートの成熟:** Cloudflare D1, Turso, PlanetScale等の分散SQLiteやグローバルKVストアが本番運用レベルに達し、「エッジはステートレスのみ」という制約が薄れている。ただし一貫性モデル（結果整合性）を理解した上での設計が必須で、物件データのような強整合性が必要な書き込みは依然オリジンDB側に残すべき。

- **Next.js 16 App RouterのEdge Runtime対応強化:** Partial Prerendering(PPR)とEdge Runtimeの統合が進み、静的部分はCDNから即時配信しつつ動的部分（在庫・価格等）のみエッジで評価する構成が標準化。現行スタック（Next.js 16）は追加コスト無しでこの恩恵を受けられるため、ローンチ後のパフォーマンス改善候補として優先度高。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証（WebAuthn/Passkeys）がデファクトスタンダードとなり、フィッシング耐性のある認証がユーザー登録時のデフォルトになっている。SMS OTPは中間者攻撃やSIMスワップに弱いため、新規実装では避けるべき。
- **トークンの短命化とDPoP/mTLS併用:** アクセストークンの盗難・再利用リスクに対し、短寿命JWT（5〜15分）+ リフレッシュトークンローテーションに加え、DPoP（Demonstrating Proof of Possession）でトークンをクライアントに紐付けるパターンが標準化しつつある。
- **AIエージェント・ボット対策としての行動的シグナル:** LLMベースの自動化攻撃が増加し、デバイスフィンガープリンティングや行動分析（タイピングパターン、操作速度）を組み合わせたリスクベース認証が重要性を増している。
- **ゼロトラスト前提のセッション管理:** ログイン成功後も継続的にリスクを再評価する「継続的認証」が主流化。IPアドレス変更やデバイス変更時に再認証を強制する仕組みをミドルウェア層で実装するのが実用的。
- **サプライチェーン経由の認証情報漏洩対策:** npmパッケージ経由のトークン窃取事例が増えており、環境変数へのシークレット格納だけでなく、短命なクラウドネイティブ認証情報（OIDC連携のworkload identity）への移行が推奨される。

### 6. database architecture Prisma Supabase 2026

- **ポイント1（RLSとPrismaの統合）:** Supabaseのトレンドは、PrismaからRow Level Security（RLS）ポリシーを活かしつつ型安全性を両立させる方向に進んでおり、Prisma単体でRLSバイパスしがちな問題を`pgbouncer`経由の接続プーリングとSupabase Auth連携で解消するパターンが主流になっている。sumitsugiのような個人情報（物件・契約情報）を扱うサービスでは、アプリ層のバリデーションだけでなくDB層でのRLS二重防御が必須。

- **ポイント2（Prisma Accelerate/Edge対応）:** Next.js 16のEdge Runtime・Server Actions活用が進む中、Prismaの従来コネクション方式はサーバーレス環境でコネクション枯渇を起こしやすく、Prisma Accelerate（コネクションプーリング+グローバルキャッシュ）かSupabaseのTransaction Pooler（PgBouncer）併用がデファクトになっている。物件検索のような読み取り多発処理はキャッシュ層でレイテンシを大幅削減できる。

- **ポイント3（マイグレーション運用の厳格化）:** `prisma migrate`とSupabase CLIの二重管理による乖離トラブルが多発するため、2026年のベストプラクティスはSupabase側をSource of Truthとし、Prismaは`db pull`でスキーマ同期のみに使う「宣言的スキーマ運用」にシフトしている。本番で`'draft'|'public'`のようなenum変更を行う際は、両ツールのスキーマファイルが同時に更新される仕組み（CI検証）を組むべき。

- **ポイント4（Branching/プレビュー環境）:** Supabaseのデータベースブランチ機能とPrismaのマイグレーションを組み合わせ、PRごとに独立したDB環境を自動生成するCI/CDパターンが普及している。E2Eテスト（Playwright）でステージングDBを汚さずに検証できるため、現行のGit Worktreeベースの開発フローとも相性が良い。

- **ポイント5（pgvector/AI機能の統合）:** 物件マッチングやレコメンド機能を見据えると、SupabaseのネイティブpgvectorサポートをPrismaのraw query経由で扱う構成が標準化しつつある。将来的な「IC相談マッチング」機能（直近のプロダクト会議の方向性）を実装する際は、通常のリレーショナルモデルとベクター検索を同一DB内で共存させる設計を早めに検討すべき。

### 7. WebAssembly Rust performance 2026

- **コンパイル最適化の進化:** Rust 2024 editionとwasm-bindgen/wasm-packのツールチェーンが成熟し、LLVM 18以降のWasm向け最適化パスにより、ネイティブコードとの性能差が5-10%程度まで縮小しています。特にSIMD128命令の標準サポートが主要ブラウザで出揃ったことで、画像処理や数値計算系の処理が大幅に高速化されています。

- **Component Model & WASIの実用化:** WASI Preview 2とComponent Modelが2026年にかけて本格普及し、Rustで書いたWasmモジュールを言語非依存の部品として組み合わせられるようになりました。sumitsugiのような物件情報の画像処理・PDF生成を、サーバーレス環境でも同一バイナリで動かせる可能性が出てきています。

- **メモリ安全性とゼロコスト抽象化の両立:** RustのownershipモデルがWasmのリニアメモリ管理と相性が良く、GCを持つ言語（JS/Pythonのトランスパイル系）と比べてメモリフットプリントが小さく、Cold Start時間も短縮されます。Next.jsのEdge RuntimeでWasmモジュールを使う場合、この起動速度の差が体感パフォーマンスに直結します。

- **ブラウザ外での採用拡大:** Wasmtime/WasmerなどのランタイムがRust製プラグインシステムの標準になりつつあり、サードパーティ連携（決済、本人確認API等)をサンドボックス化して安全に実行する用途でのRust+Wasm採用が増えています。引越し費用計算や契約書生成ロジックを外部委託先に安全に渡す仕組みとして検討の余地があります。

- **開発体験の課題は依然残る:** デバッグツール（ソースマップ、プロファイラ）はネイティブRust開発に比べてまだ発展途上で、学習コストとビルド時間の増加がボトルネックです。現状のMVPフェーズでは費用対効果が見合わないため、導入は特定のパフォーマンスクリティカルな機能（PDF生成等）に限定するのが現実的です。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16ではPPRが安定版となり、静的シェルと動的コンテンツを1つのルートで組み合わせられる。初期表示を高速化しつつパーソナライズされた部分だけをストリーミングできるため、物件一覧ページなど「静的な骨格＋動的な在庫情報」の構成に最適。

- **Server Actionsの責務分離:** `"use server"`関数をRoute Handlerの代替として多用する流れが定着し、フォーム送信や予約フローはServer Actions、外部API公開はRoute Handlersと明確に使い分けるのがベストプラクティスになっている。Zodによる入力バリデーションをServer Actions内で必ず行う設計が標準化。

- **キャッシュ戦略の明示化:** `fetch`のデフォルトキャッシュ挙動がバージョンごとに変わった反省から、`cacheLife`/`cacheTag`を使った明示的なキャッシュ制御（`use cache`ディレクティブ）が主流に。ISRに頼らず、データ更新の粒度ごとにタグベースで再検証する設計が推奨される。

- **Server/Client境界の最小化:** "Client Componentの葉っぱ化"が進み、インタラクティブな部分（フォーム、モーダル等）だけを`'use client'`境界として切り出し、それ以外は極力Server Componentに寄せるパターンが定着。バンドルサイズとTTIの両立に直結する。

- **並列ルート・インターセプトルートの実用化:** モーダルやスライドオーバーUI（物件詳細のクイックビューなど）に`@slot`やインターセプトルート（`(.)folder`）を使う実装が一般化し、URL状態と組み合わせたモーダル管理がライブラリ不要で実現できるようになった。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1（コールドスタート最小化）:** Edge RuntimeはNode.js APIの一部しか使えない代わりにV8 isolateベースで起動が高速なため、重い依存関係（大きなnpmパッケージ、Node専用ライブラリ）を避け、`fetch`ベースの軽量な実装に絞ることでレイテンシを数十ms単位で削減できる。

- **ポイント2（データ取得の近接配置）:** Vercel Edge ConfigやEdge-compatible KV（Upstash Redis等）をオリジンDBの前段に置き、ユーザーに地理的に近いエッジでデータを読むことで、認証チェックやA/Bテストのフラグ判定など「頻繁に読むが低頻度で書く」データのレイテンシを大幅短縮できる。本プロジェクトでも物件検索のフィルタ条件キャッシュに応用できる余地がある。

- **ポイント3（ストリーミングSSRとの組み合わせ）:** Next.js 16のPartial Prerendering/Streaming SSRとEdge Functionsを組み合わせると、静的部分を即座に配信しつつ動的部分（在庫状況・価格など）だけをエッジでパーソナライズでき、体感速度とSEOを両立できる。

- **ポイント4（オブザーバビリティの標準化）:** 2026年時点ではEdge関数向けのOpenTelemetry対応が成熟し、Vercelのネイティブトレーシングと合わせてエッジ層のレイテンシ内訳（DNS/TLS/関数実行/オリジンフェッチ）を可視化するのが標準になりつつある。本番前にここを計測基盤に組み込んでおくべき。

- **ポイント5（コスト最適化）:** Edge Functionsは実行時間課金のため、重い処理（画像変換、PDF生成）はEdgeではなくServerless/Node Runtimeに逃がし、Edgeはルーティング判定・認証・軽量パーソナライズに限定する「適材適所」の設計が引き続きベストプラクティス。

### 10. TypeScript type safety patterns 2026

## CTO視点: TypeScript Type Safety Patterns 2026

- **`satisfies`演算子とconst型パラメータの定着:** 型推論を保ちながら型チェックだけ行う`satisfies`が標準化し、リテラル型の過剰な広がりを防ぐ`const`型パラメータと組み合わせることで、設定オブジェクトやルーティングテーブルの型安全性が大幅に向上しています。本プロジェクトの`site-config.ts`のような設定ファイルにも適用価値があります。

- **境界でのスキーマ駆動バリデーションが標準化:** Zodなどのスキーマライブラリで型定義とランタイム検証を一元化する手法が業界標準になり、「型はコンパイル時だけの安心」から「型=実行時契約」へ移行しています。`.claude/rules/standards.md`で既に採用されている「システム境界でZodスキーマ」方針は2026年のベストプラクティスと合致しています。

- **判別可能なUnion型による網羅性チェック:** `'draft' | 'public'`のようなUnion型を使う際、`switch`文でのexhaustiveness check（`never`型を使った漏れ検出）が必須パターンとして定着。新しいステータス値を追加した際のコンパイルエラーでの検出漏れ防止が、本プロジェクトの物件ステータス管理でも重要です。

- **型レベルテストの一般化:** `tsd`や`expect-type`による型定義自体の単体テストが、ライブラリ開発だけでなく社内API型定義にも拡大。API契約が壊れた際にランタイムテストより先に検知できるため、CI高速化とリグレッション防止の両立に寄与しています。

- **AIコード生成時代の型安全性ガードレール:** LLMによるコード生成が主流になった2026年、`strict`モード＋型推論に過度に依存せず明示的な戻り値型注釈を書くパターンが再評価されています。AIが生成した一貫性のないコードを型チェッカーが即座に弾くことで、レビューコストを下げる「型をレビュアー代わりに使う」運用が広がっています。
