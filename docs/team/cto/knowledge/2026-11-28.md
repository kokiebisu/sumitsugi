# CTO Knowledge - 2026-11-28

## Daily Update (2026-11-28)

### 1. Next.js performance optimization 2026

**CTO視点: Next.js Performance Optimization 2026**

- **ポイント1（Partial Prerendering の本格活用）:** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分のみストリーミングできる。本プラットフォームの物件一覧ページなど「ヘッダーは静的・在庫状況は動的」という構成に最適で、LCPを大幅に改善できる。
- **ポイント2（React Server Componentsでのデータフェッチ最適化）:** クライアントへのJS転送量を減らすため、物件詳細や前の住人プロフィールなど読み取り専用データは極力Server Componentで取得し、インタラクティブな部分のみ`'use client'`に限定する設計が重要。
- **ポイント3（Turbopackによるビルド高速化）:** Turbopackがデフォルトビルドツールとして成熟し、`bun run build`時間とHMRが大幅短縮。CI時間の圧縮にも直結するため、ベータローンチ前のCIパイプライン見直しの好機。
- **ポイント4（画像・フォント最適化の自動化）:** `next/image`のAVIF対応強化とフォントのセルフホスティング最適化により、物件写真中心のUIでもCore Web Vitalsを維持しやすくなった。手動での画質/サイズ調整の必要性が減っている。
- **ポイント5（キャッシュ戦略の明示化）:** App Routerのキャッシュ挙動がより明示的なAPI（`fetch`オプションや`revalidate`設定）になり、「公開/非公開」ステータスが変わる物件データのキャッシュ無効化を意図通りに制御しやすくなった。draft/publicの切り替えロジックとの整合性確認が必須。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 15以降で実験的だったPPRが16で本格運用フェーズに入り、静的シェルを即時配信しつつ動的部分だけをStreamingで差し込む構成が標準パターン化。初期表示（LCP/TTFB）を犠牲にせず個人化コンテンツを扱えるため、`properties/`一覧や`listing/`詳細ページのようなSSG+パーソナライズ混在UIに直結する。
- **`loading.tsx` / Suspenseの粒度設計がパフォーマンスのボトルネック:** Streaming自体は解決済み技術になったが、2026年の実運用課題は「どこでSuspense境界を切るか」。粒度が粗いとウォーターフォールが発生し、細かすぎるとレイアウトシフトが増える。物件検索・画像ギャラリーなど非同期データが多い画面では、境界設計のレビューを必須化すべき。
- **Server Actionsとのストリーミング統合:** フォーム送信後の結果をRSCストリームで段階的に返す「Action→Streaming UI」パターンが一般化。問い合わせフォームや引越し費用の見積もりフローなど多段階フォームで、楽観的UI更新と組み合わせることでUXを大幅改善できる。
- **キャッシュ戦略の複雑化に注意:** StreamingとPPRの組み合わせはCDNキャッシュ層との相性問題を生みやすく（`fetch`のrevalidate設定ミスで過剰な動的レンダリングに陥るケースが多発）。ビルド前に`bun run build`のキャッシュ診断ログを必ず確認するルールをCIに組み込むべき。
- **可観測性（Observability）の重要性が増大:** ストリーミングはリクエストが単一のレスポンスタイムで計測できないため、従来のAPMでは「どのチャンクがどれだけ遅延したか」が見えない。RSCペイロードのチャンク単位でのトレーシング導入が、2026年のパフォーマンス改善の前提条件になっている。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの実質的デフォルト化）:** Next.js + TypeScriptモノレポ構成ではtRPCがREST/GraphQLに対して型安全性とDX面で優位に立ち、本プロジェクトのようなフルスタックTS構成では新規API層の第一候補になっている。スキーマ定義とクライアント呼び出しが型レベルで同期され、Zodバリデーションとの統合もしやすい。
- **ポイント2（GraphQLはBFF/集約層に収束）:** GraphQLは「社内全API」ではなく、複数マイクロサービスやサードパーティAPIを束ねるBFF（Backend for Frontend）層としての採用が主流化。単一チームの単一アプリではオーバーエンジニアリングになりやすく、sumitsugiの規模ではtRPC/RESTで十分。
- **ポイント3（RESTは外部連携・公開APIで継続）:** パートナー連携や将来の公開API（決済・外部システム連携等）はRESTが依然標準。社内UI向けはtRPC、外部公開はREST、という二層設計が2026年のベストプラクティス。
- **ポイント4（Server Actions/RSCとAPI層の境界の再定義）:** Next.js 16のServer Actions普及により、単純なCRUDはAPI層を経由せず直接呼び出すケースが増加。API（tRPC/REST）は「複数クライアントから再利用される」「外部公開される」処理に限定し、ページ専用ロジックはServer Actionsに任せる方が保守性が高い。
- **ポイント5（エッジ実行とレイテンシ最適化）:** API設計時点でエッジランタイム対応（Cloudflare Workers/Vercel Edge等）を意識する流れが強まっている。物件検索や引越し費用計算などレイテンシに敏感な機能は、エッジ実行可能な軽量API設計を優先すべき。

### 4. serverless edge computing 2026

- **ポイント1（コールドスタート実質ゼロ化）:** V8 isolateやWasmベースのランタイム（Cloudflare Workers, Deno Deploy等）が主流となり、コールドスタートは1桁ms台が標準に。レイテンシ要件が厳しいAPI（例: 物件検索のオートコンプリート）はエッジ関数に移す価値が高い。

- **ポイント2（エッジでのデータ整合性）:** D1/Durable Objects的なエッジネイティブDBやグローバルKVが普及し、「エッジ=読み取り専用キャッシュ」の時代は終わった。本プロジェクトでも物件のdraft/public切り替えのような書き込みを伴う処理をエッジに持たせる選択肢が現実的になっている。

- **ポイント3（フレームワーク統合の深化）:** Next.jsのEdge RuntimeはNode.js APIサブセットの制約が残るため、Prisma等のORMやNode専用ライブラリを使う処理（決済・認証）はNode runtimeに留め、表示系・検索系のみエッジに寄せるハイブリッド構成が2026年のベストプラクティス。

- **ポイント4（コスト構造の変化）:** リクエスト課金からCPU時間課金への移行が進み、重い処理をエッジに置くと逆にコスト増になるケースが増えている。引越し費用計算やPDF生成のような重処理は従来型サーバーレス（Lambda等）に残すのが得策。

- **ポイント5（観測性のギャップ）:** マルチランタイム構成（Node + Edge）でのトレーシング・ロギングの断片化が依然課題。本番導入前にOpenTelemetry等で統一的な可観測性を確保しないと、障害時の原因特定が難しくなる。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証がデフォルト標準になり、フィッシング耐性のあるパスキーをプライマリ認証手段として採用する実装が急増している。sumitsugiのような個人情報（契約・引越し情報）を扱うサービスでは、パスワード単体の認証はもはやリスクとして許容できない。

- **セッション管理とトークンの短命化:** JWTやセッショントークンの有効期限を短くし、リフレッシュトークンのローテーション（使い捨て化）を徹底することが標準化している。長寿命トークンの漏洩は被害範囲が大きいため、Next.js App RouterでのServer Actions/Middlewareでの検証を厳格に行う必要がある。

- **デバイスバインディング+継続的リスク評価:** 単発のログイン認証から、デバイスフィンガープリントや行動パターンを用いた継続的なリスクスコアリングへの移行が進んでいる。不動産取引のような高額決済フローでは、ログイン時だけでなく取引実行時にも再認証（ステップアップ認証）を要求すべき。

- **ゼロトラスト前提のAPI設計:** 認証済みであっても全APIリクエストで権限（authorization）を再検証する設計が必須になっている。特に物件ステータス（draft/public）や個人情報アクセスでは、認証と認可を分離し、最小権限の原則をZodスキーマレベルでも徹底する。

- **サプライチェーン経由の認証リスク:** OAuthプロバイダーやSDKの依存関係を経由した認証バイパス攻撃が増加しており、依存パッケージの定期的な脆弱性スキャンとCSP/CSRF対策のCI組み込みが不可欠。GitHub Actions上でのsecret管理（OAuthトークン等）も同様の厳格さで扱うべき。

### 6. database architecture Prisma Supabase 2026

- **型安全性とエッジ対応の両立:** Prisma 6以降はQuery CompilerがRust不要のTypeScript/WASMベースになり、Vercel Edge FunctionsやCloudflare Workersでもコールドスタートが大幅改善。Supabase接続時はPrisma Accelerate等のコネクションプーリングを必ず併用し、サーバーレス特有のDB接続枯渇を防ぐべき。

- **RLS（Row Level Security）とORMの責務分離:** SupabaseのRLSをDB層のセキュリティ境界として活用し、Prismaのアプリケーション層バリデーション（Zod等）と二重化するのがベストプラクティス。前の住人・次の住人間のデータアクセス権限（物件の非公開情報など）はRLSで強制し、アプリ側のミスに頼らない設計にすべき。

- **マイグレーション運用の安定性:** `prisma migrate`とSupabase CLIのマイグレーションを併用する場合、適用順序の競合が起きやすいため、Supabase Branching（開発用DBブランチ）を使ってPRごとに本番相当のスキーマ変更を検証するフローが2026年の標準になっている。

- **リアルタイム機能との統合:** 物件ステータス（draft/public）の変更通知など、Supabase Realtimeを使う場合はPrismaのトランザクション完了後にイベント発火されるよう、Webhook経由（DB Trigger→Edge Function）で疎結合にするのが推奨。ORM層で直接Realtimeを扱うと一貫性が崩れやすい。

- **コスト最適化とコネクション管理:** PgBouncer（Supabase標準搭載）経由でのPrisma接続時は`pgbouncer=true`パラメータと`directUrl`の併用が必須で、これを怠るとマイグレーション失敗やプリペアドステートメントエラーが頻発する。スケール前提ならConnection Pooling設定の見直しを早期に行うべき。

### 7. WebAssembly Rust performance 2026

- **WASM GC統合の本格化:** WasmGC仕様がブラウザ主要エンジンで安定し、RustのGCバインディング（wasm-bindgen経由）も最適化が進んだことで、メモリ管理オーバーヘッドを抑えつつJS/TS側との相互運用性が向上している。

- **コンポーネントモデルによるモジュール連携:** WASI Preview 2とComponent Modelの普及により、Rustで書いた複数のWasmモジュールを型安全に合成できるようになり、マイクロサービス的な設計をブラウザ・エッジ双方で再利用しやすくなっている。

- **SIMD・マルチスレッドの標準化完了:** Wasm SIMDとthreads（SharedArrayBuffer経由）が主要ランタイムで標準サポートされ、画像処理や物理演算などCPU負荷の高い処理をRust側で並列化しても、ネイティブに近い性能を引き出せるようになった。

- **ビルドサイズ最適化ツールチェーンの成熟:** `wasm-opt`やRustの`wee_alloc`後継（`talc`など軽量アロケータ）、Cargoの`wasm32-wasip2`ターゲットにより、バイナリサイズと起動時間（コールドスタート）を大幅に削減できる — エッジ関数やCloudflare Workers的な用途で特に重要。

- **エッジランタイムでのネイティブ代替としての定着:** Fastly ComputeやCloudflare Workersなど、Node.js的なサーバーレス実行環境でRust+Wasmがデフォルトの選択肢になりつつあり、コールドスタートの速さとサンドボックス分離の両立が評価されている。

### 8. Next.js App Router patterns 2026

- **App Router + Server Componentsのデフォルト活用:** クライアントコンポーネントの範囲を最小化し、データフェッチはServer Componentsで行うことでバンドルサイズとクライアント処理を削減できる。`'use client'`境界を末端のインタラクティブ部分だけに絞るのがベストプラクティス。

- **Partial Prerendering (PPR) の普及:** 静的シェルを即時配信しつつ動的部分をストリーミングで後から埋める手法が主流化しており、初期表示速度（LCP/TTFB）の改善に直結する。`sumitsugi`のような物件一覧ページでは、静的なレイアウトと動的な在庫データを分離することで恩恵が大きい。

- **`loading.tsx`/`error.tsx`によるきめ細かい境界設計:** route segmentごとにSuspense境界を設計し、ページ全体のブロッキングを避けるパターンが定着。特に画像多めの物件詳細ページでは、セクション単位でのストリーミングがUXを左右する。

- **Server Actionsによるフォーム処理の簡素化:** API Routeを介さずミューテーションを直接呼べるため、リクエスト数を減らし型安全性も保てる。ただし認証・入力検証（Zod等）をAction内で必ず行う必要があり、クライアント側のバリデーションだけに頼らない設計が前提。

- **キャッシュ戦略の明示化（`fetch`オプション・`revalidate`・`unstable_cache`）:** Next.js 15以降でキャッシュのデフォルト挙動が変わり「明示しないと再フェッチされる」方向にシフトしたため、パフォーマンスを狙う箇所ほど`cache: 'force-cache'`やタグベースの再検証を意識的に設計する必要がある。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化:** Vercel EdgeランタイムはV8 isolateベースのため起動が数ms単位で済むが、2026年は依存バンドルサイズの肥大化がボトルネック化しやすい。動的importやtree-shakingを徹底し、1関数あたりのバンドルを極力小さく保つ運用が重要。

- **Streaming + Partial Prerendering(PPR)の併用:** Edge Functionsとの組み合わせでTTFBを大幅短縮できるため、静的部分はPPRで配信しつつ動的部分だけEdgeでストリーミングする構成が標準化してきている。全ページをEdge化するのではなく、パーソナライズ箇所のみに限定するのが費用対効果の鍵。

- **リージョン配置とデータ局所性:** Edge Functionsは地理的に近いが、DB/APIがus-east等に固定だと往復レイテンシがボトルネックになる。Fluid Compute(Vercelの新しい実行モデル)やリージョン指定(`regions`設定)をDBレプリカの配置と揃えることで、Edge化の恩恵を実質的に出せる。

- **Node.js互換APIの拡大による移行判断:** Edge Runtimeで使えるAPIが年々増えているが、全てのnpmパッケージ(特にネイティブ依存を持つもの)が動くわけではない。全部Edgeに寄せるのではなく、「軽量・低レイテンシ要求」のルートだけEdge、重い処理はServerless/Node runtimeに残すハイブリッド戦略が現実的。

- **コストモデルの変化への対応:** 実行時間課金からリクエスト数+実行時間の複合課金へ移行しているため、不要なEdge Middlewareの多用(全リクエストに対する認証チェック等)はコスト増につながる。`matcher`設定で対象パスを絞り込み、本当に必要な箇所にのみ適用する設計が重要。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x系で導入された`const`型パラメータや`satisfies`演算子の活用が標準化し、型推論を保ちながら過剰な型注釈を減らすパターンが主流になっている。
- **ポイント2:** Zodなど実行時スキーマ検証ライブラリから型を`z.infer`で導出する「スキーマファースト」設計が、APIバウンダリやフォーム入力の型安全性を保証する標準プラクティスとして定着している。
- **ポイント3:** Branded Types（nominal typing）を使い、`string`や`number`の意味的な違い（例: `UserId` vs `PropertyId`）をコンパイル時に区別することで、ID取り違えのようなランタイムバグを未然に防げる。
- **ポイント4:** `tsgo`（TypeScriptネイティブコンパイラ）の普及により型チェック速度が大幅に改善され、大規模モノレポでもCIでの型チェックがボトルネックになりにくくなっている。
- **ポイント5:** テンプレートリテラル型とConditional Typesを組み合わせたルーティング・i18nキーの型安全化が進み、文字列ベースのAPI（パス、翻訳キーなど）でもタイポをコンパイル時に検出できるようになっている。
