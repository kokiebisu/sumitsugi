# CTO Knowledge - 2026-11-14

## Daily Update (2026-11-14)

### 1. Next.js performance optimization 2026

- **Turbopackのビルド/開発体験の成熟:** Next.js 16でTurbopackが本番ビルドでも標準化され、Webpackからの移行コストが下がった。sumitsugiのようなBunベースの環境でも、`bun run build`時のコンパイル時間短縮に直結するため積極採用すべき。

- **Partial Prerendering (PPR) の本格運用:** 静的シェルと動的コンテンツを1ページ内で混在させられるため、物件一覧ページのような「検索条件は動的だがレイアウトは静的」なページで初期表示速度を大幅に改善できる。

- **Server ActionsとキャッシュセマンティクスのシンプルさがUXに直結:** `cacheLife`/`cacheTag`による明示的な再検証制御が定着し、物件ステータス（`draft`/`public`）変更時のキャッシュ無効化を型安全に書けるようになっている。曖昧な`revalidatePath`依存から脱却すべき。

- **画像・フォント最適化はもはや前提条件:** `next/image`のAVIF優先配信とフォントのセルフホスティングはSEO・Core Web Vitals双方で必須。物件写真を多用するUIでは、CDN経由のレスポンシブ画像配信を怠るとLCPが悪化しやすい。

- **React Server Components前提の計測基盤:** クライアント/サーバー境界を跨ぐバンドルサイズをCIで継続監視するプラクティスが一般化。`'use client'`境界の肥大化を防ぐため、コンポーネント分割時に計測を自動化する仕組み（lint/Bundle Analyzer）を組み込むのが2026年のベストプラクティス。

### 2. React Server Components streaming 2026

- **部分的ハイドレーションとSuspense境界の最適化:** Next.js 16ではSuspense境界を細かく分割し、各コンポーネントが独立してストリーミングされることで、初回表示（TTFB）を維持しつつ重いデータ取得部分だけを遅延させる設計が標準化しています。本プロジェクトでも`properties/`一覧ページのような重いクエリを含むページでこの手法を活用すべきです。

- **Partial Prerendering (PPR) の実用段階入り:** 静的シェルを即時配信し、動的部分のみサーバーでストリーミングするPPRが安定版機能として定着し、ビルド時に静的化できる部分（物件カードのレイアウトなど）と動的部分（在庫状況・価格）を明確に分離する設計判断が重要になっています。

- **Server Actions のストリーミングレスポンス対応:** フォーム送信やミューテーション処理でも段階的にUIを更新できるストリーミングパターンが普及し、物件登録フローのような多段階フォームでユーザー体感速度を改善できます。

- **キャッシュ戦略とRSCの組み合わせが複雑化:** `use cache`ディレクティブやタグベースの再検証がRSCストリーミングと絡み合うため、キャッシュ無効化のタイミングを誤るとstaleなデータが配信されるリスクがあり、特にステータス変更（`draft`/`public`）のような状態遷移を扱う箇所では注意が必要です。

- **Bunとの互換性は依然要注意:** RSCのストリーミングレンダリングはNode.js Streams APIに強く依存しており、Bunランタイムでの本番運用時はエッジランタイムとの挙動差異を事前に検証する必要があります。

### 3. API design REST GraphQL tRPC 2026

- **統合的アプローチの定番化:** 2026年現在、単一プロトコルで全てを統一する流れは終わり、tRPCは社内フルスタックTypeScript環境（フロント・バック同一リポジトリ）に、GraphQLは複数クライアント・複雑な集約が必要な公開API層に、REST/OpenAPIはサードパーティ連携やシンプルなCRUDに、と用途ごとに使い分けるのが実用的です。

- **型安全性がプロトコル選定の最優先基準:** tRPCのようにスキーマ定義不要でEnd-to-Endの型推論が効く設計が評価されており、sumitsugiのようなTypeScriptフルスタック構成ではtRPC的な発想（またはzodベースの型安全REST）を社内API・BFF層で採用するとフロント/バックの型ズレによる不具合を大幅に減らせます。

- **Zodなどのスキーマバリデーションがプロトコル横断の共通言語に:** REST/GraphQL/tRPCいずれでも、Zodスキーマを単一の信頼できる定義源（source of truth）として入力検証・型生成・ドキュメント生成を同時に行う構成が主流になっており、本プロジェクトの「Zodを境界で使う」方針と直接整合します。

- **GraphQLはN+1問題とキャッシュ戦略の複雑さがコスト:** DataLoaderパターンや永続化クエリ（persisted queries）の運用負荷が高く、小〜中規模のプロダクト（物件情報程度の規模）では過剰設計になりがちなため、sumitsugiの規模では採用優先度は低いと判断できます。

- **エッジ/サーバーレス環境との親和性で差がつく:** tRPCとREST(軽量JSON)はNext.js App RouterのServer Actions・Edge Runtimeと相性が良く低レイテンシですが、GraphQLサーバーは重くなりやすいため、Next.js 16ベースの本プロジェクトの構成ならtRPC/REST寄りの選択が性能面でも合理的です。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** Cloudflare Workers AI、Vercel Edge Functions、Deno Deployなどが軽量LLM推論をエッジで提供し始め、レイテンシ要求の高いUI（検索サジェスト、画像最適化判定など）はリージョン中央のAPIではなくエッジ上での推論に移行している。弊社でも物件検索のオートコンプリートや画像の自動タグ付けをエッジ推論化することでTTFBを大幅短縮できる可能性がある。

- **Cold Startのほぼ消滅とランタイムの収束:** V8 isolateベース（Cloudflare Workers, Vercel Edge Runtime）がデファクトとなり、コールドスタートはミリ秒未満まで縮小。一方でNode.js API互換性の制約が残るため、Next.js側では「どのAPI routeをEdge Runtimeに載せられるか」の精査が必要（Prisma等のDB接続ライブラリは依然Node Runtime必須なケースが多い）。

- **ステートフルエッジ（Durable Objects / SQLite at the Edge）の普及:** Cloudflare Durable ObjectsやTurso、D1のようなエッジSQLiteレプリケーションが成熟し、「エッジ=読み取り専用キャッシュ」という制約が崩れている。将来的に内見予約の空き状況チェックなど低レイテンシな書き込みが必要な機能はこの方向で検討余地がある。

- **コスト構造の変化とVendor Lock-inリスク:** リクエスト課金からCPU時間課金への移行が進み、重い処理をエッジに置くとコストが跳ねるケースが出てきている。特定ベンダーのEdge Runtime APIに依存しすぎると移行コストが高くなるため、現状のVercelデプロイを前提にしつつも、Node.js互換APIで書ける部分は汎用的に保つのが得策。

- **観測性（Observability）の遅れが依然ボトルネック:** 分散したエッジ環境でのトレーシング・ログ集約は中央集権的なサーバーに比べ依然成熟度が低く、障害調査が難しい。sumitsugiの規模ではまだフルエッジ化よりVercelの通常SSR/API Routesで十分であり、エッジ移行は「計測可能になってから」が妥当な判断。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証（WebAuthn/パスキー）が主流となり、フィッシング耐性のある認証がデフォルトに。Sumitsugiのような個人情報（物件情報・取引履歴）を扱うサービスでは、SMS OTPより同期パスキーを優先実装すべき。

- **トークンのライフサイクル管理:** JWTのような長寿命トークンではなく、短命アクセストークン＋リフレッシュトークンのローテーション（refresh token rotation）を徹底し、漏洩時の被害範囲を最小化する設計が必須。

- **ゼロトラスト前提のセッション管理:** デバイスフィンガープリンティングや異常ログイン検知（新規デバイス・地理的異常）をセッションごとに評価し、リスクベースで追加認証（MFA）をトリガーする仕組みが標準に。

- **サプライチェーン経由の認証リスク:** OAuth/OIDCの外部IDプロバイダ連携を使う場合、スコープの最小化とクライアントシークレットの定期ローテーションを徹底。NextAuth等のライブラリも常に最新パッチを適用。

- **監査ログと異常検知の分離:** 認証イベント（ログイン失敗・パスワードリセット・権限変更）は改ざん防止のため別システムに記録し、インシデント発生時の追跡可能性を確保する。

### 6. database architecture Prisma Supabase 2026

CTOとして、"database architecture Prisma Supabase 2026"について以下の洞察をまとめました。

- **ポイント1（前提の確認）:** sumitsugiの現行スタックはPrismaではなく**Drizzle ORM + PostgreSQL**（`drizzle-kit`, `@auth/drizzle-adapter`）。Prisma/Supabase比較を議論する際は、移行コストと現状の軽量・型安全な構成を維持する優位性を前提に置くべき。
- **ポイント2（Prismaの進化）:** Prisma v6以降はRust製バイナリエンジンを廃止し、純TypeScript製の新クエリコンパイラへ移行済み。エッジランタイム（Vercel Edge, Cloudflare Workers）でのコールドスタート・バンドルサイズ問題が大幅に改善されたが、Drizzleは元々ランタイム依存が薄く、この点で優位性を保っている。
- **ポイント3（Supabaseの強み）:** SupabaseはPostgres標準拠のRow Level Security（RLS）とRealtime機能が強みで、特に「前の住人」↔「次の住人」間のチャットやステータス同期のようなリアルタイム要件に向く。自前Postgres＋Drizzleで同等機能を実装する場合、RLSポリシーかアプリ層での権限制御のどちらを採用するか明確化が必要。
- **ポイント4（コネクション管理）:** Serverless/Edge環境でのDB接続はPrisma Accelerate・Supabase Poolerのような外部プーリング層が2026年のデファクト。現在`docker compose`のローカルPostgresから本番移行する際は、Neon/Supabase等のサーバーレスPostgres＋コネクションプーラーの導入検討が必須。
- **ポイント5（マイグレーション戦略）:** `bd`タスク管理と同様、スキーマ変更も段階的ロールアウト（`drizzle-kit generate`→レビュー→`db:push`）を徹底し、`'draft'|'public'`のようなUnion型変更時は全参照箇所のgrepを忘れないこと（既存ルール通り）。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WebAssembly Component Model の標準化が進み、Rustの`wit-bindgen`を使ったモジュール間連携がブラウザ/サーバー両方で実用レベルに達している。マイクロフロントエンドやプラグイン機構を設計する際は、独自RPCを組むよりComponent Modelベースの構成を検討する価値がある。

- **ポイント2:** `wasm-bindgen` + `wasm-opt`の最適化パイプラインが成熟し、適切な設定（LTO有効化、`opt-level = "z"`または`"s"`）でバンドルサイズを大幅に削減できる。フロントエンドで重い計算処理（画像処理・PDF生成など）をRust/WASMに切り出す際は、初期ロードサイズとのトレードオフを計測してから判断すべき。

- **ポイント3:** WASI Preview 2（P2）対応が進み、サーバーサイドでのWASMランタイム（Wasmtime等）がNode.jsプロセスより軽量なサンドボックス実行環境として採用されるケースが増えている。将来的にユーザー生成コードの安全な実行（例: カスタムフィルタ処理）が必要になれば、コンテナより低オーバーヘッドな選択肢になる。

- **ポイント4:** SIMD命令（`wasm32-unknown-unknown` + `target-feature=+simd128`）のサポートがブラウザ全体で安定し、数値計算やデータ変換処理でネイティブに近い速度が出せる。ただし本プロジェクトの現状（物件検索・リスト表示中心）ではWASM導入のROIは低く、現時点では優先度を上げる必要はない。

- **ポイント5:** スレッド対応（`SharedArrayBuffer` + Web Workers）は`Cross-Origin-Isolation`ヘッダー設定が前提となり、Next.jsのホスティング環境（Vercel等）での設定確認が必須。将来重い処理をWASMに移す場合は、このヘッダー要件がCDN/キャッシュ戦略に影響する点を事前に洗い出す必要がある。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** 静的シェルと動的コンテンツを1つのルートで共存させるPPRが安定版となり、ダッシュボードや一覧ページで初期表示を高速化しつつパーソナライズ部分だけをストリーミングする構成が標準化している。本プロジェクトの`properties/`一覧でも適用候補。

- **Server Actions のバリデーション層定着:** `use server`関数の入力をZodスキーマで検証し、型安全なまま`src/lib/`のデータ層と直結するパターンが主流に。フォーム送信のクライアントJSを減らせるため、物件登録フォームなどで有効。

- **Caching戦略の明示化:** Next.js 15以降の「デフォルトキャッシュしない」方針を受け、`fetch`のキャッシュ指定や`revalidateTag`による明示的なタグベース無効化が必須パターンに。`seller`/`status`更新時の再検証漏れがバグの温床になりやすいので要注意。

- **Server/Client境界の最小化:** Composition Patternで「できるだけ下層でuse clientを切る」設計が定着し、認証コンテキストやインタラクティブUIのみをクライアント化する構成がバンドルサイズ削減に直結している。`auth-context.tsx`周りの見直しにも応用可能。

- **Route Groups + Parallel Routesによるレイアウト分離:** モーダルやタブ切り替えをParallel Routes（`@modal`等）で実装し、ブラウザ履歴と両立させるパターンが一般化。物件詳細のモーダル表示やオンボーディングフローの改善に適用できる。

### 9. Vercel Edge Functions optimization 2026

Vercel Edge Functionsの最新トレンドを踏まえ、CTO視点でまとめます。

- **ポイント1（キャッシュ戦略の徹底）:** Cache-Controlヘッダーを使ったCDNキャッシュで実行回数そのものを減らすのが最優先。p95レイテンシ100ms未満を目標にduration/errors/cache hitを継続的に計測すべき。
- **ポイント2（適用範囲を見極める）:** Edge Functionsは地理的に分散したユーザーに効くジオパーソナライズ・A/Bテスト・認証ガード・ボットフィルタリングに向いており、重いCPU処理やDB直結処理は通常のServerless/Node環境に残すべき。sumitsugiのようなサービスでは物件検索の軽量な出し分けロジック程度が適任。
- **ポイント3（単一責務・軽量化）:** Middlewareは80行以内を目安に、各Edge Functionは「リダイレクト」「リライト」「認証チェック」など単一責務に限定し、圧縮後1MB以内に収める運用ルールが実用的。
- **ポイント4（Node専用APIの排除）:** `fs`, `net`, `tls`, `Buffer`, `node:crypto`などNode専用APIはEdge Runtimeで使えないため、認証やセッション処理を組む際はWeb標準API（fetch, crypto.subtle等）で書く前提の設計が必要。シークレットは環境変数経由でのみ扱う。
- **ポイント5（開発・デバッグ手法の変化）:** `next dev`は全関数をNodeで実行してしまいEdge特有の非互換性を隠すため、`vercel dev`でのローカル検証を標準化すべき。CI上でもEdge/Node実行環境の差異をテストに組み込む価値がある。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x系では`satisfies`演算子と`const`型パラメータの活用が標準化しつつあり、型推論の精度を保ちながら過剰な型注釈を減らせるため、Zodなどのスキーマ検証と組み合わせて境界値でのランタイム検証と静的型を同時に保証するパターンが主流になっています。

- **ポイント2:** `unknown`型とDiscriminated Unionを組み合わせたResult型（`{ ok: true, data } | { ok: false, error }`）パターンがエラーハンドリングの標準になり、try/catchに依存しない明示的なエラー伝播で本プロジェクトの「エラーは必ずcatchして詳細なメッセージで再throw」という方針とも相性が良いです。

- **ポイント3:** テンプレートリテラル型とBranded Types（例：`type SellerId = string & { __brand: 'SellerId' }`）を使い、`seller`や`listing`のようなドメインIDをプリミティブ型のまま混同しないようにする手法が、本プロジェクトのような`'draft' | 'public'`ステータス管理や複数エンティティIDを持つコードベースで型安全性のコストパフォーマンスが高いです。

- **ポイント4:** tRPCやZodベースのEnd-to-End型安全性（フロントエンドとAPIレスポンスの型を自動同期）が、Next.js App RouterのServer ActionsやRoute Handlersと組み合わさることで、手動の型定義の二重管理を避けるトレンドが強まっています。

- **ポイント5:** AIコーディングエージェント（Claude Codeなど）による自動実装が増える中、型定義自体が「仕様書」として機能するケースが増え、ユニオン型を変更する際は必ずコードベース全体をgrepして全使用箇所を確認する運用（本プロジェクトのBuild Integrityルールと同様）が、AI生成コードの品質管理手法として重要度を増しています。
