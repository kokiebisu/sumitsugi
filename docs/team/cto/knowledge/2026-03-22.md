# CTO Knowledge - 2026-03-22

## Daily Update (2026-03-22)

### 1. Next.js performance optimization 2026

- **React Server Components の最大活用:** RSCはクライアントバンドルサイズを劇的に削減する。`"use client"`ディレクティブを最小限に留め、インタラクティブな部分のみクライアントコンポーネントに分離することが2026年の標準プラクティス。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15+でstableになったPPRにより、静的シェルと動的コンテンツを同一ルートで混在可能。TTFBを維持しながらパーソナライズドコンテンツを配信できる。

- **`<Image>`と`<Link>`の最適化徹底:** `priority`プロパティ・`sizes`属性の適切な設定でLCPを改善。`prefetch`戦略の見直しで不要なネットワーク消費を削減できる。

- **Route Handlers でのキャッシュ戦略:** `fetch`の`revalidate`オプションとISRを組み合わせ、APIコールを最小化。`unstable_cache`でサーバーサイドの重い計算結果をメモ化する。

- **Bundle Analysis の継続的実施:** `@next/bundle-analyzer`をCI/CDに組み込み、サードパーティライブラリの肥大化を早期検出。特にリッチテキストエディタ・日付ライブラリ・チャートライブラリは動的インポートで遅延読み込みが必須。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の本格普及:** Next.js 15以降でPPRが安定版となり、静的シェルと動的ストリーミングを同一ルートで混在させるパターンが標準化。TTFBを犠牲にせずパーソナライズドコンテンツを配信できる。

- **Suspense境界の設計がパフォーマンスの鍵:** コンポーネントツリーのどこにSuspenseを置くかで体感速度が大きく変わる。細粒度のSuspense境界を戦略的に配置し、上位コンポーネントのブロックを避けることが必須。

- **Server Actions + Optimistic UIの組み合わせ:** `useOptimistic`との連携でサーバーラウンドトリップ中もUIを即時更新するパターンが定着。フォーム操作のUXが大幅に改善され、クライアント状態管理の複雑さを削減できる。

- **キャッシュ戦略の再設計:** Next.js 15でfetchキャッシュのデフォルトが`no-store`に変更され、明示的なキャッシュ制御が必要に。`unstable_cache`や`revalidateTag`を活用したタグベースの無効化設計がアーキテクチャの中心課題になっている。

- **エッジランタイムとの相性:** RSCストリーミングはVercel/Cloudflare EdgeでCDNエッジから配信可能になり、グローバルレイテンシの大幅削減が現実的に。ただしNode.js専用APIへの依存があるコンポーネントはエッジ非対応のため、ランタイム分離の設計判断が重要。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年現在、Next.js + tRPCの組み合わせが中小規模スタートアップで主流化。型定義をクライアント・サーバー間で共有できるため、API契約のずれによるバグが実質ゼロになる。

- **GraphQLの役割の絞り込み:** GraphQLは「なんでも使える万能API」から「複雑なデータグラフを持つ大規模サービス専用」へ位置づけが変化。Federation v2（Apollo/Hive）によるマイクロサービス統合が主要ユースケースとなっている。

- **REST + OpenAPI 3.1の再評価:** 外部公開APIではRESTが依然として標準。OpenAPI 3.1 + Zodによる自動型生成（`zod-openapi`等）が普及し、REST特有の型安全性不足を補うエコシステムが成熟した。

- **HTTP/3 + EdgeでのAPI設計の変化:** CloudflareやVercel EdgeでのAPI実行が一般化し、コールドスタートやレイテンシを意識したステートレス設計が必須に。RPCスタイルの細粒度エンドポイントより、バッチ処理・ストリーミング対応APIが優位になりつつある。

- **AI Agent向けAPI設計の台頭:** LLMエージェントがAPIを直接呼ぶユースケースが急増し、ツール定義（JSON Schema / OpenAPI）の品質が開発者体験だけでなく「AIの理解精度」にも直結。MCP（Model Context Protocol）互換設計が新たなベストプラクティスになりつつある。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジの標準ランタイムに:** 2026年時点でCloudflare Workers・Fastly Compute@Edgeなど主要プラットフォームがWasmをファーストクラス対応し、言語非依存のエッジデプロイが現実的になった。コールドスタート問題もほぼ解消されている。

- **エッジDBの台頭でステートレス前提が崩れた:** Cloudflare D1・Turso・Neon（edge proxy）など低レイテンシDBがエッジに展開され、「エッジ＝ステートレス」という制約が薄れた。ただしCAP定理のトレードオフ管理が開発者の新たな責務になっている。

- **AI推論のエッジシフトが加速:** 小型LLM（1〜7Bクラス）のWasm/GPU対応により、PII処理や低遅延推論をクラウド送信せずエッジで完結できるアーキテクチャが増加。プライバシー規制対応とコスト削減の両立が主な動機。

- **オブザーバビリティが最大の運用課題:** エッジノードが数百リージョンに分散するため、分散トレーシング（OTel標準）の導入なしでは障害切り分けが困難。ローカルdev環境との再現性ギャップも依然として課題。

- **ベンダーロックインリスクの再評価:** WinterCG仕様による相互運用性は向上したものの、各プラットフォーム固有API（KV・Queue・AI binding等）への依存が深まっている。アーキテクチャ設計時にポータビリティレイヤーを意識的に設けることが重要。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** 2026年はFIDO2/WebAuthnベースのパスキーが事実上の標準となり、フィッシング耐性のある認証としてパスワードレス移行が不可逆的な流れになっている。既存システムへの段階的導入が最優先課題。

- **セッション管理の短命化とトークンローテーション:** JWTのリフレッシュトークンは15分〜1時間の短い有効期限＋サイレントローテーション戦略が標準。長寿命トークンの漏洩リスクを最小化するため、トークン無効化リスト（Redis等）との組み合わせが必須。

- **デバイスフィンガープリントによる異常検知:** ログイン時のデバイス・IPの継続的なリスクスコアリングが主流に。同一セッションでの地理的に不可能な移動（Impossible Travel）の自動検出がゼロトラスト実装の基本要件となった。

- **OAuthサプライチェーン攻撃への対策強化:** サードパーティIdPへの依存リスクが顕在化し、`state`パラメータ検証・PKCE必須化・リダイレクトURI厳格検証が最低限の実装基準。依存するOAuthライブラリの定期的なセキュリティ監査も不可欠。

- **MFAファティーグ攻撃への対応:** プッシュ通知型MFAへの連続承認攻撃が増加しているため、番号照合（Number Matching）やコンテキスト付きプッシュ通知への切り替えが推奨。TOTPやハードウェアキーへのフォールバック設計も重要。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x の Edge Runtime 対応成熟:** Prisma Client がEdge環境（Vercel Edge Functions / Cloudflare Workers）で安定稼働できるようになり、Supabase の接続プールである `pgbouncer` と組み合わせることでサーバーレス環境でのコールドスタート問題が実用レベルで解消された。

- **Supabase の Row Level Security (RLS) × Prisma の二重防衛:** RLSをDBレイヤーで有効化しつつ、Prismaのミドルウェアで認可ロジックを補完する「多層防衛」がベストプラクティスとして定着。アプリ側のバグがあってもDBレイヤーでデータ漏洩を防げる。

- **Supabase Realtime + Prisma の使い分け:** リアルタイム更新はSupabase Realtimeのwebsocketチャネル、書き込み・複雑クエリはPrismaという役割分担が主流。Prismaでリアルタイムを無理に実装しようとするのはアンチパターン。

- **型安全なマイグレーション管理:** `prisma migrate diff` と Supabase CLI の `supabase db diff` を組み合わせ、マイグレーションをCIで自動検証するパターンが普及。スキーマドリフトの早期検出が本番事故を大幅に削減している。

- **接続数管理が引き続き最重要課題:** サーバーレス構成ではDBコネクションの枯渇リスクが高く、Supabase の `pgbouncer`（トランザクションモード）と Prisma の `connection_limit=1` 設定の組み合わせが必須。2026年時点でも「接続数を意識しない設計」が最大の落とし穴。

### 7. WebAssembly Rust performance 2026

- **ポイント1: WASIp2（Component Model）の本格普及** — 2025年末にWASIp2が安定化し、RustのWASMコンポーネントが異なるランタイム間でinteropできるようになった。`wasm-tools`と`cargo-component`が標準ツールチェーンとして定着し、サーバーサイドWASMの採用が加速している。

- **ポイント2: GCとマルチスレッドの実用化** — WASM GC proposalの普及とShared Memory + Atomicsの安定化により、Rustでのマルチスレッドワークロードがブラウザ内でも現実的になった。Rayon相当の並列処理をWASM上で動かすユースケースが増加中。

- **ポイント3: Wasmtime / WasmEdgeのパフォーマンス向上** — AOTコンパイル最適化とTier-2コンパイラの改善により、ネイティブコード比95%超のスループットを達成するケースが報告されている。特にCPU集約型処理（画像処理・暗号化）でRust+WASMのROIが高い。

- **ポイント4: エッジコンピューティングとの統合** — Cloudflare Workers・Fastly Compute・Fermyon SpinなどのエッジプラットフォームがRust WASMをファーストクラスサポート。コールドスタートがNode.js比で10〜100x高速なため、レイテンシクリティカルなAPIに採用が進んでいる。

- **ポイント5: ツールチェーンの成熟とサイズ最適化** — `wasm-opt`（Binaryen）とRustの`lto = true` + `opt-level = "z"`の組み合わせで、バイナリサイズを50KB以下に抑えることが容易になった。`wasm-bindgen`の型安全性向上により、JS/Rustのインターフェース設計のミスが大幅に減少。

**実践上の優先度:** 新規のCPU集約型機能（動画処理・PDF生成・暗号化）をWASMモジュール化することで、エッジへのデプロイとブラウザオフロードの両方に対応できる設計が2026年のベストプラクティスです。

### 8. Next.js App Router patterns 2026

- **Server Componentsをデフォルトに:** 2026年現在、`'use client'`は状態・イベント・ブラウザAPIが必要な箇所のみに限定し、コンポーネントツリーの末端に押し込む設計が標準。これによりバンドルサイズを大幅に削減できる。

- **Partial Prerendering (PPR) の実用化:** 静的シェルと動的ストリーミングを同一ページで混在させるPPRが安定版になり、`<Suspense>`境界の設計がパフォーマンスの要。境界の粒度が粗すぎるとTTFBが悪化するため、インタラクティブ要素単位で囲むのが鉄則。

- **Server Actions でAPI Routeを置き換える:** フォーム送信やデータ変更は`'use server'`関数に集約し、`/api/*`ルートを排除する設計が主流。ただしZodによるサーバーサイドバリデーションは必須——クライアントからの直接呼び出しが可能なため、信頼境界として扱うこと。

- **`use cache` + `cacheTag`によるキャッシュ戦略の明示化:** `fetch`の暗黙キャッシュに依存せず、`use cache`ディレクティブでキャッシュ範囲を明示し、`revalidateTag`で部分的無効化を制御するパターンが推奨。キャッシュ設計をコードで表現できるようになった。

- **Turbopackのデフォルト採用でDX向上:** 開発サーバーがTurbopack標準になり、大規模プロジェクトでのHMRが劇的に高速化。ただしWebpackプラグインへの依存がある場合は移行コストを事前に評価すること。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge RuntimeからV8 Isolatesの活用最大化:** 2026年のEdge Functionsはコールドスタートをほぼ排除したV8 Isolatesベースで動作する。Middleware層での認証・A/Bテスト・geo-routingを積極的にEdgeに移行し、オリジンへのラウンドトリップを最小化することがパフォーマンスの核心。

- **ポイント2: Fluid Compute対応による実行時間制限の緩和:** Vercelの「Fluid Compute」により、従来のEdge制約（CPU時間・メモリ上限）が大幅に緩和された。長時間処理でもEdgeで実行可能になったが、スプレッドシートやDB接続はリージョン選択に注意が必要。

- **ポイント3: KV / R2ストレージとのEdge統合でのキャッシュ戦略:** Cloudflare KVやVercel KVをEdge Functionsと組み合わせたエッジキャッシュ層が標準パターンに。`stale-while-revalidate`戦略でAPIレスポンスをエッジにキャッシュし、TTFBを100ms以下に抑えることが現実的なゴール。

- **ポイント4: ISR（Incremental Static Regeneration）とEdgeの融合:** Next.js App RouterのServer Componentsをエッジで実行しつつ、ISRでバックグラウンド再生成する「ハイブリッド戦略」が主流。`export const runtime = 'edge'`と`revalidate`を組み合わせることで動的コンテンツのパフォーマンスとSEOを両立できる。

- **ポイント5: Observabilityの整備が必須:** Edgeは分散実行のためデバッグが難しく、OpenTelemetryベースのトレーシング（Vercel Observability / Baselime）の導入が不可欠。ローカルの`next dev`でEdge挙動を完全再現できない点を踏まえ、ステージング環境でのEdge固有バグ検出フローを確立することが開発速度維持のカギ。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなブランド型が標準化し、プリミティブ型の混同によるバグをコンパイル時に防ぐパターンが主流になっている。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` が定着し、型推論の恩恵を受けながら型チェックを強制できるため、`as` キャストの乱用を排除できる。

- **Zod + 型の単一ソース:** ランタイムバリデーションと静的型を Zod スキーマで一元管理し、`z.infer<typeof schema>` で型を導出するパターンが API境界・フォームで事実上の標準となっている。

- **Template Literal Types の実用化:** `type EventName = \`on${Capitalize<string>}\`` のようなテンプレートリテラル型が複雑なドメインモデルの表現に使われ始め、文字列ベースのAPIを型安全に設計できるようになっている。

- **`noUncheckedIndexedAccess` の有効化推奨:** `tsconfig` の厳格オプションとして広く採用が進み、配列・オブジェクトのインデックスアクセスで `T | undefined` を強制することで、実行時エラーの大半をコンパイル時に検出できる。
