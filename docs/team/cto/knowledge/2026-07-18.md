# CTO Knowledge - 2026-07-18

## Daily Update (2026-07-18)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 16ではPPRが安定版となり、静的シェルと動的コンテンツを1つのレスポンスでストリーミング配信できる。物件一覧ページなど「共通レイアウトは静的、価格や空室状況は動的」という構成に理想的で、TTFBを大幅改善できる。

- **`use cache` ディレクティブによる明示的キャッシュ制御:** ファイルベースのキャッシュ設定から、関数・コンポーネント単位で `use cache` を宣言する方式へ移行が進んでいる。`data.ts` 内のフェッチ処理を細かくキャッシュ境界で区切ることで、再検証範囲を最小化しつつビルド時間も短縮できる。

- **Turbopackによるビルド・開発体験の高速化:** Turbopackがデフォルトビルドツールとして定着し、大規模コンポーネント（`src/components/ui/`, `src/components/listing/`）でもHMRとプロダクションビルドが数倍高速化。CI時間短縮にも直結するため、`bun run build` の実行時間を継続計測する価値がある。

- **React Server Components前提のバンドル最適化:** クライアントコンポーネント境界を最小化し、`'use client'` の乱用を避けることでJSバンドルを削減するのが標準プラクティスに。認証状態を扱う `auth-context.tsx` のようなクライアント側コンテキストは、必要な葉ノードのみに絞り込むことでLCP改善が見込める。

- **画像・フォント最適化の自動化強化:** `next/image` のAVIF自動変換とレスポンシブサイズ推論が進化し、手動のsizes指定が減少傾向。物件写真中心のUIでは、CLS対策としてプレースホルダー戦略（blur/シマー）をコンポーネント単位で統一するのが効果的。

### 2. React Server Components streaming 2026

## React Server Components Streaming 2026 — CTO視点

- **ポイント1（Partial Prerendering の標準化）:** Next.js 15/16でPPR(Partial Prerendering)が安定版となり、静的シェルを即座に配信しつつ動的部分だけをストリーミングする構成が標準パターンに。物件一覧ページなど「静的なレイアウト＋動的な在庫情報」の組み合わせに最適で、sumitsugiの`properties/`配下のようなSSR依存ページのTTFB改善に直結する。
- **ポイント2（`use cache`ディレクティブの普及）:** キャッシュ境界をコンポーネント単位で明示できる`use cache`が実運用レベルで定着し、fetchレベルのキャッシュより粒度の細かい制御が可能に。データ取得（`src/lib/data.ts`）とレンダリングの責務分離が一段と重要になっている。
- **ポイント3（Suspense境界の設計がUXの生命線に）:** ストリーミングが前提化したことで、どこにSuspense境界を置くかがLCP/CLSを直接左右する。前の住人の詳細情報やレビューなど「遅くても許容できる」領域を意図的に後回しにする設計が定石化している。
- **ポイント4（Server Actionsのセキュリティ強化要求）:** Server Actionsの普及に伴い、認証チェック漏れやCSRF類似の脆弱性が2025年に多数報告され、2026年は「Server Action=公開APIエンドポイント」という前提での入力検証（Zod等）とオリジン検証がベストプラクティスとして必須化。認証フォームや引っ越し費用の決済フローなど、sumitsugiのユーザー入力系機能でも要注意。
- **ポイント5（Bunとの相性）:** Bunのネイティブストリーミング対応が進み、RSCのReadableStreamレスポンスをNode.js互換レイヤーなしで直接処理できるようになったことで、ビルド・デプロイ双方でのレイテンシが改善されている。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの実質的デファクト化）:** TypeScriptフルスタック構成（Next.js×tRPC）では、スキーマ定義とクライアント型を自動同期できるため、REST/GraphQLで必要だったOpenAPI/コード生成ステップが不要になり、開発速度が明確に上がっている。sumitsugiのようなApp Router構成では、Server Actions＋tRPCの併用が現実的な落とし所。

- **ポイント2（GraphQLは「複雑な読み取り」限定で採用）:** GraphQLは物件検索のような多条件フィルタ・関連データ取得が多い画面には強いが、N+1問題やキャッシュ制御の複雑さがあるため、全面採用ではなく特定エンドポイントのみに絞る「ハイブリッドAPI」が2026年の主流。

- **ポイント3（RESTはpublic API/外部連携で依然主流）:** 決済連携や将来の外部パートナー向けAPIなど、社外に公開する境界面はREST+OpenAPIが安定した選択。内部通信はtRPC、外部はRESTという役割分担が現実解。

- **ポイント4（型安全性がAPI設計の最優先指標に）:** エンドツーエンドの型安全性（Zodスキーマ→APIレスポンス→フロント型）がバグ削減に直結するというデータが多く、`.claude/rules/standards.md`が求める「Zodによる境界バリデーション」はこの流れと一致している。

- **ポイント5（Edge/Server Actionsとの統合が進む）:** Next.js 16世代ではServer ActionsがシンプルなCRUD（物件ステータス変更など）を代替しつつあり、API層を薄くして「本当に必要な箇所だけAPI化する」設計が推奨される。

### 4. serverless edge computing 2026

- **ポイント1（エッジランタイムの標準化）:** V8 IsolatesベースのWorkers（Cloudflare Workers, Vercel Edge, Deno Deploy）がデファクトスタンダード化し、コールドスタートは1ms未満まで短縮。sumitsugiのような物件検索・地図表示など地理的に分散したアクセスが多いプロダクトでは、TTFB短縮に直結する。

- **ポイント2（Edge DBの成熟）:** Cloudflare D1、Turso（libSQL）、PlanetScaleなどエッジレプリケーション対応DBが本番運用レベルに到達し、読み取りをユーザーに最も近いリージョンで処理できるように。物件一覧のような読み取り比率の高いクエリはエッジキャッシュ＋エッジDBの組み合わせで大幅高速化が見込める。

- **ポイント3（Next.js × Edge Runtimeの制約緩和）:** Next.js 16ではNode.js APIとEdge Runtimeの互換性ギャップが縮小し、Middlewareだけでなく一部のServer Componentsもエッジ実行可能に。ただしFull Route Cacheとの相性やPrisma等ORMのエッジ対応状況は要検証で、全面移行より段階的採用が現実的。

- **ポイント4（コスト構造の変化）:** リクエスト課金からCPU時間課金への移行が進み、静的に近いページ（物件詳細・LP）はエッジで安価に配信できる一方、認証・決済など計算量の多い処理は依然サーバーレス関数向き。用途別の使い分け設計が2026年のベストプラクティス。

- **ポイント5（可観測性のギャップ）:** エッジ分散実行はデバッグ・ロギングの難易度が上がる（OpenTelemetry対応がまだ発展途上）。導入する場合はSentry/Datadog等のエッジ対応トレーシングを事前に確保しないと、障害時の原因特定コストが跳ね上がるリスクがある。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証がデファクトスタンダード化し、フィッシング耐性のあるパスキーをプライマリ手段として設計すべき。パスワードは「レガシー互換用のフォールバック」として扱い、新規登録フローではパスキー登録を先に促す設計が主流。

- **段階的リスクベース認証（Adaptive Auth）:** デバイスフィンガープリント・行動パターン・IPレピュテーションをリアルタイムでスコアリングし、リスクが高い操作（決済・個人情報変更）にのみ追加認証を要求する設計が重要。全操作に同じ強度のMFAを課すとUX悪化とドロップ率上昇を招く。

- **セッション・トークン管理の厳格化:** アクセストークンの短寿命化（15分程度）＋リフレッシュトークンローテーション、およびDPoP（Demonstrating Proof of Possession）のようなトークン束縛技術で、トークン漏洩時の被害範囲を最小化する設計が推奨される。

- **BFF（Backend for Frontend）パターンでのトークン隠蔽:** SPAやモバイルアプリがアクセストークンを直接保持せず、BFF層がCookieベースでセッションを管理する構成にすることで、XSSによるトークン窃取リスクを構造的に排除できる。

- **AIエージェント/Bot対策としての認証強化:** 生成AIを使った自動化攻撃（クレデンシャルスタッフィング、アカウント乗っ取り）が高度化しているため、CAPTCHAだけでなくPoW（Proof of Work）チャレンジや行動生体認証を組み合わせた多層防御が必要。sumitsugiのような不動産プラットフォームでは、物件情報スクレイピングや不正な問い合わせbot対策としても同様の仕組みが有効。

### 6. database architecture Prisma Supabase 2026

## CTO視点: データベースアーキテクチャ (Prisma × Supabase 2026)

- **ポイント1: コネクションプーリングは今も落とし穴** Next.jsのサーバーレス関数はリクエストごとに新規DB接続を張りがちで、SupabaseのSupavisor（transaction mode）かPrisma Accelerateを必ず経由させないと本番で接続枯渇が起きる。うちのようなVercel/Next.js構成では特に注意が必要。

- **ポイント2: RLS（Row Level Security）をアプリ側認可の代わりに使う** Supabaseの強みはPostgresネイティブのRLSで、`前の住人`/`次の住人`のようなロールベースアクセス制御をDB層で保証できる。アプリコード側のif文だけに頼るとバグで情報漏洩するリスクがあるため、物件データの`draft`/`public`ステータス制御などはRLSポリシーとして二重化すべき。

- **ポイント3: Prismaはスキーマファースト、マイグレーション競合に注意** 複数人・複数worktreeで同時に`schema.prisma`を触ると、マイグレーション履歴が分岐しやすい。PR単位でマイグレーションファイルをレビューし、`prisma migrate diff`でステージング適用前に差分確認するフローを徹底すべき。

- **ポイント4: pgvector活用でAIマッチング機能への布石** SupabaseはPostgres拡張としてpgvectorを標準サポートしており、将来的な「引き継ぎ物件レコメンド」や意味検索機能を追加する際、別のベクトルDBを新規導入せず既存Postgresで完結できる。今のうちにスキーマ設計で拡張余地を残しておく価値がある。

- **ポイント5: Prisma ORMのRustエンジン脱却（TypeScript化）でコールドスタートが改善傾向** サーバーレス環境でのバンドルサイズ・起動時間が課題だったが、この移行によりVercelのようなエッジ/サーバーレス環境でのレイテンシ改善が期待できる。バージョンアップ時はこの変更を意識してベンチマークを取ると良い。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC（GC提案）の主要ランタイム対応が進み、Rustでも`wasm32-unknown-unknown`に加えてGC連携ターゲットが実用段階に入りつつある。ただしsumitsugiのようなNext.js/TypeScript中心のスタックでは、画像処理やPDF生成など計算集約タスクに限定して導入する方がROIが高い。

- **ポイント2:** `wasm-bindgen`と`wasm-pack`のビルド時間・バンドルサイズが改善され、Rust製WASMモジュールをNext.js App Router（RSC/Edge Runtime）に組み込む際のコールドスタート影響が縮小している。物件検索のスコアリングや大量画像のリサイズ処理をエッジ側でWASM化する選択肢が現実的になった。

- **ポイント3:** Component Model（WASI Preview 2）の安定化により、Rust製の小さな処理単位を言語非依存で再利用できるようになった。将来的に「引越し費用」計算ロジックのような業務ロジックを独立コンポーネント化し、フロント/バックエンドで共有する設計も検討可能。

- **ポイント4:** SIMD対応がブラウザ標準になり、Rust+WASMのネイティブ比パフォーマンスギャップは特定ワークロード（画像変換、PDF生成、暗号処理）で10-20%まで縮小。sumitsugiの物件写真最適化パイプラインは候補になり得るが、現状はNext.js標準の`next/image`で十分カバーできており優先度は低い。

- **ポイント5:** 開発ベストプラクティスとして、WASM導入は「JSでは遅すぎる処理が明確にある場合のみ」という原則が業界標準化しつつある。MVPローンチ準備中の現フェーズでは、パフォーマンスボトルネックが実測で特定されるまでWASM/Rust導入は見送り、TypeScript一本化を維持するのが妥当。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格採用:** 静的シェルと動的コンテンツを1つのルートで組み合わせられるPPRが安定版となり、初回表示速度を保ちながらパーソナライズされたコンテンツを配信できる。物件一覧ページなど「基本レイアウトは静的・在庫状況は動的」という構成に相性が良い。

- **Server Actions とキャッシュ戦略の成熟:** `use cache` ディレクティブやタグベースの再検証（`revalidateTag`）が定着し、ミューテーション後のキャッシュ無効化をより細かく制御できるようになった。前の住人プロフィールや物件ステータス更新のような書き込み処理をAPI Routeなしで完結できる。

- **Server Components ファーストの徹底:** Client Componentは「本当にインタラクティブが必要な葉ノード」だけに限定する設計が主流化し、バンドルサイズ削減とTTIの改善に直結する。フォームや認証状態のようなインタラクティブ要素以外はServer Componentに寄せるべき。

- **Streaming + Suspense の粒度設計:** ルート単位ではなくコンポーネント単位で `loading.tsx` / `<Suspense>` 境界を細かく設計し、遅いデータ取得（例: 引越し費用の見積もりAPI）だけを個別にストリーミングするパターンが一般化。ウォーターフォールを避けるための並列データフェッチ設計が重要。

- **Middleware の軽量化トレンド:** Edge RuntimeでのMiddlewareはコールドスタート・実行コストへの意識から責務を最小限（認証チェック・リダイレクトのみ）に絞る設計が推奨される。認可ロジックの本体はServer Component/Server Action側に置く分離が定石になりつつある。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化:** Edge RuntimeはNode.js Runtimeより起動が速いが、依存パッケージのバンドルサイズが1MBを超えると初期化コストが無視できなくなるため、`edge`指定のAPIルートは必要最小限のライブラリ構成に保つべき。

- **リージョン配置の最適化:** `export const preferredRegion`でDBやSupabase等のバックエンド近接リージョンを明示指定することで、Edge→Origin間のレイテンシを大幅削減できる。特に住人データのようなリアルタイム性が求められる読み取りではこの設定が体感速度に直結する。

- **キャッシュ戦略との併用:** Edge Functionsは計算のみで完結させ、`fetch`のキャッシュタグ（`revalidateTag`）やISRと組み合わせて再計算を最小化するのがベストプラクティス。物件一覧のようなアクセス頻度の高いページはEdge+ISRのハイブリッドで配信コストとレイテンシを両立できる。

- **Middlewareの肥大化に注意:** 認証チェックやリダイレクトロジックをMiddlewareに集約しすぎるとEdge実行時間が伸び、全リクエストに影響するボトルネックになる。sumitsugiのauth-context連携では、Middlewareは軽量なトークン検証のみに絞り、詳細な権限チェックはページ/APIレイヤーに委譲する設計が望ましい。

- **観測性（Observability）の確保:** Edge環境はNode.js APIが使えずログ収集が制約されるため、Vercelの`waitUntil()`を活用した非同期ログ送信やOpenTelemetry対応の軽量SDK導入が2026年のトレンド。障害調査のためにも本番投入前にログ経路を検証しておくべき。

### 10. TypeScript type safety patterns 2026

- **型推論の型安全性の高度化:** TypeScript 5.x以降の`satisfies`演算子とconst型パラメータが標準化し、過度な型注釈なしで正確な型推論を得られるようになった。Zodなどのスキーマライブラリと組み合わせ、実行時検証と静的型を一元化するパターンが主流。
- **ブランド型(Branded Types)によるドメイン境界の強化:** `type UserId = string & { __brand: 'UserId' }`のようなパターンで、単純なstring/numberの混同バグを型レベルで防ぐ実装がAPI境界やID管理で定着してきている。本プロジェクトでも`seller`等の内部用語とUI表示の分離同様、型レベルでの意味的な区別が重要。
- **テンプレートリテラル型とルーティングの型安全化:** Next.js App RouterのようなファイルベースルーティングでURLパスやクエリパラメータをテンプレートリテラル型で表現し、存在しないルートへのリンクをコンパイル時に検出する手法が普及。`src/app/properties/[id]`のような動的ルートの型付けに有効。
- **Zodスキーマからの型導出を単一ソースに:** `z.infer<typeof Schema>`でランタイム検証スキーマから型を導出し、システム境界（フォーム入力・API応答）での型と検証ロジックの二重管理を排除するパターンが標準ベストプラクティス化。`.claude/rules/standards.md`のZod必須方針と直結する。
- **`unknown`優先とtype guardの徹底:** `any`を撲滅し外部データは`unknown`で受けてtype predicateや`zod.safeParse`で絞り込む設計が2026年時点でのデフォルト作法となり、CIでの`noImplicitAny`/`strict`設定が事実上必須要件化している。
