# CTO Knowledge - 2026-09-25

## Daily Update (2026-09-25)

### 1. Next.js performance optimization 2026

- **React Server Components とPartial Prerenderingの本格運用:** App RouterのPPR (Partial Prerendering) が安定版となり、静的シェルを即座に配信しつつ動的部分をストリーミングする構成が標準化。TTFBとLCPの両立が容易になった。

- **Turbopackへの完全移行:** Next.js 16でdev/buildともにTurbopackがデフォルト化し、Webpackに比べてビルド時間が大幅短縮。大規模なsrc/app配下でも増分ビルドが数秒単位で完了する。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** fetchレベルではなく関数・コンポーネント単位でキャッシュ境界を明示でき、`revalidateTag`との組み合わせで過剰な再検証を防止。データ取得層（`src/lib/data.ts`など）の設計に直結する。

- **画像・フォント最適化のエッジ処理標準化:** `next/image`のエッジ最適化とVariable Fontsのサブセット化がデフォルト挙動になり、Core Web Vitals（特にCLS/LCP）の改善が実装コスト無しで得られるようになった。

- **Server Actionsのペイロード最小化とストリーミングフォーム送信:** 物件一覧・お問い合わせフォームのような多入力フォームで、Server Actions経由の差分送信＋楽観的UI更新がパフォーマンスとUXの両立に有効。listing/フォーム周りへの適用余地が大きい。

### 2. React Server Components streaming 2026

- **段階的ハイドレーションの標準化:** Next.js 16ではRSCとSuspenseによるストリーミングSSRがデフォルト挙動となり、ページ全体の初期表示を待たずに「重要な部分から順にレンダリング→クライアントへ送信」する構成が標準化されている。sumitsugiの物件一覧・詳細ページのような画像やレビューを多く含むページでは、LCP（Largest Contentful Paint）改善に直結する。

- **Server Actionsとの統合による往復削減:** フォーム送信（お問い合わせ、内見予約など）をServer Actions経由でRSCツリーに直接統合することで、従来のAPI Route+クライアントfetchより往復回数を削減できる。ただしエラーハンドリングとZodバリデーションの境界設計を誤ると、楽観的UI更新とストリーミング更新の競合でUXが崩れやすい点に注意が必要。

- **Partial Prerendering (PPR) の実用フェーズ入り:** 静的シェル（ヘッダー、ナビゲーション）を即座に配信しつつ、動的部分（在庫状況、価格変動）だけをストリーミングで後追い配信するPPRが実運用レベルに達している。物件ステータス（`draft`/`public`）のような頻繁に変わらないデータは静的化、リアルタイム性が必要な部分のみ動的化する設計判断がパフォーマンスとキャッシュ効率の両立に効く。

- **キャッシュ戦略の複雑化とデバッグコスト:** RSCストリーミングはブラウザ・CDN・サーバー間のキャッシュ層が増える分、キャッシュ不整合のデバッグが難しくなる傾向がある。本番導入前にNext.jsのキャッシュタグ（`revalidateTag`等）の運用ルールをチーム内で明文化しておくべき。

- **バンドルサイズよりTTFB最適化が焦点に:** クライアントバンドル削減はRSCの恩恵としてほぼ定着した一方、2026年のトレンドはエッジランタイムでのTTFB（Time To First Byte）最適化に移っている。ローンチ前のパフォーマンス検証では、Lighthouseのバンドルサイズ指標だけでなく、エッジ配信のTTFBも計測項目に加えることを推奨する。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの台頭）:** TypeScriptフルスタック構成（Next.js等）ではtRPCがREST/GraphQLに代わる選択肢として定着しつつある。スキーマ定義とクライアント型が自動同期されるためAPI層のボイラープレートが激減し、sumitsugiのようなNext.js App Router構成では特に相性が良い。

- **ポイント2（GraphQLは複雑なクエリ要件がある場合のみ）:** GraphQLは柔軟なクエリ能力が強みだが、N+1問題対策・認可ロジックの複雑化・キャッシュ戦略の難しさから、シンプルなCRUD中心のプロダクトでは過剰投資になりやすい。物件検索のように複雑なフィルタ・関連データ取得が必要な画面に限定して採用するのが現実的。

- **ポイント3（RESTはOpenAPI+型生成で延命）:** 素のRESTでも`openapi-typescript`等でスキーマから型を自動生成すれば、tRPCに近い型安全性を後付けできる。外部連携（決済・地図API等）や将来的なモバイルアプリ対応を見据えるなら、汎用性の高いRESTを維持する価値がある。

- **ポイント4（Server ActionsとAPI層の境界の曖昧化）:** Next.js App RouterのServer Actionsが普及し、単純なフォーム送信やミューテーションは専用APIエンドポイントを作らずServer Actionsで完結させる流れが強まっている。APIレイヤーは「外部公開が必要な操作」や「モバイル/サードパーティ連携」に限定し、内部処理はServer Actionsに寄せることで実装コストを削減できる。

- **ポイント5（バリデーションの一元化）:** Zodなどのスキーマ定義をtRPC/Server Actions双方の入力検証に共通利用する設計が主流化しており、CLAUDE.mdの「Zodスキーマで境界検証」方針とも合致する。API方式を問わず、単一のスキーマ定義をクライアント・サーバー間で共有することが型安全性とバグ削減の鍵となる。

### 4. serverless edge computing 2026

- **エッジでのAI推論の一般化:** Cloudflare WorkersやVercel Edge FunctionsでLLM推論を直接実行できるようになり、レイテンシとコストを大幅に削減できる。sumitsugiのような物件検索・レコメンド機能は、ユーザーに近いエッジで処理することでUX向上が見込める。
- **コールドスタート問題の実質的解消:** V8 IsolatesベースのランタイムやWasmの成熟により、コールドスタートがミリ秒単位まで縮小し、サーバーレスがリアルタイム性の求められる用途にも適用可能になった。
- **エッジ・オリジン間のデータ整合性:** D1やTurso、PlanetScaleなどエッジ対応DBの普及で、グローバル分散読み取りと単一書き込みリージョンを組み合わせた設計が標準化しつつある。物件データのようにReadが多くWriteが少ないユースケースと相性が良い。
- **Next.js 16のエッジランタイム統合強化:** App RouterでのPartial PrerenderingとEdge Middlewareの組み合わせが成熟し、認証チェックや地域別コンテンツ出し分けをオリジンサーバーを介さず処理できる。認証まわりの実装を見直す際の選択肢になる。
- **コスト構造の変化への注意:** リクエスト課金からCPU時間課金への移行が進むベンダーが増え、重い処理をエッジに置くと想定外のコスト増になるケースがある。ベータローンチ前にトラフィックパターンを想定したコストシミュレーションをしておくべき。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証がデファクトスタンダード化しており、フィッシング耐性のあるパスキーをプライマリな認証手段とし、パスワードは復旧経路としてのみ残す設計が推奨される。
- **段階的リスクベース認証:** ログイン時のデバイス・位置情報・行動パターンをスコアリングし、リスクが高い場合のみ追加認証（MFA/生体認証）を要求することで、UXとセキュリティを両立させる。
- **トークン管理の徹底:** アクセストークンは短命化（15分程度）し、リフレッシュトークンはローテーション＋再利用検知を実装、httpOnly/Secure/SameSiteのCookie属性を必須とする。
- **セッション・デバイス管理の可視化:** ユーザーが自分のアクティブセッション・連携デバイスを一覧・失効できるUIを提供し、不審なログインを即座に検知・通知する仕組み（メール/プッシュ）を組み込む。
- **サーバーサイドの多層防御:** レート制限・IPレピュテーション・ボット検知（CAPTCHA代替のInvisible Challengeなど）をAPI境界に配置し、認証エンドポイントへの総当たり・クレデンシャルスタッフィング攻撃を防ぐ。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** PrismaはRust製クエリエンジンからTypeScript/WASMベースへの移行を進めており、Supabase環境でのコールドスタート・エッジデプロイ時のレイテンシが改善傾向にある。エッジ関数と組み合わせる場合は最新版のドライバ互換性を都度確認すべき。

- **ポイント2:** SupabaseのRow Level Security(RLS)とPrismaのORM層を併用する構成が主流化しており、DB側で権限制御を完結させることでアプリ層のバグによる情報漏洩リスクを大幅に下げられる。物件データや個人情報を扱う本プロジェクトでは特に有効。

- **ポイント3:** Prisma Postgres（マネージドプール）やSupabaseのSupavisorなど、サーバーレス環境向けのコネクションプーリングが標準機能化しており、Vercel等のサーバーレスNext.jsデプロイでの接続枯渇問題が解消されつつある。

- **ポイント4:** マイグレーション管理はPrisma Migrate単体運用からSupabase CLIとの二重管理を避け、片方に一本化する運用が推奨されるようになっている。チーム開発では「Prisma schemaを正とし、Supabase側はマイグレーション適用のみ」というルールが事故防止に効果的。

- **ポイント5:** pgvector拡張を用いたベクトル検索がSupabase上で一般化し、Prismaからも`Unsupported("vector")`型で扱えるようになった。物件レコメンドや類似物件検索などのAI機能を将来追加する際の技術的下地として押さえておく価値がある。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデルの成熟:** WASI Preview 2とComponent Modelが実用段階に入り、Rustで書いた処理単位を言語非依存で合成できるようになった。境界を越えたデータコピーのオーバーヘッドが減り、マイクロサービス的な粒度でWASMモジュールを組み合わせる設計が現実的になっている。

- **JIT/AOTの進化でネイティブとの差が縮小:** WasmtimeやWasmerのAOTコンパイル最適化が進み、Rust製WASMは多くのワークロードでネイティブバイナリの90%超の性能に到達しつつある。ただし境界越えの呼び出し頻度が高いホットパスでは依然オーバーヘッドが無視できない点に注意。

- **SIMD/マルチスレッドの標準化定着:** Wasm SIMDとシェアードメモリ+Atomicsがブラウザ・サーバ双方で安定サポートされ、Rustの`std::simd`やrayon相当の並列処理をWASM上でも活用しやすくなった。画像処理・暗号・ML推論の前処理などCPUバウンドな処理をブラウザ側にオフロードする選択肢が増えている。

- **エッジ/サーバレスでの採用加速:** Cloudflare Workers、Fastly Compute、Fermyonなどエッジランタイムでの起動レイテンシ（ミリ秒未満のコールドスタート）がRust+WASMの強みとして評価され、Node.jsベースのサーバレス関数の置き換え先として採用が増えている。

- **実務上の注意点:** バンドルサイズとデバッグ体験（ソースマップ・スタックトレース）はまだJS/TSエコシステムに劣る部分があるため、全面移行ではなくパフォーマンスクリティカルな一部処理（画像変換、PDF生成、暗号処理など）から段階導入するのが現実的な戦略。

### 8. Next.js App Router patterns 2026

- **ポイント1（Server Components前提の設計）:** Next.js 16ではServer Componentsがデフォルトの思想となっており、データ取得はできる限りサーバー側で完結させ、Client Componentsは対話が必要な末端（フォーム、ボタン等）に限定するのがベストプラクティス。sumitsugiでも`src/app/properties/`のような一覧・詳細ページはServer Componentで統一し、フィルタUIなど状態を持つ部分だけを`'use client'`に切り出すと保守性が高まります。

- **ポイント2（Partial Prerendering / キャッシュ戦略の成熟）:** 静的部分と動的部分を1ページ内で混在させるPartial Prerendering (PPR) が実用段階に入り、`fetch`のキャッシュ制御（`cache: 'force-cache'` / `revalidate`）と組み合わせることで、SEO重視の物件詳細ページを高速配信しつつ在庫状況などの動的データもリアルタイム表示できます。

- **ポイント3（Server Actionsによるフォーム簡素化）:** 物件登録・お問い合わせフォームなどはServer Actionsを使うことでAPI Routeを別途書かずにミューテーションを完結でき、Zodバリデーションと組み合わせれば`standards.md`の「システム境界でのZod検証」方針とも整合します。

- **ポイント4（型安全なルーティングとMiddleware最適化）:** App Routerの型付きルート（typed routes）が標準化されつつあり、`account/`配下のような認証必須ページではMiddlewareでの早期リダイレクトとレイアウトレベルの認可チェックを併用することで、クライアント側でのちらつき（フラッシュ）を防げます。

- **ポイント5（画像・フォント最適化のデフォルト化）:** `next/image`や`next/font`の最適化がビルド時によりアグレッシブに行われるようになり、Airbnb風のビジュアル重視なUIでもLCP（Largest Contentful Paint）を意識せずパフォーマンスを担保しやすくなっています。

### 9. Vercel Edge Functions optimization 2026

- **リージョン最適化とデータ局所性:** Edge Functionsは実行リージョンがリクエスト元に自動選択されるが、DB接続先とリージョンがずれるとレイテンシが逆に悪化するため、`regions`設定をデータベース（例: Vercel Postgres, PlanetScale, Turso）のプライマリリージョンに近づける設計が重要。

- **Node.js RuntimeとEdge Runtimeの使い分け:** Vercel Fluid Computeの普及により、Edge限定だったAPIも大半がNode.js Runtimeで低コールドスタートを実現できるようになったため、Edge Runtimeは「本当にグローバル低レイテンシが必要な軽量処理（認証チェック、リダイレクト、A/Bテスト判定）」に絞るのが2026年のベストプラクティス。

- **ミドルウェアの肥大化を避ける:** `middleware.ts`はすべてのリクエストで実行されるため、重い処理（画像処理、複雑なJSON変換）を書くとサイト全体のTTFBが悪化する。認可判定などの軽量ロジックのみに限定し、重い処理はAPI Routeやサーバーアクションに逃がすべき。

- **キャッシュ戦略との統合:** Next.js 16のキャッシュコンポーネント（`use cache`ディレクティブ）とEdge Functionsを組み合わせることで、動的パーソナライゼーション（例: 「前の住人」情報のログイン状態別出し分け）をEdgeで行いつつ、静的部分はISR/PPRでキャッシュする構成が主流に。全ページをEdge化するのはコスト・複雑性の面で非推奨。

- **可観測性コストの管理:** Edge Functionsは実行時間課金かつログ保持期間が短いため、本番トラブルシューティング用に構造化ログを外部集約（Axiom, Datadog等）へストリームする設定を最初から組み込んでおくことが、障害対応速度に直結する。

### 10. TypeScript type safety patterns 2026

- **ポイント1（型からランタイム検証への統合）:** ZodやValibotなどのスキーマライブラリで型定義とランタイムバリデーションを一元化する `schema-first` パターンが主流化しており、APIレスポンスやフォーム入力など境界層での型安全性を保証しつつ、`z.infer`で型定義の二重管理を排除できる。sumitsugiでもZodをシステム境界（フォーム・API）で徹底することで、実行時の型崩れを防げる。

- **ポイント2（Branded Types / Nominal Typingの普及）:** `PropertyId`と`UserId`のような構造的に同じstring型を誤って混同するバグを防ぐため、Branded Types（`type PropertyId = string & { __brand: 'PropertyId' }`）の採用が増えている。IDを扱うドメインロジックが多いプラットフォームでは、コンパイル時に取り違えを検出できる効果が大きい。

- **ポイント3（Exhaustiveness Checkingの徹底）:** `'draft' | 'public'`のようなUnion型のステータス管理では、`switch`文の`default`に`never`型のアサーションを置くことで、新しいステータス追加時にコンパイルエラーで気づける仕組みが標準的になっている。CLAUDE.mdにある「Union型変更時は全usageをgrep」というルールは、この仕組みで自動化・強制できる。

- **ポイント4（TypeScript 5.x以降のconst型パラメータとsatisfies演算子）:** `satisfies`演算子により、オブジェクトリテラルの型推論を保ちながら型チェックを行うパターン（設定オブジェクトやルーティング定義など）が定着し、過度な型注釈を書かずに安全性を担保できる。site-config.tsのような設定ファイルに適用すると保守性が上がる。

- **ポイント5（AIコード生成時代の型安全性の重要性増大）:** Claude Codeのような自律開発エージェントが大量にコードを生成する環境では、型システムが「セーフティネット」として機能する比重が増しており、`strict: true`はもちろん`noUncheckedIndexedAccess`のような厳格オプションを有効化することで、エージェントが見落としがちな配列アクセスのnull安全性などを機械的に検出できる。
