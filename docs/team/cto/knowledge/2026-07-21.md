# CTO Knowledge - 2026-07-21

## Daily Update (2026-07-21)

### 1. Next.js performance optimization 2026

- **ポイント1:** Partial Prerendering (PPP) の本格運用化 — 静的シェルを即座に返しつつ動的部分をストリーミングする手法がNext.js 16で安定版となり、TTFBを大幅短縮できる。sumitsugiの物件一覧・詳細ページのような「静的な骨格＋動的な在庫情報」構成に相性が良い。

- **ポイント2:** React Server Components (RSC) のバンドル最適化が標準化 — クライアントJSを最小化し、`'use client'`境界を絞ることでCore Web Vitals（特にLCP・INP）が改善する。フォーム系（引越し費用計算など）以外は極力Server Componentに寄せるのが定石。

- **ポイント3:** キャッシュ戦略の粒度制御（`use cache`ディレクティブ）が実用段階に — ページ単位ではなく関数・データ取得単位でキャッシュを制御でき、物件検索のような頻繁に変わるデータと静的コンテンツを同一ページ内で使い分けやすくなった。

- **ポイント4:** エッジランタイムでの画像最適化とAVIF/WebPの自動配信がデフォルト化 — `next/image`のエッジ変換により、物件写真中心のUIでLCP改善とデータ転送量削減を同時に達成できる。

- **ポイント5:** ビルド時の型チェック分離（Turbopackの型チェック並列化）— `bun run build`の速度が向上し、CIパイプラインのボトルネックが軽減。ローンチ前の頻繁なデプロイサイクルにおいて開発体験の改善に直結する。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** React 19以降、`<Suspense>`境界を起点にServer Componentsのストリーミングが実用段階に入り、Next.js 16ではPPR（Partial Prerendering）と組み合わせることでTTFBとLCPを大幅に短縮できる。当プロジェクトでも`properties/`一覧ページのような重いデータフェッチを含む画面で導入価値が高い。

- **キャッシュ戦略の複雑化:** Server Componentsのストリーミングはリクエスト単位のキャッシュ制御（`use cache`ディレクティブ、`revalidateTag`）と密結合しており、物件データのようにpublic/draft状態が頻繁に変わる場合は、キャッシュ無効化ロジックの設計を最初に固めないとステール表示のバグを生みやすい。

- **クライアントバンドル削減の実効性:** RSCによりインタラクティブでないUI（物件詳細の静的情報など）をサーバー側で完結させることで、shadcn/uiコンポーネントを多用する当プロジェクトでもクライアントJSを削減できるが、`'use client'`境界の引き方を誤ると恩恵が相殺されるため、コンポーネント設計時にサーバー/クライアント境界を明示的にレビューする運用が必要。

- **エラーハンドリングとフォールバックUI:** ストリーミング中に発生したエラーは`error.tsx`とSuspense単位のフォールバックで個別に処理する必要があり、認証やフォーム送信などユーザー操作を伴う箇所では、部分的なストリーミング失敗がUXを損なわないよう明示的なローディング/エラー境界設計が重要になる。

- **計測とパフォーマンス予算:** ストリーミングは体感速度を改善する一方、Core Web Vitalsの計測方法（特にLCP/INP）がストリーミングされたコンテンツを正しく評価できるか注意が必要で、ローンチ前のパフォーマンス予算設定時にはこの点を計測基盤に反映すべき。

### 3. API design REST GraphQL tRPC 2026

- **型安全性が主戦場に:** tRPCやHono RPCのようなエンドツーエンドの型推論が標準化し、OpenAPI/GraphQLスキーマ手動同期の手間を排除する流れが加速。sumitsugiのようなNext.js+TypeScript構成では、フロントとAPI間の型共有導入が開発速度に直結する。

- **GraphQLは「集約層」として残存、素のCRUDはREST/RPCが優勢:** 複数マイクロサービスを束ねるBFF用途ではGraphQLが依然強いが、単一Next.jsモノリスのような構成ではtRPC/Server Actionsの方がオーバーヘッドが少なく実用的。

- **Server ActionsがRPCの代替として台頭:** Next.js 15/16のServer Actionsにより、API Routes自体を書かずにクライアント→サーバー呼び出しが可能になり、小規模〜中規模プロダクトではtRPC層すら不要になるケースが増えている。物件データのCRUD操作など単純な処理はServer Actionsで十分な場合が多い。

- **スキーマ駆動+Zodによる境界検証が必須化:** API設計トレンドとしてはランタイム検証（Zod等）をスキーマ定義に統合し、型定義と入力検証を一元化する手法が主流。既存の「Input validation: Zodスキーマを境界で使用」という方針は2026年のベストプラクティスと合致している。

- **AI Agent向けAPI設計（Tool/Function calling互換）が新たな検討軸:** 将来的にAIエージェント（Claude等）が物件検索・予約フローを直接操作する可能性を見据え、REST/GraphQLに加えてMCPやtool-calling互換のインターフェース設計を検討する価値がある。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG(Web-interoperable Runtimes Community Group)準拠のランタイム（Cloudflare Workers, Deno Deploy, Vercel Edge等）が主流になり、Node.js固有APIへの依存を避けることで、複数プロバイダー間での可搬性が実質的なアーキテクチャ要件になっている。

- **コールドスタート問題の実質的解消:** V8 IsolatesベースのランタイムやWASMコンパイルにより起動時間がミリ秒単位に収束し、リアルタイム性が求められるsumitsugiのような予約・決済フローでもエッジでの認証・バリデーション処理が現実的な選択肢になっている。

- **エッジDBとデータ整合性のトレードオフ:** Cloudflare D1やTurso等のエッジレプリケーションDBが普及する一方、強整合性が必要な物件ステータス更新（`draft`/`public`切り替え）のような処理は依然としてリージョナルなプライマリDBに寄せる設計判断が必要。

- **AI推論のエッジ配置:** 軽量LLM推論やベクトル検索をエッジで実行するパターン（Vectorize等）が普及し、IC（インテリアコーディネーター）マッチングのような推薦ロジックをレイテンシ最適化のためエッジ側に一部移すアーキテクチャが検討可能になっている。

- **可観測性コストの増大:** リクエストが地理的に分散するため、分散トレーシング（OpenTelemetry対応）なしでは障害の切り分けが困難になり、エッジ移行の初期投資として監視基盤整備が前提条件になっている。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への全面移行:** パスワードレス認証（WebAuthn/Passkeys）がデファクトスタンダード化しており、フィッシング耐性のある認証をデフォルトにすることでクレデンシャルスタッフィング攻撃のリスクを根本的に排除できる。

- **多層防御としてのリスクベース認証:** デバイスフィンガープリント・行動分析・地理的異常検知を組み合わせたアダプティブ認証により、UXを損なわずに不正ログインを検知する運用が主流になっている。

- **短命トークン+リフレッシュトークンローテーション:** JWTなどのアクセストークンは有効期限を短く保ち、リフレッシュトークンは使用ごとにローテーションさせることで、トークン漏洩時の被害を最小化する設計が必須。

- **認証基盤の外部化とゼロトラスト原則:** 自前実装よりAuth0/Clerk/Supabase Authのような実績あるIDプロバイダを採用し、内部・外部問わず「常に検証する」ゼロトラストモデルでセッション管理を行うことがコスト効率と安全性の両面で有利。

- **多要素認証（MFA）の強制とリカバリーフローの堅牢化:** MFAを標準化する一方で、アカウント復旧プロセス自体が新たな攻撃経路にならないよう、本人確認の厳格化とレート制限・監査ログの整備が重要な論点になっている。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Supabaseは2026年時点でPrisma ORMとの統合を公式にファーストクラスサポートしており、Prisma Postgres（旧Prisma Data Platform）とSupabaseのマネージドPostgresを併用するハイブリッド構成が一般化。エッジ関数からのDB接続にはPgBouncer/Supavisor経由のコネクションプーリングが必須で、Prismaの`directUrl`と`url`を使い分ける設定が定番になっている。

- **ポイント2:** Prisma OrmはRust製クエリエンジンからTypeScript純正エンジン（Prisma Client Rust-free）へ移行が進み、コールドスタートが速くなったためVercel EdgeやSupabase Edge Functionsとの相性が大幅改善。サーバーレス環境でのバンドルサイズとレイテンシを気にする場合は、この新エンジンへの移行を優先すべき。

- **ポイント3:** Row Level Security（RLS）をアプリケーション層のPrisma Client経由でどう扱うかが依然として設計上の課題で、Supabase Authのユーザーコンテキストをサービスロールキー越しにPrismaへ渡す際は、RLSをバイパスしないよう`SET LOCAL`でセッション変数を注入するパターンがベストプラクティスとして定着している。

- **ポイント4:** Prisma MigrateとSupabaseのブランチング機能（Supabase Branching）を組み合わせたプレビュー環境ごとのDBスキーマ分離が標準化しつつあり、PRごとに独立したDBブランチを作成してマイグレーションを検証してからマージするワークフローが、うちのようなAgent Teamsパイプラインとも相性が良い。

- **ポイント5:** リアルタイム機能（Supabase Realtime）とPrismaのスキーマ管理を併用する際は、PostgresのレプリケーションスロットとPrismaのシャドウDBが競合しやすいため、CIでのマイグレーション自動化にはシャドウDB用の別インスタンスを明示的に用意することが推奨されている。

### 7. WebAssembly Rust performance 2026

- **ポイント1（Component Model標準化の進展）:** WASI 0.3とComponent Modelの安定化により、Rust製WASMモジュールが言語横断で相互運用可能になり、フロントエンドとサーバーレス双方でネイティブに近い起動速度（コールドスタート数ms単位）を実現しやすくなっています。

- **ポイント2（SIMD/マルチスレッド対応の実用化）:** `wasm32-wasip2`ターゲットとWASM SIMD128、スレッド提案（shared memory + atomics）が主要ブラウザ・ランタイムで安定運用レベルに達し、画像処理や暗号演算など計算集約タスクでネイティブの70〜90%程度の性能が現実的になっています。

- **ポイント3（バイナリサイズとツールチェーン最適化）:** `wasm-opt`、`twiggy`、`cargo-wasi`などのエコシステムが成熟し、Rustの強みである「ランタイム無しゼロコストアブストラクション」を活かしつつバイナリサイズを大幅削減できるため、Cloudflare WorkersやFastly Compute@Edgeのようなエッジ実行環境との親和性が高いです。

- **ポイント4（開発体験の向上）:** `wasm-bindgen`/`wasm-pack`のビルド速度改善とVite/Next.js等バンドラーとの統合が進み、TypeScript側からRust実装の高速な数値計算・パーサー・暗号処理をシームレスに呼び出せるようになり、フロントエンドのボトルネック部分だけをRustに置き換える段階的移行がしやすくなっています。

- **ポイント5（運用面の実用的示唆）:** sumitsugiのようなNext.js中心のプロダクトでは、全面的なWASM導入より「画像処理・PDF生成・大量データのフィルタリングなど特定のホットパスのみをRust/WASM化する」局所適用がROIが高く、まずはプロファイリングでボトルネックを特定してから導入を検討するのが現実的です。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** 静的シェルと動的コンテンツを1つのルートで共存させるPPRが安定版として広く採用され、TTFBを保ちつつパーソナライズされた部分だけを`Suspense`でストリーミングする構成が主流になっている。物件詳細ページのように「基本情報は静的・在庫や価格は動的」というケースに特に有効。

- **Server Actions のセキュリティ強化パターン:** Server Actionsが認証・決済処理の主要な入口になる一方、CSRF対策やレート制限の実装がベストプラクティス化。`"use server"`関数内でのZodバリデーション＋Origin検証を必須とする実装が標準になりつつある。

- **キャッシュ戦略の明示化 (`cacheLife`/`cacheTag`):** Next.js 15以降で導入された`use cache`ディレクティブと`cacheTag`/`revalidateTag`によるきめ細かいキャッシュ制御が定着し、暗黙的なフルルートキャッシュへの依存から「明示的にキャッシュ範囲を宣言する」設計に移行している。前の住人のプロフィールなど更新頻度が低いデータと、空室状況など頻繁に変わるデータを分離してキャッシュ設計すべき。

- **Server Componentsファーストのデータフェッチ:** クライアントサイドの`useEffect`+fetchパターンは非推奨化が進み、Server Componentsでのデータ取得＋Client Componentsへの最小限のprops渡しが標準アーキテクチャに。ウォーターフォールを避けるため`Promise.all`での並列フェッチとstreaming SSRの組み合わせが定石。

- **Turbopackのビルド標準化とエッジランタイムの使い分け:** Turbopackが`next build`のデフォルトとなりビルド時間が大幅短縮された一方、Node.js RuntimeとEdge Runtimeの使い分け（重い処理はNode、軽量な認証チェックなどはEdge）がパフォーマンス設計の基本となっている。

### 9. Vercel Edge Functions optimization 2026

Vercel Edge Functions optimization 2026について、CTO視点でまとめます。

- **ポイント1（Node.js Runtimeとの統合が進みEdgeの使いどころが明確化）:** 2026年時点でVercelはEdge RuntimeとNode.js Runtimeの差を縮め、多くのAPI RouteはNode.js Runtime + Fluid Computeの組み合わせで十分な低レイテンシを得られるようになった。sumitsugiではEdgeは「認証チェック・地域別リダイレクト・A/Bテスト」等の軽量Middleware用途に絞り、DB接続を伴うAPI（物件検索・決済関連）はFluid Compute上のNode.js Runtimeに置くのが妥当。

- **ポイント2（Fluid Computeによるコールドスタート・コスト最適化）:** リクエスト間でインスタンスを再利用するFluid Computeがデフォルト化し、過去の「とにかくEdgeに寄せる」戦略は見直しが進んでいる。DB接続プーリング（Prisma Accelerate等）を使う処理はEdgeではなくFluid Compute上に統一する方が、コネクション数管理がシンプルになる。

- **ポイント3（Middlewareの実行コスト可視化とバンドルサイズ規律）:** Vercelダッシュボードでミドルウェアごとの実行時間・課金額が可視化され、重いライブラリimportなどの無駄が即座にコスト増として見える化されている。auth-context関連のMiddlewareはJWT検証など軽量処理に限定し、ユーザー情報のフル取得はServer Componentsに任せる設計を維持すべき。

- **ポイント4（Edge Config / ISRとの組み合わせ最適化）:** 読み取り頻度の高い物件一覧ページは、Edge ConfigやISRと組み合わせてEdgeでのオリジンアクセスを最小化しつつ最新性を保つのが2026年の定石。公開ステータス（`'public'`）変更時のみオンデマンドISR再検証をかける設計が、コストと鮮度のバランスとして有効。

- **ポイント5（過剰最適化への警戒）:** MVP〜ベータローンチ段階のトラフィック規模ではEdge特有の最適化（リージョン分散等）の投資対効果は低い。「シンプルさ > 完璧さ」の技術原則に従い、標準のNode.js Runtime + Vercel CDNキャッシュで十分。最適化はユーザー数が10倍に伸びた段階（10倍ルール）で再検討するのが妥当。

### 10. TypeScript type safety patterns 2026

- **型の実行時検証統合:** Zodなどのスキーマライブラリで型定義とランタイムバリデーションを一元化する流れが定着し、`z.infer<>`で型を自動導出することでスキーマと型定義の二重管理を防げる。

- **`satisfies`演算子の定着:** 型の広がり（widening）を防ぎつつ型推論の恩恵も残せるため、設定オブジェクトやconstマップの定義で`as const`単体より安全なパターンとして標準化しつつある。

- **Discriminated Unionによる状態管理:** `'draft' | 'public'`のようなstatus型は、フラグの組み合わせではなくtagged unionで表現することで、コンパイラが不正な状態遷移を検出できる。本プロジェクトの物件ステータス設計はこの好例。

- **strictな型チェックのCI必須化:** `tsc --noEmit`をビルドの前段階として独立させ、lint/testだけでなく型チェック自体をCIゲートにする構成が標準に。本プロジェクトのCLAUDE.mdでも「build integrity」として明文化されている通り、型の一貫性チェックを省略しないことが事故防止の鍵。

- **テンプレートリテラル型とブランド型の実務活用:** IDやパスなど文字列ベースの値をブランド型（nominal typing）で区別し、単純な`string`同士の取り違えバグをコンパイル時に検出する手法が、大規模コードベースで再評価されている。
