# CTO Knowledge - 2026-09-09

## Daily Update (2026-09-09)

### 1. Next.js performance optimization 2026

- **ポイント1: Partial Prerendering (PPR) の本格運用** App Router で静的シェルと動的コンテンツを1レスポンス内で組み合わせるPPRが安定版となり、TTFBを維持しつつパーソナライズ表示が可能に。sumitsugiでも物件一覧の静的枠＋在庫状況の動的差し込みに応用できそう。

- **ポイント2: Turbopackがビルド/開発双方でデフォルト化** `next build --turbopack`が実用レベルに達し、CI上のビルド時間短縮に直結。現状のビルド検証フロー（`bun run build`必須ルール）の実行コストを下げられる余地あり。

- **ポイント3: Server ActionsとuseOptimisticの組み合わせによるフォーム最適化** 引っ越し費用計算や問い合わせフォームのような多段階フローで、クライアントJSを増やさずに楽観的UI更新が可能。E2E必須の対象領域（フォーム・多段階フロー）と相性が良い。

- **ポイント4: 画像・フォントの自動最適化がCore Web Vitalsのしきい値を厳格化** `next/image`のLCP計測がより厳密になり、物件写真中心のUIでは`priority`指定とレスポンシブ`sizes`の見直しが必須になりつつある。

- **ポイント5: キャッシュ戦略の明示化（`use cache`ディレクティブ）** データフェッチ層でキャッシュ境界をコード上で明示する書き方が主流化し、`draft`/`public`ステータスのような状態依存データの再検証ロジックを型安全に管理しやすくなっている。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではRSCのストリーミングがデフォルト最適化され、`loading.tsx`とSuspense境界の粒度設計がTTFB改善の鍵になっている。ページ単位ではなくコンポーネント単位でSuspenseを細かく分割することで、重い物件検索クエリを待たずに骨組みUIを即表示できる。

- **ポイント2:** Partial Prerendering(PPR)が安定版に近づき、静的シェル(ヘッダー・ナビ)を即座に配信しつつ、動的部分(在庫状況・価格)だけをストリーミングする構成が主流になっている。sumitsugiの物件一覧ページでも、静的なレイアウトと動的な`draft/public`ステータス判定を分離すればLCPを大きく改善できる見込み。

- **ポイント3:** Server Actionsとストリーミングの組み合わせで、フォーム送信後の楽観的UI更新パターンが標準化されつつある。引っ越し費用計算や物件登録フォームのような多段階フローでは、`useOptimistic`とストリーミングレスポンスを組み合わせることで体感速度が向上する。

- **ポイント4:** RSCペイロードのキャッシュ戦略(`revalidateTag`ベースの部分再検証)が成熟し、物件データのようにセラー側で頻繁に更新されるが閲覧側では多少のラグが許容されるデータに対して、きめ細かいキャッシュ無効化が可能になっている。

- **ポイント5:** ストリーミングSSRのエッジランタイム対応が進み、Bunランタイム自体もエッジ相当の起動速度を持つため、Vercel以外のホスティング(自前インフラ含む)でもRSCストリーミングの恩恵を受けやすくなった。ベータローンチ後のスケール検討時に選択肢として有力。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCがフロントエンド/バックエンド共にTypeScriptな構成（Next.jsモノレポ等）でのデファクトになりつつあり、スキーマ定義とAPI実装が一体化することでコード生成やドキュメント同期の手間が消える。sumitsugiのようなNext.js Server Actions中心の構成なら、tRPC導入コストは低く型安全性の恩恵が大きい。

- **ポイント2:** GraphQLは大規模・複数クライアント（Web/モバイル/外部パートナー）が絡む場合に依然強いが、単一チーム・単一フロントエンドのプロダクトではオーバーエンジニアリングになりがち。現状の物件検索・引き継ぎフローのような比較的シンプルなドメインではREST/tRPCで十分。

- **ポイント3:** 2026年はAPIのAIエージェント消費（LLMがツールとしてAPIを呼ぶ）を前提にした設計が重要になっており、OpenAPIスキーマの厳密さやエラーメッセージの構造化がAIエージェント連携の成否を左右する。将来的にサードパーティ連携や自動化ワークフローを見据えるなら、Zodスキーマから自動でOpenAPI定義を生成する仕組みを早めに整えておく価値がある。

- **ポイント4:** Server Actions（Next.js）とtRPCの役割分担が曖昧になりがちで、「内部向けのミューテーションはServer Actions、外部/複数クライアント向けはtRPC or REST」という明確な境界線をチームで合意しておかないと、同じ機能が二重実装されるリスクがある。

- **ポイント5:** パフォーマンス面では、GraphQLのN+1問題対策（DataLoader等）やtRPCのバッチング設定を怠るとDBアクセスが爆発するケースが増えている。物件一覧・検索のような一覧系APIは特にクエリ設計とキャッシュ戦略（React Query / SWR + tRPCの組み合わせ）を初期段階で決めておくべき。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG準拠のWeb標準API（Fetch, Streams）がCloudflare Workers/Vercel Edge/Deno Deployで統一され、ベンダーロックインが大幅に減少している。

- **コールドスタート問題の実質的解消:** V8 isolateベースの起動が1桁ミリ秒台に到達し、EdgeでのSSR/APIレスポンスがオリジンサーバーと遜色ない速度になったため、Next.jsのMiddlewareやServer Actionsをエッジ配置する判断がデフォルト化しつつある。

- **エッジでのステートフル処理:** Durable Objects/Cloudflare D1のようなエッジネイティブなデータレイヤーが成熟し、認証セッションや在庫状態などをリージョンをまたいで低遅延に扱えるようになった。sumitsugiのような物件検索・予約フローでは、閲覧数の多い物件データをエッジKVにキャッシュしつつ、予約確定などの整合性が必要な処理のみオリジンDBに委譲する設計が現実的。

- **コスト構造の変化:** リクエスト課金からCPU時間課金への移行が進み、静的コンテンツ配信は劇的に安価になった一方、重い画像処理やAI推論をエッジで行うと逆にコスト増になるケースがあるため、ワークロードの見極めが重要。

- **観測性（Observability）の追いつき:** 分散したエッジ実行環境でのトレーシング・ログ集約ツール（OpenTelemetry対応）がようやく実用レベルに達し、これまで「デバッグしづらい」とされていたエッジ運用のハードルが下がった。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証（WebAuthn）が主流になり、フィッシング耐性のある認証手段としてパスキーを第一選択肢にすべき。パスワードは補助的な回復手段としてのみ残す設計が推奨される。

- **フィッシング耐性MFAの必須化:** SMS/TOTPベースのMFAはAiTM（Adversary-in-the-Middle）攻撃で突破される事例が増加しており、証明書ベースやFIDO2セキュリティキーなど、フィッシング耐性のある要素への移行が急務。

- **セッション管理とトークンバインディング:** 認証成功後もセッショントークンの窃取（Cookie盗難等）がリスクの中心となっており、デバイスバインディングや短命トークン+リフレッシュの組み合わせ、異常検知による再認証要求が標準化されつつある。

- **ゼロトラスト原則の徹底:** 「一度ログインすれば信頼」ではなく、リクエストごとにコンテキスト（デバイス・場所・行動パターン）を評価する継続的認証（Continuous Authentication）の採用が拡大している。

- **Rate LimitingとBot対策の統合:** ログイン試行・パスワードリセット等のエンドポイントに対するクレデンシャルスタッフィング攻撃が高度化しており、単純なIPベースのレート制限だけでなく、行動分析ベースの異常検知との併用が重要。

### 6. database architecture Prisma Supabase 2026

**CTO視点：database architecture Prisma × Supabase 2026 トレンド**

- **ポイント1（Prisma Postgres / Rustレスエンジン）:** Prismaは2025年にRust製クエリエンジンを廃止しTypeScript/WASMベースへ移行し、Prisma Postgres（マネージドDB＋グローバルキャッシュ）を統合。Vercel/Edge環境でのコールドスタートが大幅改善され、Next.js App Routerとの相性が良くなった。
- **ポイント2（Supabaseのブランチング + RLS運用）:** SupabaseのDBブランチ機能（PRごとに本番同型のPostgresを自動プロビジョニング）がステージング検証の標準になりつつあり、Row Level Security（RLS）をアプリ層の認可ロジックから分離できる点はsumitsugiのような`draft/public`ステータス管理に有効。
- **ポイント3（ORMは併用が現実解）:** PrismaのスキーマDXとSupabaseのRLS/Realtime/Storageを組み合わせる構成が主流化しているが、当プロジェクトは既にDrizzle + 生Postgresで運用中のため、乗り換えコストとRLS移行の複雑さを考えると現行スタック維持が合理的。
- **ポイント4（コネクションプーリング）:** サーバーレス関数からのDB接続数枯渇はPrisma Accelerate（またはSupabaseのSupavisor）でのプーリングが必須要件になっており、当プロジェクトのDockerベースPostgresでも本番移行時にはPgBouncer相当の導入を検討すべき。
- **ポイント5（pgvectorによるAI機能拡張）:** Supabaseのpgvector標準サポートにより、物件検索のセマンティック検索や「前の住人」とのマッチング機能をAI駆動で実装する際にDB内で完結できる設計が可能になっている。

### 7. WebAssembly Rust performance 2026

- **ポイント1（コンポーネントモデルの実用化）:** WASM Component Model が2026年時点でツールチェイン全体に浸透し、Rustクレートを言語非依存の再利用可能コンポーネントとして配布できるようになった。`wit-bindgen` の生成コードが安定し、FFI境界のシリアライズオーバーヘッドが大幅に削減されている点は、マイクロサービス的な設計をブラウザ/エッジ双方で採用する際の実用的な判断材料になる。

- **ポイント2（SIMD・スレッドの標準化完了）:** WASM SIMD128とShared Memory + Web Workers連携によるマルチスレッド実行が主要ブラウザで安定サポートされ、Rust側は `std::simd`（portable-simd安定化）や `wasm-bindgen-rayon` との組み合わせで、画像処理・PDF生成のようなCPUバウンド処理をネイティブの70-90%程度の速度で実行できる。引越し費用計算や物件写真の最適化処理をクライアント側に寄せる選択肢として検討価値あり。

- **ポイント3（バイナリサイズとコールドスタートの改善）:** `wasm-opt`（Binaryen）とRustの `panic = "abort"` + `lto = true` 設定の組み合わせがデファクト化し、典型的なWASMバンドルが数百KB台まで縮小可能になった。Next.jsのエッジランタイムでWASMモジュールを使う場合、コールドスタート時間が実用上無視できるレベルまで下がっている。

- **ポイント4（サーバーサイドWASMランタイムの成熟）:** Wasmtime/WasmerがOCI互換のコンテナ代替として本番投入されるケースが増え、Rust製サンドボックス実行環境（ユーザー生成コードの安全な実行、プラグインシステムなど）の構築コストが下がった。将来的に「前の住人」向けカスタムテンプレート機能などをサンドボックス実行させたい場合の選択肢になり得る。

- **ポイント5（デバッグ・可観測性の改善）:** DWARF経由のソースマップ対応が改善され、ブラウザDevToolsでRustコードを直接ステップ実行できるようになった。本番導入の心理的障壁だった「デバッグしづらさ」が緩和されており、段階的な採用（まずは重い計算処理のみWASM化）がしやすくなっている。

### 8. Next.js App Router patterns 2026

- **サーバーコンポーネント最適化の成熟:** Next.js 16ではRSC(React Server Components)のペイロード圧縮とストリーミングSSRがデフォルト最適化され、Client Componentへの`"use client"`境界を最小限に絞ることでTTFB(Time to First Byte)を大幅短縮できる。sumitsugiでも`properties/`や`listing/`配下のデータ取得部分をServer Componentに寄せ、インタラクティブなUI部分のみClient化する設計が有効。

- **Partial Prerendering (PPR) の実運用化:** 静的シェルを即座に返しつつ動的部分をストリーミングで後追いする方式が安定版となり、物件一覧ページのような「静的レイアウト＋動的な空室状況」の組み合わせに最適。ISR/SSGの使い分けを迷う場面が減り、キャッシュ戦略がシンプルになる。

- **Server Actionsのセキュリティ強化がベストプラクティス化:** フォーム送信（引越し費用の申込みなど）で`"use server"`を使う際、認可チェックをAction内部で必ず行う設計が標準に。CSRF対策やZodによる入力検証をServer Action境界で一元化するパターンが定着している。

- **App Routerのファイルベースルーティング＋並行ルート(Parallel Routes)の活用拡大:** ダッシュボードや物件詳細ページで`@modal`スロットを使ったモーダル実装（ブラウザバック対応込み）が一般化し、UXを損なわずにルーティング状態と密結合したUIが組みやすくなっている。

- **エッジランタイムとNode runtimeの使い分けの明確化:** 認証チェックや軽量なリダイレクトはEdge Middleware、DB接続や重い処理はNode runtimeという住み分けが明文化され、レイテンシとコストのバランスを取りやすくなった。前の住人/次の住人のマッチング処理のような重い計算はNode側に置く判断が重要。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1（コールドスタート削減）:** Edge Runtimeは V8 isolateベースのため元々コールドスタートが数十ms程度と軽量だが、依存パッケージのバンドルサイズが直接起動時間に効いてくるため、`middleware.ts`や個別Edge Functionでは不要なライブラリ（特にNode.js APIに依存する重量級SDK）を持ち込まないことが引き続き最重要な最適化ポイント。
- **ポイント2（Node.js APIとの互換性拡大）:** Edge RuntimeでサポートされるNode.js API（`crypto`, `Buffer`など）が年々拡大しており、以前はNode.js Runtime必須だった処理（JWT検証など）もEdgeで完結できるケースが増えている。認証まわりの軽量処理はEdgeに寄せることでレイテンシを削減できる。
- **ポイント3（Fluid ComputeとEdge Middlewareの使い分け）:** Vercelの「Fluid Compute」モデルにより、リクエストの性質（軽量・グローバル分散が必要ならEdge、DB接続や長時間処理が必要ならNode.js/Fluid）で使い分ける設計判断がより明確になった。sumitsugiでは物件検索やリダイレクトなどの軽量処理はEdge、決済・DB書き込みはNode.js Runtimeに置くのが妥当。
- **ポイント4（キャッシュ戦略との統合）:** `ISR`や`fetch`のキャッシュタグと組み合わせ、Edge Functionでのレスポンスを`Cache-Control`やVercelのData Cacheと連携させることで、Edgeの低レイテンシとキャッシュヒット率の両立が可能。物件一覧のような読み取り頻度の高いページに有効。
- **ポイント5（オブザーバビリティの強化）:** Edge Functionは分散実行のためデバッグが難しく、2026年時点ではVercelの`OpenTelemetry`統合が標準化されつつある。本番導入前にトレーシングを組み込み、リージョンごとのレイテンシ差を可視化しておくことが運用上重要。

### 10. TypeScript type safety patterns 2026

- **ポイント1（型優先の`satisfies`活用）:** `as const satisfies`パターンが定着し、リテラル型を保ちつつ構造チェックも行える書き方が標準に。設定オブジェクトやAPIレスポンス定義で`as`によるダウンキャストを避けられる。
- **ポイント2（バリデーションとの型統合）:** Zodなど実行時バリデーションから型を推論する`z.infer`パターンが主流化し、フロント/バックエンド間のスキーマ二重管理が不要に。当プロジェクトのAPI境界でのZod活用もこの流れに合致。
- **ポイント3（テンプレートリテラル型の実用化）:** ルーティングパスやCSSクラス名など文字列ベースのAPIで、テンプレートリテラル型による静的検証が一般化。`src/app/`のルート定義など動的パス生成箇所で型安全性を高められる。
- **ポイント4（strictオプションの段階的強化）:** `noUncheckedIndexedAccess`や`exactOptionalPropertyTypes`など従来「厳しすぎる」とされたstrictオプションを有効化する動きが加速。配列アクセスやオプショナルプロパティ由来のnullバグを未然に防げる。
- **ポイント5（型レベルテストの自動化）:** `tsd`や`expect-type`による型シグネチャのユニットテストがCIパイプラインに組み込まれるケースが増加。ユーティリティ型や共有インターフェースの後方互換性を機械的に保証できる。
