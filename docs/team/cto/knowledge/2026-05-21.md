# CTO Knowledge - 2026-05-21

## Daily Update (2026-05-21)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降でPPRが安定化し、静的シェルと動的コンテンツを同一ルートで混在させることで、TTFBとLCPを同時に最適化できる。従来のSSR/SSGの二択から解放される重要な転換点。

- **React Server Components によるバンドルサイズ削減:** RSCをデフォルト活用することでクライアント送信JavaScriptを大幅削減。`'use client'`の範囲を最小化し、重いライブラリ（日付処理・MDXパーサー等）をサーバー側に閉じ込めるのが2026年の標準実装。

- **Turbopack の実用段階移行:** Turbopackがdev・buildともに安定稼働し、大規模コードベースでのHMRが5〜10倍高速化。`next dev --turbo`から`next build --turbo`への移行判断がチームの生産性に直結する。

- **`after()` API によるレスポンス後処理の分離:** `unstable_after`（Next.js 15で導入）を使い、ログ・分析・キャッシュ更新をレスポンス完了後に非同期実行。ユーザーへのレスポンスタイムに影響なく副作用処理を行える。

- **Image/Font 最適化の徹底とCore Web Vitals優先設計:** `next/image`のsizes属性適切設定とpriority指定、`next/font`によるCLS撲滅が引き続き重要。2026年はLighthouse CIをPRゲートに組み込みリグレッション防止するのがベストプラクティス。

### 2. React Server Components streaming 2026

- **Suspense境界の戦略的配置が鍵:** 2026年時点では、RSCのストリーミングはSuspense境界の粒度設計が実装品質を左右する。データフェッチの遅い箇所を個別にSuspenseで囲むことで、TTFBを維持しつつ段階的なUI描画が実現できる。

- **PPR（Partial Prerendering）の本格普及:** Next.js 15以降でStableとなったPPRにより、静的シェルを即時配信しつつ動的コンポーネントのみストリームする設計が主流になった。CDNキャッシュと動的コンテンツの両立がアーキテクチャの基本パターンとなっている。

- **Server Actions + optimistic UIの組み合わせが標準化:** `useOptimistic`とServer Actionsを組み合わせたパターンが成熟し、クライアント状態管理ライブラリへの依存を大幅に削減できる。ミューテーション処理をサーバー側に集約することでセキュリティと一貫性も向上する。

- **ストリーミング中のエラーハンドリングに注意:** ストリーム開始後にサーバーエラーが発生した場合、HTTPステータス200を返した後にエラーが起きるため従来のエラーページ遷移が効かない。`error.tsx`とSuspenseの`fallback`を組み合わせた境界設計を必ず実装すること。

- **Edge Runtimeとの相性を見極める:** RSCストリーミングはNode.jsランタイムで最も安定しているが、Edge Runtimeでは一部のNode.js APIが使えず制約が多い。データベース直接接続が必要なコンポーネントはNode.jsランタイムに留め、Edgeは認証・リダイレクト等の軽量処理に限定するのが現実的な設計判断。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** Next.js + tRPC の組み合わせが2026年のスタンダードになりつつあり、クライアント・サーバー間でTypeScript型を共有することでAPI契約の破損を静的に防げる。ランタイムエラーよりコンパイル時エラーを優先する設計哲学が定着した。

- **REST vs GraphQLの決着:** GraphQLは大規模BFF（Backend for Frontend）やサードパーティ公開APIでは依然有力だが、内部APIでのオーバーヘッド（スキーマ管理・N+1問題）が再評価され、小〜中規模ではRESTまたはtRPCへの回帰が進んでいる。

- **OpenAPIの復権:** AI/LLMエージェントがAPIを自律的に呼び出すユースケースが増え、機械可読なOpenAPI仕様の重要性が再燃。`zod-openapi` や `@hono/zod-openapi` でコードファーストにスキーマを生成するアプローチが主流。

- **エッジ・ストリーミング対応:** Vercel Edge / Cloudflare Workers 上でのAPI実行が一般化し、RSC（React Server Components）のストリーミングと組み合わせたデータフェッチ設計が求められる。従来のRESTの同期レスポンスモデルだけでは対応しきれないケースが増加。

- **APIセキュリティの自動化:** OWASP API Security Top 10（BOLA・過剰データ露出等）への対応を手動レビューに頼らず、Zod/Valibotによる入力バリデーション自動化と、ミドルウェアレベルのレート制限・認証統合（Clerk, Auth.js）をセットで設計するのが2026年のベストプラクティス。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジのデファクトランタイムに:** Wasm Componentモデルの成熟により、Cloudflare Workers・Fastly Compute等でポータブルな多言語実行が実用域に達し、コールドスタート問題がほぼ解消された。

- **AI推論のエッジオフロードが本格化:** 小型LLM（1〜7Bパラメータ）をエッジノードに展開しレイテンシを10ms以下に抑える設計が標準となり、プライバシー規制対応と低遅延を同時に実現できる。

- **ステートフルエッジの台頭:** Durable Objects・SQLite-at-the-edgeパターンにより、従来「エッジはステートレス」という制約が崩れ、セッション管理やリアルタイムコラボ機能もエッジ完結で実装可能になった。

- **観測可能性（Observability）がボトルネック:** 分散エッジ環境でのトレーシングはOpenTelemetryの採用が必須だが、数百POPにまたがるトレース集約コストが高く、サンプリング戦略の設計が開発品質を左右する。

- **ベンダーロックイン対策にWinterTC準拠を選択:** Runtime互換標準（WinterCG→WinterTC）に準拠したコードを書くことで、Cloudflare・Vercel・AWS Lambda@Edge間の移植性を確保でき、マルチエッジ戦略のリスクを低減できる。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** FIDO2/WebAuthn標準に基づくパスキーがパスワードレス認証の主流となり、フィッシング耐性とUX向上を両立できる。主要ブラウザ・OSのサポートが成熟した今、新規システムはパスキーファーストで設計すべき。

- **MFAの「疲労攻撃」対策が必須:** プッシュ通知型MFAへのスパム攻撃（MFA Fatigue）が常態化しており、番号照合（Number Matching）やコンテキスト付き承認画面の実装が不可欠となった。

- **トークンの短命化とRotation戦略:** JWTの有効期限は15分以内が標準となり、Refresh Tokenのローテーション（使い捨て）とファミリー無効化によるリプレイ攻撃対策がベストプラクティス。Next.jsならEdge Middlewareでの検証が効率的。

- **デバイスフィンガープリントとリスクベース認証:** ログイン時のデバイス・IP・行動パターンを機械学習で分析し、異常検知時のみ追加認証を要求するAdaptive MFAが普及。ユーザー体験を損なわずにセキュリティを強化できる。

- **サプライチェーン攻撃への備え:** 認証ライブラリ（next-auth等）の依存関係を定期監査し、`package-lock.json`のハッシュ固定とDependabotによる自動アップデートを組み合わせることで、ゼロデイ脆弱性への露出期間を最小化する。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のEdge Runtime対応:** Prisma Accelerateを活用することでVercel EdgeやCloudflare WorkersからもPrismaが利用可能になり、レイテンシを大幅削減できる。コネクションプーリングも自動管理されるため、サーバーレス環境でのDB接続枯渇問題が解消される。

- **Supabase Branching（プレビュー環境）の実用化:** 2025-2026年にかけてSupabase Branchingが安定し、PRごとに独立したDBブランチを持てるようになった。マイグレーションのCI/CDが容易になり、本番DBを汚染せずにスキーマ変更をテストできる。

- **Row Level Security (RLS) とPrismaの組み合わせの注意点:** SupabaseのRLSはPostgres側で動作するが、PrismaはService Roleキーを使うとRLSをバイパスする。アーキテクチャ設計時にAnon/Authenticated Roleキーの使い分けを明示的に設計しないとセキュリティホールになる。

- **Vector/pgvector統合の主流化:** Supabase + pgvectorによるRAG構成が2026年現在スタンダードになっており、PrismaもUnsupported型でベクトルカラムを扱える。AIチャット・セマンティック検索機能をゼロから外部サービスなしで実装できる。

- **スキーマドリフト対策としてのマイグレーション戦略:** `prisma migrate diff`とSupabase CLIの`db diff`を組み合わせてドリフト検出を自動化するのがベストプラクティス。本番環境では`migrate deploy`のみを許可し、`migrate reset`を明示的にブロックするCI設定が必須。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASIp2（WebAssembly System Interface Preview 2）の普及により、Rust製WASMコンポーネントがサーバーレス・エッジ環境で本格的に実用化され、コールドスタートを従来のコンテナ比で10〜100倍高速化できる。

- **ポイント2:** `wasm-bindgen` + `wasm-pack` エコシステムの成熟により、RustとJavaScript間のFFIオーバーヘッドが大幅に削減され、複雑なデータ構造のやりとりでもゼロコピーに近いパフォーマンスが実現しつつある。

- **ポイント3:** WASMのSIMD命令サポートとマルチスレッド（`wasm-threads`）の安定化により、画像処理・暗号化・機械学習推論など計算集約型ワークロードでネイティブバイナリの80〜90%のスループットを達成できるケースが増えている。

- **ポイント4:** Cloudflare Workers・Fastly Compute・WasmEdgeなどのWASMランタイムがRustの `no_std` クレートと連携し、バイナリサイズを100KB以下に抑えたエッジデプロイが標準的な選択肢になってきた。

- **ポイント5:** コンポーネントモデル（Component Model）の標準化により、異なる言語間でWASMモジュールを安全に合成できるため、Rustで書いたパフォーマンスクリティカルな部分だけを既存のNode.js/Pythonスタックに組み込む「部分移行」戦略が現実的になっている。

### 8. Next.js App Router patterns 2026

- **Server Componentsをデフォルトに:** 2026年のApp Routerでは、データフェッチはServer Componentsで完結させ、`'use client'`の境界を最小化するのがベストプラクティス。クライアントバンドルサイズを大幅に削減できる。

- **Partial Prerendering（PPR）の活用:** 静的シェルと動的コンテンツを同一ルートで共存させるPPRが安定版となり、TTFBとLCPの両立が可能に。`<Suspense>`境界の設計がパフォーマンスの鍵。

- **Server Actions中心のミューテーション設計:** フォーム送信・データ変更はServer Actionsに集約し、APIルートを介さない直接DB操作パターンが主流。`revalidatePath`/`revalidateTag`との組み合わせでキャッシュ整合性を保つ。

- **`use cache`ディレクティブによる細粒度キャッシュ:** Next.js 15+で導入された`use cache`を使い、関数・コンポーネント単位でキャッシュ戦略を宣言的に定義できる。`fetch`のキャッシュオプションより柔軟で、複雑なデータ依存関係の管理が容易。

- **Parallel Routes + Intercepting Routesでモーダル設計:** `@slot`によるParallel RoutesとIntercepting Routesを組み合わせることで、URLを維持しつつモーダル・ドロワーを実装するパターンが定着。このプロジェクト（sumitsugi）の物件詳細モーダルにも適用を検討する価値がある。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeでのコールドスタート最小化:** Vercel Edge FunctionsはV8 Isolateベースのため従来のNode.jsより高速だが、バンドルサイズを50KB以下に抑えることでコールドスタートをさらに削減できる。`next/server`の`EdgeRuntime`制約を活用し、不要な依存関係を排除することが重要。

- **Fluid Computeによるコスト最適化:** 2025年後半に本格化したFluid Computeモデルにより、リクエスト処理中のCPU使用時間のみ課金される。従来の常時稼働モデルより大幅にコスト削減できるため、トラフィックが断続的なAPIに積極採用すべき。

- **KVストアとのデータ局所性:** Vercel KV（Redis互換）やEdge Configをエッジ関数と同リージョンに配置することで、レイテンシを数ms単位で削減できる。特にフィーチャーフラグや設定値の読み取りはEdge Configが最適解。

- **Middleware vs Edge Routeの使い分け:** 認証チェックやリダイレクトはMiddlewareで処理し、ビジネスロジックはEdge Route Handlersに分離する設計が2026年のベストプラクティス。Middlewareは全リクエストを通過するため、処理を最小限に絞らないとP99レイテンシに直接影響する。

- **Streaming ResponseとSuspenseの統合:** App RouterのServer ComponentsとEdge FunctionsをStreaming Response（`ReadableStream`）で組み合わせることで、TTFB（Time to First Byte）を大幅に改善できる。特にAI生成コンテンツや重いデータ取得を含むページで効果が顕著。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded Typesが標準的なパターンとなり、プリミティブ型の混在バグを型レベルで防ぐ実践が広まっている。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` を使い、型推論の恩恵を保ちながら型制約も同時に検証するパターンが定着。`as` キャストによる型の強制抑制を減らせる。

- **Result型による明示的なエラーハンドリング:** `Promise<T>` の代わりに `Promise<Result<T, E>>` パターンを採用し、例外の暗黙的な伝播を型システムで可視化する設計が増加している。特にAPIレイヤーで有効。

- **Template Literal Typesによるルート・キー検証:** `type Route = '/users' | '/users/${string}'` のような型でAPIルートやi18nキーを型安全に管理し、ランタイムエラーをコンパイル時に検出するアプローチが実用化されている。

- **`noUncheckedIndexedAccess` の実質的な標準化:** `tsconfig` で `noUncheckedIndexedAccess: true` を有効にし、配列・オブジェクトへのアクセスで `T | undefined` を強制することで、未定義アクセスによるランタイムクラッシュを大幅に削減できる。
