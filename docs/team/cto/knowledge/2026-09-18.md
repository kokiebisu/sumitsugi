# CTO Knowledge - 2026-09-18

## Daily Update (2026-09-18)

### 1. Next.js performance optimization 2026

- **ポイント1:** Partial Prerendering (PPR) が安定版に近づき、静的シェルと動的コンテンツを同一ルートで組み合わせられるようになった。ダッシュボードやEC商品ページのようにSSGとSSRを跨ぐ画面でTTFBを大幅短縮できる。

- **ポイント2:** React Compilerの標準搭載でuseMemo/useCallbackの手動最適化が不要になりつつある。物件一覧のようなリスト再レンダリングが多い画面では、コード量を減らしつつパフォーマンスを維持できる。

- **ポイント3:** `next/image`のCDN連携とAVIF/WebP自動変換に加え、Cache Componentsによる細粒度キャッシュ制御が主流化。物件写真が多いsumitsugiのようなサービスでは画像最適化とキャッシュ戦略がLCP改善の最大レバー。

- **ポイント4:** Turbopackがビルド・開発サーバーのデフォルトとなり、大規模リポジトリでのHMR/ビルド時間が数倍短縮。CI時間の削減にも直結するため、`bun run build`のCIコストにも効いてくる。

- **ポイント5:** Server Actionsのストリーミング対応とEdge Runtimeの成熟により、フォーム送信や検索のようなインタラクションでもSSRのレイテンシを抑えられる。認証・決済フローのようなmulti-stepフローで特に有効。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Prerendering との統合が主流に** Next.jsのPPR(Partial Prerendering)とRSCストリーミングの組み合わせが標準化しつつあり、静的シェルを即座に返しつつ動的部分だけを`Suspense`境界でストリーミングする構成がデフォルトパターンになっている。TTFBとインタラクティブ性を両立できるため、物件詳細ページのような「基本情報は静的・在庫状況は動的」なUIと相性が良い。

- **ポイント2: キャッシュ戦略の複雑化への対応** RSCのストリーミングが進むほど「どのコンポーネントをどの粒度でキャッシュ/再検証するか」が設計上の焦点になっており、`use cache`ディレクティブやタグベースの再検証(`revalidateTag`)を活用したセグメント単位のキャッシュ設計が重要になっている。sumitsugiのような物件一覧+個別ページ構成では、一覧はISR的に、詳細はオンデマンドrevalidateにするなど粒度を分けるのが実用的。

- **ポイント3: エラーバウンダリとストリーミングの相性問題** ストリーミング中に発生したサーバーエラーはクライアントに部分的にしか伝わらないケースがあり、`error.tsx`だけでなくストリーム単位でのフォールバックUI設計が必要。特に認証必須ページ(`account/`配下)では、ストリーミング中のセッション切れハンドリングを明示的にテストしないとUXが崩れる。

- **ポイント4: ウォーターフォール回避のためのデータフェッチ設計** Server Components内で逐次`await`を重ねるとストリーミングの恩恵が薄れるため、`Promise.all`での並列フェッチや、意図的に`Suspense`境界を分割してストリームの粒度をUI体験に合わせる設計が引き続き重要。パフォーマンス計測は「初回バイト到達時間」より「体感インタラクティブまでの時間」で評価すべき。

- **ポイント5: バンドルサイズよりもストリーム順序の最適化に焦点** RSCによりクライアントJSは既に削減済みのため、2026年のトレンドは「どのSuspense境界を先に解決させるか」の優先順位付け(loading UIの段階的表示、above-the-foldを最優先ストリーム)にシフトしている。sumitsugiでは物件画像や引越し費用サマリーなど、ユーザーの意思決定に直結する情報を最優先でストリームする設計が有効。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの実質的デファクト化）:** フルスタックTypeScriptモノレポでは、tRPCがスキーマ定義と型共有を一体化できる点から標準選択になりつつある。型安全性を保証しつつコード生成ステップを省けるため、sumitsugiのようなNext.js App Router構成との相性が良く、開発速度を落とさずAPI境界の型崩れを防げる。

- **ポイント2（GraphQLは「集約層」に用途が収束）:** GraphQLは全APIを置き換えるのではなく、複数マイクロサービス/外部APIを束ねるBFF（Backend for Frontend）としての採用に落ち着いてきている。単一サービス内の単純なCRUDにGraphQLを導入するのはオーバーエンジニアリングになりやすく、内部通信はREST/tRPCで十分というのが実務的な結論。

- **ポイント3（RESTは「境界の安定性」で生き残る）:** 外部公開API・パートナー連携・Webhookなど、クライアントを制御できない領域では依然RESTが主流。OpenAPI（Zodスキーマからの自動生成含む）でドキュメントと型を同期させる運用がベストプラクティスとして定着している。

- **ポイント4（Zodによる境界バリデーションの統一）:** REST/GraphQL/tRPCいずれを使う場合も、Zodスキーマを「単一の真実源」として入力検証・型推論・OpenAPI生成に流用する設計が一般化。sumitsugiの標準（`.claude/rules/standards.md`のInput validation方針）とも合致し、システム境界でのバリデーション漏れを防げる。

- **ポイント5（設計判断は「クライアントの多様性」で決める）:** 単一のNext.jsフロントのみが叩くAPIならtRPC一択で開発効率最大化、モバイルアプリや外部パートナーが絡むならREST or GraphQLを検討する、という「クライアント構成起点」の意思決定がベストプラクティスとして定着している。sumitsugiは現状Web単一クライアントのため、tRPC継続が妥当。

### 4. serverless edge computing 2026

- **エッジでのコールドスタート解消:** V8 Isolateベースのランタイム（Cloudflare Workers、Vercel Edge等）が主流化し、コンテナ起動待ちがほぼゼロに。低レイテンシが要求される認証・パーソナライゼーション処理をエッジに寄せる設計が2026年のデフォルトになりつつある。

- **エッジDBとの統合が鍵:** D1やTurso、PlanetScaleのようなエッジネイティブDBが普及し、従来の「エッジはstaticのみ」という制約が崩れている。物件検索や在庫確認のような読み取り中心の処理はエッジDBでレイテンシを一桁改善できる。

- **WASM移植コストの低下:** Rust/Goで書いたロジックをWASMにコンパイルしてエッジで動かす事例が増加。画像処理や料金計算エンジンなど計算負荷の高い処理をNode.jsサーバーからエッジ側に移すハードルが下がった。

- **ベンダーロックインへの警戒:** WinterCG標準（Web標準API準拠）への収斂が進み、Cloudflare/Deno/Vercel間の移植性が向上。とはいえKVストレージやCron的な機能はまだプロバイダ固有なので、抽象化レイヤーを挟む設計判断が引き続き重要。

- **コスト構造の変化に注意:** リクエスト課金からCPU時間課金へのシフトが進み、軽量な処理ほど有利になる一方、重い処理を誤ってエッジに置くと逆にコスト増になるケースが出ている。ワークロードの見極めが運用コストに直結する。

### 5. authentication security best practices 2026

- **パッキーレス認証の主流化:** Passkey（FIDO2/WebAuthn）がパスワードに代わる標準となり、フィッシング耐性のある認証をUXを損なわずに実現できる。実装コストも下がっているため、新規プロジェクトではパスワード認証をデフォルトにしない判断が増えている。

- **トークン管理の厳格化:** JWTの有効期限を短く保ち、リフレッシュトークンのローテーション＋再利用検知を組み合わせることで、トークン漏洩時の被害範囲を最小化できる。localStorage保存は避け、httpOnly Cookie＋SameSite=Strictが基本線。

- **セッション・デバイスバインディング:** 認証情報だけでなく、デバイスフィンガープリントやIPリスクスコアを組み合わせた継続的リスク評価（Continuous Authentication）が標準化しつつあり、単発ログインだけでなくセッション中の異常検知が求められる。

- **サプライチェーン経由の認証リスク:** OAuth/OIDCの外部IdP連携やSDK依存が増える中、依存ライブラリの脆弱性やミス設定（redirect_uri検証漏れなど）が侵入経路になるケースが増加しており、定期的な依存監査と設定レビューが不可欠。

- **法規制対応とプライバシー分離:** 個人情報保護法・GDPR等の強化に伴い、認証情報と個人データの保存を分離し、監査ログを暗号化・改ざん防止する設計が求められる。sumitsugiのような住所・契約情報を扱うサービスでは特に、認証基盤の設計段階から法務要件を織り込む必要がある。

## database architecture Prisma Supabase 2026

- **ポイント1: Prisma ORMとDriver Adaptersの標準化** Prisma 6系以降、Rustベースのクエリエンジンから軽量なTypeScriptネイティブエンジン＋Driver Adaptersへの移行が進み、Supabase（Postgres）接続時もエッジランタイム（Vercel Edge, Cloudflare Workers）でのコールドスタートが大幅に短縮された。sumitsugiのようなVercelデプロイ構成では、Edge Functionsでの物件検索APIをPrisma Accelerate/Driver Adapters経由に切り替えることでレイテンシ改善が見込める。

- **ポイント2: Supabaseのブランチング機能によるプレビュー環境の民主化** Supabase Branching（本番DBのコピーオンライトなプレビューブランチ）がGAし、PRごとに独立したDB環境を自動生成できるようになった。現状の`bun run worktree:create`によるワークツリー並行開発と組み合わせれば、スキーマ変更を伴うPRでもマイグレーション衝突なく並行検証でき、レビュー前のデータ破壊リスクを下げられる。

- **ポイント3: RLS（Row Level Security）とPrismaの併用がベストプラクティス化** SupabaseのRLSポリシーをアプリ層のバリデーションと二重に効かせる構成が2026年の定番になっており、Prismaは「型安全なクエリビルダー」、RLSは「DB層の最終防衛線」という役割分担が明確化している。sumitsugiの`seller`/`draft`・`public`ステータスのようなアクセス制御が絡むテーブルは、Prisma側の絞り込みだけに頼らずRLSポリシーを必ず設定すべき。

- **ポイント4: pgvectorとハイブリッド検索の一般化** Supabaseのpgvector拡張を使ったベクトル検索とPostgresの全文検索を組み合わせたハイブリッド検索が、不動産・マーケットプレイス系プロダクトで標準構成になりつつある。物件の自然言語検索（「駅近で家具付き」等）を実装する際、外部ベクトルDBを新規導入せずSupabase内で完結できる点はインフラコスト・運用面で大きな優位性になる。

- **ポイント5: マイグレーション管理はPrisma MigrateよりSupabase CLI併用が主流に** スキーマ変更をPrisma Migrateだけで完結させず、Supabase CLIのマイグレーション（`supabase db diff`）と併用してRLSポリシー・トリガー・Edge Functionsの変更もバージョン管理する運用が広がっている。CI上で`prisma migrate deploy`と`supabase db push`を順序立てて実行するパイプラインを組むことで、DBスキーマとポリシーの整合性を担保できる。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC（GC提案）が主要ランタイムで安定運用フェーズに入り、RustでもGCを前提としたホスト連携（JS/DOMオブジェクトの直接参照）がコピー・シリアライズコストを削減しつつある。線形メモリとGCヒープの橋渡し設計が新たなアーキテクチャ検討ポイントになる。

- **ポイント2:** Component Model / WASIプレビュー2の普及で、Rustクレートを言語非依存の再利用可能コンポーネントとして配布できるようになり、フロントエンドとエッジ（Cloudflare Workers等）で同一バイナリを共有する構成が現実的になっている。

- **ポイント3:** `wasm-bindgen`やSIMD対応の最適化が進み、画像処理・PDF生成のようなCPUバウンド処理はネイティブJSより数倍高速なケースが増加。sumitsugiのPDF生成や画像最適化処理をWasm化する余地があるか検討価値あり。

- **ポイント4:** マルチスレッド（`wasm-threads` + `SharedArrayBuffer`）とツリーシェイキングの成熟でバンドルサイズ・起動レイテンシが改善し、Next.js 16のRSC境界と組み合わせたクライアントサイド重処理オフロードが実用段階に入っている。

- **ポイント5:** ビルドツールチェーン（`cargo component`, `wasm-pack`）のDX向上でCI統合コストが下がった一方、デバッグ・プロファイリングは依然JSより難易度が高く、導入は「明確な性能ボトルネックが特定された箇所」に限定するのが現実的。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 15〜16でPPRが安定版となり、静的シェルを即座に返しつつ動的部分を`<Suspense>`でストリーミングする設計がデフォルトパターンに。TTFBとインタラクティブ性を両立できるため、物件一覧ページのような「共通レイアウトは静的・検索結果は動的」な構成に最適。

- **Server Actions中心のデータ変更:** フォーム送信やミューテーションはAPI Routeを介さず`'use server'`のServer Actionsで直接処理する流れが定着。問い合わせフォームや引き継ぎ申請フローの実装コード量を削減できるが、`revalidatePath`/`revalidateTag`のキャッシュ無効化設計を最初に決めておかないと本番で古いデータが表示されるバグを生みやすい。

- **`use cache`ディレクティブによる明示的キャッシュ制御:** Next.js 15以降で導入された`use cache`が主流化し、関数・コンポーネント単位で「何をどれだけキャッシュするか」を明示的に書く設計が推奨されるように。データ取得層(`src/lib/data.ts`)にこれを適用すると、物件詳細ページのDB負荷を抑えつつ更新の即時性もコントロールしやすい。

- **Route Groups + Parallel Routesでの権限分岐:** `(auth)`や`@modal`のようなroute groups/parallel routesを使い、ログイン状態や物件ステータス(`draft`/`public`)によって表示を出し分ける設計がベストプラクティス化。中間層のif分岐を減らし、ミドルウェアでのリダイレクトロジックをシンプルに保てる。

- **Server Componentsファーストの計装(Observability):** App Router全体がサーバー実行中心になったことで、OpenTelemetry等でのサーバーサイド計装が標準要件に。クライアントバンドルサイズだけでなく、Server Componentsのレンダリング時間・DBクエリ数を可視化する運用が2026年のパフォーマンス改善の主戦場になっている。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Vercel Edge FunctionsはFluid Compute（同時実行の効率化）によりコールドスタートとコストが大幅改善されており、SSRやAPIルートを積極的にEdge/Fluidランタイムへ移行する価値が高まっている。
- **ポイント2:** Node.js互換性がEdge Runtimeで拡充され、これまでServerless専用だったライブラリ（DBクライアント等）もEdgeで動かせるケースが増えているため、レイテンシ重視の物件検索・地図APIなどはEdge化を検討すべき。
- **ポイント3:** ISR/PPR（Partial Prerendering）とEdge Middlewareを組み合わせることで、物件詳細ページのような「静的部分＋パーソナライズ部分」の混在ページを高速配信しやすくなっている。
- **ポイント4:** Edge Configやキー・バリューストア（Vercel KV等）をEdge Functionsから低レイテンシで参照できるため、フィーチャーフラグやA/Bテスト、地域別料金表示のようなロジックをEdge側に寄せるアーキテクチャが主流になりつつある。
- **ポイント5:** リージョン最適化（Smart Placement）が自動化され、DBに近いリージョンへ関数を自動配置できるため、手動のリージョン指定よりも自動最適化に任せる設計が推奨されている。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScriptのバージョンアップに伴い型推論エンジンが強化され、`satisfies`演算子や`const type parameters`を活用することで、型の広がりを防ぎつつ推論の恩恵を最大化するパターンが主流になっている。
- **ポイント2:** Zodなどのスキーマバリデーションライブラリと型定義を一体化する「Schema-first型設計」が定着し、APIの入出力やフォームバリデーションで実行時検証と静的型チェックを二重管理せずに済むようになった。
- **ポイント3:** `unknown`型を起点にした型ガード・判別可能な合併型（Discriminated Union）の徹底で、`any`の使用を排除し実行時エラーをコンパイル時に検出する文化が浸透している。
- **ポイント4:** モノレポ構成でのプロジェクト参照（Project References）とインクリメンタルビルドの最適化により、型チェックのCI実行時間を大幅短縮するのが標準的なベストプラクティスになっている。
- **ポイント5:** テンプレートリテラル型やBranded Types（nominal typing）を用いて、文字列IDやドメイン固有の値を型レベルで区別し、意味的な誤代入をコンパイル時に防ぐ設計が広がっている。
