# CTO Knowledge - 2026-10-14

## Daily Update (2026-10-14)

### 1. Next.js performance optimization 2026

- **ポイント1: Partial Prerendering (PPP) の本格採用:** Next.js 16ではPartial Prerenderingが安定版となり、静的シェルを即時配信しつつ動的部分のみストリーミングするハイブリッド構成が標準化。TTFBを維持しながら個人化コンテンツを扱えるため、`sumitsugi`の物件一覧（静的な枠組み＋動的な空室状況）のようなページに特に有効。

- **ポイント2: React Server Components + キャッシュ戦略の精緻化:** `use cache`ディレクティブやキャッシュプロファイル（`cacheLife`/`cacheTag`）の実用化が進み、データフェッチ単位での粒度の高いキャッシュ制御が可能に。物件データ（`src/lib/data.ts`）のような頻繁更新されないデータはタグベースで再検証し、不要な再フェッチを削減すべき。

- **ポイント3: Turbopackのビルド/Dev両対応が標準化:** `bun run build`を含むビルド全体がTurbopackベースに移行し、webpack比で大幅な高速化が実現。ただし一部のwebpack専用プラグインは非対応のため、依存ライブラリの互換性を事前チェックする必要あり。

- **ポイント4: 画像・フォント最適化のエッジ処理:** `next/image`のエッジランタイム最適化とAVIF優先配信が進み、物件写真のような画像中心コンテンツのLCP改善に直結。CDNエッジでのオンデマンド変換により、ビルド時間への影響も最小化。

- **ポイント5: Core Web Vitalsの計測指標がINPへ完全移行:** FIDが廃止されINP（Interaction to Next Paint）が唯一のインタラクティブ性指標に。フォームや多段階フロー（予約・引き継ぎフロー）でのクライアント側JS実行コストを見直し、不要なクライアントコンポーネント化を避けることが重要。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPartial Prerendering (PPR) が安定版となり、静的シェルを即時配信しながら動的部分だけをストリーミングする設計がデフォルト化している。初回表示速度（TTFB/LCP）を落とさずに個人化コンテンツを組み込めるため、物件一覧ページのようなSEO重視+動的要素混在のUIに最適。

- **ポイント2:** Suspenseバウンダリの粒度設計が重要度を増している。大きすぎるとウォーターフォールが隠れて逆に遅くなり、小さすぎるとネットワークリクエスト数が増える。`src/app/properties/` のような一覧+詳細構成では、画像・価格・レビューなど非クリティカルな部分だけを個別にSuspenseで切り出すのがベストプラクティス。

- **ポイント3:** Server Actionsとストリーミングの組み合わせで、フォーム送信後の楽観的UI更新（`useOptimistic`）が標準パターンとして定着。問い合わせフォームや内見予約フローなど多段階フォームでUX改善効果が大きい。

- **ポイント4:** キャッシュ戦略がファイル単位（`'use cache'`ディレクティブ）で明示的に制御できるようになり、RSCのキャッシュ無効化バグが減っている。引き継ぎ物件情報のように更新頻度が異なるデータ（物件情報は低頻度、空室状況は高頻度）を同一ページで扱う際に有効。

- **ポイント5:** エッジランタイムでのRSCストリーミングが一般化し、グローバル配信時のレイテンシが大幅改善。ただしBun/Node.js依存のライブラリ（PDF生成など）はエッジ非対応のケースが多く、処理をServer Actions経由でNode runtimeに委譲する設計が必要になる点は要注意。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはフルスタックTypeScriptモノレポで型安全性のオーバーヘッドゼロを実現し、スキーマ定義とコード生成を排除できるため、2026年も社内ツールやスタートアップのMVP開発で採用が加速している。sumitsugiのようなNext.js App Router構成では特に恩恵が大きい。
- **ポイント2:** GraphQLは依然としてモバイル/マルチクライアント環境でのオーバーフェッチ削減に強いが、N+1問題やキャッシュ戦略の複雑さから、単一フロントエンド構成のプロダクトではtRPCやREST+OpenAPIに戻る「揺り戻し」が見られる。
- **ポイント3:** RESTはOpenAPI 3.1 + Zodスキーマ連携でAI駆動の自動ドキュメント生成・クライアントSDK生成が標準化され、依然として外部公開API（決済連携、パートナーAPI等）の第一選択肢であり続けている。
- **ポイント4:** 2026年のトレンドは「API層でのAI Agent対応」—LLMエージェントが直接呼び出せるツール定義（MCP等）とAPIスキーマの統合が進み、API設計時にAgent-friendlyな入出力設計（冪等性・明確なエラーメッセージ）が新たな要件になっている。
- **ポイント5:** エッジランタイム（Vercel Edge, Cloudflare Workers）前提の設計が主流化し、API Routeのコールドスタート最小化のためtRPCのバッチング機能やストリーミングレスポンス（Server Actions含む）の活用が重視されている。

### 4. serverless edge computing 2026

- **エッジでのAI推論統合:** Cloudflare Workers AIやVercel Edge Functionsなど、エッジランタイム上で軽量LLM推論を直接実行する構成が一般化。レイテンシ要件の厳しいパーソナライゼーションや検索補助機能は、中央サーバーを経由せずエッジで処理するのが2026年の標準パターンになっている。

- **WASMベースの実行環境がデフォルト化:** V8 isolateやWasmtimeを使ったコールドスタート数ms級の実行環境が主流になり、Node.js互換レイヤーよりWeb標準API（Fetch, Streams）に寄せた実装が推奨される。既存Node依存ライブラリをエッジ向けに書き換えるコストを事前に見積もる必要がある。

- **データレイヤーのエッジ分散:** Turso、PlanetScale、D1などのSQLiteベース分散DBがエッジのそばにレプリカを置く構成を実用化し、「計算はエッジ、データは中央」という旧来の制約が崩れている。グローバル展開するアプリでは読み取り遅延を大幅に削減できるが、書き込み一貫性の設計（eventual consistencyの許容範囲）を早期に決める必要がある。

- **コスト構造の変化（従量課金の細分化）:** CPU時間課金からリクエスト数・メモリ・実行時間の複合課金へ移行が進み、小規模トラフィックのサービスは従来のサーバーレスより大幅に安くなる一方、長時間実行ジョブは依然コンテナ/VMの方が有利。sumitsugiのような低〜中トラフィックのMVPフェーズではエッジ移行のROIが高い。

- **観測性（Observability）のギャップが残る課題:** エッジ実行環境は分散度が高く、従来のAPMツールでは分散トレーシングが追いづらい。本番導入前にOpenTelemetry対応状況を確認し、エッジ特有のデバッグ体制（構造化ログの集約先など）を先に整備しておくべき。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）のデフォルト化:** 2026年現在、FIDO2/WebAuthnベースのパスキーがパスワードの代替として標準化が進んでおり、フィッシング耐性とUX向上を両立できる。本サービスでも引っ越し業者・前の住人双方の認証にパスキー対応を優先的に検討すべき。

- **トークンのライフサイクル管理の厳格化:** JWTなどのアクセストークンは短寿命化し、リフレッシュトークンのローテーション（使い捨て＋再利用検知）を徹底することで、トークン漏洩時の被害範囲を最小化できる。Next.jsのServer Actions/Middlewareでの実装時は`httpOnly`・`secure`・`sameSite=strict`のCookie設定を必須とする。

- **デバイスバインディングとリスクベース認証:** IPアドレスや端末フィンガープリントの変化を検知してステップアップ認証（MFA再要求）を発動する仕組みが主流化。不動産取引のような高額・高リスク操作（内見予約確定、契約書類アップロード等）には追加認証を挟むべき。

- **サプライチェーン経由の認証基盤侵害対策:** OAuthプロバイダーやSDKの依存関係を通じた侵害事例が増加傾向にあり、`package.json`の依存脆弱性監視（Dependabot/Snyk）とOAuthクライアントシークレットのローテーション運用を定例化する必要がある。

- **ゼロトラスト前提のセッション検証:** ログイン時だけでなく、各APIリクエストごとにセッションの有効性・権限スコープを再検証する設計が推奨される。`src/contexts/auth-context.tsx`のような認証コンテキストは、クライアント側の状態を信頼せずサーバー側で都度検証するパターンを徹底すべき。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はPostgreSQLのネイティブ機能（RLS, pgvector, pg_trgm等）との統合が強化され、SupabaseのEdge FunctionsやRealtimeと組み合わせることでBaaS層とORM層の境界がより薄くなっている。弊社のproperty/listing系テーブルでもRLSベースの権限制御への移行を検討する価値がある。

- **ポイント2:** SupabaseのConnection Pooling（PgBouncer経由）とPrismaのPrisma Accelerate/Data Proxyを併用するのがサーバーレス環境（Vercel等）でのコネクション枯渇対策の定番パターンになっている。Next.js 16のServer Actionsを多用する構成では特に重要。

- **ポイント3:** Prisma SchemaからSupabaseのRLSポリシーを自動生成・同期するツールチェーンが成熟してきており、`'draft' | 'public'`のようなステータス管理をDB層のRLSで担保することで、アプリ層のバグによる非公開物件の漏洩リスクを構造的に減らせる。

- **ポイント4:** マイグレーション管理において、Prisma MigrateとSupabase CLIのマイグレーション機構が競合しやすいため、どちらを単一のソース・オブ・トゥルースにするか（通常はPrisma Migrate側に統一）を早期に決めておくことがチーム規模が大きくなる前の必須事項。

- **ポイント5:** pgvectorを使ったセマンティック検索（物件検索の自然言語クエリ対応など）がPrisma経由でも型安全に扱えるようになってきており、将来的な「次の住人」へのレコメンド機能拡張の技術的基盤として検討余地がある。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC（Garbage Collection提案）とComponent Modelの標準化が進み、RustのWasmバイナリサイズとロード時間が大幅改善。マイクロフロントエンドや軽量エッジ処理への採用が加速している。
- **ポイント2:** `wasm32-wasip2`ターゲットの成熟により、サーバーサイドでもWasmランタイム（Wasmtime、Spin等）上でRustバイナリをネイティブ並みの速度で実行可能になり、コンテナより軽量なサンドボックス実行基盤として採用が増加。
- **ポイント3:** SIMD対応とマルチスレッド（Wasm Threads proposal）がブラウザ主要実装で安定し、画像処理・PDF生成などCPU集約的な処理をクライアント側Rust/Wasmにオフロードするケースが増え、サーバー負荷削減につながる。
- **ポイント4:** `wasm-bindgen`/`wasm-pack`のビルドパイプラインが洗練され、ツリーシェイキングとAOT最適化でJS⇄Wasm間のFFIオーバーヘッドが縮小。パフォーマンスクリティカルな一部機能のみRust化する「部分移行」戦略が実用的な選択肢になっている。
- **ポイント5:** 本プロジェクト（Next.js/TypeScript中心）への適用は慎重に判断すべき — PDF生成や画像処理などの重い処理がボトルネックになった場合の将来オプションとして把握しておく価値はあるが、現フェーズ（ベータローンチ準備）では導入コストに対するリターンは低く、優先度は低い。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 15以降で導入されたPPRが16系で成熟し、静的シェルと動的コンテンツを1つのレスポンスに統合できるため、TTFBを落とさずに個人化されたUIを配信できる。`Suspense`境界の粒度設計がパフォーマンスチューニングの中心課題になっている。

- **Server Actions の本番運用パターン確立:** フォーム送信やミューテーションをAPI Routeなしで書けるようになったが、入力検証(Zod)・認可チェック・レート制限をAction内に必ず組み込む運用が定石化。クライアントから直接呼ばれる前提でセキュリティ境界として扱う必要がある。

- **キャッシュ戦略の明示化:** `fetch`のデフォルトキャッシュ挙動が過去バージョンで変更された経緯もあり、`cache: 'force-cache'`や`revalidateTag`/`revalidatePath`を明示的に指定する設計が必須になっている。暗黙のキャッシュに依存するとステールデータ事故を招く。

- **Server/Client Components の境界最適化:** "use client"境界をリーフコンポーネントまで押し下げ、JSバンドルを最小化するパターンが定着。状態管理ライブラリもRSC対応版(Zustand, Jotaiのサーバー対応)への移行が進んでいる。

- **Edge RuntimeとNode Runtimeの選択的使い分け:** 認証ミドルウェアや軽量API処理はEdge Runtimeで低レイテンシ化、DB接続やファイルI/Oが必要な処理はNode Runtimeに残すハイブリッド構成が実用パターンとして普及。すべてをEdge化しようとすると互換性問題で手戻りが発生しやすい。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1（Node.js互換性の拡大）:** 2026年時点でEdge Runtimeの制約が緩和され、一部のNode.js API（fs一部、crypto拡張）がサポートされつつあるため、従来Edgeで動かせなかった処理も移行可能になっている。sumitsugiのような物件検索・認証処理では、まずどの処理がEdge互換か再評価する価値がある。
- **ポイント2（コールドスタート最小化）:** Edge FunctionsはV8 isolateベースでコールドスタートがほぼゼロに近く、物件一覧APIや認証ミドルウェア（auth-context.tsx連携箇所）など低レイテンシが求められる箇所に優先的に適用すべき。
- **ポイント3（リージョン最適化とデータ局所性）:** Vercelのスマートルーティングにより、ユーザーに最も近いリージョンで実行されるが、DB（Supabase等）が単一リージョンの場合はEdge→DBのレイテンシが逆にボトルネック化することがあるため、Edge化はDB接続方式（Fluid Compute/Connection Pooling）とセットで検討する必要がある。
- **ポイント4（Fluid Computeとの統合）:** VercelのFluid Compute機能がEdgeとServerless Functionsの境界を曖昧にしており、同時実行の最適化（インスタンス共有）によりコスト削減と低レイテンシを両立できる。MVP後のスケール期には課金体系の見直しポイントになる。
- **ポイント5（ミドルウェアサイズ制限への注意）:** Next.js 16のMiddlewareはEdge Runtime上で動くため、バンドルサイズ制限（1-4MB程度）に注意が必要。認証チェックなど`src/contexts/auth-context.tsx`に依存する処理をMiddlewareに集約する場合、依存ライブラリの肥大化に気をつけるべき。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** `satisfies`演算子とZodスキーマの組み合わせが標準化しつつあり、ランタイム検証と型推論を同時に満たせるため、APIレスポンスやフォーム入力など境界部分での型安全性が大幅に向上している。
- **ポイント2:** `const`型パラメータやTemplate Literal Typesの活用が進み、文字列ベースのルーティングやイベント名の型チェックがコンパイル時に完結するケースが増えている。
- **ポイント3:** tRPCやHonoのようなエンドツーエンド型推論フレームワークが主流化し、フロントエンド/バックエンド間の型をコード生成なしで共有する設計が増えている。
- **ポイント4:** Branded Types（Nominal Typing）を使って`UserId`と`string`を型レベルで区別する手法が一般化し、プリミティブ型の取り違えによるバグを防ぐパターンが定着してきている。
- **ポイント5:** `unknown`優先・`any`禁止のLint設定（`@typescript-eslint/no-explicit-any`等）をCIで強制するチームが増え、型安全性の「抜け道」を仕組みで塞ぐ運用が重視されている。
