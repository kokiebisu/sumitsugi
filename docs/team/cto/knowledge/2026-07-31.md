# CTO Knowledge - 2026-07-31

## Daily Update (2026-07-31)

### 1. Next.js performance optimization 2026

- **React Server Components + Partial Prerendering (PPR) の標準化:** Next.js 16ではPPRが安定版となり、静的シェルを即座に配信しつつ動的部分をストリーミングすることで、TTFBとLCPを大幅に改善できる。ページ単位ではなくコンポーネント単位でキャッシュ戦略を選べる点が実務上のインパクトが大きい。

- **Turbopackのビルド/開発高速化:** `bun run build`でのTurbopack採用によりコールドビルドが大幅短縮され、CIパイプラインの待ち時間が削減される。開発サーバーのHMRも高速化され、開発体験（DX）とデプロイ頻度の両方に効く。

- **`use cache`ディレクティブによる粒度の細かいキャッシュ制御:** データフェッチ単位で明示的にキャッシュ境界を宣言できるようになり、従来のfetchキャッシュの暗黙的な挙動に起因するバグ（stale dataや過剰再検証）を減らせる。物件一覧・詳細ページのようなSSGとISRの混在パターンに特に有効。

- **画像・フォント最適化のエッジ処理:** `next/image`のエッジランタイム最適化とフォントのセルフホスティングが標準化され、CLS（Cumulative Layout Shift）とLCPの改善が容易になった。物件写真を多用するsumitsugiのようなUIでは特に効果が大きい。

- **Server Actionsのパフォーマンス計測とオブザーバビリティ:** Server Actions呼び出しのレイテンシがOpenTelemetry統合で可視化しやすくなり、フォーム送信・お問い合わせ等のユーザー操作のボトルネックを特定しやすくなった。引き継ぎフローのような多段階フォームでのUX改善に直結する。

### 2. React Server Components streaming 2026

- **段階的ハイドレーションとの併用が主流化:** RSC streaming単体ではなくSelective Hydration（React 19以降）と組み合わせることで、上部の重要コンテンツ（LCP要素）を即座にインタラクティブにしつつ、下部のコンポーネントは後から遅延ハイドレーションする設計が標準パターンになっている。Next.js 16では`loading.tsx`とSuspense境界の粒度設計がパフォーマンスチューニングの主戦場。

- **Partial Prerendering (PPR) の実用段階入り:** 静的シェルを即座に配信し、動的部分だけをストリームで後追いする方式がNext.jsで安定運用フェーズに入っており、CDNキャッシュと動的パーソナライゼーションの両立が可能になった。sumitsugiの物件一覧のような「静的な物件カード＋動的な空室状況」構成に相性が良い。

- **Server Actions × streamingのエラーハンドリングが課題:** フォーム送信やRSC内の非同期処理がストリーム中に失敗した場合のエラーバウンダリ設計がまだ発展途上で、`error.tsx`の粒度とtoast通知の組み合わせなど、UXパターンが各社バラバラ。引っ越し費用の申込フローのような多段階フォームでは、部分的失敗のリトライ設計を明示的に組み込む必要がある。

- **Waterfallの見えにくさが依然リスク:** RSCはネットワークタブ上でリクエストが見えないため、意図しないserver-to-serverのウォーターフォールが本番で初めて発覚するケースが多い。`React DevTools`のTimeline機能やObservabilityツール（Vercel Speed Insights等）でのRSCペイロード計測を、CI段階のパフォーマンス回帰テストに組み込むのが今年のベストプラクティス。

- **Bunとのビルド統合が加速:** BunのネイティブなSSRサポート改善により、RSCのバンドル/トランスパイル速度が向上し、開発体験（HMR含む）がストリーミングSSRでもボトルネックになりにくくなっている。ただし本番ビルドの安定性検証は引き続き必須（`bun run build`でのチェックは変わらず重要）。

### 3. API design REST GraphQL tRPC 2026

**ポイント1:** GraphQLは2026年もフロントエンド主導の複雑なデータ取得要件で強いが、over-fetchingコスト対策のPersisted Queries標準化が進み、任意クエリ実行によるDoSリスク軽減が主流になっている。

**ポイント2:** tRPCはNext.js App Router×TypeScriptモノレポ構成との相性が良く、スキーマ不要で型がエンドツーエンド保証されるため、社内向けAPIやフロント/バックエンド同一リポジトリの小〜中規模SaaSで採用が拡大している。

**ポイント3:** REST APIはOpenAPI 3.1+JSON Schemaベースのコード生成（型・クライアント自動生成）が成熟し、外部公開APIやマルチクライアント（モバイル・サードパーティ連携）が絡む場面では依然デファクトスタンダード。

**ポイント4:** 単一技術への統一ではなく「外部公開はREST、内部BFFはtRPC、集約が必要な画面はGraphQL」といったハイブリッド構成が2026年の実務的トレンドで、sumitsugiのようなNext.js App Router構成なら内部はtRPCまたはServer Actions、外部連携ポイントのみRESTで切り出すのが現実的。

**ポイント5:** キャッシュ戦略（tRPC×React Query、REST×HTTPキャッシュヘッダ、GraphQL×正規化キャッシュ）はAPI選定と不可分になっており、パフォーマンス要件から逆算してAPI方式を決めるべきというのが最新の設計思想。

### 4. serverless edge computing 2026

**CTO視点:サーバーレス・エッジコンピューティング2026のトレンド**

- **ポイント1(コールドスタート撲滅):** V8アイソレートベースのランタイム(Cloudflare Workers, Vercel Edge等)が主流化し、コールドスタートが数ミリ秒レベルまで短縮。sumitsugiのような予約・決済フローでもレイテンシSLAを気にせずエッジ配置できる時代に入っている。
- **ポイント2(エッジでのDB書き込み):** これまで「エッジは読み取り専用」が定石だったが、分散SQLite(Turso/D1)やリージョン間レプリケーション付きKVの成熟で書き込みもエッジで完結可能に。物件ステータス更新や引き継ぎフローのような低頻度書き込みは十分実用レベル。
- **ポイント3(フレームワーク統合の深化):** Next.js自体がエッジランタイムをファーストクラス扱いし、Middlewareだけでなく一部のRoute Handlerもエッジ実行が標準選択肢に。App Router構成のまま追加インフラなしで地理分散が可能。
- **ポイント4(コスト構造の逆転):** 常時起動サーバーより従量課金エッジ関数の方がMVP〜ローンチ初期のような低トラフィック期は圧倒的に安価。ベータローンチ準備中の今のフェーズにはコスト面で合理的な選択肢。
- **ポイント5(運用の落とし穴):** Node.js API非対応(fsアクセス不可、一部npmパッケージ不可)や観測性(ログ・トレース)がリージョン分散で複雑化する点は依然課題。認証・決済など複雑なロジックは通常のサーバーレス関数に残し、エッジは静的配信やリダイレクト・A/Bテストなど軽量処理に限定するのが無難。

### 5. authentication security best practices 2026

**認証セキュリティ 2026年トレンド (CTO視点)**

- **パスキー/FIDO2への完全移行:** パスワードレス認証がデファクトスタンダード化しており、フィッシング耐性の高いパスキーをプライマリ認証手段とし、パスワードは後方互換のフォールバックに留めるべき。実装コストよりも認証突破によるインシデント対応コストの方が高くつく。
- **セッション管理の厳格化:** JWTの長期発行を避け、短命アクセストークン＋リフレッシュトークンのローテーション、デバイスバインディングを組み合わせることで、トークン漏洩時の被害範囲を最小化する。
- **多層防御としてのリスクベース認証:** IPレピュテーション・デバイスフィンガープリント・行動パターンを組み合わせたアダプティブMFAを導入し、通常時はUXを損なわず、異常時のみ追加認証を要求する設計が主流。
- **Zero Trust前提のセッション検証:** ログイン時点だけでなく、各リクエストで権限・セッション有効性を再検証する設計（特に決済・個人情報アクセス等の高リスク操作時）が、住人情報を扱うsumitsugiのような個人情報プラットフォームでは必須。
- **Secrets管理の自動ローテーション:** APIキーやOAuthトークンをコードや`.env`に固定せず、Vault等でのシークレット管理＋定期ローテーションを前提にすることで、漏洩時の影響時間を短縮する。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はTypedSQLやリレーショナルクエリの最適化が進み、Supabaseの接続プーラー（Supavisor）と組み合わせることでサーバーレス環境でのコネクション枯渇問題が大幅に緩和されている。

- **ポイント2:** SupabaseのRow Level Security（RLS）とPrisma ORMを併用する構成が主流化しており、認証・認可ロジックをアプリケーション層とDB層の二重で担保するパターンが標準化しつつある。

- **ポイント3:** Prisma AccelerateやSupabaseのEdge Functionsを使ったキャッシュ層の導入で、住人情報や物件データのような読み取り比率が高いワークロードのレイテンシを大幅に改善できる。

- **ポイント4:** マイグレーション管理はPrisma Migrateで一元化しつつ、SupabaseのDeclarative Schema機能で差分レビューを行う運用が定着しており、本番DBへの破壊的変更のリスクを下げられる。

- **ポイント5:** 個人情報（住所・引き継ぎ履歴など）を扱う本プロジェクトの特性上、SupabaseのPoint-in-Time Recoveryとカラムレベル暗号化を組み合わせた設計が、法務確認フェーズを見据えた実装として重要になる。

### 7. WebAssembly Rust performance 2026

- **Component Model の実用化:** WASI Preview 2/Component Model が主要ランタイム（Wasmtime, jco）で安定し、Rustクレートをwasm componentとして言語横断で再利用できるようになった。マイクロサービスの一部をRust+Wasmに置き換える際、FFIコストを気にせず設計できる点が実務上のメリット。

- **SIMD・Memory64の普及:** wasm SIMDがブラウザ・エッジランタイム双方で標準化し、画像処理や暗号化などCPU集約タスクでネイティブの70-90%程度の性能が出るケースが増加。Memory64により4GB制限を超える大規模データ処理も現実的になった。

- **エッジ実行環境との親和性:** Cloudflare Workers/Fastly Compute等でRust+Wasmのコールドスタートがミリ秒未満まで最適化され、サーバーレスでのレイテンシ要件が厳しいAPI（例: 物件検索の高速フィルタリング）に適している。

- **ツールチェーンの成熟:** `wasm-pack`/`cargo-component` のビルド速度・DXが向上し、Next.js等のJSエコシステムへの統合コストが下がった。ただしバンドルサイズとJS↔Wasm境界でのシリアライズコストは依然としてボトルネックになりやすく、頻繁に呼び出す小粒度の関数には向かない。

- **実務判断:** sumitsugiのような通常のWebアプリでは現時点でWasm導入の緊急性は低いが、将来的にPDF生成・画像処理・全文検索など計算負荷の高い機能を追加する際の選択肢として検討価値あり。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16ではPPRが安定版となり、静的シェルと動的コンテンツを1ページ内で組み合わせられる。物件一覧ページで「基本レイアウトは静的配信、在庫状況だけ動的」といった構成にすればTTFBを大幅短縮できる。

- **Server Actions中心のミューテーション設計:** フォーム送信やお問い合わせ機能はAPI Routesを新設せずServer Actionsで完結させるのが主流。`src/app/listing/`配下のような多段階フロー（引き継ぎ申込等）でもuseActionState + Server Actionsで状態管理をシンプルに保てる。

- **Cache Componentsとexplicit caching:** `use cache`ディレクティブによる明示的キャッシュ制御がデフォルト化しつつある。物件データのようにDBアクセスを伴うコンポーネントは、キャッシュ境界を明示しないと意図しない再検証コストが発生するため、`cacheLife`/`cacheTag`での粒度管理が重要。

- **Turbopackのビルド標準化:** Turbopackがビルドでも既定になり、`bun run build`の高速化が期待できる一方、Webpack依存プラグインの互換性は都度確認が必要。CIのビルド時間短縮に直結するため導入価値は高い。

- **Route Groups + Parallel Routesによるレイアウト分離の定着:** ダッシュボード系UI（前の住人/次の住人で異なるビュー)では`@modal`のようなParallel Routesとintercepting routesを組み合わせ、モーダル遷移をURL共有可能な形で実装するパターンが標準化している。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Functionsのコールドスタートはv8 isolateベースでほぼゼロに近づいており、Node.js runtimeとの機能差も縮小しているため、レイテンシ要求が厳しいAPI（物件検索・地図表示など）は積極的にEdgeへ寄せる価値がある。ただしファイルシステムアクセスや一部npmパッケージ非対応は依然制約として残る。

- **ポイント2:** Vercelの`waitUntil`やStreaming SSRとの組み合わせで、レスポンスを即座に返しつつバックグラウンドでログ記録・キャッシュ更新を行うパターンが定着してきており、UI応答速度とデータ整合性を両立できる。

- **ポイント3:** Edge Config / ISR(Incremental Static Regeneration)との連携が強化され、物件ステータス（`draft`/`public`）のような頻繁に変わらないがリアルタイム性が欲しいデータをEdge Configにキャッシュすることで、DBアクセスを大幅削減できる。

- **ポイント4:** リージョン選択（Edge Middlewareのregion pinning）がコスト最適化の鍵になっており、日本向けサービスであれば`hnd1`（東京）に固定することでレイテンシとコストの両方を改善できる。全世界配信を狙わない限りマルチリージョンは過剰投資になりやすい。

- **ポイント5:** Observability面ではVercelのOTel(OpenTelemetry)統合が標準化され、Edge Functionsのトレースをそのままダッシュボードで追える。障害調査コストが下がるため、認証・決済まわりなどセキュリティクリティカルな処理をEdgeに置く場合は必ずOTel計装を前提にすべき。

### 10. TypeScript type safety patterns 2026

- **ポイント1（`satisfies`演算子の定着）:** TypeScript 4.9で導入された`satisfies`は2026年時点でconst assertionと組み合わせるパターンが標準化し、型推論を保ちながら型チェックを行える。設定オブジェクトやルーティング定義など「リテラル型を保持しつつ制約を検証したい」箇所で`as`より優先すべき。

- **ポイント2（Zodスキーマからの型導出が主流に）:** `z.infer<typeof schema>`でランタイムバリデーションと型定義を単一ソースにする手法が標準化。API境界・フォーム入力で型とバリデーションの二重管理を避けられ、`.claude/rules/standards.md`のZod必須ルールとも合致する。

- **ポイント3（テンプレートリテラル型による文字列安全性）:** ルートパスやCSSクラス名、i18nキーなどをテンプレートリテラル型で制約し、タイポをコンパイル時に検出するパターンが浸透。`src/app/`のルート定義や`site-config.ts`のような設定に有効。

- **ポイント4（`strict`+`noUncheckedIndexedAccess`の標準化）:** 配列・オブジェクトアクセス時の`undefined`混入をコンパイラに検出させる設定が新規プロジェクトのデフォルトになりつつある。`data.ts`のようなデータアクセス層でのnullチェック漏れバグを未然に防げる。

- **ポイント5（Branded Typesによるドメイン境界の強制）:** `type UserId = string & { __brand: 'UserId' }`のようなブランド型で、意味的に異なる文字列型（物件IDとユーザーIDなど）の取り違えを型レベルで防ぐパターンが実務で定着。`draft`/`public`のようなユニオン型のステータス管理と組み合わせると誤代入を防げる。
