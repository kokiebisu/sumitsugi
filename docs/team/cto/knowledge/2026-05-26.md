# CTO Knowledge - 2026-05-26

## Daily Update (2026-05-26)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 15/16でPPRが安定化し、静的シェルと動的コンテンツを同一ページで組み合わせ可能に。TTFB短縮と動的データの両立が実現できるため、従来のSSG/SSR二択から解放される。

- **React Server Components によるバンドルサイズ削減:** RSCでサーバー側に処理を移すことでクライアントJSを50-70%削減できるケースも。コンポーネント設計時に「これはクライアントで必要か」を問い直す習慣が重要。

- **Turbopack の採用加速:** Webpackから移行することでHMRが最大10倍高速化。大規模プロジェクトでの開発体験改善が顕著で、CI/CDのビルド時間短縮にも直結する。

- **Edge Runtime + Streaming の組み合わせ:** `Suspense` + Server Actionsによるストリーミングレスポンスと、Vercel/Cloudflare EdgeでのDB接近（Neon/PlanetScale Edge）を組み合わせることでp99レイテンシが劇的に改善。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15で導入された`use cache`でコンポーネント・関数レベルのキャッシュ制御が可能に。`revalidateTag`との組み合わせで、ページ全体ではなく変更部分だけを無効化できるため、キャッシュヒット率が大幅向上する。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Prerendering (PPR) の本格普及:** Next.js 15以降でPPRが安定化し、静的シェルを即座に配信しつつ動的コンポーネントをストリームするパターンが標準化。TTFBとLCPの両立が実現可能になった。

- **ポイント2: Suspense境界の設計がアーキテクチャの核心に:** RSCストリーミングの恩恵を最大化するには、`<Suspense>`の粒度設計が重要。粗すぎるとウォーターフォールが残り、細かすぎるとレイアウトシフトが増える——コンポーネント境界のレビュープロセスに組み込む必要がある。

- **ポイント3: Server Actions × ストリーミングの組み合わせ成熟:** Server ActionsがFormの送信後に`useOptimistic`と組み合わさり、楽観的UIとサーバーレスポンスのストリームが自然に統合できるようになった。クライアント状態管理ライブラリへの依存を大幅に削減できる。

- **ポイント4: エッジランタイムとの相性問題が依然残存:** CloudflareやVercel Edgeでのストリーミングは`ReadableStream`実装の差異により挙動が異なるケースがある。本番導入前に対象プラットフォームでの動作検証を必須とすること。

- **ポイント5: キャッシュ戦略の再設計が必須:** `fetch`のキャッシュセマンティクスがNext.js 15で変更（デフォルトno-store）。RSCストリーミング環境では`unstable_cache`や`revalidateTag`を明示的に設計しないと、意図せずサーバー負荷が増大するリスクがある。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭:** Next.js + TypeScript スタックでは tRPC が実質標準になりつつある。型安全性をエンドツーエンドで保証しコード生成が不要なため、スモールチームでの開発速度が大幅に向上する。

- **GraphQLの適用範囲の明確化:** GraphQL は「複数クライアント（Web/Mobile/外部）が異なるデータ形状を必要とする場合」に限定されるべきで、内部API全般に使うのはオーバーエンジニアリング。Federationによるマイクロサービス統合用途が主戦場になっている。

- **REST は死なず、OpenAPI 3.1 で進化:** REST + OpenAPI 3.1（JSONスキーマ完全対応）の組み合わせが外部公開APIのデファクトであり続ける。`zod-to-openapi` などのツールでコードファーストにスキーマ生成する流れが定着。

- **エッジ・ストリーミング対応が設計要件に:** Server-Sent Events や HTTP/3 ストリーミングへの対応が API 設計段階から必要になっており、REST でも GraphQL Subscription でも「接続維持コスト」を意識したアーキテクチャ選定が求められる。

- **型安全性がAPI選定の第一基準:** 2026年時点では「型が合わない API は採用しない」という判断がチームレベルで定着。tRPC か OpenAPI 自動生成クライアント（`orval`, `hey-api`）の二択で、手書きの API クライアントはレガシー扱いになっている。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジの標準ランタイムへ:** Cloudflare Workers・Fastly Compute@Edgeを中心に、Wasmがコンテナに代わるポータブルなエッジ実行環境として定着。コールドスタートが数ms以下になり、Node.jsランタイム依存から解放される。

- **エッジでのAI推論が実用段階に:** 小型LLM（1〜3Bパラメータ）やembeddingモデルをエッジで直接実行するケースが増加。レイテンシ削減とデータ主権（GDPRなど）の両立が主な動機で、Vercel AI SDKやCloudflare AI Gatewayがその基盤を提供。

- **ステートフルエッジの台頭（Durable Objects / Cloudflare D1）:** 従来「ステートレス」が前提だったエッジが、軽量SQLiteやアクターモデルで状態を持てるように進化。リアルタイムコラボレーション機能やセッション管理をオリジンサーバーなしで実装可能になった。

- **エッジネイティブなオブザーバビリティが必須に:** 分散した数百拠点のエッジ実行を追跡するため、OpenTelemetryのエッジ対応とストリーミングログの整備が急務。デバッグコストが集中型より高くなるため、設計段階からのトレーシング組み込みが開発ベストプラクティスになっている。

- **コスト構造の再評価:** リクエスト数課金モデルでトラフィックが急増した際の請求額が予測困難になるケースが増加。2026年時点では「エッジは常に安い」という前提を捨て、オリジンとエッジのコスト比較を定量的にベンチマークしてから採用判断することが重要。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準化:** FIDO2/WebAuthnベースのパスキーが主流となり、パスワードレス認証が現実的な選択肢に。フィッシング耐性が高く、ユーザー体験も向上するため、新規実装ではパスキーファーストを検討すべき。

- **トークン管理の厳格化:** JWTの有効期限を短く（15分以内）設定し、リフレッシュトークンのローテーションを必須化。セッションハイジャックリスクを最小化するため、トークンをhttpOnly Cookieに格納しlocalStorage使用を避ける。

- **デバイスバインディングとコンテキスト認証:** IPアドレス・デバイスフィンガープリント・行動パターンを組み合わせたリスクベース認証が進化。異常検知時のみ追加認証を要求するアダプティブMFAが標準的なアプローチになっている。

- **サプライチェーン攻撃への対策:** OAuth/OIDCプロバイダーへの依存リスクが顕在化し、サードパーティIDPのインシデント時のフォールバック戦略が必須。依存ライブラリの定期的なSBOM（ソフトウェア部品表）監査を自動化する。

- **ゼロトラスト原則の徹底:** 「ネットワーク内＝安全」という前提を完全廃棄し、全リクエストを継続的に検証。セッション中の再認証（継続認証）や最小権限原則の動的適用が、内部脅威対策として重要度を増している。

### 6. database architecture Prisma Supabase 2026

- **Prisma + Supabase の統合成熟:** 2026年時点でPrisma v6とSupabaseの組み合わせは実運用レベルで安定しており、`prisma migrate deploy`によるCI/CDパイプライン統合がデファクトスタンダードになっている。Row Level Security（RLS）とPrismaのミドルウェア層を組み合わせたマルチテナント設計が主流。

- **Supabase Edge Functionsとの連携パターン:** Deno Deployベースのエッジ関数でPrisma Accelerate（接続プーリング）を活用することで、サーバーレス環境でのコールドスタート問題とDB接続数枯渇を同時に解決できる。特にNext.js App RouterのServer Actionsとの相性が良い。

- **リアルタイム + 型安全の両立:** Supabase Realtimeのchannel APIとPrismaの型生成を組み合わせることで、フロントエンドまでエンドツーエンドの型安全なリアルタイムデータフローが実現できる。ただしPrismaはRealtimeを直接サポートしないため、Supabase JSクライアントとの役割分担設計が必要。

- **pgvector活用による組み込みAI検索:** SupabaseのpgvectorサポートとPrismaの`Unsupported("vector")`型を使ったベクトル検索が、RAGアーキテクチャの標準パターンになっている。Prismaからの型サポートは限定的なので、生SQLクエリと併用する実装が現実的。

- **マイグレーション管理のリスク:** Supabase CLIとPrisma Migrateが同じスキーマを操作するため、RLSポリシーやトリガーが`prisma migrate`で上書きされるリスクがある。`prisma migrate diff`でのドリフト検出とGit管理されたSupabase seed SQLの組み合わせによる二重管理が、本番環境では必須。

### 7. WebAssembly Rust performance 2026

- **ポイント1: WASIp2（Component Model）の本格普及** WebAssembly Component Modelが2025年末に安定化し、RustのWASIp2サポートが実用レベルに達した。サーバーレス・エッジ環境でのポータブルなRustバイナリ配布が現実的な選択肢になっている。

- **ポイント2: スレッド・SIMD命令の実用化** WebAssembly Threadsと128-bit SIMD（`wasm-bindgen`＋`rayon`相当）が主要ブラウザ・ランタイムで安定稼働。CPUバウンドな画像処理・暗号処理でネイティブの70〜90%程度のスループットが計測される例が増えている。

- **ポイント3: バイナリサイズの最適化が成熟** `wasm-opt`（Binaryen）＋`wasm-pack`のビルドパイプラインに加え、Rustの`min-sized-rust`手法が標準化。`std`なしのno_std＋`panic=abort`構成で50KB以下の配布が容易になり、初期ロードのボトルネックが緩和されている。

- **ポイント4: GCとメモリ管理の境界が鍵** WasmGC提案の普及でJVM/Dartターゲットが増えたが、Rustは依然として線形メモリ＋手動管理が主流。GCオーバーヘッドがない分、長時間稼働ワークロードでのレイテンシ安定性はRust Wasmが優位を保っている。

- **ポイント5: エッジ・CDNランタイム（Fastly/Cloudflare Workers）との親和性** Cloudflare WorkersのV8 isolateからWasm-firstアーキテクチャへの移行が進み、Rustで書いたWasmモジュールをCDNエッジに直デプロイするパターンが増加。コールドスタートがほぼゼロで、Node.jsランタイムより低レイテンシなAPIエンドポイントを実現できる。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** App Router では RSC をデフォルトとし、`'use client'` はインタラクティブな末端コンポーネントに限定する。データフェッチは Server Component 内で直接 `await` するのがベストプラクティスで、不要な API ルートを排除できる。

- **Partial Prerendering (PPR) の活用:** 静的シェルと動的コンテンツを同一ページに共存させる PPR が実用段階に入り、`<Suspense>` の配置戦略がパフォーマンスの鍵になる。キャッシュ境界を意識してコンポーネントを分割することで TTFB を最小化できる。

- **Server Actions によるミューテーション統一:** フォーム送信やデータ更新は Server Actions に集約し、従来の `POST /api/*` ルートを廃止するのが主流。`useOptimistic` と組み合わせることで楽観的 UI の実装コストが大幅に下がる。

- **`use()` フックと Promise パターン:** React 19 の `use()` フックにより、Server Component から Client Component への Promise 受け渡しが標準化された。データをプロップで渡しつつ、クライアント側でサスペンド可能な設計が求められる。

- **`after()` API によるサイドエフェクト分離:** レスポンス送信後に実行するロギング・分析処理を `after()` に移すことで、ユーザーへのレスポンスをブロックせずに後処理を実行できる。本番環境でのオブザーバビリティ実装に不可欠なパターン。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Fluid Compute の活用:** Vercel が2025年に導入した Fluid Compute により、Edge Functions は短命なリクエスト処理だけでなく、長時間実行も可能になった。Cold Start を避けつつ、CPU コストを最大60%削減できるケースがある。

- **ポイント2: Edge Middleware の適切な分離:** 認証チェックや A/B テストのような「判断のみ」を Edge で行い、重いビジネスロジックは Node.js Runtime に残す設計が定石。Edge の 4MB コードサイズ制限と限定的 Node API を考慮した責務分離が重要。

- **ポイント3: ISR + Edge Cache の組み合わせ:** `next/cache` の `revalidateTag` を活用した On-Demand ISR と、Edge でのキャッシュヒット率最適化が TTFB 改善の核心。`Cache-Control: stale-while-revalidate` の適切な設定でユーザー体験を損なわずにオリジン負荷を下げられる。

- **ポイント4: Regional Edge の戦略的選択:** Vercel の Edge Network は全リージョンで実行されるが、データソース（Supabase, PlanetScale 等）との物理距離が律速になりがち。`preferredRegion` 指定でデータソースと同じリージョンに固定する方が、グローバル分散より速いケースが多い。

- **ポイント5: Bundle サイズの継続的監視:** `@vercel/size-limit` や `bundle-analyzer` を CI に組み込み、Edge Bundle の肥大化を防ぐ。特に `date-fns` や `lodash` のような汎用ライブラリは tree-shaking が効かない場合があり、軽量代替（`dayjs`, native API）への置き換えがパフォーマンスに直結する。

### 10. TypeScript type safety patterns 2026

- **Branded Types の実用化:** `type UserId = string & { readonly __brand: 'UserId' }` のようなBranded Typesが標準パターンとして定着し、ドメイン間の型混在バグをコンパイル時に検出できる。

- **Template Literal Types の高度活用:** APIルートやイベント名を `type Route = '/users' | '/users/${string}/profile'` で型付けすることで、文字列ベースのAPIをtype-safeに扱えるようになった。

- **satisfies 演算子の普及:** `const config = { ... } satisfies Config` により、型推論の恩恵を保ちながら型制約を適用できる。`as` キャストの多くをこれで置き換えるべき。

- **Zod + tRPC によるエンドツーエンド型安全:** バックエンドのZodスキーマからフロントエンドの型を自動導出するパターンが主流となり、APIの型ズレによるバグがほぼ排除できる。

- **NoUncheckedIndexedAccess の標準化:** `tsconfig.json` に `"noUncheckedIndexedAccess": true` を設定し、配列・オブジェクトアクセス時の暗黙的 `undefined` を明示的に扱うことが2026年のベストプラクティスとして定着しつつある。
