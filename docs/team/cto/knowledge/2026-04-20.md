# CTO Knowledge - 2026-04-20

## Daily Update (2026-04-20)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 15+で安定化したPPRにより、静的シェルと動的コンテンツを同一ページで混在させ、TTFBを大幅短縮できる。`experimental.ppr`から本番フラグへの移行タイミングを見極めるべき。

- **React Server Components キャッシュ戦略の精緻化:** `fetch`の`cache`オプションとRoute Segment Configを組み合わせ、データフェッチ粒度でキャッシュを制御する。`unstable_cache`と`revalidateTag`によるオンデマンド再検証が複雑なUIの生命線。

- **Turbopack移行による開発・ビルド高速化:** Next.js 15でTurbopackがデフォルト化に近づき、大規模プロジェクトでのHMRが5〜10倍速になるケースも報告されている。webpack設定への依存度を洗い出し、早期移行コストを評価すべき。

- **`use client`境界の最小化とバンドルサイズ削減:** クライアントコンポーネントの範囲を葉ノードに限定し、`next/dynamic`と`React.lazy`を戦略的に使い分けることで、初期JSペイロードを抑制できる。

- **Core Web Vitals対応としてのINP重視:** LCPに加え、Interaction to Next Paint（INP）がSEOランキング要因として定着。Reactのトランジション（`useTransition`）でUIブロッキングを防ぎ、特にフォーム・モーダル系コンポーネントで計測を徹底する。

### 2. React Server Components streaming 2026

- **Suspense境界の戦略的配置が鍵:** RSCストリーミングでは、Suspense境界をデータフェッチの粒度に合わせて細かく設定することで、TTFBを維持しながらLCPを大幅に改善できる。粗すぎる境界は滝型ローディングを招く。

- **Server Actionsとの統合が成熟:** 2026年時点でNext.js 15+のServer Actionsはストリーミングレスポンスに対応し、フォーム送信後のUI更新をクライアントバンドル増加なしに実現できる設計が主流になっている。

- **PPR（Partial Prerendering）が実用フェーズへ:** 静的シェルを即座に配信し、動的部分をストリームで差し込むPPRが本番対応となり、CDNキャッシュとストリーミングの両立という従来のトレードオフが解消されつつある。

- **Edge Runtimeでのストリーミング制約に注意:** Vercel EdgeやCloudflare Workersでは長時間ストリームのタイムアウト制限があり、重いデータ取得はNode.js Runtimeに留めるアーキテクチャ判断が依然として重要。

- **クライアントコンポーネントの「汚染境界」管理がコスト削減に直結:** `'use client'`の伝播を誤ると意図せずバンドルサイズが膨張する。React DevToolsのServer/Client境界ビジュアライザーを活用したコードレビューをCI工程に組み込むことを推奨。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの実用的優位性:** フルスタックTypeScriptプロジェクトではtRPCが事実上の標準となりつつあり、スキーマ定義なしでエンドツーエンドの型安全性を実現できるため、Next.js + Prisma構成での開発速度が大幅に向上する。

- **GraphQLの適用範囲の明確化:** GraphQLは複数クライアント（Web/Mobile/サードパーティ）が異なるデータ形状を必要とする場合に真価を発揮するが、単一フロントの内部APIには過剰設計になりがちで、tRPCやREST+OpenAPIの方が保守しやすい。

- **REST + OpenAPI 3.1の復権:** Zodベースのスキーマ生成（`zod-openapi`、`@hono/zod-openapi`）により、コードファーストでOpenAPI仕様を自動生成しクライアントSDKも自動生成できる。型安全性とinteroperabilityを両立できるため、外部公開APIには依然として最適解。

- **エッジランタイム対応が選定基準に:** Cloudflare Workers / Vercel Edge等の普及により、重量級GraphQLランタイム（Apollo Server）はコールドスタートで不利になっている。Honoベースの軽量REST or tRPCがエッジ環境での主流になりつつある。

- **プロトコル選定の原則:** 「外部公開→REST+OpenAPI」「マルチクライアント複雑クエリ→GraphQL」「フルスタックTS内部API→tRPC」という使い分けが2026年時点のベストプラクティス。一つのプロジェクトで混在させることも現実的な選択肢。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジのデファクトランタイムに:** V8/Node.jsより起動が速く、言語非依存なWasmはCloudflare Workers・Fastly Computeで主流となり、コールドスタート問題がほぼ解消された。

- **エッジでのAI推論が現実的なコストに:** 量子化モデル（INT4/INT8）とWasm SIMDの組み合わせで、GPUなしでもエッジノードでの軽量LLM推論が商用ワークロードに耐えるレベルに到達しつつある。

- **ステートフルエッジの台頭:** Cloudflare Durable ObjectsやVercel KVなどの分散ステートソリューションが成熟し、「エッジはステートレスのみ」という制約が実質的に崩れた。

- **エッジ・オリジン間のデータ整合性が設計の主戦場:** CAP定理のトレードオフがより身近になり、結果整合性 vs 強整合性の選択をアプリケーション層で明示的に設計する必要がある。

- **可観測性ギャップが深刻化:** 分散エッジ環境ではトレースIDの伝播やログ集約が複雑で、OpenTelemetryのエッジ対応とコスト最適化（サンプリング戦略）が運用上の最重要課題になっている。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）への移行加速:** パスワードレス認証がデファクトスタンダードになりつつあり、フィッシング耐性の高いパスキーを優先実装すべき。主要ブラウザ・OS対応が完了し、UXとセキュリティを両立できる。

- **ゼロトラスト＋継続的認証:** 初回ログインだけでなく、セッション中もリスクベースで再認証を要求するアダプティブ認証が標準化。行動バイオメトリクスや端末シグナルを組み合わせるのが現実解。

- **OAuth 2.1 / DPoP によるトークン漏洩対策:** Bearer tokenから送信者制約トークン（DPoP）への移行が進んでおり、トークン盗取による不正利用を構造的に防げる。新規実装では必須レベル。

- **AIを悪用した攻撃への対策:** LLMを使ったフィッシング・ディープフェイク音声によるSIMスワップ詐欺が急増中。SMS OTPは廃止方向で、TOTP or パスキーへの切り替えを急ぐべき。

- **サプライチェーンリスク（IDプロバイダー依存）:** Auth0・Cognitoなど外部IdPへの依存は便利だが、障害・仕様変更リスクがある。抽象化レイヤーを設けてプロバイダー切替可能な設計にしておくことが長期的に重要。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のEdge Runtime対応成熟:** Prisma AccelerateによるエッジでのDB接続プーリングが実用段階に入り、Next.js App RouterのServer ComponentsやEdge Functionsからのレイテンシが大幅改善。Vercel/Cloudflare Workers環境では標準構成になりつつある。

- **Supabase Realtime + RLSの組み合わせが主流化:** Row Level SecurityをDB層で担保しつつリアルタイム同期を行うパターンが成熟し、クライアント側の権限チェックコードを大幅削減できる。ただしRLSポリシーのパフォーマンステストは必須。

- **Prisma vs Drizzle の選択が重要な岐路:** 型安全性重視・チーム規模が大きければPrisma、バンドルサイズ・エッジ最適化重視ならDrizzle ORMが有力。2026時点ではDrizzleの採用が急増しており、新規プロジェクトでは要検討。

- **Supabase pgvector によるAI統合がデファクト化:** ベクトル検索をアプリDB内で完結させるアーキテクチャが定番になり、外部ベクトルDBを別途運用するコストを回避できる。RAGパイプラインの実装コストが大幅に低下。

- **マルチテナント設計はSchema-per-tenantからRLS方式へ移行加速:** Supabaseの`SET app.tenant_id`パターンを活用したRLSベースのマルチテナント設計が、スキーマ分割より運用コストが低く、プール接続との相性も良い。

### 7. WebAssembly Rust performance 2026

- **WASM GCの本格普及:** WebAssembly Garbage Collection (WasmGC) がChrome/Firefox/Safariで安定稼働し、RustのWASMバインディングでメモリ管理のオーバーヘッドが大幅に削減された。`wasm-bindgen`と組み合わせることでJS/Rustの相互運用コストが実質ゼロに近づいている。

- **WASI 0.2（Component Model）が実用段階へ:** WASIのComponent Modelにより、RustコンパイルのWASMモジュールをサーバーサイド（Cloudflare Workers、Fastly Compute）でネイティブに近い速度で実行可能。エッジコンピューティングでRustの採用が急増中。

- **SIMDとスレッド並列化の最適化成熟:** WASMのSIMD命令セットとShared Memory（`wasm-threads`）が安定し、Rustの`rayon`相当の並列処理がブラウザ内で動作可能になった。画像処理・暗号処理で10〜50倍の高速化事例が報告されている。

- **ビルドサイズ問題の解消:** `wasm-opt`（Binaryen）とRustの`lto = "thin"`設定の組み合わせで、リリースビルドのWASMサイズが以前比40〜60%削減。`wasm-pack`のtree-shakingも強化され、初期ロードのボトルネックが解消されつつある。

- **Rustフロントエンドフレームワークの実用化加速:** LeptosやDioxusがSSR+ハイドレーションをサポートし、Next.jsと競合できるパフォーマンスを達成。TypeScriptとの共存戦略として「パフォーマンスクリティカルな処理だけRust/WASM」というハイブリッド構成が主流になっている。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** データフェッチはServer Componentsで完結させ、クライアントへのJS転送を最小化する。`use client`境界を葉ノードに限定することでTTI（Time to Interactive）が大幅に改善する。

- **Partial Prerendering（PPR）の本格活用:** 静的シェルと動的ストリームを同一ルートで混在させるPPRが安定化。CDNキャッシュと動的コンテンツの両立が標準パターンになりつつある。

- **Server Actions によるAPI層の簡素化:** フォーム処理・ミューテーションはServer Actionsに集約し、REST APIエンドポイントの乱立を防ぐ。`next-safe-action`等のバリデーション層と組み合わせると型安全かつセキュアに運用できる。

- **`use cache` / `cacheTag` によるきめ細かいキャッシュ制御:** Next.js 15以降の`use cache`ディレクティブで関数・コンポーネント単位のキャッシュが宣言的に書ける。タグベースの無効化（`revalidateTag`）とセットで設計することがベストプラクティス。

- **React 19 の並行機能との統合:** `useOptimistic`・`useFormStatus`を活用したオプティミスティックUIが定着。ローディング状態管理がReact本体に統合されたことで、独自状態管理の複雑さが減少している。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択基準:** 2026年時点でVercel Edge FunctionsはNode.js Runtimeより起動が速い（~0ms cold start）が、使えるAPIが限定的。`crypto`・`fetch`・Web標準APIで完結する処理のみEdgeに置き、DB接続や重いSDKはNode.js Runtimeに残すのが鉄則。

- **Fluid Compute活用:** VercelのFluid Computeにより、Edge FunctionsもCPU継続実行が可能になった。ストリーミングレスポンス（`ReadableStream`）と組み合わせることでAI推論などの長時間処理もエッジで捌けるようになった。

- **キャッシュ戦略の再設計:** `cache-control: stale-while-revalidate`とEdge Configの組み合わせが最も効果的。フィーチャーフラグや設定値はEdge Configで配信し、データベースラウンドトリップをゼロにする。

- **地理的ルーティングの精度:** `request.geo`でユーザーの国・都市を取得し、コンテンツの出し分けやリダイレクトをオリジンへ到達する前に完結させる。日本向けサービスでは`nrt1`リージョンへのトラフィック最適化を明示的に意識する。

- **バンドルサイズ制限（1MB）への対処:** Edge Functionsは1MBのコードサイズ上限がある。`import`の深さをtree-shakingで削り、`date-fns`等の重いユーティリティは`temporal`等のWeb標準APIで代替するとサイズを大幅削減できる。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の積極活用:** 型推論を保持しつつ型チェックを行える `satisfies` は、オブジェクトリテラルの過剰な型アサーション（`as`）を排除し、実行時エラーを大幅に削減できる。

- **Template Literal Types によるAPI契約の強化:** エンドポイントパスやイベント名を `\`/api/${string}\`` 形式で型定義することで、文字列ベースのAPIミスマッチをコンパイル時に検出できる。

- **`const` 型パラメータ（`<const T>`）の標準化:** 関数引数のリテラル型を自動的に推論させることで、冗長な `as const` を省略でき、型の表現力とDXが向上する。

- **Branded Types によるプリミティブ値の意味論強化:** `UserId` と `OrderId` を同じ `string` として扱うバグを防ぐため、ブランド型パターンがドメイン設計の標準手法として定着しつつある。

- **`noUncheckedIndexedAccess` + strict モードの完全適用:** 配列・オブジェクトインデックスアクセスを `T | undefined` として扱うこの設定は、nullableバグの温床を根絶する最もコストパフォーマンスの高い設定変更の一つ。
