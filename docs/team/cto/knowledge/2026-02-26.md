# CTO Knowledge - 2026-02-26

## Daily Update (2026-02-26)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチ・重いロジックはすべてServer Componentsに移行する。`'use client'`は本当に必要な対話性のある境界だけに限定することが鉄則。

- **Partial Prerendering (PPR) の本格導入:** Next.js 15以降で安定化したPPRにより、静的シェルを即時配信しつつ動的コンテンツをSuspenseでストリーミングする設計が標準化。TTFBとCLSを同時に改善できる最重要機能。

- **`next/cache` による細粒度キャッシュ戦略:** `unstable_cache`・`revalidateTag`・`revalidatePath` を組み合わせ、ページ単位ではなくデータ単位でキャッシュ無効化を制御する。過剰な`no-store`指定はパフォーマンスを著しく損なう。

- **画像・フォント最適化の自動化活用:** `next/image`の`sizes`属性と`next/font`のサブセット設定を適切に行うだけで、LCPスコアが大幅改善する。AVIFフォーマット対応とpreload設定も忘れずに。

- **バンドル分析の習慣化:** `@next/bundle-analyzer`を定期実行し、`dynamic()`による遅延ロードと`barrel file`（`index.ts`再エクスポート）の解体でTree Shakingを最大化する。特に大規模shadcn/ui利用時は要注意。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Prerendering (PPR) の実用化:** Next.js 15+でPPRが安定し、静的シェルを即座に配信しつつ動的コンテンツをストリーミングする「ハイブリッドレンダリング」がデフォルト戦略になりつつある。TTFBを犠牲にせずダイナミックコンテンツを実現できる。

- **ポイント2: `use()` フックによるストリーミング制御の簡素化:** React 19の`use()`フックでPromiseを直接Suspense境界内で解決できるようになり、ローディング状態管理のボイラープレートが大幅削減。データフェッチとUI表示の境界が明確になった。

- **ポイント3: Server Actionsとのストリーミング統合:** フォーム送信・ミューテーション後の楽観的UI更新が`useOptimistic`と組み合わさり、サーバーラウンドトリップ中もUIが即座に反応する設計がベストプラクティスとして定着。

- **ポイント4: Edge Runtimeでのストリーミング最適化:** CloudflareやVercel EdgeでのRSCストリーミングが成熟し、グローバルユーザー向けにp99レイテンシを大幅改善。ただしEdgeのCPU制限（50ms）とのトレードオフ管理が課題として残る。

- **ポイント5: キャッシュ戦略の再設計:** Next.js 15でのキャッシュ挙動変更（デフォルトno-cache化）を受け、`unstable_cache`や`revalidateTag`を使った細粒度キャッシュ設計が必須に。ストリーミングとキャッシュの組み合わせパターンの理解がアーキテクチャの差別化ポイントになっている。

### 3. API design REST GraphQL tRPC 2026

- **tRPC の台頭と型安全API:** tRPC はフルスタック TypeScript プロジェクトでデファクトに近づいており、スキーマ定義なしにサーバー・クライアント間の型安全性を実現できる点が2026年においても評価されている。Next.js / Bun との親和性が高い。

- **REST は依然として主流、OpenAPI 3.1 が標準化:** GraphQL の複雑性への反動から REST + OpenAPI 3.1 の採用が再加速しており、`zod-to-openapi` や `hono` などのツールチェーンでコードファースト仕様生成が容易になった。

- **GraphQL は「必要な場面」に絞られつつある:** 複数クライアント（Web/Mobile/Partner API）が異なるデータ形状を要求するケースに限定される傾向。Federation v2（Apollo/Netflix DGS）による分散グラフが大規模組織では有効。

- **エッジ・ストリーミング対応がAPI設計の新要件:** Vercel Edge / Cloudflare Workers の普及により、レイテンシ最小化のためにAPI設計段階からエッジ実行とストリーミングレスポンス（Server-Sent Events / ReadableStream）を考慮する必要がある。

- **AI統合API（MCP / Function Calling）が第5の選択肢に:** LLMエージェントとの連携を前提としたAPI設計（MCP準拠のツール定義、構造化出力）が2026年の新規サービスでは設計初期から求められるようになっており、既存REST/GraphQL APIへの後付けは技術的負債になりやすい。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** WebAssembly（WASM）とONNXランタイムの成熟により、LLMの軽量版（1B〜7Bパラメータ）をエッジで直接実行するパターンが主流になりつつある。レイテンシ削減とデータプライバシー強化を同時に実現できる点が注目されている。

- **ステートフルエッジの台頭:** Cloudflare Durable Objects、Fastly Compute@Edgeなどがエッジでの状態管理を実現し、従来の「エッジはステートレス」という制約が崩れてきた。セッション管理やリアルタイム同期をエッジで完結させるアーキテクチャが現実的になっている。

- **コールドスタート問題の実質的解消:** V8 Isolateベースのランタイム（Deno Deploy、Cloudflare Workers）が普及し、コールドスタートが1ms以下になった。Node.jsベースのサーバーレスとのパフォーマンスギャップが設計上の意思決定に直結する。

- **エッジ・オーケストレーションの複雑化:** マルチクラウド・マルチエッジ環境でのデプロイ管理が課題。OpenTelemetryのエッジ対応と、エッジ固有の分散トレーシングツールの整備が急務になっている。

- **コスト構造の再設計:** リクエスト課金からCPU時間課金へのシフトが進み、計算効率の高い言語（Rust/Go/WASM）の採用優位性が顕著。Next.jsのEdge Runtimeのような高レベル抽象化を使う場合も、裏側の実行コストを把握しておくことが重要。

### 5. authentication security best practices 2026

- **パスキー（Passkey）の標準化:** FIDOアライアンスのパスキーが2026年において事実上の業界標準となりつつあり、パスワードレス認証への移行が加速している。WebAuthn Level 3の普及により、クロスデバイス認証のUXも大幅に改善されている。

- **AIを活用した異常検知:** 従来のルールベースのBot検知では限界があり、行動バイオメトリクス（タイピングリズム、マウス動作等）をMLモデルでリアルタイム分析するアダプティブ認証が主流になっている。

- **トークン設計の見直し（短命JWT + ローテーション）:** JWTのアクセストークンを5〜15分に短縮し、Refresh Token Rotation（使い捨て）を組み合わせるアーキテクチャが推奨されている。長命なトークンはリーク時の被害が甚大なため、設計段階から対策必須。

- **サプライチェーン攻撃への対策:** OAuth/OIDCプロバイダーやIDaaSのサードパーティ依存そのものが攻撃ベクターになっている。プロバイダーの証明書ピニング、トークン検証の多層化、フォールバック機構の整備がエンタープライズ要件化しつつある。

- **ゼロトラスト前提のセッション管理:** 「認証済み = 信頼」という前提を廃止し、リクエストごとにデバイス健全性・ロケーション・リスクスコアを再評価するContinuous Verification（継続的検証）が金融・医療を中心に広まっている。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6+ のEdge対応強化:** Prisma Accelerateによるコネクションプーリングがエッジランタイム（Cloudflare Workers等）でも安定稼働するようになり、サーバーレス環境でのN+1問題やコネクション枯渇が実質的に解消された。

- **Supabase pgvector × RAGアーキテクチャの主流化:** pgvectorの高速化（HNSW インデックス）により、Supabase単体でベクトル検索＋リレーショナルデータを統合管理するパターンが普及し、別途Pinecone等を立てるコストが不要になりつつある。

- **Row Level Security (RLS) の設計コストとPrismaの統合:** SupabaseのRLSはセキュリティ強化に有効だが、複雑なポリシーがクエリパフォーマンスを劣化させる。Prisma Middlewareと組み合わせてアプリ層でフィルタリングするハイブリッドアプローチが現実解として浮上している。

- **Supabase Branching × GitOpsの定着:** PRごとにDB環境を自動作成するSupabase Branchingが成熟し、Prisma Migrateと組み合わせたDB-as-Codeワークフローがチーム開発のスタンダードになっている。

- **型安全クエリの進化（Prisma TypedSQL）:** 生SQLをTypeScriptの型として直接扱えるTypedSQL機能により、複雑な集計クエリでもORMと生SQL双方の利点を享受できる設計が可能になり、ORMの「型安全 vs 柔軟性」トレードオフが大幅に緩和された。

### 7. WebAssembly Rust performance 2026

- **WASI 0.2 / Component Modelの成熟:** 2026年にWASI 0.2が広く普及し、RustのWasmコンポーネントがホスト言語に依存せず相互運用可能になった。`cargo component`ツールチェーンが安定し、マイクロサービス間のポリグロット連携が現実的な選択肢に。

- **Wasmtime / WASMERのAOTコンパイル最適化:** AOT（事前コンパイル）モードが洗練され、ネイティブバイナリとのパフォーマンス差が5-15%以内に縮小。Rustの`wasm-opt`パイプラインと組み合わせることでサーバーサイドWasmが実用域に。

- **SIMD・スレッド対応の標準化:** Wasm SIMDとShared Memoryがほぼ全ランタイムで対応完了。Rustの`packed_simd`/`std::simd`を使った画像処理・ML推論ワークロードがブラウザ・エッジ両方で大幅高速化。

- **エッジ・サーバーレスでのRust Wasm採用加速:** Cloudflare Workers・Fastly Compute等でRust Wasmがデファクト言語に近づきつつある。コールドスタート数ms・メモリ数MBという特性がNode.js比で圧倒的に有利。

- **`no_std` + `wasm-bindgen`の成熟によるバイナリサイズ削減:** `cargo-component` + `wasm-pack`のエコシステム整備により、フロントエンド向けRust Wasmのバイナリサイズが50-100KB台に。Rustを採用する際は`wee_alloc`から`dlmalloc`への移行など、アロケータ選択がパフォーマンスのキーポイントになっている。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** RSC（React Server Components）をデフォルトとし、クライアントコンポーネントを末端の葉ノードに限定することで、バンドルサイズを最小化しFCPを大幅に改善できる。`"use client"` は責務の境界として意識的に配置することが重要。

- **Partial Prerendering (PPR) の実用化:** 静的シェルと動的コンテンツを同一ルートで共存させるPPRが安定化し、CDNキャッシュ効率とパーソナライズを両立できる。`<Suspense>` 境界設計がアーキテクチャの核となる。

- **Server Actions によるAPI Route の置き換え:** フォームミューテーションやデータ変更の多くをServer Actionsで処理できるようになり、API Routeの責務はサードパーティWebhookや公開APIに絞り込むのがベストプラクティス。

- **キャッシュ戦略の明示化:** Next.js 15以降、デフォルトがno-cacheに変更されたため、`fetch` の `cache` / `revalidate` オプションや `unstable_cache` を意図的に設計する必要がある。暗黙のキャッシュ依存は避けること。

- **Parallel Routes + Intercepting Routes の活用:** モーダルやスライドオーバーをURLと同期させ、ディープリンク可能なUIを実現できる。複雑なダッシュボードレイアウトでもブラウザ履歴を壊さない設計が可能になった。

### 9. Vercel Edge Functions optimization 2026

**Vercel Edge Functions最適化 2026 — CTOの視点**

- **ポイント1: V8 Isolateランタイムの制約を理解した設計が必須**
  Node.js APIが使えないため、`crypto`や`fetch`等のWeb標準APIに依存するアーキテクチャへの移行が重要。`runtime: 'edge'`指定時はNode.js専用ライブラリの依存を事前にGrepで確認する習慣が必要。

- **ポイント2: Middleware + Edge Functionsの役割分離**
  認証チェック・リダイレクト・A/Bテストはミドルウェア（全リクエストに適用）、動的レンダリングはEdge Route Handlerに分離することで、レイテンシとコストのバランスが最適化される。

- **ポイント3: Edge ConfigとKVを活用したコールドスタートレスポンス改善**
  Feature flagやルーティングルールはEdge Configに持ち、データベース接続を不要にすることでp99レイテンシを大幅削減できる。Vercel KVはエッジからのセッションキャッシュに有効。

- **ポイント4: Streaming Responseによるユーザー体験の向上**
  LLMレスポンスや大量データのストリーミングには`ReadableStream`を活用し、TTFBを最小化する。Next.jsの`streamText`パターンとの組み合わせが2026年のスタンダード。

- **ポイント5: バンドルサイズの1MB制限への継続的な注意**
  Edge Functionsはバンドルサイズが1MBに制限されるため、`next-bundle-analyzer`での定期的な監視と、重いライブラリ（例: `date-fns`全体インポート）のtree-shaking徹底が必要。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `type UserId = string & { readonly __brand: 'UserId' }` パターンが広く採用され、プリミティブ型の誤用をコンパイル時に防ぐ手法が実用段階に。TypeScript 5.x の `const type parameters` と組み合わせることでさらに表現力が向上。

- **`satisfies` 演算子の活用深化:** 型推論を保ちながら型制約を検証できる `satisfies` が設計の要に。`as` によるキャストを排除し、型の安全性を損なわずに柔軟な初期化パターンを実現できる。

- **Template Literal Types による API 型生成:** REST エンドポイントやイベント名を `\`/api/${Resource}/${Action}\`` のように型レベルで表現し、文字列の誤りをゼロコストで検出。バックエンド型定義からフロントエンドを自動生成するモノレポ構成が主流に。

- **`noUncheckedIndexedAccess` の実質的必須化:** 配列・オブジェクトアクセスの結果を `T | undefined` として扱う厳格オプションが、本番コードの基準設定として定着。`tsconfig.json` の厳格プリセットに含める動きが加速している。

- **Effect / Result 型パターンの台頭:** 例外スローの代わりに `Result<T, E>` や `Effect` ライブラリを用いたエラー型の明示化が増加。`fp-ts` から軽量な独自実装へのシフトも見られ、型レベルでエラーパスを強制する設計が特に大規模チームで有効。
