# CTO Knowledge - 2026-06-17

## Daily Update (2026-06-17)

### 1. Next.js performance optimization 2026

- **ポイント1: Partial Prerendering (PPR) の本格運用** Next.js 16でPPRが安定版となり、静的シェルと動的コンテンツを1つのルートで組み合わせられるようになった。物件一覧ページなどでヘッダーやナビは静的配信しつつ、在庫状況や価格だけをストリーミングすることで、TTFBを大幅短縮できる。

- **ポイント2: React Server Components のデータフェッチ最適化** サーバーコンポーネントでのfetchキャッシュ戦略（`cache: 'force-cache'` vs `revalidate`）を物件データの更新頻度に応じて使い分けることが重要。引越し費用や前の住人情報のような更新頻度が低いデータは長めのrevalidateで配信コストを削減できる。

- **ポイント3: Turbopackビルドの恒久採用** TurbopackがNext.js 16でデフォルトのビルドツールとなり、開発時のHMRと本番ビルド時間が大幅改善。CIのビルド時間短縮により、`bun run build`を含むPR検証サイクルが高速化し、デプロイ頻度を上げられる。

- **ポイント4: 画像・フォント最適化のエッジ処理** `next/image`のエッジ最適化とCDNキャッシュの組み合わせで、物件写真のような重い画像アセットの初期表示速度を改善。特にモバイル回線でのLCP（Largest Contentful Paint）改善に直結する。

- **ポイント5: Client Components の境界最小化** "use client"境界を必要最小限に絞り、インタラクティブなUI（検索フィルター、お気に入りボタン等）だけをクライアント化することでJSバンドルサイズを削減。ダッシュボードやアカウントページなど複雑なUIでも、サーバー側で可能な処理は極力サーバーコンポーネントに留めるのがベストプラクティス。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPPR（Partial Prerendering）が標準化され、静的シェルを即時配信しつつ動的部分のみStreamingで補完する構成が主流になっている。本プロジェクトの`properties/`一覧ページのような「静的レイアウト＋動的データ」構成に特に有効。

- **ポイント2:** Suspense境界の粒度設計が重要な最適化ポイントになっている。粒度を細かくしすぎるとウォーターフォール（直列リクエスト）が発生するため、関連データはサーバー側で`Promise.all`的に並列取得し、UI上のローディング体験とのバランスを取る必要がある。

- **ポイント3:** Server ActionsとStreamingの組み合わせで、フォーム送信後の楽観的UI更新（`useOptimistic`）がより安定して使えるようになった。引越し費用の決済フローや物件登録フォームなど多段階フローでの体感速度向上に直結する。

- **ポイント4:** RSCペイロックのキャッシュ戦略（`use cache`ディレクティブ）が成熟し、データフェッチ層とコンポーネント層のキャッシュ境界を明示的に分離できるようになった。`src/lib/data.ts`のようなデータ層を持つ構成では、キャッシュタグ設計を早期に決めておくと後続のリビジョンが楽になる。

- **ポイント5:** Streaming SSRはエッジランタイムとの相性が良いが、認証チェック（`auth-context.tsx`）など同期的に必要な処理をストリーミング開始前にブロックしてしまうケースがあるため、認証判定はミドルウェア層で済ませ、RSC側は表示用データのみを遅延ストリーミングする設計が推奨される。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** GraphQLの過剰な柔軟性によるN+1問題やキャッシュ戦略の複雑さが見直され、型安全性とシンプルさを重視したtRPCやhonoのRPCパターンへの移行が加速している。
- **ポイント2:** TypeScriptモノレポ構成（Next.js + tRPC）では、フロントエンドとバックエンドで型定義を共有できるため、API契約のズレによるバグを開発時点で検出できるのが大きな利点。
- **ポイント3:** 外部公開APIやサードパーティ連携が必要な場合はRESTやOpenAPI仕様が依然として標準であり、社内向けAPIにはtRPC、外部向けにはRESTという併用パターンが2026年も主流。
- **ポイント4:** AIエージェントによるAPI利用が増加し、LLMが理解しやすいスキーマ定義（OpenAPI/JSON Schema）や自己記述的なエンドポイント設計の重要性が高まっている。
- **ポイント5:** sumitsugiのような小〜中規模Next.jsプロジェクトでは、Server ActionsとtRPCの組み合わせでAPI層自体を薄くし、型安全性を保ちながら開発速度を優先するアプローチが適している。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** Cloudflare Workers・Vercel Edge Functions・Deno DeployなどがWASMベースのV8 isolateに収束しつつあり、コールドスタートがほぼゼロに近づいている。Next.js 16のEdge Runtimeを使えば、認証チェックやリダイレクトのような軽量処理は東京リージョンのオリジンサーバーを介さずユーザー近接ノードで完結できる。

- **エッジデータベースの実用化:** Turso（libSQL）やCloudflare D1のような分散SQLiteがレイテンシ要求の厳しい読み取り処理（物件一覧・検索）に向き始めている。ただし強整合性が必要な決済・在庫系は依然オリジンDB必須なので、読み取り専用キャッシュ層として段階導入するのが現実的。

- **AI推論のエッジ化:** 軽量モデル（埋め込み生成・分類）をエッジで実行し、レコメンドや検索の前処理をユーザー近接で行う構成が2026年で一般化。前の住人とのマッチング機能のような軽量AI処理はエッジ候補になり得るが、現フェーズではMVP安定化が優先。

- **可観測性のギャップが課題:** エッジ分散実行はトレーシング・ログ集約が難しく、デバッグコストが上がる。本番投入前にOpenTelemetry等の分散トレーシングを最低限入れておかないと障害調査が困難になる——ベータローンチ前に検討すべき項目。

- **コスト構造の変化:** エッジ実行は呼び出し回数課金が中心でサーバーレス以上に細粒度。トラフィックが小さい現フェーズでは恩恵は限定的なので、今は通常のNext.jsデプロイで十分、スケール後に段階移行が妥当という判断。

### 5. authentication security best practices 2026

## CTOの視点：認証セキュリティのベストプラクティス（2026年）

- **パスキー（Passkeys/WebAuthn）がデフォルト化:** SMS OTPやパスワードのみの認証はフィッシング耐性が低く非推奨化が進んでおり、FIDO2/WebAuthnベースのパスキーをプライマリな認証手段として実装すべき。デバイス固有の秘密鍵を使うため、認証情報の漏洩・再利用リスクを根本的に減らせる。

- **多層防御としての継続的認証（Continuous Authentication）:** ログイン時の一度きりの認証ではなく、セッション中の行動パターン・デバイス情報・位置情報などをもとにリスクベースで再認証を要求するゼロトラスト型の仕組みが主流になっている。高リスク操作（決済・個人情報変更）にはステップアップ認証を組み込むのが実用的。

- **トークン管理のセキュリティ強化:** リフレッシュトークンのローテーション、短命なアクセストークン、トークンバインディング（デバイス/クライアントに紐付け）が標準的なプラクティス。長寿命トークンの平文保存やlocalStorageへの保存は避け、httpOnly + Secure + SameSiteなCookie運用を徹底すべき。

- **サプライチェーン・依存ライブラリのリスク管理:** OAuth/OIDCライブラリや認証SDKの脆弱性が攻撃の入口になりやすいため、依存パッケージの定期的な脆弱性スキャンとアップデートが必須。自前実装よりも実績のある標準ライブラリ（NextAuth.js等）を使い、設定ミス（CSRF対策の欠如、redirect_uri検証不足など）を防ぐ。

- **ポストクアンタムへの備えと監査ログの強化:** 長期的な鍵交換アルゴリズムの耐量子化が議論され始めており、将来的な移行を見据えた暗号アジリティ（アルゴリズムの差し替えやすさ）を設計に組み込むことが望ましい。同時に、認証イベントの監査ログ（誰が・いつ・どこから）を保持し、インシデント対応に備える。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** PrismaのRust製クエリエンジンがWASM/Node-API両対応になり、Supabaseのコネクションプーラー（PgBouncer/Supavisor）との統合でサーバーレス環境でのコールドスタートとコネクション枯渇問題が大幅に改善されている。
- **ポイント2:** Prisma Accelerateのようなエッジキャッシュ層を組み合わせることで、Supabase上のPostgresへのレイテンシをグローバルに削減できるため、住人(ユーザー)向けの物件検索・一覧表示のレスポンス速度向上に直結する。
- **ポイント3:** Supabaseの行レベルセキュリティ(RLS)とPrisma Client側のスキーマ管理を併用する設計が標準化しつつあり、`'draft'|'public'`のようなステータス制御をDBレベルでも強制することで、誤公開などのセキュリティリスクを下げられる。
- **ポイント4:** PrismaのTypedSQL機能により複雑な集計クエリも型安全に書けるようになったため、引越し費用計算や活動歴の集計ロジックをORMの抽象化に縛られず最適化しやすい。
- **ポイント5:** SupabaseのBranching機能とPrisma Migrateを組み合わせたプレビュー環境ごとのDBブランチ運用が一般化しており、本番DBに影響を与えずに機能フラグ的な検証ができる体制が構築しやすくなっている。

### 7. WebAssembly Rust performance 2026

- **ポイント1: コンポーネントモデルの成熟:** WASM Component Model（WIT/wasm-tools）がRustツールチェーンと統合され、言語間バインディングのオーバーヘッドがほぼゼロになってきている。マイクロフロントエンドやプラグインアーキテクチャでRustコンポーネントを安全に合成できる。

- **ポイント2: メモリ管理の効率化:** wasm-bindgenとwee_allocの改善により、Rust→WASMのバイナリサイズとヒープ使用量が大幅に削減され、ブラウザ上でのコールドスタートが速くなっている。Sumitsugiのような画像処理（物件写真の最適化等）をクライアント側で行う場合に有利。

- **ポイント3: SIMD・マルチスレッド対応の安定化:** WASM SIMDとシェアードメモリ+Web Workersの組み合わせがブラウザ全体で標準化され、画像/PDF処理（引越し費用算出ロジックや内見資料生成）をネイティブに近い速度で実行可能になっている。

- **ポイント4: Edge Runtime統合:** Cloudflare WorkersやVercel EdgeでのRust製WASMモジュールの採用が拡大し、Next.jsのMiddlewareやAPI Routeをエッジで超低レイテンシ実行できるようになっている。地域別の物件検索など地理的に分散したワークロードに適している。

- **ポイント5: ビルドパイプラインの簡素化:** `cargo component`やTurbopack側のWASMローダー改善により、Next.js 16でのRust WASMモジュール組み込みが「ほぼゼロコンフィグ」になり、導入コストが従来より大幅に下がっている。

### 8. Next.js App Router patterns 2026

- **Server Components first（PPR標準化）:** Partial Prerendering が安定版となり、静的シェルと動的コンテンツを1つのルートで組み合わせるのが標準パターンに。`loading.tsx` よりも `<Suspense>` 境界を細かく配置し、TTFBを最小化するのが定石。

- **`use cache` ディレクティブの普及:** Next.js 15/16 で導入された `use cache` でデータ取得関数単位のキャッシュ制御が可能になり、`fetch` のキャッシュオプションより細粒度・明示的な制御が主流に。再検証は `revalidateTag`/`cacheLife` で宣言的に管理する。

- **Server Actions の責務分離:** フォーム送信や副作用は Server Actions に集約し、Zod でのスキーマ検証を Server Action 内・境界で必須化する流れが定着（本プロジェクトの `standards.md` とも一致）。クライアントバンドルを増やさず、API Route を減らせる利点が評価されている。

- **ルートグループ + Parallel Routes でのレイアウト分離:** `(group)` によるルートグループと `@slot` の Parallel Routes を組み合わせ、ダッシュボード系UI（モーダル、サイドパネルの同時表示）を実装するパターンが定番化。本プロダクトの `properties/`・`listing/` のような一覧+詳細UIにも適用余地がある。

- **Edge runtime の選択的採用:** 全ルートをEdgeにするのではなく、認証チェックや地理的パーソナライズなどレイテンシ敏感な処理のみをEdge Middlewareに限定し、DB接続を要する処理はNode runtimeに残すハイブリッド構成が2026年のベストプラクティスとして定着している。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Vercel Fluid Compute（Edge/Serverless統合モデル）の普及により、コールドスタートを抑えつつ同時実行で複数リクエストを処理できるようになり、レイテンシとコストの両方を最適化しやすくなっている。
- **ポイント2:** Edge Middlewareでの重い処理（認証チェック、リダイレクト判定）はV8 isolateのCPU時間制限に引っかかりやすいため、計算ロジックを最小限に絞り、キャッシュ済みのフラグやJWT検証のみに留めるのがベストプラクティス。
- **ポイント3:** ISR/PPR（Partial Prerendering）とEdge Functionsの組み合わせが標準化し、動的パーソナライズ部分のみEdgeで描画してそれ以外は静的配信することでTTFBを大幅短縮できる。
- **ポイント4:** リージョン選択（`regions`設定）をDBやAPIの物理的な近接性に合わせて明示指定しないと、Edge特有の「近いはずなのに遅い」というレイテンシ問題が発生しやすいため、データ層のロケーションとの整合性確認が重要。
- **ポイント5:** Edge Runtimeで使えるNode.js APIの制約（fsアクセス不可、一部npmパッケージ非対応）が依然としてあるため、依存パッケージ選定時にEdge互換性を事前検証するワークフローをCIに組み込むと手戻りを防げる。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** `satisfies`演算子の活用が定着し、型推論を保ったまま型チェックする設計が標準化。リテラル型の恩恵を失わずに安全性を確保できる。
- **ポイント2:** Zodなどのスキーマライブラリによる「実行時検証＋型推論の一体化」がAPI境界・フォーム入力の標準パターンに。型と実装のズレを防ぐ。
- **ポイント3:** Branded Types（タグ付き型）でID/単位の取り違えを防ぐ手法が普及。`UserId`と`PostId`のような名目的型付けをstring型に対して実現できる。
- **ポイント4:** Template Literal Typesを使ったルーティングやi18nキーの型安全化が進み、文字列ベースのAPIでもコンパイル時に誤りを検出できるように。
- **ポイント5:** strictモード＋`noUncheckedIndexedAccess`の組み合わせがデフォルト設定として推奨され、配列・オブジェクトアクセスのundefined漏れを未然に防ぐチームが増えている。
