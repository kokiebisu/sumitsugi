# CTO Knowledge - 2026-04-05

## Daily Update (2026-04-05)

### 1. Next.js performance optimization 2026

- **React Server Components の徹底活用:** RSCをデフォルトとし、クライアントコンポーネントは状態・インタラクションが必要な最小単位に限定する。バンドルサイズが劇的に削減され、TTFBが改善する。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降で安定化したPPRにより、静的シェル+動的ストリーミングのハイブリッドが可能になった。Suspense境界の設計がパフォーマンスの鍵となる。

- **`use cache` ディレクティブによる細粒度キャッシュ:** 関数・コンポーネント単位でキャッシュ戦略を宣言できる新API。`revalidate`タグ設計を事前に固めておかないと、キャッシュ無効化が複雑化するため注意。

- **画像・フォントの最適化は `next/image` + `next/font` で完結させる:** 外部CDNを挟まずフレームワーク内で完結させることで、LCPとCLSを同時に改善。`sizes`プロパティの適切な設定が見落とされがちなボトルネック。

- **Edge Runtime の選択的採用:** Middleware・軽量APIはEdgeで動かしてコールドスタートをゼロに近づける一方、DB接続が必要なルートはNode.js Runtimeに留める。全面Edge化は逆効果になるケースが多い。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度設計が鍵:** RSCストリーミングでは、Suspense境界をコンポーネントツリーのどの粒度に置くかがTTFB・LCPに直結する。データフェッチの依存関係を分析し、独立したウォーターフォールを避ける設計が必須。

- **PPR（Partial Prerendering）との統合が主流化:** Next.js 15以降でPPRが安定化し、静的シェルを即時配信しつつ動的部分をストリームする戦略が実用レベルに。静的/動的の境界を意識したアーキテクチャ設計が求められる。

- **Server Actionsとの組み合わせでクライアントバンドルを削減:** フォームやミューテーション処理をServer Actionsに移行することで、クライアントJSバンドルを30〜50%削減できるケースが報告されている。特にデータ変換ロジックはサーバー側に積極的に移す。

- **キャッシュ戦略の再設計が必要:** `fetch`のキャッシュ動作がNext.js 15でデフォルト変更（no-store化）。ストリーミング環境では`unstable_cache`やReact `cache()`を使った細粒度キャッシュ設計に移行しないと、過剰なオリジンリクエストが発生する。

- **エラーバウンダリとストリーミングの相性問題に注意:** ストリーミング中にthrowされたエラーはHTTPヘッダー送信後のため、ステータスコード変更不可。`error.tsx`での適切なリカバリーUIと、クリティカルパスのデータフェッチは早期にawaitする設計が現実解。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全APIの標準化:** Next.js + TypeScriptスタックでのtRPC採用が急増しており、クライアント/サーバー間でのランタイムスキーマ生成不要な型共有が開発速度を大幅に向上させている。

- **GraphQLの選択的採用:** マイクロサービス間のデータ集約やBFF（Backend for Frontend）パターンには依然有効だが、単純なCRUDにはオーバーエンジニアリングになるケースが多く、「GraphQLは複雑性のトレードオフ」として慎重に採用判断する流れが定着している。

- **REST + OpenAPIの復権:** Zodなどによるスキーマ駆動開発と組み合わせることで、tRPCに近い型安全性をREST上で実現できるようになり、特に外部APIやマルチ言語環境ではRESTが引き続き主流を維持している。

- **エッジ・ストリーミング対応の重要性:** Vercel Edge FunctionsやCloudflare Workersの普及により、APIレスポンスのストリーミング（RSC、Server-Sent Events）が設計要件として浮上し、従来のリクエスト/レスポンス設計では対応しきれないケースが増えている。

- **APIゲートウェイとObservability:** 2026年時点ではAPIの設計よりも「運用可視性」が差別化要因になっており、OpenTelemetryによるトレース、p99レイテンシ監視、レート制限の自動調整をAPI設計の初期段階から組み込むことがベストプラクティスとなっている。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジの標準ランタイムに:** V8 isolatesに代わりWasmがエッジ実行環境の主流となり、言語非依存でコールドスタートをほぼゼロに抑えられる。Cloudflare Workers・Fastly Compute等が本番対応を完了している。

- **AIインファレンスのエッジシフト加速:** LLMの量子化（INT4/INT8）技術の成熟により、小〜中規模モデルのエッジ実行が現実的になった。レイテンシ削減とデータ主権対応の両立が主要ユースケース。

- **SQLite-on-Edgeによる分散データ層の確立:** Cloudflare D1・Turso等のエッジ近接SQLiteが普及し、「エッジはステートレス」の前提が崩れつつある。ただしグローバル整合性設計は依然複雑。

- **コスト最適化としてのエッジ＋中央ハイブリッド戦略:** エッジを「すべてに使う」から「認証・キャッシュ・パーソナライゼーション」に限定し、重い処理はリージョナルサーバーに委譲するアーキテクチャが設計のベストプラクティスとして定着。

- **オブザーバビリティのギャップが最大の運用課題:** 分散エッジノードでのトレーシング・ログ集約はまだ成熟途上。OpenTelemetryのエッジ対応が進んでいるが、本番導入時は監視戦略を事前設計することが不可欠。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** FIDO2/WebAuthn標準が成熟し、パスワードレス認証がデファクトスタンダードになりつつある。Apple・Google・Microsoftのエコシステム統合が進み、UXコストなくフィッシング耐性を実現できる。

- **セッション管理の短命化とリフレッシュ戦略の見直し:** アクセストークンの有効期限を15分以下に設定し、リフレッシュトークンにRotation（ローテーション）＋Binding（デバイス紐付け）を組み合わせるのが主流。JWTのステートレス性に依存しすぎず、サーバーサイドのセッション無効化機構を必ず持つこと。

- **MFAはSMS非推奨、TOTP→パスキーへ:** SIMスワップ攻撃の普及によりSMS OTPはNISTガイドライン上も非推奨。TOTPアプリ（TOTP RFC 6238）かハードウェアキー（YubiKey等）を最低ラインとし、新規実装ではパスキーを第一選択にする。

- **サプライチェーン攻撃対策としての依存ライブラリ監査:** 認証ライブラリ（NextAuth、Auth.js等）のバージョン固定とSBOM（ソフトウェア部品表）の管理が必須。`npm audit` / `bun audit` をCI必須ステップに組み込み、依存関係のハッシュ検証を行う。

- **ゼロトラストアーキテクチャとの統合:** 「一度認証したら信頼する」モデルを廃止し、リクエストごとにコンテキスト（IP・デバイス指紋・行動パターン）を評価するリスクベース認証を導入。Next.jsのMiddlewareレイヤーでエッジ側の継続認可チェックを実装するのが実践的なアプローチ。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x の Edge Runtime 対応:** Prisma がEdge環境（Cloudflare Workers、Vercel Edge）でネイティブ動作可能になり、Supabase の接続プーリング（pgBouncer / Supavisor）と組み合わせることでサーバーレスでもコネクション枯渇を防げる。

- **Supabase Realtime v3 と Row-Level Security の成熟:** RLSポリシーをアプリ層でなくDB層に集約する設計が主流化しており、Prisma の`$executeRaw`やRLS対応ミドルウェアを使ったマルチテナント実装がベストプラクティスとなっている。

- **Prisma Accelerate によるグローバルキャッシュ:** Prisma Accelerate（旧Data Proxy）がクエリ結果をエッジでキャッシュする機能を強化。Supabase の読み取りレプリカと併用することで、レイテンシを大幅削減できる構成が現実的になった。

- **型安全なマイグレーション管理の重要性:** `prisma migrate`と Supabase の`supabase db push`を混在させると schema drift が起きやすい。2026年時点では Prisma を single source of truth とし、CI で`prisma migrate diff`を自動検証するパターンが推奨されている。

- **Supabase Vector（pgvector）との統合:** AI機能の組み込みが標準化しつつあり、Prisma の`unsupported`型経由で pgvector を扱うより、Supabase の`vecs` Python クライアントや専用RPC関数を使う役割分担が現実的な選択肢になっている。

### 7. WebAssembly Rust performance 2026

- **WASM GC / Component Modelの本格普及:** 2025年末にWASM GC仕様が主要ブラウザで安定化し、Rustのメモリ管理との相性が向上。コンポーネントモデルにより、異言語間のFFIコストが大幅に削減された。

- **SIMD・スレッド対応の成熟:** WASMのFixed-width SIMDとShared Memoryが全主要ランタイムで安定稼働。RustのRayonベースの並列処理がWASM Threadsに対応し、CPU集約型処理でネイティブの80〜90%の性能を達成するケースも報告されている。

- **Wasmtime / WASIp2によるサーバーサイド活用:** Fastly・Cloudflare・Fermyon等のエッジ環境でWASIp2が標準化。RustでビルドしたWASMモジュールのコールドスタートが<1msを実現し、コンテナ不要の軽量デプロイが現実的な選択肢になっている。

- **ツールチェーンの成熟（wasm-pack → cargo-component）:** `cargo-component`がde factoツールとなり、コンポーネントモデル対応のビルドが`cargo build`並みに簡素化。`wit-bindgen`によるインターフェース定義も整備され、チーム開発での採用障壁が低下した。

- **ボトルネックはJSバインディングのオーバーヘッド:** WASMのパフォーマンス上限はRust側でなくJS↔WASM境界のデータコピーコストに移行。大きなバッファはShared ArrayBuffer経由のゼロコピーパターンを採用すること、また小刻みな関数呼び出しをバッチ化する設計が2026年の実装では必須。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点でApp Routerの主流はRSC（React Server Components）を基本とし、インタラクティブな部分だけ`'use client'`を付与する設計。クライアントバンドルを最小化することがパフォーマンスの鍵。

- **Partial Prerendering（PPR）の本格活用:** Next.js 15+でStableになったPPRにより、静的シェルと動的コンテンツを同一ルートで混在させられる。`<Suspense>`境界の設計がアーキテクチャの核心になっている。

- **Server Actions によるAPI Route削減:** フォーム処理やデータ変異はServer Actionsに集約し、従来の`/api`ルートを最小化するパターンが定着。ただしZodによる入力バリデーションは必須（信頼境界として扱うこと）。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** Next.js 15で導入された`use cache`により、関数・コンポーネント単位でキャッシュ戦略を宣言的に記述できる。`revalidateTag`との組み合わせで従来のISRより柔軟な更新が可能。

- **Parallel Routes + Intercepting Routes でモーダルUXを実現:** `@modal`スロットとインターセプトルート`(..)`を組み合わせることで、URLを保持したまま詳細モーダルを実装できる。ディープリンクとSEOを両立する設計として標準化が進んでいる。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeのコールドスタート最適化:** 2026年時点でVercel Edge FunctionsはV8 Isolateベースのため、Node.js Runtimeと比べコールドスタートが1ms以下と劇的に速い。ただしNode.js APIの制限があるため、`runtime: 'edge'`を使う際は依存ライブラリの互換性確認が必須。

- **Fluid Compute統合による実行モデルの変化:** VercelはFluid Computeにより「リクエスト中にアイドル時間があれば課金しない」モデルを導入。外部APIコールが多いEdge Functionsでは、従来のServerless Functionsより大幅なコスト削減が期待できる。

- **ISR + Edge Middlewareの組み合わせが最強パターン:** 静的生成（ISR）とEdge Middlewareでのパーソナライゼーションを組み合わせることで、CDNキャッシュのヒット率を維持しつつユーザー固有のコンテンツを返せる。Next.js App Routerの`revalidate`とMiddlewareのヘッダー操作を活用するのが2026年のベストプラクティス。

- **バンドルサイズの上限（4MB）への注意:** Edge Functionsは依然として4MBのコードサイズ制限があり、重厚なORMやSDKを直接インポートすると容易に超過する。`next/server`の軽量APIやfetch APIを直接使い、ロジックを薄く保つ設計が重要。

- **地域指定（`preferredRegion`）による低レイテンシ戦略:** データベース（Supabase, PlanetScaleなど）と同一リージョンにEdge Functionをピン留めする`preferredRegion`設定を忘れると、地理的分散の恩恵よりもDB往復レイテンシのペナルティが上回る逆効果になる。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded Typesが実務で定着し、プリミティブ型の混在バグをコンパイル時に排除するパターンが主流になっている。

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の `satisfies` により、型推論を保ちながら型チェックを強制できる。`const config = { ... } satisfies Config` で過剰な型アサーション（`as`）を排除するのが2026年のベストプラクティス。

- **Template Literal Types によるAPIルート型付け:** `type Route = \`/api/${string}\`` のようにURLパターンを型レベルで表現し、フロントエンド・バックエンド間の型整合性をビルド時に保証する設計が普及している。

- **`noUncheckedIndexedAccess` の有効化が標準に:** `tsconfig.json` のこのオプションが「厳格モードのデフォルト」として認識され、配列・オブジェクトの添字アクセスで `T | undefined` を返すことでランタイムエラーを大幅削減できる。

- **Result型パターン（`neverthrow` 等）の台頭:** `try/catch` に頼らず `Result<T, E>` 型で成功・失敗を明示的にモデル化するアプローチが、特にAPI層やドメインロジックで採用増加。エラーハンドリングの型安全性が大幅に向上する。
