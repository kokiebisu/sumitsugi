# CTO Knowledge - 2026-03-15

## Daily Update (2026-03-15)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチとロジックをサーバーコンポーネントに集約。2026年時点では「クライアントコンポーネントは本当に必要な箇所のみ」が鉄則となっている。

- **PPR（Partial Prerendering）の本格導入:** Next.js 15以降で安定化したPPRにより、静的シェルと動的コンテンツを同一ルートで混在可能。TBT・LCPの大幅改善に直結するため、ページ設計の段階からPPRを前提にすべき。

- **Turbopack移行による開発体験とビルド最適化:** Turbopackはwebpackに比べビルド速度が大幅に向上。本番ビルドにも対応が進んでいるため、CI/CDパイプラインのビルド時間短縮効果が大きい。

- **`next/image` と `next/font` の最適化徹底:** AVIFフォーマット対応・サイズ自動計算・フォントのゼロレイアウトシフトは依然として最大CPF改善施策。`priority`属性のLCP要素への付与を自動チェックするリンタールール導入も推奨。

- **Edge Runtime とストリーミングの戦略的使い分け:** レイテンシ重視のAPIはEdge Runtime、CPUヘビーな処理はNode.js Runtimeと明確に分離。`loading.tsx` と Suspense境界を適切に配置することで、TTFB悪化を防ぎつつUX体感速度を向上できる。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の本番展開:** Next.js 15以降でPPRが安定化し、静的シェルと動的ストリーミングコンテンツを同一ルートで混在させるパターンが標準化。TTFBを犠牲にせずにインタラクティブ性を確保できる。

- **Suspense境界の粒度戦略が鍵:** コンポーネント単位でSuspenseを配置することで、遅いデータフェッチが画面全体をブロックしなくなる。ただし過度な細分化はウォーターフォールを生むため、データ依存グラフを意識した設計が必要。

- **Server Actions との統合成熟:** フォーム送信・楽観的更新・リバリデーションがRSCストリーミングと緊密に連携し、従来のAPI Route不要のフルスタックパターンが普及。バンドルサイズ削減効果が顕著。

- **Edge Runtimeでのストリーミング普及:** Vercel/Cloudflare Workers環境でのRSCストリーミングが安定し、グローバルレイテンシの改善が実用レベルに。ただしNode.js依存ライブラリの互換性チェックは依然必須。

- **React 19のuse()フック活用:** `use(promise)`によりクライアントコンポーネント内でも非同期データをSuspenseで扱えるようになり、RSC/CCの境界設計の自由度が向上。Server→Clientへのデータ受け渡しアーキテクチャが簡素化される。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性の標準化:** 2026年時点でNext.js/RemixプロジェクトではtRPCが事実上のデファクトになりつつあり、フロントエンド・バックエンド間のZodスキーマ共有による型安全性がDXの基準となっている。

- **GraphQLの「適材適所」への回帰:** マイクロサービス連携やパブリックAPIでは依然強力だが、単一チームの内部APIにGraphQLを選ぶコストメリットが薄れ、tRPCやREST+OpenAPIへの移行が加速している。

- **REST+OpenAPI 3.1の再評価:** `zod-openapi`や`@hono/zod-openapi`等のツールにより、コードファーストでOpenAPIスキーマを自動生成できるようになり、REST APIでも型安全なクライアント生成（`openapi-fetch`等）が実現できるため、既存REST資産の価値が再認識されている。

- **エッジ・サーバーレス環境でのAPI設計変化:** Cloudflare Workers / Vercel Edge Functionsの普及により、コールドスタートを意識した軽量ルーティング（Hono等）が重要になり、従来のExpressベース設計からの脱却が求められている。

- **AIエージェント向けAPI設計の新要件:** MCP（Model Context Protocol）やfunction callingとの統合を前提としたAPI設計が必要になっており、スキーマの機械可読性・ツール記述の明確さがAPI品質の新たな評価軸となっている。

### 4. serverless edge computing 2026

- **エッジでのAI推論が主流化:** 2026年にはWebAssembly + ONNX Runtimeの組み合わせにより、Cloudflare WorkersやVercel Edge Functionsで軽量LLMモデルをコールドスタートなしで実行するパターンが定着しつつある。レイテンシ要件が厳しいリアルタイム機能（チャット補完、パーソナライゼーション）はエッジ推論が第一選択肢になった。

- **SQLiteベースのエッジDBが実用段階に:** Cloudflare D1やTurso（libSQL）により、エッジノード近傍にデータを持つ分散SQLiteが本番投入できるレベルに成熟。従来のエッジ＝「ステートレス」という前提が崩れ、リード重視のワークロードなら中央集権DBへのラウンドトリップを排除できる。

- **Cold Start問題は実質解消、次の課題はメモリ上限:** V8 Isolateベースの実行環境でコールドスタートはほぼ数ms以下に収束。現在の制約はメモリ（128MB前後）とCPU時間上限であり、アーキテクチャ設計はそこに集中すべき。

- **エッジとオリジンの責務分離が鍵:** 認証トークン検証・A/Bフラグ・地理ルーティングはエッジ、ビジネスロジックの核心・トランザクション処理はオリジンという「エッジ＝ゲートウェイ層」パターンが最も保守性が高い。全処理をエッジに押し込もうとすると制約に苦しむ。

- **観測可能性がまだ弱い:** 分散エッジノードをまたいだトレーシング（OpenTelemetry対応）はツール整備が追いついておらず、デバッグコストが高い。本番導入前にログ集約・トレース戦略を確立しないと障害対応で詰まる。これが現時点での最大の運用リスク。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）へのシフト加速:** パスワードレス認証がデファクトスタンダードになりつつあり、フィッシング耐性のあるパスキーへの移行は2026年時点で必須対応。既存のパスワード認証との併存戦略より、段階的廃止ロードマップを今から設計すべき。

- **デバイス認証との統合（Passkey + Device Binding）:** 単なるパスキーに加え、デバイスレベルの信頼スコアを組み合わせたリスクベース認証が普及。異常なデバイスや地域からのアクセスに動的に追加認証を要求するアーキテクチャが標準化されている。

- **JWTのセキュリティ強化（短命トークン + DPoP）:** `alg: none`やHS256弱点への対策として、DPoP（Demonstrating Proof of Possession）を使ったトークンバインディングが主流に。アクセストークンの有効期限は5〜15分が推奨、リフレッシュトークンのローテーションは必須実装。

- **セッション管理のゼロトラスト化:** 「一度認証したら信頼する」モデルから、継続的な検証（Continuous Authentication）へ。行動バイオメトリクス（タイピングパターン、マウス動作）を組み合わせたセッション中の再評価が高セキュリティ要件では採用が増加している。

- **OAuth 2.1 + BCP（Best Current Practice）の義務化:** OAuth 2.0の脆弱な拡張（Implicit Flow廃止、PKCE必須化）を整理したOAuth 2.1への準拠が事実上必須。特にモバイルアプリやSPAでは`response_type=code`+ PKCE以外の実装は今後のセキュリティ審査でリジェクト対象になる。

### 6. database architecture Prisma Supabase 2026

- **Prisma + Supabase の統合成熟化:** Prisma v6（2025年リリース）でSupabase PostgreSQLとの接続プーリングが安定し、`prisma://` プロトコル経由のコネクション管理がエッジ環境でも実用レベルに達している。

- **Row Level Security（RLS）の設計が差別化要因:** Supabaseの真価はRLSポリシーにあり、Prismaと組み合わせる場合はアプリ層のORM制御とDB層のRLSを「多重防衛」として設計するのがベストプラクティス。Prismaだけに頼るとマルチテナント漏洩リスクが残る。

- **リアルタイム機能の設計分離:** Supabase Realtimeはwebsocket購読をPrismaと並列で扱う。CRUDはPrisma ORM経由、リアルタイムイベントはSupabase clientで直接購読する「責務分離アーキテクチャ」がスケーラブル。

- **Edge Functions × Prisma Accelerateのレイテンシ対策:** Vercel Edge / Cloudflare Workersなどのサーバーレス環境ではコネクション数上限が問題になるため、Prisma Accelerate（グローバルコネクションプーリング＋クエリキャッシュ）の導入が2026年時点での標準解となっている。

- **スキーマドリフト監視の自動化:** `prisma migrate diff` と CI/CDを組み合わせたスキーマドリフト検知が必須。本番DBとマイグレーション履歴の乖離を早期発見し、手動SQLパッチによる技術的負債を防ぐ。

### 7. WebAssembly Rust performance 2026

- **WebAssembly Component Model の本格普及:** 2026年はWASM Component Model（WIT仕様）が安定し、RustコンポーネントをJavaScript/Python等と型安全にコンポーズできる。`cargo component`ツールチェーンが成熟し、マイクロサービス粒度のWASMモジュール設計が現実的になった。

- **WASI Preview 2によるシステムAPI標準化:** WASIがソケット・ファイルシステムの完全サポートを達成し、Rustで書いたサーバーサイドロジックをブラウザ外（エッジ・サーバーレス）でも一切変更なく動作させられる。Cloudflare Workers・Fastlyのネイティブ対応が進行中。

- **Wasmtime/WasmEdgeのAOTコンパイルでネイティブ近接パフォーマンス:** JITではなくAhead-of-Time（AOT）コンパイルを使うことで、Rustで書いたWASMの実行速度がネイティブバイナリの90〜95%に達するケースが報告されている。コールドスタートが課題だったエッジ環境でも起動時間が1ms以下。

- **SIMD・マルチスレッド命令の標準化完了:** Relaxed SIMDとwasm-threads（SharedArrayBuffer経由）が主要ブラウザ・ランタイムで安定。Rustの`std::arch`と`rayon`をWASM向けにコンパイルすることで、画像処理・ML推論などのCPUバウンドタスクで3〜8倍の高速化が得られる。

- **GC提案との組み合わせでメモリ効率が向上:** WasmGC（ガベージコレクション拡張）がRustのlinear memoryと共存できる設計が整備され、RustコンポーネントがJVM/Dart製コンポーネントとメモリを安全に共有できる。ただしRust側はGCに依存しないため、リアルタイム性が要求される部分はRustに任せる設計が最適。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの設計:** 2026年時点では「クライアントコンポーネントは例外」という思想が定着。データフェッチはサーバーサイドに集約し、`'use client'`境界を末端のインタラクション層のみに限定することでバンドルサイズを最小化する。

- **Partial Prerendering (PPR) の本番活用:** 静的シェルと動的ストリームを同一ルートで混在させるPPRが安定化。`<Suspense>`境界の設計がパフォーマンス戦略の中心となり、TTFBと体感速度を両立できる。

- **Server Actions によるAPI層の簡素化:** フォーム処理やミューテーションをServer Actionsに集約することで、従来の`/api`ルートを大幅削減。ただしバリデーション（Zod）とCSRF対策を必ずサーバーサイドで実装すること。

- **`use cache` / `cacheTag` による細粒度キャッシュ制御:** `fetch`レベルではなく関数・コンポーネントレベルでキャッシュを宣言できる新APIが主流に。`revalidateTag`と組み合わせたオンデマンド再検証がCMS連携の標準パターンとなっている。

- **並列ルートと`@`スロットの活用:** モーダル・サイドパネル・ダッシュボードレイアウトを`@slot`で構築するパターンが普及。URLをシェアしつつ複数のUI状態を独立管理できるため、複雑なインタラクションを`window.history`に頼らず実装できる。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Cold Start の実質ゼロ化:** Edge Functionsはエッジノード上でV8 Isolateを再利用するため、従来のサーバーレス関数と比べCold Startがほぼ発生しない。2026年時点でVercelは200+のエッジロケーションを持ち、世界中のユーザーに低レイテンシを提供できる。

- **ポイント2: Fluid Compute との統合が鍵:** VercelのFluid Compute（2025年GA）により、Edge FunctionsとServerless Functionsの境界が曖昧になった。リクエスト処理中に別のリクエストを並列処理できるため、CPUバウンドな処理も効率化され、コスト削減に直結する。

- **ポイント3: Edge Middleware の適切なスコープ設定:** Middlewareをすべてのルートに適用するとレイテンシが蓄積する。`matcher`設定で対象パスを絞り込み、A/Bテスト・認証チェック・リダイレクトのみをエッジで処理するのがベストプラクティス。

- **ポイント4: `next/cache` と `revalidateTag` の活用:** App RouterのData CacheとEdge Functionsを組み合わせることで、エッジキャッシュのオンデマンド無効化が可能。これによりCDN依存のフルキャッシュ戦略からより細粒度なキャッシュ管理に移行できる。

- **ポイント5: Web Standard APIへの準拠が移植性を担保:** Edge RuntimeはNode.js固有のAPIを使えないため、`fetch`・`Request`・`Response`・`crypto`などのWeb Standard APIに統一することで、Vercel依存を下げCloudflare WorkersやDeno Deployへの移植も容易になる。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `type UserId = string & { __brand: 'UserId' }` パターンが広く普及し、プリミティブ型の誤用（IDの混在など）をコンパイル時に防ぐことが2026年のベストプラクティスとして定着している。

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の `satisfies` により、型推論を失わずに型チェックを適用できるようになり、設定オブジェクトやルックアップテーブルの定義が安全かつ柔軟になった。

- **Template Literal Types による API 型付け:** `type Endpoint = \`/api/${string}\`` のようなパターンでルートやイベント名を型安全に扱えるようになり、実行時エラーをビルド時に検出できる範囲が大幅に拡大した。

- **Zod + 型推論の統合:** `z.infer<typeof Schema>` でランタイムバリデーションと静的型を一元管理するアプローチが事実上の標準となり、API境界・フォーム・環境変数などすべての入力点で重複した型定義が不要になった。

- **`noUncheckedIndexedAccess` の有効化:** tsconfig の厳格オプションとして普及が進み、配列・オブジェクトのインデックスアクセスが `T | undefined` として扱われることで、実際のプロダクション障害の主要因の一つを根絶できる。
