# CTO Knowledge - 2026-05-31

## Daily Update (2026-05-31)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチロジックをサーバー側に集約し、`'use client'` は本当にインタラクティブなコンポーネントのみに限定する。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降で安定化したPPRにより、静的シェルを即時配信しつつ動的コンテンツをストリーミングする設計が標準化しつつある。キャッシュ戦略を`Suspense`境界で明示的に制御することが重要。

- **`next/image` と `next/font` による Core Web Vitals 最適化:** LCP改善のために画像は必ず`priority`フラグと適切な`sizes`属性を設定し、フォントはサブセット化して自己ホスティングすることでCLSをゼロに抑える。

- **Edge Runtime とミドルウェアの選択的利用:** 認証チェックやA/Bテスト等のロジックをEdgeに移すことでコールドスタートを削減できるが、Node.js API非対応の制約があるため、重いロジックとの分離設計が必要。

- **Bundle Analyzerとタスクベースのコード分割:** `@next/bundle-analyzer` を CI に組み込み、ルートごとのバンドルサイズを継続監視する。依存ライブラリの肥大化（特にdate-fns、lodash等）を定期的にレビューし、tree-shakingが効いているか確認することが重要。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度設計が鍵:** 2026年時点でRSCストリーミングの実運用では、Suspense境界を細かく設定しすぎるとウォーターフォールが発生しやすく、コンポーネント単位ではなくデータフェッチ戦略ベースで境界を設計するのがベストプラクティスとなっている。

- **PPR（Partial Prerendering）との統合:** Next.js 15以降でPPRが安定化し、静的シェルを即座に配信しつつ動的部分をストリームする構成が本番レベルで採用可能になった。キャッシュ戦略とストリーミングを組み合わせることでTTFBとLCPの両立が実現できる。

- **Server Actionsとの連携でクライアントJSをさらに削減:** フォームやミューテーション処理をServer Actionsに移行することで、ストリーミングSSRと合わせてクライアントバンドルを大幅に圧縮できる。特にモバイルファーストのプロダクトでは体感速度への影響が顕著。

- **エラーバウンダリとローディングUIの設計負債に注意:** ストリーミング採用時に`error.tsx`と`loading.tsx`の設計を後回しにすると、本番障害時のUXが壊滅的になるケースが多い。初期設計段階からルートレベルとコンポーネントレベルの両方を定義しておくこと。

- **Edge Runtimeとの相性:** Cloudflare WorkersやVercel Edge FunctionsでのRSCストリーミングは、Node.js APIの制約から一部のライブラリが動作しない落とし穴がある。2026年現在も`nodejs` runtimeをデフォルトとし、Edgeへの移行は慎重なベンチマーク後に判断するのが安全。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性の標準化:** 2026年時点でtRPCはNext.js/TypeScriptスタックでのデファクトに近づいており、スキーマ定義なしにクライアント・サーバー間の型安全を実現できる点が小〜中規模チームに特に支持されている。

- **GraphQLのユースケース絞り込み:** GraphQLは「外部公開APIや複数クライアントが異なるデータ形状を要求する場合」に特化し、社内BFF的な使われ方は減少傾向。フェデレーション（Apollo/Hive）を使ったマイクロサービス統合が主戦場になっている。

- **RESTはOpenAPI 3.1 + コード生成で再評価:** REST自体は廃れておらず、OpenAPI 3.1仕様 + `orval` や `hey-api` によるクライアントコード自動生成が普及し、型安全面でのtRPCとの差が縮まっている。外部API公開・長期互換性が必要な場面ではRESTが依然として最適解。

- **Edge RuntimeとAPI設計の最適化:** Vercel Edge / Cloudflare Workersの普及により、コールドスタートを避けるために「軽量なREST/tRPC」を選び、ランタイムサイズを意識したAPI設計が求められるようになっている。GraphQLランタイムはEdgeとの相性がまだ課題。

- **AIエージェント連携を見据えたAPI設計:** MCPやOpenAI Function Callingの普及により、APIをAIエージェントから呼びやすい形（明確なスキーマ・セマンティックな命名・適切な粒度）で設計することが新たなベストプラクティスとして浮上している。

### 4. serverless edge computing 2026

- **WebAssembly（WASM）がエッジのデファクトランタイムに:** Cloudflare Workers・Fastly Compute@Edgeを中心にWASMが標準化され、言語非依存でコールドスタートゼロに近い実行環境が実現。V8アイソレートとの併用でセキュリティ境界も明確になった。

- **エッジでのAI推論が主戦場に:** 小型LLM（1B〜7Bパラメータ）をエッジノードで実行するパターンが普及し、レイテンシとプライバシーを両立。中央クラウドへのラウンドトリップなしにリアルタイム応答が可能になっている。

- **Durable Objects／SQLite-at-Edgeによるステートフル化:** かつて「エッジはステートレス」が前提だったが、Cloudflare Durable ObjectsやLiteFS等により、エッジ上でのセッション管理・小規模DB運用が現実的に。アーキテクチャ設計の前提を見直す必要がある。

- **コールドスタート問題の実質的解消とコスト構造の変化:** SnapStart・プリウォーム戦略の成熟により、Lambdaクラスの関数でも初回レイテンシが数十ms台に。ただしエッジの課金モデルはリクエスト数ベースが主流で、常時接続ワークロードはコスト試算に注意が必要。

- **エッジ・オリジン間のデータ整合性がボトルネックに:** CDNエッジへのロジック移行が進むほど、キャッシュ無効化・結果整合性・グローバルstate syncの複雑さが顕在化。EventualConsistencyを許容できる設計かどうかを、機能単位で明示的に判断するアーキテクチャレビューが不可欠。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の標準採用:** パスワードレス認証がデファクトスタンダードとなりつつあり、フィッシング耐性とUX向上を同時に実現できる。Next.js環境では`@simplewebauthn`ライブラリで比較的容易に実装可能。

- **トークンの短命化とリフレッシュ戦略の厳格化:** JWTのアクセストークンは15分以内に短縮し、リフレッシュトークンはローテーション＋失効リスト管理を徹底する。長寿命トークンはセッションハイジャックのリスクが高い。

- **デバイスフィンガープリンティングによる異常検知:** IPだけでなくデバイス特性（UA、タイムゾーン、画面解像度等）を組み合わせた行動分析で、不審なセッション切り替えをリアルタイム検知する。

- **サプライチェーン攻撃対策としての依存ライブラリ監査:** 認証系ライブラリ（NextAuth.js等）は脆弱性が即座に全ユーザーに影響するため、`bun audit`による定期監査とDependabotアラートの即時対応を開発フローに組み込む。

- **ゼロトラスト前提のセッション検証:** 「一度ログインしたら信頼する」から「リクエストごとに検証する」へ移行し、特権操作（メール変更・決済等）には再認証を要求するステップアップ認証を実装する。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x の Edge Runtime 対応成熟:** Prisma Client の Edge対応が安定し、Next.js App Router の Server Components / Server Actions から直接 Supabase Postgres に接続するパターンが標準化。`@prisma/adapter-neon` や `@prisma/adapter-pg` を使ったコネクションプーリングが本番必須。

- **Supabase の Row Level Security (RLS) × Prisma の役割分担:** RLS はデータ層セキュリティの最終防衛線として活用し、Prisma はスキーマ管理・型安全クエリに専念する2層設計が主流。`SET LOCAL role` でサービスロールとユーザーロールを切り替えるパターンが定着。

- **Prisma Migrate vs Supabase Migrations の競合リスク:** Supabase Studio や Edge Functions が生成するマイグレーションと Prisma Migrate が衝突するケースが増加。`prisma db push`（開発）+ `prisma migrate diff`（CI）+ Supabase CLI の組み合わせによる一方向管理が推奨アーキテクチャ。

- **Supabase Realtime × Prisma の非対称性:** Realtime（WebSocket購読）は Prisma では扱えないため、クライアントサイドで `supabase-js` を併用するハイブリッド構成が現実解。読み書きは Prisma、リアルタイム通知は Supabase Realtime と明確に分離する設計が保守性を高める。

- **コネクション上限問題と PgBouncer / Supabase Pooler:** サーバーレス環境でのコネクション枯渇は2026年も最大の運用課題。Supabase の Transaction Pooler（PgBouncer互換）をデフォルト有効化し、Prisma の `connection_limit=1` + `pool_timeout=20` チューニングがベストプラクティスとして定着。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の本格普及:** 2026年はWASI Preview 2がエコシステムに定着し、RustのWasmコンポーネントが言語をまたいで型安全に連携できるようになった。`cargo component`が標準ツールチェーンとして機能し、バックエンドとフロントエンドでコードを安全に共有できる。

- **Wasmtime / WasmEdgeのJITコンパイル最適化:** ランタイム側のAOT/JITが成熟し、ネイティブ速度の90-95%に達するワークロードが増えた。特にCPU負荷の高い計算（画像処理・暗号・シミュレーション）でRust+Wasmは実用的な選択肢になっている。

- **SIMD・スレッド命令のブラウザ標準化完了:** `wasm-simd128`とshared memoryスレッドが全主要ブラウザで安定サポートされ、Rustの`std::arch`やRayonを活用した並列処理がブラウザ上でも動作する。音声・動画処理のクライアントサイド移行が加速。

- **バイナリサイズ問題の実用的解決:** `wasm-opt`（Binaryen）+ `twiggy`によるデッドコード解析 + `panic = "abort"` の組み合わせで、100KB以下のWasmバイナリが現実的になった。`wasm-pack`のデフォルト設定でも初回ロード時間が許容範囲に収まるケースが増加。

- **エッジ・サーバーサイドでのRust Wasmが主流化:** Cloudflare Workers・Fastly Compute・Fermyon Spinなどのエッジプラットフォームでは、RustがWasmのファーストクラス言語として確立。コールドスタートがミリ秒以下で、従来のコンテナ起動コストが不要なため、マイクロサービスの単位として採用が増えている。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** デフォルトでServer Componentsを使用し、インタラクティビティが必要な箇所のみ`'use client'`を付与する。バンドルサイズを大幅に削減でき、初回ロードパフォーマンスが向上する。

- **Partial Prerendering（PPR）の本格活用:** 静的シェルと動的コンテンツを同一ページで混在させるPPRが安定版となり、Suspense境界を活用したストリーミングUIが標準パターンになっている。

- **Server Actions によるデータミューテーション:** APIルートを経由せず、Server Actionsで直接サーバーサイドのデータ操作を行う設計が主流。`useOptimistic`と組み合わせることでUXを損なわずに実装できる。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** `fetch`キャッシュに依存せず、関数・コンポーネント単位で`use cache`を明示的に宣言するパターンが推奨されている。キャッシュタグによる精緻なパージ制御も可能。

- **Parallel Routes + Intercepting Routes によるモーダル設計:** 独立したURLを持ちながらモーダル表示ができるこのパターンは、シェア可能なURLと優れたUXを両立させる。物件詳細ページのようなオーバーレイ表示に特に有効。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの制約を理解した設計:** 2026年現在、Edge FunctionsはNode.js APIの一部（`fs`, `net`等）が使えないため、`@vercel/edge`や`next/server`のWeb標準APIに統一した実装が前提。依存ライブラリのEdge互換性チェックを開発パイプラインに組み込むことが必須。

- **Fluid Compute（動的インスタンス共有）の活用:** VercelのFluid Computeにより、同一インスタンスで複数リクエストを処理できるようになり、コールドスタートのオーバーヘッドが大幅減少。I/Oウェイトが多いAPIエンドポイントほど恩恵が大きく、従来のサーバーレス設計の見直しが有効。

- **KVキャッシュ戦略の最適化:** Vercel KVやEdge Configを組み合わせ、リクエスト単位ではなくエッジノード単位でデータをキャッシュする設計が主流。特にA/Bテストやフィーチャーフラグのような軽量設定データはEdge Configが最適（読み取りレイテンシ <1ms）。

- **Partial Prerendering（PPR）とのハイブリッド活用:** Next.js 15+のPPRによりスタティックシェル＋動的ストリーミングが可能になり、Edge FunctionsはPPRの動的部分のみに集中させるアーキテクチャが効率的。全ページをEdgeで処理するより、責務を明確に分割する設計が推奨。

- **リージョン選択とデータローカリティ:** グローバルエッジ展開時にデータベース（Supabase/PlanetScale等）のリージョンとエッジノードの距離がボトルネックになるケースが増加。`x-vercel-ip-country`ヘッダーを活用したリージョンルーティングで、レイテンシを最小化するデータアクセス戦略が重要。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の定着:** TypeScript 4.9以降の`satisfies`演算子が2026年には標準的なパターンになり、型の絞り込みを保ちながら型安全性を検証できる—`as`キャストの危険な使用を大幅に削減できる。

- **Template Literal Typesの実用化:** 文字列ベースのAPIキーやルートパスを型レベルで表現する手法が成熟し、実行時エラーをコンパイル時に検出できるケースが増加している。

- **`infer`を使った高度なConditional Types:** ライブラリ内部での型推論精度が向上し、外部APIのレスポンス型を`infer`で自動抽出するパターンが普及—手書きの型定義メンテナンスコストを削減。

- **Branded Types（名前付き型）の採用拡大:** `UserId`と`OrderId`が同じ`string`でも混在しないよう`declare const brand: unique symbol`で区別するパターンが、ドメイン駆動設計と組み合わせて広まっている。

- **`noUncheckedIndexedAccess`の標準化:** 2026年時点でこのコンパイラオプションをデフォルト有効にするプロジェクトが増加し、配列・オブジェクトアクセス時の`undefined`見落としによるバグが構造的に防止できる。
