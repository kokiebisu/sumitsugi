# CTO Knowledge - 2026-10-26

## Daily Update (2026-10-26)

### 1. Next.js performance optimization 2026

- **ポイント1: Partial Prerendering (PPR) の本格運用:** Next.js 16ではPPRが安定版となり、静的シェルと動的コンテンツを1つのレスポンスで配信できる。`listing`詳細ページのような「ヘッダーは静的・在庫状況は動的」という構成に最適で、TTFBを大幅短縮できる。

- **ポイント2: キャッシュ戦略の明示化（`use cache`ディレクティブ):** Next.js 16で導入された`use cache`により、関数・コンポーネント単位でキャッシュ境界を明示できる。暗黙的キャッシュによる不整合（物件ステータス`draft`/`public`切り替え時の反映遅延など）を防ぎやすくなる。

- **ポイント3: Turbopackのビルド高速化を前提にしたDX最適化:** Turbopackが本番ビルドでも標準化され、`bun run build`の時間が短縮される。CI時間短縮に直結するため、ビルド検証を軽視せず積極的に活用すべき。

- **ポイント4: Server Actionsのペイロード最適化:** フォーム送信（引越し費用の見積り送信など）でServer Actionsを使う際、過度なシリアライズコストに注意。Zodスキーマでの境界検証と組み合わせ、必要最小限のデータのみをクライアント・サーバー間でやり取りする設計が重要。

- **ポイント5: 画像・フォントの自動最適化とCore Web Vitals:** `next/image`のAVIF優先配信とレイアウトシフト対策が標準化されており、物件写真が多いプラットフォームでは特にLCP改善効果が大きい。モバイル回線での前の住人の物件一覧表示速度に直結する。

### 2. React Server Components streaming 2026

- **ポイント1:** React 19以降、`loading.tsx`やSuspenseバウンダリによるストリーミングSSRが標準化し、ファーストバイトまでの時間（TTFB）を犠牲にせず段階的にUIを表示できるようになった。重い物件データ取得と軽量なヘッダー/ナビゲーションを分離し、後者を即時表示することでLCPを大幅改善できる。

- **ポイント2:** Server ComponentsとClient Componentsの境界設計が依然最大の難所で、`'use client'`境界を不必要に浅く引くとバンドルサイズが肥大化する。物件一覧ページのようなインタラクティブ要素（フィルタ、お気に入りボタン）だけをClient Componentに切り出し、データ取得・レンダリングはServer Componentに残す設計が効果的。

- **ポイント3:** Partial Prerendering（PPR）がNext.js 16で本格的に使えるようになり、静的シェル＋動的ストリーミングのハイブリッドが1ルートで実現可能。物件詳細ページなど「静的な外枠＋動的な空室状況」のようなパターンに最適。

- **ポイント4:** ストリーミング下でのエラーハンドリングが重要論点に。`error.tsx`境界をSuspense境界ごとに細かく配置しないと、1箇所のデータ取得失敗がページ全体をクラッシュさせるリスクがある。本番導入前にE2Eで意図的な障害注入テストを行うべき。

- **ポイント5:** キャッシュ戦略（`fetch`のrevalidate、`unstable_cache`、Server Actionsとの連携）がストリーミングのパフォーマンスを左右する。物件データのような更新頻度が低いコンテンツはISR寄りの長めのrevalidateを設定し、リアルタイム性が必要な箇所のみ動的ストリーミングに委ねる住み分けが望ましい。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはTypeScriptフルスタック構成（Next.js + Bun）において型安全性とスキーマ定義の手間削減を両立できるため、小〜中規模チームでのAPI層として採用が広がっている。sumitsugiのようなNext.js App Router構成では、クライアント/サーバー間の型共有が自然に行えるメリットが大きい。

- **ポイント2:** GraphQLは複数クライアント（Web/モバイル/パートナー連携）が存在し、過剰取得・不足取得を避けたい場合に強みを発揮するが、単一フロントエンドのみの構成ではオーバーヘッドになりやすい。現状の物件情報プラットフォームのようにUIがほぼ単一であればREST/tRPCで十分なケースが多い。

- **ポイント3:** RESTは依然としてキャッシュ戦略（CDN/HTTPキャッシュ）やサードパーティ連携（決済、外部弁護士向け書類生成API等）との相性が最も良く、2026年時点でも「公開API・Webhook・外部連携」の領域ではデフォルト選択肢として残っている。

- **ポイント4:** 2026年の潮流として、BFF（Backend For Frontend）層を薄いtRPCルーターとして実装し、内部はRESTやDBアクセスに委譲する「ハイブリッド構成」が増えている。認証（auth-context.tsx）やステータス管理（draft/public）のような境界ロジックをBFF層に集約すると、型安全性とZodによる入力検証を一箇所で担保できる。

- **ポイント5:** スキーマファースト開発（Zod→OpenAPI/tRPCルーター自動生成）が標準化しつつあり、APIドキュメントの陳腐化を防ぐ観点からも、Zodスキーマを単一のソース・オブ・トゥルースとして扱う設計がベストプラクティスになっている。

### 4. serverless edge computing 2026

## エッジコンピューティング 2026 — CTO視点での注目トレンド

- **コールドスタート問題の実質的解消:** V8 isolateベースのランタイム（Cloudflare Workers、Deno Deploy等）がさらに進化し、ミリ秒未満の起動が標準化。sumitsugiのような物件検索API（レスポンス速度がUX直結）では、リージョンエッジでのSSRキャッシュ戦略を見直す価値がある。

- **エッジでのステートフル処理が実用域に:** Durable Objects / edge KVの成熟により、予約ロックやリアルタイム在庫管理のような強整合性が必要な処理もエッジで扱えるようになってきた。内見予約の同時枠管理などに応用余地あり。

- **AIワークロードのエッジ推論シフト:** 小型モデル（distilled/quantized）をエッジで推論させるパターンが普及。物件レコメンドや簡易チャット応答をエッジ側で処理すればオリジンへの往復コストを削減できる。

- **コスト構造の変化に要注意:** リクエスト課金からCPU時間課金への移行が進み、重い処理（画像変換、PDF生成）をエッジに置くと想定外のコスト増になりやすい。引越しコスト計算のような計算負荷が高い処理はオリジン/バックグラウンドジョブに残す判断が重要。

- **Next.js 16とのエッジ統合がより自然に:** App RouterのEdge Runtime対応が安定し、Vercel以外（Cloudflare, Fastly）でも同等のAPIが使えるようになった。ベンダーロックインを避けつつエッジ化する選択肢が増えている。

### 5. authentication security best practices 2026

- **パッキー認証とパスワードレス化の加速:** FIDO2/WebAuthnベースのパスキーが標準になりつつあり、フィッシング耐性の高い認証をデフォルトにすることで、パスワード漏洩由来のインシデントを大幅に減らせます。実装コストは下がっているため、新規サインアップフローから優先導入すべきです。

- **多要素認証(MFA)の「適応型」化:** 固定的な2FAより、デバイス・位置情報・行動パターンに基づくリスクベース認証(Adaptive MFA)が主流になっており、ユーザー体験を損なわずに不正ログインを検知できます。弁護士確認中の個人情報保護方針とも整合させやすい設計です。

- **トークン管理のゼロトラスト化:** JWTの長期有効化を避け、短命アクセストークン＋リフレッシュトークンのローテーション、サーバーサイドでの即時失効（revocation）をサポートする設計が必須です。セッション管理の脆弱性はOWASP Top10でも依然上位のため、`src/contexts/auth-context.tsx`のようなクライアント側状態管理は最小限の情報のみ保持する方針が安全です。

- **サプライチェーン・依存ライブラリの認証周り監査:** OAuth/SSOライブラリや認証SDKの脆弱性が年々増加しているため、依存パッケージの定期的な脆弱性スキャン（`bun audit`等）と、認証関連コードは`security-reviewer`エージェントによるレビューを必須化する運用が有効です。

- **監査ログとレート制限の標準装備:** ログイン試行・パスワードリセット・MFA変更などのセキュリティイベントは構造化ログで記録し、ブルートフォース対策としてIP/アカウント単位のレート制限を全エンドポイントに適用することが2026年のベースラインです。引っ越し費用決済など金銭が絡むフローでは特に重要です。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMの進化（Rust脱却とパフォーマンス改善）:** Prisma 6以降でRustベースのクエリエンジンから純TypeScript実装への移行が進み、コールドスタートの高速化とエッジランタイム（Vercel Edge, Cloudflare Workers）対応が強化されている。サーバーレス環境でのDB接続はPrisma Accelerate等のコネクションプーリング層を併用するのが実質必須。

- **SupabaseのPostgres拡張活用:** Row Level Security (RLS) を使った認可ロジックのDB層への移譲が標準化しつつあり、アプリケーション側の権限チェックとDB側のRLSポリシーを二重管理しないよう、認証コンテキスト（`auth.uid()`等）を軸に設計を統一すべき。pgvectorによるベクトル検索もSupabase上で一般化している。

- **マイグレーション運用の自動化:** Prisma MigrateとSupabase CLIのマイグレーション管理は競合しやすいため、どちらか一方を「真実のソース」とし、CI/CDパイプラインで`prisma migrate deploy`またはSupabase migrationsのいずれかに統一する運用がベストプラクティス。本プロジェクトのような小規模チームでは複雑化を避けるため一本化が重要。

- **コネクションプーリングとサーバーレスの相性:** Next.js App Routerのサーバーレス関数は短命なコネクションを多数生成しやすく、SupabaseのPgBouncer（Transaction mode）やPrisma AccelerateでDB接続数の上限枯渇を防ぐ設計が前提になっている。ローンチ前には本番相当の同時接続数でのロードテストを推奨。

- **型安全性とZodとの連携:** Prismaが生成する型とZodスキーマ（システム境界での入力検証）を重複定義せず、`zod-prisma-types`等で自動生成する構成がTypeScriptプロジェクトで広く採用されており、本プロジェクトの「Zodスキーマによる境界検証」方針とも整合する。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASM GC提案の標準化が進み、Rustでも`wasm-bindgen`を介さない軽量なメモリ管理パターンが普及。バイナリサイズが従来比20-30%削減でき、初回ロード時間の改善に直結する。
- **ポイント2:** Component Model（WASI Preview 2）の実用化により、Rust製WASMモジュール同士の相互運用が容易になり、フロントエンドの重い処理（画像処理・PDF生成など）をマイクロモジュール単位で切り出しやすくなった。
- **ポイント3:** SIMD命令のブラウザ対応がほぼ出揃い、Rustの`std::simd`やcrateレベルでの最適化だけでネイティブに近い並列計算性能が得られるため、物件検索のフィルタリングや画像処理をクライアント側に寄せる選択肢が現実的になっている。
- **ポイント4:** `wasm-pack`やViteのWASMプラグインが成熟し、Next.js 16のApp Routerとの統合もシンプルになったため、小規模チームでも「パフォーマンスが本当に必要な箇所だけRustに切り出す」ハイブリッド構成が採用しやすい。
- **ポイント5:** 一方でデバッグ・プロファイリングのツールチェーンはまだJS/TSほど成熟していないため、導入は「ボトルネックが明確な処理（例: 大量物件データのソート・集計）」に限定し、全面的なWASM化は時期尚早という判断が妥当。

### 8. Next.js App Router patterns 2026

- **ポイント1（Partial Prerendering の標準化）:** Next.js 15以降で導入されたPPRが2026年には主流パターンとなり、静的シェルを即時配信しつつ動的部分のみSuspenseでストリーミングする構成が標準化。これにより初期表示速度とパーソナライズ性を両立できる。
- **ポイント2（Server Actions中心の設計）:** API Routesを個別に書くのではなくServer Actionsでミューテーションを完結させる設計が定着し、フォーム送信や予約フローなど多段階操作のコードベースが大幅に簡素化される一方、キャッシュ無効化（`revalidatePath`/`revalidateTag`）の設計ミスが本番バグの主要原因になりやすい。
- **ポイント3（キャッシュ戦略の明示化）:** Next.js 15でデフォルトキャッシュ挙動が「明示的オプトイン」に変わったため、`fetch`のキャッシュ指定やルートごとの`dynamic`/`revalidate`設定を意識的に書く必要があり、暗黙のキャッシュに依存した実装は事故につながる。
- **ポイント4（Server/Client Componentsの境界設計）:** 認証状態やユーザー固有データを扱うコンポーネント境界を早期に設計することが重要で、`auth-context.tsx`のようなクライアント状態とServer Componentのデータ取得を安易に混在させるとハイドレーションエラーや再フェッチの無駄が発生しやすい。
- **ポイント5（Edge/Node runtimeの選択的使用）:** 物件一覧や検索などレイテンシ重視のページはEdge Runtimeで配信し、決済や重い処理を伴うページはNode Runtimeに残すというハイブリッド運用が一般化しており、全ページ一律の設定は避けるべき。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Vercel Edge FunctionsはV8 isolateベースのため、Cold Startがほぼゼロに近く、レイテンシが重要なAPI（認証チェック、A/Bテスト振り分け）に適している。ただしNode.js APIの一部（`fs`等）が使えないため、実装前に対応ランタイムの確認が必須。

- **ポイント2:** 2026年時点でVercelはEdge Middlewareの実行コストを使用量ベースで課金する方向を強めており、全ページにMiddlewareを適用する設計は無駄なコストを生みやすい。`matcher`設定でパスを絞り込むことがコスト最適化の基本になる。

- **ポイント3:** Edge RuntimeとNode.js Runtimeの使い分けが重要で、DB接続（Prisma等の一部ORM）はEdgeで制約があるため、データ取得が必要なルートはNode.js Runtime、認証・リダイレクト・ジオロケーション判定などの軽量処理はEdge Runtimeに寄せる構成が定石。

- **ポイント4:** Vercelの`@vercel/edge-config`のようなEdge-nativeなKVストアを使うことで、フィーチャーフラグや物件ステータス（`draft`/`public`）の切り替えをEdgeから低レイテンシで読めるようになり、sumitsugiのような物件公開/非公開制御に応用できる余地がある。

- **ポイント5:** Streaming SSR（React Server Components + Edge）はTTFBを大幅に改善するが、日本語フォントやレイアウトシフトの影響でCLS/LCPが悪化するケースがあるため、Edgeでの最適化はCore Web Vitals計測とセットで評価すべき。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x系で導入された`const`型パラメータや`satisfies`演算子の活用が標準化し、型推論を狭めつつ冗長な型注釈を減らすパターンが定着している。型の「書く量」を減らしながら安全性を保てるのが実用上の利点。
- **ポイント2:** Zodなど実行時スキーマからTypeScript型を自動生成する「Schema-first」アプローチが、APIバウンダリやフォームバリデーションの標準パターンになっている。本プロジェクトのZod活用方針（システム境界での入力検証）とも一致し、型と実行時検証の二重管理を避けられる。
- **ポイント3:** Branded Types（nominal typing）を使った型の意味的区別（例: `UserId`と`PropertyId`を同じ`string`でも混同しないようにする）が、特にドメインモデルが複雑なプロダクトで採用が増えている。`seller`/`listing`のような内部データ構造が多い本プロジェクトでは、ID混在バグの防止に有効。
- **ポイント4:** `unknown`優先・`any`完全排除のLintルール運用が業界標準になりつつあり、ESLintの`@typescript-eslint/no-explicit-any`を厳格化するチームが増えている。型安全性のリグレッションを防ぐガードレールとして、CIでの型チェック必須化（本プロジェクトの`bun run build`必須ルールと同方向）が重要。
- **ポイント5:** テンプレートリテラル型とユーティリティ型を組み合わせたAPIルート・URLパスの型安全な生成（type-safe routing）が、Next.js App Routerプロジェクトで広がっている。ページ構造が`src/app/`配下で増えていく本プロジェクトでも、ルート文字列のタイポ防止に応用価値がある。
