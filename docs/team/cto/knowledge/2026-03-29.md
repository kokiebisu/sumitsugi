# CTO Knowledge - 2026-03-29

## Daily Update (2026-03-29)

### 1. Next.js performance optimization 2026

- **PPR（Partial Prerendering）の本格活用:** Next.js 15以降でPPRが安定化し、静的シェルと動的コンテンツを同一ルートで混在させることでTTFBを大幅短縮できる。Suspense境界の設計がパフォーマンスの鍵。

- **React Server Componentsのバンドルサイズ削減:** RSCにより重いライブラリをサーバーサイドに閉じ込め、クライアントJSを最小化。`"use client"`の境界を慎重に設計し、不必要なハイドレーションコストを避けることが重要。

- **`next/image`と`next/font`の徹底活用:** 画像の自動最適化（AVIF/WebP）とフォントのself-hostingはCLS・LCPに直結。`sizes`属性の適切な指定とpriority設定でCore Web Vitalsスコアを最大化できる。

- **Route Groups + Parallel Routesによるコード分割戦略:** `(group)`構文でレイアウト境界を細かく制御し、不要なJS読み込みを遅延。`loading.tsx`とStreaming SSRの組み合わせで体感速度を向上させる。

- **キャッシュ戦略の再設計（Next.js 15のキャッシュ変更対応）:** Next.js 15でfetch・RouterCache・DataCacheのデフォルト動作が変更された。`revalidate`や`unstable_cache`を明示的に設定し、意図しないキャッシュミスやオーバーフェッチを防ぐ設計が必須。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化:** 2026年時点でRSCストリーミングはSuspense境界の設計が性能の鍵となっており、コンポーネント単位で細かく分割することでTTFB（初回バイト転送時間）を大幅に短縮できる。

- **PPR（Partial Prerendering）の本格普及:** Next.js 15以降でPPRが安定版となり、静的シェルを即時配信しつつ動的部分をストリーミングするハイブリッド戦略が実務標準になりつつある。

- **Server Actionsとの統合による往復削減:** RSCストリーミングとServer Actionsの組み合わせにより、フォーム送信・ミューテーション後の再レンダリングがクライアント→サーバー往復を最小化しながら差分ストリームで返せるようになった。

- **キャッシュ戦略の複雑化に注意:** `fetch`レベルのキャッシュ、ルートレベルキャッシュ、`unstable_cache`が混在し、ストリーミング環境では期待通りに動作しないケースが増加している。キャッシュ無効化の設計はアーキテクチャ初期段階で明示的に決定すべき。

- **エッジランタイムとの相性:** Cloudflare WorkersやVercel Edge Runtimeでのストリーミング対応が成熟し、Node.jsランタイムより低レイテンシを実現できるが、Node.js専用APIへの依存があるライブラリとの互換性確認が依然として必須。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全APIの標準化:** TypeScript フルスタック環境では tRPC が事実上の標準になりつつあり、スキーマ定義なしにクライアント・サーバー間の型共有が実現できるため、Next.js + Prisma 構成での開発速度が大幅に向上している。

- **GraphQLの適用範囲の絞り込み:** 複数クライアント（Web/モバイル/サードパーティ）が同一データを異なる形状で消費するケースに限定されてきており、単一クライアントのプロジェクトでは over-engineering として避けられる傾向が強まっている。

- **REST + OpenAPI の再評価:** AI コードアシスタントとの相性から OpenAPI スキーマの価値が見直されており、`zod-openapi` や `@hey-api/openapi-ts` を使った型生成パイプラインが REST を型安全に保つ現実解として浸透している。

- **エッジ・ストリーミング対応がAPI設計の必須要件に:** Vercel Edge / Cloudflare Workers の普及により、長時間レスポンスは SSE または ReadableStream で返す設計が前提となり、従来の JSON REST では LLM 応答やリアルタイム更新に対応しきれない場面が増えている。

- **API契約駆動開発（Contract-First）の復権:** チーム間の独立デプロイが当たり前になった結果、スキーマをコードより先に定義・バージョン管理する Contract-First アプローチが再注目されており、breaking change 検出を CI に組み込むことがプロダクション品質の指標になっている。

### 4. serverless edge computing 2026

- **エッジでのAI推論の本格化:** 2026年はLLMの量子化・蒸留技術の成熟により、Cloudflare Workers AIやVercel Edge Functionsでのリアルタイム推論が実用水準に達し、レイテンシ敏感なアプリでのオンデバイス→エッジへのシフトが加速している。

- **WASMがポータビリティのデファクトに:** WebAssemblyがコンテナに代わるエッジ実行単位として定着し、言語非依存で起動数μsのコールドスタートを実現。WASIp2の標準化でI/O抽象化も整い、マルチクラウドエッジ展開のロックイン問題が緩和されつつある。

- **SQLite-at-the-Edgeパターンの普及:** Cloudflare D1・Turso・LiteFS等により、エッジリージョンにSQLiteレプリカを配置するアーキテクチャが一般化。読み取り主体のワークロードでは中央DBへのラウンドトリップが不要になり、グローバルアプリの設計パターンが大きく変わった。

- **エッジファーストのオブザーバビリティが課題:** 分散エッジ環境では従来のAPMツールが追従できず、OpenTelemetryのエッジ対応とログ集約コストの最適化が実務上の痛点。トレーシングのサンプリング戦略をエッジ層で適切に設計しないと、可観測性コストがインフラコストを超えるケースがある。

- **セキュリティ境界の再定義:** エッジでのリクエスト処理増加に伴い、WAF・レート制限・Bot検知がエッジ層の責務として標準化。一方でシークレット管理（環境変数のエッジへの配布）とサプライチェーンリスク（npmパッケージのエッジバンドル）への対策が新たなセキュリティ設計の必須要件になっている。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準採用:** FIDO2/WebAuthnベースのパスキーがパスワード認証を置き換えつつあり、フィッシング耐性と利便性を両立できる。2026年時点でGoogle・Apple・Microsoftのエコシステム全体で実用レベルに達している。

- **ゼロトラスト＋継続的認証:** 「一度認証したら信頼する」モデルは廃止傾向。セッション中もリスクスコアを継続評価し、異常行動検知時に再認証を要求するアダプティブ認証が主流化。

- **MFAの必須化とリカバリーフロー強化:** SMS OTPはSIMスワップ攻撃に脆弱なため、TOTPやハードウェアキー（YubiKey等）への移行が推奨。合わせてアカウントリカバリー経路がバイパスとして悪用されるケースが増加しており、リカバリーフロー自体のセキュリティ設計が重要。

- **トークン管理のセキュリティ強化:** JWTの有効期限を短く設定しリフレッシュトークンをローテーション必須に。また`httpOnly` + `Secure` Cookie戦略をXSS対策として徹底し、トークンをlocalStorageに保存するアンチパターンを排除する。

- **サプライチェーン攻撃対策としての依存関係監査:** 認証ライブラリ（NextAuth、Passport等）は攻撃者の標的になりやすく、依存パッケージのSBOM管理とCIでの自動脆弱性スキャン（`bun audit`等）をパイプラインに組み込むことが不可欠。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応成熟:** Prisma 6はEdge/Serverless環境でのコネクションプーリング（Prisma Accelerate）が実用レベルに達し、Supabase + Next.js App RouterのServerless構成でも安定したパフォーマンスが得られるようになった。

- **Supabase Auth + RLSの組み合わせがデファクト化:** Row Level Security（RLS）をPrismaから直接活用するパターンが普及し、アプリ層でのアクセス制御ロジックをDB層に移譲することで、セキュリティ漏れのリスクを構造的に低減できる。

- **Realtime + pgvectorの統合が加速:** SupabaseのRealtime機能とpgvector拡張を組み合わせたベクトル検索＋リアルタイム同期アーキテクチャが台頭しており、AIチャットやレコメンデーション機能のインフラとして採用が増加している。

- **型安全性の強化でPrismaのスキーマ駆動開発が主流に:** `prisma generate`による自動型生成をCI/CDに組み込み、DBスキーマとアプリコードの型不整合をデプロイ前に検出するワークフローが標準化されつつある。

- **Supabase Branchingによるプレビュー環境の普及:** PR単位でDBブランチを自動作成するSupabase Branchingが安定化し、PrismaのマイグレーションをCI上で検証するフローが組みやすくなった。本番同等のDBでE2Eテストを回すことが現実的なコストで実現できる。

### 7. WebAssembly Rust performance 2026

- **Component Model の本格普及:** WASI 0.2とWasm Component Modelが2025年末に安定化し、Rustで書いたWasmコンポーネントを言語間で安全に合成できるようになった。これによりマイクロサービス的なWasmアーキテクチャが現実的な選択肢になっている。

- **GCなしでのパフォーマンス優位性が継続:** RustのゼロコストアブストラクションとWasmの線形メモリモデルの相性は依然として最良で、JVM/Go製Wasmと比べてコールドスタート・メモリフットプリントで2〜5倍の差が出るケースが多い。

- **SIMD・スレッドサポートの成熟:** Wasm SIMDとShared Memoryがほぼ全ランタイム（V8, Wasmtime, WasmEdge）で安定サポートされ、Rustの`rayon`や`packed_simd`を活用したCPU集約処理がWasm上でもネイティブの70〜90%性能に達するようになった。

- **Wasmtime + Cranelift vs. V8の選択:** エッジ・サーバーサイドではWasmtime（Craneliftバックエンド）がコンパイル速度とセキュリティ分離で優れ、ブラウザ用途ではV8のTurbofanが最適化深度で勝る。用途に応じたランタイム選定がアーキテクチャの重要な意思決定になっている。

- **ビルドサイズ最適化が開発標準に:** `wasm-opt`（Binaryen）+ `twiggy`によるサイズ分析、`wee_alloc`から`dlmalloc`への移行、LTOとstrip設定の組み合わせで、本番Wasmバイナリを200KB以下に抑える運用が定着している。CI/CDにサイズ回帰チェックを組み込むことが推奨される。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点でApp Routerの主流はServer Components優先設計。`'use client'`は状態・イベントハンドラが必要な末端コンポーネントのみに限定し、バンドルサイズを最小化する。

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降でStableになったPPRにより、静的シェル＋動的ストリーミングを1ルートで混在させられる。`<Suspense>`境界の設計がパフォーマンスの鍵。

- **Server Actions によるフォーム処理の統一:** API Routeを経由せずServer Actionsで直接DB操作が可能になり、`useFormState`/`useFormStatus`と組み合わせたプログレッシブエンハンスメントが標準パターンに。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** Next.js 15で導入された`use cache`により、関数・コンポーネント単位でキャッシュ戦略を宣言的に定義できる。`revalidateTag`と組み合わせてオンデマンド無効化を設計する。

- **Parallel Routes + Intercepting Routes でモーダル設計を標準化:** `@modal`スロットとインターセプトルートを活用することで、URLを保持したまま詳細モーダルを実装でき、SEOとUXを両立した設計が容易になった。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択的活用:** Edge FunctionsはNode.js Runtimeより起動が速い（Cold start ~0ms）が、利用可能なAPIが制限されるため、認証・リダイレクト・A/Bテストなど軽量ロジックに絞って使うのが最適解。

- **Middleware最小化の原則:** `middleware.ts`はすべてのリクエストに適用されるため、重いロジックを置くとレイテンシが増大する。`matcher`で対象パスを絞り込み、処理は10ms以内を目標にする。

- **KV・D1との組み合わせ:** Vercel KV（Redis互換）やCloudflare D1をEdgeから参照するパターンが2026年の主流。データをEdge近くに置くことでRTTを最小化し、データベース接続プールの枯渇問題を回避できる。

- **Streaming Responseの積極活用:** Edge FunctionsでのStreaming（`ReadableStream`）により、AIレスポンスや大量データを分割送信し、TTFB（Time to First Byte）を大幅に改善できる。Next.js App RouterのServer Componentsと相性が良い。

- **観測性（Observability）の強化:** Edge環境は従来のAPMツールが使いにくいため、Vercel Analytics・OpenTelemetry対応の`@vercel/otel`を早期導入し、分散トレーシングでボトルネックを可視化することが運用コスト削減の鍵。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の本格活用:** TypeScript 4.9以降の `satisfies` により、型推論を保ちながら型チェックを適用できるため、`as` キャストによる型安全性の欠損を排除するパターンが標準化されつつある。

- **Branded Types によるドメイン境界の強化:** `UserId` と `OrderId` を同じ `string` として扱うミスを防ぐため、Branded/Opaque Types パターンが実運用での採用が加速しており、実行時コストゼロで型レベルの不変条件を表現できる。

- **`noUncheckedIndexedAccess` の有効化が必須化:** 配列・オブジェクトインデックスアクセスの戻り値を `T | undefined` として扱うこのオプションが、セキュリティ・安全性重視のチームで必須設定となり、ランタイムエラーの大幅削減に寄与している。

- **Zod + tRPC による型のエンドツーエンド伝播:** API境界でのランタイムバリデーションと型生成を一体化する構成が成熟し、フロント・バック間の型ズレによるバグがほぼゼロになるアーキテクチャが一般化している。

- **`using` キーワード（Explicit Resource Management）の普及:** TypeScript 5.2の `using` / `await using` 構文により、DB接続・ファイルハンドル等のリソース管理を型安全かつ宣言的に記述できるようになり、リソースリークのレビュー負担が軽減されている。
