# CTO Knowledge - 2026-11-04

## Daily Update (2026-11-04)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Prerendering / Cache Components）:** Next.js 15以降で導入されたPPRとキャッシュ指定APIが成熟し、ページ単位ではなくコンポーネント単位で静的/動的を混在させられるようになった。静的シェルを即時配信しつつ動的部分だけストリーミングすることで、TTFBとLCPを大きく改善できる。
- **ポイント2（Turbopackのデフォルト化）:** `bun dev`/`bun run build`でのビルドがTurbopackベースに移行し、Webpack比で大幅にコールドスタート・HMRが高速化。大規模なapp/配下（properties/, listing/, account/）でも開発体験の劣化が起きにくくなっている。
- **ポイント3（Server Actionsのキャッシュ戦略）:** `revalidateTag`/`revalidatePath`の粒度管理が重要度を増しており、物件データ（`draft`/`public`ステータス）のような頻繁に更新されるリソースは、タグ単位の無効化で不要な再レンダリングを避けるべき。
- **ポイント4（画像・フォント最適化の自動化）:** `next/image`のAVIF優先配信とレイアウトシフト抑制、`next/font`のセルフホスティングが標準化され、物件写真が多いUIでは明示的なサイズ指定とpriority属性の使い分けがCore Web Vitalsに直結する。
- **ポイント5（React Compiler統合）:** React Compilerの本番採用が進み、`useMemo`/`useCallback`の手動最適化が不要になるケースが増加。ただし既存コードの依存配列ミスが compiler前提の再レンダリング挙動と噛み合わないケースがあるため、移行時は段階的な検証が必要。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** RSCのストリーミングは`loading.tsx`やSuspense境界を使ったNext.js App Routerの標準パターンとして定着しており、初期表示（TTFB）を犠牲にせず段階的にUIを配信できる。本プロジェクトのproperties一覧やlisting詳細ページのような重いデータ取得部分は、骨組みを先に出してSuspenseで個別にストリームすることでLCPを改善できる。

- **Partial Prerendering (PPR) の実用化:** 静的なシェル部分をビルド時に生成しつつ、動的部分だけをリクエスト時にストリームするPPRがNext.js 15/16系で安定運用レベルに達している。物件詳細ページのように「物件情報は静的寄り、お気に入り状態や予約可否は動的」という構成に特に適しており、キャッシュ戦略とユーザー別パーソナライズを両立できる。

- **Server Actionsとの統合深化:** フォーム送信やミューテーション後のリフレッシュがRSCストリーミングと組み合わさり、`useActionState`やoptimistic UIパターンが主流になっている。前の住人⇄次の住人間の引継ぎフローのような多段階フォームでは、Server Actions + ストリーミング更新でクライアントJSを最小限に抑えつつUXを損なわない実装が可能。

- **Client Componentの境界設計がパフォーマンスの決定要因に:** RSCではバンドルサイズそのものよりも「どこでClient Componentの境界を切るか」が重要で、認証状態やインタラクティブ要素（お気に入りボタン、フィルタUI）を細かく切り出すほどストリーミングの恩恵を受けやすい。`auth-context.tsx`のようなグローバルなClient Context は、ツリー全体をクライアント化してしまうアンチパターンになりやすいので注意が必要。

- **キャッシュの明示的制御（`use cache`ディレクティブ）:** Next.jsのキャッシュ戦略が暗黙的な自動キャッシュから`'use cache'`による明示的指定に移行しつつあり、物件データのような更新頻度が低いコンテンツと、予約状況のような即時性が求められるデータを明確に区別して扱う必要がある。draft/public状態の切り替えを伴う物件ステータス管理では、キャッシュ無効化のタイミング設計が特に重要になる。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCがBFF層でのデファクトとなり、Next.js App Router構成ではREST/GraphQLを介さずクライアント〜サーバー間の型を直接共有するパターンが主流化している。sumitsugiのようなフルスタックNext.js構成では、`src/lib`の型定義をそのままAPI契約として使い回せる利点が大きい。
- **ポイント2:** GraphQLは依然としてマルチクライアント（Web/モバイル/パートナー連携）が必要な大規模プラットフォームで選ばれるが、単一フロントエンドのみのプロダクトではオーバーヘッドと判断され、tRPC/REST+Zodへの「縮退」が2026年のトレンド。
- **ポイント3:** RESTは外部公開API・Webhook・サードパーティ連携の標準として残り続けており、内部通信はtRPC、外部公開はREST(OpenAPI)という「ハイブリッド戦略」が一般化している。
- **ポイント4:** Zodなどのスキーマ定義を型生成とランタイム検証の両方に使う「スキーマファースト」設計が、API層の重複実装を減らす実用的アプローチとして定着（本プロジェクトの標準規約とも合致）。
- **ポイント5:** エッジランタイム（Vercel Edge, Cloudflare Workers）の普及により、API設計時点でコールドスタート・レイテンシを意識したペイロード最小化が重要な評価軸になっている。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** CloudflareのWorkers、Deno Deploy、Vercel Edge FunctionsなどがWinterCG/WinterTC仕様に収束し、V8 isolateベースの軽量実行環境がデファクトスタンダード化。移植性が高まり、ベンダーロックインのリスクが低下している。

- **コールドスタート問題の実質的解消:** V8 isolate方式により起動時間がミリ秒単位になり、従来のコンテナ型サーバーレス（Lambda等）との差が明確化。低レイテンシが求められるSSR/API Routeのエッジ配置が実用レベルに達している。

- **エッジでのデータレイヤー統合:** D1 (SQLite)、Turso、PlanetScaleなどエッジネイティブなDBレプリケーション技術が成熟し、計算とデータの地理的近接性を両立。グローバル分散時のレイテンシ・一貫性トレードオフの設計判断が重要になっている。

- **Next.js 16とエッジの親和性向上:** App Routerのミドルウェア・部分的プリレンダリング(PPR)がエッジ実行を前提に最適化されており、sumitsugiのようなVercelデプロイ前提のプロジェクトでは追加設定なしでエッジ恩恵を受けられる構成が標準になりつつある。

- **コスト構造の変化への注意:** リクエスト数課金からCPU時間課金への移行が進み、計算量の多い処理（画像変換、PDF生成等）はエッジでの実行コストが読みにくい。ベータローンチ前の段階では、重い処理は従来のサーバーレス関数に残し、軽量な認証チェックやリダイレクトのみエッジに置く選択的な設計が安全。

### 5. authentication security best practices 2026

- **ポイント1:** パスキー（FIDO2/WebAuthn）の採用が2026年には標準化しつつあり、フィッシング耐性のある認証をデフォルトにすることで、パスワード漏洩由来の侵害リスクを大幅に低減できる。

- **ポイント2:** セッション管理はJWTの単純な長期発行を避け、短命アクセストークン＋リフレッシュトークンのローテーション、デバイスバインディングを組み合わせることで、トークン盗用時の被害範囲を限定すべき。

- **ポイント3:** 認可ロジックは認証と明確に分離し、リソース単位でのアクセス制御（RBAC/ABAC）をサーバーサイドで一貫して検証する必要がある。クライアント側のみの制御はBOLA/IDOR脆弱性の温床になる。

- **ポイント4:** レート制限・異常検知（impossible travel、ブルートフォース検知）をログイン・パスワードリセットエンドポイントに必須実装し、インシデント発生時のトレーサビリティ確保のため認証イベントは構造化ログで監視基盤に送る。

- **ポイント5:** シークレット管理は環境変数経由で行い、ハードコードを徹底排除。CI/CDパイプラインにシークレットスキャン（gitleaks等）を組み込み、コミット前に検出する仕組みを標準化する。

### 6. database architecture Prisma Supabase 2026

- **コロケーション戦略の重要性:** PrismaとSupabaseを組み合わせる際は、Prisma ORMのコネクションプーリング設定（PgBouncer経由）とSupabaseのPoolerモードを正しく噛み合わせないと、サーバーレス環境でコネクション枯渇が起きやすい。本番ではSupabaseのTransaction Pooler + Prisma Accelerateの併用がデフォルト構成になりつつある。

- **Row Level Security (RLS) とORMの責務分離:** Supabaseの強みはPostgresのRLSでDB層に認可ロジックを持たせられる点だが、Prisma Clientは通常service_roleで全テーブルにアクセスするため、RLSを無効化しがちなアンチパターンに陥る。認可をアプリ層（Prisma）とDB層（RLS）どちらに置くか、チームで明文化しておく必要がある。

- **マイグレーション運用の二重管理リスク:** Prisma Migrateのマイグレーション履歴とSupabase CLIのマイグレーション管理が競合するケースが増えている。2026年現在はPrisma Migrateを単一のソースオブトゥルースとし、Supabase側のダッシュボードでの直接スキーマ変更は禁止するルールを徹底するのが実用的。

- **Edge Function / Realtime連携でのスキーマ同期:** SupabaseのRealtimeやEdge FunctionsはPostgresのスキーマ変更を即時反映するため、Prisma側のスキーマファイルと物理DBのドリフトが起きやすい。CI上で`prisma db pull`による差分検知を定期実行し、ドリフトを早期発見する仕組みが推奨される。

- **型安全性のエンドツーエンド化:** Prisma生成型とSupabaseのPostgREST自動生成型（`supabase gen types`）が併存すると型のソースが二つになり不整合が起きる。どちらか一方（多くの場合Prisma）に一本化し、フロントエンドまで型を伝搬させる構成が長期的な保守性で優位。

### 7. WebAssembly Rust performance 2026

- **Component Model の実用化:** WASI Preview 2とComponent Modelの標準化が進み、Rustで書いたモジュールを言語非依存のインターフェースで安全に合成できるようになった。マイクロサービス的にWASMモジュールを組み合わせる設計がパフォーマンスとセキュリティの両面で現実的な選択肢になっている。

- **SIMD・マルチスレッドの本格活用:** WASM SIMDとthreads/atomicsのブラウザ・ランタイム対応が成熟し、Rust側もstd::simdやrayonとの連携が進んだことで、画像処理・ML推論などCPU負荷の高い処理をネイティブの70〜90%程度の速度で実行できるケースが増えている。

- **AOTコンパイル・ランタイム最適化:** Wasmtime/WasmerなどのランタイムがCranelift/LLVMベースのAOTコンパイルを強化し、コールドスタート時間を大幅短縮。サーバーレスやエッジ関数（Cloudflare Workers等）でRust+WASMを使う際のレイテンシが実用レベルに達している。

- **バイナリサイズ最適化のベストプラクティス定着:** `wasm-opt`、`wee_alloc`代替のカスタムアロケータ、`#[no_std]`構成などの最適化手法がコミュニティで標準化され、数百KB〜数MB級のバンドルでも初回ロードを現実的な範囲に抑えられるようになった。ブラウザ配信前提の機能では依然サイズとパフォーマンスのトレードオフ管理が必要。

- **実用上の注意点:** JS↔WASM間の境界を跨ぐ呼び出し（特に文字列・構造体のマーシャリング）がまだオーバーヘッドの主因であり、ホットパスでの頻繁な境界越えを避ける設計が重要。sumitsugiのような物件データ処理・画像処理を伴う機能でWASM導入を検討する場合は、境界越えの頻度を最小化する粒度でモジュールを切るべき。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 15/16でStable化したPPRにより、静的シェルを即時配信しつつ動的部分をストリーミングする構成が標準化。LCP改善とパーソナライズの両立が可能になり、ECサイトの商品一覧やダッシュボードで特に効果が大きい。

- **Server Actionsのセキュリティ強化が必須:** Server Actionsは事実上のパブリックAPIエンドポイントであるため、2026年のベストプラクティスでは全アクションにZodバリデーション＋認可チェックを必須化する流れが定着。本プロジェクトの`src/app`配下でも、フォーム送信系はこの原則を厳守する必要がある。

- **"use cache" ディレクティブによる明示的キャッシュ制御:** これまで曖昧だったfetchキャッシュの暗黙動作から脱却し、関数・コンポーネント単位で`"use cache"`を明示する方式が主流化。キャッシュ境界が読みやすくなり、不要な再検証によるコスト増を防ぎやすい。

- **Route Handlers + Server Componentsの責務分離が明確化:** データ取得はServer Component内で直接行い、Route Handlersは外部Webhook・サードパーティ連携専用に限定する設計が定石に。REST APIレイヤーを自前で増やさず、型安全性を保ったままDBアクセスを完結させる流れが強い。

- **Turbopackのビルド高速化が開発体験を左右:** Turbopackが本番ビルドでも安定し、大規模リポジトリでのビルド時間が大幅短縮。CI/CDのフィードバックループが速くなる一方、サードパーティのWebpackプラグイン依存コードは移行コストがかかるため、新規実装では極力標準機能に寄せる判断が重要。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Functionsのコールドスタートはほぼ解消され、V8 isolateベースの実行環境がグローバルPoPでミリ秒単位の初期化を実現している。地理的に分散したユーザーへのレスポンスタイム最適化において、Node.js Runtimeではなく明示的にEdge Runtimeを選択する判断がデフォルト化しつつある。

- **ポイント2:** Streaming SSR + Edge Middlewareの組み合わせで、認証チェックやA/Bテストの分岐をオリジンサーバーに到達する前に処理できる。sumitsugiのようなマーケットプレイスでは、物件詳細ページの`draft`/`public`判定をEdgeでフィルタリングすることで、不要なオリジンリクエストを削減できる。

- **ポイント3:** Edge側でのDB接続はコネクションプーリング非対応のため、Prisma Accelerateやネイティブfetch経由のHTTP型DB（Neon, PlanetScale等）が標準になっている。重い集計クエリはNode.js Runtime側に残し、Edgeは軽量な読み取り専用処理に限定する設計分離が重要。

- **ポイント4:** Vercelのコスト最適化観点では、Edge Functionsの実行時間課金がGB-sec単位で明確化され、不要なバンドルサイズ（依存関係の肥大化）が直接コストに影響するようになった。`bun run build`後のバンドル解析を定期的に行い、Edge関数の依存を最小限に保つ運用が推奨される。

- **ポイント5:** ISR（Incremental Static Regeneration）とEdge Cache Tagsの連携により、物件情報の更新時に該当ページのみを選択的に再検証できる。物件一覧・詳細ページのキャッシュ戦略をタグベースで設計することで、スケール時のオリジン負荷を抑えつつ鮮度を保てる。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** `satisfies`演算子とテンプレートリテラル型の組み合わせが標準化し、型推論を保ったままリテラル制約を課すパターンが主流に。Zodなど実行時検証ライブラリとの型推論連携（`z.infer`）が型安全性の実質的な入口になっている。
- **ポイント2:** `any`排除よりも「境界での検証」が重視される流れが定着。APIレスポンスやフォーム入力などシステム境界でZodスキーマによるパース＋型生成を行い、内部コードは生成された型を信頼する設計が標準パターン。
- **ポイント3:** ブランド型（branded types）によるプリミティブの誤用防止が普及。`type UserId = string & { __brand: 'UserId' }`のようなパターンで、IDの取り違えなどのバグをコンパイル時に検出する実装が増えている。
- **ポイント4:** 判別可能なユニオン型（discriminated union）を使った状態管理が、`'draft' | 'public'`のようなステータス管理の定石として定着。exhaustiveness checking（`never`型を使った網羅性チェック）で分岐漏れをビルド時に検出する習慣が重要。
- **ポイント5:** TypeScript 6系でのビルド速度改善（Goベースコンパイラ移行の流れ）により、大規模コードベースでも`strict`モード＋高頻度の型チェックが実用的に。型チェックをCIの必須ステップとする運用がより重要視されている。
