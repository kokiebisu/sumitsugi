# CTO Knowledge - 2026-10-11

## Daily Update (2026-10-11)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 15以降で安定したPPRを使い、静的シェルを即時配信しつつ動的部分のみSuspenseでストリーミングすることで、初回表示速度とSEOを両立できる。物件一覧ページなど「骨格は固定・価格や在庫は動的」な構成に特に有効。

- **Turbopackへの完全移行:** Next.js 16でTurbopackがビルド・devの既定になり、webpack比でビルド時間が大幅短縮される。CIのビルド時間短縮とローカル開発体験の両方に直結するため、`next.config`のカスタムwebpack設定を早めに棚卸しして移行障害を潰しておくべき。

- **Server Actionsのキャッシュ戦略見直し:** `use cache`ディレクティブとCache Componentsにより、データ取得の粒度を細かく制御できるようになった。物件詳細や引越し費用計算などDBアクセスが多い箇所は、ページ単位でなく関数単位でキャッシュを切ることでTTFBを改善できる。

- **画像・フォント最適化の自動化徹底:** `next/image`のAVIF優先配信とフォントのセルフホスティングは依然効果が大きい。物件写真が多いUIでは、LCP(Largest Contentful Paint)がCore Web Vitalsのボトルネックになりやすいので、優先度`priority`指定とレスポンシブ`sizes`の見直しを定期的に行う運用にすべき。

- **Edge Runtimeの選定は慎重に:** Edgeは低レイテンシだがNode.js APIの制約があるため、認証や決済処理など複雑なロジックはNode Runtimeに残し、静的に近い読み取り系APIのみEdgeに寄せるハイブリッド構成が2026年のベストプラクティスになっている。

### 2. React Server Components streaming 2026

- **Partial Prerendering(PPR)の標準化:** Next.js 16ではPPRが安定版として扱われ、静的シェルを即時返しつつ動的部分だけをストリーミングする構成が標準パターンになっている。sumitsugiの物件一覧ページなどSEOと動的データが混在する箇所では、静的な骨格を先に返すことでLCPを改善できる。

- **`loading.tsx` + Suspense境界の粒度設計が重要:** RSCストリーミングの効果はSuspense境界の切り方に強く依存する。物件詳細ページなら「基本情報」「画像ギャラリー」「前の住人のレビュー」のように意味単位で境界を分け、重いデータ取得（例: 外部APIコール）だけを遅延させるのが実用的。

- **Server Actionsのエラーハンドリングが成熟:** `useActionState`と組み合わせたプログレッシブエンハンスメントが一般化し、フォーム送信中のストリーミングUI（楽観的更新＋サーバー確定）が標準パターンに。問い合わせフォームやメッセージ機能で有効。

- **キャッシュ戦略の複雑化に注意:** Next.js 16のキャッシュAPI（`use cache`ディレクティブなど）が安定しつつあるが、ストリーミングと組み合わせるとキャッシュの無効化タイミングが分かりにくくなりがち。物件ステータス(`draft`/`public`)の切り替えなど即時性が求められるデータは、キャッシュ境界を明示的に設計する必要がある。

- **Edge Runtimeとの相性がボトルネック化しやすい:** RSCストリーミングはEdge環境で特に効果を発揮するが、DBアクセスを伴う処理をEdgeに持っていくとレイテンシが悪化するケースがある。sumitsugiのような地理的に分散しないサービスではNode.js runtimeでのストリーミングの方が安定することが多い。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCやGraphQLよりも「スキーマファースト+型生成」の設計思想自体が主流化しており、どのプロトコルを選ぶかより、OpenAPI/Zodスキーマからクライアント・サーバー双方の型を自動生成する運用が重要。sumitsugiでもZodで境界を固めつつ、将来的にtRPC化すれば型安全性をさらに高められる。
- **ポイント2:** BFF(Backend for Frontend)層でtRPCを採用し、外部連携やモバイルなど異種クライアント向けにはREST/GraphQLを併用するハイブリッド構成が2026年の標準的パターンになっている。単一プロトコルに固執せず、クライアントの性質で使い分けるべき。
- **ポイント3:** GraphQLはN+1問題対策（DataLoader等）やキャッシュ戦略のコストが高く、シンプルなCRUD中心のプロダクト（物件情報・予約など）ではtRPC+REST路線の方が開発速度と保守性で優位になりやすい。
- **ポイント4:** Next.js 16のServer Actions/RSCとtRPCの組み合わせが定着し、クライアント-サーバー間のAPI層を薄くして型安全なデータフェッチを実現するのがApp Routerベースのプロダクトでは効率的。
- **ポイント5:** 外部パートナー（不動産業者・決済代行）向けには依然RESTが事実上の標準であり、内部通信はtRPCで高速イテレーション、外部公開APIはREST+OpenAPIドキュメントという「内と外で分離する」設計が実用的。

### 4. serverless edge computing 2026

- **コールドスタートのほぼゼロ化:** V8 isolateやWasmベースのランタイム（Cloudflare Workers, Fastly Compute等）が主流化し、起動レイテンシが1桁ms台まで低下。これにより従来Lambdaで避けていた同期的なユーザー対面処理もエッジで実行可能になっている。

- **エッジでのステートフル処理が実用域に:** Durable Objects / Workers KV / D1のようなエッジネイティブなステート管理が成熟し、認証・レート制限・リアルタイム在庫管理など「前の住人→次の住人」の引き継ぎフローのような低レイテンシ処理をCDN層に寄せられる。本サービスのような予約・決済フローでも中央DBへの往復を減らせる余地がある。

- **AI推論のエッジ分散:** 軽量LLM/埋め込みモデルのエッジ推論（ONNX Runtime Web, WebGPU活用）が普及し、画像のモデレーションや物件検索のセマンティック検索をオリジンサーバーを経由せず処理するパターンが増加。コスト最適化の観点でも中央集権的なAPI呼び出しより有利になるケースが出てきている。

- **Next.js 16とのエッジ統合深化:** App Routerのミドルウェア／Server Actionsがエッジランタイムでの実行を前提とした最適化を進めており、Vercel以外（Cloudflare, Deno Deploy）でも同等機能が揺るみなく使えるようになってきた。現行のNext.js 16スタックでは、画像最適化やA/Bテストのロジックをミドルウェアでエッジ化することで、オリジンへの負荷を下げつつTTFBを短縮できる。

- **運用面での落とし穴:** エッジ環境はNode.js APIの一部（fsやネイティブモジュール）が使えず、観測性（ログ/トレース）も分散するため、デバッグコストが上がる。本番導入前にローカルでのエッジランタイムエミュレーションとログ集約基盤の整備が前提になる点は見落とされがち。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証(WebAuthn)が主流化し、フィッシング耐性のある認証がデフォルト要件に。従来のSMS-OTPは中間者攻撃に弱いため、段階的に廃止すべき。

- **ゼロトラスト前提のセッション管理:** 認証後も継続的にリスクスコアを評価し、デバイス・位置情報・行動パターンの異常時に再認証を要求する設計が標準に。JWTは短命化し、リフレッシュトークンのローテーション必須。

- **認可ロジックの分離(BFF/OPA):** 認証(Authentication)と認可(Authorization)を明確に分離し、Policy-as-Code(OPAなど)で権限管理を集中化。マイクロサービス化が進む中でビジネスロジックへの権限チェック漏れが最大のリスク要因。

- **サプライチェーン経由の認証情報漏洩対策:** npm/依存パッケージ経由のトークン窃取が増加しており、Secrets ScanningとSBOM管理をCI/CDに組み込むことが必須。弊社でも`bun install`時の依存監査を定期実施すべき。

- **AIエージェント向け認証の新課題:** LLMエージェントがAPIを操作する際の認可境界(どこまで自律的に操作を許可するか)が新たな脆弱性領域。人間のセッションとエージェントのセッションを明確に分離し、エージェント操作には短命スコープ付きトークンを発行する設計が求められる。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はRust不要の純TypeScriptエンジン（TypedSQL/driver adapters）に完全移行し、Supabaseのコネクションプーラー（PgBouncer/Supavisor）との相性が改善、Edge RuntimeやServerless環境でのコールドスタート問題が大幅に軽減されている。

- **ポイント2:** Supabaseの Row Level Security（RLS）とPrismaのスキーマ管理を併用する際は、PrismaではRLSを直接表現できないため、マイグレーションSQLを手動で追記する運用が定着しつつある。本プロジェクトでも`seller`等の内部テーブルに対するRLSポリシーをPrisma migrationに手書きで追加するフローを標準化すべき。

- **ポイント3:** Supabase Realtime（Postgres Changes）とPrismaのORM層を組み合わせる場合、Prisma側の楽観的ロックやトランザクション管理とRealtimeのイベント配信タイミングがズレるケースがあるため、物件ステータス（`draft`/`public`）のような状態遷移はDB側のトリガー・制約で保証し、アプリ層の検証と二重化するのが安全。

- **ポイント4:** 2026年現在、SupabaseはPostgres 17ベースのブランチング機能（開発用DBブランチ）が成熟しており、PRごとに本番スキーマのコピーを自動生成してCIでマイグレーションテストを回す構成がベストプラクティス化している。`bun run build`前のDBマイグレーション検証にも組み込む価値がある。

- **ポイント5:** マルチテナント設計（前の住人／次の住人データの分離）では、SupabaseのRLS + PrismaのミドルウェアによるテナントIDフィルタリングの二層防御が推奨される。Prisma単体の`where`句漏れによるデータ漏洩リスクをRLSが最終防衛線として吸収できる。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** 2026年現在、Rust製WASMモジュールはLLVMベースのコード生成とWasm GC/Component Model仕様の安定化により、ネイティブコードの90%以上のパフォーマンスを達成するケースが増えている。ブラウザだけでなくエッジランタイム（Cloudflare Workers、Fastly Compute）でも採用が進んでいる。

- **ポイント2:** `wasm-bindgen`や`wasm-pack`のツールチェーンが成熟し、ビルドサイズの最適化（`wee_alloc`→`talc`やLTO + `opt-level="z"`）がデフォルトのベストプラクティスとして定着しており、初回ロード時間がボトルネックになりにくくなっている。

- **ポイント3:** WASI Preview 2とComponent Modelの普及により、Rustで書いたWASMコンポーネントをフロントエンド/バックエンド/サーバーレスの各環境で再利用できるようになった。これにより「一度書けばどこでも動く」軽量サンドボックス実行がマイクロサービス設計の選択肢として現実的になっている。

- **ポイント4:** マルチスレッド対応（SharedArrayBuffer + Wasm threads）とSIMD命令の標準化で、画像処理・PDF生成・暗号処理など計算負荷の高い処理をRust/WASMにオフロードする事例が増えており、本プロジェクトのPDF生成やリスト画像最適化処理への応用余地がある。

- **ポイント5:** JS⇔WASM間のメモリコピーコストが依然として実務上の最大の性能課題であり、大きなデータを跨ぐAPI設計では「一度に大量転送してWASM側で処理」というバッチ指向の呼び出しパターンが推奨される。

### 8. Next.js App Router patterns 2026

- **サーバーコンポーネント優先の設計:** App Routerではデフォルトでサーバーコンポーネントを使い、クライアントコンポーネント（`'use client'`）は対話が必要な末端のみに限定することで、バンドルサイズとTTIを最小化できる。
- **Partial Prerendering (PPR) の実用化:** 静的シェルを即時配信しつつ動的部分を`Suspense`でストリーミングする手法が2026年には標準パターン化しており、`sumitsugi`の物件一覧ページのような「静的なレイアウト＋動的な検索結果」構成に特に適している。
- **キャッシュ戦略の明示化:** `fetch`のデフォルトキャッシュ挙動がバージョンごとに変化してきたため、`cache: 'force-cache'`や`revalidate`を暗黙に任せず明示的に指定し、`src/lib/data.ts`のようなデータ層でキャッシュポリシーを一元管理するのが現在のベストプラクティス。
- **Server Actionsによるフォーム処理の簡素化:** 物件登録・引越し費用の入力フォームなど多段階フローでAPIルートを減らしてServer Actionsに寄せることで、クライアント側のfetchロジックとエラーハンドリングのコードが大幅に削減できる（ただしZodでの境界検証は必須）。
- **Route Groupsとparallel routesでのレイアウト分離:** `(auth)`や`(dashboard)`のようなルートグループと`@slot`によるparallel routesを組み合わせ、アカウント画面と物件詳細画面で異なるレイアウト・ローディング状態を共存させる構成が、複雑な条件分岐を書かずに済む主流パターンになっている。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Functionsの実行時間制限とコールドスタートの最適化が進み、V8 isolateベースのランタイムによりミリ秒単位の起動が標準化されつつある。重い処理はNode.js RuntimeのFluid Computeに任せ、Edgeはルーティング・認証・パーソナライゼーションなど軽量処理に限定するのが2026年のベストプラクティス。

- **ポイント2:** Vercelの`Fluid Compute`モデルが主流化し、Edge/Serverlessの境界が曖昧になりつつある。インスタンスの再利用と同時実行の最適化により、同じ関数内でI/Oバウンドな処理を並行実行できるため、不必要に関数を分割せずコスト効率を上げられる。

- **ポイント3:** Edge ConfigやKVとの組み合わせによる「データをコードの近くに置く」設計が重要。本プロジェクトのような地域依存コンテンツ（物件情報・前の住人データ）はEdge Configでキャッシュし、動的パーソナライゼーションのみEdge Functionで処理すると、TTFBを大幅に短縮できる。

- **ポイント4:** Observability周りが強化され、OpenTelemetry統合がEdge Runtimeでもネイティブサポートされつつある。本番環境でのレイテンシ・コールドスタート計測を前提に、計測なしでの「最適化」は避けるべき（推測ではなく実測ベースの改善が原則）。

- **ポイント5:** Next.js 16のPartial Prerendering (PPR) とEdge Functionsの組み合わせが成熟し、静的シェルを即時返しつつ動的部分のみEdgeでストリーミングする構成が標準パターンになっている。本サービスの一覧ページなどでPPRを導入すれば、SEOと体感速度を両立できる余地がある。

### 10. TypeScript type safety patterns 2026

- **型レベルテストの標準化:** `tsd`やVitestの`expectTypeOf`を使い、型定義自体をCI でテストする文化が定着。ランタイムバグだけでなく「型が意図通り推論されるか」もPRゲートに組み込むべき。

- **`satisfies`演算子の定着:** 型注釈で広げすぎず、リテラル推論を保ったまま制約チェックできるため、`as const`との併用でconfig系オブジェクト（例: `site-config.ts`）の型安全性が大幅に向上。sumitsugiでも`'draft' | 'public'`のようなUnion型を持つオブジェクトには積極採用すべき。

- **Zodなどのスキーマファーストバリデーションがデフォルト化:** 型だけでは実行時入力を保証できないため、API境界・フォーム入力は「スキーマ定義→型はinferで導出」が主流に。本プロジェクトのStandardsにも明記されている通り、型とランタイム検証を1ソースで管理するのが鉄則。

- **Template Literal Typesによるドメイン固有の型安全性:** ルーティングパスやi18nキー（UI用語の「前の住人」「引越し費用」等のマッピング）を文字列リテラル型で縛ることで、ハードコードされた日本語文言とデータ構造上の内部用語のズレをコンパイル時に検出できる。

- **TypeScript 6系のGo移植コンパイラによる高速フィードバック:** 型チェック速度が大幅改善され、大規模コードベースでも`tsc --noEmit`をCIの必須ステップとして常時実行するのが現実的に。ビルド時の型エラー検出漏れという従来のリスクが軽減される。
