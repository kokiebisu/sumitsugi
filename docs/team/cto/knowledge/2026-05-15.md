### 2. React Server Components streaming 2026

- **Streaming SSRの成熟化:** React 19とNext.js 15以降、`Suspense`境界を活用したストリーミングSSRが本番環境でのデファクトスタンダードになっており、TTFBを維持しながらLCPを大幅に改善できる。

- **PPR（Partial Prerendering）の実用化:** Next.js 15でStableになったPPRにより、静的シェルを即時配信しつつ動的コンテンツをストリーミングで差し込むハイブリッド戦略が現実的な選択肢になった。

- **データフェッチの直列化問題への対応:** Server Componentsのネスト構造でウォーターフォールが発生しやすいため、`Promise.all`による並列フェッチや、`preload`パターンを使ったデータのホイスティングが重要な最適化手法となっている。

- **エラーハンドリングとローディングUXの設計:** `error.tsx`と`loading.tsx`のルートセグメント単位の分離により、部分的な失敗を局所化できるが、Suspense境界の粒度設計がUX品質を左右するため、コンポーネント設計段階での意識が必要。

- **キャッシュ戦略の複雑化:** `fetch`のキャッシュ、`unstable_cache`、`revalidatePath`/`revalidateTag`の使い分けが複雑になっており、チーム内でキャッシュ戦略のガイドラインを明文化しないとデータの不整合が起きやすい。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの実用的優位性:** フルスタックTypeScriptプロジェクトでは、tRPCがスキーマ定義不要でエンドツーエンドの型安全を実現し、GraphQLの複雑さなしに同等の開発体験を提供する。Next.js App Routerとの親和性が特に高く、2026年時点でスタートアップの第一選択肢になりつつある。

- **RESTの不滅:** パブリックAPI・サードパーティ連携・モバイルアプリ向けでは依然としてRESTが標準。OpenAPI 3.1 + Zodによる自動バリデーションとドキュメント生成の組み合わせが、REST開発の定番パターンとして定着した。

- **GraphQLの適所:** 複数クライアント（Web/iOS/Android）が異なるデータ形状を要求するケースや、BFF（Backend for Frontend）パターンに限定して採用するのが現実的。Relay/Apollo Clientの学習コストを正当化できるプロジェクト規模が必要。

- **Server Actions の台頭:** Next.js のServer Actionsが「APIレイヤーを書かないAPI設計」として普及し、フォーム送信・データ変更処理でtRPCやREST APIを省略できるケースが増えた。ただし再利用性・テスト容易性の観点からtRPCとの住み分けが重要。

- **選定基準の明確化:** 2026年の実践的指針は「外部公開→REST」「社内フルスタックTS→tRPC」「多クライアント複雑クエリ→GraphQL」「単純なサーバー処理→Server Actions」。技術スタックの一貫性を優先し、プロジェクト内で複数のAPIパラダイムを混在させないことがメンテナビリティに直結する。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応成熟:** Prisma 6.xではEdge RuntimeでのD1/PlanetScale接続が安定し、Next.js App RouterのServer Actionsから直接型安全なクエリが書けるようになった。ただしコネクションプーリング（Prisma Accelerate）は依然として必須。

- **Supabase pgvector + RAGの本番運用:** pgvectorの`ivfflat`から`hnsw`インデックスへの移行が推奨フローとなり、Supabaseのベクトル検索がプロダクションレベルのスループットに達した。AIアプリのストレージ層としてPostgresに集約できる点がアーキテクチャ簡素化に寄与する。

- **Row Level Security (RLS) ファーストの設計:** SupabaseのRLSポリシーをORMレイヤーより優先させ、バックエンドレスの権限モデルを構築するパターンが定着。Prismaと併用する場合はRLSバイパスのサービスロールキー管理が最大のセキュリティリスクになる。

- **スキーママイグレーションの二重管理問題:** PrismaのマイグレーションとSupabaseのマイグレーション（`supabase db push`）が競合しやすく、2026年時点ではPrismaをスキーマソースオブトゥルースに統一し、Supabase CLIはローカル開発環境管理専用に限定するパターンが安定解とされている。

- **リアルタイム＋楽観的UIの標準化:** Supabase RealtimeとReact Query（または SWR）を組み合わせた楽観的更新パターンが標準化し、Prismaで書いたServer Actionの結果をクライアントキャッシュに即反映する設計がUXの基準値を引き上げている。

### 7. WebAssembly Rust performance 2026

- **Component Modelの成熟:** WASI 0.2とComponent Modelが2025-2026年に安定版となり、RustのWasmコンポーネントを他言語と安全に合成できるようになった。マイクロサービス的なWasmエコシステムが現実的な選択肢になりつつある。

- **WasmGC対応とメモリ効率:** WasmGCの普及によりGC言語のオーバーヘッドが明確になり、相対的にRustの線形メモリ管理の優位性が際立つ。特にエッジ環境での起動時間（コールドスタート < 1ms）とメモリフットプリントでRustは依然トップクラス。

- **SIMD・スレッド活用の実用化:** WebAssembly SIMDとshared memoryが主要ランタイム（V8, Wasmtime, WasmEdge）で安定稼働し、Rustの`packed_simd`や`rayon`相当の並列処理がWasm上でも有効になった。画像処理・暗号・ML推論で2-4x高速化の事例が増加。

- **wasmtime + Cranelift vs. V8のパフォーマンスギャップ縮小:** サーバーサイドでのWasmtime採用が加速し、AOTコンパイル（`wasmtime compile`）によりネイティブ比95%以上のスループットを達成するケースが報告されている。Cloudflare WorkersやFastly Computeでの本番事例が設計判断の参考になる。

- **ツールチェーンの成熟（`cargo-component`, `wasm-pack` v2）:** `cargo-component`がWIT(WebAssembly Interface Types)ベースのビルドを標準化し、複雑なバインディング生成が不要になった。2026年時点でRust→Wasmのビルドパイプラインは「特別なもの」ではなくなりつつある。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの設計:** 2026年時点でApp Routerの主流はServer Componentsをデフォルトとし、クライアント境界を最小化する戦略。データフェッチはコンポーネント内で直接行い、プロップドリリングを排除できる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的ストリームを同一ルートで混在させるPPRが安定版となり、LCPとTTFBの両立が可能に。`experimental_ppr`フラグなしで使えるようになった。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15以降で導入された`use cache`が標準化され、関数・コンポーネント単位でのキャッシュ戦略が宣言的に書けるようになった。`revalidateTag`との組み合わせで従来のISRより柔軟な更新制御が可能。

- **Server Actions の型安全強化:** `next-safe-action`やZodとの統合が成熟し、フォーム送信・楽観的UIのパターンが確立。`useActionState`を使った段階的エラーハンドリングが推奨アーキテクチャになっている。

- **モノレポ × Turbopack のビルド高速化:** Turbopackが安定版となりWebpackを実質代替。大規模プロジェクトではビルド時間が50-70%短縮されており、当プロジェクト規模でも`bun run build`の体感が大きく改善される。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの制約を理解したコールドスタート排除:** Edge FunctionsはNode.js完全互換ではなくV8 Isolateベースのため、`node:crypto`等のNode専用APIは使用不可。2026年時点では`@edge-runtime/primitives`を活用し、Web標準APIに統一することでコールドスタートをほぼゼロに抑えられる。

- **Fluid Computeによる実行モデルの変化:** Vercelが導入したFluid Computeにより、Edge/Serverlessの境界が曖昧化。CPUバウンドな処理はEdgeで、DB接続が必要な処理はServerless Functionsに振り分けるハイブリッド戦略が最適解となっている。

- **KV・R2等のEdgeネイティブストレージとの組み合わせ:** Vercel KV（Upstash Redis）やCloudflare R2をEdge Functionと同一リージョンに配置することでレイテンシを最小化。セッション管理・レート制限・フィーチャーフラグはEdgeレイヤーで完結させるのが定石。

- **Middleware最適化とルーティングコスト:** `middleware.ts`は全リクエストに適用されるため、`matcher`で対象パスを厳密に絞ることが必須。2026年では`next/server`の`unstable_after`を使い、レスポンス後の非同期処理（ログ・アナリティクス）をブロッキングから切り離すパターンが主流。

- **Observabilityの内製化:** Vercel公式のObservability（Speed Insights / Web Analytics）はEdge Functionの実行時間・リージョン分布を可視化できるが、OpenTelemetryのEdge対応（`@vercel/otel`）を組み込み、独自のトレーシング基盤と接続することでコスト・依存度のバランスを取ることが推奨される。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded Typesが実務標準化し、プリミティブ型の混同バグをコンパイル時に防ぐパターンが定着した。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` が型推論の精度を保ちながら型チェックを強制する主力パターンになり、`as const` との組み合わせで設定オブジェクトの型安全性が大幅向上した。

- **Template Literal Types によるAPIスキーマ定義:** `type EventName = \`on${Capitalize<string>}\`` のようなテンプレートリテラル型でAPIイベント名・ルートパスを型レベルで表現し、実行時エラーをゼロに近づけるアプローチが広がっている。

- **`using` キーワードと Explicit Resource Management:** TypeScript 5.2導入の `using` 宣言によりDB接続・ファイルハンドルなどのリソース管理が型安全に自動化され、リソースリーク系バグのクラスが消滅しつつある。

- **型レベルテスト（`expect-type` / `tsd`）の CI 必須化:** 型定義そのものをテストする `expectTypeOf` アサーションをCIに組み込み、リファクタ時の型退行を検出する文化が成熟プロジェクトでは標準になっている。
