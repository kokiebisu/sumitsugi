# CTO Knowledge - 2026-11-06

## Daily Update (2026-11-06)

### 1. Next.js performance optimization 2026

- **ポイント1（部分プリレンダリング / PPR）:** Next.js 16ではPPRが安定版として本格運用レベルに達しており、静的シェルを即時配信しつつ動的部分だけSuspenseでストリーミングする構成が標準化。LCP改善とサーバー負荷削減を同時に狙えるため、一覧ページや物件詳細ページのような「ほぼ静的＋一部パーソナライズ」な画面と相性が良い。

- **ポイント2（Turbopackのビルド/devパフォーマンス）:** Turbopackがビルドでも既定になりつつあり、大規模なコンポーネント数を持つプロジェクトでもHMRとプロダクションビルドの速度差が縮小。CIのビルド時間短縮に直結するため、`bun run build` のCI必須化（本リポジトリの方針）とあわせて継続的に計測する価値がある。

- **ポイント3（Server Actionsのキャッシュ戦略）:** `use cache` ディレクティブとキャッシュプロファイルの組み合わせにより、データ取得からミューテーションまでの再検証粒度を細かく制御できるようになった。前の住人/次の住人間のやり取りなど頻繁に更新されるデータと、物件情報のような準静的データを明確に分離してキャッシュ設計することが重要。

- **ポイント4（Reactコンパイラとメモ化の自動化）:** React Compilerの普及により手動`useMemo`/`useCallback`の必要性が大幅に減少し、レンダリング最適化がビルド時に自動化される流れが強まっている。手動最適化コードの削減は保守性にも効くため、本プロジェクトの「小さい関数・低ネスト」方針とも整合しやすい。

- **ポイント5（画像・フォント最適化とCore Web Vitals）:** `next/image`のAVIF/responsive最適化とフォントのセルフホスティングがデフォルト化し、INP（Interaction to Next Paint）がCore Web Vitalsの主要指標として重視される傾向が続いている。物件写真を多用するUIでは、画像の遅延読み込みと優先度制御（`priority`属性）の設計が体感速度に直結する。

### 2. React Server Components streaming 2026

**ポイント1（Partial Prerendering の標準化）:** Next.js 16ではPPR（Partial Prerendering）が安定版となり、静的シェルを即時配信しつつ動的部分のみSuspense境界でストリーミングする構成が標準パターンに。本プロジェクトでも`properties/`一覧ページのような「レイアウトは静的・検索結果は動的」な画面で初期表示速度を大きく改善できる。

**ポイント2（Server Actionsとの統合深化）:** RSCストリーミングとServer Actionsのエラーハンドリングが統合され、フォーム送信中のUIをストリーミングで段階的に更新するパターンが一般化。問い合わせフォームや物件掲載フローなど多段階フォームでのUX改善に直結する。

**ポイント3（キャッシュ境界の明示化）:** `use cache`ディレクティブ（Next.js Cache Components）により、どのコンポーネントがキャッシュされ、どこでストリーミングが発生するかが明示的になった。パフォーマンスチューニングがブラックボックスでなくなり、データ取得層（`src/lib/data.ts`）の責務分離がしやすくなる。

**ポイント4（Suspenseの粒度設計がボトルネック）:** ストリーミング自体は成熟したが、実運用での課題は「Suspense境界をどこに置くか」の設計力に移っている。粒度が粗いとウォーターフォールが発生し、細かすぎるとレイアウトシフトが増えるため、UIコンポーネント単位での境界設計レビューが重要になる。

**ポイント5（Edge/Node runtimeでの差異縮小）:** ストリーミングSSRのパフォーマンス差がEdge runtimeとNode runtimeで縮小し、どちらを選んでもTTFBの体感差が小さくなった。これにより、認証チェック（`auth-context.tsx`）など複雑な処理が必要なページでもNode runtimeを安心して選べる。

### 3. API design REST GraphQL tRPC 2026

- **型安全性の統一が主流に:** tRPCのようなエンドツーエンドの型安全なAPI層が、フロントエンド/バックエンド分離プロジェクトでも採用が進んでおり、Next.js 16のApp Router + TypeScript構成ではSchema駆動（Zod）とtRPCの組み合わせがREST/GraphQLより開発速度とバグ検出の面で優位になっている。

- **GraphQLは複雑なデータ取得が必要な場面に限定:** 複数エンティティを横断する検索・フィルタリング（物件検索、前の住人の活動歴表示など）ではGraphQLのメリットが残るが、単純なCRUD中心のsumitsugiのようなプロダクトではオーバーヘッドが大きく、採用コストに見合わないケースが多い。

- **RESTはシンプルさと公開APIの定番であり続ける:** 外部パートナー（不動産会社、決済プロバイダ）向けの公開APIやWebhookは、ドキュメント性・キャッシュ制御・HTTPセマンティクスの明確さからRESTが依然デファクト。社内の型付きAPIはtRPC、外部公開はRESTという併用パターンが2026年のベストプラクティス。

- **Server Actions / RSCとの統合がAPI設計を変えている:** Next.js 16のServer Componentsにより、従来のAPI層を経由せずサーバー関数を直接呼び出す設計が増加。sumitsugiのような単一Next.jsアプリでは、内部通信にtRPC/Server Actionsを使い、REST/GraphQLは外部連携にのみ残す「API層の最小化」が効率的。

- **バリデーション層がAPI契約そのものに:** Zodスキーマをtプロトコル間（tRPC入出力、REST境界、フォーム）で共有する設計が標準化しつつあり、`.claude/rules/standards.md`が求める「システム境界でのZod検証」は、API形式を問わずこのトレンドに合致している。

### 4. serverless edge computing 2026

**ポイント1:** エッジでのAI推論が標準化しており、Cloudflare Workers AIやVercel Edge Functionsで軽量LLM推論がオリジンサーバーを経由せず数十ms以内に完結するようになった。レイテンシ要件の厳しいリアルタイム機能（検索サジェスト、不正検知など）はエッジ側に実装するのが2026年のデフォルト選択。

**ポイント2:** WASM（WebAssembly）がエッジランタイムの主流言語基盤になり、Node.js互換APIへの依存を減らすことでコールドスタートがほぼゼロに近づいている。Next.jsのEdge Runtimeを使う際はNode専用パッケージ（fs, crypto等のフルAPI）に依存しないよう設計段階で制約を意識する必要がある。

**ポイント3:** データレイヤーのエッジ分散（Cloudflare D1, Turso, PlanetScaleのグローバルレプリケーション）が進み、「コンピュートはエッジ、データはリージョン」という従来の分離が崩れつつある。sumitsugiのような物件検索・マッチングはread-heavyなので、エッジDBレプリカの活用でグローバル展開時のレイテンシを大幅改善できる余地がある。

**ポイント4:** コスト構造が「リクエスト課金」から「実行時間＋メモリ」の細粒度課金に移行し、小さく疎に実行する設計（モノリシックAPIルートではなく機能単位のエッジ関数）が直接コスト削減につながるようになった。MVP後のスケール局面でこの設計差が運用コストに顕著に出てくる。

**ポイント5:** エッジでの認証・認可（JWT検証、セッションチェック）をミドルウェアレベルで完結させるパターンが定着し、オリジンサーバーに到達する前に不正リクエストを遮断できるようになった。認証周りをエッジ化する際はセキュリティレビューを特に厳格にする必要がある（本プロジェクトのセキュリティ基準にも合致する方向性）。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** 2026年ではパスワードレス認証(WebAuthn/Passkeys)がデフォルトの選択肢となり、フィッシング耐性の高い公開鍵暗号ベースの認証がログインの主流に。本プロジェクトのauth-context.tsxでも早期導入を検討すべき。
- **セッション管理の厳格化:** JWTの有効期限短縮とリフレッシュトークンのローテーション、デバイスフィンガープリンティングによる異常検知の組み合わせが標準に。トークンをlocalStorageに保存せずhttpOnly Cookieで扱うのが鉄則。
- **多要素認証のリスクベース化:** 全ユーザーに固定MFAを強制するのではなく、ログイン元IP・デバイス・行動パターンからリスクスコアを算出し、必要な時だけ追加認証を要求する適応型MFAが主流。
- **ゼロトラスト前提のAPI保護:** 認証済みでも各リクエストごとに権限チェック(RLS/RBAC)を行い、CSRF対策とレート制限をAPI境界で必ず実施。本物件データのような個人情報を扱うサービスでは特に重要。
- **サプライチェーン・依存ライブラリの監査強化:** 認証関連のnpmパッケージは定期的な脆弱性スキャン(Dependabot等)と、secretsのハードコーディング排除(`process.env`経由)を徹底するのが2026年の必須プラクティス。

### 6. database architecture Prisma Supabase 2026

- **スキーマ駆動の型安全性:** Prisma 6系とSupabaseの組み合わせにより、DB定義からTypeScriptの型を自動生成し、フロントエンドまで型が伝播する。RLS（Row Level Security）ポリシーもPrisma側で検証できるようになり、認可ロジックの漏れをビルド時に検出できる。

- **Edge Function + Connection Pooling:** Supabaseのpgbouncerプール経由でPrismaを使う構成が標準化しており、Vercel/Next.js 16のEdge RuntimeからのDB接続はPrisma Accelerateやデータプロキシを併用することでコールドスタート時のコネクション枯渇を回避できる。

- **マイグレーション運用の自動化:** `prisma migrate deploy`をCI/CDパイプラインに組み込み、Supabase側のブランチ機能（Database Branching）と連携させることで、PRごとに隔離されたDB環境でスキーマ変更を検証できる。本番適用前の破壊的変更検知が容易になる。

- **リアルタイム機能との統合:** SupabaseのRealtime（Postgres論理レプリケーション）はPrisma経由では直接扱えないため、通知系の機能は素のSupabaseクライアントと併用するハイブリッド構成が実用的。sumitsugiのようなマッチング通知機能にはこの組み合わせが向いている。

- **コスト最適化の観点:** Supabaseの無料〜Proプランの接続数上限とPrismaのコネクションプール設定のミスマッチがスケール時のボトルネックになりやすいため、ベータローンチ前に想定同時接続数を見積もり、`connection_limit`とSupabase側のプールモード（Transaction/Session）を明示的に設定しておくべき。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASI 0.3/Component Model(WIT)の標準化が進み、Rustの`wasm32-wasip2`ターゲットでネイティブに近いI/O性能とモジュール間の型安全な連携が可能になった。エッジ環境（Cloudflare Workers、Fastlyなど）でのコールドスタート最適化に直結する。

- **ポイント2:** `wasm-opt`やLTO、`codegen-units=1`の組み合わせでバイナリサイズを大幅削減できるようになり、特にSIMD（`target-feature=+simd128`）を有効化したRustコードはブラウザ上で近ネイティブ速度を達成している。パフォーマンスとサイズのトレードオフを本番前に必ずベンチマークすべき。

- **ポイント3:** WasmtimeのAOTコンパイル（`wasmtime compile`）キャッシュが成熟し、サーバーサイドでの起動レイテンシが従来のJIT方式より大幅に短縮された。マイクロサービスやサーバーレス関数でのRust+WASM採用が加速している。

- **ポイント4:** メモリ64（Memory64）とマルチスレッド（shared memory + atomics）のサポートがRustツールチェーンで安定し、大規模データ処理やWASM上の並列計算が実用段階に入った。ただしブラウザ間の対応状況にはまだ差があるため、フォールバック設計が必要。

- **ポイント5:** GC提案（WasmGC）の進展により、Rustのような所有権ベース言語以外（Kotlin、Dartなど）とのWASM相互運用がしやすくなったが、Rust自体はGCなしの強みを保ちつつ`wasm-bindgen`経由でJS/TSとの境界オーバーヘッドを引き続き最小化できる点が差別化要因。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** 静的シェルと動的コンテンツを1つのレスポンスで配信するPPRが安定版となり、ダッシュボードや物件一覧のような「一部は即時表示、一部は非同期」なページで初期表示速度(TTFB/LCP)を大幅改善できる。sumitsugiの`src/app/properties/`のような一覧ページは好適用先。
- **Server Actions のキャッシュ戦略成熟:** `revalidateTag`/`revalidatePath`を使った細粒度の再検証パターンが定着し、フォーム送信やステータス変更(`draft`↔`public`)のようなミューテーション後のUI更新を、クライアント側の状態管理なしで一貫性を保てる。
- **`use cache` ディレクティブの普及:** コンポーネント/関数単位でキャッシュ境界を明示的に宣言できるようになり、従来の`fetch`オプションによる暗黙キャッシュより意図が明確で、レビュー時に「なぜキャッシュされているか」が追いやすくなった。
- **Server/Client境界の最小化パターン:** "Client Componentは葉(leaf)に留める"という設計がベストプラクティスとして定着し、`'use client'`境界を増やしすぎたことによるバンドルサイズ肥大やハイドレーション不整合のバグが減っている。認証コンテキスト(`auth-context.tsx`)のような状態は境界設計の見直し対象になりやすい。
- **型安全なルーティングとミドルウェアの軽量化:** 生成される型付きルート(`Link href`の型チェック)が標準化され、ミドルウェアはEdge実行コストを下げるために認可ロジックの一部をレイヤーごとに分割する設計が推奨されるようになっている。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Vercel Edge FunctionsはNode.js Runtimeとの機能差が縮小し続けており、2026年時点ではWebクリプトAPIやストリーミングレスポンスの対応が進んでいる。ただしコールドスタートの低さを活かすなら、重い依存関係（ORMクライアントやnode専用ライブラリ）を持ち込まないよう注意が必要。

- **ポイント2:** Middleware/Edge Functionsの実行回数課金モデルが明確化されており、認証チェックや簡易リダイレクトのような軽量処理に限定し、DBクエリや複雑なビジネスロジックはサーバーレスFunctions（Node Runtime）側に残すのがコスト最適。

- **ポイント3:** Edge ConfigやKV（Vercel KV / Upstash Redis経由）とEdge Functionsを組み合わせたパターンが定着し、フラグ管理や軽量な在庫・空室チェックなど低レイテンシが求められる処理に向いている。sumitsugiの物件検索・ステータス切替のような高頻度読み取りには検討価値がある。

- **ポイント4:** Next.js 16のPartial Prerendering (PPR) とEdge Runtimeの組み合わせにより、静的シェルをCDNから即時配信しつつ動的部分だけEdgeで補完する構成が主流になっている。物件一覧ページのような「ほぼ静的＋一部動的（空室状況等）」な画面に適している。

- **ポイント5:** リージョン指定（`regions`オプション）をデフォルトの自動選択からユーザー分布に合わせて明示指定するケースが増えている。日本向けサービスなら`hnd1`固定より、DB（Supabase等）との地理的近接性を優先したリージョン選定がレイテンシ改善に直結する。

### 10. TypeScript type safety patterns 2026

- **型推論の進化:** TypeScript 5.xの`const`型パラメータやsatisfies演算子が標準化し、過度な明示的型注釈を減らしつつ型安全性を維持する「推論優先」設計が主流になっています。

- **スキーマファーストな境界検証:** Zodなど実行時検証ライブラリと型定義を一体化させ、APIレスポンスやフォーム入力など「システム境界」で型を保証するパターンが定着（本プロジェクトのCLAUDE.mdでも`Zod`採用を規定済み）。

- **Branded Types/Nominal Typingの普及:** `UserId`と`PropertyId`のような構造的に同じstring型を誤って混同しないよう、ブランド型でコンパイル時に区別する手法が実務で広がっています。

- **Discriminated Unionによる状態管理:** `'draft' | 'public'`のようなステータス型は、switch文の網羅性チェック（`never`型の活用）と組み合わせることで、新しい状態追加時の漏れをコンパイルエラーで検出できます。

- **型とテストの二重保証:** 型安全性はコンパイル時のみの保証のため、TDDによるユニット/E2Eテストと組み合わせて実行時の振る舞いも保証する「型+テスト」の二層防御が、本プロジェクトの80%カバレッジ方針とも整合しています。
