# CTO Knowledge - 2026-03-13

## Daily Update (2026-03-13)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチとロジックはサーバーコンポーネントに集約する。`"use client"` は本当にインタラクティブな末端コンポーネントにのみ付与するのが原則。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降でStableになったPPRにより、静的シェルと動的ストリームを1リクエストで配信できる。`fallback: <Suspense>` 境界の設計がパフォーマンス差を決定的に左右する。

- **`next/image` と `next/font` の最適化徹底:** 画像は `sizes` 属性と `priority` フラグを適切に設定し、LCPスコアを直接改善する。フォントはビルド時にサブセット化・セルフホストすることでレイアウトシフト（CLS）をゼロにできる。

- **Route Groups と Parallel Routes によるバンドル分割:** `(group)` 構文でコードスプリットの粒度を制御し、不要なJSを遅延ロードする設計が重要。特に大規模アプリでは初期バンドルを100KB以下に保つことをKPIにすべき。

- **キャッシュ戦略の明示化（`fetch` cache / `revalidate`）:** Next.js 15からデフォルトキャッシュが無効化されたため、`cache: 'force-cache'` や `revalidate` を意図的に設定しないとパフォーマンスを損なう。データの鮮度要件に応じてISR・オンデマンド再検証を使い分けることが必須。

### 2. React Server Components streaming 2026

- **ポイント1: Suspense境界の粒度最適化が鍵:** RSCストリーミングでは、`<Suspense>`の配置粒度がTTFB（最初のバイト到達時間）とLCP（最大コンテンツ描画）に直結する。2026年はコンポーネント単位ではなく「データ依存単位」での境界設計が標準プラクティスとなっている。

- **ポイント2: PPR（Partial Pre-Rendering）がNext.js本番安定化:** Next.js 15以降でPPRが安定し、静的シェルを即座に返しつつ動的部分をストリーミングで補完するハイブリッドアーキテクチャが実用段階に入った。CDNキャッシュ効率と動的コンテンツを両立できる。

- **ポイント3: `use()`フックによるクライアント側データ統合:** React 19の`use()`フックがPromiseを直接受け取れるようになり、サーバーからクライアントへのデータ受け渡しがSuspenseと自然に統合された。`thenables`をpropsで渡すパターンが増加している。

- **ポイント4: ストリーミングとキャッシュ戦略の複雑化:** RSCのfetch単位キャッシュ（`cache: 'force-cache'`等）とストリーミングタイミングの組み合わせがパフォーマンスチューニングのボトルネックになりやすい。`unstable_cache`とRoute Segment Configの使い分けを明示的に設計する必要がある。

- **ポイント5: Server Actionsとの組み合わせでフォームUXが刷新:** ストリーミングSSRとServer Actionsを組み合わせることで、楽観的UIアップデート（`useOptimistic`）とサーバー処理を統合でき、従来のクライアントAPI呼び出しパターンが不要になるケースが増えている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年時点でtRPCはNext.js/TypeScriptスタックのデファクトに近づいており、クライアント〜サーバー間の型共有がゼロコスト・ゼロスキーマで実現できる点が開発速度を大幅に向上させている。

- **GraphQLの棲み分けの明確化:** GraphQLは複数クライアント（モバイル・Web・サードパーティ）が異なるデータ形状を必要とするBFF層やパブリックAPIに特化し、内部サービス間ではtRPCやgRPCに置き換えられる傾向が加速している。

- **RESTは「枯れた技術」として再評価:** OpenAPI 3.1 + Zodスキーマ生成の組み合わせにより、RESTでも型安全なクライアントSDKの自動生成が容易になり、外部公開APIや規制業界では依然として最有力の選択肢。

- **Server Actions / RPCパターンの普及:** Next.js 15のServer ActionsやReact Server Componentsの普及により「APIレイヤーを明示的に設計しない」アーキテクチャが現実的になり、社内ツールや小規模プロダクトではtRPCすら省略するケースが増えている。

- **エッジ・ストリーミング対応が選定基準に:** Vercel Edge / Cloudflare Workersでの動作要件が厳しくなる中、REST/tRPCは対応容易だがGraphQLサブスクリプションのエッジ展開はまだ課題が多く、リアルタイム要件のあるAPIはSSEまたはWebSocket設計を別途検討する必要がある。

### 4. serverless edge computing 2026

- **ポイント1: エッジでのAI推論の標準化:** WebAssembly（WASM）とWASI 2.0の成熟により、エッジノードでの軽量LLM推論（1-7Bパラメータ）が実用レベルに達した。レイテンシ重視のユースケースではクラウド往復を排除できる。

- **ポイント2: Deno Deploy / Cloudflare Workers の収束:** V8 Isolateベースのランタイムがde facto標準となり、Node.js互換性も大幅改善。`node:crypto`や`node:stream`がエッジで動くため、既存コードの移植コストが激減した。

- **ポイント3: エッジDBの台頭:** Cloudflare D1、Turso（libSQL）、Neon Serverlessがエッジ近傍にレプリカを配置。読み取りレイテンシは<10msを実現しつつ、書き込みは中央に集約するCQRS的アーキテクチャが定番パターンになっている。

- **ポイント4: Cold Start問題の実質的解消:** Isolate事前暖機とメモリスナップショット技術（V8 Snapshotの進化）により、Cold Startが0-5ms台に。Lambdaのような数百msの遅延はエッジでは過去の話になった。

- **ポイント5: オブザーバビリティの課題が顕在化:** エッジは分散ノード数が膨大なため、従来のAPMツールが追いつかない。OpenTelemetry + Tailベースサンプリングによるエッジネイティブなトレーシングへの投資が急務であり、本番投入前にこの設計を固めることが重要。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の本格採用:** 2026年時点でパスワードレス認証はデファクトスタンダードになりつつある。パスキーはフィッシング耐性が高く、生体認証と組み合わせることでUXとセキュリティを両立できる。

- **ゼロトラスト＋継続的認証:** ログイン時の一度限りの認証では不十分。セッション中もリスクスコアを動的評価し、異常検知時に再認証を要求するアダプティブ認証が標準的なアプローチになっている。

- **トークン設計の厳格化:** JWTのアクセストークンは有効期限を15分以内に短縮し、リフレッシュトークンのローテーション（Refresh Token Rotation）を必須化。トークン漏洩時の被害半径を最小化する設計が求められる。

- **サプライチェーン攻撃への対策:** OAuth/OIDCライブラリや認証プロバイダー（Auth0, Cognito等）のアップデートを自動化し、依存ライブラリの脆弱性をCIパイプラインでスキャンする体制が不可欠。

- **MFAの疲労攻撃（MFA Fatigue）対策:** プッシュ通知型MFAへの繰り返し承認要求攻撃が増加。番号マッチング（Number Matching）やコンテキスト情報表示を必須にし、単純なプッシュ承認を廃止することが推奨される。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x の Edge Runtime 対応成熟:** Prisma Client がVercel Edge / Cloudflare Workers で安定稼働するようになり、Supabase の Connection Pooler（PgBouncer / Supavisor）と組み合わせることでサーバーレス環境でのコールドスタート問題がほぼ解消された。

- **Supabase Supavisor が PgBouncer を置き換え:** Elixir製の Supavisor は水平スケール可能なコネクションプーリングを提供し、大量の同時接続（数万規模）でも安定。Prisma の `DATABASE_URL` に `?pgbouncer=true&connection_limit=1` を付与する運用が標準化されている。

- **RLS（Row Level Security）× Prisma の併用パターン確立:** Supabase の RLS をデータ層のセキュリティ境界とし、Prisma はアプリ層のクエリビルダーに徹する分離設計が主流。`SET LOCAL role` でサービスロールと匿名ロールを切り替える実装が増加。

- **Prisma Accelerate でグローバルキャッシュ:** Prisma の managed CDN キャッシュレイヤー（Accelerate）が Supabase と組み合わさることで、リードレプリカなしでも読み取りレイテンシを大幅削減できる構成が現実的な選択肢になっている。

- **スキーマ管理の二重管理問題に注意:** Supabase Migrations（`supabase db push`）と Prisma Migrate を混在させると競合しやすい。2026年時点のベストプラクティスは「Prisma Migrate を主軸にし、Supabase ダッシュボードからの直接DDL変更を禁止する」か、逆に「Supabase Migrations のみを使い Prisma は `prisma db pull` でスキーマを同期する」かの二択に収束している。

### 7. WebAssembly Rust performance 2026

- **Component Model（WASI 0.2）の成熟:** 2026年現在、WASI Preview 2が安定化し、RustのWasmコンポーネントが言語間インターフェースを型安全に共有できるようになった。`cargo component`ツールチェーンが実用段階に入り、マイクロサービス間の軽量RPCとして採用が加速している。

- **SIMD・スレッド拡張の普及:** WebAssembly SIMDとShared Memoryがほぼ全ブラウザ・ランタイムで標準サポートされ、Rustの`std::arch`や`rayon`を活用した並列処理がネイティブに近いスループットを達成。画像処理・機械学習推論などCPU集約タスクで特に効果的。

- **起動レイテンシの克服:** AOT（Ahead-of-Time）コンパイルとWasmtime/Wasmerの最適化により、コールドスタート問題が大幅に改善。FaaSやエッジコンピューティング（Cloudflare Workers、Fastly Compute）でRust+Wasmがコンテナの代替として現実的な選択肢になっている。

- **バイナリサイズの最適化成熟:** `wasm-opt`（Binaryen）+ LTOの組み合わせで、`no_std`を使わなくても実用的なサイズに収まるケースが増えた。ただしアロケータ選択（`wee_alloc`→`dlmalloc`移行など）は依然として設計判断が必要。

- **GC提案とRustの立ち位置:** WasmGC（Garbage Collection拡張）の普及でKotlin/DartなどGC言語のWasm対応が進んでいるが、Rustはそもそも不要であり「GCなしで最高性能」という差別化が明確化。メモリ安全性とゼロオーバーヘッドの組み合わせでシステム寄りWasmワークロードのデファクトとして地位を固めつつある。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの設計:** デフォルトでServer Componentsを使い、インタラクティブ性が必要な箇所のみ`'use client'`を付与する。クライアントバンドルを最小化し、Core Web Vitalsが大幅に改善される。

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降でStableになったPPRにより、静的シェルと動的コンテンツを同一ルートで混在させられる。`<Suspense>`境界を適切に設計することがパフォーマンスの鍵。

- **Server Actions によるデータミューテーション:** API Routeを介さずフォーム送信やデータ更新を`'use server'`関数で直接処理。`useActionState`と組み合わせることで、楽観的UIとエラー処理を簡潔に実装できる。

- **Parallel Routes / Intercepting Routes の戦略的利用:** モーダル・サイドパネル・タブUIを`@slot`構文で実現し、URLを保持したままオーバーレイ表示が可能。ディープリンク対応と直感的なナビゲーションを両立できる。

- **`unstable_cache` / `use cache` によるきめ細かなキャッシュ制御:** ページ単位ではなく関数・クエリ単位でキャッシュを管理する設計が主流に。`revalidateTag`でオンデマンド無効化を組み合わせると、CDNライクな効率性をEdgeなしで達成できる。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge RuntimeでのStreaming Response活用:** 2026年時点でVercel Edge FunctionsはStreaming SSEとReadableStreamが安定化しており、AIレスポンスやリアルタイムデータをCDNエッジから直接ストリーミングすることでTTFBを大幅削減できる。

- **ポイント2: Cold Start最小化のためのWasm活用:** Node.js依存を避けWASMモジュールに移行することでEdgeのCold Startをほぼゼロに抑えられる。特に認証・暗号化処理はWasmネイティブ実装が主流になりつつある。

- **ポイント3: ISR + Edge Middlewareの組み合わせ戦略:** Incremental Static Regenerationとの組み合わせでキャッシュ戦略を最適化し、`stale-while-revalidate`をEdgeレイヤーで制御することでオリジンへのリクエストを最小化できる。

- **ポイント4: 地理的ルーティングとA/Bテストの標準化:** `geo`オブジェクトを利用したリージョン別コンテンツ出し分けとフィーチャーフラグ制御がEdge Middlewareで完結できるようになり、クライアントサイドのちらつきを排除できる。

- **ポイント5: Edge Functionsのメモリ・CPU制限への対応:** 128MB/50msの制限を踏まえ、重い処理はServerless Functionsに委譲しEdgeは「ルーティング・認証・軽量変換」のみに限定する責務分離が2026年のベストプラクティスとして定着している。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `type UserId = string & { readonly __brand: 'UserId' }` パターンが広く採用され、プリミティブ型の誤用をコンパイル時に防ぐ手法が定着。ライブラリ（zod-to-ts等）も自動的にBranded Typesを生成するようになった。

- **Template Literal Types の高度活用:** APIルート、CSSクラス、SQLクエリをリテラル型で表現することで、ランタイムエラーをゼロにするアプローチが主流。`type Route = `/api/${string}`は今やボイラープレートではなく必須パターン。

- **`satisfies` 演算子の徹底活用:** `as const satisfies Schema` の組み合わせで、型推論を保ちながら型制約を強制する。`as`キャストを廃止する方向でコードレビュー基準に組み込むチームが増加。

- **Exact Types（過剰プロパティ禁止）の実装:** TypeScriptのstructural typingの落とし穴を補うため、`type Exact<T, U extends T = T> = U extends T ? T extends U ? U : never : never` のようなヘルパーが実用段階に入り、APIレスポンスの型安全性が向上。

- **型レベルテスト（`tsd` / `expect-type`）のCI統合:** 実装コードのユニットテストと同様に型の正確性をCIで検証することが標準化。型定義の変更によるリグレッションを自動検出し、型破壊的変更をリリース前にブロックする運用が浸透。
