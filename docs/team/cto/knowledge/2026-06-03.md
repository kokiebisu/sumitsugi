# CTO Knowledge - 2026-06-03

## Daily Update (2026-06-03)

### 1. Next.js performance optimization 2026

- **React Server Components の徹底活用:** RSCをデフォルトとし、クライアントコンポーネントを最小限に抑えることでバンドルサイズを劇的に削減できる。`'use client'`境界を慎重に設計し、インタラクティブ部分のみに限定するのが2026年の標準プラクティス。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降で安定化したPPRにより、静的シェルと動的コンテンツを単一リクエストで配信可能になった。Suspense境界を適切に設計することでTTFBとLCPを同時に改善できる。

- **`next/image` と `next/font` の最適化強化:** AVIFフォーマットへの移行とフォントサブセット化を組み合わせることで、ページウェイトを30〜50%削減できるケースが増えている。`sizes`属性の精密な指定がCLS防止に直結する。

- **Server Actions のパフォーマンス設計:** Server Actionsはネットワークウォーターフォールを減らす強力な手段だが、楽観的UIアップデート（`useOptimistic`）と組み合わせることでUXとパフォーマンスを両立させることが重要。

- **Edge Runtime とキャッシュ戦略の再設計:** `fetch`のキャッシュオプション（`force-cache`, `revalidate`）とRoute Handlersのキャッシュヘッダーを組み合わせた細粒度キャッシュが主流。Cloudflare Workers等のEdge環境での地理的近接化によるレイテンシ削減も標準的な選択肢になっている。

### 2. React Server Components streaming 2026

- **Suspense境界の細粒度化が標準に:** 2026年現在、RSCとSuspenseを組み合わせた「コンポーネント単位のストリーミング」が主流となり、ページ全体のウォーターフォールを排除してTTFBとLCPを大幅に改善できる。

- **Server ActionsとStreaming UIの統合:** フォーム送信後のUI更新をServer Actions + `useOptimistic` + Streamingで即時フィードバックするパターンが定着し、クライアントサイドの状態管理ライブラリへの依存を最小化できる。

- **PPR（Partial Prerendering）の本格普及:** Next.js 15以降でPPRが安定化し、静的シェルを即座に配信しつつ動的部分のみストリームするハイブリッド戦略が、CDNキャッシュ効率とUX両立の最適解となっている。

- **Edge RuntimeとStreaming相性の向上:** Cloudflare Workers / Vercel Edge FunctionsでのRSCストリーミングが成熟し、コールドスタートレイテンシが実質的に問題にならないレベルに達したため、グローバル配信の設計選択肢が広がった。

- **デバッグ・オブザーバビリティがまだ課題:** ストリーミングのウォーターフォール分析はReact DevToolsとServer Timing APIの組み合わせが必要で、可視化ツールのエコシステムはまだ成熟途上 — チーム導入時はこのオーバーヘッドを見積もりに含めること。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの実用的成熟:** 2026年時点でtRPCはNext.js/TypeScriptスタックのデファクトになりつつあり、型安全をエンドツーエンドで保証しながらスキーマ定義コストをほぼゼロにできる。特にフルスタックTypeScriptプロジェクトでは REST/GraphQLより開発速度が明確に優位。

- **GraphQLの棲み分け確立:** 複数クライアント（モバイル・Web・外部パートナー）が異なるデータ形状を要求するユースケースに特化し、社内APIに使うのはオーバーエンジニアリングという認識が定着。Relay/Fragmentsベースのコロケーションパターンが標準化されつつある。

- **REST+OpenAPIの堅牢性再評価:** Zodベースのスキーマ定義（Zod → OpenAPI自動生成）により型安全なREST APIが低コストで実現でき、外部公開APIや言語をまたぐ連携では依然RESTが最適解。`hono` + `@hono/zod-openapi` の組み合わせが注目を集めている。

- **エッジ・ストリーミング対応が設計の新軸:** Server-Sent Events / HTTP Streaming がLLM統合で必須化し、REST/GraphQL/tRPCいずれも「ストリーミングファースト」設計を考慮しなければならない時代に。tRPCのサブスクリプションやGraphQL Live Queriesが実運用に入り始めている。

- **API設計の判断基準（2026版）:** 内部フルスタックTS → tRPC、外部公開/マルチクライアント → REST+OpenAPI、複雑なデータグラフ/BFF → GraphQL。この三択を初期設計時に明示的に決定することがアーキテクチャ負債を防ぐ最重要プラクティス。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジの標準ランタイムに:** Cloudflare Workers・Fastly Compute@Edgeを中心に、Wasmがコンテナに代わるエッジ実行単位として定着。コールドスタートがほぼゼロになり、多言語対応も実現している。

- **エッジDB・ストレージの成熟:** Cloudflare D1・Turso・Neon Branchingなど、エッジに近いSQLiteベースのDBが本番利用に耐える品質に到達。読み取りレイテンシの劇的な削減が可能になった一方、書き込み整合性の設計は依然として重要な検討事項。

- **AI推論のエッジシフト加速:** 量子化モデル（Llama系、Phi-3 miniなど）をエッジで直接実行するパターンが増加。Cloudflare Workers AIやVercel AI SDKのエッジサポートにより、中央クラウドへのラウンドトリップなしで低レイテンシ推論が実現できる。

- **オブザーバビリティの整備が急務:** エッジ実行は分散度が高くデバッグが困難。OpenTelemetryのエッジ対応（Baselime買収後のCloudflare統合など）が進んでいるが、ローカル再現性の低さは開発体験上のボトルネックのまま。

- **コスト構造の再評価:** リクエスト数課金モデルはトラフィック増加時に予想外のコスト増を招くケースが増加。CPU時間ベース課金（Workers等）への移行設計と、エッジ vs オリジンの適切な責務分担が、アーキテクチャ意思決定の核心になっている。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** FIDO2/WebAuthn標準のパスキーがパスワード認証を実質的に置き換えつつあり、フィッシング耐性とUX向上を同時に実現できる。Apple/Google/Microsoftのエコシステム統合により、エンタープライズでも採用障壁が大幅に低下した。

- **ゼロトラスト前提のセッション管理:** 「一度認証すれば信頼」モデルは廃止され、短命トークン（アクセストークン5〜15分）＋継続的なデバイス・行動リスク評価が標準となっている。JWTのステートレス性に依存しすぎず、サーバーサイドでの無効化機構を必ず持つべき。

- **MFAの「疲労攻撃」対策:** プッシュ通知型MFAへのMFA Fatigue攻撃が増加しており、番号マッチング（Number Matching）や位置情報コンテキストの付加が必須対策となった。TOTPよりもハードウェアキーまたはパスキーへの移行を優先すること。

- **AIを使ったクレデンシャルスタッフィング対策:** 漏洩パスワードリストを使った自動化攻撃がAIで高度化しており、Have I Been Pwned API連携によるリアルタイム漏洩チェックと、ログイン試行のベースライン行動分析の組み合わせが現実的な防御策。

- **サプライチェーンリスクとしての認証ライブラリ管理:** OAuthライブラリやIDPのSDKは攻撃対象として注目されており、依存パッケージのSBOM管理とピン留め（exact version pinning）、定期的なセキュリティ監査を開発フローに組み込むことが不可欠。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x + Supabase の統合成熟:** Prisma 6ではEdge Runtime対応が強化され、Supabase Edge FunctionsからPrismaを直接利用するパターンが実用レベルに達した。接続プーリングはPgBouncerよりSupabase独自の`supavisor`が標準となり、サーバーレス環境での接続枯渇問題が大幅に改善された。

- **Row Level Security (RLS) との責務分担が設計の核心:** SupabaseのRLSをDBレイヤーの最終防衛線として使い、Prismaは型安全なクエリ構築に専念する二層設計が定着。アプリ層のバグがデータ漏洩に直結しない堅牢なアーキテクチャを低コストで実現できる。

- **Prisma Accelerate によるグローバルキャッシュ戦略:** Prisma AccelerateのエッジキャッシュとSupabaseのレプリカ読み取りを組み合わせることで、読み取り重視アプリのレイテンシを劇的に削減可能。ただしキャッシュ無効化戦略を設計段階で決めないと整合性バグの温床になる。

- **型安全マイグレーションの自動化:** `prisma migrate dev`とSupabase CLIの`supabase db push`が競合しないよう、どちらをsource of truthにするか明確化が必要。2026年時点ではPrismaスキーマを正とし、CIでマイグレーションの差分を自動検証するパターンがベストプラクティスとして確立されている。

- **Realtime + Prismaの使い分け:** リアルタイム同期にはSupabase Realtimeを直接使い、Prismaはバッチ処理・複雑クエリ・トランザクションに限定する役割分担が効率的。両方を中途半端に使うとコードの責務が曖昧になるため、「Realtimeはsubscription、Prismaはmutation/complex read」という境界線を明示的にアーキテクチャドキュメントに記載することを推奨。

### 7. WebAssembly Rust performance 2026

- **Component Model の普及加速:** WASIp2（WASI Preview 2）とComponent Modelが2026年に実用段階に入り、RustのWasmコンポーネントをホスト言語に依存せず安全に合成できるようになった。マイクロサービスの代替としてWasmコンポーネント設計が現実的な選択肢になっている。

- **SIMD・スレッド対応の成熟:** WebAssembly SIMDとShared Memoryスレッドのブラウザ対応が安定し、Rustの`rayon`相当の並列処理をWasm上で実現できるケースが増えた。画像処理・音声・暗号処理での純Wasmの速度はネイティブの80〜90%に到達。

- **起動レイテンシの改善（Wizer / AOT）:** `wizer`によるpre-initializationやWasmtime・V8のAOTコンパイルにより、コールドスタートが大幅に短縮。Rustで書いたWasmをエッジ環境（Fastly Compute、Cloudflare Workers）にデプロイする際のオーバーヘッドがほぼ無視できる水準に。

- **バイナリサイズ最適化の実用化:** `wasm-opt`（Binaryen）＋`cargo`の`opt-level="z"`＋`wasm-pack`の組み合わせで、プロダクション用途のバイナリを100KB以下に収めるノウハウが確立。フロントエンドへの組み込みコストが現実的になった。

- **Rust ↔ JS バインディングの低オーバーヘッド化:** `wasm-bindgen`の改善とInterface Types提案の進展により、RustとJavaScript間のデータ受け渡しコストが削減。頻繁に呼び出すホットパスでも境界越えのペナルティが問題になりにくい設計が可能になった。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** 2026年のベストプラクティスは「クライアントコンポーネントは例外」として扱うこと。データフェッチはServer Componentsで完結させ、`'use client'`はインタラクション境界のみに限定することでバンドルサイズを最小化できる。

- **Parallel Routes + Intercepting Routes の活用:** モーダルやスライドオーバーなどのUI パターンを URL-aware に実装できるため、ディープリンク対応とUXの両立が可能。複雑なレイアウトをネストされた`@slot`で分割することで、ローディング状態の粒度も向上する。

- **`use cache` / `cacheTag` による細粒度キャッシュ制御:** Next.js 15以降で安定した `use cache` ディレクティブにより、関数・コンポーネント単位でのキャッシュ戦略が宣言的に書ける。`revalidateTag` と組み合わせることで、ISRより柔軟なオンデマンド再検証が実現する。

- **Suspense境界の戦略的配置:** `loading.tsx` はルート全体のフォールバックに留め、細かいSuspense境界をコンポーネントレベルで配置することでストリーミングSSRの恩恵を最大化できる。ウォーターフォールを避けるため、`Promise.all`で並列データフェッチを意識的に設計することが重要。

- **Server Actions のフォームとミューテーション統合:** `useFormState` / `useActionState` とServer Actionsの組み合わせにより、APIルートを介さずサーバーサイドのバリデーション・DB操作が直接呼び出せる。ただし楽観的更新（`useOptimistic`）を合わせて実装しないとUXが劣化するため、セットで設計すること。

### 9. Vercel Edge Functions optimization 2026

- **Cold Start排除のためのStreaming優先設計:** Edge Functionsは起動時間が短いが、レスポンスのStreaming（`ReadableStream`）を活用することで体感レイテンシをさらに削減できる。Next.js 15+の`streaming: true`設定との組み合わせが特に効果的。

- **Edge ConfigとKVの戦略的キャッシュ層:** Vercel Edge ConfigはリクエストごとにDBを叩くのではなく、フィーチャーフラグや設定値を超低レイテンシで読み取るために使う。動的データはVercel KVをEdge近傍に配置してキャッシュ戦略を設計する。

- **Middleware vs Route Handlersの役割分離:** 認証チェック・地域リダイレクト・A/Bテストの振り分けはMiddlewareで行い、ビジネスロジックはRoute Handlersに委ねる。Middlewareに重い処理を入れると全ルートに影響するため、処理は最小限に抑える。

- **バンドルサイズの厳格管理（1MB上限）:** Edge RuntimeはNode.js APIのサブセットしか使えず、バンドル上限が厳しい。`import`するライブラリを慎重に選択し、`@vercel/edge`のビルトインユーティリティを優先する。`next build`後のバンドル解析を必ずCI/CDに組み込む。

- **地理情報の積極活用でパーソナライズ:** `request.geo`（国・都市・地域）や`request.headers.get('x-vercel-ip-timezone')`をEdge層で読み取り、コンテンツの出し分けをオリジンへの往復なしに実現できる。日本向けサービスでは`country === 'JP'`判定をMiddlewareで行うだけで体験が大きく向上する。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の標準化:** TypeScript 4.9で導入された`satisfies`が2026年の型安全パターンの基本となり、型推論を保持しながら型チェックを行える。`const config = { port: 3000 } satisfies Config`のように記述することで過剰なキャストを排除できる。

- **Template Literal Typesによる文字列の型安全:** APIルートやイベント名などの文字列を`type Route = \`/api/${string}\``のように型定義する手法が定着し、ランタイムエラーをコンパイル時に検出できるようになった。

- **Zodを中心としたスキーマファースト設計:** バリデーションとTypeScript型定義をZodスキーマから自動生成する`z.infer<typeof schema>`パターンが事実上の標準となり、境界値検証と型安全の一元管理が実現できる。

- **`const`型パラメータとVariance Annotations:** TypeScript 5.xで導入された`const`型パラメータと共変・反変アノテーション（`in`/`out`）により、ジェネリック型の意図を明示でき、型推論の精度と安全性が大幅に向上した。

- **`NoInfer<T>`による型推論の制御:** TypeScript 5.4+の`NoInfer<T>`ユーティリティで、意図しない型の拡張を防ぎ、特にライブラリ設計において呼び出し側への型漏れを防ぐパターンが普及している。
