# CTO Knowledge - 2026-09-02

## Daily Update (2026-09-02)

### 1. Next.js performance optimization 2026

- **ポイント1:** Next.js 16ではPartial Prerendering（PPR）が正式GA化され、静的シェルと動的コンテンツを1つのルートで組み合わせられるため、TTFBを保ちながら個人化されたUIを配信できる。物件詳細ページのような「静的な物件情報＋動的な空き状況」構成に最適。
- **ポイント2:** Turbopackがビルド・devサーバーのデフォルトとなり、大規模コードベースでもHMRとプロダクションビルドが大幅高速化。CI時間短縮とローカル開発体験向上に直結するため、`bun run build`の待ち時間削減が期待できる。
- **ポイント3:** `next/image`とCache Componentsの組み合わせで、画像最適化とデータフェッチのキャッシュ戦略をコンポーネント単位で明示的に制御可能に。物件写真が多いsumitsugiのようなサービスではCore Web Vitals（特にLCP）改善に直接効く。
- **ポイント4:** Server Actionsの型安全性とストリーミングUIパターンが成熟し、フォーム送信（内見予約・問い合わせ等）でのローディング状態管理が簡素化。クライアントJSバンドルを削減しつつUX向上が可能。
- **ポイント5:** React Compilerの安定版採用により、手動`useMemo`/`useCallback`の必要性が減少しコードがシンプルになる一方、ビルド時最適化に依存するためlintルールとCIでの検証が重要になる。

### 2. React Server Components streaming 2026

- **ポイント1（Partial Prerendering の主流化）:** Next.js 16ではPPR（静的シェルを即座に返し、動的部分だけをストリーミング）が事実上のデフォルトパターンとなり、TTFBを保ちながら個人化コンテンツを配信できる。物件一覧のような「静的なレイアウト＋動的な空室状況」構成に特に有効。

- **ポイント2（Suspense境界の粒度設計が重要に）:** ストリーミングの効果はSuspense境界の切り方に依存するため、「引越し費用計算」や「前の住人レビュー」など重い非同期処理を個別のSuspense境界に分離し、コア情報（物件写真・価格）を先に表示する設計が推奨される。

- **ポイント3（Server Actionsとの統合が成熟）:** RSCストリーミングとServer Actionsの組み合わせにより、フォーム送信後の楽観的UI更新とストリーミング再描画がシームレスになり、内見予約フォームなどのマルチステップフローで往復レイテンシを削減できる。

- **ポイント4（キャッシュ戦略の複雑化に注意）:** `use cache`ディレクティブとストリーミングの組み合わせは強力だが、キャッシュタグの粒度を誤ると「前の住人」情報更新時にステールデータが配信されるリスクがあるため、物件ステータス変更（draft/public）に連動したキャッシュ無効化の設計が必須。

- **ポイント5（エッジランタイムとの相性）:** ストリーミングSSRはエッジランタイムでの地理的レイテンシ削減と相性が良く、海外からのアクセスが想定される多言語対応時に検討価値がある一方、Node.js依存のライブラリ（PDF生成等）との互換性確認が必要。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** 2026年時点でtRPCはNext.jsフルスタックTypeScript構成における社内API標準として定着しつつあり、フロントエンドとバックエンドの型を共有できるため、sumitsugiのようなApp Router構成では手動のスキーマ同期コストを削減できる。
- **ポイント2:** GraphQLは複雑な関係性データ（物件・前の住人・次の住人・引継ぎ履歴など）を1リクエストで取得する用途に強いが、キャッシュ戦略とN+1問題の運用コストが高く、シンプルなCRUD中心のMVPでは過剰投資になりやすい。
- **ポイント3:** RESTはシンプルな公開API・Webhook・外部連携（決済、電子契約サービスなど）において依然として最も相互運用性が高く、外部弁護士確認後の法務・契約フロー連携ではREST＋OpenAPI仕様が無難な選択肢。
- **ポイント4:** 2026年のトレンドとして「BFF層でtRPC、外部公開APIはREST」というハイブリッド構成が主流化しており、sumitsugiも内部の物件・ユーザー操作はtRPC、将来的な外部パートナー連携用エンドポイントはRESTで分離する設計が拡張性の観点で有利。
- **ポイント5:** どの方式を採るにせよZodによるスキーマバリデーションを境界（API入出力）に必ず配置する運用がベストプラクティスとして定着しており、既存のCLAUDE.md規約（Zod at system boundaries）とも整合する。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化が進行:** WinterCG仕様（Web-interoperable Runtimes）への準拠が進み、Cloudflare Workers・Vercel Edge・Deno Deployなど主要プラットフォーム間でのコード互換性が向上。ベンダーロックインを避けた設計が現実的な選択肢になっている。

- **コールドスタートの実質ゼロ化:** V8 isolateベースの分離実行モデルが主流となり、コンテナ起動のオーバーヘッドがほぼ解消。認証チェックやリダイレクトなど軽量なミドルウェア処理をエッジで完結させ、オリジンサーバーへのリクエスト数自体を削減する設計が定着している。

- **エッジDBとの組み合わせがデファクト化:** Turso（libSQL）やCloudflare D1のようなエッジネイティブDB、あるいはグローバルレプリケーション対応のKVストアと組み合わせることで、読み取り中心の処理をユーザーに最も近いロケーションで完結できるように。sumitsugiのような物件検索・一覧表示は特に恩恵が大きい領域。

- **観測性（Observability）ツールの成熟:** 分散実行ゆえに従来のAPM導入が難しかったエッジ環境でも、OpenTelemetry対応やベンダー独自のトレーシングツールが整備され、本番デバッグの障壁が下がった。導入前提でログ設計をしておくと後戻りが少ない。

- **コスト構造の逆転リスクに注意:** リクエスト課金モデルはトラフィックが伸びるほどオリジンサーバーより割高になるケースがあるため、アクセス集中が見込まれる機能（画像配信・検索API等）では従来型サーバーとのハイブリッド構成を検討する価値がある。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への全面移行:** パスワードレス認証が業界標準となり、フィッシング耐性のあるパスキーがSMS OTPやTOTPを置き換えつつある。実装コストは初期は高いが、アカウント乗っ取りのリスクを大幅に低減できるため優先度を上げるべき。

- **セッション管理とトークンの短命化:** JWTなどのアクセストークンは有効期限を短く保ち、リフレッシュトークンのローテーションとデバイスバインディングを組み合わせることで、トークン漏洩時の被害範囲を最小化する設計が主流になっている。

- **継続的リスクベース認証（Adaptive Auth）:** ログイン時の一度きりの認証ではなく、デバイス指紋・IPレピュテーション・行動パターンを踏まえて継続的にリスクスコアを評価し、異常時のみ追加認証を要求する方式が、UXとセキュリティの両立策として定着している。

- **サプライチェーン経由の認証情報漏洩対策:** npm/依存パッケージの侵害を通じたシークレット窃取事例が増加しており、APIキーやシークレットをコードベースから排除し、Vault等のシークレット管理サービスと短命クレデンシャルの組み合わせが必須になりつつある。

- **プライバシー規制との整合:** 個人情報保護法・GDPR等の要件を踏まえ、認証ログや生体情報の保存期間・暗号化方式を明文化しておくことが、ローンチ前の法務確認フェーズでは特に重要（sumitsugiの現フェーズにも直結する論点）。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Supabaseは2026年にかけてPostgreS QLベースの「BaaS+Edge Functions」統合を強化しており、RLS（Row Level Security）をアプリ層の認可ロジックと併用する設計が標準化しつつある。sumitsugiのようにセラー/バイヤー間で厳密なアクセス制御が必要なプラットフォームでは、Prisma側のミドルウェアだけに頼らずDB層でもRLSを二重に効かせる構成が安全。

- **ポイント2:** Prisma 6系以降はSupabaseのPgBouncer（コネクションプーリング）との相性問題がかなり改善され、`directUrl`と`url`を分離する設定がベストプラクティスとして定着している。サーバーレス関数（Vercel等）からの同時接続数がスパイクしやすいため、この分離設定を怠るとコネクション枯渇で本番障害になりやすい。

- **ポイント3:** マイグレーション管理は「Prisma Migrate + Supabase CLIのマイグレーション」を併用するとコンフリクトが起きやすいため、どちらか一方を単一の真実源（source of truth）に決め、CI上でスキーマドリフト検知を自動化するのが2026年のデファクト。今のところPrisma Migrate単独運用が推奨される。

- **ポイント4:** Supabaseのリアルタイム機能（Realtime/Broadcast）とPrismaのORMレイヤーは直接統合されないため、通知機能（「引越し費用」確定通知など）を実装する場合はPrisma経由の書き込み後にSupabase Realtimeのトリガーを別途発火させる設計が必要。ここを見落とすとリアルタイム更新が反映されないバグになりやすい。

- **ポイント5:** ドラフト/公開ステータス（`'draft' | 'public'`）のような列挙値はDB層（Postgres enum or check constraint）とTypeScript型の両方で二重定義されがちなので、Prismaのスキーマを単一の真実源にし、Zodスキーマもそこから生成する運用にすると型不整合のバグを未然に防げる。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Rust 1.82以降で標準ターゲット化が進んだ`wasm32-wasip2`とWASI Preview 2により、コンポーネントモデル（Component Model）が実用段階に入り、異なる言語で書かれたWasmモジュール同士を型安全に組み合わせられるようになった。マイクロサービス的な設計をブラウザ外（サーバーサイド・エッジ）でも採用しやすくなっている。

- **ポイント2:** `wasm-bindgen`/`wasm-pack`のツールチェーンが成熟し、SIMD（`target-feature=+simd128`）とマルチスレッド（`wasm-threads` + `SharedArrayBuffer`）がstable扱いに近づいたことで、画像処理・動画エンコード・物理演算のようなCPU負荷の高い処理をブラウザ内でネイティブに近い速度で動かせる事例が増えている。

- **ポイント3:** Wasmランタイム（Wasmtime, WasmEdge, Spin）がコールドスタート数ミリ秒を達成しており、Cloudflare WorkersやFastly Compute@EdgeのようなエッジFaaS基盤でRust+Wasmが「軽量コンテナ代替」として採用されるケースが2026年にかけて拡大している。

- **ポイント4:** バイナリサイズ最適化（`wasm-opt`, `twiggy`, LTO + `opt-level="z"`）のベストプラクティスが定着し、平均的なWasmバンドルサイズが大幅に削減された結果、モバイル回線でも実用的な初期ロード時間を実現できるようになった。

- **ポイント5:** 一方でJSとWasm間の境界越え（marshaling）コストは依然としてボトルネックであり、頻繁な小さいデータのやり取りが発生する設計では逆にネイティブJSより遅くなるケースもあるため、「計算集約的な処理をまとめてWasm側に寄せる」アーキテクチャ判断が引き続き重要。

### 8. Next.js App Router patterns 2026

- **ポイント1（Partial Prerendering の本格普及）:** Next.js 15で導入されたPPR（Partial Prerendering）が2026年には標準パターンとして定着し、静的シェルと動的コンテンツをストリーミングで組み合わせる設計が主流に。初期表示速度とパーソナライズの両立が容易になった。

- **ポイント2（Server Actions のセキュリティ強化が必須に）:** Server Actionsが広く使われる一方、CSRF対策・認可チェックの実装漏れがインシデントの主要因となっており、`use server`関数内での明示的な権限検証が標準プラクティスとして定着している。

- **ポイント3（キャッシュ戦略の複雑化と`cacheLife`/`cacheTag`活用）:** App Routerのキャッシュ制御API（`cacheLife`, `cacheTag`, `revalidateTag`）を使った細粒度キャッシュ管理が主流になり、単純な`revalidate`一律指定から、データ種別ごとの最適化されたキャッシュポリシー設計へ移行が進んでいる。

- **ポイント4（Server Components中心の状態管理見直し）:** クライアント側グローバル状態（Redux/Zustand）への依存が減り、Server Componentsでのデータフェッチ＋URL状態（searchParams）＋最小限のクライアント状態という三層構成が定着。バンドルサイズ削減とハイドレーションコスト低減に直結している。

- **ポイント5（Turbopackのビルド標準化）:** Turbopackが安定版としてデフォルトビルドツールになり、開発時HMRだけでなく本番ビルドでも採用が進行。大規模プロジェクトでのビルド時間短縮が競争力に直結する要素として注目されている。

### 9. Vercel Edge Functions optimization 2026

- **統合されたランタイムモデル:** 2025年6月にVercelは単独の「Edge Functions」製品を廃止し、Edge RuntimeはFluid Compute配下のVercel Functionsに統合された。実装単位で「Edgeランタイム（軽量・低レイテンシ）」か「Nodeランタイム（npmパッケージフル対応）」を選ぶ設計になったため、関数ごとに最適なランタイムを選定する判断がアーキテクチャ上重要になる。

- **単一責務の徹底:** Edge Functionsはリダイレクト・リライト・認証チェックなど、CPUバウンドでない単一責務のタスクに特化させ、重い処理はリージョナルバックエンド（Node runtime）に委譲するのがベストプラクティス。これによりCPU時間とコールドスタートを最小化できる。

- **軽量依存関係の維持:** 重いnpmパッケージへの依存を避け、関数を小さく保つことでバンドルサイズとレイテンシを抑える。sumitsugiのようなミドルウェア（認証・リダイレクト等）を持つ構成では特に重要な指針。

- **分散環境での可観測性:** エッジ実行は複数リージョンに分散するため、構造化ログとモニタリングを意識的に設計しないと障害追跡が困難になる。従来の単一サーバー的なログ運用は通用しない。

- **キャッシュ戦略との併用:** ISR（Incremental Static Regeneration）やJamstack的アーキテクチャと組み合わせることで、エッジ実行の低レイテンシ効果を最大化できる。sumitsugiの物件一覧・詳細ページなど読み取り比率の高いページで有効な選択肢。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x以降の`satisfies`演算子と`const`型パラメータの組み合わせが標準化し、型推論を保ちながら過剰な型注釈を排除するパターンが主流になっている。本プロジェクトでもZodスキーマと`satisfies`を併用すれば、`src/lib/data.ts`のような設定オブジェクトの型安全性を保ちながら冗長な型定義を減らせる。

- **ポイント2:** Zod・Valibotなどのスキーマバリデーションライブラリから型を生成する「スキーマ駆動型定義」が定着し、ランタイム検証と静的型を単一ソースで管理するのがベストプラクティスになっている。`.claude/rules/standards.md`が定めるZod境界検証の方針と直接合致するため、APIレスポンスやフォーム入力の型はスキーマから`z.infer`で導出すべき。

- **ポイント3:** Discriminated Union（タグ付きユニオン）による状態管理が、`'draft' | 'public'`のようなステータス型でも単純なリテラルユニオンより推奨されるケースが増えている。将来ステータスが増える場合は`{status: 'draft'} | {status: 'public', publishedAt: Date}`のような構造にすると、状態ごとに必要なプロパティをコンパイル時に強制できる。

- **ポイント4:** TypeScript 6系ロードマップで議論されているネイティブGo実装コンパイラ（tsc→tsgo）により型チェック速度が大幅に向上する見込みで、大規模モノレポでのCI時間短縮が期待できる。`bun run build`のCI必須化方針とも相性が良く、導入時はビルド時間の計測をベンチマークとして残すとよい。

- **ポイント5:** テンプレートリテラル型とBranded Type（公称型）を使ったID型の区別（例: `UserId`と`ListingId`を文字列レベルで誤代入不可にする）が、大規模アプリのバグ予防策として一般化している。物件IDやユーザーIDが混在しやすいこのプロジェクトの構造上、導入すればランタイムエラーを未然に防げる可能性が高い。
