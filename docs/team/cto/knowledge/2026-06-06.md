# CTO Knowledge - 2026-06-06

## Daily Update (2026-06-06)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルを削減する最大の手段。`"use client"` は本当に必要な葉コンポーネントにのみ付与し、データフェッチは原則 Server Component で完結させる。

- **Partial Prerendering (PPR) の本番導入:** Next.js 15以降でstableになったPPRにより、静的シェル + 動的ストリーミングを1リクエストで実現できる。`<Suspense>` 境界の設計がパフォーマンスの鍵。

- **`next/image` と `next/font` の最適化は非交渉:** LCPに直結するため必須。特に `sizes` prop の適切な設定と、`font-display: swap` を避けた `optional` ローディング戦略が2026年のCore Web Vitals基準に有効。

- **Server Actions によるネットワークウォーターフォールの解消:** クライアントからのAPI呼び出しをServer Actionsに置き換えることで、RTTを削減しつつバンドルサイズも抑制できる。

- **Turbopack の活用で開発速度を上げ、品質投資に回す:** Next.js 16でTurbopackがデフォルトになり、HMRが大幅高速化。開発サイクル短縮によって生まれた時間をプロファイリングや計測に投資するのがCTO視点での正しいトレードオフ。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Pre-rendering（PPR）の本格普及** — Next.js 15以降でPPRがStableとなり、静的シェルを即座に配信しながらSuspense境界内の動的コンテンツをストリーミングするパターンが標準化。TTFBとLCPを両立できる。

- **ポイント2: Server Actionsとの統合が成熟** — RSCとServer Actionsの組み合わせで、クライアントJSバンドルを最小化しつつフォームやミューテーションを処理できる。`useOptimistic`との連携でUXを損なわずネットワーク往復を削減できる。

- **ポイント3: キャッシュ戦略の複雑化に注意** — Next.js App Routerのキャッシュレイヤー（Data Cache / Full Route Cache / Router Cache）が多層化しており、ストリーミングとの組み合わせで予期しないキャッシュヒットが発生しやすい。`revalidate`と`dynamic`設定の設計は早期から行うべき。

- **ポイント4: React 19の`use()`フックで非同期処理がシンプルに** — `use(promise)`によりSuspenseとPromiseの統合がより宣言的になり、ウォーターフォール回避のためのデータフェッチ並列化が書きやすくなった。

- **ポイント5: エッジランタイムとの相性が向上** — CloudflareやVercel Edgeでのストリーミング対応が安定し、グローバルなレイテンシ最適化が現実的に。ただしNode.js専用ライブラリとの互換性問題は引き続き設計時のリスクとして考慮が必要。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭:** TypeScript フルスタックプロジェクトでは tRPC が事実上の標準になりつつあり、型安全なエンドツーエンドAPIをスキーマ定義なしで実現できるため、Next.js + Prisma スタックとの相性が特に優れている。

- **GraphQL の選択基準の明確化:** GraphQL はマイクロサービス間のフェデレーション（Apollo Federation / Hive）や複雑なクライアント駆動クエリが必要なケースに限定されつつあり、単純なCRUDには過剰設計と見なされる傾向が強まっている。

- **REST の再評価と OpenAPI 3.1:** REST + OpenAPI 3.1 は `zod-openapi` や `Hono` 等のツールにより型安全性が大幅に向上し、「RESTで十分」という判断が 2026 年でも合理的な選択になっている。

- **エッジ対応とストリーミングAPI:** Vercel Edge / Cloudflare Workers の普及により、HTTP Streaming（`text/event-stream`, ReadableStream）を活用したリアルタイムAPI設計が重要トレンドになっており、WebSocket の代替として採用が進んでいる。

- **AIエージェント向けAPI設計:** MCP（Model Context Protocol）や OpenAI-compatible エンドポイントなど、LLMエージェントが呼び出すことを前提とした「機械可読性優先」のAPI設計が新たな設計軸として浮上している。

### 4. serverless edge computing 2026

- **WebAssembly (WASM) のエッジ標準化:** 2026年時点でWASIとComponent Modelの成熟により、言語非依存のエッジ関数が実用段階に。Cloudflare Workers・Fastly Computeがデファクトランタイムとして競合し、ベンダーロックインリスクを意識した設計が必須。

- **AI推論のエッジ配置が加速:** 小型LLM（1B〜7Bパラメータ）のエッジ実行が現実的になり、レイテンシとプライバシーの両立が可能に。ただしコールドスタート問題はGPU対応エッジノードで依然課題であり、モデルキャッシング戦略が差別化要因になる。

- **Durable Objects・SQLite on Edgeによるステートフル化:** エッジ＝ステートレスという前提が崩れ、Cloudflare Durable ObjectsやTurso（libSQL）の普及でエッジでのトランザクション処理が可能に。設計時に「どのデータをエッジに置くか」の判断がアーキテクチャの核心になった。

- **オブザーバビリティの遅れが最大の運用リスク:** 分散エッジ環境では従来のAPMが機能せず、OpenTelemetryのエッジ対応とサンプリング戦略の設計が後回しにされがち。本番投入前にトレース・ログ・メトリクスのパイプラインを確立しないと障害対応が困難になる。

- **コスト構造の再設計が必要:** リクエスト数課金からCPU時間・メモリ課金へのシフトにより、バースト処理よりも軽量・高頻度のユースケースで圧倒的なコスト優位性が生まれる。一方、重い処理をエッジに移すと逆にコスト増になるため、ワークロード分析なしの全面移行は危険。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の本格採用:** パスワードレス認証がデファクトスタンダードになりつつあり、フィッシング耐性が高くUXも優れたパスキーへの移行は2026年において最優先事項。主要ブラウザ・OSのサポートが成熟したため、実装コストも大幅に低下している。

- **ゼロトラスト＋継続的認証:** 「一度認証すれば安全」という前提を捨て、セッション中もリスクスコアを継続評価するアダプティブ認証が主流。デバイス状態・行動パターン・位置情報を組み合わせ、異常検知時に再認証を要求する設計が必須。

- **MFAの"フィッシング耐性"を評価軸に:** SMS/TOTPはSIMスワップやリアルタイムフィッシングに脆弱であることが広く認識され、FIDO2ベースのMFAのみを「強いMFA」と定義するガイドライン（NIST SP 800-63B改訂版）が基準になっている。

- **トークンの短命化とDPoP（Demonstrating Proof of Possession）:** JWTのアクセストークン有効期限を5〜15分に短縮し、DPoPヘッダーでトークン窃取後の悪用を防ぐRFC 9449が注目される。Bearer tokenのままでは不十分で、トークンバインディングが実装の差別化ポイントになる。

- **AIを活用した不正ログイン検知の内製化:** クラウドベースのFraud Detection APIだけでなく、自社データで訓練した軽量モデルをエッジ（認証サーバー直前）で動かすハイブリッドアーキテクチャが増加。レイテンシを抑えつつプライバシーも担保できる点で優位。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6のEdge Runtime対応:** Prisma 6.xではEdge Runtime（Cloudflare Workers、Vercel Edge）への対応が成熟し、`@prisma/adapter-neon`や`@prisma/adapter-pg`を介したHTTPベース接続が実用レベルに達した。サーバーレス環境でのコールドスタート問題が大幅に改善されている。

- **Supabaseのリアルタイム基盤強化:** Realtime v2とBroadcast/Presenceの安定化により、Supabaseは単なるPostgresホスティングを超えたリアルタイムアプリ基盤として確立。Row Level Security（RLS）との統合がより宣言的に書けるようになり、マルチテナント設計が容易になった。

- **PrismaとSupabase接続プーリングの必須化:** Supabase環境でのPrisma使用にはPgBouncerまたはSupavisor経由の接続プーリングが事実上必須。`DATABASE_URL`（プーリング用）と`DIRECT_URL`（マイグレーション用）の分離パターンが標準化されている。

- **型安全なDB操作の収束:** Prisma ClientとSupabase TypeScript SDKの自動型生成（`supabase gen types`）が成熟し、スキーマからE2Eで型安全を担保するアーキテクチャが一般的に。どちらを採用するかはRLSをDB層で担保するか（Supabase SDK）、アプリ層で担保するか（Prisma）の設計判断が分岐点。

- **マイグレーション管理のベストプラクティス:** Supabase CLIによる宣言的マイグレーション（`supabase db diff`）とPrisma Migrateの共存が増えているが、2つのマイグレーションシステムを同一プロジェクトで混在させると競合リスクがある。Prismaをスキーマの唯一の真実（Single Source of Truth）とし、Supabase CLIはローカルエミュレーション専用に役割を分離するパターンが安全。

### 7. WebAssembly Rust performance 2026

- **WASI Preview 2 の成熟:** WebAssembly System Interface のコンポーネントモデルが2026年に実用段階へ到達し、Rustで書いたWasmモジュールをサーバー・エッジ・ブラウザ横断で再利用できる基盤が整った。wasmtime や Spin v3 系エコシステムへの投資が加速している。

- **Cranelift / LLVM バックエンドの最適化:** Rustコンパイラの`wasm32-wasip2`ターゲット向けコード生成が改善され、ネイティブ比80〜90%のスループットが一般的なユースケースで達成されている。SIMD命令（Wasm SIMD128）の自動ベクトル化も実用的になった。

- **GC プロポーザルによるメモリ管理の変化:** WasmGC の普及でRustの線形メモリモデルが相対的に際立つ形に。GCなし言語であるRustはレイテンシ安定性の面で依然優位で、リアルタイム処理・ゲーム・音声処理に採用が増えている。

- **Extism / Component Model によるプラグインアーキテクチャ:** Rustで書いたWasmプラグインをホストアプリに動的ロードするパターンが定着。サンドボックス分離とゼロコピーインターフェース（shared-memory + wit-bindgen）の組み合わせで、セキュリティと性能を両立した拡張機構が構築できる。

- **Cloudflare Workers / Fastly Compute でのRust採用加速:** エッジランタイム上でのコールドスタートが1ms以下という実績が積み重なり、Node.js 代替としてRust+Wasmのスタックを選択するチームが増加。ただしビルドキャッシュ戦略（`cargo chef` 等）を怠るとCI時間が課題になる点は注意。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの設計:** クライアントコンポーネントは「葉」に留め、データフェッチとロジックはServer Componentsに集約する。バンドルサイズが大幅に削減され、初期表示が高速化する。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的コンテンツを同一ルートで混在させる PPR が安定化。`<Suspense>` 境界設計がアーキテクチャの中核になる。

- **`use cache` / `cacheTag` による細粒度キャッシュ:** Next.js 15以降の新しいキャッシュ API により、関数・コンポーネント単位でキャッシュ戦略を宣言的に制御できる。`revalidateTag` と組み合わせたオンデマンド無効化が標準パターンになっている。

- **Server Actions の責務分離:** フォーム送信・データ更新を Server Actions に集約し、API Routes の乱立を避ける。ただし、外部サービスから呼ばれる必要があるエンドポイントは引き続き Route Handlers を使う。

- **Parallel Routes + Intercepting Routes でモーダル設計:** URL を保持したままモーダルを実装する `@modal` スロットパターンが普及。シェアラブル URL とSPA的UXを両立できる。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択的活用:** Vercel Edge FunctionsはV8 isolateベースで低レイテンシだが、Node.js APIへのアクセスが制限されるため、認証・A/Bテスト・地理ルーティングなど「軽量ミドルウェア」用途に絞り、重い処理はServerless Functionsに残す設計が現実的。

- **Cold Start撲滅のためのStreaming優先:** 2025年以降のApp RouterではStreaming + Suspenseとの組み合わせが主流。Edge上でHTMLを先頭バイトから流すことでTTFBを大幅削減でき、LCP改善に直結する。

- **KV・Durable Objectsとのステート管理:** Edge自体はステートレスのため、Vercel KV（Upstash Redis互換）やCloudflare Durable Objectsとの組み合わせでセッション・レート制限を実装。リージョン間の一貫性トレードオフを事前に設計段階で議論すること。

- **バンドルサイズの厳格管理:** Edge Functionsの上限（1MB）は依然厳しく、`server-only`パッケージ・tree-shakingの徹底、重いライブラリ（date-fns全体import等）の排除が必須。`@next/bundle-analyzer`でCI時に自動チェックを組み込む。

- **Fluid Compute（2025〜）によるハイブリッド実行:** VercelのFluid Computeはリクエスト間でCPU時間を共有し、Edgeとサーバーレスの境界を曖昧にしつつある。固定アーキテクチャに縛られず、実測レイテンシ・コストで定期的に実行場所を見直す運用体制が2026年のベストプラクティス。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の本格普及:** TypeScript 4.9で導入された`satisfies`が2026年には標準的なパターンとなり、型推論を保持しつつ型チェックを行うことで、`as`キャストに頼った危険なコードを排除できる。

- **Template Literal Types + Branded Typesの組み合わせ:** `UserId`や`Email`などのBranded Typeが実務で定着し、プリミティブ型の誤用（IDの混同など）をコンパイル時に検出できるようになり、ランタイムエラーが大幅に減少している。

- **`const` type parametersによる精密な型推論:** TypeScript 5.xの`const`型パラメータにより、関数引数をリテラル型として推論させるパターンが普及し、マジックストリングの排除とIDEの補完精度向上を両立できる。

- **Zodを中心とした「Single Source of Truth」パターン:** ZodスキーマからTypeScript型を生成し、バリデーション・型定義・ドキュメントを一元管理するアプローチが標準化。境界値（APIレスポンス、フォーム入力）での型安全性が大幅に強化された。

- **`NoInfer`ユーティリティ型によるAPIデザインの改善:** TypeScript 5.4で導入された`NoInfer<T>`が推論の漏れを防ぎ、ライブラリ作者が意図しない型推論による誤用を設計段階でブロックできるようになっている。
