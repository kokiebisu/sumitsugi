# CTO Knowledge - 2026-06-02

## Daily Update (2026-06-02)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを劇的に削減できるRSCを最大限に使い、`'use client'`はインタラクティブな末端コンポーネントのみに限定する。

- **PPR（Partial Prerendering）の本格運用:** Next.js 15以降で安定化したPPRにより、静的シェルと動的コンテンツを同一ルートで共存させ、TTFB（初回バイト到達時間）と動的レンダリングを両立できる。

- **`next/after` によるレスポンス後処理:** レスポンス送信後に非同期処理（ログ・分析・キャッシュ更新）を実行できる`after()`APIで、ユーザー体感速度を損なわずにバックエンド処理を遅延実行する。

- **Turbopackの本番採用:** Next.js 15でデフォルト化されたTurbopackにより、大規模プロジェクトでのHMR・ビルド速度が従来比で大幅改善。`bun run dev`時のコールドスタートに特に効果的。

- **Cacheの明示的制御:** `unstable_cache`や`revalidateTag`を使ったきめ細かいキャッシュ戦略が重要で、「全部dynamic」「全部static」ではなくデータの鮮度要件ごとに使い分けることがパフォーマンスの肝となる。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化:** 2026年時点でのベストプラクティスは、データフェッチ単位でSuspense境界を細かく分割し、ウォーターフォールを排除すること。コンポーネントツリーの上位に大きな境界を一つ置くアンチパターンはTTFBを悪化させる。

- **Server Actionsとストリーミングの統合:** フォーム送信後のUI更新もストリーミングで返せるようになり、`useOptimistic`との組み合わせで楽観的UIとサーバー確定UIの差分を最小化できる。

- **PPR（Partial Prerendering）の実用化:** Next.js 15+でPPRが安定し、静的シェル+動的ストリームの構成がデフォルトになりつつある。CDNキャッシュとパーソナライズを両立できるため、アーキテクチャの前提を見直す価値がある。

- **Edge RuntimeとNode.js Runtimeの使い分け:** ストリーミングはEdgeでも動くが、Node.jsの方がメモリ効率が高く、重いデータ処理には依然としてNode.js Runtimeを選ぶべき。Edgeは地理的レイテンシ削減が目的の場合に限定する。

- **クライアントコンポーネントの「汚染」管理:** `use client`ディレクティブが子孫全体に伝播する点を見落としがち。インタラクティブ要素を葉ノードに押し込む設計（leaf-node pattern）でRSCの恩恵を最大化し、バンドルサイズを抑制する。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの主流化:** 2026年においてNext.js + TypeScriptスタックではtRPCがデファクトに近づいており、型安全なエンドツーエンドAPIが「オプション」から「標準」へシフトしている。ランタイムエラーではなくコンパイル時に契約違反を検出できるため、開発速度と信頼性が両立する。

- **GraphQLの役割の明確化:** GraphQLは「全APIに使うもの」から「複数クライアント・複雑なデータグラフが必要なユースケース専用」へ再定義が進んでいる。BFF（Backend for Frontend）パターンと組み合わせ、モバイル・Web・外部パートナー向けに柔軟なクエリが必要な場面に絞るのが現実解。

- **RESTは死んでいない、ただし進化している:** 外部公開APIやサードパーティ連携ではRESTが依然として最適。2026年はOpenAPI 3.1 + Zod/TypeBoxによるスキーマファーストな設計と自動型生成が標準となり、「手書きの型定義」はアンチパターン扱いになりつつある。

- **エッジ対応とストリーミングの台頭:** HTTP/3とEdge Runtimeの普及により、REST/GraphQL問わずストリーミングレスポンス（Server-Sent Events、ReadableStream）のサポートが設計段階から必須に。特にAI機能のストリーミング応答統合でこの傾向が加速している。

- **API契約テスト（Contract Testing）の義務化:** マイクロサービス間・チーム間のインターフェース破壊を防ぐためPact等によるコントラクトテストがCI必須項目に。「動いているから大丈夫」から「契約で証明できて大丈夫」へパラダイムが移行している。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジの標準ランタイムに:** Cloudflare Workers・Fastly Compute@Edgeを中心に、Wasmがコンテナに代わるエッジ実行環境として定着。コールドスタートが数ミリ秒以下となり、サーバーレスのレイテンシ問題がほぼ解消された。

- **エッジでのAI推論が本格化:** 量子化モデル（GGUF/ONNX）をエッジノードで直接実行するパターンが増加。ユーザーデータをオリジンに送らずに推論できるため、プライバシー規制（GDPR等）対応と低レイテンシを同時に実現できる。

- **エッジKV・SQLiteの台頭:** Cloudflare D1・Turso（libSQL）などエッジ対応の分散SQLが実用域に。「エッジはステートレス」という常識が崩れ、フルスタックアプリをエッジで完結させるアーキテクチャが現実的になった。

- **オブザーバビリティの課題が顕在化:** 数百のPoP（接続ポイント）に分散したトレースを統合するコストが増大。OTel（OpenTelemetry）のエッジネイティブ対応と、サンプリング戦略の設計が運用上のボトルネックになっている。

- **ベンダーロックインへの反発とWinterCG標準化:** Cloudflare・Deno・Bun・Node.jsが共通のWeb API仕様（WinterCG）に準拠し始め、エッジ間のポータビリティが向上。特定ベンダーへの依存を避けた設計が2026年の現場では当たり前になりつつある。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）への移行加速:** パスワードレス認証がデファクトスタンダードになりつつあり、フィッシング耐性のあるパスキーをプライマリ認証として採用することが2026年のベストプラクティス。Next.jsプロジェクトでは`SimpleWebAuthn`ライブラリが実用的な選択肢。

- **セッション管理の見直し（短命トークン＋ローテーション）:** JWTの有効期限を15分以下に抑え、Refresh Token Rotationを必須化。トークン漏洩時の被害を最小化するため、使用済みRefresh Tokenの無効化（Reuse Detection）を実装すること。

- **デバイスフィンガープリントと継続的認証:** ログイン時だけでなく、セッション中もデバイス・IPの異常を検知する「継続的認証」が標準化。特に高権限操作時の再認証（Step-up Auth）をフロー設計に組み込む。

- **サプライチェーン攻撃対策としての依存関係ロック:** 認証ライブラリへの悪意ある改ざんが増加しており、`bun.lockb`の厳格管理とDependabotによる自動更新＋SBOMの生成が必須。`npm audit`相当の`bun audit`を CI に組み込む。

- **OAuth/OIDCの設定ミス撲滅:** `redirect_uri`の厳格マッチング、PKCE必須化、`state`パラメータのCSRF対策が依然として見落とされがち。NextAuthなどのライブラリ利用時も、デフォルト設定を鵜呑みにせず設定値を明示的にレビューする習慣を持つこと。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応:** Prisma 6ではEdge-compatibleドライバーが安定版になり、Vercel Edge FunctionsやCloudflare Workersから直接Supabaseに接続可能。コールドスタートの削減とグローバルレイテンシ改善に直結する。

- **Supabase pgvectorの本格活用:** pgvector拡張がSupabaseの標準機能として成熟し、RAG構成をPostgreSQL単体で完結できる。外部ベクターDBを別途立てるコストと複雑性を排除できる。

- **Row Level Security (RLS) とPrismaの統合:** PrismaはRLSポリシーを直接扱えないため、`supabase-js`クライアントとPrismaを役割分担させるパターンが主流。認証済みリクエストはsupabase-js、サーバーサイドの集計はPrismaと使い分けることで安全性と柔軟性を両立する。

- **Connection Poolingの設計が重要:** SupabaseのPgBouncer（Session/Transaction mode）とPrismaのコネクション管理の相性を理解しないとコネクション枯渇が起きる。Prisma Accelerateを挟むことでエッジ環境でのpooling問題を一元解決できる。

- **マイグレーション戦略の分離:** `prisma migrate`とSupabaseのマイグレーション（`supabase db push`）は競合するため、どちらかに統一することが必須。2026年時点ではPrismaをORM・型生成に特化させ、マイグレーション実行はSupabase CLIに任せるパターンが安定性が高い。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASIp2（WebAssembly System Interface Preview 2）の標準化により、RustのWasmコンポーネントがサーバーサイドでも本番運用レベルに達し、コールドスタートがコンテナ比で10〜100倍高速化されている。

- **ポイント2:** Rustの`wasm-bindgen`と`wasm-pack`エコシステムが成熟し、JS/TS境界のFFIオーバーヘッドが大幅に削減された結果、CPU集約処理（画像変換・暗号・パーサー）ではネイティブ比95%以上の性能が実測値として報告されている。

- **ポイント3:** WasmGC（ガベージコレクション拡張）の普及でRust以外の言語もWasmに参入しているが、Rustは「GC不要のゼロコスト抽象」という優位性を維持しており、メモリ予測可能性が重要なリアルタイム・エッジ処理では依然として第一選択肢。

- **ポイント4:** Cloudflare Workers・Fastly Compute・WasmtimeベースのサーバーレスがRust Wasmのデファクト実行環境となり、マルチテナント分離をOSプロセスなしで実現できるため、インフラコストの削減と攻撃面の縮小を同時に達成できる。

- **ポイント5:** SIMD命令のWasm対応（Relaxed SIMD）とスレッドモデル（`wasm32-unknown-unknown` + SharedArrayBuffer）が安定化し、画像処理や機械学習推論ワークロードでのRust Wasmが実用域に入った——ただしブラウザのCOOP/COEPヘッダー制約は引き続き設計上の考慮点。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点でApp Routerの成熟が進み、データフェッチはServer Componentsで行い、インタラクティブな部分のみ`'use client'`を付与するパターンが定着。クライアントバンドルサイズの削減に直結する。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的コンテンツを同一ルートで混在させるPPRが安定版に到達し、`<Suspense>`境界を戦略的に配置することでTTFBと動的性能を両立できる。

- **Server Actions によるAPI Routes代替:** フォーム送信やミューテーション処理をServer Actionsに移行することで、API Routesのボイラープレートを削減しつつ型安全性を確保できる。`use server`ディレクティブとZodバリデーションの組み合わせがベストプラクティス。

- **Route Groups と Parallel Routes で関心の分離:** `(group)`記法によるレイアウト分離と`@slot`によるParallel Routesを活用し、認証レイアウト・モーダルUI・ダッシュボードパネルを単一ルート階層で管理する設計が普及。

- **`use cache` APIによるきめ細かいキャッシュ制御:** Next.js 15以降で導入された`use cache`ディレクティブにより、`unstable_cache`を使わずコンポーネント・関数レベルで宣言的にキャッシュ戦略を指定できる。`cacheTag`と`cacheLife`で無効化も明示的に制御可能。

### 9. Vercel Edge Functions optimization 2026

- **エッジキャッシュの戦略的活用:** Edge Functionsはリクエストごとにコールドスタートが発生するため、`Cache-Control`ヘッダーとVercelのEdge Cacheを組み合わせ、認証不要なレスポンスは積極的にキャッシュすることでレイテンシを劇的に削減できる。

- **ランタイム制約の把握:** Edge RuntimeはNode.js完全互換ではなく、`fs`モジュールや一部のnpmパッケージが使えないため、依存ライブラリの事前検証が必須。Prismaなどのフルスタックライブラリは専用のEdgeアダプタ版を選ぶこと。

- **Middleware vs Edge Route の使い分け:** 認証チェック・リダイレクト・A/BテストはMiddlewareで処理し、データ取得ロジックはEdge Route Handlersに分離する設計が保守性・パフォーマンスともに優れる。

- **Streaming Responseの活用:** AI統合ユースケースでは`ReadableStream`を使ったストリーミングレスポンスがUXの鍵。Next.js App RouterのServer Componentsとの組み合わせで、Time to First Byte（TTFB）を最小化できる。

- **観測性（Observability）の確保:** Edge環境はログが断片化しやすいため、`@vercel/otel`によるOpenTelemetryトレーシングを早期に導入し、Vercel Analytics + 外部APMツール（DatadogなどのEdge対応版）で本番パフォーマンスを継続監視する体制を整えること。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の `satisfies` は型推論を保持しつつ型検証を行えるため、`as` キャストより安全で、2026年現在は標準パターンとして定着している。

- **Template Literal Types によるAPI契約の型化:** エンドポイントパスやイベント名を `\`/api/${string}\`` のようにテンプレートリテラル型で表現することで、ランタイムエラーをコンパイル時に検出できる。

- **`branded types` によるプリミティブ値の区別:** `UserId` と `ProductId` が共に `string` でも混同しないよう Brand/Opaque型パターンが普及し、IDの取り違えバグをゼロコストで防げる。

- **`noUncheckedIndexedAccess` の有効化が事実上必須:** 配列・オブジェクトのインデックスアクセスに自動で `| undefined` を付与するこのオプションは、実行時のundefinedエラーを大幅削減し、2026年のモダンプロジェクトでは標準設定となっている。

- **Zodによるスキーマ駆動型安全性:** 外部API・フォーム入力などシステム境界では `z.infer<typeof schema>` でランタイム検証と型生成を一元化し、`any` の流入を構造的にブロックするアーキテクチャが主流。
