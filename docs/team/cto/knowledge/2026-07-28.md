# CTO Knowledge - 2026-07-28

## Daily Update (2026-07-28)

### 1. Next.js performance optimization 2026

- **ポイント1:** Next.js 16ではPartial Prerendering(PPR)が安定版となり、静的シェルと動的コンテンツを1つのルートで組み合わせられるため、TTFBを維持しつつパーソナライズされたUIを配信可能。プロパティ一覧ページの検索結果部分だけを動的にし、ヘッダーやレイアウトは静的化する設計が有効。
- **ポイント2:** Turbopackがビルド・開発サーバーのデフォルトとなり、大規模コードベースでもHMRとプロダクションビルドが大幅に高速化。物件詳細ページや会員登録フローなど複数ページを持つ本プロジェクトでは、開発体験とCI時間の両方に効いてくる。
- **ポイント3:** Server ActionsとCache Componentsの組み合わせにより、フォーム送信（内見予約・引き継ぎ申請など）でクライアントJSを最小化しつつ、キャッシュ粒度をコンポーネント単位で制御できる。無駄なクライアントバンドルを削減し、モバイル回線でのLCP改善に直結する。
- **ポイント4:** 画像最適化はnext/imageのAVIF優先配信とCDNエッジでのオンデマンド変換が主流に。物件写真が中心のUIでは、レスポンシブsize指定とpriority属性の適切な使い分けがCore Web Vitals（特にLCP）のスコアを左右する。
- **ポイント5:** RSC（React Server Components）ペイロードのストリーミング粒度を細かくし、Suspense境界を機能単位（価格表示、レビュー、地図など）で分割するのがベストプラクティスとして定着。一部データ取得が遅い外部API（地図・査定情報等）に依存する箇所でも、全体のレンダリングをブロックしない設計が可能。

### 2. React Server Components streaming 2026

- **段階的ハイドレーションの標準化:** Next.js 16ではストリーミングSSRとPartial Prerendering (PPR)が安定版となり、静的シェルを即座に返しつつ動的部分だけをSuspense境界でストリーミングする構成が標準パターンになっている。初期表示（LCP）とTTFBを分離して最適化できる点が実務上のメリット。

- **RSC Payloadのキャッシュ戦略が肝:** サーバーコンポーネントの再取得コストを抑えるため、`use cache`ディレクティブやCache Componentsを使ったフラグメント単位のキャッシュが重要になってきている。物件詳細ページのような「前の住人」情報＋写真ギャラリーの組み合わせでは、変更頻度の異なる部分をコンポーネント単位で分離してキャッシュ粒度を上げるべき。

- **Client Componentsの境界設計がパフォーマンスを左右:** `'use client'`の付与範囲を誤るとバンドルサイズが肥大化し、ストリーミングの恩恵が相殺される。フォームや認証まわりなど本当にインタラクティブな部分だけを最小単位で切り出す設計が引き続き重要。

- **エラーバウンダリとSuspenseのペアリング必須:** ストリーミング中に一部コンポーネントが失敗しても他の部分の表示を止めないよう、Suspense境界ごとに専用のerror.tsxまたはError Boundaryを配置するのがベストプラクティス化している。うちの物件一覧・詳細ページでも部分的失敗時のフォールバックUIを見直す価値がある。

- **Server Actions×Streamingでのフォーム体験向上:** `useActionState`とストリーミングを組み合わせ、送信直後に楽観的UIを返しつつバックグラウンドでバリデーション・DB処理を進める設計が主流になりつつある。引っ越し費用の見積もりフォームなど多段階入力があるフローに適用余地がある。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1: tRPCの採用拡大とスキーマ駆動開発の定着** — TypeScriptフルスタック構成（Next.js等）ではtRPCによる型安全なAPI層が主流化しつつあり、フロントエンドとバックエンド間の型不整合によるバグを大幅に削減できる。sumitsugiのような単一TSコードベースのNext.jsプロジェクトでは、内部API（BFF層）にtRPCを導入すると開発速度と型安全性の両立がしやすい。

- **ポイント2: GraphQLは「複雑な集約クエリが必要な場面」に限定活用される傾向** — 汎用GraphQL層をフル導入するコストは高く、2026年時点では「特定の集約エンドポイントだけGraphQL、それ以外はREST/tRPC」というハイブリッド構成が現実的な選択として広がっている。物件検索・フィルタリングのような多条件クエリがある場合のみ検討価値がある。

- **ポイント3: RESTは外部公開APIやパートナー連携の標準であり続ける** — OpenAPI/Swaggerによる自動ドキュメント生成とエコシステムの成熟度から、外部（不動産ポータル連携、決済代行等のサードパーティ）とのインテグレーションでは依然RESTが第一選択。内部通信はtRPC、外部公開はRESTという使い分けが実用的。

- **ポイント4: エッジランタイムとの相性がAPI設計選定に影響** — Next.js 16のEdge Runtime/Server Actionsを使う場合、Server Actions自体が疑似tRPC的な型安全RPCとして機能するため、小規模プロジェクトでは専用APIレイヤーを持たずServer Actionsのみで完結させる設計も有力な選択肢になっている。

- **ポイント5: 認証・入力検証はAPI方式に関わらずZodで統一すべき** — REST/GraphQL/tRPCいずれを採用してもリクエスト境界でのZodバリデーションは共通基盤とし、スキーマを`src/lib`で一元管理することで、API方式を将来的に切り替える際の移行コストを抑えられる（standards.mdの「Input validation: Zodスキーマ」方針とも整合）。

### 4. serverless edge computing 2026

- **エッジランタイムの統一:** Cloudflare Workers、Vercel Edge、Deno Deployなど主要プラットフォームがWinterCG準拠のWeb標準API（fetch, Request/Response）に収束し、ベンダーロックインが減少している。移行コストを抑えるため、Node.js固有APIへの依存は最小限に留めるべき。

- **コールドスタート問題の実質的解消:** V8 isolateベースの分離モデルにより起動時間がミリ秒単位まで短縮され、DBコネクションプーリングやOSSレイヤー（Hyperdrive等）と組み合わせることでエッジでも本格的なステートフル処理が現実的になった。

- **エッジでのAI推論拡大:** 小型LLM・埋め込みモデルのエッジ推論（Cloudflare Workers AI等）が普及し、レイテンシに敏感な検索・レコメンド機能をリージョンをまたがず提供できるようになった。sumitsugiのような物件検索UXでは活用余地が大きい。

- **データレイヤーの追従:** D1/Turso等のエッジネイティブSQLiteやグローバル分散KVが実用段階に入り、読み取り主体のワークロードはエッジでフルスタック化可能。ただし強整合性が必要な書き込み（決済・契約データ）は依然オリジン集約が安全。

- **運用コストの再考:** リクエスト課金モデルにより低トラフィック期は安価だが、スパイク時のコスト予測が難しく、監視・アラート設計を通常のサーバーレスより丁寧に行う必要がある。MVP規模の当プロジェクトでは過剰最適化を避け、必要になった機能から段階的に移行するのが現実的。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証（WebAuthn/Passkeys）が業界標準となり、フィッシング耐性のある認証がデフォルトに。パスワード＋SMS OTPは非推奨とし、実装コストより「パスワードリセットのサポート負荷削減」というROIで導入判断すべき。

- **継続的リスクベース認証（Continuous Auth）:** ログイン時点だけでなく、セッション中も端末指紋・行動パターン・IPレピュテーションを継続的に評価し、異常検知時に再認証を要求する仕組みが主流に。単発の認証チェックポイントに依存する設計はもはや不十分。

- **トークン漏洩対策の強化（DPoP/mTLS）:** アクセストークンが盗まれてもリプレイできないよう、DPoP（Demonstrating Proof-of-Possession）でトークンをクライアント鍵に紐付ける実装が普及。JWTをlocalStorageに保存する従来パターンはXSS経由の窃取リスクが高く、httpOnly Cookie + DPoPへの移行が推奨される。

- **ゼロトラスト前提のセッション管理:** 「一度ログインしたら信頼し続ける」設計を廃止し、権限昇格操作（決済・個人情報変更など）ごとにステップアップ認証を要求。特にsumitsugiのような取引プラットフォームでは、物件情報変更や引越し費用の決済フローで再認証を挟む設計が重要。

- **AIエージェント/ボット対策としての認証層:** 生成AIによる自動化アカウント作成・クレデンシャルスタッフィングが高度化しており、CAPTCHAだけでなくデバイス証明やレート制限をAPI Gateway層で組み合わせる多層防御が必須になっている。

### 6. database architecture Prisma Supabase 2026

## CTO視点：データベースアーキテクチャ（Prisma / Supabase 2026）

- **Prisma ORMの世代交代:** Prisma 6以降はRust製クエリエンジンを廃止し、TypeScript純正エンジンへ移行が完了。バイナリ依存が減りServerless/Edge環境（Vercel Edge, Cloudflare Workers）でのコールドスタートが大幅改善された。sumitsugiはDrizzle+Postgres構成だが、Drizzleも同様に軽量・型安全志向でこのトレンドと整合的。

- **Supabaseのマルチプロダクト化:** Postgres本体に加え、Vector（pgvector）・Realtime・Edge Functions・Auth（RLSベース）が統合され、"BaaS"というより"Postgres中心のフルスタックプラットフォーム"化が進行。RLS（Row Level Security）をアプリ層バリデーションと併用する設計が2026年のベストプラクティスとして定着。

- **接続プーリング問題の標準解決:** Serverless環境でのDB接続枯渇問題に対し、PgBouncer/Supavisorのようなトランザクションプーラーが必須構成に。sumitsugiも本番でPostgres接続数上限を意識したプーリング設定（`db:up`のdocker composeから本番移行時）を早めに検討すべき。

- **マイグレーション運用の安全性向上:** Prisma MigrateもDrizzle Kitも「shadow database」方式でスキーマドリフト検知を強化。破壊的変更（カラム削除・型変更）は`bun run db:generate`後のSQL差分レビューを必須プロセス化することを推奨（standards.mdの型整合性チェックと合わせて）。

- **セキュリティ観点:** Supabase RLSポリシーの記述ミスは典型的な情報漏洩原因になりやすく、`.claude/rules/standards.md`のセキュリティ方針（入力検証・パラメータ化クエリ）と同様、RLSポリシーもコードレビュー必須項目とすべき。

### 7. WebAssembly Rust performance 2026

- **ポイント1（Component Model普及）:** WASI Preview 2とComponent Modelの標準化が進み、Rustで書いた複数のWasmモジュールを言語非依存で合成できるようになった。マイクロサービス的な粒度でWasmコンポーネントを組み合わせる設計が実用段階に入っている。

- **ポイント2（起動速度とコールドスタート）:** RustコンパイルのWasmバイナリはコールドスタートが数ミリ秒台まで縮小し、サーバーレス関数やエッジコンピューティング用途でコンテナに対する優位性が明確になった。引っ越しマッチングのようなリクエスト単位の軽量処理をエッジ実行する選択肢として検討価値がある。

- **ポイント3（SIMDとメモリ効率）:** Wasm SIMDとmulti-memory提案の実装が主要ランタイム（Wasmtime, V8）で成熟し、画像処理・PDF生成・検索インデックスなどCPU負荷の高い処理をRust+Wasmでブラウザ/サーバー両方に同一実装で提供できる。

- **ポイント4（ツールチェーン成熟）:** `wasm-bindgen`やwasm-packに加え、Rust公式のWasmターゲットサポートが安定し、ビルド設定の複雑さが大きく低減した。既存のNext.js/TypeScriptスタックへの部分的なRust導入コストが下がっている。

- **ポイント5（採用判断の勘所）:** 全面移行より「計算集約的な特定機能だけをRust+Wasmに切り出す」ハイブリッド戦略が主流。物件データの一括変換やPDF帳票生成など、明確にボトルネックが特定できる箇所に限定投入するのが2026年のベストプラクティス。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 16では PPR が安定版となり、静的シェルと動的コンテンツを1つのルートで組み合わせられる。物件一覧ページのように「レイアウトは静的、価格や空室状況は動的」という構成に最適で、TTFBを大幅に改善できる。

- **Server Actions のセキュリティ強化が必須:** `'use server'` 関数は事実上パブリックAPIとして公開されるため、認証・入力検証（Zod）を各Actionの先頭で必ず行う必要がある。sumitsugiのようにフォーム送信（お問い合わせ、物件登録）が多いプロダクトでは、CSRF対策とレート制限をServer Actions層に組み込むのがベストプラクティスになっている。

- **`cache` / `use cache` ディレクティブによる明示的キャッシュ制御:** Next.js 15以降のキャッシュ挙動変更（デフォルトでキャッシュしない方向）を受け、2026年時点では`use cache`ディレクティブでキャッシュ範囲を明示的に指定するパターンが主流。データフェッチ関数単位で `cacheLife` / `cacheTag` を指定し、`revalidateTag`で物件データ更新時に的確に再検証する設計が求められる。

- **Route Handlers と Server Components の責務分離:** 外部Webhook（決済、メール送信サービスなど）はRoute Handlers、UI描画に必要なデータ取得はServer Componentsの`fetch`/DBクエリに寄せる分離が定着。混在させるとテスト境界が曖昧になり、E2Eカバレッジが落ちやすい。

- **Streaming + Suspense によるUX最適化:** 引き継ぎフローのような多段階フォームや、住人の活動歴を表示する重いコンポーネントは`loading.tsx`とネストした`<Suspense>`境界で個別にストリーミングし、体感速度を上げるのが標準パターン。ただしSuspense境界が増えすぎるとレイアウトシフトが起きやすいため、スケルトンのサイズ固定が重要。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Functionsの実行時間制限とコールドスタート短縮が進み、V8 isolateベースの起動が数msレベルまで最適化されている。SumitsugiのSSRページ（`src/app/properties/`等）でも、DB接続を伴わない軽量なレスポンス処理はEdgeに寄せることでTTFBを大きく改善できる。

- **ポイント2:** Streaming SSR + Partial Prerendering (PPR) との組み合わせがベストプラクティス化しており、静的な物件情報部分を事前レンダリングしつつ、動的な「引越し費用」計算や在庫ステータスのみEdgeでストリーミング配信する設計が主流になっている。

- **ポイント3:** Edge RuntimeはNode.js APIの一部が使えない制約が残るため、認証まわり（`auth-context.tsx`）で使うライブラリがEdge互換かどうかを事前に確認する必要がある。非互換な処理はNode.js Runtime側に残す判断が重要。

- **ポイント4:** リージョン単位のデータ局所性（Vercelの`regions`設定やEdge Config）を使い、DBに近いリージョンでEdge Functionsを実行することでレイテンシを抑える手法が一般化。将来的にユーザーの地理的分布が広がった場合、この設定が効いてくる。

- **ポイント5:** コスト面では実行時間・呼び出し回数課金のため、Edgeで重い処理（画像変換、PDF生成など）を行うとコストが跳ねやすい。軽量なルーティング・認証チェック・A/Bテスト分岐に限定し、重い処理はNode.js Functionsかバックグラウンドジョブに逃がす設計が推奨される。

### 10. TypeScript type safety patterns 2026

- **型推論の強化とconst型パラメータ:** TypeScript 5.x以降の`const`型パラメータやsatisfies演算子の活用が定着し、冗長な型注釈を減らしつつ厳密な型推論を維持するパターンが主流になっています。実装では過度な型注釈を書かず、コンパイラの推論に任せる設計が生産性を高めます。

- **Zodなどのスキーマファーストバリデーション:** ランタイム検証とコンパイル時型を単一のスキーマ定義から生成する手法（Zod, Valibot等）が標準化し、APIバウンダリでの型安全性が向上しています。本プロジェクトでも`standards.md`にある通りZodをシステム境界で徹底することが型とバリデーションの二重管理を防ぎます。

- **Branded Types / Nominal Typingの普及:** 構造的型付けの弱点（例: `userId: string`と`propertyId: string`の混同）を防ぐため、Branded Typesでドメイン概念を型レベルで区別する実装が増えています。特に本サービスのような複数IDが飛び交うドメイン（物件ID、ユーザーID、予約ID等）で効果的です。

- **Exhaustiveness Checkingによるユニオン型の安全な拡張:** `'draft' | 'public'`のようなステータス型に新しい値を追加する際、`never`型を使った網羅性チェック（switch文のdefaultで`assertUnreachable`）を仕込むことで、追加漏れをコンパイル時に検出するパターンが定着しています。本プロジェクトの標準にある「union型変更時は全使用箇所をgrep」という運用を、型システム側でも補強できます。

- **型のみのimportとビルド高速化:** `import type`の徹底とisolatedModules設定により、型情報の分離がビルドツール（esbuild, swc等)との親和性を高め、大規模コードベースでもコンパイル速度を維持する潮流があります。Bunベースの本プロジェクトでもビルド時間の観点でこの恩恵を受けやすい構成です。
