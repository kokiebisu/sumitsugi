# CTO Knowledge - 2026-04-06

## Daily Update (2026-04-06)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチはサーバーコンポーネントに集約し、`'use client'` は本当にインタラクティブな末端コンポーネントのみに限定する。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降でPPRが安定化し、静的シェルと動的コンテンツをページ単位でハイブリッド配信可能に。TTFBを損なわずにパーソナライズされたコンテンツを出し分けられる。

- **`use cache` APIによるきめ細かなキャッシュ戦略:** `fetch`レベルのキャッシュに加え、関数・コンポーネント単位での`use cache`ディレクティブが実用化。TTLやタグベースの無効化を組み合わせ、不要な再レンダリングを排除する。

- **Turbopackの本番利用と開発体験の向上:** Turbopackがデフォルトビルダーとして安定化し、大規模コードベースでのHMRが数秒から数百ミリ秒に短縮。CI/CDのビルド時間削減にも直結する。

- **Core Web Vitals監視の自動化:** `@next/bundle-analyzer` とVercel Speed Insightsを組み合わせ、LCP/CLS/INPをコードレビューパイプラインに組み込む。本番デプロイ前に回帰を検知する仕組みが開発標準になりつつある。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化:** 2026年時点では、RSCストリーミングはSuspense境界の配置戦略が性能を左右する。コンポーネントツリーの「重い部分」を独立したSuspense境界で囲い、FID・LCPの改善を最大化するのがベストプラクティス。

- **PPR（Partial Prerendering）との統合:** Next.js 15以降でStableになったPPRにより、静的シェルを即座に配信しつつ動的部分をストリームで埋める設計が主流。RSC単体ではなく「PPR + streaming」のセットで考えることが必須。

- **シリアライゼーションのオーバーヘッド管理:** Server→Clientへのprops転送時、大量データをRSCペイロードに含めると逆にTTFBが悪化する。データフェッチはサーバー側で完結させ、クライアントには最小限の構造化データのみ渡すアーキテクチャ規律が重要。

- **エラーバウンダリとの組み合わせ:** ストリーミング中のエラーは従来と異なりHTTPヘッダー送信後に発生するため、`error.tsx`の配置とフォールバックUI設計を事前に確立しないと本番で無言失敗するリスクがある。

- **Edge Runtimeとの相性:** Cloudflare WorkersやVercel Edgeでのストリーミングは最大実行時間制限に注意が必要。長時間のデータフェッチをEdgeで行うよりも、Node.js Runtimeに留めてキャッシュ戦略で補う選択が現実的なケースも多い。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年時点でtRPCはNext.js/TypeScriptスタックにおけるデファクトに近い存在となり、スキーマ定義不要でエンドツーエンドの型安全を実現できるため、小〜中規模チームの開発速度が大幅に向上している。

- **GraphQLの適用範囲の明確化:** GraphQLは「何でも使える万能解」から「複雑なデータグラフを持つ大規模BFF層」向けに適用範囲が絞られてきており、Federation v2とPersistedQueriesがプロダクション必須構成になっている。

- **REST+OpenAPIの再評価:** tRPCやGraphQLの複雑さへの反動として、OpenAPI 3.1 + Zodによるスキーマファーストなコード生成（`@hey-api/openapi-ts`等）が見直されており、外部公開APIではRESTが依然として最有力選択肢。

- **HTTPクライアントのRPC化:** TanStack QueryとtRPCの統合、またはServer Actionsの活用により、「APIエンドポイント」という概念自体が薄れ、関数呼び出しとして直接サーバーロジックを呼ぶパターンが普及している。

- **ストリーミング対応がAPIの新標準:** LLM連携の普及を背景にSSE/WebSocketではなくHTTP Streaming（`ReadableStream`）対応が各フレームワークで標準化されており、新規APIはストリーミングファーストで設計することが競争優位につながる。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジのデファクトランタイムに:** V8 isolatesに加えWasmが主流となり、言語非依存でコールドスタートをほぼゼロにできる。Cloudflare Workers・Fastly Compute等は既にWasm firstに移行済み。

- **エッジDBの成熟でステートフル処理が現実的に:** Cloudflare D1・Turso（libSQL）・Neon（Postgres）のエッジレプリカにより、「エッジは読み取り専用」の制約が崩れた。レイテンシクリティカルな書き込みも地理的に近いノードで処理可能。

- **AI推論のエッジオフロードが加速:** 小型LLM（1-8Bパラメータ）をエッジノードで実行するパターンが普及。クラウドへのラウンドトリップなしでpersonalizationやmoderation処理が完結し、コスト・レイテンシ両面で優位。

- **オブザーバビリティが最大の課題として浮上:** エッジは分散ノード数が桁違いに多く、従来のAPMツールでは追跡困難。OpenTelemetry + エッジネイティブな分散トレーシング（例: Baselime）の採用が急務。

- **プラットフォームロックインリスクへの警戒が高まる:** Vercel・Cloudflare等のエッジ独自APIへの依存でポータビリティが低下。WinterCG準拠の標準ランタイムAPIを使い、抽象化レイヤーを挟む設計が2026年のベストプラクティスとして定着しつつある。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の本格移行:** FIDO2/WebAuthnベースのパスキーがパスワードの実質的な代替として定着しつつあり、フィッシング耐性と利便性を両立できるため、新規サービスはパスキーファーストで設計すべき。

- **セッション管理の強化:** JWTの長寿命トークンは危険であり、アクセストークンを短命（5〜15分）にしてリフレッシュトークンをRotationで管理するパターンが標準化。トークン盗難時の影響範囲を最小化できる。

- **デバイスフィンガープリンティングによる異常検知:** ユーザーエージェントやIPだけでなく、デバイス特性・行動パターンを組み合わせたリスクベース認証が主流に。正規ユーザーへの摩擦を増やさずに不正アクセスを検出できる。

- **サプライチェーン攻撃対策としての依存関係監査:** 認証ライブラリ（NextAuth、Passportなど）の脆弱なバージョンを狙った攻撃が増加。`bun audit` や Dependabot を CI に必須組み込みし、ライブラリのアップデートを自動化する。

- **ゼロトラスト原則の内部APIへの適用:** 社内システムでも「信頼しない・常に検証する」を徹底し、サービス間通信にもmTLSまたは短命トークン認証を導入することで、内部侵害時の横展開を防ぐ。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応:** Prisma 6ではEdge RuntimeとD1/Turso等の分散SQLiteへの対応が強化され、Next.js App RouterのServer Componentsと組み合わせることでコールドスタートを最小化したサーバーレスアーキテクチャが実現可能になった。

- **Supabase Realtime + RLSの成熟:** Row Level Security（RLS）ポリシーとRealtime subscriptionsの組み合わせが本番グレードに達し、アプリケーション層でのアクセス制御ロジックをDBレイヤーに委譲するパターンが標準化されつつある。

- **PrismaとSupabaseの共存戦略:** Supabaseの型生成（`supabase gen types`）とPrismaスキーマの二重管理は技術的負債になりやすい。`prisma-supabase`等のアダプター活用か、どちらかに一本化する意思決定が重要。

- **pgvectorによるRAGアーキテクチャの統合:** Supabase上のpgvector拡張でベクターDB機能をPostgres内に集約できるようになり、外部ベクターDB（Pinecone等）を別途管理するコストを削減できる設計が現実的な選択肢になった。

- **スキーママイグレーションの安全性:** 本番DBへのPrisma migrate deployは依然としてリスクが高く、Supabase CLIの`supabase db push`との競合を避けるため、CI/CDパイプラインでのマイグレーション実行権限を一元化することが2026年時点のベストプラクティス。

### 7. WebAssembly Rust performance 2026

- **Component Model の本格普及:** WebAssembly Component Model (wasm32-wasip2) が2026年に実用段階に入り、RustコンポーネントをJSやPythonと型安全に合成できるようになった。マイクロサービス的な粒度でWasmモジュールを組み合わせるアーキテクチャが現実的な選択肢に。

- **SIMD・スレッド命令の安定化:** Fixed-width SIMDとShared Memoryスレッドがブラウザ・ランタイム双方で安定し、Rustの`std::simd`や`rayon`ベースのコードをほぼそのままWasmに持ち込めるようになった。数値計算・画像処理系で10倍超のスループット改善事例が増加。

- **GCプロポーザルによるメモリ戦略の変化:** WasmGCの普及でランタイム側GCとRustの手動メモリ管理を使い分ける設計が重要に。ホットパスはRust（線形メモリ）、UIロジックはGC言語という二層構成がパフォーマンスと開発効率のバランスとして有効。

- **Wasmtime / WASIクラウドランタイムの成熟:** Fastly・Cloudflare・Vercelなどエッジ環境でWasmtimeベースの実行が標準化。コールドスタートがコンテナ比で100倍高速なケースもあり、Rustで書いたビジネスロジックをエッジにデプロイする戦略が現実解として定着しつつある。

- **ツールチェーンの成熟（`cargo component` / `wasm-bindgen` 2.x）:** `cargo component`によるComponent Model対応ビルドと、`wasm-bindgen` 2.x系のゼロコピーAPI改善により、RustのWasm向けビルドが以前より大幅に簡略化。ただしバイナリサイズ最適化（`wasm-opt`、LTO、`strip`）は依然として手動チューニングが必要。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** 2026年はServer Componentsがデフォルトであることを前提に、クライアント境界（`'use client'`）を最小化する設計が標準化。状態管理はサーバー側に寄せ、クライアントバンドルを削減することがパフォーマンスの第一原則。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的ストリーミングを同一ルートで混在させるPPRが安定版となり、`<Suspense>`境界の設計がアーキテクチャの核心に。TTFBとLCPを同時に最適化できる唯一のアプローチとして採用が急拡大。

- **Server Actions によるフォーム・ミューテーション統一:** APIルートを別途作成せずServer Actionsで完結させるパターンが主流。`useActionState` + `useOptimistic` の組み合わせでUXを損なわずサーバーラウンドトリップを削減できる。

- **並列・インターセプトルートによるモーダルUI:** `@modal`スロットとインターセプトルート (`(.)path`) を組み合わせ、URLを維持したまま詳細モーダルを実現するパターンが定着。Airbnb的な物件詳細UIはこのパターンが最適解。

- **キャッシュ戦略の明示化:** Next.js 15以降、`fetch`のデフォルトキャッシュが`no-store`に変更されたため、`revalidate`や`cache`オプションを意図的に設定することが必須。暗黙のキャッシュに頼らず、ルート単位・データ単位でキャッシュ戦略を明文化することがバグ防止の鍵。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの戦略的配置:** 全APIをEdgeに移行するのではなく、レイテンシ感度の高いルート（認証チェック、A/Bテスト、パーソナライゼーション）に絞って適用する。Node.js Runtimeとの使い分けがパフォーマンスコストを最小化する鍵。

- **Cold Start撲滅のためのStreaming活用:** `ReadableStream` + `Suspense`の組み合わせにより、Edge Functionのコールドスタート影響をユーザーが知覚しにくくなる。TTFB（Time To First Byte）を優先指標として設計すること。

- **Bundle Size上限（1MB）の厳格管理:** Edge Runtimeはpolyfill非対応・Node.js API制限があるため、`@vercel/edge`の軽量プリミティブを優先し、`import cost`ツールで定期監査する。依存関係の肥大化がそのままコールドスタート増加につながる。

- **ISR + Edge Middlewareのハイブリッド戦略:** 静的生成（ISR）でコンテンツを配信しつつ、Edge MiddlewareでリクエストごとのロジックをCDNエッジで処理する構成が2026年のベストプラクティス。データベースへの直接接続はEdgeから避け、キャッシュレイヤーを挟む。

- **可観測性の整備が必須:** Edge Functionsのデバッグは従来のサーバーログより困難。Vercel Analytics + OTel（OpenTelemetry）によるトレーシングを初期から組み込み、エラー率・実行時間のP99をSLO指標として定義しておく。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** プリミティブ型に意味的な区別を持たせる `Brand<T, Brand>` パターンが標準化しつつあり、`UserId` と `OrderId` を誤って混在させるバグをコンパイル時に防げる。

- **satisfies 演算子の積極活用:** TypeScript 4.9以降の `satisfies` は型チェックしつつ推論を保持するため、設定オブジェクトやルートマップの定義で `as const` の代替として広く使われるようになった。

- **Template Literal Types によるAPI契約の厳格化:** `${HttpMethod} /${string}` のようなパターンでルート定義やイベント名を型レベルで制約でき、ランタイムエラーをゼロにする設計が浸透している。

- **Result型 / Never型の活用で例外を型安全に:** `Result<T, E>` パターン（Effect.tsやtrue-mythライブラリ）により、`throw` に頼らずエラーパスを型として明示し、呼び出し側に処理を強制できる。

- **Exact Types と Excess Property Checking の限界への対処:** TypeScript の構造的部分型では余剰プロパティが漏れやすいため、`StrictOmit` や `NoExtraProperties<T, U>` ユーティリティ型で境界値（APIレスポンス・フォーム入力）を厳密に検証するパターンが重要度を増している。
