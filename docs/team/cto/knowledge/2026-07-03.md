# CTO Knowledge - 2026-07-03

## Daily Update (2026-07-03)

### 1. Next.js performance optimization 2026

- **ポイント1: Partial Prerendering (PPR) の本格運用** 静的シェルと動的コンテンツを1つのルートで共存させ、初回表示を高速化しつつパーソナライズも維持できる。Next.js 16では安定版として扱われており、`loading.tsx`との組み合わせでTTFBを大幅に改善できる。

- **ポイント2: React Compiler によるメモ化の自動化** `useMemo`/`useCallback`の手動最適化が不要になり、再レンダリングコストが自動で削減される。物件一覧のような大量カード表示コンポーネントで特に効果が大きい。

- **ポイント3: キャッシュ戦略の明示化** `fetch`のデフォルトキャッシュ挙動が変わったため、`cacheLife`/`cacheTag`APIで意図を明示的に指定する必要がある。物件データのようにdraft/publicステータスが頻繁に切り替わるデータは、タグベースの再検証（`revalidateTag`）で即時反映させるのが定石。

- **ポイント4: Turbopackがビルドの標準に** Webpackからの移行でビルド時間・HMR速度が大幅短縮。CIのビルド時間短縮は`bun run build`のフィードバックループを速め、開発速度に直結する。

- **ポイント5: Server Actions のセキュリティ境界を意識した設計** フォーム送信・認証処理をServer Actionsに寄せる際、入力検証（Zod）とレート制限を境界で徹底しないと攻撃面が広がる。パフォーマンスと安全性はセットで設計すべき領域。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 16ではPPRが安定版として扱われ、静的シェルを即座に返しつつ動的な部分だけをストリーミングする構成が標準パターンに。TTFBを大幅に改善できるため、`properties/`一覧ページのような静的部分＋動的な空室状況混在ページで積極活用すべき。
- **Suspense境界の粒度設計が性能のボトルネック:** ストリーミングの効果はSuspense境界の切り方次第で、粒度が粗いと結局全体を待つことになる。物件詳細ページなど画像・レビュー・空室カレンダーなど独立性の高いセクションごとに境界を分けるのがベストプラクティス。
- **Server Actionsとの組み合わせでフォーム体験が向上:** RSCストリーミング＋Server Actionsにより、物件登録フォームなどの多段階フローでページ遷移なしに部分更新できる。CLAUDE.mdのTDD要件と合わせ、Server Action単体のunit testと組み合わせたE2Eの両輪が必須。
- **キャッシュ戦略の複雑化に注意:** `use cache`ディレクティブの普及でRSC単位のキャッシュ制御が可能になったが、`'draft' | 'public'`のようなステータス変更が即座に反映されないリスクがある。物件のステータス変更操作では明示的な再検証（revalidateTag等）を徹底する必要がある。
- **エッジランタイムとの親和性向上:** ストリーミングSSRはエッジでの分散実行と相性が良く、地方の内見ユーザーへのレイテンシ改善に直結する。ベータローンチ後のスケール局面で検討価値あり。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの台頭）:** TypeScriptフルスタック構成（Next.js等）ではtRPCがREST/GraphQLに代わる選択肢として定着しつつあり、スキーマ定義とエンドツーエンドの型安全性をコード生成なしで実現できる点が開発速度に直結する。sumitsugiのようなBun+Next.jsモノリポ構成であれば導入コストが低く、フロント/バックエンド間の型不整合バグを未然に防げる。

- **ポイント2（GraphQLは複雑なクエリ要件がある場合に限定利用）:** GraphQLは柔軟なクエリ能力が強みだが、N+1問題やキャッシュ戦略の複雑さ、認可ロジックの分散といった運用コストが高く、2026年時点では「複数クライアント（Web/モバイル/外部パートナー）が異なるデータ形状を要求する」ケースに限定して採用するのが実用的。単一のNext.jsアプリのみが叩くAPIであればオーバーエンジニアリングになりやすい。

- **ポイント3（RESTはシンプルさと外部連携で依然優位）:** 公開API・Webhook・外部パートナー連携（決済、不動産ポータル連携など）ではRESTがキャッシュ制御・HTTPセマンティクス・ツールエコシステムの成熟度で依然として最も安全な選択。sumitsugiの「引越し費用」決済や外部不動産DB連携など、社外システムとの接点はREST+OpenAPIで設計するのが妥当。

- **ポイント4（BFFパターンとAPI Gatewayの併用）:** 2026年のトレンドとして、内部通信はtRPC、外部公開はREST、複雑な集約クエリはGraphQLと使い分けるハイブリッド構成（BFF: Backend for Frontend）が主流化。単一プロトコルへの統一より「境界ごとに最適なプロトコルを選ぶ」設計判断がスケーラビリティとメンテナンス性を両立させる。

- **ポイント5（型安全性とバリデーションの一体化）:** ZodなどのランタイムバリデーションスキーマをtRPC/REST双方で共有し、コンパイル時型チェックと実行時入力検証を一元管理する構成が標準化してきている。sumitsugiの標準規約（Zodでの境界バリデーション）とも整合するため、API層全体でこの一貫性を維持することが技術的負債の予防になる。

### 4. serverless edge computing 2026

**ポイント1:** WebAssembly (WASM) ベースのエッジランタイムが主流化し、V8 Isolateよりも軽量かつ言語非依存な実行環境として、Fastly Compute@EdgeやCloudflare WorkersがWASI互換性を強化。マルチ言語（Rust/Go/TypeScript）でのエッジ関数開発が標準的な選択肢になっている。

**ポイント2:** エッジDB（Cloudflare D1、Turso、PlanetScale等）の成熟により、読み取りレイテンシだけでなく書き込みも地理分散できるようになり、グローバルユーザー向けサービスでのデータベースがボトルネックになる問題が大幅に緩和された。sumitsugiのような不動産マッチングサービスでも、物件検索の応答速度向上に直結する。

**ポイント3:** エッジでのLLM推論（軽量モデルの量子化・蒸留版）が実用段階に入り、簡易的な自然言語処理（検索クエリの意図理解、フィルタリング）をオリジン往復なしでエッジ側完結できるケースが増加。ただしフル機能のLLM推論はまだ中央集権的なAPI呼び出しが必要。

**ポイント4:** Next.js 16のApp Routerとエッジランタイムの統合が深化し、`runtime: 'edge'`指定によるMiddleware・Route Handlerの選択的エッジ配置が一般化。ただしNode.js API依存のライブラリとの互換性制約は依然として開発時の注意点。

**ポイント5:** コールドスタート問題はV8 Isolate方式でほぼ解消された一方、エッジでの可観測性（分散トレーシング、ログ集約）とコスト予測の難しさが新たな課題として浮上しており、エッジ移行前にモニタリング戦略の設計が必須になっている。

### 5. authentication security best practices 2026

## CTO視点: 認証セキュリティのベストプラクティス 2026

- **パスキー（FIDO2/WebAuthn）への移行:** パスワードレス認証がデファクトスタンダードになりつつあり、フィッシング耐性が高く、UXも向上する。sumitsugiのような個人情報（前の住人の連絡先等）を扱うサービスでは早期導入価値が高い。

- **短命トークン + リフレッシュトークンローテーション:** アクセストークンの有効期限を短く保ち（15分程度）、リフレッシュトークンは使用ごとに再発行・旧トークンを無効化することで、トークン漏洩時の被害範囲を最小化する。

- **リスクベース多要素認証（Adaptive MFA）:** 常時MFAを強制するのではなく、異常なログイン（新規デバイス・地理的異常・時間帯異常）を検知した場合のみ追加認証を要求し、セキュリティとUXのバランスを取る。

- **セッション管理の可視化と即時失効:** ユーザーが自分のアクティブセッション一覧を確認・個別に失効できるUIを提供し、不正アクセス発覚時に即座に全セッションを無効化できる仕組みを持つことが標準要件になっている。

- **認証まわりの入力値検証とレート制限の徹底:** ログイン・パスワードリセットエンドポイントへのブルートフォース攻撃対策として、Zodによる入力検証に加え、IP/アカウント単位のレート制限とCAPTCHA的な段階的防御を組み合わせる。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMの進化:** Prisma 6以降はRustフリーの純TypeScriptエンジンへ移行し、コールドスタートとエッジランタイム（Vercel Edge、Cloudflare Workers）対応が大幅に改善された。sumitsugiのようなNext.js 16 App Routerプロジェクトでは、Edge Functionsでの物件検索APIなどにこの恩恵を直接活かせる。

- **Supabaseのブランチング機能:** Supabase Branching（PRごとのDBブランチ自動生成）がGA後標準化され、`feat/rental-cost-note`のようなworktreeベースの開発フローと相性が良い。PRごとに独立したDBスキーマでテストできるため、`draft`/`public`ステータス変更のような破壊的マイグレーションを本番に影響なく検証できる。

- **RLS（Row Level Security）とPrismaの統合:** SupabaseのRLSポリシーとPrisma Clientを併用する際は、Prisma単体では行レベル権限を強制できないため、Supabase側のRLSを必ず有効化し、Prismaは「型安全なクエリビルダー」としてのみ使う設計が定石になっている。前の住人/次の住人のような個人情報を扱うテーブルでは特に重要。

- **Connection Poolingの必須化:** Supavisor（Supabase純正プーラー）がPgBouncerを置き換えつつあり、Next.jsのサーバーレス関数からのDB接続ではTransaction modeでのプーリングがデフォルト推奨に。`bun run build`後のNextサーバーレス関数が同時多発接続でDB上限に達する事故を防げる。

- **スキーマ駆動のZod連携:** Prisma Schemaから`zod-prisma-types`等でZodスキーマを自動生成し、システム境界（フォーム入力・API）でのバリデーションと二重管理を防ぐパターンが主流化。プロジェクトの「Zodスキーマを使う」標準ルールと直接整合する。

### 7. WebAssembly Rust performance 2026

- **Component Model と WASI 0.2/0.3 の成熟:** Rustの`wasm32-wasip2`ターゲットが標準化されつつあり、コンポーネント間で型安全なインターフェース連携が可能に。マイクロサービス的にWasmモジュールを組み合わせる設計が現実的になってきており、エッジ環境でのAPI境界設計に活用できる。

- **起動時間とコールドスタートの劇的な改善:** WasmtimeやWasmerのAOTコンパイル・キャッシュ機構が進化し、Rust製Wasmモジュールのコールドスタートがミリ秒未満のケースも増加。Cloudflare Workers/Fastly Compute等のエッジ実行環境でNode.jsベースより有利になっており、レイテンシ重視の機能はWasm移植を検討する価値がある。

- **SIMDとマルチスレッド対応の実用化:** `wasm32-simd128`と共有メモリ+アトミック操作の組み合わせで、画像処理・暗号化・数値計算系ワークロードがネイティブ比80-90%程度の性能を出せるように。CPU集約的な処理をブラウザ/エッジに持ち込む際の有力な選択肢。

- **バイナリサイズ最適化の重要性が継続:** `wasm-opt`、`twiggy`によるサイズ分析、`cargo-component`でのツリーシェイキングが標準ワークフロー化。Rustのモノモーフィゼーションによるコード膨張は依然課題で、ジェネリクス多用箇所はサイズ影響を計測すべき。

- **サーバーサイドWasmでのサンドボックス実行が普及:** プラグインシステムやユーザー定義ロジックの安全な実行環境としてWasmを採用する事例が増加（Rust製ホストランタイム + 任意言語のゲストコード）。将来的にsumitsugiのような物件データ処理系で、外部連携のサンドボックス実行基盤として検討余地あり。

### 8. Next.js App Router patterns 2026

- **ポイント1:** Partial Prerendering (PPR) が安定版となり、静的シェルを即座に返しつつ動的部分をストリーミングする構成がデフォルト化。ダッシュボードや物件一覧ページのようにSEO対象の静的部分とユーザー固有の動的部分が混在するページで、TTFBとインタラクティブ性を両立できる。

- **ポイント2:** Server Actions がフォーム処理・ミューテーションの標準パターンとして定着し、API Routeを介さずに `use server` 関数から直接DB操作を呼ぶ構成が主流に。ただし認証チェックとZodバリデーションをServer Action内で必ず行わないと、クライアントから直接呼び出し可能なエンドポイントとして悪用されるリスクがある点は要注意。

- **ポイント3:** `cache: 'force-cache'` を前提としたfetchキャッシュ挙動から、`use cache` ディレクティブ（Cache Components）ベースの明示的キャッシュ制御へ移行が進んでいる。キャッシュの意図をコードで明示できるため、`draft`/`public` のようなステータス別のキャッシュ戦略も宣言的に書きやすくなる。

- **ポイント4:** ルートグループ (`(group)`) と Parallel Routes / Intercepting Routes を組み合わせた「モーダル遷移でもURL共有可能」なUXパターンが一般化。物件詳細のクイックビューなど、一覧→モーダル→詳細ページの遷移を自然に実装できる。

- **ポイント5:** Edge RuntimeとNode.js Runtimeの使い分けがより明確になり、認証・DB接続を伴うページはNode Runtime、静的に近い軽量ページはEdgeという住み分けが定石化。全ページをEdge化するのではなく、レイテンシとDB互換性のトレードオフで層ごとに選択するのがベストプラクティス。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約再確認:** Vercel Edge Functionsは依然としてNode.js APIの一部（fs, 一部のnetモジュール等）が使えないため、Prisma等のORMは`edge`対応ドライバー（例: Prisma Accelerate, Neonのedge driver）を選定する必要がある。今のsumitsugiのAPI Routesを将来Edgeに寄せる際は、DBアクセス層を先に抽象化しておくと移行コストが下がる。

- **Streaming SSRとの相性:** Next.js 16のPartial Prerendering (PPR)とEdge Functionsを組み合わせることで、静的シェルを即座に返しつつ動的部分（物件詳細のリアルタイム在庫状況など）をストリーミングできる。物件一覧ページのようにLCPが重要なページから優先適用するのが費用対効果が高い。

- **コールドスタート最適化:** Edge FunctionsはV8 isolateベースで実質ゼロコールドスタートだが、バンドルサイズが1MBを超えると初期化遅延が出始める。依存関係を`edge-runtime`互換の軽量ライブラリに絞り込む（例: `zod`は問題ないが重いPDF生成ライブラリ等はNode runtime側に残す）判断が必要。

- **リージョン選定とレイテンシ:** ユーザー層が国内中心であればEdge Functionsの地理分散メリットは限定的。むしろ`regions`設定でNRT（東京）に固定し、Vercel PostgresやSupabaseとの物理的距離を最小化する方がレイテンシ改善効果が大きいケースが多い。

- **コスト管理:** Edge Functionsは実行時間課金でリクエスト数が多いと従来Serverlessより割高になりやすい。認証チェックやリダイレクトなど軽量・高頻度な処理はEdge Middleware側に寄せ、重い処理（PDF生成、メール送信）はNode.js Serverless Functionsに残すハイブリッド構成が2026年時点でのベストプラクティス。

### 10. TypeScript type safety patterns 2026

- **ポイント1（`satisfies`演算子の定着）:** 型注釈で幅を狭めずにリテラル型推論を保つ`satisfies`が標準的な書き方として定着し、設定オブジェクトやAPIレスポンスの型検証で従来の`as const`＋手動型定義の組み合わせより安全に使われている。
- **ポイント2（スキーマ駆動の型生成）:** ZodやValibotなどのスキーマライブラリから型を自動導出し、ランタイムバリデーションとコンパイル時型を単一のソースオブトゥルースに統合する流れが加速。当プロジェクトでも`Zod`を境界検証に使っている方針と整合的。
- **ポイント3（Branded Types / Nominal Typing）:** `UserId`と`ProductId`のように構造的には同じstring型でも意味的に異なるIDを取り違えないよう、branded typeで名目的型付けを補う手法が中〜大規模コードベースで一般化している。
- **ポイント4（strictな型のCI強制）:** `tsc --noEmit`をCIの必須ステップにし、型エラーはビルドを落とす方針が「ベストプラクティス」から「デファクトの必須要件」に格上げされた。ESLintやユニットテストだけでは型崩れを検出できない教訓が広く共有された結果。
- **ポイント5（Union型の網羅性チェック）:** `status: 'draft' | 'public'`のような判別可能なUnion型は、switch文で`never`型を使った網羅性チェック（exhaustiveness check）をTypeScript 5系の型絞り込み改善と組み合わせて徹底する運用が定番化し、値追加時の考慮漏れをコンパイル時に検出する動きが強まっている。
