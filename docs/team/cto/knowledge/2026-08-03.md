# CTO Knowledge - 2026-08-03

## Daily Update (2026-08-03)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Prerendering の本格運用）:** Next.js 16ではPPR（Partial Prerendering）が安定版となり、静的シェルを即座に配信しつつ動的部分をストリーミングできる。物件一覧ページのような「検索フィルタは動的だが枠組みは静的」な画面と相性が良く、TTFBを大幅に短縮できる。
- **ポイント2（React Compilerによる自動メモ化）:** React Compilerがデフォルト有効化され、`useMemo`/`useCallback`の手動最適化がほぼ不要になった。物件カード一覧や引き継ぎフローの多段フォームなど再レンダリングが多い箇所でも、コード量を増やさずパフォーマンスを維持できる。
- **ポイント3（Turbopackのビルド高速化）:** Turbopackが本番ビルドでも既定エンジンとなり、`bun run build`の時間が体感で大幅短縮。CI（GitHub Actions）のビルド時間短縮にも直結し、自律開発ワークフローの反復速度が上がる。
- **ポイント4（画像・フォントの自動最適化強化）:** `next/image`のAVIF優先配信とレスポンシブ生成がさらに賢くなり、物件写真中心のUIでLCP改善に直結。CDNキャッシュヒット率も向上するため、Vercel外へのインフラ移行時も同等最適化を意識すべき。
- **ポイント5（Server Actionsのキャッシュ戦略成熟）:** `use cache`ディレクティブが安定し、粒度の細かいキャッシュ制御が可能に。「前の住人」プロフィールや物件詳細など更新頻度が低いデータに適用すれば、DBアクセスを削減しつつリアルタイム性が必要な箇所（在庫状況など）とのバランスが取りやすい。

### 2. React Server Components streaming 2026

**ポイント1:** Next.js 16ではPartial Prerendering (PPR)がstableとなり、静的シェルを即座に返しつつ動的部分のみをストリーミングする構成が標準化された。物件一覧ページのような「ヘッダーは静的・価格や在庫は動的」な構成に特に有効で、TTFBを大幅に改善できる。

**ポイント2:** `use cache` ディレクティブとCache Componentsの組み合わせにより、RSCペイロードのキャッシュ粒度をコンポーネント単位で制御できるようになった。物件詳細ページなど更新頻度の低いデータをキャッシュしつつ、空室状況のような即時性が必要な部分だけ再検証する設計が現実的になっている。

**ポイント3:** Suspense境界の設計がパフォーマンスの肝になっている。境界を細かく切りすぎるとウォーターフォールが発生し逆に遅くなるため、「ユーザーが最初に見る情報」を軸にバウンダリを設計する必要がある（例: 物件カード画像とレビュー数を別ストリームにするなど）。

**ポイント4:** Server Actions単体でのフォーム処理は成熟したが、楽観的更新（`useOptimistic`）とストリーミングを組み合わせたUXパターンがベストプラクティスとして定着してきた。引き継ぎ申込フローのような多段階フォームでは、この組み合わせで体感速度を上げつつサーバー側バリデーションの堅牢性も維持できる。

**ポイント5:** RSCとエッジランタイムの相性が改善し、地理的に分散したユーザーへの初期表示が速くなっている。ただしエッジ環境ではNode API制約があるため、DB接続やSDK呼び出しを含むコンポーネントはNodeランタイムに残す判断が引き続き必要。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはフルスタックTypeScriptモノレポ（Next.js App Router含む）で急速に主流化しており、スキーマ定義とAPI型を単一のソースから自動生成できるため、フロントエンド/バックエンド間の型不整合バグをコンパイル時に排除できる。sumitsugiのようなNext.js＋TypeScript構成では、内部APIをtRPC化する投資対効果が高い。

- **ポイント2:** GraphQLは「柔軟なクエリ」から「BFF（Backend for Frontend）層での集約」用途にシフトしており、モバイル/Web/パートナー向けなど複数クライアントが異なる形状のデータを必要とする場合に限定して採用するのが2026年時点のベストプラクティス。単一クライアントのアプリにはオーバーエンジニアリングになりがち。

- **ポイント3:** RESTは外部公開API・パートナー連携・Webhookなど「契約の安定性」と「キャッシュ戦略（CDN/HTTPキャッシュ）」が重要な場面で依然として最適解であり、OpenAPI 3.1 + JSON Schemaによる自動ドキュメント生成・型生成が標準化している。

- **ポイント4:** 2026年のトレンドとして、単一プロトコルへの統一よりも「内部通信はtRPC、外部公開APIはREST(OpenAPI)、複雑な集約が必要な箇所のみGraphQL」という使い分け（ポリグロットAPI戦略）が定着しつつある。sumitsugiも将来的な外部パートナー連携（不動産会社API連携等）を見据え、内部tRPCと将来の公開REST APIの境界を早期に設計しておくべき。

- **ポイント5:** 認証・入力検証はプロトコルに関わらずZodなどのスキーマバリデーションを境界（API層）で一元化する設計が定着しており、`.claude/rules/standards.md`にある「Zodスキーマ利用」方針は2026年のベストプラクティスと合致している。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG/WinterTCが提唱するWeb標準API（Fetch, Streams等）への準拠が進み、Cloudflare Workers・Vercel Edge・Deno Deployなど異なるプラットフォーム間でのコード移植性が大幅に向上している。ベンダーロックインを避けるなら、Node.js固有APIではなく標準API準拠のコードを書くべき。

- **エッジでのステートフル処理:** Cloudflare Durable Objects、PartyKitのようなアクター型モデルがエッジ上でのステート管理を実用化し、WebSocketやリアルタイム協調編集機能をオリジンサーバーなしで実装可能になっている。sumitsugiのような不動産マッチングでもリアルタイム通知・チャット機能をエッジで完結できる可能性がある。

- **コールドスタート問題の実質解消:** V8 Isolateベースの分離モデル（コンテナではなく）により、起動時間がミリ秒単位まで短縮され、トラフィックの薄い深夜帯でもレイテンシが安定。Next.js 16のようなフレームワークとの統合も進み、Vercel Edge RuntimeでのSSRがデフォルト選択肢になりつつある。

- **エッジDBとの統合:** Turso（libSQL）、D1、Neonなどのエッジ最適化DBがレプリケーションでユーザー地理位置に近い読み取りを実現し、物件検索のような読み取り比率の高いワークロードでp95レイテンシを大幅改善できる。書き込みは依然中央集権的なため、読み書き分離設計が前提となる。

- **コスト構造の逆転リスク:** 従量課金のエッジ実行はトラフィックスパイク時に予測しづらいコスト増をもたらすため、2026年時点では「エッジ+従来サーバーのハイブリッド」がベストプラクティスとして定着しつつある。全面移行より、レイテンシが効くパス（検索・認証）から段階的に移行するのが現実的。

### 5. authentication security best practices 2026

- **パスキー標準化とパスワードレス移行:** 2026年時点でWebAuthn/FIDO2ベースのパスキーが主要ブラウザ・OSで標準サポートされ、フィッシング耐性の高い認証がデファクトに。sumitsugiのような個人情報（物件・引き継ぎ情報）を扱うサービスでは、パスワード認証と併用しつつパスキーへの誘導UIを早期に用意すべき。

- **多要素認証（MFA）の必須化と段階的リスクベース認証:** 単純なSMS OTPはSIMスワップ攻撃に弱く非推奨化が進行中。ログイン時の端末フィンガープリント・地理的異常検知を組み合わせたリスクベース認証（adaptive MFA）が2026年のベストプラクティス。決済・契約情報が絡む「引越し費用」決済フローでは特に重要。

- **セッション管理とトークンの短命化:** JWTなど長寿命トークンの漏洩リスクが引き続き課題。短命アクセストークン＋リフレッシュトークンローテーション、デバイスバインディングの実装が標準化。Next.js App Routerではサーバーコンポーネント側でのセッション検証を徹底し、クライアント露出を最小化する設計が推奨される。

- **サプライチェーンとゼロトラスト:** 認証ライブラリ（NextAuth/Auth.js等）自体の脆弱性が攻撃対象になるケースが増加。依存パッケージの定期監査とゼロトラスト原則（内部APIでも都度検証）の適用が必須。CI/CDに認証関連の依存脆弱性スキャンを組み込むことを推奨。

- **プライバシー規制との整合:** 認証情報・個人情報保護は日本の個人情報保護法や今後の規制強化と直結するため、法務確認待ちの現フェーズ（プライバシーポリシー策定前）でも、認証設計自体を規制準拠前提（データ最小化・監査ログ保持）で先行実装しておくと後戻りコストを抑えられる。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Supabaseの新しいBranching機能とPrisma Migrateを組み合わせることで、PR単位でデータベースの本番同等環境を自動生成できるようになり、スキーマ変更のレビュー精度とロールバック安全性が大幅に向上している。

- **ポイント2:** Prisma 6系以降はEdge Runtime対応が強化され、Supabaseのconnection poolerと組み合わせたサーバーレス環境でのコールドスタート・コネクション枯渇問題が実用レベルで解消されつつあるため、Vercel等のエッジデプロイとの相性が良い。

- **ポイント3:** Row Level Security (RLS) をPrisma側のスキーマ定義と同期させる運用が主流になりつつあり、アプリケーション層とDB層で二重に権限ロジックを書く手間を減らせる一方、Prismaのマイグレーション履歴とRLSポリシーのバージョン管理を別途仕組み化する必要がある。

- **ポイント4:** pgvectorのSupabaseネイティブサポートが成熟し、Prisma経由でベクター検索クエリを型安全に書けるライブラリ（prisma-extension-pgvector等）が普及してきており、検索・レコメンド機能を別ベンダーのベクターDBに頼らず自社Postgres内で完結できるようになっている。

- **ポイント5:** sumitsugiの規模（物件データ+ユーザー+取引履歴）であれば、Supabaseのマネージドバックアップ・PITR（Point-in-Time Recovery）とPrismaのスキーマドリフト検知を組み合わせることで、法務確認前のベータローンチ段階から低コストでデータ整合性と障害復旧の体制を整えられる。

### 7. WebAssembly Rust performance 2026

## CTO視点: WebAssembly Rust Performance 2026

- **ポイント1（コンポーネントモデルの成熟）:** WASM Component Model が標準化されつつあり、Rust製WASMモジュール間の相互運用性がFFIオーバーヘッドなしで実現可能に。マイクロサービス的な機能分割をブラウザ/エッジ両方で低コストに行える。
- **ポイント2（SIMD＋スレッドの実用化）:** `wasm-bindgen` + `wasm-simd` + shared memory(threads) の組み合わせが主要ブラウザ・ランタイムで安定し、画像処理や暗号化などCPUバウンド処理でネイティブの70-90%程度の性能に到達している。物件写真の最適化処理などに応用余地あり。
- **ポイント3（バイナリサイズ最適化）:** `wasm-opt` / `cargo-wasm-strip` の進化とtree-shakingの精度向上により、Rust WASMバンドルが大幅に軽量化。初期ロード時間がボトルネックになりやすいNext.js SSR構成でも導入しやすくなった。
- **ポイント4（エッジランタイムでの採用拡大）:** Cloudflare Workers / Vercel Edge Functions などがRust WASMを一級市民として扱うようになり、リクエストごとの起動オーバーヘッド（コールドスタート）がミリ秒未満まで低減。地図検索や物件フィルタリングAPIのエッジ実行に有望。
- **ポイント5（開発体験の改善）:** `wasm-pack` とTypeScript型生成の統合が進み、Rust側の型安全性をフロントエンドまでシームレスに引き継げるように。ただしデバッグ・プロファイリングツールはまだJSエコシステムほど成熟しておらず、導入時は計測基盤を先に整える必要がある。

**実用的示唆:** sumitsugiの現スタック（Next.js/TS）では、当面WASM導入の優先度は低いが、将来的に画像処理（内見写真の自動補正等）や地図検索の高速化が課題になった際は、Rust WASM + エッジランタイムの組み合わせを検討価値あり。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 16ではPPRが安定版となり、静的シェルを即座に返しつつ動的部分をストリーミングする構成が標準パターンに。物件一覧ページのようにヘッダー/フッターは静的、価格や空き状況だけ動的にすることでTTFBを大幅短縮できる。

- **Server Actionsのセキュリティ強化が必須化:** `use server`関数はエンドポイントとして誰でも呼び出せるため、認証チェックとZodによる入力検証をアクション内部で必ず行う必要がある。前の住人/次の住人間のやり取りなど権限確認が必要な操作は特に注意。

- **`cache: 'force-cache'`依存からの脱却:** Next.js 15以降でfetchのデフォルトキャッシュ挙動が変わり、明示的な`revalidate`戦略が必須に。物件データのようにリアルタイム性が求められる情報は`revalidateTag`によるオンデマンド再検証を活用すべき。

- **Route Groupsとparallel routesによるレイアウト分離:** `(marketing)`と`(dashboard)`のようなroute groupsでレイアウトツリーを分離し、認証済み/未認証エリアで異なるバンドルを配信するパターンが定着。account/配下は`@modal`などparallel routesでモーダルUXを実現しやすい。

- **Turbopackのビルド標準化とEdge Runtimeの使い分け:** Turbopackが`bun run build`のデフォルトとなりビルド速度が改善される一方、Edge Runtimeは軽量なミドルウェア（認証チェック等）に限定し、DBアクセスを伴う処理はNode.jsランタイムに留めるという使い分けの重要性が増している。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約設計:** Node.js APIの一部が使えないEdge Runtimeを前提に、依存パッケージを最小化し、Cold Startを数ms〜十数msに抑える設計が2026年でも標準。重い処理はEdge→Node.jsランタイムへのフォールバック（`export const runtime = 'nodejs'`）で切り分けるのが定石。

- **ストリーミングSSR/RSCとの統合:** Vercel Edge FunctionsはNext.jsのReact Server Componentsストリーミングと相性が良く、TTFB（Time to First Byte）を大幅短縮できる。物件一覧や検索結果など、データフェッチが絡む画面ではストリーミングUIとEdge Middlewareの組み合わせがUX改善の鍵。

- **Edge Configとの併用でDB往復削減:** 頻繁に読むが更新頻度の低いデータ（フィーチャーフラグ、物件ステータスのキャッシュ、地域別料金設定など）はVercel Edge Configに載せることで、Edge Function内でのDBラウンドトリップを避け、レイテンシを1桁ms台に抑えられる。

- **地理的近接性によるレイテンシ最適化:** ユーザーに最も近いエッジで認証チェックやリダイレクト判定（`middleware.ts`）を行うことで、認証まわりのUX（ログイン状態判定、アクセス制御）を高速化できる。sumitsugiのようなユーザー認証必須のプラットフォームでは、Middlewareでの軽量トークン検証がボトルネック解消に直結する。

- **観測性とコスト管理の両立:** Edge Functionsは従量課金かつ実行時間制限が厳しいため、2026年は`waitUntil`によるバックグラウンド処理の分離や、Vercel Analyticsでのファンクション単位のレイテンシ・エラー監視が実運用で重要視されている。不要なEdge化（重い処理をEdgeに置く）は逆にコスト増を招くため、Edge/Node/Serverlessの使い分け判断が引き続き技術的な論点。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** テンプレートリテラル型とconst型パラメータの組み合わせが標準化し、APIレスポンスやルーティングパスの型を文字列操作レベルで検証できるようになっている。手動で型定義を書くより、実行時スキーマ（Zod等）から型を自動導出する`z.infer`パターンが主流。
- **ポイント2:** `satisfies`演算子の活用が定着し、型の広さを保ちつつ構造チェックができるため、設定オブジェクトや定数マップの型安全性がリテラル型推論を壊さずに担保できる。sumitsugiの`site-config.ts`のような設定ファイルにも適用余地がある。
- **ポイント3:** ブランド型（Branded Types）でID同士の取り違えを防ぐパターンが浸透しており、たとえば`PropertyId`と`UserId`を同じ`string`型のまま誤って渡すバグをコンパイル時に検出できる。物件IDとユーザーIDを扱う本プロジェクトのようなドメインで特に有効。
- **ポイント4:** Zodなどのスキーマライブラリとtsの型システムを"バウンダリでのみ検証"する設計が推奨されており、内部関数では型を信頼しコード量を減らす一方、フォーム入力やAPI境界では確実にパースするという使い分けが標準ルールにまとめ直されている（`.claude/rules/standards.md`の入力検証方針と合致）。
- **ポイント5:** TypeScript 5.x系のnarrowing改善（`in`演算子やdiscriminated unionの精度向上）により、`'draft' | 'public'`のようなステータス型のswitch文で網羅性チェック（`never`型を使ったexhaustiveness check）を書くのが一般的になり、値追加時の考慮漏れをビルド時に検出できる。
