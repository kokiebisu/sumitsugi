# CTO Knowledge - 2026-10-20

## Daily Update (2026-10-20)

### 1. Next.js performance optimization 2026

- **PPR（Partial Prerendering）の本格活用:** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分のみストリーミングできるため、物件一覧ページのようなハイブリッドUIでTTFBを大幅短縮できます。

- **Turbopackへの完全移行:** devだけでなくbuildでもTurbopackがデフォルト化され、ビルド時間が従来のWebpack比で数倍高速化。CIのビルド待ち時間短縮に直結するので、早めに移行検証すべきです。

- **`use cache`による明示的キャッシュ制御:** Next.js 15以降のキャッシュデフォルト変更（fetchが非キャッシュ化）を受けて、`use cache`ディレクティブで粒度を細かく制御するのがベストプラクティス。物件検索APIなど更新頻度が異なるデータに対して個別にキャッシュ戦略を設計する必要があります。

- **React Server Componentsでのバンドルサイズ最小化:** クライアントコンポーネントの境界を意識的に絞り込み、物件詳細ページなどのインタラクティブ部分だけを`'use client'`にすることで、初回JSペイロードを削減できます。

- **Image/Fontの自動最適化とCore Web Vitals監視:** `next/image`のAVIF対応強化とフォントのセルフホスティングはLCP改善に効果的。本番ローンチ前にVercel AnalyticsやLighthouse CIでCore Web Vitalsを継続監視する体制を整えるべきです。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではRSC StreamingとPartial Prerendering (PPR) が標準化され、静的シェルを即時配信しつつ動的データ部分だけをストリームで後続表示する構成が主流になっています。本プロジェクトの`properties/`一覧ページでも、物件カードの骨格を即表示し価格・空室状況だけを非同期取得する設計に向いています。

- **ポイント2:** `loading.tsx` + `Suspense`境界の粒度設計が重要で、境界を細かく切りすぎるとウォーターフォールが発生しTTFBが悪化します。本プロジェクトでは物件詳細ページ（画像ギャラリー・引越し費用情報・前の住人レビュー）のように独立して取得できるセクション単位で境界を分けるのがベストプラクティスです。

- **ポイント3:** Server Actionsとストリーミングの組み合わせにより、フォーム送信後の楽観的UI更新がRSC側で完結できるようになり、クライアントコンポーネントの状態管理コードを大幅に削減できます。認証フローや物件ステータス変更（`draft`→`public`）のようなミューテーションはServer Actions一本化が推奨です。

- **ポイント4:** エッジランタイムでのRSCストリーミングが各クラウドベンダーで成熟し、日本国内ユーザー向けには東京リージョンのエッジ配信でTTFBを大幅短縮できます。ベータローンチ前のパフォーマンス要件次第ですが、Vercel Edge等への配置検討の価値があります。

- **ポイント5:** ストリーミング中のエラーハンドリングには`error.tsx`境界だけでなく、ストリーム分割後の部分的失敗（一部セクションだけ取得失敗）に対するフォールバックUI設計が必須です。特商法表記やプライバシーポリシーなど法務関連ページは静的生成に留め、ストリーミング起因の表示崩れリスクを避けるべきです。

### 3. API design REST GraphQL tRPC 2026

- **スキーマファースト×型安全性の統合:** tRPCやGraphQL Code Generatorの普及で「コード生成」よりも「型推論」が主流になり、バックエンドの変更がフロントエンドの型エラーとして即座に検出される開発フローが標準化している。sumitsugiのようなNext.js+TypeScript構成では、API層にtRPCを採用すればREST用のOpenAPI定義やGraphQLスキーマを別途メンテせずに済み、開発速度が上がる。
- **BFF (Backend for Frontend) パターンの定着:** モバイル/Web/管理画面など複数クライアントがある場合、単一のRESTやGraphQLエンドポイントで全てを賄うより、各クライアント専用のBFF層を薄く挟む設計が主流になっている。これにより物件検索・問い合わせフォームなど機能ごとに最適化されたレスポンス形状を維持しやすい。
- **GraphQLのN+1問題はDataLoaderだけでは不十分:** 2026年時点ではPostgresのクエリプランナーと連携したバッチング（Prisma + DataLoader、または直接SQLビューの活用）が推奨されており、物件一覧や前の住人情報など多段リレーションを持つデータ構造では特に注意が必要。
- **REST+JSON:APIの「枯れた安定性」が再評価されている:** 高トラフィックな公開APIや外部パートナー連携では、学習コストの低さとキャッシュ戦略（CDN/ETag）のしやすさからRESTが依然優位。sumitsugiの公開物件検索APIのような読み取り中心・キャッシュ可能なエンドポイントはREST、内部の複雑な引き継ぎフロー処理はtRPCという「併用」が実務的な最適解になりつつある。
- **エッジランタイムとAPIレイテンシの最適化:** Next.js 16のEdge RuntimeでtRPCやRoute Handlersを実行し、物件検索のようなレイテンシ重視の機能をユーザーに近いエッジで処理する構成が増えている。ただしDB接続（Prisma等）のエッジ対応状況は要確認で、全面移行には検証が必要。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** 2026年はCloudflare WorkersやVercel EdgeでLLM推論・軽量MLモデルの実行がデフォルト化し、CDNエッジでパーソナライズやレコメンドをミリ秒単位で返せるようになっている。弊社の物件検索でも、地域別レコメンドをエッジ関数に移すことでオリジン負荷とレイテンシを同時に削減できる可能性がある。

- **コールドスタート問題の実質的解消:** V8 isolateベースのランタイム（Workers/Deno Deploy系）がコールドスタートを1桁ミリ秒まで短縮し、トラフィックが不規則なB2Cサービスでもサーバーレスを安心して採用できる段階に来ている。アクセスが夜間・週末に偏る不動産系サービスとは相性が良い。

- **エッジとオリジンのデータ整合性がボトルネック化:** 計算はエッジに分散しても、DBは依然中央集権的なことが多く、強整合性が必要な処理（決済・在庫確定）はエッジに向かない。引越し費用決済や物件の公開/非公開ステータス切替のような強整合性操作は、エッジではなくオリジンに残す設計判断が必要。

- **Edge-first フレームワークの定着:** Next.js 16のPartial Prerendering + Edge Runtimeの組み合わせが主流化し、静的部分をエッジでキャッシュしつつ動的部分だけをストリーミングする設計が標準パターンになっている。本プロジェクトのApp Routerでも、物件一覧ページなど読み取り中心のページはこのパターンへの移行で初期表示速度を改善できる余地がある。

- **ベンダーロックインとコスト予測の難しさがトレードオフ:** エッジ実行は従量課金でスケールするが、トラフィック急増時のコスト予測が難しく、特定クラウドのエッジランタイムAPIに依存すると移行コストが高い。MVP後のスケール期に導入を検討する場合は、Web標準API（Fetch/Streams）に寄せた実装で将来の移行性を確保すべき。

### 5. authentication security best practices 2026

- **パスキー/FIDO2が標準に:** 2026年時点でパスワードレス認証（WebAuthn/パスキー）が主要ブラウザ・OSで標準サポートされており、フィッシング耐性とUX向上を両立できる。新規実装では最初からパスキー対応を前提に設計すべき。

- **トークンのライフサイクル管理:** アクセストークンは短命化（15分程度）し、リフレッシュトークンのローテーション＋再利用検知（refresh token rotation with reuse detection）を必須化する。長寿命トークンの漏洩が未だ最大のインシデント原因。

- **多要素認証もフィッシング耐性型へ:** SMS/OTPベースのMFAはSIMスワップやリアルタイムフィッシングで突破されるため、認証器（TOTPアプリ）やハードウェアキー、パスキーへの移行が推奨される。sumitsugiのような個人情報（物件情報・取引）を扱うサービスでは特に重要。

- **ゼロトラスト前提のセッション管理:** IPアドレスやデバイスフィンガープリントの変化を検知してセッションを再検証する仕組み（continuous authentication）が一般化。Next.js App Routerでは middleware層でのセッション検証を一元化し、各ルートでの検証漏れを防ぐ設計が有効。

- **シークレット管理の自動化:** APIキーやJWTシークレットの手動管理は漏洩リスクが高く、Vault系ツールや環境変数＋CI/CDでのシークレットスキャン（gitleaks等）を組み合わせた自動ローテーションが2026年のベストプラクティス。本プロジェクトのCLAUDE.mdにある「No hardcoded values」原則とも合致する。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma ORMはPostgreSQLとの型安全な連携が強みで、Supabase上でもマイグレーション管理とスキーマ駆動開発を両立できる。ただしRLS（Row Level Security）はPrisma単体では表現できないため、SupabaseのRLSポリシーはSQLマイグレーションやSupabase CLIで別管理する運用が定着している。
- **ポイント2:** Supabaseの接続プーリング（PgBouncer/Supavisor）とPrismaのコネクションプールが競合しやすく、サーバーレス環境（Vercel等）ではPrismaの`connection_limit`調整や`pgbouncer=true`パラメータの明示が必須になっている。
- **ポイント3:** Prisma Accelerate等のエッジキャッシュ層を併用することで、読み取り負荷の高いAPIルートのレイテンシを大幅に削減できる。sumitsugiのような物件一覧表示（`properties/`）は読み取り比率が高く、キャッシュ戦略の投資対効果が高い領域。
- **ポイント4:** SupabaseのリアルタイムサブスクリプションとPrismaのクエリを併用する場合、型定義の二重管理（Prisma Client型とSupabase Realtimeペイロード型）が発生しやすく、Zodスキーマを単一ソースにして両方から参照する構成が推奨される。
- **ポイント5:** マルチテナントや`draft`/`public`のようなステータス分岐が絡む設計では、RLSポリシーとアプリ層のバリデーションの二重防御が重要。Prismaのマイグレーション変更時は必ずRLSポリシーへの影響をレビューする運用ルールを設けるべき。

### 7. WebAssembly Rust performance 2026

- **コンパイル最適化の進化:** Rust 1.80以降のwasm32-wasip2ターゲットとWasm GC提案の実装進展により、コンパイル後のバイナリサイズが大幅に削減され、起動時間（コールドスタート）が従来比で数十%改善している。実用上はLambda@EdgeやCloudflare Workersのようなエッジ実行環境での採用がさらに進む。

- **SIMD128とマルチスレッド対応の標準化:** WebAssembly SIMDとthreads proposalがブラウザ・ランタイム双方で広くサポートされ、Rustから`std::simd`経由で画像処理・動画デコード・ML推論の並列計算が実用速度域に到達している。

- **Component Model採用の加速:** WASI Preview 2のComponent Modelにより、Rust製Wasmモジュール同士やホスト言語（JS/Go/Python）との相互運用性が向上し、マイクロサービスをWasmコンポーネント単位で再構築するアーキテクチャが現実的な選択肢になっている。

- **ネイティブ比のオーバーヘッド縮小:** WasmtimeやWasmerなどのランタイムがJITキャッシュとAOTコンパイルを強化し、Rust→Wasmのネイティブコード比オーバーヘッドが10-20%程度まで縮小。サーバーサイドでのサンドボックス実行（プラグインシステム、マルチテナント処理）にWasmを選ぶ技術的コストが下がった。

- **実務上の注意点:** パフォーマンス向上はツールチェーン（`wasm-opt`、`cargo-wasi`）のバージョン依存が強いため、CIでのビルド設定の固定とベンチマーク回帰テストの導入が重要。sumitsugiのような軽量Next.jsプロジェクトでは、画像処理や検証ロジックの一部をWasm化する前にまずプロファイリングでボトルネックを特定すべき。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** 静的シェルを即時配信しつつ動的部分のみStreamingで後から流し込む構成が標準化し、TTFBとパーソナライズ性を両立できるため、`properties/`一覧や`listing/`詳細ページのような「概ね静的だが一部動的」なページに適している。

- **Server Actionsのセキュリティ境界強化:** フォーム送信・決済処理をServer Actionsに寄せる流れが続いているが、認証チェックとZodによる入力検証をAction内部で必ず行う実装が標準パターンとなっており、クライアント側のガードだけに依存しないことが2026年のベストプラクティス。

- **`use cache`ディレクティブによる粒度の細かいキャッシュ制御:** ルート単位のキャッシュから関数・コンポーネント単位の明示的キャッシュへ移行が進み、`src/lib/data.ts`のようなデータ取得層でキャッシュ戦略を明示的にタグ付け・再検証できるようになっている。

- **Server Components優先、Client Componentsは「葉」に限定:** 状態を持つUI（フォーム、インタラクティブなフィルタ等）のみを`'use client'`境界に切り出し、データ取得・レイアウトはServer Componentsに留める設計が定着し、バンドルサイズとハイドレーションコストの削減に直結する。

- **型安全なルーティングとMiddlewareの軽量化:** App RouterのTyped Routesが安定し、`src/app/`配下のリンク・リダイレクトでの型チェックが可能になった一方、Edge Middlewareは認証トークン検証など最小限の処理に絞り、重い処理はServer Components/Actionsに委譲する分離が推奨されている。

### 9. Vercel Edge Functions optimization 2026

- **Fluid Compute採用:** VercelのFluid Computeモデルにより、Edge FunctionsとServerless Functionsの垣根が低くなり、同一インスタンス内で複数リクエストを並行処理できるようになった。コールドスタート削減とコスト最適化を両立できるため、全処理をEdgeに寄せる必要がなくなった点が実装方針の見直しポイント。

- **実行環境の使い分け:** Edge Runtime（V8 isolate）はWeb標準APIのみをサポートするため、Node.js依存の重いライブラリ（PDF生成、画像処理など）を使う処理はNode.js Runtimeに残し、認証チェックやリダイレクトなど軽量・低レイテンシ処理のみEdgeに配置する判断が重要。

- **Partial Prerendering(PPR)との組み合わせ:** Next.js 16のPPRと組み合わせることで、静的シェルを即時配信しつつ動的部分だけEdgeでストリーミングできる。物件一覧ページなど、SEO用の静的コンテンツと在庫状況のような動的データが混在するページで特に効果が高い。

- **Edge Configでの低レイテンシ参照:** フィーチャーフラグやA/Bテスト設定、料金テーブルのような小規模・高頻度読み取りデータはEdge Configに置くことで、DBラウンドトリップなしにグローバルで数ms以下のレスポンスが可能。認証周りの設定値管理に向いている。

- **モニタリングとコスト管理:** Edge Functionsは実行時間課金のため、無限ループや外部API呼び出しのタイムアウト設定が甘いと想定外のコスト増につながる。Vercel Observabilityでレイテンシ分布を定期確認し、閾値超えのファンクションをNode.js Runtimeへ移行する運用ルールを設けるべき。

### 10. TypeScript type safety patterns 2026

- **厳格な型推論とconst型パラメータ:** TypeScript 5.x系で導入された`const`型パラメータやTemplate Literal Typesの活用が標準化し、APIレスポンスやルーティング定義で文字列リテラルの型安全性を保ったまま推論を効かせるパターンが主流に。本プロジェクトの`'draft' | 'public'`のようなUnion型もこの恩恵を受けやすい。

- **Zodなどのランタイム検証とスキーマ駆動型生成:** `standards.md`にもある通り境界でのZod検証が定着し、スキーマから型を`z.infer`で自動生成する「スキーマファースト」設計がデフォルトになっている。フォームやAPI入出力で型とランタイム検証の二重管理を避けられる。

- **Branded Types/Nominal Typingの普及:** `string`や`number`のプリミティブ型を素通りさせず、`UserId`や`PropertyId`のようなBranded Typeで区別する手法が広まり、IDの取り違えバグをコンパイル時に検出できるようになった。物件IDとユーザーIDが混在しやすいドメインでは特に有効。

- **満足度の高いexhaustiveness checking:** `switch`文での`never`型を使った網羅性チェックが一般的になり、Union型に新しい値を追加した際の漏れをビルド時に検出できる。`'draft' | 'public'`にステータスを追加する際のレビューコストを下げる。

- **型のみのimport分離とビルド高速化:** `import type`の強制（`verbatimModuleSyntax`）がBunやesbuild系ツールチェーンと組み合わさり、型チェックとトランスパイルの分離によるビルド高速化が標準パターンになっている。
