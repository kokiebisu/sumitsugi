# CTO Knowledge - 2026-07-30

## Daily Update (2026-07-30)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Prerendering の本格運用）:** Next.js 15以降で導入されたPPR（Partial Prerendering）が2026年には標準機能として定着し、静的シェルを即座に配信しつつ動的部分だけをストリーミングすることで、TTFBを維持したままパーソナライズ表示が可能になっている。物件詳細ページのように「基本情報は静的・在庫状況や価格は動的」な構成に特に有効。

- **ポイント2（React Compiler前提のコード設計）:** React Compilerがデフォルト有効化されつつあり、`useMemo`/`useCallback`の手動最適化が不要になる一方、コンパイラが最適化しやすい純粋な関数コンポーネント設計（副作用の分離、props不変性の徹底）がより重要になっている。既存コードのリファクタ時はこの前提を意識すべき。

- **ポイント3（Server Actionsのキャッシュ戦略）:** `use cache`ディレクティブとキャッシュタグ（`revalidateTag`）を組み合わせた粒度の細かいキャッシュ制御が主流化し、物件一覧・検索結果のような更新頻度が異なるデータを個別に無効化できる設計が、CDNコストとデータ鮮度のトレードオフを大きく改善する。

- **ポイント4（画像・フォント最適化の自動化限界）:** `next/image`と`next/font`の自動最適化はコモディティ化しており、差がつくのはLCP要素の優先度指定（`priority`属性の適切な配置）と、Core Web Vitalsを実データ（RUM）で継続監視する体制の有無。ビルド時最適化だけでは不十分で、Vercel Analyticsや同等ツールでの本番計測が必須。

- **ポイント5（Edge Runtimeの使い所の見極め）:** Edge RuntimeはCold Start削減に有効だが、Node.js APIの制約（DBドライバ非対応など）が残るため、認証チェックやリダイレクトなど軽量処理はEdge、DBアクセスを伴う処理はNode.js Runtimeという使い分けが2026年のベストプラクティスとして定着しつつある。全面的なEdge移行は過剰最適化になりがちなので注意。

### 2. React Server Components streaming 2026

- **Partial Prerendering との統合が標準化:** Next.js 16では静的シェルを即座に返しつつ、動的なRSCペイロードをストリーミングで後追いする構成が主流になっており、初期表示（TTFB/LCP）とパーソナライズ性を両立できる。sumitsugiの物件一覧・詳細ページでも、静的な物件情報を即表示し、在庫状況や価格変動などの動的部分だけをストリームで差し替える設計が有効。

- **Suspense境界の粒度設計がパフォーマンスの鍵:** 境界を細かく切りすぎるとウォーターフォールが増え、粗すぎるとストリーミングの恩恵が薄れる。データ取得の依存関係（例: 物件基本情報→前の住人の活動歴→レビュー）に沿って境界を設計し、独立して取得できるものは並列にfetchするのが2026年のベストプラクティス。

- **Server ActionsとRSCストリーミングの相互作用に注意:** フォーム送信（引越し費用の見積もり依頼など）後の再検証（revalidatePath/revalidateTag）がストリーミング中の他のSuspense境界に予期せぬ再フェッチを引き起こすケースが増えている。キャッシュタグの粒度を機能単位で細かく管理する必要がある。

- **エッジランタイムでのストリーミングコスト最適化:** RSCストリーミングはエッジ環境でのコネクション保持時間が長くなりがちで、Vercel/Cloudflare等の従量課金に直結する。認証チェックなど早期に失敗しうる処理はストリーミング開始前に済ませ、無駄なストリーム開始を防ぐ設計が推奨される。

- **型安全なストリーミング境界のテスト難易度:** E2E（Playwright）でストリーミングの中間状態（loading.tsx→実データ）を検証する際、タイミング依存のflaky testが発生しやすい。`waitForResponse`やネットワークスロットリングを使った明示的な待機戦略が必要で、sumitsugiのTDD方針（80%カバレッジ）に沿うなら、ストリーミングUIのテストパターンを早めに標準化すべき。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの採用拡大）:** TypeScriptフルスタック構成（Next.js + tRPC）では型安全性がエンドツーエンドで担保され、APIスキーマの手動同期が不要になる。sumitsugiのようなTypeScript一貫構成では、REST+OpenAPIより開発速度と保守性で優位。

- **ポイント2（GraphQLは複雑なデータ要件に限定活用）:** GraphQLは物件検索のような多階層・可変フィールドのクエリには強いが、キャッシュ戦略やN+1問題への対応コストが高く、小〜中規模チームではオーバーエンジニアリングになりやすい。

- **ポイント3（RESTは依然として外部連携の標準）:** 決済代行・地図API・外部パートナー連携など、社外向けインターフェースはRESTが実質的な業界標準であり続けており、内部API（tRPC）と外部API（REST）を使い分けるハイブリッド構成が2026年の主流。

- **ポイント4（Server ActionsとAPI層の境界の曖昧化）:** Next.js App RouterのServer Actionsが普及し、単純なCRUDではtRPC/RESTすら経由せずクライアント-サーバー間を直結するケースが増加。ただし監査ログや権限チェックが必要な操作（物件公開・決済関連）は明示的なAPI層を残すべき。

- **ポイント5（スキーマファーストとZodバリデーションの統合）:** Zodスキーマを起点にtRPCの入出力・DBスキーマ・フロントのフォームバリデーションを一元化する設計が定着しつつあり、本プロジェクトの「Zodによる境界検証」方針とも合致する。

### 4. serverless edge computing 2026

- **エッジでの推論処理の標準化:** 2026年時点でCloudflare WorkersやVercel Edge FunctionsでのLLM推論実行が一般化し、軽量モデルをエッジで動かしてレイテンシを数十ms単位に抑える構成が主流になりつつある。sumitsugiのような物件検索・マッチング機能では、ユーザーに近いエッジでの初期フィルタリング処理が体感速度向上に直結する。

- **コールドスタート問題の実質的解消:** V8 isolateベースのランタイム進化により、コールドスタートが1桁ms台まで縮小し、サーバーレスとエッジの境界がほぼ消滅した。Next.js 16のApp RouterでもEdge Runtimeを部分的に採用しやすくなっており、認証チェックや地域別コンテンツ出し分けなど軽量処理から段階的に移行する価値がある。

- **データレイヤーのエッジ分散が鍵:** 計算はエッジに寄っても、DB（Postgres等）が単一リージョンだとネットワーク往復がボトルネックになる。TursoやD1のようなエッジレプリケーション対応DB、またはRead Replicaの地理分散が2026年の実質的な差別化要因になっている。

- **観測性とデバッグの複雑化に注意:** エッジ環境が増えるほど、リクエストがどのPoPで処理されたか追跡しづらくなり、障害調査コストが上がる。OpenTelemetryベースの分散トレーシングを最初から組み込まないと、本番障害時に「どこで何が起きたか」が分からなくなるリスクが高い。

- **コスト構造の見極めが必要:** サーバーレス/エッジは低トラフィック時は圧倒的に安いが、常時稼働に近いワークロード（バッチ処理、定期集計など）では専用インスタンスより割高になるケースが増えている。MVP後のスケール局面で、機能ごとにエッジ/従来型サーバーを使い分ける判断が重要になる。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証がデフォルトとなり、フィッシング耐性のあるパスキーが主要な認証手段として定着。前の住人・次の住人双方の本人確認フローでもパスワード依存を減らし、離脱率とサポート負荷を下げられる。

- **リスクベース適応型認証:** IPレピュテーション・デバイスフィンガープリント・行動パターンをリアルタイムでスコアリングし、疑わしいログインのみ追加認証を要求する方式が主流に。全ユーザーに一律MFAを課すよりUXを損なわずセキュリティを担保できる。

- **トークンのローテーションと短命化:** アクセストークンの寿命を短く保ち、リフレッシュトークンはローテーション必須（再利用検知で即時失効）にするのが標準実装。Next.jsのSession/Cookie設計でも`httpOnly` + `SameSite=Strict` + 短命JWTの組み合わせが必須要件になっている。

- **サプライチェーン経由の認証情報漏洩対策:** npm/Bunパッケージ経由の資格情報窃取が増加しており、依存パッケージのプロビナンス検証（`bun audit`相当のSCA）と、APIキーのシークレットスキャン自動化がCI必須項目になりつつある。

- **監査ログとセッション可視化:** ユーザー自身が「どのデバイス・場所からログイン中か」を確認しセッションを個別失効できるUIが標準化。物件取引のような信頼性が重要なプラットフォームでは、不正アクセス時の説明責任（誰がいつ何を見たか）が法務・カスタマーサポート双方から求められる。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma ORMはRust製クエリエンジンから軽量TypeScript実装（Prisma Client Rust-free / Kysely的アプローチ）へ移行が進み、Edge Runtime（Vercel Edge, Cloudflare Workers）でのコールドスタート短縮とバンドルサイズ削減が実用段階に入っている。sumitsugiのようなVercelデプロイ前提のプロジェクトでは、この移行によりAPI Routeのレスポンス改善が期待できる。

- **ポイント2:** SupabaseのRLS（Row Level Security）とPrismaを併用する場合、Prisma単体はRLSを意識しないため「前の住人／次の住人」間のデータ越境アクセスを防ぐには、DB接続時にJWTベースのユーザーコンテキストをセッション変数として渡すRLSポリシー設計が必須。認証コンテキストをミドルウェアで一元管理し、Prismaのraw queryでセッション変数を注入するパターンが標準化しつつある。

- **ポイント3:** Supabaseの`pg_graphql`や`pgvector`拡張を活用したベクトル検索（物件の類似性検索、インテリアマッチングなど）がプロダクション事例として増加しており、Prisma単体では対応しないためSupabase Client（`@supabase/supabase-js`）との併用アーキテクチャ（PrismaはCRUD、Supabase Clientは検索・リアルタイム機能）が現実解になっている。

- **ポイント4:** マイグレーション運用では、Prisma Migrateのシャドウデータベース要件とSupabaseのブランチング機能（Preview Branches）を組み合わせ、PRごとに独立したDBスキーマ検証環境を作るCI/CDパターンが一般化。`bun run build`前のスキーマドリフト検出を自動化することで、本番マイグレーション事故のリスクを大幅に下げられる。

- **ポイント5:** コネクションプーリングはSupabaseのPgBouncer（Transaction Mode）とPrismaの相性問題（prepared statement非対応）が既知の課題で、2026年時点では`pgbouncer=true&connection_limit=1`設定に加え、Prisma Accelerateのようなマネージド接続プーリング層を挟む構成がサーバーレス環境（Vercel Functions）でのDB接続枯渇対策として推奨される。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC(Garbage Collection提案)の標準化が進み、RustはGCコンポーネントモデルとの統合よりも従来のlinear memoryモデルで引き続き最速の実行性能を発揮 — 特に数値計算・画像処理系のワークロードでは`wasm-opt`と`wasm-bindgen`の最適化パイプラインがネイティブ比90%超の性能を安定して出せるようになっている。

- **ポイント2:** Component Model + WASIプレビュー2の普及により、Rust製Wasmモジュール同士を言語非依存で組み合わせられるようになり、サーバーサイドでは「Wasmマイクロサービス」が軽量コンテナ代替として実用段階に入っている（起動時間はコンテナの1/100以下）。

- **ポイント3:** SIMD128とマルチスレッド（`wasm-threads`+`SharedArrayBuffer`）がブラウザ主要4エンジンで安定サポートされ、Rustの`rayon`をWasm上で使う並列処理パターンがクライアントサイドの重い計算（画像編集・PDF生成等）に現実的な選択肢になった。

- **ポイント4:** バイナリサイズ最適化（`wasm-opt -Oz`, `wee_alloc`後継の軽量アロケータ）とcold-start最適化が引き続き重要課題で、エッジ環境（Cloudflare Workers等）でのRust+Wasm採用が増える一方、ツールチェインの複雑さ（`wasm-pack`, `trunk`, `cargo-component`の使い分け）が開発者体験のボトルネックとして残っている。

- **ポイント5（sumitsugi視点）:** 物件写真の圧縮・EXIF処理やPDF生成（契約書）のようなクライアントサイド処理をRust/Wasmに寄せることで、サーバー負荷を減らしつつUXを向上できる可能性があるが、現状のNext.js/TypeScriptスタックでは導入コストに見合うホットパスがあるか要検証。

### 8. Next.js App Router patterns 2026

- **サーバーコンポーネント優先設計:** Server Componentsをデフォルトとし、Client Componentsは対話性が必要な末端コンポーネントのみに限定することで、バンドルサイズとハイドレーションコストを最小化できる。sumitsugiでも`listing/`配下の一覧・詳細表示はServer Component化し、フォーム部分のみ`'use client'`を付与する構成が効果的。

- **Partial Prerendering (PPR) の実用段階入り:** 静的シェルを即座に返しつつ動的部分をストリーミングする手法が2026年時点で標準的になりつつあり、物件検索ページのような「フィルタは動的だがレイアウトは静的」なUIでTTFBとLCPを大幅改善できる。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** ルート単位ではなく関数・コンポーネント単位でキャッシュ境界を宣言できるようになり、`data.ts`のフェッチ関数にキャッシュポリシーを直接埋め込む設計がベストプラクティス化している。

- **Server Actionsのスキーマバリデーション標準化:** Zodと組み合わせたServer Actionsが「フォーム送信+DB更新」の標準パターンとして定着し、`.claude/rules/standards.md`にもあるようなZod境界検証がAPI Routeを介さず直接実現できる。引越し費用の申込フォームなど、多段階フローに向く。

- **Route Groups + Parallel Routesによる権限分離:** `(auth)`や`(public)`のようなRoute Groupsとダッシュボード用Parallel Routesを組み合わせ、前の住人/次の住人でレイアウトを分岐させる設計が、認証状態によるUI分岐の主流パターンになっている。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化:** Edge RuntimeはV8 isolateベースで数ミリ秒起動が売りだが、依存パッケージのバンドルサイズが大きいと初期化コストが跳ね上がるため、Node.js API依存を減らし軽量ライブラリに絞ることが引き続き重要。

- **Streaming SSRとの組み合わせ:** Edge Functionsで`ReadableStream`を使ったレスポンスのプログレッシブ配信を行うことで、TTFB（Time to First Byte）を大幅短縮できる。特にAI応答のようなトークン逐次生成コンテンツと相性が良く、sumitsugiのようなチャット的UIがあれば検討価値あり。

- **Regional Edge Config / KVでのデータ近接配置:** データベースへのラウンドトリップがEdge Functionsのボトルネックになりやすいため、Vercel Edge ConfigやKVで読み取り頻度の高い設定・フラグ類をエッジにキャッシュし、オリジンへの往復を減らす設計が主流になっている。

- **Fluid Compute（Edge/Serverlessの統合実行モデル）:** 2025年以降Vercelが推進するFluid Computeにより、同一インスタンス内で複数リクエストを処理しコンピュートの無駄を削減できるため、コスト最適化の観点からEdge/ServerlessどちらでFunctionを実行するかの判断基準が変わりつつある。

- **可観測性とサイズ制限の運用管理:** Edge Functionsには実行時間・メモリ・バンドルサイズの制約があるため、OpenTelemetry対応のトレーシングを導入しつつ、重い処理（画像処理・PDF生成など）は素直にServerless Functionsに逃がすハイブリッド設計が実用的。

### 10. TypeScript type safety patterns 2026

- **型安全なランタイムバリデーション:** Zodやvalibotによる「スキーマ駆動」設計が定着し、型定義とバリデーションロジックを一元化してAPI境界での不整合を防ぐパターンが標準になっている。sumitsugiでも`.claude/rules/standards.md`で定めている通り、システム境界でのZodスキーマ活用が基本方針。

- **`satisfies`演算子の定着:** 型推論を保ちつつ制約チェックもできる`satisfies`が、Union型やConfig定義で標準的に使われ、`as`によるキャストの乱用が減っている。

- **Branded/Nominal型による意味的安全性:** `UserId`と`ListingId`のような同じ`string`型でも意味の異なるIDを、branded typeで区別しミスを防ぐパターンが浸透。物件ステータスのような`'draft' | 'public'`のUnion型でも、grepで全使用箇所を確認する運用と組み合わせることで安全性が高まる。

- **テンプレートリテラル型とルーティングの型安全化:** Next.js App Routerのようなファイルベースルーティングでも、テンプレートリテラル型でパスパラメータを型検証する動きが加速し、`params`の型ズレによるランタイムエラーを未然に防げる。

- **AIコード生成との相性:** 型が厳密であるほどAIエージェント（Claude Codeなど）が生成するコードの正しさをコンパイル時に検証できるため、TDDと型安全性を組み合わせた開発フローが「AI活用時代の標準」になりつつある。
