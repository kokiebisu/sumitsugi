# CTO Knowledge - 2026-03-27

## Daily Update (2026-03-27)

### 1. Next.js performance optimization 2026

- **React Server Components の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチロジックをRSCに集約し、`'use client'`は本当にインタラクティブな末端コンポーネントにのみ付与する設計が標準となった。

- **Partial Prerendering (PPR) の本番投入:** 静的シェルと動的ストリーミングを1リクエスト内で混在させるPPRがStableになり、TTFBを落とさずにパーソナライズドコンテンツを提供できる。`next.config`で`ppr: true`を有効化するだけで既存ページも恩恵を受ける。

- **`<Image>`と`<Script>`の最適化設定の見直し:** `priority`属性の付与対象をLCP要素に絞り込み、`loading="lazy"`のデフォルト挙動に任せる範囲を明確化する。Lighthouseスコアよりもリアルユーザー指標（INP/LCP）をCIで計測することが重要。

- **Route Segment Config によるキャッシュ戦略の明示化:** `fetch`のキャッシュ動作がNext.js 15以降でデフォルトno-storeに変わったため、`revalidate`や`cache`オプションを各セグメントで意図的に宣言しないと意図せぬパフォーマンス劣化が起きる。

- **Turbopackの本番採用:** `next dev --turbopack`がStableとなり、大規模コードベースでのHMRが5〜10倍高速化。ビルド時間短縮はDX向上だけでなくCI/CDコストにも直結するため、移行の費用対効果は高い。

### 2. React Server Components streaming 2026

- **Suspense境界の戦略的配置が鍵:** RSCストリーミングはSuspenseバウンダリ単位でHTMLをチャンク送信するため、データフェッチの粒度に合わせてSuspenseを細かく配置することで、FCP（First Contentful Paint）を大幅に改善できる。

- **Partial Prerendering（PPR）との統合が主流化:** Next.js 15以降でPPRが安定化し、静的シェルを即座に配信しつつ動的コンテンツをストリームで差し込むハイブリッド戦略が標準アーキテクチャになりつつある。

- **クライアントコンポーネントのバンドルサイズ管理が重要:** RSCはサーバー側でレンダリングされJSをクライアントに送らないため、`"use client"`の境界を最小化し、インタラクティブな末端コンポーネントのみをクライアント化することでTTI（Time to Interactive）を削減できる。

- **データフェッチの並列化でウォーターフォールを排除:** `Promise.all`やReactの`use()`APIを活用し、親→子の逐次フェッチ（ウォーターフォール）を防ぐ設計が2026年のベストプラクティス。特にORMクエリの並列実行がパフォーマンスのボトルネック解消に直結する。

- **エラーバウンダリとローディングUIの設計が体験品質を左右:** `error.tsx`と`loading.tsx`をルートセグメントごとに適切に配置することで、ストリーミング中の部分的なエラーが全体のUXを壊さない堅牢な設計が実現できる。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全性の標準化:** 2026年時点でtRPCはフルスタックTypeScriptプロジェクトのデファクトになりつつあり、スキーマ定義なしでクライアント・サーバー間の型共有が実現できるため、Next.js + Prismaスタックとの親和性が特に高い。

- **GraphQLの適用領域の明確化:** GraphQLは「全APIに使う」から「複雑なデータグラフが必要な場面に限定する」方向へシフトし、Relay/Apollo Federationによるマイクロサービス統合や、BFF（Backend for Frontend）パターンでの活用が主流になっている。

- **RESTは死なず、OpenAPI 3.1で進化:** RESTは外部公開APIや異なる言語スタックとの連携では依然として最有力であり、OpenAPI 3.1 + Zodによるスキーマファーストな型生成（`zod-openapi`等）でtRPC並みの型安全性を確保できるようになった。

- **エッジランタイム対応が設計制約に:** Cloudflare Workers / Vercel Edge等の普及により、APIレイヤーは「コールドスタートなし・軽量」であることが求められ、重量級のGraphQLランタイムよりHTTP/JSONストリーミングやtRPC over Fetchが優位になっている。

- **AIエージェント統合を前提としたAPI設計:** MCPやFunction Callingの普及により、APIはLLMエージェントが自律的に呼び出す対象になっており、明示的なスキーマ・説明文・冪等性の確保がAPI品質の新たな評価軸となっている。

### 4. serverless edge computing 2026

- **エッジでのAI推論が主流化:** 2026年時点でCloudflare Workers AI、Vercel Edge Functions、Fastly Compute@Edgeがモデル推論をエッジで実行できるようになり、レイテンシを中央集権型より60-80%削減できるケースが増加。小規模モデル（SLM）のエッジ展開が実用段階に入った。

- **WebAssembly（Wasm）がデファクトランタイムに:** 言語非依存でコールドスタートがほぼゼロのWasmは、Node.js系ランタイムを置き換えつつある。RustやGo製のエッジ関数がパフォーマンスと安全性の両立を実現。

- **エッジDBとの組み合わせが設計の前提に:** Turso（libSQL）、Cloudflare D1、PlanetScale Boost等のエッジ対応DBが普及し、「エッジでステートレス＋中央DBへの往復」という旧設計から「エッジ＋分散レプリカ」へのパラダイムシフトが完了しつつある。

- **コールドスタート問題は実質解消、次の課題はデバッグ性:** V8 Isolates等の技術でコールドスタートはミリ秒以下になった一方、分散トレーシング・ログ集約のツールチェーンがまだ追いついておらず、可観測性（Observability）の整備が2026年の最重要課題。

- **ベンダーロックインリスクへの対応:** WinterCG（Web-interoperable Runtimes Community Group）標準の策定が進み、特定プロバイダーに依存しないポータブルなエッジ関数の記述が現実的に。アーキテクチャ設計時はWinterCG準拠のAPIのみに依存させる方針が推奨される。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）への移行加速:** パスワードレス認証がデファクトスタンダードになりつつあり、フィッシング耐性と利便性を両立できるパスキーの採用は2026年において必須レベルの対応となっている。

- **セッショントークンの短命化とリフレッシュ戦略:** アクセストークンの有効期限を15分以下に絞り、リフレッシュトークンのローテーション（RTR）を組み合わせることで、トークン漏洩時の被害を最小化する設計が標準的なアプローチとなっている。

- **デバイスフィンガープリンティングによる異常検知:** IPアドレスだけでなく、デバイス固有の特徴（User-Agent、タイムゾーン、画面解像度など）を組み合わせてリスクスコアリングを行い、不審なセッションをリアルタイムで検出・ブロックする手法が普及している。

- **OAuthスコープの最小権限原則の徹底:** サードパーティ連携でのスコープ過剰付与が依然として脆弱性の温床となっており、要求するスコープを機能単位で細分化し、ユーザーへの明示的な同意フローを設計することがコンプライアンス上も重要になっている。

- **サプライチェーン経由の認証ライブラリへのリスク管理:** 認証処理を担うnpmパッケージやSDKの依存関係を定期的に監査し（`bun audit`等）、SBOM（ソフトウェア部品表）を管理することで、ライブラリ汚染による認証バイパス攻撃への備えを強化することが求められている。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のEdge Runtime対応成熟:** Prisma ClientがVercel Edge・Cloudflare Workersで安定動作するようになり、Next.js App RouterのServer Componentsから直接DB接続するパターンが主流化。コネクションプーリングはPrisma Accelerateで解決するのがベストプラクティス。

- **Supabase の`pgvector`統合によるRAGアーキテクチャ:** PostgreSQLネイティブのベクトル検索がSupabaseで本番利用可能になり、外部ベクトルDBを別途立てずにRLS（行レベルセキュリティ）と組み合わせたセキュアなRAG構成が実現できる。

- **RLS × Prisma の組み合わせに要注意:** SupabaseのRLSをPrismaから利用する場合、`service_role`キーを使うとRLSがバイパスされるため、`anon`キー＋JWT設定を明示的に管理する必要がある。セキュリティ設計の早期決定が重要。

- **Database Branchingの実用化:** Supabase Branchingにより、PRごとにDB環境を分離してスキーママイグレーションをテストできる。`prisma migrate dev`との組み合わせでCI/CDパイプラインのデータ安全性が大幅向上。

- **型安全性の一気通貫:** Supabaseの`supabase gen types typescript`とPrismaの型生成を組み合わせることで、DB→API→UIまで型が繋がる設計が現実的になった。ただし二重管理になるため、どちらをsource of truthにするかアーキテクチャ上で明確化すること。

### 7. WebAssembly Rust performance 2026

- **Component Model の本格普及:** WASI 0.2 と Component Model が安定化し、Rust製WasmコンポーネントをJS/Python等と型安全に組み合わせるポリグロット設計が実用段階に入った。`cargo component` ツールチェーンで本番利用が現実的になっている。

- **SIMD・スレッド対応の成熟:** Wasm SIMD と SharedArrayBuffer ベースのマルチスレッドが主要ブラウザ・ランタイムで安定し、Rust の `std::simd` / Rayon との統合により、ネイティブ比90%超のスループットが計算集約タスクで達成されるケースが増加。

- **起動レイテンシの大幅改善:** AOT コンパイル（Wasmtime の Cranelift / WasmEdge の LLVM backend）と Module Streaming の組み合わせにより、Cold Start が数十msオーダーに短縮。エッジ・サーバーレスでのRust Wasmが競争力を持つ。

- **GC提案との共存戦略が必要:** Wasm GC Proposal の普及でJS/Dart側のランタイムサイズが縮小する一方、RustはGC不要のため依然としてメモリ効率で優位。ただし `wasm-bindgen` の型マーシャリングコストは引き続き設計上のボトルネックになり得る。

- **Wasmtime / WasmEdge の組み込み用途拡大:** IoT・プラグインシステムへの採用が加速しており、Rust + Wasm のサンドボックス実行モデルがセキュリティ要件の高い B2B SaaS のプラグイン基盤として標準的な選択肢になりつつある。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** 2026年はServer Componentsをデフォルトとし、クライアント境界を最小化する設計が標準化。`'use client'`はインタラクティブな末端コンポーネントのみに限定し、バンドルサイズを大幅削減できる。

- **Partial Prerendering (PPR) の本番採用:** 静的シェルと動的コンテンツを同一ページで混在させるPPRが安定版となり、TTFBと動的レンダリングのトレードオフを解消。`experimental_ppr: true`から正式APIへ移行済み。

- **Server Actions によるAPIレイヤー廃止:** フォーム送信・ミューテーションはServer Actionsに集約し、独立したAPI Routeを減らす設計が主流。型安全性と`revalidatePath`による自動再検証が開発効率を向上させる。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** `fetch`キャッシュに依存せず、関数・コンポーネント単位で`use cache`を宣言する新パターンが定着。`cacheLife`・`cacheTag`でキャッシュ戦略を明示的に制御できる。

- **Streaming + Suspense の階層設計:** `loading.tsx`に頼らず、コンポーネント階層ごとに`<Suspense>`を配置してストリーミングの粒度を最適化。重いデータ取得を並列化しつつ、段階的なUI表示でCLS（累積レイアウトシフト）を抑制する設計が必須。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択的活用:** 全APIルートをEdgeに移行するのではなく、レイテンシ敏感なルート（認証・パーソナライゼーション・A/Bテスト）のみを対象にすること。Node.js APIが使えない制約を考慮した設計が必要。

- **Fluid Computeへの移行:** 2025年後半からVercelはFluid Computeを推進しており、EdgeとServerlessの境界が曖昧になりつつある。コールドスタートの問題は大幅に改善されているため、「Edge一択」という判断は再検討が必要。

- **KVストア・データベース接続の最適化:** Edge FunctionsからはTCP接続が使えないため、Vercel KV（Upstash Redis）やTurso（libSQL over HTTP）など、HTTP/WebSocket対応のデータソースを選定することがボトルネック解消の鍵。

- **バンドルサイズの厳格な管理:** Edge Runtimeは1MBのバンドル制限があり、`next/server`のMiddlewareで重いライブラリ（例：zod、date-fns）を使うと超過しやすい。`@edge-runtime/primitives`の活用と依存関係の精査が必須。

- **Observabilityの強化:** Edge実行のトレーシングはNode.jsより難易度が高い。2026年時点ではVercel Speed InsightsとOTEL（OpenTelemetry）の統合が成熟してきており、`waitUntil()`を使った非同期ロギングパターンの採用が推奨される。

### 10. TypeScript type safety patterns 2026

- **Branded Types の実用化:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded Typesが、ドメイン境界での型混同バグを防ぐ標準パターンとして定着。実行時オーバーヘッドゼロで型安全性を強化できる。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` が2026年時点でほぼ全プロジェクトの必須ツールに。型推論を保ちつつ型チェックを行えるため、`as const` との組み合わせが特に強力。

- **Zod + tRPC によるスキーマ駆動型安全性:** API境界でのランタイム検証にZodスキーマを使い、そこから型を導出するパターンが主流。フロントエンド・バックエンド間の型ズレをゼロにできる。

- **Template Literal Types の高度活用:** ルートパス、イベント名、CSSクラス名などをTemplate Literal Typesで厳密に型付けするパターンが拡大。`/api/${string}` のような構造化文字列の型安全性が実用レベルに達した。

- **`noUncheckedIndexedAccess` の標準化:** `tsconfig.json` での `noUncheckedIndexedAccess: true` が「厳格設定の新デフォルト」として認知され、配列・オブジェクトアクセス時の暗黙的 `undefined` による実行時エラーを型レベルで排除する動きが加速。
