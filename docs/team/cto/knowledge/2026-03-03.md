# CTO Knowledge - 2026-03-03

## Daily Update (2026-03-03)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントに送るJavaScriptを最小化するため、デフォルトでServer Componentsを使い、インタラクティブな部分のみ`'use client'`を付与する設計が標準になっている。バンドルサイズを30〜50%削減できるケースも多い。

- **Partial Prerendering (PPR) の本番投入:** 静的シェルを即座に配信しつつ動的コンテンツをストリームする PPR が安定化し、TTFBとLCPの両立が可能になった。`next.config.ts`の`experimental.ppr`フラグで段階的に適用できる。

- **Turbopack への移行完了:** Next.js 16ではTurbopackがデフォルトバンドラーになり、大規模コードベースでのホットリロードが従来比5〜10倍高速化。`webpack`カスタム設定が残っている場合は移行コストを早めに見積もること。

- **Server Actions によるネットワーク往復削減:** フォーム送信やデータ変更を Server Actions に集約することで、API Routeを介さない直接的なサーバー処理が実現。`revalidatePath`/`revalidateTag`と組み合わせてキャッシュ戦略を精密にコントロールできる。

- **Edge Runtime と地理的分散の最適化:** ミドルウェアやAPIを Edge Runtime で動かしCDNエッジに配置することで、グローバルレイテンシを大幅削減。ただしEdgeはNode.js APIの制約があるため、DB接続（Drizzle + Neon等）はコネクションプールの設計に注意が必要。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の実用化:** Next.js 15以降でPPRが安定版となり、静的シェルを即時配信しながら動的コンテンツをストリームする「ハイブリッドレンダリング」がデフォルト戦略になりつつある。CDNキャッシュとSSRの利点を同時に得られる点が大きい。

- **`use()` フック + Suspense の組み合わせ:** React 19で安定化した `use()` によりPromiseを直接コンポーネントで扱えるようになり、データフェッチのウォーターフォール問題がコンポーネント境界で制御しやすくなった。Suspense境界の設計がアーキテクチャの核心になる。

- **Server Actions によるAPI層の簡略化:** フォーム送信・ミューテーション処理をRSCと同一コロケーションで定義できるServer Actionsが普及し、REST/GraphQL APIを介さない軽量なデータ変更フローが選択肢として定着している。ただしセキュリティ設計（CSRF・入力検証）は引き続き注意が必要。

- **Edge Runtimeとの親和性:** RSCストリーミングはEdge（Cloudflare Workers, Vercel Edge）との組み合わせで地理的レイテンシを最小化できる。ただしNode.js専用ライブラリが使えない制約があるため、ランタイム選択はアーキテクチャ設計の早期フェーズで確定すべき。

- **DevToolsとObservabilityの整備:** ストリーミングレスポンスのデバッグはこれまで困難だったが、React DevTools・Next.js OpenTelemetry統合が成熟し、チャンク単位のタイミング可視化が可能になった。パフォーマンスボトルネックの特定にはTTFB・FCP・LCPをSuspense境界ごとに計測する習慣をチームに定着させることを推奨する。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの実質標準化:** TypeScriptフルスタック（Next.js等）では tRPC が型安全なAPI層として定着し、スキーマ定義なしにクライアント・サーバー間で型共有できる点がDXを大幅に向上させている。

- **REST + OpenAPI自動生成の進化:** REST は依然として公開APIの主流だが、OpenAPI 3.1仕様から TypeScript クライアントを自動生成するツール（Orval、Hey API等）が普及し、型安全性の面で tRPC に近い体験を実現している。

- **GraphQLの選択的採用:** 複雑なデータグラフや複数クライアントへの柔軟なデータ提供が必要な場合には有効だが、over-engineering リスクから中小規模プロジェクトでは REST/tRPC が優先される傾向が強まっている。

- **AIストリーミングによるSSEの再評価:** LLM統合の普及により、Server-Sent Events（SSE）が従来のリクエスト/レスポンス型APIと組み合わされるパターンが急増。WebSocketより軽量で、Next.js の `ReadableStream` とも相性が良い。

- **BFF（Backend for Frontend）の標準化:** フロントエンド専用のAPI集約層（BFF）をNext.js Route Handlersや独立サービスで実装し、外部マイクロサービスとの複雑な通信を隠蔽するアーキテクチャが、特にモノリスからの移行パターンとして定着している。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** WebAssembly（Wasm）とONNXランタイムの成熟により、軽量LLMモデルをCloudflare Workers・Vercel Edge Functionsで直接実行するパターンが普及し、レイテンシを大幅削減できる。

- **Durable ObjectsとSQLite-at-Edgeの台頭:** Cloudflare Durable ObjectsやTurso（libSQL）により、エッジでのステートフル処理が現実的になり、従来必須だった中央集権型DBへのラウンドトリップが不要になるケースが増えた。

- **エッジ・オーケストレーション層の複雑化:** 複数CDN/エッジプロバイダー間でのルーティング・フェイルオーバーを管理するミドルウェア層が必要となり、Wrangler・OpenNext等のツールチェーン選定がインフラコストに直結する。

- **コールドスタート問題の事実上の解消:** V8 Isolateベースの実行環境（Workers/Edge Runtime）がNode.jsコンテナ起動に比べ1000倍以上高速化し、コールドスタートはもはや設計上の制約ではなくなった。

- **セキュリティ境界の再定義:** エッジでの認証トークン検証・レート制限・WAFが標準化される一方、ゼロトラスト前提でエッジ→オリジン間の通信も暗号化・署名検証を必須とするアーキテクチャが求められる。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の本格移行:** FIDOアライアンスのパスキー標準が2026年には業界デファクトとなり、パスワードベース認証からの脱却が加速。WebAuthn Level 3の実装を優先し、フォールバックとしてSMSではなくTOTPを選択する。

- **ゼロトラスト継続検証:** ログイン時の一度限りの認証では不十分。セッション中もデバイス状態・行動パターン・地理情報を継続的に評価し、リスクスコアに基づいて再認証を要求するアーキテクチャが標準化されつつある。

- **AIを活用した異常検知の必須化:** クレデンシャルスタッフィング攻撃がAIで高度化しており、従来のレート制限だけでは不十分。行動バイオメトリクスや機械学習ベースの不正ログイン検知（例: AWS Cognito Advanced Security、Auth0 Attack Protection）の導入が実質的な必須要件になっている。

- **OAuthトークン管理の厳格化:** Refresh Token Rotationの強制、Sender-Constrained Tokens（DPoP）の採用、トークン有効期限の短縮化（アクセストークン: 5〜15分）が推奨される。特にSPA/モバイルアプリでのトークン保存にはSecure Storage APIを使用し、LocalStorageは禁止。

- **サプライチェーンリスクとしての認証ライブラリ管理:** `passport.js`や`jose`等の認証関連パッケージの依存関係は定期的にSBOM（Software Bill of Materials）で追跡し、`bun audit`や`socket.dev`で脆弱性を継続監視する体制が不可欠。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x + TypedSQL の採用:** Prisma 6では生SQLをタイプセーフに書ける`TypedSQL`が安定化し、複雑クエリでもORMとSQLを柔軟に使い分けられるようになった。パフォーマンスが要求される箇所だけSQLへ落とす設計が現実的な選択肢となっている。

- **Supabase Supavisor によるコネクションプーリング:** 従来のPgBouncerに代わりRustベースの`Supavisor`が標準化し、サーバーレス環境（Vercel / Edge Functions）でのコネクション枯渇問題が大幅に緩和された。`DATABASE_URL`にpoolerエンドポイントを使うことが必須ベストプラクティス。

- **Row Level Security (RLS) とPrismaの共存:** SupabaseのRLSポリシーをDB層のセキュリティ基盤とし、Prismaはアプリ層のクエリビルダーとして使う「二層防御」アーキテクチャが定着。`set_config('request.jwt.claims', ...)`でRLSにユーザーコンテキストを渡すパターンが標準化している。

- **pgvector × Supabase でのAI統合:** `pgvector`拡張を活用したベクトル検索がSupabaseネイティブで利用可能になり、RAG（検索拡張生成）パイプラインをDBに集約できる。Prismaからは`$queryRaw`でベクトル演算クエリを呼び出す設計が現実解。

- **Prisma Accelerate によるグローバルキャッシュ:** Prisma Accelerateのエッジキャッシュ機能により、リードヘビーなクエリをDB負荷なしにグローバル低レイテンシで配信可能。Supabaseの読み取りレプリカと組み合わせることでスケーラビリティが飛躍的に向上する。

### 7. WebAssembly Rust performance 2026

- **ポイント1: WASIp2（WASI Preview 2）の本格普及:** コンポーネントモデルが安定化し、RustのWASM出力がブラウザ外（サーバー・エッジ）でも実用レベルに達した。`wasmtime` + Rustの組み合わせはサンドボックス実行環境として本番採用が急増している。

- **ポイント2: SIMD・スレッド対応の成熟:** WebAssembly SIMDとShared Memoryが主要ランタイムで安定し、Rustの`rayon`相当の並列処理がWASM上で動作可能に。画像処理・機械学習推論での速度差がネイティブの80〜95%まで縮まった。

- **ポイント3: バイナリサイズの最適化成熟:** `wasm-opt`（Binaryen）＋Rustの`opt-level='z'`＋LTOの組み合わせで、100KB以下の実用的なWASMバイナリが当たり前に。`cargo-component`により配布・バージョニングも標準化された。

- **ポイント4: ガベージコレクション非依存の優位性:** WasmGC提案の普及でGC言語のWASM対応が進む中、Rustはゼロコスト抽象とGCレスで起動レイテンシ（コールドスタート1ms以下）の面で依然として最強ポジションを維持している。

- **ポイント5: エッジ・FaaSでの採用加速:** Cloudflare Workers・Fastly Compute@Edgeでの本番ワークロードにRust+WASMが標準選択肢に。メモリ安全性とパフォーマンスの両立がセキュリティ要件の厳しいエッジ環境でのKiller App化を加速している。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** デフォルトでServer Componentsを使用し、インタラクティブな部分にのみ`'use client'`を付与する。これによりバンドルサイズを最小化し、初回表示速度（FCP/LCP）を大幅に改善できる。

- **Partial Prerendering（PPR）の実用化:** Next.js 15以降でPPRが安定化し、静的シェル+動的ストリーミングのハイブリッド配信が標準パターンに。`<Suspense>`境界を適切に設計することで、ウォーターフォールを回避しながら動的コンテンツを後続配信できる。

- **Server Actions によるAPIレス設計:** `'use server'`を活用したフォーム送信・データ変更処理が主流。REST APIエンドポイントを別途作らず、型安全なRPC的アプローチでクライアント-サーバー間通信を簡潔に書ける。

- **キャッシュ戦略の明示的管理:** `fetch`の`cache`/`revalidate`オプション、`unstable_cache`、`revalidatePath`/`revalidateTag`を組み合わせた細粒度キャッシュ制御が必須スキルに。デフォルトキャッシュ挙動がNext.js 15で変更されたため、意図を明示するコーディング規約が重要。

- **パラレルルート + インターセプトルートによるモーダルUX:** `@slot`と`(.)intercepting`を組み合わせることで、URLを維持しながらモーダル表示するAirbnb的UIが実装しやすくなった。現プロジェクトの物件詳細モーダルなどに有効。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge Runtime の制約を活かした設計:** Edge Functionsは Node.js ランタイムではなく V8 isolate ベースのため、`fs`や`crypto`など一部 Node.js APIが使えない。依存ライブラリのEdge互換性を事前にチェックし、`export const runtime = 'edge'`を追加するだけでなく、バンドルサイズを1MB以下に抑えることがコールドスタート削減の鍵。

- **ポイント2: Middleware との役割分担の明確化:** 認証チェック・リダイレクト・A/Bテストなどグローバルに低レイテンシで実行すべき処理はMiddlewareに、データ取得を伴うロジックはRoute Handlersに分離する。Middlewareに重い処理を集中させるとWARMリクエストでも50ms超えのリスクがある。

- **ポイント3: KV/Cache APIによるデータアクセス最適化:** Vercel KV（Upstash Redis）やEdge Cacheを活用し、データベース直接アクセスをエッジで避ける。`waitUntil()`でレスポンス返却後にキャッシュ更新を非同期実行することで、ユーザー体感レイテンシをさらに削減できる。

- **ポイント4: リージョン戦略の見直し:** 2026時点でVercelのEdgeは100+リージョンに拡大しているが、データベース（例: Supabase, PlanetScale）のリージョンとのRTTが支配的になりがち。`x-vercel-id`ヘッダーでリクエストリージョンを監視し、DBを近接リージョンに配置するか、Read Replicaを活用する。

- **ポイント5: Observability の強化:** Edge環境では従来のAPMツールが動かないケースが多い。Vercel SpeedInsightsとOpenTelemetry（`@vercel/otel`）を組み合わせ、エッジ関数のP99レイテンシとエラー率をダッシュボード化することが、本番品質維持の前提条件になっている。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の`satisfies`により、型推論の恩恵を維持しながら型チェックを強制できる。`as`キャストと異なり実行時安全性も担保される。

- **Template Literal Types + Branded Types の組み合わせ:** `type UserId = string & { __brand: 'UserId' }` のようなBranded Typesで意味的な型区別を実現し、IDの取り違え等の論理バグをコンパイル時に検出できる。

- **`noUncheckedIndexedAccess` の標準化:** tsconfig厳格化の次の一手として、配列・オブジェクトのインデックスアクセスで`undefined`を強制的に考慮させる。本プロジェクトでも未設定なら有効化を推奨。

- **Zod + `z.infer<>` によるスキーマ駆動型定義:** 型定義とバリデーションロジックの二重管理を排除。APIレスポンスやフォームデータは`z.infer`から型を派生させることで、スキーマが唯一の真実となる。

- **`const` 型パラメータ（TypeScript 5.0+）の活用:** `function fn<const T>(arg: T)` により、リテラル型の推論精度が向上。特にルート定義やEnum代替パターンで、より厳密な型絞り込みが可能になった。
