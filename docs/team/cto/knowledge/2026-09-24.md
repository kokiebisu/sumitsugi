# CTO Knowledge - 2026-09-24

## Daily Update (2026-09-24)

### 1. Next.js performance optimization 2026

- **React Compiler の標準採用:** Next.js 16ではReact Compilerがデフォルトでbuildプロセスにトからhy込まれ、`useMemo`/`useCallback`の手動最適化が大部分不要に。開発者はメモ化を意識せずコードを書け、コンパイラが自動で再レンダリングを最小化する。

- **Partial Prerendering (PPR) の本格運用:** 静的シェルと動的コンテンツを1つのルートで組み合わせ、TTFBを静的並みに保ちながらパーソナライズされたUIを配信可能に。sumitsugiの物件一覧ページのように「基本レイアウトは静的、価格・空室状況は動的」な構成に特に有効。

- **Turbopackのbuild完全移行:** Webpackからの移行が既定路線となり、大規模プロジェクトでのbuild時間が大幅短縮（数分→数十秒レベル）。CI/CDパイプラインの高速化に直結するため、`bun run build`の実行時間短縮にも寄与する。

- **Server ActionsのCache連携強化:** `use cache`ディレクティブとServer Actionsの組み合わせで、データ更新後の再検証が細粒度化。物件ステータス変更（draft→public）のような更新系操作でも、不要な全体再フェッチを避けられる。

- **Edge Runtimeの選択的活用:** 全ページをEdgeに寄せるのではなく、認証チェックや地域別リダイレクトなど「軽量・低レイテンシが必須な処理」に限定してEdge Runtimeを使う設計が主流に。DBアクセスを伴う処理はNode.js runtimeに残し、コールドスタートとレイテンシのバランスを取る。

### 2. React Server Components streaming 2026

- **段階的ハイドレーションの標準化:** Next.js 16ではPPR（Partial Prerendering）がstableとなり、静的シェルを即座に返しつつ動的部分をストリーミングで埋める構成が標準パターン化。sumitsugiの物件一覧・詳細ページでもLCPをこの方式で大幅短縮できる。

- **Suspenseバウンダリ設計の重要性増大:** RSCストリーミングの効果は「どこにSuspense境界を置くか」にほぼ依存する。物件検索フィルタや前の住人プロフィールなど、独立して取得できるデータ単位ごとに境界を細かく切ることで、ウォーターフォールを避けつつ体感速度を上げられる。

- **use cacheディレクティブによるキャッシュ制御の明示化:** App Routerのキャッシュ挙動がブラックボックス化しやすい問題に対し、`use cache`でコンポーネント/関数単位のキャッシュを明示指定できるようになった。物件データのような更新頻度が低いコンテンツに積極活用すべき。

- **Server Actionsとストリーミングの統合強化:** フォーム送信（引越し費用の見積もり等）でServer Actionsの結果を即座にストリームバックし、楽観的UI（`useOptimistic`）と組み合わせることで、multi-step flowの体感遅延を最小化できる。

- **エッジランタイムとの相性がボトルネックに:** RSCストリーミングはNode.jsランタイムのTTFBに強く依存するため、Vercel/CloudflareなどエッジでのRSCペイロード生成が引き続き課題。地方物件検索などレイテンシに敏感な機能はランタイム選定を慎重に検討すべき。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの台頭）:** Next.js/TypeScriptのフルスタック構成では、tRPCがコード生成なしでクライアント〜サーバー間の型安全性を保証できる点が支持を集めている。sumitsugiのようにフロントとバックエンドが同一TSコードベースの場合、公開APIが不要な内部エンドポイントはtRPC化することでスキーマ管理コストを削減できる。

- **ポイント2（GraphQLは大規模組織向けに収束）:** GraphQLは複数チーム・複数サービスを横断するFederation構成（Apollo Federation等）で依然強いが、単一プロダクト規模ではオーバーヘッド（N+1対策、キャッシュ設計の複雑さ）が見合わないケースが多い。MVPフェーズのsumitsugi規模では優先度は低い。

- **ポイント3（RESTはOpenAPI 3.1で巻き返し）:** 外部連携・パートナーAPI・決済/物件情報の第三者提供を見据えると、キャッシュ制御やHTTPセマンティクスが標準化されたRESTが依然実務的。OpenAPI 3.1 + `zod-to-openapi`のような型駆動生成で、REST側でも型安全性のギャップが縮まっている。

- **ポイント4（AIエージェント連携を見据えた設計）:** 2026年はLLMエージェントによるツール呼び出し（Function Calling）を前提にAPIを設計するケースが増加。物件検索・引き継ぎ手続きAPIをJSON Schema厳格化しておくと、将来的なAIエージェント連携（内見予約の自動化等）に流用しやすい。

- **ポイント5（結論・推奨）:** sumitsugiの現フェーズ（ベータローンチ準備）では、内部API=tRPC、外部公開が必要になった時点でREST(OpenAPI)を追加する「ハイブリッド」構成が最も投資対効果が高い。GraphQL導入は複数プロダクトへの拡大期まで見送るべき。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化が加速:** WinterCG(WinterTC)準拠のランタイム(Cloudflare Workers, Vercel Edge, Deno Deploy)が収斂し、Node.js APIとの互換性が大幅に向上。ロックインを避けつつエッジ配信できる設計が現実的な選択肢になっている。

- **コールドスタート問題はほぼ解消:** V8 isolateベースの実行環境が主流化し、起動レイテンシがミリ秒単位まで低減。sumitsugiのような物件検索・画像配信を伴うUIでは、SSR/ISRの一部をエッジ側に寄せることでTTFBを大きく改善できる。

- **エッジDBとの統合が鍵:** D1、Turso、PlanetScale等の分散SQLiteやHTTP経由DBがエッジファンクションとネイティブに連携し、リージョンをまたいだ読み取りレイテンシが実用レベルに。物件検索のような読み取り比率が高いワークロードに適している。

- **コスト構造の変化に注意:** リクエスト課金からCPU時間課金への移行が進み、画像処理や長時間処理をエッジに置くとコストが跳ねやすい。重い処理(PDF生成、画像最適化)はオリジンかバックグラウンドジョブに残す判断が引き続き有効。

- **可観測性の追いつきが課題:** 分散実行環境ゆえにトレーシング・ログ収集が複雑化しており、OpenTelemetry対応が標準要件になりつつある。導入時はエッジ特有のデバッグ体制(ログ集約・分散トレース)を先に整える必要がある。

### 5. authentication security best practices 2026

**ポイント1:** パスキー（FIDO2/WebAuthn）への完全移行が2026年の標準になりつつあり、パスワードレス認証によってフィッシング耐性を確保しつつユーザー離脱率も低減できる。

**ポイント2:** 多要素認証（MFA）はSMS-OTPからデバイスバウンドの生体認証・ハードウェアキーへ移行すべきで、SIMスワップ攻撃のリスクを根本的に排除できる。

**ポイント3:** セッション管理では短命トークン＋リフレッシュトークンローテーションを徹底し、トークン漏洩時の被害範囲を最小化することが重要（特に引越し費用決済など金銭が絡むフローでは必須）。

**ポイント4:** ゼロトラスト原則に基づき、認証後もデバイスフィンガープリンティングや異常検知（不審なIPアドレス・地理的異常など）を継続的に行うリスクベース認証（Adaptive Authentication）が主流化している。

**ポイント5:** 前の住人・次の住人間で個人情報や物件情報をやり取りするsumitsugiのようなプラットフォームでは、認可（RBAC/ABAC）の粒度設計がセキュリティの要となり、単なる認証強化だけでなく「誰が何にアクセスできるか」の最小権限原則の徹底が不可欠。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma ORMはPostgreSQL特化のクエリコンパイラ（Rust不要のTypeScriptネイティブエンジン）へ移行が進んでおり、Supabaseとの組み合わせでもコールドスタート時間とバンドルサイズが大幅に改善されている。マイグレーション時はPrisma 6系以降のドライバアダプタ方式を前提に設計するのが安全。

- **ポイント2:** SupabaseのRow Level Security（RLS）とPrismaのスキーマ管理は責務が分離しているため、認証・認可ロジックはRLSポリシー側に寄せ、Prismaはスキーマ定義とマイグレーションに専念させる構成が事故を防ぎやすい。RLSを無効化したままPrisma経由でアクセスする設計は将来の権限漏れリスクが高い。

- **ポイント3:** Supabaseのconnection pooling（PgBouncer/Supavisor）とPrismaのコネクション管理は相性問題が起きやすいため、サーバーレス環境（Vercel等）ではPrismaのDATA_PROXYまたはSupavisorのtransactionモードを明示的に指定し、コネクション枯渇を防ぐ必要がある。

- **ポイント4:** リアルタイム機能（Supabase Realtime）とPrisma管理下のテーブルを併用する場合、Prisma側のマイグレーションでレプリケーション設定（publication）が意図せず変更されるケースがあるため、`prisma migrate`実行後にRealtimeのpublicationステータスを確認するチェックをCIに組み込むのが実用的。

- **ポイント5:** sumitsugiのような個人情報（前の住人の生活情報等）を扱うプラットフォームでは、SupabaseのPoint-in-Time Recovery（PITR）とPrismaのソフトデリート設計を組み合わせ、法務確認フェーズで求められる「削除要求への対応」と「監査ログ保持」を両立させる設計が今後の要件になりやすい。

### 7. WebAssembly Rust performance 2026

- **コンパイル最適化の成熟:** Rust製WASMは`wasm-opt`やLLVMのSIMD対応が進み、ネイティブコード比で90%以上の性能を出せるケースが増えている。バイナリサイズ削減（`wee_alloc`廃止後は`wasm-pack`のデフォルト設定で十分）と実行速度の両立がしやすくなった。

- **Component Model / WASI Preview 2の普及:** モジュール間の型安全な連携が標準化され、Rustクレートを個別のWASMコンポーネントとして配布・合成する構成が実用段階に入った。マイクロサービス的にWASMモジュールを組み合わせる設計がパフォーマンスとメンテナンス性の両面で有利になっている。

- **マルチスレッド対応の実用化:** `SharedArrayBuffer`とWeb Workersを使ったWASMスレッディングがブラウザ主要4系統で安定し、Rustの`rayon`をWASMターゲットで動かす事例が増加。CPU負荷の高い処理（画像処理・検索インデックス構築等）をメインスレッドから完全に切り離せる。

- **サーバーサイドWASM（Wasmtime/Wasmer）でのコールドスタート優位性:** コンテナに比べ起動が1桁以上速く、エッジコンピューティング用途でRust+WASMの採用が加速。sumitsugiのような物件検索・マッチング処理をエッジで高速実行する選択肢として検討価値がある。

- **開発体験の向上:** `cargo component`やRust公式のwasm32-wasip2ターゲット安定化により、ビルドパイプラインの複雑さが軽減。CI/CDにWASMビルドを組み込むコストが下がり、パフォーマンスクリティカルな一部機能（画像最適化、PDF生成など）をRust/WASMに切り出す判断がしやすくなっている。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16では静的シェルと動的コンテンツを1レスポンスで組み合わせるPPRが安定版となり、`loading.tsx`によるSuspense境界設計がパフォーマンス最適化の中心的パターンになっている。物件一覧のような「静的な骨格＋動的な価格/在庫情報」という構成に相性が良い。

- **Server Actions中心のデータ変更フロー:** フォーム送信や引越し費用の計算・申込処理など、API Routeを介さずServer Actionsで直接DB操作するパターンが定着し、型安全性とコード量削減の両立が可能になった。ただしZodによる入力検証をServer Actions内でも徹底する必要がある。

- **`use cache`ディレクティブによる粒度別キャッシュ制御:** ルート単位のキャッシュではなく関数・コンポーネント単位でキャッシュ戦略を明示できるようになり、公開物件データと非公開draftデータで異なるキャッシュポリシーを同一ページ内で共存させやすくなった。

- **Server ComponentsとClient Componentsの境界最適化:** 「Client Componentを木の葉に押し込む」原則がより厳格に運用され、認証状態や前の住人プロフィールなど頻繁に変わるUIのみをClient化し、それ以外はServer Componentに留めることでバンドルサイズと初期表示速度を改善するのが標準パターン。

- **Route Groupsとparallel routesによるダッシュボード構築:** `@modal`のようなparallel routesを使い、物件詳細ページ上にモーダルで申込フローを重ねるUXパターンが一般化し、ページ遷移なしで複雑なマルチステップフォームを実現しやすくなっている。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約理解:** Vercel Edge FunctionsはNode.js APIの一部（fs, cluster等）が使えないため、実装前にRuntime="edge"対応ライブラリか確認し、DBアクセスはHTTP経由のドライバ（Neon, PlanetScale等）を使う必要がある。

- **Cold Start最小化:** Edge FunctionsはV8 isolateベースで起動が数ms〜数十msと軽量だが、バンドルサイズが肥大化すると初期化コストが増えるため、依存ライブラリは最小限に絞り、動的importで遅延読み込みするのが実用的。

- **地理的分散によるレイテンシ削減:** ユーザーに最も近いエッジで実行されるため、認証チェックやリダイレクト、A/Bテストの振り分けなど「軽量・低レイテンシが必須」な処理をEdge Middlewareに寄せ、重い処理はNode.js Serverless Functionsに残す使い分けが重要。

- **Streaming SSRとの相性:** App RouterのStreaming SSR / React Server ComponentsとEdge Runtimeを組み合わせることで、TTFB（Time to First Byte）を大幅に短縮できるが、ISR（Incremental Static Regeneration）とEdgeの組み合わせにはキャッシュ戦略の設計が別途必要。

- **コストとオブザーバビリティのトレードオフ:** Edge Functionsは実行時間課金モデルが異なるため、高頻度アクセスのAPIルートで採用するとコスト最適化になる一方、ログ・トレーシングツールがEdge Runtime非対応の場合があるため、監視体制を事前に検証すべき。

### 10. TypeScript type safety patterns 2026

- **型推論の限界を補う`satisfies`演算子の定着:** TypeScript 4.9以降で導入された`satisfies`が2026年には標準的な実践となり、型注釈による広範化を避けつつ厳密な型チェックを両立できる。`as const satisfies Config`のような組み合わせで、リテラル型保持と構造的検証を同時に実現するパターンが定番化している。

- **Zodなどのランタイムバリデーションとの型統合:** `.claude/rules/standards.md`にもある通り、システム境界（API入出力、フォーム）ではZodスキーマから型を`z.infer`で導出する手法が主流。コンパイル時の型安全性とランタイムの実データ検証を一致させることで、「型はあるのにデータが壊れている」問題を根本的に防げる。

- **Branded Types（ブランド型）によるプリミティブの誤用防止:** `type UserId = string & { __brand: 'UserId' }`のようなブランド型で、単なる`string`同士の意図しない取り違え（例: `propertyId`と`sellerId`の混同）をコンパイル時に検出するパターンが、特にID管理が複雑なマルチエンティティなドメイン（sumitsugiのような物件・セラー・引き継ぎフロー）で有効。

- **テンプレートリテラル型によるドメイン固有の型安全性:** ルーティングパスやi18nキー、CSSクラス名などを`type Route = \`/properties/${string}\``のように型レベルで表現し、文字列操作ミスをビルド時に検出する手法がNext.js App Routerのようなファイルベースルーティングと相性が良い。

- **Exhaustiveness Checkingの徹底:** union型（例: `status: 'draft' | 'public'`）を扱う`switch`文で`default`ケースに`never`型アサーション（`const _exhaustive: never = value`）を置き、新しいステータス値追加時にコンパイルエラーで検知漏れを防ぐパターンが、型の網羅性が事業ロジックに直結するプロジェクトで重視されている。
