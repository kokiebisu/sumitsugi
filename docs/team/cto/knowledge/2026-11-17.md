# CTO Knowledge - 2026-11-17

## Daily Update (2026-11-17)

### 1. Next.js performance optimization 2026

- **ポイント1: Partial Prerendering (PPR) の本格運用:** Next.js 15以降で導入されたPPRが2026年には主流となり、静的シェルと動的コンテンツを1つのレスポンスで配信することでTTFBとLCPを大幅改善できる。`loading.tsx`やSuspenseの粒度設計が重要になる。

- **ポイント2: React Server Components (RSC) のバンドル最適化:** クライアントバンドルサイズを抑えるため「Client Componentの境界を末端に寄せる」設計が標準化しており、`'use client'`を安易にトップレベルに付けないレビュー基準が必要。

- **ポイント3: キャッシュ戦略の明示化:** `fetch`のデフォルトキャッシュ挙動がバージョンごとに変化してきたため、`cache: 'force-cache'`や`revalidate`を明示的に指定する運用がベストプラクティス化。Turbopackのビルドキャッシュとも組み合わせてCI時間を短縮できる。

- **ポイント4: Edge Runtime適用範囲の拡大:** 認証チェックやA/BテストのミドルウェアロジックをEdgeで実行し、オリジンサーバーへのラウンドトリップを減らす構成が増えている。ただしDB接続が必要な処理はNode.js Runtimeに残すトレードオフ判断が必要。

- **ポイント5: Core Web Vitals計測の自動化:** Lighthouse CIやVercel Speed Insightsのようなツールをデプロイパイプラインに組み込み、リグレッションをPRレベルで検知する体制が2026年のデファクトスタンダード。sumitsugiでも`bun run build`後の計測ステップ追加を検討する価値がある。

### 2. React Server Components streaming 2026

- **ポイント1:** Partial Prerendering (PPR) が主流化し、静的シェルを即時配信しつつ、動的な部分だけをServer Componentsでストリーミングする設計がNext.js 16でも標準パターンになっている。初期表示速度とパーソナライズの両立が可能。
- **ポイント2:** `use cache` ディレクティブとキャッシュコンポーネントの粒度制御が成熟し、ページ単位ではなくコンポーネント単位でキャッシュ戦略を分離できるようになった。物件一覧のような頻繁に更新されるデータと、静的な物件説明文を同一ページ内で別々にキャッシュ・再検証できる。
- **ポイント3:** Suspenseバウンダリの設計がパフォーマンスのボトルネックになりやすく、ウォーターフォール（直列的なデータ取得）を避けるため、`Promise.all`相当の並列データフェッチとバウンダリの粒度分割が引き続き重要なベストプラクティス。
- **ポイント4:** エッジランタイムとストリーミングSSRの組み合わせで、地理的に分散したユーザーへの初期バイト到達時間（TTFB）が大幅改善。ただしDBアクセスを伴うServer Componentsはエッジから遠いリージョンのDBへのレイテンシがボトルネックになりやすく、データベースのリージョン配置とのセット設計が必要。
- **ポイント5:** Server Actionsとストリーミングの組み合わせでフォーム送信後の楽観的UI更新（`useOptimistic`）がより一般化し、問い合わせフォームや内見予約フローのようなマルチステップUXで、サーバー往復を感じさせないインタラクションが標準要件になりつつある。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCやGraphQLの型安全性メリットはNext.js 16のServer Actions普及で薄れつつあり、2026年はシンプルなREST+OpenAPI+Zodスキーマの組み合わせが「型安全な契約」を実現する主流パターンになっている。弊社のようなBun/TypeScriptスタックでは、tRPCの導入コストよりもZodバリデーション層をREST APIに薄く被せる方が開発速度とのバランスが良い。

- **ポイント2:** GraphQLは依然としてモバイルアプリや複雑なダッシュボード（複数エンティティの一括取得）で強みを持つが、N+1問題やキャッシュ戦略の複雑さから、物件検索・一覧表示のような単純なCRUD中心のsumitsugiのようなプロダクトにはオーバーエンジニアリングになりがち。

- **ポイント3:** 2026年の実務トレンドは「API層の統一」より「エンドツーエンドの型安全性」で、tRPC/Next.jsのServer Actions経由の直接呼び出しがBFF（Backend for Frontend）パターンを置き換えつつある。モノレポ構成（フロント・バック同一リポジトリ）であれば、REST/GraphQLのスキーマ同期コストそのものを排除できる。

- **ポイント4:** 認証・決済など外部法務確認が絡む領域（プライバシーポリシー、特商法対応中の現フェーズ）では、APIレイヤーに監査ログとレート制限を標準装備することが2026年のベストプラクティス。契約前の設計段階でZodによる入力検証とエラーレスポンスの型統一を組み込んでおくと、後からの法務対応修正コストが大幅に下がる。

- **ポイント5:** エッジランタイム（Vercel Edge, Cloudflare Workers）普及により、API設計時に「コールドスタート」「リージョン分散」を前提にしたステートレス設計が必須条件になっている。sumitsugiの物件データのような地域性の強いデータは、エッジキャッシュと組み合わせたREST設計の方がGraphQLより運用しやすい。

### 4. serverless edge computing 2026

- **ポイント1:** 2026年はCloudflare Workers・Vercel Edge・Fastly Compute@Edgeの性能差が縮まり、Wasm（WebAssembly）ランタイムの標準化が進んだことでコールドスタートが1桁ms台まで短縮されている。レイテンシ要件が厳しいAPI（例：物件検索のオートコンプリート）はエッジ関数への移行を検討する価値がある。

- **ポイント2:** エッジでのDB書き込み（Durable Objects、Turso、PlanetScale等の分散SQLite/MySQL）が実用段階に入り、読み取り専用キャッシュだけでなく状態を持つロジック（在庫ロック・予約フローなど）もエッジ側で完結できるようになった。sumitsugiの「引越し費用」計算や物件ステータス更新のような低レイテンシ処理に応用余地がある。

- **ポイント3:** Next.js 16のPartial Prerendering（PPR）とエッジランタイムの組み合わせがデフォルト構成になりつつあり、静的シェル＋動的データのストリーミングでTTFBを大幅改善できる。物件一覧ページのような「骨格は静的・在庫情報は動的」なUIに特に有効。

- **ポイント4:** マルチリージョンでのデータ主権（日本国内データ保存要件など）とエッジ配置の両立がコンプライアンス上の論点になっている。個人情報を扱うsumitsugiでは、エッジキャッシュに前の住人・次の住人の個人情報を乗せないよう設計段階での線引きが必要。

- **ポイント5:** Observability（分散トレーシング）のエッジ対応が進み、OpenTelemetry対応ランタイムが増えたことで、エッジ関数のデバッグ難易度が下がった。本格導入前に計測基盤を整えることが前提条件になる。

### 5. authentication security best practices 2026

- **パスキー/FIDO2が事実上の標準に:** パスワード+SMS認証はフィッシング耐性が低く、2026年時点ではWebAuthn/パスキーをデフォルトの一次認証手段とし、パスワードは後方互換のフォールバックに留めるのがベストプラクティス。弊社の`auth-context.tsx`でもパスキー対応を優先検討すべき段階にある。

- **トークンのライフサイクル管理の厳格化:** アクセストークンは短命（15分以下）に、リフレッシュトークンはローテーション必須＋再利用検知（reuse detection）を実装し、漏洩時の被害範囲を最小化する。JWTをlocalStorageに置くのは依然XSSリスクが高く、httpOnly+SameSite=StrictなCookieが推奨。

- **デバイス/セッションレベルのリスクベース認証:** IPレンジ・デバイスフィンガープリント・行動パターンの変化を見てステップアップ認証（追加のMFA要求）をトリガーする仕組みが標準化。物件オーナー・利用者双方の個人情報を扱う`sumitsugi`では、特に決済・契約関連の操作前にリスクベースの再認証を挟む設計が有効。

- **BFF（Backend For Frontend）パターンでのトークン隠蔽:** SPAやNext.jsのApp Routerでは、OAuthトークンをクライアントに直接渡さず、サーバーサイド（Route Handlers）でセッションCookieのみをフロントに渡すBFFパターンが主流になっている。これにより、トークン漏洩・リプレイ攻撃のリスクを構造的に排除できる。

- **監査ログとゼロトラストの前提:** 認証イベント（ログイン失敗・MFA変更・権限昇格）は改ざん不可能な形で記録し、「社内ネットワークだから安全」という前提を排除したゼロトラスト設計が必須。特商法・プライバシーポリシー対応を進めている現フェーズでは、法務要件（個人情報保護法）とも直結するため早期の設計組み込みが重要。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はRustバイナリ依存を段階的に廃止し、TypeScript純正のクエリエンジン（Prisma ORM Next-gen）に移行しており、Edge Runtime（Vercel Edge, Cloudflare Workers）との互換性が大幅に向上している。sumitsugiのようなNext.js App Router構成では、サーバーレス/Edge環境でのコールドスタート短縮に直結する。

- **ポイント2:** Supabaseは2026年時点でPostgres上のRLS（Row Level Security）とPrismaのスキーマ管理を併用する構成が主流になっており、認証ロジックをアプリ層だけでなくDB層でも強制できる。`seller`/`buyer`のようなロール分離が必要な物件データでは、RLSを効かせることで認可バグの影響範囲をDBレベルで最小化できる。

- **ポイント3:** SupabaseのBranching機能（開発用DBブランチ）とPrisma Migrateを組み合わせることで、PRごとに独立したDBスキーマ環境を自動生成できるようになっている。worktreeベースの並行開発フローと相性が良く、複数PRが同時進行する際のマイグレーション競合を防げる。

- **ポイント4:** pgvectorとSupabase Realtimeの統合が成熟し、物件検索のセマンティック検索（自然言語での「駅近・リノベ済み」のような条件検索）をPostgres単体で実装できるようになった。別途ベクトルDBを導入する必要がなく、インフラの複雑度を抑えられる。

- **ポイント5:** マイグレーション運用では「`status: 'draft' | 'public'`」のようなUnion型をDBのenumと同期させる際、Prisma Migrateのshadow database検証を必須化するのがベストプラクティスになっている。型の不整合が本番マイグレーションで発覚するリスクを事前に潰せる。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASM GC (Garbage Collection) 提案がブラウザ主要実装で安定し、RustでもGCを前提にしたホスト連携が増えつつあるが、Rustの強みは依然GC不要の線形メモリモデルによる低オーバーヘッド実行にある。
- **ポイント2:** `wasm-bindgen`/`wit-bindgen`によるWASI Preview 2連携が成熟し、Component Model採用でRust製WASMモジュールをポリグロットに組み合わせやすくなっている。本サービスのような画像処理・PDF生成を他言語サービスと疎結合に連携させる選択肢が広がる。
- **ポイント3:** SIMDとマルチスレッド（Shared Memory + Web Workers）がデフォルト有効化されつつあり、クライアント側での画像処理・レイアウト計算をRust/WASMにオフロードすることで、Next.jsのサーバー負荷を抑えつつUX向上が狙える。
- **ポイント4:** バンドルサイズ最適化（`wasm-opt`、`twiggy`での解析、LTO+codegen-units=1）がCore Web Vitalsに直結するため、Rust/WASM導入時はビルドパイプラインへの最適化ステップ組み込みが必須。
- **ポイント5:** Edgeランタイム（Cloudflare Workers、Vercel Edge Functions）でのWASM実行が一般化し、Rustで書いた軽量ロジック（料金計算、バリデーション等）をエッジに配置することでレイテンシ削減とサーバーコスト圧縮を同時に実現できる。

### 8. Next.js App Router patterns 2026

- **ポイント1:** Partial Prerendering (PPR) が安定版に近づき、静的シェルを即時表示しつつ動的部分をストリーミングする構成が標準化。本プロジェクトのproperties一覧ページなど、静的なレイアウト＋動的な在庫データの組み合わせに相性が良い。
- **ポイント2:** Server ActionsがAPI Routesの代替としてさらに主流化し、フォーム送信や引越し費用計算のようなミューテーション処理をクライアント側のfetchロジックなしで書けるようになっている。型安全性もEnd-to-Endで担保しやすい。
- **ポイント3:** `use cache` ディレクティブ（Next.js 15以降で導入、16で成熟）によりデータキャッシュの粒度をコンポーネント/関数単位で制御可能になり、物件データのような更新頻度が異なるデータの扱いが明確になった。
- **ポイント4:** Route Groupsとparallel routes/intercepting routesを使ったモーダル実装（例：物件詳細のクイックビュー）が定着し、URL共有可能なモーダルUXがApp Router標準パターンとして確立された。
- **ポイント5:** Turbopackがビルド・devサーバーのデフォルトとなり、ビルド時間の短縮が顕著。大規模化する前にCIのビルドステップにTurbopackを前提とした設定を入れておくと移行コストが下がる。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化:** Edge RuntimeはNode.js Runtimeと異なりV8 isolateベースで起動するため、2026年時点でもコールドスタートは数ms〜数十msに抑えられる。頻繁にデプロイが変わる関数はEdgeに寄せ、重い依存関係を持つ処理はNode.js Functionsに分離するのが実用的。

- **Fluid Compute併用:** VercelのFluid Compute（複数リクエストで実行コンテキストを再利用する仕組み）とEdge Functionsを組み合わせることで、I/O待ち時間中の課金・リソース消費を抑えられる。レイテンシが低いAPIルートほど恩恵が大きい。

- **リージョン配置とデータ局所性:** Edge Functionsはグローバル分散されるが、DB（Supabase/Postgres等）のリージョンと離れているとレイテンシが逆に悪化するケースがある。読み取り中心の処理はEdge、DB書き込みを伴う処理はDBに近いリージョンのFunctionsに置く「ハイブリッド配置」が定石。

- **バンドルサイズ制約への対応:** Edge RuntimeはNode.js APIの一部（fs, net等)が使えずバンドルサイズ上限もあるため、認証チェックやリダイレクト、A/Bテストの振り分けなど「軽量・高頻度」なロジックに限定して使うのが2026年のベストプラクティス。重いロジックはEdgeに移植しようとせず最初から対象外にする判断が重要。

- **Observability統合:** Vercel の OpenTelemetry対応が強化され、Edge Functions単位でのトレース・レイテンシ分析が標準化されてきている。本プロジェクト規模ではまだ導入優先度は低いが、ベータローンチ後にAPI Routeが増えてきたら計測を入れる価値がある。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScriptの型レベルプログラミング（Template Literal Types、Conditional Types）が標準化され、Zodなどのランタイムバリデーションとスキーマから型を自動生成するパターンが主流になっている。本プロジェクトでもZodスキーマを単一のソースとして型とバリデーションを一致させる運用を継続すべき。

- **ポイント2:** `satisfies`演算子の活用が定着し、型の広がり（widening）を防ぎつつリテラル型の推論を保持できるようになった。設定オブジェクトや定数定義（例: `site-config.ts`）で型安全性を高めつつ可読性を損なわない書き方として有効。

- **ポイント3:** Branded Types（nominal typing）パターンが`'draft' | 'public'`のような文字列リテラル型だけでなく、ID型（`UserId`, `PropertyId`など）の取り違えを防ぐ目的で広く採用されている。本プロジェクトのステータス型変更時に全使用箇所をgrepする運用をさらに型レベルで強制できる。

- **ポイント4:** tRPCやHonoのようなエンドツーエンド型推論フレームワークがApp Routerとの統合を前提に進化し、APIレスポンス型を手動定義せずクライアント・サーバー間で自動共有するのが2026年のベストプラクティス。手動の型複製によるドリフトを避けられる。

- **ポイント5:** TypeScript 5.x以降のコンパイラパフォーマンス改善（インクリメンタルビルド、`isolatedDeclarations`）により、大規模コードベースでも型チェックをCIのブロッキングステップとして常時実行するのが現実的になった。`bun run build`をCIに必須化する方針は2026年の標準的ベストプラクティスと合致している。
