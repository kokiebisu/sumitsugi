# CTO Knowledge - 2026-03-31

## Daily Update (2026-03-31)

### 1. Next.js performance optimization 2026

- **PPR（Partial Prerendering）の本格活用:** Next.js 15以降で安定化したPPRにより、静的シェルと動的コンテンツを同一ルートで混在させることが可能になり、TTFBを大幅に削減できる。Suspense境界の設計がパフォーマンス戦略の中心となっている。

- **React Server Componentsによるバンドルサイズ削減:** RSCを徹底活用することでクライアントJSを最小化し、特に重いライブラリ（date-fns、markdownパーサー等）をサーバー側に閉じ込めることが2026年のベストプラクティスとして定着。

- **`use cache` APIによる細粒度キャッシュ制御:** Next.js 15で導入された`use cache`ディレクティブにより、関数・コンポーネント単位でキャッシュ戦略を宣言的に制御できる。従来の`fetch`オプションによるキャッシュより柔軟で、API境界に依存しない設計が可能。

- **Turbopackの実用化と開発体験の向上:** Turbopackがデフォルトdev serverとして安定稼働し、大規模プロジェクトでのHMRが実質的に即時応答レベルに。ビルド時間の短縮が開発サイクル全体のスループットに直結する。

- **Edge Runtimeの選択的採用:** ミドルウェアやA/Bテストロジック等のレイテンシ敏感な処理にEdge Runtimeを限定使用し、Node.js Runtimeとの使い分けを明確化することが運用コスト・パフォーマンスのバランス最適解として認識されている。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化:** 2026年時点では、RSCのストリーミングはSuspense境界の設計が性能の鍵となっており、コンポーネントツリーの上位に単一の境界を置くのではなく、データ依存ごとに細かく分割することでTTFB（初回バイト到達時間）を大幅に改善できる。

- **PPR（Partial Prerendering）との統合:** Next.js 15以降で安定化したPPRにより、静的シェルを即座に配信しつつ動的なRSCストリームを差し込むハイブリッドアーキテクチャが実用段階に入り、CDNキャッシュとストリーミングの両立が可能になった。

- **Server Actionsとの非同期連携:** フォーム送信・ミューテーション後のUI更新において、Server Actionsがストリーミングレスポンスを返すパターンが普及し、クライアント側のstate管理を最小化しながら楽観的UIを実現できる。

- **Reactの`use()`APIによるウォーターフォール排除:** `use(promise)`を活用することで、親コンポーネントで並列フェッチを開始し子に渡すパターンが標準化され、従来のawait直列チェーンによるレイテンシ増加を防げる。

- **エラー境界とローディングUIの設計原則:** `error.tsx` / `loading.tsx` のネスト設計が本番品質の指標となっており、ストリーミング途中のエラーが上位境界に伝播しないよう、ルートセグメントごとに適切な隔離設計を施すことが運用安定性の前提条件になっている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性の標準化:** Next.js + tRPC の組み合わせが中小規模プロダクトのデファクトになりつつあり、スキーマ定義なしでフロント〜バック間の型共有が実現できるため、型エラーによるバグが大幅に減少している。

- **REST vs GraphQLの「第三の道」としてのRSC + Server Actions:** React Server Components の普及により、従来APIレイヤーで解決していた過剰フェッチ問題がUI層で解消されるケースが増え、GraphQLの採用動機が一部薄れてきている。

- **GraphQLはBFF（Backend for Frontend）パターンでまだ強い:** 複数マイクロサービスを束ねるBFFや、モバイル・Web・サードパーティが同一エンドポイントを叩く構成では、GraphQLのスキーマ駆動開発と柔軟なクエリが依然として最適解。

- **OpenAPI 3.1 + Zodによるスキーマファースト設計の復権:** `zod-openapi` や `@hono/zod-openapi` 等により、バリデーション・型生成・ドキュメントを単一ソースから自動生成できるようになり、REST API設計の開発体験が大幅に改善されている。

- **エッジランタイム対応がAPI設計の制約になる:** Cloudflare Workers / Vercel Edge Functions での動作を前提とすると、Node.js専用ライブラリが使えないため、`Hono` のようなWeb標準準拠の薄いフレームワーク選定がアーキテクチャ判断に直結する。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジのデファクトランタイムに:** V8 Isolatesに並びWasmがCloudflare Workers・Fastly Compute等で本格採用され、言語非依存でコールドスタートほぼゼロを実現。ポリグロット開発がエッジでも現実的になった。

- **エッジDBの成熟でステートレス制約が崩れる:** Cloudflare D1・Turso（libSQL）・Neon（サーバーレスPostgres）がエッジリージョン近傍にレプリカを持ち、「エッジは読み取り専用」という前提が過去のものになりつつある。

- **AI推論のエッジオフロードが加速:** LLMの軽量化（Llama 3.2 1B/3B等）とNPU搭載デバイスの普及により、プライバシーが求められるユースケースでクラウド往復を排除できるアーキテクチャが実用段階に入った。

- **オブザーバビリティのギャップが最大の運用課題:** エッジノードが数百拠点に分散するため、従来の集中型APMでは遅延・エラーの根本原因特定が困難。OpenTelemetry + エッジネイティブなトレーシング基盤の整備が急務。

- **コスト構造の再設計が必要:** リクエスト単価は安価でもエッジDBのレプリカ数・Wasm実行時間・帯域がコスト変数として増加。従来のサーバーコスト計算モデルをそのまま適用すると予算超過しやすく、フィーチャーフラグによる動的ルーティング設計が重要。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）への移行加速:** パスワードレス認証がデファクトスタンダードになりつつあり、フィッシング耐性のあるパスキーをプライマリ認証として採用することが2026年の必須要件になっている。

- **セッション管理の短命化とトークンローテーション:** JWTの有効期限を15分以下に設定し、リフレッシュトークンのローテーションを強制することで、トークン漏洩時のブラストラジウスを最小化する。

- **デバイスバインディングとコンテキスト認証:** 単なるMFAを超え、デバイス証明書・位置情報・行動パターンを組み合わせたリスクベース認証が主流に。異常なコンテキストでは追加検証を要求する。

- **サプライチェーン攻撃対策としてのOAuth/OIDCライブラリ監査:** 認証ライブラリの脆弱性（例：pkce_state固定、openredirect）が急増しており、依存パッケージを定期的にauditし、`npm audit` / `bun audit` をCIに組み込む。

- **ゼロトラスト前提のサービス間認証:** マイクロサービス間でも相互TLS（mTLS）またはSPIFFE/SPIREによるワークロードIDを採用し、「内部ネットワーク＝信頼」という前提を完全に排除する。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応:** Prisma 6がEdge RuntimeとD1/Tursoなど軽量DBへの対応を強化。Supabaseと組み合わせる場合も、`@prisma/adapter-pg`によるコネクションプーリングが必須で、サーバーレス環境でのコールド起動コストを削減できる。

- **Supabase RLSとPrismaの責務分離:** Row Level Security（RLS）はSupabase側で定義し、Prismaはスキーマ管理・型生成に専念する設計が2026年の主流。アプリ層でのアクセス制御とDB層のRLSを二重管理するアンチパターンは避ける。

- **pgvectorによるRAG統合の標準化:** Supabase上の`pgvector`拡張とPrismaスキーマの`Unsupported("vector")`型を組み合わせたベクトル検索が実用段階に。AIアプリのDB設計では最初からベクトルカラムの追加を想定したマイグレーション戦略が必要。

- **Prisma Pulse（リアルタイムCDC）の活用:** Prisma PulseがSupabaseのPostgres変更データキャプチャ（CDC）と統合可能になり、WebSocketポーリング不要のリアルタイム更新が実現。ただしコスト増になるため、Supabase Realtimeとのトレードオフを設計段階で評価すること。

- **マイグレーション戦略の再考:** Prisma Migrateのシャドウデータベース要件がSupabaseのブランチング機能（Preview Branches）と相性が良く、PR単位でのスキーマ検証が自動化できる。本番DBへの直接マイグレーションは廃止し、ブランチ→マージフローを標準にすべき。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の本格普及:** 2026年にはWASI Preview 2が安定し、RustのWasm ComponentがホストAPIと型安全にインターフェースできるようになった。`cargo component`ツールチェーンが成熟し、サーバーサイドWasmの実用性が大幅に向上。

- **Wasmtime / WasmEdgeのAOTコンパイルが主流に:** JITではなくAhead-of-Timeコンパイルが標準となり、コールドスタートがほぼゼロに。Rustで書いたWasmモジュールはネイティブバイナリの85〜95%のスループットを達成するケースが増えている。

- **SIMD・スレッド拡張の安定化:** Fixed-width SIMDとWasm Threadsが全主要ランタイムで安定稼働。RustのSIMDイントリンシックがWasm向けにも透過的に機能し、画像処理・暗号・ML推論のユースケースで顕著な性能向上。

- **エッジランタイム（Cloudflare Workers / Fastly）でのRust Wasmが事実上の標準に:** 低レイテンシが求められるエッジ環境でRust+Wasmの組み合わせが支配的。メモリ安全性とサンドボックス分離を両立できる唯一の現実解として採用が加速。

- **`wasm-opt`＋PGO（Profile-Guided Optimization）の組み合わせが必須に:** Binaryenの`wasm-opt`とRustのPGOを組み合わせることでコードサイズを30〜40%削減しつつ実行速度も向上。本番デプロイのCI/CDパイプラインに組み込むことが今やベストプラクティス。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点では、データフェッチはほぼすべてServer Componentsで行い、`'use client'`はインタラクティブな末端コンポーネントのみに限定するパターンが定着。バンドルサイズの削減効果が顕著。

- **Partial Prerendering (PPR) の本番投入:** 静的シェル＋動的ストリーミングを組み合わせるPPRが安定版となり、`export const experimental_ppr = true`不要でデフォルト利用可能に。TTFBとLCPの両立が実現しやすくなった。

- **`use cache` ディレクティブによる細粒度キャッシュ:** `unstable_cache`から`use cache`への移行が進み、関数・コンポーネント単位でキャッシュ戦略を宣言的に記述できる。`cacheTag`/`cacheLife`で無効化も明示的に管理。

- **Server Actions の設計原則が確立:** フォーム送信・楽観的更新は`useActionState`＋Server Actionsの組み合わせが標準。APIルートを新規作成する理由がほぼなくなり、`/api`ディレクトリの肥大化を防げる。

- **`after()` APIによる非同期サイドエフェクト分離:** レスポンス送信後にログ記録・分析イベント送信を行う`after()`が安定化。レイテンシに影響しない処理をリクエストパスから切り離す設計が推奨パターンに。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択的活用:** 全APIルートをEdgeに移行するのは逆効果。認証チェック・地理判定・A/Bテストなど低レイテンシが直接ユーザー体験に影響する処理のみEdgeに限定し、DBアクセスを伴うロジックはNode.jsランタイムに留める。

- **Cold Start最小化のためのコード分割:** Edge FunctionsはV8 Isolateベースのため起動は速いが、バンドルサイズが大きくなると初回実行が劣化する。`next/dynamic`と動的import を使い、各Edge関数のバンドルを50KB以下に抑えることが2026年のベストプラクティス。

- **Fluid ComputeによるEdge/Serverless境界の消滅:** VercelのFluid Compute（2025年GA）により、同一リクエスト内でEdgeとServerless処理を連鎖させるコストが激減。「Edgeで認証→ServerlessでDB処理」のパターンが低コストで実現可能になった。

- **KV・R2等のEdge-native storageとの組み合わせ:** Vercel KVやCloudflare R2をEdge Functionsと同一リージョンに配置することで、実質的なレイテンシをサーバーレスDB比で60-80%削減できる。セッション管理・レート制限・フィーチャーフラグはKVで管理するのが定石。

- **Observabilityの整備が最重要課題:** Edge環境はログ・トレースが断片化しやすく、パフォーマンス劣化の原因特定が困難。OpenTelemetry + Vercel Speed Insightsを組み合わせ、`waitUntil()`で非同期にメトリクスを送信する設計を最初から組み込むこと。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `string` や `number` をそのまま使わず、`type UserId = string & { readonly __brand: 'UserId' }` のような Branded Types が実務レベルで定着。IDの取り違えバグをコンパイル時に完全排除できる。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` が2026年時点でほぼ必須パターンに。型を広げずに推論を保持できるため、設定オブジェクトやルーティング定義の型安全性が大幅に向上した。

- **Template Literal Types による API 型生成:** `${Method}${Capitalize<Path>}` のような Template Literal Types でエンドポイント名を型レベルで表現し、手書きの型定義を排除するパターンが主流。tRPC や Hono の設計思想がその証左。

- **`noUncheckedIndexedAccess` の標準有効化:** `tsconfig.json` でこのフラグを有効にすることで配列・オブジェクトアクセスが `T | undefined` になり、ランタイムエラーの温床だったインデックスアクセスを静的に防げる。新規プロジェクトでは有効化がデフォルト推奨。

- **型レベルテスト（`tsd` / `expect-type`）の導入:** 型の正しさをユニットテストと同様に検証する `expect-type` ライブラリが普及。型定義のリグレッションをCIで検出できるため、ライブラリ開発だけでなくアプリ開発でも採用が広がっている。
