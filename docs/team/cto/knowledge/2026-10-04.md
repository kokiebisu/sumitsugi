# CTO Knowledge - 2026-10-04

## Daily Update (2026-10-04)

### 1. Next.js performance optimization 2026

- **ポイント1:** Next.js 16ではPartial Prerendering (PPR)が安定版となり、静的シェルと動的コンテンツを1つのルートで共存させられるため、TTFBを維持しつつパーソナライズされたUIを配信できる。ダッシュボードや物件詳細ページのような「一部は共通・一部は動的」な画面で特に効果が大きい。
- **ポイント2:** React Compilerの普及によりメモ化（`useMemo`/`useCallback`）の手動管理が不要になりつつあり、レンダリング最適化の工数を削減できる一方、ビルド時の変換結果を定期的に検証しないと意図しない再レンダリングを見逃すリスクがある。
- **ポイント3:** Turbopackが`bun run build`のデフォルトビルドチェーンとして本番運用レベルに達しており、大規模リポジトリでのビルド時間短縮に直結する。CIのビルド時間がボトルネックになっている場合はここが最初に効く。
- **ポイント4:** `next/image`と`next/font`に加え、Core Web Vitalsの新指標（INP重視）への対応としてサーバーアクション経由のフォーム送信やストリーミングSSRを使い、クライアントJSバンドルを削減するパターンが主流になっている。物件検索・問い合わせフォームなどインタラクション起点の機能で優先度が高い。
- **ポイント5:** エッジランタイム（Vercel Edge / Cloudflare Workers互換）でのキャッシュ戦略とISRの併用が一般化し、地理的に分散したユーザーへの配信遅延を抑えられる。ただし認証状態を含むページではキャッシュキー設計を誤るとユーザー間でのデータ混在リスクがあるため、セキュリティレビューと併せて設計すべき。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Prerendering (PPR) の標準化** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分をストリーミングで差し込む構成が標準パターンに。本プロジェクトの`properties/`一覧ページのような「レイアウトは静的・物件データは動的」な構成に直接適用できる。

- **ポイント2: Suspenseバウンダリの粒度設計がパフォーマンスの肝** 細かすぎるSuspense分割はウォーターフォール（直列リクエスト）を生み、粗すぎると初期表示が遅れる。`listing/`詳細ページなど画像・料金・レビューが混在するUIでは、データ依存関係に沿ったバウンダリ設計がLCP改善の最重要ポイント。

- **ポイント3: `use cache` ディレクティブとCache Componentsの実用化** Next.js 16で本格導入されたキャッシュディレクティブにより、RSCレベルでの部分キャッシュ制御が容易に。`data.ts`経由のDB/API呼び出しをコンポーネント単位でキャッシュ戦略を変えられるため、物件データのような更新頻度が低いデータに有効。

- **ポイント4: エラーバウンダリとストリーミングの組み合わせに注意** ストリーミング中に発生したサーバーエラーはクライアントで部分的にしか回復できないケースがあり、`error.tsx`の設計を「ストリーム単位」で見直す必要がある。本番導入前に異常系のE2Eテストを強化すべき領域。

- **ポイント5: Bunランタイムとの相性検証が必須** RSCストリーミングはNode.js前提の実装が多く、Bun 1.xでの`ReadableStream`実装差異によるストリーミング中断リスクが報告されている。本番ローンチ前にBun環境でのストリーミング挙動を実機検証しておくべき。

### 3. API design REST GraphQL tRPC 2026

- **スキーマファーストの収束:** GraphQLとtRPCの型安全性がREST開発でも標準化しつつあり、OpenAPI+Zodの組み合わせでランタイム検証とコード生成を両立させるのが2026年の主流パターンです。sumitsugiのようなNext.js/TypeScriptスタックでは、tRPCの型推論によりフロントエンド・バックエンド間のAPI契約ミスをビルド時に検出できる利点が大きいです。

- **BFF（Backend for Frontend）パターンの定着:** モバイル・Web・パートナー向けなど複数クライアントが同じデータを異なる形で必要とする場合、GraphQLまたは専用BFFレイヤーでオーバーフェッチ・アンダーフェッチ問題を解決する設計が標準になっています。物件検索やフィルタリングのような多様なクエリパターンが想定される機能では特に有効です。

- **tRPCはモノレポ内部API、RESTは外部公開APIという使い分け:** 外部向けAPI（パートナー連携、Webhook等）は依然としてREST/OpenAPIが標準で、ツール互換性とキャッシュ戦略（CDN、HTTPキャッシュ）の観点で優位性があります。一方、フロントエンドとバックエンドが同一リポジトリ内にある場合はtRPCの開発体験（型安全・ボイラープレート削減）が勝ります。

- **エッジランタイムとストリーミングレスポンス:** Next.js App RouterのServer Actions/Route HandlersをVercel Edge等で実行し、Server-Sent EventsやストリーミングJSONで段階的レンダリングを行う設計が増えています。チャット的なUXや長時間処理（PDF生成、画像処理等）を伴う機能では、同期REST呼び出しより応答性が大幅に改善されます。

- **認可ロジックのAPI層への集約:** Zodスキーマによる入力検証に加え、行レベル認可（RLS的な発想）をAPI層で一元管理する設計が重視されています。`'draft'`/`'public'`のようなステータス管理を持つsumitsugiでは、APIエンドポイントごとに閲覧権限チェックを散在させず、共通ミドルウェアで一貫して適用することがセキュリティ・保守性の両面で重要です。

### 4. serverless edge computing 2026

- **ポイント1:** エッジでのAI推論が標準化されつつあり、Cloudflare Workers AIやVercel Edge Functionsなどで軽量LLM・埋め込みモデルをCDNエッジ上で直接実行できるようになっている。レイテンシ要件の厳しい検索・レコメンド機能はエッジ推論への移行を検討する価値がある。
- **ポイント2:** WebAssembly (Wasm) がサーバーレスエッジの実行基盤として本格的に普及し、コールドスタートがミリ秒単位まで短縮されている。Node.js依存の重いランタイムよりWasm対応フレームワークを選ぶことで、グローバル配信時のレスポンス改善が期待できる。
- **ポイント3:** エッジでのデータレイヤー（Durable Objects、Turso、PlanetScale等の分散SQLite/MySQL）が成熟し、エッジ関数からの低レイテンシなステートフル処理が実用段階に入っている。本サービスのような地域性の強い物件情報は、エッジキャッシュ+エッジDBの組み合わせで表示速度を大きく改善できる可能性がある。
- **ポイント4:** マルチクラウド/マルチエッジベンダーロックインを避けるため、OpenNext・Hono等のランタイム抽象化レイヤーが普及し、Next.jsアプリをVercel以外のエッジ環境（Cloudflare, Deno Deploy）にも展開しやすくなっている。将来的なコスト最適化の選択肢を残す意味で注目すべき潮流。
- **ポイント5:** コスト面では「実行時間課金」から「リクエスト数+CPU時間」への移行が進み、低頻度アクセスのロングテールページ（物件詳細ページ等）をエッジ関数化することでサーバー常時起動コストを削減できるケースが増えている。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証（WebAuthn/Passkeys）が業界標準化し、フィッシング耐性のある認証がユーザー体験とセキュリティを両立する基盤になっている。実装コストも下がっており、新規プロダクトはパスワード認証をデフォルトにしない設計が主流。

- **ゼロトラスト前提のセッション管理:** ログイン時の一度きりの検証ではなく、デバイス・IP・行動パターンを継続的に評価するリスクベース認証（継続的認証）が標準に。セッションハイジャックやトークン盗難への対策として、短命トークン＋リフレッシュの厳格な運用が必須。

- **AIを悪用した攻撃への対応:** ディープフェイク音声/映像によるソーシャルエンジニアリングや、LLMを使った高度なフィッシングが増加しており、本人確認フローに生体認証やデバイスバインディングを組み合わせる多層防御が重要。

- **サプライチェーン経由の認証基盤侵害リスク:** 認証ライブラリ・OAuthプロバイダ・SDKの脆弱性が直接ユーザーアカウントの侵害につながる事例が増加。依存関係の定期監査とSBOM管理、認証関連パッケージの更新頻度を上げる運用が求められる。

- **プライバシー規制と認証ログの両立:** 不正検知のための行動ログ収集と、個人情報保護規制（改正個情法・GDPR等）の要求が衝突しやすく、最小限データ収集＋暗号化保存＋保持期間の明確化を設計段階から組み込む必要がある。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma ORMはPostgreSQL向けに「TypedSQL」やRustフリーのクエリエンジン（Prisma 6以降）への移行を進めており、コールドスタート時間とバンドルサイズが大幅に改善されたため、Vercel/Edge環境でのサーバーレスDB接続がより実用的になっている。

- **ポイント2:** Supabaseはconnection pooling（PgBouncer/Supavisor）をデフォルト化し、サーバーレス関数からの大量同時接続によるDB枯渇問題への対策が標準装備になっている。本プロジェクトのような小〜中規模SaaSでは、Prisma Accelerate等の外部プーラーを別途導入せずに済むケースが増えている。

- **ポイント3:** Row Level Security (RLS) をアプリケーション層の認可ロジックと併用する「DB側で最終防衛線を張る」設計が主流化しており、Next.js App Router + Server Actionsの構成ではAPI層のバグがあってもRLSがデータ漏洩を防ぐ二重防御として評価されている。前の住人/次の住人のような所有者ベースのアクセス制御には特に有効。

- **ポイント4:** SupabaseのBranching機能（開発用DBブランチ）がGit worktreeベースの開発フローと相性が良く、本プロジェクトのworktree運用（`bun run worktree:create`）と組み合わせることで、PRごとに独立したDBスキーマ・シードデータでテストできる環境構築が容易になっている。

- **ポイント5:** PrismaのmigrationとSupabaseのマネージドPostgresは、スキーマのunion型（例: `status: 'draft' | 'public'`）変更時の整合性チェックが弱点であり、CIに`prisma migrate diff`や型チェックを組み込んで本番適用前に破壊的変更を検知する運用が2026年のベストプラクティスとして定着している。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC（WebAssembly Garbage Collection）の標準化が進み、Rustの`wasm-bindgen`を介さない軽量な相互運用が可能になってきている。ただしRust自体はGC不要な言語設計のため恩恵は間接的で、主にJS/他言語との共存シナリオでの恩恵が大きい。
- **ポイント2:** `wasm32-wasip2`とComponent Model対応により、Rustで書いたモジュールをWasmtime/WasmEdge上でネイティブ同等の起動速度（コールドスタート数ms）で動かせるようになり、サーバーレスやエッジコンピューティングでの採用が加速している。
- **ポイント3:** SIMD128命令の安定化とマルチスレッド（Wasm Threads + SharedArrayBuffer）のブラウザ実装が成熟し、Rust側は`std::simd`やrayonのwasm対応を通じて画像処理・ML推論などCPU負荷の高い処理をブラウザ内で実用速度まで引き上げている。
- **ポイント4:** バイナリサイズ最適化（`wasm-opt`、`twiggy`、LTO+`panic=abort`設定）がビルドパイプラインの標準プラクティスとして定着し、本番環境では数百KB〜1MB程度のバンドルサイズを目標値とするチームが増えている。
- **ポイント5:** sumitsugiのような物件検索・フィルタリングを含むWebアプリでは、重い検索アルゴリズムやPDF生成処理（物件概要書など）をRust+Wasmにオフロードする設計が、Node.js単体実装よりCPUバウンド処理で大幅な高速化を見込める選択肢として検討価値がある。

### 8. Next.js App Router patterns 2026

- **Server Components中心の設計が標準化:** App RouterではServer Componentsがデフォルトとなり、データフェッチをコンポーネント内で直接行う設計が主流に。クライアントバンドルサイズの削減とパフォーマンス向上を両立できるため、`'use client'`は本当にインタラクティブなUIにのみ限定すべき。

- **Partial Prerendering (PPR) の実用段階入り:** 静的シェルを即座に返しつつ動的部分をストリーミングする手法が安定化し、ECサイトや物件一覧ページのような「一部は静的・一部は動的」なページで有効。sumitsugiの物件検索・詳細ページにも適用の余地がある。

- **Server Actionsによるフォーム処理の簡素化:** `use server`を使ったServer ActionsがAPI Routeに代わる標準パターンとして定着。契約フォームや問い合わせフォームなど、フォーム周りの実装・バリデーション（Zod併用）が簡潔になり、クライアント/サーバー間の型安全性も向上。

- **キャッシュ戦略の明示化が必須に:** `fetch`のキャッシュ挙動がより明示的な指定（`cache`, `revalidate`, `tags`）を要求する方向に進化しており、意図しないキャッシュによるバグを防ぐには`revalidateTag`を使った細粒度の再検証設計が重要。

- **Edge RuntimeとNode Runtimeの使い分けが成熟:** 認証チェックやリダイレクトなど軽量な処理はEdge Middlewareで、重いDB処理はNode Runtimeでという役割分担が明確になってきており、レイテンシとコストの最適化がしやすくなっている。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Functionsはコールドスタート短縮が進み、V8 isolateベースの実行モデルによりミリ秒単位の起動が標準化。認証チェックやA/Bテストのリダイレクトなど軽量処理をEdgeに寄せ、オリジンへのレイテンシを削減するのが定石。
- **ポイント2:** Streaming SSR（Next.js App Routerのstreaming + Suspense）とEdge Runtimeの組み合わせが成熟し、TTFBを大幅短縮できる一方、Node.js APIが使えない制約（fsアクセス不可、一部npmパッケージ非対応）があるため、重い処理はNode runtimeに残す判断が重要。
- **ポイント3:** リージョン最適化（`regions`設定）とデータ近接性が鍵。DBやKVストアをEdgeに近いリージョンに配置しないと、Edge化してもDB往復がボトルネックになるケースが多い。
- **ポイント4:** 実行時間・メモリ課金モデルの違いを意識したコスト最適化が重要— 不要なEdge化はコスト増になりうるため、「本当にレイテンシが重要なパス」だけをEdgeに限定するのがベストプラクティス。
- **ポイント5:** キャッシュ戦略（ISR + Edge Cache + `stale-while-revalidate`）を組み合わせることで、動的処理をEdgeで行いつつ静的コンテンツ並みの応答速度を実現できる。弊社の物件検索・一覧表示のような読み取り中心機能に特に有効。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScriptのnoUncheckedIndexedAccessやexactOptionalPropertyTypesなど厳格フラグの標準採用が進み、配列アクセスやオプショナルプロパティの暗黙的な`undefined`混入をコンパイル時に防ぐのが2026年のデフォルトになっている。
- **ポイント2:** Zodなどのスキーマライブラリによる「ランタイム検証と型推論の統合」がAPI境界（フォーム入力、外部API、環境変数）の標準パターンとして定着し、型だけでは防げない実行時データ不整合をカバーする。
- **ポイント3:** ブランド型（Branded/Nominal Types）を使った「同じprimitive型だが意味が異なる値」の混同防止（例: `UserId`と`PropertyId`を別の文字列型として区別）が、大規模コードベースでのバグ予防に効果的。
- **ポイント4:** テンプレートリテラル型とconst型パラメータを活用したAPIルートやi18nキーの型安全な自動補完が普及し、文字列ベースの設定ミスをコンパイル時に検出できるようになっている。
- **ポイント5:** `satisfies`演算子の活用が一般化し、型推論を狭めすぎずに型チェックを行うパターン（設定オブジェクトやステータス列挙など）が、過度な型注釈を避けつつ安全性を保つベストプラクティスとして広まっている。
