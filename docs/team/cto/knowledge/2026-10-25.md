# CTO Knowledge - 2026-10-25

## Daily Update (2026-10-25)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分のみストリーミングできる。弊社の物件一覧ページのように「検索UIは静的、検索結果は動的」という構成に最適で、TTFBを大幅に改善できる。

- **`use cache` ディレクティブによる粒度の細かいキャッシュ制御:** コンポーネント単位・関数単位でキャッシュ戦略を明示的に指定できるようになり、`revalidateTag`との組み合わせで「物件データ更新時のみ再生成」といった精密な無効化が可能。全ページ再生成のコストを避けられる。

- **Turbopackのビルド高速化を前提にした開発フロー:** ビルド・HMRが大幅に高速化されたことで、CIのビルド時間短縮だけでなく、ローカル開発のフィードバックループも改善される。`bun run build`の検証コストが下がるため、デプロイ前チェックの徹底がしやすくなる。

- **Server Actionsでのミューテーション集約:** API Routeを介さずServer Actionsで直接データ変更を行うことで、クライアント側JSバンドルを削減しつつ型安全性を保てる。引越し費用決済や物件ステータス変更（draft/public）など、フォーム起点の操作に特に効果的。

- **画像・フォント最適化の継続投資:** `next/image`と`next/font`の最適化は地味だが、Airbnb風のビジュアル重視UIでは依然としてLCP改善の最大要因。CDN配信とAVIF/WebP自動変換の設定を見直す価値が高い。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 16ではPPRがstableとなり、静的シェルを即時配信しつつ動的部分（例: 物件詳細の在庫状況）だけをストリーミングで後追い表示できる。静的コンテンツはCDNキャッシュの恩恵を受けつつ、動的データのTTFBを気にせず済む構成が組みやすくなっている。

- **Suspense境界の粒度設計がパフォーマンスを左右:** `loading.tsx`や`<Suspense>`を機能単位（例: 物件カード1枚ずつ）で細かく分けるほど、ユーザーは早く意味のあるコンテンツを見られるが、境界が多すぎるとウォーターフォール状のリクエストが増え逆に遅くなる。1〜3階層程度にまとめるのが実務上のバランス。

- **Server Actions + streaming のエラーハンドリングが成熟:** 2026年にはストリーミング中に発生したサーバーエラーを`error.tsx`経由で部分的にリカバリできるパターンが一般化し、フォーム送信（引越し費用の決済など）のような重要フローでも、全体を再読み込みせずに失敗箇所だけ再試行できるUXが実現しやすい。

- **キャッシュ戦略とRSCの分離がより明確に:** `use cache`ディレクティブ（Next.js 15以降で導入、16で安定化）により、データ取得層のキャッシュとコンポーネントのストリーミング挙動を独立して制御できるようになった。これにより「前の住人」プロフィールのような準静的データと、公開/非公開ステータスのような頻繁に変わるデータを同じツリー内で扱いやすくなっている。

- **Edge runtimeでのストリーミングはコストとの綺麗衡が必要:** Edgeでのストリーミングはレイテンシ面で有利だが、Node.js runtime特有のライブラリ（PDF生成など、引越し費用の見積書発行に使うような処理）が使えないケースが多い。全ページをEdge化するより、ストリーミングが効くページ（一覧・検索）とNode runtimeが必要なページ（決済・PDF）を明確に分ける設計が実務的。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCがBFF層のデファクトになりつつあり、TypeScriptモノレポ構成（Next.js App Router + tRPC）ではスキーマ共有とエンドツーエンドの型安全性により、フロントエンド/バックエンド間の契約ズレを実質ゼロにできる。sumitsugiのようなNext.js 16単一コードベースでは、REST APIルートを増やすよりtRPC化した方がZodバリデーションとも相性が良く、型の二重定義を防げる。

- **ポイント2:** GraphQLは「複数クライアント・複数チームが同じデータを異なる形で欲しがる」場合に強みが出るが、単一のWebアプリ＋シンプルなCRUDが中心のプロダクトではオーバーエンジニアリングになりがち。物件検索のようにフィルタ条件が多様で、将来モバイルアプリ等の別クライアントを想定するなら検討余地はあるが、現フェーズでは優先度低。

- **ポイント3:** RESTは依然パブリックAPI・Webhook・外部連携（決済、外部弁護士システム連携等）の標準であり、2026年時点でも「外部に公開するAPI＝REST（OpenAPI準拠）、内部のフロントエンド↔BFF＝tRPC」という使い分けが主流。sumitsugiも将来パートナー向けAPIを公開する場合はREST/OpenAPIを採用し、内部実装とは分離すべき。

- **ポイント4:** エッジランタイム（Vercel Edge, Cloudflare Workers）普及に伴い、API設計はレイテンシよりも「どこで実行されるか」を前提に考える必要がある。tRPCプロシージャやREST handlerをEdge対応にする場合、DBアクセス（Node専用ドライバ）との互換性を事前に確認すべき——Prisma等のORMがEdge Runtimeで動くかは要検証。

- **ポイント5:** 2026年はAIエージェント（MCP経由のツール呼び出し等）がAPIの「新たなクライアント」になっており、API設計時にスキーマの自己記述性（Zod/JSON Schema）がLLMツール利用の精度に直結する。将来的にsumitsugiの物件データや引き継ぎフローをAIエージェント経由で操作可能にする場合、既存のZodスキーマがそのままツール定義に転用できる設計を意識すべき。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG(WinterTC)によるWeb標準API準拠が進み、Cloudflare Workers・Vercel Edge・Deno Deployなど主要プラットフォーム間でのコード可搬性が大幅に向上。ベンダーロックインを避けるなら、Node.js固有APIよりWeb標準APIで書くのが実用的。

- **コールドスタートのほぼ解消:** V8 isolateベースの実行環境が主流化し、起動レイテンシは1桁ms台まで低下。これによりSSRやAPI Routeをエッジに全面移行する判断がしやすくなったが、DB接続プールなどステートフルな処理の設計は依然別途考慮が必要。

- **エッジでのデータレイヤー統合:** Cloudflare D1/Durable Objects、Turso、PlanetScaleなど「エッジ近接DB」が実運用レベルに成熟し、レイテンシ最小化とグローバル分散読み書きが現実的な選択肢に。sumitsugiのような物件検索・予約系は読み取り多めなので、エッジキャッシュ+リードレプリカの組み合わせが特に効く。

- **AI推論のエッジ統合:** 軽量LLM推論やembedding生成をエッジで実行する動きが加速し、レコメンドや検索ランキングのレイテンシ改善に直結。ただしモデルサイズとコストのトレードオフがあるため、重い処理は依然中央集権的なAPIに委ねる設計が現実的。

- **Observability/デバッグの課題:** 分散実行ゆえにトレーシング・ログ集約が複雑化しており、OpenTelemetryのエッジ対応が2026年の重要トピック。導入前にログ基盤の整備（構造化ログ+集中トレース）を優先すべき。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証（WebAuthn）がデフォルト選択肢になり、SMS/メールOTPはフィッシング耐性が低いため補助手段に格下げ。前の住人・次の住人の個人情報を扱う本サービスでは、認証周りはパスキー対応をロードマップに早期に組み込む価値がある。

- **セッション・トークン管理の厳格化:** JWTの長寿命アクセストークンは漏洩リスクが高く、短命トークン＋リフレッシュトークンのローテーション、サーバーサイドでの即時失効（revocation list）が必須パターンに。`src/contexts/auth-context.tsx`のセッション管理はこの前提で設計・レビューする。

- **ゼロトラスト型の多層防御:** 認証成功後も「毎リクエスト検証」の発想（デバイスフィンガープリント、異常ログイン検知、レート制限）が標準化。物件情報や引越し費用の決済が絡むフローでは、ログイン済みでも操作単位でのリスク評価が重要。

- **サプライチェーン/依存ライブラリのリスク管理:** 認証ライブラリ（NextAuth等）やOAuthプロバイダ連携は攻撃対象になりやすく、定期的な脆弱性スキャンとSBOM管理が前提に。Bun/Next.js 16移行時も認証関連パッケージのピン留め・更新ポリシーを明確化すべき。

- **CSRF/XSS対策の自動化:** フレームワークレベル（Next.jsのServer Actions、CSPヘッダー）での保護がデフォルト化しているが、Cookieの`SameSite`/`HttpOnly`設定やInput Validation（Zod）を手動で緩めないガードレール（lint rule等）をCIに組み込むのが2026年のベストプラクティス。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はORM本体をRust製クエリエンジンから軽量なTypeScript実装（Prisma Client purely in JS/WASM）に移行しており、コールドスタートが重要なサーバーレス/エッジ環境（Vercel Edge Functions等）でのレイテンシが大幅に改善されている。Next.js 16のEdge Runtimeを使う場合はこの構成が前提になる。
- **ポイント2:** SupabaseはPostgresのコネクションプーリング（PgBouncer/Supavisor）をデフォルト提供しており、サーバーレス関数からの接続過多問題を回避できるため、Prisma利用時も`DATABASE_URL`をトランザクションプーラー経由に設定するのが必須のベストプラクティスになっている。
- **ポイント3:** Row Level Security（RLS）をPrismaのスキーマ層と併用する設計が主流化し、認証・認可ロジックをアプリ層とDB層の二重で持たず、Supabase AuthのJWTクレームをPostgresのRLSポリシーに直接紐づける構成がセキュリティ・開発速度の両面で推奨されている。
- **ポイント4:** マイグレーション管理はPrisma Migrateだけでなく、SupabaseのCLIマイグレーション（`supabase db diff`）と併用し、ブランチごとのプレビューDB（Supabase Branching）でPRごとに本番相当のスキーマ検証を行うワークフローが2026年の標準になっている。
- **ポイント5:** リアルタイム要件（例：物件のステータス変更通知）にはSupabase Realtimeを使うケースが増えているが、Prismaのスキーマ変更がRealtimeのPublication設定と同期しない落とし穴があるため、`supabase_realtime`パブリケーションへのテーブル追加を忘れないようデプロイ手順に組み込む必要がある。

### 7. WebAssembly Rust performance 2026

- **WASIプレビュー2の普及:** WASI 0.2系とComponent Modelの実用化が進み、Rustで書いたWasmモジュール同士をABI差異なく組み合わせられるようになった。プラグインアーキテクチャやサンドボックス実行の設計で、FFIレイヤーを薄く保てる点が実装コストに直結する。

- **SIMD128とマルチスレッドの安定利用:** `wasm32-unknown-unknown`でのSIMD命令とWeb Workers連携によるマルチスレッド実行がブラウザ主要エンジンで安定し、画像処理・暗号化・数値計算系の重い処理をネイティブの70-90%程度の速度でブラウザ内に持ち込める。CPUバウンドな処理をサーバーからクライアントにオフロードする選択肢として現実的になった。

- **バイナリサイズ最適化が引き続き鍵:** `wasm-opt`、`twiggy`、`cargo-bloat`に加え、Rust標準ライブラリの軽量化（`panic = "abort"`、`opt-level = "z"`、LTO）を組み合わせたチューニングが定着。初回ロード時間がUX品質を左右するため、機能追加ごとにバイナリサイズのCIチェックを入れる運用が望ましい。

- **ネイティブとの差が縮小しつつも境界あり:** JIT/AOTコンパイラの改善でCPUバウンド処理はネイティブに近づいたが、DOM操作やJS↔Wasmの境界越え（marshalling）のオーバーヘッドは依然大きい。計算密度が高い部分のみWasm化し、UIロジックはJS/TSに残すハイブリッド構成が最もコストパフォーマンスが良い。

- **Rustツールチェーンの成熟:** `wasm-bindgen`/`wasm-pack`のビルドが高速化し、Vite/Next.jsとの統合もプラグイン経由でほぼシームレスになった。sumitsugiのような物件検索・画像処理が絡む機能（例: 物件写真の自動補正やPDF生成の高速化）では、該当処理のみRust+Wasm化するROIが見込める。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 15〜16でPPRが安定化し、静的シェルを即時配信しつつ動的部分を`Suspense`でストリーミングする構成が標準パターンに。物件一覧ページのように「検索フォームは静的、結果は動的」といった画面はPPRとの相性が良く、TTFBとLCPを両立できる。

- **Server Actions のバリデーション層としての成熟:** `useActionState`と組み合わせたZodスキーマ検証が定石化し、フォーム送信のクライアント/サーバー間の型不整合バグが減少。物件登録・引越し費用算出フォームなど多段階フォームでは、Server Actionごとに同一Zodスキーマを再利用し型の一元管理をすべき。

- **キャッシュ戦略の明示化（`cacheLife`/`cacheTag`):** App RouterのデフォルトキャッシュがNext.js 15で「オプトイン」に変わったことを受け、`use cache`ディレクティブと`cacheTag`による明示的な再検証設計が必須に。物件ステータス（draft/public）の変更時は`revalidateTag`で即時反映させる設計にしないと、公開直後も古いキャッシュが表示されるリスクがある。

- **Server Components とクライアント境界の最小化:** 「クライアントコンポーネントの葉を小さく保つ」設計が定着し、認証状態（`auth-context.tsx`のような）はServer Componentsで極力解決し、インタラクティブ部分のみ`'use client'`に切り出すパターンが推奨される。これによりJSバンドルサイズと初期表示速度が改善する。

- **並行ルート(Parallel Routes)とIntercepting Routesの実用化:** モーダル表示（物件詳細のクイックビューなど）でブラウザ履歴と整合させるため、`@modal`スロット+インターセプトルートの組み合わせがSPA的なUXを実現する標準手法として普及。フルページ遷移とモーダル両対応が1つの実装で済むため、物件詳細のプレビュー機能などに適している。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Vercel Edge FunctionsはV8 isolateベースで実行されるため、コールドスタートが従来のLambdaベースFunctionsより大幅に短く、位置情報判定やA/Bテストのリダイレクトなど低レイテンシが必須な処理に向いている。sumitsugiのような不動産リスティングサイトでは、地域別の表示切り替えやリダイレクト処理をEdgeに寄せることで初期表示速度を改善できる。
- **ポイント2:** 2026年時点でEdge Runtimeの制約（Node.js API非対応、実行時間・メモリ制限）が徐々に緩和されつつあるが、依然としてDBクライアントやファイルI/Oを伴う処理には不向き。認証チェックやヘッダー書き換えなど「軽量・無状態」な処理に限定して使うのがベストプラクティス。
- **ポイント3:** Next.js 16のPartial Prerendering（PPR）とEdge Middlewareを組み合わせることで、静的シェルを即時配信しつつ動的部分（ログイン状態・前の住人の在庫状況など）をEdgeでストリーミング注入できる。これにより物件一覧ページのTTFBを維持しながら動的要素を扱える。
- **ポイント4:** Edge Functionsの実行回数・帯域courseは従量課金のため、画像最適化や物件検索フィルタのような高頻度アクセス処理をEdgeに置くとコストが跳ねやすい。頻度の高いロジックはキャッシュ戦略（ISR + stale-while-revalidate）と併用してコストを抑えるべき。
- **ポイント5:** Vercelのリージョン選択機能を使い、Edge Functionsの実行リージョンをユーザー分布（国内向けなら`hnd1`等）に固定することで、不要なクロスリージョン通信を避けレイテンシを安定化できる。グローバル展開前のMVP段階では単一リージョン固定がシンプルで十分。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.xの`satisfies`演算子とconst型パラメータが定着し、型推論を保ったままリテラル型を厳密化できるようになった。これにより`as const`の濫用を避けつつ、設定オブジェクトやAPIレスポンス型を安全に扱える。
- **ポイント2:** Zodなどのスキーマライブラリで「実行時検証」と「型定義」を単一ソースから生成するパターンが標準化し、`.claude/rules/standards.md`が求める「システム境界でのZod検証」とも合致する。APIレスポンスやフォーム入力の型をスキーマから自動導出することで、型と実装のズレを防げる。
- **ポイント3:** Discriminated Union（タグ付きユニオン）による状態管理が、`'draft' | 'public'`のようなステータス管理のベストプラクティスとして定着。switch文の網羅性チェック（`never`型での exhaustiveness check）をCIに組み込むことで、新しいステータス追加時の漏れをコンパイル時に検出できる。
- **ポイント4:** テンプレートリテラル型とBranded Type（nominal typing）を組み合わせ、`UserId`と`PropertyId`のような構造的に同じstring型でも混在代入をコンパイルエラーにする手法が、中規模以上のコードベースで採用が進んでいる。
- **ポイント5:** tRPCやHono RPCのようなEnd-to-End型安全フレームワークが、フロントエンド・バックエンド間の型共有をビルド時に保証する標準パターンとして普及し、API契約のドリフトをコード生成ではなく型推論のみで防げる。
