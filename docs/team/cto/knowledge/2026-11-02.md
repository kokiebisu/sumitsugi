# CTO Knowledge - 2026-11-02

## Daily Update (2026-11-02)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 15系で導入されたPPRがNext.js 16で安定版となり、静的シェルを即時配信しつつ動的部分のみストリーミングすることで、LCP/TTFBを大幅改善できる。本プロジェクトの物件一覧・詳細ページのような「静的レイアウト＋動的データ」構成に適している。

- **Turbopackへの完全移行:** `bun dev`/`bun run build`でTurbopackがデフォルトとなり、webpackと比べてビルド・HMR速度が数倍向上。Bunランタイムとの組み合わせでローカル開発体験がさらに高速化するため、CI上のビルド時間短縮も期待できる。

- **React Server Components + Cache Componentsの活用:** `use cache`ディレクティブによる明示的キャッシュ制御がNext.js 16で洗練され、データフェッチ層（`src/lib/data.ts`相当）でキャッシュ境界を細かく指定することで、不要な再計算を削減しつつ鮮度管理が可能。

- **画像・フォント最適化の継続的重要性:** `next/image`のAVIF/WebP自動変換と`next/font`のセルフホスティングは依然として基本かつ効果が大きい。物件写真を多用するUIでは、レスポンシブ`sizes`指定とpriorityタグの適切な使い分けがCore Web Vitalsに直結する。

- **Edge RuntimeとStreaming SSRの選択的採用:** 認証チェックやリダイレクトのような軽量ロジックはEdge Runtimeに寄せ、重いレンダリングはNode.js runtimeで行うハイブリッド構成が2026年のベストプラクティス。`src/contexts/auth-context.tsx`のようなクライアント状態管理との境界設計がパフォーマンスとDXの両立に重要。

### 2. React Server Components streaming 2026

## React Server Components Streaming 2026 — CTO視点

- **ポイント1（Partial Prerenderingの標準化）:** Next.js 16ではPPR（Partial Prerendering）がデフォルト挙動に近づき、静的シェルを即時配信しつつ動的部分だけをストリーミングする設計が主流化。sumitsugiのような物件詳細ページでは、静的な物件情報を即表示しつつ「お気に入り状態」や「空室確認」のような動的データのみSuspense境界でストリーミングすることで、LCPを大幅改善できる。

- **ポイント2（`use cache` directiveとの統合）:** RSCのストリーミングとNext.jsのキャッシュディレクティブ（`use cache`）の組み合わせが実用段階に入り、データフェッチ単位での粒度の細かいキャッシュ制御が可能に。物件一覧（`src/app/properties/`）のようなSSRページで、前の住人情報など更新頻度の低いデータはキャッシュしつつ、空室状況のみ再フェッチする設計が現実的な選択肢になっている。

- **ポイント3（Server Actionsのストリーミングレスポンス）:** Server Actions自体が部分的な進捗ストリーミングに対応し始めており、引越し費用の計算や複数ステップのフォーム送信（listing作成フローなど）で、処理中の中間状態をクライアントに逐次返せるようになった。長時間処理のUXが「スピナー待ち」から「進捗表示」に変わる。

- **ポイント4（エラーバウンダリとストリーミングの相性改善）:** ストリーミング中に発生したサーバーエラーを個別のSuspense境界単位で捕捉し、ページ全体をクラッシュさせずに該当セクションのみフォールバック表示する仕組みが洗練された。認証関連コンポーネント（`auth-context.tsx`配下）など、失敗時の影響範囲を限定したい箇所で特に有効。

- **ポイント5（計測・デバッグツールの追従）:** ストリーミングSSRのボトルネック解析用にChrome DevToolsやNext.jsのビルトリンプロファイラがRSC単位のタイムライン表示に対応し始めた。本番導入前に「どのコンポーネントがストリームをブロックしているか」を可視化できるため、パフォーマンス劣化の検知コストが下がっている。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの採用拡大）:** 2026年現在、フルスタックTypeScriptプロジェクトではtRPCがGraphQLより導入コストが低く、型安全性もend-to-endで保証されるため、Next.js App Router構成のような小〜中規模チームに特に適している。Server Actionsとの組み合わせも進み、API層自体を薄くする選択肢が増えている。

- **ポイント2（GraphQLはBFF/複雑なデータ要件に残る）:** モバイル・Web混在や複数クライアントが異なる形でデータを欲しがるケースではGraphQLが依然優位だが、N+1問題やキャッシュ戦略の複雑さから「社内API」ではオーバーエンジニアリングになりやすい。sumitsugiのような単一Webアプリ中心のプロダクトでは今のところ採用の優先度は低い。

- **ポイント3（RESTは依然"退屈だが安全"な選択）:** 外部公開APIや決済連携（今後の引越し費用決済など）ではRESTfulかつOpenAPI仕様での文書化が業界標準として求められることが多く、外部弁護士・決済代行との統合時はRESTが摩擦が少ない。

- **ポイント4（スキーマファースト+Zodバリデーションの統合）:** API設計のトレンドとして、Zodスキーマを単一のソースとしてtRPC入力検証・DBスキーマ・フロントの型を共有する「スキーマファースト」設計が定着しており、CLAUDE.mdのZod境界検証ルールとも整合する。

- **ポイント5（AI時代のAPI設計はドキュメント自動生成前提）:** LLMエージェント（Claude Codeなど）がAPIを利用・生成する機会が増え、OpenAPI/JSON Schemaを自動生成できる設計（tRPC+zod-to-openapi等）が、将来的なエージェント連携（他社との引き継ぎプラットフォーム連携等）を見据えると有利。

### 4. serverless edge computing 2026

- **エッジでのAI推論最適化:** 2026年はLLM推論をエッジで分散処理する「エッジAIゲートウェイ」が主流化し、レイテンシをミリ秒単位に抑えつつ、中央クラウドへの帯域コストを削減できる。弊社のような不動産マッチングでも、物件検索のパーソナライズ処理をエッジ側で行うことでUX向上が期待できる。

- **WASMベースのランタイム統一:** Cloudflare Workers、Deno Deploy、Fastly Compute等がWasm/WASIを共通基盤とし、Node.js依存コードの移植が容易になっている。Next.js 16のEdge Runtimeとの互換性も進化しており、`src/app`配下のAPIルートを段階的にエッジ移行する選択肢が現実的になった。

- **ステートフルエッジ（Durable Objects系）の普及:** これまでエッジはステートレス処理が前提だったが、Durable Objects/KV/SQLiteライクなエッジDBの成熟により、セッション管理や在庫ロックなど低レイテンシな整合性要求にも対応可能に。認証コンテキスト(`auth-context.tsx`)のセッション検証をエッジで完結させる設計も検討価値あり。

- **コスト構造の変化(従量課金の精緻化):** リクエスト数ベースではなくCPU時間・メモリ秒単位の精緻な課金モデルが標準化し、トラフィックが少ないMVPフェーズのプロダクトではサーバーレス/エッジの方がVercel/Vultr等の固定費インフラより総コストで有利になるケースが増えている。ベータローンチ前の当プロダクトにも適した選択肢。

- **観測性(Observability)とコールドスタート問題の実質解消:** V8 isolateベースのエッジ実行環境ではコールドスタートがほぼ無視できる水準になり、代わりに分散トレーシング（OpenTelemetry対応エッジログ）がボトルネック特定の鍵になっている。本番運用に向けては、エッジ環境でのエラーログ・トレース収集の仕組みを早期に整備すべき。

### 5. authentication security best practices 2026

- **パスキー/FIDO2が標準化:** パスワードレス認証（WebAuthn/FIDO2）がデフォルト選択肢になりつつあり、フィッシング耐性とユーザー離脱率の低減を同時に実現できる。実装コストが下がっているため、新規プロジェクトでは最初からパスキー対応を前提に設計すべき。

- **セッション管理の継続的検証:** 一度ログインしたら終わりではなく、デバイスフィンガープリンティングやリスクベース認証でセッション中も継続的に信頼度を評価する「ゼロトラスト」型が主流化。特に個人情報を扱う賃貸・引越しサービスでは、不審なアクセスパターン検知を本人確認フローに組み込む価値が高い。

- **トークンの短命化とリフレッシュ戦略:** アクセストークンの寿命を短くし（15分〜1時間）、リフレッシュトークンのローテーション＋再利用検知をセットで実装するのが事実上の標準。長期間有効なJWTを単体で使う設計は漏洩時のリスクが大きく避けるべき。

- **MFA疲労攻撃への対策:** プッシュ通知型MFAの「通知スパム」攻撃が増加しており、数値マッチング（number matching）やコンテキスト情報の表示が必須に。単純な承認ボタンだけのプッシュ通知は非推奨。

- **認証ロジックの外部化:** 自前実装よりAuth0/Clerk/Supabase Authなどの認証プロバイダ活用がコスト効率で優位。sumitsugiのようなMVPフェーズでは、自前のセッション管理より実績あるライブラリに乗せる方が脆弱性リスクと開発コストの両方を下げられる。

### 6. database architecture Prisma Supabase 2026

- **ポイント1（Prisma 6の型安全性とエッジ対応）:** Prisma 6以降はEdge Runtime（Vercel Edge, Cloudflare Workers）への対応が進み、Driver Adaptersによってコネクションプーリングをアプリ層で管理できるようになった。sumitsugiのようなNext.js 16 App Router構成では、Server ComponentsからのDB直接アクセスとEdge SSRの両立を見据え、早期にDriver Adapters方式へ移行しておくと将来の拘束が減る。

- **ポイント2（SupabaseのRLSとPrismaの併用パターン）:** SupabaseのRow Level Security（RLS）はPrisma経由のクエリでは素通りしがちな落とし穴になるため、Prisma Clientを使う場合は`service_role`キー経由のサーバーサイド専用アクセスに限定し、クライアント直叩きはSupabase Auth + RLSで保護する二層構成が2026年のベストプラクティスになっている。物件データ（`draft`/`public`ステータス）のような公開範囲制御には特に重要。

- **ポイント3（コネクションプーリングの進化）:** SupabaseのSupavisor（PgBouncer後継）がサーバーレス環境での接続爆発問題を解消しつつあり、Prisma + Supavisorの組み合わせがVercelデプロイのデフォルト推奨構成になってきている。トランザクションモードとセッションモードの選択を誤るとPrismaのプリペアドステートメントが機能しない点は要注意。

- **ポイント4（マイグレーション運用の分離）:** Prisma MigrateとSupabase CLIのマイグレーションを両方使うと競合しやすいため、2026年時点では「スキーマ定義はPrisma、RLS/トリガー/Functionsのような DB側ロジックはSupabase Migrationsで分離管理」という責務分割が定着している。sumitsugiでも今後RLSを強化する際はこの分離を意識すべき。

- **ポイント5（ベータローンチ前の観点）:** 現フェーズ（法務確認待ちのベータローンチ準備）では、個人情報（住所・決済情報）を扱うテーブルに対してSupabaseのRLSポリシーを先に設計し、Prismaスキーマ変更時に`bun run build`だけでなく`supabase db diff`でRLS整合性もCIに組み込むことを推奨する。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WebAssemblyのコンポーネントモデル（WASI Preview 2）が2026年にかけて主要ランタイム（Wasmtime、wasmCloud）で安定し、Rustクレートを言語間で安全に共有できるようになった。自前実装前にWASIコンポーネントとして再利用可能か確認すると開発コストを削減できる。
- **ポイント2:** `wasm-bindgen`と`wasm-pack`のビルドパイプラインが成熟し、Rust→WasmのバンドルサイズはLTO・`wee_alloc`代替（`talc`等）の採用で数十KB台まで縮小可能。フロントエンドで画像処理やPDF生成など計算負荷の高い処理をWasm化する際はこの最適化を標準手順に含めるべき。
- **ポイント3:** SIMD128とマルチスレッド（`wasm-bindgen-rayon`）がブラウザ標準化され、Rust側で`std::simd`や`rayon`を使ったコードがほぼそのままWasmでも高速に動く。CPU負荷の高い機能（例: 物件写真の一括リサイズ）をサーバーからクライアントWasmにオフロードする選択肢が現実的になっている。
- **ポイント4:** サーバーサイドではWasmベースのプラグイン実行環境（Extism、Spin）がマイクロサービス境界をプロセスより軽量に代替し、コールドスタートがコンテナの1/10程度に短縮されるケースが増えている。将来的にマルチテナント機能拡張（サードパーティ統合など）をサンドボックス実行したい場面で検討価値がある。
- **ポイント5:** RustのWasmターゲットは依然デバッグ体験（スタックトレース、ソースマップ）が弱く、`console_error_panic_hook`やDWARF対応ツールの導入が実質必須。本番導入時は最初からエラーロギング基盤を組み込む前提で計画すべき。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分のみServer Componentでストリーミングする構成が標準化。初期表示速度とパーソナライズの両立がしやすくなった。
- **`use cache` ディレクティブによる明示的キャッシュ制御:** fetchベースの暗黙キャッシュから、関数・コンポーネント単位で`use cache`を宣言する明示的モデルへ移行。キャッシュ境界が読み取りやすくなり、意図しないキャッシュ漏れのデバッグコストが下がる。
- **Server Actions のセキュリティ境界強化:** `"use server"`境界を跨ぐデータは自動シリアライズされるが、認可チェックをAction内部で必須化するパターンが定着。フォーム送信・決済処理ではZodバリデーションと併用し、CSRF相当のリスクをフレームワークレベルで抑える設計が推奨される。
- **Parallel Routes + Intercepting Routes でのモーダル/ステップUI:** 物件詳細のモーダル表示や多段フォームなど、URL状態を保ったままオーバーレイUIを実現する手法が一般化。ブラウザの戻る/進むとの整合性が取りやすく、E2Eテストもルート単位で書ける利点がある。
- **Edge/Node runtimeの使い分け最適化:** 認証チェックや軽量リダイレクトはEdge Middlewareで低レイテンシ化し、DB接続やファイル処理が必要な処理はNode runtimeに明確に分離する構成が主流。Vercel以外のホスティングでも同様の分離がデプロイ戦略の基本になっている。

### 9. Vercel Edge Functions optimization 2026

- **Fluid Computeへの移行:** Vercelの Fluid Compute モデルを使うことで、同一インスタンス内で複数リクエストを並行処理できるため、コールドスタートの頻度とコンピュート課金を大幅に削減できる。I/O待ち時間が多いAPIルートほど効果が大きい。

- **Partial Prerendering (PPR) との併用:** Next.js 16のPPRと組み合わせ、静的シェルをEdgeでキャッシュしつつ動的部分だけをストリーミングすることで、TTFBを最小化しながらパーソナライズされたコンテンツも配信できる。全ページをEdge Functionで動かす必要はない。

- **Node.js互換APIの拡充:** Edge RuntimeでNode.js APIのサポートが広がってきたため、従来Serverless Functionに逃がしていた処理（crypto, buffer等）も徐々にEdgeに移行可能。ただし依存パッケージのバンドルサイズ制限（~1-4MB）は変わらず、重いライブラリは引き続き分離が必要。

- **Edge ConfigとKVの使い分け:** 低レイテンシな読み取り専用データ（フラグ、リダイレクトルール）はEdge Configに、頻繁に更新される状態はVercel KVやRegional DBに置く設計が定石。Edge Functionから直接DBへの同期接続はリージョン間レイテンシを生むため避けるべき。

- **リージョン実行の明示指定:** デフォルトのグローバル実行ではなく、主要ユーザー層（例: 日本なら`hnd1`）にリージョンを固定することで、DBや外部APIとのレイテンシが安定しやすい。グローバル分散が逆にp95レイテンシを悪化させるケースがあるため、計測した上で選択すべき。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x系の`satisfies`演算子と`const`型パラメータの活用が定着し、型推論を保ったままリテラル型の厳密性を強制できるようになった。sumitsugiでは`status: 'draft' | 'public'`のようなUnion型をオブジェクトリテラルに適用する際に有効で、型の取りこぼしをコンパイル時に検出できる。

- **ポイント2:** Zodなど実行時スキーマからTypeScript型を自動生成する「Schema-first」パターンが主流化し、`z.infer<typeof schema>`で型とランタイム検証を単一のソースで管理する。標準に定めている「システム境界でのZodバリデーション」はこの流れに合致しており、型安全性とセキュリティを同時に確保できる。

- **ポイント3:** Branded Types（nominal typing）がID系の値（`UserId`, `PropertyId`など）の混在防止に広く採用されている。文字列型の`sellerId`と`buyerId`を取り違えるような実装ミスを型レベルで防げるため、物件・ユーザー関連のドメインモデルに導入する価値が高い。

- **ポイント4:** `tsc --noUncheckedIndexedAccess`や`exactOptionalPropertyTypes`など厳格フラグの採用が標準化しつつあり、配列・オブジェクトアクセス時の暗黙的`undefined`漏れを防ぐ。ビルド健全性を重視する方針（build前のCI必須化）と相性が良く、今後の`tsconfig.json`更新候補として検討の余地がある。

- **ポイント5:** AIコード生成（Claude Code等）の普及に伴い、「型エラーをAIが自己修正するループ」が開発フローに組み込まれる例が増えている。`build-error-resolver`エージェントのような型エラー専門の自動修正フローは、この2026年トレンドを先取りした実践例といえる。
