# CTO Knowledge - 2026-10-17

## Daily Update (2026-10-17)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Prerendering の本格活用）:** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分のみストリーミングすることで、物件一覧ページのようなハイブリッドコンテンツでもTTFBを大幅短縮できる。これにより`src/app/properties/`配下のページでSSR全体をブロックせず、価格や空室状況だけを動的に差し替える設計が可能。

- **ポイント2（Turbopackのビルド・devサーバー最適化）:** Turbopackが本番ビルドでも既定化され、`bun run build`の時間が大幅に短縮されるため、CI/CDのフィードバックループが速くなる。大規模化しているコンポーネント群（`src/components/listing/`等）でも差分ビルドの恩恵が大きい。

- **ポイント3（React Server Components + キャッシュ戦略の精緻化）:** `use cache`ディレクティブやキャッシュプロファイルの明示的な制御が標準化され、物件データのようにセラー（前の住人）起因で更新頻度が異なるデータに対して、エンドポイント単位で細かいrevalidate戦略を組める。

- **ポイント4（画像・フォントの自動最適化の深化）:** `next/image`のAVIF優先配信とレイアウトシフト抑制がさらに進み、Airbnb風のリッチな物件写真UIでもCore Web Vitals（特にLCP）を保ちやすくなっている。

- **ポイント5（Edge Runtimeとの併用による地理的レイテンシ低減）:** 認証系（`auth-context.tsx`）など軽量なミドルウェア処理をEdgeで実行し、重いDBアクセスのみNode.jsランタイムに残す構成が主流化。国内ユーザー中心のsumitsugiでも、Edgeでのリダイレクト・AuthチェックがUX改善に直結する。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** React Server Componentsのストリーミングは2026年時点でNext.js App Routerの既定動作として定着し、`Suspense`境界ごとに段階的にHTMLを配信することでTTFBとLCPを同時に改善できる。サミツギのproperties一覧や物件詳細ページのような重いデータ取得を伴うページでは、骨組みを即時表示しつつ詳細データを後追いで流す設計が標準パターンになっている。
- **Partial Prerendering (PPR) との統合:** 静的シェルを事前生成し、動的部分だけをストリーミングで差し込むPPRが本格普及し、静的サイトのキャッシュ効率とSSRのパーソナライズ性を両立できる。物件検索結果のように「レイアウトは静的、価格や空き状況は動的」なページ構成に特に有効。
- **キャッシュ戦略の複雑化への対応:** RSCのストリーミングはCDN/エッジキャッシュとの相性を考慮したキャッシュタグ設計が必須になり、`revalidateTag`や`revalidatePath`を使った細粒度の無効化戦略が重要な実装スキルになっている。ドラフト/公開ステータス切り替えのような状態変更を伴う機能では、キャッシュ無効化漏れがバグの温床になりやすい点に注意。
- **エラーバウンダリとストリーミングの相互作用:** ストリーミング中にサーバーコンポーネントがエラーを投げた場合、既に送信済みのチャンクは変更できないため、`error.tsx`の粒度設計とSuspense境界の配置を一致させることが重要になっている。特にフォームや決済フローなど多段階フローでは、エラー境界を細かく分割してユーザー体験を損なわないようにする実践が広がっている。
- **開発者体験とデバッグツールの成熟:** React DevToolsやNext.jsの計測ツールがRSCストリーミングのタイムライン可視化に対応し、どのコンポーネントがボトルネックになっているかを特定しやすくなった。チームの実装速度を上げる観点では、ストリーミング境界の設計レビューを早期に行うことがパフォーマンス事故を防ぐ鍵になる。

### 3. API design REST GraphQL tRPC 2026

- **統一型安全性の浸透:** tRPCのようなエンドツーエンド型安全アプローチが標準化し、OpenAPI/GraphQLスキーマからのコード生成（codegen）とクライアント・サーバー間の型共有が開発速度とバグ削減に直結している。sumitsugiのようなNext.js App Router構成では、Server Actions + Zodバリデーションの組み合わせがtRPC相当の型安全性を低コストで実現できる点が実用的。

- **用途別のプロトコル併用が定石化:** 「GraphQL一強」の流れは落ち着き、内部BFF/モバイル向けは柔軟なクエリが必要な場面でGraphQL、シンプルなCRUDやSSR連携はREST/Server Actions、フルスタックTS環境はtRPCと、用途ごとに併用する設計が主流になっている。

- **BFF層の縮小とRSC/Server Actionsへの統合:** Next.jsのReact Server ComponentsとServer Actionsにより、従来API層が担っていたデータフェッチ・ミューテーションをフロントエンドのコードベースに統合する流れが加速し、API設計そのものの比重がバックエンド境界（外部連携・認証・決済）に絞られてきている。

- **スキーマファースト + AIエージェント連携の重要性:** LLMエージェントがAPIを直接呼び出す機会が増え、OpenAPI/JSON Schemaの厳密な記述がAIツール連携（MCP等）の前提になっている。将来的な外部連携（決済・物件データ連携等）を見据え、スキーマ定義を早期に整備する価値が増している。

- **パフォーマンス観点でのオーバーフェッチ対策:** REST + GraphQL的な部分フィールド指定（sparse fieldsets）やtRPCのバッチング機能を使い、Bun/Edgeランタイム環境での低レイテンシ要件に応える設計が重視されている。sumitsugiの物件一覧・検索APIのような一覧系エンドポイントでは特に有効。

### 4. serverless edge computing 2026

- **エッジでのAI推論標準化:** 2026年はCloudflare Workers AI、Vercel Edge Functions、Deno Deployなどでの軽量LLM推論がデフォルト化し、レイテンシ要件の厳しい検索・レコメンド機能はエッジ実行に移行するのが主流になっている。sumitsugiのような物件検索UXでも、画像最適化やパーソナライズのエッジ化を検討する価値がある。

- **コールドスタート問題の実質的解消:** V8 isolateベースのランタイム（Workers, Deno）がコンテナ型サーバーレス（Lambda等）を置き換えつつあり、起動時間がミリ秒単位になったことで「エッジ=常時低レイテンシ」が当たり前になった。Next.js 16のEdge Runtimeと組み合わせることで、SSRの初回表示速度を大きく改善できる。

- **データ整合性とエッジの組み合わせが鍵:** エッジ実行は読み取り重視の処理に強いが、書き込み整合性（予約・決済など）は依然リージョナルDBに依存する。sumitsugiの物件掲載や引き継ぎフローのような強整合性が必要な操作はオリジン側に残し、閲覧・検索系のみエッジ化するハイブリッド設計が実用的。

- **ベンダーロックイン回避の重要性:** WinterCG（Web-interoperable Runtimes）準拠のAPI設計が広がり、Cloudflare/Vercel/Deno間の移行コストが下がってきている。新規にエッジ機能を実装する場合、特定ベンダーAPIに依存しすぎず標準Fetch APIベースで書くことで将来の移行余地を残すべき。

- **コスト構造の変化に注意:** エッジ実行は従量課金だが、CPU時間ベースの課金モデル（Workers）とリクエスト数ベース（Lambda@Edge）で特性が異なり、アクセスパターン次第でコストが逆転することがある。MVP段階では過度な最適化より、まずVercelの標準デプロイで様子を見て、トラフィックパターンが見えてからエッジ移行を判断するのが妥当。

### 5. authentication security best practices 2026

- **パスキー/WebAuthnの標準化:** パスワード+SMS認証からパスキー（FIDO2/WebAuthn）への移行が2026年には業界標準となっており、フィッシング耐性とUX向上を両立できる。sumitsugiのようなB2C物件プラットフォームでは、本人確認の信頼性向上とログイン離脱率低減の両方に直結する。

- **セッション管理とトークンの短命化:** JWTを使う場合はアクセストークンを短寿命（5-15分）にし、リフレッシュトークンのローテーション＋再利用検知を必須にする構成が主流。長寿命トークンの漏洩リスクを抑えつつ、サーバー側での即時失効も可能になる。

- **ゼロトラスト前提のAPI保護:** 認証後も「信頼しない」設計（デバイスフィンガープリンティング、異常ログイン検知、レート制限）を組み合わせることで、クレデンシャルスタッフィングやブルートフォースへの耐性を高める。Next.js App RouterのMiddlewareでAPIルート単位の検証を一元化すると実装コストを抑えられる。

- **認可の粒度とRLS活用:** 認証（誰か）と認可（何ができるか）を分離し、物件データのようなマルチテナント性のあるリソースはDB層でのRow Level Security（RLS）併用が推奨される。アプリ層のみでの権限チェックは実装漏れのリスクが高い。

- **サプライチェーン・依存ライブラリの監査:** 認証関連ライブラリ（NextAuth/Auth.js等）は更新頻度が高く、CVE対応が遅れると直接的な脆弱性につながる。Dependabot等による自動監視とバージョン固定の両立が2026年のベストプラクティス。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prismaは5.x以降でRustバイナリエンジンを段階的に廃止し、TypeScript/WASMベースのクエリエンジンに移行しています。これによりVercel EdgeやCloudflare Workersなどのエッジランタイムでの起動が高速化し、デプロイサイズも削減されます。

- **ポイント2:** SupabaseはPgBouncer後継の「Supavisor」でトランザクションモードのコネクションプーリングを提供していますが、Prismaのprepared statementと相性が悪いケースがあるため、`pgbouncer=true`オプションや直接接続（ポート5432）との併用設計が必須です。

- **ポイント3:** SupabaseのRow Level Security（RLS）はPrismaのスキーマレベルでは表現できないため、マイグレーションを素のSQL（`prisma migrate dev --create-only`+手動SQL）で管理するか、Supabase CLIのマイグレーションと二重管理する運用が実質スタンダードになっています。

- **ポイント4:** Prisma Accelerateを使うとSupabase上でのグローバルなコネクションプーリング＋クエリキャッシュが可能になり、sumitsugiのような物件検索系の読み取り多めのワークロードではレイテンシ改善とDB接続数削減の両方に効果があります。

- **ポイント5:** Supabaseの「Database Branching」機能とPrismaのマイグレーション（`prisma migrate`）を組み合わせることで、PRごとに独立したDBブランチ上でマイグレーションを検証できるため、CI上でのスキーマ変更レビューの安全性が大きく向上します。

### 7. WebAssembly Rust performance 2026

- **WASM GCの実用化:** WebAssembly GC proposalの安定化により、RustでもGCを前提としたホスト言語（JS/Java等）とのメモリ共有が容易になり、バインディングコードの肥大化が解消されつつある。

- **コンポーネントモデルの普及:** WASI Preview 2とComponent Modelの標準化で、Rustで書いたモジュールを言語非依存で合成できるようになり、マイクロサービス的な粒度でWASMを配置する設計がサーバーサイドでも実用レベルに達している。

- **SIMD/スレッド対応の安定化:** wasm32-wasip1-threadsやSIMD命令の標準サポートにより、画像処理・ML推論などCPU負荷の高い処理でネイティブの70-90%程度の性能が出せるようになっており、ブラウザ外（エッジ・サーバーレス）での採用が加速している。

- **コールドスタート最適化:** AOTコンパイル（Wasmtimeのcomponentize-py/cargo-componentなど）とpre-compiled cacheの組み合わせで、サーバーレス環境でのコールドスタートがコンテナより1桁速いケースが増え、エッジ配信（Cloudflare Workers, Fastly Compute）での標準選択肢になっている。

- **バンドルサイズとDX:** `wasm-bindgen`/`wasm-pack`のツールチェーン成熟とtree-shaking精度向上で、Rust→WASMの出力サイズが大幅に縮小し、フロントエンドでの「重い」という過去の評価が薄れつつある点は、今後sumitsugiのような負荷の高いUI処理（画像最適化等）を検討する際の選択肢になり得る。

### 8. Next.js App Router patterns 2026

- **Server Components優先の設計:** App Routerではデフォルトでサーバーコンポーネントを使い、インタラクティブ性が必要な箇所だけ`'use client'`を最小範囲に切り出すのが2026年のベストプラクティス。JSバンドルサイズと初期表示速度（LCP）に直結するため、物件一覧ページなどデータ表示中心の画面はサーバー側に寄せるべき。

- **Partial Prerendering (PPR) の実用化:** Next.js 15以降で導入されたPPRが16系でより安定し、静的シェル＋動的部分のストリーミングが標準パターンに。物件詳細ページのように「物件情報は静的、お気に入り状態や在庫は動的」という混在ケースで特に効果が大きい。

- **`use cache`ディレクティブによるキャッシュ制御の明示化:** fetchベースの暗黙キャッシュから、関数単位で`use cache`を付与する明示的キャッシュへ移行が進んでいる。データ取得ロジック（`src/lib/data.ts`）のキャッシュ境界を明示することで、再検証漏れによるバグ（例：ステータス更新が反映されない）を防げる。

- **Server Actionsのセキュリティ境界強化:** Server Actionsは事実上の公開APIエンドポイントになるため、Zodによる入力検証と認可チェックを関数冒頭で必須化する運用が標準化。フォーム送信（引越し費用の問い合わせ等）では、CSRF対策済みのServer Actionsを使い、クライアント側APIルートを極力減らす方向が主流。

- **ルーティング構成のモジュール化（Route Groups + Parallel Routes）:** `(group)`によるルートグループと並行ルートを組み合わせ、`src/app/properties/`や`src/app/account/`のような機能単位でレイアウト・ローディング状態を分離するパターンが定着。ダッシュボード系UIでモーダルやタブを並行ルートで実装し、ブラウザの戻る/進むを自然に保つ事例が増えている。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Functionsの実行リージョンが自動的にリクエスト発生地に近いノードへ最適化されるようになり、コールドスタート遅延が大幅に短縮されている。レイテンシが重要な認証・リダイレクト処理はEdge Middlewareに寄せるのが有効。
- **ポイント2:** Edge Runtime向けのNode.js API互換性が拡大し、従来Serverless Functionsでしか動かせなかった処理（一部のcrypto/streams系API）もEdgeで実行可能になってきている。ただし依存パッケージのEdge対応状況は事前検証が必須。
- **ポイント3:** Vercelの`Edge Config`やISR（Incremental Static Regeneration）との組み合わせで、DBアクセスを伴わない読み取り頻度の高いデータ（フラグ、A/Bテスト設定）をEdgeでミリ秒単位配信できる。sumitsugiの物件一覧・検索フィルタのような読み取り比率が高い機能に適している。
- **ポイント4:** 課金モデルがCPU時間ベースに最適化されており、不要なawait連鎖やブロッキング処理を削減するだけで実行コストが直接下がる。関数の責務を小さく分割し、I/Oバウンド処理とCPUバウンド処理を分けることがコスト最適化の鍵。
- **ポイント5:** Observability機能（Vercel OTEL統合）が強化され、Edge Function単位でのトレース・レイテンシ分析が標準でできるようになった。本番投入前にこれを使ってp95/p99レイテンシを計測し、Edge化すべき処理を定量的に判断すべき。

### 10. TypeScript type safety patterns 2026

- **厳格な型推論の標準化:** TypeScript 5.x系で導入された`satisfies`演算子やconst型パラメータが主流化し、型の広がりを抑えつつ推論の恩恵を受けるパターンが標準になっている。Zodなどのスキーマライブラリとの組み合わせで「実行時検証＝型定義」の一元化が進んでいる。

- **End-to-Endの型安全性:** tRPCやHono RPCのようなフレームワークにより、APIスキーマからクライアント型を自動生成する手法が普及し、フロントエンド・バックエンド間の型不整合によるバグが大幅に減少している。本プロジェクトでもNext.js App Router + Zodの境界検証を徹底すべき。

- **Branded Types / Nominal Typingの活用:** `UserId`や`PropertyId`のような構造的に同じstring型でも意味的に異なるIDを型レベルで区別するBranded Typesパターンが、中〜大規模コードベースで事実上の標準になっている。物件ステータスなどのUnion型管理にも応用価値が高い。

- **AI生成コードに対する型の防波堤としての役割:** LLMによるコード生成が一般化した2026年現在、厳格な型システムは「AIが書いたコードの正しさを検証する最後の防衛線」として再評価されており、`strict: true`やexhaustiveness checking（`never`型による網羅性チェック）の重要性が増している。

- **ビルド時パフォーマンスとの両立:** 型の表現力が増すほどコンパイル速度が低下するトレードオフが顕在化し、`isolatedModules`やプロジェクト分割（`tsconfig`のproject references）によるインクリメンタルビルドの最適化が実務上の必須スキルとなっている。
