# CTO Knowledge - 2026-03-04

## Daily Update (2026-03-04)

### 1. Next.js performance optimization 2026

- **React Server Components の徹底活用:** RSCによりクライアントバンドルサイズを劇的に削減できる。データフェッチをサーバー側に集約し、`use client`ディレクティブは本当に必要な箇所のみに限定することが鉄則。

- **Partial Prerendering (PPR) の本格採用:** Next.js 15以降でstableとなったPPRにより、静的シェルと動的コンテンツを同一ルートで混在させられる。TTFBを維持しつつ動的データを段階的にストリーミングする設計が標準パターンに。

- **`use cache` APIによる細粒度キャッシュ制御:** 従来の`fetch`オプションベースのキャッシュから、関数・コンポーネント単位で宣言的にキャッシュ戦略を指定できる新APIへ移行中。`cacheTag`/`revalidateTag`と組み合わせたオンデマンド再検証が効果的。

- **Turbopackの実用化とビルド高速化:** Next.js 15でTurbopackがデフォルトになり、大規模プロジェクトでのHMRが従来比5〜10倍高速化。ローカル開発体験の向上が生産性に直結する。

- **Core Web Vitals対応：INP（Interaction to Next Paint）の最適化:** 2024年にLCPの代替としてINPが正式指標化。Reactの`startTransition`や`useDeferredValue`を使い、重い状態更新をユーザー操作から切り離すことがSEO・UX両面で必須。

### 2. React Server Components streaming 2026

- **Suspense境界との深い統合:** 2026年時点でRSCとSuspenseの組み合わせが成熟し、コンポーネント単位でのストリーミングが実用段階に。ウォーターフォールを避けるため、非同期コンポーネントの境界設計がアーキテクチャの核心になっている。

- **PPR（Partial Prerendering）の普及:** Next.js 15以降でPPRが安定化し、静的シェルを即時配信しつつ動的部分をストリームする設計が標準化。CDNキャッシュと動的データの両立が容易になった。

- **`use()` hookによるクライアント側ストリーミング消費:** React 19の`use()`がPromiseを直接受け取れるようになり、Server→Clientのデータ受け渡しパターンがシンプル化。`useTransition`との組み合わせでローディングUXの制御が精緻にできる。

- **ストリーミング対応のキャッシュ戦略が複雑化:** `fetch`キャッシュ、Route Cache、Full Route Cacheが層状に存在し、ストリーミングと組み合わせると意図しないキャッシュヒットが問題になりやすい。`revalidateTag`と`unstable_noStore`の適切な使い分けが運用上の重要ポイント。

- **エラーバウンダリとストリーミングの相互作用:** ストリーミング中のサーバーエラーはHTTPステータス200送信後に発生するため、クライアント側の`error.tsx`で捕捉する設計が必須。エラー回復の粒度をどのSuspense境界に委ねるか、設計段階での意思決定が重要。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの成熟と採用拡大:** 2026年時点でtRPCはNext.js/TypeScriptスタックのデファクトに近づいており、型安全なAPI契約をコンパイル時に保証できるため、フルスタックチームの生産性が大幅に向上している。

- **GraphQLの適用範囲の絞り込み:** GraphQLは「すべてのAPIに使う」から「複雑なデータグラフ・複数クライアント対応」に特化する傾向が強まり、BFF（Backend for Frontend）パターンとの組み合わせが主流。オーバーエンジニアリングを避けるためREST/tRPCとの使い分けが重要。

- **RESTはシンプルさの基準として健在:** 外部公開API・マイクロサービス間通信ではRESTのOpenAPI仕様（Swagger 3.1）が標準であり続ける。特にAI/LLMツールチェーンとの連携でOpenAPI仕様の重要性が再評価されている。

- **API-first設計とコード生成の自動化:** Zod/Valibotによるスキーマ定義からTypeScript型・OpenAPIドキュメント・バリデーションを同時生成するアプローチが普及。手書きの型定義は技術的負債になりつつある。

- **エッジ対応とストリーミングAPIの台頭:** Vercel/Cloudflare WorkersなどのエッジランタイムでRSC（React Server Components）やServer-Sent Events対応が進み、従来のリクエスト/レスポンス型設計に加え、ストリーミングファーストなAPI設計パターンが必要になっている。

### 4. serverless edge computing 2026

- **エッジでのAI推論の普及:** 2026年時点で、LLMの量子化・蒸留技術の進歩により、軽量モデルをCDNエッジノードで直接実行するパターンが定着。レイテンシを100ms以下に抑えつつパーソナライズされたレスポンスが可能になっている。

- **Wasm（WebAssembly）がエッジのデファクト実行環境に:** V8 Isolateに加えWasmランタイム（Wasmtime、WASMEdge）がエッジで主流化。言語非依存で安全なサンドボックス実行が可能となり、Rust・Goで書いたロジックをエッジに直接デプロイするケースが急増。

- **エッジDBとデータローカリティの重要性:** Cloudflare D1・Turso等の分散SQLiteや、エッジKVストアの成熟により「エッジでのステートフル処理」が現実的に。ただしグローバル整合性とのトレードオフ設計が依然として最大の課題。

- **コールドスタート問題の実質的な解消:** V8 Isolateのプリウォーム技術とWasmの高速初期化により、コールドスタートは数ms以下が標準に。従来のLambda系（Node.js）から移行するチームが増え、エッジファーストアーキテクチャの採用障壁が低下。

- **オブザーバビリティのエッジ対応が急務:** 分散エッジ環境での分散トレーシング（OpenTelemetry準拠）とログ集約の複雑性が増大。エッジ固有のコールドスタートやリージョン間の挙動差異を可視化できるツールチェーン整備がチームの生産性を左右する。

### 5. authentication security best practices 2026

- **パスキー（Passkey）の標準採用:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の主流となり、フィッシング耐性とUX向上を同時に実現。主要ブラウザ・OSの対応が揃い、新規サービスはパスキーファーストで設計すべき段階に入った。

- **ゼロトラスト + 継続的認証:** ログイン時の一度限りの認証では不十分。セッション中もリスクスコア（デバイス・行動・位置情報）を継続評価し、異常検知時に再認証を要求するアダプティブ認証が必須となっている。

- **OAuthトークン管理の厳格化:** アクセストークンの短命化（5〜15分）＋Refresh Token Rotation の組み合わせが標準。Token Binding やDPoP（Demonstration of Proof of Possession）でトークン窃取への耐性を高めることが推奨される。

- **MFAバイパス攻撃への対策:** SMSベースのOTPはSIMスワップ・リアルタイムフィッシングで陥落するケースが増加。TOTPやハードウェアキー（YubiKey等）への移行、またはフィッシング耐性MFA（FIDO2）を優先すること。

- **シークレット管理とサプライチェーンセキュリティ:** 環境変数のハードコードは論外だが、CI/CDパイプライン経由のシークレットリークが増加傾向。Vault / AWS Secrets Manager 等の動的シークレット発行と、OIDCベースのキーレス認証（GitHub Actions + OIDC等）を組み合わせることで攻撃面を最小化する。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x の Edge Runtime 対応:** Prisma が Vercel Edge / Cloudflare Workers に対応し、従来の Node.js 専用制約が解消。Supabase の pgBouncer と組み合わせることで、サーバーレス環境でのコネクション枯渇問題を根本解決できる。

- **Supabase の RLS（Row Level Security）とPrisma の統合強化:** Prisma からの直接 RLS 制御が改善され、アプリ層でのフィルタリングではなく DB 層での認可を実装しやすくなった。セキュリティとパフォーマンスを両立できる設計が標準化されつつある。

- **Prisma Postgres（マネージドサービス）の台頭:** Prisma が自社マネージドDBサービスを提供開始し、Supabase と直接競合する構図に。ベンダー選定時はロックインリスクとエコシステムの成熟度を比較検討すべき。

- **型安全なクエリビルダーとしての Prisma の地位確立:** `@prisma/client` の型生成精度が向上し、複雑なリレーショナルクエリでも TypeScript の完全な型推論が効く。`drizzle-orm` との比較では、Prisma はスキーマ駆動、drizzle はコード駆動と設計哲学が異なるため用途に応じた選択が重要。

- **Supabase Realtime + ベクトル検索の実用化:** `pgvector` 拡張と Supabase Realtime を組み合わせたリアルタイム AI 機能が実用域に到達。RAG（Retrieval-Augmented Generation）のバックエンドとして Supabase を選択するケースが急増しており、2026年は AI ネイティブ設計の標準スタックになりつつある。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデルの成熟:** WASI 0.2のリリースにより、RustベースのWasmコンポーネントが言語間インターオペラビリティを実現。マイクロサービスの境界をWasmで定義する実用事例が急増している。

- **SIMD・スレッド対応の本格化:** WebAssembly SIMDとShared Memoryが主要ブラウザ・ランタイムで安定化し、RustのSIMD組み込み関数（`std::arch`）がWasm向けに最適化。画像処理・機械学習推論のパフォーマンスがネイティブの80〜95%に到達。

- **コールドスタート問題の解消:** WasmtimeのAOT（事前コンパイル）とCraneliftバックエンドの改善により、エッジ・サーバーレス環境でのコールドスタートが<1msに。Fastly/Cloudflare Workersでのデプロイ標準として定着しつつある。

- **ガベージコレクションなしのメモリ優位性:** RustのゼロコストアブストラクションとWasmの線形メモリモデルの相性が最良。Go/Kotlinと比較してメモリフットプリントが50〜70%小さく、モバイル・IoTエッジへの展開で競争優位。

- **Rust→Wasm toolchainの成熟:** `wasm-bindgen`・`wasm-pack`・`cargo-component`の統合が進み、ビルドパイプラインの複雑性が大幅低下。Next.jsプロジェクトへのRust Wasmモジュール統合が数行の設定で可能になっている。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** デフォルトでServer Componentsを使い、クライアント状態が必要な末端コンポーネントのみ`'use client'`を追加する。バンドルサイズを最小化し、初期描画を高速化できる。

- **Partial Prerendering (PPR) の活用:** 静的シェルと動的スロットを同一ルートで共存させるPPRが安定版になりつつあり、`Suspense`境界を適切に設計することでStreaming SSRの恩恵を最大化できる。

- **データフェッチの並列化と重複排除:** `fetch`のRequest Memoizationを活用し、同一リクエストの重複を避けつつ、`Promise.all`で独立したフェッチを並列実行することがパフォーマンスの鍵。

- **Server Actions によるミューテーション統一:** `useActionState` + Server Actionsの組み合わせでAPI Routeを減らし、型安全なフォーム処理を実現。楽観的更新（`useOptimistic`）も合わせて使うとUXが向上する。

- **キャッシュ戦略の明示化:** Next.js 15以降はデフォルトキャッシュが無効化傾向にあり、`revalidatePath` / `revalidateTag` / `unstable_cache`を意図的に設計しないとパフォーマンスが劣化するため、キャッシュ設計をアーキテクチャ段階で明確化することが重要。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge Runtime の採用を選択的に:** Edge Functionsは低レイテンシに優れるが、Node.js APIの制約（fsモジュール不可、実行時間制限）があるため、全APIをEdgeに移行せず、地理的分散が効果的なルーティング・認証・A/Bテストに限定する。

- **ポイント2: Fluid Compute でコールドスタートを排除:** Vercel 2025年後半に導入されたFluid Computeにより、Edge/Serverlessのハイブリッドモデルが実現。リクエスト間でインスタンスを再利用でき、従来のコールドスタート問題が大幅に軽減された。

- **ポイント3: KV・R2との組み合わせでステートレス問題を解決:** Edge FunctionsはステートレスなためVercel KV（Redis）やCloudflare R2をセッション・キャッシュ層として活用する設計が標準化。特にユーザー認証トークンの高速検証に有効。

- **ポイント4: `edge` vs `nodejs` ランタイムの明示的指定が必須:** Next.js App Routerでは`export const runtime = 'edge'`の指定漏れが本番バグの温床。CI/CDパイプラインにランタイム整合性チェックを組み込み、意図しないNode.jsフォールバックを防ぐ。

- **ポイント5: ISRとEdge Middlewareの責務分離:** データフェッチはISR（`revalidate`設定）でキャッシュし、パーソナライゼーション・ロケール判定はEdge Middlewareで行う2層構造が高パフォーマンスの定石。両方をEdgeで実行するとオリジンリクエストが増加しコスト増につながる。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** プリミティブ型に意味的な区別を加える`Brand<T, K>`パターンが標準化し、`UserId`と`ProductId`を誤って混用するようなバグをコンパイル時に防ぐ設計が主流になっている。

- **satisfies 演算子の活用:** TypeScript 4.9以降の`satisfies`が広く定着し、型推論を保持しながら型チェックを行えるため、`as`キャストによる型安全性の損失を避けられる実践が一般化している。

- **Template Literal Types によるAPI契約:** APIルートやイベント名を`\`/users/${string}\``のようにリテラル型で表現することで、文字列ベースのインターフェースでも型安全性を確保するパターンが拡大している。

- **Zod + tRPC によるランタイム型保証:** コンパイル時の型と実行時のバリデーションを一元管理するスキーマファーストなアプローチが事実上の標準となり、フロントエンド・バックエンド間の型共有コストが大幅に削減されている。

- **NoInfer ユーティリティ型の活用:** TypeScript 5.4で導入された`NoInfer<T>`により、ジェネリック関数での意図しない型推論の広がりを制御できるようになり、より予測可能なAPIを設計できる。
