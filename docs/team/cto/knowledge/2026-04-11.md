# CTO Knowledge - 2026-04-11

## Daily Update (2026-04-11)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチ・重いロジックはすべてサーバーコンポーネントに移動する。`"use client"` を境界として意識的に引くことで、TTI（Time to Interactive）を大幅に改善できる。

- **Partial Prerendering (PPR) の本番適用:** Next.js 15以降で安定化したPPRにより、静的シェルを即時配信しつつ動的コンテンツをストリーミングできる。SPA的な体験とSSGのパフォーマンスを両立できる現時点で最も実用的なアーキテクチャ選択肢。

- **`<Image>` / `<Script>` / フォントの最適化を徹底:** `next/image` のサイズ最適化・lazy loading、`next/font` によるレイアウトシフト（CLS）ゼロ化は今や基本要件。LCP改善に直結するため必ずCore Web Vitalsで計測・検証する。

- **Route SegmentのキャッシュとRevalidation戦略の設計:** `fetch` キャッシュ・`revalidate` 設定・`unstable_cache` の使い分けを明確にする。過剰なキャッシュ無効化がサーバー負荷急増の原因になるため、データの鮮度要件ごとに戦略を分けて設計する。

- **Turbopack + バンドル分析の活用:** Next.js 15でTurbopackがデフォルト化し、ローカルのHMRは劇的に高速化。本番ビルドでは `@next/bundle-analyzer` を定期実行し、不要な依存関係・重複モジュールを定量的に把握して削除する習慣を持つ。

### 2. React Server Components streaming 2026

- **Suspense境界の戦略的配置が鍵:** RSCストリーミングでは、Suspenseの粒度設計がTTFB（初回バイト到達時間）とLCP（最大コンテンツ描画）に直結する。クリティカルパスのコンポーネントは先にストリーミングし、重いデータフェッチを伴う部分は後続ストリームに分離するパターンが定着してきた。

- **PPR（Partial Pre-Rendering）の実用化:** Next.js 15以降でPPRが安定化し、静的シェルを即座に配信しつつ動的コンテンツをストリーミングで埋め込むハイブリッド戦略が主流になりつつある。エッジキャッシュと組み合わせることでCDNコストを抑えながら動的体験を提供できる。

- **データフェッチのウォーターフォール問題は依然として最大の落とし穴:** Server Componentで`await`を直列に並べると、RSCの恩恵が消える。`Promise.all`による並列フェッチ、もしくはReact 19の`use()`フックを活用したfetch-as-you-renderパターンへの移行が必須。

- **Server ActionsとStreamingの統合でFormのUXが刷新:** 2026年時点では、Server Actionsにストリーミングレスポンスを組み合わせることで、フォーム送信中のリアルタイムフィードバック（進捗、部分結果）がクライアントサイドJSなしで実現可能になった。

- **バンドルサイズゼロへの収束:** RSCで業務ロジックをサーバー側に移行した結果、クライアントJSを50-80%削減できるプロジェクトが増加。ただし`'use client'`境界の設計ミスによる意図しないバンドル膨張が新たな技術負債として浮上しており、バンドルアナライザーの定期監査が不可欠。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの成熟とフルスタック型安全性の標準化:** tRPC v11がNext.js App Routerとの統合を深め、型定義を共有するモノレポ構成でのエンドツーエンド型安全がデファクトになりつつある。バックエンド・フロントエンド間のスキーマ重複が大幅に削減できる。

- **GraphQL採用の二極化:** 大規模データグラフ（Meta、Shopify等）では引き続き強力だが、小〜中規模プロダクトではtRPCやREST+OpenAPIに回帰する流れが顕著。オーバーエンジニアリングを避けるチームが増えている。

- **REST+OpenAPI 3.1の再評価:** `zod-openapi` や `@hono/zod-openapi` 等のツールでスキーマファーストなREST APIが書きやすくなり、自動生成クライアント（`openapi-ts`）と組み合わせることでtRPCに近い開発体験が実現できる。

- **エッジランタイム対応がAPI設計の制約に:** Cloudflare Workers・Vercel Edge等のエッジ環境ではNode.js APIの制限があるため、HonoやIttyRouterのような軽量フレームワークが選ばれる場面が増加。アーキテクチャ選定時にランタイム互換性を最初から考慮すべき。

- **AI統合とAPIデザインの変化:** LLMツール呼び出し（Function Calling / MCP）のためにAPIをマシンリーダブルに設計する要求が増加。OpenAPIスキーマをそのままMCPサーバーに変換するパターンが普及し始めており、API設計が「人間向け」と「エージェント向け」の二層になりつつある。

### 4. serverless edge computing 2026

- **エッジでのAI推論が主流化:** 2026年はLLMの軽量化（量子化・蒸留）が進み、Cloudflare Workers AIやVercel Edge Functionsで直接モデルを実行するパターンが定着。レイテンシを50ms以下に抑えつつリアルタイム推論が可能になった。

- **Durable ObjectsとWebAssemblyによるステートフルエッジ:** 従来「ステートレス」だったエッジが、Durable ObjectsやWASMのコンポーネントモデルによりセッション・リアルタイム同期をエッジ側で完結できる設計へ移行。バックエンドへのラウンドトリップを大幅削減できる。

- **ベンダーロックイン対策としてのWinterCGとWASI標準化:** WinterCG（Web-interoperable Runtimes Community Group）の仕様が成熟し、Cloudflare・Deno・Bun間でポータブルなエッジコードが書けるようになった。技術選定の際はWinterCG準拠かを確認すべき。

- **コールドスタート問題の実質的解消:** V8 SnapshotやWASMのAOTコンパイルにより、主要プラットフォームのコールドスタートは1ms以下が標準に。ただしNode.js互換レイヤーを使う場合は依然として数十msのオーバーヘッドが発生するため、依存関係の選定が重要。

- **コスト構造の変化とオブザーバビリティの課題:** エッジ実行単価は低いが、グローバル分散による**トレース収集の複雑さ**がボトルネックになりやすい。OpenTelemetryのエッジ対応とサンプリング戦略を事前設計しないと、障害調査コストが跳ね上がる。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準採用:** FIDO2/WebAuthn ベースのパスキーがパスワード認証を事実上置き換えつつある。Google・Apple・Microsoft のエコシステム統合が成熟し、ユーザー体験を損なわずにフィッシング耐性を確保できる。

- **MFA疲労攻撃への対策:** プッシュ通知型MFAへのスパム攻撃（MFA fatigue）が一般化しており、番号照合（Number Matching）やコンテキスト付き承認画面の実装が必須となった。

- **継続的認証（Continuous Authentication）:** ログイン時の一点認証ではなく、デバイス指紋・行動バイオメトリクス・セッション中のリスクスコアを継続評価するゼロトラスト型の認証モデルが実運用レベルに達している。

- **セッショントークンの短命化とDPoP:** OAuth 2.0 の DPoP（Demonstrating Proof of Possession）によりトークン窃取リスクを大幅に低減できる。アクセストークンは15分以下、リフレッシュトークンにもローテーションを適用するのが現在のベストプラクティス。

- **サプライチェーン経由の認証基盤侵害への備え:** IdP やサードパーティ認証ライブラリへの依存は単一障害点になりうる。重要なサービスでは認証フローの監査ログを自前で保持し、異常なトークン発行パターンを検知できる仕組みを持つことが求められる。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応:** Prisma 6ではEdge RuntimeとのネイティブD1/Cloudflare連携が成熟し、Next.js App RouterのServer Componentsから直接型安全なクエリを実行できる。`@prisma/adapter-pg`経由でSupabaseと組み合わせることでコネクションプーリングの設定が大幅に簡略化された。

- **Supabase Realtime + RLSの組み合わせが本番実用レベルに:** Row Level Security（RLS）とRealtime subscriptionの統合が安定し、クライアント側でのデータフィルタリングロジックを排除できる。ただしRLSポリシーのインデックス設計を怠るとN+1的なパフォーマンス劣化が発生するため、`EXPLAIN ANALYZE`による検証が必須。

- **Prisma Accelerate（旧Data Proxy）によるサーバーレス最適化:** Vercel/Cloudflare等のサーバーレス環境でのコネクション枯渇問題に対し、Prisma Accelerateがグローバルキャッシュ＋コネクションプールを提供。Supabase側の`pgbouncer`と併用する場合は二重プーリングにならないよう設定に注意。

- **型安全なマイグレーション管理の重要性:** `prisma migrate dev`と`supabase db push`の混在運用はスキーマのdriftを招きやすい。2026年時点では**どちらか一方をsource of truth**と定め、もう一方は読み取り専用で参照するアーキテクチャが推奨される。

- **Supabase Storage + pgvectorによるRAG基盤の内製化:** `pgvector`拡張の成熟により、外部ベクターDBを持たずSupabase単体でRAGパイプラインを構築するケースが増加。Prismaからpgvectorの`<->`演算子を直接使う場合は`$queryRaw`が必要となるため、型安全性との兼ね合いを設計段階で決めておくべき。

### 7. WebAssembly Rust performance 2026

- **WASI Preview 2の本格普及:** 2026年はWASI Preview 2（Component Model）が標準化され、RustのWASMコンポーネントが言語間で再利用可能になった。wasmtime・Fastlyなどのランタイムが本番対応し、サーバーレスエッジ環境でのRust WASMデプロイが現実的な選択肢となっている。

- **GCなしのメモリ効率が競争優位に:** RustのWASMバイナリはGoやC#と比較してGCオーバーヘッドがなく、コールドスタート時間が数ms以下。特にCloudflare WorkersやFastly Computeでのレイテンシ要件が厳しいワークロードでRustが第一選択になりつつある。

- **SIMD・スレッド対応の成熟:** WebAssembly SIMDとShared Memoryのブラウザサポートが安定し、Rustの`rayon`ベースの並列処理がWASMで動作可能に。画像処理・暗号化・ML推論などのCPU集約タスクでネイティブ比90%以上のパフォーマンスを達成するケースが増えている。

- **`wasm-bindgen`から`wit-bindgen`へのシフト:** ブラウザ向けの`wasm-bindgen`に加え、Component Model準拠の`wit-bindgen`が普及。型安全なインターフェース定義でRustコンポーネントをJavaScript・Python・他言語から呼び出せる標準的なパターンが確立されている。

- **ビルドサイズ最適化の自動化:** `wasm-opt`（Binaryen）・`twiggy`によるサイズ分析がCIパイプラインに組み込まれ、LTO＋`opt-level='s'`設定で100KB以下のバイナリが当たり前に。ただし依存クレートの選定（`std`排除、`no_std`対応）が依然として重要なボトルネック。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点では「必要な時だけ `'use client'`」が定石。データフェッチはServer Componentで完結させ、インタラクション境界を最小化することでバンドルサイズを大幅削減できる。

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降でStableになったPPRにより、静的シェルと動的ストリームを1ルートで共存させられる。`loading.tsx` + Suspense境界の設計がパフォーマンスの肝になる。

- **Server Actions でAPI Routes を置き換える:** フォーム送信・ミューテーション系の処理はServer Actionsに集約し、不要なAPI Routeエンドポイントを削減。型安全性が自動で保たれ、ネットワークラウンドトリップも最適化される。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15の `use cache` を関数レベルで付与することで、ページ全体ではなく「この関数の結果だけ」をキャッシュできる。従来の `revalidate` より意図が明確でバグを生みにくい。

- **Turbopack が実用段階に:** Dev環境では既にデフォルト化が進んでおり、大規模プロジェクトでのHMR速度が数倍改善。本番ビルドへの移行可否をCI時間と照らし合わせながら評価すべきタイミング。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択的活用:** Edge FunctionsはNode.js Runtimeより起動レイテンシが低い（コールドスタート ~0ms）が、利用可能なAPIに制限がある。DBアクセスやファイルシステム操作が不要なミドルウェア・認証・A/Bテストに絞って適用するのが最適解。

- **Fluid Compute（旧Serverless Functions）との使い分け:** 2025年後半にVercelが導入したFluid Computeはアイドル時間を課金対象外にした新モデル。CPUバウンドな処理はEdgeより通常のServerless（Fluid Compute）の方がコスト効率が良いケースがあり、盲目的にEdgeに寄せない設計判断が必要。

- **KV・R2との組み合わせによるステート管理:** Edge FunctionsはステートレスだがVercel KV（Redis互換）やCloudflare R2をエッジ近傍で参照することで、セッション管理やフィーチャーフラグのレイテンシを数msレベルに抑えられる。

- **ISR（Incremental Static Regeneration）との併用:** `next/headers`や`cookies()`を使うとページがEdge Runtimeに移行するが、`revalidate`オプションと組み合わせることでEdge上でもキャッシュ戦略を維持できる。動的に見えて実は静的なコンテンツはEdge Cacheに乗せるのが原則。

- **観測性（Observability）の整備が前提:** Vercel Analyticsだけでは不十分で、OpenTelemetry対応のトレーシング（Axiom等）をEdge Functionsに組み込まないとボトルネックの特定が困難。最適化の前に計測基盤を確立することが2026年時点でのベストプラクティス。

### 10. TypeScript type safety patterns 2026

- **Template Literal Types の高度活用:** 文字列リテラル型を組み合わせたAPIルート定義や国際化キーの型付けが標準化され、ランタイムエラーをコンパイル時に検出できるパターンが定着している。

- **`satisfies` 演算子の普及:** `as const` との組み合わせで型推論の精度を保ちながらスキーマ準拠を強制できるため、設定オブジェクトやフォームスキーマ定義で広く使われるようになっている。

- **Branded Types によるドメイン安全性:** `UserId`・`OrderId` のような名目型をユーティリティで生成し、`string` の誤混入をコンパイル時にブロックする手法がDDD実践プロジェクトで浸透している。

- **型レベルバリデーションとZodの深化:** Zodスキーマから型を導出する `z.infer<>` パターンに加え、`@effect/schema` や Valibot など型安全性とバンドルサイズを両立するライブラリへの移行が進んでいる。

- **`noUncheckedIndexedAccess` の標準化:** 配列・オブジェクトのインデックスアクセス時に `T | undefined` を返す厳格フラグが、新規プロジェクトの `tsconfig.json` デフォルトになりつつあり、実行時のundefined参照エラーを大幅に削減している。
