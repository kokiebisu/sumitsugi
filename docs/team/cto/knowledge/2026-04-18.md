# CTO Knowledge - 2026-04-18

## Daily Update (2026-04-18)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチはサーバーコンポーネントに集約し、`'use client'`は真にインタラクティブな部分のみに限定する。

- **PPR（Partial Prerendering）の本番投入:** Next.js 15+で安定化したPPRにより、静的シェルと動的コンテンツを同一ルートで混在させ、TTFBとLCPを同時に改善できる。

- **Turbopackへの移行:** Webpackから Turbopackへの移行でローカルビルドが最大10倍高速化。`next dev --turbopack`で段階的移行が可能で、開発体験の改善がデプロイ頻度向上に直結する。

- **`<Image>`と`<Link>`の最適化強化:** Next.js 16では画像の自動フォーマット選択（AVIF優先）とリンクのプリフェッチ戦略が改善。`priority`と`loading`属性の使い分けがCWV（Core Web Vitals）に直接影響する。

- **Edge Runtimeの戦略的使用:** 認証チェックやA/Bテストなどレイテンシーが重要なロジックはEdge Runtimeに移し、Vercel/Cloudflare Workersで地理的分散を活用することで、APIレスポンスを100ms以下に抑えられる。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化:** 2026年はRSCのSuspenseネストが精緻化され、コンポーネント単位でのストリーミング制御が標準化。ウォーターフォール排除のため、データフェッチを末端コンポーネントに近づける設計が主流になっている。

- **PPR（Partial Prerendering）の本番採用加速:** Next.js 15+でPPRがStableになり、静的シェルを即時配信しつつ動的部分をストリームで差し込むハイブリッドが実用的なデフォルトに。CDNキャッシュとの相性が良くTTFBが大幅改善。

- **Server Actionsとのストリーミング統合:** フォーム送信後のUI更新もストリーミングで返せるようになり、楽観的更新との組み合わせでSPAに遜色ない体感速度を実現。`useOptimistic`との設計パターンが確立された。

- **バンドルサイズのゼロ化戦略:** RSCによりサーバー専用ロジックをクライアントバンドルから完全排除できる。依存ライブラリの選定基準として「RSC対応か否か」が重要な評価軸になっている。

- **エラー境界とストリーミングの共存設計:** ストリーミング中の部分的エラーをError Boundaryで隔離しUX劣化を局所化するパターンが成熟。Sentryなどのモニタリングもサーバー/クライアント境界を跨いだトレースに対応済み。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** tRPCはNext.js + TypeScriptスタックで事実上の標準になりつつあり、スキーマ定義不要でエンドツーエンドの型安全性を実現できる点が、小〜中規模チームに特に刺さっている。

- **GraphQLの適用範囲の明確化:** GraphQLは「複数クライアントが異なるデータ形状を必要とする」ケース（BFF、公開API）に特化し、社内APIやシンプルなCRUDにはオーバーエンジニアリングとみなされる傾向が強まっている。

- **REST + OpenAPI の再評価:** LLMエージェントやSDK自動生成との親和性から、OpenAPI 3.1仕様に基づくRESTが見直されている。型生成ツール（`openapi-typescript`等）の成熟でtRPC並みの型安全性が確保可能になった。

- **エッジ・ストリーミング対応:** 2026年はServer-Sent Events（SSE）とHTTP Streamingが主流化し、REST/tRPCどちらもリアルタイム対応が設計上の必須要件になっている。GraphQL Subscriptionsとの差別化が薄れつつある。

- **プロトコル選定の実用基準:** チーム規模と外部公開有無で決める—「社内・TypeScript統一」→tRPC、「外部公開・多言語クライアント」→REST+OpenAPI、「複雑なデータグラフ・複数BFF」→GraphQL。

### 4. serverless edge computing 2026

- **エッジでのAI推論が主流化:** 2026年はLLMの量子化・蒸留技術の進化により、エッジノードでの小型モデル推論が実用レベルに達し、レイテンシ削減とデータプライバシー確保を両立できる。

- **WebAssembly（WASM）がエッジランタイムの標準に:** Cloudflare Workers・Fastly Compute等がWASMを主軸に据え、言語非依存でコールドスタートほぼゼロの実行環境が普及。V8 Isolateからの移行が加速している。

- **エッジDBの成熟（SQLite-at-the-edge）:** Cloudflare D1・Turso等のエッジ分散SQLiteが本番利用に耐えるレベルになり、「エッジでステートレス」という制約が緩和されつつある。

- **オブザーバビリティが最大の課題:** エッジノードが数百拠点に分散するため、従来の集中型ログ・トレーシングが機能しない。OpenTelemetryのエッジ対応と軽量サンプリング戦略の設計が必須投資となる。

- **ベンダーロックインリスクの再評価:** WinterCG標準により相互運用性は向上したが、D1/KV/Queues等のエッジ周辺サービスへの依存が深まっており、ポータビリティ設計をアーキテクチャ初期段階で意識すべき。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準化:** FIDO2/WebAuthnベースのパスキーが主流となり、パスワードレス認証が実用段階に入った。大手プラットフォームの対応が揃い、新規プロダクトはパスワード認証をデフォルトにすべきでない。

- **セッショントークンの短命化とリフレッシュ戦略:** アクセストークンの有効期限を15分以内に抑え、リフレッシュトークンはRotating方式で実装する。トークン漏洩時の被害範囲を最小化するため、Redis等でサーバーサイドの無効化リストを管理する。

- **デバイスフィンガープリントによる継続的認証:** ログイン時のみでなく、セッション中も端末・ネットワークの異常を検知するリスクベース認証が必須になった。突然の地理的変化やUser-Agent変更をリアルタイムで検知してチャレンジを要求する。

- **サプライチェーン攻撃への対策（依存ライブラリ監査）:** 認証ライブラリ（NextAuth等）の脆弱性は即座に全ユーザーに影響する。`bun audit`やDependabotを必ずCIに組み込み、認証関連パッケージは固定バージョン管理を徹底する。

- **ゼロトラスト前提のAPI認証:** JWTのアルゴリズム混乱攻撃（`alg: none`等）対策として、検証時はアルゴリズムを明示的に指定する。内部サービス間通信でもmTLSまたは短命トークンで認証し、「内部ネットワークだから安全」という前提を排除する。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応:** Prisma 6以降はCloudflare WorkersやVercel Edge Functionsでのネイティブ実行が安定し、Supabaseと組み合わせたサーバーレス構成がプロダクション品質に達した。コネクションプーリングはSupabase Poolerに委譲するのが定石。

- **Row Level Security (RLS) の設計が鍵:** SupabaseのRLSをPrismaと併用する場合、Prismaはbypass-RLSの`service_role`で動くためアプリ層での権限制御が必須。RLSはUI直接アクセス（Supabase JS）用、Prismaはサーバー処理用と役割を分離すると安全。

- **Supabase Branchingによる開発フロー改善:** 2025年にGAとなったDatabase Branchingで、PRごとに独立したDBプレビュー環境が持てる。マイグレーション衝突のリスクが下がり、チーム並行開発との相性が良い。

- **PrismaのTyped SQL（`$queryRaw`代替）:** Prisma 5.19+の`@prisma/client/sql`で型安全なraw SQLが書けるようになった。Supabaseの複雑なPostgres機能（JSONBクエリ、全文検索）をORMの制約なしに活用しつつ型安全性を保てる。

- **接続数上限への注意:** SupabaseのFreeプランは接続数60が上限。Prismaのコネクションプールデフォルト設定のままだとすぐ枯渇するため、`DATABASE_URL`に`?pgbouncer=true&connection_limit=1`を設定するのが2026年現在のベストプラクティス。

### 7. WebAssembly Rust performance 2026

- **Component Model の成熟:** WebAssembly Component Model (WIT/wasm-component) が2026年に実用段階へ移行し、RustコンポーネントをJS/Pythonから型安全に呼び出せるため、モジュール間のFFIオーバーヘッドが大幅に削減された。

- **WASI Preview 2 による本番運用:** WASI Preview 2のソケット・ファイルシステム対応により、RustのWasmバイナリがサーバーサイドでも本番稼働可能となり、コールドスタートはネイティブ比で約1.5〜2倍以内に収まっている。

- **SIMD・スレッド拡張の普及:** WebAssembly SIMDとShared Memoryスレッドの主要ブラウザ完全対応により、Rustの`rayon`相当の並列処理がWasm上でも動作し、画像処理・暗号化などのCPU負荷処理でネイティブの70〜90%性能を達成できる。

- **ツールチェーン最適化（`wasm-opt` + LTO）:** `wasm-pack`＋`wasm-opt` O3＋Link Time Optimizationの組み合わせでバイナリサイズが従来比30〜50%削減され、初期ロード時間の短縮が体感パフォーマンスに直結する。

- **Wasmtime/WasmEdge ランタイムの高速化:** サーバーサイドランタイムのAOTコンパイル対応により、Rust製WasmモジュールはColdStart後はネイティブバイナリと遜色ない実行速度を実現しており、エッジコンピューティングでの採用が加速している。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** クライアントコンポーネントは状態・インタラクションが必要な最小単位に限定し、データフェッチはすべてServer Componentsで行う。バンドルサイズ削減とTTFBの大幅改善が実現できる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェル＋動的ストリーミングの組み合わせにより、`<Suspense>` 境界単位でキャッシュ戦略を使い分ける。ISRの代替として段階的に移行が進んでいる。

- **`use cache` ディレクティブによる宣言的キャッシュ:** `unstable_cache` から `use cache` への移行が主流に。関数・コンポーネント単位でキャッシュライフタイムを明示でき、キャッシュ設計がコードレベルで可視化される。

- **Server Actions の責務分離:** フォーム送信・楽観的更新に加え、`useActionState` と組み合わせたエラーハンドリングパターンが定着。API Routes の代替として、認証チェックと入力バリデーション（Zod）をAction内に集約するのがベストプラクティス。

- **`after()` API による非同期サイドエフェクト分離:** レスポンス送信後にログ・分析・メール送信を実行できる `after()` が安定化。ユーザー応答速度に影響しないバックグラウンド処理の標準パターンとなっている。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択戦略:** Node.js RuntimeとEdge Runtimeの使い分けが重要で、コールドスタートを最小化するためにステートレスな認証・リダイレクト処理はEdgeに、DB接続が必要な処理はNode.jsに分離する。

- **Fluid Computeの活用:** Vercel 2025〜2026のFluid Computeにより、Edge Functionsがリクエスト間でCPUをスリープせず継続実行できるため、ストリーミングレスポンスのコスト効率が大幅に改善された。

- **Middleware最適化:** Next.js Middlewareはすべてのリクエストを通過するため、マッチャー設定（`config.matcher`）で静的アセットを除外し、実行時間を5ms以内に抑えることがP99レイテンシ改善の鍵。

- **KV/キャッシュ戦略:** Vercel KVやEdge Configを活用したフラグ管理・A/Bテストをエッジで実施し、`Cache-Control: stale-while-revalidate`と組み合わせることでオリジンへの負荷を90%以上削減できる。

- **バンドルサイズ制限の厳守:** Edge FunctionsはWasm含め1MBの制限があり、`@next/bundle-analyzer`で定期監視し、重量ライブラリ（moment.js等）をEdge非対応として分離することがデプロイ失敗を防ぐ実務的ベストプラクティス。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `string` や `number` をそのまま使わず `UserId`, `Email` などのブランド型で意味的安全性を担保するパターンが定着。実行時コストゼロで型システムによるドメイン境界を強制できる。

- **`satisfies` 演算子の積極活用:** 型推論を壊さずに型チェックを行う `satisfies` が設定オブジェクトやバリアント定義の主流に。`as const satisfies T` の組み合わせで過剰な型アサーションを排除できる。

- **Template Literal Types によるAPI契約:** エンドポイントパスやイベント名を `\`/api/${string}\`` 形式でモデル化し、ランタイム前にルーティングミスを検出するパターンが実用段階に入った。

- **`noUncheckedIndexedAccess` の必須化:** 配列・オブジェクトインデックスアクセスで自動的に `T | undefined` を返すこのフラグがプロダクション標準に。有効化で発見されるバグは驚くほど多い。

- **`infer` + Conditional Types による外部型の自動抽出:** Prisma や Zod スキーマから `z.infer<typeof schema>` で型を派生させ、手書き型定義ゼロを目指すアーキテクチャが主流。型の「単一信頼源」を外部スキーマに集約することで型ドリフトを根絶できる。
