# CTO Knowledge - 2026-04-16

## Daily Update (2026-04-16)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチとロジックをサーバーサイドに移動する設計が標準化。`"use client"` の使用箇所を意識的に絞り込むことが重要。

- **Partial Prerendering (PPR) の本格採用:** 静的シェルと動的コンテンツを同一ルートで混在させるPPRが安定版に。TTFBを犠牲にせずパーソナライズされたコンテンツを配信できるため、ECサイトや会員制サービスに特に有効。

- **`next/image` と `next/font` によるCWV改善:** LCP・CLSの最適化はもはや手動チューニングではなくフレームワーク機能で対応。Turbopackへの移行により開発ビルドが大幅高速化され、体験の向上がそのまま本番品質に直結。

- **Edge Runtimeの選択的利用:** 認証・リダイレクト・A/Bテストなどレイテンシ敏感な処理はEdge Middlewareへ移動。ただしNode.js APIが使えない制約があるため、ユースケースを見極めた使い分けが必要。

- **Bundle Analyzerによる継続的な依存関係監査:** `@next/bundle-analyzer` やTurbopackの組み込みトレースで肥大化したクライアントチャンクを可視化し、dynamic importと適切なコード分割で初期ロードを最適化するサイクルを開発プロセスに組み込むことが推奨。

### 2. React Server Components streaming 2026

- **Suspense境界の戦略的配置が競争優位に:** RSCのストリーミングはSuspense境界ごとに段階的にHTMLを送信するため、ファーストバイト（TTFB）を最小化しつつLCPを改善できる。粒度の細かい境界設計が体感パフォーマンスを左右する。

- **PPR（Partial Prerendering）が本番ワークフローの標準へ:** Next.js 15以降でStableになったPPRにより、静的シェルを即時配信しつつ動的スロットをストリーミングで埋める構成が実用的になった。CDNキャッシュと動的コンテンツのトレードオフを解消する設計パターンとして定着しつつある。

- **Server Actions + Optimistic UIの組み合わせがUXの基軸に:** `useOptimistic`とServer Actionsを組み合わせることで、ネットワーク遅延を隠蔽しながらサーバー権威のデータモデルを維持できる。クライアント状態管理ライブラリへの依存を大幅に削減できる。

- **ストリーミング中のエラーハンドリングが実装の要点に:** ストリーミング開始後はHTTPステータスコードを変更できないため、エラーはHTMLストリーム内のクライアントサイドエラー境界で処理する設計が必須。`error.tsx`の配置とSuspense境界の組み合わせを事前に設計しておくことが重要。

- **Edge Runtimeとの相性でインフラ選択が変わる:** RSCストリーミングはNode.js Runtimeでは完全動作するが、Edge Runtimeでは一部のNode.js APIが使用不可。Cloudflare WorkersやVercel Edgeへのデプロイを検討する場合、依存ライブラリのEdge互換性を早期に検証することが開発後半での手戻りを防ぐ。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年現在、Next.jsエコシステムでtRPCが主流化しており、TypeScriptの型定義をサーバー・クライアント間で共有することでランタイムエラーを大幅削減できる。スキーマ定義の二重管理が不要になる点が特に小〜中規模チームに刺さっている。

- **GraphQLのユースケース絞り込み:** GraphQLは「何でも使えるAPI」から「複雑なデータグラフ・マルチクライアント最適化が必要な場面専用」へと位置付けが明確化。過剰なOver-fetchingとスキーマ肥大化への反省から、シンプルなCRUDにGraphQLを使うアンチパターンは避けるべき。

- **REST+OpenAPIの再評価:** Zodベースのスキーマ検証とOpenAPI自動生成（Hono、ElysiaJS等）により、RESTが型安全性を取り戻した。外部公開APIや言語横断チームでは依然としてRESTが最も現実的な選択肢。

- **Edge RuntimeとAPIレイテンシ最適化:** Cloudflare Workers・Vercel Edge Functionsの普及により、APIルートをユーザー近傍で実行するアーキテクチャが標準化。cold startの最小化と地理分散を前提にAPIの粒度設計が必要になっている。

- **AIエージェント対応としてのMCP/Tool API設計:** LLMエージェントからの呼び出しを想定したAPI設計が新たな要件として浮上。従来のREST/GraphQLに加え、Model Context Protocol（MCP）準拠のツール定義を並行提供するハイブリッド構成が2026年の現場で増加している。

### 4. serverless edge computing 2026

## Serverless Edge Computing 2026 — CTO視点のトレンド

- **WebAssembly (Wasm) がエッジの標準ランタイムに:** Cloudflare Workers・Fastly Compute@Edgeを中心に、Wasmがコンテナ不要の軽量ポータブル実行環境として定着。コールドスタートがほぼゼロになり、Node.js依存から脱却するプロジェクトが急増している。

- **エッジでのAI推論が実用フェーズへ:** 小型LLM（1〜7Bパラメータ）やONNXモデルをエッジノードで直接実行するパターンが普及。レイテンシ削減と個人データの国外送信回避を両立できる点が、特にEU/日本市場で評価されている。

- **ステートフルエッジの台頭:** Cloudflare Durable Objects・Vercel KV等により「エッジ＝ステートレス」の制約が崩れた。リアルタイムコラボ・セッション管理をエッジ完結で実装できるが、一貫性モデルの設計ミスがバグの温床になるため注意が必要。

- **エッジ・オリジン間の責務分離が設計の核心に:** 全処理をエッジに寄せると可観測性・デバッグが困難になる。「認証・パーソナライズはエッジ、ビジネスロジック・DBはオリジン」という役割分担を明示的に設計するアーキテクチャパターンが成熟しつつある。

- **ベンダーロックインリスクの顕在化:** Cloudflare・Vercel・AWS Lambda@Edgeそれぞれの独自APIへの依存が深まっており、WinterCG（Web-interoperable Runtimes Community Group）標準への準拠度をスタック選定の重要指標とすることを推奨する。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** FIDO2/WebAuthn標準に基づくパスキーがパスワードレス認証の主流となり、フィッシング耐性が根本的に向上。主要プラットフォーム（Apple/Google/Microsoft）のネイティブサポートにより、UXを損なわずに導入可能になった。

- **セッション管理のゼロトラスト化:** 「一度認証したら信頼する」モデルから脱却し、リクエストごとにコンテキスト（デバイス・位置・行動パターン）を評価する継続的認証が標準化。JWTの有効期限を短く保ち（15分以下）、リフレッシュトークンのローテーションを必須とする。

- **AIを活用した異常検知の普及:** ユーザーの行動バイオメトリクス（タイピングパターン・マウス動作）をMLで学習し、アカウント乗っ取りをリアルタイム検出するアダプティブ認証が実用段階に。静的なMFAだけでは不十分な時代へ。

- **サプライチェーンリスクとしての認証ライブラリ管理:** OAuthライブラリやIDPクライアントの依存関係を定期監査し、既知のCVEへの対応を自動化するSBOM（ソフトウェア部品表）管理が必須。Auth0/Cognitoなどマネージドサービスへの依存は実装リスクを下げるが、ロックインリスクとのトレードオフを設計段階で評価する。

- **量子耐性暗号への準備フェーズ開始:** NIST PQC標準（ML-KEM等）の確定を受け、長期的なセッショントークンや証明書の暗号アルゴリズムを量子耐性対応に移行するロードマップ策定が2026年の重要課題。今すぐ完全移行は不要だが、「Crypto-Agility（暗号の交換容易性）」をアーキテクチャに組み込んでおくべき。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6 + Supabase の統合強化:** Prisma 6ではConnection Poolingがデフォルトでサポートされ、Supabase PgBouncerとの組み合わせで大規模トラフィックへの対応が容易になった。`DATABASE_URL`にpooler URLを使うだけでスケーラビリティが向上する。

- **Supabase Edge Functions × Prisma Accelerate:** エッジランタイムではTCP接続が使えないため、Prisma AccelerateをHTTPレイヤーとして挟むパターンが定番化。レイテンシとコールドスタートの両方を改善できる。

- **Row Level Security (RLS) とORMの責務分離:** SupabaseのRLSをDBレベルで設定し、Prismaはあくまでクエリビルダーとして使う設計が安全。アプリ層でのアクセス制御に頼ると、バイパスリスクが生じる。

- **型安全なマイグレーション管理:** Prisma MigrateによるスキーマのGit管理と、Supabase CLIの`supabase db diff`を組み合わせることで、本番環境への安全なスキーマ適用フローが確立できる。CIで`prisma migrate deploy`を自動実行するのがベストプラクティス。

- **リアルタイム機能との棲み分け:** SupabaseのRealtime（Postgres WALベース）はPrismaでは扱えないため、イベント駆動な機能はSupabase clientを直接使い、CRUD操作はPrismaに統一するという役割分担が実用的。

### 7. WebAssembly Rust performance 2026

- **WASI 0.2 (Component Model) の実用化:** 2025年末にWASI Preview 2が安定版となり、RustのWASMコンポーネントが真のポータブルAPIとして機能するようになった。wasmtime + cargo-component の組み合わせがサーバーサイドWASMのデファクトスタックになりつつある。

- **Rust→WASM のコンパイル最適化成熟:** `wasm-opt` (Binaryen) とLTOの組み合わせにより、バイナリサイズが従来比30〜50%削減できるケースが増加。`wasm-bindgen` の最新版では不要なglueコード生成が大幅に減り、初期ロード時間がクリティカルなエッジ用途で有利になっている。

- **SIMD・スレッド対応の普及:** WebAssembly SIMDがChrome/Firefox/Safariで全対応済みとなり、RustのSIMDイントリンシクスがほぼそのままWASMに移植可能。画像処理・暗号・ML推論などのユースケースで、JSの5〜10倍のスループットが現実的に達成できる。

- **エッジランタイム競争とRustの優位性:** Cloudflare Workers / Fastly Compute / Fermyon Spin いずれもRust+WASMをファーストクラスサポート。コールドスタートがNode.jsの1/100以下（〜1ms）という数値が出ており、レイテンシ重視のAPIゲートウェイ層でRustが実用選択肢になっている。

- **メモリ管理の落とし穴は依然存在:** RustのOwnershipモデルはWASMのリニアメモリと相性が良いが、JS↔WASM間の頻繁なデータコピーがボトルネックになるケースが多い。設計上、バッファを共有する（SharedArrayBuffer + `wasm-bindgen` の `&[u8]` 参照）か、処理をWASM側に閉じ込める粒度設計が依然として重要。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点でApp Routerの成熟により、`'use client'`は最小限に留めるのがベストプラクティス。データフェッチ・認証ロジックはServer Componentsに集約し、インタラクションのみClient Componentsへ委譲することでバンドルサイズを大幅削減できる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的ストリームを同一ルートに混在させるPPRが安定化。`<Suspense>`境界を戦略的に配置することで、TTFBを犠牲にせずパーソナライズコンテンツを配信できる。

- **Server Actions でAPI Routeを削減:** フォーム送信・ミューテーションはServer Actionsに移行することで、不要なREST APIエンドポイントを排除。`revalidatePath` / `revalidateTag`との組み合わせでキャッシュ無効化も宣言的に管理できる。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15以降、関数・コンポーネント単位でキャッシュを宣言できる`use cache`が主流。`cacheTag` / `cacheLife`でタグベースの無効化と有効期限を制御し、ISRより柔軟なキャッシュ戦略が実現可能。

- **Parallel Routes + Intercepting Routes でモーダル設計を統一:** モーダル・サイドパネル等のUI状態をURLに反映させるパターンが定着。`@modal`スロットとインターセプトルートを組み合わせることで、リロード・共有URLでも正しいUIを復元でき、SEOとUXを両立できる。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge Runtimeの制約を理解したコード分割:** Edge FunctionsはNode.js APIの完全サポートがなく、バンドルサイズ上限（1MB）も厳しいため、`next/dynamic`や条件インポートで重いライブラリをEdgeから除外し、必要な処理のみをEdgeに寄せる設計が不可欠。

- **ポイント2: Middleware最適化でコールドスタートを最小化:** Middlewareは全リクエストで実行されるため、`matcher`設定で静的アセット・`_next/`パスを明示除外し、不要な実行コストを削減する。2026年現在、Vercelの`matcher`パターンマッチングはWebAssemblyベースで高速化されており積極活用すべき。

- **ポイント3: Fluid ComputeによるEdge/Serverlessのハイブリッド活用:** Vercelの「Fluid Compute」モデル（2025年〜）では、Edge FunctionsとServerless Functionsの境界が曖昧になりつつある。レイテンシ重視の処理はEdge、DB接続など状態を持つ処理はServerlessと明確に役割分担することでコスト効率が向上。

- **ポイント4: KVストアとEdgeの組み合わせでキャッシュ戦略を最適化:** Vercel KV（Redis互換）をEdgeから直接参照することで、DBへのフォールバックなしにパーソナライズコンテンツをグローバル低レイテンシで配信できる。TTL設計とstale-while-revalidateパターンを組み合わせることが実践上のベストプラクティス。

- **ポイント5: OpenTelemetryによるEdge可観測性の確立:** Edge Functionsはログが揮発しやすく、デバッグが困難。`@vercel/otel`を用いたトレーシングとVercel Speed Insightsを組み合わせ、リクエストごとのレイテンシ内訳（DNS・TLS・TTFB）を計測する体制を本番前に整えることが2026年の標準プラクティス。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** プリミティブ型に名前的型付けを加える `Brand<T, K>` パターンが標準化し、`UserId` と `PropertyId` を誤って混在させるバグをコンパイル時に防止できる。

- **`satisfies` 演算子の活用:** 型推論を維持しながら型チェックを行う `satisfies` が、設定オブジェクトや定数マップの定義で `as const` の代替として定着した。

- **Template Literal Types によるAPI契約:** `${Method}:${Endpoint}` 形式でルート定義を型レベルで表現し、実装とOpenAPI仕様の乖離をビルド時に検出する設計が増加。

- **`noUncheckedIndexedAccess` の有効化が標準に:** `tsconfig` でこのフラグをオンにすることで配列・オブジェクトアクセスの `undefined` 漏れを撲滅できるため、新規プロジェクトではデフォルト採用が推奨される。

- **Zod + `infer` による Schema-First 型定義:** バリデーションスキーマをsource of truthとし `z.infer<typeof schema>` で型を導出するパターンが主流化、手書き `interface` との二重管理が不要になっている。本プロジェクトでも `src/lib/` のバリデーション層で積極採用を検討すべき。
