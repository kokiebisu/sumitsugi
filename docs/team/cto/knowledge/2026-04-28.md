# CTO Knowledge - 2026-04-28

## Daily Update (2026-04-28)

### 1. Next.js performance optimization 2026

- **React Server Components の徹底活用:** RSC をデフォルトとし、クライアントコンポーネントを末端の葉ノードに限定することで、バンドルサイズを大幅に削減できる。`"use client"` の境界を意識的に設計することが最重要。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降で安定化したPPRにより、静的シェルと動的ストリームを1リクエストで配信可能。Time to First Byte と動的コンテンツの両立が実現できる。

- **Turbopack によるビルド高速化:** Webpackから Turbopack への移行が実質的に標準となり、HMRが数百msオーダーに短縮。大規模コードベースでは開発体験と CI 時間に直結する。

- **`<Image>` と `<Font>` の最適化を再確認:** `priority` フラグの適切な設定と `next/font` によるフォントの自動インライン化は、Core Web Vitals（LCP・CLS）改善の即効策として依然有効。

- **キャッシュ戦略の明示化:** Next.js 15でキャッシュのデフォルトが変更され、`fetch` は opt-in キャッシュになった。`unstable_cache` やタグベースの `revalidateTag` を使いキャッシュ粒度を明示的に設計しないと、意図せず過剰リクエストが発生するリスクがある。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の本格普及:** Next.js 15以降でPPRが安定化し、静的シェルを即時配信しながら動的コンテンツをストリームする手法がプロダクション標準になりつつある。Suspense境界の設計がパフォーマンスのボトルネックを直接決定するため、コンポーネント境界設計のスキルが重要度を増している。

- **Server Actions との統合深化:** RSCとServer Actionsの組み合わせにより、クライアントJSバンドルを大幅削減しながらインタラクティブなフォームやデータ更新が実現できる。ただしウォーターフォール問題（サーバー→クライアント→サーバーの往復）は依然注意が必要で、`use cache`ディレクティブの適切な活用が鍵。

- **Streaming SSRのエラーハンドリング成熟:** ストリーミング中のエラー処理が複雑で、`error.tsx`とSuspenseの`fallback`の責務分離を誤ると、ユーザーに壊れたUIが部分的に表示されるリスクがある。2026年時点ではエラー境界のグラニュラリティ設計がベストプラクティスとして確立されてきた。

- **React 19 `use()` APIによるデータフェッチ統合:** `use(promise)`でサーバー・クライアント両方でPromiseを扱えるようになり、データフェッチのパターンが統一されつつある。これによりSuspenseベースのストリーミングUIの実装コストが下がり、ローディング状態管理の複雑さが軽減されている。

- **Edge RuntimeとRSCの相性問題への対処:** CDN Edgeでのストリーミングレンダリングは低レイテンシを実現するが、Node.js専用APIへの依存や長時間ストリームでのタイムアウトがエッジ環境では課題になる。Vercel/Cloudflareのインフラ差異を吸収する抽象レイヤーの整備が2026年の実装上の重要テーマとなっている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性の標準化:** 2026年現在、Next.js/RemixなどのフルスタックフレームワークではtRPCが実質的なデフォルト選択となりつつあり、クライアント・サーバー間でTypeScriptの型を共有することでランタイムエラーを大幅に削減できる。

- **GraphQLはBFF層に集約:** マイクロサービス間の集約レイヤー（BFF: Backend for Frontend）としてGraphQLが有効だが、小〜中規模プロジェクトでの採用はオーバーエンジニアリングになりやすい。Federation v2（Apollo/Hive）による分散グラフ管理が大規模組織では主流。

- **REST + OpenAPIは依然として外部API公開の最適解:** サードパーティ向けパブリックAPIではRESTとOpenAPI 3.1仕様が標準であり続ける。自動生成されるSDK（openapi-generator、Hey APIなど）との組み合わせで開発体験も大幅に改善されている。

- **エッジ・ストリーミング対応がAPI設計の新要件:** Vercel Edge / Cloudflare WorkersなどのエッジランタイムやStreaming Response（RSC、SSE）への対応が設計段階から必須となり、従来のREQ/RESモデルだけでは不十分なケースが増えている。

- **契約駆動開発（Contract-First）の普及:** APIスキーマ（OpenAPI・Protobuf・Zodスキーマ）を先に定義し、フロント・バックエンドを並行開発するContract-Firstアプローチが、チーム間の依存ブロッカーを解消する手法として定着している。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジの標準ランタイムへ:** CloudflareやFastlyがWasmファーストのアーキテクチャを推進し、コンテナより軽量・高速な実行環境として定着。言語非依存のポータビリティも開発者体験を大きく改善している。

- **エッジでのAI推論が実用段階に:** 量子化モデル（Gemma 2B、Phi-3 miniなど）をエッジノードで直接実行するパターンが普及し、レイテンシ削減とプライバシー保護を同時に実現。RAGのベクター検索もエッジDBと組み合わせる構成が増加。

- **SQLiteベースのエッジDBが主流化:** Cloudflare D1、Turso（libSQL）などが成熟し、エッジ関数から直接SQL実行が可能に。グローバルレプリケーションとの組み合わせで、従来の「エッジは読み取り専用」という制約が実質的に解消された。

- **コールドスタート問題の解決策が収束:** V8 Isolateの事前ウォームアップとスナップショット技術により、コールドスタートは1ms以下が当たり前に。Next.jsのEdge Runtimeもこの恩恵を受け、サーバーコンポーネントのエッジデプロイが現実的な選択肢となっている。

- **オブザーバビリティがエッジ固有の課題に:** 分散ノードからのトレーシング統合が複雑で、OpenTelemetryのエッジ対応実装（特にサンプリング戦略）がチームの実装負荷になりやすい。ベンダー提供のマネージドObservabilityへの依存度が高まっている点は、ベンダーロックインリスクとして認識すべき。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準採用:** FIDO2/WebAuthn ベースのパスキーがパスワード認証を実質的に置き換えつつあり、フィッシング耐性と UX の両立が実現できる。主要プラットフォームのサポートが成熟した今、新規実装ではパスキーをデフォルトにすべき。

- **トークンライフタイムの短縮化:** アクセストークンの有効期限を 15 分以下に設定し、リフレッシュトークンのローテーション（RTR）を必須化することで、トークン漏洩時の被害を最小化できる。セッション管理はサーバーサイドで状態を持つ設計に回帰しつつある。

- **デバイスバインディングと継続的認証:** 「ログイン時だけ認証」から「セッション中も継続的にリスク評価」するゼロトラスト型へシフト。デバイス証明書やふるまい分析を組み合わせた異常検知が実用段階に入っている。

- **サプライチェーンリスクとしての認証ライブラリ管理:** OAuth/OIDC ライブラリの脆弱性（例：`jose`、`next-auth` 系）は攻撃の主要経路になっており、依存関係の定期監査と SBOM 管理が必須。ライブラリのアップデートを自動化する仕組みを CI に組み込むこと。

- **AI 生成コードの認証ミス対策:** LLM が生成する認証コードに `alg: none` 受け入れや JWT 検証スキップが混入するケースが報告されている。コードレビューにセキュリティ特化の静的解析（Semgrep 等）を必ず挟み、認証周りは自動テストでクリティカルパスを網羅すること。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のエッジランタイム対応:** Prisma はEdge Runtime（Cloudflare Workers、Vercel Edge）への対応が成熟し、`@prisma/adapter-neon` や `@prisma/adapter-pg` を使ったサーバーレス接続が標準的になった。コネクションプーリングは Supabase の PgBouncer より PgBouncer + Supabase Pooler（Supavisor）への移行が推奨されている。

- **Supabase の Row Level Security (RLS) と Prisma の共存:** RLS をDBレイヤーで担保しつつ Prisma でクエリを書くアーキテクチャが定着しつつあるが、`SET LOCAL role` や `SET LOCAL request.jwt.claims` を Prisma の `$executeRaw` で渡す実装パターンが複雑になりやすいため、アプリ層とDB層の責務境界を明確に設計することが重要。

- **Prisma Postgres（旧Prisma Data Platform）の台頭:** Prisma 社が提供するマネージドPostgresが2026年に一般提供化され、Accelerate（グローバルキャッシュ）と Pulse（リアルタイムCDC）が統合されたフルスタック構成が選択肢になった。Supabase と競合するが、ORM統合の深さでは Prisma Postgres に優位性がある。

- **型安全なクエリとスキーマ駆動開発:** `prisma generate` による TypeScript 型の自動生成と Supabase の `supabase gen types typescript` を組み合わせると型の二重管理になるため、Prisma を Single Source of Truth にしてマイグレーションも `prisma migrate` に統一するのが2026年時点のベストプラクティス。

- **パフォーマンス:** N+1 問題対策として Prisma の `include` / `select` の最適化に加え、Supabase の PostgREST を直接叩くハイブリッドアーキテクチャ（重いバッチ処理はPostgREST、トランザクション処理はPrisma）が大規模プロダクトで採用されている。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の本格普及:** 2026年はWASI Preview 2が安定版となり、RustのWasmコンポーネントが言語間で型安全にコンポーザブルに連携できるようになった。`cargo component`ツールチェーンが成熟し、マイクロサービス境界でのWasm採用が加速している。

- **SIMD・スレッド対応の標準化:** WebAssembly SIMDとshared memoryスレッドが主要ブラウザ・ランタイムで安定化し、RustのSIMDクレート（`std::simd`）を活用した画像処理・音声処理・ML推論が、ネイティブ比90%以上の性能を達成するケースが増えている。

- **Wasmtimeとクラウドネイティブの融合:** Fastly・Cloudflare・ByteDanceがRust+Wasmをエッジコンピューティングの主要実行基盤として採用。コールドスタートがコンテナ比100倍以上高速で、サーバーレス関数のランタイムとしてRust/Wasmの組み合わせが事実上の標準になりつつある。

- **GCプロポーザル成熟によるメモリ管理の選択肢拡大:** WasmGCが普及したことで、Rustのゼロコストアブストラクションと手動メモリ管理の強みが再評価されている。GC言語（Kotlin/Dart）がWasmへ来る中、Rustは「GC不要でピーク性能が必要な処理」のファーストチョイスとして棲み分けが明確化。

- **`wasm-opt`・PGO・サイズ最適化の自動化:** Binaryen経由の`wasm-opt`とRustのPGO（Profile-Guided Optimization）を組み合わせたCI/CDパイプラインが一般化し、バイナリサイズを30〜50%削減しつつ実行速度を向上させる手法が定番化している。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの徹底:** 2026年時点でApp Routerの主流はServer Components優先設計。クライアントバウンダリを最小化し、`'use client'`はインタラクティブ部品の末端のみに留めることで、バンドルサイズを大幅削減できる。

- **Partial Prerendering (PPR) の実用化:** Next.js 15以降でPPRが安定し、静的シェル+動的ストリームの組み合わせがデフォルト戦略になりつつある。`<Suspense>`境界の設計がパフォーマンスの要となる。

- **Server Actions によるAPI層の簡素化:** フォーム処理やデータ変更にServer Actionsが定着し、APIルートを経由しない直接DB操作パターンが普及。ただしZodバリデーションと認可チェックをAction内に必ず組み込むことが必須。

- **`use cache` ディレクティブによる細粒度キャッシュ制御:** `fetch`キャッシュに代わり、関数・コンポーネント単位でキャッシュ戦略を宣言できる`use cache`が標準化。`cacheTag`/`cacheLife`APIで無効化コントロールが格段に明確になった。

- **パラレルルート＆インターセプトルートの活用:** モーダルやスライドオーバーをURLを持つ独立したルートとして実装するパターンが成熟。本プロジェクトの物件詳細モーダルなどにも適用可能で、ディープリンク対応とUX改善を両立できる。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Fluid Computeへの移行:** Vercelは2025年末にEdge FunctionsをFluid Computeアーキテクチャに統合し、コールドスタートをほぼ排除。リージョン選択の最適化よりも、関数の軽量化（バンドルサイズ<1MB）が優先事項になった。

- **ポイント2: Streaming ResponseとPartial Prerendering（PPR）の組み合わせ:** PPRとEdgeストリーミングを組み合わせることで、静的シェルを即座に配信しつつ動的コンテンツを並列フェッチできる。Next.js 16ではこのパターンがデフォルト推奨になっている。

- **ポイント3: Edge Configによるレイテンシ削減:** 機能フラグやA/B設定をEdge Configに移すことで、外部DBラウンドトリップを排除。グローバルp99レイテンシを50ms以下に抑えられるケースが多い。

- **ポイント4: KV・Blob・Postgresのリージョン配置戦略:** Vercel StorageはEdgeから呼ぶと物理距離でレイテンシが増大する。ユーザー集中リージョンにデータを置く「リージョンピニング」設定を怠ると、Edge化の恩恵を相殺する。

- **ポイント5: バンドルサイズ監視の自動化:** Edge RuntimeはNode.js APIの大部分が使えないため、依存ライブラリの互換性チェックをCIに組み込むことが必須。`@vercel/bundle-analyzer`をPRチェックに追加し、サイズ回帰を早期検知する体制が標準化されつつある。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の普及:** TypeScript 4.9で導入された `satisfies` が2026年のスタンダードになり、型推論を保持しながら型検証を行うパターンが定着。`as` キャストを排除できるため、ランタイムエラーの早期発見に直結する。

- **Branded Types / Nominal Typing の実用化:** `type UserId = string & { readonly __brand: 'UserId' }` パターンが広まり、プリミティブ型の取り違えによるバグをコンパイル時に防ぐ設計が主流に。特に決済・認証周りで必須の手法となっている。

- **Template Literal Types による型レベルDSL:** SQLクエリ・URLパス・イベント名などをstring literalで型付けする技法が成熟し、ランタイムではなく型レベルでのバリデーションが当たり前に。`zod` と組み合わせることで境界値の安全性が大幅に向上する。

- **`noUncheckedIndexedAccess` の標準化:** `tsconfig.json` でこのフラグをONにするプロジェクトが増加し、配列・オブジェクトアクセス時の `undefined` チェック漏れをコンパイラが強制検出。strictモードの次のデファクトスタンダードと見なされている。

- **型レベルテスト（`tsd` / `expect-type`）の導入:** 型定義そのものをユニットテストする文化が普及し、ライブラリ開発だけでなくアプリケーション開発でも型の回帰テストを CI に組み込むチームが増加。型安全性をコードレビューではなく自動化で担保する流れが加速している。
