# CTO Knowledge - 2026-06-29

## Daily Update (2026-06-29)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR)の本格活用:** Next.js 15以降で安定したPPRを使い、静的シェルと動的部分を1リクエスト内で組み合わせることで、SSRのTTFB問題を回避しつつパーソナライズされたコンテンツも高速配信できる。物件一覧ページの静的レイアウト＋動的な空室状況表示などに有効。

- **React Server Components前提のデータフェッチ最適化:** クライアントへのJS転送量を削減するため、`use cache`ディレクティブとServer Actionsでデータ取得をサーバー側に閉じ込め、Client Componentは本当にインタラクティブなUIのみに限定する設計が標準化している。

- **Turbopackのビルド高速化を前提にした開発フロー:** `bun dev`でのHMR速度がdx向上の鍵になっており、CIでも`next build --turbopack`採用でビルド時間を大幅短縮できるため、CI時間の予算を圧迫しないよう優先的に検証すべき。

- **画像・フォントの自動最適化とCore Web Vitals監視の継続:** `next/image`のAVIF優先配信とfont自体ホスティングはLCP改善に直結するが、物件写真が多いsumitsugiのようなサービスではCDNキャッシュ戦略（stale-while-revalidate）も合わせて設計しないと効果が薄い。

- **Edge RuntimeとNode.js Runtimeの使い分け再考:** 認証チェックなど軽量処理はEdgeで低レイテンシ化し、DBアクセスを伴う重い処理はNode Runtimeに残すハイブリッド構成が、グローバル配信よりも「日本国内ユーザー中心」のsumitsugiでは過剰最適化にならないよう注意が必要。

### 2. React Server Components streaming 2026

- **ポイント1（Partial Prerendering の標準化）:** Next.js 16ではPPR（Partial Prerendering）が安定版となり、静的シェルを即座に返しつつ動的な部分だけをストリーミングする構成が標準パターンに。本プロジェクトの`properties/`一覧ページのような「静的なレイアウト＋動的な物件データ」構成に特に有効。
- **ポイント2（Suspense境界の粒度設計が重要）:** RSCストリーミングの効果はSuspense境界の切り方で決まる。粒度が粗いとTTFBは速くなるがCLS（レイアウトシフト）が増え、細かすぎるとウォーターフォールが発生するため、`listing/`詳細ページなどはセクション単位（画像・価格・前の住人レビュー）で境界を切るのが実用的。
- **ポイント3（Server Actionsとの組み合わせでフォームUXが向上）:** ストリーミングSSRとServer Actionsを組み合わせ、楽観的UI更新（`useOptimistic`）を併用することで、フォーム送信後の再描画がページ全体のブロッキングなく行える。問い合わせフォームや引越し費用計算フォームに適用余地あり。
- **ポイント4（エッジランタイムでのストリーミングコスト最適化）:** Vercel Edge RuntimeでのRSCストリーミングはコールドスタートを抑えられるが、Node.js APIに依存する処理（DBクライアント等）は引き続きNode runtimeが必要。混在構成での`runtime`指定の使い分けがパフォーマンスとコストのトレードオフになる。
- **ポイント5（キャッシュ戦略の複雑化への対応）:** `unstable_cache`やTag-based invalidationの実用化が進み、ストリーミングと組み合わせた際のキャッシュ無効化タイミング管理が難しくなっている。物件の`draft`/`public`ステータス変更時にキャッシュタグでの即時無効化を設計しておくと事故が減る。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの優位性が定着:** Next.jsフルスタック構成（sumitsugiのようなNext.js + TypeScriptモノレポ）では、tRPCがREST/GraphQLより開発速度で優位。スキーマ定義不要でエンドツーエンドの型推論が効くため、フロント・バック間のAPIコントラクトのズレがコンパイル時に検出できる。

- **GraphQLは複雑なデータ取得要件がある場合のみ採用:** 物件検索のような多階層・関連データ（物件→前の住人→インテリア情報）をフロントが柔軟にクエリしたい場合はGraphQLが有効だが、N+1問題対策（DataLoader等）やキャッシュ戦略の運用コストが高く、シンプルなCRUD中心のMVPには過剰投資になりやすい。

- **RESTはまだ外部公開APIの標準:** パートナー連携や将来のモバイルアプリ、サードパーティ統合を見据える場合はREST（OpenAPI仕様）が依然主流。内部はtRPC、外部公開APIはRESTという「ハイブリッド構成」が2026年のベストプラクティスとして定着している。

- **Server Actions/RSCとの統合がAPI設計の前提に:** Next.js 16のServer ComponentsとServer Actionsにより、従来のAPI層を介さないデータ取得・更新が増加。API設計の議論は「クライアント-サーバー間」だけでなく「いつAPI層自体が不要になるか」の判断も含むようになっている。

- **Zodなどのランタイム検証がAPI境界の必須要件に:** TypeScriptの型は実行時には消えるため、tRPC/REST問わずZodスキーマでの入力検証がシステム境界（標準.mdのルールにも合致）で必須。型安全性とランタイム安全性の両立が2026年のAPI設計の前提条件になっている。

### 4. serverless edge computing 2026

**CTO視点: Serverless Edge Computing 2026**

- **コールドスタート問題の実質的解消:** V8 isolate技術(Cloudflare Workers, Vercel Edge Functions等)の成熟により起動レイテンシが1ms未満まで低下。sumitsugiのようなNext.js App Routerプロジェクトでは、Middleware/Edge Runtimeを認証チェックや地域別リダイレクトに積極採用できる段階に来ている。

- **Edge上でのデータベースアクセスが標準化:** Turso/D1/PlanetScaleなど「edge-native」DBレプリカが普及し、グローバル分散でも読み取りレイテンシが数ms台に。物件検索のような読み取り中心の機能はedge DBレプリカ化で大幅な体感速度向上が見込める。

- **AI推論のEdge化(軽量モデル):** 画像最適化・OCR・チャットボットの一次応答などをedge上の小型モデルで処理し、重い処理だけをoriginのAPIに振る「ハイブリッド推論」が定石化。物件画像の自動タグ付けや「引越し費用」見積もりの初期判定などに応用できる。

- **コスト構造の変化(従量課金の精緻化):** CPU時間ベース課金(Cloudflare Workers Paid等)が一般化し、I/O待ち時間が無課金になったことで、外部API呼び出しを含むワークロードのコストが大幅減。Linear/Beads連携のようなI/Oバウンドな自動化処理はedge化のコストメリットが大きい。

- **観測性(Observability)のEdge対応遅れが依然課題:** トレーシング・ログ集約がoriginに比べ未成熟で、本番障害時のデバッグが難しい。MVPローンチ前のsumitsugiでは、まずoriginでの安定運用を優先し、edge移行は計測基盤が整った機能から段階的に行うのが妥当。

### 5. authentication security best practices 2026

- **パスキー/WebAuthnのデフォルト化:** 2026年現在、パスワードレス認証(FIDO2/WebAuthn)はもはや「オプション」ではなく標準実装。パスワード+SMS OTPは中間者攻撃やSIMスワップに弱く、フィッシング耐性のあるパスキーへの移行が業界標準になっている。

- **トークンのライフサイクル管理:** JWTを使う場合、アクセストークンは短命化(5-15分)し、リフレッシュトークンはローテーション＋再利用検知(reuse detection)を実装することが必須。長寿命トークンの漏洩リスクを最小化する設計が前提になっている。

- **ゼロトラスト前提のセッション検証:** デバイスフィンガープリンティングやIPの急激な変化検知など、ログイン後も継続的にリスクスコアリングを行う「継続的認証」が浸透。ログイン時点だけの一発認証はもう不十分という前提でアーキテクチャを組む。

- **ボット/クレデンシャルスタッフィング対策:** ログインAPIへのレート制限だけでなく、行動分析ベースのbot検知(CAPTCHA代替含む)を組み合わせる多層防御が標準。流出パスワードDB(HaveIBeenPwned API等)との照合も実装コストが低く効果が高い。

- **秘密情報管理の自動化:** APIキーやOAuthクライアントシークレットを`.env`に手動管理するのではなく、Vault/Secrets Manager経由での発行・自動ローテーションが前提。sumitsugiのような小規模チームでも、GitHub Actionsのsecretローテーションポリシーを最低限整備すべき。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMの型安全性とPostgreSQL最適化:** Prisma 6以降はクエリエンジンがRust依存から軽量化され、Supabase上のPostgreSQLとの相性がさらに向上。型生成とマイグレーション管理を組み合わせることで、スキーマ変更時のランタイムエラーを大幅に削減できる。

- **Row Level Security (RLS) とPrismaの統合:** SupabaseのRLSはDB層でのアクセス制御を担うが、Prismaのサービスロール接続を使う場合はアプリ層でも認可ロジックを二重化する必要がある。`sumitsugi`のような認証必須機能（前の住人/次の住人のマッチング）では、RLSポリシーとPrismaのミドルウェアを併用して防御を二層化するのが実用的。

- **Connection Pooling（PgBouncer/Supavisor）の必須化:** ServerlessやEdge環境（Next.js App Router）からの直接接続はコネクション枯渇を招くため、Supabaseの Supavisor（トランザクションモード）経由でPrismaを使うのが2026年時点の標準パターン。`DATABASE_URL`とは別に`DIRECT_URL`をマイグレーション専用に分離する構成が定石。

- **マイグレーション運用の自動化:** `prisma migrate deploy`をCI/CDパイプラインに組み込み、Supabaseのブランチ機能（プレビュー環境ごとのDBブランチ）と連携させることで、PRごとに安全なスキーマ検証が可能。本番デプロイ前にステージングDBでマイグレーションを自動検証するフローが業界標準化している。

- **リアルタイム機能とPrismaの境界:** Supabase Realtimeはpostgres_changesをトリガーにするため、Prismaで書き込んだ変更も自動的にRealtimeで配信される。ただし複雑な集計や物件ステータス（draft/public）切り替えのような業務ロジックはPrisma側のトランザクションで整合性を保証し、Realtimeは通知用途に限定するのが安全な設計指針。

### 7. WebAssembly Rust performance 2026

- **WASM GCとコンポーネントモデルの成熟:** 2026年にはWASM Component ModelとWIT (WebAssembly Interface Types) がツールチェーン標準になり、Rustクレートを言語非依存の再利用可能コンポーネントとして配布できるようになった。sumitsugiのような小規模チームでも、画像処理や検索インデックスなどの重い処理をWASMモジュール化し、ブラウザとサーバー（Node/Bun）で同一バイナリを共有できる。

- **wasm32-wasip2とネイティブ並列性:** WASIプレビュー2の安定化により、スレッドやSIMDがブラウザ外でも標準サポートされ、Rust+Rayonの並列処理がWASM上でも実用速度に達した。物件画像のリサイズやPDF生成のようなCPU負荷の高い処理をエッジ（Cloudflare Workers等）にオフロードする選択肢が現実的になっている。

- **バイナリサイズ最適化の重要性は継続:** `wasm-opt`、`twiggy`によるサイズ解析、`#[no_std]`構成は依然必須で、特にモバイル回線でのLCP（読み込み体験）に直結する。Next.js 16のRSC環境ではWASM初期化コストがハイドレーション前にブロッキングしやすいため、動的importでの遅延ロードが基本戦略になる。

- **RustコンパイラのインクリメンタルWASMビルド高速化:** cargo 1.8x系のインクリメンタルコンパイル改善とsccacheのWASMターゲット対応で、CI上のビルド時間が大幅短縮された。Beadsタスクの自動実装パイプライン（autonomous-developer.yml）でWASMモジュールを扱う場合、CI時間の予算管理がしやすくなっている。

- **デバッグ・プロファイリングのDevTools統合:** ChromeDevToolsのソースマップ対応がRust DWARF情報と完全互換になり、ブラウザ上でRustのままステップデバッグが可能。本番障害の再現コストが下がり、TDD/E2Eサイクルへの組み込みも容易になった。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 15以降で実験的だったPPRが安定版となり、静的シェルと動的コンテンツを1ページ内で組み合わせられるようになった。本サービスのproperties一覧ページなど「静的なレイアウト＋動的な空室状況」に最適で、初期表示速度とSEOを両立できる。

- **Server Actions のファーストクラス化:** フォーム送信やミューテーションをAPI Routeなしで`"use server"`関数として直接呼べる設計が主流になり、契約・問い合わせフォームなどのコードが大幅に簡素化される。ただしバリデーション（Zod）と認可チェックをアクション内で必ず行う必要があり、クライアントから直接呼ばれる前提でセキュリティ設計すべき。

- **`use cache` ディレクティブによる明示的キャッシュ制御:** Next.js 16でデータフェッチのキャッシュ戦略がfetchオプションから`use cache`ディレクティブベースに移行し、コンポーネント／関数単位でキャッシュ境界を明示できる。物件データのような更新頻度が低い情報と、空室状況のような頻繁に変わる情報を分離して管理しやすくなる。

- **Server ComponentsとClient Componentsの境界最適化:** 「Client Componentを葉（leaf）に押し込む」設計パターンが定着し、インタラクティブなUI（フィルタ、フォーム）だけをクライアント化してバンドルサイズを最小化する手法が標準ベストプラクティスになっている。shadcn/uiコンポーネントの多くもこの境界を意識した設計になっている。

- **Streaming + Suspenseによる段階的レンダリング:** `loading.tsx`とSuspenseバウンダリを細かく分割し、遅いデータ取得（決済確認、外部API連携など）を待たずに画面の他部分を先に表示するパターンが一般化。引越し費用計算や住人マッチングのような重い処理を含むページのUX改善に直結する。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化:** Edge Functionsは元々V8 isolateベースで高速起動が強みですが、依存関係のバンドルサイズが肥大化するとデプロイ時のコンパイルやinitオーバーヘッドが増えるため、`next/dynamic`や条件付きimportでバンドルを切り詰め、Edge Runtime専用の軽量ライブラリ（例: `jose`ではなくWeb Crypto API直叩き）に置き換えるのが効果的です。

- **Streaming + Partial Prerendering(PPR)の活用:** Next.js 15以降で正式化されたPPRと組み合わせ、静的シェルをCDNから即時配信しつつ、動的部分のみEdge Functionでストリーミングレスポンスを返す構成にすると、TTFBとLCPを大幅に改善できます。`sumitsugi`の物件検索・一覧ページのような動的フィルタ処理に向いています。

- **リージョン指定とデータ局所性:** Edge Functionは全リージョンで実行可能ですが、Supabase/DBアクセスを伴う処理ではDBリージョンに近いEdge Regionを`export const preferredRegion`で明示指定しないと、DB往復のレイテンシがEdgeの利点を相殺してしまう点に注意が必要です。

- **Node.js Runtime併用の判断基準:** 2025年以降、Vercel Functions（Node.js）もFluid Compute対応でコールドスタートが改善されたため、「全部Edgeにする」のではなく、暗号処理やDBコネクションプーリングが必要な処理はNode Runtimeに残し、軽量な認証チェック・リダイレクト・A/Bテスト分岐のみEdgeに置くハイブリッド構成がコスト・パフォーマンス両面で最適です。

- **Observability/コスト計測の自動化:** Edge Functionの実行時間課金特性上、本物件サイトのようなトラフィック変動が大きいサービスではVercel Analytics + OpenTelemetryでp95レイテンシと実行コストを継続監視し、ミドルウェアでの重い処理（画像変換、JWT検証の二重実行など）を早期に検知・削減する運用が重要です。

### 10. TypeScript type safety patterns 2026

- **Branded Types（ブランド型）の標準化:** `string`や`number`を`UserId`や`Email`のようなブランド型でラップし、プリミティブ型の取り違えをコンパイル時に検出する手法が、Zodの`.brand()`などライブラリ標準機能として定着しつつあります。sumitsugiでも`PropertyId`や`SellerId`のようなID型に適用すると、`src/lib/data.ts`周りの取り違えバグを未然に防げます。

- **Schema-first型推論（Zod/Valibot駆動）:** `z.infer<typeof Schema>`でランタイム検証とコンパイル時型を単一ソースから生成するパターンが主流化し、APIレスポンスやフォーム入力など「システム境界」での型安全性が大幅に向上しています。本プロジェクトのZod採用方針（standards.md記載）はこの流れに合致しており、追加コストなしで継続すべきです。

- **Discriminated Union + exhaustiveness check:** `'draft' | 'public'`のようなステータス型に対し、`switch`文で`never`型を使った網羅性チェックを徹底する手法が、ステータス追加時の漏れ防止のベストプラクティスとして再注目されています。物件ステータスのような重要な状態遷移には必須です。

- **`satisfies`演算子の活用拡大:** 型を明示しつつ推論の柔軟性を保てる`satisfies`が、設定オブジェクトや定数定義（`site-config.ts`等）で型注釈より好まれる傾向にあります。型の縮小を防ぎながら過剰な型アサーションを減らせます。

- **strictness設定の段階的強化（`noUncheckedIndexedAccess`等）:** 2026年はtsconfigの厳格化オプション（配列アクセスの`undefined`強制など）をデフォルト推奨とする動きが加速しており、既存コードベースへの段階導入（ファイル単位のoverride）が実務的なアプローチとして定着しています。
