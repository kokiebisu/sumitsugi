# CTO Knowledge - 2026-04-12

## Daily Update (2026-04-12)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを劇的に削減できるため、`'use client'`境界は最小限に留め、データフェッチはサーバー側で完結させる設計が2026年の標準となっている。

- **Partial Prerendering (PPR) による静的・動的ハイブリッド配信:** Next.js 15以降で安定化したPPRにより、1ページ内で静的シェルを即座に返しつつ動的コンテンツをストリーミングできる。CDNキャッシュとリアルタイム性を両立する最重要アーキテクチャパターン。

- **`<Image>`と`next/font`によるCore Web Vitals最適化:** LCPとCLSに直結するため、画像は必ず`priority`/`sizes`を明示し、フォントはサブセット化してセルフホスト。これだけでPageSpeed Insightsスコアが20〜30点改善するケースが多い。

- **Turbopackへの移行でビルド・HMR高速化:** Next.js 15でTurbopackがstable化し、大規模プロジェクトでHMRが最大10倍高速になる。`next dev --turbopack`から段階移行し、CI/CDのビルド時間削減にも寄与する。

- **Server Actions +楽観的UIでUX向上:** `useOptimistic`とServer Actionsを組み合わせることで、APIラウンドトリップを待たずにUIを即時更新できる。フォーム送信や「いいね」系インタラクションのレイテンシを体感ゼロにする実践的アプローチ。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の本格普及:** Next.js 15以降でPPRが安定版となり、静的シェルを即座に配信しつつ動的コンテンツをSuspense境界でストリーミングする設計が標準パターンになっている。TTFBとLCPの両立が現実的に達成できるようになった。

- **Server Actions との統合深化:** フォーム送信・データ変更をRSC内のServer Actionsで完結させるアーキテクチャが定着し、クライアントバンドルサイズを大幅削減できる。ただしキャッシュ無効化（`revalidatePath`/`revalidateTag`）の設計を誤るとストリーミングの恩恵が失われるため慎重な設計が必要。

- **Suspense 境界の粒度設計がボトルネック:** ストリーミングの効果はSuspense境界の切り方に依存する。粗すぎるとウォーターフォールが残り、細かすぎるとCLS（レイアウトシフト）が多発する。データフェッチの依存関係を事前に整理し、並列フェッチ可能な単位で境界を設計することが実務上のキーポイント。

- **Edge Runtime との相性とトレードオフ:** RSCをEdgeで実行することでレイテンシは下がるが、Node.js専用APIが使えない制約がある。2026時点ではVercel・Cloudflare WorkersともにRSC対応が成熟しているため、DBアクセスパターン（接続プール問題）を考慮した上でEdge採用を判断すべき。

- **React 19 の `use()` フックによるキャッシュ戦略の変化:** `React.cache()` と `use()` の組み合わせでリクエストをまたいだメモ化が明示的に制御できるようになり、RSC間でのデータ重複フェッチが減少した。ただしキャッシュスコープ（リクエスト単位 vs. グローバル）の理解なしに使うとメモリリークや意図しないデータ共有が起きるため要注意。

- **tRPCの成熟とフルスタック型安全性の標準化:** tRPC v11とNext.js App Routerの組み合わせが2026年のデファクトになりつつあり、TypeScriptプロジェクトではAPIスキーマ定義の重複をなくせるため、REST/GraphQLより開発速度が大幅に向上している。

- **REST + OpenAPI 3.1の再評価:** Scalar・Hono・ElysiaJSなどの型安全なRESTフレームワークが台頭し、スキーマ駆動開発（Schema-First）でtRPCに近い開発体験を実現しつつ、外部公開APIの互換性を維持できる点で再評価されている。

- **Server Actions / RPC-over-HTTPの普及:** Next.js Server ActionsやRemix Actionsの浸透により「APIエンドポイントを明示的に設計しない」パターンが一般化し、BFF（Backend for Frontend）レイヤーの概念が変容している。

- **AIエージェント対応APIの設計が新たな考慮点に:** LLMやAIエージェントがAPIを直接呼び出す用途が増え、OpenAPI仕様へのdescriptionの充実・Tool呼び出し互換性・レート制限設計がAPI設計の評価軸として加わっている。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジのデファクトに:** V8アイソレーションに代わりWasmランタイム（Wasmtime, WASIp2）がエッジ実行環境の主流となり、コールドスタートがほぼゼロに近づいた。言語非依存でデプロイできる点が開発速度を大幅に向上させる。

- **エッジでのAI推論が現実解に:** 量子化モデル（INT4/INT8）とハードウェアアクセラレーション対応エッジノードの普及により、LLM推論をオリジンサーバーに戻さずエッジで完結させるアーキテクチャが実用段階に入った。レイテンシとプライバシー両面でメリットがある。

- **分散SQLとエッジDBの成熟:** Cloudflare D1・Turso（libSQL）系の分散SQLがリードレプリカをエッジ拠点に自動配置する機能を強化し、読み取り主体のワークロードであればRTTをほぼ排除できる。書き込み整合性設計が依然として最大の設計課題。

- **オブザーバビリティのコスト問題:** エッジ関数が数千ノードに分散すると、トレース・ログの集約コストがオリジン集約型の数倍になるケースが顕在化。OTel標準化とテール・サンプリングの組み合わせが必須のコスト制御策となっている。

- **ベンダーロックインリスクの再評価:** WinterCG（Web互換APIの標準化グループ）によるポータビリティ仕様が進んだ一方、各プロバイダー固有のバインディング（KV・Queue・Durable Objects等）への依存が深まる傾向も同時進行。アーキテクチャ設計時にエグジット戦略を明示的に議論することが重要。

### 5. authentication security best practices 2026

## Authentication Security Best Practices 2026 — CTO視点

- **パスキー（Passkeys）への移行加速:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の主流となり、フィッシング耐性と利便性を両立。新規サービスではパスワード認証をデフォルトにする設計自体を避けるべき。

- **デバイスバインド型セッション管理:** セッショントークンをデバイス証明書と紐づけることでトークン窃取攻撃を無効化。`Sec-Session-Registration` ヘッダー（DBSC）のブラウザ普及に合わせた実装準備が必要。

- **継続的認証（Continuous Authentication）の標準化:** ログイン時の一点認証から、行動パターン・リスクスコアに基づくリアルタイム再認証へ移行。異常検知とステップアップ認証をセットで設計する。

- **AIを悪用したソーシャルエンジニアリング対策:** ディープフェイク音声・映像を使ったなりすましが実用レベルに達しており、人間によるコードワード確認やアウトオブバンド検証が必須。MFAの「SMS OTP」は実質的に非推奨水準。

- **サプライチェーン認証リスクの可視化:** OAuthサードパーティ連携やIDプロバイダー（IdP）自体への侵害が増加。ゼロトラスト原則で「IdPを信頼しすぎない」設計—継続的なアクセストークンの最小権限化と即時失効機能が競争優位の条件。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応:** Prisma 6ではEdge-compatibleドライバが安定版となり、Vercel Edge FunctionsやCloudflare Workersから直接Supabaseに接続可能に。コールドスタートを最小化しつつ、グローバル分散アーキテクチャが現実的な選択肢となった。

- **Supabase pgvectorの本格活用:** `pgvector`拡張がSupabaseで標準化され、RAGパイプラインをPostgreSQL単体で完結できる。Pineconeなど外部ベクトルDBを排除してインフラシンプル化が図れるが、大規模（1億件以上）では依然専用DBが優位。

- **Row Level Security (RLS) × Prismaの設計パターン:** SupabaseのRLSをPrismaから呼び出す際、`SET LOCAL role = 'authenticated'`をトランザクション内で発行する方法が定着。アプリ層での認可ロジック重複を削減し、セキュリティの責務をDB層に集約できる。

- **Connection Pooling戦略の再整理:** Supabase Pooler（PgBouncer）とPrisma Accelerateの役割分担が明確化。サーバーレス環境ではPoolerのTransaction modeを使い、Prisma AccelerateはグローバルキャッシュとP99レイテンシ改善に特化するのがベストプラクティス。

- **マルチテナントアーキテクチャの主流パターン:** Schema-per-tenantではなく、`tenant_id`カラム＋RLSによるRow-levelマルチテナントがPrisma＋Supabase構成での推奨に。スキーマ分割はマイグレーション管理コストが高く、スタートアップ段階では過剰設計になりやすい。

### 7. WebAssembly Rust performance 2026

- **WASI 0.2の本格普及:** Component Modelが安定化し、RustからWasmコンポーネントを型安全にコンポーズできるエコシステムが成熟。サーバーサイドWasmがエッジ・サーバーレス環境での実用選択肢になっている。

- **GCプロポーザルによるメモリ効率の向上:** WasmGCの普及でRust以外の言語もWasmターゲットになりやすくなったが、Rustはゼロコストアブストラクションとリニアメモリの組み合わせで依然として最高のパフォーマンス特性を維持。

- **SIMD・スレッド命令の標準化:** Wasm SIMDとShared Memoryが主要ランタイム（Wasmtime、V8、SpiderMonkey）で安定サポートされ、RustのSIMD intrinsicsをWasmにコンパイルして数値計算・画像処理を大幅高速化できる。

- **JIT不要のAOTコンパイルとコールドスタート:** WasmtimeのCranelift＋AOTコンパイルにより、エッジ環境でのコールドスタートがmsオーダーに。Fastly Compute等での本番採用が増加しており、Rustは初期化コストの低さで有利。

- **ツールチェーンの成熟（`cargo component`）:** `cargo component`とWIT（WebAssembly Interface Types）によりRustでのコンポーネント開発フローが統一化。既存crateをWasmターゲットに移植する際の摩擦が大幅に低減されている。

### 8. Next.js App Router patterns 2026

- **Server Componentsをデフォルトに:** 2026年時点でApp RouterのServer Componentsは成熟し、データフェッチはコンポーネント層で完結するのが標準。`use client`は本当にインタラクションが必要な最小単位に絞ることで、バンドルサイズを劇的に削減できる。

- **Partial Prerendering (PPR) の本格活用:** Next.js 15+で安定化したPPRにより、静的シェルと動的コンテンツを1リクエストで配信可能。`<Suspense>`境界の設計がパフォーマンスの鍵となり、Streaming SSRとの組み合わせでTTFBを大幅改善できる。

- **Server Actionsによるフォーム設計の刷新:** `use server`のServer Actionsがform submitの標準手法となり、APIルート不要でDB操作が可能。`revalidatePath`/`revalidateTag`との組み合わせでオプティミスティックUIも簡潔に実装できる。

- **Route Handlersの適所利用:** webhookやOAuth callbackなど「本当にHTTPエンドポイントが必要な場面」に限定し、それ以外はServer Actionsに移行するのがベストプラクティス。APIレイヤーの肥大化を防ぎ、コードの凝集度が上がる。

- **`use cache` ディレクティブによるきめ細かなキャッシュ制御:** Next.js 15で導入された`use cache`により、関数・コンポーネント単位でキャッシュ戦略を宣言的に記述可能。`cacheLife`/`cacheTag`と組み合わせることで、従来の`fetch`オプション依存から脱却した柔軟なキャッシュ設計が実現できる。

### 9. Vercel Edge Functions optimization 2026

**Vercel Edge Functions最適化 2026 — CTOの視点**

- **ポイント1: Fluid Computeでコールドスタートを排除せよ:** 2025年に正式化されたFluid Computeモデルにより、Edge FunctionsとServerless Functionsの境界が曖昧になった。リクエストの局所性に応じて動的にルーティングされるため、従来の「Edgeか否か」の二択設計から脱却し、レスポンスタイムベースで最適化を判断するアーキテクチャが求められる。

- **ポイント2: バンドルサイズの制約（1MB圧縮）が設計の最重要制約:** Edge Runtimeは完全なNode.js APIを持たず、`fs`や`crypto`の一部が使えない。依存関係を`edge-compatible`なものに限定し、`@vercel/og`や`jose`など軽量ライブラリを選定することがパフォーマンスの前提条件。

- **ポイント3: Partial Prerendering（PPR）との組み合わせが最強パターン:** 静的シェルをCDNから即時配信しつつ、動的部分のみEdge Functionでストリーミングする設計が2026年のデファクトになりつつある。Next.js App Routerの`Suspense`境界設計がEdge最適化の鍵。

- **ポイント4: Middlewareは最小限に保て、ビジネスロジックを持ち込むな:** VercelのMiddlewareは全リクエストに実行されるため、肥大化するとグローバルレイテンシに直結する。A/Bテスト・認証チェック・地域リダイレクトに留め、DBアクセスや重い処理はRoute Handlersへ移譲する設計原則が重要。

- **ポイント5: Edge KV（Vercel KV/Redis）とのセット活用でステートレス制約を克服:** EdgeはステートレスなV8 Isolateで動くため、セッション・フィーチャーフラグ・レート制限などの状態管理にEdge-native KVストアを組み合わせるパターンが必須。レイテンシは`~5ms`以内を目標に地域を設計段階で選定すること。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `type UserId = string & { _brand: 'UserId' }` パターンが広く採用され、プリミティブ型の誤用をコンパイル時に防ぐ手法が成熟。特にドメイン駆動設計との親和性が高い。

- **satisfies 演算子の積極活用:** TypeScript 4.9+ の `satisfies` が2026年には定番化し、型推論を保持しつつ型チェックを行うことで、`as` キャストによる型安全性の喪失を避けるパターンが浸透。

- **Zod + tRPC によるエンドツーエンド型安全:** APIの境界でZodスキーマを定義し、フロントエンドからバックエンドまで型を自動伝播させるアーキテクチャが実質的な標準となり、ランタイムバリデーションと静的型チェックの二重化が解消されつつある。

- **Template Literal Types の高度な活用:** SQLクエリ、イベント名、ルートパスなどを型レベルで表現するパターンが実用段階に達し、文字列操作ミスをコンパイル時に検出できるようになった。

- **noUncheckedIndexedAccess の強制:** `tsconfig` の厳格オプションとして `noUncheckedIndexedAccess: true` が推奨設定に昇格し、配列・オブジェクトアクセス時の暗黙的 `undefined` を明示的に扱うことで、実行時エラーを大幅削減できる。
