# CTO Knowledge - 2026-10-12

## Daily Update (2026-10-12)

### 1. Next.js performance optimization 2026

- **ポイント1:** Partial Prerendering (PPR) が安定版に近づき、静的シェルを即時配信しつつ動的部分をストリーミングする構成が標準化。物件一覧など「ヘッダーは静的、価格・空室状況は動的」なページで特に効果が大きい。
- **ポイント2:** React 19のCache ComponentsとuseCache APIの活用で、DBクエリ単位の細粒度キャッシュが可能になり、revalidateTagによる選択的キャッシュ無効化が重要パターンに。物件ステータス変更時など部分的な再検証に向く。
- **ポイント3:** Turbopackがビルド・開発両方でデフォルト化され、大規模コードベースでのHMR・ビルド時間が大幅短縮。本プロジェクトのような中規模Next.js構成でも`bun run build`時間の短縮効果を検証する価値あり。
- **ポイント4:** Server ActionsのペイロードサイズとWaterfall問題への対策として、`after()` APIでの非同期処理分離や、クライアント側データフェッチとのハイブリッド設計が重視されている。
- **ポイント5:** 画像・フォント最適化はCore Web Vitals(INP重視)への対応がより厳格に。`next/image`のpriority指定ミスやレイアウトシフトがSEO・コンバージョンに直結するため、物件写真ギャラリーなど画像多用ページでの計測が必須。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Prerendering (PPR) の実質的な標準化** Next.js 16ではPPRが安定版の中核機能となり、静的シェルを即時配信しつつ動的部分だけをストリーミングする構成が「特別な最適化」ではなくデフォルトの設計パターンになっている。本プロジェクトの`properties/`一覧ページのように、ヘッダーやレイアウトは静的、物件データ部分だけ非同期にできる箇所から適用候補を洗い出すと効果が大きい。

- **ポイント2: `use cache` ディレクティブによるキャッシュ粒度の細分化** サーバーコンポーネント単位ではなく関数単位でキャッシュ境界を指定できるようになり、`cacheLife`/`cacheTag`との組み合わせでDB問い合わせ結果（例: 物件一覧のseller情報）を細かく無効化できる。`src/lib/data.ts`のデータ取得関数に適用すれば、draft/public切り替え時の再検証コストを抑えられる。

- **ポイント3: Suspenseバウンダリの「意味的分割」が設計スキルとして重要に** 単にローディングを隠すためではなく、ユーザーが最初に見るべき情報（物件タイトル・価格）とレイテンシの高い情報（レビュー・周辺施設）を分けて境界を切る設計が主流。モバイル回線でのTTI改善に直結するため、一覧/詳細ページのレイアウト設計時に意識すべき。

- **ポイント4: Server ActionsとStreamingの組み合わせでフォームUXが向上** 送信中の楽観的UI（`useOptimistic`）とサーバーアクションのストリーミングレスポンスを組み合わせ、引越し費用の見積りや問い合わせフォームのような多段階フローで「送信→即時フィードバック→バックグラウンド処理完了」のパターンが実装しやすくなっている。

- **ポイント5: エッジランタイムとRSCストリーミングの相性問題に注意** Vercel以外のホスティング（自前サーバーやDocker）でRSCストリーミングを使う場合、HTTP/2以降やレスポンスバッファリングの設定次第でストリーミングの利点が消えるケースがある。本番デプロイ先のインフラ構成を確認してから採用範囲を決めるべき。

### 3. API design REST GraphQL tRPC 2026

- **型安全ファーストの潮流:** tRPCやHonoのRPCスタイルがTypeScriptモノレポで主流化し、OpenAPI生成やスキーマ同期の手間を省きつつエンドツーエンドの型安全性を確保できる。sumitsugiのようなNext.js App Router構成では、tRPC導入でフロント/バック間の型ズレによるバグを大幅削減できる。

- **GraphQLは「内部API」に収束:** 公開APIはRESTまたはtRPCが主流になりつつあり、GraphQLは複雑な集約クエリが必要な社内/パートナー向けAPIに限定利用されるケースが増えている。全面移行ではなく、必要な箇所にだけ採用するハイブリッド戦略が実用的。

- **スキーマ駆動+Zodバリデーションの一体化:** ZodスキーマをAPI境界の入力検証とtRPC/REST両方の型定義に共用する設計が定着し、CLAUDE.mdのZod必須ルールとも整合する。1つのスキーマ定義から型・検証・ドキュメントを生成することで保守コストを下げられる。

- **Edge/Server Actions中心の軽量API:** Next.js 16のServer Actionsが単純なCRUDの大半を代替し、独立したAPI層を持たない「API-lessアーキテクチャ」が増加。本物件プラットフォームのような小〜中規模サービスでは、複雑なGraphQL層よりServer Actions + 一部tRPCの組み合わせが開発速度とパフォーマンスの両面で有利。

- **AIエージェント連携を見据えたAPI設計:** LLMエージェントがAPIを直接呼ぶケースが増え、明確なエラーメッセージ・冪等性・レート制限を備えたREST/tRPCエンドポイント設計が重要性を増している。将来的な自動化（autonomous-developer.ymlのような仕組み）とAPIを統合する際、エージェントが解釈しやすいレスポンス設計が差別化要因になる。

### 4. serverless edge computing 2026

- **ポイント1:** 2026年はエッジ推論の主戦場がV8 IsolatesやWasmベースのランタイム（Cloudflare Workers, Deno Deploy, Vercel Edge）に完全移行し、コールドスタートがほぼゼロになったことで、認証・パーソナライゼーション・軽量AI推論をオリジンサーバーに頼らずエッジで完結できるようになっています。
- **ポイント2:** エッジでの状態管理（Durable Objects、エッジKV、SQLite at the edge）が成熟し、グローバル分散でもデータの一貫性を保ちやすくなったため、物件検索やリアルタイム空室状況のようなレイテンシ敏感な機能をエッジ側に移す価値が高まっています。
- **ポイント3:** 小型LLM・量子化モデルのエッジ実行（例: 数億パラメータ級モデルのWebGPU/WASM推論）が実用段階に入り、問い合わせ対応や文章要約などの軽量AI処理をサーバーレスで低コスト・低遅延に提供できる選択肢が増えています。
- **ポイント4:** 開発体験面ではNext.js 16のエッジランタイム対応が強化され、App Routerのレンダリングを地理的に最も近いノードで実行できるため、sumitsugiのような物件一覧・検索ページでTTFBを大幅に改善できる余地があります。
- **ポイント5:** 一方でエッジ環境はNode.js APIの制約（ファイルシステム、一部npmパッケージ非対応）が残るため、全面移行ではなく「認証・リダイレクト・A/Bテスト・画像最適化」など適所にエッジを使うハイブリッド構成が現実的なベストプラクティスです。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードレス認証（WebAuthn/Passkeys）が標準化され、フィッシング耐性の高い認証をデフォルトにすることで、ログイン関連インシデントを大幅に削減できます。実装時はフォールバック手段（メールOTP等）も用意し、デバイス紛失時のリカバリー導線を設計する必要があります。

- **セッション管理とトークンの短命化:** JWTやセッショントークンの有効期限を短く設定し、リフレッシュトークンのローテーション・無効化リストを実装することで、トークン漏洩時の被害範囲を限定できます。特にSPA構成ではhttpOnly Cookie + CSRF対策の組み合わせが推奨されます。

- **多層防御としてのリスクベース認証:** IPアドレス・デバイスフィンガープリント・行動パターンを組み合わせたアダプティブMFAにより、通常と異なるログイン試行のみ追加認証を要求し、UXとセキュリティのバランスを取れます。

- **サプライチェーン・依存関係の認証周り監査:** 認証ライブラリ（NextAuth/Auth.js等）やOAuthプロバイダーのSDKは脆弱性開示が頻発するため、定期的な`bun audit`相当のチェックとバージョン固定・迅速なパッチ適用プロセスが不可欠です。

- **最小権限とゼロトラスト原則の徹底:** `src/contexts/auth-context.tsx`のようなクライアント側コンテキストに加え、サーバー側（API Routes/Server Actions）でも必ず認可チェックを行い、クライアントの状態を信頼しない設計を徹底することで、認可バイパスのリスクを防ぎます。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6系とSupabaseの統合強化:** Prisma ORMはSupabaseのPostgreSQL拡張（RLS、pgvector等）との型安全な連携が進み、`prisma db pull`でRLSポリシーも含めたスキーマ同期が可能になってきている。sumitsugiのような物件データ管理ではRow Level Securityとアプリ層の型安全性を両立できる点が魅力。

- **Edge/Serverless環境でのコネクション管理:** Next.js 16のApp Router + Vercel Edge FunctionsでSupabase/Prismaを使う場合、PrismaのConnection Pooling（Prisma Accelerate）やSupabaseのPgBouncer経由接続が必須。コールドスタート時のDB接続過多を避けるため、サーバーレス前提の設計が2026年の標準になっている。

- **Realtime機能の活用余地:** Supabase RealtimeはWebSocketベースでDB変更を即時配信でき、物件の公開/非公開ステータス変更や内見予約の通知など、sumitsugiのUXに直結する機能を低コストで実装できる可能性がある。

- **マイグレーション運用の一本化:** Prismaのマイグレーション履歴とSupabaseのダッシュボードUI変更が競合しやすいため、「Prismaスキーマを単一の真実源（Single Source of Truth）とする」運用ルールを早期に決めておくことが、チーム拡大後の事故防止に有効。

- **コスト最適化の観点:** Supabaseは無料枠〜Pro枠でのDB容量・帯域コストが明確なので、MVPローンチ初期は低コストで始めつつ、物件画像等の大容量データはSupabase StorageではなくCDN併用で分離するのが2026年時点のベストプラクティス。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASM GCやComponent Modelの標準化が進み、Rustコンパイラ(`wasm32-wasip2`)がネイティブにサポート。言語間連携のオーバーヘッドが大幅に削減され、マイクロサービス的にWASMモジュールを組み合わせる設計が実用的になっている。

- **ポイント2:** SIMD命令とマルチスレッド(`wasm-bindgen` + Web Workers)の組み合わせにより、画像処理・PDF生成などCPU集約的な処理がブラウザ上でネイティブの70-90%程度の速度に到達。sumitsugiのPDF生成や画像最適化処理をWASM化する際の参考になる。

- **ポイント3:** バンドルサイズ最適化（`wasm-opt`, `twiggy`での解析）がビルドパイプラインの標準ステップ化。Rust側で`#[no_std]`やfeature flagを適切に使うことで、不要なコードをツリーシェイクし初期ロード時間を短縮できる。

- **ポイント4:** サーバーサイドWASM（Wasmtime, Fermyon Spin等）がエッジコンピューティングで普及し、Cloudflare Workers / Vercel Edge FunctionsでのRust実装がコールドスタート数msレベルに。Next.js 16のEdge Runtime併用で地理的レイテンシ削減が狙える。

- **ポイント5:** Rustの`cargo-component`やWITツール群が成熟し、TypeScript/JSとの型安全な境界定義が容易に。既存のZodバリデーション層と組み合わせることで、パフォーマンスクリティカルな検証ロジック（住所マッチング等）をWASM化しつつ型整合性を保てる。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の標準化:** 静的シェルを即時配信し、動的部分のみストリーミングする手法が2026年には主流化しており、Next.js 16でも安定版として扱われるため、LCP改善とSEOを両立しやすい。
- **Server Actionsの責務分離:** `use server`を多用しすぎるとAPI境界が不明瞭になるため、認証・検証ロジックはZodスキーマで境界に集約し、Server Actionsは薄いオーケストレーション層に留めるパターンが定着している。
- **Cache Components / `use cache`ディレクティブ:** キャッシュ戦略をファイル単位ではなく関数単位で明示する書き方が広がり、`revalidateTag`との組み合わせでプロパティ公開状態（draft/public）のような動的データの再検証制御が明確になる。
- **Route Groups + Parallel Routesによるレイアウト分離:** `(auth)`や`@modal`のようなパターンで認証フローやモーダルUIをレイアウトレベルで分離し、ページ単位の責務を小さく保つ設計が一般化している。
- **Edge RuntimeとNode Runtimeの使い分け明確化:** 認証チェックなど低レイテンシが必要な処理はEdgeに、DB接続や重い処理はNode Runtimeにと役割分担する設計が、コスト・パフォーマンス両面のベストプラクティスとして定着している。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge Runtimeのコールドスタート最適化** V8 isolateベースの実行モデルにより、2026年時点でコールドスタートは1桁ms台まで短縮されており、Node.js Runtimeからの移行判断基準が「レイテンシ要件」から「互換性要件」にシフトしている。Prismaなど一部ORMもEdge対応ドライバーが成熟してきたため、採用範囲が広がっている。

- **ポイント2: ストリーミングSSRとの組み合わせ** Edge Functionsでのレスポンスストリーミングが標準化され、Next.js 16のPartial Prerendering（PPR）と組み合わせることで、静的シェルを即時返却しつつ動的部分をEdgeでストリーミングする構成が主流になっている。本プロジェクトの物件詳細ページなど動的データ混在のページで検討価値あり。

- **ポイント3: リージョン選択とデータレイテンシのトレードオフ** Edge Functionsは全リージョン展開がデフォルトだが、DB（例: Supabase/Postgres）が単一リージョンの場合は「Edgeでの計算は速いがDB往復で相殺される」問題が依然残る。Fluid Compute（リージョン固定+オートスケール）との併用判断が重要な設計ポイント。

- **ポイント4: 認証・ミドルウェアのEdge化** `middleware.ts`でのセッション検証がEdge Runtime上で実行されるため、JWT検証のような軽量処理に限定し、DBクエリを伴う認可チェックはServer Componentsに委譲する設計が推奨される。本プロジェクトの`auth-context.tsx`周りの認証フローを見直す際の指針になる。

- **ポイント5: コスト監視の必須化** Edge Functionsの実行時間課金モデルが変更され、2026年はInvocation数ベースよりGB-secベースの計測精度が上がったため、画像処理や大きめのレスポンス生成をEdgeに置くとコストが跳ねやすい。重い処理はNode.js Runtime or Background Functionsへの振り分けを検討すべき。

### 10. TypeScript type safety patterns 2026

- **厳格な型推論とconst型パラメータ:** TypeScript 5.x以降の`const`型パラメータやsatisfies演算子の活用が標準化し、型の過度な拡大(widening)を防ぎつつ推論精度を高めるパターンが定着している。
- **ブランド型とnewtypeパターン:** `type UserId = string & { __brand: 'UserId' }`のようなブランド型でプリミティブ型の取り違えを防ぎ、ID系のバグをコンパイル時に検出する手法がドメインモデリングの標準になっている。
- **Zodなどスキーマライブラリとの型統合:** 実行時検証と静的型を一つのスキーマ定義から自動生成する構成（`z.infer`など）がシステム境界（API・フォーム入力）での型安全性を担保する標準パターンとして広く採用されている（本プロジェクトでも採用方針）。
- **Discriminated UnionによるExhaustiveness Check:** `switch`文で`never`型を使った網羅性チェックを徹底することで、Union型に新しいケースを追加した際のハンドリング漏れをコンパイル時に検出できる。
- **型レベルテストの導入:** `tsd`や`expect-type`などを使い、ユーティリティ型やジェネリクスの振る舞いをユニットテストと同様にCIで検証する流れが広がっており、型定義自体のリグレッションを防げる。
