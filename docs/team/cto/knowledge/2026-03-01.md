# CTO Knowledge - 2026-03-01

## Daily Update (2026-03-01)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを削減するため、データフェッチはすべてServer Componentsに集約し、インタラクティブな部分のみ`'use client'`を付与する設計が標準化されている。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降でPPRが安定化し、静的シェルを即座に配信しつつ動的部分をストリーミングで差し込む手法が主流になった。これによりTTFBとLCPを同時に改善できる。

- **`next/image`と`next/font`の最適化強化:** 画像の`sizes`属性と`priority`フラグの適切な設定、そしてフォントのサブセット指定が必須となり、CLS（累積レイアウトシフト）ゼロを達成しやすくなっている。

- **Server Actions によるネットワーク往復の削減:** フォーム送信や状態更新にServer Actionsを使うことで、API RouteのラウンドトリップをRSCの再レンダリングと統合でき、不要なクライアント側状態管理が不要になる。

- **Turbopackへの移行完了:** Next.js 16ではTurbopackがデフォルトバンドラーとなり、大規模プロジェクトでの`bun dev`起動時間が従来比で大幅に短縮された。ただし、webpack固有のプラグインとの互換性は引き続き要確認。

### 2. React Server Components streaming 2026

**React Server Components Streaming 2026 — CTO視点**

- **Partial Prerendering (PPR) の本格普及:** Next.js 15以降でPPRが安定化し、静的シェルを即座に配信しつつ動的コンテンツをストリームする手法が主流になっている。TTFBの劇的な改善が可能で、既存のSSR/SSG二択の概念を刷新した。

- **Suspense境界の設計がアーキテクチャの核心に:** データフェッチの粒度とSuspense境界の配置がパフォーマンスを直接左右する。粗すぎるとウォーターフォール、細かすぎるとHTML断片の増大を招くため、コンポーネント設計段階でのストリーミング戦略が必須。

- **Server Actions + Optimistic UIの成熟:** フォーム送信や変更操作をサーバー側で完結させつつ、`useOptimistic`でUIを即時更新するパターンが定着。ネットワーク往復を意識したUX設計がフロントエンド実装標準になっている。

- **Edge Runtimeとの統合深化:** Cloudflare Workers・Vercel Edge等のエッジ環境でのRSCストリーミングが実用レベルに達し、グローバルユーザーへの低遅延配信が現実的な選択肢に。ただしNode.js APIの制約はまだ残るため、ランタイム選定は慎重に。

- **バンドルサイズとキャッシュ戦略の再設計が急務:** RSCにより「クライアントに送るJS」の境界が明確になった反面、サーバーコンポーネントのキャッシュ無効化タイミングの制御が複雑化。`fetch`のキャッシュオプションやrevalidation戦略を明示的に設計しないと、意図しない古いデータ配信が発生するリスクがある。

### 3. API design REST GraphQL tRPC 2026

- **tRPC の主流化:** TypeScript フルスタック環境では tRPC が事実上の標準になりつつあり、型安全なエンドツーエンド通信によりランタイムエラーを大幅に削減できる。Next.js + tRPC の組み合わせは内部 API の第一選択肢。

- **GraphQL の棲み分け明確化:** 複数クライアント（Web/Mobile/サードパーティ）が異なるデータ形状を必要とするケースに限定され、BFF（Backend for Frontend）パターンと組み合わせた選択的採用が主流。過剰適用による複雑性を避けるべき。

- **REST は「外部公開 API」に特化:** 外部開発者向けやサードパーティ連携では OpenAPI 3.1 + REST が依然として最適解。エコシステムの成熟度とドキュメント自動生成の容易さが強み。

- **Server Actions / RPC-first の台頭:** Next.js の Server Actions に代表される「関数を直接呼ぶ」パラダイムがアプリケーション層の API 設計を塗り替えており、HTTP の抽象化レイヤーを意識しないコードが増加。

- **API Gateway + スキーマファーストが必須:** 規模が大きくなるほど契約駆動開発（OpenAPI / Protobuf スキーマを先に定義）が生産性と品質の両面で重要。Zod や TypeSpec によるスキーマ定義から型・バリデーション・ドキュメントを自動生成するアプローチが 2026 年のベストプラクティス。

### 4. serverless edge computing 2026

- **エッジ・ファースト・アーキテクチャの標準化:** Cloudflare Workers・Vercel Edge Functions・AWS Lambda@Edgeが成熟し、レイテンシ重視のユースケース（認証・パーソナライゼーション・A/Bテスト）ではエッジ実行がデフォルト選択になっている。Next.js App RouterのEdge Runtimeとの統合も実用レベルに達した。

- **WebAssembly（Wasm）がエッジの共通言語に:** 言語非依存の実行環境としてWasmがエッジプラットフォームで標準採用され、Rust・Go・Python製のロジックをJSランタイム上で動かすパターンが普及。コールドスタートを事実上ゼロに近づけている。

- **データの「エッジ近傍化」が次の課題:** 計算のエッジ化は解決されつつあるが、データベースアクセスがボトルネック化。Cloudflare D1・Turso・PlanetScale Boostなどエッジ対応の分散SQLが台頭し、グローバルレプリケーションとエッジ実行の組み合わせ設計が必須スキルになった。

- **コスト最適化の逆転現象に注意:** リクエスト数が多いワークロードでは、エッジ実行のコストがリージョナルサーバーレスを上回るケースが増加。トラフィックパターンを計測した上でエッジ適用範囲を判断する「選択的エッジ化」が設計原則として重要。

- **セキュリティ境界の再定義:** 認証トークン検証・レートリミット・WAFロジックをエッジで実行する構成が普及し、オリジンへの不正トラフィックを大幅削減できる。ただしエッジ環境でのシークレット管理（Workers KV・環境変数の扱い）は引き続き注意が必要。

### 5. authentication security best practices 2026

- **パスキー（Passkey）の標準採用:** FIDOアライアンスのパスキーがパスワードの実質的な後継として普及が加速しており、Apple/Google/Microsoftのネイティブ対応により実装コストが大幅に低下した。

- **セッション管理のゼロトラスト化:** 長寿命セッショントークンは廃止傾向にあり、短命アクセストークン（15分以下）＋ローテーティングリフレッシュトークンの組み合わせが現代的なベストプラクティスとなっている。

- **デバイスバインディングの重要性:** トークンをデバイスのTPMチップや生体認証に紐付ける「Device-Bound Session Credentials（DBSC）」がChrome等でサポートされ始め、クッキー窃取攻撃への対策として注目されている。

- **AIを活用した異常検知の組み込み:** 認証ログをリアルタイム解析し、普段と異なる地域・デバイス・時間帯からのアクセスを自動ブロックまたはMFA要求するアダプティブ認証が標準化しつつある。

- **OAuth/OIDCのセキュリティ強化:** `Pushed Authorization Requests（PAR）`と`DPoP（Demonstrating Proof of Possession）`の組み合わせによりトークン横流し攻撃を防ぎ、BFF（Backend for Frontend）パターンでブラウザへのトークン露出を最小化する設計が推奨されている。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6のEdge Runtime対応成熟:** Prisma Client の Cloudflare Workers / Vercel Edge Functions 対応が安定し、サーバーレス環境でのコネクション管理（Prisma Accelerate）が実用段階に。コールドスタート問題を抱えるNext.js App Routerとの相性が大幅改善されている。

- **Supabase の Row Level Security (RLS) をアーキテクチャ設計の中心に:** RLSをDBレイヤーで強制することで、アプリ層の認可ロジックを排除できる。ただしPrismaからRLSを使う場合は `SET LOCAL role = authenticated` のセッション制御が必要で、設計段階での意識が不可欠。

- **Supabase Realtime + pgvector の組み合わせが主戦場に:** AIアプリ向けにベクター検索（pgvector）とリアルタイム同期を同一DBで完結できる点がSupabaseの差別化。RAGパイプラインをRDBMSに統合することで、別途ベクターDBを持つ複雑さを回避できる。

- **Prisma Migrate vs Supabase Migrations の二重管理に注意:** Supabase CLIの `supabase db push` とPrismaの `prisma migrate` を混在させるとスキーマ管理が破綻しやすい。2026時点では**Prismaをスキーマの主権者**とし、SupabaseはホスティングとRLSのみ担当する役割分担が安定運用の定石。

- **接続プーリングはPgBouncer→Supavisorへの移行完了:** Supabaseが提供するSupavisorがサーバーレス向け接続プーリングの標準となり、Prismaの接続URL設定で `?pgbouncer=true` を使った旧来の手法は非推奨。`SESSION` / `TRANSACTION` モードの選択がパフォーマンスに直結するため設計時に確定させること。

### 7. WebAssembly Rust performance 2026

- **WASI 0.3とComponent Modelの成熟:** WASIp3（Preview 3）が安定化し、RustのWASMコンポーネントが異なるランタイム間で真に相互運用可能になった。`cargo component`ツールチェーンが本番環境で実用的になり、マイクロサービスの軽量代替として注目されている。

- **Wasmtime・Wasmer のAOTコンパイル高速化:** JITウォームアップ問題がほぼ解消され、Rustで書いたWASMモジュールがネイティブ実行の85〜95%のパフォーマンスに到達。サーバーレス・エッジコンピューティングでのコールドスタートが5ms以下になるケースも増加。

- **SIMD・マルチスレッドSIMDの本番利用拡大:** WebAssembly SIMDとshared memory/Atomicsが主要ブラウザ・ランタイムで安定し、Rustの`packed_simd`/`std::simd`と組み合わせた画像処理・ML推論がCPUバウンドタスクで2〜4倍の速度向上を実現。

- **Rustの`wasm-bindgen`から`wit-bindgen`への移行加速:** `wasm-bindgen`はブラウザ特化の技術的負債となりつつあり、WIT（WebAssembly Interface Types）ベースの`wit-bindgen`がエコシステムの主流に。新規プロジェクトはComponent Model対応が事実上のデフォルトになっている。

- **メモリ管理の改善とGC提案の実用化:** WebAssembly GC proposalの普及により、RustのWASMビルドでのヒープフラグメンテション対策が容易に。`wee_alloc`の代替として`talc`や`dlmalloc`が採用され、WASM バイナリサイズと実行時メモリ効率が同時に改善されている。

### 8. Next.js App Router patterns 2026

- **Server Componentsファースト設計:** App RouterではRSCをデフォルトとし、クライアントコンポーネントを「インタラクション境界」に限定する設計が定着。バンドルサイズを大幅削減でき、`use client`の乱用はパフォーマンス負債に直結する。

- **Partial Prerendering (PPR) の実用化:** 静的シェルと動的ストリーミングを同一ルートで混在させるPPRが安定化。`<Suspense>`境界を意識した設計が必須となり、ページ単位ではなくコンポーネント単位でキャッシュ戦略を考える時代になった。

- **Server Actions によるAPI Route削減:** フォームミューテーションはAPI Routeを経由せずServer Actionsで完結させるパターンが主流。ただし複雑なバリデーション・認可ロジックは薄いAction + ドメイン層に分離しないとテスタビリティが崩壊する。

- **`use cache` と細粒度キャッシュ制御:** Next.js 15以降で導入された`use cache`ディレクティブにより、関数レベルでのキャッシュ制御が可能に。`revalidateTag`と組み合わせたオンデマンド再検証が、従来の`revalidatePath`より精度高くパフォーマンスを制御できる。

- **React 19 `use()`フックとの統合:** `use(promise)`パターンによりサーバーからクライアントへのデータフェッチ境界が柔軟化。ただしウォーターフォールを避けるため、データフェッチは可能な限りサーバーコンポーネント層でparallelに実行し、`Promise.all`で束ねて渡す設計が推奨される。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Cold Start撲滅とEdge Runtimeの成熟:** 2026年時点でVercel Edge FunctionsはV8 Isolateベースのランタイムが安定し、Node.jsランタイムとの機能差が大幅に縮小。Cold Startは事実上ゼロに近づき、グローバル分散のメリットを最大限に享受できる。

- **ポイント2: Fluid Computeによるコスト最適化:** Vercelが導入したFluid Computeモデルにより、リクエスト間でのCPUリソース共有が可能になり、特にトラフィックスパイク時の過剰課金を抑制できる。スタートアップ段階のプロジェクトでは従来比30-50%のコスト削減事例が報告されている。

- **ポイント3: Edge ConfigとKV Storageの活用がボトルネック解消の鍵:** データベースへのラウンドトリップをなくすため、フィーチャーフラグ・A/B設定・認証トークン検証はEdge Config（読み取り超高速）にオフロードするのがベストプラクティス。動的コンテンツでも待ち時間を1桁msに抑えられる。

- **ポイント4: Partial Prerendering（PPR）との組み合わせが最強構成:** Next.js App RouterのPPRとEdge Middlewareを組み合わせることで、静的シェルを即時配信しつつ動的部分だけをEdgeでストリーミング。TTFBを劇的に改善しCWVスコアを最大化できる。

- **ポイント5: Middleware肥大化のアンチパターンに注意:** Edge Middlewareはバンドルサイズ上限（通常2MB）が厳しく、重いライブラリ（ORMやSDK）を誤って含めると即デプロイ失敗。依存関係の`sideEffects`管理とtree-shakingの徹底、および`matcher`によるルート絞り込みが実運用では必須。

### 10. TypeScript type safety patterns 2026

- **Branded Types（名義型）の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなブランド型パターンが標準化し、プリミティブ型の取り違えによるバグを型レベルで防止する手法が定着している。

- **`satisfies` オペレーターの積極活用:** TypeScript 4.9以降の `satisfies` により、型推論の恩恵を失わずに型制約を検証できるようになり、`as` キャストへの依存が大幅に減少した。

- **`NoInfer<T>` による型推論の精密制御:** TypeScript 5.4で追加された `NoInfer` ユーティリティで、ジェネリック関数の型推論の曖昧さを排除し、意図しない型の広がり（widening）を防ぐパターンが実用化している。

- **Zodによるスキーマ駆動型安全性:** `z.infer<typeof Schema>` でランタイムバリデーションとコンパイル時型定義を単一ソースに統一するアプローチが、API境界・フォーム・環境変数の検証で事実上の標準となっている。

- **Template Literal Types による文字列型の構造化:** APIルートやイベント名を `type Route = '/users' | '/users/${string}'` のように型付けし、文字列操作のミスを静的解析で検出する手法が成熟し、大規模コードベースでの採用が進んでいる。
