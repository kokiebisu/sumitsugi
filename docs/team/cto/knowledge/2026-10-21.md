# CTO Knowledge - 2026-10-21

## Daily Update (2026-10-21)

### 1. Next.js performance optimization 2026

- **React Server Componentsの徹底活用:** クライアントバンドルサイズを最小化するため、インタラクティブ性が不要なコンポーネントはデフォルトでServer Componentsに保ち、`'use client'`境界を末端のUI部品だけに限定する設計が標準化している。

- **Partial Prerendering (PPR)の本格運用:** 静的シェルを即時配信しつつ動的部分をストリーミングで後追い表示する手法が安定版となり、ECサイトや一覧ページ（物件一覧など）でTTFBとLCPを大幅改善できる。

- **キャッシュ戦略の明示化（`use cache`ディレクティブ）:** 暗黙的キャッシュから明示的な`use cache`指定への移行が進み、意図しないキャッシュヒット/ミスによるバグを防ぎつつ、データ取得層でのキャッシュ粒度を細かく制御できるようになった。

- **画像・フォント最適化の自動化強化:** `next/image`のAVIF優先配信やフォントのセルフホスティング自動化により、Core Web Vitals（特にCLS・LCP）の改善が開発者の追加作業なしで実現しやすくなっている。本サービスのような物件写真中心のUIでは特に効果が大きい。

- **ビルド時の型安全性とパフォーマンスの両立:** Turbopackの本番ビルド対応が進み、大規模コードベースでもビルド時間を抑えつつ型チェックを維持できるため、「ビルドが通ることをdoneの条件とする」という本プロジェクトの方針とも相性が良い。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の実用化:** Next.js 16ではPPRが主流化し、静的シェルを即時配信しつつ動的部分だけをストリーミングする構成が標準パターンに。TTFBが大幅短縮され、ECサイトや物件一覧ページのような「上部は即表示・下部は非同期」という設計がしやすくなっている。

- **Suspense境界の粒度設計がパフォーマンスの肝:** 粒度が粗いとウォーターフォール（直列待ち）が発生し、細かすぎるとレイアウトシフトが増える。sumitsugiの物件詳細ページのような「基本情報は即表示、レビュー・類似物件は後追い」という構成は典型的な勝ちパターン。

- **Server Actionsとのキャッシュ戦略の統合:** `revalidateTag`/`revalidatePath`によるきめ細かい再検証が標準化され、ミューテーション後のストリーミング再取得がシームレスになった。フォーム送信（引越し費用の見積もりなど）でも楽観的UIと組み合わせやすい。

- **エッジランタイムでのストリーミングSSRがコスト最適化の鍵:** Vercel EdgeやCloudflare Workersでのストリーミング配信により、サーバーレスのコールドスタート影響を抑えつつグローバルでレイテンシを下げられる。トラフィックの地域分散が進めば検討価値あり。

- **RSCペイロードのシリアライズコストに注意:** 大きなpropsをクライアントコンポーネントに渡すとストリーミングの恩恵が薄れるため、「サーバーで絞り込んでから渡す」設計原則が2026年のベストプラクティスとして定着。データ取得層（`src/lib/data.ts`）での早期フィルタリングが重要になる。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** 2026年現在、tRPCはNext.js×TypeScriptのフルスタック構成において標準的選択肢になりつつあり、コード生成不要でクライアント〜サーバー間の型安全性を保証できる点が、sumitsugiのような単一リポジトリ構成に特に適している。
- **ポイント2:** RESTは依然として外部公開APIやサードパーティ連携のデフォルトであり、OpenAPI + Zodスキーマを組み合わせた「スキーマファースト」設計がdocs/validation/型定義を一元化するベストプラクティスとして定着している。
- **ポイント3:** GraphQLは複数クライアント（Web/モバイル/パートナー向け）が異なる粒度でデータを必要とする場合に強みを持つが、単一フロントエンドが中心のプロダクトではオーバーヘッドが大きく、採用コストに見合わないケースが多い。
- **ポイント4:** Next.js 16のServer Actionsの成熟により、「API層そのものを薄くする」設計が広がっており、内部用途の変更系操作はtRPC/Server Actions、公開APIはRESTという併用パターンが実用的。
- **ポイント5:** いずれの方式を選んでもZod（またはStandard Schema準拠のバリデータ）が入力検証・型推論・ドキュメント生成の共通基盤となっており、スキーマ設計への投資がAPI方式の選択より重要度が高くなっている。

### 4. serverless edge computing 2026

- **エッジランタイムの統合進展:** Cloudflare Workers、Deno Deploy、Vercel Edge Functionsなど主要プラットフォームでV8 isolateベースの起動時間がミリ秒単位まで短縮され、コールドスタート問題が実質的に解消されつつある。本番導入時はベンダーロックインを避けるため、WinterCG準拠のAPI（Fetch, Web Streams等）を使った実装を優先すべき。

- **データレイヤーのエッジ分散:** D1、Turso、PlanetScaleなどエッジネイティブDBの成熟により、SSR時のDB往復レイテンシがボトルネックでなくなってきている。ただしsumitsugiのような物件検索・リアルタイム在庫管理には強整合性が必要な箇所があるため、全面移行前に読み取り専用データ（物件一覧キャッシュ等）から段階的に試すのが安全。

- **コスト構造の変化:** 従量課金モデルが成熟し、トラフィックの少ないMVPフェーズでは従来のサーバー常駐型より大幅にコスト削減できるケースが増えている。ただし画像処理・PDF生成（引越し費用の見積書等）のような重い処理はエッジ実行時間制限に引っかかりやすく、キューベースの非同期処理と組み合わせる設計が必須。

- **可観測性ツールの追いつき:** OpenTelemetryのエッジ対応が進んだが、分散トレーシングの粒度はまだサーバーレスVM環境に劣る。法務確認後のベータローンチ時に本番監視が必要になるため、早期にSentry/Datadogのエッジ向けSDK対応状況を検証しておくべき。

- **フレームワーク側の後押し:** Next.js 16のPartial Prerenderingとエッジランタイムの組み合わせで、動的パーソナライゼーション（前の住人プロフィール等）と静的配信の両立が実用レベルに。現行Next.js 16構成なら大規模な書き換えなしに段階導入できる点が大きい。

### 5. authentication security best practices 2026

## 認証セキュリティのベストプラクティス（2026年視点）

- **パスキー（FIDO2/WebAuthn）がデフォルト化:** パスワードレス認証が主流となり、フィッシング耐性のある認証方式として業界標準に。導入コストも下がり、中小規模プロダクトでも実装しやすくなっている。
- **多要素認証（MFA）の形態変化:** SMS OTPは依然SIMスワップ等のリスクがあるため、TOTPやプッシュ通知ベースの認証器アプリへの移行が加速。特に決済・個人情報を扱う機能では必須要件。
- **トークン管理の厳格化:** JWTやセッショントークンの有効期限短縮、リフレッシュトークンのローテーション、サーバーサイドでの即時失効（revocation）対応が標準的なセキュリティ要件になっている。
- **ゼロトラスト前提の設計:** 認証後も継続的にリスクを評価する「継続的認証」の考え方が広がり、異常なアクセスパターン（デバイス変更・地理的異常等）を検知する仕組みが重要視される。
- **サプライチェーン・サードパーティ認証のリスク管理:** OAuth/OIDC連携先の権限スコープを最小化し、依存ライブラリの脆弱性監視を継続的に行うことが、認証基盤全体の安全性維持に不可欠。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMの進化:** Prisma 6以降はRust不要の新クエリエンジン（TypeScript/WASMベース）に移行し、コールドスタートが大幅改善。Supabaseのようなサーバーレス環境でのEdge Functions連携が実用的になった。
- **Supabase RLSとPrismaの併用パターン:** Row Level SecurityをDB側で強制しつつPrisma Clientでアプリ層の型安全性を確保する構成が標準化。認証ロジックをアプリ側に分散させず、DBレベルで一元管理できるのがメリット。
- **接続プーリングの重要性:** サーバーレス関数からの接続過多を防ぐため、SupabaseのPgBouncer（Transaction mode）とPrismaの`directUrl`/`pooledUrl`分離設定が必須。これを怠るとスケール時に`too many connections`エラーが頻発する。
- **マイグレーション運用:** `prisma migrate`とSupabase CLIのマイグレーションを混在させず、どちらか一方に統一するチーム運用が推奨。特にRLSポリシーやトリガーはSupabase側SQLマイグレーションで管理し、Prismaスキーマとズレないようドキュメント化が必要。
- **リアルタイム機能との組み合わせ:** Supabase Realtimeを使う場合、Prismaは書き込み/読み取りの型安全なCRUDに専念し、リアルタイム購読はSupabase Client SDKに委ねる分離アーキテクチャが2026年の主流パターン。

### 7. WebAssembly Rust performance 2026

- **WASI 0.3とasync対応の成熟:** WASI PreviewのComponent Modelがasync/streamをネイティブサポートし、RustのツールチェインでJS側とのノンブロッキング連携が書きやすくなった。I/Oバウンドな処理（画像変換・PDF生成など）をブラウザ/エッジ両方で同一バイナリとして動かせる点が実用上大きい。

- **コンポーネントモデルによるポリグロット連携:** `wit-bindgen`経由でRust製WASMコンポーネントを他言語（JS/Python/Go）から型安全に呼び出せるようになり、重い計算処理だけをRustに切り出すマイクロモジュール設計がしやすくなった。sumitsugiのような小〜中規模プロダクトでは、PDF生成や画像処理などの局所的なホットパスのみWASM化するのが費用対効果が高い。

- **SIMD128 + スレッド(wasm-threads)の安定運用:** Rustの`std::simd`やマルチスレッドWASMがChromium/Firefoxで安定し、画像リサイズやレイアウト計算のようなCPU負荷の高い処理でネイティブの60-80%程度の性能が現実的になった。ただしNode.js/Bunランタイムでのスレッドサポートはまだ制約があるため、サーバーサイドで使う場合は事前検証が必須。

- **バンドルサイズとコールドスタートのトレードオフ:** `wasm-opt`やRustの`panic=abort`設定でバイナリを数十KB〜数百KB台に抑えられるが、Next.js App Router上でのWASM初期化は依然として追加のネットワークラウンドトリップになるため、LCPに影響するページでは遅延ロード（インタラクション時にのみWASMをフェッチ）が定石。

- **「まずJSで十分」の原則は変わらず:** 2026年時点でもWASM化による恩恵が出るのは「計算量がO(n log n)以上かつnが大きい」「既存Rust/C++資産の再利用」といったケースに限られる。sumitsugiの現状のユースケース（物件データのCRUD・画像表示程度）ではROIが低く、優先度は法務対応・ローンチ準備の後でよいと判断する。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 15系で導入されたPPRが16で安定版となり、静的シェルと動的コンテンツを1ページ内で共存させられるようになった。プロパティ一覧ページのように「ヘッダーは静的・検索結果は動的」という構成に最適で、TTFBを大幅に改善できる。

- **Server Actions の型安全な活用拡大:** フォーム送信やミューテーションをAPI RouteではなくServer Actionsで直接書くパターンが主流化。Zodスキーマとの組み合わせでリクエスト境界の検証を一元化できるため、`src/app`配下のフォーム処理（物件登録・問い合わせ等）はServer Actions + Zodへの統一を検討する価値がある。

- **`use cache` ディレクティブによる明示的キャッシュ制御:** これまで暗黙的だったfetchキャッシュ挙動が`use cache`で明示化され、キャッシュの意図がコードから読み取れるようになった。物件データのような更新頻度が低いデータに対し、意図しないキャッシュミス/ヒットのデバッグコストを下げられる。

- **Server Componentsをデフォルト、Client Componentsは「葉」に限定:** インタラクティブ性が必要な最小単位（ボタン、フォーム入力など）だけを`'use client'`境界にし、データ取得・レイアウトはServer Componentsに留める設計が定着。bundleサイズとLCPの両方に効くため、`src/components/listing`のような一覧・詳細表示コンポーネントは境界の見直しが有効。

- **Route Groups + Parallel Routes でのレイアウト分離:** `(marketing)`や`(dashboard)`のようなRoute Groupsと、モーダル表示に使うParallel Routes（`@modal`）の組み合わせが、認証状態によってレイアウトを切り替えるパターンの標準解になっている。`src/app/properties`と`src/app/account`のような認証要否が異なる領域の分離に適用しやすい。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約を前提にした設計:** Vercel Edge FunctionsはNode.js APIの一部が使えないため、`fetch`ベースのAPIクライアントや軽量なバリデーション（Zodなど）に統一し、重い依存関係はNode.jsランタイム（Serverless Functions）側に残すのが効果的です。

- **Streaming SSRとの組み合わせ:** Next.js 16のPartial Prerendering（PPR）とEdge Functionsを組み合わせることで、静的シェルを即時返却しつつ動的部分だけエッジでストリーミングでき、TTFBを大幅に改善できます。

- **リージョン指定とデータ局所性:** `export const preferredRegion`を活用し、DBやAPIの物理的な近さを意識したリージョン固定を行うことで、無駄なレイテンシ（特にDB往復）を削減できます。グローバル分散よりも「データに近い場所で実行する」方が効果的な場合が多いです。

- **コールドスタート対策としてのEdge Middleware分離:** 認証チェックやリダイレクトなどの軽量処理はMiddlewareに寄せ、重いビジネスロジックはEdge Functions/Serverless Functionsに分離することで、全体のレスポンス速度を安定させられます。

- **バンドルサイズの継続的な監視:** Edge Runtimeには実行コードサイズの上限があるため、`@next/bundle-analyzer`などでEdge Functions配下のバンドルサイズをCIで監視し、肥大化を早期に検知する運用が重要です。

### 10. TypeScript type safety patterns 2026

- **型推論の進化:** TypeScript 5.x系でconst型パラメータやsatisfies演算子の活用が標準化され、冗長な型注釈を減らしつつ厳密性を保てるようになっている。
- **Zodなどのスキーマ駆動開発:** ランタイム検証とコンパイル時型を同じスキーマから生成する手法（Zod, Valibot等）が主流化し、APIバウンダリでの型安全性が大幅に向上している。本プロジェクトでもZodを境界検証に使う方針と合致する。
- **Branded Types / Nominal Typingの普及:** `UserId`と`string`を型レベルで区別するBranded Typesパターンが、ID混在バグを防ぐ実用的手法として広く採用されつつある。
- **Template Literal Typesによる文字列検証:** ルートパスやCSSクラス名など、文字列の構造自体を型で検証するパターンが普及し、設定ミスをコンパイル時に検出できるようになった。
- **strictモード+exhaustiveness checkingの徹底:** Union型（例: `'draft' | 'public'`）に対し`never`を使った網羅性チェックを徹底することで、新しいステータス追加時の見落としをビルド時に検出する運用が定着している。
