# CTO Knowledge - 2026-11-11

## Daily Update (2026-11-11)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の標準化:** Next.js 15以降で導入されたPPRがNext.js 16で本格的に安定運用フェーズに入り、静的シェルを即時配信しつつ動的部分だけストリーミングする構成がデフォルトパターンになっている。本プロジェクトでも`src/app/properties/`等の一覧ページで、物件カードの静的枠と価格・空き状況などの動的データを分離することで初期表示速度を改善できる。

- **React Server Components + Cache Componentsの活用:** `use cache`ディレクティブによるコンポーネント単位のキャッシュ制御が主流となり、データ取得ロジックを細粒度でキャッシュ可能になった。`src/lib/data.ts`のフェッチ関数群をCache Componentsでラップすることで、DB/API呼び出し回数を削減しつつ鮮度管理も明示的に行える。

- **Turbopack本番ビルドの一般化:** Turbopackが`bun run build`含む本番ビルドでも安定版として広く使われるようになり、webpackに比べてビルド時間が大幅短縮。CI実行時間の短縮に直結するため、`bun run build`をCIに組み込む際はTurbopack設定を前提にするのが実用的。

- **画像・フォント最適化の自動化深化:** `next/image`のAVIF優先配信とレイアウトシフト検出がより厳密化し、Core Web Vitals（特にLCP/CLS）への影響を自動警告する仕組みがビルド時に組み込まれてきている。物件写真を多用するUIでは、`sizes`属性の適切な指定とpriority読み込みの見直しが直接的な改善につながる。

- **Edge RuntimeとPPRの組み合わせによる地理的最適化:** 認証チェックなど軽量なミドルウェア処理をEdge Runtimeに寄せつつ、本体コンテンツはPPRで配信する構成が一般化し、グローバル配信時のTTFBが改善。`src/contexts/auth-context.tsx`周りの認証判定をEdgeで先行実行する設計は、ユーザー体験と防御の両面で有効。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの定着:** React Server Componentsのストリーミングは、Suspenseバウンダリ単位でHTMLを段階的に送信する手法が標準化し、Next.js 16でもTTFBとLCPの両立がデフォルト挙動になっています。重い処理(DB集約クエリ等)をコンポーネント単位で後回しにできるため、ページ全体のブロッキングを回避できます。

- **Partial Prerendering (PPR) の安定化:** 静的部分を事前生成し、動的部分だけをストリーミングで差し込むPPRが実運用レベルに達しており、CDNキャッシュと動的コンテンツの両立が容易になっています。物件一覧のようなSEO重視ページでは、静的シェル+動的な在庫状況のストリーミングが有効な構成です。

- **RSCペイロードのキャッシュ戦略が重要に:** ストリーミングはTTFBを改善する一方、RSCペイロード自体のキャッシュ(`use cache`ディレクティブ等)を適切に設計しないとサーバー負荷が増大します。弊社の`src/lib/data.ts`のようなデータ取得層では、キャッシュタグ戦略を明示的に設計する必要があります。

- **エラーバウンダリとストリーミングの整合性:** ストリーミング中に発生したエラーは、既に送信済みのHTMLチャンクに影響を与えずハンドリングする必要があり、`error.tsx`の粒度設計がUXに直結します。特に認証や引越し費用計算のような重要フローでは、ストリーミング失敗時のフォールバックUIを明示的に用意すべきです。

- **計測の複雑化:** ストリーミングによりTTFB/FCP/LCPの関係が従来のSSRと異なるため、Core Web Vitalsの計測・改善アプローチも見直しが必要です。特にモバイル回線でのストリーミング遅延は、物件画像を多用するUIでは要注意ポイントです。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCは単一リポジトリ（モノレポ）構成でのフロントエンド/バックエンド間の型共有に強く、E2Eの型安全性によりAPI契約ドキュメントやコード生成ステップを省略できる。ただし外部公開APIや他言語クライアントとの連携には向かず、社内向けフルスタックTypeScript構成（sumitsugiのようなNext.jsモノリス）に最適。

- **ポイント2:** GraphQLはクライアント側で必要なフィールドだけを取得できる柔軟性が強みだが、N+1問題やキャッシュ戦略の複雑さ、スキーマ管理コストが運用上の負債になりやすい。小〜中規模チームではREST/tRPCの方が開発速度と保守性で優位になるケースが多い。

- **ポイント3:** 2026年現在、「REST vs GraphQL vs tRPC」の二択ではなく、内部通信（管理画面・社内ツール）はtRPC、外部公開・サードパーティ連携はREST（OpenAPI）、複雑な集約クエリが必要な箇所だけGraphQLという併用パターンが主流になっている。

- **ポイント4:** Zodなどのスキーマ定義ライブラリを起点に、ランタイム検証・型推論・OpenAPI/JSON Schema生成を一本化する「Schema-First」設計が標準化しており、sumitsugiのようにZodをシステム境界の入力検証に使う構成ならtRPCとの統合が最も実装コストが低い。

- **ポイント5:** エッジ/サーバーレス環境（Vercel Edge Functionsなど）ではコールドスタートとペイロードサイズの影響が大きく、GraphQLよりtRPC/RESTの軽量なリクエスト構造の方がレイテンシ面で有利。Next.js 16のApp Router構成では、Route HandlersとtRPCの組み合わせが実用上もっとも素直な選択になる。

### 4. serverless edge computing 2026

- **ポイント1:** エッジでのLLM推論（Cloudflare Workers AI、Vercel Edge Functions等）がコールドスタート問題を解消し、ユーザーに近い場所でのレイテンシ最小化が標準化している。弊社でも画像最適化やレコメンド処理をエッジ化すれば表示速度改善が見込める。
- **ポイント2:** WebAssembly(WASM)ベースのランタイムがNode.js依存のサーバーレスより軽量・高速に動作し、2026年にはNext.jsのMiddleware/Edge Runtimeとの統合がさらに進んでいる。
- **ポイント3:** データレイヤーのエッジ化（Turso, PlanetScale, Cloudflare D1など）により「エッジで計算、エッジでデータ」が実現しつつあり、グローバル展開時のDB遅延問題を根本解決できる。
- **ポイント4:** コールドスタート課金モデルからリクエスト単位の超低コスト課金へ移行が進み、トラフィックが不安定な新規サービス（物件検索のピーク対応など）にコスト面で有利。
- **ポイント5:** エッジでの認証・パーソナライゼーション処理（JWT検証、A/Bテスト振り分け）がオリジンサーバー負荷を下げるパターンが定着しており、sumitsugiの物件検索・一覧表示の高速化に応用できる可能性がある。

### 5. authentication security best practices 2026

- **パスキー/FIDO2への完全移行:** パスワードベース認証からWebAuthn/パスキーへの移行がデフォルトとなり、フィッシング耐性のある認証をユーザー登録時点で強制することで、認証情報漏洩インシデントを構造的に排除できる。

- **ゼロトラスト前提のセッション管理:** トークンの寿命を短く保ち、デバイスフィンガープリントやIPリスクスコアと組み合わせた継続的な検証（Continuous Authentication）を行うことで、セッションハイジャックのリスクを下げつつUXを損なわない設計が主流になっている。

- **BFF（Backend For Frontend）パターンでのトークン管理:** アクセストークン・リフレッシュトークンをクライアント（ブラウザ/モバイル）に直接持たせず、サーバーサイドのBFFでhttpOnlyセッションとして管理することで、XSS経由のトークン盗取リスクを大幅に低減できる。sumitsugiのようなNext.js App Router構成では、Route HandlersをBFF層として活用しやすい。

- **多層防御としてのレート制限とボット検知:** 認証エンドポイント（ログイン・パスワードリセット・OTP検証）に対するクレデンシャルスタッフィングやブルートフォース攻撃を防ぐため、IP単位・アカウント単位の多層レート制限とCAPTCHA/行動分析を組み合わせることが標準的なベストプラクティスになっている。

- **監査ログとインシデント対応の自動化:** 認証イベント（ログイン失敗、パスワード変更、新規デバイス登録）を構造化ログとして記録し、異常検知を自動でアラート・自動ロックにつなげる仕組みが、セキュリティ侵害の早期発見において重要度を増している。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** PrismaはSupabaseのPgBouncer（トランザクションモード）との接続プール競合が長年の課題だったが、2026年時点では`directUrl`分離構成とPrisma Accelerateの組み合わせがデファクトとなり、サーバーレス環境（Vercel等）でのコネクション枯渇を回避できる。
- **ポイント2:** SupabaseのRow Level Security（RLS）とPrismaのORM層は責務が重複しやすく、「認可はDB側（RLS）、型安全なクエリ構築はPrisma」という分離を徹底しないと、セキュリティロジックが二重管理になりバグの温床になる。
- **ポイント3:** PrismaのEdge対応（Driver Adapters経由でSupabaseのPostgREST/pgを利用）が成熟してきており、Next.js 16のEdge RuntimeでDBアクセスを行う場合はこの構成を前提にスキーマ設計すべき。
- **ポイント4:** マイグレーションはPrisma Migrateで管理しつつ、Supabase側のダッシュボード操作（手動スキーマ変更）を併用すると差分がズレる事故が多発するため、「Supabaseダッシュボードでの直接スキーマ編集禁止、全てPrisma Migrate経由」をチーム運用ルールとして明文化すべき。
- **ポイント5:** sumitsugiのような`draft`/`public`のステータス管理を持つプロダクトでは、Supabase Realtimeとの併用で住人向けのライブ更新（物件公開時の即時反映）を実装しやすく、PrismaのスキーマからRealtime購読対象テーブルを明示的に分離しておくとパフォーマンス管理がしやすい。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGCとコンポーネントモデルの普及により、RustからWasmへのコンパイルがより軽量なバイナリと高速な起動時間を実現しつつある。Next.jsのSSR環境でも、重い計算処理（画像変換・PDF生成等）をWasmモジュールにオフロードすることで、Node.jsランタイムのボトルネックを回避できる。
- **ポイント2:** wasm-bindgen/wasm-packのツールチェーンが成熟し、TypeScriptとの型連携が改善されたため、フロントエンドでの導入コストが下がっている。ただしバンドルサイズへの影響は依然大きく、Next.jsのCode Splittingと組み合わせて遅延読み込みする設計が必須。
- **ポイント3:** SIMD対応とマルチスレッド（Web Workers + SharedArrayBuffer）がブラウザ側で標準的に使えるようになり、クライアントサイドでの画像・文書処理（物件写真の最適化など）がネイティブに近い速度で動く。sumitsugiのような物件写真多用サービスでは、アップロード時のクライアント側リサイズ処理に活用できる可能性がある。
- **ポイント4:** サーバーサイドではWasmtime/WASIのエッジランタイム採用が進み、Vercel Edge Functions等でRust製Wasmを動かすケースが増えている。レイテンシに厳しい検索・フィルタリング処理をエッジで実行する選択肢として検討価値がある。
- **ポイント5:** パフォーマンス面では「Wasmだから速い」は神話に近づいており、実際の優位性はJSエンジンのJITと拮抗するケースも多い。導入判断は計算集約的な処理（画像処理・暗号化・大規模データ変換）に限定し、通常のビジネスロジックには適用しないのが2026年時点のベストプラクティス。

### 8. Next.js App Router patterns 2026

- **部分プリレンダリング（PPR）の標準化:** Next.js 15〜16でStableとなったPartial Prerenderingにより、静的シェルを即時配信しつつ動的部分のみストリーミングする構成が標準パターンに。物件一覧ページのように「検索UIは静的、結果は動的」といった画面に特に有効。

- **Server Actionsによるフォーム処理の一元化:** APIルートを別途作らず`"use server"`でミューテーションを直接Server Componentsから呼べるため、物件登録や引越し費用の問い合わせフォームなどで型安全なエンドツーエンドの実装が可能。ただしCSRF対策（Originヘッダー検証）は自動ではないため明示的な実装が必要。

- **Cache Componentsとキャッシュ戦略の明確化:** 旧`fetch`キャッシュの曖昧さが解消され、`use cache`ディレクティブでコンポーネント単位のキャッシュ境界を明示的に宣言するパターンが浸透。公開物件データ（`status: 'public'`）のような準静的データに向き、再検証ロジックが追いやすくなる。

- **Server/Client境界の最小化設計:** 「Client Componentは葉（leaf）に限定し、できるだけ下層に配置する」という設計原則がより重視され、認証状態やインタラクションが必要な部分だけを`auth-context`経由でクライアント化し、それ以外はServer Componentsに留める構成がベストプラクティスとして定着。

- **並列ルートとIntercepting Routesの実用拡大:** モーダル表示の物件詳細（一覧ページ上にオーバーレイしつつURLは`/listing/[id]`を指す)のようなUXが、`(.)`構文のIntercepting RoutesとParallel Routesの組み合わせで実装しやすくなり、ECサイト的なクイックビューパターンがAirbnb風UIにも応用されつつある。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Runtime はNode.js APIの一部（`fs`やネイティブモジュール等）が使えないため、重い処理はEdgeではなくサーバーレスFunctionsに残し、「低レイテンシが効くルーティング/パーソナライゼーション/認証チェック」だけをEdgeに切り出す設計が定着してきている。

- **ポイント2:** Vercelの`waitUntil()`やストリーミングレスポンスを活用することで、ユーザーへの応答を待たせずにログ送信・キャッシュ更新などの後処理をバックグラウンド化できる。引越し費用計算やお気に入り記録のような非同期処理に向いている。

- **ポイント3:** Edge Config / Edge Middlewareを使ったA/Bテストやフィーチャーフラグ判定はコールドスタートがほぼゼロで、`'draft'`/`'public'`ステータスの表示切り替えのようなリクエスト単位の軽い分岐処理に適している。

- **ポイント4:** リージョン指定（`regions`オプション）をデータベースの物理ロケーションに合わせることがコスト・レイテンシ両面で重要。DBから遠いEdgeノードで実行すると往復遅延がボトルネック化するため、DB至近リージョンへのピン留めが2026年のベストプラクティス。

- **ポイント5:** 計測コスト（実行時間・帯域課金）が従来のサーバーレスより細かく発生するため、画像変換や大きめJSON処理をEdgeで行うとコスト効率が悪化する。静的化・ISRでキャッシュできる部分は極力EdgeではなくCDNキャッシュ側に逃がす判断が必要。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x系で導入された`const`型パラメータやconst assertionの活用が標準化し、リテラル型推論の精度が向上。APIレスポンスや状態管理の型を手動で書かずに、実データ構造から安全に推論できるケースが増えている。
- **ポイント2:** Zodなどのスキーマライブラリと型定義を一元化する「スキーマファースト」設計がデファクト化。システム境界（APIリクエスト、フォーム入力）でランタイム検証と型推論を同時に行い、`z.infer<typeof schema>`で型の二重管理を防ぐパターンが定着している。
- **ポイント3:** `satisfies`演算子の実務活用が進み、型の広域化（widening）を防ぎながら構造チェックを行う書き方が一般化。Union型やdiscriminated unionを使う際に、網羅性チェック（exhaustiveness check）を`never`型でコンパイル時に強制する手法も合わせて普及している。
- **ポイント4:** モノレポ構成でのプロジェクト参照（`tsconfig`の`references`）とインクリメンタルビルドの最適化が、ビルド時間短縮の鍵として重視されるように。型チェックとビルドパイプラインの分離（`tsc --noEmit`をCIの型チェック専用ステップにする等）がベストプラクティスとして広がっている。
- **ポイント5:** Branded Types（nominal typingのエミュレーション）によるID型の誤用防止が、特にドメインモデルが複雑なプロダクトで採用が進んでいる。例えば`UserId`と`PropertyId`を構造的には同じ`string`でも型レベルで区別し、取り違えバグをコンパイル時に検出する手法が実務で広がっている。
