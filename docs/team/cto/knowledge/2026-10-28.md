# CTO Knowledge - 2026-10-28

## Daily Update (2026-10-28)

### 1. Next.js performance optimization 2026

- **ポイント1（Turbopackのデフォルト化）:** Next.js 16ではTurbopackが開発・本番ビルド双方でデフォルトになり、大規模コードベースでもビルド時間とHMR速度が大幅に改善。本プロジェクトのような中規模アプリでも`bun run build`の時間短縮が期待できる。
- **ポイント2（Partial Prerendering / Cache Components）:** 静的部分と動的部分を同一ページ内で混在させ、静的シェルを即時配信しつつ動的データをストリーミングする手法が標準化。物件一覧や詳細ページのように「共通レイアウトは静的、在庫情報は動的」な構成に適している。
- **ポイント3（キャッシュ戦略の明示化）:** `fetch`のキャッシュ挙動がより明示的なAPI（`cacheLife`/`cacheTag`等）に移行し、「何をどれだけキャッシュするか」をコードで宣言する設計が推奨される。曖昧な暗黙キャッシュに依存しないことで、ステータス変更（`draft`/`public`）のような状態遷移時の不整合リスクを下げられる。
- **ポイント4（Server ComponentsとClient Bundleの最小化）:** インタラクティブ性が必要な部分だけをClient Componentに限定し、フォームや認証ロジック以外はServer Componentで完結させることで、初期JSバンドルを削減。LCPやTTIの改善に直結する。
- **ポイント5（画像・フォント最適化の自動化）:** `next/image`と`next/font`の最適化パイプラインが強化され、特に物件写真のような画像中心のUIでは、レスポンシブ配信とレイアウトシフト抑制を手動実装なしで実現できる。

### 2. React Server Components streaming 2026

- **ポイント1:** Partial Prerendering（PPR）がNext.js 16で標準化され、静的シェルを即時返しつつ動的部分だけをストリーミングする設計がデフォルトパターンに。初期表示速度（TTFB/LCP）と動的データの両立が、ページ単位の`loading.tsx`分割より細粒度で実現しやすくなっている。
- **ポイント2:** Suspenseバウンダリの粒度設計がパフォーマンスチューニングの中心課題に。境界を細かく切りすぎるとウォーターフォール（直列fetch）が発生しやすく、`Promise.all`的な並列データ取得とバウンダリ配置をセットで設計する必要がある。
- **ポイント3:** `cache()` / `use cache`ディレクティブを使ったサーバー側のリクエストメモ化・キャッシュ制御が一般化し、RSCツリー内での重複fetchを防ぐ設計がデフォルトのベストプラクティスになってきている。
- **ポイント4:** クライアントコンポーネントとの境界（`'use client'`）をどこに置くかがバンドルサイズとストリーミング効率に直結するため、「できるだけ葉に近い位置でクライアント化する」原則がより厳格に求められる。sumitsugiのようなリスティング中心のUIでは画像ギャラリーやフィルタUIなど対話要素だけをクライアント化すると効果的。
- **ポイント5:** エッジランタイム（Edge Runtime）とRSCストリーミングの組み合わせで、地理的に近いサーバーからの初期ストリーム配信が可能になり、物件検索のような地域性の高いサービスではTTFB改善の実用的な選択肢になっている。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCがモノレポ・フルスタックTypeScript構成で主流化しており、クライアント・サーバー間の型を自動共有できるためスキーマ定義（OpenAPI/GraphQL SDL）の二重管理が不要になる。sumitsugiのようなNext.js App Router単一リポジトリ構成では、tRPC導入でAPI層のボイラープレートを大幅削減できる。

- **ポイント2:** GraphQLは「複数クライアント・複数チームが同一バックエンドを叩く」大規模組織向けに残存領域が収束しつつあり、単一フロントエンド+単一バックエンドの中小規模プロダクトではオーバーエンジニアリングになりがち。現状の物件一覧・検索のようなクエリパターンはREST/tRPCの素朴な実装で十分なケースが多い。

- **ポイント3:** RESTは依然としてpublic API・サードパーティ連携・Webhookの事実上の標準で、2026年もOpenAPI 3.1 + JSON Schemaによる契約駆動開発が定着している。内部UI向けAPIと外部公開APIを分離し、内部はtRPC、外部連携（決済・外部弁護士向け書類連携など）はREST/OpenAPIという併用が現実的な選択肢。

- **ポイント4:** Server Actions（Next.js App Router）とtRPCの境界が曖昧になりつつあり、単純なCRUD（物件のdraft/public切り替え等）はServer Actionsで十分、複雑なクエリ・バリデーション・リアルタイム要件がある箇所のみtRPC/APIルートに切り出す、という「必要な箇所だけAPI層を作る」設計が2026年のベストプラクティス。

- **ポイント5:** 認証・入力検証はZodスキーマをAPI境界（tRPCプロシージャ入口、Server Actions入口）に一元化し、型とランタイム検証を一致させる構成が標準化している。現行の`.claude/rules/standards.md`方針（Zod境界検証）とも整合するため、新規API実装時はこのパターンを維持すべき。

### 4. serverless edge computing 2026

- **ポイント1:** エッジでのAI推論（LLM軽量モデル含む）がCDN事業者の標準機能化し、CloudflareやVercelのEdge Runtimeでミリ秒単位のレイテンシを実現できるようになっている。リアルタイムパーソナライゼーションや物件検索のレコメンドにも応用可能。

- **ポイント2:** WASM（WebAssembly）がエッジランタイムの事実上の標準になり、Node.js互換APIの制約を受けずにNext.jsのMiddleware/Edge Functionsで複雑なロジックを実行できる環境が整ってきている。

- **ポイント3:** コールドスタート問題がV8 Isolate方式の普及でほぼ解消され、サーバーレスでも常時起動並みの応答速度が得られるため、物件検索や予約フローのようなユーザー体感速度が重要な箇所にはエッジ処理を優先的に使う価値が高い。

- **ポイント4:** データの地理分散（エッジKV/エッジDB、例: Cloudflare D1やTurso）が進み、グローバル分散でも整合性を保ちやすくなったが、強整合性が必要な決済・契約データは依然リージョン固定のDBに置くべきというトレードオフ判断が重要。

- **ポイント5:** エッジ実行はコスト効率が高い一方、ベンダーロックインのリスクが大きいため、移行可能性を保つには標準Web API（Fetch, Request/Response）準拠のコードを書き、特定ベンダーのSDKに依存しすぎない設計が推奨される。

### 5. authentication security best practices 2026

- **パスキー/WebAuthnへの移行:** フィッシング耐性のあるパスキー認証がデフォルト化しており、パスワード+SMS認証は非推奨。NextAuth.js等でWebAuthn対応プロバイダを早期に導入すると移行コストを抑えられる。

- **短命トークン+リフレッシュローテーション:** JWTのアクセストークンは15分以内の短命化が標準になり、リフレッシュトークンもワンタイム使用+再利用検知（Refresh Token Rotation）が必須。長命トークンの漏洩リスクを大幅に下げられる。

- **リスクベース適応認証:** デバイス指紋・IPレピュテーション・行動パターンを組み合わせたアダプティブMFAが主流化。高リスクログイン（新規デバイス・異常地域）時のみ追加認証を求めることでUXとセキュリティを両立できる。

- **非人間アイデンティティの管理強化:** APIキーやサービスアカウントなどマシン間認証の漏洩がインシデントの主要因となっており、Secrets Manager（Vault/AWS Secrets Manager等）でのシークレット自動ローテーションが前提になっている。sumitsugiのようにSupabase/外部APIキーを使う構成では特に優先度が高い。

- **CSRF/セッション管理のサーバーサイド強化:** SameSite=Strict Cookie + サーバーサイドセッション検証の組み合わせが標準となり、クライアントローカルストレージへのトークン保存は非推奨。auth-context.tsxのようなクライアント側コンテキストでもトークン本体は保持せず、httpOnly Cookie経由でのセッション確認に限定するのが安全。

### 6. database architecture Prisma Supabase 2026

- **Prisma ORMの進化:** Prisma 6以降はRustエンジンへの依存を減らし、TypeScript純正のクエリコンパイラ（Prisma ORM with driver adapters）に移行しており、Supabaseのようなエッジ環境やサーバーレスでのコールドスタートが大幅に改善されている。本プロジェクトでNext.js App Router + Edge Runtimeを使う場合はdriver adapter構成を前提に設計すべき。

- **Supabase + RLS中心設計:** Row Level Security (RLS)をアプリ層ではなくDB層で強制する設計が主流になっており、`seller`/`buyer`のようなロール分離があるsumitsugiのようなマーケットプレイス型プロダクトでは、Prismaのクエリに加えてSupabase側RLSポリシーを二重で定義し、権限漏れを防ぐのがベストプラクティス。

- **Connection Pooling必須化:** サーバーレス関数（Vercel/Next.js）からSupabase Postgresへの直接接続はコネクション枯渇を招くため、PgBouncer経由のTransaction Pooler（Supavisor）を使うことが前提になっている。Prisma schemaで`directUrl`（マイグレーション用）と`url`（プール経由・実行時用）を分離するのが定番構成。

- **スキーマ変更のCI統合:** `prisma migrate diff`をCIパイプラインに組み込み、破壊的変更（カラム削除・型変更）を自動検知してPRをブロックする運用が増えている。`'draft' | 'public'`のようなUnion型ステータスを変更する際は、マイグレーションとTypeScript型定義を同時にレビューする仕組みが事故防止に有効。

- **pgvector + AIレコメンド:** Supabaseのネイティブpgvectorサポートを使い、物件検索やマッチング（IC consultation matching等）にベクトル検索を組み込むケースが増加。既存のPrisma管理テーブルと共存させる際は、ベクターカラムのみ生SQLマイグレーションで追加しPrisma側は`Unsupported`型でマッピングするのが現実的な落とし所。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Rustの`wasm-bindgen`/`wasm-pack`ツールチェーンは2026年時点で最適化がさらに進み、JS/TypeScriptバインディング生成のオーバーヘッドが大幅に削減されている。Next.js App Routerとの統合では、重い計算処理（画像変換、PDF生成等）をWasmモジュールに切り出すことでNode.jsランタイムの負荷を下げられる。

- **ポイント2:** Component Model（WASI Preview 2）の標準化が進み、言語間の相互運用性が向上した。sumitsugiのような物件マッチング・検索処理を将来的に高速化する際、Rust製Wasmモジュールをエッジ（Vercel Edge Functions等）で動かす選択肢が現実的になっている。

- **ポイント3:** SIMDとマルチスレッド（Shared Memory + Web Workers）のサポートがブラウザ標準として定着し、画像処理や大量データのクライアントサイド処理（物件写真の圧縮・リサイズ等）でネイティブに近い性能が出せる。

- **ポイント4:** バンドルサイズが依然最大の課題。`wasm-opt`やLTOでの最小化は必須で、Next.jsのコード分割と組み合わせて初回ロードに影響しないよう遅延読み込みする設計が実用上のベストプラクティス。

- **ポイント5:** 現状のMVPフェーズではWasm導入の優先度は低い——引き継ぎフローや法務対応が先であり、パフォーマンスボトルネックが明確になった時点（例: 大量物件データの検索・フィルタリング速度）で導入を検討するのが合理的。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR)の標準化:** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分のみストリーミングする構成が主流に。初期表示速度(TTFB)を犠牲にせずパーソナライズされたコンテンツを扱える。

- **Server Actionsのセキュリティ強化が必須:** Server Actionsは便利だが外部公開APIと同等のアタックサーフェスを持つため、Zodによる入力検証と認可チェックをアクション内部で必ず行う設計が定着している。CSRF対策はNext.js側で改善されたが、過信は禁物。

- **`use cache`ディレクティブによる明示的キャッシュ制御:** 従来の暗黙的fetchキャッシュから、関数単位で`use cache`を明示する方式に移行。キャッシュ境界が読みやすくなり、再検証(revalidateTag)の設計がコンポーネント単位で見通しやすくなった。

- **Route Handlersとデータ取得の責務分離:** App RouterではRSCから直接DBアクセスする設計が増えたが、テスト容易性と将来のAPI公開を見据え、`src/lib/data.ts`のようなデータアクセス層を薄く保つパターンが推奨されている（本プロジェクトの`src/lib/data.ts`もこの方針に合致）。

- **ビルド時の型安全性チェックがCIのボトルネックに:** App RouterのルートパラメータやSearch Paramsの型が複雑化しており、`bun run build`でのみ検出される型エラーが増加。CIにbuildステップを必ず含めることが、ESLintやユニットテストだけでは防げない不具合の最終防衛線になる。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Fluid Compute との統合深化:** Vercel の Fluid Compute モデルがEdge Functionsとの境界を曖昧にし、コールドスタート抑制とインスタンス再利用が標準化。同時実行リクエスト間でCPU/メモリを共有できるため、レイテンシに敏感なAPIルートのコスト効率が大幅に改善される。

- **ポイント2: リージョン指定とデータ局所性の最適化:** `sumitsugi`のようなDB依存処理ではEdge RuntimeよりNode.js RuntimeをPrimaryリージョンに固定する方が速い場合が多く、2026年のベストプラクティスは「Edgeは静的・認証チェック・リダイレクトのみ、DB読み書きはリージョナルFunctionに委譲」というハイブリッド構成。

- **ポイント3: Streaming + Partial Prerendering(PPR)との併用:** Next.js 16のPPRがEdge Middlewareと組み合わさることで、静的シェルを即時配信しつつ動的部分（在庫・価格等）だけをストリーミングする設計が主流化。物件一覧ページのようなページで初期表示速度(TTFB)を大幅短縮できる。

- **ポイント4: 可観測性コストの増大に注意:** Edge Functions の実行数増加に伴い、ログ・トレーシングのコストが見えにくく膨らむ傾向。`Vercel OpenTelemetry`連携で計測しつつ、不要なMiddleware実行（全ルードマッチなど）を`matcher`設定で絞ることが2026年のコスト最適化の定石。

- **ポイント5: セキュリティ境界としての活用:** Edge Middlewareでのレート制限・Bot検知・認証トークン検証がオリジンへの到達前に完結する構成が標準化しつつあり、認証系（`auth-context.tsx`連携）やフォーム送信系のDoS耐性向上に直結する。

### 10. TypeScript type safety patterns 2026

- **型レベルプログラミングの成熟:** TypeScript 5.x系でテンプレートリテラル型やconst型パラメータが実用段階に入り、APIレスポンスの型をバックエンドのスキーマから自動生成するパターンが標準化しつつある。Zodなどのスキーマライブラリと組み合わせ、ランタイム検証と型を単一ソースから導出する手法が定着している。

- **"Branded Types"によるドメイン制約:** `string`や`number`のプリミティブ型をそのまま使わず、`UserId`や`Email`のようにブランド化した型で区別することで、取り違えバグをコンパイル時に検出する設計が広がっている。本プロジェクトでも物件ステータス(`'draft' | 'public'`)のようなUnion型管理に同様の厳格さが求められる。

- **`satisfies`演算子の定着:** 型推論を狭めすぎずに型チェックだけ行う`satisfies`が設定オブジェクトや定数定義で標準的な書き方になり、過剰な型アサーション(`as`)を避けられる。

- **End-to-Endの型安全性:** tRPCやHono RPCのようなフレームワークで、サーバーからクライアントまで型を一本化する流れが加速しており、Next.js App RouterのServer Actions連携でも同様の型共有パターンが広まっている。

- **型チェックのCI必須化:** `tsc --noEmit`をCIパイプラインに組み込むことが業界標準となり、ESLint・テストだけでは検出できない型不整合を早期に捕捉する運用が当たり前になっている（本プロジェクトのBuild Integrity方針と一致）。
