# CTO Knowledge - 2026-05-29

## Daily Update (2026-05-29)

### 1. Next.js performance optimization 2026

- **React Server Components の徹底活用:** RSCをデフォルトとし、クライアントコンポーネントを最小化することでJSバンドルサイズを劇的に削減できる。`'use client'`境界を意識的に設計しないと、せっかくのApp Routerのメリットが失われる。

- **Partial Prerendering (PPR) の本番投入:** 静的シェルと動的ストリーミングを同一ルートで組み合わせるPPRがNext.js 15以降で安定化し、TTFB改善とダイナミックコンテンツの両立が現実的になった。

- **`use cache` ディレクティブによる細粒度キャッシュ:** `fetch`キャッシュに依存せず、関数・コンポーネント単位でキャッシュ戦略を宣言できるため、過剰な再レンダリングを防ぎつつデータ鮮度を制御しやすくなった。

- **Turbopack のデフォルト採用:** dev環境でのビルド速度が従来比最大10倍向上しており、DX改善だけでなくCI/CDのビルド時間短縮にも直結する。本番bundlerとしての成熟度も上がり移行障壁が低下している。

- **Server Actions のN+1問題に注意:** Server Actionsは手軽だが、ループ内での呼び出しやウォーターフォールが発生しやすい。`Promise.all`での並列化やデータ取得のバッチ化を意識しないと、REST時代と同じパフォーマンス問題が再現する。

### 2. React Server Components streaming 2026

- **ポイント1:** RSCのStreaming + Suspenseの成熟により、2026年時点でNext.js 15/16ではPPR（Partial Prerendering）が安定稼働し、静的シェルと動的コンテンツの段階的配信がデフォルト化しつつある。

- **ポイント2:** `use()` フックの普及でClient Component側でもPromiseをストリーム的に消費できるようになり、Server→Clientのデータフロー設計が大幅にシンプル化された。

- **ポイント3:** Turbopackの本番対応により開発時のHMRとビルドが高速化され、RSC境界を多数設けてもローカル開発体験が劣化しなくなった点は実務上の大きな改善。

- **ポイント4:** Server Actions + optimistic updateのパターンが確立され、フォーム/ミューテーション系機能でクライアントJSを極小化しながらリアルタイムなUXを実現できる。これにより本プロジェクトのような物件管理フローにも有効。

- **ポイント5:** ただしストリーミングはキャッシュ戦略（`cache()`、`revalidateTag`）と相性が複雑で、CDNエッジでのキャッシュヒット率低下に注意が必要。2026年の実運用では「何をストリームし何をキャッシュするか」の設計判断がパフォーマンスの分岐点になる。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** tRPCはNext.js/TypeScriptスタックで急速に採用が進み、API境界でのランタイムエラーをゼロにできるため、2026年時点でスタートアップの標準選択肢になりつつある。

- **GraphQLの選択基準の明確化:** 複数クライアント（Web/モバイル/パートナー連携）を持つ大規模プロダクトではGraphQLが依然優位だが、単一フロントエンドの場合はオーバーエンジニアリングになるケースが多く、採用前の費用対効果の精査が必須。

- **REST + OpenAPIの復権:** Hono・ElysiaなどのEdgeランタイム対応フレームワークがOpenAPI自動生成をサポートし、型安全なRESTクライアントを低コストで実現できるため、「tRPCかGraphQLか」でなくRESTに戻る選択肢も現実的になっている。

- **Server Actions / RSCによるAPI層の省略:** Next.js 15以降のReact Server Componentsとサーバーアクションにより、単純なCRUDはAPIエンドポイントを作らずにサーバー関数を直接呼び出すパターンが主流化しており、API設計の意思決定範囲が変化している。

- **実用指針:** チーム規模・クライアント数・型安全性要件で選択する——「単一TS monorepo」→tRPC、「マルチクライアント・スキーマ駆動」→GraphQL、「外部公開API」→REST+OpenAPI、「小規模RSCアプリ」→Server Actionsで検討するのが現時点のベストプラクティス。

### 4. serverless edge computing 2026

- **ポイント1: WebAssembly（Wasm）がエッジのデファクトランタイムに:** Cold startが事実上ゼロになりV8 Isolate（Cloudflare Workers等）と並ぶ主流となり、言語非依存でエッジデプロイが可能になった。既存のRust/Go資産をそのままエッジに持ち込めるため、移行コストが大幅に低下。

- **ポイント2: AIインファレンスのエッジシフトが加速:** LLMの量子化（INT4/INT8）と専用NPUチップの普及により、レイテンシ敏感な推論をエッジで完結させるアーキテクチャが現実的になった。中央クラウドへのラウンドトリップなしにパーソナライズ処理が可能。

- **ポイント3: Durable Objectsパターンの標準化:** ステートレス前提だったエッジにCRDTベースの分散状態管理が組み込まれ、「エッジ＝ステートレス」という制約が崩れた。リアルタイムコラボ機能をエッジで完結できるようになりDBへの書き込み頻度を削減できる。

- **ポイント4: マルチCDN/エッジメッシュの台頭:** 単一ベンダー（Cloudflare・Vercel・Fastly）への依存リスクを避けるため、OpenTelemetryと標準化されたWorker APIでポータビリティを確保しながら複数エッジを束ねる設計が重要になっている。

- **ポイント5: コールドスタート問題の終焉とコスト構造の変化:** 常時起動型インスタンスが不要になりリクエストベース課金が徹底されるが、エッジリージョン数に比例してオブザーバビリティコスト（ログ・トレース転送量）が膨張する逆転現象に注意が必要。

### 5. authentication security best practices 2026

**CTOとして — Authentication Security Best Practices 2026**

- **パスキー（FIDO2/WebAuthn）への本格移行:** パスワードはもはや負債。Apple/Google/Microsoftのパスキーエコシステムが成熟した2026年時点では、新規サービスはパスワードレス設計をデフォルトとすべきで、フィッシング耐性が本質的に担保される。

- **ゼロトラスト＋継続的認証:** 「ログイン時に一度だけ認証」モデルは終焉。セッション中も行動バイオメトリクス（タイピングパターン、操作リズム）でリスクスコアをリアルタイム評価し、異常時に再認証を要求するアーキテクチャが標準化されつつある。

- **AIによる不正ログイン検知の高度化:** 攻撃側もAIを使うクレデンシャルスタッフィングが急増しており、防御側もML based anomaly detectionが必須。IPレート制限だけでは不十分で、デバイスフィンガープリント＋地理的速度チェックを組み合わせる多層防御が求められる。

- **ポスト量子暗号（PQC）の先行導入:** NISTがML-KEM/ML-DSAを標準化した今、セッショントークンや長期鍵の暗号化アルゴリズムをPQC対応に切り替えるロードマップを持つことが技術的負債を避ける鍵。特に金融・医療系は規制対応の観点でも早急。

- **トークン設計の見直し（短命化＋バインディング）:** JWTの長期有効期限は脆弱性の温床。アクセストークンは15分以内、リフレッシュトークンはデバイス/IPにバインドするDPoP（Demonstrating Proof of Possession）を採用し、トークン窃取時の被害範囲を最小化する設計が2026年のベストプラクティス。

### 6. database architecture Prisma Supabase 2026

**2026年 Database Architecture: Prisma × Supabase の重要トレンド**

- **Prisma Postgres の台頭:** Prisma社が自社マネージドPostgresサービスをリリースし、Accelerate（接続プーリング＋キャッシュ）との統合が完成形に近づいた。Supabaseとの組み合わせよりも「Prisma一本」で完結させる構成が増えている。

- **Supabase Branching の実用化:** データベースのブランチ機能が安定し、PRごとにステージング環境を自動作成できる開発フローが標準化。Next.jsのPreview Deploymentsと組み合わせるとCI/CDの品質が大幅に向上する。

- **pgvector × Edge Functionsの標準化:** AIアプリ需要でSupabaseのpgvector活用が急増。ベクトル検索とRLSを組み合わせたマルチテナント設計が重要なアーキテクチャパターンとなった。

- **Prisma Pulse（リアルタイムCDC）の普及:** データベース変更をリアルタイムにストリーミングするPrisma Pulseが実用レベルに。Supabase Realtimeと役割が競合するため、どちらを採用するかはアーキテクチャ上の重要な判断点になっている。

- **型安全なRPC vs ORM:** Supabaseの`supabase-js`が生成する型定義の精度が向上し、複雑なJOINクエリでもPrismaと遜色ない型安全性を実現。シンプルなCRUDならSupabase直接呼び出し、複雑なビジネスロジックはPrismaという使い分けが現実的。

- **WebAssembly Component Modelの本格普及:** 2026年はWASI 0.2とComponent Modelが標準化され、RustのWasm出力が言語間インターフェースとして実用レベルに到達。マイクロサービス間の型安全な境界としての採用が加速している。

- **WasmGC対応でRustの優位性が再定義:** ガベージコレクション対応のWasmGCが主要ランタイムに展開されたことで、Rust固有のメモリ効率の強みが相対化。一方でゼロコスト抽象化による予測可能なレイテンシはリアルタイム処理で依然として圧倒的優位。

- **JIT並みの実行速度をAOTで実現:** Wasmtime・V8のコンパイラ最適化が成熟し、RustのリリースビルドWasmはネイティブの80〜95%の性能を安定して達成。コールドスタートのレイテンシが課題だったがLazy compilationで大幅改善。

- **SIMD・スレッド拡張の実用化:** Fixed-width SIMDと`wasm-bindgen`経由のWeb Workersが安定し、Rust製の画像処理・音声コーデック・ML推論がブラウザ上でネイティブに迫る性能を発揮。`rayon`のWasm対応も進んでいる。

- **Fermyon/Fastly等のWasm-nativeエッジでRustが事実上の標準:** エッジコンピューティング環境ではコールドスタートが最重要指標であり、Rustの軽量バイナリ（〜100KB台）とゼロランタイムオーバーヘッドがGoやPythonに対して構造的優位を維持している。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** クライアントコンポーネントは本当にインタラクティビティが必要な部分だけに限定し、データフェッチ・ビジネスロジックはすべてServer Componentsで処理することで、バンドルサイズを大幅に削減できる。

- **Partial Prerendering (PPR) の実用化:** 静的シェルと動的コンテンツを同一ページで混在させるPPRが安定化し、`<Suspense>`境界を戦略的に配置することで、TTFBを損なわずにパーソナライズドコンテンツを配信できる。

- **Server Actions によるAPI層の省略:** フォームやミューテーション処理にREST APIエンドポイントを作らず、Server Actionsを直接使用するパターンが主流に。ただし、バリデーション（Zod）とエラーハンドリングを必ず実装すること。

- **Streaming と Suspense の組み合わせ:** `loading.tsx`だけでなく、`<Suspense>`を細粒度で配置してウォーターフォールを回避し、重いデータフェッチを並列実行することでLCPを改善できる。

- **`use cache` ディレクティブによるきめ細かいキャッシュ制御:** Next.js 15以降で安定した`use cache`により、関数・コンポーネント単位でキャッシュ戦略を定義可能。`revalidateTag`と組み合わせることで、CMSやDBの更新を即時反映できる。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge RuntimeでのStreaming Response活用:** 2026年はStreaming Server-Sent Events（SSE）とReadableStreamの組み合わせがAI応答配信の標準になっており、初回バイトまでの時間（TTFB）を最大80%削減できる。

- **ポイント2: Cold Start撲滅のためのWarm Pooling戦略:** Vercelは`edge`ランタイムでWasmモジュールのキャッシュをリージョン間で共有する仕組みを強化しており、重いJWTライブラリをWasmに変換してEdge側に置くことがベストプラクティスになっている。

- **ポイント3: KV/R2との組み合わせによるデータ局所性最適化:** Edge FunctionsとVercel KV（Redis互換）を同一リージョンに配置するZone Affinity設定が重要で、地理的に離れたデータソースへのラウンドトリップがレイテンシのボトルネックになりがち。

- **ポイント4: Middleware Chainingの最小化:** Next.jsのMiddlewareは直列実行されるため、認証・A/Bテスト・リダイレクトを単一の薄いMiddlewareに集約し、不要な`matcher`パターンを削ることがCPU時間節約の鍵となっている。

- **ポイント5: バンドルサイズの1MB制限への対応:** Edge RuntimeはNode.js全APIを使えないため、`crypto`や`fetch`はWeb標準APIに置き換え、依存関係を定期的に`@vercel/edge-config`で計測してバンドルサイズを監視する仕組みをCIに組み込むことが必須。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly __brand: 'UserId' }` のようなBranded Typesが標準化し、ランタイムエラーをコンパイル時に防ぐパターンが2026年に主流となった。特にDDDアーキテクチャとの相性が良い。

- **`satisfies` 演算子の活用拡大:** TypeScript 4.9で導入された `satisfies` が型推論の精度を維持しつつ型チェックを強制する用途で定着。`as const satisfies Type` の組み合わせでリテラル型の保持と型安全性を両立できる。

- **Template Literal Types によるAPIコントラクト:** `type Route = \`/api/${string}\`` のようなTemplate Literal Typesで、URLパターンやイベント名などの文字列制約をコンパイル時に検証。Runtime validationとのギャップを埋める重要な手法。

- **`noUncheckedIndexedAccess` の必須化:** `tsconfig.json` の `noUncheckedIndexedAccess: true` が"strict mode 2.0"として業界標準に。配列・オブジェクトアクセスの `undefined` を型レベルで強制処理させ、null安全性を大幅に向上できる。

- **Zod + tRPC による境界型安全:** 外部データとの境界（APIレスポンス、フォーム入力、環境変数）をZodスキーマで定義し、tRPCやHono RPCで型をサーバー・クライアント間で自動伝播させるパターンが実装の基本形として定着した。
