# CTO Knowledge - 2026-03-16

## Daily Update (2026-03-16)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを削減するため、データフェッチと重いロジックはサーバーコンポーネントに移動する。2026年時点では `use client` を付けるコンポーネントを最小化するのが標準プラクティス。

- **Partial Prerendering (PPR) の本番投入:** 静的シェルを即座に配信しつつ動的コンテンツをストリーミングするPPRが安定版となり、TTFBとLCPを大幅改善できる。`experimental.ppr` から正式機能へ移行済みのため積極採用を推奨。

- **`next/image` と `next/font` の最適化継続:** 画像のsizes属性とpriority指定を正確に設定し、フォントはサブセット化することでCLSとLCPスコアを直接改善できる。これは地味だが効果が高く見落とされがち。

- **Route Segment Cache の細粒度制御:** `revalidate` と `fetchCache` をルートセグメント単位で制御し、過剰なISRによるエッジキャッシュ汚染を防ぐ。stale-while-revalidateパターンとの使い分けが重要。

- **Turbopack の本番利用と計測ドリブン最適化:** Turbopackによるビルド高速化が安定したため、CI/CDのビルド時間短縮に直結する。ただしパフォーマンス改善は必ず `next build --profile` と Core Web Vitals の実測値で判断し、体感ではなくデータで意思決定する。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化が鍵:** 2026年時点では、RSCのストリーミングはSuspense境界の配置設計が最重要課題となっており、コンポーネント単位での細粒度ストリーミングがTTFB改善に直結する。

- **PPR（Partial Prerendering）との統合が標準化:** Next.js 15+でPPRが安定版となり、静的シェルを即座に配信しつつ動的部分をストリームする構成がプロダクション標準になっている。RSCとPPRを組み合わせることでLCPを劇的に改善できる。

- **`use(Promise)`によるデータフェッチパターンの変化:** React 19の`use()`フックが普及し、Promiseを直接コンポーネントで消費するパターンが定着。サーバーサイドでのデータウォーターフォール回避のため、Promiseを親で生成し子にpropsとして渡す設計が推奨される。

- **Edge Runtimeでのストリーミング制約に注意:** Vercel EdgeやCloudflare Workersでは長時間ストリーミングのタイムアウト制限が依然として存在するため、重いデータ処理はNode.js Runtimeに留め、EdgeはShellのみ配信する設計が現実的。

- **クライアントコンポーネントの境界管理がバンドルサイズに直結:** `"use client"`ディレクティブの配置ミスがサーバーコードをクライアントバンドルに混入させるリスクがあり、`@next/bundle-analyzer`での定期監査と、インタラクティブ要素のleafコンポーネント化が2026年のベストプラクティスとして定着している。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの主流化:** 2026年時点でフルスタックTypeScriptプロジェクトではtRPCがデファクトに近い存在となり、型安全なAPI契約をコードジェネレーション不要で実現できる点が特に小〜中規模チームに支持されている。

- **REST vs GraphQLの決着:** GraphQLは複雑なマルチクライアント要件（モバイル+Web+サードパーティ）に依然有効だが、オーバーフェッチ問題はREST側もHTTP/3とSparse Fieldsetで対処できるようになり、「GraphQLでなければならない」場面は絞られてきた。

- **OpenAPI 3.1 + コード生成の復権:** Zodからスキーマを自動生成し、フロント・バック双方の型を同期するアプローチ（zodios、orvalなど）が成熟し、REST APIでもtRPC相当の型安全性を得られるようになった。

- **Edge-first API設計:** Cloudflare Workers / Vercel Edge Functionsの普及により、APIレイヤーをエッジに配置することが前提となりつつある。コールドスタートレイテンシへの配慮とステートレス設計が必須要件になった。

- **AIエージェント向けAPI設計:** LLMエージェントがAPIを自律呼び出しするユースケースが急増し、OpenAPI仕様の機械可読性・ツール記述（MCP準拠）・レート制限設計が新たな設計軸として浮上している。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジの標準実行環境に:** 2026年時点でCloudflare Workers・Fastly Compute@Edgeを中心に、WasmはJavaScript以外の言語（Rust、Go、Python）をエッジで実行する事実上の標準となっており、コールドスタートをほぼゼロに抑えている。

- **エッジDBの成熟でステートレス制約が緩和:** Cloudflare D1・Turso・PlanetScale Edgeなどの分散SQLが普及し、「エッジはステートレスのみ」という制約が崩れ、レイテンシーを維持しながらデータ処理をエッジに移譲できるアーキテクチャが現実的になった。

- **AI推論のエッジシフトが加速:** LLMの量子化・蒸留技術の進歩により、小型モデル（1〜7B）をエッジで実行するケースが増加。中央クラウドへのラウンドトリップを排除し、プライバシー要件が厳しいユースケース（医療・金融）での採用が目立つ。

- **オブザーバビリティの課題が深刻化:** リージョンが数百に分散した結果、分散トレーシングとログ集約のコストが無視できなくなっており、OpenTelemetry + エッジネイティブな収集エージェントの設計が設計品質の分水嶺になっている。

- **コスト最適化の主戦場がエッジへ:** オリジンサーバーへのリクエスト削減だけでなく、エッジ実行時間・KVストア読み書き・エグレス帯域の三軸でコストを管理する必要があり、アーキテクト層での「エッジ予算設計」が重要なスキルになっている。

### 5. authentication security best practices 2026

**authentication security best practices 2026 — CTO視点**

- **パスキー（Passkeys）への移行加速:** FIDO2/WebAuthnベースのパスキーがパスワード認証を実質的に置き換えつつある。フィッシング耐性があり、ユーザー体験も向上するため、新規実装ではパスワードレス認証をデフォルト設計にすべき。

- **ゼロトラスト＋継続的認証:** 「一度認証したら信頼」モデルは終焉。セッション中も行動パターン・デバイス状態・位置情報を継続的に検証するリスクベース認証（Adaptive MFA）が標準となっている。

- **OAuthトークンのセキュリティ強化:** DPoP（Demonstrating Proof of Possession）によるトークンバインディングが普及し、トークン盗用攻撃への対策が必須。リフレッシュトークンのローテーションも当然の実装として求められる。

- **AIを活用した異常検知:** 認証ログのリアルタイム分析にMLを組み込み、クレデンシャルスタッフィングやATO（アカウント乗っ取り）攻撃を自動検出・ブロックするアーキテクチャが競争優位になっている。

- **サプライチェーン攻撃への対策（認証ライブラリ）:** 認証SDKへの依存は攻撃面になりうる。依存パッケージの定期監査、SBOMの整備、ロックファイルの厳格管理が2026年では最低限のセキュリティ衛生として求められる。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x + Supabase の統合成熟:** Prisma 6では`prisma generate --accelerate`によるEdge Runtime対応が安定し、Supabase + Prisma Accelerateの組み合わせでコネクションプーリング問題がほぼ解消された。サーバーレス環境でのコールドスタート遅延が大幅に改善されている。

- **Row Level Security (RLS) の設計が重要:** SupabaseはRLSをアプリ層ではなくDB層で強制するため、Prismaからの直接クエリとSupabase Clientの使い分けを明確に設計しないとRLSバイパスのリスクがある。サービスロールキーの使用範囲を最小化し、anon/authenticated roleを活用する設計が2026年のベストプラクティス。

- **Supabase Branching によるスキーマ管理の変革:** Supabase Branchingが安定稼働し、PRごとにDB環境を自動分岐できるようになった。Prisma Migrationsとの組み合わせで「コードとスキーマの同期ズレ」によるCI失敗が激減している。

- **Vector/pgvector の本番運用が現実的に:** pgvectorとSupabase Vectorの統合が成熟し、Prismaの`Unsupported`型を使わずにベクトルカラムを扱えるORM拡張が整備されつつある。RAGアーキテクチャをPostgreSQL単一DBで完結させる構成が増加中。

- **型安全なリアルタイム購読の課題:** Supabase RealtimeはPrismaのスキーマ定義と型が分離しているため、Realtime経由のペイロードに型安全性が効かない。`supabase gen types`とPrismaの型を統一するコードジェン戦略、またはRealtimeをZodでバリデーションするラッパーの導入が実用上必須。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の実用化:** 2026年時点でWASI Preview 2が安定し、RustからWebAssemblyコンポーネントを生成する際の相互運用性が大幅に向上。`cargo component`ツールチェーンが成熟し、マイクロサービス間のポータブルなWasmモジュール配布が現実的になった。

- **SIMD・マルチスレッドの本格活用:** WebAssembly SIMDとThread Proposalの普及により、Rustで書いた画像処理・音声処理・ML推論コードがブラウザ上でもネイティブに近いスループットを達成。`wasm-bindgen`と`rayon`の組み合わせでスレッドプールも利用可能になっている。

- **コールドスタートのボトルネック解消:** Wasmのインスタンス化コストが引き続き課題だったが、Wasmtime/WasmEdgeのAOT（事前コンパイル）とスナップショット技術により、エッジ環境でのコールドスタートが数ms台に短縮。RustのゼロコストサービスをCDNエッジにデプロイするパターンが主流化しつつある。

- **Rustのバイナリサイズ最適化が必須:** `wasm-opt`（Binaryen）+ `wee_alloc`廃止後の`dlmalloc`代替、LTOフルビルドを組み合わせることで200KB以下の本番バイナリが標準的。`cargo-bloat`でサイズ回帰を継続監視するCIパイプラインが推奨プラクティス。

- **GC Proposalによるガベージコレクション言語との共存:** WasmのGC Proposalが主要ブラウザで安定化し、RustのWasmモジュールとKotlin/Dart製コンポーネントを同一Wasmランタイムで混在させるアーキテクチャが登場。Rustは依然としてパフォーマンスクリティカルな計算レイヤーを担うが、UI層は他言語に委ねるハイブリッド設計が増加している。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年のベストプラクティスは「必要な部分だけClient Component」という原則。データフェッチはServer Componentで完結させ、`use client`の境界を意識的に設計することでバンドルサイズを最小化できる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的ストリームを同一ルートで組み合わせるPPRが安定版に。`<Suspense>`境界の設計がアーキテクチャの核心となり、TTFBとLCPの両立が可能になった。

- **Server Actions でAPI Routeを削減:** フォーム送信・ミューテーションをServer Actionsに集約することで、`/api/*`エンドポイントの乱立を防げる。ただしCSRF対策やrate limitingはミドルウェア側で担保する設計が必要。

- **`use cache` ディレクティブによるきめ細かいキャッシュ制御:** `fetch`のキャッシュオプションに依存せず、関数・コンポーネント単位でキャッシュ戦略を宣言できるようになった。`revalidateTag`と組み合わせたオンデマンド再検証がCMS連携の標準パターン。

- **`next/after` で非同期サイドエフェクトを分離:** レスポンス返却後にログ記録・分析イベント送信などを実行できる`after()`APIが実用段階に。メインのレスポンスレイテンシに影響させずにオブザーバビリティを強化できる。

### 9. Vercel Edge Functions optimization 2026

- **Edge RuntimeでのCold Start排除:** 2026年時点でVercel Edge FunctionsはV8 Isolateベースのため従来のNode.js Lambdaと異なりコールドスタートがほぼゼロ。レイテンシクリティカルなAPI（認証・A/Bテスト・リダイレクト）は積極的にEdgeへ移行すべき。

- **Fluid Computeによるリージョン戦略の再考:** Vercelの"Fluid Compute"モデルにより、単純にEdge=高速という前提は崩れつつある。データソース（DB・KV）との地理的近接性を測定し、Edgeが実際にレイテンシ改善になるか検証してからデプロイすること。

- **バンドルサイズ制限（4MB）への対応:** Edge Runtimeは`fs`・`child_process`等Node.js coreが使えず、バンドルサイズ上限も厳しい。重いライブラリ依存（例: PDFパーサー・ORMフル機能）はServerless Functionに残し、軽量ロジックのみEdgeへ切り出す設計が現実的。

- **Middleware最適化がSEO・パフォーマンスの鍵:** Next.js Middlewareは全リクエストを通過するEdge Functionであり、ここでの処理遅延は全ページのTTFBに直結する。条件分岐・正規表現の複雑化を避け、`matcher`で対象パスを絞り込むことが重要。

- **Observability（可観測性）の整備:** Edge環境はログが散逸しやすく、デバッグコストが高い。Vercel Analytics + OpenTelemetry対応のEdge-compatibleトレーシング（例: Baselime・Axiom）を早期に導入し、本番での問題検出サイクルを短縮することを推奨。

### 10. TypeScript type safety patterns 2026

- **Template Literal Types の高度活用:** 文字列パターンを型レベルで制約できるTemplate Literal Typesが実用段階に成熟し、APIルートやイベント名のタイポをコンパイル時に検出できるようになった。`\`/api/${string}\`` のような型定義でランタイムエラーを事前排除できる。

- **Branded Types による意味的安全性:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded Typesが、同型異義（例: UserIdとOrderIdが両方string）による混入バグを防ぐ標準パターンとして定着。特にドメイン駆動設計との相性が良い。

- **`satisfies` 演算子の普及:** TypeScript 4.9で導入された `satisfies` が2026年現在フル活用フェーズに入り、型推論を維持しながら型チェックを行える。`as` キャストによる型安全性の破壊を避けつつ、オブジェクトリテラルの型検証が可能。

- **`using` / Explicit Resource Management:** TC39のExplicit Resource Management提案（`using` キーワード）がTypeScriptでサポートされ、DB接続・ファイルハンドル等のリソースリークをコンパイル時から防ぐパターンが普及中。try/finallyの手動管理が不要になる。

- **型レベルのZod統合とSchema-First開発:** ZodのスキーマからTypeScript型を自動導出する `z.infer<>` パターンが事実上の標準となり、ランタイムバリデーションと静的型定義の二重管理が不要に。APIバウンダリでのEnd-to-End型安全性の実現が現実的なコストで達成できる。
