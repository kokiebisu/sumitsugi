# CTO Knowledge - 2026-10-23

## Daily Update (2026-10-23)

### 1. Next.js performance optimization 2026

**ポイント1: Turbopackのデフォルト化とビルド高速化** Next.js 16ではTurbopackが本番ビルドでも標準となり、大規模ページ（例: `src/app/properties/`配下の一覧・詳細ページ）でのビルド時間が大幅短縮される。CIのビルド検証ステップ（`bun run build`）の実行時間短縮にも直結するため、早めに移行効果を検証する価値がある。

**ポイント2: Partial Prerendering (PPR) とCache Componentsの活用** 静的な外枠（物件一覧のレイアウトなど）を事前レンダリングしつつ、動的部分（ログイン状態・リアルタイム在庫）だけをストリーミングする設計が主流になっている。`'draft'`/`'public'`のようなステータス分岐があるページでは、PPRで公開物件の静的部分と非公開チェックの動的部分を分離するとTTFBが改善する。

**ポイント3: React Server Componentsでのデータフェッチ最適化** クライアントコンポーネントへのJS転送量を減らすため、`src/lib/data.ts`のようなデータ取得ロジックをできるだけRSC側に留め、`use client`境界を最小限にするのが2026年のベストプラクティス。フォームやインタラクションが必要な部分だけをクライアント化することで、初期表示速度と引越し費用計算のようなインタラクティブUIのバランスを取れる。

**ポイント4: next/afterとServer Actionsの非同期処理分離** レスポンス確定後に実行したい処理（分析ログ、通知送信など）を`next/after`でメインのレスポンスパスから切り離すパターンが定着している。前の住人・次の住人間のマッチング通知のような非クリティカル処理をこの仕組みに移すと、ユーザー体感速度が向上する。

**ポイント5: 画像・フォント最適化とEdge配信の見直し** `next/image`のAVIF優先配信とEdge RuntimeでのCDNキャッシュ戦略が2026年のデフォルト構成になっており、物件写真が多いUIでは特に効果が大きい。ダークモード対応のアイコン・画像切り替えも含めて、Lighthouseスコアを定期的に計測し退行を早期検知する運用が推奨される。

### 2. React Server Components streaming 2026

- **部分的Suspense境界の高度化:** Next.js 16ではストリーミング単位がコンポーネント粒度まで細分化され、`loading.tsx`に頼らず各Suspense境界ごとにプログレッシブレンダリングを設計するのが標準になっている。弊社の物件一覧ページでも、画像・価格・レビューを個別にストリーミングすればLCPを維持しつつTTFBを大幅に短縮できる。

- **Server ActionsとRSCの境界設計がパフォーマンスの肝:** クライアントバンドルサイズを抑えるには「どこをServer Componentに留めるか」の判断が重要で、むやみに`'use client'`を増やすとストリーミングの恩恵が消える。物件詳細や引越し費用計算のような重いロジックはサーバー側に残すべき。

- **キャッシュ戦略とストリーミングの両立:** Next.js 16の`use cache`ディレクティブとRSCストリーミングを組み合わせることで、動的な「次の住人」情報を待たせず静的な物件データを即時表示できる。全体を再検証するのではなく、データソース単位で粒度を分けるのが2026年のベストプラクティス。

- **E2Eテストでのストリーミング挙動検証が必須に:** Playwrightでストリーミング中の中間状態（スケルトン→実データ）を検証しないと、本番でのレイアウトシフトやCLS悪化を見逃しやすい。ユーザー向け機能ではE2Eでストリーミング完了後のDOM状態だけでなく、途中状態もアサートすべき。

- **エッジランタイムとの相性がさらに向上:** RSCストリーミングはVercel Edge RuntimeやCloudflare Workersとの組み合わせで地理的レイテンシを削減する流れが加速しており、グローバル展開を見据えるなら今のうちにEdge対応可能な実装（Node専用APIを避ける等）を意識しておくと移行コストが低い。

### 3. API design REST GraphQL tRPC 2026

- **型安全性の一体化が主流に:** tRPCやHonoのRPCモードのように、バックエンドとフロントエンドで型を共有し、スキーマ定義とコード生成を分離しない「end-to-end typesafety」が2026年の標準的アプローチになっている。sumitsugiのようなNext.js App Router構成では、tRPC導入によりAPI層のボイラープレートとランタイムバリデーションの手間を大幅に削減できる。

- **GraphQLは「社内複雑系」向けに残存:** 複数クライアント（Web/モバイル/パートナーAPI）が異なるデータ粒度を要求する大規模プロダクトではGraphQLの優位性が続くが、単一Next.jsアプリ+自社フロントのみの構成ではオーバーヘッドが過大。sumitsugiの規模感ではtRPC/REST+Zodの組み合わせが適切。

- **RESTはOpenAPI+Zod自動生成で生存:** 外部連携（決済、外部弁護士向けAPI連携など）やWebhookはRESTが依然デフォルト。Zodスキーマから OpenAPI定義を自動生成するパターンが定着し、「手書きAPI仕様書」は廃れつつある。

- **BFF（Backend for Frontend）層の軽量化:** Next.jsのRoute HandlersやServer Actionsが実質的にBFFを担い、専用APIゲートウェイを立てずに済むケースが増加。ただしServer Actionsは認可チェック漏れのリスクがあるため、ミドルウェアでの一元的な権限検証が必須。

- **AIエージェント向けAPI設計が新課題:** LLMエージェントがAPIを直接呼ぶ前提で、エラーメッセージの自然言語化・冗長なスキーマ記述（JSON Schema in tool definitions）を意識した設計が求められるようになってきている。sumitsugiの自律開発ワークフロー（Beads/Linear連携スクリプト等）もこの文脈で設計し直す価値がある。

### 4. serverless edge computing 2026

- **エッジでのAI推論標準化:** 2026年はCloudflare Workers AI、Vercel Edge Functions、Fastly Compute@EdgeなどがLLM推論を直接エッジで実行する機能を拡充し、ユーザーに最も近いPoPでレイテンシ数十msの推論が可能になっている。sumitsugiのような物件検索・レコメンド機能では、地理的に分散したユーザーへの応答速度向上に直結する。

- **コールドスタート問題の実質的解消:** V8 isolateベースのランタイム（Cloudflare Workers、Deno Deploy等）がコールドスタートを1ms未満に抑え、従来のコンテナ型サーバーレス（Lambda等）との差が明確化。Next.js 16のEdge Runtimeを使う場合、この恩恵をそのまま享受できるためミドルウェアや認証チェックをEdgeに寄せる価値が高い。

- **データレイヤーのエッジ分散（Edge-native DB）:** Turso、PlanetScale、Cloudflare D1/KVなどエッジレプリケーション型DBが実用段階に入り、読み取り中心のワークロード（物件一覧表示など）をリージョン跨ぎで低レイテンシ化できる。一方で書き込み整合性のトレードオフは依然残るため、引越し費用の決済処理など強整合性が必要な処理は中央集権DBに残す設計判断が必要。

- **コスト構造の変化と注意点:** エッジ実行は従量課金が細かく、トラフィック急増時のコスト予測が難しい。特に画像最適化やAPI呼び出しが多いUIでは、CDNキャッシュ戦略（ISR/stale-while-revalidate）を併用しないとエッジ実行コストが従来のサーバーより高くなるケースがある。

- **ベンダーロックインリスク:** 各ベンダー独自のランタイムAPI（Cloudflare Workers固有のBindings等）に依存すると移行コストが跳ね上がる。WinterCG標準（Web標準API準拠）に沿った実装を優先し、特定プラットフォームへの過度な依存を避けるのが2026年のベストプラクティス。

### 5. authentication security best practices 2026

- **パスキー/FIDO2標準化:** パスワードレス認証（WebAuthn/Passkeys）がデフォルト選択肢となり、フィッシング耐性のある認証方式への移行が業界標準に。パスワード単体での認証は非推奨とすべき。
- **ゼロトラスト前提のセッション管理:** JWTの長期保存を避け、短命トークン＋リフレッシュトークンのローテーション、デバイスフィンガープリンティングと組み合わせた継続的な検証が重要。
- **多層防御（Defense in Depth）:** MFA必須化だけでなく、異常ログイン検知（地理的異常、デバイス変更）やレート制限をAPI層に組み込み、ブルートフォース・クレデンシャルスタッフィング対策を強化。
- **サプライチェーン・サードパーティ認証リスク:** OAuth/OIDCプロバイダー連携時のスコープ最小化、トークン漏洩時の影響範囲を限定する設計（最小権限の原則）が必須。
- **監査ログとコンプライアンス:** 認証イベント（ログイン・権限変更・失敗試行）の完全なログ保持と異常検知の自動化が、個人情報を扱うプラットフォームでは法務・セキュリティ両面で必要。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma 6以降はRust不要の新クエリエンジン（TypeScript/WASMベース）に移行しており、コールドスタートが大幅に改善されたため、Supabaseのようなサーバーレス環境でのEdge Function連携がより実用的になっている。
- **ポイント2:** SupabaseはPostgreSQL本体にRLS（Row Level Security）を強制する設計思想のため、PrismaでSupabaseを使う場合はPrisma側のアクセス制御だけに頼らず、DBレベルのRLSポリシーを必ず併用すべき — アプリ層の認可漏れをDBが最終防衛線としてカバーできる。
- **ポイント3:** Prisma Accelerate等のコネクションプーリング層を使わずにSupabaseのPgBouncer（Transaction mode）と直接組み合わせると、Prepared Statementの扱いで接続エラーが起きやすいため、接続文字列の`pgbouncer=true`設定とPrismaのバージョン互換性を事前に確認する必要がある。
- **ポイント4:** マイグレーション管理において、Prisma Migrateの宣言的スキーマとSupabase CLIのマイグレーション機構が競合しやすいため、どちらか一方を「ソース・オブ・トゥルース」として明確に決め、チームの運用ルールとして固定することが重要。
- **ポイント5:** リアルタイム機能（Supabase Realtime）を使う場合、PrismaのORM層を経由しない直接DB変更通知の仕組みになるため、型安全性を保つにはSupabaseが生成する型定義とPrismaのスキーマを定期的に同期させる運用が必要。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASI 0.3の普及により、Component Model経由でRustコンポーネント間のゼロコピー連携が標準化され、従来のFFIオーバーヘッドが大幅に削減されています。マイクロサービス的な分割をWasmコンポーネント単位で行うアーキテクチャが実用段階に入っています。

- **ポイント2:** `wasm-bindgen`や`wit-bindgen`の最適化が進み、Rust→WasmのバンドルサイズはBrotli圧縮後数十KB台まで縮小可能になっており、SSR併用のNext.jsアプリでも初期ロードのボトルネックになりにくくなっています。

- **ポイント3:** SIMD128とマルチスレッド（`wasm-threads`）が主要ブラウザで標準サポートされ、画像処理・PDF生成・位置情報計算など計算負荷の高い処理をRust/WasmにオフロードしてメインスレッドのJS実行をブロックしない設計が一般化しています。

- **ポイント4:** ネイティブ比80-95%の実行速度まで近づいているため、「JSで書いてから遅ければWasm化」ではなく、設計初期から計算集約的なロジック（検索・マッチング・スコアリング）をRustコアとして分離し、Web/Node/Edgeで同一バイナリを再利用する戦略がコスト効率的です。

- **ポイント5:** Cloudflare WorkersやFastly Compute@EdgeなどのWasmベースEdgeランタイムが成熟し、コールドスタートがミリ秒単位まで短縮されているため、レイテンシが重要な検索・推薦ロジックをRust/Wasmでエッジ実行する選択肢が、サーバーレスJS/TSより有利になるケースが増えています。

### 8. Next.js App Router patterns 2026

- **ポイント1（Server Actions中心の設計）:** App Routerでは`'use server'`によるServer Actionsがデータ変更の標準パターンとして定着し、APIルートを介さずフォーム送信や状態更新を直接サーバーで処理できる。sumitsugiのような物件掲載フローでは、クライアント側のfetchロジックを削減し、型安全性を保ったままミューテーションを書けるのが利点。

- **ポイント2（Partial Prerendering / PPR）:** 静的シェルを即時返しつつ動的部分だけストリーミングするPartial Prerenderingが実用段階に入り、一覧ページのように「静的なレイアウト＋動的な検索結果」という構成に適している。物件一覧（`properties/`）のようなページで初期表示速度を大きく改善できる。

- **ポイント3（キャッシュ戦略の明示化）:** `fetch`のキャッシュ挙動がより明示的なオプトイン方式に移行しており、「デフォルトでキャッシュしない」前提で`revalidate`や`cache: 'force-cache'`を意図的に指定する設計が推奨される。ステータス`'draft'`/`'public'`の切り替えのような即時反映が必要なデータは、キャッシュ無効化（`revalidateTag`）を明示的に組み込む必要がある。

- **ポイント4（Server Components + クライアント境界の最小化）:** `'use client'`境界を末端のインタラクティブ要素（フォーム、モーダル等）のみに絞り込む設計が一般化し、認証コンテキスト（`auth-context.tsx`）のようなグローバル状態もServer Componentsとの併用を前提に再設計される傾向がある。バンドルサイズ削減とSEO両立のため、ページ全体をクライアント化しない規律が重要。

- **ポイント5（型安全なルーティング）:** Next.js 16ではtyped routesがより成熟し、`src/app/`配下のルート構造からリンクやパラメータの型が自動生成されるため、`listing/[id]`のような動的ルートでのタイプミスをビルド時に検出できる。TypeScriptプロジェクトでは有効化しておくことで、リファクタリング時の安全性が上がる。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Vercel Edge FunctionsはV8 isolateベースで動作するため、コールドスタートがほぼゼロに近く、レイテンシが重要なAPIルート（認証チェック、リダイレクト、A/Bテスト振り分けなど）を優先的にEdgeへ移行するのが2026年のベストプラクティス。sumitsugiのような物件検索・一覧表示系ページでは、地理的に分散したユーザーへの応答速度改善に直結する。

- **ポイント2:** Edge Runtimeは一部のNode.js API（`fs`、一部の暗号化モジュールなど）が使えないため、`next.config`でruntime指定を誤ると本番でのみ失敗するケースがある。移行前に対象ルートの依存関係を精査し、Node.js専用ライブラリ（画像処理やPDF生成など）はNode.js Runtimeに残す判断が必要。

- **ポイント3:** Vercelの2026年のEdge Middlewareは、キャッシュ制御とOGイメージ生成を組み合わせた「Edge Config」機能が強化されており、頻繁に変わらないデータ（物件ステータスのフラグ、サイト設定など）をEdge Configに置くことでDBクエリ回数を削減できる。`src/lib/site-config.ts`のような静的設定はこの対象候補。

- **ポイント4:** Streaming SSR（React Server Componentsのストリーミング）とEdge Functionsを組み合わせることで、TTFB（Time To First Byte）を大幅に短縮できるが、Edge環境でのストリーミングはメモリ上限（通常128MB前後）に注意が必要。大きな一覧ページ（`properties/`配下）で画像メタデータを多く含む場合は、ペイロードを絞ったレスポンス設計が必須。

- **ポイント5:** 2026年のVercel課金モデルはEdge Function実行時間とデータ転送量に応じた従量課金が主流化しており、不要なEdge Middlewareの多用（全ルートに適用するなど）はコスト増の原因になりやすい。`matcher`設定で対象パスを厳密に絞り込むことが、パフォーマンスとコストの両面で重要。

### 10. TypeScript type safety patterns 2026

**CTO視点：TypeScript Type Safety Patterns 2026**

- **ポイント1（型述語の自動推論強化）:** TypeScript 5.5以降で導入された推論型述語（inferred type predicates）が標準化され、`filter`やカスタムガード関数で明示的な`is`アノテーションを書かずに型が自動で絞り込まれるようになっている。sumitsugiの`src/lib/data.ts`のような`'draft' | 'public'`判定処理で、ボイラープレートを削減しつつ型安全性を保てる。

- **ポイント2（Zodとの型統合がデファクト標準化）:** `z.infer<typeof schema>`でスキーマから型を自動生成するパターンが、Zodスキーマを単一の信頼源（single source of truth）とする設計として定着している。standards.mdにある「システム境界でZodスキーマを使う」という方針は、型定義の重複を防ぐ観点でも正しい。

- **ポイント3（Discriminated Unionの徹底活用）:** 物件ステータスのような`'draft' | 'public'`型は、単純なUnion型よりも判別可能なオブジェクト（`{status: 'draft'} | {status: 'public', publishedAt: Date}`）にすることで、状態ごとに必要なフィールドをコンパイル時に強制できる。現状の`union型を変更する際は全使用箇所をgrepする`運用はミスが起きやすく、Discriminated Unionへの移行で構造的に防げる。

- **ポイント4（`satisfies`演算子の普及）:** オブジェクトリテラルの型を狭めすぎず検証する`satisfies`が、設定オブジェクト（`site-config.ts`など）の型安全な定義パターンとして一般化。`as const`と組み合わせることで、リテラル型の保持と型チェックを両立できる。

- **ポイント5（TS 6.x系のネイティブ型チェッカー高速化の波及効果）:** Go実装の型チェッカー移行（tsc-nativeの流れ）により大規模リポジトリでの型チェックが数倍高速化し、CI時間短縮が進んでいる。build-integrity方針（`bun run build`必須）を維持しつつ、CIのフィードバックループがさらに短縮される見込み。
