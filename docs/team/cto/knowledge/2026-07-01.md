# CTO Knowledge - 2026-07-01

## Daily Update (2026-07-01)

### 1. Next.js performance optimization 2026

- **ポイント1:** Next.js 16ではPartial Prerenderingが安定版となり、静的シェルを即座に返しつつ動的部分をストリーミングできるため、実装コストを抑えたままTTFBを大幅に改善できる。
- **ポイント2:** React Compilerの統合が進み、`useMemo`/`useCallback`の手動最適化が不要になりつつあるため、レビュー観点を「メモ化の正しさ」から「不要な再レンダリング構造そのものの排除」へシフトすべき。
- **ポイント3:** Turbopackがビルド・開発サーバーの標準になり、大規模化しても`bun run build`の時間がボトルネックになりにくいが、キャッシュ戦略（`use cache`ディレクティブ）の設計を誤るとCDN/ISRとの整合性が崩れやすい点に注意。
- **ポイント4:** 画像・フォントの自動最適化だけでなく、`next/dynamic`によるコード分割とServer Componentsの境界設計が引き続きLCP改善の主要因であり、物件詳細ページのような画像重量が大きい画面では特に効果が大きい。
- **ポイント5:** Core Web Vitalsの計測をCIに組み込み（Lighthouse CIやReal User Monitoring）、リグレッションをPRレベルで検知する体制がないと、機能追加のたびにパフォーマンスが静かに劣化するリスクがある。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPPR（Partial Prerendering）が安定版となり、静的シェルを即座に返しつつ動的部分だけをストリーミングする構成が標準化されつつある。既存の`loading.tsx`ベースのSuspense境界を見直し、より粒度の細かい境界設計に移行する価値がある。

- **ポイント2:** RSCペイロードのシリアライズコストがボトルネックになりやすく、大きなデータをServer Componentに直接渡すのではなく、必要なフィールドのみを絞り込んで渡す設計が重要。本プロジェクトの`data.ts`にある物件データ取得も、一覧・詳細で必要な列を分離する余地がある。

- **ポイント3:** `use cache`ディレクティブ（Cache Componentsモデル）が実験的機能から本格採用フェーズに入り、キャッシュ境界をコンポーネント単位で明示的に宣言できるようになった。物件検索結果など更新頻度が異なるデータの混在ページで効果が大きい。

- **ポイント4:** ストリーミングSSR環境でのエラーバウンダリ設計が引き続き課題で、Suspense境界内で発生したエラーがクライアントに部分的にしか伝わらないケースがある。認証まわり（`auth-context.tsx`）など重要な状態を含む境界は、明示的なerror.tsxでのフォールバックを徹底すべき。

- **ポイント5:** Server Actionsとストリーミングの組み合わせで、フォーム送信後の楽観的UI更新パターンが定着してきた。引越し費用の見積もりフローのような多段階フォームでは、`useOptimistic`とストリーミングを組み合わせることでUX改善とサーバー負荷軽減を両立できる。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの採用拡大）:** TypeScriptフルスタック構成（Next.js等）ではtRPCがREST/GraphQLを代替するケースが増えている。型安全性がエンドツーエンドで保証され、スキーマ定義やコード生成が不要になるため、sumitsugiのような単一TSコードベースには特に相性が良い。

- **ポイント2（GraphQLは「集約層」として生き残る）:** GraphQLは新規の小〜中規模プロダクトでは採用が減少傾向にあるが、複数バックエンド・複数チームを横断するBFF（Backend for Frontend）層としては依然強い。単一チーム・単一リポジトリのMVPフェーズでは過剰投資になりやすい。

- **ポイント3（RESTはCRUD中心の外部公開APIで依然標準）:** 決済・不動産情報連携など外部パートナー向けAPI（弁護士・行政関連含む）はRESTが依然デファクト。ドキュメント性・キャッシュ制御・HTTPセマンティクスの明快さがtRPC/GraphQLより有利。

- **ポイント4（Zodスキーマの二重活用）:** tRPC/RESTいずれを選んでも、Zodで入力検証スキーマを一元管理し、フロント・バック双方の型とバリデーションを共有するパターンが2026年のベストプラクティス。本プロジェクトの「Input validation: Zod schemas at system boundaries」方針とも直接整合する。

- **ポイント5（sumitsugiへの提言）:** 現状は社内向け機能（物件・引き継ぎフロー）が中心でクライアントは単一Next.jsアプリのみのため、tRPC継続が最適。将来的に外部パートナー（不動産会社・決済代行）向けAPIを公開する段階になったら、その部分だけRESTでラップする「ハイブリッド構成」を検討すべき。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG(Web-interoperable Runtimes)準拠がデファクト標準になりつつあり、Cloudflare Workers・Vercel Edge・Deno Deployなど各プラットフォーム間でのコード可搬性が大幅に向上している。Node.js固有APIへの依存を避けることが、将来的なベンダーロックイン回避の鍵となる。

- **エッジDBとの整合性課題:** D1やTurso、PlanetScaleなど分散SQLiteベースのエッジDBが普及した一方、強整合性が必要な処理（在庫管理・決済）はまだリージョナルDBに逃がす設計が現実解。読み取りはエッジ、書き込みはoriginという「読み書き分離」パターンの徹底が実装コストを抑える。

- **コールドスタート問題の実質的解消:** V8 Isolateベースの実行環境がミリ秒単位の起動を実現し、サーバーレスの「待ち時間」という弱点はほぼ解消された。ただし重いnpm依存（画像処理ライブラリ等）を持ち込むとバンドルサイズ制限に引っかかりやすく、依存関係の軽量化が引き続き設計上の制約になる。

- **可観測性コストの増大:** エッジで数千の実行地点に処理が分散するため、従来の集中ログ収集がボトルネックになりやすい。OpenTelemetryのエッジネイティブ対応が進み、サンプリングとエッジ側での事前集約が事実上必須の運用パターンとなっている。

- **コスト構造の逆転リスク:** リクエスト課金モデルは低トラフィック時は安いが、トラフィック急増時にVPS/コンテナ常駐型より割高になるケースが増えている。sumitsugiのような物件検索・一覧表示が中心のプロダクトでは、静的生成+ISRとエッジ関数を組み合わせ、動的処理をユーザー認証・決済など本当に必要な箇所に限定するのが費用対効果が高い。

### 5. authentication security best practices 2026

- **ポイント1（パスキー標準化）:** 2026年時点でパスキー（FIDO2/WebAuthn）はパスワードレス認証のデファクトスタンダードとなっており、フィッシング耐性の高さから金融・医療系サービスでは必須要件化が進んでいる。sumitsugiのような個人情報（引き継ぎ物件情報）を扱うプラットフォームでは、早期導入がセキュリティ差別化要因になる。

- **ポイント2（多層防御とゼロトラスト）:** 単一の認証要素に依存せず、デバイスフィンガープリンティング・行動分析・IP評判を組み合わせたリスクベース認証が主流になっている。前の住人↔次の住人間で機密性の高いやり取り（内見予約、契約情報）が発生するため、セッション単位での継続的検証が重要。

- **ポイント3（トークン管理の厳格化）:** JWTの長寿命化はリスクが高いため、短命アクセストークン＋リフレッシュトークンローテーション、かつHTTPOnly/Secure/SameSite=Strict Cookieでの保存が標準。Next.js App Routerではサーバーコンポーネント側でのトークン検証を徹底し、クライアントへの露出を最小化すべき。

- **ポイント4（サプライチェーン・依存関係リスク）:** 認証ライブラリ自体の脆弱性（npm supply chain攻撃）が増加傾向にあり、`bun audit`等での定期スキャンと、認証まわりの依存パッケージは最小限・信頼できるメンテナ限定にする方針が必要。

- **ポイント5（監査ログとインシデント対応）:** 不正ログイン試行やセッション異常を検知するリアルタイム監査ログが法規制対応（個人情報保護法改正）の観点でも必須になりつつあり、認証失敗・パスワードリセット・権限変更は最低限ログ化し、異常検知アラートと連携させるべき。

### 6. database architecture Prisma Supabase 2026

- **Prisma Postgres + Supabase の使い分け:** Supabaseは認証・Realtime・Storageまで一体化したBaaSとして強力だが、複雑なマイグレーションやマルチスキーマ運用ではPrisma ORM＋Supabase Postgresの組み合わせが型安全性とスキーマ管理の面で優位。sumitsugiのような物件×取引データを扱うプロダクトでは、Prisma Schemaを単一の真実源にしてSupabaseはインフラ（DB/Auth/Storage）として使う構成が安定する。

- **Row Level Security (RLS) とORMの整合性:** SupabaseのRLSはDB層でのアクセス制御に強いが、PrismaはRLSをネイティブに認識しないためアプリ層の権限チェックと二重管理になりがち。`前の住人`/`次の住人`のように役割ごとに閲覧範囲が異なるデータ構造では、RLSポリシーをMigrationファイルとして明示的にバージョン管理し、Prisma Migrateのフローに組み込むのが2026年のベストプラクティス。

- **Edge/Serverless最適化とコネクションプーリング:** Next.js 16のServer ActionsやRoute HandlersはEdge実行が増えており、Prisma Accelerate（またはSupabaseのPgBouncer経由プーリング）が必須。コネクション枯渇はローンチ後に顕在化しやすい問題なので、ベータ前にプーリング設定を検証しておくべき。

- **型安全なリアルタイム機能:** 物件ステータス（`draft`/`public`）のようなUnion型はPrismaのenumとSupabase Realtimeのpayload型を一致させておかないと、フロントでの型不整合バグが起きやすい。Zodスキーマをアプリ境界に置く現行方針（`standards.md`）と合わせ、DB→ORM→Zod→UIの型フローを一貫させることが重要。

- **バックアップ/リストアとコンプライアンス:** 法務確認中の現フェーズ（プライバシーポリシー・特商法）を踏まえると、SupabaseのPoint-in-Time Recoveryとデータ保持ポリシーの設定は本番ローンチ前に必須。個人情報を含むテーブルは論理削除＋監査ログ設計をPrisma Middlewareで統一しておくと、後からの法務要件変更にも対応しやすい。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WasmGC(Wasm Garbage Collection)の標準化が進み、Rustに限らずKotlinやJavaなどGC言語もネイティブに近い速度でWasm実行できるようになったが、Rustは元々GC不要なため引き続き最小バイナリサイズ・最速起動という優位性を保っている。
- **ポイント2:** Component Model(WASI Preview 2)の普及により、Rustで書いたWasmモジュールを言語横断で組み合わせられるようになり、フロントエンドの重い処理(画像処理・PDF生成など)をマイクロモジュール単位で切り出す設計が主流になりつつある。
- **ポイント3:** `wasm-bindgen`/`wasm-pack`のツールチェーンが成熟し、SIMD対応や並列化(Web Workers + `wasm-bindgen-rayon`)がデフォルトで扱いやすくなったため、画像・地図データの前処理など計算負荷の高い機能をブラウザ側にオフロードしてサーバーコストを削減する戦略が現実的になっている。
- **ポイント4:** バイナリサイズ最適化(`wasm-opt`, `twiggy`によるプロファイリング)が定石化し、数十KB台のWasmモジュールを配信できるため、モバイル回線でも初回ロードのボトルネックになりにくい。
- **ポイント5:** 弊社のNext.js構成では、物件写真の圧縮・EXIF処理やPDF帳票生成(契約書類など)をRust/Wasmに置き換えることで、サーバーレス関数の実行時間・コストを削減しつつクライアント側で完結できる可能性があり、法務書類生成フェーズで検討価値がある。

### 8. Next.js App Router patterns 2026

- **ポイント1:** Partial Prerendering（PPR）が安定版となり、静的シェルを即座に返しつつ動的部分をストリーミングする構成が標準化。物件一覧ページなど「共通レイアウトは静的・在庫情報のみ動的」なパターンに最適で、TTFBを大幅に改善できる。

- **ポイント2:** Server Actionsは`use cache`ディレクティブとの組み合わせでキャッシュ制御が明示的になり、内見予約やお問い合わせフォームのようなミューテーションでも再検証範囲を細かく指定できるようになった。誤ったキャッシュ無効化によるバグを防ぎやすい。

- **ポイント3:** `after()` APIの普及により、レスポンス返却後にログ送信や通知処理を実行するパターンが一般化。ユーザー体験（レスポンス速度）を落とさずに分析イベントや前の住人への通知を送れる。

- **ポイント4:** Route Handlersよりも Server Components + Server Actions を優先する設計が定着し、API層を薄くする方向が主流に。ただしWebhookや外部連携（決済等）は引き続きRoute Handlersが必要で、境界の見極めが重要。

- **ポイント5:** `instrumentation.ts`によるOpenTelemetry統合が標準化され、App Router特有のストリーミングSSRでもトレースが追いやすくなった。パフォーマンス問題（例: 物件詳細ページの画像読み込み遅延）の原因特定が容易に。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約を前提にした設計:** Node.js APIの一部が使えないEdge Runtimeでは、重い依存関係やNode専用ライブラリを避け、Web標準API（fetch, crypto.subtleなど）ベースの軽量な実装にすることでコールドスタートを最小化できる。

- **リージョン最適化とデータ近接性:** Edge Functionsはユーザーに最も近いリージョンで実行されるため、DBやAPIの物理的な距離がボトルネックになりやすい。Vercel EdgeとPlanetScale/Neon等のエッジ対応DBを組み合わせるか、キャッシュ層（Vercel KV, Edge Config）を挟んでレイテンシを削減するのが2026年の定石。

- **Streaming SSRとPartial Prerenderingの併用:** Next.js 16のPPR（Partial Prerendering）とEdge Functionsを組み合わせることで、静的シェルを即座に返しつつ動的部分だけEdgeでストリーミングでき、TTFBを大幅に改善できる。sumitsugiの物件一覧・詳細ページのような一部動的コンテンツを含むページに有効。

- **Middlewareの肥大化に注意:** 認証チェックやリダイレクトロジックをmiddleware.tsに詰め込みすぎると全リクエストで実行コストが発生するため、本当にエッジで判定が必要な処理（Bot判定、A/Bテスト振り分け、地域別リダイレクト）に限定し、認可の詳細判定はページ側やAPI Routeに委譲する設計が推奨される。

- **可観測性とコスト管理:** Edge Functionsは実行時間・メモリの計測がNode環境と異なるため、Vercel Observability PlusやOpenTelemetry連携で関数ごとの実行コストを可視化し、想定外の呼び出し増加（無限ループやリトライ）を早期検知する体制が必須になっている。

### 10. TypeScript type safety patterns 2026

## TypeScript Type Safety Patterns 2026 — CTO視点

- **ポイント1:branded typesの標準化:** IDや金額などプリミティブ型の取り違えバグを防ぐため、`type UserId = string & { __brand: 'UserId' }` のようなbranded/nominal typingパターンがZodスキーマと組み合わせて標準化されつつある。本プロジェクトでも`seller`/`property`のID管理に導入すれば、誤ってプロパティIDとユーザーIDを混同するバグを型レベルで防げる。

- **ポイント2:スキーマファーストのランタイム検証:** Zod（またはvalibot等の軽量代替）でスキーマを一箇所定義し、そこから型を推論する`z.infer<typeof schema>`パターンが境界（API/フォーム入力）での標準になっている。標準化ルールにある「Zodスキーマを境界で使う」方針と完全に一致しており、型定義とバリデーションの二重管理を避けられる。

- **ポイント3:Exhaustiveness checkingの徹底:** Union型（例：`status: 'draft' | 'public'`）を扱う際、`switch`文の`default`節で`const _exhaustive: never = value`パターンを使い、新しいstatus値の追加時にコンパイルエラーで検知する手法が定着。CLAUDE.mdにある「union type変更時は全使用箇所をgrep」というルールを型システムで自動化できる。

- **ポイント4:テンプレートリテラル型によるルーティング安全性:** Next.js App Routerのようなファイルベースルーティングで、テンプレートリテラル型を使って`/properties/${string}`のようなパス型を生成し、リンク先の存在をコンパイル時に保証する動きが広がっている。`src/app/properties/`のリンク生成箇所で型安全なパス生成に切り替えると、リンク切れの実行時エラーを防げる。

- **ポイント5:`satisfies`演算子の定着:** 設定オブジェクト（`site-config.ts`など）で型注釈の代わりに`satisfies`を使い、型推論の精度（リテラル型の保持）とスキーマ適合チェックを両立させるパターンが一般化。`as const`との組み合わせで、設定値の型を過度に広げずに検証できる。
