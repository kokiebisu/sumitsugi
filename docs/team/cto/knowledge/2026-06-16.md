# CTO Knowledge - 2026-06-16

## Daily Update (2026-06-16)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降でPPRが安定版となり、静的シェル+動的ストリームの組み合わせでTTFBを大幅改善できる。単一ルートで静的/動的コンテンツを混在させる設計が標準パターンになっている。

- **Turbopackへの移行完了:** webpackからTurbopack（Rust製）への完全移行が2025年末に完了し、ローカルビルドが最大10倍高速化。CIパイプラインの短縮にも直結するため、大規模チームほど恩恵が大きい。

- **React Server Components (RSC) によるバンドルサイズ削減:** クライアントに送るJSを最小化するRSC設計が定着。`"use client"`境界を意識的に末端コンポーネントに押し込めることで、インタラクティブでないUIのJS転送をゼロにできる。

- **Edge Runtimeによるグローバルレイテンシー最適化:** MiddlewareやAPIルートをEdgeで実行し、地理的にユーザーに近いノードで処理することでコールドスタートを回避。認証・リダイレクト・A/Bテストのロジックには特に効果的。

- **Core Web Vitals自動計測の内製化:** `next/image`（AVIF自動変換）・`next/font`（ゼロレイアウトシフト）・`useReportWebVitals`フックを活用し、外部RUM不要でLCP/CLS/INPを継続モニタリングする構成が推奨される。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Prerendering（PPR）の本格普及:** Next.js 15以降でPPRが安定版となり、静的シェルを即座に配信しつつ動的コンテンツをSuspense境界でストリーミングするパターンが標準化。TTFBとLCPの両立が現実的になった。

- **ポイント2: Server Actions + Optimistic UIの成熟:** `useOptimistic`と`useFormStatus`の組み合わせにより、サーバーラウンドトリップを意識させないUXが実現可能。ストリーミングと組み合わせることでSPAに近い体験をサーバー中心アーキテクチャで達成できる。

- **ポイント3: React 19のキャッシュ戦略の精緻化:** `use()`フックとサーバー側`cache()`の組み合わせにより、リクエストごとのデータ重複排除が自動化。複数のRSCが同一データを参照してもウォーターフォールが発生しにくくなった。

- **ポイント4: エッジランタイムとストリーミングの相性問題:** Cloudflare WorkersなどエッジランタイムはNode.js互換性が不完全なため、RSCのストリーミングが部分的にしか機能しないケースが依然存在する。本番運用では`runtime: 'nodejs'`との使い分けが現実解。

- **ポイント5: バンドルサイズとTree Shakingの観点:** RSCにより「サーバー専用コード」が明確に分離されるため、クライアントバンドルの肥大化を構造的に防げる。ただし`'use client'`の境界設計ミスで誤ってサーバーライブラリがクライアントに混入するリスクは継続的な監視が必要。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭:** TypeScriptフルスタック環境（Next.js等）では、エンドツーエンドの型安全性を自動生成できるtRPCが主流化しており、APIスキーマの二重管理が不要になった。

- **GraphQLの役割の明確化:** GraphQLは「全APIに使う」から「複雑なデータグラフや多クライアント向け（BFF）」に特化する使い方に落ち着き、Relay/Apollo ClientよりもTanStack Queryとの組み合わせが増えている。

- **RESTは健在、ただしOpenAPI 3.1+が必須:** REST自体は廃れていないが、型生成（Orval/openapi-ts）によりフロントエンドとの契約を自動化する運用が標準化しており、スキーマ駆動開発が前提になった。

- **エッジ・ストリーミングへの対応:** Vercel/Cloudflare Workersの普及でAPIもエッジで動くことが増え、Server-Sent Events（SSE）やHTTP Streamingが「LLM出力の受け皿」として急速に重要度を増している。

- **プロトコルの選定基準が変化:** 「REST vs GraphQL」の議論より「型安全性・生成ツールの成熟度・チームのTypeScript習熟度」で選ぶ時代。社内APIはtRPC、外部公開APIはREST+OpenAPI、が2026年のデファクト構成になりつつある。

### 4. serverless edge computing 2026

- **ポイント1: WebAssembly（Wasm）がエッジのデファクト実行環境に:** CloudflareのWorkerd、Fastly Compute、Vercel Edge FunctionsがWasmをネイティブサポートし、コールドスタートが事実上ゼロになった。Node.js互換レイヤーも成熟し、既存コードのエッジ移行コストが大幅に低下している。

- **ポイント2: SQLite-at-Edgeが分散データの主流解になりつつある:** Cloudflare D1、Turso（libSQL）などがエッジロケーションにSQLiteレプリカを配置するパターンが普及。強整合性が不要なリード重視ワークロードにおいては、レイテンシとコストの両面でセントラルDBを上回るケースが増えた。

- **ポイント3: AI推論のエッジシフトが加速:** Workers AI、Vercel AI SDK v4などでLLM推論をエッジで実行するパターンが定着。プライバシー規制（GDPR・改正個人情報保護法）への対応としてデータをリージョン外に出さない設計が求められており、エッジ推論の採用理由がパフォーマンスだけでなくコンプライアンスにも広がっている。

- **ポイント4: エッジとサーバーレスの境界が消えつつある:** AWSのLambda SnapStart、Cloudflare Durable Objects、Fastly Compute@Edgeなど、ステートフルな処理もエッジで扱えるようになり「エッジ＝ステートレス」という前提が崩れた。アーキテクチャ設計時に「どこで動かすか」より「どのデータ一貫性モデルを選ぶか」の判断が重要になっている。

- **ポイント5: オブザーバビリティの整備が急務:** エッジ環境は分散ノードが数百に及ぶためトレーシングが困難。OpenTelemetry + Baselime（Cloudflare買収）やAxiomなどエッジ特化の可観測性ツールが台頭しており、導入なしに本番運用するのはリスクが高い。ロールアウト戦略も「段階的エッジ展開」が標準になってきた。

### 5. authentication security best practices 2026

- **パスキー（Passkey）の標準化加速:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の事実上の標準となり、主要ブラウザ・OSでの対応が完成した。パスワードリスト攻撃やフィッシングを根本的に排除できるため、新規サービスではパスキーファーストの設計を推奨。

- **トークン有効期限の短縮とリフレッシュ戦略の見直し:** JWTアクセストークンは5〜15分以内、リフレッシュトークンはRotating方式（使用ごとに更新）が標準的なセキュリティ基準となった。トークン盗難時の被害を最小化するため、サーバーサイドでのリフレッシュトークン無効化リスト管理も必須。

- **デバイスバインドセッション（Device-Bound Sessions）の普及:** ChromeのDBSC（Device Bound Session Credentials）など、セッションをデバイスTPMに紐づける仕組みが実用化。Cookieの盗難によるセッションハイジャックを大幅に抑止できる。

- **AIを活用した異常ログイン検知の実装:** 通常の認証フローにML/AIベースの行動分析（ログイン時刻・地域・デバイスのパターン）を組み込み、リスクスコアに応じて追加認証を要求するアダプティブ認証が不可欠に。特にボット経由のクレデンシャルスタッフィング攻撃が増加している。

- **サプライチェーンリスクとしての認証ライブラリ管理:** Auth.js・NextAuth等の依存ライブラリのCVE監視と定期更新をCI/CDに組み込むことが必須。2025年以降、OSSの認証モジュールを標的にしたサプライチェーン攻撃が顕著に増加しており、`bun audit`等による定期スキャンを自動化すべき。

### 6. database architecture Prisma Supabase 2026

- **PrismaのPostgres-first戦略:** Prisma v6以降はSupabaseとの統合が深化し、`prisma migrate`がSupabaseのマイグレーション管理（`supabase db push`）と競合しやすいため、どちらを単一の真実源（source of truth）にするかをチームで明示的に決める必要がある。

- **Supabase Edge FunctionsとPrismaのコールドスタート問題:** Edge環境でPrismaのクライアントをそのまま使うとバンドルサイズとコールドスタートが問題になるため、2026年時点では`@prisma/adapter-pg`とコネクションプーリング（PgBouncer / Supabase Pooler）の組み合わせが推奨アーキテクチャになっている。

- **Row Level Security（RLS）との二重管理リスク:** SupabaseのRLSとPrismaのWhere句によるアクセス制御が重複するとバグの温床になる。RLSを主権者とし、Prismaは「形状変換（型・リレーション解決）」に専念させる役割分離が最も堅牢。

- **Prisma Accelerateによるグローバルキャッシュ:** Prismaの有償サービスAccelerateはエッジでクエリ結果をキャッシュし、Supabaseのread latencyをグローバルユーザーに対して大幅削減できる。自前でRedisを立てるより運用コストが低く、スタートアップフェーズには有力な選択肢。

- **スキーマドリフト検出の自動化:** CIパイプラインで`prisma migrate diff`を実行し、Supabase本番DBとPrismaスキーマの乖離を検知する仕組みを入れることが2026年のベストプラクティス。ドリフトを放置すると本番デプロイ時に予期しないマイグレーションが走るリスクがある。

### 7. WebAssembly Rust performance 2026

- **Component Model (WASM 2.0) の実用化:** 2026年時点でWASM Component Modelが安定し、RustコンポーネントをJS/Python/他言語から型安全に呼び出せるようになった。`wasm-tools` + `wit-bindgen` スタックが標準化されている。

- **WASIp2によるサーバーサイド採用加速:** WASI Preview 2が本格普及し、RustをWASMにコンパイルしてEdge/FaaS（Cloudflare Workers、Fastly Compute）で動かすパターンがコスト・起動速度の両面で優位。コールドスタートはネイティブコンテナの1/10以下。

- **SIMD + マルチスレッド対応の成熟:** Relaxed SIMDとwasm-threadsが主要ブラウザで安定サポートされ、Rustの`rayon`や`packed_simd`を使った数値計算・画像処理がネイティブの70-90%性能に到達。

- **`wasm-bindgen` から `wit-bindgen` へのシフト:** ブラウザ向けバインディングは`wasm-bindgen`が依然主流だが、クロスランタイム対応が必要な場合は`wit-bindgen`に移行が進んでいる。今から新規ライブラリを書くならComponent Model前提が将来安全。

- **ツールチェーンの成熟と落とし穴:** `cargo component`でビルドが一元化された一方、バイナリサイズ（`wasm-opt` + LTO必須）とデバッグ体験（ソースマップ精度）は依然課題。本番投入前に`twiggy`でバイナリ分析を行うことを推奨。

### 8. Next.js App Router patterns 2026

- **React Server Components (RSC) ファースト設計:** データフェッチをサーバー側に集約し、クライアントバンドルを最小化する。`'use client'` は状態・インタラクションが必要な末端コンポーネントにのみ付与するのが原則。

- **Partial Prerendering (PPR) の実用化:** 静的シェルと動的ストリームを同一ルートで共存させる PPR が安定版となり、TTFB と動的コンテンツのトレードオフを解消できる。`experimental.ppr` から正式 API へ移行済み。

- **Server Actions によるミューテーション統一:** API Routes を別途作る代わりに Server Actions でフォーム送信・DB 書き込みを処理し、`revalidatePath` / `revalidateTag` でキャッシュ無効化を宣言的に管理する。

- **`use cache` ディレクティブによる細粒度キャッシュ:** Next.js 15 以降、関数レベルで `use cache` を宣言し `cacheTag` / `cacheLife` で TTL と無効化を制御できる。`fetch` のオプションキャッシュより意図が明確で保守しやすい。

- **Turbopack のデフォルト化と開発体験向上:** `next dev --turbopack` がデフォルトになり HMR が大幅高速化。ただし webpack プラグインとの互換性ギャップが残るため、移行時は `next build` での動作検証を CI に必ず含めること。

### 9. Vercel Edge Functions optimization 2026

- **Cold Start の最小化:** Edge FunctionsはV8 Isolateベースのため従来のサーバーレスより高速だが、バンドルサイズを1MB以下に抑えることが重要。`edge` runtimeでは`node_modules`の全インポートを避け、軽量な代替（`jose`→JWT、`undici`不使用など）を選択する。

- **Fluid Compute（2025〜2026）の活用:** VercelはEdge RuntimeとServerless Runtimeを統合した「Fluid Compute」を展開中。待機時間中のCPUを他リクエストで再利用するため、ストリーミングレスポンスとの組み合わせでコストと遅延を同時削減できる。

- **Middleware の責務を限定する:** `middleware.ts`はすべてのリクエストを通過するため、重い処理（DB接続・複雑な認証）を置かない。フラグチェック・リダイレクト・地域ルーティングなど軽量ロジックに絞り、重い処理はRoute Handlersへ委譲する。

- **KV・キャッシュ戦略の見直し:** Vercel KV（Upstash Redis）との組み合わせでEdgeからのデータアクセスが高速化。`fetch()`の`cache`オプションと`revalidate`を使ったData Cacheを積極活用し、オリジンへのフォールバックを最小化する。

- **Observability の強化:** 2026時点でVercel Speed Insights・OTELトレーシングのEdge対応が成熟。`waitUntil()`でレスポンス後に非同期ロギングを実行し、レイテンシへの影響をゼロにしながら本番トレースを収集するパターンが定番化している。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の本格活用:** `satisfies` による型チェックは推論を維持しつつ安全性を担保できるため、`as` キャストの代替として標準パターンになっている。`const config = { ... } satisfies Config` でオブジェクトリテラルの型安全性を高める。

- **branded types / nominal types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなブランド型でプリミティブの混同を防ぐパターンが、特にドメイン層で定着。Zodの `.brand()` と組み合わせることでバリデーションと型安全を同時に達成できる。

- **`const` 型パラメータ（`<const T>`）の活用:** TypeScript 5.0以降の `const` 型パラメータにより、関数引数のリテラル型推論が格段に改善。ルーターやORMの型定義でwider型への拡張を抑制できる。

- **`noUncheckedIndexedAccess` の有効化が標準化:** `tsconfig.json` での `noUncheckedIndexedAccess: true` が実質的なベストプラクティスに。配列・オブジェクトのインデックスアクセスが `T | undefined` となり、実行時エラーをコンパイル時に捕捉できる。

- **Template Literal Types によるAPIパスの型付け:** `type Route = \`/api/${string}\`` のようにURL・イベント名・CSSプロパティを型で縛るパターンが増加。OpenAPIスキーマからの自動生成と組み合わせることで、バックエンドとの契約をコンパイル時に保証できる。
