# CTO Knowledge - 2026-02-19

## Daily Update (2026-02-19)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 15以降でStableになったPPRにより、静的シェルと動的コンテンツを同一ルートで混在させられる。Suspense境界の設計がパフォーマンスの鍵となる。

- **React Server Components によるバンドル削減:** RSCでサーバー側にロジックを移すことでクライアントJSを大幅削減できる。`"use client"`の境界を最小化し、データフェッチはサーバーコンポーネントで完結させるのがベストプラクティス。

- **Turbopack の実用段階移行:** Next.js 15でTurbopackがdev環境のデフォルトになり、ローカルビルドが最大50%高速化。CI/CD環境でも段階的に採用が進んでいる。

- **Server Actions のキャッシュ戦略:** `revalidatePath` / `revalidateTag` を活用したオンデマンド再検証により、過剰なISR再生成を防ぎつつデータ鮮度を保つ設計が重要。

- **Edge Runtime とRegional Caching:** Vercel Edge Networkを活用したルート単位のEdge Runtime採用で、グローバルユーザーへのレイテンシを削減。ただしNode.js APIの制約に注意しながら適用範囲を選定する必要がある。

### 2. React Server Components streaming 2026

- **RSCとSuspenseの深い統合:** 2026年時点でNext.js App RouterはRSC + Suspense境界によるストリーミングが標準化され、`loading.tsx`だけでなく細粒度のSuspenseでウォーターフォールを排除するパターンが主流になっている。

- **PPR（Partial Prerendering）の普及:** Next.js 15以降でPPRが安定版となり、静的シェルを即座に配信しつつ動的部分をストリームする「ハイブリッドレンダリング」がEdgeデプロイメントと組み合わせて実運用に入っている。

- **Server Actionsとの相互作用:** フォームやミューテーションにServer Actionsを使う場合、`useOptimistic`との組み合わせによりストリーミング中のUI状態管理が整理され、クライアントJSバンドルをさらに削減できるアーキテクチャが確立されつつある。

- **Turbopackによるビルド高速化:** Turbopackの本番対応が進み、大規模RSCプロジェクトでのHMRとビルド時間が従来比で大幅短縮。ストリーミングの恩恵を最大化するためのコード分割戦略と組み合わせが重要な設計判断になっている。

- **サードパーティライブラリのRSC対応遅れ:** 依然としてuseEffect依存や`"use client"`強制のライブラリが多く、RSCツリー内での利用境界設計（Client Boundaryの適切な配置）がアーキテクチャ上の最重要課題の一つとして残っている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの成熟とフルスタック型安全性の標準化:** tRPC v11とNext.js App Routerの統合が成熟し、フロントエンド・バックエンド間でZodスキーマを共有する型安全なAPI設計がスタートアップの事実上の標準になりつつある。

- **GraphQLの「適材適所」への回帰:** Netflixやショッピファイ規模の複雑なグラフデータには依然有効だが、オーバーエンジニアリングの反省からBFF（Backend for Frontend）パターンと組み合わせたREST+OpenAPIへの回帰も増加している。

- **REST + OpenAPI 3.1の再評価:** `zod-to-openapi`や`@hono/zod-openapi`等のツールにより、コードファーストでOpenAPI仕様を自動生成しつつ型安全を保てるようになり、RESTの「シンプルさ」と型安全の両立が実現している。

- **Server ActionsによるAPI層の薄型化:** Next.js 15のServer Actionsが実用段階に入り、CRUD操作の多いMVPではAPIエンドポイント自体を省略するアーキテクチャが選択肢として現実的になった（ただしモバイルアプリ展開時は要再設計）。

- **エッジランタイムとプロトコルの変化:** Cloudflare Workers・Vercel Edge等の普及でHTTP/3・WebSocketsの代替としてServer-Sent Events（SSE）とHTTP Streamingが再注目されており、AIチャット等のリアルタイム機能実装に実用的な選択肢となっている。

### 4. serverless edge computing 2026

- **ポイント1: WebAssembly（Wasm）がエッジの標準ランタイムに:** V8 isolateに加えWasmがCloudflare Workers・Fastly Computeで本格採用され、言語非依存のエッジ実行が現実的に。Next.jsのEdge Runtimeも`runtime: 'edge'`でWasm対応が進む。

- **ポイント2: エッジDBとの統合でコールドスタート問題が緩和:** Cloudflare D1・Turso（libSQL）などエッジネイティブなSQLiteベースDBが普及し、グローバル分散レプリカによりエッジ関数からのDBレイテンシが実質ゼロに近づいている。

- **ポイント3: AI推論のエッジオフロードが加速:** Cloudflare Workers AI・Vercel AI SDKのEdge対応により、軽量モデル（embedding生成・分類）をエッジで実行するパターンが定着。オリジンへのラウンドトリップ削減と個人データのローカル処理を両立。

- **ポイント4: エッジミドルウェアによるA/Bテスト・パーソナライゼーションが主流化:** Next.jsの`middleware.ts`やVercel Edge Configを活用し、フラグ管理やユーザーセグメント分岐をオリジン到達前に処理。レスポンスタイムへの影響を最小化しながら動的体験を提供。

- **ポイント5: コスト管理とコールドスタートのトレードオフが依然課題:** リクエスト課金モデルは低トラフィック時に有利だが、メモリ上限（128MB〜256MB）とCPU制限（数ms〜数十ms）がステートフルな処理を制約する。アーキテクチャ設計時は「エッジで何をやらないか」の判断が重要。

### 5. authentication security best practices 2026

- **パスキー（Passkey）の本格採用:** FIDO2/WebAuthnベースのパスキーがパスワードレス認証の標準となりつつあり、フィッシング耐性が高くUXも優れるため、新規システムでは最優先で採用すべきアーキテクチャ選択肢になっている。

- **トークンライフタイムの最小化とリフレッシュ戦略の厳格化:** アクセストークンの有効期限を5〜15分に短縮し、リフレッシュトークンのローテーション（RTR）を必須とすることで、トークン漏洩時の被害範囲を限定する設計が業界標準となっている。

- **デバイスバインディングとコンテキスト認証:** ログイン時のIPアドレス・デバイス指紋・行動パターンを組み合わせたリスクベース認証（RBA）が普及し、異常なアクセスパターンを検知した場合にのみ追加認証を要求するアダプティブMFAが主流になっている。

- **セッション管理のゼロトラスト化:** 「一度認証すれば信頼する」モデルを廃止し、継続的にセッションの正当性を検証するアーキテクチャ（Continuous Verification）が重要で、特に長時間セッションでのアクセス権の再評価が必須となっている。

- **OAuthサプライチェーンリスクへの対応:** サードパーティIDプロバイダー（IdP）への依存リスクが顕在化しており、IdP障害時のフォールバック戦略と、OAuthスコープの最小権限設計（Least Privilege Scoping）の徹底が求められている。

### 6. database architecture Prisma Supabase 2026

- **Prisma Accelerate の活用:** エッジキャッシングとコネクションプーリングをグローバルに提供し、Supabaseのサーバーレス環境でのコネクション枯渇問題を解消。Next.js App RouterのServer Componentsとの相性が特に良い。

- **Row Level Security (RLS) とPrismaの役割分担:** セキュリティポリシーをSupabaseのRLS層に委譲し、Prismaはスキーマ定義・型安全なクエリに特化する設計が主流。アプリケーションコードの肥大化を防ぎつつ、マルチテナント要件を満たせる。

- **Supabase Realtime + Prisma の使い分け:** リアルタイム購読はSupabaseのWebSocket経由、バッチ処理・複雑なJOINクエリはPrismaと明確に役割を分けるアーキテクチャが定石になりつつある。

- **Edge-native データアクセスパターンの普及:** Supabase Edge FunctionsとPrisma Accelerateの組み合わせにより、レイテンシ重視の読み取り処理をエッジで完結させ、書き込みはリージョナルDBへ集約するCQRS的パターンが増加している。

- **型安全性の徹底:** Prisma ClientのTypeScript型とSupabaseの自動生成型（`supabase gen types`）を組み合わせることで、DB〜フロントエンドまでの型整合性を保証する設計が2026年時点での標準プラクティス。

### 7. WebAssembly Rust performance 2026

- **WASM GCとコンポーネントモデルの本格普及:** WebAssembly Component Modelが2025年末に安定化し、Rustで書いたWASMモジュールを言語間で型安全に組み合わせられるようになった。マイクロサービス的なWASMコンポジションがエッジ環境で実用段階に入っている。

- **WASIp2によるサーバーサイド採用の加速:** WASI Preview 2の標準化により、RustのWASMバイナリがCloudflare Workers・Fastly・wasmtimeなどのランタイムで本番稼働するケースが増加。コールドスタートが数十μs台で、Dockerコンテナより桁違いに速い。

- **SIMDとスレッド並列化の成熟:** WASM SIMDおよびShared Memoryスレッドのサポートがブラウザ・サーバー両方で安定し、Rustの`rayon`相当の並列処理をWASMでも活用できるようになった。画像処理・暗号・ML推論で顕著なパフォーマンス向上が得られる。

- **バイナリサイズと起動速度のトレードオフ管理:** `wasm-opt`（Binaryen）と`wasm-pack`の最適化フラグ、そして`cargo`の`opt-level = 'z'`組み合わせが実務の標準になりつつある。ただしAOTコンパイル（Cranelift/V8 TurboFan）を前提にすれば、起動コストよりスループット最適化を優先する設計が有効。

- **Rust固有の強み——ゼロコストメモリ管理:** GCを持たないRustはWASMのLinear Memory上でのメモリ管理が予測可能で、GC pauseがない。2026時点ではGoやKotlinのWASM GC実装と比較して、レイテンシ安定性でRustが依然として優位であり、リアルタイム処理用途では第一選択肢。

### 8. Next.js App Router patterns 2026

- **Server Components ファースト設計:** RSC（React Server Components）をデフォルトとし、`'use client'`は本当に必要な箇所のみに限定する設計が定着。クライアントバンドルを最小化し、Core Web Vitalsの改善に直結する。

- **Partial Pre-rendering（PPR）の本格活用:** 静的シェルと動的コンテンツを同一ページで共存させるPPRが主流に。`<Suspense>`境界を意図的に設計することで、TTFBを犠牲にせずパーソナライズが実現できる。

- **Server Actionsによるミューテーション統一:** APIルートを介さずServer Actionsでフォーム処理・DB更新を行うパターンが成熟。`useActionState`との組み合わせで楽観的UIとエラーハンドリングが宣言的に書ける。

- **`cache()`・`revalidateTag()`によるキャッシュ戦略の明示化:** Next.jsのデータキャッシュはオプトインが基本（v15以降）。フェッチごとにキャッシュ意図を明示し、タグベースの再検証でインクリメンタル更新を細かく制御する設計が必須。

- **Parallel RoutesとIntercepting Routesの活用:** モーダルやサイドパネルをURLに紐づけるIntercepting Routes（`(.)path`）が実用フェーズに。シェアリングやブラウザ戻るボタンへの対応がUX品質の差別化ポイントになっている。

### 9. Vercel Edge Functions optimization 2026

**Vercel Edge Functions最適化 2026 — CTOの視点**

- **Fluid Computeによる並列処理:** Vercelが導入したFluid Computeにより、同一インスタンスで複数リクエストを並行処理可能になった。コールドスタートの頻度が大幅に減少し、特にトラフィックスパイク時のコスト効率が向上している。

- **Edge RuntimeとNode.js Runtimeの使い分け:** Edge FunctionsはV8 Isolateベースで起動が超高速だが、Node.js API（fs、crypto等）が使えない制約がある。2026時点のベストプラクティスは、認証チェック・A/Bテスト・リダイレクトはEdge、複雑なビジネスロジックはNode.js Serverless Functionsに分離するハイブリッドアーキテクチャ。

- **Edge Config + KV Storeの活用:** Edge Configはサブミリ秒でフラグ・設定値を読み取れるため、フィーチャーフラグやレート制限の実装に最適。Vercel KVと組み合わせることで、セッション管理をエッジで完結させられる。

- **Streaming ResponseとRSCの統合:** React Server ComponentsのStreamingと組み合わせることで、TTFBを大幅に改善できる。部分的なHTMLをエッジから即座にストリーミングし、重い処理は並行して実行するパターンが標準化している。

- **リージョン戦略とISRの最適化:** `revalidate`を短く設定したISRページをエッジでキャッシュし、Stale-While-Revalidateで提供するアーキテクチャが高トラフィックサービスの定石。日本ユーザー向けには`nrt1`（東京）リージョンをプライマリに指定することでレイテンシを最小化できる。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly __brand: 'UserId' }` のようなBranded/Nominal Typesが標準パターンとして定着し、プリミティブ型の誤用によるバグを型レベルで防ぐ手法が主流になっている。

- **Template Literal Types の実践活用:** APIルートパターン（`/users/${string}`）やCSSプロパティの型付けなど、文字列リテラルの組み合わせを型で表現することで、ランタイムエラーをコンパイル時に検出できる領域が拡大している。

- **`satisfies` 演算子の定着:** `const config = { ... } satisfies Config` により型推論の恩恵を保ちながら型チェックを行えるため、`as const` との使い分けが重要なパターンとして確立されている。

- **Zod + 型推論の連携:** バリデーションスキーマから `z.infer<typeof schema>` で型を生成する「Single Source of Truth」パターンが定着し、APIバウンダリでの型安全性を担保する実装が標準化されている（本プロジェクトでも採用推奨）。

- **`noUncheckedIndexedAccess` の普及:** `tsconfig.json` での厳格な配列アクセス型チェックが普及し、`arr[0]` が `T | undefined` として扱われることで、配列操作起因のランタイムエラーが大幅に削減されるようになっている。
