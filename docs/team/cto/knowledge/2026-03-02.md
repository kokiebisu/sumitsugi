# CTO Knowledge - 2026-03-02

## Daily Update (2026-03-02)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的コンテンツを単一リクエストで配信する PPR が Next.js 15 以降で安定化し、TTFB を劇的に改善できる。キャッシュ戦略を Suspense 境界単位で設計することが 2026 年のベストプラクティス。

- **Turbopack への移行完了:** Webpack から Turbopack へのデフォルト切り替えが完結し、ローカルビルドが最大 10 倍高速化。CI/CD パイプラインのビルド時間短縮に直結するため、早期移行で恩恵を最大化すべき。

- **React Server Components による JS バンドル削減:** データフェッチロジックをサーバーサイドに移し、クライアントへ送る JavaScript を最小化する設計が標準化。`use client` の境界を慎重に引き、不要なハイドレーションコストを排除することが重要。

- **Edge Runtime とグローバル配信の最適化:** Middleware や API Route を Edge Runtime で実行することで、ユーザー最寄りのエッジで処理し、レイテンシを削減。ただし Edge の制約（Node.js API 非対応）を把握した上で、適切なルートのみ Edge に寄せる判断が必要。

- **`next/image` と Web Vitals の継続的モニタリング:** LCP・CLS・INP の Core Web Vitals が SEO ランキングに直結する状況は変わらず。`next/image` の `priority` 属性と `sizes` 設定を丁寧に行い、Vercel Analytics や OpenTelemetry でリアルユーザー計測を継続することが競争優位の源泉。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Prerendering (PPR) の本格普及:** Next.js 15以降でPPRが安定版となり、静的シェルと動的ストリーミングを同一ページで混在できる設計が標準化。TTFBを維持しながらパーソナライズも可能になった。

- **ポイント2: Suspense境界の粒度設計が鍵:** ストリーミングの恩恵を最大化するには、Suspenseの境界をコンポーネント単位で細かく設計する必要がある。粗すぎると全体がブロックされ、細かすぎるとウォーターフォールが発生するトレードオフを理解した設計が求められる。

- **ポイント3: Server Actions との統合でRound-tripが減少:** RSCとServer Actionsの組み合わせにより、フォーム送信・データ更新のクライアント↔サーバー往復が大幅削減。楽観的UI更新（`useOptimistic`）と組み合わせると体感速度が劇的に向上する。

- **ポイント4: Edge RuntimeとのStreaming相性:** Vercel Edge / Cloudflare Workers上でのRSCストリーミングは、Node.jsランタイムより低レイテンシだが、`Node.js`固有APIが使えない制約がある。依存ライブラリのEdge対応可否を事前に確認することが実務上の必須チェック項目。

- **ポイント5: キャッシュ戦略の再設計が必要:** `fetch`のキャッシュセマンティクス（Next.js 15でデフォルトno-cache化）により、RSC内の非同期データ取得ごとにキャッシュポリシーを明示的に設定する必要がある。`unstable_cache`や`revalidateTag`を活用したきめ細かいキャッシュ制御がパフォーマンスの差別化要因となる。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの成熟とフルスタック型安全性の標準化:** 2026年時点でtRPCはNext.js/Remixとの統合が深まり、型推論をAPIレイヤー全体に伝播させる「型ファースト設計」がモダンスタックの標準となった。バックエンド・フロントエンド間の契約定義コストがほぼゼロになっている。

- **GraphQLの選択的採用:** BFF（Backend for Frontend）パターンでの採用は依然強いが、Over-fetchingやスキーマ管理コストが課題のため、小〜中規模プロジェクトではtRPCまたはREST+OpenAPIが選ばれる傾向。GraphQLは複数クライアント・複雑なデータグラフを持つ大規模サービスに限定されつつある。

- **REST + OpenAPI 3.1の再評価:** AIコード生成ツール（GitHub Copilot、Claude）との相性から、OpenAPI仕様の機械可読性が再評価されており、スキーマ駆動開発（Schema-First）+自動バリデーション生成のパイプラインが普及している。

- **Edge-First API設計:** Vercel/Cloudflare Workersの普及でAPIロジックをエッジに近づける設計が一般化。Cold startを排除するため、軽量なRPCスタイルAPIとストリーミングレスポンス（SSE/WebStreams）の組み合わせが増えている。

- **AIエージェント向けAPI設計の台頭:** MCPプロトコルに代表されるように、LLMエージェントが消費することを前提としたAPI設計（ツール定義、構造化出力、冪等性の保証）が2026年の新たな設計関心事として浮上している。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** WebAssembly（WASM）とONNXランタイムの成熟により、LLMの軽量モデルをエッジノードで直接実行するパターンが普及。レイテンシ削減と個人情報のローカル処理が両立できる。

- **Durable Objects / Stateful Edgeの台頭:** Cloudflare Durable ObjectsやVercel KVのようなエッジ近傍の永続ストレージが成熟し、「ステートレス前提」というサーバーレスの制約が実質的に解消されつつある。

- **Cold Start問題の終焉:** V8 Isolatesベースのランタイム（Cloudflare Workers, Deno Deploy）が主流化し、従来のLambdaコンテナ起動の数百ms問題が1ms以下に。Node.js互換レイヤーの完成度も向上している。

- **エッジ + データベースの距離問題への解答:** PlanetScale Boost、Neon（PostgreSQL serverless）、Turso（libSQL）など「エッジ対応DB」が実用段階に入り、グローバルレプリケーションとエッジ関数の組み合わせでデータ遅延が設計上の課題から実装の選択肢へ変わった。

- **コスト可視性とObservabilityの重要性増大:** リクエスト単位課金の複雑化により、OpenTelemetryベースの分散トレーシングをエッジ層まで貫通させるアーキテクチャが必須。コールドスタートやキャッシュミスのコストを定量把握しないと、予算超過リスクが高い。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の主流化:** パスワードレス認証がエンタープライズでも標準となり、フィッシング耐性のあるパスキーへの移行が急務。従来のパスワード+SMS 2FAは非推奨として扱うべき。

- **トークンバインディングとDPoP（Demonstrating Proof-of-Possession）:** OAuthアクセストークンの盗難・再利用攻撃に対し、DPoPによってトークンをクライアント鍵ペアに紐づける実装が2026年のAPI認可のベストプラクティスとして定着しつつある。

- **継続的アクセス評価（CAE）の実装:** セッション発行時の1回限りの認証ではなく、リスクシグナル（IP変化・デバイス状態等）をリアルタイムで評価してセッションを即時失効させる仕組みが必要。Azure AD・Google Workspaceでは既に標準実装済み。

- **AI駆動の異常検知との統合:** 認証ログをSIEMに流すだけでなく、機械学習による行動ベースライン（ログイン時刻・操作パターン）の逸脱を自動検知し、再認証をトリガーするアーキテクチャが攻撃対応の速度を大幅に向上させる。

- **サプライチェーン攻撃への対策としてのIDPの堅牢化:** OIDCプロバイダー自体が攻撃対象となるケースが増加。IDPのSLAとセキュリティ監査記録の確認、フォールバック認証フロー、セッション署名の検証を設計段階から組み込むことが不可欠。

### 6. database architecture Prisma Supabase 2026

- **Prisma Accelerate の本格採用:** エッジランタイム（Cloudflare Workers等）でのPrisma利用が標準化し、コネクションプーリングとグローバルクエリキャッシュにより、従来のサーバーレス環境でのコールドスタート問題が大幅に軽減された。

- **Supabase Branching によるDev/Prod分離:** Supabaseのデータベースブランチ機能が成熟し、PRごとに独立したDB環境を自動作成するCI/CDパイプラインが実現。スキーママイグレーションのリスクが劇的に低下した。

- **型安全性の統合強化:** Supabaseの型自動生成（`supabase gen types`）とPrismaのスキーマ定義を組み合わせ、DB→API→フロントエンドまで型が伝播するフルスタック型安全アーキテクチャが主流になりつつある。

- **Row Level Security (RLS) とアプリ層の責務分離:** SupabaseのRLSをデータアクセス制御の主要レイヤーとして活用し、アプリ層の認可ロジックを簡素化するパターンが定着。ただしPrismaと併用する場合はサービスロールキーの管理に依然注意が必要。

- **PostgreSQL拡張エコシステムの活用:** pgvector（RAG/AIベクトル検索）、pg_cron（スケジュールジョブ）等のPostgreSQL拡張をSupabase経由で活用するケースが急増。インフラをシンプルに保ちながらAI機能を統合できる点が競争優位になっている。

### 7. WebAssembly Rust performance 2026

- **WASI 2.0 (Component Model) の成熟:** WebAssembly System Interface のComponent Modelが2026年に実用段階に入り、RustコンポーネントをJavaScript/Python等と型安全に組み合わせるポリグロット設計が現実的になった。マイクロサービスのホットパス処理をRust WASMに置き換えるアーキテクチャが増加している。

- **Wasmtime/WASMERのJITコンパイル最適化:** ランタイム側のAOT/JITコンパイルが成熟し、ネイティブ比95%以上のパフォーマンスを安定して達成。特にCraneliftバックエンドの改善により、Rustで書いたCPU集約型処理（画像・暗号・ML推論）のWASMデプロイが本番選択肢になった。

- **SIMD命令セットの標準化完了:** Wasm SIMDがRelaxed SIMDまで標準化され、RustのSIMDイントリンシクスがWASMターゲットでほぼそのまま動作する。ブラウザ・サーバー両方で音声/動画処理のWASM移植が加速している。

- **Rustのコンパイルサイズ問題の改善:** `wasm-opt` + `wasm-bindgen` + Rustの`strip`オプション組み合わせにより、100KB未満のバイナリが現実的に。エッジ環境（Cloudflare Workers、Fastly Compute）でのコールドスタートが大幅改善し、サーバーレスWASMの採用障壁が下がった。

- **非同期Rustとのインテグレーション:** `tokio`ベースの非同期コードをWASMターゲットに移植するエコシステムが整備され、`wasm32-wasip2`ターゲットでI/Oを含む実用的なサービスを実装できるようになった。ただしスレッドモデルの制約（SharedArrayBuffer要件）はまだ考慮が必要。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点では「必要な時だけ `'use client'`」が標準パターン。データフェッチをサーバー側に集約することでバンドルサイズを削減し、初期ロードを最適化できる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的コンテンツを同一ルートで混在させるPPRが安定化。`next.config.ts` で `ppr: true` を有効化し、`<Suspense>` でダイナミック境界を明示するのが推奨アーキテクチャ。

- **Server Actions によるフォーム処理の統一:** `action={serverAction}` パターンがREST APIの代替として定着。Progressive Enhancementが自動対応され、クライアント/サーバー間の型共有も容易になった。

- **`use cache` / `cacheTag` による細粒度キャッシュ制御:** `fetch` オプション依存から脱却し、関数レベルでキャッシュ戦略を宣言的に指定できる。`revalidateTag` との組み合わせでISR相当の動的更新が実現可能。

- **Turbopack が本番標準に:** `next dev --turbopack` がデフォルト化し、大規模プロジェクトでもHMRが実用的な速度に。ただし一部のカスタムWebpackプラグインとの互換性は要検証。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Runtimeの選択的採用が鍵 — すべての関数をEdgeに移行するのではなく、レイテンシ感度の高いルート（認証チェック、A/Bテスト、パーソナライゼーション）に絞ることで、Cold Start問題を回避しつつ効果を最大化できる。

- **ポイント2:** Fluid Compute（旧Streaming）との組み合わせ — Edge FunctionsとVercel Fluid Computeを組み合わせ、長時間処理はNode.jsランタイムに委ねるハイブリッド構成が2026年の標準パターンとなりつつある。

- **ポイント3:** KV・Blob・Postgresとのデータ境界設計 — Edge環境ではVercel KVやPostgres（Edge compatible）との接続コストが支配的になるため、データアクセスパターンを事前設計しないとEdge移行の恩恵が相殺される。

- **ポイント4:** バンドルサイズの厳格管理 — EdgeランタイムはNode.js APIの一部しかサポートしないため、`import`するライブラリのEdge互換性確認と、バンドルサイズの1MB制限への対応が継続的な課題となる（`@vercel/edge` + tree-shakingが有効）。

- **ポイント5:** Middleware最適化の優先度 — `middleware.ts`はすべてのリクエストに適用されるため、ここに重い処理を置くと全体のレイテンシに直撃する。Matcher設定で対象パスを最小化し、処理を軽量に保つことがパフォーマンスの根幹となる。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded Types（Nominal Types）が標準パターンとして定着し、プリミティブ型の混同バグを型レベルで防ぐアプローチが広まっている。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` が2026年では必須ツールとなり、型推論を維持しながら型チェックを行うことで、`as const` との組み合わせによる厳密な型付けが一般化している。

- **Template Literal Types による API 契約:** `type Route = '/users' | '/users/${string}/posts'` のようなTemplate Literal Typesでルートやイベント名を型定義し、ランタイムエラーをコンパイル時に検出するパターンが普及している。

- **`noUncheckedIndexedAccess` の標準化:** `tsconfig.json` の厳格オプション（特に `noUncheckedIndexedAccess`）がチームの標準設定となり、配列・オブジェクトアクセスの `undefined` 漏れをゼロにする文化が定着しつつある。

- **Zod + 型推論の統合:** `z.infer<typeof schema>` によりランタイムバリデーションと静的型を一元管理するパターンが業界標準となり、`tRPC` や `Hono` のようなフレームワークと組み合わせたEnd-to-End型安全が当然の前提になっている。
