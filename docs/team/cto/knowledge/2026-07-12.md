# CTO Knowledge - 2026-07-12

## Daily Update (2026-07-12)

### 1. Next.js performance optimization 2026

- **React Server Components とストリーミングSSRの最適化:** Next.js 16ではRSCペイロードの圧縮とセレクティブハイドレーションがデフォルト最適化され、初期表示速度（TTFB/LCP）を大幅短縮できる。前の住人プロフィールや物件詳細ページのような静的性の高いコンテンツはServer Componentsに寄せ、インタラクティブ要素のみClient Componentに分離するのが鉄則。

- **Partial Prerendering (PPR) の本格運用:** 静的シェルを即座に返しつつ動的部分（在庫状況、価格変動など）を非同期でストリーミングする方式が標準化された。物件一覧ページで検索結果の動的フィルタと静的レイアウトを分離すれば、CLS（レイアウトシフト）とTTIの両方を改善できる。

- **画像・アセットの自動最適化とEdge配信:** `next/image`のAVIF/WebP自動変換とCDNエッジキャッシュの組み合わせが必須。物件写真は枚数が多くLCPのボトルネックになりやすいため、優先読み込み（`priority`属性）と遅延読み込みの使い分けを徹底すべき。

- **Turbopackによるビルド・開発体験の高速化:** 本番ビルドでもTurbopackが安定運用フェーズに入り、ビルド時間短縮とバンドルサイズの最適化が同時に得られる。CI上の`bun run build`時間短縮にも直結するため、ベータローンチ前のCIパイプライン改善に活用できる。

- **Zodバリデーションとの統合による境界最適化:** Server Actions/Route Handlerの入力検証をZodで一元化しつつ、不要なクライアントJSバンドルを削減する設計が主流化。フォーム送信（内見予約・お問い合わせ等）のパフォーマンスとセキュリティを同時に担保できる。

### 2. React Server Components streaming 2026

- **段階的ストリーミングの標準化:** `loading.tsx`とSuspense境界を組み合わせた部分的ストリーミングが2026年ではデフォルトパターンとなり、TTFB（Time to First Byte）を犠牲にせずファーストビューを即座に返せるようになっている。物件一覧ページなど重いデータ取得を伴う画面で特に効果が大きい。

- **Partial Prerendering (PPR) の本格運用:** Next.js 16ではPPRが安定版となり、静的シェルを即座に配信しつつ動的部分（在庫状況・価格など）だけをストリーミングで後追い注入できる。物件詳細ページのように「静的な間取り情報＋動的な公開ステータス」が混在するUIと相性が良い。

- **RSC Payloadのキャッシュ戦略が重要に:** ストリーミングが前提になったことで、RSCペイロード自体のCDNキャッシュ・再検証戦略（`revalidateTag`/`revalidatePath`の粒度設計）が性能のボトルネックになりやすい。前の住人→次の住人への引き継ぎフローのような更新頻度の高いデータは、キャッシュタグ設計を早期に固めておくべき。

- **エラーバウンダリとストリーミングの併用:** ストリーミング中に発生したサーバーエラーがクライアントに部分的にしか伝播しない問題が既知の落とし穴。`error.tsx`をSuspense境界ごとに細かく配置し、フォーム送信や決済など重要フローでは同期的なエラーハンドリングにフォールバックする設計が推奨される。

- **開発体験面でのデバッグ難易度上昇:** ストリーミング境界が増えるほど「どのコンポーネントがどの順番でレンダリングされたか」の把握が難しくなるため、React DevToolsのProfilerタブとNext.jsの`instrumentation.ts`を組み合わせた可観測性の確保が2026年のベストプラクティスとして定着しつつある。

### 3. API design REST GraphQL tRPC 2026

## API設計トレンド 2026(CTO視点)

- **ポイント1: tRPCの採用拡大とend-to-end型安全性の標準化** Next.js + TypeScriptモノレポ構成では、REST/GraphQLのスキーマ定義コストを避けてtRPCでフロント〜バックエンドの型を直接共有する構成が主流になりつつある。sumitsugiのようなApp Router構成では、Server ActionsとtRPCの組み合わせでAPI層自体を薄くする選択肢も検討価値あり。

- **ポイント2: GraphQLは「集約・BFF層」に用途が収束** 汎用APIとしてのGraphQLよりも、複数マイクロサービスを束ねるBFF(Backend for Frontend)としての利用が中心になっており、単一Next.jsアプリのような比較的シンプルな構成では過剰設計になりがち。

- **ポイント3: RESTは依然として外部公開API・サードパーティ連携のデファクト** 決済連携や外部弁護士向けの法務確認フローなど、社外システムとの連携ではRESTfulかつOpenAPI仕様書ベースの設計が信頼性・ドキュメント性の観点で優位。

- **ポイント4: Zodなどのランタイムバリデーションとスキーマの統合が加速** tRPC/REST問わず、Zodスキーマを「型定義兼バリデーション兼APIドキュメント」として一元管理する設計が標準化しており、`.claude/rules/standards.md`にあるZod活用方針とも合致する。

- **ポイント5: エッジ実行を前提としたAPI設計への移行** Next.js 16のエッジランタイム対応拡大に伴い、レイテンシ最適化のためAPI RouteをEdge Functionsで動かす前提の軽量なリクエスト/レスポンス設計(GraphQLの重いリゾルバより単純なJSON API)が好まれる傾向。

### 4. serverless edge computing 2026

- **エッジランタイムの標準化:** WinterCG(WinterTC)によるWeb標準API準拠が進み、Cloudflare Workers・Vercel Edge・Deno Deployなど各社ランタイム間のコード互換性が大幅に向上している。移植性を意識するなら`fetch`/`Request`/`Response`ベースのAPIに寄せて実装すべき。

- **コールドスタート実質ゼロ化:** V8 IsolateやWasmベースの軽量サンドボックスにより、コンテナ型サーバーレス(Lambda等)よりエッジ関数の起動が桁違いに速くなっている。低レイテンシが要求される認証・パーソナライゼーション処理はエッジ側に寄せる価値が高い。

- **エッジDB/ステート層の成熟:** Cloudflare D1、Turso、PlanetScaleなどエッジ最適化されたSQLiteベースDBが実用段階に入り、read-heavyなワークロードをオリジンDBに頼らずエッジで完結できるようになってきた。うちのようなpropertyデータの読み取り中心なUIには特に相性が良い。

- **AI推論のエッジ配置:** 軽量LLM推論やベクトル検索(embeddingsのキャッシュ・類似検索)をエッジで実行する構成が一般化しつつあり、レコメンド・検索系機能のレイテンシ改善に直結する。

- **コスト構造の逆転リスク:** リクエスト課金モデルのエッジ実行は、トラフィックが急増すると従来のサーバー常駐型より割高になるケースがあるため、MVPローンチ初期は良いが、スケール時のコスト試算をしておく必要がある。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証（Passkey）がデフォルトの選択肢となりつつあり、フィッシング耐性のあるWebAuthn実装への移行が本人確認コストとサポート負荷を大きく下げる。sumitsugiのような個人間取引プラットフォームでは、なりすまし防止の観点からも早期導入価値が高い。

- **多層防御としてのリスクベース認証:** 単純な2FAではなく、デバイスフィンガープリント・行動分析・IPレピュテーションを組み合わせたアダプティブ認証が主流化しており、ログイン頻度の低いユーザー（住み継ぎのような低頻度高額取引）ほど異常検知の精度が重要になる。

- **セッション管理とトークンの短寿命化:** JWTなどのアクセストークンは短命化（5-15分）し、リフレッシュトークンローテーションとデバイスバインディングを組み合わせるのが定石。長期セッションを許容する「思い出のインテリア」閲覧のようなUXと、決済フローで求められる再認証の粒度を分離設計する必要がある。

- **サプライチェーン/依存ライブラリの認証周りの脆弱性監視:** next-authやOAuthライブラリのCVEが継続的に出ており、Dependabot等での自動更新に加え、認証まわりの依存パッケージは`security-reviewer`エージェントによるレビューを必須化すべき。

- **法務要件との接続（特商法・本人確認義務）:** 引越し費用決済を伴うプラットフォームでは、犯収法・古物営業法相当の本人確認レベルが将来的に求められる可能性があり、現行の認証基盤（Supabase Auth等）が将来のeKYC連携（マイナンバーカード認証等）に拡張可能な設計かを今のうちに検証しておくべき。

### 6. database architecture Prisma Supabase 2026

- **エッジ最適化とPrisma Accelerate:** Prismaは2025年以降Accelerateによるコネクションプーリング＋グローバルキャッシュを標準化しており、Vercel Edge FunctionsやNext.js 16のServer ComponentsからSupabase Postgresへ低レイテンシでアクセスできる構成が主流になっている。sumitsugiのようなSSR中心のNext.jsアプリでは、DB接続数の枯渇を防ぐためAccelerate経由の接続を検討すべき。

- **RLS（Row Level Security）とORMの役割分担:** SupabaseのRLSでテナント/ユーザー単位のアクセス制御を担い、Prismaはスキーマ管理とクエリビルダーとして使う「認可はDB層、ロジックはORM層」という分離が2026年のベストプラクティス。前の住人/次の住人のような役割ベースのデータアクセスは、アプリ側のみでなくRLSポリシーでも二重に保護するのが安全。

- **PrismaのRust依存排除（v6以降のRustless Client）:** Prismaはクエリエンジンのバイナリ依存を段階的に廃止し、TypeScriptネイティブなクライアントに移行済み。これによりEdge/Serverless環境（Vercel等）でのコールドスタートが大幅に改善されているため、既存プロジェクトのPrismaバージョンが古い場合は移行検討価値が高い。

- **マイグレーション運用の自動化:** Supabase CLIとPrisma Migrateの併用時は「どちらが正とするか」を明確にする必要があり、多くのチームはPrisma Migrateを単一の真実源にし、Supabase側のマイグレーションは無効化する運用に統一している。物件ステータス（`draft`/`public`）のようなenum変更時は、両ツールの競合を避けるためこの一本化が特に重要。

- **pgvector＋Supabaseによる検索機能の内製化:** 物件検索やレコメンドにAI/ベクトル検索を組み込む場合、外部ベクトルDBを増やさずSupabase標準のpgvector拡張で対応するのが2026年のコスト効率的な選択。将当社の「引越し費用」見積もりや物件マッチング機能を拡張する際の技術選定候補になる。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Rustのwasm32-wasip2ターゲットとComponent Modelの標準化が進み、WASIプレビュー2ベースのモジュール間連携（ホスト関数呼び出しのオーバーヘッド削減）が実用レベルに到達している。マイクロサービス的なWasmコンポーネント設計を採用することで、デプロイ単位を細分化しつつ起動コストを抑えられる。

- **ポイント2:** WasmGCとexception-handling提案の標準化により、RustのpanicハンドリングやGCを持つ言語（Kotlin/Dart等）とのメモリ共有が現実的になり、フロントエンド側で重い画像処理・PDF生成ロジックをRust+Wasmに移管する際の相互運用コストが下がっている。sumitsugiのようなPDF生成・物件データ処理を含むプロダクトでは、サーバー負荷のオフロード先として検討価値がある。

- **ポイント3:** SIMD128とmulti-threading（SharedArrayBuffer経由）のブラウザ実装がほぼ全モダンブラウザで安定し、画像リサイズや大量データのソート・フィルタリング処理がJS実装比で2〜5倍高速化するケースが一般化している。ただしCross-Origin-Isolation（COOP/COEP）ヘッダー設定が必須になる点は、Next.jsのミドルウェア設定時に見落としやすい。

- **ポイント4:** cargo-componentやwasm-packのツールチェーン成熟により、TypeScript型定義の自動生成（wit-bindgen経由）がスムーズになり、Next.js App Router内でWasmモジュールをServer Componentsから呼び出す際の型安全性が担保しやすくなった。小規模な計算集約処理（例: 物件価格シミュレーション）をRustで書き、フロント/バックエンド両方で同一ロジックを共有する設計が現実的な選択肢になっている。

- **ポイント5:** バイナリサイズ最適化（wasm-opt、`opt-level = "z"`、LTO）とコールドスタート改善が進み、エッジランタイム（Cloudflare Workers等）でのWasm実行が本番運用に耐える水準になった。ただし導入前にビルドパイプラインの複雑化（Rustツールチェーン依存の追加）とチームのRust習熟コストを天秤にかける必要がある — 現状のNext.js/TypeScriptスタックへの追加は、明確なパフォーマンスボトルネックが特定された箇所に限定するのが妥当。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 15以降で安定した部分プリレンダリングにより、静的シェルを即座に返しつつ動的部分のみSuspenseでストリーミングできる。物件一覧ページのような「共通UIは静的・在庫情報だけ動的」な構成に最適で、TTFBを大幅に改善できる。

- **Server Actionsのセキュリティ強化が必須:** App Routerが主流化した分、Server Actionsへの不正呼び出し・CSRF類似攻撃への対策事例も増えている。`use server`関数は必ず認可チェックとZodによる入力検証をセットで行い、クライアントから直接叩かれても安全な設計にすべき。

- **`fetch`キャッシュ戦略の明示化がデフォルトに:** Next.js 15でキャッシュのデフォルトが「明示的オプトイン」に変わったため、`cache: 'force-cache'`や`revalidate`を意図的に指定しないと意図せず毎回動的取得になりコストが増える。物件データのような更新頻度が低いコンテンツはISR（`revalidate`秒数指定）で明示的に管理すべき。

- **Server ComponentsとClient Componentsの境界設計:** 「なるべくleafノードだけをClient Componentにする」パターンが定着し、認証状態や検索フィルタなどインタラクティブ性が必要な部分だけを`'use client'`で切り出すことでバンドルサイズを最小化できる。`src/contexts/auth-context.tsx`のようなグローバル状態は最小限の境界に留めるのが鉄則。

- **`instrumentation.ts`とEdge/Node runtime使い分けの成熟:** 監視・エラートラッキングの標準化に`instrumentation.ts`が使われるようになり、決済やAuthなどNode API依存の処理はNode runtime、軽量な地理情報判定などはEdge runtimeと明確に使い分ける設計が定着している。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1（コールドスタート最適化）:** V8 isolateベースのEdge RuntimeはNode.js Runtimeに比べて起動が数十ms単位で速いため、認証チェックやリダイレクト判定などレイテンシに敏感な処理はEdgeに寄せ、重いDB接続やORM処理はNode.js Runtimeに残すハイブリッド構成が2026年のベストプラクティスになっている。

- **ポイント2（Streaming + Partial Prerendering併用）:** Next.js 16のPPR（Partial Prerendering）とEdge Functionsを組み合わせることで、静的シェルを即座に返しつつ動的部分だけEdgeでストリーミング生成でき、TTFBを大幅に短縮できる。sumitsugiの物件一覧・詳細ページのような「一部パーソナライズ・大部分静的」なページ構成に特に効果が高い。

- **ポイント3（リージョン戦略）:** Edge Functionsはグローバル分散が前提だが、DB（Supabase/Postgres想定）のリージョンと物理的に離れるとレイテンシが逆に悪化するケースがあるため、`export const preferredRegion`で主要ユーザー層（日本）に近いリージョンを明示指定し、DBリージョンと揃えることが重要。

- **ポイント4（コスト最適化）:** Edge Functionsは実行時間課金モデルのため、無限ループやポーリング処理を書くとNode.js Functionsより高コストになりやすい。2026年時点ではVercelの`waitUntil()`を使った非同期後処理（ログ送信・キャッシュ更新など）をレスポンス返却後に回すパターンが定着しており、ユーザー体験とコストを両立できる。

- **ポイント5（Runtime制約の回避）:** Edge RuntimeはNode.js API（`fs`, 一部の暗号ライブラリ等）が使えない制約があるため、決済処理や法務まわり（特商法表記生成など）のように外部ライブラリ依存が強い機能はNode.js Runtimeに固定し、Edgeは「軽量・ステートレス・高頻度アクセス」なエンドポイントに限定する設計原則を徹底すべき。

### 10. TypeScript type safety patterns 2026

- **ポイント1（型推論の強化とconst型パラメータ）:** TypeScript 5.x以降の`const`型パラメータやsatisfies演算子の活用が定着し、明示的な型注釈を減らしつつ厳密な型推論を維持するパターンが主流に。過剰な型定義を避け、コンパイラの推論力を信頼する設計が生産性を高めます。

- **ポイント2（Zodなどのランタイムバリデーションとの統合）:** APIレスポンスやフォーム入力などシステム境界では、Zodスキーマから型を自動生成（`z.infer`）する手法が標準化。型安全性はコンパイル時だけでなく実行時にも担保する必要があり、sumitsugiのような不動産プラットフォームでは物件データのバリデーションに必須です。

- **ポイント3（Discriminated Unionによる状態管理）:** `status: 'draft' | 'public'`のような判別可能なユニオン型を使い、switch文の網羅性チェック（exhaustiveness check）でランタイムエラーを未然に防ぐパターンが標準化。新しい状態値を追加した際にコンパイルエラーで検知できるため、standards.mdにもある「型の整合性チェック」と直結します。

- **ポイント4（型レベルテストの導入）:** `tsd`や`expect-type`を用いた型のユニットテストが、複雑な型ユーティリティ（条件型・マップ型）を持つプロジェクトで一般化。ロジックのテストだけでなく型定義自体の回帰テストを行うことで、リファクタリング時の型崩れを防止します。

- **ポイント5（Biome/ESLintによる型安全リンティングの高速化）:** 型情報を利用したリンティング（`typescript-eslint`のtype-aware rules）とBiomeのような高速リンターの併用が進み、CIでの型チェック＋lintの実行時間短縮と厳密性の両立が可能に。ビルド速度が開発体験に直結するため、ci/cdパイプラインの最適化と併せて検討すべき領域です。
