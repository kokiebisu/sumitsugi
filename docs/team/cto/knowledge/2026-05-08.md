# CTO Knowledge - 2026-05-08

## Daily Update (2026-05-08)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを削減する最も効果的な手段。`'use client'`はインタラクティブな末端コンポーネントにのみ付与し、データフェッチはサーバー側で完結させる設計を基本とする。

- **PPR（Partial Prerendering）の本番投入:** 静的シェルと動的スロットを1リクエストで配信するPPRが安定化し、TTFBとLCPを同時に改善できる。`experimental.ppr: true`から移行し、Suspenseバウンダリの設計を見直す好機。

- **Turbopackへの移行完了:** Next.js 15以降、devサーバーはTurbopackがデフォルト。本番ビルドも対応済みで、大規模モノレポでのコールドスタートが従来比60-80%短縮される実績が出ている。

- **`next/image`とフォント最適化の再確認:** AVIFデフォルト対応・`sizes`属性の精緻化・`next/font`のpreloadキャッシュ戦略は依然としてCore Web Vitals改善の低コスト最優先施策。測定せずに飛ばしがちな箇所。

- **Observabilityの組み込み（`instrumentation.ts`）:** Next.js 15のInstrumentation APIが安定化し、OpenTelemetryとの統合が容易になった。パフォーマンス問題はコードレビューより本番トレースで発見されるため、早期にセットアップすることを強く推奨する。

### 2. React Server Components streaming 2026

- **Suspense境界の細粒度化が標準化:** RSCとStreamingを組み合わせる際、コンポーネント単位でSuspense境界を細かく設定することがベストプラクティスとして定着し、TTFBを下げつつUIの段階的ハイドレーションを実現できる。

- **PPR（Partial Prerendering）の本格採用:** Next.js 15以降でPPRが安定版となり、静的シェルを即座に返しながら動的スロットをストリーミングで埋める手法が実用段階に入った。静的・動的コンテンツの混在ページで大幅なLCP改善が見込める。

- **Server Actionsとの統合によるウォーターフォール排除:** データフェッチをサーバーコンポーネント内でawaitするパターンが浸透し、クライアント→サーバー→DBのウォーターフォールを構造的に排除できるようになった。ただしコンポーネント設計でのデータ依存関係の整理が前提。

- **Edge RuntimeとStreaming Cacheの相性問題:** CloudflareやVercel EdgeでRSCをストリーミングする際、Response Cacheとのコンフリクトが依然として課題。`export const runtime = 'edge'` を使う場合はキャッシュ戦略を慎重に設計する必要がある。

- **DevToolsの成熟と可観測性向上:** 2026年時点でReact DevToolsがStreaming RSCのタイムラインを可視化できるようになり、どのSuspense境界でブロックが発生しているかをプロファイリングしやすくなった。パフォーマンスチューニングのサイクルが大幅に短縮される。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの実用的優位性:** フルスタックTypeScriptプロジェクトではtRPCがデファクトスタンダードに近づいており、スキーマ定義不要でエンドツーエンドの型安全性を実現できる点が、Next.js/Remixとの相性で特に評価されている。

- **REST vs GraphQLの収束:** GraphQLの複雑性コストへの反省から、REST + OpenAPI 3.1の組み合わせが再評価されており、特にチーム規模が小さい場合はシンプルなRESTで十分なケースが多い。

- **Server-Sent Events / WebSocketの組み込み:** リアルタイム要件に対し、tRPC subscriptionsやGraphQL subscriptionsよりも、HTTP/2 SSEを直接活用するシンプルなアプローチが増加中。オーバーエンジニアリング回避の観点から重要。

- **API Gateway + BFFパターンの定着:** マイクロサービス環境では、クライアント向けにBFF（Backend for Frontend）を置きRESTで集約するパターンが安定した選択肢となっており、GraphQL Federationより運用コストが低い。

- **型安全APIの標準化:** Zodによるランタイムバリデーションと静的型推論の組み合わせが、REST/tRPC問わず必須の設計パターンとなっており、`zod-openapi`等でスキーマとバリデーションを一元管理するアプローチが主流になっている。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がEdgeのデファクトランタイムに:** V8 Isolatesに加えWasmが主流となり、任意の言語（Rust・Go・Python）をコールドスタートなしでEdgeにデプロイ可能になった。Cloudflare Workers・Fastly Compute・Deno Deployが競争を牽引している。

- **Edge-native DBとデータローカリティの融合:** Cloudflare D1・Turso（libSQL）・Neon Branchingなど、Edgeから直接クエリできる分散SQLが実用レベルに達した。レイテンシ最適化のため「コンピュートをデータに近づける」設計が標準になりつつある。

- **AIインファレンスのEdgeシフト加速:** 小型LLM（Llama 3.2・Phi-3-mini相当）をEdgeノードで実行するニーズが急増。プライバシー規制対応とレイテンシ削減の両立が主な動機で、Next.jsのAI SDKもEdge Runtimeを前提とした設計になってきている。

- **Observabilityの複雑性がボトルネックに:** 分散Edgeノード（100+PoP）での分散トレーシングは依然課題。OpenTelemetryのEdge対応が進んでいるが、サンプリング戦略とコスト管理のバランス設計が実運用の肝になる。

- **コールドスタート問題の「解決」と新たなトレードオフ:** Isolatesアーキテクチャによりコールドスタートはほぼ解消されたが、メモリ上限（128MB〜256MB）とCPU時間制約が新たな設計制約に。ステートフルな処理はDurable Objects・Actor Modelパターンへの移行が現実解。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の標準化:** パスワードレス認証がデファクトスタンダードになりつつあり、フィッシング耐性のあるパスキーを優先採用すべき。Apple・Google・Microsoftのエコシステム統合により実装コストも大幅に低下している。

- **セッショントークンの短命化とリフレッシュ戦略:** アクセストークンの有効期限を5〜15分に短縮し、ローテーティングリフレッシュトークンと組み合わせることがベストプラクティス。トークン漏洩時の被害範囲を最小化できる。

- **デバイスフィンガープリントと継続的認証:** ログイン時の一点認証から、セッション中の行動パターン・デバイス状態を継続的に評価するモデルへの移行が加速。異常検知時に再認証を要求する仕組みが重要。

- **サプライチェーン攻撃対策としての依存関係管理:** 認証ライブラリ（NextAuth、Auth.jsなど）の脆弱性が攻撃ベクターになるケースが増加。`bun audit` や Renovate による自動アップデートを必須プロセスに組み込むべき。

- **ゼロトラスト前提のAPI認証:** mTLS・DPoP（Demonstration of Proof-of-Possession）トークンの採用により、トークン盗用に対するリプレイ攻撃を防止。サービス間通信でも「信頼しない、常に検証する」原則を徹底することが2026年の標準水準。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x のEdge Runtime対応成熟:** Prisma ClientがVercel Edge・Cloudflare Workersで安定稼働し、Supabase接続プール（PgBouncer / Supabase Pooler）との組み合わせでサーバーレス環境のコールドスタート問題が実用レベルに解消された。

- **Supabase Realtime v3 の本番投入:** マルチテナント対応とチャンネル認可がRLS（Row Level Security）と統合され、リアルタイム機能をアプリ層で再実装するコストが大幅に低下している。

- **pgvector × Supabase Vector のRAG統合が標準化:** PostgreSQL上でベクトル検索とリレーショナルデータを同一DBで扱う構成が主流となり、外部ベクトルDBを別途運用するアーキテクチャは過剰設計になりつつある。

- **Prisma Migrate + Shadow Databaseの本番課題:** Supabase hosted環境ではshadow DBが使えないため `prisma migrate diff` ＋ 手動SQL適用が現実解。CI/CDパイプラインでの自動マイグレーションは慎重な設計が必要。

- **RLS をORMレイヤで補完する設計が浸透:** Prismaミドルウェア（またはExtensions）でテナントIDをセッション変数に注入し、SupabaseのRLSと二重防御する「Defense in Depth」パターンがマルチテナントSaaSの標準構成になっている。

### 7. WebAssembly Rust performance 2026

- **WASI Preview 2 の本格普及:** Component Model の標準化により、RustコンパイルのWasmモジュールが言語間で再利用可能になり、マイクロサービス間のFFIコストをほぼゼロに近づけられる。

- **SIMD・スレッド拡張の安定化:** WebAssembly SIMD と Shared Memory/Atomics が主要ランタイム（V8, Wasmtime, WasmEdge）で安定稼働し、Rustの`packed_simd`や`rayon`との組み合わせでネイティブ比90%以上のスループットを達成するユースケースが増加。

- **Wasmtime + Cranelift vs LLVM のコンパイル戦略:** 起動レイテンシが重要なサーバーレス環境では Cranelift の高速JITが優位だが、長時間稼働するエッジコンピューティングではLLVMバックエンドのAOTコンパイルがピーク性能で逆転。ユースケースに応じた使い分けが設計上の鍵。

- **GCプロポーザルとRustのゼロコスト抽象:** Wasm GC拡張はGC言語向けだが、Rustはそもそも所有権モデルでGC不要のため影響は軽微。ただしRust製Wasmと他言語モジュールを同一コンポーネントに混在させる際のメモリモデル設計に注意が必要。

- **ツールチェーンの成熟（`wasm-bindgen` / `cargo-component`）:** `cargo-component` CLIがComponent Model対応のビルドを簡略化し、CI/CDパイプラインへの組み込みが現実的に。ただしバイナリサイズ最適化（`wasm-opt` + LTOの組み合わせ）は依然として手動チューニングが必要な部分が残る。

### 8. Next.js App Router patterns 2026

- **Server Componentsをデフォルトに:** 2026年時点でApp RouterのServer Componentsは成熟しており、データフェッチはコンポーネント内で直接行うのが主流。`use client`は状態・イベントハンドラが必要な最小単位にのみ付与する設計が最適。

- **Partial Prerendering (PPR) の実用化:** 静的シェル＋動的ストリーミングを1ページで混在させるPPRが安定化し、LCPとTTFBの両立が現実的に。`<Suspense>`境界の設計がパフォーマンスの鍵。

- **Server Actionsによるフォーム処理の標準化:** API Routeを経由せずServer Actionsで直接ミューテーションを実装するパターンが定着。`useActionState`との組み合わせでローディング・エラー状態管理がシンプルになる。

- **Parallel Routes & Intercepting Routesの活用:** モーダルやスライドオーバーをURLと連動させる実装にIntercepting Routesが有効。ただし複雑化しやすいため、シンプルなユースケースに限定する判断力が重要。

- **キャッシュ戦略の明示化:** Next.js 15以降、デフォルトキャッシュ動作が変更され、`fetch`のキャッシュは明示的に指定する設計に移行。`revalidatePath`/`revalidateTag`を使ったオンデマンド再検証をデータ更新フローに組み込むことがベストプラクティス。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge Runtimeの制約を前提にした設計が必須** Node.js APIの一部（`fs`、`net`等）はEdge Runtimeで利用不可。2026時点ではWeb標準API（`fetch`、`Request`/`Response`、`crypto`）への移行が完了していることが前提で、依存ライブラリの互換性確認が初期設計で必要。

- **ポイント2: Cold Start排除よりもStreaming Responseの活用が主戦場** Edge FunctionsはCold Startが既にほぼゼロだが、LLMレスポンスやデータ集約処理では`ReadableStream`を使ったStreaming対応がUX・TTFB両面でのKPIになっている。

- **ポイント3: ISR（Incremental Static Regeneration）とEdgeの組み合わせが最適解** 純粋な動的処理はEdgeで、キャッシュ可能なコンテンツはISR＋Edge Cachingで捌く二層構造が、コスト・レイテンシのバランスとして定番化している。

- **ポイント4: Middleware層でのA/Bテスト・認証オフロードが標準パターン** Edge Middlewareでgeolocation・認証チェック・フィーチャーフラグを処理し、オリジンへのリクエストを最小化する設計がNext.js 15以降のベストプラクティス。Vercel KVやEdge Configとの組み合わせで低レイテンシを維持。

- **ポイント5: バンドルサイズ1MB制限への継続的な注意が必要** Edge Functionsのバンドルサイズ上限はパフォーマンスに直結する。重量級ライブラリ（例: `date-fns`全体、大型ORMクライアント）のtree-shakingやlazy import設計を怠ると、制限超過かレイテンシ悪化のどちらかが発生する。

### 10. TypeScript type safety patterns 2026

- **Branded Types の普及:** `type UserId = string & { readonly _brand: 'UserId' }` のようなBranded Typesが実務標準化し、プリミティブ型の誤用をコンパイル時に防ぐパターンが定着している。

- **satisfies 演算子の活用:** TypeScript 4.9以降の `satisfies` が広く浸透し、型推論の恩恵を保ちながら型制約を適用できるため、`as` キャストへの依存が大幅に減少している。

- **Template Literal Types によるAPI契約:** `type Route = \`/api/${string}\`` のようなTemplate Literal Typesでエンドポイント定義を型化し、ランタイムエラーをゼロに近づける設計が主流になっている。

- **Zod + tRPC による型の一気通貫:** スキーマ定義からフロント・バック両端の型を自動導出するアーキテクチャが事実上の標準となり、手動型定義の重複がほぼ不要になっている。

- **const type parameters の精緻化:** TypeScript 5.x の `const` 型パラメータにより、リテラル型の推論精度が向上し、汎用ユーティリティ関数でも型情報の損失が最小化されている。
