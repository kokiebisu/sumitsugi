# CTO Knowledge - 2026-09-27

## Daily Update (2026-09-27)

### 1. Next.js performance optimization 2026

- **React Compilerの標準採用:** Next.js 16ではReact Compilerがデフォルトで有効化され、`useMemo`/`useCallback`の手動最適化がほぼ不要に。既存コードのメモ化コードを削減し、レンダリング効率をコンパイラに委ねるのが2026年のベストプラクティス。

- **Partial Prerendering (PPR) の本番運用定着:** 静的シェルを即座に配信しつつ動的部分をストリーミングする手法が安定版として広く採用され、TTFBとLCPの両立が可能に。物件一覧ページのような「一部は静的（レイアウト）・一部は動的（在庫状況）」な画面に特に有効。

- **Turbopackへの完全移行:** ビルド・開発サーバーのデフォルトバンドラーがTurbopackに移行し、大規模リポジトリでのHMR速度とコールドビルド時間が大幅短縮。うちの規模だと `bun run build` の時間短縮効果を継続的に計測する価値あり。

- **Server Actionsのキャッシュ戦略成熟:** `use cache` ディレクティブとタグベース再検証が実用段階に入り、DB叩き過ぎによるレイテンシ問題を宣言的に解消しやすくなった。前の住人/次の住人データ取得のような読み取り頻度の高いパスから適用するのが投資対効果が高い。

- **画像・フォント最適化のエッジ処理シフト:** `next/image` の最適化処理がエッジランタイムでより効率化され、CDN層でのオンザフライ変換コストが低減。物件写真中心のUIではCore Web Vitals改善に直結する領域。

### 2. React Server Components streaming 2026

- **ポイント1（Partial Prerenderingの本格普及）:** Next.js 16ではPPRが標準機能として定着し、静的シェルを即座に返しつつ動的部分だけをストリーミングする構成が主流に。物件一覧ページのように「上部は静的、価格や空き状況だけ動的」というケースでTTFBを大幅短縮できる。

- **ポイント2（Suspenseバウンダリの粒度設計が差別化要因に）:** 単にページ単位でSuspenseを切るのではなく、コンポーネント単位で細かく境界を設定することで体感速度が変わる。sumitsugiでも物件詳細ページの画像・レビュー・周辺情報を個別にストリーミングすれば、重い外部APIコールがあってもファーストビューをブロックしない。

- **ポイント3（React Compilerとの相乗効果）:** React Compilerの安定化により`useMemo`/`useCallback`の手動最適化が不要になり、RSCとクライアントコンポーネントの境界がよりシンプルに書けるようになった。境界を減らせる分、バンドルサイズとハイドレーションコストが下がる。

- **ポイント4（Server Actionsのストリーミング対応）:** フォーム送信後の結果を逐次返す「progressive Server Actions」パターンが広がっている。引越し費用の見積もり計算など、複数ステップの処理をクライアントJSなしで段階的に表示できるようになった。

- **ポイント5（エッジ環境でのストリーミング配信）:** VercelやCloudflare等のエッジランタイムでRSCストリームを配信するケースが増え、地方ユーザーへのレイテンシが改善している。ただしNode.js専用ライブラリ依存があるとエッジ非対応になるため、依存選定時に要注意。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはフルスタックTypeScriptモノレポ（Next.js × Bunのような構成）において、コード生成なしでエンドツーエンド型安全性を実現できるため、社内API・BFF層でのデフォルト選択になりつつある。GraphQLのようなスキーマ層を挟まない分、開発速度とデバッグ体験が優れる。

- **ポイント2:** GraphQLは依然として複雑な集約・多クライアント（Web/モバイル/パートナーAPI）向けの「公開API」領域で強いが、N+1問題やキャッシュ制御の複雑さから、単一フロントエンドのプロダクトではオーバーエンジニアリングになりやすい。

- **ポイント3:** RESTはWebhook・決済連携・外部SaaS統合（Stripeなど）のような「疎結合な外部インターフェース」では今も標準であり、OpenAPI（Swagger）+ Zodでスキーマとランタイム検証を一致させる設計が定番化している。

- **ポイント4:** 2026年時点のトレンドとして、単一技術に統一するのではなく「内部通信はtRPC、公開/パートナー向けはREST（OpenAPI）、複雑な集約が必要な画面のみGraphQL的なBFFレイヤー」というハイブリッド設計が主流になっている。sumitsugiのような小〜中規模プロダクトでは、内部はtRPCまたはNext.js Server Actions、外部連携はREST一本化がシンプルで保守コストが低い。

- **ポイント5:** APIの型安全性はZodなどのランタイムスキーマとTypeScriptの静的型を両立させる方向が定着しており、`.claude/rules/standards.md`にあるZod境界検証の方針は、tRPC/REST問わずAPI設計のベストプラクティスとして継続的に有効。

### 4. serverless edge computing 2026

**ポイント1:** WinterCG(Web-interoperable Runtimes Community Group)による標準化が進み、Cloudflare Workers・Deno Deploy・Vercel Edge Functions間でFetch API/Web Standardsベースの実装が共通化。ベンダーロックインを避けるなら、Node.js固有APIではなくWeb標準APIに寄せて書くのが実用的。

**ポイント2:** Isolateベースのコールドスタート(数ms〜十数ms)が主流化し、コンテナベースのサーバーレス(Lambda等)との性能差が顕著に。ただしメモリ制限(128MB前後)とCPU時間制限があるため、重い処理は依然としてリージョナルなバックエンドに逃がす設計が必要。

**ポイント3:** エッジでのデータレイヤー(Cloudflare D1, Turso, PlanetScale)が成熟し、読み取りはエッジレプリカ、書き込みはプライマリへルーティングするパターンが定着。sumitsugiのような不動産情報のように「読み取り主体・低頻度更新」なデータ(物件詳細ページなど)はエッジキャッシュ+ISRとの相性が良い。

**ポイント4:** 軽量LLM推論(量子化モデル)をエッジで動かす事例が増加。ただし現状は分類・埋め込み生成など軽量タスクが中心で、対話生成のような重いLLM呼び出しは引き続き中央集権的なAPI(Anthropic等)に委ねるハイブリッド構成が現実的。

**ポイント5:** Next.js 16のPPR(Partial Prerendering)とエッジミドルウェアの組み合わせで、認証チェックなどをオリジンに到達する前にエッジで完結させる設計が一般化。sumitsugiの`auth-context`のようなクライアント側認証と併用する場合、エッジでのセッション検証とのロジック重複に注意が必要。

### 5. authentication security best practices 2026

- **ポイント1（パスキー/FIDO2の標準化):** パスワードレス認証（Passkeys）がブラウザ・OS標準でサポートされ、フィッシング耐性のある認証がデフォルト選択肢になっている。実装コストが下がったため、新規サービスはパスワード認証を主軸にしない設計が推奨される。

- **ポイント2（セッション管理とトークン漏洩対策):** JWTなどのステートレストークンは失効管理が難しいため、短命アクセストークン＋リフレッシュトークンローテーション、またはサーバーサイドセッション＋Redis等の組み合わせが主流。トークン漏洩時の被害範囲を最小化する設計が重要。

- **ポイント3（デバイスバインディングとリスクベース認証):** IPアドレスやデバイスフィンガープリントを用いた異常ログイン検知が標準化しつつあり、リスクスコアに応じて追加認証（MFA）を動的に要求する仕組みが求められる。

- **ポイント4（サプライチェーン/依存関係の脆弱性管理):** 認証ライブラリ自体の脆弱性（NextAuth、Supabase Auth等）が攻撃対象になるため、定期的な依存関係監査と自動アップデート（Dependabot等）の運用が必須。

- **ポイント5（個人情報・認証情報のログ出力禁止):** エラーメッセージやログにパスワード・トークン・セッションIDを含めない実装を徹底し、CSRF/XSS対策と合わせて認証まわりのコードレビューを必須プロセスにすることが、引き継ぎプラットフォームのような信頼性が重要なサービスでは特に重要。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Prisma ORMのEdge対応が進み、Supabase側のPgBouncer（トランザクションモード）との接続プーリング設定が引き続き重要。サーバーレス環境ではPrisma Accelerateなどのマネージドプール層を使うことで、コネクション枯渇を防ぎつつレイテンシも改善できる。

- **ポイント2:** SupabaseのRow Level Security (RLS) とPrismaのスキーマ管理を組み合わせる際は、Prisma側からRLSポリシーを直接管理できないため、マイグレーションSQLに手動でRLS定義を追記する運用が定着している。前の住人・次の住人のようなロール別アクセス制御を行う場合、RLSポリシー漏れがないかCIでチェックする仕組みを入れると安全。

- **ポイント3:** Supabaseのリアルタイム機能（Realtime）とPrismaのスキーマ変更を併用する場合、マイグレーション時にpublicationの再設定が必要になることが多く、`bun run build`前のマイグレーション適用手順に組み込んでおくと事故が減る。

- **ポイント4:** 型安全性の観点では、Prisma Clientの生成型とSupabase CLIが生成する`database.types.ts`が二重管理になりがちなので、どちらか一方（Prismaスキーマ）を単一の真実源として、Supabase型は生成をスキップするかCIで整合性チェックするのが実用的。

- **ポイント5:** 物件ステータス（`draft`/`public`）のようなenum的なUnion型はPrismaのenum機能で定義し、Supabase側のCHECK制約と二重に持たせることで、アプリ層とDB層の両方でデータ整合性を担保できる。ユニオン型の値を追加する際は必ずマイグレーション・Zodスキーマ・UI表示の3箇所を横断的にgrepして更新すること。

### 7. WebAssembly Rust performance 2026

- **WASI 0.3 + Component Modelの成熟:** 2026年にはWASI Preview 2以降のコンポーネントモデルが本番運用レベルで安定し、Rustの`wit-bindgen`によるモジュール間の型安全な連携が実用的になっています。マイクロサービス的にWasmモジュールを組み合わせる設計が現実的な選択肢になりつつあります。

- **SIMD128とマルチスレッド対応の一般化:** ブラウザ・サーバーサイド双方でWasm SIMDとスレッド（`wasm-bindgen-rayon`等）がデフォルト有効になり、画像処理・PDF生成のような計算負荷の高い処理をRust+Wasmに移すメリットが大きくなっています。当社のPDF生成やインテリア画像処理で検討価値あり。

- **バイナリサイズ最適化の自動化:** `wasm-opt`や`twiggy`によるツリーシェイキングがCargoワークフローに統合され、以前は数百KBだったバンドルが数十KB台まで縮小可能。Next.jsのApp Routerでのコード分割と組み合わせれば、初回ロードへの影響を最小化できます。

- **サーバーサイドWasm（Wasmtime/Wasmer）でのコールドスタート改善:** AOTコンパイルとインスタンスプーリングにより、コールドスタートがミリ秒単位に短縮。Vercel Edge FunctionsやCloudflare Workers環境でRust製ロジック（料金計算、マッチングアルゴリズムなど）を動かす選択肢が現実的になっています。

- **Rust以外言語との相互運用コスト低下:** Component Model経由でTypeScript/Rust間のFFIオーバーヘッドが下がり、既存のNext.js/TypeScriptコードベースの一部だけをRustに置き換える「部分移行」がしやすくなっています。全面移行ではなく、ボトルネック箇所のみWasm化するアプローチが投資対効果的です。

### 8. Next.js App Router patterns 2026

- **ポイント1（Server Actionsの本格定着）:** App RouterではServer Actionsが標準パターンとして定着し、フォーム送信やミューテーションをAPIルート経由ではなく直接Server Component/Client Componentから呼び出す設計が主流化。sumitsugiのような物件登録・問い合わせフォームでは、`use server`によるバリデーション＋DB更新の一体化でAPIレイヤーのボイラープレートを大幅削減できる。

- **ポイント2（部分的プリレンダリング/PPR）:** Partial Prerenderingが安定版として普及し、静的なページシェル（ヘッダー・ナビ）を即座に返しつつ、動的部分（ログイン状態・在庫状況）をストリーミングで後から埋める構成が標準に。物件一覧ページのように「検索結果は動的だがレイアウトは静的」なケースでTTFB改善に直結する。

- **ポイント3（キャッシュ戦略の明示化）:** Next.js 15以降でfetchのデフォルトキャッシュ挙動が変わり、`'use cache'`ディレクティブやキャッシュタグ（`revalidateTag`）による明示的な制御が推奨パターンに。物件ステータス（draft/public）の更新時に古いキャッシュが残るバグを防ぐには、更新系Server Actionで確実に関連タグをrevalidateする設計が必須。

- **ポイント4（Route Groupsとレイヤー分離の徹底）:** `(marketing)`, `(dashboard)`のようなRoute Groupsで公開ページと認証必須ページのレイアウト・ミドルウェアを明確に分離するパターンが定着。認証チェックをmiddlewareに寄せすぎず、各Route Groupの`layout.tsx`でセッション検証を行う「多層防御」が2026年のベストプラクティス。

- **ポイント5（Server/Client境界の最小化）:** "use client"境界をできるだけ末端のインタラクティブ部品（ボタン、フォーム入力）に限定し、データ取得ロジックはServer Componentに集約する設計原則がより厳格に運用されるように。バンドルサイズ削減とSEO両立のため、認証状態のようなグローバルなクライアント状態も必要最小限のコンテキストに絞る設計が求められる。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの軽量化:** Vercel Edge FunctionsはV8 isolateベースで動作するため、依存パッケージを最小限に抑え、Node.js固有APIへの依存を避けることでコールドスタートを大幅に削減できる。

- **Streaming SSRとの組み合わせ:** Edge Functionsをストリーミングレスポンスと組み合わせることで、TTFB（Time to First Byte）を最適化し、ユーザーの体感速度を向上させる設計が主流になっている。

- **リージョナル実行の最適化:** `regions`設定でデータベースやAPIに近いエッジロケーションを明示的に指定することで、ネットワークレイテンシを削減できる（特にDB接続を伴う処理はEdgeではなくNode.js Functionsに寄せる判断も重要）。

- **キャッシュ戦略との統合:** ISR/on-demand revalidationとEdge Middlewareを組み合わせ、パーソナライズと静的配信の両立を図るパターンが増えている。動的処理は最小限にし、キャッシュ可能な部分は積極的にCDN層に委譲すべき。

- **観測性とコスト管理:** Edge実行はリクエスト数課金モデルのため、不要な処理（画像最適化やヘビーな計算）をEdgeで行わず、実行時間とメモリ使用量をモニタリングしてコストを可視化することが重要。

### 10. TypeScript type safety patterns 2026

**ポイント1:** TypeScript 5.x以降の`satisfies`演算子とconst型パラメータ（`const T`）が定着し、リテラル型を保持したまま型推論の恩恵を受けられるようになった。過度な型アサーション（`as`）を減らし、コンパイル時の安全性を維持しつつ実装の柔軟性を高めるベストプラクティスとして広く採用されている。

**ポイント2:** Zodなどのランタイムスキーマ検証と型定義を一元化する「Schema-first」アプローチが標準化しつつある。当プロジェクトでも`standards.md`にある「システム境界でのZodバリデーション」方針と一致し、APIレスポンスやフォーム入力の型不整合をビルド時ではなく実行時にも検出できる点が実務上重要。

**ポイント3:** テンプレートリテラル型とブランド型（Branded Types）を組み合わせ、IDやステータス文字列の誤代入をコンパイル時に防ぐパターンが浸透。例えば`'draft' | 'public'`のようなUnion型に対し、単純な文字列比較のtypoをコンパイラが検出できるようになり、`grep`による手動確認への依存を減らせる。

**ポイント4:** モノレポ構成でのプロジェクト参照（`tsconfig.json`の`references`）とインクリメンタルビルドがデフォルト化し、大規模コードベースでも型チェックの高速化が進んでいる。Next.js App Routerのような大規模なファイル分割構成でもビルド時間への影響を抑えられる。

**ポイント5:** AIコード生成（Claude Codeなど）が広がる中、「型がAIへの実行可能な仕様書」として機能する動きが加速している。厳密な型定義とnarrow union型を維持することで、AIエージェントが生成するコードの正確性をコンパイラが即座に検証でき、レビュー負荷を下げる効果がある。
