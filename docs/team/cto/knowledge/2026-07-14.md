# CTO Knowledge - 2026-07-14

## Daily Update (2026-07-14)

### 1. Next.js performance optimization 2026

- **Turbopackの本番ビルド標準化:** Next.js 16ではTurbopackが安定版としてデフォルトビルドツールになり、大規模プロジェクトでもビルド時間が大幅短縮。既存Webpack設定からの移行時は`next.config`のカスタムローダー互換性を事前検証すべき。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的コンテンツを1リクエスト内で組み合わせられるPPRが安定運用フェーズに入り、物件一覧のようなSSG+パーソナライズ混在ページでTTFBを大きく改善できる。sumitsugiの`properties/`一覧ページは適用候補。

- **キャッシュ戦略の明示化 (`use cache` ディレクティブ):** 従来の暗黙的キャッシュから、関数/コンポーネント単位で`use cache`を明示指定する方式に移行が進んでおり、キャッシュの意図しない無効化バグを防ぎやすくなった。データ取得層（`src/lib/data.ts`）の見直しに活用できる。

- **React Compilerによる自動メモ化:** `useMemo`/`useCallback`の手動最適化が不要になりつつあり、コードの可読性を落とさずレンダリング最適化が可能。ただし既存コンポーネントの移行時はESLintプラグインでの検証が必須。

- **画像・フォント最適化のエッジ処理:** `next/image`のエッジ変換とCDN連携がデフォルト化し、物件写真中心のUIでLCP改善に直結。ダークモード切替のようなクライアント状態を含むページでもStreaming SSRとの組み合わせで体感速度を保てる。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** React Server Componentsのストリーミングは`loading.tsx`と`Suspense`境界の組み合わせがデファクトスタンダードとなり、TTFB（Time To First Byte）を維持しつつコンポーネント単位で段階的にHTMLを配信できる点が、物件一覧や検索結果ページのような重いデータ取得箇所で特に有効です。

- **Partial Prerendering (PPR) の実用化:** Next.js 16ではPPRが安定版として利用可能になり、静的シェル（ヘッダー・ナビゲーション等）を即座に配信しつつ、動的部分（在庫状況・価格など）だけをストリーミングで後追いする構成が主流に。sumitsugiの物件詳細ページのような「静的な物件情報＋動的な空き状況」の構成に相性が良いです。

- **キャッシュ戦略との統合:** `use cache`ディレクティブとストリーミングを組み合わせることで、データ取得層のキャッシュ粒度をコンポーネント単位で制御できるようになり、過度なre-fetchを避けつつストリーミングの恩恵を受けられます。ただしキャッシュキー設計を誤るとステールデータの露出リスクがあるため、ユーザー固有データ（認証状態など）は明示的にキャッシュ対象外にする必要があります。

- **エラーバウンダリとストリーミングの相互作用:** ストリーミング中に発生したサーバーエラーは、すでに送信済みのHTMLチャンクに対して後付けで`error.tsx`をパッチする形になるため、CLS（レイアウトシフト）やUX劣化を防ぐには各Suspense境界に適切なフォールバックUIとスケルトンを設計しておくことが重要です。

- **開発体験とデバッグの複雑化:** ストリーミングSSRはネットワークタブ上でチャンク単位の配信順序が把握しにくく、パフォーマンス計測（Core Web Vitals）がクライアント側だけでなくサーバー側のチャンク生成タイミングにも依存するため、可観測性ツール（トレーシング）の導入がこれまで以上に重要になっています。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1（tRPCの採用拡大）:** TypeScriptフルスタック構成（Next.js等）では、型安全性とスキーマ定義の二重管理を避けられるtRPCの採用が増加。sumitsugiのようなNext.js App Router構成では、APIルートとクライアント間の型共有コストを削減できるメリットが大きい。
- **ポイント2（GraphQLは複雑なクエリ要件に限定的採用）:** GraphQLは柔軟なクエリが必要な大規模・マルチクライアント環境（モバイル/Web/パートナーAPI混在）では依然強いが、N+1問題やキャッシュ戦略の複雑さから、単一フロントエンド構成のプロダクトでは過剰設計になりやすい。
- **ポイント3（RESTは依然主流、OpenAPI+Zodの組み合わせが定番化）:** 外部連携・Webhook・サードパーティ統合ではRESTが依然標準。Zodスキーマからの型生成とOpenAPI自動生成を組み合わせる構成が、バリデーションとドキュメントの一元化として定着しつつある。
- **ポイント4（Server ActionsによるAPI層の簡略化）:** Next.js App RouterのServer Actionsが、CRUD中心の内部処理においてtRPC/RESTすら不要にするケースが増加。ただし外部公開APIや複数クライアント対応が必要な場合は、依然として明示的なAPI層（REST/tRPC）の分離が推奨される。
- **ポイント5（エッジ・ストリーミング対応の重要性）:** リアルタイム性（在庫状況、チャット、通知など）が求められる機能では、tRPCのsubscriptionやServer-Sent Eventsなど、エッジランタイムと親和性の高い設計が2026年時点で標準的な選択肢になっている。

**sumitsugiへの示唆:** 現状の物件データ・ユーザー認証はServer Actions + 内部Zodバリデーションで十分だが、将来的に外部連携（不動産ポータル連携、決済代行等）が発生する場合はREST/OpenAPI層の追加を検討すべき。tRPC全面移行は現行スタックでは過剰投資になる可能性が高い。

### 4. serverless edge computing 2026

- **エッジでのAI推論が標準化:** 2026年時点で、Cloudflare Workers AIやVercel Edge Functions等がLLM推論を含む軽量AIワークロードをエッジで直接実行できるようになり、レイテンシとコストの両面でオリジンサーバーへの往復が不要になっています。sumitsugiのような不動産マッチングでも、画像解析やレコメンド処理を地理的に近いエッジで行う選択肢が現実的になってきています。

- **コールドスタート問題の実質的解消:** V8 isolateベースのランタイム（Cloudflare Workers、Deno Deploy等）の進化により、コールドスタートがミリ秒単位まで縮小し、サーバーレスでも常時起動サーバーに近い応答性が得られるようになりました。Next.js 16のEdge Runtimeも成熟しており、`middleware.ts`や一部APIルートをエッジに配置する判断がしやすくなっています。

- **データレイヤーの分散化（Edge-native DB）:** Turso、PlanetScale、Cloudflare D1のようなエッジ対応データベースが普及し、読み取りをユーザーに近いリージョンで処理できるようになっています。ただし書き込み整合性のトレードオフは依然として設計上の重要な検討事項で、物件情報の即時性が求められるsumitsugiでは書き込み経路の設計に注意が必要です。

- **開発体験とベンダーロックインのバランス:** WinterCG（Web-interoperable Runtimes）標準化により、エッジランタイム間の互換性が向上し、特定ベンダーへの依存リスクが以前より低下しています。とはいえKVストアや永続化層はまだプロバイダ固有の実装が多く、移行コストを見据えたアブストラクション設計が引き続き重要です。

- **コスト構造の見直し:** リクエスト課金モデルが成熟し、トラフィックが不安定なMVP〜ローンチ初期フェーズのプロダクト（今のsumitsugiのフェーズ）には、常時稼働サーバーより明確にコスト優位性があります。ただし高頻度アクセスが安定してくるフェーズでは、専用インスタンスとのコスト比較を定期的に見直す必要があります。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証（WebAuthn/Passkeys）がフィッシング耐性の高い認証手段として主流化しており、2026年時点で主要ブラウザ・OSが標準サポート済み。実装コストも下がっているため、新規プロダクトはパスワードをフォールバックに留め、パスキーをデフォルトにすべき。

- **多層防御としての継続的リスク評価:** ログイン時の一発認証ではなく、デバイスフィンガープリント・行動パターン・IPレピュテーションを組み合わせたリスクベース認証（Adaptive MFA）が標準化。異常時のみ追加認証を要求することでUXとセキュリティを両立できる。

- **トークン管理の厳格化:** JWTなどのアクセストークンは短命化（5〜15分）し、リフレッシュトークンはローテーション必須かつhttpOnly/Secure/SameSiteでの保管を徹底。長寿命トークンの漏洩リスクが2025年以降の主要インシデント原因になっている。

- **セッション管理とゼロトラスト:** 認証後も「信頼し続けない」設計が重要で、重要操作（決済・個人情報変更）には再認証（step-up authentication）を要求する設計が推奨される。sumitsugiのような引き継ぎプラットフォームでは物件情報変更・決済フローに適用すべき。

- **サプライチェーン・依存パッケージの認証周りの脆弱性監視:** next-auth等の認証ライブラリは頻繁にCVEが出るため、Dependabot/Renovateでの自動更新とセキュリティレビュー（`/security-review`スキル）を認証関連PRには必ず通す運用が必須。

### 6. database architecture Prisma Supabase 2026

- **エッジ最適化の必須化:** Supabaseのグローバルエッジ機能とPrisma Accelerateのコネクションプーリング/キャッシュ層を組み合わせることで、サーバーレス環境でのコールドスタート問題とDB接続数上限を同時に解決するのが2026年の標準構成になっている。

- **Row Level Security (RLS) とORMの共存:** SupabaseのRLSポリシーをPrisma経由のアクセスでも活かすため、認証コンテキストをDB接続に伝搬させる設計（`auth.uid()`連携）が重要で、アプリ層のみで権限制御を完結させないアーキテクチャが推奨されている。

- **スキーマ駆動開発の加速:** Prisma Migrateによる宣言的マイグレーションとSupabaseのブランチ機能（PRごとのDBプレビュー環境）を組み合わせることで、`draft`/`public`のようなステータス管理を含むスキーマ変更を安全にレビュー・検証できる。

- **リアルタイム機能とORMの分離:** SupabaseのRealtime（Postgres CDC）はPrisma経由の書き込みとは独立して動作するため、在庫・予約状況などの即時反映が必要な機能はRealtimeサブスクリプション、通常のCRUDはPrismaと役割を分けるのが実用的。

- **型安全性のエンドツーエンド化:** Prismaが生成する型とSupabaseのCLIが生成するDB型（`supabase gen types`）を統合し、フロントエンドまで一貫した型を流すことで、`seller`のような内部データ構造と日本語UI表示の変換ミスをコンパイル時に検出できる体制が主流になりつつある。

### 7. WebAssembly Rust performance 2026

- **コンポーネントモデルの標準化:** WASI Preview 2とWasm Component Modelが実用段階に入り、Rustで書いたモジュールを言語非依存のインターフェースで合成・再利用できるようになった。マイクロサービス的にWasmモジュールを組み合わせる設計が現実的な選択肢になっている。

- **SIMDとマルチスレッドの成熟:** Fixed-width SIMD提案とWasm Threads（SharedArrayBuffer活用）がブラウザ・エッジ双方で安定サポートされ、画像処理やPDF生成のような重い計算をRust+Wasmでネイティブに近い速度で実行できる。当社のようなドキュメント生成・画像処理を伴うプロダクトでは、クライアントサイドのCPU負荷をサーバーからオフロードする選択肢として有効。

- **エッジコンピューティングとの親和性:** Cloudflare Workers・Fastly Compute@Edgeなどでの採用が進み、Rust+Wasmは起動が数ミリ秒と軽量なためコールドスタートに強い。API層の一部をエッジ実行に移すことでレイテンシ改善が狙える。

- **ツールチェーンの実用性向上:** wasm-bindgen・wasm-packのビルド最適化とwasm-optによるバイナリサイズ削減が進み、以前は数百KB単位だったバンドルが大幅に縮小。フロントエンドのバンドルサイズ予算内でWasmモジュールを組み込みやすくなっている。

- **導入判断の実務的な注意点:** Wasmは万能ではなく、DOM操作やJS↔Wasm間の頻繁なデータ受け渡しがあるユースケードではオーバーヘッドが相殺されることが多い。純粋な計算集約タスク（暗号化処理、画像/PDF変換、バリデーションロジックの共通化）に限定して導入するのが費用対効果が高い。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 15以降で安定した部分事前レンダリングにより、静的シェルを即座に配信しつつ動的部分のみSuspenseでストリーミングできるようになった。物件一覧ページなど「多くが静的・一部が動的」な画面ではTTFBを大幅に改善できるため、`sumitsugi`の物件詳細/検索結果ページへの適用を検討すべき。

- **Server Actions のセキュリティ境界強化:** 2026年時点ではServer Actionsが認証・入力検証のデフォルト境界として定着してきたが、`"use server"`関数はエンドポイントと同等に扱い、Zodによる入力検証と認可チェックを必ず関数冒頭に置くパターンが標準化している。前の住人/次の住人間のやり取りなど個人情報を扱うActionは特に厳格な検証が必要。

- **Cache Components / `use cache` ディレクティブの普及:** きめ細かいキャッシュ制御が関数・コンポーネント単位でできるようになり、`fetch`のオプションに依存しない明示的キャッシュ戦略が主流に。物件データのような更新頻度が低いコンテンツと、予約状況のようなリアルタイム性が必要なデータを同一ページ内で適切に使い分けられる。

- **RSC + Client Component境界の最小化設計:** 「Client Componentは葉（leaf）に留める」という原則がより徹底され、フォームや認証周りのインタラクティブ部分だけを切り出し、レイアウトやデータフェッチはServer Componentに寄せる構成がベストプラクティスとして定着。バンドルサイズ削減と初期表示速度の両立に直結する。

- **並列ルート・インターセプトルートのモーダルUXへの活用:** `@modal`スロットとインターセプトルート(`(.)`)を組み合わせ、物件詳細をモーダル表示しつつURLも共有可能にするパターンが一般化。引越し費用の内訳確認や物件写真ギャラリーなど、離脱せず詳細を見せたいUIに適している。

### 9. Vercel Edge Functions optimization 2026

- **コールドスタート最小化:** Vercel Edge FunctionsはV8 isolateベースで動作し、Node.js Functionsと比べてコールドスタートが大幅に短い。頻繁にアクセスされないAPIルートやミドルウェアはEdge Runtimeに寄せることで、レイテンシのばらつきを抑えられる。

- **Streaming + RSCとの統合:** Next.js 16のReact Server Componentsと組み合わせ、Edge上でストリーミングレスポンスを返すことで、TTFB（Time to First Byte）を改善できる。物件一覧や検索結果ページなど、データ取得に時間がかかる箇所で有効。

- **Edge ConfigとKVでのデータ近接配置:** 頻繁に読むが更新頻度の低いデータ（フラグ、設定値、料金テーブルなど）はVercel Edge Configに置き、Edge Function実行時にDBラウンドトリップを避けることでレスポンスを高速化できる。

- **実行時間ベースの課金最適化:** Edge Functionsは実行時間・メモリ使用量で課金されるため、重い処理（画像変換、PDF生成など）はEdge FunctionsではなくNode.js Functions/バックグラウンドジョブに切り出す設計が2026年のベストプラクティス。用途を分離しコストを最適化する。

- **リージョン制御とデータ主権:** `regions`設定でEdge Functionsの実行リージョンを明示的に指定できるため、日本国内ユーザー向けには`hnd1`固定にすることでレイテンシと法規制（個人情報の国内保持）の両方に対応できる。sumitsugiのような個人情報を扱う不動産プラットフォームでは特に重要な設計判断。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** TypeScript 5.x以降の`satisfies`演算子と`const`型パラメータの組み合わせが標準化し、Zodスキーマから型を推論する「Schema-first」設計がsumitsugiのような入力検証の多いプラットフォームで主流になっている。境界（API、フォーム）でZodバリデーションを行い、`z.infer`で型を導出することで二重管理を排除できる。

- **ポイント2:** テンプレートリテラル型とBranded Types（nominal typing）が、`propertyId`や`userId`のようなプリミティブ型の取り違えを防ぐパターンとして定着してきている。例えば`type PropertyId = string & { __brand: 'PropertyId' }`とすることで、DraftステータスとPublicステータスの混同のようなバグをコンパイル時に検出できる。

- **ポイント3:** Discriminated Union（判別可能なユニオン型）による網羅性チェック（exhaustiveness check）が、`'draft' | 'public'`のようなステータス管理で必須パターンになっている。`switch`文の`default`節で`never`型アサーションを使うことで、新しいステータス追加時のハンドリング漏れをビルド時に強制的に検知できる。

- **ポイント4:** tRPCやHono RPCのようなEnd-to-End型安全フレームワークがNext.js App Routerとの親和性を高め、Server Actions周りの型伝播が改善されている。フロントエンドとバックエンドの型を分離せず単一のソースから共有する設計が、開発速度とバグ削減の両立に寄与する。

- **ポイント5:** `unknown`型をデフォルトとし`any`を実質禁止するLintルール（`@typescript-eslint/no-explicit-any`）の厳格運用が広がっており、外部APIレスポンスは必ずZodでパースしてから型を確定させる「信頼境界の明示化」がセキュリティレビューの観点からも推奨される。
