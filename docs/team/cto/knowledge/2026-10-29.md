# CTO Knowledge - 2026-10-29

## Daily Update (2026-10-29)

### 1. Next.js performance optimization 2026

- **ポイント1:** React Server Components (RSC) とPartial Prerendering (PPR) の組み合わせが標準化しつつあり、静的部分を即時配信しつつ動的部分をストリーミングすることでTTFBとLCPを大幅改善できる。Next.js 16ではキャッシュ戦略（`use cache`ディレクティブ）がより洗練され、明示的なキャッシュ境界設計が重要になっている。

- **ポイント2:** Turbopackが本番ビルドでも安定版となり、Webpackからの移行でビルド時間が大幅短縮される。大規模化する前に早期移行しておくことで、CI/CDパイプラインの待ち時間削減とデプロイ頻度向上につながる。

- **ポイント3:** 画像・フォント最適化は`next/image`と`next/font`で自動化されているが、物件写真を多用するsumitsugiのようなプロダクトでは、CDN側でのAVIF/WebP変換とレスポンシブ`sizes`指定の徹底が、Core Web Vitals（特にLCP）に直結する。

- **ポイント4:** Server Actionsの濫用によるウォーターフォール（直列await）がパフォーマンス劣化の典型パターン。データ取得は`Promise.all`での並列化、またはRSCでのコロケーションフェッチを徹底し、クライアント→サーバーのラウンドトリップ数を最小化すべき。

- **ポイント5:** バンドルサイズ監視が継続的な課題。`@next/bundle-analyzer`をCIに組み込み、shadcn/uiコンポーネントの未使用バリアントやLucideアイコンの個別importを徹底することで、JSペイロードの肥大化を防ぎ、モバイル回線でのTTI（Time to Interactive）を守れる。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPartial Prerendering (PPR)が安定版となり、静的シェルを即時配信しつつ動的部分をストリーミングで後追い表示する構成が標準化。物件一覧ページのような「上部は即表示、価格・在庫は非同期」な構成に最適。
- **ポイント2:** Suspense境界の粒度設計がパフォーマンスのボトルネックになりやすく、境界を細かく切り過ぎるとウォーターフォールが発生する。データ取得をParallel Data Fetchingでまとめ、意味のある単位（カード単位・セクション単位）で境界を設計すべき。
- **ポイント3:** Server Actionsとストリーミングの組み合わせで、フォーム送信後のUI更新も段階的に返せるようになり、引越し費用の見積もりフォームなど多段階フローのUXが改善できる。ただしキャッシュ無効化（revalidateTag）の設計を誤るとstaleデータが表示されるリスクがある。
- **ポイント4:** React CompilerがRSC環境でも本格普及し、Client ComponentのuseMemo/useCallback手動最適化が不要になりつつある。bunビルドとの組み合わせでビルド時間短縮の効果も大きい。
- **ポイント5:** エッジランタイムでのRSCストリーミング（Vercel Edge / Cloudflare Workers）がデフォルト選択肢になりつつあり、物件検索のようなレイテンシ敏感な機能はエッジ配信を検討する価値がある。一方でNode.js専用ライブラリ依存がある場合は互換性検証が必須。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはTypeScriptフルスタック構成（Next.js×モノレポ）での内部API定義標準として定着し、スキーマ共有とEnd-to-End型安全性によりREST/GraphQLのような別レイヤーのドキュメント管理コストを削減できる。外部公開APIが不要な自社プロダクトなら第一候補。
- **ポイント2:** GraphQLはBFF（Backend for Frontend）層でのデータ集約に強みが残るが、N+1問題やキャッシュ戦略の複雑さから、小〜中規模チームではオーバーエンジニアリングになりやすい。複数クライアント（Web/モバイル/パートナー連携）が同時に存在する場合のみ採用を検討すべき。
- **ポイント3:** RESTは依然としてシンプルさとHTTPキャッシュ・CDN親和性で優位であり、OpenAPI 3.1+codegenの組み合わせで型安全性のギャップも縮小している。外部公開・パートナー連携APIにはRESTが安全な選択。
- **ポイント4:** 2026年のトレンドは「単一プロトコルへの統一」から「用途別の併用」へ移行している。内部通信はtRPC、外部公開APIはREST、複雑なデータ集約が必要な箇所だけGraphQLという併用パターンが一般的になりつつある。
- **ポイント5:** AIエージェントからの利用を前提としたAPI設計（構造化出力・ツール呼び出しとの相性）が新たな評価軸として重要度を増しており、Zodスキーマ等で定義したtRPC/REST契約をそのままLLMツール定義に転用できる設計が実用上の優位性を生む。

### 4. serverless edge computing 2026

- **エッジでのAI推論最適化:** Cloudflare WorkersやVercel Edge FunctionsでLLM推論のプロキシ処理が一般化し、ユーザーに最も近いロケーションでストリーミングレスポンスを返すことでTTFB（Time to First Byte）を大幅短縮できる。CDNキャッシュとAI処理を組み合わせたハイブリッド構成が標準パターンになっている。

- **コールドスタート問題の実質解消:** V8 isolateベースのランタイム（Workers、Deno Deploy等）が普及し、コンテナ型サーバーレスと比べてミリ秒単位の起動時間を実現。Next.jsのApp Routerもエッジランタイム対応が進み、`runtime: 'edge'`指定だけでグローバル分散配信が可能になっている。

- **データレイヤーのエッジ化が次の課題:** 計算はエッジ化が進んだが、DBアクセスのレイテンシがボトルネックとして残る。Turso（libSQL）、PlanetScale、Cloudflare D1のようなエッジレプリケーション対応DBの採用判断が、アーキテクチャ設計の重要な分岐点になっている。

- **コスト構造の変化に注意:** リクエスト数課金から「CPU時間」課金への移行（Cloudflareの例）で、従来のサーバーレス前提のコスト見積もりが崩れやすい。重い処理をエッジに置くと想定外のコスト増につながるため、処理の配置戦略（エッジ vs オリジン）を事前に見極める必要がある。

- **ベンダーロックインのリスク管理:** エッジランタイム独自APIへの依存度が高まる一方、Web標準API準拠のフレームワーク選定（Hono等）でマルチプラットフォーム移行可能性を保つのが実用的なリスク分散策となっている。

### 5. authentication security best practices 2026

- **ポイント1（パスキー標準化）:** パスワードレス認証（WebAuthn/FIDO2ベースのパスキー）が主要ブラウザ・OSで標準搭載となり、フィッシング耐性の高い認証がデフォルト選択肢になっている。sumitsugiのような個人間取引プラットフォームでは、本人確認コストを下げつつ乗っ取りリスクを大幅に減らせるため、早期採用のROIが高い。

- **ポイント2（セッション管理の継続的検証）:** 「ログイン時のみ検証」から「リクエストごとの継続的リスク評価」へのシフトが進み、デバイスフィンガープリントや行動分析でセッション中も異常を検知する実装が一般化している。前の住人⇄次の住人の引き継ぎという高価値トランザクションが絡むフローでは、セッションハイジャック対策として重要。

- **ポイント3（最小権限とトークンのスコープ限定）:** JWT等のアクセストークンは有効期限を短くし、用途ごとにスコープを限定する設計が事実上の標準に。認証ロジックを変更する際は、Zodでの境界検証と合わせてトークンの権限範囲を見直すべき。

- **ポイント4（多層防御としてのレート制限とボット対策）:** 認証エンドポイント（ログイン・パスワードリセット）への自動化攻撃が増加しており、IP/デバイス単位のレート制限とCAPTCHA代替（プルーフオブワーク等）の併用が推奨される。公開物件情報へのスクレイピング対策とも共通する部分が多い。

- **ポイント5（シークレット管理の自動化）:** ハードコードされた秘密情報のコミットを防ぐため、pre-commitでのシークレットスキャンとCI/CDでのローテーション自動化が標準プラクティス化している。本プロジェクトの「ハードコード禁止・env変数必須」方針と直接整合する領域。

### 6. database architecture Prisma Supabase 2026

- **Edge-nativeなコネクション管理:** Supabaseの Supavisor（PgBouncer後継のconnection pooler）とPrisma Accelerateの組み合わせがデフォルト構成になりつつあり、Vercel/Cloudflare WorkersのようなEdge環境からサーバーレス関数が増えても、PostgreSQLの最大接続数を枯渇させずにスケールできる。

- **Prisma ORMのRust脱却（TypeScriptネイティブ化）:** PrismaはクエリエンジンをRustバイナリからTypeScript実装へ移行しており、コールドスタートの高速化とバンドルサイズ削減が進んでいる。Edge FunctionsやサーバーレスでのPrisma利用時のレイテンシ課題が解消されつつある。

- **Row Level Security (RLS) とORMの併用設計:** SupabaseのRLSをPrismaのアプリケーション層の型安全性と組み合わせる設計が標準化しており、認可ロジックをDB側とアプリ側の二重に書かず、`前の住人`/`次の住人`のようなロールベースアクセス制御をRLSポリシーに委譲するパターンが有効。

- **リアルタイム同期とマイグレーション運用の両立:** SupabaseのRealtime機能とPrisma Migrateのスキーマ変更フローを併用する際、マイグレーション中のRealtimeサブスクリプション破壊を避けるため、`物件ステータス`のような列追加はnullable→backfill→制約追加の段階的マイグレーションが推奨される。

- **可観測性とクエリ最適化:** Prisma Postgres（旧名から正式統合）のクエリログとSupabaseのpg_stat_statementsを組み合わせ、N+1問題や`seller`関連の集計クエリのボトルネックを本番前に検出する体制が重要になっている。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WebAssemblyのGC拡張とComponent Modelが2026年には主要ブラウザ・ランタイムで安定し、Rustのwasm-bindgen経由でのメモリ管理やモジュール間連携が大幅に簡素化されている。既存のJSグルーコード依存を減らせる好機。
- **ポイント2:** `wasm32-wasip2`やWASIプリビュー2の普及により、サーバーサイドでのRust製WASMモジュールがサンドボックス実行環境（Cloudflare Workers、Fermyon等）でネイティブに近い起動速度を実現しつつある。コールドスタートが課題のサーバーレス処理に向く。
- **ポイント3:** SIMD128とマルチスレッド（Wasm Threads + SharedArrayBuffer）がRust側で標準的に使えるようになり、画像処理・PDF生成・暗号処理などCPU負荷の高い処理をフロントエンドに移してもネイティブの70〜90%程度の性能が出せる。
- **ポイント4:** バイナリサイズ最適化（`wasm-opt`、`twiggy`、LTO設定）のツールチェーンが成熟し、Rust製WASMモジュールでも数百KB〜1MB台に抑えやすくなった。モバイル回線でのロード時間に直結するため、本番導入時は必ずサイズ計測をCIに組み込むべき。
- **ポイント5:** 実務上はWASMを「全部」ではなく「ホットパスのみ」適用するのが2026年のベストプラクティス。JS/TSとのFFI境界を越えるたびにシリアライズコストが発生するため、頻繁な小さい呼び出しより、まとまった重い計算をバッチでWASMに渡す設計が性能面で有利。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** 静的シェルと動的コンテンツを1ページ内で共存させるPPRがNext.js 15〜16で安定版となり、ダッシュボードやECの商品ページなど「一部だけ個人化」するUIで高速TTFBを実現しやすくなった。導入時はSuspense境界の設計粒度がパフォーマンスを左右するため、コンポーネント単位で見直す価値がある。

- **Server Actionsのセキュリティ境界再整備:** Server Actionsが標準パターン化した一方、CSRF対策やAuthorizationチェックの実装漏れが依然多い。`use server`関数は暗黙的にpublic APIになることを前提に、認可チェックをアクション内部で必ず行う設計を標準化すべき。

- **Cacheセマンティクスの複雑化対応:** `fetch`キャッシュ・Router Cache・Full Route Cacheの3層が絡み合い、意図しない古いデータ表示の不具合が増えている。`revalidateTag`によるタグベース無効化を基本線にし、キャッシュ戦略をコンポーネント単位でドキュメント化することが運用上重要。

- **Server/Client境界の設計原則の定着:** 「Server Componentsをデフォルト、Client Componentsは末端（leaf）に限定」という原則がチーム内で定着しつつあるが、状態管理ライブラリ（Zustand等）をServer Componentsツリーに混在させるアンチパターンがまだ見られる。境界を跨ぐpropsのシリアライズ制約も含め、オンボーディング時のレビュー観点に組み込むべき。

- **Edge Runtimeの採用判断の明確化:** Edge RuntimeはレイテンシメリットがあるがNode.js API非対応という制約があり、認証・DB接続周りで安易に採用すると詰む。sumitsugiのような物件検索・リアルタイム性が求められる機能ではEdgeを検討対象にしつつ、DB直接アクセスが必要なRoute HandlerはNode.js Runtimeに固定する方針が妥当。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge Functionsはコールドスタートがほぼゼロな分、実行時間とメモリに厳しい制約があるため、重い依存関係（大きなnpmパッケージ、ネイティブモジュール）を避けてバンドルサイズを最小化することが引き続き最重要。

- **ポイント2:** Next.js 16のPartial Prerendering（PPR）とEdge Runtimeを組み合わせることで、静的シェルを即時配信しつつ動的部分だけEdgeでストリーミングする構成が標準化しており、物件検索や一覧ページのTTFB改善に直結する。

- **ポイント3:** Edge上でのデータ取得はリージョン間レイテンシがボトルネックになりやすいため、Vercel KV/Edge Configやリージョン分散されたDB（例：Neon、PlanetScaleのedge対応）をユーザーに近いリージョンで使うことがパフォーマンスの分岐点になる。

- **ポイント4:** Middleware肥大化（認証・リダイレクト・A/Bテストを全部Middlewareに詰め込む）がEdge実行コストとレイテンシを悪化させる典型パターンなので、本当にリクエスト単位で必要な処理だけに絞るべき。

- **ポイント5:** Edge FunctionsはNode.js APIの一部が使えない制約があるため、依存ライブラリがEdge Runtime対応かを事前に確認し、非対応の処理（画像処理や重いPDF生成など）はServerless Functions側に明確に分離するアーキテクチャ判断が重要。

### 10. TypeScript type safety patterns 2026

- **厳格な型推論とconst型パラメータ:** TypeScript 5.x系で導入された`const`型パラメータやtemplate literal typesの活用がさらに進み、APIレスポンスやルーティングパスなど文字列ベースの値をコンパイル時に検証するパターンが標準化しています。本プロジェクトでも`src/app/`のルート定義やZodスキーマと組み合わせて、ランタイムエラーを未然に防ぐ設計が有効です。

- **Zodなどのスキーマ駆動型安全性:** `standards.md`にもある通り、システム境界（API入出力・フォーム）でのZod活用は2026年も主流で、`z.infer`による型生成とスキーマの単一ソース化がベストプラクティスとして定着しています。型定義とランタイム検証の二重管理を避けることが鍵です。

- **Discriminated Unionによる状態管理の厳格化:** `'draft' | 'public'`のようなステータス型は、関連フィールドを含むDiscriminated Unionに拡張し、`switch`の網羅性チェック（`never`型での保証）で未処理ケースをコンパイル時に検出するパターンが広がっています。

- **型レベルテストの導入:** `expectTypeOf`（Vitest統合）や`tsd`を使い、型定義自体をテスト対象にする動きが加速しています。UIターム変換（セラー→前の住人等）のような変換関数は、型レベルでも入出力の整合性を保証できます。

- **AIコード生成時代の型安全性ガードレール:** Claude Codeなど自動化パイプラインでの実装が増える中、型を「コミュニケーション手段」として捉え、関数シグネチャとZodスキーマを先に固定してから実装を生成させる手法が、品質とスピードを両立させる現場標準になっています。
