# CTO Knowledge - 2026-09-26

## Daily Update (2026-09-26)

### 1. Next.js performance optimization 2026

- **ポイント1（Partial Prerendering の本格運用）:** Next.js 15/16でstableになったPPR（Partial Prerendering）を使うと、静的シェルを即座に配信しつつ動的部分だけをストリーミングできるため、TTFBとLCPを大幅に改善できる。物件一覧ページのような「共通レイアウトは静的・検索結果は動的」な構成に特に有効。
- **ポイント2（React Compiler導入）:** React Compilerが安定版に近づき、`useMemo`/`useCallback`の手動最適化が不要になりつつある。物件カードや画像ギャラリーなど再レンダリングが多いコンポーネントで導入すれば、コード量を減らしつつパフォーマンスも向上する一石二鳥の施策。
- **ポイント3（画像・フォント最適化の自動化強化）:** `next/image`のAVIF優先配信とフォントのセルフホスティング自動化が進化しており、CLS（Cumulative Layout Shift）対策がほぼ設定不要になってきている。前の住人の物件写真が多いsumitsugiのようなサービスでは、Core Web Vitals改善に直結する。
- **ポイント4（Server ActionsとCache Componentsの分離）:** キャッシュ戦略が`use cache`ディレクティブによって宣言的になり、キャッシュ粒度をコンポーネント単位で制御できるようになった。ステータス（draft/public）で表示が変わる物件ページでは、キャッシュミスを最小限にしつつ最新性を担保する設計がしやすくなる。
- **ポイント5（Edge Runtimeの選択的活用）:** すべてをEdgeに寄せるのではなく、認証チェックやリダイレクトなど軽量処理のみEdge Runtimeに置き、DB接続を伴う処理はNode Runtimeに残すハイブリッド構成がベストプラクティスとして定着しつつある。Vercel以外のホスティングでも同様の切り分けが有効。

### 2. React Server Components streaming 2026

- **ストリーミングSSRの標準化:** Suspense boundaryを使ったpartial hydrationがApp Routerでデフォルト挙動になりつつあり、初回表示（TTFB）を犠牲にせず段階的にUIを届けられる。sumitsugiでは物件詳細ページの画像ギャラリーやレビュー欄をSuspenseで区切ることで、上部のコア情報（価格・住所）を即座に表示しつつ重い部分を後追いで流し込める。

- **Server Actionsとキャッシュ戦略の成熟:** `use cache`ディレクティブやgranular cache invalidationが安定し、物件ステータス（draft/public）変更のような書き込みが発生する箇所でも再検証範囲を細かく制御できるようになった。過剰な全体再検証を避け、ビルド後のパフォーマンス劣化を防げる。

- **RSC Payloadのサイズ最適化がボトルネックに:** ストリーミング自体は速くても、シリアライズされるpropsが肥大化するとネットワーク律速になる。物件一覧のようなリスト画面では、クライアントに渡すデータを表示に必要な最小限のフィールドに絞る設計が引き続き重要。

- **Bunとの相性:** Bun 1.xのモジュール解決・トランスパイル速度向上により、RSCのビルド時サーバーコンポーネント解析（React Compilerとの組み合わせ含む）が高速化され、開発体験（HMR含む）が改善している。

- **エラーバウンダリの粒度設計が必須スキルに:** ストリーミング中に一部コンポーネントがエラーを投げても他の部分の表示を止めないよう、Suspense境界ごとにError Boundaryを対応させる設計パターンが定着した。認証やフォーム送信など失敗しやすい箇所ほど、境界を細かく切ることが実用上のポイント。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCはTypeScriptモノレポ（フロント/バック同一言語）で急速に採用が進んでおり、スキーマ定義とコード生成の手間を省いて型安全性をエンドツーエンドで保証できる点が評価されている。Next.js App Router構成では特に相性が良い。
- **ポイント2:** GraphQLは大規模・複数クライアント（モバイル/Web/パートナーAPI）を抱える組織で依然強いが、N+1問題やキャッシュ戦略の複雑さから中小規模プロダクトでは過剰投資になりやすい。
- **ポイント3:** RESTはシンプルさとHTTPキャッシュ・CDNとの親和性から「枯れた技術」として今も第一選択であり、公開APIやWebhookなど外部連携が絡む場面では最も無難な選択肢。
- **ポイント4:** 2026年の潮流としては「1つのAPI方式に統一」ではなく、内部通信はtRPC、外部公開APIはREST（+OpenAPI）、複雑な集約が必要な画面はGraphQLと役割分担するハイブリッド構成が増えている。
- **ポイント5:** Zodなどのスキーマ検証ライブラリを起点に、API定義・型・バリデーションを一元化する流れが加速しており、sumitsugiのようにZodを標準採用しているプロジェクトではtRPC+Zodの組み合わせが最も開発体験とバンドルサイズのバランスが良い。

### 4. serverless edge computing 2026

- **ポイント1（エッジランタイムの標準化）:** WinterCG仕様（Fetch API準拠のWeb標準ランタイム）への収束が進み、Cloudflare Workers・Vercel Edge・Deno Deployなど各社の互換性が高まったことで、ベンダーロックインを避けたエッジファースト設計が現実的な選択肢になっています。

- **ポイント2（コールドスタート問題の実質解消）:** V8 isolateベースの実行モデルとWASMの成熟により、コールドスタートがミリ秒単位まで縮小し、認証・A/Bテスト・地域別価格表示のようなリクエスト単位のロジックをオリジンサーバーを介さずエッジで処理できるようになっています。

- **ポイント3（エッジDBとの結合）:** Turso・D1・PlanetScaleなどのエッジ対応DBが普及し、読み取りレプリカをユーザーに地理的に近い場所に配置できるため、グローバル展開時のレイテンシ改善に直結します。ただし書き込み一貫性の設計判断は依然として必要です。

- **ポイント4（コスト構造の変化）:** リクエスト課金＋実行時間ベースの従量課金が主流となり、小〜中規模トラフィックのアプリではサーバーレスエッジが従来のVM/コンテナ運用よりコスト効率が良いケースが増えていますが、常時高負荷なワークロードでは逆転することもあるため見極めが重要です。

- **ポイント5（開発体験の統合）:** Next.jsのミドルウェア/Edge Runtimeのように、フレームワークレベルでエッジとサーバーの実行環境を透過的に切り替えられるようになり、sumitsugiのようなNext.js 16ベースのプロジェクトでも、認証チェックや地域別コンテンツ出し分けを追加インフラなしでエッジ層に寄せられる余地が広がっています。

### 5. authentication security best practices 2026

- **パスキー（WebAuthn/FIDO2）への全面移行:** パスワード＋SMS認証はフィッシング耐性が低く、2026年時点ではパスキーをデフォルトの認証手段とし、パスワードは後方互換のフォールバックとして扱うのが標準。sumitsugiのようなtoC向けサービスでは、初回登録時にパスキー登録を促すUXが離脱率にも直結する。

- **フィッシング耐性MFAの必須化:** SMS/TOTPは中間者攻撃・SIMスワップに弱いため、決済や個人情報変更などの高リスク操作にはFIDO2ハードウェアキーやプラットフォーム認証子（Face ID/Touch ID経由のパスキー）を要求する段階的認証（step-up auth）を設計すべき。

- **セッション管理とトークンの短命化:** リフレッシュトークンの長期保存はセッションハイジャックの主要リスク。アクセストークンは短命（15分程度）＋リフレッシュトークンローテーション＋デバイスバインディングを組み合わせ、不正利用時の被害範囲を最小化する構成が2026年のベストプラクティス。

- **AIエージェント/ボット対策としての行動的シグナル活用:** クレデンシャルスタッフィング攻撃が生成AIで自動化・高度化している中、パスワードだけでなくデバイスフィンガープリンティングやリスクベース認証（異常ログイン検知）をNext.js middlewareレベルで組み込むことが重要。前の住人・次の住人間の個人情報を扱うsumitsugiでは特に優先度が高い。

- **CSRF/セッション固定への基本対策の徹底:** 新しいトレンドに気を取られがちだが、Auth.js/NextAuth等を使う場合でもCookieの`SameSite=Strict`＋`httpOnly`＋`Secure`属性の徹底、CSRFトークンの実装漏れがないかは依然として最頻出の脆弱性であり、`src/contexts/auth-context.tsx`実装時の基本チェック項目として外せない。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Supabase自体がPrisma向けに最適化されたコネクションプーリング（Supavisor経由のPgBouncer）を強化しており、`DATABASE_URL`にプール用ポート（6543）、`DIRECT_URL`にマイグレーション用の直接接続（5432）を分ける構成が2026年時点でも標準パターンになっている。

- **ポイント2:** Prisma 6以降のRust-freeエンジン（TypeScript/WASMベース）への移行が進み、Vercel EdgeやCloudflare Workersなどのエッジランタイムでもコールドスタートが大幅に改善されたため、サーバーレス環境でのPrisma利用がより実用的になっている。

- **ポイント3:** Supabase RLS（Row Level Security）とPrismaのスキーマ管理を併用する際、Prisma側はRLSポリシーを直接表現できないため、`supabase/migrations`とPrismaマイグレーションを分離し、RLSはSQLで別管理するハイブリッド運用が定着している。

- **ポイント4:** Prisma AccelerateやSupabaseのRead Replica機能を組み合わせることで、グローバル配信・キャッシュ層を挟んだクエリ高速化がコード変更なしで導入できるようになり、住宅情報のような読み取り比率の高いプロダクト（sumitsugiの物件一覧など）には特に有効。

- **ポイント5:** Prisma Studioに加えてSupabase Studioが両立するため、開発チームはスキーマ定義（型安全性）をPrismaに、認証・ストレージ・リアルタイム機能をSupabase側に委ねる「責務分離」の設計が2026年のベストプラクティスとして定着している。

### 7. WebAssembly Rust performance 2026

- **ポイント1: Component Model の実用化進展** — WASI Preview 2とComponent Modelの普及により、RustコンパイルのWasmモジュールを言語非依存で組み合わせられるようになってきており、マイクロサービス的な設計をエッジ環境で低コストに実現しやすくなっている。

- **ポイント2: SIMD・スレッド対応で処理性能が向上** — `wasm-bindgen`やRustのターゲット機能拡張によりWasm SIMD・マルチスレッド（`wasm32-unknown-unknown` + Web Workers）が実用段階に入り、画像処理や暗号化などCPU負荷の高い処理でネイティブに近い速度が出せるようになった。

- **ポイント3: バイナリサイズ最適化が引き続き重要** — `wasm-opt`や`twiggy`によるツリーシェイキング、`no_std`構成の活用が定着し、初回ロード時間短縮のためのバンドルサイズ管理がRust/Wasm採用時の標準プラクティスになっている。

- **ポイント4: サーバーサイドWasm（Wasmtime/WasmEdge）の採用拡大** — Rust製ランタイムがサンドボックス化されたプラグイン実行環境として採用されるケースが増えており、ユーザー生成コードの安全な実行や、コールドスタートの速いサーバーレス基盤としての評価が高まっている。

- **ポイント5: デバッグ・プロファイリング環境の成熟** — ソースマップ対応やDWARF情報のWasm出力サポートが改善され、ブラウザDevToolsでRustコードを直接デバッグしやすくなったことで、開発体験のボトルネックが解消されつつある。

### 8. Next.js App Router patterns 2026

- **ポイント1（Partial Prerendering の本格普及）:** Next.js 15〜16でstableになったPPRにより、静的シェルを即座に返しつつ動的部分だけをストリーミングする設計が標準化。TTFBを犠牲にせずパーソナライズ表示ができるため、物件詳細ページのような「静的な基本情報＋動的な空室状況」構成に相性が良い。

- **ポイント2（Server ActionsとuseActionState/useOptimisticの定着）:** フォーム送信・楽観的更新のパターンがApp Router標準になり、API Routeを介さずServer Component→Server Actionで完結する実装が主流に。物件のお問い合わせフォームや前の住人とのメッセージ機能はクライアントJSを最小化しつつ実装できる。

- **ポイント3（キャッシュ戦略の明示化: `use cache`ディレクティブ）:** 従来の暗黙的fetchキャッシュから、`use cache`と`cacheLife`/`cacheTag`によるオプトイン・明示的キャッシュ制御へ移行。物件一覧のようにDB更新頻度が異なるデータ単位で、キャッシュのTTLとタグ無効化を細かく制御できるようになった。

- **ポイント4（Server Component境界のバンドルサイズ意識）:** "use client"境界を最小単位に絞り、shadcn/uiのようなプリミティブはサーバー側でレンダリングしてインタラクティブ部分のみクライアント化する設計が定石化。ダークモード切替やモーダルなど局所的な状態のみをクライアントコンポーネント化することでLCP/TBTが改善する。

- **ポイント5（Turbopackのデフォルト化とビルド時間短縮）:** `bun run build`のようなプロダクションビルドでもTurbopackが実用段階に入り、大規模ルート構成でもビルド時間が大幅短縮。CIのビルド検証ステップ（本プロジェクトのBuild Verificationルール）のフィードバックループが速くなり、型エラー検出までのイテレーションが早まる。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1（コールドスタート最適化）:** Edge RuntimeはV8 isolateベースのため既にコールドスタートはミリ秒単位だが、依存関係のバンドルサイズを1MB未満に抑えることで初回応答をさらに安定させられる。sumitsugiのようなSSRメインの物件検索では、Edge Middlewareでの認証チェックだけをEdgeに残し、重い処理はNode.js runtimeに委譲する使い分けが有効。
- **ポイント2（Streaming SSR + Partial Prerendering）:** Next.js 16のPPR（Partial Prerendering）とEdge Functionsを組み合わせることで、静的な物件一覧の骨格を即座に返しつつ、価格や空き状況などの動的部分だけをEdgeでストリーミング配信できる。これにより体感速度（TTFB/LCP）が大幅に改善する。
- **ポイント3（リージョン配置とデータ近接性）:** Edge Functionsは実行速度が速くてもDB（例：Supabase/Postgres）が単一リージョンにあるとレイテンシがボトルネックになる。読み取り専用データはEdge Config/KVにキャッシュし、書き込みが必要な操作のみNode.js runtimeに回す設計が2026年のベストプラクティス。
- **ポイント4（可観測性とコスト管理）:** Edge Functionsは呼び出し課金モデルのため、不要なEdge化（重い計算やDBクエリの多いAPI）はコスト増につながる。Vercelのobservabilityツールで実行時間・呼び出し回数を監視し、本当にレイテンシ要求が厳しいパス（認証・リダイレクト・A/Bテスト振り分け）に限定するのが原則。
- **ポイント5（Bun/Node互換性の注意）:** 開発環境でBunを使っていても、Edge Runtimeは独自のWeb標準API限定のサンドボックスであり、Node.js固有API（fsなど）は使えない。ローカルのbun devとVercel Edge環境の挙動差異を防ぐため、Edge対象コードはWeb標準APIのみに限定して書くことをチームに徹底すべき。

### 10. TypeScript type safety patterns 2026

- **型安全なランタイムバリデーション:** Zodなどのスキーマ定義から型を自動推論する`z.infer`パターンが主流化し、型定義とバリデーションロジックの二重管理が不要に。API境界やフォーム入力の検証で型安全性を保証できる。
- **`satisfies`演算子の定着:** TypeScript 4.9以降で導入された`satisfies`により、型推論を保ちながら型チェックが可能になり、`as const`と組み合わせて設定オブジェクトやルーティング定義の型安全性が向上している。
- **Branded Types（公称型）の普及:** `type UserId = string & { __brand: 'UserId' }`のようなパターンで、構造的型付けの弱点（IDの取り違えなど）を防ぐ実装が増加。特に決済・認証まわりで有効。
- **Template Literal Typesによる文字列型の厳密化:** APIパス、CSSクラス名、i18nキーなど、文字列リテラルの組み合わせを型レベルで表現し、コンパイル時にタイポや不正な値を検出する使い方が一般化。
- **strictモード+ESLintの型情報連携:** `@typescript-eslint`の型情報を使ったルール（`no-unsafe-*`系）を有効化し、`any`の混入をCIで機械的に検出する運用が標準になりつつある。sumitsugiでもZodスキーマ+strict TypeScriptの組み合わせをシステム境界（フォーム、API）で徹底すべき。
