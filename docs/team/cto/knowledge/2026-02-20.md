# CTO Knowledge - 2026-02-20

## Daily Update (2026-02-20)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを劇的に削減できるため、デフォルトをサーバーコンポーネントとし、インタラクティブな部分だけ `'use client'` に切り出す設計が2026年の標準プラクティスとなっている。

- **Partial Prerendering (PPR) の本番導入:** Next.js 15以降で安定化したPPRにより、静的シェルを即時配信しつつ動的コンテンツをストリーミングできる。`experimental.ppr`を有効化するだけで、ISRとSSRのハイブリッドを超えたパフォーマンスが得られる。

- **Turbopack への移行加速:** `next dev --turbopack` が安定版となり、大規模コードベースでのHMR速度が従来比10倍以上向上。本番ビルドへの対応も進んでおり、CI/CDのビルド時間短縮に直結する。

- **`<Image>` と `next/font` の最大活用:** Core Web Vitals（LCP・CLS）への影響が依然大きく、画像の `priority` 指定・`sizes` 最適化・フォントのサブセット化は基本中の基本。審査基準が厳格化したGoogle検索ランキングにも直接影響する。

- **Bundle Analyzer + `experimental.optimizePackageImports` の常時監視:** `@next/bundle-analyzer`とビルドメトリクスをCI/CDに組み込み、バンドルサイズの増大を自動検知する体制が重要。特にサードパーティライブラリの意図しない全量インポートを`optimizePackageImports`で抑制することが効果的。

### 2. React Server Components streaming 2026

- **ポイント1: Partial Prerendering（PPR）の実用化が加速** PPRにより静的シェルを即時配信しつつ動的コンテンツをストリーミングする手法が標準化され、Next.js App RouterでのTTFBとLCPが大幅に改善された。

- **ポイント2: Suspenseバウンダリの粒度設計がアーキテクチャの要** ストリーミングの恩恵を最大化するには、Suspenseの分割粒度が重要で、過細分割はウォーターフォールを招き、粗すぎると体感速度が悪化する。コンポーネントツリー設計時にデータ依存関係を可視化する習慣が必須。

- **ポイント3: Server Actionsとの組み合わせで楽観的UIが簡素化** RSCストリーミングとServer Actionsの統合により、楽観的更新→サーバー確定→UI再ストリーミングのサイクルがボイラープレートなしに実現できるようになった。

- **ポイント4: エッジ・ランタイムとの親和性が鍵** CloudflareやVercelのエッジ環境でのRSCストリーミングは低レイテンシを実現できるが、Node.js専用APIへの依存が多いアプリはエッジ対応のリファクタリングコストに注意が必要。

- **ポイント5: キャッシュ戦略の再設計が不可避** `fetch`のキャッシュオプション（`force-cache` / `no-store` / `revalidate`）とストリーミングの組み合わせは複雑化しており、データの鮮度要件とパフォーマンスのトレードオフを明確なポリシーとして文書化しておくことが運用上の混乱を防ぐ。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭:** TypeScriptフルスタック環境ではtRPCがデファクトに近づいており、型安全なエンドツーエンドAPIをボイラープレートなしで実現できる。Next.js App RouterとのServer Actions統合により、そもそもAPIレイヤーを省略するパターンも増加。

- **GraphQLの選択的採用:** フェデレーション（Apollo Federation、Stellate）が成熟し、マイクロサービス間のデータグラフ統合には有効だが、単一チームの中小規模アプリでは過剰設計になるケースが多い。2026年時点では「GraphQLが必要な理由」を説明できない場合は採用を避けるべき。

- **REST + OpenAPIの底力:** Hono・Elysia（Bun対応）など軽量フレームワークとOpenAPI 3.1の組み合わせが再評価されており、自動型生成（openapi-typescript）でtRPCに近い型安全性を実現。既存チームのスキルセットを活かしつつ安全に移行できる。

- **エッジ・ストリーミング対応:** Vercel AI SDK / Server-Sent Events を活用したストリーミングAPIが標準化。LLM統合が前提となった設計では、従来のrequest-responseモデルだけでなくストリーミングプロトコルを最初から設計に組み込む必要がある。

- **APIセキュリティの自動化:** Rate limiting・認証・バリデーション（Zod/Valibot）をミドルウェア層に集約し、個別エンドポイントで再実装しないパターンが必須。特にAI生成コードの増加により、境界バリデーションの抜け漏れリスクが高まっている。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) の台頭:** CloudflareやFastlyなどのエッジランタイムでWasmが標準化しつつあり、言語非依存でコールドスタートほぼゼロの実行環境が実現。Node.js依存から脱却できる。

- **エッジDBとデータの局所化:** Cloudflare D1、Turso（libSQL）などエッジ近傍で動作する分散SQLが普及し、レイテンシ問題のボトルネックがコンピュートからデータアクセス層に移行している。

- **AI推論のエッジ実行:** 軽量LLM（Phi-3 mini、Gemma 2B相当）をエッジで動作させるユースケースが増加。クラウド往復なしでリアルタイム推論が可能になり、プライバシーとレイテンシを両立できる。

- **Durable Objects / Actor モデルの成熟:** ステートレスの限界を超えるためCloudflare Durable Objectsのようなエッジ上のステートフルActorが標準パターンになりつつあり、WebSocketやリアルタイム同期の実装が大幅に簡素化された。

- **observabilityの課題が深刻化:** エッジ拠点が200+に分散することでトレースの統合が困難になっており、OpenTelemetry対応とエッジネイティブな監視基盤（Baselime等）の整備が2026年の重要課題となっている。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）への移行加速:** パスワードレス認証の業界標準としてパスキーが定着しつつある。フィッシング耐性とUX向上を両立できるため、新規実装ではパスワード認証をデフォルトから外すべき時代になった。

- **AIを活用した不正アクセス検知の高度化:** 行動バイオメトリクス（タイピングリズム、マウス動作）とリアルタイムML推論の組み合わせが標準化。単純なIP/デバイス判定だけではbotや乗っ取りを防げなくなっている。

- **Zero Trust + 継続的認証（Continuous Authentication）:** ログイン時の一回認証では不十分。セッション中も常にリスクスコアを評価し、異常を検知した際に再認証を要求するアーキテクチャが金融・SaaS領域で必須となっている。

- **OAuth 2.1 / DPoP（Demonstrating Proof of Possession）の採用:** トークン盗難対策としてDPoP（トークンを特定クライアントに紐付ける仕組み）が実装されるようになった。BearerトークンのみのOAuth実装は脆弱性リスクとして認識される。

- **サプライチェーンリスクとしての認証ライブラリ管理:** 認証関連のnpmパッケージ改ざん事例が増加。依存ライブラリのSBOM管理・整合性検証（`--frozen-lockfile` や Sigstore）を開発パイプラインに組み込むことがDevSecOpsの基本となっている。

### 6. database architecture Prisma Supabase 2026

- **Supavisor による接続プーリングの標準化:** Supabase が独自の Rust 製コネクションプーラー Supavisor を安定リリースし、Prisma との組み合わせでは `DATABASE_URL`（Supavisor 経由）と `DIRECT_URL`（マイグレーション用直接接続）を分離する構成が事実上の標準になっている。

- **Prisma Accelerate でエッジ対応が加速:** Prisma Accelerate（グローバル接続プール＋キャッシュ）により、Vercel Edge / Cloudflare Workers などのサーバーレス環境でも Prisma が実用レベルで動作するようになり、コールドスタート問題が大幅に緩和された。

- **RLS（Row Level Security）との共存が設計上の最重要課題:** Supabase の RLS ポリシーと Prisma ORM を組み合わせる場合、Prisma はサービスロールで動作するため RLS をバイパスする点に注意が必要。認可ロジックをアプリ層（Prisma middleware / service layer）に集約するパターンが推奨される。

- **Prisma 6 以降の型安全性強化と `omit` フィールド:** Prisma 6 で `omit` オプションが安定化し、パスワードハッシュ等の機密フィールドをクエリ結果から型レベルで除外できるようになった。セキュリティ設計においてデフォルト除外を積極的に活用すべき。

- **スキーマ変更の自動化リスク管理:** `prisma migrate deploy` を CI/CD に組み込む際、Supabase の本番 DB に対して誤って破壊的マイグレーションが走るリスクを抑えるため、`--dry-run` 相当の確認ステップと shadow database の活用が不可欠になっている。

### 7. WebAssembly Rust performance 2026

- **WASM GC（Garbage Collection）の本格普及:** WasmGC提案が主要ブラウザで安定稼働し、RustからWasmへのコンパイルでメモリ管理のオーバーヘッドが削減。特にサーバーサイドWasm（WASIp2）との組み合わせでエッジコンピューティング用途が拡大している。

- **SIMD・スレッド対応の成熟:** Wasm SIMDとshared memoryの仕様が安定し、RustのRayonベースの並列処理をWasmで活用できる場面が増加。画像処理・機械学習推論など計算負荷の高いワークロードでネイティブに近いスループットを実現。

- **コンパイルサイズ vs 実行速度のトレードオフ解消:** `wasm-opt`（Binaryen）とRustの`opt-level`チューニングにより、バイナリサイズを30〜50%削減しつつパフォーマンスを維持する手法が確立。`cargo-component`ツールチェーンでWasm Component Modelへの移行が加速。

- **コンポーネントモデルによるinterop強化:** Wasm Component Model（WASI 0.2）の採用でRustモジュールをJS/Python/Go等と型安全にインターフェースできるようになり、モノリシックなWasmバイナリから分散コンポーネント構成へ移行が進んでいる。

- **実用上の注意点:** Wasm環境ではI/O・非同期処理（async Rust + wasm-bindgen-futures）のコストが依然高く、CPU集約タスクに絞って適用するのが2026時点でのベストプラクティス。Cloudflare WorkersやFastly Compute等のWasmランタイムごとにSIMD対応状況が異なるため、ターゲット環境の事前確認が必須。

### 8. Next.js App Router patterns 2026

- **React Server Components (RSC) をデフォルトに:** クライアントコンポーネントは `"use client"` で明示的に宣言し、データフェッチ・認証・DBアクセスはすべてサーバー側に集約することでバンドルサイズを大幅削減できる。

- **Partial Prerendering (PPR) の活用:** 静的シェルと動的コンテンツを同一ページ内で共存させるPPRが実用段階に入っており、`<Suspense>` 境界を適切に設計することでTTFBと動的性能を両立できる。

- **Server Actions でAPIルートを削減:** フォーム送信・データミューテーションに `"use server"` のServer Actionsを使うことで、別途APIエンドポイントを書く必要がなくなり、型安全なフルスタック開発が実現する。

- **キャッシュ戦略の精緻化:** `unstable_cache` / `revalidateTag` / `revalidatePath` を組み合わせたタグベースのISRが標準的になっており、ページ全体ではなくデータ単位での再検証が可能になっている。

- **Parallel Routes & Intercepting Routes:** モーダルやスライドオーバーをURLと同期させながら実装できるため、ブラウザの戻る/進む操作に自然に対応したUI設計が可能。本プロジェクトの物件詳細モーダルなどに特に有効。

### 9. Vercel Edge Functions optimization 2026

- **エッジファーストアーキテクチャの標準化:** 2026年時点でVercel Edge Functionsは単なる最適化手段から「デフォルト実行環境」へ移行しており、Next.js App RouterのMiddlewareとServer Componentsとの統合が前提設計となった。

- **コールドスタート問題の実質的解消:** V8 Isolatesベースのランタイムにより平均レイテンシが1ms以下に収束。ただしNode.js互換APIの制約（`fs`、`net`等の非対応）は依然残るため、依存ライブラリの互換性確認が設計段階で必須。

- **エッジでのデータアクセス最適化:** Vercel KV（Upstash Redis）・Edge Config・Turso（SQLite at edge）の組み合わせで「コンピュートとデータの同地域配置」が実現可能。グローバルDB同期のレイテンシを回避するため、読み取り専用データはEdge Configに寄せる設計が有効。

- **バンドルサイズ管理の重要性:** Edge Functionsは1MBのサイズ制限があり、重量級ライブラリ（`zod`、`date-fns`等）の全インポートが制約になるケースがある。Tree-shakingと軽量代替ライブラリ（`valibot`等）の選定が継続的なボトルネック。

- **Partial Prerendering（PPR）との組み合わせ:** Next.js 15以降のPPRとEdge Middlewareを組み合わせ、静的シェルをCDNで配信しつつ動的パーツのみEdgeで処理するパターンが最も効果的なTTFB最適化戦略として定着している。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `UserId`・`ProductId` のように同じ `string` 型でも意味的に区別する Branded Types が実務標準となり、実行時ゼロコストで型混在バグを防止できる。

- **`satisfies` 演算子の積極活用:** TypeScript 4.9 以降の `satisfies` は型チェックを行いつつ型を狭めないため、`as const` との組み合わせでリテラル型を保持しながら安全な検証が可能になった。

- **`NoInfer<T>` による推論制御:** TypeScript 5.4 導入の `NoInfer` ユーティリティ型で、ジェネリクスの推論サイトを明示的に制御でき、意図しない型拡張を防げる。

- **Zod + tRPC によるランタイム境界の型一致:** スキーマ定義から TypeScript 型を自動導出する pattern が成熟し、API境界での `unknown` 型の安全な絞り込みが宣言的に書けるようになった。

- **`using` 宣言によるリソース管理:** TC39 Explicit Resource Management（TypeScript 5.2+）の `using`/`await using` が普及し、DB接続・ファイルハンドル等のリソースリークを型システムレベルで防止できる。
