# CTO Knowledge - 2026-08-02

## Daily Update (2026-08-02)

### 1. Next.js performance optimization 2026

**CTOの視点:Next.js パフォーマンス最適化 2026**

- **ポイント1:** Partial Prerendering(PPR)が安定版として本格普及し、静的シェルを即座に配信しつつ動的部分をストリーミングする構成が標準化。sumitsugiの物件一覧・詳細ページのような「静的な骨格＋動的な在庫状況」型のUIに特に効果的。
- **ポイント2:** React Compilerの自動メモ化により、手動での`useMemo`/`useCallback`最適化がほぼ不要になり、レンダリングコストの削減がコード量削減と両立するようになった。既存コンポーネントの最適化リファクタ工数を大幅に減らせる。
- **ポイント3:** `next/image`と`next/font`のCore Web Vitals最適化がさらに進化し、特にLCP改善のためのpriority hint自動化が強化。物件写真中心のUIではLCPスコアに直結するため優先度が高い。
- **ポイント4:** Turbopackが本番ビルドでも標準化されつつあり、ビルド時間が大幅短縮。CI上での`bun run build`検証サイクルが速くなることで、PRごとのフィードバックループが改善する。
- **ポイント5:** Server ActionsとCache Componentsの組み合わせによるデータフェッチの再検証戦略が洗練され、`revalidateTag`ベースの粒度の細かいキャッシュ無効化が主流に。予約・ステータス更新(`draft`/`public`)のような頻繁に変わるデータの整合性担保がしやすくなる。

### 2. React Server Components streaming 2026

- **ポイント1:** RSC + Streaming SSRの組み合わせがNext.js 16でデフォルト最適化され、`loading.tsx`とSuspense境界の粒度設計がTTFB改善の主戦場になっている。ページ全体ではなくコンポーネント単位でストリーミング境界を切ることで、体感速度が大きく変わる。

- **ポイント2:** Server Actionsとの併用でクライアントバンドルサイズが削減される一方、"use client"境界の設計ミスがハイドレーションエラーの温床になりやすい。sumitsugiの`properties/`や`listing/`のようなデータフェッチが重いページほど、境界設計のレビューを重視すべき。

- **ポイント3:** Partial Prerendering (PPR) が安定期に入り、静的シェル+動的ストリーミングのハイブリッドが標準パターン化。物件一覧のような「静的な枠+動的な検索結果」構成に向いている。

- **ポイント4:** キャッシュ戦略（`fetch`のrevalidate、`unstable_cache`)とストリーミングの相性が悪いケースが増えており、認証済みユーザー向けの物件詳細ページなどパーソナライズが絡む箇所は明示的なキャッシュ制御が必須。

- **ポイント5:** E2Eテスト(Playwright)でストリーミング特有の「途中状態」を検証する必要が出てきており、`test:e2e`にSuspense fallback表示の検証ケースを追加することが品質担保の観点で重要。

### 3. API design REST GraphQL tRPC 2026

**API設計トレンド 2026年**

- **ポイント1（tRPC/BFF統合の主流化）:** TypeScriptフルスタック構成ではtRPCがBFF層のデファクトになりつつあり、型安全性とスキーマ手書き不要の恩恵が開発速度に直結する。sumitsugiのようなNext.js App Router構成では、Server Actionsとの併用でtRPCのオーバーヘッドが不要なケースも増えており、「どこにtRPCを使い、どこはServer Actionsで十分か」の線引きが設計判断の鍵になる。

- **ポイント2（GraphQLは複雑な集約クエリに限定活用）:** GraphQLは依然としてモバイル/複数クライアント対応や複雑なリレーション集約（物件検索の絞り込み条件が多い画面など）で強みがあるが、単一フロントエンド構成のプロダクトでは運用コスト（リゾルバのN+1対策、キャッシュ戦略）が見合わないケースが多い。小規模チームではREST/tRPCで十分というのが2026年の一般的な合意。

- **ポイント3（REST + OpenAPIの型生成が再評価）:** 外部連携（決済、行政API、地図API等）が絡む境界ではRESTが依然として標準で、OpenAPI仕様からのZodスキーマ自動生成ツールが成熟し「型安全なREST」が実用レベルに到達している。物件データの外部API連携部分はRESTで統一し、内部UIロジックはtRPCで、という使い分けが妥当。

- **ポイント4（スキーマファースト設計とZodの二重活用）:** Zodスキーマをバリデーションと型定義の両方に使う「スキーマファースト」が標準化し、フロント・バックエンド間の型ズレによるバグを大幅に削減している。既存の`.claude/rules/standards.md`にあるZod境界バリデーション方針と自然に整合するため、追加投資なしで恩恵を受けられる。

- **ポイント5（エッジ/ストリーミングAPIへの対応）:** Next.js 16のServer Components/Streaming SSRを活かすAPI設計では、レスポンスを一括返却せず段階的にストリーミングする設計（物件一覧の逐次表示など）がUX向上に直結し、2026年はこれをAPI層でどう表現するか（tRPCのsubscriptionやReact 19のuse()フック活用）が議論の中心になっている。

### 4. serverless edge computing 2026

## CTO視点: Serverless Edge Computing 2026

- **ポイント1（コールドスタート撲滅）:** V8 Isolatesベースのランタイム（Cloudflare Workers, Vercel Edge Functions等）がコールドスタートを1桁ms台まで削減し、フルサーバーレスでもリアルタイムSSR/API応答が実用レベルに到達している。sumitsugiのような物件検索・フィルタリングAPIは、エッジで実行することでTTFBを大幅短縮できる。
- **ポイント2（データレイヤーのエッジ化）:** D1/Turso/PlanetScale等のエッジネイティブDBが普及し、SQLiteベースのレプリケーションでリージョン跨ぎの読み取りレイテンシがほぼ解消された。ただし書き込み一貫性の設計（特に予約・決済フロー）は依然として慎重な検討が必要。
- **ポイント3（Next.js 16との親和性）:** App RouterのPartial Prerendering (PPR) がエッジランタイムと統合され、静的シェル+動的パーソナライズ（例: ユーザーごとの「引越し費用」表示）を1リクエストで返せるようになった。現行スタックとの相性が良く、移行コストが低い。
- **ポイント4（コスト構造の変化）:** 従量課金のエッジ実行はトラフィックが少ない初期フェーズ（ベータローンチ）で圧倒的にコスト効率が良いが、スケール後は専用インスタンスとのハイブリッド構成の方が安くなるケースが増えている。ローンチ後の閾値監視が重要。
- **ポイント5（可観測性の課題）:** エッジ分散実行はデバッグ・トレーシングの難易度が上がる。OpenTelemetryのエッジ対応が2026年で成熟してきたが、認証・決済など重要フローは引き続き集中ログ基盤への統合が必須。

### 5. authentication security best practices 2026

- **パスキー移行の加速:** パスワードレス認証（WebAuthn/FIDO2ベースのパスキー）が主流化しており、フィッシング耐性の高さから2026年時点では新規サービスのデフォルト認証手段として採用すべき。パスワード＋SMS OTPは依然攻撃対象になりやすく、段階的な移行計画（パスキー優先・パスワードはフォールバック）が現実的。

- **セッション管理とトークンの短命化:** JWTなどのアクセストークンは短寿命化し、リフレッシュトークンローテーション＋デバイスバインディングを組み合わせることで、トークン漏洩時の被害範囲を最小化するのが標準的なプラクティスになっている。

- **多要素認証の高度化:** SMS/メールOTPは依然としてSIMスワップやフィッシングに弱いため、TOTP/認証アプリやハードウェアキー（YubiKey等）への誘導、リスクベース認証（異常ログイン検知に基づく追加認証要求）の導入が重要。

- **ゼロトラスト原則の適用:** 認証成功後も「一度信頼したら永続的に信頼しない」設計、つまり継続的なセッション検証・デバイスフィンガープリンティング・地理的異常検知を組み合わせ、認証の一点突破によるアカウント乗っ取りを防ぐアプローチが広がっている。

- **サードパーティ認証基盤の活用:** 自前で認証ロジックを実装するリスク（実装ミスによる脆弱性）を避け、Auth0/Clerk/Supabase Authなど実績のあるIdPを活用しつつ、要件に応じてOAuth 2.1/OIDCの最新仕様に準拠することが、開発速度とセキュリティのバランスとして推奨される。

### 6. database architecture Prisma Supabase 2026

- **エッジ最適化とコネクションプーリング:** Supabaseの`pgbouncer`統合やPrismaの`driverAdapters`（Prisma 6以降）を使えば、Vercel Edge FunctionsやCloudflare Workersなどのサーバーレス環境でもコネクション枯渇を防ぎつつ低レイテンシを実現できる。うちのようなNext.js物件検索アプリでは、一覧ページのSSRが同時多発するため必須の構成。

- **Row Level Security (RLS) をアプリ層の権限チェックと併用:** SupabaseのRLSでDB側にも「前の住人」「次の住人」ごとのアクセス制御を二重化しておくと、アプリ層のバグがあってもデータ漏洩を防げる多層防御になる。物件の`draft`/`public`ステータス制御にも応用可能。

- **Prisma Accelerate / Read Replicaでの読み取りスケーリング:** 物件検索や一覧表示は読み取り比率が圧倒的に高いため、Prisma Accelerateのキャッシュ機能やSupabaseのRead Replicaを組み合わせることで、書き込み系（引き継ぎ手続き）のDBに負荷をかけずにスケールできる。

- **マイグレーション運用はPrisma Migrateで一本化:** SupabaseのSQL Editorで直接スキーマ変更すると`prisma/schema.prisma`との乖離が発生しやすい。CI上で`prisma migrate deploy`を必須化し、型定義とDBスキーマの整合性を常に保証する運用が2026年のベストプラクティス。

- **pgvectorによる類似物件レコメンド:** SupabaseのpgvectorをPrisma経由で扱う事例が増えており、「次の住人」候補と物件の相性マッチングに応用できる。専用ベクトルDBを別途持たずにPostgres一本で完結できるのが運用コスト面で有利。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Component Model（WASI Preview 2）の標準化が進み、Rustクレート間の連携がFFI経由の複雑なグルーコードなしで可能になりつつある。sumitsugiのような物件検索・フィルタリングロジックを将来的にWASM化する際、moduleの合成コストが大幅に下がる。
- **ポイント2:** `wasm-bindgen`や`wasm-pack`のツールチェーンが成熟し、Rust→WASMのビルド時間とバンドルサイズが継続的に改善。ただしNext.js 16のRSC(Server Components)環境ではWASMモジュールの読み込みタイミングに注意が必要で、クライアント側の重い計算処理（例：画像・PDF生成、間取り図の座標計算）以外には過剰最適化になりがち。
- **ポイント3:** SIMD命令とマルチスレッド（`SharedArrayBuffer`経由）のブラウザ対応がほぼ全モダンブラウザで揃い、画像処理やPDF生成のようなCPU負荷の高い処理でネイティブに近い速度が出せるようになった。現状のPDF出力機能をWASM化すれば、サーバー負荷を減らしクライアント完結できる可能性がある。
- **ポイント4:** JSとWASM間のメモリコピーオーバーヘッドが依然としてボトルネック。小さな関数呼び出しを頻繁に行うユースケース（フォームバリデーションなど）ではJS実装の方が速いケースも多く、「重い一括処理」にのみWASM化を限定するのが2026年時点でも定石。
- **ポイント5:** Rust製WASMのセキュリティ面では、サンドボックス実行によりXSS等の攻撃対象領域が縮小するメリットがあるが、ビルドパイプラインへの依存追加はCI時間とメンテナンスコストを増やすため、現フェーズ（ローンチ準備中でリソース限定）では優先度を下げ、パフォーマンスボトルネックが実測で確認されてから導入検討するのが妥当。

### 8. Next.js App Router patterns 2026

- **サーバーコンポーネント優先の設計:** App Routerでは原則としてServer Componentsをデフォルトとし、`'use client'`は本当にインタラクティブなUIパーツのみに限定することで、バンドルサイズとハイドレーションコストを最小化できる。

- **Partial Prerenderingの活用:** 静的な骨格を即座に配信しつつ、動的部分は`Suspense`境界でストリーミングする構成が2026年時点で主流になり、初期表示速度とパーソナライズの両立が可能になっている。

- **Server Actionsによるフォーム/変更処理の一元化:** APIルートを別途作らずServer Actionsでmutationを完結させることで、コード量削減と型安全性向上が図れる一方、認可チェックを各Action内で明示的に行う規律が必須。

- **キャッシュ戦略の明示化:** `fetch`の暗黙キャッシュ挙動が変わり続けているため、`cacheLife`/`cacheTag`など明示的なキャッシュ制御APIを使い、再検証タイミングをコードで宣言する設計が推奨される。

- **レイアウト単位でのデータ取得最適化:** ネストされた`layout.tsx`ごとに並列データフェッチを行い、ウォーターフォールを避ける設計が定着しており、`loading.tsx`とストリーミングSSRを組み合わせた体感速度改善が標準パターンになっている。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約設計:** Vercel Edge FunctionsはNode.js APIの一部が使えないため、実装前にランタイム制約（メモリ・実行時間・利用可能なAPI）を確認し、重い処理はサーバーレス関数側に分離する設計が重要です。
- **コールドスタート最小化:** Edge Functionsはグローバル分散配置により低レイテンシを実現しますが、依存パッケージを最小限に保ちバンドルサイズを削減することで、さらなる起動遅延の抑制が可能です。
- **ストリーミングレスポンス活用:** LLM連携やSSR時のTTFB改善にはストリーミングレスポンスが有効で、Next.js 16のReact Server Componentsと組み合わせることでユーザー体感速度が大きく向上します。
- **キャッシュ戦略の最適化:** Vercelの`ISR`やEdge Config、KVストレージをEdge Functions内で組み合わせることで、DB往復を減らしつつパーソナライズされたレスポンスを低レイテンシで返せます。
- **リージョン指定の見直し:** ユーザー分布やDB配置に合わせてEdge Functionのリージョンを明示的に指定（`export const preferredRegion`）することで、不要なレイテンシを削減できます。

### 10. TypeScript type safety patterns 2026

- **型推論の強化とconst型パラメータ:** TypeScript 5.x以降の`const`型パラメータや`satisfies`演算子の活用により、型の広範化を防ぎつつ推論精度を高める書き方が標準化しつつある。sumitsugiのような`'draft' | 'public'`といったUnion型を扱う箇所では、`satisfies`を使うことで意図しない型の緩みを防げる。

- **Zodなどのスキーマファーストな型安全性:** ランタイムバリデーションとコンパイル時型を一致させる「スキーマファースト」アプローチが主流に。当プロジェクトでも境界層（フォーム入力・API）でZodスキーマを使い、`z.infer`で型を導出することで二重管理を防いでいる。

- **Branded Types / Nominal Typingの普及:** `id: string`のような曖昧な型を`PropertyId`や`UserId`のようなブランド型で区別するパターンが、大規模アプリの型安全性向上策として定着してきている。物件IDとユーザーIDの取り違えなど、実行時まで気づかないバグをコンパイル時に検出できる。

- **Template Literal Typesによるドメイン固有の型安全性:** ルーティングパスやCSSクラス名など文字列ベースのAPIに対し、Template Literal Typesで構造を型レベルで表現する手法が広がっている。Next.js App Routerのパス（`src/app/properties/[id]`等）の型安全な生成にも応用可能。

- **strictな型チェックとリンティングの自動化:** `noUncheckedIndexedAccess`や`exactOptionalPropertyTypes`など、より厳格なtsconfigオプションを有効化するプロジェクトが増加。CI上でのビルド必須化（当プロジェクトのBuild Integrity方針と同様）が、型安全性を実質的に担保する前提として重視されている。
