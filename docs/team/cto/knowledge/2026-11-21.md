# CTO Knowledge - 2026-11-21

## Daily Update (2026-11-21)

### 1. Next.js performance optimization 2026

- **ポイント1（部分プリレンダリング/PPR の本格採用）:** Next.js 16ではPartial Prerenderingが安定版となり、静的シェルを即時配信しつつ動的部分をストリーミングすることで、初期表示速度（TTFB/LCP）を大幅に改善できる。既存ページを全面SSRからPPRへ移行する際は、Suspense境界の設計を見直す必要がある。

- **ポイント2（Turbopackによるビルド高速化）:** Turbopackがデフォルトビルダーとなり、開発時のHMRおよび本番ビルド時間がWebpack比で数倍高速化される。CI上の`bun run build`時間短縮にも直結するため、大規模化してきたsumitsugiのコードベースでは特に効果が大きい。

- **ポイント3（React Server Components最適化とバンドル削減）:** 'use client'境界を最小限に絞り、データ取得をServer Componentsに集約することでクライアントJSバンドルを削減できる。`src/components/listing/`配下などインタラクティブ性の低いコンポーネントはServer Component化を優先すべき。

- **ポイント4（画像・フォント最適化の自動化）:** `next/image`のAVIF優先配信とレイアウトシフト抑制、`next/font`によるフォントのセルフホスティングが標準化され、Core Web Vitals（特にCLS）改善がほぼ自動で得られる。物件写真を多用するsumitsugiのようなサービスでは画像最適化のROIが特に高い。

- **ポイント5（キャッシュ戦略の明示化）:** Next.js 16では`fetch`のキャッシュ挙動がより明示的になり、`cache: 'force-cache'`や`revalidate`タグを意図的に設計しないとキャッシュミスが増える傾向がある。物件一覧・詳細ページなど更新頻度が異なるデータには、タグベースの再検証（`revalidateTag`）を使い分けるべき。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではRSCのストリーミングSSRがデフォルト前提になり、`loading.tsx`やSuspenseバウンダリの粒度設計がパフォーマンスの肝になっている。sumitsugiの物件一覧・詳細ページでは、画像やレビューなど遅延性の高いデータ取得をSuspenseで分割し、初期HTMLを高速に返す設計が有効。

- **ポイント2:** Server Actionsとストリーミングの組み合わせにより、フォーム送信後の部分再検証（`revalidatePath`/`revalidateTag`）がより細粒度になってきている。引越し費用の申込みフローなど多段階フォームでは、各ステップごとに必要な部分だけ再フェッチする設計が応答性を左右する。

- **ポイント3:** クライアントバンドルサイズの削減が依然最大の利点で、`'use client'`境界を必要最小限に絞ることが重要。前の住人プロフィールや活動歴のような静的に近い表示部分はServer Componentに留め、インタラクティブなUI（フィルター、チャット等）だけをクライアント化するのが2026年のベストプラクティス。

- **ポイント4:** キャッシュ戦略（Full Route Cache / Data Cache）とストリーミングの相互作用が複雑化しており、`dynamic = 'force-dynamic'`や`fetch`のcacheオプションの誤用でTTFBが悪化するケースが増えている。公開/非公開（draft/public）のステータス切り替えがあるページでは、キャッシュ無効化のタイミングを明示的に設計すべき。

- **ポイント5:** エラーバウンダリとストリーミングの組み合わせ（`error.tsx`がストリーム中の例外をどう扱うか）が運用上の落とし穴になりやすい。決済や法務確認が絡む機能（ベータローンチ前のブロッカー領域）では、部分的な失敗がユーザーに不完全な状態を見せないよう、ストリーミング境界ごとのフォールバックUIを明示的にテストする必要がある。

### 3. API design REST GraphQL tRPC 2026

**ポイント1:** tRPCはTypeScriptモノレポ内のフルスタック開発で定番化しており、Next.js App Router構成ではAPI RouteをtRPCプロシージャに置き換えることでクライアント・サーバー間の型安全性をコード生成なしで確保できる——sumitsugiのような単一リポジトリ構成に特に適している。

**ポイント2:** GraphQLはマイクロサービス統合や複数クライアント（Web/モバイル/パートナーAPI）が絡む場面で依然優位だが、単一フロントエンド+単一バックエンドのプロダクトではオーバーエンジニアリングになりやすく、2026年の潮流としては「必要な場所にだけ使う」選択的採用が主流。

**ポイント3:** REST APIはWebhookや外部連携（決済、物件データ連携など）の標準として残り続けており、OpenAPI 3.1 + Zodスキーマからの自動生成で型とドキュメントを同期させる手法が定着——sumitsugiの標準に合致するアプローチ。

**ポイント4:** 2026年はAPI設計における「AIエージェント消費者」への対応が新たな軸——LLMエージェントがAPIを直接叩くケースが増え、冗長で自己説明的なエラーメッセージとスキーマ（JSON Schema/Zod）の明示性がUX設計と同等に重要視されている。

**ポイント5:** パフォーマンス面では、tRPC/GraphQLいずれもN+1問題やオーバーフェッチを防ぐためのDataLoaderパターンやバッチング（React Query/tRPCのbatch link）の活用が必須ベストプラクティスとして定着している。

### 4. serverless edge computing 2026

**ポイント1:** エッジでのコールドスタートがさらに短縮され（V8 isolate起点のランタイムが主流化）、本番APIのレイテンシSLAを東京リージョン単体ではなくグローバルエッジ分散で担保する構成が標準化している。sumitsugiのようなNext.js App Routerベースの物件検索・一覧表示は、エッジでのSSR/ISRキャッシュと組み合わせることでTTFBを大きく改善できる。

**ポイント2:** エッジ上でのデータベースアクセス（エッジ対応Postgres/SQLiteレプリカ、KVストア）が成熟し、エッジFunctionからリージョンDBへのレイテンシ往復が課金・体験両面のボトルネックになりにくくなっている。物件データのような読み取り頻度が高くドラフト/公開の整合性管理が必要な領域では、エッジKVでの読み取りキャッシュ＋オリジンでの書き込み確定という分離設計が有効。

**ポイント3:** WASMベースのランタイム（エッジ関数のサンドボックス実行）が一般化し、Node.js APIへの依存を減らしたコードがポータビリティと起動速度の両方で有利になる。認証ロジックや画像処理など重い処理は、エッジ関数の実行時間・メモリ制限を踏まえてオリジン側に残す判断が重要。

**ポイント4:** エッジでの可観測性（分散トレーシング、エッジ単位のメトリクス）がボトルネックになりやすく、リージョンをまたぐデバッグの難易度が上がっている。本番導入前にエッジ特有のログ・トレース収集基盤を用意しないと、障害時の原因特定コストが跳ね上がる。

**ポイント5:** コスト構造がリクエスト数・実行時間課金からエッジキャッシュヒット率依存にシフトしており、キャッシュ戦略（stale-while-revalidate、タグベース無効化）がインフラコストと体験品質を同時に左右する主要レバーになっている。

### 5. authentication security best practices 2026

- **パスキー/FIDO2が標準化：** パスワードレス認証（WebAuthn/Passkeys）が主流になり、フィッシング耐性のある認証がデフォルトとなっている。sumitsugiでも将来的なログイン導入時はパスキー対応を優先すべき。

- **認可の粒度管理：** 認証だけでなく「誰が何にアクセスできるか」のきめ細かい認可制御（RBAC/ABAC）が重視され、特に`seller`/`buyer`といったロール分離がある本サービスでは重要。

- **トークン管理のベストプラクティス：** JWTの短命化・リフレッシュトークンのローテーション・HttpOnly+Secure Cookieでの保管が標準。`localStorage`への生トークン保存は避けるべき。

- **CSRF/XSS対策の継続的強化：** Next.js App RouterのServer Actionsを使う場合でも、入力検証（Zod）とCSP設定は必須。特商法表記など法務確認前のベータローンチでは、個人情報保護の観点からセッション管理の脆弱性診断が推奨される。

- **多要素認証（MFA）のUX最適化：** セキュリティとUXのバランスが鍵。リスクベース認証（異常ログイン時のみMFA要求）により、通常利用時の摩擦を減らしつつ安全性を確保する手法が2026年の主流アプローチ。

### 6. database architecture Prisma Supabase 2026

- **ポイント1:** Supabaseのブランチング機能（Preview Branches）とPrisma Migrateの組み合わせが2026年の標準になりつつあり、PR単位でDBスキーマを分離検証できるため、本番前のマイグレーション事故を大幅に減らせる。
- **ポイント2:** PrismaのRust不要化（Query Compiler/TypeScriptネイティブ化）によりコールドスタートが改善され、Supabase Edge FunctionsやVercel Edgeとの統合がしやすくなっている。sumitsugiのようなサーバーレス構成では特に恩恵が大きい。
- **ポイント3:** Row Level Security (RLS) をPrismaのスキーマレベルでは表現できないため、認可ロジックはSupabase側のRLSポリシーで一元管理し、Prisma側はあくまで型安全なクエリビルダーとして使う役割分担が実務上のベストプラクティスになっている。
- **ポイント4:** Connection Pooling（PgBouncer/Supavisor）の設定ミスがサーバーレス環境でのDB接続枯渇の主因になりやすく、`DATABASE_URL`と`DIRECT_URL`を適切に分離（マイグレーション用と実行時用）することが必須。
- **ポイント5:** Supabaseのリアルタイム機能（Realtime/Postgres Changes）を使う場合、Prismaのマイグレーションで生成されるテーブルにpublicationを明示的に設定する必要があり、これを忘れるとリアルタイム通知が静かに失敗するため、マイグレーションスクリプトに組み込んでおくと安全。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** Wasmコンポーネントモデルの標準化が進み、Rust製WasmモジュールをWASI Preview 2経由で言語非依存に組み合わせられるようになった。マイクロサービスの一部をWasmサンドボックスで動かすアーキテクチャが現実的な選択肢になっている。
- **ポイント2:** `wasm-bindgen`や`wasm-pack`のビルドパイプラインが成熟し、Rust→Wasmのバンドルサイズ最適化（`wasm-opt`、LTO、`opt-level="z"`）が標準化。SSR/CSR混在のNext.jsアプリでも数十KB台の軽量モジュールとして配置しやすくなった。
- **ポイント3:** WasmGC（Garbage Collection提案）のブラウザ実装が進み、RustだけでなくGC言語ともWasm上で相互運用しやすくなった一方、Rustは所有権モデルのおかげでGCオーバーヘッドなしの高速パスを維持できる点が差別化要因。
- **ポイント4:** エッジコンピューティング（Cloudflare Workers、Fastly Compute等）でRust+Wasmがコールドスタート最速の選択肢として定着。弊社の物件検索や画像処理ロジックをエッジで動かす場合、Node.jsより1桁速い起動時間が見込める。
- **ポイント5:** SIMD命令とマルチスレッド（`SharedArrayBuffer`経由）のサポートが広範なブラウザで有効化され、画像のリサイズ・PDF生成など計算負荷の高い処理をクライアント側Rust/Wasmにオフロードしやすくなった。CPU負荷をサーバーからクライアントに移すコスト削減策として検討価値あり。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の本格運用:** Next.js 16ではPPRが安定版となり、静的シェルを即時配信しつつ動的部分のみストリーミングする構成が標準化。本プロジェクトの`properties/`一覧ページのようにSEO要件がある静的要素と、在庫・空き状況などのリアルタイムデータが混在するページで特に効果が大きい。

- **Server Actionsのセキュリティ境界強化:** `use server`関数が暗黙的に公開APIエンドポイントになる点が広く認識され、認可チェックとZodによる入力検証をAction内部で必須とする運用が定着。`src/contexts/auth-context.tsx`経由のセッション検証をServer Action側でも必ず再実施する設計が推奨される。

- **キャッシュ戦略の明示化（`cacheLife`/`cacheTag`):** 従来の暗黙的キャッシュから、`use cache`ディレクティブと明示的なキャッシュプロファイル指定への移行が進んでいる。物件データのように更新頻度が異なるコンテンツ（物件詳細は長め、空き状況は短め）を細かく制御できる。

- **Route Handlersの薄層化とレイヤードアーキテクチャ:** App RouterのRoute Handlers（`app/api/`）はルーティングと検証のみに留め、ビジネスロジックは`src/lib/`のサービス層に委譲する分離が2026年のベストプラクティスとして広く採用。テスト容易性とBuild Integrity（型整合性チェック）の両立に有効。

- **Turbopackのビルド標準化:** Next.js 16でTurbopackがデフォルトビルドツールとなり、`bun run build`の実行速度が大幅改善。ただし一部のWebpack専用プラグインとの互換性問題が残るため、移行前にビルド成果物の差分確認が必要。

### 9. Vercel Edge Functions optimization 2026

- **エッジランタイムの制約を前提にした設計:** V8 isolateベースのため、Node.js APIの一部（fsやネイティブモジュール）が使えない点を踏まえ、認証チェックやリダイレクトなど軽量なロジックのみをEdge Functionsに置き、重い処理はServerless/Node runtimeに委譲する境界設計が重要。

- **Cold Start最小化とバンドルサイズ管理:** Edge Functionsはコールドスタートが速いのが利点だが、依存パッケージが肥大化するとバンドルサイズ上限（1-4MB程度）に抵触しやすいため、tree-shaking可能な軽量ライブラリの選定とdynamic importの活用が性能とコストの両面で効く。

- **キャッシュ戦略の高度化（ISR/Data Cache併用）:** Edge Middlewareでのレスポンスキャッシュと、Next.js 16のData Cache/Partial Prerenderingを組み合わせることで、動的パーソナライズ（住所検索・地域別表示など）を保ちながらTTFBを短縮できる。sumitsugiのような物件検索UXでは地域別エッジキャッシュが有効。

- **オブザーバビリティの確保:** Edge環境はログ・トレースの取得がNode環境より制限されるため、Vercelのログドレインやトレース連携を初期段階から組み込み、障害時の原因特定コストを下げておく必要がある（本番ローンチ前に整備すべき項目）。

- **コストとレイテンシのトレードオフ最適化:** Edge Functionsは実行時間課金が細かく、呼び出し頻度が高いAPI（物件一覧取得など）では段階的にEdgeへ移行しつつ、実測レイテンシ改善とコスト増加のバランスをモニタリングしながら適用範囲を広げるアプローチが実用的。

### 10. TypeScript type safety patterns 2026

**ポイント1:** Zodなどのスキーマライブラリでランタイム検証と型推論を統合し、`z.infer<typeof schema>`でAPI境界の型安全性を保証するパターンが標準化している。

**ポイント2:** `satisfies`演算子の活用が広がり、型の widening を防ぎつつリテラル型の恩恵を受けられるため、設定オブジェクトや定数定義で型安全性と推論精度を両立できる。

**ポイント3:** Branded types（nominal typing）でID型やユニット付き数値を区別し、`string`同士の誤代入のようなコンパイル時に防げるはずのバグを型レベルで排除する手法が一般化している。

**ポイント4:** `tRPC`やGraphQL Codegenのようなエンドツーエンドの型生成ツールにより、フロントエンドとバックエンド間で型を自動同期し、APIスキーマ変更時の型不整合を即座に検出できる。

**ポイント5:** Discriminated Union（タグ付きユニオン）による状態管理で、`exhaustive switch`と`never`型チェックを組み合わせ、新しい状態追加時にコンパイルエラーで漏れを検知するパターンが定着している。
