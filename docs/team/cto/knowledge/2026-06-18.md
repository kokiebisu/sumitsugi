## Daily Update (2026-06-18)

### 1. database architecture Prisma Supabase 2026

- **ポイント1（Prisma 7系のPostgreSQLネイティブ最適化）:** Prisma 7では`driverAdapters`がデフォルト化され、Supabaseのpgbouncer経由のコネクションプーリングと組み合わせた際のレイテンシが大幅改善されており、sumitsugiのようなサーバーレス（Vercel）+ Supabase構成では`DATABASE_URL`をプール用、`DIRECT_URL`をマイグレーション用に分離する設計がデフォルトベストプラクティスになっている。
- **ポイント2（Row Level Security中心の設計シフト）:** SupabaseのRLSをアプリ層の認可と二重化せず「唯一の真実」として使う設計が2026年の主流になりつつあり、物件ステータス（draft/public）のような可視性制御もPrismaのクエリ条件ではなくRLSポリシーに集約することで、APIエンドポイント追加時の認可漏れリスクを構造的に減らせる。
- **ポイント3（Prisma Migrate + Supabase Branchingの併用）:** Supabaseのデータベースブランチ機能とPrisma Migrateを組み合わせ、PRごとに本番スキーマのクローンでマイグレーションを検証するフローが2026年標準化しており、`bun run build`前のCIにマイグレーションのドライランを組み込むことでスキーマ変更による本番障害を未然に防げる。
- **ポイント4（Edge Function + Prisma Accelerateの分離アーキテクチャ）:** Supabase Edge Functions（Deno）からは直接Prismaクライアントを使わずPrisma AccelerateやHTTP経由のデータアクセス層を挟む構成が推奨されるようになっており、sumitsugiでチャット通知や決済webhookをEdge化する場合はこの分離を前提に設計すべき。
- **ポイント5（型安全な末端までの一貫性）:** PrismaのスキーマからSupabaseの生成型・ZodスキーマまでをCIで自動同期する「スキーマ単一ソース化」がデファクト化しており、`status: 'draft' | 'public'`のようなUnion型を変更する際は、Prismaスキーマ→Zodバリデーション→フロントエンド型まで一括でgrepし整合性を取る運用が必須になっている。

## Daily Update (2026-06-18)

### 1. Next.js performance optimization 2026

- **Turbopackの本格採用とビルド高速化:** Next.js 16ではTurbopackがデフォルトのバンドラーとなり、開発時のHMRや本番ビルド時間が大幅に短縮されている。CIのビルド時間短縮は開発体験だけでなくデプロイサイクルの高速化にも直結するため、移行コストを払う価値が高い。

- **Partial Prerendering (PPR) とCache Componentsの活用:** 静的な部分は事前レンダリングしつつ、動的な部分のみをストリーミングするPPRが安定し、`use cache`ディレクティブによる明示的キャッシュ制御（Cache Components）が主流になっている。物件一覧ページのような「静的な骨組み＋動的なステータス表示」構成に特に有効。

- **React Server Componentsでのデータフェッチ最適化:** クライアントへのJS転送量を減らすRSC中心の設計が定着し、`loading.tsx`によるストリーミングUIとSuspense境界の細分化がLCP改善の標準手法になっている。一覧画面のスケルトン表示などUXとパフォーマンスを両立できる。

- **画像・フォント最適化の自動化強化:** `next/image`のAVIF優先配信やフォントの自動セルフホスティングがデフォルト挙動として強化され、CLS・LCPの改善が設定不要で得られるようになった。物件写真が多いプロダクトでは画質と転送量のバランス調整が依然重要。

- **Edge RuntimeとISRの併用によるTTFB短縮:** 認証不要な公開ページ（`public`物件詳細など）はEdge Runtime + ISRで配信し、認証必須ページ（アカウント関連）はNode.js Runtimeに残すハイブリッド構成が、コストとレイテンシのバランスとして2026年のベストプラクティスになっている。

### 2. React Server Components streaming 2026

- **段階的ハイドレーションの標準化:** Next.js 16ではRSCのストリーミングとSelective Hydrationが標準パイプラインに統合され、ページ全体のJSバンドル待ちなしに重要なUIから先に操作可能になる。本プロジェクトの物件一覧・詳細ページのようなLCPが重視される画面では、初期ペイロード削減に直結する。

- **Suspense境界の粒度設計が性能を左右する:** 部屋詳細・価格情報・前の住人レビューなど非同期データ取得が混在する画面では、Suspense境界を細かく分けるほどストリーミングの恩恵が大きいが、過度な分割はウォーターフォール（直列フェッチ）を生みやすく、`Promise.all`での並列フェッチ設計とのバランスが必要。

- **キャッシュ戦略の複雑化:** RSCのストリーミングはCDN/Edgeキャッシュとの組み合わせで真価を発揮するが、`'use cache'`ディレクティブやper-request revalidationの設定ミスは古いステータス（`draft`/`public`）の物件情報が表示されるバグに直結しやすく、ステータス変更系の機能では明示的なrevalidateTagの運用が必須。

- **Server Actions × ストリーミングのエラーハンドリング:** フォーム送信や引越し費用計算など多段階フローでServer Actionsを使う場合、ストリーミング中の部分的失敗（一部のSuspense境界だけエラー）をユーザーに分かりやすく見せるUIパターン（インラインエラー＋再試行）が2026年のベストプラクティスとして定着してきている。

- **テスト・デバッグの難易度上昇:** ストリーミングSSRはE2EテストでのタイミングやSuspense境界のレンダリング順序がフレーキーの原因になりやすいため、Playwrightでの待機戦略（`waitForSelector`より状態ベースの待機）を徹底する必要がある。本プロジェクトのE2E方針（必須領域への適用）にも影響する論点。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCの採用が拡大しているが、これは型安全性を重視するTypeScriptフルスタック構成（Next.js + tRPC）に最適。sumitsugiのようなNext.js App Router構成では、APIルートをtRPCに置き換えることでクライアント・サーバー間の型を自動同期でき、Zodバリデーションとの統合も自然。

- **ポイント2:** GraphQLは複雑なクエリ要件（関連データの一括取得、フィールド選択の柔軟性）がある場合に強みを持つが、単純なCRUD中心のプロダクトではオーバーヘッドになりやすい。物件情報・引っ越し費用などの比較的シンプルなドメインモデルであれば、RESTかtRPCで十分なケースが多い。

- **ポイント3:** RESTは依然としてエコシステムの広さ・キャッシュ戦略（HTTPキャッシュ、CDN活用）の面で優位性があり、公開APIや外部連携が必要な場合は標準的なREST設計が無難。社内向けAPIとパートナー向け公開APIを分離する設計が2026年のベストプラクティスとして定着しつつある。

- **ポイント4:** 2026年はAPI Gatewayレベルでのスキーマ駆動開発（OpenAPI/GraphQL SDLからの自動生成）がさらに浸透し、フロントエンド・バックエンド間の契約をコードではなくスキーマファイルで管理する流れが加速している。

- **ポイント5:** エンドツーエンドの型安全性とZodによる入力検証を組み合わせるアーキテクチャ（tRPC + Zod + Next.js Server Actions）が、小〜中規模チームでの開発速度とランタイム安全性の両立に最も適しており、sumitsugiの現フェーズ（MVP完了・ローンチ準備）にはこの構成の継続が合理的と考える。

### 4. serverless edge computing 2026

- **エッジでのAI推論実行:** 2026年は軽量LLMやONNX最適化モデルをCDNエッジ（Cloudflare Workers AI、Vercel Edge Functions等）で直接推論させる構成が主流化し、レイテンシを数十ms単位で削減できる。sumitsugiのような不動産検索でも、画像認識やレコメンドの一次処理をエッジ側に寄せる選択肢が出てくる。

- **コールドスタート問題の実質解消:** V8 isolateベースの実行環境やWasmランタイムの進化で、コールドスタートが1ms未満になりつつあり、サーバーレスでも常時起動サーバー並みの応答性が得られるようになってきている。Next.js 16のEdge Runtimeもこの流れに乗っており、API Routesの一部をEdgeに移行する判断がしやすくなった。

- **データの地理分散とエッジDB:** Turso、PlanetScale、Cloudflare D1のようなエッジネイティブDBが普及し、読み取りをユーザーに最も近いリージョンから返す構成が標準になってきた。物件検索のような読み取り中心のワークロードはこの恩恵を受けやすく、グローバル展開時のレイテンシ戦略として検討価値がある。

- **コスト構造の変化:** 従量課金モデルの精度が上がり、リクエスト単位ではなくCPU時間単位の課金が一般化したことで、軽い処理はサーバーレス、重い処理（PDF生成、画像処理等）は専用コンテナという「ハイブリッド配置」がコスト最適化の定石になっている。

- **観測性とデバッグの成熟:** OpenTelemetryのエッジ対応が進み、分散トレーシングがサーバーレス環境でも実用レベルになった。これまで「エッジは見えづらい」という弱点が改善され、本番障害の原因特定がしやすくなっている点は採用判断における大きな後押し材料。

### 5. authentication security best practices 2026

- **ポイント1（パスキー/FIDO2の標準化）:** 2026年時点でパスキーがパスワードレス認証の主流となり、フィッシング耐性のある公開鍵暗号方式がデフォルト選択肢になっている。本サービスでも前の住人・次の住人双方のログイン体験を簡素化しつつセキュリティを強化できる。

- **ポイント2（多層防御とリスクベース認証）:** 単純な2FAではなく、デバイスフィンガープリント・行動分析・地理的異常検知を組み合わせたリスクベース認証（条件付きMFA）が標準になりつつある。不動産取引のような高額決済が絡むフローでは、ログイン時より「契約・決済確定時」にリスクスコアに応じた追加認証を挟む設計が有効。

- **ポイント3（トークン管理とゼロトラスト）:** JWTなどのセッショントークンは短命化・ローテーション必須が常識化しており、リフレッシュトークンの保管場所（httpOnly + Secure Cookie等）の見直しが継続的な脆弱性対策の要。CLAUDE.mdの「セッショントークン保管」関連の法務指摘とも直結する論点。

- **ポイント4（サプライチェーン/依存パッケージ監査）:** 認証ライブラリ自体への攻撃（npmパッケージ乗っ取り等）が増加傾向にあり、認証関連の依存パッケージはバージョン固定・SBOM管理・定期的な脆弱性スキャン（`bun audit`相当）が必須になっている。

- **ポイント5(個人情報保護とコンプライアンス):** 本人確認（eKYC）を伴う認証フローでは、保存データの暗号化だけでなく「保持期間の最小化」と「削除請求への対応」が法務要件として強化されており、ベータローンチ前のプライバシーポリシー策定と合わせて設計段階から組み込むべき。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASMのGCサポート（WasmGC）が主要ブラウザで安定し、Rustでも`wasm-bindgen`を介さない軽量な相互運用が進んでいるが、Rustは元来GCレス設計のため恩恵は限定的で、依然としてC/C++同等の低オーバーヘッド実行が強み。
- **ポイント2:** Component Model（WASI Preview 2/3）の普及により、Rustで書いたWASMモジュールを言語を問わず組み合わせられるようになり、サーバーレスやプラグイン基盤での採用が加速している。
- **ポイント3:** SIMD128やマルチスレッド（共有メモリ+Web Workers）の標準化が進み、Rust + wasm-packで画像処理・動画変換・物理演算など計算負荷の高い機能をフロントエンドにオフロードする事例が増加。
- **ポイント4:** バイナリサイズ最適化（`wasm-opt`, `twiggy`での解析、`opt-level = "z"`設定）がパフォーマンスと同等に重視され、初回ロード時間がコア体験のKPIになっている。
- **ポイント5:** Edge Computing（Cloudflare Workers, Fastly Compute@Edge）でRust製WASMをデフォルト採用するケースが増え、コールドスタートの速さとサンドボックス安全性がNode.js代替として評価されている。

### 8. Next.js App Router patterns 2026

- **ポイント1:** Partial Prerendering（PPR）が安定版となり、静的シェルと動的コンテンツを1ページ内で共存させやすくなった。物件一覧ページのような「ヘッダーは静的・在庫データは動的」という構成に最適。
- **ポイント2:** Server Actionsのキャッシュ無効化（`revalidateTag`/`revalidatePath`）の粒度がより細かく制御できるようになり、フォーム送信後の即時反映とCDNキャッシュ効率を両立しやすい。物件公開/非公開切り替えのようなステータス変更系に有効。
- **ポイント3:** `use cache`ディレクティブ（Cache Components）によりコンポーネント単位でのキャッシュ戦略が明示的に書けるようになり、データフェッチの責務がコンポーネント内に閉じる設計が主流化している。
- **ポイント4:** Streaming SSRとSuspenseバウンダリの粒度設計がパフォーマンスチューニングの中心になっており、LCPに影響する箇所（物件詳細の画像・価格情報）を優先ストリーミングする設計が定石化している。
- **ポイント5:** Route Handlers と Server Actions の責務分離（外部API連携はRoute Handlers、フォーム処理はServer Actions）がベストプラクティスとして定着し、型安全性確保のためZodスキーマを境界に置くパターンが標準になっている。

### 9. Vercel Edge Functions optimization 2026

- **エッジファースト・キャッシング戦略:** Vercel Edge Functionsでは`stale-while-revalidate`とEdge Configを組み合わせることで、グローバルに分散したリクエストへの応答を数十ms単位まで短縮できる。sumitsugiの物件検索や一覧ページのような読み取り頻度の高いエンドポイントに有効。

- **コールドスタート対策としての軽量ランタイム維持:** Edge RuntimeはNode.js APIの一部しか使えない制約があるが、その分バンドルサイズを小さく保てばコールドスタートがほぼ発生しない。依存ライブラリを増やす際はEdge互換性とバンドルサイズへの影響を必ず確認すべき。

- **ミドルウェアでの認証・リダイレクト処理の集約:** 認証チェックやA/Bテストの振り分けをEdge Middlewareに寄せることで、オリジンサーバーへのリクエスト数を減らしコストとレイテンシを同時に削減できる。`auth-context`周りの保護ルート判定をミドルウェア層に移す余地がある。

- **Streaming SSRとの併用によるTTFB改善:** Next.js 16のApp RouterではEdge上でのStreaming Server Componentsが標準化されており、データ取得が遅い箇所（例: 物件詳細のレビュー数取得など）を`Suspense`で分離することでファーストバイトまでの時間を短縮できる。

- **リージョン指定とデータ近接性の最適化:** Edge Functionsはデフォルトで全リージョン実行だが、DB（例: Supabase/Postgres）のリージョンに近いEdgeロケーションを明示指定することで、DB往復によるレイテンシ増を回避できる。グローバル展開前に日本リージョン優先設定を検討する価値がある。

### 10. TypeScript type safety patterns 2026

- **型推論優先の設計:** 明示的な型注釈よりも、TypeScriptのコンテキスト依存型推論（`satisfies`演算子、`const`型パラメータ）を活用し、型情報の重複を避けつつ安全性を保つパターンが主流になっています。
- **スキーマファースト検証:** Zodなどのランタイム検証ライブラリで型を定義し、`z.infer`で型を導出する「スキーマ・トゥ・タイプ」アプローチが、システム境界（API入力・フォーム送信）での型安全性を担保する標準手法として定着しています。
- **Discriminated Unionによる状態管理:** `'draft' | 'public'`のようなUnion型をオブジェクトのタグ付きフィールドとして扱い、`switch`文での網羅性チェック（`never`型での悉皆性検証）を組み合わせることで、状態追加時の漏れをコンパイル時に検出できます。
- **テンプレートリテラル型とブランド型:** ルーティングパスやID（例: 物件IDとユーザーIDの混同防止）に対し、テンプレートリテラル型やブランド型（nominal typing）を使うことで、構造的に同じ`string`型同士の意図しない混在をコンパイル時に防ぐ手法が広がっています。
- **AIコード生成との型安全性の両立:** LLMによるコード自動生成が増える中、厳格な`strict`モード・ESLintの型チェックルール・CI内での`bun run build`必須化など、生成コードの型崩れを早期検知する仕組みがチーム運用の前提になっています。
