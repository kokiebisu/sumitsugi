# CTO Knowledge - 2026-05-30

## Daily Update (2026-05-30)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを劇的に削減できる。`'use client'`ディレクティブは本当に必要な葉コンポーネントのみに絞り、データフェッチはサーバー側で完結させることが2026年のベストプラクティス。

- **Partial Prerendering (PPR) による静的・動的の最適な融合:** Next.js 15以降で安定化したPPRにより、1ページ内で静的シェルと動的コンテンツを分離してServeできる。TTFBを静的サイト並みに保ちながら、パーソナライズコンテンツも配信可能。

- **`next/image` と `next/font` の適切な設定:** 画像はCDN経由のWebP/AVIF自動変換と`sizes`属性の最適化が必須。フォントはCSSサブセット化とdisplay swapで、CLS（累積レイアウトシフト）を0に近づけることが求められる。

- **Server Actions のバンドル最適化:** Server ActionsはPOST通信になるため、過剰に使うとウォーターフォールが発生する。バッチ処理可能な操作はまとめ、キャッシュ戦略（`revalidateTag` / `revalidatePath`）と組み合わせてAPIラウンドトリップを最小化する。

- **Edge RuntimeとNode.js Runtimeの使い分け:** 認証チェック・リダイレクト・A/Bテストなど低レイテンシが命のミドルウェアはEdge Runtimeが有効。ただしEdgeはNode.js APIが使えないため、DBアクセスやファイルI/Oを含む処理は無理にEdgeに載せず、Node.jsランタイムのキャッシュ活用で十分なケースが多い。

### 2. React Server Components streaming 2026

- **ポイント1:** RSC + Suspenseによるストリーミングは2026年において事実上の標準となり、Next.js App RouterのPPR（Partial Prerendering）が静的シェルと動的コンテンツのハイブリッド配信を本番レベルで実現している。

- **ポイント2:** `use cache` ディレクティブ（Next.js 15+）とサーバーコンポーネントの組み合わせにより、データフェッチのキャッシュ粒度が細かく制御できるようになり、従来の`fetch`レベルのキャッシュより大幅にパフォーマンスチューニングが容易になっている。

- **ポイント3:** Turbopackの安定化により、RSCを多用する大規模プロジェクトでのビルド・HMT速度が大幅改善され、開発者体験のボトルネックが解消されつつある。

- **ポイント4:** React 19の`useOptimistic`と`useActionState`を組み合わせたServer Actionsパターンが普及し、クライアント状態管理ライブラリ（Redux等）なしに楽観的UIを実装できるアーキテクチャが主流になってきている。

- **ポイント5:** ストリーミングの落とし穴として、過度な`Suspense`境界の細分化によるウォーターフォールが問題になるケースが増加しており、`preload`パターンや並列データフェッチ設計をアーキテクチャレベルで規約化することが重要。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭とフルスタック型安全性:** 2026年においてtRPCはNext.js/TypeScriptスタックでのデファクトに近づいており、ランタイムエラーではなくコンパイル時にAPIの型不整合を検出できるため、開発速度と信頼性が大幅に向上する。

- **GraphQLはBFFパターンに特化:** GraphQLはモバイル・マルチクライアント向けのBFF（Backend for Frontend）層として最適化されており、単一サービス間の通信には過剰なケースが多い——オーバーエンジニアリングを避けるためユースケースを明確にすることが重要。

- **REST + OpenAPI 3.1は依然として外部APIの標準:** サードパーティ向けAPIや組織横断の連携ではRESTとOpenAPI仕様が最も広く採用されており、自動SDK生成（例：`openapi-generator`）との組み合わせで開発者体験を高めることが2026年のベストプラクティス。

- **エッジ・ストリーミング対応の重要性:** Server-Sent Events（SSE）やHTTP/3によるストリーミングAPIがAI機能統合で必須となっており、REST/GraphQL問わずエッジランタイム（Cloudflare Workers等）での動作を前提とした設計が求められる。

- **Protocol Buffersの復権:** 内部マイクロサービス間通信ではgRPC/Connect-RPC + Protobufが再評価されており、型安全性・パフォーマンス・スキーマ管理の観点でJSON over HTTPより優位に立つケースが増えている。

### 4. serverless edge computing 2026

- **WebAssembly（Wasm）がエッジのデファクトランタイムへ:** V8 Isolateに加えWasmコンテナが主流となり、コールドスタートがほぼゼロに。Cloudflare Workers・Fastly Compute等でRust/Go製ロジックをネイティブ並みの速度でデプロイできる。

- **AI推論のエッジシフトが加速:** 小型LLM（1B〜7Bパラメータ）をエッジノードで実行するパターンが定着し、レイテンシ削減とデータ主権の両立が可能に。Next.jsのAI Route HandlersをVercel Edgeで動かすユースケースが急増している。

- **ステートフルエッジの台頭（Durable Objects / SQLite at Edge）:** 従来「エッジはステートレス」という制約が崩れ、Cloudflare Durable ObjectsやTurso（libSQL）でエッジ近傍にDBを持つアーキテクチャが現実的になった。セッション管理・リアルタイム同期の設計を根本から見直す必要がある。

- **エッジとオリジンの責務分離がアーキテクチャの核心に:** 認証・A/Bテスト・パーソナライゼーションはエッジ、トランザクション処理・複雑なビジネスロジックはオリジンという分離が定石化。境界の引き方を誤るとデバッグコストが跳ね上がる。

- **可観測性ギャップが最大の運用課題:** 分散エッジ環境ではトレーシングが断片化しやすく、OpenTelemetry + Baselime（Cloudflare Workers向け）などエッジ特化の監視基盤なしに本番運用は困難。ローカル開発時からトレースIDを伝播する設計を徹底すべき。

### 5. authentication security best practices 2026

- **パスキー（Passkeys）の標準採用:** FIDOアライアンスのパスキーが2026年の認証標準となり、パスワードレス認証が主流。Next.jsプロジェクトではWebAuthn APIを直接統合するか、`@simplewebauthn`ライブラリの活用を推奨。

- **トークン寿命の最小化:** アクセストークンは15分以内、リフレッシュトークンはローテーション必須。JWTのブラックリスト管理よりも短命トークン＋Redisベースのセッション管理が実装コストと安全性のバランスが良い。

- **デバイスフィンガープリント＋リスクベース認証:** IPアドレス・デバイス情報・行動パターンを組み合わせたリスクスコアリングで、不審なセッションのみ追加認証を要求。ユーザー体験を損なわずにセキュリティ強度を上げる現実的な手法。

- **サプライチェーン攻撃対策としての依存関係固定:** 認証ライブラリ（NextAuth.js等）は`package.json`でexactバージョン固定＋`bun.lockb`のCIチェックを徹底。2025年以降、OSSライブラリへの悪意あるコード注入事例が急増。

- **セッションIDとCSRFトークンの分離管理:** SameSite=Strict Cookieだけに依存せず、state-changing操作には明示的なCSRFトークン検証を併用。App RouterのServer Actionsでも`headers()`で`Origin`検証を忘れずに実装する。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6.x + Supabase の統合成熟:** Prisma の `@prisma/adapter-pg` による接続プールの最適化が進み、Supabase の Pgbouncer と組み合わせることでサーバーレス環境でのコネクション枯渇問題がほぼ解消された。Edge Functions との相性も大幅に改善されている。

- **Row Level Security (RLS) をアーキテクチャの中核に:** Supabase の RLS をアプリ層のアクセス制御と二重化する設計が標準化されつつある。Prisma 経由でも `SET LOCAL role` でユーザーコンテキストを渡す実装パターンが普及し、セキュリティ境界がDB層まで下りた。

- **Prisma Pulse / Realtime の競合と棲み分け:** Prisma Pulse（CDC ベースのリアルタイム変更検知）と Supabase Realtime（PostgreSQL レプリケーション）が機能的に重複するため、どちらかに統一する設計判断が重要になっている。マルチテナント SaaS では Supabase Realtime + RLS の組み合わせが有利。

- **型安全クエリの限界とローSQL回帰:** Prisma の型推論は強力だが、複雑な集計・全文検索・PostGIS 操作では `$queryRaw` に逃げざるを得ないケースが多い。Drizzle ORM が型安全なまま生 SQL に近い表現力を持つ点で 2025〜2026 年に急速に採用が増えており、新規プロジェクトでは選定の再検討が価値ある。

- **Supabase Auth + Database の統合設計:** `auth.uid()` を外部キー制約と組み合わせて `user_id` カラムに直接紐づける設計が定着。これにより JWT のクレームとDB行の整合性をDB層で保証でき、アプリ層での認可ロジックを大幅に削減できる。

### 7. WebAssembly Rust performance 2026

- **WASIp2（Component Model）の本格普及:** 2026年はWASI Preview 2が主要ランタイム（Wasmtime、WasmEdge）で安定し、RustのWASM向けコンポーネントが標準的なマイクロサービスの配布単位として使われ始めている。コールドスタートがコンテナ比で10〜100倍速い点が特に注目される。

- **SIMD・スレッドサポートの成熟:** Wasm SIMDとshared memoryが主要ブラウザ・ランタイムで揃い、Rustで書いた画像処理・ML推論コードがネイティブに近いスループットを達成できるようになった。`std::simd`との統合も進み、ポータブルなまま高速化が可能。

- **Garbage Collection不要の優位性が際立つ:** RustのゼロコストメモリモデルはWASMにそのまま活きており、GCランタイムを持つGo・C#製WASMに比べてメモリフットプリントが30〜50%小さい。エッジ環境（Cloudflare Workers、Fastly Compute）での採用が加速している理由がここにある。

- **`wasm-bindgen` → `wit-bindgen` へのシフト:** ブラウザ特化の`wasm-bindgen`に加え、Component Model対応の`wit-bindgen`が主流になりつつある。これによりブラウザ外（サーバー・組み込み）でも同一バイナリを再利用でき、開発コストが大幅に下がる。

- **ビルド最適化のベストプラクティスが確立:** `opt-level = 'z'`＋`wasm-opt`（Binaryen）の組み合わせで最大40%のバイナリ削減が定番化。加えて`cargo-component`がビルドパイプラインに組み込まれ、RustエンジニアがWASMを意識せず扱える環境が整ってきた。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの設計:** データフェッチはServer Componentsで完結させ、クライアントへのJS転送量を最小化する。`'use client'`境界はインタラクション必須の末端コンポーネントにのみ付与するのが2026年のベストプラクティス。

- **Partial Prerendering (PPR) の本格採用:** 静的シェルと動的ストリームを同一ルートで共存させるPPRが安定化し、TTFBとFCP両方を改善できる。`<Suspense>`境界の設計がアーキテクチャの核心になっている。

- **Server Actions によるフォーム処理の標準化:** API Routeを介さずServer Actionsで直接ミューテーションを行うパターンが定着。`useActionState`との組み合わせでオプティミスティックUIも簡潔に実装できる。

- **`use cache` / `cacheTag` による細粒度キャッシュ制御:** `fetch`オプション依存から脱却し、関数・コンポーネント単位でキャッシュ戦略を宣言する新APIが主流に。タグベースの`revalidateTag`でオンデマンド無効化が容易になった。

- **Parallel Routes と Intercepting Routes の活用:** モーダルやスライドオーバーをURLに紐づけて実装するパターンが成熟し、ディープリンク可能なUIが標準的な選択肢になっている。本プロジェクトの物件詳細モーダルなどに適用価値が高い。

### 9. Vercel Edge Functions optimization 2026

- **Cold Start の実質ゼロ化:** Edge Functionsは従来のサーバーレスと異なりV8 Isolateベースのため起動オーバーヘッドが1ms以下。2026年時点では、Fluid Compute（動的ルーティング）との組み合わせでウォームインスタンス再利用率がさらに向上し、レイテンシの予測可能性が高まった。

- **Middleware のコスト最適化が最重要課題:** 認証・ABテスト・ジオルーティング等をMiddlewareに集約する設計が主流だが、全リクエストに適用されるため不必要なロジックが含まれるとコストが線形増加する。`config.matcher` で対象パスを厳密に絞ることが必須。

- **Node.js互換APIの拡充とトレードオフ:** 2025〜2026年にかけてEdge Runtimeで利用可能なAPIが大幅拡張されたが、バンドルサイズ上限（1〜4MB）は依然として制約。`fs`依存ライブラリやHeavy ORMはNode.js Runtimeに分離し、Edge側は軽量処理に特化する設計分離が鉄則。

- **ISRとEdge Cachingの組み合わせが最強パターン:** `stale-while-revalidate` ヘッダーとEdge CDNキャッシュを組み合わせることで、動的コンテンツをほぼ静的配信に近い速度で提供できる。特に多言語・パーソナライズ対応では `Vary` ヘッダー設計が性能の分岐点になる。

- **Observabilityの整備が本番運用の前提:** Edge環境では従来のAPMツールが機能しないケースが多く、Vercel Analytics・Datadog Edge Logs・OpenTelemetry対応SDKの導入が不可欠。分散トレーシングIDをリクエストヘッダーで伝播させる設計を最初から組み込むべき。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の普及:** `satisfies` を使うことで型チェックを維持しながら推論された型を保持できる。`as const satisfies Config` パターンが設定オブジェクトの型安全性のデファクトスタンダードになっている。

- **Template Literal Types の実用化:** APIルートやイベント名などを `'GET /users/:id'` 形式で型表現し、コンパイル時にルートの整合性を保証するパターンが成熟した。`tRPC` がその好例。

- **`noUncheckedIndexedAccess` の標準化:** 配列・オブジェクトのインデックスアクセスが `T | undefined` を返すこの設定がチームの標準になりつつあり、`null` 安全性が大幅に向上している。

- **Branded Types によるドメイン安全性:** `UserId` と `ProductId` を `string` として混在させるバグを防ぐため、`type UserId = string & { readonly _brand: 'UserId' }` パターンが実務で定着。Zodの `.brand()` との組み合わせが特に有効。

- **型レベルのZod統合:** `z.infer<typeof Schema>` を単一の真実源とし、バリデーション・型定義・APIスキーマを一元管理するアーキテクチャが主流。手書きの型定義は冗長とみなされる時代に。
