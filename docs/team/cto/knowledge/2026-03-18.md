# CTO Knowledge - 2026-03-18

## Daily Update (2026-03-18)

### 1. Next.js performance optimization 2026

- **React Server Components の徹底活用:** クライアントバンドルサイズを削減するため、データフェッチやロジックはRSCに集約し、`'use client'`はインタラクティブな末端コンポーネントのみに限定する。

- **PPR（Partial Prerendering）の本番投入:** Next.js 15以降で安定化したPPRにより、静的シェルを即座に配信しつつ動的コンテンツをストリーミングする設計が標準になりつつあり、TTFBとLCPを同時に改善できる。

- **`next/image` と `next/font` の完全活用:** 画像の`sizes`属性最適化とサブセット化フォントのpreloadにより、CLS・LCPスコアの大幅改善が見込める。これは計測コストゼロで得られる即効性の高い改善。

- **Route Segment Configによるキャッシュ戦略の精緻化:** `revalidate`・`dynamic`・`fetchCache`をセグメント単位で制御し、エンドポイントの特性（静的/動的/リアルタイム）に応じた最適なキャッシュ層を設計することがパフォーマンスの差別化要因になる。

- **Turbopackへの移行:** Next.js 15でTurbopackがdev安定版となり、大規模プロジェクトではwebpackより最大5倍高速なHMRが実現可能。本番ビルドへの対応も進んでいるため、移行準備を今から進めるべき時期。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化:** 2026年現在、RSCのストリーミングはSuspense境界をコンポーネント単位で細かく設定することで、FCP（First Contentful Paint）を大幅に改善できる。クリティカルパスのUIを先行配信し、重いデータフェッチ部分を後続ストリームに分離するパターンが標準化されている。

- **PPR（Partial Prerendering）との統合:** Next.js 15以降でPPRが安定版となり、静的シェルを即時配信しつつ動的部分をストリームで補完するハイブリッド戦略が主流。これによりTTFB（Time To First Byte）を静的サイト並みに保ちながら動的コンテンツを実現できる。

- **Server Actions + optimistic UI:** Server Actionsとクライアントのoptimistic updateを組み合わせたパターンが成熟し、ストリーミング中のユーザーインタラクションの一貫性確保が重要な設計課題になっている。楽観的更新とサーバー状態の同期ロジックを明示的に管理する必要がある。

- **エッジランタイムでのストリーミング制約:** Cloudflare WorkersやVercel Edge Runtimeでは、Node.js固有のAPIが使えないため、RSCストリーミングのペイロードサイズと接続維持コストに注意が必要。長時間ストリームはエッジより通常のサーバーランタイムが適している。

- **キャッシュ戦略の再設計:** `fetch`のキャッシュタグ機能とストリーミングの組み合わせにより、コンポーネント単位でのキャッシュ無効化が可能になった。ただしストリーム途中でキャッシュミスが発生するとウォーターフォールが再発するため、データ依存関係の事前分析が不可欠。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全性の標準化:** 2026年時点でフルスタックTypeScriptプロジェクトではtRPCがデファクトに近い存在となっており、クライアント・サーバー間のスキーマ共有によりランタイムエラーを大幅に削減できる。Next.js App Routerとの親和性も高く、新規プロジェクトでは積極的に採用すべき。

- **GraphQLの適用範囲の明確化:** GraphQLは「複雑なデータグラフを持つ大規模BFF層」に特化しており、小中規模プロジェクトでのオーバーエンジニアリングリスクが再認識されている。Federation v2とPersistedOperationsが普及し、パフォーマンスと型安全性の課題は概ね解消済み。

- **REST + OpenAPI 3.1の再評価:** AIコードアシスタントとの相性の良さから、OpenAPI仕様駆動開発が見直されている。`zod-openapi`や`hono`のような軽量フレームワークと組み合わせることで、型安全性を維持しながら最小限の複雑さで実装できる。

- **Server Actions / RPC-first設計の普及:** Next.js Server ActionsやHono RPCなど、HTTP層を意識させないRPCスタイルが主流化しつつある。APIをPublic契約として外部公開する必要がない限り、REST設計の厳密な遵守より開発速度を優先するトレードオフが合理的になっている。

- **AIエージェント向けAPI設計の重要性:** MCPやOpenAPIベースのツール定義など、LLMエージェントが消費しやすいAPI設計が新たな要件として浮上。セマンティックな命名・冪等性・明確なエラースキーマが、人間だけでなくAIクライアントのためにも不可欠になっている。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジの標準ランタイムに:** V8 isolatesに代わりWasmがエッジ実行の主流となり、言語非依存・コールドスタートほぼゼロを実現。Cloudflare Workers・Fastly Compute等が本番対応を拡充している。

- **エッジDBとデータローカリティの進化:** Cloudflare D1・Turso（libSQL）・Neon Branchingなどがエッジ近傍での読み書きを可能にし、「エッジでの状態管理不可」という制約が実質的に解消されつつある。

- **AI推論のエッジオフロード加速:** LLMの量子化モデル（GGUF/INT4）をエッジノードで実行するパターンが普及し、レイテンシ削減とデータ主権（GDPR等）の両立手段として採用が増加。

- **オブザーバビリティの分散化が課題:** エッジ実行は数百リージョンに分散するため、従来の集中型APMが機能しにくい。OpenTelemetry + エッジネイティブなトレーシング基盤（Baselime等）の整備が急務。

- **コスト構造の再評価が必要:** リクエスト単価は安価だが、エッジキャッシュミス・DB往復・Wasm初期化コストが積み重なるケースがある。「何をエッジで実行すべきか」のアーキテクチャ判断がパフォーマンスとコストの鍵を握る。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の標準化:** 2026年時点でパスキーはパスワードの実質的な代替として定着しており、フィッシング耐性とユーザビリティを両立するため、新規サービスではパスワードレス認証をデフォルト設計すべき。

- **AIを活用した異常検知の組み込み:** セッションの振る舞いパターン（タイピング速度・デバイスフィンガープリント・地理的ロケーション）をリアルタイム分析し、認証後の継続的なリスク評価（Continuous Authentication）がゼロトラストアーキテクチャの必須要件になっている。

- **OAuthトークンの短命化とDPoP採用:** アクセストークンの有効期限を5〜15分に抑え、DPoP（Demonstration of Proof-of-Possession）でトークン窃取攻撃を無効化するアプローチが標準化されつつある。

- **セッション管理のサーバーサイド回帰:** JWTのステートレス設計はリスク時の即時失効が困難なため、高セキュリティ要件のサービスではサーバーサイドセッションとトークンローテーションの組み合わせが見直されている。

- **サプライチェーン攻撃への対策としての認証ライブラリ固定:** `next-auth`などのOSSライブラリはバージョン固定＋`bun.lockb`のCI検証を徹底し、依存関係の改ざんによる認証バイパスを防ぐことが実務上不可欠。

### 6. database architecture Prisma Supabase 2026

- **Prisma v6のEdge Runtime対応が実用段階に:** Prisma Accelerateを活用することでVercel Edge Functions上でもコネクションプーリング済みのDB接続が可能になり、Next.js App Routerとの相性が大幅に向上した。

- **Supabaseのリアルタイム機能とRow Level Security(RLS)の組み合わせがスタンダードに:** RLSをDBレベルで定義することでアプリ側の認可ロジックを排除でき、セキュリティの一元管理と開発速度の両立が可能。Prismaとの併用時はRLSバイパスに注意が必要。

- **Supabase Branching × Prisma Migrateでスキーマ管理が改善:** 2025年後半からSupabase BranchingがGA化し、PRごとにDBブランチを自動生成できる。Prismaのマイグレーションファイルとの組み合わせでCI/CDパイプライン上のスキーマドリフトを防止できる。

- **pgvectorによるベクトル検索がSupabaseで本番利用可能:** RAGパイプラインをアプリDB内に統合できるため、別途ベクトルDBを持つアーキテクチャが不要になりつつある。Prismaからは`$queryRaw`で対応するが、型安全性は別途担保が必要。

- **コネクション管理がボトルネック:** サーバーレス環境ではPrismaの接続プールが枯渇しやすく、Supabase側の`pgBouncer`(Transaction mode)との二重プーリングが問題になる。Prisma Accelerateか、Supabaseの接続文字列を`?pgbouncer=true&connection_limit=1`で調整するのが現時点のベストプラクティス。

### 7. WebAssembly Rust performance 2026

- **Component Model の本格普及:** WebAssembly Component Model (WASI 0.2) が2025年に安定化し、Rustで書かれたWasmコンポーネントが言語間の相互運用を型安全に実現。マイクロサービスの代替として注目度が急上昇している。

- **SIMD・スレッド対応の成熟:** Wasm SIMD命令とshared memoryスレッドのブラウザ対応が安定し、RustのSIMDクレート（`packed_simd`等）との組み合わせでネイティブC++比95%以上の演算性能を達成するケースが報告されている。

- **Wasmtime / WASMERのサーバーサイド高速化:** エッジランタイム（Cloudflare Workers、Fastly Compute）でのcold start時間がWasmtime 20+シリーズで1ms以下に到達。RustターゲットのWasmは起動オーバーヘッドがほぼゼロでコンテナ代替として実用段階に入った。

- **ガベージコレクション不要の優位性維持:** Rustの所有権モデルはWasm環境でもGCオーバーヘッドなしにメモリ管理を実現。特にリアルタイム処理（音声・画像・ゲームロジック）でJSやGo製Wasmに対して予測可能なレイテンシという決定的な差別化要素になっている。

- **`wasm-bindgen` / `wit-bindgen` エコシステムの成熟:** ツールチェーンの整備が進み、RustからWasmへのビルドパイプラインがCargoの標準フローに統合されつつある。`cargo component`コマンド一発でComponent Model準拠のバイナリが生成でき、採用コストが大幅に低下している。

### 8. Next.js App Router patterns 2026

- **Server Components ファーストの徹底:** 2026年時点でのベストプラクティスは「デフォルトServer、必要な箇所だけClient」。`'use client'`境界を最末端コンポーネントに押し込むことで、バンドルサイズを劇的に削減できる。

- **Partial Prerendering（PPR）の実用化:** Next.js 15以降でPPRが安定化し、静的シェル＋動的ストリーミングの組み合わせが標準パターンに。TTFBと動的コンテンツのトレードオフを解消する最重要アーキテクチャ。

- **`use cache` / `cacheLife` / `cacheTag` APIへの移行:** `unstable_cache`から新しいキャッシュAPIへの移行が急務。関数レベルで細粒度にキャッシュ戦略を制御でき、オンデマンド無効化も直感的に書ける。

- **Server Actions の責務明確化:** Server Actionsはフォーム送信・ミューテーション専用と割り切り、データフェッチはServer Componentsで行う設計が定着。`next-safe-action`等でZodバリデーション＋型安全を統合するパターンが主流。

- **`after()` APIによるレスポンス後処理:** レスポンス返却後に非同期処理（ログ・分析・通知）を走らせる`after()`が安定化。従来の`waitUntil`ハックが不要になり、レイテンシに影響しないサイドエフェクト処理が正式にサポートされた。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtimeの選択的活用:** 全APIをEdgeに移行するのは逆効果。レイテンシ依存のルーティング・認証ミドルウェアはEdgeに、データベース直接アクセスやCPU集約処理はNode.js Runtimeに残すのが最適解。

- **Cold Start撲滅戦略:** 2026年時点でVercel Edge FunctionsのCold Startは概ね1ms以下だが、`export const runtime = 'edge'`を付けた全Routeが対象になるよう設計し、Dynamic Importの多用は避けること。バンドルサイズは1MB以下を維持する。

- **Fluid Compute（旧Streaming）の活用:** `StreamingTextResponse`やAI SDK連携では、Edge + Streamingの組み合わせが体感速度を大幅改善。TTFBを最小化するためにレスポンスを分割して即座に送信する設計を標準化すべき。

- **KV・R2との統合コスト意識:** Vercel KVやCloudflare R2をEdge Functionから呼ぶ際、リージョン配置のミスマッチが逆にレイテンシを増加させる。`process.env.VERCEL_REGION`で動的にデータソースを選択するロジックが実用的。

- **コスト管理の現実:** Edge Functionは呼び出し回数×実行時間で課金される。無限ループ・過剰なfetch連鎖は想定外の費用を招く。`maxDuration`を明示設定し、Vercel Analyticsでp99レイテンシとコストを定期観測する体制が必須。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の積極活用:** TypeScript 4.9以降の`satisfies`は型チェックを維持しつつ推論を保持でき、`as`キャストより安全な型確認が可能。2026年では`satisfies`なしのキャストはアンチパターンとみなされつつある。

- **Template Literal Typesによる文字列型の精緻化:** APIエンドポイントやイベント名を`` `${Method}:${Resource}` ``形式で型定義することで、ランタイムエラーをコンパイル時に検出。特にRPCやイベントバスの型安全性が劇的に向上。

- **`using`キーワード（Explicit Resource Management）の普及:** TypeScript 5.2+の`using`宣言でDB接続やファイルハンドルを自動dispose。`try/finally`の書き忘れによるリソースリークがコンパイラレベルで防止できる。

- **Branded Types（Nominal Typing）の標準化:** `type UserId = string & { _brand: 'UserId' }`パターンで構造的型付けの限界を補完。IDの混同バグをゼロコストで排除でき、zodの`.brand()`との組み合わせがバリデーション層で定番化。

- **`noUncheckedIndexedAccess`の有効化が必須化傾向:** 配列・オブジェクトのインデックスアクセスに自動で`| undefined`を付与するこのフラグ、2026年では厳格な型設定の標準項目に。これなしでは`tsc --strict`だけでは不十分とされる。
