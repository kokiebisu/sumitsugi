# CTO Knowledge - 2026-04-10

## Daily Update (2026-04-10)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** データフェッチをサーバー側に集約し、クライアントバンドルサイズを削減する。`"use client"` は本当に必要な箇所（インタラクション・状態管理）のみに限定するのが2026年の基本戦略。

- **Partial Prerendering (PPR) による静的/動的の最適な組み合わせ:** Next.js 15以降で安定化したPPRにより、1ページ内で静的シェルと動的スロットを混在させられる。全体をSSRやSSGに振り切る必要がなくなり、TFBTとTTFBを同時に改善できる。

- **`next/after` でレスポンス後処理を非同期化:** レスポンス送信後にロギングや分析処理を実行できる新APIにより、メインリクエストのレイテンシに影響を与えずにサーバーサイド処理を行える。

- **Turbopack移行によるビルド・HMR高速化:** Next.js 15でデフォルト化されたTurbopackはWebpack比で大規模プロジェクトのHMRを最大10倍高速化。CI/CDのビルド時間短縮にも直結するため、早期移行を推奨。

- **`<Image>` / `<Font>` の自動最適化を信頼し、手動最適化を減らす:** Next.jsのビルトイン最適化（自動WebP変換、フォントのself-hosting、CLS防止）は成熟しており、カスタム実装より公式コンポーネントを優先することで保守コストを下げながらCore Web Vitalsを維持できる。

### 2. React Server Components streaming 2026

- **Partial Prerendering (PPR) の本格普及:** Next.js 15以降でPPRが安定化し、静的シェルと動的ストリーミングを同一ページで混在させるパターンが標準的になった。ビルド時レンダリングとSSRの境界をコンポーネント単位で制御できるため、TTFBとLCP両方を最適化できる。

- **Suspense境界設計がアーキテクチャの核心に:** データフェッチのウォーターフォールを避けるため、`<Suspense>`境界の配置がシステム設計の重要な意思決定になっている。並列フェッチ可能なコンポーネントを早期にストリームし、依存関係のあるものだけを遅延させる設計が求められる。

- **Server Actions との統合による往復削減:** RSCストリーミングとServer Actionsを組み合わせることで、クライアント→サーバーの通信をミューテーション後の再レンダリングまで一気通貫で処理できる。APIルートの大部分が不要になり、バンドルサイズと複雑性が大幅に削減される。

- **Edge Runtimeでのストリーミング制約に注意:** CloudflareやVercel EdgeはNode.js標準より制約が厳しく、一部のNode APIに依存したRSCは動作しない。データアクセス層をEdge互換に保つか、Regionalized Functionを使い分ける設計判断が必要。

- **React 19のuse()フックによるクライアント側の簡略化:** `use(promise)`でクライアントコンポーネントからもPromiseを直接消費できるようになり、RSCからクライアントへのデータ受け渡しパターンが統一された。Context経由の「prop drilling回避」に`use(Context)`も使えるため、状態管理の複雑さが下がっている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの台頭と型安全APIの標準化:** tRPCはNext.js/TypeScriptスタックで事実上の標準となりつつあり、クライアント・サーバー間の型共有によりランタイムエラーを大幅削減できる。スキーマ定義が不要なため、小〜中規模チームの開発速度が顕著に向上する。

- **GraphQLの用途特化:** GraphQLは「全APIに使う」から「複雑なデータグラフ・マルチクライアント対応が必要な場合のみ」へ役割が絞られつつある。BFFパターンとの組み合わせやFederation（Apollo/Hive）による大規模マイクロサービス統合が主要ユースケース。

- **REST+OpenAPIの根強い実用性:** 外部公開API・サードパーティ連携ではRESTとOpenAPI 3.1が依然最強。Zod→OpenAPI自動生成（`zod-to-openapi`等）により型安全とドキュメント整合性を両立できるようになった。

- **HTTP/3とストリーミングAPIの普及:** 2026年時点でHTTP/3（QUIC）対応CDNが標準化し、Server-Sent EventsやReadableStreamを活用したストリーミングレスポンス（特にAI推論結果の逐次返却）がAPI設計の新要件として浮上している。

- **コントラクトファースト設計の復権:** AIコード生成の普及により、スキーマ/型定義を先に書いてから実装するコントラクトファーストアプローチが再評価されている。tRPCのルーター定義やProtobuf/Connectがその代表例で、AIへの指示としても機能する。

### 4. serverless edge computing 2026

- **WebAssembly (Wasm) がエッジの標準ランタイムへ:** Cloudflare Workers・Fastly Compute等でWasmが主流化し、言語非依存でコールドスタートほぼゼロを実現。コンテナの代替としてエッジデプロイの事実上の単位になりつつある。

- **AI推論のエッジシフト加速:** LLMの軽量化（quantization・distillation）により、エッジノードでの推論が現実的に。レイテンシ削減とプライバシー保護の両立が可能になり、ユーザーデータをクラウドに送らないアーキテクチャが増加。

- **エッジDBとデータ整合性の成熟:** Cloudflare D1・Turso等の分散SQLiteやCRDTベースのストアが実用段階へ。「エッジで読み書き、中央で整合」のパターンが確立され、エッジをステートレスに縛る必要が薄れた。

- **オブザーバビリティのギャップが最大の課題:** 分散エッジ環境では従来のAPMが機能せず、OpenTelemetryのエッジ対応とサンプリング戦略の設計が必須。トレーシングの欠如がデバッグコストを著しく増大させる。

- **ベンダーロックインリスクの顕在化:** エッジ関数のAPI差異（Workers vs Lambda@Edge vs Vercel Edge）が移植コストを生む。WinterCG標準への準拠度を選定基準に組み込み、抽象レイヤー（Hono等）の採用でポータビリティを確保することが実務上の定石。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の標準化:** 2026年時点でパスキーはパスワードレス認証の事実上の標準となり、主要プラットフォームがネイティブサポート済み。新規サービスではパスワード認証を廃止し、パスキーをデフォルトにすべき段階。

- **セッション管理のゼロトラスト化:** 長期セッショントークンは廃止傾向。短命なアクセストークン（15分〜1時間）＋ローテーション付きリフレッシュトークンの組み合わせが標準で、盗難時の被害範囲を最小化する。

- **AIを活用した異常ログイン検知:** 地理的移動速度・デバイスフィンガープリント・行動パターンをリアルタイム分析し、通常のMFAでは防げないアカウント乗っ取り（ATO）を検出する仕組みが普及。

- **サプライチェーン攻撃対策としての依存ライブラリ監査:** `next-auth`や`passport.js`等の認証ライブラリへの悪意あるコード注入事例が増加。`bun audit`やSBOM（ソフトウェア部品表）の定期生成を CI に組み込むことが必須。

- **OAuth 2.1 / DPoP（Demonstrating Proof of Possession）の採用:** トークン漏洩時の横展開を防ぐため、DPoPでトークンをクライアントの秘密鍵に束縛する手法が主流化。既存のBearer Tokenのみの実装は2026年時点でセキュリティ上の技術負債とみなされる。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応:** Prisma 6はEdge互換ドライバー（`@prisma/adapter-pg`等）が安定化し、Vercel Edge FunctionsやCloudflare Workersからの直接DB接続が現実的になった。Next.js App RouterとのServer Actions連携でレイテンシが大幅に改善されている。

- **Supabase pgvector × AI統合の本格化:** `pgvector`拡張によるベクトル検索がSupabaseの主力機能に昇格し、RAGパイプラインをアプリDB内で完結させるアーキテクチャが主流になりつつある。外部ベクトルDBを別途立てるコスト・複雑さが不要になる。

- **Row Level Security (RLS) の設計が最重要課題:** SupabaseはRLSをアプリ層ではなくDB層で強制するため、Prismaのクライアント設定（`serviceRole` vs `anonKey`）の使い分けを誤るとセキュリティホールに直結する。RLSポリシーのテストをCIに組み込むことが必須。

- **Connection Poolingの二重管理に注意:** SupabaseはPgBouncer（Supavisor）を内蔵しているが、Prismaも独自のコネクションプールを持つ。`DATABASE_URL`に`?pgbouncer=true&connection_limit=1`を設定しないとコネクション枯渇が起きる。特にサーバーレス環境での設定ミスが多い。

- **Prisma Accelerateによるグローバルキャッシュ層:** Prisma AccelerateはCDNエッジでのクエリキャッシュを提供し、Supabaseのリージョン制約（シングルリージョンDB）を補完する設計が2026年のベストプラクティスとなっている。読み取り重視のワークロードではキャッシュTTL設計がパフォーマンスの鍵。

### 7. WebAssembly Rust performance 2026

- **WASI Component Model の実用化:** WASI Preview 2 が標準化され、Rust 製 Wasm コンポーネントを他言語（Python/JS）と安全に組み合わせられる。マイクロサービスのポータブルな実行単位として採用が急増している。

- **ランタイム最適化によるネイティブ性能への接近:** Wasmtime・Wasmer の JIT + PGO（Profile-Guided Optimization）最適化により、CPU バウンドな処理でネイティブの 85〜95% 程度の性能が安定して出せるようになった。

- **SIMD / スレッド対応でデータ処理が本番レベルに:** WebAssembly SIMD と shared memory atomics の普及により、画像処理・暗号化・推論ワークロードで Rust/Wasm がネイティブライブラリの現実的な代替になりつつある。

- **エッジ環境でのコールドスタート問題が事実上解消:** Rust の小さなバイナリサイズと Wasm のサンドボックス起動速度（<1ms）の組み合わせが Cloudflare Workers・Fastly Compute@Edge の本番採用を加速させており、Node.js より低レイテンシを実現している。

- **ツールチェーンの成熟でオンボーディングコストが低下:** `cargo-component` や `wasm-bindgen` 周辺のエコシステムが整い、Rust 未経験チームでも 1〜2 週間で Wasm モジュールを CI/CD に組み込める体制が整ってきた。実プロジェクトへの導入障壁が大幅に下がっている。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点でApp Routerの最適解は「まずServer Component、必要な部分だけ`'use client'`」。クライアントバンドルを最小化し、初期ロードを劇的に改善できる。

- **Partial Prerendering (PPR) の本格活用:** Next.js 15+で安定化したPPRにより、静的シェル＋動的ストリーミングを1ルートで混在できる。`<Suspense>`境界の設計がアーキテクチャの核心になった。

- **Server Actions でAPI層を薄く:** フォーム送信・データ変更はServer Actionsで完結させ、REST/tRPC層を省略できるケースが増えた。ただしバリデーション（Zod）とCSRF対策は必須。

- **`use cache` ディレクティブによる細粒度キャッシュ:** `fetch`キャッシュから関数レベルの`use cache`へシフト。コンポーネント単位でキャッシュ戦略を宣言でき、CDNとの協調が簡単になった。

- **`dynamicIO` + Turbopack でビルド高速化:** 2026年では`turbopack`がデフォルトビルダーに近づき、大規模プロジェクトでのビルド時間が従来比50%以上短縮。`bun run build`の待ち時間が開発体験の差別化要因になっている。

### 9. Vercel Edge Functions optimization 2026

- **Cold Start削減のためのEdge Runtimeシフト:** 2026年時点でVercel Edge FunctionsはV8 Isolateベースのため、Node.js Lambdaと比較してコールドスタートが5〜50ms程度に抑えられる。ただしNode.js APIの制約（fs, net等）があるため、移行前に依存ライブラリの互換性確認が必須。

- **Streaming ResponseとPartial Prerenderingの組み合わせ:** Next.js 15以降のPPR（Partial Prerendering）とEdge Streamingを組み合わせることで、静的シェルを即座に返しつつ動的コンテンツをEdgeからストリーミングする構成が実用レベルに。TTFBの大幅改善が見込める。

- **Edge Middlewareでの認証・A/Bテスト集約:** JWTバリデーションやフィーチャーフラグの評価をEdge Middlewareに集約することで、オリジンへのリクエストを削減できる。`@vercel/edge-config`との組み合わせで設定変更をコードデプロイなしに反映可能。

- **バンドルサイズの厳格管理（1MB制限）:** Edge Functionsは1MBのバンドル上限があり、重量級のnpmパッケージ（prisma clientなど）はそのまま使用不可。`prisma/edge`や軽量ORMへの切り替え、あるいはDB接続はオリジン側に残す設計判断が重要。

- **観測可能性（Observability）の強化:** 2026年時点でVercel Edge LogsとOTEL（OpenTelemetry）の統合が進んでおり、Edge実行のトレース・スパン可視化が可能に。本番障害の根本原因特定をEdgeレイヤーまで含めて行える体制を整えておくべき。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `type UserId = string & { readonly _brand: 'UserId' }` パターンが広く採用され、プリミティブ型の混同バグをコンパイル時に防ぐ手法が実務レベルで定着した。

- **`satisfies` 演算子の活用:** TypeScript 4.9以降の `satisfies` が2026年時点で成熟し、型推論を保持しながら型チェックを行う「型アサーションの安全な代替」として設計レビューの必須チェック項目になっている。

- **Effect・neverthrow によるエラー型安全:** `throw` を排除し `Result<T, E>` 型でエラーを明示するパターンが普及。`Effect` ライブラリのエコシステムが成長し、非同期処理の型安全性が大幅に向上した。

- **Template Literal Types の実用化:** APIルートパスや i18n キーをリテラル型で表現し、`/api/users/${string}` 形式の型がランタイムエラーをゼロにするアーキテクチャが増加している。

- **`noUncheckedIndexedAccess` の必須化:** `tsconfig.json` でこのフラグを有効化することで配列アクセスの `undefined` 見落としを排除できる。2026年ではこれを有効にしないプロジェクトは型安全とみなさない風潮が強まっている。
