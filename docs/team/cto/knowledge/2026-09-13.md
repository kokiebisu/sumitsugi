# CTO Knowledge - 2026-09-13

## Daily Update (2026-09-13)

### 1. Next.js performance optimization 2026

- **ポイント1（Turbopackの本格採用）:** Next.js 16ではTurbopackが安定版としてデフォルトビルドツールとなり、`bun run build`でのビルド時間とHMR速度が大幅に改善されるため、開発体験とCI時間の両方に直結する。

- **ポイント2（Partial Prerendering / PPRの活用）:** 静的シェルを即座に返しつつ動的部分をストリーミングする手法が主流化しており、`src/app/properties/`のような一覧ページで初期表示速度（LCP）を落とさずパーソナライズ要素を出せる。

- **ポイント3（React Server Componentsでのデータフェッチ最適化）:** クライアントバンドルを減らすためにデータ取得ロジックをServer Component側に寄せ、`use client`境界を最小限にすることが依然として最大のパフォーマンス施策。フォームや認証など状態管理が必要な部分だけをクライアント化する設計が重要。

- **ポイント4（画像・フォントの自動最適化を前提にした設計）:** `next/image`と`next/font`の最適化はデフォルトで強力になっているため、物件写真中心のUI（前の住人の暮らしを見せる写真ギャラリー等）ではこれらのAPIを使い切ることが最もコスパの良いパフォーマンス改善になる。

- **ポイント5（Edge/Node runtimeの使い分け）:** 認証やDBアクセスが絡むページはNode runtime、静的に近い軽量ページはEdge runtimeという使い分けが定着しつつあり、レイテンシとコストのバランスを取る設計判断がアーキテクチャレビューの標準項目になっている。

### 2. React Server Components streaming 2026

- **ポイント1（Partial Prerendering の主流化）:** Next.js 16ではPPR（Partial Prerendering）がデフォルト志向になりつつあり、静的シェルを即座に返しつつ動的部分だけをストリーミングする設計が標準パターンになっている。うちのproperties一覧ページのような「静的な枠+動的な物件データ」構成には特に効果が大きい。

- **ポイント2（Suspense境界の粒度設計が本質的な課題に）:** ストリーミングの効果はSuspense boundaryの切り方次第で決まるため、「何を先に見せるか」というUX設計とエンジニアリングが不可分になってきている。物件詳細ページなら「画像・タイトル」を先に返し、「価格計算・空き状況」を遅延させる、といった業務ロジックに即した境界設計が重要。

- **ポイント3（Server Actionsのキャッシュ戦略が成熟）:** `use cache` ディレクティブとタグベース再検証（`revalidateTag`）の組み合わせが標準化され、フォーム送信やミューテーション後の部分再取得が高速化している。引越し費用計算や物件ステータス変更のような書き込み系フローで活用余地が大きい。

- **ポイント4（RSC Payloadのサイズ管理が新たなパフォーマンス指標に）:** クライアントに送られるRSCペイロード自体のサイズがCore Web Vitalsと同様に監視すべき指標になってきており、不要なpropsのシリアライズを避ける設計レビューが求められる。中〜大規模なコンポーネントツリーでは特に注意が必要。

- **ポイント5（エッジランタイムとの親和性向上）:** ストリーミングSSRとEdge Runtimeの組み合わせにより、TTFB（Time to First Byte）の地理的差異が縮小しつつある。ローンチ後のグローバル/地域展開を見据えるなら、早い段階でEdge対応可能なデータ取得層を設計しておくと移行コストが下がる。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCの採用は依然としてTypeScriptフルスタック構成（Next.js＋単一リポジトリ）に限定的で、社外パートナーや異なる言語のクライアントと連携する必要がある弊社のようなプラットフォームでは、型安全性のメリットよりもエコシステムの制約が上回るため、外部公開APIには不向き。

- **ポイント2:** GraphQLは「前の住人」検索のような複雑なフィルタリング・関連データ取得（物件×レビュー×引越し費用など）に強みがあるが、キャッシュ制御やN+1問題への対策コストが高く、MVPフェーズの小規模チームにはオーバーエンジニアリングになりやすい。

- **ポイント3:** 2026年時点の実務トレンドは「内部はtRPC/REST、外部連携はREST＋OpenAPI」というハイブリッド構成が主流化しており、sumitsugiも `src/app/api` のREST層はOpenAPI仕様書化し、将来の外部パートナー連携（不動産会社API連携等）に備えるのが現実的。

- **ポイント4:** Next.js 16のServer Actions／RSCの普及により、フロントエンドとバックエンドが同一デプロイ単位にある場合はAPI層自体を薄くする設計（Server Actionsで直接DB操作）が増えており、社内向け機能（ダッシュボード等）は無理にAPIエンドポイント化せずServer Actionsで実装する方が開発速度・型安全性の両面で有利。

- **ポイント5:** どの方式を選んでも、Zodスキーマを境界（API入力）で共有し、REST/tRPC/Server Actionsいずれの層でも同じバリデーションロジックを再利用できる設計にしておくことが、将来の方式変更・移行コストを最小化する鍵になる。

### 4. serverless edge computing 2026

- **ポイント1:** WASMベースのエッジランタイム（Cloudflare Workers、Fastly Compute等）が主流化し、コールドスタートがほぼゼロになったことで、SSRやAPIレスポンスをユーザーに地理的に最も近いロケーションで処理できるようになっている。sumitsugiのような物件検索・画像配信が多いサービスでは、TTFB改善に直結する。

- **ポイント2:** エッジでのデータ整合性問題（強整合性 vs 結果整合性）が2026年も引き続き課題で、KVストア（Cloudflare KV、Vercel Edge Config等）は読み取り最適化だが書き込み反映に遅延がある。物件ステータス（draft/public）のような即時反映が必要なデータは、エッジキャッシュではなくオリジンDB直結にすべき。

- **ポイント3:** Next.js 16のPartial Prerenderingとエッジミドルウェアの組み合わせにより、静的な物件一覧はエッジでプリレンダーしつつ、認証状態や地域別料金表示だけを動的に差し込む設計が実用的になっている。ビルド時間とランタイムコストの両方を削減できる。

- **ポイント4:** エッジでのAI推論（軽量LLM推論、embeddingベースの検索）がコスト効率化し、物件マッチングや検索クエリの意図解釈をリージョンをまたがずに処理できるようになってきている。ただしモデルサイズとレイテンシのトレードオフは依然シビア。

- **ポイント5:** ベータローンチを控える段階では、エッジ導入は「今すぐ」より「後から段階的に」が現実的。まずはVercelの標準SSR/ISRで安定稼働させ、トラフィックが増えて地理的分散のニーズ（多地域ユーザー、画像配信の遅延）が明確になってから、静的資産・検索APIなど限定的な範囲からエッジ移行を検討するのが投資対効果として妥当。

### 5. authentication security best practices 2026

- **パスキー/FIDO2の標準化:** パスワードレス認証（WebAuthn/Passkeys）が主流化しており、フィッシング耐性のある認証をデフォルトにすることでクレデンシャルスタッフィング攻撃のリスクを大幅に低減できる。

- **セッション管理の厳格化:** 短命アクセストークン＋リフレッシュトークンローテーションを組み合わせ、デバイスフィンガープリンティングと組み合わせた異常検知でセッションハイジャックを防ぐ設計が標準になっている。

- **多要素認証の適応型運用:** 一律のMFAではなく、ログイン元・デバイス・行動パターンに基づくリスクベース認証（Adaptive MFA）を導入し、UXとセキュリティのバランスを取るのが2026年のベストプラクティス。

- **認可ロジックのゼロトラスト化:** 認証後も「信頼しない」前提でリクエストごとに権限を検証する仕組み（RLS/ポリシーエンジン）を徹底し、特にsumitsugiのような住宅情報プラットフォームでは`draft`/`public`ステータスや所有者情報へのアクセス制御を関数レベルで再検証すべき。

- **秘密情報のライフサイクル管理:** APIキーやJWTシークレットは環境変数管理に加え、定期ローテーションと漏洩検知（GitHub Secret Scanning等）をCI/CDに組み込み、ハードコード混入をビルド時にブロックする体制が必須。

### 6. database architecture Prisma Supabase 2026

CTOとして技術トレンドの洞察を回答します。

- **ポイント1:** Prismaは2024年以降、独自のRust製クエリエンジンから直接TypeScript実装への移行を進めており、2026年時点ではコールドスタートが大幅に短縮され、Vercel等のサーバーレス/エッジ環境との相性が改善されている。sumitsugiのようなNext.js App Router構成では、この変化によりビルドサイズとレイテンシの両面で恩恵を受けやすい。
- **ポイント2:** SupabaseはRow Level Security(RLS)をPrisma経由のアクセスと併用するパターンが定番化しており、認証済みユーザーのみが自分の物件データにアクセスできるようポリシーをDB層で強制するのがベストプラクティス。アプリ層のバリデーションだけに頼らず、DB層での多層防御を組み込むべき。
- **ポイント3:** SupabaseのConnection Pooling（PgBouncer/Supavisor）とPrismaのコネクション管理の相性は依然として注意点で、サーバーレス関数からの接続数急増を防ぐため`DATABASE_URL`とは別に`DIRECT_URL`を使い分ける設定が必須。マイグレーション実行とランタイムクエリで異なる接続方式を使い分けることでロック競合を回避できる。
- **ポイント4:** PrismaのTyped SQL機能とSupabaseのpgvector拡張を組み合わせ、型安全性を保ちながら生SQLでベクトル検索や複雑な集計を書くパターンが増えている。将来的に「前の住人」と「次の住人」のマッチング機能（インテリアの好み等の類似度検索）を実装する際に有効な選択肢になりうる。
- **ポイント5:** マイグレーション運用では、Prisma MigrateとSupabase CLIのマイグレーション機能が競合しやすいため、どちらか一方に統一するチーム規約が重要。本番ローンチ前のフェーズでは、スキーマ変更履歴の一元管理を早期に決めておくことが、後々のロールバックやCI/CD構築の複雑化を防ぐ。

### 7. WebAssembly Rust performance 2026

- **ポイント1（Component Model標準化）:** WASI Preview 2とComponent Modelの本格普及により、Rustクレートを言語非依存の再利用可能なWASMコンポーネントとして配布できるようになり、フロントエンドの重い画像処理・PDF生成処理を安全にサンドボックス化しつつネイティブに近い速度で実行できる。

- **ポイント2（SIMD/マルチスレッド標準化）:** WASM SIMDとスレッド（Web Workers + SharedArrayBuffer）がブラウザ標準機能として定着し、Rust側は`wasm-bindgen-rayon`等で並列処理を書けるため、画像リサイズや物件検索のクライアントサイドフィルタリングのようなCPU負荷の高い処理をメインスレッドをブロックせず高速化できる。

- **ポイント3（バイナリサイズ最適化）:** `wasm-opt`、`twiggy`によるサイズ解析、`wee_alloc`後継のより軽量なアロケータ選択が標準ワークフロー化しており、初期ロード時間がSEO・LCPに直結するプロダクトサイトでは、機能追加ごとにバイナリサイズをCIでチェックするゲートを設けるのが実用的。

- **ポイント4（Rust→WASM開発体験の成熟）:** `wasm-pack`と`vite-plugin-wasm`の組み合わせでNext.js 16のApp Router内でもシームレスにWASMモジュールをインポートでき、TypeScript型定義も自動生成されるため、パフォーマンスクリティカルな一部ロジック（例：料金シミュレーション計算）だけをRustに切り出す段階的採用がしやすい。

- **ポイント5（サーバーサイドWASM）:** Cloudflare Workers等のエッジランタイムでRust製WASMを動かすパターンが定着し、Node.js/Bunより起動コールドスタートが速いため、軽量なAPIエンドポイント（例：物件データのバリデーション処理）をエッジに寄せることでレイテンシ改善が見込める。

### 8. Next.js App Router patterns 2026

- **Server ActionsとuseOptimisticの標準化:** フォーム送信やデータ変更処理はServer Actions＋`useOptimistic`/`useFormStatus`の組み合わせが定番化し、クライアント側のローディング状態管理コードが大幅に削減できる。

- **Partial Prerendering (PPR) の本格運用:** 静的シェルを即座に返しつつ動的部分だけをストリーミングする構成が主流になり、`loading.tsx`とSuspense境界の設計次第でLCP・TTFBが大きく改善する。SumitsugiのようなSEOが重要な物件一覧ページに特に効果的。

- **キャッシュ戦略の明示化 (`'use cache'` ディレクティブ):** Next.js 16以降ではデータ取得のキャッシュ挙動をディレクティブで明示する方式が定着し、暗黙的キャッシュによる「なぜ最新データが出ない」問題が減った一方、意図的なキャッシュ設計スキルが必須になった。

- **Server ComponentsとClient Componentsの境界設計:** 「Client Componentを葉（leaf）に押し込む」原則がより厳格に求められ、認証状態やフォームロジックなど本当にインタラクティブな部分のみをクライアント化することでバンドルサイズを最小化する設計が評価される。

- **Route Handlers + Middlewareでの認可の一元化:** App RouterのMiddlewareでの認証チェックとRoute Handlersでの権限検証を組み合わせ、`auth-context.tsx`のようなクライアント側コンテキストに頼りすぎない多層防御パターンが推奨されている。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1:** Edge FunctionsのCold Start対策として、依存関係を最小限に抑えたバンドル設計が重要。Node.js APIに依存しないコードに書き換えることでV8 isolateの起動が数十ms単位で高速化される。

- **ポイント2:** Streaming SSR/Response streamingをEdge Functionsと組み合わせることで、TTFB（Time To First Byte）を大幅に短縮できる。特にLLM連携機能（チャット的UI等）を実装する場合、Edge上でのストリーミングレスポンスがUX向上に直結する。

- **ポイント3:** Edge ConfigやKV系ストレージ（Vercel KV, Upstash Redis）をEdge Functions内から読み書きすることで、DBラウンドトリップを減らしレイテンシを削減できる。ただし書き込み頻度が高いデータには不向きなので、読み取り主体のキャッシュ層として使うのが定石。

- **ポイント4:** リージョン指定（`regions`設定）を活用し、ユーザーの地理的分布に合わせてEdge Functionsの実行リージョンを絞ることで、不要なレイテンシとコストを削減できる。日本向けサービスなら`hnd1`固定が基本。

- **ポイント5:** Middleware肥大化によるレスポンス遅延に注意が必要。認証チェックやリダイレクトロジックを詰め込みすぎると全リクエストに影響するため、Edge Middlewareは軽量ロジックに限定し、重い処理はServer Actions/API Routesに逃がす設計が推奨される。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** `satisfies`演算子とconst型パラメータ（TS 5.x〜）の組み合わせが標準化し、リテラル型を保ったまま構造チェックできるため、Zodスキーマ由来の型とUI側の型定義の乖離を防ぐパターンが定着しています。
- **ポイント2:** Zod（v4系）やvalibotなど「スキーマ・ファースト」ライブラリで型とランタイムバリデーションを一元化し、`z.infer`から型を導出する手法が標準ルール化。sumitsugiでも境界（フォーム入力・API）でのZod必須方針と相性が良いです。
- **ポイント3:** テンプレートリテラル型やbranded type（例: `type UserId = string & { __brand: 'UserId' }`）を使い、`seller`/`buyer`のようなドメインIDを型レベルで混同不可にする設計が、物件ステータスなどのUnion型の誤用防止に有効です。
- **ポイント4:** `strict: true` + `noUncheckedIndexedAccess`をデフォルト化する動きが強まり、配列・オブジェクトアクセス時のundefined漏れをコンパイル時に検出する構成が2026年のベストプラクティスになっています。
- **ポイント5:** tRPCやHono RPCのようなEnd-to-End型推論フレームワークがApp Router構成でも普及し、API層とフロントの型を自動同期することで、`status: 'draft' | 'public'`のような列挙値変更時の型不整合を全レイヤーでコンパイルエラーとして検出できます。
