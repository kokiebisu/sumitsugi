# CTO Knowledge - 2026-11-20

## Daily Update (2026-11-20)

### 1. Next.js performance optimization 2026

- **ポイント1:** Next.js 16ではPartial Prerendering（PPR）が安定版となり、静的シェルを即時配信しつつ動的部分のみストリーミングするハイブリッド構成が標準化されている。本物件のプロパティ一覧ページなどは静的部分（レイアウト・ヘッダー）とユーザー依存部分（ログイン状態・お気に入り）を分離してPPRを適用すると初期表示速度を大幅改善できる。

- **ポイント2:** Turbopackがビルド・開発両方でデフォルトの標準ビルドツールとなり、Webpack比で大幅な高速化が実現されている。`bun run build`のビルド時間自体も短縮されるため、CIのビルド検証ステップのボトルネック解消にも直結する。

- **ポイント3:** React Server Components（RSC）とServer Actionsの組み合わせでクライアントJSバンドルを最小化する設計が主流化しており、フォームや認証フローなど`src/components/auth/`配下のインタラクティブ要素も可能な限りServer Actions化することでTTI（Time to Interactive）を削減できる。

- **ポイント4:** `next/image`のAVIF対応とレスポンシブ配信の最適化が進み、物件写真中心の本サービスでは画像最適化がLCP（Largest Contentful Paint）改善の最重要レバーになっている。CDNキャッシュ戦略と組み合わせたISR（Incremental Static Regeneration）の活用も鍵。

- **ポイント5:** Core Web Vitalsの計測観点がINP（Interaction to Next Paint）中心にシフトしており、物件検索フィルターや引越し費用計算などのインタラクション密度が高いUIでは、useTransitionやSuspense境界の適切な配置によるメインスレッドブロッキングの削減が重要な最適化ポイントとなる。

### 2. React Server Components streaming 2026

- **ポイント1:** Next.js 16ではPPR（Partial Prerendering）が標準化され、静的シェルを即時配信しつつ動的部分だけストリーミングする構成が主流になっている。sumitsugiのproperties一覧ページでも、物件カードの静的枠を即表示し、価格・在庫状況などの動的データを後から流し込む設計がTTFBとLCP両方の改善に効く。
- **ポイント2:** `loading.tsx`とSuspenseバウンダリの粒度設計がパフォーマンスの肝になっており、1ページに1個の大きなSuspenseではなく、コンポーネント単位（物件詳細の写真・レビュー・空室カレンダーなど）で分割するのがベストプラクティス。
- **ポイント3:** Server Actionsとストリーミングの組み合わせでフォーム送信後のUI更新がより滑らかになり、引越し費用の見積もりフォームのような多段階フローでクライアントJSを最小化できる。
- **ポイント4:** キャッシュ戦略（`fetch`のrevalidate設定、Data Cacheのタグベース無効化）がストリーミングと密接に絡むため、物件ステータス（draft/public）切り替え時のキャッシュ無効化漏れがバグの温床になりやすく、CI上のE2Eでキャッシュ系の挙動も検証対象にすべき。
- **ポイント5:** RSCのストリーミングはエッジランタイムとの組み合わせで地理的レイテンシを削減できるが、Bun 1.x環境でのエッジ互換性はまだ要検証な部分があり、本番導入前にビルド・デプロイ環境での動作確認が必須。

### 3. API design REST GraphQL tRPC 2026

- **ポイント1:** tRPCやHonoのようなTypeScriptネイティブなRPCレイヤーが、Next.jsのApp Router/Server Actionsと統合され、型安全性のためにスキーマを手動同期する手間が減っている。sumitsugiのような単一リポ・単一言語（TS）構成では、GraphQLのスキーマ管理コストよりtRPC/Server Actionsの方が開発速度が出やすい。

- **ポイント2:** GraphQLは依然としてモバイル/複数クライアントが絡む複雑な集約クエリに強いが、単一のWebクライアントが前提のプロダクトではオーバーエンジニアリングになりやすい。前の住人・次の住人のマッチングのように関係データが多いドメインでも、まずはRESTやtRPCで十分で、GraphQLは「複数フロントエンドが必要になった時」に導入判断すべき。

- **ポイント3:** RESTはOpenAPI/Zodスキーマからのコード生成（zod-to-openapi等）が成熟し、外部パートナー（弁護士チェック後の決済代理店API連携など）とのインテグレーションでは依然デファクト標準。社内API（tRPC）と外部公開API（REST+OpenAPI）を分離するハイブリッド構成が2026年の主流。

- **ポイント4:** Zodによる入力検証をAPI境界で一元化する流れが強まっており、tRPCのinput schemaやServer Actionsのバリデーションをそのままフロントの型にも流用できる点が、standards.mdで既に定めている「Zodスキーマを境界で使う」方針と整合している。

- **ポイント5:** パフォーマンス面では、N+1問題を避けるためのデータローダー（GraphQL）や、tRPCでのバッチング（httpBatchLink）が重要になるが、物件検索・予約のような高頻度アクセスのエンドポイントはキャッシュ戦略（Next.jsのfetchキャッシュ/ISR）と組み合わせる設計が先に来るべきで、API方式の選定自体よりキャッシュ・インデックス設計が性能の決定要因になりやすい。

### 4. serverless edge computing 2026

- **ポイント1:** Cloudflare Workers・Vercel Edge Functions・Deno Deployなどのエッジランタイムが成熟し、コールドスタートがほぼ解消。グローバル低レイテンシが必要なAPI（検索・認証チェック等）はエッジ関数へ、重い処理は従来サーバーレスに残す「ハイブリッド配置」が2026年の標準パターン。

- **ポイント2:** エッジでのSQLite互換DB（Cloudflare D1、Turso等）やKVストレージがGAレベルで安定し、「エッジ=読み取り専用キャッシュ」という制約が崩れつつある。ただし強整合性が必要な決済・在庫系は依然オリジンDB必須で、全部エッジ化は禁物。

- **ポイント3:** Next.js 16のPartial Prerendering + Edge Runtimeの組み合わせで、静的シェルをCDNエッジから即配信しつつ動的部分だけをストリーミングする構成が一般化。sumitsugiのようなApp Router構成なら、物件一覧ページなどSEO重視ページで効果が大きい。

- **ポイント4:** WASM（WebAssembly）ベースのエッジ実行が普及し、Node.js API依存のコードはそのままでは動かないケースが増加。ミドルウェアやエッジ関数を書く際はNode固有API（`fs`, `crypto`のNode実装等）を避け、Web標準APIベースで書く設計が必須。

- **ポイント5:** エッジ特有の分散デバッグ・オブザーバビリティの難しさは2026年もボトルネックで、OpenTelemetryのエッジ対応トレーシングが実質デファクト標準化。導入コストに対しROIが出るのはトラフィック規模が大きいサービスのみなので、MVPフェーズのsumitsugiでは優先度低。

### 5. authentication security best practices 2026

- **パスキー/WebAuthnのデフォルト化:** 2026年現在、パスワードレス認証（FIDO2パスキー）が主流になっており、フィッシング耐性とUX向上を両立できる。sumitsugiのようなB2Cプラットフォームでは、パスワード認証をフォールバックに留め、パスキーを第一選択肢にすることで離脱率を下げられる。

- **トークン管理の厳格化:** JWTのローカルストレージ保存は依然XSSリスクが高く、httpOnly + SameSite=Strict cookieでのセッション管理が標準。アクセストークンは短命（15分以内）、リフレッシュトークンはローテーション必須で、漏洩時の被害範囲を最小化する。

- **デバイス/行動ベースのリスク評価:** 単純なID/PW認証から、デバイスフィンガープリントやログイン挙動を組み合わせたリスクベース認証（RBA）へ移行するのが実用的。不正ログイン検知の精度が上がる一方、実装コストとレイテンシのトレードオフを見極める必要がある。

- **認可ロジックの分離:** 認証（誰か）と認可（何ができるか）を明確に分離し、RBAC/ABACをミドルウェア層に集約することで、物件データ（draft/public）やユーザー種別（前の住人/次の住人）ごとのアクセス制御の漏れを防げる。Next.jsのMiddleware + Server Actionsでの一元チェックが実装しやすい。

- **サプライチェーン・依存関係の監査:** 認証関連ライブラリ（NextAuth等)は更新頻度が高く、脆弱性修正が頻繁。`bun audit`相当のチェックをCIに組み込み、認証フローに関わる依存は特に優先的にアップデートする運用が2026年の標準的なプラクティス。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のRust-free移行:** Prisma ORMはRustバイナリ依存を廃止し、TypeScript純正のクエリエンジンに移行した。コールドスタートが大幅に短縮され、Vercel EdgeやCloudflare Workersなどのサーバーレス環境でのレイテンシ問題が解消されつつある。

- **Supabaseのブランチング機能活用:** Supabase Branching（PRごとにDBブランチを自動作成）をCI/CDに組み込むことで、マイグレーションの検証をステージング環境なしで安全に行える。弊社規模（MVP〜ベータ）では特に有効で、本番DBを汚さずにスキーマ変更を試せる。

- **RLS(Row Level Security)とPrisma併用の複雑さ:** SupabaseのRLSはPostgres標準機能だが、Prismaのコネクションプーリング（pgbouncer経由）だと`auth.uid()`等のセッションコンテキストが引き継がれない落とし穴がある。認証ロジックをDB層とアプリ層で二重管理しないよう、どちらに正を置くか早期に決める必要がある。

- **pgvectorとAI機能の標準搭載:** Supabaseはpgvectorをデフォルトで同梱し、Prismaも`vector`型の公式サポートを強化している。「次の住人」とのマッチング推薦のような検索機能を、別途ベクターDBを導入せず既存Postgresで実装できるのは運用コスト面で大きい。

- **Edge Function + Prisma Accelerateのキャッシュ戦略:** Prisma Accelerateのグローバルキャッシュ層とSupabase Edge Functionsを組み合わせることで、読み取り頻度の高い物件一覧などをリージョン分散配信できる。ただしキャッシュ無効化のタイミング管理がボトルネックになりやすく、`'draft'/'public'`のようなステータス変更時は明示的なinvalidationが必須。

### 7. WebAssembly Rust performance 2026

- **ポイント1:** WASI Preview 2とComponent Modelの普及により、RustでコンパイルしたWasmモジュールが言語間で安全に相互運用できるようになり、サーバーサイドでのプラグイン機構（例: サンドボックス化された拡張機能）に採用が広がっている。
- **ポイント2:** `wasm-bindgen`や`wasm-pack`のツールチェインが成熟し、ブラウザ側での画像処理・PDF生成・暗号処理など計算負荷の高い処理をRust/WasmにオフロードするパターンがNext.jsプロジェクトでも実用的な選択肢になっている。
- **ポイント3:** WasmGCやSIMD命令のサポートが主要ランタイム（V8, Wasmtime）で安定し、純粋なJS実装と比べて2〜5倍の性能向上が見込める処理（画像変換、位置情報計算など）がある一方、JS↔Wasm間のデータマーシャリングのオーバーヘッドが依然ボトルネックになりやすい。
- **ポイント4:** Cloudflare WorkersやFastlyなどのエッジランタイムがWasmをファーストクラスでサポートしており、Rust/Wasmで書いたロジックをエッジで低レイテンシ実行できるため、物件検索のようなAPIをエッジ最適化する選択肢として検討価値がある。
- **ポイント5:** 小規模チームにとっては、Rust/Wasm導入はビルド複雑性・デバッグ難易度・学習コストのトレードオフが大きく、計測可能なボトルネック（大量データのクライアント処理など）が実際に存在する場合にのみ導入すべきで、現状のMVPフェーズでは優先度は低い。

### 8. Next.js App Router patterns 2026

- **ポイント1:** Partial Prerendering (PPR) が安定版の主流パターンとなり、静的シェルを即時返しつつ動的部分を`<Suspense>`でストリーミングする構成が標準化。物件一覧ページのようにヘッダー/フッターは静的、検索結果だけ動的というケースに最適。
- **ポイント2:** `use cache`ディレクティブによる関数・コンポーネント単位のキャッシュ制御がデフォルト化し、従来の`fetch`オプションやrevalidateタグより細粒度のキャッシュ戦略が組みやすくなった。物件詳細データのキャッシュ無効化をタグベースで精密に制御できる。
- **ポイント3:** Server Actionsが単純なmutationだけでなく、楽観的UI更新（`useOptimistic`）とエラーバウンダリを組み合わせた「フォーム→即時反映→裏で検証」パターンが定着。予約・お問い合わせフォームのUXを大きく改善できる。
- **ポイント4:** `middleware.ts`の責務が肥大化しがちな問題への対策として、認証・リダイレクト判定をEdge Runtimeからより軽量な`proxy`層や`layout`レベルのガードに分散する設計が推奨されるようになった。大規模化しても起動レイテンシを抑えられる。
- **ポイント5:** Route Groups + Parallel Routes + Interceptorsを組み合わせたモーダル実装（詳細→一覧に戻ってもURLが保持される）が、物件詳細のライトボックス表示などで事実上の標準パターンになっている。

### 9. Vercel Edge Functions optimization 2026

- **Edge RuntimeとNode.js Runtimeの統合が進展:** Vercel Fluid Computeの普及により、Edge FunctionsとServerless Functionsの実行モデルの境界が薄くなり、コールドスタートを抑えつつNode.js APIも使えるハイブリッド構成が主流になっています。

- **リージョン単位の実行最適化:** `regions`設定やWaitUntil APIを活用し、DBに近いリージョンでEdge処理を完結させることでレイテンシを削減できます。認証チェックやリダイレクトなどの軽量処理はEdgeに、重い処理はFluid Compute側に振り分ける設計が有効です。

- **バンドルサイズとコールドスタートの監視が必須:** Edge Functionsは1MB前後のサイズ制限があるため、依存パッケージの肥大化がデプロイ失敗やレイテンシ悪化に直結します。`@vercel/edge`やWeb標準API中心の実装に寄せることで軽量化を保てます。

- **ストリーミングレスポンスとAI推論の組み合わせ:** Edge FunctionsからのストリーミングSSE/Server ActionsがAIチャット機能などで一般化しており、TTFB（Time To First Byte）短縮の観点からEdge側でストリームを開始しつつ本体処理をバックグラウンドに委譲する設計が増えています。

- **Observabilityの標準化:** Vercel ObservabilityやOpenTelemetry連携により、Edge Functionsの実行トレースをリージョン別・関数別に可視化できるようになり、コスト（実行時間課金）とパフォーマンスのトレードオフを定量的に判断しやすくなっています。

### 10. TypeScript type safety patterns 2026

- **ポイント1:** `satisfies`演算子と型推論の組み合わせが標準化し、型の明示的な上書きを避けつつ安全性を保つパターンが主流になっている。設定オブジェクトやAPIレスポンスの型チェックで特に有効。
- **ポイント2:** Zodなどのスキーマライブラリによる「実行時検証＋型推論」の一体化が、APIバウンダリやフォーム入力の必須パターンとして定着（本プロジェクトでも`src/lib`のバウンダリで採用方針）。
- **ポイント3:** Branded Types（nominal typing）を使い、`UserId`と`PropertyId`のような構造的に同一だが意味が異なるstring/number型を区別する実装が増え、取り違えバグを型レベルで防止している。
- **ポイント4:** TypeScript 5.x系のconst型パラメータやテンプレートリテラル型を活用し、ステータス管理（例: `'draft' | 'public'`のようなUnion型）でexhaustiveness checkingを強制する設計が定着しつつある。
- **ポイント5:** tRPCやHono RPCのようなEnd-to-Endの型共有アプローチが、フロントエンド・バックエンド間のスキーマずれを防ぐ手段としてAPI層のデファクトになっている。
