# CTO Knowledge - 2026-02-25

## Daily Update (2026-02-25)

### 1. Next.js performance optimization 2026

- **Partial Prerendering (PPR) の本格活用:** Next.js 15+で安定化したPPRにより、静的シェルを即座に配信しつつ動的コンテンツをストリーミングで補完できる。TTFBを劇的に改善しながらパーソナライズも維持できる最重要アーキテクチャパターン。

- **React Server Components による bundle 最小化:** RSCを徹底活用してクライアントサイドJSを削減し、`"use client"` の境界を葉コンポーネントに限定することがベストプラクティス。依存ライブラリのサイズ影響がサーバー側に閉じるため、LCPへの直接改善効果が高い。

- **Turbopack による開発・ビルド高速化:** Webpack後継のTurbopackが本番ビルドでも実用段階に達し、大規模プロジェクトでのビルド時間を60〜80%削減。CI/CDのフィードバックループ短縮が開発速度に直結する。

- **Streaming + Suspense によるデータフェッチ戦略:** `loading.tsx` とネストされたSuspense境界を活用し、ページ全体のブロッキングを排除する。`fetch` のキャッシュ戦略（`no-store` vs `revalidate`）を明示的に設計することで、不要な再フェッチと古いキャッシュの両方を防ぐ。

- **Edge Runtime の選択的適用:** ミドルウェアや認証チェックはEdge Runtimeで実行してレイテンシを最小化する一方、重い処理はNode.js Runtimeに留める使い分けが2026年の標準設計。地理的に近いエッジでの認証判断がUXの体感速度に大きく影響する。

### 2. React Server Components streaming 2026

- **ポイント1:** RSC + Suspense の成熟により、サーバーからのストリーミングが標準パターンとなった。`<Suspense>` バウンダリを細粒度に配置することで、TTFBを最小化しつつ段階的なUI表示が実現可能になっている。

- **ポイント2:** Next.js App Router の `dynamicIO` モードとPartial Prerenderingが安定化し、静的シェルを即時配信しながら動的部分をストリームする「ハイブリッド戦略」がプロダクション標準になりつつある。

- **ポイント3:** Server Actions との統合が深まり、フォームsubmit後のUI更新もストリームで返せるようになった。クライアント側のstate管理を大幅に削減でき、Zustand/Jotaiの使用範囲が自然と縮小している。

- **ポイント4:** React 19の`use()`フックとStreamの組み合わせにより、Promiseを直接renderツリーで扱えるようになった。ウォーターフォールを避けるためには、データフェッチをできるだけServer Componentの上位に引き上げる「Lift data fetching up」パターンが重要。

- **ポイント5:** エラーハンドリングが課題として残る。ストリーミング中のエラーはHTTPヘッダー送信後なので、`error.tsx` での補足に限界がある。本番環境では `onError` コールバックと監視ツール（Sentry等）の適切な統合が必須。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの成熟と採用拡大:** tRPC v11以降、Next.js App RouterやReact Server Componentsとの統合が洗練され、フルスタックTypeScriptプロジェクトでの型安全なAPIが事実上の標準に近づいている。バックエンド・フロントエンド間の型定義重複が排除でき、開発速度が大幅に向上する。

- **GraphQLの位置づけ再評価:** 複雑なデータグラフや多クライアント対応が必要な大規模プロダクトでは依然有効だが、スタートアップや中小規模では過剰設計になりやすい。Apollo Federationの複雑さへの反省から、シンプルなREST or tRPCへの回帰も見られる。

- **RESTの不変的な強さ:** HTTP/3・CDNキャッシュ・OpenAPI 3.1との相性の良さから、外部公開APIや他社連携ではRESTが最適解であり続ける。特にOpenAPIからのコード生成（`openapi-typescript`等）で型安全性も確保できる。

- **エッジ・ストリーミング対応が設計要件に:** Vercel Edge Functions、Cloudflare Workersの普及に伴い、APIはストリーミングレスポンス（Server-Sent Events、ReadableStream）を前提に設計する必要がある。tRPCとGraphQLともにストリーミング対応が進んでいる。

- **選択基準の明確化:** 2026年の実践的指針として「内部API→tRPC、外部公開API→REST+OpenAPI、複雑なデータ集約→GraphQL」という棲み分けが定着しつつあり、一つの技術に統一しようとする動きより、用途別の使い分けが合理的とされている。

### 4. serverless edge computing 2026

- **ポイント1: WebAssembly（Wasm）がエッジの標準実行環境に:** CloudflareやFastlyのエッジランタイムでWasmが主流化し、言語非依存・コールドスタートゼロの軽量コンテナとして本番採用が急増している。

- **ポイント2: AI推論のエッジシフトが加速:** GPUを持つエッジノード（Cloudflare Workers AI、Vercel AI Gateway等）が普及し、LLMの推論をオリジンサーバーではなくユーザー近傍で実行するアーキテクチャが現実的な選択肢になった。

- **ポイント3: エッジDBとのデータ整合性問題が設計の核心:** Cloudflare D1、Turso（libSQL）などのエッジ分散DBが成熟する一方、結果整合性 vs 強整合性のトレードオフ設計がアーキテクチャ品質を左右する最重要課題になっている。

- **ポイント4: コールドスタート問題はほぼ解決済み、次の壁はメモリ制限:** V8 IsolatesベースのランタイムでP99レイテンシは数ms以下に改善されたが、128MB〜256MBのメモリ上限が重量級ライブラリや複雑な処理のエッジ移行を阻んでいる。

- **ポイント5: Next.js等のフレームワークがエッジを「デフォルト」に:** App RouterのEdge Runtimeサポートにより、開発者が意識せずともクリティカルパス（認証・ルーティング・A/Bテスト）がエッジで実行される構成が標準化しつつある。

### 5. authentication security best practices 2026

- **パスキー（Passkey）への移行加速:** FIDO2/WebAuthn標準のパスキーがパスワードレス認証の主流となり、フィッシング耐性と利便性を両立。2026年時点では主要プラットフォーム（Apple/Google/Microsoft）が完全サポートしており、新規プロジェクトではパスワード認証を廃止すべき段階に来ている。

- **継続的認証（Continuous Authentication）の実装:** ログイン時の一回限りの認証から、セッション中の行動分析・デバイス状態監視へシフト。リスクベース認証エンジンを組み合わせることで、ユーザー体験を損なわずに異常アクセスをリアルタイム検知できる。

- **トークン管理のセキュリティ強化:** JWTの有効期限は15分以内を推奨し、リフレッシュトークンはローテーション＋失効リストで管理。`httpOnly` / `Secure` / `SameSite=Strict` Cookieの徹底と、ブラウザストレージへのトークン保存の完全廃止が必須。

- **サプライチェーン攻撃対策としての依存ライブラリ監査:** 認証ライブラリ（OAuth、OIDCクライアント等）への悪意あるコード混入リスクが増大。`bun audit` や Dependabotによる自動更新＋SBOM管理を CI/CD に組み込み、脆弱なバージョンを即検知する体制が不可欠。

- **AI生成コードの認証脆弱性レビュー義務化:** LLMが生成する認証コードにはリレーアタック耐性の欠如やセッション固定化バグが混入しやすい。コードレビューチェックリストに認証フロー専用項目を追加し、セキュリティスキャン（Semgrep等）を自動化することで、AI支援開発時代の品質ゲートを確立する。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6 + Supabase の統合成熟:** Prisma 6のPostgres Adapterが安定し、PrismaとSupabaseの直接統合（`prisma-client-js` + Supabase Connection Pooler via PgBouncer）がプロダクション標準となった。接続数管理とコールドスタート問題が大幅に改善されている。

- **Edge Runtime対応の重要性:** Next.js App RouterやVercel Edge FunctionsではNode.js非対応のためPrisma Accelerateが事実上必須に。SupabaseのEdge Functionsとの組み合わせで、グローバル低レイテンシアーキテクチャが構築しやすくなっている。

- **Row Level Security (RLS) の設計が品質を左右する:** SupabaseのRLSポリシーをORM層（Prisma）と二重管理するアンチパターンが問題化。RLSをデータ層の単一真実源として設計し、アプリ側でのフィルタリングを排除する方針が推奨されている。

- **Supabase Realtime + データモデル設計の連動:** Realtimeのサブスクリプション効率はスキーマ設計に直結する。過度に正規化されたテーブル構成はRealtimeのペイロードを複雑にするため、読み取り最適化の非正規化（ビューやマテリアライズドビュー）との使い分けが重要。

- **型安全性の一気通貫:** Supabase CLIの`supabase gen types typescript`とPrismaのクライアント生成を組み合わせ、DB→API→UIまでの型安全性を確保するパターンが定着。スキーマドリブン開発でランタイムエラーを設計段階で排除できる。

### 7. WebAssembly Rust performance 2026

- **ポイント1: WASM Component Modelの成熟** Component Model（WIT/WASIp2）が2026年に広く採用され、RustのWasmターゲットがサーバーレス・エッジ環境での主流選択肢となっている。`cargo component`ツールチェーンが安定化し、クロス言語相互運用のオーバーヘッドが大幅に削減された。

- **ポイント2: GCとスレッドのネイティブサポート進化** WASMのGC提案とShared Memory/Atomics仕様の安定化により、RustのWasm出力でのゼロコスト抽象化がさらに活きる設計が可能に。特にマルチスレッドWASMでRustの所有権モデルがデータ競合を静的に排除できる強みが際立つ。

- **ポイント3: SIMD・AOTコンパイルによるネイティブ比90%以上の性能** WasmのSIMD拡張（Relaxed SIMD含む）とWasmtime/V8のAOTコンパイル最適化により、数値計算・画像処理・暗号化処理でネイティブコードとほぼ同等の性能を達成。Rustはunsafe不要でこれを活用できる稀有な言語。

- **ポイント4: WASIp2によるサーバーサイドWasmの本格普及** Cloudflare Workers・Fastly Compute・wasmCloudなどがWASIp2ベースのRust WasmをFaaS基盤として採用拡大。コールドスタートがJVMやNode.jsの1/10以下という実測値が出始めており、マイクロサービスの分解戦略に影響。

- **ポイント5: フロントエンドでのWasm利用パターンの収束** Leptos・Yewなど純RustフロントエンドフレームワークよりもRust+JS混在（重処理コアのみWasm化）が実務標準に。バンドルサイズとロード時間のトレードオフを考慮し、「計算集約型処理だけWasm」が推奨アーキテクチャとして定着しつつある。

### 8. Next.js App Router patterns 2026

- **Partial Prerendering (PPR) の実用化:** Next.js 15でPPRが安定版に。静的シェルを即座に配信しつつ動的コンテンツをStreaming注入する手法が主流となり、TTFBとLCPの両立が現実的になった。

- **Server Actions の成熟:** フォーム送信・データ変更をServer Actionsに集約するパターンが定着。APIルートを介さずにサーバー処理が書けるため、コードの往復が減り型安全性も向上した。

- **RSC Boundary 設計の重要性:** `'use client'`境界をコンポーネントツリーの末端に追いやることで、クライアントバンドルを最小化する設計が必須スキルに。Leafコンポーネント戦略と呼ばれるアプローチが広まっている。

- **Parallel Routes + Intercepting Routes の活用:** モーダル、スライドオーバー、タブUIをURLに紐づけて実装するパターンが増加。ブラウザバックで自然に閉じる動作など、UX品質が大幅に向上する。

- **`next/cache` と細粒度キャッシュ制御:** `revalidateTag` / `revalidatePath` を使ったオンデマンドキャッシュ無効化が標準化。CDNとサーバーキャッシュの二層管理がApp Routerの性能チューニングの核心になっている。

### 9. Vercel Edge Functions optimization 2026

- **ポイント1: Edge Runtimeの積極活用でCold Startを排除:** Edge FunctionsはV8 Isolateベースのためサーバーレス関数より起動が高速（~0ms Cold Start）。認証ミドルウェア・A/Bテスト・ジオルーティングはEdgeに移行し、Node.js Runtimeはデータベース接続が必要な処理に限定する。

- **ポイント2: Streaming ResponseとSuspenseの組み合わせ:** `ReadableStream`を使ったストリーミングレスポンスをApp RouterのServer Componentsと組み合わせることで、TTFB（初回バイト時間）を大幅削減。AIレスポンス・長文生成などのユースケースで特に効果的。

- **ポイント3: Edge ConfigとKVの使い分けを徹底:** Vercel Edge Config（超低レイテンシ読み取り専用ストア）はフィーチャーフラグ・リダイレクトルール管理に特化させ、Vercel KVはセッションキャッシュに使う。用途を混同するとコスト増と遅延悪化を招く。

- **ポイント4: Region制約とデータ主権への対応:** Edge Functionsはグローバル分散実行のため、特定リージョンのデータベースへの接続はレイテンシが増大する。`export const config = { regions: ['nrt1'] }`で東京リージョン固定化し、Supabase/PlanetScaleのリージョンと合わせる設計が2026年のベストプラクティス。

- **ポイント5: Bundleサイズ制限（1MB）の意識:** Edge RuntimeはNode.js APIの大部分が使えず、かつバンドルサイズ上限が厳しい。`@vercel/og`等の重いライブラリは動的インポートかServer Functionsへ退避し、Edge用コードは依存関係を最小化したうえで`next build`後に`vercel build`でサイズを定期確認する。

### 10. TypeScript type safety patterns 2026

- **`satisfies` 演算子の本格活用:** TypeScript 4.9以降の`satisfies`は型チェックと型推論を両立でき、設定オブジェクトや定数定義で`as const`の代替として広く採用されている。型安全性を犠牲にせずに値の自動補完が得られる。

- **Branded Types（Opaque Types）によるドメイン型安全:** `type UserId = string & { readonly _brand: 'UserId' }`パターンが主流化し、プリミティブ型の誤用（UserIdをOrderIdに渡すミスなど）をコンパイル時に防ぐ。`zod`や`effect-ts`がこれをネイティブサポート。

- **`NoInfer<T>`ユーティリティ（TS 5.4）の実用化:** ジェネリック関数の型推論を意図的に制限できるようになり、APIデザインの誤用防止が格段に向上した。特にデフォルト値を持つジェネリック関数で意図しない型推論を抑制できる。

- **`using`宣言とリソース管理（TS 5.2）:** `Symbol.dispose`を利用した明示的リソース管理が普及し、DB接続・ファイルハンドル・ロックなどのリーク防止を型システムで保証できる。Next.jsやBunのサーバーサイドコードで特に有効。

- **Template Literal TypesとPattern Matching:** 文字列リテラル型の組み合わせで、APIルートパスやCSSクラス名などの文字列構造を型レベルで検証するパターンが定着。ランタイムエラーの大幅削減につながり、`tRPC`や`Hono`のルーティングAPIがこれを応用している。
