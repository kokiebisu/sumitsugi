# CTO Knowledge - 2026-03-11

## Daily Update (2026-03-11)

### 1. Next.js performance optimization 2026

- **React Server Components (RSC) の徹底活用:** クライアントバンドルサイズを最小化するため、データフェッチロジックをすべてServer Componentsに移行し、`'use client'`はインタラクティブな葉コンポーネントのみに限定する。

- **Partial Prerendering (PPR) の本番投入:** Next.js 15以降でStableになったPPRにより、静的シェルを即座に返しつつ動的コンテンツをStreaming配信できる。TTFB改善とパーソナライズの両立が実現可能。

- **`<Image>`と`next/font`による Core Web Vitals 最適化:** LCP改善のため`priority`属性と`sizes`の適切な設定が必須。フォントは`next/font`でセルフホスティングし、layout shiftを排除する。

- **Route Segment Configによるキャッシュ戦略の精緻化:** `revalidate`・`dynamic`・`fetchCache`をセグメント単位で制御し、過剰なon-demand revalidationを避けてサーバー負荷を抑制する。

- **Bundle Analyzerと`@next/bundle-analyzer`の定期実行:** 大型依存パッケージ（date-fns, lodash等）のtree-shakingやdynamic importによるコード分割を継続的に検証し、JS転送量を監視する体制を開発フローに組み込む。

### 2. React Server Components streaming 2026

- **Suspense境界の粒度最適化:** 2026年現在、RSCストリーミングはSuspense境界をコンポーネント単位ではなくデータ依存グラフ単位で設計することがベストプラクティスとなり、TTFBを維持しながらLCPを大幅改善できる。

- **PPR（Partial Prerendering）の本番採用加速:** Next.js 15以降でPPRが安定化し、静的シェルを即座に配信しつつ動的スロットをストリームで埋めるパターンが主流に。キャッシュ戦略との組み合わせでサーバーコスト削減も実現している。

- **Server Actions × Optimistic UIの成熟:** RSCとServer Actionsの統合により、楽観的更新とリバリデーションが宣言的に書けるようになり、従来のREST+クライアント状態管理より大幅にコード量が削減されている。

- **Edge Runtimeでのストリーミング制約解消:** Cloudflare Workers・Vercel Edge等でのWeb Streams API対応が整い、Node.js RuntimeとEdge Runtimeで同等のRSCストリーミング体験が得られるようになった。デプロイ先の選択肢が広がっている。

- **バンドルサイズとWaterfall問題のトレードオフ管理:** RSCによりクライアントJSを削減できる一方、サーバー側のデータfetchウォーターフォールが新たなボトルネックに。`Promise.all`による並列fetch設計とpreloadパターンの徹底が2026年の重要な設計指針となっている。

### 3. API design REST GraphQL tRPC 2026

- **tRPCの本格普及:** Next.js + TypeScript環境でのtRPC採用が加速し、エンドツーエンドの型安全性がスタンダードになりつつある。スキーマ定義なしにフロントとバックで型を共有できる開発体験は、小〜中規模チームでの生産性を大幅に向上させる。

- **GraphQLの役割の再定義:** 複雑なBFF（Backend for Frontend）や複数マイクロサービスの集約には依然有効だが、単一サービスへの過剰採用は減少傾向。Federation v2によるスキーマ合成が大規模組織での主要ユースケースになっている。

- **RESTの回帰とHTTP/3活用:** シンプルなCRUD操作ではRESTが再評価されており、OpenAPI 3.1 + Zodによる自動バリデーション・型生成が実用的な選択肢として定着。HTTP/3対応により低レイテンシが得られる環境ではREST Streamingも有力。

- **Hono / ElysiaJSなど軽量ランタイム対応フレームワークの台頭:** EdgeランタイムやBun対応のAPIフレームワークが成熟し、コールドスタートを気にせずサーバーレスAPIを設計できる時代になった。tRPCとの組み合わせが特に相性が良い。

- **AIエージェント向けAPI設計の重要性:** MCPやOpenAPI仕様をベースにしたツール公開が急増しており、人間だけでなくAIエージェントが消費しやすいAPI設計（明確なスキーマ、冪等性、適切なエラーコード）が新たなベストプラクティスとして浮上している。

### 4. serverless edge computing 2026

- **エッジでのAI推論の標準化:** WebAssembly（WASM）とWASI P2の成熟により、LLMの軽量モデル（1-7Bパラメータ）がCDNエッジノードで直接実行可能になり、レイテンシを100ms以下に抑えたリアルタイムAI処理が普及している。

- **Durable ObjectsとEdge SQLの台頭:** Cloudflare D1・Workers KVの進化により、エッジでのステートフルなアプリケーション構築が現実的になった。従来「エッジはステートレス」という制約が崩れ、グローバル分散DBとの組み合わせでフルスタックをエッジに移行するアーキテクチャが増加している。

- **Cold Startの事実上の解消:** V8 Isolateベースのランタイム（Cloudflare Workers, Deno Deploy）がNode.jsベースのLambdaに対して圧倒的な起動速度優位を持ち、2026年時点では「サーバーレス＝レイテンシ問題」という認識は過去のものになりつつある。

- **マルチクラウドエッジオーケストレーション:** AWS CloudFront Functions、Vercel Edge Runtime、Fastly Compute@Edgeなど各社の仕様差異を吸収するための抽象化レイヤー（WinterTC/WinterCG準拠）が業界標準として定着し、ベンダーロックイン回避が容易になっている。

- **コスト構造の再評価が必須:** エッジ実行はリクエスト数課金のため、バースト耐性は高いが、常時高頻度のワークロードではオリジンサーバーより高コストになるケースがある。アーキテクチャ設計時にエッジ適合性（キャッシュ可能・軽量・ステートレス寄り）を事前に判断するガバナンスが重要。

### 5. authentication security best practices 2026

- **パスキー（FIDO2/WebAuthn）の標準採用:** パスワードレス認証がデファクトスタンダードとなり、フィッシング耐性のあるパスキーをプライマリ認証手段として実装することが必須。レガシーパスワードフローの段階的廃止を計画に組み込むべき。

- **ゼロトラスト＋継続的認証:** 「一度認証すれば信頼」モデルは終焉。セッション中も行動パターン・デバイス状態・ネットワーク文脈を継続評価し、リスクスコアが閾値を超えた時点で再認証を要求するアダプティブ認証が基本設計となる。

- **トークンバインディングとDPoP（Demonstrating Proof-of-Possession）:** Bearer tokenの横取り攻撃対策として、OAuthトークンをクライアント鍵ペアに紐づけるDPoPが実用フェーズへ。JWTをそのままlocalStorageに保存するパターンは2026年時点では設計ミスとみなされる。

- **AIを活用した異常検知の内製化:** サードパーティIDaaSに依存するだけでなく、ログイン試行パターン・地理的異常・デバイスフィンガープリントをMLで分析する層を自前で持つことで、Account Takeover（ATO）攻撃の早期検知精度が大幅に向上する。

- **サプライチェーン攻撃への認証ライブラリ監査:** 認証関連npm/pypiパッケージへの悪意ある依存注入が増加傾向。`bun audit`や`socket.dev`によるリアルタイム依存関係監視をCIに組み込み、認証スタックの変更PRは必ずセキュリティレビューを必須化する。

### 6. database architecture Prisma Supabase 2026

- **Prisma 6のEdge Runtime対応:** Prisma 6でEdge Runtime（Vercel Edge, Cloudflare Workers）への本格対応が進み、`@prisma/adapter-pg`等のドライバーアダプターを使うことでサーバーレス環境でのコネクション管理が大幅に改善された。

- **Supabase + Prismaの相性問題とPgBouncer:** SupabaseはデフォルトでPgBouncerトランザクションモードを使用するため、Prismaのマイグレーション・名前付きプリペアドステートメントと競合する。本番では`?pgbouncer=true&connection_limit=1`パラメータを必ず設定し、Direct URLとPooling URLを分けて管理することが必須。

- **Supabase Auth + Row Level Security（RLS）の強化:** 2025-2026年にかけてRLSのパフォーマンス最適化が進み、Prismaからも`SET LOCAL role`でRLSコンテキストを渡すパターンが定番化。ただしPrismaはRLS自体を管理できないため、マイグレーションファイルにSQL直書きでポリシーを追加する運用が必要。

- **Drizzle ORMの台頭とPrismaとの比較:** 型安全なSQLファーストアプローチのDrizzleがSupabaseコミュニティで急速に普及。PrismaはDX（開発体験）で優位だが、Drizzleはバンドルサイズ・Edge性能・Supabaseとの親和性で勝る。新規プロジェクトでは要件に応じた選択が重要。

- **Supabase Realtime + 楽観的UI設計:** Supabase Realtimeのブロードキャスト・プレゼンス機能が成熟し、Prismaによるデータ書き込みとRealtimeのサブスクリプションを組み合わせたリアルタイムUIが実用段階に。ただしPrismaトランザクションとRealtimeイベントの整合性はアプリ層で担保する必要がある。

### 7. WebAssembly Rust performance 2026

- **Component Model の成熟:** WASIp2（WASI Preview 2）とComponent Modelが2026年に実用段階に達し、Rustで書いたWasmモジュールを言語をまたいで安全に合成できるようになった。マイクロサービス的なWasm合成アーキテクチャが現実的な選択肢になっている。

- **GC不要の優位性が際立つ:** JavaやKotlinのWasm-GC対応が進む中、RustはGCオーバーヘッドゼロのまま同等機能を提供できる。レイテンシ予測可能性が求められるリアルタイム処理（音声・映像・ゲーム）でRust+Wasmが事実上の標準になりつつある。

- **SIMD・スレッド対応の普及:** Wasm SIMDとshared memoryスレッドがChrome/Firefox/Node.js全環境で安定稼働。`std::simd`（Rustの標準SIMD API）経由で自動的にWasm SIMDにコンパイルされ、CPU集約処理で2〜4倍の高速化が得られるケースが増えている。

- **ツールチェーン成熟によるビルドサイズ問題の緩和:** `wasm-opt`（Binaryen）+ Rustの`wasm-pack`最新版の組み合わせで、バイナリサイズが大幅に削減。`cargo-component`がComponent Model対応ビルドを自動化し、開発者体験が大きく改善した。

- **エッジ実行環境との親和性:** Cloudflare Workers・Fastly Compute@Edge等がWasm Rustをファーストクラスサポート。コールドスタート1ms以下・メモリ分離保証という特性が、セキュリティ要件の高いエッジAPIで評価されており、Node.js/Denoからの移行事例が増加中。

### 8. Next.js App Router patterns 2026

- **Server Components をデフォルトに:** 2026年時点では、データフェッチはServer Componentsで完結させ、`'use client'`はインタラクション必須の末端コンポーネントのみに限定するのが鉄則。クライアントバンドルサイズを劇的に削減できる。

- **Partial Prerendering (PPR) の本格活用:** 静的シェルと動的ストリーミングを同一ページで混在させるPPRが安定版に。`<Suspense>`境界の設計がパフォーマンス最適化の主戦場になっている。

- **`use cache` ディレクティブへの移行:** Next.js 15以降、`fetch`のキャッシュオプションより`use cache`ディレクティブが推奨に。関数・コンポーネント単位でキャッシュ戦略を明示でき、`cacheLife`/`cacheTag`でfine-grainedな制御が可能。

- **Server Actions の成熟:** フォーム処理・ミューテーションはServer Actionsに集約。`useActionState`と組み合わせることでAPI Routeを介さない型安全なデータ更新が実現でき、コードが大幅にシンプルになる。

- **`next/after` でリクエスト後処理を分離:** レスポンス返却後の非同期処理（ログ送信・分析・通知）は`after()`APIで明示的に分離するパターンが定着。メインレスポンスのレイテンシに影響を与えずバックグラウンド処理を実行できる。

### 9. Vercel Edge Functions optimization 2026

- **Edge Runtime の成熟とフルスタック化:** Vercel Edge Functions は2026年時点でWASM対応が本格化し、Node.js互換APIの範囲が大幅拡張。従来はMiddlewareに限定していた用途が、データ取得・認証・レスポンス加工まで統合可能になった。

- **Fluid Compute による Cold Start 撲滅:** Vercelが導入したFluid Computeモデルにより、従来のEdge/Serverlessの境界が曖昧化。リクエスト間でのV8 Isolate再利用が標準化され、実測でのp99レイテンシが大幅改善されている。

- **ISR + Edge Cache の組み合わせが最強パターン:** `stale-while-revalidate` をEdge側でコントロールするパターンが確立。特に日本語コンテンツ重視のサービスでは、CDN境界でのキャッシュ戦略がTTFBに直結するため、`Cache-Control` ヘッダ設計が差別化ポイントになる。

- **Compute Limit の現実的な壁:** Edge Functionsの実行時間上限（25ms CPU時間）は依然として厳しく、重い処理はServer Actionsや通常のServerless Functionsに委譲する設計分離が必須。ORMや暗号処理をEdgeに混在させるアンチパターンが散見される。

- **Regional Execution の精度向上:** `export const runtime = 'edge'` に加え、`preferredRegion` 指定による近距離実行が実用レベルに。データベース（Supabase/PlanetScale）のリージョンとEdge実行リージョンを揃えることで、往復レイテンシを50ms以下に抑えるアーキテクチャが標準化されつつある。

### 10. TypeScript type safety patterns 2026

- **Branded Types の標準化:** `string` や `number` の素朴な利用を避け、`type UserId = string & { readonly _brand: 'UserId' }` のようなブランド型が設計上の境界を強化する主流パターンになっている。ドメイン境界での型混入バグをコンパイル時に防げる。

- **`satisfies` 演算子の積極活用:** TypeScript 4.9+ の `satisfies` が2026年では必須知識。型推論の恩恵を保ちつつ型チェックを適用できるため、設定オブジェクトやルートマップの定義で `as const` と組み合わせる実践が定着している。

- **Zod + `z.infer<>` によるランタイム・コンパイル時の統一:** APIレスポンスやフォーム入力のバリデーションをZodスキーマで定義し、`z.infer<typeof schema>` で型を導出するパターンが事実上のスタンダード。型定義とバリデーションロジックの二重管理が消える。

- **Template Literal Types の実戦投入:** `type Route = '/users' | '/users/${string}'` のようなテンプレートリテラル型が、ルーティングやイベント名の型安全性を劇的に向上させる。特にAPI定義ライブラリ（tRPC等）の内部実装で複雑な型パズルが現実的に動作するようになった。

- **`noUncheckedIndexedAccess` の有効化が標準に:** `tsconfig.json` でこのオプションを有効にすることで、配列アクセス時に `T | undefined` が返るようになり、境界外アクセスのバグをコンパイル時に検出できる。2026年の新規プロジェクトではデフォルト有効が推奨される。
