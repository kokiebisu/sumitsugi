# プロダクトミーティング #14-3: 問い合わせ機能（F-201〜F-206）

**日時:** 2026-02-09
**参加ペルソナ:** 🌱 ハル、🏠 ユキ、🏢 田中オーナー、📋 佐藤さん
**ファシリテーター:** 👤 CPO

---

## 背景

`docs/requirements/features/inquiry.md` の機能仕様について、ペルソナ座談会で決定根拠を検証・記録する。

---

## 議論

👤 **CPO:** 次は問い合わせの仕組みです。ハルさんが気になる部屋を見つけて、どうアクションしますか？

🌱 **ハル:** 「問い合わせフォーム（F-201）は当然として、**送った後どうなるか**が気になります。『問い合わせを受け付けました』って確認メール（F-204）は欲しい。返事がいつ来るか分からないのが一番不安。あと、自分の問い合わせがどの段階にあるか（F-203）は...MVPでは手動案内でいい気がする。最初は件数少ないし」

🏠 **ユキ:** 「問い合わせ一覧（F-202）は私にとって必須です。何人から問い合わせが来てるか把握したい。**F-204の自動通知**は絶対欲しい。問い合わせが来てるのに気づかないのが一番怖い。メール通知、必須です」

🏢 **田中オーナー:** 「問い合わせの流れは入居者同士の話だから口を出すつもりはないけど、**承認リマインド（F-205）と期限切れ処理（F-206）**は気になります。管理会社に相談するタイミングが遅れると、退去日に間に合わなくなるでしょ？でも自動通知って...最初の数件で仕組みが分かってないうちに自動で通知が来ても混乱するだけでは？」

📋 **佐藤さん:** 「田中さん、その通りです。**最初は運営が手動でやった方がいい**。通知のタイミングや文面って、実際にやってみないと分からないじゃないですか。自動化は後でいい。うちに余計な通知が飛んでくるのも困るし」

🌱 **ハル:** 「佐藤さんの言う通り、**MVPは手動で十分**ですよね。ステータスの8段階も、画面に表示するのはPost-MVPでいい。メッセージで『今こういう状況です』って教えてもらえれば」

🏠 **ユキ:** 「ハルさんに同意。F-205とF-206はPost-MVPでいい。**最初は運営がつきっきりで対応する**んだから、自動化は知見が貯まってから。文面とタイミングを間違えると、前の住人のプレッシャーになる。『早くしろ』みたいな通知が来たら萎えます」

---

## 決定事項

| 機能                         | 決定     | 根拠                                                                       |
| ---------------------------- | -------- | -------------------------------------------------------------------------- |
| **F-201 問い合わせフォーム** | MVP必須  | 次の住人のアクション起点（ハル）                                           |
| **F-202 問い合わせ一覧**     | MVP必須  | 前の住人の管理に不可欠（ユキ「気づかないのが一番怖い」）                   |
| **F-203 ステータス管理画面** | Post-MVP | データモデルは8段階保持、画面表示はPost-MVP。メッセージで手動案内（ハル）  |
| **F-204 自動通知メール**     | MVP必須  | 問い合わせの取りこぼし防止（ユキ）                                         |
| **F-205 承認リマインド**     | Post-MVP | 最初は運営手動プッシュ。文面・タイミングは実運用で見極め（佐藤さん、ユキ） |
| **F-206 期限切れ自動処理**   | Post-MVP | 最初の数件は手動対応（田中オーナー）                                       |
