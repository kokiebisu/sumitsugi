# プロダクトミーティング #8: 内見体験の具体設計

**日時:** 2026-02-07
**議題:** 内見フロー（ステップ4〜5）の具体設計 + 簡易メッセージ機能のMVP格上げ
**参加ペルソナ:** 🏠 ユキ、🔄 トモヤ、🌱 ハル、💐 ミナ、🍵 ノリコ

---

## 背景

引き継ぎフロー9ステップのうち、ステップ4「内見調整」とステップ5「内見実施」の具体的な体験設計が未詳細だった。「内見日程の調整」「前の住人が家具を説明」としか書かれておらず、以下が未定義：

- **安全策**: 知らない人を自宅に招く/知らない人の自宅に行くリスクへの対処
- **日程調整の仕組み**: メール往復の摩擦をどう減らすか
- **内見当日のガイダンス**: 初めての人が何を確認すべきか
- **内見後のフォロー**: 返事がない場合の対処
- **コミュニケーション手段**: メールのみで内見調整が回るのか（#3で「メッセージングはPhase 2」と仮決定していたが再検証が必要）

---

## 議論のハイライト

### 1. 安全面の懸念 — 「受け入れる側」と「訪問する側」の双方が不安

> 🏠 ユキ: 「正直、ちょっと怖い。一人暮らしの部屋に知らない人を入れるわけだから。せめて事前にどんな人か分かってたら安心」
> 🍵 ノリコ: 「女性の一人暮らしに知らない人が来るのは年齢関係なく心配」
> 🌱 ハル: 「行く側も不安。一人で知らない人の家に行くのも結構勇気いる」

**議論の深掘り:**

当初、本人確認の厳格化（身分証アップロード等）も検討された。しかしトモヤが「Airbnbだって最初は最低限の本人確認で始めた。MVPで身分証まで求めたら登録のハードルが上がりすぎる」と指摘。

**結論の根拠:**

- tsumugiの問い合わせ時点で**アカウント登録済み**（名前・メールアドレスが紐づいている）→ 完全匿名ではない
- 問い合わせフォームに既に「自己紹介」「興味の理由」フィールドがある → 追加開発なしで事前情報共有が可能
- 内見日時をtsumugiに記録することで**万一のトラブル時に第三者的な記録**が残る
- 身分証確認はPhase 2以降、トラブル事例が実際に発生した場合に検討

**却下された案:**

- 身分証アップロード必須 → 登録ハードル過剰（MVP段階）
- 管理会社の立ち会い → 座談会#5で佐藤さんが明確に拒否「立ち会いは正直きつい」
- ビデオ通話での事前面談 → 開発工数に見合わない

### 2. 日程調整の摩擦 — メール3往復問題

> 🔄 トモヤ: 「日程調整が一番モタつく。メールで3往復くらいかかる」
> 🍵 ノリコ: 「前の住人が空いてる日を3つ出して、そこから選んでもらう方がシンプル」

**議論の深掘り:**

トモヤの実体験として、前回tsumugiで家具を引き継いだ際に日程調整だけで**5日間**かかった。原因は「いつが空いてますか？」→「土曜日は？」→「その日は予定が...来週は？」のオープンエンドな往復。

ノリコの「3候補提示」案は、ビジネスのミーティング調整ツール（Calendly等）のパターンを日常に落とし込んだもの。選択肢を絞ることで往復を**1回**に削減できる。

**結論の根拠:**

- 3候補提示→選択は**テンプレート化可能**（簡易メッセージの日程調整テンプレートで実装）
- Calendly等の外部ツール連携はMVPでは過剰
- 所要時間「30分〜1時間」はトモヤの実体験とユキの感覚の合意。ユキ：「1時間あれば十分。それ以上は疲れる」

**却下された案:**

- Calendly連携 → 外部ツール依存、年配ユーザー（ノリコ）にハードル
- 自由入力の日程提案 → オープンエンドになり往復が増える
- tsumugiがAIで最適日程を提案 → MVP段階で過剰

### 3. 内見当日のガイダンス不足 — 「何を聞けばいいか分からない」問題

> 🔄 トモヤ: 「前に内見した時、何を聞けばいいか分からなかった」
> 🌱 ハル: 「初めての一人暮らしで内見自体が初めて。緊張する」

**議論の深掘り:**

通常の賃貸内見は不動産屋が案内・説明するが、tsumugiの内見は**前の住人が直接案内する**という特殊な形態。次の住人にとっては「何を確認すべきか」、前の住人にとっては「何を説明すべきか」のガイダンスが不在。

トモヤが「家具リスト（写真付き）を印刷できるようにすれば、リスティングに載ってる情報がそのまま内見のガイドになる」と提案。ノリコは「スマホだけだとやっぱり不安。紙の方が一緒に見やすい」と印刷可能形式を支持。

**結論の根拠:**

- リスティングの家具リスト（出品時に登録済み）を**印刷可能なレイアウト**で出力 → 追加のコンテンツ作成不要
- チェックリスト形式にすることで**内見の議題リスト**として機能 → 「何を話せばいいか」問題を解決
- 「引き継ぐ / 引き継がない / 検討中」の3択は、ステップ6（家具リスト確定）の**事前整理**として機能
- 印刷可能にすることで、デジタルが苦手なノリコでも安心して使える

### 4. 部分引き継ぎの気まずさ — チェックリストが解消する対人ストレス

> 💐 ミナ: 「全部じゃなくて一部だけ引き継ぎたいけど、その場で気まずくならないか心配」
> 🏠 ユキ: 「正直に言ってくれた方が助かる。口頭だけだと後から言った言わないになるから、チェックリストで一緒に確認できるといい」

**議論の深掘り:**

ミナの懸念は座談会#7（部分引き継ぎモデル）の文脈と直結。「前の住人が全部引き継いでほしいと思っている場合に、目の前で『これいらない』と言うのが気まずい」。

ユキの回答が意外だった：「後から言われる方が困る」。つまり前の住人側も**早い段階で正直な意向を知りたい**。チェックリストという「フォーマット」があることで、**個人的な拒否ではなくプロセスの一部**として「引き継がない」を表明できる。

**結論の根拠:**

- チェックリストは「仕組みとしてNoを言える場」を提供 → 対人ストレスの構造的解決
- 座談会#7のFurnitureItem型（core/additional）の設計と連動
- 口頭の曖昧な合意を防ぎ、ステップ6の`agreedFurnitureIds`確定がスムーズに

### 5. 内見後のフォロー不在問題 — 「音信不通」が最大のストレス

> 🏠 ユキ: 「内見して『いい感じでした！』で終わって、そのあと連絡がないパターンが一番困る」
> 💐 ミナ: 「すぐ決められない場合もある。彼氏と相談しないといけないし、3日〜1週間は考える時間がほしい」

**議論の深掘り:**

ユキとミナの間に「前の住人は早く返事がほしい」vs「次の住人には考える時間がほしい」の対立が発生。

落としどころとして**期限の明示化**が浮上。ミナ：「期限があれば逆に安心。なんとなく先延ばしにしなくて済む」。ユキ：「7日なら全然待てる。でもそれ以上だと不安」。

トモヤが「前の住人側にもステータスが見えるようにすべき」と提案。7日未回答の場合は前の住人に「まだ検討中のようです」と通知することで、**双方の期待値を揃える**。

**結論の根拠:**

- フォローメール自動送信（内見翌日）で**次の住人に行動を促す**
- 「3日以内にご意向をお聞かせください」は推奨であり、期限は7日 → ミナのような「相談が必要」なケースにも対応
- 7日未回答で前の住人に通知 → 前の住人が「忘れられてるのでは」と不安にならない
- 意向回答の選択肢に「②一部のみ希望」を含めることで、部分引き継ぎへのスムーズな移行を担保

**却下された案:**

- 3日期限（厳格） → ミナのようなカップルの相談時間が足りない
- 期限なし → ユキの不安解消にならない、フロー全体が停滞するリスク
- 前の住人から催促メッセージ → 対人ストレスが生じる。tsumugiが自動で間に入る方が良い

### 6. メッセージング機能のMVP格上げ — メールのみでは内見フローが回らない

内見フローの議論を通じて、メールベースのコミュニケーションに**3つの構造的問題**があると判明：

> 🔄 トモヤ: 「メールって見逃す。スレッドがバラバラになる」
> 🏠 ユキ: 「知らない人にメールアドレスを知られるのは微妙」
> 🌱 ハル: 「メールだと毎回『お世話になっております』から書かないといけない気がして腰が重い」

**3つの構造的問題:**

| #   | 問題               | 影響                                                     | メールでは解決不可能な理由                                                 |
| --- | ------------------ | -------------------------------------------------------- | -------------------------------------------------------------------------- |
| 1   | **メアド露出**     | 安全面のリスク。特に女性の一人暮らし（ユキ、ノリコ）     | Reply-toでメアドが見える。匿名リレーは開発コストが簡易メッセージと大差ない |
| 2   | **スレッド分散**   | 日程調整・家具相談・フォローが別々のメールに散らばる     | メーラー依存。tsumugiが履歴を管理できない                                  |
| 3   | **心理的ハードル** | メールの形式性が返信を遅らせる（特にハルのような若年層） | メール文化自体の問題。チャット的UIでないと解決しない                       |

**3つの選択肢を比較検討:**

|                  | **A: メールのみ** | **B: 簡易メッセージ** | **C: フルチャット** |
| ---------------- | ----------------- | --------------------- | ------------------- |
| 開発工数         | ゼロ              | 中程度                | 大                  |
| メアド露出       | あり              | なし                  | なし                |
| スレッド管理     | 不可              | 可能                  | 可能                |
| 心理的ハードル   | 高い              | 低い                  | 最低                |
| 既読表示         | なし              | **なし**              | あり                |
| リアルタイム更新 | なし              | **なし**              | あり                |
| MVPに妥当？      | 摩擦大            | **バランス良**        | 過剰                |

**Cを却下した根拠（ノリコの指摘）:**

> 🍵 ノリコ: 「チャット機能を作り込むのって大変なんじゃないの？既読とか通知とか、ちゃんと作ろうとしたらすごい量になりそう」

既読表示は**「読んだのに返事しない」プレッシャー**を生むデメリットもある（ミナ：「既読つくと焦る」）。リアルタイム更新もWebSocket等の追加インフラが必要。

**Aを却下した根拠:**
メアド露出問題は匿名リレー（メールを中継する仕組み）で技術的に解決可能だが、その開発コストは簡易メッセージ機能と**ほぼ同等**。同じコストをかけるなら、スレッド管理・心理的ハードル問題も同時に解決できるBの方が合理的。

**Bに決定した根拠:**

- メアド露出・スレッド管理・心理的ハードルの**3問題を同時に解決**
- 既読表示・リアルタイム更新を**意図的に除外**することで開発スコープを制限
- メールは「通知」として残り、実際の会話はtsumugi画面上 → メルカリと同じモデルで、ユーザーにとって理解しやすい
- 日程調整テンプレートを組み込むことで**内見調整の摩擦を直接解消**

## 決定事項

### 内見前

| 項目               | 決定内容                                                                             | 根拠                                                                       |
| ------------------ | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| **日程調整方法**   | 前の住人が空き日時を3候補提示 → 次の住人が選択（簡易メッセージ内のテンプレート使用） | メール往復を1回に削減（トモヤの5日間→最短即日）                            |
| **事前共有情報**   | 次の住人: 名前、入居予定時期、興味の理由、同行者の有無。前の住人: 退去予定日         | 安全面の担保＋「本気度」判断材料（問い合わせフォームに既存フィールドあり） |
| **所要時間の目安** | 30分〜1時間                                                                          | トモヤの実体験（30分で十分）＋ユキの許容範囲（1時間が上限）                |

### 内見当日

| 項目                   | 決定内容                                                                                     | 根拠                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| **内見チェックリスト** | 家具リスト（写真付き）を印刷可能な形式で提供。「引き継ぐ / 引き継がない / 検討中」をチェック | ①ガイダンス不足の解消 ②部分引き継ぎの気まずさ軽減 ③ステップ6のagreedFurnitureIds事前整理 |
| **案内者**             | 前の住人が直接案内（管理会社の立ち会い不要）                                                 | 座談会#5で佐藤さんが明確に拒否。前の住人が住んでいる物件なので入居者対応                 |
| **同行者**             | 事前連絡あれば複数人OK                                                                       | ミナの同棲ケース。事前連絡がないと前の住人が不安（ユキ）                                 |

### 内見後

| 項目                 | 決定内容                                                                                           | 根拠                                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **フォローメール**   | 内見翌日にtsumugiから次の住人に自動送信「内見はいかがでしたか？3日以内にご意向をお聞かせください」 | 前の住人が催促する対人ストレスを回避。tsumugiが間に入る                                                |
| **意向回答期限**     | 内見後7日以内に回答（3日推奨）。7日未回答で前の住人に「まだ検討中のようです」通知                  | 3日: 即決可能な人向け推奨。7日: 相談が必要なカップル（ミナ）への配慮。前の住人への状況通知で不安を解消 |
| **意向回答の選択肢** | ①引き継ぎ希望（家具リスト確定フローへ）②一部のみ希望（詳細選択）③辞退                              | 座談会#7の部分引き継ぎモデルとの接続。「②一部のみ」を明示することで辞退率を下げる                      |

### 安全策（MVP）

| 対策                                                                | 根拠                                                                              |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 問い合わせ時点でtsumugiアカウント＋氏名が交換済み（メアドは非公開） | 簡易メッセージ導入により個人メアド非公開が実現。完全匿名ではない安心感            |
| 内見日時がtsumugiに記録される（タイムスタンプ）                     | 万一のトラブル時の第三者記録。追加開発コストほぼゼロ（viewingDateフィールド既存） |
| 複数人内見は事前連絡制                                              | 「何人来るか分からない方が怖い」（ユキ）。同棲カップルの内見は自然なユースケース  |

**Phase 2で検討:** 身分証アップロード、ビデオ通話での事前面談、内見後の安全確認通知

### 簡易メッセージ機能（Phase 2 → MVP格上げ）

**MVPスコープ（意図的に小さく）:**

- テキストメッセージの送受信（画像・ファイル添付なし）
- 日程調整テンプレート（日付3候補をポチポチ選択）
- 新着メッセージのメール通知
- 問い合わせごとのスレッド管理

**意図的に除外（スコープクリープ防止）:**

| 除外機能                 | 除外理由                                                      |
| ------------------------ | ------------------------------------------------------------- |
| 既読表示                 | 「読んだのに返事しない」プレッシャーがUXを悪化させる（ミナ）  |
| リアルタイム更新         | WebSocket等の追加インフラが必要。ページリロードで十分         |
| タイピングインジケーター | フルチャットの領域。MVPでは不要                               |
| 画像・ファイル添付       | リスティングに写真は既にある。メッセージ内の画像共有はPhase 2 |
