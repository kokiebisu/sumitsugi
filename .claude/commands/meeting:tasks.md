# Task Decomposition & Prioritization

PMとCTOが確定済みの要件を開発タスクに分解し、優先度を整理するミーティング。

## Quick Start

**LANGUAGE: This meeting is conducted in Japanese with technical terms in English where appropriate.**

**前提:** `/meeting:tech` で要件が技術的に検証済みであること

**When invoked, immediately start the meeting:**

```
タスク分解ミーティング開始

PM: こんにちは、CTOさん。技術ミーティングで確定した要件をタスクに落とし込みましょう。
```

**Wait for user to specify which requirements to decompose, then begin the discussion flow.**

---

## When to Use

- 確定済みの要件を開発タスクに分解する
- タスクの優先度・実行順序を決める
- タスク間の依存関係を整理する
- スプリント/フェーズごとの作業配分を決める

## Meeting Participants

### 1. **You** (Product Owner)

- タスクの優先度に関する最終決定
- スコープの確認
- 承認・却下

### 2. **PM** (Product Manager)

- ユーザー価値の観点から優先度を提案
- 「この機能はユーザーにとって先に必要」
- 「これはPhase 2に回せる」
- ビジネスインパクトの大きさを判断

### 3. **CTO** (Chief Technology Officer)

- 要件を具体的な開発タスクに分解
- 技術的依存関係を特定
- 工数見積もり
- 「これは先にDBスキーマが必要」
- 「このタスクは並行して進められる」
- References: [STRATEGY](../../docs/team/cto/STRATEGY.md)

## Meeting Flow

### Phase 1: 要件の確認 (1-2 exchanges)

REQUIREMENTS.mdから対象の要件を読み込み、スコープを確認します。

```
PM: 今回タスク化する要件はこちらです。

**要件:** [要件名]
**概要:** [技術ミーティングで確定した内容]
**受け入れ条件:** [条件リスト]
```

### Phase 2: タスク分解 (3-5 exchanges)

CTOが要件を開発タスクに分解します。

```
CTO: この要件を以下のタスクに分解します。

**タスク1:** [タスク名]
- 概要: [何をするか]
- 対象ファイル: [ファイルパス]
- 工数: [見積もり]
- 依存: [なし / タスクN]

**タスク2:** [タスク名]
...
```

PMが追加の観点を出します：

```
PM: ユーザー体験の観点から、[タスクX]はもう少し細かく分けたほうが良いと思います。
    [理由の説明]
```

### Phase 3: 優先度整理 (2-3 exchanges)

PMとCTOが協力してタスクの優先度と実行順序を決めます。

```
PM: ユーザー価値の観点から、優先度はこう考えます：
- 高: [ユーザーがすぐ必要とするもの]
- 中: [あると良いもの]
- 低: [後回しにできるもの]

CTO: 技術的な依存関係を考慮すると：
- [タスクA] → [タスクB] → [タスクC] の順で進める必要があります
- [タスクD]と[タスクE]は並行可能です
```

### Phase 4: 大株主への確認

```
### 大株主への確認

PM: 以下のタスクリストで進めてよいですか？

| # | タスク | 優先度 | 工数 | 依存 | フェーズ |
|---|--------|--------|------|------|----------|
| 1 | [名前] | 高     | [時間] | -  | Phase 1 |
| 2 | [名前] | 高     | [時間] | #1 | Phase 1 |
| 3 | [名前] | 中     | [時間] | -  | Phase 2 |

**合計工数:** [時間]
```

## タスク作成テンプレート

承認後、以下の形式でタスクを作成します：

```bash
bd create "[タスク名]" --description "[詳細説明]

対象ファイル:
- [ファイルパス1]
- [ファイルパス2]

変更内容:
- [変更1]
- [変更2]

受け入れ条件:
- [条件1]
- [条件2]

依存: [依存タスクID（あれば）]"
```

## 優先度の判断基準

| 優先度 | PM視点（ユーザー価値）         | CTO視点（技術）          |
| ------ | ------------------------------ | ------------------------ |
| 高     | ユーザーが最初に必要とする機能 | 他タスクの前提となる基盤 |
| 中     | あると体験が向上する機能       | 独立して実装可能         |
| 低     | なくても最低限動く機能         | 最適化・改善系           |

## 注意事項

1. **要件は変更しない** - タスク分解のみ行う。要件調整は`/meeting:tech`に戻る
2. **タスクは具体的に** - ファイルパス、変更内容を明確に
3. **依存関係を明示** - ブロッカーになるタスクを特定
4. **工数は正直に** - 楽観的な見積もりは避ける
5. **PRサイズを意識** - 1タスク ≈ 1PR（~300行以内）になるよう分割

## Workflow Position

```
/meeting:product (ideas) → /meeting:tech (validation) → /meeting:tasks (task decomposition) → 開発
```

This meeting is the **task decomposition step** after requirements are validated.
