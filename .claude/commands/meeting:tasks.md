# Task Decomposition & Prioritization

CPOとCTOが確定済みの要件を開発タスクに分解し、優先度を整理するミーティング。

## Quick Start

**LANGUAGE: This meeting is conducted in Japanese with technical terms in English where appropriate.**

**前提:** `/meeting:tech` で要件が技術的に検証済みであること

**When invoked, immediately start the meeting:**

```
タスク分解ミーティング開始

CPO: こんにちは、CTOさん。技術ミーティングで確定した要件をタスクに落とし込みましょう。
```

**Wait for user to specify which requirements to decompose, then begin the discussion flow.**

---

## When to Use

- 確定済みの要件を開発タスクに分解する
- タスクの優先度・実行順序を決める
- タスク間の依存関係を整理する
- スプリント/フェーズごとの作業配分を決める
- **ロードマップからの逆算で各タスクの期限を設定する**

## Meeting Participants

### 1. **You** (Product Owner)

- タスクの優先度に関する最終決定
- スコープの確認
- 承認・却下

### 2. **CPO** (Chief Product Officer)

- ユーザー価値の観点から優先度を提案
- 「この機能はユーザーにとって先に必要」
- 「これはPhase 2に回せる」
- ビジネスインパクトの大きさを判断

### 3. **CTO** (Chief Technology Officer)

- 要件を具体的な開発タスクに分解
- 技術的依存関係を特定
- 工数見積もり
- 「これは先にDBスキーマが必要」
- 「このタスクは並行して進められる」
- References: [STRATEGY](../../docs/team/cto/STRATEGY.md)

## Meeting Flow

### Phase 1: 要件の確認 (1-2 exchanges)

REQUIREMENTS.mdから対象の要件を読み込み、スコープを確認します。

```
CPO: 今回タスク化する要件はこちらです。

**要件:** [要件名]
**概要:** [技術ミーティングで確定した内容]
**受け入れ条件:** [条件リスト]
```

### Phase 2: タスク分解 (3-5 exchanges)

CTOが要件を開発タスクに分解します。

```
CTO: この要件を以下のタスクに分解します。

**タスク1:** [タスク名]
- 概要: [何をするか]
- 対象ファイル: [ファイルパス]
- 工数: [見積もり]
- 依存: [なし / タスクN]

**タスク2:** [タスク名]
...
```

CPOが追加の観点を出します：

```
CPO: ユーザー体験の観点から、[タスクX]はもう少し細かく分けたほうが良いと思います。
    [理由の説明]
```

### Phase 3: 優先度整理 (2-3 exchanges)

CPOとCTOが協力してタスクの優先度と実行順序を決めます。

```
CPO: ユーザー価値の観点から、優先度はこう考えます：
- 高: [ユーザーがすぐ必要とするもの]
- 中: [あると良いもの]
- 低: [後回しにできるもの]

CTO: 技術的な依存関係を考慮すると：
- [タスクA] → [タスクB] → [タスクC] の順で進める必要があります
- [タスクD]と[タスクE]は並行可能です
```

### Phase 4: 大株主への確認（タスク内容）

```
### 大株主への確認

CPO: 以下のタスクリストで進めてよいですか？

| # | タスク | Refs | 優先度 | 工数 | 依存 | フェーズ |
|---|--------|------|--------|------|------|----------|
| 1 | [名前] | F-XXX | 高     | [時間] | -  | Phase 1 |
| 2 | [名前] | F-YYY | 高     | [時間] | #1 | Phase 1 |
| 3 | [名前] | F-ZZZ | 中     | [時間] | -  | Phase 2 |

**合計工数:** [時間]
```

### Phase 5: 期限設定 (2-3 exchanges)

**トップダウン逆算でタスクの期限を決定します。**

#### Step 1: ロードマップ確認

CTOが `docs/design/roadmap.md` からフェーズ期限を読み込みます。

```
CTO: ロードマップのフェーズ期限を確認します。

**現在のフェーズ期限:**
- Phase 0: [開始日] - [終了日] (インフラ整備)
- Phase 1: [開始日] - [終了日] (コア機能)
- Phase 2: [開始日] - [終了日] (PDF + B2B)
- Phase 3: [開始日] - [終了日] (メッセージング + 同意書)
- Phase 4: [開始日] - [終了日] (決済基盤)
- **MVPローンチ目標:** [日付]
```

#### Step 2: タスク期限の逆算

CTOが各タスクの期限を逆算提案し、CPOがビジネス観点で調整します。

```
CTO: 依存関係とフェーズ期限から、各タスクの期限を逆算しました。

**逆算ロジック:**
1. フェーズ終了日がハード期限
2. 後続タスクが存在する場合、後続の着手日−1日がデッドライン
3. 並行可能タスクはフェーズ内で均等配分
4. クリティカルパス上のタスクは前倒し

| # | タスク | フェーズ | 期限 | 根拠 |
|---|--------|----------|------|------|
| 1 | [名前] | Phase 0 | [日付] | クリティカルパス。Phase 1全タスクが依存。 |
| 2 | [名前] | Phase 1 | [日付] | #1完了後着手。#3の前提条件。 |
| 3 | [名前] | Phase 1 | [日付] | #2完了後。並行タスクなし。 |

CPO: ビジネス観点から調整が必要な点：
- [タスクX]は[イベント/リリース日]に合わせて前倒しが必要
- [タスクY]はユーザーヒアリングの結果待ちで、期限を[日付]に後ろ倒し推奨
```

#### Step 3: 大株主の期限承認

```
CPO: 最終的な期限付きタスクリストです。

| # | タスク | Refs | 優先度 | 工数 | 依存 | フェーズ | 期限 | 根拠 |
|---|--------|------|--------|------|------|----------|------|------|
| 1 | [名前] | F-XXX | 高 | [時間] | - | Phase 0 | [日付] | [理由] |
| 2 | [名前] | F-YYY | 高 | [時間] | #1 | Phase 1 | [日付] | [理由] |

この期限で進めてよいですか？調整したい項目があればお知らせください。
```

### Phase 4.5: トレーサビリティ検証

タスクリスト確定前に以下を確認：

1. **全タスクにRefs:** 全タスクが最低1つのF-XXXを参照しているか
2. **全F-XXXにタスク:** デルタサマリー（存在する場合）の新規/変更Feature IDが全てタスクにマップされているか
3. **孤立Feature ID検出:** タスクにマップされていないF-XXXがあれば、意図的な除外か確認

```
✅ 全タスクにRefs確認済み
✅ 新規F-XXXのタスクカバレッジ確認済み
⚠️ F-XXX はPhase 2延期のためタスク化しない（理由: [理由]）
```

## タスク作成テンプレート

承認後、以下の形式でタスクを作成します。**`Refs:` 行は必須。**

```bash
bd create "[タスク名]" --description "Refs: F-XXX, F-YYY

[詳細説明]

対象ファイル:
- [ファイルパス1]
- [ファイルパス2]

変更内容:
- [変更1]
- [変更2]

受け入れ条件:
- [条件1]
- [条件2]

依存: [依存タスクID（あれば）]"
```

**CRITICAL:** 全てのタスクは最低1つのF-XXXに紐づくこと。F-XXXが存在しない基盤タスク（DBマイグレーション、インフラ設定等）は `Refs: T-N`（DESIGN_DOC.mdの技術決定ID）を使用する。

## 優先度の判断基準

| 優先度 | CPO視点（ユーザー価値）        | CTO視点（技術）          |
| ------ | ------------------------------ | ------------------------ |
| 高     | ユーザーが最初に必要とする機能 | 他タスクの前提となる基盤 |
| 中     | あると体験が向上する機能       | 独立して実装可能         |
| 低     | なくても最低限動く機能         | 最適化・改善系           |

## 注意事項

1. **要件は変更しない** - タスク分解のみ行う。要件調整は`/meeting:tech`に戻る
2. **タスクは具体的に** - ファイルパス、変更内容を明確に
3. **依存関係を明示** - ブロッカーになるタスクを特定
4. **工数は正直に** - 楽観的な見積もりは避ける
5. **PRサイズを意識** - 1タスク ≈ 1PR（~300行以内）になるよう分割
6. **期限はトップダウン** - ロードマップ → フェーズ期限 → タスク期限の順に逆算。ボトムアップの積み上げだけで決めない

## Workflow Position

```
/meeting:product (ideas) → /meeting:tech (validation) → /meeting:tasks (task decomposition + deadline setting) → 開発
```

This meeting is the **task decomposition and deadline setting step** after requirements are validated.
Deadlines are derived top-down from the roadmap (`docs/design/roadmap.md`), not bottom-up from effort estimates alone.
